Sheet 5: Trade-off phrases

The pattern: "I would pick X because of A; the cost is B; if C becomes a problem I would switch to Y."

DecisionSay it like this
SQL vs NoSQL"Postgres for orders because we need transactions and constraints; the cost is harder write scaling; if one primary is not enough, I would shard by customer ID or move hot tables to a distributed SQL store."
Kafka vs SQS"Kafka because several teams read the same events and we need replay; the cost is running partitions and consumer groups; if this were just a job queue, SQS would be simpler."
Push vs pull feed"Fan-out on write so reads are fast; the cost is expensive writes for celebrities; above a follower threshold I switch those users to pull and merge at read time."
Cache-aside vs write-through"Cache-aside because it is simple and survives cache loss; the cost is a miss after every write; if read-after-write freshness matters, write-through for that key family."
Sync vs async"Synchronous for the payment authorisation the user waits for; everything after (email, analytics, loyalty points) goes async through Kafka so a slow downstream cannot slow checkout."
Strong vs eventual"Strong consistency for inventory decrements; the cost is latency and lower availability during partitions; likes and view counts can be eventual."
Monolith vs microservices"A modular monolith first because the team is small; the cost is coupled deploys; when teams or scaling needs diverge, I would extract the part that hurts most."
Polling vs WebSockets"WebSockets for chat because both sides send often and latency matters; the cost is stateful connections; for one-way status updates SSE or long polling is simpler."
Single vs multi-region"Multi-AZ in one region meets the target; the cost is downtime if the whole region fails; if the RTO drops below an hour, add a warm standby region with async replication."
Partition count"12 partitions to cover peak throughput and 12 parallel consumers with headroom; the cost is more files and longer recovery; partitions cannot be reduced and adding them remaps keys, so I size up front."
Optimistic vs pessimistic locking"Optimistic version checks because conflicts are rare; the cost is retries; for a hot row under heavy contention I switch to an atomic update or a queue."
Deployments: canary vs blue-green"Canary because it limits the blast radius and we have good metrics; the cost is a slower rollout; for schema-coupled releases, blue-green gives an instant switch back."

Phrases that drive the round

  • "Before I draw, can I confirm the scope?"
  • "Let me assume X; tell me if that is wrong."
  • "The number that matters here is the write rate, because..."
  • "I will start simple and then fix the bottleneck."
  • "The single point of failure in this picture is..."
  • "Which would you like me to go deeper on: A or B?"
  • "To know it is healthy I would watch p99, error rate and lag."

Phrases for "I don't know"

  • "I have not used that directly; let me reason it through."
  • "What I am sure of is... so it follows that..."
  • "Is ordering per user enough, or do you need global order?"
  • "I would verify that number in the docs before relying on it."

Words that cost points

  • "It just scales." (How? What breaks first?)
  • "Kafka guarantees ordering." (Only within a partition.)
  • "Exactly once, so no duplicates." (Within Kafka; side effects need idempotency.)
  • "Kubernetes heals it." (Which controller, and how long?)
