Sheet 3: Kafka CLI and configs

Kafka 4.x runs KRaft only (no ZooKeeper). The scripts live in bin/ of the Kafka download, or /opt/kafka/bin inside the apache/kafka image. Every command needs --bootstrap-server. Learn the concepts on the Kafka track; try them in the local pipeline.

# one-broker lab (combined broker + controller, dev only)
docker run -d --name kafka -p 9092:9092 apache/kafka:4.4.0
docker exec -it kafka bash
cd /opt/kafka/bin
B=localhost:9092
JobCommand
Create a topic./kafka-topics.sh --bootstrap-server $B --create --topic orders --partitions 6 --replication-factor 1
On this one-broker lab the replication factor can only be 1 (with 3 you get "Replication factor: 3 larger than available brokers: 1"). On a real 3-broker cluster use --replication-factor 3 --config min.insync.replicas=2; try that on the 3-broker Compose stack.
Describe (leaders, ISR)./kafka-topics.sh --bootstrap-server $B --describe --topic orders
Find sick partitions./kafka-topics.sh --bootstrap-server $B --describe --under-replicated-partitions (also --unavailable-partitions)
Add partitions./kafka-topics.sh --bootstrap-server $B --alter --topic orders --partitions 12 (keys remap; never shrinks)
Produce with keys./kafka-console-producer.sh --bootstrap-server $B --topic orders --property parse.key=true --property key.separator=:
Consume from start./kafka-console-consumer.sh --bootstrap-server $B --topic orders --from-beginning --property print.key=true
--from-beginning only applies when the group has no committed offset. Without --group the tool uses a fresh random group every time, so it always re-reads. With a fixed --group, the second run starts from the committed offset: use a new group name or reset offsets to re-read.
Lag per partition./kafka-consumer-groups.sh --bootstrap-server $B --describe --group billing
Replay from a time./kafka-consumer-groups.sh --bootstrap-server $B --group billing --topic orders --reset-offsets --to-datetime 2026-11-22T00:00:00.000 --execute (group must be stopped; run without --execute to preview)
Skip to the end... --reset-offsets --to-latest --execute (also --to-earliest, --shift-by -100)
Change retention./kafka-configs.sh --bootstrap-server $B --alter --entity-type topics --entity-name orders --add-config retention.ms=86400000
Show topic configs./kafka-configs.sh --bootstrap-server $B --describe --entity-type topics --entity-name orders
Disk per partition./kafka-log-dirs.sh --bootstrap-server $B --describe --topic-list orders
Latest offsets./kafka-get-offsets.sh --bootstrap-server $B --topic orders
KRaft quorum health./kafka-metadata-quorum.sh --bootstrap-server $B describe --status

From your world

linger.ms and batch.size are interrupt coalescing: wait a little to send more at once. Consumer lag is queue depth on a ring. Key partitioning is ECMP flow hashing. The ISR is the set of standbys that are hot and in sync. Where this breaks: a Kafka partition is not a ring that overwrites - old data stays until retention deletes whole segments, which is why replay is possible.

Metrics to alert on

  • UnderReplicatedPartitions > 0 and UnderMinIsrPartitionCount > 0: a broker is slow or gone.
  • OfflinePartitionsCount > 0: an outage for those partitions.
  • ActiveControllerCount: exactly one across the cluster.
  • Request handler and network processor idle percent: low means saturated.
  • Consumer lag, ideally converted to seconds, per group and partition.
