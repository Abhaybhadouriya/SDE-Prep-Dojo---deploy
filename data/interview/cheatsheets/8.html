A pod is in CrashLoopBackOff. Which commands do you run, in what order?

kubectl get pods to confirm the status and restart count; kubectl describe pod POD for Last State (exit code, OOMKilled) and Events (probe failures, missing Secrets); kubectl logs POD --previous for the crashed run's output. Exit 137 with OOMKilled points to memory; exit 1 points to the app or its config. If the image has no shell, kubectl debug attaches an ephemeral container.

How to answer

Name the commands in order and say what you look for in each. Interviewers want evidence-first habits, not guesses.

Likely follow-ups
  • What if the previous logs are empty?
  • How do backoff delays grow?
One partition of a consumer group has huge lag; the others are near zero. What does it mean?

The consumers as a whole are fast enough, so adding consumers will not help. Either one key is hot (that partition receives far more records), or the consumer owning it is stuck on one record (a poison message, a slow external call) or is unhealthy. Check bytes-in per partition, the consumer's logs and the record at the committed offset. Fix with a better key or key salting, or with retry and dead-letter topics for poison messages.

How to answer

Contrast "all partitions lagging" (capacity) with "one partition lagging" (skew or a stuck record). The contrast is the answer.

Likely follow-ups
  • How do you look at the record at a specific offset?
How do you find out why a Docker host is out of disk?

docker system df splits usage into images, containers, local volumes and build cache. Common causes: unrotated json-file logs, old images from CI, a large build cache, and dangling volumes. Clean with docker image prune -a and docker builder prune, be careful with volumes, and prevent with log rotation (max-size, max-file) in daemon.json.

How to answer

Measure, clean safely, then prevent. Mention that deleting a container does not delete its image or named volumes.

Likely follow-ups
  • Where are container logs stored on disk?
Estimate the storage for a chat app: 50M daily users, 40 messages each per day, kept 1 year.

50M x 40 = 2B messages a day. At about 200 bytes per message with metadata, that is about 400 GB a day. A year is about 400 GB x 365, roughly 146 TB, and with 3 replicas about 440 TB. Write rate: 2B / 10^5 s = about 20k messages per second on average, perhaps 2-3x at peak. Conclusion: a horizontally scalable wide-column store partitioned by conversation, with media in object storage and only pointers in the message rows.

How to answer

State each assumption, round aggressively, and end with the design decision the numbers force.

Likely follow-ups
  • How does adding images change the estimate?
  • What is the read rate if each message is read twice?
Which Kafka defaults would you change before going to production, and why?

Replication factor 1 to 3 and min.insync.replicas 1 to 2 (durability), auto.create.topics.enable to false (typos create bad topics), a deliberate partition count instead of 1, retention per topic, and on clients: manual commits after processing instead of auto commit where duplicates or loss matter, compression (lz4 or zstd), and group.instance.id for consumers on Kubernetes to avoid rebalances on restarts.

How to answer

Group by broker, producer and consumer; give one reason each.
