Each answer is the 60-second skeleton of a full design: the key decisions and the deep dive you should steer towards. Every one links to its full design page with requirements, estimates, an animated architecture and follow-ups. Browse all of them in the design gallery.

Level 3 - Intermediate 5 questions

Design a URL shortener. What are the key decisions?

Read-heavy (redirects far outnumber creates). API: POST /urls returns a short code; GET /{code} returns a redirect. The trade-off: 301 (permanent) is cached by browsers, so there is less load on you, but you lose click analytics and cannot change the target later; 302/307 sends every click back to you, so pick 302 if analytics or editable links matter. Key generation: base62 of a unique counter or Snowflake ID (no collisions) or a random 7-character code with a uniqueness check; 62^7 is about 3.5 trillion codes. Store code to URL in a key-value store; cache hot codes in Redis and at the CDN. Analytics clicks go async to Kafka. Deep dives: collision handling, custom aliases, expiry, abuse and malicious links. Page: URL shortener.

How to answer

Start from the read/write ratio; it explains the cache-first design. Pick 302 if you need click analytics (301s get cached by browsers).

Likely follow-ups
  • How do you stop two servers generating the same code?
Design a distributed rate limiter.

Where: at the API gateway, keyed by user, API key or IP. Algorithm: token bucket for APIs (allows bursts). State: counters in Redis, updated atomically with a Lua script so check-and-decrement cannot race; keys expire automatically. At very high QPS, keep local buckets per gateway node and sync to Redis periodically (slightly approximate). Return 429 with Retry-After and rate-limit headers. Decide fail-open vs fail-closed when Redis is down (usually fail open with local limits). Page: Rate limiter.

How to answer

Ask what is being limited and how exact it must be. That decides centralised vs local counting.

Likely follow-ups
  • How do you rate-limit across multiple regions?
Design a notification system (push, SMS, email).

Services call one POST /notify API; it validates, checks user preferences and rate limits, renders templates, and enqueues to Kafka topics per channel and priority. Channel workers call providers (APNs, FCM, SMS gateways, email) with retries, backoff and provider failover; failures go to a DLQ. Idempotency keys stop duplicate sends on retries; a delivery-status store tracks sent/delivered/opened. Scheduled notifications sit in a delay store. Page: Notification system.

How to answer

Separate "decide what to send" from "send it". Discuss priority isolation so marketing blasts do not delay OTPs.

Likely follow-ups
  • How do you guarantee an OTP is never sent twice?
Design search autocomplete.

Precompute top-k completions per prefix from query logs (a batch or streaming job counting queries with time decay), store them in a trie or a prefix-to-list key-value map, and serve from memory with very low latency; cache popular prefixes at the edge. Clients debounce keystrokes. Updates roll out as new versions of the index. Filter offensive terms and personalise lightly by merging user history. Page: Autocomplete.

How to answer

Latency budget first (tens of ms per keystroke) - it forces precomputation.

Likely follow-ups
  • How do trending queries appear quickly?
Design a real-time leaderboard.

Redis sorted sets: ZINCRBY on score updates and ZREVRANK for a user's rank are O(log n); top N with ZRANGE key 0 N-1 REV WITHSCORES is O(log n + N) (ZREVRANGE is the older, deprecated form). For huge player counts, shard by game or region and merge top lists; for an approximate global rank, keep score-bucket histograms. Persist scores in a durable DB; Redis is the serving layer, rebuilt from the DB or a Kafka log on failure. Page: Leaderboard.

How to answer

Name the data structure in the first minute; then scale it.

Likely follow-ups
  • How do you show a player's rank among 100 million players?

Level 4 - Advanced 18 questions

Design WhatsApp-style chat. How do you keep ordering and durability?

Clients hold a WebSocket to a gateway; a session service maps user to gateway. Sending: the server assigns a per-conversation sequence number, persists the message (wide-column store keyed by conversation, sorted by sequence), acks the sender (one tick), then delivers to online recipients or stores it for offline delivery plus a push notification. Recipient acks advance delivered and read states. Ordering is per conversation, not global. Group chats fan out per member; large groups fan out on read. Page: Chat.

How to answer

Define the three ack states first; they drive the whole design. Then per-conversation ordering.

Likely follow-ups
  • How do you sync history across a user's multiple devices?
Design a news feed.

Write path: posts go to a posts store; a fan-out service pushes post IDs into followers' feed caches (Redis lists), except for celebrities whose posts are pulled at read time. Read path: fetch cached IDs, merge celebrity posts, rank, hydrate post details from cache, paginate with a cursor. Kafka carries post events to fan-out workers, ranking features and notifications. Media is in object storage behind a CDN. Page: News feed.

How to answer

Push vs pull with the celebrity case is the core deep dive; get there quickly.

Likely follow-ups
  • How do you handle a user who follows 5,000 accounts?
Design ride hailing (Uber/Ola). How do you find nearby drivers?

Drivers send location every few seconds to a location service that keeps the latest position in memory (Redis GEO or an in-memory geo index by geohash/H3 cell), not in the primary DB. A rider request queries the rider's cell plus neighbours, filters available drivers, ranks by ETA, and offers the trip to one driver at a time with a timeout. Trip state lives in a strongly consistent store; location streams go through Kafka for ETA, surge pricing and analytics. Page: Ride hailing.

How to answer

Estimate the location write rate first (drivers x updates per second); it forces the in-memory design.

Likely follow-ups
  • How do you stop two riders being matched to the same driver?
Design food delivery (Swiggy/Zomato).

Three sides: customer, restaurant, delivery partner. Catalogue and menu served from cache and a search index with geo filters. Order service runs a state machine (placed, accepted, preparing, picked up, delivered) with events on Kafka. Dispatch assigns a nearby partner using a geo index and predicted food-ready time. Payment uses idempotency keys. Live tracking streams partner location over WebSockets. Peak lunch and dinner spikes need autoscaling and surge logic. Page: Food delivery.

How to answer

Use the order state machine as your backbone; every service reacts to its events.

Likely follow-ups
  • How do you predict when food will be ready?
Design e-commerce checkout.

Cart service (per-user, can be eventually consistent) then checkout: price and promotion validation, inventory reservation with a TTL, payment with an idempotency key, then order confirmation. Coordinate as a saga: if payment fails, release the reservation; if confirmation fails after payment, refund. The order DB is relational (transactions and constraints). The outbox publishes OrderPlaced to Kafka for fulfilment, email and analytics. Page: Checkout.

How to answer

Walk the happy path, then each failure with its compensation.

Likely follow-ups
  • What if the user clicks "Pay" twice?
Design inventory management for many stores and warehouses.

Stock per (SKU, location) in a relational store; changes recorded as events (received, reserved, picked, sold, returned). Reservations at checkout with TTL; the available count is on-hand minus reserved. Store systems and warehouses publish events through Kafka; a projection keeps a fast read model for "available near me" in a cache. Handle oversell risk with atomic conditional updates and periodic reconciliation against physical counts. Page: Inventory.

How to answer

Distinguish on-hand, reserved and available - interviewers like the precision.

Likely follow-ups
  • How do you handle a store that goes offline for an hour?
Design video streaming (Netflix).

Upload and transcode offline into many bitrates and resolutions, split into short segments with a manifest (HLS/DASH). Segments are served from a CDN close to users (Netflix uses its own Open Connect appliances inside ISPs, filled during off-peak hours). The player uses adaptive bitrate: it measures throughput and buffer and switches quality per segment. Control plane (catalogue, auth, recommendations, playback licences) runs in the cloud; playback events stream to Kafka for analytics. Page: Streaming.

How to answer

Split control plane from data plane - a networking person's natural framing.

Likely follow-ups
  • How does the player choose a bitrate?
Design YouTube upload and transcoding.

Resumable chunked uploads directly to object storage via pre-signed URLs. An upload-complete event goes to a queue; a DAG of jobs (validate, transcode to multiple renditions in parallel chunks, thumbnails, captions, content checks) runs on a worker fleet, often Kubernetes Jobs that scale with queue depth. Metadata and processing status in a DB; when renditions are ready, publish and warm the CDN for popular videos. Page: YouTube upload.

How to answer

Parallelise by splitting the video into chunks; that is the main scaling idea.

Likely follow-ups
  • How do you retry a failed transcode step without redoing everything?
Design ticket booking (BookMyShow). Optimistic or pessimistic locking?

Seat map per show. When a user selects seats, create a hold with a short TTL (say 5-10 minutes) using a conditional insert or a row lock so two users cannot hold the same seat; payment must finish before the hold expires; then confirm the booking. Optimistic version checks suit normal shows; for hot launches add a waiting room and queue users. Holds expire automatically and seats return. Page: Ticket booking.

How to answer

Explain the hold-then-confirm two-phase flow and justify the TTL.

Likely follow-ups
  • What if the payment succeeds just after the hold expired?
Design a web crawler.

A URL frontier with priority and per-host politeness queues; fetchers respect robots.txt and rate limits per domain; DNS caching; parsers extract links; a "seen" check (Bloom filter plus a store) avoids revisits; content dedup by hash; storage in object storage with metadata in a DB. Partition the frontier by host hash so one worker owns a host's politeness. Re-crawl by change frequency. Page: Web crawler.

How to answer

Politeness and dedup are the two deep dives; mention traps (infinite calendars).

Likely follow-ups
  • How do you handle a site that changes every minute?
Design a distributed cache (like Redis Cluster) with LRU.

Each node: a hash map plus a doubly linked list for O(1) get, put and eviction. Cluster: partition keys with consistent hashing or fixed hash slots; replicate each partition to a follower for failover; clients learn the slot map and go direct. Deep dives: hot keys (local caches, key replication), eviction policy, TTL expiry, cache stampede protection, and what consistency the cache promises. Page: Distributed cache.

How to answer

Do the single-node data structure quickly, then spend time on partitioning and failover.

Likely follow-ups
  • What happens to in-flight writes during failover?
Design a metrics and monitoring system (Prometheus-like).

Agents scrape or receive metrics; a write path ingests into a time-series database (compressed chunks by series, sharded by series hash); downsampling and retention tiers; a query engine with aggregation; an alert evaluator running rules and routing to on-call with deduplication and silencing. The big risk is cardinality (labels like user ID explode series counts) - enforce limits. Page: Metrics.

How to answer

Name cardinality early; it is what breaks these systems.

Likely follow-ups
  • How do you monitor the monitoring system?
Design Dropbox / file sync.

Split files into chunks (for example 4 MB), hash each chunk, and upload only chunks the server does not have (dedup, resumable). A metadata service stores file trees, versions and chunk lists in a consistent DB. Blocks go to object storage. Clients learn about changes through a notification channel (long poll or WebSocket) and pull deltas. Conflicts create "conflicted copy" files. Page: File sync.

How to answer

Chunking plus content hashing is the key idea; everything follows from it.

Likely follow-ups
  • How do you sync a 10 GB file that changed by one byte?
Design a distributed job scheduler.

Jobs stored with next-run time in a DB indexed by time; scheduler nodes poll due jobs in partitions (or use a time-bucketed queue), claim each with a lease (conditional update) so only one node runs it, and push to worker queues. Workers report status; retries with backoff; idempotent jobs because a lease timeout can cause a second run. Support cron schedules, priorities and per-tenant limits. Page: Job scheduler.

How to answer

Exactly-once execution is impossible to guarantee; say "at least once plus idempotent jobs".

Likely follow-ups
  • How do you run a million jobs scheduled for exactly midnight?
Design a CDC pipeline from Postgres to a data lake.

Debezium reads the WAL through a logical replication slot and publishes change events to Kafka topics per table; a schema registry tracks schemas; a sink (Kafka Connect or Flink) writes to a lakehouse table format with upserts using primary keys and the source LSN for ordering. Monitor replication-slot lag and WAL size, handle schema changes, and use an initial snapshot for backfill. Page: CDC pipeline.

How to answer

Lead with the replication-slot risk; it shows production experience.

Likely follow-ups
  • How do you handle a column type change upstream?
Design trending topics / top-K heavy hitters.

Stream hashtags through Kafka; a stream processor counts per sliding window with a Count-Min Sketch (fixed memory, small overestimates) plus a min-heap of the current top K per partition; a merger combines partition top lists into a global top K every few seconds. Apply time decay so old spikes fade. Exact counts come from batch jobs later. Page: Trending topics and Top-K.

How to answer

Explain why exact counting of every key is too expensive, then the sketch plus heap.

Likely follow-ups
  • Why can you not just merge each partition's top 10 to get a global top 10 exactly?
Design a CI/CD platform on Kubernetes.

Git webhooks enqueue pipeline runs; a controller schedules each step as a pod (Tekton-style or Jobs) with resource limits, caches (build cache, dependency cache) on persistent volumes or a remote cache, and secrets from a vault. Artifacts are pushed by digest to a registry; deployment is GitOps (Argo CD) with canary analysis. Scale runners with the queue length, isolate untrusted builds (separate nodes or sandboxed runtimes). Page: CI/CD platform.

How to answer

Treat each build as a short-lived, isolated pod; the hard parts are caching and isolation.

Likely follow-ups
  • How do you stop a malicious PR from stealing secrets?
Design an Amazon Locker style pickup system.

Lockers have compartments by size per location. At checkout, find nearby lockers with a free compartment of the right size and reserve it with a TTL until delivery; on delivery, the courier's scan marks it occupied and generates an OTP for the customer; pickup frees it; expiry after N days triggers return. Compartment state transitions need atomic updates; the locker device syncs with a central service and works offline with cached codes. Page: Locker pickup.

How to answer

Model the compartment state machine; it is the heart of the design.

Likely follow-ups
  • What happens if the locker loses connectivity?

Level 5 - Interview-ready 7 questions

Design a flash sale (Big Billion Days style) for a limited stock item.

Protect the core: static content on the CDN, a virtual waiting room or token gate at the edge, and aggressive rate limiting. Inventory for the hot SKU lives in Redis with an atomic decrement (Lua script); a successful decrement grants a time-limited purchase token, and orders are written asynchronously through Kafka into the order DB. Reservations expire and stock returns if payment does not complete. Pre-scale everything; autoscaling is too slow for a cliff. Reconcile Redis against the DB after the sale. Page: Flash sale.

How to answer

Say "the hard part is one hot row" in the first minute. Then show how you move contention off the database.

Likely follow-ups
  • How do you stop bots?
Design a payment system.

API with mandatory idempotency keys; a payment state machine (created, authorised, captured, refunded, failed); calls to external processors with timeouts and retries that reuse the same key; a double-entry ledger (every movement is a debit and a credit that sum to zero) in a strongly consistent relational DB; asynchronous webhooks from processors handled idempotently; daily reconciliation against processor reports. Never lose a record: outbox for events, audit logs, encryption and PCI scope reduction via tokenisation. Page: Payments.

How to answer

Correctness over latency: lead with idempotency and the ledger.

Likely follow-ups
  • A processor times out - did the charge happen? What do you do?
Design a message queue (Kafka itself).

Partitioned append-only logs on brokers, segment files with sparse indexes, replication with leader, followers and ISR, a metadata quorum for leadership, producers batching by partition key, consumer groups with a coordinator and committed offsets, retention and compaction, zero-copy reads. Deep dives: durability settings, rebalancing, ordering, and delayed messages. Page: Message queue, plus the Kafka track.

How to answer

Build it layer by layer, each layer solving one scaling or failure problem.

Likely follow-ups
  • How would you support per-message acknowledgement?
Design an ad click aggregator.

Clicks arrive at an ingestion API, are validated and deduplicated (click ID), and written to Kafka. A Flink job aggregates counts per ad per minute with event-time windows and watermarks, writing to an OLAP store for dashboards. Raw events also land in a data lake; a batch job recomputes exact counts for billing and reconciles. Fraud filtering runs in the stream. Idempotent writes keyed by (ad, window). Page: Ad clicks.

How to answer

Separate "fast approximate for dashboards" and "exact for billing".

Likely follow-ups
  • How do you handle a click that arrives 2 hours late?
Design a collaborative editor (Google Docs). OT or CRDT?

Clients send operations over WebSockets to a document session server. OT (operational transformation) with a central server ordering operations is the classic approach. CRDTs let replicas merge without a central order, good for offline and peer-to-peer, at the cost of metadata size. Store an operation log plus periodic snapshots; presence and cursors over the same socket; one server owns each active document. Page: Collaborative editor.

How to answer

Compare OT and CRDT on central server need, offline support and complexity, then pick one.

Likely follow-ups
  • How do you handle a user editing offline for an hour?
Design a stock-broking price alert system.

Price ticks stream in through Kafka partitioned by symbol. For each symbol, keep users' alert thresholds in sorted structures (one for "above", one for "below"); each tick checks only the boundary: all thresholds crossed since the last price fire. Fired alerts go to the notification system with dedup so an alert fires once. Alerts are stored durably and loaded into the in-memory index by symbol partition. Page: Price alerts.

How to answer

The sorted-threshold trick turns a scan of millions of alerts into a range query; say it early.

Likely follow-ups
  • How do you handle a symbol with millions of alerts?
Design real-time fraud detection.

Transactions go through a low-latency scoring path: features from an online feature store (recent counts per card, device, location computed by a streaming job on Kafka), a rules engine plus an ML model, and a decision (approve, challenge, block) within a strict latency budget. Async paths retrain models and investigate cases. Fail-safe policy if the scorer is down. Page: Fraud detection.

How to answer

Split the synchronous scoring path from asynchronous learning; state the latency budget.

Likely follow-ups
  • How do you compute "transactions in the last 10 minutes" per card in real time?
