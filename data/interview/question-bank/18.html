Cloud, IaC, CI/CD and SRE questions (30)

AWS networking and compute, Terraform, Git and pipelines, on-call and cost, plus two HLD concepts (bot defense, recommendations). Two of the best questions from each page; every page has more in its own interview section.

AWS and cloud 10 questions

From: devops-aws-01, devops-aws-02, devops-aws-03, devops-aws-04, devops-aws-05

What makes a subnet public versus private in AWS?

Only its route table. A public subnet's table has 0.0.0.0/0 -> internet gateway; a private subnet's default route points to a NAT gateway (or nothing). Resources in a public subnet also need a public IPv4 or Elastic IP to be reachable, and their security group must allow the traffic. Private resources can make outbound connections through NAT but cannot accept inbound connections from the internet.

How to answer

Lead with "it is the route, not a flag". Then the three things inbound access needs: IGW route, public IP, security group rule. Mention isolated subnets for databases.

Likely follow-ups
  • Can an instance in a public subnet without a public IP reach the internet? (No: the IGW has nothing to translate it to. It needs a public IP or a NAT gateway.)
  • What happens to unassociated subnets? (They use the main route table.)
How would you plan CIDR ranges for a company with 3 environments in 2 regions that will also connect to an on-prem network?

Start from a company-wide plan, not per VPC. Reserve a big private block (for example 10.0.0.0/8), carve it hierarchically: per region a /12, per environment a /16 (prod, staging, dev), and keep the on-prem ranges out of it. Inside each /16: three public /20s, three large private /19s (pods consume IPs with the VPC CNI) and three data /22s, leaving spare space. No two VPCs overlap, so peering, Transit Gateway and VPN routing all work, and each region can be summarised. Track allocations in AWS VPC IPAM so new accounts get the next free block automatically.

How to answer

Say "non-overlapping and hierarchical" in the first sentence. Show the maths for one /16. Mention growth (secondary CIDRs, 100.64.0.0/10 for pods, IPv6) and the 5 reserved IPs.

Likely follow-ups
  • Two acquired companies both use 10.0.0.0/16. Options? (Re-IP one side, or use private NAT gateways / PrivateLink to expose only specific services across the overlap.)
  • Why not just make every VPC a /16 of 10.0.0.0? (They would all overlap.)
What is the difference between a security group and a network ACL?

A security group is a stateful firewall attached to an ENI (so per instance or load balancer node). It has allow rules only, all rules are evaluated together, replies to allowed traffic are automatically allowed, and it can reference other security groups. A network ACL is stateless and attached to a subnet: numbered allow and deny rules evaluated in order, first match wins, and return traffic (ephemeral ports 1024-65535) must be allowed explicitly. Security groups are the primary control; NACLs are coarse guard rails, mostly for explicit denies.

How to answer

Four contrasts in one breath: where (ENI vs subnet), state (stateful vs stateless), rules (allow vs allow+deny), evaluation (all vs ordered). Then when you would use each.

Likely follow-ups
  • How do you block one attacker IP immediately? (NACL deny with a low rule number; SGs cannot deny, and SG changes do not cut tracked connections.)
  • Why reference SGs instead of CIDRs? (Membership changes automatically as the ASG scales.)
How does an Auto Scaling Group decide to add instances? Compare target tracking and step scaling.

Scaling policies watch CloudWatch metrics aggregated over the group and change desired capacity; the ASG then launches or terminates to match, within min and max. Target tracking works like a thermostat: you set a target (say 50 % CPU or 1,000 requests per target) and AWS creates the alarms and computes proportional changes. Step scaling uses alarms you define and step adjustments by breach size, giving finer control for spiky loads. AWS recommends target tracking with a metric that is inversely proportional to capacity. Add scheduled scaling for known peaks and predictive scaling for regular cycles.

How to answer

Explain the loop (metric, alarm, desired, launch), then the policy types, then the metric choice rule and warmup.

Likely follow-ups
  • Two policies fire at once - which wins? (The one giving the larger capacity.)
  • How do you scale on memory? (CloudWatch agent custom metric.)
Is S3 a filesystem? What is the difference between a bucket, a key and a prefix?

No. S3 is a flat key-value object store with an HTTP API. A bucket is a Region-scoped, globally named container; a key is the full string name of an object; a prefix is just the leading part of keys that the console and LIST calls use to simulate folders. There is no rename and no partial overwrite: PUT replaces the whole object atomically, and "moving a folder" is copy + delete of every object. Since 2020 reads after writes and lists are strongly consistent.

How to answer

Say "flat key-value store" in the first sentence, then the consequences (no rename, whole-object PUT, prefixes for listing and request-rate scaling).

Likely follow-ups
  • How does S3 scale request rate? (Per prefix: at least 3,500 writes and 5,500 reads per second each.)
IAM policy vs bucket policy - when do you need which? What changes for cross-account access?

An IAM policy is attached to a principal and says what it can do everywhere; a bucket policy is attached to the bucket and says who can do what to it. Within one account, an allow in either is enough and an explicit deny in either wins. Cross-account, both sides must allow: the other account's IAM policy lets its role call S3, and our bucket policy names that role (or account) as a principal. If the bucket uses SSE-KMS, the KMS key policy must allow it too - a third gate people forget. Use bucket policies for guard rails (deny non-TLS, require VPC endpoint, require encryption) because they apply to everyone.

How to answer

Describe the evaluation order: explicit deny, then any allow, else implicit deny. Then the cross-account "both must allow" rule and the KMS gotcha.

Likely follow-ups
  • What does Block Public Access do that a policy cannot? (It overrides any policy or ACL that would grant public access, at account level too.)
What are an ECS task definition, a task and a service? Map them to Kubernetes.

A task definition is a versioned, immutable blueprint (images, CPU/memory, ports, env and secrets, IAM roles, log config, network mode) - like a pod spec. A task is a running instance of it - like a pod. A service keeps a desired count of tasks running, replaces unhealthy ones, rolls out new revisions with min/max percent and a circuit breaker, and registers tasks in a load balancer target group - like a Deployment plus a Service, with Service Auto Scaling playing the HPA's role.

How to answer

Three nouns, three Kubernetes equivalents, then one ECS-specific detail (task role vs execution role) to show hands-on knowledge.

Likely follow-ups
  • What does minimumHealthyPercent=100, maximumPercent=200 mean during a deploy?
Fargate vs EC2 launch type: what do you gain and what do you give up?

Fargate removes node management: no AMIs, patching, instance sizing, bin-packing or cluster scaling, and each task gets its own isolation boundary (Firecracker microVMs). You pay per task vCPU and GB-second. You give up host access (no privileged containers, DaemonSets, GPUs, custom kernels or sysctls beyond the allowed set), shared image caching (each task pulls its image), and usually some cost efficiency at large steady scale compared with well-packed EC2 on Savings Plans or Spot. Rule of thumb: Fargate for small teams and spiky or modest services; EC2 for large steady fleets and special hardware.

How to answer

Frame it as a responsibility line: "what is mine vs AWS's", then cost and limits.

Likely follow-ups
  • How is a Fargate task isolated from another customer's task?
  • How would you run a logging agent on Fargate? (Sidecar or FireLens, since there are no DaemonSets.)
Design a pipeline that detects SSH brute force attempts from EC2 auth logs in near real time.

The CloudWatch agent ships /var/log/secure to a log group. A subscription filter matches "Failed password" lines and invokes a Lambda. The Lambda decodes the gzip payload, counts failures per source IP, emits an EMF metric, and publishes an SNS alert above a threshold. For cross-batch counting (failures spread over minutes), keep counters in DynamoDB with a TTL, or emit per-IP metrics and let a CloudWatch alarm do the windowing. Failures go to an on-failure destination; the function has reserved concurrency so a storm cannot starve other functions.

How to answer

Draw source, filter, function, sinks; then say the three production words: idempotency, failure destination, concurrency cap. Mention that a pure metric filter plus alarm could do the simple version with no code.

Likely follow-ups
  • The volume grows 50x. What changes? (Subscription to Kinesis or Firehose first, then Lambda via ESM, or a container consumer.)
  • How do you avoid alert floods? (Dedup per IP per window.)
What are the Lambda invocation models, and how does error handling differ between them?

Synchronous: the caller waits and handles errors itself. Asynchronous (S3, SNS, CloudWatch Logs, EventBridge): Lambda queues the event, retries twice on function errors, keeps throttled events up to 6 hours, then sends failures to an on-failure destination or DLQ. Event source mapping (Kinesis, DynamoDB Streams, Kafka, SQS): a poller reads batches and invokes synchronously; for streams the poller retries (by default until the record expires), for SQS the message returns after the visibility timeout and the queue's redrive policy moves it to a DLQ.

How to answer

Use a three-row table in words: who holds the event, who retries, where failures go.

Likely follow-ups
  • Destination vs DLQ? (Destinations carry response and error details and support more targets; a DLQ holds only the payload.)

Terraform / IaC 6 questions

From: devops-tf-01, devops-tf-02, devops-tf-03

What is Infrastructure as Code, and why declarative rather than scripts?

IaC means infrastructure is defined in version-controlled files and created by a tool, not by hand. Declarative IaC (Terraform, CloudFormation) describes the end state; the tool computes the actions. That gives idempotency (re-running changes nothing), a reviewable diff before any change (plan), reproducible environments (dev and prod from the same code), easy teardown in the right order, and an audit trail in Git. Imperative scripts describe steps, so every change and every "already exists" case needs new code.

How to answer

Define it in one sentence, then give three concrete benefits (reproducible, reviewable plan, idempotent). Close with a real pain it removed, such as "dev and prod VPCs were built by hand and had different route tables".

Likely follow-ups
  • Terraform vs CloudFormation vs Pulumi?
  • What does idempotent mean here?
  • What still needs to be imperative (data migrations, one-off scripts)?
Walk me through what happens on terraform init, plan and apply.

init reads required_providers, downloads provider plugins (respecting .terraform.lock.hcl), downloads modules and configures the backend. plan loads config and state, refreshes state by reading each real object through the provider, builds the dependency graph, and diffs desired vs actual into a list of create/update/replace/delete actions. Nothing changes. apply executes a plan (a saved one, or a fresh one after confirmation), walking the graph with up to 10 parallel operations and writing state as resources complete.

How to answer

One line per command, then mention "in CI we save the plan with -out and apply that exact file after review".

Likely follow-ups
  • What does refresh do and when can you skip it (-refresh=false)?
  • What happens if apply fails halfway? (State records what succeeded; fix and re-apply.)
What is the Terraform state file and why does Terraform need it?

It is a JSON record that maps every resource address in the config (aws_vpc.main) to the real object's ID (vpc-0a1b2c3d) and caches its attributes. Terraform needs it to know which real objects it owns, to compute diffs, to remember dependencies for deleting resources that are no longer in config, and to speed up large plans. Without it, Terraform cannot tell its objects from anyone else's.

How to answer

Lead with "mapping config to real-world IDs", then name the other three purposes (metadata/dependencies, performance, team sync). Finish with what happens if it is lost.

Likely follow-ups
  • What are serial and lineage?
  • Why not just query the cloud by tags every time?
How would you set up Terraform state for a team on AWS?

An S3 backend: a dedicated bucket per environment (ideally per AWS account), versioning on, SSE-KMS with a customer-managed key, Block Public Access, a bucket policy denying non-TLS, and locking via use_lockfile = true (or a DynamoDB table with a LockID key on older Terraform). One state key per stack per environment. Write access to prod state only for the CI role assumed via OIDC; humans read-only. CloudTrail data events on the bucket. The bucket itself is created by a small bootstrap config and protected with prevent_destroy.

How to answer

Structure as storage, locking, security, layout. Mention the DynamoDB deprecation to show you are current.

Likely follow-ups
  • How do you bootstrap the bucket?
  • HCP Terraform vs self-managed S3?
  • How do other stacks read this stack's outputs?
What is a Terraform module, and what makes a module good?

A module is a folder of Terraform files with input variables, resources and outputs. The folder you run Terraform in is the root module; it calls child modules with module blocks. A good module does one job (a VPC, an EKS cluster, a service behind a load balancer), exposes a small set of typed, validated inputs with sensible defaults, outputs everything a caller needs (ids, ARNs, DNS names), does not declare providers itself, and does not hard-code environment names. It is versioned with semantic tags and has automated checks (fmt, validate, tflint, ideally terraform test). Wrapping a single resource just to rename arguments is an anti-pattern.

How to answer

Definition in one line, then the "good module" checklist, then one concrete example from your experience (a VPC module with CIDR and AZ inputs and subnet-id outputs).

Likely follow-ups
  • Why should child modules not configure providers?
  • How do you test a module?
  • When is a module too big?
How do you version and roll out a shared module used by many teams?

Put modules in a repo (or a private registry), release them with semver tags, and have every caller pin a version: version = "~> 2.3" for registry sources, ?ref=v2.3.0 for Git sources (the version argument does not work for Git). Breaking changes bump the major version and come with a changelog and upgrade notes. Callers upgrade by bumping the pin in a PR and reviewing the plan; dev first, then staging, then prod. Renovate or Dependabot can open those PRs. Note that the dependency lock file pins providers, not modules, so module constraints must be tight.

How to answer

Treat it as library release management: semver, pinning, changelog, staged promotion. Mention the lock-file gotcha; it shows real experience.

Likely follow-ups
  • What does ~> mean exactly?
  • A team pinned ?ref=main. What can go wrong?
  • How do you deprecate an input?

Git and CI/CD 6 questions

From: devops-cicd-01, devops-cicd-02, devops-cicd-03

What is the difference between git merge and git rebase?

Both integrate changes from one branch into another. Merge creates a merge commit with two parents (or fast-forwards), keeps all existing commits and their hashes, and records when branches joined. Rebase replays your commits as patches on top of the other branch, producing new commits with new hashes and a linear history. Merge is safe anywhere; rebase rewrites history, so only use it on commits nobody else has built on.

How to answer

Draw the graph before and after for both. Then state the golden rule and your team policy (rebase locally, squash or rebase-merge PRs).

Likely follow-ups
  • Why do rebased commits get new hashes? (The parent is part of the hashed content.)
  • What does --force-with-lease protect against, and why add --force-if-includes? (A teammate's push you have not fetched. After a fetch, a bare lease passes anyway; --force-if-includes also requires that the remote tip is in your local history.)
What is the golden rule of rebasing, and what goes wrong if you break it?

Do not rebase commits that exist outside your own repository and that others may have based work on. If you rebase a shared branch and force-push, everyone else still has the old commits. When they pull, git sees two different histories with the same changes, so they get duplicate commits or conflicts, and if they force-push back, your rewrite or their work can be lost.

How to answer

Explain via hashes: same change, different commit IDs, so git cannot tell they are the same.

Likely follow-ups
  • How do you recover a teammate's branch after someone force-pushed over it? (Their local reflog, or the old SHA from CI logs or the PR timeline.)
Walk me through the Maven build lifecycle. What does "mvn deploy" actually do?

Maven has three lifecycles: clean, default and site. The default lifecycle's main phases are validate, compile, test, package, verify, install, deploy. Asking for a phase runs every earlier phase first. Plugins bind goals to phases: compiler to compile, Surefire to test, jar to package, Failsafe around verify. So mvn deploy compiles, runs unit tests, packages, runs integration tests and checks, installs the artifact into the local ~/.m2, and finally uploads the jar and pom to the remote repository named in distributionManagement, using credentials from settings.xml.

How to answer

Say "phases are cumulative" in the first sentence, list the seven phases, then contrast install (local) with deploy (remote). Mention you use verify for PRs.

Likely follow-ups
  • Difference between a phase and a goal? (A goal is a plugin task; a phase is a slot goals bind to.)
  • How does Maven resolve two versions of one dependency? (Nearest wins; use dependencyManagement.)
What does "build once, deploy many" mean, and why is it important?

Each commit is built and tested once, producing one immutable artifact (a release version in Nexus, an image digest in a registry). Every environment gets that same artifact; only configuration differs and is injected at deploy time. This guarantees what you tested is what you ship, gives exact traceability from production back to a commit, and makes rollback a pointer change instead of a rebuild. Rebuilding per environment lets floating inputs (base images, transitive deps, compilers) drift between staging and production.

How to answer

Definition, then the three benefits (fidelity, traceability, fast rollback), then one concrete mechanism: "we deploy images by digest and the release repo forbids redeploy".

Likely follow-ups
  • How do you handle environment-specific config? (Env vars, ConfigMaps, secrets manager; never baked into the image.)
  • What about a hotfix? (New commit, new version, same pipeline; never patch an existing artifact.)
How do you rename a column in a live database with zero downtime?

Never in one step, because during any rollout the old and new app versions share the database. Use expand-migrate-contract: (1) add the new nullable column; (2) release an app that writes both columns in one statement but still reads the old one; (3) once that is fully rolled out, backfill old rows in small, throttled, idempotent batches and verify the count of missing values is zero; (4) release an app that reads the new column, behind a flag, still writing both; (5) release an app that writes only the new column, wait a bake period, then drop the old column. Each step is its own release, and every step except the final drop can be rolled back by deploying the previous app version.

How to answer

Start with "old and new code run together", then the five steps, then say where rollback stops being free. Draw the release table if there is a whiteboard.

Likely follow-ups
  • Why backfill only after dual write is fully rolled out?
  • How do you backfill 500 million rows without hurting production?
  • How do you make the new column NOT NULL safely?
Compare rolling, blue-green and canary deployments.

Rolling replaces instances in batches: cheap, slow-ish rollback, and both versions run during the rollout. Blue-green keeps two full environments and switches the router in one step: instant rollback, roughly double infrastructure during the release, and both stacks still share the database. Canary sends a small share of real traffic to the new version and grows it while metrics stay healthy: smallest blast radius and fast rollback, but needs good metrics, automated analysis and a traffic-splitting layer, and both versions run for a long time. In all three, the schema must be compatible with both versions.

How to answer

Use the same four axes for each: cost, rollback speed, blast radius, compatibility window. End with when you pick each (canary for high-traffic services with good observability; blue-green for systems that need instant cut-over like payments).

Likely follow-ups
  • What metrics decide a canary? (Error rate, p99 latency, saturation, business KPIs vs baseline.)
  • How do you do canary on Kubernetes? (Argo Rollouts, Flagger, Gateway API weights, mesh.)

On-call, incidents and cost 4 questions

From: devops-sre-01, devops-sre-02

How would you set up on-call for a new team of 7 engineers?

Weekly primary and secondary rotation, handed off on a weekday morning with a written handoff note. Escalation: primary paged, secondary after 5 minutes without ack, engineering manager after another 10. Only symptom-based, actionable alerts page (SLO burn rates on the key user journeys); everything else becomes a ticket or a dashboard. Every paging alert links to a runbook. New joiners shadow, then reverse-shadow, before going solo. I would track pages per shift and review noisy alerts weekly, aiming for no more than a couple of incidents per shift as Google's SRE book suggests. With 7 people on one site, each is primary about one week in seven; if night pages are frequent, I would split shifts or partner with a team in another time zone for follow-the-sun. Comp time after rough nights.

How to answer

Cover rotation, escalation, what pages, runbooks, onboarding, load measurement and humane policies. Numbers (5-minute ack, 2 incidents per shift) show you know the reference material.

Likely follow-ups
  • What if the team gets 20 pages a week?
  • Should developers be on call for their own services?
What should page a human, and what should not?

A page must be urgent, actionable and tied to user impact, now or very soon. So I page on symptoms: SLO burn-rate alerts on availability and latency of user journeys, plus a few "about to hurt" conditions like a disk that will be full in two hours. I do not page on causes such as high CPU or a single pod restart; those go to dashboards, or to tickets when they need attention within days. Slow budget burns are tickets. Alertmanager-style routing sends severity=page to the pager and the rest to a chat or ticket queue, with inhibition so one regional failure does not trigger fifty pages. Any alert that pages and turns out not actionable gets fixed or deleted in the weekly review.

How to answer

State the three-part rule, then symptoms vs causes, then give two examples of each side, then mention noise review. Linking to error budgets earns points.

Likely follow-ups
  • How do you alert on a low-traffic service?
  • What is a multi-window burn-rate alert?
Our AWS bill doubled in six months but traffic grew only 20%. How do you investigate?

Start with attribution, not guessing. In Cost Explorer, group by service, then by account and by the team or service tag, and compare month over month to find the top movers. Check untagged spend; if it is large, the first fix is tagging. For each top mover, drill into usage type: is it instance-hours (more or bigger instances), EBS GB-months, NatGateway-Bytes, cross-AZ DataTransfer-Regional-Bytes, or a new managed service? Then compare against unit cost (cost per 1,000 requests or per order) to separate healthy growth from waste. Typical findings: autoscaling floors raised during an incident and never lowered, a new service with inflated requests, S3 traffic through a NAT, logs with no retention, dev environments running 24/7.

How to answer

Show a method: allocate, find top movers, drill into usage type, normalise by a business metric, then fix the biggest items first. Mention that you would add budgets and anomaly alerts so it is caught next time.

Likely follow-ups
  • How do you split shared costs like the EKS cluster?
  • What is a good unit cost metric for an e-commerce site?
Savings Plans or Reserved Instances? How much would you commit?

For EC2 compute I default to Savings Plans: a Compute Savings Plan (up to 66% off) follows the workload across instance families, Regions, Fargate and Lambda, so it survives a migration to Graviton or containers; an EC2 Instance Savings Plan (up to 72%) is cheaper but locked to one family in one Region. Reserved Instances still make sense for services billed by RI (for example some database engines) and when I need a capacity guarantee in a specific AZ, which only a zonal RI or a capacity reservation gives. For the amount: right-size first, then look at hourly usage for 30-60 days and commit to the steady floor, not the average, so utilisation stays near 100%. Buy in small slices each month or quarter (laddering) so commitments expire at different times and I can adjust as the architecture changes.

How to answer

Name the flexibility vs discount trade-off, the "commit to the floor" rule, and the two metrics: coverage and utilisation.

Likely follow-ups
  • What happens if usage drops below the commitment?
  • Do Savings Plans guarantee capacity?
  • 1-year or 3-year, and why?

Edge defense and recommendations (HLD) 4 questions

From: hld-18, hld-19

How does a reCAPTCHA Enterprise-style system tell bots from humans without showing a puzzle?

It runs a script that collects signals passively while the user browses: device and browser environment, consistency between claimed and real browser, interaction behaviour, and network context. On a sensitive action it issues a token bound to that action. The site's backend sends the token to the risk service, which combines those signals with what it sees across many sites and returns a score (0.0 to 1.0, higher is safer) plus reason codes. The site applies its own policy per action: allow, add friction like OTP, or block. Puzzles become a fallback for uncertain cases rather than a gate for everyone, which keeps friction low for real users.

How to answer

Signals, token bound to an action, server-side assessment, score plus reasons, policy per action. Stress that the decision is yours.

Likely follow-ups
  • How do you choose thresholds?
  • How would you handle a mobile app?
WAF vs rate limiter vs bot management: why do you need all three?

They catch different things. A WAF inspects one request for malicious content (SQL injection, XSS, path traversal, bad inputs) and enforces simple lists (IP, geo). A rate limiter counts requests per key over time and caps volume, protecting capacity and fairness. Bot management decides whether the client is automated, using fingerprints, challenges and behaviour, which catches valid-looking requests made by scripts at polite rates, like credential stuffing from residential proxies. A credential-stuffing request passes the WAF (it is a valid login) and may pass a per-IP limit (each IP sends a few requests); only bot and risk signals catch it. Layer them cheapest first at the edge.

How to answer

Give one attack each layer catches that the others miss. The credential-stuffing example is the clincher.

Likely follow-ups
  • Where does DDoS protection fit?
  • What key would you rate-limit login on?
User-based or item-based collaborative filtering for an e-commerce "customers also bought" widget? Why?

Item-based. Item-item similarity is stable (an item's buyer base changes slowly), so it can be computed offline, truncated to top-K per item and served from a key-value store; the online cost is a few lookups proportional to the items the user touched, independent of the number of users. User-based needs a neighbour search over all users at request time, user rows are sparse and drift quickly, and new users have almost no row. Item-based is also explainable ("because you bought X"). This is the choice in Amazon's 2003 item-to-item paper.

How to answer

Name both, pick item-based, give the three reasons: stability (offline), online cost, sparsity/cold users. Then sketch the offline job and the KV layout with a storage estimate.

Likely follow-ups
  • How do you stop the phone charger being similar to everything?
  • How fresh does the table need to be, and how do you refresh it?
Why cosine similarity and not Euclidean distance for rating vectors? When is cosine wrong?

Cosine compares direction and ignores magnitude, so heavy and light users (or popular and niche items) with the same pattern still match; Euclidean distance would call two items far apart just because one has many more interactions. Cosine is wrong when magnitude is the signal: for MF embeddings trained for dot product, the vector length encodes popularity or confidence, and the objective is maximum inner product, so normalising throws information away. Also, raw cosine is unstable for tiny overlaps (two co-buyers can give 1.0), so add shrinkage or a minimum co-count.

How to answer

Define it in one line, give the "generous vs harsh rater" example, then the counter-case (MIPS) and the small-sample fix.

Likely follow-ups
  • What does adjusted cosine change?
  • What would you use for 0/1 data?
