Level 2 - Beginner 10 questions

Is a container a VM? What exactly is different?

No. A VM runs its own guest kernel on top of a hypervisor (KVM, Hyper-V) that fakes hardware. A container is a normal Linux process on the host kernel, fenced in by namespaces (what it can see) and limited by cgroups (what it can use). Nothing is emulated, so a container starts in milliseconds and its image can be a few MB, while a VM boots a whole OS and is usually GBs.

The price is isolation: all containers share one kernel, so a kernel bug can affect all of them. A VM has a much smaller attack surface (the hypervisor). That is why untrusted multi-tenant code often runs in gVisor or Firecracker microVMs instead of plain runc.

How to answer

One sentence claim ("a container is a process, a VM is a computer"), then the two kernel features, then the trade-off (speed and density vs isolation). Close with when you would pick a VM.

Likely follow-ups
  • Can a container crash the host kernel?
  • Why does Docker Desktop on a Mac run a VM?
  • What are gVisor and Kata Containers for?
What is the difference between an image and a container?

An image is a read-only, content-addressed bundle: an ordered list of filesystem layers plus a config JSON (entrypoint, env, user). A container is a running (or stopped) instance of that image: the image layers mounted read-only, plus one thin writable layer on top, plus namespaces and cgroups around a process. One image can start many containers, the same way one ELF binary can start many processes.

How to answer

Use the binary vs process analogy, then say where writes go (the writable layer) and what happens on docker rm (that layer is deleted).

Likely follow-ups
  • Where is the writable layer on disk?
  • What happens to files when the container stops (not removed)?
What is a layer, and why does changing one line rebuild everything after it?

Each RUN, COPY or ADD produces a layer: a tarball of the filesystem changes made by that step, identified by its sha256 digest. BuildKit caches each step keyed by the instruction text, the checksums of copied files and the parent layer. The moment one step misses the cache, every later step has a different parent, so all of them rebuild.

That is why you copy the dependency manifest (requirements.txt, package.json, go.mod) and install dependencies before copying source code: code changes often, dependencies rarely.

How to answer

Define layer, state the cache key rule, then give the "copy manifest first" fix with a two-line Dockerfile.

Likely follow-ups
  • Which instructions do not create filesystem layers?
  • How do cache mounts (--mount=type=cache) help?
CMD vs ENTRYPOINT - what is the difference?

ENTRYPOINT is the fixed program the container runs. CMD gives default arguments (or the default command if there is no ENTRYPOINT). docker run image foo replaces CMD only; --entrypoint replaces ENTRYPOINT. A common pattern: ENTRYPOINT ["python", "app.py"] with CMD ["--port", "8080"].

Always use the exec form (JSON array). The shell form wraps your command in /bin/sh -c, so the shell becomes PID 1 and usually does not forward SIGTERM to your app.

How to answer

Give the rule, a tiny example, then the exec-form vs shell-form signal gotcha. The gotcha is what separates a good answer.

Likely follow-ups
  • What happens on docker stop if the app ignores SIGTERM?
  • How do you pass runtime flags to the app?
COPY vs ADD?

Both copy files into the image. ADD also downloads URLs and auto-extracts local tar archives. Because that magic surprises people, the guidance is: use COPY unless you specifically need tar extraction, and for URLs prefer ADD --checksum=sha256:... or a RUN curl you can verify.

How to answer

Short answer: "prefer COPY; ADD only for its two extra features". Do not spend more than 20 seconds here.

Likely follow-ups
  • How does .dockerignore affect COPY?
Volumes vs bind mounts vs tmpfs - when do you use each?

A named volume is storage managed by Docker (under /var/lib/docker/volumes/), survives container removal and bypasses the overlay copy-up cost, so it is the default for databases. A bind mount maps any host path into the container: perfect for local development (hot reload), but it depends on the host layout and UID permissions. tmpfs lives in RAM only and vanishes on stop: good for scratch data and secrets you never want on disk.

How to answer

Lead with the use case for each, then one gotcha: an empty named volume is pre-filled from the image, a bind mount hides what was there.

Likely follow-ups
  • How do you back up a named volume?
  • Why are writes to a big file inside the container layer slow?
What do bridge, host and none networking mean?

bridge (default): the container gets its own network namespace and a veth pair whose host end plugs into a Linux bridge (docker0 or a user-defined one); outbound traffic is masqueraded and published ports are DNAT'd. host: no network namespace, the process uses the host's interfaces directly, so no port mapping and no NAT overhead. none: only loopback, fully cut off.

User-defined bridges add DNS by container name via Docker's embedded DNS at 127.0.0.11; the default bridge does not.

How to answer

Draw veth + bridge + NAT in words. Mention the embedded DNS difference, which interviewers like as a practical detail.

Likely follow-ups
  • How do two containers on different hosts talk?
  • What is macvlan for?
What does docker run -p 8080:80 nginx do on the host?

Docker creates a DNAT rule in the nat table (DOCKER chain): traffic arriving at host port 8080 is rewritten to the container IP port 80, then forwarded across the bridge into the container's veth. By default it also starts a small docker-proxy process for some local cases. It binds 0.0.0.0 and [::], so the port is open to the network unless you write -p 127.0.0.1:8080:80.

How to answer

Name the table, the chain and the rewrite. Then give the security gotcha: ufw rules do not block it because DNAT happens before the INPUT chain; filter in DOCKER-USER.

Likely follow-ups
  • How would you see the rule? (sudo iptables -t nat -L DOCKER -n)
  • What does EXPOSE do? (nothing; documentation only)
What is Docker Compose for, if Kubernetes exists?

Compose describes a multi-container app on one host in one YAML file: services, networks, volumes, health checks and start order. It is ideal for local development, CI integration tests and small single-machine deployments (for example app + Postgres + Kafka on a laptop). Kubernetes is for many hosts: scheduling, self-healing, rolling updates, autoscaling. Many teams use Compose locally and Kubernetes in production with the same images.

How to answer

Say "single host vs cluster" first, then the typical dev-to-prod flow. Mention depends_on with condition: service_healthy.

Likely follow-ups
  • Why does my app crash on startup in Compose even with depends_on?
  • How do services find each other in Compose?
What is a registry and how do pushes stay fast?

A registry is an HTTP server that speaks the OCI Distribution API: clients GET manifests by tag or digest and GET blobs (layers) by digest. Because everything is content-addressed, a push first checks which blobs already exist and skips them, so only changed layers travel. Examples: Docker Hub, GHCR, ECR, ACR, Artifact Registry, Harbor.

How to answer

From your world: it is a firmware image server, but every file is named by its SHA-256, so dedup and integrity come for free.

Likely follow-ups
  • Tag vs digest - which do you deploy?
  • What are Docker Hub pull limits and why do they bite CI?

Level 3 - Intermediate 13 questions

How do you shrink a 1.2 GB image?

Use a multi-stage build: compile in a full SDK image, then copy only the artifact into a small runtime base (-slim, distroless, or scratch for static Go). Add a .dockerignore (drop .git, node_modules, test data). Do download, extract and cleanup in one RUN, because deleting a file in a later layer does not shrink earlier layers. Use --no-cache-dir for pip and remove package manager caches.

A Go service commonly drops from hundreds of MB (golang base) to under 20 MB this way. Measure with docker images and inspect layers with docker history or dive.

How to answer

Give the biggest win first (multi-stage), then the layer-deletion trap, then how you would measure. Numbers make it believable.

Likely follow-ups
  • Alpine vs distroless vs slim - which and why?
  • How do you keep debugging tools if the image has no shell?
Why does my container ignore docker stop and take 10 seconds to die?

docker stop sends SIGTERM, waits 10 s, then sends SIGKILL. If you used the shell form (CMD node server.js), PID 1 is /bin/sh, which does not forward SIGTERM to node, so nothing happens until the SIGKILL. Also, PID 1 in a PID namespace gets no default signal handlers: if your app does not install a SIGTERM handler, the signal is ignored.

Fix: exec form CMD ["node", "server.js"], handle SIGTERM in the app (stop accepting, drain, exit), or run with --init (tini) to forward signals and reap zombies.

How to answer

Explain the 10-second number, then the PID 1 rule from the kernel, then three fixes in order of preference.

Likely follow-ups
  • What is a zombie and who reaps it?
  • How does this show up in Kubernetes? (terminationGracePeriodSeconds, default 30 s)
A container exits with code 137. What happened? What about 143 and 1?

Exit codes above 128 mean "killed by signal (code - 128)". 137 = signal 9, SIGKILL: either someone ran docker kill, or the kernel OOM killer killed it for crossing its cgroup memory.max. 143 = 128 + 15: the process was ended by SIGTERM (for example by docker stop or a pod deletion) and did not handle it itself. An app that catches SIGTERM and drains cleanly usually exits 0; JVMs are the exception and report 143 even after running their shutdown hooks. 1 = the application itself exited with an error.

Confirm OOM with docker inspect -f '{{.State.OOMKilled}}' <c> or kubectl describe pod showing Last State: OOMKilled.

How to answer

Do the arithmetic out loud, list the two causes of 137, then say exactly how you would confirm.

Likely follow-ups
  • How do you fix a JVM that gets OOMKilled?
  • Does a CPU limit ever kill a container?
How do you set CPU and memory limits, and what happens when they are exceeded?

docker run --memory=512m --cpus=1.5. These become cgroup v2 files: memory.max = 536870912 and cpu.max = 150000 100000 (quota and period in microseconds). Memory is a hard wall: crossing it triggers the OOM killer (exit 137). CPU is a rate: crossing the quota means the process is throttled until the next 100 ms period, never killed. Watch nr_throttled in cpu.stat.

How to answer

Show the flag-to-file mapping (the learner's world), then the "memory kills, CPU throttles" rule.

Likely follow-ups
  • Why do latency spikes appear with tight CPU limits?
  • Does Java see the container limit?
How is a container isolated from the host? List the kernel features.

Namespaces hide things: pid, net, mnt, uts, ipc, cgroup (and user when enabled). cgroups v2 limit CPU, memory, IO and PIDs. Then a security layer: capabilities (Docker keeps 14 by default and drops the rest, such as SYS_ADMIN and NET_ADMIN), a seccomp allowlist that blocks dangerous syscalls (mount, reboot, kexec_load, bpf and more), and an LSM profile (AppArmor or SELinux). Rootless mode or user namespaces add UID remapping so root inside is not root outside.

How to answer

Group them: "see" (namespaces), "use" (cgroups), "do" (capabilities, seccomp, LSM). Three buckets are easy to remember and sound structured.

Likely follow-ups
  • What does --privileged turn off?
  • Name a real container escape CVE.
Is running as root inside a container dangerous if the host is patched?

Yes, by default container root is host UID 0 (unless user namespaces are on). It is restricted by dropped capabilities and seccomp, but any escape bug (for example runc CVE-2019-5736) or a careless mount (/var/run/docker.sock, host paths) turns it into host root. Run as a numeric non-root user (USER 10001), drop all capabilities, use --read-only and no-new-privileges. In Kubernetes enforce runAsNonRoot with the Restricted Pod Security Standard.

How to answer

Say "defence in depth": non-root is one cheap layer that turns many escapes into nothing.

Likely follow-ups
  • Rootless Docker vs a non-root USER - what is the difference?
  • Why must the UID be numeric for Kubernetes?
Why should you never put secrets in ENV, ARG or a COPY'd file?

Every layer and the image config are shipped to everyone who can pull the image. ARG values appear in docker history, ENV values in docker inspect, and a file deleted in a later layer is still inside the earlier layer's tarball. Use BuildKit secret mounts (RUN --mount=type=secret,id=npmrc ...) for build time, and inject runtime secrets from the orchestrator (Kubernetes Secrets backed by a vault, or a secrets CSI driver).

How to answer

Explain why (layers are forever), then the build-time fix and the runtime fix separately.

Likely follow-ups
  • How would you check an existing image for leaked secrets?
dockerd vs containerd vs runc - why three pieces? What is OCI?

docker CLI talks REST to dockerd (images, networks, volumes, build). dockerd asks containerd (over gRPC) to manage container lifecycle and image storage. containerd starts a small shim per container, which calls runc: runc reads an OCI config.json, creates namespaces and cgroups, execs your process, then exits. The shim stays to hold stdio and report the exit code, so containerd can restart without killing containers.

OCI (Open Container Initiative) standardises the image format, the runtime spec and the distribution API, so any compliant tool can build, push and run the same image.

How to answer

Draw the chain left to right and give each piece one job. Then explain the shim's reason to exist; that shows real depth.

Likely follow-ups
  • Why could Kubernetes drop dockershim without breaking images?
  • What is CRI-O?
Why did Kubernetes remove dockershim, and did Docker images stop working?

Kubernetes talks to runtimes through the CRI (Container Runtime Interface). Docker Engine never implemented CRI, so kubelet carried an adapter called dockershim. It was removed in v1.24 (2022) to cut that maintenance. Images built with Docker are OCI images, so containerd and CRI-O run them unchanged. Only setups that depended on the Docker socket on nodes (for example some log agents or Docker-in-Docker builds) had to change.

How to answer

Clear "no, images still work" first, then the reason (CRI), then who was actually affected.

Likely follow-ups
  • What is the CRI made of? (gRPC services for runtime and images)
Why is :latest dangerous in production?

latest is just a default tag name, not "newest", and tags are mutable pointers. Two nodes pulling app:latest an hour apart can run different code; rollbacks become guesswork. Deploy immutable tags (git SHA, semver) and ideally pin by digest (app@sha256:...). Build once and promote the same digest from dev to staging to prod.

How to answer

Mutable vs immutable is the key word. Add "build once, deploy many".

Likely follow-ups
  • How do you map a running container back to its source commit? (labels, provenance)
My image built on an M1/M2 Mac fails on an x86 server with "exec format error". Why?

The image layers contain binaries compiled for the build machine's CPU (arm64). The x86 server (amd64) cannot execute them. Fix: build multi-platform with docker buildx build --platform linux/amd64,linux/arm64 --push, which produces an image index listing one manifest per platform; the server pulls the right one. Cross-compiling with --platform=$BUILDPLATFORM and TARGETARCH is much faster than QEMU emulation.

How to answer

Name the error, the cause (architecture), and the buildx fix with the image index concept.

Likely follow-ups
  • How do you check which platforms an image supports? (docker buildx imagetools inspect)
"Works on my laptop, fails in the container." What do you check?

In order: (1) localhost binding - the app listens on 127.0.0.1 inside the container, so the published port reaches nothing; bind 0.0.0.0. (2) "localhost" means the container itself - a DB on the host is host.docker.internal or a service name, not localhost. (3) Missing env vars or config files. (4) CPU architecture mismatch. (5) File permissions when running as non-root. (6) musl vs glibc on Alpine (DNS and native wheels behave differently). (7) Time zone and locale.

How to answer

Give an ordered checklist and show the command for each: docker logs, docker exec -it c sh, docker inspect, ss -lntp inside.

Likely follow-ups
  • How do you debug a distroless image with no shell? (docker debug, or an ephemeral debug container in K8s)
Why does Docker keep using disk after I delete containers?

Deleting containers does not delete images, named volumes or the build cache, and the json-file log driver keeps logs with no rotation by default. Check with docker system df. Clean with docker system prune (add -a for unused images, --volumes carefully), and docker builder prune for build cache. Set log rotation in daemon.json (max-size, max-file) or use the local driver.

How to answer

Name the four disk consumers, the measurement command, then the cleanup plus the prevention (log rotation).

Likely follow-ups
  • Why is --volumes risky on a shared host?

Level 4 - Advanced 6 questions

What is an image physically on disk? Explain OverlayFS.

An image is an OCI index (per platform) pointing at a manifest, which lists a config JSON and ordered layer tarballs, all named by sha256. When unpacked with overlay2, each layer is a directory. A container mount combines lowerdir (read-only image layers), upperdir (the writable container layer), workdir, and the merged view the process sees.

Reads fall through to the highest layer holding the file. The first write to a lower file triggers copy-up of the whole file to upperdir. Deleting a lower file creates a whiteout entry in upperdir. Because copy-up is per file, big database files belong in a volume.

How to answer

Draw the stack of four directories. Then copy-up and whiteouts, and the practical consequence.

Likely follow-ups
  • Why can rename(2) of a directory fail with EXDEV?
  • How is page cache shared between containers from the same image?
What does docker exec do at the kernel level?

It starts a new process that joins the existing container's namespaces with setns() (and enters its cgroup), so it sees the same filesystem, network and PIDs. That is why it needs a binary that exists in the container image (sh may not exist in distroless). You can do the same by hand with nsenter -t <pid> -a.

How to answer

Say "setns into existing namespaces"; mention nsenter to show you know the primitive.

Likely follow-ups
  • How would you find the host PID of a container? (docker inspect -f '{{.State.Pid}}')
How does a container on the default bridge reach the internet?

The packet leaves the container's eth0, crosses the veth pair to docker0, and the host routes it out of its uplink. On the way out, an iptables MASQUERADE rule in nat POSTROUTING rewrites the source from 172.17.x.x to the host IP. conntrack remembers the mapping so replies are translated back. It is exactly a home router doing SNAT.

How to answer

Walk the packet hop by hop, naming the table and chain; finish with conntrack.

Likely follow-ups
  • What breaks with a VPN or overlay underlay? (MTU; set the network MTU lower, such as 1450)
How do you build and ship images securely in CI?

Pipeline: build with BuildKit and cache (cache-from/to type=gha or a registry cache), generate an SBOM and provenance (--sbom=true --provenance=mode=max), scan with Trivy or Grype and fail on CRITICAL, sign with cosign (keyless via Sigstore), push immutable tags, and deploy by digest. In Kubernetes, verify signatures with an admission policy (Kyverno or a policy controller). Use minimal, regularly rebuilt base images.

How to answer

Present it as a left-to-right pipeline with one tool per stage, then say what blocks a deploy.

Likely follow-ups
  • Docker-in-Docker vs mounting the socket in CI - risks?
  • What is SLSA provenance?
Containers share the kernel. Can one container crash the host or starve the others?

Crash: yes, a kernel bug or panic triggered from a container affects the whole host, because there is only one kernel. Starve: without limits, yes - one container can eat all memory (triggering host OOM), all CPU, all PIDs (fork bomb) or disk IO. Defences: cgroup limits on memory, CPU, pids.max and IO; seccomp to shrink the syscall surface; and for hostile tenants, a sandboxed runtime (gVisor, Kata, Firecracker).

How to answer

Separate the two threats (kernel crash vs resource starvation) and give the defence for each.

Likely follow-ups
  • What is a noisy neighbour in Kubernetes terms? (requests, limits, QoS classes)
What is the containerd image store change in Docker Engine 29?

From Engine 29.0, fresh installs use containerd's image store and snapshotters by default instead of Docker's classic overlay2 graph driver (upgraded installs keep their old store). Practical effects: native support for multi-platform images and attestations in the local store, and one shared store model with Kubernetes nodes running containerd. It is an implementation change; Dockerfiles and commands stay the same.

How to answer

Show you follow current versions, but keep it short and say what users notice.

Likely follow-ups
  • What else did Engine 29 deprecate? (cgroup v1; Docker Content Trust removed from the CLI)

Level 5 - Interview-ready 2 questions

Design the container build-and-deploy flow for 200 microservices.

One shared CI template: build with BuildKit and a remote cache, run unit tests in a --target test stage, scan, sign, push to a private registry with a pull-through cache for public bases, tag by git SHA. A GitOps repo holds the desired image digests per environment; Argo CD (pull-based) syncs clusters. Promote the same digest dev to staging to prod with a canary step and automated rollback on SLO breach. Base images are rebuilt weekly and a bot opens upgrade PRs.

How to answer

Structure: build, verify, store, deploy, promote, maintain. Mention the scale-specific bits: shared template, registry mirror, rebuild cadence.

Likely follow-ups
  • How do you stop 200 teams from all pulling from Docker Hub?
  • How do you roll back in 1 minute?
Teach me: when would you NOT use containers?

When the workload needs a different kernel or kernel modules, hard real-time or dedicated hardware access that does not fit device plugins, strong isolation for untrusted tenants (use VMs or microVMs), or when a single static binary on a managed platform (for example serverless) is simpler. Also tiny teams with one server may not need the extra moving parts.

How to answer

Interviewers like a balanced engineer. Give three honest cases and the alternative for each.
