Low-level design and machine coding (10)

Many SDE-1 and SDE-2 loops have an LLD (object-oriented design) or machine-coding round, and some have one instead of HLD: Flipkart often opens with an eliminating machine-coding round, Uber and Microsoft report parking-lot and file-system LLD, and Atlassian has a "code design" round. HLD draws the boxes between services; LLD designs the classes inside one box, and machine coding asks you to make them run. Concept page: HLD vs LLD: Handling Combined Design Rounds.

Want more LLD? These 10 are the cross-track sample. The LLD question bank has 150+ more (OOP, SOLID, patterns, UML, concurrency, case studies), the recently asked LLD list ranks 135 real problems from 311 reports, and every case study has code that runs.

The same five steps work for every LLD prompt. (1) Ask for the 3-5 core use cases and say what you will leave out. (2) List the nouns: they become your entities. (3) List the verbs: they become methods on a service. (4) Find the part that will change (pricing, allocation, split rules) and hide it behind an interface: that is where the strategy pattern goes. (5) Say where concurrency bites and how you lock it. In machine coding, add (6): keep it runnable after every 20 minutes, with an in-memory repository and a small demo main.

Level 2 - Beginner 1 question

Explain the SOLID principles in one minute, with one example each.

S - Single responsibility: a class has one reason to change. Invoice holds data; InvoicePrinter prints it. O - Open/closed: add behaviour by adding a class, not by editing a growing if/else. A new PricingStrategy for weekends, not a new branch in calculatePrice(). L - Liskov substitution: a subclass must work anywhere its parent works. If Square extends Rectangle breaks setWidth(), the hierarchy is wrong. I - Interface segregation: many small interfaces beat one fat one; a Printer should not be forced to implement fax(). D - Dependency inversion: depend on interfaces and inject them. OrderService takes a PaymentGateway interface, so tests pass a fake and production passes Razorpay or Stripe.

In an interview, you rarely recite SOLID. You use it: "I put allocation behind a SpotAllocationStrategy interface so a new rule does not touch ParkingLot (open/closed)."

How to answer

One line per letter with a tiny example, then say which two you use most in LLD rounds (single responsibility and open/closed via the strategy pattern). Under a minute.

Likely follow-ups
  • Where did you over-apply SOLID and make code harder to read?
  • Strategy vs state pattern: what is the difference?
  • How does dependency injection help testing?

Level 3 - Intermediate 4 questions

Design a multi-floor parking lot (LLD).

Use cases: park a vehicle, issue a ticket, unpark and pay, show free spots per floor. Entities: ParkingLot (has floors and gates), Floor (has spots), Spot (id, size: SMALL / MEDIUM / LARGE, occupied), Vehicle (bike, car, truck map to a size), Ticket (id, spot, entry time), Payment. Services: ParkingService.park(vehicle) returns a Ticket; unpark(ticketId) returns the fee.

The parts that change go behind interfaces: SpotAllocationStrategy (nearest to gate, lowest floor first, EV spots first) and PricingStrategy (hourly, flat weekend rate). A new vehicle type is a new enum value plus a size mapping, not a new class tree. Concurrency: two gates must not hand out the same spot. Keep free spots per size in a thread-safe queue and take one atomically (poll()), or lock per floor; never "check free, then mark taken" as two steps.

interface SpotAllocationStrategy { Optional<Spot> pick(VehicleSize size, List<Floor> floors); }
interface PricingStrategy { long fee(Ticket t, Instant exit); }

class ParkingService {
  private final SpotAllocationStrategy alloc; private final PricingStrategy pricing;
  Ticket park(Vehicle v) {
    Spot s = alloc.pick(v.size(), floors).orElseThrow(LotFullException::new); // pick() must claim the spot atomically
    return tickets.save(new Ticket(UUID.randomUUID(), s, Instant.now()));
  }
}
How to answer

Use cases (1 min), entity list with one-line responsibilities, a small class diagram, then the two strategies, then the concurrency point. Interviewers score extensibility ("add EV charging spots") and the race on spot assignment.

Likely follow-ups
  • Add EV spots with chargers and a per-kWh price.
  • Two entry gates assign spots at the same time: show the race and the fix.
  • How would you show a live "free spots" board per floor? (observer pattern)
Machine coding: build Splitwise (expenses, splits, balances) in memory.

Use cases: add users, add an expense paid by one user split EQUAL, EXACT or PERCENT among others, show balances for a user, show all balances, optionally simplify debts. Entities: User, Expense (payer, amount, list of Split), Split (user, amount). Balance sheet: a map balance[a][b] = how much b owes a; adding an expense updates it in O(number of splits).

Extensibility: a SplitStrategy interface with EqualSplit, ExactSplit and PercentSplit, each with validate() (exact amounts must sum to the total; percents must sum to 100). Use integer paise or cents, never floating point, and give the rounding remainder to the first person so totals always match. Simplify debts: compute each user's net balance, then repeatedly settle the largest creditor against the largest debtor with two heaps; this needs at most n-1 payments.

Machine-coding rubric: it runs, inputs are validated, classes are small, a new split type is one new class, and there is a demo or a few tests. Keep a command parser (EXPENSE u1 1000 4 u1 u2 u3 u4 EQUAL) separate from the service.

How to answer

Spend 10 minutes on the model and interfaces, then code the happy path end to end first (EQUAL split and show balances), then add EXACT and PERCENT, then simplify. Something running at minute 45 beats a perfect design at minute 90.

Likely follow-ups
  • Add groups and per-group balances.
  • How do you handle rounding (100 split three ways)?
  • How would this change if expenses came from many servers? (persist, idempotency key per expense)
Implement an LRU cache class with O(1) get and put.

Combine a hash map (key to node) with a doubly linked list ordered by recency. get: look up the node, move it to the head, return the value. put: if present, update and move to head; else insert at head, and if over capacity remove the tail node and its map entry. Every step is O(1). Sentinel head and tail nodes remove the null checks.

class Node:
    __slots__ = ("k", "v", "prev", "next")
    def __init__(self, k=None, v=None): self.k, self.v, self.prev, self.next = k, v, None, None

class LRUCache:
    def __init__(self, cap):
        self.cap, self.map = cap, {}
        self.head, self.tail = Node(), Node()          # sentinels
        self.head.next, self.tail.prev = self.tail, self.head
    def _unlink(self, n): n.prev.next, n.next.prev = n.next, n.prev
    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n; self.head.next = n
    def get(self, k):
        n = self.map.get(k)
        if not n: return -1
        self._unlink(n); self._push_front(n); return n.v
    def put(self, k, v):
        if k in self.map: self._unlink(self.map[k])
        n = self.map[k] = Node(k, v); self._push_front(n)
        if len(self.map) > self.cap:
            lru = self.tail.prev; self._unlink(lru); del self.map[lru.k]

Thread safety: the map and list must change together, so guard both with one lock (or use striped caches, each with its own lock, keyed by hash). In Java, LinkedHashMap with accessOrder=true and removeEldestEntry gives the same thing in a few lines; say so, then show you can build it.

How to answer

Name the two structures and why each is needed (map for O(1) lookup, list for O(1) reorder and evict). Code it with sentinels. Then mention thread safety and the library shortcut. Microsoft has asked a "distributed LRU cache" that starts here and grows into consistent hashing.

Likely follow-ups
  • Make it thread-safe without one global lock.
  • Add a TTL per entry.
  • LRU vs LFU: when is LFU better, and how do you make it O(1)?
  • Now make it distributed across 10 nodes (distributed cache).
Design a rate-limiter class (token bucket) that many threads can call.

Interface first: boolean tryAcquire(String key). Behind it, a RateLimiter interface with TokenBucketLimiter, SlidingWindowLimiter and FixedWindowLimiter implementations, chosen per rule by a factory or config. A TokenBucket holds capacity, refillPerSecond, tokens and lastRefill. On each call: add elapsed * rate tokens (capped at capacity), then take one if available.

Lazy refill means no background thread: tokens are computed from the time since the last call. Concurrency: one bucket per key in a ConcurrentHashMap (computeIfAbsent), and a lock or a compare-and-set loop inside each bucket, so two threads cannot both take the last token. Inject a Clock so tests can move time without sleeping. Evict idle buckets so the map does not grow forever.

How to answer

Interface, the bucket fields, the refill formula, then the race and the per-key lock. Close with "across many servers this state moves to Redis with a Lua script", which links to the distributed rate limiter HLD.

Likely follow-ups
  • Token bucket vs sliding window log vs sliding window counter: memory and accuracy.
  • How do you test it without Thread.sleep?
  • Different limits per user tier, changed at runtime.

Level 4 - Advanced 5 questions

Design an elevator system for a building with several lifts.

Entities: Building, Elevator (id, current floor, direction, state: IDLE / MOVING_UP / MOVING_DOWN / DOORS_OPEN / MAINTENANCE, a set of target floors), HallRequest (floor, direction, pressed outside), CarRequest (floor, pressed inside), Dispatcher. Each elevator runs a small state machine; illegal moves (moving with doors open) are impossible by design.

Scheduling is the part that changes, so it sits behind DispatchStrategy. The classic is the SCAN or "elevator" algorithm: keep moving in one direction serving every requested floor, then reverse. The dispatcher assigns a hall call to the lift with the lowest cost (already moving towards the floor in the same direction beats idle, beats moving away). Each elevator keeps two sorted sets (floors above, floors below) so the next stop is O(log n).

Concurrency: buttons arrive on many threads; each elevator has its own thread or event loop that consumes a queue of requests, so its state is changed by one thread only. That avoids locks on elevator state entirely.

How to answer

Clarify (how many lifts and floors, is there a VIP or fire mode), then entities and the state machine diagram, then the dispatch strategy, then the threading model. The state machine is what interviewers look for.

Likely follow-ups
  • Add a fire mode that sends all lifts to the ground floor.
  • How would you minimise average wait time at 9 am?
  • One lift goes into maintenance mid-trip: what happens to its requests?
Design a task scheduler that assigns jobs to a pool of worker threads (with priorities, delays and retries).

API: submit(task, priority), schedule(task, runAt), cancel(taskId), status(taskId). Core: a PriorityBlockingQueue (or a DelayQueue for scheduled tasks) ordered by run time, then priority; a fixed pool of N worker threads that take() from the queue; a TaskRecord with state PENDING / RUNNING / SUCCEEDED / FAILED / CANCELLED and an attempt count.

Retries: on failure, if attempts are left, re-enqueue with exponential backoff and jitter (runAt = now + base * 2^attempt + random); otherwise mark FAILED and send it to a dead-letter list. Cancel flips the state; a worker checks the state before running, and running tasks get an interrupt. Shutdown: stop accepting, let running tasks finish within a timeout, persist the pending ones. Workers never busy-wait: take() blocks.

From your world: this is a run queue with a timer wheel, and the worker pool is a set of CPUs pulling from it.

How to answer

API, the queue choice and why, the worker loop, the state machine, then retries and cancellation. Mention starvation: a stream of high-priority jobs can starve low ones, so age priorities over time.

Likely follow-ups
  • Recurring tasks (every 5 minutes): how do you avoid drift and overlap?
  • How do you avoid starvation of low-priority tasks?
  • Now the scheduler runs on 5 machines: who runs each task once? (job scheduler HLD)
Build an in-memory pub/sub (topics, subscribers, at-least-once delivery).

API: createTopic(name), publish(topic, message), subscribe(topic, subscriberId, handler), ack(subscriberId, offset). Model it like a tiny Kafka: each Topic keeps an append-only list of messages; each Subscription keeps its own offset. Publishing appends once; each subscriber reads from its own offset, so a slow subscriber does not slow the others and a new one can replay from the start.

Delivery: one dispatcher thread (or one per subscriber) pushes messages to the handler; the offset moves forward only after ack, so a crash means redelivery (at-least-once) and handlers must be idempotent. Concurrency: appends under a lock or a CopyOnWriteArrayList per topic (reads are lock-free); offsets in an AtomicLong. Retention: trim messages below the smallest subscriber offset, or by age.

How to answer

State the delivery guarantee first (at-least-once), then the log-plus-offsets model, then threads. Explaining why per-subscriber offsets beat per-subscriber queues (one copy of data, replay for free) shows real understanding.

Likely follow-ups
  • Add message filtering per subscriber.
  • How do you handle a subscriber that always throws? (retry count, dead-letter list)
  • Make ordering per key while delivering in parallel (partition by key).
BookMyShow: lock seats while the user pays, without double booking.

Entities: Show (movie, screen, time), Seat, ShowSeat (show, seat, state: AVAILABLE / HELD / BOOKED, heldBy, holdExpiresAt, version), Booking. Flow: holdSeats(showId, seatIds, userId) moves all requested seats from AVAILABLE to HELD for 10 minutes, all or nothing; confirm(bookingId) after payment moves HELD to BOOKED; an expiry job (or a check on read) releases holds whose time has passed.

The race: two users pick seat F7 at the same moment. In memory: lock the seats in a fixed order (sorted seat IDs, so two holds cannot deadlock), check all are AVAILABLE, then mark them. In a database: optimistic UPDATE show_seat SET state='HELD', version=version+1 WHERE id IN (...) AND state='AVAILABLE' AND version=? and check the row count, or pessimistic SELECT ... FOR UPDATE in one transaction. Optimistic is better when most seats are not contested; pessimistic when a hot show makes conflicts common.

How to answer

State machine for a seat, the hold with a timeout, then the race with both locking choices and when each wins. Walmart has asked "optimistic vs pessimistic locking" in exactly this setting. Link to the ticket booking HLD.

Likely follow-ups
  • Payment succeeds one second after the hold expired: what now?
  • Why lock seats in sorted order?
  • A 50,000-person queue opens for a big release: what changes? (virtual waiting room)
Design an in-memory file system with mkdir, ls, write, read and wildcard search.

Use the composite pattern: an abstract Node (name, parent, created time) with File (content, size) and Directory (a Map<String, Node> of children, sorted if ls must be ordered). Path operations split on / and walk from the root; mkdir -p creates missing directories on the way. ls on a file returns the file name; on a directory, the sorted children.

Wildcard search (find("/logs", "*.txt") or "app-?.log"): walk the subtree with DFS and match each name against the pattern. Match glob patterns with a small dynamic-programming matcher (* matches any run, ? matches one character), the same as the classic wildcard-matching problem, O(name length x pattern length). Put matchers behind a SearchFilter interface (by name pattern, by size, by extension) and combine them with AND / OR, so new filters do not change the walker.

How to answer

Composite pattern and path walking first, then the search as a filter interface plus a DFS, then the glob matcher. Uber has reported this exact LLD.

Likely follow-ups
  • Support ** (match across directories).
  • Add move and rename: what must change in the tree?
  • Make it safe for many threads (read-write lock per directory, or one lock for the tree).
