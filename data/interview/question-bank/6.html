Level 2 - Beginner 7 questions

Explain topic, partition, offset and broker.

A broker is a Kafka server. A topic is a named stream of records (for example orders). Each topic is split into partitions: ordered, append-only logs spread over brokers so the topic can scale. An offset is a record's position number inside one partition. Producers append to the end; consumers read forward from an offset they choose and remember.

How to answer

Draw it: topic box, three partition rows, numbered cells, an arrow for the consumer's position. Then say "ordering is per partition".

Likely follow-ups
  • Who stores the consumer's offset?
  • What is a segment?
Is Kafka a queue? If a consumer reads a message, is it deleted?

No. Kafka is a retained log. Reading does not delete anything; each consumer group just moves its own offset forward. Records are deleted later by retention (default 7 days, or by size) or kept latest-per-key by compaction. That is why many independent groups can read the same data and why you can replay history - things a classic queue (RabbitMQ, SQS) does not do, because there a message is gone once acknowledged.

How to answer

Contrast "delete on ack" with "retain and move a pointer". Mention replay as the practical payoff.

Likely follow-ups
  • Can Kafka act like a work queue? (share groups, production ready since Kafka 4.2)
If Kafka stores data on disk, how is it different from a database?

Kafka stores an ordered log of events and lets you read it sequentially by offset; it has no secondary indexes, no ad-hoc queries, no updates in place. A database stores current state and answers queries on it. In practice they work together: Kafka moves and buffers changes between systems, databases (or caches, search indexes) hold the queryable state built from those events.

How to answer

"Log of changes vs table of current state." Mention that a compacted topic is the closest Kafka gets to a table.

Likely follow-ups
  • What is a KTable?
Why is ordering only guaranteed inside a partition? How do you pick the key?

Each partition is a separate log, possibly on a different broker, with no global sequence across them; enforcing a total order would mean one serialised writer and kill scaling. The producer hashes the key (murmur2(key) % partitions), so all records with the same key go to the same partition and stay in order. Pick the key that matches what must stay ordered: order_id for order lifecycle events, account_id for a ledger. Check cardinality and skew so no partition gets hot.

How to answer

From your world: it is ECMP flow hashing - same 5-tuple, same path, so packets in a flow do not reorder.

Likely follow-ups
  • What happens to key ordering if you add partitions later?
Consumer group: 10 partitions and 15 consumers - what do the extra 5 do?

Nothing; they sit idle as hot standbys. Inside one group, each partition is assigned to exactly one consumer, so maximum parallelism equals the partition count. If a consumer dies, a rebalance moves its partitions to the idle ones. Different groups each get all partitions - that is how Kafka does pub/sub and queuing at once.

How to answer

State the rule ("one partition, one consumer per group"), then what extras are good for, then the multi-group fan-out.

Likely follow-ups
  • How would you get more than 10-way parallelism? (more partitions, or process records concurrently inside a consumer with care, or share groups)
Who stores the consumer offset?

The broker does. Consumers commit offsets to the internal compacted topic __consumer_offsets (50 partitions by default); the broker that leads the partition for hash(group.id) % 50 acts as that group's coordinator. The consumer decides when to commit: automatically every 5 s (default) or manually after processing.

How to answer

Say "the broker stores it, the consumer decides when". That split is the key insight.

Likely follow-ups
  • What does auto commit risk?
  • Where did offsets live in very old versions? (ZooKeeper)
Kafka vs RabbitMQ vs SQS - when do you pick each?

Kafka: high-throughput event streams, many independent consumers, replay, ordering per key, stream processing. RabbitMQ: rich routing (exchanges), per-message acks, priorities, low-latency task queues. SQS: a zero-ops managed queue on AWS, pay per request, at-least-once (FIFO queues add ordering per message group and deduplication). Sentence to use: "I'd pick Kafka because several teams need to read the same order events and we may need to replay them; the cost is running partitions and consumer groups; if we only needed a simple job queue I'd use SQS."

How to answer

Use the trade-off sentence pattern and pick based on the requirement given, never on taste.

Level 3 - Intermediate 13 questions

What do acks=0, acks=1 and acks=all trade off, and what does min.insync.replicas add?

acks=0: the producer does not wait; fastest, can lose data silently. acks=1: the leader wrote it (to page cache); lost if the leader dies before followers copy it. acks=all (the default since 3.0): every current in-sync replica has it. But if the ISR shrinks to just the leader, acks=all means only one copy - so set min.insync.replicas=2: writes fail with NotEnoughReplicas instead of silently having one copy. Production recipe: replication factor 3, min.insync.replicas=2, acks=all: survives one broker loss without data loss and keeps accepting writes.

How to answer

Build the durability ladder, then the ISR-shrink trap, then the recipe with the "survives one broker" sentence.

Likely follow-ups
  • What happens to writes when two of three brokers are down?
What are ISR, LEO and the high watermark?

Each partition has a leader and followers that fetch from it. The ISR (in-sync replicas) is the set of replicas caught up within replica.lag.time.max.ms (30 s). LEO (log end offset) is the next offset a replica will write. The high watermark is the smallest LEO across the ISR: records below it are on every in-sync replica and are "committed", so consumers can only read up to it.

How to answer

Use the redundancy-group analogy: ISR is the set of standbys that are hot and ready to take over.

Likely follow-ups
  • What is unclean leader election?
At-most-once vs at-least-once vs exactly-once - how do you get each?

At-most-once: commit the offset, then process (a crash loses records). At-least-once: process, then commit (a crash re-delivers records, so handlers must be idempotent) - this is the normal choice. Exactly-once inside Kafka: an idempotent producer plus transactions that write output records and the consumer offsets atomically, with consumers using isolation.level=read_committed. For side effects outside Kafka (a DB, an email, a payment), you get "effectively once" with idempotency keys or upserts at the sink.

How to answer

Show the commit-before vs commit-after ordering first; it explains the first two in one picture.

Likely follow-ups
  • Is exactly-once real or marketing?
What does the idempotent producer do?

The broker assigns the producer an ID and epoch; each batch carries a per-partition sequence number. The broker drops a batch whose sequence it has already written (a retry after a lost ack) and rejects gaps, which also preserves order with up to 5 in-flight requests. It is on by default since Kafka 3.0. It only deduplicates retries within one producer session; surviving restarts needs a transactional.id.

How to answer

From your world: sequence numbers on a link that let the receiver drop retransmitted duplicates.

Likely follow-ups
  • Why is max.in.flight.requests.per.connection limited to 5 with idempotence?
Why do duplicates appear after a consumer crash?

With at-least-once, the consumer processes records and commits the offset later (auto commit every 5 s, or after a batch). If it crashes after processing but before committing, the new owner restarts from the last committed offset and processes those records again. The same happens after a rebalance if the consumer exceeded max.poll.interval.ms. Fix: commit after processing (sync per batch), and make handlers idempotent - dedupe table keyed by event ID, upserts, or conditional writes.

How to answer

Draw the timeline: process, crash, restart from old offset. Then make the handler idempotent rather than "trying harder".

Likely follow-ups
  • How would you store processed IDs efficiently?
What is a rebalance, and why do people say it stops the world?

A rebalance reassigns partitions when consumers join, leave, crash or miss heartbeats. In the classic eager protocol every consumer revokes all partitions and waits for the new assignment, so the whole group pauses. Cooperative sticky assignment (2.4+) only moves the partitions that change. The new KIP-848 protocol (GA in Kafka 4.0, opt in with group.protocol=consumer) moves assignment to the broker and reconciles members incrementally, with no global barrier. Static membership (group.instance.id) avoids rebalances during quick restarts such as rolling deploys.

How to answer

Old vs new protocols as a timeline. Mention static membership as the Kubernetes tie-in.

Likely follow-ups
  • What triggers a rebalance storm?
How many partitions should a topic have? Can you change it later?

Size for peak throughput and for consumer parallelism: partitions >= max(target MB/s / per-partition producer MB/s, target / per-partition consumer MB/s), plus headroom for growth, and at least the maximum number of consumers you want in a group. You can add partitions but never remove them, and adding remaps keys (hash mod N changes), which breaks per-key ordering during the switch. Too many partitions cost open files, memory, longer leader elections and recovery.

How to answer

Give the formula, then the "add, never remove, keys remap" warning. Measure per-partition throughput rather than quoting a magic number.

Likely follow-ups
  • How would you migrate to more partitions while keeping key order? (new topic and a controlled cutover)
What is consumer lag, and what number is bad?

Lag = log end offset minus committed offset, per partition: how many records are waiting. There is no universal bad number; what matters is the trend and the time it represents. Lag that is steady (even if large) is fine; lag that grows means consumers are slower than producers. Convert it to time (lag / consume rate) and alert against your freshness SLO, for example "orders older than 2 minutes".

How to answer

From your world: it is queue depth. A deep but stable queue is fine; a growing one is a drop waiting to happen.

Likely follow-ups
  • What tools show lag? (kafka-consumer-groups.sh --describe, kafka_exporter, Burrow)
What is log compaction and when would you use it?

With cleanup.policy=compact, Kafka keeps at least the latest record per key and removes older ones in the background. A record with a null value (a tombstone) deletes the key after delete.retention.ms. Use it for "current state" streams: CDC tables, user profiles, configuration, Kafka Streams changelogs and __consumer_offsets itself. A new consumer can rebuild the full current state by reading the topic from the beginning.

How to answer

From your world: a MAC or ARP table that only keeps the latest entry per key.

Likely follow-ups
  • Can you combine compaction and time retention? (compact,delete)
What is a poison message and how do you handle it?

A record that always fails processing (bad format, a bug). In Kafka it blocks its partition, because the consumer cannot commit past it. Handle it: catch the error, retry a few times with backoff (often via retry topics such as orders.retry.1m), then publish it with error headers to a dead-letter topic and commit past it, alert, and provide a tool to inspect and replay the DLQ after a fix. Schema validation at the producer prevents many poison messages.

How to answer

From your world: the punt path for packets the fast path cannot handle. Mention not blocking the partition.

Likely follow-ups
  • How do you keep order if one record goes to a retry topic?
Hot partition - causes and fixes?

A key with far more traffic than others (a celebrity user, a flash-sale SKU, a null-key bug with a custom partitioner) overloads one partition and one consumer. Fixes: choose a higher-cardinality key; add a salt suffix to hot keys (sku123#0..7) and merge downstream if order allows; split hot tenants into their own topic; pre-aggregate at the producer. Detect it with per-partition bytes-in and per-partition lag.

How to answer

Name the signal first (one partition's lag grows while others are flat).

Likely follow-ups
  • What do you lose by salting the key?
How do you replay yesterday's events?

Stop the consumer group (offsets can only be reset when the group is inactive), then reset offsets by time: kafka-consumer-groups.sh --bootstrap-server ... --group billing --topic orders --reset-offsets --to-datetime 2026-11-22T00:00:00.000 --execute. Or replay with a new group ID. Make sure the data is still within retention and that downstream writes are idempotent, because replay re-delivers everything.

How to answer

Command, preconditions (group stopped, data retained), and the idempotency warning.

Likely follow-ups
  • What if the data is already past retention? (tiered storage, or the data lake)
What happened to ZooKeeper, and what is KRaft?

Kafka used to keep cluster metadata in ZooKeeper. KRaft replaces it with a Raft-replicated metadata log (__cluster_metadata) run by a small quorum of controller nodes (typically 3); brokers replicate the metadata log instead of being pushed updates. Kafka 4.0 (March 2025) removed ZooKeeper entirely. Benefits: one system to run and secure, faster controller failover and much higher partition limits. Migration had to happen on 3.x (3.9 is the bridge) before upgrading to 4.x.

How to answer

Before/after picture, three benefits, and the migration fact to show you are current.

Level 4 - Advanced 12 questions

Why is Kafka so fast if it writes to disk?

(1) Sequential appends - no random seeks. (2) The OS page cache does the caching; reads of recent data come from memory. (3) Zero-copy sendfile() moves bytes from page cache to the socket without copying through user space. (4) Batching and per-batch compression amortise network and disk cost. (5) The same binary format on disk and on the wire, so the broker does not re-encode. Note: zero-copy does not apply with TLS, since encryption happens in user space.

How to answer

List the five, then the TLS caveat - the caveat is what interviewers remember.

Likely follow-ups
  • Why does a consumer reading old data hurt tail readers? (page cache pollution and disk reads)
Does Kafka fsync every message? How is it durable then?

No. By default Kafka leaves flushing to the OS. Durability comes from replication: with acks=all and min.insync.replicas=2, a record is acknowledged only when at least two brokers have it in memory, so a single machine crash does not lose it. Losing all replicas at the same instant (a whole-rack power loss with no rack awareness) is the risk, which is why replicas are spread across racks or zones with broker.rack.

How to answer

Contrast "durable by disk" vs "durable by copies"; networking folks know this from replicated state machines.

Likely follow-ups
  • When would you force flushes?
What does a segment file look like on disk?

Each partition is a directory such as orders-3/. Inside are segments named by their base offset: 00000000000000000000.log (records), .index (sparse offset to byte position), .timeindex (timestamp to offset), plus producer snapshots and the leader-epoch checkpoint. Only the newest (active) segment is written; retention deletes whole old segments. Default segment size is 1 GiB.

How to answer

Show the file listing. Explain why sparse indexes plus a binary search make offset lookup cheap.

Likely follow-ups
  • Why does retention not free space until a segment rolls?
How do Kafka transactions give exactly-once read-process-write?

A producer with a transactional.id calls initTransactions() (fencing older instances by bumping the epoch), then beginTransaction(), sends output records to many partitions, adds the consumer's offsets with sendOffsetsToTransaction(), and calls commitTransaction(). The transaction coordinator logs state in __transaction_state and writes commit or abort markers into every partition. Consumers with read_committed only see committed records. It covers Kafka-to-Kafka only, not external side effects.

How to answer

Walk the API calls in order, then the scope limit.

Likely follow-ups
  • What is a zombie producer and how is it fenced?
Unclean leader election - when is it acceptable?

If every in-sync replica is gone, the partition is offline. unclean.leader.election.enable=true lets an out-of-sync replica become leader: the partition comes back, but records it never received are lost forever. It is off by default. Acceptable only where availability beats completeness (metrics, logs, clickstream), never for orders or payments. Kafka 4.x also has Eligible Leader Replicas, which safely widens the set of replicas that may lead without losing committed data.

How to answer

Frame it as CAP made visible: availability vs consistency for one partition.

Likely follow-ups
  • How would you detect that data was lost this way?
linger.ms and batch.size - what is the trade-off?

The producer sends a batch when it reaches batch.size (default 16 KiB) or when linger.ms expires (default 5 ms since Kafka 4.0, earlier 0). Waiting longer builds bigger batches: better compression, fewer requests, higher throughput, but more latency. For throughput: batch 64-256 KiB, linger 10-50 ms, lz4 or zstd compression. For latency: small linger.

How to answer

From your world: interrupt coalescing / NAPI budget - trading latency for throughput.

Likely follow-ups
  • What happens when the producer buffer is full? (send() blocks up to max.block.ms, then throws - that is backpressure)
Schema evolution: how does Schema Registry stop you from breaking consumers?

Producers register schemas per subject (orders-value) and embed only a 4-byte schema ID in each message (after a magic byte). The registry checks each new version against a compatibility mode: BACKWARD (default; new schema can read old data, upgrade consumers first), FORWARD, FULL and the transitive variants. Safe Avro changes: add fields with defaults, remove fields that had defaults; never change a type in place.

How to answer

Explain the wire format briefly, then the compatibility modes with "who upgrades first".

Likely follow-ups
  • How would you rename a field safely?
What is the outbox pattern and why not just write to the DB and Kafka?

The dual-write problem: if the service commits to the DB and then publishes to Kafka, a crash in between leaves them inconsistent (or the reverse). With the outbox, the service writes the business row and an outbox row in one DB transaction. A relay - often Debezium reading the DB's transaction log - publishes outbox rows to Kafka. The DB is now the single source of truth and events are published at least once; consumers dedupe by event ID.

How to answer

Show the crash window first, then the fix. Name CDC and Debezium.

Likely follow-ups
  • What are the costs? (extra table, relay lag, replication slot management)
Kafka Streams vs Flink vs a plain consumer?

A plain consumer is fine for stateless per-record work (enrich, route, write to a DB). Kafka Streams is a library inside your service: stateful operations (joins, windows, aggregations) with local RocksDB state backed by changelog topics; no extra cluster. Flink is a separate cluster with checkpointed state, strong event-time windowing and SQL - better for large, shared, stateful pipelines. Rule of thumb: Streams for app-embedded processing, Flink for big platform jobs.

How to answer

Decide by state size, team ownership and ops appetite.

Likely follow-ups
  • Where does Kafka Streams keep state when a pod moves?
Share groups (Queues for Kafka) - when would you use them?

Share groups (KIP-932, production ready in Kafka 4.2) let many consumers read the same partition, each record acquired with a time-limited lock and acknowledged individually (accept, release, reject, renew). Failed records are redelivered up to a delivery limit, and since 4.4 can go to a DLQ. Use them for work-queue jobs where per-record acks and scaling past the partition count matter more than ordering. Trade-off: no per-partition ordering.

How to answer

Compare with consumer groups in one line: "ordered and partition-bound vs unordered and elastic".

Likely follow-ups
  • Would you still pick SQS or RabbitMQ? When?
Multi-region Kafka: what are the options?

(1) Active-passive with MirrorMaker 2 replicating topics and translating consumer offsets to a DR cluster: simple, async, so a failover may lose the last seconds and re-deliver some. (2) Active-active with MirrorMaker 2 in both directions and prefixed topic names to avoid loops; consumers read local plus remote topics. (3) A stretch cluster across nearby regions with synchronous replication: no data loss, but cross-region latency on every write. Pick by RPO/RTO and latency budget.

How to answer

Name the three, then pick using RPO and RTO language.

Likely follow-ups
  • How do consumers resume at the right offset after failover?
What does tiered storage change?

Closed segments are uploaded to object storage (via a remote storage plugin) and deleted locally after local.retention.ms, while retention.ms sets total retention. Benefits: much cheaper long retention, smaller local disks, faster broker replacement and rebalancing (less data to copy). Limits: compacted topics are not supported, and reading old data now has object-storage latency. Production ready since Kafka 3.9.

How to answer

Cost and elasticity are the two wins; name one limit.

Likely follow-ups
  • Does Kafka ship an S3 plugin? (no; it ships the interface)

Level 5 - Interview-ready 5 questions

Broker disk is 95% full at 3 am. What do you do?

Stabilise first: find the topics growing fastest (kafka-log-dirs.sh --describe), temporarily lower retention.ms or retention.bytes on non-critical high-volume topics (whole old segments delete within the retention check interval, 5 min by default), or add disk if the platform allows. Do not delete files by hand. Then root cause: a producer bug flooding a topic, retention set too long, a partition reassignment in progress, or uneven partition placement. Prevent: disk alerts at 70/80%, quotas per client, capacity planning, tiered storage.

How to answer

Stabilise, find, fix, prevent. Say clearly what you would never do (rm segment files).

Likely follow-ups
  • What happens to a broker whose disk fills completely? (the log directory goes offline)
A consumer group rebalances every few minutes. Diagnose it.

Usually consumers exceed max.poll.interval.ms (5 min default): processing a batch of up to 500 records takes too long, the consumer is kicked out, partitions move, duplicates follow. Other causes: missed heartbeats (session.timeout.ms, GC pauses, CPU throttling in Kubernetes), crash loops, or pods restarting during deploys. Fixes: fewer records per poll, faster or async processing with care for commits, static membership for rolling restarts, the cooperative or KIP-848 protocol, and right-sized CPU.

How to answer

Ask "what changed?" then read the consumer logs for "leaving group" reasons. Tie in CPU throttling as a Kubernetes cause.

Likely follow-ups
  • How do you prove it is max.poll.interval? (log messages and the rebalance rate metric)
Messages came out of order after retries. Why?

With idempotence disabled and more than one in-flight request per connection, batch 1 can fail and be retried after batch 2 succeeded, so 2 lands before 1. Fix: keep enable.idempotence=true (the default) with max.in.flight.requests.per.connection up to 5, which lets the broker enforce sequence order. Also check the key: if related events use different keys, they were never ordered in the first place.

How to answer

Explain the race, then the two-part check (producer settings and key choice).

Likely follow-ups
  • Can consumers reorder records? (yes, if they process in parallel threads)
Design retry with backoff and a DLQ on Kafka.

Main consumer fails a record: publish it to topic.retry.1m with headers (attempt count, error, original offset) and commit. A retry consumer reads it, waits until the timestamp plus delay, then reprocesses; failures go to retry.10m, then topic.dlq. Never sleep inside the main consumer (it blocks the partition and trips max.poll.interval.ms). Add an inspection UI and a replay tool for the DLQ, and alert on DLQ rate. If strict per-key ordering matters, park later records of the same key too.

How to answer

Draw the chain of topics. Cover ordering, idempotency and observability - the three things interviewers poke.

Likely follow-ups
  • Why not just retry in place forever?
Design Kafka itself: what are the core components?

Brokers storing partitions as segmented append-only logs; replication with leader/followers and an ISR; a metadata quorum (KRaft) that tracks brokers, topics and leaders; producers that batch and route by key; consumer groups with a coordinator and committed offsets in an internal topic; retention and compaction; zero-copy reads from the page cache. Then failure handling: leader election from ISR, fencing with epochs, and rack-aware placement.

How to answer

Build it in layers: single log, then partitioning, then replication, then groups, then metadata. Each layer answers a scaling or failure question.

Likely follow-ups
  • How would you add delayed messages to it?
