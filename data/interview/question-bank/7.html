Data pipeline questions (19)

Getting data in, processing it in streams, getting it out correctly, and operating the whole chain. Concept pages: ShopStream project, stream processing, retries and DLQ, failure drills.

Level 2 - Beginner 3 questions

What does a data pipeline look like from a click in the app to a number on a dashboard?

The app (or its database) emits an event; it lands in a Kafka topic (raw events); a stream processor validates, enriches, deduplicates and aggregates it (for example counts per minute); results go to a sink - an OLAP store, a cache, a search index or a data lake; the dashboard queries the sink. Around it: a schema registry for contracts, a dead-letter topic for bad records, and monitoring of lag and end-to-end latency.

How to answer

Draw six boxes left to right and name one technology per box. Then say what you would monitor.

Likely follow-ups
  • Where would you put the deduplication step?
Where does data enter Kafka: the app, a log shipper or CDC?

Three common ways. Direct produce from the service (lowest latency, but the service owns delivery and the dual-write risk). Log shippers (Fluent Bit, Vector) tail log files and forward them - good for logs and metrics. CDC (Debezium) reads the database's transaction log and emits row changes - no app changes, consistent with what was committed, ideal with the outbox pattern.

How to answer

Give each its best use case. Pick CDC/outbox when the event must match a DB write.

Likely follow-ups
  • What does a Debezium change event contain? (before, after, op, source)
Batch vs streaming - when is a nightly job fine?

Batch is fine when the answer can be hours old and correctness over complete data matters more than freshness: invoicing, monthly reports, model training, reconciliation. Streaming is needed when the value decays fast: fraud checks, live inventory, alerting, recommendations. Streaming costs more to build and run (state, late data, always-on). Many systems do both: streaming for fresh approximate numbers and batch for the final correct ones.

How to answer

Ask "how old can the answer be?" out loud, then decide.

Likely follow-ups
  • What is the Lambda vs Kappa architecture?

Level 3 - Intermediate 7 questions

Explain tumbling, sliding and session windows with a clock.

Tumbling: fixed, non-overlapping buckets - 12:00-12:05, 12:05-12:10; each event falls in exactly one. Hopping/sliding: windows of 5 minutes that start every minute, so they overlap and one event counts in several. Session: a window per user that stays open while events keep arriving and closes after a gap of inactivity (say 30 minutes), so its length varies.

How to answer

Draw a timeline with dots and brackets; it beats any definition.

Likely follow-ups
  • Which window would you use for "orders per minute" on a dashboard?
Event time vs processing time, and how does a system decide a window is done?

Event time is when it happened (stamped by the device); processing time is when the processor sees it. Mobile events can arrive minutes late and out of order. Stream processors track a watermark: "I believe all events before time T have arrived". A window closes when the watermark passes its end plus an allowed lateness (grace period). Later events are dropped, sent to a side output, or trigger an update to an already-emitted result.

How to answer

Use the example of a phone in a tunnel. Then watermark and grace period. Then the three options for very late events.

Likely follow-ups
  • How do you choose the grace period?
What is backpressure in a pipeline, and who slows down whom?

When a downstream stage cannot keep up, upstream must slow or buffer. With Kafka in the middle, the buffer is the topic itself: producers keep writing, the slow consumer simply falls behind (lag grows) without pushing back on producers, until retention runs out. Inside a processor like Flink, backpressure propagates through bounded network buffers back to the source, which reads more slowly. At the producer, a full buffer.memory blocks send().

How to answer

From your world: TCP flow control and PFC pause frames. Kafka is a giant buffer that decouples the two speeds.

Likely follow-ups
  • What is the danger if lag grows past retention? (data loss for that consumer)
How do you avoid duplicates at the sink?

Assume at-least-once delivery and make writes idempotent. Options: upsert by a natural or event key (INSERT ... ON CONFLICT DO UPDATE), a processed-events table checked in the same transaction as the write, conditional writes with a version number, or a sink connector in upsert mode. For aggregates, make the aggregation keyed by event ID or use exactly-once processing within Kafka and an idempotent final write.

How to answer

"Exactly-once delivery is hard; idempotent effects are easy." Then two concrete SQL patterns.

Likely follow-ups
  • How long must you keep processed IDs?
How do schema changes roll out without breaking old consumers?

Use a schema registry with BACKWARD compatibility (the default): add new fields with defaults, upgrade consumers first if they need the new field, then producers. For breaking changes, create a new topic version (orders.v2), dual-publish for a migration window, move consumers, then retire the old topic. Contract tests in CI catch incompatible changes before deploy.

How to answer

Show the safe path and the breaking path separately.

Likely follow-ups
  • Who should own the schema - producer or consumer team?
How do you test a pipeline locally?

A Docker Compose file with one Kafka broker in KRaft mode, the schema registry if used, the database and your services is enough for development and integration tests. Add a health check on Kafka and depends_on: condition: service_healthy, configure two listeners (one for containers, one for the host), and seed test data with a script. In CI use Testcontainers to spin the same broker per test suite. Load and failure behaviour still need a staging cluster.

How to answer

Say what local covers (logic, contracts, happy path) and what it does not (scale, multi-broker failures).

Likely follow-ups
  • Why does the app fail to connect to localhost:9092 from inside a container? (advertised listeners)
What do you monitor in a streaming pipeline?

Per stage: throughput (records/s in and out), consumer lag in records and in seconds, error rate and DLQ rate, processing latency, and the end-to-end latency (event time to sink write time) against an SLO. Platform: broker under-replicated and offline partitions, request latency, disk usage; processor checkpoint duration and failures; sink write errors. Plus a data quality check: counts at source vs sink.

How to answer

Group by "is it flowing", "is it correct", "is it healthy".

Likely follow-ups
  • How would you measure end-to-end latency? (embed the event timestamp, compare at the sink)

Level 4 - Advanced 6 questions

Explain the dual-write problem with a concrete failure.

An order service writes an order row to Postgres and then publishes OrderCreated to Kafka. The DB commit succeeds, then the pod is OOMKilled before the publish. Now the order exists but inventory, email and analytics never hear about it. Reversing the order (publish first) creates phantom events for orders that failed to commit. There is no transaction spanning both systems, so one of them can always be out of step. Fix: transactional outbox plus CDC, or event sourcing with Kafka as the source of truth.

How to answer

Tell it as a two-line story with a crash in the middle. Then the fix.

Likely follow-ups
  • Why not use 2PC between the DB and Kafka?
What is CDC with Debezium, and what can go wrong?

Debezium is a set of Kafka Connect source connectors that read the database's change log (Postgres WAL through a logical replication slot, MySQL binlog), take an initial snapshot, then stream each committed row change as an event with before/after values. Gotchas: an unused or stalled Postgres replication slot keeps WAL forever and can fill the database disk; schema changes need handling; large snapshots take time; and the events reflect tables, so use the outbox to publish business events instead of raw table internals.

How to answer

Explain the mechanism, then lead the gotchas with the replication-slot disk-fill story.

Likely follow-ups
  • How would you monitor the slot? (replication lag and retained WAL size)
Where is state kept in a stream processor, and what happens when an instance dies?

Kafka Streams keeps state in local RocksDB stores, backed up to compacted changelog topics; when a task moves to another instance it restores state from the changelog (standby replicas make that faster). Flink keeps state in its state backend (heap or RocksDB) and takes periodic checkpoints to durable storage; on failure the job restarts from the last checkpoint and rewinds Kafka offsets to match, which gives exactly-once state.

How to answer

Compare the two recovery stories in one sentence each.

Likely follow-ups
  • Why can restore take a long time, and how do you shorten it?
Your consumer had a bug for 3 hours. How do you fix the data?

Fix and deploy the consumer. Decide the blast radius: which outputs were wrong. Then reprocess: reset the group's offsets to just before the bug (--to-datetime) or run a separate backfill group writing to a new table, making sure sink writes are idempotent upserts so reprocessing overwrites bad rows. Verify with counts and spot checks, then switch reads. Kafka's retention is what makes this possible - a queue that deletes on ack could not do it.

How to answer

Fix, scope, replay, verify. Mention idempotent sinks as the precondition for safe replay.

Likely follow-ups
  • What if downstream services already acted on the bad data (for example sent emails)?
How would you scale consumers automatically on Kubernetes?

Use KEDA with the Kafka scaler: it reads consumer lag for the group and drives an HPA, scaling replicas up when lag per partition crosses a threshold and down (even to zero) when idle. Cap maxReplicas at the partition count, because extra consumers sit idle. Use static membership and cooperative rebalancing so scaling events do not stall the group, and make sure the cluster has node headroom.

How to answer

Name KEDA, the metric (lag), the cap and the rebalance cost of scaling.

Likely follow-ups
  • Why not scale on CPU?
Is running Kafka on Kubernetes a good idea?

It can be, with an operator such as Strimzi, which handles broker identity, storage, rolling restarts, certificates and rebalancing through CRDs. It is a good fit when the company already runs a strong Kubernetes platform and wants one way to operate everything. It is a poor fit when the team is small: a managed service (MSK, Confluent Cloud, Event Hubs for Kafka) removes most of the operational load. Either way, use fast persistent disks, spread brokers across zones and plan per-broker external access.

How to answer

Give a conditional answer with the deciding factors; interviewers dislike absolute claims here.

Likely follow-ups
  • What is the first thing that goes wrong for teams new to Kafka on K8s?

Level 5 - Interview-ready 3 questions

Design an order events pipeline for an e-commerce site.

Order service writes orders plus an outbox row in Postgres; Debezium publishes to orders keyed by order_id (RF 3, min ISR 2). Consumers: inventory reservation, payment, notifications, and a Flink job computing real-time sales per category into an OLAP store for dashboards; a sink connector lands raw events in the data lake. Retries and DLQ per consumer, idempotent handlers keyed by event ID, schema registry with backward compatibility, KEDA autoscaling on lag, and alerts on lag-in-seconds and DLQ rate.

How to answer

Follow the data, name the key and the durability settings, then failure handling and monitoring.

Likely follow-ups
  • How do you keep inventory correct if the payment fails? (saga with compensation)
End-to-end latency jumped from 2 s to 5 minutes. Walk me through it.

Find the stage where time is spent: compare event timestamps at each hop or lag per consumer group. If one group's lag grows: check its throughput, errors, rebalances, and whether it is one hot partition. If all lag: check brokers (under-replicated partitions, request latency, disk) and the producer. If lag is fine but the sink is slow: database locks, connection pool, slow upserts. Mitigate (scale consumers up to the partition count, pause non-critical consumers, raise sink capacity), then fix the root cause.

How to answer

Bisect the pipeline like a packet path: find the hop where the delay appears.

Likely follow-ups
  • What dashboard would have caught this earlier?
How do you guarantee an analytics count is "effectively once" end to end?

Producer: idempotent (default) and outbox for DB-derived events. Processing: Kafka Streams with exactly_once_v2 or Flink checkpoints with a transactional Kafka sink, so counts and offsets commit together. Sink: idempotent upserts keyed by (window, dimension) so a replay overwrites rather than adds. Verification: reconcile counts against the source of truth daily.

How to answer

Cover each stage; say honestly that "exactly once" is a property of the whole chain, not of one setting.

Likely follow-ups
  • What breaks it? (a non-idempotent side effect anywhere in the chain)
