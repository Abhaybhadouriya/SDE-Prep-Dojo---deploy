Kubernetes questions (37)

Architecture, workloads, networking, scheduling, probes, autoscaling, security and production failures. Concept pages: Kubernetes track, Services and networking, troubleshooting, Kubernetes interview page.

Level 2 - Beginner 7 questions

What problem does Kubernetes solve that Docker plus a shell script on 10 machines does not?

The script starts containers once. Kubernetes keeps them right forever: it picks a machine with room (scheduling), restarts or replaces failed containers (self-healing), gives a stable name and IP in front of moving pods (Services), rolls out new versions without downtime and rolls back, scales replicas on load, and stores all of it as declarative desired state that control loops reconcile continuously.

How to answer

Contrast "imperative, one-shot" with "declarative, continuous". Give four concrete jobs the script would have to reinvent.

Likely follow-ups
  • When is Kubernetes overkill?
  • What runs the reconciliation?
Name the control plane and node components and what each does.

Control plane: kube-apiserver (the only door; validates and stores objects; the only thing that talks to etcd), etcd (Raft-replicated key-value store, the source of truth), kube-scheduler (assigns unscheduled pods to nodes), kube-controller-manager (many control loops: Deployment, ReplicaSet, Node, Job, EndpointSlice), cloud-controller-manager (cloud load balancers, node lifecycle). Node: kubelet (agent that runs pods bound to its node via the CRI), kube-proxy (programs Service rules), the container runtime (containerd or CRI-O) and the CNI plugin (pod networking).

How to answer

One line per component, in the order a request flows. Say "everything goes through the API server" - it shows you understand the hub-and-spoke design.

Likely follow-ups
  • What happens if the scheduler is down?
  • Can you scale the API server horizontally?
What is a Pod, and why not schedule containers directly?

A Pod is the smallest unit Kubernetes schedules: one or more containers that always land on the same node and share a network namespace (one IP, talk over localhost), IPC and volumes. A hidden pause container holds the namespaces. This lets tightly coupled helpers (a log shipper, a proxy sidecar, an init step) live with the app as one unit, without merging them into one image.

How to answer

Give the shared-namespace detail (it is literally --network container: in Docker terms) and one sidecar example.

Likely follow-ups
  • When would you put two containers in one pod vs two pods?
  • What is a native sidecar?
Deployment vs StatefulSet vs DaemonSet vs Job - when do you use each?

Deployment: stateless replicas that are interchangeable (web APIs). StatefulSet: replicas that need a stable name (kafka-0), a stable per-pod disk and ordered start/stop (databases, Kafka, ZooKeeper-style quorums). DaemonSet: exactly one pod per node (log agents, CNI, node exporters). Job: run to completion (migrations, batch); CronJob runs Jobs on a schedule.

How to answer

Ask yourself two questions out loud: "Does each copy need its own identity or disk?" and "Does it ever finish?" The answers pick the controller.

Likely follow-ups
  • Why is a StatefulSet pod not replaced when its node becomes unreachable?
ClusterIP vs NodePort vs LoadBalancer vs headless Service?

ClusterIP (default): a virtual IP reachable only inside the cluster. NodePort: also opens the same port (default range 30000-32767) on every node. LoadBalancer: also asks the cloud for an external load balancer pointing at the nodes or pods. Headless (clusterIP: None): no virtual IP; DNS returns the pod IPs directly, which StatefulSets and Kafka clients need to reach a specific pod. ExternalName is just a DNS CNAME.

How to answer

Present them as layers (each type builds on the previous), then headless as the odd one out.

Likely follow-ups
  • Which one is "the front door" for HTTP traffic? (usually a Gateway or Ingress behind one LoadBalancer)
ConfigMap vs Secret - is a Secret encrypted?

Both inject config as env vars or files. Secrets are only base64-encoded, not encrypted by default: anyone with get secrets permission or etcd access can read them. To protect them: enable encryption at rest (EncryptionConfiguration with a KMS provider), tighten RBAC, and/or keep the real value in Vault or a cloud secret manager via External Secrets Operator or the Secrets Store CSI driver. Both objects are limited to 1 MiB.

How to answer

Say "base64 is encoding, not encryption" in the first sentence. Then give the three protections.

Likely follow-ups
  • Do env vars update when the ConfigMap changes? (no; mounted files update eventually, subPath never)
Is a Kubernetes namespace the same as a Linux namespace?

No - same word, different thing. A Kubernetes namespace is an API grouping: a name scope for objects plus a boundary for RBAC, ResourceQuota, LimitRange and NetworkPolicy. A Linux namespace is a kernel feature that isolates what a process sees (pid, net, mnt...). Pods in different Kubernetes namespaces can still talk to each other unless a NetworkPolicy says otherwise.

How to answer

State the confusion explicitly - interviewers sometimes test it on purpose.

Likely follow-ups
  • How would you isolate two teams in one cluster?

Level 3 - Intermediate 14 questions

Walk me through kubectl apply -f deployment.yaml until the pod serves traffic.

(1) kubectl sends the object to the API server: authentication, RBAC authorization, mutating admission, schema validation, validating admission, then it is stored in etcd. (2) The Deployment controller sees it and creates a ReplicaSet. (3) The ReplicaSet controller creates Pods with no node. (4) The scheduler filters and scores nodes and writes a binding. (5) The kubelet on that node sees its new pod, asks the runtime via CRI to create the sandbox (pause container, network namespace); the CNI plugin assigns the pod IP. (6) The image is pulled and containers start; probes run. (7) When the readiness probe passes, the EndpointSlice controller adds the pod IP, and kube-proxy on every node updates its rules. Traffic flows.

How to answer

Name the process at every step and say "watch" (not polling) for how each component learns about changes. This is the single most valuable K8s answer to rehearse.

Likely follow-ups
  • Where can it get stuck, and what status would you see at each point?
What does "desired state" and "reconciliation loop" mean?

You store what you want (3 replicas of image X) in the API server. Each controller runs a loop: observe actual state (via watches), compare with desired, act to close the gap, repeat. It is level-triggered: if a controller misses an event, the next pass still sees the difference and fixes it. That makes the system self-healing and idempotent.

How to answer

Use the routing daemon analogy: the RIB says what should be in the FIB, a loop keeps pushing until they match.

Likely follow-ups
  • What is the difference between level-triggered and edge-triggered here?
How does a Service route traffic to pods whose IPs keep changing?

A Service selects pods by label. The EndpointSlice controller keeps a list of ready pod IPs for it. kube-proxy on every node watches Services and EndpointSlices and programs kernel rules (iptables by default, nftables recommended, IPVS deprecated) that DNAT the virtual ClusterIP:port to one ready pod IP:port. CoreDNS maps svc.namespace.svc.cluster.local to the ClusterIP. The ClusterIP is on no interface - it exists only in NAT rules - which is why you cannot ping it.

How to answer

Three moving parts: selector to EndpointSlice, kube-proxy rules, DNS. Then the "cannot ping" detail that proves you understand it is NAT.

Likely follow-ups
  • How does Cilium replace kube-proxy?
  • Why is iptables mode slow with tens of thousands of Services?
Liveness vs readiness vs startup probes - how do they hurt you if wrong?

Readiness failing removes the pod from Service endpoints (no restart). Liveness failing restarts the container. Startup holds off the other two until the app has booted. Defaults: period 10 s, timeout 1 s, failure threshold 3. Classic mistakes: a liveness probe that checks a database (DB blips, every pod restarts at once - a self-inflicted outage); no startup probe for a slow JVM (killed while booting, CrashLoopBackOff); no readiness probe (traffic hits pods that are not ready during rollouts).

How to answer

Define each by its action (remove vs restart vs wait), then give the cascading-restart story.

Likely follow-ups
  • What should a liveness endpoint check? (only "is this process stuck", nothing external)
Requests vs limits, QoS classes, throttling vs OOMKilled?

Requests are what the scheduler reserves; limits are hard caps enforced by cgroups. Over the CPU limit the container is throttled (CFS quota); over the memory limit it is OOMKilled (exit 137). QoS: Guaranteed (requests = limits for CPU and memory in every container), Burstable (some requests set), BestEffort (nothing set). Under node memory pressure the kubelet ranks pods for eviction by whether their usage exceeds their requests, then by PriorityClass, then by how far over requests they are. In practice BestEffort and over-request Burstable pods go first, and Guaranteed pods under their requests go last. (Note that PriorityClass can override the QoS-like order.)

How to answer

Use the hotel analogy (requests = booked room, limits = the room walls), then the two failure modes, then QoS ordering.

Likely follow-ups
  • Why do many teams set CPU requests but no CPU limit?
  • How does the scheduler pick a node if all are 90% used by real usage but not by requests?
How does a rolling update avoid downtime? What are maxSurge and maxUnavailable?

The Deployment creates a new ReplicaSet and shifts pods over gradually. maxSurge (default 25%) is how many extra pods may exist above the desired count; maxUnavailable (default 25%) is how many may be missing. A new pod only counts once its readiness probe passes, so old pods are removed only as new ones are ready. For zero dropped requests you also need graceful shutdown: a preStop sleep so endpoint removal propagates before SIGTERM, and an app that drains connections.

How to answer

Explain the two knobs with a concrete example (10 replicas: up to 13 pods, at least 8 ready), then the shutdown detail most people miss.

Likely follow-ups
  • How do you roll back? (kubectl rollout undo)
  • Canary vs blue-green on Kubernetes?
Pod is stuck in Pending. How do you debug it?

Pending means not yet scheduled (or waiting on volumes). kubectl describe pod and read Events: "Insufficient cpu/memory" (requests too big or cluster full - cluster autoscaler should add a node), "didn't match node affinity/selector", "untolerated taint", "pod has unbound PersistentVolumeClaims" or "volume node affinity conflict" (zone mismatch - use WaitForFirstConsumer), or a ResourceQuota blocking creation.

How to answer

Lead with "describe and read Events", then group causes by resources, placement rules and storage.

Likely follow-ups
  • Why can a cluster with 50% real CPU usage still have Pending pods?
A pod is in CrashLoopBackOff. Walk me through it.

CrashLoopBackOff is not a phase; it means the container keeps exiting and the kubelet waits longer between restarts (by default 10 s, doubling, capped at 5 min; since 1.35 the kubelet can be configured with a lower maximum backoff, KEP-5593, beta). Steps: kubectl describe pod (last state, exit code, events), kubectl logs <pod> --previous (logs of the crashed run). Exit 137 + OOMKilled: raise the limit or fix memory. Exit 1: app error - often a missing env var, Secret or ConfigMap key, or a wrong command. Liveness failures in events: probe too aggressive. If the image has no shell, use kubectl debug with an ephemeral container.

How to answer

Explain what the status means, then a decision tree by exit code. Interviewers want commands, not guesses.

Likely follow-ups
  • What if --previous logs are empty?
ImagePullBackOff - what are the usual causes?

Wrong image name or tag (typo, tag never pushed), a private registry without imagePullSecrets or node IAM permission, registry rate limits (Docker Hub anonymous pulls are limited per IP over 6 hours, and a NAT gateway shares one IP across the cluster), wrong architecture manifest, or network/DNS from the node to the registry. kubectl describe pod shows the exact pull error.

How to answer

List causes from most to least common and say "read the event message" first.

Likely follow-ups
  • How do you avoid Docker Hub limits in a big cluster? (mirror or pull-through cache, authenticated pulls)
How does pod-to-pod networking work across nodes?

The Kubernetes network model says every pod has its own IP and can reach every other pod without NAT. A CNI plugin makes it true. Each node owns a pod CIDR. Overlay CNIs (Flannel VXLAN, Calico VXLAN or IP-in-IP) encapsulate the pod packet in a node-to-node packet. Routed CNIs (Calico BGP) advertise each node's pod CIDR to the network so packets go natively. eBPF CNIs (Cilium) do routing and policy in eBPF. Cloud CNIs (AWS VPC CNI) give pods real VPC IPs.

How to answer

This is your home turf - talk VTEPs, BGP peering, MTU overhead of VXLAN (about 50 bytes). It is a chance to shine.

Likely follow-ups
  • What is the cost of an overlay?
  • How do you run out of IPs with AWS VPC CNI?
Ingress vs Gateway API vs a LoadBalancer Service?

A LoadBalancer Service gives one external L4 entry per Service. Ingress is an L7 HTTP routing object (host and path to Service) implemented by a controller; the API is stable but frozen and many features hide in vendor annotations. Gateway API is the newer, role-split model: GatewayClass (provider), Gateway (listeners, TLS - owned by the platform team), HTTPRoute/GRPCRoute/TLSRoute (owned by app teams), with weighted traffic splitting and cross-namespace rules built in. Note that the community Ingress NGINX controller was retired in March 2026; the Ingress API itself still exists.

How to answer

Explain who owns what in Gateway API - that is the reason it exists. Mention the retirement to show you are current.

Likely follow-ups
  • How would you do a 5% canary with Gateway API?
PV vs PVC vs StorageClass?

A PersistentVolume is a real piece of storage (a cloud disk, an NFS share). A PersistentVolumeClaim is a pod's request ("10 GiB, ReadWriteOnce"). A StorageClass is a recipe that lets a CSI driver create PVs on demand when a claim appears (dynamic provisioning). Access modes: RWO (one node), ROX, RWX, RWOP (one pod). Use volumeBindingMode: WaitForFirstConsumer so the disk is created in the same zone the pod is scheduled to.

How to answer

Use the parking analogy: PVC is the ticket, PV is the spot, StorageClass is the valet who builds new spots.

Likely follow-ups
  • What happens to the disk when the PVC is deleted? (reclaim policy Delete or Retain)
What is etcd, why Raft, and why odd member counts?

etcd is the cluster's key-value store and single source of truth; only the API server talks to it. Raft keeps the replicas consistent: a leader orders writes and a write commits when a majority has it. Quorum = floor(n/2)+1, so 3 members tolerate 1 failure and 5 tolerate 2; 4 members still tolerate only 1, so even counts add cost without adding tolerance. If quorum is lost, etcd stops accepting writes: the API server cannot change anything, but running pods keep running.

How to answer

Do the quorum maths out loud and end with the "running pods survive" point.

Likely follow-ups
  • How do you back up etcd? (etcdctl snapshot save)
  • What is the default storage quota? (2 GB)
If the control plane dies, do running pods die?

No. Kubelets keep running the pods they already have, and kube-proxy rules stay in the kernel, so existing traffic keeps flowing. What you lose: no new scheduling, no self-healing (a crashed pod on a dead node is not replaced), no scaling, no rollouts, no Service endpoint updates. It is exactly like non-stop forwarding on a router: the data plane forwards with the last programmed tables while the control plane is down.

How to answer

Separate data plane (keeps working) from control plane (frozen), then list what freezes.

Likely follow-ups
  • What breaks first in practice? (endpoint updates during pod churn)

Level 4 - Advanced 12 questions

A node dies. What happens to its pods, and how long does it take?

The kubelet stops renewing its Lease. After the node monitor grace period (about 50 s in current docs) the node controller marks it NotReady/Unknown and adds not-ready/unreachable taints. Pods have a default toleration of 300 s for those taints, so they are evicted roughly 5 minutes later; the ReplicaSet controller then creates replacements elsewhere. Meanwhile, endpoints for those pods are removed once the node is NotReady. StatefulSet pods are not replaced automatically until the node is confirmed gone, to avoid two pods with one identity.

How to answer

Give the timeline with numbers and name the controller at each step. Then the StatefulSet caveat. Offer the tuning: shorter tolerationSeconds for latency-critical apps.

Likely follow-ups
  • How would you make failover faster?
  • Why is it deliberately slow?
How does the HPA decide how many replicas?

Every 15 s it computes desired = ceil(current * currentMetric / targetMetric), with a 10% tolerance band to avoid flapping and a 5-minute scale-down stabilisation window by default. CPU utilisation is measured relative to requests, so pods without requests cannot be scaled on CPU. Metrics come from metrics-server, or custom/external metrics adapters (Prometheus Adapter, KEDA). KEDA can scale on Kafka consumer lag and scale to zero. The cluster autoscaler or Karpenter adds nodes when the new pods are Pending.

How to answer

Write the formula, then the "relative to requests" gotcha, then how pods turn into nodes.

Likely follow-ups
  • Why cap a Kafka consumer HPA at the partition count?
  • HPA vs VPA on the same metric?
How does the scheduler pick a node?

Two phases. Filter: drop nodes that cannot run the pod (not enough allocatable CPU or memory by requests, taints not tolerated, node selector or affinity mismatch, port conflicts, volume zone). Score: rank the rest (balanced allocation, least allocated, image locality, topology spread, inter-pod affinity). Highest score wins and the scheduler writes a Binding. It schedules on requests, not on real usage.

How to answer

Filter then score - like admission control then placement. Name three of each.

Likely follow-ups
  • Taints vs node affinity - which repels and which attracts?
  • What is preemption?
Latency spikes every few seconds on a pod with a CPU limit. Why?

CFS quota throttling. With limits.cpu: 1, the container may use 100 ms of CPU per 100 ms period across all threads. A multi-threaded app (JVM GC threads, Go runtime) can burn the quota in 20 ms and then sit frozen for 80 ms, even when the node is idle. Confirm with nr_throttled/throttled_usec in the cgroup cpu.stat or the container_cpu_cfs_throttled_periods_total metric. Fixes: raise or remove the CPU limit (keep requests), right-size thread pools, and make runtimes cgroup-aware.

How to answer

Explain the 100 ms period mechanic - it is the "aha" - then how you prove it and fix it.

Likely follow-ups
  • Why does average CPU look fine on the dashboard?
DNS lookups from pods are slow or time out. What do you check?

Pods get ndots:5 with several search domains, so a name like api.example.com (2 dots) is first tried with every cluster suffix, which multiplies queries. Fixes: use a trailing dot (api.example.com.), lower ndots in dnsConfig, use FQDNs. Then: CoreDNS replicas and CPU, conntrack races on UDP (seen on older kernels), and NodeLocal DNSCache to cut cross-node DNS hops. Test with kubectl run tmp --rm -it --image=busybox -- nslookup kubernetes.default.

How to answer

Start with ndots (the most common cause), then capacity, then the kernel-level race - which you can discuss as a networking person.

Likely follow-ups
  • How would you measure DNS latency in the cluster?
Users see errors for a few seconds during every deploy. Why?

Usually shutdown ordering. When a pod is deleted, endpoint removal and SIGTERM happen in parallel, so for a moment kube-proxy and load balancers still send traffic to a pod that is already shutting down. Fixes: a preStop hook that sleeps a few seconds, the app handling SIGTERM by finishing in-flight requests, terminationGracePeriodSeconds long enough, readiness probes on new pods, and connection draining at the load balancer. Also check maxUnavailable and a PodDisruptionBudget.

How to answer

Say "it is a race between two parallel actions" and show the fix for each side of the race.

Likely follow-ups
  • How do long-lived connections (WebSockets, gRPC) change this?
What is a PodDisruptionBudget?

A PDB limits voluntary disruptions (node drains, cluster upgrades, autoscaler scale-down) for a set of pods: minAvailable: 2 or maxUnavailable: 1. The eviction API refuses to evict a pod if it would break the budget, so a drain waits. It does not protect against involuntary failures like a node crash. Gotcha: a PDB that allows zero disruptions blocks node upgrades forever.

How to answer

Voluntary vs involuntary is the key distinction.

Likely follow-ups
  • How do PDBs interact with Kafka brokers on Kubernetes?
RBAC: Role vs ClusterRole, and how do pods authenticate?

RBAC is additive allow rules (no deny). A Role grants verbs on resources inside one namespace; a ClusterRole is cluster-wide or reusable; RoleBinding/ClusterRoleBinding attach them to users, groups or ServiceAccounts. Pods authenticate as their ServiceAccount with a short-lived, audience-bound projected token. Dangerous grants: * verbs, escalate, bind, impersonate, creating pods (can mount any secret in the namespace). Check with kubectl auth can-i.

How to answer

Define, then least-privilege examples, then the dangerous verbs list.

Likely follow-ups
  • How do you stop a pod from getting an API token at all? (automountServiceAccountToken: false)
NetworkPolicy: what is the default and how do you lock down a namespace?

Default is allow-all. Once any policy selects a pod for a direction (ingress or egress), only traffic matched by some policy is allowed. Common setup: a default-deny ingress policy per namespace, then allow rules by pod labels and namespaces, and if you deny egress, remember to allow DNS (UDP/TCP 53). Policies need a CNI that enforces them (Calico, Cilium; plain Flannel does not).

How to answer

Like ACLs with an implicit deny that only kicks in once a policy exists. Mention the DNS egress trap.

Likely follow-ups
  • Can NetworkPolicy match on HTTP paths? (not the core API; Cilium adds L7 policy)
What are CRDs and operators? Give an example.

A CRD adds a new resource type to the API (for example Kafka). An operator is a controller that watches those objects and reconciles real resources to match, encoding the human runbook: creating brokers, rolling restarts in a safe order, certificate rotation, scaling. Example: Strimzi manages Kafka clusters from Kafka, KafkaNodePool, KafkaTopic and KafkaUser resources. Others: cert-manager, Prometheus Operator, CloudNativePG.

How to answer

CRD = the noun, operator = the verb. Then one real example in depth.

Likely follow-ups
  • What is hard about writing an operator? (idempotency, status, upgrades)
What are the hard parts of running Kafka on Kubernetes?

Brokers are stateful and have identity: they need stable names, persistent volumes per broker, and per-broker addressing - a client must reach the specific partition leader, so advertised listeners must point to each broker (headless Service inside, per-broker NodePort/LoadBalancer outside). Also: rack awareness across zones, PodDisruptionBudgets so drains do not take out quorum, ordered rolling restarts that wait for in-sync replicas, disk sizing, and network throughput. An operator (Strimzi) handles most of this.

How to answer

Lead with "clients must hit a specific broker" - the most common gotcha - then the rest as a list.

Likely follow-ups
  • Would you run Kafka on K8s or use a managed service? Why?
What are sidecars and a service mesh? When is a mesh worth it?

A sidecar is a helper container next to the app in the same pod (a proxy, a log shipper). Native sidecars (init containers with restartPolicy: Always, GA in 1.33) start before and stop after the app. A service mesh (Istio, Linkerd, or sidecar-less modes like Istio ambient or Cilium) puts a proxy on every traffic path to give mTLS, retries, timeouts, traffic splitting and per-call metrics without app code changes. Worth it with many services and strict security or traffic needs; costly in latency, memory and operational complexity for small systems.

How to answer

Define, give three features, then an honest cost-benefit.

Likely follow-ups
  • What is the latency cost of an extra proxy hop?

Level 5 - Interview-ready 4 questions

Design multi-tenant isolation for 30 teams in one cluster.

Namespace per team (or per team-environment) with RBAC bound to team groups; ResourceQuota and LimitRange per namespace; default-deny NetworkPolicy; Pod Security Admission at Restricted; separate node pools with taints for noisy or sensitive workloads; admission policies (Kyverno or ValidatingAdmissionPolicy) for image registry and label rules; per-namespace cost and usage dashboards. For hostile tenants, separate clusters or sandboxed runtimes, because a shared kernel is not a hard boundary.

How to answer

Layer it: identity, quotas, network, pod security, nodes, policy, visibility. Finish with when one cluster is not enough.

Likely follow-ups
  • How do you stop one team's HPA from consuming the whole cluster?
How would you prepare a Kubernetes platform for a 10x flash sale?

Before: load test at 10x, pre-scale (raise HPA minReplicas, pre-warm nodes since node provisioning takes minutes), check IP space, quotas and cloud limits, scale CoreDNS and ingress, set PDBs, freeze deploys. During: dashboards for saturation (CPU throttling, pending pods, LB 5xx), rate limiting and load shedding at the edge, feature flags to switch off expensive features. After: scale down gradually and review. Flipkart publicly described chaos engineering ahead of Big Billion Days as part of this preparation.

How to answer

Before / during / after keeps it tidy. Mention that autoscaling is too slow for a cliff-edge spike, so you pre-scale.

Likely follow-ups
  • What breaks first when everything autoscales at once?
GitOps with Argo CD - why pull-based deployment?

Git holds the desired state; an in-cluster agent (Argo CD or Flux) pulls and applies it, and continuously reports drift. Benefits: the cluster credentials never leave the cluster (CI does not need kube-admin), every change is a reviewed commit with history and easy revert, and drift is detected and corrected. Cost: another system to run, and secrets need special handling (sealed secrets, external secrets).

How to answer

Compare with push-based CI (kubectl apply from Jenkins) on security and auditability.

Likely follow-ups
  • How do you promote between environments in GitOps?
Explain blue-green vs canary on Kubernetes and how you would automate rollback.

Blue-green: run the full new version beside the old and switch the Service selector or route at once; instant rollback, double cost during the switch. Canary: send a small weight (1-5%) to the new version through Gateway API weights or a mesh, watch SLO metrics (error rate, p99), then step up. Automate with Argo Rollouts or Flagger: each step runs an analysis query against Prometheus and aborts and reverts on breach.

How to answer

Contrast cost vs blast radius, then the automated analysis loop.

Likely follow-ups
  • What metric would you gate a payment service canary on?
