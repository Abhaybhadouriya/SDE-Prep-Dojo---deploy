60-second answers to the most asked questions

These are the questions that come up again and again. Each answer is written to be spoken in about a minute. Read it aloud once, then close the page and say it in your own words. Each one links to the full question below and the page that teaches it.

"Is a container a VM?"

"No. A VM runs its own kernel on a hypervisor. A container is an ordinary Linux process on the host kernel. The kernel gives it namespaces, so it has its own view of process IDs, network, mounts and hostname, and cgroups, which cap its CPU, memory and process count. Because nothing is emulated, a container starts in milliseconds and the image can be a few megabytes. The trade-off is isolation: every container shares one kernel, so for untrusted code I would add a sandbox such as gVisor or use microVMs like Firecracker." Learn it

"What happens when you run kubectl apply on a Deployment?"

"kubectl sends the object to the API server, which authenticates me, checks RBAC, runs admission and stores it in etcd. The Deployment controller notices through a watch and creates a ReplicaSet; the ReplicaSet controller creates pods with no node. The scheduler filters and scores nodes and binds each pod. The kubelet on that node asks containerd to create the pod sandbox, the CNI plugin gives it an IP, the image is pulled and the containers start. When the readiness probe passes, the EndpointSlice controller adds the pod IP and kube-proxy on every node updates its rules, so the Service starts sending traffic." Learn it

"Why is Kafka fast if it writes to disk?"

"Five reasons. It only appends, so disk access is sequential. It relies on the operating system's page cache instead of its own heap cache, so recent data is served from memory. It uses zero-copy sendfile, so bytes go from the page cache to the socket without passing through user space. It batches and compresses records per batch end to end. And it uses the same binary format on disk and on the wire, so the broker does not re-encode. One caveat: with TLS, zero-copy no longer applies because encryption happens in user space." Learn it

"How do you make Kafka not lose data?"

"Replication factor 3, min.insync.replicas 2, and producers with acks=all, which is the default now along with idempotence. A write is acknowledged only when at least two brokers have it, so losing one broker loses nothing and the topic keeps accepting writes. If two brokers are down, writes fail instead of silently keeping one copy. I keep unclean leader election off, spread replicas across zones with rack awareness, and on the consumer side I commit offsets only after processing." Learn it

"What happens when a Kubernetes node dies?"

"The kubelet stops renewing its lease. After the node monitor grace period, about 50 seconds in current versions, the node controller marks it not ready and taints it. Pods tolerate that taint for 300 seconds by default, so roughly five minutes later they are evicted and the ReplicaSet controller creates replacements on healthy nodes. Endpoints for those pods are removed earlier, once the node is not ready. StatefulSet pods are deliberately not replaced until the node is confirmed gone, to avoid two pods with the same identity writing the same disk." Learn it

"How do consumer groups work?"

"Within one group, each partition is read by exactly one consumer, so the maximum parallelism is the number of partitions; extra consumers sit idle as standbys. Each group keeps its own committed offsets in an internal topic, so different groups read the same data independently - that is pub/sub. When members join or leave, a rebalance reassigns partitions. Modern clients use cooperative assignment or the new broker-side protocol so only the moved partitions pause." Learn it

"Explain the CAP theorem."

"In a distributed system, network partitions will happen, so the real choice is what to do during one: stay consistent by refusing some requests, or stay available by answering with possibly stale data. For a bank balance or seat booking I choose consistency. For a like counter or a feed I choose availability. PACELC adds that even without a partition there is a latency versus consistency trade-off, because synchronous replication costs time on every write." Learn it

"What is an idempotency key?"

"A unique ID the client creates for one logical operation, like 'pay order 123', and sends with every retry. The server stores it under a unique constraint along with the result. If the same key comes back, the server returns the stored result instead of doing the work again. It matters because a timeout does not tell you whether the server acted, so without it a retry can charge a customer twice." Learn it

"What is the outbox pattern?"

"It fixes the dual-write problem. If a service writes to its database and then publishes to Kafka, a crash in between leaves the two out of step. With the outbox, the service writes the business row and an event row into an outbox table in the same database transaction. A separate relay, often Debezium reading the database log, publishes those rows to Kafka. Now the database is the single source of truth, events are delivered at least once, and consumers deduplicate by event ID." Learn it

"How would you design a rate limiter?"

"I would put it at the API gateway, keyed by user or API key, using a token bucket because it allows short bursts but caps the average rate. The bucket state lives in Redis and the check-and-take step is one Lua script so concurrent requests cannot race. At very high traffic each gateway keeps a local bucket and syncs, accepting a little inaccuracy. Over the limit I return 429 with Retry-After. If Redis is down I fail open with local limits so the limiter does not become the outage." Learn it

"SQL or NoSQL?"

"It depends on the access pattern and consistency needs. For orders and payments I pick a relational database because I need transactions and constraints across rows; the cost is harder write scaling, and if one primary is not enough I shard by customer. For chat messages or location pings I pick a wide-column or key-value store because the access is always by one key at very high write volume; the cost is no joins and limited transactions." Learn it
