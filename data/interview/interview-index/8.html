The trade-off sentence (use it everywhere)

Strong candidates sound the same on every design question because they reuse one sentence pattern:

"I would pick X because of A. The cost is B. If C becomes a problem, I would switch to Y."

DecisionWorked sentence
SQL vs NoSQLI would pick Postgres because orders need transactions and joins. The cost is harder horizontal scaling. If write volume outgrows one primary, I would shard by customer ID or move hot tables to a wide-column store.
Kafka vs SQSI would pick Kafka because several teams need to replay the same order events. The cost is running a cluster. If we only needed one simple work queue, SQS would be cheaper to operate.
Push vs pull feedI would push posts into followers' feeds because reads dominate. The cost is huge fan-out for celebrities. For accounts above a follower threshold I would switch to pull at read time.
Cache-aside vs write-throughI would use cache-aside because it is simple and the cache can fail safely. The cost is a short window of stale data. If staleness hurts, I would invalidate on write or use CDC events to update the cache.
Sync vs asyncI would make payment confirmation synchronous and notifications asynchronous through Kafka. The cost is eventual delivery of emails. If users need instant receipts, I would send one synchronous message and queue the rest.
Strong vs eventual consistencyI would use strong consistency for inventory decrement because overselling costs money. The cost is latency and lower availability under partition. For the product page stock badge, eventual is fine.
Monolith vs microservicesI would start with a modular monolith because the team is small. The cost is shared deploys. When teams step on each other, I would split along the module boundaries.
Polling vs WebSocketsI would use WebSockets for chat because messages must arrive within a second. The cost is stateful connections to manage. For a dashboard refreshed every minute, polling is simpler.
Single vs multi-regionI would start in one region across three availability zones because it is simpler and meets the SLO. The cost is a regional outage risk. If the business needs regional failover, I would add an active-passive second region.
Partition countI would start with enough partitions for the target consumer parallelism plus headroom, say 12. The cost of too many is metadata and recovery time. Adding partitions later changes key-to-partition mapping, so I would size for growth up front.
