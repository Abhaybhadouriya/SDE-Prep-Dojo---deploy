What each round is really testing

The table below is the rubric view. Read the last column twice: it is the most common way strong engineers fail.

RoundWhat they write downHow it feelsClassic failure
DSA / codingProblem solving, correctness, complexity, code quality, testing your own codeLeetCode medium, sometimes hard, 45 minCoding in silence, then running out of time with no working solution
LLD / OODClean classes, interfaces, extensibility, design patterns, SOLID"Design a parking lot / rate limiter / elevator"Writing one giant class; no way to add a new vehicle type
Machine coding (Flipkart, Swiggy, Uber)Working, runnable, extensible code in 60-90 min"Build Splitwise in memory, then demo it"Beautiful design, nothing runs at the end
HLD / system designRequirements, estimates, API, data model, scaling, failure handling, trade-offs"Design a URL shortener / flash sale / chat app"Jumping into internals before the user, the API and the numbers
Behavioural (Amazon LPs, Googleyness, Microsoft values)Ownership, impact, conflict handling, learning, evidence with numbers"Tell me about a time..."Saying "we" all the time, no numbers, no clear result
Project deep-dive / hiring managerDepth on your own work, judgement, motivation, team fit"Walk me through the hardest system you built"Too much jargon from your old domain, no link to the new role

Here is where the four topics of this site actually show up. Bigger circles, and the 1-3 number next to each, mean "asked more often in this round" (a rule of thumb from the public interview reports collected in our research notes, not an official statistic).

Interviewers love a candidate who says early: "Let me first check the requirements and the scale, then I will propose an API and a data model, then a diagram, then we can go deep where you want." It shows you know the rubric.
