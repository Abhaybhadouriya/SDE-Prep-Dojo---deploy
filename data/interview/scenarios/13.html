Quiz

A container exits with code 137. What does that number tell you first?

  1. The app threw an exception
  2. The container got SIGTERM
  3. The process was killed by SIGKILL (128 + 9), often by the OOM killer
  4. The image is for the wrong CPU architecture
Exit codes above 128 mean "killed by signal (code - 128)". 9 is SIGKILL. Confirm OOM with the OOMKilled flag or dmesg.

Your topic has 8 partitions and the consumer group already has 8 consumers. Lag is even across partitions. What will adding 4 more consumers do?

  1. Increase throughput by 50%
  2. Nothing useful: the extra 4 consumers sit idle
  3. Break ordering for every key
  4. Cause Kafka to add partitions automatically
In a classic consumer group each partition goes to exactly one consumer. Make each consumer faster, or plan more partitions.

A pod is Pending. Where do you look first?

  1. kubectl describe pod Events, for the scheduler's reason
  2. kubectl logs of the pod
  3. The application's database
  4. The container's exit code
A Pending pod has not started, so there are no logs. The scheduler writes the reason (insufficient CPU, taints, PVC) into events.

Which statement about Kafka exactly-once is correct?

  1. It guarantees a payment gateway is called only once
  2. It is on by default for all consumers
  3. It removes the need for idempotent consumers everywhere
  4. It covers read-from-Kafka, process, write-to-Kafka; external side effects still need idempotency
Transactions and read_committed cover Kafka-to-Kafka flows. Emails, payments and DB writes outside Kafka need idempotency keys or the outbox pattern.

Every docker stop takes exactly 10 seconds. The most likely cause is:

  1. The disk is slow
  2. The app ignores SIGTERM (often because a shell is PID 1), so Docker waits for the grace period and then sends SIGKILL
  3. The network is slow
  4. The image is too large
10 seconds is Docker's default stop timeout. Use the exec form of CMD or --init, and handle SIGTERM.

The app saves an order to the database and then publishes an event; sometimes the event is missing. The best fix is:

  1. Publish the event before saving
  2. Retry the publish forever in the same request
  3. The transactional outbox: write the event to an outbox table in the same DB transaction, then relay it to Kafka
  4. Use a bigger Kafka cluster
The outbox makes the business write and the event one atomic DB transaction. A relay (CDC or poller) publishes it; consumers dedup by event ID.

Latency is high, CPU average is 40%, and the container has a CPU limit. What should you check?

  1. CFS throttling (throttled periods), because bursts can hit the quota even when the average is low
  2. The disk usage
  3. The image size
  4. The number of Kafka partitions
A CPU limit is a quota per 100 ms period. Multi-threaded bursts use it up early and then wait. Look at the throttled-periods ratio.

In the six-step incident loop, what comes immediately after scoping the blast radius?

  1. Writing the postmortem
  2. Finding the root cause
  3. Adding an alert
  4. Mitigating the user impact
Detect, scope, mitigate, diagnose, fix, prevent. Users first, curiosity second.
