System design drills (H1 - H7)

These come up inside HLD rounds as "what happens when..." follow-ups, and in hiring-manager rounds as "tell me how you would handle...". They join the pieces together: caches, databases, queues and the cluster. Background: Resilience patterns, Distributed transactions, Multi-region and DR, Scaling reads.

Many of these incidents are feedback loops: a small failure causes retries, retries cause more load, more load causes more failure. The picture shows a retry storm, and where the circuit breaker cuts the loop.

Scenario H1: the database hits 100% CPU two minutes into a flash sale

At 12:00 a sale starts. Product page latency goes from 100 ms to 6 seconds. The primary database is at 100% CPU, mostly running the same "get product and stock" query.

HLD caching, hot keys level: SDE-2 commonly reported at: Amazon, Walmart, Flipkart

Weak answer: "Buy a bigger database." Vertical scaling takes time, has a ceiling, and does not stop the same few rows from being hammered.

Strong answer:

  1. Mitigate in minutes. Turn on a waiting room or rate limit at the edge for the sale page, serve product details from cache or CDN, and shed non-critical traffic (recommendations, reviews) with feature flags.
  2. Separate reads from writes. Product details rarely change: cache them aggressively (CDN plus Redis) and send leftover reads to read replicas. Only stock changes on the hot path.
  3. Handle the hot rows. Keep stock counters for sale items in Redis and decrement atomically (a Lua script or DECR), then write orders to the DB asynchronously through a queue. Or split one item's stock into several sub-counters.
  4. Check the query. Slow query log and EXPLAIN: a missing index can turn a 1 ms query into a full scan.
  5. Prevent. Load-test with the expected sale traffic beforehand, pre-warm caches, and pre-scale. Flipkart has described running large-scale chaos experiments before its Big Billion Days sale.
Likely follow-ups
  • How do you avoid overselling if stock lives in Redis? (Atomic decrement that refuses below zero, reservation with a timeout, and the DB as the final source of truth with reconciliation.)
  • Full design: Flash sale.

Scenario H2: Redis restarted and the database fell over a minute later

A cache node restarted with an empty memory. Within 60 seconds the database behind it was overloaded and the whole site slowed down, even though Redis was back.

HLD cache stampede level: SDE-2 commonly reported at: Amazon, Microsoft

Weak answer: "Redis should not restart." Everything restarts eventually; design for it.

Strong answer: this is a cache stampede (also called thundering herd or dog-piling). With an empty cache, every request misses, and thousands of requests for the same popular key all hit the DB at once.

  1. Mitigate. Rate limit traffic to the DB (a connection pool cap protects it), serve stale or default data for non-critical parts.
  2. Request coalescing. Only one request per key rebuilds the value; others wait for it (a short lock or "single flight").
  3. Jitter the TTLs. If all keys expire at the same time, you create your own stampede every hour. Add random spread to TTLs.
  4. Serve stale while revalidating. Keep a slightly old value and refresh it in the background.
  5. Prevent. Replicas and persistence for the cache so a restart is not a cold start, and warm hot keys before sending traffic.
Likely follow-ups
  • Cache-aside vs write-through vs write-behind: which did this system use, and what would change?
  • How do you handle one key that is too hot for one Redis node? (Replicate it to several keys or a local in-process cache.)

Scenario H3: a slow dependency takes down every service (retry storm)

The recommendations service became slow (3 s instead of 50 ms). Soon the product page, the cart and checkout all failed, even though they do not need recommendations to work.

HLD resilience level: SDE-2 commonly reported at: Amazon, Microsoft, Uber

Weak answer: "Increase the timeout to 10 seconds so calls succeed." Longer timeouts hold threads longer and spread the failure faster.

Strong answer: a non-critical dependency used up shared resources (threads, connections) of critical paths. That is a cascading failure.

  1. Mitigate. Turn off the recommendations widget with a feature flag; the page loads without it.
  2. Timeouts. Every remote call gets a timeout based on that dependency's normal latency (for example a little above its p99), and shorter than the caller's own timeout.
  3. Retries done right. Few retries, exponential backoff with jitter, only for safe (idempotent) operations, and a retry budget so retries can never multiply traffic.
  4. Circuit breaker. After many failures, stop calling for a while and return a fallback immediately.
  5. Bulkheads. Separate thread pools or connection pools per dependency, so one slow dependency cannot eat everyone's threads.
  6. Prevent. Chaos tests that inject latency (not just failure) into dependencies.
Likely follow-ups
  • How would a queue (Kafka) between services change this failure? (The caller no longer waits; lag grows instead of threads blocking.)
  • What is load shedding and how do you choose what to drop?

Scenario H4: users get the same push notification three times

A notification service reads from Kafka and calls a push provider. After a provider slowdown, many users received the same "Your order has shipped" message three times.

HLD dedup, at-least-once level: SDE-2 commonly reported at: Amazon, Flipkart, Swiggy

Weak answer: "Use exactly-once in Kafka." Same mistake as F7: the push provider is outside Kafka.

Strong answer:

  1. Find the duplication point. The provider was slow, the HTTP call timed out on our side, but the provider had actually sent it. Our retry sent it again. Possibly a rebalance re-delivered too.
  2. Dedup by notification ID. Each notification gets a stable ID when it is created. Before sending, do an atomic "set if not exists" with a TTL in Redis (or a unique row in the DB). If the key is already there, skip.
  3. Use the provider's idempotency features where they exist (collapse keys or IDs).
  4. Tune retries. Retry timeouts with backoff, and do not retry when the provider says the message was accepted.
  5. Prevent. Track a "duplicate sends" metric and alert on it.
# Redis: claim the notification ID for 24 hours; only the first worker succeeds
SET notif:9f3c2a sent NX EX 86400
Likely follow-ups
  • How would you add per-user rate limits ("no more than 3 marketing pushes a day")?
  • Full design: Notification system.

Scenario H5: the order exists in the database but no event was ever published

Some orders are saved, but the warehouse never hears about them. The code saves the order to the DB, then publishes OrderCreated to Kafka. Rarely, the pod dies between the two steps.

HLD dual write, outbox level: SDE-2 commonly reported at: Amazon, Walmart, Uber

Weak answer: "Publish to Kafka first, then save." Now you can publish an event for an order that was never saved.

Strong answer: this is the dual-write problem: two systems, no shared transaction, so one write can succeed while the other fails.

  1. Mitigate. Find orders with no matching event (a reconciliation query) and republish them.
  2. Use the transactional outbox. In the same DB transaction that saves the order, insert a row into an outbox table. Either both commit or neither does.
  3. Relay the outbox. A CDC connector (Debezium) or a small poller reads new outbox rows and publishes them to Kafka. It may publish twice after a crash, so consumers dedup by event ID.
  4. Prevent. A periodic reconciliation job and a metric for "orders without events older than N minutes".
BEGIN;
INSERT INTO orders (id, user_id, total, status) VALUES (:id, :user, :total, 'CREATED');
INSERT INTO outbox (event_id, aggregate_id, type, payload)
VALUES (:eventId, :id, 'OrderCreated', :json);
COMMIT;
Likely follow-ups
  • Outbox vs Kafka transactions vs a saga: when do you use which?
  • How does the warehouse cancel if payment later fails? (A saga with compensating events.)

Scenario H6: a whole cloud region goes down

Your main region has a major outage. The company says the service must be back within 15 minutes and lose at most 1 minute of data.

HLD DR, multi-region level: SDE-2 commonly reported at: Amazon, Walmart, Microsoft

Weak answer: "We have backups, we will restore them." Restoring a large database from backup rarely fits in 15 minutes, and backups may be hours old.

Strong answer: translate the business words into numbers first: RTO 15 minutes (time to recover), RPO 1 minute (data you may lose).

  1. Design to the target. An RPO of 1 minute needs continuous asynchronous replication to a second region (database replicas, Kafka MirrorMaker 2, object storage replication). An RTO of 15 minutes needs a warm standby: the second region runs a scaled-down copy of the services, already deployed.
  2. Failover steps. Promote the standby database, scale up the services, switch traffic with DNS or a global load balancer, point consumers at the mirrored Kafka with translated offsets.
  3. Explain the trade-off. Active-passive is simpler and cheaper but you lose the replication lag. Active-active gives near-zero RTO but forces you to handle write conflicts (region-pinned users, CRDTs, or one region owning each record).
  4. Prevent surprise. Practise failover on a schedule (game days). An untested DR plan is a hope, not a plan.
Likely follow-ups
  • Why are synchronous cross-region writes usually avoided? (Every write pays the round-trip latency between regions.)
  • Full topic: Reliability, multi-region and DR.

Scenario H7: p99 latency doubled after a "harmless" deploy

A deploy changed only logging and a library version. Error rate is flat, but p99 latency of the search API went from 200 ms to 450 ms.

HLD performance regression level: SDE-2 commonly reported at: Microsoft, Uber, Google

Weak answer: "It is probably the network." No evidence, no test.

Strong answer:

  1. Mitigate. The timing matches the deploy, so roll back first and confirm latency recovers. That alone proves the deploy is the cause.
  2. Compare old and new. Run a canary of the new version beside the old one and compare traces: which span got slower?
  3. Usual suspects for "harmless" changes: synchronous logging on the request path (disk or network flush per line), a new library that changed connection pool sizes or timeouts, a different JSON or TLS implementation, more memory allocation causing longer GC pauses.
  4. Profile. A CPU or allocation profile (a flame graph) of the new version under the same load shows where time goes.
  5. Prevent. Automated canary analysis that compares p99 latency (not only errors) between canary and baseline before a full rollout.
Likely follow-ups
  • Why look at p99 and not the average? (Averages hide the slow tail that users feel, and one page load may call many services, so tails add up.)
  • What is tail-latency amplification in fan-out requests?
