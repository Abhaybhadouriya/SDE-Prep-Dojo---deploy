60-second answers for the most asked scenarios

Sometimes an interviewer asks a scenario as a quick check, in a screen or at the end of a round. Here are compact answers you can say in about a minute. Each one still has the shape: mechanism, first command, fix, prevention.

Question60-second answer
"Pod is in CrashLoopBackOff."The container keeps exiting and the kubelet restarts it with growing back-off. I run kubectl logs --previous and describe pod for the exit code and events: 1 is an app or config error, 137 with OOMKilled is the memory limit, liveness failures show in events. I roll back if users are affected, fix the config or limit, and alert on restarts.
"Pod is Pending."The scheduler found no node. Events say why: not enough CPU or memory requests, taints, affinity, or an unbound PVC. I fix the cause, check the cluster autoscaler can add nodes, and right-size requests.
"Exit code 137."128 + 9 = SIGKILL, usually the kernel OOM killer because the cgroup hit memory.max. I confirm with OOMKilled in inspect or describe and in dmesg, then check whether it is a leak or a too-small limit, and make the runtime container-aware.
"Consumer lag is growing."I check lag per partition. Even lag: consumers are too slow, so scale up to the partition count and speed up processing, and check the downstream DB. One hot partition: a key-skew problem, so fix the key or add parallelism inside that consumer. Alert on lag growth rate.
"How do you avoid losing messages in Kafka?"Replication factor 3, min.insync.replicas=2, acks=all, idempotent producer, unclean leader election off, replicas in different zones. Consumers commit after processing and are idempotent. Monitor under-replicated partitions.
"How do you handle failed messages?"Retry transient errors with backoff, then send to a retry topic with delay, then a dead-letter topic with the error in headers. Alert on DLQ depth and give operators a replay tool. Use a schema registry to stop bad data at the producer.
"Messages are processed twice."Normal under at-least-once after a crash or rebalance. Make the handler idempotent: a unique business key with an upsert or "insert, do nothing on conflict", and idempotency keys for external calls. Kafka exactly-once only covers Kafka-to-Kafka.
"502s during deploys."New pods get traffic before they are ready, or old pods exit before the load balancer stops sending. I add a real readiness probe, a short preStop sleep plus graceful drain, and maxUnavailable: 0.
"The database is the bottleneck."First find out if it is reads or writes. Reads: cache (cache-aside with jittered TTLs), read replicas, CDN. Writes: batch, queue, shard by a well-spread key. Always check indexes and the slow query log first; often it is one bad query.
"A dependency is slow and everything breaks."Cascading failure. Timeouts on every call, retries with backoff and jitter plus a retry budget, circuit breakers with fallbacks, bulkheads per dependency, and feature flags to switch off non-critical features.
