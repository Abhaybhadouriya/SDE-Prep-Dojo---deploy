Walk the request path, hop by hop

When a request fails, you can check each hop it passes through, in order, like a traceroute for your whole stack. Click through the stepper: the ring shows the hop, and the caption under the diagram says what usually breaks there and the first command to run.

  1. Client. Start at the user. Is it everyone, or one app version, one country, one ISP? Reproduce it first: a failure you can reproduce is half solved. First command: curl -sv https://shop.example.com/health
  2. DNS and CDN. A wrong record, an expired certificate, or a CDN serving a stale error page. A changed DNS record or an expired TLS certificate breaks every user at once. First command: dig +short shop.example.com ; openssl s_client -connect shop.example.com:443
  3. Cloud load balancer. Unhealthy targets, 502/504 counts, connection limits. 502 means the backend closed or refused the connection; 504 means the backend was too slow. First command: check target health and 5xx metrics for the load balancer in the cloud console
  4. Ingress or Gateway (layer 7 routing). A wrong host or path rule, a missing TLS secret, upstream errors. The controller log shows which upstream pod answered and how long it took. The controller depends on your cluster: for example Envoy Gateway or another Gateway API implementation, or ingress-nginx on older clusters (the community ingress-nginx project was retired in 2026). First command: kubectl logs -n <gateway-namespace> deploy/<gateway-controller> | tail
  5. Service and its EndpointSlices (layer 4 virtual IP). The selector does not match the pods, so there are no endpoints and traffic has nowhere to go. Check labels and readiness. First command: kubectl get endpointslices -l kubernetes.io/service-name=orders
  6. Pod and its containers. Crashing, not Ready, OOMKilled, CPU throttled, bad config. The events at the bottom of describe are the platform's diary: read them first. First command: kubectl describe pod orders-7d9 ; kubectl logs orders-7d9 --previous
  7. Dependencies: databases, caches and Kafka. DB connections exhausted, slow queries, Kafka lag, timeouts. Most "my service is slow" incidents are really "my dependency is slow". First command: kafka-consumer-groups.sh --describe --group orders ; check the DB slow-query log

From your world

This is the same discipline as debugging a packet path through a router: ingress port, classifier, forwarding lookup, egress queue, wire. In Kubernetes, the Service hop is literally NAT done by kube-proxy with iptables or nftables rules (IPVS mode is deprecated; Cilium uses eBPF instead), so conntrack -L and iptables-save | grep KUBE-SVC on a node are fair game when the interviewer pushes you deeper. SignalQuestion it answersTool examples
MetricsHow much, how fast, since when? (rates, errors, latency, saturation)Prometheus + Grafana, CloudWatch, Azure Monitor

ChangesWhat changed just before it started?Deploy history, kubectl rollout history, Git log, change calendar

The four "golden signals" from Google's SRE book are latency, traffic, errors and saturation. If you mention them by name while scoping, interviewers hear "this person has run services". For queues, add a fifth: backlog (consumer lag).
