Interview Q&A about scenario rounds

These questions are about the round itself and about the general skills behind every drill. Use the filters to pick by level, topic or company.

What is the very first thing you say when the interviewer finishes describing an incident?

Ask one or two questions that change the answer: "Is this affecting all users or a subset? When did it start, and did anything change around then (a deploy, a config change, a traffic spike)?" Then say your plan out loud: "I will first make sure users stop hurting, then find the root cause."

How to answer

Short questions, then a one-line plan. Do not spend five minutes on questions; the interviewer wants to see you move.

Likely follow-ups
  • "Assume nothing changed." (Then look at traffic, dependencies, time-based things like certificates, cron jobs, cache expiry, OS updates.)
What is the difference between mitigation and a fix?

Mitigation stops the user impact quickly, even if the cause is unknown: rollback, failover, scale out, disable a feature. A fix removes the root cause so it does not come back: a code change, a config change, a new limit. You usually do both, in that order.

How to answer

Give one example of each from the same incident. "Rollback was the mitigation; the fix was making the config key optional with a default and adding a startup check."

Likely follow-ups
  • When is rollback not possible? (A database migration already ran: so design migrations to be backwards compatible, expand then contract.)
Which kubectl commands do you use most when debugging?

kubectl get pods -o wide (status, node, restarts), kubectl describe pod (events, last state, exit code), kubectl logs POD --previous, kubectl get events --sort-by=.lastTimestamp, kubectl top pod/node, kubectl get endpointslices for Services, kubectl exec and kubectl debug to look inside, kubectl rollout status/undo for deploys.

How to answer

Group them by question: "what state is it in, why did it change, what is inside it, how do I undo".

Likely follow-ups
  • How do you debug a distroless container? (kubectl debug with an ephemeral container.)
Tell me about a time you debugged a difficult production issue. (Amazon "Dive Deep")

Use STAR, and use your real systems work. For example: Situation: a customer's optical network had intermittent packet loss on one line card under high load. Task: I owned finding the cause before the next maintenance window. Action: I reproduced it in the lab with traffic at the customer's peak rate, used counters to rule out the optics, found that a ring buffer was overflowing because an interrupt handler held a lock too long, and changed it to defer work. Result: loss went to zero in the lab and in the field, and I added a counter alarm so the support team could see it early.

How to answer

Show the same incident loop: symptom, scope, mitigation, evidence, root cause, prevention. Put numbers in the result. Then translate: "This is the same skill as debugging consumer lag: a queue is filling because the consumer is slower than the producer." The Interview Hub has more story templates.

Likely follow-ups
  • What would you do differently? (Have a good answer: earlier alerting, better test coverage.)
  • How did you know it was fixed?
What should a blameless postmortem contain?

A summary, the impact (users, duration, money if known), a timeline with timestamps, the root cause and contributing factors, what went well, what went badly, where we got lucky, and action items with owners and dates. "Blameless" means it focuses on how the system and process allowed the mistake, not on who made it, so people report problems honestly.

How to answer

Mention the Google SRE book chapter on postmortem culture, and stress that action items must be tracked to completion.

Likely follow-ups
  • How do you decide which incidents need a postmortem? (Severity thresholds: user impact, data loss, on-call intervention, long time to detect.)
An app works on your laptop but not in the container. Name five causes.

(1) localhost inside a container is the container itself (D4). (2) CPU architecture mismatch, arm64 vs amd64 (D5). (3) A missing environment variable or config file. (4) File permissions when the container runs as a non-root user. (5) Alpine's musl libc not working with a native library built for glibc. Others: time zone, DNS, missing CA certificates, the app binding to 127.0.0.1.

How to answer

List fast, then pick one and explain how you would prove it with a command.

Likely follow-ups
  • How do you get a shell in a running container? (docker exec -it c sh, or a debug container sharing its namespaces.)
How do you monitor a Kafka pipeline so you hear about problems before customers do?

Broker health: under-replicated partitions, offline partitions, active controller count (exactly one), request handler idle percentage, produce and fetch p99 latency, disk usage. Client health: consumer lag per partition and its growth rate, rebalance rate, producer error and retry rates. Business health: end-to-end latency (event time to processing time), DLQ depth, and a count reconciliation between source and sink.

How to answer

Three layers: broker, client, business. Interviewers like the business layer because it catches silent data loss that infrastructure metrics miss.

Likely follow-ups
  • Which of these would page someone at 3 a.m.? (Offline partitions, lag growth on critical groups, DLQ spikes.)
What happens, step by step, when a Kubernetes node dies?

The kubelet stops renewing its node Lease. After the node monitor grace period (about 50 seconds in recent versions) the node controller marks it NotReady/Unknown and adds taints. Pods have a default toleration of 300 seconds for those taints; after that they are evicted. Their controllers (ReplicaSet, StatefulSet) create replacements, which the scheduler puts on other nodes. Services stop sending traffic to the dead pods once they are not Ready. StatefulSet pods wait for the old pod to be confirmed gone (K11).

How to answer

Walk the control loop in order: heartbeat, mark, taint, evict, recreate, reschedule, re-route. Mention that you can lower the tolerations for faster failover, at the risk of churn during short network blips.

Likely follow-ups
  • Why not fail over in 5 seconds? (False positives from short network issues cause expensive churn.)
Your consumer must call a slow external API for every message. How do you keep up without breaking ordering?

Inside each consumer, keep partition order but process different keys in parallel: hand records to a pool of workers sharded by key, so the same key always goes to the same worker, and commit an offset only when all records before it are done. Add batching to the API if it supports it, and a bounded queue so memory does not explode. If ordering is not needed, Kafka 4.x share groups or a consumer proxy let you scale beyond the partition count. This is similar to the per-key in-flight rule Walmart described for its messaging proxy.

How to answer

Separate "ordering per key" from "ordering per partition"; most businesses need only the first.

Likely follow-ups
  • How do you commit offsets safely with parallel workers? (Track the lowest unfinished offset per partition and commit below it.)
How do you pick timeouts and retries for a service-to-service call?

Set the timeout a bit above the dependency's normal p99 latency, and always below the caller's own deadline (propagate a deadline down the call chain). Retry only idempotent operations, at most a couple of times, with exponential backoff plus jitter, and cap retries with a budget (for example retries may add at most 10% extra traffic). Combine with a circuit breaker so a dead dependency fails fast.

How to answer

Explain why each rule exists: retries multiply load at every layer, so three layers each retrying three times can turn one request into many more.

Likely follow-ups
  • Why add jitter? (Without it, all clients retry at the same moment and create synchronized waves.)
Active-active or active-passive across regions: how do you choose?

Active-passive: one region takes writes, the other is a replicated standby. Simple, cheaper, no write conflicts, but failover takes minutes and you lose data equal to the replication lag (RPO). Active-active: both regions take writes. Near-zero RTO and lower latency for users close to each region, but you must solve conflicts (pin each user or record to a home region, or use conflict-free data types) and pay for full capacity twice. Choose from the RTO and RPO the business needs and how conflict-prone the data is.

How to answer

Start with RTO/RPO numbers, then pick. Mention that Kafka MirrorMaker 2 is usually used active-passive, and active-active needs topic prefixes to avoid replication loops.

Likely follow-ups
  • Which data can be active-active safely? (Append-only data, user sessions pinned to a region, counters with CRDTs.)
"You are on call and three alerts fire at once: high latency, consumer lag and DB CPU. Where do you start?"

Look for the common cause rather than three problems. Ask what changed and in which order the alerts fired. DB CPU high could make the API slow (latency) and make consumers that write to the DB slow (lag): one root cause, two symptoms. Check the DB first: top queries, recent deploys or migrations, connection count. Mitigate by shedding load (pause non-critical consumers so the API gets the DB, or the other way round, depending on what users need most).

How to answer

Say "correlate before you investigate". Draw the dependency graph in ten seconds; the shared node is your first suspect.

Likely follow-ups
  • How do you avoid alert storms? (Alert on user-facing symptoms and SLOs, group related alerts, page only on what needs a human now.)
How would you make cluster upgrades safe after a bad experience like Reddit's?

Everything in Git (including CNI and network config), so a reviewer can see what depends on what. Read release notes for removals and deprecations, scan manifests for removed APIs, upgrade a canary or staging cluster that mirrors production first, back up etcd and practise the restore, upgrade the control plane then node pools gradually with PDBs, and keep the option to move traffic to another cluster during the upgrade.

How to answer

Tie each step to the failure it prevents. Mention that Kubernetes has no supported downgrade, so the real rollback plan is a restore or a traffic shift.

Likely follow-ups
  • Blue/green clusters vs in-place upgrades: costs and benefits?
What if you genuinely do not know the answer to a scenario?

Say so honestly and reason from first principles: "I have not run Kafka in production, but from how consumer groups work, if one partition has all the lag I would suspect key skew, and I would confirm it with the per-partition lag." Interviewers score reasoning and honesty; bluffing about a tool is easy to spot and costs trust.

How to answer

Use the bridge from your own world: "In networking we had the same pattern with ECMP hashing." It turns a gap into a strength.

Likely follow-ups
  • The interviewer will often give a hint; take it and say how it changes your plan.
