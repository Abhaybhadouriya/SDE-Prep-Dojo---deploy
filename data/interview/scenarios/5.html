Kubernetes drills (K1 - K11)

Kubernetes adds a control loop on top of containers, so failures can come from your app, the pod spec, the scheduler, the network plugin or the control plane. Background: Pods, Deployments, Services, Scheduling and autoscaling, Observability and troubleshooting.

Most pod problems can be sorted with one decision tree. Memorise it; you can draw it on the whiteboard in a minute.

Scenario K1: CrashLoopBackOff right after a deploy

A new version of payments-api was rolled out. New pods go Running, then Error, then CrashLoopBackOff. Old pods are still serving, so the rollout is stuck halfway.

Kubernetes most asked K8s scenario level: SDE-1 and SDE-2 commonly reported at: any company

Weak answer: "Delete the pods so they restart." Kubernetes is already restarting them; that is what the loop is. Deleting them also throws away the previous container's logs.

Strong answer:

  1. Mitigate. The Deployment's rolling update has kept old pods alive (good). If users see errors, run kubectl rollout undo deployment/payments-api.
  2. Read the crashed container, not the new one. kubectl logs POD --previous shows the output of the run that died.
  3. Read the exit code and events. kubectl describe pod shows "Last State: Terminated, Reason, Exit Code". Exit 1 = app error (bad config, missing env var, failed migration). 137 with reason OOMKilled = memory limit. Liveness probe failures appear in Events as "Liveness probe failed ... will be restarted".
  4. Diff the change. Compare the new pod spec with the old ReplicaSet: new env var, new Secret key, new command, lower limits, new probe?
  5. Prevent. Run the new image in staging with the same config, use maxUnavailable: 0 so a bad version never reduces capacity, and alert on restart count.
$ kubectl get pods -l app=payments-api
NAME                            READY   STATUS             RESTARTS      AGE
payments-api-7c9d8f6b5-2xkqp    0/1     CrashLoopBackOff   5 (40s ago)   4m
payments-api-6f4b7d9c8-hq7lm    1/1     Running            0             2d
$ kubectl logs payments-api-7c9d8f6b5-2xkqp --previous | tail -2
ERROR Config: required key DB_PASSWORD not found
Exiting with status 1
$ kubectl describe pod payments-api-7c9d8f6b5-2xkqp | grep -A3 "Last State"
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
Likely follow-ups
  • Why is the restart delay growing? (Exponential back-off: 10 s, 20 s, 40 s ... capped at five minutes.)
  • How do you debug a crashing container that has no shell? (kubectl debug -it POD --image=busybox --target=app adds an ephemeral container in the same namespaces.)
  • What if the logs are empty? (The process died before logging: wrong command, missing binary, exec format error, or a startup probe killing it.)

Scenario K2: pods stay Pending during a traffic spike

The HPA scaled the Deployment from 10 to 40 replicas, but 25 of the new pods are stuck in Pending. Latency is climbing.

Kubernetes scheduling, capacity level: SDE-1 and SDE-2 commonly reported at: Amazon, Flipkart

Weak answer: "Pending means it is starting, wait a bit." Pending means no node was chosen at all.

Strong answer:

  1. Read the scheduler's reason. The Events of a Pending pod say exactly why: "0/12 nodes are available: 12 Insufficient cpu", or "had untolerated taint", or "didn't match node affinity", or "unbound PersistentVolumeClaim".
  2. If it is capacity: is the cluster autoscaler (or Karpenter) adding nodes? Check its logs: maybe the node group hit its max size or the cloud account hit a quota.
  3. Check requests. The scheduler places pods by requests, not real usage. Requests far above real usage waste capacity. Datadog's container report found that most Kubernetes workloads use less than half of what they request.
  4. Mitigate. Raise the node group max, or shift lower-priority work away (PriorityClasses let critical pods preempt batch pods).
  5. Prevent. For known events (a sale), pre-scale nodes ahead of time; autoscalers take minutes to add nodes.
$ kubectl describe pod checkout-5d8f7-zk2lp | tail -3
Events:
  Warning  FailedScheduling  12s  default-scheduler  0/12 nodes are available: 12 Insufficient cpu.
           preemption: 0/12 nodes are available: 12 No preemption victims found for incoming pod.
Likely follow-ups
  • What are QoS classes and which pods get evicted first? (BestEffort, then Burstable, then Guaranteed.)
  • Why can an HPA based on CPU be too slow for a flash sale? (Metrics lag, plus node start time; scale on requests per second or queue depth, and pre-scale.)

Scenario K3: p99 latency doubles but CPU usage is only 40%

A latency-sensitive API has a CPU limit of 1 core. Dashboards show average CPU at 40%, but p99 latency jumped from 80 ms to 400 ms after traffic grew.

Kubernetes CFS throttling level: SDE-2 commonly reported at: any company team: kernel background helps

Weak answer: "CPU is low so it must be the database." Possible, but they never checked the most common hidden cause.

Strong answer: averages hide bursts. A CPU limit becomes a CFS quota: for every 100 ms period the container may use its quota (here 100 ms of CPU time across all threads). A multi-threaded app can burn the whole quota in the first 20 ms of the period and then sit throttled for 80 ms, even though the average looks low.

  1. Prove it. Check the throttling metric from cAdvisor, or read the cgroup's cpu.stat directly.
  2. Rule out the dependency too. A trace shows whether the time is spent inside the service or waiting on the DB.
  3. Fix. Raise the CPU limit, or remove CPU limits for latency-sensitive services and rely on requests for fair sharing (a common practice; keep memory limits). Tune thread pools to the CPU you actually have.
  4. Prevent. Alert on the throttled ratio, not just CPU usage.
# PromQL: fraction of CFS periods in which the container was throttled
sum(rate(container_cpu_cfs_throttled_periods_total{container="api"}[5m]))
  / sum(rate(container_cpu_cfs_periods_total{container="api"}[5m]))
$ kubectl exec api-6c9f -- cat /sys/fs/cgroup/cpu.stat | grep throttled
nr_throttled 18422
throttled_usec 921334012

From your world

This is the same as a token-bucket policer on an interface: the average rate is under the contract, but bursts above the bucket size get dropped (here: paused). You would never debug a policer with a five-minute average graph, and you should not debug CPU limits that way either.

Likely follow-ups
  • What is the difference between requests and limits for CPU vs memory? (CPU over limit = throttled; memory over limit = OOM killed.)
  • How would the Vertical Pod Autoscaler help?

Scenario K4: the Service returns "connection refused" even though pods are Running

After a teammate "cleaned up labels", calls to http://orders from other pods fail. All orders pods are Running and Ready.

Kubernetes Services, selectors level: SDE-1 and SDE-2 commonly reported at: any company

Weak answer: "Restart CoreDNS." DNS works fine here; the name resolves to the Service IP. The Service simply has nowhere to send traffic.

Strong answer: walk the Service path from name to pod.

  1. DNS: does orders resolve to the ClusterIP? (Yes.)
  2. Endpoints: does the Service have any? A Service only sends traffic to Ready pods whose labels match its selector. Empty EndpointSlices = selector mismatch or no Ready pods.
  3. Ports: does targetPort match the port the container really listens on?
  4. Policy: is there a NetworkPolicy that denies the caller?
  5. Fix and prevent. Restore the label (through Git, not by hand), and add a test or policy check that every Service selects at least one pod in staging.
$ kubectl get endpointslices -l kubernetes.io/service-name=orders
NAME           ADDRESSTYPE   PORTS     ENDPOINTS   AGE
orders-8xk2p   IPv4          <unset>   <unset>     41d
$ kubectl get svc orders -o jsonpath='{.spec.selector}'
{"app":"orders"}
$ kubectl get pods --show-labels | grep orders
orders-7f9c-abc12   1/1   Running   ...   app.kubernetes.io/name=orders,pod-template-hash=7f9c
Likely follow-ups
  • How does kube-proxy actually forward to a pod? (iptables or nftables rules, or the deprecated IPVS mode, that DNAT the ClusterIP to a chosen pod IP; or eBPF with Cilium.)
  • How would you test from inside the cluster? (kubectl run tmp --rm -it --image=busybox -- wget -qO- http://orders, or kubectl port-forward.)

Scenario K5: every outbound call is 5 seconds slower than it should be

Calls from pods to an external API (api.partner.com) sometimes take an extra 5 seconds. Calls by IP address are always fast.

Kubernetes DNS level: SDE-2 commonly reported at: any company team: networking background helps

Weak answer: "The partner API is slow." The clue "by IP is fast" points straight at name resolution.

Strong answer: it is DNS until proven otherwise.

  1. Read the pod's resolv.conf. Pods with the default DNS policy get ndots:5 and several search domains. A name with fewer than five dots is first tried with every search suffix (api.partner.com.default.svc.cluster.local, and so on), so one lookup becomes several queries, each for A and AAAA.
  2. Find the 5 seconds. A default resolver timeout is 5 seconds. If any one of those queries is dropped (an overloaded CoreDNS, or a conntrack race on UDP that has been reported for parallel A/AAAA queries), the client waits the full timeout before retrying.
  3. Fix. Use a fully qualified name with a trailing dot (api.partner.com.), or lower ndots in the pod's dnsConfig, scale CoreDNS, and run NodeLocal DNSCache so lookups hit a cache on each node.
  4. Prevent. Monitor CoreDNS latency and errors; DNS is a shared dependency for the whole cluster.
$ kubectl exec web-5c7d -- cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
Likely follow-ups
  • Why does Kubernetes use ndots:5 at all? (So short names like orders or orders.payments resolve inside the cluster.)
  • The public collection Kubernetes Failure Stories has several DNS post-mortems; which would you read first?

Scenario K6: every rolling deploy causes a burst of 502 errors

The app is healthy, but during each deploy the load balancer logs a few hundred 502/503 errors for about 30 seconds.

Kubernetes graceful shutdown, readiness level: SDE-1 and SDE-2 commonly reported at: Amazon, Walmart, Uber

Weak answer: "Deploy at night when traffic is low." That hides the bug and makes every deploy risky.

Strong answer: errors at the start and the end of a pod's life have different causes.

  1. New pods get traffic too early. Without a correct readiness probe, a pod is added to the Service before the app has warmed up (caches, connections, JIT). Fix: a readiness probe that checks the app can really serve.
  2. Old pods are killed while still receiving traffic. When a pod is deleted, two things happen in parallel: the kubelet sends SIGTERM, and the endpoint is removed from the Service and the load balancer. The removal takes a few seconds to spread. If the app exits immediately on SIGTERM, it refuses requests that are still on their way. Fix: a short preStop sleep (for example 5-10 s), then graceful drain of in-flight requests, all within terminationGracePeriodSeconds.
  3. Keep capacity. maxUnavailable: 0 and maxSurge: 25% so the old pods only go once new ones are Ready.
  4. Prevent. Watch the 5xx rate during deploys as a release gate; automate rollback if it rises.
spec:
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 25% }
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
          lifecycle:
            preStop:
              sleep: { seconds: 10 }   # native sleep action, stable since 1.34

The native sleep action (PodLifecycleSleepAction, stable since Kubernetes 1.34) works even in distroless or scratch images that have no shell; the older exec: { command: ["sleep", "10"] } form needs a sleep binary inside the image.

Likely follow-ups
  • Why must a liveness probe not check the database? (If the DB blips, every pod restarts at once and makes the outage worse.)
  • How would you do a canary instead of a rolling update? (Two Deployments with weighted routing, or Argo Rollouts / a service mesh.)

Scenario K7: a node drain for an upgrade hangs forever

During a node-pool upgrade, kubectl drain on one node waits for many minutes and never finishes.

Kubernetes PDB, upgrades level: SDE-2 commonly reported at: Amazon, Microsoft team: managed-Kubernetes platform teams

Weak answer: "Use --force and --disable-eviction." That deletes pods and ignores the safety rules that protect availability.

Strong answer:

  1. Read what drain is waiting for. Drain uses the Eviction API, which respects PodDisruptionBudgets. The output says "Cannot evict pod as it would violate the pod's disruption budget".
  2. Find the bad budget. A PDB with minAvailable equal to the replica count (or a 1-replica app with minAvailable: 1) can never allow an eviction. Another cause: the app's other pods are not Ready, so no disruption is allowed.
  3. Fix the right way. Scale the app up first so the budget has room, or correct the PDB, then drain again.
  4. Other blockers: pods with local storage (emptyDir) need --delete-emptydir-data; DaemonSet pods need --ignore-daemonsets; pods with finalizers may hang in Terminating.
  5. Prevent. A policy check that flags PDBs allowing zero disruptions.
$ kubectl get pdb -A
NAMESPACE  NAME        MIN AVAILABLE  MAX UNAVAILABLE  ALLOWED DISRUPTIONS  AGE
search     search-pdb  3              N/A              0                    90d
Likely follow-ups
  • What happens to pods when a node dies without a drain? (After the node is marked NotReady, pods get a default 300-second toleration, then are evicted and recreated elsewhere by their controllers.)
  • Why upgrade the control plane before the nodes? (The version skew policy allows kubelets to be older than the API server, not newer.)

Scenario K8: a cluster upgrade breaks all pod networking (the Reddit Pi-Day story)

You upgrade a production cluster by one minor version. Minutes later, pods on different nodes cannot talk to each other. The site is down. This is close to what Reddit described in its public post-mortem of 14 March 2023, a 314-minute outage after a 1.23 to 1.24 upgrade.

Kubernetes upgrades, CNI level: SDE-2 commonly reported at: any company team: infra teams

Weak answer: "Downgrade back to 1.23." Kubernetes has no supported in-place downgrade of the control plane.

Strong answer:

  1. Mitigate. Shift traffic to another healthy cluster or region if you have one. Otherwise, the recovery path is to restore the control plane from an etcd backup taken before the upgrade, which you must have tested.
  2. Diagnose what changed. In Reddit's case, Calico BGP route reflectors were selected with the node label node-role.kubernetes.io/master. Version 1.24 removed that label (it is now control-plane), so no node acted as route reflector and routes between nodes disappeared.
  3. Notice the deeper cause. That configuration was not in Git, so nobody reviewing the upgrade knew it depended on the old label.
  4. Prevent. Read release notes for removals (not just new features), keep all cluster config in Git (GitOps), upgrade a non-critical canary cluster first, scan manifests for removed APIs, and practise the etcd restore.

From your world

You know BGP route reflectors from carrier networks. Here the CNI plugin uses BGP between nodes to share pod routes. If the reflectors disappear, every node loses routes to every other node's pod subnet: a classic control-plane failure that kills a healthy data plane.

Likely follow-ups
  • Why is etcd usually run with 3 or 5 members? (Raft needs a majority; 3 tolerates 1 failure, 5 tolerates 2.)
  • If the API server is down, do running pods stop? (No. Kubelets keep containers running, but nothing new can be scheduled or healed.)

Scenario K9: an OS security patch takes down pod networking on many nodes

No deploy happened. At the same time across several regions, pods start losing network connectivity. Node auto-repair begins replacing machines. This mirrors Datadog's public write-up of its 8 March 2023 outage.

Kubernetes kernel routing, change management level: SDE-2 commonly reported at: any company team: networking background helps

Weak answer: "Kubernetes must have a bug." Kubernetes did not change; the node underneath it did.

Strong answer:

  1. "What changed?" includes the OS. Check unattended upgrades and package logs on the nodes. In Datadog's case, an automatic Ubuntu security update restarted systemd-networkd, which removed IP routing rules it did not own, including the rules Cilium needs.
  2. Verify on a node. Compare ip rule and routing tables on a broken node and a healthy node.
  3. Mitigate. Restart the CNI agent to re-add rules, pause node auto-repair if it is replacing nodes faster than stateful systems can recover (Datadog reported that replacing many instances wiped local disks and slowed recovery).
  4. Prevent. Treat OS updates as a deploy: roll them out progressively, one zone or one percentage at a time, with health checks. Pin or configure network daemons so they do not touch rules they do not own.
$ ip rule show            # on a healthy node: extra rules from the CNI
0:      from all lookup local
9:      from all fwmark 0x200/0xf00 lookup 2004
32766:  from all lookup main
$ ip rule show            # on a broken node: the CNI rule is gone
0:      from all lookup local
32766:  from all lookup main
Likely follow-ups
  • Why can automatic node repair make a stateful outage worse?
  • What is a "progressive rollout" for infrastructure, and how do you measure each step?

Scenario K10: the HPA does not scale up even though the service is overloaded

Queue latency is high, users wait, but kubectl get hpa shows the target as <unknown>/70% and replicas never change.

Kubernetes autoscaling level: SDE-2 commonly reported at: Amazon, Flipkart

Weak answer: "Set minReplicas to 100." It burns money and does not fix autoscaling.

Strong answer:

  1. <unknown> means no metric. Either metrics-server is not running, or the pods have no CPU request; utilisation is calculated as a percentage of the request, so without a request there is nothing to divide by.
  2. Check the right signal. If the service is waiting on I/O or a queue, CPU may stay low while users suffer. Scale on a better metric: requests per second, or queue depth / Kafka lag via KEDA or an external metric.
  3. Check limits. Is maxReplicas already reached? Are new pods Pending (scenario K2)?
  4. Prevent. Alert when an HPA is at max for a long time or when its metric is missing.
$ kubectl describe hpa worker | grep -A2 Conditions
Conditions:
  ScalingActive  False  FailedGetResourceMetric  the HPA was unable to compute the replica count:
                 failed to get cpu utilization: missing request for cpu in container "worker"
Likely follow-ups
  • Why would you scale Kafka consumers on lag rather than CPU? And what is the ceiling? (The number of partitions; see drill F1.)
  • What is scale-down stabilisation and why does it exist? (To stop flapping.)

Scenario K11: a stateful pod is stuck after its node died

A node running postgres-0 (a StatefulSet pod with a cloud disk) became unreachable. The pod is stuck in Terminating and the replacement will not start, saying the volume is still attached elsewhere.

Kubernetes StatefulSets, storage level: SDE-2 commonly reported at: any company

Weak answer: "Force delete the pod right away." Maybe, but only after you know the old node is really dead, otherwise two database processes could write to the same disk.

Strong answer: this is a fencing problem. A StatefulSet promises at most one pod per identity. Kubernetes cannot tell "the node is dead" from "the network to the node is broken", so it refuses to start postgres-0 twice.

  1. Confirm the node is gone. Check the cloud console: is the VM stopped or terminated?
  2. Fence it. If the node is truly down, delete the Node object (or let the cloud controller do it) or force-delete the pod; then the volume can be detached and attached to the new node.
  3. Recover. The new postgres-0 starts with the same PVC and name.
  4. Prevent. Run databases with replication through an operator (for example CloudNativePG) so a replica takes over without waiting, and know your RTO.
Likely follow-ups
  • Would you run your database on Kubernetes or use a managed service? Give the trade-offs.
  • What is split brain and how do leases or STONITH prevent it?
