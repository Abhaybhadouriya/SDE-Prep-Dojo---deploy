Multi-stage builds: build fat, ship thin

To compile a Go or Java service you need compilers, SDKs and build tools: hundreds of megabytes. To run it you need only the output: one binary or one jar plus a runtime. A multi-stage build uses several FROM lines in one Dockerfile. Early stages build; the final stage copies just the result with COPY --from=. Everything else is thrown away.

# syntax=docker/dockerfile:1
FROM golang:1.25 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
# syntax=docker/dockerfile:1
FROM python:3.12-slim AS build
RUN python -m venv /venv
ENV PATH=/venv/bin:$PATH
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

FROM python:3.12-slim
RUN useradd --uid 10001 --no-create-home --shell /usr/sbin/nologin app
COPY --from=build /venv /venv
ENV PATH=/venv/bin:$PATH PYTHONUNBUFFERED=1
WORKDIR /app
COPY --chown=10001:10001 . .
USER 10001
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/healthz')"
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -q package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/*.jar /app/app.jar
USER 10001
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]

Things to notice in all three:

  • Dependencies before source in the build stage, for the cache reason above.
  • Cache mounts (RUN --mount=type=cache,...) keep the package manager's download cache on the builder between builds, but never put it in a layer. Even when the layer misses, packages do not re-download from the internet.
  • A non-root numeric user in the final stage.
  • Java: -XX:MaxRAMPercentage=75 sizes the heap from the container's memory limit (JVMs are container-aware since JDK 10, and cgroup v2-aware since JDK 15 (backported to 11.0.16 and 8u372); on older builds running on a cgroup v2 host the JVM sees the host's RAM), leaving room for non-heap memory. Without it, a JVM in a container is a classic exit-137 story.
