Secrets during the build, the right way

Sometimes a build needs a token, for example to download a private package. Never use ARG, ENV or COPY for it: all three end up readable in the image. BuildKit can mount a secret file for one RUN step only; it never touches a layer.

# syntax=docker/dockerfile:1
FROM node:22-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]
docker build --secret id=npmrc,src=$HOME/.npmrc -t web:1.0 .

For private Git repositories use RUN --mount=type=ssh with docker build --ssh default, which forwards your SSH agent instead of copying a key. Uber and Shopify both wrote about secrets leaking into images as one of the hard lessons of running containers at scale.

How big should an image be? (rule of thumb)

There is no official number, but these ranges are what a well-built runtime image usually lands at. Treat them as a rule of thumb (uncompressed size as shown by docker images; your sizes will differ):

Service typeTypical runtime baseGood targetRed flag
Static Go or Rust binaryscratch or distroless/staticTens of MB or less (base is a few MB, the rest is your binary)Hundreds of MB: you shipped the compiler image
Python servicepython:3.12-slimAbout 100-200 MB (most of it is the interpreter and your wheels)Over 1 GB: full python base, build tools or caches left in
Node.js servicenode:22-slim or distroless nodeAbout 150-300 MBOver 1 GB: dev dependencies, .git or the full node base
JVM serviceA JRE base such as eclipse-temurin:21-jreAbout 200-300 MB (the JRE is most of it)A JDK or Maven image in the final stage

Why it matters, and when it stops mattering. Size is mostly a pull-time problem: when an autoscaler adds a new node, that node must download the image before the first pod can start, so a 1.4 GB image adds real seconds to every scale-out and every deploy (see page 02, "Image size is a deploy-speed problem"). A smaller image also has fewer packages for a scanner to flag. Once you are in the "good target" column, shaving the last 20 MB rarely pays; spend the time on cache ordering instead. Shared base layers are downloaded once per node, so ten services on the same base cost less than ten times the size.

More BuildKit features worth knowing

  • Heredocs make long scripts readable: 
    RUN <<EOF
set -eux
apt-get update
apt-get install -y --no-install-recommends ca-certificates curl
rm -rf /var/lib/apt/lists/*
EOF
  • COPY --link makes a copied layer independent of the layers below it, so changing the base image does not force that copy to redo.
  • RUN --mount=type=bind reads files from the context during one step without copying them into a layer.
  • Remote cache: docker buildx build --cache-to type=registry,ref=... --cache-from type=registry,ref=... (or type=gha on GitHub Actions) shares the cache between CI runners (the throwaway machines a CI system builds on), which otherwise start cold every time. Page 09 shows a full CI pipeline.
  • Linting: hadolint Dockerfile catches common mistakes (unpinned versions, apt without cleanup, missing USER).

Shrinking a 1.2 GB image: the checklist

  1. Measure. docker history --no-trunc img or dive img to see which layer is big.
  2. Multi-stage. Keep compilers, SDKs and test data in the build stage.
  3. Smaller base. -slim, distroless or scratch for the runtime stage.
  4. .dockerignore. Stop .git, node_modules, datasets and logs from being copied.
  5. Clean in the same RUN. --no-install-recommends, rm -rf /var/lib/apt/lists/*, pip --no-cache-dir or cache mounts.
  6. Only production dependencies. npm ci --omit=dev, no test frameworks in the final image.
