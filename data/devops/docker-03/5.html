CMD vs ENTRYPOINT, shell form vs exec form, and PID 1

This topic causes real production bugs ("why does docker stop always take 10 seconds?") and comes up in almost every Docker interview.

ENTRYPOINT is the program, CMD is the default arguments

Dockerfiledocker run imgdocker run img -b 0.0.0.0:9000 app:app
CMD ["gunicorn","app:app"]gunicorn app:app-b 0.0.0.0:9000 app:app (CMD replaced: Docker tries to run a program called -b, fails)
ENTRYPOINT ["gunicorn"]
CMD ["app:app"]		gunicorn app:appgunicorn -b 0.0.0.0:9000 app:app (CMD replaced, ENTRYPOINT kept)
ENTRYPOINT ["/server"] only/server/server -b 0.0.0.0:9000 app:app (arguments appended)

Rule of thumb: use CMD alone for most apps (easy to override for debugging, for example docker run -it img sh). Use ENTRYPOINT when the image is a single tool, like a CLI, where arguments should be appended. --entrypoint on docker run replaces the ENTRYPOINT.

Shell form vs exec form

# exec form (JSON list): the program itself becomes PID 1
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

# shell form (plain string): Docker runs /bin/sh -c "..."; for a compound command like this, the SHELL stays PID 1
CMD echo "starting" && gunicorn -b 0.0.0.0:8000 app:app

Why does it matter? Because of how docker stop works and how Linux treats PID 1.

  • docker stop sends SIGTERM to PID 1 in the container, waits 10 seconds (change with -t), then sends SIGKILL.
  • PID 1 of a PID namespace is special: the kernel does not apply default signal actions to it. If PID 1 has no handler for SIGTERM, the signal is simply ignored. Only SIGKILL (sent from outside) always works.
  • With a single simple command some shells (dash, bash) exec it directly, so the bug shows with && chains, pipes or scripts. Shells differ in how clever they are here, so do not guess: check /proc/1/comm inside the container, as in the lab below.
  • In shell form with a compound command, PID 1 is sh. It has no SIGTERM handler and does not forward the signal to your app. Your app never hears "please shut down", so it cannot finish requests or close connections. After 10 seconds everything is SIGKILLed, and the exit code is 137.
  • PID 1 also has to reap zombies: adopt orphaned child processes and call wait() on them. A normal app does not do that, so a container whose app spawns helper processes can fill up with zombies.

Measure it yourself. First start two containers that run the same long-lived program, one behind a shell command that has more work after the app (so sh must stay PID 1) and one in exec form. We use sleep as the "app" because it has no SIGTERM handler, so we add --init to the exec-form one to show the fixed behaviour:

# shell form with a command after the app: sh -c must stay PID 1, sleep is its child
docker run -d --name shellform alpine:3.24 sh -c 'sleep 1000; echo stopped'

# exec form plus an init: tini is PID 1 and forwards SIGTERM to sleep
docker run -d --init --name execform alpine:3.24 sleep 1000

# check who is PID 1 in each
docker exec shellform cat /proc/1/comm
docker exec execform cat /proc/1/comm
$ docker exec shellform cat /proc/1/comm
sh
$ docker exec execform cat /proc/1/comm
docker-init

Now stop both and compare:

$ time docker stop shellform
shellform
real    0m10.4s
$ docker inspect -f '{{.State.ExitCode}}' shellform
137
$ time docker stop execform
execform
real    0m0.6s
$ docker inspect -f '{{.State.ExitCode}}' execform
143

Your times will differ slightly. The shell-form container waits the full 10 seconds and is SIGKILLed (137). In the second one the signal reaches sleep, which dies at once; tini reports 128 + 15 = 143. A real app with a SIGTERM handler that exits cleanly reports 0. Clean up with docker rm shellform execform.

Exec form is necessary but not always enough. Even as PID 1 in exec form, a program with no SIGTERM handler ignores SIGTERM (the kernel's PID 1 rule). Node.js and simple Python scripts are common examples. Fixes: handle SIGTERM in your code (process.on('SIGTERM', ...), Python signal.signal(...)), or run with docker run --init, which starts tini as PID 1 to forward signals and reap zombies. Yelp built dumb-init for exactly this reason in 2016, and Docker later added --init. In Kubernetes, the same SIGTERM, wait, SIGKILL dance happens on every pod shutdown (default grace period 30 seconds).

From your world

PID 1 in a container is init on an embedded board. On your line cards, whatever runs as PID 1 must install signal handlers, reap children and coordinate shutdown, or you get zombies and boards that hang on reboot. In a container, your app is suddenly that init, whether it was written for the job or not. Where it breaks: a board's init usually lives forever; a container's PID 1 exiting ends the whole container immediately, killing every other process in its PID namespace.

ARG vs ENV

# build-time only; change it with: docker build --build-arg PY_VERSION=3.13 .
ARG PY_VERSION=3.12
FROM python:${PY_VERSION}-slim
# an ARG must be declared again after FROM to be used inside this stage
ARG APP_VERSION=dev
# copy it into ENV if the running app needs it
ENV APP_VERSION=${APP_VERSION}
# runtime setting: Python log lines appear immediately
ENV PYTHONUNBUFFERED=1

Note: in a Dockerfile, # starts a comment only at the beginning of a line. A # after an instruction becomes part of its value, so comments always go on their own line.

ARG exists only while building; ENV is baked into the image config and visible to the running container. Both are readable by anyone with the image (docker history, docker inspect), so neither is safe for passwords or tokens.
