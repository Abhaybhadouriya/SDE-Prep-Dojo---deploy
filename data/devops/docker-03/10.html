Interview questions

The 60-second answer: "How do you write a good Dockerfile?"
"I start from a small, pinned base and use a multi-stage build: a build stage with the compiler and dependencies, and a final runtime stage that copies in only the artifact, usually on slim or distroless. I order instructions from least to most frequently changing, so I copy the dependency manifest and install dependencies before copying the source; that keeps the slow install cached across code edits. I use BuildKit cache mounts for package managers and secret mounts for any credentials, never ARG or ENV. A .dockerignore keeps .git and local secrets out of the context. The final stage runs as a non-root numeric user, uses exec-form CMD so the app gets SIGTERM for graceful shutdown, and has a healthcheck. In CI I lint with hadolint, share the build cache through the registry, and tag images immutably by commit SHA."

What is the difference between CMD and ENTRYPOINT?

ENTRYPOINT sets the program the container always runs; CMD sets default arguments (or the default command if there is no ENTRYPOINT). Arguments after the image name in docker run replace CMD, while ENTRYPOINT is only replaced with --entrypoint. A common pattern is ENTRYPOINT ["gunicorn"] plus CMD ["app:app"], so users can change the arguments but not the program. Both should use exec form so the process is PID 1 and receives signals.

How to answer

One sentence each ("program" vs "default args"), then the override rules, then the exec-form point, which shows production awareness.

Likely follow-ups
  • What happens with shell form when you run docker stop?
  • How do you get a shell in an image whose ENTRYPOINT is a binary? (--entrypoint sh.)
Every CI build reinstalls all dependencies and takes 10 minutes. How do you speed it up?

First check the cache in the build log to see where the first miss is. Usually the Dockerfile copies the whole source before installing dependencies, so any code change invalidates the install; I would copy only the lock file first and install, then copy the source. Second, CI runners start with an empty cache, so I would export and import the BuildKit cache through the registry or the CI's cache backend (--cache-to/--cache-from, type=gha on GitHub Actions). Third, cache mounts keep package downloads between builds even when a layer misses. Fourth, multi-stage builds let independent stages run in parallel and skip unneeded ones. And a good .dockerignore prevents spurious misses from changing files like .git.

How to answer

Diagnose first ("where is the first cache miss?"), then fixes in order of impact. Uber's Makisu post is a nice real story: they reported builds of up to 2 hours before rethinking caching.

Likely follow-ups
  • Does the cache notice that a package has a new version upstream? (No: RUN text is the key.)
  • How would you force a refresh of the base image? (--pull.)
What is a multi-stage build and why use it?

A Dockerfile with several FROM stages. Earlier stages compile or install with the full toolchain; the final stage starts from a small base and copies only the artifacts with COPY --from=stage. The result is a much smaller image with fewer packages, so it pulls faster and has a smaller attack surface, while the build stays a single reproducible file. BuildKit also runs independent stages in parallel, skips stages the target does not need, and lets you build a test stage with --target.

How to answer

Definition, then the two wins (size, security), then a concrete number with a hedge ("a Go service typically goes from hundreds of MB to tens of MB"), then the trade-off: no shell in distroless makes debugging harder.

Likely follow-ups
  • How do you debug a distroless container? (docker debug, a debug container sharing namespaces, or kubectl debug in K8s.)
  • Alpine or distroless for a Python service?
docker stop takes exactly 10 seconds every time and the app logs no shutdown message. Why?

10 seconds is the default stop timeout, so SIGTERM is being ignored and Docker falls back to SIGKILL (exit code 137). Usual causes: shell-form CMD, so /bin/sh is PID 1 and does not forward the signal; or the app is PID 1 with no SIGTERM handler, and the kernel does not apply default signal actions to PID 1 of a namespace. Fixes: exec-form CMD; add a SIGTERM handler that drains in-flight work; or docker run --init (tini) to forward signals and reap zombies; set STOPSIGNAL if the app expects a different signal.

How to answer

Decode the clue (exactly 10 s = timeout), name the PID 1 rule, give fixes, and say why it matters: in-flight requests and connections are cut, and in Kubernetes rolling updates this causes errors during every deploy.

Likely follow-ups
  • What is a zombie process and who reaps it in a container?
  • How does Kubernetes' termination grace period relate to this?
How do you pass secrets to a Docker build safely?

With BuildKit secret mounts: RUN --mount=type=secret,id=token,... plus docker build --secret id=token,src=.... The secret is available as a file only during that one RUN and is never written to a layer or the build cache. For Git over SSH, use --mount=type=ssh with agent forwarding. Never use ARG or ENV (visible in history and inspect) and never COPY then delete (the file stays in the earlier layer). Runtime secrets should come from the platform at run time, such as Kubernetes Secrets or a secret manager, not from the image.

How to answer

Give the right tool, then explain why each wrong tool fails (this shows you understand layers), then separate build-time from run-time secrets.

Likely follow-ups
  • A secret already leaked into an image. What now? (Rotate first, then purge digests, then fix the build.)
  • How would CI provide the secret? (CI secret store passed to --secret.)
Alpine, Debian slim or distroless: which base would you choose and why?

For most services I default to a Debian-slim based image for the build and slim or distroless for the runtime. Alpine is tiny but uses musl libc, which behaves differently from glibc (DNS resolution details, some performance characteristics) and often forces Python packages to compile from source because standard wheels target glibc. Distroless and similar hardened images remove the shell and package manager, which cuts CVEs and attack surface, at the cost of harder debugging. For fully static Go binaries, scratch or distroless/static is ideal.

How to answer

Give a default with a reason, then the specific gotcha of each alternative. Mentioning musl shows real experience.

Likely follow-ups
  • How do you keep base images patched?
  • What would you add to a scratch image for HTTPS calls? (CA certificates.)

Scenario: the 1.4 GB Node.js image

Your team's Node.js API image is 1.4 GB. Deploys are slow because new Kubernetes nodes take a long time to pull it. The Dockerfile is FROM node:22, COPY . ., RUN npm install, CMD npm start.

Weak answer: "Switch to Alpine, that will fix it."

Strong answer: "I would measure with docker history or dive first, but this Dockerfile has four problems. One: the full node:22 image includes build tools; use a slim base for runtime. Two: COPY . . probably copies the local node_modules and .git, so add a .dockerignore. Three: npm install installs dev dependencies; use a multi-stage build with npm ci in a build stage and npm ci --omit=dev or a pruned copy in the final stage, and copy package*.json before the source for caching. Four: CMD npm start is shell form, so /bin/sh is PID 1 with npm under it, and SIGTERM never reaches node. Even CMD ["npm","start"] is weak, because npm is a poor signal forwarder; use CMD ["node", "server.js"] with a SIGTERM handler, or --init. Then verify the new size and pull time, and add hadolint to CI so it does not regress."

Likely follow-ups
  • What if the app needs native modules compiled with node-gyp? (Compile in the build stage on the same base family as runtime.)
  • How would you stop images from growing again? (Size budget check in CI.)

Scenario: "It passed on my Mac, crashes on the server"

A developer builds an image on an Apple Silicon MacBook and pushes it. On the x86 production server, the container exits immediately with exec /server: exec format error.

Weak answer: "The image is corrupted, rebuild and push again."

Strong answer: "Exec format error means the binary's CPU architecture does not match the host. The Mac built a linux/arm64 image. Containers share the host kernel but do not emulate the CPU. Short term: build with --platform linux/amd64. Long term: CI should build multi-platform images with docker buildx build --platform linux/amd64,linux/arm64 --push, ideally cross-compiling with --platform=$BUILDPLATFORM in the build stage rather than slow QEMU emulation, and images should be built in CI, not on laptops, so what we test is what we ship."

Likely follow-ups
  • How does a single tag serve both architectures? (Image index; see page 02.)
  • Why move to ARM servers at all? (Price/performance, as in Swiggy's Graviton migration.)
