The build cache: why one changed line rebuilds everything after it

Must know. The cache rules and the "copy the lock file first" ordering are asked in almost every Docker interview, and they decide whether your builds take seconds or minutes. Do not skip this section.

This is the learner's question: "why does changing one line in my Dockerfile rebuild everything after it?" Here is the exact rule BuildKit uses for each step, top to bottom:

  1. Was the parent step a cache hit? If any earlier step was rebuilt, this step must be rebuilt too. Layers are stacked, so a new bottom means a new everything-above.
  2. Is the instruction text identical? RUN pip install -r requirements.txt must match character for character. Note: Docker does not re-check what a RUN downloads; if the text is the same, it reuses the layer even if a newer package exists upstream.
  3. For COPY and ADD: are the files identical? BuildKit compares checksums of the copied files (contents and metadata). Change one byte in any copied file and that COPY misses.

Once one step misses, every later step rebuilds. Click through to see why the order of two lines matters so much.

  1. First build. Both Dockerfiles build every step once. They produce images that work the same way.
  2. You change app.py. This is what developers do fifty times a day. requirements.txt did not change.
  3. Rebuild. Left: COPY . . sees a changed file and misses, so pip install runs again even though no dependency changed. Right: COPY requirements.txt still matches, so the slow install is cached; only the final COPY . . reruns.
  4. The cost. On the left, every code edit pays the full dependency install. On the right, it costs about as long as copying a few files. Same rule for package.json, go.mod/go.sum, pom.xml and Cargo.toml.

See it for real. Change app.py and rebuild:

$ echo "# tiny change" >> app.py
$ docker build -t hello-py:1.1 .
[+] Building 0.9s (11/11) FINISHED                                 docker:default
 => [1/5] FROM docker.io/library/python:3.12-slim@sha256:...                 0.0s
 => CACHED [2/5] WORKDIR /app                                                0.0s
 => CACHED [3/5] COPY requirements.txt .                                     0.0s
 => CACHED [4/5] RUN pip install --no-cache-dir -r requirements.txt          0.0s
 => [5/5] COPY . .                                                           0.1s
 => exporting to image                                                       0.2s

From your world

The build cache works like make: each step is a target whose inputs are its parent layer, its command text and its copied files. If no input changed, the old output is reused. The difference from make is that Docker's dependency chain is a straight line by default (each step depends on the one above), so ordering is your only lever, unless you use multi-stage builds, which turn the line into a graph. Where it breaks: make checks timestamps of outputs; BuildKit checks content hashes of inputs, so touching a file without changing it does not break the cache.

The stale-cache trap: RUN apt-get update on its own line gets cached forever, so a later RUN apt-get install curl may use a months-old package list and fail. Always write RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/* as one step. To force a fresh build on purpose, use docker build --no-cache or --pull (to refresh the base image).
