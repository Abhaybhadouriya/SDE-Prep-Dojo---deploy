Interview questions

Scenario: "cut our EKS compute bill by 40% without hurting availability"

The cluster runs 60 m5.2xlarge On-Demand nodes in three managed node groups with the Cluster Autoscaler. Average CPU use is 25%.

Weak answer: "Move everything to Spot."

Strong answer: "First fix requests: 25% use usually means requests are inflated, so nodes look full. Right-size from VPA recommendations. Then move to Karpenter with two NodePools: an On-Demand pool (tainted) for stateful and critical system pods, and a flexible pool allowing Spot and On-Demand across many c/m/r families and both amd64 and arm64. Consolidation packs the cluster continuously. Build multi-arch images so Graviton can be used. Protect availability with PDBs, zone and capacity-type topology spread, SIGTERM handling and the interruption queue. Cover the steady baseline with a Compute Savings Plan. Measure cost per request before and after."

Likely follow-ups
  • What would you not put on Spot? (Kafka brokers, databases, single-replica services, long jobs without checkpoints.)
What are an ECS task definition, a task and a service? Map them to Kubernetes.

A task definition is a versioned, immutable blueprint (images, CPU/memory, ports, env and secrets, IAM roles, log config, network mode) - like a pod spec. A task is a running instance of it - like a pod. A service keeps a desired count of tasks running, replaces unhealthy ones, rolls out new revisions with min/max percent and a circuit breaker, and registers tasks in a load balancer target group - like a Deployment plus a Service, with Service Auto Scaling playing the HPA's role.

How to answer

Three nouns, three Kubernetes equivalents, then one ECS-specific detail (task role vs execution role) to show hands-on knowledge.

Likely follow-ups
  • What does minimumHealthyPercent=100, maximumPercent=200 mean during a deploy?
Fargate vs EC2 launch type: what do you gain and what do you give up?

Fargate removes node management: no AMIs, patching, instance sizing, bin-packing or cluster scaling, and each task gets its own isolation boundary (Firecracker microVMs). You pay per task vCPU and GB-second. You give up host access (no privileged containers, DaemonSets, GPUs, custom kernels or sysctls beyond the allowed set), shared image caching (each task pulls its image), and usually some cost efficiency at large steady scale compared with well-packed EC2 on Savings Plans or Spot. Rule of thumb: Fargate for small teams and spiky or modest services; EC2 for large steady fleets and special hardware.

How to answer

Frame it as a responsibility line: "what is mine vs AWS's", then cost and limits.

Likely follow-ups
  • How is a Fargate task isolated from another customer's task?
  • How would you run a logging agent on Fargate? (Sidecar or FireLens, since there are no DaemonSets.)
ECS or EKS for a new product team? Defend your choice.

Ask about team skills, portability needs, ecosystem needs and scale. For a small team, AWS-only, a handful of stateless services: ECS on Fargate - no control-plane fee, no version upgrades, deep AWS integration, least to operate. For an organisation already on Kubernetes, needing operators (Strimzi, cert-manager), GitOps with Argo CD, a service mesh, or multi-cloud: EKS, accepting the cluster fee, regular upgrades and a platform team. Either way the containers and CI stay the same, so the choice is reversible at moderate cost.

How to answer

Never answer with a product name first; list the deciding factors, then decide for the stated context.

Likely follow-ups
  • What does the EKS control plane fee buy you?
How do pods get IP addresses on EKS, and why can a node run out of pod IPs while CPU is free?

The Amazon VPC CNI attaches ENIs to the node and assigns pods secondary IPs from the subnet, so pods are first-class VPC addresses with no overlay. Each instance type has a maximum number of ENIs and IPs per ENI, which caps pods per node (roughly ENIs x (IPs per ENI - 1) + 2), and the subnet itself can run out. Fixes: prefix delegation (a /28 per slot), larger subnets or a secondary CIDR for pods, or IPv6. Security groups for pods use branch ENIs via trunking.

How to answer

Contrast with overlay CNIs (Flannel VXLAN): no encapsulation, but IP-hungry. That contrast is what the interviewer wants.

Likely follow-ups
  • How big should EKS subnets be?
Karpenter vs Cluster Autoscaler: how do they differ?

The Cluster Autoscaler increases the desired size of pre-defined node groups (ASGs) when pods are Pending, and scales them down when nodes are underused; each node group is one shape, so flexibility means many groups. Karpenter has no node groups: it reads pending pods' constraints, chooses from all allowed instance types, launches instances directly through EC2 Fleet, and continuously consolidates by replacing or deleting nodes when a cheaper packing exists. It also handles Spot interruption events, drift (AMI or config changes) and node expiry. Results: faster scale-out, better bin-packing, fewer configs. Trade-offs: more node churn (needs PDBs and graceful shutdown), and an AWS-centric provider ecosystem.

How to answer

"Groups vs groupless" in the first sentence, then consolidation, then the churn trade-off.

Likely follow-ups
  • Where should the Karpenter controller itself run?
  • How do you stop consolidation during business hours? (Disruption budget with a schedule.)
Design node pools for a cluster that runs Kafka, a web tier and nightly batch jobs, using Spot where safe.

Three NodePools. (1) stateful: On-Demand only, tainted, storage-optimised or memory families, for Kafka brokers with zone spread and PDBs (maxUnavailable 1); consolidation WhenEmpty only. (2) web: Spot + On-Demand, amd64 + arm64, many families; replicas spread across zones and capacity types; PDBs; interruption queue on. (3) batch: Spot-heavy, large instances, tainted for batch; jobs checkpoint or are idempotent and retried; do-not-disrupt on long non-checkpointing jobs; limits to cap spend. Weights or taints keep pools mutually exclusive. Multi-arch images for anything allowed on arm64.

How to answer

Classify workloads by interruption tolerance first, then derive pools. Mention limits and budgets for cost safety.

Likely follow-ups
  • What happens to a Spot node's pods in the two minutes after a reclaim notice?
We want to move to Graviton. What can break and how do you roll it out?

Images must be multi-arch; native dependencies (C extensions, JNI, vendored binaries, third-party agents and sidecars) must have ARM64 builds; performance can differ per workload, so benchmark. Rollout: build multi-arch images in CI with buildx; add arm64 to one NodePool for one service, or use node affinity preferences; compare latency and cost per request; expand service by service. Failures show as exec format error only on arm64 nodes, so keep a kubernetes.io/arch selector as an escape hatch. On ECS, set runtimePlatform.cpuArchitecture: ARM64 in the task definition.

How to answer

Three risks, a canary-style rollout, and a measured success metric.

Likely follow-ups
  • How does a multi-arch image work under the hood? (Image index pointing at per-platform manifests.)

Interviewers love this: "Requests drive both the scheduler and Karpenter. Fix requests first, then consolidation and Spot do the saving." It shows you know where cost really comes from.

How does a pod on EKS get AWS permissions, and how is that different from ECS?

On ECS, the task definition names a task role and the ECS agent serves temporary credentials for it on a task-local endpoint. On EKS you bind a Kubernetes service account to an IAM role. With EKS Pod Identity you install the agent add-on and create an association (cluster, namespace, service account, role); the role trusts pods.eks.amazonaws.com, and the node agent hands out the credentials. With IRSA, the cluster has an IAM OIDC provider, the service account is annotated with the role ARN, the pod gets a projected token, and the SDK exchanges it with STS AssumeRoleWithWebIdentity; the role trust policy restricts the OIDC subject to that service account. Either way, never use the node's instance role for app permissions, because every pod on the node would share it.

How to answer

Contrast the three in one breath, then say why not the node role. Mention that Karpenter and the Load Balancer Controller depend on this.

Likely follow-ups
  • Why might you still use IRSA? (Non-EKS clusters, Fargate pods, or existing setups.)
  • How do you stop pods from using the node role through IMDS? (IMDSv2 with hop limit 1, or block 169.254.169.254 with a NetworkPolicy.)
