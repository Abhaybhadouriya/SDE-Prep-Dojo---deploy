Spot plus On-Demand, amd64 plus arm64 (Graviton)

Good to know (SDE-2)

Two cost levers stack well on Kubernetes: Spot instances (spare EC2 capacity, priced up to 90% below On-Demand, reclaimable with a two-minute warning) and Graviton (AWS-designed ARM64 CPUs; AWS states up to 40% better price performance than comparable x86 instances). Both need preparation.

Making Spot safe

  1. Diversify. Allow many instance families, sizes and all AZs. Every type+AZ is a separate Spot pool; more pools means fewer interruptions and fewer "insufficient capacity" errors.
  2. Handle the two-minute warning. Point Karpenter's --interruption-queue at the SQS queue that receives EC2 interruption events: it taints and drains the node and launches a replacement in parallel. Your pods must shut down cleanly on SIGTERM well within that window (graceful shutdown).
  3. Spread replicas across zones and capacity types so one reclaim wave cannot take every replica: topologySpreadConstraints on topology.kubernetes.io/zone and on karpenter.sh/capacity-type.
  4. PDBs on every service, so voluntary drains (consolidation) never take too many at once.
  5. Keep state off Spot. Brokers, databases and anything with long recovery go to the On-Demand pool.
# In the Deployment: guarantee some replicas on on-demand, spread over zones
spec:
  template:
    spec:
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: web } }
        - maxSkew: 2
          topologyKey: karpenter.sh/capacity-type
          whenUnsatisfiable: ScheduleAnyway
          labelSelector: { matchLabels: { app: web } }

Making arm64 safe: multi-arch images

A node only runs images built for its CPU. If a NodePool allows both amd64 and arm64, every image a pod might use must be a multi-arch image: one tag pointing to an OCI image index (manifest list) with one image per platform. The container runtime picks the right one at pull time. Build it once in CI (see Production, Security & CI):

docker buildx create --use --name multi
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 111122223333.dkr.ecr.ap-south-1.amazonaws.com/web:1.8.2 --push .

From your world

This is cross-compiling for two targets, the same problem as building a kernel or a router image for x86 line cards and ARM control cards. buildx either uses native builders per arch or emulates the other arch with QEMU user-mode registered through binfmt_misc (slow for compile-heavy builds - use native ARM runners or cross-compilation when you can). Interpreted and JIT languages (Java, Python, Node, Go with GOARCH) port easily; the traps are native dependencies: C extensions, JNI libraries, vendored .so files and agents built only for x86, which fail with exec format error.
