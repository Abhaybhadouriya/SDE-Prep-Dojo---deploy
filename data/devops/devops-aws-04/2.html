Fargate: serverless compute for containers

Must know (SDE-1)

A third option arrived in late 2025: ECS Managed Instances, EC2 capacity that AWS provisions, patches and scales for you, while you still choose instance families (including GPUs) and keep EC2 pricing options. It sits between "your own EC2 fleet" and Fargate.

With the EC2 launch type you run a fleet of EC2 instances (usually in an Auto Scaling group linked to an ECS capacity provider), the ECS agent on each registers it, and ECS packs tasks onto them. You patch the AMI, choose instance types and pay for idle headroom. With Fargate there are no instances in your account: you give each task a size (from 0.25 vCPU / 0.5 GB up to 16 vCPU / 120 GB, with 20 GiB of ephemeral storage by default, configurable up to 200 GiB) and AWS finds somewhere to run it. You pay per second for the vCPU and memory of the task while it runs. Fargate also works under EKS: a Fargate profile selects pods by namespace and labels and runs each one on Fargate.

From your world

On a normal container host, all containers share one kernel: namespaces and cgroups are partitions inside it, and a kernel exploit crosses every boundary. Fargate gives each task its own isolation boundary - AWS documents that tasks do not share the kernel, CPU, memory or ENI with other tasks. AWS's Firecracker paper (NSDI 2020) explains the technology: Firecracker, a minimal virtual machine monitor in Rust that uses KVM to boot a tiny microVM in about 125 ms with under 5 MiB of overhead, wrapped in a "jailer" (seccomp, chroot, cgroups) as a second wall. It was built for Lambda and Fargate. So a Fargate task is closer to "a very small VM per pod" than to "a container on a shared host" - the same idea as Kata Containers or gVisor (sandboxed runtimes).

Fargate is great when
  • Small team, no wish to patch nodes or tune bin-packing
  • Spiky or batch workloads that are idle most of the day
  • Strong isolation per task is a requirement
  • Many small services, each with steady but modest load
Prefer EC2 / nodes when
  • Large steady fleets: per-vCPU price is higher than well-packed EC2, especially with Savings Plans or Spot
  • You need GPUs, privileged mode, DaemonSets, custom kernels or host tuning (sysctls, huge pages)
  • Very fast scale-out: a Fargate task pulls its whole image on every start (no shared image cache; SOCI lazy loading helps for big images)

Fargate Spot runs tasks on spare capacity at a discount; when AWS needs it back, the task gets a two-minute warning (a task state-change event and SIGTERM to the containers). Run only interruption-tolerant tasks there - stateless web replicas behind a load balancer, queue workers that checkpoint - and keep a base on regular Fargate.
