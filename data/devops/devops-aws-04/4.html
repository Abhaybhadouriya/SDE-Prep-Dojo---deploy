Karpenter: just-in-time nodes, NodePools and consolidation

Good to know (SDE-2)

The Cluster Autoscaler grows an existing Auto Scaling group when pods are Pending; it can only add more of the shapes you pre-defined, one ASG per shape. Karpenter (open source, started by AWS, now a Kubernetes SIG Autoscaling project) skips node groups. It watches for unschedulable pods, reads their requests, node selectors, affinities, tolerations and topology spread, picks instance types that fit from everything the NodePool allows, and calls the EC2 Fleet API directly. Click through one scale-out:

  1. Pending. The HPA scaled a Deployment from 10 to 15 replicas. kube-scheduler finds no node with 1 CPU / 2 Gi of unrequested capacity and marks 5 pods Unschedulable.
  2. Batch. Karpenter watches those pods. It waits a short batching window (seconds) so it can plan for the whole burst at once instead of one node per pod, then simulates scheduling with the same constraints the scheduler uses.
  3. Choose. It intersects the pods' needs with the NodePool's requirements (instance category, generation, arch, capacity type, zones) and ranks instance types that fit all 5 pods on as few nodes as possible.
  4. Launch. It creates a NodeClaim and calls EC2 CreateFleet with a list of acceptable instance types. For Spot it uses the price-capacity-optimized strategy: the deepest, least-likely-to-be-interrupted pools, then the cheapest of those. No ASG involved.
  5. Join and bind. The instance boots the AMI from the EC2NodeClass, the kubelet registers the node, and kube-scheduler binds the pending pods to it. Typically about a minute from Pending to Running, dominated by instance boot and image pull.
  6. Consolidate (later). Load drops. Karpenter keeps simulating: "could these pods fit on the other nodes, or on one cheaper node?" If yes, it cordons and drains the extra node (respecting PodDisruptionBudgets and disruption budgets) and terminates it.

Karpenter is configured with two kinds of objects. A NodePool (karpenter.sh/v1) says what kinds of nodes pods may get and how nodes may be disrupted. An EC2NodeClass (karpenter.k8s.aws/v1) says how to launch them on AWS: AMI, IAM role, subnets, security groups, disks.

apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  role: KarpenterNodeRole-dojo           # instance profile role for nodes
  amiSelectorTerms:
    - alias: al2023@latest               # pin a tested version (al2023@vYYYYMMDD) in prod
  subnetSelectorTerms:
    - tags: { karpenter.sh/discovery: dojo }   # the private subnets, one per AZ
  securityGroupSelectorTerms:
    - tags: { karpenter.sh/discovery: dojo }
---
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
      expireAfter: 720h                  # recycle nodes every 30 days (fresh AMI)
      requirements:
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["5"]
  limits:
    cpu: "400"                           # hard ceiling for this pool
    memory: 1600Gi
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
    budgets:
      - nodes: "10%"                     # never disrupt more than 10% of nodes at once
      - nodes: "0"                       # and nothing during business hours (UTC cron)
        schedule: "0 3 * * mon-fri"
        duration: 12h
        reasons: ["Underutilized"]

Key behaviours to know:

  • Consolidation policy. WhenEmptyOrUnderutilized (the default) deletes or replaces any node when that lowers cost; WhenEmpty only removes nodes with no workload pods. consolidateAfter is how long a node must be stable before it is a candidate.
  • Disruption budgets rate-limit voluntary disruption (consolidation, drift, emptiness). With none set, the default is 10% of nodes. The most restrictive matching budget wins.
  • Drift. Change the AMI alias, subnets or requirements and existing nodes become "drifted" and are replaced gradually - this is how you roll out a new AMI.
  • Expiry. expireAfter (default 720h) forces node replacement, a simple way to keep AMIs fresh.
  • Opt-out per pod. The annotation karpenter.sh/do-not-disrupt: "true" protects a long batch job's node from voluntary disruption.
  • Do not run Karpenter on nodes it manages. Put its controller on a small managed node group or on Fargate.

From your world

Consolidation is memory compaction for a cluster. The kernel migrates movable pages to free up whole contiguous blocks it can return; Karpenter migrates movable pods (evicts them, the ReplicaSet recreates them elsewhere) to free up whole nodes it can return to EC2. Just as unmovable pages block compaction, pods with do-not-disrupt, a PDB at its limit, or local storage block consolidation. And the disruption budget is your rate limiter - like bounding how much CPU kcompactd may burn.
