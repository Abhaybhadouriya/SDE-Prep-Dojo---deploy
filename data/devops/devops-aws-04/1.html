ECS: task definitions, services and desired count

Must know (SDE-1)

Amazon ECS (Elastic Container Service) is AWS's own container orchestrator. Its control plane is fully managed and free; you pay only for the compute your containers run on. Four nouns cover it:

ECS termWhat it isKubernetes cousin
ClusterA logical group of capacity (EC2 instances and/or Fargate) and servicesCluster
Task definitionVersioned JSON blueprint: images, CPU/memory, ports, env, secrets, IAM roles, log driver, network mode. Immutable; each change registers a new revision (web:7)Pod spec
TaskA running instance of a task definition: one or more containers sharing a network stackPod
ServiceKeeps desiredCount tasks running, replaces failed ones, does rolling deployments, registers tasks in a load balancer target group, scales with Service Auto ScalingDeployment + Service + HPA

A small but realistic task definition for Fargate on Graviton (ARM64):

{
  "family": "web",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512",
  "memory": "1024",
  "runtimePlatform": { "cpuArchitecture": "ARM64", "operatingSystemFamily": "LINUX" },
  "executionRoleArn": "arn:aws:iam::111122223333:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::111122223333:role/web-task",
  "containerDefinitions": [{
    "name": "web",
    "image": "111122223333.dkr.ecr.ap-south-1.amazonaws.com/web:1.8.2",
    "essential": true,
    "portMappings": [{ "containerPort": 8080, "protocol": "tcp" }],
    "secrets": [{ "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:ap-south-1:111122223333:secret:web-db" }],
    "healthCheck": { "command": ["CMD-SHELL", "curl -fs http://localhost:8080/healthz || exit 1"], "interval": 15, "retries": 3 },
    "logConfiguration": { "logDriver": "awslogs",
      "options": { "awslogs-group": "/ecs/web", "awslogs-region": "ap-south-1", "awslogs-stream-prefix": "web" } }
  }]
}

Two roles, often confused. The task execution role is used by the ECS agent/Fargate to pull the image from ECR, fetch secrets and write logs. The task role is what your code gets as AWS credentials - for example permission to s3:PutObject on one prefix (see S3 access). Never bake access keys into images.

aws ecs register-task-definition --cli-input-json file://web-taskdef.json \
  --query 'taskDefinition.[family,revision]' --output text
aws ecs create-service --cluster dojo --service-name web --task-definition web:7 \
  --desired-count 3 \
  --capacity-provider-strategy capacityProvider=FARGATE,base=2,weight=1 capacityProvider=FARGATE_SPOT,weight=3 \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-0a11,subnet-0b22],securityGroups=[sg-0web],assignPublicIp=DISABLED}' \
  --load-balancers targetGroupArn=arn:aws:elasticloadbalancing:ap-south-1:111122223333:targetgroup/web/abc123,containerName=web,containerPort=8080 \
  --deployment-configuration 'deploymentCircuitBreaker={enable=true,rollback=true},minimumHealthyPercent=100,maximumPercent=200'
aws ecs describe-services --cluster dojo --services web \
  --query 'services[0].[desiredCount,runningCount,pendingCount,deployments[0].rolloutState]'
web	7

Read the deployment settings like a Kubernetes rolling update: minimumHealthyPercent=100 and maximumPercent=200 mean "start new tasks first, never drop below 3 healthy" (like maxUnavailable: 0, maxSurge: 100% in Deployments). The deployment circuit breaker watches the new tasks; if they keep failing to start or failing health checks, it marks the rollout FAILED and rolls back to the last good revision. The capacity provider strategy says: the first 2 tasks (base) on regular Fargate, then 1 of every 4 extra tasks on Fargate and 3 on cheaper Fargate Spot.

From your world

The awsvpc network mode gives every task its own elastic network interface (ENI) - a real virtual NIC in your subnet, with its own private IP and its own security groups, exactly like an EC2 instance. Inside, ECS starts a hidden pause container that owns the network namespace, configures it with CNI plugins, and the app containers join that namespace, so they talk over localhost. That is the same trick as a Kubernetes pod sandbox. No NAT, no bridge, no port mapping: VPC route tables, NACLs and flow logs see the task as a first-class host. The cost: on EC2 instances, the number of ENIs per instance limits tasks per instance (a c5.large can attach 3 ENIs, one is the primary, so 2 awsvpc tasks) unless you turn on ENI trunking.

Deployment strategies: rolling, blue/green, linear, canary

Rolling (above) is the default, but since 2025 ECS has built-in alternatives set with deploymentConfiguration.strategy: BLUE_GREEN starts a full new task set, shifts traffic at the load balancer in one step, and keeps the old set during a bake time so rollback is instant; LINEAR and CANARY shift traffic in steps (for example 10% every few minutes, or 5% first and the rest later). All of them can roll back automatically on CloudWatch alarms and call lifecycle hooks (a Lambda that runs smoke tests before traffic moves). Before that you needed CodeDeploy for blue/green on ECS; it still works, but it is now the legacy path. The concepts are the same as in Zero-Downtime Releases.

"deploymentConfiguration": {
  "strategy": "BLUE_GREEN",
  "bakeTimeInMinutes": 15,
  "alarms": { "alarmNames": ["payments-5xx-high"], "enable": true, "rollback": true }
}
