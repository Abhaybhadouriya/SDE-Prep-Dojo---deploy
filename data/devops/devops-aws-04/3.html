ECS or EKS? A decision you must be able to defend

Must know (SDE-1)

Amazon EKS is managed Kubernetes: AWS runs the control plane (API server, etcd, scheduler, controllers) across three AZs and you pay a per-cluster hourly fee; you bring the data plane (nodes or Fargate). ECS is simpler and AWS-only; EKS is portable and has the Kubernetes ecosystem.

A strong interview answer is not "EKS is better". It is: "For a 6-person team running 10 stateless services on AWS only, ECS on Fargate gives the least operational load. If we already run Kubernetes elsewhere, need operators like Strimzi for Kafka, or want one deployment model across clouds, EKS is worth its upgrade cost."

EKS data plane options

  • Managed node groups - EKS creates and manages an EC2 Auto Scaling group with the EKS-optimized AMI; it drains nodes for you during AMI and version upgrades. Scale with the Cluster Autoscaler (one ASG per instance shape and AZ).
  • Self-managed nodes - your own ASG and launch template; full control, full responsibility.
  • Fargate profiles - pod-per-microVM; no DaemonSets, so logging and monitoring agents run as sidecars.
  • Karpenter - no node groups at all; it launches EC2 instances directly for pending pods (next section). EKS Auto Mode is AWS running Karpenter-based node management for you.

From your world

The default EKS networking plugin, the Amazon VPC CNI, does not build an overlay. Each pod gets a real secondary IP address from the node's ENIs, taken from your subnet's CIDR. Pod-to-pod traffic is plain routed VPC traffic - no VXLAN encapsulation, no extra MTU loss, and VPC flow logs show pod IPs. The price is IP address consumption: pods per node is bounded by ENIs x (IPs per ENI - 1) + 2, and a busy cluster can exhaust a /24 subnet. Prefix delegation assigns a whole /28 (16 addresses) per ENI slot instead of one IP - think of it as handing each line card a block of addresses instead of one at a time - which raises pod density and cuts EC2 API calls. Plan big private subnets (for example /19 per AZ) for EKS from day one; it is the networking decision that is hardest to change later.

Pod IAM: how a task or pod gets AWS credentials

Never put access keys in an image or a Secret. Every platform here hands out temporary credentials from an IAM role (see IAM in 10 minutes), but the plumbing differs:

  1. The kubelet mounts a short-lived service-account token (a JWT issued by the cluster) into the pod. The webhook also sets AWS_ROLE_ARN and the token path.
  2. The AWS SDK calls STS AssumeRoleWithWebIdentity with that token.
  3. STS checks the token's signature against the cluster's OIDC issuer and matches the role's trust policy conditions (issuer, system:serviceaccount:kube-system:karpenter).
  4. STS returns temporary credentials for the role. Pod Identity does the same job, but the node agent performs the exchange.
  5. The pod calls AWS as that role. Karpenter, the AWS Load Balancer Controller and ExternalDNS all get their permissions this way.

The Kubernetes side (service accounts, token projection, RBAC) is in Kubernetes Security: service accounts.
