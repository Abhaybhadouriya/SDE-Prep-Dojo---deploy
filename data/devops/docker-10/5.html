Explain Docker's architecture. Why is there a shim?

CLI -> REST over /var/run/docker.sock -> dockerd (API, builds via BuildKit, networks, volumes) -> gRPC (a binary RPC protocol over HTTP/2) -> containerd (images, snapshots, lifecycle) -> containerd-shim-runc-v2 (one per container) -> runc (creates namespaces and cgroups from the OCI config, execs the process, exits). The shim stays as the container's parent, holds its stdio and reports the exit code, so dockerd and containerd can restart or upgrade without killing containers (live-restore).

How to answer

Draw the chain left to right; make runc "disappear" after start. Bridge: shim = non-stop forwarding.

What exactly happens when you run docker run -p 8080:80 nginx? (full walk)

Use the stepper below. How are namespaces and cgroups used, and what changed in cgroup v2?

Namespaces isolate visibility; cgroups account and limit resources. cgroup v2 uses one unified tree at /sys/fs/cgroup where all controllers share the same hierarchy, with files like memory.max, cpu.max, pids.max, io.max, plus PSI pressure files and better memory accounting. v1 had a separate tree per controller (memory.limit_in_bytes, cpu.cfs_quota_us). Docker 29 deprecated v1.

How to answer

"See vs use" for the first half; "one tree, cleaner files, PSI" for v2.

Likely follow-ups
  • Where is a Docker container's cgroup folder on a systemd host?
What is OverlayFS copy-on-write, and what does it cost?

overlay2 merges read-only lower directories (image layers) with a writable upper directory into a merged view. Reads come from the topmost layer that has the file, shared across containers. The first write to a lower file copies the whole file up; deletes create whiteouts. Costs: first-write latency for large files, duplicated disk usage, rename quirks (EXDEV for directories). Write-heavy data goes on volumes.

How to answer

Lower, upper, work, merged; read, write, delete; then the rule "state on volumes".

Likely follow-ups
  • Why does deleting a file in a later layer not shrink the image?
What is the PID 1 problem in containers?

The process that is PID 1 in a PID namespace gets special treatment: the kernel does not apply default actions for signals it has no handler for, so an app that never installed a SIGTERM handler simply ignores docker stop and gets SIGKILLed after the timeout. PID 1 also inherits orphaned processes and must reap them, or zombies accumulate. Fixes: exec-form commands, a SIGTERM handler for graceful shutdown, and a tiny init (--init uses tini; Yelp built dumb-init for this).

How to answer

Two problems: signals and zombies. Then the fixes. Mention graceful shutdown matters for zero-downtime deploys.

Likely follow-ups
  • How long does Kubernetes wait before SIGKILL? (terminationGracePeriodSeconds, 30 s by default.)
A container restarts with exit 137. How do you debug it end to end?

Decode: SIGKILL. Check docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}'. If OOM: compare docker stats or memory.current with memory.max over time, check memory.events and dmesg. Look for runtimes sizing from host RAM (old JVMs; set -XX:MaxRAMPercentage), real leaks (heap dumps), or a too-small limit. If not OOM: who sent the kill? A stop timeout because SIGTERM was ignored, an orchestrator killing it after failed health or liveness checks (Swarm, Kubernetes, or an autoheal helper container; plain Docker never kills a container just because its HEALTHCHECK fails), or an operator.

How to answer

A decision tree: OOM yes or no, then causes on each branch, then prevention (alerts on memory near limit).

Likely follow-ups
  • What does PSI tell you that usage percent does not?
What are containerd, runc and the OCI? Why did Kubernetes drop Docker?

OCI defines the image, runtime and distribution standards. runc is the reference low-level runtime; containerd is a high-level runtime with a CRI plugin. Kubernetes' kubelet talks CRI; Docker never implemented CRI, so Kubernetes maintained an adapter called dockershim. It was deprecated and removed in v1.24 (May 2022). Since Docker builds OCI images, everything kept running on containerd or CRI-O. Docker remains a great developer tool. If you really need dockerd on a node, Mirantis' cri-dockerd adapter still exists (it moved dockershim out of the kubelet), but containerd is the default.

How to answer

Clarify "Kubernetes dropped dockershim, not Docker images". Platform teams (Intuit, NVIDIA-style Kubernetes-heavy interviews have been reported) often ask this.

Likely follow-ups
  • How do you inspect containers on a node without Docker? (crictl ps, crictl logs.)
Is running as root inside a container dangerous? How do you harden a container?

Yes: without a user namespace, container UID 0 is host UID 0, held back only by trimmed capabilities, seccomp and an LSM. Harden in rings: image (minimal base, numeric non-root USER, no secrets), runtime (--cap-drop=ALL, no-new-privileges, read-only root, limits, default seccomp, never --privileged or socket mounts), host (patched runc and kernel, rootless or userns-remap), pipeline (scan, sign, deploy by digest).

How to answer

Ring by ring with one reason each. See the production page for the full checklist.

Why is access to the Docker socket equal to root?

The daemon runs as root and does what the API asks. With the socket you can run docker run --privileged -v /:/host alpine chroot /host and get a root shell on the host. So the docker group is effectively sudo, and mounting the socket into a container gives that container host root. Mounting it read-only does not help; the API still works. CI alternatives: rootless BuildKit, remote builders, Buildah.

How to answer

Show the one-liner, then the policy, then the alternative.

Likely follow-ups
  • What is wrong with Docker-in-Docker? (Needs --privileged.)
How do you pass secrets to a build safely?

RUN --mount=type=secret,id=x exposes a file only for that RUN step via tmpfs; --mount=type=ssh forwards the SSH agent for private git. Never ARG, ENV or COPY-then-delete: layers keep history. Uber's Makisu post describes secrets surviving in layers as a real pain at scale. If a secret leaked into a published image, rotate it immediately; you cannot recall pulled layers.

How to answer

The mechanism, the anti-patterns, and the incident response (rotate).

Why did ufw not block my published container port?

Docker's DNAT runs in nat PREROUTING, so a packet for a published port is rewritten to the container IP and routed through FORWARD; ufw's rules sit on INPUT, which only sees packets for the host itself. Filter in the DOCKER-USER chain (evaluated before Docker's rules), bind published ports to specific addresses (-p 127.0.0.1:...), or do not publish internal services at all.

How to answer

Draw the netfilter path. Your iptables experience shines here.

How do you debug a running container that has no shell (distroless)?

Options: docker debug (attaches a toolbox), a debug container sharing its namespaces (docker run -it --pid=container:app --network=container:app busybox), nsenter --target PID --net --pid from the host to use host tools, docker cp to pull files out, and logs and metrics first. In Kubernetes, kubectl debug adds an ephemeral container to the pod.

How to answer

Show you understand that "entering a container" means joining its namespaces, so any tool can do it.

What do capabilities and seccomp do in Docker?

Capabilities split root's powers. Docker keeps 14 by default (for example CHOWN, NET_BIND_SERVICE, SETUID, KILL, NET_RAW) and drops the rest (SYS_ADMIN, NET_ADMIN, SYS_MODULE, SYS_PTRACE...). seccomp attaches a BPF filter to every syscall; the default profile blocks around 44 risky calls (mount, reboot, kexec_load, bpf, keyctl, ...). --privileged disables both. Best practice: --cap-drop=ALL plus only what is needed, default or tighter seccomp.

How to answer

Bridge: capabilities = privilege levels, seccomp = ACL on the syscall table.

Likely follow-ups
  • How would you build a custom seccomp profile? (Trace the syscalls the app uses, then allowlist.)
Rootless mode vs userns-remap vs a non-root USER?

USER changes only the app's UID; the daemon is still root. userns-remap maps container root to a high unprivileged host UID range, so an escape lands as nobody; the daemon is still root. Rootless runs the daemon itself as a normal user inside a user namespace, so even a daemon compromise gives no root; costs include slower networking (slirp4netns or pasta), no ports below 1024 by default and some limits needing systemd delegation. Netflix has written about adopting user namespaces in its Titus platform.

How to answer

A 3-column comparison: who is root, what it protects, what it costs.

Likely follow-ups
  • Why does userns-remap complicate volumes? (File ownership on the host.)
Name some recent Docker or container runtime vulnerabilities and what they teach.

CVE-2019-5736: a container overwrote the host runc binary via /proc/self/exe and got host root; fixed by runc cloning itself into a sealed memfd. CVE-2024-21626 ("Leaky Vessels", January 2024): a WORKDIR ordering bug leaked a host file descriptor so a malicious image could reach the host filesystem; fixed in runc 1.1.12, alongside three BuildKit CVEs. Lessons: the shared kernel and runtime are the real attack surface, so patch hosts and runtimes, treat untrusted images and Dockerfiles as code execution, and add user namespaces so escapes land unprivileged.

How to answer

Two stories, one sentence each on the mechanism, then the lessons. A Walmart SDE-2 report specifically advised knowing these.

Likely follow-ups
  • How would you roll out a runc patch across 5,000 nodes? (Rolling node drain and upgrade, canary first.)
