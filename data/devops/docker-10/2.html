60-second answers to the most asked questions

Practise these out loud until they flow. Each one is roughly 60 seconds spoken.

1. "What is a container, and how is it different from a VM?"

"A container is a normal Linux process that the kernel isolates. Namespaces give it its own view of process IDs, network interfaces, mounts and hostname, and cgroups cap its memory and CPU. It shares the host kernel. A VM runs a full guest kernel on virtual hardware through a hypervisor. So containers start in milliseconds and pack densely, while VMs give stronger isolation. That is why clouds often run containers inside VMs, and why AWS Lambda uses Firecracker microVMs for multi-tenant code."

2. "Image vs container?"

"An image is a read-only template: an ordered stack of filesystem layers plus a JSON config with the command, environment and user, all addressed by sha256 digests. A container is a running instance of that image: the kernel mounts the layers with OverlayFS, adds a thin writable layer on top and starts the process. It is like a binary versus a process, or a class versus an object. Many containers share one image's layers on disk and in the page cache; each has its own writable layer, which disappears when the container is removed. So anything that must survive goes on a volume."

3. "What happens when you run docker run -p 8080:80 nginx?"

"The CLI sends a REST call (a plain HTTP request such as POST /containers/create) over the Docker socket to dockerd. The name resolves to docker.io/library/nginx:latest; if it is not local, the manifest for my CPU architecture is pulled and only missing layers are downloaded by digest. containerd unpacks them as overlay snapshots and writes an OCI bundle. A shim starts runc, which creates the namespaces and cgroup, mounts the root filesystem, applies capabilities and seccomp, and execs nginx as PID 1, then exits. Docker's network code creates a veth pair, one end as eth0 in the container, the other on the docker0 bridge, and adds an iptables DNAT rule from host port 8080 to the container's port 80. Logs from stdout go to the json-file driver."

4. "Your image is 1.2 GB. How do you shrink it?"

"First I measure with docker history or dive to see which layers are big. Then: a multi-stage build so compilers and dev dependencies stay in the builder stage; a slim or distroless runtime base; a .dockerignore so .git and node_modules stay out; and downloading, installing and cleaning package caches in the same RUN, because a delete in a later layer does not shrink anything. A Go service typically goes from around 800 MB to under 20 MB. The trade-off is debuggability: no shell in distroless, so I plan to use docker debug or ephemeral debug containers."

5. "A container keeps dying with exit code 137. What do you do?"

"137 is 128 plus 9, so it got SIGKILL. I check docker inspect for OOMKilled: true. If yes, the memory cgroup limit was hit and the kernel's OOM killer fired. Common root causes are a runtime that sizes itself from host memory, like an old JVM, a real leak, or a limit that is simply too small. I look at docker stats or the cgroup's memory.current over time, then right-size the limit or set the heap as a percentage of the container limit. If OOMKilled is false, something sent a kill, often docker stop after the 10-second grace period because the app ignored SIGTERM."

6. "Docker vs Kubernetes? And why do we still need Compose?"

"Docker builds images and runs containers on one machine. Kubernetes runs containers across many machines and keeps them in a desired state: it schedules them, restarts them, rolls out new versions, gives them stable service addresses and scales them. Kubernetes does not even use Docker as its runtime anymore; it talks to containerd or CRI-O, and Docker-built images run fine because they are OCI images. Compose is the single-host, developer-friendly way to describe a few services together, like an app, Postgres and Kafka for local testing. I use Compose on my laptop and in CI integration tests, and Kubernetes in production."

7. "How do you secure a container?"

"In rings. Image: minimal base, multi-stage, non-root numeric user, no secrets, pinned and scanned. Runtime: drop all capabilities, no-new-privileges, keep the default seccomp and AppArmor, read-only root, resource limits, never privileged, never the Docker socket. Host: patch runc, containerd and the kernel, because escapes like CVE-2024-21626 live there; use rootless or user-namespace remapping. Pipeline: sign images and deploy by digest with verification at admission. For untrusted code I go to gVisor or Firecracker."

8. "What are containerd, runc and OCI?"

"OCI is the set of open standards for the image format, the runtime bundle and the registry API. runc is the low-level OCI runtime: it reads a config.json, sets up namespaces and cgroups, execs the process and exits. containerd is the high-level runtime that pulls images, manages snapshots and supervises containers through one shim per container. dockerd sits on top for Docker's API, builds, networks and volumes. Kubernetes talks to containerd directly through CRI, which is why dockershim could be removed in v1.24 without breaking anyone's images."
