Production scenario drills

Interviewers love "here is what broke; what do you do?" For each one, read the situation, try your own answer out loud, then compare with the weak and strong versions. The strong answers all follow one shape: gather facts, form a hypothesis, test it, fix the root cause, prevent it next time.

Scenario: the Java service that dies every 20 minutes

A Java service in a container with --memory=1g restarts every 20 minutes with exit code 137. The heap graphs look fine. The host has 64 GB of RAM.

Weak answer: "Increase the memory limit to 4 GB."

Strong answer: "137 is SIGKILL; I would confirm OOMKilled: true. A 1 GB container on a 64 GB host suggests the JVM is sizing from host memory or that non-heap memory (metaspace, thread stacks, direct buffers) is growing. I would check the JVM version and flags (modern JVMs are container-aware; set -XX:MaxRAMPercentage=75), compare memory.current over time with heap usage, and look at native memory tracking. Fix the sizing or the leak, then right-size the limit with headroom, and alert when memory approaches the limit."

Likely follow-ups
  • What would you see in Kubernetes? (Pod restarts, last state OOMKilled.)
  • Why is "just raise the limit" risky? (It hides leaks and reduces packing density.)

Scenario: errors spike during every deploy

Each deploy causes a burst of 502 errors for about 10 seconds. Stopping a container always takes exactly 10 seconds.

Weak answer: "Deploy at night when traffic is low."

Strong answer: "Exactly 10 seconds is docker stop's grace period, so SIGTERM is being ignored and the process is SIGKILLed mid-request. Likely the Dockerfile uses shell-form CMD, so /bin/sh is PID 1 and does not forward signals. Fix: exec-form CMD (or exec in the entrypoint script), a SIGTERM handler that stops accepting connections and drains in-flight requests, --init if it spawns children, and have the load balancer stop sending traffic before the stop (readiness goes false first)."

Likely follow-ups
  • How does Kubernetes order endpoint removal and SIGTERM? (A preStop sleep helps.)

Scenario: the host disk is full again

A Docker host running 30 containers hits 100% disk every few days, and all containers start failing.

Weak answer: "Run docker system prune -a --volumes."

Strong answer: "First measure: docker system df, then du on /var/lib/docker/containers and overlay2. The usual culprit is json-file logs with no rotation, then old images from frequent deploys, build cache and anonymous volumes. Immediate relief: truncate the biggest log safely and prune old images. Permanent fix: local log driver or max-size and max-file in daemon.json, scheduled image prune with an age filter, ship logs off the host, and a disk alert at 80%. I would not prune volumes blindly: since Engine 23 plain docker volume prune only removes anonymous volumes, but docker volume prune -a (or system prune -a --volumes on older engines) can delete a stopped database's named volume."

Likely follow-ups
  • Why does deleting a log file inside the container not free space? (The file is on the host; the process may still hold it open.)

Scenario: "connection refused" to the database

A developer containerized an API. On the laptop it connected to Postgres at localhost:5432. Now, with both in containers, the API logs "connection refused".

Weak answer: "Use --network host for everything."

Strong answer: "Each container has its own network namespace, so localhost is the API container itself. Put both on a user-defined network (Compose does this) and connect to db:5432; Docker's DNS at 127.0.0.11 resolves the name. Also check the database listens on 0.0.0.0 inside its container, that the API retries while the database starts (or use depends_on with service_healthy), and that credentials come from env or secrets, not hard-coded."

Likely follow-ups
  • Why is host networking a bad general fix? (No isolation, port clashes, does not carry over to Kubernetes.)

Scenario: exec format error after a laptop upgrade

After the team moved to Apple Silicon laptops, images pushed from laptops crash on production x86 servers with exec format error.

Weak answer: "Ask everyone to use Intel laptops."

Strong answer: "The laptops build linux/arm64 images. Production pulls the only manifest there is, and the binary cannot run. Root fix: stop pushing from laptops; build in CI with buildx --platform linux/amd64,linux/arm64 to publish an image index, using cross-compilation or native builders for speed. Add a CI check that the index contains the platforms production needs. Bonus: arm64 builds also enable cheaper Graviton nodes."

Likely follow-ups
  • How do you check the architecture of an image? (docker image inspect --format '{{.Architecture}}'.)

Scenario: CI image builds take 15 minutes

Every commit re-installs all dependencies; builds take 15 minutes; developers complain.

Weak answer: "Buy bigger CI machines."

Strong answer: "Ephemeral CI runners start with an empty cache, and the Dockerfile probably copies all source before installing dependencies, so every change invalidates the install layer. Fix the order (manifests first, install, then source), add BuildKit cache mounts for the package manager, and export a remote cache (cache-to: type=registry or type=gha, mode=max). Split slow independent work into parallel stages. Measure before and after per stage."

Likely follow-ups
  • When does a remote cache hurt? (Huge cache exports slower than rebuilding.)

Scenario: Redis exposed to the internet

A security scan finds your Redis container reachable from the internet, although the host's ufw denies port 6379.

Weak answer: "ufw must be broken; reinstall it."

Strong answer: "Contain first: stop publishing the port or bind it to 127.0.0.1, and rotate any data or credentials that may have been exposed. Root cause: -p 6379:6379 binds all interfaces and Docker's DNAT in PREROUTING forwards the traffic, so ufw's INPUT rules never see it. Prevention: internal services are not published at all (containers reach them over a private network), DOCKER-USER rules as a safety net, Redis with auth, a policy check in CI for published ports, and regular external port scans."

Likely follow-ups
  • How would you find every published port on 200 hosts? (docker ps --format '{{.Ports}}' via fleet tooling, or an external scan.)

Scenario: an API key shipped in a public image

Someone notices a cloud API key inside an image layer on a public registry. The Dockerfile copies .env and deletes it two steps later.

Weak answer: "Push a new image without the key and delete the old tag."

Strong answer: "Treat the key as compromised: revoke and rotate it now and check the provider's audit logs for misuse, because anyone could have pulled the layer. Then fix the build: add .env to .dockerignore, pass build-time secrets with --mount=type=secret, inject runtime secrets as files. Delete the image versions from the registry, add a secret scanner (Trivy or similar) as a CI gate, and run a blameless post-mortem."

Likely follow-ups
  • Why did the delete in a later step not help? (Layers are additive.)

Scenario: p99 latency doubles but CPU is only 40%

p99 = the latency that 99% of requests beat, i.e. the slowest 1% (defined on page 08).

A service with --cpus=2 on a 16-core host shows p99 latency doubling at peak, while its average CPU usage graph shows 40% of its limit.

Weak answer: "CPU is fine, so it must be the database."

Strong answer: "Averages hide bursts. With CFS quotas, a multi-threaded app can burn its 200 ms of quota early in each 100 ms period and then sit throttled for the rest. I would check nr_throttled and throttled_usec in cpu.stat (in Kubernetes, the cAdvisor throttling metric). Also check the runtime sees 2 CPUs, not 16, or it spawns too many threads. Fixes: right-size the limit, cap thread pools to the CPU limit, or for latency-critical services consider no CPU limit with a request-based guarantee."

Likely follow-ups
  • What is the trade-off of removing CPU limits? (Noisy-neighbour risk.)

Scenario: CI fails with "toomanyrequests"

At 10 a.m. every day, many CI jobs fail pulling node and postgres base images from Docker Hub.

Weak answer: "Retry the jobs until they pass."

Strong answer: "Docker Hub rate-limits pulls per 6 hours: 100 for anonymous users per IP, 200 for authenticated personal accounts. All runners share one NAT IP, so the busy morning burns through the limit. Short term: authenticate pulls. Long term: a pull-through cache or mirror (ECR, ACR, Harbor, Artifactory), copying base images into our own registry, and pinning by digest so caches hit."

Likely follow-ups
  • How do you keep mirrored base images patched? (Scheduled sync plus rebuild triggers.)
