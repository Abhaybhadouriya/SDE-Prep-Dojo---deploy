Level 3 questions: building, running, networking

Why does changing one line in my Dockerfile rebuild everything after it?

Each instruction's cache key depends on its text, the checksums of copied files, and the parent layer. If one layer changes, every later layer has a new parent, so it misses the cache. Fix the order: copy dependency manifests (package.json, requirements.txt, go.mod) and install dependencies first; copy the frequently changing source last. Add BuildKit cache mounts for package managers and a remote cache in CI.

How to answer

Explain the chain rule, show the before/after order, then mention CI cache backends for extra credit.

  • How do you share cache across CI runners?
What is a multi-stage build and why use it?

A Dockerfile with several FROM stages. You build in a heavy stage (compilers, dev dependencies) and COPY --from=build only the artifact into a small runtime stage. Benefits: much smaller images, fewer CVEs, no build tools for an attacker. --target lets CI build just one stage (a test stage, say), and BuildKit skips stages the target does not need and builds independent stages in parallel.

How to answer

Show a 2-stage Go or Java example in words, give a realistic size result, mention --target.

Likely follow-ups
  • How would you run unit tests inside the build?
Your image is 1.2 GB. How do you make it smaller?

Measure with docker history and dive. Then: multi-stage; slim, distroless or hardened base; .dockerignore; combine download, install and cleanup in one RUN (apt-get install --no-install-recommends ... && rm -rf /var/lib/apt/lists/*); do not ship tests or docs; for compiled languages copy a static binary into scratch or distroless static. Trade-off: less debuggability (no shell).

How to answer

Measure, then fix in order of impact, then the trade-off. Quoting a before/after number from your own project is gold.

  • How do you debug a distroless container?
Why should you not use :latest in production? Tags vs digests?

latest is just the default tag name, not "newest", and every tag is a movable pointer. Two nodes pulling at different times can get different images; rollbacks are ambiguous; you cannot tell what is running. Use immutable tags (git SHA, semver) and deploy by digest (@sha256:...), which is a content hash and cannot change.

How to answer

Reproducibility and rollback are the two words to say.

Likely follow-ups
  • How do you get the digest of what you just pushed?
Alpine vs Debian-slim vs distroless: which base would you pick?

Alpine is tiny but uses musl libc instead of glibc: DNS resolver behaviour differs and many Python wheels must compile from source, which can make builds slower and bigger. Debian slim is glibc, compatible and still small. Distroless has no shell or package manager: smallest attack surface, hardest to debug. For static Go binaries, distroless static or scratch. For Python or Java, slim or distroless language images. Hardened images (Docker Hardened Images, Chainguard) are similar ideas with patch commitments.

How to answer

Pick with a reason, name the musl gotcha, mention debuggability.

Likely follow-ups
  • How do you get CA certificates into a scratch image?
How do two containers on the same host talk to each other?

Put them on the same user-defined bridge network. Docker's embedded DNS server at 127.0.0.11 inside each container resolves container and service names, so the app connects to db:5432. The default bridge network has no name-based DNS (the old --link is deprecated). Compose creates a project network automatically, so service names just work.

How to answer

Name the DNS server address; it proves you have looked inside.

Likely follow-ups
  • Why not use container IPs? (They change on restart.)
Explain -p 8080:80 at the packet level.

Docker adds a DNAT rule in the nat table (the DOCKER chain, reached from PREROUTING for external traffic and OUTPUT for local) that rewrites destination host:8080 to container-IP:80. conntrack remembers the translation so replies are rewritten back. The packet is forwarded through the FORWARD chain (DOCKER-USER first) to docker0 and down the veth into the container's eth0. Outbound traffic from containers is MASQUERADEd. A userland docker-proxy also listens on 8080 for cases NAT does not cover, like localhost hairpin. By default it binds 0.0.0.0 and [::], so the port is public unless you write -p 127.0.0.1:8080:80.

How to answer

Walk the packet hop by hop. This is your home turf; draw it.

Likely follow-ups
  • Why did ufw not block it?
  • What changes with --network host?
bridge vs host vs none vs overlay vs macvlan: when would you use each?

bridge: default, single host, NAT to the outside. host: no network namespace, no port mapping, best performance, no isolation. none: loopback only, for batch jobs that need no network. overlay: multi-host networks (Swarm) using VXLAN on UDP 4789, with about 50 bytes of header overhead (MTU 1450 on a 1500 underlay). macvlan: container gets its own MAC and IP on the physical LAN, useful for legacy apps or network appliances; ipvlan shares the parent MAC when switch ports limit MAC addresses.

How to answer

One line each with a use case. Offer the MTU and VXLAN details; a networking interviewer will dig there.

Likely follow-ups
  • Why can a macvlan container not talk to its own host by default?
The app works on my laptop but in a container it cannot reach the database on localhost. Why?

Inside a container, localhost is the container's own loopback in its own network namespace, not the host and not another container. Connect to the database by its service name on a shared user-defined network (db:5432), or to the host via host.docker.internal on Docker Desktop. A related bug: an app listening on 127.0.0.1 inside the container cannot be reached through a published port; it must listen on 0.0.0.0.

How to answer

Explain network namespaces in one sentence, then give both directions of the bug.

How do restart policies differ?

no (default), on-failure[:N] (only on non-zero exit, up to N times), always (also after daemon restart, even if you stopped it manually before the restart), unless-stopped (like always, but respects a manual stop). Restarts back off, starting at 100 ms and doubling. They only help on one host and need dockerd itself to start at boot; real self-healing across machines is an orchestrator's job.

How to answer

What is a HEALTHCHECK, and how does it relate to depends_on?

A HEALTHCHECK is a command Docker runs inside the container periodically (defaults: every 30 s, 30 s timeout, 3 retries). Status shows as starting, healthy or unhealthy in docker ps. Plain Docker does not restart unhealthy containers by itself, but Compose's depends_on: condition: service_healthy waits for it before starting dependents, which fixes the classic "app starts before Kafka or Postgres is ready" problem. Still add client retries; readiness can change later.

How to answer

Define, give the Compose use, then the "still retry" point. In K8s this becomes readiness and liveness probes.

How do you get logs out of containers in production?

Apps log to stdout/stderr, ideally as structured JSON. The logging driver (json-file or local) stores it on the host with rotation, and a node-level agent (Fluent Bit, Vector) ships it to a central store (Elasticsearch, Loki, a cloud service). Avoid log files inside the container layer. Shopify, an early large Docker user, chose a host-side logger listening to Docker events instead of an agent in every container; in Kubernetes the same idea is a DaemonSet.

How to answer

stdout, driver with rotation, node agent, central store. Mention the default json-file driver does not rotate.

Likely follow-ups
  • How do you correlate logs across services? (Trace IDs.)
How do you limit CPU and memory, and what happens at each limit?

--memory=512m writes memory.max; exceeding it triggers the OOM killer (exit 137, OOMKilled true). --cpus=1.5 writes cpu.max = 150000 100000; exceeding it means throttling until the next 100 ms period, which raises latency but kills nothing. --pids-limit caps processes. Check with docker stats and the cgroup files.

How to answer

The key contrast: memory kills, CPU throttles. Name the files.

An image built on my Mac fails on the server with "exec format error". Fix it.

Apple Silicon builds arm64 images by default; the server is amd64. Build a multi-platform image with docker buildx build --platform linux/amd64,linux/arm64 --push, which produces an image index so each machine pulls its own architecture. QEMU emulation works but is slow; cross-compiling with --platform=$BUILDPLATFORM and TARGETARCH, or native arm64 builders, is faster. Swiggy wrote about needing multi-arch images when moving Kubernetes workloads to AWS Graviton.

How to answer

Diagnose (architecture mismatch), fix (multi-platform index), optimize (native or cross builds).

Likely follow-ups
  • How do you check which platforms an image supports? (docker buildx imagetools inspect.)
What are "Docker namespaces"?

Linux kernel namespaces Docker creates for each container: pid (process IDs), net (interfaces, routes, ports), mnt (mounts), uts (hostname), ipc (shared memory, message queues) and cgroup (cgroup view). The user namespace is only used with userns-remap or rootless mode. They control what a container can see; cgroups control what it can use. docker exec joins them with setns().

How to answer
