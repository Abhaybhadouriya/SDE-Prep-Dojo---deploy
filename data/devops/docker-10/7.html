Level 5 questions: design and deep scenarios

SDE-2+ (deep dive). These are design-style questions. SDE-1 candidates rarely get them; skim the approach boxes and come back after the Level 2-4 blocks feel easy.

How would you build a container from scratch with Linux primitives?

Rootfs (ideally overlay of image layers), cgroup folder with memory, CPU and pids limits, clone() with NEWPID|NEWNS|NEWUTS|NEWIPC|NEWNET|NEWCGROUP (plus NEWUSER for rootless), in the child make mounts private, pivot_root, mount /proc, detach the old root, set hostname; in the parent create a veth pair and move one end into the child's netns, add NAT; drop capabilities, set no-new-privileges, load seccomp last; execve the app. The internals page has a runnable script.

How to answer

Group into see / use / files / ask. Explain why pivot_root beats chroot and why seccomp goes last.

Likely follow-ups
  • How does rootless networking work without root? (slirp4netns or pasta in user space.)
Design the CI/CD pipeline that builds and ships images for 300 microservices (many small services, each deployed on its own).

Triggers: per-service path filters in a monorepo (one git repository holding many services) (or per-repo pipelines). Build: ephemeral runners with rootless BuildKit or a remote builder pool, a registry-backed layer cache, dependency-first Dockerfiles, shared org base images. Quality gates: unit tests in a test stage, SBOM, vulnerability scan failing on fixable criticals, signature and provenance. Registry: one per region with replication, pull-through caches for Docker Hub, lifecycle retention. Deploy: immutable digest promoted dev to staging to prod, progressive rollout, rollback by previous digest. Operations: nightly rescans, automated base-image bumps when a CVE lands, build-time dashboards. Uber's Makisu post shows the pain at about 3,000 services: slow builds, huge images, secrets in layers.

How to answer

Treat it like an HLD: requirements (build time target, security gates), components, scale bottlenecks (cache, registry, rate limits), failure modes. See CI/CD Platform design.

Likely follow-ups
  • A critical CVE hits the base image: how fast can you patch all 300?
  • How do you stop a compromised build from shipping? (Isolated runners, signed provenance, admission checks.)
Design a system that runs untrusted user code (online judge, notebooks). Containers, gVisor or Firecracker?

Flow: API -> queue -> worker pool -> one sandbox per submission -> results store. Isolation: plain runc shares the kernel's full syscall surface with attackers, so use gVisor (syscalls handled by a user-space kernel) or Firecracker or Kata microVMs (hardware virtualization; Firecracker's spec targets at most 5 MiB of VMM overhead per microVM). Add: no network or an egress allowlist, cgroup CPU, memory and pids limits, wall-clock timeouts, read-only base image with a tmpfs workspace, non-root user, seccomp. Latency: a warm pool of pre-booted sandboxes. Scale: autoscale workers on queue depth. AWS Lambda and Fargate run on Firecracker; Fly.io runs customers' OCI images as Firecracker VMs.

How to answer

Start with the threat model ("users are attackers"), choose isolation with the trade-off, then the HLD around it. See Online Judge design.

Likely follow-ups
  • How do you stop a fork bomb? (pids.max.)
  • How do you stop crypto mining? (CPU quota, timeouts, no network.)
Image pulls are slowing down deploys at scale. What do you do?

Measure pull time vs start time. Then: smaller images and shared base layers (pulled once per node), regional registry mirrors, pre-pulling popular images on node start, keeping hot images cached, lazy-pulling snapshotters (stargz, AWS SOCI) that start the container before all bytes arrive, and peer-to-peer distribution (Uber's Kraken, Dragonfly) for huge fleets. Netflix's Titus runs millions of container launches per week, which makes pull time a first-class concern.

How to answer

Measure first, then reduce bytes, then move bytes closer, then avoid waiting for bytes.

Likely follow-ups
  • What breaks with lazy pulling? (First-access latency, registry dependency at runtime.)
You must containerize a legacy app that writes to local disk and expects a fixed IP.

State: identify every write path; mount data directories as volumes; move logs to stdout. Config: externalize to environment or mounted files. Fixed IP: prefer putting a stable name or virtual IP in front (a reverse proxy, a DNS name, or a Kubernetes Service); if the network truly needs an L2 identity, macvlan or ipvlan gives the container its own address on the LAN. Add a health check, graceful SIGTERM handling, and run it as one replica first (it was not designed for many). Migrate gradually: run old and new side by side behind the proxy.

How to answer

Separate "make it work" (volumes, config, network) from "make it cloud-native later" (stateless, replicas).

Likely follow-ups
  • What if two copies of it must never run at once? (Leader election or a singleton with a lock.)
How would you do a zero-downtime deploy with plain Docker on one host?

Put a reverse proxy (nginx, Traefik, HAProxy) in front. Start the new version alongside the old one, wait for its health check, add it to the proxy, drain and remove the old one (stop accepting new connections, finish in-flight requests on SIGTERM, then exit). Keep the old image to roll back. Then say honestly that this is exactly what an orchestrator automates as a rolling update with readiness probes, and that one host is still a single point of failure.

How to answer

Do the manual version briefly, then connect to Kubernetes rolling updates (maxSurge, maxUnavailable).

Likely follow-ups
  • What about database schema changes during the deploy? (Expand and contract migrations.)
"Containers isolate namespaces, not performance." What does that mean?

cgroups cap CPU time, memory and I/O, but many resources are still shared: the last-level CPU cache, memory bandwidth, NIC queues, kernel locks and the network stack. A noisy neighbour can raise others' latency without breaking any limit. Netflix reported in 2026 that even with tuned cgroups and traffic shaping, a container flooding small packets could starve neighbours, so for sensitive workloads they moved to one task per right-sized instance. Mitigations: CPU pinning (cpuset), dedicated nodes, network QoS, or VM-level isolation.

How to answer

Name what cgroups do and do not divide; give the Netflix story; give mitigations with costs.

Likely follow-ups
  • How would you detect a noisy neighbour? (Per-host latency vs per-container CPU, PSI, cache-miss counters.)
How does a Kubernetes pod share one IP between containers, and how would you mimic that in Docker?

Each pod has a tiny "pause" container that creates and holds the network namespace (and optionally IPC). The app containers join it, so they share one IP and port space and talk over localhost. In Docker: docker run -d --name holder pause-image, then docker run --network container:holder app and --network container:holder sidecar. This is the basis of the sidecar pattern.

How to answer

Explain with namespaces; show the Docker flag; connect to sidecars and service meshes. See Pods.

Likely follow-ups
  • Why is the pause container needed at all? (So the namespace outlives app container restarts.)
