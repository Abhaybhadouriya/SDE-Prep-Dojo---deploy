Turn your systems work into SDE stories (STAR)

Behavioural and project rounds want STAR answers: Situation, Task, Action, Result. Your kernel and networking work is full of good stories; you only need to translate the words. Here are three worked translations and a script for "you have no web experience". Replace the details with your real ones, and never invent numbers.

Story 1: a daemon that ignored SIGTERM during ISSU -> graceful container shutdown

Situation: during an in-service software upgrade (ISSU), a line-card process ignored SIGTERM, so the upgrade waited for a watchdog and then hard-killed it, which dropped sessions. Task: make the upgrade clean.

Action: "I found the process installed no SIGTERM handler and was started through a wrapper shell, so the signal never reached it. I made it the direct child, added a handler that stopped taking new work, drained in-flight work, and exited inside the grace window." Result: "Upgrades stopped dropping sessions." The bridge to say: "That is exactly the container PID 1 problem: shell-form CMD hides SIGTERM, docker stop waits 10 seconds then sends SIGKILL (exit 137). I would use exec form, a SIGTERM handler that drains, --init if the app spawns children, and a Kubernetes preStop plus terminationGracePeriodSeconds that fit the drain time."

Story 2: buffer exhaustion on a box -> OOM and exit 137 debugging

Situation: a router's packet-buffer pool ran out under a traffic burst and a process was killed. Task: find whether it was a leak or a sizing problem.

Action: "I graphed pool usage over time against the configured limit, separated steady growth (a leak) from sudden peaks (sizing), and fixed the allocation path that never freed on an error branch." Result: "No more kills under the same burst." The bridge: "In containers I debug the same way: State.OOMKilled in docker inspect, memory.current against memory.max over time, memory.events, then decide leak versus limit too small versus a runtime sizing itself from host RAM."

Story 3: NAT and VRF work -> explaining -p and DOCKER-USER

Situation: a management service in its own VRF had to be reachable from the out-of-band network only. Task: expose it safely.

Action: "I added a DNAT rule from the management address to the service. I filtered on the original destination before the DNAT, because after DNAT the destination address and port had already been rewritten, so a rule keyed on the public address never matched. The source address is not touched by DNAT, so source filters work on either side." Result: "Only the out-of-band network could reach it." The bridge: "That is exactly how docker run -p works: a DNAT rule in the nat table's DOCKER chain. It is also why ufw rules do not protect published ports (DNAT happens before the INPUT chain), and why your own filters belong in the DOCKER-USER chain, or you bind to 127.0.0.1. DOCKER-USER sees packets after DNAT, so to match the published port I would use -m conntrack --ctorigdstport 8080, not --dport 8080."
