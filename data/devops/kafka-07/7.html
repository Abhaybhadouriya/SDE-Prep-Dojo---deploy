Tiered storage: a hot shelf and a cheap warehouse

deep dive

Stop here for SDE-1? Segments, the sparse index, the five reasons Kafka is fast, retention and compaction are what SDE-1 rounds ask. Tiered storage is SDE-2 / deep dive: useful when the interviewer asks "how would you keep 90 days of data cheaply?"

Keeping months of data on broker disks is expensive, and it makes brokers "heavy": replacing a failed broker means copying all its data from replicas, which can take hours. Tiered storage (KIP-405, production ready since Kafka 3.9) splits the log into two tiers:

  • How: enable remote.log.storage.system.enable=true on brokers and remote.storage.enable=true per topic. local.retention.ms / local.retention.bytes limit the local tail; retention.ms stays the total retention.
  • Plugin: the broker talks to remote storage through a RemoteStorageManager interface. Apache Kafka ships the interface and a topic-based metadata manager, not an S3 implementation; you plug one in (open-source and vendor plugins exist).
  • Benefits: cheap long retention (replay months of data), much faster broker replacement and partition reassignment (only the local tail moves), and old-data reads stop polluting the page cache of hot brokers.
  • Limits: compacted topics are not supported; remote reads are slower; the plugin becomes part of your durability story. Recent releases keep improving it (4.3 added follower fetch from a tiered offset, 4.4 added delayed upload), and 4.3.2 fixed two possible data-loss bugs in tiered storage, so stay on patch releases and read the tiered storage ops page for the current limitations.
# broker (server.properties)
remote.log.storage.system.enable=true
# your plugin class (Kafka ships no S3 implementation)
remote.log.storage.manager.class.name=com.example.S3RemoteStorageManager
remote.log.storage.manager.class.path=/opt/kafka/plugins/tiered/*
# topic
remote.log.metadata.manager.listener.name=PLAINTEXT
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic clickstream \
  --partitions 12 --replication-factor 3 \
  --config remote.storage.enable=true \
  --config local.retention.ms=86400000 \
  --config retention.ms=7776000000

The S3 class name above is a placeholder for whichever plugin you install. This idea has been pushed further by "diskless" Kafka-compatible systems that keep almost everything in object storage (for example AutoMQ, and Pinterest's MemQ for some pipelines), trading latency for cost. That is a good point to raise in Kafka vs others discussions.
