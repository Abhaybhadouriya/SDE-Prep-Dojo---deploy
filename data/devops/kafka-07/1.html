What a partition looks like on disk

must know

Every broker has one or more data directories, set by log.dirs. Inside, every partition the broker holds (leader or follower) gets its own folder named <topic>-<partition>, for example orders-0. Inside that folder are the segment files. The file name is the base offset of the first record in that segment, padded with zeros to 20 digits so files sort correctly with plain ls.

Three files make up each segment:

  1. .log The records themselves, stored in record batches exactly as the producer sent them (still compressed, if the producer compressed them).
  2. .index A sparse map from offset to byte position inside the .log file. "Sparse" means it does not have an entry for every record, only one every few kilobytes.
  3. .timeindex A sparse map from timestamp to offset. It answers "where does 10:00 this morning start?" and drives time-based retention.

A segment is rolled (closed, and a new one started) when it reaches segment.bytes (default 1 GiB) or gets older than segment.ms (default 7 days), whichever comes first. You can see the files on any broker. With the official apache/kafka Docker image the data directory is under /tmp by default:

$ docker exec -it broker ls -l /tmp/kraft-combined-logs/orders-0/
-rw-r--r-- 1 appuser appuser 10485760 Nov 23 10:02 00000000000000000000.index
-rw-r--r-- 1 appuser appuser     4189 Nov 23 10:02 00000000000000000000.log
-rw-r--r-- 1 appuser appuser 10485756 Nov 23 10:02 00000000000000000000.timeindex
-rw-r--r-- 1 appuser appuser        8 Nov 23 10:01 leader-epoch-checkpoint
-rw-r--r-- 1 appuser appuser       43 Nov 23 10:01 partition.metadata

Notice the index files are already 10 MiB while the log is tiny. Kafka pre-allocates the active segment's index files (segment.index.bytes, default 10 MiB) and memory-maps them. When the segment is closed, the index files are trimmed to their real size.

Try it: du -sh /tmp/kraft-combined-logs/* shows per-partition disk use. This is often the fastest way to find which topic is eating a full disk at 3 a.m.

What is inside the .log file: record batches

Kafka does not store "one message, one write". The producer groups records into a record batch, and the batch is the unit that travels over the network, gets written to the log, is replicated and is sent to consumers. A batch (format version 2, used by all modern clients) has a fixed 61-byte header followed by the records.

Two things to notice. First, the broker does not unpack and re-pack batches on the normal path: the bytes the producer sent are the bytes on disk and the bytes the consumer receives. Second, compression is applied to the whole batch, so bigger batches compress better. This "same format on the wire and on disk" design is one of the quiet secrets of Kafka's speed, as we will see.
