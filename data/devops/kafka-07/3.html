Why Kafka is fast: the five secrets

must know

Interviewers ask "Why is Kafka fast?" all the time. The weak answer is "because it is distributed". The strong answer names five concrete mechanisms, and you can explain each one from first principles.

1Sequential appends, no random seeks
2OS page cache instead of a JVM cache
3Zero-copy sendfile() to the socket
4Batching + compression end to end
5Same binary format on wire and disk

Secret 1: sequential I/O

A partition is only ever appended to at the end. Reads by consumers are mostly sequential too: a consumer reads offset 100, then 101, then 102. Disks of every kind (spinning disks especially, but SSDs as well) are much better at long sequential transfers than at scattered small ones, and the kernel's read-ahead logic loves sequential patterns. A traditional database, in contrast, updates B-tree pages in place all over the file.

LinkedIn's classic 2014 benchmark, written up by Jay Kreps, showed a three-machine cluster of ordinary hardware taking about two million writes per second, and the explanation was exactly this: linear disk access plus batching. Treat that as a historical data point, not a promise for your hardware.

Secret 2: trust the page cache

Many systems keep their own in-process cache of hot data. Kafka mostly does not. The official design doc argues the opposite: write to the filesystem and let the operating system's page cache (the kernel's cache of file pages in free RAM) do the caching. Reasons:

  • Objects on the JVM heap cost far more memory than the raw bytes, and a big heap means long garbage-collection pauses.
  • The page cache survives a broker process restart. A JVM cache would start cold.
  • The kernel already does read-ahead, write-back and LRU-style eviction, tuned over decades.
  • Consumers that keep up with producers ("tail readers") read data that was written seconds ago, which is still in the page cache. So most reads never touch the disk at all.

That is why Kafka brokers typically run with a modest JVM heap (a few gigabytes) and leave most of the machine's RAM free for the page cache. When someone says "my broker has 64 GB of RAM but the JVM only uses 6", that is by design.

From your world

write() on a Kafka log returns once the bytes are in the page cache and marked dirty. The kernel flushes them later with its normal write-back threads (governed by vm.dirty_background_ratio, vm.dirty_ratio and friends). Kafka does not call fsync() per message by default. Durability comes from replication to other brokers (see Replication & ISR), like RAID-1 across machines instead of waiting on one disk.

Where the analogy breaks: if all replicas lose power at the same instant before write-back, unflushed data is lost. That is why replicas go in different racks or availability zones. If you truly need fsync, flush.messages / flush.ms exist per topic, at a big throughput cost.

Secret 3: zero-copy with sendfile()

This is the one you, as a kernel person, will enjoy most. It gets its own section below.

Secret 4: batching and compression everywhere

The producer waits up to linger.ms (default 5 ms since Kafka 4.0, it was 0 before) or until batch.size (default 16 KiB) fills, then sends one batch. The broker appends the batch with one write. The follower fetches many batches in one request. The consumer receives many batches per fetch. Each network round trip and each system call is shared by hundreds of records. With compression.type=lz4 or zstd, the batch is compressed once by the producer, stored compressed and decompressed only by the consumer. The broker spends no CPU on it in the common case. See Producers for the tuning knobs.

Secret 5: one binary format and a "dumb" broker

Because the log format and the network format are the same, the broker can pass bytes straight from the file to the socket. It also keeps almost no per-message state: it does not track which consumer read which record (consumers track their own offsets), and it does not delete records on acknowledgement. Compare a classic queue that must update per-message state on every ack. Less bookkeeping per message means more messages per second.

Say this: "Kafka is fast because it turns everything into large sequential I/O: producers batch, the broker appends batches to a log in the page cache without fsync, durability comes from replication, and consumers are served with sendfile() straight from the page cache to the socket. The broker never parses or re-encodes records on the hot path."
