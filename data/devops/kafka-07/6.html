Log compaction: keep the latest value per key

must know

Some topics are not "a history of events" but "the current state of things": a user's latest address, a product's latest price, a consumer group's latest committed offset. For those, deleting by age is wrong (the newest value of a key that has not changed in a month would vanish). Instead you set cleanup.policy=compact, and Kafka's log cleaner keeps at least the latest value for every key and throws away older values for the same key.

How the log cleaner works

  1. Clean head and dirty tail. The cleaner tracks a "cleaner point". Records before it were already compacted (the clean part); records after it are new (the dirty part). The active segment is never cleaned.
  2. When it runs. A partition becomes eligible when the dirty part is at least min.cleanable.dirty.ratio (default 0.5) of the log. min.compaction.lag.ms can force records to stay uncompacted for a while; max.compaction.lag.ms forces compaction even if the ratio is not reached.
  3. Build an offset map. The cleaner scans the dirty part and builds an in-memory map of key hash to latest offset.
  4. Recopy. It rewrites the segments, keeping a record only if it is the latest for its key (or newer than the map), then atomically swaps the new segment files in.

Important properties: offsets never change (survivors keep their original offsets, so there are gaps), order is preserved, and a consumer that keeps up sees every update anyway; compaction only affects readers who come later and start from the beginning.

From your world

A compacted topic is a routing table (RIB) written as a log. Each record is "prefix (key) now points to next hop (value)". Only the latest route per prefix matters, and a withdraw is a tombstone. A new router joining can replay the compacted log and end up with the full current table, without replaying years of flaps. It is also like an ARP or MAC table: latest entry per key wins.

Where the analogy breaks: compaction is lazy and background. Between cleaner runs, old values for a key are still in the log, so a reader may see several versions before the newest one.

Where compaction is used for real

  • __consumer_offsets: the internal topic (50 partitions by default) where consumer groups commit offsets. Key = (group, topic, partition), value = offset. Only the latest matters. See Consumers & Consumer Groups.
  • Kafka Streams changelogs that back state stores and KTables (see Connect & Streams).
  • CDC topics: a Debezium topic keyed by primary key can be compacted to act like a replicated copy of the table.
  • Kafka Connect and Schema Registry store their own config and offsets in compacted topics.
# Create a compacted topic for "latest price per product"
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic product-prices --partitions 6 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.1 \
  --config segment.ms=600000 \
  --config delete.retention.ms=86400000

# Write keyed records (key:value)
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic product-prices \
  --reader-property parse.key=true --reader-property key.separator=:
> sku-1:99
> sku-2:250
> sku-1:89

# Check the topic config
kafka-configs.sh --bootstrap-server localhost:9092 --describe \
  --entity-type topics --entity-name product-prices
Dynamic configs for topic product-prices are:
  cleanup.policy=compact sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:cleanup.policy=compact, DEFAULT_CONFIG:log.cleanup.policy=delete}
  delete.retention.ms=86400000 sensitive=false synonyms={...}
  min.cleanable.dirty.ratio=0.1 sensitive=false synonyms={...}
  segment.ms=600000 sensitive=false synonyms={...}

The small segment.ms and low dirty ratio are only for a lab, so you can watch compaction happen within minutes. In production, very small segments mean many files and extra cleaner work.

Both at once: cleanup.policy=compact,delete compacts and deletes segments older than retention. Useful for "latest value per key, but forget keys untouched for 30 days".

Keys are required. A compacted topic rejects records with a null key. And compaction is not a database index: you still cannot ask Kafka "what is the value of key K?" directly. You read the topic into a local table (which is exactly what a KTable does).
