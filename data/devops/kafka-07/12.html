Quick quiz

The file 00000000000000005000.log tells you...

  1. It is the 5000th segment of the partition
  2. It is 5000 bytes long
  3. Its first record has offset 5000
  4. It was created at timestamp 5000
Segment files are named after their base offset, the offset of the first record they contain.

Why is Kafka's .index file sparse?

  1. To save CPU during compression
  2. So it stays small enough to keep in memory; a short forward scan finishes the lookup
  3. Because offsets are random
  4. Because the index is rebuilt on every read
An entry roughly every 4 KiB of log keeps the index tiny and mmapped. The broker lands just before the target and scans forward.

With sendfile(), which copies remain when serving a tail consumer on a NIC with scatter-gather DMA?

  1. Only DMA copies; the CPU copies nothing
  2. Two CPU copies through user space
  3. One CPU copy into the JVM heap
  4. None at all, not even DMA
Data goes page cache to NIC by DMA; the socket buffer only receives descriptors. If the data was cold, there is also a DMA from disk into the page cache.

Which situation stops Kafka from using zero-copy?

  1. Using keys on records
  2. Using lz4 compression
  3. A replication factor of 3
  4. A TLS-encrypted listener
Encryption happens in user space in the JVM, so the bytes must leave the kernel. Compression does not break it, because the broker sends the compressed batch as-is.

A topic has retention.ms = 7 days but you still see 10-day-old records. Most likely reason?

  1. The cleaner thread crashed
  2. Those records are in the active segment, which is never deleted until it rolls
  3. Retention is measured in hours
  4. Consumers have not read them yet
Retention deletes whole closed segments. A low-traffic topic's active segment can hold old records until it rolls (segment.ms or segment.bytes).

On a compacted topic, a record with key user-7 and a null value means...

  1. A corrupt record that the broker will reject
  2. Reset the consumer offset for user-7
  3. Delete user-7: a tombstone, removed itself after delete.retention.ms
  4. Nothing; null values are ignored
That is a tombstone. Earlier values for the key are cleaned, and the tombstone survives long enough for consumers to see it.

What gives Kafka durability for acknowledged writes by default?

  1. Copies on multiple brokers (replication), not fsync on each write
  2. An fsync after every record
  3. A battery-backed RAID controller
  4. The JVM heap
Kafka relies on replication to in-sync replicas. fsync is left to the OS write-back unless you set flush.*.

Which is NOT a benefit of tiered storage?

  1. Cheaper long retention
  2. Faster broker replacement
  3. Old reads stop polluting hot page cache
  4. Lower latency for consumers reading very old data
Reading old data from object storage is slower than local disk. The benefits are cost and operability.
