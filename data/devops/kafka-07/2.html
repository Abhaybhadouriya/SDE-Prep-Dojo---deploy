Finding offset 1368: the sparse index

good to know

When a consumer says "give me records from offset 1368", the broker must find the right byte in the right file quickly, without scanning gigabytes. It does it in two binary searches and one short scan. Click Next or Play.

  1. Request arrives. A consumer (or a follower replica) asks for records starting at offset 1368.
  2. Pick the segment. The broker keeps all segments of the partition in a sorted map keyed by base offset. A floor lookup picks segment 1000.
  3. Search the index. 1368 - 1000 = relative offset 368. A binary search over the memory-mapped .index finds the largest entry at or below 368: relative offset 351 at byte position 12340.
  4. Short scan. The broker reads the .log forward from byte 12340, skipping whole batches by their length field, until it reaches the batch that contains offset 1368.
  5. Done. From here the broker can hand this file region to the kernel to send (zero-copy, below). The index is tiny, so it stays hot in memory.

Why sparse? An entry is added only about every index.interval.bytes (default 4096 bytes of log). Each .index entry is 8 bytes (a 4-byte relative offset plus a 4-byte file position), and each .timeindex entry is 12 bytes (8-byte timestamp plus 4-byte relative offset). Storing offsets relative to the segment's base offset is why 4 bytes are enough. A 1 GiB segment therefore needs only a couple of megabytes of index, which easily stays in the page cache.

From your world

This is the same trade-off as a multi-level page table or a sparse FIB lookup: do not store an entry for every byte, store enough coarse entries to land close, then walk a short distance. The .index file is mmap()ed, so a lookup is a binary search over memory that the kernel pages in on demand.

Where the analogy breaks: a page table must be exact for every page. Kafka's index only needs to land at or before the target, because the log can always be scanned forward.

The .timeindex works the same way for time. That is what powers commands like "reset my consumer group to 2 hours ago" (kafka-consumer-groups.sh --reset-offsets --to-datetime) and the consumer API offsetsForTimes(). It is a lovely tool for replaying data after a bug, as the failure drills page shows.
