Zero-copy: read()/write() vs sendfile()

good to know

Imagine a broker serving a consumer the naive way: read a chunk of the log file into a user-space buffer, then write that buffer to the consumer's socket. Walk through what the hardware and kernel actually do. Click through both paths.

  1. read() step 1. The broker calls read(). That is a switch into the kernel. If the page is not cached, the disk controller DMAs it into the page cache.
  2. read() step 2. The kernel copies the bytes from the page cache into the broker's user-space buffer with the CPU, then returns to user space (second switch).
  3. write() step 3. The broker calls write() on the socket (third switch). The CPU copies the same bytes again, from the user buffer into the kernel socket buffer.
  4. write() step 4. The NIC DMAs from the socket buffer to the wire and write() returns (fourth switch). Two pointless CPU copies through user space, polluting the CPU caches, and Kafka never even looked at the bytes.
  5. sendfile(). Kafka instead calls Java's FileChannel.transferTo(), which on Linux becomes sendfile(). One system call says "move these bytes of this file to that socket".
  6. Result. The bytes go page cache to NIC inside the kernel. With a NIC that supports scatter-gather DMA, the socket buffer only gets descriptors pointing at the page-cache pages, so no CPU copy is left at all. Hot data comes straight from RAM; the disk is not touched.

Now multiply this by fan-out. If five consumer groups read the same topic, the data is read from disk at most once into the page cache, then sendfile()d five times. The design doc makes exactly this point: one copy in the cache serves every consumer.

/* Naive copy loop: 2 CPU copies + 4 mode switches per chunk */
char buf[65536];
ssize_t n;
while ((n = read(file_fd, buf, sizeof buf)) > 0)
    write(sock_fd, buf, n);

/* Zero-copy: the kernel moves page-cache pages to the socket */
off_t off = segment_pos;              /* from the .index lookup   */
size_t left = bytes_to_send;
while (left > 0) {
    ssize_t sent = sendfile(sock_fd, file_fd, &off, left);
    if (sent <= 0) break;             /* EAGAIN on a full socket  */
    left -= sent;
}
// Simplified from the idea in Kafka's FileRecords / network layer.
// FileChannel.transferTo() maps to sendfile(2) on Linux.
try (FileChannel log = FileChannel.open(segmentPath, StandardOpenOption.READ)) {
    long position = 12340;     // byte position found via the .index file
    long count    = 1_048_576; // e.g. max.partition.fetch.bytes
    long sent = log.transferTo(position, count, socketChannel);
}

Run a plaintext consumer against a broker while tracing. Arguments are (socket_fd, file_fd, offset, count). Your fd numbers and sizes will differ; the point is seeing sendfile calls instead of read/write pairs.

From your world

This is the same family of tricks as splice(), NIC scatter-gather and DMA rings that avoid touching packet payloads in a fast path: move descriptors, not bytes. Kafka is effectively a file server whose hot path is a sequence of sendfile() calls, plus a small amount of protocol framing around them.

Where the analogy breaks: it only works if nobody needs to transform the bytes. Encryption is a transform.

When zero-copy does not happen

SituationWhyEffect
TLS / SSL listenerJava's TLS encrypts in user space, so bytes must come up into the JVM to be encrypted. Stock Kafka does not use kernel TLS (kTLS).Extra CPU per byte. Plan more broker CPU when you turn on TLS, and measure.
Cold reads (a consumer far behind)The pages are not in the page cache, so the kernel must read from disk first.Disk reads, and those pages can push out hot pages that tail readers need ("cache pollution").
Format conversionVery old clients that need an older message format force the broker to rewrite batches. Kafka 4.x removed the oldest protocol versions, so this is mostly history now.CPU and memory cost per fetch.
Producer writessendfile is for the read path. Writes still arrive on a socket and are appended with normal file writes.Writes are fast because they are sequential and batched, not because of zero-copy.

Common trap: saying "Kafka writes with zero-copy". Zero-copy (sendfile) is the consumer and follower read path. The write path's speed comes from sequential appends, batching and the page cache.
