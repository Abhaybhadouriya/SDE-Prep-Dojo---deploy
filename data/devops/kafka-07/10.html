Interview questions

Why is Kafka so fast even though it writes everything to disk?

Because it uses the disk in the one way disks are good at, and it avoids work on the hot path. Producers batch and compress records. The broker appends each batch to the end of a partition log, so all writes are sequential, and it writes into the OS page cache without fsync; durability comes from replication. Tail consumers read data that is still in the page cache, and the broker serves it with sendfile(), so bytes go from page cache to NIC without being copied into the JVM. The on-disk format is the wire format, so the broker never re-encodes records. Finally, partitions spread the load over many disks and brokers.

How to answer

List the five mechanisms in order (sequential I/O, page cache, zero-copy, batching/compression, simple broker), give one sentence each, then volunteer a caveat (TLS breaks zero-copy; cold reads hit disk). The caveat is what separates you from candidates who memorized a blog post.

Likely follow-ups
  • Explain the copies in read/write vs sendfile. (4 copies and 4 switches vs 2 DMA copies and 2 switches.)
  • Does Kafka fsync? (Not per message by default; replication provides durability.)
  • What happens to throughput with TLS? (CPU goes up; zero-copy is lost.)
How does Kafka store a partition on disk, and how does it find a given offset?

A partition is a directory of segment files. Each segment has a .log with record batches, a sparse .index mapping relative offset to byte position, and a .timeindex mapping timestamp to offset. File names are the segment's base offset. Only the newest segment is written. To find offset N, the broker floor-searches the segment list for the largest base offset at or below N, binary-searches that segment's memory-mapped index for the closest entry at or below N, then scans the log forward a few kilobytes.

How to answer

Draw the folder with three segments, then do the lookup with a concrete number. Mention "sparse, every 4 KiB" and "relative offsets fit in 4 bytes" to show depth.

Likely follow-ups
  • Why sparse and not dense? (Small enough to stay in memory; scanning a few KiB is cheap.)
  • How does "reset offsets to yesterday 10:00" work? (The time index.)
What is log compaction, when would you use it, and what are tombstones?

Compaction is a cleanup policy that keeps at least the latest record per key instead of deleting by age. It turns a topic into a durable changelog of current state: user profiles, prices, CDC tables, Kafka Streams state, and Kafka's own __consumer_offsets. A tombstone is a record with a key and a null value; it tells the cleaner and every consumer that the key is deleted. Tombstones are kept for delete.retention.ms (default 1 day) so slow consumers see them, then removed. Offsets are never renumbered, and order of the survivors is kept.

How to answer

Contrast with delete retention first, give two real uses, then explain tombstones. A great extra: "a new service can bootstrap its full state by reading the compacted topic from offset 0".

Likely follow-ups
  • Is the latest value available instantly? (No; compaction is lazy, older versions linger.)
  • Can you use compaction with tiered storage? (Not currently supported.)
  • What if you need GDPR deletion? (Tombstone the key, plus short segment.ms and max.compaction.lag.ms.)
A consumer that is three days behind slows down every other consumer on the cluster. Why, and how do you fix it?

The lagging consumer reads old segments that are no longer in the page cache, so the broker does real disk reads. Those reads also pull old pages into the cache, evicting the recent pages that tail consumers and followers rely on, so their reads start hitting disk too and latency rises for everyone. Fixes: throttle the catch-up consumer (client quotas), give the backfill its own time window, move long-retention data to tiered storage so old reads come from object storage, or serve replays from a separate cluster or the data lake. Also check that broker RAM is going to page cache, not an oversized heap.

How to answer

Name the mechanism (cache pollution), prove it with metrics (disk read throughput up, fetch latency p99 up, page cache hit ratio down), then give fixes from cheapest to biggest.

Likely follow-ups
  • How would you measure page cache hit ratio? (Disk read bytes vs bytes out; tools like cachestat from bcc.)
  • What are Kafka client quotas?
Your team wants to keep 1 year of clickstream data in Kafka. What do you propose?

First ask why: replay for reprocessing, audit, or ML features? If replay, tiered storage is the natural fit: keep a short local tail (say a day) for producers and live consumers, and offload closed segments to object storage with retention.ms set to a year. Brokers stay light, so replacing one is fast. Costs: remote reads are slower, you need a trusted storage plugin, and compacted topics cannot use it. Alternative: keep a week in Kafka and sink everything to a data lake (S3 with Iceberg or Parquet) for long-term queries, which is often cheaper and easier to query with SQL.

How to answer

Clarify the use case, give a primary design with numbers you derive (bytes per event times events per day times 365 times replication), then an alternative and the trade-off between them.

Likely follow-ups
  • How does tiered storage change broker recovery time?
  • Who uploads segments, leader or followers? (The leader copies closed segments.)
Is Kafka a queue? When I read a message, is it deleted?

No. A consumer reading a record does not change the log at all; it only moves its own offset. Records are removed only by retention (time or size, whole segments) or compaction (older values per key). That is why many consumer groups can read the same data independently and why you can replay. Since Kafka 4.2, share groups add queue-like consumption (per-record acknowledgement), but even there the log itself is still governed by retention.

How to answer

Say "log, not queue" in the first sentence, then the consequence (replay, fan-out), then the nuance (share groups).

Likely follow-ups
  • Then how does Kafka know what each consumer has read? (Committed offsets in __consumer_offsets.)

Scenario: a broker disk is 95% full at 2 a.m.

Alerts say one broker's data volume is almost full. Producers have not failed yet. What do you do?

Weak answer: "Delete some old .log files by hand to free space."

Strong answer: "Never delete segment files by hand; the broker's in-memory segment map and indexes would disagree with the disk. First find what is big with kafka-log-dirs.sh or du per partition. If one topic exploded (a runaway producer, a debug topic with infinite retention), lower that topic's retention.ms or retention.bytes dynamically with kafka-configs.sh; the cleaner deletes whole segments within the next check interval. If it is skew (this broker holds more partitions), reassign partitions to other brokers. Longer term: disk alerts at 70%, retention by size as a safety net, tiered storage, and capacity planning."

Likely follow-ups
  • What happens if the disk actually fills? (The broker marks that log dir offline; partitions on it move leadership elsewhere if replicas exist.)

60-second answer: "Why is Kafka fast?"

"Kafka treats each partition as an append-only log, so writes are sequential, which is the fastest way to use any disk. Producers batch and compress records, and the broker stores the batches as-is in the OS page cache instead of a JVM cache, so it does very little work per message and does not fsync each write; replication gives durability. Consumers that are caught up read from the page cache, and the broker uses sendfile() to push bytes from the page cache to the socket without copying them through user space. Lookups are cheap because each segment has a small sparse index. The two caveats I would mention are that TLS removes the zero-copy benefit and that consumers reading very old data cause disk reads, which is where tiered storage helps."
