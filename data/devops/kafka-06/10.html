Common mistakes and gotchas

You might confuse these:

  • Idempotent producer vs idempotent consumer. The idempotent producer is a Kafka feature (enable.idempotence): the broker drops a retried batch it already wrote. An idempotent consumer is something you build: processing the same record twice has the same effect as once (upsert by key, dedup table). You usually need both.
  • Exactly-once vs "effectively once". Kafka's exactly-once means each record's effect lands once inside Kafka (read-process-write). The work may physically run twice after a crash; the duplicate output is aborted. Outside Kafka, "effectively once" = at-least-once delivery + an idempotent sink. People use the two phrases loosely; say which one you mean.
  • LSO vs high watermark. The high watermark (HW) is the end of replicated data; read_uncommitted reads up to it. The last stable offset (LSO) is the first offset of a still-open transaction, always at or before the HW; read_committed reads up to it. On a topic with no open transactions they are the same.
  • Transactions on the producer, default isolation on the consumer. isolation.level defaults to read_uncommitted. Without switching it, consumers read aborted records and the whole effort is wasted.
  • Believing EOS covers the database or the email. It covers Kafka-to-Kafka only. External side effects need idempotency keys, upserts, dedup tables, or the outbox.
  • Auto-commit with async processing. Handing records to a thread pool while auto-commit is on commits offsets for work that has not finished: a crash loses them.
  • Random or per-start transactional.id (for example a UUID at boot). Then a restarted instance cannot fence its zombie, and the old open transaction blocks readers until it times out. Use a stable id per logical instance (for example the StatefulSet pod name app-0, app-1 on Kubernetes - see Kubernetes).
  • Sharing one transactional.id between two live instances. They fence each other in a loop.
  • Committing one transaction per record. Correct but slow; batch records per transaction.
  • Long transactions. Every second a transaction stays open is a second of latency for read_committed consumers. Keep processing inside a transaction short.
  • Counting messages by subtracting offsets. Control markers and aborted records make offsets non-contiguous.
  • Retrying "by hand" after a send error by calling send() again in application code. That creates a new record with a new sequence number - idempotence cannot catch it. Let the client retry; handle the final failure in the callback.
  • Ignoring the send callback. send() is asynchronous. If you never check the future or callback, a record that failed after delivery.timeout.ms is lost silently - "at least once" becomes "at most once".
  • Assuming idempotence survives a restart. It does not: a new process gets a new PID. Only transactional.id gives continuity.
