Interview questions

Company chips mean "commonly reported at", not "always asked at". For the full bank see Kafka Interview Questions.

Explain at-most-once, at-least-once and exactly-once in Kafka.

They describe how many times a message's effect can happen when something fails. At-most-once may lose but never duplicates: the consumer commits the offset before processing, or the producer does not retry. At-least-once never loses but may duplicate: the producer retries with acks=all, and the consumer processes before committing. Exactly-once means the effect happens once: inside Kafka it comes from the idempotent producer plus transactions plus read_committed consumers; at an external sink it comes from idempotent writes. In practice most systems run at-least-once with idempotent handlers.

How to answer

Define each by "lost or duplicated?", give the config or commit order that produces it, then state your default (at-least-once + idempotency) and when you would pay for exactly-once.

Likely follow-ups
  • Which one does auto-commit give you?
  • Where do duplicates come from besides retries? (rebalances)
  • Is exactly-once delivery possible over a network?
How does the idempotent producer work, and what does it NOT protect against?

The broker assigns the producer a producer ID and epoch. Each batch carries a per-partition sequence number. The partition leader remembers recent sequences per producer (the last 5 batches) and drops a batch it has already written, replying success; it rejects gaps. That removes duplicates caused by the client's own retries and keeps ordering with up to 5 in-flight requests. It does not protect against an application restart (new producer ID), against the application calling send() again for the same business event, or against duplicates on the consumer side. Since Kafka 3.0 it is on by default.

How to answer

Mechanism in three nouns (PID, epoch, sequence), the benefit (dedup + ordering), then the limits - the limits are what the interviewer is fishing for.

Likely follow-ups
  • Why must max.in.flight be 5 or less?
  • What survives a leader failover?
  • How do transactions extend this across restarts?
Walk me through a Kafka transaction. What is the transaction coordinator, and what are control markers?

The producer has a stable transactional.id. initTransactions() finds the coordinator (the leader of the __transaction_state partition the id hashes to), bumps the epoch and cleans up any unfinished transaction from a previous instance. In a loop: beginTransaction, send records - the first write to each partition registers it with the coordinator - then sendOffsetsToTransaction to include the consumer offsets, then commitTransaction. The coordinator logs PrepareCommit (the point of no return), writes a COMMIT control marker to every partition involved, and logs CompleteCommit. read_committed consumers only read up to the last stable offset and skip aborted records, so they see all of the transaction's writes or none.

How to answer

Draw it: producer, coordinator, three partitions. Name the two-phase shape (prepare in the transaction log, then markers). Finish with the reader side - transactions mean nothing without read_committed.

Likely follow-ups
  • What happens if the coordinator dies after PrepareCommit?
  • Why do offsets go into the transaction?
  • What is the performance cost?
What is a zombie producer, and how does Kafka fence it?

A zombie is an old instance that was presumed dead - a long GC pause or a network partition - while a replacement took over, and that then resumes writing. If both write, results are duplicated. With transactions, the replacement calls initTransactions() with the same transactional.id, which bumps the epoch. The coordinator and partition leaders reject anything with an older epoch, so the zombie gets ProducerFencedException and its open transaction is aborted. Since KIP-447, offset commits are also fenced by the consumer group generation, so an instance that lost its partitions in a rebalance cannot commit offsets for them.

How to answer

Tell the story (GC pause, replacement, wake-up), then "highest epoch wins". Mention the requirement this puts on you: stable, unique transactional.ids.

Likely follow-ups
  • How would you assign transactional.ids on Kubernetes?
  • What should the zombie do on ProducerFencedException?
  • What problem did KIP-890 fix?
Design: a consumer reads payment events and charges cards. How do you make sure nobody is charged twice?

First, say Kafka exactly-once does not cover the card gateway, so the design is at-least-once delivery plus idempotency at every side effect. Every payment event carries a unique payment ID created at the API (the client's idempotency key). The consumer processes, then commits. Before calling the gateway it records "attempt for payment X" in the ledger database under a unique constraint, and it passes payment X as the gateway's idempotency key, so a retried call returns the first result instead of charging again. The ledger update uses the payment ID as a unique key, so a replayed event becomes a no-op. A state machine (PENDING to CHARGED) rejects illegal repeats. A reconciliation job compares the ledger with the gateway's settlement report to catch anything that slipped through. Events reach Kafka through an outbox so the DB and the event never disagree.

How to answer

Lead with the caveat, then go hop by hop: API (idempotency key), DB to Kafka (outbox), consumer (commit order), sink (unique key + gateway key), safety net (reconciliation). Interviewers reward the hop-by-hop structure.

Likely follow-ups
  • What if the gateway times out - charged or not?
  • How long do you keep dedup keys?
  • Where do you use Kafka transactions in this design, if anywhere?
Our read_committed consumers suddenly stopped making progress, but the producer looks fine. What could it be?

A read_committed consumer cannot read past the last stable offset, which is pinned at the first record of the oldest open transaction. If a transaction is open for a long time - a producer stuck mid-transaction, a very long transaction.timeout.ms, or a hanging transaction from a late write - every reader of that partition stalls and lag grows. I would check per-partition lag to see which partitions are stuck, then run kafka-transactions.sh describe-producers / find-hanging on those partitions, and abort a hanging transaction with kafka-transactions.sh abort if needed. Long term: keep transactions short, keep transaction.timeout.ms modest, and upgrade to Kafka 4.x where KIP-890 prevents the hanging-transaction case.

How to answer

Name the mechanism (LSO), the symptom (lag on specific partitions, not all), the tool, and the prevention. Debugging questions reward a clear order of checks.

Likely follow-ups
  • Why don't read_uncommitted consumers stall?
  • Who aborts a timed-out transaction?

Scenario: double-counted orders after a deploy

After a rolling deploy of the order-count service, the dashboard shows about 2% more orders than the database. The service reads orders with auto-commit on and increments a Redis counter per record.
Weak answer: "Turn on Kafka exactly-once and it will be fixed."
Strong answer: "The deploy caused rebalances; each moved partition restarted from the last committed offset, so records processed since the last auto-commit (up to 5 s) were counted again. Kafka transactions would not cover the Redis increment anyway. Fix: make the update idempotent - keep a set of counted order IDs (or count distinct order IDs per window), or move the count into Kafka Streams with exactly_once_v2 and write the result as an upsert. Also commit in onPartitionsRevoked and use static membership to cut rebalances during deploys."
Follow-ups: how big does the dedup set get, and how do you expire it? Would cooperative rebalancing alone fix it? (It reduces the moved partitions, not the replay of uncommitted work.)

Your 60-second answer: "Does Kafka support exactly-once?"

"Yes, within Kafka. The idempotent producer - on by default - gives every batch a producer ID and sequence number, so the broker drops duplicates from retries. Transactions, with a stable transactional.id, make writes to many partitions plus the consumer offset commit atomic, and fence zombie instances by epoch. Consumers using read_committed only see committed data. Together that is exactly-once for read-process-write pipelines, which is what Kafka Streams' exactly_once_v2 uses. But it stops at Kafka's edge: for a database or a payment API I still design at-least-once plus idempotency - unique event IDs, upserts, dedup tables, idempotency keys - and I'd say 'effectively once' rather than 'exactly-once delivery'."
