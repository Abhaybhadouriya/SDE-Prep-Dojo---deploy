Zombie fencing: stopping the instance that came back

good to know

A zombie is an old instance of your app that everyone thinks is dead, but is still running. Maybe it had a 40-second garbage-collection pause, or a network partition cut it off. Kubernetes or the consumer group already started a replacement. Then the zombie wakes up and carries on writing as if nothing happened. Now two copies of "payment-validator-0" are writing the same results: duplicates, and possibly conflicting ones.

Because both instances use the same transactional.id, the replacement's initTransactions() bumps the epoch to 5. From then on, any request carrying epoch 4 is refused with ProducerFencedException (or InvalidProducerEpochException). The zombie's half-done transaction is aborted. This is why transactional.id must be stable and unique per logical producer: two different live instances must never share one, and a restarted instance must reuse its old one.

Stop here for SDE-1? If you can explain the epoch bump and "the newest instance wins", you are ready for most SDE-1 rounds. The two subsections below (KIP-447 and KIP-890 hanging transactions) are deep dive, SDE-2+: good for showing depth, rarely asked first.

How to pick the transactional.id (old way vs KIP-447) deep dive

Before Kafka 2.5, fencing worked only per transactional.id, so apps used one producer per input partition with ids like app-orders-5. That meant many producers. KIP-447 (Kafka 2.5) added a second fence: sendOffsetsToTransaction takes the consumer's group metadata (including its generation), so the coordinator can reject offset commits from a consumer that has already lost its partitions in a rebalance. Now one transactional producer per application instance is enough. Kafka Streams calls this mode exactly_once_v2; the older modes exactly_once and exactly_once_beta are removed in 4.x.

Hanging transactions and KIP-890 deep dive

A rare but nasty bug: a producer's write is delayed in the network, the transaction it belonged to is already committed or aborted, and then the late write arrives and accidentally becomes part of a new, open transaction that never completes - a hanging transaction. KIP-890 (server-side defence, Kafka 4.0, transaction.version=2) closes this by bumping the producer epoch on every transaction and having the partition leader verify a transaction is really ongoing before accepting transactional writes. A late write from an old transaction now carries a stale epoch and is rejected.

Why does a hanging transaction hurt so much? The next section explains: it freezes every read_committed consumer of that partition.
