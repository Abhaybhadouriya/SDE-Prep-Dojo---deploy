The consumer's choice: commit before or after?

must know

This is the most common source of duplicates and losses in real systems, and it is entirely in your code. Compare two timelines where the consumer crashes halfway:

The trap is auto-commit. By default enable.auto.commit=true, and the client commits the offsets returned by previous polls every auto.commit.interval.ms (5 seconds). In a simple single-threaded loop that behaves like at-least-once, because the commit happens inside the next poll() after you finished the previous batch. But if you hand records to another thread and return to poll() straight away, the offsets get committed while the work is still running - a crash then loses those records. And a crash just before an auto-commit repeats up to 5 seconds of work. Neither is visible in testing.

Properties p = new Properties();
p.put("bootstrap.servers", "localhost:9092");
p.put("group.id", "payments");
p.put("enable.auto.commit", "false");          // we decide when to commit
p.put("key.deserializer", StringDeserializer.class.getName());
p.put("value.deserializer", StringDeserializer.class.getName());

try (KafkaConsumer<String, String> c = new KafkaConsumer<>(p)) {
  c.subscribe(List.of("orders"));
  while (true) {
    ConsumerRecords<String, String> batch = c.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : batch) {
      handle(r);                                // must be idempotent!
    }
    if (!batch.isEmpty()) c.commitSync();       // commit AFTER processing
  }
}
from confluent_kafka import Consumer

c = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "payments",
    "enable.auto.commit": False,      # we decide when to commit
    "auto.offset.reset": "earliest",
})
c.subscribe(["orders"])
while True:
    msg = c.poll(0.5)
    if msg is None or msg.error():
        continue
    handle(msg)                       # must be idempotent!
    c.commit(message=msg, asynchronous=False)   # commit AFTER processing
// Only when losing a record is acceptable (e.g. a dashboard sample)
ConsumerRecords<String, String> batch = c.poll(Duration.ofMillis(500));
c.commitSync();                 // bookmark moves FIRST
for (ConsumerRecord<String, String> r : batch) handle(r);   // crash here = lost

Rebalances also cause duplicates. When a partition moves to another consumer during a rebalance, the new owner starts from the last committed offset. Anything the old owner processed but had not committed is processed again. Commit in the onPartitionsRevoked callback to shrink this window - but never assume it is zero.
