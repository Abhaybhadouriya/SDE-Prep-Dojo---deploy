Transactions: all-or-nothing writes across partitions

good to know

What interviewers actually expect here: three things. (1) A stable transactional.id plus an epoch fences zombie instances. (2) sendOffsetsToTransaction puts the consumer offset into the same transaction, so read-process-write is atomic. (3) Consumers must use isolation.level=read_committed to hide open and aborted data. In the stepper below, steps 3, 7 and 8 (partition registration, markers, CompleteCommit) are deep-dive detail: know they exist, do not memorise them.

The idempotent producer fixes duplicates for one producer, one partition, one session. Real stream processing needs more. Picture a "payment-validator" service that reads from orders, writes a result to payments and another to audit, and must move its consumer offset forward. Three separate writes:

  • a record to payments (partition 2),
  • a record to audit (partition 0),
  • the new offset for orders partition 5 (offsets are records too, in the internal topic __consumer_offsets).

A crash after the first write and before the offset commit gives a duplicate result on restart. Kafka transactions (KIP-98, Kafka 0.11) make these writes atomic: either all of them become visible, or none do. "Atomic" means all-or-nothing, like a database transaction.

The pieces

  • transactional.id: a name you choose, stable across restarts (for example payment-validator-0). This is what lets the broker recognise "the same producer, restarted".
  • Transaction coordinator: a broker module that manages a transaction's state. Which broker? The leader of the partition of the internal topic __transaction_state that the transactional.id hashes to - the same trick used for consumer group coordinators.
  • Transaction log (__transaction_state): where the coordinator writes the state changes ("ongoing", "prepare commit", "complete commit"). It is replicated like any topic, so a coordinator can fail over.
  • Control markers: special records the coordinator writes into each data partition at the end: a COMMIT or ABORT marker. Readers use them to decide which records count.

Step through one read-process-write transaction:

  1. initTransactions() - once at start-up. The producer finds its coordinator and registers transactional.id=pv-0. The coordinator bumps the epoch (4 to 5) and aborts or completes any transaction a previous instance left open. Any old instance still running with epoch 4 is now fenced.
  2. beginTransaction() - only flips a flag inside the client. Nothing is sent yet.
  3. Register partitions. The first time the transaction writes to a partition, the producer tells the coordinator (AddPartitionsToTxn). The coordinator logs "Ongoing, partitions = payments-2, audit-0" in __transaction_state.
  4. Write data. The producer sends records to the partition leaders as usual. They are in the log, replicated - but marked as part of an open transaction, so read_committed consumers cannot see them yet.
  5. Write offsets. sendOffsetsToTransaction(offsets, consumer.groupMetadata()) puts the consumer's offset commit for orders into the same transaction.
  6. commitTransaction() - the producer flushes, then asks the coordinator to commit. The coordinator writes PrepareCommit to its log. From this moment the commit will finish, even if the coordinator crashes (a new one reads its log and continues).
  7. Markers. The coordinator writes a COMMIT control marker into every partition in the transaction, including the offsets partition.
  8. Done. The coordinator logs CompleteCommit. Consumers in read_committed mode now see the payment, the audit record, and the group's offset moves - together. On abortTransaction() the same path writes ABORT markers instead, and readers skip those records.

The code

Properties pp = new Properties();
pp.put("bootstrap.servers", "localhost:9092");
pp.put("transactional.id", "payment-validator-0");   // stable across restarts
pp.put("key.serializer", StringSerializer.class.getName());
pp.put("value.serializer", StringSerializer.class.getName());
// enable.idempotence=true and acks=all are implied by transactional.id

KafkaProducer<String, String> producer = new KafkaProducer<>(pp);
producer.initTransactions();                          // fences old instances

consumer.subscribe(List.of("orders"));                // isolation.level=read_committed,
while (true) {                                        // enable.auto.commit=false
  ConsumerRecords<String, String> batch = consumer.poll(Duration.ofMillis(500));
  if (batch.isEmpty()) continue;
  producer.beginTransaction();
  try {
    for (ConsumerRecord<String, String> r : batch) {
      producer.send(new ProducerRecord<>("payments", r.key(), validate(r.value())));
      producer.send(new ProducerRecord<>("audit", r.key(), "validated"));
    }
    producer.sendOffsetsToTransaction(nextOffsets(batch), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (ProducerFencedException | InvalidProducerEpochException e) {
    producer.close();                                 // a newer instance owns this id: stop
    throw e;
  } catch (KafkaException e) {
    producer.abortTransaction();                      // nothing becomes visible
    rewindToLastCommitted(consumer);                  // re-read the batch
  }
}
from confluent_kafka import Consumer, Producer, KafkaException

consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "payment-validator",
    "enable.auto.commit": False,
    "isolation.level": "read_committed",
    "auto.offset.reset": "earliest",
})
producer = Producer({
    "bootstrap.servers": "localhost:9092",
    "transactional.id": "payment-validator-0",
})
producer.init_transactions()
consumer.subscribe(["orders"])

while True:
    msgs = consumer.consume(num_messages=100, timeout=0.5)
    if not msgs:
        continue
    producer.begin_transaction()
    try:
        for m in msgs:
            if m.error():                        # consume() can return error events
                raise KafkaException(m.error())  # -> abort below, never commit garbage
            producer.produce("payments", key=m.key(), value=validate(m.value()))
        producer.send_offsets_to_transaction(
            consumer.position(consumer.assignment()),
            consumer.consumer_group_metadata())
        producer.commit_transaction()
    except KafkaException:
        producer.abort_transaction()
        # rewind to the last committed offsets and retry the batch

Cost. A transaction adds a few extra round trips (register partitions, commit, markers) per transaction, not per message. So batch many records into one transaction: committing every record would be slow; committing every few hundred milliseconds is common. Kafka Streams with exactly-once commits every 100 ms by default (commit.interval.ms), versus 30 s for at-least-once.
