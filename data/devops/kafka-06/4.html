The idempotent producer: Grandma's stamp book, inside the broker

must know

Hole A (the lost ack) is fixed by the idempotent producer, added in Kafka 0.11 (KIP-98) and on by default since Kafka 3.0 (enable.idempotence=true, together with acks=all). Here is how it works:

  1. The producer gets an ID. On start-up the broker hands it a producer ID (PID) and an epoch (a generation number).
  2. Every batch gets a number. For each partition, the producer numbers its batches with a sequence number starting at 0: 0, 1, 2, ...
  3. The broker remembers. The partition leader keeps, for each PID, the sequence numbers of the most recent batches (up to the last 5). A batch whose sequence it has already written is answered "OK, duplicate" and not written again. A batch that skips ahead (a gap) is rejected with an out-of-order error.
  4. It survives failover. This producer state is written into the log and snapshot files, so followers have it too. A new leader can still recognise a retried batch.

Watch batch #1 get retried after a lost ack:

  1. Start. The producer has PID 42. Partition 0 already holds the batch with sequence 0; the leader remembers "last sequence from PID 42 is 0".
  2. Send. The producer sends the next batch for partition 0 with sequence 1.
  3. Written, but the ack is lost. The leader appends it and updates its memory to 1. The response never reaches the producer (network blip, or the request timed out).
  4. Retry. After request.timeout.ms the producer retries the same batch with the same PID and sequence 1. Retries are automatic: retries defaults to a huge number, bounded by delivery.timeout.ms (2 minutes).
  5. Duplicate detected. The leader sees PID 42, sequence 1 - already written. It does not append, and replies success so the producer moves on.
  6. Result. One copy in the log. Hole A is closed for retries inside this producer session.
  7. The limit. If your application crashes and restarts, it gets a brand-new PID, and the broker has no way to know the record it re-sends is old. Idempotence alone covers retries, not restarts. That gap is what transactional.id fixes.

Why max.in.flight.requests.per.connection must be 5 or less

A producer may have several requests "in the air" at once (default 5). Without idempotence, if request 1 fails and request 2 succeeds, the retry of 1 lands after 2 - reordered. With idempotence the broker insists on consecutive sequence numbers per partition, so it rejects 2 until 1 is in place, and order is kept. The broker remembers only the last 5 batches per producer per partition, which is why idempotence requires max.in.flight.requests.per.connection of 5 or less. Old advice says "set it to 1 to keep order" - with idempotence, that is no longer needed.

A silent switch-off. Since Kafka 3.2 (and still in 4.x), if you did not set enable.idempotence explicitly but set a conflicting option (for example acks=1, or max.in.flight.requests.per.connection=10), the client quietly turns idempotence off. If you set enable.idempotence=true explicitly with conflicting options, it fails at start-up with a config error instead. Write enable.idempotence=true in your config so a mistake is loud.

From your world

The epoch is the same idea as a generation number or term ID in a redundancy protocol: a node that comes back with an old generation knows it is stale and must not act. And the 5-batch window is a tiny sliding window, like TCP's, but measured in batches and kept per (producer, partition) "flow".
