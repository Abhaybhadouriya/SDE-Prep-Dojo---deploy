The big caveat: exactly-once stops at Kafka's edge

must know

Kafka's exactly-once covers read from Kafka, process, write to Kafka. The moment your code touches something else - a database, Redis, an email server, a payment gateway, an HTTP API - Kafka transactions cannot roll that back. If you charge a card inside a Kafka transaction and the transaction aborts, the card is still charged, and the retry charges it again.

  • Hop 1 (DB → Kafka): outbox table + CDC (Debezium). At-least-once, so carry an event ID.
  • Hop 2 (Kafka → Kafka): transactions / Kafka Streams exactly_once_v2 / Flink EXACTLY_ONCE.
  • Hop 3a (Kafka → DB): upsert by event ID, or store offsets in the same DB transaction.
  • Hop 3b (Kafka → payment API): idempotency key sent to the gateway; gateway dedups.

For each kind of sink, the standard toolbox:

TechniqueHow it worksUse when
Upsert by a natural keyINSERT ... ON CONFLICT (event_id) DO NOTHING or UPDATE ... SET status='PAID'. A replay overwrites with the same value.The write is "set state", not "add to state"
Dedup tableIn the same DB transaction as the business change, insert the event ID into a processed_events table with a unique constraint. A duplicate fails the insert and the transaction rolls back.Increments, counters, ledger entries
Offsets in the sinkStore the Kafka offset in the same DB transaction as the result. On restart, seek() to the stored offset instead of using Kafka's commit.One database sink, you control the consumer
Idempotency key to the APISend a unique key (derived from the event ID) with the request. The provider returns the first result for repeats.Payment gateways, third-party APIs that support it
Version / state machine checksApply an event only if the row's version is older, or only if the state transition is legal (PENDING to PAID, never PAID to PAID).Out-of-order or repeated events on an entity

-- Dedup table pattern (PostgreSQL). Run both statements in ONE transaction.
BEGIN;
INSERT INTO processed_events (event_id) VALUES ('ord-981-paid');   -- PRIMARY KEY
UPDATE wallets SET balance = balance - 500 WHERE user_id = 77;
COMMIT;
-- A duplicate event fails the first INSERT with a unique violation:
-- roll back, treat it as "already done", and commit the Kafka offset.

Interviewers love this: in a payment or wallet design, say "Kafka gives us at-least-once delivery between services; the ledger write is made idempotent with the event ID as a unique key, and the gateway call carries an idempotency key. Kafka transactions only help on Kafka-to-Kafka hops." That one paragraph answers the follow-up before it comes. See Payment System, Digital Wallet & Ledger and Distributed Transactions & Events.

And the first hop has a classic trap of its own: the dual write. An order service that does "commit to DB, then publish to Kafka" can crash between the two, leaving a DB row with no event (or an event with no row, if done the other way round). The fix is the transactional outbox: write the event into an outbox table in the same DB transaction, and let a relay (often Debezium CDC) publish it. The relay is at-least-once, so consumers still dedup by event ID. The Stream Processing, Retries & DLQ page builds this end to end, and Pipeline Architecture shows where it sits.
