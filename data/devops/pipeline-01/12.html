Interview questions

How do you choose the partition key for an orders topic?

"I start from the ordering requirement. Kafka only orders within a partition, so the key is whatever must stay in sequence. If the business rule is 'process a customer's orders in order', I key by customer id. If each order has a lifecycle of events and those must be in order, I key by order id. Then I check the spread: is there a customer big enough to make one partition hot? If yes, I either accept it, salt that one key, or give large tenants their own topic. I also fix the partition count up front because adding partitions remaps keys."

How to answer

Requirement first (what must be ordered), then distribution (hot keys), then the operational constraint (partition count is hard to change). Mention one concrete hot-key fix.

Likely follow-ups
  • A seller on sale day generates 40% of orders. What breaks and what do you do?
  • Why not use a null key and get perfect balance?
  • Two services in Java and Python produce with the same keys. Any risk?
What delivery guarantee does your pipeline give end to end?

"It is different per hop, so I will go hop by hop. API to Kafka: no loss and no producer-retry duplicates, thanks to the idempotent producer, acks=all and min ISR 2. Kafka to Kafka in the enricher: exactly-once, using transactions that commit the outputs and the input offsets together. Kafka to Postgres: at-least-once delivery, made effectively-once by an upsert on order id and committing the offset after the database commit. Analytics can both undercount (a crash loses open windows, because offsets were already committed) and overcount (re-driven duplicates). If that mattered I would checkpoint state with the offsets (Kafka Streams or Flink) and dedupe by order id. So: no order is lost, and the stored order table has no duplicates."

How to answer

Refuse to give one word. Walk the chain and name the mechanism at each hop. End with the user-visible promise.

Likely follow-ups
  • Why does Kafka exactly-once not cover the Postgres write?
  • What if the sink crashes between the DB commit and the offset commit?
Explain the dual-write problem and how you would avoid it.

"If a service writes to its database and then publishes to Kafka, those are two commits with nothing tying them together. A crash between them leaves the database saying the order exists while no event was ever sent, or the reverse. Two fixes: make one system the only write, for example write only to Kafka and build the database from the log, which is what my order pipeline does. Or, if the database must be the source of truth, use a transactional outbox: insert the event into an outbox table in the same DB transaction, and let a relay such as Debezium publish it. The relay is at-least-once, so consumers must be idempotent."

How to answer

Define it in one sentence with a failure example, then give both fixes and say when each fits. Finish with the idempotency caveat.

Likely follow-ups
  • Why not wrap both in a distributed (two-phase) transaction?
  • How does Debezium know which rows to publish, and what if it falls behind?
How do you handle a message that keeps failing?

"First I classify the failure. If waiting could help, like a timeout from a dependency, it is transient: I move the record to a retry topic with an attempt counter and a 'retry at' time using exponential backoff with jitter, so the main partition keeps flowing. After a fixed number of attempts, four in my design, it goes to the dead-letter topic. If waiting cannot help, like invalid JSON or an unknown product, it is poison and goes to the DLQ immediately. DLQ records keep the original bytes plus headers with the error and the origin topic, partition and offset. I alert on any DLQ arrival and have a tool to re-drive records after a fix. The trade-off is that retried records can overtake newer ones with the same key."

How to answer

Classify, route, cap the attempts, preserve evidence, monitor, re-drive. Then the ordering trade-off and when to park the key instead.

Likely follow-ups
  • How does the retry consumer wait without breaking the consumer group?
  • What exactly do you put in a DLQ record?
Why replication factor 3 and min.insync.replicas 2, and not 3 and 3?

"RF 3 with min ISR 2 means every write is on at least two brokers before it is acknowledged, so losing any single broker loses nothing, and writes continue with the two that remain. With min ISR 3, any one broker being down or slow, including a routine rolling restart, would stop all writes. With min ISR 1, acks=all could mean a single copy. So 3 and 2 is the usual balance: survive one failure with no loss and no downtime. If two brokers fail, writes stop on purpose: we choose consistency over availability."

How to answer

Show the failure arithmetic for each option. Mention rolling restarts, since that is when min ISR 3 hurts in practice.

Likely follow-ups
  • What does unclean leader election do, and when would you enable it?
  • How would you spread the 3 replicas across availability zones?

Scenario: the interviewer says "scale this to a national sale"

"Traffic will be 50 times normal for six hours. Your consumers already run at 6 instances on 6 partitions. What do you do?"

Weak answer: "Add more partitions and more consumers on the day."

Strong answer: "Adding partitions on the day remaps customer keys and breaks per-customer ordering, so I would plan ahead: before the sale, size partitions for the peak (for example from measured per-partition consumer throughput), and pre-scale consumers. During the sale, Kafka absorbs bursts, so short lag is fine; I alert on lag growth rate, not on a fixed number. I make the sink batch larger and check the database is the real bottleneck, not Kafka. I make sure retention is long enough that a backlog cannot expire before it is read. And I would protect the API with rate limits so a retry storm cannot overload the producers."

Likely follow-ups
  • What metric tells you consumers will catch up after the peak?
  • What would you do if the bottleneck is Postgres, not the consumers?
