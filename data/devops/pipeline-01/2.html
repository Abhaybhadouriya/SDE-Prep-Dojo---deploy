How data enters Kafka (and the dual-write trap)

There are three common ways events get into Kafka. Knowing them, and why ShopStream picks the first, is a classic interview point.

  1. The application produces directly. The service calls the Kafka producer in its request path. ShopStream does this: order-api writes to orders.created and writes nothing else.
  2. A log shipper or agent. Programs write log files; an agent (for example Fluent Bit) tails them and produces to Kafka. Common for logs and clickstream, where losing a few lines is acceptable.
  3. Change data capture (CDC). The application writes only to its database. A connector such as Debezium reads the database's own transaction log (the Postgres WAL, the MySQL binlog) and turns each committed change into a Kafka event. Shopify uses this to capture changes from more than 100 MySQL shards.

The dual-write problem, in plain words

Suppose the order service saves the order in its database and then publishes an event to Kafka. Those are two separate writes to two separate systems. There is no single "commit" that covers both. So one can succeed and the other fail:

ShopStream sidesteps the problem by design: the API's only durable write is to Kafka. The database is a downstream copy built by postgres-sink. If Postgres is down, nothing is lost; the sink waits and catches up.

That choice works because the order's "source of truth" is the event log. In many real companies, the database must be the source of truth (because other code reads it right after the write, or because it enforces stock limits). Then the standard fix is the transactional outbox: in the same database transaction as the business row, insert a row into an outbox table. A relay (often Debezium with its Outbox Event Router) publishes the outbox rows to Kafka. Both rows commit or neither does, so the event can never be lost. The relay is at-least-once, so consumers still need to handle duplicates. Page 03 goes deeper, and Kafka Connect and Debezium explains CDC itself.

From your world

The dual-write problem is the same as updating the RIB and the hardware FIB as two independent steps with no rollback: if the second step fails, the two tables disagree and nothing tells you. The outbox is like writing the intended change into a journal inside the same atomic commit, and letting a separate daemon replay the journal into the second table until it succeeds. Where it breaks: the replay daemon may apply the same entry twice after a crash, so the second table must accept repeats (be idempotent).
