The whiteboard version and the 60-second answer

In an interview you do not draw ten boxes. You draw six, say one sentence per box, and add detail only where the interviewer points.

60-second answer: "Walk me through your pipeline's design decisions." "The API validates an order and writes one event to Kafka, keyed by customer id, so one customer's orders stay in order in one partition. It waits for acks from all in-sync replicas, with min ISR 2 and an idempotent producer, so an accepted order is never lost or duplicated by retries. An enricher reads, prices and writes to a second topic inside a Kafka transaction, so outputs and the read position commit together. Temporary failures go to a retry topic with backoff and jitter, so one bad record never blocks a partition; poison records go to a dead-letter topic with an alert. A sink upserts into Postgres by order id, so redelivery is harmless, and an analytics consumer computes revenue per minute in its own consumer group. Six partitions give me up to six parallel consumers. The trade-off I chose is consistency over availability: with two brokers down, the API returns 503 rather than accept an order it might lose."

You might confuse these:

  • Partition vs replica. A partition is a slice of a topic: the unit of parallelism and of ordering. A replica is a copy of one partition on another broker, for durability. 6 partitions x 3 replicas = 18 partition copies.
  • Consumer group vs topic. A topic is where data lives. A consumer group is one reader application with its own bookmark (offsets) on that topic. Two groups read the same topic fully and independently.
  • Retry topic vs DLQ. The retry topic holds records that will be tried again automatically. The DLQ holds records a machine has given up on; only a human (or a redrive tool) moves them on.
