Event schemas: what is inside each message

A Kafka record has a key (bytes), a value (bytes), optional headers (small key/value pairs, like HTTP headers) and a timestamp. Kafka does not care what the bytes mean. Producers and consumers must agree. ShopStream uses compact JSON (sorted keys, no spaces) produced by to_json() in the common module.

// topic orders.created, key "C-42", headers event-type=OrderCreated, schema-version=1
{
  "created_at": "2026-11-23T10:15:02.481920+00:00",
  "customer_id": "C-42",
  "items": [
    {"product_id": "P-102", "quantity": 1},
    {"product_id": "P-100", "quantity": 2}
  ],
  "order_id": "3f6c2a8e-5d1b-4c7e-9a0f-2b8d7e1c4a90",
  "schema_version": 1,
  "type": "OrderCreated"
}

Built in create_order() in app.py. Pretty-printed here; on the wire it is one line. The order_id is a random UUID unless the client sends its own.

// topic orders.enriched, same key "C-42", header event-type=OrderEnriched
{
  "created_at": "2026-11-23T10:15:02.481920+00:00",
  "currency": "INR",
  "customer_id": "C-42",
  "enriched_at_ms": 1795428902611,
  "items": [
    {"line_total_cents": 249900, "name": "Headphones", "product_id": "P-102",
     "quantity": 1, "unit_price_cents": 249900},
    {"line_total_cents": 59800, "name": "Coffee mug", "product_id": "P-100",
     "quantity": 2, "unit_price_cents": 29900}
  ],
  "order_id": "3f6c2a8e-5d1b-4c7e-9a0f-2b8d7e1c4a90",
  "schema_version": 1,
  "total_cents": 309700,
  "type": "OrderEnriched"
}

Built in enrich() in enricher.py: it copies the input and adds prices, line totals and the total. 309700 paise is INR 3097.00.

orders.retry  (value = the original OrderCreated bytes, unchanged)
  attempt      = 2
  retry-at-ms  = 1795428906611          when it may be tried again
  error        = price service timeout (simulated)
  origin       = orders.created/3/1287  topic/partition/offset it came from

orders.dlq    (value = the original bytes, unchanged)
  error        = unknown product P-DOES-NOT-EXIST
  origin       = orders.created/1/512
  failed-at-ms = 1795428907002

The value is never rewritten on the failure path. Everything about the failure goes in headers, so a fixed record can be re-driven byte-for-byte.

Schema decisions and why

  • Money as integer cents. total_cents is an integer. Floating point cannot represent 0.10 exactly; money in floats eventually gives wrong totals.
  • A type and a version in every event. type and schema_version in the body, and event-type / schema-version as headers. A consumer could route or skip records by header without parsing the body (ShopStream's consumers do not need to yet). Page 03 has a try-it that sends an extra field through the pipeline and shows what a rename would break.
  • Event time travels with the event. created_at is set once, by the API. Analytics buckets by this time, not by when it happens to read the record. Page 03 explains why.
  • Enrich by copying, not by mutating upstream. orders.created is never changed. If the pricing logic had a bug, you fix it and re-run the enricher over the 7-day history.
  • Evolution rules. Add new fields as optional; never rename or change the type of an existing field; bump schema_version only for a breaking change, and then prefer a new topic. These are the same rules a Schema Registry enforces in BACKWARD mode (its default).

At larger scale you would use Avro or Protobuf with a Schema Registry. Each message then carries only a 5-byte prefix (a magic byte plus a 4-byte schema id) instead of repeating field names, and the registry refuses incompatible schema changes before they reach production. JSON keeps ShopStream readable in kafka-ui, which is the right trade for learning.
