Durability: RF 3, min ISR 2, acks=all

"The order was accepted" must mean "the order cannot be lost", even if a broker dies one millisecond later. Three settings work together to make that true.

  1. Replication factor 3. Every partition is stored on 3 brokers: one leader (takes all reads and writes) and two followers (copy from the leader).
  2. acks=all on the producer. The leader answers only after every member of the ISR (in-sync replicas: the copies that are caught up) has the record.
  3. min.insync.replicas=2 on the topic. If the ISR shrinks below 2, the leader refuses acks=all writes with NOT_ENOUGH_REPLICAS. Without this, acks=all with an ISR of just the leader means "one copy", and losing that broker loses the data.

Together: one broker can die and every accepted order still exists on at least one other broker, and writes keep working. Two brokers down and writes stop. That is a deliberate choice of consistency over availability: better to return an error than to accept an order you might lose. Page Replication & ISR explains leaders, followers and the high watermark in detail.

The producer settings live in idempotent_producer_config():

def idempotent_producer_config() -> dict[str, Any]:
    return {
        **base_config(),
        "enable.idempotence": True,
        "acks": "all",
        "max.in.flight.requests.per.connection": 5,  # max allowed with idempotence, ordering kept
        "retries": 2147483647,
        "delivery.timeout.ms": 120000,
        "linger.ms": int(os.getenv("PRODUCER_LINGER_MS", "5")),
        "batch.size": 64 * 1024,
        "compression.type": os.getenv("PRODUCER_COMPRESSION", "zstd"),
    }
  • enable.idempotence: the broker gives the producer an id and every batch a sequence number per partition. If a network blip makes the producer resend a batch the broker already has, the broker drops the duplicate. Retries become safe.
  • retries huge, bounded by delivery.timeout.ms (2 minutes): keep retrying through a leader election, but give up eventually and report an error instead of hanging forever.
  • linger.ms=5, batch.size=64 KiB, zstd: wait up to 5 ms to fill a batch, then compress the whole batch. Fewer, bigger requests. (5 ms is also the Kafka 4.x default.)

From your world

The idempotent producer is TCP sequence numbers at the application layer: the receiver tracks the last sequence per stream (per producer, per partition) and silently discards a retransmitted segment it has already accepted. acks=all with min ISR 2 is "commit only when the standby has synced". Where it breaks: the sequence state is tied to one producer session. If the order-api process restarts and the client resends a request, that is a new session, and only an application-level id (order_id) can catch the duplicate.

The cluster itself: KRaft with 3 combined nodes

Kafka 4.x has no ZooKeeper. Cluster metadata (which topics exist, who leads which partition) lives in a Raft-replicated log managed by controllers. In docker-compose.yml each of the three nodes runs as both broker and controller (KAFKA_PROCESS_ROLES: broker,controller), with KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka-1:29093,2@kafka-2:29093,3@kafka-3:29093. Raft needs a majority (2 of 3) to make decisions. Combined mode is right for a laptop; production clusters usually run dedicated controller nodes. More on KRaft.
