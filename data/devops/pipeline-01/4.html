Keys: why customer_id?

Every Kafka record can carry a key. The producer client hashes the key and takes it modulo the number of partitions. Same key, same partition, every time (as long as the partition count does not change). And Kafka keeps order only inside one partition. So choosing the key is choosing what stays in order.

Here is the real produce call in app.py:

producer.produce(
    TOPIC_CREATED,
    key=order.customer_id.encode(),
    value=to_json(event),
    headers={"event-type": "OrderCreated", "schema-version": "1"},
    on_delivery=on_delivery,
)
  1. Hash the key. The producer client (librdkafka inside confluent-kafka) hashes the key bytes and takes the result modulo 6. The broker does not choose; the client does.
  2. Same key, same partition. Both orders of C-42 land in the same partition (p3 in this example), one after the other. C-7 lands somewhere else. Order is kept per customer, not across customers.
  3. One partition, one owner. In the enricher group each partition is owned by exactly one instance, so C-42's two orders are processed by one program, in sequence. With 3 instances the split is 2/2/2.
  4. Changing the count breaks the mapping. hash mod 6 and hash mod 7 give different answers, so after adding partitions a customer's new orders may go to a different partition than their old ones. Pick the count up front.

Comparing the key choices

KeyWhat stays in orderSpreadVerdict for ShopStream
customer_id (chosen)All events of one customerGood: thousands of customersMatches the business rule "process a customer's orders in sequence". Risk: one giant customer becomes a hot partition.
order_idAll events of one order (created, paid, shipped)Excellent: every order is newGreat if each order has a lifecycle of events. Loses per-customer order, which matters for things like "first order discount".
none (null key)NothingBest: the client spreads batches across partitionsFine for logs and metrics. Wrong for orders.
product_idEvents of one productPoor: a best-seller is a hot spotUseful for an inventory topic, not for orders.

From your world

Key partitioning is ECMP flow hashing. The 5-tuple hash keeps one TCP flow on one link so its packets do not reorder; the customer id keeps one customer on one partition for the same reason. A hot customer is an elephant flow pinned to one link while the others idle. And adding a partition is like adding an ECMP member without resilient hashing: many flows move at once. Where it breaks: ECMP rehashing causes a moment of reordering; Kafka rehashing permanently splits a customer's history across two partitions.

Gotcha with mixed languages. Different clients use different default hash functions. The Java client uses murmur2; librdkafka (Python, Go's confluent client, C) defaults to a CRC32-based partitioner called consistent_random. If a Java service and a Python service both produce to the same topic with the same keys, the same customer can land in two partitions. Fix: set partitioner=murmur2_random in librdkafka so it matches Java.

Hot keys. The load generator has a flag for exactly this: --hot-customer 0.5 sends half of all orders from one customer, C-HOT. One partition then gets roughly half the traffic, and one enricher instance does half the work while others idle. Standard fixes, in order of preference: accept it if that partition still keeps up; split the heavy key (C-HOT#0 ... C-HOT#3) and re-combine downstream if order across the splits does not matter; or route very large tenants to their own topic.
