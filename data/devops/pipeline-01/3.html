Topic design: names, counts, retention

Four topics, all created by scripts/create-topics.sh before any service starts. Here is the real script, slightly trimmed:

BOOTSTRAP="${1:-kafka-1:19092}"
RF="${2:-3}"
MIN_ISR="${3:-2}"
BIN=/opt/kafka/bin

echo "waiting for Kafka at $BOOTSTRAP ..."
until $BIN/kafka-broker-api-versions.sh --bootstrap-server "$BOOTSTRAP" >/dev/null 2>&1; do sleep 2; done

create() { # name partitions extra-configs...
  local name=$1 parts=$2; shift 2
  $BIN/kafka-topics.sh --bootstrap-server "$BOOTSTRAP" --create --if-not-exists \
    --topic "$name" --partitions "$parts" --replication-factor "$RF" \
    --config min.insync.replicas="$MIN_ISR" "$@"
}
# 6 partitions = up to 6 consumers in a group can work in parallel.
create orders.created  6 --config retention.ms=604800000      # 7 days: replay window
create orders.enriched 6 --config retention.ms=604800000
create orders.retry    3 --config retention.ms=86400000       # 1 day
create orders.dlq      3 --config retention.ms=1209600000     # 14 days: time to investigate
TopicPartitionsRF / min ISRRetentionWhy these numbers
orders.created63 / 27 daysThe main input. 6 partitions lets up to 6 enricher instances work in parallel. 7 days is the replay window: if a bug is found on Friday, Monday's orders can still be reprocessed.
orders.enriched63 / 27 daysSame key and same count as the input, so partition 2 in maps naturally to partition 2 out, and sinks can scale to 6 too.
orders.retry33 / 21 dayOnly a small fraction of traffic should land here. A retry older than a day is not a retry any more, it is an incident.
orders.dlq33 / 214 daysHumans read this. Two weeks covers a holiday and gives time to fix and re-drive.

Naming rules worth stealing

  • domain.event in lower case. orders.created says what happened, in past tense. Avoid naming topics after the program that writes them (enricher-output), because programs change and events do not.
  • Suffixes for the plumbing. .retry and .dlq sit next to their main topic, so anyone browsing kafka-ui understands the family. Bigger systems use several retry tiers such as orders.retry.1m and orders.retry.10m (the Uber pattern).
  • One place for names in code. shopstream_common.py defines TOPIC_CREATED, TOPIC_ENRICHED, TOPIC_RETRY and TOPIC_DLQ once. A typo becomes an import error, not a new topic.
  • Auto-create is off. The compose file sets KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false". With the broker default (true), a typo like orders.cretaed silently creates a topic with the broker defaults, and your events vanish into it.

Defaults are not durable. Out of the box, Kafka's broker defaults are num.partitions=1, default.replication.factor=1 and min.insync.replicas=1. That is fine for a laptop demo and dangerous in production. ShopStream sets RF 3 and min ISR 2 both as broker defaults (in docker-compose.yml) and on every topic (in the script), so it never relies on defaults.
