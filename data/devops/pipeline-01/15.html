Quick quiz

An enricher group has 6 partitions to read. You start 8 instances. What happens?

  1. Each instance reads 0.75 partitions
  2. 6 instances get one partition each; 2 sit idle
  3. Kafka creates 2 new partitions
Within a group each partition has exactly one owner. Extra members wait as standbys until someone leaves.

With RF 3 and min.insync.replicas=2, two brokers die. What does the order-api see?

  1. Writes continue on one broker
  2. Orders are silently lost
  3. Writes fail (NOT_ENOUGH_REPLICAS / timeouts), so the API returns errors
The ISR is below 2, so the leader refuses acks=all writes. The system chooses consistency over availability; the API surfaces 503 or 504.

Which hop does Kafka's exactly-once (transactions) actually cover in ShopStream?

  1. orders.created through the enricher to its output topics
  2. orders.enriched to Postgres
  3. The customer's HTTP request
Transactions cover reading from Kafka and writing to Kafka. The Postgres hop is made safe by an idempotent upsert instead.

An order has "quantity": -3. Where does it go?

  1. orders.retry, up to 4 times
  2. orders.dlq immediately, because retrying cannot fix it
  3. orders.enriched with a negative total
enrich() raises PoisonMessage("bad quantity ..."), which routes straight to the DLQ.

Why does the sink commit its Kafka offsets after the Postgres transaction?

  1. It is faster
  2. Kafka requires it
  3. If it crashes in between, it re-reads and re-upserts (safe), instead of skipping rows (data loss)
Commit-after-work gives at-least-once; the upsert turns repeats into no-ops. Committing first would give at-most-once.

What is the main risk of adding partitions to orders.created later?

  1. Keys map to different partitions, so a customer's old and new orders are no longer in one ordered log
  2. Existing data is deleted
  3. Consumers stop working
hash mod 6 differs from hash mod 8. Existing data stays where it is; new records for the same key may go elsewhere.

Why does ShopStream set KAFKA_AUTO_CREATE_TOPICS_ENABLE to false?

  1. To save disk space
  2. So a typo in a topic name fails loudly instead of creating a new topic with default (non-durable) settings
  3. Because KRaft does not support it
Auto-created topics get broker defaults and absorb events nobody reads. Topics should be created on purpose, by the init script or an operator.
