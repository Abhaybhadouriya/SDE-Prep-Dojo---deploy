Common mistakes

Auto-committing offsets. The consumer default is enable.auto.commit=true: offsets are committed every 5 seconds whether or not you finished. Crash after the commit and before the DB write, and the order is lost. ShopStream sets it to False everywhere and commits after the work.

New groups skip old data. The consumer default auto.offset.reset=latest means a brand new group starts at the end and sees nothing that was already there. ShopStream sets earliest, so a new sink fills the table from the full 7-day history.

Retrying in place. Catching an exception and sleeping in a loop inside the consumer blocks the whole partition behind one record (head-of-line blocking) and can exceed max.poll.interval.ms, triggering a rebalance. Move the record aside instead.

Treating poison as transient. A malformed record retried forever is an infinite loop. Classify errors: will waiting help? If not, DLQ it now.

Client retries without an id. If the API returns 504 and the client resends without order_id, the API generates a new UUID and the order is stored twice. Clients should generate the order_id (an idempotency key) and resend the same one.

Assuming analytics is exactly-once. A duplicate record in orders.enriched is harmless for the sink (upsert) but counts twice in a revenue window. Each consumer needs its own duplicate strategy.

Two instances with the same transactional.id. The newer one fences the older one: the older one gets a fatal ProducerFenced error and exits. That is a feature (it kills zombies), but if you hard-code the id and run two copies, they will keep killing each other. ShopStream derives it from the hostname.
