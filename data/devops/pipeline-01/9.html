Delivery guarantees, hop by hop

"What guarantee does the pipeline give?" has no single answer. It is a chain, and you should state it per hop. This table is the most important thing on the page for an interview.

HopGuaranteeHow
client to order-apiAt-least-once if the client retriesA resend with the same order_id is harmless, because the sink upserts on it
order-api to KafkaNo loss, no duplicates from producer retriesIdempotent producer, acks=all, min ISR 2
orders.created to enricher to enriched/retry/dlqExactly-onceKafka transactions: outputs and input offsets commit atomically; readers use read_committed
orders.enriched to PostgresEffectively-onceAt-least-once delivery + INSERT ... ON CONFLICT (order_id) DO UPDATE; offsets committed only after the DB commit
orders.enriched to analyticsAt-most-once for open windows (offsets committed while state is only in memory; a crash loses them); duplicates from upstream re-drives are counted twiceIn-memory windows; a real system checkpoints state together with offsets (Kafka Streams or Flink state stores)

The sink's trick in one SQL statement (from sink.py):

INSERT INTO orders (order_id, customer_id, total_cents, currency, items, created_at,
                    kafka_partition, kafka_offset)
VALUES (...)
ON CONFLICT (order_id) DO UPDATE SET
    total_cents = EXCLUDED.total_cents,
    items       = EXCLUDED.items,
    kafka_partition = EXCLUDED.kafka_partition,
    kafka_offset    = EXCLUDED.kafka_offset,
    updated_at  = now()
WHERE orders.kafka_offset <= EXCLUDED.kafka_offset

If the sink crashes after the database commit but before the offset commit, it will read the same records again. The upsert just rewrites the same row. The WHERE clause adds one more guard: an older copy of a record never overwrites a newer one.

Backpressure: who slows down whom

Backpressure means a slow part of the system pushes back on the fast part instead of being overwhelmed. In ShopStream it happens at two places:

  • Between Kafka and consumers: lag. Consumers pull at their own speed. If the sink is slow, records wait on disk. Nothing is dropped; the gap between the newest offset and the sink's committed offset grows. That gap is consumer lag, and Prometheus alerts on it (EnricherLagHigh fires when the enricher group is more than 1000 records behind for 2 minutes).
  • Between clients and the API: 503. The producer buffers records in memory before sending. If brokers are down, that buffer fills and produce() raises BufferError. The API turns that into HTTP 503 "producer queue full, retry later" with Retry-After: 1. If the broker does not acknowledge within 10 s (ACK_TIMEOUT_S) the API returns 504, honestly saying the order "may still be delivered".

From your world

Consumer lag is queue depth on an egress interface: if it grows steadily, the drain rate is lower than the fill rate. The 503 is TCP flow control at the edge: when the send buffer is full, tell the sender to back off rather than accept bytes you cannot hold. Where it breaks: a NIC queue is microseconds deep and drops on overflow; a Kafka partition can hold days of backlog on disk, so lag is a slow-burning problem you watch on a graph, not a drop counter.

The ordering caveat

On the happy path, a customer's orders stay in order (same key, same partition, one owner). But a retried order takes a detour through orders.retry and comes back later, so a newer order from the same customer can overtake it. That is the trade-off of non-blocking retries. If a domain needs strict per-key order (for example account balance updates), you instead park the key: stop processing that customer's later records until the retry succeeds, while other customers keep flowing.
