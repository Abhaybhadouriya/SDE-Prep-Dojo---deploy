Keys: how a record picks its partition

When a producer sends a record, a small function inside the client called the partitioner decides which partition it goes to. The rule for the Java client (and therefore the console tools) is:

  • Record has a key: partition = murmur2(key bytes), made positive, modulo the number of partitions. Same key, same partition, every time - as long as the number of partitions does not change.
  • Record has no key (key is null): since Kafka 3.3 the default is the uniform sticky partitioner. It fills a batch for one partition, then switches to another, so records spread out evenly over time while batches stay big. (Very old clients did plain round-robin per record.)
  • You set the partition explicitly in the send call, or plug in a custom partitioner. Rarely needed.

Click through the stepper to see one key travel, and what goes wrong when someone adds a partition.

  1. A record with a key. The producer sends an OrderPlaced event with key o-3 (the order ID).
  2. Hash the key. The partitioner runs the murmur2 hash on the key's bytes and makes the result positive. The same bytes always give the same number.
  3. Modulo the partition count. With 3 partitions, the number modulo 3 is 1, so the record goes to P1 and is appended at the end.
  4. Same key again. The OrderPaid event for o-3 hashes to the same number, so it lands in P1 too, after OrderPlaced. Any consumer of P1 sees them in the right order.
  5. No key. A click event with a null key has no "home" partition. The sticky partitioner fills a whole batch for one partition (here P2), then moves on, which keeps batches large and the load balanced.
  6. Someone adds a partition. Now the hash is taken modulo 4, and o-3 maps to P0. Old o-3 events are in P1, new ones in P0, and nothing orders them against each other. This is why you choose the partition count up front.

From your world

Key partitioning is ECMP flow hashing. A router hashes the 5-tuple so every packet of one TCP flow takes the same path, which keeps that flow in order, while different flows spread over all links. Kafka hashes the key so every record of one order takes the same partition. Adding a partition is like adding an ECMP member with plain modulo hashing: most flows get re-hashed to a new path and can reorder during the change. Kafka's default partitioner does not use consistent or resilient hashing, so the remap is large. A hot partition is an elephant flow pinned to one link. Where this breaks: routers can rebalance buckets on the fly; Kafka never moves records that are already written, so the old and new partitions both hold history for the key.

Choosing a good key

Ask one question: "What must stay in order?" The answer is your key.

DataGood keyWhy
Order lifecycle eventsorderIdPlaced, Paid, Shipped for one order must be read in order.
Bank account changesaccountIdBalance updates for one account must apply in order.
Driver GPS updatesdriverIdThe latest position per driver must win; mixing would make the car jump around.
Page-view clicks for analyticsnull (no key)No ordering need; spread load evenly.
Database change events (CDC)the row's primary keyUpdates to one row must apply in order; also needed for compaction.

Hot partition warning: a key must also have many different values that are used evenly. Keying sales events by sellerId on a marketplace sends every sale of the biggest seller to one partition during a sale day. That partition's broker and its single consumer become the bottleneck while others sit idle. Fixes include a more specific key (orderId), "salting" the hot key into a few sub-keys (seller42#0 to seller42#7) and merging downstream, or a separate topic for the giants.
