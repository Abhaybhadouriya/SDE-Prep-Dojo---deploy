Partitions: how one topic becomes many logs

One log on one machine has limits: one disk, one network card, one CPU handling it. If orders receives more data than one broker can write, or more than one consumer can process, a single log becomes the bottleneck. So Kafka splits each topic into partitions. Each partition is its own independent log with its own offsets starting at 0, and different partitions can live on different brokers.

Partitions give you two things at once, and this sentence is worth memorising: the partition is the unit of parallelism and the unit of ordering.

  • Parallelism. Different partitions can sit on different brokers (spreading disk and network load), and in a consumer group each partition is read by exactly one consumer. So 12 partitions allow up to 12 consumers in one group to work in parallel. A 13th consumer would sit idle (that is page 04's story).
  • Ordering. Inside one partition, records are stored and delivered in offset order. Across partitions there is no ordering. P0 offset 5 and P1 offset 2 have no "before" or "after" relation at all.

Why is ordering only inside a partition?

Because a global order would need one single place that decides "this record comes next" for the whole topic. That single place would be a bottleneck and a single point of failure, which is exactly what partitions were invented to remove. Kafka makes a deliberate trade: you give up total order across the topic, and in return the topic can scale across many machines. In practice you rarely need total order. You need order per thing: all events of one order, one user, one bank account. Keys give you exactly that.
