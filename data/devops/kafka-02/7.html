Brokers and the cluster

A broker is one Kafka server process (one JVM) with its own disks. A cluster is a set of brokers that together hold all the partitions of all the topics. In Kafka 4.x, a cluster also has controllers: nodes that manage cluster metadata (which brokers are alive, which topics exist, who leads each partition). A small dev setup can run both roles in one process, as in our lab; production runs them separately. Page 08 covers controllers.

Each partition is stored on several brokers for safety. The number of copies is the topic's replication factor (RF). One copy is the leader: all writes and (by default) all reads go to it. The other copies are followers that keep copying from the leader. If the leader's broker dies, a follower that is fully caught up becomes the new leader. That whole dance is page 05; here, just see the layout.

Now the question every networking person asks: how does a client know which broker to talk to? It does not use a load balancer in front of the brokers. It asks for a map first. Step through it:

  1. Bootstrap. The client is configured with bootstrap.servers: one or more broker addresses, used only to get started. Any broker will do.
  2. Metadata. The client asks for metadata and gets the full map: every partition of the topic, which broker leads it, and every broker's advertised address. The client caches this.
  3. Direct to the leader. For each record the client computes the partition, looks up the leader in its cache, and sends straight to that broker. No proxy or load balancer in between.
  4. Leader fails. Broker 2 dies. The send fails with a "not leader" or connection error.
  5. Refresh. Meanwhile the cluster's controller has made broker 3 the new leader of P1. The client refreshes its metadata and learns the new map.
  6. Retry. The client retries on broker 3. With the default producer settings (retries enabled, idempotence on) this happens automatically and without duplicates.

From your world

The metadata cache is a forwarding table: "for destination partition P1, next hop is broker 2". A leader change is a route change; the "not leader" error is like an ICMP redirect telling the client its route is stale, and the client re-learns the route. Where this breaks: there is no anycast or VIP. The client must reach each specific broker at the address that broker advertises. That is why Kafka behind Docker port-mapping or Kubernetes Services so often fails with "connected to bootstrap, then timed out": the advertised address is not reachable from the client. You will hit this on page 11 and in the Kubernetes deployment.
