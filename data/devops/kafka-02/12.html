Common mistakes and gotchas

  1. Assuming topic-wide order. "The consumer will see events in the order we sent them" is only true per partition. Use a key for things that must stay in order.
  2. A key with too few values. Keying by country, status or a boolean puts most traffic in a handful of partitions. Choose a high-cardinality key that is spread evenly.
  3. Adding partitions to a keyed topic in a hurry. It remaps keys and breaks per-key order during the switch. If you must, pause producers, let consumers drain, then add partitions - or create a new topic and migrate.
  4. Expecting the partition count to shrink. You cannot remove partitions. Over-partitioning is fixed only by creating a new topic.
  5. Relying on auto-created topics. A typo silently creates a topic with default settings. Create topics explicitly with the partition count and replication factor you want.
  6. Different clients, different partitioners. The Java client uses murmur2. Clients built on librdkafka (such as Python's confluent-kafka) default to a different hash, so the same key can land in a different partition. If services in different languages write the same topic, set librdkafka's partitioner to murmur2_random. Page 03 shows this.
  7. Huge records. Records over about 1 MiB are rejected by default. Store big payloads elsewhere and send a pointer.
