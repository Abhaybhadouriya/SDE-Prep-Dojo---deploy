Lab: partitions, keys and offsets on your laptop

Use the single-broker container from the track overview. Open a shell inside it so the commands stay short:

docker run -d --name broker -p 9092:9092 apache/kafka:4.4.0   # skip if already running
docker exec -it --workdir /opt/kafka/bin broker sh

1. Create and describe a topic

./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic shop-orders --partitions 3
./kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic shop-orders
$ ./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic shop-orders --partitions 3
Created topic shop-orders.
$ ./kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic shop-orders
Topic: shop-orders	TopicId: hX3k9QvVTnGq1u8cY0a7Bw	PartitionCount: 3	ReplicationFactor: 1	Configs:
	Topic: shop-orders	Partition: 0	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
	Topic: shop-orders	Partition: 1	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:
	Topic: shop-orders	Partition: 2	Leader: 1	Replicas: 1	Isr: 1	Elr: 	LastKnownElr:

Read each column: Leader 1 means node 1 (our only broker) leads the partition. Replicas lists every broker that holds a copy; Isr lists the copies that are fully caught up ("in-sync replicas"). Elr and LastKnownElr are newer replication fields from Kafka 4.x, explained on page 05. Your TopicId will be different.

2. Produce records with keys

Tell the console producer to split each line at the colon: left part = key, right part = value.

./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic shop-orders \
  --reader-property parse.key=true --reader-property key.separator=:
>o-1:placed
>o-2:placed
>o-3:placed
>o-1:paid
>o-4:placed
>o-5:placed
>o-6:placed
>o-3:paid
^C

Version note: Kafka 4.2 renamed some console-tool flags (KIP-1147, a Kafka Improvement Proposal). This track uses the new names: --reader-property for the console producer, --formatter-property for the console consumer, and --command-property for client settings such as acks. On older versions use the old names (--property, --producer-property, --consumer-property); they still work on 4.x until 5.0 but print a deprecation warning.

3. Read them back and see where they landed

./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic shop-orders --from-beginning \
  --formatter-property print.partition=true --formatter-property print.offset=true --formatter-property print.key=true
Partition:0	Offset:0	o-1	placed
Partition:0	Offset:1	o-2	placed
Partition:0	Offset:2	o-1	paid
Partition:1	Offset:0	o-3	placed
Partition:1	Offset:1	o-4	placed
Partition:1	Offset:2	o-6	placed
Partition:1	Offset:3	o-3	paid
Partition:2	Offset:0	o-5	placed
^CProcessed a total of 8 messages

Check it against the table earlier on this page: o-1 and o-2 went to P0, o-3, o-4, o-6 to P1, o-5 to P2. Inside each partition, o-1 placed comes before o-1 paid, and o-3 placed before o-3 paid. Offsets restart at 0 in each partition. The consumer may print partitions in a different interleaving each time you run it - that is "no order across partitions" in action. Within a partition, the order never changes.

4. Count records per partition, then look at the files

./kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic shop-orders
ls /tmp/kraft-combined-logs/shop-orders-1/
./kafka-dump-log.sh --print-data-log --files /tmp/kraft-combined-logs/shop-orders-1/00000000000000000000.log
$ ./kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic shop-orders
shop-orders:0:3
shop-orders:1:4
shop-orders:2:1
$ ls /tmp/kraft-combined-logs/shop-orders-1/

00000000000000000000.log        leader-epoch-checkpoint
$ ./kafka-dump-log.sh --print-data-log --files /tmp/kraft-combined-logs/shop-orders-1/00000000000000000000.log
Dumping /tmp/kraft-combined-logs/shop-orders-1/00000000000000000000.log
Log starting offset: 0
baseOffset: 0 lastOffset: 0 count: 1 ... isTransactional: false ... compresscodec: none ...
| offset: 0 CreateTime: 1763884800123 keySize: 3 valueSize: 6 sequence: 0 headerKeys: [] key: o-3 payload: placed

kafka-get-offsets.sh prints topic:partition:log-end-offset: 3 + 4 + 1 = 8 records. The directory listing is the real partition on disk: one segment (.log) with its two index files, named after its first offset, 0. The /tmp/kraft-combined-logs path is where the official Docker image keeps data; on a real server it is whatever log.dirs says. (Lines are trimmed; the full dump shows each batch's producer ID, sequence and CRC.)

5. Break it: add a partition and watch keys move

./kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic shop-orders --partitions 4
./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic shop-orders \
  --reader-property parse.key=true --reader-property key.separator=:
#  type:  o-3:shipped   then Ctrl+C
./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic shop-orders --from-beginning \
  --formatter-property print.partition=true --formatter-property print.key=true
Partition:0	o-3	shipped
Partition:1	o-3	placed
Partition:1	o-3	paid
...

The new o-3 shipped event went to P0, while its earlier events are in P1. A consumer reading P0 could process "shipped" before another consumer has processed "paid". That is the ordering break from the stepper, made real. Also try --partitions 2: Kafka refuses, because partitions can be added but never removed.

Clean up with exit and then docker rm -f broker when you are done. Starting again gives you a fresh, empty cluster.
