Interview questions

The 60-second answer: "Explain Kafka's core concepts."
"Kafka stores streams of records in topics. Each topic is split into partitions, and each partition is an append-only, ordered log where every record gets an increasing offset. Partitions are spread over brokers, the servers in the cluster, and each partition is replicated to a few brokers with one leader taking the writes. Producers choose the partition by hashing the record key, so all records with the same key stay in order in one partition; there is no ordering across partitions. Consumers pull from partitions and track their position as a committed offset, which Kafka stores in an internal topic. Reading does not delete anything; data is removed by retention or compaction. So the partition is the unit of both ordering and parallelism, and choosing the key and the partition count are the two big design decisions."

Explain topic, partition, offset and broker.

A topic is a named stream of records. It is split into partitions, each an ordered append-only log. An offset is a record's position inside one partition. A broker is a Kafka server that stores partitions; a cluster of brokers holds all partitions, each replicated to several brokers with one leader.

How to answer

Draw the three-partition picture while you talk: boxes for partitions, numbered cells for offsets, brokers around them. Finish with "ordering is per partition, and the key decides the partition".

Likely follow-ups
  • Where are consumer offsets stored? (__consumer_offsets, an internal compacted topic.)
  • What is in a record? (Key, value, timestamp, headers.)
  • What happens to a record after it is read? (Nothing; retention removes it later.)
How do you keep all events for one order in sequence?

Use the order ID as the record key. The default partitioner hashes the key, so every event of that order goes to the same partition, which preserves order. Keep the idempotent producer on (the default) so retries cannot reorder batches, and on the consumer side process each partition sequentially, or route by key to a fixed worker if you parallelise inside the consumer. Avoid changing the partition count, because that remaps keys.

How to answer

Three layers: producer (key + idempotence), broker (order within a partition), consumer (do not reorder in your thread pool). Mentioning all three is what separates SDE-2 answers.

Likely follow-ups
  • What if one order has a huge number of events? (Fine; order IDs are many and spread evenly.)
  • What if you key by customer instead? (Coarser ordering, risk of hot keys for heavy customers.)
  • Can you get a global order across all orders? (Only with one partition, which does not scale.)
What is a hot partition, and how do you fix it?

A hot partition gets far more traffic than the others because the key is skewed: a celebrity user, a giant seller, a single default value like "unknown". Its leader broker and its single consumer become the bottleneck while other partitions are idle, and lag grows only on that partition. Fixes: pick a finer key (order ID instead of seller ID), salt the hot key into N sub-keys and re-combine downstream (you lose strict order for that key, so only do this when order across sub-keys does not matter), move whales to their own topic, or use a custom partitioner.

How to answer

Define it, show how you would detect it (per-partition bytes-in and lag in monitoring), then give two fixes and the trade-off of each.

Likely follow-ups
  • Does adding partitions fix a hot key? (No. One key always maps to one partition.)
  • How is this like an elephant flow on ECMP? (Same problem, same fix: split the flow.)
Can you change the number of partitions later? What breaks?

You can increase it with kafka-topics.sh --alter --partitions, but never decrease it. Increasing it changes the modulo in the default partitioner, so most keys map to a new partition. Existing data does not move, so a key's old events stay in the old partition and new events go to the new one, breaking per-key ordering across that moment. Consumer groups rebalance to pick up the new partitions, and by default consumers start new partitions from the latest offset, so check auto.offset.reset to avoid skipping early records.

How to answer

Say "increase yes, decrease no", then the key-remapping consequence, then how you would do it safely: drain, then add; or migrate to a new topic.

Likely follow-ups
  • How do you pick the initial count?
  • Why can't Kafka shrink a topic? (Records in the removed partition would have nowhere to go without breaking offsets.)
If Kafka stores data on disk, how is it different from a database?

Kafka is optimised for one access pattern: append at the end and read sequentially from a position. It has no secondary indexes, no queries by content, no in-place updates, and it is partitioned by key with ordering only per partition. A database is optimised for random reads and updates of current state. They complement each other: Kafka is the ordered history of changes, and consumers build databases, caches and search indexes from it (the stream-table duality). With compaction, a topic can hold the latest value per key, which looks like a table, but you still cannot query it like one.

How to answer

Contrast access patterns first, then say "stream of changes vs current state", then give one example of using both together, such as CDC from a database into Kafka feeding a search index.

Likely follow-ups
  • Can Kafka be your source of truth? (Some event-sourced systems do this with infinite retention or compaction, but you need a query layer.)
  • What is log compaction for?

Scenario: one consumer is always behind on sale day

Your marketplace publishes sale events keyed by sellerId to a 24-partition topic. On a big sale day, total lag is fine except on partition 7, where it climbs into millions while the other 23 partitions are nearly at zero. Adding more consumers does nothing. What is happening and what do you do?

Weak answer: "Add more partitions and more consumers." More partitions do not split one key, and more consumers than partitions just sit idle. It also remaps every other seller's key mid-sale.

Strong answer: "A single hot key is pinned to partition 7: probably the biggest seller. One partition is read by one consumer in the group, so that consumer is the bottleneck. I would confirm with per-partition bytes-in and the top keys on partition 7. Short term, speed up that consumer (batch its database writes) and accept the lag if it drains after the peak. Real fix: ask what must be ordered. If it is per order, re-key by orderId, which spreads evenly. If seller order matters, salt only the known hot sellers into sub-keys and merge downstream, or route the top sellers to a dedicated topic with its own consumers. I would roll that out as a new topic and migrate, not by altering partitions in the middle of the sale."

Likely follow-ups
  • How would you detect this before the sale? (Key-distribution analysis, load tests with production-like skew.)
  • What does salting cost you? (Per-key ordering across the sub-keys.)
