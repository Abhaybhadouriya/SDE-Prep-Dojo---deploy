The big idea: desired state and the control loop

Must know (SDE-1)

There are two ways to tell a computer what to do:

  • Imperative ("do this, then this"): "Start a container on server-2. Then start one on server-5." If anything changes later, your commands are out of date.
  • Declarative ("this is what I want"): "There should be 3 copies of shop:1.0." The system works out the steps, and keeps working them out forever.

Kubernetes is declarative. You write down the desired state (what you want). Kubernetes measures the actual state (what is really running). A small program called a controller compares the two and takes one step to make them closer. Then it does it again. And again. This forever loop is called reconciliation, and it is the single most important idea in Kubernetes. Almost every feature you will learn is "just another controller".

Explain like I'm 5

A controller is like the thermostat in your house. You set it to 22 degrees (desired state). It keeps checking the room (actual state). Too cold? Heater on. Warm enough? Heater off. You never tell it "run the heater for 14 minutes". You just set the number.

Why is this better than commands? Because the loop also fixes things nobody predicted. A node dies, someone deletes a pod by mistake, a container crashes, a cloud VM is reclaimed: in every case, the controller just sees "want 3, have 2" and fixes it. It does not need to know why the count dropped.

Interviewers love the phrase "level-triggered, not edge-triggered". An edge-triggered system reacts to events ("pod died!"), so if it misses one event, it is wrong forever. Kubernetes controllers are level-triggered: they look at the current level (how many pods exist now) every time, so a missed event is fixed on the next pass. If you have written interrupt handlers versus polling loops, you already know this trade-off.
