When you should NOT use Kubernetes

Must know (SDE-1)

Saying "Kubernetes for everything" in an interview is a red flag. Kubernetes has a real cost: there are many moving parts to learn, upgrade (about three minor releases a year, each supported for roughly 14 months) and secure. Here is an honest comparison of the common choices.

OptionGood forYou still have to handle
Docker on one VM (+ systemd)A hobby app, an internal tool, a single small service.Everything when that VM dies. No automatic failover.
Docker ComposeRunning several containers together on one machine: local dev, tests, small single-host apps. See Docker Compose.Multiple machines, failover, rolling updates across hosts.
Serverless containers (AWS Fargate / App Runner, Azure Container Apps, Google Cloud Run)Stateless web APIs and jobs where you want zero servers to manage.Less control over networking, sidecars, long-lived state; per-request pricing can grow.
Simpler orchestrators (Amazon ECS, HashiCorp Nomad)Teams that want scheduling and self-healing with fewer concepts.Smaller ecosystem; less portable across clouds.
Managed Kubernetes (EKS, AKS, GKE)Many services, many teams, need for portability, custom controllers, a big ecosystem (Helm charts = installable app packages of templated YAML; operators = custom controllers that run complex software like a database for you).Upgrades of nodes and add-ons, YAML sprawl, security policy, cost control.
Pros of Kubernetes
  • Self-healing and scheduling across a fleet
  • One API for every cloud and on-premises
  • Huge ecosystem: operators, Helm charts, autoscalers
  • Declarative, git-friendly, easy to automate
  • Extensible: you can add your own resource types
Cons of Kubernetes
  • Steep learning curve (this track exists for a reason)
  • Operational work: upgrades, add-ons, security
  • Overkill for one or two services
  • Easy to misconfigure (probes, limits, RBAC = role-based access control, who may do what)
  • Stateful apps need extra care

A strong trade-off sentence: "For a single service with a small team I would start with a managed container service like Cloud Run or ECS on Fargate, because it removes cluster operations. If we grow to many services and teams, need custom controllers or want to stay cloud-portable, I would move to managed Kubernetes and accept the operational cost."
