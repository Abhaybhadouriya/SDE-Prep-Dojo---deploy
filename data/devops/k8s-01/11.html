Interview questions

What problem does Kubernetes solve? Why not just run Docker on VMs?

Docker runs containers on one machine. Kubernetes manages containers across a fleet of machines. It decides where each container runs (scheduling), restarts or replaces it when it or its machine fails (self-healing), gives groups of containers a stable name and virtual IP with load balancing (service discovery), replaces versions gradually with rollback (rolling updates), and adds or removes copies with load (autoscaling). The key design idea is declarative desired state: I write "3 replicas of image X" and controllers continuously reconcile the real world toward that. Docker on VMs plus scripts gives you none of that continuous reconciliation; you would be rebuilding it by hand.

How to answer

One sentence of contrast (one host vs a fleet), then 4-5 capabilities, then the core idea (desired state + control loops). Finish with a short trade-off: "for one small service I would not use it".

Likely follow-ups
  • Which component actually restarts a crashed container? (kubelet)
  • Which one replaces pods from a dead node? (controllers in kube-controller-manager, then the scheduler)
  • When would you not use Kubernetes?
What is the difference between declarative and imperative configuration? Why does Kubernetes prefer declarative?

Imperative means giving step-by-step commands ("start a container on node 2"). Declarative means describing the end state ("there should be 3 replicas") and letting the system work out the steps. Kubernetes prefers declarative because its controllers are reconciliation loops: they compare desired and actual state every time, so they also repair drift nobody predicted, like a crashed node or a manual deletion. Declarative files are also idempotent and can live in git, so changes are reviewed, versioned and easy to roll back.

How to answer

Define both with a tiny example, then connect declarative to the control loop, then give the practical win (GitOps, review, rollback).

Likely follow-ups
  • What is level-triggered vs edge-triggered?
  • What is GitOps?
  • What happens if two people apply different YAML?
When would you NOT choose Kubernetes?

When the operational cost is bigger than the benefit: a single service or a small team, a short-lived prototype, or stateless HTTP workloads that fit well on a serverless container platform like Cloud Run, Azure Container Apps or ECS on Fargate. Kubernetes needs ongoing work: version upgrades roughly three times a year, add-ons (ingress, monitoring, autoscalers), security policy and cost tuning. I would choose it when there are many services and teams, when we need portability across clouds or on-premises, or when we want its ecosystem, such as operators for Kafka or databases.

How to answer

Use the pattern "I would pick X because A; the cost is B; if C changes, I would switch to Y". Interviewers reward judgement more than enthusiasm.

Likely follow-ups
  • Managed Kubernetes vs self-managed: what do you still own on EKS/AKS?
  • ECS vs EKS for a new team on AWS?
Is a Kubernetes namespace the same as a Linux namespace?

No. A Linux namespace is a kernel feature that isolates what a process sees: PIDs, network stack, mounts, hostname, IPC, users. Containers are built from them. A Kubernetes namespace is an API-level grouping of objects, used to avoid name clashes and to attach RBAC permissions, resource quotas and network policies per team or environment. Pods in different Kubernetes namespaces can still run on the same node and share the same kernel, so a Kubernetes namespace is not a hard security boundary by itself.

How to answer

Say "no" clearly, define both in one sentence each, then add the security nuance. This shows you understand both the kernel and the platform.

Likely follow-ups
  • How would you isolate two teams on one cluster?
  • Which Linux namespaces do containers in one pod share?
"Kubernetes is self-healing." Explain exactly what heals and how fast.

There are two layers. Locally, the kubelet restarts a crashed container in the same pod, with exponential back-off from 10 seconds up to 5 minutes if it keeps failing. Globally, if a node stops renewing its Lease heartbeat, the node lifecycle controller marks it NotReady after the grace period (about 50 seconds by default), and pods are evicted after their default 300-second toleration for unreachable nodes. Then the ReplicaSet controller sees too few pods and creates new Pod objects, the scheduler binds them to healthy nodes, and those nodes' kubelets start them. So container restarts take seconds, but replacement after a node failure takes roughly 5-6 minutes by default. You can shorten it with per-pod tolerationSeconds, and you protect users by running several replicas across nodes and zones behind a Service with readiness probes.

How to answer

Name each component and what it writes. Give the default timings. End with how you design around them. This is where your networking-timer intuition shines.

Likely follow-ups
  • Why does Kubernetes wait so long?
  • What is different for a StatefulSet pod on a dead node?
  • How do readiness probes help users during this time?

Scenario: "Our startup has 2 services. The CTO wants Kubernetes."

The interviewer says: you are the first backend engineer at a startup with one web API and one background worker, about 50 requests per second, and two engineers. The CTO read that Kubernetes is the standard. What do you recommend?

Weak answer: "Kubernetes is the industry standard, so yes, let's set up a cluster with Helm, Istio and Prometheus."

Strong answer: "At 2 services and 50 RPS, the main risk is shipping product, not orchestration. I would containerize both with Docker so we are portable, and run them on a managed container service such as Cloud Run or ECS on Fargate, with a managed database. That gives us autoscaling and health checks with almost no ops. I would keep configs declarative in git. If we grow to many services or teams, or need things like custom controllers or Kafka on our own infrastructure, the containers move to managed Kubernetes with little change. I would revisit at a clear trigger, for example more than about 10 services or a platform team being formed." (The trigger number is a judgement call; say so.)

Likely follow-ups
  • What would make you switch earlier?
  • How do you avoid lock-in to the serverless platform?
