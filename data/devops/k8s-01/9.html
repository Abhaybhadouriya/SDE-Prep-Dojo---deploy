Under the hood of "self-healing" (no magic allowed)

Good to know (SDE-2)

A good systems engineer distrusts magic, and so should you. "Kubernetes heals the pod" is not an answer. Here is exactly who does what when the count drops from 3 to 2 because a container crashed and then the whole node died.

  1. Container crashes (local). The kubelet (the agent on each node) is told by the container runtime that the process exited. Because the pod's restartPolicy is Always, the kubelet restarts the container in the same pod, on the same node. If it keeps crashing, the kubelet waits longer each time (10 s, 20 s, 40 s, ... up to 5 minutes). That waiting state is the famous CrashLoopBackOff. Details in Pods.
  2. Node goes silent (global). Each kubelet renews a small Lease object (a tiny heartbeat record with a "last renewed" time) in the API server every few seconds as a heartbeat. The node lifecycle controller inside kube-controller-manager watches these. If a node has not renewed for the grace period (50 seconds by default in current versions), it marks the node NotReady and adds a taint to it (a taint is a "keep out" mark on a node; pods avoid tainted nodes unless they carry a matching toleration, an "I accept that mark" note. Page 09 covers both).
  3. Waiting to be sure. Every pod gets a default toleration for the "not-ready" and "unreachable" taints that lasts 300 seconds: it may stay bound to such a node for 5 minutes. Only after that are the pods on the dead node marked for deletion. Total: roughly 5-6 minutes from power loss to replacement, unless you tune it.
  4. Counting. The ReplicaSet controller (the controller whose only job is "keep N copies of this pod"; page 04) watches pods with its label. It now counts 2 healthy pods but wants 3, so it creates one new Pod object in the API server. Notice: it writes a record; it does not start anything.
  5. Placing. The kube-scheduler watches for Pod objects with no node assigned. It filters out nodes that cannot fit the pod, scores the rest, and writes the chosen node name into the pod (a "binding").
  6. Running. The kubelet on the chosen node is watching for pods assigned to it. It sees the new one and asks the container runtime to pull the image and start it.

See the pattern? No component calls another component directly. Each one watches the API server for objects it cares about, does one job, and writes its result back. That loose design is why Kubernetes survives partial failures so well. Page 02 Architecture animates the full chain.

From your world

The 50-second grace period plus 300-second toleration is exactly like hello and dead timers in OSPF, or BFD multipliers: short timers mean fast failover but more false alarms (flapping) on a busy or lossy network; long timers mean stability but slower recovery. Kubernetes chose safe defaults. For latency-critical apps you can lower tolerationSeconds per pod. Where the analogy breaks: Kubernetes cannot know whether a silent node is dead or just cut off, so for stateful apps it is deliberately extra careful (two copies writing the same disk would be worse than a short outage).
