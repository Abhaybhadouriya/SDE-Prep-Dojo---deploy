See it with your own eyes (lab)

Must know (SDE-1)

If you set up the kind cluster from the track overview, try this. We ask for 3 copies of the nginx web server, then we kill one and watch Kubernetes bring it back.

kubectl create deployment hello --image=nginx:1.27 --replicas=3
kubectl get pods -o wide
$ kubectl create deployment hello --image=nginx:1.27 --replicas=3
deployment.apps/hello created

$ kubectl get pods -o wide
NAME                     READY   STATUS    RESTARTS   AGE   IP           NODE
hello-6d8f7b9c54-4kq2m   1/1     Running   0          25s   10.244.1.3   dojo-worker
hello-6d8f7b9c54-9xvzt   1/1     Running   0          25s   10.244.2.2   dojo-worker2
hello-6d8f7b9c54-tp7lw   1/1     Running   0          25s   10.244.1.4   dojo-worker

(The real output has two more columns, NOMINATED NODE and READINESS GATES, trimmed here. Your pod names will be different random strings.) Now delete one pod, as if it crashed, and look again:

kubectl delete pod hello-6d8f7b9c54-4kq2m
kubectl get pods
$ kubectl delete pod hello-6d8f7b9c54-4kq2m
pod "hello-6d8f7b9c54-4kq2m" deleted

$ kubectl get pods
NAME                     READY   STATUS    RESTARTS   AGE
hello-6d8f7b9c54-9xvzt   1/1     Running   0          2m
hello-6d8f7b9c54-tp7lw   1/1     Running   0          2m
hello-6d8f7b9c54-zr8nd   1/1     Running   0          4s

Look at the last line: a brand-new pod with a new name, only 4 seconds old. You never asked for it. A controller saw "want 3, have 2" and made one. Now change the desired state:

$ kubectl scale deployment hello --replicas=5
deployment.apps/hello scaled

$ kubectl get deployment hello
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   5/5     5            5           3m

Want to see a whole "server" die? In kind, a node is just a Docker container, so you can stop it:

$ docker stop dojo-worker2
dojo-worker2

$ kubectl get nodes        # wait about a minute
NAME                 STATUS     ROLES           AGE   VERSION
dojo-control-plane   Ready      control-plane   20m   v1.35.0
dojo-worker          Ready      <none>          20m   v1.35.0
dojo-worker2         NotReady   <none>          20m   v1.35.0

Keep running kubectl get pods -o wide. You will see the node go NotReady after roughly 50 seconds, and the pods on it get replaced on dojo-worker only after about 5 more minutes. That delay is on purpose, and it is a famous interview question. Run docker start dojo-worker2 to bring the node back, and kubectl delete deployment hello to clean up.

The declarative way: real teams do not type kubectl create and kubectl scale. They keep a YAML file in git and run kubectl apply -f hello.yaml. Change replicas: 3 to replicas: 5 in the file, apply again, and Kubernetes moves reality to match. This is called GitOps when a tool (like Argo CD or Flux) applies git automatically.

# hello.yaml - the same thing, written as desired state
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 3                 # "I always want 3 copies"
  selector:
    matchLabels:
      app: hello              # "the copies are the pods with this label"
  template:                   # "and each copy looks like this"
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
$ kubectl apply -f hello.yaml
deployment.apps/hello created
$ kubectl apply -f hello.yaml        # run it again, nothing changed
deployment.apps/hello unchanged

Notice the second apply says unchanged. Applying the same desired state twice is safe. That property is called idempotent (doing it once or ten times gives the same result), and it is why declarative config is easy to automate.

What are all those fields? Every Kubernetes object has the same five parts: apiVersion, kind, metadata, spec (what you want) and status (what the cluster reports back). The Anatomy of an object section on the next page walks through this file field by field.
