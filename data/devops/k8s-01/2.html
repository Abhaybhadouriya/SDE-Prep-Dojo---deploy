"Can't I just write a shell script?"

Must know (SDE-1)

This is the most honest question, and it is probably the first one you will ask. Let us try. A first script might be: SSH into each server, run docker run, done. It works on Monday. Then real life happens. Click through the stepper to see the same 3 a.m. failure handled two ways.

Six words you need first

  • Cluster = the whole group of machines Kubernetes manages, seen as one big computer.
  • Node = one machine in that group (a real server or a VM). In the picture below, node-1, node-2, node-3.
  • Pod = the small box Kubernetes runs your container in. One copy of your app = one pod. (Full page: Pods.)
  • Control plane = the "brain" machines. They store what you asked for and decide where things run. They do not run your app.
  • kubelet = a small agent program on every node. It starts the pods the brain asks for and reports "I am alive" every few seconds.
  • kubectl (say "cube-control") = the command-line tool you type, to talk to the control plane. Do not mix it up with kubelet, which runs on the nodes.

From your world

Cluster = a chassis. Node = a line card. Control plane = the route processor. kubelet = the line-card agent that programs the hardware and sends keepalives. kubectl = the CLI you log in to. Pod = one forwarding instance running on a card.

  1. Normal day. Both worlds run 3 copies of the shop app on 3 servers.
  2. 3 a.m. One server loses power. Its copy of the app is gone in both worlds.
  3. Detection. The script ran once and is not watching anything. In Kubernetes, each node's agent (the kubelet) sends regular heartbeats; when they stop, the control plane marks the node NotReady.
  4. Decision. In script world, a human gets paged. In Kubernetes, a controller sees "I want 3 copies, I can count 2 healthy ones" and creates a replacement.
  5. Repair. A human picks a server by hand at 3:20 a.m. Kubernetes' scheduler picks a node with free room, and the kubelet there starts the new copy. Nobody woke up.

You could, of course, keep improving the script. You would add a loop that checks every server. Then a list of which app runs where. Then a way to store that list so it survives a crash. Then a voting system so two copies of your script do not fight. Then health checks, then rolling upgrades, then a way for apps to find each other... Ten years later you would have written your own Kubernetes. Google did exactly that, twice: an internal system called Borg, and later the open-source Kubernetes, which they announced in 2014 and gave to the Cloud Native Computing Foundation (CNCF), a neutral home under the Linux Foundation.

From your world

Think of a chassis router. You do not tell each line card "forward this packet to port 7". You configure intent (routes, policies) on the route processor. The routing daemons compute the RIB, and a separate process keeps pushing the result into each line card's FIB. If a line card reboots, that process notices and re-programs it. Kubernetes works the same way: you store intent in the API, and controllers keep pushing reality toward it. Where this breaks: a FIB update takes microseconds; Kubernetes reconciles in seconds, because it is starting whole processes on remote machines.
