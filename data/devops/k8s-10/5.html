Operators: a controller with expert knowledge

Good to know (SDE-2)

Every built-in object already works this way. The Deployment controller watches Deployments and makes ReplicaSets. The StatefulSet controller watches StatefulSets and makes pods and PVCs. An operator is the same pattern for your own CRD: watch the custom resource, compare desired vs actual, act, write status, repeat.

Key properties of a well-built operator:

  • Level-triggered, idempotent. Running reconcile twice must be safe. "Ensure a Service named X exists" - not "create a Service".
  • Informers and a work queue. Client libraries keep a local cache of watched objects and push object keys into a queue; reconcile is called with a key, re-reads state and acts. Failed keys are retried with backoff, and a periodic resync catches anything missed.
  • Owner references. Objects the operator creates point back to the CR, so deleting the CR garbage-collects them.
  • Finalizers let the operator clean up outside things (a cloud bucket, a Kafka topic) before the CR disappears.
  • Status. The operator reports progress in .status (conditions such as Ready), which is how kubectl wait and other tools know it is done.
// The heart of an operator built with controller-runtime (Kubebuilder / Operator SDK).
func (r *BackupReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var b examplev1.Backup
    if err := r.Get(ctx, req.NamespacedName, &b); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err) // deleted: nothing to do
    }
    cron := desiredCronJob(&b)                            // what SHOULD exist
    if err := ctrl.SetControllerReference(&b, cron, r.Scheme); err != nil {
        return ctrl.Result{}, err
    }
    if err := r.applyCronJob(ctx, cron); err != nil {   // create or patch to match
        return ctrl.Result{}, err                         // returned error = retried with backoff
    }
    b.Status.Ready = true
    return ctrl.Result{}, r.Status().Update(ctx, &b)
}

From your world

An operator is a routing daemon. The CR is the configured intent (like the running config), the operator is the daemon that computes and programs state, and the objects it creates are the FIB entries pushed to hardware. Like a good daemon, it listens for events (netlink, watches) and does periodic full syncs, because events can be lost. If the daemon dies, forwarding continues on the last programmed state - and if the operator pod dies, Kafka keeps running; only changes and self-healing pause. Where this breaks: an operator acts through the API server, so it can only do what its RBAC allows, and its "hardware" is other Kubernetes objects.

The operator maturity ladder

The Operator Framework describes five capability levels. It is a handy way to judge any operator in an interview:

  1. Basic install - creates the app from a CR.
  2. Seamless upgrades - upgrades the app and the operator safely.
  3. Full lifecycle - backups, restore, failure recovery, scaling.
  4. Deep insights - metrics, alerts, logs about the app.
  5. Auto pilot - auto-scaling, auto-tuning, rebalancing without humans.

Well-known operators: Strimzi (Kafka), Prometheus Operator (monitoring, Observability), cert-manager (TLS certificates), CloudNativePG (PostgreSQL), Argo CD (GitOps; its Application is a CRD). Frameworks to build your own: Kubebuilder and Operator SDK, both on top of controller-runtime. Browse more on OperatorHub.
