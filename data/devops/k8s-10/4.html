CRDs: teaching Kubernetes new words

Good to know (SDE-2)

Kubernetes ships with nouns like Pod, Service and Deployment. A CustomResourceDefinition (CRD) adds a new noun to the API server, with a schema. After you install a CRD, the API server will store, validate and serve objects of that kind exactly like built-in ones - in etcd, with RBAC, with kubectl get and watch.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.example.com
spec:
  group: example.com
  scope: Namespaced
  names: { plural: backups, singular: backup, kind: Backup, shortNames: [bk] }
  versions:
    - name: v1
      served: true
      storage: true
      subresources: { status: {} }
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                database: { type: string }
                schedule: { type: string }
                retainDays: { type: integer, minimum: 1 }
$ kubectl apply -f backup-crd.yaml
customresourcedefinition.apiextensions.k8s.io/backups.example.com created
$ kubectl apply -f - <<'EOF'
apiVersion: example.com/v1
kind: Backup
metadata: { name: orders-nightly }
spec: { database: orders, schedule: "0 2 * * *", retainDays: 14 }
EOF
backup.example.com/orders-nightly created
$ kubectl get bk
NAME             AGE
orders-nightly   3s

And... nothing happens. No backup runs. A CRD is only a noun: it stores your wish. Something has to read the wish and act. That something is a controller, and a controller that encodes expert knowledge about one application is called an operator.
