Redraw this in 30 seconds

Six boxes. An operator is a controller for your own resource type; a StatefulSet gives each pod a fixed name and its own disk.

Deployment vs StatefulSet - when do you use each?

Deployment for interchangeable pods: web APIs, workers whose state lives elsewhere. StatefulSet when each replica has an identity: stable ordinal name, stable DNS through a headless Service, its own PVC that follows it, and ordered start, stop and updates. Typical StatefulSet workloads are databases, Kafka brokers, Elasticsearch, etcd-like quorums. In practice these are usually run through an operator, which builds on the same ideas and adds application knowledge.

How to answer

Give the "cattle vs pets" one-liner, then list the four guarantees. End with "and in production I would use an operator such as Strimzi".

Likely follow-ups
  • Why does a StatefulSet need a headless Service?
  • What happens to the PVCs when you delete a StatefulSet?
A node running kafka-1 (a StatefulSet pod) goes NotReady. What happens, and why is it different from a Deployment?

The node controller marks the node NotReady after the heartbeat grace period, and after the default 300 s toleration the pod is marked for deletion. For a Deployment, the ReplicaSet controller immediately creates a replacement with a new name elsewhere. For a StatefulSet, the controller will not create a new kafka-1 until the old one is confirmed gone, because the node might be partitioned rather than dead and two pods with the same identity could corrupt data - StatefulSets guarantee at most one. Recovery comes when the node returns, the Node object is deleted, the out-of-service taint is applied, or an admin force-deletes after fencing. Meanwhile Kafka itself fails over partition leadership to in-sync replicas on other brokers, so clients keep working.

How to answer

Timeline first (detection, eviction), then the "at most one" reason with the split-brain word, then what the application does meanwhile. This shows you understand both layers.

Likely follow-ups
  • When is force-deleting safe?
  • How would you make failover faster? (Tune tolerations carefully, rely on app-level replication.)
What is a CRD, what is an operator, and how is an operator different from a Helm chart?

A CRD adds a new resource type to the Kubernetes API, so users can store objects like Kafka or Backup with a schema, RBAC and watch support. An operator is a controller - a program running in the cluster - that watches those objects and continuously reconciles the real world toward them, encoding the operational knowledge of a specific application: upgrades, failover, scaling, backups. A Helm chart is a templating and packaging tool: it renders YAML once at install or upgrade time and then walks away. Helm is a one-time "install"; an operator is an always-on "operate". They are often combined: Helm installs the operator.

How to answer

"CRD is the noun, the operator is the verb, Helm is the delivery truck." Then one example (Strimzi).

Likely follow-ups
  • What does level-triggered reconciliation mean?
  • What happens to the app if the operator pod crashes?
Explain the reconcile loop. What does "level-triggered" mean and why does it matter?

A controller watches objects through informers, puts the key of any changed object into a work queue, and a reconcile function reads the current desired state and actual state and makes changes to close the gap, then updates status. Level-triggered means it reacts to the current state, not to the specific event: "there should be 3 pods and there are 2" rather than "a pod was deleted". So missed or duplicated events do not matter, a restart halfway is harmless, and periodic resyncs repair drift. That forces reconcile to be idempotent. Uber described forcing reconciles every 15 minutes after finding missed events during controller leader changes - a practical reason resync exists.

How to answer

Use the thermostat analogy, then the edge vs level distinction, then one consequence (idempotency).

Likely follow-ups
  • How do you avoid two operator replicas acting at once? (Leader election with a Lease.)
  • What are finalizers for?
How would you run Kafka on Kubernetes, and what is hard about it?

I would use the Strimzi operator rather than hand-written manifests. Separate node pools: three or more KRaft controllers, and brokers sized for throughput, spread across zones with rack awareness, each with its own SSD PVC. RF=3 and min ISR 2. The hard parts: stable per-broker identity and storage (operator plus StrimziPodSets), rolling restarts that keep every partition in sync (the operator checks before each restart, and Drain Cleaner routes node drains through it), clients outside the cluster needing per-broker addresses, partition rebalancing when adding brokers (Cruise Control), and storage performance and zone pinning. If the team is small, I would also weigh a managed Kafka service - the trade-off is control and cost versus operational load.

How to answer

Lead with "operator, not StatefulSet by hand", then list hard parts as identity, rolling, networking, balancing, storage. Close with the managed-service trade-off.

Likely follow-ups
  • Why did Strimzi stop using StatefulSets?
  • How do you scale consumers? (See KEDA on lag.)

Scenario: producers outside the cluster time out after "connecting"

A team exposed the Strimzi bootstrap Service through a single cloud load balancer. Their producer logs show a successful bootstrap connection, then repeated timeouts connecting to addresses like my-cluster-broker-4.my-cluster-kafka-brokers.kafka.svc:9092.

Weak answer: "The load balancer is broken; increase the timeout."

Strong answer: "The bootstrap step worked, so the LB is fine. The metadata response is advertising internal cluster DNS names, which the external client cannot resolve or route to. Kafka clients must reach each partition leader directly. I would add an external listener in the Kafka CR (type loadbalancer or nodeport, with TLS), which creates one address per broker and sets each broker's advertised listener to it, then point the client at the new bootstrap address."

Likely follow-ups
  • What are the cost implications of one load balancer per broker? (NodePort or a single ingress with TLS passthrough and SNI are alternatives.)

Scenario: a rolling upgrade stalled with kafka-2 in CrashLoopBackOff

A hand-rolled Kafka StatefulSet was updated with a new image and a config change. kafka-2 was replaced first and now crash-loops. kafka-1 and kafka-0 are still on the old version. Producers with acks=all see some errors.

Weak answer: "Delete all the pods so they restart with the new config."

Strong answer: "The StatefulSet stopped at the first unhealthy pod, which protects the others - good. Producers fail on partitions where the remaining in-sync replicas drop below min ISR. Mitigate first: revert the template to the old image and config (or kubectl rollout undo), then delete kafka-2 so it comes back on the old spec, and wait for under-replicated partitions to reach zero. Then read kubectl logs kafka-2 --previous for the real error. Next time use the partition field to canary one broker, and move to an operator whose rolling logic checks ISR before each restart."

Likely follow-ups
  • Why did the StatefulSet start with kafka-2? (Rolling updates go from the highest ordinal down.)

60-second answer - "How do you run stateful systems like Kafka on Kubernetes?"
"Deployments assume interchangeable pods, but a Kafka broker has an identity and its own data. A StatefulSet gives each pod a stable ordinal name, a stable DNS name through a headless Service, its own PVC from a claim template that re-attaches when the pod is recreated, and ordered start and updates. It also guarantees at most one pod per identity, so if a node is unreachable it will not start a duplicate until the old one is fenced. For Kafka specifically I would use an operator like Strimzi: I declare a Kafka resource and node pools as CRDs, and the operator's reconcile loop creates the brokers, certificates, services and disruption budget, does rolling restarts that never drop a partition below min ISR, manages topics and users, and exposes per-broker addresses to external clients. Kafka's own replication across zones gives the durability."
