The four StatefulSet guarantees

Must know (SDE-1)
GuaranteeHow it is doneExample
Stable namePods are named <set>-<ordinal>, from 0 to N-1kafka-0, kafka-1, kafka-2
Stable network identityA headless Service (clusterIP: None) gives each pod a DNS recordkafka-1.kafka-headless.kafka.svc.cluster.local
Stable storagevolumeClaimTemplates create one PVC per pod, named <template>-<pod>data-kafka-1 always mounts into kafka-1
OrderingDefault podManagementPolicy: OrderedReady: create 0, wait for Ready, then 1...; delete in reversekafka-2 stops first on scale-down

Try it: a small StatefulSet

apiVersion: v1
kind: Service
metadata:
  name: web-headless
spec:
  clusterIP: None              # headless: DNS returns pod IPs, no virtual IP
  selector: { app: web }
  ports: [{ port: 80, name: http }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web-headless    # links the pods' DNS names to this Service
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports: [{ containerPort: 80, name: http }]
          volumeMounts:
            - { name: data, mountPath: /usr/share/nginx/html }
  volumeClaimTemplates:        # one PVC per pod, created automatically
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 1Gi } }

Watch the order: web-1 was not even created until web-0 was Running and Ready. Now the important test - kill a pod:

$ kubectl exec web-1 -- sh -c 'echo "I am web-1" > /usr/share/nginx/html/index.html'
$ kubectl delete pod web-1
pod "web-1" deleted
$ kubectl get pods -l app=web
NAME    READY   STATUS    RESTARTS   AGE
web-0   1/1     Running   0          5m
web-1   1/1     Running   0          4s
web-2   1/1     Running   0          5m
$ kubectl exec web-1 -- cat /usr/share/nginx/html/index.html
I am web-1

Same name, same disk, same data. Its IP may have changed, but its DNS name did not - which is why stateful systems are configured with DNS names, never pod IPs.

  1. Ordinal 0 first. The StatefulSet controller (inside kube-controller-manager) creates data-kafka-0 from the claim template, then pod kafka-0 that mounts it.
  2. Wait for Ready. Only when kafka-0 passes its readiness probe does the controller create kafka-1 and its claim.
  3. And so on. kafka-2 comes last. Scale-down and deletion go the other way: 2, then 1, then 0.
  4. A pod dies. kafka-1 is deleted (a crash, an eviction, or you). Its PVC is not deleted - the disk keeps the partition data.
  5. Same identity returns. The controller recreates a pod called exactly kafka-1, which mounts data-kafka-1 again. Kafka sees broker 1 come back with its log and only needs to catch up on what it missed.

You might confuse this with... a headless Service and a normal Service. A normal Service has a virtual ClusterIP and load-balances across pods - good when any pod will do. A headless Service has clusterIP: None: DNS returns the pod IPs directly, and each StatefulSet pod gets its own name. Kafka clients must reach the leader of a partition, a specific broker, so brokers are addressed through a headless Service (see Services & Networking).
