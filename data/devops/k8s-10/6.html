Strimzi: Kafka on Kubernetes, the operator way

Deep dive (platform teams)

Deep dive - skip on first pass. This section assumes a little Kafka. If you have not done the Kafka track yet, read the box below, finish the rest of this page, and come back after Why messaging? and KRaft.

Kafka in 30 seconds (just enough for this section)

  • A broker is one Kafka server. A cluster has several. Apps write messages into named topics.
  • Each topic is split into partitions (ordered, append-only logs). Partitions are spread over brokers, so more partitions means more parallel work.
  • Each partition is copied to N brokers (replicas). One copy is the leader; clients read and write through it. The copies that are fully caught up are the ISR (in-sync replicas). min.insync.replicas is how many ISR copies must confirm a write before Kafka says "OK" - restarting a broker can push a partition below that number.
  • KRaft is Kafka's built-in metadata quorum (Raft, like etcd). Some nodes run the controller role (they hold cluster metadata), others the broker role (they hold data); a dev node can do both. The old external ZooKeeper is gone in Kafka 4.
  • Other names you will see: listeners (the ports and protocols a broker accepts clients on), ACLs (per-user permissions on topics), JBOD ("just a bunch of disks": a list of separate volumes per broker), Cruise Control (a tool that moves partitions to balance brokers) and MirrorMaker 2 (copies topics between clusters).

Running Kafka with a hand-written StatefulSet is possible, but you would have to solve these yourself: unique broker config per pod, TLS certificates, rolling restarts that never take a partition below its minimum in-sync replicas, moving partitions when you add brokers, creating topics and users, and exposing each broker to clients outside the cluster. Strimzi (a CNCF project; version 1.3.x in late 2026, KRaft only, no ZooKeeper) packages that knowledge into operators.

Strimzi CRDWhat it describes
KafkaThe cluster: Kafka version, listeners, cluster-wide config, Entity Operator

KafkaTopic, KafkaUserTopics (partitions, replicas, config) and users (auth, ACLs)

Hands-on: Kafka on kind in five commands

These are the commands from the official Strimzi quickstart (checked November 2026). The example cluster is a single dual-role node - fine for a laptop, never for production.

kubectl create namespace kafka
kubectl create -f 'https://strimzi.io/install/latest?namespace=kafka' -n kafka      # CRDs + Cluster Operator
kubectl apply -f https://strimzi.io/examples/latest/kafka/kafka-single-node.yaml -n kafka
kubectl wait kafka/my-cluster --for=condition=Ready --timeout=300s -n kafka
kubectl get pods -n kafka -w      # watch the operator create the node pod and the Entity Operator (Ctrl+C to stop)

The example file contains two CRs (trimmed here; the full file sets a few more replication defaults to 1):

apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: dual-role
  labels:
    strimzi.io/cluster: my-cluster      # which Kafka cluster this pool belongs to
spec:
  replicas: 1
  roles: [controller, broker]           # KRaft controller + broker in one node (dev only)
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim          # a PVC from the default StorageClass
        size: 100Gi
        kraftMetadata: shared
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: my-cluster
spec:
  kafka:
    version: 4.3.2
    listeners:
      - { name: plain, port: 9092, type: internal, tls: false }
      - { name: tls,   port: 9093, type: internal, tls: true }
    config:
      default.replication.factor: 1
      min.insync.replicas: 1
  entityOperator:
    topicOperator: {}
    userOperator: {}

What the Cluster Operator does on each reconcile

  1. Read intent. The Cluster Operator watches Kafka and KafkaNodePool resources (and runs a periodic full reconcile anyway). A new or changed CR starts a reconcile of that cluster.
  2. Certificates. It creates (and later renews) a cluster CA and a TLS certificate for every node, stored in Secrets - something you would otherwise script by hand.
  3. Config and plumbing. It renders a separate config for each node (node ID, roles, listeners, advertised hostnames), plus the bootstrap and headless Services and a PodDisruptionBudget.
  4. Pods via StrimziPodSets. Instead of StatefulSets, it manages pods through its own StrimziPodSet resource, so each node can have its own config and storage and any specific node can be removed - not only the highest ordinal.
  5. Safe rolling restarts. When a change needs a restart (new version, new config, renewed certs), it rolls nodes one at a time and, before restarting a broker, checks that doing so will not leave any partition under its min.insync.replicas. A plain StatefulSet rolling update knows nothing about Kafka and would happily restart a broker whose partitions are already short of replicas.
  6. Report. It writes conditions and listener addresses into .status of the Kafka CR. That is what kubectl wait --for=condition=Ready was waiting for.

Why Strimzi left StatefulSets behind

Strimzi originally used StatefulSets and replaced them with StrimziPodSets (introduced in 0.29, May 2022). The project's design proposal lists the limits it kept hitting - and they are excellent interview material because they show where StatefulSets stop:

StatefulSet gives you
  • Stable names, DNS, per-pod PVCs
  • Ordered start and rolling updates
  • At-most-one pod per identity
  • A built-in, well-understood controller
Where it hurt Kafka
  • Scale-down only removes the highest ordinal - you cannot retire broker 1 specifically
  • Broker IDs tied to the pod index
  • One template: every pod gets identical config and mounts
  • Changing storage layout needed fragile workarounds
  • Hard to build mixed controller/broker roles and stretch clusters

The trade-off: StrimziPodSets are reconciled by the Strimzi operator, not by kube-controller-manager, so the operator becomes a critical component. If it is down, running brokers keep serving, but nothing heals or changes until it returns.

Production checklist for Kafka on Kubernetes

  • Separate node pools: a dedicated pool of at least three controllers, separate broker pool(s). Dual-role nodes are for development.
  • Replication: default.replication.factor: 3, min.insync.replicas: 2, producers with acks=all (Delivery semantics).
  • Rack awareness: set rack.topologyKey: topology.kubernetes.io/zone so Kafka places the replicas of each partition in different zones, and spread pods across zones.
  • Storage: one PVC per broker, WaitForFirstConsumer, SSD class, Retain or deleteClaim: false, expansion allowed.
  • Disruptions: keep the PDB the operator creates, and use the Strimzi Drain Cleaner so node drains hand broker evictions to the operator, which rolls them safely instead of Kubernetes evicting them blindly.
  • Balance: after adding brokers, new brokers get no existing partitions until you move some - use KafkaRebalance (Cruise Control).
  • Monitoring: metrics exporter, consumer lag alerts (Kafka operations).

So... is running Kafka on Kubernetes a good idea?

This is a real interview question, and there is no single right answer - the interviewer wants to hear you weigh it. The honest summary: it is a reasonable, widely used choice if the team already runs Kubernetes well and uses a mature operator such as Strimzi. It is a poor choice if Kubernetes itself is new to the team, because now two hard distributed systems can fail at once.

Good reasons to do it
  • One platform: the same deploy, monitoring, RBAC and GitOps flow as every other service
  • The operator encodes Kafka know-how: safe rolling restarts, certificate rotation, users and topics as YAML
  • Easy to create short-lived clusters for dev and CI
  • Self-healing: a lost broker pod comes back with its own disk
Reasons to think twice
  • Brokers are long-lived and disk-heavy; Kubernetes is happiest with disposable pods
  • Node drains, upgrades and evictions can restart brokers more often than on VMs
  • Networking for external clients is harder (per-broker addresses, see below)
  • Storage performance depends on the CSI driver and disk type you choose
  • A managed service (Amazon MSK, Confluent Cloud, Azure Event Hubs for Kafka) removes the work entirely

Strong answer shape: "It depends on the team. If we already operate Kubernetes in production, I would run Kafka with Strimzi: dedicated node pools, one PVC per broker on SSD, rack awareness across zones, PDBs plus Drain Cleaner. If we are small or new to Kubernetes, I would pick a managed Kafka and spend the effort on the product."

The #1 Kafka-on-Kubernetes gotcha: clients outside the cluster

A Kafka client first connects to any broker (the bootstrap address) and asks for metadata. The answer lists each broker's advertised address, and the client then connects directly to the leader of each partition it needs. That means a single load-balanced address is not enough: every broker must be individually reachable from where the client runs.

From your world

This is the classic NAT problem with protocols that carry addresses in the payload (like FTP's PORT command or SIP's SDP): the control conversation tells the peer "now talk to 10.244.1.7", which is meaningless outside the private network. The fix is the same idea as an ALG or a proper public mapping: advertise addresses that are valid from the client's side, one per broker.
