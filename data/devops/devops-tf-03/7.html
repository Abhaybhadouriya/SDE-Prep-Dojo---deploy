Interview questions

What is a Terraform module, and what makes a module good?

A module is a folder of Terraform files with input variables, resources and outputs. The folder you run Terraform in is the root module; it calls child modules with module blocks. A good module does one job (a VPC, an EKS cluster, a service behind a load balancer), exposes a small set of typed, validated inputs with sensible defaults, outputs everything a caller needs (ids, ARNs, DNS names), does not declare providers itself, and does not hard-code environment names. It is versioned with semantic tags and has automated checks (fmt, validate, tflint, ideally terraform test). Wrapping a single resource just to rename arguments is an anti-pattern.

How to answer

Definition in one line, then the "good module" checklist, then one concrete example from your experience (a VPC module with CIDR and AZ inputs and subnet-id outputs).

Likely follow-ups
  • Why should child modules not configure providers?
  • How do you test a module?
  • When is a module too big?
How do you version and roll out a shared module used by many teams?

Put modules in a repo (or a private registry), release them with semver tags, and have every caller pin a version: version = "~> 2.3" for registry sources, ?ref=v2.3.0 for Git sources (the version argument does not work for Git). Breaking changes bump the major version and come with a changelog and upgrade notes. Callers upgrade by bumping the pin in a PR and reviewing the plan; dev first, then staging, then prod. Renovate or Dependabot can open those PRs. Note that the dependency lock file pins providers, not modules, so module constraints must be tight.

How to answer

Treat it as library release management: semver, pinning, changelog, staged promotion. Mention the lock-file gotcha; it shows real experience.

Likely follow-ups
  • What does ~> mean exactly?
  • A team pinned ?ref=main. What can go wrong?
  • How do you deprecate an input?
Workspaces or separate folders for dev, staging and prod? Defend your choice.

For long-lived environments I use one root module (folder) per environment, each with its own backend, ideally in its own AWS account and with its own IAM role, calling shared versioned modules. CLI workspaces separate state but share the backend and credentials, so they give no access isolation; the current workspace is invisible in the folder, which makes "applied dev change to prod" easy; and every environment must run the same code version, so you cannot roll a module upgrade through dev first. HashiCorp's docs also say workspaces are not suitable when deployments need separate credentials and access controls. I do use workspaces for short-lived copies: a per-PR preview stack or a developer sandbox. The cost of folders is some duplicated wiring, which modules (or Terragrunt) keep small.

How to answer

Give your pick, three concrete reasons (access isolation, visibility, staged rollout), cite the docs' guidance, then concede where workspaces are good. Balanced answers score higher than dogma.

Likely follow-ups
  • Where does the S3 backend store non-default workspace state?
  • How does an HCP Terraform workspace differ from a CLI workspace?
  • How do you keep three folders from drifting apart in code?
What is drift, how do you detect it, and what do you do when you find it?

Drift is when real infrastructure differs from Terraform state and code, usually from a manual console change, another tool changing the same field, or a resource deleted by hand. Terraform only sees it when it refreshes during a plan. I detect it with a scheduled CI job that runs terraform plan -detailed-exitcode per stack with a read-only role (exit code 2 means a diff) and alerts; plan -refresh-only shows just the outside changes. Then a human decides: revert (normal apply, code wins), or codify (update the code so plan shows no changes), or rarely accept into state with apply -refresh-only. New hand-made objects come in with an import block. To keep alerts meaningful I add ignore_changes for fields another system owns, like ASG desired capacity. Prevention matters most: read-only console in prod and an audited break-glass role.

How to answer

Definition, causes, detection (exit code 2), the three remediation choices, noise control, prevention. That order covers what most interviewers probe.

Likely follow-ups
  • Why not just run terraform apply on a schedule to auto-revert?
  • What is the difference between apply -refresh-only and the old terraform refresh?
  • How do you find who made the manual change? (CloudTrail)
Design a CI/CD pipeline for Terraform. How do you make apply safe?

On every pull request CI runs fmt, validate, tflint and a security scanner, then terraform plan -out=tfplan for each affected stack, posts terraform show output as a PR comment and runs policy checks on terraform show -json (for example: no destroys of databases, no public SSH). A human approves. On merge, CI applies the saved plan from that run, so what is applied is exactly what was reviewed; if state changed meanwhile, Terraform rejects the stale plan and we re-plan. Only CI can assume the apply role (OIDC, no static keys); humans get read-only. State is remote with locking and split by environment and layer. Prod applies can require a second approval through an environment protection rule. Stateful resources have prevent_destroy plus provider deletion protection.

How to answer

Walk the pipeline left to right, then list guard rails: saved plan, policy, least privilege, state isolation, lifecycle protections. Draw the PR-plan-review-merge-apply line if there is a whiteboard.

Likely follow-ups
  • Saved plans contain secrets. How do you store them?
  • Two PRs touch the same stack. What happens?
  • How do you handle a monorepo with 80 stacks? (only plan changed folders)
What does prevent_destroy do, and why is it not enough on its own?

lifecycle { prevent_destroy = true } makes Terraform error out on any plan that would destroy that resource, including replacements caused by changing a "forces replacement" attribute and terraform destroy. It is not enough because lifecycle settings live in code, not state: if someone deletes the whole resource block, the protection disappears with it and the plan destroys the object. So I pair it with provider-side protection (RDS deletion_protection, EC2 termination protection, S3 Object Lock), backups, a policy-as-code rule in CI that blocks destroy actions on stateful types, and a removed block with destroy = false when we genuinely want to stop managing something.

How to answer

What it does, the hole, then defence in depth. Mention create_before_destroy and ignore_changes briefly if time allows.

Likely follow-ups
  • When would you use create_before_destroy?
  • How do you rename a resource without destroying it? (moved block)
When is terraform apply -target acceptable?

Only in exceptional situations: recovering from a mistake, breaking a dependency cycle during a migration, or an emergency where a full plan is blocked by an unrelated broken resource. Terraform's docs call it not recommended for routine use, because everything outside the target is skipped, so drift and pending changes go unnoticed and state can diverge from code. After a targeted apply I immediately run a full plan and expect "No changes". If I just need to recreate one degraded object, -replace=ADDRESS is better because it still plans everything. If people reach for -target routinely, the state is too big and should be split.

How to answer

Say "exceptional only", explain why, give the safer alternatives (-replace, smaller states).

Likely follow-ups
  • What does -target include besides the target itself? (all its dependencies)
Your company has one 4,000-resource Terraform state. Plans take 25 minutes and engineers fight over the lock. What do you do?

Split the state by environment and layer (network, data, cluster, per-team app stacks) so each plan refreshes hundreds of resources, not thousands, and teams lock only their own stack. Mechanically: create the new root modules with their own backends; move resources with terraform state mv across states (or, per stack, removed blocks with destroy = false in the old config plus import blocks in the new one), one layer at a time, starting with the most stable (network); after each move both old and new stacks must plan "No changes". Upper layers read lower layers through data sources or remote-state outputs. Then CI plans only stacks whose folders changed. Result: faster plans, fewer lock conflicts, smaller blast radius, and per-stack IAM roles become possible.

How to answer

Diagnose (refresh cost, lock contention, blast radius), propose the target layout, explain a safe migration with a "no changes" check after each step, and close with the benefits.

Likely follow-ups
  • How do you share values between stacks without tight coupling?
  • How do you prevent the migration from destroying anything? (backups of state, plan review, prevent_destroy)

Interviewers love this: "I never apply a plan I have not reviewed, and I never let a human apply prod." Then explain saved plans, CI-only apply roles and policy checks. It shows you think about process, not just syntax.

Scenario: someone hand-edited a security group; plan shows drift

The nightly drift job opens an alert: terraform plan on prod/network wants to remove an ingress rule allowing port 5432 from 10.30.0.0/16 on the database security group. Nobody has a PR for it.

Weak answer: "Run apply to put it back."

Strong answer: First find out why the rule exists before deleting it: CloudTrail shows who called AuthorizeSecurityGroupIngress and when; maybe an on-call engineer opened it during an incident for a new analytics VPC. Applying blindly could cause an outage. Then decide: if the change was wrong, apply the code and the rule goes; if it was needed, codify it in a PR (a new aws_vpc_security_group_ingress_rule) so plan shows no changes. Finally close the gap: remove console write access in prod (read-only roles, break-glass with audit), keep the scheduled drift plan, and consider an SCP or Config rule for SG changes outside the CI role.

Likely follow-ups
  • How does Terraform notice drift at all? (Refresh reads the real object and compares it with state and code.)
  • What about attributes you want Terraform to ignore? (lifecycle { ignore_changes = [...] }, used sparingly.)
