Safe apply: plan review in CI, saved plans and blast radius

Good to know (SDE-2)

At small scale, people run terraform apply from their laptops. At scale that breaks: nobody knows who changed what, credentials live on laptops, and two people can apply different branches. The grown-up pattern is "plan on pull request, apply the reviewed plan on merge", run only by CI.

  1. An engineer opens a pull request with the change. Nobody runs apply from a laptop.
  2. CI runs terraform plan -out=tfplan with a read-only role and posts the plan text on the PR. The binary plan is kept as an artifact.
  3. Policy as code checks the plan (terraform show -json tfplan) with Checkov, OPA/Conftest or Sentinel: no public buckets, no destroying databases, required tags.
  4. A human reads the plan, not just the code diff, and approves. Merge.
  5. CI assumes the apply role and runs terraform apply tfplan: exactly the plan that was reviewed. If the state moved meanwhile, Terraform refuses the stale plan.
  6. After apply, a scheduled plan (-detailed-exitcode) proves there is no drift and alerts if someone changes things by hand later.

Saved plans: apply exactly what was reviewed

Plain terraform apply makes a new plan and applies it. Between your review and the apply, the world may have changed (another merge, drift), so you could apply something nobody saw. A saved plan fixes this:

$ terraform plan -input=false -out=tfplan
...
Plan: 2 to add, 1 to change, 0 to destroy.

Saved the plan to: tfplan

To perform exactly these actions, run the following command to apply:
    terraform apply "tfplan"

$ terraform show -no-color tfplan > plan.txt      # human-readable, for the PR comment
$ terraform show -json tfplan > plan.json         # machine-readable, for policy checks
$ terraform apply -input=false tfplan

If the state changed after the plan was made (someone else applied), Terraform refuses the saved plan with a "Saved plan is stale" error, which is what you want: re-plan and re-review. Two important cautions:

  • A saved plan file contains secrets in clear text (all planned values, including sensitive ones). Store it as a short-lived, encrypted CI artifact, never in git or a public log.
  • A plan is tied to the exact code, provider versions and state it came from. Apply it in the same pipeline, soon after.

That last line, "1 to destroy" on a database, is exactly what policy checks exist to catch automatically.

Guard rails in the code: lifecycle, moved and removed

resource "aws_db_instance" "main" {
  identifier          = "orders-db"
  deletion_protection = true          # AWS-side guard: the API refuses DeleteDBInstance
  # ...
  lifecycle {
    prevent_destroy = true            # Terraform-side guard: any plan that destroys this errors out
    ignore_changes  = [password]      # rotated by Secrets Manager, not by Terraform
  }
}

resource "aws_lb_target_group" "web" {
  name_prefix = "web-"
  # ...
  lifecycle {
    create_before_destroy = true      # new TG exists before the old one is removed
  }
}

# a refactor renamed the resource address; tell Terraform it is the SAME object
moved {
  from = aws_instance.web
  to   = module.web.aws_instance.this
}

# stop managing an object without deleting it (Terraform 1.7+)
removed {
  from = aws_s3_bucket.legacy_logs
  lifecycle {
    destroy = false
  }
}
$ terraform plan
...
Error: Instance cannot be destroyed

  on data.tf line 1:
   1: resource "aws_db_instance" "main" {

Resource aws_db_instance.main has lifecycle.prevent_destroy set, but the plan
calls for this resource to be destroyed. To avoid this error and continue with
the plan, either disable lifecycle.prevent_destroy or reduce the scope of the
plan using the -target option.

prevent_destroy has a hole. It only protects while the resource block is in the code. If someone deletes the whole block, the setting goes with it and the next plan happily destroys the database. Pair it with the provider-side flag (deletion_protection on RDS, termination protection on EC2, S3 Object Lock or MFA delete) and a CI policy that blocks deletes of stateful types.

Targeted applies and forced replacement

-target=ADDRESS limits a plan to one resource (plus everything it depends on). The Terraform docs say it is for exceptional cases such as recovering from a mistake, not for routine use, because the rest of the configuration is left un-planned and drift can hide. Terraform even prints a warning that the result may be incomplete.

# OK: emergency, recreate one broken instance, then immediately run a full plan
$ terraform apply -replace="aws_instance.web[\"ap-south-1a\"]"
$ terraform plan        # confirm "No changes" for everything else

# Avoid as a habit: "only apply my bit"
$ terraform apply -target=module.payments

-replace=ADDRESS (the modern replacement for terraform taint) forces a destroy/create of one object that is degraded, while still showing the full plan.

Blast radius: how much can one apply break?

The blast radius of a change is the set of things that can break if it goes wrong. You shrink it in layers:

Shrinks blast radius
  • Small states split by environment, layer and team
  • Separate AWS accounts per environment (an account is a hard IAM boundary)
  • Least-privilege apply roles per stack; plan roles are read-only
  • Module versions promoted dev, then staging, then prod
  • Policy as code on the plan JSON (OPA/conftest, Sentinel, Checkov): "no deletes of aws_db_instance", "no 0.0.0.0/0 on port 22"
  • prevent_destroy + provider deletion protection on stateful resources
Grows blast radius
  • One state for the whole company
  • Admin credentials on laptops; anyone can apply prod
  • Unpinned module sources (?ref=main)
  • Applying a fresh plan instead of the reviewed one
  • Habitual -target applies that leave the rest un-planned
  • Big-bang refactors without moved blocks (renames look like destroy + create)

$ terraform show -json tfplan > plan.json
$ conftest test plan.json -p policy/

From your world

This is change management for a carrier network, written as code. The PR plan is your method of procedure with the exact commands; the reviewer is the change advisory board; the saved plan is "execute exactly the MOP, nothing else"; the stale-plan error is "the device config changed since the MOP was written, re-validate". Splitting state is limiting a change to one PoP at a time. Policy as code is the pre-check script that refuses a config that shuts down a core-facing interface.
