You want the same infrastructure shape in dev, staging and prod, with different sizes, and above all you want each environment's state kept apart, so a mistake in dev cannot rewrite prod. There are two common ways to do it.

Option A: CLI workspaces

One folder, one backend config, several workspaces. Each workspace has its own state file. You switch with a command, and the code reads the current name from terraform.workspace.

$ terraform workspace new staging
Created and switched to workspace "staging"!

You're now on a new, empty workspace. Workspaces isolate their state,
so if you run "terraform plan" Terraform will not see any existing state
for this configuration.

$ terraform workspace list
  default
  dev
* staging

$ terraform workspace show
staging
locals {
  sizes = {
    dev     = { instance = "t3.small",  min = 1 }
    staging = { instance = "t3.medium", min = 2 }
    prod    = { instance = "m6i.large", min = 6 }
  }
  env = local.sizes[terraform.workspace]
}

resource "aws_autoscaling_group" "web" {
  name     = "web-${terraform.workspace}"
  min_size = local.env.min
  # ...
}

With the S3 backend, the default workspace uses your key as written, and every other workspace is stored under a prefix (by default env:/): s3://acme-tfstate/env:/staging/app/terraform.tfstate. Same bucket, same credentials, same lock table.

Option B: one folder (and one backend key) per environment

infra/
  modules/
    vpc/  eks/  rds/  ecs-service/
  envs/
    dev/
      backend.tf      # key = "dev/app.tfstate",     role = tf-dev
      main.tf         # module "network" { source = "../../modules/vpc" ... }
      dev.auto.tfvars
    staging/
      backend.tf      # key = "staging/app.tfstate", role = tf-staging
      main.tf
    prod/
      backend.tf      # bucket in the PROD account,  role = tf-prod
      main.tf         # pins module refs that staging has already proven

Each environment is its own root module with its own backend block. The shared logic lives in modules, so the duplication is only the thin wiring layer. You run Terraform by cd-ing into the folder, so the folder path itself tells you (and your CI job) which environment you are touching.

HashiCorp's own documentation says CLI workspaces are not a fit when deployments need separate credentials and access controls, which is exactly the dev-vs-prod case, and recommends reusable modules plus a separate configuration and backend per deployment. (HCP Terraform "workspaces" are a different thing: each one is effectively its own state, variables and permissions, much closer to the folder model.)

The classic accident. An engineer runs terraform workspace select prod to check something, forgets, and the next afternoon runs terraform apply meant for dev. Nothing in the folder or prompt says "prod". Folder-per-env plus a prod role that only the CI pipeline can assume makes this mistake impossible rather than unlikely.

Split state by layer, not only by environment

Even inside prod, one giant state is a bad idea. Every plan refreshes every object (slow, and it hits API rate limits), every apply holds one lock for everybody, and a bad change can touch anything. Split by layer and rate of change:

# envs/prod/app-payments/main.tf - read the network layer without owning it
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "acme-prod-tfstate"
    key    = "network/terraform.tfstate"
    region = "ap-south-1"
  }
}

module "payments" {
  source     = "git::https://github.com/acme/tf-modules.git//ecs-service?ref=v1.8.2"
  subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids
}

From your world

Layered state is a failure domain design, the same instinct as not running your core routing protocol and a customer-facing VRF change in one maintenance window. The network layer is your underlay (rarely touched, everything depends on it), the app stacks are the overlay services that change daily. Reading another layer's outputs is like learning a prefix via a route import: you consume it, you cannot withdraw it.

Tools such as Terragrunt exist mainly to remove the repeated backend and provider boilerplate in a folder-per-env, layer-per-folder tree, and to run plan across many folders in dependency order. They are optional; plain folders plus modules are enough to explain in an interview.
