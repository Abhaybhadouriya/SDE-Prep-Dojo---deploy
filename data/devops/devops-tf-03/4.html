Drift: when reality and state disagree

Good to know (SDE-2)

Drift means the real infrastructure no longer matches what Terraform last recorded (and usually no longer matches the code). Terraform does not watch your cloud; it only notices drift when it next refreshes during a plan. Common causes:

  • A manual console change during an incident: someone opens port 22 on a security group, raises an instance size, or edits a route table.
  • Another tool managing the same object: an autoscaler changing desired_count, a Kubernetes controller adding tags, AWS adding default values.
  • Two Terraform stacks managing the same object (for example two states both declaring the same security group rule).
  • Deleted resources: someone removes a resource by hand, so the next plan wants to create it again.
  1. Normal day: code in git, the state file and the real cloud all agree.
  2. During an incident someone opens SSH on the security group in the console. The cloud changed; code and state did not.
  3. The next plan refreshes: it asks AWS for the live object, compares with state and reports "Objects have changed outside of Terraform".
  4. A human decides. Either the code is right (apply reverts the manual change) or the change was right (update the code so they match again).
  5. To catch drift within hours instead of at the next unrelated deploy, run a scheduled plan and alert on a non-empty diff.

Seeing drift with a refresh-only plan

terraform plan -refresh-only compares state with the real objects and shows only what changed outside Terraform, without proposing to change anything back. It is the safe, read-only way to look.

$ terraform plan -refresh-only
aws_security_group.web: Refreshing state... [id=sg-0a1b2c3d4e5f60718]

Note: Objects have changed outside of Terraform

Terraform detected the following changes made outside of Terraform since the
last "terraform apply" which may have affected this plan:

  # aws_security_group.web has changed
  ~ resource "aws_security_group" "web" {
        id      = "sg-0a1b2c3d4e5f60718"
      ~ ingress = [
          + {
              + cidr_blocks = ["0.0.0.0/0"]
              + from_port   = 22
              + protocol    = "tcp"
              + to_port     = 22
            },
            # (1 unchanged element hidden)
        ]
    }

This is a refresh-only plan, so Terraform will not take any actions to undo
these. If you were expecting these changes then you can apply this plan to
record the updated values in the Terraform state without changing any remote
objects.

Now there are three choices, and you should say them in this order in an interview:

  1. Revert (code is the truth): run a normal terraform plan/apply. Terraform proposes removing the port-22 rule and puts things back.
  2. Codify (the change was right): edit the code to include the rule, open a PR, plan shows "No changes", merge. Now git, state and cloud agree again.
  3. Accept into state only: terraform apply -refresh-only writes the new values into state without touching the cloud. Use this rarely; if the code still disagrees, the very next normal plan will propose reverting anyway.

If someone created a brand-new object by hand that should be managed, bring it in with an import block (Terraform 1.5+) so the import itself is reviewed in a plan:

import {
  to = aws_security_group_rule.bastion_ssh
  id = "sgrule-1234567890"
}

Scheduled drift detection in CI

terraform plan -detailed-exitcode returns 0 when there is no diff, 1 on error and 2 when there are changes. That makes a cron job trivial: run a plan for each stack every night (or every few hours for prod) and alert on exit code 2. HCP Terraform and other managed platforms offer the same idea as built-in "health assessments".

# .github/workflows/drift.yml
name: drift-detection
on:
  schedule:
    - cron: "0 2 * * *"        # 02:00 UTC every day
  workflow_dispatch: {}
permissions:
  id-token: write              # OIDC to AWS, no long-lived keys
  contents: read
jobs:
  plan:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        stack: [prod/network, prod/data, prod/cluster, prod/app-payments]
    steps:
      - uses: actions/checkout@v5
      - uses: hashicorp/setup-terraform@dfe3c3f87815947d99a8997f908cb6525fc44e9e   # v4.0.1
        with:
          terraform_wrapper: false
      - uses: aws-actions/configure-aws-credentials@v5
        with:
          role-to-assume: arn:aws:iam::111122223333:role/tf-readonly-plan
          aws-region: ap-south-1
      - name: Plan
        working-directory: envs/${{ matrix.stack }}
        run: |
          terraform init -input=false
          set +e
          terraform plan -input=false -lock=false -detailed-exitcode -no-color > plan.txt
          code=$?
          set -e
          if [ "$code" -eq 2 ]; then
            echo "::warning::Drift detected in ${{ matrix.stack }}"
            exit 2
          fi
          exit $code

Why -lock=false and a read-only role? A drift job only reads. Running it without taking the state lock means it never blocks a real deploy, and a role that can only Describe*/Get* plus read the state bucket means a bug in the job can never change prod. (If you need perfectly consistent results, keep the lock; it is a trade-off.)

Noisy drift is worse than no drift detection. If an autoscaler legitimately changes desired_capacity every hour, the job reports drift every night and people learn to ignore it. Tell Terraform to stop tracking fields another system owns, with lifecycle { ignore_changes = [desired_capacity] }, so the remaining alerts are real.

The best drift detection is prevention: make production console access read-only for humans, keep a break-glass role for real emergencies that pages the team when assumed, and add a "codify or revert within 24 hours" item to every incident where someone used it.
