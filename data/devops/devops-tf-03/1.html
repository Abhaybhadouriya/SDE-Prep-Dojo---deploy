Modules: reusable groups of resources

Must know (SDE-1)

A module is just a folder of .tf files. That is it. The folder where you run terraform plan is the root module. Any folder it calls with a module block is a child module. A good child module bundles a set of resources that always travel together (for example "a VPC with subnets and route tables") behind a small set of input variables and outputs, so every team builds the same well-tested pattern instead of copy-pasting 300 lines and changing them a little each time.

A small VPC module, end to end

The standard layout is three files: variables.tf (inputs), main.tf (resources), outputs.tf (what callers may read). Callers can only see outputs; everything else inside is private, just like a C file with static functions and a header.

# modules/vpc/variables.tf
variable "name" {
  type        = string
  description = "Prefix for every resource name, e.g. prod-core"
}

variable "cidr" {
  type        = string
  description = "VPC CIDR block, e.g. 10.20.0.0/16"
  validation {
    condition     = can(cidrhost(var.cidr, 0))
    error_message = "cidr must be a valid IPv4 CIDR block."
  }
}

variable "azs" {
  type    = list(string)
  default = ["ap-south-1a", "ap-south-1b", "ap-south-1c"]
}
# modules/vpc/main.tf
resource "aws_vpc" "this" {
  cidr_block           = var.cidr
  enable_dns_hostnames = true
  tags = { Name = var.name }
}

# carve one /20 public and one /20 private subnet per AZ
resource "aws_subnet" "private" {
  for_each          = { for i, az in var.azs : az => i }
  vpc_id            = aws_vpc.this.id
  availability_zone = each.key
  cidr_block        = cidrsubnet(var.cidr, 4, each.value)        # 10.20.0.0/20, 10.20.16.0/20 ...
  tags = { Name = "${var.name}-private-${each.key}" }
}

resource "aws_subnet" "public" {
  for_each                = { for i, az in var.azs : az => i }
  vpc_id                  = aws_vpc.this.id
  availability_zone       = each.key
  cidr_block              = cidrsubnet(var.cidr, 4, each.value + 8) # 10.20.128.0/20 ...
  map_public_ip_on_launch = true
  tags = { Name = "${var.name}-public-${each.key}" }
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id
  }
}

resource "aws_route_table_association" "public" {
  for_each       = aws_subnet.public
  subnet_id      = each.value.id
  route_table_id = aws_route_table.public.id
}
# modules/vpc/outputs.tf
output "vpc_id" {
  value = aws_vpc.this.id
}

output "private_subnet_ids" {
  value = [for s in aws_subnet.private : s.id]
}

output "public_subnet_ids" {
  value = [for s in aws_subnet.public : s.id]
}
# envs/prod/main.tf
module "network" {
  source = "git::https://github.com/acme/tf-modules.git//vpc?ref=v2.3.0"
  name   = "prod-core"
  cidr   = "10.20.0.0/16"
}

module "app" {
  source     = "git::https://github.com/acme/tf-modules.git//ecs-service?ref=v1.8.2"
  subnet_ids = module.network.private_subnet_ids
}

output "alb_dns" {
  value = module.app.alb_dns_name
}

From your world

Read that module as a network engineer and it is pure muscle memory. cidrsubnet("10.20.0.0/16", 4, 1) borrows 4 bits from the host part, giving sixteen /20s, and picks number 1: 10.20.16.0/20. That is the subnet planning you do on a whiteboard for VLANs. The aws_route_table with 0.0.0.0/0 -> igw is a static default route; the association binds a subnet to that routing table the way you bind an interface to a VRF. Private subnets have no default route to the internet gateway, so they are your "inside" VRF. A VPC module is therefore a config template for one routing domain, and its inputs (CIDR, AZ list) are the template variables.

After adding or changing a module block you must run terraform init again, because init is what downloads modules into .terraform/modules:

What makes a good module

  • One job, small surface. "VPC", "EKS cluster", "service with ALB". Not "the whole company in one module".
  • Few, typed inputs with validation and sensible defaults. Every input you add is a knob someone will turn wrong.
  • Outputs for everything a caller needs (ids, ARNs, DNS names), so nobody reaches inside with a data source lookup by name.
  • No provider blocks inside child modules. The root module configures providers (region, credentials) and passes them down. A module with its own provider "aws" block cannot be used with for_each or count and is hard to remove.
  • No hard-coded environment names. The module does not know it is "prod"; the caller tells it.
  • Do not wrap a single resource in a module just to rename its arguments. That adds a layer and removes nothing.
