Versioning modules: pin, tag, upgrade on purpose

Must know (SDE-1)

A shared module is a library. If ten teams call main of your module repo, then your next merge changes ten production stacks on their next plan, without them asking. So modules are released with semantic version tags (v2.3.0: major for breaking changes, minor for new features, patch for fixes) and every caller pins a version.

Source typeHow to pinExample
Terraform Registry (public or private)version argument with a constraintsource = "terraform-aws-modules/vpc/aws"
version = "~> 6.0"
Git?ref= a tag (or a commit SHA) inside the source URLgit::https://github.com/acme/tf-modules.git//vpc?ref=v2.3.0
Local pathNot versioned; moves with the reposource = "../../modules/vpc"
S3 / GCS / HTTP archivePut the version in the object paths3::https://s3.amazonaws.com/acme-modules/vpc-2.3.0.zip

Match module majors to provider majors: the 6.x line of terraform-aws-modules/vpc/aws is built for AWS provider 6.x, which is what tf-01 pins (~> 6.0). The version argument only works for registry sources. For Git you must use ref. Constraint operators: = 6.0.1 exact, >= 6.0 at least, ~> 6.0 "6.0 or any newer 6.x, but not 7.0" (the pessimistic operator allows only the rightmost number to grow).

Gotcha: the lock file does not lock modules. .terraform.lock.hcl records exact provider versions and hashes. Module versions are not in it. A loose module constraint like >= 5.0 will silently pick up a new release on the next terraform init on a fresh CI runner. Pin modules tightly (exact tag or ~> on the minor) and commit the lock file for providers.

A healthy module release flow looks like any library release: PR to the module repo, automated checks (terraform fmt -check, terraform validate, a linter such as tflint, and ideally terraform test against a sandbox account), merge, tag v2.4.0, write a changelog. Callers upgrade by bumping the ref in a PR, which produces a plan they review like any other change. Tools like Renovate or Dependabot can open those bump PRs automatically.

# upgrade a pinned module on purpose
$ sed -i 's/?ref=v2.3.0/?ref=v2.4.0/' envs/staging/main.tf
$ terraform init -upgrade      # re-download modules (and allow newer providers within constraints)
$ terraform plan               # read the diff the new module version causes

Promote module versions like application builds. Bump dev first, then staging a day later, then prod. Because each environment pins its own ref, a broken module release can only hurt the environments that opted in.
