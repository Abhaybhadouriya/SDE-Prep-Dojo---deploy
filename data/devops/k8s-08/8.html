The key idea: who provides durability? If the storage layer does (network disks are replicated inside the zone by the cloud), you can use one copy per pod. If the application does (Kafka keeps 3 replicas on 3 brokers), you can choose fast but fragile local disks - losing one node just means one replica rebuilds from the others. Doing both (Kafka RF=3 on top of replicated network disks) is common on cloud and simply costs more.

Real outage lesson (Datadog, March 2023): after a bad OS update broke node networking, cloud auto-healing replaced a large share of instances in one region within hours. Stateful stores that relied on local disks lost those disks with the instances, which made recovery much slower. Local NVMe is fast, but "replace the node" then means "rebuild the data". Source: Datadog engineering blog.

Storage for Kafka on Kubernetes

A Kafka broker writes its partition logs (Kafka storage internals) to a directory that must survive restarts, because a broker that comes back empty has to re-copy every replica it hosted over the network. So each broker needs its own PVC - never a shared RWX volume, and never a single PVC shared by all replicas of a Deployment. That "one disk per replica, with a stable name" requirement is exactly what StatefulSets and the Strimzi operator provide through volumeClaimTemplates or per-pod claims. Kafka's own replication (RF=3, min.insync.replicas=2) provides the cross-zone durability; see Replication & ISR.

Performance knobs that bite

  • fsGroup ownership change. If the pod sets securityContext.fsGroup, the kubelet may chown every file in the volume on each mount. On a volume with millions of files, pod start can take minutes. Set fsGroupChangePolicy: OnRootMismatch so it only walks the tree when the top directory is wrong.
  • Attach limits per node. Cloud VMs can attach only a limited number of disks (the limit depends on instance type). The CSI node plugin reports it, and the scheduler counts it. Pods can be Pending with "node(s) exceed max volume count" even when CPU is free.
  • emptyDir on memory. emptyDir: { medium: Memory } is a tmpfs; what you write there counts against the container's memory limit. Fill it and you get OOMKilled, not "disk full". Set sizeLimit.
  • Ephemeral storage limits. Container logs, the writable layer and disk-backed emptyDir all use node disk. Set resources.requests/limits.ephemeral-storage, or a noisy pod can trigger node DiskPressure and evictions of its neighbours (see Scheduling & Autoscaling).

From your world

"Volume moves when the pod moves" is not free. Detaching means the old node must finish umount - which flushes dirty pages - and the cloud API must confirm the detach before attaching to the new node. If the old node is dead, nobody can run umount, so the system waits (by default for minutes) to be sure it is not still writing. It is the same fear you have with a dual-homed SCSI disk: two hosts writing the same block device without a cluster filesystem corrupts it. Kubernetes chooses waiting over corruption.
