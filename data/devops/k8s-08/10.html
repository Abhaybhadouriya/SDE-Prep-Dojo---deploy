Interview questions

Redraw this in 30 seconds

Six boxes. The pod asks (PVC), the cluster supplies (PV), the StorageClass says how, and the CSI driver makes the cloud calls.

Explain PV, PVC and StorageClass. Why three objects instead of one?

A PVC is a namespaced request from an app ("20 GiB, RWO, class fast-ssd"). A PV is the cluster-scoped object representing a real piece of storage. A StorageClass is a recipe that lets a CSI driver create PVs on demand. They are separate so that responsibilities are separate: app developers write claims and stay portable across clouds, platform admins define classes and policies (encryption, reclaim, binding mode), and drivers do the vendor-specific work. The pod only references the claim, so the same manifest runs on EKS, AKS or a laptop by changing only the class.

How to answer

Use the locker analogy in one line, then give the owner of each object. Interviewers want the "separation of concerns / portability" reason, not just definitions.

Likely follow-ups
  • Which ones are namespaced? (PVC and VolumeSnapshot are; PV, StorageClass and VolumeSnapshotContent are not.)
  • What is the difference between static and dynamic provisioning?
A pod is Pending and the PVC is Pending. How do you debug it?

First, kubectl describe pvc and read the Events. If it says "waiting for first consumer", the PVC is fine and the real problem is the pod's scheduling - kubectl describe pod will show which filter failed (CPU, taints, or "volume node affinity conflict"). If there is no StorageClass, the name is wrong, or no default class exists, fix the claim. If the event comes from the external-provisioner with an error, the driver failed - check the CSI controller pod logs (quota, permissions, an unsupported access mode such as RWX on a block disk). For a zone conflict, make sure the class uses WaitForFirstConsumer and that the zone where the existing disk lives has capacity.

How to answer

Name the process that would act at each step (PV controller, external-provisioner, scheduler) and the command that shows its message. That proves you are not guessing.

Likely follow-ups
  • Why does WaitForFirstConsumer exist?
  • What if the disk already exists in zone A and zone A is down?
What do RWO, RWX and RWOP mean? Can two pods share an RWO volume?

RWO: mounted read-write by a single node - so yes, two pods on the same node can share it. RWOP (ReadWriteOncePod, stable in v1.29): a single pod in the whole cluster. RWX: many nodes read-write at once, which requires a shared filesystem (NFS, CephFS, EFS, Azure Files); block disks cannot do it. ROX: many nodes read-only. For a database that must have exactly one writer, I would use RWOP or rely on a StatefulSet's one-pod-per-claim pattern.

How to answer

Say "node, not pod" early - it is the trap the question is testing.

Likely follow-ups
  • Why can't EBS be RWX? (It is a block device; two kernels mounting ext4 at once would corrupt it.)
  • What would you use for shared user uploads? (Object storage like S3 first; RWX only if the app needs a POSIX filesystem.)
Walk me through what happens, component by component, from creating a PVC to the container writing to the disk.

PVC stored via the API server. With WaitForFirstConsumer, the scheduler places the pod and annotates the PVC with the selected node. The CSI external-provisioner sidecar sees that and calls the driver's CreateVolume with the node's zone; the driver calls the cloud API; the sidecar creates a PV; the PV controller in kube-controller-manager binds it. The attach/detach controller creates a VolumeAttachment; the external-attacher calls ControllerPublishVolume and the cloud attaches the disk to the VM. On the node, the kubelet calls the CSI node plugin: NodeStageVolume formats and mounts it at a global path, NodePublishVolume bind-mounts it into the pod's directory. Then the runtime starts containers with that mount. On pod deletion it runs in reverse.

How to answer

Draw two columns, control plane and node, and move left to right. Use the three verbs provision, attach, mount as headings; the details hang off them.

Likely follow-ups
  • What changes if the node dies with the disk attached?
  • Where does the CSI driver run? (Controller part as a Deployment, node part as a DaemonSet.)
Would you run a database or Kafka on Kubernetes? What storage would you pick?

It depends on the team's operational maturity, not on Kubernetes ability. Operators like CloudNativePG and Strimzi made it practical, and companies such as Flipkart run large stateful workloads on Kubernetes. If a managed service (RDS, MSK, Confluent Cloud) fits the budget and the team is small, I would start there and keep only stateless services in the cluster. If we run it ourselves: one PVC per replica via a StatefulSet or operator, WaitForFirstConsumer, Retain reclaim policy, replicas spread across zones, PodDisruptionBudgets, and backups outside the cluster. For Kafka, network SSDs are the simple choice on cloud; local NVMe gives more throughput but replacing a node means re-replicating its data, so it fits only when Kafka's RF=3 and enough spare bandwidth are in place.

How to answer

Use the trade-off sentence: "I would pick X because A; the cost is B; if C, I would switch to Y." Avoid both "never" and "always".

Likely follow-ups
  • How do Kafka clients outside the cluster reach a specific broker? (See StatefulSets & Operators.)
  • How do you back up a PVC?

Scenario: "We deleted the namespace and the customer's data is gone"

A cleanup script ran kubectl delete namespace staging-eu - but it was actually the production EU namespace. Every PVC was deleted. The StorageClass had the default reclaimPolicy: Delete.

Weak answer: "Restore from the PVs." (They are already deleted, together with the cloud disks.)

Strong answer: "Immediate: check whether the cloud provider kept snapshots or the disks are in a recycle bin (some clouds have one), and restore the database from its own off-cluster backups. Root causes: a destructive operation with no guard, and a reclaim policy that turns a mistake into data loss. Prevention: Retain on classes holding precious data, scheduled VolumeSnapshots plus application backups to another region, RBAC so humans and scripts cannot delete prod namespaces, admission policies that block namespace deletion without an annotation, and GitOps so namespaces are recreated from git."

Likely follow-ups
  • With Retain, how do you re-attach the old disk to a new PVC? (Clear the PV's claimRef, or create a new static PV with the same volume handle and pre-bind it.)

60-second answer - "How does storage work in Kubernetes?"
"Pods are disposable, so anything stored inside a container is lost on restart. For data that must survive, a pod mounts a PersistentVolumeClaim - a namespaced request for size and access mode. The claim is bound one-to-one to a PersistentVolume, which represents the real disk. In cloud clusters PVs are created on demand from a StorageClass by a CSI driver; with WaitForFirstConsumer the disk is created in the zone where the scheduler placed the pod, which avoids zone conflicts. Then the attach/detach controller attaches it to the node and the kubelet, through the CSI node plugin, formats and mounts it. Block disks are ReadWriteOnce - one node at a time - and zonal, so cross-zone durability comes from the application replicating, like Kafka with three replicas. For production data I use Retain, snapshots and off-cluster backups."
