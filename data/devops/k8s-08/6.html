What actually happens: from claim to mounted disk

Good to know (SDE-2)

"Kubernetes mounts the disk" hides about seven separate actors. This is the walk-through to know by heart. Click Next or Play.

  1. Claim. You apply a PVC. The API server stores it in etcd. With WaitForFirstConsumer nothing else happens yet, so kubectl get pvc says Pending. Then you create a pod that uses it.
  2. Schedule. kube-scheduler filters nodes (CPU, memory, taints) and asks the volume binding plugin whether storage can be provided there. It picks node-2 and writes the annotation volume.kubernetes.io/selected-node on the PVC.
  3. Provision. The external-provisioner sidecar (running next to the driver's controller plugin, usually in a Deployment) watches PVCs. It sees the annotation and calls the driver's CreateVolume gRPC with a topology hint "zone 1b". The driver calls the cloud API. The sidecar then creates a PV object, and the PV controller in kube-controller-manager binds PVC and PV.
  4. Attach. The attach/detach controller in kube-controller-manager creates a VolumeAttachment object. The external-attacher sidecar sees it and calls ControllerPublishVolume: the cloud attaches the disk to node-2's VM, and a new block device such as /dev/nvme1n1 appears in that node's kernel.
  5. Stage. The kubelet on node-2 calls the CSI node plugin (a DaemonSet pod on every node) with NodeStageVolume: format the device if it is blank (ext4 or xfs) and mount it once at a global path under /var/lib/kubelet/plugins/....
  6. Publish. The kubelet calls NodePublishVolume: the plugin bind-mounts the staged directory into /var/lib/kubelet/pods/<pod-uid>/volumes/.... The container runtime then mounts that into the container at mountPath.
  7. Run. Only now do the containers start. When the pod later moves, the same steps run backwards (unpublish, unstage, detach) on the old node before the disk can attach to the new one.

From your world

Steps 5 and 6 are plain Linux: mkfs.ext4 /dev/nvme1n1, mount /dev/nvme1n1 /staging/path, then mount --bind /staging/path /var/lib/kubelet/pods/UID/volumes/.... The container sees it through its own mount namespace. CSI itself is just a gRPC API over a Unix socket with three services (Identity, Controller, Node) - a pluggable driver model, like a vendor plugging a block driver into the kernel's VFS without changing the kernel. Where this breaks: the "controller" half of a CSI driver is not in the kernel at all; it is a normal pod calling a cloud HTTP API.
