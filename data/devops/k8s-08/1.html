Why a container cannot just write to its own disk

Must know (SDE-1)

A container's root filesystem is an overlay: read-only image layers with a thin writable layer on top (you met this on the Docker internals page). That writable layer belongs to one container instance. When the container restarts, the kubelet creates a fresh container from the image, with a fresh, empty writable layer. When the pod is deleted, everything goes.

A volume is a directory that Kubernetes mounts into the container at a path you choose, for example /var/lib/data. What backs that directory decides how long the data lives:

The volume types you will actually meet

Volume typeWhat backs itLives untilTypical use
emptyDirNode disk (or RAM with medium: Memory)Pod is deletedScratch space; sharing files between containers in one pod
configMap / secret / projectedAPI objects written as files by the kubeletPod is deletedConfig files, certificates, ServiceAccount tokens (ConfigMaps & Secrets)
persistentVolumeClaimA PV: cloud disk, NFS, Ceph, local SSD...You delete the PVC (and maybe longer)Anything that must survive: DBs, Kafka, uploads
Generic ephemeral volumeA PVC created and deleted together with the podPod is deletedBig scratch space from a real StorageClass
hostPathA directory on the node itselfNode is wipedNode agents only (log collectors, CSI node plugins). Dangerous for apps
imageFiles from an OCI image, mounted read-onlyPod is deletedShipping models or static data as an image (stable in v1.36)

Careful: hostPath looks tempting ("just write to /data on the node") but it ties the pod to that node, gives no capacity limit, and a container that can write to host paths can often take over the node. Pod Security "baseline" and "restricted" profiles forbid it. Use it only for node-level system agents.

Note: the old gitRepo volume type was permanently disabled in v1.36 because it could run code as root on the node. If an old tutorial uses it, replace it with an init container that runs git clone, or the git-sync sidecar.
