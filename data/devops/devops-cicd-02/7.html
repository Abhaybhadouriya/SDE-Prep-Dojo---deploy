Dependency caching: three layers

Must know (SDE-1)

"Make CI faster" almost always means "stop downloading and recompiling the same things". There are three caches, and they stack:

  1. Runner cache. actions/cache or setup-java's cache: maven on GitHub; a persistent volume or a cache plugin on Jenkins agents. Key it on a hash of pom.xml (or the lock file for npm, go.sum for Go).
  2. Repository proxy. Nexus or Artifactory next to your runners. Shared by every build in the company, survives runner churn.
  3. Docker layer cache. Order your Dockerfile so dependencies are resolved in a layer that only changes when pom.xml changes (covered in docker-09). With BuildKit you can export that cache to the registry (--cache-to type=registry).

Never cache build outputs between unrelated builds (for example target/). A stale class file from yesterday can make today's build pass when the clean build would fail. Cache inputs (downloaded dependencies), rebuild outputs.
