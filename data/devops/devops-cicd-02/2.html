Maven: the lifecycle and pom.xml

Must know (SDE-1)

Maven is the standard Java build tool. You describe the project in one XML file, pom.xml (Project Object Model): who it is, what it depends on and which plugins to run. Maven does the rest by convention: source in src/main/java, tests in src/test/java, output in target/.

Every artifact has three coordinates, called GAV: groupId (the team or company, like a Java package), artifactId (the module name) and version. A version ending in -SNAPSHOT means "work in progress, may change". A version without it is a release and must never change again.

<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.dojo.payments</groupId>
  <artifactId>payment-api</artifactId>
  <version>${revision}</version>          <!-- set by CI: -Drevision=1.4.2 -->
  <packaging>jar</packaging>

  <properties>
    <revision>1.4.0-SNAPSHOT</revision>     <!-- default for laptops -->
    <maven.compiler.release>21</maven.compiler.release>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.postgresql</groupId>
      <artifactId>postgresql</artifactId>
      <version>42.7.4</version>           <!-- pinned, never a range -->
    </dependency>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>5.11.3</version>
      <scope>test</scope>                 <!-- not shipped in the jar -->
    </dependency>
  </dependencies>

  <distributionManagement>                <!-- where "mvn deploy" uploads -->
    <repository>
      <id>nexus-releases</id>
      <url>https://nexus.example.internal/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
      <id>nexus-snapshots</id>
      <url>https://nexus.example.internal/repository/maven-snapshots/</url>
    </snapshotRepository>
  </distributionManagement>

  <build>
    <plugins>
      <plugin>                              <!-- needed with ${revision} on Maven 3 -->
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>flatten-maven-plugin</artifactId>
        <version>1.6.0</version>
        <configuration>
          <updatePomFile>true</updatePomFile>
          <flattenMode>resolveCiFriendliesOnly</flattenMode>
        </configuration>
        <executions>
          <execution><id>flatten</id><phase>process-resources</phase><goals><goal>flatten</goal></goals></execution>
          <execution><id>flatten-clean</id><phase>clean</phase><goals><goal>clean</goal></goals></execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</project>

The ${revision} placeholder is Maven's official "CI friendly versions" feature: the pipeline passes the real version on the command line instead of committing a version bump for every build. On Maven 3 it needs the flatten-maven-plugin shown above: without it, install and deploy publish a .pom that still contains the literal ${revision}, and every consumer or child module that reads it breaks. The plugin writes a resolved .flattened-pom.xml and deploys that instead. Maven 4 builds a separate consumer POM itself, so there the plugin is no longer needed.

The default lifecycle, phase by phase

A lifecycle is an ordered list of phases. When you ask for one phase, Maven runs every phase before it, in order. Plugins attach goals to phases: the compiler plugin's compile goal is bound to the compile phase, Surefire runs unit tests in test, Failsafe runs integration tests around verify. The full default lifecycle has 23 phases; these seven are the ones you name in an interview. Click through:

  1. validate - check the project is correct and all needed information is there.
  2. compile - compile main sources. Resolving dependencies happens here (first run downloads half the internet into ~/.m2).
  3. test - run unit tests with Surefire. They must not need a packaged jar or a deployed service.
  4. package - produce the distributable: jar, war, or (with a plugin) a container image.
  5. verify - run integration tests and checks on the package. The Maven guide calls this the safe default phase when unsure.
  6. install - put the package into the local repository of this machine.
  7. deploy - copy the final package to the remote repository so other teams and the deploy pipeline can fetch it.

From your world

The lifecycle is a Makefile with fixed targets and fixed prerequisites. make install first builds everything install depends on; mvn install first runs every earlier phase. ~/.m2/repository is a per-user package cache, like /var/cache/apt/archives, and a Nexus proxy repository is the local apt mirror in your lab that saves everyone from pulling from the internet.

Tip: always pass -B (batch mode, no colour codes or progress bars) in CI, and use mvn dependency:tree when two libraries pull different versions of the same jar. Maven picks the nearest declaration in the tree, not the newest, which surprises everyone once.

From your world

A phase is like a make target that depends on every earlier target: mvn install runs validate, compile, test, package and verify first, the way make install builds and tests before installing. Plugins are the recipe commands bound to targets (the compiler plugin's compile goal is the $(CC) line). ~/.m2/repository is a local package cache keyed by groupId:artifactId:version, like the apt or dnf cache. A -SNAPSHOT is a nightly build that may be replaced; a release version is a tagged kernel release that never changes.
