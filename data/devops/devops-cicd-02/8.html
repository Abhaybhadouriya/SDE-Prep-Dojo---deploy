Build once, promote many

Good to know (SDE-2)

The single most important rule of a delivery pipeline: the bytes that reach production are the bytes that were tested. So you build exactly once per commit, give the result an immutable version, and "deploying to the next environment" only means pointing that environment at the same version. Configuration that differs per environment (database URL, feature flags, replica count) is injected at deploy time from outside the artifact.

  1. Build once. The pipeline compiles and tests commit a1b2c3 exactly one time.
  2. Seal it. The result is stored as 1.4.2 (a jar in Nexus, an image in the registry with a content digest). The version maps back to the commit. It can never be overwritten.
  3. Dev pulls 1.4.2 and gets dev configuration from env vars, ConfigMaps or a config service.
  4. Staging pulls the same 1.4.2. Tests here are meaningful because the binary is identical to what prod will get.
  5. Production pulls the same 1.4.2 after the gates pass (tests, approval, canary metrics).
  6. Rollback is not a rebuild. It is pointing production at the previous immutable version, which still exists in the repository.

Why rebuilding per environment is wrong

  • Floating inputs. A rebuild an hour later can pull a different base image, a new transitive dependency or a newer compiler. Staging tested build A; prod got build B.
  • Lost traceability. "Which code is running in prod?" must be answerable as "1.4.2 = commit a1b2c3", not "whatever main was when someone clicked deploy".
  • Slow rollback. If the old version must be rebuilt, rollback takes a full pipeline run during an outage.

What "immutable version" means in practice

ArtifactImmutable identityAnti-pattern
Maven jarRelease version 1.4.2 in a no-redeploy repoDeploying a -SNAPSHOT to prod
Docker / OCI imagedigest sha256:..., plus a unique tag like 1.4.2 or the git SHA:latest, or re-pushing the same tag
Helm chartChart version + pinned image digest in valuesChart pointing at a moving tag
 
$ docker buildx imagetools inspect registry.example.internal/payments:1.4.2 | head -3
Name:      registry.example.internal/payments:1.4.2
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:9f3c0d...e1

# Deploy by digest, so even a re-pushed tag cannot change what runs:
$ kubectl set image deploy/payments app=registry.example.internal/payments@sha256:9f3c0d...e1

Container registries like ECR can also enforce this with tag immutability turned on, the same idea as Nexus "disable redeploy". The Google SRE book's release-engineering chapter calls the same property hermetic, reproducible builds: the build depends only on pinned inputs, so the same commit always yields the same artifact.

From your world

The image digest is a content hash, exactly like verifying an image with sha256sum before boot system flash:. A tag is a symlink or a DNS name: it can be repointed. A digest is the inode content itself: if one bit changes, it is a different digest. Deploy by digest and you have the same guarantee you had when the line card refused an image whose checksum did not match.
