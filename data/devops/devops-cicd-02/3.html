Jenkins: a declarative Jenkinsfile

Good to know (SDE-2)

Jenkins is a self-hosted automation server. You run a controller (web UI, job config, scheduling, credentials store) and a pool of agents (the machines that actually run builds). The pipeline itself lives in your repo as a Jenkinsfile, so the build is versioned with the code ("pipeline as code").

// Jenkinsfile (declarative)
pipeline {
  agent none                                 // each stage picks its own agent
  options {
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '50'))
  }
  environment {
    VERSION = "1.4.${env.BUILD_NUMBER}"      // immutable per build
  }
  stages {
    stage('Build & Test') {
      agent { label 'linux' }
      options { timeout(time: 30, unit: 'MINUTES') }
      steps {
        sh 'mvn -B clean verify -Drevision=$VERSION'
      }
      post {
        always { junit 'target/surefire-reports/*.xml, target/failsafe-reports/*.xml' }
      }
    }
    stage('Publish') {
      agent { label 'linux' }
      when { branch 'main' }                 // PR builds stop after tests
      steps {
        withCredentials([usernamePassword(credentialsId: 'nexus-ci',
                         usernameVariable: 'NEXUS_USER', passwordVariable: 'NEXUS_PASS')]) {
          sh 'mvn -B deploy -DskipTests -Drevision=$VERSION -s ci-settings.xml'
        }
      }
    }
    stage('Deploy to staging') {
      agent { label 'linux' }
      when { branch 'main' }
      steps { sh './deploy.sh staging $VERSION' }
    }
    stage('Promote to prod') {
      agent { label 'linux' }                // taken only AFTER the input is approved
      when { branch 'main' }
      options { timeout(time: 1, unit: 'DAYS') }   // the approval may wait up to a day
      input { message "Promote ${env.VERSION} to production?" }   // manual gate
      steps { sh './deploy.sh prod $VERSION' }
    }
  }
  post {
    failure { echo "Build ${env.BUILD_NUMBER} failed - notify the team here" }
  }
}

The pieces an interviewer expects you to name:

  • agent - where to run (any machine, a label, a Docker image, a Kubernetes pod template). Here it is agent none at the top and one agent per stage, for a reason: declarative Jenkins evaluates a stage-level input before it enters that stage's agent, so the prod approval waits without holding a build executor. With a pipeline-wide agent the executor would sit idle for hours, and a pipeline-wide 30-minute timeout would also abort the unattended approval. Since verify also runs Failsafe integration tests, junit publishes both report folders.
  • stages / stage / steps - ordered blocks; each stage shows as a column in the UI.
  • when - conditions (branch, tag, changed files). input - pause for a human approval.
  • post - always / success / failure hooks for reports and notifications.
  • withCredentials - pulls a secret from the Jenkins credentials store into an env var for one block only and masks it in the log.

Declarative vs scripted: declarative (pipeline { }) has a fixed structure that Jenkins validates before running. Scripted (node { }) is plain Groovy, more flexible but easy to turn into an unmaintainable program. Default to declarative; drop into a script { } block only when you must. Note the single quotes around sh '...$VERSION': the shell expands the variable, so Groovy never interpolates a secret into the command string.
