Interview questions

Walk me through the Maven build lifecycle. What does "mvn deploy" actually do?

Maven has three lifecycles: clean, default and site. The default lifecycle's main phases are validate, compile, test, package, verify, install, deploy. Asking for a phase runs every earlier phase first. Plugins bind goals to phases: compiler to compile, Surefire to test, jar to package, Failsafe around verify. So mvn deploy compiles, runs unit tests, packages, runs integration tests and checks, installs the artifact into the local ~/.m2, and finally uploads the jar and pom to the remote repository named in distributionManagement, using credentials from settings.xml.

How to answer

Say "phases are cumulative" in the first sentence, list the seven phases, then contrast install (local) with deploy (remote). Mention you use verify for PRs.

Likely follow-ups
  • Difference between a phase and a goal? (A goal is a plugin task; a phase is a slot goals bind to.)
  • How does Maven resolve two versions of one dependency? (Nearest wins; use dependencyManagement.)
What does "build once, deploy many" mean, and why is it important?

Each commit is built and tested once, producing one immutable artifact (a release version in Nexus, an image digest in a registry). Every environment gets that same artifact; only configuration differs and is injected at deploy time. This guarantees what you tested is what you ship, gives exact traceability from production back to a commit, and makes rollback a pointer change instead of a rebuild. Rebuilding per environment lets floating inputs (base images, transitive deps, compilers) drift between staging and production.

How to answer

Definition, then the three benefits (fidelity, traceability, fast rollback), then one concrete mechanism: "we deploy images by digest and the release repo forbids redeploy".

Likely follow-ups
  • How do you handle environment-specific config? (Env vars, ConfigMaps, secrets manager; never baked into the image.)
  • What about a hotfix? (New commit, new version, same pipeline; never patch an existing artifact.)
Compare Jenkins and GitHub Actions. When would you choose each?

Both run pipelines as code. Jenkins is self-hosted: a controller schedules work onto agents, pipelines are Groovy Jenkinsfiles, and everything is extended with plugins. It suits companies with many SCMs, air-gapped networks or special hardware, at the cost of operating and patching the controller and its plugins. GitHub Actions is built into GitHub: YAML workflows, jobs on hosted or self-hosted runners, reusable actions, environments with approvals and OIDC to clouds. It suits teams already on GitHub who want no CI infrastructure to run. The concepts map: agent to runner, stage to job, credentials to secrets, input step to environment approval.

How to answer

Lead with "hosted vs self-operated", give the concept mapping, end with a decision rule. Avoid tool fandom.

Likely follow-ups
  • How do you scale Jenkins? (Ephemeral agents on Kubernetes, no builds on the controller.)
  • How do you secure a self-hosted runner? (Ephemeral, never for public repos, isolated network.)
Your CI build takes 25 minutes. How do you make it faster?

Measure first: look at per-step timings. Then attack the usual suspects in order. Dependency download: cache ~/.m2 keyed on the pom hash and put a Nexus proxy near the runners. Docker builds: order layers so dependencies are cached, use BuildKit cache export. Tests: run in parallel (Surefire forks, matrix sharding), split slow integration tests into a separate job that runs in parallel. Work avoidance: in a multi-module repo build only changed modules and their dependents (mvn -pl module -am). Pipeline shape: run independent jobs in parallel, cancel superseded runs with concurrency groups. Finally, bigger runners if CPU bound.

How to answer

"Measure, then cache, parallelize, avoid work." Give one number you would track, like p50 and p95 build time per step.

Likely follow-ups
  • What should you never cache? (Build outputs across unrelated builds.)
  • How do you find flaky tests? (Track per-test failure rate across reruns; quarantine.)
What are hosted, proxy and group repositories in Nexus?

Hosted repos store artifacts you publish, usually split into releases (write once) and snapshots (many timestamped uploads). Proxy repos cache a remote repository like Maven Central, so builds are fast, keep working when the remote is down, and you have a record of exactly which external bytes you used. A group (Artifactory: virtual) repo combines several behind one URL; builds point only at the group through a Maven mirror.

How to answer

One line per type, then why the proxy matters for reliability and supply-chain security.

Likely follow-ups
  • Why separate snapshot and release repos? (Different mutability and cleanup policies.)
  • How do you clean up? (Retention policies on snapshots; never on releases that may still run in prod.)
How do you manage secrets in a CI/CD pipeline?

Never in the repo or the image. Store them in the CI's secret store (Jenkins credentials, GitHub secrets) or better in a secrets manager, and expose them only to the steps that need them (withCredentials, step-level env). Prefer short-lived credentials: OIDC federation from the CI job to the cloud gives tokens valid for minutes, so there is no long-lived key to leak. Gate production secrets behind protected environments with approvals. Set minimal token permissions, pin third-party actions to commit SHAs, and never run untrusted PR code with secrets.

How to answer

Storage, scope, lifetime, gating, supply chain: five words, one sentence each.

Likely follow-ups
  • Why is pull_request_target dangerous?
  • A secret leaked into a log. What now? (Rotate first, then purge logs, then find the cause.)
How do you version artifacts so production is traceable?

Every build that can reach production gets a unique, never-reused version tied to the commit: semantic version plus build number (1.4.237), or the git SHA, set from CI (Maven's ${revision}). The image is tagged with that version and deployed by digest. The release repo and registry forbid overwriting. The deploy records which version runs where, so "what is in prod?" is one lookup, and git show on the SHA gives the code.

How to answer

Unique, immutable, traceable to commit, recorded at deploy. Mention digest pinning.

Likely follow-ups
  • Why not :latest? (Moving pointer; nodes cache different images; no rollback target.)
Explain a GitHub Actions matrix and dependency caching. What goes in the cache key?

A matrix expands one job into one job per combination of variables (OS, Java version), each on its own runner, in parallel; include/exclude adjust the set and fail-fast controls whether one failure cancels the rest. A cache saves a path at the end of a job under a key and restores it next time. The key should change exactly when the cached content should change: OS plus a hash of the dependency manifest (hashFiles('**/pom.xml')). restore-keys give a prefix fallback so a changed pom still starts from a nearly right cache. Caches are scoped to the branch and default branch, 10 GB per repo, evicted after 7 days unused.

How to answer

Explain the key design rule ("changes exactly when content should change") before syntax.

Likely follow-ups
  • Why does a feature branch not see another feature branch's cache? (Isolation; prevents cache poisoning.)

Scenario: "it worked in staging"

A release passed every staging test. The production deploy job, which rebuilds from the release tag, ships, and errors start: a JSON library behaves differently.
Weak answer: "Add more tests in staging."
Strong answer: The artifact in production is not the artifact that was tested. The rebuild picked up a different transitive version (a range, a snapshot or a moved base image). Roll back by pointing prod at the previous version. Then fix the pipeline: build once, publish an immutable version, promote that same version; pin dependencies and fail release builds that use snapshots; deploy images by digest.
Likely follow-ups
  • How do you prove which jar is in prod? (Version in the manifest, digest in the pod spec.)
