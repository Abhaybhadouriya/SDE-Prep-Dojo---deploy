A taste of the interview questions

Here are three questions you will be able to answer by the end of the track. Try answering each out loud before opening it.

In one minute: what is Docker, and why do companies use it?

"Docker is a tool for packaging an application with everything it needs, its libraries, runtime and config, into an image, and running that image as a container. A container is an isolated Linux process that shares the host kernel, so it starts in well under a second and uses far less memory than a virtual machine. Companies use it because the same image runs identically on a laptop, in CI and in production, which removes 'works on my machine' bugs, and because images are the unit that orchestrators like Kubernetes schedule."

How to answer

Three beats: what it is (package + run), how it works in one phrase (isolated process on a shared kernel), and why the business cares (consistency, speed, it feeds Kubernetes). Do not dive into namespaces unless they ask.

Likely follow-ups
  • How is a container different from a VM? (Page 01)
  • What is inside an image? (Page 02)
  • Is Docker the same as a container? (No: Podman, containerd and CRI-O run containers too.)
Your Docker image is 1.2 GB. How would you make it smaller?

"First I would look at where the size is, with docker history or the dive tool. The usual fixes are a multi-stage build so compilers and build tools stay in the build stage, a smaller base like -slim or distroless, a .dockerignore so .git and test data are not copied, and cleaning package caches in the same RUN step that created them. A Go service often drops from around 800 MB on the full golang image to under 20 MB on a static base."

How to answer

Measure first, then list fixes from biggest win to smallest, then give one trade-off: distroless images have no shell, so debugging needs docker debug or a debug container. Full details on page 03.

Likely follow-ups
  • Why does RUN rm big.tar in a later step not shrink the image?
  • Alpine or Debian slim, and why?
A container keeps dying with exit code 137. What happened?

"137 is 128 plus 9, so the process received SIGKILL. The most common cause is the kernel OOM killer: the container went over its memory cgroup limit, memory.max. I would confirm with docker inspect, which shows OOMKilled: true, and look at docker stats to see memory growth. The fix is either a real memory leak fix or a limit that matches the app, for example making the JVM heap smaller than the container limit."

How to answer

Decode the number, name the likely cause, say how you confirm it, then the fix. Mention the other cause too: docker stop sends SIGKILL after 10 seconds if SIGTERM is ignored.

Likely follow-ups
  • What happens when a container hits its CPU limit instead? (It is throttled, not killed.)
  • How does this look in Kubernetes? (Status OOMKilled, see the requests and limits page.)
