The story: one box for every program

Explain like I'm 5

Long ago, ships carried sacks, barrels, boxes and crates of every shape. Loading a ship took days because every item needed special handling. Then someone said: "Let's put everything inside one standard metal box." Suddenly any crane, any truck and any ship could carry anything, and nobody needed to care what was inside.

Docker does the same thing for computer programs. It packs a program and everything it needs into one standard box, called a container. Any computer that understands the box can run it, and it behaves the same everywhere.

You have probably heard the sentence "but it works on my machine!" A program runs on a developer's laptop and then fails on a server because the server has a different Python version, a missing library, or a different setting. Docker's big idea is to ship the machine's environment together with the program, so that sentence stops being a problem.

This track teaches Docker the way this site teaches everything: we start with a story, give real names to the parts, open up the inside, and finish with interview questions and real production failures. Every page climbs from Level 1 (kid) towards Level 5 (interview-ready).

From your world

You already know most of Docker; you just have not seen the packaging. A container is a normal Linux process created with clone() flags for new namespaces, limited by cgroups, with an OverlayFS root filesystem, and wired to a Linux bridge through a veth pair plus iptables NAT. Docker is the friendly tool and API on top of those kernel features. Where the analogy breaks: the hard new part is not the kernel, it is the ecosystem around it: images, registries, build caches and how teams ship software.

From your code to a running container

Click Next. This is the whole Docker track in five moves; each page zooms into one of them.

  1. You write a Dockerfile: a short recipe saying which base system to start from, which files to copy and which command to run.
  2. docker build follows the recipe and makes an image: a stack of read-only layers, like a frozen snapshot of a filesystem.
  3. docker push uploads the image to a registry, a shared shelf of images.
  4. On any server, docker pull downloads only the layers that server does not already have.
  5. docker run starts a container from the image: an ordinary Linux process with its own namespaces and cgroup limits. One image can start many identical containers.
