Why databases must use volumes: copy-on-write cost

You can technically run Postgres with its data in the writable layer. Do not. Three reasons, from most to least important:

  1. You will lose it. The next docker rm, deploy or re-create deletes the data.
  2. Copy-up is expensive. The first write to any file that came from an image layer copies the whole file up to the writable layer before the write happens. Large files with small random writes (exactly what databases do) suffer the most. Many small layer lookups also add overhead on file open.
  3. Volumes bypass the storage driver. A volume is a plain directory on the host filesystem (ext4 or xfs) bind-mounted in. Reads and writes go at native speed, with no overlay lookups and no copy-up.

Where is the writable layer on disk? With the classic overlay2 storage driver it is under /var/lib/docker/overlay2/<id>/diff. Newer installs of Docker Engine 29 use the containerd image store by default, so snapshots live under containerd's directory (/var/lib/containerd/...) instead. Either way: never edit these by hand. Use docker inspect, docker diff and docker cp.

Docker Desktop (Mac and Windows) is special

On Mac and Windows, containers run inside a small Linux VM. Named volumes live inside that VM's disk (fast). Bind mounts must cross the VM boundary through a file-sharing layer (VirtioFS on macOS), which is slower for workloads with many small files, such as node_modules or big Git trees. The usual trick is the one above: bind-mount your source, keep heavy dependency directories in a named volume.
