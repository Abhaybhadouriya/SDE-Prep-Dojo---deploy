Where does a container write by default?

An image is a stack of read-only layers (see Images & Layers). When a container starts, Docker adds one thin writable layer on top. Every file the app creates or changes goes into that layer.

Prove it to yourself in 30 seconds:

$ docker run --name t1 alpine:3.24 sh -c "echo hello > /note.txt"
$ docker diff t1
A /note.txt
$ docker start -a t1 && docker run --rm alpine:3.24 cat /note.txt
cat: can't open '/note.txt': No such file or directory
$ docker rm t1
t1

docker diff shows what the container changed in its writable layer (A added, C changed, D deleted). A new container from the same image does not see the file, because each container gets its own fresh writable layer. And after docker rm t1, that layer and the note are gone forever.

Stopping is not removing. A stopped container keeps its writable layer. docker start brings back the same files. Only docker rm (or --rm) deletes them. This is why you can still docker cp a log file out of a crashed container.

From your world

This is OverlayFS: a union mount with the image layers as lowerdir and the container layer as upperdir, just like an OpenWrt-style read-only squashfs firmware with a writable overlay partition on top. Changing a file in a lower layer triggers a copy-up of the whole file into the upper layer, similar in spirit to copy-on-write pages after fork(), except the unit is a whole file, not a 4 KiB page. Where the analogy breaks: copy-on-write pages are cheap; copying up a 2 GB database file because you changed one byte is very much not. The full mechanics are on Internals.
