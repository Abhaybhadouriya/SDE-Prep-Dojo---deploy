Bind mounts: for your code and your config

A bind mount makes a host directory or file appear at a path inside the container. It is the same kernel feature as mount --bind. The classic use is development: edit code on your laptop and the server inside the container sees the change immediately.

# Live-reload a Node app: host folder at /app, but keep node_modules in a volume
docker run -d --name dev -p 3000:3000 \
  --mount type=bind,src="$(pwd)",dst=/app \
  --mount type=volume,src=node_modules,dst=/app/node_modules \
  -w /app node:22-alpine npm run dev

Bind mounts hide what is underneath. If the image has files at /app and you bind-mount a host folder there, the container sees only the host folder. The image's files are still in the layer, just covered. That is why the example above puts a volume over /app/node_modules: otherwise your laptop's folder (with no or wrong-platform node_modules) would hide the dependencies installed in the image.

The permissions puzzle (UIDs are just numbers)

The most common bind-mount bug: "Permission denied" when the container writes to the mounted folder, or files on your laptop suddenly owned by root. The reason is simple once you see it: the kernel checks numeric user IDs. The container's /etc/passwd and your host's are different files, but the UID number on each inode is shared.

  • If the container runs as root (UID 0, the default in many images), it can write anywhere in the mount, and new files on your host are owned by root. Annoying in dev, dangerous in principle.
  • If the container runs as a non-root user (good practice), that UID must have permission on the host folder. Use --user "$(id -u):$(id -g)" in dev, or chown the folder to the container's UID.
  • User namespaces (userns-remap, rootless Docker) shift container UIDs to a high host range, so container root is not host root. That improves security but makes bind-mount ownership look even stranger. See Production & Security.
  • On SELinux hosts (Fedora, RHEL) add :z or :Z to the -v option so the mount gets the right label.

From your world

Same as NFS without ID mapping: the server checks the numeric UID the client sends, and if the two machines disagree about who UID 1000 is, you get surprises. A bind mount is mount --bind inside the container's mount namespace; no file is copied and no translation happens. Where the analogy breaks: there is no network or protocol in between; it is the same kernel and the same inode, so permissions and inotify behave exactly as on the host (on Linux).
