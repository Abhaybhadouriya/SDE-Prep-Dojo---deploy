Quick quiz

You write /report.csv in a container (no mounts), stop it, and run docker start on it. Is the file there?

  1. No, stopping deletes the writable layer
  2. Yes, stopping keeps the writable layer; only removing deletes it
  3. Only if the image has a VOLUME
Stop keeps the container and its layer. docker rm deletes them.

Which is the best home for Postgres data files?

  1. The container's writable layer
  2. A tmpfs mount
  3. A named volume
Named volumes survive container removal and avoid copy-on-write overhead. tmpfs is lost on stop.

What does -v ./site:/usr/share/nginx/html create?

  1. A bind mount of the host folder ./site
  2. A named volume called "site"
  3. A tmpfs mount
A left side that looks like a path is a bind mount. A bare name like site: would be a volume.

You bind-mount an empty host folder over /app, where the image had your code. What does the container see?

  1. The image's code, merged with the host folder
  2. Only the empty host folder; the image's files are hidden
  3. An error
Bind mounts cover whatever is beneath. Only a new, empty named volume gets pre-filled from the image.

Why is modifying a large file that came from an image layer slow the first time?

  1. Docker encrypts it
  2. The registry is contacted
  3. OverlayFS copies the whole file up to the writable layer before the write
Copy-up works on whole files. Volumes avoid this because they are not part of the overlay.

A non-root container user (UID 10001) cannot write to a bind-mounted folder owned by UID 1000. The core reason?

  1. The kernel compares numeric UIDs; 10001 is not the owner and lacks write permission
  2. Bind mounts are always read-only
  3. Docker blocks non-root writes
Names come from each side's own /etc/passwd; the kernel only sees numbers on the inode.
