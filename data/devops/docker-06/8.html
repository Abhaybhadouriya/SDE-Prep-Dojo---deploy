The big idea: keep containers stateless

Must know. This rule, and the one-sentence volume / bind mount / tmpfs choice, are the two things from this page every interviewer expects.

Everything on this page leads to one design rule that interviewers love: containers should be stateless and disposable; state lives in volumes or, better, in managed services. A stateless web container can be killed, moved, or multiplied to 50 copies without anyone noticing. Its state (sessions, uploads, orders) lives in a database, a cache like Redis, object storage like S3, or a log like Kafka.

Stateless service containers
  • Scale out by adding copies
  • Any copy can serve any request
  • Deploy = replace containers, roll back = replace again
  • Crash = restart anywhere
Stateful containers (DB, Kafka)
  • Need a volume tied to an identity
  • Cannot just run 5 copies; need replication built into the software
  • Moving them means moving data
  • On Kubernetes: StatefulSets + PVCs (StatefulSets)

From your world

It is the line-card vs. config-store split: line cards (stateless workers) can be pulled and replaced because the authoritative state lives on the route processor and in the startup config. In web systems, app containers are the line cards and the database is the config store. Where it breaks: web databases are themselves clusters with replication and failover, so "the one place state lives" is really a distributed system of its own, covered in HLD Fundamentals.
