Now the real test. We write a row, destroy the container completely, and start a brand-new one on the same volume. Step through it.

  1. Mount. Container #1 starts with pgdata mounted at Postgres's data directory. Because the volume was empty, Docker first copied the image's files at that path into it.
  2. Write. Postgres writes table files and its write-ahead log. They go straight into the volume on the host disk, not into the container's writable layer.
  3. Destroy. docker rm -f db kills the process and deletes the container and its writable layer. The volume is a separate object, so it is untouched.
  4. Re-create. A brand-new container (maybe from a newer patch version of the image) mounts the same volume.
  5. Data is back. Postgres finds its existing data directory and starts with all rows intact. This is how you upgrade a database container safely.
$ docker exec db psql -U postgres -c "CREATE TABLE t(x int); INSERT INTO t VALUES (42);"
INSERT 0 1
$ docker rm -f db
db
$ docker run -d --name db -e POSTGRES_PASSWORD=dev -v pgdata:/var/lib/postgresql/data postgres:17-alpine
$ docker exec db psql -U postgres -c "SELECT * FROM t;"
 x
----
 42
(1 row)

Major-version upgrades are different. Moving Postgres 16 data to 17 is not just a new image; the on-disk format changes and you need pg_upgrade or a dump/restore. The volume keeps your bytes; it does not migrate them. One more trap: from postgres:18 the official image keeps data under /var/lib/postgresql/<major>/docker (for example /var/lib/postgresql/18/docker); mount the volume at /var/lib/postgresql when you move to 18+. If you keep mounting /var/lib/postgresql/data, the new server starts with an empty data directory and your data seems "lost" (it is still in the old volume).

-v or --mount?

Both syntaxes work. --mount is longer but explicit and stricter, so it is the better habit for anything you will read again later.

WhatShort -vLong --mount
Named volume-v pgdata:/var/lib/postgresql/data--mount type=volume,src=pgdata,dst=/var/lib/postgresql/data
Bind mount, read-only-v ./nginx.conf:/etc/nginx/nginx.conf:ro--mount type=bind,src=./nginx.conf,dst=/etc/nginx/nginx.conf,readonly
tmpfs--tmpfs /tmp:size=64m--mount type=tmpfs,dst=/tmp,tmpfs-size=64m
Missing host path (bind)Silently creates an empty root-owned directoryErrors out (good: catches typos)

The rule for -v: if the left side looks like a path (starts with / or .), it is a bind mount; otherwise it is a volume name. -v data:/x and -v ./data:/x mean completely different things.
