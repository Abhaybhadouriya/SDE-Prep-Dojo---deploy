Interview questions

Volumes vs bind mounts vs tmpfs: when do you use each?

A named volume is storage managed by Docker in its own area of the host; it survives container removal, is not tied to a host path, and is the right choice for data the application owns, like database files. A bind mount maps a specific host path into the container; I use it in development to live-reload source code or to inject a config file read-only. tmpfs is RAM-only and disappears when the container stops; I use it for secrets and scratch space, and with a read-only root filesystem. All three bypass the copy-on-write layer, so they also perform better than writing into the container.

How to answer

Give the one-sentence rule (app's data, my files, never on disk), then one example each. Add the performance point (no copy-up) to show depth.

Likely follow-ups
  • What happens to the image's files when you mount over a directory?
  • How does this map to Kubernetes? (PVC, hostPath, emptyDir with medium Memory)
Where does a container's data go when you write a file, and what happens when the container stops or is removed?

Unless the path is a mount, the write goes into the container's writable layer, the top layer of an OverlayFS union mount over the read-only image layers. Stopping keeps it, so docker start sees the file again. Removing deletes the writable layer and the file. A new container from the same image starts with a clean writable layer and never sees it. So anything that must survive goes to a volume or an external store.

How to answer

Separate the three events clearly: stop, remove, new container. Mention docker diff as the way to see the layer's changes.

Likely follow-ups
  • What is copy-up?
  • Why does deleting a file in a container not free space in the image?
Why should a database container's data not live in the container's writable layer?

Two reasons. Durability: the writable layer is deleted with the container, so a redeploy or re-create loses everything. Performance: OverlayFS copy-on-write copies an entire file up from the image layer the first time it is modified and adds lookup overhead, which hurts databases that do many small random writes to big files. A volume is a plain host directory mounted in, so it is durable across containers and runs at native filesystem speed. In production I would also want the volume on reliable storage with backups, or use a managed database.

How to answer

Lead with durability (obvious), then show depth with copy-up. Close with a production-grade alternative.

Likely follow-ups
  • How do you back up a Docker volume?
  • How would you run a database on Kubernetes? (StatefulSet + PVC, or managed DB)
A container running as a non-root user gets "Permission denied" writing to a bind-mounted folder. Explain and fix.

The kernel checks the numeric UID of the process against the inode's owner and mode. The container's user (say UID 10001) is not the owner of the host folder (say UID 1000), and the folder is not writable by others, so writes are denied. Names do not matter because each side has its own /etc/passwd. Fixes: run the container with the host user's UID (--user 1000:1000) in development, or chown the folder to the container's UID, or use a named volume, which Docker initialises with the image's ownership for that path. With user namespaces on, remember the container UID is shifted on the host.

How to answer

"UIDs are numbers, not names" is the key sentence. Then give the dev fix and the production fix separately, and do not suggest running as root.

Likely follow-ups
  • Why is running as root inside a container risky?
  • What does rootless Docker change?
Why do people say containers should be stateless? Where does the state go?

Containers are replaced all the time by deploys, crashes and autoscaling. If a container holds state, every replacement risks data loss and you cannot simply run more copies behind a load balancer. So service containers keep no local state: sessions go to Redis (an in-memory key-value store) or a signed cookie, files to object storage, business data to a database, events to Kafka. The few truly stateful components (databases, brokers) run with persistent volumes and their own replication, ideally as managed services or as Kubernetes StatefulSets with stable identities.

How to answer

Explain the benefit (horizontal scaling, disposability), list where each kind of state goes, then acknowledge the stateful exceptions and how they are run.

Likely follow-ups
  • How would you handle user sessions with 10 web containers?
  • Would you run Kafka in containers? (See Kafka on K8s.)

Scenario: "we redeployed and the uploads disappeared"

A small team runs their app with docker run on one VM. Users upload profile pictures. After a deploy (stop old container, run new image), all uploaded pictures are gone. The database still has the file names.

Weak answer: "Use docker commit to save the container before deploying."

Strong answer: The uploads were written into the old container's writable layer, which was removed with it. If the old container still exists (stopped, not removed), recover the files with docker cp old:/app/uploads ./recovered. Then fix the design: mount a named volume at the upload path so deploys keep the files, and for anything beyond one VM move uploads to object storage (S3, Azure Blob) so any number of app containers can serve them. Add a deploy checklist item that lists every writable path, and run the container with --read-only so an unexpected write path fails loudly in testing instead of silently losing data.

Likely follow-ups
  • Why is docker commit a bad deployment practice?
  • How would this look on Kubernetes with 3 replicas?

60-second answer - "How does storage work in Docker?": "A container's filesystem is an OverlayFS union: read-only image layers plus one writable layer per container. Writes go to that layer, which is deleted when the container is removed, and modifying an image file costs a full-file copy-up. For data that must survive or be fast, I mount storage from outside: a named volume, managed by Docker under /var/lib/docker/volumes, for data the app owns like a database; a bind mount for host files like source code in dev or a read-only config; and tmpfs for secrets and scratch that must never hit disk. In production I keep service containers stateless, run them read-only with a small tmpfs, and push state to databases, object storage or Kafka, with real backups."
