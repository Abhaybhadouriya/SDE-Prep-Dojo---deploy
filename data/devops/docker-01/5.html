What actually happens when you type docker run

Must know. This walkthrough is asked in some form in almost every container conversation. This is the short version; page 08 opens every box.

Interviewers love "walk me through docker run -p 8080:80 nginx". Here is the chain, naming the real program at each step. Click Next or Play.

  1. CLI to daemon. The docker command is only a client. It sends a REST API request over the Unix socket /var/run/docker.sock to dockerd, the Docker daemon. (REST API = the daemon accepts plain HTTP requests like POST /containers/create; the docker CLI is just an HTTP client. Think of a RESTCONF/NETCONF management API on a router.)
  2. Find the image. dockerd turns nginx into the full name docker.io/library/nginx:latest (here we asked for 1.30). If it is not on disk, it asks the registry for the manifest for your CPU type and downloads only the layers it does not already have. (Manifest = the image's table of contents; digest = its SHA-256 fingerprint. Page 02 explains both.)
  3. Hand over to the runtime. dockerd asks containerd to create the container. containerd starts a small containerd-shim process for it, and the shim calls runc, the low-level tool that talks to the kernel.
  4. Build the fences. runc reads an OCI config.json, calls clone()/unshare() for new namespaces, creates a cgroup and writes the limits, and mounts the image layers as the new root filesystem with pivot_root.
  5. Wire the network. Docker creates a veth pair: one end becomes eth0 inside the container, the other is plugged into the docker0 Linux bridge. For -p 8080:80 it adds an iptables DNAT rule from host port 8080 to the container's port 80.
  6. Run the program. runc execve()s the image's entrypoint, so nginx becomes PID 1 in the new PID namespace. runc then exits; the shim stays as the parent, holding stdio and waiting for the exit code. The dot is an HTTP request arriving on port 8080.

Must know: steps 1, 2 and 6 (client and daemon, the image is found or pulled, your program becomes PID 1). Steps 3 to 5 are a preview: page 08 opens up the runtime and the fences, and page 05 the network. You do not need their details yet.

Why does the shim stay around? It lets the daemon restart without killing containers, like non-stop forwarding on a router; the full story is on page 08.

Page 05 shows the packet path of -p rule by rule, and page 08 opens up every box in this stepper. For now, remember the chain: CLI, dockerd, containerd, shim, runc, your process. Why so many? Each does one job, and the lower ones (containerd, runc) are also used without Docker, for example by Kubernetes.
