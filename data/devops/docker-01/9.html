Interview questions

The 60-second answer: "What is a container and how is it different from a VM?"
"A container is a normal Linux process that the kernel isolates and limits. Namespaces give it its own view of the filesystem, process IDs, network and hostname, and cgroups cap how much CPU and memory it can use. It ships with its own libraries in an image, so it runs the same everywhere. The key difference from a VM is the kernel: a VM boots its own kernel on a hypervisor and gets hardware-level isolation, while containers all share the host kernel. That makes containers much lighter, megabytes instead of gigabytes, and they start in milliseconds instead of seconds. The cost is weaker isolation, so in practice clouds run containers inside VMs, and for untrusted code you use a sandbox like gVisor or a microVM like Firecracker."

What is the difference between a container and a virtual machine?

A VM virtualizes hardware: a hypervisor gives each VM virtual CPUs, memory and devices, and each VM runs its own full operating system and kernel. A container virtualizes the operating system: it is a process on the host, and the host kernel isolates it with namespaces and limits it with cgroups. So containers are smaller and faster to start, but every container depends on the same kernel, which is a larger shared attack surface.

How to answer

Draw the two stacks (the diagram above, six boxes each). Name the one key difference, the kernel, then give the trade-off in both directions. Finish with the real-world twist: they are combined, not competing.

Likely follow-ups
  • Can you run a Windows container on a Linux host? (No, the kernel must match.)
  • Why does Docker Desktop need a VM on a Mac?
  • Where does Firecracker fit?
If containers share the kernel, what exactly keeps them apart?

Several kernel features stacked together. Namespaces (mnt, pid, net, uts, ipc, cgroup, and optionally user) limit what each process can see. cgroups limit what it can use. Capabilities split root's powers so the container keeps only a small set. Seccomp filters block dangerous system calls. AppArmor or SELinux add mandatory access control. And the root filesystem is a separate overlay mount, so it cannot see host files unless you mount them in.

How to answer

Give the list in order "see, use, do": namespaces (see), cgroups (use), capabilities + seccomp + LSM (Linux Security Module: AppArmor or SELinux) (do). Then show you know the limit: all of these are enforced by one kernel, so a kernel bug breaks them all.

Likely follow-ups
  • What is the user namespace and why is it off by default?
  • Name a real container escape. (runc CVE-2019-5736 or CVE-2024-21626.)
Walk me through what happens when you run docker run -p 8080:80 nginx.

The CLI sends a REST call over /var/run/docker.sock to dockerd. dockerd resolves the name to docker.io/library/nginx:latest, pulls the manifest for the host's platform and downloads any missing layers by digest, then unpacks them. It asks containerd to create the container; containerd starts a shim, which runs runc. runc reads the OCI config, creates namespaces and a cgroup, mounts the overlay root filesystem, and execs the nginx entrypoint as PID 1, then exits. Networking creates a veth pair between the container's eth0 and the docker0 bridge, and adds an iptables DNAT rule from host port 8080 to container port 80. Logs from stdout go to the json-file log driver.

How to answer

Use the stepper order: client, daemon, image, runtime, fences, network, process. Name each real program. If you have time, offer one deeper branch: "I can go into the packet path of the DNAT rule if useful", which plays to a networking background.

Likely follow-ups
  • Why does the shim exist?
  • What if the image was built on an ARM Mac?
  • Why can other machines on the network reach port 8080? (It binds 0.0.0.0 by default.)
Can a process inside a container crash the host? How would you run untrusted user code safely?

Yes. All containers make system calls into the same kernel, so a kernel bug can panic the host, and runtime bugs have allowed escapes. To run untrusted code, for example in an online judge, I would add layers: a non-root user, all capabilities dropped, the default or a stricter seccomp profile, no network, read-only root filesystem, tight cgroup limits on memory, CPU and pids, and a timeout. For real multi-tenant safety I would use a stronger sandbox: gVisor, which handles most system calls in a user-space kernel, or a microVM like Firecracker or Kata, which gives hardware isolation with a small overhead.

How to answer

Admit the risk first (honesty scores), then defence in depth from cheap to strong, then the choice with its cost: gVisor costs some system-call performance, microVMs cost a bit of start-up time and memory.

Likely follow-ups
  • How would you keep start-up latency low? (Warm pool of sandboxes.)
  • How would you stop a fork bomb? (pids.max via --pids-limit.)
A container hits its memory limit, and another hits its CPU limit. What happens to each?

At the memory limit (memory.max), the kernel tries to reclaim memory; if it cannot, the OOM killer kills a process in that cgroup with SIGKILL, and the container exits with 137 and OOMKilled: true. At the CPU limit (cpu.max), nothing is killed: the scheduler throttles the cgroup until the next period, so the app gets slower and latency goes up. You see that in cpu.stat as nr_throttled and throttled_usec.

How to answer

Contrast the two in one sentence ("memory is fatal, CPU is slow"), then give the evidence you would check for each. Link it to Kubernetes limits, where the same thing happens to pods.

Likely follow-ups
  • Why might a Java app get OOM-killed even with a "big enough" heap? (Heap is not the only memory: metaspace, threads, native buffers.)
  • How do Kubernetes requests differ from limits?

Scenario: "It works on my laptop but not in the container"

A teammate's Flask app works when run directly on a laptop. Inside a container, started with -p 5000:5000, the browser shows "connection reset" (or an empty reply). The container is running and logs show "Running on http://127.0.0.1:5000".

Weak answer: "Docker networking is flaky, I would restart Docker or try host networking."

Strong answer: "The log is the clue: the app binds to 127.0.0.1, which inside the container is the container's own loopback, in its own network namespace. Docker's port forwarding delivers traffic to the container's eth0 address, where nothing listens. From another machine you would see "connection refused" instead, because there is no docker-proxy in the path to accept the connection first; page 05 explains both. The fix is to bind to 0.0.0.0, for example flask run --host=0.0.0.0. I would confirm with docker exec and ss -ltn inside the container before and after. Other usual suspects for this class of bug are missing environment variables, a different CPU architecture, and using localhost to reach a database that is really in another container."

Likely follow-ups
  • Why does --network host "fix" it, and why is that a bad fix?
  • How would the app reach a Postgres container?
