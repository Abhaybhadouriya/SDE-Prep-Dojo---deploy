How isolated is a container, really?

Good to know. This section climbs fast. Read it for the big picture; each tool named here gets a full explanation on page 08 and page 09. For SDE-1 you can skim it.

Here is the honest answer to the learner question "if everything shares my kernel, how is that isolated, and can a container crash the kernel?"

  • Yes, a container can hurt the kernel. Every system call from every container goes into the same host kernel. A kernel bug triggered from one container can panic the whole machine and take every container down with it. A container escape bug can give a process inside the container control of the host.
  • Real escapes have happened. In 2019, CVE-2019-5736 let a malicious container overwrite the host's runc binary through /proc/self/exe, turning root-in-container into root on the host. In January 2024, the "Leaky Vessels" bug CVE-2024-21626 let a crafted image escape through a leaked file descriptor during WORKDIR handling; it was fixed in runc 1.1.12. The lesson: keep the runtime patched, not only your images.
  • Docker adds more walls by default. Beyond namespaces and cgroups, Docker drops most Linux capabilities (think of root's powers cut into separate keys, and the container only gets some of the keys: it keeps 14, such as CHOWN and NET_BIND_SERVICE, and drops powerful ones like SYS_ADMIN), applies a seccomp filter (a list of kernel calls the process is not allowed to make) that blocks around 44 risky system calls such as mount, reboot and kexec_load, and adds an AppArmor or SELinux profile (a rule book saying which files and actions the program may touch). Details on page 08; page 09 shows how to tighten these further.
  • Namespaces isolate visibility, not performance. cgroups cap CPU and memory, but containers still share CPU caches, kernel locks and NIC queues. Netflix reported in 2026 that even with careful cgroup and traffic-shaping tuning on Titus, one noisy container could still hurt its neighbours, so they added a mode that gives sensitive workloads their own right-sized VM.

Say this in interviews: "A container is isolation by the kernel, a VM is isolation by the hardware. Containers win on speed and density; VMs win on isolation strength. For untrusted multi-tenant code I would use a sandbox like gVisor or a microVM like Firecracker, which is what AWS Lambda does."

Limits: what happens at the edge

cgroups behave very differently for memory and CPU, and this difference is a favourite interview trap.

# memory: go over the limit and the kernel OOM killer kills you
docker run --rm --memory=64m --name hog python:3.12-slim \
  python -c "x = bytearray(200 * 1024 * 1024)"
echo "exit code: $?"

# CPU: go over the limit and you are slowed down (throttled), not killed
docker run -d --rm --cpus=0.5 --name spin alpine:3.24 sh -c 'while :; do :; done'
docker stats --no-stream spin
docker rm -f spin
$ docker run --rm --memory=64m --name hog python:3.12-slim python -c "x = bytearray(200 * 1024 * 1024)"
$ echo "exit code: $?"
exit code: 137
$ docker stats --no-stream spin
CONTAINER ID   NAME   CPU %     MEM USAGE / LIMIT     MEM %   NET I/O       BLOCK I/O   PIDS
a41b9e0c7d22   spin   50.12%    1.1MiB / 7.6GiB       0.01%   1.2kB / 0B    0B / 0B     1

Exit code 137 means 128 + 9: the process got signal 9, SIGKILL, from the OOM killer. Without --rm, docker inspect would show "OOMKilled": true. The CPU hog, on the other hand, keeps running at about 50% of one CPU forever. Memory over the limit is fatal; CPU over the limit is just slow.
