Why the world needed containers

Before we learn the parts, let us see the problem containers solved. Software teams went through three stages, and each stage fixed the pain of the one before it.

  1. Bare metal. One server, one operating system, many apps installed side by side. App A needs library version 1, app B needs version 2, and they break each other. Servers sit mostly idle because sharing is risky.
  2. Virtual machines. A hypervisor (a program that creates pretend hardware) runs many guest operating systems on one server. Apps are separated well, but each VM carries a whole OS: gigabytes of disk and a boot that takes seconds to minutes.
  3. Containers. Keep one kernel, but give each app its own private view of files, processes and network. Each app carries only its own libraries. Containers are megabytes and start in well under a second.
  4. Both together. In real clouds, containers usually run inside VMs. Netflix's Titus platform, for example, runs containers on top of EC2 virtual machines: the VM is the strong wall between customers, and containers pack many apps densely inside it.
