The two kernel tricks: namespaces and cgroups

Explain like I'm 5

A horse in a busy city wears blinkers so it only sees the road in front of it. It still walks on the same road as everyone else. Namespaces are blinkers for a program: it sees only its own little world.

At lunch, everyone gets a tray with a fixed size. If you try to pile on more food than the tray holds, the lunch lady takes your tray away. cgroups are lunch trays for programs: they limit how much memory and CPU each one can take.

A container is built from exactly these two ideas, plus a filesystem trick we cover on the next page.

  • Namespaces control what a process can see. Linux has eight kinds. Docker uses six by default: mnt (its own mount table, so its own /), pid (its own process numbers, starting at 1), net (its own network interfaces, IP, routing table and firewall rules), uts (its own hostname), ipc (its own shared memory and message queues), and cgroup (its own view of the cgroup tree). The user namespace is only used in special modes (rootless Docker or user-namespace remapping), and the time namespace is not used.
  • cgroups (control groups) control how much a process can use: memory, CPU time, number of processes, disk I/O. Modern systems use cgroup v2, a single tree mounted at /sys/fs/cgroup.

From your world

Start with the network namespace, because you already know its twin. A net namespace is a VRF for a process. Each one has its own interfaces, routing table, ARP/neighbour table and iptables rules, the same way a VRF gives each customer a private routing instance on a Cisco or Ciena box. And cgroup cpu.max is a policer: CFS bandwidth control gives a quota of CPU microseconds per period (by default 100 ms), like a token bucket on an interface. Where it breaks: a VRF isolates only routing; a container stacks six namespaces at once, and it still shares one kernel scheduler, page cache and NIC queues with its neighbours.

See it from the host: a container is just a process

This is the experiment that makes everything click. Start a container, then look at it from outside, on a Linux host. On Windows or macOS, see Lab setup on Windows/macOS for two ways to get a host shell (WSL 2 Ubuntu, or nsenter into Docker Desktop's VM); or just read the output.

docker run -d --name web --memory=256m nginx:1.30
PID=$(docker inspect -f '{{.State.Pid}}' web)
ps -o pid,user,cmd -p "$PID"
sudo ls -l /proc/$PID/ns
cat /proc/$PID/cgroup
cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' web).scope/memory.max
$ ps -o pid,user,cmd -p "$PID"
    PID USER     CMD
  48213 root     nginx: master process nginx -g daemon off;
$ sudo ls -l /proc/48213/ns
lrwxrwxrwx 1 root root 0 Nov 23 10:12 cgroup -> 'cgroup:[4026532671]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 ipc -> 'ipc:[4026532669]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 mnt -> 'mnt:[4026532667]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 net -> 'net:[4026532672]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 pid -> 'pid:[4026532670]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 time -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 user -> 'user:[4026531837]'
lrwxrwxrwx 1 root root 0 Nov 23 10:12 uts -> 'uts:[4026532668]'
$ cat /proc/48213/cgroup
0::/system.slice/docker-8d3f1c2a9e4b....scope
$ cat /sys/fs/cgroup/system.slice/docker-8d3f....scope/memory.max
268435456

Read it slowly. On the host, nginx is an ordinary process with an ordinary PID (48213 here; your number will differ). Inside the container the same process believes it is PID 1. Its cgroup, ipc, mnt, net, pid and uts namespace numbers are new, while time and user point to the same numbers as every normal host process (check with readlink /proc/1/ns/user). And the --memory=256m flag simply became the number 268435456 in a cgroup file. No magic: Docker wrote a file.

The cgroup path shown assumes the common systemd cgroup driver; with the cgroupfs driver it lives under /sys/fs/cgroup/docker/<id> instead. Clean up with docker rm -f web.
