Two kinds of failure: poison and transient

The most important design decision in a stream processor is not the happy path. It is: when a record fails, is it the record's fault or the world's fault?

Transient (the world's fault)
  • Price service timed out
  • Catalog database restarting
  • Network blip
  • Retrying later can work, so send it to orders.retry
Poison (the record's fault)
  • Not valid JSON
  • Missing items field
  • Unknown product, quantity of -3
  • Retrying will never work, so send it to orders.dlq

The enricher turns this decision into two Python exception classes. The business logic raises one or the other; the main loop routes by type. This is the real code:

# services/enricher/enricher.py (excerpt)
class PoisonMessage(Exception):
    """Retrying cannot fix this record. Send it to the DLQ."""

class TransientError(Exception):
    """Might work later (dependency down / timeout). Send to retry topic."""

def enrich(raw: bytes | None, catalog: Catalog) -> dict:
    """Pure-ish business logic: validate + add prices. Raises Poison/Transient."""
    try:
        order = json.loads(raw or b"")
    except (ValueError, UnicodeDecodeError) as exc:
        raise PoisonMessage(f"not valid JSON: {exc}") from exc
    if not isinstance(order, dict):
        raise PoisonMessage("event is not a JSON object")
    for field in ("order_id", "customer_id", "items"):
        if field not in order:
            raise PoisonMessage(f"missing field {field}")
    ...
    for item in order["items"]:
        qty = item.get("quantity") if isinstance(item, dict) else None
        if not isinstance(qty, int) or qty <= 0:
            raise PoisonMessage(f"bad quantity in {item}")
        name, unit = catalog.price(item.get("product_id", ""))   # may raise either kind
        ...

And inside Catalog.price(), a database connection error becomes TransientError ("try later"), while a product that is not in the catalog becomes PoisonMessage ("never going to work"). The split is made where the knowledge is.

Careful: if you treat everything as transient, one bad record loops forever through the retry topic and wastes capacity. If you treat everything as poison, a 30-second database restart fills your DLQ with thousands of perfectly good orders. (Honest note: ShopStream's default retry ladder lasts only about 30 s at most, so even a short restart can exhaust it. For real outages raise BASE_BACKOFF_MS and MAX_ATTEMPTS, for example 5000 and 6 gives caps of 5, 10, 20, 40, 60, 60 s, up to about 3 minutes.) Classify at the point where you know why it failed.

Why not just retry in place?

The simplest retry is "sleep and try again, right here". In Kafka that is a trap. A partition is a single ordered line, and one consumer owns it. If the consumer sleeps on record 57, records 58, 59, 60 and every other order in that partition wait too. This is called head-of-line blocking. Worse, if the consumer does not call poll() for longer than max.poll.interval.ms (5 minutes by default), the group coordinator decides it is dead and triggers a rebalance.

From your world

Head-of-line blocking is exactly the HOL problem in an input-queued switch: one packet waiting for a busy output port blocks the packets behind it that want free ports. The fix there is virtual output queues; the fix here is a separate queue (topic) for the slow cases. Where it breaks: switch VOQs keep per-flow order, but a Kafka retry topic does not (see the ordering note below).
