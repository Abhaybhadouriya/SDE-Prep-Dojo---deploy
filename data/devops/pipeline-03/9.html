Try it: turn on failures and watch the routes

The enricher has two demo knobs. Put them in .env (or set them in your shell) and recreate the enricher:

# 20 % of price lookups "time out"
echo "TRANSIENT_FAIL_RATE=0.2" >> .env
docker compose up -d enricher
python loadgen/loadgen.py --rps 20 --seconds 60 --bad 0.05

# Watch where records go
curl -s localhost:9090/api/v1/query --data-urlencode 'query=sum by (outcome) (rate(shopstream_enricher_records_total[1m]))'
docker compose logs -f retry-worker
$ docker compose logs -f retry-worker
retry-worker-1  | ... INFO  retry-worker retried key=b'C-17' attempt=1
retry-worker-1  | ... INFO  retry-worker retried key=b'C-03' attempt=2
retry-worker-1  | ... INFO  retry-worker retried key=b'C-17' attempt=2

In Grafana (localhost:3000) the Enricher outcomes per second panel splits into three lines: enriched (most), retry (about a fifth of lookups, and more as retries also fail), and dlq (the 5 % unknown products, plus the unlucky orders that failed four retries in a row). In kafka-ui (localhost:8080), open orders.retry and look at the message headers: you will see attempt climb.

Set it back with TRANSIENT_FAIL_RATE=0.0 and docker compose up -d enricher again.

Try it: a schema change that is safe, and one that is not

Send an order with an extra optional field the code has never heard of:

curl -s -X POST localhost:8000/orders -H "content-type: application/json" \
  -d '{"customer_id":"C-77","items":[{"product_id":"P-100","quantity":1}],"coupon":"DIWALI10"}'

The order is accepted, but look in kafka-ui at orders.created: there is no coupon. The order-api's Pydantic model ignores unknown fields, so the event it builds never has one. That is the first lesson: every hop decides what to do with fields it does not know. Now write the field straight into the topic, as a newer producer would:

echo 'C-77|{"order_id":"cpn-1","customer_id":"C-77","created_at":"2026-11-23T10:00:00+00:00","items":[{"product_id":"P-100","quantity":1}],"coupon":"DIWALI10"}' | \
  docker compose exec -T kafka-1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 --topic orders.created \
  --property parse.key=true --property key.separator='|'

The enricher builds its output with {**order, ...}, so coupon passes straight through to orders.enriched; the sink writes only the columns it knows and ignores it. Adding an optional field is safe. Now imagine a producer renames items to lines: the enricher's "missing field items" check sends every new order to the DLQ. That is why the rule is "add optional fields, never rename or change a type", and why real systems put a Schema Registry check in CI.

Experiment: scale the enricher to 3 (docker compose up -d --scale enricher=3). Each replica gets its own container hostname, so its own transactional.id. Look at the logs for assigned and revoked lines: with the cooperative-sticky strategy only the partitions that move are revoked.
