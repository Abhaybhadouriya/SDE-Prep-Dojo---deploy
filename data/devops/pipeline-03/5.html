Exactly-once inside Kafka: the transaction loop

The enricher reads a record and writes a record. Two things must happen: the output must be written, and the input offset must be committed. If you do them one after the other, a crash in between gives you either a lost record (offset committed, output missing) or a duplicate (output written, offset not committed, so you read it again).

Kafka transactions make both happen together. The trick is that a consumer offset commit is itself just a write to an internal topic, __consumer_offsets. So a transaction can include the output records and the offset write, and commit them as one unit.

  1. Consume a batch. consumer.consume(num_messages=200, timeout=1.0) returns up to 200 records, here offsets 100 to 104.
  2. Begin. producer.begin_transaction(). The first write tells the transaction coordinator (the broker that owns this transactional.id's partition of __transaction_state) which partitions are in the transaction.
  3. Produce outputs. Each record goes to enriched, retry or dlq. They are really written to the logs, but read_committed consumers cannot read past them yet.
  4. Add the offsets. send_offsets_to_transaction(consumer.position(...), group_metadata) puts "enricher has done up to 104" into the same transaction.
  5. Commit. The coordinator writes a COMMIT marker into every partition involved. Now the outputs and the offset become visible at the same moment.
  6. Or crash. If the enricher dies or hits an error before commit, the transaction is aborted (by the code, or by the coordinator after transaction.timeout.ms). Readers skip the aborted records, the offset never moved, and the batch is read again.

Here is the real loop, trimmed only of the per-record routing you saw above:

# services/enricher/enricher.py (excerpt)
    producer = Producer({
        **idempotent_producer_config(),
        # Stable id per instance. A restarted instance with the same id "fences"
        # its zombie predecessor (broker bumps the producer epoch).
        "transactional.id": os.getenv("TRANSACTIONAL_ID", f"enricher-{HOSTNAME}"),
        "transaction.timeout.ms": 60000,
    })
    producer.init_transactions(30)
    ...
    while stop.running:
        msgs = consumer.consume(num_messages=BATCH_SIZE, timeout=1.0)
        if not msgs:
            continue
        producer.begin_transaction()
        try:
            for m in msgs:
                ...                       # enrich -> produce to enriched / retry / dlq
            # Commit the INPUT offsets as part of the same transaction.
            # (The real code commits only what it finished if the batch ran
            #  past BATCH_BUDGET_S, and seeks back to re-read the rest.)
            producer.send_offsets_to_transaction(
                consumer.position(consumer.assignment()),
                consumer.consumer_group_metadata(), 30)
            producer.commit_transaction(30)
        except KafkaException as exc:
            err = exc.args[0]
            TXN_ABORTS.inc()
            if err.txn_requires_abort():
                producer.abort_transaction(30)
                rewind(consumer)
            elif err.retriable():
                producer.abort_transaction(30)
                rewind(consumer)
            else:
                # Fatal (e.g. we were fenced by a newer instance). Exit; k8s restarts us.
                raise

Three details are easy to miss:

  • rewind() after abort. Aborting the transaction does not move the consumer back. The consumer's in-memory position is already past the batch. So the code seeks every assigned partition back to its last committed offset and reads the batch again. Forget this and an aborted batch is silently skipped.
  • consumer_group_metadata(). This passes the group's generation to the broker. If a rebalance happened and this instance no longer owns the partitions, the commit is rejected instead of corrupting offsets.
  • The batch has a time budget. One transaction covers a whole batch of up to 200 records. If one batch takes longer than transaction.timeout.ms (60 s), the coordinator aborts it and the batch is re-read in a loop; past max.poll.interval.ms (5 min) the group also kicks the consumer out. So batch time must stay well below both. The enricher stops a batch after BATCH_BUDGET_S (20 s), commits what it finished and re-reads the rest, and its catalog lookup has a small circuit breaker: after the database fails once, it fails fast for DB_COOLDOWN_S (5 s) instead of spending a 3-second connect timeout on every record.
  • The transactional producer is also idempotent. idempotent_producer_config() sets enable.idempotence, acks=all and infinite retries, so the broker de-duplicates producer retries using a producer id and per-partition sequence numbers.

Zombies and fencing

A zombie is an old instance that everyone thinks is dead but is still running: for example a pod that froze in a long GC pause or lost its network, was replaced, and then woke up. If both the old and new instance commit transactions for the same partitions, you get duplicates.

The fix is a stable transactional.id. When the new instance calls init_transactions(), the coordinator bumps the epoch (a generation number) for that id and aborts anything the old epoch left open. When the zombie wakes and tries to commit with the old epoch, the broker rejects it with a fatal ProducerFenced error, and the enricher code exits. On Kubernetes the pod name is injected as HOSTNAME, so transactional.id = enricher-<pod name>. Kafka 4.0 brokers support transaction protocol v2 (KIP-890): clients that also speak it bump the epoch on every transaction, closing older "hanging transaction" holes. The server-side check that a partition was really added to the transaction protects all clients, old ones included.

Gotcha from the project's troubleshooting table: "a fatal ProducerFenced means two instances had the same transactional.id." If you hard-code the id, every replica fences every other one and the group crash-loops.

From your world

The transaction coordinator is a two-phase-commit arbiter, and the epoch is a generation number like a VRRP or Raft term: whoever holds the newest number is the only one allowed to write. The COMMIT marker is a control record written into each data log, similar to a barrier token in a pipeline. Where it breaks: classic 2PC can block if the coordinator dies; Kafka's coordinator state is itself a replicated log, so another broker takes over and finishes or aborts the transaction.

Where exactly-once stops

Kafka EOS covers read from Kafka, process, write to Kafka. It does not cover anything outside Kafka: a database write, an email, a payment API call. If the enricher sent an email inside the loop and then aborted, the email is already sent, and the retry sends it again. Outside Kafka, you need a different tool: idempotent writes.
