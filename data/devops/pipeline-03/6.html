The idempotent sink: effectively-once into Postgres

The postgres-sink cannot join a Kafka transaction, because Postgres is not Kafka. So it uses the oldest reliable recipe in distributed systems:

At-least-once delivery + idempotent write = effectively exactly-once. Commit the offset only after the database commit, and make the database write safe to repeat.

The "safe to repeat" part is a SQL upsert keyed on order_id, the table's primary key:

-- services/postgres-sink/sink.py (the UPSERT statement)
INSERT INTO orders (order_id, customer_id, total_cents, currency, items, created_at,
                    kafka_partition, kafka_offset)
VALUES (%(order_id)s, %(customer_id)s, %(total_cents)s, %(currency)s, %(items)s,
        %(created_at)s, %(kafka_partition)s, %(kafka_offset)s)
ON CONFLICT (order_id) DO UPDATE SET
    total_cents = EXCLUDED.total_cents,
    items       = EXCLUDED.items,
    kafka_partition = EXCLUDED.kafka_partition,
    kafka_offset    = EXCLUDED.kafka_offset,
    updated_at  = now()
-- Only move forward: an older copy never overwrites a newer one.
WHERE orders.kafka_offset <= EXCLUDED.kafka_offset

The last line is a nice extra: if an older copy of an order arrives after a newer one (for example during a replay), it does not overwrite the newer row. That works because the same order_id always has the same key, so it is always in the same partition, so its offsets can be compared.

The loop then commits in the right order:

# services/postgres-sink/sink.py (excerpt)
        while stop.running:
            try:
                with conn.transaction():
                    with conn.cursor() as cur:
                        cur.executemany(UPSERT, rows)
                break
            except psycopg.OperationalError as exc:
                # DB down: keep the batch, reconnect, try again. Lag grows meanwhile
                # (that is backpressure - Kafka buffers for us).
                DB_ERRORS.inc()
                time.sleep(2)
                conn = connect()
        else:
            break  # shutting down without writing: do NOT commit offsets
        WRITTEN.inc(len(rows))
        consumer.commit(asynchronous=False)  # commit AFTER the DB commit

From your world

The sink's own docstring says it: like a NIC driver that only advances the RX ring head after the packet was copied into the socket buffer, and the copy is safe to repeat. The primary key is the sequence number a TCP receiver uses to drop retransmitted segments. Where it breaks: TCP sequence numbers are per connection, but order_id is global and lives forever in the table, so it also catches duplicates from client retries days apart.

Notice what the sink does when the database is down: it keeps the batch, reconnects every 2 seconds, and does not commit offsets. Kafka holds the records. Lag grows. That is backpressure done right: the slow part slows only itself, and the upstream order-api keeps accepting orders. The failure drills page lets you watch this happen.

The same idea is behind a payment ledger's idempotency key; see Digital Wallet & Ledger.
