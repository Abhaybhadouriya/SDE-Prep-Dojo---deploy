The map: four topics, five workers

Here is everything that happens after the order-api writes an OrderCreated event. Watch the dots: green is a good order, gold is an order taking the retry loop, red is a poison record going to the DLQ.

Every worker is a small Python program that uses confluent-kafka (the Python wrapper around librdkafka, the C client library). They all share one helper file, shopstream_common.py, so the safety settings are written once:

WorkerReadsWritesGuarantee it shows

analyticsorders.enriched/metrics, /windowsAt-least-once, in-memory windows

Two consumer settings appear in every worker, and they are the base for everything else on this page:

# services/common/shopstream_common.py (excerpt)
def consumer_config(group_id: str, *, read_committed: bool = True) -> dict[str, Any]:
    return {
        **base_config(),
        "group.id": group_id,
        "enable.auto.commit": False,
        "auto.offset.reset": os.getenv("AUTO_OFFSET_RESET", "earliest"),
        "isolation.level": "read_committed" if read_committed else "read_uncommitted",
        "partition.assignment.strategy": "cooperative-sticky",
        "session.timeout.ms": 45000,
        "max.poll.interval.ms": int(os.getenv("MAX_POLL_INTERVAL_MS", "300000")),
    }
  • enable.auto.commit: False: the worker, not a background timer, decides when an offset is saved. The Kafka default is true (every 5 seconds), which can save the offset before your work is done; crash then, and the record is lost.
  • isolation.level: read_committed: skip records written by a transaction that was later aborted. Without this, a reader could see half-done output from a crashed enricher.
  • auto.offset.reset: earliest: a brand new group starts from the oldest record, not the newest. The Kafka default is latest, a classic "my new consumer sees nothing" bug.
