The retry loop, step by step

Click Next or Play to follow one order whose price lookup timed out.

  1. Fail. The enricher reads offset 57 and calls the price lookup. It times out, so Catalog.price() raises TransientError.
  2. Move aside. Inside the same transaction as the batch, the enricher writes the original record to orders.retry with headers: the attempt number, the earliest retry time, the error text and where it came from. Offset 57 is marked done, and offset 58 is processed right away.
  3. Wait without sleeping. The retry-worker reads it. retry-at-ms is in the future, so it seeks back to that record and pauses the partition. It keeps calling poll() every second, so the group coordinator still sees a live member.
  4. Send back. When the time comes it resumes the partition and, in one transaction, produces the record to orders.created (keeping the attempt header) and commits the retry offset.
  5. Try again. The enricher sees the order a second time. The price service is back, so it is enriched normally.
  6. Give up. If it keeps failing, each attempt waits longer. "4 attempts" means 4 retries after the first try, so 5 tries in total: the fifth failure routes it to orders.dlq with "gave up after 4 attempts" in the error header. The whole ladder waits at most 2 + 4 + 8 + 16 = 30 s, about 15 s on average.

The routing decision in the enricher's loop is short. Note the backoff function: exponential backoff with full jitter. The waiting time cap doubles each attempt (2 s, 4 s, 8 s, 16 s; the code has a 60 s ceiling, but with the default MAX_ATTEMPTS=4 it is never reached), and the actual wait is a random number between 0 and that cap, so a thousand orders that failed together do not all come back in the same millisecond and knock the price service over again.

def backoff_ms(attempt: int) -> int:
    """Exponential backoff with full jitter: 2s, 4s, 8s ... capped at 60s."""
    return random.randint(0, min(60000, BASE_BACKOFF_MS * (2 ** (attempt - 1))))

And the heart of the retry-worker: "if it is not time yet, rewind and pause". pause() tells librdkafka to stop fetching that partition while poll() keeps the membership alive.

# services/enricher/retry_worker.py (excerpt)
        msg = consumer.poll(1.0)
        if msg is None or msg.error():
            continue
        hdrs = headers_to_dict(msg.headers())
        retry_at = int(hdrs.get("retry-at-ms", "0"))
        if retry_at > now_ms():
            # Not yet. Rewind to this record and pause the partition until retry_at.
            tp = TopicPartition(msg.topic(), msg.partition(), msg.offset())
            consumer.seek(tp)
            consumer.pause([tp])
            paused[(msg.topic(), msg.partition())] = retry_at
            continue

Small head-of-line blocking on the retry topic. The worker pauses a whole partition for its head record. With full jitter, a record behind the head can be due sooner (attempt 1, under 2 s) but still waits while the head (attempt 4, up to 16 s) keeps the partition paused. At ShopStream's volume that costs a few seconds and nobody notices. At scale, use one topic per delay tier (for example orders.retry.5s, orders.retry.1m, orders.retry.10m) so every record in one topic has the same delay and the head is always the first one due. That is the real reason Uber's retry design uses fixed-delay tiers.

From your world

pause() plus a polling loop is the same trick as NAPI: stop taking new work from one source (mask the interrupt) without going to sleep, and keep the watchdog fed. Exponential backoff with jitter is what Ethernet's CSMA/CD did after a collision: wait a random slot count from a window that doubles each time. Where it breaks: NAPI drains the ring in budgets and then re-enables the interrupt; pause() drains nothing, it only stops fetching, and records already fetched for that partition are thrown away and fetched again after resume().

The ordering trade-off you must say out loud

Orders are keyed by customer_id, so one customer's orders sit in one partition, in order. A retried order leaves that line. If customer C-42 places order A (fails, goes to retry) and then order B (succeeds), B reaches orders.enriched before A. For a shop, that is fine: two orders are independent. For a bank account balance it is not.

When per-key order matters, you park the key instead: when a record for key K fails, remember K, and send every later record for K to the retry path too, until K's oldest record succeeds. The README of the project describes this option; ShopStream does not implement it because shop orders do not need it.

  1. A fails. Order A for customer C-42 hits a transient error and is moved to orders.retry, as before.
  2. Park the key. The enricher adds C-42 to a "parked keys" set. To survive a restart, the set is written to a small compacted topic (key = customer, value = parked or a tombstone), and every instance rebuilds it on start-up from that topic. Memory alone would forget the park after a crash and let B overtake A.
  3. B follows A. Order B for C-42 would succeed, but its key is parked, so it is sent to the retry topic too, behind A. Other customers are not affected.
  4. Unpark. A is retried and succeeds, B goes right after it, and when no record for C-42 is waiting any more the key is removed (tombstone). Order per key is kept; the cost is that one customer's orders all wait for the slowest one.

Say this in interviews: "A retry topic trades per-key ordering for throughput. If ordering per key matters, I park the key: later events for that key also wait until the failed one succeeds."
