Windowed analytics: revenue per minute

The analytics service answers one question: "how much money did we take in each minute?" That sounds easy until you remember three facts about streams: events arrive out of order, some arrive late, and the stream never ends, so you can never say "now I have everything".

Explain like I'm 5

You have a row of jars, one for each minute on the clock. Each coin has the time it was earned stamped on it. You drop each coin in the jar for its minute, even if the coin reaches you a bit late. You cannot wait forever to close a jar, so you follow a rule: "when I see coins stamped 10 seconds after a jar's minute ended, I close that jar and write its total on the board." A coin for a closed jar is too late: you count it as "late" and set it aside.

  • Tumbling window: fixed, non-overlapping buckets. [12:00, 12:01), [12:01, 12:02)... Every event is in exactly one.
  • Event time: the time the thing happened (created_at written by the order-api). Processing time is when our code reads it. They differ by network delay, retries and lag. ShopStream buckets by event time, so a retried order still counts in the minute it was placed.
  • Watermark: the processor's belief "I have probably seen everything up to time T". ShopStream's watermark is simply the largest event time seen so far.
  • Allowed lateness: keep a window open this long after the watermark passes its end (10 seconds here) to catch slightly late events.

The whole windowing engine is one small function:

# services/analytics/analytics.py (excerpt)
def add(order: dict):
    global watermark_ms
    ts = event_time_ms(order)                       # from created_at, not "now"
    start = ts - (ts % WINDOW_MS)                   # which 1-minute bucket
    with lock:
        if start + WINDOW_MS + ALLOWED_LATENESS_MS <= watermark_ms:
            LATE.inc()                              # window already closed
            return
        w = open_windows.setdefault(start, {"revenue": 0, "orders": 0})
        w["revenue"] += order["total_cents"]
        w["orders"] += 1
        REV_TOTAL.inc(order["total_cents"])
        watermark_ms = max(watermark_ms, ts)
        # Close every window the watermark has passed (plus lateness).
        for s in sorted(k for k in open_windows if k + WINDOW_MS + ALLOWED_LATENESS_MS <= watermark_ms):
            done = open_windows.pop(s)
            ...
            log.info("WINDOW %s orders=%d revenue=INR %.2f", row["window"], done["orders"], done["revenue"] / 100)

The numbers are random each run, because the load generator picks random products. The shape is what matters: about 60 seconds times your requests per second orders per closed window.

Estimation exercise: the load generator picks 1 to 3 items (mean 2), quantity 1 to 3 (mean 2), from an 8-product catalog whose mean price is about INR 974. So one order is worth about 2 x 2 x 974 = INR 3,896 on average, and 1,197 orders should be about INR 4.66 million. If your window is far off that, something is being dropped or double-counted.

Where the toy version stops

ShopStream's analytics keeps its windows in a Python dict. The code's own comment admits the cost: committing offsets while state lives only in memory means a crash loses open windows. Real stream processors solve this with state stores backed by a changelog:

  • Kafka Streams (a Java library inside your app) keeps state in a local RocksDB store and writes every change to a compacted changelog topic. A restarted instance replays the changelog to rebuild its state. With processing.guarantee=exactly_once_v2, state updates, outputs and offsets commit together. Windows have a grace period for late data, like our allowed lateness.
  • Apache Flink (a separate cluster) takes periodic checkpoints of all operator state using barriers that flow through the stream, and its watermarks are generated per source partition, so one slow partition holds the watermark back instead of letting its events be called late.

That last point exposes a real bug class in hand-written processors like ours: ShopStream's watermark is one global "max timestamp seen", taken across all partitions it reads. If one partition is behind (say a hot partition with lots of lag), its events will look late once the other partitions push the watermark ahead. A per-partition watermark (the minimum across partitions) fixes that. It is a good thing to mention in an interview to show you understand why frameworks exist.
