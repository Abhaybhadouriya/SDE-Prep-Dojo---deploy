Interview questions

A consumer gets a message it cannot process. What do you do?

First I decide whether the failure is about the message or about the world. If the message is malformed (bad JSON, missing field, unknown product), retrying cannot help, so I publish the original bytes to a dead-letter topic with headers for the error, the source topic/partition/offset and a timestamp, and move on. If it is a dependency problem (timeout, DB restarting), I publish it to a retry topic with an attempt counter and a "not before" time using exponential backoff with jitter; a retry worker sends it back when the time comes, and after N attempts it goes to the DLQ too. The key point is never to block the partition: in-place retries cause head-of-line blocking and, past max.poll.interval.ms, a rebalance. Then I alert on DLQ growth and have a redrive tool, and I make sure the sink is idempotent so redriven records cannot duplicate.

How to answer

Classify (poison vs transient), route (DLQ vs retry topic), protect the partition (no blocking), then operate (alert, retention, redrive). Mention the ordering trade-off before they ask.

Likely follow-ups
  • What if per-key ordering matters? (Park the key: later records of that key also wait.)
  • How do you implement a delay in Kafka, which has no delayed delivery? (Header with retry time, pause the partition until then; or several retry topics with fixed delays like Uber.)
  • How big can the DLQ get before you worry? (Any growth is an alert; a sudden flood means a bug or bad deploy upstream.)
How does Kafka achieve exactly-once in a read-process-write loop, and where does it stop?

The processor uses a transactional producer with a stable transactional.id. For each batch it begins a transaction, produces the outputs, and calls sendOffsetsToTransaction so the input offsets, which are just writes to __consumer_offsets, join the same transaction. Commit makes the transaction coordinator write commit markers to every partition involved, so outputs and offsets appear together. Readers use read_committed and only read up to the last stable offset, skipping aborted data. A crash before commit means abort, nothing visible, re-read. Zombies are fenced by the epoch: a new instance with the same id bumps it, and the old one gets ProducerFenced. It stops at Kafka's edge: a DB write or an email inside the loop is not rolled back, so for those I use idempotent writes or the outbox pattern.

How to answer

Start with the insight "an offset commit is just a Kafka write", then the four calls (begin, produce, send offsets, commit), then readers (read_committed), then zombies (epoch), then the boundary. That order shows you understand it rather than memorised it.

Likely follow-ups
  • What is the cost? (Extra round trips per transaction and commit-marker writes; latency for read_committed consumers equals the transaction length. Bigger batches amortise it.)
  • What is the LSO? (Last stable offset: the first offset of the oldest still-open transaction; read_committed consumers stop there.)
  • What happens if the producer hangs mid-transaction? (The coordinator aborts it after transaction.timeout.ms.)
How do you avoid duplicates when writing from Kafka to a database?

Accept at-least-once delivery and make the write idempotent. I commit Kafka offsets only after the database transaction commits, so I never lose a record; the price is that a crash between the two replays a batch. To make the replay harmless I write with an upsert on a natural unique key, such as INSERT ... ON CONFLICT (order_id) DO UPDATE. In our pipeline there is also a guard WHERE orders.kafka_offset <= EXCLUDED.kafka_offset, so an older copy never overwrites a newer one. If there is no natural key, I use an idempotency key from the producer, or store the last applied partition and offset in the same DB transaction and skip anything at or below it.

How to answer

Give the formula "at-least-once + idempotent = effectively-once", show the order of commits, show the SQL, then give the fallback when no natural key exists.

Likely follow-ups
  • What about writes that are not idempotent, like incrementing a counter? (Store processed offsets or event ids in the same DB transaction, or convert to "set" semantics.)
  • Could you use Kafka Connect instead? (Yes, the JDBC sink connector supports upsert mode and has its own DLQ settings.)
Explain event time, processing time and watermarks. How does a stream processor decide a window is done?

Event time is when something happened, written into the event by its source. Processing time is when my code sees it. They drift apart because of network delay, retries, lag and replays. If I bucket by processing time, a lag spike dumps an hour of orders into the current minute, so for business metrics I use event time. But in event time I never know that a window is complete, so the processor tracks a watermark: an estimate that all events up to time T have arrived. A window closes when the watermark passes its end plus an allowed lateness or grace period. Events for already-closed windows are late: I can drop and count them, send them to a side output, or emit a correction. Frameworks compute the watermark per input partition and take the minimum, so one slow partition does not make everyone else's events look late.

How to answer

Use a clock example: "an order placed at 12:00:59 that arrives at 12:01:05". Then define watermark and lateness, then name the three choices for late data. Finish with the latency vs completeness trade-off: a longer grace period means later but more correct results.

Likely follow-ups
  • Where is the window state stored so a crash does not lose it? (Kafka Streams: RocksDB plus changelog topic; Flink: checkpoints.)
  • Tumbling vs hopping vs session: when do you use each?
What is a zombie instance and how does Kafka fence it?

A zombie is a process that the rest of the system believes is dead but is still running, for example after a long GC pause, a network partition, or a Kubernetes pod that was replaced while the old one was frozen. If it keeps writing, you get duplicates or conflicting results. Kafka fences zombies with the transactional.id and an epoch. When the replacement calls initTransactions with the same id, the coordinator increments the epoch and aborts any open transaction from the old epoch. Any later write or commit with the old epoch is rejected with a fatal fenced error. On the consumer side, passing the group metadata with the offsets lets the broker reject commits from a member of an old group generation. In our enricher, the id is enricher-<pod name>, and the fenced error makes the process exit so Kubernetes can restart it cleanly.

How to answer

Define it with a concrete cause, then the mechanism (same id, higher epoch wins), then the operational rule (stable per-instance id, exit on fatal errors).

Likely follow-ups
  • Is this like a lease or fencing token in distributed locks? (Yes, the same idea: a monotonically increasing token checked by the storage layer.)
  • What happens if two replicas share one id? (They fence each other in a loop.)
When would you use Kafka Streams or Flink instead of a hand-written consumer like ShopStream's?

A hand-written consumer is fine for stateless, per-record work like validation and enrichment, which is what our enricher does. As soon as I need state that must survive restarts, joins between streams, windows with late data, or exactly-once state updates, I would use a framework. Kafka Streams is a library inside my service: no extra cluster, state in RocksDB backed by changelog topics, exactly_once_v2, and it scales by partitions like any consumer. Flink is a separate cluster with checkpointing, per-partition watermarks and SQL, better for large shared stateful jobs. Rule of thumb: Kafka Streams for app-embedded processing, Flink for big platform pipelines.

How to answer

Draw the line at state. Name what the framework gives you (state store, changelog, checkpoint, watermarks), then the deployment difference (library vs cluster).

Likely follow-ups
  • How does Kafka Streams rebuild state after a crash?
  • What is a repartition topic and why does it appear when you change the key?

Scenario: the price service went down for 10 minutes and the DLQ has 40,000 orders

On Monday morning the on-call engineer sees 40,000 records in orders.dlq, all with error "catalog db unavailable". Customers are asking where their orders are.

Weak answer: "Delete the DLQ and ask customers to re-order." Or: "Make MAX_ATTEMPTS a million."

Strong answer: First, these are transient failures that exhausted their retries, so the data is good and can be redriven. Confirm the catalog is healthy, then re-publish the DLQ records to orders.created (rate limited, so we do not overload the catalog again). The sink upserts on order_id, so any order that partly succeeded will not duplicate. Then fix the root cause: the retry budget (4 retries with caps of 2/4/8/16 s and full jitter) covers at most about 30 s, about 15 s on average, so even a short database restart exhausts it. Options: a longer backoff ladder for this error type, a circuit breaker that pauses consumption while the dependency is down (lag grows instead of DLQ), and an alert on the retry rate, not only on the DLQ.

Likely follow-ups
  • How do you avoid reordering during redrive? (Redrive per key in offset order, or accept it if orders are independent.)
  • Why might pausing consumption be better than retrying? (Lag is cheap and self-healing; DLQ needs a human.)

60-second answer: "Walk me through how your pipeline handles failures."
"Each stage classifies failures. Poison records, like bad JSON or an unknown product, go to a dead-letter topic with the error and the source offset in headers, so the partition never blocks. Transient failures, like a timeout, go to a retry topic with an attempt count and a backoff time; a retry worker pauses the partition until it is due and sends it back, and after four attempts it goes to the DLQ. The enricher does all of this inside a Kafka transaction with the input offsets, so it is exactly-once within Kafka. The database sink commits offsets after the DB commit and upserts on order_id, so duplicates are harmless. We alert on lag, retry rate and DLQ growth, and we can redrive from the DLQ or replay from the topic because Kafka keeps 7 days."
