Quick quiz

The enricher sees an order for product "P-NOPE", which is not in the catalog. Where should it go?

  1. orders.retry, with backoff
  2. Retry in place three times, then skip
  3. orders.dlq, because retrying can never fix it
  4. orders.enriched with a total of 0
An unknown product is the record's fault, not the world's. Retrying wastes capacity; the DLQ keeps it for a human with the error header.

Why does the retry-worker call pause() instead of time.sleep() until the retry time?

  1. Sleep uses more CPU
  2. Sleeping stops poll(); past max.poll.interval.ms the consumer is thrown out of the group and a rebalance starts
  3. Kafka forbids sleep in consumers
  4. pause() deletes the record
pause() stops fetching that partition while the loop keeps polling, so the member stays alive and other partitions keep moving.

In the enricher's transaction, why are input offsets sent with send_offsets_to_transaction instead of consumer.commit()?

  1. So outputs and the offset commit become visible together or not at all
  2. Because commit() is slower
  3. Because read_committed requires it
  4. To skip the transaction coordinator
Committing separately reopens the gap between "output written" and "offset saved", which is exactly where duplicates or loss come from.

The postgres-sink crashes after the DB commit but before consumer.commit(). What happens on restart?

  1. The rows are lost
  2. The rows are inserted twice
  3. Kafka rolls back the database
  4. The batch is re-read and the upsert rewrites the same rows: no duplicates
At-least-once delivery replays the batch; ON CONFLICT (order_id) DO UPDATE makes the replay harmless.

A new enricher pod starts with the same transactional.id as an old frozen pod. The old pod wakes and tries to commit. What happens?

  1. Both commits succeed
  2. The broker rejects the old pod with a fenced error, because the epoch was bumped
  3. The new pod is fenced instead
  4. The coordinator merges both transactions
init_transactions() bumps the epoch for that id; writes with the older epoch are rejected. That is zombie fencing.

An order created at 12:00:58 reaches analytics at 12:01:40, and the watermark is already 12:01:30. Window size 1 minute, allowed lateness 10 s. What happens?

  1. It is added to the 12:01-12:02 window
  2. It is added to the 12:00-12:01 window
  3. It is counted as late and dropped, because that window closed at watermark 12:01:10
  4. The window re-opens
Windows are chosen by event time (12:00 window), but that window closed once the watermark passed 12:01 + 10 s.

Which statement about Kafka exactly-once is true?

  1. It covers Kafka-to-Kafka processing; database writes and emails need idempotency
  2. It covers every system the consumer talks to
  3. It works with read_uncommitted consumers
  4. It removes the need for unique keys in the sink
Transactions only cover Kafka partitions (including __consumer_offsets). Side effects outside Kafka are not rolled back.
