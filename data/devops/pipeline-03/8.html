The guarantee at every hop

Interviewers often ask "is your pipeline exactly-once?". The honest answer is per hop. This table is from the project README:

HopGuaranteeWhy
client to order-apiat-least-once if the client retriesresend with the same order_id is safe: the sink upserts
order-api to Kafkano loss, no duplicates from producer retriesidempotent producer + acks=all + min.insync.replicas=2
orders.created to enricher to enriched/retry/dlqexactly-onceKafka transactions: outputs + input offsets commit atomically
orders.enriched to Postgreseffectively-onceat-least-once delivery + upsert on order_id primary key
orders.enriched to analyticsat-most-once for open windows; duplicates from upstream re-drives are counted twiceoffsets are committed while window state lives only in memory, so a crash loses open windows and they are never re-read (a real system checkpoints state with offsets: Kafka Streams / Flink state stores)

You might confuse this with: "exactly-once delivery" (the network delivering a message exactly once, which is impossible in general) versus "exactly-once processing / effect" (the visible result is as if each message were processed once). Kafka and every honest system promise the second one, built from retries plus de-duplication.
