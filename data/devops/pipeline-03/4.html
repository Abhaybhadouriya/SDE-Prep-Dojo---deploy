The dead-letter topic: a quarantine with labels

A DLQ is only useful if a person can answer three questions from it: what was the record, why did it fail, and where did it come from. ShopStream keeps the original key and value untouched and adds headers (small key-value labels Kafka stores next to each record): error, origin (topic/partition/offset) and failed-at-ms.

Try it with the drill script. It writes three bad records straight into orders.created, sends one good order, and reads the DLQ:

bash scripts/chaos/03-poison-message.sh
# PowerShell: .\scripts\chaos\03-poison-message.ps1
==> Writing 3 bad records straight into orders.created

==> A good order still works
{"order_id":"7c0e...","status":"ACCEPTED","partition":4,"offset":112}

==> Reading the DLQ (with headers)
error:not valid JSON: Expecting value: line 1 column 1 (char 0),origin:orders.created/2/88,failed-at-ms:1795...	C-POISON	this is not json
error:missing field items,origin:orders.created/2/89,failed-at-ms:1795...	C-POISON	{"order_id":"bad-1","customer_id":"C-POISON"}
error:unknown product P-NOPE,origin:orders.created/2/90,failed-at-ms:1795...	C-POISON	{"order_id":"bad-2","customer_id":"C-POISON","items":[{"product_id":"P-NOPE","quantity":1}]}
Processed a total of 3 messages

Your partition and offset numbers will differ, but notice two things. All three bad records went to the same partition, because they share the key C-POISON. And the good order was accepted and processed: the enricher did not get stuck. The enricher log shows the same story:

$ docker compose logs enricher | grep poison
... WARNING enricher poison -> DLQ: not valid JSON: Expecting value: line 1 column 1 (char 0) (orders.created/2/88)
... WARNING enricher poison -> DLQ: missing field items (orders.created/2/89)
... WARNING enricher poison -> DLQ: unknown product P-NOPE (orders.created/2/90)

What happens to DLQ records next?

  1. Alert. Prometheus has a rule DLQReceivingMessages that fires when the DLQ's end offset is growing. A DLQ nobody watches is a silent data-loss bin.
  2. Triage. Group by the error header. One kind of error in thousands of records usually means one bug or one bad deploy upstream.
  3. Fix the cause. Add the missing product to the catalog, fix the producer that writes bad JSON, and so on.
  4. Redrive. Re-publish the fixed records to the start of the pipeline (here orders.created). Because the sink is idempotent on order_id, a record that somehow got through earlier is not duplicated.

Uber's engineering blog describes the same layered idea at large scale: a failed message goes to retry topic 1, then retry topic 2 with longer delays, then a DLQ, and DLQ messages can be merged back into the first retry topic once fixed. Kafka 4.4 also added DLQ support for the new share groups (KIP-1191), which shows how common this pattern is.

Tip: give the DLQ a longer retention than the main topic (ShopStream: 14 days vs 7) so a long weekend does not delete evidence. And never let the DLQ writer itself fail silently: in ShopStream the DLQ write is inside the same transaction, so if it fails, the whole batch is retried.
