Five boxes. Config is data stored in the API like everything else; the protection is RBAC, encryption at rest and node scoping.

ConfigMap vs Secret - and are Kubernetes Secrets secure?

Both inject configuration into pods as env vars or files, both limited to 1 MiB. ConfigMaps are for non-sensitive settings; Secrets for credentials and keys. Out of the box, Secrets are only base64-encoded, not encrypted: anyone with get secrets in the namespace, anyone who can create pods there, or anyone with etcd access can read them. To make them reasonably secure: least-privilege RBAC, encryption at rest with a KMS provider, mounting as files rather than env vars, and often an external manager (Vault, AWS Secrets Manager, Azure Key Vault) synced with External Secrets Operator or the CSI driver - or workload identity so there is no static secret at all.

How to answer

Answer the trap directly - "base64 is encoding, not encryption" - then list the layers in order: who can read (RBAC), what is stored (encryption at rest), where it lives (external store), and avoiding secrets entirely (workload identity).

Likely follow-ups
  • How does envelope encryption work? (DEK per object, wrapped by a KEK in the KMS.)
  • Why is "create pod" permission dangerous? (It can mount any Secret in the namespace.)
You updated a ConfigMap but the app still uses the old value. Why, and how do you roll config out properly?

If it is consumed as an env var, the value was copied at container start and never changes. If it is a volume, the kubelet updates the files on a later sync (not instantly), unless the mount uses subPath, which never updates - and the app may only read the file at startup anyway. The proper approach is to make config changes part of a rollout: generate a new ConfigMap name per version (Kustomize hash suffix) or put a checksum of the config in the pod template annotations (Helm pattern). Then a config change is a normal rolling update with readiness gates and kubectl rollout undo.

How to answer

Diagnose by consumption method first (env, volume, subPath, app caching), then give the "config as a deploy" fix.

Likely follow-ups
  • What does immutable: true buy you? (Safety plus less kubelet/API load.)
  • How would you hot-reload safely? (Watch the directory, validate, swap atomically, expose a config version metric.)
How should a pod access cloud resources such as S3 or Key Vault?

Not with static access keys in a Secret. Use workload identity: the pod runs as a ServiceAccount; the cluster issues it a short-lived, audience-bound token; the cloud trusts that token through federation and exchanges it for short-lived credentials scoped to an IAM role (EKS Pod Identity or IRSA, Azure Workload Identity, GKE Workload Identity). Nothing long-lived to leak or rotate; access is per workload and auditable.

How to answer

Say what you avoid (static keys), the mechanism in one sentence (federated short-lived token), and the benefits (no rotation, least privilege, audit).

Likely follow-ups
  • What if the app needs a database password? (Store it in a secret manager, sync with ESO, or use dynamic credentials from Vault.)
How do you manage secrets in a GitOps workflow where everything lives in git?

Never commit plain Secret manifests. Two good options: commit only a reference - an ExternalSecret object that says which key to fetch from Vault or a cloud secret manager - and let External Secrets Operator create the Secret in-cluster; or commit an encrypted form (Sealed Secrets or SOPS with a KMS key) that only the cluster or the CD tool can decrypt. I prefer references, because rotation happens in one central store and git never holds ciphertext of real secrets.

How to answer

Name both patterns, pick one with a reason, mention rotation.

Likely follow-ups
  • A secret was committed by mistake. What now? (Rotate it immediately; rewriting history is not enough.)
A pod is stuck in CreateContainerConfigError. What is going on?

The kubelet could not build the container's configuration, almost always because a referenced ConfigMap or Secret, or a key inside it, does not exist in the pod's namespace. kubectl describe pod shows the exact missing name. Fix the reference or create the object; mark it optional only if the app can run without it.

How to answer

Name the cause, the command that proves it, and the fix - in that order.

Likely follow-ups
  • How does that differ from CrashLoopBackOff? (There the container starts and then exits.)

Scenario: database password must be rotated today

Security says the production database password was exposed in a log file. 60 pods use it through a Secret mounted as an env var. You must rotate with no downtime.

Weak answer: "Change the password in the database and in the Secret, then restart everything." (Pods fail between the two steps, and a big-bang restart risks an outage.)

Strong answer: "First stop the leak (fix the logging, scrub log storage). Then rotate in an expand-contract way: create a second valid credential in the database, update the Secret to the new one, do a rolling restart (env vars only change on restart) and watch error rates, then revoke the old credential once all pods use the new one. Afterwards: move the secret to files or to dynamic credentials from Vault, and add a log scrubber so it cannot happen again."

Likely follow-ups
  • The database supports only one password per user? (Create a second user, switch, delete the first.)

60-second answer - "How do you handle configuration and secrets on Kubernetes?"
"I keep the image identical across environments and inject settings with ConfigMaps and credentials with Secrets, preferably mounted as files. Env vars are fixed at start; mounted files update eventually, so I version config and roll it out like code, with a checksum annotation or versioned names. Secrets are only base64 in the API, so I lock them down: least-privilege RBAC, encryption at rest with a KMS provider, and the real values in a secret manager such as Vault or AWS Secrets Manager, synced by External Secrets Operator. Where possible I avoid secrets entirely with workload identity, so pods get short-lived cloud credentials instead of keys."
