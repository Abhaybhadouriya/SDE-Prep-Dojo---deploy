External secret managers and GitOps

Good to know (SDE-2)

Many companies keep the real secrets in a dedicated store (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, Google Secret Manager) and treat Kubernetes as a consumer. Three common patterns:

PatternHow it worksGoodWatch out
External Secrets OperatorController syncs values from the store into K8s Secrets on a refresh intervalApps stay unchanged (they read normal Secrets); central rotationThe value still exists as a K8s Secret, so encryption at rest and RBAC still matter
Secrets Store CSI DriverA CSI volume fetches the secret at pod start and mounts it as filesCan avoid a K8s Secret object entirelyPod start depends on the external store being up
Vault Agent sidecar / injectorA sidecar authenticates to Vault and renders secrets into a shared volumeDynamic, short-lived credentials (e.g. per-pod DB users)Extra container per pod; Vault becomes critical infrastructure
Sealed Secrets / SOPSEncrypt the Secret YAML so it can be committed to git; decrypted in-cluster or by the CD toolPure GitOps: everything in gitKey management for the decryption key; rotation is manual

Even better than storing a cloud password is not having one: with workload identity (EKS Pod Identity / IRSA, Azure Workload Identity, GKE Workload Identity) the pod's ServiceAccount is exchanged for short-lived cloud credentials, so there is no static key to leak. This is how a Kafka consumer in your pipeline on Kubernetes should reach cloud storage.
