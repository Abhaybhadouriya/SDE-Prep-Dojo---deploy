Protecting Secrets: four layers

Good to know (SDE-2)

Here is the full path of a Secret, and where each protection sits.

  1. RBAC least privilege. Very few people and service accounts should have get/list/watch on secrets. Remember that list returns the values too, and that permission to create pods in a namespace is effectively permission to read its Secrets. Details on Security & RBAC.
  2. Encryption at rest. By default, Secret data sits in etcd unencrypted (just base64). Configure the API server with an EncryptionConfiguration, ideally the KMS v2 provider: the API server encrypts each object with a data key (DEK), and the DEK itself is encrypted by a key-encryption key (KEK) held in a cloud KMS or HSM. Managed clusters (EKS, AKS, GKE) offer this as a setting.
  3. Node scoping. The Node authorizer and NodeRestriction admission plugin limit each kubelet to Secrets of pods scheduled on that node, so one compromised node does not leak everything.
  4. In the pod. Secret volumes are tmpfs; mount read-only with tight defaultMode; set automountServiceAccountToken: false when the pod does not call the API.
# /etc/kubernetes/encryption-config.yaml, passed to kube-apiserver with
#   --encryption-provider-config=/etc/kubernetes/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: ["secrets"]
  providers:
  - kms:
      apiVersion: v2
      name: cloud-kms
      endpoint: unix:///var/run/kms-plugin/socket.sock   # local KMS plugin talks to the real KMS
  - identity: {}          # fallback: lets the server still read old, unencrypted data

Here is the moment that makes it real. First, before encryption at rest is enabled. Anyone with get on the Secret, and anyone who can read etcd or an etcd backup, sees the value:

# through the API: base64 is only an encoding
$ kubectl get secret db-cred -n shop -o jsonpath='{.data.password}'
UzNjcjN0IQ==
$ kubectl get secret db-cred -n shop -o jsonpath='{.data.password}' | base64 -d
S3cr3t!

# straight from etcd (on a control-plane node, default kubeadm setup = no encryption)
$ ETCDCTL_API=3 etcdctl get /registry/secrets/shop/db-cred | strings | grep -A1 password
password
S3cr3t!

Then after the EncryptionConfiguration above is in place and the API server has been restarted:

# after enabling, rewrite existing Secrets so they get encrypted
$ kubectl get secrets -A -o json | kubectl replace -f -

# proof, on a control-plane node: the value in etcd is now ciphertext
$ ETCDCTL_API=3 etcdctl get /registry/secrets/shop/db-cred | hexdump -C | head -2
00000000  2f 72 65 67 69 73 74 72  79 2f 73 65 63 72 65 74  |/registry/secret|
00000010  73 2f 73 68 6f 70 2f 64  62 2d 63 72 65 64 0a 6b  |s/shop/db-cred.k|
# the next bytes begin with a "k8s:enc:kms:v2:" prefix followed by unreadable bytes

# but the API still decrypts for anyone RBAC allows
$ kubectl get secret db-cred -n shop -o jsonpath='{.data.password}' | base64 -d
S3cr3t!

So "is a Secret encrypted?" has three answers, one per place the Secret lives:

Where the Secret isEncrypted by default?What protects it
At rest (etcd files, etcd backups)No. Plain base64 unless you set an EncryptionConfiguration (many managed clusters turn on envelope encryption for you; check yours)KMS v2 envelope encryption, encrypted disks, guarded backups
In transit (kubectl or kubelet to API server, API server to etcd)Yes. All of these connections use TLSTLS with client certificates or tokens
On the node (inside the pod)No. It is plain text, but on a tmpfs (RAM) volume that is never written to the node's diskFile mode (defaultMode: 0400), node authorizer (a kubelet only gets Secrets for its own pods), not using env vars

From your world

Envelope encryption is the same key hierarchy you see in secure boot or MACsec key management: a long-lived master key (KEK) that never leaves the HSM wraps short-lived data keys (DEKs) that do the bulk encryption. Rotating the master key does not mean re-encrypting everything at once. Where it breaks: encryption at rest protects etcd files and backups, not the API - anyone allowed to get the Secret through the API still sees the plain value.
