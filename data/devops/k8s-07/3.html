When does a change reach the running pod?

Good to know (SDE-2)

This is the question that bites everyone in production. You edit a ConfigMap. What happens?

How it is consumedDoes the pod see the change?When
Environment variable (env, envFrom)NoOnly when the container is (re)started
Volume mount (whole ConfigMap or items)Yes, eventuallyOn a later kubelet sync, typically within a minute or so (sync period plus cache delay); not instant
Volume with subPathNeversubPath mounts are a one-time copy
immutable: trueCannot change at allCreate a new object (e.g. shop-config-v2) and point pods at it

And even when the file changes, your app must notice. Many apps read config once at startup. So the usual pattern is: treat a config change like a deploy - trigger a rolling restart so the change is gradual, observable and reversible.

  1. You change it. kubectl apply sends the new ConfigMap to the API server, which validates it and stores it in etcd. Running pods do not know yet.
  2. The kubelet notices. Each kubelet periodically resyncs the pods on its node and checks whether mounted ConfigMaps/Secrets are fresh (by watch or a cached GET, depending on configuration). This is why there is a delay.
  3. Write the new version beside the old. The kubelet writes all keys into a new timestamped directory inside the volume.
  4. Atomic swap. It repoints the ..data symlink to the new directory with an atomic rename, then deletes the old directory. A reader never sees half-old, half-new files.
  5. Your app's turn. The files are new, but the process may still hold the old values in memory. Either watch the file (inotify) and reload, or do kubectl rollout restart. Env vars never change without a restart.

From your world

The ..data trick is the classic Unix atomic-update pattern: write to a temp location, then rename(2) a symlink over the old one, because rename is atomic within a filesystem. Reloading on change is like sending a daemon SIGHUP after editing its config. Where it breaks: if your app watches the file itself with inotify, watch the directory, because the file you opened is replaced through a symlink, not modified in place.

Making config changes roll out safely

# simplest: restart pods with a rolling update after changing config
kubectl rollout restart deployment/shop-api -n shop

# Helm / Kustomize pattern: put a hash of the config in the pod template,
# so any config change changes the template and triggers a normal rollout
#   annotations:
#     checksum/config: 3f2a9c...   (Helm: sha256sum of the rendered ConfigMap)
# Kustomize's configMapGenerator does the same by adding a hash suffix to the name.
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config-v7          # new name per version
immutable: true                 # cannot be edited; kubelet stops watching it (less API load)
data:
  LOG_LEVEL: "info"

Interviewers love this: "Env vars are read once at container start; mounted files update eventually except with subPath; and in either case I treat config as part of the release - versioned names or a checksum annotation, so a config change is a rolling update I can watch and roll back."
