OverlayFS: the see-through stickers (where files come from)

Explain like I'm 5

You have a picture book you are not allowed to draw in. So you lay a clean sheet of tracing paper on top and draw on that. When you look down, you see the book and your drawing together. If you want to "erase" a tree in the book, you paint a white blob over it on your tracing paper. Throw away the tracing paper and the book is like new.

An image is a stack of read-only layers (the book). A running container adds one thin writable layer on top (the tracing paper). OverlayFS, a union filesystem built into the Linux kernel, glues them into one view. It has four parts:

  • lowerdir: one or more read-only folders, the image layers. Docker's overlay2 driver supports up to 128 of them.
  • upperdir: the writable folder for this container.
  • workdir: an empty scratch folder the kernel needs on the same filesystem as upperdir, to make copy-up atomic.
  • merged: the mount point the container sees as /.
  1. Read. The container opens /app.py. OverlayFS looks top-down: not in upperdir, found in layer 2. It reads it straight from there. No copy. Many containers reading the same file share it in the page cache.
  2. Copy-up. The container writes to config.ini, which lives in read-only layer 1. On the first write OverlayFS copies the whole file into upperdir, then changes the copy. Later reads find the copy first.
  3. Whiteout. The container deletes big.log. The file in layer 1 cannot be touched, so OverlayFS creates a whiteout (a character device with number 0/0) in upperdir that hides it. Disk space is not freed.
  4. Remove. docker rm throws away upperdir. The image layers stay, ready for the next container. That is why writes are lost unless you used a volume.

Deep dive: Labs 8 and 9 are for SDE-2, platform and infra roles. For SDE-1 it is enough to explain lower, upper, work and merged in words. Linux root shell needed (see the note above Lab 1).

Lab 8: mount an overlay by hand

$ mkdir -p /tmp/ov/{lower,upper,work,merged}
$ echo "from the image" > /tmp/ov/lower/a.txt
$ echo "delete me"      > /tmp/ov/lower/b.txt
$ sudo mount -t overlay overlay \
    -o lowerdir=/tmp/ov/lower,upperdir=/tmp/ov/upper,workdir=/tmp/ov/work /tmp/ov/merged
$ ls /tmp/ov/merged
a.txt  b.txt
$ echo "changed" | sudo tee /tmp/ov/merged/a.txt
$ sudo rm /tmp/ov/merged/b.txt
$ cat /tmp/ov/lower/a.txt
from the image
$ sudo ls -l /tmp/ov/upper
-rw-r--r-- 1 root root    8 Nov 23 10:40 a.txt
c--------- 2 root root 0, 0 Nov 23 10:40 b.txt

The lower folder never changed. a.txt was copied up and edited. b.txt in upper is a whiteout: a character device numbered 0, 0 (the link count you see may differ by kernel version). Real Docker does the same, just with many lower folders. You can see the real paths for a container that uses the classic overlay2 store:

$ docker inspect --format '{{json .GraphDriver.Data}}' web | python3 -m json.tool
{
    "LowerDir": "/var/lib/docker/overlay2/9b1e...-init/diff:/var/lib/docker/overlay2/c41f.../diff:...",
    "MergedDir": "/var/lib/docker/overlay2/9b1e.../merged",
    "UpperDir": "/var/lib/docker/overlay2/9b1e.../diff",
    "WorkDir": "/var/lib/docker/overlay2/9b1e.../work"
}

Version note (late 2026): fresh installs of Docker Engine 29 use the containerd image store by default, so layers are managed by containerd's overlayfs snapshotter instead of the classic overlay2 graph driver, and the paths above live under containerd's folders. The kernel mechanism is identical. mount | grep overlay shows the real lowerdir/upperdir either way.

From your world

This is the read-only firmware image plus writable overlay partition design. OpenWrt does literally this: a squashfs root (lower) with a jffs2 overlay (upper). Factory reset = wipe the upper. And an image digest (sha256:...) is a firmware checksum you verify before flashing, while a tag like :1.30 is a movable symlink. Where it breaks: OverlayFS copies whole files, not blocks; a 2 GB database file touched once is copied once in full.
