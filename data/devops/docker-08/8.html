Common mistakes and gotchas

  1. "A container is a lightweight VM." No kernel is booted. There is no hypervisor. Say "a process with namespaces and cgroups" and you will sound like you understand it.
  2. Forgetting --fork with unshare --pid. The caller does not move into the new PID namespace; only its children do. Without --fork you get errors like "fork: Cannot allocate memory" after the first child exits.
  3. Assuming CPU limits kill. Only memory limits kill. CPU limits throttle, which shows up as latency, not crashes. Check cpu.stat.
  4. Reading host memory inside the container. free and /proc/meminfo show the host's RAM, not your limit (unless a helper like LXCFS is installed). Read /sys/fs/cgroup/memory.max.
  5. Writing heavy data into the container layer. Copy-up copies whole files, and the layer vanishes with the container. Databases and logs belong on volumes.
  6. Thinking rm in a later layer shrinks the image. It only adds a whiteout. Delete in the same RUN step or use a multi-stage build.
  7. Using --privileged "to make it work". It gives all capabilities, all devices, and turns off seccomp and AppArmor. It is root on the host with extra steps.
  8. Mixing up the three kinds of "namespace". Linux namespaces (kernel isolation), containerd namespaces (labels like moby), Kubernetes namespaces (API object scoping). Only the first is about isolation.
  9. Trusting old cgroup v1 blog posts. Files like memory.limit_in_bytes and cpu.cfs_quota_us are v1 names. On v2 use memory.max and cpu.max.
