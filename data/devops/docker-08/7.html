How strong is the wall? Container vs gVisor vs microVM vs VM

Deep dive: gVisor, Kata and Firecracker are for SDE-2, platform and security roles. For SDE-1, know one sentence: "containers share the host kernel, so for untrusted code you add a sandbox kernel (gVisor) or a microVM (Firecracker)".

Because every container shares one kernel, the kernel's whole system call interface is the attack surface. When you run code you do not trust (customers' code, an online judge, a notebook service), teams move along a spectrum:

OptionHow it isolatesStart time (typical)Used by
Plain processUIDs and file permissions onlyinstanteverything
Container (runc)Namespaces + cgroups + caps + seccomp + LSM, shared kerneltens to hundreds of msmost Docker and Kubernetes workloads
gVisor (runsc)A user-space kernel written in Go intercepts syscalls; the host kernel sees far fewersub-secondGoogle Cloud Run, GKE Sandbox
microVM (Firecracker, Kata)Hardware virtualization (KVM) with a tiny guest kernel per workloadwell under a second; Firecracker VMM overhead is at most 5 MiB per its specAWS Lambda and Fargate, Fly.io
Full VMOwn kernel and virtual hardware on a hypervisorseconds to tens of secondscloud instances

All of these can run the same OCI image, because the runtime spec is the contract. Netflix shared a useful lesson in 2026: even with tuned cgroups and traffic shaping, a container flooding small packets could still hurt neighbours on the same host, so for sensitive workloads they moved to one task per right-sized EC2 instance. Containers isolate what you can see far better than what you can disturb: shared NIC queues, the last-level CPU cache and kernel locks are not divided by cgroups. Keep this in mind for the Online Judge design.
