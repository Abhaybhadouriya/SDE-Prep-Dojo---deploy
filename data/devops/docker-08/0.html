The story: one building, many flats

Explain like I'm 5

Remember the building of flats from page 01? Every family had its own front door, but all the flats shared one foundation, one set of water pipes and one electricity line. On this page we stop admiring the building and open the walls to see how it is actually built.

Behind the plaster, the building manager has two jobs. First, she puts up walls so nobody can peek into another flat (that is hiding). Second, she puts a meter on every flat so one family cannot use all the hot water (that is sharing fairly). If a family tries to use far more electricity than their meter allows, she switches their power off.

A container is a flat. The building is your computer. The foundation and pipes are the Linux kernel. The walls are called namespaces. The meters are called cgroups. And the furniture each family brings is the container's own files, stacked like see-through stickers with OverlayFS.

On the earlier pages you used Docker like a magic box: you typed docker run and a "container" appeared. This page opens the box. The surprise is that there is no single thing called "a container" inside the Linux kernel. There is no container_create() system call. A container is a normal Linux process that the kernel has been asked to treat in a special way, using a handful of features that existed long before Docker.

Those features are:

  1. Namespaces decide what the process can see: its own process list, its own network cards, its own hostname, its own mount table.
  2. cgroups (control groups) decide how much the process can use: memory, CPU time, number of processes, disk bandwidth.
  3. A root filesystem, usually built from image layers with OverlayFS, decides what files it finds at /.
  4. Security filters (capabilities, seccomp, AppArmor or SELinux) decide what the process is allowed to ask the kernel to do.

Docker, containerd and runc are just the tools that set these four things up for you, in the right order, very quickly. Once you see that, most "magic" questions in interviews become simple.

From your world

You already know every system call involved. docker run ends with something very close to clone(CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWCGROUP), then pivot_root() into the image's files, then execve() of your program. If you have written a daemon that forks children, you have done 80% of what runc does. Docker is packaging, an API and a lot of careful ordering around these calls.

Where the analogy breaks: on a router, a crashed line card does not take down the route processor. Here, a kernel bug triggered from any container can crash the whole host, because there is only one kernel.
