cgroups v2: the meters (how much a process can use)

Namespaces hide things but do not limit anything. A process in its own PID namespace can still eat all the RAM on the box. Limits come from control groups. A cgroup is a folder in a special filesystem mounted at /sys/fs/cgroup. You create a folder, write limits into files in it, and write process IDs into its cgroup.procs file. The kernel then counts and caps everything those processes do.

Linux has two versions. cgroup v2 has one single tree (the "unified hierarchy") where every controller (memory, cpu, io, pids) follows the same folders. The older v1 had a separate tree per controller, which got messy. Docker Engine 29 deprecated cgroup v1 (support is promised until at least May 2029), and modern distros boot with v2, so learn v2 and treat v1 as legacy.

From your world

cpu.max is CFS bandwidth control: a quota of microseconds per period. 150000 100000 means "150 ms of CPU time every 100 ms period", which is 1.5 cores. That is a token-bucket policer: the bucket refills every period, and once the tokens are gone the task waits, just like packets above the CIR waiting in a shaper. memory.max is a hard ceiling that calls the same OOM killer you have debugged on embedded boards. Where it breaks: a policer drops excess packets; CPU throttling never drops work, it only delays it, which shows up as latency spikes rather than errors.

Must know: Labs 5 and 6 (OOM kill vs CPU throttling) and the "Who does what" section below come up in almost every container interview and incident. Do these two labs even if you skip the others.

Lab 5: build a cgroup by hand and trigger the OOM killer

First check you are on v2 and see which controllers are on offer. (On systemd distros the root usually delegates cpu, memory, io and pids to children already.)

$ stat -fc %T /sys/fs/cgroup
cgroup2fs
$ cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma misc
$ cat /sys/fs/cgroup/cgroup.subtree_control
cpu io memory pids

Now make a group, cap it at 50 MB with no swap, and move your own shell into it. Everything that shell starts is now inside the meter.

$ sudo mkdir /sys/fs/cgroup/demo
$ echo 50M  | sudo tee /sys/fs/cgroup/demo/memory.max
50M
$ echo 0    | sudo tee /sys/fs/cgroup/demo/memory.swap.max
0
$ echo $$   | sudo tee /sys/fs/cgroup/demo/cgroup.procs
5521
$ cat /proc/self/cgroup
0::/demo
$ python3 -c 'x = bytearray(200 * 1024 * 1024)'
Killed
$ grep oom_kill /sys/fs/cgroup/demo/memory.events
oom_kill 1

Python asked for 200 MB, the group only allowed 50 MB, the kernel's OOM killer sent SIGKILL, and the shell printed Killed. The counter in memory.events is the proof. Docker reads exactly that kind of signal to set "OOMKilled": true.

Lab 6: CPU throttling is a pause, not a kill

$ echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max     # 0.2 of one core
$ timeout 5 sh -c 'while :; do :; done'
$ cat /sys/fs/cgroup/demo/cpu.stat
usage_usec 1003874
user_usec 1001502
system_usec 2372
nr_periods 50
nr_throttled 50
throttled_usec 3987520

In 5 seconds of wall time the busy loop got about 1 second of CPU (20%), was throttled in every one of the 50 periods and spent about 4 seconds waiting. Nothing was killed. In production this is the silent latency killer: a service with a tight CPU limit looks healthy but its p99 latency (p99 = the latency that 99% of requests beat; it describes the slowest 1%) jumps. Watch nr_throttled (in Kubernetes the cAdvisor metric, cAdvisor being the kubelet's built-in container metrics collector, container_cpu_cfs_throttled_periods_total).

Clean up by moving your shell back to the root and removing the folder: echo $$ | sudo tee /sys/fs/cgroup/cgroup.procs; sudo rmdir /sys/fs/cgroup/demo.

docker stats has no secret source: it reads these same cgroup files. If you use the cgroupfs driver instead of systemd, the path is /sys/fs/cgroup/docker/<id>/; docker info | grep -i cgroup tells you which.

Careful: the runtime inside may not know its limit. A program that sizes itself from /proc/meminfo or the host CPU count will see the whole machine. JVMs are container-aware since JDK 10, and cgroup v2-aware since JDK 15 (backported to 11.0.16 and 8u372); on older builds running on a cgroup v2 host the JVM sees the host's RAM; Go 1.25 and later respect the cgroup CPU limit when picking GOMAXPROCS; Node.js has historically needed --max-old-space-size. An older JVM on a 64 GB host inside a 1 GB container will plan a huge heap and get OOM-killed. This is the root cause of many "random" exit 137 crashes.

cgroup v2 also adds PSI (pressure stall information) files such as memory.pressure and cpu.pressure, which say what percentage of time tasks were stalled waiting for that resource. They are a better early warning than "usage is 90%". Kubernetes enforces pod requests and limits through cpu.weight, cpu.max and memory.max in the pod's cgroup, not through PSI. Recent kubelets also export PSI (memory, CPU and I/O pressure) as metrics (the KubeletPSI feature, beta in Kubernetes 1.34), which make a good early warning for node pressure; see Scheduling & Autoscaling.
