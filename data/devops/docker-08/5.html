Security filters: capabilities, seccomp, LSMs, user namespaces

Namespaces and cgroups do not stop a process from asking the kernel to do dangerous things, like loading a kernel module or rebooting the host. Four more layers handle that. Every system call from a container passes through them.

Capabilities: root cut into pieces

Since Linux 2.2, the all-powerful root has been split into about 40 separate capabilities (see capabilities(7)). CAP_NET_BIND_SERVICE lets you bind ports below 1024, CAP_NET_ADMIN lets you change routes and interfaces, CAP_SYS_ADMIN is a huge bag that includes mount(). Docker keeps only 14 by default (the list lives in moby's defaults.go): CHOWN, DAC_OVERRIDE, FSETID, FOWNER, MKNOD, NET_RAW, SETGID, SETUID, SETFCAP, SETPCAP, NET_BIND_SERVICE, SYS_CHROOT, KILL, AUDIT_WRITE. So "root in a container" is already weaker than real root.

$ docker run --rm alpine grep Cap /proc/self/status
CapInh:	0000000000000000
CapPrm:	00000000a80425fb
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap
$ docker run --rm --cap-drop=ALL alpine grep CapEff /proc/self/status
CapEff:	0000000000000000
$ docker run --rm alpine ip link add dummy0 type dummy
ip: RTNETLINK answers: Operation not permitted
$ docker run --rm --cap-add=NET_ADMIN alpine ip link add dummy0 type dummy && echo ok
ok

seccomp: an ACL on system calls

seccomp (secure computing mode) lets a process install a small BPF program that the kernel runs on every system call, before doing any work. Docker's default profile is an allowlist that blocks around 44 of the 300+ system calls, including reboot, kexec_load, init_module, mount, keyctl, bpf and others that have been sources of kernel exploits. Details are in the Docker seccomp doc.

$ docker run --rm alpine grep '^Seccomp:' /proc/self/status
Seccomp:	2
$ docker run --rm --security-opt seccomp=unconfined alpine grep '^Seccomp:' /proc/self/status
Seccomp:	0
$ docker info --format '{{.SecurityOptions}}'
[name=apparmor name=seccomp,profile=builtin name=cgroupns]

2 means "filter mode is on"; 0 means no filter. You never want unconfined in production.

From your world

seccomp is an ACL on the syscall table; capabilities are CLI privilege levels. A seccomp profile is a match-action list keyed on the syscall number (and sometimes arguments), just like an ingress ACL keyed on the 5-tuple, with a default action. Capabilities are like splitting "enable" mode into fine-grained RBAC roles: you can let a user change interface descriptions without letting them reload the box.

Where it breaks: an ACL can look deep into headers; seccomp only sees the syscall number and the raw register arguments. It cannot follow a pointer, so it cannot filter on a file name passed to open() or a path in mount(). That is why path-based rules live in an LSM (AppArmor, SELinux), not in seccomp.

LSMs and user namespaces

  • AppArmor (Ubuntu, Debian) or SELinux (RHEL, Fedora) are Linux Security Modules. Docker loads a profile called docker-default on AppArmor systems that, for example, denies writes to most of /proc and /sys. On SELinux, bind mounts need :z or :Z to get the right label.
  • User namespaces map UIDs. With userns-remap or rootless Docker, UID 0 in the container becomes, for example, UID 100000 on the host (ranges come from /etc/subuid and /etc/subgid). If the process escapes, it lands as a nobody. This is off by default in Docker, which is why "root in the container is root on the host" is the honest default answer. More on this in Production, Security & CI.
$ cat /proc/$PID/uid_map            # default Docker: no remapping
         0          0 4294967295
$ cat /proc/$PID_REMAPPED/uid_map   # with userns-remap
         0     100000      65536

Read a uid_map line as "inside-start, outside-start, count". The first line says UID 0 inside is UID 0 outside: no protection. The second says inside 0..65535 is outside 100000..165535.

Real escapes: In CVE-2019-5736 a malicious container overwrote the host's runc binary through /proc/self/exe and became root on the host; runc now clones itself into a sealed memfd before entering a container. In CVE-2024-21626 ("Leaky Vessels", January 2024) a WORKDIR ordering bug leaked a host file descriptor; fixed in runc 1.1.12. Lesson: patch the runtime, not only your images. Both stories are explained by Palo Alto Unit 42 and Snyk (links in Resources).
