Namespaces: the walls (what a process can see)

A namespace wraps one kind of global kernel resource so that the processes inside get their own private copy of it. Linux has eight kinds today (see the namespaces(7) man page). Each kind is turned on by one CLONE_NEW* flag passed to clone() or unshare(), and you can join an existing one with setns().

NamespaceClone flagWhat gets its own copyWhat you notice inside a container
pidCLONE_NEWPIDProcess ID numbersYour app is PID 1; ps shows only your processes
netCLONE_NEWNETInterfaces, IPs, routes, ARP table, iptables, sockets, portsOwn eth0 and lo; port 80 is free even if the host uses 80
mntCLONE_NEWNSThe list of mountsYour / is the image, not the host disk
utsCLONE_NEWUTSHostname and domain namehostname prints the container ID
ipcCLONE_NEWIPCSystem V IPC, POSIX message queuesShared memory of other containers is invisible
cgroupCLONE_NEWCGROUPThe view of /sys/fs/cgroupYour cgroup looks like the root /
userCLONE_NEWUSERUID and GID numbers, capabilitiesroot inside can be an unprivileged user outside
timeCLONE_NEWTIMEMonotonic and boot-time clocksUsed for checkpoint/restore, not by Docker

The mount namespace flag is called CLONE_NEWNS ("new namespace") and not CLONE_NEWMNT because it was the very first one, added in 2002, when nobody expected there would be more.

From your world

A network namespace is a VRF. Each one has its own interfaces, routing table, neighbour (ARP) table and netfilter rules, exactly like a VRF gives each customer a separate routing instance on a Cisco or Ciena box. Moving a veth end into a namespace is like assigning an interface to a VRF. Where it breaks: a VRF only separates forwarding state; a net namespace also separates the socket table, so two containers can both bind() port 80.

Before the labs: all nine labs on this page need a Linux root shell (sudo on a Linux VM, a cloud box, or WSL 2). On Windows use WSL 2 with Ubuntu; on macOS use a Linux VM. Docker Desktop's own VM is not enough, because you need unshare, mount and write access to /sys/fs/cgroup. See Lab setup. If you see unshare: command not found, you are not in a Linux shell yet.

Lab 1: make a PID namespace with one command

You need a Linux machine (a VM, WSL 2 or a cloud box). unshare is in the util-linux package that every distro ships. --fork is needed because the first child, not the caller, becomes PID 1. --mount-proc mounts a fresh /proc so ps reads the new namespace.

$ sudo unshare --pid --fork --mount-proc bash
# ps -ef
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 10:02 pts/0    00:00:00 bash
root           8       1  0 10:02 pts/0    00:00:00 ps -ef
# echo $$
1

Your shell now believes it is the first process on the machine. Open a second terminal on the host and look for it. The host still sees it with a normal, large PID. Both numbers are true at the same time; the NSpid line lists the PID in every namespace level, outermost first.

$ ps -ef | grep 'unshare --pid'
root       23810   23790  0 10:02 pts/0    00:00:00 sudo unshare --pid --fork --mount-proc bash
root       23811   23810  0 10:02 pts/0    00:00:00 unshare --pid --fork --mount-proc bash
$ grep NSpid /proc/$(pgrep -P 23811)/status
NSpid:	23812	1

Lab 3: a network namespace wired with a veth pair

This is exactly what Docker does for every container on the default bridge network, minus the bridge. A veth pair is a virtual cable: whatever goes in one end comes out the other.

sudo ip netns add red                              # new, empty net namespace
sudo ip link add veth-host type veth peer name veth-red
sudo ip link set veth-red netns red                # push one end into "red"
sudo ip addr add 10.10.0.1/24 dev veth-host
sudo ip link set veth-host up
sudo ip netns exec red ip addr add 10.10.0.2/24 dev veth-red
sudo ip netns exec red ip link set veth-red up
sudo ip netns exec red ip link set lo up
sudo ip netns exec red ping -c 2 10.10.0.1
$ sudo ip netns exec red ip -brief addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
veth-red@if7     UP             10.10.0.2/24 fe80::5c1e:9fff:fe2a:11b0/64
$ sudo ip netns exec red ping -c 2 10.10.0.1
64 bytes from 10.10.0.1: icmp_seq=1 ttl=64 time=0.051 ms
64 bytes from 10.10.0.1: icmp_seq=2 ttl=64 time=0.043 ms

Add a Linux bridge, plug several veth host ends into it and add a MASQUERADE rule, and you have rebuilt docker0. The Docker Networking page walks that packet path in full.

Lab 4: look inside a real container with nsenter

Every process has a folder /proc/<pid>/ns/ with one symlink per namespace. The number in brackets is the namespace's inode number. Two processes are in the same namespace exactly when those numbers match.

$ docker run -d --name web nginx:1.30
$ PID=$(docker inspect --format '{{.State.Pid}}' web)
$ echo $PID
24117
$ sudo ls -l /proc/$PID/ns
lrwxrwxrwx 1 root root 0 Nov 23 10:15 cgroup -> 'cgroup:[4026532611]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 ipc -> 'ipc:[4026532543]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 mnt -> 'mnt:[4026532541]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 net -> 'net:[4026532546]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 pid -> 'pid:[4026532544]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 time -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 user -> 'user:[4026531837]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 uts -> 'uts:[4026532542]'
$ sudo ls -l /proc/1/ns/user /proc/1/ns/time
lrwxrwxrwx 1 root root 0 Nov 23 10:15 /proc/1/ns/time -> 'time:[4026531834]'
lrwxrwxrwx 1 root root 0 Nov 23 10:15 /proc/1/ns/user -> 'user:[4026531837]'

See it? user and time have the same numbers as host PID 1: the container shares those with the host. The other six are new. Now step into only the container's network namespace while keeping the host's tools (handy because the nginx image has no ip command):

$ sudo nsenter --target $PID --net ip -brief addr
lo               UNKNOWN        127.0.0.1/8
eth0@if12        UP             172.17.0.2/16
$ sudo nsenter --target $PID --net ss -ltn
State   Recv-Q  Send-Q   Local Address:Port   Peer Address:Port
LISTEN  0       511            0.0.0.0:80          0.0.0.0:*

Tip: docker exec is built on the same idea. It asks runc to start a new process and setns() it into all of the container's namespaces and its cgroup. That is why docker exec only works on a running container: no process, no namespaces to join. lsns lists every namespace on the host with the process that owns it.
