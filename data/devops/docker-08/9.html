Interview questions on internals

Say this early: "A container is a regular Linux process. Namespaces control what it can see, cgroups control how much it can use, and an overlay root filesystem gives it its files. All containers share the host kernel, so the isolation is weaker than a VM's." Then prove each clause with one concrete detail.

How is a container different from a virtual machine?

A VM runs its own guest kernel on virtual hardware provided by a hypervisor (KVM, Hyper-V), using CPU virtualization features like VT-x and EPT. A container runs no kernel of its own. It is a process on the host kernel, fenced in by namespaces (pid, net, mnt, uts, ipc, cgroup), limited by cgroups, and filtered by capabilities, seccomp and an LSM. Result: containers start in milliseconds and pack densely, but a kernel bug reachable from one container affects every container on the host. That is why public clouds run containers inside VMs, and why Lambda uses Firecracker microVMs.

How to answer

One sentence each for VM and container, then the trade-off (density and speed vs isolation strength), then one real-world proof (containers inside VMs, or Firecracker). Do not just say "lighter".

Likely follow-ups
  • Can a container run a different kernel version? (No. It can run a different distro userland, but uname shows the host kernel.)
  • Why can Docker Desktop run Linux containers on a Mac? (It runs a small Linux VM.)
  • When would you pick gVisor or Firecracker?
Which namespaces does Docker use, and how does docker exec work?

By default: pid, net, mnt, uts, ipc and cgroup. The user namespace only with userns-remap or rootless mode; the time namespace is not used. Each is created with a CLONE_NEW* flag. docker exec asks the runtime to start a new process and call setns() on each file under /proc/<container-pid>/ns/, and to put it into the same cgroup, so it sees exactly what PID 1 sees. Flags like --network host or --pid host simply skip creating one namespace.

How to answer

List them fast, name the syscalls (clone, unshare, setns), then show the debugging tool: nsenter --target PID --net. Interviewers with a systems background love the /proc/PID/ns inode detail.

Likely follow-ups
  • How do containers in a Kubernetes pod share an IP? (They join one net namespace held by the pause container; Docker equivalent: --network container:<id>.)
  • Why is PID 1 special inside a container?
A container dies with exit code 137. Walk me through what happened in the kernel.

137 is 128 + 9, so the process got SIGKILL. The most common source is the memory cgroup: the container's usage hit memory.max, the kernel failed to reclaim enough page cache, and the OOM killer chose a process in that cgroup and killed it. Confirm with docker inspect --format '{{.State.OOMKilled}}', the oom_kill counter in memory.events, or dmesg lines mentioning the memory cgroup. The other source is a manual kill, or docker stop sending SIGKILL after the 10-second grace period. Fix: right-size the limit, make the runtime cgroup-aware (JVM heap percentage, Node heap flag), or fix the leak.

How to answer

Decode the number, name the mechanism (memory.max -> reclaim -> OOM killer), show how you would prove it, then fix and prevent (alert on memory.current near memory.max, or on PSI memory pressure).

Likely follow-ups
  • What does the same thing look like in Kubernetes? (Pod status OOMKilled, reason in kubectl describe.)
  • What happens at the CPU limit instead? (Throttling, not killing.)
Explain OverlayFS copy-on-write and its performance cost.

OverlayFS merges read-only lower directories (image layers) and one writable upper directory into a single mount. Reads go to the topmost layer that has the file, with no copying, and identical files are shared in the page cache across containers. The first write to a file from a lower layer triggers a copy-up of the entire file into the upper directory. Deletes create whiteouts. Costs: first-write latency proportional to file size, extra disk usage, and some odd semantics (renaming a directory that lives in a lower layer can return EXDEV). That is why write-heavy paths (databases, logs) go on volumes, which bypass the overlay entirely.

How to answer

Draw the four directories (lower, upper, work, merged), describe read / write / delete in one line each, then give the practical rule: "state goes on volumes".

Likely follow-ups
  • Why does deleting a file in a later Dockerfile step not shrink the image?
  • What is the role of the workdir?
What are dockerd, containerd and runc, and why did Kubernetes drop Docker?

dockerd is Docker's daemon: the API, builds via BuildKit, networks and volumes. containerd is a high-level runtime that manages images, snapshots and container lifecycle, and starts one shim per container. runc is the low-level OCI runtime that creates namespaces and cgroups from config.json, execs the process and exits. Kubernetes only needs the containerd part, through its Container Runtime Interface (CRI). The adapter it kept for Docker, dockershim, was removed in v1.24. Nothing broke for developers because Docker builds standard OCI images, which containerd and CRI-O run as-is.

How to answer

Draw the chain left to right. Point out the shim (why containers survive daemon restarts). End with "Docker is a developer tool; the runtime underneath is the standard part".

Likely follow-ups
  • What is CRI-O?
  • How would you debug containers on a Kubernetes node without Docker? (crictl, ctr, nsenter.)
Build a container from Linux primitives, step by step.

(1) Prepare a root filesystem, ideally as an overlay of read-only layers plus a writable upper. (2) Create a cgroup folder, write memory.max, cpu.max, pids.max. (3) clone() with NEWPID, NEWNS, NEWUTS, NEWIPC, NEWNET, NEWCGROUP (and NEWUSER for rootless). (4) In the child: make mounts private, pivot_root into the rootfs, mount /proc, unmount the old root, set the hostname. (5) Parent: create a veth pair, move one end into the child's net namespace, attach the other to a bridge, add NAT. (6) Move the child PID into cgroup.procs. (7) Drop capabilities, set no-new-privileges, load a seccomp filter. (8) execve the app as PID 1, with an init like tini if it spawns children.

How to answer

Group the steps as "see" (namespaces), "use" (cgroups), "files" (rootfs) and "ask" (security). Order matters: say why seccomp goes last (the setup itself needs syscalls the filter blocks).

Likely follow-ups
  • Why pivot_root and not chroot?
  • How would you make it rootless? (User namespace first, then the rest as an unprivileged user.)

Your 60-second answer: "What is a container, really?"

"A container is just a Linux process with extra settings. Namespaces give it a private view: its own PID numbers, network interfaces, mount table and hostname. A cgroup gives it budgets: memory.max where the OOM killer steps in, and cpu.max where it gets throttled. Its root filesystem is an OverlayFS mount of read-only image layers with a writable layer on top. Capabilities, seccomp and AppArmor limit what it may ask the kernel to do. Docker's CLI talks to dockerd, which asks containerd, which starts a shim, which runs runc to set all of that up and exec the app. Since everything shares one kernel, it is much faster than a VM but less isolated, so for untrusted code I would use gVisor or Firecracker microVMs."
