Who does what: dockerd, containerd, shim, runc

Beginners ask: "Why are there three programs? Isn't Docker one program?" It used to be closer to one. Over time it was split so that each piece has one job and can be reused. Kubernetes, for example, uses containerd and runc without dockerd at all. Click through what happens when you type docker run -d -p 8080:80 nginx:1.30.

  1. CLI to dockerd. The docker command is only a client. It sends an HTTP REST request over the Unix socket /var/run/docker.sock to the daemon dockerd.
  2. Pull if needed. If the image is missing, the image is resolved to docker.io/library/nginx:1.30; the manifest for your CPU architecture is fetched and only missing layers are downloaded, each by its sha256 digest.
  3. dockerd to containerd. dockerd handles Docker-only features (networks, volumes, the API) and asks containerd over gRPC to create the container. containerd owns images, unpacks layers into snapshots (the overlay mounts) and writes an OCI bundle: a config.json plus a root filesystem.
  4. Start a shim. containerd starts a small containerd-shim-runc-v2 process for this container. The shim will be the container's parent for its whole life.
  5. runc does the kernel work. The shim calls runc, the low-level OCI runtime. runc reads config.json, creates the namespaces, sets up the cgroup, mounts /proc, pivot_roots into the merged overlay, applies capabilities, seccomp and AppArmor, and finally execves nginx.
  6. runc leaves. runc exits right after the start. nginx is now PID 1 in its PID namespace; on the host it is a child of the shim. The shim keeps its stdin/stdout open and collects its exit code later. Because of this, dockerd and containerd can restart without killing your containers (Docker's live-restore option).
  7. Networking and logs. dockerd's network code already created a veth pair, put one end inside the new net namespace as eth0, plugged the other into the docker0 bridge, and added a DNAT rule for -p 8080:80. Output on stdout goes to the json-file log driver.

The OCI: three standards that make it all swappable

The Open Container Initiative (OCI) is a Linux Foundation project that wrote down the formats so any tool can work with any other:

SpecWhat it definesWho uses it
Image specIndex (per-platform list) -> manifest -> config JSON + ordered layer tarballs, all addressed by sha256BuildKit, Buildah, registries, containerd
Runtime specA "bundle" = config.json + rootfs/; lifecycle verbs create, start, kill, deleterunc, crun, gVisor's runsc, Kata
Distribution specThe HTTP API a registry speaks: /v2/<name>/manifests/<ref>, /v2/<name>/blobs/<digest>Docker Hub, ECR, ACR, GHCR, Harbor

Lab 9: run a container with runc only, no Docker

This is the flow from the runc README. We borrow Docker only to get a root filesystem out of an image.

$ mkdir -p ~/mycontainer/rootfs && cd ~/mycontainer
$ docker export $(docker create busybox) | tar -C rootfs -xf -
$ runc spec                       # writes a default config.json
$ ls
config.json  rootfs
$ grep -A3 '"args"' config.json
		"args": [
			"sh"
		],
$ sudo runc run demo
/ # ps
PID   USER     TIME  COMMAND
    1 root      0:00 sh
    7 root      0:00 ps
/ # hostname
runc

That is a full container: own PID 1, own hostname (runc is the default in the generated spec), own mounts. No daemon, no image, no network (the default spec gives only loopback). Open config.json and you will find the namespaces list, the capability sets and the cgroup settings in plain JSON. Docker's job is mostly to generate this file well.

$ sudo ctr --namespace moby containers list
CONTAINER                                                           IMAGE    RUNTIME
5c1d0a7e2b9f4f...                                                   -        io.containerd.runc.v2
$ ps -ef --forest | grep -A1 containerd-shim
root  24090     1  0 10:15 ?  00:00:00 /usr/bin/containerd-shim-runc-v2 -namespace moby -id 5c1d0a7e2b9f... -address /run/containerd/containerd.sock
root  24117 24090  0 10:15 ?  00:00:00  \_ nginx: master process nginx -g daemon off;

ctr is containerd's debug client. Docker keeps its containers in the containerd namespace called moby (a containerd "namespace" is just a label for multi-tenancy, not a Linux namespace). The forest view shows nginx's parent is the shim, and the shim's parent is PID 1 (systemd): runc is gone.

From your world

The shim is non-stop forwarding. On a router, the route processor (control plane) can restart while line cards keep forwarding packets. Here dockerd and containerd are the control plane; the shim and your process are the data plane. With "live-restore": true in daemon.json you can upgrade dockerd and your containers keep serving.

Where it breaks: unlike NSF on most routers, this is not on by default. A dockerd restart without live-restore does stop your containers. Even with it, the "data plane" is not complete: log collection and docker-proxy port forwarding pause until dockerd is back, and live-restore is not promised across a jump between major Docker versions.
