The gates every API request passes

Good to know (SDE-2)

Every action in Kubernetes is an HTTPS call to the kube-apiserver: your kubectl apply, the scheduler binding a pod, a controller creating a ReplicaSet, the kubelet updating status. All of them go through the same gates, in this order. Click Next.

  1. TLS. The connection is HTTPS. The API server presents its certificate; clients usually trust the cluster CA from their kubeconfig.
  2. Authentication. Who is calling? The API server tries its authenticators: client certificates (the common name becomes the user), OIDC tokens from your identity provider (Entra ID, Okta, Google), or ServiceAccount tokens for pods. If none accept the request, the answer is 401. Kubernetes has no "User" objects; users live outside the cluster.
  3. Authorization. May this identity do this verb on this resource in this namespace? The Node authorizer handles kubelets, RBAC handles everyone else. No matching allow rule means 403 Forbidden.
  4. Mutating admission. Plugins and webhooks may change the object: add default values, inject a sidecar, set a default StorageClass, add labels. MutatingAdmissionPolicy (CEL-based, GA in v1.36) can do this without running a webhook server.
  5. Schema validation. Is it a well-formed object of that kind? Unknown fields and wrong types are rejected here.
  6. Validating admission. Policies that can only say yes or no: Pod Security Admission, ValidatingAdmissionPolicy (CEL rules inside the API server, GA in v1.30), and webhooks like Kyverno or OPA Gatekeeper. One "no" rejects the request.
  7. Persist. Only now is the object written to etcd. Controllers and the scheduler see it through their watches and start working. Every gate was also recorded in the audit log if auditing is enabled.

From your world

This is a packet pipeline with ACL stages. TLS is the encrypted tunnel, authn is matching the source to a known peer, authz is the ACL lookup (permit or implicit deny), mutating admission is a policy that rewrites the packet (like setting DSCP), and validating admission is a final drop-or-forward filter. Where this breaks: packets are processed in nanoseconds in hardware; each API request can call out to webhook servers over the network, so a slow or dead webhook can slow down or block the whole cluster. Always set timeoutSeconds and think about failurePolicy.
