Designing a shared cluster (multi-tenancy)

Deep dive (platform teams)

Many teams on one cluster save money but need fences. This is a favourite SDE-2 question at companies with large platform teams. Build the answer from layers:

  1. Namespace per team (or per team and environment). The unit everything else attaches to.
  2. RBAC: the team's identity-provider group gets edit in its namespaces, view elsewhere if needed; a small SRE group has cluster-admin through a "break-glass" process with audit.
  3. ResourceQuota and LimitRange: cap total CPU, memory and object counts per namespace, and give every container default requests and limits, so one team cannot starve the others.
  4. NetworkPolicy default deny plus explicit allows between teams.
  5. Pod Security restricted on every tenant namespace.
  6. Node isolation for sensitive or noisy tenants: taints and tolerations plus node affinity, so their pods run on their own machines (shared kernel risk goes away between teams).
  7. Separate clusters when the tenants do not trust each other at all (different customers, regulated data). Namespaces are not a hard security boundary; a cluster is a much stronger one.

Interviewers love this: say the trade-off out loud. "Namespaces give soft isolation that is cheap and easy to operate. For hostile tenants I would use separate clusters, or at least dedicated node pools and sandboxed runtimes, because all pods on a node share one kernel."
