Supply chain and policy as code

Deep dive (platform teams)

Attackers do not only break in through the API. They also hide inside the images you run. Securing the software supply chain means knowing what is inside each image and only running images you built.

  • Scan images in CI for known vulnerabilities (Trivy, Grype) and produce an SBOM (software bill of materials, a list of every package inside).
  • Sign images after the build (Sigstore cosign) and verify signatures at admission (Kyverno, Sigstore policy-controller). Unsigned image? Rejected at gate 6.
  • Pin by digest (image: web@sha256:...) in production, so the bytes you tested are the bytes you run. Tags can be moved; digests cannot.
  • Allow only your registries, for example with a ValidatingAdmissionPolicy.

Here is a policy that runs inside the API server, with no webhook, and rejects any Deployment whose images come from outside your registry. It uses CEL (Common Expression Language), a small, safe expression language.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: only-company-registry
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: ["apps"]
      apiVersions: ["v1"]
      operations: ["CREATE", "UPDATE"]
      resources: ["deployments"]
  validations:
  - expression: >-
      object.spec.template.spec.containers.all(c,
        c.image.startsWith('registry.example.com/')) &&
      (!has(object.spec.template.spec.initContainers) ||
        object.spec.template.spec.initContainers.all(c,
          c.image.startsWith('registry.example.com/')))
    message: "images must come from registry.example.com"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: only-company-registry-binding
spec:
  policyName: only-company-registry
  validationActions: ["Deny"]
  matchResources:
    namespaceSelector:
      matchLabels: { team-owned: "true" }
$ kubectl apply -f deploy-from-dockerhub.yaml
The deployments "web" is invalid: : ValidatingAdmissionPolicy 'only-company-registry' with binding 'only-company-registry-binding' denied request: images must come from registry.example.com

Close the side doors. This teaching policy checks only Deployments, and the expression has to cover initContainers too, or a sneaky init container pulls from anywhere. Production policies usually match Pods as well (plus the other workload kinds: StatefulSets, DaemonSets, Jobs, CronJobs), so every path to a running image is checked, including bare pods and kubectl debug ephemeral containers. Kyverno and Gatekeeper ship ready-made "allowed registries" policies that do this for you.

Audit logs: who did what

The API server can write an audit log entry for every request: who, what verb, which object, allowed or denied, from which IP. You choose the detail per rule in an audit policy (None, Metadata, Request, RequestResponse). Log Secrets at Metadata level only, or the audit log itself becomes a store of passwords. Managed clusters can stream audit logs to the cloud's log service. In an incident, "who deleted this Deployment at 3 a.m.?" is answered here.
