RBAC hands-on

Good to know (SDE-2)

Let us give the dev team read access to pods and logs in the shop namespace, and nothing else.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: shop
rules:
- apiGroups: [""]                 # "" = the core API group (pods, services, secrets...)
  resources: ["pods", "pods/log"] # pods/log is a subresource; it needs its own entry
  verbs: ["get", "list", "watch"]
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-team-reads-pods
  namespace: shop
subjects:
- kind: Group
  name: dev-team                  # group name as your OIDC provider sends it
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
# Kubernetes ships ClusterRoles named view, edit, admin and cluster-admin.
# Binding a ClusterRole with a RoleBinding limits it to THIS namespace only.
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: sre-edit-shop
  namespace: shop
subjects:
- kind: Group
  name: sre
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: edit
  apiGroup: rbac.authorization.k8s.io

Then test it. kubectl auth can-i asks the API server "would this be allowed?" without doing it. With --as you can impersonate someone (if you have the impersonate right, which admins do).

$ kubectl auth can-i list pods -n shop --as=alice --as-group=dev-team
yes
$ kubectl auth can-i delete pods -n shop --as=alice --as-group=dev-team
no
$ kubectl auth can-i get secrets -n shop --as=system:serviceaccount:shop:web
no
$ kubectl auth can-i --list -n shop --as=alice --as-group=dev-team
Resources                                       Non-Resource URLs   Resource Names   Verbs

$ kubectl delete pod web-7c9d8f6b5d-2xkqp -n shop      # as alice
Error from server (Forbidden): pods "web-7c9d8f6b5d-2xkqp" is forbidden: User "alice" cannot delete resource "pods" in API group "" in the namespace "shop"

Tip: kubectl auth whoami prints the user and groups the API server sees for you. When an OIDC login "does not work", this is the first thing to check: often the group claim is missing or named differently.

Permissions that are more powerful than they look

RBAC is only as good as the roles you write. Some rights quietly give away much more:

PermissionWhy it is dangerous
verbs: ["*"], resources: ["*"]Grants everything, including resource types that will be added in the future.
create pods (or Deployments, Jobs...)Anyone who can create a pod can mount any Secret in that namespace and run as any ServiceAccount there. "Create workload" is close to "read all secrets in the namespace".
get/list secretsSecrets include ServiceAccount tokens, database passwords and TLS keys. list returns the full content, not just names.
escalate, bindNormally you cannot grant rights you do not have. These verbs remove that protection.
impersonateLets you act as another user, group or ServiceAccount, including admins.
nodes/proxyDirect access to the kubelet API on nodes, which can run commands in any pod on that node.
Group system:mastersHard-coded superuser: bypasses RBAC entirely and cannot be limited by any Role. Never put normal users in it.
