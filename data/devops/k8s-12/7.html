Secrets: the safe that is made of glass

Good to know (SDE-2)

A Kubernetes Secret stores small sensitive values (up to 1 MiB) such as passwords and TLS keys. The surprise for everyone: by default the values are only base64-encoded, which is a way of writing bytes as text, not encryption. Anyone who can read the Secret object, or read etcd's disk, can read the password.

$ kubectl create secret generic db-cred -n shop --from-literal=password='S3cr3t!'
secret/db-cred created
$ kubectl get secret db-cred -n shop -o jsonpath='{.data.password}'; echo
UzNjcjN0IQ==
$ echo 'UzNjcjN0IQ==' | base64 -d; echo
S3cr3t!

How teams make Secrets genuinely safe, in rising order of effort:

  1. Lock down RBAC. Very few subjects get get/list on secrets. Remember that "create pods" is almost the same as "read secrets".
  2. Encrypt at rest in etcd. Configure the API server with an EncryptionConfiguration, ideally the KMS v2 provider, so the encryption key lives in a cloud key service. Managed clusters (EKS, AKS, GKE) offer this as a setting.
  3. Keep the real secret outside the cluster. Store it in Vault, AWS Secrets Manager or Azure Key Vault, and sync it in with the External Secrets Operator or mount it with the Secrets Store CSI Driver.
  4. Never commit plain Secrets to git. If you use GitOps, commit encrypted ones (Sealed Secrets, SOPS) or only references to an external store.
