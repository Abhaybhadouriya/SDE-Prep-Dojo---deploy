Interview questions

More on the Kubernetes interview page and in Security & Identity in System Design.

Redraw this in 30 seconds

Five boxes. Every request, from a human or a pod, crosses the same gates in the same order.

How does RBAC work in Kubernetes? Role vs ClusterRole, RoleBinding vs ClusterRoleBinding.

"RBAC is the authorizer that decides whether an authenticated identity may perform a verb on a resource. A Role is a list of allow rules in one namespace; a ClusterRole is the same but cluster-scoped, so it can cover nodes or be reused everywhere. A RoleBinding grants a Role or ClusterRole to users, groups or ServiceAccounts in one namespace; a ClusterRoleBinding grants a ClusterRole across the whole cluster. Rules only add up, there is no deny, so anything not granted is forbidden. A neat trick is binding the built-in edit ClusterRole with a RoleBinding, which gives edit rights only in that namespace."

How to answer

Two pairs (what vs who-gets-it, namespace vs cluster), then "additive, default deny", then one practical example. Mention kubectl auth can-i to show you have used it.

Likely follow-ups
  • Can you write a deny rule? (No. Use admission policy for denials.)
  • Why can't a user grant a role with more rights than they have? (Escalation prevention, unless they hold escalate or bind.)
Are Kubernetes Secrets secure? How would you manage secrets in production?

"By default, no. Secret values are base64-encoded in etcd, so anyone with read access to the Secret or to etcd backups can read them. In production I would do four things: tight RBAC on secrets (and remember 'create pods' implies reading secrets in that namespace), encryption at rest with a KMS v2 provider so the key lives in a cloud key service, keep the source of truth in Vault or a cloud secret manager synced via External Secrets Operator or the Secrets Store CSI driver, and use workload identity so pods get short-lived cloud credentials instead of static keys. Plus: never commit plain Secrets to git, and keep Secrets at Metadata level in audit logs."

How to answer

Correct the myth first (base64 is not encryption), then layer the fixes from cheapest to strongest.

Likely follow-ups
  • Env var or mounted file for a secret? (Files can be rotated without restart and do not leak into crash dumps or child processes as easily.)
  • How does IRSA / EKS Pod Identity avoid static keys?
Write a NetworkPolicy so only the frontend can call the backend. What else must you remember?

"I select the backend pods with podSelector: app=backend, set policyTypes: [Ingress], and add one ingress rule from podSelector: app=frontend on TCP 8080. Because a pod becomes isolated as soon as one policy selects it, that alone blocks everyone else. I would also add a namespace-wide default deny so new services start closed, and if I deny egress I must allow DNS on UDP and TCP 53 to CoreDNS, or everything breaks. Finally I check the CNI actually enforces policies, Calico or Cilium do, and test it with a pod that should be blocked."

How to answer

Describe the YAML in words, state the isolation rule, then name the two gotchas (DNS egress, CNI support). Bonus: AND vs OR between namespaceSelector and podSelector.

Likely follow-ups
  • How would you allow traffic only for GET requests? (L7 policy: Cilium or service mesh.)
  • How does the CNI turn labels into rules? (Watches pods, maintains IP sets, programs iptables/nftables/eBPF.)
How would you isolate multiple teams (tenants) on one shared cluster?

"Namespace per team as the unit. RBAC from identity-provider groups: each team gets edit in its namespaces. ResourceQuota and LimitRange so nobody starves others and every container has requests and limits. Default-deny NetworkPolicies with explicit allows. Pod Security Admission at restricted. For sensitive or noisy teams, dedicated node pools with taints and affinity. Policy-as-code (ValidatingAdmissionPolicy or Kyverno) to enforce registries and labels. And I would say clearly: this is soft isolation. For untrusted tenants, separate clusters or sandboxed runtimes, because pods on a node share a kernel and some cluster-scoped objects like CRDs are shared."

How to answer

Walk the layers like a checklist, then close with the honest trade-off: cost and ops simplicity vs strength of isolation.

Likely follow-ups
  • What is shared between tenants that you cannot isolate with namespaces? (CRDs, cluster-scoped resources, the API server's capacity, the kernel on shared nodes.)
  • How do you stop one team overloading the API server? (API Priority and Fairness.)
An attacker gets a shell inside one of your pods. What can they do, and what limits the damage?

"It depends on our layers. With a mounted ServiceAccount token they can call the API with that account's rights, so least-privilege RBAC and automountServiceAccountToken: false matter. Without NetworkPolicies they can reach every pod and maybe the cloud metadata endpoint to steal node credentials, so default-deny egress and blocking metadata access matter. If the container runs as root with capabilities, a kernel or runtime bug could let them escape to the node; non-root, drop ALL, seccomp, read-only root filesystem and user namespaces shrink that. Workload identity limits cloud access to that one app's role. And audit logs plus runtime detection like Falco help us notice."

How to answer

Think like the attacker, step by step (API, network, node, cloud), and name the control that blocks each step.

Likely follow-ups
  • Why block the cloud metadata IP (169.254.169.254) from pods?
  • What does privileged: true give a container? (Nearly all host devices and capabilities: effectively root on the node.)

Scenario: a CI token with cluster-admin leaked on GitHub

A developer pushed a kubeconfig with a long-lived ServiceAccount token to a public repo. That account is bound to cluster-admin. The leak was 40 minutes ago. What do you do?

Weak answer: "Delete the file from the repo and change the password."

Strong answer: "Contain first: revoke the credential by deleting the token Secret (or the ServiceAccount) so the API server rejects it, and remove the ClusterRoleBinding. Deleting it from git does nothing, because it is already cloned and cached. Then investigate: search API server audit logs for that identity since the leak, looking for new RoleBindings, new ServiceAccounts, privileged pods, DaemonSets, changed webhooks or Secrets read. Remove anything the attacker created, and rotate every Secret they could have read, because cluster-admin could read all of them. Then prevent: CI uses short-lived tokens or OIDC federation instead of stored kubeconfigs, the deploy account gets edit only in its namespaces, and secret scanning blocks pushes like this."

Likely follow-ups
  • How do you know nothing persistent was left behind?
  • Why are short-lived tokens better even if they leak?

Your 60-second answer, "How do you secure a Kubernetes cluster?": "I think of it as gates and walls. Every request to the API server passes authentication, then RBAC authorization, then admission. So: humans log in through OIDC with groups, programs use their own ServiceAccounts, and RBAC is least privilege, no cluster-admin for CI, careful with secrets and pod creation rights. In admission I enforce Pod Security restricted, so containers run as non-root with all capabilities dropped and seccomp on, plus policies that only allow signed images from our registry. Inside the cluster the network is open by default, so I add default-deny NetworkPolicies and explicit allows, remembering DNS. Secrets are encrypted at rest with KMS and ideally sourced from Vault or a cloud secret manager, and pods reach the cloud with workload identity, not static keys. Audit logs on, and for untrusted tenants I use separate clusters, because namespaces are not a hard boundary."
