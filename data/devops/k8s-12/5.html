Locking down the pod itself

Good to know (SDE-2)

A container is a process sharing the host's kernel (see Docker internals). If it runs as root with extra kernel privileges and escapes, it owns the node. So we take privileges away, using fields in the pod's securityContext.

apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: shop
spec:
  securityContext:
    runAsNonRoot: true          # refuse to start if the image's user is root
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault      # the runtime's default syscall filter
  containers:
  - name: web
    image: registry.example.com/shop/web:1.8.2
    securityContext:
      allowPrivilegeEscalation: false   # no setuid tricks to gain more rights
      readOnlyRootFilesystem: true      # app cannot modify its own binaries
      capabilities:
        drop: ["ALL"]                   # remove every Linux capability
    volumeMounts:
    - name: tmp
      mountPath: /tmp                   # give it one writable place
  volumes:
  - name: tmp
    emptyDir: {}

From your world

These are kernel features you know. capabilities.drop: ["ALL"] removes things like CAP_NET_ADMIN (change routes and iptables) and CAP_SYS_ADMIN (mount, and much more). seccompProfile: RuntimeDefault applies a seccomp-BPF filter that blocks rarely needed syscalls. allowPrivilegeEscalation: false sets the no_new_privs flag on the process. And hostUsers: false (user namespaces, GA in v1.36) maps root inside the container to an unprivileged UID on the host, so even "root" inside is nobody outside. Where this breaks: all of these still share one kernel. A kernel bug can beat them all, which is why truly untrusted code gets a sandbox (gVisor, Kata Containers) or a separate VM.

Pod Security Standards and Pod Security Admission

Instead of reviewing every YAML by hand, Kubernetes defines three standard levels and a built-in admission controller, Pod Security Admission, that enforces them per namespace. It replaced PodSecurityPolicy, which was removed in v1.25.

LevelWhat it allowsUse for
PrivilegedAnything, including host network, host PID, privileged containers.System components only: CNI agents, storage drivers, node monitoring.
BaselineBlocks the known escalations (privileged, hostPath, host namespaces, adding dangerous capabilities) but allows root.A minimum for every app namespace; easy to adopt.
RestrictedBaseline plus: must run as non-root, drop ALL capabilities, no privilege escalation, seccomp RuntimeDefault.The goal for your own services.
 
$ kubectl label namespace shop \
    pod-security.kubernetes.io/enforce=restricted \
    pod-security.kubernetes.io/warn=restricted \
    pod-security.kubernetes.io/audit=restricted
namespace/shop labeled

$ kubectl apply -f bad-pod.yaml
Error from server (Forbidden): error when creating "bad-pod.yaml": pods "bad" is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "app" must set securityContext.allowPrivilegeEscalation=false), unrestricted capabilities (container "app" must set securityContext.capabilities.drop=["ALL"]), runAsNonRoot != true (pod or container "app" must set securityContext.runAsNonRoot=true), seccompProfile (pod or container "app" must set securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")

Careful: enforce applies to Pods. If you apply a Deployment that breaks the rules, the Deployment is accepted (you only get a warning), and then its ReplicaSet silently fails to create pods. You see "0/3 ready" and must run kubectl describe rs to find the PodSecurity error. Roll out new levels with warn and audit first, then enforce.
