ServiceAccounts: identities for programs

Good to know (SDE-2)

Every pod runs as a ServiceAccount. If you do not choose one, it gets the namespace's default ServiceAccount. The kubelet mounts a token for it at /var/run/secrets/kubernetes.io/serviceaccount/token. Modern tokens are short-lived (about an hour, refreshed by the kubelet automatically), bound to that one pod, and have an audience. Since v1.24 Kubernetes no longer auto-creates the old never-expiring token Secrets.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: web
  namespace: shop
automountServiceAccountToken: false   # most web apps never call the Kubernetes API
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: shop
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      serviceAccountName: web
      containers:
      - name: web
        image: registry.example.com/shop/web:1.8.2

Rules of thumb: one ServiceAccount per app, no token mounted unless the app talks to the Kubernetes API, and never give the default ServiceAccount extra rights (every pod that forgets to set one would inherit them).

Pods talking to the cloud: workload identity

Your pod needs to read from S3 or Azure Key Vault. The old way was to put a cloud access key into a Secret. If that key leaks, it works from anywhere, forever. The modern way is workload identity: the cloud trusts the cluster's ServiceAccount tokens and swaps them for short-lived cloud credentials. On AWS this is EKS Pod Identity or IRSA (IAM Roles for Service Accounts), on Azure it is Microsoft Entra Workload ID, on Google Cloud it is GKE Workload Identity Federation. No static keys exist to steal.
