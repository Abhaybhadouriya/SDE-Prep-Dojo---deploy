Interview questions

What is Schema Registry and why would you use it with Kafka?

Kafka brokers treat messages as opaque bytes, so nothing stops a producer from changing a format and breaking consumers. Schema Registry is a separate service that stores versioned schemas per subject, gives each schema a unique ID and enforces a compatibility rule when a new version is registered. Producers' serializers send a 5-byte header (magic byte plus schema ID) and a compact Avro or Protobuf payload; consumers fetch the schema by ID once and cache it. You get smaller messages, a shared contract and incompatible changes blocked before they ship.

How to answer

Start from the problem (opaque bytes, many teams), then the three things the registry does: store, identify, enforce. Mention the wire header to show you know how it works, not just that it exists.

Likely follow-ups
  • What happens if the registry is down? (Clients with cached IDs keep working; new schemas or new clients cannot start.)
  • Where does it store data? (The compacted _schemas topic.)
Explain BACKWARD vs FORWARD vs FULL compatibility. Which would you choose?

BACKWARD: a consumer using the new schema can read data written with the old one, so you can delete fields and add fields with defaults, and you upgrade consumers first. FORWARD: a consumer on the old schema can read data written with the new one, so you add fields and delete only fields with defaults, and you upgrade producers first. FULL: both. The transitive variants check against every earlier version instead of only the last. For Kafka topics with long retention or compaction I would choose BACKWARD_TRANSITIVE, or FULL_TRANSITIVE when producers and consumers deploy independently, because new consumers may replay old data.

How to answer

Frame each mode as "who reads whose data" and tie it to deployment order. Then justify a choice with Kafka's retention: that is the senior insight.

Likely follow-ups
  • Is adding a required field backward compatible? (No: old data has no value.)
  • Is renaming a field? (No, unless you use an alias and default; treat as add + deprecate.)
How do you evolve an event schema without breaking consumers? Walk through a real change.

Say we add a coupon field to Order. I add it as an optional union with "default": null, open a PR, and CI runs the registry's compatibility check against orders-value. Under BACKWARD it passes. I deploy consumers that understand coupon first (they read old records with the default), then producers start sending it. For a breaking change, such as changing money from rupees to paise, I create orders.v2 with a new subject, bridge or dual-publish for a while, migrate consumers one at a time, then retire v1 once its lag is zero.

How to answer

Use a concrete field, name the compatibility mode, state the deploy order, and separately describe the breaking-change path. Mentioning CI checks and auto.register.schemas=false shows production experience.

Likely follow-ups
  • How do consumers on v1 position themselves on v2? (Reset by timestamp; idempotent processing covers overlap.)
  • What about the key schema? (Keep it stable; changing it changes partitioning.)
Avro vs Protobuf vs JSON for Kafka events?

JSON is readable and needs no tooling, but it repeats field names in every message, is slower to parse and has no enforced contract unless you add JSON Schema. Avro writes only values, so it is very compact, and it resolves writer and reader schemas by field name, which suits Kafka and the Hadoop/data-lake world; it needs the writer's schema, which the registry provides. Protobuf uses numbered tags, so it is compact and tolerant of unknown fields, and it fits teams already using gRPC across many languages. I would pick Avro for data-platform and CDC topics, Protobuf where services already share .proto files, and JSON Schema only where human readability matters most.

How to answer

Compare on size, contract, evolution rules and ecosystem; finish with a recommendation tied to context. Avoid "X is always best".

Likely follow-ups
  • Why can Protobuf decode without the exact writer schema but Avro cannot? (Tags vs positional encoding.)
  • Does compression make JSON as small as Avro? (It narrows the gap, but parsing cost and the missing contract remain.)

Scenario: a producer deploy broke three consumers at 2 a.m.

The order service shipped a new version at 1:50 a.m. By 2 a.m. three consumer services (billing, search indexer, analytics) are crash-looping with deserialization errors on the orders topic, and lag is climbing. Asked by the interviewer: how do you recover, and how do you stop it happening again? Amazon Flipkart Walmart

Weak answer: "Restart the consumers and tell the producer team to be more careful." Or: "Delete the bad messages from the topic." (Restarts crash on the same record again; Kafka cannot delete single records; and "be careful" is not a fix.)

Strong answer, in two halves. Recover: roll back the producer first so no more bad records are written. Find the first bad offset per partition (deserialization errors in consumer logs, or the new schema ID in the message bytes). For each crashed consumer, either deploy a tolerant version that skips or routes the bad range to a DLQ, or reset its offsets past the bad range and re-process those records later from the DLQ after fixing them. Prevent: put the topic under Schema Registry with BACKWARD_TRANSITIVE, register schemas from CI with a compatibility check that blocks the merge, set auto.register.schemas=false in apps, and alert on deserialization error rates. Stop the bleeding, then make the mistake impossible, blameless and concrete.

Likely follow-ups
  • Can you delete the bad records from Kafka? (Not individually; you can skip them, or use kafka-delete-records.sh to truncate a partition's start, which is rarely right.)
  • How would you find who registered the schema? (Registry audit logs, git history of the schema.)
  • Which compatibility mode would have blocked this change, and why? (Depends on the change: removing a field without a default fails FORWARD; adding one without a default fails BACKWARD.)

Say it in 60 seconds

"Kafka only stores bytes, so the contract between teams has to live somewhere else. Schema Registry stores versioned Avro, Protobuf or JSON schemas per subject, usually topic-value, gives each a unique ID, and checks compatibility on registration. Each message starts with a magic byte and the 4-byte schema ID, so consumers fetch the schema once and cache it. I pick BACKWARD or BACKWARD_TRANSITIVE so new consumers can read all retained data, add fields only with defaults, register from CI, and ship true breaking changes as a new topic with a migration."
