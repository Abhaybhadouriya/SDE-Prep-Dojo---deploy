Shipping a breaking change safely

Sometimes the change truly cannot be compatible: a field's meaning changes, money moves from rupees as int to paise as long plus a currency code, or the whole event is redesigned. Do not set the subject to NONE and hope. Treat it like an API v2:

  1. Today. All producers write orders with the v1 schema; all consumers read it.
  2. New topic. Create orders.v2 with its own subject and the new schema. Either the producer writes both topics for a while, or a small stream job reads v1 and writes translated v2 records (which avoids a dual write in the app).
  3. Migrate consumers one by one. Each team moves to orders.v2 at its own pace, starting from an offset that matches where it was on v1 (usually by time). Nothing is forced on a Friday.
  4. Retire v1. When the last consumer has moved and lag on v1 is zero, stop writing v1 and let retention delete it. Document the change in the topic's catalogue entry.

From your world

This is the same playbook as migrating a routing protocol or changing an on-the-wire format between routers: run old and new side by side (like dual-stack IPv4/IPv6 or ships-in-the-night IGP migration), move neighbours one at a time, and remove the old one only when nothing uses it. Capability negotiation in BGP is the "compatibility check" that stops a peer from sending what the other side cannot parse.

Data contracts in practice

  1. Schemas live in git next to the producer's code, reviewed like an API.
  2. CI runs the compatibility check against the real registry (or uses the Maven/Gradle plug-ins) and fails the build on a breaking change.
  3. CI registers the schema on merge; applications run with auto.register.schemas=false so a laptop cannot register junk in production.
  4. Choose a transitive mode for long-retention or compacted topics that new consumers will read from the start.
  5. Protect the registry with authentication and ACLs. Anyone who can register schemas can block producers or change what consumers decode.
