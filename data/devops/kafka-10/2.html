How Schema Registry works

Schema Registry is a separate small REST service (Confluent's is the best known; Apicurio, Karapace and AWS Glue Schema Registry are alternatives). It stores its own data in a compacted Kafka topic called _schemas, so it is stateless and easy to run as a few replicas. Clients talk to it over HTTP, by default on port 8081. The magic happens inside the serializer and deserializer libraries in your producers and consumers. Step through one message:

  1. Producer asks. On the first send with a given schema, the serializer asks the registry about it under the subject orders-value. With auto.register.schemas=true (the client default) it registers it; in production you usually register from CI and set this to false.
  2. Registry checks and answers. The registry runs the compatibility check against the subject's existing versions. If it passes, the schema gets a globally unique ID, say 7. The same schema text always gets the same ID. The producer caches the ID, so this HTTP call happens once, not per message.
  3. Write the 5-byte header. Each message value is: magic byte 0, then the 4-byte schema ID in big-endian, then the binary payload. The full schema is never in the message.
  4. Consumer reads the ID. The deserializer peels off the 5 bytes and, if it has not seen ID 7 before, fetches it from the registry.
  5. Fetch once, cache forever. Schema IDs are immutable, so the consumer can cache ID 7 for its lifetime. A registry outage does not stop clients that already have their schemas cached.
  6. Decode. The deserializer decodes the bytes with the writer's schema (ID 7) and, for Avro, resolves them into the reader's own schema version. That resolution is what makes evolution work.

The wire format, byte by byte

$ kcat -b localhost:9092 -t orders -C -c 1 -f '%s' | xxd | head -1
00000000: 0000 0000 0754 0841 7368 61e6 07         .....T.Asha..

There it is: 00 magic, 00 00 00 07 schema ID, then the same 8 Avro bytes we counted by hand. (If your example also has the coupon field, a null union adds one more byte, 00, for the union branch.)

From your world

The 5-byte header is your EtherType + version field. The receiver reads a tiny fixed header to decide how to parse everything after it, and the meaning of each value is held in a shared registry (IANA there, Schema Registry here). Nobody puts the full protocol spec in every frame.

Subjects: where versions are grouped

A subject is a named list of schema versions, and compatibility is checked within one subject. Which subject a message's schema belongs to is decided by the subject name strategy:

  • TopicNameStrategy (default): subject = <topic>-key or <topic>-value. One event type per topic. Simple and the most common.
  • RecordNameStrategy: subject = the record's full name, e.g. com.shop.events.Order. The same type can appear in many topics.
  • TopicRecordNameStrategy: subject = <topic>-<record name>. Lets one topic carry several event types (OrderPlaced, OrderPaid) while still keeping ordering per order key. Useful for event-sourced aggregates.

Talking to the registry with curl

SR=http://localhost:8081
CT='Content-Type: application/vnd.schemaregistry.v1+json'

# Register version 1 of the value schema for topic "orders"
curl -s -X POST -H "$CT" $SR/subjects/orders-value/versions \
  --data '{"schema": "{\"type\":\"record\",\"name\":\"Order\",\"namespace\":\"com.shop.events\",\"fields\":[{\"name\":\"id\",\"type\":\"long\"},{\"name\":\"name\",\"type\":\"string\"},{\"name\":\"amount\",\"type\":\"int\"}]}"}'

curl -s $SR/subjects
curl -s $SR/subjects/orders-value/versions
curl -s $SR/config                                  # global compatibility level
{"id":7}
["orders-value"]
[1]
{"compatibilityLevel":"BACKWARD"}

Before you ship a change, ask the registry whether it would be accepted. This is the command to put in CI:

# Proposed v2: rename amount -> total (a breaking change)
curl -s -X POST -H "$CT" $SR/compatibility/subjects/orders-value/versions/latest?verbose=true \
  --data '{"schema": "{\"type\":\"record\",\"name\":\"Order\",\"namespace\":\"com.shop.events\",\"fields\":[{\"name\":\"id\",\"type\":\"long\"},{\"name\":\"name\",\"type\":\"string\"},{\"name\":\"total\",\"type\":\"int\"}]}"}'
{"is_compatible":false,"messages":["... READER_FIELD_MISSING_DEFAULT_VALUE, location:/fields/2, message:total, ..."]}

The new reader expects a field total that old messages do not have, and it has no default, so it could not read old data. Add "default": 0 and keep amount (or use an Avro alias) and the check passes. You can also set the mode per subject with curl -X PUT -H "$CT" $SR/config/orders-value --data '{"compatibility":"FULL"}'.

Producer and consumer config

Properties p = new Properties();
p.put("bootstrap.servers", "kafka:9092");
p.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "io.confluent.kafka.serializers.KafkaAvroSerializer");
p.put("schema.registry.url", "http://schema-registry:8081");
p.put("auto.register.schemas", "false");   // CI registers schemas; apps only look them up
p.put("use.latest.version", "true");       // serialize with the latest registered version

// consumer side
c.put("value.deserializer", "io.confluent.kafka.serializers.KafkaAvroDeserializer");
c.put("schema.registry.url", "http://schema-registry:8081");
c.put("specific.avro.reader", "true");     // decode into generated Order classes
from confluent_kafka import Producer
from confluent_kafka.schema_registry import SchemaRegistryClient
from confluent_kafka.schema_registry.avro import AvroSerializer
from confluent_kafka.serialization import SerializationContext, MessageField

schema_str = open("order.avsc").read()
sr = SchemaRegistryClient({"url": "http://localhost:8081"})
# Same rule as the Java client: CI registers schemas, the app only looks them up.
# (For a quick lab you can drop conf=... and let it auto-register, never in production.)
to_avro = AvroSerializer(sr, schema_str,
                         conf={"auto.register.schemas": False, "use.latest.version": True})

p = Producer({"bootstrap.servers": "localhost:9092"})
order = {"id": 42, "name": "Asha", "amount": 499, "coupon": None}
p.produce("orders", key="42",
          value=to_avro(order, SerializationContext("orders", MessageField.VALUE)))
p.flush()

Kafka Connect uses the same idea through converters: set value.converter=io.confluent.connect.avro.AvroConverter and value.converter.schema.registry.url=..., and every Debezium change event is registered and sent as Avro. See Connect & Streams.
