The story

Explain like I'm 5

Imagine a toy shop with a big window. Kids push order slips through a slot in the window. Behind the window there is a long notebook. A helper copies every slip onto the next empty line of the notebook and says "Got it!" to the kid. That is all the window helper does, so the line of kids moves fast.

Behind the helper sit more helpers. One reads the notebook and writes the price next to each slip. If a slip says "a purple dragon" and the shop has no purple dragons, she does not get stuck. She puts that slip in a "confused" box and moves on. Another helper copies the priced slips into the shop's big ledger book. A third helper counts how much money the shop made every minute and writes it on a board on the wall.

Nobody waits for anybody. If the ledger helper goes for a snack, the notebook just keeps growing. When she comes back she starts from the line where she left her bookmark. Nothing is lost.

That toy shop is ShopStream, the project you will build in this track. The window is an HTTP API (a program that answers web requests). The long notebook is Kafka (a system that stores events in order, on disk, and lets many programs read them). The helpers are small programs called services. The "confused" box is a dead-letter queue. The ledger is a Postgres database. The board on the wall is a Grafana dashboard.

Everything runs on your own laptop inside Docker containers (sealed boxes that hold one program each), started with a single command. Later you move the same programs onto Kubernetes (a system that runs containers across many machines). The full code is in this site, in pipeline/code. Nothing on these pages is pretend: every command, file name and setting comes from that folder.

From your world

Think of ShopStream as a packet pipeline on a line card. The order-api is the ingress port: it classifies the request, stamps it, and puts it on a ring. Kafka is a set of huge, persistent rings (one per partition) that never wrap and overwrite. The enricher is a processing stage that reads the ring, looks things up (like a FIB lookup), and writes to the next ring. The dead-letter topic is the punt or drop queue for packets that cannot be forwarded, with a counter you can inspect. Consumer lag is simply ring occupancy: how far the reader's index is behind the writer's index. Where this breaks: Kafka rings live on disk across three machines and keep data for days, so a slow reader never causes a drop, it only falls behind.
