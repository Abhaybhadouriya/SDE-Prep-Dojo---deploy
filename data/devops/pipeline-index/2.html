Life of one order, step by step

Click Next or Play. Each step names the exact program doing the work, because "the system handles it" is not an answer.

  1. Request arrives. order-api (a FastAPI program) checks the JSON: a customer id and at least one item with a quantity from 1 to 100. It adds an order_id (a random UUID) and a created_at time.
  2. Written to the log. The API's Kafka producer sends the event with key C-42. The client library hashes the key to pick a partition (here, for example, partition 3), so every order of customer C-42 lands in the same partition, in order.
  3. Acknowledged. Only after every in-sync copy has the event (all three normally, and never fewer than two, because min.insync.replicas=2) does the API answer 202 ACCEPTED with the partition and offset. 202 means "accepted, work continues in the background".
  4. Enriched. The enricher consumer group reads the event, looks up prices (Postgres table products), computes the total, and writes orders.enriched inside a Kafka transaction.
  5. Stored. postgres-sink reads orders.enriched and does an upsert (insert, or update if the order id already exists) into the orders table. Only then does it save its bookmark.
  6. Counted. analytics reads the same topic with its own bookmark and adds the total to the current one-minute window. When the minute is over it publishes the number for Grafana.
