Quick quiz

Why does the order-api answer 202 instead of 201 Created?

  1. 202 is faster to send
  2. The order is accepted into the log; the rest of the work happens later in other services
  3. Kafka only understands 202
202 means "accepted for processing". The order is durable in Kafka, but pricing and storage finish asynchronously.

A product id does not exist in the catalog. Where does that order end up?

  1. orders.retry, forever
  2. It blocks the partition until a human fixes it
  3. orders.dlq, the dead-letter topic
Retrying will never fix an unknown product, so it is a "poison" message and goes straight to the DLQ with error headers. The partition keeps flowing.

postgres-sink is paused for five minutes. What happens to analytics?

  1. Nothing; it reads with its own consumer group and offsets
  2. It also stops
  3. It reads the sink's messages twice
Different consumer groups are independent. The sink just builds lag and catches up later.

Why are all orders of customer C-42 in the same partition?

  1. Kafka puts everything in partition 0
  2. The key is the customer id, and the same key always hashes to the same partition
  3. C-42 is a VIP customer
Kafka keeps order only inside a partition, and the default partitioner maps a key to a partition by hashing it.

Which of these is a real cost of the event pipeline design?

  1. The API gets slower
  2. Data can never be replayed
  3. The final result is visible a little later, and you must handle duplicates and retries
Event pipelines trade immediate consistency for decoupling. The API gets faster, and replay becomes possible.
