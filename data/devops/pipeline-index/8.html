Interview warm-up

Three questions this project prepares you for. Deeper questions live on each page and in the Kafka interview bank.

Walk me through an order pipeline you would build with Kafka.

"The order API validates the request and writes one OrderCreated event to a topic called orders.created, keyed by customer id so one customer's orders stay in order. It uses an idempotent producer with acks=all, and the topic has replication factor 3 with min.insync.replicas=2, so one broker can die without losing an accepted order. The API returns 202, meaning accepted. An enricher consumer group validates and prices orders and writes to orders.enriched, using a Kafka transaction so the outputs and its read position commit together. Temporary failures go to a retry topic with backoff; bad records go to a dead-letter topic. Two independent groups read the enriched topic: a Postgres sink that upserts on order id, and an analytics job that sums revenue per minute. I watch consumer lag, under-replicated partitions and DLQ arrivals."

How to answer

Follow the data left to right, and for every hop say one sentence about what guarantee it gives. Draw at most six boxes. Stop and ask "should I go deeper on any hop?" after two minutes.

Likely follow-ups
  • Why key by customer and not by order id?
  • What happens if Postgres is down for ten minutes?
  • How do you avoid charging or storing an order twice?
Why put Kafka in the middle instead of having the API write straight to the database?

"Three reasons. First, decoupling: the API only needs Kafka to be up, not the pricing lookup, the database and analytics all at once. Second, buffering: during a sale spike the log absorbs the burst and the consumers catch up at their own pace, instead of the database falling over. Third, fan-out and replay: many independent readers can use the same events, and I can re-read history after a bug. The cost is eventual consistency and more operational work, so for a small internal tool I would just write to the database."

How to answer

Give the benefits as a numbered list, then volunteer the cost and the case where you would not do it. Saying when not to use Kafka is a strong maturity signal.

Likely follow-ups
  • The customer wants to see the order total immediately. Now what?
  • Would SQS or RabbitMQ work here instead?
How would you test a pipeline like this before production?

"Three layers. Unit tests for the pure business logic (the enrich() function takes bytes and returns a dict, so it needs no Kafka). Integration tests with a real broker in a container, which is exactly what the ShopStream compose file gives you. And failure drills: kill a broker, pause a consumer, inject a poison message, force a rebalance, and check the numbers in Postgres still match what was sent. Load tests with a generator that can create a hot key and bad records."

How to answer

Split by layer, and make the point that most Kafka bugs show up only under failure, so failure drills are part of testing, not an afterthought.

Likely follow-ups
  • How do you check that no order was lost or duplicated?
  • How would you run these drills in a staging Kubernetes cluster?
