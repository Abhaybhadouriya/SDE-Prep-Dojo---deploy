CPU and memory limits (cgroups)

By default a container may use all the CPU and memory of the host. One leaky container can starve everything else. Limits fix that, and they are just numbers Docker writes into the container's cgroup (control group, the kernel's resource-accounting tree).

docker run -d --name api --memory 256m --memory-swap 256m --cpus 1.5 --pids-limit 200 myapi:1.0
# --memory-swap equal to --memory means "no extra swap"
# --pids-limit stops a fork bomb from eating the PID table
docker update --memory 512m --memory-swap 512m api   # change limits on a running container
$ CID=$(docker inspect api --format '{{.Id}}')
$ cat /sys/fs/cgroup/system.slice/docker-$CID.scope/memory.max
268435456
$ cat /sys/fs/cgroup/system.slice/docker-$CID.scope/cpu.max
150000 100000

The path above is for cgroup v2 with the systemd cgroup driver (the default on current Ubuntu, Debian and Fedora). On other setups it may be /sys/fs/cgroup/docker/<id>/.

From your world

cpu.max is CFS bandwidth control: a quota per period, which behaves like a token-bucket policer on an interface. Spend your tokens early in the period and you are held until the bucket refills, which shows up as latency spikes ("CPU throttling"), not drops. memory.max triggers the same OOM killer you know from the kernel, just scoped to one cgroup instead of the whole box. Where it breaks: cgroups do not isolate shared things like the last-level CPU cache, NIC queues or kernel locks, so a noisy neighbour can still hurt you.

Java and Node trap: older runtimes sized their heap from the host's RAM, not the container limit, and got OOM-killed. Modern JVMs are container-aware since JDK 10, and cgroup v2-aware since JDK 15 (backported to 11.0.16 and 8u372); on older builds running on a cgroup v2 host the JVM sees the host's RAM; still set -XX:MaxRAMPercentage (or an explicit -Xmx) below the limit, because the JVM needs memory outside the heap too (threads, metaspace, buffers).
