Stopping: SIGTERM, 10 seconds, SIGKILL

There are two ways to end a container, and the difference matters a lot in production.

  • docker stop web politely sends SIGTERM (or the image's STOPSIGNAL) to PID 1, waits up to 10 seconds (change with -t), then sends SIGKILL if it is still alive.
  • docker kill web sends SIGKILL right away (or another signal with -s). No cleanup, no chance to finish requests.

Reading exit codes like a pro

Must know. The exit-code table below shows up in almost every container incident and in most Docker interviews. Learn 0, 1, 125, 126, 127, 137 and 143 by heart.

When a process dies from a signal, the shell convention is 128 + signal number. Docker reports the same number. Memorise this small table; it shows up in incidents and interviews.

Exit codeMeaningTypical cause
0Clean exitJob finished, or app handled SIGTERM and exited cleanly
1 (or other small number)App errorUnhandled exception, bad config, cannot reach DB
125Docker itself failedBad flag, port already in use, daemon error
126Command cannot be invokedEntrypoint not executable (missing chmod +x)
127Command not foundTypo, or binary not in this image (common with slim images)
137128 + 9 = SIGKILLOOM killer, docker kill, or docker stop timeout
143128 + 15 = SIGTERMStopped by SIGTERM and the app did not convert it to exit 0
 
$ docker run --name boom --memory 64m python:3.12-slim \
    python -c "x = bytearray(200*1024*1024)"
$ echo $?
137
$ docker inspect boom --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
exit=137 oom=true

The script tried to grab 200 MiB inside a 64 MiB box, so the kernel's OOM killer (the kernel code that picks a process to kill when memory runs out) sent SIGKILL. OOMKilled=true is your proof. If 137 shows oom=false, look for a docker kill or a stop timeout instead (docker events tells you).
