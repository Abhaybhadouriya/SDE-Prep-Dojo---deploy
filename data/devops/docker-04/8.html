Restart policies: who brings it back?

Good to know. For SDE-1, know the four policies in the table. The restart loop and backoff below are for SDE-2, SRE and platform roles. Cleanup (next section) is daily operations: skim it now, come back when a disk fills up.

If your app crashes at 3 a.m., dockerd can restart it for you. You choose the rule with --restart.

PolicyRestarts on crash?After dockerd / host reboot?Use for
no (default)NoNoOne-off jobs, experiments
on-failure[:N]Only on non-zero exit, max N triesNo (on-failure never restarts on a daemon restart)Batch jobs that may fail transiently
alwaysYesYes, even if you had stopped it manuallyServices that must always be up
unless-stoppedYesYes, unless you stopped it by handMost local services (the usual pick)

For services that must survive a reboot, use unless-stopped or always; on-failure only reacts to crashes while the daemon keeps running. Docker waits a little before each restart and doubles the wait every time (starting at 100 ms), so a crash loop does not hammer the host. A manual docker stop is always respected while the daemon is running.

The restart loop, step by step

  1. Running. The container's main process is alive. dockerd is watching it through containerd's events.
  2. It crashes. The process exits with code 1. The container is now exited, and dockerd gets the exit event with the code.
  3. Policy check. dockerd looks at --restart. With no it stays exited. With on-failure:N it restarts only if the code is not 0 and fewer than N retries have been used. With always and unless-stopped it always restarts.
  4. Backoff. The state is restarting. Docker waits 100 ms before the first restart and doubles the delay after each crash, so a broken container settles into slow retries instead of a busy loop.
  5. Start again. The same container (same writable layer, same name) starts again and RestartCount goes up. If it then stays up for at least 10 seconds, the delay resets to 100 ms.
  6. Two special exits. A docker stop you type is never undone while the daemon runs. When dockerd itself restarts (or the host reboots), always and unless-stopped containers are started again (unless-stopped skips ones you stopped by hand); on-failure and no are not.

Try a crash loop that gives up after three tries:

$ docker run -d --name flaky --restart on-failure:3 alpine:3.24 sh -c 'echo boom; exit 1'
$ docker logs flaky
boom
boom
boom
boom
$ docker inspect -f 'status={{.State.Status}} restarts={{.RestartCount}} exit={{.State.ExitCode}}' flaky
status=exited restarts=3 exit=1

One first run plus three restarts gives four "boom" lines. Wait a few seconds after docker run for the backoff to finish.

Limits of restart policies: they only restart on this one host, they do not notice an app that is alive but stuck (no health-based restarts in plain Docker), and if the host dies nothing moves the container elsewhere. That gap is exactly why Kubernetes exists: its controllers recreate pods on healthy nodes and liveness probes restart stuck ones.
