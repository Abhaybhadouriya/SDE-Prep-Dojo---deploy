Interview questions

A container keeps restarting with exit code 137. How do you debug it?

137 is 128 + 9, so the main process received SIGKILL. The usual cause is the kernel OOM killer because the container passed its memory limit; the other causes are a manual docker kill or a docker stop that hit its 10-second timeout. I would run docker inspect --format '{{.State.OOMKilled}}': if true, it is memory. Then docker stats to watch usage climb, and check whether the runtime's heap (JVM -Xmx, Node --max-old-space-size) is bigger than the limit. The fix is either a real leak fix, a heap setting below the limit, or a bigger limit if the workload genuinely needs it. On Kubernetes the same thing shows up as OOMKilled in kubectl describe pod and a CrashLoopBackOff.

How to answer

Decode the number first (shows you know signals), list the two or three causes, give the one command that tells them apart, then the fix and how you would prevent it (limits plus a memory alert).

Likely follow-ups
  • What is the difference between hitting a CPU limit and a memory limit? (throttling vs kill)
  • Why can a JVM with -Xmx equal to the limit still be killed? (off-heap memory)
  • What would 143 mean instead?
docker stop takes exactly 10 seconds every time. Why, and how do you fix it?

Ten seconds is the default grace period, so the process is ignoring SIGTERM and is being SIGKILLed at the deadline. Two common reasons: the Dockerfile uses shell form, so /bin/sh is PID 1 and does not forward the signal; or the app is PID 1 and never installed a SIGTERM handler, and the kernel does not apply default signal actions to PID 1 of a namespace. Fix: exec-form CMD/ENTRYPOINT, a SIGTERM handler that drains and exits, and --init (tini) if the app spawns children. This matters because SIGKILL means in-flight requests are cut and buffers are not flushed.

How to answer

Spot the "exactly 10 s" clue out loud, explain PID 1 semantics in one sentence, then give the three fixes. Connect to Kubernetes graceful shutdown for bonus points.

Likely follow-ups
  • What is a zombie process and who reaps it in a container?
  • How does Kubernetes shut down a pod? (preStop hook, SIGTERM, grace period, SIGKILL)
What is the difference between docker run, docker start and docker exec?

docker run creates a brand-new container from an image and starts it. docker start starts an existing, stopped container again, with its old writable layer. docker exec runs an extra process inside a container that is already running, by joining its namespaces. So run = new container, start = same container again, exec = new process in a running container.

How to answer

One line each, then one practical example: "to debug I exec a shell; to re-run a finished job I start it; to deploy a new version I run a new container from the new image".

Likely follow-ups
  • What happens to files you changed with exec when the container is removed?
  • What does attach do, and why is it risky?
How do you limit a container's CPU and memory, and what happens at the limit?

--memory and --cpus become cgroup v2 settings: memory.max and cpu.max (a quota per 100 ms period). Memory is a hard limit, so going over it gets the process OOM-killed (exit 137). CPU is a rate limit, so going over the quota throttles the process until the next period: it gets slower and latency rises, but it is not killed. I also set --pids-limit against fork bombs. In Kubernetes these become requests and limits, and the scheduler uses requests to place pods.

How to answer

Name the flag, the kernel file, and the behaviour at the limit for each resource. The "kill vs throttle" contrast is what they are listening for.

Likely follow-ups
  • How would you detect CPU throttling? (cpu.stat nr_throttled, container metrics)
  • Do cgroups stop noisy neighbours completely? (no: caches, NIC queues, kernel locks are shared)
If dockerd crashes, do running containers die?

Not necessarily. Each container's parent is a containerd-shim process, not dockerd. With live-restore enabled in daemon.json, containers keep running while dockerd is restarted or upgraded, and dockerd reconnects to them when it comes back. Without live-restore, Docker stops containers when the daemon shuts down. While the daemon is down you cannot manage them (no new containers, no logs via the API). This split between a management plane and a per-container supervisor is the same idea as the kubelet and container runtime on a Kubernetes node.

How to answer

Draw CLI → dockerd → containerd → shim → process, point at the shim, then mention live-restore and its limit.

Likely follow-ups
  • Why are there three daemons/programs (dockerd, containerd, runc)?
  • What happens to Kubernetes pods if the control plane is down?

Scenario: the build server's disk is 100% full

CI jobs on a shared build host start failing with "no space left on device". The host only runs Docker builds and a few test containers.

Weak answer: "Run docker system prune -a --volumes and move on."

Strong answer: First measure: docker system df and du -sh /var/lib/docker/* to see if it is images, build cache, volumes or container logs. Typical culprits are unrotated json-file logs of a chatty test container, old images from every build, and BuildKit cache. Clean safely (stopped containers, dangling images, build cache older than a day with docker builder prune --filter until=24h), avoid deleting volumes blindly. Then prevent: log rotation in daemon.json, a scheduled prune job, --rm on test containers, and a disk-usage alert at 80%.

Likely follow-ups
  • Why does deleting a big file in a later Dockerfile layer not free space?
  • How would you size the build cache?

60-second answer - "Walk me through running and operating a container": "docker run is create plus start. The CLI calls dockerd, which pulls missing layers, then containerd prepares the root filesystem and starts a shim, and runc creates the namespaces and the cgroup and execs the entrypoint, which becomes PID 1 in the container. I watch it with logs, stats and inspect, and debug inside with exec. I always set memory and CPU limits; memory over the limit is an OOM kill with exit 137, CPU over the limit is throttling. docker stop sends SIGTERM and SIGKILLs after 10 seconds, so the app must run in exec form and handle SIGTERM. Restart policies handle crashes on one host; for health checks, rescheduling and multiple hosts I move to Kubernetes."
