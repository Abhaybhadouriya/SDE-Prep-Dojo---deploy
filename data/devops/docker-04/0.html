The story: a wind-up toy robot

Explain like I'm 5

You have a box of toy-robot kits (the image). You take one kit out and build a robot (the container). You wind it up and it walks (running). You can freeze it with your hand (paused), let go (running again), ask it nicely to sit down (stop), or just pull out its battery (kill). When you are done, you put the robot in the bin (remove). The kit box is still on the shelf, so you can build another robot any time.

Each robot gets a small plate of snacks (memory). If it tries to eat more than its plate, a grown-up takes the robot away. That is the "out of memory" kill you will meet later.

On the previous pages you learned what a container is and how an image is built from a Dockerfile. This page is about day-to-day life with containers: the commands you type a hundred times a week, and what each one really does underneath.

Two words first. A container is a normal Linux process that the kernel fences in (it sees its own files, its own process list, its own network). The Docker CLI (the docker command) is only a remote control. It sends REST calls to a background program called dockerd (the Docker daemon, a program that runs in the background with no terminal), which does the real work with help from containerd and runc. You will see all three in the step-by-step below.

From your world

The robot "freeze" above is docker pause, and it maps to something you know: it is like sending SIGSTOP to a whole process group at once. Docker does not send a signal at all. It writes to the container's cgroup freezer (a cgroup, or control group, is the kernel's resource-accounting tree; on cgroup v2 the file cgroup.freeze becomes 1), and the scheduler simply stops running every process in that cgroup. docker unpause writes 0 and they continue exactly where they were, with memory and open sockets intact. Where the analogy breaks: a stopped process can be noticed (its parent gets a waitpid report, and a SIGCONT handler runs on resume); the freezer is invisible to the frozen processes, they cannot catch or block it. Their TCP peers still notice the silence and may time out.

(The "image is like an ELF binary, a container is like the process" mapping is on page 01.)
