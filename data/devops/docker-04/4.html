Looking inside a running container

Debugging containers uses six commands over and over. Learn them as a set.

docker logs prints what the main process wrote to stdout and stderr. Docker does not read log files inside the container, which is why images like nginx link their log files to /dev/stdout.

docker logs web              # everything so far
docker logs -f --tail 20 web # follow, start from last 20 lines
docker logs --since 10m web  # only the last 10 minutes
$ docker logs --tail 2 web
172.17.0.1 - - [23/Nov/2026:10:05:11 +0000] "GET / HTTP/1.1" 200 615 "-" "curl/8.5.0" "-"
172.17.0.1 - - [23/Nov/2026:10:05:14 +0000] "GET /favicon.ico HTTP/1.1" 404 153 "-" "curl/8.5.0" "-"

docker exec starts a new extra process inside the namespaces of a running container. It does not restart anything. Under the hood it uses the setns() system call to join the existing namespaces.

docker exec -it web sh       # a shell inside the running container
docker exec web nginx -t     # run one command and come back
$ docker exec web nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

docker inspect dumps the full JSON truth about a container: config, state, mounts, IP, exit code, whether the OOM killer hit it. Use --format with Go templates to pick one field.

docker inspect web --format '{{.State.Status}} pid={{.State.Pid}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
$ docker inspect web --format '{{.State.Status}} pid={{.State.Pid}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
running pid=4142 exit=0 oom=false
$ docker inspect web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
172.17.0.2

docker stats is top for containers. It reads the numbers straight from each container's cgroup files. web was started without --memory, so its LIMIT column shows the host's (here the Docker VM's) total RAM.

$ docker stats --no-stream
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O         BLOCK I/O   PIDS
3f2a9c1b7d4e   web    0.00%   7.9MiB / 7.6GiB     0.10%   1.2kB / 2.4kB   0B / 4.1kB  9
docker cp web:/etc/nginx/nginx.conf ./nginx.conf   # copy a file out
docker cp ./index.html web:/usr/share/nginx/html/    # copy a file in (lost when the container is removed!)
docker events --filter container=web                 # live stream: start, die, oom, kill...
$ docker events --filter container=web
2026-11-23T10:09:01.512 container kill 3f2a9c1b7d4e (image=nginx:1.30, name=web, signal=15)
2026-11-23T10:09:01.640 container die 3f2a9c1b7d4e (exitCode=0, image=nginx:1.30, name=web)
2026-11-23T10:09:01.702 container stop 3f2a9c1b7d4e (image=nginx:1.30, name=web)

Where do logs physically go?

Production trap: the default json-file log driver never rotates by default, so a chatty container can fill the host disk. Set rotation in /etc/docker/daemon.json (applies to new containers):

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

Or use the local driver, which rotates and compresses by default.
