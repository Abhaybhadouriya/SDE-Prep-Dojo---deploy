PID 1 in practice: spot a slow stop and fix it

Inside a container your app is usually PID 1, and Linux gives PID 1 no default signal actions. Why that happens, why shell-form CMD hides your app behind /bin/sh, and the signal diagram are all on page 03 (see 03 for why). This section is the operational side: how you notice the problem on a running host, how you read the result, and the three knobs you have.

  1. Spot it. time docker stop NAME takes almost exactly the timeout (10 s by default). That means PID 1 ignored SIGTERM and was SIGKILLed at the deadline.
  2. Read the result. docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}': 0 means the app handled SIGTERM and exited cleanly; 143 means it died from SIGTERM without a handler (fine, but nothing was drained); 137 with OOMKilled=false after a docker stop means the stop timed out.
  3. Knob 1: more time. docker stop -t 30 NAME for one stop, or docker run --stop-timeout 30 to change the default for that container. Use it for apps that need longer to drain, not to hide a missing handler.
  4. Knob 2: a different signal. docker run --stop-signal SIGQUIT or STOPSIGNAL in the Dockerfile, for apps whose graceful shutdown signal is not SIGTERM. The official nginx image does this: it sets STOPSIGNAL SIGQUIT, nginx's "finish current requests, then quit" signal.
  5. Knob 3: an init. docker run --init starts Docker's bundled tini as PID 1. tini forwards signals to your app (which is now an ordinary process, so default actions apply again) and reaps zombies.

Lab: measure it

A Python script with no signal handler is the classic stubborn PID 1. Run it twice, with and without --init:

# 1. stubborn: python is PID 1 and has no SIGTERM handler
docker run -d --name stubborn python:3.12-slim python -c "import time; time.sleep(1000)"
time docker stop stubborn
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' stubborn

# 2. same program, tini as PID 1
docker run -d --init --name polite python:3.12-slim python -c "import time; time.sleep(1000)"
time docker stop polite
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' polite

# 3. see the signals Docker sent
docker events --since 5m --filter container=stubborn --filter event=kill
$ time docker stop stubborn
stubborn
real    0m10.3s
$ docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' stubborn
exit=137 oom=false
$ time docker stop polite
polite
real    0m0.4s
$ docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}' polite
exit=143 oom=false
$ docker events --since 5m --filter container=stubborn --filter event=kill
2026-11-23T10:21:04.118 container kill 9b1e... (image=python:3.12-slim, name=stubborn, signal=15)
2026-11-23T10:21:14.131 container kill 9b1e... (image=python:3.12-slim, name=stubborn, signal=9)

Your times and IDs will differ. Read the events: signal 15 (SIGTERM) at t = 0, signal 9 (SIGKILL) ten seconds later. With --init, python is no longer PID 1, so SIGTERM's default action (die) works, and tini reports 128 + 15 = 143. To get 0, add a SIGTERM handler in the app (example on page 03).

Check what PID 1 really is

$ docker exec polite cat /proc/1/comm
docker-init
$ docker top polite -o pid,comm
PID     COMMAND
23817   docker-init
23841   python

python:3.12-slim does not ship ps (the procps package), so we read /proc/1/comm directly, or ask the host with docker top (which shows host PIDs). If PID 1 is sh, your CMD is in shell form: fix the Dockerfile (page 03).

The same rule matters even more on Kubernetes, where the grace period is terminationGracePeriodSeconds (30 s by default) and a preStop hook can run first. That production angle is on page 09 and Pods.
