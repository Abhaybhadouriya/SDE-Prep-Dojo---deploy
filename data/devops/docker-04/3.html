What actually happens on docker run (recap) and what each control command touches

Recap in two lines. The chain is CLI → dockerd → containerd → shim → runc → your process. Page 01 steps through it once, and page 08 opens every box, including why the shim lets the daemon restart without killing containers.

One detail worth getting right: runc makes the namespaces (joining the network namespace that dockerd's networking code, libnetwork, has already prepared with the veth inside), creates the cgroup and writes your limits, sets up mounts, drops capabilities, applies seccomp, then calls execve. runc does not configure the network itself.

What this page cares about is the operations side: when you type a control command, which part of the kernel does it actually touch? This picture answers that for the five commands you will use most.

$ ps -ef --forest | grep -A2 containerd-shim | head -n 3
root  4120     1  0 10:02 ?  00:00:00 /usr/bin/containerd-shim-runc-v2 -namespace moby -id 3f2a9c1b7d4e...
root  4142  4120  0 10:02 ?  00:00:00  \_ nginx: master process nginx -g daemon off;
101   4190  4142  0 10:02 ?  00:00:00      \_ nginx: worker process

$ docker top web
UID   PID    PPID   C   STIME   TTY   TIME       CMD
root  4142   4120   0   10:02   ?     00:00:00   nginx: master process nginx -g daemon off;
101   4190   4142   0   10:02   ?     00:00:00   nginx: worker process

You can see the result from the host. Look at that: nginx is a child of the shim, and it has a normal host PID (4142). Inside the container the same process believes it is PID 1. Same process, two numbers, because of the PID namespace. The deep version of this (clone flags, cgroup files, overlay mounts) is on Internals. Because the shim, not dockerd, is the parent, a daemon restart with live-restore leaves containers running; the full explanation (and the router non-stop forwarding comparison) is on page 08.
