Production: many VPCs, flow logs and cost traps

Good to know (SDE-2)

Connecting VPCs: peering vs Transit Gateway

VPC peering
  • Direct, private, no single bottleneck device, no hourly charge for the peering itself.
  • Works across accounts and regions.
  • Not transitive: if A peers with B and B with C, A cannot reach C through B. N VPCs need N(N-1)/2 peerings.
  • CIDRs must not overlap.
Transit Gateway
  • Hub-and-spoke regional router: each VPC/VPN/Direct Connect attaches once.
  • Its own route tables let you segment (prod cannot reach dev) and centralise egress or inspection.
  • Charged per attachment hour and per GB processed.
  • CIDRs still must not overlap for routed traffic.

Typical large setups (multi-account AWS Organizations at Amazon, Flipkart or Atlassian scale) use a Transit Gateway per region, a central "egress VPC" with shared NAT gateways and a firewall, and IPAM to hand out non-overlapping /16s per account.

See every flow: VPC Flow Logs

Flow logs record accepted and rejected flows per ENI, subnet or VPC to CloudWatch Logs or S3: NetFlow for the cloud, with 5-tuples, bytes, packets and ACCEPT/REJECT, no payloads.

2 123456789012 eni-0a1b2c3d 49.36.1.9 10.10.0.40 50122 443 6 12 4380 1732340000 1732340060 ACCEPT OK
2 123456789012 eni-0a1b2c3d 198.51.100.7 10.10.0.40 41234 22 6 1 60 1732340000 1732340060 REJECT OK

Fields: version, account, ENI, src, dst, src port, dst port, protocol (6 = TCP), packets, bytes, start, end, action, log status. The second line is someone scanning SSH and the security group rejecting it.

Where the money goes

Three line items surprise teams most: NAT data processing (fix: the free S3 gateway endpoint first), cross-AZ traffic billed per GB in each direction (fix: same-AZ NAT routes and zone-aware calls), and public IPv4 addresses billed per hour each. Interface endpoints also cost per AZ per hour, so create them only for services you call heavily.

Scenario: pods cannot pull images after a "cost clean-up"

Monday morning, new pods in one EKS node group are stuck in ImagePullBackOff. Old pods are fine. Over the weekend someone deleted "unused" NAT gateways to save money.
Weak answer: "Restart the nodes" or "the registry is down".
Strong answer: Image pulls go out to ECR over HTTPS (API + S3 for layers). Check the private subnet's route table: 0.0.0.0/0 now points to a deleted NAT gateway, shown as blackhole. Only AZs whose NAT was deleted are affected, which explains "one node group". Fix: recreate the NAT gateway and update the route, or better, add the S3 gateway endpoint plus ecr.api/ecr.dkr interface endpoints so image pulls never need NAT. Prevent it with Terraform-only changes and an alarm on blackhole routes.
Likely follow-ups
  • Why did the running pods keep working? (They already had their images cached on the node.)
  • How would you prove the route is the problem? (Route table State, VPC Reachability Analyzer, flow logs showing no traffic leaving.)
