CIDR planning: pick address ranges that never collide

Must know (SDE-1)

CIDR (Classless Inter-Domain Routing) writes a range as base/prefix. 10.0.0.0/16 means "the first 16 bits are fixed", so 32 - 16 = 16 free bits = 65,536 addresses. Each extra prefix bit halves the block: a /17 has 32,768, a /20 has 4,096, a /24 has 256.

Rule (from the AWS VPC docs)What it means for you
VPC IPv4 block: between /16 and /28Largest single block is 65,536 addresses; you can add more blocks later (secondary CIDRs).
Subnet block: between /16 and /28, inside the VPC range, no overlap with other subnetsSmallest subnet is 16 addresses, of which only 11 are usable.
5 addresses reserved in every subnetIn 10.0.0.0/24: .0 network, .1 VPC router, .2 Amazon DNS, .3 reserved for future use, .255 broadcast (not supported, still reserved). A /24 gives you 251 usable IPs.
Use RFC 1918 space (10/8, 172.16/12, 192.168/16)Also avoid 172.17.0.0/16: Docker's default bridge and some AWS services use it, and collisions are painful.
You cannot resize an existing CIDR blockPlan big enough on day one, or add a secondary block later (subnets never move between blocks).

Why overlapping ranges are a disaster

The moment two networks need to talk - VPC peering, a Transit Gateway (a regional hub router that many VPCs and VPNs attach to), a VPN to the office, or a merger with another company - their ranges must not overlap. A route says "send 10.0.0.0/16 over there". If both sides own 10.0.0.0/16, there is no way to say which "there" you mean. AWS simply refuses to create a peering between VPCs with overlapping CIDRs, and a Transit Gateway cannot route to two attachments with the same prefix. The fix afterwards is re-addressing (re-IP), which means rebuilding subnets and every service in them. Teams that learn this once never forget it.

Do the subnet maths yourself

You do not need a website. Python's standard library splits blocks exactly like a router engineer would:

import ipaddress
vpc = ipaddress.ip_network("10.10.0.0/16")
publics = list(vpc.subnets(new_prefix=20))[:3]                  # 10.10.0.0/20, 10.10.16.0/20, 10.10.32.0/20
privates = list(ipaddress.ip_network("10.10.64.0/18").subnets(new_prefix=20))[:3]
for s in publics + privates:
    print(s, "usable in AWS:", s.num_addresses - 5)

Kubernetes makes this urgent. On Amazon EKS the default CNI (the AWS VPC CNI) gives every pod a real VPC IP from the node's subnet. A node running 50 pods uses 50+ subnet addresses, plus a warm pool the CNI keeps ready. A /24 private subnet can run out after a handful of nodes. The EKS best-practices guide recommends sizing subnets for growth (eksctl creates /19 subnets by default), and, when RFC 1918 space runs short, adding a secondary CIDR from 100.64.0.0/10 just for pods ("custom networking") or moving to IPv6.

From your world

This is IPAM and route summarisation, exactly as in an ISP or enterprise WAN. Allocate hierarchically (company /8 -> region /12 -> environment /16 -> tier /19) so that each level can be summarised by one route at the next level up, and a Transit Gateway or on-prem router carries a few aggregates instead of hundreds of prefixes. AWS even has a managed IPAM service that hands out non-overlapping blocks per account. The 5 reserved addresses are like a router stealing the gateway, DNS and broadcast addresses from every LAN you plan.
