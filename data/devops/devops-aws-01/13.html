Quick quiz

What makes a subnet "public" in AWS?

  1. A "public" checkbox on the subnet
  2. A route 0.0.0.0/0 to an internet gateway in its route table
  3. Having a NAT gateway inside it
  4. Its CIDR block being outside RFC 1918
Publicness is only routing. The NAT gateway lives in a public subnet but does not make it public.

How many usable addresses does a /28 subnet have in AWS?

  1. 16
  2. 14
  3. 11
  4. 8
16 addresses minus the 5 AWS reserves (network, router, DNS, future, broadcast) = 11.

Your three private subnets (AZ a, b, c) all route to a single NAT gateway in AZ a. AZ a goes down. What happens?

  1. Private resources in AZ b and c lose outbound internet access
  2. AWS moves the NAT gateway to AZ b automatically
  3. Nothing, NAT gateways are regional
A zonal NAT gateway is redundant only within its AZ. Use one per AZ (or a regional NAT gateway).

Two VPCs both use 10.0.0.0/16. Which is true?

  1. Peering works if you enable DNS resolution
  2. A Transit Gateway will route between them automatically
  3. Only cross-region peering works
  4. You cannot peer them; overlapping CIDRs make routing ambiguous
AWS refuses peering between overlapping CIDRs. Options are re-IP or service-level connectivity such as PrivateLink or private NAT.

A route table has 0.0.0.0/0 -> nat-1 and an S3 gateway endpoint route (pl-xxxx -> vpce-1). Traffic to S3 in the same region goes...

  1. Through the NAT gateway, because 0.0.0.0/0 was added first
  2. Through the gateway endpoint, because the prefix list entries are more specific
  3. Randomly to either
Longest prefix match: the S3 prefixes are far more specific than /0.

Why does ip addr on an EC2 instance with a public IP show only 10.x.x.x?

  1. The public IP is hidden by the security group
  2. The kernel strips it
  3. The internet gateway does 1:1 NAT between the public and private IP; the instance never sees the public one
  4. Public IPs only exist on load balancers
The IGW translates addresses at the VPC edge, so the OS only knows the private address.

An EKS cluster reports "failed to assign an IP address to container". The most likely root cause?

  1. The pod subnets ran out of free IPs (VPC CNI gives each pod a VPC IP)
  2. CoreDNS is down
  3. The NAT gateway hit 100 Gbps
Subnet IP exhaustion (or per-instance ENI/IP limits). Fix with bigger subnets, prefix delegation, a 100.64.0.0/10 secondary CIDR or IPv6.
