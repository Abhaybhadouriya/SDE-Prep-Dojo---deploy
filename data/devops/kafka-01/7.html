What async costs you

An interviewer will respect you more for knowing the costs than for knowing the benefits. Every one of these appears again later in the track, with the fix.

  1. Eventual consistency. After "Order placed!", the user's order history page might not show the order for a second, because the service that builds that page has not read the event yet. Systems become eventually consistent: correct soon, not instantly. Design the screens for it.
  2. Duplicates. Networks fail in the middle of things. A consumer may process a message, crash before saving its position, restart and process it again. Kafka's normal guarantee is at-least-once: never lost, sometimes repeated. So consumers must be idempotent - a fancy word for "doing it twice has the same effect as doing it once" (for example, "set order o-981 to PAID" is idempotent; "add 499 to the balance" is not). Page 06 covers this.
  3. Ordering. If OrderPlaced and OrderCancelled for the same order are read in the wrong order, you ship a cancelled order. Kafka keeps order only inside one partition, so you must send all events of one order to the same partition by giving them the same key. That is the heart of page 02.
  4. The dual-write trap. The order service writes to its database and to Kafka. What if the database write succeeds and the Kafka write fails? Now the order exists but nobody hears about it. This is the famous dual-write problem, and its fix (the outbox pattern) is built in the pipeline project and explained in Distributed Transactions & Event-Driven Data.
  5. Harder debugging. A request no longer has one call stack. To follow one order across six services you need a shared ID in every event (a correlation or trace ID) and distributed tracing.
  6. More infrastructure. A Kafka cluster is a real system to run, upgrade and monitor - or to pay a cloud provider for (Amazon MSK, Confluent Cloud, Azure Event Hubs with its Kafka endpoint).
