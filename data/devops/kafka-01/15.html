Quick quiz

The order service calls five services one after another and waits for each. One of them is down. What happens?

  1. Only that one step is skipped
  2. The whole order request fails or times out (cascading failure)
  3. Kafka stores the request automatically
In a synchronous chain, every service must be up at the same time. One failure fails the whole request.

Which of these is NOT a benefit of putting a broker between services?

  1. Producers do not need to know who the consumers are
  2. Bursts of traffic can be absorbed as backlog
  3. Every consumer sees every change instantly with no delay
Messaging gives eventual consistency, not instant consistency. Consumers see changes a little later.

kafka-consumer-groups.sh shows CURRENT-OFFSET 120 and LOG-END-OFFSET 200 for a partition. What is the lag?

  1. 80
  2. 200
  3. 320
Lag = log-end offset - committed offset = 200 - 120 = 80 messages waiting for this group.

A consumer reads message A from a Kafka topic. A new consumer group starts an hour later with --from-beginning. Does it see A?

  1. No, A was deleted when it was read
  2. Yes, as long as A is still within retention
  3. Only if the first consumer allows it
Reading does not delete in Kafka. Each group has its own offset, so the new group can replay from the start.

Which handler is idempotent (safe to run twice)?

  1. "Add 499 to the customer's balance"
  2. "Send a confirmation email"
  3. "Set order o-981 status to PAID"
Setting a value to a fixed state gives the same result no matter how often it runs. Adding money or sending email twice has a different effect.

Which request should stay synchronous in a shopping app?

  1. Updating the analytics dashboard
  2. "Is this item in stock?" on the product page
  3. Sending the shipping confirmation email
The user is staring at the page waiting for the stock answer. The other two can happen a few seconds later.

In the networking analogy, consumer lag is most like...

  1. Queue depth on an egress interface
  2. Round-trip time
  3. The MTU
Lag is the backlog waiting to be drained. If it keeps growing, the drain rate is below the fill rate - exactly like a congested egress queue.
