When NOT to use messaging (or Kafka)

"When would you not use Kafka?" is one of the best signals of maturity in an interview. Here are honest answers:

Messaging fits when
  • The caller does not need the result to answer the user (emails, analytics, search indexing, notifications).
  • Load is bursty and the downstream has a fixed speed.
  • Many teams need the same events.
  • You want to replay history (rebuild a cache, backfill a new service, fix a bug).
  • Volume is large: logs, clicks, metrics, location updates.
Use a direct call (or something simpler) when
  • The user needs the answer now: login, "is this item in stock?", price check, search results.
  • Volume is tiny: a managed queue (SQS) or even a database table is simpler to run.
  • You need per-message delays, priorities or complex routing: RabbitMQ or SQS fit better (or Kafka share groups, if you already run Kafka).
  • You need one strict global order across all events: Kafka gives order per partition, and a single partition does not scale.
  • The team has no capacity to operate it and no budget for a managed service.

Use the trade-off sentence pattern: "I would make the email step async through Kafka because the user does not need it to finish checkout; the cost is eventual consistency and possible duplicates, so the email consumer de-duplicates by order ID; if we only sent a few hundred emails a day, I would use SQS instead because it is zero-ops."
