Lab: see decoupling and fan-out with your own eyes

Start the single-broker lab from the track overview if it is not running (docker run -d --name broker -p 9092:9092 apache/kafka:4.4.0). We will create an orders topic, write orders while the "email service" is switched off, and then watch it catch up. To keep typing short, open a shell inside the container first:

docker exec -it --workdir /opt/kafka/bin broker sh

# inside the container: one topic with a single partition (so order is easy to see)
./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 1

# write three orders while NO consumer is running (type them, then Ctrl+C)
./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
$ ./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 1
Created topic orders.
$ ./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
>{"orderId":"o-1","item":"pen","total":20}
>{"orderId":"o-2","item":"bag","total":499}
>{"orderId":"o-3","item":"lamp","total":899}
^C

The producer finished and went away. Nobody has read anything. Now check how far behind the (not yet started) email service is. A consumer group that has never run has no position yet, so first start it once as a named group and stop it:

# the "email service" comes online, reads everything, then we stop it (Ctrl+C)
./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group email-service --from-beginning

# while it is stopped, two more orders arrive
./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders

# how far behind is email-service?
./kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group email-service
$ ./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group email-service --from-beginning
{"orderId":"o-1","item":"pen","total":20}
{"orderId":"o-2","item":"bag","total":499}
{"orderId":"o-3","item":"lamp","total":899}
^CProcessed a total of 3 messages
$ ./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
>{"orderId":"o-4","item":"mug","total":150}
>{"orderId":"o-5","item":"desk","total":4999}
^C
$ ./kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group email-service

Consumer group 'email-service' has no active members.

GROUP           TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG             CONSUMER-ID     HOST            CLIENT-ID
email-service   orders          0          3               5               2               -               -               -

Read that last line like a networking counter. LOG-END-OFFSET 5: five orders have been written. CURRENT-OFFSET 3: the email service has finished the first three. LAG 2: two orders are waiting for it - the depth of its queue. The email service was down, and nothing failed. Now bring it back:

# email-service comes back; note: no --from-beginning needed, it resumes from its saved offset
./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group email-service

# meanwhile a brand-new analytics team joins and reads ALL history
./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group analytics --from-beginning
$ ./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group email-service
{"orderId":"o-4","item":"mug","total":150}
{"orderId":"o-5","item":"desk","total":4999}

$ ./kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group analytics --from-beginning
{"orderId":"o-1","item":"pen","total":20}
{"orderId":"o-2","item":"bag","total":499}
{"orderId":"o-3","item":"lamp","total":899}
{"orderId":"o-4","item":"mug","total":150}
{"orderId":"o-5","item":"desk","total":4999}

You just saw all three superpowers. Decoupling in time: the producer wrote while email was down. Buffering: the backlog (lag 2) waited safely. Fan-out with replay: a new group read every order from the start, while email read only what it had missed.

Gotcha you just avoided: --from-beginning only matters for a group that has no saved offset. For an existing group, Kafka always resumes from the saved offset. In real code this behaviour is the consumer setting auto.offset.reset, whose default is latest - so a brand-new group in your app skips all old data unless you set it to earliest. "My new consumer sees nothing!" is one of the most common beginner bugs.
