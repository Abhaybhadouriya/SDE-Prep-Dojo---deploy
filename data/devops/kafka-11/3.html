Disk and network sizing

Partitions are not the only number. You also need enough disk to hold the retention window and enough network for replication and readers. Here is the arithmetic, step by step, for an example topic that receives 50 MB/s on average and keeps data for 7 days (the default retention) with replication factor 3.

  1. Per day: 50 MB/s x 86,400 s = 4,320,000 MB, about 4.3 TB per day (after compression, as stored).
  2. Retention: 4.3 TB x 7 days = about 30 TB of unique data.
  3. Replication: x 3 copies = about 91 TB on disk across the cluster.
  4. Headroom: never run disks near full. Plan to stay well below capacity (many teams alert around 70-80% used, a rule of thumb), so buy roughly 120 TB, or turn on tiered storage so old segments live in object storage.

Network is the second budget. Each byte that comes in is also sent out several times:

  • Replication: with RF 3 the leader sends every byte to 2 followers, so the cluster carries 2 x 50 = 100 MB/s of extra traffic between brokers.
  • Readers: each consumer group reads everything once. Four groups (search, analytics, fraud, archive) = 4 x 50 = 200 MB/s out.
  • Total out of the leaders = 300 MB/s for 50 MB/s in. Outbound is usually the bigger number. That matches LinkedIn's reference cluster in the Kafka docs, which shows 300 MB/s in and over 1 GB/s out.

Cloud bill tip: in AWS, Azure or GCP, traffic between availability zones costs money. Spreading replicas across zones (broker.rack) is right for safety, and letting consumers read from a same-zone follower (client.rack, KIP-392 follower fetching) avoids paying for the reader traffic twice.

Memory: a broker needs only a modest JVM heap (the Kafka docs' example uses 6 GB with the G1 collector). Give the rest of the machine's RAM to the operating system's page cache, because that is where Kafka serves recent data from. A healthy cluster serves almost all tail reads from memory and hardly touches the disk for reads. See Storage internals for why.
