The tuning knobs that matter

Kafka has hundreds of settings. About fifteen matter for most teams. This table is the cheat sheet; defaults are from the Kafka 4.4 configuration docs.

WhereKnob (default)Turn it up / on forCost
Producerbatch.size (16384 = 16 KiB)Throughput. 64-256 KiB is a common range for busy topics.More memory per partition in buffer.memory.
Producerlinger.ms (5; was 0 before 4.0)Fuller batches. 5-50 ms for throughput.Adds up to that much latency per message.
Producercompression.type (none)lz4 or zstd cut network and disk a lot for text/JSON.Producer CPU (and consumer CPU to decompress).
Produceracks (all)Durability. Keep all for anything important.Waits for in-sync followers: slower than acks=1.
Producerenable.idempotence (true)No duplicates or reordering on retry.Needs max.in.flight.requests.per.connection <= 5.
Producerbuffer.memory (32 MiB)Bursty producers with many partitions.When full, send() blocks for max.block.ms (60 s) then throws.
Consumerfetch.min.bytes (1)Bigger fetches, fewer requests, less broker CPU.Waits up to fetch.max.wait.ms (500 ms) for data.
Consumermax.poll.records (500)Lower it if each record is slow to process.Too high + slow code = kicked out of the group.
Consumermax.poll.interval.ms (300000 = 5 min)Raise only if a batch truly needs longer.A stuck consumer is detected later.
Consumergroup.protocol (classic)Set consumer to use the new KIP-848 rebalance protocol.Needs 4.0+ brokers and clients.
Brokernum.network.threads (3), num.io.threads (8)Raise when the idle-percent metrics drop low.More threads, more context switches.
Brokernum.replica.fetchers (1)Followers falling behind the leader.More connections and CPU.
Topic/brokermin.insync.replicas (1)Set 2 with RF 3 for real durability.If only 1 replica is in sync, acks=all writes fail.
Topicretention.ms (7 days)Replay window and slow-consumer safety.Disk (see the sizing above).
Brokerunclean.leader.election.enable (false)Keep false unless availability beats correctness.True can silently lose committed data.

The trade is always the same: batching buys throughput with latency. So teams keep two "profiles":

# producer.properties - logs, clickstream, metrics (big volume, a few ms of delay is fine)
acks=all
enable.idempotence=true
compression.type=lz4
# 128 KiB
batch.size=131072
linger.ms=20
# 64 MiB
buffer.memory=67108864

# consumer.properties
# wait for 64 KiB ...
fetch.min.bytes=65536
# ... or 500 ms, whichever comes first
fetch.max.wait.ms=500
max.poll.records=1000
# producer.properties - payments events, user-facing notifications
# keep acks=all for durability; it costs one replication round trip,
# usually a few ms inside one data centre - most avoidable latency is batching (linger.ms)
acks=all
enable.idempotence=true
compression.type=none
batch.size=16384
# send as soon as the sender thread is free
linger.ms=0

# consumer.properties
# return as soon as anything arrives
fetch.min.bytes=1
fetch.max.wait.ms=100
max.poll.records=100
Properties p = new Properties();
p.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
p.put(ProducerConfig.ACKS_CONFIG, "all");
p.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");
p.put(ProducerConfig.BATCH_SIZE_CONFIG, 128 * 1024);
p.put(ProducerConfig.LINGER_MS_CONFIG, 20);
p.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
p.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
try (KafkaProducer<String, String> producer = new KafkaProducer<>(p)) {
    producer.send(new ProducerRecord<>("orders", "order-42", "{\"status\":\"PAID\"}"),
        (meta, err) -> { if (err != null) log.error("send failed", err); });
}

Comments go on their own line. In a Java .properties file, # only starts a comment at the beginning of a line. batch.size=131072 # 128 KiB sets the value to the whole string "131072 # 128 KiB", and the client fails with a ConfigException (invalid integer).

From your world

linger.ms plus batch.size is interrupt coalescing. A NIC that raises one interrupt per packet burns the CPU; one that waits a few microseconds or N packets (or a NAPI budget) gets far more done per wakeup, at the price of a little latency. Kafka's producer waits up to linger.ms or until a batch is full - whichever comes first - for the same reason. fetch.min.bytes / fetch.max.wait.ms is the same trick on the read side. Where this breaks: coalescing in a NIC is microseconds; Kafka batching is milliseconds, because it also wants better compression, which needs bigger batches.

Measure, do not guess

Kafka ships perf tools. Run them against a test topic with the same message size and settings you plan for production. This is how you get the p and c numbers for the partition formula.

# Start a local single-node broker (KRaft mode) with the official image
docker run -d --name broker -p 9092:9092 apache/kafka:4.4.0
docker exec -it broker bash
cd /opt/kafka/bin

./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic perf --partitions 1

# Producer test: 1 million 1 KB records, no rate limit (-1)
./kafka-producer-perf-test.sh --bootstrap-server localhost:9092 --topic perf \
  --num-records 1000000 --record-size 1024 --throughput -1 \
  --command-property acks=all linger.ms=20 batch.size=131072 compression.type=lz4

# Consumer test: read them back
./kafka-consumer-perf-test.sh --bootstrap-server localhost:9092 --topic perf --num-records 1000000
$ ./kafka-producer-perf-test.sh ... --num-records 1000000 --record-size 1024 ...
412873 records sent, 82574.6 records/sec (80.64 MB/sec), 210.4 ms avg latency, 402.0 ms max latency.
1000000 records sent, 90538.704370 records/sec (88.42 MB/sec), 228.71 ms avg latency, 455.00 ms max latency, 221 ms 50th, 390 ms 95th, 431 ms 99th, 450 ms 99.9th.

$ ./kafka-consumer-perf-test.sh ... --num-records 1000000
start.time, end.time, data.consumed.in.MB, MB.sec, data.consumed.in.nMsg, nMsg.sec, rebalance.time.ms, fetch.time.ms, fetch.MB.sec, fetch.nMsg.sec
2026-11-23 10:15:02:114, 2026-11-23 10:15:07:902, 976.5625, 168.7219, 1000000, 172771.2509, 3021, 2767, 352.9318, 361402.2407

The numbers above are an example run on a laptop - yours will differ. Look at the shape: the producer line gives records/sec, MB/sec and latency percentiles (50th, 95th, 99th). The 99th percentile (p99: 99 out of 100 requests were faster than this) is the number interviewers care about, not the average. Run the producer test again with linger.ms=0 and compression.type=none and you will see the trade-off with your own eyes.

The perf consumer does no work. Your real consumer writes to a database, so its per-partition limit c is usually far lower than what kafka-consumer-perf-test.sh shows. Measure your real consumer by watching its lag drain rate under a known load.
