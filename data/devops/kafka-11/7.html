Kafka on Kubernetes with Strimzi

Kafka brokers are stateful: each one owns specific data on its own disk and has a stable identity (node.id). Kubernetes was born for stateless web pods that can be killed and replaced anywhere. Running Kafka well on it needs extra knowledge, and that knowledge is packaged in an operator - a program that runs inside the cluster and knows how to manage one specific system (see Operators).

Strimzi is the best-known open-source Kafka operator (a CNCF project). Version 1.3.1 came out in November 2026 and it is KRaft-only. You describe the cluster you want in YAML custom resources (CRs); the Strimzi Cluster Operator watches them and creates the pods, disks, services, certificates and config to match - the same "desired state, then reconcile" loop Kubernetes uses everywhere.

Here is a small production-shaped cluster: three controllers, three brokers, replication factor 3, minimum ISR 2, replicas spread across availability zones, Cruise Control and lag metrics turned on. It matches the Strimzi 1.3.1 examples.

apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: controller
  labels:
    strimzi.io/cluster: my-cluster
spec:
  replicas: 3
  roles: [controller]
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 20Gi
        kraftMetadata: shared
---
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: broker
  labels:
    strimzi.io/cluster: my-cluster
spec:
  replicas: 3
  roles: [broker]
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 500Gi
        kraftMetadata: shared
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: my-cluster
spec:
  kafka:
    version: 4.3.2
    metadataVersion: 4.3-IV0
    rack:
      topologyKey: topology.kubernetes.io/zone   # spread replicas across zones
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
      - name: external
        port: 9094
        type: loadbalancer        # one LB per broker + one bootstrap LB
        tls: true
    config:
      default.replication.factor: 3
      min.insync.replicas: 2
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      auto.create.topics.enable: false
  entityOperator:
    topicOperator: {}
    userOperator: {}
  cruiseControl: {}
  kafkaExporter:
    topicRegex: ".*"
    groupRegex: ".*"
---
apiVersion: kafka.strimzi.io/v1
kind: KafkaTopic
metadata:
  name: orders
  labels:
    strimzi.io/cluster: my-cluster
spec:
  partitions: 40
  replicas: 3
  config:
    retention.ms: 604800000
    min.insync.replicas: 2
kubectl create namespace kafka
kubectl create -f 'https://strimzi.io/install/latest?namespace=kafka' -n kafka
kubectl apply -f my-cluster.yaml -n kafka
kubectl wait kafka/my-cluster --for=condition=Ready --timeout=300s -n kafka
kubectl get pods -n kafka

To rebalance partitions after adding brokers, you create a KafkaRebalance resource, Cruise Control writes a proposal into its status, and you approve it with an annotation. The operator also performs rolling restarts for you and checks that restarting a broker will not push any partition below its minimum ISR - the stepper above, automated.

The number-one gotcha: clients must reach every broker

A web service sits behind one load balancer, and any pod can answer. Kafka is different. A client first asks any broker for metadata, gets back "the leader of partition 7 is broker 4 at address X", and then connects directly to X. If X is an internal pod address the client cannot reach, the first call works and every produce times out.

From your world

Think of a routing protocol that advertises a next hop the receiver cannot reach: the route installs, the traffic black-holes. Kafka's advertised.listeners is that next-hop address. A load-balancer VIP in front of all brokers is like advertising one anycast address for a service that is really stateful per box - the first packet lands, the session does not. Where this breaks: unlike routing, Kafka clients do not fall back to another path; they keep retrying the advertised address until delivery.timeout.ms (2 minutes) expires.

Is running Kafka on Kubernetes a good idea?

You asked this too. Honest answer: it can be, if you have the people for it.

Good reasons
  • Same platform, tooling, GitOps and monitoring as the rest of your services.
  • The operator automates the hard, repetitive parts: rolling restarts, certificates, users, topics, rebalancing.
  • Easy to spin up many small clusters (per team, per environment).
  • Topics and users live as YAML in Git and get code review.
Real costs
  • Brokers need fast, persistent disks; network-attached volumes can add latency.
  • Pod rescheduling, node drains and autoscalers must respect Kafka (PodDisruptionBudgets, no surprise evictions).
  • External access needs per-broker addressing (above).
  • You now debug two complex systems at once.

Many companies avoid running it at all and use a managed service: Amazon MSK, Confluent Cloud, or Azure Event Hubs (which speaks the Kafka protocol). In an interview, "Strimzi if we already run a mature Kubernetes platform; otherwise a managed service, because Kafka ops is a full-time skill" is a mature answer. The pipeline project deploys our ShopStream Kafka with Strimzi end to end.
