How many partitions? The math

This is the question you asked: "How many partitions should a topic have, and can I change it later?" Here is the honest method. It is short, and you can do it on a whiteboard.

Step 1: two speed limits

One partition can only go so fast in two places:

  • p = how many MB/s one producer can push into one partition.
  • c = how many MB/s one consumer can process from one partition. This is usually the smaller number, because your consumer does real work (writes to a database, calls a service).

Then, for a target throughput T:

partitions  >=  max( T / p ,  T / c )

You measure p and c on your own hardware with the perf tools shown below. Nobody can give you a universal number, because it depends on message size, compression, network, disks and how heavy your consumer code is.

Step 2: check the other constraints

CheckWhy it mattersRule
Consumer parallelismIn a group, one partition goes to exactly one consumer. Extra consumers sit idle.Partitions >= the most consumers you will ever want in one group.
Key cardinalityAll records with one key go to one partition. If you have only 8 distinct keys, partitions beyond 8 stay empty.Many more distinct keys than partitions, and no single key bigger than one partition's limit.
Future growthAdding partitions later moves keys (see the stepper below).Size for 1-2 years if you need key ordering.
Per-partition costEvery partition replica is a directory of segment files, open file handles, a replication fetch, a producer batch buffer, and metadata.Do not create 10,000 partitions "just in case".
Even spreadPartitions are spread across brokers.A multiple of the broker count spreads leaders evenly (nice, not required).

Rule of thumb: partitions are cheap to have a few of and expensive to have tens of thousands of. KRaft (the new built-in controller, see kafka-08) raised the ceiling on how many partitions a cluster can hold, but each partition still costs memory, files and recovery time.

Step 3: can I change it later?

You can increase the partition count of a topic at any time. You can never decrease it. The catch is keys. The default partitioner computes murmur2(key) % numPartitions. Change the number at the end and most keys land somewhere new. Click through to see why that breaks ordering.

  1. Before. The topic has 3 partitions. The key order-42 hashes to 18 (an example number). 18 % 3 = 0, so every event for this order goes to P0, in order.
  2. Add a partition. Someone runs kafka-topics.sh --alter --partitions 4 because traffic grew. Existing data does not move. Only the routing rule changes.
  3. New events go elsewhere. 18 % 4 = 2. The next event for order-42 lands in P2, while its older events still sit in P0.
  4. Ordering breaks for a while. Two different consumers now hold events for the same order. If P0's consumer is behind, "shipped" can be processed before "paid". This lasts until P0's old events drain.
  5. Safe ways out. Size the topic for growth on day one; or pause producers, let consumers drain to lag 0, then add partitions; or create a new topic with more partitions and migrate consumers. If you have no keys (or do not care about order) adding partitions is harmless.

From your world

This is ECMP. A 5-tuple hash pins each flow to one link, so packets in a flow stay in order. Add a fifth link to a 4-way ECMP group and plain modulo hashing re-maps most flows; packets already queued on the old link can arrive after the new ones. "Resilient hashing" in switches limits that churn. Kafka's default partitioner has no resilient hashing - it is plain modulo - so plan the group size up front. Where this breaks: in ECMP the reorder window is microseconds; in Kafka a lagging partition can hold old events for hours.

Commands you will use

# Create a topic with an explicit partition count and replication factor
kafka-topics.sh --bootstrap-server localhost:9092 --create \
  --topic orders --partitions 40 --replication-factor 3 \
  --config min.insync.replicas=2

# Look at where partitions and leaders live
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# Grow it (only up, never down)
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 60
$ kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

Read it like a routing table: for each partition, who is Leader (serves reads and writes), who holds Replicas, and who is in the Isr (in-sync replicas, the copies that are caught up). Elr is the eligible-leader-replicas list added in Kafka 4.x (see kafka-05).
