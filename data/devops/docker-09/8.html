Interview questions on production and security

Structure every security answer in rings: "image, runtime, host, pipeline." It shows you think in defence in depth, and it stops you from listing flags in random order.

How would you harden a Docker container for production?

Image: minimal or distroless base, multi-stage so no compilers ship, a numeric non-root USER, exec-form entrypoint, no secrets, pinned base, scanned. Runtime: --cap-drop=ALL and add back only what is needed, no-new-privileges, keep the default seccomp and AppArmor profiles, read-only root filesystem with a small tmpfs, memory, CPU and pids limits, log rotation, never --privileged, never mount the Docker socket. Host: patched kernel and runc, rootless Docker or userns-remap, firewall rules in DOCKER-USER, ports bound to specific interfaces. Pipeline: deploy by digest, sign with cosign and verify at admission. For untrusted code, a gVisor or microVM sandbox.

How to answer

Go ring by ring and give one reason per item ("drop capabilities because root in a container is UID 0 on the host without a user namespace"). Finish with how you verify it (docker-bench, admission policy). Walmart SDE-2 candidates have reported being told to know recent Docker vulnerabilities, so mention runc CVE-2024-21626.

Likely follow-ups
  • What does no-new-privileges actually block?
  • Rootless Docker vs a non-root USER: what is the difference?
  • How do you do the same in Kubernetes? (securityContext, Pod Security Admission "restricted".)
Why is access to the Docker socket equivalent to root?

The daemon runs as root and executes whatever its API is asked. With the socket you can start a container with --privileged -v /:/host and chroot /host, which is a root shell on the host. So the docker group is effectively the sudoers file, and mounting the socket into a container gives that container host root. In CI, use rootless BuildKit, a remote builder, or Buildah instead of socket mounts or privileged Docker-in-Docker.

How to answer

Show the one-line escape, then the policy consequence, then the alternative design. That order proves you understand the mechanism, not just the rule.

Likely follow-ups
  • How would you let developers run containers on a shared build server safely?
  • Does rootless mode fix this? (Mostly: the daemon then has only your user's power.)
How do you pass secrets to a Docker build and to a running container?

Build time: BuildKit secret mounts, RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci, with docker build --secret id=npmrc,src=.... The secret is a tmpfs file for that one step and never lands in a layer. For private git, --mount=type=ssh forwards the SSH agent. Runtime: mount secrets as files from Compose or Kubernetes Secrets backed by a vault, with rotation. Avoid ARG (visible in history) and avoid ENV for anything sensitive (visible in inspect, inherited by children). If a secret ever entered a layer, deleting it later does not help: rotate it.

How to answer

Split build time and run time explicitly. Mention the "deleted in a later layer" trap; interviewers often set it up.

Likely follow-ups
  • How would you find secrets already leaked in old images? (Scan layers with a secret scanner; Trivy has one.)
  • Are Kubernetes Secrets encrypted? (Base64 only, unless encryption at rest is configured.)
Design the CI pipeline that builds and ships container images.

On each commit: build with BuildKit using a remote cache (registry or GitHub Actions cache) and dependency-first layer ordering; run unit tests in a --target test stage; produce an SBOM; scan and fail on fixable critical vulnerabilities; push multi-arch if needed; tag with the git SHA and semver; sign the digest with cosign keyless and attach SLSA provenance. Deploy by digest and promote the same digest through dev, staging and prod; never rebuild per environment. At the cluster, an admission policy verifies the signature. Around it: pull-through caches to avoid Docker Hub limits, regional replication, retention rules, and a nightly rescan of running images.

How to answer

Draw the conveyor (build, SBOM, scan, push, sign, promote, verify). Then add the scale concerns: cache, rate limits, many services. Uber's 3,000-service Makisu story is a good anchor.

Likely follow-ups
  • A critical CVE lands in your base image. How do you patch 300 services quickly? (SBOM lookup to find affected images, automated base bumps, rebuild and promote.)
  • How do you roll back? (Redeploy the previous digest.)
Is running as root inside a container dangerous if the host is safe?

Yes. Without a user namespace, UID 0 in the container is UID 0 on the host kernel. Docker trims its power with 14 default capabilities and seccomp, but root can still write to any file mounted in, and if any escape bug exists (a runc CVE, a kernel bug, a careless --privileged or a socket mount), it lands as host root. A non-root USER, dropped capabilities and userns-remap or rootless mode turn an escape from "game over" into "landed as nobody".

How to answer

Say "yes, because there is no user namespace by default", then layer the mitigations. Avoid saying containers are "secure" or "insecure" in absolute terms.

Likely follow-ups
  • Can a non-root container bind port 80? (Under plain Docker on a bridge network, yes: Docker sets the net.ipv4.ip_unprivileged_port_start sysctl to 0 inside each container's network namespace, so any UID may bind low ports. With --network host, rootless Docker, or a Kubernetes runtime that does not set that sysctl, it fails. Then listen on 8080 and map 80 to it (-p 80:8080 or a Service port: 80, targetPort: 8080), or give the binary a file capability with setcap cap_net_bind_service=+ep. --cap-add alone does not reach a non-root process's effective set.)
A Docker host's disk fills up every few days. What do you look at?

Start with docker system df and du on /var/lib/docker. Usual suspects: json-file logs with no rotation (check /var/lib/docker/containers/*/*-json.log), dangling and old images from frequent deploys, build cache on CI hosts, anonymous volumes left behind, and apps writing into the container layer. Fix: log rotation or the local driver in daemon.json, scheduled image and builder prune with an age filter, --rm for one-off containers, and volumes for data. Alert on disk usage before it hits 100%.

How to answer

Measure first, then list causes from most to least likely, then a permanent fix plus an alert. Do not jump to prune --volumes; say why that is dangerous.

Likely follow-ups
  • Why does deleting a container not free its image space?

Your 60-second answer: "How do you run Docker safely in production?"

"I think in four rings. The image: minimal or distroless base, multi-stage build, numeric non-root user, no secrets in layers, pinned base. The runtime: drop all capabilities and add back only what is needed, no-new-privileges, keep the default seccomp and AppArmor, read-only root filesystem, memory, CPU and pids limits, rotated logs, and never privileged mode or the Docker socket. The host: patch runc, containerd and the kernel because that is where escapes happen, use rootless or user-namespace remapping, and filter published ports in DOCKER-USER because ufw does not see them. The pipeline: build once, scan with a gate, generate an SBOM, sign the digest with cosign, and deploy that exact digest everywhere with verification at admission. For untrusted code I would move to gVisor or Firecracker."
