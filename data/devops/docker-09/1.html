Step 1: a safe image

The image is the easiest place to remove risk, because whatever is not in the image cannot be attacked. Five rules cover most of it.

  1. Start small. Use a minimal base: -slim Debian images, Google's distroless images (no shell, no package manager), Docker Hardened Images (made free and Apache 2.0 licensed in December 2025), Chainguard images, or scratch for static binaries. Fewer packages means fewer CVEs (published security bugs) to patch.
  2. Multi-stage builds. Compile in a big "builder" stage, copy only the final artifact into a tiny runtime stage. Compilers and test tools never ship. A Go service typically drops from around 800 MB (the golang image) to under 20 MB.
  3. Run as a non-root user. Add USER 10001 with a numeric UID. Kubernetes' runAsNonRoot check can only verify a number, not a name.
  4. No secrets in layers. Never COPY a key file, never pass tokens as ARG or ENV. Use BuildKit secret mounts (below).
  5. Pin versions. Pin the base image (by tag and, ideally, by @sha256: digest) so a rebuild today and next week start from the same bytes. Never deploy :latest; it is just a default tag name, not "the newest".

A hardened Dockerfile

# syntax=docker/dockerfile:1
# ---------- build stage ----------
FROM --platform=$BUILDPLATFORM golang:1.25 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
ARG TARGETOS TARGETARCH
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/orders ./cmd/orders

# ---------- runtime stage ----------
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/orders /orders
USER 65532:65532
EXPOSE 8080
# exec form: runs the binary directly, no shell needed (distroless has none)
HEALTHCHECK --interval=30s --timeout=3s CMD ["/orders","healthcheck"]
ENTRYPOINT ["/orders"]

Line by line: the builder stage caches Go modules with a BuildKit cache mount so CI does not re-download them each time. FROM --platform=$BUILDPLATFORM makes the build stage run on the CI machine's own CPU type, and TARGETOS/TARGETARCH tell the Go compiler which CPU to produce code for, so one Dockerfile cross-compiles for amd64 and arm64 without slow emulation. The HEALTHCHECK uses exec form (a JSON list), so Docker runs the binary directly; this matters because distroless has no /bin/sh. The runtime stage is distroless "static" with the built-in nonroot user (UID 65532). The ENTRYPOINT uses exec form, so the binary is PID 1 and receives SIGTERM directly. There is no shell, so an attacker who gets code execution also gets no sh, curl or package manager to play with.

$ docker build -t orders:1.4.2 .
$ docker images orders
REPOSITORY   TAG     IMAGE ID       CREATED          SIZE
orders       1.4.2   7d3c0f19a2b4   12 seconds ago   9.8MB
$ docker run --rm --entrypoint id orders:1.4.2
docker: Error response from daemon: failed to create task for container: ... exec: "id": executable file not found in $PATH

That last error is a feature: there is no id command to run, because there is nothing in the image except your binary and a few certificate and timezone files.

Secrets during the build

# syntax=docker/dockerfile:1
FROM node:22-slim
WORKDIR /app
COPY package.json package-lock.json ./
# The token is mounted only for this RUN at /root/.npmrc (target=); without target= it would be at /run/secrets/npmrc.
# It is never written to a layer.
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci --omit=dev
COPY . .
USER 10001
CMD ["node", "server.js"]
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t web:2.0.1 .
$ docker history --no-trunc web:2.0.1 | grep -c npm_
0

Never do this: COPY id_rsa /root/.ssh/ and then RUN rm /root/.ssh/id_rsa in a later step. The key is still inside the earlier layer, and anyone who can pull the image can extract it with docker save and tar. Same for ARG NPM_TOKEN: build args show up in docker history. Uber's engineering blog on their Makisu builder describes exactly this problem (secrets kept in layers even after deletion) as one reason they built a new tool.

For runtime secrets (database passwords, API keys), do not bake them into the image at all. Mount them as files at start time: Docker or Compose secrets:, a tmpfs mount, or in Kubernetes a Secret volume, ideally fed from a vault. Environment variables are convenient but leak easily: they show in docker inspect, in crash dumps and in child processes. Shopify called secrets the "most unexpectedly complex" part of their move to Docker. See ConfigMaps & Secrets for how Kubernetes does it.
