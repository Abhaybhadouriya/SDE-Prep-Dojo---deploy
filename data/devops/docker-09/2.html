Step 2: a safe runtime (the hardened docker run)

Here is the "production" version of a docker run. Every flag maps to a kernel feature from the internals page. You will rarely type this by hand in real life (Compose files or Kubernetes manifests carry the same settings), but knowing each flag is what interviewers test.

docker run -d --name orders \
  --user 10001:10001 \
  --read-only --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop=ALL \
  --security-opt no-new-privileges \
  --memory=512m --memory-swap=512m --cpus=1 --pids-limit=200 \
  --init \
  --restart=on-failure:5 \
\
  --log-driver=local --log-opt max-size=10m --log-opt max-file=3 \
  -p 127.0.0.1:8080:8080 \
  registry.example.com/shop/orders@sha256:7d3c0f19a2b4...
FlagKernel / Docker featureWhy
--user 10001:10001process UID/GIDWithout a user namespace, root in the container is UID 0 on the host. A non-root UID limits damage after an escape.
--read-only + --tmpfs /tmpread-only overlay mount, RAM mountMalware cannot drop files or modify binaries; the app gets a small writable scratch area.
--cap-drop=ALLcapabilitiesStart from zero privileges. The app listens on 8080, so it needs none. (Adding one back with --cap-add only helps a root process: for a non-root UID Docker puts it in the bounding set, not the effective set, so the process still cannot use it.)
--security-opt no-new-privilegesPR_SET_NO_NEW_PRIVSsetuid binaries like su cannot raise privileges.
default seccomp + AppArmor/SELinuxsyscall filter, LSMOn by default. The rule is: never pass seccomp=unconfined or --privileged.
--memory, --cpus, --pids-limitcgroupsOne bad container cannot starve the host or fork-bomb it. Setting --memory-swap equal to --memory means no swap.
--inittini as PID 1Forwards signals and reaps zombie child processes.
--restart=on-failure:5dockerd restart managerBounded automatic restarts (back-off doubles from 100 ms).
HEALTHCHECK in the Dockerfilehealth check run by dockerdShows healthy/unhealthy in docker ps; Compose service_healthy waits on it. It is baked into the image above, so no flag is needed here.
--log-driver=local / rotationlogging driverThe default json-file driver does not rotate; disks fill up.
-p 127.0.0.1:8080:8080iptables DNATPlain -p 8080:8080 listens on every interface (0.0.0.0 and [::]).
@sha256:...content addressingRuns exactly the bytes that were scanned and signed. Tags can move.

Careful with --health-cmd: the docker run --health-cmd flag always runs its string through /bin/sh -c (it does not understand a JSON list). On a distroless or scratch image there is no shell, so the check can never pass and the container stays unhealthy forever. For shell-less images, put an exec-form HEALTHCHECK CMD ["/bin","arg"] in the Dockerfile instead.

Check that the hardening is real

$ docker exec orders sh -c 'id; touch /x'    # (works only if your image has a shell)
uid=10001 gid=10001
touch: /x: Read-only file system
$ docker inspect --format '{{.HostConfig.CapDrop}} {{.HostConfig.CapAdd}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.SecurityOpt}}' orders
[ALL] [] true [no-new-privileges]
$ docker inspect --format '{{.State.Health.Status}}' orders
healthy

The same knobs exist in Compose and Kubernetes. In Compose you write read_only: true, cap_drop: [ALL], security_opt: [no-new-privileges:true], user: "10001". In a Kubernetes pod spec they live in securityContext (runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation: false, capabilities.drop: ["ALL"], seccompProfile: RuntimeDefault). The Kubernetes Security & RBAC page covers that side.

Graceful shutdown in production: grace periods and preStop

The PID 1 rules themselves (why shell-form CMD hides your app behind /bin/sh, why PID 1 has no default signal actions, and the fixes: exec form, a SIGTERM handler, --init) are taught once, on page 03; the operational side (docker stop -t, reading exit codes 137 and 143) is on page 04. This section is about what changes when an orchestrator, not you, does the stopping.

In production a stop is rarely one container on one host. It is a rolling update or a node drain, and the danger is not a slow stop but dropped requests while traffic is still being routed to a pod that is going away. Kubernetes stops a pod like this:

  1. The pod is marked "Terminating". Two things then start at the same time: the pod is removed from the Service's endpoints (so kube-proxy and load balancers stop sending it new traffic), and the kubelet begins the shutdown.
  2. preStop hook runs first. If the container has a lifecycle.preStop hook, the kubelet runs it before any signal. A common one is just sleep 5: it gives the endpoint removal a few seconds to reach every node and load balancer.
  3. SIGTERM to PID 1. Your app stops accepting new connections, finishes the in-flight ones, closes DB and Kafka clients cleanly, and exits 0.
  4. Deadline, then SIGKILL. The whole budget is terminationGracePeriodSeconds (30 s by default), and it includes the preStop time. Anything still running at the deadline is SIGKILLed (exit 137).
spec:
  terminationGracePeriodSeconds: 45     # preStop + drain must fit inside this
  containers:
    - name: orders
      image: ghcr.io/acme/shop/orders@sha256:7d3c0f19...
      lifecycle:
        preStop:
          sleep:
            seconds: 5                  # built-in sleep action (Kubernetes 1.30+); older clusters use exec: ["sleep","5"]
  • Size the budget from measurements. If your slowest request takes 20 s and preStop is 5 s, a 30 s grace period leaves almost no margin. Raise the grace period rather than cutting the drain.
  • Readiness should fail on SIGTERM. Many frameworks flip the readiness endpoint to "not ready" as soon as SIGTERM arrives, which is a second signal to the load balancer to stop routing.
  • Zombies still matter. If your app spawns helpers, run it under an init (--init in Docker, or tini / dumb-init as the image's entrypoint in Kubernetes, which has no --init flag). Yelp built dumb-init for exactly this.

From your world

preStop plus a grace period is graceful maintenance on a router: before you reload a box you cost it out (raise the IGP metric, or send BGP graceful-shutdown so neighbours prefer other paths), wait for traffic to move away, and only then take it down. The preStop sleep is that "wait for the network to converge" step. Where it breaks: a routing protocol tells you when convergence is done; Kubernetes gives no signal that every load balancer and kube-proxy has removed the pod, so the sleep is a guess you size from measurements.

Logs, disk and metrics

Containers should log to stdout and stderr, and the platform should collect it. Do not write log files inside the container layer. In production a node agent (Fluent Bit, Vector, the cloud provider's agent) ships logs to Elasticsearch, Loki or a cloud log service. Shopify, an early large Docker user, chose a host-side logger subscribing to Docker events rather than an agent inside every container; the same "agent per node" pattern became a DaemonSet in Kubernetes.

Set the daemon defaults once in /etc/docker/daemon.json:

{
  "log-driver": "local",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "live-restore": true,
  "no-new-privileges": true,
  "icc": false,
  "userns-remap": "default",
  "metrics-addr": "127.0.0.1:9323"
}

live-restore keeps containers running while dockerd restarts or upgrades (the shim from the internals page makes this possible). icc: false blocks container-to-container traffic on the default bridge (the legacy --link option is the only exception). Containers that must talk should join a user-defined network, which icc does not affect. userns-remap maps container root to an unprivileged range of host UIDs (note: the containerd image store, the default on fresh Engine 29 installs, is not used when userns-remap is on). metrics-addr exposes the daemon's Prometheus metrics. Restart dockerd after editing (sudo systemctl restart docker).
