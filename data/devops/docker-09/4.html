Step 4: a safe pipeline (supply chain)

Quick reminder of the words: CI (continuous integration) is a server that builds and tests every commit automatically; CD (continuous delivery or deployment) means it also ships the result. It is the container-world version of the nightly image build plus regression lab that runs on every commit to a router OS branch.

Words in this step

The software supply chain is everything between a developer's commit and the bytes running in production: base images, packages, the build machine, the registry. Attacks there are attractive because one poisoned dependency reaches thousands of victims. The defence is a pipeline where every step leaves evidence that the next step checks. Click through it.

  1. Build. CI checks out the commit and runs docker buildx build with a remote cache, so unchanged layers are reused between runs.
  2. SBOM. BuildKit attaches a software bill of materials (--sbom=true, or Syft): the exact list of packages and versions inside the image.
  3. Scan gate. Trivy, Grype or Docker Scout compares that list against vulnerability databases. A CRITICAL finding with a fix available fails the job. (In the workflow below the tags are pushed before the scan, and the scanner reads that exact pushed digest. A failed scan means the digest is never signed, and the admission policy in step 7 rejects unsigned digests. The pushed tags still exist, so this is only safe if that admission check is really enforced.)
  4. Push. The image goes to the registry and gets an immutable digest (sha256:...). Tags like 1.4.2 and git-3f2a1c9 point at it.
  5. Sign. cosign signs the digest (keyless, through Sigstore, using the CI job's identity) and BuildKit adds SLSA provenance: who built it, from which commit, with which steps.
  6. Promote. The same digest moves dev -> staging -> prod. Nothing is rebuilt per environment, so what you tested is what you ship. Rollback means pointing back to the previous digest.
  7. Verify at the door. Before a cluster runs it, an admission policy (a gate that checks every new pod before the cluster accepts it: Kyverno, Sigstore policy-controller, or a cloud equivalent) checks the signature and that the image comes from your registry by digest.

The GitHub Actions version

name: image
on:
  push:
    branches: [main]
    tags: ["v*"]
permissions:
  contents: read
  packages: write
  id-token: write            # lets cosign sign keylessly with the job's OIDC identity
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5          # example tag; pin a commit SHA in real repos
      - uses: docker/setup-qemu-action@v3          # only needed for emulated arm64 builds
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}/orders
          tags: |
            # semver = MAJOR.MINOR.PATCH, taken from a git tag like v1.4.2
            type=sha
            type=semver,pattern={{version}}
      - id: push
        name: Build once (both CPUs) and push (unsigned until scanned)
        uses: docker/build-push-action@v6
        with:
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          sbom: true
          provenance: mode=max
      # Trivy scans ONE platform per run, so scan each platform we ship.
      - name: Scan the pushed digest, linux/amd64 (fail on fixable CRITICAL/HIGH)
        uses: aquasecurity/trivy-action@0.28.0   # in a real repo, pin to a full commit SHA
        env:
          TRIVY_USERNAME: ${{ github.actor }}
          TRIVY_PASSWORD: ${{ secrets.GITHUB_TOKEN }}
          TRIVY_PLATFORM: linux/amd64            # same as trivy --platform
        with:
          image-ref: ghcr.io/${{ github.repository }}/orders@${{ steps.push.outputs.digest }}
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"
      - name: Scan the pushed digest, linux/arm64
        uses: aquasecurity/trivy-action@0.28.0
        env:
          TRIVY_USERNAME: ${{ github.actor }}
          TRIVY_PASSWORD: ${{ secrets.GITHUB_TOKEN }}
          TRIVY_PLATFORM: linux/arm64
        with:
          image-ref: ghcr.io/${{ github.repository }}/orders@${{ steps.push.outputs.digest }}
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"
      - uses: sigstore/cosign-installer@v3
      - name: Sign only if the scan passed
        run: cosign sign --yes ghcr.io/${{ github.repository }}/orders@${{ steps.push.outputs.digest }}

Notes: the image is built once for both CPU types and pushed. The digest is an image index, but Trivy scans one platform per run (by default the runner's, linux/amd64 on ubuntu-latest). That is why there are two scan steps, one per platform; with only one, the arm64 image would ship unscanned ("scan one platform, ship another"). You could also use a job matrix over [linux/amd64, linux/arm64], or scan each per-platform manifest digest. cosign signs the digest only if both scan steps passed, so the bytes you sign are the bytes you scanned. Be honest about one gap: the real sha and semver tags are pushed before the scan, so a failed scan leaves pullable, unsigned tags in the registry, and only the admission policy stops them. In a stricter setup the first push goes to a separate staging repository (for example images: ghcr.io/${{ github.repository }}/orders-staging), and a later job copies (promotes) the signed digest to the production repository with crane copy or docker buildx imagetools create. ${{ steps.push.outputs.digest }} is the immutable digest you deploy.

Pin your CI tools too. Tags like @v4 or :0.28.0 can be moved by whoever controls that repository. A re-pointed tag on an action or a scanner image is a known supply-chain attack path, because the action runs with your job's secrets. In real repos pin actions to a full commit SHA (uses: actions/checkout@<40-char-sha> # v5) and scanner images by digest (aquasec/trivy@sha256:...); a bot like Dependabot or Renovate keeps the pins fresh. The versions above are examples, not checked pins.

Multi-architecture images

An image built on an Apple Silicon Mac is arm64 by default and will fail on an x86 server with exec format error. The fix is an image index (a "manifest list"): one tag pointing at one manifest per platform; each machine pulls the one matching its CPU.

$ docker buildx build --platform linux/amd64,linux/arm64 -t ghcr.io/acme/orders:1.4.2 --push .
$ docker buildx imagetools inspect ghcr.io/acme/orders:1.4.2
Name:      ghcr.io/acme/orders:1.4.2
MediaType: application/vnd.oci.image.index.v1+json
Digest:    sha256:5e1b...
Manifests:
  Name:        ghcr.io/acme/orders:1.4.2@sha256:a9c4...
  Platform:    linux/amd64
  Name:        ghcr.io/acme/orders:1.4.2@sha256:41d0...
  Platform:    linux/arm64

QEMU emulation works but is slow for compiled languages; native arm64 builders or cross-compiling (the --platform=$BUILDPLATFORM plus TARGETARCH trick in the Dockerfile above) are much faster. Swiggy wrote about needing exactly this kind of multi-arch pipeline when they moved Kubernetes workloads to AWS Graviton (arm64) for better price-performance.

Registries at scale: pull limits, mirrors, retention

  • Docker Hub pull limits (per 6 hours): 100 pulls for anonymous users per IPv4 address (or IPv6 /64), 200 for a logged-in personal account, unlimited on paid plans. A CI fleet behind one NAT IP hits this fast. Log in, or use a pull-through cache (ECR, ACR, Artifact Registry, Harbor, Artifactory).
  • Regional replication. Pulling from a registry in another region adds latency and cost to every deploy. Replicate to each region you run in.
  • Retention. Every commit produces an image. Set lifecycle rules (keep the last N, keep anything deployed) or storage grows forever.
  • Pull speed. Small images and shared base layers make deploys fast. At very large scale, companies add lazy-pulling snapshotters (stargz, AWS SOCI) or peer-to-peer distribution (Uber's Kraken, Dragonfly).

Uber's Makisu post is a good real-world read: as they grew from about 400 services in early 2015 to more than 3,000 by 2017, builds of up to 2 hours and images over 10 GB pushed them to a distributed layer cache and a builder that did not need a privileged daemon. They report P90 build time falling by almost half. The CI/CD platform design on this site, CI/CD Platform on Kubernetes, uses all of these ideas.
