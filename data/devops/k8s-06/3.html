Gateway API: roles, listeners and routes

Good to know (SDE-2)

The Gateway API is the official successor, developed by SIG Network. Its core went GA (v1.0) in October 2023; the current release is v1.6 (June 2026), in which TCPRoute and UDPRoute also reached the Standard channel. Its big idea is to split the front door into layers, one per role:

ObjectOwnerSaysScope
GatewayClassInfra provider / whoever installs the controller"Gateways of this class are implemented by controller X" (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, a cloud's controller...)Cluster
GatewayPlatform teamListeners: port, protocol, host names, TLS certificates, which namespaces may attach routesNamespace
HTTPRoute, GRPCRoute, TLSRoute, TCPRoute, UDPRouteApp teamsMatch rules (path, header, method, query) to weighted backends, plus filters (redirects, header changes, mirroring)Namespace
ReferenceGrantOwner of the target namespace"Routes in namespace A may point to Services/Secrets in my namespace"Namespace
 
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gw
  namespace: infra
spec:
  gatewayClassName: eg                 # e.g. Envoy Gateway's class
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: "*.shop.example.com"
    tls:
      mode: Terminate
      certificateRefs:
      - kind: Secret
        name: shop-wildcard-tls
    allowedRoutes:
      namespaces:
        from: Selector
        selector:
          matchLabels:
            shop-gateway-access: "true"   # only labelled namespaces may attach
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: orders
  namespace: orders                    # labelled shop-gateway-access=true
spec:
  parentRefs:
  - name: shop-gw
    namespace: infra
  hostnames: ["api.shop.example.com"]
  rules:
  - matches:                           # testers opt in with a header
    - path: { type: PathPrefix, value: /orders }
      headers:
      - name: x-canary
        value: "true"
    backendRefs:
    - name: orders-v2
      port: 80
  - matches:                           # everyone else: 90 / 10 canary split
    - path: { type: PathPrefix, value: /orders }
    backendRefs:
    - name: orders-v1
      port: 80
      weight: 90
    - name: orders-v2
      port: 80
      weight: 10
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: redirect-to-https
  namespace: infra
spec:
  parentRefs:
  - name: shop-gw
    sectionName: http                  # needs an HTTP :80 listener on the Gateway
  rules:
  - filters:
    - type: RequestRedirect
      requestRedirect:
        scheme: https
        statusCode: 301
$ kubectl get gatewayclass
NAME   CONTROLLER                                      ACCEPTED   AGE
eg     gateway.envoyproxy.io/gatewayclass-controller   True       10m

$ kubectl get gateway -n infra
NAME      CLASS   ADDRESS        PROGRAMMED   AGE
shop-gw   eg      203.0.113.50   True         5m

$ kubectl get httproute -n orders
NAME     HOSTNAMES                  AGE
orders   ["api.shop.example.com"]   1m

$ kubectl describe httproute orders -n orders | grep -A3 Conditions
    Conditions:
      Type:     Accepted       Status: True    Reason: Accepted
      Type:     ResolvedRefs   Status: True    Reason: ResolvedRefs

Tip: the Gateway API reports problems in status conditions. If a route "does nothing", kubectl describe httproute usually tells you why: NotAllowedByListeners (namespace not allowed to attach), RefNotPermitted (missing ReferenceGrant), or BackendNotFound. Ingress gave you no such feedback.
