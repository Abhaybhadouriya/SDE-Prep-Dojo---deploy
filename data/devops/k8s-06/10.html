Six boxes. One front door (the Gateway) decides by host and path, then hands off to an ordinary Service.

Ingress vs LoadBalancer Service vs NodePort - which one is the front door?

NodePort opens the same high port (30000-32767) on every node - fine for labs, not for users. A LoadBalancer Service asks the cloud for an L4 load balancer per Service: simple, but one LB and IP per service, and no HTTP awareness. Ingress (or, today, a Gateway) is an L7 entry point: one LoadBalancer in front of a proxy that routes many hosts and paths to many Services and terminates TLS once. For an HTTP product, the front door is a Gateway; LoadBalancer Services are for non-HTTP protocols or for exposing the gateway itself.

How to answer

Order them by layer (NodePort and LB are L4, Ingress/Gateway is L7), then give the cost argument and the "the gateway itself is behind one LoadBalancer" insight.

Likely follow-ups
  • How does an Ingress controller get its public IP? (Its own Service of type LoadBalancer.)
Why was the Gateway API created, and what are its main objects?

Ingress was too small: only host/path routing and TLS, with everything else in non-portable, controller-specific annotations, and no separation between platform and app owners. The Gateway API is role-oriented: a GatewayClass (which implementation, owned by the infra provider), a Gateway (listeners, ports, certificates and which namespaces may attach - owned by the platform team), and Routes (HTTPRoute, GRPCRoute, TLSRoute, TCPRoute, UDPRoute) owned by app teams. ReferenceGrant controls cross-namespace references. Features like header matching, weighted traffic splitting, redirects and mirroring are in the spec itself, and status conditions explain failures. It is GA since 2023 and the recommended path after the Ingress NGINX retirement in March 2026.

How to answer

"Problem with the old thing, three-layer model, two killer features (portable canary weights, role-based ownership)." Mention the 2026 retirement to show you are current.

Likely follow-ups
  • Is the Ingress API deprecated? (No; frozen, still supported.)
  • How would you stop team A from hijacking team B's host name? (allowedRoutes, RBAC, separate listeners or Gateways.)
How would you run a 5% canary of a new API version on Kubernetes?

Deploy the new version as a separate Deployment and Service (orders-v2). In the HTTPRoute, list both Services in backendRefs with weights 95 and 5. Optionally add a header-match rule so testers can force v2. Watch v2's error rate and latency against v1 (per-backend metrics from the gateway), then raise the weight in steps, or set it to 0 instantly to roll back. In practice I would let Argo Rollouts or Flagger edit the weights based on Prometheus queries so promotion and rollback are automatic.

How to answer

Show the YAML shape (two backendRefs with weights), name the metric that decides, and say what triggers rollback.

Likely follow-ups
  • What about sticky sessions or users flipping between versions? (Use a cookie/header based route for consistency.)
  • How do you canary a database change? (You don't, with weights; use expand/contract.)
How would you preserve the client's source IP through the cloud LB and the gateway?

Set externalTrafficPolicy: Local on the gateway's LoadBalancer Service so nodes do not SNAT (at the cost of uneven spread and health checks that skip nodes without proxy pods), or enable the PROXY protocol between the cloud LB and the proxy. Then have the proxy add or append X-Forwarded-For so backends see the original client. Only trust XFF from your own proxies.

How to answer

Name where the IP gets lost (the SNAT hop), then give one L4 fix and one L7 fix, plus the trust caveat.

Likely follow-ups
  • Why does SNAT happen in Cluster mode? (So the reply returns via the same node to be un-NATed.)
Design the edge for an e-commerce site on Kubernetes during a big sale.

CDN in front for static assets and cacheable pages; a cloud L4 LB per region; a Gateway API implementation with proxy replicas spread across three zones, PDB and HPA (scaled ahead of the sale, not just reactively); TLS terminated at the gateway with cert-manager; HTTPRoutes per domain team; rate limiting and bot protection at the gateway; per-route timeouts and retries with budgets; canary weights for any change during the sale (ideally a change freeze). Metrics per route feed alerts. Backends are reached directly by pod IP. For multi-region, global DNS or anycast sends users to the nearest healthy region. See Flash Sale design.

How to answer

Draw outside-in: CDN, LB, gateway, services. At each box say how it scales and how it fails.

Likely follow-ups
  • Where do you enforce per-user rate limits? (Gateway with a shared counter store, see the rate limiter design.)

60-second answer - "What is Ingress / the Gateway API?"
"Services give me stable internal addresses, but for HTTP traffic from the internet I want one entry point that routes by host and path and terminates TLS. That's an L7 proxy - Envoy, NGINX and so on - exposed by a single LoadBalancer. Ingress was the first API to describe those rules, but it was minimal and pushed everything else into vendor annotations, and the popular community Ingress NGINX controller was retired in March 2026. The Gateway API is the successor: a GatewayClass picks the implementation, the platform team owns a Gateway with listeners and certificates, and app teams attach HTTPRoutes with matches and weighted backends - so a canary is just two backendRefs with weights 95 and 5. A controller watches those objects and programs the proxies."
