TLS: terminate, pass through, or re-encrypt

Good to know (SDE-2)
ModeWhat happensWhen
Terminate (most common)Gateway decrypts; plain HTTP inside the clusterNormal web traffic; lets the gateway route on path and headers
Passthrough (TLSRoute: a route that matches on SNI only)Gateway routes on SNI only, never decryptsThe backend must hold its own keys (compliance), or non-HTTP TLS protocols
Re-encrypt (BackendTLSPolicy: says how the gateway should verify the backend's certificate)Decrypt at the gateway, then open a new TLS connection to the backend"Encrypt everything in transit" rules, zero-trust networks

An HTTPS listener in YAML

In the Gateway API, TLS lives on the listener of the Gateway (owned by the platform team). App teams only write HTTPRoutes and never touch keys.

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gw
  namespace: infra
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # ask cert-manager to issue the cert below
spec:
  gatewayClassName: eg                 # which implementation (here Envoy Gateway)
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "api.shop.example.com" # SNI value this listener answers for
      tls:
        mode: Terminate                # decrypt here; use a TLSRoute + mode Passthrough to skip decryption
        certificateRefs:
          - kind: Secret
            name: api-shop-tls         # a kubernetes.io/tls Secret: tls.crt + tls.key
      allowedRoutes:
        namespaces:
          from: All                    # app namespaces may attach HTTPRoutes

Several listeners with different hostnames can share port 443; the proxy picks the listener, and so the certificate, from the SNI field of the TLS ClientHello.

Where the certificate comes from: cert-manager

cert-manager is a popular add-on controller that issues and renews certificates for you. Let's Encrypt is a free public certificate authority that proves you own a domain with the ACME protocol. The flow:

  1. You declare an issuer. A ClusterIssuer object says "use Let's Encrypt with this account".
  2. cert-manager notices the Gateway. It sees the annotation and the listener's certificateRefs, and creates a Certificate request for api.shop.example.com.
  3. It proves you own the domain. Let's Encrypt asks for a challenge: a token served over HTTP (HTTP-01) or a DNS TXT record (DNS-01). cert-manager sets it up and cleans it up.
  4. It writes the Secret. The signed certificate and private key land in the api-shop-tls Secret. The gateway controller sees the Secret and loads it into Envoy.
  5. It renews. Before expiry (Let's Encrypt certificates are short-lived), cert-manager repeats the process and updates the Secret. Nobody has to remember a renewal date.

See ConfigMaps & Secrets for how TLS Secrets are stored.

From your world

SNI-based routing is exactly what an L7 load balancer or an SSL offload card does: terminate TLS on the box, pick the certificate by server name, and forward clear text (or re-encrypt) to the real servers. The Gateway listener is that box's virtual-server config. Where it breaks: here the "box" is a set of ordinary pods that scale out and are configured from the Kubernetes API, and keys live in Secrets, not in a hardware security module, unless you add one.
