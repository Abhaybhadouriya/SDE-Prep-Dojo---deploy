Ingress: the original front-door rules

Must know (SDE-1)

An Ingress is a Kubernetes object that says "for this host and path, send to that Service". By itself it does nothing. An Ingress controller - a pod running a proxy plus a small program that watches Ingress objects - must be installed. The controller turns the rules into proxy configuration. ingressClassName picks which controller should handle the object.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
spec:
  ingressClassName: traefik          # which controller implements this
  tls:
  - hosts: ["shop.example.com"]
    secretName: shop-tls             # a kubernetes.io/tls Secret with cert + key
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /cart
        pathType: Prefix
        backend:
          service:
            name: cart
            port:
              number: 80
      - path: /search
        pathType: Prefix
        backend:
          service:
            name: search
            port:
              number: 80
$ kubectl get ingress -n shop
NAME   CLASS     HOSTS              ADDRESS        PORTS     AGE
shop   traefik   shop.example.com   203.0.113.20   80, 443   2m

$ curl -s https://shop.example.com/cart/health
{"service":"cart","status":"ok"}

The 2026 news you must know. The community Ingress NGINX controller (the kubernetes/ingress-nginx project, for years the most common choice) was retired in March 2026: no more releases or security fixes. Kubernetes SIG Network and the Security Response Committee recommend moving to the Gateway API or another maintained controller. Two things are often confused: (1) the Ingress API itself is not removed - it is stable but frozen, with no new features; (2) F5's separate commercial "NGINX Ingress Controller" product is a different project. Sources: retirement announcement, Steering and SRC statement.

Why Ingress hit its limits

  • Too small a spec. It covers host + path to Service, and TLS. Everything else - timeouts, rewrites, header matching, canary weights, rate limits - lives in controller-specific annotations like nginx.ingress.kubernetes.io/canary-weight. Change controllers and your annotations mean nothing.
  • One object, many owners. The platform team owns TLS and ports; app teams own their paths. Ingress mixes both in one object, which makes permissions awkward.
  • HTTP only. No first-class gRPC, TCP or UDP routing.
