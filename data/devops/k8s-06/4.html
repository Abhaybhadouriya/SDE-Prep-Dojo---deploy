The journey of one HTTPS request

Good to know (SDE-2)

What actually happens when a user opens https://api.shop.example.com/orders/42? Click through.

  1. DNS. The browser resolves api.shop.example.com to the Gateway's public address (often managed automatically by a tool like ExternalDNS).
  2. L4 hop. The cloud load balancer (created because the Gateway's proxy is exposed by a LoadBalancer Service) forwards the TCP connection to one of the proxy pods. It does not look inside.
  3. TLS termination. Envoy uses the SNI (server name in the TLS hello) to pick the right certificate from the Gateway listener and decrypts the request.
  4. Route match. Envoy's routing table was compiled earlier by the gateway controller, which watches Gateway and HTTPRoute objects and pushes config to Envoy (over xDS, Envoy's config API). It matches host, path and headers, then picks a backend by weight.
  5. To the pod. Most gateway implementations read EndpointSlices and connect straight to a pod IP, skipping the ClusterIP and kube-proxy. That allows per-request load balancing, retries and timeouts.
  6. Response. The pod answers; Envoy sends the response back over the user's TLS session. Logs and metrics for every request are emitted at this single point.

From your world

The split between the gateway controller (watches the API, computes config) and the Envoy data plane (forwards requests) is the classic router split: routing process computes the RIB, then downloads the FIB to the forwarding engine. xDS is that download channel. If the controller crashes, Envoy keeps forwarding with its last config - non-stop forwarding again. Where it breaks: this data plane works per request, not per packet, so it is millions of times "heavier" per unit of work than an ASIC.
