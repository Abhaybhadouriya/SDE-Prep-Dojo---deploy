Who may do what: private by default, Block Public Access, IAM vs bucket policies

New to IAM roles and policy evaluation? Read IAM in 10 minutes first.

Must know (SDE-1)Top real-world mistake

Every bucket and object starts private: only the account that owns it can touch it. Access is then opened up deliberately with policies. There are three places a permission can live:

MechanismAttached toAnswersUse it for
IAM identity policya user, group or role"What may this principal do, across all resources?"Your own services: "the uploader role may PutObject on dojo-uploads/*"
Bucket policy (resource policy)the bucket"Who may do what to this bucket?"Cross-account access, guard rails for everyone (deny non-TLS, require a VPC endpoint, require KMS)
ACLs (legacy)bucket or objectCoarse grants to accounts or groupsNothing new. Since April 2023 new buckets have ACLs disabled ("Bucket owner enforced") - keep it that way

Block Public Access (BPA) is a set of four switches (at account and bucket level) that override everything else: even if someone writes a policy granting "Principal": "*", BPA blocks or ignores it. New buckets have all four switches on since April 2023. Leave them on for every bucket that is not a deliberate public website, and serve public content through CloudFront with Origin Access Control instead.

Here is how S3 decides on one request. Click through it:

  1. Request. Every call is signed with Signature Version 4 using the caller's credentials (an IAM role on EC2/ECS/EKS, never long-lived keys in code). An unsigned request is "anonymous".
  2. Identify. S3 works out the principal - here the role uploader - and gathers every policy that applies: the role's IAM policies, the bucket policy, any Organizations SCP/RCP, and the VPC endpoint policy if the call came through one.
  3. Explicit deny wins. If any of those policies has a matching "Effect": "Deny", the answer is 403 immediately. Nothing can override an explicit deny - this is why guard-rail policies are written as denies.
  4. Block Public Access. Grants that would make the bucket public (principal * without a narrowing condition, public ACLs) are blocked or ignored.
  5. Find an Allow. Same account: an allow in either the IAM policy or the bucket policy is enough. Cross-account: the caller's IAM policy and the bucket policy must both allow. If nothing allows, the default is an implicit deny: 403 AccessDenied.

From your world

This is a firewall rule chain with a default-drop policy. iptables -P INPUT DROP is "private by default"; a -j DROP rule early in the chain is an explicit deny that no later ACCEPT can undo; the ACCEPT rules are the Allows. Cross-account access is like traffic crossing two firewalls - the sender's egress rule and the receiver's ingress rule must both permit it. And the VPC side maps directly onto routing: an S3 gateway VPC endpoint is literally a route-table entry whose destination is an AWS-managed prefix list (pl-xxxx, the S3 IP ranges) and whose next hop is the endpoint, so S3 traffic from private subnets skips the NAT gateway (and its per-GB charge). See AWS Networking for route tables.

A bucket policy that a reviewer would be happy with: deny plain HTTP, only allow traffic through our VPC endpoint, and give one role write access to one prefix.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": ["arn:aws:s3:::dojo-uploads-surbhi", "arn:aws:s3:::dojo-uploads-surbhi/*"],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    },
    {
      "Sid": "DenyOutsideOurVpce",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::dojo-uploads-surbhi/*",
      "Condition": { "StringNotEquals": { "aws:SourceVpce": "vpce-0a1b2c3d4e5f67890" } }
    },
    {
      "Sid": "UploaderMayWriteIncoming",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/uploader" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::dojo-uploads-surbhi/incoming/*"
    }
  ]
}

A DenyOutsideOurVpce statement like the one above also blocks you in the console and on your laptop. Real policies add an exception (for example aws:PrincipalArn of a break-glass admin role) before applying it. Test with a second session open.

ListBucket is granted on the bucket ARN (arn:aws:s3:::name); GetObject/PutObject on the object ARN (arn:aws:s3:::name/*). Mixing them up is the most common reason a policy "looks right" but returns 403. Also: without ListBucket, a GET on a missing key returns 403 instead of 404, so the caller cannot probe which keys exist.
