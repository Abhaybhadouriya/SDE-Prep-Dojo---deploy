Encryption at rest: SSE-S3, SSE-KMS and friends

Good to know (SDE-2)

All new objects are encrypted at rest; your only choice is whose key and who can audit its use.

OptionKey managed byWhat you getCost / catch
SSE-S3 (default)S3, AES-256Encryption with zero workAnyone with S3 read permission can read; no separate key permission

From your world

SSE-KMS is envelope encryption, the same idea as LUKS/dm-crypt: a per-object data key encrypts the bytes, and that data key is itself stored encrypted ("wrapped") under a master key that never leaves KMS hardware. Reading the object means asking KMS to unwrap the data key - which is why a KMS outage, a missing kms:Decrypt grant, or a KMS throttle shows up as an S3 error. Bucket Keys add one more level: a bucket-level key is cached for a while and used to make data keys, so S3 stops calling KMS for every single object.

aws s3api put-bucket-encryption --bucket dojo-uploads-surbhi \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "alias/dojo-uploads"
      },
      "BucketKeyEnabled": true
    }]
  }'

Changing default encryption only affects new objects. Existing objects keep the encryption they were written with; re-encrypting them means copying them (S3 Batch Operations does this at scale).

From your world

This is a key hierarchy, like a TPM's wrapped keys: the root key never leaves the hardware, and it only wraps and unwraps smaller keys that do the bulk encryption. Revoke or disable the root key and every wrapped key, and so every object, becomes unreadable at once.
