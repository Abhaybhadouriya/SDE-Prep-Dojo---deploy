Multipart and resumable uploads (recap)

Must know (SDE-1)

A single PUT can carry at most 5 GiB, and AWS suggests switching to multipart from about 100 MB. A multipart upload has three calls: CreateMultipartUpload returns an UploadId; UploadPart sends numbered parts (1 to 10,000, each 5 MiB to 5 GiB except the last, uploaded in any order and in parallel); CompleteMultipartUpload sends the list of part numbers + ETags and S3 stitches the object. The largest object you can build this way is 48.8 TiB.

This is what makes uploads resumable: if the connection drops on part 37, the client calls ListParts, sees 1-36 are done, and re-sends only 37 onwards. Each part is an independent, idempotent PUT, so retries are safe. Pre-sign each UploadPart URL and a browser can do all of this without AWS credentials. The full design of a resumable chunked uploader, and how S3 itself stores parts, are in Pattern: Handling Large Blobs and S3-like Object Storage.

  1. CreateMultipartUpload returns an UploadId. Nothing is visible in the bucket yet.
  2. The client sends parts (5 MiB to 5 GiB each, up to 10,000) in parallel with UploadPart. Each response carries that part's ETag.
  3. One part fails on a flaky link. Only that part is re-sent; the others are already stored. This is what makes uploads resumable.
  4. CompleteMultipartUpload sends the list of part numbers and ETags. S3 stitches the parts in order.
  5. Now the object appears, atomically. Its ETag is a hash of the part hashes plus "-N", not the file's MD5.
  6. If the client dies and never completes or aborts, the parts stay invisible in listings but billed. A lifecycle rule with AbortIncompleteMultipartUpload cleans them up.

For the internals (how a storage system tracks parts and assembles them), see S3-like Object Storage deep dives.

split -b 100M big.tar part-
UPLOAD_ID=$(aws s3api create-multipart-upload --bucket dojo-uploads-surbhi \
  --key backups/big.tar --query UploadId --output text)
aws s3api upload-part --bucket dojo-uploads-surbhi --key backups/big.tar \
  --upload-id "$UPLOAD_ID" --part-number 1 --body part-aa
# ... parts 2..N (in parallel), then:
aws s3api complete-multipart-upload --bucket dojo-uploads-surbhi --key backups/big.tar \
  --upload-id "$UPLOAD_ID" --multipart-upload file://parts.json
{
    "ETag": "\"7a1e4c2b9f0d3e8a5c6b1f2e9d0a4c7b\""
}
...
{
    "Location": "https://dojo-uploads-surbhi.s3.ap-south-1.amazonaws.com/backups/big.tar",
    "Bucket": "dojo-uploads-surbhi",
    "Key": "backups/big.tar",
    "ETag": "\"5f0b2a1e7c4d...-21\""
}

Note the -21 at the end of the final ETag: a multipart object's ETag is a hash of the parts' hashes plus the part count, not the MD5 of the file. Do not compare it to md5sum; use S3 checksums (CRC32/CRC64NVME/SHA-256) instead. In practice aws s3 cp and the SDK transfer managers do multipart automatically (the CLI default threshold and part size are 8 MB) - you hand-roll it only for browser or mobile resumable uploads.

An upload that is started but never completed or aborted keeps its parts stored and billed, and they do not appear in aws s3 ls. The AbortIncompleteMultipartUpload lifecycle rule above is the fix; put it on every bucket.
