Interview questions

Scenario: "users upload profile videos up to 2 GB"

The interviewer asks how uploads reach S3 and how you keep the bucket safe.

Weak answer: "The client sends the file to our API, which saves it to a public S3 bucket."

Strong answer: "The API authenticates the user and returns pre-signed URLs for a multipart upload - one per part, 10-minute expiry, key chosen by the server under incoming/. The client uploads parts in parallel and resumes failed ones via ListParts. The bucket keeps Block Public Access on, has a deny-non-TLS policy, SSE-KMS with Bucket Keys, versioning, an abort-incomplete-multipart rule and a lifecycle rule moving originals to IA after 30 days. An S3 event triggers transcoding; viewers get media through CloudFront, never directly from the bucket."

Likely follow-ups
  • How do you stop a user uploading 50 GB? (Presigned POST with content-length-range, or a server-side check per part count, plus a post-upload size check.)
Is S3 a filesystem? What is the difference between a bucket, a key and a prefix?

No. S3 is a flat key-value object store with an HTTP API. A bucket is a Region-scoped, globally named container; a key is the full string name of an object; a prefix is just the leading part of keys that the console and LIST calls use to simulate folders. There is no rename and no partial overwrite: PUT replaces the whole object atomically, and "moving a folder" is copy + delete of every object. Since 2020 reads after writes and lists are strongly consistent.

How to answer

Say "flat key-value store" in the first sentence, then the consequences (no rename, whole-object PUT, prefixes for listing and request-rate scaling).

Likely follow-ups
  • How does S3 scale request rate? (Per prefix: at least 3,500 writes and 5,500 reads per second each.)
IAM policy vs bucket policy - when do you need which? What changes for cross-account access?

An IAM policy is attached to a principal and says what it can do everywhere; a bucket policy is attached to the bucket and says who can do what to it. Within one account, an allow in either is enough and an explicit deny in either wins. Cross-account, both sides must allow: the other account's IAM policy lets its role call S3, and our bucket policy names that role (or account) as a principal. If the bucket uses SSE-KMS, the KMS key policy must allow it too - a third gate people forget. Use bucket policies for guard rails (deny non-TLS, require VPC endpoint, require encryption) because they apply to everyone.

How to answer

Describe the evaluation order: explicit deny, then any allow, else implicit deny. Then the cross-account "both must allow" rule and the KMS gotcha.

Likely follow-ups
  • What does Block Public Access do that a policy cannot? (It overrides any policy or ACL that would grant public access, at account level too.)
How do pre-signed URLs work, and what are their security pitfalls?

A backend with S3 permissions computes a SigV4 signature over the method, bucket, key, expiry and chosen headers, and puts it in the query string. Anyone with the URL can perform exactly that operation until expiry; S3 verifies the signature and then checks that the signer still has the permission. Pitfalls: it is a bearer token (do not log it), long expiries widen the window (max 7 days, and shorter when signed with temporary credentials), the client could upload anything unless you constrain content type/size (presigned POST conditions) and validate after upload, and the server must choose the key so users cannot overwrite each other.

How to answer

Explain why: offload bandwidth from app servers. Then mechanism, then four pitfalls.

Likely follow-ups
  • How would you do a resumable 5 GB browser upload? (Pre-signed URL per multipart part.)
SSE-S3 vs SSE-KMS: which would you choose for customer documents and why?

SSE-KMS with a customer-managed key. Both encrypt at rest, but KMS adds an independent permission (kms:Decrypt), so a misconfigured bucket policy alone cannot expose data; every key use is logged in CloudTrail; and you can disable the key to crypto-shred access. Costs: KMS calls and request quotas, so enable S3 Bucket Keys. SSE-S3 is fine for non-sensitive data such as build artifacts.

How to answer

Frame it as "who can decrypt and can I audit it", not "is it encrypted" - both are.

Likely follow-ups
  • What is envelope encryption?
  • What happens to replication with SSE-KMS? (The replication role needs decrypt on the source key and encrypt on the destination key.)
Someone deleted important objects from a versioned bucket. Can you recover them?

If they did a normal DELETE, yes: versioning turned it into a delete marker. List versions, then delete the delete marker (or copy the previous version over the key) and the object is back. If they deleted specific version ids, those versions are gone - unless a replica exists (version-id deletes are not replicated), a backup exists (AWS Backup supports S3), or Object Lock prevented the delete. Prevention: Object Lock for critical data, MFA delete, SCPs denying s3:DeleteObjectVersion, and SRR/CRR into a separate account.

How to answer

Separate "delete marker" from "version delete" - that is the whole question.

Likely follow-ups
  • Why can versioning never be turned off, only suspended?
Design a retention policy for application logs: hot for 30 days, kept 1 year, then deleted.

A lifecycle rule on logs/: Standard for 30 days (dashboards and incident queries), transition to Standard-IA at 30 days, to Glacier Flexible Retrieval (or Instant Retrieval if audits need fast reads) at 90, expire at 365. Add noncurrent-version expiration if versioning is on, and an abort-incomplete-multipart rule. Check object size: if log files are tiny, batch them (Firehose or the shipper) into larger compressed objects first, because objects under 128 KB do not transition by default and per-object fees dominate.

How to answer

Give the timeline as numbers, then show you know the minimum-duration and small-object traps.

Likely follow-ups
  • When would you pick Intelligent-Tiering instead? (When access is unpredictable.)
How does S3 cross-region replication work, and what is not replicated?

A replication configuration on a versioned source bucket names an IAM role and one or more rules (filter, destination bucket and optional storage class, account, KMS key). After a PUT, S3 asynchronously copies the object, its metadata and version id, setting ReplicationStatus to PENDING then COMPLETED or FAILED. Not replicated by default: objects that existed before the rule (use Batch Replication), delete markers (opt-in), version-id deletes (never), objects that are themselves replicas (no chaining), and lifecycle actions. Timing is best effort unless RTC is enabled: 99.99% within 15 minutes under an SLA.

How to answer

Mechanism in one sentence, then the "not replicated" list - that list is what separates a strong answer.

Likely follow-ups
  • Is CRR a backup? (Partly - it copies mistakes too, except version deletes. A separate account plus Object Lock is closer to a backup.)
  • How would you do active-active? (Two-way replication + Multi-Region Access Point.)
Explain multipart upload. Why is the final ETag not the file's MD5, and what does an incomplete upload cost?

Create returns an UploadId; parts 1-10,000 of 5 MiB-5 GiB are uploaded independently (parallel, retryable, resumable via ListParts); Complete sends the ordered part list and S3 assembles the object, up to 48.8 TiB. The ETag is computed from the parts' MD5s and ends in -<partCount>, so it depends on the part size chosen - use S3's additional checksums for end-to-end integrity. An upload never completed or aborted keeps its parts stored and billed, invisible to normal listings, until an abort call or an AbortIncompleteMultipartUpload lifecycle rule removes it.

How to answer

Three API calls, the limits, then the two gotchas. Link to the HLD resumable-upload design if time allows.

Likely follow-ups
  • How would a browser resume after a page reload? (Store UploadId locally, ListParts, continue.)

Interviewers love this: "S3 is private by default, Block Public Access is on, explicit deny always wins, and anything public goes through CloudFront." One sentence covers the top cloud misconfiguration.
