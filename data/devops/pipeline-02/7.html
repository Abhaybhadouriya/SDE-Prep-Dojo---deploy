Step 5: query Postgres and prove idempotency

docker compose exec postgres psql -U shopstream -c "SELECT order_id, customer_id, total_cents/100.0 AS inr, kafka_partition, kafka_offset FROM orders ORDER BY inserted_at DESC LIMIT 5;"
               order_id               | customer_id |          inr          | kafka_partition | kafka_offset
--------------------------------------+-------------+-----------------------+-----------------+--------------
 1c7d5e90-0a4b-4f61-b2c3-8e9d7f6a5b41 | C-42        | 3097.0000000000000000 |               3 |            4
 9b0e44d1-77c2-4a1e-a0b9-5f3e2d1c0b8a | C-42        | 3097.0000000000000000 |               3 |            2
 3f6c2a8e-5d1b-4c7e-9a0f-2b8d7e1c4a90 | C-42        | 3097.0000000000000000 |               3 |            0
(3 rows)

The total is INR 3097.00: one pair of headphones at 2499 plus two mugs at 299 each. Postgres prints many zeros because dividing a BIGINT by 100.0 gives a NUMERIC; add ::numeric(12,2) if it bothers you. The kafka_partition and kafka_offset columns are the record's position in orders.enriched; storing them makes every row traceable back to the log.

Why do enriched offsets skip numbers (0, 2, 4)? Each enricher transaction ends with a COMMIT marker (a control record) that takes one offset. read_committed consumers skip it, so your code never sees it. The orders.created offsets from the API go up by 1 (0, 1, 2) because the API's producer is idempotent but not transactional, so it writes no markers. If you sent orders very quickly, two of them may share one transaction and the gap disappears between them. See exactly-once inside Kafka. Interview nugget: "offsets are positions, not message counts".

Prove that duplicates are harmless

The API accepts an optional order_id. Send the same id twice, the way a client would after a timeout:

curl -X POST localhost:8000/orders -H "Content-Type: application/json" \
  -d '{"order_id":"demo-dup-1","customer_id":"C-9","items":[{"product_id":"P-101","quantity":3}]}'
sleep 2    # PowerShell: Start-Sleep 2
curl -X POST localhost:8000/orders -H "Content-Type: application/json" \
  -d '{"order_id":"demo-dup-1","customer_id":"C-9","items":[{"product_id":"P-101","quantity":3}]}'
docker compose exec postgres psql -U shopstream -c "SELECT order_id, total_cents, kafka_offset, inserted_at < updated_at AS was_updated FROM orders WHERE order_id = 'demo-dup-1';"
{"order_id":"demo-dup-1","status":"ACCEPTED","partition":1,"offset":0}
{"order_id":"demo-dup-1","status":"ACCEPTED","partition":1,"offset":1}
  order_id  | total_cents | kafka_offset | was_updated
------------+-------------+--------------+-------------
 demo-dup-1 |       29700 |            2 | t
(1 row)

Two events in orders.created (offsets 0 and 1), one row in Postgres. The second upsert hit ON CONFLICT (order_id), updated the row, moved kafka_offset forward (to 2, the second record's position in orders.enriched, because of the commit marker at 1) and set updated_at. Why the sleep 2? The sink reads in batches (consume(500, timeout=1.0)) and writes each batch in one database transaction. In Postgres, now() is the transaction start time, not the wall clock. Without the pause, both copies usually land in the same batch and the same transaction, so updated_at equals inserted_at and was_updated prints f even though the upsert worked. The kafka_offset column is the more reliable proof: it always holds the second record's offset. That is "at-least-once delivery plus an idempotent write equals effectively-once". The key lines of the sink loop:

        while stop.running:
            try:
                with conn.transaction():
                    with conn.cursor() as cur:
                        cur.executemany(UPSERT, rows)
                break
            except psycopg.OperationalError as exc:
                # DB down: keep the batch, reconnect, try again. Lag grows meanwhile
                # (that is backpressure - Kafka buffers for us).
                DB_ERRORS.inc()
                log.warning("db write failed (%s); reconnecting", exc)
                time.sleep(2)
                conn = connect()
        else:
            break  # shutting down without writing: do NOT commit offsets
        WRITTEN.inc(len(rows))
        consumer.commit(asynchronous=False)  # commit AFTER the DB commit

Read the order carefully: database transaction first, Kafka offset commit second, and a synchronous commit so the loop does not move on until Kafka has it. If Postgres is down, the batch is retried forever and nothing is committed, so lag grows but nothing is lost. The analytics revenue, by contrast, would count demo-dup-1 twice; idempotency is a property of each consumer, not of the pipeline.
