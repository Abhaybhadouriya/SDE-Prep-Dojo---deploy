Step 8: Prometheus and Grafana

URLWhat you see
localhost:8080kafka-ui: topics, partitions, messages with headers, consumer groups and lag
localhost:3000Grafana (anonymous viewer): "ShopStream - Kafka lag & pipeline health"

localhost:8001/windowsanalytics: closed one-minute revenue windows as JSON
localhost:8000/docsorder-api Swagger UI

Prometheus pulls (scrapes) /metrics from kafka-exporter:9308 and from each service every 10 s (prometheus.yml). kafka-exporter turns Kafka's offsets into metrics such as kafka_consumergroup_lag. In the Prometheus page, try:

sum by (consumergroup) (kafka_consumergroup_lag)
rate(shopstream_orders_accepted_total[1m])
sum by (outcome) (rate(shopstream_enricher_records_total[1m]))

The first is lag per group (the step 7 experiment as a graph). The second is orders accepted per second by the API. The third splits the enricher's work into enriched, retry and dlq. Open /targets first: every target should be UP. If Grafana panels are empty, wait 30 s for the first scrapes.

When the enricher is scaled to 3, the Prometheus target enricher:8000 resolves through Docker DNS to just one of the replicas, so the enricher's own counters are partial. The lag metric from kafka-exporter is still complete, because it comes from Kafka, not from the instances. In Kubernetes you would run Prometheus in a monitoring namespace and let it discover each pod separately. That is not included in this lab, but the NetworkPolicy on page 04 already allows a monitoring namespace to scrape the pods.
