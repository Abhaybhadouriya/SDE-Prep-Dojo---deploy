Under the hood: how the service images are built

All four service images follow the same multi-stage pattern. Here is the real order-api/Dockerfile:

# syntax=docker/dockerfile:1
# Stage 1 "builder": install dependencies into a virtualenv (has pip, caches).
FROM python:3.12-slim AS builder
ENV PIP_NO_CACHE_DIR=1 PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /venv
COPY order-api/requirements.txt /tmp/requirements.txt
RUN /venv/bin/pip install -r /tmp/requirements.txt

# Stage 2 "runtime": only the venv + our code. No compilers, no pip cache.
FROM python:3.12-slim
ENV PATH=/venv/bin:$PATH PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=/app
# Run as an unprivileged user (uid 10001), never as root.
RUN useradd --uid 10001 --no-create-home --shell /usr/sbin/nologin app
COPY --from=builder /venv /venv
WORKDIR /app
COPY common/shopstream_common.py ./
COPY order-api/*.py ./
USER 10001
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
  • Build context is services/ (build: {context: ./services, dockerfile: order-api/Dockerfile}), so the shared common/shopstream_common.py can be copied into every image.
  • Requirements are copied before code. Editing app.py does not invalidate the slow pip install layer. See Images & Layers for why order matters.
  • --host 0.0.0.0, not 127.0.0.1. Inside a container, localhost is the container's own loopback; binding there makes the app unreachable through the published port. This is the number one "works on my laptop, not in Docker" bug.
  • Non-root user 10001. If someone breaks into the process, they are not root in the container. Production & Security covers more.
  • PYTHONUNBUFFERED=1 makes logs appear immediately in docker compose logs instead of sitting in a buffer.
  • The enricher image runs two programs. retry-worker reuses shopstream/enricher:dev with command: ["python", "retry_worker.py"]. One image, two roles.

Graceful shutdown

When you run docker compose stop or down, Docker sends SIGTERM, waits (10 s by default), then SIGKILL. Ten seconds is too short for us: the order-api flushes for up to 15 s, and an enricher batch with PROCESSING_DELAY_MS=50 can take 200 x 50 ms = 10 s. So docker-compose.yml sets stop_grace_period: 30s on the five services, to match Kubernetes' terminationGracePeriodSeconds. Every ShopStream consumer installs a GracefulExit handler that flips a flag; the loop finishes its current batch, commits, and calls consumer.close(), which tells the group coordinator "I am leaving" so the rebalance starts immediately instead of after the 45 s session timeout. The order-api flushes its producer buffer for up to 15 s on shutdown so in-flight orders are not lost. Kubernetes uses the same signal sequence, which is why page 04 needs no code change.

From your world

This is the same discipline as a line-card driver's remove path: stop taking new work, drain the rings, write back state, then release resources. A hard kill (SIGKILL, like yanking the card) skips all of that, and the cluster only notices through a timeout (the 45 s session timeout here, like a BFD or hello dead interval). Where it breaks: a driver's remove path has no deadline, but a container's does. If draining takes longer than the grace period, SIGKILL arrives mid-drain, exactly like a hot-swap with no wait.
