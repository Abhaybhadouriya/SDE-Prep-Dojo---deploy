Interview questions

Your producer connects to Kafka in Docker but every send times out. What is wrong?

"The classic cause is advertised listeners. The bootstrap connection only fetches metadata; the client then connects to whatever address each broker advertises for the partition leaders. If the broker advertises a container hostname to a client on the host, or localhost to a client in another container, the first connection works and every produce times out. The fix is one listener per network audience: an internal listener advertised as the container name, and an external listener advertised as localhost with a published port per broker. I would confirm by checking the metadata the client receives, for example with kafka-broker-api-versions.sh from the client's side."

How to answer

Explain the two-step connection (bootstrap, then leader), name advertised listeners, then the fix. Mention that Kubernetes has the same problem for clients outside the cluster.

Likely follow-ups
  • Other reasons for produce timeouts? (ISR below min ISR, buffer full, quotas, TLS errors)
  • How does Strimzi solve this for external clients?
Consumer lag is growing. How do you find out why, and fix it?

"First, where: lag per group and per partition. If one group lags and others reading the same topic do not, the problem is that consumer, not Kafka. If only one partition lags, it is a hot key or one stuck instance. If all partitions lag evenly, the group's total throughput is too low. Then why: check the consumer's processing time, its downstream dependency, crash loops and rebalances in the logs. Fixes in order: fix a slow dependency or batch the writes; scale out up to the partition count; if already at the partition count, the long-term fix is more partitions, planned carefully because of key remapping. Lag growth rate matters more than the absolute value: steady lag is fine, a rising line is not."

How to answer

Localise (which group, which partitions), diagnose (processing, dependency, rebalances), then fix in increasing cost. Use arrival rate vs processing rate arithmetic.

Likely follow-ups
  • You are already at 6 consumers for 6 partitions. Now what?
  • What alert would you set, and on what threshold?
How do you prove your sink does not create duplicates?

"I make it testable. The sink upserts on the business id, order_id, which is the primary key, and commits offsets only after the database transaction. To prove it, I send the same order id twice and check there is exactly one row, and I crash the sink between the DB commit and the offset commit, then check the row count is unchanged after it re-reads. In production I would add a reconciliation job that compares counts per hour between the topic and the table."

How to answer

Mechanism (unique key + upsert + commit after write), then a concrete test, then ongoing verification in production.

Likely follow-ups
  • What if the table has no natural unique key?
  • Why keep the Kafka partition and offset in the row?
Why does the compose file use healthchecks and an init container instead of plain depends_on?

"Plain depends_on only waits for a container to start, not to be ready. A Kafka JVM can be running long before it can serve requests, and services would crash or, worse, auto-create topics with the wrong settings. Healthchecks make readiness explicit, condition: service_healthy waits for them, and a one-shot topics-init container with service_completed_successfully guarantees every topic exists with the right partitions and replication before any service runs. It is the same idea as readiness probes and init containers in Kubernetes."

How to answer

Started vs ready, then the mechanism, then the bridge to Kubernetes. Short and concrete.

Likely follow-ups
  • Should services still retry connections even with healthchecks? (Yes: brokers can restart later.)

Scenario: "it worked yesterday"

You restart the lab the next day with docker compose up -d. kafka-1 keeps restarting; the others are fine. The interviewer asks how you would debug it.

Weak answer: "Delete everything and start again."

Strong answer: "I look before I delete. docker compose ps shows kafka-1 restarting, so I read docker compose logs kafka-1. If it says Invalid cluster.id, the data volume was formatted for a different cluster id, maybe because I changed .env. In a lab I would wipe it with down -v. In production I would never wipe a broker's disk without checking replicas elsewhere: I would restore the right cluster id, because wiping a broker means it must re-replicate everything from its peers."

Likely follow-ups
  • What happens to the partitions kafka-1 led while it is down?
  • How long would re-replication take for a broker with 2 TB?

60-second answer: "How would you test a Kafka pipeline locally?" "I run the real thing, small. One Compose file starts a three-broker KRaft cluster, so replication and min ISR behave like production, plus Postgres, my services and the tools: kafka-ui to look inside topics, kafka-exporter, Prometheus and Grafana for lag. Topics are created by a one-shot init container, so every run starts the same. Then I test in layers: unit-test the pure logic (validation, pricing) with no Kafka; send real orders with curl and a load generator; and run scripted failure drills: kill a broker, pause a consumer, inject poison messages, replay a group. For each drill I write down what the dashboard should show before I run it. Small single-broker setups hide replication bugs, so I keep three brokers even on a laptop."
