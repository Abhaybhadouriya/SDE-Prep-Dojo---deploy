Step 7: create lag, then scale it away

First make the enricher slow on purpose. PROCESSING_DELAY_MS=50 makes it sleep 50 ms per record, so one instance handles about 20 records per second.

PROCESSING_DELAY_MS=50 docker compose up -d enricher
python loadgen/loadgen.py --rps 50 --seconds 120
$env:PROCESSING_DELAY_MS = "50"; docker compose up -d enricher
python loadgen/loadgen.py --rps 50 --seconds 120
# edit .env and set:
PROCESSING_DELAY_MS=50
# then recreate only the enricher:
docker compose up -d enricher

Compose notices the changed environment and recreates only the enricher container. Now do the arithmetic before you look, as you would in an interview: 50 orders arrive per second, about 20 are processed per second, so lag should grow by roughly 30 per second. After a minute, about 1800 behind. Check:

docker compose exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 --describe --group enricher
GROUP     TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID       HOST         CLIENT-ID
enricher  orders.created  0          1903            2214            311   e4a1c07d9b22-...  /172.19.0.14 e4a1c07d9b22
enricher  orders.created  1          1870            2190            320   e4a1c07d9b22-...  /172.19.0.14 e4a1c07d9b22
enricher  orders.created  2          1925            2231            306   e4a1c07d9b22-...  /172.19.0.14 e4a1c07d9b22
...

The numbers are illustrative; yours depend on timing. The shape is what matters: every partition has lag, and it keeps rising. The postgres-sink lag, meanwhile, is near zero: it is starved, not slow. Lag shows where the bottleneck is.

Now scale the group to three instances while load is still running:

PROCESSING_DELAY_MS=50 docker compose up -d --scale enricher=3      # PowerShell: keep $env:PROCESSING_DELAY_MS set
docker compose logs --since 1m enricher | grep -E "assigned|revoked"   # PowerShell: ... | Select-String "assigned|revoked"
enricher-1  | ... INFO  enricher revoked ['orders.created[4]', 'orders.created[5]']
enricher-1  | ... INFO  enricher revoked ['orders.created[2]', 'orders.created[3]']
enricher-2  | ... INFO  enricher assigned ['orders.created[2]', 'orders.created[3]']
enricher-3  | ... INFO  enricher assigned ['orders.created[4]', 'orders.created[5]']

That is a cooperative rebalance. The first instance keeps partitions 0 and 1 and gives up only the four that must move (the exact numbers may differ). With the older "eager" protocol, every member would stop and give up everything first. Each new instance gets its own transactional.id from its hostname, so they do not fence each other. Run the describe command again: three CONSUMER-IDs, two partitions each, and the lag shrinking.

Scaling past the partition count does nothing. --scale enricher=8 gives six busy instances and two idle ones. The partition count is the ceiling. Reset with docker compose up -d --scale enricher=1 and a normal PROCESSING_DELAY_MS (unset or 0) when you are done.

Bonus: replay history (a 30-second taste)

Kafka keeps the events for days, so a consumer can read them again. Found a bug in the analytics math? Fix it, then rewind the analytics group to the start of orders.enriched and it recomputes every window. Offsets can only be moved while the group has no running members, so stop it first. These are the same steps as scripts/chaos/05-replay.sh:

docker compose stop analytics
docker compose exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 \
  --group analytics --topic orders.enriched --reset-offsets --to-earliest --dry-run
docker compose exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kafka-1:19092 \
  --group analytics --topic orders.enriched --reset-offsets --to-earliest --execute
docker compose start analytics

The dry run prints a table with each partition and its NEW-OFFSET (0 for a fresh topic) without changing anything; --execute applies it. Replay is safe here because analytics rebuilds its windows from scratch in memory (a restart starts empty), and the Postgres sink uses ON CONFLICT (order_id) DO UPDATE, so re-reading orders never creates duplicate rows. The full drill, with what to watch for, is on Observability & Failure Drills.

Watch shopstream_late_events_total during the replay. Our toy processor has one global watermark across all six partitions. A replay reads up to 500 records per fetch, often mostly from one partition, so the watermark races ahead to that partition's newest time and many events from the other partitions are then marked late and dropped. The replayed windows can be smaller than the originals. Real frameworks track a watermark per partition and use the minimum (see windowed analytics).
