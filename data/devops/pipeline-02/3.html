Step 1: start everything

docker compose up -d --build

up creates and starts all services, -d runs them in the background (detached), and --build builds our four service images from their Dockerfiles first. The first run downloads images and installs Python packages, so give it a few minutes. Later runs take seconds because image layers are cached.

Then check health. Plain docker compose ps hides containers that have exited, so add -a to see topics-init too, and a format string to keep it narrow:

docker compose ps -a --format "table {{.Service}}\t{{.Status}}"
$ docker compose ps -a --format "table {{.Service}}\t{{.Status}}"
SERVICE          STATUS
analytics        Up About a minute
enricher         Up About a minute
grafana          Up About a minute
kafka-1          Up 2 minutes (healthy)
kafka-2          Up 2 minutes (healthy)
kafka-3          Up 2 minutes (healthy)
kafka-exporter   Up About a minute
kafka-ui         Up About a minute
order-api        Up About a minute (healthy)
postgres         Up 2 minutes (healthy)
postgres-sink    Up About a minute
prometheus       Up 2 minutes
retry-worker     Up About a minute
topics-init      Exited (0) About a minute ago

What you want: three brokers (healthy), topics-init Exited (0), everything else Up. Times will differ. If a broker says (health: starting), wait; the healthcheck allows up to two minutes.

You might confuse this with: service name vs container name, and depends_on vs readiness.

Service name vs container name. Commands like docker compose logs kafka-1 use the service name. The container name adds the project name and a replica number, so the container for service kafka-1 is shopstream-kafka-1-1. Stick to docker compose ... commands and you rarely need container names.

depends_on vs a healthcheck. Plain depends_on only controls start order: "start kafka-1 before order-api". It does not wait until Kafka can serve requests. Waiting for readiness needs a healthcheck plus condition: service_healthy. Kubernetes has no start order at all; there a readiness probe decides when a pod gets traffic, and apps must retry their connections (page 04).

How to read a partition row: Leader is the broker id that takes reads and writes for that partition. Replicas are the three brokers holding a copy (the first is the "preferred" leader). Isr are the copies that are caught up right now; all three is healthy. Elr (eligible leader replicas) is a newer Kafka feature and is empty when everything is in sync. Notice the leaders are spread: each broker leads two of the six partitions. Your exact assignment will differ.
