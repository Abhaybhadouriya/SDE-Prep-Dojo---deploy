Your order_id is a fresh random UUID and the partition can be any of 0 to 5. The important part: send the same command again. The partition stays the same (same key, same partition), and the offset goes up by one. You just watched an append-only log grow.

{"order_id":"9b0e...","status":"ACCEPTED","partition":3,"offset":1}
{"order_id":"1c7d...","status":"ACCEPTED","partition":3,"offset":2}

Now change C-42 to C-7 and send it. Probably a different partition, starting at its own offset 0. Offsets are numbered per partition, not per topic.

A FastAPI gotcha worth knowing. An earlier version of this code set response.headers["Retry-After"] on the injected Response object and then raised HTTPException. That header was never sent: headers on the injected response are only used when the handler returns normally. A raised exception builds a brand-new error response, so headers must be passed to the exception itself. Check it with curl -i, which prints response headers.

produce() only puts the record into the client's memory buffer and returns at once. librdkafka sends it in the background, and calls on_delivery when the broker has acknowledged (with acks=all, after the in-sync followers have it). Delivery callbacks only fire from poll(), so the API runs a small background thread that calls producer.poll(0.1) forever. The request thread waits on a threading.Event until the callback fires, up to 10 s. That is why the response can include the real partition and offset.

Try the API docs page. FastAPI generates an interactive page at localhost:8000/docs (only while the stack is running). You can send orders from the browser. /healthz says the process is alive; /readyz says it can reach Kafka metadata for orders.created.
