A tour of the compose file

Before you run it, spend five minutes reading what it will do. Here are the parts that matter most.

Shared settings with YAML anchors

The three brokers share almost everything. Instead of copying it three times, the file defines it once with an anchor (&kafka-env) and merges it with <<: *kafka-env. Here is the real block:

x-kafka-env: &kafka-env
  # KRaft "combined" mode: every node is a broker AND a controller (no ZooKeeper).
  KAFKA_PROCESS_ROLES: broker,controller
  CLUSTER_ID: ${KAFKA_CLUSTER_ID:-5L6g3nShT-eMCtK--X86sw}
  KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka-1:29093,2@kafka-2:29093,3@kafka-3:29093
  KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
  KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
  KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT
  # Durability defaults (topics-init also sets min.insync.replicas per topic).
  KAFKA_DEFAULT_REPLICATION_FACTOR: 3
  KAFKA_MIN_INSYNC_REPLICAS: 2
  KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 3
  KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 3
  KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 2
  KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"   # typos must fail loudly, not create topics
  KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
  KAFKA_LOG_DIRS: /var/lib/kafka/data
  KAFKA_HEAP_OPTS: -Xms512m -Xmx512m

The official apache/kafka image turns every KAFKA_* environment variable into a line of the broker's server.properties: KAFKA_MIN_INSYNC_REPLICAS becomes min.insync.replicas. CLUSTER_ID is used to format the storage directory the first time. The internal topics that hold consumer offsets and transaction state also get replication factor 3, so the enricher's transactions survive a broker loss too.

Three listeners per broker (the classic Kafka-in-Docker trap)

  kafka-1:
    <<: *kafka-common
    hostname: kafka-1
    ports: ["9092:9092"]
    environment:
      <<: *kafka-env
      KAFKA_NODE_ID: 1
      KAFKA_LISTENERS: INTERNAL://:19092,EXTERNAL://:9092,CONTROLLER://:29093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka-1:19092,EXTERNAL://localhost:9092
    volumes: ["kafka1-data:/var/lib/kafka/data"]

Why three? A Kafka client only uses the bootstrap address to discover the cluster. The broker then replies with metadata: "partition 3's leader is at this address". That address is the advertised listener. If the broker advertised kafka-1:19092 to your laptop, your laptop could not resolve kafka-1; if it advertised localhost:9092 to a container, the container would try to connect to itself. So each audience gets its own listener with an address that works from where it sits.

From your world

Advertised listeners are like the BGP next-hop attribute. The bootstrap connection is the session that hands you routes; the advertised address is the next hop you must actually reach. A perfectly good route with an unreachable next hop is useless, and that is exactly the symptom: the first connection works, then produce or consume calls time out. Where it breaks: Kafka has no recursive resolution; the client must reach the advertised host:port directly.

Start order with healthchecks

x-kafka-common: &kafka-common
  image: ${KAFKA_IMAGE:-apache/kafka:4.3.2}
  restart: unless-stopped
  healthcheck:
    test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:19092 > /dev/null 2>&1"]
    interval: 10s
    timeout: 10s
    retries: 12
    start_period: 20s

x-app-depends: &app-depends
  topics-init:
    condition: service_completed_successfully
  1. Brokers and Postgres start. Each broker formats its data volume on first run (using CLUSTER_ID), then the three controllers elect a Raft leader. Postgres starts and, only the first time its volume is created, runs db/init.sql (tables + 8 products).
  2. Healthchecks turn green. Every 10 s Compose runs kafka-broker-api-versions.sh inside each broker. "Started" is not "ready": a JVM can be up long before it can serve requests. Postgres uses pg_isready.
  3. topics-init runs. It waits for all three brokers to be healthy (condition: service_healthy), then runs create-topics.sh, which creates the four topics with --if-not-exists and prints a describe of orders.created.
  4. topics-init exits 0. A one-shot container, like an init script. Its success is the signal for the next wave.
  5. The services start. Each has condition: service_completed_successfully on topics-init, so no service ever sees a missing topic. The enricher and sink also wait for Postgres to be healthy.
  6. The tools start. kafka-ui and kafka-exporter also wait for topics-init. Prometheus scrapes every 10 s; Grafana loads the provisioned dashboard.
