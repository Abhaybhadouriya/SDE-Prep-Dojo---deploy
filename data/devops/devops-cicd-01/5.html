Rebase: replay your commits on a new base

Must know (SDE-1)

git rebase main (run on your feature branch) finds the merge base, takes each of your commits after it as a patch, and replays them one by one on top of the current main. The result looks as if you had started your work today. Because each replayed commit has a new parent, each gets a new hash: D becomes D', E becomes E'.

  1. You branched from B and made commits D and E on feature/login.
  2. Meanwhile someone merged C into main. Your branch is now "behind".
  3. You run git rebase main. Git finds the merge base (B) and turns D and E into patches.
  4. Git applies D's change on top of C, creating a new commit D' (same change, new parent, new hash).
  5. It applies E on top of D', creating E'. The old D and E are no longer on any branch; the reflog still remembers them.
  6. Now main can fast-forward to E'. History is a single straight line: A, B, C, D', E'.
git switch feature/login
git fetch origin
git rebase origin/main
Successfully rebased and updated refs/heads/feature/login.
# the branch was already pushed, so the remote still has the old D and E
git push --force-with-lease --force-if-includes      # Git 2.30+
# or name the exact commit you expect to overwrite:
git push --force-with-lease=feature/login:9f3c2e1
To github.com:acme/shop.git
 + 9f3c2e1...c41e0b7 feature/login -> feature/login (forced update)

--force-with-lease overwrites the remote branch only if it still points where your remote-tracking ref (origin/feature/login) says it does. Plain --force has no check at all. But a bare lease is weaker than it looks: the git fetch above (or your IDE's background auto-fetch) moves that tracking ref to include a teammate's new commit, so the lease "matches" and their commit is overwritten anyway even though you never integrated it. Add --force-if-includes (Git 2.30+): it also checks that the remote tip you are replacing is already part of your local branch's history, so a fetched-but-not-integrated commit makes the push fail. The other safe form is an explicit lease, --force-with-lease=<branch>:<sha you expect>. Many teams set git config --global push.useForceIfIncludes true.

The golden rule of rebasing: do not rebase commits that other people have already based work on. Rebase your own local or personal branch freely; never rebase main or a shared branch. If you do, everyone else's history still has the old hashes, and the next pull creates duplicate commits and painful conflicts.

From your world

Rebase is exactly what kernel developers do when they respin a patch series on the latest -rc: export the series as patches, check out the new base, apply them one by one (git format-patch then git am, or quilt push). The patches are the same changes, but they are new commits. And the golden rule matches mailing-list etiquette: once a maintainer has pulled your branch into their tree, you never rewrite it; you send fixes on top.
