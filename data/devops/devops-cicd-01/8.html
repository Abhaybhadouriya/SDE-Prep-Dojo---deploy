Conflicts: what they are and how to resolve them

Must know (SDE-1)

A conflict happens when both sides changed the same lines (or one side changed a file the other deleted) since the merge base. Git cannot pick, so it stops and writes both versions into the file with markers:

$ git merge feature/login
Auto-merging src/config.py
CONFLICT (content): Merge conflict in src/config.py
Automatic merge failed; fix conflicts and then commit the result.
<<<<<<< HEAD
TIMEOUT_SECONDS = 10
=======
TIMEOUT_SECONDS = 30
RETRIES = 3
>>>>>>> feature/login
  1. Understand both intents. Why did main change it to 10? Why did the feature want 30? Read the commits (git log -p --merge), and ask the other author if unsure.
  2. Edit to the correct result and remove every marker line.
  3. Mark resolved and continue. Merge: git add src/config.py then git commit. Rebase: git add then git rebase --continue. Changed your mind: git merge --abort or git rebase --abort.
  4. Run the tests. A textually clean merge can still be wrong.

"Ours" and "theirs" swap during a rebase. In a merge, --ours is the branch you are on. In a rebase, git is replaying your commits onto main, so --ours is main (the new base) and --theirs is your commit being replayed. Read the markers, not your memory.

Tips that cut conflict pain: merge or rebase from main often (small conflicts are easy), keep PRs small, avoid "format the whole file" commits mixed with logic changes, and turn on git config --global rerere.enabled true ("reuse recorded resolution") so git remembers how you solved a conflict and replays the fix if the same conflict comes back on the next rebase.
