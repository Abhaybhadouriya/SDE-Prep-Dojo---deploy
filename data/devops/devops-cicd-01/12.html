Interview questions

What is the difference between git merge and git rebase?

Both integrate changes from one branch into another. Merge creates a merge commit with two parents (or fast-forwards), keeps all existing commits and their hashes, and records when branches joined. Rebase replays your commits as patches on top of the other branch, producing new commits with new hashes and a linear history. Merge is safe anywhere; rebase rewrites history, so only use it on commits nobody else has built on.

How to answer

Draw the graph before and after for both. Then state the golden rule and your team policy (rebase locally, squash or rebase-merge PRs).

Likely follow-ups
  • Why do rebased commits get new hashes? (The parent is part of the hashed content.)
  • What does --force-with-lease protect against, and why add --force-if-includes? (A teammate's push you have not fetched. After a fetch, a bare lease passes anyway; --force-if-includes also requires that the remote tip is in your local history.)
What is the golden rule of rebasing, and what goes wrong if you break it?

Do not rebase commits that exist outside your own repository and that others may have based work on. If you rebase a shared branch and force-push, everyone else still has the old commits. When they pull, git sees two different histories with the same changes, so they get duplicate commits or conflicts, and if they force-push back, your rewrite or their work can be lost.

How to answer

Explain via hashes: same change, different commit IDs, so git cannot tell they are the same.

Likely follow-ups
  • How do you recover a teammate's branch after someone force-pushed over it? (Their local reflog, or the old SHA from CI logs or the PR timeline.)
Trunk-based development or GitFlow: which would you choose and why?

It depends on how the product ships. For a web service with continuous delivery, trunk-based: one main branch, short-lived branches, feature flags for unfinished work, small frequent merges, and a release is just a deploy of main. For installed or embedded software that supports several released versions at once, a GitFlow-like model with release and maintenance branches makes sense, because you must patch v1.4 while v2.0 is being built.

How to answer

Tie the choice to release cadence and number of supported versions, not to taste.

Likely follow-ups
  • How do you ship half-built features in trunk-based? (Feature flags, dark launches.)
  • How do hotfixes work in each model?
Why squash commits before merging, and when should you not?

Squashing turns many WIP commits into one meaningful commit, so main reads as one line per change, reverts are one command, and bisect lands on complete, buildable changes. Do not squash when a branch holds several logically separate changes (a refactor plus a feature) that you would want to bisect or revert separately; keep those as clean separate commits or separate PRs.

How to answer

Mention both ways: git rebase -i with fixup/squash (and --autosquash), and the platform's squash merge.

Likely follow-ups
  • What happens if you keep working on a branch after it was squash-merged?
Walk me through resolving a merge conflict safely.

Read the conflict markers, understand why each side changed the lines (log of both sides since the merge base), edit to the correct combined result, remove markers, git add, then commit (merge) or git rebase --continue. Then build and run tests, because a resolution can compile and still be wrong. If it gets messy, abort and retry, or talk to the other author. Prevent conflicts with small PRs, frequent syncs, and rerere for repeated ones.

How to answer

Emphasise understanding intent, not picking a side blindly, and testing the result.

Likely follow-ups
  • Why are "ours" and "theirs" reversed during a rebase?
Both PRs passed CI, both merged cleanly, and main is broken. How? How do you prevent it?

A semantic conflict: each PR was tested against an older main, not against main plus the other PR (for example, one renamed a function, the other added a call to the old name). Prevent it with a merge queue: PRs are tested in order on a temporary branch of latest main plus the PRs ahead of them, and main only advances to tested states. A lighter option is the "require branch to be up to date before merging" rule, which works for low merge rates but makes everyone rebase and re-run CI repeatedly when busy.

How to answer

Name the failure (semantic conflict), then the fix (merge queue), then its cost (CI capacity, queue latency) and how it batches to scale.

Likely follow-ups
  • How does the queue handle a failure in the middle? (Remove that PR, rebuild and retest the ones behind it.)
  • What CI change does GitHub's merge queue need? (Trigger on merge_group.)
A bad commit is on main and already pulled by everyone. How do you undo it?

Use git revert <sha>, which adds a new commit that reverses the change; push it through the normal PR flow. Do not use reset plus force-push on a shared branch. For a merge commit, git revert -m 1 <merge-sha> keeps the mainline parent. Remember that reverting a merge means re-merging the same branch later will not bring those changes back unless you revert the revert.

How to answer

Contrast revert (forward, safe) with reset (rewrite, local only).

Likely follow-ups
  • The bad commit leaked a password. Is revert enough? (No: rotate the secret; history still contains it.)
What exactly is a branch in git, and what is HEAD?

A branch is a named pointer to a commit, stored as a small ref holding the commit hash; committing moves it forward. HEAD normally points to the current branch (a symbolic ref); in "detached HEAD" it points straight at a commit. Creating a branch is therefore cheap: it copies nothing but a hash.

How to answer

Show cat .git/HEAD and the ref file. Concrete beats abstract.

Likely follow-ups
  • What happens to commits made in detached HEAD when you switch away? (They become unreachable; the reflog can save them.)
Production needs a hotfix today, and main already has unreleased work. Where do you commit first?

Fix on main first (or on a short branch merged to main), then cherry-pick the commit with git cherry-pick -x onto the release or hotfix branch cut from the tag that is in production, build that branch and deploy it. Committing only on the hotfix branch risks the fix silently disappearing in the next release. If the code on main has drifted so far that the fix does not apply, write the backport by hand and reference the main commit. With trunk-based delivery and feature flags there is often no release branch: you merge the fix to main, keep the unfinished work behind its flag, and deploy main.

How to answer

Say "upstream first, then backport", name cherry-pick -x, and mention the tag of the running version as the base for the hotfix branch.

Likely follow-ups
  • What if the fix conflicts on the release branch? (Resolve it there, keep -x, and note what differs in the message.)
  • How do you make sure the hotfix reaches main if someone did commit it on the release branch first? (Merge or cherry-pick the release branch back; some teams automate a check.)

Scenario: a teammate force-pushed over my branch

You and a teammate both pushed to feature/checkout. This morning your last two commits are gone from the remote: they rebased and ran git push --force.

Weak answer: "Rewrite the two commits from memory."

Strong answer: Nothing is lost while my clone has it. First stop further pushes and tell the teammate. In my clone, git reflog (or git log origin/feature/checkout@{1}, the remote-tracking reflog) shows my old tip. I create a rescue branch at it, rebase my two commits onto the new remote tip (git rebase --onto origin/feature/checkout <old-base> rescue) or cherry-pick them, test, and push normally. If no clone has the commits, the hosting platform often keeps the old SHA (GitHub shows it in the PR timeline and it can still be fetched for a while). Then fix the process: protect shared branches against force pushes, and use --force-with-lease --force-if-includes on personal ones.

Likely follow-ups
  • Why did --force-with-lease not save us? (It may have, if used; a bare lease after a fetch still overwrites fetched-but-unintegrated commits.)
  • How long does the reflog keep entries? (By default 90 days for reachable entries, 30 days for unreachable ones.)
