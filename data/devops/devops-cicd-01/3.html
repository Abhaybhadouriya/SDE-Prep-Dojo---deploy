Branching models: trunk-based vs GitFlow

Must know (SDE-1)

A branching model is the team's agreement about which long-lived branches exist and how work flows between them.

Trunk-based developmentGitFlow
Long-lived branchesJust mainmain, develop, plus release and hotfix branches
Feature branch lifeHours to a couple of daysDays to weeks
Unfinished workMerged behind feature flagsStays on its branch
Merge painSmall and frequentLarger, less frequent ("merge hell" risk)
Best forWeb services with continuous deliveryInstalled software with several supported versions, scheduled releases

Most companies that deploy many times a day use trunk-based development (or "GitHub flow", which is trunk-based with PRs). Even the author of the original GitFlow post later added a note saying that for continuously delivered web apps, a simpler flow is usually better. In an interview, say which you would pick and why, tied to how the product ships.

From your world

GitFlow looks like the classic network OS release train: a development mainline, release branches that get only fixes, and maintenance branches for each shipped version. That is the right tool when customers run v7.2 for years. A SaaS service that deploys every hour has only one version in production, so it needs only one trunk.

Backports: cherry-pick a fix to a release branch

With release or hotfix branches you often need one fix in two places. The rule most teams use: fix on main first, then backport, so the fix can never be lost in the next release. git cherry-pick applies the change from one existing commit onto the branch you are on, as a new commit.

git switch release/1.4
git cherry-pick -x 7c1d2e9          # -x adds "(cherry picked from commit 7c1d2e9...)"
git push origin release/1.4
[release/1.4 a83f0b2] Fix rounding in refund total
 Date: Mon Nov 23 11:40:02 2026 +0530
 1 file changed, 3 insertions(+), 1 deletion(-)

From your world

This is exactly how the stable and longterm kernel trees work: a fix lands in mainline first with a Fixes: tag and Cc: stable@vger.kernel.org, and the stable maintainers cherry-pick it into each supported branch. -x is the same idea as the "commit <sha> upstream" line in a stable backport.

Two everyday settings while you are here: git config --global pull.rebase true makes git pull rebase your local commits on top of the fetched branch instead of creating "Merge branch 'main' of ..." commits, and rerere.enabled true remembers how you resolved a conflict so the next rebase reuses it.
