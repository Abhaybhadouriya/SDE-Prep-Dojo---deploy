Merge queues: when green PRs still break main

Good to know (SDE-2)

PR #1 and PR #2 are both green against yesterday's main. #1 renames a function; #2 adds a new call to the old name. Neither conflicts in text, both merge, and main is now broken. This is a semantic conflict, and it gets more likely as the number of merges per hour grows.

A merge queue fixes it. Instead of merging directly, an approved PR joins a queue. The queue builds a temporary branch made of the latest main plus every PR ahead of it plus this PR, runs the required checks on that combination, and only fast-forwards main if it passes. On GitHub those temporary branches are named gh-readonly-queue/main/..., and GitHub Actions workflows must listen for the merge_group event or the required checks never report.

From your world

A merge queue is a serialising lock with speculative execution: it decides an order (like a sequencer), then tests several future states in parallel, the way a CPU speculates down a path and throws the work away if the branch was mispredicted. When a PR fails, everything queued behind it is "flushed" and re-tested, just like a pipeline flush.

This is the developer-facing half of the CI/CD platform design: the queue is where source control meets the build farm, and its throughput (merges per hour) is a real capacity-planning number.
