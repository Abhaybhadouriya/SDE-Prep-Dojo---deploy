Quick quiz

Why do commits get new hashes after a rebase?

  1. Git adds a random salt each time
  2. Each commit's parent changed, and the parent is part of what is hashed
  3. The file contents always change
  4. Rebase compresses commits differently
Same change, new parent, so a new commit object and a new hash.

Which command is safe to undo a bad commit that is already on a shared main branch?

  1. git reset --hard HEAD~1 then force-push
  2. git rebase -i and drop it
  3. git revert <sha>
  4. git checkout -- .
Revert adds a new commit that undoes the change, so nobody's history is rewritten.

Your team deploys a web service 20 times a day with one version in production. Which branching model fits best?

  1. Trunk-based development with feature flags
  2. GitFlow with develop and release branches
  3. One long-lived branch per developer
One live version and continuous delivery: one trunk, short branches, flags for unfinished work.

What does git push --force-with-lease add over --force?

  1. It pushes faster
  2. It also pushes tags
  3. It squashes commits first
  4. It refuses if the remote branch no longer matches your remote-tracking ref
It protects pushes you have not fetched. It does not protect commits you fetched but never integrated (a fetch moves the ref it compares against), which is why you add --force-if-includes or name the expected SHA.

During git rebase main, a conflict appears. What does --ours refer to?

  1. Your feature commit being replayed
  2. The new base (main side)
  3. The merge base
  4. The remote branch
Rebase checks out the new base and applies your commits onto it, so "ours" is the base and "theirs" is your commit.

Two PRs each pass CI and merge without textual conflicts, yet main fails to build. What prevents this?

  1. Squash merging
  2. Longer code reviews
  3. A merge queue that tests main plus the queued PRs together
  4. Using GitFlow
The PRs were tested against different, older bases. A merge queue tests the exact future state of main.

You squash-merged PR #1 and kept committing on the same branch for PR #2. Why do you get conflicts?

  1. Main contains a new squashed commit with a different hash, so git does not see your old commits as already merged
  2. Git forbids two PRs from one branch
  3. Squash merges delete the branch on the server
The changes are in main, but under a different commit. Start PR #2 from fresh origin/main.
