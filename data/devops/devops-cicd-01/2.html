The team loop: feature branch, pull request, review

Must know (SDE-1)
  1. Branch. git switch -c feature/login origin/main. One branch per change, small and short-lived.
  2. Commit. Small commits with clear messages. Messy work-in-progress (WIP) commits are fine locally; you can clean them up later.
  3. Push and open a PR. git push -u origin feature/login, then open a pull request against main.
  4. Automated checks. CI builds and tests the PR. A protected branch rule can require green checks before anything merges.
  5. Review. At least one teammate reads the diff, asks questions, approves. Code owners can be required for sensitive paths.
  6. Merge. The platform merges with the method the repo allows: merge commit, squash, or rebase. Then delete the branch.

Small PRs get reviewed faster and more carefully. A 50-line PR gets real comments; a 2,000-line PR gets "looks good to me". Split big work behind a feature flag so you can merge pieces early.

From your world

If you have sent kernel patches, you already know this loop: a topic branch, a patch series, review on the mailing list, a maintainer applying it to their tree. A PR is that review thread in a web UI, and "required checks" is the bot that builds your series against several configs before a human reads it.
