OverlayFS: how the stack becomes one folder

The kernel needs to show the container one normal root filesystem, even though the files live in many layer folders. The tool for that is OverlayFS, a union filesystem built into Linux. Docker's classic storage driver for it is called overlay2; with the containerd image store (the default for fresh installs since Docker Engine 29) containerd's overlayfs snapshotter does the same job.

  • lowerdir: the read-only image layers, stacked. Up to 128 of them natively.
  • upperdir: the container's writable layer.
  • workdir: a scratch folder OverlayFS needs for atomic operations.
  • merged: the combined view. This becomes the container's /.
  1. Read. The container opens config.ini. OverlayFS looks in upperdir, does not find it, and serves it straight from the read-only lower layer. No copy, no cost.
  2. First write = copy-up. The app writes one byte to app.db. OverlayFS first copies the whole file up into upperdir, then lets the write happen there. It is file-level, not block-level: a 1 GB file means a 1 GB copy before the first write returns.
  3. Delete = whiteout. The app deletes old.log. The lower file cannot be removed (it is read-only and shared), so OverlayFS puts a whiteout marker, a character device with number 0/0, in upperdir. The merged view now hides the file, but the lower copy still exists.
  4. Remove the container. docker rm deletes upperdir. The image layers are untouched, ready for the next container. This is why the tracing-paper story works.

From your world

If you have worked on embedded routers or access points, you already know this design: OpenWrt boots a read-only squashfs firmware image with a writable jffs2 overlay on top using the same overlayfs. "Factory reset" there means wiping the overlay, just like docker rm wipes upperdir. Where it breaks: Docker stacks many lower layers, and those layers are shared live between many containers at once.

Try OverlayFS by hand (Linux only)

No Docker needed. This is the kernel feature on its own.

mkdir -p /tmp/ov/{lower,upper,work,merged}
echo "from image" > /tmp/ov/lower/a.txt
echo "delete me"  > /tmp/ov/lower/b.txt
sudo mount -t overlay overlay \
  -o lowerdir=/tmp/ov/lower,upperdir=/tmp/ov/upper,workdir=/tmp/ov/work /tmp/ov/merged
echo "changed" | sudo tee /tmp/ov/merged/a.txt > /dev/null
sudo rm /tmp/ov/merged/b.txt
ls -l /tmp/ov/upper
cat /tmp/ov/lower/a.txt /tmp/ov/merged/a.txt
sudo umount /tmp/ov/merged
$ ls -l /tmp/ov/upper
total 4
-rw-r--r-- 1 root root    8 Nov 23 10:40 a.txt
c--------- 2 root root 0, 0 Nov 23 10:40 b.txt
$ cat /tmp/ov/lower/a.txt /tmp/ov/merged/a.txt
from image
changed

The lower file is unchanged. The changed copy lives in upper. And b.txt in upper is a character device with major/minor 0, 0: that is the whiteout. You just did by hand what Docker does for every container.

Find a real container's overlay

docker run -d --name web nginx:1.30
docker exec web sh -c 'echo hi > /tmp/note; rm /etc/nginx/conf.d/default.conf'
docker container diff web
mount | grep overlay | head -1 | tr ',' '\n' | head -5
$ docker container diff web
C /etc
C /etc/nginx
C /etc/nginx/conf.d
D /etc/nginx/conf.d/default.conf
C /tmp
A /tmp/note
...
$ mount | grep overlay | head -1 | tr ',' '\n' | head -5
overlay on /var/lib/docker/rootfs/overlayfs/8d3f1c2a9e4b... type overlay (rw
relatime
lowerdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/41/fs:...
upperdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/57/fs
workdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/57/work

docker container diff lists what is in the container's writable layer: A added, C changed, D deleted (a whiteout). The mount line shows the real lowerdir/upperdir/workdir. The exact paths depend on your setup: the containerd image store uses /var/lib/containerd/...snapshots, while the classic overlay2 driver uses /var/lib/docker/overlay2/<id>/diff. Run docker info | grep -i -A2 storage to see which one you have.
