Interview questions

The 60-second answer: "What are image layers and why do they matter?"
"An image is a stack of read-only layers plus a small JSON config. Each filesystem-changing build step, RUN, COPY or ADD, produces one layer, which is a tar of the files that changed, named by its SHA-256 hash. At run time the kernel's OverlayFS merges the layers into one root filesystem and adds a thin writable layer per container, using copy-on-write. Layers matter for three reasons: they are shared, so ten containers or fifty images reuse one copy on disk and over the network; they are cached, so rebuilds only redo steps after the first change; and they are append-only, so deleting a file in a later layer never makes the image smaller and never removes a leaked secret."

What is the difference between an image and a container?

An image is a read-only, layered template: files plus config such as the default command. A container is a running (or stopped) instance of an image: a process with namespaces and cgroups, plus its own writable layer on top of the image layers. Many containers can run from one image at the same time and share its layers.

How to answer

Use the analogy first (class vs object, or binary vs process), then the layer detail (shared read-only layers, one writable layer each), then one consequence (writes vanish on docker rm, so use volumes).

Likely follow-ups
  • Where exactly do a container's writes go?
  • Can you turn a container back into an image? (Yes, docker commit, but a Dockerfile is reproducible and preferred.)
What is an image physically on disk and in a registry?

Following the OCI Image Spec, it is a set of content-addressed blobs: an index listing per-platform manifests, a manifest per platform listing one config blob and the ordered layer blobs, a config JSON, and layer tarballs (usually gzip compressed). Everything is referenced by SHA-256 digest. A registry is an HTTP service implementing the OCI Distribution Spec, mainly GET /v2/<name>/manifests/<ref> and GET /v2/<name>/blobs/<digest>. On a host, layers are unpacked into snapshot directories that OverlayFS stacks.

How to answer

Draw the tree: index, manifest, config + layers. Say "content-addressed" early; it explains deduplication, integrity checks and why digests are immutable.

Likely follow-ups
  • What is the difference between a tag and a digest?
  • How does one tag support both amd64 and arm64?
Why should you not deploy the latest tag in production?

A tag is a movable pointer, and latest is just the default tag name, not "the newest version". If it moves between deploys, different servers can run different code under the same name, a restart can silently pick up a new version, and rolling back is ambiguous because you cannot say what "the previous latest" was. Use immutable tags, for example the git commit SHA plus a semantic version, and ideally deploy by digest so the exact bytes are pinned.

How to answer

Three problems (non-reproducible, silent drift, unclear rollback), one fix (immutable tag or digest), one practice ("build once, promote the same digest from staging to production").

Likely follow-ups
  • How would Kubernetes behave with imagePullPolicy: Always and latest?
  • How do you still get base image security patches if you pin digests? (Rebuild regularly with automated update tools.)
Explain copy-on-write in Docker. What is its performance cost?

Image layers are read-only lowerdirs; each container has a writable upperdir, and OverlayFS shows a merged view. Reads come straight from whichever layer has the file. The first write to a file from a lower layer triggers a copy-up of the entire file into the upperdir, which for large files is expensive and adds latency to that first write. Deletes create whiteout entries. The cost is mostly for write-heavy workloads on large files, like databases, so those should write to volumes, which bypass the overlay. Many small files and deep directory trees also make copy-up and lookups slower.

How to answer

Name the four dirs, then read vs first write vs delete, then the production rule (state on volumes). If you have a kernel background, mention that copy-up is file-granular, unlike page-level copy-on-write in fork(); interviewers like that contrast.

Likely follow-ups
  • Why does RUN rm in a later step not shrink the image?
  • What happens to page cache when many containers read the same file? (Shared, one copy.)
Image pulls are making deployments and autoscaling slow. What would you do?

First measure: image sizes, how many layers are already cached on nodes, and pull time versus start time. Then fix from cheapest to biggest: shrink images with multi-stage builds and slim bases; share a common base image across services so nodes already have most layers; put a registry mirror or pull-through cache in each region close to the nodes; pre-pull hot images onto new nodes. At large scale, use lazy-pulling snapshotters such as stargz or AWS SOCI so containers start before every byte arrives, or peer-to-peer distribution like Uber's Kraken or Dragonfly.

How to answer

Show you measure first, then give a ladder of fixes with their cost. Connecting it to autoscaling speed shows product thinking, not just Docker knowledge.

Likely follow-ups
  • How does Docker Hub's pull rate limit affect CI? (Unauthenticated pulls are limited per IP; log in or mirror.)
  • How would you keep the shared base image patched?

Scenario: "We deleted the leaked key, so we are safe, right?"

A developer notices an AWS access key was copied into an image with COPY .aws /root/.aws. They add RUN rm -rf /root/.aws as the next line, rebuild, push the new image with the same tag, and close the ticket.

Weak answer: "Good, the file is gone from the container, so the issue is fixed."

Strong answer: "No. Layers are append-only: the key is still inside the COPY layer, and anyone who pulls the image can extract it with docker save and tar. Also, the old image digests are still in the registry and in node caches. Steps: rotate the key immediately, because we must assume it leaked; delete the affected image digests from the registry; rebuild without the files, using a .dockerignore and build secrets mounted only during RUN; and add a secret scanner to CI. Root cause: credentials in the build context."

Likely follow-ups
  • How do you pass a private package token to a build safely?
  • How would you find other images with leaked secrets? (Scan registries with a secret scanner.)
