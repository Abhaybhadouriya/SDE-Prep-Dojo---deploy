Layer consequences that bite in production

1. Deleting in a later layer never shrinks the image

Because layers only add, a file created in one layer and deleted in the next is still shipped inside the first layer. The later layer only adds a whiteout.

FROM alpine:3.24
RUN dd if=/dev/zero of=/big.bin bs=1M count=50
RUN rm /big.bin
$ docker history fat-demo --format '{{.Size}}\t{{.CreatedBy}}'
0B      RUN /bin/sh -c rm /big.bin # buildkit
52.4MB  RUN /bin/sh -c dd if=/dev/zero of=/big.bin bs=1M count=50 # buildkit
0B      CMD ["/bin/sh"]
7.8MB   ADD alpine-minirootfs-3.24.x-x86_64.tar.gz / # buildkit

The image still carries 52 MB of zeros that no container can ever see. The fix is to create and delete in the same RUN step, or better, use a multi-stage build so temporary files never reach the final image. This also has a security side: a secret copied in one layer and deleted in the next is still readable by anyone who pulls the image. Uber's engineering team described exactly this "secrets stay in layers" problem as one reason they built their own image builder, Makisu.

2. Writes in the container layer are slow for big files

Copy-up copies whole files. A database that modifies a few pages of a 2 GB file inside the container layer pays a 2 GB copy on first write, and every later write goes through the overlay. Databases, queues like Kafka, and anything write-heavy should use a volume, which bypasses OverlayFS entirely.

3. Renaming directories across layers

Renaming a directory that lives in a lower layer can fail with EXDEV (the errno for a cross-filesystem rename, "cross-device link") on overlay, so applications must fall back to copy-and-delete. Most tools already do this, but some older software breaks in containers because of it.

4. Image size is a deploy-speed problem

Every new server, and every Kubernetes node that has not seen an image, must pull it before the container starts. A 1.5 GB image on a fresh node during an autoscaling burst means minutes of waiting. Shared base layers, small runtime images, and regional registry mirrors all help. At very large scale, companies use lazy-pulling snapshotters (such as stargz, or SOCI on AWS) that start the container before all layers arrive, or peer-to-peer distribution like Uber's Kraken.

5. Disk fills up quietly

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          23        4         6.1GB     4.8GB (78%)
Containers      6         2         310MB     290MB (93%)
Local Volumes   5         2         1.2GB     800MB (66%)
Build Cache     118       0         3.4GB     3.4GB

Old images, stopped containers and build cache pile up. docker image prune removes dangling images (layers with no tag, usually left behind when you rebuild a tag), docker builder prune clears build cache, and docker system prune does several at once. Removing a container never removes its image or its named volumes. (Numbers above are an example.)

Why layers are great
  • Pull and push only what changed
  • One copy on disk and in page cache for many containers
  • Build cache reuses unchanged steps
  • Content hashes make images tamper-evident
What layers cost you
  • Deletes never shrink an image
  • Secrets in any layer are forever
  • Copy-up makes big-file writes slow
  • Order of steps matters for the cache
