Image names, tags and digests

Before we look inside, learn to read an image's full name. When you type nginx, Docker silently fills in the parts you left out.

  • A tag is a human label like 1.30 or latest. Tags are movable: the owner can point nginx:1.30 at a newer build tomorrow (for a security patch, say).
  • A digest such as sha256:4f2c... is a hash of the image's manifest file (the small JSON "table of contents" that lists the image's config and layers). It can never change. If one byte of the image changed, the digest would change. Production systems should deploy by digest, or at least by a tag that the team never reuses.
  • latest is not magic and does not mean "newest". It is just the default tag name when you do not type one.

From your world

A digest is the SHA-256 checksum you verify before flashing a firmware image, and a tag is a symlink like current.bin -> fw-7.2.1.bin. You would never trust a symlink alone when upgrading 500 line cards; you check the hash. Same here. Where it breaks: the digest covers the manifest, which in turn lists the digests of every layer, so one hash pins the whole tree, like a Merkle tree rather than a single file checksum.

Pulling an image, and watching layers

docker pull python:3.12-slim
docker pull python:3.12-slim-trixie     # same image, a second tag (slim = Debian 13 "trixie" today)
docker images python
docker image inspect -f '{{.RepoDigests}}' python:3.12-slim
$ docker pull python:3.12-slim
3.12-slim: Pulling from library/python
a2318d6c47ec: Pull complete
40d734479f14: Pull complete
0b61b7b259eb: Pull complete
081a3493c0e7: Pull complete
Digest: sha256:...
Status: Downloaded newer image for python:3.12-slim
docker.io/library/python:3.12-slim
$ docker pull python:3.12-slim-trixie
3.12-slim-trixie: Pulling from library/python
Digest: sha256:...
Status: Downloaded newer image for python:3.12-slim-trixie

Each line like a2318d6c47ec: Pull complete is one layer (the short IDs and count you see will differ; images are rebuilt often). The second pull downloaded nothing new, because the two tags are aliases for the same image. (Careful: tag aliases change over time. 3.12-slim moved from Debian 12 "bookworm" to Debian 13 "trixie", so pulling 3.12-slim-bookworm today downloads a whole different set of layers. Check the tag list on the image's Docker Hub page.) When only some layers are shared, you see Already exists next to those and Docker fetches only the rest. This is the first big win of layers: you never download the same layer twice.

Looking at the layers of an image

Make a tiny image so the layers are easy to read. Create a folder with these two files and build it (the next page explains every Dockerfile line).

# Dockerfile
FROM alpine:3.24
RUN apk add --no-cache curl
COPY hello.txt /hello.txt
CMD ["cat", "/hello.txt"]
echo "hi from a layer" > hello.txt
docker build -t layers-demo .
docker history layers-demo
$ docker history layers-demo
IMAGE          CREATED          CREATED BY                                      SIZE      COMMENT
4b1d0e6c2f3a   10 seconds ago   CMD ["cat" "/hello.txt"]                        0B        buildkit.dockerfile.v0
<missing>      10 seconds ago   COPY hello.txt /hello.txt # buildkit            16B       buildkit.dockerfile.v0
<missing>      12 seconds ago   RUN /bin/sh -c apk add --no-cache curl # bui…   5.2MB     buildkit.dockerfile.v0
<missing>      3 weeks ago      CMD ["/bin/sh"]                                 0B
<missing>      3 weeks ago      ADD alpine-minirootfs-3.24.x-x86_64.tar.gz /    7.8MB

Read it from the bottom up, like the sticker stack. The Alpine base adds about 8 MB of files. RUN apk add adds a layer with curl and its libraries. COPY adds a 16-byte layer with our text file. CMD adds 0 bytes: it is not a filesystem layer at all, just a setting in the image's config. Only RUN, COPY and ADD create real filesystem layers (WORKDIR can add a tiny one when it has to create the directory). (<missing> just means those steps have no separate local image ID; it is normal. Sizes here are approximate.)
