What an image physically is

The learner question was: "Is an image a tarball? A filesystem? Many filesystems?" The honest answer: an image is a few small JSON files plus a list of tarballs, all named by their SHA-256 hash. The format is an open standard, the OCI Image Spec, which is why images built by Docker run on Podman, containerd and Kubernetes. Fly.io's engineering blog puts it memorably: an OCI image is "just a stack of tarballs".

  • Index (also called a manifest list): "this tag has builds for amd64 and arm64; here are their manifests." This is how one tag works on both an Intel server and an Apple Silicon Mac.
  • Manifest: "for this platform, the config is blob X and the layers are blobs A, B, C, in this order."
  • Config: a JSON file with the default command, environment variables, working directory, user, exposed ports, the build history, and the list of uncompressed layer hashes (diff_ids).
  • Layers: tar archives (usually gzip, sometimes zstd compressed) of the files that changed in that step. Each one is just a normal tar file you could open with tar -t.

Prove it: open an image with tar

docker save layers-demo -o layers-demo.tar
mkdir demo && tar -xf layers-demo.tar -C demo
ls demo
cat demo/index.json | python3 -m json.tool | head -20
ls demo/blobs/sha256 | head
$ ls demo
blobs  index.json  manifest.json  oci-layout
$ ls demo/blobs/sha256 | head -4
0c5a1c8a9d2f...
3b18e5124e5a...
8e1d0f2a6c44...
c9e2d4b1f7a3...
$ tar -tf demo/blobs/sha256/8e1d0f2a6c44...
hello.txt

The layer created by COPY hello.txt is literally a tar file containing one file. Your hashes will differ, and on older Docker versions without the containerd image store (where containerd, the container runtime under dockerd that page 08 explains, keeps the images) the layout of docker save output looks slightly different, but the idea is the same.

The registry is an HTTP file server for blobs

A registry (Docker Hub, GitHub's GHCR, Amazon ECR, Azure ACR, Google Artifact Registry, self-hosted Harbor) speaks a small HTTP API defined by the OCI Distribution Spec. Two URLs do most of the work: GET /v2/<name>/manifests/<tag or digest> and GET /v2/<name>/blobs/<digest>. You can talk to Docker Hub with plain curl:

TOKEN=$(curl -s "https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/alpine:pull" | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" \
     -H "Accept: application/vnd.oci.image.index.v1+json" \
     https://registry-1.docker.io/v2/library/alpine/manifests/3.24 \
  | jq -r '.manifests[] | "\(.platform.architecture)\t\(.digest)"' | head -4
amd64   sha256:...
arm     sha256:...
arm     sha256:...
arm64   sha256:...

From your world

A registry is the TFTP/HTTP server you pull line-card firmware from, but content-addressed: files are named by their hash, so the client asks "do you have sha256:a231...?" and skips anything it already holds. Pushes use a HEAD request per blob to skip uploads too. Where it breaks: firmware is one big file; an image is a tree of many blobs, so updating one small layer means re-sending only that layer, not the whole image.

Step by step: what a pull does

  1. Ask for the tag. The client (dockerd, or containerd underneath it) authenticates and requests the manifest for library/python:3.12-slim.
  2. Pick your platform. The registry returns an index. The client chooses the manifest that matches its OS and CPU, for example linux/amd64, and fetches it by digest.
  3. Fetch the config. The small config blob arrives: the default command, environment, and the list of layer hashes.
  4. Fetch only missing layers. Layers already on disk are shown as Already exists and skipped. Missing ones download in parallel.
  5. Verify and unpack. Each blob's SHA-256 is checked against its name, so a corrupted or tampered download is rejected. Layers are then unpacked into snapshot directories (one unpacked folder per layer) ready for OverlayFS.

This answers the Mac vs server question. If you build on an Apple Silicon Mac, you get a linux/arm64 image with only one manifest. An x86 server pulling it finds no amd64 manifest (or runs the wrong one and fails with exec format error). The fix is to build for the server's platform or publish a multi-platform index with docker buildx build --platform linux/amd64,linux/arm64. Swiggy described exactly this need when moving Kubernetes workloads to ARM-based AWS Graviton nodes. Page 09 covers multi-arch builds.
