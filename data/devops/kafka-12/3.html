RabbitMQ: the smart post room

RabbitMQ speaks AMQP 0-9-1 (and other protocols). Producers never write to a queue directly. They publish to an exchange with a routing key (a label such as order.created.india). The exchange looks at its bindings (rules like "queue india-orders wants order.*.india") and copies the message into every matching queue. Consumers subscribe to queues and the broker pushes messages to them.

There are four exchange types:

  • direct - deliver where the binding key equals the routing key exactly.
  • topic - pattern match on dotted words: * = exactly one word, # = zero or more words.
  • fanout - copy to every bound queue, ignore the key (broadcast).
  • headers - match on message header values instead of the key.

Click through to follow one message.

  1. Publish. The producer sends the message to an exchange with routing key order.created.in. It does not know any queue names.
  2. Route. The topic exchange checks bindings. order.*.in matches, # matches everything, order.*.us does not. The message is copied into two queues.
  3. Push. RabbitMQ pushes messages to subscribed consumers, limited by the consumer's prefetch count (how many un-acked messages it may hold).
  4. Ack. When the consumer acks, RabbitMQ deletes the message from that queue. The copy in the other queue lives on independently.
  5. Failure. If the consumer's connection drops before acking, the message goes back to the queue and is redelivered (marked "redelivered"). So consumers must still be idempotent.

Try it locally

# RabbitMQ with the management UI on http://localhost:15672 (guest / guest, local only)
docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:4-management

# after ~10 seconds, list queues and exchanges from inside the container
docker exec rabbit rabbitmqctl list_exchanges name type
docker exec rabbit rabbitmqctl list_queues name messages consumers

The nameless exchange at the bottom is the default exchange: a direct exchange where every queue is automatically bound by its own name. That is why tutorials can "publish to a queue" - they are really publishing to the default exchange with the queue name as the key.

What RabbitMQ is great at

  • Routing logic in the broker. Patterns, broadcast, header matching, dead-letter exchanges, per-queue TTLs.
  • Per-message work distribution. Ten workers on one queue share the load; a slow message only slows one worker.
  • Priorities and delays (priority queues; delays via TTL + dead-letter tricks or a plugin).
  • Low latency at moderate volume with simple, familiar semantics.

Where it hurts

  • No replay for classic and quorum queues: once acked, it is gone. A new service cannot read last week's orders.
  • Big backlogs are painful. Queues are designed to be mostly empty; millions of waiting messages raise memory and disk pressure.
  • Ordering holds for one queue with one consumer; with many consumers, prefetch and redeliveries, it is not strict.

Modern RabbitMQ in one breath. Quorum queues are replicated with the Raft consensus algorithm and are the recommended durable queue type. RabbitMQ Streams add an append-only, replayable log inside RabbitMQ, so "RabbitMQ cannot replay" is only true for normal queues. Mentioning both shows you are current. Docs: quorum queues, streams.

From your world

The exchange is a classifier in a packet pipeline: match on a header field (the routing key), look up the binding table (like an ACL or a policy-based routing table), and replicate to N egress queues (like multicast replication). Prefetch is a credit-based flow control window, the same idea as PCIe credits or a TCP receive window: the broker may only push as many un-acked messages as the consumer has granted.

Where this breaks: a router drops packets on congestion; RabbitMQ stores them (in memory or on disk) and pushes back on publishers with flow control instead.
