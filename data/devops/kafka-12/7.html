Kafka-compatible engines: same API, different insides

The Kafka protocol has become a standard of its own, like SQL for databases. Several systems speak it so existing clients keep working:

  • Redpanda - a C++ broker with a thread-per-core design and a Raft group per partition; no JVM and no separate controller. Note from our research: its GitHub repository shows as archived (November 2026), though the product and docs are live. Check before calling it an "active open-source project".
  • "Diskless" designs such as AutoMQ, and Pinterest's in-house MemQ (not Kafka-compatible, but the same idea), keep data on object storage like S3. Pinterest reported large cost savings for some workloads at the price of higher latency. Kafka's own tiered storage is a middle ground: recent segments on local disk, older ones in object storage.
  • Azure Event Hubs and managed services (Amazon MSK, Confluent Cloud) - see above.

A strong SDE-2 line: "I would design against the Kafka API, because Kafka, MSK, Confluent, Event Hubs and Redpanda all speak it. That keeps the engine a deployment decision, not a code rewrite."
