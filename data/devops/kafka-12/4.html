Amazon SQS and SNS: the managed drop box

SQS (Simple Queue Service) is a queue that AWS runs for you. You never see a broker, a disk or a partition. Consumers pull with ReceiveMessage, process, then call DeleteMessage. The trick that makes it safe is the visibility timeout: when a consumer receives a message, SQS hides it from everyone else for a while (30 seconds by default, up to 12 hours). If the consumer deletes it in time, it is done. If the consumer crashes, the message becomes visible again and another consumer gets it.

  1. Send. The producer calls SendMessage. SQS stores it redundantly across machines; you do not see any of that.
  2. Receive. Worker 1 pulls the message. SQS hides it from other workers for the visibility timeout.
  3. Happy path. Worker 1 finishes and calls DeleteMessage. The message is removed for good.
  4. Crash. Worker 1 dies mid-job. Nobody deletes the message, and the timer runs out.
  5. Redelivery. The message is visible again and Worker 2 receives it. This is why SQS is "at-least-once": the same job can run twice.
  6. Dead-letter queue. A redrive policy moves a message that failed maxReceiveCount times into a DLQ for a human or tool to inspect.

Standard vs FIFO

  • Standard queues: very high throughput, best-effort ordering, and at-least-once delivery (occasionally a message is delivered twice).
  • FIFO queues: strict order within a message group (MessageGroupId, the SQS cousin of a Kafka key) and de-duplication within a 5-minute window. Throughput is lower: the research notes list 300 messages/s per API action without batching, 3,000 with batching, plus a "high throughput FIFO" mode with higher limits.

Useful limits from the SQS message quotas page (checked November 2026): retention defaults to 4 days, maximum 14 days; the maximum message size is 1 MiB (bigger payloads go to S3 with a pointer, the "claim check" pattern); per-message delay up to 15 minutes. Limits change, so check the page before quoting a number in a design doc.

SNS + SQS fan-out

SNS (Simple Notification Service) is pub/sub: you publish once to a topic and SNS pushes a copy to every subscriber (SQS queues, Lambda functions, HTTP endpoints, email, SMS). The classic AWS pattern is SNS → many SQS queues: each service gets its own durable queue with its own pace and its own DLQ.

# Works against real AWS (costs fractions of a cent) or LocalStack on localhost:4566 (add --endpoint-url)
QURL=$(aws sqs create-queue --queue-name resize-jobs --query QueueUrl --output text)
aws sqs send-message --queue-url "$QURL" --message-body '{"photo":81}'
aws sqs receive-message --queue-url "$QURL" --wait-time-seconds 10 --visibility-timeout 60
# receive again (after the 60 s visibility timeout) and keep the receipt handle this time
HANDLE=$(aws sqs receive-message --queue-url "$QURL" --wait-time-seconds 10 --visibility-timeout 60   --query 'Messages[0].ReceiptHandle' --output text)
aws sqs delete-message --queue-url "$QURL" --receipt-handle "$HANDLE"
$ aws sqs receive-message --queue-url "$QURL" --wait-time-seconds 10
{
    "Messages": [
        {
            "MessageId": "6b1c...e2",
            "ReceiptHandle": "AQEB...long-opaque-string...",
            "MD5OfBody": "...",
            "Body": "{\"photo\":81}"
        }
    ]
}

Notice that you delete with the receipt handle, not the message ID: the handle proves you are the one who received it this time. --wait-time-seconds turns on long polling, which avoids burning requests on an empty queue (and money, since you pay per request).

Careful: if your job takes longer than the visibility timeout, a second worker will pick up the same message while the first is still working. Either set the timeout above your worst-case job time or extend it with ChangeMessageVisibility as you go.
