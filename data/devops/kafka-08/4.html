What actually happens: creating a topic

good to know

Let us name every process involved when you run kafka-topics.sh --create --topic payments --partitions 3 --replication-factor 3.

  1. Client asks a broker. Admin clients normally talk to brokers (--bootstrap-server). They do not need to know where the controllers are.
  2. Forward. The broker forwards the request to the active controller over the controller listener.
  3. Decide. The controller validates the request, picks 3 replicas for each partition spread across racks, chooses initial leaders, and appends metadata records to __cluster_metadata.
  4. Replicate in the quorum. Standby controllers fetch the records. When a majority has them, they are committed.
  5. Brokers fetch. Every broker is continuously fetching the metadata log. They receive the new records in their next fetch.
  6. Act. Each broker applies the change to its in-memory metadata image. Brokers named as replicas create the partition folders; leaders start accepting writes and followers start fetching. The response flows back to the admin client.

What happens when a broker dies

This is a favourite interview question. Here are the exact mechanics in KRaft:

  1. Heartbeats stop. Each broker sends a BrokerHeartbeat to the active controller every broker.heartbeat.interval.ms (default 2 s). The heartbeat renews the broker's lease.
  2. Lease expires and the broker is fenced. If no heartbeat arrives for broker.session.timeout.ms (default 9 s), the controller marks the broker as fenced (not allowed to lead) by writing a record to the metadata log. A clean shutdown is faster: the broker tells the controller it is leaving and leadership moves first ("controlled shutdown").
  3. New leaders are chosen. For every partition the dead broker led, the controller picks a new leader from the ISR (or, with Eligible Leader Replicas, from the ELR) and writes PartitionChangeRecords with a bumped leader epoch. Unclean election (a stale replica) happens only if you allowed it. Details in Replication & ISR.
  4. Brokers apply it. Surviving brokers fetch those records and become leaders or followers. Producers and consumers get "not leader" errors, refresh their metadata from any broker and retry against the new leader.
  5. Under-replicated partitions. Until the dead broker returns (or its replicas are reassigned), those partitions have fewer copies. UnderReplicatedPartitions > 0 is the alert. When it comes back, it catches up from the leaders and rejoins the ISR.

Interview trap: "So if a broker dies, Kafka switches leaders instantly?" Say: "No. On a hard crash there is a detection delay, roughly the broker session timeout (9 seconds by default), then the controller elects new leaders from the in-sync replicas and brokers learn it from the metadata log. Clients see a short spike of retries. A planned shutdown is much faster because leadership is moved first."

What happens when a controller dies

  • A standby dies: nothing visible happens as long as a majority remains. Replace it.
  • The active controller dies: standbys detect it within about the fetch timeout (default 2 s) and elect a new leader. Because they already have the log, the new active controller starts working right away; there is no "load everything from ZooKeeper" step.
  • The quorum loses its majority (for example 2 of 3 down): brokers keep serving existing partitions with their current leaders, but no metadata can change. No new topics, no leader elections. If a broker then dies too, its partitions stay offline until the quorum is back. This is why controllers go in separate failure domains.

Snapshots keep the log small

The metadata log would grow forever, so controllers and brokers periodically write a snapshot (a full picture of the metadata at some offset, stored as a .checkpoint file) and older log segments can be deleted. A new snapshot is generated after a set amount of new log data (metadata.log.max.record.bytes.between.snapshots, 20 MiB by default) or after a time interval. A restarting broker loads the latest snapshot and replays only the records after it, which is why restarts are faster than in the ZooKeeper era.
