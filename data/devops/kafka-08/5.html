Lab: run and inspect a KRaft cluster

good to know

Option A: one combined node (laptop)

The official image starts a single combined broker+controller with sensible defaults. This is the quickest way to poke at metadata.

docker run -d --name kafka -p 9092:9092 apache/kafka:4.4.0

docker exec -it kafka /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server localhost:9092 describe --status
ClusterId:              5L6g3nShT-eMCtK--X86sw
LeaderId:               1
LeaderEpoch:            1
HighWatermark:          142
MaxFollowerLag:         0
MaxFollowerLagTimeMs:   0
CurrentVoters:          [{"id": 1, "directoryId": "...", "endpoints": ["CONTROLLER://localhost:9093"]}]
CurrentObservers:       []

(Your cluster ID, epoch and high watermark will differ.) LeaderId is the active controller. HighWatermark is the committed end of the metadata log. MaxFollowerLag tells you if a standby or broker is falling behind.

Option B: 3 controllers + 3 brokers (isolated mode)

This follows the official example in the Kafka repo (docker/examples/.../cluster/isolated/plaintext). It uses the static controller.quorum.voters style, which is still supported; new production clusters are better formatted with a dynamic quorum (below). Only controller-1 and kafka-1 are shown; copy them for ids 2, 3 and 5, 6.

services:
  controller-1:
    image: apache/kafka:4.4.0
    container_name: controller-1   # so "docker stop controller-1" works
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: 'controller'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@controller-1:9093,2@controller-2:9093,3@controller-3:9093'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      KAFKA_LISTENERS: 'CONTROLLER://:9093'
      CLUSTER_ID: '4L6g3nShT-eMCtK--X86sw'
  # controller-2, controller-3: same, with KAFKA_NODE_ID 2 and 3
  # and container_name controller-2 / controller-3

  kafka-1:
    image: apache/kafka:4.4.0
    container_name: kafka-1
    ports: ["29092:9092"]
    hostname: kafka-1
    environment:
      KAFKA_NODE_ID: 4
      KAFKA_PROCESS_ROLES: 'broker'
      KAFKA_CONTROLLER_QUORUM_VOTERS: '1@controller-1:9093,2@controller-2:9093,3@controller-3:9093'
      KAFKA_LISTENERS: 'PLAINTEXT://:19092,PLAINTEXT_HOST://:9092'
      KAFKA_ADVERTISED_LISTENERS: 'PLAINTEXT://kafka-1:19092,PLAINTEXT_HOST://localhost:29092'
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: 'CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT'
      KAFKA_INTER_BROKER_LISTENER_NAME: 'PLAINTEXT'
      KAFKA_CONTROLLER_LISTENER_NAMES: 'CONTROLLER'
      CLUSTER_ID: '4L6g3nShT-eMCtK--X86sw'
    depends_on: [controller-1, controller-2, controller-3]
  # kafka-2, kafka-3: ids 5 and 6, host ports 39092 and 49092,
  # container_name kafka-2 / kafka-3

Why container_name? Without it, Docker Compose v2 names containers <project>-controller-2-1 and so on, and the plain docker stop controller-2 below would fail with "No such container". If you leave it out, use docker compose stop controller-2 and docker compose exec kafka-1 ... instead; Compose then finds the container by service name.

Then break things on purpose and watch the quorum react:

# Who is the active controller, and how far behind is everyone?
docker exec kafka-1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server kafka-1:19092 describe --replication

# Kill the active controller (say it is controller-2), then ask again
docker stop controller-2
docker exec kafka-1 /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server kafka-1:19092 describe --status   # LeaderId changes, LeaderEpoch +1

# Stop a second controller: metadata changes now fail
docker stop controller-3
docker exec kafka-1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka-1:19092 \
  --create --topic will-not-work --partitions 1   # times out: no quorum
docker start controller-2 controller-3

Voters show as Leader or Follower; brokers are Observers. A large or growing Lag on a broker means it is applying metadata late, which can explain clients seeing stale leaders on that broker.

Formatting storage (bare-metal or VMs)

Docker images do this for you. On real machines, KRaft refuses to auto-format a blank disk, on purpose: if a majority of controllers started with empty logs, a leader could be elected that has lost committed data. So you format each node explicitly with the same cluster ID:

CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"

# First controller of a new dynamic quorum (KIP-853): start with one voter...
bin/kafka-storage.sh format --cluster-id "$CLUSTER_ID" --standalone --config config/controller.properties

# ...format other controllers without initial voters, start them, then add them:
bin/kafka-storage.sh format --cluster-id "$CLUSTER_ID" --no-initial-controllers --config config/controller.properties
bin/kafka-metadata-quorum.sh --command-config config/controller.properties \
  --bootstrap-controller controller1:9093 add-controller

# Brokers: plain format
bin/kafka-storage.sh format --cluster-id "$CLUSTER_ID" --config config/server.properties
# controller.properties (dynamic quorum)
process.roles=controller
node.id=1
listeners=CONTROLLER://controller1.example.com:9093
controller.listener.names=CONTROLLER
controller.quorum.bootstrap.servers=controller1.example.com:9093,controller2.example.com:9093,controller3.example.com:9093

With a dynamic quorum you can add or remove controllers while running (add-controller, remove-controller). With a static quorum (controller.quorum.voters), membership is fixed in every node's config. kafka-features.sh --bootstrap-controller ... describe tells you which you have: kraft.version level 1 or higher means dynamic.

Peek inside the metadata

# Decode the metadata log records
bin/kafka-dump-log.sh --cluster-metadata-decoder \
  --files /var/lib/kafka/meta/__cluster_metadata-0/00000000000000000000.log

# Browse a snapshot like a filesystem
bin/kafka-metadata-shell.sh --snapshot /var/lib/kafka/meta/__cluster_metadata-0/00000000000000007228-0000000001.checkpoint
>> ls /
image  local
>> ls /image
acls  clientQuotas  cluster  configs  delegationTokens  features  producerIds  provenance  scram  topics
>> ls /image/topics
byId  byName
>> cat /image/topics/byName/payments/0
  replicas: [4, 5, 6]
  isr: [4, 5, 6]
  leader: 4
  leaderEpoch: 0
  partitionEpoch: 0
  ...

The tree mirrors the in-memory metadata image that every broker keeps: /image/topics, /image/cluster (registered brokers and controllers), /image/configs and so on, while /local shows details about the shell itself. The exact print format of a partition differs between versions (older 3.x releases had a different tree with /brokers and /topics at the top), so look for the fields, not the formatting: replicas, ISR, leader and the two epochs.

The paths depend on your metadata.log.dir (or the first log.dirs entry). On Kubernetes, the Strimzi operator runs controllers and brokers as separate KafkaNodePools; see Operations & Kafka on K8s and the operators page.
