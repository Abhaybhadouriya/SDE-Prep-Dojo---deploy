Production notes: threads, slow work and share groups

good to know

One consumer, one thread

The Java KafkaConsumer is not thread-safe: only one thread may call it (the one exception is wakeup(), used to break out of poll on shutdown). Two common shapes:

One consumer per thread
  • Simplest; ordering per partition is automatic.
  • Scale by adding threads/pods up to the partition count.
  • Commits are easy to reason about.
One consumer + worker pool
  • More parallelism than partitions (e.g. slow HTTP calls).
  • You must keep per-key order yourself (route each key to the same worker).
  • You may commit only offsets whose records are all finished, so you track "completed up to" per partition.

Slow processing and max.poll.interval.ms

If the time between two poll() calls exceeds max.poll.interval.ms (5 minutes), the client considers itself failed and leaves the group. Its partitions move, the batch it was working on is re-delivered to someone else, and when it finally returns it may hit a CommitFailedException. Fixes, in order: lower max.poll.records so each batch is quicker; make the work faster (batch database writes); only then raise the interval. For truly long jobs, pause() the partitions, keep calling poll() (which then returns nothing but keeps you alive), and resume() when the job is done.

Consumer proxies and share groups

Big companies hit the "one partition, one consumer" limit and the "a slow message blocks its partition" problem (head-of-line blocking). Uber built a push-based Consumer Proxy and Walmart a Messaging Proxy Service: a proxy reads partitions and pushes records to many service instances, keeping per-key order by allowing at most one in-flight message per key (as described in their engineering posts linked below). Kafka itself now ships the idea as share groups (KIP-932, production ready in 4.2):

  • Many consumers can read the same partition at once.
  • Each record is acquired with a lock (30 s by default) and acknowledged one by one: ACCEPT, RELEASE (try again), REJECT, or RENEW (4.2+, extend the lock).
  • After 5 delivery attempts (default) a record is archived, and since 4.4 it can go to a dead-letter queue (KIP-1191).
  • The price: no ordering guarantee. Use it for independent jobs (send an email, resize an image), not for "events of one order in sequence".

Compare with RabbitMQ and SQS on Kafka vs Others, and see retries and DLQ design in Stream Processing, Retries & DLQ.

You might confuse this with: a partition replica. Consumers in a group split partitions; they do not read different replicas. By default every consumer reads from the partition leader (Kafka can be configured to let consumers fetch from a nearby follower with client.rack, KIP-392). Replicas are about safety, covered on Replication & ISR.
