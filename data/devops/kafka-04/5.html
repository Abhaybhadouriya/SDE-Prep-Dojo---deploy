When one record keeps failing: retry topics and the DLQ

must know

Sooner or later a consumer meets a record it cannot process. Maybe the JSON is broken, a field is missing, or the payment service it calls returns an error for that one customer. Kafka hands records out in order per partition, and the committed offset is a single bookmark. So if your code retries that record forever, the bookmark never moves and every record behind it on the partition waits. One bad record (a "poison pill") can stop a whole partition, and lag climbs while the pods look healthy.

The usual fix is to move the problem out of the way: after a few quick in-process retries, publish the record to a retry topic, commit the original offset, and carry on. A separate consumer reads the retry topic after a delay. If the record still fails after the last tier, it goes to a dead-letter topic (DLQ, "dead-letter queue"), where a human or a tool looks at it and later re-drives it (publishes it back to the main topic) once the bug is fixed.

Poison record or outage? Treat them differently

  • Poison record (bad data, a bug that hits one input): retrying will never help. Send it to the DLQ quickly so the partition moves on.
  • Outage (the database or a downstream API is down for everyone): every record will fail. Do not flood the DLQ with millions of good records. Pause the consumer (pause() / resume()), back off, and let lag build; once the dependency is back, you catch up from the same offset.

A simple rule: classify the error. "Permanent" errors (validation, deserialisation) go to the DLQ; "transient" errors (timeouts, 503s) mean back off and retry in place, with a circuit breaker if many records fail in a row.

The trade-off: ordering. Once a record goes to a retry topic, later records with the same key may be processed before it. If order per key matters (for example "order paid" must come after "order placed"), either park the whole key (send every later record for that key to the retry path too, tracked in a small "blocked keys" store) or retry in place and accept the stall. Say this out loud in an interview; it is what separates a good answer from a textbook one.

From your world

A DLQ is the punt path of a router: packets the fast path cannot handle (options, unknown destinations) are moved aside to a slow path, so the line-rate forwarding behind them is not blocked. Where it breaks: punted packets are usually rate-limited and dropped when the CPU queue fills, while DLQ records are kept (with retention you choose), inspected, and re-driven back into the main flow.

Tools that do this for you: Kafka Connect has errors.tolerance=all plus errors.deadletterqueue.topic.name (see Connect, Streams & Flink); Spring Kafka has DefaultErrorHandler with a dead-letter publisher; share groups (below) can mark a record as rejected after a delivery-count limit.
