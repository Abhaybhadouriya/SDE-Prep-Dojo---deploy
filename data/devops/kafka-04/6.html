Consumer lag: the pile of unread worksheets

must know

Lag for one partition = log-end offset (the offset the next produced record will get) minus the group's committed offset. Lag of a group = the sum over its partitions (look at the max partition too). It is the single most useful health number for a consumer.

From your world

Lag is queue depth on an egress interface. A deep queue that is stable is just buffering. A queue that grows without stopping means the drain rate (consumers) is below the fill rate (producers), and something will eventually drop: in Kafka, "drop" means retention deletes records your group has not read yet.

"What number is bad?"

There is no universal number, because 10,000 records of lag is 0.1 seconds for one service and 3 hours for another. Better rules:

  1. Watch the trend, not the value Lag that rises and falls with traffic is fine. Lag that only goes up means you are falling behind.
  2. Convert to time "We are 4 minutes behind" means more to a product owner than "250k records". Tools such as Burrow or kafka_exporter, plus a consume-rate metric, give you this.
  3. Compare to retention If the time lag approaches the topic's retention (7 days by default), you are about to lose data for real.
  4. Alert on the SLO (service level objective: the target you promise, for example 99% of notifications sent within 30 s), e.g. "notifications must go out within 30 s, page if time lag > 30 s for 5 minutes".

Try it: a lab you can run

You need only Docker. This starts one Kafka 4.4 node in KRaft mode (broker + controller in one process, fine for a laptop).

On Windows? The commands are bash. Run them in Git Bash or WSL. In PowerShell, set the variable with $K="/opt/kafka/bin" (quotes needed) and replace each trailing \ line continuation with a backtick `, or simply join the lines into one.

docker run -d --name kafka -p 9092:9092 apache/kafka:4.4.0
K=/opt/kafka/bin
docker exec kafka $K/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3
# write 3,000 test records
docker exec kafka $K/kafka-producer-perf-test.sh --topic orders --num-records 3000 \
  --record-size 100 --throughput -1 --bootstrap-server localhost:9092
# terminal 1 and terminal 2: two members of the same group (new protocol)
docker exec -it kafka $K/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --group billing --from-beginning \
  --command-property group.protocol=consumer
# terminal 3: who owns what, and how far behind is each partition?
docker exec kafka $K/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group billing

Expected output (IDs shortened; your offsets will differ):

$ kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group billing

GROUP    TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID       HOST         CLIENT-ID
billing  orders  0          1012            1012            0    t9Qk...-consumer  /172.17.0.2  console-consumer
billing  orders  1          996             996             0    t9Qk...-consumer  /172.17.0.2  console-consumer
billing  orders  2          992             992             0    Xb2m...-consumer  /172.17.0.2  console-consumer

Stop both consumers (Ctrl+C), produce 3,000 more records, and describe again: LAG jumps to about 1,000 per partition and CONSUMER-ID is empty. Then rewind the group to replay everything (the group must be inactive):

docker exec kafka $K/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group billing --topic orders --reset-offsets --to-earliest --dry-run
# looks right? replace --dry-run with --execute
GROUP     TOPIC     PARTITION  NEW-OFFSET
billing   orders    0          0
billing   orders    1          0
billing   orders    2          0

Other useful reset targets: --to-datetime 2026-11-23T10:00:00.000, --by-duration PT30M, --shift-by -500, --to-offset 42. Replaying after a bug fix is a superpower Kafka has and a classic queue does not. The failure drills page uses this on the reference pipeline.
