Offsets and commits: the bookmark

must know

A consumer has two numbers per partition. Its position is the next offset it will fetch (it lives in the client's memory). Its committed offset is what the group has saved to Kafka. The committed offset is the next record to read, not the last one processed. If you processed offsets 0 to 41, you commit 42. Commits are written as records into __consumer_offsets, a compacted topic (it keeps only the latest value per group+topic+partition key), via the group coordinator.

Auto-commit vs manual commit

By default enable.auto.commit=true: inside poll(), the client commits the offsets returned by the previous poll, at most every auto.commit.interval.ms (5 s). It is convenient, and it hides two traps:

  • Lost messages: if you hand records to another thread and return to poll(), the offsets may be committed before that thread finishes. Crash now, and those records are never processed.
  • Duplicates: if you crash after processing but before the next auto-commit, the new owner re-reads up to 5 seconds of records.

The safe default for most services: turn auto-commit off and commit after processing. That gives at-least-once delivery, and you make your processing idempotent (safe to repeat) so duplicates are harmless. The Delivery Semantics page goes deep on this. Step through what happens on a crash:

  1. Poll. The group's committed offset for P2 is 42. Consumer C2 polls and gets records 42 to 46.
  2. Process. C2 handles 42, 43 and 44 (writes them to the database). It plans to commit after the whole batch.
  3. Crash. C2's pod is OOM-killed before it commits. Kafka still says "committed = 42" for this group.
  4. Take over. After the rebalance, C5 owns P2 and starts at the committed offset, 42. Records 42 to 44 are delivered again: a duplicate.
  5. Done. C5 processes 42 to 46 and commits 47. Because the handler upserts by order ID, the repeats changed nothing. That is at-least-once done right.

p.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

p.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(p)) {
    consumer.subscribe(List.of("orders"));
    while (running) {
        ConsumerRecords<String, String> batch = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> r : batch) {
            billing.upsert(r.key(), r.value());   // idempotent: same orderId twice = same row
        }
        if (!batch.isEmpty()) consumer.commitSync();   // commit AFTER the work is done
    }
}

Committing per message (as in the Python tab) is the simplest correct code, but each commit is a round trip to the coordinator. At high rates, commit every N records or every few hundred milliseconds, and accept that up to N records may be re-delivered after a crash. The reference project in the ShopStream pipeline commits after the database commit for exactly this reason.

Where does a brand-new group start?

auto.offset.reset decides what happens when the group has no committed offset for a partition (or the committed offset was already deleted by retention):

  • latest (the default): start at the end, so you see only new records. A new group skips all existing data. This is the number one "my consumer sees nothing" bug.
  • earliest: start from the oldest record still kept.
  • by_duration:PT1H (newer clients): start from records written in the last hour (ISO-8601 duration).
  • none: throw an error, so a human decides.

Also know offsets.retention.minutes (7 days by default): once a group has been empty for that long, its committed offsets are deleted. Bring the group back after a 10-day outage and auto.offset.reset kicks in again.
