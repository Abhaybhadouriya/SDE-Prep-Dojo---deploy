acks and min.insync.replicas: the matrix

must know

Two settings decide when a write counts as successful.

  • acks is a producer setting (see Producers). acks=0: do not wait at all. acks=1: wait until the leader has appended the record to its log (page cache, not fsync). acks=all (or -1, the default since Kafka 3.0): wait until every replica currently in the ISR has it.
  • min.insync.replicas is a topic or broker setting (default 1). It only matters for acks=all: if the ISR has fewer members than this, the leader refuses the write with NotEnoughReplicas instead of accepting it with too few copies.

Why do you need both? Because "all of the ISR" can shrink. If two followers fall out, the ISR is just the leader, and acks=all silently becomes acks=1. min.insync.replicas=2 is the floor that stops that. Here is the full picture for RF = 3:

Setting (RF=3)Brokers that can be down and still writeCan an acked write be lost?Typical use
acks=0Up to 2 (if leaders move)Yes, easilyMetrics where a gap is fine
acks=1Up to 2Yes, on leader failureLogs, clickstream, high volume and low value
acks=all, min.insync=1Up to 2Yes, if the ISR had shrunk to 1Out-of-the-box default (not durable)
acks=all, min.insync=21No, unless 2 brokers fail togetherOrders, payments, anything that matters
acks=all, min.insync=30NoRare; every maintenance blocks writes

The out-of-the-box broker defaults are not durable: default.replication.factor=1 and min.insync.replicas=1. Set RF and min ISR on every important topic (or as broker defaults) yourself. Also note min.insync.replicas counts the leader: 2 means "leader + at least 1 follower".

Try it: watch the ISR shrink

The reference project has a 3-broker KRaft cluster. From pipeline/code:

Version note: the reference project pins apache/kafka:4.3.2 (the newest version that Strimzi 1.3.1 supports, so the local and Kubernetes labs run the same Kafka). Everything on this page behaves the same on 4.4. Shell note: the commands are bash ($K/... and trailing \). On Windows use Git Bash or WSL. In PowerShell, write the full docker compose exec kafka-1 /opt/kafka/bin/kafka-topics.sh ... each time and replace each trailing \ with a backtick (`).

docker compose up -d kafka-1 kafka-2 kafka-3
K="docker compose exec kafka-1 /opt/kafka/bin"
$K/kafka-topics.sh --bootstrap-server kafka-1:19092 --create --topic payments \
  --partitions 3 --replication-factor 3 --config min.insync.replicas=2
$K/kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --topic payments
Topic: payments  TopicId: 9mJ3...  PartitionCount: 3  ReplicationFactor: 3  Configs: min.insync.replicas=2
    Topic: payments  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3  Elr:   LastKnownElr:
    Topic: payments  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1  Elr:   LastKnownElr:
    Topic: payments  Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2  Elr:   LastKnownElr:

The Elr and LastKnownElr columns are explained in Leader epochs, unclean election and ELR below. Empty is normal for a healthy topic.

Kill broker 2, wait a few seconds, and describe again. Partition 1 has a new leader and every ISR has shrunk to two members:

docker compose kill kafka-2
$K/kafka-topics.sh --bootstrap-server kafka-1:19092 --describe --under-replicated-partitions
    Topic: payments  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,3  Elr:   LastKnownElr:
    Topic: payments  Partition: 1  Leader: 3  Replicas: 2,3,1  Isr: 3,1  Elr:   LastKnownElr:
    Topic: payments  Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1  Elr:   LastKnownElr:

Writes with acks=all still succeed (2 in ISR, min is 2). To see the producer refuse to write, keep kafka-2 down and raise the bar instead of killing a second node: ask for 3 in-sync replicas when only 2 are alive.

$K/kafka-configs.sh --bootstrap-server kafka-1:19092 --alter   --entity-type topics --entity-name payments --add-config min.insync.replicas=3
# produce with acks=all: every send is now rejected
docker compose exec kafka-1 bash -c "echo hello | /opt/kafka/bin/kafka-console-producer.sh   --bootstrap-server kafka-1:19092 --topic payments --command-property acks=all"
# put it back
$K/kafka-configs.sh --bootstrap-server kafka-1:19092 --alter   --entity-type topics --entity-name payments --add-config min.insync.replicas=2

The producer keeps retrying with NOT_ENOUGH_REPLICAS until its delivery.timeout.ms (2 minutes) expires. That is the system choosing consistency over availability on purpose. Bring the broker back with docker compose start kafka-2 and watch the ISR grow again. The scripted version of this drill is scripts/chaos/01-kill-broker.sh.

WARN [Producer clientId=console-producer] Got error produce response with correlation id 7 on topic-partition payments-0, retrying (2147483646 attempts left). Error: NOT_ENOUGH_REPLICAS

The exact log text varies by client version; the error name is what to look for.

Why not just kill a second broker? In this lab every node is also a controller (combined mode, 3 voters). Killing two of three nodes also kills the controller quorum: with only 1 of 3 voters left there is no active controller, so leaders cannot move and ISRs cannot shrink. Clients then see request timeouts, and partitions led by the dead broker have no leader at all, instead of the clean NOT_ENOUGH_REPLICAS. In production, run controllers on separate nodes (see KRaft & the controller quorum) so losing brokers never costs you the quorum.
