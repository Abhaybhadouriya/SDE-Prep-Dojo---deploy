Variables, locals, outputs and loops

Good to know (SDE-2)

Where variable values come from, lowest to highest priority (later wins): the default in the block, environment variables TF_VAR_name, terraform.tfvars, *.auto.tfvars (alphabetical), then -var and -var-file on the command line in the order given. If a variable has no value from anywhere, Terraform prompts for it (in CI that is a failure, which is what you want).

Types: string, number, bool, list(string), map(string), object({ name = string, cidr = string }). Types plus validation blocks catch mistakes at plan time instead of halfway through an apply.

count vs for_each: both create many copies of a resource. count gives you a list indexed 0, 1, 2. for_each gives you a map keyed by strings. Prefer for_each for anything whose members can change:

variable "subnets" {
  type = map(object({ cidr = string, az = string }))
  default = {
    "app-a" = { cidr = "10.0.10.0/24", az = "ap-south-1a" }
    "app-b" = { cidr = "10.0.11.0/24", az = "ap-south-1b" }
  }
}

resource "aws_subnet" "app" {
  for_each          = var.subnets
  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value.cidr
  availability_zone = each.value.az
  tags              = { Name = each.key }
}

output "app_subnet_ids" {
  value = { for k, s in aws_subnet.app : k => s.id }
}

The count trap. With count over a list ["a","b","c"], deleting "a" shifts b to index 0 and c to index 1. Terraform sees index 2 removed and indexes 0 and 1 changed, so it may destroy and recreate subnets that you did not touch. With for_each, the addresses are aws_subnet.app["b"] and aws_subnet.app["c"] and stay stable.

Outputs are the public interface of a configuration: another team's Terraform can read them through a terraform_remote_state data source, and modules (covered on the "Terraform at Scale" page) use them to pass IDs to each other. Mark secrets with sensitive = true so the CLI hides them, but remember they still sit in state (see secrets in state).
