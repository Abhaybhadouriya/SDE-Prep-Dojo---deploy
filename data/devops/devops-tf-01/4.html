The workflow: init, plan, apply

Must know (SDE-1)

Three commands do almost all the work. Click Play to see what each one touches.

  1. terraform init: reads required_providers, downloads the AWS provider plugin into .terraform/, writes .terraform.lock.hcl, and sets up the backend. Run it once per folder, and again when providers or backend change.
  2. terraform plan (part 1): parses all .tf files, loads the last state, and refreshes it by reading the real objects through the provider (read-only API calls).
  3. terraform plan (part 2): compares desired (config) against actual (refreshed state) and prints the diff. Nothing has changed in the cloud yet.
  4. terraform apply: shows the plan again, asks for yes, then walks the dependency graph making create / update / delete API calls, saving state as it goes.

Outputs:

private_subnet_ids = [
  "subnet-0aa11",
  "subnet-0bb22",
]
vpc_id = "vpc-0a1b2c3d"

Look at two details. First, vpc_id = (known after apply): the subnet needs the VPC ID, which does not exist until AWS creates the VPC. That unknown value is the visible sign of a dependency. Second, in the apply log, the VPC is created first, then the gateway and four subnets start at the same time. That is the dependency graph at work.

Run terraform plan again straight after and you get No changes. Your infrastructure matches the configuration. That is idempotency.

Reading plan symbols

SymbolMeaningExample cause
+createnew block
-destroyblock removed from config
~update in placechanged a tag
-/+destroy, then create a replacementchanged a field the API cannot modify, e.g. a subnet's cidr_block (plan says # forces replacement)
+/-create replacement first, then destroysame, with lifecycle { create_before_destroy = true }
<=read (data source)data source that depends on something not yet known

Always read -/+ lines twice. "Replace" on a database, a subnet with running instances, or a NAT gateway with an allow-listed Elastic IP is an outage. Plan in CI, save it with -out, and apply exactly that saved plan so what was reviewed is what runs.

The other everyday commands: terraform fmt (canonical formatting), terraform validate (syntax and type check, no API calls), terraform output, terraform console (try expressions like cidrsubnet("10.0.0.0/16", 8, 10) interactively), and terraform destroy (delete everything in state, in reverse dependency order).
