Explicit dependencies: when (and when not) to use depends_on

Must know (SDE-1)

Sometimes A needs B to exist, but A's arguments never mention B. Terraform cannot see that, so it may create them in parallel, and A fails or misbehaves. That is the only job of depends_on: add an edge Terraform could not infer.

The classic example (it is the one in the Terraform docs): an EC2 instance whose startup script reads from S3. The instance references an instance profile (implicit edge, fine), but the IAM policy that actually grants S3 access is attached to the role separately. Nothing in the instance block mentions the policy:

resource "aws_iam_role_policy" "read_bucket" {
  role   = aws_iam_role.app.id
  policy = data.aws_iam_policy_document.read_bucket.json
}

resource "aws_instance" "app" {
  ami                  = data.aws_ami.al2023.id
  instance_type        = "t3.small"
  subnet_id            = aws_subnet.private[0].id
  iam_instance_profile = aws_iam_instance_profile.app.name   # implicit edge
  user_data            = file("boot.sh")                     # boot.sh runs "aws s3 cp ..."

  # The boot script needs the policy attached BEFORE the instance starts.
  # No argument above mentions the policy, so we say it explicitly.
  depends_on = [aws_iam_role_policy.read_bucket]
}

Another common one in networking: a NAT gateway (or an instance in a public subnet) needs the internet gateway attached to the VPC before it works, but the NAT gateway block only references a subnet and an Elastic IP. The AWS provider docs recommend depends_on = [aws_internet_gateway.igw] on the NAT gateway for exactly this reason.

Use depends_on when
  • The dependency is about behaviour (permissions, a gateway being attached, a DNS record propagating), not data
  • You checked that no real reference can express it
  • You leave a comment saying why
Avoid depends_on when
  • A reference exists or could exist (pass aws_vpc.main.id instead)
  • You put it on a whole module: every data source inside becomes "known after apply" and plans get noisy and conservative
  • You are "just making sure": extra edges reduce parallelism and can cause needless replacements

The docs call depends_on a last resort. In an interview, say: "I prefer implicit dependencies through references, because Terraform then plans based on the exact attribute that changed. I use depends_on only for hidden behavioural dependencies like IAM propagation, with a comment."

Other lifecycle knobs you will meet

resource "aws_lb_target_group" "app" {
  # ...
  lifecycle {
    create_before_destroy = true          # replacement: new one first, then delete old (no gap)
    prevent_destroy       = false         # true = any plan that destroys this errors out
    ignore_changes        = [tags["LastDeployedBy"]]   # someone else manages this field
  }
}
