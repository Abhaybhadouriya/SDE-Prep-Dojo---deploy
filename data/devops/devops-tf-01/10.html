Interview questions

What is Infrastructure as Code, and why declarative rather than scripts?

IaC means infrastructure is defined in version-controlled files and created by a tool, not by hand. Declarative IaC (Terraform, CloudFormation) describes the end state; the tool computes the actions. That gives idempotency (re-running changes nothing), a reviewable diff before any change (plan), reproducible environments (dev and prod from the same code), easy teardown in the right order, and an audit trail in Git. Imperative scripts describe steps, so every change and every "already exists" case needs new code.

How to answer

Define it in one sentence, then give three concrete benefits (reproducible, reviewable plan, idempotent). Close with a real pain it removed, such as "dev and prod VPCs were built by hand and had different route tables".

Likely follow-ups
  • Terraform vs CloudFormation vs Pulumi?
  • What does idempotent mean here?
  • What still needs to be imperative (data migrations, one-off scripts)?
Walk me through what happens on terraform init, plan and apply.

init reads required_providers, downloads provider plugins (respecting .terraform.lock.hcl), downloads modules and configures the backend. plan loads config and state, refreshes state by reading each real object through the provider, builds the dependency graph, and diffs desired vs actual into a list of create/update/replace/delete actions. Nothing changes. apply executes a plan (a saved one, or a fresh one after confirmation), walking the graph with up to 10 parallel operations and writing state as resources complete.

How to answer

One line per command, then mention "in CI we save the plan with -out and apply that exact file after review".

Likely follow-ups
  • What does refresh do and when can you skip it (-refresh=false)?
  • What happens if apply fails halfway? (State records what succeeded; fix and re-apply.)
How does Terraform decide the order in which to create resources?

It builds a DAG. Every reference in an expression (vpc_id = aws_vpc.main.id) creates an edge from the subnet to the VPC; depends_on adds edges that cannot be inferred. Provider nodes come first. After checking there are no cycles, it walks the graph: a node starts when all its dependencies are done, with a concurrency limit of 10 (-parallelism). Destroy walks the reversed graph, so the VPC is deleted last.

How to answer

Say "topological sort with a worker pool", draw three boxes (VPC, two subnets) and show the two subnets running in parallel. Mention cycles are detected at plan time.

Likely follow-ups
  • How do you debug a cycle error?
  • Why might raising parallelism not speed things up? (API rate limits; providers already retry with backoff.)
Implicit vs explicit dependencies: when do you need depends_on?

Implicit dependencies come from references and are preferred because Terraform knows which attribute matters and can plan precisely. depends_on is for dependencies that are about behaviour, not data: an instance whose boot script needs an IAM policy that is attached separately; a NAT gateway that needs the internet gateway attached; an app that needs a DB to exist but gets the address from a config service. Overusing it makes plans conservative (more "known after apply", unnecessary replacements), especially on modules.

How to answer

Definition, one real example (IAM policy before instance boot), one cost ("last resort" per the docs).

Likely follow-ups
  • What does depends_on on a module do?
  • Can depends_on take a variable? (No: only static references.)
Resource vs data source: what is the difference?

A resource is owned by this configuration: Terraform creates, updates and deletes it, and it lives in state. A data source is a read-only lookup of something that exists already (latest AMI, the AZ list, a shared VPC owned by the network team). Deleting a data block never deletes anything in the cloud. Data sources are how you depend on infrastructure you do not own without importing it.

How to answer

"Own vs read." Give the shared-VPC example: the platform team owns the VPC; my service looks it up by tag with data "aws_vpc".

Likely follow-ups
  • When is a data source read during plan vs during apply?
  • data source vs terraform_remote_state?
count vs for_each: which do you use and why?

count creates a list of instances addressed by index; for_each creates a map addressed by key. If items can be added or removed from the middle, count renumbers and causes Terraform to destroy and recreate unrelated instances. for_each keeps addresses stable. I use count only for "0 or 1" toggles (count = var.enable_nat ? 1 : 0) or truly identical copies.

How to answer

Explain the index-shift problem with three subnets and removing the first.

Likely follow-ups
  • How do you migrate from count to for_each without destroying anything? (moved blocks.)
What is a provider, and how does "multi-cloud" work in Terraform?

A provider is a plugin binary that maps resource types to one API (AWS, GCP, Kubernetes, GitHub). Core launches it as a separate process and talks gRPC. Multi-cloud means one workflow, one state and one dependency graph across several providers, and cross-provider references (a GCP DNS record pointing at an AWS load balancer). It does not mean portable resources: you still rewrite aws_instance as google_compute_instance. Versions are pinned in required_providers and locked in .terraform.lock.hcl; aliases give multiple regions or accounts.

How to answer

Clear up the myth first ("not write once, run on any cloud"), then plugin architecture, then pinning.

Likely follow-ups
  • How would you deploy the same stack to two regions?
  • What is in the dependency lock file?
A plan shows -/+ on your production database. What do you do?

Stop. Find the line marked # forces replacement to see which argument triggered it (often an engine version, a subnet group, an identifier or a renamed resource address). Options: revert the change; if it was a rename, use a moved block so the address changes without replacement; if it was an argument someone changed in the console, align the code with reality; if replacement is truly needed, plan a migration (snapshot, new instance, cutover). Protect critical resources with prevent_destroy = true and policy checks in CI so this never reaches apply.

How to answer

Show calm process: identify the forcing argument, choose the non-destructive fix, then add a guardrail.

Likely follow-ups
  • How would CI block a destructive plan automatically? (Parse terraform show -json tfplan for delete actions.)
Terraform or OpenTofu: which would you pick for a new platform, and why?

Both read the same HCL and largely the same state, so the choice is about licence policy, features and support rather than syntax. Terraform moved to the Business Source License in 2023 (from 1.6); that matters if you build a competing hosted product or your legal team rejects non-OSI licences, not for an ordinary company running its own infrastructure. OpenTofu is the MPL fork under the Linux Foundation and adds features such as client-side state encryption. Terraform has HCP Terraform, the larger vendor ecosystem and commercial support. Migration between them is low-risk, but pin one tool and version per repository and in CI so state is never written by both.

How to answer

Say "same language, different licence and governance", name one concrete difference each way, and end with "pin one tool per repo".

Likely follow-ups
  • What breaks if half the team uses each? (State written by a newer or different tool may not be readable by the other; lock the version in required_version and CI.)

Scenario: Error: Cycle in a plan

terraform plan fails with Error: Cycle: aws_security_group.app, aws_security_group.db after a teammate made the app SG allow the DB SG and the DB SG allow the app SG, both with inline rules.

Weak answer: "Add depends_on so Terraform knows the order."

Strong answer: A cycle means the dependency graph has a loop, so no order exists; depends_on only adds edges and makes it worse. Each SG references the other's ID inside its own resource, so neither can be created first. Break the loop by creating the two groups with no inline rules and moving each rule into its own aws_vpc_security_group_ingress_rule resource: both groups are created first, then the rules that reference them. terraform graph helps to see the loop. The same fix applies to any two resources that point at each other.

Likely follow-ups
  • Why is a cycle an error and not a runtime deadlock? (Terraform builds and checks the whole graph before acting.)
