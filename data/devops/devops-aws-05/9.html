When Lambda wins, and when a long-running consumer wins

Must know (SDE-1)
Lambda is a great fit when
  • Traffic is spiky or low on average (security alerts, nightly files, a few thousand events a minute).
  • Each unit of work is small and independent: one file, one batch of log lines.
  • You want zero servers to patch and built-in retries, DLQs and scaling.
  • It is glue between managed services: S3 to OpenSearch, Logs to metrics, stream to alert.
Prefer a long-running consumer (ECS, EKS, EC2) when
  • Volume is high and steady 24 x 7: always-on compute is usually cheaper per event at that point. Measure with your own numbers before deciding.
  • You need big in-memory state across events: sessionization, large joins, windows longer than Lambda's tumbling window limit (900 s on Kinesis).
  • Work can exceed the per-invocation timeout, or needs special hardware, a long-lived connection pool or a GPU.
  • You need exactly-once stateful stream processing: use Flink or Kafka Streams (see Kafka vs SQS for the queue side).
  • Strict tail latency where cold starts matter.

Late-2025 options that blur the line. Lambda Managed Instances run functions on EC2 capacity you choose (Savings Plans apply, and one environment handles several requests at once), which suits steady high volume. Lambda durable functions checkpoint multi-step work so a workflow can wait far beyond 15 minutes; Step Functions remains the other way to orchestrate long flows. The rule of thumb above still holds; these just move the break-even point.

Also consider no code at all: CloudWatch metric filters can turn a log pattern into a metric directly, and Data Firehose can deliver logs to S3 or OpenSearch with an optional transform Lambda. Write a custom function only when the logic needs real code (enrichment, lookups, multi-line parsing, custom alert rules).

Where this shows up in designs

  • Log Aggregation: Lambda as the light "parse, enrich, route" stage between collection and the index; Kafka or Kinesis as the buffer.
  • Metrics and Monitoring: extracting metrics from logs (EMF), and alert fan-out to SNS or chat.
  • Long-running tasks: the queue + worker pattern; Lambda is a worker for short tasks, a container for long ones.
