Three ways Lambda gets triggered

Must know (SDE-1)

Where the event comes from decides almost everything: who retries, how batches are built, and where failed data ends up. There are three invocation models. Learn them by heart; interviewers ask about this split all the time.

SourceModelBatch?Who retries on errorWhere failures go
S3 event notificationAsyncUsually 1 object per eventLambda: 2 more tries by defaultOn-failure destination or function DLQ
CloudWatch Logs subscription filterAsyncYes: many log events, gzippedLambda async retriesOn-failure destination or function DLQ
Kinesis Data StreamsEvent source mappingYes, per shard (default 100, max 10,000)The poller, until success or record expiryOn-failure destination (SQS/SNS) gets metadata
SQSEvent source mappingYes (default 10)SQS itself, after the visibility timeoutThe queue's redrive DLQ

Say it like this: "S3 and CloudWatch Logs push to Lambda asynchronously, so Lambda's own retry and destination settings apply. Kinesis and SQS are pulled by an event source mapping, so retries are about the stream position or the queue's visibility timeout, and the DLQ for SQS lives on the queue, not on the function."
