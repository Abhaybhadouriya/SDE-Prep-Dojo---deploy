Lambda inside your VPC: the networking view

Good to know (SDE-2)

By default a function runs in an AWS-owned network with internet access. When it must reach something private (an OpenSearch domain, an RDS database, an internal API), you attach it to your VPC: you pick subnets and security groups. AWS then creates Hyperplane ENIs (elastic network interfaces, shared across environments that use the same subnet + security group combination) in those subnets, and the function's traffic leaves through them.

From your world

This is plain routing, and it is where your background shines. The subnet's route table is a FIB: the local route covers the VPC CIDR, 0.0.0.0/0 points at a NAT gateway (a managed SNAT box with an Elastic IP), and a gateway endpoint for S3 shows up as a prefix list route so S3 traffic never leaves the AWS network. Security groups are a stateful firewall on the ENI (think conntrack-based iptables on a vNIC); network ACLs are stateless filters on the subnet, so you must allow the return ephemeral ports. The classic bug: "my Lambda in a VPC times out calling SNS" = it sits in a subnet whose default route goes nowhere (or to an IGW, which does not work without a public IP). Fix it with a NAT gateway or an interface endpoint for that service.

  • Pick at least two subnets in different Availability Zones so the function survives an AZ outage.
  • Make sure the subnets have enough free IPs; Hyperplane ENIs are shared, but they still use addresses.
  • Do not attach to a VPC "just because". If the function only talks to AWS public APIs and the internet, leaving it out of the VPC is simpler and avoids NAT data-processing charges.
