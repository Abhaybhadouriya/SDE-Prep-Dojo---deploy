Interview questions

Design a pipeline that detects SSH brute force attempts from EC2 auth logs in near real time.

The CloudWatch agent ships /var/log/secure to a log group. A subscription filter matches "Failed password" lines and invokes a Lambda. The Lambda decodes the gzip payload, counts failures per source IP, emits an EMF metric, and publishes an SNS alert above a threshold. For cross-batch counting (failures spread over minutes), keep counters in DynamoDB with a TTL, or emit per-IP metrics and let a CloudWatch alarm do the windowing. Failures go to an on-failure destination; the function has reserved concurrency so a storm cannot starve other functions.

How to answer

Draw source, filter, function, sinks; then say the three production words: idempotency, failure destination, concurrency cap. Mention that a pure metric filter plus alarm could do the simple version with no code.

Likely follow-ups
  • The volume grows 50x. What changes? (Subscription to Kinesis or Firehose first, then Lambda via ESM, or a container consumer.)
  • How do you avoid alert floods? (Dedup per IP per window.)
What are the Lambda invocation models, and how does error handling differ between them?

Synchronous: the caller waits and handles errors itself. Asynchronous (S3, SNS, CloudWatch Logs, EventBridge): Lambda queues the event, retries twice on function errors, keeps throttled events up to 6 hours, then sends failures to an on-failure destination or DLQ. Event source mapping (Kinesis, DynamoDB Streams, Kafka, SQS): a poller reads batches and invokes synchronously; for streams the poller retries (by default until the record expires), for SQS the message returns after the visibility timeout and the queue's redrive policy moves it to a DLQ.

How to answer

Use a three-row table in words: who holds the event, who retries, where failures go.

Likely follow-ups
  • Destination vs DLQ? (Destinations carry response and error details and support more targets; a DLQ holds only the payload.)
One malformed record is stalling your Kinesis-triggered Lambda. What is happening and how do you fix it?

Kinesis processing is ordered per shard, so a batch that keeps failing blocks that shard; IteratorAge climbs while other shards are fine. Fixes: catch errors per record and return batchItemFailures with the failing sequence number; turn on BisectBatchOnFunctionError; cap MaximumRetryAttempts and MaximumRecordAgeInSeconds; configure an on-failure destination so the shard can move on, then replay from the recorded sequence numbers after fixing the parser.

How to answer

Name the symptom metric (IteratorAge), the cause (head-of-line blocking), then the four knobs.

Likely follow-ups
  • What does the on-failure destination contain for Kinesis? (Metadata: shard and sequence range, not the records.)
  • How is this similar to a Kafka poison pill?
How do you size Lambda concurrency for a log processor, and what happens when you hit the limit?

Concurrency is roughly requests per second times average duration. 400 batches per second at 250 ms needs about 100. Check the account Region limit (default 1,000, shared), set reserved concurrency for the heavy function, and cap source concurrency (SQS MaximumConcurrency, Kinesis shards x parallelization factor). Over the limit you get throttles: async events are retried for up to 6 hours, SQS messages go back to the queue, Kinesis waits; nothing is lost if failure capture is configured, but latency grows.

How to answer

Show Little's law with numbers, then talk about protecting both neighbours (reserved concurrency) and the downstream sink (caps).

Likely follow-ups
  • Reserved vs provisioned concurrency? (Reserved = guarantee + cap; provisioned = pre-warmed environments to remove cold starts, billed while idle.)
When would you NOT use Lambda for log processing?

When volume is high and steady (always-on containers usually cost less per event), when you need large state across events or long windows (Flink, Kafka Streams), when work can run longer than the invocation timeout, when you need long-lived connections or special hardware, or when cold-start tail latency matters. Also when no code is needed: metric filters and Firehose cover many cases.

How to answer

Give the decision axes (traffic shape, state, duration, latency, cost) and say you would measure the cost crossover with real numbers.

Likely follow-ups
  • How would you migrate from Lambda to a container consumer without losing data? (Run both on the stream with separate consumers, compare output, then switch.)
Your VPC-attached Lambda can reach the database but times out calling SNS. Why?

The function's ENI is in a private subnet with no public IP. The database is reachable through the VPC's local route, but SNS is a public AWS endpoint. The subnet route table has no 0.0.0.0/0 to a NAT gateway (or routes to an IGW, which needs a public IP). Fix: add a NAT gateway route, or better, an interface VPC endpoint for SNS (and a gateway endpoint for S3) so traffic stays private and avoids NAT charges.

How to answer

Walk the packet: ENI, security group egress, route table lookup, next hop. Interviewers love candidates who debug cloud networking like real networking.

Likely follow-ups
  • Security group vs network ACL? (Stateful on the ENI vs stateless on the subnet.)
How do you make an S3-triggered log processor idempotent?

S3 notifications are at least once, so the same object can arrive twice. Use a natural key such as bucket + key + version ID (or ETag) and record "processed" in DynamoDB with a conditional write (attribute_not_exists); skip if the write fails. Make outputs deterministic too, such as writing results to a key derived from the input key so a rerun overwrites instead of appending.

How to answer

Say "at least once" first, then the idempotency key and the conditional write.

Likely follow-ups
  • What if the function crashes after writing output but before marking processed? (Deterministic output keys make the retry harmless.)
Why does the SQS visibility timeout matter for a Lambda consumer?

While Lambda processes a batch, its messages are hidden only for the visibility timeout. If the function takes longer than that, the messages reappear and another invocation processes them again. Set the timeout to several times the function timeout, use partial batch responses so only failed messages return, and set a redrive policy with a sensible maxReceiveCount so poison messages end up in a DLQ.

How to answer

Explain the lease idea: visibility timeout is a lease on the message.

Likely follow-ups
  • Standard vs FIFO queue for logs? (FIFO keeps order per message group but limits concurrency to the number of groups.)

Scenario: Lambda throttled, Kinesis iterator age climbing

A Lambda reads a Kinesis stream of 8 shards for fraud signals. After a deploy, IteratorAge climbs from seconds to 40 minutes and the function shows Throttles and errors.

Weak answer: "Raise the memory and wait."

Strong answer: Two things can each stall a shard, so separate them. Throttles: check the account's regional concurrency and whether another function is eating it; give this function reserved concurrency so it always gets its slots. Errors: with a stream source, one poison record makes Lambda retry the same batch and the whole shard stops moving, which is exactly a rising iterator age. Mitigate first: roll back the deploy if the errors started with it. Then make it robust: enable BisectBatchOnFunctionError, set MaximumRetryAttempts and MaximumRecordAgeInSeconds, add an on-failure destination, and report partial failures. To catch up, raise ParallelizationFactor (up to 10 concurrent batches per shard) or reshard. Alarm on IteratorAge, not only on errors.

Likely follow-ups
  • Why does order still hold with ParallelizationFactor? (Records with the same partition key go to the same batch sequence.)
  • How would the same bug look with an SQS trigger? (No blocking: the bad message retries until maxReceiveCount and lands in the DLQ.)
