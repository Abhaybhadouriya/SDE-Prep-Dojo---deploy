Pattern 3: Kinesis and SQS with an event source mapping

Good to know (SDE-2)

For high, steady volume you usually put a buffer in front: a Kinesis data stream (an ordered, replayable log split into shards, very like a Kafka topic with partitions) or an SQS queue (a message queue where each message is worked on by one consumer and then deleted). Lambda reads them through an event source mapping (ESM): a poller run by AWS that builds batches and invokes your function synchronously.

The batching knobs

  • BatchSize: most records per invoke. Kinesis default 100 (max 10,000); SQS default 10.
  • MaximumBatchingWindowInSeconds: wait up to this long (max 300 s) to fill a batch. Bigger batches = fewer invocations = lower cost, but more latency.
  • Payload cap: a batch also stops at the 6 MB invocation payload limit.
  • FilterCriteria: drop events before they reach your code (you are not billed for invocations that never happen).
aws lambda create-event-source-mapping \
  --function-name metrics-extractor \
  --event-source-arn arn:aws:kinesis:us-east-1:111122223333:stream/app-logs \
  --starting-position LATEST \
  --batch-size 500 \
  --maximum-batching-window-in-seconds 5 \
  --parallelization-factor 2 \
  --bisect-batch-on-function-error \
  --maximum-retry-attempts 3 \
  --maximum-record-age-in-seconds 3600 \
  --function-response-types ReportBatchItemFailures \
  --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:us-east-1:111122223333:app-logs-failed"}}'

Watch a failing batch on a Kinesis shard

Kinesis keeps order per shard, so a failing batch blocks its shard until it succeeds, is split, or gives up. Click through to see how the knobs above stop one bad record from freezing the pipeline.

  1. Records sit in shard-0 in order. Record 57 is malformed and will make the parser throw.
  2. The poller reads a batch (here 100 records, or fewer if the batching window ends first).
  3. The poller invokes your function synchronously with the whole batch.
  4. The function throws on record 57. By default the whole batch is retried, and the shard cannot move forward. The IteratorAge metric (how old the newest record you processed is) starts to climb.
  5. With BisectBatchOnFunctionError, Lambda splits the batch in two and retries each half. The good half succeeds.
  6. Splitting repeats until the bad record is alone. Each retry counts against MaximumRetryAttempts (and MaximumRecordAgeInSeconds caps how long it can keep trying).
  7. When retries run out, Lambda sends a record describing the failed batch (shard ID and sequence number range, not the data itself) to the on-failure destination and moves on. You can re-read the data from the stream later using those sequence numbers, as long as it is still within the stream's retention.

With ReportBatchItemFailures your function can do even better: catch the error per record and return the first failing sequence number. Lambda then checkpoints everything before it and retries from that record only.

def handler(event, context):
    for r in event["Records"]:
        try:
            process(r)                      # parse, extract metric
        except Exception:
            # Kinesis: return the FIRST failed record; Lambda checkpoints before it
            return {"batchItemFailures": [{"itemIdentifier": r["kinesis"]["sequenceNumber"]}]}
    return {"batchItemFailures": []}

SQS: the queue owns retries

With SQS, a message picked up by the poller becomes invisible for the queue's visibility timeout. If the function succeeds, Lambda deletes the batch. If it fails, the messages reappear after the timeout and are retried. After maxReceiveCount receives, the queue's redrive policy moves the message to the DLQ. Set the visibility timeout well above the function timeout (AWS guidance has long been about six times), otherwise a message can reappear while the first copy is still running and be processed twice.

aws sqs set-queue-attributes --queue-url https://sqs.us-east-1.amazonaws.com/111122223333/log-jobs \
  --attributes '{"VisibilityTimeout":"360",
                 "RedrivePolicy":"{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:111122223333:log-jobs-dlq\",\"maxReceiveCount\":\"5\"}"}'

For SQS, partial batch responses use the message ID (any order is fine for a standard queue): return {"batchItemFailures": [{"itemIdentifier": "<messageId>"}]} for each failed message, and only those come back.

From your world

A Kinesis shard is a per-flow receive queue, like an RSS (receive side scaling) queue on a multi-queue NIC: records with the same partition key hash to the same shard, so they stay in order, and each queue is drained by one worker. ParallelizationFactor (1 to 10) is like giving each hardware queue several softirq workers while still keeping order per partition key. A poison record blocking a shard is head-of-line blocking, the same pain you know from a single FIFO with a stuck packet at the front.

Compare with Kafka: this is the same consumer-group, offset and poison-pill problem covered in Kafka consumers and DLQs and the pipeline's retry and DLQ design. Lambda just runs the consumer loop for you.
