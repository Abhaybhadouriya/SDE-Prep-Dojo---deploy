host, none, and sharing a namespace

Three more ways to wire a container, each one a direct consequence of network namespaces.

  • --network host: Docker does not create a network namespace. The container uses the host's interfaces, routing table and ports directly. No veth, no bridge, no NAT, so no overhead and no -p (it is ignored). Two containers cannot both bind port 80. Use it for network-heavy agents (packet capture, monitoring daemons) and when you measure NAT overhead and it matters. On Docker Desktop, "host" means the hidden Linux VM's network, not your Mac or Windows network. (Docker Desktop 4.34+ has an opt-in Host networking setting that forwards these ports to your real machine; without it, host means the VM's network.)
  • --network none: a namespace with only lo. Nothing in, nothing out. Good for jobs that crunch files and must not phone home.
  • --network container:web: join an existing container's namespace. Both containers share one eth0, one IP, one port space and one loopback, so they can talk over localhost. This is exactly how a Kubernetes pod works: a tiny "pause" container holds the namespace and the app containers join it.
# Debug a container that has no tools: borrow its network namespace with a toolbox image
docker run --rm -it --network container:web nicolaka/netshoot \
  sh -c "ss -ltnp; ip route; dig +short db"
State   Recv-Q  Send-Q   Local Address:Port   Peer Address:Port  Process
LISTEN  0       511            0.0.0.0:80          0.0.0.0:*
LISTEN  0       511               [::]:80             [::]:*
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2

Because the toolbox joined web's namespace, ss shows nginx's listening sockets even though the two programs live in different images. (dig printed nothing here because web is on the default bridge, which has no name DNS.)
