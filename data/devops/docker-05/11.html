Interview questions

What happens at the packet level when you run docker run -p 8080:80 nginx and someone connects to port 8080?

At container start Docker creates a network namespace, a veth pair with one end as eth0 in the container and the other attached to the docker0 bridge, and assigns an IP like 172.17.0.2. It adds a DNAT rule in the nat table's DOCKER chain (reached from PREROUTING): TCP 8080 to 172.17.0.2:80, plus a filter rule allowing that forward, and starts a docker-proxy for host-local connections. When a SYN arrives on the host's eth0, PREROUTING rewrites the destination and conntrack records the flow, routing sends it to docker0, it passes FORWARD (DOCKER-USER first), the bridge delivers it to the veth, and nginx receives it on eth0 with the real client IP. Replies are un-NATed by conntrack. Egress from the container uses MASQUERADE in POSTROUTING.

How to answer

Draw it left to right: client, host eth0, PREROUTING/DNAT, route, FORWARD, docker0, veth, container. Name the chains. Then add one production point: it binds 0.0.0.0 by default and ufw does not filter it, use DOCKER-USER or bind 127.0.0.1.

My app container cannot connect to the database container at localhost:5432. Why?

Each container has its own network namespace with its own loopback. localhost inside the app container is the app container itself, and nothing listens on 5432 there. Put both containers on the same user-defined network (Compose does this automatically) and connect to db:5432; Docker's embedded DNS at 127.0.0.11 resolves the name. Also check the database listens on 0.0.0.0 inside its container, and remember that inside the network you use the container port (5432), not whatever host port you published.

How to answer

Say "separate network namespaces, separate loopbacks" in the first sentence, then the fix, then the two secondary checks (listen address and container vs host port).

Bridge vs host vs overlay vs macvlan: when would you use each?

Bridge is the default for containers on a single host: private subnet, NAT at the edge, DNS on user-defined networks. Host removes the network namespace for maximum performance and no NAT, at the cost of isolation and port conflicts; good for network agents. Overlay stretches one network across many hosts with VXLAN, used by Swarm. macvlan/ipvlan put containers directly on the physical LAN with their own IPs, for legacy apps or appliances that must be addressable like real machines, with ipvlan preferred when the switch limits MAC addresses. none for full isolation.

How to answer

For each: one line on mechanism, one on the trade-off. Finish with "in Kubernetes, CNI plugins replace these drivers".

How does service discovery work between containers on one host?

On a user-defined network, Docker writes nameserver 127.0.0.11 into each container's /etc/resolv.conf. That address is served by the embedded DNS in dockerd, which knows every container name, network alias and Compose service name on the networks that container is attached to, and forwards other names to the host's upstream resolvers. Several containers with the same alias get round-robin DNS answers. The default bridge does not have this, which is why you always create your own network.

How to answer

Give the magic IP, say what it knows and what it forwards, and mention the default-bridge exception. Bridge to Kubernetes: CoreDNS plus Services do the same job at cluster scale.

We blocked port 5432 with ufw, but the Postgres container is still reachable from the internet. Why?

Docker publishes ports with a DNAT rule in the nat table's PREROUTING path. After DNAT the packet is destined for a container IP, so it is forwarded and goes through the FORWARD chain, never INPUT, which is where ufw's rules live. So ufw never sees it. Fixes: do not publish the port at all if only other containers need it; or bind it to 127.0.0.1; or put filtering rules in the DOCKER-USER chain, which Docker evaluates before its own forward rules and never overwrites. Then verify from an outside host with nc -zv.

How to answer

Explain netfilter order (PREROUTING, routing decision, FORWARD vs INPUT). Give the three fixes in order of preference. This shows security judgment, which matters at Amazon and Microsoft.

How do containers in a Kubernetes pod share one IP, and how would you reproduce that with plain Docker?

A pod is a group of containers that share one network namespace. The kubelet first starts a tiny "pause" container that creates and holds the namespace; the app containers are started into it, so they share eth0, the IP, the port space and loopback. In Docker: docker run -d --name pause ... then docker run --network container:pause app and docker run --network container:pause sidecar. The sidecar can reach the app at localhost.

How to answer

Name the namespace and the pause container, show the Docker flag. It proves you understand that "pod" is a Linux feature, not magic.

Scenario: large downloads hang inside containers on the corporate VPN

Developers report that apt-get update and git clone inside containers hang halfway, but curl of small pages works. On the host, everything works. The office recently moved to a new VPN.

Weak answer: "Docker networking is flaky; restart Docker and try again."

Strong answer: Small works, large hangs is the MTU signature. The VPN reduced the path MTU (say to 1400) but containers still use 1500. The host may use PMTUD or MSS clamping on its own sockets, while container traffic is forwarded and NATed. Confirm with ping -M do -s 1372 from inside a container to find the largest size that passes, and tcpdump on the host for missing ICMP "frag needed". Fix by setting the Docker network MTU (daemon.json "mtu", or per network com.docker.network.driver.mtu), or clamp TCP MSS on the host. Check also that 172.17.0.0/16 does not clash with a new VPN route.

60-second answer - "How does Docker networking work?": "Each container gets its own Linux network namespace, which is like a VRF: its own interfaces, routes and iptables. On the default setup Docker creates a veth pair per container, one end as eth0 inside, the other plugged into a Linux bridge, docker0, which is the gateway. Containers on the same bridge talk at L2. Going out, the host routes and MASQUERADEs. Coming in, -p 8080:80 adds a DNAT rule in PREROUTING, conntrack handles the reply, and a docker-proxy covers host-local traffic. On user-defined networks an embedded DNS at 127.0.0.11 resolves container names. For multi-host there is VXLAN overlay, and macvlan/ipvlan to sit on the physical LAN. Two gotchas I always mention: published ports bind to all interfaces and bypass ufw, and localhost inside a container is the container itself."
