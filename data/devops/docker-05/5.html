What -p 8080:80 really does (packet by packet)

Must know. This is the canonical home of the "-p at packet level" answer on this site; the VRF bridge at the top of this page is the one the other pages point back to.

Now the part you asked for most. We run docker run -d --name web -p 8080:80 nginx:1.30 and a laptop at 192.168.1.50 opens http://192.168.1.10:8080. Step through the journey. (To run the iptables and conntrack commands below on Windows or macOS, use WSL 2 Ubuntu with Docker Engine; see Lab setup.)

  1. Arrives. The TCP SYN reaches the host's eth0 with destination 192.168.1.10:8080. Nothing on the host needs to listen on 8080 for this to work (but see docker-proxy below).
  2. DNAT. In the nat table, PREROUTING jumps to Docker's DOCKER chain, which has a rule: TCP port 8080 → 172.17.0.2:80. The kernel rewrites the destination and creates a conntrack entry.
  3. Route. Because the destination is now 172.17.0.2, the routing table says "connected via docker0". This is forwarding, not local delivery, so the INPUT chain is never involved.
  4. Filter. The packet goes through the filter FORWARD chain. Docker sends it to DOCKER-USER first (the place for your rules), then to its own chains that accept traffic to published ports and isolate networks from each other.
  5. Switch. The bridge looks up the container's MAC in its forwarding table and sends the frame out of the veth port for web.
  6. Delivered. The frame pops out of the other end of the veth pair as eth0 inside the container. nginx, listening on 0.0.0.0:80, accepts the connection. It sees the real client IP 192.168.1.50.
  7. Reply. The response is routed back to the host side. Conntrack recognises the flow and reverses the NAT, so the laptop sees replies from 192.168.1.10:8080. Outbound connections started by the container use the separate MASQUERADE rule.

See the rules yourself

$ sudo iptables -t nat -S DOCKER
-N DOCKER
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80

$ sudo iptables -t nat -S POSTROUTING
-P POSTROUTING ACCEPT
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE

$ sudo conntrack -L -p tcp --dport 8080
tcp  6 431999 ESTABLISHED src=192.168.1.50 dst=192.168.1.10 sport=53122 dport=8080 src=172.17.0.2 dst=192.168.1.50 sport=80 dport=53122 [ASSURED] mark=0 use=1

$ ps -eo pid,args | grep [d]ocker-proxy
 4301 /usr/bin/docker-proxy -proto tcp -host-ip 0.0.0.0 -host-port 8080 -container-ip 172.17.0.2 -container-port 80

Exact rule text varies by Docker version and by whether your host uses iptables-legacy, iptables-nft or (experimental in Engine 29) native nftables. The shape is always the same: DNAT in, MASQUERADE out.

  • The DNAT rule (! -i docker0 means "not coming from the bridge itself") is the fast path. It is all kernel work, no extra process touches the bytes.
  • MASQUERADE rewrites the source of anything leaving 172.17.0.0/16 through another interface. That is how containers reach the internet.
  • The conntrack line shows both directions of the flow: original tuple and the reply tuple after DNAT. If you have debugged NAT on a firewall, this is identical.
  • docker-proxy is a small user-space process per published port. It handles cases that the DNAT rule does not catch, mainly connections to localhost:8080 from the host itself (locally generated packets do not pass PREROUTING). It also holds the port open so nothing else on the host can bind it. You can disable it with "userland-proxy": false, and Docker then uses hairpin NAT rules instead.

From your world

This is a textbook port-forward on a CPE router: DNAT on the WAN side, connected route to the LAN, stateful firewall in FORWARD, PAT/masquerade for egress. The only Docker-specific bits are the chain names. If you can debug a NAT box with conntrack -L and tcpdump on both sides, you can debug Docker networking. Where it breaks: Docker rewrites these chains whenever containers start and stop, so hand-made rules in Docker's own chains get wiped. Your rules belong in DOCKER-USER.

Security trap: "-p is public". -p 8080:80 binds 0.0.0.0 and [::], so the port is open on every interface of the host. Docker's own docs call this insecure by default. For something only you should reach (a database on a dev box), bind to loopback: -p 127.0.0.1:5432:5432. And note that ufw / firewalld rules do not protect published ports: the DNAT happens in PREROUTING and the packet is forwarded, so it never hits the INPUT chain that ufw filters. Filter in DOCKER-USER instead:

# allow only the office subnet to reach published container ports arriving on eth0
sudo iptables -I DOCKER-USER -i eth0 ! -s 10.20.0.0/16 -j DROP

# match the ORIGINAL published host port, not --dport (see the note below)
sudo iptables -I DOCKER-USER -i eth0 -p tcp -m conntrack --ctorigdstport 8080 --ctdir ORIGINAL ! -s 10.20.0.0/16 -j DROP

Interview follow-up: packets reach DOCKER-USER after DNAT, so to match the original host port use -m conntrack --ctorigdstport 8080 (and --ctorigdst for the host IP), not --dport 8080. By the time the packet is in FORWARD its destination is already container-IP:80, so a --dport 8080 rule never matches. Source-based rules like the first one work either way, because DNAT does not change the source.

What changed in Docker Engine 28 (2025): before it, a machine on the same LAN could add a route to 172.17.0.0/16 via your Docker host and reach container ports directly, even ports published only on 127.0.0.1 or not published at all, because the host simply forwarded those packets. Engine 28 adds rules in the iptables raw table (PREROUTING) that drop packets addressed to a container's IP unless they arrive from that container's own bridge, so unpublished ports really are private and loopback-published ports are not reachable from neighbours (28.0.1 closed a remaining gap). The escape hatch DOCKER_INSECURE_NO_IPTABLES_RAW=1 turns this protection off; do not set it. Source: Docker blog: Engine v28 hardening container networking and the Engine 28 release notes.
