Inside the default bridge: docker0 and veth pairs

Let us start two containers and look at what Docker built on the host.

docker run -d --name web nginx:1.30
docker run -d --name api nginx:1.30
ip -br addr show docker0
ip -br link | grep veth
bridge link show
$ ip -br addr show docker0
docker0          UP             172.17.0.1/16 fe80::42:9cff:fe1a:2b3c/64

$ ip -br link | grep veth
veth3a1b2c4@if6  UP             1e:4f:aa:10:22:31 <BROADCAST,MULTICAST,UP,LOWER_UP>
veth9d8e7f1@if8  UP             6a:12:bc:33:44:55 <BROADCAST,MULTICAST,UP,LOWER_UP>

$ bridge link show
7: veth3a1b2c4@if6: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master docker0 state forwarding priority 32 cost 2
9: veth9d8e7f1@if8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master docker0 state forwarding priority 32 cost 2

$ docker exec web cat /sys/class/net/eth0/iflink
7

Read that like a network engineer: docker0 is the gateway 172.17.0.1/16. Each container added one veth pair. The host end (veth3a1b2c4, ifindex 7) is a port on the bridge; its peer is ifindex 6, which lives inside the web container's namespace and is called eth0 there. The @if6 suffix and the iflink file are how you match the two ends.

Defaults worth knowing: the default bridge usually uses 172.17.0.0/16 with gateway 172.17.0.1. If that clashes with your office VPN or lab subnet, change it with "bip" or "default-address-pools" in /etc/docker/daemon.json. Subnet clashes with corporate networks are a real, common outage cause on developer laptops.
