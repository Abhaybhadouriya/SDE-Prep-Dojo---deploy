User-defined bridges and the embedded DNS

The default bridge is old behaviour kept for compatibility. It has one big missing feature: no name resolution. Containers can only find each other by IP, and IPs change on every restart. A user-defined bridge fixes this, and also isolates groups of containers from each other. Always create your own network.

docker network create shopnet
docker run -d --name db  --network shopnet -e POSTGRES_PASSWORD=dev postgres:17-alpine
docker run --rm --network shopnet alpine:3.24 sh -c "cat /etc/resolv.conf; nslookup db"
$ docker run --rm --network shopnet alpine:3.24 sh -c "cat /etc/resolv.conf; nslookup db"
# Generated by Docker Engine.
nameserver 127.0.0.11
options ndots:0
Server:         127.0.0.11
Address:        127.0.0.11:53

Non-authoritative answer:
Name:   db
Address: 172.18.0.2

Every container on a user-defined network is told its DNS server is 127.0.0.11. That is Docker's embedded DNS server. It answers names of containers (and their --network-alias names, and Compose service names) on the networks this container has joined, and forwards everything else (like google.com) to the resolvers the host uses. Under the hood, rules inside the container's namespace redirect port 53 on 127.0.0.11 to a listener run by dockerd, so the container never needs a real DNS server inside it.

Round-robin trick: give two containers the same alias (--network-alias search) and the embedded DNS returns both IPs. It is basic DNS load spreading, the same idea a Kubernetes headless Service uses. It is not real load balancing: clients cache answers and there are no health checks.

A container can be on several networks at once (one veth pair per network). A common pattern is a frontend network for the proxy and API, and a backend network for the API and database, so the proxy can never reach the database directly. Add --internal to a network to give it no route to the outside world at all.
