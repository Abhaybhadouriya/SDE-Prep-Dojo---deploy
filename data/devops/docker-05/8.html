MTU, performance and debugging toolkit

The MTU trap

Inside a VPN, a cloud overlay, or an overlay network, the real path MTU can be smaller than 1500. A container that still sends 1500-byte packets gets them dropped or fragmented. The classic symptom: small requests work, large responses hang (TLS handshakes with big certificates, git clone, apt-get stalling mid-download). Fix it by setting the network MTU, for example docker network create -o com.docker.network.driver.mtu=1400 mynet, or "mtu" in daemon.json for the default bridge. If ICMP "fragmentation needed" messages are blocked somewhere, path MTU discovery cannot save you, which you probably know from long nights with GRE tunnels.

How much does NAT cost?

For most web services the bridge + NAT path is not the bottleneck: it is the same kernel forwarding and conntrack you would have on any Linux router. It starts to matter for very high packet rates (many small UDP packets) or huge numbers of short connections, where the veth hop and conntrack table become visible. Measure first; if it matters, --network host or the routed gateway mode (container IPs routed, no NAT) remove the translation step.

The debugging order

  1. Is the app listening on the right address? docker exec web ss -ltn (or the netshoot trick). 127.0.0.1:80 is the bug; 0.0.0.0:80 is fine.
  2. Is the port published? docker port web, and the PORTS column of docker ps.
  3. Are they on the same network? docker network inspect shopnet lists attached containers and IPs.
  4. Does the name resolve? docker exec api nslookup db. No answer on the default bridge is expected.
  5. Where do packets stop? tcpdump -ni docker0 port 80 on the host, or enter the namespace: sudo nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n tcpdump -ni eth0.
  6. Is a firewall eating it? sudo iptables -t nat -S, sudo iptables -S DOCKER-USER, and the packet counters in iptables -L -v -n.
$ sudo nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0@if7         UP             172.17.0.2/16

nsenter -n runs a host binary inside the container's network namespace only. Your host's ip, ss and tcpdump work even if the image has no tools at all. This is the single most useful trick for a networking engineer on a Docker host.
