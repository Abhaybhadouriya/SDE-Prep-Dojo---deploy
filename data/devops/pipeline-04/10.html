Is running Kafka on Kubernetes a good idea?

You asked this directly, so here is a straight answer: yes, with an operator, if your team runs Kubernetes well; otherwise a managed service is often the better trade.

Good reasons
  • One platform for apps and Kafka: same GitOps (the cluster is synced from a git repo by a tool like Argo CD), same monitoring, same RBAC (role-based access control: who may change which objects)
  • Operators encode the hard runbooks (safe rolling restarts, cert rotation, scaling)
  • Topics and users as code, reviewed in pull requests
  • Easy dev/test clusters that match production
Real costs
  • Kafka is stateful and disk-heavy; you need good persistent volumes and to understand zonal disks
  • Clients outside the cluster need per-broker addresses (see below)
  • Noisy neighbours on shared nodes can hurt latency; production often uses dedicated node pools
  • Your team now operates Kafka, not just uses it; managed options (MSK, Confluent Cloud, Event Hubs) take that away for a price

The number one gotcha: clients must reach the leader broker

This is why you cannot put one plain load balancer in front of Kafka and call it done: the load balancer would send a produce request for partition 0 to a broker that is not its leader. Strimzi solves it with external listener types (nodeport, loadbalancer, ingress, route) that create one address per broker and set each broker's advertised listener. ShopStream keeps everything inside the cluster, so it only uses type: internal. The same "one leader per partition" idea is explored in KRaft & cluster metadata and Operations & Kafka on K8s.
