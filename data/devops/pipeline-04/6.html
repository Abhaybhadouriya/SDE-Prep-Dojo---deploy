Steps 6 and 7: images, config and the apps

Getting images into the cluster without a registry

A real cluster pulls images from a registry. kind can skip that: kind load docker-image copies an image from your laptop's Docker into each node's containerd. The manifests use imagePullPolicy: IfNotPresent, so the kubelet uses the copied image instead of trying to download shopstream/enricher:dev from Docker Hub.

docker compose build
for s in order-api enricher postgres-sink analytics; do kind load docker-image shopstream/$s:dev --name shopstream; done
# PowerShell:
# foreach ($s in "order-api","enricher","postgres-sink","analytics") { kind load docker-image "shopstream/${s}:dev" --name shopstream }

Config and secrets

  name: shopstream-config
  namespace: shopstream
data:
  KAFKA_BOOTSTRAP: shopstream-kafka-bootstrap.kafka.svc:9092
  TOPIC_CREATED: orders.created
  CATALOG_SOURCE: postgres
  TRANSIENT_FAIL_RATE: "0.0"
  PROCESSING_DELAY_MS: "0"

The Secret named shopstream-db lives in its own file, 20-secret.example.yaml, with an obvious placeholder password. Apply that file or create your own Secret with kubectl create secret generic (the command is in the file's comment), never both. The example file is deliberately not listed in kustomization.yaml: otherwise a later kubectl apply -k k8s/ would silently reset your real password to the placeholder, and Postgres, which keeps the password it was first initialised with, would start rejecting the apps. It is a placeholder on purpose: a Secret is only base64-encoded in the API, not encrypted, unless the cluster enables encryption at rest. Real clusters create it from a secret manager (External Secrets, Sealed Secrets, a cloud vault). See ConfigMaps & Secrets.

One Deployment, read slowly

The order-api Deployment shows every production habit in about 50 lines. These are the important parts:

# k8s/30-order-api.yaml (excerpt)
spec:
  # no replicas: field on purpose - the HPA owns the count (min 2)
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxUnavailable: 0, maxSurge: 1}
  template:
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile: {type: RuntimeDefault}
      containers:
        - name: order-api
          image: shopstream/order-api:dev
          envFrom:
            - configMapRef: {name: shopstream-config}
          env:
            - name: HOSTNAME   # pod name => unique transactional.id / client.id per pod
              valueFrom: {fieldRef: {fieldPath: metadata.name}}
          startupProbe:          # give the producer time to connect at boot
            httpGet: {path: /healthz, port: http}
            periodSeconds: 2
            failureThreshold: 30
          livenessProbe:         # restart only if the process is stuck
            httpGet: {path: /healthz, port: http}
            periodSeconds: 10
          readinessProbe:        # stop sending traffic when Kafka is unreachable
            httpGet: {path: /readyz, port: http}
            periodSeconds: 5
            failureThreshold: 3
          resources:
            requests: {cpu: 200m, memory: 128Mi}   # HPA % is computed against requests
            limits: {memory: 256Mi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: [ALL]}
  1. Three different probes, three different jobs. /healthz only says "the process answers". /readyz asks Kafka for topic metadata. If Kafka is unreachable, the pod is taken out of the Service (no traffic) but not restarted, because restarting would not fix Kafka. Using /readyz as the liveness probe would be a classic mistake: a Kafka blip would restart every API pod at once.
  2. No replicas: field. The HPA owns the replica count. If the manifest said replicas: 2, every kubectl apply would reset the Deployment to 2 and the HPA would have to scale up again: a scale-down in the middle of a load test or an incident. The enricher Deployment leaves it out for the same reason (KEDA owns it there, and a reset would also cause a consumer rebalance).
  3. maxUnavailable: 0, maxSurge: 1: during a rollout, start one new pod, wait until it is ready, then stop one old pod. Capacity never drops.
  4. The pod name as HOSTNAME (the Downward API). For the enricher this becomes transactional.id = enricher-<pod name>: unique per pod, as zombie fencing needs (see Stream Processing).
  5. terminationGracePeriodSeconds: on delete, the kubelet sends SIGTERM, waits this long, then SIGKILL. The services' GracefulExit class turns SIGTERM into "finish the batch, commit, close the consumer", so the member leaves the group cleanly and the rebalance is fast. The enricher gets 45 seconds.
  6. Memory limit but no CPU limit. A memory limit protects the node (over it, the kernel OOM-kills the container). No CPU limit avoids CFS throttling (the kernel's Completely Fair Scheduler pauses a cgroup that used up its CPU quota for the current 100 ms period, even when the node has idle cores); the CPU request still reserves a share and is what the HPA percentage is based on.
  7. Locked-down security context. Non-root user 10001 (the Dockerfile creates it), read-only root filesystem, all Linux capabilities dropped, default seccomp profile.

From your world

Readiness is like BFD pulling a next hop out of an ECMP group while the box stays up; liveness is the hardware watchdog that reboots a hung process. You would never wire the watchdog to "is my upstream neighbour reachable", for the same reason you should not wire liveness to Kafka. The Downward API is like a line card reading its slot number from the backplane at boot. Where it breaks: BFD reacts in milliseconds, but a readiness probe with periodSeconds: 5 and failureThreshold: 3 needs about 15 s to pull a pod out, and kube-proxy needs a moment more to update every node, so a few requests still reach a pod that has just lost Kafka.
