What an operator actually does

You asked "who notices, how, and what does it write?" for Kubernetes. Here is the answer for Strimzi:

An operator earns its keep on the hard operations: a rolling restart that restarts one broker at a time and waits until its partitions are back in sync before touching the next; never restarting the active KRaft controller first; renewing TLS certificates; growing disks. A plain StatefulSet would restart pods in order without knowing anything about Kafka. (Strimzi actually manages broker pods through its own StrimziPodSet resource rather than a StatefulSet, so it can treat each broker individually.)

The Kafka cluster as YAML

Two node pools: three nodes that are only KRaft controllers (they hold the cluster metadata log and elect a leader with Raft) and three that are only brokers (they hold data). Then one Kafka resource with the cluster-wide settings:

# k8s/10-kafka-cluster.yaml (excerpts)
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: broker
  namespace: kafka
  labels:
    strimzi.io/cluster: shopstream
spec:
  replicas: 3
  roles: [broker]
  storage:
    type: jbod
    volumes:
      - {id: 0, type: persistent-claim, size: 5Gi, deleteClaim: true, kraftMetadata: shared}
  resources:
    requests: {cpu: 200m, memory: 1Gi}
    limits: {memory: 1536Mi}
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: shopstream
  namespace: kafka
spec:
  kafka:
    version: 4.3.2
    metadataVersion: 4.3-IV0
    listeners:
      - {name: plain, port: 9092, type: internal, tls: false}
      - {name: tls, port: 9093, type: internal, tls: true}
    # Spread replicas of each partition across zones (kind worker labels above).
    rack:
      topologyKey: topology.kubernetes.io/zone
    config:
      default.replication.factor: 3
      min.insync.replicas: 2
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      auto.create.topics.enable: false
  entityOperator:
    topicOperator: {}   # turns KafkaTopic CRs into real topics
    userOperator: {}    # turns KafkaUser CRs into users/ACLs
  kafkaExporter:
    topicRegex: 'orders\..*'
    groupRegex: ".*"
  • type: jbod: JBOD = Just a Bunch Of Disks. Kafka can spread its log directories across several volumes; here there is one (id 0), which also holds the KRaft metadata (kraftMetadata: shared).
  • rack.topologyKey: Strimzi sets each broker's broker.rack from the zone label of its node. Kafka then places the 3 replicas of every partition in 3 different zones (so the ISR, the in-sync replicas, normally spans all three zones), so losing a whole zone loses one copy, not two.
  • transaction.state.log.*: the enricher uses transactions; the coordinator's own log must be replicated as safely as the data.
  • auto.create.topics.enable: false: a typo in a topic name should fail loudly, not silently create a 1-partition topic.
  • kafkaExporter: Strimzi runs the same lag exporter you used in Compose, so dashboards work unchanged.
  • deleteClaim: true: deleting the cluster deletes its disks. Right for a lab, dangerous in production.

Pod names are <cluster>-<pool>-<node id>. Node IDs are unique across both pools, so your brokers may be numbered 0-2 or 3-5. That is why the Kubernetes drill script (scripts/chaos/k8s-drills.sh and .ps1) never hard-codes a name: it finds the broker pods by label, kubectl -n kafka get pods -l strimzi.io/pool-name=broker, and uses the first one to run admin tools and the second one as the victim.

Strimzi also creates Services. The one apps use is shopstream-kafka-bootstrap, a normal ClusterIP Service in front of all brokers. Its full DNS name from another namespace is shopstream-kafka-bootstrap.kafka.svc, which is exactly what our ConfigMap says.
