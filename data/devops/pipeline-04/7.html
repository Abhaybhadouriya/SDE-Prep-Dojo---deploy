Two autoscalers, two signals

This is the most interview-worthy idea on the page. The order-api and the enricher need different autoscalers, because they are busy in different ways.

Install the two autoscaler helpers first

kind ships neither piece. Without metrics-server the HPA has no CPU numbers; without KEDA the ScaledObject in 31-enricher.yaml is an unknown resource type. Run this once per cluster (the same commands are in k8s/README.md, steps 3 and 3b):

# metrics-server: CPU/memory numbers for the HPA and for kubectl top
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# kind's kubelets use self-signed certificates, so metrics-server must skip verifying them (lab only!)
kubectl -n kube-system patch deploy metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deploy/metrics-server
kubectl top nodes            # numbers instead of an error = working

# KEDA v2.21.1 (server-side apply: its CRDs are too big for client-side apply)
kubectl apply --server-side -f https://github.com/kedacore/keda/releases/download/v2.21.1/keda-2.21.1.yaml
kubectl -n keda rollout status deploy/keda-operator

PowerShell: the JSON patch is easiest from a file. Save [{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}] as patch.json and run kubectl -n kube-system patch deploy metrics-server --type=json --patch-file patch.json.

The HPA for order-api

# k8s/30-order-api.yaml (HPA part)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
  namespace: shopstream
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: order-api}
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 70}
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120   # avoid flapping

The HPA controller (inside kube-controller-manager) runs every 15 seconds and computes desired = ceil(current replicas x current metric / target). With 2 pods at 140 % of their CPU request: ceil(2 x 140 / 70) = 4. It needs metrics-server (installed in the block above); without it, kubectl get hpa shows <unknown>/70% and nothing scales.

KEDA for the enricher

# k8s/31-enricher.yaml (ScaledObject part)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: enricher
  namespace: shopstream
spec:
  scaleTargetRef: {name: enricher}
  minReplicaCount: 1
  maxReplicaCount: 6           # = partitions of orders.created; more consumers would sit idle
  pollingInterval: 15
  cooldownPeriod: 120
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: shopstream-kafka-bootstrap.kafka.svc:9092
        consumerGroup: enricher
        topic: orders.created
        lagThreshold: "100"        # target lag per replica
        activationLagThreshold: "10"
        offsetResetPolicy: earliest
        version: "3.9.0"           # protocol version KEDA's Kafka client speaks
  1. Lag grows. A load spike, or the PROCESSING_DELAY_MS knob, makes one enricher fall behind. Total lag is 480.
  2. KEDA measures. Every pollingInterval (15 s) the KEDA operator asks Kafka for the group's committed offsets and each partition's end offset, and serves the lag to Kubernetes as an external metric.
  3. The HPA decides. KEDA created an HPA for the enricher (named keda-hpa-enricher) with a target of 100 per replica: ceil(480 / 100) = 5. It is capped at maxReplicaCount: 6; KEDA's Kafka scaler also does not go above the partition count by default.
  4. Pods start and join. The Deployment adds pods. Each joins consumer group enricher, and the cooperative-sticky assignor moves only the partitions that must move.
  5. Lag drains. Five consumers drain six partitions in parallel.
  6. Scale down slowly. With minReplicaCount: 1, scaling down is done by the HPA, which by default waits a 5-minute stabilization window, so a short dip does not cause another rebalance. (KEDA's cooldownPeriod only applies to scaling all the way to zero.)

Do not create your own HPA for a Deployment that a ScaledObject targets. KEDA owns one. Two HPAs fighting over the same replica count is a confusing failure. And remember why maxReplicaCount is 6: in a classic consumer group each partition goes to one member, so a seventh enricher would sit idle.

Columns are trimmed and the numbers are an example; how far it scales depends on your laptop. To force it, set PROCESSING_DELAY_MS: "50" in the ConfigMap and restart the enricher (kubectl -n shopstream rollout restart deploy/enricher): each instance then handles about 20 messages a second.

From your world

Scaling on lag is scaling on queue depth, the same signal you would use to add a link to a LAG bundle or to trigger a congestion alarm. CPU is a lagging, indirect signal for a consumer; queue depth is the direct one. Where it breaks: adding a link to a bundle is instant, but adding a Kafka consumer costs a rebalance during which some partitions pause, so you scale in steps and slowly scale down.
