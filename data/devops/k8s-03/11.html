What is a pod, and why does Kubernetes schedule pods instead of containers?

A pod is the smallest deployable unit: one or more containers that are always co-located on the same node and share a network namespace (one IP, talk over localhost), IPC and UTS namespaces, and optionally volumes. Kubernetes schedules pods because some processes must live together, like an app and a proxy or log-shipper sidecar, and the pod guarantees they are placed, started, scaled and removed as one unit. Pods are ephemeral: if one is lost, a controller creates a new pod, with a new name and usually a new IP, rather than repairing the old one.

How to answer

Definition, then the "why" (co-location), then one Linux detail (shared network namespace held by the pause container) to show depth, then "ephemeral, use Services".

Likely follow-ups
  • What does the pause container do?
  • When would you put two containers in one pod?
  • What happens to the pod IP when a container restarts?
Explain liveness, readiness and startup probes. How can they hurt you?

The kubelet runs all three. A startup probe gates the other two until the app has booted, which protects slow starters. A liveness probe restarts the container when it fails, for unrecoverable hangs. A readiness probe removes the pod from Service endpoints when it fails, without restarting it, for warm-up, overload or shutdown. They hurt when misused: a liveness probe that checks a downstream dependency causes cascading restarts when that dependency slows down; a liveness probe without a startup probe kills slow-booting apps in a loop; tight timeouts (default 1 second) turn a busy but healthy app into restarts; and no readiness probe means traffic reaches pods before they are ready.

How to answer

Table in your head: probe, what fails, what happens. Then give the cascading-restart failure story. That story is what separates a strong answer.

Likely follow-ups
  • What should a /healthz endpoint check?
  • What are the default probe timings?
  • How does readiness help during a rolling update?
A pod is in CrashLoopBackOff. Walk me through how you debug it.

CrashLoopBackOff is not a phase; it means the container keeps exiting and the kubelet is waiting between restarts with exponential back-off from 10 seconds up to 5 minutes. I start with kubectl describe pod to read the events and the Last State, especially the exit code and reason. Then kubectl logs --previous to see the output of the crashed run. Exit code 1 usually means an application error such as bad config or a missing environment variable or Secret; 137 means SIGKILL, often OOMKilled because the memory limit is too low; a failing liveness probe also shows in events. I then check the command and args, the image tag, mounted ConfigMaps and Secrets, and resource limits. If the image has no shell, I use kubectl debug with an ephemeral container, or run the image locally with the same env.

How to answer

Define it correctly first (not a phase). Then a fixed order: describe, logs --previous, exit code, then hypotheses by exit code. Interviewers want a method, not a guess.

Likely follow-ups
  • How do you tell OOMKilled from a liveness kill?
  • The logs are empty. Now what?
  • How would you prevent bad config from reaching production?
How do you make sure no requests are dropped when pods are terminated during a deploy?

On deletion, endpoint removal and container shutdown happen in parallel, so a pod can still get a few requests after it starts terminating. I handle it in layers: a readiness probe so only ready pods get traffic; a short preStop sleep so endpoints, kube-proxy rules and external load balancers stop routing to the pod before the app is signalled; the app handles SIGTERM by stopping new connections, draining in-flight requests and exiting; the process is PID 1 or behind an init like tini so it actually receives the signal; and terminationGracePeriodSeconds is longer than preStop plus the drain time. At the Deployment level I use a rolling update with maxUnavailable 0 and a PodDisruptionBudget for voluntary disruptions like node drains.

How to answer

Name the race condition first. Then go from network (readiness, preStop) to process (SIGTERM, PID 1) to rollout settings. Mention numbers: 30-second default grace period.

Likely follow-ups
  • What about long-lived connections such as WebSockets or gRPC streams?
  • What is a PodDisruptionBudget?
Init containers vs sidecar containers: what is the difference, and what changed with native sidecars?

Init containers run before the app containers, one at a time in order, and each must exit successfully; they are for setup like waiting for a dependency or running a migration. Sidecars run alongside the app for its whole life, for example log shippers or service-mesh proxies. Classic sidecars were just extra entries in containers, with no start or stop ordering, which caused problems: the app could start before the proxy was ready, and Jobs never completed because the sidecar never exited. Native sidecars, stable since Kubernetes 1.33, are init containers with restartPolicy: Always: they start before the app containers, keep running, and are stopped after them, and they do not block Job completion.

How to answer

Two definitions, the old problem, the new fix with the field name and version. Short and precise.

Likely follow-ups
  • What is a service mesh and why does it need a sidecar?
  • Ambassador vs adapter patterns?
Two containers in the same pod: how do they talk, and can both listen on port 8080?

They share one network namespace, so they talk over localhost and share the pod's IP and port space. That also means both cannot bind port 8080; the second bind fails with "address already in use". They can also share files through a volume mounted in both, such as an emptyDir, and use IPC because the IPC namespace is shared. Their filesystems and, by default, process trees are separate.

How to answer

Answer the question directly, then name exactly which namespaces are shared and which are not. Your Linux background makes this an easy win.

Likely follow-ups
  • How would container A send a signal to container B? (shareProcessNamespace)
  • How do two pods talk to each other?

Scenario: every pod restarted at once when the database got slow

During a sale, the database's latency rises from 5 ms to 2 seconds for about a minute. Within that minute, all 40 pods of your order service restart at the same time, and the service is fully down for several minutes even after the database recovers. What happened and how do you fix it?

Weak answer: "The database was down, so the pods crashed. We should add more database replicas."

Strong answer: "Pods restarting all together points at the kubelet acting on a probe, not at a crash. I would check events for 'Liveness probe failed'. Most likely the liveness endpoint queries the database and the probe's 1-second timeout was exceeded three times in a row, so every container was restarted. The restarts then caused a thundering herd of new connections and cold caches against a database that was already struggling, which extended the outage. Fix: make liveness check only the process itself, move dependency checks to readiness (or drop them, and rely on timeouts and circuit breakers in the app), add a startup probe, give realistic timeouts, and add connection-pool limits and jittered retries. Then add an alert on restart counts, since restart spikes are an early warning."

Likely follow-ups
  • Should readiness check the database? What are the trade-offs?
  • What is a circuit breaker? (see Resilience Patterns)
