Graceful shutdown: how a pod dies without dropping requests

Must know (SDE-1)

Pods are deleted all the time: rollouts, scale-down, node drains. If a pod just vanished, requests in flight would fail. Kubernetes gives it a polite goodbye. Click through:

  1. Delete. The API server sets a deletionTimestamp on the pod. It shows as Terminating. The countdown of terminationGracePeriodSeconds (default 30 s) starts now.
  2. Two things at once. The EndpointSlice controller removes the pod from its Services, and kube-proxy on every node (plus any external load balancer) must catch up. At the same time, the kubelet starts shutting the pod down. These happen in parallel, so for a moment the pod may still receive new requests.
  3. preStop hook. If the container has a preStop hook, the kubelet runs it first. A short sleep (a few seconds) here gives the rest of the cluster time to stop sending traffic.
  4. SIGTERM. The kubelet (through the runtime) sends SIGTERM to the container's main process (PID 1). A well-behaved app stops accepting new connections, finishes in-flight work, closes database connections and exits 0.
  5. SIGKILL. If anything is still running when the grace period ends, it is killed with SIGKILL (exit code 137). The pod object is then removed.
spec:
  terminationGracePeriodSeconds: 45      # total budget, including preStop
  containers:
    - name: orders-api
      image: ghcr.io/example/orders-api:1.4.2
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 5"]   # let endpoints and LBs drain first

The PID 1 trap: SIGTERM goes to PID 1 of the container. If your Dockerfile uses the shell form (CMD java -jar app.jar), PID 1 is /bin/sh, which may not forward the signal, so your app never hears it and is SIGKILLed after 30 seconds. Use the exec form (CMD ["java", "-jar", "app.jar"]) or a tiny init such as tini. See Writing a Dockerfile. Newer Kubernetes versions also offer a built-in sleep action for preStop, so the image does not need a sleep binary.
