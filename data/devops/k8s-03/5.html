Multi-container pods: init containers and sidecars

Must know (SDE-1)

There are two special kinds of helper containers, and one newer combination of the two:

KindWhen it runsTypical use
Init container (initContainers)Before the app containers, one at a time, in order. Each must exit successfully before the next starts.Wait for a database to be reachable, run a schema migration, download config, fix file permissions.
Classic sidecar (a second entry in containers)At the same time as the app, no ordering guarantees.Log shipper, metrics exporter, a proxy such as Envoy in a service mesh.
Native sidecar (an init container with restartPolicy: Always)Starts before the app containers and keeps running; stops after them. Stable (GA) since Kubernetes 1.33.Same jobs as a classic sidecar, but with correct ordering. Fixes the old "Job never finishes because the mesh sidecar keeps running" problem.

Common named patterns you may hear in interviews: sidecar (adds a feature next to the app, such as log shipping), ambassador (a local proxy that the app talks to on localhost, which then talks to the outside world), and adapter (converts the app's output into a standard format, such as exposing metrics for Prometheus).

Click through to see the start-up order of a pod with one init container, one native sidecar and one app container.

  1. Sandbox. The kubelet asks the runtime for the pod sandbox: namespaces, the pause container, and a pod IP from the CNI plugin. Init containers already have networking.
  2. Init container runs. wait-for-db loops until the database answers. Nothing else starts yet. If it exits with an error, the kubelet retries it (depending on the pod's restart policy).
  3. Init done, sidecar starts. wait-for-db exited 0. The next init entry is the native sidecar (restartPolicy: Always): it starts and keeps running; once its startup probe (if any) passes, the kubelet moves on.
  4. App starts. Now orders-api starts, with the log shipper already in place. Its probes begin.
  5. Ready. When readiness passes for the containers, the pod is Ready and a Service starts sending it traffic. On shutdown, the order reverses: app first, sidecar last.
apiVersion: v1
kind: Pod
metadata:
  name: orders
  labels:
    app: orders
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh", "-c", "until nc -z postgres 5432; do echo waiting; sleep 2; done"]
    - name: log-shipper              # a native sidecar: init container + restartPolicy Always
      image: fluent/fluent-bit:3.1
      restartPolicy: Always
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  containers:
    - name: orders-api
      image: ghcr.io/example/orders-api:1.4.2   # placeholder image name
      ports:
        - containerPort: 8080
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
  volumes:
    - name: logs
      emptyDir: {}

Watch an init container wait: apply the pod above without a postgres Service. kubectl get pod orders shows Init:0/2, and kubectl logs orders -c wait-for-db prints "waiting" every 2 seconds. That is exactly how you debug a pod stuck in Init.
