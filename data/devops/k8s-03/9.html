Advanced pod facts worth knowing

Deep dive (platform teams)
  • Resources live on containers. Each container can set requests (what the scheduler reserves) and limits (the cgroup ceiling). Go over the memory limit and the kernel OOM killer ends the container (OOMKilled, exit 137); go over the CPU limit and you are throttled. The pod's QoS class (Guaranteed, Burstable, BestEffort) is derived from these. Full story in Scheduling & Autoscaling.
  • In-place resize (GA in 1.35). You can now change a running pod's CPU and memory through its resize subresource without recreating it; a per-resource resizePolicy says whether the container must restart.
  • Static pods. Pods defined by files in a folder on the node (for example /etc/kubernetes/manifests), started by the kubelet without the scheduler. That is how kubeadm and kind run the control plane itself; see Architecture.
  • Ephemeral debug containers. kubectl debug -it pod/web --image=busybox:1.36 --target=nginx adds a temporary container to a running pod, sharing its namespaces, so you can debug "distroless" images that have no shell.
  • Pod-level security. securityContext sets the user ID, drops Linux capabilities, makes the root filesystem read-only. Since 1.36, user namespaces (hostUsers: false) are stable: root inside the pod maps to an unprivileged user on the host. See Security & RBAC.
  • Pods for stateful apps (databases, Kafka brokers) need stable names and disks, which bare pods and Deployments do not give. That is what StatefulSets are for, and why Kafka on Kubernetes uses them (Kafka on K8s).

From your world

Requests and limits are cgroup v2 knobs you already know. The CPU limit becomes cpu.max (CFS quota per period, the source of throttling); the CPU request becomes cpu.weight (relative share under contention); the memory limit becomes memory.max (hit it and the kernel OOM killer picks a process). The QoS class sets oom_score_adj, so BestEffort pods are killed first when the node itself runs low on memory. Since 1.35, the kubelet refuses to start on cgroup v1 by default.

Two different "namespaces" - do not mix them up. A Kubernetes namespace (kubectl get pods -n kube-system) is only a folder for API objects: it groups names, RBAC rules and quotas inside the API server. It creates nothing in the kernel. A Linux namespace (net, pid, mnt, ipc, uts, user) is a kernel feature that isolates what a process can see; the pod's containers share some of these. Two pods in the same Kubernetes namespace still get separate Linux network namespaces, and by default can still reach pods in other Kubernetes namespaces over the network.
