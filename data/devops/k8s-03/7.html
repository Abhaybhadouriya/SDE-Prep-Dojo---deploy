Health checks: startup, liveness and readiness probes

Must know (SDE-1)

"Running" only means the process exists. It does not mean the app works. Probes let the kubelet ask the app how it is doing. There are three, and confusing them is one of the most common production mistakes.

Explain like I'm 5

A liveness probe is poking a sleeping friend: "Are you alive?" No answer three times, and the teacher calls for help (restarts them). A readiness probe is asking "Are you ready to play?" A friend can be awake but still tying their shoes, so you just do not pass them the ball yet. A startup probe is for the friend who always takes a long time to wake up: you do not start poking until they are up.

ProbeQuestionIf it failsUse it for
startupProbeHas the app finished starting?Keeps waiting; after failureThreshold failures, the container is restarted. Liveness and readiness are not run until it passes.Slow starters (a JVM app warming caches) so liveness does not kill them during boot.
livenessProbeIs the app stuck beyond repair?The kubelet restarts the container.Deadlocks and hangs that the app cannot recover from.
readinessProbeCan it serve traffic right now?Pod is removed from Service endpoints (no restart). Added back when it passes.Warming up, overloaded, temporarily disconnected; also during shutdown.

Probes can be an HTTP GET (any 2xx or 3xx status is success), a TCP connect, a gRPC health check, or a command run inside the container (exec, exit 0 is success). The default timing is: every 10 s (periodSeconds), 1 s timeout, failure after 3 consecutive failures, success after 1. A sensible setup for a web API:

containers:
  - name: orders-api
    image: ghcr.io/example/orders-api:1.4.2
    ports:
      - containerPort: 8080
    startupProbe:              # up to 30 x 2 s = 60 s to boot
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 2
      failureThreshold: 30
    livenessProbe:             # only "is this process wedged?" - no dependency checks
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
    readinessProbe:            # "can I take requests right now?"
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 2

From your world

A readiness probe is like BFD or an IP SLA tracker that withdraws a route or pulls a member out of an ECMP group: the box stays up, it just stops receiving traffic. A liveness probe is a hardware watchdog: if the process stops kicking it, it gets reset. Where the analogy breaks: a liveness probe is checked from outside the process over the network or by exec, so a slow response (beyond the 1-second default timeout) counts as a failure even if the app is only busy, not stuck.

The classic outage: a liveness probe that checks the database. The database slows down for 30 seconds, every pod's liveness fails, the kubelet restarts every pod at once, all of them reconnect to the already-struggling database at the same time, and a small slowdown becomes a full outage. Liveness should only check "is this process alive". Put dependency checks in readiness, if anywhere.
