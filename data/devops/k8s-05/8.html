Cluster DNS and the ndots:5 trap

Must know (SDE-1)

CoreDNS runs as a Deployment (usually 2 pods) behind a Service conventionally named kube-dns. Every Service gets a name:

  • backend - works from the same namespace
  • backend.payments - Service backend in namespace payments
  • backend.payments.svc.cluster.local - the fully qualified name
  • Headless Service of a StatefulSet: kafka-0.kafka-headless.kafka.svc.cluster.local resolves to that one pod's IP
$ kubectl exec -it frontend-5c9d -- cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

$ kubectl exec -it frontend-5c9d -- nslookup backend
Server:    10.96.0.10
Address:   10.96.0.10:53
Name:      backend.default.svc.cluster.local
Address:   10.96.45.10

The trap: ndots:5 means "if a name has fewer than 5 dots, try the search domains first". So looking up api.stripe.com (2 dots) first tries api.stripe.com.default.svc.cluster.local, then .svc.cluster.local, then .cluster.local - each failing (often for both A and AAAA records) - before the real lookup. A chatty service calling external APIs can multiply DNS load several times and add latency. This is one of the most famous Kubernetes production gotchas (see the Kubernetes failure stories).

spec:
  dnsConfig:
    options:
    - name: ndots
      value: "2"        # names with 2+ dots are tried as absolute first

You might confuse this with... a Kubernetes namespace (like payments in the DNS name) has nothing to do with a Linux network namespace. A K8s namespace is a naming and permission folder in the API. A pod's Linux network namespace is the kernel object holding its eth0. Pods in different K8s namespaces talk freely unless a NetworkPolicy says otherwise.
