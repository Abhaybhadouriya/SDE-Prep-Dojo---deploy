Pod networking inside one node

Must know (SDE-1)

When the kubelet starts a pod, the container runtime first creates a pod sandbox: a tiny "pause" process that owns a fresh network namespace. Then the runtime calls the CNI plugin with the command ADD. The plugin:

  1. Creates a veth pair - one end becomes eth0 inside the pod's namespace, the other end stays on the host (named like veth3a9f... or cali...).
  2. Asks IPAM for an address - IPAM (IP address management) is a separate small plugin that hands out an IP from this node's pod CIDR, for example 10.244.1.7.
  3. Wires the host side - attaches it to a Linux bridge (cni0, Flannel/bridge plugin style) or adds a /32 host route to it (Calico/Cilium style).
  4. Sets the pod's default route and returns the IP as JSON to the runtime, which reports it to the kubelet, which writes it into the pod's status.podIP.

The CNI config lives on every node in /etc/cni/net.d/ and the plugin binaries in /opt/cni/bin/. A trimmed example (Flannel):

{
  "name": "cbr0",
  "cniVersion": "1.0.0",
  "plugins": [
    { "type": "flannel", "delegate": { "hairpinMode": true, "isDefaultGateway": true } },
    { "type": "portmap", "capabilities": { "portMappings": true } }
  ]
}

hairpinMode: true lets a pod reach itself through its own Service IP (the packet leaves on the veth, is DNATed back to the same pod, and must be allowed to go back out the port it came in on, a "hairpin" turn). isDefaultGateway makes the bridge the pod's default route.

$ kubectl get pods -o wide
NAME        READY   STATUS    IP            NODE
backend-1   1/1     Running   10.244.1.7    node-1
backend-2   1/1     Running   10.244.2.9    node-2

$ kubectl get node node-1 -o jsonpath='{.spec.podCIDR}'
10.244.1.0/24

# on node-1
$ ip route
default via 192.168.1.1 dev eth0
10.244.1.0/24 dev cni0 proto kernel scope link src 10.244.1.1
10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10

Look at the third line: "to reach node-2's pods, go via flannel.1". That device is a VXLAN tunnel endpoint. Which brings us to the big question.

From your world

This is plain Linux: ip netns, ip link add type veth, a Linux bridge acting as a soft L2 switch, and a routing table. You could build it by hand with a dozen ip commands. The pause container is just a process that keeps /proc/<pid>/ns/net alive while app containers come and go. Where it breaks: you never configure it by hand; the CNI binary does it in milliseconds on every pod start, and does the reverse on DEL.

Go deeper. On EKS the VPC CNI gives every pod a real VPC IP, so subnet sizing matters: see AWS Networking: CIDR planning.
