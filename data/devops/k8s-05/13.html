Five boxes. The Service is not a box in the data path: it is a DNS name plus a DNAT rule on the sending node.

Explain the Kubernetes networking model.

Every pod gets its own IP, every pod can reach every other pod across nodes without NAT, and node agents can reach their pods. Kubernetes defines the rules; a CNI plugin implements them. That gives four problems: container-to-container (shared network namespace, localhost), pod-to-pod (CNI: veth plus bridge or routes, and an overlay like VXLAN, BGP routing, or cloud-native IPs between nodes), pod-to-Service (a stable virtual IP that kube-proxy or eBPF translates to pod IPs, plus CoreDNS for names), and external-to-Service (NodePort, LoadBalancer, Ingress or Gateway).

How to answer

State the three rules, then list the four problems and one mechanism each. If you have a networking background, say so and offer to go deep on one ("I can walk a packet through the DNAT and VXLAN if useful").

Likely follow-ups
  • Overlay vs BGP - trade-offs? (Encap overhead and MTU vs needing the fabric to carry pod routes.)
  • What does the pause container do?
How does a ClusterIP actually work? Can you ping it? Who answers ARP for it?

A ClusterIP is a virtual IP allocated by the API server from the service CIDR. It is not on any interface. kube-proxy on every node watches Services and EndpointSlices and installs netfilter rules (iptables or nftables) that DNAT traffic for ClusterIP:port to one ready pod IP:port; conntrack reverses it on replies. Packets reach the node because it is the pod's default gateway, so no ARP for the ClusterIP happens. Ping fails in iptables/nftables mode because the rules only match the Service's protocol and port and nothing owns the IP. With Cilium's kube-proxy replacement, the translation happens in eBPF, even at connect() time.

How to answer

Lead with "it's a NAT rule, not an interface", then name the writer of each piece of state (API server, EndpointSlice controller, kube-proxy, kernel). Mention the IPVS dummy-interface exception to show depth.

Likely follow-ups
  • Where does load balancing happen - at the source or destination node? (Source node.)
  • Why does kube-proxy balance connections, not requests?
iptables vs IPVS vs nftables vs eBPF for Services - which would you choose in 2026 and why?

iptables is still the default but scales poorly: linear chains and large rewrites on every change. IPVS uses hash tables but has been deprecated since 1.35, with removal planned around 1.40, so I would not pick it for a new cluster. nftables mode is GA since 1.33 and recommended on 1.36+ with a 5.13+ kernel: verdict maps give fast lookups and incremental updates, and it is upstream. If I also want L7 policy and flow visibility, I would use Cilium with kube-proxy replacement. My default for a new cluster: nftables, or Cilium if the team can operate it.

How to answer

Use the pattern "I'd pick X because A; the cost is B; if C, I'd switch to Y". Citing the deprecation status shows you are current.

Likely follow-ups
  • What breaks when migrating from IPVS? (Ping to ClusterIP stops working; NodePort address defaults differ in nftables mode.)
A pod cannot reach another Service. Walk me through debugging.

Top-down: does DNS resolve the name (nslookup from a debug pod)? Does the Service have endpoints (EndpointSlices)? If not, compare labels and selector and check readiness probes. Is targetPort right and is the app bound to 0.0.0.0? Curl a pod IP directly to split the problem: if that works, look at kube-proxy rules; if not, look at the pod or CNI. Then check NetworkPolicies (including DNS egress), kube-proxy and CNI agent health, conntrack exhaustion and MTU. Tools: kubectl debug with netshoot, port-forward, iptables-save or nft list ruleset, tcpdump on the veth.

How to answer

Show a method, not a list: "each step halves the search space". Interviewers want to see you bisect.

Likely follow-ups
  • It works for small requests but hangs for big ones. (MTU.)
  • It fails only from one node. (That node's kube-proxy/CNI agent or conntrack.)
Why are DNS lookups slow, or why so many DNS queries, inside Kubernetes?

Pods get ndots:5 and three search domains. Any name with fewer than five dots - most external names - is first tried with each search suffix, each returning NXDOMAIN (often for both A and AAAA), before the real lookup. Fixes: use fully qualified names with a trailing dot, lower ndots via dnsConfig, run NodeLocal DNSCache, and make sure CoreDNS is scaled.

How to answer

Show the resolv.conf, count the wasted queries out loud, give two fixes.

Likely follow-ups
  • Why is ndots 5 the default? (So in-cluster names with up to 4 dots, such as SRV records like _http._tcp.svc.ns.svc or StatefulSet pod names like kafka-0.kafka-headless.kafka.svc, are still completed through the search path; the price is extra lookups for external names.)
Why do Kafka brokers on Kubernetes use a headless Service?

Kafka clients must talk to a specific broker - the leader of each partition - not "any broker". A normal ClusterIP would load-balance to a random broker. A headless Service (clusterIP: None) has no virtual IP; DNS returns individual pod records, and with a StatefulSet each broker gets a stable name like kafka-0.kafka-headless.kafka.svc that it advertises to clients. External clients need per-broker exposure too (one LoadBalancer or NodePort per broker), which operators like Strimzi set up.

How to answer

Start from the client's need (talk to the partition leader), then explain why a VIP breaks it. Link to StatefulSets.

Likely follow-ups
  • What is advertised.listeners and why does it matter here? (See Kafka on K8s.)

60-second answer - "How does a Service route traffic to changing pods?"
"A Service gives a group of pods, chosen by label selector, one stable virtual IP and DNS name. The API server allocates the IP, and the EndpointSlice controller keeps a list of the ready pod IPs. kube-proxy on every node watches those and programs the kernel - iptables or nftables rules - so a packet to the ClusterIP is DNATed to one pod IP, with conntrack reversing it on the way back. The IP is not on any interface; it's purely a NAT rule, so you can't ping it. CoreDNS answers the name with that IP. When a pod dies or fails readiness, it drops out of the EndpointSlice and the rules update within moments. Between nodes, the CNI plugin carries the packet, with a VXLAN overlay, BGP routes or native cloud IPs."
