How a ClusterIP really works: kube-proxy and DNAT

Must know (SDE-1)

Here is the question every networking engineer should ask: "Is the Service IP a real IP on an interface? Who answers ARP for it?"

Answer: in the default mode, nobody. 10.96.45.10 is not configured on any interface on any machine. It exists only as matching rules in netfilter on every node. When a pod sends a packet to it, the packet goes to the pod's default gateway (the node) - so no ARP for the ClusterIP is ever needed - and in the node's netfilter nat table a rule rewrites the destination (DNAT) to a real pod IP before routing. conntrack remembers the rewrite so replies are translated back.

# on any node (trimmed; real chain names are hashes)
$ sudo iptables-save -t nat | grep -E 'backend|KUBE-SVC-XYZ|KUBE-SEP'
-A KUBE-SERVICES -d 10.96.45.10/32 -p tcp -m comment --comment "default/backend:http cluster IP" -m tcp --dport 80 -j KUBE-SVC-XYZ
-A KUBE-SVC-XYZ -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-1
-A KUBE-SVC-XYZ -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-2
-A KUBE-SVC-XYZ -j KUBE-SEP-3
-A KUBE-SEP-1 -p tcp -m tcp -j DNAT --to-destination 10.244.1.7:8080
-A KUBE-SEP-2 -p tcp -m tcp -j DNAT --to-destination 10.244.2.9:8080
-A KUBE-SEP-3 -p tcp -m tcp -j DNAT --to-destination 10.244.2.12:8080

$ sudo conntrack -L -d 10.96.45.10
tcp 6 86397 ESTABLISHED src=10.244.1.20 dst=10.96.45.10 sport=40112 dport=80 src=10.244.2.9 dst=10.244.1.20 sport=8080 dport=40112 [ASSURED] use=1

Read the conntrack line like a networking engineer: original tuple to the ClusterIP, reply tuple from the real pod. That pair is the whole trick.

Can you ping a ClusterIP? In iptables and nftables mode, no: the rules only match the Service's protocol and port, and no interface owns the IP, so ICMP echo gets no answer. (In the old IPVS mode, the IPs are bound to a dummy kube-ipvs0 interface, so ping does answer - a nice detail to mention.) Test Services with curl or nc, never ping.

From your world

kube-proxy is "pushing NAT/ACL tables to every line card": one agent per node, each with the full table, so any node can forward to any Service. iptables mode is like a linear ACL evaluated top to bottom; nftables verdict maps are like moving to a hash/TCAM lookup. IPVS is LVS, the kernel's L4 load balancer. Where it breaks: unlike a hardware VIP on a load balancer appliance, there is no central box here - the "load balancer" is distributed into the source node's kernel, so traffic never hairpins through a middle hop.
