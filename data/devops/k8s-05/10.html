Production: scale limits and real outages

Deep dive (platform teams)
  • EndpointSlices exist because of scale. The old Endpoints object put every pod IP of a Service in one object; one pod change meant re-sending the whole list to every kube-proxy on every node. Slices (up to 100 endpoints each by default) send only the changed slice. OpenAI reported that switching to EndpointSlices cut that watch load about 1000x in their 7,500-node clusters.
  • iptables at scale. In iptables mode, rule count grows with Services and endpoints, and each sync rewrites big tables, so rule updates get slow with tens of thousands of Services. That is the motivation for nftables mode and eBPF dataplanes.
  • conntrack table full. Every connection through a ClusterIP uses a conntrack entry. A node with heavy short-lived connections can fill nf_conntrack_max and start dropping new connections ("nf_conntrack: table full, dropping packet" in dmesg) - a very kernel-shaped incident.
  • MTU black holes. With an overlay, pod MTU must be host MTU minus the encapsulation overhead. A mismatch shows up as "small requests work, big responses hang" - classic PMTU trouble.

Scenario: Reddit's Pi-Day outage (14 March 2023)

Reddit upgraded a key cluster from Kubernetes 1.23 to 1.24 and was down for 314 minutes. Their Calico setup chose BGP route reflectors using the node label node-role.kubernetes.io/master. Version 1.24 removed that label in favour of control-plane. Suddenly no node was a route reflector, routes were withdrawn and pod networking broke. That route-reflector config was not in git, so few people knew it existed, and Kubernetes has no supported downgrade, so they restored from backup.

Weak lesson: "Kubernetes upgrades are dangerous, avoid them."

Strong lesson: "Read the release notes for removals, keep all cluster configuration in git (GitOps) so hidden dependencies are visible, upgrade a non-critical canary cluster first, and practise restoring the control plane. For a networking person: the BGP control plane was keyed on a label - a 'routing policy' that no one reviewed." Source: Reddit engineering post.

Likely follow-ups
  • How would you detect this before production? (Canary cluster, diff of node labels across versions, synthetic pod-to-pod probes.)

Scenario: Datadog's multi-region outage (8 March 2023)

An automatic Ubuntu security update restarted systemd-networkd on many nodes at once. That version flushed IP routing-policy rules it did not own - including the ones Cilium had installed. Pods lost networking. On one cloud, auto-healing then replaced a large share of instances (Datadog reports about 60% in one region within two hours), wiping local disks that stateful stores depended on and slowing recovery.

Weak lesson: "Cilium is unreliable."

Strong lesson: "The CNI's dataplane is kernel state (ip rule, routes, BPF maps), and anything else on the node that touches that state is a change to the network. OS updates on nodes need the same progressive rollout as application deploys, and auto-healing should not blindly destroy nodes holding local state." Source: Datadog engineering blog.

Likely follow-ups
  • How would you limit blast radius? (Staged OS patching by node pool and region, pinned package versions, alerts on pod-to-pod probe failures.)
