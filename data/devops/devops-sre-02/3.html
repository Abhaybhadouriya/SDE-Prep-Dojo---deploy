Right-sizing: pay for what you use

Must know (SDE-1)

Right-sizing means matching the size and type of a resource to the load it really carries. It is usually the biggest and safest saving, because most servers are sized for a guess made on launch day and never revisited.

Three levels of right-sizing

  1. Instance size. An instance at 8% average CPU and low memory can drop one size (2xlarge to xlarge halves the price). Look at p95 or p99 over 2-4 weeks, not the average of one day, and check memory too (CloudWatch needs the agent for memory). AWS Compute Optimizer gives per-instance recommendations from that history.
  2. Instance family. Match the shape: c (compute-heavy, less memory per vCPU), m (balanced), r (memory-heavy), t (burstable, for low steady load with spikes). Newer generations usually give more performance per dollar, and Arm-based Graviton families (the g suffix, like m7g) are often cheaper for the same work if your images are built for arm64.
  3. Pod requests. In Kubernetes, the node bill follows the sum of requests. The Vertical Pod Autoscaler (VPA) watches real CPU and memory use (plus OOM kills) and recommends better requests.

VPA in recommendation-only mode

The VPA has three parts: a recommender that computes target, lower and upper bounds from history; an updater that can evict or update pods whose requests are far off; and an admission controller that rewrites requests on new pods. Start with updateMode: "Off": you get advice, nothing changes.

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: checkout-api
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-api
  updatePolicy:
    updateMode: "Off"        # Off = recommend only; Initial = set on pod creation; Recreate = evict and resize
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed: { cpu: 100m, memory: 128Mi }
      maxAllowed: { cpu: "2",  memory: 2Gi }
$ kubectl get vpa checkout-api -o jsonpath='{.status.recommendation.containerRecommendations[0]}' | jq
{
  "containerName": "app",
  "lowerBound":     { "cpu": "310m", "memory": "402Mi" },
  "target":         { "cpu": "587m", "memory": "512Mi" },
  "upperBound":     { "cpu": "1210m", "memory": "903Mi" },
  "uncappedTarget": { "cpu": "587m", "memory": "512Mi" }
}
$ kubectl top pod -l app=checkout-api
NAME                            CPU(cores)   MEMORY(bytes)
checkout-api-6f9c7d8b5c-2kq9m   402m         455Mi
checkout-api-6f9c7d8b5c-x7lp4   377m         470Mi

Here the deployment requests 2 CPU per pod and the target is about 600m: a 3x over-request. Apply the new value through your normal Git change, watch latency and throttling for a few days, then repeat.

VPA and HPA on the same metric fight. If the Horizontal Pod Autoscaler scales on CPU utilisation (usage divided by request) and VPA changes the request, each one moves the other's input. Common pattern: HPA on CPU or a custom metric for replica count, VPA in Off mode as an advisor, or VPA managing memory only.

From your world

An inflated request is like statically reserving a ring buffer far bigger than the NIC ever fills: the memory is pinned and nobody else can use it. Right-sizing is tuning the reservation to the measured high-water mark plus headroom. The node-level effect is an oversubscription ratio, just like on a switch uplink: requests are your guaranteed allocations, limits are the burst ceiling, and the scheduler only packs by the guaranteed part.
