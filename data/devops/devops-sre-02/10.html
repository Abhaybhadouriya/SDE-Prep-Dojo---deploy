Interview questions

Our AWS bill doubled in six months but traffic grew only 20%. How do you investigate?

Start with attribution, not guessing. In Cost Explorer, group by service, then by account and by the team or service tag, and compare month over month to find the top movers. Check untagged spend; if it is large, the first fix is tagging. For each top mover, drill into usage type: is it instance-hours (more or bigger instances), EBS GB-months, NatGateway-Bytes, cross-AZ DataTransfer-Regional-Bytes, or a new managed service? Then compare against unit cost (cost per 1,000 requests or per order) to separate healthy growth from waste. Typical findings: autoscaling floors raised during an incident and never lowered, a new service with inflated requests, S3 traffic through a NAT, logs with no retention, dev environments running 24/7.

How to answer

Show a method: allocate, find top movers, drill into usage type, normalise by a business metric, then fix the biggest items first. Mention that you would add budgets and anomaly alerts so it is caught next time.

Likely follow-ups
  • How do you split shared costs like the EKS cluster?
  • What is a good unit cost metric for an e-commerce site?
Savings Plans or Reserved Instances? How much would you commit?

For EC2 compute I default to Savings Plans: a Compute Savings Plan (up to 66% off) follows the workload across instance families, Regions, Fargate and Lambda, so it survives a migration to Graviton or containers; an EC2 Instance Savings Plan (up to 72%) is cheaper but locked to one family in one Region. Reserved Instances still make sense for services billed by RI (for example some database engines) and when I need a capacity guarantee in a specific AZ, which only a zonal RI or a capacity reservation gives. For the amount: right-size first, then look at hourly usage for 30-60 days and commit to the steady floor, not the average, so utilisation stays near 100%. Buy in small slices each month or quarter (laddering) so commitments expire at different times and I can adjust as the architecture changes.

How to answer

Name the flexibility vs discount trade-off, the "commit to the floor" rule, and the two metrics: coverage and utilisation.

Likely follow-ups
  • What happens if usage drops below the commitment?
  • Do Savings Plans guarantee capacity?
  • 1-year or 3-year, and why?
Which workloads would you move to Spot, and how do you make them survive interruptions?

Anything stateless and horizontally scaled: web and API pods behind a load balancer with enough replicas, CI runners, batch and ETL workers that checkpoint, Kafka consumers that can rebalance, and spare capacity in a node pool. Not single-replica stateful services or databases. To survive: diversify across many instance types and all AZs with a price-capacity-optimized strategy; keep an On-Demand floor that can serve minimum traffic; handle the two-minute notice (Karpenter with an SQS interruption queue, or the Node Termination Handler) by cordoning, draining and launching a replacement in parallel; make pods shut down gracefully on SIGTERM well within two minutes; and use PodDisruptionBudgets and topology spread so one reclaimed pool never takes out all replicas.

How to answer

Classify workloads first, then give the four survival tools: diversification, floor, notice handling, graceful shutdown.

Likely follow-ups
  • What is a rebalance recommendation?
  • How would you run a Kafka broker cost-effectively?
The Kubernetes cluster is at 25% CPU utilisation but the autoscaler keeps adding nodes. Why, and what do you do?

The scheduler and cluster autoscaler pack by requests, not usage. If pods request 2 CPU and use 0.4, nodes look full on paper while being idle in reality, so new pods go Pending and the autoscaler adds nodes. Fix the requests: run VPA in Off mode to get p95-based targets, compare with kubectl top and Prometheus history, and lower requests through Git, service by service, watching throttling and latency. Then let consolidation (Karpenter's WhenEmptyOrUnderutilized, or cluster autoscaler scale-down) repack pods onto fewer nodes. Also check for things that block scale-down: pods with local storage, strict PDBs, or DaemonSets on oversized nodes.

How to answer

Say "requests, not usage" in the first sentence. Then measure, adjust, consolidate, and mention the VPA/HPA conflict.

Likely follow-ups
  • Should you set CPU limits?
  • How do VPA and HPA interact?
The NAT gateway line on our bill is larger than EC2. What is going on?

Private-subnet workloads reach S3, ECR, DynamoDB or the internet through the NAT gateway, which charges a per-GB processing fee on top of its hourly fee. Heavy flows like log shipping to S3, image pulls, or backups hairpin through it. Steps: use VPC Flow Logs or the NatGateway-Bytes usage type to find top destinations; add S3 and DynamoDB gateway endpoints to the private route tables (free; their prefix-list routes are more specific than 0.0.0.0/0, so traffic takes them automatically); consider interface endpoints for ECR and other AWS APIs if volume justifies them; use a pull-through cache for images; and place one NAT per AZ so you do not add cross-AZ charges on the way to the NAT.

How to answer

Walk the packet path through the route table, then show the longest-prefix-match fix. This is where a networking background shines.

Likely follow-ups
  • Gateway vs interface endpoints?
  • Would IPv6 with an egress-only internet gateway help?
Design a storage lifecycle for application logs that must be searchable for 30 days and retained for 2 years.

Hot search for 30 days lives in the log platform (OpenSearch, Loki) with its own retention of 30 days. The raw logs land in S3 Standard, compressed and batched into large objects (well above 128 KB, ideally tens of MB) so per-object fees and archive overhead stay small. A lifecycle rule moves them to Standard-IA at 30 days, Glacier Instant Retrieval or Flexible Retrieval at 90 days, Deep Archive at 180 days, and expires them at 730 days. Add noncurrent-version expiration and abort-incomplete-multipart rules. If an audit needs old logs, restore from Glacier and query with Athena. Respect minimum durations: never archive data you will delete within 90-180 days.

How to answer

Separate the search tier from the archive tier, give the day thresholds, and mention object size and minimum durations as the two traps.

Likely follow-ups
  • When would you use Intelligent-Tiering instead?
  • How do you enforce legal retention (Object Lock)?
Our AWS bill rose 40% this month. Walk me through how you find out why.

Start from data, not guesses. In Cost Explorer (or the CUR in Athena) group the month-over-month change by service, then by linked account, region, usage type and cost-allocation tag. Usually one or two lines explain most of it. Typical culprits: data transfer (a new cross-AZ or NAT path, a chatty service calling S3 through NAT instead of a gateway endpoint), a new or oversized fleet, Spot capacity falling back to On-Demand, expired Savings Plan or RI coverage, logs or metrics volume, snapshots and orphaned volumes. Tie the jump to a date and correlate with deploys and infrastructure changes. Fix the cause, then prevent repeats: anomaly detection alerts per account and team, budgets, and tagging that maps every line to an owner.

How to answer

Say "group by service, then usage type, then tag; find the date it started". Name two or three likely suspects with how you would confirm each.

Likely follow-ups
  • How would AWS Cost Anomaly Detection have helped? (It alerts on unusual spend per service or tag within a day.)
Savings Plan, Reserved Instance or Spot for a 24x7 Kafka cluster?

Kafka brokers are stateful and long-lived, with data on local or EBS disks and partition replicas that are expensive to move, so Spot interruptions (two minutes' notice) cause re-replication storms and possible under-replicated partitions: not a good fit for brokers. The load is steady, so a commitment fits: a Compute Savings Plan if the fleet may change instance family or move to Graviton or to containers, or an EC2 Instance Savings Plan or RI for a bigger discount when the instance family and region are fixed. Size the commitment to the steady baseline, not the peak. Spot can still serve stateless consumers and batch jobs around the cluster. A managed service (MSK) changes the maths again.

How to answer

Lead with "stateful brokers do not belong on Spot", then commitment type by flexibility, then size it to the baseline.

Likely follow-ups
  • What about tiered storage? (Moving old segments to S3 shrinks the disks you pay for.)
How do you show each team its cost on a shared EKS cluster?

Cloud bills stop at the node, so you need allocation inside the cluster. Tag the cluster and node groups for the shared total, then split node cost by what each workload requests (or uses, whichever is larger) per namespace and label, with a tool such as Kubecost or OpenCost, or EKS split cost allocation data in the CUR. Decide how to share idle capacity and cluster overhead (system pods, control plane fee): proportionally, or as a platform line item. Publish a monthly showback per team, and make requests honest with VPA recommendations, because inflated requests are what teams are billed for.

How to answer

Mention "allocate by requests per namespace", name one tool, and say how idle cost is shared.

Likely follow-ups
  • Showback vs chargeback? (Showback reports cost; chargeback actually bills the team budget.)

Scenario: the NAT bill doubled overnight

The daily cost alert shows NatGateway-Bytes in ap-south-1 doubled since yesterday. Nothing obvious was deployed to the network.

Weak answer: "Add a second NAT gateway to spread the load."

Strong answer: A second NAT gateway does not reduce per-GB processing. Find who is sending the bytes: enable or query VPC Flow Logs for the NAT gateway's ENI and group by source IP and destination, then map the source IPs to pods or instances. Common causes: a new service pulling large objects from S3 through NAT instead of a free S3 gateway endpoint, container images pulled from a public registry on every scale-out, a log shipper sending to a SaaS endpoint, or traffic hairpinning across AZs to a NAT in another AZ. Fix the path (gateway endpoint for S3 and DynamoDB, interface endpoints or a pull-through cache for ECR, one NAT per AZ with AZ-local routes) and add a CloudWatch alarm on BytesOutToDestination.

Likely follow-ups
  • How do you confirm the fix worked? (Watch BytesOutToDestination on the NAT and the next day's cost line.)
