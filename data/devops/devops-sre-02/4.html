Spot for stateless pools

Must know (SDE-1)

Spot Instances are spare EC2 capacity. AWS says they can save up to 90% against On-Demand prices. The catch: when EC2 needs the capacity back, it interrupts your instance with a two-minute warning. So Spot is perfect for work that can be killed and restarted somewhere else: stateless web pods behind a load balancer, CI runners, batch jobs, Kafka consumers that can rebalance, and big-data workers. It is a bad fit for a single database primary or anything that cannot lose a node with two minutes' notice.

  1. EC2 emits the interruption notice two minutes ahead, as an EventBridge event and in instance metadata at spot/instance-action.
  2. The node is tainted and cordoned so the scheduler stops placing pods on it.
  3. A replacement node starts in parallel, ideally from a different instance type or AZ so it is not in the same reclaimed pool.
  4. Pods are drained: graceful termination runs, PodDisruptionBudgets keep enough replicas up, pods reschedule.
  5. The load balancer deregisters old targets after connection draining. Then EC2 reclaims node A. Users saw nothing.

You can see the notice yourself from inside the instance. Before any interruption the path returns HTTP 404; when one is scheduled it returns JSON (the AWS docs recommend checking about every 5 seconds):

$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
$ curl -s -o /dev/null -w "%{http_code}\n" -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/spot/instance-action
404
# ... later, when EC2 decides to reclaim the instance:
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/spot/instance-action
{"action": "terminate", "time": "2026-11-23T08:22:00Z"}

Rules for using Spot well

  • Diversify. Allow many instance types and sizes across all AZs. Each type in each AZ is a separate capacity pool; ten pools rarely all run dry at once. Use the price-capacity-optimized allocation strategy in Auto Scaling groups.
  • Keep a floor on On-Demand. Run the minimum needed to survive with zero Spot (often covered by a Savings Plan) and burst on Spot.
  • Make shutdown graceful. Handle SIGTERM, set terminationGracePeriodSeconds well under 120 seconds, and set PodDisruptionBudgets.
  • Do not set a low max price. AWS notes that a maximum price makes interruptions more frequent; the default (capped at On-Demand) is usually right.

With Karpenter on EKS, a NodePool can allow both capacity types; Karpenter prefers Spot when it is allowed and falls back to On-Demand. With an SQS interruption queue configured, it handles the two-minute warning by tainting, draining and replacing the node in parallel:

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: web-stateless
spec:
  template:
    spec:
      requirements:
      - key: karpenter.sh/capacity-type
        operator: In
        values: ["spot", "on-demand"]
      - key: karpenter.k8s.aws/instance-category
        operator: In
        values: ["c", "m", "r"]          # many families = many Spot pools
      - key: kubernetes.io/arch
        operator: In
        values: ["amd64", "arm64"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized   # repack and remove half-empty nodes
    consolidateAfter: 5m
    budgets:
    - nodes: "10%"                                   # never disrupt more than 10% of nodes at once

From your world

Spot is a best-effort QoS class, like traffic marked CS1 (scavenger) that a router drops first under congestion. The two-minute notice is a graceful-restart timer: you get a short window to move state before the adjacency goes down. Diversifying across instance types and AZs is ECMP across independent links - one link failing (one pool reclaimed) only removes a slice of capacity.
