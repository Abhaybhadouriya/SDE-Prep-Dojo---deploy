Consumer lag, properly

Lag for one partition and one consumer group is: log end offset (the offset the next new record will get) minus the group's committed offset (the next record the group will read). It is the number of records written but not yet processed.

The command-line view is the most useful tool you will learn on this page:

docker compose exec kafka-1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server kafka-1:19092 --describe --group enricher
GROUP     TOPIC          PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID            HOST         CLIENT-ID
enricher  orders.created 0          1204            1204            0    0d3c1a9e7f21-8b2f...   /172.18.0.9  0d3c1a9e7f21
enricher  orders.created 1          1187            1189            2    0d3c1a9e7f21-8b2f...   /172.18.0.9  0d3c1a9e7f21
enricher  orders.created 2          1251            1251            0    0d3c1a9e7f21-8b2f...   /172.18.0.9  0d3c1a9e7f21
...

The CLIENT-ID is the container hostname, because the shared config sets client.id to HOSTNAME. That makes it easy to see which instance owns which partition.

"What lag number is bad?"

There is no magic number, and saying one in an interview is a small red flag. Think about it the way you think about a buffer:

  1. Trend beats size. Lag of 5,000 that is shrinking is a consumer catching up after a restart. Lag of 500 that grows every minute is a consumer that is slower than the producer, and it will never catch up on its own.
  2. Convert to time. Lag divided by the consume rate is roughly "how many seconds behind are we". 10,000 messages at 5,000 per second is 2 seconds, fine for a dashboard. 100 messages at 1 per second is nearly 2 minutes, maybe too slow for fraud checks.
  3. Compare to retention. If lag in time approaches the topic's retention (7 days for orders.created), the oldest unread records will be deleted before they are read. That is real data loss.
  4. Look per partition. If one partition holds most of the lag, adding consumers will not help (see the hot-partition drill).

ShopStream's alert is a simple threshold with a duration, which is a reasonable start:

# infra/prometheus/alerts.yml (excerpt)
      - alert: EnricherLagHigh
        expr: sum(kafka_consumergroup_lag{consumergroup="enricher"}) > 1000
        for: 2m
        labels: {severity: warning}
        annotations:
          summary: "enricher is {{ $value }} messages behind on orders.created"
      - alert: UnderReplicatedPartitions
        expr: sum(kafka_topic_partition_under_replicated_partition) > 0
        for: 1m
        labels: {severity: critical}

The for: 2m means "only fire if it stays true for 2 minutes", so a short burst during a deploy does not page anyone. The third rule, DLQReceivingMessages, fires when the DLQ end offset is still growing.

Better lag tooling: LinkedIn's Burrow evaluates lag over a sliding window and reports a status (OK, warning, stalled) instead of a raw number, which turns "is it growing?" into an alert you can trust. Strimzi on Kubernetes runs the same kafka-exporter for you (kafkaExporter: in the Kafka resource).
