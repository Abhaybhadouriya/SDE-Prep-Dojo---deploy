Drill 5: replay history

Kafka keeps data for the retention period whether anyone has read it or not. So a consumer group can be moved back in time. The script stops analytics (offsets can only be reset when the group has no active members), resets the group to the earliest offset, and starts it again.

==> Stopping analytics (offsets can only be reset when the group is empty)
==> Dry run, then execute the reset
GROUP      TOPIC            PARTITION  NEW-OFFSET
analytics  orders.enriched  0          0
analytics  orders.enriched  1          0
...
==> Start again and watch it re-read
analytics-1  | ... INFO  analytics analytics up: window=60s lateness=10s
analytics-1  | ... INFO  analytics WINDOW 10:15:00-10:16:00 orders=1186 revenue=INR 4620934.00
analytics-1  | ... INFO  analytics WINDOW 10:16:00-10:17:00 orders=1203 revenue=INR ...

What you see: analytics prints old windows again, quickly, one after another: it is recomputing history. The revenue panel shows the replayed values. The replayed windows may differ from the ones you saw live (in the sample, 1186 orders instead of 1197); see the warning below.

Why it works: windows are keyed by event time (created_at), so replayed orders are meant to land in their original minutes, not "now". This is how you fix a bug in a consumer: deploy the fix, reset the group to before the bug, and let it reprocess. For a sink, replay is safe only because the write is idempotent (the upsert on order_id).

Watch shopstream_late_events_total during the replay. Our toy processor has one global watermark across all six partitions. A replay reads up to 500 records per fetch, often mostly from one partition, so the watermark races ahead to that partition's newest time and many events from the other partitions are then marked late and dropped. The replayed windows can be smaller than the originals. Real frameworks track a watermark per partition and use the minimum (see windowed analytics).

Replay is not free. Old data is usually not in the broker's page cache, so a big replay reads from disk and can slow brokers for everyone else. And be careful which group you reset: resetting the sink group of a non-idempotent sink duplicates everything. Always run --dry-run first, as the script does. Other useful reset targets: --to-datetime 2026-11-23T10:00:00.000, --shift-by -1000, --to-offset.
