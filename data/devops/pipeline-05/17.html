Quick quiz

A partition's log end offset is 5,000 and the group's committed offset is 4,200. What is the lag?

  1. 4,200
  2. 800
  3. 5,000
  4. 9,200
Lag = log end offset minus committed offset = 5,000 - 4,200 = 800 records not yet processed by this group.

You kill one of three brokers (RF 3, min ISR 2, acks=all). What happens to new orders?

  1. All writes fail until it returns
  2. Writes succeed but may be lost
  3. Writes succeed, stored on the two remaining in-sync replicas
  4. Only half the partitions accept writes
New leaders are elected from the ISR; with two in-sync replicas, min ISR 2 is still met, so acks=all writes succeed durably.

And if you kill two of the three brokers?

  1. acks=all producers get NOT_ENOUGH_REPLICAS; writes are refused
  2. Writes continue on one replica
  3. Kafka elects an out-of-sync leader automatically
  4. Consumers stop but producers continue
The ISR drops to 1, below min.insync.replicas=2, so Kafka refuses acks=all writes rather than risk loss. In this compose setup the KRaft quorum (2 of 3) is also lost.

During drill 4 you hard-kill one of three enrichers. Its two partitions make no progress for about how long?

  1. 0 seconds
  2. 3 seconds (heartbeat interval)
  3. 5 minutes (max.poll.interval.ms)
  4. About 45 seconds (session.timeout.ms)
A killed process sends no leave-group, so the coordinator waits for the session timeout (45 s in ShopStream) before reassigning its partitions.

Half of all orders come from customer C-HOT. You scale the enricher from 3 to 6. What happens to C-HOT's delay?

  1. It halves
  2. Nothing much: all C-HOT orders are on one partition, which only one consumer can read
  3. It disappears
  4. Kafka moves C-HOT to a new partition
Same key, same partition, one owner per partition in a group. Hot keys need a different key, salting or cheaper processing.

Why must the analytics service be stopped before resetting its offsets?

  1. Kafka deletes the topic otherwise
  2. The reset tool needs root
  3. Offsets can only be reset when the group has no active members
  4. To clear the page cache
kafka-consumer-groups refuses to reset offsets for a group with active members, because they would overwrite the new offsets.

Which alert rule is the most useful for a consumer?

  1. Lag above a threshold for a few minutes (or a growing-lag status)
  2. Any lag above 0
  3. CPU above 80 %
  4. Number of topics changed
Lag is always slightly above 0 under load. A duration or trend separates "busy" from "falling behind". CPU says little about a consumer waiting on I/O.

The sink lag is a saw-tooth that resets every 5 minutes, with members leaving and rejoining. Most likely cause?

  1. A broker is down
  2. Retention is too short
  3. The topic needs more partitions
  4. Processing a batch takes longer than max.poll.interval.ms (5 min), so the member is kicked and rejoins
The period matches the 300,000 ms default. The member re-reads the same batch each time. Fix the slow processing or shrink the batch.
