Interview questions about the pipeline

These are the questions people report getting when they put a Kafka pipeline on their resume or design one in an HLD round. Company tags mean "commonly reported at", not "always asked at".

What would you monitor in a Kafka pipeline?

Five things. Consumer lag per group and per partition, ideally converted to time, because it tells me whether each stage keeps up. Throughput in and out per topic, so I can tell "more traffic" from "slower consumer". Error outcomes: retry rate, DLQ growth, producer publish errors. Broker and replication health: under-replicated partitions, offline partitions, exactly one active controller. And the user-facing view: API success rate and end-to-end latency from event creation to the sink. I alert on symptoms with durations (lag growing for 2 minutes, any under-replicated partition for 1 minute, DLQ growing) and use the rest for diagnosis.

How to answer

Give a short, ordered list from user-facing to internal, and separate "what pages me" from "what I look at when debugging".

Likely follow-ups
  • How is lag computed? (Log end offset minus committed offset, per partition per group.)
  • How would you measure end-to-end latency? (Event timestamp at the source, a histogram of now minus that at the sink.)
Consumer lag is growing. Walk me through your investigation.

First, is it real and how bad: lag per group in time versus retention, and is it still growing. Then I find the cause. Did input throughput rise, for example a sale? Then scale consumers up to the partition count, which we do automatically on lag. Is the consumer erroring or restarting? Logs and restart counts: a poison record, a crash loop, a fenced transactional producer. Is the group rebalancing repeatedly? Processing longer than max.poll.interval.ms, or probes killing pods. Is one partition far above the rest? A hot key, which scaling will not fix. Is a downstream dependency slow? Then the database or API is the bottleneck and lag is just Kafka buffering for it. I fix the cause, let lag drain, and if lag approached retention I check whether anything was deleted unread.

How to answer

Structure beats speed: severity, then a short decision tree, then the fix, then "how do we make sure it does not happen again" (autoscaling, alerts, load tests).

Likely follow-ups
  • You added consumers and lag did not go down. Why? (Hot partition, more consumers than partitions, or a downstream bottleneck.)
  • What happens if lag exceeds retention? (Records are deleted before they are read: data loss.)
A broker dies. What happens to producers and consumers, and can data be lost?

The KRaft controller notices the broker stopped heartbeating, shrinks the ISR of every partition it hosted and elects new leaders from the remaining in-sync replicas. Clients get errors on the old leader, refresh metadata and continue with the new one, usually within seconds. With replication factor 3, min.insync.replicas=2 and acks=all, every acknowledged write is on at least two brokers, so nothing acknowledged is lost and writes continue with two replicas. If a second broker fails, the ISR drops below 2 and acks=all producers get NOT_ENOUGH_REPLICAS: the system refuses writes rather than risk loss. Data can be lost if you use acks=1 (the leader acked, then died before followers copied), or if unclean leader election is enabled and an out-of-sync replica becomes leader. When the broker returns it truncates to the high watermark, catches up and rejoins the ISR; a preferred leader election rebalances leadership.

How to answer

Sequence of events naming the component (controller), then the durability math (RF, min ISR, acks), then the two ways to lose data, then recovery.

Likely follow-ups
  • Why RF 3 and min ISR 2 rather than min ISR 3? (Min ISR 3 means any single broker failure stops writes.)
  • What is the high watermark? (The highest offset replicated to all ISR members; consumers only read up to it.)
You found a bug in a consumer that has been writing wrong results for 3 hours. How do you recover?

Kafka keeps the input, so I can replay. Fix and deploy the consumer. Stop the group (offsets can only be reset with no active members), reset its offsets to a time before the bug with kafka-consumer-groups --reset-offsets --to-datetime, dry run first, then execute and start the consumer. It reprocesses the 3 hours. This is safe only if the sink is idempotent, for example an upsert on a business key, so corrected rows overwrite wrong ones instead of being added. If the output topic was consumed by others, I may need to publish corrections or have downstream consumers reprocess too. Replay reads cold data from disk, so I throttle it or run it off-peak.

How to answer

Name the property that makes it possible (retention), the exact tool, the safety condition (idempotent sink), and the side effects (downstream consumers, broker load).

Likely follow-ups
  • What if the data is older than retention? (Then you need an archive: tiered storage, or a copy in a data lake.)
  • How would you replay without stopping the live consumer? (A new consumer group writing to a shadow table, then swap.)
What causes rebalance storms and how do you prevent them?

A rebalance happens whenever group membership or subscriptions change. Storms come from members repeatedly leaving: processing a batch takes longer than max.poll.interval.ms so the member is kicked out and rejoins; heartbeats missed because of long GC pauses or CPU starvation; liveness probes restarting pods; autoscalers flapping; or rolling deploys that restart many pods quickly. Prevention: keep the poll loop fast (smaller batches, move retries to a retry topic, pause partitions instead of sleeping), use the cooperative-sticky assignor or the new KIP-848 consumer protocol (group.protocol=consumer) so only moved partitions pause, static membership with group.instance.id for quick restarts, graceful shutdown so members leave cleanly, slow scale-down, and PDBs to limit evictions.

How to answer

Two lists: causes, then fixes, matched to each other. Mention that eager rebalances stop the whole group, while cooperative ones only move what must move.

Likely follow-ups
  • What does KIP-848 change? (The broker computes assignments and reconciles members one by one; no global sync barrier.)
  • What would switching ShopStream take? (Set group.protocol=consumer and remove partition.assignment.strategy and session.timeout.ms from consumer_config(): with the new protocol the client may not set them. Assignment moves to the broker (group.consumer.assignors) and the session timeout becomes a broker/group setting (group.consumer.session.timeout.ms, default 45 s). It also needs a librdkafka version with GA KIP-848 support.)
How do you know your pipeline does not lose or duplicate orders?

By design and by checking. By design: idempotent producer with acks=all and min ISR 2, so no loss or producer duplicates into Kafka; a transactional read-process-write in the enricher; offsets committed only after the database commit; an upsert on order_id at the sink; every failure routed to a retry topic or DLQ instead of dropped. By checking: reconciliation. Count accepted orders at the API per minute and compare with rows in the database for the same event-time minute, plus the DLQ count. Any gap that persists beyond expected lag is an alert. And chaos drills: kill brokers and consumers under load, then reconcile.

How to answer

Interviewers love the second half. Most candidates only describe the guarantees; describing how you would verify them is a senior signal.

Likely follow-ups
  • What if the API crashed after the Kafka ack but before answering the client? (The client retries; the same order_id upserts once, if the client supplies the id.)
What is backpressure in this pipeline, and who slows down whom?

Backpressure is a slow stage pushing back on faster stages instead of being overwhelmed. Between consumers and Kafka it is natural: consumers pull, so a slow sink just reads slower and lag grows; Kafka is the buffer, bounded by retention. The sink in our project does exactly this when Postgres is down: it keeps its batch, retries, and does not commit. At the producer side the buffer is the client's in-memory queue: when brokers are slow, librdkafka's queue fills, produce() raises BufferError, and the order-api returns 503 with Retry-After, which pushes back on the callers. So the chain is: DB slows sink, lag absorbs it; brokers slow, producer queue fills, API sheds load to clients.

How to answer

Define it, then walk each boundary and name what absorbs or rejects the pressure there. A TCP flow-control analogy works well.

Likely follow-ups
  • Why is pull better than push for consumers? (The consumer controls its rate; the broker does not need per-consumer flow control.)
Design question: how would you make this pipeline multi-region?

First I ask what the requirement is: disaster recovery (survive a region loss with some RPO) or active-active (serve writes in both). For DR, the common pattern is active-passive: the primary cluster serves everything and MirrorMaker 2 replicates topics and translates consumer offsets to a standby cluster in another region; on failover consumers start from translated offsets, accepting a few seconds of duplicates, which our idempotent sink absorbs. Replication is asynchronous, so the RPO is the replication lag, which I monitor like consumer lag. For active-active, each region writes to its own local topics with a region prefix so MirrorMaker does not loop, and consumers read both local and mirrored topics; that requires the business logic to tolerate events from two places, for example orders owned by the region where they were placed. Within one region, the cheaper step is three availability zones with rack awareness, which is what our Strimzi setup simulates.

How to answer

Clarify RPO/RTO and active-passive vs active-active before drawing. Name the tool, the lag it introduces, and how duplicates are handled.

Likely follow-ups
  • Why not stretch one Kafka cluster across regions? (Synchronous replication across high-RTT links makes every acks=all write slow.)

Scenario: Big Billion Day, lag climbing, autoscaler at max

During a flash sale, enricher lag climbs past 200,000. KEDA has already scaled to 6 replicas, the maximum. CPU on the enricher pods is modest. Customers see "order placed", but confirmation emails (driven by orders.enriched) arrive 10 minutes late.

Weak answer: "Raise maxReplicaCount to 20." (A seventh to twentieth consumer would be idle; there are only 6 partitions.)

Strong answer: Six replicas for six partitions means we are at the parallelism ceiling, and modest CPU says the enricher is waiting on something, probably the catalog lookup in Postgres. Short term: cache prices in memory (they barely change during a sale), raise batch size so transactions are amortised, and check the catalog DB's latency. Check lag per partition for a hot key. Medium term: more partitions for future events (planned before the sale, since adding partitions remaps keys), or concurrent processing inside each consumer while keeping per-key order. The API is unaffected because Kafka absorbs the burst; I would communicate that emails are delayed, not lost, and watch lag in time versus the 7-day retention, which is nowhere near.

Likely follow-ups
  • How would you pick the partition count before the sale? (Target throughput divided by measured per-partition consumer throughput, plus headroom.)
  • Would share groups help? (Yes for unordered work: many consumers per partition, at the cost of per-key ordering.)

Scenario: under-replicated partitions alert at 3 a.m.

The UnderReplicatedPartitions alert fires and stays firing. Orders are still being accepted. The on-call engineer asks whether to wake anyone up.

Weak answer: "Orders work, so it can wait until morning."

Strong answer: Writes work because the ISR is still at 2, but we have lost our safety margin: one more broker problem and acks=all writes stop. So it is urgent, not an outage. I check which broker the under-replicated partitions have in common (the --under-replicated-partitions output lists replicas and ISR). If a broker is down, I restart it or let the orchestrator replace it and watch it catch up. If it is up but falling behind, I look at its disk, network and request-handler saturation. Once the ISR is full again I confirm with the same command, then do a preferred leader election, and write up why it happened.

Likely follow-ups
  • What is the difference between under-replicated and offline partitions? (Offline = no leader at all = outage for that partition.)

Scenario: after a deploy, the DLQ fills with "missing field items"

Ten minutes after the mobile team shipped a new app version, the DLQ alert fires. Thousands of records, all with the same error header, all from new app versions.

Weak answer: "Make the enricher accept orders without items."

Strong answer: One error type in a burst right after a deploy points at the deploy. The DLQ did its job: good orders keep flowing and the bad ones are kept with their origin. I would get the producer fixed or rolled back first (stop the bleeding), then look at a sample: maybe the field was renamed. Once fixed, I write a small transform that maps the old shape to the new, and redrive the DLQ records to orders.created; the idempotent sink protects against duplicates. Then prevent it: a schema registry with compatibility checks in the producer's CI would have rejected the change before it shipped.

Likely follow-ups
  • What compatibility mode would you use? (BACKWARD, the Schema Registry default: consumers on the new schema can read data written with the old one. You may delete fields and add optional fields with defaults, but not add a required field. Upgrade consumers first. Use FULL if producers and consumers deploy independently.)

Scenario: the sink lag graph is a saw-tooth

postgres-sink lag rises for about 5 minutes, drops to zero, rises again. Logs show the members joining and leaving the group every few minutes.

Weak answer: "Add more sink replicas."

Strong answer: A regular saw-tooth with join/leave lines is a rebalance loop. Five minutes matches the default max.poll.interval.ms (300,000 ms): a batch takes longer than that, maybe because of a slow query or a lock, so the member is removed, rejoins, re-reads the same batch, and repeats. Fix: find the slow write, reduce the batch size so each poll returns faster, and alert on rebalance rate. Adding replicas would make it worse: more members, more rebalances.

Likely follow-ups
  • How would you confirm? (Consumer logs for "revoked" lines and the time between polls; DB slow-query log.)
