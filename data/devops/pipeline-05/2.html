The five numbers that matter

You could chart hundreds of Kafka metrics. For a pipeline, five answer almost every question. Here they are, with the exact PromQL (Prometheus Query Language) that ShopStream's dashboard uses:

#SignalQuestion it answersShopStream query
1Consumer lagAre we keeping up?sum by (consumergroup) (kafka_consumergroup_lag)
2ThroughputHow much is flowing in?sum by (topic) (rate(kafka_topic_partition_current_offset{topic=~"orders.*"}[1m]))
3Outcomes / errorsAre records failing?sum by (outcome) (rate(shopstream_enricher_records_total[1m])) and the DLQ size
4Replication healthIs the cluster safe?sum(kafka_topic_partition_under_replicated_partition)
5Front-door healthAre users being served?rate(shopstream_orders_accepted_total[1m]) vs rate(shopstream_publish_errors_total[1m])

The DLQ panel estimates how many records are sitting in the DLQ right now: end offset minus oldest offset, summed over partitions:

sum(kafka_topic_partition_current_offset{topic="orders.dlq"}) - sum(kafka_topic_partition_oldest_offset{topic="orders.dlq"})

Offsets are positions, not message counts. orders.dlq is only written inside enricher transactions, and every commit adds a COMMIT marker (a control record) that takes one offset in each partition the transaction touched. So this number is an upper bound: 3 poison records in one batch show as 4. That is why the panel is titled "DLQ end-offset span (includes txn markers)". The exact count comes from kafka-ui or a read_committed console consumer. For a rate of records going to the DLQ, the application counter is exact: sum(rate(shopstream_enricher_records_total{outcome="dlq"}[5m])) (it resets when the enricher restarts, so it is not a good "total"). The same marker effect inflates "messages in per second" for the transactional topics orders.enriched and orders.retry a little.

One more you should ask for: end-to-end latency. How long from "customer clicked buy" to "order in the database"? The enricher stamps enriched_at_ms on every enriched event next to the original created_at, so the processing delay is in the data. ShopStream does not chart it; adding a histogram of now - created_at in the sink would be a good exercise. In interviews, mention that lag counts messages but users feel time.
