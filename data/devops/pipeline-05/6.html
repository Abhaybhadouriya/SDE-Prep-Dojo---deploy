Drill 1: kill a broker

The script SIGKILLs kafka-2 ("like pulling the power cord"), waits 15 seconds (the controller needs about 9 s to notice), lists under-replicated partitions, sends 5 orders, starts the broker again, waits 30 seconds and checks again. Step through what happens inside Kafka:

  1. Before. Partition 1 of orders.created has three replicas. kafka-2 is the leader; all three are in the ISR (in-sync replicas: the copies that are fully caught up).
  2. Kill. docker compose kill kafka-2. Nothing changes at once: the active controller only fences a broker (declares it dead) after its heartbeats have been missing for broker.session.timeout.ms, 9 s by default. In this compose setup every node is both broker and KRaft controller, so we also lose one of three controller voters; 2 of 3 is still a majority, so the cluster keeps working.
  3. Failover (about 9 s later). The controller removes kafka-2 from the ISR of every partition it hosted and picks a new leader from the remaining ISR, here kafka-3 (the next one in the replica list 2, 3, 1). Clients refresh metadata and follow. During those seconds, writes to partitions kafka-2 led wait, so the API may return a few slow responses or 504s.
  4. Writes continue. The order-api uses acks=all, and the topic has min.insync.replicas=2. The ISR is now {3, 1}: two copies, so writes succeed and every acknowledged order is on two brokers.
  5. Recovery. docker compose start kafka-2. The broker comes back with its old disk. It truncates its log to the high watermark (HW = the last offset that all ISR members have, so anything after it may never have been acknowledged), fetches what it missed from the new leader, and rejoins the ISR.
  6. Rebalance leaders. Leadership does not move back by itself instantly. The script runs a preferred leader election, and kafka-2, first in the replica list, leads again, so the load spreads evenly.

In Grafana, Under-replicated partitions jumps from 0 to a positive number, the UnderReplicatedPartitions alert goes pending and then firing after 1 minute, and drops back to 0 after the restart. order-api accepted vs errors may show a short blip while clients refresh metadata, then normal.

Now the bonus question: what if you kill two brokers? The project README answers it. Partitions drop to an ISR of 1, below min.insync.replicas=2, so producers with acks=all get NOT_ENOUGH_REPLICAS and the order-api returns errors (503/504). And with only 1 of 3 controller voters left, the KRaft quorum is lost. The system chooses consistency over availability: it refuses writes rather than accept orders that exist on only one disk. That is the CAP trade-off made visible, and a great thing to say in an interview.

From your world

The ISR is a redundancy group where only members whose state is synced are eligible to take over, like an HA pair where a standby with stale state is not allowed to go active. min.insync.replicas is "do not forward unless the mirror is up". Where it breaks: VRRP failover is about one virtual IP; Kafka does a separate leader election for every partition, so one broker failure triggers many small elections at once, all decided by the KRaft controller.
