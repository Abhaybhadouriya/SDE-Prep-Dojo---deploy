depends_on, healthchecks and the "started is not ready" trap

A healthcheck is a command Docker runs inside the container every few seconds to ask "are you really working?". Plain depends_on: [db] only means "start the db container first". A database container is "started" the instant its process launches, but Postgres needs a few seconds to initialise, and a Kafka broker longer. Your API starts, tries to connect, gets "connection refused", and crashes.

Three conditions exist:

  • service_started - the default: just started.
  • service_healthy - the dependency's healthcheck passes. Use this for databases and brokers.
  • service_completed_successfully - the dependency ran and exited with code 0. Perfect for one-shot jobs like database migrations or creating Kafka topics.
services:
  migrate:
    build: .
    command: ["alembic", "upgrade", "head"]
    depends_on:
      db: { condition: service_healthy }
  api:
    build: .
    depends_on:
      migrate: { condition: service_completed_successfully }

Still add retries in your code. Healthchecks only help at startup. In production (and on Kubernetes, which has no depends_on at all) the database can restart at any time, so clients must reconnect with backoff. Treat depends_on as a developer convenience, not a reliability feature.

From your world

"Started" vs "healthy" is "link up" vs "adjacency FULL". An OSPF interface can be up long before the neighbour reaches FULL state and routes are installed; sending traffic as soon as the link comes up just blackholes it. A healthcheck is the protocol-level check that the peer is really ready. Where it breaks: a Docker healthcheck is just a command that Docker runs on a timer inside the container; there is no state machine and no neighbour talking back.
