Kafka in Compose: the two-listener trick

Good to know (Level 4). You have not read the Kafka track yet, so here is all the Kafka you need for this section. Come back to it after the Kafka track if it feels fast.

Explain like I'm 5

Kafka is a big shared notebook where programs write messages and other programs read them later. One Kafka server is called a broker. When a program wants to use the notebook, it first knocks on any broker's door and asks "who is in charge of which page?". The broker answers with an address card: "come to this door". The program then walks to the door on the card. If the card shows a door the program cannot reach, it gets lost.

The Kafka words this section uses (one line each; the Kafka track has the full story):

WordOne lineDetails
BrokerOne Kafka server process. A cluster is several brokers.Kafka 02
Topic / partitionA topic is a named stream of messages (like orders). It is split into partitions, append-only logs that can live on different brokers, so "3 partitions" means 3 logs read in parallel.Kafka 02
Replication factorHow many brokers keep a copy of each partition. 3 means "survive losing 2 copies"; it cannot be higher than the number of brokers.Kafka 05
Consumer group + coordinatorReaders that share the work of one topic. One broker acts as the group's coordinator and stores how far each reader got (its offsets) in an internal topic, __consumer_offsets.Kafka 04
KRaftKafka's built-in way to keep cluster metadata (no ZooKeeper since Kafka 4.0). Storage is formatted once with a fixed CLUSTER_ID.Kafka 08

From your world

The advertised listener is a BGP next-hop problem. A route is only useful if the next-hop it announces is reachable from the receiver's side; announce an address that only makes sense on your side and traffic black-holes. It is also the classic FTP active mode behind NAT bug: the server puts an address inside the payload, and that address is wrong on the other side of the NAT (which is why NAT boxes needed an FTP ALG). Where it breaks: nothing rewrites Kafka's address for you the way an ALG does; you must configure one listener per "side" yourself.

You will run Kafka in Compose for the ShopStream pipeline (ShopStream is the order-events demo app this site builds in the Pipeline track: a shop writes order events to Kafka and other services read them). It has one famous trap that is pure networking, so you will enjoy it. When a Kafka client connects, it first asks the broker for cluster metadata, and the broker answers with the address clients should use, called the advertised listener. The client then reconnects to that address. So the broker must advertise an address that works from wherever the client is.

# Single-broker Kafka in KRaft mode (no ZooKeeper; Kafka 4.x removed it)
services:
  kafka:
    image: apache/kafka:4.3.2
    hostname: kafka
    ports: ["9092:9092"]                       # only the EXTERNAL listener is published
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller   # one node does both jobs
      CLUSTER_ID: ${KAFKA_CLUSTER_ID:-5L6g3nShT-eMCtK--X86sw}
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:29093
      KAFKA_LISTENERS: INTERNAL://:19092,EXTERNAL://:9092,CONTROLLER://:29093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:19092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1  # single broker: RF must be 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_LOG_DIRS: /var/lib/kafka/data      # without this the image writes to /tmp and the volume is unused
    volumes: ["kafka-data:/var/lib/kafka/data"]
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:19092 > /dev/null 2>&1"]
      interval: 10s
      timeout: 10s
      retries: 12
      start_period: 15s

  order-api:
    build: ./order-api
    environment:
      KAFKA_BOOTSTRAP: kafka:19092             # internal listener, by service name
    depends_on:
      kafka: { condition: service_healthy }

volumes:
  kafka-data: {}

This is a trimmed version of the reference project's pipeline/code/compose.single-broker.yml (the image is pinned to 4.3.2 to match pipeline/code; 4.4.x is the newest Kafka line as of late 2026). KAFKA_LOG_DIRS matters: the apache/kafka image writes its data to /tmp/kraft-combined-logs by default, so without it the named volume stays empty and your topics vanish when the container is re-created. CLUSTER_ID is the fixed cluster identity that KRaft formats the storage with.

Why replication factor 1? (If this paragraph feels fast, come back after Kafka 05; you only need the result: one broker means every replication factor must be 1.) Kafka keeps consumer-group positions in an internal topic called __consumer_offsets, whose default replication factor is 3. With one broker that can never be met, so the topic is never created, the group coordinator never comes up, and every consumer hangs waiting for it. Setting the offsets and transaction-log factors to 1 is what makes a single broker usable.

The full 3-broker version (with replication factor 3, Postgres, Prometheus and Grafana) is in pipeline/code/docker-compose.yml; Build It Locally walks through it.

Try it: one complete compose.yaml (producer + database + Kafka + sink)

This is the "run a 3-service app locally: app, database, Kafka" exercise in one copy-paste file. Nothing to build: a producer uses Kafka's own console tool to send one fake order every 2 seconds, a tiny Python sink app reads the orders and stores them in Postgres, and a one-shot kafka-init job creates the topic before any app starts. Save it as compose.yaml in an empty folder.

name: mini-shop

configs:
  sink_py:                       # the whole "app": read orders from Kafka, write them to Postgres
    content: |
      import json, psycopg
      from confluent_kafka import Consumer
      c = Consumer({"bootstrap.servers": "kafka:19092", "group.id": "order-sink",
                    "auto.offset.reset": "earliest"})
      c.subscribe(["orders"])
      db = psycopg.connect("host=db user=postgres password=devpass dbname=shop", autocommit=True)
      db.execute("CREATE TABLE IF NOT EXISTS orders (order_id int PRIMARY KEY, amount_paise int)")
      print("sink ready", flush=True)
      while True:
          m = c.poll(1.0)
          if m is None or m.error():
              continue
          o = json.loads(m.value())
          db.execute("INSERT INTO orders VALUES (%s, %s) ON CONFLICT DO NOTHING",
                     (o["order_id"], o["amount_paise"]))
          print("stored order", o["order_id"], "from partition", m.partition(), flush=True)

services:
  kafka:
    image: apache/kafka:4.3.2
    hostname: kafka
    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      CLUSTER_ID: 5L6g3nShT-eMCtK--X86sw
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:29093
      KAFKA_LISTENERS: INTERNAL://:19092,EXTERNAL://:9092,CONTROLLER://:29093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:19092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
      KAFKA_LOG_DIRS: /var/lib/kafka/data
    volumes: ["kafka-data:/var/lib/kafka/data"]
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:19092 > /dev/null 2>&1"]
      interval: 10s
      timeout: 10s
      retries: 12
      start_period: 15s

  kafka-init:                    # runs once, creates the topic, exits 0
    image: apache/kafka:4.3.2
    depends_on:
      kafka: { condition: service_healthy }
    entrypoint: ["/opt/kafka/bin/kafka-topics.sh", "--bootstrap-server", "kafka:19092",
                 "--create", "--if-not-exists", "--topic", "orders",
                 "--partitions", "3", "--replication-factor", "1"]
    restart: "no"

  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: devpass   # local demo only; use secrets for anything real
      POSTGRES_DB: shop
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d shop"]
      interval: 5s
      retries: 10

  producer:
    image: apache/kafka:4.3.2
    depends_on:
      kafka-init: { condition: service_completed_successfully }
    entrypoint: ["sh", "-c"]
    command:
      - |
        i=0
        while true; do
          i=$$((i+1))
          echo "{\"order_id\": $$i, \"amount_paise\": 49900}"
          sleep 2
        done | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka:19092 --topic orders

  sink:
    image: python:3.12-slim
    depends_on:
      kafka-init: { condition: service_completed_successfully }
      db: { condition: service_healthy }
    configs:
      - source: sink_py
        target: /app/sink.py
    command: ["sh", "-c", "pip install -q confluent-kafka==2.6.1 'psycopg[binary]==3.2.3' && python -u /app/sink.py"]

volumes:
  kafka-data: {}
  pgdata: {}

Notes: $$ is how you write a literal $ in a Compose file (a single $ would be read as a Compose variable). The inline configs: content: block needs Compose v2.23 or newer. The sink installs its two libraries when it starts, so the first start needs internet and takes a little while; in a real project you would bake them into an image with a Dockerfile. service_completed_successfully means "wait until that one-shot container has exited with code 0".

Your timings, partitions and counts will differ (the producer sends with no key, so orders spread across the 3 partitions). You can also read the topic yourself: docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning. The classic symptom: if you advertise only localhost:9092, a client inside another container bootstraps fine (it reached kafka:9092), receives metadata saying "talk to localhost:9092", reconnects to its own loopback, and fails with connection errors. If you advertise only kafka:9092, host tools fail because your laptop cannot resolve kafka. Two listeners, two advertised addresses. The same issue appears again on Kubernetes (see Kafka on K8s).
