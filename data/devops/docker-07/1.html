Your first compose.yaml

Here is a small but realistic app: a Python API that talks to Postgres and Redis (an in-memory key-value store, used here as a cache). Save it as compose.yaml next to the API's Dockerfile.

# compose.yaml  (no "version:" key needed any more)
services:
  api:
    build: .                       # build the image from ./Dockerfile
    ports:
      - "8000:8000"                # host:container, only the API is published
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/shop
      REDIS_URL: redis://cache:6379/0
    depends_on:
      db:
        condition: service_healthy # wait until db's healthcheck passes
      cache:
        condition: service_started
    restart: unless-stopped

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10

  cache:
    image: redis:7-alpine

volumes:
  pgdata: {}
  1. services - each entry becomes one or more containers. The key (api, db, cache) is the service name, and it is also the DNS name other containers use.
  2. build or image - build from a Dockerfile, or pull a ready image. You can have both: build it and tag it with that name.
  3. ports - same as -p. Only publish what a human or outside tool needs (here, just the API). The database is reachable from api without publishing anything.
  4. environment - same as -e. Note the URL says db:5432, not localhost: from the API container, the database is another host on the network.
  5. depends_on - start order, and with condition, readiness. More on this below; it is the most misunderstood key.
  6. volumes (top level) - declares a named volume. Compose creates it as <project>_pgdata.

Postgres 18+ moved its data path. The examples on this page pin postgres:17, where /var/lib/postgresql/data is correct. From postgres:18 the official image keeps data under /var/lib/postgresql/<major>/docker, so when you move to 18+ mount the volume at /var/lib/postgresql instead. Keep the old path and the new server starts with an empty data directory, so your data seems "lost" (it is still in the volume). A major upgrade also needs pg_upgrade or dump/restore; see Volumes.

The project name (shop here) defaults to the folder name. Every network, volume and container gets that prefix, which is how two projects on one machine stay separate. Override it with name: at the top of the file or docker compose -p.

The commands you will use daily

CommandWhat it does
docker compose up -dCreate/update everything and start it in the background. Re-run it after editing the file: only changed services are re-created.
docker compose up -d --buildRebuild images first (after code changes)
docker compose psStatus and health of this project's containers
docker compose logs -f apiFollow logs of one service (omit the name for all, colour-coded)
docker compose exec db psql -U app shopRun a command inside a running service
docker compose run --rm api pytestOne-off container from a service definition (tests, migrations)
docker compose restart apiRestart containers (does not pick up file changes; use up -d)
docker compose downStop and remove containers and the network. Volumes are kept.
docker compose down -vAlso delete named volumes: your database is gone
docker compose configPrint the final, merged, variable-substituted file. Your best debugging friend.
docker compose watchSync or rebuild automatically when source files change (needs a develop.watch section)
