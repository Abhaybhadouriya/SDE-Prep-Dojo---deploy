What docker compose up actually does

Compose is not a separate engine. It is a client (a CLI plugin) that reads your file and makes the same API calls to dockerd that docker network create, docker volume create and docker run make. Step through it.

  1. Resolve. Compose reads compose.yaml, merges any override files, substitutes ${VARIABLES} from your shell and the .env file, and validates it against the Compose Specification. docker compose config shows you this exact result.
  2. Network. It creates a user-defined bridge network <project>_default. Every service joins it, so all of them get DNS by service name (see Networking).
  3. Volumes. It creates any named volumes that do not exist yet. Existing ones are reused, which is why your data survives down / up.
  4. Images. It pulls images that are missing and builds services that have a build: section (through BuildKit).
  5. Start in order. It builds a dependency graph from depends_on and starts services with no dependencies first. Independent services start in parallel.
  6. Wait for health. For condition: service_healthy, Compose waits until Docker marks the container healthy (its healthcheck command succeeded).
  7. Start dependants. Only then is api created and started. It connects to db:5432; the embedded DNS returns the db container's IP on the project network.

On a second docker compose up -d, Compose compares each service's configuration with a hash stored in container labels. Unchanged services are left running; changed ones are re-created. That is why editing one environment variable re-creates only that service.
