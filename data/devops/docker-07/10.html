Interview questions

What is Docker Compose and when would you NOT use it?

Compose is a tool that defines a multi-container application in one declarative YAML file (services, networks, volumes, configuration) and manages its lifecycle with commands like up and down. It is great for local development, CI integration tests and small single-host deployments. I would not use it for production systems that need high availability across machines, automatic rescheduling when a host fails, rolling updates without downtime, or autoscaling, because Compose is single-host and only acts when you run it. For those I would use Kubernetes or a managed container service.

How to answer

Define it in one sentence, give 2-3 good uses, then the limits with the reason (single host, no continuous reconciliation). Compose follow-ups like this were reported in a public Walmart SDE-2 LLD round write-up.

Likely follow-ups
  • How do services find each other in Compose?
  • How would you move this Compose app to Kubernetes?
Does depends_on guarantee that the database is ready before the app starts?

Not by itself. Plain depends_on only controls start order: the database container is started first, but its process may still be initialising when the app connects. To wait for readiness, give the database a healthcheck (for example pg_isready) and use condition: service_healthy on the dependant. Even then, I make the app retry connections with backoff, because a dependency can restart later, and in Kubernetes there is no depends_on at all; there you rely on readiness probes and retries.

How to answer

Say "start order, not readiness" first. Then the fix, then why retries are still needed. That last step separates SDE-2 answers from SDE-1 answers.

Likely follow-ups
  • What is service_completed_successfully used for?
  • How do readiness probes differ from Docker healthchecks?
How do services in a Compose project discover and talk to each other?

Compose creates a user-defined bridge network called <project>_default and attaches every service to it. Docker's embedded DNS server at 127.0.0.11 resolves each service name to its container IP (or to several IPs if the service is scaled). So the API connects to db:5432 using the container port; host port publishing is only for access from outside. You can define extra networks to isolate tiers, for example the proxy cannot reach the database.

How to answer

Network, DNS, container port vs host port. Bonus: mention that this is the Compose equivalent of a Kubernetes Service name resolved by CoreDNS.

Likely follow-ups
  • What happens to DNS when you run --scale worker=3?
  • Why can't you scale a service with a fixed published port?
Your app container cannot produce to Kafka in Compose, but the Kafka CLI on your laptop works. What is wrong?

Almost certainly advertised listeners. Kafka clients bootstrap, fetch metadata, then reconnect to the broker's advertised address. If the broker advertises localhost:9092, the laptop is happy, but the app container receives "localhost:9092", connects to its own loopback, and fails. The fix is two listeners: an internal one advertised as kafka:19092 for containers on the Compose network, and an external one advertised as localhost:9092 and published to the host, mapped in KAFKA_LISTENER_SECURITY_PROTOCOL_MAP. The app's bootstrap setting should be kafka:19092.

How to answer

Explain the bootstrap-then-metadata flow first; the bug follows logically. Drawing the two clients on either side of the broker makes it obvious.

Likely follow-ups
  • How does this change on Kubernetes with a Strimzi cluster? (Strimzi is an operator: a controller that runs Kafka on Kubernetes for you. It generates the listeners itself: an internal one advertised as each broker pod's Service DNS name, and an external one through a NodePort, LoadBalancer or Ingress that advertises the address reachable from outside.)
  • Why must the offsets topic replication factor be 1 on a single broker? (Its default is 3; with one broker the topic cannot be created, so the group coordinator never starts and consumers hang.)
How do you keep different settings for dev, CI and production with Compose?

Keep a base compose.yaml with the shared service definitions, and layer environment-specific files on top: compose.override.yaml is merged automatically for local development (bind mounts, debug ports, reload), and CI uses -f compose.yaml -f compose.ci.yaml. Variables like image tags come from .env or the CI environment through ${VAR} substitution, and optional tools sit behind profiles. docker compose config shows the merged result so you can review it. Secrets come from files or the CI secret store, never from the committed YAML.

How to answer

Base plus overrides, variables, profiles, secrets. Mention the config command as how you verify.

Likely follow-ups
  • What is the difference between .env and env_file?
  • How would you handle secrets in production instead?

Scenario: "the integration tests are flaky in CI"

A team runs docker compose up -d then their test suite in CI. About one run in five fails with "connection refused" to Postgres or Kafka in the first test. Rerunning the job usually passes.

Weak answer: "Add sleep 30 before the tests."

Strong answer: It is a readiness race: services are started but not ready, and CI machines vary in speed, so a fixed sleep is both slow and still flaky. Add real healthchecks (pg_isready, kafka-broker-api-versions.sh), make dependants use condition: service_healthy, put migrations and topic creation in one-shot services with service_completed_successfully, and start the test run with docker compose up -d --wait, which blocks until services are running and healthy. Also add connection retries with backoff in the test fixtures, pin image versions so a new latest does not change startup time, and on failure dump docker compose logs as a CI artifact.

Likely follow-ups
  • How would you speed up the CI run? (cache images, smaller images, tmpfs for test DB data)
  • Would you use Testcontainers (a library that starts throw-away Docker containers from inside your test code) instead? Trade-offs?

60-second answer - "Explain Docker Compose": "Compose describes a multi-container app in one YAML file: services with their image or build, ports, environment, volumes and dependencies. docker compose up resolves the file and variables, creates a project network, so services find each other by name through Docker's embedded DNS, creates named volumes, pulls or builds images, and starts services in dependency order; with healthchecks and service_healthy it waits for real readiness. It is declarative, so a second up only re-creates what changed. I use it for local dev and CI, with override files and profiles per environment. It is single-host and does not keep reconciling, so for production I move to Kubernetes, where readiness probes and controllers replace depends_on and restart policies."
