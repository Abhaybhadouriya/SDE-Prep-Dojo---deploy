Compose vs Kubernetes: why both exist

This was one of your questions: "what is Compose for, if Kubernetes exists?" Short answer: Compose runs an app on one machine for development and testing; Kubernetes runs apps across many machines in production. Many teams use both: Compose on laptops and in CI, Kubernetes in staging and production.

Docker ComposeKubernetes
ScopeOne hostA cluster of many nodes
Who keeps things runningdockerd restart policies; Compose acts only when you run itControllers that reconcile continuously (see Architecture)
Host diesEverything on it is downPods are rescheduled on other nodes
HealthHealthcheck status, used for start orderLiveness, readiness and startup probes that restart pods and gate traffic
Load balancingDNS round-robin between replicasServices with stable virtual IPs (Services)
Rolling updatesRe-create containers (brief downtime)Rolling updates with surge and rollback (Deployments)
Learning curveMinutesWeeks
Best forDev laptops, CI integration tests, demos, small single-server appsProduction at scale, many teams, high availability

Say it like this: "I would use Compose for local development and integration tests because it is one file and starts in seconds. For production I need multi-node scheduling, self-healing, rolling updates and service discovery with health-aware load balancing, so I would deploy to Kubernetes or a managed service like ECS (AWS's managed container service). The Compose file is still useful as documentation of how services connect." Mentioning that depends_on does not exist in Kubernetes (you use readiness probes and client retries) shows real understanding.

Docker also has its own multi-host orchestrator, Swarm mode, which can deploy Compose files with docker stack deploy. It works, but industry has largely standardised on Kubernetes, so learn Swarm only if a job requires it.
