Gotchas

  • v1 overwrites a v2 row. While both versions run, a v1 pod updates phone on a row v2 already wrote, leaving phone_e164 stale but not NULL. A NULL-only backfill and a NULL-only check both pass. Backfill and verify on IS DISTINCT FROM normalize(phone), or use a trigger.
  • Backfill before dual write is complete. If any pod still runs v1 (which writes only the old column), rows it touches after the backfill are missed. Start the backfill only after the v2 rollout is 100% done, and verify with a count afterwards.
  • NOT NULL on the new column too early. v1 inserts do not provide it and start failing. Constraints come at the end.
  • Dropping NOT NULL too late on the old column. v4 stops writing it, so v4 inserts fail. Relax it before v4.
  • SELECT * and strict mappers. Some code breaks on a new, unknown column. Name your columns.
  • Volatile defaults and type changes rewrite the whole table under an exclusive lock. Read the database docs for which ALTER forms are metadata-only.
  • Forgetting other readers. Reports, data pipelines, CDC consumers and other services read the old column too. Contract only after they move.
  • Canary plus migration. A canary may run v2 for hours or days next to v1, so compatibility must hold for that whole window, not just for a quick rolling update.
  • Blue-green does not mean two databases. Both stacks almost always share one database, so blue-green needs expand-migrate-contract just as much as rolling does.
  • Caches and serialized objects. A v2 pod writes a cache entry or a queued message in the new shape; a v1 pod reads it. Version your cache keys and message schemas the same way.
