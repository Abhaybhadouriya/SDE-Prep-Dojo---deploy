Where migrations run in a Kubernetes pipeline

Good to know (SDE-2)

The schema step must run once, before the app rollout that needs it, and must not depend on how many pods start. The common patterns:

PatternHowWatch out
Pipeline stepCI/CD job runs flyway migrate against the DB, then triggers the deployPipeline needs DB network access and credentials
Argo CD sync hook / waveA Job annotated argocd.argoproj.io/hook: PreSync (or a lower sync-wave) runs before the Deployment is appliedJob must be idempotent; set backoffLimit and a deadline
Helm hookhelm.sh/hook: pre-upgrade JobFailed hook leaves the release failed; know how to retry
On app startup / initContainerEvery pod runs migrate on boot (tool lock serializes them)Couples pod start to DB locks; slow migration = pods stuck, readiness fails, rollout stalls. Avoid for anything non-trivial.
 
apiVersion: batch/v1
kind: Job
metadata:
  name: users-migrate-v42
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
spec:
  backoffLimit: 1
  activeDeadlineSeconds: 900
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: flyway
          image: registry.example.internal/users-migrations:1.9.0   # immutable, built once
          args: ["migrate"]
          envFrom:
            - secretRef: { name: users-db-migrator }               # DDL-capable user, not the app user
$ kubectl logs job/users-migrate-v42
Flyway OSS Edition by Redgate
Database: jdbc:postgresql://users-db:5432/users (PostgreSQL 18.1)
Successfully validated 42 migrations (execution time 00:00.031s)
Current version of schema "public": 41
Migrating schema "public" to version "42 - phone e164 constraint"
Successfully applied 1 migration to schema "public", now at version v42 (execution time 00:04.212s)

Notice the migration image is itself an immutable artifact built once (the rule from build once, promote many), and it uses a separate database user with DDL rights, so the app's own credentials cannot alter the schema.

The lock queue outage. In Postgres, ALTER TABLE needs an ACCESS EXCLUSIVE lock for an instant. If one long-running query (an analytics report) holds a conflicting lock, the ALTER waits, and every new query on that table queues behind the ALTER. A "instant" metadata change takes the whole service down. Always SET lock_timeout (a few seconds) in migrations, and retry with backoff when it fires.
