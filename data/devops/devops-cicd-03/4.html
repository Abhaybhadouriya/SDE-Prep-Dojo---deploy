The full walkthrough with real SQL and code

Must know (SDE-1)

Postgres syntax below; the ideas are the same on MySQL. Migrations are versioned files run by a tool such as Flyway or Liquibase, which records what ran in a history table and takes a lock so two runners cannot apply the same migration at once.

Step 1 - Expand (migration V41)

-- V41__add_phone_e164.sql
SET lock_timeout = '3s';            -- give up instead of queueing behind a long query
ALTER TABLE users ADD COLUMN phone_e164 text;   -- nullable, no default: catalog-only change

Why it is safe for v1: v1 never mentions phone_e164. Two conditions make that true, and both are worth saying in an interview: the column is nullable (v1's inserts do not supply it), and v1 does not do SELECT * into a strict mapper that fails on unknown columns.

Why it is fast: in Postgres, adding a nullable column, or one with a constant default (Postgres 11+), only updates the catalog; existing rows are not rewritten. A volatile default such as clock_timestamp() forces a full table rewrite under an exclusive lock, which is an outage on a big table.

Step 2 - Dual write (app v2)

// v2: write both, read old
public void updatePhone(long userId, String raw) {
    String e164 = PhoneNormalizer.toE164(raw, "IN");   // may return null if unparseable
    jdbc.update("UPDATE users SET phone = ?, phone_e164 = ? WHERE id = ?",
                raw, e164, userId);                     // ONE statement: both columns or neither
}

public String getPhone(long userId) {
    return jdbc.queryForObject("SELECT phone FROM users WHERE id = ?", String.class, userId);
}

Write both columns in the same statement or transaction. Writing them in two separate calls lets a crash leave them disagreeing. If the data lived in two different stores (a table in another service, a search index), you could not get one transaction; you would use change data capture or an outbox instead, and treat the new store as eventually consistent.

Step 3 - Backfill (a one-off Job)

-- run repeatedly until it updates 0 rows; each run is one short transaction
WITH batch AS (
  SELECT id FROM users
  WHERE phone IS NOT NULL
    AND phone_e164 IS DISTINCT FROM normalize_e164(phone)   -- NULL *or* stale
    AND id > :last_id                -- keyset cursor, so each pass moves forward
  ORDER BY id
  LIMIT 5000
  FOR UPDATE SKIP LOCKED          -- never wait on rows the live app is updating
)
UPDATE users u
SET    phone_e164 = normalize_e164(u.phone)
FROM   batch
WHERE  u.id = batch.id
RETURNING u.id;                     -- the job saves max(id) as the next :last_id
$ ./backfill-phone.sh --batch 5000 --sleep-ms 200
batch 1     updated 5000   last_id 41877     replica_lag 0.2s
batch 2     updated 5000   last_id 83511     replica_lag 0.3s
...
batch 371   updated 642    last_id 9918034   replica_lag 0.1s
done: 1849102 rows in 26m31s   (1843210 NULL + 5892 stale)

$ psql -c "SELECT count(*) FILTER (WHERE phone_e164 IS NULL)              AS missing,
                  count(*) FILTER (WHERE phone_e164 <> normalize_e164(phone)) AS mismatched
           FROM users WHERE phone IS NOT NULL;"
 missing | mismatched
---------+------------
       0 |          0
(1 row)

(Your counts and timings will differ; the shape of the output is the point.) Rules for a backfill that does not hurt production:

  • Small batches, short transactions. One giant UPDATE users SET ... holds row locks for the whole run, bloats the table and floods replication.
  • Throttle on a signal. Sleep between batches and slow down when replica lag or p99 latency climbs.
  • Idempotent and resumable. The filter selects only rows whose new column is missing or disagrees with the old one, and the job stores its last_id cursor, so a crashed run just starts again. Never keep progress only in memory.
  • Compare values, not NULLs. During the v2 rollout a row can be written by a v2 pod (both columns set) and then updated by a v1 pod, which changes only phone. Its phone_e164 is now stale but not NULL, so an IS NULL backfill and an IS NULL check would both miss it and v3 would read wrong data. Re-deriving the value with IS DISTINCT FROM normalize_e164(phone) catches both cases, and rewriting an already-correct row is harmless because the value is a pure function of phone. (If normalising in SQL is not possible, re-process every row with updated_at after the v2 rollout started, once v2 is at 100%.)
  • Trigger instead of app dual-write. On hot tables many teams let a database trigger keep phone_e164 in sync from phone. Every writer, old or new, goes through it, so there is no version race at all; drop the trigger at the contract step.
  • Unparseable values. Decide up front: leave NULL and log, or write to a quarantine table for a human. Do not invent data.

Optional hardening once the backfill is done: make the database enforce the invariant, without a long lock.

-- V42: enforce "if phone is set, phone_e164 is set" without a blocking scan
ALTER TABLE users ADD CONSTRAINT phone_e164_present
  CHECK (phone IS NULL OR phone_e164 IS NOT NULL) NOT VALID;    -- new writes checked now
ALTER TABLE users VALIDATE CONSTRAINT phone_e164_present;        -- scans old rows, weaker lock

-- and if lookups by the new column need an index:
CREATE INDEX CONCURRENTLY idx_users_phone_e164 ON users (phone_e164);

(On PostgreSQL 18 you can skip the CHECK detour: ALTER TABLE users ADD CONSTRAINT phone_e164_nn NOT NULL phone_e164 NOT VALID; then VALIDATE CONSTRAINT. Older versions need the CHECK shown here.) NOT VALID skips checking existing rows, so the ALTER is quick; VALIDATE CONSTRAINT then scans them holding only a SHARE UPDATE EXCLUSIVE lock, which does not block reads or writes. CREATE INDEX CONCURRENTLY builds without blocking writes (it cannot run inside a transaction block, so tell your migration tool).

Step 4 - Switch reads (app v3)

public String getPhone(long userId) {
    if (flags.isOn("read-phone-e164")) {                 // flip off = instant rollback of reads
        return jdbc.queryForObject("SELECT phone_e164 FROM users WHERE id = ?", String.class, userId);
    }
    return jdbc.queryForObject("SELECT phone FROM users WHERE id = ?", String.class, userId);
}
// writes: still BOTH columns, exactly as v2

Before trusting the new column, many teams run shadow reads: read both, return the old value, log any mismatch. Stripe described doing this for a large migration with GitHub's Scientist library, comparing results from the old and new data models in production before switching.

Step 5 - Contract (app v4, then migration V43)

// v4: new column only
jdbc.update("UPDATE users SET phone_e164 = ? WHERE id = ?", e164, userId);
-- V43__drop_phone.sql   (ships days later, after v4 has baked)
SET lock_timeout = '3s';
ALTER TABLE users DROP COLUMN phone;

Two details people miss. First, if phone was NOT NULL, drop that constraint before v4 ships, or v4's inserts (which no longer set it) fail. Second, with ORMs like Hibernate or ActiveRecord, the app must stop referencing the column before the drop (Rails has ignored_columns for exactly this), or the old code's cached column list breaks.
