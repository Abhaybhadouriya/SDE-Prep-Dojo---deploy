Rollback at each step: where the point of no return is

Must know (SDE-1)

Three habits make the rollback plan real instead of theoretical:

  1. Forward-only migrations. Many teams never run "down" migrations in production. Rolling back means deploying the previous app version, which works because the schema is still compatible. A down script that drops a freshly filled column is a data-loss button.
  2. One step per release. Never ship "add column + switch reads" together. If the release goes wrong, you want to know which step caused it, and you want the previous release to be a valid target.
  3. Bake time before contract. Wait at least one full business cycle (batch jobs, month-end reports, the analytics export nobody remembered) before dropping. Search every repo and every BI tool for the old column name first.

From your world

This is how you would renumber a production network. You add the new subnet as a secondary address on the interface (expand), advertise both prefixes, move hosts over one by one with DHCP (migrate), switch the default route and DNS to the new range (switch reads), and only after the ARP and flow tables show zero traffic on the old prefix do you remove the secondary address (contract). Pulling the old prefix first is the network version of dropping the column first.
