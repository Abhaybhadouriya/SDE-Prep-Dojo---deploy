The hidden problem: two app versions, one database

Must know (SDE-1)

Look at the last column of the table again. In every strategy, v1 and v2 of the application are live at the same time, and they talk to the same database. The database has exactly one schema at any moment. So every schema must work for both the app version that is leaving and the one that is arriving.

Now try the naive change: "rename users.phone to users.phone_e164" in one release, with the migration running just before the rollout.

There is a second trap: rollback. Code rollback is a pointer change (you learned that on the builds page). A destructive schema change is not reversible that way; once a column is dropped, its data is gone unless you restore a backup. So the rule is:

Interviewers love this: "Every schema change must be backward compatible with the app version currently running (so the old app survives the migration) and every app release must be forward compatible with the schema that will exist after it (so you can roll it back). Expand-migrate-contract is the recipe that guarantees both."

From your world

This is protocol versioning between routers. When BGP gained new capabilities, nobody changed the meaning of an existing field. New things arrived as new, optional attributes that old speakers could ignore, and capabilities were negotiated. A field could only be retired after every peer in the network had upgraded. A database column is a field in a wire format shared by every app instance: add new fields first, retire old ones last.
