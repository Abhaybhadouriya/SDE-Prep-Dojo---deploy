Interview questions

How do you rename a column in a live database with zero downtime?

Never in one step, because during any rollout the old and new app versions share the database. Use expand-migrate-contract: (1) add the new nullable column; (2) release an app that writes both columns in one statement but still reads the old one; (3) once that is fully rolled out, backfill old rows in small, throttled, idempotent batches and verify the count of missing values is zero; (4) release an app that reads the new column, behind a flag, still writing both; (5) release an app that writes only the new column, wait a bake period, then drop the old column. Each step is its own release, and every step except the final drop can be rolled back by deploying the previous app version.

How to answer

Start with "old and new code run together", then the five steps, then say where rollback stops being free. Draw the release table if there is a whiteboard.

Likely follow-ups
  • Why backfill only after dual write is fully rolled out?
  • How do you backfill 500 million rows without hurting production?
  • How do you make the new column NOT NULL safely?
Compare rolling, blue-green and canary deployments.

Rolling replaces instances in batches: cheap, slow-ish rollback, and both versions run during the rollout. Blue-green keeps two full environments and switches the router in one step: instant rollback, roughly double infrastructure during the release, and both stacks still share the database. Canary sends a small share of real traffic to the new version and grows it while metrics stay healthy: smallest blast radius and fast rollback, but needs good metrics, automated analysis and a traffic-splitting layer, and both versions run for a long time. In all three, the schema must be compatible with both versions.

How to answer

Use the same four axes for each: cost, rollback speed, blast radius, compatibility window. End with when you pick each (canary for high-traffic services with good observability; blue-green for systems that need instant cut-over like payments).

Likely follow-ups
  • What metrics decide a canary? (Error rate, p99 latency, saturation, business KPIs vs baseline.)
  • How do you do canary on Kubernetes? (Argo Rollouts, Flagger, Gateway API weights, mesh.)
What is GitOps and how is it different from a CI pipeline running kubectl apply?

In push-based CD, the pipeline holds cluster credentials and pushes changes. In GitOps, the desired state lives in a git repo and a controller inside the cluster (Argo CD, Flux) continuously pulls it and reconciles live state to match, reporting and optionally reverting drift. Benefits: git history is the audit log, rollback is git revert, the cluster does not expose credentials to CI, and manual changes are detected. CI still builds and publishes the image; it just updates a manifest in git instead of talking to the cluster.

How to answer

Contrast push and pull in one sentence each, then list the three benefits: audit, rollback, drift correction.

Likely follow-ups
  • How do you run a database migration with Argo CD? (PreSync hook Job or sync waves.)
  • How do secrets work with GitOps? (Sealed Secrets, External Secrets Operator, SOPS.)
How would you backfill a new column on a table with hundreds of millions of rows?

As a separate, resumable job, not a single UPDATE. Select a batch of a few thousand primary keys that still need the value (so the job is idempotent and restartable), update them in a short transaction, skip rows locked by the live app, and sleep between batches. Throttle on replica lag and database latency. Select rows where the new column is NULL or differs from the value derived from the old column, because a v1 pod can update the old column on a row v2 already wrote, leaving the new one stale but not NULL. Because the new value is a pure function of the old one, recomputing it is always safe. On hot tables a database trigger avoids the version race altogether. Log progress, handle unparseable values explicitly, and finish with a verification query. For very large MySQL tables, or type changes, consider a copy-based tool such as gh-ost.

How to answer

Batch, idempotent, throttled, verified. Mention replication lag; it shows you have run one for real.

Likely follow-ups
  • The backfill job crashed at 60%. What now? (Rerun; the NULL filter resumes it.)
Where should database migrations run in a Kubernetes deployment, and why not in the app's startup?

As a single-run step that gates the rollout: a pipeline stage, an Argo CD PreSync hook Job or sync wave, or a Helm pre-upgrade hook, using an immutable migration image and a separate DDL-capable database user. Running migrations on every pod's startup couples pod readiness to schema locks: with 50 replicas you get 50 contenders for the migration lock, a slow migration keeps pods un-ready and stalls the rollout, and a failure shows up as crash-looping pods instead of one clear failed job.

How to answer

"Once, before, gated, idempotent." Then one sentence on why startup migrations fail at scale.

Likely follow-ups
  • How do you avoid a migration blocking all queries? (lock_timeout, retries, metadata-only forms, CONCURRENTLY.)
A release added a NOT NULL column and the canary started failing. What happened and how do you fix it?

The migration ran before the rollout, and the old version, still serving most traffic, does not supply the new column on insert, so its inserts violate the constraint. The canary metrics show failures (possibly on the old pods, which is confusing). Immediate fix: relax the constraint (ALTER COLUMN ... DROP NOT NULL) or add a default; the code rollback alone will not help because the schema stays. Proper fix: add the column nullable, make the app always write it, backfill, then add CHECK ... NOT VALID, VALIDATE, and only then SET NOT NULL.

How to answer

Diagnose ("schema not backward compatible with the running version"), mitigate, then the permanent recipe.

Likely follow-ups
  • How do you catch this in CI? (Run the old app's test suite against the new schema.)
Can you always roll back? Where is the point of no return in a schema change?

Code can always be rolled back to any version that is compatible with the current schema. With expand-migrate-contract, every step up to "stop writing the old column" keeps the previous version valid, so rollback is a normal deploy. Once the app stops writing the old column, rolling back to a version that reads it gives stale data, and once the column is dropped, only a backup restore helps. So you delay the contract step, bake each release, keep forward-only migrations, and treat the drop as a separate change with its own review.

How to answer

Separate "code rollback" from "data rollback". Name the exact step where the safe window ends.

Likely follow-ups
  • Do you write down migrations? (Usually not run in prod; roll forward instead.)

Scenario: "just rename it, it's one line"

A teammate's PR renames orders.cust_id to orders.customer_id with one migration and updates all code in the same release. The service runs 40 pods with rolling updates and a nightly reporting job reads the table.
Weak answer: "Approve it but deploy at 3 AM when traffic is low."
Strong answer: Low traffic does not fix incompatibility: during the rollout, old pods query a column that no longer exists, and the nightly job breaks too. Split it: add customer_id; release dual-write; backfill in batches; switch reads behind a flag; move the reporting job; stop writing cust_id; drop it after a bake period. Each step is its own release with a rollback path.
Likely follow-ups
  • Could a database view help? (Yes: a view with the new name can bridge reads while you migrate, but writes and indexes still need the plan.)
