Expand-migrate-contract, step by step

Must know (SDE-1)

Expand-migrate-contract (also called parallel change; Danilo Sato described it on martinfowler.com in 2014) splits one breaking change into several small, individually safe releases:

  1. Expand - add the new structure next to the old one. Nothing reads it yet.
  2. Migrate - make the app write both, copy the old data across (backfill), then switch reads to the new structure.
  3. Contract - stop writing the old structure, wait, then remove it.

The running example: users.phone is free text ("98450 12345", "+91-98450-12345"). We want users.phone_e164 in a normalized format ("+919845012345"). It is a rename and a format change, which is the realistic case. Step through it and watch the schema, the app versions and the rollback status together:

  1. Expand: add the column. ALTER TABLE users ADD COLUMN phone_e164 text; Nullable, no default, so v1 keeps working and the change is instant. Ship this migration on its own.
  2. Dual write. Release v2: on every insert or update it writes phone and the normalized phone_e164. It still reads phone. During the rollout, v1 pods still write only phone, so some rows will have NULL in the new column; that is expected.
  3. Backfill. Only after v2 is fully rolled out (so no writer skips the new column any more), a batched job fills phone_e164 for every row where it is NULL. Then verify: the count of NULLs where phone is not NULL is zero.
  4. Switch reads. Release v3 reads phone_e164 (often behind a feature flag you can turn off instantly) and keeps dual-writing so v2 stays a valid rollback target.
  5. Contract. Release v4 stops writing phone. After v4 has run cleanly for a bake period and nothing else reads the old column, a final migration drops it.

Count the releases: two schema migrations and three app versions for one "rename". That is the price of zero downtime and a rollback at every step. In practice the steps are often days apart, and v2/v3 can be one release when you use a feature flag for the read switch.
