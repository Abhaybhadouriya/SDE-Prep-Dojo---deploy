Quick quiz

Why can't you rename a column in the same release as the code that uses the new name, with a rolling update?

  1. Kubernetes does not allow it
  2. Old and new pods run at the same time, so one of them always sees the wrong column
  3. Renames are slow in every database
Whichever order you choose, part of the fleet is incompatible with the schema during the rollout.

When is it safe to start the backfill?

  1. Right after adding the column
  2. Halfway through the dual-write rollout
  3. After the dual-write version is fully rolled out
  4. After dropping the old column
Until every pod dual-writes, old pods can write rows the backfill already passed, leaving holes.

App v4 writes only the new column. Which rollback target is still safe?

  1. v3 (reads new, writes both)
  2. v2 (reads old)
  3. v1
v4 stopped updating the old column, so any version that reads it would see stale data.

What is the safest way to make an existing column NOT NULL on a big Postgres table?

  1. ALTER COLUMN SET NOT NULL directly at peak
  2. Add NOT NULL with the column in step one
  3. Lock the table and scan it in a maintenance window
  4. Add CHECK (col IS NOT NULL) NOT VALID, VALIDATE it, then SET NOT NULL
NOT VALID is quick, VALIDATE uses a weaker lock, and SET NOT NULL can then skip the full scan because a valid CHECK already proves it.

A tiny ALTER TABLE ... ADD COLUMN took the service down for a minute. Most likely cause?

  1. The column type was text
  2. It waited for an exclusive lock behind a long query, and all new queries queued behind it
  3. Postgres always rewrites the table
The lock queue. Set lock_timeout and retry.

Blue-green deployment means you do not need expand-migrate-contract. True?

  1. True, each colour has its own database
  2. True, the switch is instant
  3. False: both stacks usually share one database, and rollback must still work
Blue-green duplicates compute, not normally the database, so the schema must serve both colours.

In GitOps, who applies changes to the cluster?

  1. A controller in the cluster that pulls desired state from git
  2. The CI job with cluster-admin credentials
  3. Developers with kubectl
Pull-based: Argo CD or Flux reconcile the cluster to the repo.
