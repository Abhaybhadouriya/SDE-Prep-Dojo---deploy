Interview questions

What is the dual-write problem and how does the outbox pattern solve it?

A service that writes to its database and then publishes to Kafka performs two non-atomic writes. A crash in between loses the event; reversing the order can publish an event for a transaction that later rolls back. With the outbox pattern the service writes the business row and an outbox row describing the event in the same local transaction. A relay (Debezium reading the WAL, or a poller) publishes outbox rows to Kafka. The DB and the stream can no longer disagree. The relay is at-least-once, so consumers deduplicate by event id.

How to answer

Draw the two writes and the crash point first, then the outbox table and the relay. End with "consumers still need idempotency", which interviewers specifically listen for. Mention that CDC is better than polling: no extra query load and exact commit order.

Likely follow-ups
  • Why not Kafka transactions? (They cover Kafka writes, not your Postgres commit.)
  • How do you keep per-order ordering? (Key by aggregate id.)
  • What if the outbox grows forever? (Delete after capture, or partition and drop old partitions.)
Kafka Connect vs writing your own producer/consumer: when would you choose each?

Choose Connect when you are moving data between Kafka and a common system (databases, Elasticsearch, S3, warehouses) and a connector already exists. You get scaling by tasks, offset tracking, restarts, a REST API, converters and a DLQ without writing code. Choose your own client when the logic is business-specific, needs calls to several services, or the target has no good connector. Connect is integration; services are logic.

How to answer

Name the five parts (worker, connector, task, converter, SMT), then give the rule "integration with config, logic in code". Add that sinks are at-least-once, so use upserts.

Likely follow-ups
  • Where does Connect store state? (Three compacted topics: configs, offsets, status.)
  • What limits sink parallelism? (Partition count of the input topic.)
Kafka Streams vs Flink: how do you choose?

Kafka Streams is a library inside your service: no cluster, scales with app instances, Kafka in and Kafka out, exactly-once via Kafka transactions. It fits per-service processing such as enriching events, maintaining a materialized view or counting per key. Flink is a separate cluster with a JobManager and TaskManagers, many sources and sinks, very large state with incremental checkpoints, strong event-time and watermark support and SQL. It fits shared, large, stateful pipelines like clickstream analytics or fraud features across many topics. Rule of thumb: Streams for app-embedded processing, Flink for big platform pipelines.

How to answer

Compare on four axes: deployment, sources/sinks, state size and recovery, team skills. Give one example for each. Avoid "Flink is better": the cluster is an operational cost.

Likely follow-ups
  • How does each recover state? (Changelog topics vs checkpoints to object storage.)
  • What caps parallelism? (Input partitions for both.)
Where does a Kafka Streams app keep its state, and what happens when an instance crashes?

In local state stores, RocksDB by default, one per task. Every update is also written to a compacted changelog topic. When an instance dies, the group reassigns its tasks; the new owner rebuilds each store by replaying its changelog, then resumes from the committed offsets. With exactly_once_v2, input offsets, changelog writes and output writes commit atomically, so the restored state matches the offsets. Standby replicas keep warm copies to shorten failover.

How to answer

Say "local + changelog backup", then walk through the failover. Mention restore time as the real-life problem and the two fixes (standbys, persistent volumes).

Likely follow-ups
  • Why not keep state in Redis? (Network call per record, and no atomic commit with offsets.)
  • What is a repartition topic? (Re-keyed data so the same key reaches the same task.)
Explain event time, processing time and watermarks. How do you handle late events?

Event time is when the event happened, processing time is when the system sees it. Business windows should use event time, but then you cannot know for sure that a window is complete. A watermark (Flink) or grace period (Kafka Streams) states how much lateness you accept: once the watermark passes the window end, the window fires. Events later than that are dropped and counted, sent to a side output, or used to emit a corrected result. The trade-off is latency versus completeness.

How to answer

Use the "phone on a train" example, then the dial: bigger allowed lateness means more correct but slower results. Mention a batch correction job from the lake for the very late tail.

Likely follow-ups
  • Tumbling vs hopping vs session windows? (Draw the clock.)
  • What if one partition is idle? (Its watermark does not advance; Flink has idleness settings.)
Design: keep Elasticsearch and a Redis cache in sync with a sharded MySQL database.

Run a Debezium MySQL connector per shard reading the binlog. Each publishes row changes to topics keyed by primary key, so changes to one row stay ordered within a partition. Use Avro or Protobuf with Schema Registry for evolution. An Elasticsearch sink connector upserts documents with id = primary key and treats tombstones as deletes. A small consumer invalidates or updates Redis keys. Start with Debezium's snapshot, then stream. Monitor connector lag and binlog retention, and send poison records to a DLQ. Because everything is upsert-by-key, replays and duplicates are harmless.

How to answer

Say why CDC beats dual writes from the app, show per-key ordering, idempotent sinks and the snapshot-then-stream bootstrap. Mention a real reference: Shopify's sharded-monolith CDC post.

Likely follow-ups
  • A column is added: what breaks? (See Schema Registry: backward-compatible change.)
  • How to rebuild the index from scratch? (New index, new sink from earliest of a compacted topic, then swap an alias.)

Scenario: the orders table and Kafka disagree after a crash

The order service saves an order in Postgres and then calls producer.send() to publish OrderPlaced. After a pod was killed during a deploy, support finds 37 orders that exist in the database but that the shipping service never heard about, and two OrderPlaced events for orders that were rolled back. The interviewer asks how you would fix this for good.

Weak answer: "Write to the database, then produce, and add retries around send()." Or: "Produce first, then write to the database." (Both are still two separate writes. A crash between them loses an event in the first order, or invents one in the second, and retries cannot help if the process is dead. Kafka transactions do not cover Postgres either.)

Strong answer: "This is the dual-write problem: two systems, no shared transaction. I make the database the only write. In the same transaction that inserts the order, I insert a row into an outbox table. Debezium reads the committed rows from the write-ahead log and publishes them to Kafka with the Outbox Event Router, keyed by order ID so events for one order stay in order. If Debezium or Connect crashes, it resumes from its stored log position, so it may publish a row twice but never skips one; consumers therefore deduplicate by event ID. To repair the 37 missing orders I would backfill: select orders with no matching event in a time range and insert outbox rows for them. Then I monitor replication slot lag so a stuck connector cannot fill the database disk."

Likely follow-ups
  • Why not a polling relay instead of Debezium? (Works, simpler, but adds query load and latency, and ordering needs care; CDC reads the log the database already writes.)
  • Who cleans up the outbox table? (Delete rows right after insert in the same transaction, since Debezium reads the log not the table, or purge old rows on a schedule.)
  • What if the event must be published only after a payment API call succeeds? (Make that call a separate step that consumes the event, with an idempotency key; do not put external calls inside the DB transaction.)

Say it in 60 seconds

"Connect moves data in and out of Kafka with configuration: workers run connector tasks, converters handle formats, and state lives in three compacted topics. Debezium is a set of source connectors that read the database's commit log, which is the clean fix for dual writes when combined with the outbox pattern. For processing, Kafka Streams is a library inside my service with local RocksDB state backed by changelog topics and exactly-once inside Kafka; Flink is a separate cluster for big stateful, event-time pipelines with checkpoints. Sinks are at-least-once, so I always make them idempotent."
