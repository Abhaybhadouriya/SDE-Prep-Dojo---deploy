Apache Flink: the big separate workshop

Flink is a distributed processing engine with its own cluster. A JobManager plans and coordinates jobs; many TaskManagers run the operators in parallel slots. Flink reads from Kafka with its Kafka connector, but it can equally read files, databases (via Flink CDC) or other queues. Netflix's Keystone platform is a well-known example: Kafka in front, Flink offered as "stream processing as a service" to internal teams (InfoQ summary in resources).

Checkpoints: how Flink keeps exactly-once state

Every few seconds the JobManager injects a special barrier into every source. Barriers flow through the job with the data. When an operator has received the barrier on all its inputs, it snapshots its state to durable storage and passes the barrier on. When every operator has done so, the checkpoint is complete: it contains the Kafka offsets of the sources and all state as of the same logical moment. After a crash, Flink restores the last checkpoint and rewinds the Kafka sources to those offsets. This is based on the Chandy-Lamport snapshot algorithm.

From your world

Checkpoint barriers are like a marker packet injected into every ingress queue of a pipeline for a consistent counter snapshot: each stage dumps its counters when the marker passes, so the totals across stages refer to the same instant even though stages run at different speeds. The Kafka sink's two-phase commit is like a make-before-break commit: stage the new state, then flip it atomically once everyone agrees.

Flink SQL on a Kafka topic

Much of Flink's recent momentum is Flink SQL: you declare a Kafka topic as a table, including its event-time column and watermark, and write streaming SQL.

CREATE TABLE orders (
  order_id STRING,
  city     STRING,
  amount   DOUBLE,
  ts       TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '5' SECOND      -- allow 5 s of lateness
) WITH (
  'connector' = 'kafka',
  'topic' = 'orders',
  'properties.bootstrap.servers' = 'kafka:9092',
  'properties.group.id' = 'flink-order-stats',
  'scan.startup.mode' = 'earliest-offset',
  'format' = 'json'
);

-- Orders and revenue per city per minute (tumbling window on event time)
SELECT window_start, city, COUNT(*) AS orders, SUM(amount) AS revenue
FROM TABLE(TUMBLE(TABLE orders, DESCRIPTOR(ts), INTERVAL '1' MINUTE))
GROUP BY window_start, window_end, city;

The same query in ksqlDB would be a CREATE TABLE ... AS SELECT ... WINDOW TUMBLING (SIZE 1 MINUTE). ksqlDB is handy when your team already runs Confluent Platform; otherwise Flink SQL is the more common choice for new projects, and there is no ksqlDB under the Apache licence.
