Kafka Streams inside: tasks, state stores, changelogs

Kafka Streams is "just a library". You add a JAR to your Spring Boot or plain Java service, describe a topology (a graph of steps), and start it. There is no Streams cluster to run. To scale, you start more copies of your service with the same application.id; they form a group and split the work, the same way consumers in a group split partitions. That makes it ideal for "processing inside a microservice".

Properties p = new Properties();
p.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-stats");         // group id + prefix of internal topics
p.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
p.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
p.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);
p.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

StreamsBuilder b = new StreamsBuilder();
KStream<String, String> orders = b.stream("orders");             // key = orderId, value = city

orders
  .filter((orderId, city) -> city != null)
  .groupBy((orderId, city) -> city)                                // re-key by city -> repartition topic
  .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(1), Duration.ofSeconds(30)))
  .count(Materialized.as("orders-per-city"))                        // RocksDB store + changelog topic
  .toStream()
  .map((win, count) -> KeyValue.pair(win.key() + "@" + win.window().startTime(), count.toString()))
  .to("orders.stats");

KafkaStreams app = new KafkaStreams(b.build(), p);
Runtime.getRuntime().addShutdownHook(new Thread(app::close));
app.start();
// Enrich every payment with the latest customer record (a KTable from a compacted topic)
KTable<String, Customer> customers = b.table("customers");          // key = customerId
KStream<String, Payment> payments = b.stream("payments");          // key MUST be customerId too

payments
  .join(customers, (pay, cust) -> new EnrichedPayment(pay, cust.tier(), cust.country()))
  .to("payments.enriched");
// Both topics must be co-partitioned: same key and the same number of partitions,
// otherwise Streams refuses to start (or you must repartition first).

What the library builds for you

  • Task: the unit of parallelism, one per input partition (per sub-topology). With 4 partitions, at most 4 tasks do useful work, so a fifth instance would sit idle. Partition count caps your parallelism, just like with plain consumers.
  • State store: by default RocksDB on local disk (or in-memory). Fast local reads and writes.
  • Changelog topic <application.id>-<store>-changelog: compacted, receives every store update. This is the store's backup.
  • Repartition topic: created when you change the key (groupBy, selectKey before an aggregation or join). Records are written out and read back so that all records with the new key land in the same task. This costs a network round trip and storage; avoid needless re-keying.
  • Standby replicas (num.standby.replicas=1): another instance keeps a warm copy of a store by reading its changelog, so failover does not wait for a full restore.
  • Exactly-once (processing.guarantee=exactly_once_v2): reading input, updating the store's changelog, writing output and committing offsets all happen in one Kafka transaction. See delivery semantics. It is exactly-once inside Kafka; a side effect like calling an email API is still at-least-once.

What happens when an instance dies

  1. Normal. Each instance owns two tasks, keeps their stores in RocksDB and streams every update to the changelog.
  2. Failure. Instance B's pod is killed. After the session timeout (or immediately on a clean shutdown) the group notices.
  3. Rebalance. The group coordinator moves tasks 0_2 and 0_3 to instance A. With the new Streams rebalance protocol (KIP-1071, GA in Kafka 4.2, group.protocol=streams) the broker drives this assignment.
  4. Restore. Instance A rebuilds the two missing stores by reading their changelog partitions from the start (compaction keeps this bounded). Processing for those tasks waits until the restore is done.
  5. Lesson. Big state means slow failover. Use standby replicas, keep stores small (windows with retention), and on Kubernetes use a StatefulSet with persistent volumes so a restarted pod finds its RocksDB files and replays only the tail.

Your question answered: "How do I replay data if I find a bug in my consumer?" For a plain consumer group: stop it, then kafka-consumer-groups.sh --reset-offsets --to-datetime ... --execute, fix the bug, restart. For a Streams app, local state and internal topics also need resetting: use kafka-streams-application-reset.sh --application-id order-stats --input-topics orders --bootstrap-server kafka:9092, delete local state (KafkaStreams#cleanUp()), then restart. Make the output idempotent (upserts) so re-processed results overwrite old ones. Replay only works if input retention still covers the period, which is a good reason for longer retention or tiered storage.
