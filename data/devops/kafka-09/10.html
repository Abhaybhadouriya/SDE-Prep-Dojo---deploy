Where does a Kafka Streams application run?

  1. Inside the Kafka brokers
  2. Inside your own application process, as a library
  3. On a separate Streams cluster with a JobManager
  4. Inside the Connect workers
Kafka Streams is a Java library. You scale it by running more instances of your app with the same application.id.

A Connect sink task crashes after writing to Elasticsearch but before committing offsets. What happens after restart?

  1. The records are lost
  2. Connect detects the write and skips them
  3. The same records are written again, so the sink should upsert by key
  4. The connector stays FAILED forever
Sinks are at-least-once. Idempotent writes (document id = record key) make the duplicate harmless.

What does the outbox pattern guarantee?

  1. The business change and the event record are committed atomically in one DB transaction
  2. Consumers receive each event exactly once
  3. Kafka and Postgres share one distributed transaction
  4. The outbox table never needs cleaning
Only the local commit is atomic. The relay is at-least-once, so consumers still deduplicate.

A Debezium Postgres connector has been stopped for a week. What is the main danger?

  1. Kafka deletes the topic
  2. Debezium loses its snapshot
  3. The tables get locked
  4. Postgres keeps WAL for the replication slot and the disk can fill up
A logical replication slot pins WAL until the consumer confirms it. Monitor slot lag and drop unused slots.

"Count clicks per user session that ends after 30 minutes of inactivity" needs which window?

  1. Tumbling
  2. Session
  3. Hopping
  4. No window
Session windows close after a gap of inactivity, so each user gets windows of different lengths.

Your input topic has 6 partitions. You run 10 instances of a Kafka Streams app (1 thread each). How many do useful work on that sub-topology?

  1. 10
  2. 1
  3. 6
  4. 3
One task per input partition, so at most 6 instances have work; the others are idle (they can still host standby replicas).

How does a Flink job recover state after a TaskManager crash?

  1. It restores the last completed checkpoint and rewinds Kafka sources to the offsets stored in it
  2. It replays the changelog topics of each operator
  3. It reads all Kafka topics from the earliest offset
  4. It cannot; state is lost
Checkpoints store source offsets and operator state for the same logical instant, taken by barriers flowing through the job.

Which of these is the best fit for an SMT?

  1. Joining orders with customers
  2. Counting orders per minute
  3. Calling a fraud API per record
  4. Dropping a sensitive field before records reach the sink
SMTs are for light, stateless per-record edits. Joins, aggregations and remote calls belong in a stream processor or service.
