What is a stream processor, and what is "state"?

A stream processor is a program that runs forever, reading records as they arrive and producing results continuously. A normal consumer that reads a record and writes to a database is already a tiny stream processor. Frameworks like Kafka Streams and Flink add the hard parts for you: keeping state safely, handling time, scaling out, and recovering after crashes.

  • Stateless operations look at one record at a time: filter out test orders, convert currency, mask a card number. Any instance can handle any record.
  • Stateful operations need memory of the past: "count orders per city per minute", "join each payment to its order", "alert if one card is used in 3 cities within 10 minutes". That memory is the state.

Where is the state stored? Not in an external database on every record; that would be far too slow. It is kept locally next to the processing (in memory, or in an embedded key-value store such as RocksDB on local disk), and it is backed up somewhere durable so a new instance can rebuild it: Kafka Streams writes every state change to a compacted changelog topic; Flink takes periodic checkpoints to S3, HDFS or similar.

Streams and tables are two views of the same thing

This idea unlocks everything else. A stream is the list of events: "Asha's balance became 10", "Ravi's became 5", "Asha's became 25". A table is the latest value per key: Asha = 25, Ravi = 5. If you replay the stream from the start, you rebuild the table. If you record every change to a table, you get the stream. Kafka Streams calls them KStream and KTable: a KStream treats every record as a new, independent event (two payments by Asha are two payments), while a KTable treats each record as an update to the value for its key (a new "Asha's balance" replaces the old one, and a record with a null value deletes the key).

From your world

You already live this duality. A routing table (RIB) is the table; the stream of BGP UPDATE and WITHDRAW messages is the stream. A new peer rebuilds the full table by receiving the stream from the start. A withdraw is a tombstone.

Windows, explained with a clock

"Count orders per minute" needs a rule for which events belong to which minute. That rule is a window. Picture a wall clock:

  • Tumbling: back-to-back boxes that never overlap. 10:00-10:01, 10:01-10:02. Every event is in exactly one box. "Orders per minute."
  • Hopping: fixed-size boxes that start every few seconds and overlap. A 5-minute box every 1 minute. Each event is in up to 5 boxes. "Moving 5-minute average, updated every minute."
  • Sliding: a box defined by how close two events are in time. "Two logins within 30 seconds of each other." Kafka Streams has a dedicated sliding window for aggregations.
  • Session: a box that stays open while the user is active and closes after a gap of inactivity (say 30 minutes). Different users get different-length boxes. "One browsing session."

Event time vs processing time: when is a window "done"?

A phone on a train records a click at 10:00:58, loses signal, and sends it at 10:03:10. Which minute does it belong to? Event time is when it happened (10:00); processing time is when the processor saw it (10:03). Almost every business question wants event time. But then the processor can never be 100% sure that a minute is finished, because a late event might still arrive.

Systems solve this with a promise about lateness. Flink uses a watermark: a marker that flows with the data and says "I believe no events older than T will arrive now", typically "the largest event time seen minus 5 seconds". When the watermark passes 10:01, the 10:00 window fires. Kafka Streams uses a grace period per window: keep accepting late records for, say, 2 minutes after the window end, then close it for good. Anything later than that is dropped (and counted in a metric), or routed to a side output in Flink.

From your world

A watermark is very like a TCP reassembly timeout or a jitter buffer in voice: you hold the window open a little while to collect late or reordered segments, then you commit to an answer. A larger buffer means more correct but more delayed results. Same trade-off.
