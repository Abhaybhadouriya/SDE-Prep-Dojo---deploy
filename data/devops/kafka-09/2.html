CDC with Debezium, and the outbox pattern

Where should data enter Kafka? There are three common doors:

  • The app produces directly. The service calls producer.send(). Simple, but see the "dual write" trap below.
  • A log shipper (Fluent Bit, Vector, Filebeat) tails log files and sends lines to Kafka. Good for logs and metrics.
  • CDC from the database. A connector reads the database's own transaction log and publishes every committed change. Good whenever the database is the source of truth.

The dual-write problem, in simple words

An order service must do two things: save the order in Postgres, and tell the world with an OrderPlaced event on Kafka. Those are two different systems. There is no single "commit" that covers both. Whatever order you do them in, a crash in the middle leaves them disagreeing. Step through it:

  1. Write 1 succeeds. The service inserts the order and the database commits.
  2. Crash before write 2. The process dies (deploy, OOM, network blip) before it publishes. The order exists, but no one downstream ever hears about it. Payment never starts.
  3. Swap the order? Still broken. Publish first, then commit: now the event is out, but the database transaction can still fail or roll back. Consumers act on an order that does not exist.
  4. Outbox fix. In the same database transaction, insert the order row and a row into an outbox table that describes the event. One commit, so both exist or neither does.
  5. Relay. Debezium reads the committed outbox rows from the write-ahead log and publishes them to Kafka. If it crashes, it resumes from its stored log position.
  6. Result. The database and the event stream can no longer disagree. The relay may publish an event twice after a crash, so consumers must still be idempotent (dedupe by event id).

Explain like I'm 5

The outbox is like writing in your diary "I broke the vase" and, at the very same moment, putting a sticky note on the same page that says "tell Mom". You cannot do one without the other, because it is the same page. Later a helper reads the sticky notes and tells Mom. Even if you fall asleep, the note is still there.

How Debezium reads the database

Every serious database already writes a log of every change, so it can recover after a crash and feed replicas: MySQL has the binlog, Postgres has the WAL (write-ahead log), MongoDB has change streams, SQL Server has CDC tables. Debezium connects as if it were a replica and reads that log. For Postgres it uses a logical replication slot with the built-in pgoutput plug-in. On first start it takes a snapshot of the existing rows, then switches to streaming new changes.

Because it reads the log, Debezium sees committed changes in commit order, it adds almost no load on the tables, and nobody has to change the application. That is why CDC is the favourite answer to "how do I get the data from my service's DB into search, cache and the lake".

{
  "name": "shop-pg-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/opt/secrets/pg.properties:password}",
    "database.dbname": "shop",
    "topic.prefix": "shop",
    "plugin.name": "pgoutput",
    "slot.name": "debezium_shop",
    "table.include.list": "public.orders,public.customers",
    "tasks.max": "1"
  }
}

Records for table public.orders land in topic shop.public.orders (prefix, schema, table), keyed by the primary key. Keying by primary key means all changes to one row go to one partition, so they stay in order. Each change event looks like this (simplified):

{
  "before": { "id": 42, "status": "PLACED", "amount": 499 },
  "after":  { "id": 42, "status": "PAID",   "amount": 499 },
  "op": "u",
  "ts_ms": 1795400000000,
  "source": { "db": "shop", "table": "orders", "lsn": 23983712, "txId": 771 }
}

op is c (create), u (update), d (delete) or r (read during the snapshot). A delete is followed by a tombstone (same key, null value), so a compacted topic eventually forgets the row, exactly like a table.

Outbox with Debezium's Event Router

Streaming raw table changes leaks your internal table design to every consumer. If you rename a column, everyone breaks. The outbox pattern fixes this too: the outbox row is a deliberate public event. Debezium ships a transform for it:

-- Same transaction as the business write
BEGIN;
INSERT INTO orders (id, customer_id, amount, status) VALUES (42, 7, 499, 'PLACED');
INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)
VALUES (gen_random_uuid(), 'order', '42', 'OrderPlaced',
        '{"orderId":42,"customerId":7,"amount":499}');
COMMIT;
"table.include.list": "public.outbox",
"transforms": "outbox",
"transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
"transforms.outbox.route.by.field": "aggregatetype",
"transforms.outbox.table.field.event.key": "aggregateid"

The router reads each outbox row, picks the topic from aggregatetype (by default the topic becomes outbox.event.order), uses aggregateid as the key so all events of order 42 stay ordered, and sends only the payload as the value. You can delete outbox rows after they are captured; the WAL already has them.

From your world

Debezium is like a SPAN / mirror port on the database's journal. The database keeps forwarding as usual; a copy of every committed change flows out to an analyzer without the main path noticing. Or, closer to routing: it is a BGP Monitoring Protocol (BMP) feed of the RIB. You do not poll the table, you get every update as it is committed.

Where the analogy breaks: a mirror port drops copies when it is congested. A replication slot never drops: Postgres keeps WAL until Debezium confirms it. If the connector stops for days, WAL piles up and can fill the database disk. Monitor slot lag.

When an interviewer draws "service writes to DB, then publishes to Kafka", say: "That is a dual write; a crash between them loses or invents events. I would use the transactional outbox with CDC (Debezium) as the relay, and make consumers idempotent because the relay is at-least-once." This one sentence comes up in almost every order, payment and booking design at Amazon, Flipkart and Swiggy style rounds.
