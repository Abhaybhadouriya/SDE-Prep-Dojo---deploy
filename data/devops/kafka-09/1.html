Kafka Connect: moving data with config, not code

Imagine you need to copy every new row of a customers table into Kafka, and every record of a Kafka topic into Elasticsearch. You could write two small programs with a producer and a consumer. But then you must also handle retries, offsets, restarts, scaling, schema conversion and monitoring yourself. And every team in the company would write their own slightly broken version.

Kafka Connect solves this once. You run a few worker processes, and you give them a JSON config that says "use the Elasticsearch sink connector, read topic orders, write to this URL". The worker does the rest. Cloudflare, for example, describes building shared connectors and a common library so that each team does not misuse Kafka on its own (see their post in the resources).

The five words you need

  1. Worker A JVM process that runs Connect. Several workers with the same group.id form a Connect cluster and share the work.
  2. Connector A plug-in plus its config, for example "Debezium Postgres connector for the shop database". It knows how to talk to one outside system. A source connector reads from outside and writes to Kafka. A sink connector reads from Kafka and writes outside.
  3. Task The unit of real work. A connector splits its job into up to tasks.max tasks, and the workers run tasks in threads. A sink connector reading a 12-partition topic can run up to 12 useful tasks.
  4. Converter Turns Connect's internal record format into bytes and back (JSON, Avro, Protobuf, plain string). Set by key.converter and value.converter. This is where Schema Registry plugs in.
  5. SMT (single message transform) A small per-record change on the way through: rename a field, drop a field, add a timestamp, route to a different topic. Fine for light edits; anything bigger belongs in a stream processor.

Connect runs in two modes. Standalone mode is one process with its offsets in a local file, good for a laptop demo. Distributed mode is what you use in production: many workers, one REST API on each (port 8083 by default), and all state stored in Kafka topics. Because state lives in Kafka, you can kill any worker and the others pick up its tasks. This is the same group-membership idea as a consumer group.

A real distributed worker config

# config/connect-distributed.properties (the important lines)
bootstrap.servers=kafka-1:9092,kafka-2:9092,kafka-3:9092
# workers with the same id form one cluster
group.id=connect-shop
# connector configs (compacted)
config.storage.topic=connect-configs
# where source connectors keep their position
offset.storage.topic=connect-offsets
# RUNNING / FAILED per connector and task
status.storage.topic=connect-status
config.storage.replication.factor=3
offset.storage.replication.factor=3
status.storage.replication.factor=3
key.converter=org.apache.kafka.connect.json.JsonConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
# folder with connector JARs (Debezium, ES, S3...)
plugin.path=/opt/connectors
# lets connector configs reference secrets in files, e.g. ${file:/opt/secrets/pg.properties:password}
config.providers=file
config.providers.file.class=org.apache.kafka.common.config.provider.FileConfigProvider

Why the comments sit on their own lines: in a .properties file, # only starts a comment at the beginning of a line. An inline group.id=connect-shop # ... would make the comment part of the group id.

The three internal topics are compacted (see storage internals), because only the latest config, offset and status per key matter. This is a nice real example of why compaction exists.

Creating and checking a connector through the REST API

You never "deploy code" to Connect. You PUT JSON. Here is a sink that writes topic orders into Elasticsearch, with bad records sent to a dead-letter topic instead of killing the task:

curl -s -X PUT localhost:8083/connectors/orders-to-es/config \
  -H 'Content-Type: application/json' -d '{
    "connector.class": "io.confluent.connect.elasticsearch.ElasticsearchSinkConnector",
    "topics": "orders",
    "connection.url": "http://elasticsearch:9200",
    "tasks.max": "3",
    "key.ignore": "false",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "orders.dlq",
    "errors.deadletterqueue.context.headers.enable": "true",
    "errors.deadletterqueue.topic.replication.factor": "3"
  }'
$ curl -s localhost:8083/connectors/orders-to-es/status | jq .
{
  "name": "orders-to-es",
  "connector": { "state": "RUNNING", "worker_id": "10.0.1.7:8083" },
  "tasks": [
    { "id": 0, "state": "RUNNING", "worker_id": "10.0.1.7:8083" },
    { "id": 1, "state": "RUNNING", "worker_id": "10.0.1.8:8083" },
    { "id": 2, "state": "RUNNING", "worker_id": "10.0.1.7:8083" }
  ],
  "type": "sink"
}
$ curl -s -X POST 'localhost:8083/connectors/orders-to-es/restart?includeTasks=true&onlyFailed=true'

The errors.* lines matter in real life. The default errors.tolerance=none means one record that cannot be converted stops the task (state FAILED) and the whole sink stalls. With all, bad records go to orders.dlq with headers that explain the error, and the rest keep flowing. Note that the dead-letter queue setting exists for sink connectors. The pipeline DLQ page shows how to re-drive those records later.

Sink delivery is at-least-once. A sink task commits its consumer offsets after it writes to the target. If it crashes in between, the same records are written again after restart. So design sinks to be idempotent: upsert by primary key (Elasticsearch document id = record key, JDBC sink in upsert mode). This also answers the pipeline question "how do I avoid duplicates at the sink?"
