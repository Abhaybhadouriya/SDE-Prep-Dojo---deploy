When state goes wrong: recovery playbook

Good to know (SDE-2)
SituationWhat you seeFix
Stale lock after a crashed CI jobError acquiring the state lock, holder is a dead jobConfirm the job is gone; terraform force-unlock <ID>
Bad state write (wrong surgery)Plan wants to recreate things that existRestore the previous S3 object version (below)
Resource created by handPlan wants to create it; apply fails "already exists"import block, then plan shows no changes
Resource deleted by handRefresh finds it gone; plan recreates itLet it recreate, or remove the block if it should stay gone
State lost completelyPlan wants to create everythingRestore from versions; worst case, import every resource back
Apply failed halfwaySome resources created, error on oneNothing special: state recorded the successes. Fix the error, apply again

Rb1cPfwK7d4vWl0aE2H2nF.Lb9mXk1dQ  2026-11-22T17:10:44Z
$ aws s3api get-object --bucket dojo-tfstate-123456789012-ap-south-1 \
    --key network/prod/terraform.tfstate --version-id Rb1cPfwK7d4vWl0aE2H2nF.Lb9mXk1dQ good.tfstate
$ terraform state push good.tfstate
$ # refused if good.tfstate has a lower serial than the current state (it does: it is older).
$ # Edit "serial" in good.tfstate to above the current one and push again, or use -force only if you are sure.
$ terraform plan        # expect: No changes

state push refuses a state with a different lineage or a lower serial: those are the safety checks that stop you from writing an old or unrelated notebook over the current one.
