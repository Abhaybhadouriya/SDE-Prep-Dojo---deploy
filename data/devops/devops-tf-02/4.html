The S3 backend with locking

Must know (SDE-1)

Here is a production-shaped backend block:

terraform {
  required_version = ">= 1.11"

  backend "s3" {
    bucket       = "dojo-tfstate-123456789012-ap-south-1"
    key          = "network/prod/terraform.tfstate"   # one key per stack + environment
    region       = "ap-south-1"
    encrypt      = true                                # server-side encryption of state + lock
    kms_key_id   = "arn:aws:kms:ap-south-1:123456789012:key/EXAMPLE-KEY-ID"
    use_lockfile = true                                # S3-native locking (1.11+)
  }
}

Backend blocks cannot use variables (they are read before anything else). For "same code, different environment", leave values out and pass them at init: terraform init -backend-config=backend/prod.hcl. This is called partial configuration.

Why locking: two applies at once

Without a lock, Alice and the CI pipeline can both read serial 7, both make changes, and both write serial 8. The second write silently overwrites the first, and state no longer matches reality. A lock turns this into a clean error for the second runner.

Use -lock-timeout=5m in CI to wait instead of failing at once. If a run crashed and left a stale lock, confirm nobody is running, then terraform force-unlock 6b1c2f0e-4d7a-.... Never use -lock=false on shared state.

S3-native lock vs the classic DynamoDB lock

Configdynamodb_table = "tf-locks"use_lockfile = true
MechanismConditional PutItem on a table whose partition key is the string LockID; fails if the item existsConditional PutObject of <key>.tflock; fails if the object exists

Many existing companies still run the S3 + DynamoDB pattern, so you must know both. To migrate, set both arguments and run terraform init -reconfigure (Terraform then takes both locks); once every user and pipeline is on 1.11+, remove dynamodb_table.

From your world

Both are a compare-and-swap on a remote key. The S3 version is literally open(path, O_CREAT | O_EXCL) as a lock file, the oldest trick in Unix (think /var/run/*.pid or /var/lock/LCK..ttyS0), except the filesystem is S3 and the atomicity comes from S3's conditional writes. And like a lock file after kill -9, a crashed run leaves a stale lock that someone must remove by hand (force-unlock). There is no lease or TTL: this is not a lease-based distributed lock, so it relies on humans checking that the holder is really dead.

Bootstrapping: the bucket that holds the state of the bucket

Chicken and egg: the state bucket must exist before any config can use it. The usual answer is a tiny bootstrap config, applied once with local state, that creates the bucket (and the KMS key). Then you add a backend block to it and run terraform init -migrate-state, which copies the local state into S3.

resource "aws_s3_bucket" "tfstate" {
  bucket = "dojo-tfstate-123456789012-ap-south-1"
  lifecycle { prevent_destroy = true }          # a destroy plan errors out
}

resource "aws_s3_bucket_versioning" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  versioning_configuration { status = "Enabled" }   # every state write kept
}

resource "aws_s3_bucket_server_side_encryption_configuration" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.tfstate.arn
    }
    bucket_key_enabled = true
  }
}

resource "aws_s3_bucket_public_access_block" "tfstate" {
  bucket                  = aws_s3_bucket.tfstate.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

Key layout. One state file per stack per environment (network/prod/terraform.tfstate, network/dev/..., app-payments/prod/...). Smaller states mean faster plans, smaller blast radius, and fewer people blocked by one lock. AWS's guidance goes further: separate buckets (ideally separate AWS accounts) per environment, so dev credentials simply cannot read prod state. If you use workspaces with the S3 backend, non-default workspaces are stored under env:/<workspace>/<key>.
