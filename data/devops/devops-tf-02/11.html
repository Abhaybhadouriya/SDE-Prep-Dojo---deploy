Quick quiz

What is the most important thing the state file records?

  1. The Terraform source code
  2. The mapping from each resource address to the real object's ID
  3. The AWS credentials
That binding is how Terraform knows which real objects it manages.

Two engineers run terraform apply on the same stack at the same time with a remote backend and no locking. What is the risk?

  1. Terraform merges both plans automatically
  2. AWS rejects the second set of API calls
  3. The last writer overwrites the state, so some real resources are no longer tracked
Without a lock both read the same serial; the later write wins silently.

With use_lockfile = true, where is the lock?

  1. An object named <key>.tflock next to the state in the same bucket
  2. A DynamoDB table
  3. A local file in .terraform/
S3-native locking creates the .tflock object with a conditional write.

You mark a variable sensitive = true and pass it as a DB password. Where can the password still be read?

  1. Nowhere
  2. Only in the plan output
  3. Only in CloudTrail
  4. In the state file and in saved plan files
sensitive redacts display only. Use managed secrets or write-only arguments to keep it out.

You renamed aws_instance.web to aws_instance.app. What avoids a destroy and recreate, reviewed in a PR?

  1. terraform state rm
  2. A moved block
  3. -refresh=false
  4. depends_on
moved tells Terraform the address changed; plan shows 0 to add, 0 to destroy.

Why enable versioning on the state bucket?

  1. It is required for locking
  2. It encrypts the state
  3. Every state write is kept, so a bad write or deletion can be rolled back
Versioning is the undo button for state. (Locking and encryption are separate settings.)

What does terraform state rm aws_s3_bucket.logs do to the real bucket?

  1. Nothing: Terraform just forgets it
  2. Deletes the bucket
  3. Empties the bucket
State commands change only state. The bucket keeps existing, now unmanaged.
