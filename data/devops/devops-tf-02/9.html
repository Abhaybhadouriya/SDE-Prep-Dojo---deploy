Interview questions

What is the Terraform state file and why does Terraform need it?

It is a JSON record that maps every resource address in the config (aws_vpc.main) to the real object's ID (vpc-0a1b2c3d) and caches its attributes. Terraform needs it to know which real objects it owns, to compute diffs, to remember dependencies for deleting resources that are no longer in config, and to speed up large plans. Without it, Terraform cannot tell its objects from anyone else's.

How to answer

Lead with "mapping config to real-world IDs", then name the other three purposes (metadata/dependencies, performance, team sync). Finish with what happens if it is lost.

Likely follow-ups
  • What are serial and lineage?
  • Why not just query the cloud by tags every time?
How would you set up Terraform state for a team on AWS?

An S3 backend: a dedicated bucket per environment (ideally per AWS account), versioning on, SSE-KMS with a customer-managed key, Block Public Access, a bucket policy denying non-TLS, and locking via use_lockfile = true (or a DynamoDB table with a LockID key on older Terraform). One state key per stack per environment. Write access to prod state only for the CI role assumed via OIDC; humans read-only. CloudTrail data events on the bucket. The bucket itself is created by a small bootstrap config and protected with prevent_destroy.

How to answer

Structure as storage, locking, security, layout. Mention the DynamoDB deprecation to show you are current.

Likely follow-ups
  • How do you bootstrap the bucket?
  • HCP Terraform vs self-managed S3?
  • How do other stacks read this stack's outputs?
How does state locking work with S3 and DynamoDB, and what happens without it?

Before any write operation Terraform takes a lock. With DynamoDB it does a conditional PutItem of an item keyed by LockID that fails if one exists. With S3-native locking it creates <key>.tflock with a conditional write that fails if the object exists (HTTP 412). Either way, it is an atomic compare-and-swap, so exactly one run wins; the loser gets "Error acquiring the state lock" with the holder's name. Without a lock, two runs read the same serial, both apply, and the last writer silently overwrites the other's state, leaving resources that exist but are not tracked.

How to answer

Explain it as CAS, give the race without it, then mention stale locks and force-unlock.

Likely follow-ups
  • Is there a lock timeout or lease? (No TTL; use -lock-timeout to wait, force-unlock to clear.)
  • How do you migrate from DynamoDB to S3 locking safely?
Does sensitive = true protect secrets in state? How do you really protect them?

No. It only redacts values in CLI and UI output; the value is still stored in plain text in state and in saved plan files. Real protection: first keep secrets out of state (let RDS manage the password in Secrets Manager, use ephemeral values and write-only _wo arguments from Terraform 1.11, or have the app read secrets at runtime). Then protect the backend: SSE-KMS with a restricted key policy, least-privilege IAM, TLS-only bucket policy, Block Public Access, CloudTrail data events, and treat plan artifacts like state.

How to answer

Correct the misconception in the first sentence, then "remove, then protect" as two layers.

Likely follow-ups
  • What does terraform output -raw show for a sensitive output? (The plain value.)
  • Old object versions still hold old secrets. What do you do?
You renamed a resource in code and plan wants to destroy and recreate it. Fix it.

The address changed, so Terraform sees the old address as gone (destroy) and the new one as new (create). Add a moved { from = aws_instance.web to = aws_instance.app } block; plan then shows "has moved to" and 0 to add / destroy. The older way is terraform state mv, but a block is reviewed in the PR and applies to every environment's state, not just the one you ran it on.

How to answer

Name the cause (addresses are identity), give the block, explain why the block beats the CLI.

Likely follow-ups
  • Moving resources into a module?
  • Moving resources between two different state files? (removed + import, or state mv with -state-out.)
A team created resources by hand during an incident. How do you bring them under Terraform?

Write import blocks with the target address and the real ID, run terraform plan -generate-config-out=generated.tf to get starting resource blocks, clean them up (references instead of hard-coded IDs), and iterate until plan shows "N to import, 0 to add, 0 to change, 0 to destroy". Merge via PR so apply records them in state. For things that should stay gone, delete them by hand instead.

How to answer

Give the four steps and stress the success condition: an import plan with zero changes.

Likely follow-ups
  • How do you stop this happening again? (Read-only console for Terraform-owned accounts, drift detection in CI.)
The state file was overwritten with a bad version. Walk me through recovery.

Stop all applies (hold the lock or pause the pipeline). List object versions of the state key in S3, download the last good one, and compare it with the current one (terraform show on each, or a JSON diff). Push it with terraform state push; it refuses a lower serial or a different lineage, so set the serial above the current one deliberately (or use -force once you are sure). Run plan: expect "No changes" or only the drift you understand. Then find why it happened (CloudTrail on the bucket shows who wrote it) and add a guardrail.

How to answer

Freeze, restore from versioning, verify with plan, root-cause with CloudTrail. Versioning is the hero; say so.

Likely follow-ups
  • What if versioning was off? (Rebuild by importing every resource.)
Why split state into many small files instead of one big one?

Blast radius (a bad apply to the app stack cannot touch the network stack), speed (plan refreshes only what is in this state), concurrency (each state has its own lock, so teams do not queue behind each other), and access control (the payments team can be denied the network state). The cost is wiring between stacks: outputs read via terraform_remote_state or, better, via data sources and SSM parameters, plus an apply order across stacks.

How to answer

Four benefits, one cost, and how you would split (by lifecycle: network, data, app; by environment).

Likely follow-ups
  • Workspaces vs separate folders for environments? (Covered on the Terraform at Scale page.)

Scenario: "the pipeline is stuck on a lock"

Monday morning, every Terraform job for the prod network stack fails with "Error acquiring the state lock". The Lock Info says the holder is a CI job from Friday night.
Weak answer: "Run it with -lock=false so we can deploy."
Strong answer: Check whether Friday's job is really dead (CI history, runner status). If it died mid-apply, run plan after unlocking to see what it left half-done. Only then terraform force-unlock <ID>, run a plan, and expect drift to show what the interrupted apply did. Afterwards: add -lock-timeout, make the CI job release the lock on cancel, and alert when a non-pipeline identity deletes a .tflock object.
Follow-ups: why does Terraform not expire locks automatically? What would happen if two jobs really did apply at once?
