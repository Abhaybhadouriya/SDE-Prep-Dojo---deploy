Secrets in state: the trap everyone falls into

Must know (SDE-1)

State stores every attribute of every resource, because that is its job. If a resource has a password, a private key, or a token as an attribute, that value is in the state file. In plain text, by default.

variable "db_password" {
  type      = string
  sensitive = true          # hides it from CLI output... and that is all
}

resource "aws_db_instance" "orders" {
  identifier        = "orders"
  engine            = "postgres"
  instance_class    = "db.t4g.medium"
  allocated_storage = 50
  username          = "app"
  password          = var.db_password
}
$ terraform plan
  + password = (sensitive value)              <- hidden in plan output

$ terraform state pull | jq -r '.resources[] | select(.type=="aws_db_instance")
    | .instances[0].attributes.password'
S3cr3t-Pa55w0rd!                              <- but sitting in state

sensitive = true is a display filter, not encryption. The Terraform docs say it directly: values marked sensitive are still stored in state and plan files. Saved plan files (tfplan) in CI artifacts leak in the same way.

From your world

It is show running-config printing password 7 ...: the display is masked or obfuscated, but the config file on flash still holds a reversible secret, and anyone who can copy the file has it. Or a core dump of a process that held a TLS key. The fix is the same as in your world: control who can read the file, encrypt it at rest, and best of all, do not put the secret in it.

Layer 1: keep the secret out of state

Many AWS services can generate and store the secret themselves. For RDS, ask it to manage the master password in AWS Secrets Manager. Terraform never sees the password; state only holds the secret's ARN.

resource "aws_db_instance" "orders" {
  identifier                  = "orders"
  engine                      = "postgres"
  instance_class              = "db.t4g.medium"
  allocated_storage           = 50
  username                    = "app"
  manage_master_user_password = true   # RDS creates + rotates it in Secrets Manager
}

output "db_secret_arn" {
  value = aws_db_instance.orders.master_user_secret[0].secret_arn
}

Terraform 1.10 added ephemeral values (variables and ephemeral resources that exist only during a run) and 1.11 added write-only arguments: the provider sends the value to the API but it is never stored in plan or state. By convention they end in _wo, with a _wo_version you bump to rotate.

ephemeral "random_password" "db" {
  length = 24
}

resource "aws_db_instance" "orders" {
  # ...
  username            = "app"
  password_wo         = ephemeral.random_password.db.result
  password_wo_version = 1      # change to 2 to push a new password
}

The app then needs the password from somewhere else, so in practice you also write it into Secrets Manager with a write-only secret_string_wo, or prefer the managed option.

Do not pass secrets through Terraform at all. Terraform creates the empty secret container and the IAM permission; the application reads the value at startup (Secrets Manager / SSM Parameter Store, or a Kubernetes Secret synced by an operator). State then contains an ARN, not a password.

resource "aws_secretsmanager_secret" "stripe_key" {
  name = "prod/payments/stripe-key"
  # the value is put in by a human or a rotation Lambda, never by Terraform
}

Layers 2 to 5: protect the backend

  1. Encrypt. encrypt = true plus a customer-managed kms_key_id. A KMS key gives you a second permission check: reading the object needs both s3:GetObject and kms:Decrypt on that key.
  2. Least privilege. The S3 backend needs only s3:ListBucket on the bucket and s3:GetObject / s3:PutObject on the state key (plus Get/Put/Delete on the .tflock key). Give prod write access only to the CI role; humans get read-only or a break-glass role.
  3. Enforce TLS and block public access. A bucket policy that denies every request where aws:SecureTransport is false, plus S3 Block Public Access.
  4. Version and expire. Versioning is your undo button, but each old version is another copy of old secrets. Keep enough history to recover (for example 90 days of noncurrent versions) via a lifecycle rule.
  5. Audit. Turn on CloudTrail data events for the state bucket (off by default) so every GetObject on state is logged with the caller's identity.

OpenTofu difference. OpenTofu (since 1.7) can encrypt state and plan files on the client before they leave your machine, with keys from AWS KMS, GCP KMS or a passphrase. Terraform relies on the backend's encryption at rest. Worth one sentence in an interview if the team uses OpenTofu.
