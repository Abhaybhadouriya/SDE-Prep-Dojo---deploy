State surgery: list, mv, rm, import and their safer blocks

Must know (SDE-1)

Sometimes the code and the state need to be re-linked without touching the cloud: you renamed a resource, split a config in two, or adopted something built by hand. That is what the state commands do. They change only the state, never the real objects.

$ terraform state list
data.aws_availability_zones.up
aws_internet_gateway.igw
aws_route_table.public
aws_subnet.private[0]
aws_subnet.private[1]
aws_subnet.public[0]
aws_subnet.public[1]
aws_vpc.main

$ terraform state show aws_vpc.main
# aws_vpc.main:
resource "aws_vpc" "main" {
    cidr_block           = "10.20.0.0/16"
    enable_dns_hostnames = true
    id                   = "vpc-0a1b2c3d"
    ...
}

$ terraform state mv aws_internet_gateway.igw aws_internet_gateway.main
Move "aws_internet_gateway.igw" to "aws_internet_gateway.main"
Successfully moved 1 object(s).

$ terraform state rm 'aws_subnet.private[1]'
Removed aws_subnet.private[1]
Successfully removed 1 resource instance(s).

Quote indexed addresses. In zsh, [1] is a glob and the command fails with "no matches found", so write terraform state rm 'aws_subnet.private[1]' (single quotes work in bash and zsh). for_each keys contain double quotes: in bash or zsh use 'aws_subnet.private["ap-south-1a"]'; in PowerShell escape the inner quotes, for example terraform state show 'aws_subnet.private[\"ap-south-1a\"]', or put the address in a variable first.

Rename / move into a moduleterraform state mv A Bmoved { from = A to = B } (1.1+)
Adopt an existing objectterraform import ADDR IDimport { to = ADDR id = "..." } (1.5+)

Prefer the blocks. They go through a pull request, show up in plan, run in CI with the lock held, and work for every environment that uses the code (a state mv on your laptop fixes only the one state you ran it against).

# Adopt a bucket someone created by hand, then let Terraform write the config for you
import {
  to = aws_s3_bucket.legacy_logs
  id = "dojo-legacy-logs"
}

# Rename without destroy + create
moved {
  from = aws_internet_gateway.igw
  to   = aws_internet_gateway.main
}
$ terraform plan -generate-config-out=generated.tf
...
  # aws_s3_bucket.legacy_logs will be imported
  # (config will be generated)
    resource "aws_s3_bucket" "legacy_logs" {
        bucket = "dojo-legacy-logs"
        ...
    }

  # aws_internet_gateway.igw has moved to aws_internet_gateway.main
    resource "aws_internet_gateway" "main" {
        id = "igw-0f00ba12"
        ...
    }

Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.

Before any state surgery: terraform state pull > before.tfstate, make the change, then run terraform plan and expect "No changes" (or exactly what you intended). A plan that suddenly wants to create or destroy things means the surgery went wrong. With a versioned bucket you can also roll back to the previous object version.
