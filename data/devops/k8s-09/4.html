CPU limits and the throttling surprise

Must know (SDE-1)

Here is a story that confuses many teams. A service has a CPU limit of 1 core. Dashboards show average CPU at 40%. Yet p99 latency (the slowest 1% of requests) is terrible. Why?

The CFS bandwidth controller counts CPU time in periods of 100 ms. A limit of 1 core means 100 ms of CPU time per 100 ms period, summed over all threads. A multi-threaded app (a JVM with 8 GC and worker threads, say) can burn through those 100 ms in the first 15 ms of wall time when a burst of requests arrives. Then every thread is frozen for the remaining 85 ms. Averaged over a minute, usage looks low. Per request, latency jumps.

That is why many teams set CPU requests but no CPU limits for latency-sensitive services: the request still guarantees a fair share through cpu.weight, and spare CPU on the node is used instead of wasted. Memory limits stay, because memory overuse hurts neighbours in a way that cannot be undone. This is a judgement call, not a law - multi-tenant clusters often require CPU limits for fairness, so be ready to argue both sides.

New in recent releases: in-place pod resize became GA in v1.35. You can change a running pod's CPU and memory through the resize subresource without restarting it (each resource's resizePolicy says whether a restart is needed). This makes vertical autoscaling far less disruptive.

$ kubectl patch pod api-7c9d5-4xkzq --subresource resize --patch \
    '{"spec":{"containers":[{"name":"api","resources":{"requests":{"cpu":"500m"}}}]}}'
pod/api-7c9d5-4xkzq patched
$ kubectl get pod api-7c9d5-4xkzq -o jsonpath='{.status.containerStatuses[0].resources.requests.cpu}'
500m
