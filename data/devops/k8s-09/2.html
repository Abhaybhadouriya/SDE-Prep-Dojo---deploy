How kube-scheduler picks a node: filter, score, bind

Must know (SDE-1)

kube-scheduler is one process (usually several replicas with one leader) that watches the API server for pods whose spec.nodeName is empty. For each one it runs a pipeline of plug-ins - the scheduling framework. Click through it:

  1. Queue. A controller (for example a ReplicaSet) created a pod with no nodeName. The scheduler's watch sees it and adds it to its scheduling queue, ordered by priority.
  2. Filter. Filter plug-ins run against every node (in big clusters it stops after finding enough feasible nodes). node-1 lacks 1 CPU of unrequested capacity. node-2 has a taint the pod does not tolerate. Other filters check node affinity, free host ports, volume zone, and the volume count limit.
  3. Score. Score plug-ins rate each survivor 0-100: by default it prefers less-allocated nodes, spreading per topology constraints, inter-pod affinity, and nodes that already have the image. Scores are weighted and summed.
  4. Bind. The highest score wins (ties broken at random). The scheduler reserves the resources in its cache and POSTs a Binding to the API server, which sets spec.nodeName: node-4.
  5. Run. The kubelet on node-4 is watching for pods with its own name, sees the new one and starts it. The scheduler is already working on the next pod.

If no node passes the filters, the pod stays Pending and the scheduler writes an event that explains, per filter, how many nodes failed. This message is the most useful thing on this page in real life:

$ kubectl describe pod api-7c9d5-9zt2m | tail -3
Events:
  Warning  FailedScheduling  12s  default-scheduler  0/4 nodes are available: 1 Insufficient cpu, 1 node(s) had untolerated taint {dedicated: gpu}, 2 node(s) didn't match pod topology spread constraints. preemption: 0/4 nodes are available: 4 No preemption victims found for incoming pod.

From your world

Filter-then-score is admission control plus path selection. Think of placing a new flow or a new service on line cards: first discard cards without enough bandwidth or with the wrong capability (filter, like an ACL or a constraint check), then pick the best of the rest by a cost metric (score, like a routing metric). The scheduler then writes the decision into the shared database and leaves the "programming the hardware" to the agent on that card (the kubelet). Where this breaks: the scheduler decides once. It never moves a running pod later, even if a better node appears - that would need a separate tool such as the descheduler.
