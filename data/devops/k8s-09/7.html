Six boxes, two loops: the scheduler places pods by their requests, and the HPA loop changes how many pods there are.

What is the difference between requests and limits? What happens when a container exceeds each?

Requests are what the scheduler reserves: a pod is placed only on a node whose unrequested capacity covers its requests, and the CPU request also becomes the container's cgroup CPU weight. Limits are hard caps enforced by the kernel. Exceeding the CPU limit means the container is throttled by the CFS quota - it slows down but lives. Exceeding the memory limit means the kernel OOM killer sends SIGKILL - the container dies with exit code 137 and shows OOMKilled, and the kubelet restarts it. Together they determine the QoS class, which decides eviction order under node pressure.

How to answer

"Requests are for placement, limits are for enforcement", then the two penalties, then QoS. If you can, mention the cgroup files - it signals real depth.

Likely follow-ups
  • Should you set CPU limits? (Trade-off: throttling vs noisy neighbours.)
  • What is the QoS class if requests equal limits for every container? (Guaranteed.)
A pod is stuck in Pending. List the causes and how you find which one.

kubectl describe pod and read the FailedScheduling event - it counts failures per filter. Typical causes: insufficient CPU or memory requests on every node; a taint the pod does not tolerate; nodeSelector or required affinity that no node matches; topology spread or anti-affinity that cannot be satisfied; a PVC that is unbound or bound to a disk in another zone; the node's volume attach limit; a ResourceQuota (then the pod is not even created - the ReplicaSet shows the error). If it is resources, check whether a node autoscaler exists and why it did not add a node (max size reached, no node group whose shape fits).

How to answer

Start from the one command that shows the reason, then group causes as resources / rules / storage / quota. That structure sounds like experience.

Likely follow-ups
  • The event says "Insufficient cpu" but nodes show 30% CPU usage. Why? (Scheduling is on requests, not usage.)
  • How does preemption change this?
Taints and tolerations vs node affinity - how would you dedicate a pool of GPU nodes to ML jobs?

A taint is set on the node and repels every pod that does not tolerate it. Affinity is set on the pod and attracts it to matching nodes. Neither alone dedicates a pool: a taint keeps others out but does not force the ML pods in; affinity pulls ML pods in but does not keep others out. So: label and taint the GPU nodes (gpu=true:NoSchedule), give ML pods a matching toleration plus required node affinity on the label, and request the GPU resource (for example nvidia.com/gpu: 1), which the device plugin advertises. Use NoExecute if pods already on those nodes must be evicted.

How to answer

Say "repel vs attract" in the first sentence, then show why you need both.

Likely follow-ups
  • What does tolerationSeconds do? (How long a pod stays on a node after a NoExecute taint appears - the 300 s default for not-ready/unreachable nodes.)
How does the HPA work? Walk through the formula and what can make it slow or wrong.

The HPA controller in kube-controller-manager runs every 15 s. It reads the metric from the metrics API, computes desired = ceil(current x currentMetric / target), skips changes within the 10% tolerance, applies behaviour policies and a 5-minute scale-down stabilization window, then updates the target's scale subresource. For CPU, utilization is relative to requests, so missing requests break it. It can be slow because the chain includes metric scrape delay, the 15 s loop, pod scheduling, possibly a new node, image pull and readiness. It can be wrong when the metric does not lead the load - CPU lags behind queue growth, so for consumers use lag, and for web services RPS or concurrency via custom metrics.

How to answer

Give the formula with a small worked example (4 pods at 90% vs 50% target = 8), then the "why it is slow" chain. Numbers make it memorable.

Likely follow-ups
  • Why is scale-down slower than scale-up?
  • HPA vs VPA vs Cluster Autoscaler vs Karpenter?
How would you autoscale Kafka consumers running on Kubernetes?

Scale on consumer-group lag, not CPU, using KEDA's Kafka scaler (or an HPA on an external lag metric from Prometheus). Set maxReplicaCount to the partition count, because extra consumers in a group get no partitions. Every replica change causes a group rebalance, so use cooperative rebalancing or the new consumer protocol, a stabilization window, and avoid scaling on tiny lag changes. If lag keeps growing at max replicas, the fix is upstream: more partitions (which changes key-to-partition mapping for new data), faster processing, or batching sink writes.

How to answer

Name the metric, the cap and the rebalance cost - those three points are what separate a strong answer.

Likely follow-ups
  • Can you scale to zero? (Yes with KEDA; the first message then waits for a cold start.)
  • What lag number is "bad"? (Measure it as time behind, against your latency SLO.)
HPA, VPA, Cluster Autoscaler, Karpenter - when do you use which, and can you combine them?

HPA changes pod count for stateless services whose load splits across replicas. VPA changes pod size, useful for right-sizing and for things that cannot scale out. Cluster Autoscaler adds nodes to predefined node groups when pods are Pending; Karpenter does the same without fixed groups, choosing instance types per batch and consolidating onto cheaper nodes. The common production combo is HPA for pods plus Cluster Autoscaler or Karpenter for nodes, with VPA in recommendation mode to tune requests. Do not run HPA and VPA on the same CPU/memory metric.

How to answer

Draw two layers: pods (HPA, VPA) and nodes (CA, Karpenter). Then "they are triggered by different signals: metrics vs Pending pods".

Likely follow-ups
  • Why does Cluster Autoscaler not look at node CPU usage?
  • How do spot instances fit in?

Scenario: Big Billion Days / Prime Day - 10x traffic at exactly 00:00

Your checkout service runs 20 pods with an HPA on CPU. Last year, at midnight when the sale opened, error rates spiked for several minutes before autoscaling caught up. Plan for this year.

Weak answer: "Lower the HPA CPU target so it scales sooner."

Strong answer: "Reactive scaling is too late for a spike at a known time - the chain of metrics, HPA loop, new nodes, image pulls and warm-up takes minutes. So: (1) pre-scale - raise minReplicas before the event with a scheduled job or KEDA's cron trigger, and pre-warm node pools; (2) keep headroom with low-priority placeholder pods that get preempted instantly when real pods need room, so new pods do not wait for nodes; (3) pre-pull images on nodes; (4) scale on a leading metric like RPS or queue depth rather than CPU; (5) protect dependencies - rate limiting and load shedding at the gateway, and the database and Kafka sized for peak; (6) PDBs and spread across zones; (7) load test at the expected peak beforehand and run failure drills - Flipkart describes running chaos experiments before its sale. After the sale, let the stabilization window scale down gently."

Likely follow-ups
  • How do the placeholder pods work exactly? (A Deployment of pause containers with requests and a negative-priority PriorityClass; real pods preempt them; the evicted placeholders go Pending and trigger the node autoscaler to add buffer again.)
  • What if the database is the bottleneck?

Scenario: low CPU, high latency

A Java service shows 35% average CPU, but p99 latency doubled after the team added a CPU limit of 1 core "for safety".

Weak answer: "Add more replicas."

Strong answer: "This smells like CFS throttling: the limit is a 100 ms budget shared by all threads, and a multi-threaded JVM can exhaust it in a burst. I would confirm with container_cpu_cfs_throttled_periods_total versus total periods, then remove or raise the CPU limit and keep the request, and check the JVM's processor count assumption, which follows the limit."

Likely follow-ups
  • When would you keep CPU limits anyway? (Multi-tenant fairness, cost control, predictable benchmarks.)

60-second answer - "How does Kubernetes scheduling and autoscaling work?"
"kube-scheduler watches for pods without a node. For each it filters out nodes that cannot run it - not enough unrequested CPU or memory, taints, affinity rules, volume zones - then scores the rest and binds the pod to the best one by writing nodeName; the kubelet there starts it. Scheduling uses requests; limits are enforced by the kernel through cgroups, so CPU over limit is throttled and memory over limit is OOMKilled. For scaling, the HPA in the controller manager runs every 15 seconds, computes desired replicas as current times metric over target, and updates the Deployment. If new pods do not fit, they go Pending and the Cluster Autoscaler or Karpenter adds nodes. Because that chain takes minutes, for known spikes I pre-scale and keep headroom, and for Kafka consumers I scale on lag with KEDA, capped at the partition count."
