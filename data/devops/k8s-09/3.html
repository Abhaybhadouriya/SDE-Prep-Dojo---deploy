Steering pods: selectors, affinity, taints, spread

Must know (SDE-1)

You often need to say where pods may or should go: GPU jobs only on GPU nodes, replicas spread over zones, a cache next to its app. There are four tools, and people mix them up constantly.

ToolWho sets itMeaningExample
nodeSelectorPodSimple "must have this label" matchkubernetes.io/arch: arm64
nodeAffinityPodRich rules; required... (hard) or preferred... (soft, weighted)Prefer spot nodes, require zone in [a, b]
podAffinity / podAntiAffinityPodPlace near / away from other pods in a topology (host, zone)Never two Kafka brokers on one host
Taints + tolerationsNode (taint), pod (toleration)Node repels pods; effects NoSchedule, PreferNoSchedule, NoExecute (also evicts running pods)Control-plane nodes: node-role.kubernetes.io/control-plane:NoSchedule
topologySpreadConstraintsPodKeep counts balanced across zones or hosts, within maxSkew6 replicas = 2 per zone

The phrase IgnoredDuringExecution in the affinity field names is honest: rules are checked at scheduling time only. If you relabel a node later, already-running pods stay.

Spreading replicas across zones

For anything user-facing you want replicas in different failure domains. The modern tool is a topology spread constraint:

spec:
  topologySpreadConstraints:
    - maxSkew: 1                                # zones may differ by at most 1 pod
      topologyKey: topology.kubernetes.io/zone  # spread by this node label
      whenUnsatisfiable: DoNotSchedule          # hard rule (ScheduleAnyway = soft)
      labelSelector:
        matchLabels: { app: api }
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            topologyKey: kubernetes.io/hostname   # and try not to share a host
            labelSelector:
              matchLabels: { app: api }

Priority and preemption

A PriorityClass gives pods a number. When a high-priority pod cannot fit anywhere, the scheduler may preempt (evict) lower-priority pods on a node to make room, respecting PodDisruptionBudgets where it can. Clusters ship with system-cluster-critical and system-node-critical for core add-ons like DNS. A clever use, shown later: low-priority "placeholder" pods that hold spare capacity and are pushed out the moment real work arrives.

Real example: Swiggy wrote about moving Kubernetes workloads to AWS Graviton (ARM) nodes with a pipeline that let teams onboard service by service. The generic recipe for any such migration is the toolkit above: build multi-arch images, add a new node pool, and steer pods with the built-in kubernetes.io/arch label, affinity and taints.
