The autoscaling family

Good to know (SDE-2)

"Autoscaling" is really five separate controllers, each answering a different question. Mixing them up is the most common interview slip.

HPA: the control loop and its formula

Every 15 seconds (the default --horizontal-pod-autoscaler-sync-period) the HPA controller inside kube-controller-manager does this for each HPA object:

  1. Read metrics from the metrics APIs: metrics.k8s.io (served by metrics-server, from each kubelet) for CPU and memory, or custom.metrics.k8s.io / external.metrics.k8s.io (served by an adapter such as Prometheus Adapter or KEDA).
  2. Compute desired = ceil(current replicas x current metric / target metric). For CPU the metric is the average across pods, as a percentage of their request.
  3. Apply tolerance: if the ratio is within 10% of 1.0 (default tolerance 0.1, now configurable per HPA), do nothing - this stops flapping.
  4. Apply behaviour rules: scale-down uses a 5-minute stabilization window by default (it picks the highest recommendation of the last 5 minutes), plus any rate policies.
  5. Write the new replica count to the Deployment's scale subresource. The Deployment and ReplicaSet controllers then create pods; the scheduler places them.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }
  behavior:
    scaleUp:
      policies:
        - { type: Percent, value: 100, periodSeconds: 30 }   # at most double every 30 s
    scaleDown:
      stabilizationWindowSeconds: 300                       # the default, written out
      policies:
        - { type: Pods, value: 2, periodSeconds: 60 }        # remove at most 2 pods a minute
$ kubectl get hpa api
NAME   REFERENCE        TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
api    Deployment/api   cpu: 92%/60%    3         30        6          4m

$ kubectl get hpa api      # if the pods have no CPU request
NAME   REFERENCE        TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
api    Deployment/api   cpu: <unknown>/60%   3         30        3          1m

Careful: <unknown> means the HPA cannot compute - usually metrics-server is not installed or the pods have no CPU request (utilization is a percentage of the request, and x / 0 is undefined). Also remove replicas: from the Deployment YAML once an HPA owns it, or every kubectl apply resets the count.

Two recent additions worth knowing: per-HPA configurable tolerance is stable in v1.37, and HPA scale to zero (minReplicas: 0) is beta (on by default) in v1.37. Before that, scale to zero was KEDA's main selling point. Catch: it only works when the HPA scales on an Object or External metric (for example queue depth or Kafka lag). A pod CPU or memory metric cannot wake a Deployment that has zero pods, because with zero pods there is no CPU number to read. KEDA still adds the 0-to-1 activation logic and dozens of event sources.

From your world

The HPA is a discrete-time control loop with a deadband (the 10% tolerance) and asymmetric damping (fast up, slow down via the stabilization window) - the same reasons you add hysteresis to a fan controller or hold-down timers to route flapping. Adding replicas behind a Service is like adding members to an ECMP group when link utilization crosses a threshold. Where this breaks: a new pod is not instant capacity; it needs to be scheduled, pull its image, start and pass readiness, which can take from seconds to minutes.

VPA: right-sizing the pod

VPA watches real usage over time and recommends (or applies) better requests. Modes: Off (recommend only - the safe start), Initial (set at pod creation), Recreate (evict and recreate pods with new values), and InPlaceOrRecreate, which uses the GA in-place resize. Rule: never let HPA and VPA act on the same CPU/memory metric, or they fight: VPA raises the request, utilization percentage drops, HPA removes pods, usage per pod rises, and so on. Combine them only when the HPA scales on a different metric (RPS, lag).

Node autoscaling: Cluster Autoscaler and Karpenter

The HPA can ask for 30 pods, but if the nodes are full those pods are just Pending. The node autoscalers react to exactly that signal - not to node CPU usage.

  1. Steady state. Two nodes, four pods. Each node is "full" in terms of requests, even if real CPU use is lower.
  2. Spike. The HPA raises replicas. Two new pods fit; two more fail the scheduler's resource filter and stay Pending with "Insufficient cpu".
  3. Detect. The node autoscaler watches for unschedulable pods. It simulates: "if I added a node of this type, would these pods fit?" Cluster Autoscaler picks a node group (an AWS Auto Scaling group, Azure VM scale set, GCP managed instance group); Karpenter picks the cheapest instance type that fits the whole batch.
  4. Provision. The cloud boots a VM. It runs the kubelet, registers a Node object and becomes Ready. This is the slow part - typically on the order of a minute or more, depending on cloud, image and node setup (rule of thumb, measure in your cluster).
  5. Schedule. The scheduler places the Pending pods on node-3. They pull images, start and pass readiness. Later, when load falls, the autoscaler removes underused nodes (Cluster Autoscaler: by default when requests are below 50% of the node for about 10 minutes and its pods can move elsewhere).

Add up the chain for a cold spike: metrics lag + 15 s HPA loop + pod Pending + node boot + image pull + app warm-up + readiness. That can be minutes. For a flash sale that starts at a known second, reactive autoscaling alone is too late, which leads to the strongest interview answer on this page (see the scenario below).

What blocks scale-down? From the Cluster Autoscaler FAQ: pods that cannot be moved, such as pods without a controller, pods with local storage (emptyDir) unless marked safe to evict, pods whose PodDisruptionBudget would be violated, and pods annotated cluster-autoscaler.kubernetes.io/safe-to-evict: "false". A single such pod can keep an expensive node alive for weeks.

KEDA: scaling Kafka consumers on lag

CPU is a poor signal for a Kafka consumer: a consumer waiting on a slow database uses little CPU while its backlog grows. The right signal is consumer lag - how many messages are waiting (Consumers & Consumer Groups). KEDA reads lag straight from Kafka and drives an HPA for you:

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-consumer
spec:
  scaleTargetRef:
    name: order-consumer            # a Deployment
  minReplicaCount: 1
  maxReplicaCount: 12               # = partitions of the topic; more would sit idle
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: my-cluster-kafka-bootstrap.kafka:9092
        consumerGroup: order-consumer
        topic: orders
        lagThreshold: "500"         # target lag per replica

Interviewers love this: "I cap consumer replicas at the partition count, because in a consumer group each partition is read by at most one consumer - the 13th consumer of a 12-partition topic would sit idle. And every scale event triggers a rebalance, so I add a stabilization window and use the cooperative rebalance protocol to keep pauses short." This ties K8s scaling to Kafka internals; see the pipeline deploy page for the full setup.
