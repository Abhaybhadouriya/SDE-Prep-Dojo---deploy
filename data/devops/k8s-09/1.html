Requests and limits: the two numbers that drive everything

Must know (SDE-1)

Every container can declare two numbers for CPU and for memory:

  • Request - "I need at least this much." The scheduler uses only requests to decide if a pod fits on a node. It is a reservation.
  • Limit - "Never let me use more than this." The kernel enforces it while the container runs.

CPU is measured in cores or millicores (500m = half a core). Memory is in bytes (256Mi = 256 mebibytes).

containers:
  - name: api
    image: ghcr.io/example/api:1.4.0
    resources:
      requests:
        cpu: 250m        # used by the scheduler, and as the CPU weight
        memory: 256Mi    # used by the scheduler
      limits:
        memory: 512Mi    # over this = OOMKilled
        # no CPU limit on purpose - see "throttling" below

From your world

These become cgroup v2 files the kubelet and container runtime write for the container: CPU request becomes cpu.weight (relative share when the CPU is contended), CPU limit becomes cpu.max (CFS quota and period: a 500m limit is 50000 100000, i.e. 50 ms of CPU per 100 ms), memory limit becomes memory.max. When memory.max is hit and reclaim fails, the kernel OOM killer picks a victim inside that cgroup - that is the exit code 137 (128 + SIGKILL 9). Since v1.35, the kubelet refuses to start on cgroup v1 by default. Where this breaks: the scheduler's view is pure bookkeeping on requests; the kernel never sees "requests" as a hard reservation, only as weights.

QoS classes: who gets evicted first

From the numbers you set, Kubernetes puts each pod into a Quality of Service class. You never write the class; it is derived:

QoS classRuleUnder node memory pressure
GuaranteedEvery container has CPU and memory requests equal to limitsEvicted last
BurstableAt least one request or limit set, but not GuaranteedEvicted if using more than its requests
BestEffortNo requests or limits anywhereEvicted first
 
$ kubectl get pod api-7c9d5-4xkzq -o jsonpath='{.status.qosClass}'
Burstable

The class also sets each container's oom_score_adj, so even the kernel's own OOM killer prefers BestEffort victims. Separately, the kubelet watches the node and evicts pods before the kernel has to act when free resources cross thresholds. Hard eviction defaults include memory.available<100Mi, nodefs.available<10% and imagefs.available<15%. Evicted pods show status Evicted and the node gets a MemoryPressure or DiskPressure condition.

Trap: "My app only uses 300 MB but keeps getting OOMKilled at a 512Mi limit." The limit covers everything in the cgroup: the JVM heap plus metaspace, thread stacks, native buffers, and file-backed tmpfs (memory-medium emptyDir). Check the runtime's container-aware settings (for Java, size the heap as a percentage of the limit) and leave headroom.
