A single ASG can mix them with a mixed instances policy: keep a base of On-Demand, fill the rest with Spot across many instance types and all AZs, so a Spot shortage in one pool does not hurt.

{
  "LaunchTemplate": {
    "LaunchTemplateSpecification": { "LaunchTemplateName": "web-lt", "Version": "$Latest" },
    "Overrides": [
      { "InstanceType": "m7i.large" }, { "InstanceType": "m6i.large" },
      { "InstanceType": "m7a.large" }, { "InstanceType": "m6a.large" }, { "InstanceType": "m5.large" }
    ]
  },
  "InstancesDistribution": {
    "OnDemandBaseCapacity": 2,
    "OnDemandPercentageAboveBaseCapacity": 20,
    "SpotAllocationStrategy": "price-capacity-optimized"
  }
}

Pair it with Capacity Rebalancing on the ASG: when EC2 sends a rebalance recommendation (elevated interruption risk), the ASG proactively launches a replacement before the 2-minute notice arrives. Inside the instance, poll the metadata service (AWS suggests every 5 seconds) and drain when a notice appears:

TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/spot/instance-action
{"action": "terminate", "time": "2026-11-23T08:22:00Z"}

No notice? You get HTTP 404. On Kubernetes, the AWS Node Termination Handler or Karpenter's interruption handling watches the same signal (via EventBridge) and cordons and drains the node so pods move gracefully.

Graviton (ARM) vs x86

Graviton is AWS's own ARM64 CPU (the g in m7g). AWS states Graviton instances cost up to 20 % less than comparable x86 instances and use up to 60 % less energy for the same performance. Your real gain depends on the workload, so benchmark. The catch is software:

  • Container images must be multi-arch: one tag, a manifest list pointing at an amd64 and an arm64 image.
  • Every dependency must exist for arm64: native libraries, JNI bits, old Python wheels, sidecar and agent images (monitoring, security scanners).
  • Interpreted and JIT languages (Java 17+, Go, Node, Python) usually just work; C/C++ with x86 intrinsics needs porting.
  • Do not mix architectures in one launch template. Use a separate ASG or Kubernetes node group, and steer pods with nodeSelector: kubernetes.io/arch: arm64.

From your world

This is cross-compiling for a different target, exactly like building a kernel for an ARM line card versus an x86 control card: same source, different toolchain, and any hand-written assembly or architecture-specific intrinsics must be ported. Endianness is not an issue (both are little-endian here), but memory ordering is: ARM is weakly ordered, so racy code that "worked" on x86's stronger ordering can break.
