Production stories: what goes wrong

Good to know (SDE-2)

Scenario: the ASG keeps killing healthy-looking instances

After a release the ASG launches instances, and two minutes later terminates them as unhealthy, forever. Desired is 6, but there are never more than 2 in service. The app takes about 4 minutes to start (JVM warm-up, cache load).
Weak answer: "Increase max size" or "switch off health checks".
Strong answer: ELB health checks are failing during startup, and the health check grace period is too short (or 0, the CLI default), so the ASG replaces instances before they ever become ready. Fix: set the grace period (and default instance warmup) above real startup time, or better, use a launch lifecycle hook that completes only when the app reports ready. Then attack the root cause: bake dependencies into the AMI and make /healthz return 200 only when ready (readiness), not to report deep dependency health, so a database blip does not make the ASG recycle the whole fleet.
Likely follow-ups
  • Why is a deep health check (checks the DB) dangerous here? (A DB outage marks every instance unhealthy, the ASG replaces all of them, and you add a cold-start storm to the outage.)

Scenario: Spot capacity disappears during a sale

An e-commerce web tier runs 90 % Spot with a single instance type, c5.xlarge, in one AZ. During a big sale, interruptions spike and replacements fail with InsufficientInstanceCapacity.
Weak answer: "Spot is unreliable, move everything to On-Demand."
Strong answer: The design concentrated risk in one Spot pool (one type, one AZ). Diversify: 5-10 similar instance types across all AZs, price-capacity-optimized allocation, Capacity Rebalancing on, an On-Demand base sized for the critical minimum, and scheduled scale-out before the sale so capacity is acquired before the rush. Keep stateful parts (databases, Kafka brokers) off Spot.
Likely follow-ups
  • How does the app survive the 2-minute notice? (Deregister from the target group, connection draining / deregistration delay, finish in-flight requests, idempotent jobs.)
