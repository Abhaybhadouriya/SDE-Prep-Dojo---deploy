Scaling policies: target tracking, step, scheduled, predictive

Must know (SDE-1)
PolicyHow it decidesUse when
Target trackingLike a thermostat: keep a metric at a value (CPU 50 %, 1,000 requests per target). AWS creates and manages the CloudWatch alarms.Default choice. AWS recommends it.
Step scalingYou define alarms and steps: +1 instance if CPU 60-80 %, +3 if above 80 %.You need different reactions to small and huge breaches.
Simple scalingOne adjustment, then a cooldown before anything else happens.Legacy. Prefer the two above.
ScheduledSet min/max/desired at a time (cron, UTC by default or a time zone you give).Known peaks: a 10 am sale, IPL match start, office hours.
PredictiveLearns daily/weekly patterns from history and scales before the load.Strong, regular cycles plus slow boot times.

Pick a metric that moves inversely with capacity. AWS's guidance: if you double the instances, the metric should halve. Average CPU and ALBRequestCountPerTarget behave like that. Total request count does not (it does not change when you add machines), so it makes a terrible target. Memory is not even published by EC2 - install the CloudWatch agent and track mem_used_percent as a custom metric if memory is your bottleneck.

cat > tt.json <<'EOF'
{
  "PredefinedMetricSpecification": {
    "PredefinedMetricType": "ALBRequestCountPerTarget",
    "ResourceLabel": "app/web-alb/50dc6c495c0c9188/targetgroup/web-tg/943f017f100becff"
  },
  "TargetValue": 1000.0
}
EOF
aws autoscaling put-scaling-policy --auto-scaling-group-name web-asg \
  --policy-name keep-1000-rpm-per-target --policy-type TargetTrackingScaling \
  --target-tracking-configuration file://tt.json
{
    "PolicyARN": "arn:aws:autoscaling:ap-south-1:123456789012:scalingPolicy:...:policyName/keep-1000-rpm-per-target",
    "Alarms": [
        { "AlarmName": "TargetTracking-web-asg-AlarmHigh-1f3e...", "AlarmARN": "arn:aws:cloudwatch:..." },
        { "AlarmName": "TargetTracking-web-asg-AlarmLow-9c2a...",  "AlarmARN": "arn:aws:cloudwatch:..." }
    ]
}
# scheduled: be at 10 instances before the 09:30 IST rush (04:00 UTC), weekdays
aws autoscaling put-scheduled-update-group-action --auto-scaling-group-name web-asg \
  --scheduled-action-name morning-rush --recurrence "0 4 * * MON-FRI" \
  --min-size 10 --desired-capacity 10

Warmup matters. Set a default instance warmup on the group (for example 120 s). Until a new instance has warmed up, its metrics do not count toward the group average - otherwise a booting instance at 0 % CPU drags the average down and the policy scales in again too early. Scale out fast, scale in slowly: target tracking already scales in more conservatively than it scales out.

Running Kubernetes? Pods scale with the HPA, and nodes with the Cluster Autoscaler (which resizes ASGs) or Karpenter (which launches EC2 directly). See Scheduling & Autoscaling. The ASG concepts here are exactly what those tools drive underneath.
