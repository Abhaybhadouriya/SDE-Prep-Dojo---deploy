IAM in 10 minutes: principals, roles and temporary credentials

Must know (SDE-1)

Every AWS API call, whether it comes from your laptop, an EC2 instance, a Lambda function or a pod, is answered by one question: is this principal allowed to do this action on this resource? The rest of the AWS pages assume this model, so here it is in one place.

  • Principal - who is calling: an IAM user (a person or legacy key; avoid), an IAM role session (the normal case for software), or an AWS service.
  • Identity policy - attached to a user or role: "this role may s3:GetObject on arn:aws:s3:::invoices/*". Resource policy - attached to the resource: a bucket policy, a KMS key policy, an SQS queue policy. Cross-account access needs both sides to agree.
  • Role - an identity with permissions but no password or long-lived keys. Its trust policy says who may assume it (the EC2 service, the ECS tasks service, Lambda, an OIDC provider for pods or CI, another account).
  • STS - assuming a role returns temporary credentials (access key, secret, session token) that expire. EC2 gets them through the instance profile and IMDS; ECS gives a task role to your code and a separate execution role to the agent that pulls images and secrets; Lambda has an execution role.
  • Evaluation - an explicit deny anywhere wins; otherwise some policy must allow; otherwise it is an implicit deny. Organisation SCPs and permission boundaries can only take permissions away.
  • Least privilege - grant exact actions on exact ARNs, add conditions (aws:SourceVpce, tags), and use IAM Access Analyzer to trim what is unused.
// trust policy on role app-s3-reader: "EC2 instances may assume me"
{
  "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow",
                  "Principal": { "Service": "ec2.amazonaws.com" },
                  "Action": "sts:AssumeRole" }]
}
// permission policy on the same role: "and then you may read one bucket"
{
  "Version": "2012-10-17",
  "Statement": [{ "Effect": "Allow",
                  "Action": ["s3:GetObject"],
                  "Resource": "arn:aws:s3:::dojo-invoices/*" }]
}

Click Play to follow one call from an app on EC2 to S3:

  1. The SDK asks the instance metadata service for a session token with a PUT (IMDSv2). Code never reads keys from a file.
  2. EC2 obtains temporary credentials for the instance profile's role from STS (the role's trust policy allows ec2.amazonaws.com), and refreshes them before they expire.
  3. With the token, the SDK reads those credentials from IMDS: access key, secret key and a session token, valid for a few hours.
  4. The app calls S3. The SDK signs the request with Signature Version 4 using the temporary secret; the secret itself never travels.
  5. S3 identifies the principal (the assumed role session) and evaluates every policy that applies: an explicit deny anywhere wins, otherwise an allow from the identity or bucket policy is needed, otherwise implicit deny.
  6. The answer comes back: 200 if allowed, 403 AccessDenied if not. CloudTrail records who did what.

From your world

A role is like a setuid-style capability grant with an expiry: the process does not own the power, it borrows it for a few hours, and only for the operations written on it. Policy evaluation is an ACL chain with a default deny at the end, where any explicit deny entry wins no matter where it sits, like a deny in a prefix-list that no permit can override. STS is the key server handing out short-lived session keys, so a leaked credential dies on its own.
