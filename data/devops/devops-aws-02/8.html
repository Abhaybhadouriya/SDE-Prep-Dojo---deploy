Multi-AZ: what actually fails over, and how fast

Must know (SDE-1)

An AZ is a failure domain: separate power, cooling and networking. AWS designs for whole AZs to fail occasionally, and so must you. "Multi-AZ" is not one switch; every component has its own story.

ComponentScopeWhen an AZ fails
ASGRegional (subnets in several AZs)Instances there go unhealthy and are replaced in the remaining AZs (balanced best effort). Takes minutes: boot + warmup.
ALB / NLBA node per enabled AZDNS stops returning the failed AZ's node; healthy targets elsewhere keep serving. ALB cross-zone load balancing is on by default (NLB off).
RDS Multi-AZPrimary + synchronous standby in another AZAutomatic failover; the DB endpoint's DNS is repointed to the standby, typically in one to two minutes. Apps must reconnect and respect DNS TTL.
RDS Multi-AZ DB clusterWriter + 2 readable standbys in 3 AZsFailover typically under 35 seconds; the standbys also serve reads.
AuroraStorage replicated 6 ways across 3 AZsA replica is promoted in about 30 seconds; no data copy needed. Put RDS Proxy or a smart driver in front to hide the DNS flip.
EBS volumeOne AZDoes not move. Data survives only via snapshots (stored regionally) or app-level replication.
Zonal NAT gatewayOne AZOnly subnets routed to it lose egress - if you built one per AZ (see NAT gateway).
S3, DynamoDB, SQSRegional, multi-AZ by designNothing to do.

The table lists components one by one. Here is the same AZ failure as one picture, across network and compute together. Click through:

  1. Normal day: every AZ has an ALB node, web instances from one ASG, its own NAT gateway, and the database primary happens to live in AZ b.
  2. AZ b loses power or networking. Everything inside the red box stops answering.
  3. The ALB's health checks fail for that node, and DNS stops returning its IP. New connections go only to the nodes in a and c.
  4. The ASG's instances in b are gone. Because each AZ was provisioned at 50% of peak, a and c already carry 100%: static stability means nothing has to launch.
  5. NAT gateway b is gone too, but with one NAT per AZ only AZ-b's own private subnets used it, and they are down anyway. With a single shared NAT in b, a and c would have lost all outbound internet as well.
  6. RDS fails over: the standby in a becomes the primary and the endpoint's DNS name is repointed (1-2 minutes for Multi-AZ instance, under 35 s for a Multi-AZ DB cluster). Apps reconnect.

From your world

An AZ is a failure domain like a chassis or a line card. Per-AZ NAT gateways are per-line-card uplinks: losing one card takes out only the ports on that card, with no shared single point. Static stability is N+1 provisioning of the forwarding plane, so a failure needs no control-plane action (no new launches) to keep forwarding. Interface endpoints follow the same rule: one ENI per AZ, so lose the AZ and you lose only that ENI.

Static stability (a term from the Amazon Builders' Library) means the system keeps working during an AZ failure without needing to do anything - no new launches, no config changes - because the control plane (the API that launches instances) may itself be slow or overloaded during the event. With N AZs, run enough so that N-1 can handle peak: for 3 AZs, each AZ carries 50 % of peak, 150 % in total. It costs more and is the reason big services rarely run on just two AZs (2 AZs means 200 %). For the regional and multi-region picture, see Reliability at Scale.
