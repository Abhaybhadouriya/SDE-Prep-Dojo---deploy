Interview questions

What is the difference between a security group and a network ACL?

A security group is a stateful firewall attached to an ENI (so per instance or load balancer node). It has allow rules only, all rules are evaluated together, replies to allowed traffic are automatically allowed, and it can reference other security groups. A network ACL is stateless and attached to a subnet: numbered allow and deny rules evaluated in order, first match wins, and return traffic (ephemeral ports 1024-65535) must be allowed explicitly. Security groups are the primary control; NACLs are coarse guard rails, mostly for explicit denies.

How to answer

Four contrasts in one breath: where (ENI vs subnet), state (stateful vs stateless), rules (allow vs allow+deny), evaluation (all vs ordered). Then when you would use each.

Likely follow-ups
  • How do you block one attacker IP immediately? (NACL deny with a low rule number; SGs cannot deny, and SG changes do not cut tracked connections.)
  • Why reference SGs instead of CIDRs? (Membership changes automatically as the ASG scales.)
How does an Auto Scaling Group decide to add instances? Compare target tracking and step scaling.

Scaling policies watch CloudWatch metrics aggregated over the group and change desired capacity; the ASG then launches or terminates to match, within min and max. Target tracking works like a thermostat: you set a target (say 50 % CPU or 1,000 requests per target) and AWS creates the alarms and computes proportional changes. Step scaling uses alarms you define and step adjustments by breach size, giving finer control for spiky loads. AWS recommends target tracking with a metric that is inversely proportional to capacity. Add scheduled scaling for known peaks and predictive scaling for regular cycles.

How to answer

Explain the loop (metric, alarm, desired, launch), then the policy types, then the metric choice rule and warmup.

Likely follow-ups
  • Two policies fire at once - which wins? (The one giving the larger capacity.)
  • How do you scale on memory? (CloudWatch agent custom metric.)
Your service runs in three AZs. Walk me through what happens when one AZ goes down.

The load balancer's health checks fail for targets in that AZ and DNS stops handing out that AZ's LB node, so traffic shifts to the other two within seconds. The ASG marks those instances unhealthy and launches replacements in the healthy AZs, which takes minutes. RDS Multi-AZ fails over to its synchronous standby if the primary was there, typically within one to two minutes, by repointing its DNS name; apps must reconnect. Zonal resources in the failed AZ - EBS volumes, the NAT gateway there - are simply unavailable. If we provisioned for static stability (each AZ carries 50 % of peak), the two remaining AZs already handle full load and we do not depend on launching anything during the event.

How to answer

Go layer by layer: LB, compute, database, zonal resources. Give timings. Finish with static stability, which is the senior-level insight.

Likely follow-ups
  • Why not rely on the ASG to scale up? (The control plane may be overloaded during the event; capacity in the remaining AZs may be scarce.)
  • How do you test it? (Chaos experiments with AWS FIS, zonal shift on the load balancer.)
When would you use Spot instances, and how do you make a service safe on them?

For fault-tolerant, stateless or retryable work: web tiers behind a load balancer, CI runners, batch and data processing, Kubernetes workers for replicated pods. Not for single-instance stateful systems. Make it safe by diversifying across many instance types and all AZs with price-capacity-optimized allocation, keeping an On-Demand base for the critical minimum, enabling Capacity Rebalancing, and handling the 2-minute interruption notice: deregister from the LB, drain connections, checkpoint jobs, and make work idempotent.

How to answer

Workload fit first, then the mixed instances policy, then interruption handling. Mention the price (up to 90 % off) only as motivation.

Likely follow-ups
  • How do you detect the interruption? (EventBridge event or IMDS spot/instance-action.)
How do you roll out a new AMI to 200 instances with zero downtime and a way back?

Publish a new launch template version and start an instance refresh with a minimum healthy percentage of 90 and max healthy above 100 so it launches before it terminates, an instance warmup matching real startup time, checkpoints (say 10 %, 50 %, 100 %) with a pause to watch metrics, and auto rollback tied to CloudWatch alarms such as 5xx rate and latency. Skip matching avoids replacing already-updated instances on retry. Alternatively, blue/green: a second ASG behind the same target group or a weighted listener, then shift traffic.

How to answer

Name the mechanism (instance refresh), the safety knobs (min/max healthy, warmup, checkpoints, alarms, rollback), then mention blue/green as the alternative.

Likely follow-ups
  • What if instances hold state? (Drain with lifecycle hooks; better, move state off the instance.)
You removed an SSH rule from a security group, but an existing SSH session is still alive. Why?

Security groups are stateful and use connection tracking. Changing a rule does not interrupt connections that are already tracked; they continue until they go idle and time out. (Exception: untracked flows - when both the inbound and outbound rules allow 0.0.0.0/0 - are cut immediately because there was no state.) To cut traffic at once, add a NACL deny on the subnet, which is stateless and applies to every packet, or terminate the session at the host.

How to answer

Say "connection tracking" in the first sentence. Show you know the untracked edge case. Give the immediate fix.

Likely follow-ups
  • What happens if an instance hits its tracked-connection limit? (New connections are dropped; watch conntrack_allowance_exceeded.)
Should we move our fleet to Graviton? What would you check?

Probably for most services, but verify. AWS states up to 20 % lower cost and up to 60 % less energy than comparable x86; real gains depend on the workload, so benchmark requests per dollar on the real service. Check: every container image (including sidecars and agents) is multi-arch; native dependencies and JNI libraries exist for arm64; build pipeline runs docker buildx for both platforms; there is no x86-specific assembly. Roll out as a separate node group or ASG, canary a slice of traffic, compare latency and error rates, then shift.

How to answer

Do not just quote a percentage. Show a migration plan: inventory, build, canary, measure, shift.

Likely follow-ups
  • What error do you see when an amd64-only image lands on an arm64 node? (exec format error.)

60-second answer - "How would you run this service on EC2 so it scales and survives failures?"
"Bake an AMI and define a launch template with IMDSv2 and an instance role. Put an Auto Scaling Group across private subnets in three AZs behind an ALB, with ELB health checks, a grace period longer than startup, and a target tracking policy on request count per target, plus scheduled scaling for known peaks. Size for static stability, so two AZs can carry peak. Security groups chain: ALB from the internet on 443, app from the ALB SG only, DB from the app SG only; NACLs for coarse denies. Deploy new AMIs with instance refresh, checkpoints and alarm-based rollback. For cost, an On-Demand base with diversified Spot on top and Graviton where the images are multi-arch."

How does code running on an EC2 instance get permission to read an S3 bucket, without any keys on disk?

Create an IAM role whose trust policy lets ec2.amazonaws.com assume it and whose permission policy allows s3:GetObject on that bucket's ARN, and attach it to the instance through an instance profile (in the launch template). The SDK finds credentials through its default chain: it calls IMDSv2 (PUT for a session token, then GET the role credentials), which returns temporary credentials from STS that are rotated before they expire. Every S3 request is signed with SigV4. S3 evaluates the role's identity policy together with the bucket policy: an explicit deny wins, otherwise an allow is needed. Enforce IMDSv2 to block SSRF credential theft, and scope the policy to exact actions and ARNs.

How to answer

Say the chain in order: trust policy, instance profile, IMDSv2, STS temporary credentials, SigV4, policy evaluation. Then one sentence on least privilege and IMDSv2.

Likely follow-ups
  • How is this different on ECS or EKS? (ECS task role via the task credentials endpoint; EKS via IRSA or Pod Identity, see Pod IAM.)
  • The bucket is in another account. What changes? (The bucket policy must also allow the role ARN.)
