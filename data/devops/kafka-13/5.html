Level 4 questions: internals, performance and operations

SDE-2 territory. You do not need every detail, but you must be able to go one level below the obvious answer. Background: Storage Internals, KRaft, Operations & Tuning.

Why is Kafka fast? Go deeper than "it uses the disk sequentially".

Five things stack up. (1) Sequential appends to a log, so the disk never seeks on the write path, and readers mostly read recent, sequential data. (2) The OS page cache instead of a JVM cache: no double buffering, no garbage collection pressure, and the cache survives a broker restart. (3) Zero-copy: for plaintext connections the broker calls sendfile, so data moves from page cache to the socket inside the kernel. (4) Batching and compression end to end: the producer compresses a batch, the broker stores it as is, and the consumer decompresses it, so the broker does little CPU work per message. (5) Partitioning spreads load across brokers and disks, and the broker keeps almost no per-message state because consumers track their own offsets. Caveats: TLS breaks zero-copy, and consumers reading old data that is not in cache cause disk reads that can evict hot pages for tail readers.

How to answer

Number the reasons, add one caveat. With your kernel background, name sendfile(2) and the page cache confidently; it will land.

Likely follow-ups
  • Does Kafka fsync every write? (No by default; durability comes from replication.)
  • How does tiered storage change the cold-read problem? (Old reads come from object storage, not the hot disk.)
How does Kafka store a partition on disk, and how does it find offset N?

A partition is a directory like orders-3/ containing segments. Each segment has a .log file with the record batches, a sparse .index mapping some offsets to byte positions, and a .timeindex mapping timestamps to offsets. Each file is named by the segment's base offset, the first offset it contains. Only the newest, active segment is written; a segment rolls when it reaches segment.bytes (1 GiB) or segment.ms. To find offset N, the broker picks the segment whose base offset is the largest one not above N (a binary search over the segment list), binary-searches the sparse index for the nearest entry below N, then scans forward a little in the log file. Retention deletes whole closed segments.

How to answer

Directory, segment files, file naming, the lookup in two binary searches plus a short scan. Draw the file names.

Likely follow-ups
  • Why a sparse index? (Small enough to memory-map; a short scan is cheap.)
  • How is "replay from a timestamp" served? (The time index.)
Can Kafka lose acknowledged data? List the ways.

Producer side: acks=0 or acks=1 with a leader crash before followers fetch; replication factor 1 with a dead disk; acks=all with min.insync.replicas=1 after the ISR has shrunk to the leader; unclean leader election enabled, so a stale replica becomes leader and the newer records are truncated away; and producers that never check the send callback, so failed sends are silently dropped. Consumer side: auto-commit before processing finishes, then a crash; and retention deleting data a slow consumer has not read. Operations: deleting a topic, or resetting offsets past data. A correlated failure of all replicas (all in one zone, power loss before page cache flush) is also possible, which is why replicas go in different zones.

How to answer

Group by producer, broker, consumer, operations. For each, the fix in a few words. This shows a structured mind.

Likely follow-ups
  • Which of these did you personally see? (Have one story ready, even from a lab.)
A broker dies. Walk through what happens, step by step.

1) The broker stops heartbeating to the active KRaft controller; after the broker session timeout, the controller fences it. 2) For every partition where it was leader, the controller picks a new leader from the remaining ISR (or, with ELR, from eligible replicas), bumps the leader epoch, and writes these changes to the metadata log. 3) Other brokers replicate the metadata log and start acting as leaders or followers. 4) Producers and consumers get errors such as NOT_LEADER_OR_FOLLOWER, refresh metadata and retry against the new leaders; with idempotence the retries do not create duplicates. 5) Those partitions now have one replica fewer, so under-replicated partition alerts fire; if the ISR drops below min ISR, acks=all writes fail. 6) When the broker returns or is replaced, it truncates to the leader epoch boundary, catches up from the leaders and rejoins the ISR. Partitions it led do not move back automatically unless preferred-leader election runs (it does by default periodically).

How to answer

Number the steps and name the actor at each one (controller, brokers, clients). The learner input asked "never make me guess which process does what"; interviewers want the same.

Likely follow-ups
  • How long is the client-visible blip? (Detection timeout plus metadata refresh; typically seconds.)
  • What if it was the active controller that died? (The Raft quorum elects a new controller.)
How do Kafka transactions work, and what is a zombie producer?

A transactional producer has a stable transactional.id. On initTransactions(), the transaction coordinator (a broker, state kept in __transaction_state) bumps the producer's epoch and finishes or aborts any half-done transaction from a previous instance. Then the app calls beginTransaction(), sends to many partitions, adds its consumed offsets with sendOffsetsToTransaction(), and calls commitTransaction(). The coordinator writes commit or abort markers into every partition involved. Consumers with isolation.level=read_committed read only up to the last stable offset and skip aborted records. A zombie is an old instance that was presumed dead (for example a long GC pause during failover) and wakes up still thinking it owns the work; because its epoch is older, its writes are rejected with ProducerFencedException. Since 4.0 (KIP-890) the epoch is bumped on every transaction, closing "hanging transaction" holes.

How to answer

The API sequence, the coordinator and markers, read_committed, then fencing. Draw two producers with epochs 4 and 5.

Likely follow-ups
  • What is the cost? (Extra round trips and latency up to the commit interval for read_committed readers.)
How do you get exactly-once results when the consumer writes to a database?

Kafka transactions do not reach into your database, so pick one of three patterns. (1) Store offsets with the data: in one DB transaction, write the result and the consumed partition-offset into an offsets table; on start, seek to the stored offsets instead of Kafka's. This is truly exactly-once into that database. (2) Idempotent writes: upsert by a natural key, or insert with the event ID under a unique constraint and ignore conflicts; at-least-once delivery then produces exactly-once state. (3) Versioned updates: only apply an event if its version is newer than the stored one. For side effects that cannot be undone, like charging a card or sending an email, pass an idempotency key to the provider and record it. I would say "effectively once" and explain which of these I use.

How to answer

Start with "Kafka EOS stops at Kafka's edge". Interview write-ups note candidates often overclaim here, so being precise is the win.

Likely follow-ups
  • Which pattern for a counter? (Offsets with data, or dedup table, since increments are not idempotent.)
How do you choose the number of partitions? Show the math.

Partitions ≥ max(target throughput / per-partition producer throughput, target throughput / per-partition consumer throughput), plus headroom. Example: we need 60 MB/s at peak. A test with kafka-producer-perf-test.sh shows about 20 MB/s per partition on the produce side, but our consumer does a database write and manages only 5 MB/s per partition. So 60 / 20 = 3 and 60 / 5 = 12; we need at least 12. Planning for 2-3x growth gives 24 to 36; I would choose something like 24 or 30 rather than re-partition later, because adding partitions remaps keys. Then a sanity check against cost: each partition adds open files, memory, replication fetches and leader elections during failure, so thousands of partitions per broker are a smell. KRaft raised the cluster-wide ceiling, but per-partition costs remain.

How to answer

Formula, worked example with made-up but labelled numbers, growth factor, cost of too many. The numbers here are illustrative; say "I would measure".

Likely follow-ups
  • Can you reduce the partition count later? (No; you must create a new topic and migrate.)
What is a hot partition and how do you fix it?

A hot partition gets far more traffic than its siblings because the key is skewed: a celebrity user, a giant seller during a sale, a default key like "unknown". Its consumer lags while others idle, and its leader broker runs hot. Fixes, depending on whether you need per-key order: salt the key (sellerId#0..7) to spread one key over several partitions and re-aggregate downstream, accepting no order across the salted sub-keys; a custom partitioner that sends known heavy keys to dedicated partitions; a separate topic for the whales; or fix the bad default key. Detect it with per-partition bytes-in and per-partition lag, not topic totals.

How to answer

Cause, symptom, detection, then fixes ordered by how much ordering they give up. The ECMP elephant-flow analogy is ideal for you.

Likely follow-ups
  • How do you re-aggregate salted keys? (A second stage keyed by the original key, or sum in the sink.)
What happens if you add partitions to a live keyed topic?

New records are hashed modulo the new count, so many keys now map to a different partition, while their older records stay in the old partition. For a while, a consumer may see a key's new events on partition 7 before it finishes the old events on partition 2: per-key ordering breaks across the change. Consumers also rebalance to pick up the new partitions, and if they start new partitions at latest they can skip records written before they were assigned (set auto.offset.reset=earliest). Safe approaches: over-provision partitions at creation; or create a new topic with more partitions, dual-write or migrate, and cut consumers over once the old topic is drained.

How to answer

Explain the hash change, the ordering consequence, the subtle offset-reset trap, then the safe migration.

Likely follow-ups
  • Would consistent hashing help? (It would reduce how many keys move, but Kafka's default partitioner is plain modulo.)
ZooKeeper vs KRaft: what changed and why does it matter?

Before, cluster metadata (brokers, topics, partition leaders, ISR, configs) lived in a separate ZooKeeper ensemble, and one broker acted as controller, pushing changes to others over RPC. That meant two distributed systems to run and secure, and a slow controller failover because a new controller had to load all metadata from ZooKeeper. With KRaft (KIP-500), metadata is itself a Raft-replicated log, __cluster_metadata, managed by a small quorum of controller nodes (usually 3, or 5 for large clusters). Brokers simply replicate that log, like consumers. Benefits: one system, much faster failover and restart, and far more partitions per cluster. ZooKeeper mode was removed in Kafka 4.0 (March 2025); you migrate on 3.9 first, then upgrade.

How to answer

Before, after, three benefits, and the 4.0 fact. A control-plane vs data-plane bridge from routers works well.

Likely follow-ups
  • How many controller failures can a 3-node quorum survive? (One; 5 nodes survive two.)
What is unclean leader election, and when would you enable it?

If every in-sync replica of a partition is gone, Kafka must choose: wait for an ISR member to come back (the partition stays offline) or let an out-of-sync replica become leader (the partition comes back now, but records it never received are lost, and the others truncate to match). unclean.leader.election.enable is false by default, which picks consistency. Enabling it picks availability. It can make sense for data where gaps are acceptable and an outage is not, like metrics or logs; never for orders or payments. Our research notes record that Slack ran with it enabled for some clusters, favouring availability. This is the CAP trade-off made into one config flag.

How to answer

The dilemma, the default, one use case per side, the CAP link.

Likely follow-ups
  • How does ELR change this? (Some replicas outside the ISR are known to have every committed record and can lead safely.)
What is tiered storage and when would you enable it?

With tiered storage (KIP-405, production-ready since 3.9), closed segments are uploaded to remote object storage through a plugin, while a short hot tail stays on local disk (local.retention.ms), and retention.ms sets the total. Benefits: long retention (months) at object-storage prices, smaller local disks, and much faster broker replacement and rebalancing because less data lives locally. Costs: reads of old data have higher latency, you depend on a plugin (Kafka ships no S3 implementation itself), and compacted topics are not supported. I would enable it when teams need weeks or months of replay, or when disk cost and rebalance time dominate.

How to answer

Mechanism, three benefits, three costs, one decision rule.

Likely follow-ups
  • How is this different from Pulsar's design? (Pulsar always separates storage; Kafka keeps a local hot tier.)
How do you run Kafka on Kubernetes, and what is hard about it?

I would use an operator, usually Strimzi: you declare a Kafka resource plus KafkaNodePools for controllers and brokers, and topics and users as KafkaTopic and KafkaUser resources; the operator creates pods, persistent volumes, certificates and does safe rolling restarts. The hard parts: each broker needs stable identity and its own persistent volume; clients outside the cluster must reach a specific broker (the partition leader), so you need per-broker addresses through advertised listeners (NodePort, LoadBalancer or Ingress), not one load-balanced address; rack awareness from zone labels; PodDisruptionBudgets so node drains never take two replicas down; rolling updates that wait for no under-replicated partitions; and rebalancing data when scaling, which Strimzi does through Cruise Control (KafkaRebalance).

How to answer

Operator first, then the "per-broker addressing" gotcha, which is the number-one issue. Link it to operators and StatefulSets: StatefulSets & Operators.

Likely follow-ups
  • Is running Kafka on K8s a good idea? (Fine with an operator and a team that knows both; otherwise use a managed service.)
Kafka Streams vs Flink vs a plain consumer: how do you choose?

A plain consumer is right for stateless or simple work: read, call a service, write. Kafka Streams is a library inside your app, no cluster to run, with local RocksDB state backed by changelog topics, windows, joins and exactly-once within Kafka; good for microservice-sized stateful processing where input and output are Kafka. Flink is a separate cluster with checkpointed state, strong event-time and watermark handling, SQL, and many sources and sinks; good for large, shared, stateful pipelines like windowed analytics or fraud features. Rule of thumb from our research: Kafka Streams for app-embedded processing, Flink for big shared pipelines.

How to answer

One line per option, then one example each. See Connect, Streams & Flink.

Likely follow-ups
  • Where does state live, and how is it recovered after a crash? (RocksDB plus changelog topic; Flink checkpoints.)
What are share groups (Queues for Kafka), and when would you use one?

Share groups (KIP-932, production-ready in Kafka 4.2) are a new kind of group where many consumers can read the same partition. Each record is acquired with a time-limited lock (30 seconds by default) and acknowledged individually: accept, release for redelivery, reject, or renew the lock (since 4.2). Each record counts its delivery attempts; after 5 by default it is archived, and since 4.4 it can go to a dead-letter queue (KIP-1191). You give up ordering, and you gain scaling beyond the partition count and per-message acks, so slow jobs no longer block a partition. I would use it for work queues such as sending notifications or resizing images, exactly the gap Uber's and Walmart's consumer proxies were built to fill.

How to answer

What, how (lock, acks, delivery count), trade-off (ordering), when. Mention the version; it shows you are current.

Likely follow-ups
  • Would you replace SQS with this? (If we already run Kafka 4.2+, maybe; otherwise SQS is less to operate.)
