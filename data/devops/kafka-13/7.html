Level 5 questions: design with Kafka

These are HLD prompts where Kafka is the backbone. Use the 6-step pattern. Each answer is a compressed version of a 15-minute discussion; the linked design pages go deeper. The end-to-end version lives in the ShopStream pipeline project.

Explain the dual-write problem and how the outbox pattern solves it.

An order service that does "commit the order to the database, then publish OrderPlaced to Kafka" has two separate writes with no shared transaction. If the process crashes between them, the order exists but nobody hears about it; if it publishes first and the DB commit fails, consumers act on an order that does not exist. Retrying does not fix it, it only changes which half is missing. The outbox pattern: in the same database transaction as the business write, insert a row into an outbox table describing the event. A relay then publishes outbox rows to Kafka, either a CDC connector such as Debezium tailing the database log (with its Outbox Event Router routing rows to topics keyed by aggregate ID), or a poller. The relay is at-least-once, so consumers still dedup by event ID.

How to answer

Show the two failure orders on a timeline, then the outbox with "same transaction" emphasised, then the relay choice, then idempotent consumers. See Distributed Transactions & Events.

Likely follow-ups
  • CDC vs polling relay? (CDC: low latency, no extra DB load from polling, but more infrastructure; polling: simple, adds query load and latency.)
  • How do you clean the outbox table? (Delete after publish, or let Debezium read inserts and delete rows in the same transaction.)
Design an e-commerce order-processing pipeline with Kafka.

Order service writes the order plus an outbox row; Debezium publishes to order.events keyed by orderId, so each order's events are ordered. Consumers in separate groups: payment (idempotent by event ID, calls the payment provider with an idempotency key), inventory (reserves stock with a TTL), notification, and analytics. The flow is a saga (a sequence of local steps with compensating actions): PaymentFailed triggers inventory release and order cancellation. The order service keeps a state machine (CREATED, PAID, RESERVED, SHIPPED) that ignores repeated or out-of-date transitions. Failures go through retry topics to a DLQ with an alert. Settings: RF 3, min ISR 2, acks all, partitions sized for the sale-day peak. Monitoring: lag per group, DLQ depth, end-to-end time from order created to confirmed.

How to answer

Clarify first (scale, sale-day peak, which steps must be synchronous: payment authorisation often is). Then the 6-step pattern. See E-commerce Checkout and Flash Sale.

Likely follow-ups
  • Orchestration or choreography for the saga? (Orchestrator for complex flows and visibility; choreography for few steps.)
  • What does the user see while payment is pending?
Design a notification system (push, SMS, email) using Kafka.

Producers publish "notify" requests to a topic keyed by user ID. A preference service filters (opt-outs, quiet hours) and fans out to per-channel topics (notify.push, notify.sms, notify.email), optionally split by priority so a marketing blast cannot delay one-time passwords. Channel workers call providers with per-provider rate limits (token buckets), retry topics with backoff, and a DLQ. Dedup by notification ID so a retry does not text the user twice. Scheduled sends go to a scheduler service that publishes when due, because Kafka has no per-message delay. Since each send is an independent slow job, this is a good fit for a share group on Kafka 4.2+ or SQS per channel.

How to answer

Separate channels and priorities early; it shows you think about isolation. See Notification System.

Likely follow-ups
  • How do you send to 50 million users for a campaign without hurting OTPs? (Separate topic and quota, throttled producer.)
Design a real-time clickstream or analytics pipeline.

Client SDKs batch events to an edge collector service, which validates and produces to a clicks topic with many partitions, lz4 or zstd compression and acks=all (or acks=1 if some loss is acceptable). A stream processor (Flink, or Kafka Streams for smaller jobs) does windowed aggregates by event time with watermarks and a grace period for late events, writing results to an OLAP store (Druid, Pinot or ClickHouse) for dashboards; a sink connector also writes raw events to object storage (a data lake) for batch jobs and replay. Keys: session or user ID for sessionisation, otherwise null keys for even spread. Handle bots and sampling at the edge. Monitor lag, late-event rate and end-to-end freshness.

How to answer

Ingest, buffer, process, serve, archive. Event time vs processing time is the deep dive interviewers want. See Ad Click Aggregator and Big Data & Streaming.

Likely follow-ups
  • How do you avoid double counting after a processor restart? (Checkpoints plus transactional or idempotent sinks.)
Design a payment event system where a customer must never be charged twice.

The guarantee comes from idempotency at every boundary, not from Kafka alone. The client sends an idempotency key with the payment request; the payment API stores it with a unique constraint, so a retried request returns the original result. The payment and its outbox event commit in one transaction. Internal Kafka hops can use transactions, but every consumer that causes a side effect dedups by payment ID, and calls to the bank or card network carry the provider's idempotency key. A ledger (double-entry, append-only) is the source of truth, and reconciliation jobs compare it against provider reports daily to catch anything that slipped. Topics: RF 3, min ISR 2, acks all, unclean election off, keyed by payment or account ID.

How to answer

Say early "Kafka exactly-once does not cover the bank call". Then idempotency keys, outbox, ledger, reconciliation. See Payment System.

Likely follow-ups
  • The bank call times out. Did it charge? (Unknown; query status with the idempotency key before retrying.)
How would you build delayed or scheduled messages on Kafka?

Kafka has no per-message delay or visibility timeout, so you build it around Kafka. Options: (1) delay topics by bucket (delay.1m, delay.1h): the consumer of each reads a record, and if it is not yet due, pauses that partition until it is (records in one bucket topic share the same delay, so they arrive in due order); (2) a scheduler service that stores jobs in a database indexed by due time (or a timer wheel in memory backed by the DB) and publishes to Kafka when due; (3) use a system with native delays (SQS up to 15 minutes, RabbitMQ delayed-message plugin) for that part. For long or exact schedules, option 2 is the usual interview answer.

How to answer

State the limitation first, then two or three options with when each fits. See Distributed Job Scheduler.

Likely follow-ups
  • How do you avoid two scheduler instances firing the same job? (Lease or lock per job shard, plus idempotent consumers.)
How do you design Kafka for disaster recovery across regions?

Usually one cluster per region, with MirrorMaker 2 (built on Kafka Connect) replicating topics to the DR region and translating consumer offsets, so consumers can resume roughly where they left off. Active-passive is the common setup: producers write to the primary, and on failover clients switch bootstrap servers. Replication is asynchronous, so the RPO (data you may lose) is the mirror lag, and consumers must tolerate some re-reads after failover. Active-active needs topic prefixes per region to avoid replication loops and conflict handling in the apps. A stretch cluster across zones or very close regions gives zero RPO but adds cross-site latency to every acks=all write, so it only suits low-latency links. PhonePe's published setup uses per-data-centre clusters mirrored with MirrorMaker 2.

How to answer

Name RPO and RTO explicitly, compare the three topologies, and say which you would pick and why. See Reliability & Multi-region.

Likely follow-ups
  • How do you test failover? (Regular game days; measure real RTO.)
Your team wants one topic per customer, for 100,000 customers. Good idea?

No. 100,000 topics with even 3 partitions and replication factor 3 is about 900,000 partition replicas, which means huge metadata, many open files, slow recovery and an operational mess, even though KRaft raised the ceiling. Better: one shared topic (or a few tiers, such as standard and premium) keyed by customer ID, so each customer's events stay ordered; per-customer filtering in consumers; client quotas for noisy customers; and a dedicated topic only for the few very large customers. If true isolation is a hard requirement, separate clusters per tenant tier, or a system with built-in multi-tenancy such as Pulsar.

How to answer

Do the multiplication out loud. Then the alternative and the isolation escape hatch.

Likely follow-ups
  • How do you stop one customer flooding the shared topic? (Producer quotas, rate limits at the API.)
How would you migrate a live system from RabbitMQ (or Kinesis) to Kafka without downtime?

In phases, always with a rollback. (1) Set up Kafka and a bridge: either producers dual-publish to both systems, or a connector copies messages from the old system into Kafka. (2) Run shadow consumers on Kafka that process but do not cause side effects, and compare their outputs with the live path. (3) Cut consumers over one service at a time, with idempotency so the overlap does not double-apply anything. (4) Switch producers to Kafka only. (5) Keep the old system for a rollback window, then retire it. Atlassian has written about moving its StreamHub platform from Kinesis to Kafka at about 145 billion events per day; their post is good preparation.

How to answer

Phases, comparison, idempotency during overlap, rollback. Interviewers listen for "how do you know it worked?".

Likely follow-ups
  • What about ordering during the switch? (Drain per key before switching, or switch by partition or customer range.)
Design a distributed message queue like Kafka itself.

Requirements: durable, ordered per partition, many consumers with replay, high throughput, horizontal scale. Design: topics split into partitions, each an append-only log of segment files with a sparse offset index and a time index; a leader per partition with followers that fetch; an ISR and a high watermark so consumers only read committed data; a metadata controller replicated with Raft that assigns leaders; producers that batch, compress and choose partitions by key hash; consumers that pull and commit offsets to an internal compacted topic; group coordination for assignment; retention by time or size and compaction by key; zero-copy reads from the page cache. Then deep dives: acks and min ISR, leader failover with epochs, rebalancing, and hot partitions.

How to answer

Walmart reports include exactly this prompt. Spend the first minutes on the storage model; everything else follows from "partitioned, replicated log". Full design: Design a Message Queue.

Likely follow-ups
  • Why pull and not push? Why not store offsets per message on the broker?
When would you NOT use Kafka in a design?

When the caller needs an immediate answer (use a synchronous API); when volume is low and the team is small (a database table, SQS or RabbitMQ is far cheaper to run); when each message needs its own delay, priority or complex routing (RabbitMQ or SQS); when you need strict global order across everything (a single partition kills parallelism); and when nobody can operate it (use managed Kafka or a managed queue). Saying this calmly is one of the clearest maturity signals in a design round. The full comparison is on Kafka vs Others.

How to answer

Four or five cases, each with the alternative.

Likely follow-ups
  • Your company already runs Kafka. Does the answer change? (Marginal cost drops; share groups may cover the work-queue case.)
