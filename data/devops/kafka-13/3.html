Level 2 questions: fundamentals

These are SDE-1 bread and butter. Answer each in under a minute, then stop and let the interviewer pick the next thread. Background: Core Concepts, Consumers & Groups.

Why use Kafka (or any message queue) instead of direct REST calls between services?

Direct calls couple services in time: the caller waits, latencies add up, and if the callee is down or slow the failure cascades back to the user. Putting Kafka in between gives decoupling (the producer does not know or wait for consumers), buffering (a traffic spike piles up as lag instead of crashing the downstream), fan-out (payments, inventory and email each read the same "order placed" event), replay (re-read history after a bug fix or for a new service) and resilience (consumers catch up after an outage). The cost is eventual consistency, an extra system to run, and harder debugging. I would not use it when the user needs an immediate answer, like "is this username free?".

How to answer

List four or five benefits with a one-line example each, then the costs, then one case where you would not use it. That last part is what makes it sound senior.

Likely follow-ups
  • What does the user see while the order is "processing"?
  • How would you trace a request across the async hop? (Correlation ID in headers.)
Explain topic, partition, offset, broker and consumer group.

A topic is a named stream of events, like orders. It is split into partitions; each partition is an ordered, append-only log stored on a broker. An offset is the position of a record inside one partition, a 64-bit number that only grows. A broker is a Kafka server that stores partitions and serves clients; a cluster has several. A consumer group is a set of consumers that share the work of reading a topic: each partition goes to one member, and the group remembers one committed offset per partition. Ordering is guaranteed only within a partition.

How to answer

Draw while you talk: a topic box with three partition rows, numbered cells for offsets, two brokers, and a group of two consumers. One sentence per term.

Likely follow-ups
  • Where are partitions physically stored? (A directory of segment files per partition.)
  • What is a replica? (A copy of a partition on another broker.)
Is Kafka a queue? When a consumer reads a message, is it deleted?

No, a classic Kafka topic is a log, not a queue. Reading does not delete anything; the consumer group just moves its offset forward. Records are deleted only by retention, by time (7 days by default) or size, in whole segments, whether or not anyone read them, or kept as "latest per key" by compaction. That is why several groups can read the same data and why you can replay. Since Kafka 4.2, share groups (KIP-932) add real queue behaviour with per-record acknowledgement, but the data still stays in the log until retention.

How to answer

Say "no" clearly, explain offsets and retention, then mention share groups as the modern nuance.

Likely follow-ups
  • What happens to a consumer that falls further behind than retention? (It loses those records; on restart auto.offset.reset decides where it jumps.)
Kafka keeps data on disk. How is it different from a database?

A database is built to answer questions about the current state: look up a row by key, update it in place, run queries with indexes and transactions. Kafka is built to move and keep a sequence of events: you append to the end and read forward from an offset. There are no secondary indexes, no updates in place, and no ad-hoc queries; you can only find a record by partition and offset (or timestamp). The two work together: Kafka carries the changes, and consumers build databases, caches and search indexes from them. A compacted topic gets close to a key-value table, but you still read it by scanning, not by querying.

How to answer

State vs events, query vs scan, update vs append. Finish with "they complement each other", using CDC as the example.

Likely follow-ups
  • Could you use Kafka as your source of truth? (Event sourcing; possible, but you still need materialised views for queries.)
A topic has 10 partitions and your group has 15 consumers. What do the extra 5 do?

They sit idle. In a classic consumer group each partition is assigned to exactly one consumer, so at most 10 consumers can be active; the other 5 are hot standbys that take over if an active member leaves. The maximum parallelism of a group is the partition count. To use more consumers you add partitions (and accept the key remapping), make each consumer faster, process with a thread pool inside each consumer while keeping per-key order, or use a share group, which lets many consumers read the same partition without ordering.

How to answer

Answer in one word ("idle"), give the rule (parallelism = partitions), then list the ways around it.

Likely follow-ups
  • And with 5 consumers and 10 partitions? (Each gets about two.)
  • Is it wasteful to keep the idle ones? (They speed up failover; cost vs recovery time.)
Where are consumer offsets stored, and who owns them?

The consumer group owns its offsets, and by default they are committed to an internal compacted topic called __consumer_offsets, which has 50 partitions. The broker that leads partition hash(group.id) % 50 acts as that group's group coordinator. Because the topic is compacted, only the latest committed offset per group-topic-partition survives. You can also store offsets yourself, for example in the same database transaction as your results, which gives exactly-once into that database. The old ZooKeeper-based offset storage is long gone.

How to answer

Name the topic, the coordinator rule and compaction. Mention storing offsets externally as the advanced option.

Likely follow-ups
  • Do committed offsets live forever? (No: offsets.retention.minutes, 7 days by default, after the group becomes empty.)
Push vs pull: why do Kafka consumers pull?

Pull lets each consumer go at its own pace, which is natural back-pressure: a slow consumer simply asks less often, and data waits safely on disk. It also lets the broker return big batches efficiently, and it makes rewinding trivial, since the consumer just asks for a different offset. The downside of pull is busy-polling an empty topic, which Kafka avoids with long polling: fetch.min.bytes and fetch.max.wait.ms (500 ms by default) let the broker hold the request until data arrives. Push systems like RabbitMQ need explicit flow control (prefetch) to avoid drowning consumers.

How to answer

Back-pressure, batching, rewind; then the cost and how long polling fixes it. The NAPI analogy works well if the interviewer likes systems.

Likely follow-ups
  • How do you get low latency with pull? (Small fetch.max.wait.ms, fast poll loop.)
What is retention, and how is it different from compaction?

Retention (cleanup.policy=delete) removes whole old segments when they pass a time limit (retention.ms, 7 days by default) or a size limit per partition. Compaction (cleanup.policy=compact) keeps at least the latest value for each key and throws away older values, so the topic behaves like a changelog of a table. A record with a null value, a tombstone, deletes the key after delete.retention.ms. Use retention for event streams like clicks; use compaction for "current state" streams like user profiles, CDC tables and __consumer_offsets. You can combine both with compact,delete.

How to answer

One line each, one use case each, mention tombstones. The ARP or MAC table analogy lands well.

Likely follow-ups
  • Does compaction keep ordering? (Yes; surviving records keep their offsets, there are just gaps.)
What do acks=0, acks=1 and acks=all mean?

acks=0: the producer does not wait for any reply; fastest, and data can vanish silently. acks=1: the leader wrote the record to its log (its page cache, not necessarily disk) and replied; if the leader dies before followers copy it, the record is lost. acks=all: the leader waits until every replica in the current in-sync set has it; this is the default since Kafka 3.0. The catch is that "all of the ISR" might be just the leader, so pair it with min.insync.replicas=2 on a replication factor 3 topic.

How to answer

Three short lines, then the catch. The catch is the whole point of the question.

Likely follow-ups
  • What is the latency cost of acks=all? (One extra replication round trip, usually within one data centre.)
  • Where would you choose acks=1? (High-volume metrics where a little loss is fine.)
What is consumer lag, and how do you monitor it?

Lag is, per partition, the log-end offset minus the group's committed offset: how many records are written but not yet processed. It is the queue depth. You check it with kafka-consumer-groups.sh --describe, the consumer metric records-lag-max, or an exporter such as kafka_exporter or Burrow into Prometheus and Grafana. The useful alert is on the trend, lag growing for several minutes, or on time lag ("we are 10 minutes behind"), not on a raw number, because a big but shrinking lag after a deploy is fine. Also alert if lag in time gets close to retention, because then you start losing data.

How to answer

Formula, tools, then the "alert on trend and time, not on count" insight.

Likely follow-ups
  • Lag is growing. What do you do? (See the scenario drills below.)

How do you make sure all events for one order are processed in sequence?

Use the order ID as the record key. The default partitioner hashes the key, so every event for that order goes to the same partition, and a partition is strictly ordered. Keep the idempotent producer on (the default) so retries cannot reorder records. On the consumer side, one partition is read by one consumer in the group; if I process with a thread pool, I route by key so one order's events stay on one thread. And I never change the partition count casually, because that remaps keys to new partitions.

How to answer

Key, partition, producer setting, consumer threading, the partition-count trap. Four parts, one breath each.

Likely follow-ups
  • What if you need ordering across all orders of one customer? (Key by customer ID, with the hot-key risk.)
  • What if a key has no value at all? (Null keys spread with the sticky partitioner; no ordering.)
What are replication factor, leader and follower?

The replication factor is how many copies of each partition exist, usually 3 on different brokers (and ideally in different availability zones with broker.rack). One copy is the leader: all writes and, by default, all reads go to it. The others are followers that continuously fetch from the leader, exactly like consumers. If the leader's broker fails, the controller picks a new leader from the followers that were in sync. Note the defaults are not durable: the broker defaults are replication factor 1 and min ISR 1, so production clusters set 3 and 2 explicitly.

How to answer

Define the three terms, say who elects the leader, and call out the unsafe defaults.

Likely follow-ups
  • Can consumers read from followers? (Yes, with rack-aware follower fetching, KIP-392, to save cross-AZ cost.)
