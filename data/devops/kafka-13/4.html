Level 3 questions: guarantees, commits and failures

This is where SDE-1 candidates separate from each other and SDE-2 candidates must be solid. Background: Replication & ISR, Delivery Semantics, Producers.

Explain ISR, high watermark and what min.insync.replicas does.

The ISR (in-sync replicas) is the set of replicas of a partition that are caught up with the leader; a follower that has not caught up within replica.lag.time.max.ms (30 seconds by default) is removed. Each replica has a log end offset, the next offset it will write. The high watermark is the smallest log end offset across the ISR: everything below it is on every in-sync replica, so it is "committed", and consumers can only read up to it. min.insync.replicas is the minimum ISR size for a write with acks=all to succeed; below it, producers get NotEnoughReplicas and the partition is effectively read-only for those writers. That is Kafka choosing durability over availability.

How to answer

Define ISR with the timer, then HW as "the TCP cumulative ACK of the cluster", then min ISR with the error name. Draw three replica bars with different lengths.

Likely follow-ups
  • Why can consumers not read beyond the HW? (Those records could disappear if the leader fails.)
  • What is ELR? (Eligible Leader Replicas, KIP-966, on by default for new clusters since 4.1.)
What configuration would you use for a topic that must not lose data, and what does it survive?

Replication factor 3, with replicas spread across three racks or availability zones; min.insync.replicas=2; producers with acks=all and idempotence on (both defaults since 3.0); unclean.leader.election.enable=false (the default); and producers that handle the send callback instead of ignoring errors. This survives one broker or one zone failing with no data loss and no write outage. If two of three replicas are down, writes fail rather than risk loss, which is the right behaviour for orders or payments. On the consumer side, commit offsets only after processing, so a crash causes a re-read, not a loss.

How to answer

Producer, broker/topic and consumer settings in that order, then "what it survives" in one sentence. Mention the consumer side; many candidates forget it.

Likely follow-ups
  • Why not fsync every message? (Durability comes from replication across machines, not from flushing one disk.)
  • Why not RF 5? (More disk and network; worth it only for very critical topics.)
At-most-once, at-least-once, exactly-once: what does each mean in Kafka?

It is about the order of "process" and "commit offset". At-most-once: commit first, then process; a crash after the commit skips the record, so it is processed zero or one times. At-least-once: process first, then commit; a crash before the commit means the record is processed again, so one or more times. This is the normal choice, with idempotent handlers. Exactly-once: the effects happen once even with crashes; Kafka gives it for read-from-Kafka, write-to-Kafka jobs through idempotent producers plus transactions plus read_committed consumers. For external systems you need idempotent writes or offsets stored with the results.

How to answer

Frame all three as "where is the commit relative to processing?". Then say which you would choose (at-least-once + idempotency).

Likely follow-ups
  • What does enable.auto.commit=true give you? (Neither cleanly; it can lose or duplicate.)
How do you handle duplicate messages on the consumer side?

Assume duplicates will happen, from producer retries without idempotence, consumer crashes before commit, and rebalances. Then make the handler idempotent. Options: give every event a unique ID and keep a dedup table (insert with a unique constraint, skip on conflict) or a dedup cache with a TTL longer than any plausible redelivery window; use upserts keyed by business ID so writing twice gives the same row; use a version or sequence per entity and ignore anything older than what is stored; or design state machines that ignore repeated transitions (an order already "PAID" ignores another "PAID"). For money, the dedup check and the side effect must be in one database transaction.

How to answer

Name the sources of duplicates first, then three or four techniques, then the "same transaction" point for payments.

Likely follow-ups
  • How long do you keep dedup keys? (Longer than the max retry and replay window; a TTL or partitioned table.)
What is wrong with enable.auto.commit=true, and what do you do instead?

Auto-commit commits the offsets returned by the last poll() every 5 seconds (by default), regardless of whether your code finished with them. If you hand records to another thread and the process crashes, offsets may already be committed for records you never processed: loss. If you processed records and crash before the next auto-commit: duplicates. The safer pattern is enable.auto.commit=false, process the batch, then commitSync() (or commitAsync() with a final sync commit on shutdown and in the rebalance callback). Auto-commit is fine only when processing is synchronous inside the poll loop and duplicates are harmless.

How to answer

Explain both failure modes with a timeline, then the manual commit pattern.

Likely follow-ups
  • Commit per record or per batch? (Per batch for throughput; the cost is a few more duplicates after a crash.)
What is a rebalance, why do people hate it, and how do you reduce it?

A rebalance reassigns partitions among the members of a consumer group. It is triggered when a member joins, leaves, crashes, misses heartbeats for session.timeout.ms (45 s), or fails to call poll() within max.poll.interval.ms (5 minutes). With the old eager protocol every member gave up all partitions and waited, a stop-the-world pause, and uncommitted work was redone. Ways to reduce the pain: the CooperativeStickyAssignor (only moved partitions are revoked); the new KIP-848 protocol in Kafka 4 (group.protocol=consumer, broker-side incremental assignment); static membership (group.instance.id) so a quick restart does not rebalance; and keeping processing per poll short with a smaller max.poll.records. Walmart's engineering blog described rebalancing-driven lag as a major pain at their scale.

How to answer

Triggers, why it hurts, then four fixes from simplest to newest. The routing reconvergence analogy is perfect for you.

Likely follow-ups
  • How do you avoid duplicates during a rebalance? (Commit in onPartitionsRevoked.)
Your consumers run on Kubernetes. Every deploy causes several rebalances. Why, and what helps?

A rolling update replaces pods one by one; each pod that stops leaves the group and each new pod joins, so one deploy of 10 pods can cause about 20 rebalances with the classic protocol. Fixes: static membership with group.instance.id set from the pod's stable name (works best with a StatefulSet), so a member that comes back within session.timeout.ms keeps its partitions without a rebalance; the cooperative assignor or KIP-848 so only the departing member's partitions move; a graceful shutdown that commits and closes the consumer on SIGTERM with enough terminationGracePeriodSeconds; and maxSurge/maxUnavailable settings that do not churn too many members at once.

How to answer

Do the arithmetic (two membership changes per pod), then the K8s-aware fixes. This links the K8s and Kafka tracks, which interviewers like. See Deployments.

Likely follow-ups
  • Why does a StatefulSet help? (Stable pod names make a stable group.instance.id.)
What do linger.ms and batch.size do?

The producer groups records per partition into batches in memory. A batch is sent when it reaches batch.size bytes (16 KiB by default) or when it has waited linger.ms, whichever comes first. Since Kafka 4.0 linger.ms defaults to 5 ms, up from 0. Waiting a little longer makes bigger batches, which means fewer requests and better compression (compression works per batch), so more throughput at a small latency cost. For throughput, people raise batch.size into the 64-256 KiB range, set linger.ms to 5-50 and use lz4 or zstd. For lowest latency, keep linger small.

How to answer

"Whichever comes first" is the key phrase. Then the trade-off and the 4.0 default change, which shows you are current. The school bus or interrupt coalescing analogy helps.

Likely follow-ups
  • What happens when buffer.memory (32 MiB) fills? (send() blocks up to max.block.ms, then throws: producer back-pressure.)
How does the idempotent producer work?

When it starts, the producer gets a producer ID and an epoch from the broker. Every batch it sends to a partition carries a sequence number that increases by one per batch. The broker remembers the last sequence numbers per producer and partition; if a retry arrives with a sequence it already has, it acknowledges without writing again, and if a gap appears it rejects the batch. So network retries cannot create duplicates or reorder records, even with up to 5 requests in flight. It is on by default since Kafka 3.0. The limit: it only covers retries within one producer session; if the application restarts and resends, that is a new producer ID, so you need transactions with a stable transactional.id or consumer-side dedup.

How to answer

PID, epoch, sequence per partition, broker-side check. Then the limitation. TCP sequence numbers are your bridge.

Likely follow-ups
  • Why the limit of 5 in flight? (The broker tracks a window of recent batches per producer-partition.)
How do you handle a message that keeps failing? Explain retry topics and a DLQ.

If the consumer just retries forever, one bad record (a poison pill) blocks its whole partition. Uber's published pattern is non-blocking retries: on failure, publish the record to orders.retry.1m, whose consumer waits until the record is old enough and retries; if it fails again, move it to orders.retry.10m; after the last retry, to orders.dlq. The main consumer commits and moves on. A DLQ record should carry the original payload and headers plus the error, the source topic, partition and offset, the attempt count and a timestamp. Then you need an alert on DLQ depth and a re-drive tool. The trade-off: retried records leave their partition, so ordering for that key breaks; for strictly ordered domains, use a blocking retry with backoff, or park all later records of that key too.

How to answer

Problem (poison pill), pattern (retry tiers, DLQ), DLQ contents, operations (alert, re-drive), and the ordering trade-off. That last part is the SDE-2 signal.

Likely follow-ups
  • How do you tell a poison pill from a downstream outage? (Outages fail everything, so pause the consumer instead of flooding the DLQ.)
  • Does Kafka have a built-in DLQ? (Connect sinks do; share groups got one in 4.4, KIP-1191.)
You found a bug in a consumer. How do you replay yesterday's events?

Deploy the fixed consumer, stop the group (offsets can only be reset when the group has no active members), then reset offsets by timestamp with kafka-consumer-groups.sh --reset-offsets --to-datetime, first with --dry-run, then --execute. Restart the consumers and they re-read from that point. This only works if the data is still within retention, and it only works safely if the consumer is idempotent, because records after the bug will be processed twice. If other consumers in the same group should not replay, use a new group name for the replay job instead.

How to answer

Steps in order, then the two preconditions (retention and idempotency). Show the command if you have a whiteboard.

Likely follow-ups
  • What if the data is past retention? (Tiered storage or a data lake copy; otherwise it is gone.)

A brand-new consumer group starts and sees nothing, although the topic has millions of records. Why?

auto.offset.reset decides where a group with no committed offsets starts, and its default is latest: it starts at the end and only sees new records. Set it to earliest to read from the beginning, or reset the group's offsets explicitly. The same setting bites in reverse: if a group's offsets expire (7 days after the group became empty, by default) and it is set to earliest, it silently reprocesses all retained data on restart.

How to answer

Name the setting and default immediately; then show you know the reverse trap.

Likely follow-ups
  • Which would you choose for a new analytics consumer? (Earliest, with an idempotent sink.)
How do you change an event's schema without breaking existing consumers?

Use a Schema Registry with a compatibility rule, usually BACKWARD (the default): a new schema must be able to read data written with the old one, so consumers upgrade first. In practice: add new fields with defaults, remove only fields that had defaults, never change a field's type in place, and never rename without aliases. The registry rejects an incompatible schema at deploy time instead of breaking consumers at run time. Each record carries only a small schema ID (magic byte, then a 4-byte ID). For a truly breaking change, publish to a new versioned topic and migrate consumers over.

How to answer

Tool, rule, safe changes, the breaking-change escape hatch. See Schemas & Schema Registry.

Likely follow-ups
  • BACKWARD vs FORWARD: who upgrades first? (Backward: consumers; forward: producers.)
  • Avro or Protobuf? (Both fine; Protobuf if the company already uses gRPC.)
