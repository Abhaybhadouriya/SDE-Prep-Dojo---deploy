60-second answers to the most asked questions

Practise these out loud until they flow. Each is roughly 60 seconds spoken. They are written as a person talks, not as a textbook.

1. "Why is Kafka so fast if it writes to disk?"

"Because it uses the disk the way disks like to be used. Each partition is an append-only log, so writes are sequential, with no random seeks. Kafka leans on the operating system's page cache instead of its own heap cache, so recent data is usually served from memory. When a consumer reads, the broker uses zero-copy sendfile, so bytes go from page cache to the socket without passing through user space. Producers batch and compress many records together, and the broker stores the batch as it arrived, so it never re-encodes. And partitions spread the work across brokers and disks. One caveat: with TLS on, zero-copy no longer applies because the broker must encrypt in user space."

2. "Kafka vs RabbitMQ?"

"Kafka is a distributed log: messages are kept for a retention period, consumers pull and track their own offsets, many consumer groups read the same data, and you can replay. RabbitMQ is a broker with queues: exchanges route messages by rules, the broker pushes to consumers, and a message is deleted once acked. So I use Kafka for event streams with several readers, replay, CDC and very high throughput, and RabbitMQ for task queues, complex routing and priorities at moderate volume. The line is blurring: RabbitMQ has Streams, and Kafka has share groups since 4.2. I would decide on shape and on who operates it."

3. "How does Kafka guarantee ordering?"

"Only within a partition. The producer hashes the key, murmur2 modulo the partition count by default, so every event with the same key lands in the same partition in send order. With the idempotent producer, which is on by default, order is safe even with up to five in-flight requests and retries. On the consumer side, one partition goes to one consumer in a group, so if I process it on one thread, order holds. If I parallelise inside the consumer, I must keep per-key ordering myself. There is no ordering across partitions, and adding partitions later remaps keys, so I plan the count up front."

4. "What do acks and min.insync.replicas do?"

"acks is the producer asking 'when do you tell me it is safe?'. Zero means do not wait at all; one means the leader wrote it; all means every replica currently in the in-sync set has it. But 'all' alone can mean 'just the leader' if the ISR has shrunk to one. min.insync.replicas fixes that: with 2, a write with acks=all fails with NotEnoughReplicas unless at least two replicas have it. So the standard recipe is replication factor 3, min ISR 2, acks all: you can lose one broker with no data loss and still accept writes. Lose two and the partition refuses writes rather than risk loss."

5. "Does Kafka support exactly-once?"

"Inside Kafka, yes. The idempotent producer removes duplicates from retries using a producer ID and per-partition sequence numbers. Transactions, with a stable transactional.id, let a read-process-write job atomically write output records and commit its input offsets, and read_committed consumers never see aborted data. But the guarantee stops at Kafka's edge. If my consumer writes to a database, sends an email or charges a card, I need idempotency there: an idempotency key with a unique constraint, an upsert, or storing the offset in the same database transaction as the result. So I say 'effectively once' end to end, not 'Kafka does exactly-once for me'."

6. "What is a consumer group and what is a rebalance?"

"A consumer group is a team of consumers sharing a topic. Each partition is assigned to exactly one member, so the group's maximum parallelism equals the number of partitions, and extra members sit idle. Different groups each get all the data. A rebalance is the reshuffle of partitions when a member joins, leaves or misses its deadline. In the old eager protocol everyone stopped and gave up everything, a stop-the-world pause. Cooperative rebalancing only moves the partitions that must move, and the new KIP-848 protocol in Kafka 4 lets the broker compute assignments incrementally. To avoid rebalances I keep processing under max.poll.interval.ms and use static membership for rolling restarts."

7. "How many partitions should a topic have?"

"I do the math. Take the target throughput, divide by what one partition can do on the producer side and on the consumer side, and take the larger. For example, 100 MB/s with consumers that handle 10 MB/s per partition needs at least 10 partitions; I would add headroom for two to three years of growth, because adding partitions later remaps keys and breaks per-key ordering for a while. I also check the consumer side: I need at least as many partitions as consumers I want running. And I do not go wild, because every partition costs file handles, memory, replication traffic and recovery time."

8. "Can Kafka lose data?"

"Yes, if it is configured or used carelessly. On the produce side: acks=0 or 1 with a leader crash before followers copy the data; replication factor 1; min ISR 1 with a shrunken ISR; unclean leader election, which lets a stale replica lead; or a producer that ignores send errors. On the consume side: auto-commit committing an offset before processing finishes, then a crash; or retention deleting data before a slow consumer reads it. The fixes are RF 3, min ISR 2, acks all, unclean election off, handling the send callback, committing after processing, and alerting on lag versus retention."
