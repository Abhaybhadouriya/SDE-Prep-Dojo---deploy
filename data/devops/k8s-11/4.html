The debugging flowchart

Must know (SDE-1)

Print this in your head. Start at the top-left, read the STATUS, follow the line to the matching row, and run the "first look" command. In an interview, drawing this tree is far better than listing random commands.

#STATUS you seeUsual causesFirst look
1Pending (no node or no IP yet)Requests too big for any node, taint not tolerated, affinity rules, PVC unbound, namespace quotakubectl describe pod P and read the FailedScheduling event
2ImagePullBackOff or ErrImagePullTypo in image name or tag, private registry without imagePullSecret, registry rate limit, wrong CPU architecturekubectl describe pod P and read the "Failed to pull" line
3CrashLoopBackOff (RESTARTS keeps growing)App error (exit 1), missing env var or Secret, wrong command, liveness probe too strictkubectl logs P --previous; in describe: Last State, Exit Code
4OOMKilled (Last State, exit 137)Memory limit too low, a leak, JVM heap bigger than the limit, sidecar memorykubectl describe pod P; kubectl top pod P --containers
5Running, 0/1 Ready (alive, gets no traffic)Readiness path or port wrong, app still warming up, a dependency is downdescribe: "Readiness probe failed"; curl the probe from inside the pod
6Running 1/1, but the Service is unreachableSelector labels do not match, wrong targetPort, NetworkPolicy, wrong DNS namekubectl get endpointslices -l kubernetes.io/service-name=S

Interviewers love this: "I start from the status, because the status tells me which component failed. Pending is the scheduler, ImagePullBackOff is the runtime and registry, CrashLoopBackOff is my own process, OOMKilled is the kernel enforcing my memory limit, and 0/1 Ready is my readiness probe." That one sentence shows you understand the whole pipeline.
