Logs and traces at cluster scale

Deep dive (platform teams)

Logs. The container writes to stdout and stderr. The runtime saves that to a file on the node under /var/log/pods/NAMESPACE_POD_UID/CONTAINER/0.log. The kubelet rotates these files (defaults: 10 MiB per file, 5 files per container). kubectl logs simply asks the kubelet to read that file. When the pod is deleted, or the node dies, the file is gone. That is why every production cluster runs a log agent DaemonSet (Fluent Bit, Vector, the OpenTelemetry Collector) that tails those files and ships them to central storage (Loki, Elasticsearch/OpenSearch, a cloud logging service).

  • Log in JSON with fields like level, trace_id, order_id, so you can filter instead of grep.
  • Never log secrets or full card numbers. Logs are copied to many places.
  • Do not write logs to a file inside the container. Nobody collects them and they fill the writable layer.

Traces. One checkout click may touch the gateway, the cart service, pricing, inventory, payments and Kafka. A trace is the tree of timed spans for that one request, linked by a shared trace ID passed in an HTTP header (traceparent, from the W3C Trace Context standard). Apps use an OpenTelemetry SDK, send spans to an OpenTelemetry Collector, which forwards them to Jaeger or Tempo. When p99 latency doubles, the trace shows you which hop got slow. Logs say what, metrics say how much, traces say where.

Kafka pipelines need the same three signals plus one more: consumer lag. See Pipeline observability & failure drills and Kafka operations.
