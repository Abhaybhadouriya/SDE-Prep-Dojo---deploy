No magic: which process writes each status

Must know (SDE-1)

You said you distrust magic. Good. Every word in the STATUS column was written by a specific program at a specific moment. Click Next to follow one pod's life from "just created" to "serving traffic". At each step the red tag shows the failure that appears if that step goes wrong.

  1. Scheduler. A new pod has no nodeName. The kube-scheduler watches for such pods, filters nodes (enough requested CPU/memory? taints? affinity? volume zone?) and scores the rest. If no node passes the filter, it writes a FailedScheduling event and the pod stays Pending.
  2. Kubelet. Once bound, the kubelet on that node sees the pod through a watch. It sets up volumes, asks the CNI plugin for an IP and fetches referenced ConfigMaps/Secrets. If any of that hangs, you see ContainerCreating for a long time, or CreateContainerConfigError when a Secret key is missing.
  3. Container runtime. The kubelet asks containerd (over CRI, a gRPC API) to pull the image. Wrong tag, private registry without credentials, or a registry rate limit gives ErrImagePull; after repeated failures the kubelet backs off and shows ImagePullBackOff.
  4. Your process. The image is fine and the process starts. If it exits (bad config, missing env var, crash, failing liveness probe), the kubelet restarts it with a growing delay. While it waits, the reason is CrashLoopBackOff.
  5. The kernel. If the container uses more memory than its limit, the Linux kernel's OOM killer (inside the container's cgroup) sends SIGKILL. The runtime reports it, the kubelet records OOMKilled with exit code 137, then restarts it (and may end up in CrashLoopBackOff).
  6. Readiness. The kubelet runs the readiness probe. Only when it passes is the pod marked Ready, and only then does the EndpointSlice controller add its IP behind the Service. Failing readiness gives Running 0/1: alive, but no traffic.
  7. Healthy. All gates passed: the pod is Running 1/1, listed in the Service's EndpointSlice, and kube-proxy (or Cilium) on every node now sends it traffic.

From your world

Think of a line card booting: the supervisor assigns a slot (scheduler), the card agent loads the image (runtime pull), the forwarding process starts (container), a hardware watchdog kills it if it hangs (liveness, OOM), and only after the health check passes does the route get installed into ECMP (readiness, then EndpointSlice). Where this breaks: a line card is repaired in place; a broken pod is usually replaced by a new one with a new name and IP.
