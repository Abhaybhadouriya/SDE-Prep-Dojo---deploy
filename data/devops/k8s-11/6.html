Going inside: exec, debug, and the node

Must know (SDE-1)

Modern images are often distroless (no shell, no curl, nothing). That is good for security but means kubectl exec -- sh fails. The answer is kubectl debug, which adds an ephemeral container (a temporary extra container) to the running pod. It shares the pod's network namespace, and with --target it can also see the app's processes.

$ kubectl debug -it web-7c9d8f6b5d-2xkqp --image=nicolaka/netshoot --target=web
Targeting container "web". If you don't see processes from this container it may be because the container runtime doesn't support this feature.
Defaulting debug container name to debugger-x7k2p.
If you don't see a command prompt, try pressing enter.
web-7c9d8f6b5d-2xkqp:~# ss -lntp
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       4096        127.0.0.1:8080        0.0.0.0:*
web-7c9d8f6b5d-2xkqp:~# nslookup orders.shop.svc.cluster.local
Server:         10.96.0.10
Address:        10.96.0.10#53
Name:   orders.shop.svc.cluster.local
Address: 10.96.112.40

And there is a real bug in that output: the app listens on 127.0.0.1:8080, so only processes inside the pod can reach it. Other pods cannot. The fix is to bind to 0.0.0.0.

Two more ways in:

# Copy a crashing pod, but replace its command so it stays up and you can look around
kubectl debug web-7c9d8f6b5d-8hj4n -it --copy-to=web-debug --container=web -- sh

# Get a shell on the node itself (host filesystem is mounted at /host)
kubectl debug node/node-2 -it --image=busybox:1.36
chroot /host
crictl ps -a                     # containers as the runtime sees them
crictl logs CONTAINER_ID         # logs even if the API server is down
journalctl -u kubelet --since "10 min ago"   # the kubelet's own diary

Tip: crictl is to Kubernetes nodes what docker is to your laptop: it talks straight to the runtime over CRI. When the control plane itself is sick, crictl and journalctl -u kubelet still work because they live on the node.
