The five-command toolkit

Must know (SDE-1)

You can solve most problems with five commands, used in this order. Think of it as zooming in: first the whole room, then one robot, then its diary.

  1. See the shape of the problem. kubectl get pods -o wide shows STATUS, READY, RESTARTS and which node each pod is on.
  2. Read the notice board. kubectl describe pod NAME shows the container states, the last exit code, and the Events at the bottom. Read the Events first.
  3. Read the diary. kubectl logs NAME for the current run, and kubectl logs NAME --previous for the run that just crashed.
  4. Check the thermometer. kubectl top pod and kubectl top node (needs metrics-server).
  5. Go inside. kubectl exec -it NAME -- sh, or if the image has no shell, kubectl debug to attach a toolbox container.
$ kubectl get pods -o wide
NAME                      READY   STATUS             RESTARTS      AGE     IP            NODE
web-7c9d8f6b5d-2xkqp      1/1     Running            0             12m     10.244.1.7    node-1
web-7c9d8f6b5d-8hj4n      0/1     CrashLoopBackOff   5 (32s ago)   4m10s   10.244.2.9    node-2
api-5f6c7d9b8-qwz7r       0/1     Pending            0             2m      <none>        <none>
worker-6d8f9c7b5-lm2xp    0/1     ImagePullBackOff   0             90s     10.244.1.12   node-1
report-84d7c6f9b-7tq2m    0/1     Running            0             3m      10.244.2.15   node-2

Read this output like a doctor reads a chart. Five pods, five different stories:

  • web-...2xkqp is healthy: 1/1 ready, Running, no restarts.
  • web-...8hj4n keeps dying and Kubernetes is waiting longer and longer before restarting it.
  • api-... has no node and no IP. The scheduler could not place it.
  • worker-... got a node, but the image could not be downloaded.
  • report-... is the sneaky one: it says Running but 0/1 ready. The process is alive but failing its readiness check, so it gets no traffic.

Tip: kubectl events (a proper subcommand in recent kubectl) sorts by time for you. On older clients use kubectl get events --sort-by=.lastTimestamp. Events are kept for about one hour by default (the API server flag --event-ttl defaults to 1h), so look early, or ship them to your log system.
