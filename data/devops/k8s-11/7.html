Metrics in production: metrics-server vs Prometheus

Deep dive (platform teams)

Beginners often think kubectl top is monitoring. It is not. There are two separate metric paths and they solve different problems.

metrics-server
  • Small add-on that asks every kubelet for current CPU and memory (every 15 s by default).
  • Serves the metrics.k8s.io API (stable in v1.37).
  • Feeds kubectl top and the HPA.
  • Keeps no history. Not for dashboards or alerts.
Prometheus stack
  • A time-series database that scrapes (pulls) HTTP /metrics endpoints on a schedule.
  • Stores history, has a query language (PromQL) and alert rules.
  • Usually deployed with kube-state-metrics, node-exporter, Grafana and Alertmanager (the kube-prometheus project bundles them).
  • Needs storage planning; high-cardinality labels can blow it up.

From your world

Prometheus scraping is SNMP polling: a central poller asks each device for counters on a timer. The modern equivalent of gNMI streaming telemetry is the push side (OpenTelemetry). Counters in Prometheus are monotonic, like interface octet counters, so you almost always wrap them in rate(), the same way you would compute bits per second from two SNMP polls. Where this breaks: pods come and go, so Prometheus uses Kubernetes service discovery to find new scrape targets automatically; there is no static device list.

Five PromQL queries worth memorising

# 1. Containers restarting in the last 15 minutes (crash loops)
increase(kube_pod_container_status_restarts_total[15m]) > 0

# 2. Last termination was an OOM kill
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1

# 3. CPU throttling ratio per pod (above 0.25 = throttled 1 period in 4)
sum by (pod) (rate(container_cpu_cfs_throttled_periods_total{namespace="shop"}[5m]))
  /
sum by (pod) (rate(container_cpu_cfs_periods_total{namespace="shop"}[5m]))

# 4. Pods stuck Pending
sum by (namespace) (kube_pod_status_phase{phase="Pending"}) > 0

# 5. Memory working set as a share of the limit (alert before the OOM, not after)
sum by (pod) (container_memory_working_set_bytes{namespace="shop", container!=""})
  /
sum by (pod) (kube_pod_container_resource_limits{namespace="shop", resource="memory"})

The "0.25" in query 3 is a team choice, not an official number. Pick thresholds from your own SLOs.

What to alert on: golden signals first

Google's SRE book names four golden signals for any user-facing service: latency (how long requests take), traffic (how many), errors (how many fail), saturation (how full the system is). Alert on what users feel (error rate and latency against an SLO, a promised level such as "99.9% of requests succeed"). Use pod restarts, throttling and Pending counts as diagnostic dashboards and low-urgency tickets. If you page someone every time one pod restarts, they will learn to ignore pages.

A word you will hear: p99 latency means "99% of requests were faster than this number". The average hides the slow 1%, and the slow 1% is often your most important customers (big carts, big accounts).
