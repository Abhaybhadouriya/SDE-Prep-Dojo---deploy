Each failure, up close

Must know (SDE-1)

1. Pending: the scheduler said no

A pod is Pending when it is accepted by the API server but not yet running. Most of the time it means the scheduler found no node that fits. Remember: the scheduler looks at requests (what pods ask for), not at real usage. A node can be 10% busy in reality and still be "full" because its pods requested a lot.

$ kubectl describe pod api-5f6c7d9b8-qwz7r
...
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  2m    default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient memory. preemption: 0/3 nodes are available: 1 Preemption is not helpful for scheduling, 2 No preemption victims found for incoming pod.

Read the message like a vote count: 3 nodes, 1 rejected for a taint, 2 rejected for memory. Fixes, in order of how often they are right:

  • Insufficient cpu/memory: lower the requests if they were guessed too high, or add nodes (the Cluster Autoscaler or Karpenter does this automatically when it sees Pending pods; see Scheduling & Autoscaling).
  • Untolerated taint: the node says "keep out" and your pod has no matching toleration. Often fine (control-plane nodes should repel apps).
  • Node affinity / selector mismatch: you asked for disktype=ssd and no node has that label.
  • Unbound PersistentVolumeClaim or volume node affinity conflict: the disk lives in zone A and the free nodes are in zone B. See Storage.
  • ResourceQuota exceeded: this one is sneaky, because the pod is never even created. You see the error on the ReplicaSet: kubectl describe rs.

2. ImagePullBackOff: the runtime could not download the image

$ kubectl describe pod worker-6d8f9c7b5-lm2xp | tail -6
  Normal   Pulling    50s (x3 over 90s)  kubelet  Pulling image "myrepo/worker:v1.2.3"
  Warning  Failed     49s (x3 over 89s)  kubelet  Failed to pull image "myrepo/worker:v1.2.3": rpc error: code = NotFound desc = failed to pull and unpack image "docker.io/myrepo/worker:v1.2.3": not found
  Warning  Failed     49s (x3 over 89s)  kubelet  Error: ErrImagePull
  Normal   BackOff    10s (x5 over 88s)  kubelet  Back-off pulling image "myrepo/worker:v1.2.3"
  Warning  Failed     10s (x5 over 88s)  kubelet  Error: ImagePullBackOff

The message tells you which kind of failure it is. not found means a typo or a tag nobody pushed. unauthorized or pull access denied means the node has no credentials: create a registry Secret and reference it with imagePullSecrets. 429 Too Many Requests means you hit a registry rate limit (anonymous Docker Hub pulls are limited), so use a mirror or authenticated pulls. no match for platform in manifest means you built an ARM image on a Mac and the node is x86 (see Images & Layers for multi-arch builds).

3. CrashLoopBackOff: your program keeps dying

CrashLoopBackOff is not an error by itself. It is Kubernetes saying: "your container exited, I restarted it, it exited again, so now I am waiting before I try again." The wait starts at 10 seconds and doubles each time, up to a cap of 5 minutes. If the container then runs fine for 10 minutes, the timer resets.

$ kubectl describe pod web-7c9d8f6b5d-8hj4n
...
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
      Started:      Mon, 23 Nov 2026 10:41:02 +0530
      Finished:     Mon, 23 Nov 2026 10:41:03 +0530
    Ready:          False
    Restart Count:  5

$ kubectl logs web-7c9d8f6b5d-8hj4n --previous
Starting web on :8080
FATAL: environment variable DATABASE_URL is not set

Two things to notice. First, the container ran for one second, so this is a startup failure, not a slow leak. Second, --previous is the key flag: the current container is in its waiting period and may have no logs at all; the evidence is in the one that died.

Decode the exit code before guessing:

Exit codeMeaningUsual cause
0Finished normallyThe program has nothing to do and exits. In a Deployment that looks like a crash loop (wrong command, or a script that should be a Job).
1 (or other small numbers)The app reported an errorBad config, missing env var or file, cannot connect to the database at start.
126 / 127Command not executable / not foundWrong command in the YAML, binary missing from the image, wrong architecture.
137128 + 9 = SIGKILLOOM kill, or the grace period ran out after SIGTERM, or a failed liveness probe forced a kill.
143128 + 15 = SIGTERMNormal shutdown request, for example during a rollout or a liveness restart.

Careful: a liveness probe that is too strict causes a crash loop by itself. If your app needs 40 seconds to start and the liveness probe starts checking at 10 seconds with 3 failures allowed, the kubelet kills it before it is ever ready, forever. Use a startupProbe for slow starters. Events will say Liveness probe failed ... will be restarted.

4. OOMKilled: the kernel enforced your memory limit

When you set resources.limits.memory: 512Mi, the kubelet asks the runtime to write that number into the container's cgroup file memory.max (cgroup v2). The kubelet does not police memory itself. The Linux kernel does. When the processes in that cgroup try to use more, the kernel reclaims what it can and then the OOM killer sends SIGKILL. No warning, no chance to clean up.

$ kubectl describe pod orders-6b9f7d8c4-k2l9z | grep -A4 "Last State"
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Mon, 23 Nov 2026 11:02:10 +0530
      Finished:     Mon, 23 Nov 2026 11:19:44 +0530

$ kubectl top pod orders-6b9f7d8c4-k2l9z --containers
POD                        NAME     CPU(cores)   MEMORY(bytes)
orders-6b9f7d8c4-k2l9z     orders   120m         487Mi

This one ran for 17 minutes before it died, so it is probably a slow climb (a leak, a growing cache, or a heap that is allowed to grow past the limit). Common real causes:

  • JVM or Node.js heap larger than the limit. The heap is only part of a process's memory. Threads, buffers, code cache and native libraries add more. Set the heap as a percentage of the container limit (for example -XX:MaxRAMPercentage=75), not a fixed big number.
  • A sidecar in the same pod uses memory too, but each container has its own limit, so check per container with --containers.
  • Files in emptyDir with medium: Memory (tmpfs) count against memory.

From your world

This is pure kernel. resources.limits.memory becomes memory.max in the container's cgroup v2 directory, CPU limit becomes cpu.max (CFS quota and period), and CPU request becomes cpu.weight. On cgroup v2 the kubelet also sets memory.oom.group, so an OOM kills the whole container's process group rather than one random child. You can check it on the node: cat /sys/fs/cgroup/kubepods.slice/.../memory.events shows the oom_kill counter. Where this breaks: there is a second, different killer. When the whole node runs low on memory, the kubelet (not the kernel) evicts pods, choosing BestEffort pods first. Evicted pods show status Evicted, not OOMKilled.

5. Running but not Ready: the readiness gate is closed

A readiness probe is a question the kubelet asks your container every few seconds (default every 10 s): "can you take traffic?" If the answer is no 3 times in a row (default failureThreshold), the pod is marked not Ready. Nothing is restarted. The EndpointSlice controller simply removes the pod's IP from the Service, and traffic flows only to the other pods. Watch the dots: they skip the grey pod.

$ kubectl describe pod report-84d7c6f9b-7tq2m | grep -i readiness
    Readiness:      http-get http://:8080/ready delay=0s timeout=1s period=10s #success=1 #failure=3
  Warning  Unhealthy  10s (x14 over 2m20s)  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 503

$ kubectl exec report-84d7c6f9b-7tq2m -- wget -qO- -S http://localhost:8080/ready
  HTTP/1.1 503 Service Unavailable
{"status":"waiting","reason":"cache warm-up 63% done"}

Here the probe is honest: the app really is not ready because it is still warming a cache. That is correct behaviour. The bugs are when the probe is wrong: wrong path (/health vs /healthz), wrong port (the probe hits 80, the app listens on 8080), a 1-second timeout on an endpoint that does a slow database query, or a readiness check that depends on a downstream service so all pods go unready together when that service blips. That last one turns a small outage into a total one.

From your world

Readiness is a BFD session or IP SLA tracker that withdraws a route from an ECMP group without rebooting anything. Liveness is a hardware watchdog that reboots a hung process. You would never wire your watchdog to "is the upstream router reachable?", because then one upstream failure reboots every box. Same rule here: never put dependency checks in a liveness probe.

6. Running 1/1, but the Service does not answer

Debug this bottom-up, exactly like you would debug a network path. Stop at the first layer that is broken.

  1. Does the pod answer by itself? kubectl port-forward pod/P 8080:8080 then curl localhost:8080. If not, it is the app (listening on 127.0.0.1 instead of 0.0.0.0 is a classic).
  2. Does the Service have endpoints? kubectl get endpointslices -l kubernetes.io/service-name=S. Empty means the Service selector does not match the pod labels, or no pod is Ready.
  3. Is the port mapping right? Service port is what clients call; targetPort must equal the port the container listens on.
  4. Does DNS resolve? From a debug pod: nslookup S.NAMESPACE.svc.cluster.local. Cross-namespace calls need the namespace in the name.
  5. Is a NetworkPolicy blocking it? kubectl get networkpolicy -A. A default-deny policy without an allow rule drops the traffic silently. See Security & RBAC.
  6. Is the node data plane healthy? kube-proxy or Cilium pods running on that node? CNI pods healthy? See Services & Networking.
$ kubectl get endpointslices -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-x7k2p   IPv4          <unset>   <unset>     3d

$ kubectl get svc web -o jsonpath='{.spec.selector}'; echo
{"app":"web"}
$ kubectl get pods --show-labels | grep web
web-7c9d8f6b5d-2xkqp   1/1   Running   0   12m   app=web-frontend,pod-template-hash=7c9d8f6b5d

Found it: the Service selects app=web but the pods are labelled app=web-frontend. The Service is a phone number that rings nobody.
