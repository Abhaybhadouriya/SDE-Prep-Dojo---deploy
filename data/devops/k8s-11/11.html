A pod is in CrashLoopBackOff. Walk me through how you debug it.

"CrashLoopBackOff means the container keeps exiting and the kubelet is waiting longer between restarts, so the question is why does my process exit. First I run kubectl describe pod and look at Last State: the exit code and how long it ran. Exit 1 after one second says startup config; 137 says SIGKILL, usually OOM or a liveness kill; 0 says the command finishes and should maybe be a Job. Then kubectl logs --previous to read the crashed container's output. Then I check the Events for liveness failures, and the spec for a missing env var, Secret, or wrong command. If the image has no shell I use kubectl debug --copy-to with the command replaced by sleep so I can look around. Once fixed, I would add an alert on restart rate so we notice earlier next time."

How to answer

Define it in one line, then go evidence first: exit code, previous logs, events, spec. Show that you decode exit codes. Finish with prevention.

Likely follow-ups
  • Why is the wait getting longer? (10 s doubling to a 5-minute cap.)
  • Logs are empty. Now what? (Crash before logging: check command, image architecture, permissions; use --copy-to.)
Pods are stuck in Pending. What are the possible causes?

"Pending means no node accepted it yet, so I read the scheduler's FailedScheduling event, which lists why each node was rejected. Typical reasons: total CPU or memory requests do not fit on any node; a taint the pod does not tolerate; node selector or affinity that no node matches; a PVC that is not bound or a zone conflict between the disk and the nodes; or pod anti-affinity that cannot be satisfied. If there is no pod at all, I check the ReplicaSet for a ResourceQuota error. If the cluster autoscaler is installed, I check whether it tried to add a node and why it could not, for example hitting the node group's max size."

How to answer

Say "scheduler" and "requests, not usage" early. Group the causes: resources, rules (taints, affinity), storage, quota.

Likely follow-ups
  • The node shows 20% CPU used but the pod will not fit. Why? (Scheduling uses requests.)
  • How does the Cluster Autoscaler react to Pending pods?
Latency spikes every few seconds, but the pod's CPU usage looks low. What is going on?

"My first suspect is CPU throttling from a CPU limit. A CPU limit becomes a CFS quota in the cgroup's cpu.max: for example 200 ms of CPU every 100 ms period for a 2-core limit. A multi-threaded app can burn the whole quota in the first part of the period, then all its threads are paused until the next period starts. Average usage looks low because it is averaged over seconds, but individual requests stall. I would confirm with container_cpu_cfs_throttled_periods_total divided by container_cpu_cfs_periods_total. The fix is to raise or remove the CPU limit while keeping a sensible CPU request, or reduce thread counts so they match the limit. For JVMs, check that the runtime sees the right CPU count."

How to answer

Name the mechanism (CFS quota per period), explain why averages hide it, name the metric that proves it, then give the fix and its trade-off (noisy neighbours without limits).

Likely follow-ups
  • If you remove CPU limits, what protects other pods? (CPU requests become cpu.weight, which still gives fair share under contention.)
  • Why not do the same for memory? (Memory cannot be throttled; without a limit one leak can push the whole node into eviction.)
What is the difference between liveness, readiness and startup probes, and how can a wrong probe cause an outage?

"Readiness decides traffic: if it fails, the pod's IP is removed from the Service endpoints but the container is not touched. Liveness decides life: if it fails enough times, the kubelet restarts the container. A startup probe runs first and holds the other two off until the app has finished booting. Wrong probes hurt in two classic ways. A liveness probe that checks a shared dependency like the database will restart every pod when the database is slow, which turns a slowdown into an outage. And a liveness probe that starts too early on a slow-starting app causes an endless CrashLoopBackOff. My rule: liveness checks only 'is this process stuck', readiness can include 'am I able to serve right now', and slow starters get a startup probe."

How to answer

One line per probe saying what the kubelet does on failure. Then the two failure stories. Then your rule.

Likely follow-ups
  • Should readiness check the database? (Debatable: only if this pod truly cannot serve anything without it, and be aware all pods go unready together.)
  • What are the default probe timings? (period 10 s, timeout 1 s, failureThreshold 3.)
How would you set up monitoring and alerting for a Kubernetes platform?

"Three layers. For apps: each service exposes RED metrics (rate, errors, duration) and logs in JSON with a trace ID; I alert on SLO burn, meaning error rate and p99 latency against what we promised users. For Kubernetes objects: kube-state-metrics gives restarts, Pending pods, unavailable replicas, failed Jobs; those go to dashboards and lower-urgency alerts. For the platform: node-exporter for nodes, plus control-plane metrics such as API server request latency and 429/5xx rates, etcd health and disk latency. Prometheus scrapes all of it, Grafana shows it, Alertmanager routes pages. Logs go through a Fluent Bit DaemonSet into Loki or Elasticsearch, traces via the OpenTelemetry Collector. metrics-server is only for kubectl top and the HPA."

How to answer

Layer it (app, objects, platform), say what pages a human versus what goes to a dashboard, and mention one control-plane signal; that shows maturity.

Likely follow-ups
  • How do you avoid alert fatigue?
  • What is high cardinality and why does it hurt Prometheus? (A label like user_id creates one time series per user.)

Scenario: after a Friday deploy, 30% of requests return 502

A new version of the checkout service rolled out 10 minutes ago. Dashboards show 30% of requests failing with 502 at the gateway. Pods show Running. What do you do?

Weak answer: "I would delete the pods so they restart, and check the logs."

Strong answer: "Users are hurting and the change is recent, so I roll back first with kubectl rollout undo deployment/checkout (or revert the GitOps commit) and watch the error rate return to normal. Then I debug calmly. kubectl get pods: are new pods 1/1 Ready or 0/1? A 30% failure rate during a rollout often means new pods were added to the Service before they could really serve, so I check the readiness probe exists and hits a real endpoint. I also check shutdown: if old pods die without a preStop delay and graceful SIGTERM handling, in-flight requests get cut. Then events, logs, and a trace of one failing request to see which hop returns the error. Finally, a blameless review: add readiness gates and canary analysis so a bad version stops at 5% of traffic."

Likely follow-ups
  • How would you detect this automatically? (Canary with metric analysis, for example Argo Rollouts; progressDeadlineSeconds.)
  • Why can pods get traffic after they receive SIGTERM? (Endpoint removal and SIGTERM happen in parallel.)

Your 60-second answer, "How do you troubleshoot Kubernetes?": "I start from the pod status, because each status points to one component. Pending is the scheduler, so I read FailedScheduling in describe. ImagePullBackOff is the runtime and registry: tag, credentials, rate limits. CrashLoopBackOff is my own process: exit code and logs --previous. OOMKilled is the kernel enforcing the memory limit: exit 137, so I compare usage to the limit. Running but not Ready is the readiness probe, and Running and Ready but unreachable means I check the Service's EndpointSlices, ports, DNS and NetworkPolicies, bottom-up like a network path. Behind all of it I rely on Prometheus metrics, central logs and traces, because pods are short-lived and their evidence disappears with them."
