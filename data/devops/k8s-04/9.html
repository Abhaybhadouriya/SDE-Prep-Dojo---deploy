Internals and production lessons

Deep dive (platform teams)

What the Deployment controller actually loops over

  1. Hash the template. It computes a hash of spec.template and looks for a ReplicaSet whose pod-template-hash label matches. None? Create one with 0 replicas.
  2. Do the arithmetic. Count available pods across all its ReplicaSets, then scale the new one up by at most replicas + maxSurge - total and old ones down by at most available - (replicas - maxUnavailable).
  3. Wait for readiness. It only proceeds when new pods become available (Ready for minReadySeconds). That is why a broken readiness probe "stalls" a rollout rather than breaking the whole app: old pods stay.
  4. Report progress. It updates the Progressing condition. If no progress happens within progressDeadlineSeconds (default 600), it sets reason: ProgressDeadlineExceeded. It does not roll back by itself; your CD pipeline must read that and act.
  5. Clean up. It keeps the newest revisionHistoryLimit (default 10) old ReplicaSets and lets garbage collection remove the rest. Deleting the Deployment deletes its ReplicaSets and pods through ownerReferences (cascading deletion).
$ kubectl set image deployment/web web=nginx:does-not-exist
$ kubectl get pods -l app=web
NAME                   READY   STATUS             RESTARTS   AGE
web-84c5d9f6b7-6x2vq   1/1     Running            0          9m
web-84c5d9f6b7-c8wlm   1/1     Running            0          9m
web-84c5d9f6b7-pq7zn   1/1     Running            0          9m
web-7b9f8d5c4d-hh2km   0/1     ImagePullBackOff   0          45s

$ kubectl rollout undo deployment/web
deployment.apps/web rolled back

Notice how maxUnavailable: 0 saved us: the broken pod never became Ready, so no old pod was removed. Users saw nothing. With maxUnavailable: 1 (or the 25% default on 4 or more replicas) one old pod would already have been killed and the Deployment would be running below full capacity. On our 3 replicas the 25% default rounds down to 0, so it would also have been safe here.

Real-world lessons

  • Automatic rollback signals. Uber's migration write-up describes a rollback rule of "more than 10% of pods restarting 5 or more times", and notes that disabled health checks hid crash loops (see Uber engineering blog). Lesson: a rollout tool is only as good as the health signal you feed it.
  • Progressive delivery. Tools such as Argo Rollouts and Flagger replace the Deployment's simple arithmetic with steps like "5% for 10 minutes, check error rate in Prometheus, then 25%..." and roll back automatically.
  • Selector is immutable. In apps/v1 you cannot change spec.selector after creation. Renaming the app label means a new Deployment.
  • HPA owns replicas. If an autoscaler (HPA, see Scheduling & Autoscaling) manages the Deployment, remove replicas from your YAML. Otherwise every kubectl apply resets the count to the file's number, and you may suddenly shrink from 40 pods to 3 at peak.
  • Kafka consumers are a classic Deployment. Every new consumer pod triggers a consumer-group rebalance. A rolling update of 30 consumers can cause 30+ rebalances; cooperative rebalancing and static membership reduce the pain. On Kafka 4.x, set group.protocol=consumer (KIP-848). The broker then assigns partitions incrementally, with no group-wide stop-the-world rebalance, so rolling updates and KEDA scale events barely pause consumption. See Kafka consumer groups and Deploying the pipeline on K8s.
