What is the difference between a Pod, a ReplicaSet and a Deployment?

A pod is one running instance. A ReplicaSet keeps a fixed number of identical pods alive by label selector - it only counts and fixes. A Deployment sits on top and manages ReplicaSets over time: one ReplicaSet per version of the pod template, so an upgrade scales the new one up and the old one down, and a rollback scales the old one back up. In practice you only write Deployments; ReplicaSets are an implementation detail you see in kubectl get rs.

How to answer

Go bottom-up in three sentences, one job per layer, then say "rollback is just scaling an old ReplicaSet" - that one line shows you understand why the middle layer exists.

Likely follow-ups
  • What happens if you delete a ReplicaSet owned by a Deployment? (The Deployment recreates it.)
  • How does a ReplicaSet know which pods are "its"? (Selector + ownerReferences.)
How does a rolling update avoid downtime? Explain maxSurge and maxUnavailable.

The Deployment controller creates a new ReplicaSet and shifts pods across in small batches. maxSurge is how many extra pods may exist above the desired count; maxUnavailable is how many may be missing. Defaults are 25% each (surge rounds up, unavailable rounds down). It only removes old pods once new ones are available, meaning their readiness probe passed for minReadySeconds. For a critical service I use surge 1, unavailable 0. But true zero downtime also needs graceful SIGTERM handling, a preStop delay so endpoint removal propagates, and backward-compatible changes because both versions serve at once.

How to answer

Define both knobs with a worked number (replicas 4 -> max 5 pods, min 3 available). Then volunteer the three hidden requirements - that is what separates SDE-2 from SDE-1.

Likely follow-ups
  • Can both be 0? (No - no progress possible.)
  • What if the new version never gets Ready? (Rollout stalls, old pods keep serving, ProgressDeadlineExceeded after 600 s.)
A deploy just went out and error rates jumped. What do you do, and how would you detect it automatically next time?

First mitigate, then investigate: kubectl rollout undo deployment/x (or revert the commit in a GitOps repo so the cluster does not drift back). That scales the previous ReplicaSet up immediately. Then look at kubectl rollout history, pod logs with --previous, events, and the diff between revisions. For next time: canary releases with automated analysis (Argo Rollouts or Flagger reading Prometheus error rate and latency), alerts on ProgressDeadlineExceeded, and rollback triggers such as restart counts - Uber described using "over 10% of pods restarting 5+ times".

How to answer

Say "roll back first, debug second" in the first sentence. Interviewers at Amazon especially look for customer-first mitigation. Then show you would make detection automatic.

Likely follow-ups
  • What if the new version ran a DB migration? (Rollback of code may not undo schema; that is why expand/contract matters.)
  • Does the Deployment roll back by itself? (No.)
How would you do canary or blue/green on Kubernetes?

Both use two Deployments (stable and new). Blue/green: a Service or route points at one color via its selector; once green passes checks, flip the selector; flip back to roll back. It costs double capacity briefly. Canary: send a small weight (say 5%) to the new version using a Gateway API HTTPRoute with weighted backendRefs, or a service mesh; watch error rate and latency; increase in steps. Without extra tooling, a replica-ratio canary (9 stable + 1 canary pods behind one Service) gives roughly 10%. Argo Rollouts or Flagger automate the steps and the rollback.

How to answer

Draw two boxes and a switch for blue/green, two boxes and a dial for canary. Mention the metric you would watch - without it a canary is pointless.

Likely follow-ups
  • How do you canary a Kafka consumer? (Traffic splitting does not apply; use a separate consumer group on a mirrored topic or a small share of partitions.)
  • How do sticky sessions affect canaries?
Deployment vs DaemonSet vs StatefulSet vs Job - pick one for: a REST API, a log shipper, a Kafka broker, a DB migration.

REST API: Deployment, because pods are interchangeable. Log shipper: DaemonSet, because the work is per node. Kafka broker: StatefulSet, because each broker needs a stable identity (kafka-0) and its own disk; usually managed by an operator such as Strimzi. DB migration: Job, because it must run to completion once, with retries.

How to answer

Give the rule first ("interchangeable / per node / identity + data / has an end"), then map each workload.

Likely follow-ups
  • Why not run the migration as an init container? (Every replica would run it, concurrently.)
  • Can a Deployment use a PVC? (Yes, but with RWO all replicas share one claim - usually wrong.)

Scenario: every deploy causes about 30 seconds of 502 errors

The team uses a standard Deployment with defaults. Each release, the load balancer logs show a burst of 502/503 responses, then everything is fine.

Weak answer: "Increase replicas so there are more pods."

Strong answer: "Errors at both ends of a pod's life. At start: is there a readiness probe, and does it reflect that the app can serve? At stop: does the app handle SIGTERM (exec-form CMD, not a shell), and is there a preStop sleep so kube-proxy and the external LB stop sending traffic before the process exits? I would also set maxUnavailable to 0 and check the LB's own health-check and deregistration delay, which is often longer than Kubernetes' grace period."

Likely follow-ups
  • How long should the preStop sleep be? (A few seconds, tuned to how fast endpoints propagate; it must fit inside terminationGracePeriodSeconds.)

60-second answer - "What is a Deployment?"
"A Deployment is the object I use to run a stateless service on Kubernetes. I declare the pod template and how many replicas I want. Under the hood it creates a ReplicaSet for each version of the template, and the ReplicaSet controller in the controller manager keeps that many pods alive by watching the API server - if a pod dies it creates a new one, the scheduler places it, and the kubelet starts it. When I change the image, the Deployment does a rolling update bounded by maxSurge and maxUnavailable, and only moves on when new pods pass their readiness probe. The old ReplicaSet is kept at zero, so kubectl rollout undo is near-instant. For zero downtime I also need graceful shutdown, a preStop delay and backward-compatible changes."
