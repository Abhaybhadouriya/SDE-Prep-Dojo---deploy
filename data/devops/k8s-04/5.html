Truly zero downtime: the four things that must be true

Must know (SDE-1)

A rolling update alone does not guarantee zero errors. Many teams see a burst of 502s on every deploy. These are the four ingredients, and what goes wrong without each:

  1. Readiness probe - without it, a pod receives traffic the moment its container starts, before the app has opened its port or warmed caches. Users get "connection refused".
  2. Graceful shutdown on SIGTERM - when an old pod is removed, the kubelet sends SIGTERM, waits terminationGracePeriodSeconds (default 30 s), then SIGKILL. Your app must stop accepting new work, finish in-flight requests, and exit. An app that dies instantly on SIGTERM drops requests.
  3. A short preStop sleep - removing the pod from the Service endpoints and sending SIGTERM happen in parallel. kube-proxy on every node takes a moment to update its rules, so some requests still arrive after SIGTERM. A preStop: sleep 5 keeps the pod serving until the network catches up.
  4. maxUnavailable: 0 plus enough capacity - so you never run below the replica count, and a PodDisruptionBudget so node drains do not take too many pods at once.
    spec:
      terminationGracePeriodSeconds: 40
      containers:
      - name: web
        image: myorg/web:2.3.1
        lifecycle:
          preStop:
            sleep:
              seconds: 5        # native sleep action (K8s 1.30+); older clusters use exec: ["sleep","5"]
        readinessProbe:
          httpGet: { path: /healthz/ready, port: 8080 }
          periodSeconds: 5
          failureThreshold: 2

Interviewers love this: "Rolling updates give zero downtime only if readiness is honest, the app handles SIGTERM, and endpoint removal is allowed to propagate before the process stops. And the old and new versions run side by side, so the API and DB schema must be backward compatible."
