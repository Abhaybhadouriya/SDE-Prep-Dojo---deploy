Packaging: Helm and Kustomize

Must know (SDE-1)

By now you have written a Deployment, a Service, maybe a ConfigMap and a PDB. A real app has ten of these files, and you need slightly different copies for dev, staging and production (3 replicas here, 40 there; a different image tag; a different hostname). Copy-pasting YAML for each environment goes wrong fast. Two tools solve this, and you will see both in every job.

Explain like I'm 5

A Helm chart is a cake recipe with blanks: "add ___ cups of sugar, bake for ___ minutes". The values file fills in the blanks. Same recipe, a small cake for a birthday and a big one for a wedding. Kustomize is different: you bake one normal cake, then for the wedding you put a note on top saying "make this one twice as big". You patch a finished thing instead of filling in blanks.

Three words to know: a chart is the package (a folder of templates plus a default values.yaml), a release is one installed copy of a chart in a cluster, with a name you choose, and a revision is one version of that release (every upgrade or rollback adds one). Charts are shared through chart repositories and, more and more, as OCI artifacts in the same registries that hold container images.

Lab: install, upgrade and roll back a chart on kind

Install the Helm CLI (winget install Helm.Helm, brew install helm or the install script on helm.sh). We use podinfo, a tiny demo web app whose chart is published as an OCI artifact on GitHub's container registry.

helm install demo oci://ghcr.io/stefanprodan/charts/podinfo --set replicaCount=2
helm list
kubectl get deploy,svc -l app.kubernetes.io/instance=demo

helm upgrade demo oci://ghcr.io/stefanprodan/charts/podinfo --set replicaCount=3
helm history demo
helm rollback demo 1          # back to 2 replicas; this creates revision 3, a copy of revision 1

# see the YAML a chart would send, without applying anything
helm template demo oci://ghcr.io/stefanprodan/charts/podinfo --set replicaCount=5 | head -40
helm uninstall demo

Habit worth having: run helm template (or the popular helm diff plugin) before every upgrade. A chart is someone else's code; look at the YAML it will actually send.

Kustomize: patches instead of templates

Kustomize is built into kubectl (kubectl apply -k). You keep one plain base and a small overlay per environment:

# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base              # base/ holds a normal deployment.yaml and service.yaml
images:
  - name: myorg/web
    newTag: "2.4.1"
patches:
  - target:
      kind: Deployment
      name: web
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 40
kubectl kustomize overlays/prod      # print the final YAML
kubectl apply -k overlays/prod       # apply it

From your world

Helm is like a router config template rendered per site from a variables file (the Jinja templates many network-automation teams use), plus a package manager's install history. Kustomize is like keeping one golden config and applying a small per-site diff. Where the analogy breaks: Helm also records what it installed, so helm uninstall removes exactly those objects; a plain template renderer would not know what it created.

Interviewers love this: "Why is YAML templated?" Answer: one app, many environments; templating (Helm) or patching (Kustomize) keeps one source of truth. Then give the trade-off: Helm is best for distributing software to other teams and strangers, Kustomize for your own services, and many teams use both (GitOps tools such as Argo CD can render either).
