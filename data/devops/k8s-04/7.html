The family: DaemonSet, Job, CronJob, StatefulSet

Must know (SDE-1)

You might ask: "why so many controllers?" The answer is simple: each one encodes a different promise about pods.

ControllerIts promiseTypical usePick it when...
DeploymentN interchangeable pods, versioned rolloutsWeb APIs, stateless workers, Kafka consumersAny pod can die and be replaced by any other
StatefulSetStable names (kafka-0), own disk per pod, ordered startKafka brokers, databases, ZooKeeperEach replica has an identity and data (see StatefulSets & Operators)
DaemonSetExactly one pod on every (matching) nodeLog shippers, node-exporter (host metrics agent, page 11), CNI agent, CSI node plugin (the per-node storage driver, page 08), kube-proxyThe work is "per machine"
JobRun pods until N succeed, retry on failure (backoffLimit, default 6)DB migration, batch report, one-off backfillThe work has an end
CronJobCreate a Job on a scheduleNightly cleanup, hourly exportThe work has an end and repeats

From your world

A DaemonSet is "a process that must run on every line card" - like a local telemetry agent or a per-card health daemon. Add a card (node) to the chassis and the agent appears on it automatically. A Job is like a one-shot diagnostic you run on a card: it must finish, and you care about its exit code.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"           # 02:00 every day (controller's time zone unless spec.timeZone set)
  concurrencyPolicy: Forbid       # do not start a new run while the old one is still going
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report
            image: myorg/report:1.4
            args: ["--date", "yesterday"]

PodDisruptionBudget: protect replicas from "polite" disruptions

When an admin drains a node (for an OS patch or a cluster upgrade), Kubernetes evicts its pods. A PodDisruptionBudget (PDB) says "never voluntarily take my app below this many pods". The drain then waits instead of evicting too much. A PDB does not protect against involuntary disruptions such as a node crashing.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2          # or maxUnavailable: 1
  selector:
    matchLabels:
      app: web

Careful: a PDB with minAvailable equal to replicas (for example 3 of 3) blocks every drain forever. Cluster upgrades then hang. Leave room for at least one pod to move.
