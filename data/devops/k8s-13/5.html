Advanced questions (SDE-2 and platform teams)

How do pods on different nodes talk? Overlay vs routed networking; Flannel vs Calico vs Cilium.

"The Kubernetes model says every pod gets its own IP and can reach every other pod without NAT; the CNI plugin makes that true. Each node gets a pod CIDR. In overlay mode, like Flannel's default VXLAN, a packet to a pod on another node is encapsulated in UDP to that node's IP, which works on any underlay but costs about 50 bytes of header, so the pod MTU must be lower, plus some CPU. In routed mode, like Calico with BGP, each node advertises its pod CIDR to the fabric or to route reflectors, so packets are routed natively with no encapsulation. Cilium uses eBPF in the kernel for the datapath, can replace kube-proxy, adds L7-aware policy and Hubble flow visibility. Cloud CNIs like the AWS VPC CNI give pods real VPC IPs, which is fast but can exhaust subnet addresses."

How to answer

This is your strongest question. Use VTEP, MTU, BGP and route-reflector vocabulary naturally. Mention a trade-off for each. Then stop; do not lecture.

Likely follow-ups
  • Where did route reflectors bite someone? (Reddit's 2023 outage.)
  • Why did OpenAI move off Flannel at 7,500 nodes? (Overlay throughput; they used native pod networking.)
kube-proxy modes: iptables vs IPVS vs nftables vs eBPF. Which would you pick?

"iptables mode is still the default in v1.37: rules are chains walked in order, with random-probability backend selection, and big clusters suffer because updates rewrite large rule sets and matching is linear. IPVS uses the kernel's L4 load balancer with hash tables, but it is deprecated since v1.35 with removal planned around v1.40. nftables mode is GA since v1.33 and the recommended direction: verdict maps give hash lookups and incremental updates, and it needs a reasonably new kernel (5.13+). Cilium's eBPF mode replaces kube-proxy entirely. For a new large cluster I would pick nftables, or Cilium if we want its policy and observability features too."

How to answer

Compare by data structure (linear chain vs hash), update cost and status (default, deprecated, recommended). The ACL-vs-TCAM analogy works.

Likely follow-ups
  • What breaks if kube-proxy on one node dies? (Existing rules stay; new Service changes are not applied on that node.)
Why do DNS lookups from pods sometimes cause latency, and how do you fix it?

"Pods get an /etc/resolv.conf with several search domains and ndots:5. Any name with fewer than five dots is tried with each search suffix first, so a lookup of api.payments.com becomes several failed queries like api.payments.com.shop.svc.cluster.local before the real one, each for A and AAAA. Under load this multiplies DNS traffic, and conntrack races on UDP can add multi-second timeouts. Fixes: use fully qualified names with a trailing dot for external hosts, lower ndots through the pod's dnsConfig, run NodeLocal DNSCache so lookups stay on the node, and scale CoreDNS."

How to answer

Explain the mechanism (search list x ndots), quantify roughly, list fixes cheapest first. This appears in many public failure stories.

Likely follow-ups
  • How would you prove DNS is the problem? (Latency breakdown in traces, CoreDNS metrics, tcpdump on port 53.)
A node dies. What happens, which components act, and how long does it take?

"The kubelet renews a Lease object as its heartbeat. The node lifecycle controller in the controller-manager notices missed heartbeats and after the grace period, 50 seconds in current defaults, marks the node NotReady or Unknown and taints it. Pods get default tolerations for those taints of 300 seconds, so after about five minutes they are evicted. Their ReplicaSets then create replacements, which the scheduler places on healthy nodes. So by default, pods on a dead node take roughly five to six minutes to come back elsewhere, plus image pull and startup. You can shorten tolerationSeconds per pod for faster failover, at the cost of more churn on short network blips."

How to answer

Name each actor in order, give the two default numbers, then the trade-off. These are hold-down timers, which you know well.

Likely follow-ups
  • Is the same true for StatefulSet pods? (No, next question.)
  • How do you make sure traffic stops going to that node immediately? (Readiness and endpoints update when the node goes NotReady.)
What happens to a StatefulSet pod when its node becomes unreachable?

"It is not replaced automatically. A StatefulSet promises at most one pod per identity, like kafka-1 with its own disk. If the node is only partitioned, the old pod might still be running and writing to its volume, so starting a second kafka-1 could corrupt data. Kubernetes waits until it is sure: the node object is deleted, the node comes back, or an operator force-deletes the pod. Deployments do not have this rule and simply create replacements. This is why stateful systems on Kubernetes rely on operators and on the application's own replication, like Kafka's ISR, for availability."

How to answer

Name the guarantee (at most one), explain split-brain risk, give the manual and automated ways out.

Likely follow-ups
  • What is the risk of force-deleting it?
  • How does non-graceful node shutdown handling help? (An out-of-service taint tells Kubernetes the node is really gone.)
p99 latency spikes but CPU usage looks low. What is happening?

"Most likely CPU throttling from a CPU limit. The limit becomes a CFS quota per 100 ms period in the cgroup's cpu.max. A multi-threaded app can use its whole quota in the first few milliseconds, then every thread is paused until the next period, so some requests wait tens of milliseconds. Averaged over a minute, usage looks low. I would prove it with container_cpu_cfs_throttled_periods_total over container_cpu_cfs_periods_total. Fixes: raise or remove CPU limits while keeping CPU requests, which still give a fair share under contention, and size thread pools to the CPU the container really has."

How to answer

Mechanism, why averages hide it, the metric that proves it, the fix and its trade-off.

Likely follow-ups
  • Without CPU limits, what stops a noisy neighbour? (Requests become cpu.weight; contention is shared proportionally.)
The app "only uses 300 MB" but keeps getting OOMKilled with a 512 Mi limit. Why?

"'Uses 300 MB' is usually the heap the app reports, not what the kernel counts. The cgroup counts the whole process: heap, thread stacks, JIT and code cache, direct buffers, native libraries, plus page cache attributed to the container, and any tmpfs volumes. A JVM with a fixed big -Xmx or an old runtime that does not read cgroup limits can also size itself for the whole node. I would compare container_memory_working_set_bytes to the limit over time, check per-container usage including sidecars, set heap as a percentage of the container limit, and then either right-size the limit or fix the leak."

How to answer

Distinguish "app-reported" from "kernel-counted" memory. Then evidence, then fix.

Likely follow-ups
  • How is OOMKilled different from Evicted?
  • Why does exit code 137 appear?
HPA vs VPA vs Cluster Autoscaler vs Karpenter vs KEDA.

"HPA changes the number of pods based on a metric. VPA changes the size of pods, their requests, based on observed usage, and can now resize in place since in-place resize is GA in v1.35; do not run it on the same CPU or memory metric as an HPA. The Cluster Autoscaler changes the number of nodes: it adds nodes from predefined node groups when pods are Pending and removes underused ones. Karpenter does the same job without fixed node groups: it looks at the pending pods and launches the best-fitting instance types directly, and consolidates onto cheaper nodes. KEDA is event-driven: it scales on things like Kafka consumer lag or queue depth and can scale to zero, driving an HPA underneath."

How to answer

Sort them by what they change: pod count, pod size, node count. Then where KEDA fits.

Likely follow-ups
  • Why is node scale-up slower than pod scale-up, and what do you do about it? (Overprovisioning with low-priority placeholder pods.)
What is an Operator / CRD? Give a real example.

"A CRD, CustomResourceDefinition, adds a new type to the Kubernetes API, like Kafka or PostgresCluster. An operator is a controller that reconciles that type, encoding the knowledge a human operator would apply. Strimzi is a good example: I write a Kafka resource saying three brokers, this version, this storage, and the operator creates the StatefulSet-like pods, Services, certificates and configs, performs rolling upgrades broker by broker, and handles config changes safely. Other examples are the Prometheus Operator, cert-manager and CloudNativePG. It is the same reconcile-loop idea as built-in controllers, applied to your own domain."

How to answer

CRD = new noun, operator = the loop that acts on it. One concrete example with what it automates. See StatefulSets & Operators and Kafka on Kubernetes with Strimzi.

Likely follow-ups
  • How would you write one? (Kubebuilder or Operator SDK on controller-runtime.)
  • What makes a reconcile function correct? (Idempotent, level-triggered, uses status and conditions.)
Users see errors during every deploy even with rolling updates. Why, and how do you get true zero downtime?

"Usually two races. On startup, pods get traffic before they can really serve, because there is no readiness probe or it checks too little. On shutdown, when a pod is deleted, the kubelet sends SIGTERM at the same time as the endpoint is being removed; kube-proxy on other nodes may keep sending new connections for a moment, and if the app exits immediately those requests fail. The fixes: a real readiness probe; a preStop hook that sleeps a few seconds so endpoint removal propagates; the app handling SIGTERM by finishing in-flight requests; terminationGracePeriodSeconds long enough; maxUnavailable 0; a PodDisruptionBudget; and backward-compatible database migrations (expand, then contract)."

How to answer

Name both races explicitly; most candidates only know the first. Then list fixes in order of the pod lifecycle.

Likely follow-ups
  • What is the default grace period? (30 s.)
  • How do long-lived connections like WebSockets change this?
How do you do canary and blue/green deployments on Kubernetes?

"Blue/green: run two Deployments, blue (current) and green (new), and switch the Service selector or the route from blue to green in one step once green is verified; rollback is switching back. Canary: send a small share of traffic, say 5%, to the new version, watch error rate and latency, then increase. A plain Service can only split by replica ratio, so for precise weights I use a Gateway API HTTPRoute with weighted backends, or a service mesh. Tools like Argo Rollouts or Flagger automate the steps and run metric analysis against Prometheus, rolling back automatically if the canary is worse."

How to answer

Define both, say what Kubernetes gives natively and what needs a tool, mention automated analysis.

Likely follow-ups
  • What signal decides the canary is bad?
  • Cost of blue/green? (Double capacity during the switch.)
How do you upgrade a production cluster safely?

"Read the release notes for removals and deprecated APIs first, and scan manifests and Helm charts for them. Back up etcd, because there is no supported downgrade. Upgrade a non-critical cluster first. Then the control plane, one minor version at a time, then node pools: the kubelet may be up to three minor versions older than the API server but never newer. For nodes I add new upgraded nodes, cordon and drain old ones respecting PodDisruptionBudgets, and watch dashboards between batches. Everything, including add-on configuration, lives in git, so nothing hidden can surprise us; that hidden-config problem is exactly what caused Reddit's 2023 outage."

How to answer

Before, during, after. Name version skew and "no downgrade". A real incident makes it memorable.

Likely follow-ups
  • What does kubectl drain do? (Cordon, then evict pods through the eviction API, which respects PDBs.)
  • Blue/green clusters instead of in-place upgrades?
What is a sidecar and a service mesh? When is a mesh worth it?

"A sidecar is a helper container in the same pod as the app, for example an Envoy proxy. A service mesh like Istio or Linkerd puts such a proxy next to every service, or uses a per-node or ambient mode, and gives you mutual TLS between services, retries, timeouts, traffic splitting and per-request metrics without changing app code. The cost is extra latency per hop, more memory, and a complex control plane to operate. I would adopt one when we have many services and need mTLS and consistent traffic policy everywhere; for a handful of services, libraries and Gateway API are simpler. Since v1.33, native sidecars start before and stop after the app container, which fixed the old problem of Jobs never finishing."

How to answer

Define, list benefits, list costs, give your decision rule. "Bump-in-the-wire proxy per host" is your analogy.

Likely follow-ups
  • What does mTLS give you that NetworkPolicy does not? (Identity-based auth and encryption, at L7.)
What limits how big a cluster can get, and how do large companies scale the control plane?

"The official tested limits are about 5,000 nodes, 150,000 pods and 110 pods per node. The bottleneck is the control plane: etcd size and write latency, and the API server serving watches and LIST calls. Public write-ups show the fixes. OpenAI at 7,500 nodes moved Kubernetes Events into a separate etcd cluster, and found EndpointSlices cut endpoint watch load dramatically compared with the old Endpoints object. Large operators such as OpenAI and Uber (Uber moved millions of cores off Mesos) also describe tuning such as scheduler and controller concurrency, API Priority and Fairness to stop expensive LIST calls hurting everyone, and Protobuf instead of JSON for component traffic; I would not pin each item on one company without the posts in front of me. Many companies also choose many medium clusters over one giant cluster to limit blast radius."

How to answer

Give the official limits, name the bottleneck (etcd and API server), then two real examples. Say "blast radius".

Likely follow-ups
  • What is API Priority and Fairness? (Request queuing and fair sharing inside the API server.)
  • Many clusters: how do you manage them? (GitOps per cluster, a fleet or federation layer.)
