60-second answers to the most asked questions

Read each one out loud with a timer. They are written the way you would say them, not the way a textbook writes.

"What is Kubernetes?"

"Kubernetes is a system that runs containers across many machines and keeps them in the state you asked for. You describe what you want, for example five copies of this image behind this name, and store it through the API server in etcd. Controllers keep comparing that desired state with what is actually running and fix differences: they restart crashed containers, replace pods on dead nodes, roll out new versions gradually and scale with load. The scheduler picks a node for each pod, and an agent on every node, the kubelet, actually starts the containers. Services give pods stable names and load balancing. So it is a control loop for a whole fleet, much like a routing control plane keeping the forwarding tables right."

"What happens when you run kubectl apply?"

"kubectl sends the YAML to the API server. It authenticates me, checks RBAC, runs admission policies, validates the object, and stores it in etcd. The Deployment controller sees it and creates a ReplicaSet; the ReplicaSet controller creates pods. The scheduler picks a node for each pod by filtering and scoring, and writes the binding. The kubelet on that node notices, asks containerd to create the pod sandbox, the CNI plugin gives it an IP, the image is pulled and containers start. When the readiness probe passes, the EndpointSlice controller adds the pod behind its Service and kube-proxy updates rules on every node. Every step is a separate component watching the API server."

"How does a Service find pods?"

"A Service selects pods by labels and gets a stable virtual IP and a DNS name. The EndpointSlice controller keeps the list of ready pod IPs that match. kube-proxy on every node watches that list and programs NAT rules, so a packet to the virtual IP is rewritten to one real pod IP. Nothing owns that IP; it exists only as rules in each node's kernel. When pods are replaced, only the endpoint list changes, and clients keep using the same name."

"Debug a pod in CrashLoopBackOff."

"It means the container keeps exiting and the kubelet is backing off between restarts, from 10 seconds up to five minutes. I run describe to see the last exit code and how long it ran, and the events. Exit 1 after a second is usually config: a missing env var or Secret. 137 is SIGKILL, usually OOM or a liveness kill. Then I read kubectl logs --previous, because the evidence is in the container that died. I check the probes and the command. If the image has no shell, I use kubectl debug with a copy of the pod. After fixing, I add an alert on restart rate."

"What happens when a node dies?"

"The kubelet heartbeats through a Lease. When heartbeats stop, the node lifecycle controller marks the node NotReady after about 50 seconds and taints it, and endpoints for its pods are removed, so traffic shifts to other replicas. Pods tolerate that taint for 300 seconds by default, then they are evicted and their controllers create replacements, which the scheduler places on healthy nodes. So by default it is roughly five to six minutes for replacement. StatefulSet pods are the exception: they wait until the node is confirmed gone, to avoid two copies of one identity."

"How do you deploy with zero downtime?"

"A rolling update with maxUnavailable zero so capacity never drops, and a real readiness probe so new pods get traffic only when they can serve. On shutdown, a preStop delay so endpoint removal reaches every node before the app stops, and the app handles SIGTERM by finishing in-flight requests within the grace period. A PodDisruptionBudget for node drains. Database changes that are backward compatible, expand then contract. And a canary with automatic rollback on error rate, so a bad version reaches only a few percent of users."
