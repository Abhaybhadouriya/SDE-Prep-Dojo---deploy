Beginner questions (SDE-1 must-know)

What problem does Kubernetes solve? Why not just run Docker on a few VMs with a script?

"Docker runs containers on one machine. Kubernetes manages containers across a whole fleet of machines. With a script, I have to decide placement myself, notice when a container or a machine dies and restart it somewhere else, update load balancer entries when IPs change, do rolling upgrades without downtime, and scale up when traffic grows. Kubernetes does all of that from a declarative description: I say 'I want 5 copies of this image, reachable at this name', and controllers keep comparing that desired state with reality and fixing the difference. The script approach works for ten servers and breaks at a hundred, mostly in failure handling."

How to answer

Contrast one host vs a fleet, list four or five jobs (placement, self-healing, discovery, rollouts, scaling), then say "desired state + reconciliation" as the key idea.

Likely follow-ups
  • When would you not use Kubernetes? (Small app, a single VM or a managed PaaS is simpler; the ops cost is real.)
  • What does "declarative" mean here?
What is a Pod, and why does Kubernetes schedule pods instead of containers?

"A pod is the smallest unit Kubernetes runs: one or more containers that are always placed together on the same node and share a network namespace, so they have one IP and talk over localhost, and can share volumes. Most pods have one main container. The pod wrapper exists for helpers that must live next to the app: a log shipper, a proxy sidecar, an init container that prepares files. Pods are disposable: when one dies it is replaced by a new pod with a new name and IP, not repaired. Under the hood, a tiny 'pause' container holds the shared namespaces open."

How to answer

Definition, the shared-namespace detail (your kernel strength), one sidecar example, and "replaced, not repaired".

Likely follow-ups
  • What is an init container? What is a native sidecar? (An init container with restartPolicy: Always, GA in v1.33.)
  • Why not put the app and its database in one pod? (They scale and fail independently.)
Pod vs ReplicaSet vs Deployment: what is the relationship?

"A ReplicaSet keeps N pods that match a label selector alive: if one disappears it creates another. A Deployment sits on top and manages ReplicaSets to do versioned rollouts. When I change the pod template, say a new image tag, the Deployment creates a new ReplicaSet and gradually scales it up while scaling the old one down. Rollback is just scaling the old ReplicaSet back up, which is why kubectl rollout undo is fast. In practice I never create ReplicaSets or bare pods directly; I create Deployments."

How to answer

Draw three nested boxes. Say what each controller watches and does. End with the rollback trick.

Likely follow-ups
  • How many old ReplicaSets are kept? (revisionHistoryLimit, default 10.)
  • What happens if you delete a pod owned by a ReplicaSet?
Deployment vs StatefulSet vs DaemonSet vs Job: when do you use each?

"Deployment for stateless services where any copy is as good as another: web APIs, workers. StatefulSet when each replica needs a stable identity and its own disk: databases, Kafka brokers, ZooKeeper; pods are named kafka-0, kafka-1, start in order, and each keeps its own PersistentVolumeClaim. DaemonSet when exactly one pod must run on every node (or every matching node): log shippers, node-exporter, CNI and storage agents. Job for work that runs to completion, like a migration or a batch export, and CronJob for the same on a schedule."

How to answer

One line each with a concrete example. The question is really "do you know the trade-offs of identity and lifetime".

Likely follow-ups
  • Why can't Kafka just be a Deployment? (Stable network identity and per-broker storage.)
  • How does a Job handle failures? (backoffLimit, default 6.)
Explain the Service types: ClusterIP, NodePort, LoadBalancer, ExternalName and headless.

"A Service gives a stable name and virtual IP in front of a changing set of pods. ClusterIP is the default and only reachable inside the cluster. NodePort also opens the same port, from 30000-32767 by default, on every node. LoadBalancer asks the cloud for an external load balancer that forwards to the nodes or pods; it is the simple L4 front door. ExternalName is just a DNS CNAME to something outside. Headless, with clusterIP: None, has no virtual IP: DNS returns the pod IPs directly, which StatefulSets and Kafka clients need because they must talk to a specific broker."

How to answer

Say what a Service is for (stable identity over changing pods) before listing types. Give one use case each.

Likely follow-ups
  • How does a ClusterIP actually route? (See the Intermediate section.)
  • One LoadBalancer per service gets expensive. What do you do? (Ingress or Gateway API.)
Pods get new IPs when they restart. How do other services find them?

"Clients never use pod IPs. They call a Service name like orders.shop.svc.cluster.local. CoreDNS answers with the Service's ClusterIP, which never changes. Behind it, the EndpointSlice controller keeps a list of the IPs of pods that match the Service selector and are Ready. kube-proxy on every node watches those lists and programs NAT rules, so a packet to the ClusterIP is rewritten to one of the current pod IPs. When a pod is replaced, only the EndpointSlice changes; clients notice nothing."

How to answer

Three hops: DNS name, stable virtual IP, live endpoint list. Name the component at each hop.

Likely follow-ups
  • What if the selector matches no pods? (Empty endpoints, connections fail.)
  • Why can a client still hit a dying pod for a moment? (Rule updates are asynchronous.)
ConfigMap vs Secret. Is a Secret actually secret?

"Both inject configuration into pods as environment variables or mounted files, and both are limited to 1 MiB. ConfigMaps hold normal settings; Secrets hold sensitive values and get slightly special handling, for example tmpfs mounts and separate RBAC. But by default a Secret is only base64-encoded, not encrypted, so anyone who can read the object or etcd can read it. In production you add encryption at rest with a KMS provider, tight RBAC, and often an external store like Vault or a cloud secret manager synced in by External Secrets Operator."

How to answer

Similarities, then bust the myth, then the production fix. Detail on ConfigMaps & Secrets and Security.

Likely follow-ups
  • If I update a ConfigMap, does the pod see it? (Mounted files update after a delay, env vars and subPath mounts do not.)
  • How do you rotate a database password without downtime?
What is a Kubernetes namespace? Is it related to Linux namespaces? Is it a security boundary?

"A Kubernetes namespace is a logical folder for API objects: it scopes names, RBAC permissions, resource quotas and policies, so team A and team B can both have a Service called api. It has nothing to do with Linux namespaces, which are the kernel feature that isolates processes inside containers. And it is not a hard security boundary on its own: pods in different namespaces can share a node and, without NetworkPolicies, can talk to each other freely. You get real isolation by stacking RBAC, quotas, NetworkPolicy and Pod Security on top, or by using separate clusters."

How to answer

Interviewers love catching the confusion with Linux namespaces. Say the difference first, clearly.

Likely follow-ups
  • Which objects are not namespaced? (Nodes, PersistentVolumes, ClusterRoles, StorageClasses, CRDs.)
  • How would you isolate tenants?
What are labels and selectors, and why are they so important?

"Labels are key-value tags on objects, like app=checkout, version=v2. Selectors are queries over labels. They are the glue of Kubernetes: a ReplicaSet owns the pods its selector matches, a Service sends traffic to pods its selector matches, NetworkPolicies and scheduling rules pick pods and nodes by labels. Nothing is linked by name or IP. That makes the system loosely coupled, and it is also a classic source of bugs: one typo in a label and the Service has zero endpoints with no error anywhere."

How to answer

Definition, three consumers of selectors, one failure story. Short.

Likely follow-ups
  • Labels vs annotations? (Annotations are non-identifying metadata, not used by selectors.)
  • Why is a Deployment's selector immutable?
Liveness vs readiness vs startup probes.

"All three are checks the kubelet runs against a container, by HTTP, TCP, gRPC or a command. Readiness failing removes the pod from Service endpoints, so it gets no traffic, but nothing restarts. Liveness failing makes the kubelet restart the container, for a process that is stuck. Startup probe runs first and holds the other two off until a slow app has booted. The big rule: liveness should only detect 'this process is wedged'; if it checks a shared database, one database blip restarts every pod and you have caused an outage."

How to answer

Say what the kubelet does on each failure. Then the cascading-restart trap. Deep dive on Observability & Troubleshooting.

Likely follow-ups
  • Defaults? (Period 10 s, timeout 1 s, failure threshold 3.)
  • Should readiness check dependencies?
What are resource requests and limits?

"A request is what the container is guaranteed and what the scheduler uses to place it: a node 'fits' if the sum of requests fits. A limit is the ceiling. If a container goes over its CPU limit it is throttled, slowed down by the kernel's CFS quota. If it goes over its memory limit it is killed by the kernel OOM killer and shows OOMKilled, exit code 137, because memory cannot be throttled. Requests and limits also decide the QoS class, which decides who gets evicted first when a node runs short."

How to answer

Request = scheduling and guarantee, limit = ceiling. Then the CPU vs memory difference. That difference is what they are testing.

Likely follow-ups
  • What happens if you set no requests? (BestEffort, first to be evicted; HPA on CPU cannot work.)
  • Should you set CPU limits?
kubectl apply vs kubectl create: imperative vs declarative.

"create is imperative: 'make this object now', and it fails if it exists. apply is declarative: 'make the live object look like this file', creating or updating as needed, and with server-side apply the API server tracks which fields each manager owns. Teams keep YAML in git and apply it, ideally through a GitOps tool like Argo CD or Flux that continuously syncs the cluster to git. That gives review, history and easy rollback, and avoids snowflake changes nobody remembers, which is exactly what bit Reddit in 2023."

How to answer

Define both, say which you use and why (git as the source of truth), and add the GitOps word.

Likely follow-ups
  • What is drift and how does GitOps handle it?
  • What is Helm for?
