Intermediate questions (how it works inside)

Explain the Kubernetes architecture: every control-plane and node component in one line.

"Control plane: the API server is the front door, the only component that talks to etcd, and it is stateless so it scales horizontally. etcd is a Raft-replicated key-value store holding all cluster state. The scheduler assigns new pods to nodes. The controller-manager runs many reconcile loops: Deployments, ReplicaSets, nodes, Jobs, EndpointSlices. The cloud-controller-manager talks to the cloud for load balancers and node lifecycle. On each node: the kubelet runs the pods assigned to it, through the container runtime like containerd over CRI; kube-proxy programs Service rules; and the CNI plugin wires pod networking. Everything communicates through the API server using watches."

How to answer

Draw the whiteboard picture while talking. End with "everything goes through the API server, by watch". A public SDE-2 report (Robin.io) lists this exact question.

Likely follow-ups
  • Why does only the API server talk to etcd?
  • Is kube-proxy required? (No, Cilium can replace it with eBPF.)
What happens, step by step, when you run kubectl apply -f deployment.yaml?

"kubectl sends the object to the API server over HTTPS. The API server authenticates me, authorizes the action with RBAC, runs mutating admission, validates the schema, runs validating admission like Pod Security, and stores the Deployment in etcd. The Deployment controller, watching, creates a ReplicaSet. The ReplicaSet controller creates pods with no node assigned. The scheduler sees unscheduled pods, filters and scores nodes, and writes a binding. The kubelet on the chosen node sees the pod, asks the runtime to create a sandbox, the CNI plugin gives it an IP, the image is pulled and containers start. Probes run; once readiness passes, the pod is Ready, the EndpointSlice controller adds its IP behind the Service, and kube-proxy on every node updates its rules. Each step is a separate controller reacting to a change in the API server."

How to answer

This is the single best question to prepare. Practise it until it takes 60-90 seconds. Name every component. The full animated walk-through is on Architecture.

Likely follow-ups
  • Where can this fail, and what status would you see at each step?
  • Does kubectl talk to the kubelet? (No, only to the API server, except for logs/exec which the API server proxies.)
What is a controller or reconciliation loop? What does "level-triggered" mean?

"A controller is a loop: watch the desired state and the actual state, compare, take one action to move actual toward desired, repeat. For example the ReplicaSet controller sees 'want 3, have 2' and creates a pod. Level-triggered means it acts on the current state, not on the event that happened. If it misses an event or crashes, it just looks at the world again and still does the right thing. That is why controllers also do periodic resyncs and must be idempotent: running the same reconcile twice must be safe. In code they use informers (a local watched cache) and a work queue."

How to answer

Thermostat analogy, then level vs edge, then why it makes the system robust to missed events.

Likely follow-ups
  • What would go wrong with an edge-triggered design?
  • How does leader election work for controllers? (Lease objects; one active replica.)
etcd: why an odd number of members, and what happens if it loses quorum?

"etcd uses Raft, so every write needs a majority, floor(n/2)+1 members, to agree. Three members tolerate one failure, five tolerate two. Four members still only tolerate one, so even numbers add cost without adding safety. If quorum is lost, etcd refuses writes, so the API server cannot change anything: no new pods, no scaling, no self-healing. But the data plane keeps going. Running pods keep running and existing Service rules keep forwarding. Recovery is restoring quorum, or in the worst case restoring from an etcd snapshot, which is why regular snapshots are non-negotiable."

How to answer

Majority math, then the control plane vs data plane split. Your router analogy (non-stop forwarding) fits perfectly.

Likely follow-ups
  • Why not seven members? (Each write waits for more members; latency rises. The etcd docs suggest 5 as a sensible max.)
  • What is etcd's default storage quota? (2 GB.)
If the API server (or the whole control plane) goes down, do your pods die?

"No. The kubelet keeps running the containers it already knows about and restarts them locally if they crash, and kube-proxy's rules stay in the kernel, so traffic keeps flowing. What stops is everything that needs a decision: no new pods get scheduled, Deployments cannot scale or roll out, a dead node's pods are not replaced, and kubectl does not work. It is exactly like a router whose route processor crashed: forwarding continues on the line cards, but no new routes are learned."

How to answer

Short "no", then what keeps working, then what stops. Use your router analogy here; it lands well.

Likely follow-ups
  • How do managed services keep the API server available? (Multiple replicas across zones behind a load balancer.)
How does a ClusterIP Service actually work? Can you ping it?

"A ClusterIP is a virtual IP. No interface owns it and nothing answers ARP for it. kube-proxy runs on every node, watches Services and EndpointSlices, and programs NAT rules: in iptables or nftables mode, a packet sent to ClusterIP:port is DNAT-ed to one of the ready pod IPs, chosen randomly, and conntrack remembers the choice for the connection. So the 'load balancer' is distributed into every node's kernel. Ping usually fails because the rules only match the Service's TCP, UDP or SCTP ports; ICMP to the virtual IP matches nothing."

How to answer

This is your home ground. Say "DNAT in every node's kernel, programmed by kube-proxy", then explain the ping result as a consequence.

Likely follow-ups
  • What changes with Cilium? (eBPF maps at the socket or tc layer replace kube-proxy rules.)
  • How does traffic from outside reach a pod? (NodePort or LoadBalancer then the same DNAT.)
How does a rolling update avoid downtime? What are maxSurge and maxUnavailable?

"The Deployment creates a new ReplicaSet and shifts pods over in steps. maxSurge is how many extra pods above the desired count may exist during the update; maxUnavailable is how many below desired may be not-ready. Both default to 25%. With 4 replicas, maxSurge 1 and maxUnavailable 0, it starts one new pod, waits until it is Ready, then removes one old pod, and repeats, so capacity never drops. Readiness probes are what make this safe, because 'Ready' is the signal to continue. To roll back, kubectl rollout undo scales the previous ReplicaSet back up."

How to answer

Define both knobs, walk one concrete example with numbers, mention readiness as the gate.

Likely follow-ups
  • What if the new version never becomes Ready? (Rollout stalls; progressDeadlineSeconds, default 600, marks it failed. It does not auto-rollback.)
  • Why can users still see errors during a rolling update? (Graceful shutdown, see Advanced.)
Ingress vs LoadBalancer Service vs Gateway API: which is the front door?

"A LoadBalancer Service gives one cloud L4 load balancer per Service, simple but costly with many services and no HTTP routing. Ingress is one L7 entry point with host and path rules, implemented by a controller; the API is stable but frozen, and many features live in non-portable annotations. Gateway API is the newer, role-oriented model: the infra team owns GatewayClass and Gateway (listeners, TLS), app teams own HTTPRoutes with header matching and weighted traffic splits for canaries. For a new design I would choose Gateway API. Worth knowing: the community ingress-nginx controller was retired in March 2026, which pushed many teams to migrate."

How to answer

L4 per service vs L7 shared, then why Gateway API exists (roles, portability, traffic splitting). Details on Ingress & Gateway API.

Likely follow-ups
  • Where does TLS terminate?
  • How would you do a 5% canary with Gateway API?
PersistentVolume, PersistentVolumeClaim, StorageClass: how do they fit together?

"A PVC is a pod's request: 'I need 20 GiB, ReadWriteOnce, of class fast-ssd'. A PV is the actual piece of storage. A StorageClass is the recipe a CSI driver uses to create PVs on demand, so with dynamic provisioning the PV is created automatically when the PVC appears. One important setting is volumeBindingMode: WaitForFirstConsumer: it delays creating the disk until the pod is scheduled, so the disk lands in the same zone as the pod. Without it you can get a disk in zone A and a pod that can only fit in zone B, stuck Pending."

How to answer

Request vs supply vs recipe, then the zone trap. Deep dive on Storage.

Likely follow-ups
  • Access modes? (RWO, ROX, RWX, RWOP.)
  • What happens to the data when the PVC is deleted? (Reclaim policy: Delete by default for dynamic, or Retain.)
Explain QoS classes and how the kubelet decides which pods to evict.

"QoS is derived from requests and limits. Guaranteed: every container has CPU and memory requests equal to limits. Burstable: at least one request set but not Guaranteed. BestEffort: nothing set. When a node runs low on memory or disk, the kubelet evicts pods to protect the node, BestEffort first, then Burstable pods using more than they requested, and Guaranteed last. Precisely, the kubelet ranks pods by whether usage exceeds requests, then by PriorityClass, then by how far usage exceeds requests. That is why BestEffort (request 0) goes first and why a high PriorityClass helps protect a pod. The QoS class also sets the kernel's oom_score_adj, so if the kernel OOM killer has to act at node level, it prefers the same victims."

How to answer

Three definitions, eviction order, and the kernel link (oom_score_adj) as your bonus.

Likely follow-ups
  • Difference between eviction and OOMKilled? (kubelet at node level vs kernel at container limit.)
  • How would you protect a critical pod? (Guaranteed QoS plus a high PriorityClass.)
How does the Horizontal Pod Autoscaler (HPA) decide how many replicas to run?

"Every 15 seconds by default it reads the metric, for example average CPU as a percentage of requests, and computes desired = ceil(current replicas x current metric / target). With 4 pods at 90% CPU and a 60% target, that is ceil(4 x 90/60) = 6. It ignores changes within a 10% tolerance and, by default, waits a 5-minute stabilization window before scaling down, so it does not flap. CPU metrics come from metrics-server; for better signals like requests per second or Kafka lag you use custom or external metrics through an adapter or KEDA."

How to answer

Formula with one worked example. Mention that CPU is relative to requests (no requests, no HPA). Deep dive on Scheduling & Autoscaling.

Likely follow-ups
  • Why is CPU a poor scaling signal for some services? (It lags; I/O-bound services never get busy CPU.)
  • HPA adds pods but they stay Pending. Now what? (Cluster Autoscaler or Karpenter adds nodes.)
Taints and tolerations vs node affinity. How do you dedicate GPU nodes to ML pods?

"A taint on a node repels pods: only pods with a matching toleration may schedule there. Node affinity attracts: the pod says 'I want nodes with this label'. They solve opposite halves. A toleration only allows a pod on the tainted node; it does not send it there. So for GPU nodes I do both: taint them gpu=true:NoSchedule so normal pods stay away, and give ML pods a toleration plus a node affinity for the GPU label so they land there and nowhere else."

How to answer

Repel vs attract, then the "you need both" example.

Likely follow-ups
  • What does the NoExecute effect do? (Evicts running pods without a toleration, optionally after tolerationSeconds.)
  • How do you spread replicas across zones? (Topology spread constraints.)
Docker vs containerd vs CRI-O. What did the dockershim removal mean?

"The kubelet talks to a container runtime through CRI, a gRPC API. containerd and CRI-O implement CRI; each uses a low-level runtime like runc to create the actual namespaced processes. Docker Engine never implemented CRI, so Kubernetes carried an adapter called dockershim, removed in v1.24. That only changed what runs on the node. Images built with Docker are standard OCI images, so they run unchanged on containerd. Developers still use Docker to build; nodes run containerd."

How to answer

Layer it: kubelet, CRI, high-level runtime, runc. Then "images are OCI, nothing broke for apps". See Docker internals.

Likely follow-ups
  • What is OCI? (Open standards for image format and runtime.)
  • How do you debug containers on a node without Docker? (crictl.)
What is Helm, and why do people template YAML? Helm vs Kustomize?

"The same app needs slightly different YAML per environment: replicas, image tag, resource sizes, hostnames. Helm is a package manager: a chart is templated YAML plus a values file, and a release is an installed instance you can upgrade and roll back. It is also how most third-party software is distributed. Kustomize takes the other approach: no templates, just a base set of plain YAML plus overlays that patch it, built into kubectl. I would use Helm to install third-party components and either for our own services; the key is that the rendered output lives in git and goes through review, often via Argo CD."

How to answer

The problem (per-environment differences), then the two styles, then a pragmatic choice.

Likely follow-ups
  • What are the downsides of heavy templating? (Hard to read, logic in YAML, surprises at render time.)
