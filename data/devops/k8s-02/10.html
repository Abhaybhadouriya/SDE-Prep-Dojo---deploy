Lab: find every component in your own cluster

Deep dive (platform teams)

Everything on this page is visible in your kind cluster. In kind (and in kubeadm clusters), the control-plane components run as pods in the kube-system namespace.

$ kubectl get pods -n kube-system -o wide

coredns-668d6bf9bc-5vb7k                     1/1     Running   dojo-control-plane
coredns-668d6bf9bc-lq9wz                     1/1     Running   dojo-control-plane
etcd-dojo-control-plane                      1/1     Running   dojo-control-plane
kindnet-7xk2p                                1/1     Running   dojo-worker
kindnet-mm4cd                                1/1     Running   dojo-control-plane

(Columns trimmed.) Notice: etcd, kube-apiserver, kube-controller-manager and kube-scheduler have the node name in their pod name and exist once. kube-proxy and kindnet (kind's simple CNI) have one per node: they are DaemonSets. But who starts the API server pod, if the API server is needed to start pods? A chicken-and-egg problem. The answer is static pods: the kubelet on the control-plane node reads YAML files straight from a folder on disk.

$ docker exec dojo-control-plane ls /etc/kubernetes/manifests
etcd.yaml
kube-apiserver.yaml
kube-controller-manager.yaml
kube-scheduler.yaml

Ask the API server how it feels, and watch kubectl's real HTTP calls with a higher verbosity level:

$ kubectl get --raw='/readyz?verbose' | tail -4
[+]poststarthook/apiservice-openapiv3-controller ok
[+]shutdown ok
[+]etcd ok
readyz check passed

$ kubectl get pods -v=6 2>&1 | grep GET
... round_trippers.go:...] "Response" verb="GET" url="https://127.0.0.1:41235/api/v1/namespaces/default/pods?limit=500" status="200 OK" milliseconds=7

(The exact log format of -v=6 changes between kubectl versions; what matters is that every kubectl command is a plain HTTPS REST call.) Finally, list every kind of object the API server knows about:

$ kubectl api-resources | head -6

componentstatuses     cs           v1           false        ComponentStatus

Try breaking it: move the scheduler's manifest out of the folder (docker exec dojo-control-plane mv /etc/kubernetes/manifests/kube-scheduler.yaml /root/), then create a deployment. Pods stay Pending forever, while existing pods are fine. Move the file back and the pending pods get scheduled within seconds. You just proved the control plane / data plane split.
