Inside the API server: three gates (the third has two halves)

Must know (SDE-1)

Step 2 above deserves its own picture, because security questions (page 12) all hang off it. Every request, from a human or from a component, goes through the same pipeline. There are three gates: who are you, may you, and is this object acceptable. The third gate, admission, has a "may rewrite" half and a "may only say no" half, with a schema check in between.

  1. Authentication: who are you? The API server checks a client certificate, a bearer token (a ServiceAccount token or an OIDC token from your company login) or a webhook. It only learns a user name and groups; it decides nothing yet. Fails with 401 Unauthorized.
  2. Authorization: may you do this verb on this resource? Usually RBAC (role-based access control: roles list allowed verbs, bindings give roles to users), plus the Node authorizer that limits each kubelet to its own pods. Fails with 403 Forbidden. Read-only requests such as get and watch stop here; admission is only for writes.
  3. Mutating admission: may rewrite the object. Built-in plugins and your webhooks can change what you sent: fill in a default ServiceAccount, add default resource limits, or inject a sidecar container (this is how a service mesh adds its proxy). They run first, so the later checks see the final object.
  4. Schema validation: is it a well-formed object? Correct types, required fields, valid names. Fails with 422 Unprocessable Entity.
  5. Validating admission: may only say yes or no. Pod Security Admission, ValidatingAdmissionPolicy rules and validating webhooks look at the final object and can only reject it (for example "privileged containers are not allowed here"). They cannot change it. Only after all of this is the object written to etcd.

From your world

It is the ingress pipeline of a router: first an ACL check on who the packet is from (authentication and authorization), then a policy map that may rewrite the packet (set DSCP, NAT: mutating admission), then a final deny filter that can only drop (validating admission). Order matters for the same reason: the last filter must see the packet after it was rewritten. Where it breaks: a webhook is a remote call to someone else's server, so a slow or dead webhook can block every write in the cluster. Set timeoutSeconds and failurePolicy on purpose.
