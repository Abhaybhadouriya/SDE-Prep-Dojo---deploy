The golden rule: everything goes through the API server

Must know (SDE-1)

This is the design choice that makes Kubernetes understandable. No component talks to another component directly to coordinate work. The scheduler does not call the kubelet. The ReplicaSet controller does not call the scheduler. Each one:

  1. Watches the API server for the kinds of objects it cares about (a long-lived HTTP stream of "added / modified / deleted" events).
  2. Decides something, using only what it sees in those objects.
  3. Writes its decision back to the API server as a change to an object.

The API server validates the write, stores it in etcd, and notifies everyone else who is watching. This is a hub-and-spoke design, with the API server as the hub.

Why is this so good?

  • One place to secure and audit. Every change passes authentication, authorization and admission checks in one spot.
  • etcd is protected. Only the API server touches it, so it is never flooded by hundreds of kubelets.
  • Components fail independently. If the scheduler crashes, kubelets keep running pods; when the scheduler comes back, it reads the current state and carries on. There is no in-memory conversation to lose.
  • You can add your own loop. Write a program that watches some object and writes others, and you have extended Kubernetes. That is what an operator is (see StatefulSets & Operators).

One exception to remember: for kubectl logs, kubectl exec and kubectl port-forward, the API server opens a connection to the kubelet on the node (port 10250) and streams the data back. So the API server must be able to reach every node.
