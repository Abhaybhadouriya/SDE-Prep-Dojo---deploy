How components "notice" things: list, watch and informers

Must know (SDE-1)

A question every systems engineer asks first: is it polling or a watch? It is a watch, plus a safety net.

  1. List. When a controller starts, it asks the API server for all objects of a kind (for example all Pods). Every object carries a resourceVersion, a number that increases with every change in etcd.
  2. Watch. It then opens a long-lived HTTP stream: "send me every change after resourceVersion N". The API server pushes ADDED, MODIFIED and DELETED events as they happen.
  3. Local cache. Client libraries wrap this in an informer: it keeps an in-memory copy of all the objects, so the controller reads from local memory instead of hammering the API server.
  4. Work queue. Events only put an object's name into a queue. A worker takes the name, reads the current object from the cache, and reconciles. If ten events arrive for the same object, it may reconcile just once. That is level-triggered behaviour.
  5. Resync and retry. If a watch breaks, the client lists again and continues. Failed reconciles are re-queued with back-off. Controllers can also periodically re-process everything as a safety net.

From your world

This is the same pattern as a routing daemon that subscribes to netlink events for interface and route changes, keeps its own table in memory, and also does a periodic full dump to catch anything it missed. Events give speed; the full sync gives correctness. Where it breaks: Kubernetes events can be coalesced and old ones are not kept forever (etcd compacts its history), so a controller must always act on the current object, never on the event's contents alone.

Real-world lesson (Uber): when Uber moved about 3 million CPU cores from Mesos to Kubernetes, they hit a case where a controller missed deployment events during a leader change, and its informer resync period was many hours. They added a forced reconcile every 15 minutes. Moral: never rely on events alone.
