Production: a highly available control plane

Deep dive (platform teams)

Your kind cluster has one control-plane node. Production clusters run three (sometimes five) control-plane machines, ideally in different availability zones, with a load balancer in front of the API servers.

  • API servers: active-active. They keep no state of their own, so any of them can serve any request.
  • Scheduler and controller manager: active-standby. Two schedulers acting at once could place the same pod twice, so they use leader election through a Lease object in kube-system. The leader keeps renewing it; if it stops, a standby takes the lease within seconds.
  • etcd: Raft quorum. Either "stacked" on the control-plane machines (simpler) or on its own dedicated machines ("external etcd", more isolation). OpenAI, at 7,500 nodes, ran 5 etcd and 5 API servers on dedicated machines and even moved Kubernetes Events into a separate etcd cluster so noisy events could not slow down real state.

Managed Kubernetes: who runs what

With Amazon EKS, Azure AKS or Google GKE, the cloud runs the control plane (API servers, etcd, scheduler, controller manager) for you, usually spread across zones, and you only see the API endpoint. You still own the worker nodes (or use a serverless node option), node upgrades, add-ons, your workloads and their security. That split is worth stating in an interview at Microsoft or Amazon, because those teams build exactly these services.

Version skew and upgrades

Components do not all have to run the same version, but there are rules. The kubelet may be up to three minor versions older than the API server, and never newer. So you upgrade the control plane first, then the nodes, one minor version at a time. There is no supported downgrade, which is why an etcd backup and a canary cluster (a small, low-risk cluster you upgrade first, like a canary in a coal mine) matter. Kubernetes ships about three minor releases a year (the current one is v1.37, from August 2026).

How big can a cluster get?

110pods per node (official guideline)
5,000nodes per cluster (guideline)
150,000pods per cluster (guideline)
7,500nodes in one OpenAI cluster, with heavy tuning

These are the limits from the official "considerations for large clusters" page; they are tested guidelines, not hard walls. OpenAI's 7,500-node write-up describes the tuning that got them past 5,000 nodes: more API server memory (up to 70 GB heap per API server), Kubernetes Events moved into a separate etcd cluster, and EndpointSlices, which they say cut endpoint watch load by about 1000 times. Other large operators such as Uber describe the same family of tuning (rate-limiting expensive LIST calls with API Priority and Fairness, compact Protobuf encoding instead of JSON, forced periodic reconciles); read both posts in Resources for which team did what. The lesson for interviews: the scaling bottleneck of Kubernetes is the API server and etcd, not the nodes.
