Six boxes. Everything talks only to the API server; only the API server talks to etcd; everyone else watches.

Explain the Kubernetes architecture.

A cluster has a control plane and worker nodes. The control plane has kube-apiserver, the only entry point and the only component that talks to etcd; etcd, a Raft-replicated key-value store holding all cluster state; kube-scheduler, which assigns unscheduled pods to nodes; kube-controller-manager, which runs reconciliation loops such as the Deployment, ReplicaSet, node lifecycle and EndpointSlice controllers; and, in clouds, the cloud-controller-manager. Each node runs the kubelet, which watches for pods bound to it and drives the container runtime (containerd or CRI-O) over CRI; a CNI plugin for pod networking; and usually kube-proxy, which programs Service virtual IPs into iptables or nftables. All coordination happens by watching and writing objects through the API server.

How to answer

Draw two boxes (control plane, nodes), list components with one verb each, then state the hub-and-spoke rule. If you have time, compare it to a router's control and data planes; it makes your answer memorable.

  • Which components are active-active vs leader-elected?
  • What runs as a static pod?
What happens, step by step, when you run kubectl apply -f deployment.yaml?

kubectl sends an HTTPS request to the API server. The API server authenticates the caller, authorizes it with RBAC, runs mutating admission, validates the schema, runs validating admission, and stores the Deployment in etcd; kubectl returns here. The Deployment controller sees the new Deployment and creates a ReplicaSet. The ReplicaSet controller creates the Pod objects with no node. The scheduler filters and scores nodes and binds each pod to one. The kubelet on that node sees the bound pod through its watch, calls the runtime over CRI to create a pod sandbox (namespaces plus the pause container), the runtime calls the CNI plugin to give the pod an IP, then the image is pulled and containers start. The kubelet runs probes; once readiness passes it marks the pod Ready, the EndpointSlice controller adds the pod IP to the Service's EndpointSlice, and kube-proxy on every node updates its rules so traffic can reach it.

How to answer

State the pattern first (watch, act, write), then walk the chain, naming the component at each step. Draw it as you speak. Mention that kubectl returns after the etcd write.

Likely follow-ups
  • Where could this get stuck, and how would you see it? (Pending = scheduler; ContainerCreating = CNI or image; not Ready = probes)
  • What does the pause container do?
  • What exactly does the scheduler look at?
What happens to running applications if the API server (or the whole control plane) goes down?

They keep running. The kubelet keeps the containers it already manages alive and still restarts crashed containers locally; kube-proxy's rules stay in the kernel, so Service traffic still flows to the pods that were known. What stops is everything that needs the API: kubectl, new deployments, scaling, scheduling, and recovery from node failures. Also, endpoints are not updated, so if a pod dies, Services may keep sending traffic to its IP until the control plane returns. It is like non-stop forwarding on a router during a route-processor failure.

How to answer

Separate data plane (continues) from control plane (frozen). Give one subtle consequence, such as stale endpoints. Then say how you prevent it: three API servers behind a load balancer, 3 or 5 etcd members across zones.

Likely follow-ups
  • And if etcd loses quorum?
  • How is the control plane made highly available?
Why does etcd use an odd number of members? What happens when it loses quorum?

etcd uses Raft, which commits a write only when a majority of members have it. Quorum is floor(n/2)+1, so 3 members tolerate 1 failure and 5 tolerate 2; 4 members still tolerate only 1, so even numbers add cost and failure points without adding tolerance. If quorum is lost, the remaining members cannot elect a leader or commit writes, so the API server cannot store any change and the control plane is effectively frozen, while running pods continue. Recovery means bringing members back, or restoring from a snapshot if data is lost.

How to answer

Formula, a two-row example (3 and 5), then the impact on Kubernetes. Mention disk latency sensitivity for bonus points.

Likely follow-ups
  • Why not 7 or 9 members?
  • Stacked vs external etcd?
  • How do you back up etcd?
How do controllers know when something changes? Is it polling?

They use list-and-watch. A controller lists all objects of a type once, getting a resourceVersion, then opens a watch stream from that version, and the API server pushes add, update and delete events. Client libraries wrap this in informers that keep a local cache and feed object keys into a rate-limited work queue. Workers always read the latest object from the cache and reconcile, so the design is level-triggered: duplicate or missed events do not matter because the next reconcile looks at the current state. If a watch breaks, the informer re-lists; failed reconciles are retried with back-off, and periodic resyncs act as a safety net.

How to answer

Say "watch, not polling", then informer, cache, work queue, level-triggered. Mention a real failure mode: missed events during leader change (Uber) and why periodic reconcile matters.

Likely follow-ups
  • Why must reconcile be idempotent?
  • How would you write your own controller? (controller-runtime / Kubebuilder)
How do you make the control plane highly available, and how do you upgrade a cluster safely?

Run at least three control-plane nodes across zones with a load balancer in front of the stateless API servers; the scheduler and controller manager run on each but use Lease-based leader election so only one acts; etcd runs three or five members, stacked or external, with regular snapshots. For upgrades: read the release notes for removed APIs and labels, test on a canary cluster, upgrade the control plane first one minor version at a time, then node pools by cordoning and draining nodes while respecting PodDisruptionBudgets, because the kubelet may lag the API server by up to three minor versions but never lead it. There is no supported downgrade, so the etcd backup is the rollback plan. On managed services the provider handles the control plane, but node pools and add-ons are still yours.

How to answer

Two halves: HA layout, then upgrade order. Back it with a real incident (Reddit Pi-Day) to show you know why each step exists.

Likely follow-ups
  • What is a PodDisruptionBudget?
  • How do you find deprecated APIs before upgrading?

Scenario: the upgrade that broke pod networking (Reddit, Pi Day 2023)

You upgrade a critical cluster from Kubernetes 1.23 to 1.24. The control plane comes up, but pods across nodes suddenly cannot talk to each other. The site is down. What happened and what would you do?

Weak answer: "Roll back to 1.23." (There is no supported downgrade.) Or: "Restart all the pods."

Strong answer: "First, stop the bleeding: freeze further changes and check what the release removed. In Reddit's real outage, their Calico setup chose BGP route-reflector nodes using the label node-role.kubernetes.io/master, and 1.24 removed that label in favour of control-plane. No node was a route reflector anymore, so pod routes disappeared. That config was not in git, so nobody knew it existed. They were down for 314 minutes and restored the control plane from backup. To prevent it: keep all cluster config in git, read the deprecations for every release, upgrade a non-critical canary cluster first, test etcd restore regularly, and alert on pod-to-pod connectivity, not just pod status."

Likely follow-ups
  • What is a BGP route reflector? (Your networking background wins here.)
  • How would you detect this in a canary before production?
