The journey of kubectl apply (the most important animation on this site)

Must know (SDE-1)

"What happens when you run kubectl apply -f deployment.yaml?" is the best single Kubernetes question to prepare. It tests whether you really know every component. Click Next or Play. Each step names the real process and what it writes.

  1. kubectl sends the request. kubectl reads your YAML and your ~/.kube/config (server address and credentials), then sends an HTTPS request to the API server. With apply it is a create or a patch of the Deployment object.
  2. Three gates. The API server runs authentication (who are you: client certificate, OIDC token or ServiceAccount token), authorization (may you do this: usually RBAC), then admission (mutating webhooks can add defaults; then schema validation; then validating policies such as Pod Security can reject it).
  3. Stored in etcd. The API server writes the Deployment into etcd and returns success to kubectl. Your command finishes here, before anything is running. That is why kubectl apply returns in milliseconds.
  4. Deployment controller. Inside kube-controller-manager, the Deployment controller's watch fires. It sees a Deployment with no matching ReplicaSet for this pod template, so it creates a ReplicaSet object (named after a hash of the template).
  5. ReplicaSet controller. Its watch fires. The ReplicaSet wants 3 pods and owns 0, so it creates 3 Pod objects. They have no nodeName yet, so they show as Pending.
  6. Scheduler. kube-scheduler watches for pods with an empty nodeName. For each, it filters nodes (enough CPU and memory requests free? taints, the node-side "keep out" marks? affinity, the pod-side "I want to be near X" rules? volume zone? All on page 09), scores the survivors, and writes a Binding that sets nodeName: dojo-worker.
  7. kubelet notices. The kubelet on dojo-worker watches pods whose nodeName is itself. A new one appeared. Nobody pushed it; the kubelet pulled it through its watch.
  8. Pod sandbox. The kubelet calls the runtime over CRI: RunPodSandbox. containerd creates the pod's Linux namespaces (network, IPC, UTS) and starts the tiny pause container that holds them open.
  9. Networking. The runtime calls the CNI plugin with ADD and the path of the new network namespace. The plugin creates a veth pair, moves one end into the namespace, assigns a pod IP (here 10.244.1.5) and sets up routes.
  10. Containers start. The kubelet asks the runtime to pull the image (if not cached) and create and start the app container inside the sandbox. Then it begins the startup, liveness and readiness probes from your spec.
  11. Ready. When the readiness probe passes, the kubelet updates the pod's status to Ready through the API server. The EndpointSlice controller sees a ready pod matching a Service's selector and adds its IP to that Service's EndpointSlice.
  12. Traffic. kube-proxy on every node watches EndpointSlices. It adds the new pod IP to the NAT rules for the Service's virtual IP. Now requests to the Service can land on the new pod. The whole chain usually takes a few seconds, mostly image pull and app start-up.

When you answer this in an interview, say the pattern out loud before the details: "Every step is a component watching the API server, doing one job, and writing the result back. kubectl only writes desired state; controllers, the scheduler and the kubelet each react." Then walk the steps. Pause after step 3 and point out that kubectl has already returned.

Want to see the events yourself? In your kind cluster, open two terminals. In the first, watch events; in the second, create a deployment.

# terminal 1
kubectl get events --watch
# terminal 2
kubectl create deployment web --image=nginx:1.27 --replicas=3
$ kubectl get events --watch

Read the REASON column from top to bottom: ScalingReplicaSet (Deployment controller), SuccessfulCreate (ReplicaSet controller), Scheduled (scheduler), Pulling / Pulled / Created / Started (kubelet). It is the stepper above, printed by the cluster itself. (Exact message wording varies a little between versions.)
