What a producer really is

A producer is not a server. It is a client library that lives inside your application process: the Java KafkaProducer class, Python's confluent-kafka Producer, Go's franz-go or sarama, and so on. Your order service, your click tracker or your log shipper creates one producer object at startup and keeps it for the life of the process.

The producer has three jobs:

  1. Find the right broker. On start it asks any broker in bootstrap.servers for metadata: "which topics exist, how many partitions each has, and which broker is the leader of each partition?" It caches the answer.
  2. Pick a partition and pack batches. For each record it chooses a partition (using the key) and adds the record to that partition's current batch.
  3. Ship batches to leaders and handle the replies. A background thread sends batches straight to each partition's leader broker, waits for acks, and retries failures. There is no load balancer in between.

The smallest useful producer

Here is the same tiny producer in three forms. Each one sends record o-3 -> placed to topic shop-orders and prints where it landed. Do not worry about every setting yet; each one is explained below.

from confluent_kafka import Producer

p = Producer({
    "bootstrap.servers": "localhost:9092",
    "enable.idempotence": True,       # NOT on by default in librdkafka-based clients
    "acks": "all",
    "linger.ms": 5,
    "compression.type": "lz4",
    "partitioner": "murmur2_random",  # same key-to-partition mapping as the Java client
})

def on_delivery(err, msg):
    if err is not None:
        print("FAILED:", err)
    else:
        print(f"ok partition={msg.partition()} offset={msg.offset()}")

p.produce("shop-orders", key="o-3", value="placed", on_delivery=on_delivery)
p.flush(10)   # wait up to 10 s for the buffer to drain and callbacks to run
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
// These two are already the defaults since Kafka 3.0; written out so you can see them.
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("linger.ms", "5");
props.put("compression.type", "lz4");

try (KafkaProducer<String, String> producer = new KafkaProducer<>(props)) {
    ProducerRecord<String, String> record =
        new ProducerRecord<>("shop-orders", "o-3", "placed");
    producer.send(record, (metadata, exception) -> {
        if (exception != null) {
            System.err.println("FAILED: " + exception);
        } else {
            System.out.printf("ok partition=%d offset=%d%n",
                              metadata.partition(), metadata.offset());
        }
    });
}   // close() waits for buffered records to be sent before it returns
./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic shop-orders \
  --command-property acks=all \
  --reader-property parse.key=true --reader-property key.separator=:
>o-3:placed
$ python tiny_producer.py
ok partition=1 offset=0

Key o-3 landed in partition 1 because murmur2("o-3") modulo 3 is 1 (you saw the same thing in the page 02 lab). The offset is whatever comes next in that partition; on a fresh topic it is 0.

Notice the big word: asynchronous. send() / produce() returns almost at once, before the record has reached any broker. It only puts the record in a memory buffer. You learn the real outcome later, in the callback (or by waiting on the Java Future). If your program exits without flush() or close(), records still in the buffer are simply lost.

One producer per process. A producer is thread-safe and holds connections, buffers and a background thread. Create it once and share it. Creating a producer per request is a classic beginner bug: every call pays the metadata lookup and a new connection, and nothing ever gets batched.
