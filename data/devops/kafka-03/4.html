Batching, linger and compression

Batching is the single biggest reason Kafka producers are fast. Two settings control it, and a batch is sent when either one triggers first:

  • batch.size (default 16384 bytes = 16 KiB): the size of one batch for one partition. When the batch is full, it is ready to send right away.
  • linger.ms (default 5 ms since Kafka 4.0; it was 0 before): how long the producer will wait for more records to join a batch that is not full yet. Old blog posts that say "the default is 0" are out of date.

Why bigger batches help so much

  • Fewer requests. Every request has fixed costs: a network round trip, request headers, a trip through the broker's network and I/O threads. One 64 KiB request is much cheaper than a hundred 640-byte requests.
  • Better compression. Compression works on the whole batch, not record by record. JSON events in one batch share lots of repeated field names, so a full batch shrinks far more than a lone record.
  • Cheaper all the way down. The broker stores the batch as it arrived, still compressed, and consumers receive it the same way and decompress it themselves. Fewer bytes on the producer's network, on the broker's disk, in replication traffic and on the consumer's network. (The disk-and-network side of that story is on page 07.)

Compression choices

compression.typeGood forNote
none (default)Already-compressed data (images, encrypted blobs)No CPU cost, most bytes.
lz4A common default choice for high-volume, low-latency trafficVery fast, moderate ratio.
zstdSaving network and storage costBetter ratio, a bit more CPU. Needs brokers and clients that support it (any recent version does).
snappyOlder setupsFast, similar role to lz4.
gzipMaximum ratio when CPU is cheapSlowest of the group.

Topic-level compression: topics have their own compression.type, which defaults to producer ("keep whatever the producer used"). If you set a topic to, say, gzip while producers send lz4, the broker must decompress and recompress every batch, which burns broker CPU. Usually leave the topic at producer.

From your world

linger.ms is Nagle's algorithm (or TCP_CORK) for Kafka: hold small writes briefly so they can go out together. It is also interrupt coalescing on a NIC: trade a tiny, bounded delay for far fewer interrupts. linger.ms=0 is like TCP_NODELAY. Where this breaks: Nagle waits for an ACK of in-flight data, which can stall for a full RTT; linger.ms is a plain timer with a hard upper bound, so the worst-case extra delay is known in advance.
