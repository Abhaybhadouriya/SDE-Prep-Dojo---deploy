Quick quiz

Your code calls producer.send(record) and it returns. What do you know?

  1. The record is stored on the leader
  2. The record is in the producer's memory buffer; the outcome comes later in the callback or Future
  3. The record is replicated to all followers
send() is asynchronous. It serializes, partitions and buffers, then returns. Only the callback (or Future.get()) tells you whether it was stored.

With linger.ms=5 and batch.size=16384, when is a batch sent?

  1. Exactly every 5 ms
  2. Only when it reaches 16 KiB
  3. When it reaches 16 KiB or 5 ms have passed, whichever comes first
Either trigger makes a batch ready. Busy partitions fill batches quickly and rarely wait the full linger time.

Topic with RF 3 and min.insync.replicas=2. Two of the three replicas go down. What happens to an acks=all producer?

  1. Writes fail with NOT_ENOUGH_REPLICAS (retried until the delivery timeout)
  2. Writes succeed on the one remaining replica
  3. Writes are silently dropped
The ISR is now 1, below the minimum of 2, so the leader refuses acks=all writes. You get an error instead of silent loss on a single copy.

Which setting makes acknowledged data most likely to be lost if the leader crashes right after replying?

  1. acks=all with min ISR 2
  2. acks=1
  3. enable.idempotence=true
With acks=1 the leader replies after its own write; if followers have not copied it yet, a new leader takes over without the record.

The idempotent producer removes duplicates caused by...

  1. Your application calling send() again after an error
  2. Consumers processing a record twice after a rebalance
  3. The producer's own retries within one session
Sequence numbers are per producer ID and partition. An app-level resend is a new record, a restart gets a new ID, and consumers are a separate problem.

A Java service and a Python (confluent-kafka) service both write key o-3 to the same topic with default settings. What can happen?

  1. The key can land in different partitions, breaking per-key order
  2. Nothing; all clients use the same hash
  3. The broker re-partitions the records to fix it
librdkafka's default partitioner hashes with CRC32; Java uses murmur2. Set partitioner=murmur2_random in librdkafka clients.

Your web handler's send() calls hang for up to a minute when Kafka is slow. Which setting controls that?

  1. delivery.timeout.ms
  2. max.block.ms
  3. linger.ms
max.block.ms (60 s by default) limits how long send() may block waiting for metadata or buffer space. delivery.timeout.ms is the background deadline after send() returns.

Why does compression work better with larger batches?

  1. The broker compresses again after each batch
  2. Larger batches use a different algorithm
  3. Compression runs on the whole batch, so repeated patterns across records shrink together
Records in a batch are compressed as one block, and the block stays compressed on the broker and on the way to consumers.
