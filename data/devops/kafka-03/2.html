Inside send(): the full journey

You said "no magic", so here is every hop, with the thread that does it. The Java client is the reference implementation, and librdkafka (used by Python, Go's confluent client, .NET and C/C++) follows the same shape. Click Next or Play.

  1. Your code calls send(). In Java, any configured interceptors run first. If the producer does not yet have metadata for the topic, this call blocks (up to max.block.ms, default 60 s) while it fetches it.
  2. Serialize. The key serializer and value serializer turn your objects into bytes (string, JSON, Avro, Protobuf). Kafka itself only ever sees bytes. A serialization error fails right here, on your thread.
  3. Choose the partition. If you set a partition explicitly, that wins. Otherwise a key is hashed (murmur2(key) % partitions in Java), and a record with no key goes to the current "sticky" partition. Here o-3 lands in P1.
  4. Append to the accumulator. The record joins the open batch for P1 in the RecordAccumulator, an in-memory set of per-partition queues capped by buffer.memory (32 MiB). send() returns a Future now. Nothing has gone over the network yet.
  5. The Sender thread wakes up. This one background thread checks which batches are ready (full, or linger.ms expired), groups ready batches by leader broker, and packs them into one ProduceRequest per broker (up to max.request.size, 1 MiB).
  6. The leader writes. The leader broker of P1 checks the batch, appends it to the end of its partition log and gives it offsets. Followers fetch the new data. How long the leader waits before replying depends on acks.
  7. The ack comes back. The Sender thread receives the reply, completes each record's Future and runs your callback with the partition and offset (or an error). Retriable errors are re-queued instead, as explained below.

Two threads, one buffer between them. That is the whole design. Your thread does cheap CPU work (serialize, hash, copy into a buffer) and returns. The I/O thread does the slow network work in bulk. This split is why a single producer can push a very large number of small records per second: the expensive parts happen once per batch, not once per record.

From your world

This is the transmit path of a NIC driver. send() is like the stack placing a packet on the TX ring; it returns before the packet is on the wire. The Sender thread is like the DMA engine draining the ring in bursts, and the callback is the TX-completion interrupt that tells you the descriptor is done. buffer.memory is the ring size. Where this breaks: a TX completion only says "the packet left this host"; a Kafka ack can mean "stored on three machines" if you ask for it with acks=all. And a producer never drops on a full ring; it blocks the caller instead (more on that in errors and backpressure).

Java gotcha: callbacks run on the producer's single I/O thread. If your callback does something slow (a database write, a blocking HTTP call, a long log line under a lock), it stalls every send of that producer. Keep callbacks tiny; hand real work to another executor. In Python confluent-kafka, callbacks run inside your own calls to poll() or flush() - if you never call poll(), you never hear about failures at all.
