Retries and the idempotent producer

Stop here for SDE-1? If you can explain batching, keys and acks, you are in good shape for most SDE-1 rounds. Everything from here down is what SDE-2 interviewers probe: what goes wrong on retries, timeouts and backpressure.

Networks fail in an annoying way: sometimes a request arrives and is written, but the reply is lost on the way back. The producer cannot tell this apart from "the request never arrived". So it does the only sensible thing and retries. Without protection, that retry writes the same batch a second time: a duplicate.

Retries also cause a second problem: reordering. A producer can have several requests "in flight" to the same broker at once (max.in.flight.requests.per.connection, default 5). If batch 1 fails and batch 2 succeeds, then batch 1 is retried, the log ends up as 2, 1.

  1. Send. At start-up, the idempotent producer gets a producer ID (PID) and an epoch from the cluster. Every batch it sends to a partition carries the PID and a sequence number that increases per partition: 0, 1, 2...
  2. Written, but the ack is lost. The leader appends the batch at offset 42 and remembers "PID 7, P1, last sequence 0". The reply never reaches the producer (a timeout, a dropped connection, a leader change).
  3. Retry. The producer does not know the batch was written, so it sends the same batch again with the same sequence number 0.
  4. Duplicate detected. The broker sees sequence 0 from PID 7 again, does not append anything, and answers success. The record exists exactly once. If a sequence number arrives with a gap (say 2 before 1), the broker rejects it, which is how ordering is kept with up to 5 requests in flight.
  5. Without idempotence, the retry looks like brand-new data and gets offset 43. Every consumer now sees "o-3 paid" twice. This is why idempotence became the default.

Idempotence (enable.idempotence=true) has been the default in the Java client since Kafka 3.0. It needs acks=all, retries > 0 and max.in.flight.requests.per.connection <= 5. The limit of 5 exists because the broker remembers the metadata of the last 5 batches per producer and partition; that window is what lets it detect duplicates and gaps among in-flight requests. In practice, idempotence is close to free: it adds a few bytes per batch.

Silent downgrade: in the Java client, if you did not set enable.idempotence yourself and you set a conflicting option such as acks=1, idempotence is quietly switched off. If you set enable.idempotence=true explicitly together with a conflicting option, the producer refuses to start with a config error. And in librdkafka clients (Python, .NET, Go-confluent) enable.idempotence defaults to false; you must turn it on. When safety matters, set it explicitly.

What idempotence does NOT cover

This is the part interviewers love, because many candidates over-claim. The idempotent producer removes duplicates caused by its own internal retries, within one producer session, per partition. It does not help with:

  • Your application resending. If your code catches an error and calls send() again, that is a new record with a new sequence number. The broker cannot know it is the "same" order event.
  • A restarted process. A new producer instance gets a new PID, so the broker has no memory of what the old one sent. If the old process crashed after sending but before recording that it sent, the restarted one may send again.
  • Atomic writes to several partitions or topics. "Write to orders and payments, all or nothing" needs transactions, which add a stable transactional.id and fence "zombie" instances. That is page 06.
  • Consumers. A consumer can still process a record twice after a crash or a rebalance (page 04). End-to-end "exactly once" needs idempotent consumers too.

The practical rule: keep idempotence on, and also give every business event its own event ID (for example orderId + status or a UUID chosen once, before the first attempt) so consumers can drop repeats. That event-ID habit is what payment systems rely on; see Design a Payment System.

From your world

The PID plus per-partition sequence number is TCP's sequence number, one level up: the receiver drops a segment it already has and notices a gap. The producer epoch is like a connection generation (think of a new ISN after a reconnect). Where this breaks: TCP state dies with the connection, but Kafka keeps producer state on the broker across reconnects and leader changes (it is saved with the log), so a retry to a new leader is still de-duplicated. What is lost is the producer's identity when your process restarts.
