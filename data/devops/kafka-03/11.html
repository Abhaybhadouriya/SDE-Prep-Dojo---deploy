Common mistakes and gotchas

  1. Fire and forget by accident. Calling send() without a callback and never checking the Future. Errors happen silently. Always handle the callback, and count failures in a metric.
  2. Calling .get() on every send. The opposite mistake: producer.send(r).get() waits for each record before sending the next, so you get one record per round trip and no batching. Only block when you truly need a synchronous answer.
  3. Exiting without flush() or close(). Records still in the buffer vanish. Hook producer shutdown into your app's shutdown, including in containers that get SIGTERM from Kubernetes (pods get a grace period for exactly this).
  4. A new producer per request. No batching, a metadata fetch and new connections every time. Create one per process and share it.
  5. Turning off idempotence by setting acks=1 for "speed", then wondering about duplicates and reordering after a broker restart.
  6. Mixed partitioners across languages. librdkafka's default hash is CRC32, Java's is murmur2. Set partitioner=murmur2_random in librdkafka clients.
  7. Application-level resend loops. Wrapping send() in your own retry loop creates duplicates the broker cannot detect. Let the producer retry; raise delivery.timeout.ms if needed; put a business event ID in every record.
  8. Huge records. Anything over about 1 MiB fails (RecordTooLargeException) unless the producer, broker and topic limits are all raised. Store big blobs in object storage and send a link (the claim-check pattern).
  9. Slow work in the callback (Java). It runs on the single I/O thread and stalls every send.
  10. Advertised listener problems (Docker and Kubernetes). The bootstrap connection works, but metadata returns a broker address your app cannot reach, so every send times out. Check advertised.listeners first when "it connects but nothing is delivered". The Kubernetes deploy page deals with this.
