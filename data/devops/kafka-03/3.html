Choosing the partition

Page 02 showed why the key matters: same key, same partition, so events for one key stay in order. Here is how the producer decides, in priority order:

  1. You named a partition. new ProducerRecord<>("orders", 2, key, value) always goes to partition 2. Rarely needed.
  2. A custom partitioner is configured. Set partitioner.class to your own class implementing Partitioner, and it decides. Used for special routing, for example sending a few known giant customers to dedicated partitions.
  3. The record has a key. Java: toPositive(murmur2(keyBytes)) % numPartitions. Deterministic: the same key and the same partition count always give the same answer, on every machine.
  4. No key. Since Kafka 3.3 the producer uses the uniform sticky strategy (KIP-794; a KIP is a Kafka Improvement Proposal, the numbered design document behind a feature, and you never need to memorise the numbers): it "sticks" to one partition until about a batch.size worth of data has gone there, then moves to another. It also leans away from partitions whose brokers are slow (adaptive partitioning).

Look at the last column: grow the topic to 4 partitions and four of these five keys move. That is why the partition count is a design decision, not a knob you turn on a busy day.

Why "sticky" and not round-robin?

Old clients (before 2.4) sent keyless records round-robin, one record per partition in turn. With 30 partitions, 30 records made 30 tiny batches, and each batch waited for its own linger.ms. The sticky idea (KIP-480 in 2.4, improved to "uniform sticky" in 3.3 by KIP-794) fills one batch at a time. Over a few seconds, the load still evens out across partitions, but each request carries far more data. Same records, fewer and bigger requests.

From your world

Keyed partitioning is ECMP flow hashing. The key is the 5-tuple; the partition is the next-hop link. Hashing keeps one flow on one link, so its packets stay in order, and adding a link re-hashes flows - exactly like adding a partition. A hot key is an elephant flow pinned to one link. Sticky partitioning for keyless data is closer to flowlet switching: send a burst down one path, then switch at a burst boundary. Where this breaks: ECMP members come and go all the time and routers use resilient hashing to limit churn. Kafka's default partitioner has no consistent hashing, so adding a partition moves most keys.

Mixed-language trap: clients built on librdkafka (Python confluent-kafka, .NET, Go's confluent client) use a different default partitioner, consistent_random, which hashes keys with CRC32. A Java service and a Python service writing the same keys to the same topic will put them in different partitions, which silently breaks per-key ordering. Fix: set "partitioner": "murmur2_random" in every librdkafka client so it matches Java.
