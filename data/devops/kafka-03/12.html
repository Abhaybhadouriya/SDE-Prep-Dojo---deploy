Interview questions

The 60-second answer: "How does a Kafka producer work, and how do you make it reliable?"
"A producer is a client library in the application. When I call send(), it serializes the key and value, picks a partition - by hashing the key, so the same key always goes to the same partition and stays in order - and appends the record to an in-memory batch for that partition. send() returns right away. A background thread sends a batch when it is full (batch.size) or when linger.ms runs out, groups batches per leader broker, and compresses them per batch, which is where most of Kafka's producer throughput comes from. Reliability is about acks: with replication factor 3, min.insync.replicas=2 and acks=all, a write is only acknowledged once two copies exist, so one broker can fail without data loss. Retries can create duplicates or reorder data, so I keep the idempotent producer on: each batch carries a producer ID and sequence number and the broker drops repeats. That covers retries inside one session; for atomic multi-partition writes I would use transactions, and consumers still need to be idempotent."

Walk me through what happens when a producer calls send().

On the calling thread: interceptors run, the producer makes sure it has metadata for the topic (blocking up to max.block.ms if not), the serializers turn key and value into bytes, the partitioner picks a partition (explicit partition, custom partitioner, murmur2 of the key, or the sticky partition for null keys), and the record is appended to that partition's open batch in the RecordAccumulator. send() returns a Future. On the Sender (I/O) thread: batches that are full or past linger.ms are drained, grouped by leader broker into ProduceRequests, and sent. The leader appends, waits according to acks, and replies with the base offset. The Sender completes the Futures and runs callbacks, or re-queues the batch on a retriable error until delivery.timeout.ms.

How to answer

Split it into "my thread" and "the I/O thread" - that structure alone signals understanding. Name the accumulator and the two batching triggers. End with what the ack means under each acks value.

Likely follow-ups
  • Where can send() block? (Metadata fetch and a full buffer.memory, both limited by max.block.ms.)
  • How does the producer find the leader? (Cached metadata, refreshed on NOT_LEADER_OR_FOLLOWER.)
  • Is the producer thread-safe? (Yes; share one per process.)
Explain acks=0, 1 and all. Is acks=all enough to never lose data?

acks=0: no reply; any failure loses data. acks=1: the leader replies after writing to its own log; if it dies before followers copy the batch, acknowledged data is lost. acks=all: the leader replies after all in-sync replicas have it. It is not enough on its own, because the ISR can shrink to just the leader; then "all" means one copy. You need replication factor 3 and min.insync.replicas=2, so the leader rejects writes (NOT_ENOUGH_REPLICAS) when fewer than two copies are in sync, and unclean leader election left disabled (the default). Even then, the producer must check its callbacks, and consumers must commit offsets only after processing, or data is lost at the edges rather than in Kafka.

How to answer

Give the three meanings in one line each, then say "acks=all is necessary but not sufficient" and add min ISR. Close with the trade-off: with two of three replicas down, writes stop by design.

Likely follow-ups
  • What does acks=1 really wait for - disk? (The leader's log in page cache, not an fsync.)
  • What is the latency cost of acks=all? (The slowest in-sync follower's fetch; small within one region.)
  • What is unclean leader election?
How does the idempotent producer prevent duplicates, and what does it not protect against?

The producer gets a producer ID and epoch when it starts. Every batch to a partition carries a sequence number that increases per partition. The leader remembers recent sequence numbers for each producer and partition (the last 5 batches), so a retried batch with a sequence it has already written is acknowledged without being appended again, and a gap is rejected as out of order. That is why max.in.flight.requests.per.connection must be at most 5, and why ordering survives retries. It does not cover application-level resends (a new record, new sequence), a producer restart (new PID), atomic writes across partitions (that needs transactions with a transactional.id), or duplicate processing on the consumer side.

How to answer

Mechanism (PID + sequence per partition), the guarantee (no duplicates or reordering from internal retries), then the limits. The limits are what interviewers are really testing. A TCP sequence-number analogy is a nice touch.

Likely follow-ups
  • How do transactions fence a zombie producer? (Epoch bump on initTransactions().)
  • Is idempotence on by default? (Java since 3.0, unless a conflicting setting quietly disables it; not in librdkafka.)
  • How would you de-duplicate on the consumer side?
How would you tune a producer for maximum throughput? What do you give up?

Make batches bigger and fewer: raise linger.ms (say 20-100 ms) and batch.size (64 KiB to 1 MiB), turn on compression.type=lz4 or zstd, give buffer.memory room for many in-flight batches, keep idempotence on with up to 5 in-flight requests, and either use a well-spread key or no key so the sticky partitioner fills batches. Make sure the topic has enough partitions across enough brokers to parallelise writes. The price is latency when traffic is light (up to linger.ms), more memory, and compression CPU on both ends. If loss is acceptable, acks=1 removes the follower wait, but I would only do that for data like metrics. I would measure before and after with kafka-producer-perf-test.sh and watch the producer metrics for average batch size, compression ratio and request latency.

How to answer

Lead with the principle ("amortise per-request cost over bigger batches"), list the knobs in that light, name the cost of each, and finish with "and I would measure it". Avoid quoting magic throughput numbers.

Likely follow-ups
  • Now tune for low latency instead. (linger.ms 0-5, small batches, maybe no compression; keep acks=all if durability matters.)
  • Why does compression get better with bigger batches?
  • Which side is usually the real bottleneck - producer or consumer?
Producers are timing out in production. How do you debug it?

First read the underlying errors, not just the final timeout: retry warnings show the real cause. Then check, in order: can the app reach the broker addresses that metadata returns (advertised.listeners, a frequent Docker/Kubernetes issue); does the topic exist with leaders for every partition; is the ISR below min.insync.replicas (NOT_ENOUGH_REPLICAS, under-replicated partitions); is buffer.memory full so send() blocks on max.block.ms (producer metrics for buffer available bytes and record queue time); is a quota throttling the client; are TLS or SASL failing; are brokers saturated (request queue time, network and I/O thread idle ratios). Fix the cause, and make sure request paths have a short max.block.ms and a fallback so a Kafka problem does not take the web tier down.

How to answer

Show a method: client side first (config, connectivity, buffer), then cluster side (leaders, ISR, load), then the protection you would add. Mention that a "timeout" is usually a symptom wrapping a retriable error.

Likely follow-ups
  • What metrics would you alert on for producers? (Error rate, retry rate, record queue time, request latency, buffer exhaustion.)
  • How does delivery.timeout.ms relate to request.timeout.ms?
Your service writes an order to its database and then publishes to Kafka. What can go wrong?

That is the dual-write problem. The DB commit and the Kafka send are not atomic. If the service crashes after the commit but before the send succeeds, the order exists but no event is published, so inventory and notifications never hear about it. If you send first and the DB commit fails, consumers act on an order that does not exist. Retrying the send from application code can also publish duplicates. The standard fix is the transactional outbox: write the event into an outbox table in the same DB transaction as the order, and have a relay (a poller or Debezium CDC) publish outbox rows to Kafka with an idempotent producer. The relay is at-least-once, so consumers de-duplicate by event ID.

How to answer

Name the problem ("dual write"), give both crash orderings, then the outbox fix, then the remaining duty on consumers. This question appears in many order-flow and payment designs.

Likely follow-ups
  • Why not use Kafka transactions for this? (They cover Kafka writes only, not your database.)
  • Poller vs CDC for the relay?
  • See Distributed Transactions & Event-Driven Data.

Scenario: duplicate "payment captured" events after a broker restart

During a routine rolling restart of the Kafka brokers, the payments team sees some payment.captured events twice in the topic, and a few customers get two confirmation emails. The producer is a Python service. Nobody changed producer code. What happened and how do you fix it?

Weak answer: "Kafka is at-least-once, duplicates happen, tell the email team to ignore them." It is not an explanation, and it leaves the duplicates in the source of truth.

Strong answer: "When a leader moves during a restart, in-flight requests can be written but not acknowledged, so the producer retries. A Python confluent-kafka producer does not enable idempotence by default, so those retries created real duplicates; with several requests in flight they may even be reordered. Fix one: set enable.idempotence=true (which also forces acks=all and safe in-flight limits) and verify the effective config at startup. Fix two: check the service does not resend on its own after an error callback; if it must, it should reuse the same business event ID. Fix three, defence in depth: the email and ledger consumers de-duplicate by paymentId (a unique constraint or a processed-IDs table with a TTL). I would also add a check that rolling restarts happen one broker at a time, only when there are no under-replicated partitions."

Likely follow-ups
  • Would Java have had the same problem? (Not with defaults since 3.0, unless someone set acks=1.)
  • Would transactions help here? (Only if you also need atomic multi-partition writes; idempotence is enough for retry duplicates.)

Scenario: the checkout API freezes when Kafka is slow

On a sale day, one Kafka broker becomes very slow. Within a minute, your checkout API stops answering entirely, even for requests that do not need Kafka. Thread dumps show every request thread stuck inside KafkaProducer.send().

Weak answer: "Add more API servers." More servers will freeze the same way, because each one blocks on the same slow broker.

Strong answer: "The producer buffer filled up because batches to the slow broker could not drain, so send() started blocking for up to max.block.ms, 60 seconds by default, on request threads. The thread pool ran out and the whole API stopped. Immediate fix: lower max.block.ms to something like a few hundred milliseconds in request paths, catch the exception and fail fast or fall back, and bulkhead Kafka calls onto their own small executor so they cannot eat every request thread. Structural fix: move publishing out of the request path with a transactional outbox, so checkout only depends on its own database and a relay publishes to Kafka at its own pace. Then find out why the broker was slow (disk, GC, a hot partition, replication) and add alerts on producer buffer exhaustion and request latency."

Likely follow-ups
  • Why did requests that do not use Kafka also hang? (Shared thread pool exhaustion.)
  • What is a bulkhead? (Isolating resources per dependency; see resilience patterns.)
