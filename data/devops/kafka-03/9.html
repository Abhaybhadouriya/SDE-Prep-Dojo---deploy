Lab: watch the producer work

Use the single-broker container from the track overview (Docker basics are on Running & Managing Containers). Open a shell inside the container for the Kafka tools:

docker run -d --name broker -p 9092:9092 apache/kafka:4.4.0   # skip if already running
docker exec -it --workdir /opt/kafka/bin broker sh

1. Keyed records and delivery reports (Python, on your laptop)

./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic producer-lab --partitions 3
exit
pip install confluent-kafka

Save this as keyed_producer.py on your laptop and run it:

from confluent_kafka import Producer

p = Producer({
    "bootstrap.servers": "localhost:9092",
    "enable.idempotence": True,
    "acks": "all",
    "linger.ms": 5,
    "compression.type": "lz4",
    "partitioner": "murmur2_random",
})

def on_delivery(err, msg):
    if err is not None:
        print("FAILED:", err)
    else:
        print(f"ok key={msg.key().decode()} partition={msg.partition()} offset={msg.offset()}")

events = [("o-1", "placed"), ("o-2", "placed"), ("o-3", "placed"), ("o-1", "paid")]
for key, status in events:
    p.produce("producer-lab", key=key, value=status, on_delivery=on_delivery)
    p.poll(0)                     # run any callbacks that are ready; never blocks

left = p.flush(10)                # wait up to 10 s
print("still undelivered:", left)
$ python keyed_producer.py
ok key=o-1 partition=0 offset=0
ok key=o-2 partition=0 offset=1
ok key=o-1 partition=0 offset=2
ok key=o-3 partition=1 offset=0
still undelivered: 0

Three things to notice. Both o-1 events are in partition 0, in the order sent (offset 0, then 2). The callbacks arrive grouped by batch, so the line for o-3 can print before or after the partition 0 lines on your machine - order across partitions is not promised. And flush() returned 0, meaning nothing was left in the buffer. Now delete the p.flush(10) line and run it again: most likely nothing prints at all, because the program exits while the records are still in memory.

2. Break it: acks=all versus too few replicas

A single broker can only hold one replica. Create a topic that demands two in-sync replicas, then write to it with acks=all. Short timeouts make the failure show up in 15 seconds instead of 2 minutes.

docker exec -it --workdir /opt/kafka/bin broker sh
./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic strict \
  --partitions 1 --config min.insync.replicas=2
./kafka-console-producer.sh --bootstrap-server localhost:9092 --topic strict \
  --command-property acks=all \
  --command-property delivery.timeout.ms=15000 \
  --command-property request.timeout.ms=5000
>hello
[...] WARN [Producer clientId=console-producer] Got error produce response with correlation id 6 on topic-partition strict-0, retrying (2147483646 attempts left). Error: NOT_ENOUGH_REPLICAS (org.apache.kafka.clients.producer.internals.Sender)
[...] WARN [Producer clientId=console-producer] Got error produce response with correlation id 8 on topic-partition strict-0, retrying (2147483645 attempts left). Error: NOT_ENOUGH_REPLICAS (org.apache.kafka.clients.producer.internals.Sender)
... (repeats with backoff)
[...] ERROR Error when sending message to topic strict with key: null, value: 5 bytes with error: (org.apache.kafka.clients.producer.internals.ErrorLoggingCallback)
org.apache.kafka.common.errors.TimeoutException: Expiring 1 record(s) for strict-0:15006 ms has passed since batch creation

Read it like an on-call engineer. The final error says only "timeout". The real reason is in the retry warnings above it: NOT_ENOUGH_REPLICAS, a retriable error, retried with backoff until the 15 s delivery deadline ran out. Many production "Kafka timeout" tickets are exactly this. Now press Ctrl+C and start the producer again with --command-property acks=1: the same write succeeds immediately, because min.insync.replicas only guards acks=all writes. Safe settings refuse unsafe conditions; weak settings do not even notice. (Exact log wording can vary a little between versions.)

3. Measure batching with the perf tool

./kafka-topics.sh --bootstrap-server localhost:9092 --create --topic perf --partitions 3
# A: no waiting, small batches, no compression
./kafka-producer-perf-test.sh --topic perf --num-records 300000 --record-size 500 --throughput -1 \
  --bootstrap-server localhost:9092 --command-property linger.ms=0 batch.size=16384 compression.type=none
# B: wait a little, bigger batches, lz4
./kafka-producer-perf-test.sh --topic perf --num-records 300000 --record-size 500 --throughput -1 \
  --bootstrap-server localhost:9092 --command-property linger.ms=20 batch.size=131072 compression.type=lz4

The tool prints a progress line every few seconds and one summary line at the end, in this shape (p50/p95/p99 are percentiles: p99 = 99 of every 100 records were acknowledged faster than this, so it shows the slow tail an average hides):

300000 records sent, <R> records/sec (<M> MB/sec), <avg> ms avg latency, <max> ms max latency, <p50> ms 50th, <p95> ms 95th, <p99> ms 99th, <p99.9> ms 99.9th.

Compare the records/sec and the latency percentiles of run A and run B on your own machine; a laptop with one broker will give very different numbers from a real cluster, so do not quote them as "Kafka's speed". The perf tool's payload is random text, so compression gains here are smaller than with real JSON. Try a third run with acks=1 to see what the replication wait costs (on one broker, almost nothing - another reason laptop numbers mislead). The flags are the Kafka 4.2+ names (KIP-1147): --bootstrap-server plus --command-property replace the old --producer-props bootstrap.servers=..., and --command-property replaces --producer-property. On a pre-4.2 image use the old names.
