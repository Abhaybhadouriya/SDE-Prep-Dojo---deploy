The NIC ring: a lock-free single-producer single-consumer queue

With exactly one producer and exactly one consumer, you do not need a lock at all. The producer is the only writer of tail; the consumer is the only writer of head. Each side only reads the other's index. All you need is the right memory ordering, so that the consumer cannot see the new tail before it can see the data in the slot. This is the structure of NIC descriptor rings, kfifo, and the Linux tracing ring buffer.

template <typename T, size_t N>          // N must be a power of two
class SpscRing {
public:
    bool push(const T& v) {               // producer thread only
        size_t t = tail_.load(std::memory_order_relaxed);
        if (t - head_.load(std::memory_order_acquire) == N) return false;   // full
        slots_[t & (N - 1)] = v;                      // 1. write the data
        tail_.store(t + 1, std::memory_order_release); // 2. then publish the index
        return true;
    }
    bool pop(T& out) {                    // consumer thread only
        size_t h = head_.load(std::memory_order_relaxed);
        if (h == tail_.load(std::memory_order_acquire)) return false;       // empty
        out = slots_[h & (N - 1)];
        head_.store(h + 1, std::memory_order_release); // give the slot back
        return true;
    }
private:
    T slots_[N];
    std::atomic<size_t> head_{0}, tail_{0};           // free-running counters; unsigned wrap is fine
};
// Our run: 1,000,000 items through a 256-slot ring, sum checked exactly; the producer
// sometimes found the ring full and had to retry (a NIC would drop and count instead).

Only for one-to-one. The moment you have two producers or two consumers, two threads can claim the same slot. Multi-producer lock-free queues need compare-and-swap loops and are much harder to get right (the JDK's ConcurrentLinkedQueue and the LMAX Disruptor are examples). In an interview, use a blocking queue and mention SPSC rings as the high-performance special case; that shows depth without wasting your 45 minutes.

Other advanced points worth one sentence each in an interview:

  • Batching. drainTo(list, max) takes many items under one lock acquisition, the same reason NAPI processes a budget of packets per poll instead of one interrupt per packet.
  • Two locks. LinkedBlockingQueue uses separate put and take locks, so a producer and a consumer can work at the same time when the queue is neither empty nor full.
  • False sharing. If head and tail sit on the same cache line, the two cores keep stealing the line from each other. High-performance rings pad them onto separate lines.
  • Many queues instead of one. One queue per consumer (or per key hash) removes contention and keeps per-key order, like RSS spreading flows across per-CPU RX queues, or Kafka partitions.
