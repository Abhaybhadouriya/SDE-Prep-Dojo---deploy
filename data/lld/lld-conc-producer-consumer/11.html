Interview questions

Implement a bounded blocking queue.

Ring array plus head, tail, count; one ReentrantLock; two conditions notFull and notEmpty. put: lock, while (count == cap) notFull.await(), insert, notEmpty.signal(), unlock in finally. take mirrors it. Mention that ArrayBlockingQueue is built this way.

How to answer

State the interface first, then write Way 2. Call out while vs if, why two conditions allow signal(), and unlock in finally. Offer the semaphore version if they want alternatives.

Likely follow-ups
  • Add offer(item, timeout). (Use awaitNanos and track remaining time.)
  • Add size(); does it need the lock? (Yes, for visibility.)
  • Make it support many producers and consumers efficiently. (Two locks like LinkedBlockingQueue, or sharding.)
With wait/notify, why notifyAll and not notify?

Producers and consumers share one wait set. notify() may wake a thread of the same kind (a consumer waking a consumer), which re-checks, finds nothing to do and sleeps again, while the thread that could make progress keeps sleeping. Every thread can end up asleep. notifyAll() wakes everyone so the right one always gets a chance. Separate Conditions fix the waste.

How to answer

Describe the exact bad interleaving with two consumers and one producer, then give the two fixes.

Likely follow-ups
  • When is notify() safe? (All waiters wait for the same condition and any one can proceed.)
How do you shut down consumers without losing messages?

Poison pill: after every producer has finished (join or latch), put one pill per consumer; each consumer exits when it takes one. FIFO order guarantees every earlier item is processed first. For "stop now", interrupt the workers and drain what is left with drainTo.

How to answer

Give the three rules (one per consumer, only after producers finish, pill cannot be real data) and contrast with interrupts in one line.

Likely follow-ups
  • The number of consumers is not known. (Consumer re-puts the pill before exiting, or use an executor's shutdown + awaitTermination.)
  • What if a consumer crashes mid-item? (At-least-once: acknowledge after processing, like Kafka committing offsets.)
Producers are faster than consumers. What do you do?

First, bound the queue. Then choose a policy by item type: block producers (nothing may be lost), time out and reject to the caller (they can retry; HTTP 429), drop newest or oldest (telemetry, positions). Then fix the rate: add consumers, batch with drainTo, or partition so consumers do not contend. Monitor queue depth as the early-warning signal.

How to answer

"Bound, choose a policy, scale consumers, measure depth." Name a concrete example for each policy.

Likely follow-ups
  • Why is new LinkedBlockingQueue() dangerous? (Default capacity is Integer.MAX_VALUE.)
  • How does this map to a thread pool's rejection policies?
Design a multithreaded in-memory message queue with topics where one slow subscriber must not block others.

Each topic keeps an append-only list of messages. Each subscriber has its own worker thread and its own offset. Publishing appends under the topic's lock and signals the topic's condition. Each subscriber worker waits on that condition while its offset equals the topic size, then processes messages one by one and advances its offset. A slow subscriber only falls behind; it never blocks the publisher or other subscribers. Bound memory with retention (drop messages every subscriber has passed).

How to answer

Entities (Topic, Message, Subscriber, SubscriberWorker), the offset idea, then the wait/signal loop, then retention and reset-offset as extensions.

Likely follow-ups
  • Replay from an offset? (Set the subscriber's offset and signal.)
  • Consumer groups? (One offset per group, a queue per partition.)
Can a queue be thread-safe with no locks at all?

Yes for one producer and one consumer: a power-of-two ring where each side writes only its own index, with a release store after writing data and an acquire load before reading it. NIC descriptor rings and kfifo work this way. With several producers or consumers you need CAS loops (ConcurrentLinkedQueue) or a lock.

How to answer

Draw head and tail, show the release/acquire pair, and state the single-writer-per-index rule. Mention false sharing padding as a performance detail.

Likely follow-ups
  • Why power-of-two size? (Mask instead of modulo, and free-running counters wrap cleanly.)
ArrayBlockingQueue vs LinkedBlockingQueue vs SynchronousQueue?

ArrayBlockingQueue: fixed array, one lock, always bounded, predictable memory. LinkedBlockingQueue: nodes, separate put and take locks so both ends work in parallel, optionally bounded (pass a capacity). SynchronousQueue: no storage, every put waits for a take; a direct hand-off used when you want a new thread rather than queuing.

How to answer

One line each on storage, locking and bound, then when you pick each.

Likely follow-ups
  • Which does Executors.newFixedThreadPool use, and why is that a risk? (An unbounded LinkedBlockingQueue.)
