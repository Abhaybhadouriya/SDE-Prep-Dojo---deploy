Way 2: ReentrantLock with two Conditions

The waste in Way 1 comes from one shared wait set. A ReentrantLock can have several Conditions, so producers wait on notFull and consumers wait on notEmpty. Now every signal reaches the right kind of thread, and signal() (wake one) is safe: any waiting producer can use the one free slot.

final class ConditionBuffer<T> implements BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();   // producers wait here
    private final Condition notEmpty = lock.newCondition();   // consumers wait here

    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly();                  // a shutdown can interrupt a blocked producer
        try {
            while (count == items.length) notFull.await();
            items[tail] = item;
            tail = (tail + 1) % items.length;
            count++;
            notEmpty.signal();                     // one item arrived: wake ONE consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T item = (T) items[head];
            items[head] = null;
            head = (head + 1) % items.length;
            count--;
            notFull.signal();                      // one slot freed: wake ONE producer
            return item;
        } finally { lock.unlock(); }
    }
}
  1. The producer takes the lock and finds the buffer full (count equals capacity).
  2. notFull.await() atomically releases the lock and puts the producer to sleep on the notFull queue.
  3. The consumer takes the lock, removes A from the head and decrements count.
  4. The consumer signals notFull. Only producers sleep there, so signal() wakes the right kind of thread. Then it unlocks.
  5. The producer wakes, wins the lock back, re-checks the while condition (now there is space), writes E at the tail and signals notEmpty.

This is literally how ArrayBlockingQueue is built: one ReentrantLock and two conditions named notEmpty and notFull. The Condition interface's own Javadoc uses a bounded buffer as its example. If you write this version in an interview and then say "in production I would use ArrayBlockingQueue, which is implemented the same way", you have covered both what they test and what they want to hear.

The same shape can be built from semaphores, the textbook form from operating systems courses: a semaphore slots starting at capacity, a semaphore items starting at 0, and a mutex around the array. put does slots.acquire(), writes, items.release(); take does the mirror image. It is a nice answer to LeetCode's "Design Bounded Blocking Queue" (problem 1188), which asks for exactly this class with a size() method.

class SemaphoreQueue {        // LeetCode 1188 style, our own solution (SemaphoreBuffer in the demo)
    private final Deque<Integer> q = new ArrayDeque<>();
    private final Semaphore slots, items = new Semaphore(0);
    private final Object mutex = new Object();
    SemaphoreQueue(int capacity) { slots = new Semaphore(capacity); }

    void enqueue(int v) throws InterruptedException {
        slots.acquire();                                 // wait for a free slot
        synchronized (mutex) { q.addLast(v); }
        items.release();                                 // announce one item
    }
    int dequeue() throws InterruptedException {
        items.acquire();                                 // wait for an item
        int v;
        synchronized (mutex) { v = q.removeFirst(); }
        slots.release();                                 // announce one free slot
        return v;
    }
    int size() { synchronized (mutex) { return q.size(); } }
}
