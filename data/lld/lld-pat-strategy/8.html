When to use it, when not to

Use it when
  • There are several ways to do one job and the choice depends on configuration, the user, the city or the time (fees, payment, split, pricing, routing, matching, eviction, rate limiting).
  • A switch on a "mode" field appears, or appears in more than one method.
  • You need to change the algorithm at runtime, per object (per socket, per lot, per user).
  • You want to test each algorithm alone, or let other teams add algorithms without your source (plug-ins).
Avoid it when
  • There is one algorithm and no real second one in sight. An interface with one implementation is ceremony (YAGNI).
  • The choice never changes and is two lines long; a plain if is easier to read.
  • The "algorithms" need very different inputs. If every strategy needs its own extra parameters, the common interface is a lie.
  • The thing that changes is the object's own status (idle, paid, dispensing). That is State, not Strategy.

Design tips that interviewers notice

  • Pair it with a factory or registry. Strategy removes the if from the context, but someone still has to choose. Put that one decision in a factory, a map from config key to supplier, or a DI container, so it lives in exactly one place. The Simple Factory page shows the registry idea.
  • Prefer stateless strategies. Pass the data in, return the result. A stateless strategy can be a shared singleton and is safe across threads (no shared mutable state, no race: see immutability and safe publication). If a strategy must keep state (Reno's acked_ counter above), give each context its own instance.
  • Lambdas for small strategies. If the interface has one method, Java lambdas and Python functions remove the class boilerplate. Keep named classes for strategies with configuration or that need a good name in logs.
  • Compose strategies. A strategy that wraps another (WeekendSurcharge) or a list of them (discount rules applied in order) avoids a class per combination. That is Strategy meeting Decorator.
  • Keep the interface narrow. If you find yourself adding supportsBikes() or getDiscountForGold() to it, the strategies are not interchangeable any more.
