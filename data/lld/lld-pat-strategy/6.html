The kernel's strategies, in C

In C, a strategy is a struct of function pointers plus a pointer to it in the context. The shape, trimmed to the idea (not the exact kernel definitions):

/* Strategy interface */
struct tcp_congestion_ops {
    u32  (*ssthresh)(struct sock *sk);                       /* new threshold after loss */
    void (*cong_avoid)(struct sock *sk, u32 ack, u32 acked); /* grow cwnd */
    void (*set_state)(struct sock *sk, u8 new_state);
    u32  (*undo_cwnd)(struct sock *sk);
    char name[TCP_CA_NAME_MAX];
    struct module *owner;
    /* ... */
};

/* Concrete strategy: a module fills the table and registers it */
static struct tcp_congestion_ops my_cc = {
    .ssthresh   = my_ssthresh,
    .cong_avoid = my_cong_avoid,
    .undo_cwnd  = my_undo_cwnd,
    .name       = "mycc",
    .owner      = THIS_MODULE,
};
/* module init: tcp_register_congestion_control(&my_cc); */

/* Context: the TCP core calls through the pointer, never by name */
icsk->icsk_ca_ops->cong_avoid(sk, ack, acked);

From your world

The same idea shows up across the kernel wherever an administrator picks "how": the default congestion control in net.ipv4.tcp_congestion_control; the block-layer I/O scheduler per device (echo mq-deadline > /sys/block/sda/queue/scheduler, with bfq and kyber as other choices); the queueing discipline on an interface (tc qdisc replace dev eth0 root fq_codel); CPU frequency governors. Each is a named ops table, registered by a module, chosen per object at runtime. Where does per-algorithm private data go? In C the ops table is shared code, so the data lives elsewhere and you find it from the object you were given (inet_csk_ca(sk), or container_of() when the ops struct is embedded in a bigger one). A Java strategy object simply carries its own fields, and this is the pointer you would have computed. Notice the owner field: the kernel takes a module reference while a socket uses the algorithm, so the module cannot be unloaded under it. That is the refcounting side of "who owns the strategy object".

Is this Strategy or Bridge? The shapes are the same (an object holding a pointer to an ops table). Strategy fits when one context swaps one algorithm; Bridge fits when a whole abstraction layer (the VFS file API) sits on top of a whole implementation layer (filesystems), each growing on its own. See patterns in the Linux kernel.
