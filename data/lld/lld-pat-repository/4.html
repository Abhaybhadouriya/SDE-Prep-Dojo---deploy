How it works: one borrow, step by step

  1. The driver calls one use-case method on the service with ids, not objects. It knows nothing about maps.
  2. The service loads what it needs through repositories. Missing data comes back as an empty Optional, which the service turns into a named NotFoundException.
  3. A rule that spans entities (the two-loan limit) needs a query. The repository answers it in domain words: "open loans of this member".
  4. A rule about one entity's own state lives on the entity: a book refuses to be lent twice.
  5. The service writes changes back through the repositories. With a map this is a put; with a database it is an UPDATE and an INSERT inside one transaction.
  6. The driver gets a domain object back (or an exception) and decides how to print it.

Notice where the lock goes: on the service method. "Check the limit, then save" is a check-then-act sequence; two threads must not interleave between the check and the save. The repository's ConcurrentHashMap makes single operations safe, but only the service knows which operations form one unit. That is the same reason database transactions are opened in the service layer, not in each repository call.
