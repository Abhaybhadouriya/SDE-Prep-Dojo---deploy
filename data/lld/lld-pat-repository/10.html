In interviews

Nobody says "implement the Repository pattern". It is assumed. India product-company machine-coding rounds (Flipkart, PhonePe, Meesho, Razorpay, Groww) state "in-memory only, no DB", and the evaluation call almost always asks how you would add persistence. Write the layers from minute 10 and you have the answer ready.

  • Library management: exactly this page's example, plus fines and reservations.
  • BookMyShow and slot booking: ShowRepository, BookingRepository; the seat-lock rule sits in the booking service.
  • Splitwise: UserRepository, ExpenseRepository, a balance service.
  • Parking lot: tickets and spots behind repositories; the allocation strategy in the service.
  • Food delivery and quick commerce: order, restaurant and inventory repositories; reservation rules in services.
  • In-memory KV store: here the store is the product, so the "repository" becomes the core data structure.

Strong 30-second answer: "I keep three layers. Entities hold data and their own invariants. Repositories are interfaces with in-memory ConcurrentHashMap implementations, named in domain terms. Services run each use case, own cross-entity rules and the lock. Main wires them with constructor injection. To add MySQL I write a new repository class and change one line in main; services and tests stay as they are."
