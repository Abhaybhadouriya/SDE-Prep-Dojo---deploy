Where should the rule "a member may hold at most two books" live?

  1. In BookRepository.save()
  2. In the Member entity, reading the loan map directly
  3. In LendingService.borrow()
  4. In main()
It spans members and loans and needs a query, so it is a service rule. Repositories store; entities guard only their own state.

What does the service depend on?

  1. Repository interfaces
  2. InMemoryBookRepository directly
  3. The HashMap inside the repository
  4. The driver
Depending on interfaces is what makes "swap to a database" a one-line change.

Each repository uses ConcurrentHashMap. Two threads borrow for the same member at once. What can happen?

  1. Nothing; the map is thread-safe
  2. A deadlock
  3. A ConcurrentModificationException
  4. Both pass the limit check and the member ends up with three books
Check-then-act across several calls is not atomic. Lock or transact in the service.

Which best describes a repository compared with a DAO?

  1. A repository is always faster
  2. A repository is a collection of domain objects; a DAO wraps table access
  3. A DAO has no interface
  4. They are unrelated
Domain-shaped vs table-shaped; a repository may use DAOs inside.

Why should findAll() return a copy instead of the internal map's values view?

  1. Copies are faster
  2. Java requires it
  3. So callers cannot change storage behind the repository's back
  4. To save memory
The repository must stay the single owner of state, like a database owning its rows.
