Interview Q&A

Your machine-coding solution uses HashMaps. The reviewer asks: how would you move it to a database?

Because services depend on repository interfaces, I add a new implementation (JDBC, JPA or a NoSQL client) and change the wiring in main. Entities and services do not change, and the in-memory version stays for tests. Then I would mention what else changes: the service-level lock becomes a transaction, concurrent updates to the same row need optimistic versioning or row locks, and queries like "open loans of a member" need an index.

How to answer

One-line swap first, then the two honest caveats (transactions, indexes). Point at the interface in your code.

Likely follow-ups
  • Where exactly does the transaction start and end?
  • How would you add a cache in front of the repository? (A decorator implementing the same interface.)
Repository vs DAO: what is the difference?

A DAO wraps database access, typically one per table, with row-shaped methods. A repository presents a collection of domain objects, usually one per aggregate root, with domain-shaped queries, and may use DAOs or an ORM inside. A repository returns complete entities with their invariants; a DAO may return partial rows.

How to answer

Level of abstraction (database vs domain), granularity (table vs aggregate), vocabulary (columns vs business terms).

Likely follow-ups
  • What is an aggregate root? Give one from your design.
Where do business rules go: entity, service or repository?

A rule about one entity's own state goes on the entity (a book cannot be lent twice; an account balance cannot go negative). A rule that needs other entities or a query goes in the service (a member can hold at most two books). Repositories hold no rules; they store and retrieve. This keeps each rule in one place and every use case passes through it.

How to answer

Give one example of each and say why the repository is not a home for rules.

Likely follow-ups
  • What is an anemic domain model and is it bad?
Your repository uses ConcurrentHashMap. Is the booking flow thread-safe now?

No. Each map operation is atomic, but "check the limit, mark the book, save the loan" is a compound check-then-act sequence. Two threads can both see one open loan and both save a second. The service must make the sequence atomic: a lock (global, or striped per member or per book), or an atomic map operation like compute on the right key, or in a database a transaction with row locks or a version check.

How to answer

Name the race, show the interleaving in one sentence, then give a fix and its granularity trade-off.

Likely follow-ups
  • Per-book lock vs per-member lock: which rule needs which? (The limit needs the member; double-lending needs the book; take both in a fixed order to avoid deadlock.)
  • See booking concurrency.
Should findById return null, throw, or return Optional?

Return Optional (or a nullable type in Python and Kotlin): "not found" is a normal outcome for a lookup, and the repository does not know whether it is an error. The service decides: orElseThrow(NotFoundException::new) when the use case requires it, or a default when it does not. Returning bare null pushes the check onto every caller and fails late.

How to answer

Separate "the lookup found nothing" (repository) from "this is an error" (service).

Likely follow-ups
  • When would a Null Object be better than Optional?
How does this layering help testing?

Services take repositories through the constructor, so a test passes in-memory or fake repositories, seeds exact data, calls the use case and asserts on results and on what was saved. No database, no network, milliseconds per test. Entities are tested on their own. Only a few integration tests need the real store, and they test the repository implementation against the same interface contract.

How to answer

Constructor injection, in-memory fake, contract tests for each implementation.

Likely follow-ups
  • Fake vs mock: which do you prefer for repositories and why?
Your repository interface keeps growing: findByTitle, findByAuthor, findByTitleAndAuthor... How do you stop it?

Accept a query object: findAll(Specification<Book> spec), where specifications compose with and / or / not. The in-memory implementation filters with spec.isSatisfiedBy; a database implementation translates the spec into a WHERE clause (Spring Data JPA's Specification does this). Keep a few named methods for the hot paths that need specific indexes.

How to answer

Name the smell (combinatorial finder methods), then the Specification fix and its push-down caveat.

Likely follow-ups
  • How do you avoid loading every row into memory to filter it?
