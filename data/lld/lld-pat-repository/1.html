The problem: one god class that does everything

Under time pressure the first draft of a library or booking system often looks like this:

public class LibrarySystem {
    // storage, rules and printing all mixed together
    static Map<String, String[]> books = new HashMap<>();      // id -> {title, "LENT"|"FREE"}
    static Map<String, List<String>> loansByMember = new HashMap<>();

    public static void borrow(String memberId, String bookId) {
        String[] b = books.get(bookId);
        if (b == null) { System.out.println("no such book"); return; }
        List<String> mine = loansByMember.computeIfAbsent(memberId, k -> new ArrayList<>());
        if (mine.size() >= 2) { System.out.println("limit"); return; }
        if (b[1].equals("LENT")) { System.out.println("lent"); return; }
        b[1] = "LENT";
        mine.add(bookId);
        System.out.println("ok");
    }
    // giveBack(), search(), report() ... all poking the same static maps
}

It runs. Reviewers still mark it down, and in the follow-up it falls apart:

  • Storage is everywhere. Every method touches the raw maps. "How would you move this to a database?" means rewriting every method.
  • No types. String[] with a magic index and a "LENT" string instead of a Book entity and an enum.
  • Rules are not reusable. The two-book limit lives inside borrow(). A new "renew" use case copies it.
  • Errors are prints. The caller cannot tell success from failure, and tests cannot assert on it.
  • Static global state. Two tests in one JVM see each other's data; concurrency has nowhere obvious to put a lock.

Machine-coding rubrics (Flipkart, PhonePe, Meesho, Cleartrip review calls in our company notes) score exactly these: modularity, separation of concerns, extensibility, and a ready answer to "how do you add a DB".
