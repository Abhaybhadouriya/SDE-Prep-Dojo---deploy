When to use it, when not to

Use it when
  • The domain is really a part-whole tree: folders and files, menus and items, org charts, bundles, UI widgets, expressions, permission groups.
  • You want clients to call one method on a single item or on a whole group without branching.
  • Operations naturally recurse: total, render, search, validate, delete-cascade.
  • New node kinds should be addable without touching existing traversal code (Open/Closed).
Avoid it, or watch out, when
  • Leaves and containers share almost no operations. Forcing a common interface gives you a fat Component full of methods that throw.
  • The structure is not a tree: nodes shared by many parents (a graph) need reference counting, cycle checks and careful "visited" sets.
  • Very deep trees: naive recursion can overflow the stack. Kernel code walks iteratively for exactly this reason (the kernel stack is small).
  • Hot repeated queries on a huge tree: recomputing size() each time is O(n). Cache aggregates in each composite and invalidate up the parent chain on change.
  • You need type-specific rules ("only these leaf types may go in this container"). The uniform interface makes such restrictions harder; you end up with runtime checks.

Pitfalls to name: cycles (a folder added to its own descendant), dangling parent pointers after a move, child order bugs (use an ordered map or list when order matters), and a Component interface that grows a method for every feature.
