Interview Q&A

Design an in-memory file system. Which pattern and which classes?

Composite. An abstract FileSystemNode with name, parent, created time and abstract size(). File (leaf) holds content or byte count. Directory (composite) holds a map from name to child node, so lookup by name is O(1) and duplicates are refused. A FileSystem class owns the root and parses paths: split on /, walk from the root through Directory.child(name), and create missing directories for mkdir -p.

How to answer

Draw the three classes and the "children : Node" arrow first. Then list operations (ls, mkdir, addFile, readFile, size, delete) and show which class each lives on.

Likely follow-ups
  • How do you support symlinks? (A third node type that resolves to another path; guard against loops with a hop limit, like ELOOP.)
  • How would you make it thread-safe? (Lock per directory, or one read-write lock; lock parent before child to avoid deadlock.)
Should add() and remove() be on the Component or only on the Composite?

It is the safety vs transparency trade-off. On the Component (transparency) every node looks the same, but leaves must throw or silently ignore, which strains Liskov substitution and moves errors to run time. On the Composite only (safety) a wrong call is a compile error, but code that builds the tree must hold a Composite. I prefer safety, because uniformity matters for the operations (size, render), not for building.

How to answer

Name both variants, give one consequence of each, then pick one and say why.

Likely follow-ups
  • How does the client add to a node it holds as a Component? (Ask the node for its composite: a asDirectory() that returns null or an Optional for leaves, instead of instanceof everywhere.)
How do you prevent cycles, for example moving a folder into its own subfolder?

Before adding child C under parent P, walk up from P through parent pointers to the root. If you meet C, refuse. That is O(depth). Linux does the same for rename(2): moving a directory into its own subtree returns EINVAL. Keeping a single parent pointer per node (a tree, not a graph) also means a move must detach the node from its old parent first.

How to answer

State the invariant ("each node has exactly one parent, no node is its own ancestor"), then the check.

Likely follow-ups
  • What changes if a node can have several parents (hard links to directories)? (You get a graph; that is why Unix forbids hard links to directories.)
size() on the root of a tree with millions of files is slow. What do you do?

Cache the aggregate. Each directory stores its total size. When a file changes by delta bytes, walk up the parent chain and add delta to each ancestor's cached total. Reads become O(1); writes become O(depth). This is how quota and disk-usage accounting works in real file systems, and the same idea applies to cart totals or task progress roll-ups.

How to answer

Give the naive cost (O(n) per query), the cached cost (O(1) read, O(depth) update), and mention concurrency (atomic counters or a lock per directory).

Likely follow-ups
  • How do you keep the cache correct during a move? (Subtract from the old ancestors, add to the new ones.)
Design a calculator that evaluates nested expressions like 2 + (3 * 4).

An Expression interface with evaluate(). Number is the leaf. BinaryOp (or one class per operator: Add, Multiply) is the composite, holding left and right Expressions. A parser builds the tree; evaluation is a post-order walk. New operators are new classes, and the client calls evaluate() on the root only.

How to answer

Draw the tree for the sample expression, then the classes. Mention division by zero as a domain error and that operator lookup can be a Strategy map.

Likely follow-ups
  • How do you add pretty-printing and simplification without touching every class? (Visitor.)
Composite vs Decorator: both hold a Component and are a Component. What is the difference?

Intent and fan-out. A Composite holds many children and combines their results to represent a group (a folder's size is the sum of its files). A Decorator holds exactly one wrapped component and adds behaviour around the same call (a milk decorator adds 20 to the coffee's price). Composite builds trees; Decorator builds chains.

How to answer

"Many and combine" vs "one and enhance", plus one example each.

Likely follow-ups
  • Can you use both together? (Yes: decorate a whole bundle, for example a discount wrapper around a combo.)
Where is the Composite pattern in the Linux kernel?

The dentry cache: each struct dentry has a parent and a list of children, whether it is a file or a directory, and generic code like d_walk() visits subtrees uniformly. The device tree (device_node), kobjects behind sysfs, and the cgroup hierarchy (limits apply to the whole subtree) are composites too. The kernel uses the "safe" variant: only directory inodes provide lookup, mkdir and unlink in their inode_operations.

How to answer

Name one structure, its parent/child fields, and one operation that walks it.

Likely follow-ups
  • Why does kernel code avoid deep recursion over these trees? (Small fixed-size kernel stacks.)
