How to refactor safely

Refactoring is only safe if you can tell, after each step, that behaviour did not change. That needs tests. If the code has none, write characterization tests first: tests that record what the code does today (even if it is odd), so any change in output is caught.

  1. Start with passing tests. No tests? Write characterization tests that pin current outputs.
  2. Make one small, named step: extract one method, move one field, rename one thing.
  3. Run the tests immediately - in seconds, not at the end of the day.
  4. Green? Commit (or at least save a checkpoint). Each commit is a safe place to return to.
  5. Repeat. Big restructurings are just many small steps in a row.
  6. Red? Do not debug a big diff. Undo the last small step and take a smaller one.

All ten examples on this page come from one program, lld-code/lld-prin-smells/SmellsDemo.java. Its main() runs every "before" and "after" on the same inputs and fails if any result differs - a tiny characterization suite:

Two lines in that output are not "same", on purpose. The money split and the order state machine show that refactoring often reveals a bug. When that happens, finish the refactoring first (same behaviour, bug included), then fix the bug in a separate step with a test that fails before the fix. Two hats, never both at once.
