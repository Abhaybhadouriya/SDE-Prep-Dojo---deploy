Judgement: when to refactor, and when not to

  • Rule of three. First time, just write it. Second time, notice the duplication. Third time, extract. Extracting after one example often produces the wrong abstraction, and a wrong abstraction is harder to undo than duplication.
  • Refactor right before a change. "Make the change easy, then make the easy change." When a new requirement lands in messy code, first refactor until the change is a one-liner, then add it.
  • Do not refactor code you are not touching without a reason; it costs review time and risks regressions for no gain.
  • Speculative generality is a smell too. An interface with one implementation and no test fake, a factory for one class, a Strategy with one strategy - remove them until a second case is real.
  • Refactoring is not rewriting. If you cannot keep the program working between steps, you are rewriting, and that needs a different plan (and usually a different conversation with your manager).

In a 90-minute machine-coding round

  1. Minutes 0-60: write it cleanly from the start - small methods, value objects for money and IDs, an interface where the problem says "types may be added". Cheaper than refactoring later.
  2. Minutes 60-75: get all P0 features running end to end with a driver. Working code beats neat but incomplete code in every evaluation report.
  3. Minutes 75-85: do the cheap, safe refactorings: rename unclear names, extract the longest method, replace magic numbers, delete dead code. Re-run the driver after each.
  4. Review call: name the remaining smells yourself and the refactoring you would apply ("the fee switch would become a PricingStrategy"). Interviewers reward self-awareness.

A strong closing line in a review: "If I had another hour, I would replace the status int with State classes - right now cancel() has the refund rule mixed with every other state." It shows you know the smell, the cure and the risk.
