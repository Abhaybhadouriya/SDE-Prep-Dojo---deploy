Two definitions

  • Code smell (term from Kent Beck, made popular by Martin Fowler's book Refactoring): a surface sign that usually points to a deeper design problem. A smell is quick to see - a 200-line method, the same switch in four places - but it is not automatically a bug. It is a reason to look closer.
  • Refactoring: changing the internal structure of code without changing what it does from the outside, in small steps that each keep the program working. "Without changing behaviour" is the key part. Adding a feature while restructuring is not refactoring - it is two jobs at once.

Each smell has well-known cures, and each cure is a named refactoring with a recipe: Extract Method, Move Method, Replace Conditional with Polymorphism and so on. Fowler's catalogue lists dozens; refactoring.guru groups 66 of them in six families. You need perhaps fifteen in daily work, and ten cover most interview code.

From your world

The kernel has a habit that is pure refactoring discipline: a patch series where the early patches say "no functional change" and only move or rename code, and a later patch adds the feature. Reviewers can check the cleanup patches quickly because behaviour must be identical, and git bisect can blame the one patch that changed behaviour. That is Fowler's "two hats" rule, enforced by maintainers.
