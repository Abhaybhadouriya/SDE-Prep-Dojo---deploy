Ten key refactorings (6-10)

6. Replace Type Code with State - cures Switch Statements on a changing status

Smell: int status with constants NEW, PAID, SHIPPED, CANCELLED, and every method starts with if (status == ...). Unlike case 5, the type changes at runtime, so the object must be able to swap its behaviour. Recipe: one class per state; each method returns the next state; the context object just delegates.

static final int NEW = 0, PAID = 1, SHIPPED = 2, CANCELLED = 3;
int status = NEW;
String pay()    { if (status == NEW)  { status = PAID;    return "paid"; }    return "cannot pay"; }
String ship()   { if (status == PAID) { status = SHIPPED; return "shipped"; } return "cannot ship"; }
String cancel() {
    if (status == NEW || status == PAID) {
        status = CANCELLED;
        return status == PAID ? "refund" : "cancelled";   // BUG: status was overwritten one line up
    }
    return "cannot cancel";
}
interface OrderState {
    default OrderState pay(List<String> log)    { log.add("cannot pay");    return this; }
    default OrderState ship(List<String> log)   { log.add("cannot ship");   return this; }
    default OrderState cancel(List<String> log) { log.add("cannot cancel"); return this; }
}
final class NewOrder implements OrderState {
    public OrderState pay(List<String> log)    { log.add("paid");      return new PaidOrder(); }
    public OrderState cancel(List<String> log) { log.add("cancelled"); return new CancelledOrder(); }
}
final class PaidOrder implements OrderState {
    public OrderState ship(List<String> log)   { log.add("shipped");   return new ShippedOrder(); }
    public OrderState cancel(List<String> log) { log.add("refund");    return new CancelledOrder(); }
}
final class ShippedOrder implements OrderState {}
final class CancelledOrder implements OrderState {}

final class Order {
    private OrderState state = new NewOrder();
    final List<String> log = new ArrayList<>();
    Order pay()    { state = state.pay(log);    return this; }
    Order ship()   { state = state.ship(log);   return this; }
    Order cancel() { state = state.cancel(log); return this; }
}

Notice the bug in the "before" code: it sets the status before checking it, so a paid order never gets a refund. With type codes, each method mixes all states and bugs like this hide easily. With one class per state, "what does cancel do when paid?" has exactly one place to look. As the two-hats rule says, the demo first proves the refactor (the output line shows both versions), and the fixed behaviour is then asserted as a separate check. Full pattern: State.

From your world

The TCP state machine in the kernel uses a type code (sk->sk_state) and big switches in functions like tcp_rcv_state_process(). That is a reasonable choice there: the states are fixed by an RFC, performance matters, and one team owns all of it. The smell becomes real when states are added often or owned by different people - the usual situation in application code.

7. Move Method - cures Feature Envy, Data Class

Smell: Invoice.total() reads two fields of Customer and none of its own to compute a loyalty discount. Recipe: move the method (or the envious part) into the class whose data it uses, and call it from the old place. This is GRASP's Information Expert applied after the fact.

final class Customer { int ordersThisYear; boolean premium; }   // a data class
final class Invoice {
    long total(long subtotal, Customer c) {
        int pct = c.premium ? 10 : (c.ordersThisYear >= 12 ? 5 : 0);   // envy
        return subtotal - subtotal * pct / 100;
    }
}
final class Customer {
    private final int ordersThisYear; private final boolean premium;
    Customer(int orders, boolean premium) { this.ordersThisYear = orders; this.premium = premium; }
    int loyaltyPercent() { return premium ? 10 : (ordersThisYear >= 12 ? 5 : 0); }   // rule next to data
}
final class Invoice {
    long total(long subtotal, Customer c) { return subtotal - subtotal * c.loyaltyPercent() / 100; }
}

The fields could now become private, and the loyalty rule is reusable by the checkout page, emails and reports.

8. Replace Nested Conditional with Guard Clauses - cures arrow-shaped code

Smell: if inside if inside if, with the normal case buried in the middle. Recipe: handle each special case first and return early; what is left at the bottom is the normal path.

static String refund(boolean delivered, int daysSince, boolean opened, boolean isElectronics) {
    String result;
    if (delivered) {
        if (daysSince <= 7) {
            if (!(opened && isElectronics)) { result = "FULL"; }
            else { result = "INSPECT"; }
        } else { result = "EXPIRED"; }
    } else { result = "CANCEL_INSTEAD"; }
    return result;
}
static final int RETURN_WINDOW_DAYS = 7;

static String refund(boolean delivered, int daysSince, boolean opened, boolean isElectronics) {
    if (!delivered)                      return "CANCEL_INSTEAD";
    if (daysSince > RETURN_WINDOW_DAYS)  return "EXPIRED";
    if (opened && isElectronics)         return "INSPECT";
    return "FULL";
}

The demo checks all 16 combinations of the inputs, which is cheap and gives full confidence for a pure function like this.

From your world

Kernel style already prefers guard clauses: check, return -EINVAL, continue. The goto err_free cleanup ladder is the C answer to "early return but still release what I acquired" - it is not a smell in C. In Java the same role is played by try-with-resources, and in C++ by RAII destructors.

9. Hide Delegate - cures Message Chains (Law of Demeter)

Smell: shipment.customer().address().city(). The courier code now depends on three classes and on the exact path between them; if address moves from Person to Order, every chain breaks. Recipe: add a method on the first object that walks the path for you.

// before: courier code
String zone = s.customer().address().city().equals("Pune") ? "LOCAL" : "NATIONAL";

// after: the path lives in one place
record Shipment(Person customer) {
    String deliveryCity() { return customer.address().city(); }
}
String zone = s.deliveryCity().equals("Pune") ? "LOCAL" : "NATIONAL";

Do not overdo it: if Shipment ends up with twenty forwarding methods, you have created the Middle Man smell, and the cure is the reverse refactoring. Fluent APIs and streams (list.stream().filter(...).map(...)) are not message chains - each call returns the same kind of thing, not a walk through other objects' internals.

10. Introduce Null Object - cures repeated null checks, Temporary Field

Smell: if (coupon != null) before every use of a coupon - in pricing, in the receipt, in analytics. One missed check is a NullPointerException in production. Recipe: create an object of the same interface that does "nothing" correctly, and return it instead of null.

static long price(long paise, String code) {
    Integer pct = code == null ? null : COUPONS.get(code);
    if (pct == null) return paise;          // ...and the same check in receipt(), analytics()...
    return paise - paise * pct / 100;
}
interface Coupon { long apply(long paise); String label(); }
record PercentCoupon(String code, int pct) implements Coupon {
    public long apply(long p) { return p - p * pct / 100; }
    public String label()     { return code + " (-" + pct + "%)"; }
}
static final Coupon NO_COUPON = new Coupon() {     // does nothing, safely
    public long apply(long p) { return p; }
    public String label()     { return "no coupon"; }
};
static Coupon findCoupon(String code) {
    Integer pct = code == null ? null : COUPONS.get(code);
    return pct == null ? NO_COUPON : new PercentCoupon(code, pct);   // the only null check
}
static long price(long paise, String code) { return findCoupon(code).apply(paise); }

Use a Null Object when "absent" has a sensible do-nothing behaviour. When absence is an error the caller must handle, return Optional or throw instead. More in Null Object.
