Interview follow-ups

Why order by a server sequence number and not by timestamp?

Device clocks are wrong, sometimes by minutes, and two messages can share a millisecond. A per-chat counter assigned by the server under one lock gives one total order that every member agrees on, has no ties, and has no gaps, so a device can tell "I am missing 41" and ask for it. Timestamps are still stored for display.

How to answer

Name the two failure modes of timestamps (skew, ties), then the two extra powers of a dense counter (gap detection, cursor paging).

Likely follow-ups
  • What if the chat is sharded across servers? (One owner per chat assigns the seq; or a per-chat counter in the database.)
In a group of 50, when does the sender see blue ticks?

When all 49 recipients have read it. Overall status is the minimum receipt over recipients. The per-member detail ("read by 31, delivered to 49") is available from the same map. If a member is removed before reading, their receipt is dropped so the message can still reach READ.

How to answer

State the rule, then the removal edge case. That second sentence is what shows you ran it.

Why is the server a Mediator and not just users holding references to each other?

Direct references give every user a list of everyone they talk to and duplicate the membership rules in each. Nobody owns ordering. Offline handling has no home. With a mediator, users and devices know one object; membership, sequence numbers, receipts and fan-out are in one place and testable without a network. The cost is that the mediator can grow into a god class, so keep model rules in the model (Chat.checkCanChangeMembers, Receipt) and coordination in the server.

Likely follow-ups
  • Mediator versus Observer? (Mediator coordinates peers who would otherwise talk to each other; Observer is one-to-many broadcast. Here the server is the mediator and uses observers to reach devices.)
A message is sent at the same moment the recipient reconnects. Can it be shown twice, or lost?

Neither, once DELIVERED comes from the device. Shown twice: both paths call deliver, and the per-connection push flag (a CAS on the message) lets only one of them push; even if a copy does slip through, the device drops it by seq. Lost in the race: connect registers the device before scanning, so any message appended after the scan sees the device in online. Lost on the wire: the receipt moves SENT to DELIVERED only on the device's ack, so a push that never arrived stays SENT and the next connect re-sends it. An earlier version of this design moved the receipt to DELIVERED before the push; that is at-most-once, and a disconnect between the push and the write loses the message for good. That is the follow-up strong interviewers ask.

How to answer

Walk both interleavings. Then name the invariants: "a CAS decides who pushes; only the device's ack makes it DELIVERED; unacked messages are re-sent on connect".

Why not push to devices while holding the chat lock? It would keep order.

Because one slow or dead device would block every sender in that chat, and a callback that sends a reply (a bot) would either re-enter send() mid-operation (Java monitors are re-entrant, so the same thread does not block) or, if it replies into another chat or hands off to another thread, set up an ABBA deadlock. Order is restored on the device by sequence number. If the interviewer insists on in-order pushes from the server, give each user an outbox queue and one drainer per user: order per user, no I/O under the chat lock.

How would you store receipts for a 10,000-member group?

Not as a row per message per member, which is 10,000 rows per message. Store two numbers per member per chat, deliveredUpTo and readUpTo, and derive any message's tick by comparing seq. "Read by" counts for the sender can be computed lazily or kept approximately. Big groups often show only "delivered" and drop per-member read detail entirely; that is a product trade-off to state.

Should a new member see old group messages?

It is a product choice, so ask. WhatsApp-style groups say no (privacy; with end-to-end encryption the new member could not decrypt them anyway). Slack channels say yes (shared knowledge). Our model stores the join seq per member, and every read path filters by it, so either policy is one line. Without the join seq you cannot implement the "no" policy at all.

Support several devices per user. What changes, and what does "delivered" mean now?

The online map holds a set of clients per user. DELIVERED means at least one device has it; each device tracks its own highest seq per chat and asks for anything after it when it connects, so a phone that was off catches up even though the laptop already acknowledged. READ on any device is READ for the user, and the other devices are told so they clear their badges. The ack and the re-push become per device, keyed by (device, chat, seq).

Your process restarts. What is lost and how would you fix it?

Everything: it is in memory. With a repository per chat, messages are stored with their seq before the send returns (that is the commit point); nextSeq is recovered as max stored seq plus one; receipts as the two counters per member. Devices reconnect and ask "everything after seq N". Pushes that were in flight are simply redone, which is safe because devices de-duplicate by seq.

Why is Receipt an enum with methods and not three State classes?

Three states, two events, no data per state. Enum constants with their own onDelivered and onRead are the State pattern without the ceremony: no if-ladder, illegal moves impossible, and Java gives you EnumMap and switch for free. Move to classes when a state needs its own data or timers (for example disappearing messages with an expiry).
