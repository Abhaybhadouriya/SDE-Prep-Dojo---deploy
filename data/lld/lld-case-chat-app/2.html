Clarify the requirements

Five minutes. A chat app sounds obvious, so candidates skip this and then argue later about what "read" means in a group.

Functional (P0: must work in the demo)

  1. Users Register users. A user can have zero or one connected device in P0 (multi-device is an extension).
  2. 1:1 chats direct(a, b) returns the same chat whichever side calls it, every time.
  3. Group chats A creator becomes admin. Only admins add or remove members; anyone may leave. When the last admin leaves, the oldest member becomes admin. Cap of 256 members.
  4. Send Only members may send. Empty text is rejected. Each message gets the next sequence number of its chat.
  5. Deliver Online recipients get the message pushed at once. Offline recipients get every pending message, in order, when they connect.
  6. Receipts Per recipient: SENT, then DELIVERED, then READ. The sender sees the lowest of them (a group message is "read" only when everyone has read it) and is told each time one changes.
  7. Read, unread, history markRead(user, chat, uptoSeq) marks everything up to that number. Unread count per chat. History pages backwards by sequence number. A member who joined late sees nothing from before they joined.

Non-functional

  • Ordering: within one chat, every member agrees on one order (the sequence number). No gaps, no duplicates, even with many senders at once.
  • No lost or doubled messages per device: a message that races with a reconnect is not shown twice, and a push lost on the wire is re-sent (at-least-once push + dedupe by seq on the device = effectively once).
  • Thread safe without one global lock: two busy chats must not block each other.
  • Extensible: new message types (image, reply, reaction), new delivery channels (push notification when offline) without editing send.

Out of scope (say it out loud)

Network transport (WebSocket / long polling), login, end-to-end encryption, media upload, persistence, search, typing indicators and presence ("last seen"). Name where each would plug in: transport is a ChatClient implementation, persistence is a repository behind the chat's message list, presence is another observer event.

Questions to ask

  • Is "read" per recipient, and what does the sender see in a group? (Per recipient; the sender sees the minimum, with per-member detail on request.)
  • Does a new group member see old messages? (No in our version. WhatsApp-style privacy. Say that Slack channels do the opposite; it is a product decision.)
  • Do receipts ever go backwards? Can a message be read without being delivered? (Never backwards; reading implies delivery, so SENT can jump straight to READ.)
  • Ordering by timestamp or by server sequence? (Server sequence per chat. Device clocks lie.)
  • Several devices per user? (One in P0, many as an extension.)
  • Edit, delete, reactions, replies? (P1. Show that the model takes them.)
