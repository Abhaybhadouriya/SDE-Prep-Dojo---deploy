Core flows

Send to a group with one member offline, then that member connects

  1. Ben's device calls send. The server knows nothing about Asha or Chen yet beyond the chat's member list.
  2. Under the chat's lock only: check membership, take the next sequence number, create the message with one SENT receipt per other member, append, unlock. This is the only critical section.
  3. Outside the lock, fan out. Asha is online, so the server pushes m2 to her device (a per-connection flag stops a second push on the same connection). Her device stores it and calls ack(asha, chat, seq); that ack, not the push, moves her receipt SENT to DELIVERED and tells Ben. Overall is still SENT, because Chen has not got it.
  4. Chen is offline. Nothing is queued separately: "pending for Chen" simply means "Chen's receipt is still SENT", that is, not acknowledged.
  5. Chen connects. The server walks Chen's chats under each chat's lock and collects messages whose receipt for Chen is SENT, in sequence order.
  6. After unlocking, each is pushed the same way as step 3 and Chen's device acks it. Ben now sees DELIVERED overall, two grey ticks. A push that was lost on the wire is simply pushed again on the next connect, because its receipt is still SENT. READ follows the same path when members call markRead.

Mark read up to a sequence number

Devices do not send one "read" per message; they say "I have seen everything up to 42". Under the chat lock, the server walks the messages this user may see, skips their own, and calls apply(user, read) on each one up to 42. Only messages whose state really changed are collected. After unlocking, the sender of each is told. Calling it twice changes nothing and sends nothing, which matters because mobile clients retry.

Join late, leave, remove

A member's entry stores the sequence number they joined at, and every read path (history, unread, pending on connect) filters by it. Removing a member also drops their not-yet-read receipts from existing messages; otherwise a group message could never reach READ overall, because the removed member will never read it. The last admin leaving hands admin rights to the oldest remaining member, so a group is never stuck without one.
