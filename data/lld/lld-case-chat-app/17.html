Why is the per-chat sequence number assigned under the chat's lock?

  1. So two concurrent senders never get the same number or leave a gap
  2. So the message reaches devices faster
  3. Because ArrayList is slow
  4. To make receipts thread safe
Read-increment-append is a compound action. Without the lock, two senders can read the same value.

The send fan-out and a reconnect's pending scan both try to deliver message 9 to Ben. What stops a second push on that connection?

  1. The chat lock is held during the push
  2. The device ignores duplicates by text
  3. A global lock in connect
  4. A compare-and-set on the message that records which connection was already pushed
claimPush is atomic on the message and returns true once per connection, so it elects one pusher. It does not mark the message DELIVERED: only the device's ack does, so a push that is lost is re-sent on the next connect, and the device dedupes by seq.

Which pattern describes "users never reference each other; one object routes all messages"?

  1. Observer
  2. Mediator
  3. Facade
  4. Proxy
Mediator replaces many-to-many links between peers with one coordinator. The server also uses Observer to reach devices.

The member entry stores the join seq, and every read path filters by it (a WhatsApp-style policy).

In production, what is the compact way to store read receipts for a big group?
