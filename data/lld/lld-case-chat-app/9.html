Concurrency and thread safety

Background: races and atomicity, locks, concurrent collections.

  1. Sequence numbers "Read nextSeq, increment, append" must be one atomic step per chat, or two senders get the same number. That is the only thing done under Chat.lock in send. Different chats have different locks, so they never contend.
  2. Fan-out after unlock Pushing to devices is I/O and can be slow, or can call back into the server (a bot that replies). Doing it under the chat lock would serialise the whole chat behind the slowest device. Java monitors are re-entrant, so a same-thread reply would not deadlock: it would re-enter send() in the middle of the operation and append a message inside what we called one atomic step. A reply into another chat while holding this chat's lock, or a hand-off to a thread that waits for this lock, can deadlock (ABBA). Calling out after unlock avoids both. So send returns the new message from the critical section and pushes afterwards.
  3. At-least-once push, DELIVERED on ack send's fan-out and connect's pending scan can race for the same message and user. Both call deliver, which pushes only if Message.claimPush (synchronized on the message) says this connection has not had it yet: a compare-and-set that only avoids a duplicate push. The receipt moves SENT to DELIVERED only when the device calls ack(user, chat, seq). If the device drops off between the push and the ack, or the socket write is lost, the receipt stays SENT and the next connect pushes it again; the device drops a copy it already stored (dedupe by chat + seq) and acks again. At-least-once push plus dedupe by seq is effectively once. Demo "lost push and lost ack" shows both failures.
  4. Order at the device Because fan-out happens after unlock, two concurrent senders can push seq 8 before seq 7. The fix in real systems is the same as TCP: the client buffers by sequence number and renders in order (it also uses the number to spot duplicates after a reconnect). If the interviewer wants server-side ordering, give each user an outbox queue drained by one thread.
  5. Registries Users, chats and online devices are ConcurrentHashMaps. direct() uses computeIfAbsent, so two users opening a chat with each other at the same moment still get one chat.
  6. Reads history, unread and markRead take the same chat lock briefly. If reads dominate, switch the chat to a read-write lock or keep messages in a copy-on-write list per page.

Say the lock order out loud: "chat lock, then message monitor, never the other way; and no callbacks while holding either". Interviewers ask "can this deadlock?"; that one sentence is the answer.
