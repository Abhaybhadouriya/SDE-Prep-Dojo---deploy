Key relationships and patterns (and why each)

Pattern / choiceWhereWhy it earns its placeWhat you say in the room
MediatorChatServerN users talking to each other directly is N x N links, and every user would need to know who is online. With a mediator, users know one object. Membership checks, sequence numbers and fan-out live in one place. This is the textbook chat-room example of the pattern."Users only know the server. Membership, sequence numbers and fan-out live in one place."
ObserverChatClient registered by connectThe server should not know whether the device is a console, a WebSocket or a test. It calls onMessage and onReceipt; adding push notifications or a second device is a new observer, not a change to send."A device is a callback. Push notifications or a second device are one more observer."
State (enum form)Receipt.onDelivered(), Receipt.onRead()Each state decides what an event does to it, so there is no if-ladder over statuses in the server. Three states with tiny behaviour fit in an enum with per-constant methods. Use full state classes if states grow real behaviour (for example "expired" messages with disappearing timers)."A receipt only moves forward, and only an ack moves SENT to DELIVERED."
Inheritance with a template hookChat to DirectChat, GroupChatSequence numbers, message storage and visibility are shared. Only the membership rule differs, and that is one abstract method, checkCanChangeMembers. A type field with if (type == GROUP) everywhere is the alternative you are avoiding."Direct and group chats share storage and sequencing; only the membership rule is a subclass hook."
Lock per chat (lock striping: many locks, one per partition, like per-bucket locks in a hash table; here the partition is one chat, see locks)Chat.lockSequence numbers must be unique within a chat, not globally. One lock per chat means two busy groups never wait for each other."One lock per chat: seq++ and append are one step, and two busy groups never wait for each other."
FacadeChatServer againOne entry point for the driver, a REST controller or a socket handler."The driver, a REST controller and a socket handler all call the same methods."

Patterns we deliberately skipped: a Singleton server (see the warning below), a Command object per message (nothing needs undo or replay beyond the history itself), and a full State class per receipt (three states, each with one or two moves).

Two traps. Do not give User a send(otherUser, text) method that writes into the other user's inbox: now users know each other, membership rules are scattered, and ordering has no owner. And do not make the server a Singleton "because there is one server": tests then share state, and the concurrency demo below needs two independent servers.

From your world

The server as Mediator is the D-Bus daemon: processes do not open channels to each other, they talk to one broker that knows the subscribers and routes each message. (Netlink is different: a kernel-to-user socket family whose multicast groups deliver kernel events to many listeners, which is the Observer half.) connect(user, client) is register_netdevice_notifier(): the core keeps a list of callbacks and calls them on events, without knowing what they do. Receipt with per-constant methods is like the switch (sk->sk_state) in tcp_rcv_state_process(), but with each case moved into the enum constant, so the table of moves lives next to the state it belongs to.
