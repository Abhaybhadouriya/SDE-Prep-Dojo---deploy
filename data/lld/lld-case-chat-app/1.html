How it is asked

Before you start: this case assumes OOP from C structs (objects as structs with an ops table) and interfaces vs abstract classes. The patterns it uses are explained on their own pages: Mediator, Observer, State, Facade. The locking uses locks and concurrent maps.

"Design a chat app" is asked in two very different rounds, and the first job is to find out which one you are in. In a system design round they want WebSockets, fan-out, storage partitioning and presence at millions of users (our Chat App (WhatsApp) HLD). In an LLD or machine-coding round they want classes, a clean message model, receipts, groups and running code in memory. The table shows both; read the round type before you start drawing boxes. Round styles are covered in How LLD rounds work.

As a pure LLD prompt, the chat app is mostly a question-bank and course staple: it is item 9 in a widely read frequently asked LLD questions list (users, messages, chat rooms, send / receive / store), it is in a 2025 LLD question bank as "Chat System (WhatsApp)", and it is a full chapter in free courses such as AlgoMaster's chat application LLD. We found few first-hand 2024-2026 reports of it as a machine-coding problem, so treat it as a likely LLD prompt rather than a hot one. What makes it worth 40 minutes: it is the cleanest way to show Mediator, Observer and State together, and the same model (sequence per stream, per-subscriber state, fan-out after unlock) reappears in Pub-Sub and Notification service.

First sentence in the room: "Should I treat this as an object model with running code in memory, or as a distributed system?" The Uber SDE-1 report above is the cautionary tale. If it is LLD, say out loud that WebSockets, storage and scale are out of scope and name where they would plug in.
