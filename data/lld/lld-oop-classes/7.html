Lifetime, reachability and the garbage collector

In Java an object is alive while it is reachable: some chain of references leads to it from a GC root (a local variable in a live stack frame, a static field, an active thread). When the last chain breaks, the object becomes garbage and the collector may reclaim it at some later time. You never call free, and you cannot know exactly when memory is reclaimed.

Consequences you should be able to say in an interview:

  • Memory leaks still exist in Java: they are objects that stay reachable by mistake. The classic LLD case is a listener list or a static cache that only grows. Observer designs need unsubscribe; caches need eviction (LRU Cache).
  • Memory is not the only resource. Files, sockets and locks need deterministic release: try (var in = Files.newInputStream(p)) { ... } in Java, destructors (RAII) in C++, with in Python.
  • C++ gives you precise lifetime instead: a stack object dies at its closing brace, a unique_ptr's object dies with its owner, a shared_ptr's object dies with the last copy. Mistakes give dangling pointers rather than leaks.
  • Python frees most objects as soon as their reference count drops to zero, and a cycle collector handles the rest.
