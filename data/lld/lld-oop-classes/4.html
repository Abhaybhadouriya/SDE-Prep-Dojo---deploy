Identity vs equality

Two different questions:

  • Identity: are these the same object? In Java a == b on references, in Python a is b, in C/C++ &a == &b (comparing addresses).
  • Equality: do these objects mean the same thing? In Java a.equals(b), in Python a == b (calls __eq__), in C++ a == b if the class defines operator==.

What "means the same thing" is a design decision. Two Ticket objects with the same ticket id are the same ticket even if one has an outdated seat, so equals compares id only. Objects like this, defined by an identity that survives changes, are called entities. Objects defined entirely by their values, like a Money(100, "INR") or a Point(3, 4), are value objects: they compare all fields and should be immutable (Java record types do this for you).

The equals/hashCode contract

Hash-based collections (HashMap, HashSet) first use hashCode() to choose a bucket, then equals() to compare inside the bucket. So the rule from java.lang.Object's documentation is: if two objects are equal, they must have the same hash code. Override equals alone, and two equal tickets land in different buckets, so lookups fail.

final class Seat {
    private final String code;
    Seat(String code) { this.code = code; }
    @Override public boolean equals(Object o) {
        return o instanceof Seat s && s.code.equals(code);
    }
    // no hashCode(): each object keeps its identity hash
}

Set<Seat> set = new HashSet<>();
set.add(new Seat("A12"));
set.contains(new Seat("A12"));   // false: different hashCodes, so the set never calls equals (usually not even the same bucket)
final class FixedSeat {
    private final String code;
    FixedSeat(String code) { this.code = code; }
    @Override public boolean equals(Object o) {
        return o instanceof FixedSeat s && s.code.equals(code);
    }
    @Override public int hashCode() { return code.hashCode(); }  // same fields as equals
}

// or let the compiler write both: a value object as a record
record SeatCode(String code) {}

set.contains(new FixedSeat("A12"));  // true

Real output of lld-code/lld-oop-classes/BrokenHash.java:

$ java BrokenHash.java
equals: true
contains: false
fixed contains: true

Do not use mutable fields in equals/hashCode for keys. If a HashMap key's hash changes after insertion (because seat changed and hashCode uses it), the entry is stranded in the old bucket and can never be found again. Base equality on fields that never change (final id), or make the class immutable.

Classic trap: Integer x = 1000, y = 1000; x == y is false, but with 100 it is true. Java caches boxed values from -128 to 127, so small values share objects and == happens to work. Strings have the same trap with literals versus new String(...). Always compare objects with equals (or Objects.equals(a, b), which is null-safe).
