null: the reference to nothing

null means "this reference points at no object". Calling a method on it throws NullPointerException in Java, AttributeError on None in Python, and is undefined behaviour in C and C++ (usually a crash, like a NULL dereference oops in the kernel). In LLD code, decide for every field and return value whether "nothing" is allowed, and make it visible:

  • Constructor checks: this.id = Objects.requireNonNull(id, "id"); fails fast at creation instead of deep inside a later call.
  • Optional<T> return types for "may be absent": Optional<Spot> findFreeSpot(VehicleSize size) tells the caller to handle the empty case. Do not use Optional for fields or parameters; it is meant for return values.
  • Empty collections, not null: return List.of() when there are no bookings.
  • The Null Object pattern: a do-nothing implementation (for example a NoDiscount strategy) instead of null checks everywhere. See Null Object.

From your world

The kernel's ERR_PTR/IS_ERR convention exists because "NULL or a valid pointer" was not expressive enough: callers needed to know why nothing came back. Optional covers "nothing"; exceptions cover "why". And the habit of checking an ops slot for NULL before calling it is what Null Object removes, the same point LWN makes about preferring explicit default functions.
