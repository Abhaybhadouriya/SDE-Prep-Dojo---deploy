Where objects live: stack, heap, static

A running program keeps data in three main places. You know them from C; the rules for where an object ends up differ by language.

  • Stack: one per thread. Each function call pushes a frame with its parameters and local variables; returning pops it. Fast and automatic, but the data dies when the function returns.
  • Heap: shared by all threads. Memory you ask for explicitly (new, malloc); it lives until it is freed, by you (C, C++) or by a garbage collector (Java, Python).
  • Static (global) storage: lives for the whole program. Static fields and globals sit here, one copy each.

From your world

The kernel's 8 or 16 KB thread stacks make you allergic to big locals; you kmalloc anything sizeable. Java makes that choice for you: every object is "kmalloc'd" and only references and primitives sit on the stack. C++ gives you the C choice back: small value objects on the stack, long-lived or large ones on the heap behind a smart pointer. In LLD code the rule of thumb is the same as in the kernel: if it must outlive the function or be shared, it goes on the heap with a clear owner.
