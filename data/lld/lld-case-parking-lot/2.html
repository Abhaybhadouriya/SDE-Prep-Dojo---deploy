Clarify requirements

Never start drawing classes before you have spent 5 to 8 minutes on questions. The goal is a short, written list that you and the interviewer agree on. Here is the list we will build against.

Functional (P0 - must work in the demo)

  1. Layout The lot has one or more levels. Each level has spots of three sizes: small, medium and large.
  2. Vehicles Three types: motorcycle (fits any spot), car (medium or large), truck (large only).
  3. Park At the entry gate the system picks a free spot that fits and issues a ticket (ticket id, spot, entry time). If nothing fits, it says "full" for that vehicle type.
  4. Unpark At the exit gate the driver gives the ticket; the system computes the fee, frees the spot and returns a receipt.
  5. Fee Hourly rate per vehicle type; every started hour is billed; minimum one hour.
  6. Availability Show free spots per size (the display board at the entrance).

Functional (P1 - say you can add them, build if time allows)

  • Choosing the allocation rule at runtime: nearest-to-gate or best-fit (keep large spots for trucks).
  • Peak-hour pricing (the Amazon follow-up): hours that start between 17:00 and 21:00 cost 150%.
  • Several entry and exit gates working at the same time.

Non-functional

  • Correct under concurrency: a spot is never given to two vehicles; a ticket is never accepted twice.
  • Fast enough: picking a spot should not scan every spot of a 5,000-spot lot; we keep sorted free sets per size, so a pick is O(log n) per size we try.
  • Extensible: a new pricing rule or allocation rule is a new class, not an edit of the park/unpark code.
  • Testable: time is passed in (no hidden now()), so tests can say "entered 16:30, left 19:10".

Out of scope (say it out loud)

  • Real payment processing (we compute the amount; a PaymentProcessor would be a separate interface).
  • Persistence, cameras, number-plate recognition, boom barriers, UI.
  • Reservations in advance (a good follow-up; see extensibility).
