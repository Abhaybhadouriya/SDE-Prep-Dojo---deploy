Interview follow-ups

Why is pricing a Strategy and not a method on ParkingLot with a switch?

Because pricing is the rule that changes most: peak hours, weekends, passes, grace periods. With a switch, every new rule edits and re-tests unpark. With a FeeStrategy, a new rule is a new class, and unpark is closed for modification (Open/Closed). It also lets us test each rule alone with plain numbers.

How to answer

Name the rule that varies, show the one-line call pricing.fee(type, entry, exit), then name the follow-up it absorbs (peak pricing) without touching the service.

Likely follow-ups
  • How would you combine a weekend surcharge with peak hours? (Decorator around a base strategy.)
  • Who picks the strategy at runtime? (Config through the factory, or an admin call.)
Two gates try to park in the last spot at the same time. What happens in your design?

Both strategies call level.tryTake(MEDIUM), which is pollFirst() on a concurrent sorted set. That removal is atomic, so one thread gets the spot and the other gets null and moves on to the next size or level; if nothing is left, it throws LotFullException. There is no window between "check" and "take".

How to answer

Name the race (check-then-act), show the single atomic step, then mention the alternatives (one lock, per-level lock) and why you chose this one. Offer the 200-car test as proof.

Likely follow-ups
  • Pessimistic or optimistic locking if spots are in a database?
  • What if allocation must touch two levels at once? (Lock ordering by level number.)
Pessimistic or optimistic locking for spot allocation?

It depends on contention. A nearly full lot at rush hour has many gates chasing few rows; optimistic updates would fail and retry repeatedly, so pessimistic row locks with FOR UPDATE SKIP LOCKED are better (each gate grabs a different free row without waiting). A big, mostly empty lot rarely conflicts, so an optimistic version check is cheaper and never blocks.

How to answer

Give the rule (high contention: pessimistic; low contention: optimistic), the SQL shape of each, and the retry behaviour of optimistic locking.

Likely follow-ups
  • What does SKIP LOCKED do and why does it help here?
  • How do you avoid a deadlock if one transaction locks a spot and a ticket row?
Should ParkingLot be a Singleton?

I would not make it a global Singleton. There is one lot per process today, but a Singleton hides the dependency, makes tests share state, and breaks when the company runs two lots. I create one instance in main and pass it to the gates. If a single shared instance is a hard requirement, the initialisation-on-demand holder gives a lazy, thread-safe instance without locking code.

How to answer

Show you know the pattern (holder idiom or enum singleton), then argue for dependency injection with one concrete testing example.

Likely follow-ups
  • Why is double-checked locking broken without volatile?
  • How would you support a chain of lots under one company?
Why not create Car, Bike and Truck subclasses of Vehicle?

Subclasses are for different behaviour. Here the types differ only in data: which spot sizes fit and which rate applies. An enum VehicleType with a fits() list captures that and keeps the factory trivial. If a type later gets real behaviour (an EV that needs a charger), I can add a capability set or, if behaviour really differs, introduce subclasses then.

How to answer

Say "class per concept, not per instance or per value", give the data-only argument, and say what would make you change your mind.

Likely follow-ups
  • How would you add an electric car that needs a charging spot?
Add peak and non-peak pricing without breaking existing code.

Write PeakHourFee implements FeeStrategy: it walks each billed hour, and hours that start inside the peak window cost a percentage more. Register it in the factory under "peak" and call setPricing. ParkingLot and existing strategies are untouched. In our test, 16:30 to 19:10 for a car is 20 + 30 + 30 = Rs 80.

How to answer

Define the rule precisely first (per started hour, by hour start), then show the new class, then a test with numbers.

Likely follow-ups
  • What if the peak window differs on weekends? (A schedule object passed to the strategy.)
  • What if prices change while a car is inside? (Snapshot the tariff on the ticket.)
Companies can reserve slots for time ranges. How do you prevent overlapping bookings?

Each spot keeps its bookings in a sorted map from start time to end time. To book [s, e), look at the booking that starts just before s (floorEntry) and the one that starts at or after s (ceilingEntry); the new booking is valid if the first ends at or before s and the second starts at or after e. Do the check and the insert under the spot's lock so two companies cannot both pass the check. Allocation then skips spots reserved for the current time unless the vehicle belongs to that company.

How to answer

Reduce it to interval overlap, give the O(log n) check, then the locking granularity (per spot).

Likely follow-ups
  • Find any spot free for a whole range across the lot. (Iterate spots of that size, or keep an interval tree per size.)
Find where a car with a given plate is parked, or all white cars.

Keep secondary indexes in the service: plate to ticket (we already have it for duplicate checks) and colour to set of tickets. Update them on park and unpark in the same place as the ticket map. Lookups become O(1) instead of scanning every spot.

How to answer

Name the index, where it is updated, and the consistency rule (update together with the main map).

Likely follow-ups
  • How do you keep indexes consistent under concurrency? (Same atomic step or a lock covering both.)
How would you add a nearest-spot-to-this-gate rule for a lot with four gates?

Precompute, for each gate, the list of spots sorted by walking distance. A NearestToGateAllocation strategy takes the gate id and returns the first free spot in that order. Keep one free set per gate ordering, or keep a global free set and check membership while walking the gate's order. park gains a gateId parameter; nothing else changes.

How to answer

New strategy plus one parameter; mention the memory and time trade-off of per-gate orderings.

Likely follow-ups
  • How do you keep it O(log n)? (A priority queue per gate keyed by distance.)
Draw the sequence diagram for a car leaving the lot.

ExitGate calls unpark(ticketId, time) on ParkingLot; ParkingLot validates and removes the ticket, calls fee() on the current FeeStrategy, calls release(spot) on the spot's Level, notifies listeners with onLeft(receipt), and returns the receipt to the gate.

How to answer

Draw lifelines left to right in call order; make returns dashed; point out that only the Level touches free spots.
