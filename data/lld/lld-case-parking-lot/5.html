If the interviewer insists on a Singleton, this is the version to write: the holder idiom. It is a nested class whose static field the JVM initialises once, on first use, thread-safely, like a function-local static in C++11. There is no locking code to get wrong:

final class ParkingLotHolder {
    private ParkingLotHolder() {}
    private static final class Holder {          // loaded on first call to get()
        static final ParkingLot INSTANCE = Config.buildLotFromFile();
    }
    static ParkingLot get() { return Holder.INSTANCE; }
}

Then say the trade-off in one breath: a global instance hides a dependency, makes tests share state, and breaks the day the company runs two car parks. Passing the lot in (dependency injection) costs nothing and keeps those doors open.

From your world

FeeStrategy is a struct file_operations for money: the lot holds a pointer to "whatever implements fee()", exactly like a VFS inode holds i_fop and calls f_op->read() without knowing the filesystem. ParkingEventListener is a notifier chain: register_netdevice_notifier() lets any module hear NETDEV_UP without the core knowing the module exists; addListener() does the same for parking events.

Where this breaks: kernel notifier callbacks often run in atomic context and must not sleep; our listeners run on the gate's thread, so a slow listener slows the gate. In production you would hand events to a queue.
