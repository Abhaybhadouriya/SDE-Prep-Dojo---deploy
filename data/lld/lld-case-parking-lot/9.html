Concurrency and thread safety

Two entry gates, one free spot. Both gates run "find a free spot, then mark it taken". If the find and the mark are two separate steps, both gates can find the same spot before either marks it. This is the check-then-act race, and it is the number one concurrency topic in LLD rounds (it appeared in 9 of the interview reports we collected, from parking to seats to drivers).

  1. Gate A checks the spot: it is free.
  2. Before A writes anything, gate B checks the same spot: still free.
  3. Both write "taken". Two tickets point at one spot. No exception, no log line: the bug only shows up as an angry customer.
  4. The fix is to make "find and take" a single atomic operation. Our level stores free spots in a ConcurrentSkipListSet, and pollFirst() removes and returns the nearest free spot in one step.

Every shared thing and how it is protected

The demo proves it: 8 threads park 200 cars into 50 spots, and the result is exactly 50 tickets on 50 distinct spots; then every ticket is presented twice at the exits and exactly 50 exits succeed.

Three ways to lock, and which to say

ApproachHowGoodBad
One big locksynchronized park() and unpark()Obviously correct; fine for a demoAll gates wait for each other, even on different levels
Lock per level (or per size per level)ReentrantLock in each Level; strategy calls tryTake under itGates on different levels run in parallelNeed lock ordering if one operation touches two levels (it does not here)
Lock-free collections (ours)Concurrent sorted set + concurrent maps with atomic methodsNo lock code to get wrong; scales with gatesEach single step is atomic, but a multi-step invariant still needs care (we claim the plate first, and undo it on failure)

The database version (Microsoft's follow-up). If spots live in a table, the same choice appears as pessimistic versus optimistic locking:

-- Pessimistic: lock the row you are about to take; other gates skip locked rows instead of waiting
BEGIN;
SELECT id FROM spot
 WHERE level = 1 AND size = 'MEDIUM' AND vehicle IS NULL
 ORDER BY number LIMIT 1
 FOR UPDATE SKIP LOCKED;
UPDATE spot SET vehicle = 'KA01AB1234' WHERE id = :id;
COMMIT;

-- Optimistic: no lock; the write succeeds only if nobody changed the row since you read it
UPDATE spot SET vehicle = 'KA01AB1234', version = version + 1
 WHERE id = :id AND version = :seenVersion AND vehicle IS NULL;
-- 0 rows updated means you lost the race: pick another spot and retry

Say when to use which: pessimistic when contention is high (a nearly full lot at 9 a.m.: optimistic would retry a lot), optimistic when conflicts are rare (a big, mostly empty lot). SKIP LOCKED is the trick that keeps pessimistic locking from turning gates into a queue. More in Locks for LLD and Booking concurrency.

From your world

Taking a spot is the kernel's bitmap allocator: find_first_zero_bit() followed by test_and_set_bit(), retried if the atomic set loses, is how IDs and IRQ vectors are handed out without a global lock. pollFirst() on a concurrent set gives the same "find and claim in one atomic step" guarantee. The optimistic SQL update is a cmpxchg loop on a version number; the pessimistic one is a spin_lock on the row.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • CopyOnWriteArrayList = an RCU-style list: readers walk a snapshot with no lock, writers copy the array and publish it; good for read-mostly listener sets.
  • ConcurrentSkipListSet / Map = a sorted, lock-free set; pollFirst() removes the smallest element in one atomic step.
