Interview questions on running the round

The interviewer interrupts your class diagram at minute 12 and says "just start coding". What do you do?

Follow their lead. Spend 30 seconds to say which 3-4 classes you will start with and how they relate, then code the orchestrator and the method that carries the logic. Fill in the rest of the design as code; the diagram was a means, not the goal.

How to answer

The framework is an order, not a contract. Adapt, then steer back: after coding, say "let me quickly show where extensions would plug in".

Likely follow-ups
  • Which class did you code first, and why?
How do you decide which nouns become classes?

A noun becomes a class when it has its own state that changes or rules it must enforce (a room with bookings and a no-overlap rule). It becomes a field when it is just data of another object (a room's floor), an enum when it is a fixed set (booking status), and a value object when it is immutable data with behaviour (an interval with overlaps()). Anything you cannot tie to a requirement waits.

How to answer

Show the filter on your actual problem, including one noun you deliberately did not make a class.

Likely follow-ups
  • When would "Employee" become a class? (When a requirement needs its data: permissions, home floor, quotas.)
Why does the overlap check live in Room and not in BookingService?

Because Room owns the bookings list, it is the only class that can check and insert atomically. Putting the rule in the service would require the service to read the room's internals, and the lock would have to be held across two objects. Keeping data and the rule that protects it together gives encapsulation and a natural lock scope.

How to answer

Mention the two principles: Information Expert (the class with the data owns the rule) and encapsulation of the invariant.

Likely follow-ups
  • What if the rule needed data from two rooms (adjacent-room booking)? (A coordinator with ordered locks, or one lock for the group.)
In a machine-coding round, when do you add thread safety: from the start or at the end?

If the brief lists concurrency as a P0 requirement (Flipkart's 2026 quick-commerce brief did), design for it from the start: pick the lock scope while you design the entity that owns the shared state, because retrofitting locks onto a design often exposes check-then-act sequences that span several classes. If the brief does not mention it, build single-threaded but keep mutations inside owning classes, then add locks there if time allows and mention them in the review.

How to answer

Tie the decision to the written requirements, and point at where the locks live.

Likely follow-ups
  • Show me a race test for your code.
  • Why ConcurrentHashMap and not Collections.synchronizedMap?
How do you handle a round that drifts into database schema and APIs?

Treat it as step 4 extended. Map your classes to tables (rooms, bookings with a foreign key and an index on room plus time), and your orchestrator's methods to REST endpoints (POST /bookings, DELETE /bookings/{id}). Mention how the database would enforce no-overlap (a transaction with a row lock on the room, or an exclusion constraint where the database supports one).

How to answer

Keep the class design as the anchor and show both views map onto it.

Likely follow-ups
  • Optimistic vs pessimistic locking for bookings?

Scenario: 25 minutes left and no code

A 60-minute round. You spent too long on requirements and a detailed diagram. 25 minutes remain and the interviewer has not seen a line of code.

Keep polishing the diagram, then rush every class at once and run out of time with nothing complete.

Say "Let me move to code now." Write the orchestrator and the single logic-carrying method in full (15 min), trace one example (3 min), then spend the rest naming extensions and the lock scope. A complete core beats a complete skeleton.

Likely follow-ups
  • What would you code next with 10 more minutes?
