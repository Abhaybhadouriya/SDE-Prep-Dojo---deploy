Step 8 - Concurrency (5 min)

Almost every booking-style problem has the same race: check-then-act. Two threads both check "is the room free?", both see yes, and both add a booking. The fix is to make the check and the act one atomic step, under a lock that covers exactly the data being checked.

What to say, in order:

  1. Name the shared state. "Each room's booking list is mutated by concurrent book calls."
  2. Name the race. "Check-then-act on the list."
  3. Pick the scope. "A lock per room: tryAdd is synchronized on the room, so rooms do not block each other." A single global lock is also correct and simpler; say it is your fallback if time is short.
  4. Handle the other shared bits. IDs come from an AtomicInteger (a failed tryAdd uses one up, so ids are unique but can have gaps, which is fine); the id-to-booking map and the room map are ConcurrentHashMaps, so addRoom can run while bookings are in flight; the strategy reference is volatile so a swap is visible to all threads.
  5. Prove it. "My driver fires 50 threads at one slot with 3 free rooms; exactly 3 succeed." (Our driver does exactly this.)

From your world

This is the same reasoning as choosing between one big lock and per-object locks in the kernel - the move from the old Big Kernel Lock to fine-grained locks. synchronized on a room is a per-object mutex, like a spinlock_t embedded in each struct. The AtomicInteger id counter is atomic_inc_return(). And "never take two room locks at once" is your lock-ordering rule for avoiding deadlock.
