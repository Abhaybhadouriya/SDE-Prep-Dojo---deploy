What a pattern is (and is not)

A design pattern is a named, reusable solution shape for a problem that keeps coming back in a context. It has four parts: a name, the problem it fits, the solution (roles and how they collaborate), and the consequences (trade-offs).

A pattern isA pattern is not
a vocabulary: "use a Strategy for pricing" says a paragraph in four wordsa library or framework you import
a shape you adapt (names, number of classes, language features change)a fixed template you must copy exactly
a tool for one kind of changea goal; "use as many patterns as possible" is a bad design
language-shaped: in Python a Strategy may be a plain functiononly for Java

The GoF book rests on two rules you should quote in interviews:

  • Program to an interface, not an implementation. Depend on FeePolicy, not HourlyFee.
  • Favour object composition over class inheritance. Hold a FeePolicy object (has-a) instead of subclassing the parking lot for each plan (is-a). See Composition over Inheritance.

GoF also says to encapsulate the concept that varies (chapter 1, on designing for change); Head First Design Patterns made it its first design principle, and it is the key to choosing. Find the part that changes, and wrap exactly that. The selection guide below is built on it.
