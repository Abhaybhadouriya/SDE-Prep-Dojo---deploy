The problem patterns solve: code that fights change

Look at this parking lot exit method. It works on day one.

int exit(String vehicleType, int hours, String plan) {
    Vehicle v;
    if (vehicleType.equals("car")) v = new Car(); else if (vehicleType.equals("bike")) v = new Bike(); else ...
    int fee;
    if (plan.equals("FLAT")) fee = v instanceof Bike ? 20 : 50;
    else if (plan.equals("HOURLY")) fee = hours * (v instanceof Bike ? 10 : 30);
    else if (plan.equals("WEEKEND")) ...
    freeSpots++;
    displayBoard.update(freeSpots);      // and the SMS service, and the ops dashboard, and ...
    smsService.send(...);
    return fee;
}

Then the changes arrive: electric cars, a festival pricing plan, a new dashboard that wants spot updates. Each one means editing this same method. Every edit risks breaking the others, and the method grows into a god function. Three different kinds of change are knotted together:

  1. What gets created (car, bike, EV) - a creation problem.
  2. How the fee is computed (flat, hourly, weekend) - an algorithm problem.
  3. Who must hear about it (board, SMS, dashboard) - a notification problem.

A pattern untangles one kind of change and puts it behind an interface, so new cases are added as new classes instead of new if branches. (An interface is a promised set of functions with no implementation, exactly a struct of function pointers like file_operations; a class "implements" it by filling in the slots. More in Interfaces and the glossary.) That is the whole game, and it is called the Open/Closed Principle: open to extension, closed to modification.
