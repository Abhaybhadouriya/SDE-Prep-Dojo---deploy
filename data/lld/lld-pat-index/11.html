Interview questions

What is a design pattern? Why should we use them?

A named, reusable solution shape for a recurring design problem in a context, with known trade-offs. They give a team a shared vocabulary and a tested way to isolate one kind of change behind an interface, so new cases are added as new classes rather than edits to working code.

How to answer

Definition, then one concrete example from a case study ("pricing as Strategy in a parking lot"), then one caution (do not force them).

Likely follow-ups
  • What are the three GoF categories?
  • Which patterns have you used in your own project?
Name the three GoF categories with two examples each.

Creational (how objects are made): Factory Method, Builder, Singleton. Structural (how objects are composed or wrapped): Adapter, Decorator, Composite. Behavioral (how objects share responsibility and talk): Strategy, Observer, State. The book has 23 in total: 5, 7 and 11.

How to answer

Give the one-line question each category answers before the examples; it shows understanding, not memory.

Likely follow-ups
  • Is Simple Factory one of them? (No, it is an idiom.)
How do you decide which pattern to use in a new problem?

I look for what varies. If which class to create varies, a creational pattern (key, subclass or family). If an algorithm or rule varies, Strategy, Template Method or State depending on who chooses. If who reacts to an event varies, Observer or Pub-Sub. If an interface does not fit or needs wrapping, Adapter, Decorator, Proxy, Facade. If a request moves through steps or must be undone, Chain of Responsibility, Command, Memento. Then I check the pattern against a stated requirement, and drop it if there is none.

How to answer

Walk the five questions on a real example, such as the vending machine.

Likely follow-ups
  • Design an elevator: which patterns, and why?
Strategy and State have the same class diagram. What is the difference?

Both have a context that delegates to an interface. With Strategy, the client (or config) picks the algorithm and it usually stays fixed for the operation; strategies do not know each other. With State, the state objects represent the context's mode and decide the transition to the next state themselves, so the behaviour changes as the object's internal state changes.

How to answer

"Who changes it?" is the one-line test: the client (Strategy) or the state itself (State). Example: payment method vs vending machine mode.

Likely follow-ups
  • Could you implement State with an enum and a switch? When is that better?
Can you over-use design patterns? Give an example.

Yes. A UserFactory that only ever builds one User class, a Singleton ConfigManager that every class reaches for (hidden global, hard to test), or a Visitor added "for future operations" on a hierarchy that keeps gaining new types. Each adds indirection without guarding a real change. I add a pattern when the second case is real or explicitly required.

How to answer

Concrete examples plus a rule (YAGNI, rule of three).

Likely follow-ups
  • Then how do you keep code extensible? (Clean interfaces at the obvious seams; refactor to a pattern when needed.)
Which design patterns have you used in your own work?

Prepare two honest stories. For a kernel or networking engineer, good ones are: a driver filling struct net_device_ops or file_operations (Strategy/Bridge through function-pointer tables); registering a netdevice notifier to react to link up/down (Observer); a protocol or link state machine (State); netfilter hooks or a packet-processing pipeline (Chain of Responsibility); refcounted objects with kref. For each: the problem, why that shape, and one trade-off you hit.

How to answer

STAR-lite: situation, the shape you chose, result, trade-off. Translate C terms to pattern names.

Likely follow-ups
  • How would that look in Java?
  • What went wrong with it?
In a 90-minute machine-coding round, how many patterns should you use?

As many as the requirements justify, usually two or three: often a Strategy for the main varying rule, a factory for creating types from input, and maybe State or Observer. The rest of the score comes from working code, clean separation (models, services, repositories, a driver), and handling edge cases. A pattern you cannot finish in time is worse than a clear if.

How to answer

Tie patterns to requirements and to the time budget.
