Concurrency and thread safety

What can go wrong if two shells share the tree without a lock? Two mkdir /a calls both see "no child a" and both insert: one directory silently replaces the other with its subtree. Two appends to one StringBuilder corrupt it. A find walking a TreeMap while rm changes it throws ConcurrentModificationException. Every one is a check-then-act race.

Step through the race this section is about, then the fix the code uses:

  1. Shell A runs mkdir /home/a and looks up the child: there is none.
  2. Shell B runs the same command and also finds no child named a.
  3. Both insert. The second put silently replaces the first directory, and anything A already created inside it is gone.
  4. The fix: every mutating command takes the tree's write lock for the lookup and the insert together, so B waits and then gets "already exists". Reads (ls, cat, find) share the read lock. The demo's 8 threads x 400 appends end with exactly 3,200 bytes.

Level 1: one read-write lock on the tree (what the code does)

ls, cat, du, find and wildcard resolution take the read lock; mkdir, write, rm take the write lock. Readers run in parallel; a writer runs alone. The demo's 8 threads x 400 appends end with exactly 3,200 bytes, so no write was lost. It is correct, simple, and impossible to deadlock because there is only one lock. Its cost: one writer anywhere blocks every reader everywhere. Details of the lock itself are in locks and synchronisation.

Level 2: finer locks (the follow-up answer)

  • A lock per directory. mkdir /a/b/c only needs c's parent. Walk down taking each directory's read lock (or no lock with a stable snapshot), then take the parent's write lock for the insert. Two mkdirs in different folders no longer block each other.
  • Lock ordering for two-directory operations. mv /a/x /b/x touches two parents. Always lock them in one global order (for example ancestor first, then by node id) or two opposite moves deadlock. Linux does this in lock_rename(), with a file-system-wide rename mutex to stop a directory being moved into its own subtree.
  • Lock-free reads. Readers walk without locks while writers publish changes by swapping in new child maps (copy-on-write). That is the idea behind RCU path walk in the kernel and behind ConcurrentHashMap lookups in Java.
  • Per-file content lock. Two appends to different files should not wait for each other: give each FileNode its own lock (or a synchronized block) for content, separate from the tree structure lock.

From your world

The kernel's answer is the same ladder. Each directory inode has i_rwsem (taken exclusive for create and unlink in that directory, shared for lookup on many file systems). The dentry hash is read under RCU and a rename_lock seqlock, so a lookup that raced with a rename simply retries. And a shell that sits in a removed directory keeps it alive through a dentry reference count (dget/dput): the directory is unhashed but not freed, and /proc/self/cwd shows it as "(deleted)". Our Java code takes the simpler route and moves the shell to /; the C++ version keeps the removed directory alive through its shared_ptr, exactly like a dentry refcount, before falling back.

What about the Shell?

A Shell is not thread-safe and does not need to be: one session is driven by one thread, like one process's cwd. If the interviewer wants a session shared across threads, make cwd volatile (it is a single reference swap) and keep all tree work inside FileSystem.
