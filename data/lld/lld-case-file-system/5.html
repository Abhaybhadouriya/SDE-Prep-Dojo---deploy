Key relationships and patterns

PatternWhereWhy here (say this in the room)
CompositeNode / FileNode / DirectoryThe domain is a part-whole tree. du, path() and find treat a file and a whole folder the same way, with no if (isFolder) ladders. We chose the safe variant: only Directory has add/remove, so file.add(x) cannot even compile.
SpecificationSpec, Specsfind filters combine freely (-type f -size +10 ! -name '*.txt'). One small predicate per rule plus and/or/not gives any combination without a new method per combination. The classic "design Unix find" follow-up is usually answered with composable filters like these.
FacadeFileSystemOne entry point hides path parsing, the walk, wildcard expansion and locking. Callers never touch nodes directly.
Session objectShellKeeps the per-user state (cwd) out of the shared object. Same reason a process, not the VFS, holds its cwd.
Iterative DFS (explicit stack), not yet the Iterator patternfind()A pre-order walk without recursion, so a 10,000-deep tree cannot blow the call stack. It returns a finished List, so it is a traversal, not the Iterator pattern. To make it one, return an Iterator<Node> (or a Python generator) that keeps the stack as its own state: callers then get lazy, early-exit find ("first 10 results") without seeing the tree's structure.
Command (optional)command parserIf asked for a shell prompt, map each command word to a handler object; a new command is one new class. Shown in extensibility.

From your world

Bridge, as the kernel does it. Our FileSystem talks to nodes through a tiny abstract API (isDirectory, size, children). The VFS talks to every file system through struct inode_operations and struct file_operations: tables of function pointers that ext4, tmpfs and procfs each fill differently. The abstraction (vfs_mkdir(), vfs_read()) and the implementation (ext4_mkdir, shmem_mkdir) vary independently. In Java we would get that by making Directory an interface with an in-memory and a disk-backed implementation; in C you write the ops table by hand. Same idea, different syntax.

Why the safe Composite and not the transparent one

If add() lived on Node, the parser could call it on anything, and FileNode.add() would have to throw at runtime. That violates the Liskov Substitution Principle: a file could not keep a promise its base class makes. With the safe variant the cost is one downcast in walk() after an isDirectory() check, which is exactly where Unix reports ENOTDIR anyway.

Why the pattern earns its place: the if-ladder it replaces

Without Specification, each new find option is another parameter and another branch:

List<String> find(Directory root, String name, Character type, Long minSize, boolean notTxt) {
    List<String> out = new ArrayList<>();
    for (Node n : walk(root)) {
        if (name != null && !Glob.matches(name, n.name)) continue;
        if (type != null && type == 'f' && !(n instanceof FileNode)) continue;
        if (type != null && type == 'd' && !(n instanceof Directory)) continue;
        if (minSize != null && n.size() <= minSize) continue;
        if (notTxt && n.name.endsWith(".txt")) continue;   // "-o" (or) cannot be expressed at all
        out.add(n.path());
    }
    return out;
}
interface Spec {
    boolean test(Node n);
    default Spec and(Spec o) { return n -> test(n) && o.test(n); }
    default Spec or(Spec o)  { return n -> test(n) || o.test(n); }
    default Spec not()       { return n -> !test(n); }
}
// find / -type f -size +10 ! -name '*.txt'
Spec s = Specs.isFile().and(Specs.sizeOver(10)).and(Specs.name("*.txt").not());
fs.find(root, "/", s);

With the parameter list, the follow-up "support -o and -mtime" changes find's signature and every caller. With Spec it adds one factory method in Specs.java; FileSystem.find does not change. It is the same idea as composing BPF predicates.

From your world: the same move in C

struct spec { bool (*test)(const struct spec *s, const struct node *n); };
struct spec_and { struct spec base; const struct spec *l, *r; };
static bool and_test(const struct spec *s, const struct node *n)
{ const struct spec_and *a = (const void *)s; return a->l->test(a->l, n) && a->r->test(a->r, n); }
/* build a tree of predicates once, then walk the file tree calling root->test(root, n) */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
