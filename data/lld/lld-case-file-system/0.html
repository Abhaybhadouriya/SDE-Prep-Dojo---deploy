The story: the cupboard of boxes

Explain like I'm 5

You have a big cupboard. Inside are boxes, and inside the boxes are more boxes, and some boxes hold drawings. Every box has a name written on it. To find your cat drawing you say: "open the big cupboard, then the box called school, then the box called art, and take out cat". That list of names is a path.

You always stand next to one box: that is where you are. "Go back one box" means go to the box that holds this one. If a friend asks "how heavy is the school box?", you weigh every drawing inside it, and every box inside it, and add it all up. And if your friend says "go into any box and then into art", you try each box until one of them has an art box inside.

That is the whole problem. A directory is a box that holds named things. A file is a drawing: it holds content and nothing else. The current directory is the box you stand next to. A path is the list of names to walk, starting either from the top of the cupboard (/home/asha, absolute) or from where you stand (../ravi, relative). Interviewers then add twists: wildcards, search by size or name, many users at once, moving folders.

From your world

You have read this code before. The Linux VFS keeps a tree of struct dentry (name, d_parent, children) pointing at struct inodes. A path lookup (link_path_walk() in fs/namei.c) splits the path on /, handles . and .., and looks up one component at a time in the current dentry: exactly the walk() method on this page. A directory inode carries inode_operations with lookup, mkdir and unlink; a regular file's does not. And every real file system (ext4, tmpfs, procfs) plugs its own file_operations and inode_operations tables in under the same VFS calls, which is the Bridge pattern. What we build today is roughly a ramfs: the tree, with the content kept in memory.

New to classes? Read OOP from C first: it maps structs, function pointers and ops tables onto classes, interfaces and virtual calls. Every pattern on this page also appears in Patterns in the kernel.
