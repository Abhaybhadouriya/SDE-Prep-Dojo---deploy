Core flows

Flow 1: cd */projects from /home/asha

This is the call the Uber reports call hard. The trick is to stop thinking "walk one path" and think "walk a set of directories, one segment at a time". Each segment maps every directory in the set to zero or more next directories. A segment that leads nowhere simply drops that branch. This is a breadth-first search over the tree, and it is how a shell expands globs too.

  1. The driver calls cd on its own Shell. The Shell sees a wildcard in the path, so a plain walk will not do.
  2. The Shell asks the shared FileSystem for every directory the pattern can reach from its cwd. The tree takes a read lock: many shells may resolve at once.
  3. Segment * on the set {asha}: "." gives asha, ".." gives home, and the children give projects. An identity set removes duplicates (".." of root is root, so "/*" would see root twice).
  4. Segment projects on each member: only asha has a child called projects; home/projects and projects/projects do not exist, so those branches drop out.
  5. The final set is sorted by absolute path so the answer is deterministic, and the lock is released.
  6. The Shell applies the agreed rule (first match) and updates its own cwd. Nothing in the shared tree changed, which is why a read lock was enough.

Cost: if the tree has branching factor b and the pattern has k wildcard segments, the set can grow to O(bk) in the worst case, bounded by the number of directories (the identity set stops repeats). Real shells have the same cost: ls /*/*/* on a big disk is slow for the same reason.

Flow 2: find /var -type f -size +10 ! -name '*.txt'

From your world

A Spec tree is a tiny version of a BPF filter program or an nftables rule expression: small predicates combined with AND/OR/NOT and evaluated per packet, where here the "packet" is a node. find(1) itself parses its command line into exactly such an expression tree before walking, with -a, -o and ! as the operators.
