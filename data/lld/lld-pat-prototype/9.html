When to use it, and when not to

Use it when
  • Building an object is expensive (I/O, parsing, heavy computation) and many objects start out the same.
  • You hold an object through an interface and need "another one like this" without knowing its class.
  • Objects are configured at run time (from files or users) rather than by subclasses; a registry of prototypes replaces a zoo of subclasses.
  • You need snapshots of state, for example to try a move on a copy of a chess board.
Avoid it when
  • Construction is cheap and simple: just call the constructor or a factory.
  • Objects hold resources that cannot be copied meaningfully (sockets, DB connections, threads, locks).
  • The object graph is large with cycles and back-pointers: a correct deep copy is hard and easy to get subtly wrong.
  • Objects are immutable: you can share the same instance instead of copying it (see Flyweight).

Why Java's Cloneable is considered broken. Cloneable has no methods at all; it only changes how the protected Object.clone() behaves. That clone() makes a field-by-field shallow copy without running any constructor, throws a checked CloneNotSupportedException, and cannot reassign final fields, so deep-copying a final mutable field is impossible. Effective Java Item 13 ("Override clone judiciously") recommends a copy constructor or a static copy factory instead. Arrays are the exception: array.clone() is fine.
