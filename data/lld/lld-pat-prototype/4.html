Deep vs shallow: the part interviews test

A shallow copy makes a new outer object but copies references to inner objects, so inner objects are shared. A deep copy also copies the inner objects, recursively, so nothing mutable is shared.

Field typeShallow copy is fine?Why
Primitives (int, bool)YesCopied by value.
Immutable objects (String, records, Python tuple of immutables)YesNobody can change them, so sharing is safe and saves memory.
Mutable collections and objects (List<Seat>, dict)NoChanges through one copy appear in the other.
Resources (sockets, file handles, locks, threads)NeitherUsually must not be copied at all: open a new one, or share deliberately with reference counting.
Back-pointers and cycles (child points to parent)Needs careA naive recursive copy loops forever; keep a map "original -> copy" (Python's deepcopy uses a memo dict for this).

From your world

fork() is the most famous prototype in computing. The kernel's copy_process() starts from the running parent and duplicates its task_struct; the address space is copied lazily with copy-on-write, so you get deep-copy semantics at shallow-copy cost until someone writes. And clone(2) lets you choose per resource: CLONE_VM, CLONE_FILES, CLONE_FS mean "share it" (shallow), leaving the flag out means "copy it" (deep). A thread is a very shallow clone; a forked process is a deep one.

Even fork() has a shallow corner: the child gets its own file descriptor table, but each entry points to the same open file description, so parent and child share the file offset. Networking has the same pair: skb_clone() makes a new sk_buff header that shares the data buffer (shallow, reference-counted), while skb_copy() copies the data too (deep). You pick based on whether anyone will write.
