Interview Q&A

What is the difference between a shallow copy and a deep copy?

A shallow copy creates a new outer object but copies references to the inner objects, so those inner objects are shared. A deep copy also copies the inner objects recursively, so the two copies share nothing mutable. Shallow is fine for primitives and immutable fields; mutable inner objects need deep copies.

How to answer

Definition, then a concrete bug (seat booked in two shows), then the rule "share immutables, copy mutables".

Likely follow-ups
  • Is new ArrayList<>(list) deep or shallow? (Shallow: new list, same elements.)
  • How does Python's deepcopy avoid infinite loops?
When would you use Prototype instead of a factory?

When building from scratch is expensive and many objects start identical, or when you only hold an interface reference and need another object of the same concrete type with the same configuration. A factory knows how to construct a type; a prototype already is one, configured, and copies itself.

How to answer

Cost argument plus "unknown concrete class" argument; one example each.

Likely follow-ups
  • Could a factory use prototypes internally? (Yes, a registry-backed factory clones stored prototypes.)
Why is Java's Cloneable considered broken, and what do you use instead?

Cloneable is a marker interface with no clone() method; Object.clone() is protected, shallow by default, skips constructors (so invariants set there are not re-established), throws a checked exception, and cannot assign to final fields, which blocks deep copies of final mutable fields. Use a copy constructor (new Order(other)) or a static factory (Order.copyOf(other)) that you control; for polymorphic copies, declare your own copy() method in an interface.

How to answer

Three or four concrete defects, then the replacement, citing Effective Java Item 13.

Likely follow-ups
  • Is int[].clone() ok? (Yes for arrays of primitives; arrays of objects are shallow.)
How do you deep-copy an object graph that has cycles (for example, a doubly linked list or parent pointers)?

Keep an identity map from original object to its copy. Before copying a node, check the map: if it is already there, reuse that copy; otherwise create the copy, put it in the map first, then copy its fields recursively. This copies each object exactly once and preserves shared structure and cycles. Python's copy.deepcopy does exactly this with its memo dict. It is the same algorithm as LeetCode 138 "Copy List with Random Pointer" and 133 "Clone Graph".

How to answer

State the identity map, the "insert before recursing" rule, and link to the graph-clone problem they probably know.

Likely follow-ups
  • Why IdentityHashMap and not HashMap in Java? (Two distinct but equal objects must get two copies.)
Your object holds a database connection and a lock. How should clone() treat them?

Do not copy them blindly. A lock copied with the object would be either a second lock that protects nothing shared, or the same lock, causing hidden contention. A connection cannot be duplicated by copying bytes. Options: share the connection deliberately (reference-counted or owned by a pool), give the copy a fresh lock, or exclude these fields from the copy and re-initialise them, for example in __deepcopy__ in Python.

How to answer

Separate "state" (copy) from "resources" (share on purpose or recreate).

Likely follow-ups
  • How does fork() handle open file descriptors? (Shared open file descriptions, including the offset.)
Explain fork() as a prototype. How does copy-on-write change the cost?

fork() makes a new process by copying the calling one: copy_process() duplicates the task structure and sets up the child's address space. With copy-on-write, both processes share the same physical pages marked read-only; only when one of them writes does the kernel copy that page. So the clone has deep-copy semantics but costs roughly a shallow copy until writes happen. clone(2) flags let callers pick per resource whether to share or copy, which is how threads are made.

How to answer

Map prototype = parent, clone = child, then explain COW as "lazy deep copy", then mention the CLONE_* flags as per-field shallow/deep choice.

Likely follow-ups
  • Could you do copy-on-write in an application object? (Yes: share an immutable inner structure and copy it on first write, as CopyOnWriteArrayList does on every write.)
