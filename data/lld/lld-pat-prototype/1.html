The problem: expensive setup, unknown classes

Without the pattern, the show-creation code rebuilds the layout every time and has to know every layout class:

Show createShow(String screenId, LocalDateTime time) {
    ScreenRow row = db.loadScreen(screenId);          // network + DB round trip
    PricingRules rules = pricing.rulesFor(screenId);  // another call
    SeatLayout layout;
    if (row.kind().equals("IMAX"))       layout = new ImaxLayout(row, rules, glassesStock());
    else if (row.kind().equals("4DX"))   layout = new FourDxLayout(row, rules, motionSeats());
    else                                 layout = new SeatLayout(row, rules);
    return new Show(screenId, time, layout);           // 500 shows a day = 500 loads
}

Two separate pains:

  1. Cost. The work to make the first object (I/O, parsing, computing) is repeated for objects that differ only in a few fields.
  2. Coupling. The creator must know every concrete class and its constructor arguments. Code that only holds a SeatLayout reference cannot make "another one like this" without an if on the type.

A naive fix makes it worse:

SeatLayout template = loadOnce("AUDI-1");
Show monday  = new Show(..., template);   // both shows point at ONE layout object
Show tuesday = new Show(..., template);
monday.layout().book("A1");                // tuesday now shows A1 as booked too

Sharing the template is not copying it. We need each show to get an independent copy, made cheaply, without knowing the concrete class.
