The story: the driving-test examiner

Explain like I'm 5

A driving examiner sits next to you with a clipboard. The clipboard has boxes. The first box is the big one: did the car move and stop safely? If you crash, nothing else matters. If you drive safely, the examiner then ticks smaller boxes: did you use the mirror, did you signal, did you park neatly?

Some learners practise fancy parking for weeks but forget to check the mirror. Others drive perfectly but so slowly that the test time runs out. Both fail, for very different reasons.

An LLD evaluator has a clipboard too. The big box is "does the code run and do what was asked?" The small boxes are "is it split into sensible parts?", "can I add a feature easily?", "does it fail politely on bad input?". This page shows you the clipboard.

From your world

You already know this rubric. It is patch review on a kernel mailing list. A maintainer first checks that the patch applies and builds (does it run?). Then: does it do one thing per patch (single responsibility)? Does it add a new if (vendor == X) in the core path, or a new entry in an ops table (extensibility)? Does it handle the error path and free what it allocated (error handling)? Is the locking right (concurrency)? A machine-coding evaluator reads your zip the way a maintainer reads your patch series.
