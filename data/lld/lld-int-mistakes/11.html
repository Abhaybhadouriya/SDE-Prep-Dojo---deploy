Interview Q&A: questions about your own design

These are the "meta" questions evaluators ask about the code you just wrote. Filter by level or company.

Walk me through your code in two minutes.

Use a fixed shape: problem in one sentence, layers, one flow, what is missing.

"It's a bug-bounty tracker. model has the entities and the status state machine; repository hides storage behind interfaces with in-memory maps; service holds the use cases and checks permissions; Main wires it and runs the demo. Take changeStatus: it checks the user is the assignee, locks that one report, asks the status enum whether the move is legal, then records history and notifies the reporter. All P0 and three bonus features are done: the transition table, the status history and reporter notification. The time log and adding users at runtime are not."

How to answer

Top-down, never line by line (a workat.tech red flag). End with an honest status of what is done. Flipkart evaluators start by asking you to explain the problem and your code (2026-02-19).

Likely follow-ups
  • Which class would you split first if it grew? (the service with the most reasons to change, usually by pulling one rule out into a Strategy)
  • Where are the tests? (point to the test file, or to the driver cases that act as tests, and name the edge cases covered)
How would you move this from in-memory maps to a real database?

Write a new implementation of the repository interface (for example JdbcOrderRepository) and change one line in the wiring code. The services do not change because they only know the interface. Then mention what does change: ids come from the database, the per-object locks become row locks or conditional updates with a version column, and multi-step operations need a transaction.

How to answer

Show the seam first (interface plus composition root), then the parts that are not a simple swap (transactions, locking). That second half is what makes it an SDE-2 answer.

Likely follow-ups
  • SQL or NoSQL here, and why? (SQL for transactional state such as bookings and money; say which constraint the database enforces for you)
  • What happens to your in-memory locks with two app servers? (they protect nothing across servers; move the guard into the shared store (a row lock or a conditional update) or into a distributed lease)
Your feedback says "modular but not extensible". What does that mean, concretely?

"Modular" means the code is split into parts. "Extensible" means a new requirement is a new part, not edits across the old ones. You can have many files and still be closed to change: if adding a payment mode means touching the enum, a switch in the service, a switch in the validator and the printer, the design is modular but not extensible. The fix is to put each axis of change behind one interface or one table, so a new variant is one new class or one new row.

How to answer

Give a count: "a new mode touched N files before, one after". This exact feedback appears in a Flipkart rejection (2023-04-01) and a Razorpay one (2025-06-26).

Likely follow-ups
  • Is that the open/closed principle? (Yes; see OCP.)
Why did you use a pattern here? Would the code be worse without it?

Justify a pattern by the change it absorbs, not by its name. "Allocation can be nearest-first or highest-rated, and the brief hints at more, so AllocationStrategy is an interface with two classes. Without it, every new rule edits assign()." If you cannot name the variation, say so and remove the pattern: HelloInterview warns against forcing patterns where they do not fit.

How to answer

Pattern = answer to "what varies?" Name the varying thing, the alternative you rejected, and the cost (one more indirection).

Likely follow-ups
  • Strategy or State here? (See pattern look-alikes.)
Two requests hit the same resource at once. Show me where your code breaks and fix it.

Point to the check-then-act: "if (seat.isFree()) seat.book(user) - two threads can both see free." Then fix it at the smallest scope: lock that seat (or use a compare-and-set on its state), do check and act inside, and let the loser get a clear "already booked" error. Say what you did not lock and why (other seats proceed in parallel). Finally show a test: N threads, one seat, exactly one success.

How to answer

Race, scope, mechanism, proof. Avoid "make the method synchronized" as your whole answer; a Google interviewer was not satisfied with that (2019-09-10).

Likely follow-ups
  • Can this deadlock? (Only if you take two locks; always take them in id order.)
  • Optimistic version? (keep a version per entity, write with WHERE id=? AND version=?, and retry from a fresh read when zero rows change)
What happens if I pass an invalid id or call cancel twice?

Both must fail with a named, specific exception and leave state unchanged. Invalid id: the repository lookup throws NotFound. Double cancel: the entity's state machine rejects CANCELLED -> CANCELLED. The driver shows both, so the evaluator sees it before asking.

How to answer

Run it live. Then mention the design reason: all state changes go through one guarded method, so there is one place to get it right.

Likely follow-ups
  • Checked or unchecked exceptions, and why? (A checked exception is one the compiler forces every caller to catch or declare, like a __must_check return value. Business errors are usually unchecked, extending RuntimeException, so one handler in the driver catches them and the service signatures stay clean.)
You sorted the list on every call. Is there a better structure?

If items arrive over time and you always need the smallest or highest-priority one, keep a priority queue (heap): insert and remove are O(log n) and you never re-sort, while sorting on each call is O(n log n). If you need ordered iteration and removal by key, a tree map. Say which access pattern you have, then pick. A Flipkart evaluator asked exactly this about a task scheduler (2026-02-19).

How to answer

Name the operations and their frequency first, then the structure, then the complexity.

Likely follow-ups
  • What if priorities change after insertion? (a binary heap cannot re-key in place: remove and re-insert (a TreeSet or an indexed heap), or push a new entry and skip stale ones on pop)
You named an LRU cache. Write it.

When your design leans on one algorithm, the interviewer will ask for it. LRU = hash map from key to node + doubly linked list ordered by recency; get moves the node to the front, put inserts at the front and evicts the tail when full; both O(1). In Java, LinkedHashMap with access order and removeEldestEntry is acceptable if you say what it does inside. An Amazon candidate who named LRU but did not implement it called that round the one they "messed up" (2025-07-15).

How to answer

Find the core algorithm in every prompt (cache: eviction; parking: spot finding; rate limiter: the window) and plan time to write it in real code. See LRU cache case.

Likely follow-ups
  • Make it thread-safe without one global lock. (stripe it: N shards, each with its own map, list and lock, chosen by the key's hash)
  • TTL per entry? (store an expiry time per node, treat expired entries as misses on get, and sweep lazily or with a timer wheel)
Before you start: do you want running code or a design discussion?

This is a question you ask, in the first minute. Interviewers differ inside the same company: one Microsoft loop wanted end-to-end running code (2024-12-03), another was whiteboard only (2026-03-09). An Amazon candidate asked the community "UML or code?" before their round (2026-07-07). Asking costs five seconds and prevents mistake 8.

How to answer

"Should I aim for compiling code with a small demo, or class design plus the key methods?" Then also ask about language and whether tests are expected.

Likely follow-ups
  • "Whatever you prefer." (Then pick running code for the core and say so.)
How did you test this? Show me a failing test first.

Atlassian's official page says tests are crucial and suggests brushing up on TDD. Have the framework ready (JUnit 5 or pytest), write one test per requirement named after it (trialDaysAreFree), and run them after every change. For a follow-up, write its failing test first, then make it pass while the old tests stay green. That is the habit the round grades.

How to answer

Show the test list as a spec: it is also the fastest way to show what you covered.

Likely follow-ups
  • How do you test time-dependent code? (Inject a clock: pass a Clock or a now() function into the service instead of calling the system time, so a test can fix or step time, like handing code a jiffies source you can mock. The Flipkart mock on the mock interviews page uses a test clock that moves one minute per reading.)
  • How do you test the concurrency claim? (start N threads behind a latch on the same resource and assert the invariant (exactly one winner); run it many times)
Why is your service class 600 lines long?

Because it does several jobs. Split by reason to change: parsing input (driver or command parser), storage (repository), rules that vary (strategies), state rules (the entity or a state machine), output (printer/notifier). The remaining service orchestrates: validate, load, call the rule, save. A god service is the most common reason behind "SRP not followed" feedback.

How to answer

List the jobs it does, then name the class each job moves to. See anti-patterns and SRP.

Likely follow-ups
  • Isn't that over-engineering for 90 minutes? (Only if you build splits nobody needs; these follow the brief.)
My code worked and the feedback was still negative. What else could it have been?

Working code passes the gate; the decision comes from the score boxes and from signals you may not notice: how many hints you needed, whether you clarified, how you handled the concurrency follow-up, how you took pushback, and level calibration (an SDE-2 bar expects you to drive). Feedback is also noisy: one Uber candidate heard "negative LLD feedback" after giving working code and still got an offer after the debrief (2025-05-22). A Swiggy candidate who "thought it went well" was rejected and felt the bar had risen (2025-11-30).

How to answer

If a recruiter asks for your self-assessment, name one concrete thing you would do differently. For your own prep, grade yourself on the full rubric with the mock self-grading sheet, not just "it ran".

Likely follow-ups
  • What would a "strong hire" have done in the same round? (the same working code plus named trade-offs, an extension done live without a rewrite, and tests for the edge cases)
Is comments-everywhere the same as readable code?

No. Readable code first comes from names (assignNextWaitingOrder, not process), small methods and one level of abstraction per method. Comments then explain why: an assumption ("partners are available 24x7, as the brief says"), a trade-off, or a rule from the brief. Flipkart lists code comments as a criterion, so a short header comment per class plus assumptions at the top of the driver is a cheap win.

How to answer

Show your assumptions block: it is also where the Flipkart brief asks you to convey assumptions to the panel.

Likely follow-ups
  • How do you name exceptions? (after the business failure, such as SlotUnavailableException or LimitExceededException, under one base type)
AI tools: allowed or banned, and what changes in grading?

Both exist in 2026. The Flipkart 2026 brief bans AI tools outright and allows the internet only for syntax (2026-02-18). Other companies run "AI-assisted" rounds; a CRED SDE-2 report describes a 120-minute AI-assisted design round (2026-01-03). Where AI is allowed, the boxes move up a level: they assume code appears fast, so they grade your decomposition, how you check generated code, your tests and your answers to "why". Ask the recruiter; never assume.

How to answer

Say how you would verify AI output: read every line, run tests, and own each design choice in the review.

Likely follow-ups
  • What did the tool get wrong, and how did you notice? (give one concrete case, such as a missing lock found by your race test or an invented API found when it failed to compile)
