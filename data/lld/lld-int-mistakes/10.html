Scenario drills

Six moments where rounds are won or lost. Read the situation, decide what you would say, then compare.

Scenario: minute 70 of 90, one P0 still broken

Flipkart-style round. Five of six P0 features work. Cancel-order throws a NullPointerException. You also planned a nice Observer for notifications (bonus).

Keep building the Observer because "it shows design skill", and leave cancel for the review call.

Freeze bonus work. Fix cancel with the simplest correct code, add it to the driver, run everything. With the minutes left, put a one-line interface where notifications would plug in and say so in the review. A broken P0 costs more than a missing bonus every time (Flipkart brief, 2026).

Likely follow-ups
  • "How would you add notifications now?" (Show the interface and the one place it is called.)

Scenario: "Just cover the basic requirements"

You ask about future features so you can design for them. The interviewer says to focus on the basics. Later the feedback says "not extensible". This happened to a Razorpay candidate (2025-06-26).

Write the basics as one class with everything inline, since no future features were promised.

Extensibility is graded even when no future is stated. Build the basics, but with seams that cost nothing: entities separate from the service, storage behind a small interface, the obvious variant point (ranking, pricing, matching) as an interface with one implementation. Then say in one sentence where a new feature would plug in.

Likely follow-ups
  • "Add search by tag." (A new index in the repository, no change to the service API.)

Scenario: you planned a whiteboard, they open an IDE

Walmart-style LLD round: connection pool for any kind of resource. You start drawing classes; the interviewer wants code right away (2024-12-14).

Insist on finishing the diagram first because "that is how LLD works".

Switch at once. Create the empty classes and interfaces in the IDE as your diagram (Pool<T>, ResourceFactory<T>, acquire/release), say the relationships aloud, then fill in acquire with a bounded blocking queue. The code becomes the diagram.

Likely follow-ups
  • "What if no resource is free?" (Block with timeout, or fail fast; make it a policy.)
  • "How do you detect a leaked resource?" (wrap each handle with the time and the borrowing thread, and have a reaper log or reclaim any held past a timeout, the way a leak detector tracks allocations)

Scenario: the evaluator types an input you never tried

Review call. They call cancelOrder("XYZ") with an id that does not exist, then cancel the same real order twice.

The first prints a stack trace; the second silently cancels again and refunds twice.

Both are refused with a named exception and a clear message (OrderNotFound, InvalidTransition CANCELLED -> CANCELLED). This only happens if state changes go through one guarded method. The Cleartrip interviewer checked exactly these cases (2026-07-21).

Likely follow-ups
  • "Where do you validate, in the service or the entity?" (Entity guards its own state; service checks ids and permissions.)

Scenario: "Make it thread-safe"

Ride hailing. Two riders request at the same instant; one free driver nearby.

"I'll add synchronized to requestRide."

"The race is on the driver's state: AVAILABLE to ASSIGNED. I make that one transition atomic per driver, either synchronized(driver) around check-and-set or an AtomicReference compare-and-set. The loser tries the next driver. Different drivers never block each other." The Uber report says this was the real test (2026-08-29).

Likely follow-ups
  • "Pessimistic or optimistic, and why?" (pessimistic here: one hot driver gets many concurrent requests, so retries would pile up)
  • "How would this look with drivers in a database?" (a conditional update, UPDATE driver SET state='BUSY' WHERE id=? AND state='FREE', and one affected row means you won)

Scenario: a follow-up that would need a rewrite

Atlassian-style code design. Part 1 works with tests. Part 2: "add a free trial period". Your cost logic is a single loop with prices inline.

Rewrite the whole calculation with trial logic mixed into the loop, breaking part 1's tests along the way.

First run the part-1 tests (green). Pull the "is this day charged?" question out into a small rule interface, re-run (still green), then add a trial rule and its tests. Refactor, then extend: the round grades exactly that habit. The full version is mock 3 on the mock interviews page.

Likely follow-ups
  • "Now a plan can change mid-month." (One more small change if the data model holds periods.)
