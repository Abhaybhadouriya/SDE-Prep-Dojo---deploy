Concurrency mistakes, the ones that cost SDE-2 offers

About 24 of the posts in our company research mention concurrency, and about 15 make it a real requirement or follow-up. The question is nearly always the same shape: two actors grab the last unit of something (seat, driver, delivery partner, stock). The mistakes are also the same.

Weak answers
  • "Make every method synchronized." Correct but serial: one lock for the whole system.
  • "Use ConcurrentHashMap." The map is safe; your check-then-act on the value inside it is not.
  • Locking the collection but mutating the entity outside the lock.
  • Not knowing optimistic vs pessimistic locking (asked at Cleartrip, 2026-07-21).
  • Never testing it: no thread race in the driver.
Strong answers
  • Name the shared state and the race: "status check, then assign, on one driver".
  • Pick the scope: per entity lock (per seat, per driver) or an atomic compare-and-set on its state.
  • Say the trade-off: pessimistic is simple and right when conflicts are common; optimistic (version check, retry) is better when they are rare.
  • Prove it: N threads race for one item, exactly one wins (see the Flipkart mock on the mock interviews page).
  • Mention what changes with a database: row lock or a conditional update with a version column.

What a version check looks like, in memory and in SQL. Read the version, compute, and write only if nobody changed it in between; otherwise retry:

Seat old = seatRef.get();                          // an immutable snapshot with a version number
Seat next = old.book(userId).withVersion(old.version() + 1);
if (!seatRef.compareAndSet(old, next)) retry();    // someone else won: re-read and try again
UPDATE seat SET status = 'BOOKED', version = version + 1
 WHERE id = ? AND version = ?;   -- 0 rows updated means another writer won: retry or refuse

From your world

This is exactly "take the spinlock on the object, not a global lock", and "check-then-act needs one critical section, or a cmpxchg". A per-seat lock is a per-socket lock; an optimistic version check is a seqlock-style retry. You already have the instincts; just say them in Java words. More on the booking concurrency page.
