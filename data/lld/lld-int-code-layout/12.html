Where the locks go (and where they do not)

Concurrency is the most common follow-up in these rounds: double allocation of the last seat, the same driver, the same item. The layout decides where the answer goes. Locks belong in the service, around the check-then-act on one entity, at the smallest scope that protects the invariant.

Java in one line: every Java object carries a built-in lock (a "monitor"). synchronized (fc) { ... } takes the lock that lives inside the object fc and releases it at the closing brace, even if an exception is thrown. So two threads booking different classes never wait for each other; two threads on the same class do. Python has no built-in per-object lock, so our Python objects carry an explicit threading.Lock field and use with fc.lock:.

Never call alien code while holding a lock. Listeners are someone else's code: they may be slow (an SMS gateway), throw, or call back into the service and deadlock. So book() and cancel() collect their events under the lock and fire them after releasing it, and each listener call sits in a try/catch that logs the failure. The booking is already committed; a broken listener must not turn it into an error. Our tests include a listener that always throws, and the booking still comes back CONFIRMED.

Our race test starts 64 threads held at a start gate, all booking the one seat of class hot. The gate is a latch (Java CountDownLatch, Python threading.Event): a counter every thread waits on, so releasing it starts them all at the same instant, like a struct completion or a pthread_barrier. The test checks that exactly one booking is CONFIRMED and 63 are WAITLISTED. Remove the class lock and the count of confirmed seats goes above one on some runs. That race is the reason the lock exists. (This is the one place in the interview pages where the race test is explained in full; the other pages link here.)

From your world

"User lock, then class lock, in that order everywhere" is the same lock-ordering rule lockdep checks for you: take rtnl_lock before a device's own lock, never the reverse. cancel() only takes the class lock, which is safe because it never then waits for a user lock. Firing listeners after the unlock is the kernel habit of not running callbacks that may sleep while a spinlock is held. Our deadlock page and booking concurrency page go deeper.
