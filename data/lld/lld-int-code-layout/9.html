Services: one public method per requirement

Open the problem statement and copy its numbered features as method names. "Book a class" becomes book(userId, classId), "cancel a booking" becomes cancel(bookingId). The reviewer can then tick requirements off by reading your service's public methods.

public Booking book(String userId, String classId) {
    User user = users.get(userId);
    FitnessClass fc = classes.get(classId);
    Booking b;
    synchronized (user) {                         // lock order everywhere: user first, then class
        List<Booking> active = activeFor(userId);
        if (active.stream().anyMatch(x -> x.getClassId().equals(classId)))
            throw new ValidationException(userId + " already holds a booking for " + classId);
        int limit = limitPolicy.maxActiveBookings(user);
        if (active.size() >= limit)
            throw new LimitExceededException(userId + " reached the " + user.getTier()
                    + " limit of " + limit + " active bookings");
        synchronized (fc) {                       // per-class lock: two users racing for the last seat
            String id = "B" + nextId.getAndIncrement();
            if (fc.hasFreeSeat()) {
                b = new Booking(id, userId, classId, BookingStatus.CONFIRMED);
                fc.addConfirmed(id);
            } else {
                b = new Booking(id, userId, classId, BookingStatus.WAITLISTED);
                fc.addWaitlisted(id);
            }
            bookings.save(b);
        }
    }
    fire(b.getStatus().name(), b);                // after the locks: never call alien code while holding one
    return b;
}

(This is the method exactly as it is in the repo.) Note the shape: b is declared before the locks, assigned inside them, and the listeners are called only after both synchronized blocks close. Rules for this room:

  • Constructor injection. Every dependency arrives through the constructor. No new InMemoryRepository() inside a service, no static singletons. Tests can then build a service in one line.
  • Split by noun when a service passes ~150 lines. UserService, ClassService, BookingService, not one FlipFitService with 25 methods (the "SRP not followed" rejection).
  • Services may call services (booking uses user and class services) but never in a cycle.
  • Never call listener code while holding a lock. A listener is foreign code: if it calls back into the service it can deadlock on the lock you hold, and if it blocks (sending an SMS) every other booking waits. Collect the event under the lock, deliver it after. It is the same rule as never calling a blocking notifier chain with a spinlock held.
  • Return objects, not strings. Formatting is the driver's job; tests then assert on fields, not on text.
