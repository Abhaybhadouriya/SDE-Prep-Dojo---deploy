Entities and enums: data with a few rules of their own

An entity is a thing with an identity that lives over time: a user, a class, a booking. It holds its fields and the rules that only need its own fields. "A class never has more confirmed seats than its capacity" is the class's rule, so it lives in FitnessClass.addConfirmed(), not in the service.

public final class Booking implements Entity {
    private final String id, userId, classId;
    private BookingStatus status;
    // constructor and getters ...

    /** The only legal moves: WAITLISTED to CONFIRMED, and anything active to CANCELLED. */
    public void promote() {
        if (status != BookingStatus.WAITLISTED) throw new IllegalStateException(id + " is " + status);
        status = BookingStatus.CONFIRMED;
    }
    public void cancel() {
        if (status == BookingStatus.CANCELLED) throw new IllegalStateException(id + " already cancelled");
        status = BookingStatus.CANCELLED;
    }
}
@dataclass
class Booking:
    id: str
    user_id: str
    class_id: str
    status: BookingStatus

    @property
    def active(self) -> bool:
        return self.status is not BookingStatus.CANCELLED

    def promote(self) -> None:
        if self.status is not BookingStatus.WAITLISTED:
            raise RuntimeError(f"{self.id} is {self.status.value}")
        self.status = BookingStatus.CONFIRMED

Reading the syntax. @dataclass writes the boring parts of a Python class for you (the constructor that copies each listed field, equality and a printable form), so the class body is just the field list: a struct declaration. @property turns a method into something read like a field: b.active calls the function, like a C accessor macro that looks like a member read.

  • No setters for everything. Expose the moves that are legal (promote, cancel) instead of setStatus(). That is encapsulation in one line.
  • Ids are strings or longs, and references are by id. Booking stores userId, not a User object. It keeps the graph simple and makes "swap to a database" honest.
  • Enums for closed sets (status, vehicle type, tier). If the problem says a set will grow with behaviour attached (new payment modes, new eviction policies), that is an interface plus classes, not an enum.
  • One class per concept, not per instance. Four registers are four Register objects in a map, never RegisterA..RegisterD (the CRED rejection above).

From your world

An entity is a struct plus the small inline helpers in its header that only touch its own fields, like skb_put() checking tailroom. The state check in promote() is the same as a protocol control block refusing an illegal transition: a TCP socket in TCP_CLOSE cannot be "promoted" to TCP_ESTABLISHED without going through the handshake states.
