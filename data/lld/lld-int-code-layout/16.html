Evaluation-call questions about your layout

These are the questions reviewers ask about structure. Filter by level or company. Report links show where a question was seen.

Walk me through how your code is organised.

Reported as the opening of PhonePe's review call (2023-06-23) and Flipkart's evaluation (2025-04-26). Use the five-beat pitch above: layers, seams, error handling, concurrency, next steps.

How to answer

Scroll the folder tree while you talk, top to bottom. Do not open method bodies until asked. Stop at 60 seconds and let them choose where to dig.

Likely follow-ups
  • Show me where requirement 3 is handled. (open the one service method that owns it and trace it from the driver line that calls it; if you cannot point to one place, the layering is wrong)
  • Which class would change if the limit rule changed? (only the BookingLimitPolicy implementation, or a new one passed in from Main; the service does not change)
How would you move this from in-memory to a real database?

"Services depend on Repository<T>, not on a map. I would write JdbcBookingRepository (or a JPA one) implementing the same interface and change the constructor call in Main. The in-memory version stays for tests." Then add the honest parts: transactions (book must update the class and insert the booking atomically), the per-object synchronized locks no longer work across two app servers, so the seat check moves to the database (a row lock, or a conditional update such as UPDATE ... SET booked = booked + 1 WHERE booked < capacity).

How to answer

One sentence for the swap, then one for what does not carry over (locking and transactions). The second sentence is what separates SDE-2 answers.

Likely follow-ups
  • Which tables and keys? (users, classes, bookings with unique (user, class) for active rows)
  • Optimistic or pessimistic locking for the seat? (pessimistic (a row lock, SELECT ... FOR UPDATE) when the last seat is hot and conflicts are common; optimistic (a version column, retry on conflict) when conflicts are rare)
A new tier PREMIUM with a limit of 8 arrives. What changes?

Add PREMIUM to the Tier enum and one entry in the map Main passes to TierLimitPolicy: Map.of(NORMAL, 2, VIP, 5, PREMIUM, 8). The constructor takes a map, not one argument per tier, so its signature and its call sites do not change, and it checks that every Tier has a limit, so a forgotten entry fails at start-up instead of as a null at booking time. No service changes. If the new rule is not a number per tier (for example "unlimited on weekdays"), write a new BookingLimitPolicy class and pass it in Main; still no service change. That is the open/closed principle in practice.

How to answer

Name the exact files that change, and the file that does not (BookingService). Reviewers test "extensible" with exactly this kind of change.

Likely follow-ups
  • What if limits must change at runtime without a restart? (read them from a config source the policy looks up on each call, or swap an immutable limits map in an AtomicReference, the way a sysctl changes a value under a running kernel)
  • Would you still keep Tier as an enum? (yes while the tier set is fixed in code; once product adds tiers without a deploy, make Tier data (a table row with its limit))
Why unchecked exceptions, and why catch them only in the driver?

Business errors (unknown id, duplicate, limit) cannot be fixed by the code in between, only reported to the user. Unchecked exceptions keep the service signatures clean, and one catch in the driver turns them into an error line while the program keeps running. Programming bugs (an entity's IllegalStateException) are not caught as business errors, so they stay loud in testing.

How to answer

Say the rule ("catch where you can do something about it") and show the driver's single catch.

Likely follow-ups
  • Would an HTTP layer map these to status codes? (NotFound to 404, Validation to 400, Limit to 409 or 429)
Is your code thread-safe? Where are the locks and why there?

Thread safety was a stated requirement in the Flipkart Minutes problem (2026-02-18) and a next-day review topic at PhonePe (2025-09-23). Walk the table in where the locks go: concurrent map for storage, per-class lock for the seat check-then-act, per-user lock for the limit, atomic id counter, fixed lock order user-then-class. Then cover the read side, which SDE-2 interviewers ask next ("is your read path safe?"): a read of a mutable field either takes the writer's lock or the field is volatile or immutable (Booking.status is volatile), and list views are copies, so a reader sees a snapshot. See the locks lesson.

How to answer

Name the invariant first ("never more confirmed than capacity"), then the lock that protects it, then the test that shows it.

Likely follow-ups
  • Why not one global lock? (correct but serialises every booking)
  • Could cancel deadlock with book? (no: cancel takes only the class lock, book takes user then class)
Why is there one Repository class and not one per entity?

The three stores do the same three things, so a generic InMemoryRepository<T extends Entity> avoids copy-paste. When one entity needs its own query (bookings by user), I add a BookingRepository interface that extends Repository<Booking> with findByUser, and keep the others generic.

How to answer

Show that you know both options and choose by need, not by habit.

Likely follow-ups
  • What is the difference between a repository and a DAO? (see the Repository page)
How did you test this, and how would you test it with more time?

Now: a scripted demo in Main covering every P0 plus five failure cases, and a test class with four scenarios including the concurrent last-seat race. With more time: JUnit 5 / pytest with one test per rule, a fake BookingLimitPolicy to test the service without tiers, and a property-style test that random book/cancel sequences never exceed capacity. CRED's machine-coding round lists "sufficient unit test cases" as a grading point (2023-08-31).

How to answer

Point out that constructor injection is what made the tests easy: each test builds a fresh service in one line.

Likely follow-ups
  • How do you make the concurrency test reliable? (start latch, many threads, assert the invariant, not timing)
Notifications must now be async and go to SMS and email. Where does that go?

The service already fires events to BookingListeners. Add SmsListener and EmailListener, and make delivery async by wrapping them in a listener that hands the event to an ExecutorService (or a BlockingQueue drained by a worker). The booking path never waits for SMS. This matches the Flipkart evaluator's "which pattern for an async task" question (2025-04-26): Observer for fan-out, producer-consumer for async delivery.

How to answer

Two patterns, two jobs: Observer decouples who listens; the queue decouples when they run.

Likely follow-ups
  • What if the SMS provider is down? (retry with backoff, dead-letter list)
  • Should a listener failure fail the booking? (no: listeners run after the locks are released, each inside a try/catch that logs, so the committed booking stands)
Your BookingService is 300 lines. Is that a problem?

Probably. Check if it is doing several jobs: validation, pricing, waitlist handling, notifications. Split by responsibility: a WaitlistManager or a pricing strategy can come out cleanly. A Flipkart rejection named exactly this: single responsibility and separation of concerns not followed (2023-04-01).

How to answer

Do not defend a god class. Say how you would split it and which method moves first.

Likely follow-ups
  • How do you decide what is "one responsibility"? (one reason to change; see SRP)
Why not use Spring (or a DI framework) for the wiring?

The rounds ban external services and usually want a standalone app; a framework costs setup time and hides the wiring the reviewer wants to see. Manual constructor injection in Main is the same idea in 10 lines. If the reviewer asks, the mapping is direct: each new in wire() would be a @Component or @Bean, and constructor parameters would be injected.

How to answer

Show you know DI is the principle and the framework is just one tool for it.

Likely follow-ups
  • Singleton beans vs your objects: what is the difference? (one per container vs one created in Main; both are "one", neither is a static global)
You ran out of time on a bonus feature. What do you hand in?

Code that compiles and a demo that runs every finished feature. Leave the unfinished part as a clearly named interface or a commented stub ("the auto-cancel scheduler would implement Runnable here and run on a ScheduledExecutorService"). The PhonePe report advises exactly this kind of comment, and stresses compiling as you go (2023-06-23).

How to answer

Working beats complete. Say what is missing before the reviewer finds it.

Likely follow-ups
  • Code it now in five minutes: where does it go? (say the file first, add one method or one Strategy class, wire it in Main, add one driver line, compile and run)
