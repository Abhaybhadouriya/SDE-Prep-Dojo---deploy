Repository: the store-room keeper

The Repository pattern hides "where are things kept" behind a collection-like interface. In a machine-coding round you will never write a database, but you will always be asked "how would you add one?". With a repository interface the answer is one sentence: "write JdbcBookingRepository implements Repository<Booking> and change one line in Main."

Two pieces of new syntax first. Repository<T> is a generic: one interface written once for any entity type T (users, classes, bookings). It is like a C macro or a void *-based container, except the compiler checks that a Repository<Booking> only ever holds bookings, so no casts. Optional<T> is a return value that is either "one T" or "empty"; it forces the caller to handle not-found, where C code would return NULL and hope the caller checks. Python spells the same ideas Protocol[T] / Generic[T] and Optional[T] (a type hint only; the runtime value is None).

Three more. <T extends Entity> limits the template parameter to types that have getId(), so the repository can key its map by id. A Python Protocol is an interface checked by shape: any class that has those methods fits, without inheriting from anything, like filling in an ops table by duck typing. InMemoryRepository[User]() just creates the generic class with the type filled in; at runtime it is the same class.

public interface Repository<T> {
    T save(T item);
    Optional<T> findById(String id);
    List<T> findAll();
}

public class InMemoryRepository<T extends Entity> implements Repository<T> {
    private final Map<String, T> items = new ConcurrentHashMap<>();
    public T save(T item) { items.put(item.getId(), item); return item; }
    public Optional<T> findById(String id) { return Optional.ofNullable(items.get(id)); }
    public List<T> findAll() { return new ArrayList<>(items.values()); }
}
class Repository(Protocol[T]):
    def save(self, item: T) -> T: ...
    def find_by_id(self, key: str) -> Optional[T]: ...
    def find_all(self) -> list[T]: ...

class InMemoryRepository(Generic[T]):
    def __init__(self) -> None:
        self._items: dict[str, T] = {}
        self._lock = threading.Lock()

    def save(self, item: T) -> T:
        with self._lock:
            self._items[item.id] = item
        return item
  • One generic class instead of three copy-pasted maps. Add a typed sub-interface only when you need a query like findByUser(userId); that is where an index map goes.
  • No rules in the repository. "Is the class full?" is not a storage question.
  • Return Optional (Java) or None (Python), and let the service turn "missing" into NotFoundException, so the error message knows what was missing.

From your world

The kernel's answer to "one container for every type" is a struct list_head embedded in your struct, plus container_of() to get from the node back to the object. That works for any type, but nothing stops list_entry(pos, struct wrong_type, list). Repository<T> is the same "write the container once" idea with the type check moved to compile time. Optional plays the role of the NULL / ERR_PTR() convention, except the compiler makes the caller unwrap it.

Our activeFor(userId) scans findAll(). That is fine for a demo of a few hundred rows and keeps the code short. Say so out loud in the review, and say the fix: a Map<userId, Set<bookingId>> index kept in a BookingRepository. Naming the shortcut yourself scores better than having it found.
