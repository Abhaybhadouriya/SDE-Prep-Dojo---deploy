Scenario drills

Scenario: the reviewer adds a feature live

In the evaluation call: "Classes can now be recurring every Monday. Show me what you would change."
Weak answer: starts editing BookingService.book() with an if (recurring) branch and a loop that creates bookings.
Strong answer: "Recurrence is about creating classes, not booking them. I would add a Schedule (or RecurrenceRule) to the model and a ClassService.addRecurring() that creates one FitnessClass per date. Booking stays untouched because a recurring class is still a list of ordinary classes."
Follow-up: "Book all Mondays in one call?" A new service method that calls book() per class and rolls back on failure.

Scenario: one file, 15 minutes left, it does not compile

On CodeSignal, with 40 compile errors after a big paste.
Weak answer: keeps adding features, hoping to fix it all at the end.
Strong answer: comment out the newest service method, get back to the last compiling state, run the demo, then add the method back in small pieces. This is why the plan says compile every ten minutes.
Lesson: the skeleton must compile in minute 10, before any logic exists.

Scenario: "Why is this a Strategy? It is one class."

The reviewer challenges BookingLimitPolicy with only one implementation.
Weak answer: "Because patterns make code extensible."
Strong answer: "The problem statement said limits differ by tier and may change, so I put the one decision that changes behind an interface. It cost one small file. I did not add interfaces for things the problem did not say would vary, like ids or the waitlist order."
Follow-up: "What else would you have made pluggable?" Name one candidate and say why you did not yet.
