Common mistakes on class diagrams

Weak diagram
  • One box per object: Level1, Level2, RegisterA
  • Every getter and setter listed; real behaviour missing
  • No types on attributes; no multiplicities
  • Inheritance for things that differ only in data (RedCar extends Car)
  • Arrows everywhere, all with the same head
  • No interface anywhere, so no visible extension point
  • 20 minutes of drawing, no code
Strong diagram
  • One box per concept; instances are objects or enum values
  • Meaningful operations: park, canFit, cancel
  • Types and the important multiplicities (0..1, 1..*)
  • Subclasses only where behaviour differs; enums for kinds
  • Correct line ends: diamonds for ownership, triangles for is-a/implements
  • Interfaces exactly where requirements will change
  • 8-10 minutes, then code

Also: show the orchestrator. The class that receives the use cases (ParkingLot, BookingService) is the first thing an interviewer reads, and its public operations are your API (see API & Interface Design). For turning requirements into the right set of boxes, see From Use Cases to Classes.
