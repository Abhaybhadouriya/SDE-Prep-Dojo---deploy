Scenario drills

Scenario: "Explain OOP to a five-year-old" (Mastercard screening)

First question of the round, reported in LeetCode Discuss, 2025-10-25. You have 60 seconds.
"OOP is a programming paradigm based on objects which contain data and code, with four pillars: encapsulation, abstraction, inheritance and polymorphism." (Correct, but it ignores the question and sounds memorised.)
"Think of a toy shop. Every toy is made from a mould: that's a class, and each toy is an object. A toy car knows its colour and can drive; you press its button, you don't touch its motor: that's hiding the inside. A race car is a special car: that's inheritance. And when you say 'go!' to a car, a plane and a boat, each moves its own way: that's polymorphism. Programs built like that are easier to change." Then offer the grown-up version.
Likely follow-ups
  • Now the four pillars with code.
  • Debug this Singleton.

Scenario: "Why this class hierarchy?" (Cleartrip evaluation)

You built a food-ordering system with User, Restaurant, MenuItem, Order, OrderStatus, Catalog and one FoodOrderingService (LeetCode Discuss, 2026-07-21). The interviewer asks why this hierarchy, whether a class could be split, and where you would use interfaces.
"I just followed the requirements. The service handles everything so it's simple." (No reasons, and admits a god class.)
"Entities are nouns from the problem; none inherit from each other because none is a kind of another. The service is the one class I'd split: ordering, inventory and catalog change for different reasons, so OrderService, InventoryService and CatalogService. Interfaces go where variants appear: PaymentMethod, PricingRule, and repositories so the in-memory maps can become a DB. Inventory updates need a per-item lock or atomic decrement, which I'd show next."
Likely follow-ups
  • Is HashMap thread-safe? What would you use instead?

Scenario: "Create an always-sorted list class" (Walmart Java + LLD)

Reported in LeetCode Discuss, 2024-10-25, next to "why inheritance if composition works?".
class SortedList extends ArrayList with add() overridden to sort after each insert. Callers can still call add(index, x), set() or addAll() and break the order; and sorting on every insert costs O(n log n).
Wrap a private ArrayList (composition), expose only add, get, size, iteration; insert at the binary-search position (O(log n) search, O(n) shift); make the element type Comparable or accept a Comparator. Mention TreeMap/PriorityQueue as alternatives when duplicates or index access are not needed.
Likely follow-ups
  • Make it thread-safe.
  • Support a custom Comparator.

Scenario: "Make Vehicle abstract" in the middle of the round (parking lot)

You are 35 minutes into a parking-lot round of the kind Uber asks (LeetCode Discuss, 2026-04-13). Your Vehicle is a concrete class with a VehicleType enum, and pricing does switch (vehicle.type()). The interviewer says: "Electric cars need a charging spot and a different fee. Make Vehicle abstract."
Make Vehicle abstract, add Car, Bike, Truck, ElectricCar extends Car, and add one more case to every switch. The code compiles, but now behaviour lives in two places (subclasses and switches), and new Vehicle(...) calls in the driver all break at once.
"First I check what varies. Spot size and fee are behaviour that differs per kind, so they move into the type: abstract class Vehicle with abstract SpotSize spotSize() and abstract Money hourlyRate(), and each subclass answers for itself. The switch statements go away. Creation goes through one VehicleFactory.of(type, plate), so only that method changes in the driver. If the rates came from config rather than code, I would keep the enum with data instead of subclasses, because data does not need polymorphism." Then make the change, re-run the driver, and show the old flows still pass.
Likely follow-ups
  • Why not an interface instead of an abstract class here?
  • Where does the charging-spot rule live: Vehicle, Spot or the allocator?

Scenario: "Why is this class final?" (evaluation call)

In the code walkthrough after a Flipkart-style machine-coding round (LeetCode Discuss, 2026-06-13), the reviewer points at public final class OrderService and record Money and asks: "Why final? What if someone needs to extend it?"
"My IDE suggested it." Or: "I can remove it if you like." (No reason, and it gives away a good decision.)
"Final means this class was not designed for inheritance, so nobody can override half of it and break its rules (the fragile base class problem). The extension points are explicit: OrderService takes a PricingPolicy and a PaymentGateway interface in its constructor, so new behaviour is a new implementation, not a subclass. Tests do not need to subclass it either; they pass fakes of those interfaces. Money is a record, which is final by definition, because a value object must stay immutable and equal by value." Mention that this is the Effective Java rule: design and document for inheritance, or prohibit it.
Likely follow-ups
  • Does final help performance? (Barely; the JIT already inlines monomorphic calls.)
  • How do mocking libraries handle final classes?
