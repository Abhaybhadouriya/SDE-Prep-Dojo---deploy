Java specifics: equality, immutability, Singleton

Why must equals and hashCode be overridden together?

Hash collections pick the bucket from hashCode() and only then call equals(). If equal objects have different hash codes, lookups miss and sets accept duplicates. Base both on the same fields; for entities use the id; never mutate a field used in hashCode while the object is a key. Records generate both. The HashMap-internals follow-up (buckets, collisions, treeification) often comes in the same breath.

Reported: Walmart (LeetCode Discuss, 2025-09-21).

How do you design an immutable class?

Final class; private final fields; no setters; defensive copies of mutable inputs (List.copyOf); never return internal mutable objects; return new objects from "change" methods. Benefits: thread safety without locks, safe map keys, invariants checked once. A record is a shortcut for the boilerplate but is only shallowly immutable.

How to answer

final vs finally vs finalize.

final: a variable cannot be reassigned, a method cannot be overridden, a class cannot be extended. finally: a block that runs after try/catch whatever happens (cleanup). finalize(): an old GC hook, deprecated for removal since Java 18; use try-with-resources or Cleaner.

How to answer

Three one-liners. Mention that finalize is deprecated; that shows you are current.

Shallow copy vs deep copy?

A shallow copy copies the fields, so referenced objects are shared; a deep copy copies the referenced objects too. Object.clone() is shallow by default. Our demo: after adding to the original's list, the shallow copy sees the change, the deep copy does not. Prefer copy constructors or factory methods over clone().

How to answer

Write a thread-safe Singleton. How else can it break?
public final class Config implements java.io.Serializable {
    private static final long serialVersionUID = 1L;
    private static volatile Config instance;          // volatile: no half-built object seen by other threads
    private Config() {
        if (instance != null) throw new IllegalStateException("use Config.get()");  // partial reflection guard
    }
    public static Config get() {
        Config c = instance;
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
    private Object readResolve() { return get(); }     // deserialization returns the one instance
}
// simplest complete answer: enum Config { INSTANCE; }

Ways it breaks: no volatile in double-checked locking; reflection calling the private constructor; deserialization; cloning; several class loaders. readResolve only matters if the class is Serializable (without that, there is nothing to deserialize and the method is dead code), so the class above implements it and pins a serialVersionUID. The constructor check is only a partial reflection defence: it stops a second instance after the first exists, not a reflective call that wins the race to be first. An enum singleton is the complete answer: the JVM guarantees one instance per constant, serialization returns that constant, and reflection cannot construct an enum. The class, a serialize-and-deserialize identity check and a reflection attempt are case 8 in OopPuzzles.java below.

Reported: Walmart (LeetCode Discuss, 2024-10-25); Goldman Sachs (LeetCode Discuss, 2025-05-08); Mastercard (LeetCode Discuss, 2025-10-25).

How to answer

Write the holder idiom or the enum first (shortest correct answer); show double-checked locking only if asked, and explain why volatile is needed.

== vs equals() for Strings?

== compares references; equals() compares characters. String literals are interned, so two equal literals are often the same object and == happens to be true, but new String("dojo") is a different object. Always use equals().
