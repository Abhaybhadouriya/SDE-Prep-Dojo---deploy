Use an interface for a capability many unrelated classes may have, and as the type your code depends on (DIP). Use an abstract class when subclasses share state and a fixed algorithm skeleton (Template Method), often implementing an interface.

In your design, where would you use interfaces?

Wherever there is (or will soon be) more than one variant, or an external dependency: pricing and discount rules, payment methods, notification channels, storage (repository), matching or allocation strategies, clocks and id generators (so tests can fake them). Not for plain data entities like User or MenuItem.

An interface with 3 abstract methods has 2 production implementations. A new implementation needs only 2 methods. How do you handle it?

That is an Interface Segregation smell. Best: split into role interfaces (the old classes implement both, the new one only the role it has). Quick and safe: a default method with a sensible no-op only if "no-op" is truly correct behaviour. Wrong: making the new class throw UnsupportedOperationException, which breaks Liskov for every caller.

Reported: Walmart (LeetCode Discuss, 2024-11-28).

What is a marker interface and a functional interface?

A marker interface has no methods; it tags a class for a framework (Serializable, Cloneable). Annotations mostly replace them today. A functional interface has exactly one abstract method (Runnable, Comparator), so a lambda can implement it.
