Build a fixed pool in 30 lines

Interviewers often start with "write me a simple thread pool". This is a small answer that holds up to the usual follow-ups (it is lld-code/lld-conc-thread-pool/FixedPool.java; FixedPoolTest.java races submit against shutdown and checks that every accepted task ran). Say out loud that it reuses the producer-consumer idea: submit is the producer, the workers are the consumers.

import java.util.*;
import java.util.concurrent.*;

public final class FixedPool {
    private final BlockingQueue<Runnable> queue;
    private final List<Thread> workers = new ArrayList<>();
    private final Object lock = new Object();          // guards "check shutdown + enqueue"
    private volatile boolean shutdown;                 // read by workers without the lock

    public FixedPool(int threads, int capacity) {
        queue = new ArrayBlockingQueue<>(capacity);     // bounded: memory cannot run away
        for (int i = 0; i < threads; i++) {
            Thread t = new Thread(this::loop, "pool-" + i);
            workers.add(t);
            t.start();
        }
    }
    private void loop() {
        while (!shutdown || !queue.isEmpty()) {         // drain the queue before exiting
            try {
                Runnable r = queue.poll(100, TimeUnit.MILLISECONDS);
                if (r != null) r.run();                 // run OUTSIDE any lock
            } catch (InterruptedException e) { return; }
              catch (RuntimeException e) { e.printStackTrace(); }  // one bad task must not kill the worker
        }
    }
    public void submit(Runnable r) {
        synchronized (lock) {                           // check-then-act as ONE step
            if (shutdown) throw new RejectedExecutionException("shut down");
            if (!queue.offer(r)) throw new RejectedExecutionException("queue full");
        }
    }
    public void shutdown() { synchronized (lock) { shutdown = true; } }
    public void awaitTermination() throws InterruptedException { for (Thread t : workers) t.join(); }
}

Six decisions in that code are what the interviewer is really grading:

  • Bounded queue: offer() fails fast.
  • Run tasks outside any lock, or user code can deadlock the pool.
  • Catch task exceptions, or the pool slowly shrinks to zero workers.
  • volatile shutdown flag. Without it a worker may never see the change (see visibility).
  • Check and enqueue under one lock. An earlier draft of this class checked the volatile flag and then called offer() as two steps. If shutdown() ran between them, every worker could see "shut down and empty" and exit, and then the offer succeeded: the task was accepted and never ran. That is check-then-act again. Setting the flag under the same lock closes the gap: once a worker reads shutdown == true, every accepted task is already in the queue. The window is tiny (our stress test did not hit it even on the unlocked version), which is exactly why interviewers ask about it instead of testing for it.
  • Drain, then exit. "Graceful shutdown" means finish what was accepted. A poison pill (one "stop" task per worker) is the other common answer.

This loop wakes every 100 ms when idle; the real ThreadPoolExecutor does not. Idle workers block in take(), and shutdown() interrupts only the idle ones. It knows which ones are idle because each worker holds a small lock while it runs a task, so a successful tryLock() means "idle". Our full version does that too.
