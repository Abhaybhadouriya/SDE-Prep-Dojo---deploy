The problem: one thread per request

The first version of most servers looks like this. It works in a demo and falls over in production.

void onRequest(Request req) {
    new Thread(() -> handle(req)).start();   // a new OS thread for every request
}
private final ExecutorService pool = new ThreadPoolExecutor(
        8, 16, 30, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(500),                 // bounded rail of tickets
        r -> new Thread(r, "req-worker"),
        new ThreadPoolExecutor.CallerRunsPolicy());    // full? slow the caller down

void onRequest(Request req) {
    pool.execute(() -> handle(req));                   // reuse one of at most 16 threads
}

What goes wrong with the "before" version:

  • Creation cost on every request. A Java platform thread is a real OS thread: a kernel task, a stack (the -Xss default is 1 MB of reserved stack on 64-bit Linux), and a trip through the scheduler.
  • No upper limit. A traffic spike creates thousands of threads. Memory runs out, or the threads spend their time context-switching instead of working.
  • No control. You cannot ask "how many are running?", cannot wait for all of them to finish, cannot cancel one, and an exception just prints a stack trace and is lost.

A thread pool fixes all three: it creates a bounded number of threads once and reuses them, it queues work when they are busy, and it gives you a handle (a Future) for each task.
