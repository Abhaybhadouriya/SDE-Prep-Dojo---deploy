In the interview: "Design a ThreadPoolExecutor"

A 2026 Walmart SDE-3 report (LeetCode post) asked for exactly this: a class diagram, worker lifecycle, the internal queue, task flow, synchronisation and rejection policies. A custom thread pool write-up covers the same ground. Drive it in this order:

  1. Clarify (2 min) Fixed or elastic size? Results needed (Futures)? Bounded queue? What on overload? Graceful vs immediate shutdown? Priorities or scheduling?
  2. Classes (5 min) Draw the four-part diagram above: Executor, ThreadPool, Worker, BlockingQueue, RejectionPolicy (Strategy), ThreadFactory (Factory).
  3. The submit algorithm (5 min) core, then queue, then max, then reject. Mention the unbounded-queue trap.
  4. Code (20 min) execute, the worker loop, shutdown. Say where every lock is and why the task runs outside it.
  5. Hard parts (10 min) Exception in a task, keep-alive shrink without going below core, interrupting only idle workers, awaitTermination with a Condition, Futures via FutureTask.
  6. Extensions Priorities, metrics (queue depth, rejections), per-tenant pools, scheduling.

Strong phrases: "A pool is producer-consumer plus lifecycle." "I keep the queue bounded so overload becomes a decision, not an OutOfMemoryError." "Rejection is a Strategy and thread creation is a Factory." "The task runs outside every lock, so user code cannot deadlock the pool."
