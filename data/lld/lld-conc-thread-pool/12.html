Interview Q&A

Walk me through what happens when a task is submitted to a ThreadPoolExecutor.

If fewer than core threads are running, start a new thread with this task as its first task. Otherwise offer it to the queue. If that succeeds, re-check that the pool is still running (and start a thread if there are none). If the queue is full, try to start a thread above core, up to max. If that fails too, call the rejection handler. Extra threads exit after keepAlive of idleness.

How to answer

Draw the four boxes (core, queue, max, reject) and point to them in order. Then mention that an unbounded queue means max is never used.

Likely follow-ups
  • Why does the JDK queue before growing? (Prefer few threads; grow only under real overload.)
  • How would you make it grow before queueing? (A custom queue whose offer returns false while below max, as Tomcat's executor does.)
Runnable vs Callable, execute vs submit: what happens to an exception in each?

Runnable.run() returns nothing and cannot throw checked exceptions. Callable.call() returns a value and may throw. With execute, an exception goes to the thread's uncaught-exception handler, and the worker dies and is replaced. With submit, it is captured in the Future and only appears when someone calls get() (wrapped in ExecutionException). If nobody calls get(), it is lost silently.

How to answer

Give the two-by-two answer, then the fix: always consume Futures, or log in afterExecute or a wrapper.

Likely follow-ups
  • How does submit work internally? (Wraps the task in a FutureTask, which is a Runnable, and calls execute.)
Future vs CompletableFuture? Which thread runs thenApply?

A Future can only be polled or blocked on. A CompletableFuture can be completed by anyone and composed: thenApply, thenCompose, thenCombine, allOf, exceptionally, timeouts. A non-async thenApply runs on the thread that completes the previous stage, or on the caller if that stage is already done. thenApplyAsync runs on the given executor, or the common pool if none is given.

How to answer

Contrast block vs compose, show a two-call fan-out with thenCombine, and warn about blocking I/O on the common pool.

Likely follow-ups
  • thenApply vs thenCompose? (map vs flatMap.)
  • How do you time out a call? (orTimeout or completeOnTimeout, Java 9+.)
Your service's pool has 50 threads, all stuck, and CPU is idle. What happened?

Likely suspects: thread-starvation deadlock (tasks waiting on subtasks queued behind them in the same pool), every thread blocked on a slow downstream with no timeout, or waiting for a resource from a smaller pool (DB connections). Take a thread dump (jstack or jcmd Thread.print) and look at what each named thread waits on. Fixes: timeouts on every remote call, separate pools per dependency, never block on a Future from the same pool, and size the DB pool and the thread pool together.

How to answer

Diagnose first (dump, names), then the three causes, then the fixes.

Likely follow-ups
  • What is a bulkhead? (Separate, bounded pools so one dependency cannot use every thread.)
How does shutdown() avoid interrupting a worker that is in the middle of a task?

Each worker holds its own non-reentrant lock while it runs a task. shutdown() walks the worker set and calls tryLock() on each. Success means the worker is idle (blocked in take()), so it interrupts it and unlocks. Busy workers are left alone, finish their task, then see SHUTDOWN plus an empty queue and exit. shutdownNow() interrupts everyone.

How to answer

Explain the idle test, then the check order in the worker loop.

Likely follow-ups
  • Why does the worker clear the interrupt flag before running a task? (A stray idle-interrupt must not hit the next task unless the pool is stopping.)
