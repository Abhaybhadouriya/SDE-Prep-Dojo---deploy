Scheduled, fork-join and virtual-thread executors

  • ScheduledThreadPoolExecutor runs delayed and periodic tasks from a delay queue (a heap ordered by time). scheduleAtFixedRate aims for a fixed start-to-start period. scheduleWithFixedDelay waits a fixed gap after each run ends. Runs of one periodic task never overlap. If a run throws, every later run is silently cancelled. Our demo shows it: ticks stop at 3. Wrap the body in try/catch. See also the Distributed Job Scheduler.
  • ForkJoinPool gives each worker its own deque; idle workers steal from the far end of a busy worker's deque. Built for divide-and-conquer and parallel streams, not blocking I/O.
  • Virtual threads (final in Java 21): Executors.newVirtualThreadPerTaskExecutor() starts a cheap, JVM-scheduled thread for every task. When a virtual thread blocks on I/O, it is unmounted from its carrier OS thread. Our demo ran 10,000 tasks that each sleep 100 ms in about 200 ms. Do not pool virtual threads. To limit load on a downstream service, use a Semaphore. In Java 21, blocking inside synchronized pins the carrier thread; JDK 24 removed that limit (JEP 491).

Pitfalls that show up in reviews

  • Thread-starvation deadlock. A task in a pool of size n submits a subtask to the same pool and waits for it with get(). With n such parents running, every thread waits and no thread is left to run the children. Fix: separate pools, CompletableFuture composition, or ForkJoin.
  • ThreadLocal leaks. Pool threads live forever, so a ThreadLocal set by one task (user id, transaction) is still there for the next task. Clear it in finally.

From your world

Work stealing is how the Linux scheduler balances run queues: each CPU has its own run queue, and an idle CPU pulls tasks from a busy one. The kernel's concurrency-managed workqueue (cmwq) solves the thread-starvation problem in its own way: per-CPU worker pools notice when a running work item goes to sleep and start another kworker, so a blocked item does not stall the rest.
