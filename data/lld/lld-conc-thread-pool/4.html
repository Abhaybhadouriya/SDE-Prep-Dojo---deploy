ThreadPoolExecutor: the decision every submit makes

The constructor takes seven parameters (keep-alive time and its unit count as two). Know them cold:

ParameterMeaningTypical choice
corePoolSizeThreads kept alive even when idleCPU-bound: number of cores
maximumPoolSizeUpper limit, used only when the queue is full2 to 4 times core for I/O work
keepAliveTime + unitHow long a thread above core may sit idle before it exits30-60 s
workQueueWhere waiting tasks sitArrayBlockingQueue(n): bounded
threadFactoryBuilds threads: name, daemon flag, uncaught-exception handlerAlways name them, for thread dumps
handlerThe rejection policyCallerRunsPolicy or AbortPolicy

The order of the checks inside execute() surprises most people. Step through it with core=2, max=4, queue capacity=2 and eight slow tasks:

  1. Fewer than corePoolSize threads exist, so each submit starts a new core thread and hands it the task directly, even if another core thread is idle.
  2. Core is full. The next tasks go into the queue. No new thread is created yet.
  3. The queue is full. Only now does the pool add threads above core, up to maximumPoolSize. Tasks 5 and 6 go straight to the new threads.
  4. Queue full and max reached: the pool is saturated, and tasks 7 and 8 go to the rejection policy.
  5. A side effect of this order: tasks 5 and 6 run before 3 and 4, which are still queued. Never assume submit order equals run order.
  6. Threads above core that stay idle for keepAliveTime exit. Call allowCoreThreadTimeOut(true) to let core threads time out too.

Our MiniThreadPool printed exactly this: pool size 1, 2, 2, 2, 3, 4 after submits 1-6, then 7 and 8 rejected, and back to 2 threads after keep-alive.

The unbounded-queue trap. With an unbounded LinkedBlockingQueue the queue is never full, so step 3 never happens and maximumPoolSize is ignored. Executors.newFixedThreadPool(n) is built this way: n threads and an unbounded queue, so a slow downstream lets the queue grow until the heap runs out. Executors.newCachedThreadPool() is the opposite trap: core 0, max Integer.MAX_VALUE, and a SynchronousQueue (a queue of size zero that hands each task straight to a thread), so a spike creates unlimited threads. In production code, call the constructor and choose the numbers yourself.
