The problem: new inside business code

class OrderService {
    private final CardGateway gateway = new CardGateway("live-merchant-id");   // concrete, hard-wired
    private final MySqlOrders orders = new MySqlOrders("jdbc:mysql://prod/...");
    private final EmailNotifier notifier = new EmailNotifier(new SmtpClient("smtp.corp"));

    String placeOrder(String id, String customer, long paise) {
        boolean lateNight = LocalTime.now().getHour() >= 23;   // hidden dependency: the system clock
        long total = lateNight ? paise + 2_000 : paise;
        String status = gateway.charge(id, total) ? "PAID" : "FAILED";
        orders.save(id, status);
        notifier.send(customer, "order " + id + " " + status);
        return status;
    }
}

Looks normal. Now try to live with it:

  • Untestable. A unit test of placeOrder charges a real card, writes to a real database and sends a real email. And you cannot test the late-night fee unless you run the test after 11 pm.
  • Rigid. Switching to UPI or to SMS means editing OrderService, a class whose business rules did not change. That breaks the Open/Closed Principle.
  • Hidden. Nothing in the class's public surface says "I need a database and an SMTP server". You find out when it fails in staging.
  • Configuration leaks into logic. Merchant ids, JDBC URLs and host names sit inside a domain class.
  • Lifecycle chaos. Every service that does new MySqlOrders(...) opens its own pool. Nobody owns the shared objects.
