Interview Q&A

What is the difference between Dependency Injection, Dependency Inversion and Inversion of Control?

Dependency Inversion is a SOLID principle: high-level and low-level modules both depend on abstractions. Inversion of Control is a broad idea: the framework calls your code rather than your code driving everything (callbacks, template methods, event loops). Dependency Injection is a specific technique and one form of IoC: the creation and wiring of a class's dependencies is moved outside the class and they are passed in. DI is the usual way to satisfy DIP; a container is a tool that automates DI.

How to answer

Principle, idea, technique, tool. One example each: an interface, a servlet's doGet, a constructor parameter, Spring.

Likely follow-ups
  • Can you follow DIP without DI? (Yes: a factory or locator can hand out interfaces.)
Constructor injection vs setter vs field injection. Which do you prefer and why?

Constructor injection for required dependencies: fields can be final, the object cannot exist half-initialised, dependencies are visible in the signature, and a plain unit test can call new with fakes. Setter injection for optional dependencies with defaults, or to break a real cycle. Field injection (@Autowired on a private field) hides dependencies, prevents final, needs reflection or a container in tests, and makes it easy to pile up too many dependencies unnoticed. Spring's own reference documentation recommends constructors for mandatory dependencies.

How to answer

Choose constructor, give three reasons, give the one legitimate use of setters, and say why field injection is discouraged.

Likely follow-ups
  • Your constructor has nine parameters. What now? (Split responsibilities; group related parameters into a cohesive object; do not hide them with field injection.)
DI vs Service Locator: both decouple from concrete classes. Why prefer DI?

With a locator the class pulls dependencies from a global registry inside its methods. The dependencies are invisible from outside, missing registrations fail only when that code path runs, every class depends on the locator itself, and tests must mutate global state. With DI dependencies are pushed in, visible in the constructor, checked when the graph is built, and tests just pass fakes. Locators still have a place at the edges: plug-in discovery (ServiceLoader) or legacy code mid-refactor.

How to answer

Push vs pull, then visibility, failure time and testability. Our demo's step 3 failure is the concrete example.

Likely follow-ups
  • Is the Spring ApplicationContext.getBean() a service locator? (Yes, when called from business code; that is why you inject instead.)
How does DI make a class testable? Show it with a time-dependent rule.

If OrderService calls LocalTime.now(), a "late-night fee after 11 pm" test only passes at night. Inject a java.time.Clock instead and call LocalTime.now(clock). In production the composition root passes Clock.systemUTC(); in the test you pass Clock.fixed(Instant.parse("...T23:30:00Z"), UTC) and assert the fee. Same for the payment gateway: inject a fake that records charges and returns approve or decline.

How to answer

Name the hidden dependency (time), inject it, show the fixed-clock test. Then generalise to gateways and repositories.

Likely follow-ups
  • Fakes vs mocks? (A fake is a working lightweight implementation, like an in-memory repository; a mock verifies interactions. Prefer fakes for state, mocks for "was it called".)
What is a composition root, and where would you put it in a machine-coding round?

The single place where the object graph is built: it knows concrete classes, chooses lifetimes, and passes objects into constructors. Everything else knows only interfaces. In a machine-coding round put it in main() or a small AppFactory/Bootstrap class next to the demo driver. Wire repositories (in-memory), strategies and services there, then run the scenarios. This keeps domain classes free of new calls on services and makes the "extend it" follow-up a one-line change in one file.

How to answer

Definition, rule ("only one place calls new on services"), location in your code, benefit for extension.

Likely follow-ups
  • The interviewer adds "support SMS too". What changes? (A new SmsNotifier class and one line in the root.)
Spring: what happens with two beans of the same type, and with a circular dependency?

Two candidates for one injection point make startup fail with an ambiguity error. Resolve it with @Primary on the default, @Qualifier at the injection point, or by injecting List<Notifier> or Map<String, Notifier> to receive all of them. A constructor-injection cycle (A needs B, B needs A) cannot be built, and Spring Boot prohibits circular references by default since 2.6. Setter or field injection or @Lazy can make it start, but the better fix is to extract the shared logic into a third class both depend on, or to decouple with events.

How to answer

Error, three fixes for ambiguity; cycle, why constructor injection exposes it, design fix over framework workaround.

Likely follow-ups
  • Default bean scope? (Singleton per container. Prototype for a new instance per injection.)
  • Why does a prototype bean injected into a singleton behave like a singleton? (It was injected once; use a provider or lookup method.)
What is java.util.ServiceLoader, and is it DI?

It discovers implementations of an interface listed in META-INF/services/<interface> files on the classpath (or provides clauses in module-info.java) and instantiates them lazily with their public no-arg constructors. JDBC drivers and NIO file-system providers use it. It is closer to a service locator for plug-ins than to DI: the caller asks for implementations. Use it in the composition root to find plug-ins, then inject what it found into the classes that need them.

How to answer

What it reads, what it creates, a JDK example, then "locator at the edge, injection inside".

Likely follow-ups
  • How would you design a plug-in system for payment providers? (Interface + ServiceLoader discovery + a registry keyed by provider name injected into checkout.)
Singleton vs injecting a single instance: why do people say "use DI instead of Singleton"?

A GoF Singleton gives "only one" and a global access point. The global access point is the problem: callers grab it from anywhere, so the dependency is hidden and tests cannot substitute it. With DI you create one instance in the composition root and pass it to everyone who needs it. You keep the single instance, lose the global, and tests can build a fresh one. Spring's default singleton scope is exactly this.

How to answer

Separate "one instance" (fine) from "global access" (harmful), then show DI giving the first without the second.

Likely follow-ups
  • When is a real Singleton still reasonable? (Truly process-wide, stateless or immutable services like a logger, or where no DI exists.)
Your 25-line container: what happens on a binding cycle, and is it thread-safe?

A naive recursive resolver with no bookkeeping hits a cycle (A needs B, B needs A) as a StackOverflowError. Ours keeps the current resolution path in a set: add on entry, throw "cycle: A -> B -> A" if the type is already there, remove in finally. It is single-threaded by design (plain HashMaps), so two threads could build two "singletons"; build the graph in main() before starting threads.

Making it concurrent is harder than it looks: ConcurrentHashMap.computeIfAbsent cannot be used recursively on the same map (resolving A inside A's mapping function updates the map again, which is illegal and can throw or hang), which is why real containers use locks around creation instead.
