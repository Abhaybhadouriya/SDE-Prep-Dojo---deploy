When to use it, when not to

Use it when
  • A class talks to anything slow, external or non-deterministic: network, database, file system, clock, randomness. These are what you want to fake in tests.
  • You need to swap implementations: payment providers, notification channels, storage back-ends, pricing strategies (see Strategy).
  • Several objects should share one instance (a connection pool, a cache) with one owner deciding its lifetime.
  • You want dependencies visible: reading a constructor tells you what the class touches.
Avoid it, or watch out, when
  • The "dependency" is a value object or a simple helper (new ArrayList<>(), a Money, a LocalDate). Inject services, not values.
  • Every class gets an interface "just in case" with exactly one implementation forever. Interfaces are cheap, but not free.
  • A container for a 300-line program: a few new calls in main are clearer than annotations.
  • Constructor parameter lists keep growing. That is a Single Responsibility smell; split the class rather than switching to field injection to hide it.
  • Container magic: wiring errors appear at startup (or at first use with lazy beans), and "where did this object come from?" becomes a search.
