Clarify requirements

Spend the first 5-8 minutes here. Write the list where the interviewer can see it, and ask before you assume.

Functional (must have)
  • Log a message with a level: DEBUG < INFO < WARN < ERROR < FATAL.
  • A global minimum level: below it, nothing happens.
  • Many destinations (sinks): console, file, in-memory; later DB, Kafka, pager.
  • Each destination has its own threshold and format (plain text, JSON).
  • Named loggers ("payments", "orders") that share one configuration.
  • Change configuration at run time (raise to WARN during an incident).
Non-functional
  • Thread-safe: many threads log at once; lines never interleave mid-line.
  • Low latency for the caller: logging must not block on disk or network (async option).
  • No lost lines on clean shutdown; under overload, drop (and count) instead of freezing the app.
  • Extensible: a new sink or format without editing existing classes (Open/Closed).
  • Message order kept per sink.

Out of scope (say it out loud): log shipping across machines, retention and rotation policies beyond a mention, a query UI, distributed tracing. Those are HLD topics; see Log Aggregation (ELK at scale).

Questions to ask

  1. Library or service? A library inside one process (this page) or a central logging service other apps call? The answer changes everything.
  2. Which sinks first? Console + file is the usual minimum. Is a slow sink (DB, HTTP) expected? That pushes you to async.
  3. Threshold per sink or one global level? Usually both.
  4. Sync or async? If async: is it OK to drop under burst, or must the caller block?
  5. Formats? Plain and JSON; any required fields (timestamp, thread, logger name, request id)?
  6. Runtime reconfiguration? From a config file or an API call?
  7. Follow-ups they may have in mind: search by word, rate limiting noisy logs, rotation by size.
