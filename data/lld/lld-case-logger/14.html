Follow-up questions

Why Chain of Responsibility and not just a list of sinks in the Logger?

For pure "send to every sink above its threshold", a list is equal and simpler, and I would say so. The chain pays off when a handler may stop the message (sampling, dedupe, PII filter), when order matters, or when handlers do different jobs (filter, enrich, write) instead of all writing.

How to answer

Give the honest comparison, then name the follow-up that tips it: "if you later ask for rate limiting of noisy logs, the chain lets me add a stopping handler in front without touching the others".

Likely follow-ups
  • Show the classic "first handler wins" version.
  • How is this different from Observer?
Should callers be able to choose the sink, like log(msg, FILE)?

No. Callers describe the event and its severity; routing is configuration. If callers name sinks, every call site changes when ops moves logs from file to Kafka. If a team really needs a separate stream (audit), give it its own named logger, and route that name in config.

How to answer

Tie it to Dependency Inversion: business code depends on the Logger abstraction, not on destinations.

Likely follow-ups
  • How would you route the "audit" logger only to a durable sink?
How do you make the logger thread-safe without one global lock?

Remove shared mutable state where you can and narrow locks where you cannot: immutable LogMessage; immutable config behind a volatile reference (lock-free reads); ConcurrentHashMap for the registry; one lock per sink held only around the write; formatting outside any lock. With async, the queue is the only point of contention and it is a well-tested concurrent structure.

How to answer

Walk through the shared state table: name each shared item and its guard.

Likely follow-ups
  • Why is volatile enough for the config but not for a counter?
  • What happens if a sink's write is slow?
The async queue is full. What do you do?

Pick a policy per sink: drop newest and count (default for debug/info), block the caller (only for must-not-lose audit logs), or overwrite oldest (ring buffer, keeps recent history). Expose the drop count as a metric and log a summary line ("dropped 1 234 lines") once the queue drains. Size the queue from burst rate x expected writer stall time.

Likely follow-ups
  • Could you batch writes to the file to make the writer faster?
  • What does Log4j 2 do? (Disruptor ring buffer, configurable wait strategy.)
How do you guarantee nothing is lost on shutdown?

Close sinks in a shutdown hook. AsyncSink.close() marks itself closed (under the write side of a read-write lock, so no writer is half-way between its "closed?" check and its enqueue), puts a poison pill after all queued lines, joins the writer thread, and then closes the wrapped sink, which flushes the file buffer. close() is idempotent so double shutdown is safe. A hard kill (SIGKILL, power loss) can still lose buffered lines; only a synchronous, fsync-ed sink avoids that, at a big cost.

Is Singleton a good idea here? People call it an anti-pattern.

Logging is the textbook acceptable case: truly process-wide, stateless for callers, and needed from code that has no injection path (static helpers, libraries). The risks (hidden global state, hard tests) are reduced because the config is replaceable via configure() and tests inject a MemorySink and a fake clock. In a DI framework I would register LogManager as a singleton bean instead of a static.

Likely follow-ups
  • Write a thread-safe lazy singleton (holder idiom / double-checked locking with volatile).
Add "search logs by a word".

Add a sink, do not change the logger: SearchIndexSink stores lines and an inverted index from lower-cased word to line numbers (a TreeSet keeps them in order). Query is a map lookup. Discuss limits: memory grows forever (cap it or age out), phrase search needs positions, multi-word AND is a set intersection. At scale this is a search engine (Elasticsearch), which is an HLD topic.

Likely follow-ups
  • Search within a time range? (Index by time bucket, or binary search on timestamps.)
Why is the level check the first line of log()?

Most debug calls are disabled in production. Checking first means a disabled call costs one comparison: no message object, no timestamp, no string formatting. For expensive messages, offer a lazy API (log.debug(() -> dump(state))) or a macro like our C++ LOG that does not even evaluate the expression, just as pr_debug compiles away.

How would you support different levels for different packages?

Use dotted names as a tree: com.shop.payments inherits from com.shop unless it has its own level. Resolve the effective level by walking up the name, and cache the result per logger, invalidated on reconfigure. That is how Java's built-in logging and Python's logging work (Python also "propagates" records up to parent handlers, which is a chain).

Decorator or Chain of Responsibility: which is AsyncSink, and why not the other?

Decorator: it has the same interface as what it wraps, wraps exactly one target, and always forwards (it adds behaviour, it never decides "not mine"). A chain node may handle, pass or stop, and links to a different kind of next step. Structurally they look alike (both hold a reference of the same type); the intent differs. See pattern look-alikes.
