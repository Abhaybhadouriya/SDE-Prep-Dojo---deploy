Concurrency and thread safety

A logger is called from every thread in the process, so this is where SDE-2 rounds dig. Go through the shared state one item at a time:

  1. A writer checked closed (false) and is about to call offer(). In that gap, close() sets closed and queues the POISON pill. The writer's line then lands behind POISON: the worker stops before it, so the line is neither written nor counted as dropped.
  2. The guard: write() holds the read side of a ReentrantReadWriteLock (writers never block each other), and close() takes the write side just to flip closed. So the check and the offer can no longer be split by a close.
  3. close() waits for the writers already inside write(), then flips the flag and queues POISON last. Every later write sees closed and is counted as dropped. The demo checks written + dropped == attempted.

Full queue: drop, block or overwrite?

There is no free answer; pick per sink and say why.

  • Drop newest and count (our AsyncSink): the app never stalls; you lose lines under a burst but you know how many. Good for DEBUG/INFO.
  • Block the caller (put()): nothing lost, but a slow disk now slows checkout. Only for audit logs that must never be lost, and then it should be its own sink.
  • Overwrite oldest (ring buffer, our C++ version): keeps the most recent history, the right choice for "what happened just before the crash". This is what the kernel log buffer does.

From your world

printk can be called from interrupt context, so it must never sleep. The kernel's answer is a lock-free ring buffer (since 5.10) that writers append to, and printing to slow consoles can be deferred instead of done by the caller. Same lesson as AsyncSink: the producer side must be cheap and non-blocking, and the slow device is drained by someone else. Log4j 2's async loggers make the same trade with the LMAX Disruptor ring buffer.

Do not hold the sink lock while formatting. Format first (no shared state), then lock only for the write. In the C++ AsyncSink sketch the writer even unlocks the queue before doing I/O. Holding a lock across I/O is the classic way a logger turns into a global bottleneck.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • BlockingQueue = a bounded producer-consumer ring with a mutex and two condition variables (a kfifo plus wait queues).
