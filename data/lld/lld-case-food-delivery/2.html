Clarify the requirements

Spend the first five minutes writing these down. Read them back to the interviewer; it costs nothing and catches the requirement you missed.

Functional (P0)

  1. Onboard a restaurant with a name, a menu (item to price) and a processing capacity (how many items it can cook at once).
  2. Update the menu: add an item or change a price.
  3. Place an order of several items with quantities. The system picks one restaurant using the current selection strategy (lowest total price; also "most free capacity"). Accept only if that restaurant serves every item and has enough free capacity.
  4. Mark an order ready (the kitchen dispatched it): capacity is returned and the items count as served.
  5. Assign a delivery partner: any free partner; if none is free the order waits in FIFO order.
  6. Deliver and cancel (cancel only before the food is ready).
  7. Report: items served per restaurant, order status, restaurant details.

Non-functional

  • In-memory only, no DB, no UI, no HTTP. A driver main that demos every feature.
  • Thread-safe: many customers order at once; capacity must never go negative or above the limit.
  • Extensible: a new selection rule or a new notification channel must not change the service.
  • Fail clearly: unknown restaurant/item, bad quantity, illegal state change give a named exception with a message.

Out of scope (say it out loud)

Payments, user accounts, ratings, distance and ETA, splitting one order across restaurants, persistence. Each is a follow-up; you will see how the design absorbs them in Extensibility.
