Concurrency and thread safety

List the shared mutable state, then give each piece one owner and one lock. That is the whole method.

Step through the race this section is about, then the fix the code uses:

  1. Order thread A reads the counter: 3 of 4 pots in use, so one is free.
  2. Before A writes, order thread B reads the same counter and also sees one free pot.
  3. Both add their order. The kitchen now has 5 pots on a 4-pot stove. Nothing crashes; one order is late or burnt.
  4. The fix is one critical section: synchronized tryReserve checks and adds under the restaurant's lock. The demo fires 16 threads at capacity 4: exactly 4 accepted, 0 free afterwards.

From your world

tryReserve is atomic_add_unless() on a credit counter: "add qty unless it would exceed the limit", one indivisible step. The two-line version (if (free >= qty) inUse += qty; without a lock) is the classic check-then-act bug you would never accept in a driver's TX ring. The Dispatcher's single lock is the same reason a wait queue and its condition share one spinlock: "nothing free, so sleep" and "I freed one, wake a waiter" must not interleave, or you get a lost wakeup.

Two subtle points that earn credit

  1. Move state first, then side effects. markReady calls moveTo(READY) before release(). If a cancel races, one of the two transitions throws, so capacity comes back exactly once. Reverse the order and you can release twice.
  2. Never call listeners while holding a lock. A listener may be slow (SMS) or call back into the service (re-reading the order). Holding the order lock during callbacks invites deadlock. Java's move() returns from moveTo (lock released) and only then notifies.

The demo proves the first row: 16 threads race for a restaurant with capacity 4 and exactly 4 orders are accepted, leaving 0 free. Remove synchronized from tryReserve and the test fails intermittently, which is precisely why you write it.

Many servers? In-process locks stop at the JVM. With several app servers the capacity counter moves to the database or Redis: UPDATE restaurant SET in_use = in_use + :q WHERE id = :id AND in_use + :q <= capacity and check that one row changed. Same idea, the atomic step just lives elsewhere. The HLD view is in Food Delivery (Swiggy/Zomato) system design.
