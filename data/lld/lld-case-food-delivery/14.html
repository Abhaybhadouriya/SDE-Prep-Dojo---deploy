Interview follow-ups

How do you make sure a restaurant never accepts more items than its capacity when orders arrive concurrently?

The check and the increment must be one atomic step owned by the restaurant: synchronized boolean tryReserve(qty). The service may pre-filter candidates without a lock (it is only a hint), but the decision is the reserve call. If it returns false, drop that restaurant and ask the strategy again. For several servers, the same atomic step becomes a conditional SQL update or a Redis Lua script.

How to answer

Name the race (check-then-act), show the one-lock fix, then mention the retry loop and the distributed version.

Likely follow-ups
  • Why not one global lock? (Serialises all restaurants; per-restaurant locks let different kitchens proceed in parallel.)
  • Could you use an AtomicInteger? (Yes, with a CAS loop: read, check, compareAndSet.)
Add a third selection strategy, "highest rated restaurant", during the evaluation call.

Add a rating field to Restaurant (set at onboarding, default 0), then one class: RatingSelector implements RestaurantSelector returning the candidate with the highest rating, ties by name. Switch with setSelector(new RatingSelector()). No change to placeOrder: that is the evidence that the Strategy was worth it.

How to answer

Code it live; it is about ten lines. Say "Open/Closed: open for a new rule, closed for the flow".

Likely follow-ups
  • Combine rules (cheapest among 4+ stars)? (A composite selector that filters then delegates, or a comparator chain.)
Why model order status with the State pattern? Isn't an enum field enough?

An enum field alone lets any code assign any status. The State idea is that the current state decides what is allowed next. Here that is a transition table (canMoveTo) behind one guarded moveTo. When states gain their own behaviour (cancellation fee depends on state, READY times out), each becomes a class implementing cancel(), next() and so on, and the Order delegates to it.

How to answer

Draw the state diagram first, then say "enum table now, classes when states get behaviour". That shows judgement, not pattern-matching.

Likely follow-ups
  • Where does the cancellation fee go? (A method on the state, or a CancellationPolicy strategy keyed by state.)
The Observer cross-question: a listener throws, or is slow. What happens to the order?

The order's state change has already committed, so it must not be undone by a notification failure. Call listeners outside the lock, catch and log each listener's exception so one bad subscriber does not stop the others, and for slow channels (SMS, push) hand the event to an executor or a queue instead of calling inline. In a real system the event goes to Kafka and consumers retry independently.

How to answer

Separate "state changed" (must be correct) from "people were told" (best effort, retried). Mention ordering: per-order events must arrive in order, so key the queue by order id.

Likely follow-ups
  • Push vs pull? (Push the event with from/to; listeners do not re-read the order.)
  • WebSocket vs SSE vs webhook for the customer app? (SSE for one-way status updates, WebSocket when the client also talks, webhook for server-to-server partners.)
Cancel and markReady arrive at the same time for one order. Walk through it.

Both call order.moveTo(), which is synchronized. Whichever runs first changes the status; the second finds the transition illegal (READY to CANCELLED, or CANCELLED to READY) and throws. Each method performs its side effect (release capacity) only after its own transition succeeded, so capacity is released exactly once.

How to answer

The rule "transition first, side effects after, only for the winner" is the thing to say.

Likely follow-ups
  • What does the losing caller see? (A 409 Conflict with the current status.)
The customer's app retries "place order" after a timeout. How do you avoid two orders?

Idempotency key: the client generates a UUID per checkout and sends it with the request. The service keeps Map<key, orderId> (with putIfAbsent); a repeat with the same key returns the first order instead of creating another. In a database it is a unique index on the key.

How to answer

Name the problem (at-least-once delivery), the key, and where it is stored. Keys expire after a day or so.

Likely follow-ups
  • Same key, different items? (Reject: the key is bound to the first request's content hash.)
How would you support splitting one order across restaurants?

Make Order a parent with SubOrders, one per restaurant, each with its own status and capacity reservation. The selector returns a plan (list of restaurant, items). Reserve each sub-order; if any fails, release the ones already reserved (all-or-nothing). Parent status is derived: DELIVERED when all sub-orders are delivered.

How to answer

Admit it is a model change, then show the rollback. Choosing the split is an optimisation problem; a greedy "cheapest restaurant per item" is a fine first answer.

Likely follow-ups
  • Deadlock when reserving several restaurants? (Each reserve is a separate short lock, never nested, so no.)
Interface or abstract class for RestaurantSelector?

Interface: strategies share no state or code, only a contract, and a lambda can implement a single-method interface. An abstract class makes sense if every strategy shared a step (for example "filter by open hours, then rank") - then it becomes a Template Method.

How to answer

Default to interface; name the case where abstract wins.

Likely follow-ups
  • Composition over inheritance here? (Service has a selector rather than subclasses per rule.)
A rider finishes while a READY order is being queued. Can the order wait forever?

Only if "find a free rider or enqueue" and "dequeue or mark free" are under different locks. Then: order thread sees no free rider, rider thread sees an empty queue and marks itself free, order thread enqueues: a lost wakeup. The Dispatcher uses one lock for both operations, so one always sees the other's effect.

How to answer

Describe the interleaving step by step; that is what convinces the interviewer.

Likely follow-ups
  • Many dispatchers (one per zone)? (Partition by zone; each zone has its own lock and queue.)
Draw the database schema for this design.

restaurant(id, name, capacity, in_use), menu_item(restaurant_id, item, price, PK(restaurant_id, item)), orders(id, customer_id, restaurant_id, status, total, partner_id NULL, created_at, idempotency_key UNIQUE), order_line(order_id, item, qty, unit_price), partner(id, name, status). unit_price on the line is the snapshot. Capacity changes use the conditional update.

How to answer

Say which column carries the invariant and which unique index stops duplicates.

Likely follow-ups
  • SQL or NoSQL? (SQL for orders and money: transactions and constraints. Menus could be a document store or cache.)
