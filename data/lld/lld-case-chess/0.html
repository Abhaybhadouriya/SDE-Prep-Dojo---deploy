The story: one referee, six kinds of walkers

Explain like I'm 5

Imagine a playground game with six kinds of children. Rabbits jump in an L shape. Runners go straight as far as they like. Sliders go only diagonally. One little child, the king, takes one step at a time, and if he is caught the team loses.

The referee does not memorise every rule. When a child wants to move, the referee asks that child: "where can you go from here?" The child answers by its own rule. Then the referee checks only the team rule: "after this move, can someone catch your king?" If yes, the move is not allowed.

The referee also writes every move in a notebook. If both players agree to take a move back, he reads the last line and puts everything back exactly as it was, even the child that was knocked out.

That is the whole design. Each child is a Piece subclass with its own move rule (polymorphism). The referee is the Game: it owns turns, check, checkmate and stalemate. The playground is the Board. Each line in the notebook is a Move object that can execute() and undo() itself (the Command pattern). And "playing / in check / checkmate / stalemate / resigned" is the game's state.

From your world

A Piece is a struct file_operations for chess: every piece type fills the same small table of function pointers (attacks, candidate_moves), and the Game calls through the table without a switch on piece type, exactly as the VFS calls f_op->read without knowing ext4 from procfs. In Java and C++ the compiler builds that table for you (the vtable). Move.undo() is the error-unwind path you write in a driver probe (goto err_free_irq): every step that changed state records what it needs to reverse itself. And perft, the move-count test used here, is a conformance test vector, like checking your TCP stack against known RFC traces.
