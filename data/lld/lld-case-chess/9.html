Concurrency and thread safety

A local two-player game is single-threaded, and you should say so. Threads only appear when the game leaves one laptop: many games on one server, a chess clock that ticks on its own thread, or an online opponent whose moves arrive over the network. The interviewer's follow-up is usually "now it is online":

  1. A double click (or a second browser tab) sends the same move twice. Both requests read ply 10 and both apply a move.
  2. The guard: commands for one game run under that game's lock (or on one queue per game), and each carries expectedPly. A move applies only if it matches the current ply.
  3. The second request finds ply 11, not 10, and is rejected with a conflict, so the client re-reads the board. Different games have different locks and run in parallel.

Level check. For SDE-1, a single-game, single-threaded design is a complete answer; say "turns are serial, so one thread per game" and move on. SDE-2 candidates are expected to handle the list below. New to Java threads? Read Concurrency basics and Locks first.

  • One writer per game. Two players' requests for the same game arrive on different threads. Serialize them: a lock per game (synchronized (game) or a ReentrantLock in a ConcurrentHashMap<gameId, Game>), or route every command for a game to one single-threaded executor (an actor). Different games run in parallel; there is no global lock.
  • Stale requests. A double-clicked move or a move from a second browser tab must not apply twice. Each request carries expectedPly; the move applies only if it matches (optimistic concurrency, the ply column in the schema). The second request gets 409 and re-reads.
  • Readers (spectators). Do not let them read the mutable board while a move is half-applied (the king-safety check temporarily executes moves!). Publish an immutable snapshot (FEN string + status) after each move, behind a volatile reference; readers never lock.
  • Clocks. A scheduled task per game flags "time out"; it must go through the same per-game lock or queue, otherwise "last-second move" and "flag" race. Resolve by the server timestamp at which the lock was taken.
  • Persistence. Insert into moves and update games in one transaction with WHERE ply = :expected; that row lock is the cross-server version of the per-game lock.

From your world

"Try the move, check, undo" is a speculative write to shared state. Inside one lock it is fine; outside it, a reader could see the speculative board, the same reason the kernel publishes a new routing table with RCU (rcu_assign_pointer) instead of editing the live one in place. The snapshot-for-spectators idea is exactly RCU: writers build a new version, readers grab the current pointer and never block.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
