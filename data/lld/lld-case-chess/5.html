Key relationships and patterns (and why each)

Pattern / ideaWhereWhy
Polymorphism (replace conditional with polymorphism)Piece.attacks() per subclassNo switch(pieceType) in the game loop. A new piece type is a new class (Open/Closed).
Template Method-style base classesSlidingPiece, StepPieceRook, bishop and queen share one walking loop and differ only in directions: three classes of two lines each.
CommandMove.execute / undoTake-back, move history, replay, and the trick "try the move, test king safety, undo" all come from one object.
State (as an enum)GameStatusTerminal states reject moves. An enum is enough because behaviour per state is tiny; switch to State classes if states gain behaviour (clocks, draw offers).
Simple FactoryPiece.fromSymbol('q')Board setup and promotion create pieces from one letter; set up any test position from 8 strings.
Information Expert (GRASP: a short list of rules for deciding which class gets which responsibility)Board.isAttackedInformation Expert means: give a method to the class that already holds the data it needs. The board has all pieces, so it answers "is this square attacked?".
Value objectsPosition, Player recordsImmutable, comparable with equals, safe as map keys.

A common answer is "Strategy pattern for move validation". It is not wrong, but notice that a piece's rule never changes at runtime; a knight is always a knight. That makes plain inheritance (one subclass per piece) the simpler and more honest model. Strategy earns its place when rules vary at runtime, for example a chess variant chosen by the player: then Game takes a RuleSet strategy. Saying this distinction out loud is a strong signal; see pattern look-alikes.
