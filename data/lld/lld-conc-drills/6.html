Coarse vs fine-grained: the trade-off table

Coarse (one lock)Fine-grained (shards, per key)Lock-free (CAS, adders)
Correctness proofEasy: one invariant, one lockPer part; cross-part operations are hard (global size, global LRU)Hard beyond one variable
Throughput under contentionLimited to one thread at a timeScales with independent partsHigh for simple counters
Deadlock riskNone (one lock)Yes if an operation needs two parts: lock in a fixed orderNone (but livelock-ish retry storms)
SemanticsExactOften approximate (per-shard LRU)Snapshot reads may be stale (LongAdder.sum())
Interview useSay first, alwaysThe "how would you scale it" follow-upCounters, flags, single-word state

Two more ideas that often beat any lock:

  • Confinement: give the structure to one owner thread and send it requests over a queue (like an event loop). No locks at all, and ordering is obvious. Redis is single-threaded for command execution for this reason.
  • Immutability and copy-on-write: for read-mostly data (configuration, routing tables) readers use an immutable snapshot through a volatile reference, and writers build a new copy and swap it. This is RCU in kernel terms. It does not suit an LRU (every read is a write) but suits a rate-limit rules table perfectly.
