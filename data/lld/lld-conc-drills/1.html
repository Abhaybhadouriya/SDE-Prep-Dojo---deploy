The recipe: making any class thread-safe

Do not start by sprinkling synchronized. Interviewers have heard that answer and usually reject it on its own (a Google candidate reported exactly that for an LFU cache follow-up). Walk through these steps out loud instead:

  1. List the shared mutable state. Fields that more than one thread can reach and that change. Immutable fields and thread-local data are free.
  2. Write down the invariants. Rules that link fields: "map size equals list length", "size <= capacity", "tokens between 0 and capacity". Any invariant that spans two fields needs both updated in one atomic step.
  3. Find the compound actions. Check-then-act ("if absent, put"), read-modify-write (count++), and reads that also write (LRU get).
  4. Pick a granularity. Start with one lock for the whole object. It is correct and easy to review. Then, only if contention is a real problem, split the state into independent parts (shards, per-key objects) that each keep their own invariant.
  5. Prefer a ready-made building block. ConcurrentHashMap.compute, AtomicLong, LongAdder, BlockingQueue, or a production library (Caffeine for caches, Resilience4j or Guava for rate limiting) beat hand-rolled locking in real code. In the interview, say so, then build it yourself.
  6. Prove it. A stress test with many threads that checks the invariants at the end (the code on this page does exactly that), plus a fake clock for anything time-based.

The building blocks themselves are covered earlier: races, visibility and atomicity in Thread Safety Basics, and synchronized, ReentrantLock and CAS in the locks lesson; this page uses them. For the deadlock risks of taking more than one of these locks, see Deadlock, Livelock & Starvation.
