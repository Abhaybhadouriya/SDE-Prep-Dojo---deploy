Make your LRU (or LFU) cache thread-safe. The interviewer says "not just synchronized".

Start by explaining why a lock is needed on get too: it reorders the list (LRU) or moves the key between frequency buckets (LFU), so it is a write. Baseline: one ReentrantLock around each method, which is O(1) work under the lock. To scale: shard into N independent caches by key hash (approximate global eviction), or record reads in a buffer and apply them to the recency order in batches under the lock (the approach production caches like Caffeine use). Reject a ReadWriteLock with get under the read lock, and explain the lost-node race.

How to answer

Correct first, then scale, then name what each step gives up. Offer a stress test that checks map size equals list length.

Likely follow-ups
  • What does sharding do to eviction order? (LRU per shard only.)
  • How do you avoid a stampede when many threads miss the same key? (Load once per key: a per-key future in a ConcurrentHashMap.)
Design a thread-safe rate limiter allowing N requests per second per user.

A ConcurrentHashMap<userId, TokenBucket> with computeIfAbsent; each bucket has capacity N, refill rate N per second, and a synchronized tryAcquire that refills lazily from a monotonic clock, then takes a token. Inject the clock for tests. Evict idle full buckets. For several servers, move the bucket to shared storage (Redis with an atomic script) as in the distributed rate limiter design.

How to answer

State the invariant (tokens and last-refill time change together), the per-key granularity, and lazy refill. Mention the Strategy pattern for swapping in sliding-window or fixed-window algorithms.

Likely follow-ups
  • Token bucket vs sliding window log vs fixed window? (Bursts allowed, memory, boundary spikes.)
  • Why not a refill thread? (A million timers; drift.)
AtomicLong vs LongAdder vs synchronized for a counter?

synchronized when the counter is part of a bigger invariant. AtomicLong for an exact single value with CAS semantics (ids, sequence numbers, "decrement if positive"). LongAdder for hot statistics: it spreads writes over cells and sums on read, so it scales much better under contention but has no compare-and-set and its sum is not an atomic snapshot.

How to answer

Decision (exact or approximate, standalone or invariant), then the kernel analogy (atomic_t vs percpu_counter).

Likely follow-ups
  • Is volatile long count; count++ safe? (No: visibility is not atomicity.)
Design a hit counter for the last 5 minutes that many threads update.

Ring of 300 one-second buckets, each (second, count). hit(): index = now mod 300; if the bucket's second is stale, reset it; increment. getHits(): sum buckets whose second is within the last 300. One lock is the simple correct answer; for scale, stripe the lock per bucket or use LongAdder per bucket, accepting small boundary error. Memory is fixed, unlike a timestamp queue.

How to answer

Start with the queue of timestamps (simple, unbounded), then the ring (bounded), then thread safety.

Likely follow-ups
  • Per user? (Map of rings, evict idle users.)
  • Millisecond precision? (Smaller buckets or a two-level ring.)
Coarse-grained vs fine-grained locking: when do you switch?

Start coarse: one lock is easy to prove and often fast enough because the critical section is tiny. Switch when profiling shows threads waiting on that lock and the state splits into independent parts (per key, per shard). Fine-grained locking costs complexity, approximate global semantics and deadlock risk when an operation spans two parts. In our LRU run, 8 shards were not faster than one lock for tiny operations: measure.

How to answer

Trade-off sentence, the measurement point, and a concrete example.

Likely follow-ups
  • How would you find lock contention in Java? (Thread dumps showing BLOCKED threads, JFR lock events, async-profiler lock mode.)
Why is ConcurrentHashMap + ConcurrentLinkedDeque not a correct LRU by itself?

Each structure is thread-safe, but an LRU operation changes both, and nothing makes the pair atomic. Between updating the map and moving the key in the deque another thread can evict it or move it, leaving duplicates or orphans. deque.remove(key) is also O(n). It can be made "good enough" with care, but say clearly that composition of thread-safe parts is not thread-safe.

How to answer

The general rule ("thread-safe + thread-safe is not thread-safe"), then the specific race.

Likely follow-ups
  • Fix it without one big lock? (Shards, each with its own lock and plain structures.)
