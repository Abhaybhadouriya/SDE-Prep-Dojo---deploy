Drill 1: a thread-safe LRU cache

The single-threaded LRU is a classic (LeetCode 146): a HashMap from key to node gives O(1) lookup, and a doubly linked list keeps recency order, most recent at the head. get moves the node to the head; put on a full cache unlinks the tail. Both are O(1).

The trap: get() is a write

Most people's first idea: "reads are 80% of the traffic, so use a ReadWriteLock: many threads can get at once, only put is exclusive". That is wrong for LRU, because get relinks list nodes. Two threads holding the read lock both run unlink(n); addFront(n); at the same time:

  1. Under a shared read lock, T1 and T2 both run get at once. Each unlinks its node and reads head.next, which is A for both.
  2. Each sets its node's next to A and writes head.next. The second write wins; the first is silently overwritten.
  3. B is reachable from the map but not from the list. Eviction walks the list, so B can never be evicted, and map size and list length disagree. Run the Java drill: the read-lock version ended consistent=false in every one of our runs, and in one run it held 300 entries in a cache of capacity 100.

So the correct options are:

OptionCorrect?Notes
synchronized / one ReentrantLock around get and putYesThe baseline answer. Every operation is O(1), so the critical section is tiny. Say it first.
ReadWriteLock with get under the read lockNoget mutates the list. Under the write lock it is correct but then you gained nothing.
Collections.synchronizedMap(new LinkedHashMap(cap, 0.75f, true))YesSame as one lock; accessOrder = true makes get reorder, and removeEldestEntry evicts. Iteration still needs manual locking.
Sharded: N independent LRUs, key picks a shardYes (approximate)Up to N threads in parallel. Eviction is LRU per shard, not global, and hot keys can still pile into one shard.
ConcurrentHashMap + ConcurrentLinkedDequeNot atomic togetherEach structure is safe, but "update map and move in deque" is two steps; removing from the middle of the deque is O(n). Common, but explain the gap.
Record reads in a buffer, replay them under the lock in batchesYesWhat production caches such as Caffeine do: reads never wait for the eviction lock; recency is updated a little later.

Measure before you shard. In our run on a laptop, 8 threads doing 200,000 tiny operations each, the single-lock LRU was actually faster than the 8-shard one (see the timings in the output; they vary per run). When the critical section is a few pointer writes, lock hand-off is cheap and sharding adds hashing and cache misses. Sharding pays off when the work under the lock is bigger or the thread count is much higher. Saying "I would measure" is a strong answer.

LFU: the same lock, more state

An LFU cache (LeetCode 460) evicts the key used the fewest times, breaking ties by least recently used. The O(1) design keeps key to value, key to count, and for each count an ordered set of keys, plus minFreq. A get moves a key from bucket f to bucket f+1 and may bump minFreq: four structures change together, so a single lock around each public method is the clear answer. The Python tab implements it. Note that Python's GIL does not make it safe: the GIL only keeps single bytecodes atomic, and each method is dozens of bytecodes across several dicts.
