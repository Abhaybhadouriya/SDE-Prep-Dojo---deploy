Concurrency and thread safety

This is the part Meesho's SDE-3 round called out. Two kinds of shared state exist, and each gets its own guard:

  1. Two buyers hit the same resting ask at the same moment. If matching ran on both threads at once, both would read "10 left" and both would fill 10: twenty shares sold from a ten-share order.
  2. The guard: each symbol's book has one lock (a single writer per symbol), so match() handles one incoming order at a time in arrival order. That also gives price-time fairness and a deterministic result.
  3. B is matched after A. The ask is gone, so B's order rests on the book as the new best bid. Orders for other symbols use other locks and run in parallel.

Deadlock check: lock order

The only nesting is book lock, then one account lock (settlement inside onTrade). Placing an order takes an account lock, releases it, and only then takes the book lock. Settlement takes the buyer's lock, releases it, then the seller's: never two account locks at once. So there is no cycle, and no deadlock. Say this explicitly; it is what "take care of concurrency" means. See deadlocks and lock ordering.

How real engines do it

Production matching engines avoid locks completely: each symbol (or shard of symbols) is owned by one thread that reads orders from an inbound queue, matches, and writes trades to an outbound queue. LMAX's published architecture is the best-known example: a single business-logic thread fed by ring buffers, with state rebuilt by replaying the input log. Our lock per book is the in-process, 90-minute version of the same rule: one writer per book.

From your world

This is RSS / per-queue NAPI thinking. Hash flows to one CPU, and that CPU processes its queue without locks, in order. Here you hash symbols to one matching thread. Cross-symbol consistency is not needed, just as cross-flow ordering is not needed in the network stack.

Calling listeners under the book lock keeps settlement in trade order and is simple, but a slow listener now stalls matching for that symbol. Fine for an interview; in production publish trades to a queue and let consumers process them on their own threads (Observer becomes pub-sub).

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • CopyOnWriteArrayList = an RCU-style list: readers walk a snapshot with no lock, writers copy the array and publish it; good for read-mostly listener sets.
