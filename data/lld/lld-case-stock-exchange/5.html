Key relationships and patterns, and why each

Pattern / ideaWhereWhy here
ObserverTradeListener: Broker, PriceTickerThe exchange must not know who cares about trades. Settlement, the price ticker and price alerts subscribe; a new consumer (analytics, tax report) needs no exchange change.
Validator chain (Chain of Responsibility style)OrderRulePre-trade checks grow (lot size, circuit limits, margin, max order value). Each is one class; the broker runs them in order and stops at the first failure. It is not Strategy: Strategy picks one interchangeable algorithm at runtime, while here every rule runs and none is chosen over another. (A rule that combines others with and/or would be the Specification pattern.)
State (as an enum)OrderStatusFive states with clear transitions. An enum with guarded transitions is enough; full State objects would be over-design for 90 minutes. Say that.
FacadeBrokerOne entry point for the client app: place, cancel, portfolio, history. It hides accounts, rules and the exchange.
Data structure choiceTreeMap<price, ArrayDeque<Order>>Sorted map gives the best price in O(log P); the deque keeps time order at one price in O(1) at the head. Bids sorted descending, asks ascending, so both "best" are firstEntry().
Single writer per symbolOrderBook.lockMatching must be sequential per symbol for determinism; different symbols run in parallel.
Dependency InversionExchange depends on TradeListener, not on BrokerThe exchange is reusable for many brokers; the broker can be tested with a fake exchange.

Why not Strategy for matching? You can put the loop behind a MatchingPolicy interface (FIFO vs pro-rata, used in some futures markets). Mention it as an extension point; do not build it unless asked. Interviewers at MakeMyTrip asked "why each pattern": having a reason not to use one counts too.
