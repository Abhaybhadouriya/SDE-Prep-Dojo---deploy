Concurrency and thread safety

The hard case is the open auction: many buyers read the current highest bid and try to beat it at the same moment. The rule "a bid must beat the highest by the increment" is a check-then-act, and check-then-act is a race unless both halves happen under one lock.

  • One lock per auction, not one global lock. Auction.bid() reads the best bid, validates and stores under its own ReentrantLock. Bids on different auctions never wait for each other. The registries are ConcurrentHashMaps and use putIfAbsent, so two "create A1" calls cannot both succeed.
  • Reject stale bids; do not lose them. The 8-thread test in Main has every thread read the best, add 5 and try. Thousands of attempts are rejected as stale, and the check proves what matters: every accepted bid is in the log once, the log strictly increases, and the winner is the last accepted bid. In a REST API the same idea is optimistic concurrency: the client sends the version it saw, and a stale version gets HTTP 409.
  • Close is idempotent. The timer thread and a manual close can arrive together. close() flips OPEN to CLOSED under the lock; the loser gets null and the house returns the stored result. Listeners are notified once.
  • The deadline is checked on every bid. A timer can fire late (GC pause, busy executor). ensureOpen() compares the injected Clock with endsAt, so a bid one millisecond late fails even if the timer has not run yet. The injected clock is also what makes the deadline test deterministic.
  • Never call listeners under the lock. The auction returns an outcome; the house notifies after unlock. A listener that sends an email or takes another lock cannot stall bids or deadlock with them.
  • Hot auctions at scale. One lock per auction is a single-writer queue per item. For a flash auction with heavy contention, the next step is to route all bids for an auction to one thread or one partition (actor style), the same shape as the HLD answer.

From your world

The per-auction lock is lock striping, like the per-bucket spinlocks of a kernel hash table instead of one big lock. The deadline check is the same lesson as TCP timers: mod_timer() may fire late, so the receive path still checks sequence and time itself instead of trusting that the timer already cleaned up. Closing once under the lock is test_and_set_bit() on a "done" flag: only the first caller does the work.
