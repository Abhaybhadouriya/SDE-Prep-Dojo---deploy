Two threads both read a best bid of 150 and both bid 160 (increment 10). What does the per-auction lock guarantee?

  1. Both bids are accepted
  2. Both are rejected
  3. One is accepted; the other is validated against 160 and rejected
Read-best, validate and store run as one critical section, so the second check sees the first bid.

Why does every bid check the clock even though a timer closes the auction?

  1. A timer can fire late, and the deadline must still hold
  2. Timers do not work in Java
  3. To make bids slower
The timer is how the auction gets closed; the clock check is what enforces the deadline.

Where should listeners be notified?

  1. Inside the auction lock, so they see a consistent state
  2. After the lock is released, using the returned outcome
  3. From a separate thread that polls every auction
Foreign code under a lock blocks other bidders and risks deadlock; the outcome object carries what they need.
