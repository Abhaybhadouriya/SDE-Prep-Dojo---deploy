Mediator and Observer are often confused here. The difference: Observer is one-to-many broadcast (the house tells all listeners "A1 closed"), while Mediator is many-to-many coordination through a hub (buyers, sellers and auctions all talk to the house instead of each other). This design uses both: the house mediates requests, then broadcasts events. See pattern look-alikes.

From your world

Mediator is the D-Bus daemon: processes never open sockets to each other, they all talk to the bus, which routes and checks policy. Strategy is tcp_congestion_ops: the socket code calls ->cong_avoid() and the algorithm (cubic, bbr) is chosen by name at runtime, as EnglishAuctionRules or HighestUniqueBidRules is chosen per auction. Observer is a notifier chain: register_netdevice_notifier() callers get every NETDEV_UP without the core knowing who they are. The OPEN/CLOSED enum is the same idea as sk->sk_state: one field, and every entry point checks it first.

Patterns we deliberately skipped: a Singleton house (tests need fresh houses, and the timer demo uses a second one), inheritance such as EnglishAuction extends Auction (the auction's data and locking are the same for every type; only the rules differ, so composition wins), and a Command object per input line (worth it only if they ask for undo or replay).
