The opposite mistake: interface confetti

Some candidates learn ISP and then create one interface per method: Printable, Stapleable, DuplexPrintable, ColorPrintable, each with one implementer. That is not good design; it is noise. Every interface is one more name to learn and one more file to open.

Guidelines that keep you in the middle:

  • Split when there is a second client or a second implementer that does not fit. Before that, an interface with one client and one implementer is often just a class in disguise (see YAGNI).
  • Methods that must stay consistent stay together. lock() and unlock() in separate interfaces would be absurd: no client uses one without the other.
  • A role interface usually has 1 to 5 methods. That is a rule of thumb, not a rule.
  • Watch the constructor. If a class now needs seven narrow interfaces injected, the class itself may be doing too much - an SRP problem, not an ISP one.

Dynamic languages (Python, JS) feel ISP differently: there is no compile step, so the "rebuild ripple" cost is gone, but the "lying type" cost remains. With typing.Protocol you can still declare a narrow role (Printer) and let a type checker catch misuse.
