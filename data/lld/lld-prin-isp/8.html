Where ISP shows up in LLD rounds

Interviewers rarely say "apply ISP". They hand you a problem where one actor needs far less than another. Spot it and name it.

ProblemThe fat temptationThe role split
Vending machineOne VendingMachine interface with insertCoin, selectItem, restock, collectCashCustomerPanel (insert, select, cancel) vs MaintenancePanel (restock, collect, setPrice)
ATMOne ATM with withdraw, deposit, refillCash, runDiagnosticsCustomer operations vs technician operations; different auth too

What is the Interface Segregation Principle? Give an example.

Clients should not be forced to depend on methods they do not use. Example: a Machine interface with print, scan and fax forces a print-only printer to throw on scan and fax, and forces a print queue to depend on fax methods. Split it into Printer, Scanner, Fax; the office machine implements all three, the cheap printer only Printer, and the print queue asks only for Printer.

How to answer

Definition in one line, a 3-method example, then the benefit: smaller blast radius of change, honest types, easier test doubles.

Likely follow-ups
  • How is ISP different from SRP?
  • Is it ever fine to throw UnsupportedOperationException?
ISP vs SRP - aren't they the same thing?

They aim at the same goal (limit the reasons a piece of code has to change) from different sides. SRP looks at a class from the implementer's side: does it have one reason to change? ISP looks at an interface from the caller's side: does each client see only what it uses? A class can obey SRP (one cohesive job, e.g. "office device driver") and still expose that job through several role interfaces for different callers.

How to answer

"SRP: implementer's view of a class. ISP: client's view of an interface." Then give one case where they diverge.

Likely follow-ups
  • Which one would you fix first in a legacy codebase?
Java's List has "optional" add/remove that throw on immutable lists. Is that an ISP violation? Would you design it differently?

Yes, by the letter of ISP: a caller holding a List cannot know whether add() works. The JDK chose it deliberately to avoid doubling the number of collection interfaces (ReadOnlyList, MutableList, for each of List, Set, Map ...). Kotlin later made the other choice: List is read-only and MutableList extends it. A good answer names both options and the trade-off: API size versus compile-time safety.

How to answer

Do not be dogmatic. Show you understand ISP is a cost/benefit decision, and cite a concrete alternative design.

Likely follow-ups
  • How would you expose a read-only view of your own collection class?
In a parking lot design, only electric cars can charge. Where does the charge() method go?

Not on Vehicle - that would force bikes and petrol cars to fake it. Create a Chargeable role interface with startCharging(port)/stopCharging(); ElectricCar implements Vehicle, Chargeable. The ChargingSpot accepts only Chargeable, so the type system prevents a petrol car from being plugged in.

How to answer

Say "role interface" and show the method signature of the spot: void plugIn(Chargeable c).

Likely follow-ups
  • What if hybrid cars arrive? (they implement Chargeable too - no change to Vehicle)
  • How does the spot assignment strategy know a car is chargeable without instanceof?
The Linux struct file_operations has many optional members. Is that bad design?

It is a deliberate fat interface that stays safe because (1) there is one caller, the VFS, which checks NULL in one place and maps it to an error like -ENOTTY or -EINVAL; (2) NULL is explicit, unlike a silently throwing method; (3) the kernel does segregate by subsystem: file, inode, address-space and net-device ops are separate tables. C lacks multiple interface inheritance, so one table per subsystem is the pragmatic shape. In Java I would split into role interfaces and let the compiler enforce it.

How to answer

Show you can judge a design by its context rather than reciting the rule.

Likely follow-ups
  • How does a vtable relate to an ops table? (see polymorphism and vtables)
You split an interface into 12 one-method interfaces. Your reviewer says it is worse. Why might they be right?

Over-segregation adds names, files and wiring without removing any real coupling. If every client uses all of the methods, or methods must be used together (open/close, lock/unlock), splitting them hides the real contract. Group by what each client calls together; split only when a second client or implementer needs less.

How to answer

Name the two failure modes (fat vs confetti) and the rule: cohesion from the caller's point of view.

Scenario: the 20-method NotificationService

In a machine-coding evaluation the reviewer opens your NotificationService interface: sendEmail, sendSms, sendPush, retryFailed, getDeliveryReport, updateTemplate, setRateLimit ... The OrderService only sends an order-confirmation. The reviewer asks: "What would you change?"
"I'd keep it, it's one service so it's simple. Classes that don't need a method can just ignore it."
"The order flow only needs Notifier.send(userId, message), so I'd give it exactly that role interface. Template admin and delivery reports have different callers (an admin console, a reporting job), so they get TemplateAdmin and DeliveryReports. The concrete NotificationHub can still implement all of them. Now testing OrderService needs a one-method fake, and changing report formats cannot break checkout."
Follow-up: "How does OrderService get its Notifier?" - constructor injection; see Dependency Inversion.
