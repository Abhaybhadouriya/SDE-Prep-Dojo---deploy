How to spot an ISP violation in code review

SmellWhat you seeTypical fix
Exceptions as "not supported"throw new UnsupportedOperationException() in an implementerSplit the interface; the implementer drops the role it cannot play
Empty bodiespublic void fax(...) { } - silently does nothing, worse than throwingSame: split; or a Null Object only if "do nothing" is a real behaviour
Type checks in callersif (m instanceof OfficeMachine) before callingAsk for the narrower type in the constructor instead
Huge mocksTest doubles stubbing 15 methods to test oneClient depends on a 1-3 method role interface
"God" interfaceUserService with login, billing, reports, adminSplit by caller: Authenticator, BillingAccount, UserAdmin
Refused bequestA subclass inherits methods it does not want and overrides them to failComposition / smaller interfaces (see refactoring.guru: Refused Bequest)

ISP and LSP are cousins. When CheapPrinter.scan() throws, it also breaks the Liskov Substitution Principle: you cannot substitute a CheapPrinter wherever a Machine is expected. Very often, fixing ISP is the cleanest way to fix the LSP violation too.
