From your world: file_operations, a fat interface on purpose

From your world

You already know the most famous "interface" in Linux: struct file_operations. It is a struct of function pointers - an interface in C. A character driver fills in the entries it supports and leaves the rest NULL. /dev/null supports read and write; it does not supply mmap. A simple sensor driver might supply read and unlocked_ioctl only.

So is file_operations a giant ISP violation? It has dozens of members. Honest answer: it is a deliberate, well-managed fat interface, and it is a great counter-example to talk about in an interview.

Look at how the kernel keeps the fat table safe. The trick is that "not supported" is part of the contract, and the caller (the VFS layer) checks for it in one place, so drivers never fake anything:

struct my_file_ops {
    long (*read)(struct my_file *f, char *buf, size_t n);
    long (*write)(struct my_file *f, const char *buf, size_t n);
    long (*ioctl)(struct my_file *f, unsigned int cmd);   /* optional */
};
struct my_file { const char *name; const struct my_file_ops *ops; };

static long null_read(struct my_file *f, char *buf, size_t n) { (void)f; (void)buf; (void)n; return 0; }
static long null_write(struct my_file *f, const char *buf, size_t n) { (void)f; (void)buf; return (long)n; }

/* designated initializer: ioctl left NULL = "I don't play this role" */
static const struct my_file_ops null_ops = { .read = null_read, .write = null_write };

/* the "VFS" checks NULL once, so no driver has to write a stub */
static long vfs_ioctl(struct my_file *f, unsigned int cmd) {
    if (!f->ops->ioctl) return -ENOTTY;
    return f->ops->ioctl(f, cmd);
}

This is a runnable toy in lld-code/lld-prin-isp/file_ops_style.c. In the real kernel, vfs_ioctl() in fs/ioctl.c returns -ENOTTY when a driver has no unlocked_ioctl, and a read on a file whose ops table has neither read nor read_iter fails with -EINVAL.

Why does this work in the kernel when it fails in application code?

  • One caller. Drivers do not call each other through file_operations; only the VFS does. So "clients forced to depend on what they don't use" barely applies: the VFS really does use every slot.
  • NULL is honest. A missing entry is visible and checked. Compare that with a Java class that silently throws: the caller has no way to know before calling.
  • The kernel does segregate, by concern. Operations on an open file live in file_operations, operations on an inode in inode_operations, page-cache operations in address_space_operations, network devices in net_device_ops. That is ISP at the level of "which subsystem calls this table".

Strong line for a systems candidate: "C has no cheap way for one object to implement several interfaces, so the kernel uses one ops table per subsystem with optional NULL slots and a single checking caller. In Java I get multiple interfaces for free, so I'd rather split - the type system then guarantees an unsupported call cannot even compile."
