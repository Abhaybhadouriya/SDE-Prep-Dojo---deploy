What a fat interface looks like

Let us build the classic example. We have an office printer that can print, scan and fax. Someone designs one interface for "a machine":

interface Machine {
    void print(String doc);
    String scan(String doc);
    void fax(String doc, String number);
}

That looks fine for the office printer. Then the shop starts selling a cheap printer that can only print. It must implement Machine, because every part of the code expects a Machine. So the developer writes this:

static class CheapPrinter implements Machine {
    public void print(String doc) { System.out.println("[fat] printing " + doc); }
    public String scan(String doc) { throw new UnsupportedOperationException("no scanner"); }
    public void fax(String doc, String number) { throw new UnsupportedOperationException("no fax"); }
}

The compiler is happy. The program is not. Any code holding a Machine believes it can call scan(). The type says "yes", the runtime says "boom". This is the first and most visible cost of a fat interface: lies in the type system.

Reading UML: a box with three compartments is a class (name / fields / methods). «interface» above the name marks an interface. A dashed line with a hollow triangle means "implements". A dashed line with an open arrow means "uses / depends on". See UML class diagrams for the full notation.
