How to split well: by client, then compose

Splitting is easy. Splitting well is the skill. Use these rules:

  1. List the clients. For each caller, write down exactly which methods it calls. Methods that are always called together by the same clients belong in the same interface.
  2. Name interfaces after roles, not implementers. Printer, Readable, Payable - not IOfficeMachine. The name should finish the sentence "this client needs something that is a ...".
  3. Compose when a client really needs several roles. Java lets an interface extend several others: interface MultiFunctionDevice extends Printer, Scanner, Fax {}. Big where it must be, narrow everywhere else.
  4. Wrap legacy fat interfaces. If you cannot change a vendor's 30-method SDK, put an Adapter in front that exposes only the role your code needs.
  5. Read vs write is the most common useful split. A reporting service needs find(), a checkout service needs save(). Splitting the repository into OrderReader and OrderWriter also makes read-only clients safe by construction.

Real examples from the JDK

  • Good segregation: Comparable, Runnable, AutoCloseable, Iterable, Readable and Appendable are tiny role interfaces. A class like StringBuilder implements Appendable and CharSequence; a method that only appends asks for Appendable.
  • A famous compromise: java.util.List marks add, remove and set as "optional operations". List.of(...) returns an immutable list whose add() throws UnsupportedOperationException. The JDK designers chose one interface to keep the collections API small; the price is exactly the runtime surprise ISP warns about. Mention this trade-off and you show you understand ISP is a design choice, not a law of physics.
