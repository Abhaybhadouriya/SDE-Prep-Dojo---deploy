Clarify the requirements

Spend 5-8 minutes here and write the list where the interviewer can see it. Coupon problems hide many product decisions (stacking, order, caps, rounding). Each one you settle now is one fewer surprise at minute 70.

Functional (P0: must work in the demo)

  1. Catalogue and stock Add products (id, name, category, price) with a stock count.
  2. Cart Per user: add an item (quantities merge), update quantity, remove. Adding more than the stock is rejected with a clear message.
  3. Coupons Types: flat X off; Z% off with an optional cap; Z% off one category only. Rules: minimum cart value, category present, first order only, valid until a date, maximum uses per user.
  4. Apply coupon Rejected with a reason when a rule fails, when the code is unknown, or when it cannot be combined with coupons already applied.
  5. Price Subtotal, each discount line, final total. Discounts run in a fixed priority order (item-level first), each on the running total; total never below zero.
  6. Checkout Re-check everything, reserve stock for all lines at once, record coupon use, create an order, empty the cart. A failure changes nothing.

P1 (bonus, only after P0 runs)

  • Buy-X-get-Y offers, global usage limits ("first 1000 users"), automatic best-coupon suggestion, tax, payment and order notifications.

Non-functional

  • Correct money: integer paise (long); percentages as basis points (1000 bp = 10%); state the rounding rule (we floor each discount).
  • Extensible: a new coupon type or rule is a new class or factory method, with no edits to the service (Open/Closed: open to extension by adding classes, closed to modification of tested ones).
  • Thread safe: two buyers racing for the last unit, and one user on two devices, must not corrupt stock or the cart.
  • In memory, no UI or HTTP, a driver that demos every feature.

Out of scope (say it out loud)

Login, real payment, search, product variants (size, colour), shipping fees, returns and refunds. Name the interface where each would plug in (PaymentGateway, OrderListener), then move on.

Questions to ask

  • Can coupons stack? How many? Are some exclusive? (We allow stacking, with a per-coupon stackable flag.)
  • In which order do stacked coupons run? Percent then flat, or flat then percent? (The order changes the total. We use a priority number: category offers, then cart percent, then flat.)
  • Is the minimum-cart rule checked on the subtotal or on the total after earlier discounts? (Subtotal; say it.)
  • What if the cart changes after a coupon was applied and the rule no longer holds? (The coupon stays attached but gives nothing, and the bill says why.)
  • Does adding to the cart reserve stock? (No; only checkout does. A soft check at add time gives early feedback.)
  • Method calls or text commands for input? (Method calls; a parser would be a thin layer on top.)
