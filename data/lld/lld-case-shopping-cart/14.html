Interview follow-ups

Percent first, then flat, or flat first? Does it matter?

Yes. On 1000 with "10% off" and "100 off": percent first gives 1000 - 100 - 100 = 800; flat first gives 1000 - 100 - 90 = 810. Because the order changes money, it must be a business rule, not an accident of the order the user typed codes. We give every coupon a priority and sort the layers by it (tie-break on code), so the result is deterministic. Most shops run item-level offers first, then cart-level percent, then flat.

How to answer

Show the two numbers, then say "priority field, sorted, tested for order independence".

Likely follow-ups
  • Should a percent coupon be computed on the subtotal or on the running total?
  • How would marketing change the order without a deploy?
Why separate Rule and DiscountStrategy instead of one Coupon subclass per type?

They vary independently. With 4 rule shapes and 3 discount shapes, subclasses give up to 12 classes (more with combined rules), and every new rule touches every type. With composition, a coupon is one Rule (possibly combined with and) plus one Strategy, so 4 + 3 small classes cover every combination, and coupons can be built from config rows. It is the Bridge idea applied to two axes.

How to answer

Count the classes both ways; mention config-driven coupons as the payoff.

Likely follow-ups
  • Where does the usage limit live, in a Rule or in the Coupon? Why?
Is your pricing a Decorator or a Chain of Responsibility?

A Decorator: every CouponLayer implements the same PriceCalculator interface as the thing it wraps, always calls the inner one, and adds its own effect to the result. In a Chain of Responsibility, handlers sit in a list and one of them may handle and stop the request. If the business wants "an exclusive coupon cancels the rest", CoR fits better. We moved that decision to apply time (the stackable check), so every layer always runs and Decorator is the simpler fit.

How to answer

State the structural test (same interface + wraps one vs. list + may stop), then tie it to the requirement.

Likely follow-ups
  • Could you write the same pipeline as a plain loop? (Yes; say when a loop is enough.)
Two users buy the last unit at the same time. Walk me through what happens.

Each thread locks its own cart, prices it, then calls inventory.reserveAll. The inventory lock lets only one in at a time. The first one sees stock 1 >= 1, decrements to 0 and returns. The second sees 0 < 1 and throws "out of stock" before changing anything; its cart, coupons and usage stay intact so the user can try again. In a database the same thing is a conditional UPDATE ... WHERE stock >= qty and a row-count check.

How to answer

Name the race (check-then-act), the critical section, and what the loser sees.

Likely follow-ups
  • Should adding to the cart reserve stock? What about a 10-minute hold?
  • How do you avoid one global inventory lock?
The user applied a coupon, then removed the item that made it valid. What should happen?

Rules are evaluated on every price() and again at checkout, not only at apply time. The coupon stays attached (so it comes back if the item comes back) but the layer adds a note instead of a discount: "FASHION20 not applied: needs a FASHION item in the cart". The other choice, auto-removing the coupon, is also fine; what matters is that a stale coupon never gives money away.

How to answer

Say "re-validate at price and at checkout", then pick a UX and state it.

Likely follow-ups
  • And if the coupon expires between pricing and checkout?
Add "buy 2 get 1 free" right now.

A new BuyXGetY(productId, x, y) implements DiscountStrategy: find the line, compute free = qty / (x + y) * y, return min(free * price, running). Pair it with Rule.always() or a minimum-quantity rule, give it a low priority number so it runs first, and register the coupon. No change to ShopService, CouponLayer or the other strategies.

How to answer

Code it in two minutes, then point at the files you did not touch.

Likely follow-ups
  • Which unit is free if the items have different prices? (Usually the cheapest.)
Design the coupon tables and make "first 1000 users" safe.

A coupons row holds type, value, cap, priority, stackable, per-user limit, a nullable remaining count and the rules as JSON; redemptions(order_id, code, user_id) records each use. The global limit is a conditional decrement in the checkout transaction (WHERE remaining > 0, check rows affected). The per-user limit is a count over redemptions, or a unique key on (code, user_id) when the limit is one. Cache active coupons, but never cache remaining.

How to answer

Tables first, then the one SQL statement that makes the limit atomic.

Likely follow-ups
  • The order fails after the decrement. How do you give the use back?
Why integer paise and basis points? Where does rounding happen?

Binary floating point cannot store 0.1 exactly, so sums drift and a hidden test expecting 539.20 sees 539.1999. Store paise in a long and percentages as basis points (10% = 1000), compute amount * bp / 10000 with integer division (floor), and round only there, once per discount. Converting from the user's "799.00" happens at the edge with BigDecimal (Java) or Decimal (Python).

How to answer

Problem, representation, the single place rounding happens, and which way it rounds.

Likely follow-ups
  • Should the shop round discounts down or half-up? Who decides?
Add payment and notifications without making checkout slow.

Reserve stock, then call a PaymentGateway interface; on failure release the reservation (a compensating step). After the order is committed and the locks are released, publish an OrderPlaced event to OrderListener observers (email, push, loyalty points). Slow I/O never runs under the cart or inventory lock. For real scale the event goes to a queue and workers consume it.

How to answer

Name the order: reserve, pay, commit, then notify asynchronously; and what undoes what.

Likely follow-ups
  • What if the payment succeeds but the response is lost?
Suggest the best coupon for the user's cart.

For each coupon the user could apply, build a candidate list (current coupons plus this one, if stacking allows), price it, and keep the lowest total. Because Bill and PricingContext are immutable and pricing has no side effects, this is safe to run without locks on a snapshot. With many coupons, first filter by cheap rules (category, min cart) using an index by category.

How to answer

Brute force over eligible coupons is fine; the design makes it side-effect free.
