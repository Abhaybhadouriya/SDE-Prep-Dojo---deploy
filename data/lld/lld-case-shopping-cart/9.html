Concurrency and thread safety

Three races matter, and an interviewer at Swiggy or Amazon will ask about at least one of them (background: races and atomicity, booking without double-booking).

Step through the race this section is about, then the fix the code uses:

  1. u3's checkout reads the laptop's stock: 1, enough.
  2. u4's checkout reads it before u3 writes: still 1.
  3. Both decrement. Stock is -1, two orders are paid and one customer will get a cancellation email.
  4. The fix: Inventory.reserveAll checks every line and then decrements them all inside one lock, so the second buyer sees 0 and gets "out of stock: Laptop". The Java demo races two threads for the last laptop; exactly one wins every time.
  1. Overselling the last unit Two users check out the last laptop at once. A per-product "if stock >= qty then stock -= qty" without a lock is a check-then-act race. Our Inventory.reserveAll does check and decrement for all lines inside one lock, so it is atomic for the whole order. The Java demo races two threads for the last laptop and the Python test races eight buyers for five headphones; exactly the right number win every time.
  2. One user, two devices The phone applies a coupon while the laptop checks out. Every cart method is synchronized on the cart, and checkout holds the cart lock for its whole run, so the coupon either lands before the price is computed or waits until the cart is cleared.
  3. Lock order Checkout holds the cart lock and then takes the inventory lock. Nothing ever takes them in the other order, so there is no deadlock (see deadlock). Say the order out loud; it is the first thing a reviewer looks for when two locks nest.
  4. Global usage limits "First 1000 orders only" is a shared counter across users, so the per-cart lock does not protect it. Use an AtomicInteger with a compare-and-set loop (decrement only if > 0), or in SQL UPDATE coupons SET remaining = remaining - 1 WHERE code = ? AND remaining > 0 and check the row count. If the stock reservation then fails, give the use back.
  5. Scaling the inventory lock One lock for all products is fine for an interview. For more throughput use one lock per product and take them in sorted product-id order, or move stock to the database with conditional updates. Flash-sale scale needs reservations with a time-out (see Flash Sale (HLD) and Inventory Management (HLD)).
  6. Retries A mobile client that times out and retries checkout must not create two orders. Accept a client idempotencyKey and return the existing order for a key already seen (as in E-commerce Checkout (HLD)).

From your world

reserveAll is the "check everything, then commit" shape of a multi-page allocation that must not leave half the pages mapped: validate the whole request under the lock, and only then mutate. The global-limit counter is atomic_dec_if_positive() from the kernel's atomic API, which does exactly the "decrement unless it would go below zero" step with a cmpxchg loop.
