Core flows

Pricing: how the layers build the bill

  1. The innermost layer, BasePrice, adds up the lines: 51598.00. Every outer layer starts from what the inner one returned.
  2. Layers are wrapped in priority order. FASHION20 (priority 10, item-level) looks only at FASHION lines: 20% of 1598.00 is 319.60.
  3. SAVE10 (priority 20) works on the running total 51278.40. 10% would be 5127.84; the cap makes it 500.00.
  4. FLAT200 never got here: it is not stackable, so applyCoupon refused it while other coupons were attached. Stacking policy is checked at apply time, not in the pipeline.
  5. The outermost layer returns the final Bill. Because the order comes from priority, not from the order the user typed codes, the same cart always gives the same total.

Checkout: validate everything, then change everything

  1. The driver calls the facade with only the user id. The cart and the applied codes are already on the server side.
  2. The service locks this user's cart (so a second device cannot change it mid-checkout) and takes a snapshot of the lines.
  3. It prices again with fresh rules: dates, past orders and usage may have changed since the coupon was applied. A coupon that no longer qualifies becomes a note, not a discount.
  4. It asks the inventory to reserve every line in one call. Inside its own lock the inventory checks all lines first, then decrements.
  5. If any line is short, an exception is thrown before any count changes, so stock, cart and coupon usage stay exactly as they were.
  6. Only then are coupon uses and the order count recorded and the cart cleared. The immutable Order keeps the Bill it was charged.
