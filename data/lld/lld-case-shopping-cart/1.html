How it is asked

The cart shows up in two shapes. The machine-coding shape (Meesho, Amazon) wants a running "shop manager" with a small fixed API: add product, add to cart, apply coupon, total, discounted total, checkout. The design shape (Swiggy, Microsoft) wants classes, APIs and a database schema, and then pushes on stacking rules, payment and notifications. Our design covers both: the core runs in under an hour, and the follow-ups plug in without rewrites. Round styles are explained in How LLD rounds work.

Older Amazon reports ask for a coupon and voucher manager with rule matching and usage limits, and the public low-level-design-primer question list carries a "generic coupon / promo code system" with the classic rule set: Z% off up to X, flat X off, with or without a minimum cart size, for one / some / all customers, usable once / a few times / always. Our rule set covers that list.

Read the Meesho campus report again: completeness first, then OOP. A beautiful Specification framework (small filter objects you combine with and/or/not, like composing BPF predicates) with no working checkout scores lower than a plain one that runs every API. Get the cart, one flat coupon, one percent coupon and checkout running by minute 45; add the rule framework and stacking after.
