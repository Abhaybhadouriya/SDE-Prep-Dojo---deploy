Key relationships and patterns (and why each)

Pattern / choiceWhereWhy it earns its place
SpecificationRule with and; factories minSubtotal, hasCategory, firstOrderOnly, validUntilCoupon eligibility is a boolean formula over the cart. Small named predicates you combine beat a growing if chain inside the coupon. Each rule also says why it failed, so the user sees "needs a cart value of at least 1000.00", not "invalid coupon".
StrategyDiscountStrategy: FlatOff, PercentOff, CategoryPercentOff"How much comes off" is the part that varies by coupon type. A new type (buy 2 get 1, free shipping) is a new class; the service and the layers never change.
DecoratorCouponLayer wraps a PriceCalculator, starting at BasePriceEach coupon adds one line to the bill on top of whatever the inner layers produced. Stacking is just wrapping, the order is the wrapping order, and a layer can be added (tax, delivery fee, loyalty points) without touching the others.
FacadeShopServiceOne entry point for the driver, a command parser or a REST controller. Locking and the all-or-nothing checkout live here.
Immutable value objectsProduct, CartLine, Bill, Order, PricingContextA Bill is a fact about one moment; layers return a new Bill instead of mutating a shared one, so the pipeline has no hidden order bugs and an Order can keep its Bill forever.
Chain of Responsibility (alternative)Coupon validation steps or pricing handlers in a listA CoR list of handlers sorted by priority is the other common answer, and it fits when a handler may stop the chain ("exclusive coupon: skip the rest"). Our Decorator stack and a CoR list are look-alikes here (see pattern look-alikes); pick one and say why.

Avoid the subclass explosion many tutorials show: FlatCouponWithMinCart, PercentCouponForNewUsers, PercentCappedCategoryCoupon... Every new rule doubles the classes. Keeping when (Rule) and how much (Strategy) apart is the same move as the Bridge pattern: two independent axes, joined by composition. Also avoid one applyCoupon with a switch (coupon.type); that is the exact thing interviewers wait for you to refactor.

From your world

The Decorator stack is the network stack's view of a packet, in miniature: each layer gets the result of the layer below and adds its own header. Or think of stacked block devices: dm-crypt on top of LVM on top of a disk, each one implementing the same block interface and holding a pointer to the one below. In C it is struct price_calc { const struct price_calc_ops *ops; struct price_calc *inner; const struct coupon *c; }; and calculate() first calls inner->ops->calculate(inner, ctx).

Why the pattern earns its place: the if-ladder it replaces

Without Strategy and Specification, every coupon type is a branch in the pricing method:

long discount(Coupon c, Cart cart) {
    switch (c.type) {
        case FLAT:
            return cart.subtotal() >= c.minValue ? c.amount : 0;
        case PERCENT:
            return Math.min(cart.subtotal() * c.percent / 100, c.cap);
        case CATEGORY_PERCENT:
            long s = 0;
            for (CartLine l : cart.lines()) if (l.product.category == c.category) s += l.total();
            return s * c.percent / 100;
        case FIRST_ORDER:   // follow-up: "buy 2 get 1" edits this switch,
            ...             // and the eligibility ifs above it, and every test of discount()
    }
}
interface DiscountStrategy { long amount(PricingContext ctx); }
interface Rule { Optional<String> whyNot(PricingContext ctx); /* and(..) combines rules */ }

final class Coupon {
    final Rule rule;                   // when (Specification)
    final DiscountStrategy discount;   // how much (Strategy)
}
// "buy 2 get 1" = one new DiscountStrategy class; ShopService does not change

With the switch, the follow-up "buy 2, get 1 free" edits the pricing method, the coupon enum and its tests. With the two interfaces it is one new DiscountStrategy class and one factory line; ShopService is untouched.

From your world: the same move in C

struct discount_ops { long (*amount)(const struct pricing_ctx *c, const void *arg); };
struct rule { const char *(*why_not)(const struct rule *r, const struct pricing_ctx *c); };
struct coupon { const struct rule *rule; const struct discount_ops *disc; const void *arg; };
/* price: for each coupon: if (!c->rule->why_not(c->rule, ctx)) total -= c->disc->amount(ctx, c->arg); */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
