What does the subject depend on in a correct Observer design?

  1. Every concrete observer class
  2. Only the observer interface (and its list)
  3. A message broker
  4. Nothing at all
The subject knows the callback interface; concrete observers can come and go.

In the pull model, what does notify pass to observers?

  1. The full new state
  2. A diff of old and new values
  3. Just a signal or a reference to the subject; observers query what they need
  4. Nothing; observers poll on a timer
Push sends the data; pull sends "I changed" and observers read from the subject.

A screen subscribes to a ticker and is closed without unsubscribing. What happens?

  1. The screen object is kept alive by the ticker's list and keeps getting updates (a leak)
  2. The JVM unsubscribes it automatically
  3. The ticker throws an exception
  4. Nothing, observers are always weak
The lapsed listener problem: a strong reference from the subject keeps the observer reachable.

Which collection lets an observer unsubscribe itself during notification without errors?

  1. ArrayList
  2. LinkedList
  3. HashSet
  4. CopyOnWriteArrayList
Its iterator walks a snapshot, so changes during the walk are safe.

What makes publish-subscribe different from plain Observer?

  1. Pub-sub has only one subscriber
  2. A broker sits between publishers and subscribers, who know only topics; delivery can be async and durable
  3. Pub-sub cannot be asynchronous
  4. Observer needs a network
Who holds the list is the key: the subject itself, or a broker in the middle.

In a Linux notifier chain, a callback returns NOTIFY_STOP. What happens?

  1. The callback is unregistered
  2. All callbacks run again
  3. Lower-priority callbacks are not called for this event
  4. The kernel panics
The stop bit ends the walk; the chain is ordered by priority, so later (lower) blocks are skipped.

In java.util.concurrent.Flow, how does a subscriber apply back-pressure?

  1. By calling Subscription.request(n) only when it can take more
  2. By throwing an exception
  3. By sleeping in onNext
  4. By unsubscribing and resubscribing
Demand is signalled with request(n); the publisher must not send more than requested.
