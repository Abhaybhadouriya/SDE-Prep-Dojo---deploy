The kernel's observers, in C

A notifier chain is a singly linked list of notifier_blocks sorted by priority. The shape, trimmed to the idea:

struct notifier_block {
    int (*notifier_call)(struct notifier_block *nb, unsigned long action, void *data);
    struct notifier_block __rcu *next;
    int priority;                         /* higher runs earlier */
};

/* An observer: return NOTIFY_DONE (not interested), NOTIFY_OK, or NOTIFY_BAD / NOTIFY_STOP to end the walk */
static int my_netdev_event(struct notifier_block *nb, unsigned long event, void *ptr)
{
    struct net_device *dev = netdev_notifier_info_to_dev(ptr);
    if (event == NETDEV_DOWN)
        pr_info("%s went down\n", dev->name);
    return NOTIFY_DONE;
}

static struct notifier_block my_nb = { .notifier_call = my_netdev_event };

/* module init */  register_netdevice_notifier(&my_nb);
/* module exit */  unregister_netdevice_notifier(&my_nb);   /* forget this and the chain
                                                                calls into freed module text */

Real drivers need their own state in the callback. The block is embedded in the driver's struct, and the callback climbs back out with container_of():

struct my_drv {
    struct notifier_block nb;             /* the observer "interface" part */
    int down_count;                       /* the observer's own state */
};

static int my_drv_event(struct notifier_block *nb, unsigned long event, void *ptr)
{
    struct my_drv *d = container_of(nb, struct my_drv, nb);   /* back to "this" */
    if (event == NETDEV_DOWN)
        d->down_count++;
    return NOTIFY_DONE;
}

That container_of line is what Java's implicit this does for you. An observer class is that enclosing struct: onStockChanged is called on the object, so it reads its own fields (user, sku) with no cast. The memory picture above shows both side by side.

From your world

The kernel offers several chain types, and they answer the questions interviewers ask about Observer. Atomic chains run callbacks in atomic context (they must not sleep) and are protected by a spinlock with RCU for the walk. Blocking chains use an rw-semaphore, so callbacks may sleep. Raw chains have no locking and the caller must provide it. SRCU chains suit callers that need sleepable read-side protection. That is the "thread safety while iterating observers" problem, solved four ways. Other observers you know: inotify and fanotify (watch a file, get events), and rtnetlink multicast groups like RTNLGRP_LINK that tools such as ip monitor join to hear about link changes from user space. The last one crosses a process boundary, which makes it closer to publish-subscribe.
