When to use it, when not to

Use it when
  • One change must trigger several independent reactions, and the set of reactions grows or changes at runtime.
  • The subject should not depend on the reacting modules (layering: domain core must not import SMS or analytics).
  • You are replacing polling ("is it back yet?") with notification.
Avoid it, or use something heavier, when
  • There is exactly one reaction that will always exist: a direct call is clearer.
  • Delivery must survive a crash, be retried or be replayed: you need a durable queue or log (a pub-sub broker, Kafka consumer groups), not an in-memory list.
  • The reactions must run as one transaction or in a strict order with rollback: use an explicit workflow (sagas and workflows).
  • Debuggability matters more than decoupling: event chains are hard to trace ("who changed this?").
