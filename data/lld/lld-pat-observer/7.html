The hard parts: leaks, threads, storms

1. The lapsed listener (unsubscribe leaks)

The subject holds a strong reference to every observer. If a screen, a session or a per-request object subscribes and never unsubscribes, it can never be garbage collected, and it keeps receiving events it no longer cares about. This is one of the most common memory leaks in GUI and long-running server code. Fixes, in order of preference:

  • Return a handle from subscribe (AutoCloseable, a Disposable, a Subscription) and close it in the owner's lifecycle (close(), onDestroy, try-with-resources). Making the handle visible makes forgetting it visible in code review.
  • Tie the subscription to a lifecycle (frameworks bind listeners to a component or scope and remove them automatically).
  • Weak references (WeakSet, WeakReference) as a safety net, not a design: cleanup timing then depends on the garbage collector.

2. Sync vs async delivery

Synchronous (call each observer in the subject's thread)Asynchronous (queue events, deliver on other threads)
OrderingSimple: list order, completes before setQty returnsPer-observer order only if each has its own queue
Latency of the subjectSum of all observers; one slow SMS call slows every stock updateConstant: enqueue and return
FailuresExceptions arrive in the subject's thread; catch per observerNeed error callbacks, retries, dead-letter handling
ConsistencyObservers see the state right after the changeState may have moved on; push an immutable event
FitsIn-process UI, small fast listeners, testsSlow listeners (network calls), many listeners, back-pressure needed

Java 9 added java.util.concurrent.Flow (Publisher, Subscriber, Subscription, Processor) as the standard interfaces for asynchronous observers with back-pressure, the same contract as the Reactive Streams specification. SubmissionPublisher is the JDK's ready-made publisher, delivering on an executor (the common fork-join pool by default).

3. Thread safety of the observer list

If one thread notifies while another subscribes, a plain ArrayList throws ConcurrentModificationException or worse. Options: CopyOnWriteArrayList (iteration uses a snapshot, see copy-on-write and concurrent collections; perfect when subscriptions are rare and notifications frequent); copy the list under a lock and notify outside the lock; or a concurrent queue per observer for async delivery. Never call observers while holding the subject's lock: an observer that calls back into the subject, or takes another lock, can deadlock you (the "open call" rule on the deadlock page).

4. Re-entrancy, cascades and storms

  • Re-entrancy: an observer changes the subject inside its callback, which triggers a new notification in the middle of the first. Guard with a "notifying" flag, queue the second change, or forbid it.
  • Cascades: observer A updates subject B whose observer updates C, and so on; a cycle loops forever. Keep the graph acyclic or deduplicate by version number.
  • Update storms: 1,000 price ticks per second, each repainting a chart. Coalesce (deliver the latest value at most every N ms) or batch.
  • Ordering assumptions: never rely on observer A running before B unless the API promises it (notifier chains promise priority order; most listener lists promise nothing).
