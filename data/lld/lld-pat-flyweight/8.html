When to use it, when not to

Use it when
  • You have a very large number of objects (tens of thousands and up) and memory or GC time is a measured problem.
  • Most of each object's state can be made extrinsic, leaving a small set of distinct intrinsic values (few styles, few QoS classes, few piece types).
  • The program does not depend on object identity for these objects (nobody does == to mean "same glyph at the same place").
  • The intrinsic part is naturally immutable (values, configuration, read-only assets).
Avoid it, or watch out, when
  • Objects are few. The factory and the split state are pure complexity for a 200-item list.
  • The state cannot be cleanly split, or the "shared" part needs to change per object. Mutable shared state is a bug factory: change one, change all.
  • Extrinsic state is expensive to recompute on every call; you may trade memory for CPU.
  • The pool grows without bound (one entry per user-supplied colour). Put a cap or use weak references, or the cache becomes a leak.
  • Many threads hit the factory: the pool needs a concurrent map or a lock, and the flyweights must be safely published (immutable objects with final fields are).

The classic bug this pattern creates is a comparison bug, not a memory bug: Integer values compared with == pass every test with small numbers and fail in production at 128. Compare values with equals() (Java) or == on values, never is (Python).
