The problem: a million copies of the same four fields

Here is the naive editor model. Every character is a full object:

class Glyph {                       // one per character in the document
    char ch;
    String font;                    // "Inter"
    int sizePt;                     // 12
    boolean bold;
    String color;                   // "black"
    int row, col;                   // where it is drawn
}

List<Glyph> doc = new ArrayList<>();
for (char c : bigText.toCharArray())
    doc.add(new Glyph(c, "Inter", 12, false, "black", r, col));   // same 4 style fields, again and again

It is simple and it works for a page of text. Then the document grows. Count the pains:

  • Memory grows with the number of characters, not with the number of distinct styles. A 500-page book has maybe five styles but millions of glyph objects, each with its own header and fields. In our Python measurement below, 100,000 style objects took about 7 MB; sharing three of them took under 1 MB.
  • GC and cache pressure. Millions of small objects mean more garbage-collector work and worse CPU cache use when you walk them.
  • Changing a style is expensive. "Make all headings blue" means touching every glyph that has heading style.
  • Wrong data in the wrong place. row and col depend on window width; storing them per glyph means recomputing and rewriting them on every resize.
