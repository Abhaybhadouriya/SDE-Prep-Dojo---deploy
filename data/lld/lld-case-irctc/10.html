Extensibility: the follow-ups

Follow-upChange
"Show me the DB schema" (Adobe, Zepto)station(code), train(no), route_stop(train_no, seq, station, km), berth(train_no, class, no, type, quota), booking(pnr, user, train_no, date, class, from_seq, to_seq, quota, fare), passenger_ticket(pnr, idx, name, status, berth_no, rac_slot, queue_pos). Availability for a berth: no ticket with the same berth, date and from_seq < :to AND to_seq > :from. Lock the journey with a row in journey(train_no, date, class) and SELECT ... FOR UPDATE.
Multiple coaches (B1..B10)Berth gets a coach id; describe() prints it. The allocator does not change; a picker may prefer keeping a PNR in one coach.
Keep a family togetherA GroupPicker that picks for the whole PNR at once (same bay first). The interface takes a list instead of one passenger.
Cancel one passenger, not the whole PNRcancel(pnr, passengerIdx): the inventory already releases per ticket; only the service API changes.
Unsold tatkal berths at chart timeA prepareChart() that moves unsold tatkal berths to the general quota and runs promote(); WL passengers still waiting are then cancelled and refunded.
More quotas (ladies, senior, foreign tourist)Quota grows; each quota has its own berths and waitlist. Allocation tries the passenger's quota, then falls back by a rule table.
Routes longer than 64 stopsReplace long with java.util.BitSet (or long[]); the AND / OR / AND NOT logic is identical.
Payment before confirmationAdd a HELD status with an expiry (the BookMyShow hold): allocate as HELD, confirm after payment, release on timeout, then promote.
Faster search ("multi-level indexing", Amazon)Index station to trains (done), then (station, day of week) to trains; precompute availability counts per journey and update them under the same lock so the search page never scans masks.
Many serversShard by journey (train + date). Each journey's bookings go to one owner (partitioned queue or a DB row lock); the catalogue is a read-only replica everywhere.
