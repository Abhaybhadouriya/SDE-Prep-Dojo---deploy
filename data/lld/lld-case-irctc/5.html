Key relationships and patterns (and why each)

Pattern / ideaWhereWhy hereWhat you say in the room
StrategyBerthPicker (preference + best fit, first free), FareRuleBerth assignment is a policy debate (preference? fragmentation? keep lowers for seniors?). Fares change with rules nobody codes in a round. Both swap without touching the allocator."Berth choice and fare are policies. The allocator calls picker.pick() and never knows which picker it has."
DecoratorTatkalSurcharge wraps DistanceFareSurcharges stack (tatkal, dynamic pricing, convenience fee) without a class per combination."Tatkal is a FareRule that holds another FareRule and adds to its answer, so surcharges stack in any order."
ObserverBookingListenerEvery status change (CNF to CAN, WL 1 to RAC 1) goes to SMS, email and the PNR-status page. Events are collected under the lock and delivered after it is released, so a slow SMS gateway never blocks booking."Events are queued under the lock and sent after it, so SMS latency never sits inside the tatkal queue."
State machineStatus of a PassengerTicket: WL to RAC to CNF, any to CANPromotion only ever moves "up"; cancellation is terminal. The legal moves are few, so an enum plus the allocator's rules is enough (see State for when to go further)."A ticket only moves up, WL to RAC to CNF, or to CAN. An enum plus the allocator's rules covers it."
One lock per aggregate (a monitor)JourneyInventoryAn aggregate is the cluster of objects that must change together, so one lock guards them all: here the masks, the RAC queue and the WL queue (a cancel touches all three). A monitor is an object whose methods all take the same lock, like Java synchronized. One lock around the whole aggregate is simple and correct; per-berth locks would not protect the queues."The unit of locking is the journey: train + date + class. Everything one cancel touches sits behind that one lock."
Inverted indexTrainCatalog.byStationAn inverted index (station -> trains), as in the Amazon version of the question ("reverse indexing"): look up both stations, intersect, then check the stop order. Search never scans all trains."Search is two set lookups and an intersection; cost grows with trains through those stations, not with all trains."
Bitmask value objectRoute.mask(i, j)A value object is immutable and compared by value, like a struct passed by value. Interval overlap becomes one AND. 64 stops fit in a long; longer routes use BitSet."A trip is a mask of segments. It fits a berth when the AND is zero."

Patterns we deliberately skipped: a Singleton ReservationService (it would hide the clock and the catalogue it depends on, and tests would share state), per-berth locks (they cannot protect the RAC and WL queues that one cancel changes together), the full State pattern with a class per ticket status (four statuses, and the allocator, not the ticket, decides each move), and inheritance such as TatkalBooking extends Booking (tatkal changes only the fare and the quota, and both are already strategies).

From your world

BerthPicker is a function-pointer slot, like the .get_unmapped_area hook a file system can supply: the core allocator stays the same, the placement policy is pluggable. The listener list is a notifier chain (blocking_notifier_call_chain): the kernel also refuses to call a blocking notifier while holding a spinlock, and we refuse to call listeners while holding the inventory lock for the same reason.
