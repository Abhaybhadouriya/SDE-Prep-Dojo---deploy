Concurrency: the 10:00 tatkal rush

At tatkal opening, thousands of requests arrive for the same train, date and class within the same second, and there are only a handful of tatkal berths. The race is the classic check-then-act (see booking concurrency): two threads both see "berth 5 free for NDLS-NGP", both OR their mask in, and berth 5 is sold twice. Step through the fix.

  1. Without mutual exclusion, two threads read the same free mask and both write. The berth is sold twice; the invariant checker in our demo would throw "berth sold twice".
  2. With one lock per JourneyInventory, T1 enters and does the whole check-and-allocate for all its passengers. Everybody else for this journey waits.
  3. A fair lock is FIFO among the threads already queued on the lock: the thread that started waiting first gets it next. That is arrival order at lock(), not request time: network delay and thread scheduling decide who reaches the lock first. Once the two tatkal berths are sold, the remaining 98 requests fail fast with REGRET.
  4. The lock key is train + date + class, so a rush on 12627 for the 10th never slows down bookings for the 11th or for another train.

Other shared state in our code

  • Inventory map: ConcurrentHashMap.computeIfAbsent so two first requests for a new journey create exactly one inventory (one lock), not two.
  • PNR numbers: an AtomicLong; PNRs are unique without a lock.
  • Listeners: a CopyOnWriteArrayList, and they are called after allocate/cancel return, outside the lock.
  • Tickets are mutated only under their inventory's lock; readers of describe() in the demo read after the threads have joined. In production, return an immutable snapshot from the service instead of the live ticket.
  • Clock: a volatile field in the manual test clock.

What "fair" can and cannot promise. ReentrantLock(true) is FIFO among threads already queued on the lock. If the requirement is "earliest request wins", stamp a sequence number at ingress (the API gateway) and serialise per journey in that order (a single-threaded actor or one partition per journey). And never call the untimed tryLock() on a fair lock: it barges ahead of the queue even when fairness is on; use tryLock(0, TimeUnit.SECONDS) if you need a non-blocking attempt that respects fairness.

From your world

The fair lock is a ticket lock: the kernel replaced plain test-and-set spinlocks with ticket spinlocks so that CPUs get the lock in the order they asked, because the unfair version starved some CPUs under contention. Since Linux 4.2 mainline uses the queued spinlock (qspinlock, built on an MCS queue), which keeps FIFO order without every CPU spinning on one cache line. Partitioning by journey is like per-CPU or per-queue locks on a NIC driver: no global lock, each queue serialised on its own.
