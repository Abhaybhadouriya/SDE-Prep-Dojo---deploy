Interview follow-ups

How do you let one seat be sold to A for station 1 to 2 and to B from station 3 onward?

Number the stops 0..n-1; segment i is stop i to stop i+1. A trip from stop a to stop b occupies segments a..b-1, a half-open interval. Each berth stores a bitmask of sold segments. The trip fits when (occupied & mask(a, b)) == 0; booking ORs the mask in, cancelling clears it with AND NOT. In SQL, the same check is "no ticket on this berth and date with from_seq < :b AND to_seq > :a".

How to answer

Define segment and the half-open interval first, then the bitmask, then the SQL form. Draw the chart.

Likely follow-ups
  • What if a route has 120 stops? (BitSet or long[].)
  • How do you pick among several free berths?
Several berths fit a short trip. Which one do you give, and why does it matter?

If you give a short trip an empty berth, you may cut it in the middle and later have no berth that fits a full-length trip, even though total free capacity is enough: fragmentation. Best fit gives the berth that is already busiest on other segments (most bits set), keeping empty berths whole for long trips. Preference (lower berth) is checked first. It is a BerthPicker strategy, so the business can change the policy; our demo shows Bob landing on Alice's berth because of it.

How to answer

Name fragmentation, compare first-fit and best-fit like a memory allocator, and say it is pluggable.

Likely follow-ups
  • Is best fit optimal? (No; optimal offline assignment is interval scheduling / colouring, but bookings arrive online.)
Thousands of users hit tatkal at 10:00. How do you stop double booking and stay fair?

All mutable state of one journey (train, date, class) is in one object guarded by one fair lock. Inside the lock we only do in-memory bit work, so each request takes microseconds; validation, fare and notifications happen outside. A fair lock serves waiters in arrival order. Different journeys have different locks. When scaled out, route each journey to one owner (partition key = train+date) so the same serialisation holds across servers, or use a DB row lock on the journey.

How to answer

Check-then-act race, unit of locking, critical section size, fairness, then the distributed version.

Likely follow-ups
  • Why not per-berth locks? (Queues and multi-passenger PNRs.)
  • How would you protect the system from bots? (Rate limiting, captcha, a virtual waiting room - outside the LLD core.)
How do you find trains between two stations quickly ("reverse indexing")?

Keep a map from station code to the set of trains that stop there. For a query (A, B), intersect the two sets (iterate the smaller one), then keep trains where A's stop index is before B's in that train's route. Each route also keeps a map station to index, so that check is O(1). Add day-of-week or date into the key for "runs on" filtering, and precompute availability counts so the result page does not touch inventories.

How to answer

Inverted index, intersection, direction check, then what you would cache.

Likely follow-ups
  • Journeys with one change of train? (Graph search over the index, bounded by time.)
Walk me through what happens when a confirmed passenger cancels.

Under the journey lock: clear their segments from their berth, mark them CAN, then promote. RAC queue first, in order: each RAC passenger who now fits a full berth gets it and frees their RAC half. Then the waitlist in order: each WL passenger gets a berth if one fits, else an RAC half if one fits. Passengers who do not fit are skipped, not blocking later ones. Recompute RAC and WL numbers. Collect every status change as an event, release the lock, then notify.

How to answer

Order of queues, skip rule, renumbering, notifications outside the lock. Mention the invariant "no waiting passenger fits a free place".

Likely follow-ups
  • Can one cancellation cause a chain of promotions? (Yes: a RAC upgrade frees a half, which a WL passenger takes.)
Four passengers on one PNR, but only three places are left. What do you do?

Ask. Our default is all-or-nothing per PNR: place passengers one by one, and if one cannot get even a WL place, release every passenger already placed and throw REGRET. Within a successful PNR, passengers can end with different statuses (2 CNF + 2 RAC), which matches how Indian Railways shows it. A partial-booking option would be a flag, not a different algorithm.

How to answer

Clarify, choose, show the rollback, test it (our scene 4).

Likely follow-ups
  • Keep the group in one coach or bay?
Design the tables. How does the availability query look?

Catalogue tables: train, station, route_stop (train, seq, station, km), berth (train, class, no, type, quota). Booking tables: booking (pnr, train, date, class, from_seq, to_seq, quota, fare, user) and passenger_ticket (pnr, idx, name, status, berth_no, rac_slot, queue_pos). A berth is free for (a, b) if no CNF ticket for that train/date/berth has from_seq < b AND to_seq > a. Count free berths with a NOT EXISTS subquery; index passenger_ticket on (train, date, class, berth_no). For writes, lock the journey row with SELECT ... FOR UPDATE, then run the allocation in one transaction.

How to answer

Separate catalogue from bookings, show the overlap predicate, name the index and the locking statement.

Likely follow-ups
  • How do you keep counts fast? (A per-journey summary row updated in the same transaction.)
Why is a notification sent after releasing the lock, and what can go wrong?

An SMS gateway can take seconds or hang. Calling it under the journey lock would make every other booking for that train wait, the worst possible moment being tatkal opening. So the allocator returns a list of events and the service calls listeners after unlocking. The risk is ordering and loss: two quick changes could be delivered out of order, and a crash after commit but before notify loses the SMS. Fix with a sequence number per ticket and an outbox table (write the event in the same transaction, a worker sends it).

How to answer

Lock scope, then the at-least-once outbox.

Likely follow-ups
  • How do you make SMS sending idempotent?
How would you scale this beyond one server?

The natural shard key is the journey (train + date), because every booking and cancel touches exactly one journey and journeys never interact. Route requests by that key to one owner: a partition of a log consumed by one worker, or a DB where the journey row is the lock. The catalogue is read-mostly, so cache it everywhere. Search reads precomputed availability, which can be slightly stale; the booking itself is always checked by the owner.

How to answer

Find the aggregate, shard by it, keep reads cheap and possibly stale, keep writes serial per aggregate.

Likely follow-ups
  • A hot journey on festival days? (Still one owner; it is a small amount of bit work, so one core goes a long way.)
Where do you put tatkal rules so they do not spread everywhere?

Three places, each small: the opening time is a function of the class and journey date read from an injected clock (in the service); the extra price is a TatkalSurcharge decorator around the base fare; the berths are tagged with a quota and the allocator only gives tatkal berths to tatkal requests. Nothing else knows tatkal exists. A new "premium tatkal" with dynamic pricing is a new fare decorator.

How to answer

Time, price, inventory: one mechanism each.

Likely follow-ups
  • Test "before 10:00" without waiting? (ManualClock.)
