Clarify requirements

Functional (P0)

  1. Catalogue Trains have a number, a route (ordered stops with distance) and classes (3A, SL...). Each class has berths of a type (lower, middle, upper, side-lower, side-upper).
  2. Search Trains between two stations, in the right direction.
  3. Availability For a train, date, class and segment: free berths, RAC places left, waitlist number.
  4. Book 1 to N passengers on one PNR (booking id). Each passenger gets CNF, else RAC, else WL; if even WL is full the whole request is refused ("REGRET"). All passengers placed, or none.
  5. Seat reuse A berth booked for part of the route can be sold for the other part.
  6. Cancel Cancelling frees the passenger's segments, then RAC passengers are confirmed and waitlisted passengers promoted, in booking order.

Functional (P1)

  • Tatkal: a separate berth quota that opens one day before the journey (AC classes at 10:00, non-AC at 11:00), with a surcharge and a smaller passenger limit.
  • Berth preference (lower for a senior citizen), fares by distance, notifications on every status change.

Non-functional

  • No berth sold twice for the same segment, ever, under any interleaving.
  • Fairness: at tatkal opening, requests are served in arrival order; nobody is starved.
  • No missed promotion: after a cancel, no RAC or WL passenger may stay waiting while a place that fits them is free.
  • Isolation: two different trains or dates never block each other.
  • Testable time: tatkal windows read an injected clock.

Out of scope

  • Payment (assume paid before book, or see the hold pattern in BookMyShow), real fare tables and refund rules, multiple coaches per class (one coach "B1" here, the code works for any berth list), login, chart preparation, distributed deployment (discussed, not built).
