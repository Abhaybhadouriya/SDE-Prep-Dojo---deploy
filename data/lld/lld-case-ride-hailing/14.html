Interview follow-ups

How do you guarantee a driver is never assigned to two riders?

Make "check free and take" one atomic step on the driver: status.compareAndSet(AVAILABLE, ON_TRIP). Searching and ranking read a snapshot without locks; only the claim is atomic. A thread that loses the CAS moves to its next candidate. I prove it with a test: 40 threads behind a latch, 5 drivers, assert exactly 5 trips with 5 distinct drivers.

How to answer

Name the race (check-then-act), give the atomic fix, show the test. Mention the lock-based alternative and why CAS fits.

Explain your driver allocation algorithm. How does it scale to 100,000 drivers?

Candidates = available drivers of the right type within a radius; rank them with the strategy (nearest first, or a weighted score); claim the first with CAS, fall back down the list. Scanning all drivers is O(N); at scale, keep a grid or geohash index of driver locations updated on each ping, and search the pickup cell and expanding rings of neighbours until there are k candidates. Ranking is then over tens of drivers, not thousands.

How to answer

Correct version first, then the index, then the ring expansion.

Likely follow-ups
  • Distance or ETA? (ETA is better; same strategy interface, a routing service behind it.)
  • How often do drivers send location, and how do you avoid stale cells?
Model the trip lifecycle. State pattern or enum?

An enum plus a transition table (canMoveTo) and one moveTo that validates and notifies. That is enough while states only gate transitions. When states gain behaviour (a cancel fee that differs by state, timeouts per state, different fare logic), move to the State pattern: one class per state implementing cancel(), start(), end(), each returning the next state.

How to answer

Draw the diagram first, then say which implementation and when you would switch.

Likely follow-ups
  • Add DRIVER_ARRIVED and NO_SHOW. What changes?
The driver must accept the request. Design the offer flow with a timeout.

Reserve the top candidate (CAS AVAILABLE to OFFERED), send the offer, schedule a timeout. On accept: CAS OFFERED to ON_TRIP and move the trip to DRIVER_ASSIGNED. On reject or timeout: CAS OFFERED back to AVAILABLE and offer the next candidate. Both accept and timeout race; the CAS decides which wins, so a late accept after a timeout fails cleanly. Cap the number of offers and fail the request after that.

How to answer

Add one state, reuse the CAS, and name the accept-vs-timeout race.

Likely follow-ups
  • Offer to 3 drivers at once? (First accept wins by CAS; release the others.)
How do you add surge pricing without touching the fare code?

SurgeFare is a decorator: it holds any FareStrategy and multiplies its result. Discounts and taxes are more decorators. The multiplier comes from a provider per zone and time. Quote the fare at request time and store it on the trip, so a surge change mid-ride does not surprise the rider.

How to answer

Decorator, provider, quote-and-store.

Likely follow-ups
  • Order of decorators: surge before or after discount?
Why does the matching strategy return a list instead of one driver?

Because the best driver can be taken by another thread between ranking and claiming. With a ranked list the service just tries the next one. A single-driver API forces a global lock around "pick and claim" or a retry loop that re-ranks everything.

How to answer

Connect the API shape to the concurrency design.

Likely follow-ups
  • How long should the list be?
What if pushing the trip event to Kafka fails?

This is the HLD question Uber candidates report. In-process: listeners run after the state change; a failing listener must not undo the trip. For a durable event, write the trip change and an "outbox" row in the same transaction, and let a relay publish to Kafka with retries; consumers dedupe by trip id and version. If publishing keeps failing, park the event in a dead-letter topic and alert.

How to answer

Separate the source of truth (trip state) from notification; name the outbox pattern.

Likely follow-ups
  • At-least-once vs exactly-once for receipts?
Why is Driver separate from Rider? Should both extend User?

They share only identity fields. A driver has cab, location, status and rating; a rider has payment methods and history. Inheritance would force both through one base class that changes for either reason. Prefer composition: both have a Profile. If one person can be both, they have two roles linked to one account.

How to answer

Composition over inheritance, with the "one person, two roles" case.

Likely follow-ups
  • Where does the driver's vehicle go if a driver can switch cars?
Location updates arrive every 4 seconds from every driver. Does that break your locking?

No. Location is a volatile reference to an immutable Location, so writers just swap it and readers always see a whole value. Matching may use a location a few seconds old, which is acceptable. Status changes, which must be exact, go only through CAS. With a geo index, moving a driver between cells is the one compound update; do it with per-cell concurrent sets, and accept that a driver may briefly appear in two cells (the CAS still prevents double booking).

How to answer

Separate "eventually fresh" data (location) from "must be exact" data (status).

Likely follow-ups
  • How would you throttle updates from a stationary driver?
Walk me through what happens when a rider cancels.

trip.moveTo(CANCELLED) validates (only from REQUESTED or DRIVER_ASSIGNED), listeners fire, then the driver is released (ON_TRIP to AVAILABLE) and the rider removed from the busy set. If the driver pressed "start" at the same moment, one of the two synchronized moveTo calls loses and throws. A cancellation-fee policy can be a strategy called here.

How to answer

Validate, change state, release resources, mention the race.

  • Who pays when the driver cancels?
