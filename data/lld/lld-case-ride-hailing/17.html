Quiz

Two threads both see driver p1 as AVAILABLE. What prevents both from booking p1?

  1. Sorting candidates by distance
  2. Making the drivers map a ConcurrentHashMap
  3. An atomic compare-and-set from AVAILABLE to ON_TRIP on the driver
  4. Checking status twice
The concurrent map makes map operations safe, not the check-then-act on a driver's status. Only an atomic claim (CAS or a lock around check and set) does.

A rider tries to cancel a trip that is IN_PROGRESS. What should happen in our design?

  1. The state machine rejects it
  2. The trip is cancelled and the driver released
  3. The fare is set to zero
  4. It silently does nothing
IN_PROGRESS can only move to COMPLETED. Rejecting loudly is better than ignoring.

Which pattern fits "surge multiplies whatever the normal fare is"?

  1. Singleton
  2. Factory method
  3. Observer
  4. Decorator
SurgeFare wraps another FareStrategy and changes its result, so surge, discounts and taxes can be stacked.

Why does DriverMatchingStrategy return a ranked list?

  1. To print all drivers
  2. So the service can fall back when its first choice was claimed by another request
  3. Because Java cannot return one object
  4. To sort by rating
The list is the fallback path for a lost CAS, with no global lock.

At the end of a trip, in which order should we update the driver?

  1. Release, then move to drop
  2. It does not matter
  3. Move to drop, then release
  4. Release, compute fare, then move
Once released, the driver can be matched immediately; their location must already be correct.

Matching scans all 100,000 drivers per request. The best first improvement is:

  1. A bigger thread pool
  2. A grid or geohash index of driver locations, searched in rings around the pickup
  3. Caching the last result for every rider
  4. A global lock
The index cuts the candidate set to the neighbourhood; the strategy then ranks a few dozen drivers.
