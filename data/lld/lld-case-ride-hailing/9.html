Concurrency and thread safety

Uber's round reports say this part decides the verdict, so know the three races and how each is closed.

  1. Both request threads look at p1 in their snapshot and see AVAILABLE. If each then writes "assigned", p1 gets two trips: the check-then-act race.
  2. The guard: Driver.tryReserve() is one compareAndSet(AVAILABLE, ON_TRIP) on an AtomicReference (atomic_cmpxchg in kernel terms). Exactly one thread wins it. If any later step fails, the winner calls release().
  3. The loser's CAS returns false because the value is already ON_TRIP. It does not wait for p1; it moves to its next ranked candidate, and with none left it throws NoDriverAvailable and frees its rider.

Why not just synchronize requestRide?

A single lock around the whole request is correct and is a fine first answer. It serialises every booking in the city, though, and the interviewer will ask how it scales. The CAS design keeps the slow parts (scanning, sorting by distance) lock-free and makes only the claim atomic. If the interviewer prefers locks, use one lock per driver (or per geo cell) and say the trade-off: pessimistic locks block, optimistic CAS retries. More on this choice: preventing double booking and atomics and CAS.

From your world

"Read without a lock, then claim with one atomic instruction, retry on failure" is exactly how lock-free kernel code works: walk an RCU-protected list, pick an entry, then cmpxchg its state. A stale read is harmless because the claim re-checks it. The listener calls are another kernel lesson: do not call slow callbacks while holding a lock you need on the hot path; in production you would hand trip events to a queue (producer-consumer).

Scaling the matcher

Scanning all drivers is O(N) per request. Fine for the round; at 100,000 drivers, index them by location. Divide the city into grid cells (or geohash / H3 hexagons), keep Map<cellId, Set<Driver>> updated on every location ping, and search the pickup cell plus its neighbours, widening the ring until you have enough candidates. The strategy interface does not change; only the candidate source does. The HLD side is in geo and proximity queries and geospatial indexes.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • Condition.await / awaitNanos, wait / notifyAll = pthread_cond_wait / pthread_cond_timedwait; always recheck the predicate in a while loop because of spurious wake-ups, as wait_event() does.
  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • CopyOnWriteArrayList = an RCU-style list: readers walk a snapshot with no lock, writers copy the array and publish it; good for read-mostly listener sets.
  • CountDownLatch / Barrier = struct completion: threads wait until a count reaches zero (the tests use it to release all threads at once).
  • ExecutorService = a thread pool with a work queue, like a kernel workqueue.
  • Python threading.Lock = a plain mutex; with lock: is lock and unlock on every exit path.
