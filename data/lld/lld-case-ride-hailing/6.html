Core flow: requesting a ride, with a race

The most important flow is not the happy path. It is two riders asking for the last PREMIUM cab at the same moment. Step through it:

  1. Two threads call requestRide at the same moment. Each first adds its rider to the busy set (so the same rider cannot double-request).
  2. Each thread takes a snapshot of nearby available drivers of the right type. Both see p1 as available. The snapshot is only a suggestion; it can be stale a microsecond later.
  3. The matching strategy ranks the candidates (nearest first here). This part needs no lock at all.
  4. Each thread tries tryReserve() on its first choice: a compare-and-set from AVAILABLE to ON_TRIP. Exactly one wins. This is the only step that must be atomic.
  5. The winner creates the Trip, moves it to DRIVER_ASSIGNED (listeners fire, after the trip lock is released) and returns it. If anything after the CAS throws, a catch calls d.release() and rethrows: release on failure, or the driver would stay ON_TRIP forever. It is the same discipline as the parking lot's plate-claim undo.
  6. The loser moves to its next candidate. With none left it throws NoDriverAvailable and removes its rider from the busy set so the rider can retry.

Ending a trip

  1. Price first fareRule.fare(cab, km, minutes): 60.00 base + 14.00 x 10 km + 1.50 x 25 min = 237.50 for a SEDAN.
  2. Then change state trip.complete(fare) checks the move (it throws unless the trip is IN_PROGRESS) and stores the fare and COMPLETED in one critical section. Only after leaving it does it notify the listeners. Order matters: if COMPLETED fired before the fare was set, a receipts listener would print a fare of 0. The demo has a receipts observer that checks exactly this.
  3. Free the driver Move the driver to the drop location, then release() (ON_TRIP to AVAILABLE). Order matters: if you release first, a new request could match the driver at the old pickup location.
  4. Free the rider Remove the rider from the busy set.
