Interview Q&A

Your code has if (logger != null) in twenty places. How do you clean it up?

Make the logger a required constructor dependency and pass a NullLogger (implements Logger, does nothing) when logging is off. All twenty checks disappear, and a forgotten check can no longer throw. The choice "logging on or off" moves to one place: the composition root.

How to answer

Name the pattern, show the two-line class, say where it is wired.

Likely follow-ups
  • Why not make the logger field Optional<Logger>? (Optional is meant for return values; as a field it just moves the check.)
Null Object vs Optional: when do you use which?

Null Object when absence has a harmless default behaviour and callers should not care: policies, loggers, observers, empty collections. Optional when absence is information the caller must act on: a lookup that may fail, where one caller throws, another uses a default, another skips. A repository returns Optional; the service that knows the meaning converts it.

How to answer

"Who decides what absence means?" is the deciding question. Give one example of each.

Likely follow-ups
  • Can Optional be a null itself? (Yes, if you are careless; never return a null Optional.)
What is the danger of the Null Object pattern?

It can hide real failures. If an unknown customer id silently becomes a guest during a refund, money goes nowhere and no error is raised. Use it only where doing nothing is genuinely correct, keep a way to tell (an isGuest() or a metric counting fallbacks) for the few places that must know, and log when a fallback happens in surprising places.

How to answer

One concrete bad case, then the guard rails.

Likely follow-ups
  • If callers check isGuest() everywhere, what went wrong? (The design leaks; move the behaviour into the guest class.)
Should a method that returns a list ever return null?

No. Return an empty list (Collections.emptyList() or List.of()). The empty list is the null object for collections: loops run zero times, size() is 0, streams are empty. Callers never need a null check, and "no results" is a normal, typed answer.

How to answer

Short rule plus the JDK method name.

Likely follow-ups
  • Why can't you add to Collections.emptyList()? (It is immutable and shared.)
Why is a null object usually a singleton, and is that safe?

It has no state, so every instance would be identical; sharing one saves allocations and allows identity checks if ever needed. It is safe precisely because it is immutable and stateless: there is nothing for threads or callers to corrupt. If a "null" class needs state, it is no longer a null object but a special case, and should be created per use.

How to answer

Stateless + immutable = shareable. Mention an enum constant in Java as the simplest safe singleton.

Likely follow-ups
  • Compare with the Flyweight idea of sharing.
In C, ops tables often allow NULL members. What are the trade-offs versus filling them with no-op functions?

NULL members keep tables small and let the core apply a default or return an error code (for example "operation not supported"), but every call site must test the pointer, and a missed test is a crash. A no-op function (like noop_llseek) makes calls unconditional and removes that class of bug, at the cost of an indirect call and of hiding the fact that the operation is unsupported. Use no-ops when "nothing" is correct behaviour; use NULL plus an explicit error when the caller must learn that the feature is missing.

How to answer

Map it onto Null Object vs Optional: the same question in C.

Likely follow-ups
  • How does C++ give you this for free? (A base class with default virtual implementations.)
