When to use it, when not to

Use it when
  • "Absent" has an obvious, harmless meaning: no discount = 0, no logger = silent, no observers = nobody notified, no results = empty list.
  • The same null check is repeated in many places.
  • You own the interface and can add the null class next to the real ones.
  • An optional collaborator (logger, metrics, notifier, observer) is injected and may be switched off.
Avoid it when
  • Absence is an error the caller must handle: an unknown account for a payment, a missing config value, a seat that does not exist. Use Optional or throw.
  • A silent no-op would hide a bug. Fowler warns that null objects can make errors look like normal execution.
  • The interface has methods that return values with no sensible neutral (what is the "null" balance of a bank account?).
  • Callers keep asking isNull() everywhere; then you have only renamed the null check.

A practical rule: repositories return Optional (they do not know whether absence is an error); services and factories that know the meaning turn it into a null object or an exception. Our Repository page uses exactly this split.
