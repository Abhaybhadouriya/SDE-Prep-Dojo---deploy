The state machine (step through it)

  1. The happy path: a card moves IDLE to CARD_INSERTED; a correct PIN moves to AUTHENTICATED, where balance and withdraw are allowed.
  2. Withdraw enters DISPENSING for the duration of the money movement and always returns to AUTHENTICATED, whether it succeeded or failed, so the customer can try a smaller amount.
  3. The ways out: eject the card from CARD_INSERTED or AUTHENTICATED, or lose the card on the third wrong PIN. All go back to IDLE.
  4. OUT_OF_SERVICE is entered when a session ends and the cash is below the minimum, and left only by an operator refill. It accepts no user action at all, which the interface's default methods give us for free.

The note chain: greedy, then back off (step through it)

  1. The request enters the head of the chain, the 2000 handler. 600 is smaller than 2000, so it takes nothing and passes all 600 on.
  2. The 500 handler takes one note and passes 100. The 200 handler cannot use 100 and passes it on.
  3. The 100 cassette is empty. The tail returns "impossible". A plain greedy chain would now refuse the withdrawal, even though 3 x 200 works.
  4. So each handler tries again with one note fewer: the 500 handler takes zero and passes 600; the 200 handler takes three; done. With 4 or 5 denominations and a cap of 40 notes, this search is tiny. Only after a plan is found do we take the notes out of the counts.

From your world

State in C is a pointer to a table of function pointers that you swap: atm->ops = &authenticated_ops;, and every event calls atm->ops->withdraw(atm, amount). A Java interface with default methods is that table with a "return -EINVAL" in every slot you do not fill. Chain of Responsibility is the netfilter hook list: each registered hook returns NF_ACCEPT to pass the packet on or a verdict to stop. Adapter is the compat_ioctl layer: 32-bit user structs come in, it converts them to the 64-bit kernel layout and calls the real handler; neither side knows about the other.

Where this breaks: a netfilter hook never goes back and asks an earlier hook to change its verdict. Our note chain does (the backtracking), which is why each handler returns a plan instead of acting immediately. Plan first, commit later.

Why the pattern earns its place: the if-ladder it replaces

Without the State pattern, withdraw (and every other action) starts with a switch on the session state:

Receipt withdraw(long amount) {
    switch (state) {
        case IDLE:           throw new InvalidOperationException("insert a card first");
        case CARD_INSERTED:  throw new InvalidOperationException("enter your PIN first");
        case AUTHENTICATED:  state = DISPENSING; return dispense(amount);
        case DISPENSING:     throw new InvalidOperationException("busy");
        case OUT_OF_SERVICE: throw new InvalidOperationException("out of service");
    }
}
void insertCard(String c) { switch (state) { /* five more cases */ } }
void enterPin(String p)   { switch (state) { /* five more cases */ } }
interface AtmState {
    default Receipt withdraw(Atm atm, long amount) { reject("withdraw"); return null; }
    default void enterPin(Atm atm, String pin) { reject("enter PIN"); }
    ...
}
final class AuthenticatedState implements AtmState {
    public Receipt withdraw(Atm atm, long amount) { ... atm.moveTo(new DispensingState(...)); ... }
}
synchronized Receipt withdraw(long amount) { return state.withdraw(this, amount); }

With the switch, the follow-up "add a DEPOSIT_PENDING state" edits every action method. With State it is one new class plus the transition in the state that leads to it; Atm itself is unchanged.

struct atm_state_ops {

    int (*enter_pin)(struct atm *a, const char *pin);

static const struct atm_state_ops idle_ops = { .insert_card = idle_insert, .enter_pin = reject_pin, .withdraw = reject_withdraw };
/* a->ops->withdraw(a, amount, &r); moving state = a->ops = &authenticated_ops; */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
