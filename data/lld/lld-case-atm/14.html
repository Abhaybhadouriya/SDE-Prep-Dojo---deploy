Interview follow-ups

Why use the State pattern here instead of an enum and a switch?

With an enum, every action method starts with a switch over every state, so the rules for one state are spread across five methods, and adding a state means editing all of them. With State classes, each state's rules are in one class, the interface's defaults reject everything that is not allowed, and a new state is a new class. For a tiny machine (three states, two events) an enum with a transition table is fine and simpler; say so.

How to answer

Give the cost of the switch (scattered rules, Open/Closed broken), then the honest counterpoint for small machines.

Likely follow-ups
  • Where do transitions live, in the states or in the context? (In the states here; a table in the context is the alternative.)
  • State versus Strategy? (Same shape; a state changes itself, a strategy is chosen from outside.)
Dispense 600 from 2000x1, 500x1, 200x4 and no 100s. Your greedy chain fails. Fix it.

Let each handler return a plan instead of acting: take as many notes as possible, ask the next handler to cover the rest, and if it cannot, retry with one note fewer, down to zero. Only when the head returns a full plan do we subtract the notes. With 4 or 5 denominations and a cap of about 40 notes per withdrawal, the search is a few hundred steps at worst. A coin-change DP over amount/100 also works and gives the fewest notes, but it is more code for no gain at this size.

How to answer

Show the failing trace first (500 then stuck at 100), then the one-line change: loop the count down instead of taking the maximum once.

Likely follow-ups
  • Is greedy ever optimal? (For canonical systems like 2000/500/200/100 with unlimited notes, yes; limited counts break it.)
The bank debited the account but the cash did not come out. What happens?

The dispenser reports a fault, so the ATM sends reverse(txnId) with the same id it used for the debit and puts the reserved notes back in the counts. The customer sees a REVERSED receipt. If the reversal cannot be sent (network down, power cut), the ATM's journal still records "debit approved, eject failed", and it sends the reversal when it can; the bank also reverses on its own if no completion arrives in time. In India the RBI sets T+5 days as the limit for this kind of failure.

How to answer

Name it a compensating transaction, stress the same id, and mention the journal for the case where the ATM itself dies.

Likely follow-ups
  • Some notes came out and then it jammed? (Count what came out via sensors, reverse only the rest, flag for reconciliation.)
Why reserve notes before calling the bank, and why debit before ejecting?

Order the steps so every failure is cheap to undo. Reserving notes is local and free to undo, so it goes first: if we cannot pay the amount out, we never bother the bank. The debit goes before the eject because cash that has left the machine cannot be pulled back, while a debit can be reversed. Do it the other way round and a failed debit means free money for the customer.

How to answer

Say the rule "do the reversible steps first, the irreversible step last" and apply it to the three steps.

Likely follow-ups
  • What does a refill thread see while notes are reserved? (Reduced counts; the reservation is real.)
Where does the Adapter pattern fit, and what does it buy you?

The ATM is written against BankService: rupees, enums, plain methods. The bank's library (or the network switch) speaks paise, two-character response codes like "51" for insufficient funds, and hashed PIN blocks. CoreBankingAdapter implements the first on top of the second. Changing banks, or testing with a fake, never touches the ATM code, and all the unit conversion bugs live in one small class.

How to answer

Name the two interfaces and one concrete conversion (paise, a response code). Then the testing benefit.

Likely follow-ups
  • Adapter versus Facade? (Adapter converts one interface to another; Facade simplifies many into one.)
  • Many banks? (A router choosing an adapter by card prefix.)
The debit request timed out. Do you retry? What stops a double debit?

Retry with the same transaction id. The bank stores ids it has posted and answers a repeat with the original result without debiting again. That makes the operation idempotent, so "at least once" delivery gives "exactly once" effect. The id must be unique across all ATMs: we prefix it with the ATM id, after a real bug where two ATMs both sent "T1" and the second withdrawal was never debited.

How to answer

Say "idempotency key", show where it is stored and checked (inside the same lock as the debit), and explain uniqueness.

Likely follow-ups
  • How long does the bank keep ids? (At least as long as any retry or reversal can arrive.)
One ATM serves one customer. Where is the concurrency?

Three places: the operator refilling or shutting down while a customer is mid-session (lock the ATM's public methods and the dispenser); many ATMs debiting one account (the bank must check and debit atomically); and network retries (idempotent debit and reversal). Our demo runs 20 ATMs against one joint account of 10,000 and gets exactly 10 approvals and a balance of 0.

How to answer

Refuse the premise politely, then list the three with one fix each.

Likely follow-ups
  • In SQL? (UPDATE account SET balance = balance - :amt WHERE id = :id AND balance >= :amt, check rows affected.)
How would you add deposit and change-PIN without breaking existing code?

Add deposit and changePin to AtmState as default methods that reject. Only AuthenticatedState overrides them, so every other state is unchanged and still safe. Add matching methods to BankService and the adapter. If transaction types grow further, move to a Transaction hierarchy with a template method (validate, authorize, execute, receipt) so the state just runs a transaction object.

How to answer

Point at the default methods: that is the reason the interface was written that way.

Likely follow-ups
  • Deposit needs a new state? (Yes, COUNTING_CASH while the machine counts notes.)
Should the ATM be a Singleton?

No. A bank has thousands of ATMs, and even in one process the demo creates several (ATM1, ATM2, 20 joint-account ATMs). A Singleton would also make tests share state. Create ATMs in main and pass in the bank and dispenser (dependency injection). If anything is shared, it is the bank service, and that is shared by passing the same instance, not by a global.

How to answer

Short no, one reason from the domain, one from testing.

Likely follow-ups
  • When is a Singleton right? (A true process-wide resource such as a config registry, and even then prefer injection.)
Where do the PIN and the 3-tries rule live, ATM or bank?

The PIN check is the bank's: the ATM sends a hashed PIN block, never the clear PIN, and the bank compares. The try counter is in both places for different reasons: the ATM counts per session so it can retain the card on the third failure, and the bank counts per card across all ATMs so an attacker cannot try two PINs at each of many machines. Our ATM retains the card and tells the bank to block it.

How to answer

Split "session rule" from "account rule"; mention that real PIN handling uses hardware security modules.

Likely follow-ups
  • Unblocking a card? (A bank-side flow, not an ATM state.)
