Follow-up questions from all three mocks

Practise these aloud after each mock. Filter by company or level.

Package delivery: a non-Prime package keeps getting pushed back by Prime ones. Fix it.

That is starvation. Add aging: the queue's priority becomes a score from both Prime status and waiting time, for example "Prime adds a fixed bonus; every 10 minutes waiting adds one point". Because the queue already takes a comparator, only the comparator changes. Mention that a score that changes over time needs the heap to be rebuilt periodically, or a bucketed queue per priority level checked in order.

How to answer

Name the problem (starvation), the classic fix (aging), and where it lands in your code (one comparator).

Likely follow-ups
  • How would you test it? (Inject a clock; advance time; assert order.)
Package delivery: why is Status an enum with canMoveTo and not the State pattern?

Because the states differ only in which moves are legal, not in behaviour. A transition table is the smallest correct thing. If states start to carry behaviour (OUT_FOR_DELIVERY sends live location; ATTEMPT_FAILED schedules a retry), each state becomes a class with its own handler methods: that is the State pattern. Say both, and the trigger for switching.

How to answer

Start simple and name the trigger for the heavier pattern. See State and state diagrams.

Likely follow-ups
  • Where would you put "notify customer on each status change"? (An observer on the transition.)
Package delivery: scale it to 10,000 agents across many cities.

Partition by city or zone: one dispatcher (and one queue) per zone, so locks never cross zones. Choosing the nearest free agent needs a spatial index (geohash buckets or a grid) instead of scanning a list. Moving past one process: agent state in a store with conditional updates, packages as events on a queue per zone. In an LLD round, stop at the class boundary: "the AssignmentStrategy takes a candidate list from an AgentLocator; that locator is where the spatial index goes".

How to answer

Show which class absorbs the scale change, then name the HLD ideas briefly. See ride hailing.

Likely follow-ups
  • What if an agent's app goes offline mid-delivery? (heartbeats with a timeout; after the lease expires, mark the agent unavailable and re-queue the package as an attempt that did not finish)
Bug bounty: add an ON_HOLD status reachable from REPORT_REVIEW.

One new enum constant, one new edge in next() (REPORT_REVIEW to ON_HOLD, ON_HOLD back to REPORT_REVIEW), done. Services, repositories and the driver do not change; add a line to the driver to demo it. That is the payoff of keeping the transition rule in one table.

How to answer

Say the number of files touched before you touch them, then do it live.

Likely follow-ups
  • Different transition rules per product team? (Make the table data: a Workflow object per team.)
Bug bounty: your AuthService has one logged-in user. What breaks with two users at once?

The current user is global, so two concurrent sessions overwrite each other. That was a stated assumption for the demo; the fix is to pass the caller explicitly (changeStatus(userId, bugId, next)) or a session token per call, and keep AuthService to validate the token. Admitting the shortcut and its fix is better than hiding it.

How to answer

Own the assumption, give the fix, estimate the change (signature change in the service; driver passes the user).

Likely follow-ups
  • Where do permission checks go once there are more roles? (in one authorisation policy (role to allowed actions) that every service method calls first, not in if-statements spread through the code)
Bug bounty: why per-report synchronized and not a ReentrantLock or optimistic version?

For an in-memory demo, synchronized (report) is the smallest correct scope: one report's check-and-move is atomic, different reports run in parallel, and nothing can be forgotten in a finally block. ReentrantLock adds tryLock with timeout and fairness, useful if callers must not wait forever. Optimistic versioning (compare a version, retry on conflict) fits best once state lives in a database and conflicts are rare.

How to answer

Give the choice, the reason, and the condition under which you would switch. See locks.

Likely follow-ups
  • Can assign and changeStatus deadlock? (No: each takes one lock.)
  • Is your read path safe? (Reads of mutable fields either take the same lock or the field is volatile or immutable; list views are snapshots. See the locks lesson.)
Bug bounty: the bonus asks for a time log per report. Where does it go?

A small TimeEntry (user, minutes, note, at) list on the report, a logTime method in the service with validation (positive minutes, logged-in user), and a total in the report view. No existing method changes. If time logs grow large or need queries across reports, they get their own repository.

How to answer

New entity, new method, no edits elsewhere: that is the sentence evaluators listen for.

Likely follow-ups
  • Show time spent per user across all reports. (walk every report's time entries and sum minutes into a map from user to total; keep a running total per user if it is asked often)
Cost explorer: why not use double for prices?

Binary floating point cannot represent most decimal cents exactly, so sums drift and rounding is unpredictable (0.1 + 0.2 is not 0.3). Use BigDecimal in Java or Decimal in Python with an explicit rounding mode, or integer cents. Decide where rounding happens (per month per plan here) and test it: the 24.995 to 25.00 test exists for exactly this.

How to answer

One sentence of why, one of what you used, one about where you round.

Likely follow-ups
  • Should the yearly total be the sum of rounded months or the rounded sum? (State a rule; billing usually sums the billed months.)
Cost explorer: the day loop is O(365). Make it faster.

Compute overlaps instead of walking days: for each month and each plan period, billable days = overlap of [period start, period end) with [month start, month end) minus its overlap with the trial window. That is O(periods) per month. Keep the simple loop as the reference implementation in tests and check the fast one against it on random inputs.

How to answer

Clarity first, then optimise when asked, with the slow version as a test oracle.

Likely follow-ups
  • What changes if rules are arbitrary (like "free on weekends")? (Overlap math stops working; the day loop or per-rule interval sets.)
Cost explorer: add annual plans billed upfront, without breaking monthly ones.

Billing timing is a new axis, separate from "which days are free". Add a PricingModel on the subscription: MonthlyProRata (today's logic) and AnnualUpfront (full year charged in the start month, nothing after). The explorer asks the model for each month's charge. ChargeRules still decide free days for monthly; for annual, say how a trial interacts (start the year after the trial). Write the failing test first.

How to answer

Spot that it is a new axis of change, give it its own interface, and keep the old tests green.

Likely follow-ups
  • Refunds on downgrade mid-year? (a pro-rata credit for the unused months at the old price minus the new price, posted as its own ledger line, never as an edit to the old bill)
After any mock: what is the first thing you check in your self-review?

The gates: did it run (or, on a whiteboard, did you write and trace the core methods) and was P0 complete at the time limit? If either is a 0, the rest of the score does not matter yet; your next practice is time management and compiling early. Only once gates are reliably 2 do structure and extensibility deserve the practice time.

How to answer

Gates first, then the two lowest score rows. One focus per week.

Likely follow-ups
  • How many mocks before the real round? (Enough that the gates are boring: usually several per round type.)
