Mock 2: Flipkart-style 90-120 minute machine-coding round

Prompt (our summary of a reported brief). Build an internal tool for a bug-bounty programme. Employees log in, register bug reports received by email, assign them, move them through statuses, edit, comment, and view lists (all, assigned to me, open, done). Only admins may delete. Bonus: add users at runtime, message the reporter, keep a status history, log time spent, and allow only these status moves: Open to Report-Review; Report-Review to Rejected or Acknowledged; Rejected to Closed; Acknowledged to Bounty-Review to Bounty-Paid to Closed. Expectations listed in the brief: working demoable code, functional correctness, concurrent requests handled, modular and readable, separation of concerns, new requirements with minimal change, testable, proper error handling. In-memory only, no UI (Flipkart SDE-2 report, 2025-04-02). Time: the cited 2025 round was 90 minutes of coding plus a 30-minute review, and the 2026 Flipkart reports we collected also give 90. The plan below uses 120 minutes, the longer slot some drives allow, but finish P0 by minute 90 either way.

Flipkart drives in 2025-2026 follow the same frame: a group video call with a problem walkthrough, coding in your own IDE, a zip upload, then a separate evaluation call where an engineer runs your code and asks for changes (2026-02-19, 2026-02-18). The 2026 brief also bans AI tools and allows the internet only for syntax.

The 120 minutes, step by step

  1. Plan (0-10). Write the P0 list from the brief. Entities: User, BugReport, BugStatus. Change points: bounty amount rule, notification channel, storage. Assumptions: one logged-in user at a time; amounts by severity.
  2. Skeleton (10-20). Create packages model, exception, repository, service and an empty Main. Everything compiles before any logic exists.
  3. First flow (20-40). Preload users, login, report a bug, assign it, print the list. Ugly is fine. You now cannot submit nothing.
  4. All P0 (40-70). Status change by assignee only, edit, comment, admin-only delete, the four list views. Run after each feature.
  5. Driver and edge cases (70-90). The driver becomes the demo script: numbered steps, then refused cases (empty title, unknown user, wrong assignee, illegal transition, logged out, non-admin delete).
  6. Bonus and concurrency (90-110). The transition table (cheap because status is already an enum), status history, reporter messages through a Notifier, and a thread race on one report.
  7. Final (110-120). Clean build, full run, a five-line README with the run command and assumptions, zip.

How the nine files connect

From your world

BugStatus.next() is a protocol state transition table. TCP keeps the same kind of table: each segment is checked against the current state, and only the allowed next states are taken through tcp_set_state(); anything else is dropped instead of corrupting the connection. The 8-thread race on b2 is the classic "read state, check, write state" problem: our synchronized (r) makes it one step, which you would do in C with a lock or a cmpxchg on the state field (succeed only if the state is still OPEN). Exactly one thread wins, the other seven see the new state and are refused.

The code that carries the grade

/** Bonus rule "status may only move along these edges" lives here, in ONE table. */
public enum BugStatus {
    OPEN, REPORT_REVIEW, REJECTED, ACKNOWLEDGED, BOUNTY_REVIEW, BOUNTY_PAID, CLOSED;

    public Set<BugStatus> next() {
        switch (this) {
            case OPEN:          return EnumSet.of(REPORT_REVIEW);
            case REPORT_REVIEW: return EnumSet.of(REJECTED, ACKNOWLEDGED);
            case REJECTED:      return EnumSet.of(CLOSED);
            case ACKNOWLEDGED:  return EnumSet.of(BOUNTY_REVIEW);
            case BOUNTY_REVIEW: return EnumSet.of(BOUNTY_PAID);
            case BOUNTY_PAID:   return EnumSet.of(CLOSED);
            default:            return EnumSet.noneOf(BugStatus.class);
        }
    }

    public boolean isDone() { return this == CLOSED; }

    /** May the bounty still be re-priced? Named, not derived from ordinal(), so a new constant
     *  (ON_HOLD appended after CLOSED) is priceable unless it is listed here. */
    public boolean isPriceable() { return this != BOUNTY_PAID && this != CLOSED && this != REJECTED; }
}
/** Only the assignee may change status, and only along an allowed edge. */
public void changeStatus(String bugId, BugStatus next) {
    User me = auth.requireUser();
    BugReport r = get(bugId);
    synchronized (r) {                                   // per-report lock: two agents cannot race one report
        live(r);                                         // looked up before the lock: a delete may have won
        if (!me.getId().equals(r.getAssignedUserId()))
            throw new BugBountyException.Forbidden(me.getId() + " is not the assignee of " + bugId);
        if (!r.canMoveTo(next)) throw new BugBountyException.InvalidTransition(bugId, r.getStatus(), next);
        r.moveTo(next, now());
    }
    if (next == BugStatus.ACKNOWLEDGED || next == BugStatus.REJECTED || next == BugStatus.BOUNTY_PAID)
        notifier.notify(r.getReporterEmail(), bugId + " is now " + next);
}

public void delete(String bugId) {
    User me = auth.requireUser();
    if (!me.isAdmin()) throw new BugBountyException.Forbidden(me.getId() + " is not an admin");
    BugReport r = get(bugId);                            // NotFound if the id is bad
    synchronized (r) {                                   // same per-report lock as the mutators
        live(r);
        r.markDeleted();                                 // a mutator that fetched r before us now refuses
        reports.delete(bugId);
    }
}

public void edit(String bugId, String title, String description, Severity severity) {
    auth.requireUser();
    BugReport r = get(bugId);
    synchronized (r) {
        live(r);
        r.edit(title, description, severity);
        if (severity != null && r.getStatus().isPriceable())
            r.setBountyAmount(bounty.amountFor(r));     // re-price until paid, closed or rejected
    }
}

/** Call with r's lock held. The lookup happened before the lock, so re-check: like a use-after-free guard. */
private static void live(BugReport r) {
    if (r.isDeleted()) throw new BugBountyException.NotFound("bug report", r.getId());
}

public List<BugReport> mine(Boolean done) {             // null = all of mine
    String me = auth.requireUser().getId();
    return reports.find(r -> me.equals(r.getAssignedUserId())
            && (done == null || r.getStatus().isDone() == done));
}
public interface BugReportRepository {
    void save(BugReport r);
    Optional<BugReport> findById(String id);
    void delete(String id);
    List<BugReport> find(Predicate<BugReport> filter);
}

public static final class InMemoryBugReportRepository implements BugReportRepository {
    private final Map<String, BugReport> reports = new ConcurrentHashMap<>();
    public void save(BugReport r) { reports.put(r.getId(), r); }
    public Optional<BugReport> findById(String id) { return Optional.ofNullable(reports.get(id)); }
    public void delete(String id) { reports.remove(id); }
    public List<BugReport> find(Predicate<BugReport> filter) { /* filter + sort by the number in the id, so BUG-2 < BUG-10 */ }
}

/** "Reward based on criticality" - the formula WILL change, so isolate it. */
public interface BountyPolicy { long amountFor(BugReport r); }

/** "Send communication to the reporter": print now, email later. */
public interface Notifier { void notify(String toEmail, String message); }

Notice what the driver does for the evaluator: every P0 appears in order, six bad inputs are refused with clear messages, and a thread race proves the per-report lock (exactly one of eight threads wins). Each expected refusal is labelled as expected, and each happy action prints a success line ("deleted BUG-2"), so nothing in the output reads like a failure. The clock is injected: a small test clock that moves one minute forward on every reading, so the history shows the real order and the output is the same on every run. All nine files compile with javac on Java 21 and run as shown.

The evaluation call (30-45 minutes, later)

Evaluator asksStrong answer, short
"Explain the problem and your code."Two minutes, top-down: packages, then one flow (changeStatus), then "all P0 and three bonus items done (the transition table, the status history, reporter notification); time logging and runtime user add not done".
"Run it."Run the driver live from a clean build. Point at sections 2 and 4.
"Add a new status, ON_HOLD, reachable from REPORT_REVIEW."One enum constant and one edge in next(). No service change, because edit() asks status.isPriceable() instead of comparing ordinal() values (an ordinal check would silently treat a constant appended after CLOSED as "already paid"). Show it compiling.
"Bounty should depend on severity and on the product area."New BountyPolicy implementation; the area becomes a field on the report. Wiring changes one line.
"Why synchronized (r) and not a lock on the service?"Different reports never contend; one report's check-then-move is atomic, and delete takes the same lock. The lookup happens before the lock, so a delete can win the race between get() and synchronized (r); delete therefore marks the report deleted under the lock and every mutator re-checks with live(r) once it holds it. That is the "lookup outside the lock" race, the same bug as using an object after another CPU freed it, and the same fix as checking a dead flag under the object lock. The map itself is a ConcurrentHashMap. List views (all, mine) do not lock each report: status and the assignee are volatile, so a list is a best-effort snapshot, which is fine for a screen and is what you say if asked.
"What changes with MySQL?"A JDBC repository; the in-object lock becomes a conditional update (UPDATE ... WHERE id=? AND status=?) or a version column; ids from the database.
"What would you refactor with more time?"Move permission checks into a small policy class; replace the single-session AuthService with per-call user context; add unit tests per service method.
