Law of Demeter: talk only to your friends

The Law of Demeter (also called the principle of least knowledge) was written up at Northeastern University in 1987. Its formal version says a method m of an object O should only call methods on:

  1. O itself (this).
  2. m's parameters.
  3. Objects m creates.
  4. O's own fields (its direct components).

Anything you get back from one of those friends is a stranger. Calling methods on it means you know the inside of your friend's friend - and when that inside changes, you break.

Before: reaching through the customer into the wallet

static boolean checkout(Customer c, int paise) {
    if (c.getWallet().getBalance() >= paise) {                    // ask ...
        c.getWallet().setBalance(c.getWallet().getBalance() - paise);   // ... then act
        return true;
    }
    return false;
}

After: tell, don't ask

static class Wallet {
    private int balancePaise;
    Wallet(int b) { balancePaise = b; }
    boolean debit(int paise) {                 // the rule lives with the data
        if (paise > balancePaise) return false;
        balancePaise -= paise;
        return true;
    }
}
static class Customer {
    private final Wallet wallet;
    Customer(Wallet w) { wallet = w; }
    boolean pay(int paise) { return wallet.debit(paise); }
}
static boolean checkout(Customer c, int paise) { return c.pay(paise); }   // one friend, one call

Tell, Don't Ask is the habit that produces Demeter-friendly code: instead of pulling data out of an object to make a decision, tell the object what you want and let it decide. In the "before" code the balance check and the update are two separate steps done by an outsider; in the "after" code they are one operation owned by Wallet.

From your world

Ask-then-act is a race. You know this pattern from the kernel: reading a reference count with atomic_read(), seeing 1, and then freeing the object is a time-of-check/time-of-use bug, because another CPU can take a reference in between. The correct API is "tell": kref_put(&obj->ref, release) decrements and calls release only if the count hit zero, atomically. Same lesson as Wallet.debit(): let the owner of the data do the check and the change together - and in a multi-threaded LLD round, that is also where you put the lock.

Hide the delegate. Kernel code used to write filp->f_path.dentry->d_inode all over the place. The helper file_inode(filp) hides that chain, so callers no longer depend on how a struct file reaches its inode. That is exactly the "Hide Delegate" refactoring for a message chain.

What is not a Demeter violation

  • Fluent builders and streams. builder.name("a").size(3).build() and list.stream().filter(..).map(..) keep talking to the same kind of object (the builder, the stream). Counting dots is not the rule.
  • Plain data / value objects. Reading order.address().city() from an immutable record is navigating data, not commanding a stranger. Many teams accept this.
  • The "middle man" overcorrection. If Customer grows 30 one-line methods that just forward to Wallet, Address and Cart, you have created the opposite smell. Forward only the operations clients really need.
