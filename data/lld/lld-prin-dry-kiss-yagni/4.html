YAGNI: build it when it is needed

YAGNI comes from Extreme Programming: do not add a capability because you might need it. Martin Fowler's article on YAGNI lists what a "presumptive feature" costs even when you guess right: the cost of building it, the cost of delaying the features you actually need, the cost of carrying the extra complexity in every later change, and the cost of repairing it when the guess was wrong.

Before: a payments framework for one payment method

// Spec: "user pays by UPI".  Candidate builds (bodies left out; count the classes):
interface PaymentProcessor { }
abstract static class AbstractPaymentProcessor implements PaymentProcessor { }
static class PaymentProcessorFactory { }     // one product
static class PaymentPluginRegistry { }       // loads plugins by reflection
static class RetryPolicyConfig { }           // not in the spec
static class CurrencyConverter { }           // only INR in the spec

After: the simplest thing, with one honest seam

interface PaymentMethod { boolean pay(int paise); }   // seam: the spec hints more methods will come
static class Upi implements PaymentMethod {
    public boolean pay(int paise) { System.out.println("UPI paid " + paise); return true; }
}

The one interface is not a YAGNI violation: payment methods are a well-known axis of change, the interviewer will almost certainly ask "add card payments", and the seam costs three lines. The factory, registry, retry config and currency converter answer questions nobody asked.

What YAGNI does not cover. Fowler is explicit that YAGNI applies to features, not to practices that keep code easy to change: tests, refactoring, clear names, small classes. "I won't write tests, YAGNI" is a misuse.

  1. Both start. A builds generic infrastructure; B models the entities and the main flow.
  2. At 45 minutes B has a running demo. A is still building configuration and plugin loading.
  3. B handles edge cases. A realises the core flow is half done.
  4. The interviewer asks for an extension. B adds one class behind the existing seam in minutes.
  5. Feedback: A is "over-engineered and incomplete"; B is "working, clean and extensible". Working code first, then extensibility.

Company rubrics written up by candidates (see the machine-coding guide) put working, demo-able code first, then readability and extensibility. A half-built framework with no demo scores below a simple solution that runs.
