KISS: the simplest design that works

KISS ("keep it simple") says that extra complexity must pay rent. Every layer, generic type, reflection trick or clever one-liner makes the code slower to read, review and debug.

// BEFORE: clever - correct, but who can review it in 10 seconds?
static boolean isLeapClever(int y) { return ((y & 3) == 0 && y % 25 != 0) || (y & 15) == 0; }

// AFTER: reads like the rule
static boolean isLeap(int y) {
    if (y % 400 == 0) return true;
    if (y % 100 == 0) return false;
    return y % 4 == 0;
}

Both give the same answers (the demo checks 1900, 2000, 2023 and 2024). Only one of them can be verified by a reviewer at a glance.

KISS in an LLD round

  • In-memory first. Machine-coding rounds (Flipkart, PhonePe, Swiggy, CRED style) ask for an in-memory, demo-able program. A HashMap behind a repository interface is the simple, correct answer; a real database is not.
  • Plain classes before frameworks. main() wiring beats a DI container. A switch over three states can be fine before a full State pattern - unless the problem is a state machine at heart (vending machine, elevator), where State is the simple design.
  • Simple is not the same as easy. A god class with everything in main() is easy to write and not simple to change. KISS means few concepts with clear jobs, not "no structure".

A useful test: Kent Beck's four rules of simple design, in priority order - passes the tests, reveals intention, no duplication, fewest elements. Note how DRY (rule 3) and KISS (rule 4) are ranked below "works" and "is clear". (Fowler's summary is linked in Resources.)
