Interview questions

Explain DRY, KISS and YAGNI with one example each.

DRY: the free-delivery threshold lives in one DeliveryPolicy instead of in the cart page and checkout, so a change cannot drift. KISS: store bookings in a HashMap behind a repository interface in a machine-coding round instead of wiring a database. YAGNI: do not build a plugin registry for payment methods when the spec has only UPI; add a PaymentMethod seam and stop.

How to answer

One line each, one concrete example each, then mention that they can conflict and you decide by cost.

Likely follow-ups
  • Is all duplication bad?
  • How does YAGNI relate to the Open/Closed Principle?
Is all duplication bad? When would you keep duplicated code?

No. DRY is about knowledge, not text. Keep duplicates when (1) they are coincidental - same code, different facts that will change for different reasons; (2) merging needs flags or caller checks, i.e. the wrong abstraction; (3) the copies sit across service or team boundaries where sharing would force lock-step releases. Use the rule of three before extracting.

How to answer

Name "coincidental duplication" and "wrong abstraction" explicitly; give the microservice DTO example.

Likely follow-ups
  • How would you undo a bad abstraction? (inline it back into callers, then re-extract)
What is the Law of Demeter? Is list.stream().filter(..).map(..) a violation?

A method should only call methods on itself, its parameters, objects it creates, and its own fields - not on objects returned by those. order.getCustomer().getWallet().debit() violates it: the caller knows the internal structure of two other classes. A stream pipeline is not a violation: each call returns the same kind of object (a stream) designed for chaining. The rule is about knowledge of structure, not counting dots.

How to answer

Give the 4 allowed targets, a violating example, the fix (customer.pay(x)), then the stream/builder exception.

Likely follow-ups
  • What is Tell, Don't Ask?
  • What is the "middle man" smell?
Your machine-coding feedback says "over-engineered". What does that mean and how would you avoid it next time?

It means structure that does not pay for itself: interfaces with one implementation and no reason to vary, factories with one product, generic repositories, layers that only forward, config/plugins nobody asked for - usually at the cost of a working demo. Next time: entities and main flow first, running by mid-time, seams only on axes the problem names, then refactor for duplication and train wrecks, and verbally mention where other extensions would plug in.

How to answer

Show you understand the rubric: working code, then clarity, then extensibility.

Likely follow-ups
  • Then how do you show extensibility without building it?
YAGNI says don't build for the future; Open/Closed says design for extension. How do you reconcile them?

Open/Closed tells you how to extend once an axis of change is known; YAGNI tells you not to guess axes. So: add an extension point when there is evidence - the requirements list variants, a second case appears, or the domain is well known to vary (payment methods, notification channels, pricing). Otherwise keep a concrete class; extracting an interface later is a cheap, safe refactoring if the code is tested.

How to answer

"Evidence-driven seams." Mention that tests make later refactoring cheap, which is what makes YAGNI safe.

Likely follow-ups
  • Give an example of a seam you would add on day one in a parking lot design.
How does Tell, Don't Ask help with thread safety?

Ask-then-act from outside (if (w.getBalance() >= x) w.setBalance(w.getBalance() - x)) is a check-then-act race: another thread can change the balance between the read and the write. Moving the operation into the owner (w.debit(x)) lets one class hold the lock (or use an atomic compare-and-set) around both steps. It is the same reason the kernel provides kref_put() instead of letting callers read the count and free.

How to answer

Name "check-then-act", show the fix, mention where the lock goes. Link to concurrency in LLD.

Likely follow-ups
  • Would you use synchronized or an AtomicLong here?

Scenario: the reviewer finds the same discount logic in three classes

During the evaluation of your shopping-cart machine-coding solution, the reviewer points out that "10% off above Rs 1000" is written in Cart, InvoiceGenerator and OrderSummaryPrinter. They ask you to add "flat Rs 100 off for first order".
"I'll add the first-order check in all three places. I'll be careful to keep them the same."
"That's duplicated knowledge, so first I'll extract a PricingPolicy that returns the final amount and the applied discounts; the three classes call it. Then the new rule is one more DiscountRule implementation registered in the policy, so I add it in one place and one test covers all three outputs. I won't build a rule engine with priorities and stacking config yet - I'll mention where it would go if they ask for combining rules."
Follow-up: "Two rules apply - which wins?" - a small, explicit ordering in PricingPolicy (best-for-customer, or a fixed order), stated as an assumption.
