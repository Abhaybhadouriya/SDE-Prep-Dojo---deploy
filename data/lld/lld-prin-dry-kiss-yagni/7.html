The over-engineering pitfall in machine coding

Candidates with strong backgrounds - including systems engineers who know how big real software gets - often fail machine-coding rounds not by under-designing, but by over-designing. Warning signs in your own code:

  • Interfaces with exactly one implementation and no stated reason to vary.
  • A factory that creates one product, or a builder for a class with two fields.
  • Generic type parameters (Repository<T, ID>) before a second entity uses them.
  • Configuration files, plugin loading or reflection in a 90-minute exercise.
  • Design patterns named in class names (OrderStrategyFactoryManager) instead of domain names.
  • Layers that only forward calls (controller - service - manager - handler - DAO for a HashMap).

A simple-first checklist for the round

  1. Model the nouns. Entities and their relationships from the requirements, as plain classes.
  2. Make the main flow run. In-memory storage, a driver in main(), printed output. Commit to working code by mid-time.
  3. Put seams only on the axes the problem names. "Different pricing for cars and bikes" - Strategy. "Notify by email or SMS" - Notifier interface. Nothing else.
  4. Remove duplication you can see. Rules repeated across classes go into one policy object (DRY).
  5. Check for train wrecks. Replace a.getB().getC().x() with a method on a (Demeter).
  6. Say what you left out. "I did not add persistence or retries; here is where they would plug in." That earns extensibility credit without the cost.

The opposite failure exists too: one 600-line class with everything in main(). YAGNI is not permission to skip structure. The goal is the smallest structure that keeps the code easy to change on the axes that matter.
