DRY: one piece of knowledge, one place

The Pragmatic Programmer's definition is precise: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." Notice the word knowledge. DRY is not "never type the same characters twice". It is "never encode the same business fact twice".

Before: the delivery rule typed twice

static class CartPage {
    int deliveryFee(int totalPaise) { return totalPaise >= 49900 ? 0 : 4000; }
}
static class Checkout {
    int deliveryFee(int totalPaise) { return totalPaise > 49900 ? 0 : 4000; }   // drifted: > vs >=
}

Someone fixed one copy months ago and missed the other. Now a cart of exactly Rs 499 shows "Free delivery" on the cart page and charges Rs 40 at checkout. The demo in lld-code/lld-prin-dry-kiss-yagni/PrinciplesDemo.java (every code block on this page is copied from that file) prints exactly this: same cart, two answers.

After: one authoritative place

static final class DeliveryPolicy {
    static final int FREE_ABOVE_PAISE = 49900, FEE_PAISE = 4000;
    static int fee(int totalPaise) { return totalPaise >= FREE_ABOVE_PAISE ? 0 : FEE_PAISE; }
}
// CartPage and Checkout both call DeliveryPolicy.fee(total)

DRY is about knowledge, not text

  • Coincidental duplication is fine. "Max username length 30" and "max coupon-code length 30" are both 30, but they are different facts owned by different people. Merging them into one constant MAX_LEN couples two things that will change for different reasons.
  • Rule of three. The first time, write it. The second time, notice the duplication. The third time, extract. Two examples rarely show you the right shape of the abstraction.
  • The wrong abstraction costs more than duplication. Sandi Metz's well-known essay (linked below) describes the trap: a shared helper grows flags and if branches for every new caller until nobody can change it. If you see that, it is fine to inline the copies back and start again.
  • DRY reaches beyond code. Schema in one place and generated code from it; config values in one file; documentation generated from the source of truth.

From your world

You already practise DRY in C with a shared header: an enum of error codes or a struct layout defined once in a .h and included by both the driver and the user-space tool. The classic bug when someone copies a struct definition into a second file instead of including the header - fields drift, offsets differ, the ioctl corrupts memory - is the C version of the drifting delivery rule.
