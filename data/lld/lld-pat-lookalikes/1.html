The problem: learning shapes instead of reasons

Here is a class that a candidate described as "the Strategy pattern":

class Order {
    private OrderStatus status = new Placed();     // holds an interface...
    void next() { status = status.next(); }        // ...but the status picks the NEXT status
}
interface OrderStatus { OrderStatus next(); }
class Placed implements OrderStatus { public OrderStatus next() { return new Shipped(); } }
class Shipped implements OrderStatus { public OrderStatus next() { return new Delivered(); } }

The shape (context holds an interface and delegates) is the same as Strategy. But nobody outside ever chooses an OrderStatus; each status object decides which one comes next. That is State. Calling it Strategy is not a typo to an interviewer; it signals that you will also pick the wrong tool in a real design, for example by letting callers set any status they like and breaking the order lifecycle.

The cure is to remember each pattern as a problem plus a key question, not as a picture.
