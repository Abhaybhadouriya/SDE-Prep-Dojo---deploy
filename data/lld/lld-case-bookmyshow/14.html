Interview follow-ups

Two users select the same seat at the same moment. How do you prevent double booking?

Seat state for a show is Free, Held or Booked. Holding is one atomic step: either under a lock per show (check every requested seat, then write Held on every seat, then unlock) or with compare-and-set per seat plus rollback. Only one of the two users can move the seat out of Free; the other is told the seat is taken before paying. Confirming re-checks that the seat is still held by that user's hold.

How to answer

State machine first, then where the atomicity comes from, then the pessimistic vs optimistic choice, then the database or distributed version.

Likely follow-ups
  • What if the app runs on 20 servers?
  • What if the user's payment succeeds after the hold expired?
Pessimistic or optimistic locking for seats? Defend your choice.

For hot shows I would pick pessimistic with short critical sections: contention on popular seats is high, so optimistic updates would fail often, and multi-seat holds need rollback logic. The lock is per show (or per seat in sorted order), held only while checking and writing a few entries, never during payment. For low-traffic inventory (a small theatre, a weekday matinee) optimistic is cheaper. Because the inventory is an interface, both can exist and be chosen per show category.

How to answer

Contention level decides; mention lock duration (never across I/O), granularity, deadlock avoidance via ordering, and the rollback cost of optimistic multi-seat holds.

Likely follow-ups
  • How would you measure which one is better in production?
  • Write the SQL for each.
How do holds expire? Do you need a background job?

Each held seat stores expiresAt. Every check treats a hold whose time has passed as free, so correctness never depends on a cleanup thread (lazy expiry). A periodic sweeper is still useful to mark bookings EXPIRED, send "your hold expired" messages and keep availability counts tidy, but if it is late, nobody is blocked. In Redis the key's own expiry does the same job.

How to answer

Lazy expiry for correctness, sweeper for housekeeping; show the one-line isFreeNow check.

Likely follow-ups
  • What clock do you trust across servers? (The database's or Redis's clock, not each app server's.)
The payment gateway charged the user but the hold had expired. What now?

First, make it rare: check the hold before calling the gateway, and give the payment page a timeout shorter than the hold. If it still happens, confirm fails (the seat is gone or re-held), the booking goes to EXPIRED and a refund is triggered automatically, with the user told immediately. Payments use an idempotency key per booking so retries never charge twice. An alternative some systems use: if the seats happen to be still free, re-hold and confirm them.

The stronger SDE-2 answer prevents the two-sided failure instead of compensating for it. Our demo's pay() captures money first and confirms seats second, so a failed confirm leaves "money taken, no seats". Split the payment into the two steps every card and UPI-mandate gateway offers: authorize (hold the funds on the user's account), then confirm the seats under the show lock, then capture. If confirm fails, void the authorization: the hold simply disappears from the user's statement, and nothing was ever charged, so there is no refund to chase. Another option is to extend the seat hold atomically (under the show lock) for the length of the gateway call, so it cannot expire mid-payment. Keep the outbox refund only as the last line of defence, for the rare capture that succeeds after a timeout.

How to answer

Prevention (authorize, confirm, capture; or extend the hold), detection, compensation (refund via outbox) as the last resort, idempotency.

Likely follow-ups
  • How do you make the refund reliable? (Outbox table plus a retrying worker.)
  • What if capture fails after confirm? (Retry capture with the same idempotency key; authorizations stay valid for days, and the seats are already yours.)
Why is the seat's booked status not a field on Seat?

A physical seat is reused by every show on that screen. Booking A1 for the 6 pm show must not book it for 9 pm. So availability is keyed by (show, seat): in our code, the inventory keeps one state map per show; in a database, a show_seat table with a row per show per seat.

How to answer

Name the many-to-many (shows x seats) and the association entity it needs.

Likely follow-ups
  • How many show_seat rows per day for a 300-seat screen with 5 shows? (1,500; creating them when the show is scheduled is cheap.)
The app runs on many servers. Your Java lock no longer works. What changes?

The lock must live where all servers see it. Three options: row locks or conditional updates in the database (simplest and strongly consistent); Redis SET key value NX PX ttl per seat for holds, with the final confirmation in the database; or route all traffic for a show to one partition so an in-process lock is enough. The service code does not change, because only the SeatInventory implementation changes.

How to answer

Point at the interface, then give the options with their trade-offs; mention that a Redis lock needs a fencing token or a database check at confirm time.

Likely follow-ups
  • What happens if Redis loses the key on failover?
How would you add dynamic pricing without changing BookingService?

Pricing is a strategy. A DemandPricing decorator wraps the base seat-type pricing and adds a surcharge above an occupancy threshold; weekend or morning-show rules are more decorators. The price is computed once at hold time and stored on the booking, so the user pays what they were shown even if occupancy changes during payment.

How to answer

Strategy + decorator, plus the "snapshot the price" rule.

Likely follow-ups
  • Different prices per row inside the same seat type?
What happens if a user double-clicks Pay?

Both requests reach pay(). They are serialised on the booking's monitor; the first moves PENDING to CONFIRMED, the second sees CONFIRMED and is rejected before calling the gateway. Across servers, the same guarantee comes from an idempotency key on the payment API and a conditional status update (UPDATE booking SET status='CONFIRMED' WHERE id=? AND status='PENDING').

How to answer

Per-booking serialisation plus idempotency; never rely on the UI to disable a button.

Likely follow-ups
  • Where do you store idempotency keys and for how long?
Other platforms also sell the same seats. How do you avoid double booking across platforms?

Only one system can own availability: the cinema's (or airline's) inventory. Every platform asks the owner for a hold through its API and gets a lease id with an expiry, then confirms with that id. Platforms may cache availability for display, but never treat the cache as truth. This is the same design as ours, with the owner's API as the SeatInventory implementation.

How to answer

Single source of truth plus leases; caches are hints.

Likely follow-ups
  • What if the owner's API is slow or down?
Walk me through the class diagram in two minutes.

Catalogue side: Show links a Movie and a Screen at a time; Screen owns Seats with a type. Booking side: BookingService uses a SeatInventory (the only place that knows a seat's state per show), a PricingStrategy and a PaymentStrategy, and keeps Bookings.
