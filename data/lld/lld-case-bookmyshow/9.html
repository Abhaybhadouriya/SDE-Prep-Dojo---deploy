Concurrency: pessimistic vs optimistic seat locking

The race is the same check-then-act you saw in the parking lot, with two extra twists: a request covers several seats that must be taken all together, and a successful take is only temporary until payment. Step through both answers.

  1. Pessimistic: Alice takes the show's lock. Bob, who wants an overlapping seat, waits. Critical sections are tiny (check a few map entries, write a few), so the wait is microseconds.
  2. Alice checks every seat, writes Held on every seat, unlocks. Bob then sees A2 held and is rejected without having written anything: all-or-nothing for free.
  3. Optimistic: nobody locks. Each seat is an atomic reference; a write succeeds only if the seat still has the value you read (compare-and-set). Alice and Bob both read A2; only the first CAS succeeds.
  4. The price of optimism: if Bob had already taken A3 before failing on A2, he must undo A3. Taking seats in sorted order keeps two users from repeatedly undoing each other.

In the database, the same two answers look like this. Note that the expiry check is part of the condition, so an expired hold is overwritten without any cleanup job:

-- Pessimistic: lock the rows, check, write, commit (all seats in one transaction)
BEGIN;
SELECT seat_id, status, hold_expires_at FROM show_seat
 WHERE show_id = :show AND seat_id IN ('A1','A2')
 ORDER BY seat_id
 FOR UPDATE;                       -- sorted order: two transactions cannot deadlock
-- application checks every row is FREE or HELD with hold_expires_at < now(); else ROLLBACK
UPDATE show_seat SET status = 'HELD', hold_id = :hold, hold_expires_at = now() + interval '5 minutes'
 WHERE show_id = :show AND seat_id IN ('A1','A2');
COMMIT;

-- Optimistic: one conditional update; it either changes every requested row or you roll back
UPDATE show_seat
   SET status = 'HELD', hold_id = :hold, hold_expires_at = now() + interval '5 minutes', version = version + 1
 WHERE show_id = :show AND seat_id IN ('A1','A2')
   AND (status = 'FREE' OR (status = 'HELD' AND hold_expires_at < now()));
-- rows updated must equal 2; if it is 1, ROLLBACK the transaction: someone got the other seat first

Across many app servers the per-show lock in our Java code no longer works (each JVM has its own). Options, in the order to mention them: the database row locks above (simplest, strongly consistent); a Redis key per seat set with SET seat:SH1:A2 <holdId> NX PX 300000 (atomic "set if absent" with an expiry, a perfect fit for TTL holds, but you then confirm in the database); or partitioning: route all requests for one show to one server, so an in-process lock is enough again. Other shared state in our code

  • Booking status is guarded by the booking's own monitor (synchronized (b)), so a double "pay" click or a pay racing a cancel is serialised per booking, while different bookings run in parallel.
  • Expiry check before charging: pay() checks the hold time first, so an expired hold never reaches the gateway. The tiny window between that check and confirm() is covered: confirm re-checks under the lock, and a failure there is reported as EXPIRED (the real system would refund).
  • Pricing swap: volatile field holding an immutable strategy, same as the parking lot.
  • Lock ordering: the service never holds the booking monitor while waiting for another booking; it holds booking then show lock, always in that order, so there is no cycle.

From your world

The optimistic inventory is a cmpxchg loop: read the old value, compute the new one, publish only if memory still holds the old value. The version number is the same defence you use against ABA problems in lock-free lists. The pessimistic one is a spin_lock_irqsave around a short critical section; the rule "never sleep while holding a spinlock" becomes "never call the payment gateway while holding the show lock".

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.
