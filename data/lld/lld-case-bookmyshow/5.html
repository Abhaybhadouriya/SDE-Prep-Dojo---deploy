Key relationships and patterns (and why each)

Pattern / ideaWhereWhy here
StrategySeatInventory (pessimistic / optimistic), PricingStrategy, PaymentStrategyThe locking approach is the most debated choice in the interview; making it an interface lets you swap it and even run the same tests against both. Prices and payment methods change by business rule.
DecoratorDemandPricing wraps any base pricingSurcharges stack (demand, weekend, convenience fee) without a class per combination.
State machineBookingStatus with moveTo(); SeatState Free / Held / BookedIllegal moves (cancel an expired booking, pay twice) are rejected in one place. With only five states and simple rules, an enum plus a transition table is enough; full State-pattern classes would be heavier than the problem.
ObserverBookingListener (NotificationService)SMS, email and analytics react to confirmations without the booking code knowing them.
Sealed types / tagged unionSeatStateA seat is in exactly one state, and each state carries its own data (who holds it, until when). The compiler knows all three cases.
Lease (TTL)Held.expiresAtAn abandoned checkout must not block a seat forever, and expiry needs no background thread to be correct.

From your world

SeatState is the C tagged union you have written many times: struct seat_state { enum kind kind; union { struct held h; struct booked b; }; }. Java's sealed interface plus records is the type-checked version: you cannot read expiresAt from a Booked seat by accident. The booking state machine is the TCP state machine in miniature: a table of legal transitions, and anything else is a protocol error.
