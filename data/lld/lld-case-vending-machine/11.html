Concurrency and thread safety

A machine has one keypad, but the software still has several threads: the coin-validator interrupt, the keypad, the admin panel, a telemetry or remote-price-update thread. Two dangers:

Step through the race this section is about, then the fix the code uses:

  1. The coin-validator thread sees IDLE and starts adding a Rs 10 coin to escrow.
  2. Before it switches to HAS_MONEY, the admin thread also sees IDLE and switches to MAINTENANCE.
  3. The machine is in MAINTENANCE holding a customer's Rs 10 that no state will ever refund.
  4. The fix: every public method is synchronized on the machine, so each event runs to completion before the next. The admin call then sees HAS_MONEY and is refused ("cannot enter maintenance while HAS_MONEY"), which the demo's step 6 shows.
  1. Torn state If "insert" from the coin thread and "enterMaintenance" from the admin thread interleave, the machine could go to MAINTENANCE holding a customer's coins. Fix: every public method is synchronized on the machine (Python: one lock; C++: a std::mutex in the threaded build). Each event runs to completion before the next, exactly like a state machine driven from one event queue.
  2. Sessions span events A purchase is insert, insert, select. The per-method lock makes each event atomic, but not the whole session. On a physical machine the single keypad serialises customers. For a remote or app-driven machine, bind the session to a customer id (only that customer may select or cancel while HAS_MONEY) or queue the events. Our Python test models the keypad with an outer lock and proves 10 concurrent buyers never oversell 3 items.
  3. No check-then-act across the lock The stock check, the change computation and the commit all happen inside one select call, under one lock. Never ask "is A1 in stock?" in one call and dispense in another.
  4. Many machines A fleet shares nothing at runtime; each machine is its own lock domain. Central inventory or pricing is an HLD question: the machine syncs through a queue and treats the server as eventually consistent.

The event-queue alternative is worth one sentence: put every event (coin, key, admin) into a single BlockingQueue drained by one thread that owns the machine. No locks inside the states at all; this is how embedded firmware and many UI frameworks run state machines (the producer-consumer pattern; locks are covered in locks and conditions).
