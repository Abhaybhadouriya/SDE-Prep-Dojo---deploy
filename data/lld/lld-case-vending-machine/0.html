The story: the shopkeeper in a box

Explain like I'm 5

Imagine a tiny shopkeeper living inside a box. When nobody is there, she waits. You push a coin through the slot: she holds it in her hand, not in the till yet. You press "Chips". She checks: are there chips? Is your money enough? Can she give you your change with the coins she has? Only if all three answers are yes does she drop your coin into the till, take out your change and push the chips down the chute. If you press "Cancel", she gives you back the very coins in her hand.

While she is pushing chips down the chute, she ignores every button. When the owner opens the box to refill it, she does not sell anything. Same buttons, different answers, depending on what she is doing right now. That "what she is doing right now" is the machine's state.

The interview tests three things. First, can you model behaviour that depends on state without a switch in every method (the State pattern)? Second, is the money correct: a purchase either completes fully or leaves no trace, and change is paid from a cash box that has a limited number of each coin? Third, can you grow the design when the interviewer adds card payment, an admin mode or a coffee machine?

From your world

You have built this machine before: it is a protocol state machine. In C you would write struct vm_state_ops { int (*insert)(struct vm *, int coin); int (*select)(struct vm *, const char *code); int (*cancel)(struct vm *); };, one static table per state, and vm->ops = &has_money_ops; on a transition. The TCP stack does the same with sk->sk_state and a big switch in tcp_rcv_state_process; the State pattern turns that switch into one table per state, like a driver's file_operations. The coins held "in her hand" are an escrow buffer: staged like a transaction and committed only when every check passes, the same idea as building a whole netlink message before sending it, so the receiver never sees half.

New to classes? Read OOP from C first: it maps structs, function pointers and ops tables onto classes, interfaces and virtual calls. Every pattern on this page also appears in Patterns in the kernel.
