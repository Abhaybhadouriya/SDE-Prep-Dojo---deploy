Change-making: why greedy is not enough

With an unlimited supply of Indian coins, "largest coin first" (greedy) always gives the fewest coins, because the denominations 1, 2, 5, 10, 20, 50, 100 form a canonical system. A real machine has a limited number of each coin, and then greedy can fail even when a solution exists.

The bounded DP is the coin-change DP from DSA with a count limit per coin. best[a] is the fewest coins that make amount a. For each denomination v with have coins, for each amount from high to low, try using 1..have of that coin. Going from high to low means each denomination is counted only once per layer, which enforces the limit. A second table used[i][a] remembers how many of coin i were used, so the actual coins can be rebuilt. Cost: O(types x amount x maxCount), tiny for vending amounts (a few hundred rupees). The Python tests check the DP against greedy on every amount from 0 to 60 for several cash boxes.

From your world

This is the same trap as a greedy buddy allocator under fragmentation: free memory exists, but not in the right block sizes, so a first-fit or largest-first choice fails where a careful search succeeds. Keep the fast path (greedy) when the supply is "infinite" (an ATM refilled daily), and the exact search when resources are scarce.
