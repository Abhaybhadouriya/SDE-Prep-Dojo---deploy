StateState + Idle, HasMoney, Dispensing, SoldOut, MaintenanceSix events times five states. Each state class answers every event for its own state, and chooses the next state itself. No switch(state) anywhere. A new state is a new class plus edits only in the states that lead to it: its behaviour is isolated (SRP), but Open/Closed holds only partly.

Mention it and say why we chose the DP.

"This VendingMachine can be a Singleton" (from the MakeMyTrip interviewer) is a trap worth answering calmly: there is one physical machine per process, but a Singleton makes every test share one machine and hides the dependency. Create it in main and pass it in (dependency injection); if the process truly must have one, a single instance created at startup is enough. Say you know the pattern and why you did not use it.

Why the pattern earns its place: the if-ladder it replaces

Without the State pattern, every public method opens with the same switch:

int insert(Denomination d) {
    switch (state) {
        case IDLE:        escrow.add(d); state = HAS_MONEY; return balance();
        case HAS_MONEY:   escrow.add(d); return balance();
        case DISPENSING:  throw new VendingException("busy");
        case SOLD_OUT:    throw new VendingException("sold out, " + d + " returned");
        case MAINTENANCE: throw new VendingException("in maintenance");
    }
}
Purchase select(String code)  { switch (state) { /* five more cases */ } }
List<Denomination> cancel()   { switch (state) { /* five more cases */ } }
// ...six methods x five states = 30 cases; a new state edits all six
interface State {
    default int insert(VendingMachine m, Denomination d) { throw refuse("insert money"); }
    default Purchase select(VendingMachine m, String code) { throw refuse("select a product"); }
    ...
}
final class IdleState implements State {
    public int insert(VendingMachine m, Denomination d) {
        m.escrow.add(d); m.setState(m.hasMoney); return m.balance();
    }
}
public synchronized int insert(Denomination d) { return state.insert(this, d); }

With the switch, the follow-up "add an OUT_OF_CHANGE state" edits all six methods. With State it is one new class, plus a line in each state that can lead to it (the states that hand over to OUT_OF_CHANGE); nothing else moves.

From your world: the same move in C

struct vm_state_ops {
    int (*insert)(struct vm *m, int coin);
    int (*select)(struct vm *m, const char *code);
    int (*cancel)(struct vm *m);
};
static const struct vm_state_ops idle_ops = { .insert = idle_insert, .select = refuse_select, ... };
/* m->ops->insert(m, coin);  the state is the ops pointer itself */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.

Our state objects hold no data, so one instance of each is shared by every machine, and the machine (the context) holds the escrow, inventory and cash box. That is exactly static const struct file_operations plus struct file: the ops table is shared and read-only, the per-instance data lives in the struct the ops receive.
