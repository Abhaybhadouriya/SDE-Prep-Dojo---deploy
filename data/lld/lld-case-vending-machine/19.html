The machine is in HAS_MONEY and the operator tries to enter maintenance. What should happen?

  1. Ignore the request without a message
  2. Switch to MAINTENANCE and keep the coins
  3. Refund silently and switch
  4. Refuse: a customer is mid-purchase
Only IDLE and SOLD_OUT accept enterMaintenance. Refusal with a message is the safe default.

Change due is Rs 8. The box has one Rs 5 and four Rs 2 coins, no Rs 1. What does greedy do?

  1. Pays 5 + 2 and keeps Rs 1
  2. Pays 2 + 2 + 2 + 2
  3. Fails after 5 + 2, though 2 + 2 + 2 + 2 exists
  4. Pays 5 + 2 + 1
Largest-first takes the 5, then a 2, and needs a 1 it does not have. The bounded DP finds four 2s.

Where should inserted coins go before the sale completes?

  1. Straight into the cash box
  2. Into the HasMoneyState object
  3. Nowhere; only the balance number is stored
  4. An escrow list in the machine, moved to the cash box only on commit
Escrow makes refunds exact and failed sales traceless; states stay stateless.

Which design lets you add an OUT_OF_SERVICE state with the fewest edits?

  1. Subclass VendingMachine
  2. A new State class that refuses everything except maintenance
  3. Add a case to each switch(state)
  4. Add a boolean isBroken checked in every method
With the State pattern a state is one class; existing states change only where they transition into it.
