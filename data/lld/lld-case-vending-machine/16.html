Interview follow-ups

Why the State pattern here? Would an enum and a switch not be simpler?

With 5 states and 6 events, a switch version has a switch(state) in every one of the six methods: 30 cases spread across the class, and adding a state means editing all six. The State pattern puts each state's answers in one class, lets each state choose its successor, and makes a new state a new class plus a change in each state that transitions into it (so Open/Closed holds only partly; the gain is that each state's behaviour sits in one place). An enum plus switch is fine for a 3-state machine with one event (like tic-tac-toe's game state); here it is not.

How to answer

Draw the event x state table, then say "each column becomes a class". Mention the threshold where the enum is still better.

Likely follow-ups
  • Who changes the state: the context or the state? (The state, through m.setState.)
  • State vs Strategy?
State vs Strategy: they look the same in UML. What is the difference?

Both are "an interface with swappable implementations held by a context". In Strategy the client picks the algorithm and it rarely changes (our ChangeMaker). In State the states replace each other as events arrive, and they know about each other's existence (HasMoney moves to Dispensing). Same structure, different intent and different owner of the switch.

How do you return change with the fewest coins? Is greedy correct?

Greedy is optimal only for a canonical coin system with unlimited coins. A machine has limited coins, and then greedy can fail: change 8 from one Rs 5 and four Rs 2 coins. Use the bounded coin-change DP (fewest coins, each denomination limited by its count), O(types x amount x count), and rebuild the coins from a choice table. If the DP finds nothing, refuse the sale before taking any money.

Likely follow-ups
  • Can the customer's own inserted coins be used as change? (Yes; include escrow in the pool.)
  • Which non-canonical system breaks greedy even with unlimited coins? (For example coins 1, 3, 4 for amount 6: greedy gives 4+1+1, best is 3+3.)
The product drops but the machine cannot pay change. How do you avoid that?

Order the work: check stock, check balance, compute change against the current cash box, and only then commit (escrow in, change out, item out). Each commit step is guaranteed to succeed because it was checked under the same lock. If change cannot be made, the customer keeps their escrowed coins and can add money, choose another product or cancel.

What does cancel give back?

The exact coins inserted in this session, which live in the escrow list and never entered the cash box. That refund can never fail, unlike "return the same value in any coins", which may need change the box does not have. It is also what customers expect from a real machine.

How do you handle concurrency?

Every public method takes the machine's lock, so each event runs to completion and the state can never be torn (insert and enterMaintenance cannot interleave). A purchase spans several events, so the session needs an owner: on hardware the single keypad gives that; for an app-driven machine bind HAS_MONEY to a customer id. All checks and the commit live inside one select call, so there is no check-then-act across calls. Alternative: a single event queue drained by one thread, with no locks in the states.

Add card and wallet payment.

Introduce PaymentMethod (Strategy): authorize(amount), capture(), refund(). Cash wraps escrow and change; card authorises the price and needs no change. HasMoney becomes PaymentPending; the commit captures the payment. If dispensing fails after capture (jammed coil), refund through the same method. The states and inventory do not change.

Should VendingMachine be a Singleton?

Not as a pattern. One process may control one physical machine, but a Singleton forces global state on every test and hides the dependency. Create one instance at startup and inject it. If an interviewer insists, show a thread-safe lazy holder, and say why you would still prefer injection (Singleton).

The admin wants an alert when a slot runs out, and a daily sales report.

Observer: the inventory publishes onLowStock(code, count) and onSoldOut(code); the machine publishes onSale(product, price). An AlertService and a SalesReport subscribe. The states never call email or SMS code directly, so adding a channel is a new listener.

Turn it into a coffee machine.

The state machine stays (Idle, PaymentPending, Brewing, OutOfIngredients, Maintenance). Products become recipes: a map of ingredient to quantity. Inventory tracks ingredients, and "in stock" means every ingredient of the recipe is available. Add-ons like extra shot or milk wrap the beverage price with a Decorator. Brewing replaces Dispensing and takes time, so it is a real state that refuses input until the brew-done event.

Why integers for money?

Binary floating point cannot represent most decimal fractions exactly, so sums drift (0.1 + 0.2 is not 0.3). Store whole rupees (or paise) as integers, or use BigDecimal with a fixed scale. Our coins are whole rupees, so int is exact; the conservation check (cash = float + sales) would catch any drift.
