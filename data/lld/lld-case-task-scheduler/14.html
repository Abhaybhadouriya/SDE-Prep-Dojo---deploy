Interview follow-ups

Why a heap and not a sorted list, or sorting the tasks each time?

A binary heap gives O(log n) insert and O(log n) remove-min, and O(1) peek at the earliest job, which is all a dispatcher needs. Sorting on every submit is O(n log n); a sorted linked list is O(n) per insert. A balanced tree (TreeSet) also works and allows O(log n) removal of any element, which helps eager cancellation, at a higher constant cost.

How to answer

List the three operations (insert, peek, remove-min), give each structure's cost, and pick the heap. Mention the tree if cancel must free memory at once.

Likely follow-ups
  • When is a timer wheel better than a heap?
  • How do you handle two jobs with the same run time? (Tie-break on a sequence number for FIFO.)
Fixed rate versus fixed delay: what is the difference and what happens when a run is slow?

Fixed rate anchors to the planned start: runs at 0, 100, 200 whatever their length. Fixed delay anchors to the finish: if a run takes 30 ms, the next starts 130 ms after the previous start. If a fixed-rate run takes longer than the period, we start the next one immediately after it finishes, and never in parallel with itself (the JDK's scheduleAtFixedRate documents the same no-overlap rule). Uber's statement asked for fixed delay.

How to answer

Draw two short timelines, then say "never overlaps itself" and where the code enforces it (rescheduled on completion).

Likely follow-ups
  • Should missed fixed-rate runs be caught up or skipped? (Our formula skips them; a backlog of runs is rarely wanted.)
Two tasks are submitted at the same instant from two threads. What happens?

Both callers take the same lock, so their admissions are serialised: each gets a distinct sequence number and is pushed onto the heap. If both are due at the same millisecond, priority decides; with equal priority, the lower sequence number (the one that got the lock first) runs first. Neither can be lost or admitted twice, and the dispatcher is signalled by each.

How to answer

"Serialised by the lock, ordered by (time, priority, sequence)". Then show the stress test result.

Likely follow-ups
  • Could you make submit lock-free? (A concurrent queue as an inbox, drained by the dispatcher.)
Why does the dispatcher acquire a worker permit before it picks a job?

To keep the priority decision late. If due jobs were pushed into a FIFO executor queue as soon as they were due, a burst of low-priority jobs would sit ahead of a high-priority job that arrives a moment later, and the priority heap would have no effect. With the permit, a job leaves the ready queue only when a worker can start it at once. A side effect is backpressure: in-flight work never exceeds the pool size.

How to answer

Describe the failure (priority inversion through a FIFO queue), then the fix, then the bonus (bounded queue).

Likely follow-ups
  • Could you use a PriorityBlockingQueue inside a ThreadPoolExecutor instead? (Yes, for due jobs; you still need the time queue.)
How do you run jobs with dependencies, and how do you detect a cycle?

Each job keeps a count of unfinished parents and each parent keeps a list of children. A job with count 0 is scheduled; when a job succeeds, each child's count drops by one, and a child reaching 0 is scheduled. That is Kahn's topological sort, driven by completions. For a batch, run Kahn's algorithm once at submit time: if fewer than all jobs come out, the rest are on a cycle, and we reject the whole batch before admitting anything. With single submits, a dependency must already exist, so a cycle cannot even be expressed.

How to answer

Counts plus child lists, release on zero, Kahn for the batch, all or nothing. Then say what happens on failure (children SKIPPED).

Likely follow-ups
  • Make it thread safe (the Rubrik follow-up): counts under the lock, release only on the transition to zero.
  • Add priorities among ready jobs (the Goldman Sachs follow-up): already the ready-queue order.
A job is running when the process crashes. What happens after restart?

In our in-memory version it is lost, which is why persistence is out of scope. With a repository, we would write every state change; on restart, RUNNING jobs are reset to SCHEDULED and run again. That gives at-least-once execution, so tasks must be idempotent (safe to repeat), for example by writing results under the job id. Exactly-once needs the task's side effect and the "done" mark to commit together.

How to answer

Say "at-least-once plus idempotent tasks" and give one concrete idempotency trick.

Likely follow-ups
  • How do two scheduler instances avoid running the same job? (Leases with expiry, or row locks.)
Jobs need capabilities that only some machines have. How does the design change?

A worker gets a capability set, a job gets a required set, and a job can run on a worker only if the required set is a subset. The dispatcher no longer asks "any free worker?" but "which free worker can run the best due job?". A simple version keeps one ready queue per distinct requirement set and, when a worker frees up, looks at the heads of the queues it can serve and takes the highest priority. Represent capabilities as a bitmask so the subset test is one AND.

How to answer

Model it (two sets and a subset test), then change only the matching step in the dispatcher. The bitmask detail lands well with systems interviewers.

Likely follow-ups
  • A job that no worker can run: reject at submit.
  • Preferring the least capable worker that fits, to keep special machines free (best fit).
How do you cancel a job, and why not remove it from the heap?

We set the state to CANCELLED under the lock and signal the dispatcher. The job stays in the heap until it reaches the top, where the dispatcher sees the state and drops it. Removing an arbitrary heap element is O(n); flipping a flag is O(1). The cost is memory held until the job's time comes; if many far-future jobs get cancelled, a tree-based queue or a periodic purge fixes that.

How to answer

"Lazy deletion": O(1) cancel, filtered at pop. Name the memory trade-off yourself.

Likely follow-ups
  • Can you cancel a running job? (Only cooperatively: interrupt the thread and have the task check.)
Why are listeners called outside the lock?

Listener code is foreign code. It may be slow (a network log), it may block, or it may call back into the scheduler. Under the lock, a slow listener stalls every submitter and the dispatcher; a blocking one can deadlock. So state changes record small events in a list while the lock is held, and the list is delivered after unlock(). The cost is that a listener may see an event slightly after another thread already moved the job on, which is acceptable for metrics and logs.

How to answer

"Never call alien code while holding a lock", then the trade-off on ordering.

Likely follow-ups
  • Need strict per-job event order? Deliver through a single event thread with a queue.
The statement says "no library schedulers". What may you still use?

Threads, locks, condition variables, semaphores and plain collections (heap, map, blocking queue) are fair: they are the building blocks, not the answer. ScheduledThreadPoolExecutor, Timer, DelayQueue or Python's sched are the answer, so do not use them, but do mention them to show you know the standard tools and that your design matches theirs.

How to answer

Confirm with the interviewer, then name what you will and will not use.

Likely follow-ups
  • How does DelayQueue work inside? (A priority queue plus a leader thread doing a timed wait: our dispatcher.)
