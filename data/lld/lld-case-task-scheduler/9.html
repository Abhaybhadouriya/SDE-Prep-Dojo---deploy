Concurrency and thread safety

Start the answer with a list of shared state and who touches it. Then pick one protection per row. Here a single lock is the right call: every operation is a few heap and map steps (microseconds), and the slow part, the task body, runs outside it.

Five decisions that interviewers probe

  1. The dispatcher waits for a free worker before it picks a job. If it pushed every due job into the pool's FIFO queue at once, a priority-9 job arriving a moment later would queue behind 500 priority-1 jobs: the priority heap would be useless. Acquiring a semaphore permit first means the choice is made at the last possible moment, when a worker can actually start. It also gives backpressure: the pool queue never holds more than N items.
  2. Wait with a deadline, re-check after every wake-up. changed.await(head.runAt - now) sleeps exactly until the earliest job is due. A new, earlier job calls signal() so the dispatcher recomputes. Every wait sits in a while loop because wake-ups can be spurious and the head may have changed. This is the classic lost wake-up trap: if you check the queue, release the lock and then sleep, a signal in between is lost.
  3. Run the task and the listeners without the lock. A task that sleeps for a minute while holding the lock freezes every submitter. A listener that calls scheduler.info() while the lock is held by another thread is fine with a reentrant lock, but a listener that blocks on something a worker needs would deadlock. We collect events under the lock and fire them after unlock().
  4. Lazy cancellation. Removing an arbitrary element from a binary heap is O(n). We flip the state to CANCELLED (O(1)) and the dispatcher drops the job when it reaches the top: a tombstone. The kernel's timer wheel avoids the problem differently: timers sit on doubly linked bucket lists, so del_timer() is an O(1) unlink, and hrtimer_cancel() removes the node from an rbtree in O(log n). A binary heap cannot unlink in place, so we tombstone; an indexed heap that tracks each job's position would give O(log n) removal.
  5. A monotonic clock. System.nanoTime(), not currentTimeMillis(). If NTP steps the wall clock back an hour, a wall-clock scheduler goes silent for an hour. This is CLOCK_MONOTONIC versus CLOCK_REALTIME.

The stress test is the proof: 8 submitter threads, 8,000 jobs with random priorities and delays, 4 workers. Every job ran exactly once, and the in-flight counter never went above 4.

Python note. The Python version is correct under threads, but the GIL means the task bodies do not run Python bytecode in parallel. For CPU-heavy jobs use a process pool for the workers; the scheduler logic does not change.

Why not one lock per job instead of one global lock?

Because the operations that matter span many jobs at once: picking the top of a heap, decrementing several children's counters, skipping a whole subtree. Per-job locks would force a lock ordering across the DAG and still need a lock for the heaps. The global lock is held for microseconds, so contention is low. If profiling ever showed it hot, the first step would be sharding: N independent schedulers by hash of job id, each with its own lock and pool (DAG edges must then stay inside one shard).

How to answer

Name the multi-object operations, state the hold time, and offer sharding as the measured next step.

Likely follow-ups
  • Could the time queue be a DelayQueue or ConcurrentSkipListSet instead?
  • How would you measure lock contention? (JFR lock events; time waiting in lock().)
