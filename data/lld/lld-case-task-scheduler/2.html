Clarify requirements

Spend 5 to 8 minutes here. A scheduler question is vague on purpose: "schedule tasks" can mean cron, a thread pool, a build system or a cluster manager. Pin it down to one process, in memory.

Functional (P0 - must work in the demo)

  1. One-shot jobs Run a task now, or after a delay ("not before now + 300 ms").
  2. Periodic jobs Fixed rate (start every 100 ms, like a clock tick) and fixed delay (start 100 ms after the previous run finished, the Uber definition).
  3. Worker pool A configurable number of worker threads; never more jobs running at once than workers.
  4. Priority Among jobs that are due, the higher priority runs first; equal priority runs in the order it became due.
  5. Dependencies A job may list jobs it depends on; it runs only after all of them succeeded (a DAG). A cycle is rejected.
  6. Cancel and status Cancel a job that has not run yet (or stop a periodic job); query any job's state.

Functional (P1 - say you can add them, build if time allows)

  • Retries with exponential backoff; when retries run out the job is FAILED and its dependents are SKIPPED.
  • Submit a whole graph at once, all or nothing (the Rubrik shape).
  • Listeners for state changes (metrics, logs, a UI).

Non-functional

  • Thread safe: many threads submit and cancel at once; a job never runs twice in parallel and never gets lost.
  • Efficient waiting: no busy loop. The dispatcher sleeps until the next job is due or until something changes.
  • Fast operations: submit is O(log n) (heap insert); picking the next job is O(log n).
  • Testable: time comes from an injected clock; a monotonic clock in production.
  • Isolated failures: an exception in one job never kills a worker or the dispatcher.

Out of scope (say it out loud)

  • Persistence and crash recovery, multiple machines, leader election (that is the HLD problem: Distributed Job Scheduler).
  • Cron expressions (the design leaves a slot for them: one more Schedule class).
  • Preempting a running job, or killing it on a timeout.
