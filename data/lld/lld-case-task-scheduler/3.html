Identify the entities

Underline nouns (candidate classes) and verbs (candidate methods), then remove actors and plain values. Click through.

  1. Underline every noun. Most become fields, a few become classes.
  2. Underline every verb. They become the public API (submit, cancel, status) or private steps (dispatch, run, retry).
  3. Drop the actor, keep plain values as fields, and spot the two rules that vary (when to run again; how to retry). Split "job" into the immutable request and the mutable run-time record.
  4. The final list. The split between JobSpec (immutable, built once) and Job (mutable, guarded by the lock) is the most important modelling decision on this page.
EntityKindResponsibility (one line)
TaskSchedulerService / facadeThe API: submit, submitGraph, cancel, info, awaitTerminal, shutdown. Owns all queues and the lock.
JobSpec + BuilderImmutable valueWhat the client asked for: id, task, priority, delay, schedule, dependencies, retry policy.
JobEntity (mutable)Run-time state: current state, next run time, attempt count, pending dependency count, dependents.
TaskInterface (Command)The work: one method, run(), which may throw.
ScheduleInterface (Strategy)"When next?" Once, FixedRate, FixedDelay (cron later).
RetryPolicyValueMax attempts and backoff.
JobStateEnum (state machine)WAITING, SCHEDULED, RUNNING, SUCCEEDED, FAILED, CANCELLED, SKIPPED.
WorkerPoolInfrastructureN threads taking work from a queue.
JobListenerInterface (Observer)Hears every state change.
ClockInterfaceMonotonic milliseconds; fake it in tests.

Why split JobSpec and Job? The client's request never changes, so it can be shared freely between threads with no lock. The run-time record changes on every dispatch and completion, so exactly one lock guards it. Mixing them in one class makes every field look like it needs locking. This is the same split as a kernel's read-only file_operations table versus the per-open struct file.
