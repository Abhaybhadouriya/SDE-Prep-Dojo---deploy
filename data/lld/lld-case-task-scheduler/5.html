The job state machine

From your world

This is a TCP-style state machine: a fixed set of states, a few legal transitions, and one function that performs them. In the kernel, tcp_set_state() is that one function, and it also updates counters, exactly like our move() also signals waiters and queues listener events. The dependents list with a pendingDeps counter is a reference count in reverse: each parent holds one count on the child, and the child is released when the count hits zero.

Why the pattern earns its place: the if-ladder it replaces

Without the Schedule interface, every kind of timing is a branch in the completion path:

long nextRun(Job j, long now) {
    if (j.kind == Kind.ONCE) {
        return -1;
    } else if (j.kind == Kind.FIXED_DELAY) {
        return now + j.periodMs;
    } else if (j.kind == Kind.FIXED_RATE) {
        return j.lastPlannedAt + j.periodMs;
    } else if (j.kind == Kind.CRON) {        // follow-up: cron edits the scheduler's core
        return Cron.parse(j.expr).next(now);
    }
    throw new IllegalStateException();
}
interface Schedule {
    long nextRunAfter(long plannedAt, long finishedAt);   // -1 = no more runs
}
// once(), fixedDelay(ms), fixedRate(ms) are small implementations in Model.java

long next = job.spec.schedule.nextRunAfter(job.runAt, now);   // in execute(); no kind flag
if (next >= 0) schedule(job, next, events);

With the ladder, the follow-up "cron expressions" edits TaskScheduler, the class with all the locking. With the interface it is one new Schedule class in Model.java, and the concurrent core is not touched.

From your world: the same move in C

struct schedule_ops { long (*next_run)(const struct schedule *s, long planned, long finished); };
struct schedule { const struct schedule_ops *ops; long period_ms; };
/* next = job->sched->ops->next_run(job->sched, job->run_at, now); if (next >= 0) requeue(job, next); */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
