Fix-this-code drills

Read the "before", decide which principle breaks and what you would change, then open the diagnosis. All twelve versions live in one file, lld-code/lld-prin-interview/Drills.java; java Drills.java runs every before/after pair and checks they produce the same results. Time yourself: about 3 minutes per drill is interview pace.

Drill 1: the invoice that does everything

Which principle does this break? Who are the actors that will ask for changes?

static class Invoice {
    final List<long[]> lines = new ArrayList<>();          // {qty, unitPaise}
    long total() { return lines.stream().mapToLong(l -> l[0] * l[1]).sum(); }
    String toPdfText() { return "INVOICE total=" + total(); }          // presentation
    void saveTo(Map<String, String> db, String id) { db.put(id, toPdfText()); } // persistence
    void email(String to) { System.out.println("mail " + to + ": " + toPdfText()); } // delivery
}
Drill 1: diagnosis and fix

SRP. Three actors: finance (totals/tax), design (rendering), infra (storage and mail). Split into a value object that knows its total, plus formatter, repository and sender roles. The values stay identical (the driver checks it).

record Line(long qty, long unitPaise) { long amount() { return qty * unitPaise; } }
record Bill(List<Line> lines) { long total() { return lines.stream().mapToLong(Line::amount).sum(); } }
interface BillFormatter { String format(Bill b); }
interface BillRepository { void save(String id, String rendered); }
interface BillSender { void send(String to, String rendered); }
static class TextFormatter implements BillFormatter { public String format(Bill b) { return "INVOICE total=" + b.total(); } }
How to answer

Name the principle, point at the exact line that breaks it, then show the smallest fix. Keep the old behaviour identical.

Drill 2: the growing fee switch

A new payment method (WALLET) is coming next sprint. What will you have to edit, and what principle is that?

static class FeeCalculatorBefore {
    long fee(String method, long amount) {
        switch (method) {                       // every new method = edit + retest this class
            case "UPI":  return 0;
            case "CARD": return amount * 2 / 100;
            case "NETBANKING": return 10;
            default: throw new IllegalArgumentException(method);
        }
    }
}
Drill 2: diagnosis and fix

OCP. Each new method edits and re-tests the calculator. With a rule map, WALLET is one register call; the calculator is untouched. Unknown methods still fail loudly.

interface FeeRule { long fee(long amount); }
static class FeeCalculator {
    private final Map<String, FeeRule> rules = new HashMap<>();
    FeeCalculator register(String method, FeeRule rule) { rules.put(method, rule); return this; }
    long fee(String method, long amount) {
        FeeRule r = rules.get(method);
        if (r == null) throw new IllegalArgumentException("unknown method " + method);
        return r.fee(amount);
    }
}

Drill 3: the vehicle hierarchy (Goldman-style)

A round showed vehicle classes and asked which SOLID principle is violated, then asked for a fix (Goldman Sachs, 2025-05). What breaks when fillAll gets an electric car?

static abstract class Vehicle {
    abstract void refuel(int litres);
    abstract int range();
}
static class PetrolCar extends Vehicle {
    int fuel; void refuel(int l) { fuel += l; } int range() { return fuel * 15; }
}
static class ElectricCar extends Vehicle {
    int charge = 40;
    void refuel(int l) { throw new UnsupportedOperationException("no tank"); } // breaks callers
    int range() { return charge * 6; }
}
static void fillAll(List<Vehicle> fleet) { for (Vehicle v : fleet) v.refuel(10); }
Drill 3: diagnosis and fix

LSP (and ISP underneath). ElectricCar cannot honour refuel, so substituting it crashes callers. Split capabilities into role interfaces; code that refuels asks for Refuelable, code that needs range asks for Drivable.

interface Drivable { int range(); }
interface Refuelable { void refuel(int litres); }
interface Rechargeable { void recharge(int kwh); }
static class Petrol implements Drivable, Refuelable {
    int fuel; public void refuel(int l) { fuel += l; } public int range() { return fuel * 15; }
}
static class Electric implements Drivable, Rechargeable {
    int charge; public void recharge(int k) { charge += k; } public int range() { return charge * 6; }
}
static void fillTanks(List<? extends Refuelable> tanks) { for (Refuelable r : tanks) r.refuel(10); }
How to answer

Name the principle, point at the exact line that breaks it, then show the smallest fix. Keep the old behaviour identical.

Drill 4: the fat machine interface

Why does BasicPrinter contain methods that throw?

interface Machine { void print(String doc); void scan(String doc); void fax(String doc, String to); }
static class BasicPrinter implements Machine {
    public void print(String doc) { System.out.println("print " + doc); }
    public void scan(String doc) { throw new UnsupportedOperationException(); }   // forced stub
    public void fax(String doc, String to) { throw new UnsupportedOperationException(); }
}
Drill 4: diagnosis and fix

ISP. One fat interface forces stubs. Role interfaces let each class implement only what it supports, and clients depend only on the role they use.

interface Printer { void print(String doc); }
interface Scanner { String scan(String doc); }
static class SimplePrinter implements Printer { public void print(String d) { System.out.println("print " + d); } }
static class OfficeMachine implements Printer, Scanner {
    public void print(String d) { System.out.println("print " + d); }
    public String scan(String d) { return "scan:" + d; }
}

Drill 5: the notifier welded to SMTP

How would you unit-test orderPlaced without sending mail? How would you add SMS?

static class SmtpClient { void sendMail(String to, String body) { System.out.println("SMTP " + to + " " + body); } }
static class OrderNotifierBefore {
    private final SmtpClient smtp = new SmtpClient();   // policy welded to one detail
    void orderPlaced(String user) { smtp.sendMail(user, "order placed"); }
}
Drill 5: diagnosis and fix

DIP. The policy (notify on order) creates the detail (SMTP). Define MessageChannel on the policy side and inject implementations; tests pass a lambda fake, SMS is a new class.

interface MessageChannel { void send(String to, String body); }
static class EmailChannel implements MessageChannel {
    public void send(String to, String body) { System.out.println("email " + to + " " + body); }
}
static class OrderNotifier {
    private final List<MessageChannel> channels;
    OrderNotifier(List<MessageChannel> channels) { this.channels = List.copyOf(channels); }
    void orderPlaced(String user) { channels.forEach(c -> c.send(user, "order placed")); }
}

Drill 6: the train wreck

What does checkoutBefore need to know about Customer and Wallet?

static class WalletB { long balance = 500; }
static class CustomerB { WalletB wallet = new WalletB(); WalletB getWallet() { return wallet; } }
static class OrderB {
    CustomerB customer = new CustomerB(); long amount = 200;
    CustomerB getCustomer() { return customer; }
}
static void checkoutBefore(OrderB o) {         // reaches through three objects
    WalletB w = o.getCustomer().getWallet();
    if (w.balance < o.amount) throw new IllegalStateException("low balance");
    w.balance -= o.amount;
}
Drill 6: diagnosis and fix

Law of Demeter / Tell, Don't Ask. The function reaches through two objects and edits a wallet's field directly. After the fix, each object exposes a verb and guards its own rule.

static class Wallet {
    private long balance;
    Wallet(long b) { balance = b; }
    void debit(long amt) { if (balance < amt) throw new IllegalStateException("low balance"); balance -= amt; }
    long balance() { return balance; }
}
static class Customer { private final Wallet wallet; Customer(Wallet w) { wallet = w; } void pay(long amt) { wallet.debit(amt); } }
static class Order {
    private final Customer customer; private final long amount;
    Order(Customer c, long amount) { customer = c; this.amount = amount; }
    void checkout() { customer.pay(amount); }     // tell, don't ask
}
How to answer

Name the principle, point at the exact line that breaks it, then show the smallest fix. Keep the old behaviour identical.
