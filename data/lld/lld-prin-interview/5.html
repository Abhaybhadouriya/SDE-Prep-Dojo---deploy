Q&A: beyond SOLID - DRY, Demeter, cohesion, smells, judgement

DRY, KISS and YAGNI - and what happens when DRY conflicts with decoupling?

DRY: every piece of knowledge has one authoritative place. KISS: prefer the simplest design that works. YAGNI: do not build for requirements you do not have. The conflict: two pieces of code that look identical but change for different reasons (say, a delivery fee and a GST rounding rule) should not be merged - merging couples two actors. DRY is about knowledge, not about text that happens to match.

How to answer

Define all three briefly, then spend your time on the conflict - that is the senior part of the answer.

Likely follow-ups
  • What is the rule of three?
  • How do KISS and YAGNI apply in a 90-minute machine coding round?
What is the Law of Demeter? Show a violation.

A method should talk only to its immediate friends: its own fields, its parameters, objects it creates. order.getCustomer().getWallet().debit(x) reaches through three objects, so checkout now depends on the internals of Customer and Wallet. Fix: tell, don't ask - order.checkout() calls customer.pay(amount), which calls wallet.debit(amount). See Drill 6. Fluent builders and streams (a.b().c() on the same object type) are not violations.

How to answer

Give the "only talk to friends" rule, the train-wreck example, the fix and the exception (fluent APIs).

Likely follow-ups
  • Doesn't the fix add lots of tiny delegating methods?
What are coupling and cohesion, and how do you measure them in an interview?

Coupling is how much one module depends on another's details; cohesion is how strongly the parts inside one module belong together. Aim for low coupling, high cohesion. The interview measurement is a thought experiment: "if requirement X changes, which classes change?" One class = good; five = coupled. A Salesforce SMTS round asked exactly this kind of follow-up - if a user changes their preferences, which components are affected (2026-11).

How to answer

Answer with the change-impact test and walk your own diagram for one change.

Likely follow-ups
  • Name kinds of coupling from worst to best.
  • How do events reduce coupling, and what do they cost?
Which GRASP principle tells you where a method belongs?

Information Expert: give a responsibility to the class that has the information needed to fulfil it. Ticket has the entry time, so ticket.durationUntil(now) lives there; PricingPolicy owns the tariff, so it computes the fee from the duration. Creator says who should create an object (the one that contains or closely uses it), and Controller says which object receives a system event (a use-case coordinator, kept thin).

How to answer

Use it to justify placement decisions out loud: "I put this here because this class has the data."

Likely follow-ups
  • What is a Pure Fabrication and when do you need one?
Name five code smells you would look for in your own machine-coding solution before submitting.
  1. Long method / large class (god object).
  2. Switch on type codes (missing polymorphism).
  3. Primitive obsession (status strings, money as double).
  4. Feature envy (a method that mostly uses another class's data - move it).
  5. Shotgun surgery (one change touches many classes) or its opposite, divergent change.
How to answer

Name each with its standard refactoring: Extract Class, Replace Conditional with Polymorphism, Replace Primitive with Object (enum/value object), Move Method.

Likely follow-ups
  • Which smell do you tolerate in a 90-minute round?
Is Singleton an anti-pattern?

The pattern is fine when "exactly one" is a real property (process-wide config, a hardware block, a connection pool). It becomes an anti-pattern when getInstance() is a shortcut to a global: hidden dependencies, test pollution, contention, and pain when "one" becomes "two". Inject the single instance through constructors; let the composition root decide the count. Goldman Sachs asked for a thread-safe Singleton and a SOLID fix in the same round (2025-05); Walmart asked for double-checked locking with volatile (2024-12).

How to answer

Code it correctly first (holder idiom or enum), then show judgement. See Anti-Patterns.

Likely follow-ups
  • Why is volatile needed in double-checked locking?
  • How do you break a Singleton with reflection or serialization, and prevent it?
When do SOLID principles make a design worse?

When applied without a requirement: interfaces with one implementation, factories for one product, classes split so small that one change touches ten files, abstraction layers that hide simple logic. SOLID trades simplicity for changeability; if nothing will change, you paid for nothing. In a timed round, unfinished P0 features cost more than a missing abstraction. A Razorpay candidate was told to cover the basic requirements first when they wanted to design for future features (2025-06).

How to answer

This is the trade-off beat. Show you can turn principles down as well as up, and name the signal you use (a second implementation, a stated requirement, an interviewer hint).

Likely follow-ups
  • How do you know which axis of change to prepare for?
Your working machine-coding solution got "not extensible" feedback. How do you make extensibility visible?

Extensibility only counts if the grader sees it. (1) Put variation points behind interfaces and name them after the requirement (AllocationStrategy, not Helper). (2) Show one extension in the driver: register a second strategy and run it. (3) Say it in the review: "adding a new vehicle type is one class and one registration". (4) Keep the core free of type switches. Flipkart's published evaluation criteria list modularity and extensibility, separation of concerns and abstractions next to working code (2026-02); an Uber L4 candidate reported initially negative LLD feedback despite working code (2025-05).

How to answer

Answer as a checklist you actually run in the last 10 minutes.

Likely follow-ups
  • What would you cut if you were 15 minutes behind?
You get a codebase with model classes and failing unit tests, and must make the tests pass "following SOLID". How do you approach it?

Read the tests first - they are the specification and they show the intended API. Run them to see what fails. Sketch the seams the tests imply (which collaborators are injected, which are mocked). Implement the smallest thing that passes one test at a time, extracting interfaces only where the tests or the problem statement show variation. Keep commands/operations as separate classes when the problem is a command interpreter (CRED's microprocessor/registers problem, 2024-10). Finish with a refactor pass for names and duplication, re-running tests each time.

How to answer

Show a test-first loop and the discipline of not breaking the given API. Mention that you would add your own tests for edge cases.

Likely follow-ups
  • How would you model SET/INC/MOVE commands?
  • What if a given model class violates SRP - do you change it?
Tell me about a time you applied a design principle at work.

Use STAR with a real, small story. For a networking/kernel background a strong example is an ops table: "Our packet-processing code had a switch on NIC model in five places. I moved per-NIC behaviour into a struct of function pointers each driver filled in, so adding a NIC became one new file. That is Open/Closed and Dependency Inversion in C." Quantify: files touched per new NIC before and after, bugs avoided.

How to answer

Situation in one line, the smell, your change, the measurable result, and what you would do differently. Amazon will tie this to a Leadership Principle (Insist on the Highest Standards, Invent and Simplify).

Likely follow-ups
  • What did it cost?
  • Who disagreed, and why?
In the review call: "Add a new log destination (say Kafka) to your logger. Which files change?"

The right answer is "one new class and one line of wiring". The logger depends on a Sink interface (write(LogRecord)) and a Formatter interface; KafkaSink implements Sink is added, and the composition root (driver or config) registers it. Logger, the level filter and the existing sinks do not change. That is Open/Closed (extend by adding) resting on Dependency Inversion (the logger owns the Sink abstraction). If your answer is "I add a case to the switch in Logger.log", the reviewer has found the extensibility gap they were looking for.

Context: a PhonePe SDE-2 take-home asked for an extensible logger library with levels, sinks and formats (LeetCode Discuss, 2026-03-27).

How to answer

Name the interface, the new class and the one wiring line; then say which principle that is, in one sentence.

Likely follow-ups
  • The Kafka sink is slow. Does the caller wait? (async sink with a bounded queue)
  • How do you test the logger without Kafka?
Charges differ per broker plan and trade type. Where does a new charge rule go?

Not into an if (plan == ...) else if (type == ...) ladder that grows with every plan. Model each charge as a small rule object behind one interface, ChargeRule.apply(Trade): Money, and give each plan a list of rules (brokerage, exchange fee, tax). A new charge is a new rule class; a new plan is a new list. The calculator sums the list and never changes. This is Open/Closed plus Single Responsibility: each rule has one reason to change (its regulator or its pricing team).

Context: a Groww SDE-2 machine-coding round asked for a brokerage calculator with charges per plan and trade type, built to be extensible (LeetCode Discuss, 2026-09-25).

How to answer

Show the interface, two rule classes and the summing loop; mention that rules could later be loaded from config.

Likely follow-ups
  • Rules that depend on each other (tax on brokerage): order or composition?
  • Where do you use BigDecimal instead of double?
You are given an existing codebase and asked to add a feature "following SOLID". How do you start?

Read before writing: find the model classes and the place where behaviour varies today. Then make the smallest change that turns that place into an extension point (extract an interface from the concrete class the new feature must vary, inject it through the constructor), and add the feature as a new implementation. Keep existing tests green after each step. Do not rename or restructure code that the feature does not touch; reviewers grade the diff, and a large rewrite reads as risk, not skill.

Context: a CRED round handed candidates model classes for a circuit simulation and asked them to extend it, applying SOLID so that provided tests pass (LeetCode Discuss, 2024-10-17).

How to answer

Read, find the variation point, extract the interface, add the new class, run the tests; say why you did not rewrite.

Likely follow-ups
  • The existing class has no tests. What do you do first?
The reviewer asks: "Which principles does your solution follow?" How do you answer without name-dropping?

Point at code, not at acronyms. Pick three concrete spots: "LeaderboardService only ranks; scoring lives in ScoringPolicy, so a new scoring rule does not touch ranking (single responsibility, open/closed)." "The service takes repositories as interfaces in its constructor, which is why my driver can use in-memory maps (dependency inversion)." "Entities enforce their own rules; the service only coordinates (information expert)." Then name one place you knowingly kept simple, and why (YAGNI). One honest trade-off is worth more than five principle names.

Context: a PhonePe machine-coding round was followed by a 30-minute call on patterns and extensibility (LeetCode Discuss, 2026-07-07); Flipkart drives end with a walkthrough where you explain your code (LeetCode Discuss, 2026-06-13).

How to answer

Three code locations, each with the principle in brackets, plus one deliberate simplification.

Likely follow-ups
  • Where does your code break a principle on purpose?
