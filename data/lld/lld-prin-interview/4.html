Q&A: SOLID

What is SOLID? Explain each letter in one line.
  • Single Responsibility: a class should have one reason to change (one actor who asks for changes).
  • Open/Closed: add behaviour by adding code (a new class), not by editing working code.
  • Liskov Substitution: a subtype must work anywhere its base type is expected, without surprises.
  • Interface Segregation: clients should not depend on methods they do not use; prefer small role interfaces.
  • Dependency Inversion: high-level policy and low-level details both depend on abstractions; the policy owns the interface.

Asked directly at Walmart (SSE, 2024-12) and used as the grading lens in CRED machine coding (2024-10).

How to answer

Five crisp lines, then offer one example: "In my parking lot, pricing was a Strategy, so a weekend tariff was a new class - that is OCP." Do not recite textbook definitions for five minutes.

Likely follow-ups
  • Which one do you find hardest to apply?
  • Which is most often violated in your own code?
  • How do SOLID and design patterns relate?
What does "one reason to change" actually mean? Isn't a class with one method the ideal?

"Reason to change" means a source of change requests - an actor, team or policy. An Invoice that totals lines, renders a PDF and saves itself changes when finance changes tax rules, when design changes the layout, and when infra changes the database. Three reasons. It does not mean one method per class: Account with deposit, withdraw and freeze has one reason (account rules) and should stay together. Over-splitting gives anemic, scattered code.

How to answer

Use the "who would ask me to change this?" test, show the Invoice split, and mention the over-splitting risk unprompted.

Likely follow-ups
  • How do you decide where validation goes?
  • Isn't a Controller/Service always an SRP violation?
How do you apply Open/Closed in practice? Show the before and after.

Find the switch or if/else on a type code that grows with every new case. Replace each branch with an implementation of an interface, and pick implementations through a map (registry) or factory. New behaviour is a new class plus one registration line; the calculator itself is closed. See Drill 2 below for code.

Uber's 2026 cab round wanted the driver-allocation rule swappable (SDE-II, 2026-08); Amazon asked follow-ups on a split Strategy in Splitwise (SDE-2, 2025-10).

How to answer

Code a tiny before/after (5 lines each). Then say which axis you closed it against: "closed for new payment methods, not for a new fee model". OCP protects against the changes you predicted, not all changes.

Likely follow-ups
  • Your factory still has a switch. Is that an OCP violation?
  • Can you be closed against every change?
  • How do plugins/registries work in Java (ServiceLoader)?
Your Factory has a switch on type. Doesn't adding a product break Open/Closed?

Yes, a little - and it is the cheapest place for it. The factory concentrates the only edit in one line, so every client stays closed. To remove even that edit: a registry map filled at startup (register("UPI", UpiFee::new)), Java's ServiceLoader, or an enum whose constants carry their own behaviour. Known failure cases: the registry is filled in many places (hidden coupling), a missing registration fails only at runtime (so fail fast with a clear error and a startup check), and string keys allow typos (prefer an enum key).

An Arcesium hiring-manager round asked exactly this - OCP failure cases and fixes in the Factory pattern - and the reported feedback was that answers needed more depth and examples (SSE, 2025-09).

How to answer

Concede the point, show you know three ways to close it further, and name the trade-off of each. That is the "depth and examples" the feedback asked for.

Likely follow-ups
  • Registry vs reflection-based discovery?
  • How do you test that every enum value has a handler?
Explain Liskov Substitution with an example that is not Rectangle/Square.

A Vehicle base class has refuel(litres). ElectricCar extends Vehicle throws UnsupportedOperationException from refuel. Code that loops over a fleet and refuels every vehicle now crashes when an electric car is passed - a subtype broke the base type's promise. The rules: a subtype may not demand more (stronger preconditions), may not promise less (weaker postconditions), must keep the base invariants, and must not throw new kinds of exceptions callers do not expect. Fix: model capabilities as separate interfaces (Refuelable, Rechargeable), see Drill 3.

How to answer

Pick a domain example, state the four contract rules, and show the fix. Mention that "throws UnsupportedOperationException" in an override is the quickest LSP smell to spot.

Likely follow-ups
  • Is Java's unmodifiable List an LSP violation?
  • How does LSP relate to design by contract?
  • Square/Rectangle: what if both are immutable?
Is Collections.unmodifiableList() throwing on add() an LSP violation?

Formally, no: List.add is documented as an optional operation that may throw UnsupportedOperationException, so throwing honours the base contract. In spirit, yes: the contract was weakened for every caller, and every user of List must now consider that add can fail. The cleaner design is separate read and write roles (Kotlin's List vs MutableList, or Guava's ImmutableList as its own type). It is a good example of ISP and LSP being two sides of one problem.

How to answer

Show you know "optional operations" in the Collections docs, then give the cleaner alternative. Nuance wins here.

Likely follow-ups
  • How would you design read-only and mutable views?
What is Interface Segregation? When would you split an interface?

Clients should not be forced to depend on methods they do not use. Split when implementers start writing empty or throwing methods, or when different clients use disjoint subsets. Example: a Machine with print/scan/fax forces a basic printer to stub two methods. Split into Printer, Scanner, Fax; a multifunction device implements all three.

An Amazon SDE-1 LLD round asked for devices with different capability combinations (display, speaker, charging); the candidate reported the design got messy when one class re-implemented the same capability three times (2026-08). Role interfaces plus composition (a Tablet holding a Display and a Speaker component) keep it clean.

How to answer

Give the smell (stub methods), the split, and the composition follow-through so implementations are not duplicated.

Likely follow-ups
  • Can interfaces become too small?
  • How does the kernel's file_operations handle optional operations?
Dependency Inversion vs Dependency Injection vs Inversion of Control - what is the difference?
  • Dependency Inversion (DIP) is a design principle about direction: the high-level module defines the abstraction it needs (MessageChannel) and the low-level detail (EmailChannel) implements it. Source-code arrows point toward the policy.
  • Dependency Injection (DI) is a technique: an object receives its collaborators (constructor, setter) instead of creating them. It is the usual way to achieve DIP.
  • Inversion of Control (IoC) is the broad idea that a framework calls your code (callbacks, containers, event loops). A DI container (Spring) is one form.
How to answer

Three bullets, one sentence each, then Drill 5's code. Interviewers want to hear that DIP is about who owns the interface.

Likely follow-ups
  • Constructor vs setter vs field injection?
  • Can you do DI without a framework?
  • What is a composition root?
Why do we need inheritance if composition can do the same thing?

Inheritance is the right tool for a true, stable is-a relationship where the subtype honours the whole base contract (LSP) and you want polymorphic substitution plus shared implementation - e.g. a sealed hierarchy of Shapes or exception types. Composition is better when behaviour varies independently along several axes, when you need to change behaviour at runtime, or when the base class is not designed for extension (fragile base class). Default to composition, inherit deliberately. Asked at Walmart SDE-3 (2024-10).

How to answer

Do not say "inheritance is bad". Give one case each way and the deciding questions: is it really is-a? will behaviour vary on more than one axis? do I control the base class?

Likely follow-ups
  • What is the fragile base class problem?
  • Interfaces with default methods: inheritance or composition?
Where would you use interfaces in your design?

At the seams where implementations vary or will be swapped: strategies (pricing, allocation, split type), external gateways (payment, notification, storage), and roles that different classes play (Refuelable, Printer). Also where tests need a fake. Not for every class: an entity like Seat with one implementation does not need ISeat. Asked in a Cleartrip LLD round (2026-07).

How to answer

Point at your own diagram: "these three boxes are interfaces because X varies; these are concrete because they don't".

Likely follow-ups
  • Abstract class or interface for PaymentGateway?
