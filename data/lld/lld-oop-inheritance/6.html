The diamond problem

Take Device with a field id. Switch and Router both extend it. An L3Switch is both a switch and a router, so it extends both. Two questions follow: how many Device parts does an L3Switch contain? and if Switch and Router both override a method, which one does L3Switch get? Each language answers differently.

C++: two copies by default, virtual to share

struct Device { int id; explicit Device(int i) : id(i) {} };
struct Switch : Device { explicit Switch(int i) : Device(i) {} };
struct Router : Device { explicit Router(int i) : Device(i) {} };
struct L3Switch : Switch, Router { L3Switch() : Switch(1), Router(2) {} };
// a.id -> error: request for member 'id' is ambiguous

struct VDevice { int id; explicit VDevice(int i) : id(i) {} };
struct VSwitch : virtual VDevice { VSwitch() : VDevice(1) {} };   // ignored when not most-derived
struct VRouter : virtual VDevice { VRouter() : VDevice(2) {} };   // ignored when not most-derived
struct VL3Switch : VSwitch, VRouter {
    VL3Switch() : VDevice(42) {}          // the MOST-DERIVED class constructs the virtual base
};
$ g++ -std=c++14 -Wall -Wextra -o diamond diamond.cpp && ./diamond
1) plain diamond:
  Device(1)
  Device(2)
  a.Switch::id=1 a.Router::id=2  (two Device sub-objects)
  sizeof(L3Switch)=8
2) virtual inheritance:
  VDevice(42)
  b.id=42 (one shared VDevice, built once by VL3Switch)
  upcast ok, base.id=42

Virtual inheritance is not free: the shared base is reached through an extra offset stored per object (a virtual base pointer or offset in the vtable), and the most-derived class must remember to construct the virtual base. That is why it is rare outside library code like std::iostream (which inherits from both istream and ostream, sharing one virtual ios_base state). If two parents override the same virtual method differently, C++ also requires the bottom class to override it, or the call is ambiguous.

Java: classes cannot form a diamond; interfaces can, and you must decide

Java avoids the state half of the problem completely: a class has one superclass, and interfaces have no instance fields. Since Java 8 interfaces can have default methods, so the behaviour half came back. Java resolves it with three rules, in order:

  1. Class wins. A method declared in a class (or inherited from a superclass) beats any interface default.
  2. More specific interface wins. If B extends A and both provide the default, B's version is used.
  3. Otherwise you must override, and you may pick or combine with X.super.method(). If you do not, it is a compile error.
interface Logger  { default String log(String m) { return "[log] " + m; } }
interface Auditor { default String log(String m) { return "[audit] " + m; } }

static class Gateway implements Logger, Auditor {
    // Without this: "class Gateway inherits unrelated defaults for log(String)" - compile error
    @Override public String log(String m) { return Logger.super.log(m) + " + " + Auditor.super.log(m); }
}

static class BaseSvc { public String log(String m) { return "[base] " + m; } }
static class Svc extends BaseSvc implements Logger { }   // rule 1: BaseSvc.log wins
3) default-method diamond:
  [log] login + [audit] login
  [base] start   (class wins over interface default)

Python: one linear order (C3 MRO) and cooperative super()

Python allows full multiple inheritance and flattens the graph into a single list, the method resolution order (MRO), computed by the C3 algorithm: children before parents, and left-to-right order of the bases is kept. super() means "next class in the MRO", not "my parent", so when every class calls super().__init__(), each class in the diamond runs exactly once.

class L3Switch(Switch, Router):
    def __init__(self, **kw):
        print("  L3Switch.__init__")
        super().__init__(**kw)
# each of Switch, Router, Device also calls super().__init__(**kw)
$ python mro.py
MRO: ['L3Switch', 'Switch', 'Router', 'Device', 'object']
  L3Switch.__init__
  Switch.__init__
  Router.__init__
  Device.__init__

"Why doesn't Java support multiple inheritance?" Strong answer: "Java supports multiple inheritance of type (a class can implement many interfaces) but not of state (one superclass), which removes the duplicated-field half of the diamond. Since default methods, behaviour conflicts can happen, and Java makes them explicit: class wins, then the more specific interface, otherwise the class must override and choose with X.super.m(). C++ allows it fully and uses virtual base classes; Python linearises with the C3 MRO."
