Constructor order, static initialisers and super

A child object contains a parent "part". The parent part must be valid before the child's code touches it, so construction runs top-down: the root parent first, the most-derived class last. Destruction (in C++) runs in the reverse order: child destructor first, then parents. Static initialisation happens earlier and only once, when each class is first loaded and initialised, also parent first.

  1. First use of EthernetPort triggers class initialisation. The parent class is initialised first: Device's static {} block runs.
  2. Then NetDevice's static block.
  3. Then EthernetPort's. These three never run again for later objects.
  4. Now the object. Each constructor's first statement is a call up the chain: super(...), written or implied. The calls go up until Object().
  5. Bodies run on the way back down. The root's field initialisers and body finish first.
  6. Then NetDevice: its field initialisers, then its body (this.mtu = mtu).
  7. Finally EthernetPort's body. Only now is the whole object valid.

The rules of super

  • super(args) calls a parent constructor. In Java it must be the first statement (or you write this(...) instead). If you omit it, Java inserts super(), which fails to compile if the parent has no no-arg constructor. In C++, you name the parent in the initializer list: NetDevice(...) : Device(name), mtu_(mtu) {}.
  • super.method() calls the parent's version of an overridden method. Use it to extend behaviour (our describe() chain) instead of copy-pasting the parent's code. C++ writes Device::describe(); Python writes super().describe().
  • Constructors are not inherited. A child must declare its own (C++11 lets you opt in with using Base::Base;).
  • Never call an overridable method from a constructor. In Java the child's override runs while the child's fields are still zero; in C++ the parent's version runs because the object is "still a parent" during the parent constructor. Both surprise people. See initialisation order.
