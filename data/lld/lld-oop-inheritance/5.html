Overriding vs hiding

This is a favourite trick question. Overriding applies to instance methods: the child redefines a method with the same signature, and the version that runs is chosen by the runtime type of the object (dynamic dispatch). Hiding applies to static methods and to fields: the child declares a member with the same name, both exist, and which one you get is chosen by the static type of the expression, at compile time.

static class Device {
    String describe() { return "device " + name; }   // instance: can be overridden
    static String kind() { return "Device.kind"; }   // static: can only be hidden
    String tag = "Device.tag";                         // field: can only be hidden
}
static class EthernetPort extends NetDevice {
    @Override String describe() { return super.describe() + ", ethernet"; }
    static String kind() { return "EthernetPort.kind"; }
    String tag = "EthernetPort.tag";                   // a SECOND field; Device.tag still exists
}

Device d = new EthernetPort("eth0");   // static type Device, runtime type EthernetPort
2) overriding vs hiding:
  d.describe()  -> device eth0, mtu 1500, ethernet   (overriding: runtime type decides)
  Device.kind() -> Device.kind, EthernetPort.kind() -> EthernetPort.kind   (static: no dispatch)
  d.tag -> Device.tag, p.tag -> EthernetPort.tag   (fields: static type decides)

Always write @Override (Java) or override (C++): if you misspell the name or get a parameter type wrong, the compiler tells you instead of silently creating an overload. Use final on a method to forbid overriding, and on a class to forbid subclassing (String is final). Java 17 added sealed classes: sealed interface Shape permits Circle, Square fixes the exact set of subclasses, which is handy for closed hierarchies like the states of an order.

C++ name hiding goes further. If Base has f(int) and f(double) and Derived declares just f(int), then both base overloads are hidden for calls through a Derived. Bring them back with using Base::f;. And in C++ a method that is not virtual is never dispatched dynamically, even if the child redefines it; that is hiding too. Details in polymorphism and vtables.
