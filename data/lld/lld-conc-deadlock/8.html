Interview questions

Where this is asked

Lock ordering is the answer the interviewer wants whenever one operation touches two of something:

Snapchat's phone screen asked for a detector that reads a log of lock acquire/release events and reports the line where a deadlock first appears (LeetCode Discuss, 2016-06-15): that is the wait-for graph and cycle check from the detection section above.

What is a deadlock, and what four conditions are needed?

A set of threads each waiting for a resource held by another thread in the set, so none can proceed. It needs mutual exclusion, hold-and-wait, no preemption and circular wait, all at once (the Coffman conditions). Remove any one and deadlock is impossible.

How to answer

Definition in one line, the four names, then immediately say which one you would break in this design and how. The last part is what gets marks.

Likely follow-ups
  • Which condition does lock ordering break? (Circular wait.)
  • Which does tryLock break? (No preemption.)
Write a thread-safe transfer(from, to, amount) that cannot deadlock.

Lock both accounts in a global order (lower id first), check the balance, move the money, unlock in finally. If from == to, return early or lock once (a reentrant lock would not deadlock, but the logic is meaningless). If ids could tie, use a third tie-breaker lock.

How to answer

Write the naive version first in two lines and point at the ABBA problem, then the ordered one. Mention the alternatives: tryLock with back-off, or a single-threaded ledger.

Likely follow-ups
  • Now transfers can involve three accounts (fees). (Sort all ids.)
  • What if accounts live in a database? (Row locks in id order, or optimistic versions; retry on 40P01.)
Your service hangs in production. How do you confirm it is a deadlock?

Take two or three thread dumps a few seconds apart (jstack or jcmd Thread.print). The JVM prints "Found one Java-level deadlock" if monitors or ReentrantLocks form a cycle. If not, look for threads blocked on the same lock in every dump (contention or starvation), threads parked in take() / get() with no producer (lost signal), or all pool threads waiting on futures for work queued behind them (pool self-deadlock).

How to answer

Tools first, then the four stuck patterns. Close with prevention: timeouts on every wait, and a health check using findDeadlockedThreads().

Likely follow-ups
  • How do you recover without a restart? (Usually you cannot for monitors; that is why timeouts and tryLock matter.)
Deadlock vs livelock vs starvation?

Deadlock: blocked in a cycle, no CPU used, no progress. Livelock: threads keep reacting to each other (retrying, backing off in lockstep), CPU busy, no progress. Starvation: the system progresses but one thread never gets its turn (unfair lock, reader flood, priorities).

How to answer

The bridge story, then one fix each: lock order; random back-off; fair lock or shorter critical sections.

Likely follow-ups
  • Why is ReentrantLock unfair by default? (Barging gives higher throughput.)
Can you deadlock with only one lock, or with no locks at all?

Yes. With one non-reentrant lock a thread can block on itself (a Semaphore(1) acquired twice by the same thread). With no locks: a fixed thread pool whose tasks wait on futures of tasks queued in the same pool; two actors waiting synchronously on each other's replies; a bounded queue where the consumer is also the only producer of what it waits for. The cycle is in waiting, not in mutexes.

How to answer

Generalise: deadlock = cycle in the wait-for graph of any resource, including threads and queue slots.

Likely follow-ups
  • Why is synchronized safe to re-enter? (Monitors are reentrant; they count holds per owner.)
Food ordering: lock the restaurant or the item?

Lock the item, because two orders for different items should not wait for each other. But never nest: if one path holds the restaurant lock and then takes item locks while another holds an item lock and calls something that takes the restaurant lock, you have ABBA. Pick one level per operation. For a multi-item cart, sort item ids and lock in order, or skip locks and use an atomic conditional decrement per item with compensation if a later item fails.

How to answer

Granularity trade-off (contention vs complexity), then the ordering rule, then the lock-free alternative.

Likely follow-ups
  • Optimistic vs pessimistic here? (See the booking lesson.)
How does the Linux kernel catch lock-order bugs before they hang?

lockdep groups locks into classes, records the order in which classes are taken (and the IRQ context), and reports a possible circular dependency the first time an acquisition would complete a cycle in that graph, even if no hang happened. It turns "rare interleaving" bugs into deterministic warnings on the first run of each path.

How to answer

Great place to use your background; then map it to Java: documented lock levels plus an ordered-lock wrapper in tests.

Likely follow-ups
  • Why lock classes, not lock instances? (Millions of instances; the order rule is per type.)
Dining philosophers: give two solutions.

(1) Resource ordering: number the forks, each philosopher picks the lower-numbered fork first; the last philosopher then reaches for fork 0 first, which breaks the cycle. (2) Limit the table: a semaphore lets only N-1 philosophers try to eat at once, so at least one always gets both forks. Others: tryLock both and put down on failure (with random back-off), or a waiter (central arbiter).

How to answer

Map each solution to the Coffman condition it breaks.

Likely follow-ups
  • Which solution can starve a philosopher? (tryLock without fairness; the arbiter if it is unfair.)
