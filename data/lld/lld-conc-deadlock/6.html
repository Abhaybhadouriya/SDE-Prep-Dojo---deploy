Livelock and starvation: the cousins

Livelock

Livelock is what tryLock code turns into when every thread backs off for the same fixed time. They retry in lockstep and collide again. Signs: high CPU, rising retry counters, no completed work. Fixes:

  • Random back-off (jitter), and usually exponential growth with a cap, the same idea as Ethernet's binary exponential back-off after a collision and as retry jitter in client libraries.
  • A retry limit or deadline, after which you fail the request with "busy, try again" instead of spinning.
  • If contention is the normal case, stop retrying and switch to ordered blocking locks; tryLock is best when conflicts are rare.

Starvation

A thread is starved when it is runnable but never gets the resource. Common causes:

  • Unfair locks. new ReentrantLock() is non-fair by default: a thread that just arrived can "barge" ahead of threads already queued. That gives higher throughput, but a waiter can lose many times in a row. new ReentrantLock(true) hands the lock out in roughly arrival order, at a throughput cost. synchronized makes no fairness promise.
  • Reader-heavy read-write locks. A steady stream of readers can keep a writer out. See the LRU drill for why a read-write lock is often the wrong tool anyway.
  • Priority. A low-priority thread never scheduled while high-priority work exists. In real-time systems the related bug is priority inversion (a low-priority holder is pre-empted by medium-priority work while a high-priority thread waits); the cure there is priority inheritance, which Linux rt-mutexes implement.
  • Long critical sections. One thread holds the lock while doing I/O, so everyone else waits. Do I/O outside the lock.
