Finding a deadlock: thread dumps, the JVM, lockdep, the database

Prevention is the design answer. Detection is the "it is 2 a.m. and checkout is hung" answer, and good interviewers ask for both.

Java: take a thread dump

Run jstack <pid> (or jcmd <pid> Thread.print, or kill -3 on Linux, which prints to the process's stdout). The JVM walks the wait-for graph of monitors and ReentrantLocks and prints any cycle at the bottom. This is real output from Hang.java in the code folder (JDK 21, a few lambda frames removed):

Found 1 deadlock.
  • In code: ManagementFactory.getThreadMXBean().findDeadlockedThreads() returns the ids of threads in a cycle (monitors and ownable synchronizers like ReentrantLock). Some teams run it from a health check and page on a non-empty result.
  • Waiting on a condition is not in the cycle check. A thread parked forever in queue.take() or future.get() with no producer is "stuck" but the JVM will not call it a deadlock, because no lock owner exists. Timeouts on every blocking call are your protection there.
  • Thread pool self-deadlock: a task running on a fixed pool of size 4 submits sub-tasks to the same pool and waits on their futures. When all 4 threads are waiting, the sub-tasks never get a thread. No lock is involved, yet nothing moves. Fix: a separate pool for sub-tasks, or non-blocking composition (CompletableFuture.thenCompose).

Kernel: lockdep

From your world

CONFIG_PROVE_LOCKING (lockdep) does not wait for a hang. It tracks lock classes (all locks initialised at the same place share a class), records every "took B while holding A" edge, and reports "possible circular locking dependency detected" the first time an acquisition would close a cycle, even if the two paths ran minutes apart on one CPU. It also checks IRQ-safety rules (a lock taken in hard-IRQ context must be taken with IRQs disabled elsewhere). That is the Java lock-order rule enforced by a tool. The C++ tab above is a 60-line toy of that idea; in Java the closest equivalents are static analysers and lock-order checkers in tests, plus documented lock levels in code review.

Databases detect it for you

Relational databases build the wait-for graph of row locks and, when they find a cycle, abort one transaction (PostgreSQL raises error 40P01 deadlock_detected; MySQL InnoDB rolls back the cheaper transaction with error 1213). Your code must catch that error and retry the whole transaction. The prevention rule is the same as in memory: update rows in a consistent order (for example ORDER BY id before SELECT ... FOR UPDATE). More on row locks in the booking lesson.
