Under the hood: vptr and vtable

How does d->xmit(1500) know which function to call? The C++ standard does not say, but every mainstream compiler (GCC and Clang follow the Itanium C++ ABI; MSVC has its own layout) uses the same idea:

  • For each class with virtual functions, the compiler emits one read-only vtable (virtual method table): an array of function pointers, one slot per virtual function, in declaration order. A subclass's table copies the parent's slots and replaces the ones it overrides.
  • Every object of such a class carries a hidden pointer, the vptr, usually at offset 0. The constructor sets it to point at the table of the class being built.
  • A virtual call becomes: load the vptr from the object, load slot n from the table, make an indirect call, passing the object as the hidden this argument.

Click through one call, d->xmit(1500), where d is a NetDevice*:

  1. The pointer d holds the address of an object. The calling code only knows "this is some NetDevice".
  2. Load 1: read the hidden vptr from the start of the object. The Ethernet constructor stored the Ethernet table's address there.
  3. Load 2: the compiler knows xmit is slot 2 in every NetDevice-family table, so it reads vptr[2]. The slot number is fixed at compile time; only the table differs.
  4. Indirect call to the address found, passing d as this. Ethernet::xmit runs and adds 18 bytes of header and FCS.
  5. For a Loopback object the instructions are identical. Its vptr leads to a different table, so a different function runs. One call site, many behaviours.
class NetDevice {
public:
    explicit NetDevice(const char* name) : name_(name) {
        // During the base constructor the object is still "a NetDevice":
        // its vptr points at NetDevice's table, so this prints "generic".
        std::printf("  constructing %s, kind() says %s\n", name_, kind());
    }
    virtual ~NetDevice() { std::printf("  ~NetDevice(%s)\n", name_); }
    virtual const char* kind() const { return "generic"; }
    virtual int xmit(int len) = 0;               // pure virtual: no default
    void report(int len) {                       // non-virtual, but calls virtuals
        std::printf("  %-4s %-9s xmit(%d) -> %d bytes on wire\n", name_, kind(), len, xmit(len));
    }
protected:
    const char* name_;
};

class Ethernet : public NetDevice {
public:
    explicit Ethernet(const char* name) : NetDevice(name), ring_(new int[256]) {}
    ~Ethernet() override { delete[] ring_; std::printf("  ~Ethernet frees its ring\n"); }
    const char* kind() const override { return "ethernet"; }
    int xmit(int len) override { return len + 18; }   // 14 header + 4 FCS
private:
    int* ring_;
};

class Loopback : public NetDevice {
public:
    Loopback() : NetDevice("lo") {}
    const char* kind() const override { return "loopback"; }
    int xmit(int len) override { return len; }
};
/* One table per "class", shared by every object of that class (like .rodata). */
struct netdev_vtable {
    const char *(*kind)(const struct netdev *self);
    int         (*xmit)(struct netdev *self, int len);
};

/* Every object starts with a pointer to its class table: the vptr. */
struct netdev {
    const struct netdev_vtable *vptr;
    const char *name;
};

/* A "virtual call": load vptr, load slot, indirect call. Exactly what d->xmit(len) compiles to. */
static void report(struct netdev *d, int len)
{
    printf("  %-4s %-9s xmit(%d) -> %d bytes on wire\n",
           d->name, d->vptr->kind(d), len, d->vptr->xmit(d, len));
}
$ g++ -std=c++14 -Wall -o vtable vtable.cpp && ./vtable

2. Build devices (watch kind() inside the base constructor):

3. One loop, two behaviours (dynamic dispatch through the vptr):

From your world

The hand-made C version is the kernel pattern exactly. struct net_device has a const struct net_device_ops *netdev_ops; struct file has f_op; struct sock reaches struct proto. LWN's "Object-oriented design patterns in the kernel" calls these vtables by name. The differences: the compiler writes the table, guarantees every slot is filled, sets the vptr in the constructor, and type-checks this. You lose the kernel's option of swapping one function pointer at run time on a single object (C++ tables are read-only and shared per class); to get that flexibility in C++ or Java you hold a separate strategy object instead, which is the Strategy pattern.

What does a virtual call cost?

  • Memory: one pointer per object, one table per class. Tiny, unless you have millions of small objects (then it can matter, like an extra field in sk_buff).
  • Time: two dependent loads and an indirect branch. Usually cheap when the branch predictor guesses right. The bigger cost is that the compiler cannot inline a call when it does not know the target.
  • Java's JIT: HotSpot can often remove the cost. If only one class implementing a method is loaded, or profiling shows one receiver type at a call site, it inlines the call with a cheap type check and undoes this if a new class shows up. Marking classes final also helps C++ compilers devirtualize.
