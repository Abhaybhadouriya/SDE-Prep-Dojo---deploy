Using it in LLD: replace the switch with polymorphism

In a machine-coding round, polymorphism shows up as a refactoring the interviewer expects you to know: Replace Conditional with Polymorphism. If you see the same switch (type) in several places, each new type forces edits in all of them. Move each branch into its own class behind an interface.

// BEFORE: one function knows every vehicle type. Adding "TRUCK" means editing it
// (and every other switch like it scattered around the code base).
enum VehicleType { BIKE, CAR, BUS }
static int feeBefore(VehicleType t, int hours) {
    switch (t) {
        case BIKE: return 10 * hours;
        case CAR:  return 20 * hours;
        case BUS:  return 50 * hours + 100;
        default:   throw new IllegalArgumentException("unknown type " + t);
    }
}
// AFTER: each type owns its rule. Adding Truck = one new class, no edits elsewhere.
interface Vehicle { int fee(int hours); }
static final class Bike implements Vehicle { public int fee(int h) { return 10 * h; } }
static final class Car  implements Vehicle { public int fee(int h) { return 20 * h; } }
static final class Bus  implements Vehicle { public int fee(int h) { return 50 * h + 100; } }
static final class Truck implements Vehicle { public int fee(int h) { return 80 * h + 150; } }
// ALTERNATIVE (Java 21): a closed set of data types + an exhaustive switch.
// Good when the TYPES are fixed but you keep adding new OPERATIONS.
sealed interface Ticket permits Hourly, Monthly {}
record Hourly(int hours) implements Ticket {}
record Monthly(int months) implements Ticket {}
static int price(Ticket t) {
    return switch (t) {                 // compiler error if a permitted type is missing
        case Hourly h  -> 20 * h.hours();
        case Monthly m -> 3000 * m.months();
    };
}
$ javac -d out ReplaceSwitch.java && java -cp out ReplaceSwitch
before: car 3h = 60
after:  Bike 3h = 30
after:  Car 3h = 60
after:  Bus 3h = 250
after:  Truck 3h = 390
sealed: 60 / 3000

Which one is right? It depends on what changes more often. This trade-off is called the expression problem:

Polymorphic classes win when
  • New types keep arriving (new vehicle, new payment method, new notification channel).
  • Each type has its own data and several behaviours.
  • You want the Open/Closed Principle: add a class, edit nothing.
A sealed switch wins when
  • The set of types is fixed (the cases of a parse result, the states of a protocol).
  • New operations keep arriving (pricing, rendering, auditing over the same types).
  • You want the compiler to flag every switch when a case is added.

You will see the polymorphic version all over the case studies: parking fee by vehicle type in Parking Lot, split types in Splitwise, and piece moves in Chess.
