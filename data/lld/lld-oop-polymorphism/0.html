The story: one socket, many machines

Explain like I'm 5

The wall in your kitchen has one kind of socket. Plug in a kettle and water boils. Plug in a lamp and the room lights up. Plug in a phone charger and the battery fills. The socket does not know what you plugged in. It just gives power the same way every time, and each machine does its own thing with it. If tomorrow you buy a toaster, you do not change the wall. You just plug it in.

That is polymorphism (Greek for "many shapes"): one way of calling, many behaviours. The socket is the interface (or base class). The kettle, lamp and charger are implementations (subclasses). Plugging in is the method call. The wall not caring what is plugged in is why polymorphic code is easy to extend: new machines need no new wiring.

From your world

You use this every day. The VFS calls file->f_op->read(...) without knowing whether the file lives on ext4, procfs or a character device. Each driver fills in its own struct file_operations. That table of function pointers is runtime polymorphism. C++ and Java simply generate the table for you, put a hidden pointer to it in every object, and type-check every call.

Where this breaks: in the kernel a NULL slot often means "use the default" or "not supported", and you check for it. In C++ and Java every slot is always filled (with the inherited method if a class does not override it), so you never test a slot for NULL.

The interview question you will hear is short: "What is the difference between compile-time and runtime polymorphism, and how does runtime polymorphism work under the hood?" By the end of this page you can answer both halves in two minutes, with a drawing.
