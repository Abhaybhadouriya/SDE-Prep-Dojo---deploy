Overloading: the compiler decides

With overloading, several methods share a name, and the compiler chooses one by looking at the declared types of the arguments at the call site. The object's real class at run time plays no part. This surprises people, so it is a favourite trick question.

// ---- 1. Compile-time polymorphism: overloading ----
// Same name, different parameter lists. javac picks ONE of these
// while compiling, using the STATIC (declared) type of the argument.
static String describe(Object o)  { return "describe(Object)"; }
static String describe(String s)  { return "describe(String)"; }
static String describe(Integer i) { return "describe(Integer)"; }
static String describe(long n)    { return "describe(long)"; }

Now call them:

Object o = "hello";        // the object is a String, but the variable is declared Object
describe("hello");          // describe(String)
describe(o);                // describe(Object)   <- not String!
describe(42);               // describe(long)     <- not Integer!
$ javac -d out Dispatch.java && java -cp out Dispatch
1. Overloading uses the static type, decided by javac:
  describe("hello") -> describe(String)
  describe(o)       -> describe(Object)
  describe(42)      -> describe(long)
  describe(42L)     -> describe(long)

Two lessons hide in that output:

  1. Static type wins. o holds a String, but the compiler only knows "Object", so it bakes describe(Object) into the bytecode. Overloading never looks at the runtime object.
  2. Java has a fixed order of conversions. For 42 (an int) javac first tries an exact match, then widening (int to long), and only then boxing (int to Integer), and last of all varargs. Widening comes first, so describe(long) wins. The rules live in the Java Language Specification, section 15.12.

From your world

C has no overloading, so you wrote htons/htonl or kmalloc/kzalloc: one name per variant. C++ allows one name by quietly mangling it into a unique linker symbol per parameter list (on GCC, describe(int) becomes _Z8describei). Run nm on a C++ object file and you will see them. That is why overloading costs nothing at run time: after compiling, the overloads are just different functions.

Careful: two methods that differ only by return type are not overloads; javac rejects them. And mixing overloading with inheritance is confusing: if a subclass adds equals(Point p) instead of overriding equals(Object o), it has overloaded it, and collections keep calling the old one. Always put @Override on overrides so the compiler catches this.
