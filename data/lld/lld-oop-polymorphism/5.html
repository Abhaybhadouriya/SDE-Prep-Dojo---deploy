Virtual destructors and virtual calls in constructors

Two classic traps come straight from how the vptr is set up.

Trap 1: deleting through a base pointer

If you delete a derived object through a base pointer and the base destructor is not virtual, the call is bound at compile time to the base destructor only. The C++ standard calls this undefined behaviour; in practice the derived destructor is skipped and its resources leak.

struct BadBase    { ~BadBase()    { std::printf("  ~BadBase\n"); } };       // NOT virtual
struct BadDerived : BadBase {
    ~BadDerived() { std::printf("  ~BadDerived\n"); }
};

BadBase* b = new BadDerived();
delete b;   // undefined behaviour: base destructor is not virtual
4. Destroy through base pointers (virtual destructor = full cleanup):

5. Missing virtual destructor (undefined behaviour; this compiler skips ~BadDerived):

Rule: in C++, a class meant to be used through a base pointer needs a public virtual destructor (or a protected non-virtual one so nobody can delete through the base). If a class has any virtual function, give it a virtual destructor. Java and Python have garbage collection and no destructor to forget, but the same idea shows up as close() in AutoCloseable.

Trap 2: calling a virtual method from a constructor

Look again at line 2 of the output: constructing eth0, kind() says generic. While NetDevice's constructor runs, the object is not an Ethernet yet. C++ sets the vptr to the base table first, and switches it to the derived table only when the derived constructor starts. So a virtual call from a base constructor runs the base version.

Java does the opposite, which is worse: the object's class is fixed from the start, so a base constructor calling an overridden method runs the subclass version, before the subclass's fields have been assigned. Those fields are still null or 0. Either way, the advice is the same: do not call overridable methods from constructors. Use a factory method or an explicit init() step.
