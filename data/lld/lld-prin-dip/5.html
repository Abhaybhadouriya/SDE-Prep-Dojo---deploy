The subtle part: who owns the interface?

Many people "apply DIP" by writing interface IMySqlOrderDao next to the MySQL class and calling it done. That misses the point. If the interface lives in the infra package and is shaped like MySQL, the order package still depends on infra. Nothing was inverted.

Abstraction shaped by the detail (leaky)
  • executeSql(String sql)
  • ResultSet findRows(String where)
  • Lives in package infra.mysql
  • Swapping to DynamoDB means changing the interface and every caller
Abstraction shaped by the policy (good)
  • save(Order o)
  • Order byId(String id)
  • Lives in package order
  • Swapping to DynamoDB means one new class; callers untouched

That is rule 2 of DIP: abstractions should not depend on details. An interface that returns a JDBC ResultSet depends on a detail even if it is technically an interface. The test: could you implement this interface with an in-memory HashMap in ten lines? If yes, it is a good abstraction.

This idea grows into ports and adapters (hexagonal architecture) and clean architecture: the core defines ports (interfaces it needs), and the outside world plugs in adapters (MySQL, Kafka, REST). If you can explain DIP with ownership, you can explain those architectures in an HLD round too.
