What is the Dependency Inversion Principle? How is it different from Dependency Injection?

DIP is a principle: high-level policy should not depend on low-level details; both depend on abstractions, and the abstraction is owned by the policy side. Dependency Injection is a technique for supplying collaborators from outside, typically through the constructor. DI is the usual way to apply DIP, but you can inject a concrete class (DI without DIP) and you can wire by hand in main() (DIP without a container).

How to answer

Principle vs technique, then one sentence each for IoC and Service Locator. Draw the before/after arrows if there is a whiteboard.

Likely follow-ups
  • What exactly is "inverted"?
  • Constructor vs field injection?
Design the fare calculation for a ride-hailing app so new pricing (surge, pool, airport flat rate) can be added without touching the trip code.

The trip module owns interface FareCalculator { Money fare(Trip t); }. TripService takes a FareCalculator in its constructor. BaseFare, SurgeFare (decorates another calculator with a multiplier from an injected SurgeProvider) and AirportFlatFare implement it. A small factory at the composition root picks one per city/product. Time comes from an injected Clock so tests can fix "6 pm".

How to answer

Name the abstraction, say which package owns it, show constructor injection, mention the test seam (Clock), and connect to OCP: new pricing = new class.

Likely follow-ups
  • How do you combine surge and pool? (Decorator)
  • Where does the city-to-calculator mapping live?
Why is constructor injection preferred over field injection?

Dependencies are explicit in the signature; fields can be final (immutable, safely published); the object can never exist half-wired; a plain unit test can build it with fakes without a container; and a long constructor is a visible SRP warning. Field injection hides all of that behind reflection.

How to answer

Give 3 crisp reasons; mention setter injection for genuinely optional deps.

Likely follow-ups
  • What about circular dependencies? (constructor injection exposes them at startup, which is a feature - break the cycle with an event or a new abstraction)
"If the call still goes from OrderService to MySQL at runtime, what is actually inverted?"

The source-code (compile-time) dependency and the ownership of the contract. Before, the order package imported the MySQL package. After, the MySQL package imports the order package's interface. The flow of control is unchanged; the flow of dependency is reversed, so changes in MySQL code can no longer force changes in the order code.

How to answer

Separate "flow of control" from "direction of dependency". Draw two arrows going opposite ways.

Likely follow-ups
  • How does this relate to hexagonal architecture?
Would you create an interface for every class to follow DIP?

No. Interfaces cost names, indirection and navigation. I add them at volatile boundaries: I/O (storage, network), third-party services, clock and randomness, and policies the problem says will vary (pricing, matching, splitting). Value objects and stable domain classes stay concrete. If a second implementation appears later, extracting an interface is a quick refactor.

How to answer

Show judgement: DIP balanced with YAGNI and KISS.

Likely follow-ups
  • How would you test a class that calls LocalDateTime.now()?
How does the Linux kernel apply DIP between the network stack and NIC drivers?

The core defines struct net_device_ops; drivers include the core's header, implement the function pointers, and register with register_netdev(). The core never includes driver headers. The driver depends on the core's abstraction (DIP), receives its objects as arguments (DI), and is called by the core when there is work (IoC).

How to answer

Great for systems candidates: map each of DIP, DI and IoC to a concrete kernel mechanism.

Likely follow-ups
  • Where else does the kernel do this? (VFS file_operations, block layer, notifier chains)

Scenario: "Now make it send SMS too"

Forty minutes into a machine-coding round, your BookingService works and sends email with new EmailClient() inside confirm(). The interviewer says: "Some users want SMS. Also, how would you test confirm()?"
"I'll add an if (user.prefersSms) branch inside confirm() and create an SmsClient there. For testing I'd run it against a test mail server."
"I'll introduce a Notifier interface owned by the booking package, inject it through BookingService's constructor, and move the email code into EmailNotifier. SMS becomes SmsNotifier; per-user choice is a small NotifierSelector (or a Strategy map keyed by preference) wired in main(). For tests I pass a RecordingNotifier that stores messages in a list, so confirm() runs with no network."
Follow-ups: "What if notification fails - should booking fail?" (decouple: queue/outbox, retry); "What if there are ten channels?" (registry of channels, Observer for fan-out).
