Pitfalls: when DIP goes wrong

  1. Interface for everything. IOrder, IMoney, IAddress for value objects with one implementation forever is noise. Apply DIP at volatile boundaries: I/O, third-party services, clocks, randomness, policies likely to vary (pricing, matching, payment).
  2. Leaky abstractions. Repository.findBySql(String) or returning vendor types (ResultSet, SdkResponse) means the abstraction depends on a detail.
  3. Abstraction in the wrong package. Interface next to the implementation, policy still imports infra. Nothing inverted.
  4. Constructor with 8+ dependencies. DIP did not cause it; it revealed it. The class has too many jobs (SRP). Split it or introduce a Facade over a cluster of collaborators.
  5. Service Locator everywhere. ServiceRegistry.get(X.class) deep inside methods makes dependencies invisible and tests order-dependent.
  6. Static calls and singletons. PaymentGateway.getInstance().charge() inside business logic is a hidden hard-wire. Inject it instead; see Singleton for the trade-offs.
  7. Hidden time and randomness. LocalDateTime.now() inside a fare calculator makes "surge at 6 pm" untestable. Inject a java.time.Clock.

Senior signal: "I put interfaces only where I expect a second implementation or need a test seam - storage, notifications, payments, the clock. Inside the domain I use plain classes." This shows you balance DIP with YAGNI.
