Concurrency and thread safety

Even in a "design only" round, expect "what if two requests arrive at once?". Walk the shared state.

  1. A client retries a bulk send, and both copies arrive together. With "check, then add" both see the key as new and both enqueue: the user is notified twice.
  2. The guard: keys.add(key) on a ConcurrentHashMap.newKeySet() tests and inserts in one atomic step. Only one caller gets true.
  3. The second copy gets false and returns as a duplicate without touching the queue. Exactly one job is sent.

The worker's wait, line by line

  • Timed wait until the head is due. changed.await(head.sendAt - now): the worker sleeps exactly as long as needed; no polling every 10 ms.
  • Re-check in a while. After waking (signal, timeout or spurious wake-up) it re-evaluates "is the head due?", because a new, earlier job may have arrived, or nothing changed.
  • Signal on every submit. A new job may be earlier than the one the worker is waiting for; the signal makes it recompute its timeout.
  • Deliver outside the lock. Providers take hundreds of milliseconds. Holding the queue lock while sending would block every submit.

From your world

This loop is a kernel timer queue in miniature: the earliest-expiry job is the head of a heap (like the next hrtimer in the red-black tree), and the worker programs its "alarm" for that time. Adding an earlier timer reprograms the alarm, which is exactly what changed.signal() forces. Delivering outside the lock is the softirq rule again: take the item off the queue under the spinlock, do the slow work after dropping it.

More workers, and per-user order

One worker is a bottleneck when providers are slow. Two ways out, with different trade-offs:

Pool of N workers on the same queue
  • Simple: same loop, N threads.
  • Throughput scales with N.
  • Two messages to one user may arrive out of order ("shipped" before "placed").
Lane per user: hash(userId) % N
  • Keeps per-user order: one lane serves one user.
  • A hot user only slows their own lane.
  • This is the partition idea from the pub-sub case.

A further option is a small executor per channel so a slow SMS gateway cannot starve e-mail; combine it with per-channel bulkheads (bounded queues) so one provider's outage does not eat all memory.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • Condition.await / awaitNanos, wait / notifyAll = pthread_cond_wait / pthread_cond_timedwait; always recheck the predicate in a while loop because of spurious wake-ups, as wait_event() does.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
