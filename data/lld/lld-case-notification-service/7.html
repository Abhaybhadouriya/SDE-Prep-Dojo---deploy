APIs and interfaces

// Facade used by application code
Optional<String> submit(NotificationRequest r);  // id, or empty if the idempotency key was seen
int  processDue();                               // synchronous: deliver every due job now
void start(); void stop();                       // background worker
void optOut(String userId, Channel c);
List<DeliveryRecord> historyOf(String userId);

// The request: WHAT to say, to WHOM, WHEN, how URGENT, on which channels
record NotificationRequest(String idempotencyKey, String userId, String templateId,
                           Map<String,String> params, Set<Channel> channels,
                           Priority priority, long sendAtMs) {}

// Extension points
interface ChannelSender { String send(Message m) throws DeliveryException; } // Strategy (+ Decorators)
interface EventListener { void onEvent(DomainEvent e); }                     // Observer
interface Clock { long nowMs(); }                                             // injected time

Design notes worth saying aloud. submit returns an id so the caller can query status later, and an empty result for duplicates instead of throwing, because a duplicate is a normal event in distributed systems. send returns the provider that delivered, which goes into history ("via sms-B") and is the first thing support asks for. DeliveryException carries a retryable flag: a timeout is worth retrying, "invalid phone number" is not.

If they ask for a DB schema (Swiggy, Walmart style)

notification(id PK, idempotency_key UNIQUE, user_id, template_id, params_json,
             priority, send_at, status, created_at)          -- index (status, send_at, priority)
delivery(id PK, notification_id FK, channel, provider, status, detail, attempt, at)
                                                             -- index (notification_id), (user_id, at)
template(id, channel, version, body, PRIMARY KEY (id, channel, version))
user_channel_pref(user_id, channel, opted_in, quiet_from, quiet_to, PRIMARY KEY (user_id, channel))
user_address(user_id, channel, address, verified, PRIMARY KEY (user_id, channel))

The UNIQUE constraint on idempotency_key is the durable version of seenKeys: two servers racing to insert the same key get one row and one constraint error. The worker's "poll due jobs" becomes SELECT ... WHERE status='PENDING' AND send_at <= now() ORDER BY send_at, priority LIMIT 100 FOR UPDATE SKIP LOCKED, which lets several workers share the table without taking the same row.
