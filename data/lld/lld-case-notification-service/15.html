Follow-up questions

Why Strategy per channel instead of an abstract Notification class with subclasses per channel?

A notification is what to say; a channel is how to deliver it. One notification goes out on several channels, and the same channel carries many notification types. Subclassing EmailNotification, SmsNotification ties the two together, so "order shipped on SMS and push" needs two objects that duplicate content, and a new channel means a new subclass of every notification type. With a request plus a ChannelSender per channel, the two axes vary independently: N types plus M channels, not N times M classes.

How to answer

Name the two axes of change, show the N x M explosion, then the composition fix. This is the Bridge idea too.

How do priorities work, and can a flood of LOW promotions delay an OTP?

Among jobs that are due, the queue orders HIGH before MEDIUM before LOW, so an OTP submitted after 10,000 promotions is the next one taken. It can still wait for the job currently being sent, and for the provider: if the SMS gateway is saturated by promotions, the OTP queues there. The fix is separation: HIGH goes on its own sender chain (its own provider account, as PhonePe asked), is exempt from per-user rate limits, and in a pool gets reserved workers. Starvation of LOW is possible in theory; ageing (raise priority after waiting T) fixes it if the business cares.

How to answer

Queue order first, then the hidden queues (worker, provider), then isolation and ageing.

The order service retried and published ORDER_PLACED twice. What stops a double SMS?

Each rule derives a deterministic idempotency key from the event, such as 101/placed/customer. submit adds it to a concurrent set; add returns false for the second copy, so nothing is queued. In a database the same is a UNIQUE index on the key. The key must come from the business event, not from a random UUID created on each attempt, or every retry looks new.

How to answer

Deterministic key, atomic insert-if-absent, durable version with a unique index.

A provider times out. Did the SMS go or not? How do you retry safely?

A timeout is ambiguous: the message may have been sent. Retrying gives at-least-once delivery, which is acceptable for most notifications but not ideal for, say, a "payment received" SMS. Options: pass our notification id as the provider's idempotency or client reference field when the provider supports it; prefer the provider's status webhook over blind retry; and for the rare cases where a duplicate is worse than a miss, mark the error non-retryable. Our DeliveryException.retryable flag is where that decision lives.

How to answer

Say "ambiguous outcome", then at-least-once, provider-side dedupe, and the per-error retry decision.

Why Decorators for retry and rate limiting instead of putting them in the service?

They are per channel and per provider choices: e-mail wants 3 retries, SMS wants failover and a spam limit, in-app wants neither. In the service they would become flags and if chains per channel. As decorators each is a small class with one job, tested alone, and composed in setup code in any order. The order is a real design decision: limiter outside retry so a retried send counts once; failover inside retry so one dead gateway costs no backoff.

How to answer

Per-channel variation, SRP, composable order. Draw the onion.

How do you schedule "send in one hour" without a thread per job?

Put the job in the same priority queue with sendAt = now + 1h. The worker waits with a timeout equal to the head's remaining time, wakes when it is due, or earlier if a new job arrives (signal). One thread serves any number of scheduled jobs. For durability the queue becomes a table indexed by (status, send_at) and workers poll it. Cancelling a scheduled notification is a status change the worker checks before sending.

How to answer

Delay queue, timed wait, signal on insert; then the persistent version and cancellation.

Two threads submit at the same time. Walk through what can go wrong.

Three places. Dedupe: a contains then add on a plain set lets both through, so we use one atomic add on a concurrent set. The queue: PriorityQueue is not thread-safe, so push and poll are under one lock, and the signal is sent while holding it. The rate limiter: "count, compare, record" must be one critical section or two sends both take the last slot. Everything else is immutable records or concurrent maps. Delivery happens outside the queue lock so submitters never wait for providers.

How to answer

Walk every shared structure, name the race, name the fix. The concurrency table on this page is the script.

Likely follow-ups
  • Would PriorityBlockingQueue work? (Yes for ordering, but you still need a timed wait for the head's due time; DelayQueue does both.)
Design Windows-style notifications where many apps raise toasts. What changes?

The "channel" becomes the local display surface (toast, action centre, badge), and the senders are renderers. The new concerns are per-app permissions and settings (an app can be muted), focus / do-not-disturb modes (queue and show later, like quiet hours), grouping and replacing (a newer toast from the same app and tag replaces the old one), limits per app, and an action centre that is the history with read state. The same skeleton fits: requests from apps, a preference check, a priority queue, renderers as strategies.

Each channel has several providers and each provider several accounts; OTPs must use a separate account. Where does that logic go?

Inside the sender for that channel, never in the service. Model ProviderAccount implements ChannelSender (credentials and quota per account), a RoutingSender that picks the account list by message priority or type (OTP accounts vs bulk accounts), and a FailoverSender or random selector over the active accounts. Per-type mandatory fields (an e-mail needs a subject, a soundbox needs an amount) are validated by the template or a per-channel validator at submit time.

Observer here vs a real message broker: when would you switch?

The in-process EventBus calls listeners synchronously in the publisher's thread and loses events if the process dies. That is fine inside one service and in an LLD round. Once producers are other services, or events must survive crashes and be replayed, put a broker between them (Kafka topic per event type) and make the rules consumers. The listener code barely changes; the transport does. Salesforce's "news alert subscriptions" is this exact Observer with users as subscribers to topics.

How to answer

Sync and in-memory vs async and durable; the switch point is process boundaries and durability.
