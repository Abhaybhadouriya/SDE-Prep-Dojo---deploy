Clarify requirements

Spend 5-8 minutes here. This prompt is short and vague on purpose ("design a notification system"), so the requirement list is where you show judgement. Write it down; it becomes your demo script.

Functional

  1. Channels Send through e-mail, SMS, push and in-app. Adding a channel (WhatsApp, a payment soundbox) must not change the core.
  2. Triggers Business events (order placed, shipped, delivered) produce notifications for different audiences: customer, seller, logistics partner. Direct API calls (an OTP) also work.
  3. Templates Each notification type has a template per channel with placeholders; missing parameters are rejected at submit time.
  4. Preferences A user can opt out of a channel. A user without an address for a channel (no app installed) is skipped, not an error.
  5. Priority HIGH (OTP, fraud alert) goes before MEDIUM (order updates) and LOW (promotions).
  6. Scheduling "Send at T" ("ask for a rating one hour after delivery").
  7. Reliability Retry transient provider errors with backoff; fail over to a second provider for the same channel.
  8. Protection Rate-limit non-urgent messages per user; never send the same notification twice when the caller retries (idempotency key).
  9. History Record every outcome per channel (sent, failed, skipped, rate-limited) and let support query a user's history.

Non-functional

  • Callers never wait for providers. submit validates and enqueues; sending happens on a worker.
  • Thread-safe under many concurrent callers.
  • One channel's failure does not block the others (SMS down must not stop e-mail).
  • Testable without sleeping: time is injected (a clock), so scheduling and rate limits are tested in microseconds.
  • Open for extension: new channel, provider, retry rule or limit is a new class, not an edit to NotificationService.

Out of scope (say it)

  • Real provider SDKs (SES, Twilio, FCM). We use fake providers that can be told to fail.
  • Durable storage of the queue and history; we keep them in memory and say where a database would go.
  • Distributed workers, Kafka, provider quotas across machines (HLD).
  • Rich template language, localisation, A/B tests, analytics (mention as follow-ups).
