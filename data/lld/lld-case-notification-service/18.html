The interviewer says "now add WhatsApp". In this design, what changes?

  1. A new case in NotificationService's switch
  2. A new ChannelSender class, an enum value, an address and a template, plus one registration
  3. A new subclass of every notification type
  4. The EventBus
Strategy per channel: the service does not change.

ORDER_PLACED is published twice by an upstream retry. What prevents a double send?

  1. The rate limiter
  2. The priority queue
  3. A deterministic idempotency key added atomically at submit
  4. The retry decorator
The key, e.g. 101/placed/customer, is accepted once.

Why is the rate limiter the outermost decorator in the SMS chain?

  1. So a send that is retried counts once against the user's limit
  2. So it runs last
  3. Because decorators must be sorted by name
  4. So failover is skipped
Inside the retry, each attempt would use a slot.

Two jobs are due now: a LOW promo submitted first and a HIGH OTP submitted second. Which is sent first?

  1. The promo, FIFO
  2. Both at once
  3. Whichever was rendered first
  4. The OTP: same send time, higher priority
Comparator: send time, then priority, then sequence.

Why does the worker deliver after releasing the queue lock?

  1. Providers need the lock
  2. Providers are slow; holding the lock would block every submit
  3. Java forbids I/O under a lock
  4. To keep FIFO order
Take the job under the lock, do slow work outside it.

A user has no device token and you were asked to send push. What should happen?

  1. Throw and stop all channels
  2. Retry until a token appears
  3. Record NO_ADDRESS for push and continue with the other channels
  4. Send by SMS silently
Explicit status per channel; a fallback channel would be a deliberate feature.

Which error should the retry decorator NOT retry?

  1. "Invalid phone number"
  2. Gateway timeout
  3. HTTP 503 from the provider
  4. Connection reset
Permanent errors are non-retryable; retrying only adds load and delay.
