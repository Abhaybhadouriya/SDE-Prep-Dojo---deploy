Core flows

Order placed: event, submit, deliver over SMS with failover

  1. The order service publishes ORDER_PLACED with the order data. Two rules are subscribed to that type: one for the customer, one for the seller. The customer rule builds a request with idempotency key 101/placed/customer and channels e-mail, SMS and push.
  2. submit checks the user and template exist and does a dry-run render for each channel, so a missing {name} fails now, at the caller, not at 3 a.m. in a worker log. The key is new, so the job goes into the priority queue and the caller gets n1 back immediately.
  3. The upstream retried and published the same event again. seenKeys.add returns false, so submit returns empty and nothing is queued. This is how "published twice" turns into "sent once".
  4. The enqueue signalled the condition variable. The worker wakes, takes the earliest due job under the lock, releases the lock, then for each channel checks opt-out, address and template support, and renders the SMS body.
  5. The worker calls the one SMS sender it knows. Inside, the rate limiter counts it (1 of 3), the retry wrapper calls failover, failover tries sms-A (down, throws) and then sms-B, which succeeds. No backoff was needed because failover handled it.
  6. The sender returns the provider name. The worker appends a DeliveryRecord for SMS with status SENT. E-mail and push are handled the same way, each with its own record, so one channel's failure never hides another's success.

What the queue does with mixed jobs

JobsendAtpriorityseqDelivered
promo pushnowLOW62nd
OTP SMSnowHIGH71st (same time, higher priority)
rate-order e-mailnow + 1 hLOW8only after the clock passes now + 1 h

The comparator is send time, then priority, then sequence. Putting time first means a HIGH job scheduled for tomorrow does not jump ahead of a LOW job due now. If the interviewer wants "HIGH always first among due jobs, even if a LOW was due earlier", keep two structures: a delay queue by time that moves due jobs into a ready queue ordered by priority. Say the trade-off; both are defensible.

The flows in words

  1. Submit Validate user, template and parameters; dedupe on the key; wrap in a Job with a sequence number; push into the queue under the lock; signal; return the id.
  2. Worker loop Under the lock, wait while the queue is empty or the head is not due (timed wait until the head's sendAt); poll the head; release the lock; deliver.
  3. Deliver For each requested channel: skip if opted out; skip with NO_ADDRESS if the user has no address, no sender or no template for it; else render and call the sender; map exceptions to FAILED or RATE_LIMITED; append a record.
  4. Synchronous mode processDue() runs the same delivery for all due jobs on the calling thread. Tests and the demo use it with a fake clock.
