When to use it, when not to, and the testability cost

Use it when
  • There truly is one of the thing per process: one hardware device handle, one process-wide registry, one runtime.
  • Construction is expensive or must happen once (load a big rule file, open a pool).
  • The object is stateless or immutable after construction (constants, caches of pure data).
  • You need a quick, honest answer in a 45-minute machine-coding round and the interviewer accepts it.
Avoid it when
  • It is just a global variable with a nicer name. Any code can now change shared state, and you cannot see the dependency in a constructor signature.
  • Tests need a fake. OrderService that calls PaymentClient.getInstance() inside a method cannot be tested without the real client.
  • "One" might become "two": two tenants, two regions, two databases. Singletons make that change painful.
  • Mutable shared state under heavy contention: one lock becomes the bottleneck of the whole service.

Why people call it an anti-pattern

The pattern bundles two ideas. "Only one instance" is a lifetime decision. "Reach it from anywhere" is a coupling decision. The second one hides dependencies, breaks the Dependency Inversion Principle (code depends on a concrete class, not an interface), and leaks state between unit tests (test A leaves a value in the singleton, test B fails only when run after A).

The fix interviewers want to hear: create one instance at the composition root and inject it.

interface Clock { long now(); }

class OrderService {
    private final Clock clock;
    OrderService(Clock clock) { this.clock = clock; }      // dependency is visible
}

// main(): one real clock for the whole program ("singleton by convention")
Clock clock = System::currentTimeMillis;
OrderService orders = new OrderService(clock);

// test: a fake clock, no global state to reset
OrderService underTest = new OrderService(() -> 1_000L);

If you must keep a legacy singleton, add a package-private resetForTests() or hide it behind an interface so callers depend on the interface. Both are band-aids; injection is the cure. The kernel equivalent: code that hard-wires &init_net works until network namespaces arrive, which is why modern networking code passes a struct net * around instead.

Singleton for a database connection is a classic wrong answer. One connection serialises every query in the service. The right answer is one connection pool (often a singleton or a single injected bean) that hands out many connections. See Object Pool.
