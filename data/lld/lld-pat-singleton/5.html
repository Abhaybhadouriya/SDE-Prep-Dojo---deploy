Why DCL needs volatile

The line instance = new Config(); looks like one step. It is really three:

Declaring the field volatile fixes it. Under the Java memory model (Java 5 and later), a write to a volatile field "happens-before" every later read of that field. So everything the constructor wrote is visible to any thread that reads a non-null reference. The pre-Java-5 memory model could not fix DCL at all; that is the story told in the well-known "Double-Checked Locking is Broken" declaration linked in the resources.

From your world

This is exactly a publish/subscribe pair of barriers. In the kernel you would build the object, then publish it with smp_store_release(&global_ptr, obj) (or rcu_assign_pointer()), and readers would use smp_load_acquire() (or rcu_dereference()). Java volatile write = release, volatile read = acquire. Without them, a reader on another CPU can see the pointer before the stores that filled in the struct, which is the same bug you guard against with wmb() before ringing a NIC doorbell.

The small local variable in our code (DclConfig local = instance;) is an optional speed-up: it reads the volatile field once on the fast path instead of twice.
