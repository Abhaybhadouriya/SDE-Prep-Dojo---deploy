Interview Q&A

Write a thread-safe lazy singleton in Java.

Give two answers and say which you prefer. The holder idiom: a private static nested class with static final INSTANCE = new X(), and getInstance() returns Holder.INSTANCE. The JVM initialises the nested class only on first access and does it exactly once under its class-initialisation lock, so it is lazy, thread-safe and lock-free afterwards. Or DCL with a volatile field if they explicitly ask for it.

How to answer

Write the holder version first (fewer ways to get wrong), then offer DCL and enum, and name the trade-off of each in one line.

Likely follow-ups
  • Why is the holder lazy when the outer class is loaded?
  • What if construction throws an exception?
Why does double-checked locking need volatile? What exactly goes wrong without it?

instance = new X() is allocate, construct, assign. Without a memory barrier, the assignment can become visible to other threads before the constructor's writes. A thread doing the unlocked first check sees non-null and returns an object whose fields still hold default values. volatile gives the write release semantics and the read acquire semantics (a happens-before edge in the Java memory model), so a non-null reference implies a fully built object.

How to answer

Draw the three steps, show the reorder, then say "volatile write happens-before the volatile read". Mention that this only works since Java 5.

Likely follow-ups
  • Would making every field final help? (Yes. If the singleton is immutable with only final fields and this does not escape the constructor, DCL is correct without volatile because of the final-field rules (JLS 17.5), provided you read the field once into a local: a reader sees either null and takes the lock, or a fully built object. I still use volatile or the holder idiom, because one later non-final field silently breaks it.)
  • What is the C++ equivalent? (std::atomic with acquire/release, or just a function-local static.)
How can a singleton be broken, and how do you protect it?

Reflection (call the private constructor), serialization (deserialising makes a new object), cloning (if Cloneable), and multiple class loaders (one static per loader). Protect with a guard in the constructor that throws if an instance exists, readResolve() returning the real instance, not implementing Cloneable. Or use an enum, which the JVM protects against the first two automatically.

How to answer

List all four first, then defences, then end with "an enum solves both reflection and serialization".

Likely follow-ups
  • Can you break an enum singleton? (Not with reflection or serialization; a second class loader still gives a second enum class.)
Singleton vs a class with only static methods: which and why?

A singleton is an object, so it can implement an interface, be passed to a constructor, be replaced by a fake in tests, be lazily created, and hold resources with a clear lifetime. A static class is fixed at compile time and cannot be polymorphic. Use static methods for pure, stateless helpers (Math.max); use a single instance for anything with state or a resource behind it.

How to answer

Anchor on polymorphism and testability, give one example of each.

Likely follow-ups
  • Where does each live in memory, and when is it initialised?
Why is Singleton called an anti-pattern? What would you do instead?

Global access hides dependencies, couples callers to a concrete class, leaks state between tests, and makes "one" hard to change into "many" (multi-tenant, multi-region). Keep the single lifetime but drop the global access: create one instance at the composition root (or let Spring's singleton scope do it) and inject it through constructors, behind an interface.

How to answer

Separate "one instance" (fine) from "global access point" (the problem), then show a two-line constructor-injection example.

Likely follow-ups
  • How do you test code that already calls getInstance() everywhere?
  • Is a Spring singleton bean the same as GoF Singleton?
Should the database connection be a singleton?

No. One connection means every request queues behind one socket, and if it drops the whole service is down. Use a connection pool with a maximum size, validation on borrow and timeouts. The pool itself is typically a single shared object.

How to answer

Say "no, a pool" in the first sentence, then explain why, then mention HikariCP-style settings.

Likely follow-ups
  • Design the pool: what happens when it is exhausted?
In C++, is the Meyers singleton thread-safe? What about destruction order?

Since C++11, yes for construction: a function-local static is initialised once and concurrent callers wait. Destruction happens at program exit in reverse order of construction, so another static object's destructor that calls instance() after it was destroyed hits a dead object (the "static destruction order" problem). Fixes: never use singletons from destructors, or intentionally leak a heap instance (static X* p = new X;) so it is never destroyed.

How to answer

Construction: magic statics. Destruction: reverse order, the dead-reference risk, the leak trick.

Likely follow-ups
  • How would you do it with std::call_once?
  • Singleton in a shared library loaded twice?
How do you make a singleton in Python?

Usually you do not write a class at all: a module-level object is created once on first import and cached in sys.modules. If a class is required, override __new__ with a lock and a double check, or use a metaclass whose __call__ caches the instance. Remember __init__ runs on every call unless you guard it.

How to answer

Lead with "modules are singletons", then show __new__.

Likely follow-ups
  • What is the Borg pattern?
  • Does the GIL make the check-then-create race impossible? (No: a thread switch can happen between the check and the assignment.)
