In interviews

Singleton shows up in two ways. First as a standalone question: "write a thread-safe singleton", often in Java-heavy rounds (Walmart, Goldman Sachs, Adobe for C++). Our research found LeetCode interview reports of a Walmart round asking for DCL with volatile (post), another asking for a serialization-safe singleton (post), a Goldman Sachs round pairing a thread-safe singleton with a SOLID refactor (post), and an Adobe C++ round on smart pointers plus singleton (post).

Second, inside a case study, where the right move is to name the singleton and immediately say how you keep it testable:

  • Parking lot: one ParkingLot object for the building. Say "one instance, created in main and injected", not a static getInstance() that every class calls.
  • Logger: one logger per name (multiton) with thread-safe appenders.
  • Key-value store and LRU cache: one shared store, so the follow-up is about locking, not about the pattern.
  • Rate limiter: one limiter registry holding one bucket per user (multiton again).
  • Vending machine and elevator: one controller per machine or bank of lifts.

For the concurrency side of the same question (immutability, safe publication), see Thread-safe singleton and immutability.

A 60-second answer: "Private constructor, static instance, static accessor. For thread safety I prefer an enum or the holder idiom. If asked for lazy DCL, the field must be volatile because object creation can be reordered. I would defend against reflection and serialization with a constructor guard and readResolve. In real code I would rather create one instance at startup and inject it, so it stays testable."
