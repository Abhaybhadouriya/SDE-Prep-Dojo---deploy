Four ways to break a singleton (and the defences)

A follow-up interviewers like: "Your constructor is private. Can someone still make a second object?" Yes, four ways.

  1. Reflection. getDeclaredConstructor().setAccessible(true).newInstance() calls a private constructor. Defence: make the constructor throw if an instance already exists (our created flag), or use an enum, where the JDK refuses with "Cannot reflectively create enum objects". The guard only blocks a second instance: if reflection wins the very first call, the reflective object becomes the only one and every later get() throws from inside get(). That is why enum is the real answer.
  2. Serialization. Reading a serialized object back with ObjectInputStream builds a fresh object without calling your constructor. Defence: add private Object readResolve() { return getInstance(); } so the stream swaps the copy for the real one. Enums are serialized by name and come back as the same constant automatically.
  3. Cloning. If the class (or a parent) implements Cloneable, clone() copies it. Defence: do not implement Cloneable, or override clone() to throw CloneNotSupportedException.
  4. Several class loaders. A static field is "one per class per class loader". An app server or a plugin system that loads your class twice gets two singletons. Defence: there is no clean one inside the class; load it from a shared parent loader. This is a reminder that "only one" really means "only one per some scope".

Our Java demo runs both attacks. The output shows serialization same object = true and both reflection attempts blocked.

The enum answer is short and strong: "If I really need a Java singleton, I use a single-element enum. The JVM gives me one instance, thread-safe initialisation, and protection from reflection and serialization. I switch to the holder idiom only when the class must extend something."
