How it works: two threads race for the first call

The hard case is the very first call, when two threads ask at the same moment and the object does not exist yet. Step through the double-checked locking (DCL) version. "Check, lock, check again, create" is the whole trick.

From your world: two Java words before the stepper

Java synchronized (X.class) { ... } = mutex_lock() / mutex_unlock() on a lock that belongs to that object. Java volatile on a field = every write is a release and every read is an acquire, like smp_store_release() / smp_load_acquire(). It is not C volatile, which only stops the compiler caching the value in a register and gives no ordering between CPUs. The section "Why DCL needs volatile" below explains the reorder hazard in full.

  1. T1 calls getInstance(). First check without the lock: the field is null.
  2. T1 enters the synchronized block and owns the lock.
  3. T2 arrives a moment later. Its first check also sees null (T1 has not finished). T2 tries the lock and blocks.
  4. T1 checks again under the lock, still null, so it builds the object and writes it into the volatile field. Then it leaves the block.
  5. T2 finally gets the lock. Its second check sees the object T1 stored, so it does not build another. Without this second check, T2 would create object number two.
  6. From now on every call sees a non-null field on the first check and returns at once. The lock cost was paid only during the first race.

Two checks, two jobs. The first check (no lock) makes the common case fast. The second check (under the lock) makes the rare racing case correct.
