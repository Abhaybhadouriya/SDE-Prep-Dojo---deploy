Interview follow-ups

Why store sum and count instead of the average?

An average cannot be updated without the count, cannot be combined across months, and loses precision every time you round it. Sum and count are exact integers, update in O(1), add across buckets (all time = sum of months), and support removal (subtract). The average is computed only when someone reads it.

How to answer

Name the follow-ups it enables: monthly, edits, merging.

Likely follow-ups
  • What if you need the median? (Then keep a count per star value, 1 to 5: five counters per agent.)
Two agents have the same average. Who comes first, and how does your code decide?

Ask the interviewer. A sensible default is more ratings first (an average from 40 ratings is more trustworthy than one from 2), then agent id alphabetically so the output is deterministic. In the code the rule is a Comparator passed into the service, so changing it never touches the service or its other tests.

How to answer

Ask, propose a default with a reason, show the seam.

Likely follow-ups
  • "Most recent rating wins the tie": what do you add? (A lastRatedAt field in Stats.)
Why not compare averages as doubles?

Doubles usually work, but equal fractions can come out a bit apart after division, so a tie can be missed and the tie-break skipped, making the order unstable. Cross-multiplying (a.sum * b.count versus b.sum * a.count) compares exactly with integers. It is also cheaper than division.

How to answer

Show the inequality and why the sign is preserved (counts are positive).

Likely follow-ups
  • When can the product overflow a long? (When countA x countB x 5 passes 9.2e18: about 1.3 billion ratings each. Then use Math.multiplyExact, BigInteger, or __int128 in C.)
Now show me the best agents each month. What changes?

Ratings get a date. Add a second map keyed by YearMonth whose values are the same per-agent Stats maps, updated in rate next to the all-time map. bestOfMonth ranks that month's map with the same comparator. Old tests keep compiling through an overload of rate that takes the date from an injected Clock. Nothing else changes, which is what the interviewer is checking.

How to answer

"One more bucket map; same ranking code." Then write the test.

Likely follow-ups
  • Rolling 30 days instead of calendar months? (Daily buckets, sum the last 30 on read, drop older ones.)
How would you export the results as CSV and JSON?

An Exporter interface with one method that turns ranked rows into a string, and one class per format. The service passes rows through and never knows about commas or braces. CSV must quote fields containing commas, quotes or newlines (doubling inner quotes). JSON must escape quotes and backslashes in names; in production use a JSON library.

How to answer

Strategy, then the one format detail people forget (quoting).

Likely follow-ups
  • Stream a million rows without building one huge string? (Write to a Writer.)
Make rate() thread safe. Is your averages() consistent?

Stats is immutable and replaced with ConcurrentHashMap.compute, so each agent's update is atomic and a reader sees a whole (sum, count) pair. Different agents update in parallel. averages() iterates a weakly consistent view: each agent's value is valid, but the list is not a snapshot of one instant, and the all-time and monthly maps are updated in two steps. For a dashboard that is fine; for an exact report, take a lock (or a read-write lock) around both updates and the read.

How to answer

Per-key atomicity, then what is and is not consistent, then the stronger option.

Likely follow-ups
  • One agent gets 10,000 ratings a second. (LongAdder counters.)
A new agent with one 5-star rating tops the chart. Fix the ranking.

Use a Bayesian (damped) average: (sum + C x m) / (count + C), where m is a prior mean (say the global average) and C is how many "virtual" ratings the prior is worth. Agents with few ratings are pulled toward m; agents with many are barely affected. Alternatively, require a minimum count to be ranked. Both are a new Comparator in our design.

How to answer

Name the problem (small samples), give the formula, show it plugs into the same seam.

Likely follow-ups
  • How do you choose C? (Roughly the typical rating count, tuned with data.)
Why not keep agents in a PriorityQueue sorted by average?

A heap does not re-order when an element's key changes after insertion, so updating an agent's average in place corrupts it; and iterating a Java PriorityQueue is not in sorted order. You would have to remove and re-insert on every rating (O(n) removal for PriorityQueue). Sorting on read is O(n log n) and simple; a TreeSet with remove-reinsert gives O(log n) updates if reads must be instant.

How to answer

The mutable-key problem, then the two valid options with costs.

Likely follow-ups
  • Top 10 only, out of a million agents? (Size-10 heap over a snapshot, O(n log 10).)
A customer edits their rating from 2 to 5. Support it.

Key ratings by ticket id (one rating per ticket) in a map. An edit looks up the old stars and date, subtracts them from the right buckets (sum minus old, count unchanged), and adds the new stars. A delete subtracts stars and decrements count, removing the Stats entry at zero. Sum and count make every case O(1).

How to answer

Idempotency key (ticket id), then subtract-and-add.

Likely follow-ups
  • The edit lands in a different month from the original rating. Which bucket changes? (The original month's.)
Ratings now arrive as events from many services. How does this scale?

Ratings go into a queue (Kafka topic keyed by agent id, so one agent's events stay ordered in one partition). Consumers update per-agent, per-month counters in a store such as Redis (HINCRBY on sum and count) or a database row with an atomic increment. Rankings are computed periodically into a cached leaderboard, or kept live in a sorted set keyed by the damped average. Store the raw rating events too, so counters can be rebuilt. This is the real-time leaderboard design.

How to answer

Partition by agent, counters not averages, periodic ranking, raw log for rebuilds.

Likely follow-ups
  • A rating event is delivered twice. (Dedupe by ticket id.)
