Key relationships and patterns (and why each)

Pattern / choiceWhereWhy it earns its placeWhat you say in the room
Aggregate, do not store derived valuesStats(sum, count)Averages are derived on read. Monthly, weekly or all-time views are just different buckets of the same two numbers, and removing a rating is "subtract". Storing the average makes every follow-up harder."I store sum and count, never the average. Every view is derived on read, and a removal is a subtraction."
Strategy (as a Comparator)Rankings.DEFAULT, ALPHABETICAL_TIESThe tie-break rule is a product decision that changes. Passing a Comparator into the constructor keeps the service untouched when it does. In Java a Comparator is the smallest possible Strategy object."The ranking is a Comparator passed in. A new tie-break is a new comparator, not an edit to the service."
Strategy (interface)Exporter with CSV and JSONOutput format has nothing to do with ranking logic. A new format (XML, Markdown table) is a new class. The service never imports a format."Export format is a separate strategy, so ranking code never knows about CSV or JSON."
Immutable value objectsStats, AgentScoreAn immutable Stats lets ConcurrentHashMap.compute replace it atomically; readers always see a consistent (sum, count) pair, never a sum from one update and a count from another."Stats is immutable, so one compute() swaps sum and count together; a reader never sees half an update."
Bucketing by keybyMonth: Map<YearMonth, Map<agent, Stats>>"Per month" is one more map keyed by period. Per week, per team or per product are the same move with a different key."Per month is one more map keyed by period; per week or per team is the same move."
Open/Closed, test per stageStage tests in test_main.pyEach stage adds classes or a map; earlier tests keep passing unchanged. That is the evidence an Atlassian interviewer looks for."Each stage only adds code; the earlier tests keep passing unchanged."

From your world

The ranking Comparator is the cmp function pointer you pass to qsort() or to sort() in lib/sort.c: the sorting code is fixed, the order is plugged in, and returning negative / zero / positive is the same contract. The Exporter interface is a small ops table with one slot, like a seq_operations->show that decides how each record is printed while the iteration stays the same.

Patterns we deliberately skipped: a Singleton rating service (each test stage builds a fresh one), an Observer on every rating (nothing in the statement reacts to a single rating; add it when a leaderboard must update live), and a PriorityQueue kept in sorted order (see the warning below).

Do not keep agents in a PriorityQueue ordered by average and update it in place. A Java PriorityQueue does not re-sort when an element's key changes, and iterating it does not give sorted order. If you need a live top-k, use a TreeSet and remove-then-reinsert the agent on every rating; for this round, sorting on read is simpler and fast enough.
