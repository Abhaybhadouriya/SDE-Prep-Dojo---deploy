Concurrency and thread safety

Ratings come from many support sessions at once. The race to name: rate is read-modify-write on (sum, count). Two threads read (9, 2), both write (13, 3) and (14, 3), and one rating is lost. Worse, with two separate fields a reader can see the new sum with the old count and print an average above 5.

  1. Java: immutable Stats + ConcurrentHashMap.compute compute runs the remapping function atomically for that key, and the new Stats object replaces the old one in one step. Different agents update in parallel (the map locks per bin). Readers get a whole Stats or the previous one, never half of each. The Java driver proves it with 8 threads x 1,000 ratings.
  2. Two buckets are not one transaction All-time and monthly updates are two separate atomic steps. A reader between them can see the all-time count one ahead of the monthly count for a moment. Say this. If it matters, take one lock around both, or derive all-time by summing the months.
  3. Python: one lock Dictionary get-then-set is not atomic across threads, so rate takes a threading.Lock around both updates. Readers copy the dict under the lock and sort outside it.
  4. Hot agent contention If one agent gets thousands of ratings a second, every compute on that key serialises. Use striped counters: LongAdder for sum and for count, read together only for display, accepting that the pair is approximately consistent. This is per-CPU counters summed on read.
  5. Read-heavy ranking Sorting on every read is O(n log n). Cache the sorted list and invalidate on write, or recompute every few seconds; a dashboard does not need the exact current ranking.

From your world

Replacing an immutable Stats object instead of editing two fields is the RCU publish pattern in miniature: build the new version, publish it with one pointer store, and readers see either the old or the new snapshot. LongAdder is the per-CPU counter idea: each thread bumps its own cell, and the reader sums the cells.
