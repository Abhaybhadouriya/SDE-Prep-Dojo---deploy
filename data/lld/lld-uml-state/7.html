Failure modes: concurrent events, nested states and timers

Two events on the same object at once

A diagram processes one event at a time; a server receives "cancel" from the customer and "ship" from the warehouse in the same millisecond. If both read PACKED, one ships and the other refunds. The fix is to make each transition atomic: either one lock per object around read-state, check, act, write-state (declare fire() and tick() synchronized; the demo above is single-threaded, so it does not), or a compare-and-set on an immutable snapshot as with Trip above. In a database it is the conditional update ... WHERE id=? AND state='PACKED'. Whichever runs second sees the new state and gets "not allowed in SHIPPED" (or CANCELLED), which is correct.

From your world

The kernel's TCP code changes socket state with tcp_set_state() while holding the socket lock (process context takes lock_sock(); the softirq receive path takes the bottom-half socket lock and defers to the backlog if a user holds it). That is "one lock per object around every transition", and the backlog is the queue of events that arrived while the machine was busy.

Nested (hierarchical) states

Use a superstate when several states share the same exits. In code it is often a set (EnumSet.of(CREATED, PAID, PACKED), exactly what Order does for cancel) or a parent class in the State pattern whose default method handles the shared event. TCP has the same shape: the connection-teardown states (FIN-WAIT-1, FIN-WAIT-2, CLOSING, TIME-WAIT) all react to a reset by going to CLOSED, so a reset handler applies to the whole group rather than one arrow per state.

Timeouts are events too

after(7 days) and TCP's TIME-WAIT 2MSL timer are not background magic: a timer fires an event into the same machine, through the same lock or CAS, like any user action. Two traps: the timer may fire after the state already moved on (so the handler must check "am I still DELIVERED?", as tick() does), and a timer must be cancelled or ignored when its state is left (a payment-page hold that expires after the payment succeeded must not release the seats).
