In an interview, say which you picked and why: "four states with real behaviour each, so the State pattern; the order lifecycle has almost no per-state logic, so an enum plus a table".

The race on a transition

A state diagram assumes one event at a time. A server does not. In the Uber-style question "assign a premium cab without double-booking a driver", two drivers can tap "accept" in the same millisecond. Both read REQUESTED, both write ASSIGNED, and the rider has two cars.

record Assignment(TripState state, String driver) {}                     // immutable snapshot
static final class Trip {
    // CAS the whole snapshot (state + driver), not just the enum: no reader can ever see
    // ASSIGNED with driver == null, because both change in one atomic step.
    final AtomicReference<Assignment> snap = new AtomicReference<>(new Assignment(TripState.REQUESTED, null));
    boolean assign(String d) {
        Assignment cur = snap.get();
        if (cur.state() != TripState.REQUESTED) return false;
        return snap.compareAndSet(cur, new Assignment(TripState.ASSIGNED, d));   // exactly one winner
    }
}
// 4 threads race on assign(): output  "winners=1 state=ASSIGNED driver=driver-1"

CAS the whole snapshot, not just the enum. A tempting version does state.compareAndSet(REQUESTED, ASSIGNED) and then writes driver = d on the next line. Between those two lines another thread can read ASSIGNED with driver == null. Putting state and driver in one immutable record and swapping the record publishes both together. A synchronized transition method is the other correct answer.

From your world

This is cmpxchg on a state word: the same trick the kernel uses when it moves a socket or a page between states under contention. In a database, the same guard becomes a conditional update: UPDATE trip SET state='ASSIGNED', driver=? WHERE id=? AND state='REQUESTED', and "1 row updated" means you won.
