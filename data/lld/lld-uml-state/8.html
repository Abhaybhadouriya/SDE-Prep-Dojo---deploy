In the interview

When the prompt has a noun with a lifecycle (order, ride, ticket, booking, elevator, machine), spend two minutes drawing its states before coding. Then every method you write is "which transition is this?", and every edge case is "is there an arrow for that?".

Design the states of a vending machine. How do you implement them?

States: Idle, HasMoney, Dispensing (plus SoldOut or OutOfService if asked). Events: insert coin, select item, cancel, dispense done. Guards: [balance >= price], [in stock]. Actions: add to balance, refund, drop item, return change. Implement with the State pattern: a VendingState interface with one method per event, one class per state returning the next state; the machine delegates to its current state.

How to answer

Draw the diagram first, then say "each box is a class, each arrow a method". Handle undrawn events explicitly (ignore vs throw).

Likely follow-ups
  • Add a maintenance mode: what changes? (One new state class, a few arrows; no edits to the others' logic.)
  • Two users press buttons at the same time?
Model a ride's lifecycle. How do you stop two drivers being assigned to one ride?

States: REQUESTED, ASSIGNED, DRIVER_ARRIVED, IN_PROGRESS, COMPLETED, CANCELLED. The accept transition must be atomic: compare-and-set from REQUESTED to ASSIGNED in memory (AtomicReference.compareAndSet), or a conditional update (WHERE state='REQUESTED') in the database. The losers get "already assigned" and move on. Mirror this for the driver: AVAILABLE to ON_TRIP must also be atomic so a driver cannot take two rides.

How to answer

Point at the one arrow that races, name the primitive, and remember the driver's own state machine.

Likely follow-ups
  • What if the driver accepted but the trip-to-driver update fails? (Do both in one transaction, or a saga with compensation.)
What is a guard, and how is it different from an event?

An event is what happens (coin inserted, timer expired, "cancel" called). A guard is a boolean condition checked when the event arrives; the transition fires only if it is true. The same event can lead to different states depending on guards (select with enough money vs not enough).

How to answer

Use the vending select example: one event, two guarded transitions.

Likely follow-ups
  • What if two guards on the same event are both true? (The machine is ambiguous: make them mutually exclusive.)
switch, transition table, or State pattern: how do you choose?

switch on an enum for a handful of states with tiny behaviour; a transition table when there are many states but little per-state logic (the table is data you can print and test); the State pattern when each state has real behaviour of its own and you expect new states. Mention the cost: the pattern adds classes; switch scatters logic across methods.

How to answer

Give one example of each from the problem at hand: order status = table, vending/elevator = State pattern.

Likely follow-ups
  • How would you persist the state? (Store the enum name in the row; rebuild the state object on load.)
Draw the states of an elevator.

Minimal: IDLE, MOVING_UP, MOVING_DOWN, DOORS_OPEN (plus MAINTENANCE). Events: request(floor), arrived(floor), door timer, emergency. Guards: [floor > current] chooses MOVING_UP. Doors may open only when stopped: the diagram makes "move while doors open" impossible because no arrow allows it.

How to answer

Keep direction and door state separate if it gets messy, and leave scheduling (which request next) to a Strategy, not to the state machine.

Likely follow-ups
  • Where does the request queue live, and who decides the next stop?
When do you draw an activity diagram instead of a state diagram?

When the question is about the steps of a process rather than the life of one object: checkout, onboarding, refund approval, anything with parallel branches or several participants (swimlanes). State diagrams answer "what can this object do now?"; activity diagrams answer "what happens next in this workflow?".

How to answer

Contrast them in one sentence each, then point out fork/join as the activity diagram's unique power.

Likely follow-ups
  • Your fork runs payment and reservation in parallel. What if one fails? (Compensation.)
Your interviewer says: "this order can be cancelled after shipping in some regions". How does the design change?

Add a guarded transition: cancel [region allows post-ship cancel] / start return pickup from Shipped to a new state such as CancelRequested (it still needs the parcel back). Keep the rule outside the state machine in a policy object the guard calls, so regions can differ without new states per region.

How to answer

Show that a new rule is a new arrow (and perhaps a state), and that variable rules belong in a guard backed by a policy/Strategy.

Likely follow-ups
  • How do you test every transition? (Table-driven tests over (state, event) pairs, including the invalid ones.)

Scenario: "A shipped order got cancelled and refunded"

In your machine-coding solution, cancel() checks if (status != DELIVERED) and refunds. Support reports that orders already on the truck were cancelled and refunded, and still delivered.
Weak answer: add another check && status != SHIPPED in cancel().
Strong answer: the bug is a missing state diagram. A negative check ("not delivered") silently allows every state added later. Draw the lifecycle, list the states cancel may leave from (Created, Paid, Packed), and encode it positively: a transition table or State classes where cancel exists only on those states. Add tests for every (state, event) pair, including the disallowed ones. Make the transition atomic so a concurrent ship and cancel cannot both win.
Follow-ups: how do you migrate existing orders? How do you audit transitions? (Append a row per transition: from, to, event, actor, time.)
