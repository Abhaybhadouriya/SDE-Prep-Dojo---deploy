The story: the museum guide

Explain like I'm 5

You visit a huge museum. You do not get a map of every room, every storeroom and every staircase. You get a guide. The guide does only two things: tells you "there is one more painting" and walks you to it. You say "next", the guide shows the next painting. When there are no more, the guide says "that is all".

The museum can move paintings around, add a new wing, or keep half of them in the basement. You do not care. As long as the guide knows the way, you can see every painting. A second guide could even show you the same paintings in a different order: "oldest first" or "only the blue ones".

In code the museum is a collection (a list, a tree, a hash table, a ring buffer, a database table that comes back in pages). The guide is an iterator: a small object that remembers where you are and gives you the next element. Your loop talks only to the guide, so the collection is free to change how it stores things.

From your world

You already use iterators daily in the kernel. list_for_each_entry(pos, &head, member) walks any struct list_head chain without you touching next and prev by hand. And seq_file is an iterator written as an ops table: struct seq_operations has start, next, stop and show. The /proc reader calls them in a loop and never learns whether the data lives in a list, a hash table or an array. That ops table is the Iterator interface; each /proc file supplies its concrete iterator.
