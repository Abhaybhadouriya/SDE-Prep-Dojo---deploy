When to use it, when not to

Use it when
  • The collection has a non-trivial inside (tree, graph, hash table, ring buffer, paged API, file) that callers should not see.
  • You need several traversal orders over the same data (in-order and level-order, forward and reverse, filtered).
  • Data is large or infinite and should be produced lazily, one item at a time (streams, pages, generators).
  • You want your own type to work with the language's loops and libraries (for-each, STL algorithms, itertools).
Avoid or keep it simple when
  • It is a plain array or list in one class: an index loop or the built-in iterator is clearer than a custom class.
  • You need random access by position: an iterator walks forward and is the wrong tool for get(i).
  • The iterator would hold a lock or a database connection for a long time: callers may forget to finish, so prefer closing iterators (try-with-resources, with) or an internal iterator.
  • Writers change the collection constantly: decide the consistency story (snapshot, weakly consistent, lock) first.
