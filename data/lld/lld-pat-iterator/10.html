In interviews

Iterator shows up in two very different ways.

  1. As a coding problem. "Implement an iterator over X" is a common phone-screen and machine-coding task: BST iterator (LeetCode 173), Flatten Nested List Iterator (341), Peeking Iterator (284), Zigzag Iterator (281), Flatten 2D Vector (251). A public LeetCode Discuss report describes a Microsoft round asking for a post-order binary-tree iterator, and another collects a frequently reported Coinbase task of composable iterators (even/odd filters over an infinite stream, an interleaving iterator over several iterators, a limit iterator). The skill being tested: store the minimum state, make hasNext() idempotent (calling it twice must not skip an item), and compose iterators by wrapping one in another.
  2. Inside a case study. Whenever a design has a collection callers walk: a file system (walk a directory tree), a news feed (paged, merged timelines), a key-value store (range scans with a cursor), an LRU cache (iteration order), or a library catalogue (search results). Saying "the repository returns an iterator, so callers do not care that results come in pages" is a cheap, strong signal.

Coding-round checklist for any custom iterator: (1) what state do I keep, (2) is hasNext() free of side effects, or does it pre-fetch into a buffered "next" slot, (3) what does next() do at the end (throw NoSuchElementException), (4) time per call and memory, (5) what happens if the source changes.

Strong 30-second answer: "Iterator lets callers walk a collection without knowing its storage. The collection is a factory for iterators, each with its own cursor, so I can offer several orders and lazy loading. Java's iterators are fail-fast through a modCount check; concurrent collections use snapshot or weakly consistent iterators instead. In the kernel the same idea is list_for_each_entry and seq_file."
