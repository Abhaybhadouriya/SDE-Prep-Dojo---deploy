Fail-fast vs fail-safe (weakly consistent)

The classic interview question: what happens if the collection changes while you iterate?

KindHow it worksExamplesCost
Fail-fastThe collection keeps a change counter (modCount). The iterator saves it at creation and compares on each next(). A mismatch throws.ArrayList, HashMap, LinkedList iterators; Python dict and set raise RuntimeError on a size changeOne integer compare. Detection is best effort, not a thread-safety guarantee: the JDK docs say you must not rely on it for correctness.
Snapshot (fail-safe)The iterator walks a copy taken when it was created. Writers make a new copy.CopyOnWriteArrayList, CopyOnWriteArraySetEvery write copies the array. Good for read-mostly lists such as listener lists. Iterator remove() is unsupported.
Weakly consistentNo copy and no exception. The iterator may or may not show changes made after it started, but never shows an element twice or crashes.ConcurrentHashMap, ConcurrentLinkedQueueCheap and concurrent. Results are "some valid state", not one exact moment.
UndefinedNo check at all.C++ std::vector iterators after a reallocating push_back; a Python list changed mid-loop (items are silently skipped)Free, and dangerous: dangling pointers or wrong results.

The right way to delete while walking is to delete through the iterator (it.remove() in Java, it = v.erase(it) in C++, iterate over list(d) in Python), or to use a bulk operation like removeIf. The kernel has the same rule: plain list_for_each_entry() breaks if the body frees the current node, so you use list_for_each_entry_safe(), which saves the next pointer before the body runs.

Fail-fast is a bug detector, not a lock. Two threads sharing an ArrayList can still corrupt it without an exception. For real concurrency pick a concurrent collection or a lock (see concurrent collections).
