Interview Q&A

What is the difference between a fail-fast and a fail-safe iterator?

A fail-fast iterator (ArrayList, HashMap) checks the collection's modification counter on every next() and throws ConcurrentModificationException if the collection was changed other than through the iterator itself. A fail-safe or snapshot iterator (CopyOnWriteArrayList) walks a copy, so it never throws but may miss recent changes. Concurrent maps and queues use weakly consistent iterators: no copy, no exception, may or may not reflect concurrent updates. Fail-fast detection is best effort and single-threaded in spirit; it is not a thread-safety mechanism.

How to answer

Define both, explain the modCount mechanism in one sentence, give one class each, add the third category (weakly consistent) to stand out.

Likely follow-ups
  • How do you remove elements safely while iterating? (it.remove() or removeIf.)
  • Why is CopyOnWriteArrayList a good fit for listener lists?
Design an iterator over a binary search tree that returns values in sorted order.

Keep a stack. In the constructor push the root and all its left children. next() pops a node, then pushes its right child and that child's left chain, and returns the popped value. hasNext() is "stack not empty". Memory is O(h); each node is pushed and popped once, so next() is amortised O(1). Flattening the whole tree into a list first works but uses O(n) memory and does all the work up front.

How to answer

Say the naive O(n) flatten first, then the stack solution with its complexity. Mention that a Python generator expresses the same thing recursively.

Likely follow-ups
  • Post-order instead of in-order?
  • What if the tree is modified during iteration?
Implement a PeekingIterator on top of a normal iterator.

Wrap the inner iterator and keep a one-element buffer: a nextVal field plus a hasPeeked flag. peek() fills the buffer if empty and returns it. next() returns the buffer if full (and clears it), else delegates. hasNext() is hasPeeked || inner.hasNext(). This is a decorator over an iterator: same interface plus one method.

How to answer

State the buffer invariant, then code three methods. Point out that the same wrapping idea composes filter, limit and interleave iterators.

Likely follow-ups
  • Make it generic.
  • Build an interleaving iterator over k iterators. (A queue of iterators; take from the front, push back if it still has items.)
External vs internal iteration: when would you choose each?

External (pull) iteration puts the caller in control: easy to stop early, skip, or walk two sequences in lockstep (merge two sorted lists). Internal (push) iteration hands a function to the collection (forEach, streams, map), which lets the collection optimise: run in parallel, batch, or hold a lock once for the whole walk. Choose external for complex control flow, internal for simple per-element work or parallelism.

How to answer

One example of each and one reason to prefer each.

A repository returns millions of rows. How do you expose them to callers?

Return an iterator (or a stream) that fetches pages lazily using keyset pagination: remember the last key seen and ask for "rows after key K, limit N". Callers write one loop; memory stays bounded at one page. Make the iterator closeable so a connection or cursor is released if the caller stops early, and document the consistency (rows inserted during the scan may or may not appear). Offset-based pages get slower and can skip or repeat rows when data changes, so the cursor should be a key, not an offset.

How to answer

Iterator hides paging, keyset beats offset, closeable, consistency statement.

Likely follow-ups
  • How would a REST API expose the same thing? (Opaque next_page_token.)
Why does the kernel have both list_for_each_entry and list_for_each_entry_safe?

The plain macro computes the next element from pos->member.next after the loop body runs. If the body frees or unlinks pos, that read touches freed memory. The _safe variant keeps a second cursor that already holds the next element before the body runs, so deleting the current node is safe. It does not protect against other threads; that still needs a lock, or the _rcu variant for lock-free readers. This is the kernel's version of "remove through the iterator".

How to answer

Explain the read-after-free, the extra cursor, and the concurrency caveat. Link it to Java's it.remove().

Your hasNext() reads from a network stream. What can go wrong?

hasNext() can only answer by trying to read ahead, so it must buffer what it read and hand it out on the next next(). Otherwise calling hasNext() twice loses an item. It may also block or fail: decide whether an I/O error becomes an unchecked exception, a sentinel, or a separate error state, and make the iterator closeable. Python generators and Java's Scanner both handle this with an internal look-ahead buffer.

How to answer

Idempotent hasNext() via a look-ahead slot, then errors and resource cleanup.
