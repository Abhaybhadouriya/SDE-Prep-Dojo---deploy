Embedding and container_of: inheritance in C

Java says class Ext4Inode extends Inode. The kernel puts the base struct inside the derived struct and gets back from base to derived with pointer arithmetic:

struct ext4_inode_info {
    /* ... ext4-only fields: extents, journal state ... */
    struct inode vfs_inode;          /* the "base class", embedded */
};

static inline struct ext4_inode_info *EXT4_I(struct inode *inode)
{
    return container_of(inode, struct ext4_inode_info, vfs_inode);   /* the "downcast" */
}

The VFS only ever sees struct inode *. The file system allocates the bigger struct through super_operations->alloc_inode (a factory method) and recovers its own fields with container_of. According to LWN part 2, the kernel moved to this layout from an older design in which struct inode held a union of every file system's private data: every new file system had to edit a shared header, and every inode was as large as the largest variant. That union was removed during 2.5 development.

TechniqueOOP meaningTrade-off
Embedding + container_ofInheritance; the derived object contains the baseOne allocation, no extra pointer; the preferred approach
void *private (i_private, s_fs_info, seq_file->private)Composition through an untyped pointerExtra allocation and dereference, no type safety; LWN calls it usually a poor choice
Union of variantsA closed sum typeFine when one module knows all variants; bad for extension

Two other embedding tricks you use every day are patterns too. struct list_head embedded in your object is what LWN calls the embedded anchor: one object can sit on several lists by embedding several anchors, and list_for_each_entry is an Iterator that hands you the enclosing object. And struct work_struct embedded in your context struct is how a Command carries its arguments (next sections).
