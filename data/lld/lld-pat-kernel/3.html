Ops tables: the kernel's interfaces and vtables

The LWN article on object-oriented patterns in the kernel describes several variations. Knowing them by name makes you sound fluent:

  • Pure vtable: a struct containing only function pointers, usually named *_operations or *_ops and declared const. Every object of that "type" points to the same table. This is exactly what a C++ compiler generates for a class with virtual functions.
  • NULL means "default" or "not supported": the caller checks before calling. vfs_create() refuses when an inode has no create op, and an absent ndo_change_mtu means the core uses its default. In Java you would write a default method; in C++ a non-pure virtual with a base implementation.
  • Mixin tables: a second, independently chosen ops table on an object that already has one. tcp_congestion_ops is the classic: a TCP socket already has its protocol ops, and you choose congestion control (cubic, bbr, reno) separately per socket with setsockopt(TCP_CONGESTION). That is the cleanest Strategy in the kernel.
  • Singleton ops: when there is only one object (the platform's suspend handling, the active security module hooks), the methods drop the object argument. That is a Singleton plus a Strategy chosen at boot.
  • Function pointers embedded in the object: when an object has only one or two methods, or each object needs its own, the pointer lives in the object itself (sk_data_ready in struct sock). This is a per-object strategy or callback.

Ops table or Bridge or Strategy? Use the intent test from the look-alikes page: tcp_congestion_ops swaps one algorithm inside a socket (Strategy); file_operations separates the whole generic file layer from every file system (Bridge). Both are "struct with an ops pointer".
