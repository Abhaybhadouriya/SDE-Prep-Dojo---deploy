Netfilter hooks: Chain of Responsibility

A module registers a struct nf_hook_ops with a hook function, a protocol family, a hook point (NF_INET_PRE_ROUTING, LOCAL_IN, FORWARD, LOCAL_OUT, POST_ROUTING) and a priority. Each packet passing a hook point visits the registered functions in priority order. Each returns a verdict:

VerdictMeaningChain behaviour
NF_ACCEPTfine by mecontinue to the next hook
NF_DROPdiscard the packetstop; packet freed
NF_STOLENI took ownershipstop; the hook is now responsible for the packet
NF_QUEUEsend to user spacestop here, continue later after the user-space verdict

That is the pipeline variant of Chain of Responsibility: an ordered list of handlers in which every handler may act on the packet and pass it on, and any handler can end the walk (NF_DROP, NF_STOLEN). Classic GoF CoR stops at the first handler that takes the request (ATM denominations, approval levels); the shared-IRQ case in the next sentence, where usually one handler usually claims the interrupt with IRQ_HANDLED, is the closer fit. Conntrack, NAT, iptables or nftables filtering and your own module all live on the same chain without knowing each other, ordered by priority constants. The same shape appears in shared interrupt lines (each handler returns IRQ_HANDLED or IRQ_NONE) and, in user space, servlet filters and HTTP middleware. Case studies: logger (level filtering), rate limiter (a filter in a request pipeline).
