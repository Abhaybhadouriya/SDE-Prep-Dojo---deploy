kref and refcounting: shared ownership with a destructor

A kref is a counter plus a rule: whoever drops the count to zero calls the release function, which usually uses container_of to find and free the enclosing object. That is std::shared_ptr with a custom deleter, written by hand, and it is why the kernel can free an object safely when many subsystems hold pointers to it.

  1. The driver allocates the adapter and calls kref_init(): one reference, owned by the driver.
  2. The driver queues deferred work that will touch the device later. Before queuing, it takes a reference with kref_get(), so the work owns a share of the object.
  3. The device is unregistered and the driver calls kref_put(). The count drops to 1, so nothing is freed. Without the work's reference, the work would later touch freed memory: a use-after-free.
  4. The worker thread runs the work and, as its last act, calls kref_put(). The count reaches 0.
  5. The put that reaches zero calls the release function, which recovers the adapter with container_of and frees it. Exactly one caller frees, no matter which order the puts happened in.

Neil Brown's first LWN design-patterns article names three refcount styles and one anti-pattern; summarised in our words:

  • kref style: the object dies with its last external reference. Turning an internal pointer (say, from a lookup table) into a new reference must use "increment unless zero" (kref_get_unless_zero()) so you never revive a dying object.
  • kcref style (a name the article proposes): the object can outlive its last external reference, for example in a cache. The final decrement is done with the lock held (atomic_dec_and_lock()), and lookups take new references under the same lock. The inode cache works this way.
  • Plain counter: just counts users of something whose lifetime is owned by a parent object; reaching zero triggers nothing special.
  • Anti-pattern, biased references: adding a large offset to the count to encode a state. A separate flag says the same thing clearly.

In Java the garbage collector handles memory, but the kref idea is still needed for external resources: connections, file handles, leases, shared buffers (Netty's ReferenceCounted uses retain() / release()). In C++ it is std::shared_ptr; in Python, CPython's own reference count plus with blocks for resources.
