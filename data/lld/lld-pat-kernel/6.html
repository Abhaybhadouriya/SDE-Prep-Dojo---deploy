Notifier chains: the Observer pattern

A struct notifier_block holds a callback, a priority and a next pointer. Subsystems register blocks on a chain owned by the subject; when something happens the subject walks the chain and calls each one with an event code and a data pointer.

static int my_netdev_event(struct notifier_block *nb, unsigned long event, void *ptr)
{
    struct net_device *dev = netdev_notifier_info_to_dev(ptr);
    if (event == NETDEV_UP)   pr_info("%s is up\n", dev->name);
    if (event == NETDEV_DOWN) pr_info("%s is down\n", dev->name);
    return NOTIFY_DONE;                       /* "not interested / carry on" */
}
static struct notifier_block my_nb = { .notifier_call = my_netdev_event };

register_netdevice_notifier(&my_nb);         /* subscribe   */
unregister_netdevice_notifier(&my_nb);       /* unsubscribe */
  • Subject: the chain head (here, the netdevice notifier chain). Observer: each notifier_block. Update method: notifier_call. Event: the unsigned long code plus void * data.
  • Ordering: blocks are kept sorted by priority, so higher priority hears first.
  • Stopping: a callback can return a value with NOTIFY_STOP_MASK set (NOTIFY_STOP, NOTIFY_BAD) to end the walk; this lets a chain also veto an action, which adds a Chain of Responsibility flavour.
  • Concurrency variants: atomic chains (callbacks may not sleep), blocking chains (callbacks may sleep), raw chains (caller does the locking) and SRCU chains. Choosing among them is choosing a thread-safety policy for the observer list, a question interviewers ask about Java's Observer too ("what if a listener unsubscribes during notification?").

Java equivalents: PropertyChangeListener, Spring's ApplicationListener. The kernel's netlink multicast groups, which user-space processes join, are closer to publish-subscribe, because the publisher does not hold the list of receivers. Case studies: pub-sub system, notification service.
