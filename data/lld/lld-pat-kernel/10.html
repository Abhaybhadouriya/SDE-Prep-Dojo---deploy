The kernel's own lessons: library over midlayer

The third article in Neil Brown's series is a design lesson, not a pattern catalogue, and it is gold for LLD interviews. Its claim: a midlayer that sits between a thin top layer and drivers, does common work and then calls down into drivers, tends to go wrong. Drivers have needs its authors did not foresee, so it gathers special cases and flags. The better design is a library: the top layer calls the driver directly, and the driver calls shared helper functions when it wants them, and can extend or skip them.

  • Good example from the article: the page cache. Most file systems plug the generic page-cache functions straight into their ops tables, wrap the few they need to change, and pseudo file systems such as procfs can ignore the page cache.
  • Partly midlayer: the dentry cache is mandatory for every file system. It brings real benefits (it prevents rename races) but forces caching on network and virtual file systems, and needs "NULL means default" hooks for them.
  • Historical case: early block-layer requests all went through the I/O scheduler; later, drivers could register their own request handling and the elevator became optional.

Data-structure patterns from part 2

  • Embedded anchor: the list or tree node lives inside your object (list_head, rb_node), so there is no separate node allocation.
  • Broad interfaces: many narrow, specific functions (around twenty list iteration macros) instead of one function with flags.
  • Tool box: rbtree deliberately gives you rebalancing helpers but no generic search or insert, so you write the compare and avoid a function-pointer call per step. A library, not a framework, again.
  • Preallocate outside locks: radix_tree_preload() fills a small per-CPU reserve before taking a spinlock so the insert cannot fail inside it: an object pool used for correctness.
