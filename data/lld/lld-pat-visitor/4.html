Double dispatch: why accept exists at all

Why not just write taxVisitor.visit(item) with three overloads visit(Book), visit(Electronics), visit(Grocery)? Because in Java, C++ and C#, overloads are chosen at compile time from the static type of the argument. If the variable is declared Item, the compiler can only pick visit(Item), whatever the object really is at runtime. Our Java demo prints exactly this:

static type Item, overload picked: describe(Item)
via accept (double dispatch): tax = 0.0

Virtual calls, by contrast, are chosen at runtime, but only on one object: the receiver. Visitor gets a choice on two runtime types by making two virtual calls in a row:

  1. Dispatch 1, on the element. item.accept(v) is virtual, so it runs Electronics.accept because the object is an Electronics.
  2. Dispatch 2, on the visitor. Inside Electronics.accept, this has the static type Electronics, so the call v.visitElectronics(this) is fixed at compile time to the right case, and is virtual on v, so it runs TaxVisitor's version.

From your world

In C, the same 2-D table is literal. You write struct node_visitor { void (*visit[N_TYPES])(struct node *, void *ctx); }; and the walker calls v->visit[n->type](n, ctx). The array index is dispatch 1 (the node's tag), the choice of v is dispatch 2 (which pass). A C++ vtable gives you only one of those indexes for free, so Visitor spends a second virtual call to get the other. Python and Lisp-style multimethods can dispatch on both arguments directly, which is why Visitor feels heavier there.
