Interview Q&A

What is double dispatch, and why does Visitor need it?

Double dispatch means choosing the code to run from the runtime types of two objects. Java, C++ and C# virtual calls dispatch on one (the receiver), and overloads are resolved at compile time from static types. Visitor makes two virtual calls: element.accept(v) resolves the element's type, and inside it v.visitX(this) resolves the visitor's type. Together they select one cell of the (element type x operation) table.

How to answer

Show the overload trap first (visit(item) with a variable typed Item always picks the Item overload), then the two hops.

Likely follow-ups
  • Does Python need accept? (No overloading, so it dispatches on a method name built from the class name, as ast.NodeVisitor does.)
  • What is multiple dispatch?
Your cart has books, electronics and groceries. Add tax and shipping without editing the item classes.

Give Item one method, <R> R accept(CartVisitor<R> v). Define CartVisitor with visitBook, visitElectronics, visitGrocery. Write TaxVisitor and ShippingVisitor; the cart sums item.accept(visitor). Loyalty points next sprint is one more visitor class.

How to answer

Draw the two hierarchies, write one accept and one visitor, then name the trade-off before they ask.

Likely follow-ups
  • Now add a GiftCard item type. What changes? (Every visitor gains a method.)
  • Tax rates differ by state. Where does that go? (Constructor parameter of TaxVisitor, or a Strategy inside it.)
When is Visitor a bad idea?

When element types change often, because each new type means editing every visitor. When there are only one or two operations, because a polymorphic method is simpler. When visitors need private state, because elements must expose it. And in languages with sealed types and exhaustive pattern matching, where a switch gives the same grouping with less code.

How to answer

Frame it as the expression problem: Visitor makes operations cheap and types expensive.

Likely follow-ups
  • How can a default base visitor soften this, and what do you lose? (You lose the compile-time error for a missing case.)
Visitor vs a Java 21 sealed interface with a pattern-matching switch: which would you choose?

On Java 21 with a hierarchy I own, a sealed interface plus exhaustive switch is usually simpler: no accept methods, and the compiler still errors on a missing case. I would keep Visitor when the hierarchy is in a library I cannot seal, when I need older Java, when the operation is stateful and walks a deep tree (a visitor object is a natural home for that state), or when the codebase already standardises on visitors (ANTLR, javac tree API).

How to answer

Show you know both and give a rule for choosing, rather than calling one obsolete.

Likely follow-ups
  • What does sealed ... permits guarantee?
Visitor vs Iterator: both walk a structure. What is the difference?

Iterator gives you the elements one by one and does not care about their types; your loop body decides what to do. Visitor brings a different method per element type and lets the elements call the right one. They complement each other: the structure or an iterator controls the order, the visitor controls the work.

How to answer

"Iterator answers which one next, Visitor answers what to do with this kind."

Likely follow-ups
  • Who should own traversal order in a Visitor design?
Where have you seen Visitor in the JDK or Python standard library?

java.nio.file.FileVisitor with Files.walkFileTree (and SimpleFileVisitor as the default base); javax.lang.model.element.ElementVisitor for annotation processing; the javac TreeVisitor. In Python, ast.NodeVisitor and ast.NodeTransformer. Outside the standard libraries, ANTLR-generated visitors and Clang's RecursiveASTVisitor.

How to answer

Name one and say what the visit methods are and what FileVisitResult lets the visitor control.

Likely follow-ups
  • How would you skip node_modules during a walk? (SKIP_SUBTREE from preVisitDirectory.)
Does Visitor break encapsulation? How do you limit that?

Somewhat. A visitor computes things from element data, so elements must expose what visitors need (getters, or Java records' accessors). Limit it by exposing read-only, intention-revealing accessors rather than raw fields, keeping visitors in the same package, and keeping invariant-protecting logic (validation, state changes) inside the element. If a visitor needs to mutate elements heavily, the operation probably belongs on the element.

How to answer

Admit the cost, then give two concrete mitigations.

Likely follow-ups
  • Can visitors be used to transform a tree immutably? (Yes: return new nodes, like NodeTransformer.)
