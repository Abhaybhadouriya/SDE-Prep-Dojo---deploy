When to use it, when it hurts

Use it when
  • The set of element classes is stable (AST node kinds, a fixed product taxonomy, file/dir/symlink) and new operations keep coming.
  • An operation has many type-specific cases and you want them together in one reviewable file, owned by one team (tax rules, export format).
  • You cannot or do not want to edit the element classes (a library's tree, generated parser classes).
  • The operation needs to accumulate state across a walk (running totals, symbol tables, indentation depth).
It hurts when
  • Element types change often: every new type breaks every visitor. With 8 visitors, one new node type is 8 edits.
  • Visitors need private data, so elements expose getters they would rather hide (weaker encapsulation).
  • There are only one or two operations. A plain polymorphic method is simpler and reads better.
  • The language has better tools: Java 21 sealed interfaces with exhaustive switch patterns, Kotlin when on sealed classes, Rust match on enums, C++17 std::variant + std::visit.
  • Newcomers find the two-hop call flow hard to follow in a debugger.

The modern alternative: sealed types and pattern matching

Java 21 (JEP 441) made switch over a sealed interface exhaustive: if you forget a permitted subtype, the code does not compile. That gives you Visitor's biggest benefit (operations in one place, compiler-checked completeness) with none of the accept plumbing, as the area(Shape) method in the Java tab shows. In a fresh Java 21 codebase or an interview where you say "Java 21", it is fair to say: "I would model these as a sealed hierarchy and switch over them; on older Java, or when the hierarchy lives in a library I cannot seal, I would use a Visitor." Python 3.10's match statement offers the same shape, without the exhaustiveness check.

Design tips

  • Return a value with a generic Visitor<R> instead of forcing every visitor to stash results in a field.
  • Decide who traverses. Structure-driven (the cart loops) keeps visitors simple; visitor-driven (the visitor recurses) lets an operation prune or reorder. Do not mix both in one design.
  • Provide a default base class (like SimpleFileVisitor or ast.NodeVisitor) so a visitor overrides only the cases it cares about. It also softens the "new type breaks every visitor" cost, at the price of losing the compile error.
  • Keep elements dumb. If accept grows logic, the operation is leaking back into the element.
