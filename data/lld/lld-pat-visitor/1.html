The problem: every new operation edits every class

A shopping cart holds books, electronics and groceries. Product asks for tax. Next sprint, shipping. Then a printable receipt, then loyalty points, then an export for the warehouse. The first instinct is a method per feature on every item class:

interface Item {
    double price();
    double tax();        // sprint 1
    double shipping();   // sprint 2: edit Book, Electronics, Grocery
    String receipt();    // sprint 3: edit all three again
    int loyaltyPoints(); // sprint 4: and again
}

class Electronics implements Item {
    public double tax()      { return price * 0.18; }               // tax rules
    public double shipping() { return 50 + 10 * weightKg; }         // logistics rules
    public String receipt()  { return "[Elec] " + name + " " + price; } // formatting rules
    // ... the "Electronics" class now knows about tax law, courier rates and printing
}

Three things hurt:

  • Every new feature touches every class. With 3 item types and 5 features you have 15 methods spread across 3 files, and each feature's logic is split across all of them.
  • The classes lose their single responsibility. Electronics should describe a product. Now it carries tax law, courier tables and receipt layout.
  • Related logic is scattered. To review "how do we compute tax?" you open three files. A tax change for books is in Book.java, next to shipping code that the tax team does not own.

The second instinct, an instanceof chain in a TaxCalculator, gathers the tax logic in one place but is fragile: add a GiftCard class and nothing fails to compile; the chain silently falls through to a default.

double tax(Item i) {
    if (i instanceof Book) return 0;
    else if (i instanceof Electronics e) return e.price() * 0.18;
    else if (i instanceof Grocery g) return g.perishable() ? 0 : g.price() * 0.05;
    return 0;   // GiftCard added last week lands here, untaxed, with no warning
}
