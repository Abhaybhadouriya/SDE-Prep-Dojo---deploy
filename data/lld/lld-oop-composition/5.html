When inheritance is the right tool

"Composition over inheritance" is a default, not a ban. A good answer shows you know both sides.

Inheritance fits when
  • The relationship is a true, permanent is-a, and the subclass can stand in everywhere (Liskov holds).
  • The base class was designed for extension: documented hooks, a template method, protected steps (frameworks, AbstractList).
  • You are modelling a closed family of types, like exception hierarchies or a sealed set of result types.
  • Both classes are in the same module, owned by the same team, and change together.
Prefer composition when
  • You only want to reuse code, not to be substitutable.
  • Behaviour varies on several independent axes (class explosion).
  • Behaviour must change at run time, or per object.
  • The base class belongs to someone else (a library) or was not designed for extension.
  • You would inherit methods that break your class's rules (Stack extends Vector).

What composition costs

  • More objects and wiring: someone has to create the parts and pass them in (main, a factory, or a DI container).
  • Indirection: reading the code means following calls into parts. Good names and small interfaces keep this cheap.
  • Forwarding boilerplate: wrappers must repeat each method they expose.
  • No automatic substitutability: a wrapper is not a subtype of what it wraps unless both implement a shared interface. That is why step 4 of the refactor extracts one.

Mixins: a middle path

A mixin is a small unit of behaviour meant to be added to many classes, not to stand alone. Python does this with multiple inheritance (class Handler(LoggingMixin, RetryMixin, Base)). Java's default methods give a limited, stateless form (our Auditable interface in Abstract Classes vs Interfaces). LWN's kernel-patterns article also describes "mixin" style ops tables. Mixins share the inheritance downside of hidden coupling, so keep them tiny and stateless.

From your world

Kernel "inheritance" is usually embedding a parent struct as the first member and using container_of to get back to the child, while behaviour lives in a separately pointed-to ops table. Data is embedded; behaviour is composed. That is a sound split for user-space designs too: inherit (or embed) only the stable shape, compose the parts that vary.
