The fragile base class problem

Inheritance couples a subclass to the implementation of its parent, not just its interface. If the parent calls its own overridable methods internally ("self-use"), a subclass that overrides those methods gets pulled into calls it never expected. Change the parent's internals and subclasses can break without a single line of their code changing. This is the fragile base class problem.

Here is a small, real demonstration. Inventory.addAll happens to call add in a loop. A subclass wants to count everything added:

// ---- Part 1: fragile base class ----
// A base class whose addAll() happens to call add() ("self-use").
static class Inventory {
    private final List<String> items = new ArrayList<>();
    public void add(String item) { items.add(item); }
    public void addAll(List<String> batch) { for (String i : batch) add(i); } // calls add()!
    public int size() { return items.size(); }
}

// Subclass that counts every item ever added, by overriding BOTH methods.
static class CountingInventory extends Inventory {
    private int added = 0;
    @Override public void add(String item) { added++; super.add(item); }
    @Override public void addAll(List<String> batch) { added += batch.size(); super.addAll(batch); }
    public int added() { return added; }
}
$ javac -d out Composition.java && java -cp out Composition
1. Fragile base class: 3 items added with addAll
  inheritance: size=3 added=6   <- wrong, counted twice

Click through why three items count as six:

  1. main calls the subclass's addAll with 3 items. It adds 3 to the counter.
  2. It then calls super.addAll so the base class actually stores the items.
  3. The base's addAll calls add(i) for each item. add is overridden, so dynamic dispatch sends each call back down to the subclass.
  4. The subclass's add counts again: 3 more. The counter says 6 for 3 items. Nothing in the subclass is "wrong"; it relied on a detail it could not see.
  5. And if the base author later rewrites addAll to append directly without calling add, a subclass that only overrode add would suddenly count zero. Either way the subclass is at the base's mercy.

The composition version wraps any Store and forwards calls. The wrapped object's internal self-calls stay inside it; the wrapper only sees the calls it receives:

// The fix: HOLD an Inventory instead of BEING one. Forward calls; count in one place.
interface Store { void add(String item); void addAll(List<String> batch); int size(); }

static final class BasicStore implements Store {             // same logic as Inventory
    private final Inventory inv = new Inventory();
    public void add(String item) { inv.add(item); }
    public void addAll(List<String> batch) { inv.addAll(batch); }
    public int size() { return inv.size(); }
}

static final class CountingStore implements Store {          // wrapper, works with ANY Store
    private final Store inner;
    private int added = 0;
    CountingStore(Store inner) { this.inner = inner; }
    public void add(String item) { added++; inner.add(item); }
    public void addAll(List<String> batch) { added += batch.size(); inner.addAll(batch); }
    public int size() { return inner.size(); }
    int added() { return added; }
}
  composition: size=3 added=3   <- correct

Note: this exact trap is a well-known item in Joshua Bloch's Effective Java ("favor composition over inheritance" and "design and document for inheritance or else prohibit it"). The practical rule: if a class is not designed to be extended, make it final. Our CountingStore wrapper is also the shape of the Decorator pattern.
