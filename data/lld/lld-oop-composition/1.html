is-a vs has-a

  • Inheritance (is-a): class Car extends Vehicle. Car gets all of Vehicle's fields and methods and can be used wherever a Vehicle is expected. The link is fixed at compile time.
  • Composition (has-a): class Car { private final Engine engine; }. Car owns an Engine and calls it. The Engine can be any implementation of an Engine interface, passed in or swapped later. In UML, a filled diamond on the owner's end means the part lives and dies with the owner (strong has-a).
  • Delegation: the act of handing a call to the part: car.start() calls engine.start(). Composition gives you the part; delegation is how you use it.

A quick test before you write extends: say "every B is a A, everywhere an A is used, forever". "Every Car is a Vehicle" passes. "Every Stack is a Vector" fails (a stack must not allow inserting in the middle), yet Java 1.0 shipped java.util.Stack extends Vector, and to this day you can call stack.add(0, x) on it. The JDK docs now recommend Deque instead. That is the textbook warning sign: the subclass inherits methods that break its own rules (a Liskov violation).
