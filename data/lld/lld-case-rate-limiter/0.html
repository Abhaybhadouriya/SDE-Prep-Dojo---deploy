The story: the ticket counter at the fair

Explain like I'm 5

A fair has one popular ride. If everyone rushes it at once, the ride breaks. So the man at the gate has a jar of 5 tickets. Each child who wants to ride takes one ticket. When the jar is empty, the next child must wait. Every few seconds the man drops one new ticket into the jar, but the jar never holds more than 5.

If nobody came for a while, the jar is full, so 5 friends arriving together can all ride at once. If a big crowd comes, they ride at the speed the man adds tickets, never faster. Nobody gets hurt, and the ride keeps working.

That jar is a token bucket, the most common rate limiter. The man is the limiter. Each child is a request. "Wait" is the answer HTTP 429 Too Many Requests.

From your world

You have shipped rate limiters already. tc qdisc add ... tbf rate 1mbit burst 32kbit is a token bucket filter on a NIC queue. The iptables limit match (--limit 10/second --limit-burst 20) is a token bucket per rule, and hashlimit is the same thing with one bucket per source IP: exactly the per-client limiter of this page. And every driver author has used printk_ratelimited(), backed by struct ratelimit_state { interval, burst, ... } in lib/ratelimit.c: "at most burst messages per interval", which is a fixed window. An interview rate limiter is those ideas moved into user space, wrapped in classes, and made safe for many threads.

In an LLD round, the rate limiter is popular because it is small enough to finish in 60-90 minutes, yet it tests four things at once: can you separate the algorithm from the bookkeeping (Strategy), can you create objects by configuration (Factory), can you keep shared state correct under many threads, and can you extend it when the interviewer adds "now limit two APIs together".
