Concurrency and thread safety

There are two pieces of shared state, and each gets its own, smallest possible protection.

  1. Two requests for the same client arrive together. Both read tokens = 1, both decide "allow", both write 0. Two requests passed on one token: a lost update.
  2. The guard: acquire() is synchronized on that client's limiter, so refill, check and subtract are one step. Different clients have different limiter objects and never wait for each other (per-key locking).
  3. B gets the lock only after A has released it. It sees 0 tokens and returns NO_PERMIT, so the service answers 429. Exactly one request was admitted.
  1. The map of limiters. Two threads may see a brand-new key at the same moment. With a plain get then put, both create a bucket, one overwrites the other, and that client gets twice the limit for a moment. ConcurrentHashMap.computeIfAbsent runs the factory at most once per key, atomically. Python uses a double-checked lock around creation only; C++ locks the map around find-or-emplace.
  2. The state inside each limiter. "Read tokens, refill, compare, subtract" is a read-modify-write. Two threads could both read tokens = 1 and both pass. Each tryAcquire is synchronized on its own limiter object, so threads for different clients never wait for each other. This is per-key locking, the same idea as one spinlock per hash bucket rather than one global lock.
  3. The composite takes no lock of its own, and never holds two limiter locks at once: it calls child A (lock, unlock), then child B (lock, unlock). No nested locks means no lock-order deadlock, by construction. See Deadlock for why that matters.

The cost of not nesting locks. Between "A said yes" and "B said no, roll A back", another thread may see A's permit as used and be rejected, so the system can briefly under-admit. For a rate limiter that is the safe direction. It is only safe if the rollback is exact, though. A naive rollback(now) that just does count-- is wrong when a new window starts between the acquire and the rollback: it frees a slot in a window the request never used, which over-admits. A naive sliding-log rollback that pops the newest timestamp can remove another thread's entry and leave ours, which expires earlier and frees capacity too soon. So acquire returns a permit token (the window start for the window algorithms, the exact timestamp for the log), and rollback(permit) undoes only if that window is still the current one (the sliding counter also refunds the previous window, which still weighs in) and removes exactly that timestamp from the log. Demo line 6b tests exactly this interleaving. If the interviewer wants strict all-or-nothing instead, lock all children in a fixed global order (for example by key string), check all, then consume all.

Lock-free alternative

A fixed window can be an AtomicLong counter plus a window id, updated with a compare-and-set loop. A token bucket can pack (tokens, lastRefill) into one immutable object held in an AtomicReference and swap it with CAS (this is roughly what libraries such as Bucket4j do). Lock-free wins under very heavy contention on one hot key; synchronized on a per-key object is simpler, obviously correct, and fast enough for an interview. Say both, code the simple one.

From your world

computeIfAbsent is the user-space version of the kernel idiom "look up under RCU; on a miss take the bucket lock, look up again, then insert". The per-limiter synchronized is a spin_lock(&rs->lock) around the counter, which is what ___ratelimit() itself does: it guards struct ratelimit_state with a spinlock taken by trylock, and long-standing versions simply suppress the message when that lock is busy, choosing under-admission too.

The Java demo proves both rules with a test: 8 threads released together by a CountDownLatch fire 4,000 requests at one new key with capacity 100 and a frozen clock. Exactly 100 pass, and exactly one limiter object exists. A second test hammers a group limit of 50 from 8 threads and gets exactly 50.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • CountDownLatch / Barrier = struct completion: threads wait until a count reaches zero (the tests use it to release all threads at once).
