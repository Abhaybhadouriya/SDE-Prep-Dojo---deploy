APIs and interfaces

Agree on these signatures before writing bodies. They are small on purpose.

interface Limiter {                      // Strategy: one key's state + one algorithm
    long NO_PERMIT = Long.MIN_VALUE;
    long acquire(long nowMs);            // take one permit if allowed; returns WHERE it was counted
                                         // (window start or timestamp), or NO_PERMIT
    void rollback(long permit);          // give that permit back, only if its window is still current
    default boolean tryAcquire(long nowMs) { return acquire(nowMs) != NO_PERMIT; }
}

interface Clock { long nowMs(); }        // SystemClock (monotonic) or ManualClock (tests)

record LimitRule(Algorithm algorithm, long limit, long windowMs) { }   // "limit per windowMs"

final class RateLimiterService {
    RateLimiterService(Clock clock, LimitRule defaultRule);
    void setApiRule(String api, LimitRule rule);                        // per-API limit
    void setGroupRule(String group, Set<String> apis, LimitRule rule);  // combined limit
    boolean allow(String clientId, String api);                         // the hot path
}
  • Time is a parameter (nowMs), not read inside the algorithm. This keeps algorithms pure and testable, and lets a composite pass one consistent instant to all children.
  • One rule shape for all algorithms. "limit per window" is enough: buckets use limit as capacity and limit / window as the refill rate. A real product might give buckets an explicit burst size; say so as an extension.
  • Monotonic time. SystemClock uses System.nanoTime(), not currentTimeMillis(), so an NTP step backwards cannot refill a bucket or reopen a window.
