Clarify the requirements

Spend the first 5-8 minutes here. Say the requirements out loud and write them at the top of your file as a comment. The interviewer is checking that you scope the problem instead of jumping to code.

Functional (in scope)
  • allow(clientId, api) returns yes or no, immediately (no waiting).
  • Limits are per client (user id, API key or IP) and per API, with a default rule for APIs that have none.
  • The algorithm is configurable per rule: token bucket, leaky bucket, fixed window, sliding log, sliding counter.
  • A group rule can cap several APIs together (for example /pay + /refund: 3 per minute in total).
  • Rules are set by configuration at start-up.
Out of scope (say so)
  • Distributed limiting across many servers (Redis, gossip): mention it, do not build it. That is the HLD question, see Distributed Rate Limiter.
  • Queuing or delaying requests (a "shaping" limiter). We only accept or reject.
  • Persisting counters across restarts.
  • HTTP plumbing. We return a boolean; the caller maps no to 429.

Non-functional

  • Fast: allow() sits on every request path, so O(1) time per call (the sliding log is O(limit) memory, which we will call out).
  • Thread-safe: many request threads call it at once. The limit must never be exceeded because of a race.
  • Memory-bounded: state per (client, rule) key must be small; idle keys should be removable.
  • Testable: time must be injectable, so tests do not sleep.
  • Extensible: a new algorithm or a new kind of rule must not change existing classes (Open/Closed).

Questions to ask the interviewer

  1. Who is the client? User id, API key, or IP? (Decides the key. We take any string.)
  2. Hard or soft limit? Must we never exceed it, or is "about right" fine? (Decides sliding log vs counter.)
  3. Are bursts OK? Should an idle client be able to send 10 requests at once? (Yes: token bucket. No: leaky bucket or sliding log.)
  4. One limit or several? Per API, per client, global, combined? (Decides whether we need a Composite.)
  5. Single process or a fleet? (Decides in-memory vs a shared store. In LLD: single process.)
  6. What does the caller need back? Just yes/no, or also "retry after N ms" and "remaining"? (Start with boolean; mention a Decision object.)
