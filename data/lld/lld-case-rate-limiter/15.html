Interview follow-ups (with answers)

Compare token bucket, fixed window and sliding window. Which would you pick for a public API?

Fixed window is one counter per aligned window: cheapest, but a client can get 2x the limit across an edge. Sliding log is exact but stores one timestamp per accepted request. Sliding counter is O(1) and close to exact. Token bucket stores a level and a timestamp, allows bursts up to capacity, and caps the long-run rate. For a public API I would pick a token bucket: users get a small burst allowance, the average is enforced, and state is tiny.

How to answer

Draw the 0-1000-2000 timeline with six dots around the edge. Then one row per algorithm: state, accuracy, burst. Finish with a choice and a reason.

Likely follow-ups
  • When would you choose the sliding log anyway? (Small strict limits like 5 login attempts per 15 minutes.)
  • Token vs leaky bucket? (Same state; token allows bursts out, leaky smooths them.)
Different APIs need different limits and time periods. How does your design handle it?

Each API maps to a LimitRule(algorithm, limit, window); APIs without one use a default. The limiter key is client|api:<name>, so each (client, API) pair has its own state with its own window. Adding a rule is configuration, not code.

How to answer

Show the rule map and the key format. Point out that rules are immutable values, so reading them needs no lock.

Likely follow-ups
  • What if an API needs two limits, 10/s and 1000/day? (A list of rules per API, composed like a group.)
Now put one limit on two APIs combined. What breaks if you just check both limiters?

If you call the API limiter, it consumes a permit; then the group limiter rejects. The request was rejected but still used the API quota. So the composite must roll back earlier permits when a later child says no. We call children in order without nesting locks; the worst case is brief under-admission. The rollback must name the permit it is undoing (its window start or timestamp): a plain count-- after the window rolled over would refund a slot in the new window and over-admit.

How to answer

Name the bug first ("a rejected request ate quota"), then the fix (rollback), then the concurrency consequence and the strict alternative (lock all in a fixed order).

Likely follow-ups
  • Could you check all first, then consume? (Only atomically: hold all locks in a global order, else another thread slips in between.)
Is your limiter thread-safe? Prove it.

Two shared things: the key map (atomic create via computeIfAbsent) and each limiter's state (synchronized read-modify-write per object). The proof is a test: 8 threads released together, 4,000 calls to one new key with capacity 100 and a frozen clock; exactly 100 pass and one limiter exists. Remove synchronized and the count goes above 100 on a multi-core machine.

How to answer

Name the race ("two threads read tokens = 1"), the fix, and the test. A test with a start latch beats any amount of arguing.

Likely follow-ups
  • Why not one global lock? (All clients would serialise on it; per-key locks scale with clients.)
  • Could you make it lock-free? (CAS on an AtomicReference of an immutable state.)
How much memory does your limiter use with 10 million clients? How do you bound it?

Counter and bucket algorithms keep a few longs per key, plus the map entry and key string, so memory is roughly linear in active keys: tens of bytes of state plus per-object overhead. The sliding log is worse: up to limit timestamps per key. Bound it by evicting keys idle for longer than their window (their state is equivalent to a fresh limiter anyway), or by a size-capped LRU map, and by preferring the sliding counter for large limits.

How to answer

Separate per-key state from the number of keys. Then make the key: "an idle limiter carries no information, so evicting it is free".

Likely follow-ups
  • Who runs eviction? (A scheduled sweeper, or lazy eviction on access with a timestamp.)
Why do you pass the time into tryAcquire instead of calling System.currentTimeMillis() inside?

Three reasons. Tests can use exact times without sleeping. A composite passes the same instant to every child, so they agree. And the system clock can be swapped for a monotonic one: wall-clock time can jump backwards with NTP, which would corrupt refill logic.

How to answer

Lead with testability; it is the one the interviewer is fishing for.

Likely follow-ups
  • Which Java API is monotonic? (System.nanoTime().)
Implement the sliding window counter. Where is its error?

Keep the current aligned window's start and count plus the previous window's count. Estimate = previous x (1 - elapsed fraction of the current window) + current. Allow if estimate + 1 <= limit. The error comes from assuming the previous window's requests were spread evenly; if they all arrived at its very end, the estimate is too low and slightly more than the limit can pass.

How to answer

Write the formula, run one number (prev 3, half-way, current 0 gives 1.5), then state the assumption.

Likely follow-ups
  • What if more than one window passed? (Previous count is 0.)
How would this work across 20 application servers?

In-memory state per server gives each server its own limit, so the global limit becomes 20x. Options: a shared store such as Redis with atomic operations (INCR + EXPIRE for fixed window, a Lua script for token bucket); or split the limit across nodes (limit / N each) with sticky routing by client; or local limiters that sync counts periodically, accepting some error. Our Limiter interface stays the same; a Redis-backed class implements it.

How to answer

Say the failure (20x), then two or three options with their trade-off (latency, accuracy, availability), then hand off to the HLD design.

Likely follow-ups
  • Redis is down: fail open or closed? (Usually fail open for user APIs, closed for abuse-sensitive ones like OTP.)
Where does the limiter sit in a web service, and what does the client see?

In front of the handler as middleware, a servlet filter or an API gateway policy: a protection proxy. On reject, return HTTP 429 Too Many Requests, ideally with Retry-After and remaining-quota headers, and do no expensive work (no DB call) before the check.

How to answer

Name the layer, the status code, and the headers. Mention that the client key comes from authentication (API key or user id), or IP for anonymous traffic.

Likely follow-ups
  • Why is IP a weak key? (NAT: many users behind one IP; attackers rotate IPs.)
Your token bucket uses a double. Is that a problem?

For a yes/no decision it is fine: the error is far below one token. For exact accounting (billing, quotas), use integer fixed-point such as milli-tokens, or GCRA, which stores one integer "theoretical arrival time" and needs no fractional tokens.

How to answer

Agree it is a trade-off, give the integer alternative, and name GCRA if you know it.

Likely follow-ups
  • Explain GCRA in one line. (Each request pushes a "next allowed time" forward by 1/rate; reject if it is too far ahead of now.)
