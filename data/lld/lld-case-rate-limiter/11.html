Extensibility: the follow-ups interviewers ask

Follow-upChange in our designClasses touched
"Different APIs have different limits and periods" (Microsoft)Already there: setApiRule(api, rule); each rule has its own window and algorithm.none
"One limit on two APIs combined" (Microsoft)Already there: setGroupRule + CompositeLimiter.none
"Add a global limit for the whole service"A group rule that contains every API, keyed without the client id ("*|group:global").service: key building
"Add a new algorithm, for example GCRA"One new class implementing Limiter, one enum value, one factory case.new class + factory
"Different tiers: free users 10/min, premium 100/min"A RuleResolver strategy: (clientId, api) -> List<LimitRule>, looking up the client's plan. Put the tier in the key so changing plan gets a fresh limiter.new interface; service delegates to it
"Return Retry-After and remaining count"Change the return type to a Decision(allowed, remaining, retryAfterMs). Token bucket: retry after (1 - tokens) / rate.interface + algorithms
"Memory keeps growing with clients" (Microsoft)Store lastSeen per limiter and evict idle keys on a timer, or use a size-bounded LRU map (the LRU Cache case study). Prefer counter algorithms over the log for large limits.service
"Change a rule at runtime"Keep rules in a volatile immutable map swapped on update; include a rule version in the key so old limiters age out.service
"Run on 20 servers"Move state to Redis: fixed window via INCR + EXPIRE, token bucket via a Lua script for atomicity; or split the limit per node. That is the HLD round: Distributed Rate Limiter.new Limiter implementation backed by a store

Answer follow-ups by pointing at the diagram. "That is a new Limiter class; nothing else changes" is the sentence that scores. If a follow-up forces you to edit three existing classes, stop and say what abstraction is missing.
