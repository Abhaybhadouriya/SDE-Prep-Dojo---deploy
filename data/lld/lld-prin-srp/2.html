Before: the god Invoice class

Here is a classic machine-coding shape. An Invoice class holds line items and also prints itself, saves itself and emails the customer. It works. The demo runs. It is still a design problem, and Flipkart and Razorpay interviewers say so in their feedback (more on that below).

import java.util.ArrayList;
import java.util.List;

// BEFORE: one class, three actors (finance, ops/DBA, customer support).
public class InvoiceBefore {
    record Line(String item, int qty, long unitPaise) {}

    private final String id;
    private final String customerEmail;
    private final List<Line> lines = new ArrayList<>();

    InvoiceBefore(String id, String customerEmail) { this.id = id; this.customerEmail = customerEmail; }

    void add(String item, int qty, long unitPaise) { lines.add(new Line(item, qty, unitPaise)); }

    // Finance owns this rule (GST rate, rounding).
    long totalPaise() {
        long sub = 0;
        for (Line l : lines) sub += l.qty() * l.unitPaise();
        return sub + Math.round(sub * 0.18);
    }

    // Support / design team owns this format.
    String render() {
        StringBuilder sb = new StringBuilder("INVOICE " + id + "\n");
        for (Line l : lines) sb.append(String.format("  %-8s x%d  %8.2f%n", l.item(), l.qty(), l.unitPaise() / 100.0));
        return sb.append(String.format("  TOTAL      %8.2f%n", totalPaise() / 100.0)).toString();
    }

    // Ops / DBA own the storage (here: a fake SQL string).
    String saveSql() {
        return "INSERT INTO invoices(id,total_paise) VALUES('" + id + "'," + totalPaise() + ")";
    }

    // Customer-comms team owns this (SMTP today, WhatsApp tomorrow).
    String email() { return "to=" + customerEmail + " subject=Invoice " + id; }

    public static void main(String[] args) {
        InvoiceBefore inv = new InvoiceBefore("INV-7", "asha@example.com");
        inv.add("dosa", 2, 6000);
        inv.add("coffee", 1, 3000);
        System.out.print(inv.render());
        System.out.println(inv.saveSql());
        System.out.println(inv.email());
    }
}

Ask the actor question, method by method:

  1. totalPaise() changes when finance changes the GST rate or the rounding rule.
  2. render() changes when support wants a logo, a new column or a different language.
  3. saveSql() changes when the DBA renames a table or moves to a different database.
  4. email() changes when the comms team switches from email to SMS or WhatsApp.

Four actors, so four reasons to change. Three concrete pains follow:

  • Accidental breakage. render() calls totalPaise(). A support engineer who "just changes the layout" can break the money math, and the money math has nothing to do with them.
  • Merge conflicts. Two teams edit the same file in the same sprint.
  • Hard tests. To unit-test the 18% GST rule you build an object that also knows SQL and email. In real code that means mocking a database and an SMTP client just to check one multiplication.
