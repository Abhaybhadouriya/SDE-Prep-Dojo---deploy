Spotting SRP violations in your own code

During a 90-minute machine-coding round you will not draw actor maps. Use these quick smells instead. Each one is a hint; two or more together are a strong signal.

SmellWhat you seeUsual fix
Vague nameOrderManager, ParkingUtils, Helper, or a name with "And" in itName the actor's job: FeeCalculator, TicketPrinter
Mixed importsOne file imports JDBC, an HTTP client and a PDF libraryPush each kind of I/O behind its own interface
Field clustersMethods A and B use fields x, y; methods C and D use fields p, q; nobody uses bothExtract Class along the cluster line
Divergent changeThe same class is edited for unrelated tickets ("new tax", "new layout")Split by the actor behind each ticket
Test painA unit test of pure logic needs a DB, clock, network or file mockSeparate the pure rule from the I/O
"And" description"This class finds a slot and computes fees and prints tickets"One class per clause
Main does the workAll logic lives in main() or a controllerController parses input and delegates; services hold rules

The "describe it in one sentence without and" test is the fastest. Try it on a parking lot design. "ParkingLot finds a free spot, calculates the fee, takes the payment and prints a ticket" has three "and"s. A cleaner set: ParkingLot (owns floors and spots), SpotAllocator (picks a spot), FeeCalculator (prices a stay), PaymentProcessor, TicketPrinter. Each one-sentence description now stands alone.

Refactoring.guru calls the "one class edited for many reasons" smell Divergent Change, and the opposite smell, where one change forces edits in many classes, Shotgun Surgery. SRP problems show up as the first; over-splitting shows up as the second.
