Interview questions

What is the Single Responsibility Principle? Give an example.

A class should have one reason to change, meaning it should answer to one actor: one team or role that can request changes. Example: an Invoice that computes tax, renders a PDF and writes to the database serves finance, support and the DBA. Split it into Invoice (data and money rule), InvoiceFormatter and InvoiceRepository. Now a GST change touches one class and can be tested without a database.

How to answer

Give the actor definition, not "does one thing". Then a 20-second before/after and the concrete benefit (isolated change, easy test).

Likely follow-ups
  • How do you decide where to draw the line?
  • Is SRP about classes only, or also modules and services?
Your machine-coding solution works, but feedback says "not modular". What would you change?

Look for classes whose description needs "and", models that print or do I/O, and logic inside main or a controller. Split rules (fee, fine, discount) into their own classes, push storage behind a repository interface with an in-memory implementation, put all printing in one presenter, and keep main to wiring. Say that each split matches a different reason to change.

How to answer

Name the smells, then the layout (model / service / repository / presenter / main). Keep it practical: this is about the 90-minute round.

Likely follow-ups
  • Would you write tests in the round? Which ones first?
  • How do you avoid over-engineering under time pressure?
Does SRP mean every class should have only one method?

No. That reading confuses the class rule with the function rule "a function should do one thing". A class can have many methods if they all serve the same actor and change together. Over-splitting causes shotgun surgery: one change from one actor edits many files, which is as bad as a god class.

How to answer

Correct the misconception, name shotgun surgery, and give the balance rule: split by actors, not by verbs.

Likely follow-ups
  • What is an anemic domain model?
  • Can a class be too small?
How do you detect SRP violations in an existing codebase?

Use change history and structure. Change history: files edited for unrelated tickets (divergent change) or that cause merge conflicts between teams. Structure: vague names (Manager, Util), mixed imports (DB, HTTP and formatting in one file), clusters of methods that use disjoint sets of fields, and unit tests that need I/O mocks to check pure logic.

How to answer

Give two kinds of evidence: version-control history and code structure. Add one tool-free test (describe it without "and").

Likely follow-ups
  • How would you split it safely without breaking production?
  • How do you choose which god class to split first?
Does SRP apply above the class level?

Yes. The same idea drives package, module and even microservice boundaries: keep together things that change for the same reason and separate things that change for different reasons. Martin calls the package-level form the Common Closure Principle. In the kernel, subsystem layering (driver, protocol, socket layer) is the same idea.

How to answer

Show you can scale the principle up: class, package, service. Link it to team ownership if the interviewer is senior.

Likely follow-ups
  • How does this relate to microservice decomposition?
  • What is the Common Closure Principle?
Your InvoiceService calls a repository, a notifier and a formatter. Is that a violation, since it touches three things?

No. Its one responsibility is the order of steps for the "issue invoice" use case. It does not know how storage, messaging or formatting work; it only coordinates. A thin coordinator like this is a Facade or application service. It would become a violation if it also computed tax or built SQL strings.

How to answer

Separate "coordinates" from "implements". Name the Facade / application-service role.

Likely follow-ups
  • What would make this service grow into a god class?
  • How would you test it?
