Why machine-coding rounds care

Indian product companies grade machine-coding rounds on a rubric: does it run, is it modular, is it extensible, does it handle edge cases. "Modular" in that rubric mostly means SRP. In the LeetCode Discuss reports we collected for this module, modularity and separation of concerns come up again and again in rejection feedback. One Flipkart SDE-2 report quotes HR feedback that single responsibility and separation of concerns were not followed (post); a Razorpay report lists "code was not modular" and "not extensible" as the cons even though the solution was optimal (post).

A practical layout that keeps you SRP-clean under time pressure:

src/
  model/        Invoice, Line, Ticket, Spot        <- data + rules that guard the data
  service/      InvoiceService, FeeCalculator      <- one use case or one rule each
  repository/   InvoiceRepository (interface)      <- storage; an in-memory map in the round
                InMemoryInvoiceRepository
  notify/       Notifier (interface), ConsoleNotifier
  Main.java     <- builds objects, runs the demo, nothing else

Two cheap habits help most. First, put every System.out.println in one presenter or notifier class, never inside a model. Second, keep Main as wiring only, so the interviewer can see each piece in isolation.

Scenario: "it works, why the low score?"

You built a library management system in 90 minutes. One Library class holds books, members, issue/return logic, fine calculation and console printing. All test cases pass. Feedback says "not modular".

"The requirements were small, so one class was enough." (True for the demo, but the round tests how the code would grow.)

Split by who would change it: Catalog (books), MemberRegistry, LendingService (issue/return rules), FinePolicy (the library's late-fee rules), ConsolePresenter. Say: "the fine rule changes when the librarian changes policy; nothing else should be touched".

Likely follow-ups
  • How would you add a different fine rule for premium members? (Strategy, OCP)
  • Where does input validation live?
