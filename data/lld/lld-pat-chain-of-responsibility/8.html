When to use it, when not to

Use it when
  • Several objects might handle a request and the sender should not know which one.
  • The order of steps matters and must be configurable per use (different chains per endpoint).
  • You want to add, remove or reorder steps without editing the sender (Open/Closed).
  • Escalation: approval limits (team lead up to a limit, then manager, then finance), support tiers.
Avoid it when
  • Every request has exactly one obvious handler: a map from type to handler is simpler and faster.
  • Every handler must always run and none can stop: that is a plain list loop or Observer.
  • The chain gets long and hard to debug ("which of 14 filters returned 403?"). Add logging per hop, or reconsider.
  • Hot paths where each hop costs an indirect call and you could decide in one table lookup.

Pitfalls

  • The request falls off the end. Nobody handled it and nobody noticed. Always add a terminal default (an error handler, a default verdict, a "no approver" exception).
  • Cycles. If chains are built from configuration, A -> B -> A loops forever. Validate the chain when it is built.
  • Order bugs. Rate limiting after an expensive database check wastes the database; auth after logging may log secrets. Order is part of the design; write it down.
  • Side effects before a later stop. In the ATM, nothing touches the stock until the plan succeeds. In general: plan, then commit; or make each handler's effect undoable.
  • Hidden coupling through the request. Handlers that stash data in the request (req["user"]) for later handlers create an ordering dependency. Name such fields clearly.
