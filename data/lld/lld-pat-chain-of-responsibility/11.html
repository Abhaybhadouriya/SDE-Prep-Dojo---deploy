Interview Q&A

Design the cash dispenser of an ATM.

One handler per denomination, in descending order, each holding its note count and a link to the next. A handler takes min(amount / note, count) notes and passes the rest on. The ATM first checks the amount is a positive multiple of the smallest note. To survive limited stock, each handler backs off one note at a time if the rest of the chain fails, and the ATM commits stock changes only after the full plan succeeds. Concurrency: one dispense at a time per machine (a lock around plan + commit).

How to answer

Draw the chain, run one amount through it, then raise the limited-stock trap yourself and fix it with plan-then-commit.

Likely follow-ups
  • Add a new 50 note? (One new handler at the end; nothing else changes.)
  • Prefer fewer notes, or keep 500s for later? (Swap the selection policy: a Strategy inside each handler.)
Chain of Responsibility vs Decorator: both wrap the next object. How do they differ?

Intent and stopping. A decorator adds behaviour around a call and always forwards it; the inner object always runs. A chain handler decides whether to forward at all; it can stop the request and produce the result itself. Structurally both hold a reference to the next object with the same interface, so the shapes look alike; the test is "can it stop?".

How to answer

Give one example of each from HTTP: a timing wrapper (decorator) vs an auth check that returns 401 (chain).

Likely follow-ups
  • Is servlet Filter one or the other? (A chain: a filter may skip doFilter().)
Design an expense approval flow: up to 10k by team lead, up to 1L by manager, above that by finance.

Classic CoR. Approver has a limit and a next approver. approve(expense): if the amount is within my limit, decide; else pass to next. The last handler (finance or the CFO) has no limit, or a terminal handler rejects with "no approver". Limits come from configuration, so policy changes do not need code changes. Record who approved in an audit log.

How to answer

Name the terminal handler explicitly and mention configuration-driven chain building.

Likely follow-ups
  • What if the manager is on leave? (A delegate handler, or skip with a rule.)
  • Some expenses need two approvals? (That is a workflow, not a pure chain; consider State.)
Where does the Linux kernel use Chain of Responsibility?

Netfilter: hook functions registered per protocol family and hook point, sorted by priority, each returning a verdict; NF_ACCEPT continues, NF_DROP and NF_STOLEN stop, NF_QUEUE hands the packet to user space. Notifier chains: priority-sorted callbacks where NOTIFY_STOP ends the walk. Contrast with shared IRQ handlers, where every handler on the line is called: pass-through, not stop-on-handle.

How to answer

Name the struct (nf_hook_ops), the ordering field (priority) and the stop rule (verdicts).

Likely follow-ups
  • Why is priority better than registration order? (Modules load in any order; priority makes the chain deterministic.)
A request was rejected with 403 and nobody knows which of 12 filters did it. How do you design for debuggability?

Make the chain observable: each handler has a name; the chain runner (not each handler) logs entry and decision per hop with a request id, and returns a structured rejection ({handler: "fraud", reason: "score 0.93"}). Expose the configured order (a debug endpoint or a startup log line). Metrics per handler: count of passes and stops. Keep chains short and grouped by concern.

How to answer

Push cross-cutting logging into the runner so handlers stay single-purpose.

Likely follow-ups
  • How do you test one handler alone? (Give it a fake next handler and assert it was or was not called.)
What happens if no handler handles the request? How do you prevent silent failures?

In a naive chain the last handler calls a null next, or returns nothing, and the request vanishes. Prevent it with a terminal handler that always answers (an error, a default verdict, a dead-letter queue), or make the base class's "no next" path return an explicit failure, as the Python example does with 500. Validate chains at build time: non-empty, ends in a terminal handler, no cycles.

How to answer

Mention it before being asked; it shows production experience.

Likely follow-ups
  • What does netfilter do if every hook accepts? (The packet continues; the default is to accept unless a table policy drops it.)
Design a logger with levels where DEBUG goes to console, INFO also to a file, ERROR also pages on-call.

A pass-through chain: console(min DEBUG) -> file(min INFO) -> pager(min ERROR). Every handler sees every record and writes it if the level is at or above its minimum. The walk is fixed in a final log() in the base class; subclasses implement only write(). For production, make handlers asynchronous (a queue in front of the file and pager handlers) so a slow pager never blocks request threads, and keep the chain configurable from a file.

How to answer

Point out that this is the pass-through style and say why (multiple sinks); compare with the stop-on-handle style.

Likely follow-ups
  • How do Java and Python loggers do it? (Handlers per logger, plus propagation to parent loggers.)
