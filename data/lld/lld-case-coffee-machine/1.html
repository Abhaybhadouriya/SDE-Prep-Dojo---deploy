How it is asked

Before you start: this case assumes OOP from C structs (objects as structs with an ops table) and interfaces vs abstract classes. The patterns it uses are explained on their own pages: Decorator, Factory Method, Observer, dependency injection. The outlets use a thread pool.

Two versions exist. The Dunzo version is a machine-coding round or take-home: a fixed requirement list (beverages from ingredients, N outlets in parallel, serve only if every ingredient is available, low-ingredient indicator, refill, integration tests), with a JSON file of ingredients and recipes, and working code expected. The vending-style version (Amazon, Walmart) is a 45-60 minute LLD round: select a drink, pay, pour, admin refills, discussed on a whiteboard or in an editor.

A 2025-10 community design of the same problem (LC 7241428) used State for the machine, Strategy plus Factory for payment and a Singleton; we discuss each of those choices below. The coffee machine is also the standard Decorator example in pattern books and on Refactoring.Guru, so interviewers expect you to reach for it when toppings appear.

The Dunzo statement says "maximum N beverages can be served in parallel" and "provide functional integration test cases". Those two lines are the grading: a correct, tested inventory under concurrency beats a beautiful class diagram. In the Amazon/Walmart style round, ask early whether payment is in scope; if it is, reuse the escrow idea from the vending machine.
