Interview follow-ups

Why Decorator for add-ons instead of subclasses or a list of add-ons?

Subclasses explode: every combination needs a class, and repeats (double shot) are impossible. A plain List<AddOn> inside the drink also works for price and ingredients, and is a fair answer. Decorator is better when add-ons change behaviour, not just numbers: an add-on that changes the name, adds a brewing step, or applies a discount to the inner price can do it in its own method. It also keeps the base drink closed for modification.

How to answer

Give the 64-class count, then present Decorator, then admit the list is fine if add-ons are pure data. Interviewers like the trade-off.

Likely follow-ups
  • Does the order of decorators matter? (For sums no; for a "20% off" wrapper yes.)
  • Decorator vs Proxy?
Two outlets both want the last 150 ml of milk. Walk me through what your code does.

Reservation happens in tryReserve, which holds the inventory lock while it checks every ingredient and then subtracts all of them. The first caller to get the lock sees 150, takes it, and releases the lock. The second sees 0 and is refused with "milk is not available". No negative stock, no half-taken recipe. The concurrency test runs 200 orders on 8 threads for 20 shots and asserts exactly 20 served.

Likely follow-ups
  • Why not a ConcurrentHashMap? (Atomic per key, not per recipe.)
  • How would finer-grained locks look? (Sorted lock order plus rollback.)
How do you guarantee at most N beverages in parallel?

The outlets are a fixed thread pool of size N, so at most N pour tasks run at once and the rest wait in the pool's queue. I measure it with an atomic busy counter and assert the peak is at most N. A Semaphore(N) around brewing is the alternative if callers should brew on their own thread; with a semaphore, use tryAcquire if the requirement is "refuse when busy" instead of "queue".

Do you take the ingredients when the order is accepted or when brewing starts?

At acceptance. Then "yes, we will make it" is a promise: a queued order can never fail later because the milk was used by an order behind it, and the customer gets an immediate refusal otherwise. The cost is that reserved stock is not available to others while the order waits for an outlet, which is the correct behaviour anyway. If brewing fails, the outlet releases the reservation.

How does the low-ingredient indicator work, and why does it not fire on every order?

Each ingredient has a low mark. lowIngredients() lists everything below its mark, for the display. Alerts are edge-triggered: the inventory fires onLow only when a subtraction moves a level from at or above the mark to below it. Listeners (Observer) are called after the lock is released. A refill above the mark re-arms the alert.

Likely follow-ups
  • Level- vs edge-triggered: which would you use for a pager? (Edge, plus a periodic reminder.)
Why is the factory a registry and not a switch on the drink name?

A switch must be edited for every new drink, and it ties the code to a fixed menu. A map from name to recipe (and name to wrapper constructor) lets the menu come from config, lets tests register a fake drink, and keeps the factory closed for modification. It is the same idea as a driver registering itself by name.

Add payment. Where does it go in the flow?

Order becomes: build the beverage, reserve ingredients, charge through a PaymentMethod strategy (UPI, card, cash), then submit to an outlet. If the charge fails, release the reservation. If brewing fails after a charge, refund through the same method. Reserving before charging means we never take money for a drink we cannot make. Cash with change reuses escrow from the vending machine.

Would you use the State pattern here?

Not for the Dunzo version: each order is accept-or-refuse, and the machine behaves the same at all times. Once there are machine modes (maintenance, out of order, cleaning) or a multi-step customer flow (select, pay, pour), yes: each state answers order, pay and refill differently, exactly like the vending machine. Adding patterns only when a requirement needs them is part of the score.

Should CoffeeMachine be a Singleton?

No. One physical machine per process does not need a global access point. A Singleton makes tests share state (our tests build a fresh machine with 1, 3 or 4 outlets) and hides the dependency. Create it at startup and pass it to whoever needs it (dependency injection).

How do you test multithreaded behaviour without flaky tests?

Make outcomes deterministic and assert invariants, not timings. Example: stock exactly k servings, fire many orders from many threads, assert exactly k served and stock 0. For the outlet limit, assert "peak <= N", never "peak == N". Inject the brewer so tests use an instant or failing fake. Await all futures before asserting, and use a timeout so a deadlock fails the test instead of hanging it.

Decorator vs Builder for a custom order: which one?

They solve different problems and work together. Builder collects the choices (drink, size, add-ons, milk type) into a valid order object step by step. Decorator is how the resulting beverage computes price, name and recipe at runtime. The builder's build() can call the factory, which applies the decorators.
