Clarify the requirements

Functional (P0)

  1. Menu The machine serves named beverages (espresso, americano, latte, cappuccino). Each has a base price and a recipe: ingredient name to quantity.
  2. Add-ons A customer can add toppings in any combination and any number (extra shot, extra milk, sugar, caramel). Each add-on adds a price and extra ingredients.
  3. Serve only if complete A drink is made only if every ingredient of its final recipe is available in the needed quantity. Otherwise refuse with the reason ("caramel is not available", "milk is not sufficient").
  4. N outlets The machine has N outlets; at most N drinks are prepared in parallel. Extra orders wait for a free outlet.
  5. Low indicator Show which ingredients are running low (below a per-ingredient threshold), and raise an alert when one crosses the threshold.
  6. Refill An operator can refill any known ingredient.
  7. Tests Integration tests for the flows above, including the parallel case.

P1 (mention, build if time allows)

  • Payment (cash with change, UPI, card), machine modes (ready, maintenance, out of order), sizes (small, large), order history and sales report, timed brewing per drink.

Non-functional

  • Never oversell: under any interleaving, the sum of quantities used by served drinks never exceeds what was loaded plus refills. No ingredient goes negative.
  • All or nothing: a refused order leaves the inventory exactly as it was.
  • Extensible: a new drink or add-on is data or one small class, not an edit to a switch.
  • Responsive: a refusal returns at once; it does not wait for an outlet.

Out of scope (say it)

Real hardware (pumps, heaters, grinders), temperature control, networking, a fleet of machines, user accounts. Hide hardware behind a Brewer interface so tests can use a fake.

Questions to ask

  • Are drinks fixed, or loaded from a config file at start (the Dunzo JSON)? Can the menu change at runtime?
  • Can the same add-on be applied twice (double shot)? Is there a limit?
  • What happens when all outlets are busy: queue the order, or refuse with "busy"?
  • Do ingredients leave the store when the order is accepted, or when pouring starts? (We reserve at acceptance, so an accepted order can never fail later for lack of milk.)
  • What is "low": an absolute amount per ingredient, or a percentage of capacity? One alert per crossing, or a repeating alert?
  • Is payment in scope? Which modes?
  • If an outlet fails mid-brew, are the ingredients lost or returned?
