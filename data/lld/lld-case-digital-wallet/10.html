Lock hierarchy, stated once: transaction lock, then (for a reversal) the original transaction's lock, then the two wallet locks in id order. Nobody takes them in another order, so there is no cycle. The ledger list has its own small lock and is touched only while holding wallet locks, never the other way round.

  1. T1 moves money from asha to bala and locks its source first; T2 does the opposite at the same moment. Each holds one wallet lock and waits for the other: the classic AB-BA deadlock.
  2. The guard: post() always locks the wallet with the smaller id first, whatever the direction. This is the kernel rule of a fixed lock order (for example double_rq_lock() locks the two runqueues by address).
  3. T2 now asks for W_asha first too, so it waits while holding nothing. There is no cycle, so no deadlock; T2 runs as soon as T1 has debited, credited and unlocked.

Why not AtomicLong balances?

A single-wallet debit can be a lock-free compareAndSet loop. A transfer cannot: it changes two balances and appends two ledger lines as one unit, and CAS works on one word. You would need two-wallet locking anyway, or a different model: in a database, a single transaction with SELECT ... FOR UPDATE on both rows (ordered by id) or optimistic locking with a version column and retry. Mention both; they are the production versions of the same idea. See locks and deadlock and lock ordering.

From your world

double_rq_lock() in the scheduler locks two runqueues by address order for exactly this reason when migrating a task between CPUs. Our post() is a double-runqueue-lock for money.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
