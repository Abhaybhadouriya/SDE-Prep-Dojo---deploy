Key relationships and patterns, and why each

Pattern / ideaWhereWhy here
AdapterUpiAdapter, CardAdapterEach provider SDK has its own units (rupee strings vs paise), method names (collect vs authorize+capture) and error style (codes vs exceptions). Adapters convert all of that into one charge() returning one result type. The service never sees vendor types.
StrategyGatewayRouter picks a PaymentGatewayWhich gateway runs depends on the method and the amount (CRED: "disable modes by amount"). New method = register one more strategy. Walmart's round was a deep dive on exactly this.
FacadeWalletServiceOne small API for the app; ledger, locks, keys and gateways stay hidden.
Idempotency key (a request registry)byKey map + begin()Clients and networks retry. The first request with a key wins (putIfAbsent); every repeat gets the same transaction back.
Double-entry ledger (append-only)LedgerEntry, post()Auditable history; balances can be rebuilt; conservation is checkable. Accountants have used it for centuries for the same reason.
Command-like transactionsTransactionA request is an object with an id, a status and an inverse (reversal), so it can be stored, retried and undone.
State (as enum)TxnStatusPENDING to SUCCESS or FAILED; SUCCESS to REVERSED. Final states never change.

Adapter vs Strategy, in one sentence each. Adapter changes an interface so a foreign object fits ours. Strategy swaps one algorithm for another behind the same interface. Here both appear on the same class: the router chooses among strategies, and each strategy happens to be an adapter. Interviewers like it when you separate the two roles out loud.
