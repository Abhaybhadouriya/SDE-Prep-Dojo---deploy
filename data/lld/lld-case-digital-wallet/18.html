Quiz

Two requests with the same idempotency key arrive at the same time. What prevents a double transfer?

  1. Checking map.containsKey(key) before inserting
  2. An atomic putIfAbsent (or a unique index) that lets only one request register the key
  3. Making the balance volatile
Check-then-insert is a race. One atomic operation decides a single owner; the other request gets the owner's transaction.

Why lock the two wallets in id order?

  1. So opposite transfers cannot deadlock
  2. To make transfers faster
  3. Because the ledger is sorted by id
A consistent global lock order removes the cycle that causes deadlock.

A deposit's gateway call times out. Best status?

  1. FAILED, so the user can retry with a new key
  2. SUCCESS, to be safe
  3. Keep it PENDING and resolve with the same key or reconciliation
The outcome is unknown. A new key risks a double charge; FAILED may hide a real payment.

How is a transfer reversed?

  1. Delete its two ledger entries
  2. Post a new transaction with the opposite legs and mark the original REVERSED
  3. Set both balances back by hand
Ledgers are append-only. The reversal is itself recorded, linked and idempotent.

Which class is the Adapter?

  1. GatewayRouter
  2. WalletService
  3. CardAdapter, which turns authorize + capture + exceptions into our charge() result
An adapter converts a foreign interface into ours. The router is the strategy selector; the service is the facade.

After a deposit of 1000 and a transfer of 300, what is the sum of all wallet balances including SYS_BANK?

  1. 0
  2. 1000
  3. 700
SYS_BANK is -1000, the users hold 700 + 300. Double entry keeps the total at zero.

Why not call the payment gateway while holding the wallet lock?

  1. It is not thread-safe
  2. A slow network call would block every other transfer on that wallet
  3. The gateway needs the lock itself
Keep slow I/O outside critical sections; lock only around the in-memory posting.
