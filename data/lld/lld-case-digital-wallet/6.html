Core flow: a transfer

  1. The app sends the transfer with its idempotency key. The service tries to register a new PENDING transaction under that key with an atomic putIfAbsent. Nothing was there, so this request owns the work.
  2. It locks the transaction (so a concurrent duplicate waits instead of racing), then both wallets in a fixed order: smaller id first. If another thread is moving money B to A at the same time, it takes the locks in the same order, so no deadlock is possible.
  3. Debit first. If the balance is too low, the debit throws, the transaction becomes FAILED with a reason, and nothing else changes. Otherwise credit the receiver.
  4. Append the two ledger lines (debit and credit, same amount, same transaction id) and mark SUCCESS, all while both locks are held. No other thread ever sees a half-done transfer.
  5. The result goes back. If the response was lost and the app retries with the same key, begin() finds T6 and returns it: no second debit.
