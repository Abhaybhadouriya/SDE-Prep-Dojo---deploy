Retries and the payment gateway

Deposits are where idempotency matters most, because they call the outside world. The classic failure: the gateway charged the user, but the response timed out, and the app retries.

  1. The first request registers k1 as a PENDING transaction before doing anything else.
  2. It calls the gateway (passing k1 on, since most real gateways accept an idempotency key too), gets success, and posts the ledger entries.
  3. The response to the app is lost: timeout, mobile network, app killed.
  4. The app retries with the same key. The service finds T1 (if T1 were still in flight, the retry would wait on T1's lock) and returns it. The user is charged once and credited once.

Unknown outcome. If the gateway itself times out, you do not know whether the user was charged. Do not mark the deposit FAILED (the user may have paid) and do not retry blindly with a new key (double charge). Keep it PENDING, retry with the same key, or ask the gateway for the status of that key; a reconciliation job settles anything still pending. Saying this is what separates a strong answer. The code builds this path: ChargeResult.unknown() is a third result next to ok and failed, the fake UPI SDK can lose one reply after charging (like a real timeout), the deposit stays PENDING with no ledger posting, and calling deposit again with the same key charges nothing new (the gateway dedupes on the key) and posts once.
