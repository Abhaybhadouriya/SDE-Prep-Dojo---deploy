Follow-up questions

How do you implement idempotency, and where is the race?

Store transactions by key. The race is two copies of the same key arriving together: a plain "get, then put" lets both through. Use one atomic step (ConcurrentHashMap.putIfAbsent, or a unique index on the key column in a database). The loser gets the winner's transaction; if the winner is still working, the loser waits on the transaction's lock and returns the final status. Also compare the request body: same key with a different amount is a client bug, so reject it.

How to answer

Name the race before the interviewer does, then show the one-line atomic fix.

Likely follow-ups
  • How long do you keep keys? (A retention window, e.g. 24 h or a few days, then expire.)
  • What does Stripe do? (Client sends an Idempotency-Key header; the server stores the first response and replays it.)
Why a ledger? Why not just keep a balance field?

A balance alone cannot explain itself. With an append-only ledger you can show the user a statement, audit any change, rebuild balances after a bug, and assert "sum of all entries = 0". The balance field stays as a cached, quickly readable projection of the ledger, updated in the same critical section. In databases it is the same pattern: an entries table plus a balances table in one transaction.

A to B and B to A happen at the same moment. Walk me through why it does not deadlock.

Both threads compute the same lock order: the smaller wallet id first. Whichever gets that lock first proceeds to the second; the other blocks on the first lock while holding nothing, so there is no cycle. Without ordering, thread 1 holds A and wants B while thread 2 holds B and wants A: deadlock.

Likely follow-ups
  • What about tryLock with timeout? (Works, but needs retry logic and can livelock; ordering is simpler.)
  • Why might volatile not be enough for a balance? (Visibility, not atomicity of read-modify-write.)
Strategy or Adapter for payment methods?

Both, in different roles. Each vendor SDK is wrapped by an Adapter that implements our PaymentGateway. The Strategy is choosing which gateway handles a payment, based on method, amount, category or provider health. If you write only UpiPayment, CardPayment classes with business logic inside, you have strategies; the moment they call foreign SDKs, the translation part is an adapter.

The gateway times out. Did the user pay?

Unknown. Keep the deposit PENDING. Retry with the same idempotency key (the gateway dedupes), or query the gateway's status API for that key. A reconciliation job compares our PENDING list with the gateway's settlement report and resolves each one. Never mark it FAILED (the user may have been debited) and never retry with a new key (double charge).

How do you reverse a transaction?

Never edit or delete ledger lines. Create a new REVERSAL transaction that posts the opposite legs, link it with reversalOf, and mark the original REVERSED in the same critical section. Make it idempotent with a derived key ("reverse:" + id). Only SUCCESS transfers can be reversed; if the receiver no longer has the money, the reversal fails (or, if the business allows, their wallet goes into a recorded debt).

How would you add offers ("10% cashback on the first transfer")?

After a SUCCESS, run offer rules (each a small strategy or specification: eligible? amount?). A granted cashback is a normal transfer from a SYS_PROMO wallet, with key "cashback:" + txnId so it is granted once. Keep it outside the transfer's locks; it is a follow-up action, ideally triggered by an event.

Wallets now live in different database shards. What changes?

You can no longer lock both rows in one local transaction. Options: two-phase commit (strong but blocking), or a saga: debit A with a pending outgoing record, then credit B, and on failure run a compensating credit back to A; all steps idempotent with derived keys. The ledger and the conservation check become a reconciliation job. That is the HLD version of this problem.

Why integer paise and not double rupees?

Binary floating point cannot represent 0.1 exactly, so sums drift (0.1 + 0.2 is not 0.3). Money needs exact arithmetic: use long minor units (paise) or BigDecimal with a fixed scale. Convert to display strings only at the edge, as our adapters do for the vendor SDK.

Every deposit locks SYS_BANK. Isn't that a global lock?

Yes. Double entry means every external movement has a second leg on the system account, and our post() locks both wallets, so all deposits and withdrawals in the system serialise on one monitor. Two fixes. (1) No balance check on the external leg. The system account is allowed to go negative (it mirrors money held at the bank), so its leg needs no check-then-act: append the ledger line and derive its balance from the ledger (or a striped counter such as LongAdder) instead of locking a shared balance. Only the user wallet is locked. (2) Shard the system account. Use SYS_BANK_0..N-1 chosen by hash of the user wallet id, or one system account per gateway; the total system balance is the sum of the shards. In a database this is the classic hot row problem, solved the same two ways (append-only entries, or N sub-rows summed on read).

How to answer

Admit the hot spot before the interviewer finds it, right after you explain double entry. Then give the fix and its cost: reading the system balance now means a sum.

"Disable a payment mode above an amount and prefer modes by category." Design it.

Per method, a list of rules (min/max amount, allowed categories, enabled flag). Per category, a preference order of methods. The router filters the preference list by rules and returns the first that passes; the client can show the filtered list as "available modes". Adding a rule type is a new class implementing one isAllowed(payment) method (Specification pattern).
