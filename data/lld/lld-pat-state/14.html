Quiz

In the classic State pattern, who decides which state comes next?

  1. The client
  2. A global configuration file
  3. The current state object, by calling the context's setState
  4. The garbage collector
States know their successors. That is the main difference from Strategy, where the client chooses.

Where should the vending machine's balance live if state objects are shared by all machines?

  1. In the context (the machine)
  2. In the HasMoney state object
  3. In a static field of the interface
  4. In every state object
Shared state objects must be stateless; per-machine data belongs to the machine.

Your order system has nine statuses, almost no behaviour per status, and product managers change the allowed moves every quarter. Best fit?

  1. Nine State classes
  2. An enum plus a transition table, possibly in configuration
  3. A Singleton
  4. A switch in every method
When states are mostly labels and the legal moves change often, keep the moves as data.

A SYN arrives on a Linux socket. Which tells the kernel what it means?

  1. The source port
  2. The congestion control algorithm
  3. The receive buffer size
  4. The socket's current sk_state
In LISTEN it starts a connection; in ESTABLISHED it is unexpected. Behaviour depends on state.

What is the clearest sign that State fits better than Strategy?

  1. There are several algorithms
  2. The delegate is injected through the constructor
  3. The delegate changes because of events that happen to the object, and each one knows what comes next
  4. The code is in Java
Lifecycle-driven self-replacement is State; client-driven choice is Strategy.

How should you store a State-pattern entity in a database?

  1. Store the state's name and map it back to a state object when loading
  2. Serialize the state object's class bytes
  3. Store nothing; always start in the initial state
  4. Store every state object
Persist a stable name (enum); behaviour is code and comes back through a mapping.

Two threads call select() on the same machine in HAS_MONEY at the same time. What is the simplest correct fix for one in-memory machine?

  1. Make the state objects synchronized singletons
  2. Serialize events on that machine (a lock per machine or a single-threaded event queue)
  3. Add more states
  4. Nothing; State is thread-safe by design
The race is on the context's data and current state; serialize events per context.
