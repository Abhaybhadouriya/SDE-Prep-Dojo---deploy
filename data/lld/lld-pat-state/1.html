The problem: the same switch in every method

A first vending machine is usually an enum and a switch in every public method:

enum Mode { IDLE, HAS_MONEY, DISPENSING, SOLD_OUT }

class VendingMachine {
    Mode mode = Mode.SOLD_OUT;

    void insertCoin(int r) {
        switch (mode) {
            case IDLE:       balance += r; mode = Mode.HAS_MONEY; break;
            case HAS_MONEY:  balance += r; break;
            case DISPENSING: returnCoin(r); break;
            case SOLD_OUT:   returnCoin(r); break;
        }
    }
    void select(String code) {
        switch (mode) {
            case HAS_MONEY:  /* check stock, check balance, dispense, change mode ... */ break;
            default:         say("ignored");
        }
    }
    void cancel()  { switch (mode) { /* ... again ... */ } }
    void refill()  { switch (mode) { /* ... and again ... */ } }
}
  • One state's behaviour is spread across every method. To understand "what does HAS_MONEY do?" you read four switches.
  • Adding a state edits every method. Add MAINTENANCE and every switch needs a new case; miss one and the machine does something random (or nothing) in that state.
  • Transitions are hidden. mode = ... assignments are buried in branches, so nobody can see the whole lifecycle.
  • Conditions pile up inside cases. "Has money but the item is empty" turns into nested ifs inside a case.

For two or three states this is fine, even best. At five states and four events it is twenty cells of behaviour scattered through four methods.
