The story: the moody vending machine

Explain like I'm 5

Press the button on a vending machine before putting in a coin, and nothing happens. Put in a coin, press the button, and a chocolate drops. Press the button while the chocolate is falling, and nothing happens again. Same button, three different reactions.

It is as if the machine has moods: "waiting for money", "has money", "busy dropping", "empty". In each mood it knows how to react to every button. When something happens, it changes mood: a coin turns "waiting" into "has money".

Now imagine each mood is a little helper living inside the machine. Only one helper is awake at a time. When you press a button, the awake helper decides what to do, and when it is finished it wakes up the next helper and goes to sleep.

That is the State pattern. The machine is the context. Each mood is a state object with one method per event (insert coin, select, cancel). The context forwards every event to the current state, and the state decides both what happens and which state comes next. From outside, the machine seems to change its class.

From your world

You have stepped through this in a debugger. A Linux socket's sk->sk_state holds TCP_LISTEN, TCP_SYN_RECV, TCP_ESTABLISHED, TCP_CLOSE_WAIT and the rest, and tcp_rcv_state_process() in net/ipv4/tcp_input.c is largely a switch (sk->sk_state) deciding what an incoming segment means right now. A SYN means "new connection" in LISTEN and "something is wrong" in ESTABLISHED. The State pattern is the object-oriented way of writing that switch: one class per TCP_* value, each with its own onSyn, onAck, onFin. Same machine, the switch turned inside out.
