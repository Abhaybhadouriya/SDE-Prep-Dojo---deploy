In interviews

State is a Tier 1 pattern. Any problem with a lifecycle invites it, and interviewers ask "how would you add state X?" or "what happens if Y arrives while in Z?" to check that you modelled the states explicitly. Where it fits in our case studies:

Case studyStates
Vending machine, coffee machineIdle, has money, dispensing, sold out (this page)
ATMIdle, card inserted, PIN verified, transaction selected, dispensing, out of service
ElevatorIdle, moving up, moving down, doors open, maintenance (scheduling is a Strategy)
Ride hailingRequested, accepted, arrived, in progress, completed, cancelled (this page's table)
Traffic signalRed, green, yellow, flashing; timed transitions
Food delivery, shopping cartOrder lifecycle: placed, confirmed, preparing, picked up, delivered, cancelled
BookMyShow, hotel bookingSeat or room: available, held (with expiry), booked, released
Chess, tic-tac-toeGame status: in progress, check, won, draw
Customer issue, task trackerTicket: open, assigned, in progress, resolved, closed, reopened

Strong 30-second answer: "The machine reacts to the same buttons differently depending on where it is in its lifecycle, so I'll use State. I'll draw the state diagram first: Idle, HasMoney, Dispensing, SoldOut. Each state is a class with a method per event; the interface's defaults reject unexpected events. States decide the next state. Data (balance, inventory) stays in the machine, so the states are stateless and shared. I'll store the state name as an enum for persistence. If the states had no real behaviour I'd use a transition table instead."
