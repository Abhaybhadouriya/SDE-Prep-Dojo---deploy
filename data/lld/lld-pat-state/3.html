Structure: context, state interface, one class per state

  • Context (VendingMachine): the object clients use. It owns the data (balance, stock), holds the current state, and forwards every public call to it. It has no switch on state.
  • State (interface): one method per event. Default implementations (Java default methods, a C++ base class) give "ignore" or "reject" behaviour so each state overrides only the events it cares about.
  • Concrete States (Idle, HasMoney, ...): the behaviour for one situation, plus the decision about the next state.

Three design choices you must make (and say aloud)

  1. Who decides the transition? In classic State the states do (m.setState(HAS_MONEY) inside Idle.insertCoin). The alternative is that the context looks up a table after the state returns. States-decide keeps behaviour and transition together; a table keeps the whole lifecycle visible in one place.
  2. Where does the data live? Put shared data (balance, stock) in the context. Then state objects are stateless and can be shared singletons (one IDLE for every machine), like the kernel's TCP_* constants. Per-state data (a timer started when entering Dispensing) can live in a state instance created on entry.
  3. What happens on an illegal event? Ignore it, reject it with an error, or (like TCP) answer with a reset. Decide per event; the default methods on the interface are the place for it.

Draw the lifecycle as a UML state diagram before writing code. Every arrow becomes one method in one state class.
