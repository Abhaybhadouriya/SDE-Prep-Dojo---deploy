Enum + switch vs transition table vs State classes

Enum + switchTransition table (data)State classes (the pattern)
Best when2-4 states, few events, simple behaviourMany states, little behaviour per state; workflows that change often or come from configEach state has real, different behaviour for several events
See the whole lifecycleScattered across methodsYes, in one placeSpread across classes (draw the diagram)
Add a stateEdit every switchAdd rowsAdd a class, edit only states that lead to it
Add an eventAdd one methodAdd rowsAdd a method to the interface (default helps)
Illegal transitionsEasy to miss a case (Java switch on enum warns only in some forms)Rejected centrally: missing keyDefault method rejects or ignores
Per-state behaviour and guardsNested ifs in casesNeeds guard and action callbacksNatural: code in the state's method
ExamplesThread.State checks, kernel TCPOrder and payment workflows, Spring Statemachine configs, our ride tableVending machine, ATM, elevator, game phases

A good interview answer often combines them: an enum for the name of the state (stored in the database, sent in APIs), State classes for behaviour, and a small map from enum to state object. In Java, an enum whose constants override abstract methods is a compact State pattern by itself.

Pitfalls

  • Class explosion: twelve states with one line each is worse than a table. Use the pattern where states have real behaviour.
  • Mutable data in shared state objects: if IDLE is shared by all machines, it must not hold a balance. Keep data in the context.
  • Transitions in two places: half in states, half in the context, and nobody knows which wins. Pick one owner.
  • Concurrency: two threads firing events on one context can both read "HAS_MONEY" and both dispense. Serialize events per context (a lock, an actor, a single-threaded event queue), the way the kernel holds the socket lock while processing a segment.
  • Persistence: objects do not survive restarts. Store the state's enum name with the entity and map it back to the state object when loading.
  • Entry and exit actions: "start a 30 s timer when entering DISPENSING" belongs in an onEnter hook called by setState, not copied into every transition that leads there.
