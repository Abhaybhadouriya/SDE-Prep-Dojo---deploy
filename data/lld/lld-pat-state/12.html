Interview Q&A

Design a vending machine. Which pattern and why?

State. The same events (insert coin, select, cancel) behave differently in Idle, HasMoney, Dispensing and SoldOut, and a switch would be repeated in every method. A State interface with a method per event, one class per state, the machine forwarding calls and the states choosing successors. Inventory and balance in the machine; payment methods can be a Strategy; the item catalogue a simple map.

How to answer

Requirements, then the state diagram, then classes, then one or two methods in code. Ask about change, multiple coins and refunds.

Likely follow-ups
  • Add a maintenance mode.
  • What if two users press buttons at once?
  • Coin in while dispensing?
State vs Strategy: the class diagrams are the same. What is the difference?

Who changes the delegate, and when. Strategy: the client picks an algorithm from outside; strategies do not know each other. State: the current state changes the delegate in response to events, from inside; states know their successors and together form a lifecycle. Test: "if I swap it, did something happen to the object (State) or did someone choose a different way of doing the job (Strategy)?"

How to answer

Admit the shapes match, give the "who swaps" test, one example each, and note they combine (a state can use a strategy).

Likely follow-ups
  • Can a strategy change itself? (Then it is drifting toward State.)
When would you use an enum and a switch, or a transition table, instead of State classes?

Enum and switch for two to four states with trivial behaviour. A transition table when states are mostly labels and what matters is which moves are legal, especially if workflows change often or are configured (order status, ticket status). State classes when each state has real, different behaviour across several events. Often combine: an enum for the persisted name, State classes for behaviour.

How to answer

Give the three options with one criterion each; show you are not pattern-happy.

Likely follow-ups
  • How do you stop illegal transitions in each approach?
Where should transition logic live: in the states or in the context?

Either works; pick one and be consistent. In the states (classic GoF): behaviour and its consequence sit together and new states are added locally, but the lifecycle is spread across classes. In the context or a table: the whole lifecycle is visible and checkable in one place, but states lose some autonomy. With guards and entry actions, a table plus small action functions is common in production; for interview-sized machines, states-decide is clean.

How to answer

Name the trade-off (locality vs visibility), choose, and say why.

Likely follow-ups
  • How would you audit every transition? (One setState that logs and validates.)
Two threads fire events on the same machine at once. What can go wrong and how do you fix it?

Both read HAS_MONEY and both dispense, or one changes the state while the other is mid-transition. Serialize events per context: a lock around each public method (fine for one machine), a single-threaded executor or actor per context (events queue up and run in order), or optimistic concurrency with a version number when the state is in a database (UPDATE ... WHERE id = ? AND state = 'HAS_MONEY'). Shared stateless state objects need no locking.

How to answer

Show the race, then the per-context serialization options, then the DB version for persisted entities.

Likely follow-ups
  • How does the kernel do it for sockets? (Socket lock held while a segment is processed; softirq backlog when the user holds it.)
Model a booking with a seat hold that expires after 10 minutes.

States: Available, Held, Booked, Released (or back to Available). Held is entered with an expiry time stored in the context (the booking), and an entry action schedules a timeout event. Events: hold, pay, cancel, timeout. Held.pay moves to Booked; Held.timeout to Available; Booked.timeout is ignored (the hold already became a booking). Persist the state and the expiry, and on restart re-schedule or sweep expired holds.

How to answer

Draw it, make "timeout" an explicit event, and handle the late-timeout race.

Likely follow-ups
  • Payment succeeds one second after expiry?
Walk through the TCP state machine. Would you implement it with the State pattern?

Passive open: LISTEN, SYN arrives, send SYN-ACK, SYN-RECEIVED, ACK arrives, ESTABLISHED. Active open goes through SYN-SENT. Close: the side that closes first goes FIN-WAIT-1, FIN-WAIT-2 and TIME-WAIT; the other goes CLOSE-WAIT and LAST-ACK. State classes fit for clarity or teaching, since a segment means different things per state. Linux uses an integer state and switches in tcp_rcv_state_process() because much processing is shared across states and it is a very hot path.

How to answer

Draw the main path both ways, then give a reasoned yes-or-no with the shared-processing argument.

Likely follow-ups
  • Why does TIME-WAIT exist? (Absorb delayed segments and allow a lost final ACK to be retransmitted.)
How do you persist an object that uses the State pattern?

Store the state's name (an enum or string column) with the entity, not the object. On load, map the name back to the state object through a registry (Map<Status, State>, or an enum whose constants implement the behaviour). Keep a transition history table if you need audit. With stateless state objects there is nothing else to save.

How to answer

Name, mapping, history.

Likely follow-ups
  • How do you migrate when a state is added or renamed?
