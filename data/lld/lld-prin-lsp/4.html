The rules a subtype must follow

Liskov and Wing's paper, and Bertrand Meyer's Design by Contract, give a checklist. There are two groups: signature rules (mostly checked by the compiler) and behaviour rules (checked only by you and your tests).

Signature rules

RuleMeaningIn Java
Parameter types: same or wider (contravariant)The subtype must accept at least what the base acceptsJava requires the same parameter types; a different type is an overload, not an override
Return type: same or narrower (covariant)The subtype may return something more specificAllowed: an override can return a subclass of the base return type
Exceptions: no new kindsCallers only prepared for the base's errors must not meet new onesChecked exceptions are enforced by javac; unchecked ones (UnsupportedOperationException) are not, which is how Bird/Penguin slips through

Behaviour rules

RuleA subtype mayA subtype must not
Preconditions (what must be true before a call)accept more inputs (weaker)demand more (stronger), for example "only if matured"
Postconditions (what is guaranteed after)guarantee more (stronger)guarantee less (weaker), for example "balance dropped by amount plus a fee"
Invariants (always true about the object)add its own extra invariantsbreak the base's invariants, for example "balance is never negative"
History constraint (how state may change over time)change lessallow changes the base forbids, for example a mutable subtype of an immutable type

Here are all four behaviour cases running against one client-side contract check:

import java.util.List;

// The behavioural LSP rules, checked by one client-side contract test.
// Base contract of withdraw(amount):
//   precondition : 0 < amount <= balance
//   postcondition: balance decreases by exactly amount
//   invariant    : balance >= 0
public class ContractRules {
    static class Account {
        protected long balance;
        Account(long opening) { balance = opening; }
        void withdraw(long amount) {
            if (amount <= 0 || amount > balance) throw new IllegalArgumentException("bad amount");
            balance -= amount;
        }
        long balance() { return balance; }
    }

    // OK: WEAKER precondition. Also accepts amount == 0 (a no-op). Everything the base accepts still works.
    static class LenientAccount extends Account {
        LenientAccount(long opening) { super(opening); }
        @Override void withdraw(long amount) {
            if (amount < 0 || amount > balance) throw new IllegalArgumentException("bad amount");
            balance -= amount;
        }
    }

    // OK: STRONGER postcondition. Same balance effect, plus it promises one extra thing.
    static class AuditedAccount extends Account {
        long lastWithdrawal = -1;
        AuditedAccount(long opening) { super(opening); }
        @Override void withdraw(long amount) { super.withdraw(amount); lastWithdrawal = amount; }
    }

    // BROKEN: STRONGER precondition (rejects inputs the base accepts).
    static class LockedDeposit extends Account {
        LockedDeposit(long opening) { super(opening); }
        @Override void withdraw(long amount) { throw new IllegalStateException("locked until maturity"); }
    }

    // BROKEN: WEAKER postcondition (balance drops by more than amount).
    static class FeeAccount extends Account {
        FeeAccount(long opening) { super(opening); }
        @Override void withdraw(long amount) { super.withdraw(amount); balance -= 10; }
    }

    // Client code written only against Account's documented contract.
    static String check(Account a) {
        long before = a.balance();
        try { a.withdraw(100); }
        catch (RuntimeException e) { return "VIOLATES (stronger precondition: " + e.getMessage() + ")"; }
        if (a.balance() != before - 100) return "VIOLATES (weaker postcondition: dropped by " + (before - a.balance()) + ")";
        if (a.balance() < 0) return "VIOLATES (invariant)";
        return "substitutable";
    }

    public static void main(String[] args) {
        List<Account> accounts = List.of(new Account(500), new LenientAccount(500), new AuditedAccount(500),
                                         new LockedDeposit(500), new FeeAccount(500));
        for (Account a : accounts)
            System.out.printf("%-15s %s%n", a.getClass().getSimpleName(), check(a));
    }
}

Two subtle cases are worth knowing for SDE-2 rounds:

  • Overdraft accounts. An overdraft account accepts larger withdrawals (a weaker precondition, which sounds fine) but lets the balance go negative, which breaks the base invariant "balance is never negative". Weakening a precondition is only safe if every invariant still holds. Either the base must not promise a non-negative balance, or overdraft is not a subtype of it.
  • History constraint. If a base type is immutable (callers cache it, share it across threads), a subclass that adds a setter breaks callers even though no single method misbehaves. This is why Java value types like String are final.
