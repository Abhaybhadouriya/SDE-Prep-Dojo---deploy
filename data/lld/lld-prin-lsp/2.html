Trap 1: Rectangle and Square

This is the example every interviewer knows. In maths, every square is a rectangle, so it feels natural to write class Square extends Rectangle. A square must keep its own rule (width equals height), so it overrides both setters to change both sides.

Now take client code that was written for rectangles and hand it a square. Step through what happens:

  1. resize() was written against Rectangle. It receives an object whose real class is Square; the compiler is happy.
  2. setWidth(5): the Square keeps its own rule and sets both sides to 5.
  3. setHeight(4): again both sides change. The width the client just set is silently lost. Rectangle promised it would not be.
  4. area() returns 16, a perfectly valid square area.
  5. The client's assumption (5 x 4 = 20) fails. No line of the client changed: the subtype broke it. That is an LSP violation.

The full runnable version, with the second trap included:

import java.util.List;

// BEFORE: two classic LSP violations. Both compile. Both break a client at runtime.
public class LspBefore {
    // ---- 1. Rectangle / Square ----
    static class Rectangle {
        protected int w, h;
        void setWidth(int w)  { this.w = w; }
        void setHeight(int h) { this.h = h; }
        int area() { return w * h; }
    }
    static class Square extends Rectangle {            // "a square IS-A rectangle"... in maths
        @Override void setWidth(int w)  { this.w = w; this.h = w; }   // keeps its own invariant w == h
        @Override void setHeight(int h) { this.w = h; this.h = h; }   // ...but breaks the parent's promise
    }

    // Client written against Rectangle's contract: setHeight does not change the width.
    static void resize(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        int a = r.area();
        System.out.println(r.getClass().getSimpleName() + ": expected 20, got " + a + (a == 20 ? "  ok" : "  BROKEN"));
    }

    // ---- 2. Bird / Penguin ----
    static class Bird {
        void fly() { System.out.println(getClass().getSimpleName() + " flies south"); }
    }
    static class Sparrow extends Bird {}
    static class Penguin extends Bird {
        @Override void fly() { throw new UnsupportedOperationException("penguins cannot fly"); }
    }

    static void migrate(List<Bird> flock) {
        for (Bird b : flock) b.fly();                   // trusts Bird's contract
    }

    public static void main(String[] args) {
        resize(new Rectangle());
        resize(new Square());
        try { migrate(List.of(new Sparrow(), new Penguin())); }
        catch (UnsupportedOperationException e) { System.out.println("migrate crashed: " + e.getMessage()); }
    }
}
$ javac -d out LspBefore.java && java -cp out LspBefore
Rectangle: expected 20, got 20  ok
Square: expected 20, got 16  BROKEN
Sparrow flies south
migrate crashed: penguins cannot fly

Why is the maths intuition wrong? A mathematical square never changes; it is a value. A mutable Rectangle object makes a promise that maths squares never had to make: "you can change the height alone". A square cannot keep that promise. So the question is never "is a square a rectangle?" but "can a square do everything my Rectangle class promises?" Here, no.

Three honest fixes, from most to least common:

  1. Make them siblings. Both implement a Shape interface with area(). No shared setters, so no broken promise.
  2. Make them immutable. If shapes are values with no setters, a square really is a special rectangle again, and "change" means "make a new one" (withWidth returns a new object).
  3. Drop the subtype. A Rectangle with an isSquare() query is often enough.
