LSP violations in real libraries

Even the JDK has famous examples. They make good interview material because they show you read real code, not just textbook shapes.

  • java.util.Stack extends Vector. A stack should only allow push, pop and peek, but because it inherits from Vector it also exposes insertElementAt and get(i), which break last-in-first-out. The JDK documentation itself points you to Deque instead. The fix in design terms is Replace Inheritance with Delegation: a stack should have a list, not be one.
  • Unmodifiable lists. List.of(...) and Collections.unmodifiableList throw UnsupportedOperationException from add. The JDK avoids calling this an LSP violation by documenting add as an "optional operation" in the Collection contract. That works only because the base contract was written to allow it. Interviewers like asking whether this is good design; a fair answer is "it is a pragmatic trade-off that weakens what List promises, and a separate read-only interface would have been cleaner".
  • Properties extends Hashtable. Properties expects string keys and values, but the inherited put accepts any object, and the Javadoc warns against using it.

Signs of an LSP problem in a code review: instanceof checks or type switches in client code ("if it is a Penguin, skip"); overrides that throw "not supported"; empty overrides that silently do nothing; overrides that ignore an argument; and subclass comments like "do not call X on this one".
