Interview questions

What is the Liskov Substitution Principle, and what problem does it solve?

Objects of a subtype must be usable wherever the base type is expected, without the client noticing or breaking. It solves the problem of inheritance that compiles but misbehaves: without it, polymorphism is unsafe, because every caller would need instanceof checks for special subtypes. With it, you can add subtypes (and follow OCP) safely.

How to answer

One-line definition, the problem it prevents (unsafe polymorphism, instanceof checks), then one example in 20 seconds.

Likely follow-ups
  • Give an example of a violation.
  • How is LSP different from just "using inheritance correctly"?
Why does Square extending Rectangle violate LSP? How would you fix it?

A mutable Rectangle promises that setHeight leaves the width unchanged. A Square must change both sides to keep width equal to height, so a client that sets width 5 and height 4 gets area 16 instead of 20. Fix: make both implement a Shape interface with no shared setters, or make shapes immutable so "changing" returns a new object.

How to answer

State the broken promise precisely (setHeight keeps width), show the 5x4 calculation, then give two fixes.

Likely follow-ups
  • Is it ever OK for Square to extend Rectangle?
  • What if Rectangle is immutable?
You are given code where Penguin extends Bird and fly() throws. Refactor it to follow LSP.

The base type promises too much. Keep Bird to what all birds do (eat, name). Add FlyingBird extends Bird { fly(); } and optionally SwimmingBird. Sparrow implements FlyingBird, Penguin implements SwimmingBird, and any code that needs flight takes a FlyingBird. Passing a penguin there now fails at compile time.

How to answer

Name the cause (base promises too much), split the interface, and point out the compile-time payoff.

Likely follow-ups
  • Which other SOLID principle did you just apply?
  • What if a bird can fly only sometimes, like a bird with a broken wing?
What are the precondition and postcondition rules of LSP?

A subtype may not strengthen preconditions (it must accept everything the base accepts) and may not weaken postconditions (it must guarantee at least what the base guarantees). It must also keep the base invariants and must not allow state changes the base forbids (the history constraint). Example: a LockedDeposit whose withdraw always throws strengthens the precondition; a FeeAccount that deducts an extra fee weakens the postcondition.

How to answer

Use the words "strengthen" and "weaken" correctly and give one banking example for each.

Likely follow-ups
  • Where do invariants and the history constraint fit?
  • How do you test these rules?
Is throwing UnsupportedOperationException from an override always an LSP violation? What about Java's unmodifiable lists?

It is a violation unless the base contract allows it. The JDK marks List.add as an "optional operation" that may throw, so unmodifiable lists technically honour the documented contract. It is still a weak design, because every caller must remember the hidden failure path. A cleaner design separates read-only and mutable interfaces, as Kotlin does with List and MutableList.

How to answer

Show nuance: the contract decides. Then give your design opinion and the cleaner alternative.

Likely follow-ups
  • Name another LSP problem in the JDK (Stack extends Vector).
  • How would you design a read-only collection API?
How do you detect and prevent LSP violations in a large codebase?

Detect: look for instanceof or type checks in client code, overrides that throw "not supported" or do nothing, and subclass-specific comments. Prevent: write contract tests that run the base type's test suite against every implementation, prefer composition when a subclass would disable behaviour, make classes final unless designed for extension, document contracts, and use sealed hierarchies when the subtypes are known.

How to answer

Two lists: detection signals and prevention practices. Mention contract tests explicitly.

Likely follow-ups
  • How would you structure contract tests in JUnit?
  • Does LSP apply to interfaces with no shared code?
Give an example of LSP outside object-oriented class hierarchies.

Any interface with many implementations: Linux file_operations (a driver's read must honour the byte-count, EOF, errno and O_NONBLOCK rules), REST API versions (v2 must accept what v1 clients send), and drop-in library replacements. In each case callers rely on behaviour, not just on a signature, and a "compatible" replacement that changes behaviour breaks them.

How to answer

Show the principle is about contracts in general. Use your kernel background.

Likely follow-ups
  • How do you version an API so that it stays substitutable?
  • What happens if a driver returns more bytes than requested?
Where have you used (or seen) LSP in your own projects?

Prepare an honest example. For a kernel or networking engineer: "Our driver framework had a struct device_ops with reset(). One hardware variant could not reset without a power cycle, and its implementation silently returned success. Callers assumed the device was clean after reset, which caused hard-to-find failures. We changed the contract so reset() returns -EOPNOTSUPP and callers check a capability flag first." Keep it to the broken promise, the symptom and the fix.

How to answer

Use the STAR shape: situation, the broken promise, impact, fix. Interviewers ask this because candidates often know only the textbook example (one LeetCode report describes failing exactly this question).

Likely follow-ups
  • How did you find the bug?
  • How did you stop it happening again?
