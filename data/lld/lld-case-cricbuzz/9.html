Concurrency and thread safety

The honest first answer: one match has exactly one writer, the scorer. Balls are strictly ordered, so there is nothing to parallelise in the scoring itself. The interesting part is the read side: thousands of viewers polling or subscribed to the same match.

Step through the race this section is about, then the fix the code uses:

  1. The scorer thread applies a four: it has updated the runs (45 to 49) but not yet the ball count.
  2. A viewer's request reads the live fields in between.
  3. The viewer sees 49/2 in 5.2 overs, a score that never existed. Nothing crashes; the numbers are just wrong.
  4. The fix: the scorer builds a new immutable snapshot after each ball and publishes it with one AtomicReference.set; a reader does one get() and always sees a whole ball applied or none. Writers stay single-threaded per match.
  • Single writer per match. Route every ball for match m to one thread, actor or queue partition (key = match id). No locks inside Innings are needed because nothing else writes it. Many matches run in parallel because they share nothing mutable.
  • Readers get immutable snapshots. LiveScore publishes a new immutable string (in production, an immutable ScoreSnapshot object) through an AtomicReference. A reader does one get() and sees a consistent total, wickets and overs, never a half-applied ball. Python uses a tiny lock for the same effect.
  • Do not let readers walk the live maps. If a REST handler iterated battingCard() while the scorer updated it, a reader could see runs updated but balls not yet. Either copy under a lock, or (better) build the snapshot on the writer thread after each ball.
  • Idempotent input. Scorer apps retry on bad networks. Give each ball a sequence number; the match accepts seq == lastSeq + 1, ignores duplicates and rejects gaps. That is the same as TCP sequence numbers protecting against duplicated segments.
  • Slow listeners. A listener that pushes to the network must not block the scorer. Hand events to a queue and let a separate sender deliver them (this is where the HLD's pub-sub and fan-out begin; see Pub-Sub and Notification Service).

From your world

"Writer builds a new immutable object, then swaps one pointer; readers just load the pointer" is RCU: rcu_assign_pointer() on the update side and rcu_dereference() on the read side. AtomicReference.set/get gives you the publish/subscribe ordering, and the garbage collector plays the role of the grace period that frees old snapshots.
