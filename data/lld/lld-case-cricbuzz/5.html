Equality and sharing are safe."Parse, then apply: a typo can never half-update the score."
Information expert / SRPRules in Innings, result in Match, text in listenersEach class changes for one reason: rules, flow or presentation."If the scoring rule changes, only Innings changes."
CompositionMatch has Innings; Innings has stats; Team has PlayersNothing "is a" Match. No inheritance except listener implementations."No base class Player with Batter and Bowler subclasses: a player does both."

Patterns we deliberately skipped: a Singleton scoreboard (you want many matches in one process and in one test), Batter/Bowler subclasses of Player (an all-rounder is both, so roles are stats, not types) and a Strategy per ball type (four branches in one method is clearer than four classes; revisit if byes, leg byes, penalty runs and free hits all arrive).

From your world

This is the same discipline as a protocol state machine in a network stack: TCP in SYN_SENT rejects data, and the handler first checks sk->sk_state before acting. A small enum plus a guard at the top of each entry point is how the kernel writes most state machines; full State objects (one ops table per state) pay off only when each state has a lot of different behaviour.

Why the pattern earns its place: the if-ladder it replaces

Without the Observer, the scoring code calls every consumer by name:

void bowl(String token) {
    Ball b = Ball.parse(token);
    current().bowl(b);
    printer.printBall(b, current());          // console
    liveScore.update(current());              // website
    commentary.say(b);                        // follow-up 1: edits Match
    pushNotifier.maybeAlert(b, current());    // follow-up 2: edits Match again
    if (current().isComplete()) {
        printer.printScorecard(current());
        liveScore.update(current());
    }
}
interface MatchListener {
    default void onBall(Match m, Ball b) {}
    default void onOverEnd(Match m, Innings in) {}
    default void onInningsEnd(Match m, Innings in) {}
}
void bowl(String token) {
    Ball b = Ball.parse(token);
    current().bowl(b);
    for (MatchListener l : listeners) l.onBall(this, b);   // Match knows no consumer
}

With direct calls, the follow-ups "add commentary" and "push alerts on wickets" each edit Match, the class with the scoring rules. With the Observer each is one new listener class registered in the driver; Match is closed.

From your world: the same move in C

struct match_listener_ops {
    void (*on_ball)(struct match_listener *l, const struct match *m, const struct ball *b);
    void (*on_innings_end)(struct match_listener *l, const struct match *m);
};
/* like a notifier chain: list_for_each_entry(l, &m->listeners, node) if (l->ops->on_ball) l->ops->on_ball(l, m, b); */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
