Interview follow-ups

Two patients book the last seat at the same moment. Who gets it, and how do you guarantee only one?

Whoever acquires the lock first. Check and insert run inside one critical section, so the second request sees free() == 0 and goes to the waitlist. "First" means first to the lock, not first to tap; that is fair enough for an in-memory system. With a database it becomes a conditional update or row lock, and the loser gets "slot just filled".

How to answer

Name the race (check-then-act), show where the lock is, and mention the 50-thread test you wrote.

Likely follow-ups
  • Is ReentrantLock(true) fairer? (Yes, FIFO among waiting threads, at a throughput cost.)
  • What with 1,000s of users, like BookMyShow? (Hold a seat for N minutes, then confirm.)
Why not one lock per slot?

Because the rules span slots: the overlap and quota rules read the user's other bookings. Two threads booking the same user into two different 12:30 slots would each hold a different slot lock and both pass. The correct fine-grained version locks the user first, then the slot, always in that order. It is a good "next step", not a 90-minute default.

How to answer

Give the counterexample in one sentence; then give the lock order.

The waitlisted user now has another class at the same time. What happens on promotion?

Promotion re-runs every rule for that user, with their waitlisted booking removed from "others". If a rule fails, that entry is cancelled, the user is told "dropped from waitlist", and the loop tries the next person. Rules can change while someone waits (they booked elsewhere, they used up quota), so checking only at join time is a bug.

Add "rank by doctor rating" without touching the service.

Write ByRating implements RankingStrategy and pass it to available. The service never sorts; it filters, then hands the list to the strategy. Ties break by start time so output is stable. That is exactly what the Flipkart prompt asks for.

How do you keep "trending doctor" cheap?

A counter per provider, incremented on confirm or promote and decremented on cancel, all under the same lock. Reading the max over a few hundred providers is fine. For many providers, keep a sorted structure (a TreeMap<count, Set<provider>>) or a heap with lazy updates, the same trick as a leaderboard.

How is "cancel at least 30 minutes before" testable?

The service takes a clock (IntSupplier, or java.time.Clock in real code) in its constructor. The test moves a fake clock to 05:45 and asserts the cancel of a 06:00 class fails. A hidden System.currentTimeMillis() makes this impossible without sleeping.

Send a reminder 15 minutes before each class. Where does that live?

Outside the booking service. A reminder component owns a ScheduledExecutorService or DelayQueue; on confirm it schedules a task at start minus 15, and on cancel it cancels the task (keep the ScheduledFuture by booking id). Or poll every minute for bookings in the window. The service only fires events; it does not schedule.

Likely follow-ups
  • Across restarts? (Persist the reminders, or derive them from bookings on startup.)
Doctors and gym centres: one class or two?

One Provider with a category, because booking logic does not differ. If doctors later get qualifications and gyms get equipment, add subclasses or a details object, but the service should still depend only on what booking needs. That is Interface Segregation proper: BookingService would depend on a small Bookable interface exposing only time, capacity, rating and category, not on the whole Provider, so adding qualifications or equipment never touches booking code.

Make the storage swappable for a database.

Extract SlotRepository and BookingRepository interfaces with in-memory implementations. The service keeps the business rules; the repository hides the maps. With a DB the lock moves into the store: a transaction that selects the slot FOR UPDATE, checks, inserts the booking, and commits.

Why are notifications sent after unlocking, and what can go wrong?

A listener may do I/O; holding the lock during I/O stalls every booking. Collect events while locked, fire after. The risk: a listener could see "promoted" after another thread already cancelled that booking. If ordering matters, attach a version or timestamp to each event, or push events into a single-consumer queue.
