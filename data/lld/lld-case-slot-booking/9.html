Concurrency and thread safety

The race every reviewer asks about (Meesho asked it directly, Flipkart in the review call): two people tap "Book" on the last seat at the same instant. Without a lock both read free() == 1, both insert, and the class has one person too many. The fix is that check and insert happen inside one critical section.

Why one lock for the whole service is the right first answer

A booking touches two things: the slot (seats, waitlist) and the user's other bookings (overlap and quota rules). A per-slot lock alone is not enough: PatientA could book S2 and S5 (same time, different doctors) on two threads, each holding a different slot lock, and both pass the overlap rule. You would need the user's lock too, and then a lock order (user first, then slot) to avoid deadlock. In a 90-minute round, one ReentrantLock on the service is correct, simple, and fast enough for an in-memory demo. Say the finer-grained version out loud as the next step.

Notifications go out after the lock is released

book, cancel and cancelSlot collect messages into a local list while locked and call the listeners after unlock(). A slow SMS gateway must not block every other booking. The price: a listener may see events slightly after another thread's later change. For notifications that is fine.

The proof in the demo

50 threads wait on a CountDownLatch, then all book a class with capacity 10 and waitlist 5. The output is always confirmed=10 waitlisted=5 rejected=35. The Python test does the same with 50 threads and a threading.Event.

From your world

This is the same reasoning as a single spinlock around a driver's ring buffer before you split it per queue. Start with one lock that is obviously correct; split it only with a lock order you can write down (like the kernel's documented mmap_lock before page_table_lock), because lockdep will not run in an interview.

Trade-offs to say out loud

One service lock
  • Trivially correct: rules see a consistent world
  • No deadlock possible
  • Easy to explain in 30 seconds
Costs
  • Bookings for unrelated slots queue up behind each other
  • Does not scale across processes
  • Next step: per-user then per-slot locks in a fixed order, or optimistic version checks in a DB

For the database version (the "what changes with a DB" question), see booking concurrency: a conditional update (UPDATE slot SET booked = booked + 1 WHERE id = ? AND booked < capacity) or a row lock does the same job as our lock.
