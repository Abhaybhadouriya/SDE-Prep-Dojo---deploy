A note on the label: this is not GoF Chain of Responsibility. Real CoR stops at the first handler that handles the request; here every rule runs and all must pass. For a true chain, see the autocomplete router's ordered fallbacks (literal, then parameter, then wildcard: the first match answers).

Patterns we deliberately skipped: a Singleton BookingService (the demo runs a clinic and a gym side by side, with different slot lengths and cutoffs), inheritance such as Doctor extends Provider and GymClass extends Provider (booking logic is the same for both; only data differs), and a full State class per booking status (three states, four transitions).

From your world

The rule list is a netfilter chain: each hook looks at the packet (the booking request) and either lets it pass or drops it with a reason. Adding a rule is registering another hook, not editing the core. The ranking strategy is a function pointer in an ops table, like choosing a TCP congestion-control module by name: same socket code, a different cong_avoid behind the pointer.

The overlap test in one line

Two half-open ranges [s1, e1) and [s2, e2) overlap exactly when s1 < e2 && s2 < e1. That single condition covers partial overlap, containment and equality, and says "no" for back-to-back slots (9:30-10:00 and 10:00-10:30). It is used twice: a doctor's new slot must not overlap the doctor's other open slots, and a user's new booking must not overlap their other confirmed bookings.

Why rules see only "others", not the whole service

A rule gets the user, the target slot and that user's other active bookings. It cannot change anything. That keeps rules pure (easy to unit-test), and it means the service can reuse the same rules at promotion time with a slightly different "others" list (the promoted booking itself removed).
