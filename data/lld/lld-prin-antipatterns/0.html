The story: Mr. Do-It-All and the hammer

Explain like I'm 5

A small school has one office clerk, Mr. Do-It-All. He takes admissions, collects fees, plans the bus routes, prints report cards and keeps the keys. At first it is great: one person knows everything.

Then the school grows. Every change - a new fee, a new bus stop, a new report card - waits in his queue. When two teachers ask him for things at the same time, he mixes them up. When he is sick, the whole school stops.

His friend, Ms. Hammer, is a carpenter with one favourite tool. She uses it on nails, on screws, on windows and on cakes. The nails go in fine. The cakes do not.

Mr. Do-It-All is a god object: one class that knows and does too much. Ms. Hammer is the golden hammer: one familiar tool (or design pattern) used for every problem. Both are anti-patterns.

An anti-pattern is a solution that is common, looks sensible when you write it, and reliably causes more pain than it saves. Each one also has a known better way to do it. Compare that with a code smell (a symptom you notice, like a 600-line class; see Code Smells & Refactoring) and a bug (code that gives the wrong answer). Anti-pattern code often works today. The cost arrives with the next requirement - and in an interview, the next requirement arrives in ten minutes.

From your world

You already know kernel anti-patterns by heart, even if nobody called them that: the 5,000-line driver with a giant switch on the ioctl command, the global variable that broke when network namespaces arrived, the subsystem that forced every driver through code it did not want. The object-oriented versions have the same shapes and the same cures.
