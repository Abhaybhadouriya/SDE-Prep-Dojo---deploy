God object: one class to rule them all

A god object is a class that holds most of the system's data and makes most of its decisions. In LLD rounds it is the single most common design failure, because it is the natural result of "start coding and keep adding methods".

How to spot it in 10 seconds

  • Disjoint clusters. Some methods use only the spot maps, others only the price table, others only the SMS key. That is low cohesion (how strongly the parts of a class belong together; see Coupling & Cohesion).
  • Many reasons to change. Ask "which team would ask me to edit this?" If the answer is more than one, the Single Responsibility Principle is broken.
  • Name smells. Manager, Handler, System, Util, Helper with no noun after it. Not proof, but a hint.
  • Everything imports it, and it imports everything.

Refactoring it out, live

You do not need a rewrite. Group fields by the methods that use them, give each cluster a class or an interface, and leave a thin coordinator. Click through the steps:

  1. The god class. Before moving code, list its fields and mark which methods touch which field. Clusters appear: spots, prices, messages, money.
  2. Extract the pricing cluster behind a PricingPolicy interface. ParkingService keeps a reference to it and asks it for the fee.
  3. Do the same for messages (Notifier) and money (PaymentGateway). The service no longer holds API keys or URLs.
  4. Spot allocation becomes SpotAllocator; the loose "plate + spot + time" triple becomes a Ticket record. The service is now a thin coordinator.
  5. Concrete classes implement the interfaces (dashed line, hollow triangle). A weekend tariff is a new class; ParkingService is not edited.
static class ParkingLotManager {
    private final Map<String, String> spotToPlate = new HashMap<>();   // spot id -> plate
    private final Map<String, Long> entryTime = new HashMap<>();       // plate -> entry minute
    private final List<String> freeSpots = new ArrayList<>(List.of("S1", "S2", "S3"));

    String park(String plate, long nowMin) {
        if (freeSpots.isEmpty()) throw new IllegalStateException("full");
        String spot = freeSpots.remove(0);              // allocation policy
        spotToPlate.put(spot, plate);                   // bookkeeping
        entryTime.put(plate, nowMin);
        System.out.println("SMS to owner of " + plate + ": parked at " + spot); // notification
        return spot;
    }

    long unpark(String spot, long nowMin) {
        String plate = spotToPlate.remove(spot);
        long mins = nowMin - entryTime.remove(plate);
        long fee = 20 + Math.max(0, (mins - 60 + 59) / 60) * 10;  // pricing rule baked in
        System.out.println("Charging card for " + plate + ": " + fee);   // payment
        System.out.println("SMS to owner of " + plate + ": fee " + fee); // notification again
        freeSpots.add(spot);
        return fee;
    }
    // ...in a real round this class also grows report(), audit(), exportCsv(), adminLogin()...
interface SpotAllocator { Optional<String> allocate(); void release(String spot); }
interface PricingPolicy { long fee(long minutes); }
interface Notifier { void send(String plate, String msg); }
interface PaymentGateway { void charge(String plate, long amount); }

record Ticket(String plate, String spot, long entryMin) {}

static class FirstFreeAllocator implements SpotAllocator {
    private final Deque<String> free = new ArrayDeque<>();
    FirstFreeAllocator(List<String> spots) { free.addAll(spots); }
    public Optional<String> allocate() { return Optional.ofNullable(free.pollFirst()); }
    public void release(String spot) { free.addLast(spot); }
}

static class HourlyPricing implements PricingPolicy {
    public long fee(long minutes) { return 20 + Math.max(0, (minutes - 60 + 59) / 60) * 10; }
}

/** Thin coordinator: it only orders the steps; every decision lives in a collaborator. */
static class ParkingService {
    private final SpotAllocator allocator; private final PricingPolicy pricing;
    private final Notifier notifier; private final PaymentGateway payments;
    private final Map<String, Ticket> active = new HashMap<>();

    ParkingService(SpotAllocator a, PricingPolicy p, Notifier n, PaymentGateway g) {
        allocator = a; pricing = p; notifier = n; payments = g;
    }
    Ticket park(String plate, long nowMin) {
        String spot = allocator.allocate().orElseThrow(() -> new IllegalStateException("full"));
        Ticket t = new Ticket(plate, spot, nowMin);
        active.put(spot, t);
        notifier.send(plate, "parked at " + spot);
        return t;
    }
    long unpark(String spot, long nowMin) {
        Ticket t = active.remove(spot);
        if (t == null) throw new IllegalArgumentException("no car at " + spot);
        long fee = pricing.fee(nowMin - t.entryMin());
        payments.charge(t.plate(), fee);
        notifier.send(t.plate(), "fee " + fee);
        allocator.release(spot);
        return fee;
    }
}

Both versions print the same fee for the same input; run java GodObject.java in lld-code/lld-prin-antipatterns/. The difference shows up only when a requirement changes: in the "after" version a weekend tariff is a new PricingPolicy, and ParkingService is not opened.

Do not overshoot. Splitting every method into its own class gives "ravioli code": dozens of tiny classes nobody can follow, and an anemic model (next section). Split where a different reason to change exists, not everywhere.

From your world

struct net_device is huge, yet it is not a god object in the bad sense: its behaviour is pushed out to net_device_ops and ethtool_ops tables that each driver fills in. The god-object version is the driver whose single .c file parses ioctls, owns the DMA rings, talks to the PHY and prints statistics through one giant switch. Same cure: split by job, connect through function tables (interfaces).
