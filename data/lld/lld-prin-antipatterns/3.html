Anemic domain model: data here, rules over there

Martin Fowler named the anemic domain model in 2003: domain objects that look like real objects (they have the right names and fields) but hold no behaviour, while "service" classes contain all the rules. It feels clean, because the entities are tiny. It is really procedural code dressed up as objects, and it loses the main benefit of objects: an object can protect its own invariants (rules that must always be true, like "balance is never negative").

static class AnemicAccount {
    private long balance;
    private boolean frozen;
    public long getBalance() { return balance; }
    public void setBalance(long b) { balance = b; }      // anyone can set anything
    public boolean isFrozen() { return frozen; }
    public void setFrozen(boolean f) { frozen = f; }
}

static class TransferService {          // every caller must remember every rule
    void transfer(AnemicAccount from, AnemicAccount to, long amt) {
        if (from.isFrozen()) throw new IllegalStateException("frozen");
        if (amt <= 0 || from.getBalance() < amt) throw new IllegalArgumentException("bad amount");
        from.setBalance(from.getBalance() - amt);
        to.setBalance(to.getBalance() + amt);
    }
}
static final class Account {
    private long balance;
    private boolean frozen;
    Account(long opening) { if (opening < 0) throw new IllegalArgumentException(); balance = opening; }
    long balance() { return balance; }
    void freeze() { frozen = true; }
    void withdraw(long amt) {
        requireActive();
        if (amt <= 0) throw new IllegalArgumentException("amount must be > 0");
        if (balance < amt) throw new IllegalStateException("insufficient funds");
        balance -= amt;
    }
    void deposit(long amt) {
        requireActive();
        if (amt <= 0) throw new IllegalArgumentException("amount must be > 0");
        balance += amt;
    }
    private void requireActive() { if (frozen) throw new IllegalStateException("frozen"); }
}

/** A service still exists, but only for work that spans several objects. */
static class Transfers {
    void transfer(Account from, Account to, long amt) { from.withdraw(amt); to.deposit(amt); }
}
"""Anemic vs rich model in Python 3.11. Run: python anemic_vs_rich.py"""
from dataclasses import dataclass


@dataclass
class AnemicAccount:          # BEFORE: public fields, rules live in some service
    balance: int = 0
    frozen: bool = False


class Account:                # AFTER: behaviour sits next to the data it protects
    def __init__(self, opening: int) -> None:
        if opening < 0:
            raise ValueError("opening balance must be >= 0")
        self._balance = opening
        self._frozen = False

    @property
    def balance(self) -> int:
        return self._balance

    def freeze(self) -> None:
        self._frozen = True

    def withdraw(self, amt: int) -> None:
        self._require_active()
        if amt <= 0:
            raise ValueError("amount must be > 0")
        if self._balance < amt:
            raise RuntimeError("insufficient funds")
        self._balance -= amt

    def deposit(self, amt: int) -> None:
        self._require_active()
        if amt <= 0:
            raise ValueError("amount must be > 0")
        self._balance += amt

    def _require_active(self) -> None:
        if self._frozen:
            raise RuntimeError("frozen")


def transfer(src: Account, dst: Account, amt: int) -> None:
    src.withdraw(amt)
    dst.deposit(amt)


if __name__ == "__main__":
    bad = AnemicAccount(balance=100)
    bad.balance = -5000                     # nothing stops it
    print("anemic:", bad.balance)
    x, y = Account(100), Account(0)
    transfer(x, y, 40)
    print("rich:", x.balance, y.balance)
    try:
        x.withdraw(1000)
    except RuntimeError as e:
        print("rich refuses:", e)

When data-only classes are the right answer

  • DTOs and events crossing a boundary (API payloads, Kafka messages, DB rows).
  • Value records such as Ticket(plate, spot, entryMin): immutable, no rules beyond construction.
  • CRUD screens with no business rules worth protecting.

The interview rule of thumb: if an entity has a rule, the rule lives in the entity. seat.hold(userId, until) beats seat.setStatus(SeatStatus.HELD); order.cancel() beats a service that checks the state and calls three setters. A service still coordinates work that spans several entities - a transfer touches two accounts, a booking locks seats and calls a payment gateway. This is Tell, Don't Ask: tell the object what you want, do not ask for its data and decide for it.

From your world

C structs are anemic by nature, and the kernel fights that with helper functions that guard invariants. Nobody writes skb->tail += len by hand; you call skb_put(), which extends the data area and panics if it would run past the end of the buffer. Opaque structs plus accessor functions are C's way of saying "the rule lives next to the data".
