Singleton abuse: the global variable with a pattern name

The Singleton pattern guarantees one instance and gives a global access point. Interviewers ask it often - a Goldman Sachs LLD round asked for it and then for thread safety (2025-05), Walmart asked about double-checked locking and volatile (2024-12) and about serialization safety (2024-10). So learn it. The anti-pattern is not the pattern; it is using the global access point as a shortcut so that any class can reach any service.

Four costs of getInstance() everywhere

  1. Hidden dependencies. order(sku) looks pure, but it reads and writes a database. The constructor and signature lie about what the class needs.
  2. Test pollution. State left by one test leaks into the next; you cannot hand the class a fake.
  3. Contention. One shared object with one lock becomes the hot spot when you add threads.
  4. "Only one" stops being true. Two parking lots, two tenants, a staging and a live gateway. Now every call site must change.
static final class Db {                       // global, mutable, hard-wired
    private static final Db INSTANCE = new Db();
    private final Map<String, Integer> stock = new HashMap<>(Map.of("pen", 2));
    private Db() {}
    static Db get() { return INSTANCE; }
    int stock(String sku) { return stock.getOrDefault(sku, 0); }
    void setStock(String sku, int n) { stock.put(sku, n); }
}

static class OrderServiceBefore {
    boolean order(String sku) {               // the signature hides that it touches a DB
        int n = Db.get().stock(sku);
        if (n == 0) return false;
        Db.get().setStock(sku, n - 1);
        return true;
    }
}
interface Inventory { int stock(String sku); void setStock(String sku, int n); }

static class InMemoryInventory implements Inventory {
    private final Map<String, Integer> stock = new HashMap<>();
    InMemoryInventory(Map<String, Integer> seed) { stock.putAll(seed); }
    public int stock(String sku) { return stock.getOrDefault(sku, 0); }
    public void setStock(String sku, int n) { stock.put(sku, n); }
}

static class OrderService {
    private final Inventory inventory;        // the dependency is visible in the constructor
    OrderService(Inventory inventory) { this.inventory = Objects.requireNonNull(inventory); }
    boolean order(String sku) {
        int n = inventory.stock(sku);
        if (n == 0) return false;
        inventory.setStock(sku, n - 1);
        return true;
    }
}

The fixed version still shares a single inventory in production; the difference is that main decides (the composition root, the one place where objects are created and wired), not the class. See Dependency Inversion for the full technique (constructor injection, DIP vs DI vs IoC).

From your world

Before network namespaces, a lot of networking code reached for global state. Making the stack namespace-aware meant threading a struct net * through the APIs so each call says which namespace it works on, with init_net left as the initial one. That is singleton abuse being paid back: explicit context passed in beats a global you reach out to.
