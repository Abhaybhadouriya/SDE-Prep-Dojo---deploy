Interview questions on anti-patterns

More principle questions, with fix-this-code drills, are on Design Principles Interview Questions.

Your machine-coding feedback says "SRP and separation of concerns not followed". What did the grader probably see, and how do you avoid it next time?

Almost always a god service: one XyzService or XyzManager that parses input, validates, stores in maps, applies pricing, sends notifications and prints output. A real Flipkart feedback note said exactly this, plus "modular but not extensible" (Flipkart SDE-2, 2023-04); a Razorpay one said "not modular, not extensible" (Razorpay SSE, 2025-06).

Fix in the round: list the reasons to change (pricing, allocation, storage, notification), give each its own class or interface, and keep one thin coordinator that only orders the calls. Keep entities rich (they protect their own state) and keep the driver/main separate from the service.

How to answer

Name the anti-pattern ("god object"), show you can see the clusters, and say what you would extract first. Do not promise ten classes; promise the two or three seams where requirements will actually change.

Likely follow-ups
  • How do you know you have split too far?
  • Where does validation live: entity, service or controller?
  • Which seam would you add first if pricing rules change weekly?
You just wrote a thread-safe Singleton. Now: when is Singleton an anti-pattern?

Singleton is asked a lot (a Goldman Sachs LLD round asked for it, then for thread safety, 2025-05; Walmart asked for double-checked locking and volatile, 2024-12, and for serialization safety, 2024-10). It becomes an anti-pattern when it is used as a convenient global:

  • the dependency is hidden inside method bodies (Db.get()), so the signature lies;
  • tests share mutable state and cannot swap in a fake;
  • it becomes a lock hot spot under concurrency;
  • "there is only one" turns out false (two parking lots, multi-tenant, per-namespace).

Keep "one instance" as a decision of the composition root and pass the object in through constructors. If the class itself must enforce one instance (a hardware register block, a process-wide config), still depend on an interface.

How to answer

First show you can write it correctly (holder idiom or enum in Java), then show judgement: "I would not make ParkingLot a Singleton; main creates one and injects it."

Likely follow-ups
  • Enum singleton vs holder idiom vs double-checked locking?
  • How does a DI container give you singletons without the pattern?
  • How do you reset a singleton between tests?
Explain the "midlayer mistake" and how it shows up in object-oriented code.

From the Linux kernel (Neil Brown, LWN, 2009): a midlayer sits between a generic top layer and the specific drivers and does "common" work for all of them. Because it cannot foresee every driver's needs, it grows special cases, it hides its own data inside the primary structures, and drivers cannot opt out. The advice is a very thin top layer that calls drivers directly, plus a library of helpers drivers may call, augment or ignore.

In OO code the same shape is a mandatory base class or "engine" that runs the whole flow and calls hooks, plus flags like if (vehicle.isElectric()) for the cases it did not foresee. The library version is composition: small helpers or strategies that each class uses as it needs.

How to answer

Tell it as a story with one picture (top, middle, drivers) and end with the OO translation: prefer helpers you call over a framework that calls you, unless the flow is truly fixed.

Likely follow-ups
  • Is Template Method then always bad?
  • Where in the kernel do you still see a midlayer-like design?
A candidate modelled four CPU registers as classes RegisterA, RegisterB, RegisterC and RegisterD. What is wrong?

That is "class per instance": the four registers differ only in data (their name and value), not in behaviour. One Register class with four instances in a Map<String, Register> is the right model; the switch statement that picks a register disappears. The real post (CRED machine coding, 2023-08) shows the candidate asking exactly this after the round; the stated rubric was working code, enough unit tests, extensibility and OOP design principles.

How to answer

Ask "do these differ in behaviour or only in data?" Behaviour differences justify subclasses or strategies; data differences are instances or enum values.

Likely follow-ups
  • Then how do you model the commands (SET, MOVE, INC)?
  • When would a subclass per register be justified?
