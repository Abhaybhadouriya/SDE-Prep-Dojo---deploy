Concurrency and thread safety

A board game is turn-based, so the honest first answer is: one game is single-threaded by design, and that is a feature. Turns are strictly ordered, so there is nothing to parallelise inside a game. Threads only appear when the game leaves one laptop: many games on one server, players sending rolls from their phones, or a turn timer running on its own thread. Say this, then answer the follow-ups:

  1. On a server, a flaky phone sends Asha's roll and then a retry. Both requests check "is it Asha's turn?" before either has moved her piece, so both are applied.
  2. The guard: requests for one game run under that game's lock (or one queue per game), and each carries the turn number it is meant for. playTurn() applies a request only if its turn number matches.
  3. The retry arrives for turn 7, but the game is at turn 8, so it is ignored. Retrying is now harmless (idempotent), and turns stay in order.

Level check. For SDE-1, a single-game, single-threaded design is a complete answer. SDE-2 candidates should be ready for the follow-ups below. New to Java threads? Read Concurrency basics and Locks first.

  • "Many games at once on a server?" Each Game owns its own state and shares only the immutable Board. Run each game on one thread (or one actor / one event-loop task). No locks are needed because nothing mutable is shared. Board is safe to share because its map is copied into an unmodifiable map at build time.
  • "Players send roll requests from their phones." Now requests arrive concurrently. Put them into a per-game queue and let one worker apply them in order, or guard playTurn() with a per-game lock. Reject a request whose player is not at the head of turnOrder ("not your turn"). Add a turn number to each request so a retried request is ignored (idempotency).
  • "Random numbers from many threads?" java.util.Random is thread-safe but contended; give each game its own instance (as we do) or use ThreadLocalRandom. For a real-money game you would use SecureRandom and log every roll for audit.
  • Listeners run on the game's thread. A slow listener (a network push) slows the game, so hand events to a queue and deliver them asynchronously.

From your world

"One writer per object, many readers of immutable data" is the per-CPU pattern: each CPU owns its run queue and nobody locks it from outside, while read-mostly shared tables are published once and only read. The immutable Board is like a routing table snapshot that readers use without a lock.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.
