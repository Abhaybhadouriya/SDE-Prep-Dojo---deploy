Relationships and patterns used (and why)

PatternWhereWhy here
SpecificationSpec<Vehicle>, VehicleSpecs.ofType(..).and(minSeats(5))Search filters multiply (type, seats, branch, price, fuel, transmission). One small rule per filter, combined at the call site, instead of a search(type, seats, branch, maxPrice, ...) method with ten nullable parameters.
StrategyPricingStrategy: HourlyPricing, DailyCapPricingPricing rules change by city, season and product. The service only calls price(v, slot).
DecoratorWeekendSurcharge(inner, 20)A surcharge applies on top of whatever base rule is in use. Stacking decorators (weekend, then coupon) avoids a class per combination.
FacadeRentalServiceOne entry point for the driver, the tests and (later) a REST controller.
State machine (enum)ReservationStatus + guarded transitionsFour states and four transitions: an enum with guards is enough. Switch to the State pattern only if each state grows its own behaviour.
Value objectsTimeSlot, Quote, VehicleImmutable, validated on creation, so invalid ranges never reach the booking code.

From your world

Specification is a BPF filter for objects. A tcpdump expression like tcp and port 443 and not host 10.0.0.1 is built from small predicates joined with and / or / not, compiled once and run against every packet. atBranch("KOR").and(minSeats(5)) is the same idea run against every vehicle. And a pricing decorator wrapping a base strategy is a stacked netfilter target: each layer adjusts the verdict of the one beneath.
