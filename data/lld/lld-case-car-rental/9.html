Concurrency and thread safety

The race is check-then-act: "is it free?" and "insert my booking" must happen as one atomic step for that car. Here is the broken version almost everyone writes first:

  1. Two customers book the same car for overlapping times. Each checks the car's reservations, finds no overlap, and inserts: check-then-act again.
  2. The guard: book() takes the lock for that one car (locks.computeIfAbsent(id, ...)) and does the overlap check and the insert inside it. The intervals are half-open, so 10:00-12:00 and 12:00-14:00 do not clash.
  3. B gets the lock after A, sees the overlap with 10:00-12:00 and fails with VehicleUnavailableException. Bookings for other cars use other locks and never wait.
// BROKEN: two threads can both pass the check before either inserts
Reservation book(String user, String vehicleId, TimeSlot slot) {
    if (!isFree(vehicleId, slot)) throw new VehicleUnavailableException(vehicleId);
    Reservation r = new Reservation(...);          // thread B is here too
    byVehicle.get(vehicleId).add(r);               // and ArrayList.add is not thread-safe either
    return r;
}

In PostgreSQL the database can enforce "no overlap per vehicle" for you with an exclusion constraint, which is the cleanest answer to Adobe's schema follow-up:

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE reservation (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  vehicle_id  TEXT   NOT NULL REFERENCES vehicle(id),
  period      TSRANGE NOT NULL,                 -- half-open by default: [start, end)
  status      TEXT   NOT NULL CHECK (status IN ('CONFIRMED','PICKED_UP','RETURNED','CANCELLED')),
  price       BIGINT NOT NULL,
  EXCLUDE USING gist (vehicle_id WITH =, period WITH &&)
    WHERE (status IN ('CONFIRMED','PICKED_UP'))
);

-- available vehicles at a branch for a slot
SELECT v.* FROM vehicle v
WHERE v.branch_id = 'KOR' AND v.seats >= 5
  AND NOT EXISTS (SELECT 1 FROM reservation r
                  WHERE r.vehicle_id = v.id AND r.status IN ('CONFIRMED','PICKED_UP')
                    AND r.period && tsrange('2026-12-02 10:00', '2026-12-03 10:00'));

Without a range type, use SELECT ... FROM vehicle WHERE id = ? FOR UPDATE to lock the car's row, run the overlap check, insert, commit. That is our per-vehicle lock, moved into the database.

From your world

Our code keeps one lock per car: locks.computeIfAbsent(id, ...) creates it on first use, so the lock table grows with the fleet. A C++ port would use a std::unordered_map<std::string, std::mutex> guarded by one small mutex for lookups, then std::lock_guard<std::mutex> g(locks[id]); around check and insert. The kernel's futex hash is a different design, lock striping: a fixed array of N buckets, each with its own spinlock, indexed by a hash of the key (here it would be stripes[hash(id) % N]). Striping gives bounded memory and no per-key allocation, at the price of occasional false sharing: two unrelated cars that hash to the same stripe wait for each other. Per-key locks never contend falsely but cost one object per car. Both are fine for a rental fleet; say which one you chose and why.

  • Reads: search takes each car's lock briefly to read its list. For a read-heavy system, use a ReadWriteLock per car or copy-on-write lists (see locks).
  • Deadlock: one booking takes one lock, so there is no lock ordering problem. A "book two cars together" feature would need locks in a fixed order (sorted by id). See deadlock.
  • Idempotency: a client retry after a timeout should not create a second booking. Accept an idempotency key with book() and return the earlier reservation for a repeated key.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReadWriteLock = rwlock_t / rw_semaphore: many readers or one writer.
  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
