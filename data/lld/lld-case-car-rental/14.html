Interview follow-ups (Q&A)

Why not keep an isAvailable flag on Vehicle?

Availability depends on a time range. A car can be free today and booked on Saturday, so a single flag cannot answer the question users ask. It also goes stale: a booking that ends at 18:00 would need a timer to flip the flag. Derive availability from the active reservations that overlap the requested slot.

How to answer

Give the Saturday example; then say "store facts, derive answers".

Likely follow-ups
  • Is the scan per car fast enough? (Yes for tens of bookings per car; use a sorted map / interval tree for thousands.)
Write the overlap condition for two time ranges.

For half-open ranges [s1, e1) and [s2, e2): they overlap if and only if s1 < e2 && s2 < e1. This one expression covers partial overlap on either side and full containment, and it allows back-to-back bookings.

How to answer

Draw two bars, state half-open, then write the expression. Do not enumerate four cases with ifs.

Likely follow-ups
  • How do you add a 30-minute cleaning buffer?
Two users book the same car at the same time. Walk me through what happens in your code.

Both threads call book(). Both look up the same lock object for that vehicle (computeIfAbsent is atomic, so they get the same one). One enters the synchronized block, scans the list, finds no overlap, inserts and leaves. The second then enters, sees the new reservation, and throws VehicleUnavailableException. Bookings of other cars proceed in parallel. My test races 16 threads 20 times and asserts one winner.

How to answer

Name the race (check-then-act), the lock scope (one car), and the test that proves it.

Likely follow-ups
  • What if you run 10 servers? (Database constraint or row lock.)
  • Optimistic instead of pessimistic?
Design the schema and write the query for available cars.

Tables: branch, vehicle(id, branch_id, type, seats, hourly_rate, daily_rate), reservation(id, user_id, vehicle_id, start_ts, end_ts, status, price) with an index on (vehicle_id, start_ts). Available cars: vehicles at the branch matching filters where NOT EXISTS an active reservation with start_ts < :end AND :start < end_ts. In PostgreSQL, an exclusion constraint on (vehicle_id, period) makes double booking impossible at the database level.

How to answer

Same overlap rule as the code, now in SQL. Mention the index.

Likely follow-ups
  • Revenue per branch last month? (GROUP BY branch over RETURNED reservations.)
Search has ten optional filters. How do you keep the method signature sane?

Use the Specification pattern: each filter is a small object with isSatisfiedBy(vehicle), combined with and / or / not. search(spec, slot) takes one combined spec. A new filter is a new spec; the search method never changes. If the API layer receives query parameters, a small builder turns each present parameter into a spec.

How to answer

Contrast with the ten-nullable-parameters method; mention OCP.

Likely follow-ups
  • How would a spec become a SQL WHERE clause? (Each spec can also render a predicate fragment.)
How do you add weekend pricing and a coupon without touching existing pricing classes?

Decorators over the PricingStrategy interface: new CouponDiscount(new WeekendSurcharge(new DailyCapPricing(), 20), "FIRST50"). Each wraps another strategy and adjusts its result. The order is a business decision (discount before or after surcharge), so make it explicit in one factory.

How to answer

Strategy for the base rule, Decorator for adjustments; say who decides the order.

Likely follow-ups
  • Should the price be recomputed at return time? (No: fix it at booking; only the late part is priced at return.)
The user must pay before the booking is confirmed. Payment takes up to a minute. What changes?

Add a HELD status with an expiry. hold() runs the same atomic overlap check and inserts a HELD reservation that counts as active. Payment success moves it to CONFIRMED; failure or timeout moves it to EXPIRED, freeing the car. A scheduled sweeper (or lazy expiry on read) clears old holds. The lock is never held during the payment call.

How to answer

Never hold a lock across a network call; use a state with a deadline instead.

Likely follow-ups
  • Payment succeeds after the hold expired and someone else booked. Now what? (Refund automatically; make that path explicit.)
The previous renter returns 2 hours late and the next customer is waiting. How does the system handle it?

The late fee is computed by pricing the extra time with the same strategy. Operationally, a job watches PICKED_UP reservations past their end; when the next booking for that car starts within a threshold, it raises an event. Policy options: offer the next customer a similar car (an allocation strategy over search results), or delay with compensation. The design point is that "car is late" is an event other components react to (Observer), not logic inside book().

How to answer

Fee first, then event, then policy options.

Likely follow-ups
  • Should new bookings keep a default buffer after every trip?
A car has thousands of future reservations. The overlap scan is slow. What do you do?

Keep each car's active reservations in a TreeMap<start, Reservation>. For a new slot, only the floor entry (latest start before the new end) can overlap if bookings never overlap each other, so the check is O(log n): look at floorEntry(newEnd - epsilon) and test its end against the new start. For general interval queries, an interval tree. In the database, the GiST index behind the exclusion constraint does this.

How to answer

Use the invariant "active bookings never overlap" to reduce the check to one neighbour.

Likely follow-ups
  • Prove that one neighbour is enough.
Pessimistic lock or optimistic concurrency for bookings?

Optimistic (version check, retry on conflict) wins when conflicts are rare and you want no blocking: most cars are not contested. Pessimistic (lock, check, insert) wins when one item is hot (a popular car on a holiday) because retries would storm. In the round, pessimistic per-car locking is simpler to get right and to explain; mention optimistic as the scale-out option and the database constraint as the final guard.

How to answer

Depends on contention; give both and pick one with a reason.

Likely follow-ups
  • How would you implement the version check in SQL? (UPDATE vehicle SET version = version + 1 WHERE id = ? AND version = ?.)
