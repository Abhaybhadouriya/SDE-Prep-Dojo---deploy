Core flows

Search

  1. Filter stream all vehicles through the Spec (cheap, no locks: vehicles are immutable).
  2. Check availability for each match, look at that vehicle's active reservations for an overlap with the requested slot.
  3. Price ask the pricing strategy for this vehicle and slot, so the quote is what the user will pay.
  4. Sort cheapest first, ties broken by id so output is stable for tests.

Search results can be stale the moment they are returned: another user may book the car a second later. That is fine, as long as book() checks again. Search is advisory; book is authoritative.

Book (two users at once)

  1. Asha and Ravi both ask for KA02 for Saturday 9 to 18, on two request threads, at the same instant.
  2. Asha's thread gets into synchronized (lockFor("KA02")) first.
  3. Ravi's thread tries the same lock and blocks. Bookings for other cars are not blocked at all.
  4. Holding the lock, Asha's thread scans KA02's reservations, finds no active overlap, and appends R1.
  5. Asha's thread leaves the synchronized block; the lock is released and Asha gets R1.
  6. Ravi's thread now enters and scans the same list. It sees R1, which overlaps.
  7. Ravi gets VehicleUnavailableException with the clashing reservation. The demo races 8 threads, and the tests race 16 threads 20 times: exactly one booking succeeds every time.

Pick up and return

Amazon's version of the question focuses here: "write the code that hands a reserved car to the customer". pickUp(id) moves CONFIRMED to PICKED_UP (in real life after licence and payment checks). returnVehicle(id, at) computes a late fee by pricing the extra time [slot.end, returnedAt) with the same strategy, then moves to RETURNED. Re-using the strategy means a weekend late fee automatically includes the weekend surcharge.
