Concurrency and thread safety

Buttons are pressed on many threads; cars move on a clock. The tempting design is a lock per car. It breaks on dispatch: to choose a car, the controller must read every car's floor, direction and stops at the same moment, so it would take every car's lock (in a fixed order, or deadlock), while each car's own thread holds its lock to move. That is a lot of locking for a decision that should be quick.

  1. If a button thread wrote into a car's stop set while the controller thread was iterating it to decide the next move, the iteration could fail or a stop could be lost.
  2. The guard: button threads never touch a car. submit() validates and puts an immutable HallCall into a LinkedBlockingQueue, which is thread-safe.
  3. Only the controller thread reads or writes car state: each tick() drains the queue, dispatches the calls and steps every car. One writer means no locks on the cars at all.

This design uses the single-writer rule instead:

  • Any thread may call submit(). It only validates (reads immutable fields: minFloor, maxFloor) and puts an immutable record into a LinkedBlockingQueue, which is thread-safe.
  • One controller thread calls tick(). It drains the queue with drainTo, runs the commands, retries unassigned calls and steps each car. It is the only code that reads or writes car state, so cars need no locks at all.
  • Listeners live in a CopyOnWriteArrayList, so a display can register while the controller is iterating. Listener callbacks run on the controller thread and must be quick; a slow display should hand off to its own queue.
  • Reads from outside (a status API asking "where is E2?") should not touch car fields from another thread. Publish a snapshot after each tick (an immutable record in a volatile field), or send a query command through the inbox.
// BROKEN alternative: button threads call the car directly
void press(int floor, Direction d) {
    Elevator e = dispatch.choose(elevators, new HallCall(floor, d)).get();  // reads cars while they move
    e.addHallCall(new HallCall(floor, d));     // TreeSet.add races with the car's own tick()
}
// Two presses can choose using stale positions, and two threads mutating one TreeSet can corrupt it.

The tests prove the queue design: 4 button threads submit 200 hall calls each while a controller thread ticks 50 times; afterwards runUntilIdle finishes the work and the test asserts exactly 800 onDispatch events and every car idle. Python does the same with queue.Queue and threading.Thread.

From your world

This is the top half / bottom half split. A NIC interrupt handler does the minimum (acknowledge, queue the packet, raise a softirq), and NAPI processing runs later in one context per queue that owns the ring. Here a button press is the interrupt, the inbox is the ring, and tick() is the softirq. The same idea is a workqueue drained by one kworker, or the Linux rule that only the owning CPU touches its per-CPU data. In C++ with threads, the only lock is a std::mutex held to push in submit and to swap the deque out in tick, never while running commands.

More: producer-consumer (the inbox is one) and locks.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • CopyOnWriteArrayList = an RCU-style list: readers walk a snapshot with no lock, writers copy the array and publish it; good for read-mostly listener sets.
  • BlockingQueue = a bounded producer-consumer ring with a mutex and two condition variables (a kfifo plus wait queues).
