Relationships and patterns used (and why)

PatternWhereWhy here
StateElevatorState: Idle, Moving, DoorsOpen, OutOfServiceWhat a tick means depends on the state. Each state is ten lines and decides its own next state, so adding "fire service" is one new class plus one transition, not edits across a big switch. The states hold no fields, so each is a stateless singleton shared by all cars (safe because there is nothing in it to share).
Strategy (in the car)MovementPolicy: LookPolicy, ScanPolicyThe turnaround rule is the whole difference between LOOK and SCAN. Pulling it out lets one test compare them on the same scenario (6 floors versus 14).
Strategy (across cars)DispatchStrategy: nearest car, direction-aware costBuildings tune dispatch (up-peak in the morning, zones, energy saving). The controller only calls choose(cars, call).
CommandHallCall, CarCall with execute(controller)A press becomes an object that can be queued, logged, replayed in a test, or retried later when no car is free. It also moves work from the button thread to the controller thread. In Java, Request is a sealed interface: only the two listed record types may implement it (a record is an immutable struct with equals and hash written for you), much like a tagged union in C whose tag can only take the listed values.
MediatorElevatorControllerWithout it, every button needs references to every car, and cars need to know about each other to avoid answering the same call. With it, every arrow goes through one object.
ObserverElevatorListener with default no-op methodsFloor displays, logs, metrics and the test passengers all react to the same events without the car knowing who they are.

State or Strategy? They have the same shape (an interface with swappable implementations); the real difference is intent. State models behaviour that changes with the object's internal condition (idle, moving, doors open): the same tick() means different things in each. Strategy is an interchangeable algorithm chosen by the client (LOOK or SCAN), and it does not switch itself. Who picks the next state is a separate choice: GoF allows either the context or the states themselves to define transitions. Here the states pick their successor (each tick() returns the next state), which is one of the two options, not the definition of the pattern. See pattern look-alikes.

From your world

ElevatorState is a struct of function pointers, one per state, like the per-state handlers in a TCP state machine where tcp_rcv_state_process() dispatches on sk->sk_state; making each state a separate ops table removes the switch. The two strategies are ops tables chosen at setup, like struct elevator_ops in the old block layer, where deadline, cfq and noop plugged into the same request queue. The listener list is a notifier chain (register_netdevice_notifier): the car calls every registered callback and does not care who they are.
