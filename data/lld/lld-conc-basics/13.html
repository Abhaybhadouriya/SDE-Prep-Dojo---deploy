In interviews

When the interviewer says "make it thread-safe", do not sprinkle synchronized on every method. Walk through it out loud:

  1. Find the shared mutable state. Point at the fields in your class diagram: "the spot map, the bookings map, the wallet balance".
  2. Find the invariants. "A seat is in at most one booking." "Balance never goes below zero." Invariants that span several fields need one lock around all of them.
  3. Find the compound actions. Every check-then-act and read-modify-write on that state. Those are your critical sections.
  4. Pick the cheapest tool. Confine or make immutable if you can; then an atomic or a concurrent collection method (computeIfAbsent, compareAndSet); then a lock, scoped as small as possible (per show, per spot, not one global lock).

Where this comes up on this site: parking lot (two cars, one spot), BookMyShow (seat locks), ride hailing (one driver, two riders), digital wallet (balance updates), rate limiter (counters), LRU cache (even get mutates), and singleton (lazy init).

Strong 30-second answer: "Thread safety has three parts. Atomicity: compound actions like check-then-act and count++ must not interleave, so I use a lock or an atomic. Visibility: one thread's write must be seen by others, which the Java memory model guarantees only through happens-before edges such as unlock-then-lock of the same monitor, volatile write-then-read, start and join. Ordering: without those edges, the compiler and CPU may reorder writes, which is why double-checked locking needs volatile. volatile gives visibility and ordering, never atomicity of ++."

Scenario: "Is this counter thread-safe?"

The interviewer shows class Hits { private volatile int n; void hit() { n++; } int get() { return n; } } and asks if it is safe because the field is volatile.
"Yes, volatile makes it thread-safe."
"No. volatile makes each read and write visible, but n++ is a read, an add and a write, so two threads can both read 41 and both write 42. Use AtomicInteger.incrementAndGet(), or LongAdder if it is a hot counter read rarely, or a synchronized method if hit() also updates other fields."
Follow-ups: when is volatile alone enough? Why might LongAdder beat AtomicLong under contention?
