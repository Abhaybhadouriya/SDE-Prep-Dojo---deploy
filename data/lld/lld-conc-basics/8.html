Happens-before: the rulebook

The Java Memory Model (JLS 17.4) does not talk about caches or registers. It defines a relation called happens-before between actions. The guarantee: if action X happens-before action Y, then X's effects are visible to Y, and X appears ordered before Y. If two conflicting accesses (one is a write) are not ordered by happens-before, you have a data race, and the JMM promises very little about what you read.

The rules you need for interviews:

  1. Program order. Each action in a thread happens-before every later action in the same thread.
  2. Monitor lock. An unlock of a monitor (leaving synchronized) happens-before every later lock of the same monitor. ReentrantLock gives the same guarantee.
  3. Volatile. A write to a volatile field happens-before every later read of that same field.
  4. Thread start. t.start() happens-before any action in the started thread.
  5. Thread join. All actions in a thread happen-before another thread returns from join() on it (this is why our counter demo can read the totals safely after the joins).
  6. Transitivity. If X hb Y and Y hb Z, then X hb Z. This is the rule that makes everything above useful.

The java.util.concurrent classes document their own happens-before edges, for example: putting an object into a BlockingQueue or ConcurrentHashMap happens-before taking it out in another thread, and actions before executor.submit(task) happen-before the task runs. That is why you can hand a freshly built, non-volatile object to another thread through a queue and it arrives complete.

Final fields have one more guarantee (JLS 17.5): if an object's constructor does not leak this, any thread that sees a reference to the object sees its final fields fully initialised, even without synchronisation. That is the foundation of immutable objects being safe to share.
