Visibility: the write that nobody sees

Races 1 and 2 are about steps interleaving. Visibility is stranger: there is no interleaving bug at all, yet one thread does not observe another thread's write, possibly forever. Run this:

static boolean stopPlain = false;          // ordinary field
static volatile boolean stopVolatile = false;

Thread w1 = new Thread(() -> { long n = 0; while (!stopPlain) n++; });
Thread w2 = new Thread(() -> { long n = 0; while (!stopVolatile) n++; });
// ... start both, sleep 500 ms, then:
stopPlain = true;
stopVolatile = true;
3) plain flag worker still running after 1 s: true
   volatile flag worker still running after 1 s: false

On our machine (OpenJDK 21, HotSpot) the plain-flag worker never stopped. Nothing in the language promises that outcome either way; the point is that it is allowed. Two layers can hide a write:

From your world

The kernel version of the worker loop is while (!dev->stop) cpu_relax();, and without READ_ONCE(dev->stop) the compiler is free to read stop once. READ_ONCE/WRITE_ONCE stop the compiler from tearing, merging or hoisting accesses, but on their own they do not order other memory accesses around them; for that you pair smp_store_release() with smp_load_acquire(), or use barriers. A Java volatile field gives roughly both at once: every access really happens, and a volatile write/read pair acts as a release/acquire pair (in fact volatile accesses are sequentially consistent, which is a bit stronger). Careful with the word, though: C's volatile is not Java's. In C it only stops the compiler from optimising accesses away, with no inter-thread ordering, which is why the kernel's "volatile considered harmful" document tells you not to use it for synchronisation.
