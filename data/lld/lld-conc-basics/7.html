Ordering: steps that swap places

Compilers and CPUs reorder independent memory operations to go faster. Inside one thread you can never tell (the result is as if the code ran in order). Another thread can tell. The classic shape is "prepare data, then raise a flag":

// Thread A (producer)              // Thread B (consumer)
config = loadConfig();              if (ready) {
ready = true;                           use(config);     // may see config == null!
                                    }

With plain fields, B may see ready == true but an old config: A's two writes were reordered, or B's two reads were. Even worse, a reference can become visible before the object's fields are initialised, so B sees a half-built object. That is exactly why naive double-checked locking is broken, and why a volatile on the instance field fixes it (details).

One detail interviewers like: the JLS (17.7) lets a non-volatile long or double write be split into two 32-bit halves ("word tearing"). Making the field volatile makes its reads and writes atomic.
