Interview Q&A

What is a race condition? Give the two most common kinds.

A race condition is a bug where the outcome depends on how threads happen to interleave. The two shapes are read-modify-write (count++, balance -= x: two threads read the same old value and one update is lost) and check-then-act (if (seatFree) book(): the check is stale by the time you act, so two threads book the same seat). Both are fixed by making the compound action atomic.

How to answer

Name both, give one line of code for each, then the fix for each (atomic/lock, and one critical section or an atomic method such as putIfAbsent).

Likely follow-ups
  • Race condition vs data race?
  • Where is the race in your parking-lot design?
What does volatile guarantee in Java? Does it make count++ safe?

Visibility and ordering: every read sees the latest write to that field, and a volatile write happens-before every later read of it, so writes made before the volatile write are visible to a thread after it reads the field. Reads and writes of volatile long/double are also atomic. It does not make compound actions atomic, so count++ on a volatile still loses updates; use AtomicInteger or a lock.

How to answer

"Visibility and ordering, yes; atomicity of compound actions, no", then the example where volatile is enough (a stop flag).

Likely follow-ups
  • Why does double-checked locking need volatile?
  • Is Java's volatile the same as C's?
Explain happens-before. Which actions create happens-before edges?

Happens-before is the Java memory model's ordering relation: if X happens-before Y, X's effects are visible to Y. Edges come from program order within a thread, unlocking a monitor before a later lock of the same monitor, a volatile write before a later read of the same field, Thread.start() before the new thread's actions, a thread's actions before another thread's successful join(), and transitivity. Library classes add more: a BlockingQueue.put happens-before the matching take, and work before executor.submit happens-before the task runs.

How to answer

Define it by its guarantee (visibility + order), list the rules, then draw the volatile-flag publication chain.

Likely follow-ups
  • Two threads lock different objects. Is there an edge? (No.)
A ConcurrentHashMap is thread-safe. Is if (!map.containsKey(k)) map.put(k, v) thread-safe?

No. Each call is atomic, but the pair is a check-then-act: two threads can both see "absent" and both put, and the second silently overwrites the first. Use the atomic compound methods: putIfAbsent, computeIfAbsent, compute or merge (for example map.merge(k, 1, Integer::sum) for counting).

How to answer

"Thread-safe parts do not make a thread-safe whole", then the right method.

Likely follow-ups
  • What must not happen inside a computeIfAbsent function? (Long work or updates to the same map.)
Why can a thread spin forever on a boolean flag that another thread set to true?

Without a happens-before edge between the write and the reads, the JMM does not require the reader ever to see the write. In practice the JIT sees that the loop body never changes the field, reads it once into a register and loops on the register. Declaring the flag volatile (or reading it under the same lock as the writer, or using AtomicBoolean) forces a real read each time and creates the edge. Our demo on OpenJDK 21 shows the plain-flag thread still running after the flag was set.

How to answer

Name both layers (compiler hoisting, CPU buffering), then the fix and why it works (happens-before).

Likely follow-ups
  • How would you stop a worker thread properly? (Interrupts, or a volatile flag checked in the loop.)
Python has a GIL. Do you still need locks?

Yes. The GIL makes single bytecodes indivisible, but x += 1 is several bytecodes, and a check-then-act that does I/O releases the GIL in the middle. Your invariants are your job: use threading.Lock.

How to answer

Show the bytecode split or the sleep-in-the-window example.

Likely follow-ups
  • Threads vs processes vs asyncio for CPU-bound work in Python?
How do you make a class thread-safe in an LLD round without making it slow?

Minimise shared mutable state first: confine per-request data, make value objects immutable. For what remains, guard each invariant with one lock and keep critical sections small. Prefer fine-grained locks (per show, per spot) over a global one, and atomic or concurrent-collection methods for single-variable updates. Document which lock guards which field.

How to answer

The three strategies (confine, immutable, synchronise), then granularity, then a concrete example from your design.

Likely follow-ups
  • What new risk do fine-grained locks introduce? (Deadlock: see deadlock.)
