Inside ConcurrentHashMap (Java 8+)

Java 7's version split the map into 16 segments, each its own lock. Java 8 rewrote it with a finer design, and that design is what interviewers expect:

  • Reads (get, containsKey) take no lock. They see the latest completed write to that key.
  • Insert into an empty bin is a single CAS. Insert into a busy bin locks only that bin's first node with synchronized.
  • A bin with 8 or more nodes becomes a red-black tree (when the table has at least 64 bins; smaller tables resize instead), so a flood of colliding keys costs O(log n), not O(n).
  • Size uses the LongAdder trick. size() is an estimate while writers run. Prefer mappingCount(), which returns a long.
  • No null keys or values. get(k) == null must mean "absent", with no ambiguity. Our demo: put(k, null) throws NullPointerException.
  • Iterators are weakly consistent. They never throw ConcurrentModificationException and may or may not show changes made after they were created.

compute, merge, computeIfAbsent: atomic per key

These methods run your function while holding that key's bin, so read-modify-write becomes one step. They are the answer to "make this map update thread-safe" in nearly every LLD round:

// 1. counting
counts.put(item, counts.getOrDefault(item, 0) + 1);       // lost updates

// 2. lazy per-key value
if (!followers.containsKey(user))                         // two threads both see "absent"
    followers.put(user, new HashSet<>());                 // second put replaces the first set
followers.get(user).add(f);                               // and HashSet itself is unsafe
// 1. counting: one atomic step per key
counts.merge(item, 1, Integer::sum);

// 2. lazy per-key value: built exactly once, and the set is concurrent too
followers.computeIfAbsent(user, k -> ConcurrentHashMap.newKeySet()).add(f);

// 3. conditional update: reserve stock only if enough is left
boolean[] ok = {false};
stock.computeIfPresent(item, (k, left) -> {
    if (left < qty) return left;          // refuse, unchanged
    ok[0] = true;
    return left - qty;
});

Our demo: merge reached 800,000 / 800,000, and computeIfAbsent built the follower set exactly once while 8 threads raced.

Rules for the function you pass: keep it short, and never touch other keys of the same map inside it. Other writers to that bin wait while it runs. Updating another key from inside can deadlock or, in recent JDKs, throw IllegalStateException: Recursive update. No I/O, no remote calls, no locks inside.

One atomic key is not a transaction across keys. "Move 5 units from warehouse A to warehouse B" touches two keys, and two separate compute calls can be seen half-done. For that you need a lock that covers both (taken in a fixed order to avoid deadlock), or one immutable value that holds both, swapped with CAS.
