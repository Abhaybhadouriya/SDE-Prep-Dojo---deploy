LongAdder and per-CPU counters

With AtomicLong, every increment from every core hits one cache line. The line has to move between cores for each write (the coherence protocol bounces it), so adding cores does not add throughput. LongAdder keeps a base value plus an array of padded cells. A thread that loses a CAS on the base is moved to a cell, chosen by a per-thread hash. Cells grow up to about the number of CPUs. sum() adds them all up.

On our 16-thread laptop, one run of 8 threads × 100,000 increments took about 95 ms with synchronized, 18 ms with AtomicLong and 8 ms with LongAdder (the next run gave 71 / 23 / 9, and the run captured in the Code section gave 53 / 17 / 9). Treat these as a rough sign of direction, not a benchmark. Use JMH for real measurements.

LongAdder.sum() is not an atomic snapshot: increments that happen while it runs may or may not be counted. That is fine for metrics. It is wrong for a sequence or ID generator, a "stock left" value you decide on, or a rate-limit check. Those need AtomicLong or a lock.

From your world

The kernel's percpu_counter is the same trade. percpu_counter_add() changes this CPU's local count and folds it into the shared count only when the local value passes a batch size. percpu_counter_read() is fast but approximate. percpu_counter_sum() walks every CPU for the exact value. Many network drivers keep per-CPU packet counters (pcpu_sw_netstats) that are summed only when someone runs ip -s link. A distributed version of this, sharded counters, appears in the Distributed Counter design.
