Interview Q&A

HashMap vs Hashtable vs synchronizedMap vs ConcurrentHashMap?

HashMap: not thread-safe at all. Hashtable and synchronizedMap: one lock for the whole map, so every call is serialised, iteration needs manual locking, and compound actions are still racy. ConcurrentHashMap: lock-free reads, CAS into empty bins, a lock per bin on collision, weakly consistent iterators, and atomic per-key compute/merge. It also forbids nulls.

How to answer

Give one line per map, then say "and none of them makes get followed by put atomic; use merge".

Likely follow-ups
  • Why no nulls in CHM? (A null from get must mean absent; you cannot check containsKey separately without a race.)
  • How did Java 7's CHM differ? (16 segments, each a ReentrantLock.)
What is CAS and how do you build an increment with it?

Compare-and-swap atomically replaces a value only if it still equals the expected value, and reports whether it did. An increment is a loop: read v, try CAS(v, v+1), retry on failure. It is lock-free: some thread always makes progress, and nobody blocks. Under heavy contention the retries and cache-line bouncing cost time, which is why LongAdder exists.

How to answer

Write the four-line loop, then name the hardware instruction (lock cmpxchg), then the downside (contention, ABA).

Likely follow-ups
  • Lock-free vs wait-free? (Lock-free: the system progresses. Wait-free: every thread finishes in bounded steps.)
Explain the ABA problem. Does it happen in Java?

CAS sees the same value and cannot know that it changed and came back. On a lock-free stack, a popped and freed node can be reused at the same address, so a stale CAS installs a dangling pointer. In Java, GC prevents reuse while you hold a reference, so allocating fresh nodes avoids it. It still happens with object pools or recycled numeric states. Fix with a version stamp (AtomicStampedReference, tagged pointers), or with safe memory reclamation (hazard pointers, epochs, RCU).

How to answer

Draw the three-step stack picture, then the two fixes.

Likely follow-ups
  • How does the kernel avoid it? (RCU grace periods: nothing is freed until every reader that could see it has finished.)
AtomicLong or LongAdder for a request counter? For an order ID?

Request counter: LongAdder. It is written by every request and read by a metrics scrape, and an approximate read is fine. Order ID: AtomicLong (incrementAndGet). Each value must be unique and exact at the moment it is taken, and LongAdder cannot hand out a value.

How to answer

"Write-heavy and read-rarely means LongAdder; a value you decide on means AtomicLong."

Likely follow-ups
  • IDs across many servers? (Snowflake-style IDs: Unique ID Generator.)
Two users order the last unit at the same time. Make placeOrder safe without a global lock.

Keep stock per item in a ConcurrentHashMap<ItemId, Integer> and reserve with computeIfPresent that refuses when stock is below the quantity, or keep an AtomicInteger per item and use a CAS loop. Only that item's bin is locked, so other items proceed in parallel. For a multi-item order, reserve items in sorted id order and roll back the reserved ones if a later item fails. With a database, the same idea is a conditional update (UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?) and a check of the affected row count.

How to answer

Name the granularity (per item, not per restaurant), show the atomic check-and-decrement, then cover multi-item orders and the DB version.

Likely follow-ups
  • Optimistic vs pessimistic? (CAS and conditional updates are optimistic; SELECT ... FOR UPDATE is pessimistic.)
When would you use CopyOnWriteArrayList?

When reads and iteration vastly outnumber writes and the list is small: observer listener lists, routing tables, plugin registries. Iteration needs no lock and sees a stable snapshot, so a listener can unsubscribe during dispatch. Every write copies the whole array, so it is wrong for frequently changing or large lists.

How to answer

Name the Observer use case and the O(n) write cost.

Likely follow-ups
  • Kernel analogue? (RCU-protected list: readers walk without locks, writers publish a new version.)
