CAS: compare-and-swap, the magic pen

CAS(address, expected, new) is one atomic hardware instruction: "if the value at address is still expected, store new and report success; otherwise change nothing and report failure". Java exposes it as compareAndSet on the atomic classes. To do any read-modify-write with it, you wrap it in a CAS loop: read, compute, try, and on failure re-read and try again.

  1. Two buyers want one unit each. Both threads read the current stock: 5.
  2. Both compute their new value: 4. With a plain int, both would now write 4 and one sale would vanish.
  3. T1's CAS runs first. The value is still 5, so it becomes 4. Success.
  4. T2's CAS says "expected 5", but the value is now 4. The hardware refuses and nothing is written.
  5. T2 loops: re-reads 4, computes 3, CAS succeeds. Both sales counted, no lock, nobody slept.
// Take n units only if enough are left: stock can never go below zero.
static boolean tryTake(AtomicInteger stock, int n) {
    while (true) {
        int cur = stock.get();                      // 1. read
        if (cur < n) return false;                  //    business rule, no write
        if (stock.compareAndSet(cur, cur - n))      // 2. try to publish
            return true;
        // 3. someone changed it between read and CAS: loop
    }
}

Our demo ran 800,000 attempts from 8 threads against 1,000 units: exactly 1,000 sold, 0 left, never negative. The JDK gives you ready-made loops: updateAndGet(f), accumulateAndGet(x, f), getAndIncrement(). The function you pass may run more than once under contention, so it must have no side effects.

Atomic does not mean "lock-free for free". incrementAndGet on HotSpot x86 compiles to a single lock xadd, with no retry loop. A CAS loop can retry many times under heavy contention. The trade: no thread ever sleeps holding something others need (no deadlock, no priority inversion), but a hot CAS target makes cores fight over one cache line.
