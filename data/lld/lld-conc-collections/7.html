Code review drill: a "thread-safe" rate limiter

A LeetCode Discuss post asked the community to check a fixed-window rate limiter that mixed a ConcurrentHashMap, an AtomicInteger and double-checked locking. Interviewers like handing you code of this shape. Here is our own version of the pattern. Find the bugs before reading on.

class Window { final AtomicInteger left = new AtomicInteger(); long start; }

boolean allow(String key) {
    Window w = windows.computeIfAbsent(key, k -> new Window());
    long now = clock.millis();
    if (now - w.start >= windowMs) {                  // (a)
        synchronized (w) {
            if (now - w.start >= windowMs) { w.start = now; w.left.set(limit); }
        }
    }
    return w.left.getAndDecrement() >= 0;             // (b)
}
  1. Off by one at (b). The counter starts at limit, and getAndDecrement() >= 0 passes for limit, limit-1, ..., 0. That is limit + 1 requests. Our demo, limit 1,000, let 1,001 through.
  2. A data race at (a). start is a plain field read outside the lock. Without volatile, another thread may see a stale value, so the fast path is not reliable.
  3. The two fields are not one unit. A thread can pass check (a) in the old window, get delayed, then decrement after another thread reset the window. The old request spends the new window's budget.
  4. Unbounded drift. Rejected calls keep decrementing, so a flood drives left toward Integer.MIN_VALUE.

The fix is the idea from this whole page: make the state one immutable value and replace it atomically per key.

record Window(long start, int used) {}

boolean allow(String key) {
    long now = clock.millis();
    boolean[] ok = {false};
    windows.compute(key, (k, w) -> {                  // atomic for this key
        if (w == null || now - w.start() >= windowMs) w = new Window(now, 0);
        ok[0] = w.used() < limit;
        return ok[0] ? new Window(w.start(), w.used() + 1) : w;
    });
    return ok[0];
}

The fixed version let exactly 1,000 through under the same 800,000-call race. A single synchronized block per window object would also be correct and simple. Say that too, and pick CAS only when profiling says the lock is hot. More rate limiters (token bucket, sliding window) are in the Distributed Rate Limiter design.
