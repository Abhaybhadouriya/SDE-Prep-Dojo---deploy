The ABA problem

CAS checks that the value is the same. It cannot tell whether the value changed and changed back. That matters when the value is a pointer that can be freed and reused. The classic victim is a lock-free stack (a Treiber stack: push and pop each CAS the top pointer):

In Java, garbage collection removes most of the danger: a node that T1 still references cannot be freed and reused, so a Treiber stack that always allocates new nodes is ABA-safe. ABA still bites when you recycle objects (a node pool), or when the value is a plain number that can return to an old value with a different meaning (version 5 → 6 → 5 after a rollback). The fix is to CAS a pair: value plus a counter that only goes up.

AtomicStampedReference<String> top = new AtomicStampedReference<>("A", 0);
int[] h = new int[1];
String seen = top.get(h);  int seenStamp = h[0];     // read value AND stamp
// ... another thread does A -> B -> A, the stamp goes 0 -> 1 -> 2 ...
top.compareAndSet(seen, "C", seenStamp, seenStamp + 1);   // false: stamp is 2, not 0

Our demo ran exactly this: the plain AtomicReference CAS succeeded after A → B → A, the stamped one failed. In C, the same trick packs a version into the spare bits of a 64-bit word, or uses a double-width CAS (cmpxchg16b) for pointer plus counter.
