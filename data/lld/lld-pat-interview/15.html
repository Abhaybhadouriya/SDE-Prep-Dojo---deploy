Why does double-checked locking in Java need the field to be volatile?

  1. So that two threads cannot enter the synchronized block together
  2. So that no thread can see the reference before the constructor's writes are visible
  3. So that the garbage collector does not free the instance
  4. It does not; synchronized is enough
Without volatile, publishing the reference can be reordered before the constructor's writes, and the unlocked first check can return a half-built object.

In which pattern do the objects themselves choose what the next behaviour object will be?

  1. Strategy
  2. Decorator
  3. State
  4. Template Method
States return or set the next state. In Strategy, the client chooses.

A wrapper serves repeated reads from a cache and refuses keys the user may not read. Which pattern is it?

  1. Proxy
  2. Decorator
  3. Adapter
  4. Facade
It controls access and may answer without calling the real object: Proxy.

Your converter must handle 6 formats, any to any. Going through one internal model, how many reader/writer pieces do you need?

  1. 30
  2. 36
  3. 6
  4. 12
One reader and one writer per format: 2N = 12, instead of N x (N-1) = 30 direct converters.

An interviewer asks if the database connection should be a singleton. The best short answer:

  1. Yes, one connection is fastest
  2. No: one connection pool, many connections, created at startup and injected
  3. Yes, but make getConnection() synchronized
  4. No, create a new connection per query
A single connection serialises all queries. The pool is the shared resource, and injection keeps it testable.

What separates Chain of Responsibility from Decorator?

  1. CoR uses inheritance, Decorator uses interfaces
  2. Decorator has many children per node
  3. Any CoR handler may stop the request; every decorator forwards it
  4. There is no difference
Both are chains of objects with one interface. Only in CoR may a link end the walk (like NF_DROP in netfilter).

An Amazon report's feedback was "over-designed". Which habit most directly prevents that?

  1. Add a pattern only for a change you can name in the requirements
  2. Use an interface for every class
  3. Make the main object a Singleton
  4. Draw the UML before asking questions
A pattern is a cost paid for an expected change. If you cannot name the change, skip the pattern.
