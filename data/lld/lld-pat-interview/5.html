Write a thread-safe singleton. Give me three ways and say which you would use.

Reported almost word for word at Nykaa SDE-2 (2026-04-04), WEX SDE-2 (2026-08-30) and Goldman Sachs (2025-05-08).

  1. Holder idiom (Bill Pugh). A private static nested class holds the instance. The JVM loads and initialises that class only on the first get(), and class initialisation is done once under a JVM lock. Lazy, thread-safe, no synchronized on the hot path. My default.
  2. Enum singleton. enum Config { INSTANCE; }. The JVM guarantees one instance and also defends against reflection and serialization. Best when the class does not need to extend another class.
  3. Double-checked locking with volatile. Check, lock, check again, create. Needed when creation takes run-time arguments. Without volatile it is broken (next question).
final class Config {
    private Config() { }
    private static final class Holder { static final Config INSTANCE = new Config(); }
    static Config get() { return Holder.INSTANCE; }
}

Our runnable file races 64 threads against both the holder and the DCL versions and counts distinct instances (always 1): see the code section.

How to answer

Write the holder version first (it is short and correct), name the other two, then say the honest part: "In a real service I would rather create one instance in main and inject it, because a global singleton makes tests share state." Interviewers often ask that next anyway.

Likely follow-ups
  • Why is plain synchronized getInstance() slow? (every call takes the lock, even after creation)
  • Eager vs lazy: when is eager fine? (cheap object, always used)
  • How do you reset it in a unit test?
Why does double-checked locking need volatile?

instance = new Registry() is not one step. It is: allocate memory, run the constructor, publish the reference. The compiler or CPU may reorder so the reference is published before the constructor finishes. A second thread does the first (unlocked) check, sees a non-null reference, skips the lock and uses a half-built object. volatile adds a happens-before edge: everything written before the volatile write (the constructor's fields) is visible to any thread that reads the volatile field. Since Java 5 (JSR-133) this makes DCL correct.

Asked at Tripjack SDE-1 as "optimise the singleton with synchronized and lazy loading" (2026-08-18).

From your world

This is the same bug as publishing a pointer to a struct in C before its fields are visible on another CPU. In the kernel you fix it with smp_store_release() on the writer and smp_load_acquire() on the reader, or with rcu_assign_pointer(). volatile in Java gives release/acquire semantics. (C's volatile does not; do not mix them up in the interview.)

How to answer

Name the three steps, name the reordering, name the fix and the Java version that made it work. Copy the field to a local variable so the fast path does one volatile read.

Likely follow-ups
  • Is DCL needed at all? (usually not: holder idiom)
  • What does final on fields guarantee? (safe publication of immutable objects)

Singleton vs a class with only static methods: what is the difference?

A static utility class has no instance: you cannot pass it as an argument, it cannot implement an interface, and you cannot swap it for a fake in a test. A singleton is a real object: it can implement an interface, be passed around, be lazily created, and hold state with a lifecycle. Use static methods for pure functions with no state (Math.max). Use one instance (singleton or injected) when there is state or when callers should depend on an interface.

Goldman Sachs asked "define a singleton class; what is its purpose?" (2025-05-27); the static comparison is the usual next line.

How to answer

Interface, polymorphism, testability, lazy init, lifecycle. Five words, one sentence each.

Likely follow-ups
  • Can a static class be mocked? (only with bytecode tricks; that is the point)
"You say you rarely write singletons, but you use Spring Boot. How is that possible?"

Reported at Walmart SE-III (2025-05-25). The answer: Spring's default bean scope is "singleton", but that means one instance per application context, created and injected by the container. It is not the GoF Singleton: the class has a normal public constructor, no static getInstance(), and a test can build a second instance with a fake dependency. You get the "only one" property without the global access point. That is exactly why people who use DI rarely hand-write singletons.

How to answer

Separate the two ideas: "one instance" (a lifecycle choice) and "global access through a static method" (the part that hurts tests). Spring gives the first without the second. Link: Dependency Injection.

Likely follow-ups
  • What other bean scopes exist? (prototype, request, session)
  • Is a singleton bean thread-safe? (only if it has no mutable state, or guards it)
Why and when do you need a Factory? Doesn't a Factory with a switch break Open/Closed?

Arcesium asked exactly this pair: Factory "why/when" with code, then OCP failure cases in a Factory and how to fix them (2025-09-11). Oracle Health's file exporter was also Factory-focused (2026-04-27).

Why: callers should depend on an interface (Exporter), not on new CsvExporter(). The factory is the one place that knows concrete classes, so adding a type touches one file instead of every caller.

OCP: yes, a switch inside the factory must be edited for each new type. That is usually acceptable: it is one small, obvious place. If types are added often (plugins, per-tenant formats), use a registry: a Map<String, Supplier<Exporter>> where each type registers itself, or Java's ServiceLoader. Then the factory never changes.

final class ExporterFactory {
    private static final Map<String, Supplier<Exporter>> REG = new ConcurrentHashMap<>();
    static void register(String fmt, Supplier<Exporter> s) { REG.put(fmt, s); }
    static Exporter create(String fmt) {
        Supplier<Exporter> s = REG.get(fmt);
        if (s == null) throw new IllegalArgumentException("unknown format " + fmt);
        return s.get();
    }
}
How to answer

Say "the switch moves the change into one place; a registry removes it." That shows you know OCP is a direction, not a law. See OCP and Simple Factory.

Likely follow-ups
  • Who calls register? (a static block, a module init, or main wiring)
  • How is this like a C table of function pointers indexed by type?

Write a Builder by hand (no Lombok). When is it better than a constructor?

Walmart SE-III: "write code for builder pattern", and "assume you have all dependencies" when the candidate mentioned Lombok (2025-05-25). Zomato asked a configurable pizza where Builder is one good answer (2025-09-19).

final class Pizza {
    private final String size, crust; private final List<String> toppings;
    private Pizza(Builder b) { size = b.size; crust = b.crust; toppings = List.copyOf(b.toppings); }
    static Builder builder(String size) { return new Builder(size); }
    static final class Builder {
        private final String size; private String crust = "thin"; private final List<String> toppings = new ArrayList<>();
        private Builder(String size) { this.size = Objects.requireNonNull(size); }
        Builder crust(String c) { crust = c; return this; }
        Builder topping(String t) { toppings.add(t); return this; }
        Pizza build() {
            if (toppings.size() > 5) throw new IllegalStateException("max 5 toppings");
            return new Pizza(this);
        }
    }
}

Better than a constructor when there are many optional fields (no "telescoping" constructors), when you want the result immutable, and when you must validate the whole object once in build().

How to answer

Required fields go in the builder's constructor, optional ones get fluent setters, build() validates and copies collections. Mention that the product has a private constructor. More on the Builder page.

Likely follow-ups
  • Builder vs Decorator for the pizza? (Builder if toppings are data; Decorator if each topping changes behaviour such as price rules)
  • Is the builder thread-safe? (no; it is a short-lived local)
When would you use Prototype instead of new?

When building an object from scratch is expensive or complicated, but copying a ready one is cheap: a game level template, a pre-configured request, a document with default styles. You keep a registry of prototypes and hand out copies. The trap is deep vs shallow copy: a shallow copy shares the inner lists, so changing one copy changes the template. In Java, prefer a copy constructor or a copy() method over Cloneable, which is famously awkward.

How to answer

Give one real case, then say the words "deep copy". That is the whole question. See Prototype.

Likely follow-ups
  • How does fork() relate? (copy-on-write prototype of a whole process)
Write a singleton in C++, then a ref-counted smart pointer.

Adobe MTS C++ round (2026-10-13): Singleton in about 15 minutes, then smart pointers and RAII.

C++11 and later: the Meyers singleton. A function-local static is initialised exactly once even under concurrent calls (the standard requires it), so no lock is needed. Delete copy and move so nobody can make a second one.

class Logger {
public:
    static Logger& get() { static Logger instance; return instance; }
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
private:
    Logger() = default;
};

The smart pointer: hold a raw pointer plus a shared counter; the copy constructor increments, the destructor decrements and deletes at zero, assignment does both (and checks self-assignment). The block above is the minimal shape to write on a whiteboard. Our compiled version (singleton.cpp, excerpted in the code section) adds a counter and log(), an exception-safe constructor (if allocating the counter throws, delete p, as shared_ptr does), move operations that leave the source empty, and a null-safe release.

From your world

The function-local static is a compiler-generated pthread_once(). The smart pointer is kref_get() / kref_put() with a release function, wrapped in a class so the destructor does the put for you. Saying "this is kref with RAII" lands well.

How to answer

Meyers first, deleted copy and move second, then the destruction-order caveat (statics are destroyed in reverse order at exit, so do not log from another static's destructor).

Likely follow-ups
  • Is the counter in your smart pointer thread-safe? (No. Make it std::atomic<int>: increment with fetch_add(1, std::memory_order_relaxed), and release with if (count->fetch_sub(1, std::memory_order_acq_rel) == 1) delete p; so the last owner sees every other owner's writes, the same ordering as refcount_dec_and_test().)
