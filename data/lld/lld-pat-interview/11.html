Scenario drills: the moments that go wrong

Scenario: you put six patterns into a chess game

45-minute LLD round, "design chess". You have Factory for pieces, Strategy for moves, Observer for the board view, Command for moves, Memento for undo and a Singleton game. The interviewer says: "This feels heavy." (Close to an Amazon SDE-2 report whose feedback was "over-designed", 2025-02-09.)

"These are all best practices, so it is good design." (Defends complexity with no requirement behind it.)

"You're right. The requirements are: legal moves, check and checkmate, two players. Polymorphic Piece.canMove() covers moves without a separate Strategy. I'll drop Observer and Memento since there is no UI or undo in scope, and create the Game in main instead of a Singleton. If you'd like undo later, Command is where I'd add it." Then redraw with five classes.

Likely follow-ups
  • Now add undo. (Now Command earns its place.)

Scenario: "Your vending machine is full of if-else"

You coded if (hasCoin) ... else if (soldOut) ... in every method. The interviewer asks if a design pattern could help (similar to a MakeMyTrip SDE-2 report, 2025-07-25).

"It works, so I don't think we need a pattern." (Misses the hint.)

"Yes, the State pattern. Each condition becomes a state class implementing insertCoin, select and dispense, and each returns the next state. The machine just delegates: state = state.insertCoin(this). Adding a 'maintenance' state is one new class instead of a new branch in four methods." Then refactor one method live.

Likely follow-ups
  • Two users press buttons at once? (one lock around each transition)

Scenario: fee rules change every month

Parking lot. The product manager adds a festival surcharge, then an EV discount, then a first-hour-free rule.

Add another if to calculateFee() each time, and a boolean flag per rule.

A FeeStrategy per base rule, plus Decorators for adjustments that stack (new EvDiscount(new FestivalSurcharge(hourly))), chosen by a small factory from config. The ticket only knows FeeStrategy. New rule = new class plus one config line; no existing code is edited.

Likely follow-ups
  • Order of adjustments matters (discount before or after surcharge)? (make the order explicit in config, and test it)

Scenario: "Write a singleton in five minutes. Now break it."

Java round. You wrote a lazy singleton with if (instance == null) instance = new X();. The interviewer asks what is wrong and how it can be broken (Visa and ServiceNow style, 2026-04-03).

"Make the method synchronized." (Correct but slow, and it answers only one of five attacks.)

"Two threads can both see null: use the holder idiom. Reflection can call the private constructor: throw if an instance exists, or use an enum. Deserialisation makes a copy: add readResolve, or use an enum. Clone: don't implement Cloneable. Two class loaders give two copies, so it is one per loader. The enum version fixes the first three for free." Then write the enum.

Likely follow-ups
  • Why do you avoid singletons in production code? (hidden global state, hard to test; inject one instance instead)

Scenario: Observer, then "make it Kafka"

You implemented an in-process Observer for task completion events. The interviewer now wants producers and consumers on Kafka (Salesforce SMTS style, 2026-03-02).

Rewrite every class to call the Kafka client directly.

"My domain code depends on an EventPublisher interface, so I add a KafkaEventPublisher that sends to a topic keyed by task id. Each listener becomes a consumer in its own group. Kafka is at-least-once, so consumers dedupe by event id. Ordering holds per task because of the key." No domain class changes.

Likely follow-ups
  • A consumer crashes mid-batch: what happens? (it re-reads from the last committed offset; idempotency saves you)

Scenario: the interviewer has a different pattern in mind

Logger machine coding. You chose Chain of Responsibility for log levels; the interviewer keeps steering toward a Facade with a Factory of appenders (a Razorpay SDE-2 report, 2024-03-05).

Argue for ten minutes that CoR is more elegant.

"Both work. CoR is nice if levels each need their own handling; a Facade with a Factory of appenders is simpler if the main change is new destinations (file, console, remote). Which change matters more for you?" Then build theirs cleanly, and keep the level filter as one method.

Likely follow-ups
  • Make logging async (a queue and a writer thread: Producer-Consumer)

Scenario: "Which pattern fits this?" and you have no idea

An unfamiliar prompt: a multi-format data library (XML, JSON, CSV in and out). Your mind goes blank on names (Microsoft-style, 2024-10-27).

Guess a pattern name and hope.

Reason out loud from "what varies": "The formats vary, and there will be more. If I convert each pair directly, that's N x (N-1) converters. If I go through one internal model, it's a reader and a writer per format, 2N. Each reader adapts a format to my model: that is Adapter, and picking one by name is a Factory." The names come out of the reasoning.

Likely follow-ups
  • Streaming huge files (event-based readers and writers)
