Q&A: behavioral patterns (Strategy, State, Observer, Command, Chain)

Deep dive on Strategy: a payment gateway choosing UPI, bank transfer or card at run time.

Walmart SE-III asked "which design patterns did you use recently", then this exact Strategy deep dive (2025-09-21). Walmart also wanted Strategy and Factory in a running message-delivery system (2024-08-19).

  • interface PaymentStrategy { PaymentResult pay(Order o, PaymentDetails d); } with UpiPayment, CardPayment, NetBankingPayment.
  • PaymentService holds a Map<PaymentMethod, PaymentStrategy> (filled by DI or a registry) and calls strategies.get(req.method()).pay(...). No if/else on method type.
  • Common steps (validate, idempotency key, audit log) live in the service, not repeated in each strategy. If the steps are fixed and only one varies, a Template Method base class is an option.
How to answer

Show the interface, the map, and one implementation. Then raise the real-world points yourself: idempotency key per request, timeouts and retries, a fallback strategy if one provider is down. That moves the talk from "knows the pattern" to "has built payments".

Likely follow-ups
  • Add wallets without touching the service (register a new strategy)
  • Choose the cheapest provider dynamically (a strategy that picks strategies: a router)
  • How do you test it? (fake strategy in the map)
Strategy vs State: the class diagrams are identical. What is the real difference?
  • Who switches: in Strategy the client (or config) picks once; in State the state objects decide the next state themselves, as events arrive.
  • Do they know each other: strategies are independent; states know their successors.
  • What it models: Strategy = how to do one job; State = what the object is right now, with its allowed transitions.

MakeMyTrip's vending-machine interviewer expected State and the candidate managed state another way (2025-07-25). Zomato's SDE-1 list had both (2026-10-24).

How to answer

"Same diagram, different owner of the switch." Then one example each: parking fee (Strategy), vending machine (State). Our runnable file puts both side by side.

Likely follow-ups
  • Can a state use a strategy? (yes: a "dispensing" state can use a pricing strategy)
  • Where do you store the transition table? (in states, or in one table if transitions are data)
Is an enum plus a switch good enough for a state machine, or must you use the State pattern?

An enum state plus a transition table is often the better answer for small machines: one place to read every transition, easy to print, easy to validate (Map<State, Map<Event, State>>). Switch to the State pattern when each state has a lot of distinct behaviour (several methods, each different per state), or when states will be added by other teams. Then a class per state keeps each one small and stops the "giant switch in every method" smell.

From your world

The Linux TCP stack keeps sk->sk_state as an enum and dispatches in tcp_rcv_state_process() with a switch: the table approach, chosen for speed and auditability. Per-protocol behaviour is pushed into ops tables instead. Both choices are defensible, and saying why is the answer.

How to answer

Do not argue with the interviewer's expectation. Say: "For four states with one action each I would start with an enum and a table; if each state grows its own behaviour I would move to State classes, like this", and sketch one state class. That shows both.

Likely follow-ups
  • How do you reject an invalid transition? (throw, or return the same state and log)
  • Make transitions thread-safe (one lock per machine; or CAS on an AtomicReference<State>)
Design notifications with Observer. Then: what can go wrong?

Kotak's bar raiser wanted Observer to notify followers about new posts (2026-02-04); a Zomato SDE-1 poster warns that Observer gets the most cross-questioning (2026-10-24). Be ready for this ladder:

  1. Basic Observer: the subject keeps a list of observers and calls update(event) on each.
  2. Memory leaks: observers that are never removed keep objects alive. Return an unsubscribe handle, or hold weak references.
  3. One slow or failing observer must not break the others: try/catch per observer, plus a timeout or a retry policy.
  4. Make delivery asynchronous: put events on a queue and let a worker pool deliver, so the publisher is not blocked by SMS latency.
  5. Across services: the queue becomes a broker (Kafka, SNS). Now it is Pub-Sub: publishers and subscribers do not know each other at all.
How to answer

Code step 1 in three minutes, then walk the ladder yourself before you are pushed. Also mention ordering (per-user order needs a partition key) and iterate over a copy (CopyOnWriteArrayList) so a subscribe during notify does not throw.

Likely follow-ups
  • Push vs pull model (send the data, or send "changed" and let observers fetch)
  • User preferences: which channels per user? (a filter or a Strategy per channel)

In code: keep your EventPublisher interface. Today's implementation loops over listeners; the new one calls a Kafka producer. Each observer becomes a consumer in its own group. Your domain code does not change. That is Dependency Inversion paying off.

How to answer

"Observer becomes Pub-Sub: the broker takes the list." Then coupling, durability, at-least-once, ordering by key. Link the concept to Kafka replication if they go deeper.

Likely follow-ups
  • How do you make the consumer idempotent? (dedupe by event id)
  • What if a consumer keeps failing on one message? (retry topic, dead-letter topic)
Add undo and redo to a text editor.

Each user action becomes a Command object with execute() and undo(). Keep two stacks: run a command, push it on undo; undo pops it, calls undo(), pushes it on redo; any new command clears the redo stack. Our runnable version is in the code section.

The alternative is Memento: snapshot the whole state before each change. Simple and always correct, but memory-heavy for big documents. Real editors mix: commands for small edits, periodic snapshots as checkpoints.

How to answer

Two stacks and the "new command clears redo" rule. Then the trade-off: store operations (Command) vs store states (Memento). Full design: Text Editor with Undo/Redo.

Likely follow-ups
  • Merge consecutive typing into one undo step (coalesce commands)
  • Limit history to 100 steps (bounded deque)
  • Collaborative editing? (operational transform or CRDTs; out of LLD scope, just name it)
Where is Chain of Responsibility the right answer? Show the ATM note dispenser.

Use it when a request should pass along a line of handlers until one (or several) handle it, and the line can change: ATM note dispensing (2000, then 500, then 100), leave approval (lead, manager, director by amount), log levels, HTTP middleware, validation steps. A Razorpay candidate built a logger with it (2024-03-05), and a 2026 forum post asks how much of an ATM (states plus a cash-withdrawal chain) to code in one hour (2026-04-03).

void dispense(int amount, Map<Integer, Integer> out) {
    int count = amount / note;
    if (count > 0) out.put(note, count);
    int rest = amount % note;
    if (rest == 0) return;
    if (next == null) throw new IllegalArgumentException("cannot dispense " + rest);
    next.dispense(rest, out);
}

From your world

Netfilter is the textbook case: hooks registered at NF_INET_PRE_ROUTING run in priority order, and each returns NF_ACCEPT (pass it on), NF_DROP (stop) or NF_STOLEN (I took it). That is a chain where any link may end the walk.

How to answer

Name the "any link may stop" property; that is what separates it from Decorator, where every link forwards. Then mention the real ATM catch: check that the full amount can be paid (and notes are in stock) before dispensing anything. Full design: ATM.

Likely follow-ups
  • Limited notes per denomination: what changes? (each handler checks stock; dry-run first)
  • Who builds the chain? (a factory or config, so the order can change)
Template Method vs Strategy.

Both vary part of an algorithm. Template Method uses inheritance: a base class fixes the steps (final void export() { open(); writeHeader(); writeRows(); close(); }) and subclasses override some steps. Strategy uses composition: the whole varying algorithm is an object you pass in, and it can change at run time. Prefer Strategy when you need to swap at run time or combine several varying parts; Template Method is fine when the skeleton is fixed and there is exactly one axis of change.

How to answer

"Inheritance and compile time vs composition and run time." Mention the Hollywood principle (the base class calls you). See Template Method.

Likely follow-ups
  • Where is Template Method in the JDK? (AbstractList: implement get and size, inherit the rest)
