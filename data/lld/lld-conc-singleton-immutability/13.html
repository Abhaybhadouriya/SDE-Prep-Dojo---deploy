Quiz

In broken DCL, what exactly can the second thread see?

  1. Two different instances
  2. A non-null reference to an object whose constructor writes are not yet visible
  3. A NullPointerException inside synchronized
  4. A deadlock
The reference store can become visible before the field stores. The unlocked first check then returns a half-built object.

Why is the holder idiom thread-safe without any lock in your code?

  1. Nested classes are always synchronized
  2. Because the field is private
  3. The JVM initialises the Holder class once under its own lock, and class init creates a happens-before edge
  4. It is not thread-safe
Class initialisation is done exactly once by the JVM, with a lock, on first active use, and everything it did is visible to later users of the class.

Which of these is NOT enough to make a class immutable?

  1. Wrapping an internal list with Collections.unmodifiableList of the caller's list
  2. Making all fields private final
  3. Making the class final
  4. Copying the input list with List.copyOf
An unmodifiable view still reflects changes the caller makes to the original list. Copy it.

A config is read on every request and changed twice a day. Best design?

  1. synchronized getter and setter
  2. A volatile HashMap that writers modify in place
  3. A fair ReentrantLock
  4. An immutable snapshot behind an AtomicReference, replaced on change
Copy-on-write gives lock-free reads and a consistent snapshot per request. A volatile reference to a map modified in place is still a race.

What is the C++11 (and later) one-line thread-safe singleton?

  1. A global T* p = new T;
  2. static T& get() { static T t; return t; }
  3. A volatile T*
  4. It needs pthread_mutex
Function-local statics are initialised exactly once even when threads race ("magic statics").

A constructor calls bus.register(this) before setting its final fields. What can happen?

  1. Nothing, final fields are always safe
  2. A compile error
  3. Another thread can call back into the object and see default field values
  4. The object is garbage collected
Letting this escape during construction voids the final-field guarantee. Register from a static factory after construction.

Your broken (non-volatile) DCL passed 10,000 test runs on your laptop. What does that prove?

  1. Very little: x86 rarely reorders stores, but the JMM allows the reordering and the JIT or an ARM CPU may do it
  2. That it is correct
  3. That volatile is unnecessary on Java 21
  4. That the JIT is disabled
Memory-ordering bugs are about what the language permits, not what one machine happens to do.
