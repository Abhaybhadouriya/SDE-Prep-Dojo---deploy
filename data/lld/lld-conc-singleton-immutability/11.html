Interview questions

"Write the code for singleton pattern. Explain double locking. Why is volatile used?" is asked word for word in Walmart LLD rounds (LC 6146141).

Write double-checked locking and explain why volatile is needed.

Write the version with private static volatile and the two null checks. Then explain: new is allocate, construct, assign; without volatile the assignment may become visible before the constructor's writes. A thread on the unlocked fast path can then return a half-initialised object. A volatile write is a release, a volatile read is an acquire, so seeing the reference implies seeing everything written before it.

How to answer

Code first (with the local variable), then the three steps, then the happens-before rule. Close with "or I would use the holder idiom, which needs none of this".

Likely follow-ups
  • Why the second null check? (Two threads can both pass the first check before either takes the lock.)
  • Why copy into a local variable? (One volatile read on the fast path instead of two.)
  • Did this work before Java 5? (No; JSR-133 strengthened volatile.)
Which thread-safe singleton would you actually write, and why?

The holder idiom when I want laziness, the enum when I also want protection from reflection and serialization. Both delegate thread safety to class initialisation, which the JVM already makes safe and lock-free after the first use. DCL only when initialisation needs arguments that arrive at runtime.

How to answer

Give the choice, the reason (class-init happens-before), and the trade-off of each in one line. Mention C++ local statics as the equivalent.

Likely follow-ups
  • Is the holder lazy even though the outer class is loaded? (Yes, a nested class is initialised only on first active use.)
  • What if the constructor throws in the holder version?
How do you make a class immutable in Java? What are the traps?

Final class (or record), all fields private final, no setters, validate in the constructor, defensive copies of mutable inputs and outputs, and do not leak this from the constructor. Traps: mutable field types (Date, arrays), unmodifiable views instead of copies, subclassing, and lazy caches inside the object.

How to answer

List the rules, then show a Money or Route record with List.copyOf and a with-style method that returns a new object.

Likely follow-ups
  • Is String immutable? Why does that matter for HashMap keys and security?
  • Does a record make a deep copy of a list component? (No; copy it in the compact constructor.)
What is safe publication? Give the ways to do it.

Making an object reachable from another thread in a way that guarantees that thread sees its fully constructed state. Four ways: static initialiser, volatile field or AtomicReference, final field of a properly constructed object, or a field guarded by a lock on both sides. Putting it in a concurrent collection also works.

How to answer

Define it, list the four, and give the counter-example: a plain field written by one thread and read by another can expose default values.

Likely follow-ups
  • Do immutable objects need safe publication? (Their final fields are safe even through a race, but the reference itself may never become visible without it.)
Design a config store that many threads read on every request and an admin updates a few times a day.

Copy-on-write: an immutable Config snapshot behind an AtomicReference (or a volatile field). Readers call get() once per request and use that snapshot throughout, so a request never sees half old, half new values. Writers build a new snapshot and swap with updateAndGet/compareAndSet. No reader ever blocks.

How to answer

State the read/write ratio, pick COW, draw the pointer swap, and mention why not a ReadWriteLock (readers would still contend on the lock state, and a request could read two different versions in one flow).

Likely follow-ups
  • Two admins update at the same time? (CAS retry, or a writer lock.)
  • How do you notify listeners of a change? (CopyOnWriteArrayList of listeners, called after the swap, outside any lock.)
How do you write a thread-safe singleton in C++?

Since C++11 a function-local static is initialised exactly once even under concurrent calls, so static T& get() { static T t; return t; } is enough. For non-static state use std::call_once with a std::once_flag. A hand-written DCL needs std::atomic<T*> with acquire load and release store.

How to answer

Give the Meyers singleton first, then call_once, and say it is the C++ form of pthread_once.

Likely follow-ups
  • What about destruction order at exit? (Statics are destroyed in reverse order of construction; using one singleton from another's destructor can touch a dead object.)
When would you use CopyOnWriteArrayList, and when not?

For read-mostly lists that are iterated often while rarely changed: listener lists, plug-in registries, routing rules. Iteration is lock-free on a snapshot and never throws ConcurrentModificationException. Avoid it for write-heavy or large lists, since every write copies the whole array.

How to answer

Name the trade-off (O(n) write, free reads), give the Observer use case, and offer ConcurrentLinkedQueue or a locked list for write-heavy cases.

Likely follow-ups
  • Does an iterator see elements added after it started? (No; it walks the old snapshot.)
