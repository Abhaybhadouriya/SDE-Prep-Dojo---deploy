Double-checked locking and why it breaks

Double-checked locking (DCL): check without the lock; if the object is missing, take the lock, check again, and create it. After the first call, threads never touch the lock.

class Config {
    private static Config instance;              // BUG: not volatile
    private int port;
    private Config() { port = 8080; }

    static Config get() {
        if (instance == null) {                  // check 1: no lock
            synchronized (Config.class) {
                if (instance == null) {          // check 2: with lock
                    instance = new Config();     // the dangerous line
                }
            }
        }
        return instance;                         // may be half-built!
    }
}

The dangerous line is three operations, not one: (1) allocate memory, (2) run the constructor (write port = 8080), (3) store the address in instance. Inside one thread you cannot tell whether (2) or (3) became visible first, so the JIT compiler and the CPU are allowed to make (3) visible to other cores before (2). Thread T2 does check 1 without the lock, so the lock's visibility guarantee does not apply to it. It can see a non-null instance and read port == 0.

  1. T1 holds the lock and allocates the object. All fields start at their default (0, null).
  2. The JMM allows the store to instance (step 3) to become visible before the constructor's write to port (step 2).
  3. T2 runs check 1 without the lock. It sees a non-null reference and skips the synchronized block entirely.
  4. T2 reads port and gets 0. The program runs with a half-built config. Nothing crashes; it is just wrong.
  5. Fix: declare instance volatile. A volatile write cannot be moved before earlier writes, and a thread that reads the reference through a volatile read sees everything written before it.

Do not try to prove this with a test. On x86, the hardware rarely reorders two stores, so the broken version passes almost every test (our demo prints the right value). The bug comes from what the language allows the JIT and weaker CPUs (ARM, as in many phones and Graviton servers) to do. "My test passed" is not evidence of thread safety.

This bug was famous enough to get its own document: "The Double-Checked Locking is Broken Declaration", signed by a group of JVM and memory-model experts. It explained that no clever trick fixed DCL under the original Java memory model. The JMM rewrite in Java 5 (JSR-133) strengthened volatile, and that made the volatile version below correct.
