Copy-on-write: change by replacing

Immutability is great until something really must change: feature flags, a routing table, a price list. Copy-on-write (COW) combines the two ideas. The data itself is an immutable snapshot. A single mutable reference points at the current snapshot. Readers read the reference (one volatile read, no lock) and then work on a snapshot that can never change under them. A writer copies the snapshot, changes the copy, and swaps the reference in one atomic step.

record Config(int version, Map<String, String> values) {
    Config { values = Map.copyOf(values); }                 // immutable snapshot
    Config with(String k, String v) {
        Map<String, String> m = new HashMap<>(values);
        m.put(k, v);
        return new Config(version + 1, m);
    }
}

final class ConfigStore {
    private final AtomicReference<Config> current = new AtomicReference<>(new Config(0, Map.of()));

    Config snapshot() { return current.get(); }               // readers: no lock
    void put(String k, String v) {
        current.updateAndGet(c -> c.with(k, v));              // writers: copy, modify, CAS; retry on clash
    }
}

Our demo runs one reader in a tight loop checking the invariant version == number of keys on every snapshot, while 4 writers make 250 updates each. Result: version 1000, 1000 keys, no lost update, and the reader never saw a torn snapshot. The C++ version uses std::shared_ptr<const Config> with std::atomic_load/std::atomic_store; the reference count keeps an old snapshot alive while a reader still holds it.

CopyOnWriteArrayList for listeners

The JDK ships the same idea as CopyOnWriteArrayList: every add or remove copies the whole backing array, and iterators walk the snapshot that existed when they started, so they never throw ConcurrentModificationException. It is ideal for strategy or listener lists in an Observer, where events fire constantly and subscriptions change rarely. It is a bad choice for a list that is written often: each write costs O(n) copying.

COW is good when
  • Reads vastly outnumber writes (config, routing tables, listener lists)
  • Readers must never block or see a partial update
  • A full snapshot per read is what callers want
COW is bad when
  • Writes are frequent or the data is large (each write copies everything)
  • Writers need to see each other's changes instantly in a read-modify-write (use a lock or CAS loop)
  • Memory is tight: old snapshots live until the last reader drops them

From your world

This is RCU (read-copy-update) without the hard part. In the kernel, readers enter rcu_read_lock(), follow a pointer with rcu_dereference(), and never block; a writer builds a new copy, publishes it with rcu_assign_pointer(), then waits in synchronize_rcu() for a grace period before freeing the old copy. In Java the garbage collector does the "wait until no reader holds it" step for you; in C++ shared_ptr reference counts do it (like kref). Routing tables and netfilter rule sets use this pattern for the same reason a Java config store does: lookups on the fast path, rare updates.
