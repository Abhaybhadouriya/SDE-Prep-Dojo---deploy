From naive to synchronized

The Singleton pattern page covers the pattern itself: the private constructor, eager vs lazy, and attacks by reflection and serialization. Here we focus only on threads. Start with the version everybody writes first:

class Config {
    private static Config instance;
    private Config() { load(); }

    static Config get() {
        if (instance == null) {        // T1 and T2 both see null ...
            instance = new Config();   // ... and both construct one
        }
        return instance;
    }
}
class Config {
    private static Config instance;
    private Config() { load(); }

    static synchronized Config get() { // the lock fixes "once" AND "visible"
        if (instance == null) instance = new Config();
        return instance;
    }
}

The synchronized version is fully correct. Its only cost is that every call, forever, takes a lock, even though the lock is only needed for the first call. With an uncontended lock that cost is small, and for most programs it is fine. But if a hot path calls get() millions of times from many threads, they all queue on one lock. That is what double-checked locking tries to avoid.

In an interview, saying "the synchronized version is correct and simple; I would only optimise it if profiling shows contention" is a strong answer, not a weak one.
