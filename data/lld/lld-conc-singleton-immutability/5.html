Happens-before: the rules that make the fixes work

The JMM does not promise that threads see writes in order. It promises something narrower: if action A happens-before action B, then B sees A's effects. Thread safety means making sure every read of shared data is connected to the write it needs by a chain of these edges. The rules you will use in interviews:

  • Program order: inside one thread, each action happens-before the next.
  • Monitor lock: an unlock happens-before every later lock of the same monitor. (Why the synchronized version works.)
  • Volatile: a write to a volatile field happens-before every later read of that field. (Why volatile DCL works.)
  • Class initialisation: the JVM's initialisation lock gives an edge from finishing static initialisers to every thread that then uses the class. (Why holder and enum work.)
  • Thread start and join: t.start() happens-before anything in t; everything in t happens-before t.join() returns.
  • Transitivity: A before B and B before C gives A before C. This is how a whole object built before a volatile write becomes visible.

Final fields get a special guarantee (JLS 17.5): if a constructor sets a final field and does not let this escape, any thread that later obtains a reference to the object sees the field's constructed value, even if the reference reached it through a data race. That is why the "Broken Declaration" notes that DCL works without volatile when the object is immutable with all fields final. Use volatile anyway: it is clearer, and one non-final field added later silently brings the bug back.
