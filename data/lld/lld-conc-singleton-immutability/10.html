Pitfalls and senior-level nuance

  • "Immutable" class with a mutable field. A final Date or final int[] field can still be changed through the reference. Copy it in and out, or use an immutable type (Instant, List.copyOf).
  • Unmodifiable view is not a copy. Collections.unmodifiableList(list) reflects later changes to list. If the caller keeps the original, your "immutable" object changes under you.
  • Volatile makes the reference safe, not the object. A volatile Map pointing at a HashMap that threads keep modifying is still broken. Volatile only works with COW (replace the whole object) or with an immutable object.
  • Check-then-act on a snapshot. if (store.snapshot().has(k)) store.put(...) is two steps; another writer can slip between them. Put the decision inside the update function (updateAndGet) so it is retried with fresh data.
  • Singletons hurt testability. A global instance is hidden shared state. In an LLD answer, prefer creating one instance at start-up and passing it in (dependency injection); say "one instance" without "global access". Our Singleton page covers this.
  • Serialization and reflection can create a second instance of a class-based singleton; enum is immune to both. That is covered in detail in the Singleton attacks section, which Walmart has asked about (LC 5967414).
  • Exception in the constructor. With DCL, nothing is published and the next caller tries again. With the holder idiom, a failed static initialiser leaves the class unusable: later calls get NoClassDefFoundError. Know which behaviour you want.

A strong closing line: "My first choice for thread safety is to not share mutable state: immutable value objects, and a copy-on-write snapshot behind an AtomicReference for the rare changes. I reach for locks only where several fields must change together under a read-modify-write."
