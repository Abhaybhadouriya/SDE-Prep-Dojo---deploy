Extensibility: the follow-ups

Follow-upChange
Count active keys, and per-key counts (Uber)Keep counters updated on every insert, delete and expiry (in put, delete, purgeLocked); call purgeExpired before reading them. The single global heap is what the Uber interviewer asked for.
O(1) getRandom() (Uber 2026)Add an ArrayList<String> of keys and a key to index map; delete swaps the last key into the hole (LeetCode 380 trick). Expired keys found by getRandom are purged and it retries.
Count keys with a given value (NUMEQUALTO)A value to count map maintained in put and removal; inside a transaction compute it from layers + store, or keep a delta per layer.
Rollback with an undo log instead of layersWrite straight to the store and record the inverse (old value or "did not exist") per change; rollback replays them in reverse. Reads are faster (no layer walk), but uncommitted data is visible to others unless you also lock: a Command-style design.
Memory limitAn eviction strategy (LRU, LFU, volatile-ttl) called from put; see LRU cache.
Very many TTL keysReplace the heap with a hierarchical timing wheel (O(1) insert, bucketed expiry), as in Kafka and the Linux kernel timers.
PersistenceAppend every committed write set to a log (write-ahead), replay on start; periodic snapshots (our Memento serialised) to bound replay time.
Tables and indexes (Razorpay "in-memory DB")A Table with a schema, rows by id (auto-increment AtomicLong), and a secondary index map field value to set of ids updated in the same write; transactions work unchanged if a row is one entry.
Watch / notify on changeGeneralise ExpiryListener to a key-event listener (set, delete, expired), like Redis keyspace notifications.
Sharding across coresN stores, key hash mod N, each with its own lock; transactions across shards then need two-phase commit, so say "transactions are per shard" first.
