Key relationships and patterns (and why each)

Pattern / ideaWhereWhy hereWhat you say in the room
MementoInMemoryStore.Snapshot; the driver is the caretakerThe caller can keep and hand back a saved state without being able to read or change it. Entries are immutable, so the copy shares them (cheap, no deep copy)."A snapshot is an opaque token. Only the store can read it, and restoring is swapping the map back."
Layered write set (a unit of work: a private buffer of pending writes, applied at commit)Session.layers with tombstonesNested rollback is "pop a map"; nested commit is "merge into the parent map". Cost is proportional to what the transaction wrote, not to the store size. Compare with an undo log (Command-style inverse operations) in the follow-ups."BEGIN pushes a map, ROLLBACK pops it, COMMIT merges it down. A delete inside a transaction is a tombstone."
Optimistic concurrency (version check)Entry.version, Session.readVersions, InMemoryStore.commitTransactions never hold locks while the client thinks; conflicts are detected at commit. First committer wins; the loser retries. This is the kernel's seqlock idea at transaction scope: note each key's version on read, and at commit retry if any version moved (the concurrency section spells it out)."No locks are held while the client thinks. At commit I compare versions; if one changed, the commit fails and the caller retries."
ObserverExpiryListenerCache invalidation, session logout, metrics react to expiries without the store knowing them. Called after the lock is released."Expiry fires events after unlock, so a slow listener never stalls the store."
Strategy / dependency injectionClockTests jump time; production uses the system clock. See dependency injection."Time is injected, so the TTL tests run in microseconds and never sleep."
Interface + substitutionKeyValueStore implemented by store and sessionA Session outside a transaction is just the store (autocommit). Code written against the interface does not care. See LSP."Callers use KeyValueStore; with no transaction open, a session behaves exactly like the store."
Lazy deletion in a heapExpiryRef.versionRewriting a key does not search the heap for the old item; the old item is simply skipped when it surfaces."An old heap item whose version no longer matches is ignored when it reaches the top."

Patterns we deliberately skipped: an undo log of inverse Commands (it works, but rollback then replays inverses and must remember old values; a layer stack makes rollback a pop), a Singleton store (the demo and the tests need fresh stores, each with its own fake clock), and pessimistic per-key locks taken by a transaction (they would be held while the client thinks, and two transactions locking keys in different orders can deadlock).

From your world

The Memento is a saved CPU context on a context switch, or a CRIU checkpoint: an opaque blob that only the owner (the scheduler, the kernel) knows how to restore. The lazily-deleted heap is what the kernel's timer code avoids by design: del_timer unlinks in O(1) from a timer-wheel list. A Java PriorityQueue cannot remove an arbitrary item cheaply (O(n)), so we keep the item and ignore it later.
