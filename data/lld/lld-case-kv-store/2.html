Clarify requirements

Functional (P0)

  1. CRUD get(k), set(k, v), delete(k) on string keys and values.
  2. TTL set(k, v, ttl), expire(k, ttl), ttl(k) (-2 no key, -1 no TTL, else time left). An expired key behaves exactly like a missing key. A plain set clears an old TTL (Redis does the same).
  3. Transactions begin, commit, rollback; they nest. Rollback undoes the innermost open transaction only. Writes are invisible to others until the outermost commit.
  4. Snapshots Take a snapshot of the whole store; restore it later.
  5. Count Number of live keys (Uber's "count of active keys").

Functional (P1)

  • Expiry notifications (a listener told when a key expires).
  • Conflict detection when two clients change the same key in overlapping transactions.

Non-functional

  • O(1) average get/set/delete; expiry cost proportional to the keys that actually expire, never a full scan.
  • Correct at the deadline: a read one millisecond after expiry must miss, even if no sweep has run.
  • Thread safe: many readers in parallel; no lost update for read-modify-write in transactions.
  • Testable time: an injected clock, so a test can jump 30 seconds.

Out of scope

  • Persistence (AOF, snapshots on disk), replication, eviction under memory pressure (see LRU cache), data types beyond strings, a network protocol.
