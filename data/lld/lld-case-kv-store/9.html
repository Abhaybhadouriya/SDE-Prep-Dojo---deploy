Concurrency and thread safety

Three kinds of shared state need protection: the entry map, the expiry heap, and the version counter. Sessions are owned by one client (one thread) and are not shared, so their layers need no lock at all.

Optimistic or pessimistic transactions?

Optimistic (ours): validate at commit
  • No lock held while the client works; readers never block writers.
  • No deadlocks possible.
  • Cheap when conflicts are rare (most KV workloads).
  • Matches Redis WATCH + MULTI/EXEC: the transaction aborts if a watched key changed.
Costs and the alternative
  • Hot keys (one global counter) cause many retries: our 8-thread test retries a lot.
  • Callers must loop on ConflictException.
  • Pessimistic alternative: lock each key on first read or write (two-phase locking), release at commit; no retries but deadlocks need ordering or timeouts.
  • For a hot counter, offer an atomic incr instead of a transaction.

What we validate matters. Only keys the transaction read from the store are checked. A blind write (set without reading) does not conflict: last writer wins, which is correct because the transaction's result did not depend on the old value. A key read as absent is recorded as version 0, so "someone created it meanwhile" is caught too. Rolling back an inner transaction keeps its reads in the set: conservative (may cause an extra retry) but never wrong.

Our reads see the latest committed value each time (read committed while running), but because every read is validated at commit, any transaction that commits behaves as if it ran at its commit instant (serialisable for the keys it read). Snapshot isolation (MVCC: keep several versions per key, read the one as of begin) is the next step if the interviewer asks for repeatable reads.

From your world

This is the kernel's seqlock pattern: readers note the sequence number, read without a lock, and retry if the number changed; writers bump it under a spinlock. Our versions are a per-key sequence, our commit is the writer, and ConflictException is the reader's retry. A read-write lock with "no upgrade" is the same rule as rwlock_t: you cannot turn a read_lock into a write_lock without dropping it first.
