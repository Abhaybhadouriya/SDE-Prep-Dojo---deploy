Interview follow-ups

Why a trie and not a sorted list or a hash map of prefixes?

A hash map of every prefix to its phrases costs memory proportional to the sum of all phrase lengths times the phrases, and every insert touches L map entries anyway. A sorted list finds the prefix range by binary search (O(log n)) but then must scan the whole range to find the top k by score. A trie shares prefixes, finds the prefix node in O(prefix length) independent of n, and is the natural place to hang a per-subtree summary (the cached top-k).

How to answer

Compare the three on "find the prefix" and on "best k inside it"; the trie wins the second only with the cache.

Likely follow-ups
  • When is a sorted array plus binary search better? (Static vocabulary, ranking by text, tiny memory.)
Prove the incremental top-k cache stays exact. When does it break?

Invariant: each node's list holds the best k entries of its subtree. A record changes one entry's score, upward, and that entry is in the subtree of exactly the nodes on its path. Other nodes are unaffected. On a path node, every entry other than the recorded one keeps its score, so their relative order is unchanged, and an entry outside the old top-k is still worse than all of them. Only the recorded entry can enter or move up, so "remove it, add it, sort, keep k" restores the invariant. It breaks when any score can fall: delete, time decay, a negative-feedback signal. Then rebuild affected nodes from their children's caches (what remove does) or recompute periodically.

How to answer

State the invariant, then the one-line monotonicity argument, then the two operations that violate it.

Where does the Strategy pattern fit, and what does a new strategy have to promise?

RankingStrategy is a comparator over entries; the engine sorts and caches with whatever it was given. A new strategy is a new class. But it must keep the cache's contract: an entry's score may only rise when it is recorded and must not change otherwise. Frequency and recency both satisfy that. A "trending in the last hour" strategy does not (scores fall as time passes), so it either runs with cacheTopK = false or with periodic rebuilds. Saying that contract out loud is the senior-level part of the answer.

Why must the router backtrack? Show a case where greedy fails.

Routes /a/b/x and /a/*/c; request /a/b/c. Greedy picks the literal "b" at segment two (most specific), then finds no "c" under it and returns 404, although /a/*/c matches. Precedence is a preference order among branches, not a commitment; the matcher must try the next branch when one dead-ends, and undo any params captured along the failed branch.

Likely follow-ups
  • Worst case cost? (Exponential in principle with many wildcards per level; in practice tiny. Memoising (node, index) bounds it.)
What should put("/users/:uid") do when /users/:id already exists?

Reject it at registration. Both patterns match exactly the same paths, so the second would either be unreachable or silently rename the captured param for the first. One param child per node with one name keeps captures unambiguous. Likewise, registering the same pattern twice is an error, not an overwrite: silent overwrites in a router are production incidents.

The follow-up moves the wildcard into get. How does your design change?

Same trie, different walk. Keys are stored as plain literal paths; the query is walked segment by segment, and a * in the query fans out over all literal children of the current node. It is a DFS that collects every terminal node reached at the last segment, returned in sorted order because the children map is sorted. Cost is the number of nodes visited, which a * near the root makes large: mention a limit or pagination.

Suggestions are called on every keystroke for millions of users. What changes beyond the class design?

The LLD stays: a trie with cached top-k per node. Around it: the trie is built offline from aggregated query logs and shipped read-only to many servers (no write lock on the hot path); sharded by prefix range when it does not fit in memory; results cached in the browser for short prefixes; requests debounced by the client. Recording becomes a log event aggregated in batches rather than a live record call. That is the bridge to the HLD version.

How much memory does the cache cost, and how would you cut it?

k references per node, and a trie has up to one node per character of every phrase, so roughly k x total characters. Cuts: a radix trie (merge single-child chains, fewer nodes); cache only to depth d and scan below (short prefixes are the hot ones and have the biggest subtrees; long prefixes have tiny subtrees that are cheap to scan); store entry ids instead of references in compact arrays.

Make it thread safe. Why a read-write lock and not synchronized on every method?

Reads vastly outnumber writes and do not modify anything, so they can run in parallel; a plain monitor would serialise every keystroke. Writes need exclusivity because one record updates up to L caches and readers must not see a partial update. Results are copied out under the read lock. If writes become frequent, batch them; if reads must never block, publish an immutable trie by reference and rebuild it in the background (copy-on-write, like RCU).

In the typing session, each keystroke walks from the root. Can you avoid that?

Yes: keep the current node in the session. Each new character is one child lookup; a character with no child sets the node to "none" so later keystrokes return empty immediately; # resets to the root. Beware concurrent remove: the held node may be pruned, so either re-walk after any structural change (a version counter) or never prune nodes.
