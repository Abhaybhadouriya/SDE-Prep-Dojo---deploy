Concurrency and thread safety

Background: read-write locks, races and atomicity.

  1. Read-mostly, so a read-write lock suggest and match take the read lock and run in parallel. record, remove and put take the write lock. A record touches up to L caches, and a reader must never see some updated and some not, so the whole update is one write section.
  2. Snapshots out suggest copies entries into immutable Suggestion records while it holds the read lock. Returning the live Entry objects would let a caller read a count while a writer changes it.
  3. Lost updates count += times is a read-modify-write; without the write lock, 4 writers x 500 would end below 2000. The Java demo checks exactly that.
  4. Write-heavy traffic If every keystroke records (rare, but asked), the write lock becomes the bottleneck. Options: buffer records in a concurrent map of counters and apply them in batches every second (suggestions become slightly stale, which is fine for search); or shard by first character, one trie and one lock per shard.
  5. Router Routes are registered at startup and then only read. A neat alternative to locking: build the trie, then publish it through one volatile reference (copy-on-write). Readers need no lock at all; a rare put builds a new trie and swaps the reference.

A strong closing line: "Reads are per keystroke, so I optimised reads: O(prefix + k) with cached top-k and a shared lock. Writes pay O(L x k log k) under an exclusive lock, and if writes grow I batch them." It shows you know which side you traded.

From your world

The copy-on-write router is RCU: readers walk the current version with no lock; the writer builds a new version and publishes it with one pointer store (rcu_assign_pointer); the old one is freed when no reader can still hold it, which in Java the garbage collector does for you. The routing FIB is updated in the kernel in exactly this style.
