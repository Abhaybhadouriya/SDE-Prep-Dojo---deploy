With cached top-k per node, what does suggest(prefix) cost?

  1. O(number of phrases)
  2. O(prefix length + k)
  3. O(size of the subtree)
  4. O(k log n)
Walk the prefix, then copy the node's k cached entries.

Which change makes the incremental top-k update incorrect?

  1. Recording a phrase twice
  2. Switching from frequency to recency ranking
  3. Adding a new phrase
  4. Removing a phrase or letting scores decay over time
The proof relies on scores only rising. Removal and decay make scores fall, so entries outside the cache could now belong in it.

Counts: "ab" 2, "aa" 2, "ac" 5. Frequency ranking with alphabetical ties, k = 2, prefix "a"?

  1. ac, aa
  2. ac, ab
  3. aa, ab
  4. ab, aa
5 first; then the tie between "aa" and "ab" is broken alphabetically.

Routes /a/b/x and /a/*/c. What should match("/a/b/c") return?

  1. 404, because the literal "b" was chosen
  2. /a/b/x
  3. /a/*/c, after backtracking
  4. An error: ambiguous routes
Literal is preferred, but when that branch dead-ends the matcher tries the next branch.

What should happen on put("/users/:uid", v) when /users/:id exists?

  1. Overwrite the old route
  2. Reject it as a conflict
  3. Keep both and match the newest
  4. Rename the param
Both match the same paths; failing at registration avoids unreachable routes and ambiguous captures.

Which lock fits the autocomplete engine best?

  1. A read-write lock: suggest shares, record and remove are exclusive
  2. One lock per trie node
  3. No lock, because reads do not modify
  4. synchronized on every method
Reads dominate and can run in parallel; a record updates many caches and needs exclusivity to stay consistent for readers.

A ranking strategy for "trending in the last hour" is added. What is the safe choice?

  1. Use it with the incremental cache unchanged
  2. Make it a Singleton
  3. Store the scores in the router
  4. Disable the incremental cache (scan with a heap) or rebuild caches periodically
Its scores fall as time passes, which breaks the cache's contract.
