Core flows

record("lru cache") with cached top-k

  1. The session sees # and records what was typed. A direct record call from a search service takes the same path.
  2. One write lock for the whole update, so a reader never sees a half-updated set of caches. The text is lower-cased and spaces collapsed.
  3. Walk the trie character by character, creating nodes as needed, and remember the path (root included).
  4. Create the entry if new, add to its count, stamp it with the logical clock (for the recency strategy).
  5. For every node on the path: take the entry out of the node's top-k if present, add it, sort with the strategy, drop the (k+1)th. Correct because only this entry's score changed and it only went up.
  6. Release. The cost is O(L x k log k) for a phrase of length L; reads stay O(prefix + k).

match("/a/b/c") with backtracking

  1. Segment "a" matches a literal child.
  2. Segment "b": the literal child exists, so it is tried first (most specific).
  3. Segment "c": the "b" node only has literal "x". No param, no star, no globstar: this branch fails.
  4. Back at the "a" node, the matcher tries the next kind of child. There is no param child, so it tries *, which takes "b".
  5. Segment "c" is a literal under * and holds a value: the answer is anyC via /a/*/c. A greedy matcher that never backtracks would return 404 here; this is the bug interviewers probe.

Params are written into the result map on the way down and removed when a branch fails, so a failed :id attempt never leaks into the final answer. ** is tried last and captures the rest of the path (or nothing: /static matches /static/**).
