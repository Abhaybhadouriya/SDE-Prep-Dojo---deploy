Concurrency and thread safety

Background: races and atomicity, booking without double-booking.

Step through the race this section is about, then the fix the code uses:

  1. Student A's borrow scans the copies and finds C2 AVAILABLE.
  2. Student B's borrow scans before A writes and finds the same copy.
  3. Both create a loan for C2. The system says two people have it; the shelf had one book.
  4. The fix: the whole borrow runs under one lock, so the second scan finds no free copy and gets "no copy available; reserve it". The Java demo sends 6 students at 2 copies: exactly 2 win.
  1. Two members, one copy Finding an AVAILABLE copy and marking it BORROWED is a check-then-act. Without a lock both threads see the same free copy. We run the whole borrow under one lock; the Java demo sends 6 students at 2 copies and the Python test sends 8; exactly 2 win every time.
  2. Return racing with borrow A return that hands the copy to the queue must be atomic: if the copy were visible as AVAILABLE for even a moment, a walk-in borrower could take the copy promised to m2. Our return moves AVAILABLE then ON_HOLD inside the same critical section, so nobody can observe the middle state.
  3. Notify outside the lock The return collects "notify m2" events while holding the lock and runs them after releasing it. Calling an email service under the lock would make every borrower wait for SMTP. It also avoids a listener calling back into the service and deadlocking.
  4. Scaling the lock One lock is fine for a single library. For more, use one lock per book (lock striping): a borrow, return or reserve touches one book's copies and queue. The member's loan count and dues are then shared across books, so take the member lock first and the book lock second, always in that order (see deadlock).
  5. In a database Pick and claim a copy with one conditional statement: UPDATE copies SET status = 'BORROWED' WHERE barcode = ? AND status = 'AVAILABLE' and check the row count; or SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1 to grab any free copy without waiting on rows another transaction holds.

From your world

"Collect events under the lock, run them after" is the same reason the kernel defers work out of a spinlock-held section to a workqueue or softirq: never sleep or do slow I/O while holding a lock others spin on. The AVAILABLE then ON_HOLD move inside one critical section is like updating a socket's state and its queue under the same lock so a reader never sees a half-done transition.
