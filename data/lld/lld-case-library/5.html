Key relationships and patterns (and why each)

Pattern / choiceWhereWhy it earns its place
Type versus instance (sometimes called Type Object)Book and BookCopyShared facts live once; per-item state (status, rack, holder) lives on each copy. Search and reservations use the type; loans use the instance.
StrategyFineStrategy: PerDayFine, GraceThenPerDayFine, chosen per MemberType from an EnumMapFine rules change often (caps, grace days, holiday waivers) and differ by member type. A new rule is a new class and one map entry; returnCopy never changes.
ObserverAvailabilityListener registered with subscribeThe service should not know about email, SMS or push. It announces "copy held for member X until date Y"; listeners decide what to do. Listeners are called after the lock is released.
State table (enum), not the full State patternCopyStatus.canMoveToFour states and simple transitions with no per-state behaviour. A transition table is enough; one class per state would be ceremony. Switch to the State pattern if states start to carry real behaviour (for example, different return logic per state).
FacadeLibraryServiceOne entry point for the driver, a CLI or a REST controller, and one place to hold the lock.
Injected clocksetToday(date) (or a Clock in production)Fines and holds depend on dates. Tests jump to day 18 instead of sleeping, and the demo is deterministic.

Two traps. Do not make LibraryService a Singleton "because there is one library"; it makes tests share state, and patterns alone did not carry the Zepto candidate (who used Singleton and was still rejected without feedback). And do not give Member a borrow(book) method that edits copies and queues directly: the member would need to know the catalogue, the waitlists and the fine rules. Keep the coordination in the service; keep Member as data plus its own invariants.

From your world

The fine table is an ops table indexed by type, the way the block layer picks an I/O scheduler or the network stack picks a congestion-control algorithm per socket (tcp_congestion_ops: cubic, bbr, reno, each a struct of function pointers chosen by name). AvailabilityListener is register_netdevice_notifier() in miniature: subscribers register a callback, the core calls them when the event happens, and the core does not care what they do with it.

Why the pattern earns its place: the if-ladder it replaces

Without the Strategy, every member type is a branch in the fine calculation:

long fine(Member m, long daysLate) {
    if (m.type == MemberType.STUDENT) {
        return daysLate * 10_00;
    } else if (m.type == MemberType.FACULTY) {
        return Math.max(0, daysLate - 2) * 5_00;
    } else if (m.type == MemberType.STAFF) {       // follow-up: a new type edits here,
        return Math.min(daysLate * 7_00, 200_00);  // and in the loan-limit if-ladder,
    }                                              // and in the loan-days if-ladder
    throw new IllegalStateException();
}
interface FineStrategy { long fine(long daysLate); }
final class PerDayFine implements FineStrategy { ... }
final class GraceThenPerDayFine implements FineStrategy { ... }

enum MemberType {
    STUDENT(2, 14, new PerDayFine(10_00)),
    FACULTY(5, 30, new GraceThenPerDayFine(2, 5_00));   // a new type is one line here
    ...
}

With the ladder, the follow-up "add STAFF members" edits fine, the loan-limit check and the loan-length check. With the Strategy in the enum it is one enum line (and a new FineStrategy class only if the rule is new); LibraryService is not opened.

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
