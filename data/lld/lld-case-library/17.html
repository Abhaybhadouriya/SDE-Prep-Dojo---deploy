Quiz

Which class should hold the rack number and the current borrower?

  1. Book
  2. Member
  3. LibraryService
  4. BookCopy
Rack and status belong to each physical copy; two copies of one book can sit on different racks and be with different people.

A copy is returned and two members are waiting for that book. What is the copy's new status?

  1. AVAILABLE
  2. ON_HOLD for the first member
  3. ON_HOLD for both
  4. BORROWED by the first member
It is held for the first in line, who must come and borrow it within the hold period. Auto-borrowing would start a loan the member never picked up.

A student returns a book 3 days late at 10.00 a day; a faculty member, with 2 days of grace and 5.00 a day, returns 3 days late. Fines?

  1. 30.00 and 5.00
  2. 10.00 and 5.00
  3. 30.00 and 15.00
  4. 30.00 and 0.00
Student: 3 x 10.00. Faculty: (3 - 2) x 5.00. Two strategies, one per member type.

Why does the service take "today" from outside instead of reading the system clock?

  1. To support time zones
  2. It is faster
  3. So fines and hold expiry can be tested deterministically
  4. Java dates are not thread safe
Injected time lets tests jump to day 18 and makes the demo output the same on every run.

Where should listeners be notified that a copy is on hold?

  1. From the Member class
  2. Inside the lock, right after the status change
  3. From a finalizer
  4. After the lock is released, from events recorded inside it
Recording under the lock keeps it consistent; running after keeps slow I/O and re-entrant calls out of the critical section.

For four copy states with simple transitions and no per-state behaviour, what is the lightest safe model?

  1. Two booleans
  2. An enum with a transition table checked in one method
  3. A string field
  4. The full State pattern, one class per state
An enum plus a table gives compile-time names and refuses illegal moves. The State pattern pays off when states have their own behaviour.

Which SQL statement prevents lending one copy twice when many app servers run?

  1. UPDATE copies SET status='BORROWED' WHERE barcode=? AND status='AVAILABLE', then check rows affected
  2. SELECT status then UPDATE in application code
  3. Caching copy status in Redis
  4. A synchronized method on each server
Only a conditional update (or a row lock) in the shared database is atomic across servers.
