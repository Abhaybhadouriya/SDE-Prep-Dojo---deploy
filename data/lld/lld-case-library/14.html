Interview follow-ups

Why not just keep a copy count on Book?

A count answers "how many are free" and nothing else. It cannot say which physical copy is overdue, which one is held for Ben until Friday, which rack it sits on, or which one was reported lost. Each copy has its own state and history, so it is its own object. The count becomes a derived value: the number of copies in AVAILABLE.

How to answer

List two questions a count cannot answer; then say "type versus instance".

Likely follow-ups
  • When is a count good enough? (E-book licences.)
Is the reservation on a book or on a copy? Why?

On the book. Members want "Linux Kernel Development", not copy C3. Whichever copy comes back first goes to the first person in that book's queue. Reserving a specific copy would make people wait for one copy while another sits on the shelf.

How to answer

User intent first, then the consequence of the wrong choice.

Likely follow-ups
  • What if branches differ? (Queue per book per branch, or let the member pick.)
A copy is returned while three people are waiting. Walk through it.

Under the lock: close the loan, charge the fine, move the copy to AVAILABLE and at once to ON_HOLD for the first member in the FIFO queue, with a hold date three days out. Record a "notify" event. Release the lock, then call the listeners. The other two stay in the queue. If the first member does not come, expireHolds passes the copy to the second, and so on; only when the queue is empty does the copy go back on the shelf.

How to answer

Name the states the copy goes through and where the lock boundary is.

Likely follow-ups
  • Who runs expireHolds, and what if it runs twice?
Where do you use Strategy here, and is it worth it?

For fines. Students pay per day with a cap; faculty get a grace period; next term the library may waive weekends. Each is a class with one method, fine(daysLate), and the service picks one by member type from a map. The alternative, an if (type == STUDENT) inside returnCopy, grows with every rule and every type. It is worth it as soon as there are two rules; with one, a plain method is fine and you say "I would extract a strategy when a second rule appears".

How to answer

Pattern, the variation it absorbs, and when you would not use it.

Likely follow-ups
  • Fine depends on the book's price too. What changes?
Do you need the State pattern for BookCopy?

Not here. The states carry no behaviour of their own; only the allowed transitions matter. An enum with a canMoveTo table, checked in one moveTo method, gives the safety with a tenth of the code. The State pattern (one class per state, each implementing borrow, return) pays off when each state behaves differently, as in a vending machine; see state diagrams.

How to answer

Show you know the pattern and choose the lighter tool on purpose.

Likely follow-ups
  • Add IN_TRANSIT between branches. What changes?
Why notify after releasing the lock?

Listeners do slow or unknown work: send an email, call another service, maybe call back into the library. Under the lock, every borrower and returner would wait for that I/O, and a listener calling back into the service could deadlock or see half-updated state. So the critical section only records what to send; the sending happens after. The cost is that a listener may run slightly after the state changed, which is fine for a notification.

How to answer

Two reasons (latency and re-entrancy) and the trade-off you accept.

Likely follow-ups
  • What if the notification fails? (Retry from a queue; the hold is already safe.)
Two members borrow the last copy at the same moment.

Both requests enter borrow; the lock lets one in. It finds the AVAILABLE copy, moves it to BORROWED and records the loan. The second then finds no free copy and gets "no copy available; reserve it". Without the lock both could pick the same copy and the library would lend it twice. In a database the same guarantee comes from a conditional update on the copy's status, plus a unique index on open loans per copy.

How to answer

Race, critical section, what the loser sees, and the database equivalent.

Likely follow-ups
  • How would you avoid one lock for the whole library?
How do you test fines without waiting two weeks?

The service never calls the system clock. It takes "today" from outside (setToday in the demo, a java.time.Clock in production code). Tests borrow on 11-01, set the date to 11-18 and return. The same trick makes hold expiry testable. It is dependency injection applied to time.

How to answer

Name the dependency (time), how it is injected, and one test it enables.

Likely follow-ups
  • Time zones: when does "day 15" end?
Make search fast for a million books.

Scanning every title is O(n) per query. Build an inverted index on addBook: lowercase tokens of title, author and subject map to sets of isbns. A query intersects the sets of its tokens, smallest first; prefix search uses a trie or a sorted token list. Availability is looked up per result from the copy states. Beyond one machine, a search engine indexes the catalogue and the library service stays the source of truth for availability.

How to answer

Data structure, update path, query path, and where it stops scaling.

Likely follow-ups
  • Typos and ranking?
Design the tables and the borrow transaction.

books, copies (with status and hold columns), members (with dues), loans (with a partial unique index on open loans per copy) and reservations (isbn, member, time). Borrow in one transaction: check member dues and open-loan count, claim a copy with a conditional UPDATE ... WHERE status = 'AVAILABLE' (or the held copy for this member), insert the loan, delete the member's reservation row. Any failed check rolls the whole thing back.

How to answer

Tables, the one statement that prevents double lending, and the transaction boundary.
