The problem: if/else on the vendor, everywhere

Imagine a checkout service that started with one payment gateway and then had to support a second. The first version usually looks like this:

class CheckoutService {
    private final String gateway;              // "acme" or "zen", read from config

    String pay(String orderId, long paise) {
        if (gateway.equals("acme")) return new AcmeCharger().charge(orderId, paise);
        else if (gateway.equals("zen")) return new ZenCharger().charge(orderId, paise);
        throw new IllegalStateException(gateway);
    }
    String refund(String chargeId, long paise) {
        if (gateway.equals("acme")) return new AcmeRefunder().refund(chargeId, paise);
        else return new ZenCharger().refund(chargeId, paise);   // BUG: wrong class, and nobody noticed
    }
    boolean onWebhook(String body, String sig) {
        if (gateway.equals("zen")) return new ZenVerifier().verify(body, sig);
        return new AcmeVerifier().verify(body, sig);          // a 3rd gateway silently falls here
    }
}

Why this hurts:

  1. The vendor check is copied into every method. Adding a third gateway means finding and editing every if. Miss one and you get the silent fall-through in onWebhook.
  2. Families can mix. Nothing stops a ZenPay refund being sent through an Acme class. The compiler cannot help, because the choice is a string.
  3. The client knows every concrete class. CheckoutService imports all six vendor classes. It breaks the Open/Closed Principle (open for extension, closed for modification) and the Dependency Inversion Principle (depend on interfaces, not concrete classes).
  4. Tests are painful. To test checkout with a fake gateway you would have to add a fourth branch to production code.

One if on the vendor is fine. The smell is the same if repeated in many places, choosing between groups of classes that must stay together.
