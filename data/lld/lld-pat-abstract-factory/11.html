Interview Q&A

What is the difference between Factory Method and Abstract Factory?

Factory Method makes one product, and the choice is made by inheritance: a subclass overrides createX(). Abstract Factory makes a family of related products, and the choice is made by composition: the client is given a factory object. Each method on an abstract factory is itself a factory method; the pattern groups them so the products stay consistent.

How to answer

One sentence each (one product vs family; inheritance vs composition), then the payment-gateway example, then the cost asymmetry (new family cheap, new kind expensive).

Likely follow-ups
  • Can you build an abstract factory out of factory methods?
  • Which one would you use for a parking lot's vehicle creation? (Usually a simple factory or factory method: one product.)
Design payment-provider support so we can switch providers without touching checkout code.

Define interfaces for each thing that depends on the provider (Charger, Refunder, WebhookVerifier), a GatewayFactory with one method per interface, and one concrete factory per provider. The checkout service gets a GatewayFactory in its constructor. A registry map from config name to factory is the only place that knows providers.

How to answer

Draw the grid (kinds x families), show the client depends only on interfaces, mention dependency injection and testing with a fake factory, then idempotency keys on charge/refund as a bonus.

Likely follow-ups
  • What if we need per-merchant providers at run time? (Look up the factory per request from the merchant's config; factories are stateless, so cache one per provider.)
  • How do you fall back to a second provider when the first is down? (A wrapper factory or a Strategy/Chain on top.)
You need to add a new product kind to every family. What breaks, and how do you limit the damage?

The abstract factory interface gets a new method, so every concrete factory must implement it; that violates Open/Closed for the factories. Ways to soften it: give the new method a default implementation (Java default method) that throws an "unsupported" error; split a fat factory into smaller role-based factories (Interface Segregation); or use a single generic create(Class<T> kind) method backed by a map, which trades compile-time safety for flexibility.

How to answer

Name the asymmetry first, then give two mitigations and their cost.

Likely follow-ups
  • Is the generic create(kind) version still type safe?
How does Abstract Factory help unit testing?

The client depends on one factory interface, so a test passes a FakeGatewayFactory that returns in-memory products (a charger that records calls, a verifier that always says yes). No network, no mocking framework, no test-only branches in production code.

How to answer

Connect it to Dependency Inversion: high-level code depends on an abstraction you can substitute.

Likely follow-ups
  • Would you use a mocking library instead? When?
Should concrete factories be singletons?

Often one instance per family is enough because factories are usually stateless, and GoF mentions this pairing. But do not hard-code a global getInstance(); create one at startup and inject it. You get "only one" without global state, and tests can still pass a fake.

How to answer

Yes in effect, no in mechanism: one instance, owned by the composition root (startup code).

Likely follow-ups
  • What if a factory holds a connection pool? (Then it has state and lifecycle; it must be thread-safe and closed on shutdown.)
Name an Abstract Factory in the JDK and explain why it is one.

java.sql.Connection: it creates Statement, PreparedStatement and CallableStatement objects, all from the same driver, so the family matches. DocumentBuilderFactory and TransformerFactory are also cited: newInstance() locates one implementation and everything you then get comes from it.

How to answer

Name it, say what family it makes, and say what would go wrong if families mixed.

Likely follow-ups
  • Is Calendar.getInstance() an abstract factory? (No: one product, a static factory method.)
Where in systems code have you seen this pattern without the name?

Linux VFS: each file system's superblock creates inodes that carry that file system's inode_operations and file_operations, a consistent family per file system. NIC drivers that support many chip variants keep a per-chip info struct pointing at matching MAC, PHY and NVM ops tables chosen at probe time. Both are tables of function pointers chosen once, then used everywhere.

How to answer

This is where a kernel engineer stands out. Map each GoF participant to the C structure, and say why mixing families would be a real bug (wrong register layout, wrong on-disk format).

Likely follow-ups
  • How is that different from a plain Strategy? (A strategy swaps one behaviour; here several related objects are produced together.)
