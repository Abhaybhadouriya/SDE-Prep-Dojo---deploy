In the interview

Candidates often ask whether an LLD round wants "UML or code" (for example this Amazon SDE-2 thread). The practical answer: a quick class sketch with the right relationships first (3-5 minutes), then code. Use the sketch to agree on ownership before you write fields. Say the relationship out loud as you draw it: "Order composes OrderLine, filled diamond, because lines die with the order".

What is the difference between aggregation and composition?

Both are whole-part associations. In composition the part belongs to one whole only and its lifetime is controlled by the whole: create the order, it creates its lines; delete the order, the lines go. In aggregation the part has its own lifetime and may be shared: a team groups players who existed before it and remain after it. Notation: filled diamond vs hollow diamond, both at the whole's end.

How to answer

Give the one-line rule (lifetime and exclusive ownership), one example of each, and then the code shape: composition creates the part inside and never leaks it; aggregation receives the part from outside.

Likely follow-ups
  • How do you enforce composition in Java, where the GC frees objects?
  • Is Car-Engine composition or aggregation? (Depends on the domain: say which requirement decides.)
How do you tell association from dependency on a diagram and in code?

Association is structural: A keeps a reference to B in a field, so the link lasts. Dependency is transient: A uses B as a parameter, local, return type or static call, then forgets it. Diagram: solid line vs dashed arrow.

How to answer

Use the field test, and add that a dependency on an interface is the shape dependency injection gives you.

Likely follow-ups
  • Constructor injection stores the dependency in a field: is it now an association? (Yes, structurally; many diagrams still show it as a dependency on the interface to stress DIP.)
Why do we need inheritance at all if composition can achieve the same thing?

Use inheritance (generalization) for a true, stable is-a where every child can stand in for the parent (Liskov), and where shared state or a template of steps really belongs in the parent. Use composition for has-a and for behaviour that varies independently, because it can be swapped at runtime and does not couple you to the parent's internals (the fragile base class problem). Interfaces (realization) give polymorphism without inheriting implementation.

How to answer

Do not say "inheritance is bad". Give one case for each: CardPayment extends Payment is fine; Car extends Engine is wrong. Mention class explosion (every combination as a subclass) as the classic sign you need composition.

Likely follow-ups
  • Give an example where composition plus Strategy replaces a subclass tree.
  • How does an interface differ from an abstract class?
Model a many-to-many relationship between Student and Course where each enrolment has a grade.

The grade belongs to the pair, not to either side, so introduce an Enrollment class (an association class): Student 1 — * Enrollment * — 1 Course. Enrollment holds the grade and the date. Students and courses each keep a list of enrolments, or one side keeps it and a repository answers the reverse query.

How to answer

Say "this is the join-table move". Draw the class, then mention which side needs navigation for the use cases (list my courses vs list a course's students).

Likely follow-ups
  • Would you store both directions in memory? What about consistency when one side is updated?
What do the numbers at the ends of a line mean, and where do you write them?

Multiplicity: how many instances of the class at that end can be linked to one instance at the other end. Write it next to the class being counted. "Customer 1 — 0..* Order" reads "one customer has zero or more orders; each order has exactly one customer". On composition, the whole's end is always 1 (or 0..1).

How to answer

Read it out as two sentences, one in each direction. That proves you know which end is which.

Likely follow-ups
  • How does 0..1 show up in code? (A nullable field or an Optional.)
Is a parking lot's ParkingFloor composed or aggregated? And its ParkingSpots? And the Vehicles?

Floors and spots are composition: they are created when the lot is set up, belong to one lot or floor, and have no meaning without it. Vehicles are not parts at all: a spot has a 0..1 association to the vehicle currently parked, and a Ticket associates vehicle, spot and entry time. Vehicles come and go with their own lifetime.

How to answer

Separate static structure (lot, floor, spot) from runtime visitors (vehicle, ticket). Interviewers watch for candidates who "compose" vehicles into spots.

Likely follow-ups
  • Where does the ticket live, and who creates it?
  • How would the spot-to-vehicle link change under concurrency?
How do these relationships show up in a C codebase like the Linux kernel?

Composition is an embedded struct; aggregation is a pointer with a reference count (kref, dev_hold); association is a plain pointer to an object managed elsewhere; realization is filling an ops table like file_operations; generalization is embedding a base struct and using container_of; dependency is a function argument that is not stored.

How to answer

Use it to show depth: you understand that UML lines are about lifetime and coupling, not about a language feature.

Likely follow-ups
  • What goes wrong if an aggregated object is freed while the whole still points at it? (Use-after-free: the reason refcounts exist.)
How much UML should you draw in a 45-minute LLD round?

Boxes for the core entities with a few key fields and methods, the relationships that carry design meaning (ownership, inheritance, interfaces you depend on), and multiplicities on the important associations. Skip getters, setters and trivial dependencies. Then move to code.

How to answer

State the plan to the interviewer: "a 3-minute class sketch to agree on entities and ownership, then code". It shows time control.

Likely follow-ups
  • Which other diagram would you add, and when? (A sequence diagram for a tricky flow, a state diagram for a lifecycle.)

Scenario: "Library: Book, BookCopy, Member, Loan"

The interviewer asks you to draw the relationships for a library where a book title has several physical copies, members borrow copies, and every borrow is recorded.
Weak answer: Member aggregates Book; Book composes Member's loans; draws inheritance from Book to BookCopy "because a copy is a book".
Strong answer: Book (title, ISBN) ◆— 1..* BookCopy (barcode), because copies are created for a title and deleted with it in this system. Loan is its own class: Loan * — 1 Member and Loan * — 1 BookCopy, with dates. Member and BookCopy have independent lifetimes, so plain associations. BookCopy is not a subclass of Book: a copy is an instance of a title, not a kind of title.
Follow-ups: where do you check "max 5 active loans"? (On Member or a LoanService, with a query over active loans.) Would you ever make Book ◇ BookCopy aggregation? (If copies can be transferred between catalog entries.)
