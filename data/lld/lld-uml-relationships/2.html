Association: "A knows B"

An association is the plain solid line. It says objects of one class hold a long-lived link to objects of the other: usually a field with a reference (or an id). The two objects were not born together and do not die together. A Customer knows its Orders; an Order knows its Customer. Deleting a customer account does not have to delete the order records (finance needs them), and an order cannot "create" a customer.

Three decorations make an association precise:

  • Multiplicity: how many on each end. 1, 0..1, * (same as 0..*), 1..*. Write the number next to the class it counts. "One customer has zero or more orders" puts 1 next to Customer and 0..* next to Order.
  • Navigability: an open arrowhead means "you can get from here to there". No arrow on either end is read as "not decided" or "both ways". In code, the arrow points from the class that has the field to the class it refers to.
  • Role name: a label near the end, like buyer or items. It often becomes the field name.
class Customer {
    private final List<Order> orders = new ArrayList<>();   // 1 -- 0..*
    Order placeOrder(String id) { Order o = new Order(id, this); orders.add(o); return o; }
}
class Order {
    private final Customer customer;   // the other end of the same association
    Order(String id, Customer c) { this.customer = c; }
}

Many-to-many with data becomes a class. If a Student-Course link needs a grade or an enrolment date, that data belongs to neither end. Promote the line to an association class (or just a plain class) called Enrollment. Interviewers like it when you spot this, because it is the same move as a join table in SQL.
