Generalization and realization: is-a and can-do

Generalization is inheritance. The child "is a kind of" the parent: a CardPayment is a Payment. Draw a solid line with a hollow triangle at the parent. Put the parent on top and the children below, so the triangles point up.

Realization is implementing an interface. EmailNotifier promises to do what Notifier describes. Same triangle, but a dashed line, and the interface box carries the keyword «interface» above its name. Abstract classes and abstract methods are written in italics (or tagged {abstract} on a whiteboard, where italics are hard).

abstract class Payment { protected final long amount; abstract Result pay(); }
final class CardPayment extends Payment { Result pay() { /* charge card */ } }   // generalization

interface Notifier { void send(String to, String msg); }
final class EmailNotifier implements Notifier { public void send(String to, String msg) { /* SMTP */ } }  // realization

Do not draw a triangle for "has a". If you catch yourself drawing Car inheriting from Engine so the car "gets" the engine's methods, stop. A car is not an engine. That is composition plus delegation. Walmart has asked exactly this ("why inheritance if composition can do it?", LeetCode post); Composition over Inheritance covers the full argument.
