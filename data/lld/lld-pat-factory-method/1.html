The problem: a workflow that must create things it cannot know

A notification service sends order updates. Every send follows the same steps: build the channel, format the message, send it, record the result. The first version puts a switch in the middle of that workflow:

class NotificationService {
    String notifyUser(String channelType, String user, String msg) {
        Channel ch;
        switch (channelType) {                 // creation tangled into the workflow
            case "email" -> ch = new EmailChannel(smtpHost, port);
            case "sms"   -> ch = new SmsChannel(twilioKey);
            case "push"  -> ch = new PushChannel(fcmKey);
            default      -> throw new IllegalArgumentException(channelType);
        }
        String body = channelType.equals("email") ? "Hi,\n" + msg : msg;   // and a second switch...
        boolean ok = ch.send(user, body);
        audit(channelType, ok);
        return ok ? "sent" : "failed";
    }
}

What hurts:

  • The workflow is edited for every new channel. WhatsApp means touching notifyUser, the place that holds the audit and retry logic you most want to keep stable.
  • Per-channel rules leak in as more switches (formatting here; later, retries, rate limits). They spread through the method.
  • A library cannot be extended by its users. If NotificationService ships in a shared library (a jar in Java, a .so in C), another team cannot add a channel without forking it. Compare a kernel subsystem that lets an out-of-tree module register a new driver without patching the core: that is the property we want.
  • The class knows every concrete channel and its config (SMTP host, API keys): many reasons to change, which breaks the Single Responsibility Principle.

A Simple Factory would move the switch out, which is already better. Factory Method goes further: the workflow lives in a base class, and each subclass supplies its own product. There is no switch anywhere.
