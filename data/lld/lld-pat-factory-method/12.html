Interview questions

What is the Factory Method pattern? Explain with an example.

A creator class declares an overridable method that returns a product interface, and its own logic calls that method. Subclasses override it to return a concrete product. Example: Notifier.notifyUser() calls createChannel(); SmsNotifier returns an SmsChannel. The workflow never names a concrete channel.

How to answer

Give the one-line definition, draw the two hierarchies (creators, products), and point out that the base class uses the product.

Likely follow-ups
  • Why is it called a "method"?
  • Where in the JDK have you seen it?
Factory Method vs Abstract Factory vs Simple Factory?

Simple Factory: one function chooses a class from a key; not GoF. Factory Method: a subclass chooses by overriding one method; one product. Abstract Factory: an object with several creation methods that makes a matching family (all Windows widgets or all Mac widgets); you swap the whole family by swapping the factory object.

How to answer

Use "key / subclass / family" as the three hook words, and give one example for each. Mention that Abstract Factory methods are often factory methods.

Likely follow-ups
  • Which one would you use in a parking lot? (Usually Simple Factory for vehicles and spots; say why.)
  • How do you add a new product kind to an Abstract Factory? (Every factory must change - its weak spot.)
How does Factory Method support the Open/Closed and Dependency Inversion principles?

Open/Closed: new products arrive as new subclasses; the tested workflow in the base class is not edited. Dependency Inversion: the high-level workflow depends on the Channel abstraction, and the low-level concrete channels also depend on (implement) it. Neither depends on the other directly.

How to answer

Point at the class diagram: no arrow from Notifier to SmsChannel.

Likely follow-ups
  • Where does the choice of SmsNotifier happen then? (Composition root: main, config, DI container.)
Your design has one creator subclass per product. Isn't that too many classes?

It can be. If creators differ only in what they create, replace inheritance with composition: pass a Supplier<Channel> (Java), a callable (Python) or a std::function (C++) into one Notifier. If the choice comes from data, use a registry map. Keep subclasses when they also override other hooks (formatting, retries), because then the subclass carries real behaviour.

How to answer

Agree, give the lambda refactor, state the rule for when subclasses are still worth it.

Likely follow-ups
  • Is the injected supplier still "Factory Method"? (It is the same intent implemented with composition; many call it a creation strategy.)
Can you call the factory method from the base class constructor?

Avoid it. In C++ the object is still the base type while the base constructor runs, so the virtual call does not reach the subclass override; calling a pure virtual function there is undefined behaviour and typically aborts. In Java the call does reach the override, but the subclass's fields are not initialised yet, so the override may see null config. Create lazily on first use, or call it from a normal method or an init() step after construction.

How to answer

State the language difference precisely; it signals real experience.

Likely follow-ups
  • How would you make lazy creation thread-safe? (Double-checked locking or holder idiom; see Singleton.)
Design ride types (Mini, Sedan, Auto) so a new type needs no change to booking code.

Booking code depends on RideType with a factory method createFareCalculator() (and maybe createVehicleMatcher()). The base RideType.quote(trip) calls it and adds shared parts (surge, taxes). MiniRide, SedanRide, AutoRide override it. A registry maps the ride type key from the app to the creator instance. New type = new subclass + one registry line.

How to answer

Show the workflow in the base, the hook, and where the key is mapped. Note that the fare calculator is itself a Strategy.

Likely follow-ups
  • If two hooks must always match (fare + vehicle class), is this becoming an Abstract Factory? (Yes - say it.)
Give a real example of Factory Method outside textbook code.

Iterable.iterator() in Java: the for-each loop is generic, and each collection returns its own iterator class that understands its internals. In Python, __iter__ is the same. In Linux, super_operations->alloc_inode lets each file system allocate its own inode struct while the VFS runs the generic workflow. (net_proto_family->create, looked up by family number at socket(2) time, is the registry cousin of the same idea.)

How to answer

One JDK example plus one from your own background. For this reader, the kernel example is a strong, honest story.

Likely follow-ups
  • Is Calendar.getInstance() a Factory Method? (No - it is a static factory, closer to Simple Factory.)
How do you unit-test a class that uses Factory Method?

Create a test subclass whose factory method returns a fake product (a FakeChannel that records calls), then assert on the workflow: was send called once, with the formatted body, and was the failure path handled. This is one of the pattern's hidden benefits: the override is a natural seam for tests. With the supplier variant, just pass () -> fake.

How to answer

Name the seam, describe the fake, list two assertions.

Likely follow-ups
  • Would you mock with Mockito instead? (Fine; a hand-written fake is clearer for a workflow test.)
