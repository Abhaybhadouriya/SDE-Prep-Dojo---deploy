Concurrency and thread safety

Unlike a booking system, there is no scarce seat here. The shared state that breaks is counters derived from events: a post's votes and a user's reputation. Two races matter.

Race 1: one user, many clicks

A double-click sends two "upvote" requests. Without a lock both read "no vote yet" and both count. With the post's lock around "read old vote, write new vote, apply deltas", the second request finds UP already there and is rejected. The demo fires 20 parallel votes from one user: score 1, 19 rejections.

Race 2: many users, one post, one author

100 different voters upvote the same answer. The per-post lock serialises the vote map; the author's reputation is an AtomicInteger updated with updateAndGet(r -> max(1, r + d)), a lock-free compare-and-swap loop. Result: score 100, reputation exactly 1 + 1000.

From your world

This is the classic split between a per-object spinlock and an atomic_t statistic. The vote map needs the lock because it is a compound update (check then write two things). The reputation is a single integer, so an atomic add is enough, the way per-device packet counters use atomics instead of the device lock. Never hold the post lock while waiting on a user lock and the reverse elsewhere: here we never hold two locks at once, so no lock order is needed.

What is only eventually consistent (say it)

  • A feed or search running during a vote may see the old score. That is fine for a feed.
  • Reputation can briefly lag a score by one update across two posts. Nothing checks them against each other atomically.
  • A privilege check (rep >= 15) runs before the post lock; a user at exactly 15 who is downvoted at that instant may cast one more vote. Real sites accept this; a strict version re-checks under the lock.

At scale, votes become an append-only event stream and scores and reputation are aggregated asynchronously, like the Reddit / Quora HLD design. In-memory, locks and atomics are the right size. More on the toolbox: locks and concurrent collections.
