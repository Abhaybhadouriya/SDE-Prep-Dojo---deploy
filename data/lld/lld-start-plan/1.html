How the plan works

The plan assumes about 2 to 3 hours on a weekday and 4 hours on a weekend day. Each day has three parts: read, build, recall. Reading alone feels productive but does not stick. Building a small program, even 60 lines, is what turns "I know Observer" into "I can write Observer in five minutes with an interviewer watching".

  1. Read. Two or three pages from the day's list. Every page in this module climbs from a Level-1 story to interview depth, so read in order and do not skip the "From your world" boxes; they map each idea to kernel code you already know.
  2. Build. Write the day's pattern or case in your interview language, from a blank file, without looking. Then compare with the page's code. Every case-study page ships a runnable driver; make yours print the same output.
  3. Recall. Do the page quiz and answer two interview questions out loud, as if to an interviewer. Speaking the answer is a different skill from knowing it.
  4. Log. One line per weak spot in a text file: "forgot that Observer needs unsubscribe", "my ParkingLot class did too much". Re-read the log the next morning.

Pick one interview language now. Java is the safest default for LLD: most interviewers, books and reference solutions use it, and interface, enum and java.util.concurrent make designs short. C++ is fine if you are fluent (pages show it in tabs), and Python is accepted at many companies but makes interfaces and access control less visible. The first OOP pages show C, Java and C++ side by side so you can decide.
