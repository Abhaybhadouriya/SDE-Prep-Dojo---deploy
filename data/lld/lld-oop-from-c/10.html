Interview questions

What are the four pillars of OOP? Explain each with an example from your work.

Encapsulation: keep state private and change it only through operations that protect its rules; a driver's ring indices are touched only by its own push/pop. Abstraction: callers see what an object does, not how; the network stack sees ndo_start_xmit, not DMA descriptors. Inheritance: a specific type reuses a general one's data and contract; every driver's private struct embeds struct net_device. Polymorphism: one call, behaviour chosen by the actual object; dev->netdev_ops->ndo_start_xmit(skb, dev) runs e1000 code or virtio code depending on the device.

How to answer

One sentence of definition, one concrete example each. Kernel examples are memorable and show real experience; then translate one into Java to show you know the syntax.

Likely follow-ups
  • Abstraction vs encapsulation: what is the difference?
  • Is inheritance needed for polymorphism? (No: interfaces give it without data inheritance.)
How does a virtual function call work under the hood?

Each polymorphic class has one vtable, an array of function pointers, built by the compiler. Each object has a hidden vptr pointing to its class's vtable, set by the constructor. A virtual call loads the vptr from the object, loads the slot at a fixed index, and makes an indirect call passing this. It is the same as dev->ops->xmit(dev, ...) in C. In C++ the base class needs a virtual destructor if you delete through a base pointer, otherwise only the base part is destroyed. Java does the equivalent with per-class method tables, and its JIT often inlines calls that have only one target in practice.

How to answer

Draw the object, the vptr arrow and the table. Mention the cost (two loads + indirect branch) and the virtual-destructor rule.

Likely follow-ups
  • What happens if you call a virtual function from a constructor in C++?
  • Where is the vptr with multiple inheritance?
How would you implement polymorphism in plain C?

Define a struct of function pointers for the operations, with the object pointer as the first parameter. Give the base struct a pointer to a const instance of that table. Each "subclass" embeds the base struct and defines its own functions and its own const table; it uses container_of to get from the base pointer back to itself. Generic code calls obj->ops->fn(obj, ...). Optional operations are NULL with a default in the caller, or better, explicit default functions. The Linux VFS (file_operations) and network stack (net_device_ops) are large working examples.

How to answer

Write the two structs and one call on the board. Then say what C++ automates: the table, the pointer, this, and the compile-time check that every slot is filled.

Likely follow-ups
  • Why keep the table separate instead of putting function pointers in each object?
  • How do you do "super" calls in this scheme?
Why put the function pointers in a shared table instead of directly in each object?

Memory and safety. A table is shared by every object of a type, so a million objects pay one pointer each instead of one pointer per method. The table can be const and live in read-only memory, so a stray write cannot redirect a method. And "type" becomes one comparable value. Per-object function pointers make sense when there are few objects or each one needs its own behaviour; the kernel does that for some structures like struct sock's callbacks.

How to answer

Give the memory argument with a number (N objects x M methods vs N pointers), then the read-only argument, then the exception.

Likely follow-ups
  • Which design pattern is "per-object function pointer"? (Strategy, held by composition.)
Compare kref, std::shared_ptr and Java garbage collection.

All three answer "when is it safe to free?". kref is a manual atomic count with a release callback: precise and cheap, but every get must be matched by a put on every path. shared_ptr does the same counting automatically on copy and destruction (atomically, so copies across threads are safe), frees deterministically at the last release, and leaks on cycles unless one side is a weak_ptr. Java's GC traces reachable objects from roots, so there is no count to get wrong and cycles are fine, but freeing time is not deterministic, and non-memory resources still need close().

How to answer

Same question, three answers, one trade-off each: precision vs effort vs determinism.

Likely follow-ups
  • When would you use unique_ptr instead?
  • How do you handle a socket in Java so it is always closed?
The kernel uses OOP ideas in C. Why not write the design in C in an LLD round?

Because the round grades the design, and an OO language states the design directly: interfaces, access control, constructors and generics are visible in the code instead of being conventions. In C the reviewer must trust that every table is filled, every container_of is right and every get has a put. I would bring the C intuition (ownership, cost of indirection, locking) and write it in Java or C++, naming the kernel parallel when it clarifies a choice.

How to answer

Shows judgment: right tool for the audience, and you know both worlds.
