The C habit to unlearn: switching on a type

The most common mistake C engineers make in LLD interviews is a type field plus a switch. It works, but every new type edits every switch. The ops-table habit you already use in the kernel is the cure: put the behaviour behind an interface. This is the Open/Closed Principle: open to new types, closed to editing old code.

From your world

You would never patch vfs_read() with a switch on the filesystem type; you register a new file_operations. Same rule here: a new kind of thing is a new class that fills the interface, and the generic code does not change.

enum DevType { LOOPBACK, RING }

class Device {
    DevType type;
    int looped;            // only used by LOOPBACK
    Deque<String> ring;    // only used by RING

    boolean xmit(String pkt) {
        switch (type) {    // every new device type edits this method,
            case LOOPBACK: looped++; return true;          // and open(), and stop()...
            case RING:     if (ring.size() == 4) return false; ring.add(pkt); return true;
            default:       throw new IllegalStateException();
        }
    }
}
interface NetDevice { void open(); boolean xmit(String pkt); default void stop() {} }

final class LoopbackDevice implements NetDevice {
    private int looped;
    public void open() {}
    public boolean xmit(String pkt) { looped++; return true; }
}

final class RingDevice implements NetDevice {
    private final Deque<String> ring = new ArrayDeque<>();
    public void open() { ring.clear(); }
    public boolean xmit(String pkt) { if (ring.size() == 4) return false; ring.add(pkt); return true; }
}
// A new device = one new class. No existing file changes.

A switch on an enum is still fine when the set of cases is closed and small and the behaviour is data-like (for example mapping a vehicle size to a parking-spot size). Use polymorphism when each case has its own behaviour that will grow.
