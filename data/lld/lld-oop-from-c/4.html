Inheritance of data: embedding and container_of

Behaviour comes from the ops table. Data comes from embedding: a specific device puts the generic struct net_dev inside itself and adds its own fields. Generic code is handed a pointer to the embedded part; the driver gets back to its full struct with container_of, which subtracts the member's offset from the pointer.

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

struct loopback_dev {
    struct net_dev base;        /* "extends net_dev" */
    int looped;                 /* subclass-only field */
};

static int lo_xmit(struct net_dev *dev, const char *pkt)
{
    struct loopback_dev *lo = container_of(dev, struct loopback_dev, base);  /* downcast */
    lo->looped++;
    return 0;
}

In Java and C++ this is class inheritance: class LoopbackDevice extends BaseDevice. The compiler lays out the base fields first and the subclass fields after (C++ guarantees a base subobject; Java's layout is the JVM's business). Inside a method, this already points at the full object, so no container_of is needed. When you do need a downcast, C++ has dynamic_cast (checked at run time, returns nullptr on failure) and Java has a cast that throws ClassCastException if wrong. container_of has no check at all: hand it the wrong pointer and you get silent memory corruption.

From your world

The kernel also has a second way: a void *private pointer to a separately allocated struct (i_private, s_fs_info, netdev_priv() area). LWN part 2 explains why embedding is usually preferred: one allocation, one fewer pointer hop, and type safety through container_of. Java has no embedding; every field that is an object is a reference, which is closer to the void *private style. That is fine because the JVM allocator and garbage collector make small allocations cheap.
