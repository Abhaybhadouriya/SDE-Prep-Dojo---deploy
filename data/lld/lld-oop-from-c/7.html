kref and shared ownership

Who frees an object when several parts of the system hold it? In the kernel the answer is a reference count: kref_get when you take a pointer you will keep, kref_put when you drop it, and the last put calls a release function. The object lives exactly as long as someone needs it.

What the languages take off your plate
  • C++ shared_ptr: get/put happen on copy/destroy, so you cannot forget a put on an error path.
  • C++ RAII: any resource (lock, file, socket) is released in a destructor when the owner leaves scope, like a scoped guard or goto out unwinding done by the compiler.
  • Java GC: no counts at all, and reference cycles are collected too.
What they do not solve
  • shared_ptr cycles leak; break them with weak_ptr (like a non-counted back pointer).
  • GC frees memory, not sockets or file handles: use try-with-resources and close().
  • In both, you still have to decide who owns what. LLD interviewers ask exactly that ("who creates the Ticket? who can delete it?").

Ownership in class diagrams is drawn as composition (filled diamond: the part dies with the whole) or aggregation (hollow diamond: the part can outlive it). Both are covered on Class Relationships.
