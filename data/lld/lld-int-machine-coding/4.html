Checkpoints: always have a runnable version

A checkpoint is a moment where the code compiles, the driver runs, and you save a copy. The rule we use on every interview page: compile and run after every feature, and never go more than 10-15 minutes without doing it. If the next 15 minutes go wrong, you fall back to it. One PhonePe candidate's advice was to compile side by side as you go so the end has no surprises (post 3671731 (2023-06-23, older post)); an Atlassian candidate lost minutes to typos and IDE auto-complete (post 8293408 (2026-05-25)).

  1. Pick exactly one P0 feature from your checklist. Not two.
  2. Write the service method and its validation (unknown id, wrong state) with your custom exception.
  3. Add one or two driver lines that call it: one happy path, one failure.
  4. Compile and run the whole driver. If it fails, fix it now or revert; never stack a second feature on a broken build.
  5. Commit (git commit -am "cancel order") or copy the file. This is your fallback.
  6. Tick the feature off and loop. Five or six loops cover most P0 lists.
$ git init -q && git add -A && git commit -qm "skeleton runs"
$ javac -d out src/*.java && java -cp out Main     # after every feature
$ git commit -qam "P0-3 assign with waiting queue"

If git is not available (browser editors), keep a second tab or a copy of the file named Main_cp3.java. The point is a known-good state you can return to in one step.
