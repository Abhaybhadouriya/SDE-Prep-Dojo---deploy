The demo and the evaluation call

After you submit, an engineer runs your code and talks to you - in the same session (Flipkart often about an hour later, post 5221179 (2024-05-28, older post)) or 1-2 days later (PhonePe, post 3671731 (2023-06-23, older post)). Some calls add a new feature live (post 5241117 (2024-06-01)). Here is how a typical call flows and what to say at each step.

  1. The evaluator runs your driver (and maybe their own commands). Give them a one-line run command. A crash here is the worst outcome of the whole round.
  2. Give a 2-minute tour: "Entities here, one service per area, repositories are maps behind interfaces, the driver is a command table. P0 1-6 done, bonus 1 done, bonus 2 not done."
  3. They ask why. Answer with the requirement: "Assignment has two policies in the doc, so it is a Strategy." If a pattern was not needed, say so - forced patterns are a known red flag.
  4. They ask for a change. Point to the one place it goes (a new Strategy class, a new command line). If coding live, add a driver line first, then the code.
  5. Production questions: which store (swap the repository), which parts become services, what state is shared and how you lock it (item vs restaurant level, optimistic vs pessimistic, as in post 8411392 (2026-07-21)).
Question you will hearAnswer shape
"Walk me through your code."Layers top-down in 2 minutes; what is done and what is not. Do not read code line by line.
"Where would you use interfaces?"Wherever the doc lists several kinds of something, and for storage (repository) so a DB can replace the map.
"How do you add a real database?"New repository implementation; services do not change; transactions around the multi-step operations.
"Two users book the last item at once?"Name the check-then-act, the lock and its granularity, or a versioned (optimistic) update; show your race test.
"What would you refactor with more time?"Have two honest answers ready (a coarse lock, a growing switch). Self-awareness scores.
