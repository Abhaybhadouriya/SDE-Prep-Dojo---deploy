In interviews

"Design a connection pool" is a classic machine-coding and senior-round question because it combines a creational pattern with real concurrency. A good answer covers, in this order: the API (acquire(timeout), a closeable handle), the data structures (idle queue, in-use set, a semaphore or lock plus condition), the full-pool policy, validation and reset, leak detection, and metrics (active, idle, waiting, wait time). Where pools appear in our case studies:

  • Parking lot: spots are a bounded pool; park is acquire, leave is release, "lot full" is the fail-fast policy.
  • Amazon locker: lockers by size are pools; a parcel never collected is a leak handled by an expiry job.
  • Car rental and hotel booking: a fleet or room inventory per type, with reservations as time-bounded leases.
  • Rate limiter: a semaphore of permits is a pool of nothing but tokens.
  • Task scheduler and logger: worker threads and reusable buffers.

Concurrency details for the coding part: producer-consumer (the blocking queue underneath) and thread pool.

Strong 30-second answer: "An object pool keeps expensive objects ready and lends them out exclusively. Clients acquire with a timeout and release through a closeable handle, so try-with-resources guarantees return. The pool bounds the total with a semaphore, validates and resets objects between users, and reports leases held too long. Use it for connections, threads and big buffers, not for cheap objects. The kernel's slab caches and mempool are the same idea."

Scenario: the service hangs every afternoon

A Java service with a pool of 10 connections stops answering around 3 pm. CPU is idle, the database is healthy, and thread dumps show 200 threads waiting in getConnection().
Weak answer: "Raise the pool to 100."
Strong answer: "Idle CPU plus threads parked in acquire means the pool is drained, not overloaded. Most likely a code path borrows a connection and does not return it on an error branch, so the pool loses one connection per failure until it is empty. I would turn on leak detection with a threshold just above our slowest normal query to get the stack trace of the borrower, fix that path with try-with-resources, and set a connection timeout so callers fail with an error instead of hanging. A bigger pool would only delay the outage."
Likely follow-ups
  • How do you size the pool properly?
  • Which metrics would have warned you earlier? (Active count climbing while traffic is flat; wait time.)
