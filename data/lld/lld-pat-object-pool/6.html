The kernel's pools: slab, mempool, page_pool

From your world

The kernel is full of object pools, each tuned for a different promise:

  • Slab caches (kmem_cache_create, kmem_cache_alloc, kmem_cache_free): a pool per object type. Freed objects go back on a per-cache (and per-CPU) free list, so the next alloc is cheap and cache-hot. The optional constructor runs when slab memory is first set up, not on every alloc, which is exactly the pool idea of "initialise once, reuse many times". SLAB_HWCACHE_ALIGN and per-CPU lists answer the "pool becomes a contention point" problem that user-space pools also face.
  • mempool_t (mempool_create, mempool_alloc, mempool_free): wraps an allocator and keeps min_nr elements in reserve. When normal allocation fails, it hands out a reserved element; if the reserve is empty and the caller may sleep, it waits for someone to call mempool_free. That is a bounded blocking pool whose purpose is forward progress: the block layer needs memory to write dirty pages, which is how memory gets freed.
  • page_pool in network drivers: recycles RX pages so a NIC driver does not go to the page allocator for every received packet.
  • Pre-allocation outside locks: radix_tree_preload() fills a small per-CPU pool before taking a spinlock, so the insert under the lock cannot fail. LWN's kernel design patterns series calls this out as a pattern.
