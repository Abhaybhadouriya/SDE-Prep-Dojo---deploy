Interview Q&A

What is the Object Pool pattern and when would you use it?

A creational pattern that keeps initialised objects ready, lends each to one client at a time and takes it back for reuse. Use it when creation is expensive compared with use (connections, threads, big buffers) and when you need a hard limit on how many exist, to protect the resource behind them.

How to answer

Give the two motives, reuse and bound, then one example of each.

Likely follow-ups
  • Why is it not in the GoF book?
  • Pool vs cache?
Design a thread-safe, bounded connection pool. What happens when it is exhausted?

State: an idle queue, a set of active leases, and a fair semaphore with max permits. acquire(timeout) takes a permit with tryAcquire(timeout); if it fails, throw a timeout error. With a permit, pop an idle connection and validate it, or create a new one if none is idle; if creation throws, release the permit. Return a Lease whose close() resets the connection, pushes it back and releases the permit. When exhausted, callers wait up to the timeout and then fail; never wait forever.

How to answer

Draw the three data structures, write acquire and release, then state the exhaustion policy and why a timeout matters.

Likely follow-ups
  • Why a fair semaphore? (No starvation of early waiters.)
  • How would you shrink idle connections at night?
How do you detect and prevent leaks from a pool?

Prevent: hand out a closeable handle and require try-with-resources, with or RAII, so release happens on every path. Detect: record borrow time and borrower (thread, and optionally a stack trace) per lease and report any lease held longer than a threshold, as HikariCP's leak detection does; optionally reclaim abandoned objects after a longer limit. Also alert when the active count stays at max while traffic is flat.

How to answer

Split prevention (API design) from detection (bookkeeping), then give the metric.

Likely follow-ups
  • Is forcibly reclaiming an abandoned connection safe? (Only if the old holder can no longer use it; otherwise you get two users.)
  • Do real pools reclaim? (HikariCP's leakDetectionThreshold only logs a warning with the borrower's stack; Apache DBCP's removeAbandoned settings forcibly take the connection back. Our demo, like Hikari, only reports.)
Object Pool vs Flyweight: both reuse objects. What is the difference?

Flyweight shares immutable objects among many clients at the same time; nothing is borrowed or returned. A pool lends mutable objects exclusively, one client at a time, and resets them between clients. Integer cache: Flyweight. Connection pool: Object Pool.

How to answer

Two words: shared-immutable vs exclusive-mutable.

Likely follow-ups
  • Which one needs a release method?
Where does the Linux kernel use object pools?

Slab caches (kmem_cache_create and friends) pool same-size objects with per-CPU free lists. mempool_t keeps a minimum reserve so allocations on the I/O path make progress under memory pressure, and a sleeping mempool_alloc waits for an element to be freed. Network drivers use page_pool to recycle RX pages. Radix-tree preloading fills a small per-CPU pool before taking a spinlock.

How to answer

Name the API and the promise each one makes (speed, guaranteed progress, recycling).

Likely follow-ups
  • Why can a mempool not just use a bigger slab cache? (A cache can still fail; the reserve is what guarantees progress.)
Is pooling small objects in Java a good idea today?

Usually not. Generational garbage collectors allocate short-lived objects very cheaply, and a pool adds synchronisation, keeps objects alive longer (moving them into the old generation) and risks dirty state. Pool when the cost is outside the heap (sockets, threads, native or direct buffers) or when you need a hard bound. Measure before and after.

How to answer

Say "it depends on where the cost is", then give the GC argument and the exceptions.

Likely follow-ups
  • Why does Netty still pool buffers? (Direct memory is expensive to allocate and free.)
How do you choose the pool size?

Start from the bottleneck behind the pool, not from the number of client threads. For a database, true parallelism is limited by its cores and disks, so a small pool often gives better throughput than a large one; HikariCP's sizing notes make this argument. Also respect the server's connection limit divided across all service instances. Then load-test and watch wait time and active count.

How to answer

Bottleneck first, global limit second, measurement last.

Likely follow-ups
  • 50 pods, each with pool size 20, database limit 500: what breaks?
