How it works: one acquire and one release

  1. Client A calls acquire(). An idle connection exists, so the pool moves it to the in-use set and returns a Lease. Cost: a queue pop, not a handshake.
  2. A uses the connection. Meanwhile another client (C) holds conn-2, so the pool is fully lent out.
  3. Client B calls acquire(2s). Nothing is idle and the pool is at max, so B blocks on the pool's semaphore or condition variable. It will give up with a timeout after 2 seconds.
  4. A finishes; the try-with-resources block calls close(). The pool validates the connection (still alive?) and resets it (roll back any open transaction, clear session variables).
  5. Releasing signals the waiter. B wakes up and gets conn-1. The database saw two clients served with zero new connections.

The three policy questions every pool answers, and that interviewers love to ask:

QuestionCommon choices
Pool is empty but below max?Create lazily (grow) or pre-fill at start (minIdle, warm-up).
Pool is empty and at max?Block until free; block with a timeout (most common); fail fast; or grow past max temporarily (rarely wise).
Object comes back?Validate (on borrow, on return, or periodically in the background), reset state, then push to the idle list. If broken, destroy it and let the pool create a replacement.
Object has been idle a long time?Evict it to shrink the pool (idle timeout), and retire very old ones (max lifetime) before the server closes them on you.
