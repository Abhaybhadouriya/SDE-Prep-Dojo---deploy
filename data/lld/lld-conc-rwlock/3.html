The rules that trip people up

  • Reentrant. A thread holding the read lock may take it again; the same is true for the write lock. A writer may also take the read lock.
  • Downgrade is allowed: take the write lock, take the read lock, release the write lock. You keep reading what you just wrote, and no other writer can slip in between.
  • Upgrade is not allowed. Holding the read lock and calling writeLock().lock() blocks forever: the writer waits for all readers to leave, including you. If two readers both try to upgrade, each waits for the other. Our demo used tryLock(200 ms) to show that the write lock is never granted. Fix: release the read lock, take the write lock, then re-check the condition, because the world may have changed in the gap.
  • Only the write lock has Conditions. readLock().newCondition() throws UnsupportedOperationException.
  • Limits. The state is one 32-bit word: 16 bits for read holds and 16 for write holds, so at most 65,535 of each.
// Cache fill with a downgrade: check under read, fill under write, keep reading under read.
V getOrLoad(K k) {
    r.lock();
    try { V v = map.get(k); if (v != null) return v; } finally { r.unlock(); }
    w.lock();                                   // NOT an upgrade: the read lock was released first
    V v;
    try {
        v = map.get(k);                         // re-check: another thread may have loaded it
        if (v == null) { v = loader.load(k); map.put(k, v); }
        r.lock();                               // downgrade: take read before releasing write
    } finally {
        w.unlock();
    }
    try { return render(v); }                   // still under the read lock: no writer can change k yet
    finally { r.unlock(); }
}

Loading inside the write lock blocks every reader of the whole cache for the length of a database call. For a slow loader, use ConcurrentHashMap.computeIfAbsent, which only blocks callers of that one key, or a per-key future (see Concurrent Collections).
