Interview Q&A

When would you use a ReadWriteLock instead of synchronized?

When reads far outnumber writes, the read section does real work, and readers would otherwise queue behind each other. Readers then run in parallel and writers get exclusive access. If reads are tiny (one map lookup) or writes are frequent, the extra bookkeeping can make it slower than a plain lock. If the data is a map, a ConcurrentHashMap is usually better.

How to answer

Give the read/write compatibility rule, the conditions where it wins, and one case where it loses.

Likely follow-ups
  • Why can it be slower? (Readers still CAS one shared count.)
Can you upgrade a read lock to a write lock in ReentrantReadWriteLock?

No. The writer waits for all readers to leave, including itself, so it blocks forever, and two upgrading readers deadlock each other. Release the read lock, take the write lock and re-check the condition. Downgrading (write, then read, then release write) is allowed. StampedLock offers tryConvertToWriteLock, which succeeds only when it is safe.

How to answer

Say no, explain why in one sentence, then show release-reacquire-recheck.

Likely follow-ups
  • Why the re-check? (Another writer may have done the work in the gap.)
What is writer starvation and how do locks prevent it?

If new readers may enter while a writer waits, overlapping reads keep the lock busy forever and the writer never runs. Writer-preferring locks block new readers once a writer is queued. Java's nonfair RRWL blocks a new reader if the head of the queue is a writer; fair mode serves in arrival order. Readers can starve too, under writer preference with constant writes. Fair mode bounds both.

How to answer

Draw the R1, R2, W, R3 timeline and say who waits in each policy.

Likely follow-ups
  • Which policy suits a config store? (Writer-preferring or fair; updates must land promptly.)
How does a StampedLock optimistic read work, and what are its dangers?

tryOptimisticRead returns a version stamp without locking. You copy fields into locals, then validate(stamp) checks that no write happened since. If one did, you take a real read lock and re-read. Dangers: values may be inconsistent before validation, so never dereference or index with them first; the lock is not reentrant; there are no Conditions.

How to answer

Write the five-line read method, then list the three rules.

Likely follow-ups
  • What is the kernel equivalent? (seqlock: read_seqbegin / read_seqretry.)
Design a thread-safe configuration service read on every request and updated a few times a day.

Keep an immutable Config snapshot behind an AtomicReference (or a volatile field with a single writer). Requests call current.get() once and use that snapshot for the whole request, so every flag they read is consistent. An updater thread polls or receives a push, validates the new config, builds a new immutable object and swaps it in, then notifies listeners held in a CopyOnWriteArrayList. Rollback is swapping the previous version back. Reads never lock.

How to answer

Start with the RW-lock version, then say why the snapshot is better (wait-free reads, consistency per request), and name RCU as the kernel's version.

Likely follow-ups
  • Two admins update at once? (CAS with updateAndGet, or serialise writers with a lock.)
  • Huge config? (Split into independent snapshots per area.)
Seqlock vs RCU: when does each fit?

Seqlock: small plain data, copied whole, where the writer must never wait. Readers retry when a write overlaps. It cannot protect pointers that may be freed. RCU: linked or pointer-rich data (lists, trees, tables). Readers follow pointers with no retry, writers publish a new version, and old versions are freed after a grace period. RCU readers may see the old version for a while, so it fits data where slightly stale is fine.

How to answer

Compare by data shape (plain vs pointers) and reader behaviour (retry vs stale but stable).

Likely follow-ups
  • Java equivalents? (StampedLock optimistic reads; immutable snapshot + AtomicReference.)
