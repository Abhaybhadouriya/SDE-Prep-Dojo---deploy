Q&A: concurrency and thread safety

Races and double booking, locks and their granularity, volatile and atomics, producer-consumer, thread pools, deadlock, and thread-safe versions of the classic cases. Runnable versions of several answers are in lld-code/lld-int-question-bank/ (Java, Python and C++). The Java and Python checks pass with real threads. The C++ file runs two ways. With a posix-threads g++ (we used WSL Ubuntu 24.04, g++ 13.3: g++ -std=c++14 -pthread cpp_drills.cpp) the closable queue runs with 4 real worker threads and passes (run-cpp-wsl.txt). On Windows MinGW g++ 6.3 (win32 threads, no std::thread) it builds with g++ -std=c++14 -Wall cpp_drills.cpp and runs single-threaded with a no-op lock, so only the close and drain logic is checked there (run-cpp.txt).

Two users try to book the last seat at the same time. How do you prevent a double booking?

The bug is check-then-act: both threads see "free", both write "booked". Fixes, from simplest: (1) a per-seat (or per-show) lock around check and book; (2) an atomic compare-and-set on the seat status (AtomicReference or ConcurrentHashMap.putIfAbsent(seatId, userId)); (3) in a database, a conditional update (UPDATE seat SET status='HELD' WHERE id=? AND status='FREE', check rows updated = 1) or optimistic versioning; (4) a temporary hold with an expiry while payment runs, released on timeout.

Seen in reports: Paytm 2026-11-11, Uber 2026-08-29, Microsoft 2025-11-17.

How to answer

Name the race first, then lock granularity (per seat, not global), then the hold-with-timeout flow. That order is what interviewers want.

Likely follow-ups
  • Pessimistic vs optimistic: which here? (pessimistic for a hot last seat; optimistic when seats rarely collide and a retry is cheap)
  • What if the payment takes 10 minutes? (hold expiry)
  • Across two app servers? (the DB or a distributed lock must decide)
Pessimistic vs optimistic locking: explain and choose.

Pessimistic: lock before reading (synchronized, ReentrantLock, SELECT ... FOR UPDATE); others wait. Good when conflicts are common or a retry is expensive. Optimistic: read a version, do the work, and write only if the version is unchanged (CAS, UPDATE ... WHERE version = ?); on conflict, retry. Good when conflicts are rare and reads dominate. For a hot concert seat: pessimistic with short holds. For editing a user profile: optimistic.

Seen in reports: Microsoft 2025-11-17, Cleartrip 2026-07-21.

How to answer

Define both, give the conflict-rate rule, then pick one for the interviewer's problem.

Likely follow-ups
  • What happens under heavy contention with optimistic locking? (retry storms)
  • How does a version column work? (each row carries a number; UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?; zero rows updated means someone else won, so retry)
synchronized vs ReentrantLock: when do you need the lock object?

synchronized is simpler and released automatically. ReentrantLock adds tryLock() with a timeout (avoid waiting forever, back off to avoid deadlock), lockInterruptibly(), optional fairness, and several Condition objects (separate "not full" and "not empty" queues). Both are reentrant. Always unlock in finally.

Seen in reports: Walmart 2024-12-14.

How to answer

Default to synchronized; list the three features that justify ReentrantLock.

Likely follow-ups
  • What does reentrant mean? (the same thread can take it again)
  • Fair locks: cost? (lower throughput)
Is ConcurrentHashMap enough to make your service thread-safe?

Only for single operations. Each get or put is atomic, but if (!map.containsKey(k)) map.put(k, v) is two operations and still races. Use the atomic compound methods: putIfAbsent, computeIfAbsent, compute, merge. If an invariant spans two maps or two entries (move stock from A to B), you still need a lock around both.

Seen in reports: Cleartrip 2026-07-21, Uber 2026-08-29.

How to answer

Give the containsKey/put race, the atomic replacement, and the two-entry case.

Likely follow-ups
  • How does ConcurrentHashMap lock internally in Java 8? (CAS on empty bins, synchronized on the bin head otherwise)
What does volatile guarantee, and what does it not?

It guarantees visibility and ordering: a write is seen by later reads in other threads, and writes before it are not reordered past it. It does not make compound actions atomic: count++ on a volatile is still a lost-update race. Use it for flags (running = false) and safe publication; use AtomicInteger or a lock for counters.

Seen in reports: Walmart 2025-09-21.

How to answer

Visibility yes, atomicity no; give one example of each.

Likely follow-ups
  • Why does double-checked locking need it? (without volatile, another thread can see the reference before the constructor's writes are visible and use a half-built object)
  • Compare with C volatile. (C volatile is about the compiler and device memory, not thread visibility)
Runnable vs Callable vs Future vs CompletableFuture.

Runnable: a task with no result and no checked exception. Callable<T>: returns T and may throw. Submitting either to an ExecutorService gives a Future: get() blocks for the result, cancel() tries to stop it. CompletableFuture adds non-blocking chaining (thenApply, thenCompose, allOf) and error handling (exceptionally).

Seen in reports: Walmart 2024-12-14.

How to answer

One line each, then a two-line CompletableFuture example calling two services in parallel.

Likely follow-ups
  • Which thread runs thenApply? (the completing thread, unless you use the Async variant with an executor)
Implement producer-consumer.

Use a bounded BlockingQueue: producers call put() (blocks when full: backpressure), consumers call take() (blocks when empty). Stop with a poison pill per consumer or by interrupting. If asked to build the queue yourself: a lock with two conditions, notFull and notEmpty, and while loops (not if) around each await() to handle spurious wakeups.

Seen in reports: Razorpay 2026-02-22, Uber 2021-03-03.

How to answer

Show the BlockingQueue version first, then offer the wait/notify version. The while loop is the detail graders check.

Likely follow-ups
  • Why while and not if? (spurious wakeups and other consumers taking the item first)
  • How do you shut down cleanly? (stop accepting work, then put one poison pill per consumer (or close the queue); consumers finish and exit, and you join them)
Design a thread pool (like ThreadPoolExecutor).

Parts: a task queue (BlockingQueue<Runnable>), N worker threads each looping take() then run(), a state (RUNNING, SHUTDOWN, TERMINATED), and a rejection policy when the queue is full (abort, caller-runs, discard). submit() wraps a Callable in a FutureTask. shutdown() stops accepting and lets workers drain; shutdownNow() interrupts them. Real ThreadPoolExecutor also grows from core to max size when the queue is full and lets idle extra threads time out.

Seen in reports: Walmart 2026-03-02, post 2026-02-24.

How to answer

Draw queue plus workers plus policy, then code the worker loop. Mention a worker must catch task exceptions or the thread dies.

Likely follow-ups
  • What happens to a task that throws? (caught, stored in the Future; the worker survives)
  • How do you size the pool? (CPU-bound: cores; I/O-bound: more)
What is a deadlock, and how do you prevent it?

Threads wait forever for each other's locks. It needs all four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. Break one: the usual fix is a global lock order (always lock the lower account id first in a transfer), or tryLock with a timeout and back off, or take one coarser lock. Detect with thread dumps (jstack) showing a cycle.

How to answer

List the four conditions, then fix circular wait with lock ordering in a bank transfer.

Likely follow-ups
  • Livelock vs deadlock vs starvation? (deadlock: all blocked forever; livelock: all busy reacting to each other and making no progress; starvation: others progress while one thread never gets the resource)
  • How does the kernel's lockdep help? (it checks lock order at run time)
Mutex vs semaphore.

A mutex allows one holder, and only the holder should release it (ownership). A counting semaphore holds N permits; any thread may release; used to limit concurrency (at most 10 DB connections, at most 3 people in the room). A binary semaphore looks like a mutex but has no ownership, so it is used for signalling between threads.

Seen in reports: LinkedIn 2025-02-05, AMD 2026-10-07, Sprinklr 2026-03-10.

How to answer

Ownership is the key difference. Give one limit-N example for the semaphore.

Likely follow-ups
  • Implement a bounded resource pool with a semaphore. (a semaphore with N permits plus a queue of free objects: acquire a permit, then take one; on release return it, then release the permit)
Read-write lock: when does it help, and when does it hurt?

Many readers can hold the read lock together; a writer needs exclusive access. It helps when reads vastly outnumber writes and reads are long enough to matter (a config cache). It hurts when writes are frequent or reads are tiny (lock overhead beats a plain mutex), and naive versions starve writers. Java: ReentrantReadWriteLock, or StampedLock with optimistic reads.

Seen in reports: Rubrik 2026-04-16.

How to answer

Give the read-heavy example and the starvation warning.

Likely follow-ups
  • Can you upgrade a read lock to a write lock? (not in ReentrantReadWriteLock: it deadlocks)
  • Kernel analogue? (rwlock, or RCU for read-mostly data)
Make an LRU cache thread-safe. Why is a read also a write?

In an LRU, get() moves the key to the front of the recency list, so it mutates shared state. A read-write lock does not help: every call is a write. Options: one lock around the map plus list (simple, correct); a LinkedHashMap subclass with accessOrder = true and removeEldestEntry returning size() > cap (without that override it never evicts), wrapped in Collections.synchronizedMap (iterating it still needs synchronized (map)); or striping into several smaller LRU segments by key hash for more throughput (approximate global LRU).

Seen in reports: Google 2019-09-10, Sprinklr 2026-03-10.

How to answer

Point out that get mutates, so 'just add synchronized to put' is wrong. A Google report says plain synchronized was not enough for an LFU follow-up.

Likely follow-ups
  • How would you get more throughput? (segments, or a concurrent approximate policy like Caffeine's)
Print odd and even numbers alternately with two threads.

Share a counter and a lock with a condition. Each thread loops: lock; while the counter's parity is not mine, wait; print; increment; signal all; unlock. Stop when the counter passes N. Alternatives: two semaphores handing a single permit back and forth (odd starts with 1 permit, even with 0).

Seen in reports: Omnissa 2026-06-16, post 2024-12-04.

How to answer

Write the while-wait loop; mention the semaphore version as the cleanest.

Likely follow-ups
  • Extend to three threads printing 1, 2, 3 in turn. (turn = counter mod 3)
Make a rate limiter thread-safe.

Per-key buckets in a ConcurrentHashMap created with computeIfAbsent. Each bucket's refill-and-take must be atomic: synchronized on the bucket, or a CAS loop on a packed state. Do not lock the whole map. For a fixed window counter, an AtomicLong per (key, window) works with incrementAndGet and a compare against the limit.

Seen in reports: post 2024-09-29.

How to answer

Per-key locking is the key point; one global lock kills throughput.

Likely follow-ups
  • How do you clean up idle keys? (expiry sweep or a cache with TTL)
Thread-safe message queue in C++: what happens if the destructor runs while threads are waiting?

Waiting threads would wake on a destroyed mutex and condition variable: undefined behaviour. Add a closed flag: close() sets it under the lock and calls notify_all(); pop() returns empty (or throws) when closed and empty. The owner calls close(), then joins the worker threads, and only then destroys the queue. RAII: put close-and-join in the owning object's destructor.

Seen in reports: Adobe 2026-08-10.

How to answer

Name the undefined behaviour, then the close-notify-join order.

Likely follow-ups
  • Why use a predicate with condition_variable::wait? (spurious wakeups)
Implement a task scheduler that runs tasks at a time or at a fixed interval.

A PriorityQueue (or DelayQueue) ordered by next run time, one scheduler thread that waits until the head is due (Condition.awaitNanos for the gap, woken early when an earlier task is added), and a worker pool that runs due tasks. Periodic tasks are re-queued with next = last + interval. Without library schedulers, this is exactly what was asked in an Uber machine-coding round.

Seen in reports: Uber 2020-10-12, Salesforce 2026-03-02.

How to answer

Draw heap, timer thread, pool. Handle 'new earlier task arrives while sleeping'.

Likely follow-ups
  • Fixed rate vs fixed delay? (fixed rate schedules from the start times (catches up after a slow run); fixed delay waits a full period after each run ends)
  • What if a task runs longer than its interval? (Java never runs the same periodic task concurrently: the next run starts late; decide whether to skip missed runs or catch up)
What is a race condition? Give a non-obvious one.

A bug where the result depends on thread timing. Obvious: count++. Non-obvious: lazy initialisation (two threads build two caches), iterating an ArrayList while another thread adds (ConcurrentModificationException or missed items), check-then-act on a file ("exists? then create"), and publishing an object before its constructor finishes.

How to answer

Define it in one line and spend the time on one subtle example.

Likely follow-ups
  • How do you test for races? (many threads, a start latch, repeat runs, check invariants)
What do atomic classes give you, and how does CAS work?

AtomicInteger, AtomicLong, AtomicReference do lock-free updates using the CPU's compare-and-swap: read the value, compute, and write only if the value is still what you read, otherwise retry. incrementAndGet() is one CAS loop. Under heavy contention many threads retry; LongAdder spreads the counter over cells to cut that.

Seen in reports: Uber 2026-08-29.

How to answer

Tie it to cmpxchg and atomic_t from the kernel. Mention the ABA problem as a bonus.

Likely follow-ups
  • What is ABA? (value changes A to B to A; fix with a version stamp)
wait/notify vs sleep: what is the difference?

wait() must be called holding the object's monitor; it releases the lock and sleeps until notify/notifyAll (or a spurious wakeup). Thread.sleep() keeps any locks held and just pauses. Use notifyAll unless you are sure every waiter waits for the same condition. Modern code prefers Condition or higher-level tools (queues, latches).

How to answer

Lock released vs lock held is the key line.

Likely follow-ups
  • Why must wait be in a loop? (spurious wake-ups happen, and another thread may consume the condition first, so re-check it after every wake-up)
How do you design a thread-safe in-memory pub-sub (Kafka-like) system?

Per topic, an append-only list (or ring buffer) of messages with offsets. Publishers append under a per-topic (or per-partition) lock. Each subscriber (or consumer group) keeps its own offset and reads on its own thread, so slow subscribers do not block publishers or each other. Ordering is guaranteed per partition; partition by key. Retention trims old messages. A known Uber round asked that publishers and subscribers never block each other.

Seen in reports: Uber 2021-03-03, Flipkart 2025-10-01, Uber 2026-04-06, Razorpay 2025-06-27.

How to answer

Offsets per subscriber are the core idea; without them you are building a shared queue, not pub-sub.

Likely follow-ups
  • Replay from an offset? (keep the log append-only and let each consumer own its offset; replay is just resetting the offset)
  • At-least-once delivery and acknowledgements? (advance the consumer offset only after the handler acknowledges; a crash re-delivers, so handlers must be idempotent)
Lock granularity: one lock, a lock per entity, or lock striping?

One global lock: always correct, serialises everything. A lock per entity (per seat, per account, per spot): concurrency between unrelated entities; needs a lock order if you hold two. Lock striping: a fixed array of locks indexed by hash, a middle ground when entities are too many to each own a lock. Pick the coarsest that meets the load; say what invariant each lock protects.

Seen in reports: Cleartrip 2026-07-21.

How to answer

Explain the trade-off, then pick for the problem in front of you.

Likely follow-ups
  • How many stripes? (a few times the number of cores)
  • Where does a map of locks leak memory? (locks never removed)
Ensure a user never has more than 2 in-progress tickets, under concurrent edits.

The limit is an invariant across several tickets of one user, so a per-ticket lock is not enough. Take a per-user lock (or keep an AtomicInteger count per user and increment with a CAS that refuses to pass the limit) around "count in-progress, then move this ticket to in-progress". In a database: a conditional update on a per-user counter row, or a serialisable transaction.

Seen in reports: Meesho 2024-04-20.

How to answer

Find the invariant's scope (the user), lock at that scope. A Meesho machine-coding round asked exactly this.

Likely follow-ups
  • What if the limit becomes per team? (lock the team (or a counter per team) instead of the user, and take it in one fixed order with any other lock)
Uber premium cab: concurrent requests must not double-book a driver. Design the allocation.

Drivers have a state (AVAILABLE, ASSIGNED, ON_TRIP). Allocation: find candidates (a Strategy: nearest, highest rated), then try to claim one with an atomic state change (AtomicReference.compareAndSet(AVAILABLE, ASSIGNED) or a per-driver lock). If the CAS fails, try the next candidate. Trip lifecycle is a State machine. Release on cancel or timeout.

Seen in reports: Uber 2026-08-29, Uber 2026-08-22.

How to answer

Strategy to choose, CAS to claim, State to track: three patterns, each with one job.

Likely follow-ups
  • What if the driver rejects? (back to AVAILABLE, retry allocation)
  • Fairness across riders? (serve requests in FIFO order per zone, or age waiting requests so nobody waits forever)
Is immutability a concurrency strategy?

Yes, the cheapest one: immutable objects can be shared by any number of threads with no locks. Combine with an atomic reference to swap whole snapshots: readers grab the current snapshot, a writer builds a new one and publishes it with one write (copy-on-write). The kernel's RCU is the same idea at high speed.

How to answer

Say where you would use it in the design (configs, price lists, read-mostly catalogues).

Likely follow-ups
  • Cost? (allocations on each write)
