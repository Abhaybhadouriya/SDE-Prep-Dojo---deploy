Q&A: UML and modelling

Which diagrams to draw, the arrows, going from a problem statement to classes, and how much schema and API to add.

Which UML diagrams matter in an LLD interview, and which can you skip?

Three cover almost every round: the class diagram (classes, fields, key methods, relationships), a sequence diagram for the one or two main flows (book a seat, park a car), and a state diagram when an object has a lifecycle (order, elevator, vending machine). Use-case diagrams help only to list actors at the start. Component, deployment and activity diagrams are rarely asked in LLD.

Seen in reports: Salesforce 2025-05-27, Salesforce 2026-01-01.

How to answer

Say which you will draw and why, then draw the class diagram first.

Likely follow-ups
  • How much detail on the class diagram? (key fields and methods, not every getter)
Draw and explain the UML relationship arrows.
  • Association: solid line (optionally with an open arrow for direction).
  • Aggregation: solid line, hollow diamond at the whole.
  • Composition: solid line, filled diamond at the whole.
  • Inheritance (generalisation): solid line, hollow triangle at the parent.
  • Realisation (implements): dashed line, hollow triangle at the interface.
  • Dependency (uses): dashed line, open arrow.
How to answer

Draw them, do not just name them. The diamond is always on the owner's side; the triangle always points at the parent.

Likely follow-ups
  • Composition or aggregation for Order and OrderLine? (composition)
How do you get from a problem statement to a class diagram quickly?
  1. Underline nouns: candidates for classes (and drop those that are just attributes, like "colour").
  2. Underline verbs: candidates for methods, placed on the class that has the data.
  3. Find the things that vary ("types", "strategies") and make them interfaces.
  4. Add relationships with multiplicities (1, 0..1, *).
  5. Walk one use case through the diagram; missing classes show up immediately.
How to answer

Do it out loud with the interviewer's problem. Five minutes is enough for a first version.

Likely follow-ups
  • How do you avoid too many classes? (merge classes with no behaviour into attributes or enums)
Draw a sequence diagram for 'user books the last seat'.

Lifelines: User, BookingController, BookingService, SeatLockManager, PaymentService, BookingRepository. Flow: request, service asks the lock manager to lock the seat (with a timeout), on success creates a PENDING booking, calls payment, on success marks CONFIRMED and releases the lock; an alt fragment shows payment failure (release lock, mark FAILED). Activation bars show who is busy; return arrows are dashed.

How to answer

Draw the happy path first, then one alt fragment for failure. That is what makes it SDE-2 level.

Likely follow-ups
  • Where is the lock released if the user closes the app? (lock expiry)
When do you draw a state diagram, and what goes on it?

When an object's allowed actions depend on its current status: order (PLACED, PAID, SHIPPED, DELIVERED, CANCELLED), vending machine (IDLE, HAS_MONEY, DISPENSING), elevator (IDLE, MOVING_UP, DOOR_OPEN). States are rounded boxes, transitions are arrows labelled event [guard] / action, with a start dot and end states. Every transition not drawn is illegal, and your code should reject it.

Seen in reports: MakeMyTrip 2025-07-25.

How to answer

Draw it before coding the State pattern; the diagram becomes the class list.

Likely follow-ups
  • How do you enforce it in code? (enum + transition table, or State classes)
What do multiplicities like 1, 0..1, 1..* and * mean on a class diagram?

How many objects on that end relate to one object on the other end. ParkingLot 1 -- 1..* ParkingFloor: a lot has one or more floors, each floor belongs to exactly one lot. Ticket 0..1 -- 1 Vehicle: a vehicle has at most one active ticket. They become field types in code: a single reference, an Optional, or a collection.

How to answer

Translate one multiplicity into a Java field type to show you can go from diagram to code.

Likely follow-ups
  • How would 0..1 look in a database? (nullable foreign key)
How do you show an interface, an abstract class and an enum in UML?

An interface: a class box with <<interface>> above the name (or a lollipop). An abstract class: name in italics or {abstract}. An enum: <<enumeration>> with its values listed. Visibility: + public, - private, # protected, ~ package. Static members are underlined.

How to answer

Quick facts; use them correctly on your own diagram rather than reciting them.

Likely follow-ups
  • How do you show a method's parameters and return type? (+book(userId: String): Booking)
Class diagram, DB schema and API: in what order, and how much of each?

Some rounds (Zepto via third-party interviewers, Amazon onsite) expect all three. Order: requirements, then the class diagram (core entities and relations), then the schema derived from entities (tables, keys, indexes), then 3-6 key APIs (method, path, request, response, errors). Keep each to what the main flows need; spend the saved time on concurrency or extensibility.

Seen in reports: Zepto 2026-05-29, Zepto 2024-10-18, Swiggy 2026-03-27.

How to answer

Ask early whether schema and APIs are expected; it changes how you split the hour.

Likely follow-ups
  • Do classes map 1:1 to tables? (mostly for entities; strategies and services do not become tables)
What is a use-case diagram good for in an LLD round?

Listing actors (customer, admin, delivery partner, a payment gateway as an external system) and what each can do. It is a requirements tool: two minutes of it prevents missing the admin flows or a system actor such as a scheduler. Keep it as a bullet list unless asked to draw it.

How to answer

Use it to confirm scope with the interviewer, then move on.

Likely follow-ups
  • What is the difference between include and extend? (include: always part of; extend: optional add-on)
Draw the class diagram for a parking lot in five minutes.

ParkingLot (1) composes ParkingFloor (1..*), each composes ParkingSpot (*), with SpotType enum (SMALL, COMPACT, LARGE). Vehicle (abstract) with Car, Bike, Truck. Ticket associates one Vehicle and one ParkingSpot, with entry time. Interfaces: SpotAllocationStrategy (nearest, by floor) and FeeStrategy (hourly, flat). ParkingService (or EntryGate/ExitGate) uses them.

Seen in reports: Microsoft 2025-11-17, Swiggy 2025-11-30, Amazon 2026-09-16.

How to answer

Start from the nouns, put the two strategies in, then walk 'car enters' through it. The most reported LLD problem in our survey.

Likely follow-ups
  • Two cars arrive at two gates for one spot: what locks? (claim the spot atomically with a per-spot lock or a compare-and-set from FREE to TAKEN; the loser picks again)
  • Add EV charging spots: what changes? (a new spot type with a charger attribute and a spot-matching rule that knows it; fee calculation gains a charging line)
How do you show a design pattern on a class diagram?

Draw the roles, not a label. Strategy: the context holds an association to the <<interface>> with 2+ realisations. Observer: subject holds * observers through an interface. Decorator: the decorator both realises and aggregates the component interface. A note box naming the pattern helps, but the arrows must show it.

How to answer

Use this when the interviewer asks 'where is the pattern?': point at the arrows.

Likely follow-ups
  • Strategy and State look the same on a diagram. How do you tell them apart? (who changes the object: client vs state itself)
UML or code? What do interviewers actually want?

It depends on the round. Amazon and Zepto discussion rounds lean on class diagrams plus key code paths; Uber, Microsoft and Atlassian often want running code; machine-coding rounds want only code. A candidate asked exactly this before an Amazon SDE-2 LLD round. Default: a short class diagram, then real code for the core methods. Ask the interviewer in the first minute.

Seen in reports: Amazon 2026-07-07, Microsoft 2026-03-09.

How to answer

Ask, do not guess. Several rejections in the reports came from whiteboarding when code was expected, or the reverse.

Likely follow-ups
  • How detailed should the code be? (core logic compiled in your head, edge cases handled)
