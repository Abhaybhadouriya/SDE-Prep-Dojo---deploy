Q&A: SOLID and design principles

The five SOLID principles, DRY/KISS/YAGNI, GRASP, coupling and cohesion, code smells, and the judgement questions about when to bend them.

What are the SOLID principles? One line and one example each.
  • Single Responsibility: one reason to change. InvoicePrinter separate from InvoiceCalculator.
  • Open/Closed: add behaviour by adding code, not editing it. A new PricingStrategy class instead of a new if.
  • Liskov Substitution: a subtype must work wherever its parent is expected. A ReadOnlyList that throws on add breaks it.
  • Interface Segregation: small, client-shaped interfaces. Printer and Scanner, not one Machine.
  • Dependency Inversion: depend on abstractions; inject them. A service takes a Repository interface.

Seen in reports: Microsoft 2024-09-12, Walmart 2024-12-14, Goldman Sachs 2025-05-08, WEX 2026-08-30, Zomato 2026-10-24.

How to answer

Do not just expand the acronym. Give each letter a code-level example, ideally from the same small domain so they connect.

Likely follow-ups
  • Which one do you violate most often in practice? (say SRP honestly: services grow until a rule is pulled out into its own class)
  • Show a violation in this code and fix it. (point to a type switch (OCP) or a class that both computes and prints (SRP), then move that piece behind an interface)
Here are Vehicle classes. Find the SOLID violation and fix it.

A typical version: Vehicle has fly() and drive(), and Car.fly() throws. That breaks LSP (a Car cannot stand in for a Vehicle that flies) and ISP (Car is forced to depend on fly). Fix: split capabilities into Drivable and Flyable; Car implements Drivable, Plane implements Drivable, Flyable. Another common one: a Vehicle that also calculates parking fees and prints receipts (an SRP break): move fees to a FeeCalculator.

Seen in reports: Goldman Sachs 2025-05-08.

How to answer

Read the code out loud, name the principle, then show the smallest refactor. Do not rewrite everything.

Likely follow-ups
  • After the split, where does shared code go? (a small abstract base or composition)
What does Single Responsibility really mean? Is it 'one method per class'?

No. It means a class should have one reason to change, that is, serve one actor or concern. An Order class that holds items and totals is fine; one that also formats emails and writes SQL changes for three different reasons (business rules, marketing, storage). Split along those reasons. Many small methods in one cohesive class are fine.

Seen in reports: Flipkart 2023-04-01.

How to answer

Use the 'who would ask for this change?' test, and show one class that violates it in a design you have seen.

Likely follow-ups
  • How do you avoid splitting too far? (if two pieces always change together, keep them together)
Show Open/Closed in code. How does a Factory violate it, and how do you fix that?

OCP: adding a new payment mode should mean adding a class, not editing old ones. A strategy interface does that for behaviour. A factory with a switch (type) must be edited for every new type, so it is the one place that is not closed. Fixes: a registry map (Map<String, Supplier<PaymentMethod>>) filled at start-up, Java ServiceLoader, or DI framework discovery. In an interview, accepting the switch in one small factory is a reasonable trade-off if you say so.

Seen in reports: Arcesium 2025-09-11.

How to answer

Say where change is concentrated: one switch in one factory is acceptable; the same switch copied in five services is not.

Likely follow-ups
  • Can any real system be fully closed? (no; you choose which changes to be closed against)
Give a Liskov Substitution violation that compiles fine.

The classic: Square extends Rectangle. Code that does r.setWidth(5); r.setHeight(4); assert r.area() == 20 fails for a Square that keeps sides equal. It compiles, but the subtype breaks the parent's promise. Others: a subclass that throws UnsupportedOperationException, needs stronger preconditions (accepts fewer inputs) or gives weaker guarantees (may return null where the parent never did).

How to answer

Explain LSP as a contract: preconditions cannot be stronger, postconditions cannot be weaker, invariants must hold.

Likely follow-ups
  • How would you model Square and Rectangle instead? (immutable shapes, or no inheritance between them)
Dependency Inversion vs dependency injection vs IoC: are they the same?

Related, not the same. Dependency Inversion is a principle: high-level code and low-level code both depend on an abstraction (the interface is owned by the high-level side). Dependency injection is a technique: objects receive their dependencies (usually through the constructor) instead of creating them. Inversion of Control is the broader idea that a framework calls your code and manages object creation (Spring's container).

How to answer

One sentence each, then show constructor injection in your own design.

Likely follow-ups
  • Constructor vs setter vs field injection: which and why? (constructor: required deps, immutable, testable)
What are DRY, KISS and YAGNI, and when do they conflict?

DRY: each piece of knowledge has one home. KISS: prefer the simplest design that works. YAGNI: do not build features until needed. They conflict when removing duplication needs a clever abstraction (DRY vs KISS): two similar 5-line methods are often better left alone than merged into a 20-line generic one. In a 90-minute round YAGNI wins: build P0 first.

How to answer

Define them briefly and spend most of the time on the conflict; that is where judgement shows.

Likely follow-ups
  • Rule of three: when do you extract the abstraction? (on the third copy)
What is 'program to an interface, not an implementation'?

Declare variables, fields and parameters by the interface type (List, PaymentMethod, Repository), and only name the concrete class where the object is created. Callers then work with any implementation, and tests can pass fakes. It is the practical form of DIP and the reason Strategy, Repository and Observer work.

How to answer

Show List<String> xs = new ArrayList<>(), then a service constructor taking an interface.

Likely follow-ups
  • Does every class need an interface? (no, only where you expect variation or need a test seam)
Composition over inheritance: show it with a real refactor.

Before: InstrumentedHashSet extends HashSet overrides add and addAll to count insertions. addAll of three items reports 6, because HashSet inherits addAll from AbstractCollection, which calls add once per item. (An ArrayList subclass reports 3, because ArrayList.addAll copies the array directly: whether you double count depends on a parent implementation detail you do not control, and that is the point.) After: CountingSet implements Set wraps a private Set and forwards each call (a "forwarding set"); it counts in its own methods and does not depend on how the parent is written inside. Same idea at design level: Duck holds a FlyBehavior instead of subclasses for every flying style.

Seen in reports: Walmart 2024-10-25.

How to answer

The double-count bug is the convincing part; tell it as a story in three lines, and name HashSet, not ArrayList.

Likely follow-ups
  • What does composition cost? (delegation boilerplate)
What is GRASP, and which of its ideas help most in LLD rounds?

GRASP is a set of responsibility-assignment guidelines from Craig Larman. The useful ones in rounds: Information Expert (give a job to the class that has the data: Cart.total()), Creator (the class that contains or closely uses objects creates them: Order creates OrderLine), Controller (a service handles a system event), Low Coupling, High Cohesion, Polymorphism and Pure Fabrication (invent a class like Repository when no domain class fits).

How to answer

Use Information Expert to justify where each method went in your design. It is the fastest way to answer 'why is this method here?'.

Likely follow-ups
  • Who should calculate a parking fee: Ticket, Spot or a FeeCalculator? Defend it. (a FeeCalculator (pure fabrication in GRASP terms): pricing changes on its own schedule, and Ticket only supplies the times)
Tell, don't ask: what does it mean in code?

Instead of pulling data out and deciding outside (if (account.getBalance() >= amt) account.setBalance(...)), tell the object to do the job (account.withdraw(amt)) and let it enforce its own rule. It keeps logic next to data (Information Expert) and avoids race-prone check-then-act from outside.

How to answer

Show the before/after in two lines; mention that the 'after' is also the version you can make thread-safe inside the class.

Likely follow-ups
  • Is a getter always wrong? (no, reading for display is fine)
What is the difference between coupling to an interface and coupling to a data format?

Two services can share no classes and still be tightly coupled if both depend on the same JSON field names or the same database table. Interface coupling is explicit and checked by the compiler; data coupling is hidden and breaks at run time. Ways to manage it: versioned contracts, one owner per table, and translation at the boundary (an Adapter or anti-corruption layer).

How to answer

This is an SDE-2 stretch question. Show you know coupling exists beyond imports.

Likely follow-ups
  • How would you detect hidden coupling? (contract tests, schema registry)
Your design has a ParkingLotManager with 25 methods. What principles does that break and how do you split it?

It is a god class: it breaks SRP and usually ISP (callers need only a few of its methods). Split by responsibility: SpotAllocator (finding a spot, behind a strategy), TicketService (issue, close), FeeCalculator (pricing strategy), PaymentService, and keep a thin ParkingLotFacade if the problem wants one entry point.

How to answer

Group the 25 methods into 4-5 nouns on the whiteboard; the split falls out.

Likely follow-ups
  • Isn't the facade a god class again? (no, it only delegates)
Is it ever right to break SOLID?

Yes. Principles serve change; if something will not change, an extra interface is cost without benefit. In a 90-minute round, a concrete class with a clear name beats an interface with one implementation and no reason to vary. Prototypes, scripts and performance-critical inner loops also justify fewer abstractions. Say which principle you are bending and why.

How to answer

Show judgement: name the change you are not designing for, and how you would add the seam later.

Likely follow-ups
  • Where in your design did you choose not to add an interface? (the repository had one in-memory implementation and no second one coming, so you note where the seam would go)
How do SOLID principles map to the patterns you use?

Strategy, State, Decorator, Observer: OCP (add behaviour as new classes). Factory and DI: DIP (callers do not name concrete classes). Adapter and small role interfaces: ISP. Template Method and class hierarchies must respect LSP. Facade and splitting services: SRP. Patterns are tested solutions; the principles explain why they work.

How to answer

Make the table in your head: principle on the left, 1-2 patterns on the right.

Likely follow-ups
  • Which pattern most often violates a principle? (Singleton: hidden global state, hurts DIP and testing)
What is a code smell? Name five you check for in an LLD solution.

A surface sign of a deeper design problem. Five common ones in rounds: long method, god class, switch on type repeated in several places (missing polymorphism), primitive obsession (status as raw strings, money as double), feature envy (a method using another class's data more than its own).

How to answer

List them with the fix next to each (extract method, split class, polymorphism, enums/value objects, move method).

Likely follow-ups
  • Why is money as double a bug? (binary floating point cannot represent 0.10 exactly; use BigDecimal or long paise)
Interviewers say 'this is over-engineered'. How do you respond?

Agree where it is true, and show you can simplify: "You are right: the RuleEngine abstraction has one rule. I will inline it into the service and keep only the PricingStrategy interface, because the problem says pricing varies." Then make the change. Feedback of "over-designed" appears in real reports (an Amazon SDE-2 chess round), so practise trimming.

Seen in reports: Amazon 2025-02-09.

How to answer

Do not defend every abstraction. Keep the seams the requirements justify, cut the rest.

Likely follow-ups
  • Which abstraction would you keep and why? (the one around the requirement most likely to change, usually the pricing or assignment Strategy)
Explain cohesion, coupling and SOLID using the Linux kernel.

struct file_operations is DIP and OCP: the VFS depends on a table of function pointers, and a new filesystem plugs in without changing the VFS. Small ops tables (inode_operations, address_space_operations) are ISP. A driver that only fills the ops it supports relies on the VFS treating NULL entries as "not supported", which is the kernel's way of avoiding LSP-style surprises. Subsystems with one job (the block layer, netfilter) show high cohesion.

How to answer

This is your edge as a systems engineer. Use it when asked for a real example of a principle.

Likely follow-ups
  • Where does the kernel break these on purpose for speed? (direct calls instead of indirect, to avoid retpoline cost)
