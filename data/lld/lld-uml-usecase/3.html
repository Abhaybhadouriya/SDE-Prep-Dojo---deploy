Entity, value object, service: three kinds of class

Not every class is the same kind of thing. Naming the kind out loud ("Money is a value object") shows the interviewer you are thinking, and it decides how you write the code: whether it gets an id, whether it is mutable, how equals works. The vocabulary comes from Domain-Driven Design; Martin Fowler's short notes on the Evans classification and value objects are worth five minutes.

Why value objects matter in interviews

Using a raw double for money or a String for an ISBN is the smell called primitive obsession. The cost shows up in follow-ups: "what if someone passes a negative fine?", "what about floating-point rounding?". A value object answers both in one place.

class Loan {
    double fine;                 // rupees? paise? can it be negative?
    String isbn;                 // any string at all, checked nowhere
    void addFine(double r) { fine += r; }   // 0.1 + 0.2 problems
}
record Money(long paise) {                       // whole paise: no float errors
    Money { if (paise < 0) throw new IllegalArgumentException("negative money"); }
    Money plus(Money o)  { return new Money(paise + o.paise); }   // returns NEW value
    Money times(long n)  { return new Money(paise * n); }
}
record Isbn(String value) {
    Isbn { if (value == null || !value.matches("\\d{13}"))
               throw new IllegalArgumentException("bad ISBN: " + value); }
}
// records give equals/hashCode by value for free:
// new Isbn("9781449373320").equals(new Isbn("9781449373320")) == true

From your world

A value object is a const struct passed by value, like struct in6_addr or a ktime_t: you never "update" an address in place, you build a new one, and two addresses with the same bytes are the same address. An entity is like a struct task_struct: it has a PID, it is refcounted and its fields change all the time, but it stays the same task.

Managers, repositories and "-er" classes

Two more names you will see in solutions:

  • Repository (MemberRepository): hides how entities are stored and found. In machine coding it is a HashMap behind an interface, so a database can replace it later. See Repository.
  • Manager (ParkingManager): often a service in disguise. Fine when it means "coordinates one area". A warning sign when one SystemManager holds every method of the design: that is a god class, not a service.

Do not swing too far the other way. If every rule lives in services and entities are bags of getters and setters, you have an anemic domain model. Rules about one object's own data (canBorrow, isAvailable, fineOn) belong on that object.
