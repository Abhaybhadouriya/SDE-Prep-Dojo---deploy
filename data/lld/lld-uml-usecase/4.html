The trap: one class per instance

This is the most common modelling mistake in machine-coding rounds, and it is easy to see in a real report. In a CRED backend machine-coding round shared on LeetCode Discuss, the task was a toy microprocessor with registers A, B, C and D and commands such as SET A 25, INC, MOVE and ADDR. The candidate wrote four classes, RegisterA to RegisterD, each with the same value field and the same getter and setter, plus a switch on the register name to find the right object. The outcome posted was a reject, and the grading criteria listed working code, unit tests, extensibility and OOP principles.

// lld-code/lld-uml-usecase/Microprocessor.java (compiled and run)
static final class Register {
    private final String name;
    private int value;
    Register(String name) { this.name = name; }
    int get() { return value; }
    void set(int v) { value = v; }
}
private final Map<String, Register> registers = new LinkedHashMap<>();

Microprocessor(String... names) { for (String n : names) registers.put(n, new Register(n)); }

private Register reg(String name) {
    Register r = registers.get(name);
    if (r == null) throw new IllegalArgumentException("unknown register: " + name);
    return r;
}
public void move(String dst, String src) { reg(dst).set(reg(src).get()); }
public void addR(String dst, String src) { reg(dst).set(reg(dst).get() + reg(src).get()); }

When is a subclass justified, then?

Ask one question: does the behaviour differ, or only the data?

SituationModel it asExample
Same behaviour, different valuesOne class, different objectsRegisters A-D, floors 1-20, seats A1-J10
Fixed small set of kinds, behaviour the same, maybe a few constantsAn enum field (enums can carry data)SpotSize.SMALL/LARGE, CopyStatus
Kinds really behave differently and new kinds will be addedInterface + implementations (Strategy, polymorphism)FeeStrategy: hourly vs flat; PaymentMethod: UPI vs card
The object's behaviour changes as its status changesState pattern or a state enum + transition tableVending machine, order lifecycle

Say it out loud: "Car, bike and truck only differ in size, so I will use a VehicleType enum. If pricing per type gets different rules later, I will move pricing behind a PricingStrategy interface, not subclass Vehicle." That one sentence shows you know both tools and why you picked the cheaper one.

From your world

The kernel never writes struct eth0_device and struct eth1_device. It has one struct net_device, and each interface is an instance with a name field (dev->name), found by name through a lookup (dev_get_by_name). Different drivers are where behaviour differs, and there the kernel uses a table of function pointers (net_device_ops): that is the interface + implementations row of the table.
