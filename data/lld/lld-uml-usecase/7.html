Where the model goes wrong: boundaries and enums

One aggregate or two?

Once the classes exist, the next question is which of them change together. An aggregate is a cluster of objects that must stay consistent as one unit, with one root that outsiders talk to. Loan and the BookCopy status it changes must flip together (a copy is never "on loan" without a loan), so the service updates both under one lock or one transaction. Member and Loan do not need that: a member's address can change while a loan is open. So Loan holds a memberId (or a reference it never edits through), not ownership of the member.

The two common mistakes, and their signs:

  • Boundary too big. Show owns every Seat, every Booking and every Payment, so booking seat A1 locks the whole show. Sign: unrelated users block each other, and the root class grows every sprint. Fix: seats (or seat holds) are their own unit, keyed by show and seat; payments live outside and refer to a booking id.
  • Boundary too small. Order and its OrderItems are saved and locked separately, so a total can be computed from half-updated items. Sign: invariants such as "total = sum of items" need two locks or a retry loop. Fix: items are parts of the order, created and changed only through Order (composition).

From your world

This is lock granularity in data-structure form. An sk_buff and its data area change together; a socket and the device it transmits on do not, so the socket holds a reference to the device (counted, not owned). One aggregate per lock is the same rule as "one lock protects one consistent set of fields".

When a noun should be an enum, and when it must stop being one

The instances rule says: kinds that differ only in data become an enum. Two advanced failure modes sit on either side of it.

  • Enum that grows behaviour. VehicleType starts as data. Then pricing does switch (type), allocation does another, and charging electric cars adds a third. When the same switch appears in a second place, move the behaviour onto the enum's own methods; when kinds need different collaborators or state, promote them to an interface with classes.
  • Enum for data the business adds at run time. Cities, product categories, membership plans and coupon types change without a deploy. An enum forces a code release for each new value. Model them as entities loaded from storage (City, Plan), and keep enums for values the code itself branches on and that only a developer adds (BookingStatus, SpotSize).

Say the test out loud in the interview: "Does code branch on it, and does only a developer add values? Then enum. Does an admin add values? Then a class backed by data."
