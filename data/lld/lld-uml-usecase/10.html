Which of these is not an actor in a parking-lot system?

  1. Driver
  2. Payment gateway
  3. ParkingSpot
  4. Night-time billing scheduler
ParkingSpot lives inside the system: it is a class. Actors are outside the boundary, and they can be other systems or timers.

The requirements say "users" in one place and "customers" in another. What do you do?

  1. Make two classes in case they differ
  2. Ask once, then use one name and one class
  3. Make Customer extend User
Synonyms produce duplicate classes that drift apart. Confirm and pick one word.

Which is the best candidate for a value object?

  1. Money amount
  2. Order
  3. Driver
  4. ParkingLotService
Money has no identity, should be immutable and is equal by value. Order and Driver are entities; the service is a service.

Seats A1 to J10 in a cinema hall behave identically. How do you model them?

  1. One class per row
  2. An enum with 100 values
  3. One Seat class with row/number fields, 100 objects
They differ only in data. One class, many instances, typically held in a map or list on the Screen.

Where should canBorrow() (fewer than 3 active loans) live?

  1. LibraryService, reading member.getLoans().size()
  2. Member, since it owns its active loans
  3. A static utility class
Information Expert: the rule reads only Member's data, so it belongs on Member. The service asks, it does not reach in.

"Pay a fine" only happens when a return is late. In a use-case diagram this is...

  1. an include
  2. a generalization
  3. a separate actor
  4. an extend
Extend = optional behaviour under a condition. Include = always-run shared step.

When is an interface with several implementations better than an enum field?

  1. When there are exactly three kinds
  2. When the kinds differ only in a number
  3. When kinds behave differently and new ones keep being added
Behaviour that varies and grows is what polymorphism is for; pure data differences fit an enum.
