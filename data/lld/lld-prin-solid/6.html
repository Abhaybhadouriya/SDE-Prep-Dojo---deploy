D: Dependency Inversion Principle

Rule: high-level policy should not depend on low-level details. Both depend on abstractions, and the abstraction belongs to the policy side.

Smell: new MySqlRepo(), new EmailSender() or new RazorpayClient() inside a business class; you cannot unit test the class without a real database or network; swapping a vendor means editing business logic.

Cure: define an interface (Notifier, PaymentGateway, OrderRepository) next to the policy, implement it in the detail, and pass the implementation in through the constructor (dependency injection, DI).

interface Notifier { void send(String to, String message); }

class OrderService {
    private final Notifier notifier;
    OrderService(Notifier notifier) { this.notifier = notifier; }      // injected, not new-ed
    void place(String user) { notifier.send(user, "order placed"); }
}

new OrderService(new EmailNotifier());    // production
new OrderService(new SmsNotifier());      // new channel, no edit to OrderService
new OrderService(new FakeNotifier());     // unit test, no network

From your world

The VFS is high-level policy (path lookup, permissions, page cache). It never includes ext4 or XFS headers. Instead it defines the abstractions (file_operations, inode_operations) and each filesystem implements them. The detail depends on the abstraction, not the other way round. The block layer does the same with blk_mq_ops for drivers. When an interviewer asks "how would you swap the DB?", this is the answer: the repository interface is your file_operations.

DIP vs DI vs IoC. DIP is the principle (depend on abstractions). DI is a technique (hand dependencies in from outside, usually through the constructor). IoC (inversion of control) is the broader idea that a framework calls your code. Spring is an IoC container that does DI. See Fowler's article on injection.
