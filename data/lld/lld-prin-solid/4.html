L: Liskov Substitution Principle

Rule: if code works with a parent type, it must keep working when you hand it any child type. A subtype may do more, never less: it must accept at least what the parent accepts, promise at least what the parent promises, and keep the parent's invariants. Barbara Liskov and Jeannette Wing wrote the formal version in 1994 ("A behavioral notion of subtyping").

Smell: an override that throws UnsupportedOperationException, does nothing, or needs a special case; callers writing if (bird instanceof Penguin); a Square extends Rectangle whose setWidth also changes the height.

Cure: make the parent promise only what every child can keep. Split the hierarchy (Bird and FlyingBird), or use composition instead of inheritance.

// BEFORE
class Bird    { String fly() { return "flap flap"; } }
class Penguin extends Bird { @Override String fly() { throw new UnsupportedOperationException(); } }

// AFTER
interface Bird { String name(); }
interface FlyingBird extends Bird { String fly(); }
record Sparrow(String name) implements FlyingBird { public String fly() { return name + " flies"; } }
record Penguin(String name) implements Bird {}

From your world

Every driver that fills a struct file_operations is a subtype of "a file". User space trusts the contract: read() returns the number of bytes copied, 0 at end of file, or a negative errno. A driver whose read() returns a random positive number on error would make cat, dd and every library misbehave, although it "implements the interface". LSP is that contract, enforced for objects. See the VFS docs for how each operation's meaning is specified.
