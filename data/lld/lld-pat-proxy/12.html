Interview Q&A

Proxy vs Decorator: the code looks the same. What is the difference?

Structure is the same: both implement the subject's interface and hold a reference to it. The difference is intent and ownership. A Decorator adds responsibilities and is composed by the client on purpose, often several deep (new Buffered(new Gzip(new FileStream()))). A Proxy controls access (lazy creation, permission, remoting, caching, limits), is usually created by a factory or framework, and often controls the real object's lifecycle: a virtual proxy creates it; a remote proxy connects to it.

How to answer

Concede the structural sameness first, then intent, who builds it, and lifecycle. One example each.

Likely follow-ups
  • Is a caching wrapper a proxy or a decorator? (Argue it: it controls whether the real object is called, so Proxy; many people call it a decorator, and that is fine if you explain.)
Design a rate-limiting proxy for a third-party API client.

Define the client interface (WeatherApi.forecast(city)). The real client calls the vendor. RateLimitedWeatherApi implements WeatherApi holds the real client and a RateLimiter strategy (token bucket or sliding window) plus an injected clock. On each call it asks the limiter; if allowed it delegates, else it throws a clear RateLimitExceeded or waits up to a timeout (a policy choice to state). Make the limiter thread-safe (atomic counters or a lock). Put a caching proxy in front if responses can be reused, so repeat calls do not spend quota.

How to answer

Interface, real client, proxy with a pluggable algorithm, clock injection for tests, thread safety, reject-or-wait policy, and proxy order.

Likely follow-ups
  • Several limits at once (3/s, 20/10 s, 60/min)? (Check all windows; admit only if every one allows; record in all.)
  • Across many servers? (Shared counter in Redis: see the HLD rate limiter.)
How does Spring's @Transactional work, and why does a self-call skip the transaction?

At startup Spring wraps the bean in a proxy: a JDK dynamic proxy if it is used through an interface, otherwise a CGLIB subclass. Other beans get the proxy injected. When they call a transactional method, the proxy's interceptor opens a transaction, calls the real method, and commits or rolls back on exception. A call from inside the bean uses this, which is the real object, not the proxy, so no interceptor runs. Fixes: move the method to another bean, inject the proxy of the bean itself, or use AspectJ weaving which changes the bytecode instead of wrapping.

How to answer

Proxy generation, interceptor around the call, then the this explanation. Mention that final or private methods cannot be intercepted by subclass proxies.

Likely follow-ups
  • JDK proxy vs CGLIB? (Interfaces only vs subclass; CGLIB cannot proxy final classes or methods.)
Write a virtual proxy that is safe when many threads call it at once.

Use double-checked locking with a volatile field: read the field; if null, lock, check again, create, assign. volatile stops another thread from seeing a half-constructed object. Alternatives: create eagerly if it is cheap enough, use a holder class (lazy and thread-safe by the class-loading rules), or in Java a Supplier memoised with a lock. Our Java demo's LazyQuoteProxy does exactly this.

How to answer

Show the double check, say why volatile, offer the holder idiom. See Singleton for the same reasoning.

Likely follow-ups
  • What if creation throws? (Do not cache the failure; the next call retries, or cache it with a backoff.)
Name the kinds of proxy, with one example each.

Virtual (lazy creation: Hibernate lazy association), protection (access checks: Collections.unmodifiableList, role checks), remote (gRPC or RMI stub), caching (read-through cache in front of a service), rate-limiting (API client with a quota), smart reference (std::shared_ptr, weakref.proxy, refcounting).

How to answer

"When, whether, where, how often, bookkeeping" covers them all.

Likely follow-ups
  • Which kind is an API gateway? (Several at once: protection, rate limiting, caching, and remote routing.)
What are the risks of a remote proxy?

It hides the network. Callers treat it like a local call: they loop over it, call it while holding locks, and forget timeouts and retries. Partial failure appears (the call may have run even though you got a timeout), so you need idempotency keys. Serialisation costs and version skew between client stub and server appear. Mitigations: make remote interfaces coarse-grained, return futures or name methods so remoteness is obvious, always set deadlines, and retry only idempotent calls.

How to answer

Name the fallacy ("the network is reliable"), then three concrete mitigations.

Likely follow-ups
  • How does gRPC expose deadlines on its stubs?
Where do you see Proxy in the Linux kernel?

Demand paging: an mmap region stands in for file contents, and pages are read only on first touch (virtual proxy). The page cache answers reads without touching the disk, and the dentry cache answers path lookups without calling the filesystem's lookup() (both caching proxies). NFS and FUSE inodes look like local files but forward operations to a server or a user-space daemon (remote proxy). kref, get_file()/fput() count references so the object is freed when the last user drops it (smart reference).

How to answer

Pick one kind, name what is controlled (when the page is read), and draw the parallel to the class version.

Likely follow-ups
  • What is the equivalent of the "self-invocation" trap there? (Code that bypasses the VFS and touches the underlying object directly skips the checks.)
Your caching proxy is synchronized. What goes wrong under load, and what is still missing?

A whole-method lock is held while the slow remote call runs, so one slow AAPL fetch blocks every cached INFY read. Fix: a ConcurrentHashMap<String, CompletableFuture<Entry>>; the first caller for a key installs a future and does the load with no lock held, and concurrent callers for the same key wait on that future. That also prevents a cache stampede (a hundred misses for one hot key all hitting the backend at once). Do not cache failures: remove the future if the load throws.

Still missing in our demo: the cache has a TTL but no size bound, so it grows with every symbol ever asked. Add an LRU or size cap (Caffeine in Java, functools.lru_cache or an OrderedDict in Python).

Likely follow-ups
  • Why not computeIfAbsent with the remote call inside? (The mapping function runs under the map's bin lock, so a slow load blocks other keys in that bin, and recursive updates on the same map are illegal.)
