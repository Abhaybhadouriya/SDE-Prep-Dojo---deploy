Dynamic proxies: how frameworks do it for you

A dynamic proxy is a proxy class the runtime generates while the program runs, instead of one you write by hand. Every method of the interface lands in one dispatch function, which can log, check or forward. From your world: it is like an ops table in which every slot points at the same generic_dispatch(op_id, args), or like LD_PRELOAD putting a wrapper in front of every libc call without recompiling the program.

  • Reflection = code asking the runtime about types at run time ("which methods does this interface have?") and calling a method found that way. Roughly: walking a symbol table and calling through the pointer you found.
  • JDK dynamic proxies (java.lang.reflect.Proxy): you give it the interfaces and one InvocationHandler (the dispatch function); it returns an object implementing those interfaces whose every call goes to handler.invoke(proxy, method, args). Interfaces only. Our Java tab builds one in eight lines.
  • Python: __getattr__ forwarding (our Python tab), unittest.mock.Mock (records calls), xmlrpc.client.ServerProxy (turns attribute calls into remote calls).

The one rule worth remembering for any framework: a proxy only sees calls that come in through it. A call the real object makes on itself (this.foo()) skips the proxy.

Level 5: Java framework follow-ups (only if your interviewer works in Spring or Hibernate)
  • Annotation = a tag such as @Transactional attached to a class or method; a framework reads it at start-up and acts on it. AOP (aspect-oriented programming) = adding the same behaviour (transactions, caching, security) around many methods without editing them, which in practice means "wrap the object in a generated proxy".
  • Subclass proxies (CGLIB, ByteBuddy, libraries that generate classes at run time): generate a subclass of a concrete class and override its methods. Spring uses JDK proxies when the bean implements an interface and a CGLIB subclass otherwise (Spring Boot defaults to CGLIB). A final class or method cannot be overridden, so it cannot be proxied this way.
  • Spring AOP: @Transactional, @Cacheable, @Async and security annotations work by wrapping your bean in a proxy that begins and commits the transaction, checks the cache, or hands the call to an executor.
  • Hibernate / JPA (the Java database mapping layer): a lazily loaded association is a proxy subclass of your entity; touching it after the database session is closed throws LazyInitializationException.
  • The self-invocation trap: inside a bean, this.saveAll() calling another @Transactional method of the same bean does not go through the proxy, so no transaction starts. Fix it by moving the method to another bean, or by injecting the bean's own proxy.
