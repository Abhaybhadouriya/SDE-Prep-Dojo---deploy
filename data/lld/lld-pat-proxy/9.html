When to use it, when not to

Use it when
  • An object is expensive to create and often not needed (virtual).
  • Access must be checked in one place, not in every caller (protection).
  • The real object lives in another process or machine and callers should not deal with sockets and serialisation (remote).
  • Repeated calls with the same input can be answered locally (caching), or a vendor quota must be respected (rate limiting).
  • You want cross-cutting control (transactions, metrics, audit logs) without touching business classes.
Avoid it, or watch out, when
  • There is nothing to control. An extra hop that only forwards is noise.
  • Hidden latency: a remote proxy makes a network call look like a cheap local call. Callers may loop over it. Name remote interfaces honestly and give them timeouts.
  • Stale data: a caching proxy needs a TTL or invalidation story.
  • Self-invocation bypasses the proxy (see above).
  • Identity and equality: a proxy is not the same object as its target; ==, getClass() and instanceof on concrete classes can surprise you.
  • Thread safety: lazy creation and caches inside a proxy need the same care as any shared state (double-checked locking with volatile, concurrent maps). Never hold a lock across the slow forwarded call: a synchronized caching proxy serialises every symbol behind one network call. Our CachingQuoteProxy keeps one in-flight CompletableFuture per key in a ConcurrentHashMap, and the rate limiter takes its permit under the lock but calls the target outside it.
