Why the pattern earns its place: the if-ladder it replaces

Without the transition table, every handler re-implements "is this move legal?" with its own ifs, and they drift apart:

OrderStatus onPayment(Order o, boolean ok) {
    if (o.status == CREATED && ok) { o.status = CONFIRMED; commit(o); }
    else if (o.status == CREATED) { o.status = CANCELLED; release(o); }
    else if (!ok && o.status == CONFIRMED) {     // late failure webhook...
        o.status = CANCELLED; release(o);         // ...releases committed stock: the real bug
    }
    return o.status;
}
void cancel(Order o) {
    if (o.status == CREATED) { o.status = CANCELLED; release(o); }
    else if (o.status == CONFIRMED || o.status == PACKED) { o.status = CANCELLED; restock(o); }
}
enum OrderStatus {
    CREATED, CONFIRMED, PACKED, DISPATCHED, CANCELLED, EXPIRED;
    boolean canMoveTo(OrderStatus n) { ... one table, read by every caller ... }
}
OrderStatus onPayment(String id, boolean ok) {
    synchronized (o) {
        if (o.status() != CREATED) return o.status();   // duplicate or late: ignored
        o.moveTo(ok ? CONFIRMED : CANCELLED);            // the only way status changes
        ...side effect for the winning transition only...
    }
}

With scattered ifs, the follow-up "add a RETURNED state" edits onPayment, cancel, the sweeper and every test. With the table it edits one enum row; the handlers keep calling moveTo.

From your world: the same move in C

enum order_state { CREATED, CONFIRMED, PACKED, DISPATCHED, CANCELLED, EXPIRED, NSTATE };
static const bool legal[NSTATE][NSTATE] = {
    [CREATED]   = { [CONFIRMED] = 1, [CANCELLED] = 1, [EXPIRED] = 1 },
    [CONFIRMED] = { [PACKED] = 1, [CANCELLED] = 1 },
    [PACKED]    = { [DISPATCHED] = 1, [CANCELLED] = 1 },
};
static int move_to(struct order *o, enum order_state n)
{ if (!legal[o->state][n]) return -EINVAL; o->state = n; return 0; }

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.

The order table is a protocol state table, the same shape as TCP's: one array says which moves are legal, and every event handler consults it instead of carrying its own copy of the rules.
