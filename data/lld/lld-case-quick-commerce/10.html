2. Deadlock and the sorted-lock rule

The Java demo makes half the threads list bread before milk on purpose. lockSorted walks a TreeSet of SKUs, so every thread locks in the same order and the four Coffman conditions cannot all hold (no circular wait). More in Deadlock: the fixes.

3. Check all, then reserve all

Inside the locks, reserveAll loops twice: first check every line, then apply every line. Reserving line by line and "rolling back" on the first failure also works but is easy to get wrong (forgetting to undo lines already applied). Two loops under the same locks are all-or-nothing by construction.

4. One winner per order

Payment, cancel and expiry each run both the transition and its side effect (commit, release, restock) inside one critical section on the order's monitor (synchronized (o) in Java, o.lock in Python). The transition table alone is not enough: CONFIRMED to CANCELLED is legal, so a payment-failure webhook that arrives after the success webhook (gateways retry and reorder deliveries) used to pass the table and release stock that was already committed, stealing another order's reservation. onPayment therefore acts only while the order is still CREATED and ignores every later webhook; a real cancellation goes through cancel(), which restocks according to the old state. Because cancel holds the same monitor, it cannot slip in between onPayment's moveTo(CONFIRMED) and commitAll. Two duplicate webhooks cannot both pass the "still CREATED?" check either. Lock order is always order first, then SKUs, never the reverse, so this adds no deadlock.

5. Expiry: lazy check plus sweeper

The sweeper is not on time to the millisecond, so onPayment also checks now > expiresAt itself. Between them, an expired hold can never be confirmed, and stock comes back within one sweep interval. In production, holds also live in Redis with a TTL or in the DB with an index on expires_at, so a restart does not leak reservations.

From your world

This is how conntrack and the neighbour table work: an entry has a timeout, a periodic GC worker reaps stale entries, and the fast path also checks expiry when it touches an entry, because the worker may be late. The "one winner" rule is the same as a test_and_clear_bit(PENDING) guard: whichever path clears the bit owns the cleanup, the other backs off.
