Registry pitfalls in real code

  • Duplicate keys. Two rules registering "CARD" should fail loudly, like -EEXIST. Silent overwrite hides bugs.
  • Unknown keys. Decide: throw (strict), or fall back to a default rule (a Null Object). Never return a magic number such as -1 that callers can add to a bill.
  • Global mutable state. A static registry makes tests leak into each other. Prefer a registry object that is built in the composition root and injected (as in the Java code), or freeze it after start-up.
  • Thread safety. If rules can be registered while requests run, use a ConcurrentHashMap or build the map once and publish it immutably. The kernel protects its lists with locks and RCU for the same reason.
  • Unload / lifetime. The kernel must stop a module from unloading while sockets still use its ops (module reference counts). In Java the analogue is hot-reloaded plugins holding stale references.
  • Order. When several handlers can apply (discount rules, netfilter hooks), make priority explicit rather than relying on registration order.

Scenario: Swiggy-style coupon engine

"Design the discount engine. Today: flat Rs 100 off, 20% off up to Rs 150, and free delivery. Marketing adds a new coupon type every few weeks."

A CouponService.apply() with an if (type == FLAT) ... else if (type == PERCENT) ... ladder, plus eligibility checks mixed into each branch.

A Coupon interface with isApplicable(cart) and discount(cart), one class per coupon type, a registry or factory keyed by type, and a DiscountEngine that picks the best applicable coupon. Purely numeric variants (a different percentage) are data, not classes. Say: "a new coupon type is a new class and one registration line; the engine is closed".
