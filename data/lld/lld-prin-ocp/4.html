Ways to make code open for extension

Polymorphism plus a registry is the most common answer, but it is not the only tool. Pick the one that matches the kind of change you expect.

TechniqueExtension pointGood forPattern page
Interface + implementationsa new classa family of interchangeable algorithms (fees, pricing, routing)Strategy
Registry / map lookupa new entrypicking an implementation by name or type at runtimeFactory + registry
Abstract base with hooksoverride a hook methodfixed steps, variable details (export CSV vs JSON)Template Method
Wrappinga new wrapperadding behaviour around a call (logging, retry, caching)Decorator
Events / listenersa new subscriber"when X happens, also do Y" (notify, audit, analytics)Observer
Handler chaina new handler in the chaina pipeline of checks or filters (validation, discounts)Chain of Responsibility
Data / configa new row in a tablerules that differ only in numbers (rate, cap, min fee)none: just data
Plugin discoverya new jar or modulethird-party extensions (Java ServiceLoader, kernel modules)Plugin

The last-but-one row matters in interviews. If BNPL differs from Card only in its percentage and cap, a new class is overkill; a new row ({method: "BNPL", pct: 3, capPaise: 5000}) keeps the code closed with even less code. Reach for classes when the logic differs, not just the numbers.

Java also offers enums with behaviour (each constant overrides an abstract method). That removes the switch, but adding a constant still edits the enum file. It is a good choice when the set of variants is truly fixed (days of the week, chess piece types) and a poor one when product adds variants every quarter.
