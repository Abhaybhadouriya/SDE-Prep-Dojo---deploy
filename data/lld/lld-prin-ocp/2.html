Before: the fee calculator with a type switch

A payment gateway charges a fee per payment method. (The rates below are made up for teaching.) The first version is a switch on an enum. It is short and clear, and for four methods it is honestly fine.

// BEFORE: every new payment method means editing this tested method.
public class FeeBefore {
    enum Method { UPI, CARD, NETBANKING, WALLET }

    static long feePaise(Method m, long amountPaise) {
        switch (m) {
            case UPI:        return 0;                                    // made-up demo rates
            case CARD:       return Math.round(amountPaise * 0.02);
            case NETBANKING: return 1000;                                 // flat Rs 10
            case WALLET:     return Math.max(500, Math.round(amountPaise * 0.015));
            default: throw new IllegalArgumentException("unknown method " + m);
        }
    }

    public static void main(String[] args) {
        for (Method m : Method.values())
            System.out.println(m + " fee on Rs 1000 = " + feePaise(m, 100_000) / 100.0);
        // Adding BNPL: edit the enum, edit this switch, edit every other switch on Method
        // (refund rules, settlement days, UI labels...) and re-test all of them.
    }
}

The trouble starts when product says "add Buy-Now-Pay-Later (BNPL)". The switch in feePaise() is rarely the only one. Refund rules, settlement days, risk checks and UI labels also switch on the same enum. Every one must be found and edited. Miss one and you get the default branch at runtime, in production.

Refactoring.guru lists this as the Switch Statements smell, and the cure as Replace Conditional with Polymorphism.
