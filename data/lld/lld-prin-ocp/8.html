Interview questions

Explain the Open/Closed Principle with an example.

Modules should be open for extension and closed for modification: you add new behaviour by adding new code, not by editing tested code. Example: a fee calculator with a switch over payment methods must be edited for every new method. Replace each branch with a class implementing FeeRule, look rules up in a registry, and a new method like BNPL becomes one new class plus one registration line.

How to answer

Definition in one line, a before/after in 30 seconds, then the diff test (one new file, one wiring line).

Likely follow-ups
  • Where does the switch go?
  • Is OCP the same as Strategy?
Design fare calculation for Auto, Mini, Sedan and future vehicle types so that adding a type does not change existing code.

Define FareStrategy with fare(trip). Implement one per vehicle type. Keep a registry from VehicleType to strategy, built at start-up. FareService looks up the strategy and adds cross-cutting parts (surge, taxes) as decorators or separate steps. If types differ only in base fare and per-km rate, store those as data and use one strategy class.

How to answer

Show the interface, the registry, and the data-vs-class judgement. Mention surge as a separate, composable concern.

Likely follow-ups
  • How would you apply surge pricing?
  • How do you test all strategies?
Does OCP mean you can never modify a class?

No. You fix bugs, and you change the composition root to register new parts. OCP is about not editing working code to add a new variant along an axis you expected to change. You also cannot be closed against every change (strategic closure); you choose the likely axes and accept that a change to the interface itself will touch implementations.

How to answer

Correct the absolute reading. Name strategic closure and the composition root.

Likely follow-ups
  • How do you choose which axis to close?
  • What happens when the interface must change?
How is OCP related to Strategy, Factory and Dependency Inversion?

OCP is the goal; patterns are ways to reach it. Strategy gives the interchangeable implementations. A Factory or registry hides which concrete class is created, so callers stay closed. Dependency Inversion makes high-level code depend on the abstraction, which is what lets it stay unchanged when new implementations appear.

How to answer

Principle = goal, pattern = mechanism. One sentence per pattern.

Likely follow-ups
  • Which other patterns support OCP?
  • Can a Factory itself violate OCP?
Your factory has a switch on type to create objects. Isn't that an OCP violation?

It moves the violation to one place, which is usually acceptable: the factory is the single spot that knows the concrete classes. To make even the factory closed, use a registry that implementations add themselves to (a map of suppliers), or plugin discovery such as Java's ServiceLoader. The cost is less explicit wiring and errors that show up at runtime rather than compile time.

How to answer

Admit the trade-off honestly; show the registry/plugin options and their costs.

Likely follow-ups
  • How does ServiceLoader work?
  • How do you catch a missing registration early?
Give an OCP example from operating systems or networking.

Linux TCP congestion control: the core calls through struct tcp_congestion_ops, and algorithms such as Reno, CUBIC and BBR are modules that register themselves with tcp_register_congestion_control(). Choosing one is a sysctl or setsockopt(TCP_CONGESTION). Netfilter hooks and register_filesystem() follow the same pattern: the core is closed, new behaviour plugs in through an ops table.

How to answer

Use your background: name the struct, the register call and how one is selected.

Likely follow-ups
  • How does the kernel stop a module unloading while in use?
  • How is the ops list protected for concurrent readers?
