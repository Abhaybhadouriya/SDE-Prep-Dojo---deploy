Where OCP stops: strategic closure

No code can be closed against every possible change. Martin calls this strategic closure: you choose which kinds of change to protect against. The fee design above is closed against "new payment method". It is not closed against "fees now depend on the merchant's plan", which changes the FeeRule interface itself. Interfaces are the hard part to change later, so choose the axis carefully.

  • First case: just write it. One payment method does not need an interface.
  • Second or third case: consider the seam. When the second variant arrives, or when the interviewer tells you more are coming, extract the interface. This matches the "rule of three" and keeps you clear of YAGNI.
  • Ask in the interview. "Which parts are likely to change: vehicle types, pricing, payment?" The answer tells you where the sockets go. Spending ten minutes on extension points nobody asked for is a common machine-coding mistake.
  • Stable code can stay a switch. A switch over HTTP status families or over the four directions of a snake game is fine.
What OCP buys you
  • Old, tested code is not touched, so no re-testing and no regressions there.
  • Each variant is small and testable alone.
  • Teams can add variants in parallel without merge conflicts.
What it costs
  • More classes and one level of indirection.
  • The interface is a commitment; changing it later touches every implementation.
  • Runtime lookup can fail (unknown key), so add a clear error or a default rule.
