Interview questions

What is the difference between an abstract class and an interface?

An interface is a contract: method signatures (plus default/static helpers since Java 8) with no instance state and no constructors; a class can implement many. An abstract class is a partially implemented class: it can hold fields, constructors, finished and final methods, and abstract methods; a class can extend only one. Use an interface for a capability shared by unrelated classes, an abstract class for a family that shares code and state.

How to answer

Lead with the one-line meaning (contract vs partial implementation), then three concrete differences (state, constructors, multiple inheritance), then when to use each with an example from a design (PaymentGateway interface; AbstractNotifier base).

Likely follow-ups
  • Since Java 8 interfaces have method bodies; is there still a difference? (Yes: no state, no constructors, no final/protected methods.)
  • Can an abstract class have no abstract methods?
Why were default methods added, and what happens when two interfaces define the same default?

To evolve interfaces without breaking existing implementers (Java 8 added forEach, stream, removeIf and others to collection interfaces this way). On a clash: superclass methods win over interface defaults; a more specific sub-interface wins over its parent; otherwise the class must override the method and may call A.super.m() to pick one.

How to answer

Give the motivation in one sentence, then the three rules in order, then the Logs.super.describe() snippet.

Likely follow-ups
  • Can a default method override equals or hashCode? (No; a default method may not override a public Object method.)
  • Does this make Java support multiple inheritance? (Of behaviour, partly; never of state.)
Where would you use interfaces in your machine-coding solution?

At the seams that vary or reach outside the process: repositories (in-memory now, database later), payment gateways, notification channels, pricing or discount rules, search and sort strategies, ID generators and clocks (so tests can fix time). The service receives them through its constructor. Plain entities and value objects stay concrete.

How to answer

Name 3 to 5 specific interfaces from your own design, say what varies behind each, and show one constructor that takes them. Avoid "an interface for every class".

Likely follow-ups
  • How would you add a new payment provider? (New class, wire it in main, no service edits.)
  • How would you test the order flow without a real gateway?
How do you write an interface in C++, and why must it have a virtual destructor?

A class with only pure virtual functions (virtual bool allow(...) = 0;) and a virtual ~RateLimiter() = default;. It cannot be instantiated. The virtual destructor matters because objects are usually owned through the interface pointer (std::unique_ptr<RateLimiter>); without it, deleting through that pointer is undefined behaviour and skips the derived destructor.

How to answer

Write the three-line class, then explain ownership through base pointers. Mention that C++ allows multiple inheritance, so several interfaces are fine.

Likely follow-ups
  • Can a pure virtual function have a body? (Yes, defined outside the class; derived classes can call it explicitly. A pure virtual destructor must have one.)
What does "program to an interface, not an implementation" mean?

Declare variables, fields, parameters and return types using the abstract type (List, PaymentGateway) rather than a concrete class (ArrayList, RazorGateway), and choose the concrete class in one place. The calling code then works with any implementation, can be tested with fakes, and does not change when a new implementation arrives.

How to answer

Show List<Order> orders = new ArrayList<>(); as the tiny example, then the CheckoutService constructor taking a PaymentGateway. Connect it to Dependency Inversion.

Likely follow-ups
  • Who creates the concrete object then? (main, a factory, or a DI container.)
When would you use both an interface and an abstract class for the same concept?

When clients need a flexible contract but implementers would otherwise duplicate a lot of code. Publish the interface (clients depend on it) and provide an abstract skeletal implementation that builds the convenience methods on a few primitives (the JDK's List / AbstractList). Implementers extend the skeleton, or implement the interface directly if they already have a parent class.

How to answer

Draw the three layers. Give a design example: Repository<T> interface plus InMemoryRepository<T> abstract base holding the map and ID generation.

Likely follow-ups
  • What goes wrong if clients depend on the abstract class instead? (They are tied to its inheritance chain and its protected internals.)
