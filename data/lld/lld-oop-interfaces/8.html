"Where would you use interfaces?"

A Cleartrip backend candidate who built a food-ordering system in a 90-minute machine-coding round was asked this in the next-day follow-up, along with "why this class hierarchy?" and "how would you persist data if a database was introduced?" (LeetCode Discuss, July 2026). The interviewer wants to see that you know where the design will change.

Scenario: food-ordering system, follow-up round

You wrote User, Restaurant, MenuItem, Order and one big FoodOrderingService that keeps HashMaps. The interviewer asks: "Where would you use interfaces here?"
"Everywhere. I would make an interface for every class: IUser, IRestaurant, IOrder..." (Interfaces for plain data add noise and show no judgement.)
"At the points that vary or touch the outside: OrderRepository / RestaurantRepository (in-memory today, a database tomorrow, and that answers your persistence question), PaymentGateway (several vendors, a fake in tests), NotificationSender (SMS, email, push), ItemSearchStrategy or a Comparator for sorting by price or rating, and PricingRule for discounts and delivery fees. The service takes these in its constructor. Entities like Order and MenuItem stay concrete classes."
Follow-ups: "How does the service get the right implementation?" (constructor injection, wired in main). "What would an abstract class add?" (shared code, for example an AbstractRepository<T> holding the map and ID generation). "How do you make the in-memory repository thread-safe?"
