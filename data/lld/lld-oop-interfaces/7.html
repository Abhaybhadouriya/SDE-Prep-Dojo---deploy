Using both: interface on top, skeleton underneath

In real libraries the answer to "interface or abstract class?" is often "both". The JDK does this with collections: List is the interface, AbstractList is a skeletal implementation that builds most methods (iterator, indexOf, equals, hashCode) on top of get and size, and ArrayList extends it. Clients depend on List. Authors of a new list can extend AbstractList to save work, or implement List directly if they need a different base class.

Design heuristics for an LLD round

  • Start with interfaces at the seams. Anything that has (or will have) more than one implementation, or that touches the outside world: payment, notifications, storage, pricing rules, search ranking, clocks.
  • Add an abstract class only when you see duplication. If SmsNotifier and EmailNotifier both count sends and both format a header, pull that into AbstractNotifier.
  • Keep interfaces small. Five unrelated methods on one interface force every implementer to write stubs. Split them into roles.
  • Do not force an interface onto a value. Money, Address or OrderId rarely need one; they are records or final classes.
  • Prefer composition for sharing behaviour across families. An abstract class ties you to one parent forever; see Composition over Inheritance.
