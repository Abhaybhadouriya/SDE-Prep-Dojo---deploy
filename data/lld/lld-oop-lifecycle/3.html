Destructors, finalizers, try-with-resources and RAII

A destructor is the mirror of a constructor: code that runs when an object's life ends, to give back what it holds. "What it holds" is the important part. Memory is only one kind of resource. Others are file descriptors, sockets, locks, database connections, DMA mappings, IRQ lines. Different languages answer "who runs the cleanup, and when?" very differently.

C++: deterministic destructors and RAII

In C++, a local object's destructor ~T() runs exactly when it goes out of scope, including when an exception flies through. Objects in a scope are destroyed in the reverse order of construction. This gives the idiom called RAII (Resource Acquisition Is Initialization): acquire the resource in the constructor, release it in the destructor, and let scope do the rest. std::lock_guard, std::unique_ptr, std::fstream and std::vector all work this way.

struct Guard {
    const char* name;
    explicit Guard(const char* n) : name(n) { std::printf("  acquire %s\n", name); }
    ~Guard() { std::printf("  release %s\n", name); }
};

static void work(bool fail) {
    Guard lock("lock");
    Guard file("file");
    if (fail) throw 42;           // both guards still release, in reverse order
    std::printf("  work done\n");
}
$ g++ -std=c++14 -Wall -Wextra -o buffer buffer.cpp && ./buffer
3) RAII on exception:
  acquire lock
  acquire file
  release file
  release lock

From your world

This is your goto err_unmap; ... err_unmap: dma_unmap_single(); err_free: kfree(); ladder, generated by the compiler. Each object you finish building adds one rung; leaving the scope by any path walks back down the rungs. The kernel itself has started to adopt this: newer kernels have scope-based cleanup helpers (__free(), guard(mutex) in linux/cleanup.h) built on the compiler's cleanup attribute, which is RAII in C.

Java: no destructors, and finalizers are on the way out

Java has a garbage collector (GC). You never free memory yourself; the GC reclaims an object some time after nothing references it. "Some time" is the catch: maybe in a millisecond, maybe never before the program exits. That is fine for memory and terrible for a socket or a lock.

Early Java offered finalize(), a method the GC might call before reclaiming an object. It turned out to be a bad idea: no timing guarantee, no ordering guarantee, it can resurrect the object, it slows the GC, and exceptions inside it are ignored. Finalization was deprecated for removal by JEP 421 (Java 18). For a safety net, the modern tool is java.lang.ref.Cleaner, but a safety net is not the plan.

The plan is explicit close: the class implements AutoCloseable (one method, close()), and callers use try-with-resources. Java then guarantees that every resource opened in the try (...) header is closed when the block ends, in reverse order of opening, even if the block throws. If close() also throws, that second exception is not lost: it is attached to the first one as a suppressed exception.

  1. Resources open left to right. A is fully constructed before B starts.
  2. B opens. If B's constructor had thrown, only A would be closed (B never existed).
  3. The body throws. Java does not jump straight to catch: it first closes what was opened.
  4. Close in reverse order: B first. Its close() throws too; Java records that exception as suppressed instead of losing the original.
  5. Then A is closed, even though closing B failed.
  6. The catch receives the original exception; e.getSuppressed() holds the close failure.
3) try-with-resources:
  open  A
  open  B
  close B
  close A
  caught: work failed while using B
  suppressed: close failed for B

Python's equivalent is the with statement and context managers (__enter__ / __exit__), or contextlib.ExitStack for a dynamic number of resources. Python's __del__ exists, but like finalize() you should not rely on it for anything important: its timing depends on the interpreter and on reference cycles.

"Does Java have destructors?" Strong answer: "No. Memory is the GC's job and its timing is not deterministic, so Java separates memory from resources. Resources implement AutoCloseable and are released by try-with-resources, which closes in reverse order and keeps close failures as suppressed exceptions. finalize() is deprecated for removal (JEP 421); Cleaner is only a safety net."
