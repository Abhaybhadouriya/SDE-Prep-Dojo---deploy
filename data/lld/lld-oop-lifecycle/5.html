The rule of three, five and zero (C++)

In C++, the compiler can write five "special member functions" for you: destructor, copy constructor, copy assignment, move constructor and move assignment. The generated versions just copy or move each member. That is perfect when each member already knows how to copy itself (std::string, std::vector, int). It is a disaster when a member is a raw owning pointer.

  1. Rule of three (C++98): if your class needs a custom destructor, copy constructor or copy assignment, it almost certainly needs all three. A custom destructor is the tell: it means the class owns something the defaults do not understand.
  2. Rule of five (C++11): add the move constructor and move assignment. If you declare any of the copy operations or the destructor, the compiler stops generating moves, so your class silently falls back to (slower) copies unless you write them.
  3. Rule of zero: best of all, write none of them. Hold resources in members that already manage themselves (std::vector, std::string, std::unique_ptr, std::shared_ptr) and the generated five are correct. Only a small "resource handle" class should ever define the five; everything else composes those handles.
class PacketBuf {
public:
    explicit PacketBuf(std::size_t n) : len_(n), data_(new unsigned char[n]) {}
    ~PacketBuf() { delete[] data_; }          // custom destructor...
    // ...but compiler-made copy ctor / copy assign copy the POINTER.
private:
    std::size_t len_;
    unsigned char* data_;
};

void f() {
    PacketBuf a(64);
    PacketBuf b = a;     // b.data_ == a.data_
}                        // ~b frees, then ~a frees the same block: double free
class PacketBuf {
public:
    explicit PacketBuf(std::size_t n) : len_(n), data_(new unsigned char[n]) {}
    ~PacketBuf() { delete[] data_; }                                   // 1
    PacketBuf(const PacketBuf& o)                                      // 2 deep copy
        : len_(o.len_), data_(new unsigned char[o.len_]) {
        if (len_) std::memcpy(data_, o.data_, len_); // moved-from source has data_ == nullptr: memcpy(.., nullptr, 0) is UB
    }
    PacketBuf& operator=(const PacketBuf& o) {                         // 3 copy-and-swap
        PacketBuf tmp(o);
        swap(tmp);
        return *this;
    }
    PacketBuf(PacketBuf&& o) noexcept : len_(o.len_), data_(o.data_) { // 4 steal
        o.data_ = nullptr; o.len_ = 0;
    }
    PacketBuf& operator=(PacketBuf&& o) noexcept {                     // 5
        if (this != &o) {
            delete[] data_;
            data_ = o.data_; len_ = o.len_;
            o.data_ = nullptr; o.len_ = 0;
        }
        return *this;
    }
    void swap(PacketBuf& o) noexcept { std::swap(len_, o.len_); std::swap(data_, o.data_); }
private:
    std::size_t len_;
    unsigned char* data_;
};
class Frame {
public:
    explicit Frame(std::size_t n) : bytes_(n, 0) {}
    std::size_t size() const { return bytes_.size(); }
private:
    std::vector<unsigned char> bytes_;   // copy, move and destroy are correct for free
};

Notice two details in the output. After the move, a is empty but still a valid object (its destructor runs and does nothing, which is why the move constructor sets o.data_ = nullptr). And there are exactly two destructor lines for two heap blocks: no leak, no double free. Copy-and-swap makes copy assignment safe for self-assignment and gives the strong exception guarantee: if allocating the copy throws, *this is untouched.

Mark move operations noexcept. std::vector only moves its elements during a resize when the move constructor cannot throw; otherwise it copies them to keep its own exception guarantee.

To forbid copying entirely (a mutex, a device handle, a singleton), write T(const T&) = delete; T& operator=(const T&) = delete;. In Java, simply do not offer a copy constructor and do not implement Cloneable.
