Conditions: waiting for something to become true

A lock answers "who may touch the data". It does not answer "the data is not ready yet, what now?". Spinning in a loop (while (queue.isEmpty()) {}) burns a whole CPU core. Sleeping in a loop (Thread.sleep(10)) is slow and still wastes work. The right tool is a condition variable: give up the lock and sleep, atomically, until another thread says "it might be true now".

class Gate {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition opened = lock.newCondition();
    private boolean open;                    // the "condition predicate", guarded by lock

    void await() throws InterruptedException {
        lock.lock();
        try {
            while (!open) {                  // WHILE, never IF
                opened.await();              // atomically: release lock + sleep; re-lock on wake
            }
            // here: we hold the lock AND open is true
        } finally { lock.unlock(); }
    }

    void open() {
        lock.lock();
        try {
            open = true;                     // change the state first ...
            opened.signalAll();              // ... then wake the waiters (while holding the lock)
        } finally { lock.unlock(); }
    }
}

Why the check must be a while loop

  1. Spurious wakeups. The Condition documentation explicitly allows a thread to wake up without any signal. POSIX pthread_cond_wait says the same. Your loop is what makes a spurious wakeup harmless.
  2. Stolen state. Between the signal and the moment the woken thread gets the lock back, a third thread can take the lock first and consume the item. When you finally run, the queue is empty again.
  3. One condition, many reasons. With Object.wait() there is only one wait set per object, so producers and consumers share it. A thread may wake for a reason that is not its own.

From your world

The kernel macro wait_event(wq, condition) is literally this loop: it sets the task state, checks condition, calls schedule(), and checks again after every wake. wake_up(&wq) is signalAll(). The "set state, then check, then sleep" ordering exists for the same reason Java makes await() release the lock atomically: to avoid the lost wakeup, where the signal arrives between your check and your sleep and nobody ever wakes you.

signal or signalAll?

signal() (like notify()) wakes one waiter; signalAll() wakes all of them. Use signal() only when every waiter on that condition waits for the same thing and any one of them can make progress, for example "one item was added, wake one consumer". If waiters on one condition wait for different things, signal() can wake the wrong one and the right one sleeps forever. With Object.wait/notify there is only one wait set, which is why the safe default there is notifyAll(). Separate Conditions (notFull, notEmpty) let you use the cheaper signal() safely.
