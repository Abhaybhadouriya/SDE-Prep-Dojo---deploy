Why we need locks at all

A race condition happens when the result depends on which thread runs first. The classic example is count++. It looks like one step, but the machine does three: read count, add one, write it back. Two threads can both read 41, both add one, and both write 42. One increment is lost.

The part of the code that touches the shared data is the critical section. A lock makes the critical section run by one thread at a time, so the three steps behave like one. A lock in Java also does a second job that is easy to forget: it makes the writes done before unlock visible to the next thread that does lock. Without it, another core may keep reading a stale value from its cache. (The Java memory model calls this a happens-before edge: everything before an unlock happens-before everything after the next lock of the same lock.)

Rule of thumb: if two threads touch the same mutable data and at least one of them writes, every access needs the same lock, reads included. A lock only protects data when every thread agrees to use it.
