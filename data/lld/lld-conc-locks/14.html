Quiz

Why is lock.lock() called before the try, not inside it?

  1. It is faster
  2. The compiler requires it
  3. If lock() throws, we never got the lock, so the finally must not unlock it
  4. It makes the lock fair
Unlocking a lock you do not hold throws IllegalMonitorStateException and hides the real error. Take the lock, then enter the try.

A consumer does if (queue.isEmpty()) notEmpty.await(); queue.remove();. What can go wrong?

  1. Nothing, await only returns after a signal
  2. A spurious wakeup or another consumer taking the item can make remove() run on an empty queue
  3. It deadlocks immediately
  4. await does not release the lock
Returning from await() does not mean the condition holds. Use while to re-check after every wake.

Which feature does synchronized NOT have?

  1. Giving up after a timeout
  2. Reentrancy
  3. Memory visibility on unlock/lock
  4. Automatic release on exception
Only ReentrantLock.tryLock(timeout) can give up. synchronized is reentrant, gives visibility, and releases automatically.

You must allow at most 10 concurrent calls to a payment provider. Best primitive?

  1. A fair ReentrantLock
  2. CountDownLatch(10)
  3. CyclicBarrier(10)
  4. Semaphore(10)
A semaphore counts permits: acquire before the call, release in finally. tryAcquire(timeout) adds load shedding.

What is the key difference between a mutex and a binary semaphore?

  1. A semaphore is always faster
  2. A mutex has an owner that must unlock it; any thread can release a semaphore
  3. Only semaphores can be reentrant
  4. There is no difference
Ownership is the difference. It enables reentrancy and debugging for mutexes, and signalling for semaphores.

When is a spinlock the right choice?

  1. When the critical section does disk I/O
  2. On a single-core machine without preemption control
  3. When the section is a few instructions and the holder is running on another CPU and never sleeps
  4. Whenever you want fairness
Spinning only pays when the wait is shorter than a sleep/wake round trip. If the holder sleeps or cannot run, spinning burns CPU for nothing.

Two threads transfer A to B and B to A, each locking "from" then "to". The fix that removes the deadlock completely is:

  1. Always lock the account with the smaller id first
  2. Make the lock fair
  3. Add Thread.sleep between the two locks
  4. Use notifyAll()
A global lock order breaks the circular-wait condition. Fairness and sleeping do not.
