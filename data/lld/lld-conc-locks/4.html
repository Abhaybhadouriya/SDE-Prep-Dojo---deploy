ReentrantLock: the same lock with more buttons

java.util.concurrent.locks.ReentrantLock gives the same mutual exclusion and the same visibility guarantee as synchronized. It adds features synchronized does not have. The price is that you must unlock, always in a finally block.

private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();          // take it OUTSIDE the try: if lock() itself fails, we must not unlock
    try {
        // critical section
    } finally {
        lock.unlock();    // runs on return, on break, on exception
    }
}

The answer interviewers want: "I default to synchronized because it cannot leak a lock. I switch to ReentrantLock when I need one of its features: tryLock with a timeout, interruptible waiting, fairness, or more than one condition, like notFull and notEmpty in a bounded queue." Then name the feature you are using.

Fairness. A fair lock hands the lock to the thread that has waited longest. That stops starvation but costs throughput, because a thread that is already running and could take the lock right now must park and let a sleeping thread wake up first. The default (non-fair) lock lets a newcomer "barge" ahead. The JDK documentation also notes that the untimed tryLock() barges even on a fair lock. Use fairness only when you have measured starvation.

Java 21 virtual threads. In Java 21, a virtual thread that blocks inside a synchronized block pins its carrier OS thread, so code that used virtual threads was often told to prefer ReentrantLock. JDK 24 (JEP 491) removed most of that pinning. If an interviewer asks about Loom, this is the point to mention.
