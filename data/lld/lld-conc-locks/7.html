Semaphores: N permits instead of one key

A semaphore is a counter of permits. acquire() takes one, and blocks while the count is zero. release() gives one back and wakes a waiter. A semaphore with 3 permits lets up to 3 threads into a region at once. It is the natural tool for "limit concurrency": database connections, calls to a slow third-party API, parallel downloads.

class ConnectionLimiter {
    private final Semaphore permits = new Semaphore(3, true);   // fair: FIFO order of waiters

    Result query(String sql) throws InterruptedException {
        permits.acquire();               // blocks while 3 are inside
        try {
            return db.run(sql);
        } finally {
            permits.release();           // ALWAYS give it back
        }
    }

    Result queryOrFail(String sql) throws InterruptedException {
        if (!permits.tryAcquire(200, TimeUnit.MILLISECONDS))
            throw new BusyException("DB saturated");                // load shedding
        try { return db.run(sql); } finally { permits.release(); }
    }
}

Semaphore vs mutex: the ownership question

A semaphore with one permit (a binary semaphore) looks like a mutex but is not the same thing. A mutex has an owner: only the thread that locked it may unlock it, and a reentrant mutex lets the owner lock it again. A semaphore has no owner: any thread may call release(), even one that never called acquire(). That makes a semaphore useful for signalling between threads (start one at 0 permits; thread A waits with acquire(), thread B signals with release()), and dangerous as a plain lock (a bug can release a permit you never took, and now 4 threads fit in a 3-permit pool). Java's Semaphore will happily count above its starting value; Python's BoundedSemaphore raises an error instead, which catches that bug.

From your world

Linux moved most code from struct semaphore to struct mutex for exactly this reason: a mutex has an owner, which lets the kernel debug it (who holds it, did the same task unlock it) and lets it spin briefly while the owner is still running on another CPU. Semaphores stayed where a real count or cross-task signalling is needed, and struct completion took over the "wait for this event" case.
