Choosing a tool in an LLD round

  1. Can you avoid sharing? Immutable objects, one thread owning the data, or a concurrent collection (ConcurrentHashMap) need no lock in your code at all. See Thread-Safe Singleton & Immutability.
  2. One field, one counter? Use an atomic (AtomicInteger, LongAdder).
  3. Several fields that must change together? synchronized on a private lock, or one ReentrantLock.
  4. Need to wait for a state? ReentrantLock + one Condition per reason (or wait/notifyAll in a pinch).
  5. Need a limit of N? Semaphore(N).
  6. Need "do not hang"? tryLock(timeout) / tryAcquire(timeout) and a clear "busy" result.
  7. Many readers, few writers? A read-write lock (its own lesson in this section).
  8. Lock granularity. One lock per seat, per account, per parking spot, not one lock for the whole system. Fine-grained locks give more parallelism; then you need a lock order. This is the heart of the Dealing with Contention pattern at the HLD level.

Common mistakes we see in mock rounds:

  • lock.lock() without try/finally: one exception and the lock is held forever.
  • if (!ready) cond.await();: works in the demo, fails under load.
  • Locking writes but not reads ("reads are safe"): they are not, because of visibility.
  • Calling await() or signal() without holding the lock: Java throws IllegalMonitorStateException.
  • Synchronising on a String literal or a boxed Integer: those objects are shared across the whole JVM, so unrelated code can lock the same object.
  • Holding a lock while calling a listener, a network service or a user callback.
