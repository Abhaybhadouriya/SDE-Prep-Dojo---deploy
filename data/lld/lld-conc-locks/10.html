Spinlock vs mutex: spin or sleep?

When a lock is busy, a thread has two choices. A spinlock keeps the CPU and loops on an atomic test until the lock is free. A mutex (blocking lock) asks the operating system to put the thread to sleep and wake it when the lock is released. Neither is always better; it depends on how long the lock is held compared to the cost of sleeping and waking.

Real locks are hybrids. A Linux pthread mutex is built on a futex ("fast user-space mutex"): the uncontended lock and unlock are a single atomic instruction in user space, and the thread only enters the kernel to sleep when there is contention. The kernel's own struct mutex spins for a short while if the owner is currently running on another CPU, and sleeps otherwise (the kernel's mutex design notes call this optimistic spinning). The JVM's monitors also try cheap atomic operations first and only park the thread through the OS when contention persists. So in Java you almost never write a spinlock: synchronized already spins a little for you.

From your world

spin_lock_irqsave() exists because an interrupt handler on the same CPU might want the same lock: if you held it with interrupts enabled, the handler would spin forever on a lock its own CPU holds. Java has no interrupt context, so this case does not exist there, but the rule "never sleep holding a spinlock" maps to a Java rule: never do blocking I/O or call unknown code while holding a lock. Every other thread that needs the lock now waits for your network call.
