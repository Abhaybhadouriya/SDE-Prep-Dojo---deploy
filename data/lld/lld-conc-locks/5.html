tryLock: do not wait forever

A thread blocked in lock() waits as long as it takes. If two threads each hold one lock and want the other, they wait forever: a deadlock. The textbook case is a money transfer that locks the source account and then the destination, while another thread transfers the other way.

void transfer(Account from, Account to, int amount) {
    synchronized (from) {              // T1 locks A, T2 locks B
        synchronized (to) {            // T1 wants B, T2 wants A: stuck forever
            from.balance -= amount;
            to.balance   += amount;
        }
    }
}
boolean transfer(Account from, Account to, int amount) throws InterruptedException {
    Account first  = from.id < to.id ? from : to;   // 1. global order: lower id first
    Account second = from.id < to.id ? to : from;
    if (!first.lock.tryLock(50, TimeUnit.MILLISECONDS)) return false;   // 2. time limit
    try {
        if (!second.lock.tryLock(50, TimeUnit.MILLISECONDS)) return false;
        try {
            if (from.balance < amount) return false;
            from.balance -= amount;
            to.balance   += amount;
            return true;
        } finally { second.lock.unlock(); }
    } finally { first.lock.unlock(); }
}

Two defences are stacked here. Lock ordering (always take the lower id first) makes a cycle impossible, so it removes the deadlock completely. tryLock with a timeout is a safety net: if something is slow, the caller gets false and can retry with a small random back-off or tell the user "busy, try again". Our demo runs 4 threads doing 8,000 opposite-direction transfers; total money stays 2,000 and nothing hangs.

  1. Naive code locks the source first. T1 takes A, T2 takes B at the same moment.
  2. T1 now wants B and T2 wants A. Neither will ever let go: a wait-for cycle, which is a deadlock.
  3. Fix: always lock the account with the lower id first. Both threads try A first; T2 blocks on A while holding nothing.
  4. T1 gets A, then B, does the transfer and releases both.
  5. T2 now gets A and B in the same order. A cycle needs someone to lock "backwards", and nobody does. tryLock is the extra safety net for slow paths.

The full theory of deadlock (the four Coffman conditions, livelock, thread dumps) is the subject of Deadlock, Livelock & Starvation. For locks across many machines instead of many threads, see Distributed Lock Service.
