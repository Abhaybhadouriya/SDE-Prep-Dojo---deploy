The story: the train on the toy table

Explain like I'm 5

Imagine a toy train made of wooden blocks on a chessboard table. Every second, you move the train one square. You do not slide every block. You take the last block from the back and put it in front. The train looks like it moved, but you touched only one block.

When the train reaches a sweet, you put a new block in front and do not take one from the back. Now the train is one block longer. If the front block runs off the table, or onto the train's own blocks, the game is over.

That is the whole snake game. The table is a Board. The train is a Snake: an ordered line of cells with a head and a tail. The sweet is food. Each "second" is a tick of a game loop. The trick in the story (move the back block to the front) is why a good design moves the snake in O(1), whatever its length. That trick is exactly what the Zomato interviewer asked for: "movement in O(1), and explain your data structure choices".

From your world

The snake body is a struct list_head queue: list_add() a new head, list_del() the tail, both O(1). To answer "is this cell part of the snake?" in O(1) you keep a hash set next to it, just like conntrack keeps a hash table for lookup and a list for order. The game loop is a timer: one tick per period, like a jiffy-driven timer callback or a NAPI poll. Key presses come from another context (the input thread) into a tiny bounded buffer that the tick drains, the same producer/consumer split as an interrupt handler filling a ring and a softirq emptying it. The pluggable rules (walls or wrap-around, how food appears, how the snake grows) are ops tables: struct boundary_ops { bool (*next)(...); }.

Interfaces in C terms: every interface on this page is, in C, a struct of function pointers; each implementation fills one in, like file_operations. Java and C++ build that table (the vtable) for you, and every object carries a pointer to it. More in OOP from C structs and polymorphism and vtables.
