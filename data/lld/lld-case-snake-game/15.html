Interview follow-ups

How do you make each move O(1)? Why those data structures?

A move adds one cell at the head and removes one at the tail; the middle does not change. A deque (Java ArrayDeque, Python collections.deque, C++ std::deque) does both ends in O(1). The collision check needs "is this cell part of the body?", which is O(length) on a deque, so I also keep a hash set of the same cells: O(1) average lookup. Both are updated together inside advance(). Memory is O(length) twice, which is fine.

How to answer

Name the two operations (move ends, membership), the structure for each, and the cost of keeping two views in sync (both change in one method, under one lock).

Likely follow-ups
  • Could a boolean grid replace the set? (Yes: O(rows x cols) memory but faster and no hashing; good for small boards.)
  • Why not a linked list of nodes? (Same O(1), more allocation; deque is the standard tool.)
The head moves into the cell the tail is leaving. Collision or not?

Not a collision, because the tail leaves in the same tick, unless the snake grows this tick (then the tail stays and it is a collision). So the check is: in the set, and not (it is the tail and no growth is pending). Apply growth before this check, and in advance() remove the tail from the set before adding the new head. LeetCode 353 uses the same rule.

Likely follow-ups
  • Which test proves it? (A length-4 snake circling a 2 x 2 square for 8 ticks must stay alive.)
The interviewer says "now the snake wraps around the edges". What changes?

Only the boundary strategy: WrapBoundary returns (floorMod(r + dr, rows), floorMod(c + dc, cols)) and never null. Use floorMod, not %: in Java and C++ -1 % 4 is -1. Game, Snake and tests for other rules are untouched; I add one test for the wrap.

How do you place new food so it never lands on the snake?

For a given list (LeetCode style), skip entries under the body. For random food, try a few random cells and check the set; when the board is crowded, scan the free cells and pick one. For guaranteed O(1), keep a free-cell array plus a cell-to-index map: on every move, remove the new head from the free array (swap with last) and add the old tail back. If no free cell is left, the snake has filled the board: the game is won.

Likely follow-ups
  • How do you test random food? (Inject a seeded spawner, or a fake spawner in tests.)
The user presses UP then LEFT within one tick while moving RIGHT. What happens in your game?

Both are buffered (up to 2), each validated against the last buffered direction: UP is fine after RIGHT, LEFT is fine after UP. The next tick moves up, the one after moves left. Without a buffer, a naive "last key wins" stores LEFT, which is the reverse of the current RIGHT: either it is rejected and the user's UP is lost, or it is accepted and the snake turns into itself. A bounded buffer keeps the player's intent and stops a held key from queueing many moves.

How is the game loop structured, and how do you test it?

The rules expose tick(); time lives in a separate GameLoop that calls tick() on a ScheduledExecutorService at a fixed rate and stops when the game ends. Tests never use the loop: they call tick() directly, so they are instant and deterministic. Speed levels change only the loop period. This is the "fixed time step" loop from game programming.

Likely follow-ups
  • Fixed rate or fixed delay? (Fixed rate keeps the pace steady; if one tick runs long, the next ones catch up. For a snake, either works; say which you chose and why.)
Is your game thread safe? Where are the locks?

One lock per Game. turn() (input thread) and tick() (loop thread) are both synchronized; the critical section is O(1). Only tick() changes the snake, food and status, so there is a single writer for all game state, and the input thread only appends to a bounded buffer. Reads such as render() take the lock to get a consistent snapshot. Listeners are in a copy-on-write list and must be fast because they run under the lock.

Should Board or Game be a Singleton?

No. Tests create many games, multiplayer needs many snakes, and a server may run many games. A singleton turns game state into a global and makes tests depend on each other. Create one Game per match and inject its rules. See Singleton for when it does fit.

Add two snakes on one board. What is hard?

Fairness of order. If snake A moves first, snake B's tail has not left yet, so results depend on the loop order. Do the tick in phases: compute every next head; detect head-on collisions (two heads into one cell, or swapping cells); check each head against all bodies with the tail exception for tails that will leave; then advance all survivors. Food eaten by two heads at once needs a rule (both die, or a tie-break). Snake becomes a list, and collision becomes a small CollisionDetector class.

What do you throw, and what do you just ignore?

Throw for programming errors in setup: board smaller than 1 x 1, start off the board, null strategies. Ignore (return false) for events that are normal in play: a reverse key, a repeated key, keys after the end, a full buffer. Hitting a wall is not an exception either: it is a state change to OVER. Using exceptions for game over makes control flow hard to follow and slow in a loop.

How would you save and replay a game?

Because the rules are deterministic given the seed and the inputs, record only the random seed and the list of (tick number, accepted turn). Replay creates the same Game with the same seed and feeds the turns at the same ticks. This is far smaller than saving every frame. It works only because time is outside the rules and the spawner's randomness is injected.
