Identify the entities (nouns and verbs)

Read the problem statement and underline nouns (candidate classes) and verbs (candidate methods). Then drop nouns that are only data. The method is explained in use cases to classes.

  1. Start from a two-sentence statement of the game. Read it twice and confirm it with the interviewer.
  2. Underline the nouns: snake, board, cell, tick, direction, food, point (score), wall.
  3. Underline the verbs. The owner of each verb is a design choice: the snake advances itself, the game decides when.
  4. Drop nouns that are only data. A cell is an immutable Position value; a tick is a counter; a direction is an enum; the score is an int on the Game.
  5. "Wall" and "food appears" are rules that interviewers change, so they become strategy interfaces. Add a listener for "something happened" so the UI is not inside the game.

A common practice-post shape is a Board singleton that owns everything, with a Cell class holding a type (EMPTY, FOOD, SNAKE). Both hurt you: a singleton blocks running two games in tests, and a typed cell grid must be rewritten on every move (O(length)). Keep the grid implicit: the snake's set says which cells are body, one field says where food is.
