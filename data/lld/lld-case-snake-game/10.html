Concurrency and thread safety

A real snake game has two kinds of threads: an input thread (keyboard, touch, network) that calls turn() at any moment, and a loop thread that calls tick() every period. Our rules:

  1. One lock per game Both turn() and tick() are synchronized on the Game. A tick is short (a few hash operations), so holding the lock for the whole tick is fine and keeps every invariant simple: the deque, the set, the food and the status always change together.
  2. Single writer for the body Only tick() touches the snake. turn() only appends to the small buffer. That is the producer/consumer split from your kernel world: the interrupt fills, the softirq drains.
  3. Bounded buffer, validated on entry Each turn is checked against the last buffered direction, not the current one. If both were checked against the current RIGHT, then UP followed by DOWN inside one tick would both pass (neither is the reverse of RIGHT), and on the second tick the snake would reverse straight into its own neck. The buffer holds at most 2 turns, so a held key cannot queue a hundred moves.
  4. Listeners outside the hot data Listeners are a CopyOnWriteArrayList, so adding a listener while the loop iterates is safe. Listeners run inside the lock, so they must be quick; a slow UI should copy the event and return (or hand it to its own queue). Listeners run under the lock here for simplicity: a listener must not block, and must not call back into the game from another thread (its turn() would wait for the lock the tick holds: the tick stalls, or deadlocks if it waits for that thread). The production version queues events under the lock and fires them after unlock, as in the auction and coffee machine cases.
  5. Reads are snapshots head(), score() and render() take the same lock, so a UI never sees a half-moved snake.

Game 7 in the Java demo runs a 1 ms ScheduledExecutorService loop while 4 threads send 8,000 random turns; then it checks the invariants (deque size equals set size, food not under the body). The Python test does the same with threading and an RLock (re-entrant because move() calls turn() and tick()). The C++ build is single-threaded because MinGW g++ 6.3 has no std::mutex; the file says where the lock goes.

From your world

Why not lock-free? You could make the turn buffer an SPSC ring (one producer, one consumer, two atomic indices, like a NIC descriptor ring) and keep the body owned by the loop thread only, with no lock at all. That is the right answer for a 60 FPS game with one input source. In an interview, start with one lock and say: "the critical section is O(1), contention is one key press per tick, so a mutex is cheaper than its complexity; I would move to an SPSC ring if profiling showed lock waits."

Do not use Thread.sleep inside Game to make "the snake move every 200 ms". It welds time into the rules, so tests become slow and flaky. Keep time in GameLoop; keep rules in Game. Levels that speed up only change the loop period.
