The story: the playground referee

Explain like I'm 5

Two kids draw a 3 by 3 grid in the sand. One draws crosses, the other draws circles. They take turns. A third kid is the referee. The referee has three jobs: make sure each kid plays only on their own turn, make sure nobody draws on a square that is already used, and shout "You win!" the moment someone has three in a line. If all nine squares fill up with no line, the referee says "Draw".

A lazy referee looks at the whole grid after every move to find a line. A clever referee keeps a tally on her fingers: "crosses have 2 in the top row, 1 in the middle column...". When a tally reaches 3, she shouts at once, without looking at the whole grid again.

In the interview you write that referee as code. The grid is a Board. The kids are Players. The referee is the Game, which owns the turn order and the state. The clever tally is the trick that turns an O(N squared) win check into O(1). Everything else is about keeping these jobs in separate classes so the interviewer's follow-ups ("make it 5 x 5", "three players", "4 in a row wins", "add undo") are small changes, not rewrites.

From your world

The win rule is an ops table: in C you would write struct win_ops { bool (*on_move)(struct game *, int r, int c); void (*on_undo)(struct game *, int r, int c); }; and point the game at full_line_ops or k_in_row_ops, the same way a driver fills in file_operations. In Java and C++ that table is the WinStrategy interface. The per-line tallies are plain counters updated on every event, like the per-interface packet counters you bump in the fast path instead of walking a list. The game state (in progress, won, draw) is a tiny protocol state machine: events are only legal in some states, exactly like a TCP socket refusing send() after FIN.
