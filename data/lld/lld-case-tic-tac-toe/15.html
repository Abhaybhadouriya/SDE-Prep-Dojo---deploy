Interview follow-ups

How do you check for a winner efficiently?

Only lines through the last move can change, so never scan the board. Keep per-player counters for each row, each column and the two diagonals. On a move at (r, c) by player p, increment rows[p][r], cols[p][c], diag[p] if r == c, anti[p] if r + c == n - 1. A counter equal to n is a win. O(1) time per move, O(k n) memory. For exactly two players, one signed counter per line (+1 / -1) is enough.

How to answer

Give the three levels: full scan O(n squared), lines through the move O(n), counters O(1). Then code the counters.

Likely follow-ups
  • Why does +1/-1 not work for three players?
  • What if the win is K in a row, not a full line?
Which data structure stores the board, and why?

A 2-D char array (or a flat array of n * n with index r * n + c): O(1) access, tiny, cache friendly, trivial to print. Keep a filled counter so "is the board full?" is O(1) too. For a huge, sparse board use a hash map keyed by r * n + c holding only the placed cells, and keep the counters in maps as well.

How to answer

Pick the array, give two reasons, then say when you would switch to a map.

The last cell fills the board and also completes a line. What does your game report?

WON. The order of checks matters: check the winning move first, then "board full". Reversing them reports a draw for a game that was won on its last move. It is a classic hidden test case; keep it in your driver.

Win rule changes to "4 in a row" on a 10 x 10 board. What changes?

Only the strategy. Full-line counters no longer work, because a row can contain 4 in a row without being full. KInARowWinStrategy walks both ways along 4 lines through the last move (horizontal, vertical and the two diagonals), counts consecutive symbols and wins if 1 + one side + the other side reaches K. O(K) per move, independent of board size. Game and Board are untouched: that is the point of Strategy here.

Likely follow-ups
  • Could you make K-in-a-row O(1)? (Yes, with run-length tracking per cell and direction, but it is complex and O(n squared) memory; O(K) is the right answer.)
Why not PlayingPiece with PieceX and PieceO subclasses?

Subclasses should differ in behaviour. X and O differ only in a letter, so a symbol field is enough, and it scales to any number of players without a new class each time. If pieces had rules (chess), a piece hierarchy would be right. Saying this shows you choose inheritance on purpose, not by habit (composition over inheritance).

Should Game be a Singleton?

No. You can run many games at once (a server, a tournament, tests), and a singleton forces shared global state into every test. Create a Game per match; if you need one place to find games, a GameRegistry map is enough. Singleton fits a truly global resource, like a configuration, and even then dependency injection is usually better (Singleton).

Add undo. What must it roll back?

Everything the move changed: the cell, the filled count, the rule's counters, the state and winner, and the turn. Our history stack holds Move objects; undo pops one, calls rule.undo (counters -1), clears the cell and gives the turn back to that move's player. Our test proves it: undo a winning move, play the same cell again, and it must win again; if counters were not rolled back, the diagonal would read 4 and never equal N. Redo adds a second stack that any new move clears.

Turn it into a web game. APIs and storage?

Keep Game as the domain core. APIs: POST /games (players, size) returns id; POST /games/{id}/moves with player, row, col and the move count the client saw; GET /games/{id} returns board, turn and state. Store games(id, size, players, state, winner, move_count) and moves(game_id, seq, player, row, col), primary key (game_id, seq), so two concurrent moves cannot both take the same sequence number. Load the game by replaying moves (or cache the board). Push updates to the other player with a WebSocket or polling.

How to answer

Domain class first, then the thin API, then the two tables, then the concurrency guard.

Add a computer player.

Introduce MoveSource with nextMove(GameView); a human source reads input, a bot source decides. Simple bot: win if you can, else block the opponent's winning cell, else take the centre, else a corner, else any cell. For 3 x 3, minimax with alpha-beta plays perfectly (the state space is tiny). The Game stays the same: it only accepts moves.

Strategy vs State: which one did you use, and where?

Strategy for the win rule: the client (the game constructor) chooses one algorithm and it never changes during the game. The game state is a 3-value enum with one guard, because there is only one event (a move) and the only difference between states is "allowed or not". If states had many events with different behaviour, like a vending machine, the State pattern would pay off.
