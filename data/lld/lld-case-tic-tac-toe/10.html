Concurrency and thread safety

A console game has one thread, so no locks are needed. The question becomes real in the web version: two browser tabs (or a double-click) send moves for the same game at the same moment. Without a lock both requests can pass "is the cell empty?" before either writes: the classic check-then-act race (see races and atomicity).

Step through the race this section is about, then the fix the code uses:

  1. Tab A sends "Asha plays (1,1)". The server reads the cell: empty, and it is Asha's turn.
  2. Tab B (a double-click) sends the same move; its thread also reads an empty cell before A writes.
  3. Both write. The turn switches twice, so Asha moves again, and the win counters count one piece as two.
  4. The fix: makeMove is synchronized on the game, so validate, place, check and switch turn run as one unit. Tab B then fails with "cell (1,1) is taken" (or "not Asha's turn"). The Python test fires 8 threads at one cell: exactly one succeeds.
  1. One lock per game makeMove and undo are synchronized (Python: a threading.Lock). Validate, place, check and switch turn happen as one unit. The Python test fires 8 threads at the same cell; exactly one succeeds.
  2. Many games in parallel Different games share nothing, so keep them in a ConcurrentHashMap<gameId, Game> (a hash map that many threads may read and insert into at once, without one big lock). Each game has its own lock, so games never block each other: lock per object, like a per-socket lock in a network stack.
  3. Across servers When games live in a database, use optimistic versioning: each move says which move number it saw (expectedMoveCount); if the stored number has moved on, the move is rejected. No lock is held across the network, and a stale or duplicate request is rejected, not applied twice (more in booking without double-booking).

The turn check already gives you idempotency (doing the same request twice has the same effect as doing it once) for free: a retried "Asha plays (1,1)" after it was applied fails with "not Asha's turn", so it can never be applied twice. Mention it when asked about retries.

On this page: one lock per game is a per-socket lock; games share nothing, so they never contend. The cross-server version below rejects stale moves the way TCP drops a segment whose sequence number is old.
