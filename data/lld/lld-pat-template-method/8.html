When to use it, when not to

Use it when
  • Several classes run the same steps in the same order and differ in one or two of them.
  • The order and the invariant steps must be enforced (transactions, cleanup, logging, security checks).
  • You are writing a framework or library and want users to plug in at well-defined points.
  • You are removing duplication from near-identical classes (Form Template Method).
Avoid it when
  • The variations are many and independent (parse format x validation rule x storage target). Inheritance would give you one subclass per combination; use Strategy objects for each axis.
  • The variation must change at runtime: a subclass is fixed when the object is created.
  • The base class is in someone else's library and may change: subclasses are tightly coupled to its internals (the fragile base class problem).
  • There is only one implementation: just write the method.

Pitfalls

  • Forgetting final. If run() can be overridden, a subclass will one day override it and skip the transaction. Make the skeleton final (C++: non-virtual).
  • Hooks that must call super. "Override setUp() but remember to call super.setUp()" is a bug factory. Prefer an empty hook the base class calls itself.
  • Liskov violations. A subclass step that throws "not supported" or changes what the skeleton expects (returns null where a list was expected) breaks every caller. See LSP.
  • Too many hooks. A base class with 12 hooks is hard to read: nobody knows which ones matter. Group them or split the class.
  • Calling overridable methods from a constructor (Java, C++): the subclass part is not ready yet. In C++ the call does not even dispatch to the derived class. Keep the template method out of constructors.
