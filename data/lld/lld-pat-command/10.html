In interviews

Command almost never appears as "implement the Command pattern". It appears as a follow-up: "how would you add undo?", "what if this must run later?", "how do you retry failed operations?". The moment you hear undo, queue, schedule, retry or replay, reach for it. Case studies where it fits:

  • Text editor: the classic. Insert/delete commands, two stacks, macro recording, merging keystrokes.
  • Task scheduler: each task is a command with a run time; a priority queue is the invoker; a thread pool executes.
  • Splitwise: "add expense" and "settle up" as commands give you an audit trail and an "undo last expense" feature.
  • Chess and tic-tac-toe: each move is a command, so undo-move and game replay are free.
  • Stock exchange: place/cancel/modify order requests as command objects flowing into a matching engine queue.
  • Shopping cart: add/remove item commands for undo and for syncing a cart across devices.

For the thread-pool angle, see thread pool and producer-consumer: the queue between them holds commands.

Strong 30-second answer: "Command turns a request into an object holding the receiver and the arguments, with execute() and optionally undo(). The invoker only knows the interface, so I can queue, log, retry or undo requests. Undo/redo is two stacks, and a new command clears redo. In Java the lightweight form is Runnable; in the kernel it is work_struct."

A public LeetCode Discuss post describes a Microsoft round asking for undo/redo where some commands run locally and some on a service (post). The Command answer scales to that: each command knows whether it is local or remote, remote commands are sent as serialized objects, and their undo is a compensating command sent to the service.
