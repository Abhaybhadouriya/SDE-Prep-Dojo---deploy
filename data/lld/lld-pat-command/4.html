How it works: undo and redo with two stacks

The invoker keeps two stacks of command objects. run executes and pushes onto the undo stack, and clears the redo stack. undo pops from undo, calls undo(), pushes onto redo. redo pops from redo, calls execute() again, pushes onto undo. Click through the exact sequence the Java program below runs:

  1. run(insert "hello" @0): execute, push onto the undo stack. The document is "hello".
  2. run(insert " world" @5): a second command on top. Document "hello world".
  3. run(delete 6 @0): DeleteText saves the removed text "hello " inside itself, then deletes. Document "world".
  4. undo(): pop the delete, call its undo() (re-insert the saved text), push it onto the redo stack. Document "hello world".
  5. undo() again: the insert of " world" is reversed and moves to redo. Document "hello".
  6. redo(): pop " world" from redo, execute() it again, push it back onto undo. Document "hello world".
  7. run(insert "!"): a brand new action. The redo stack is cleared, because "delete 6 @0" was planned against a document that no longer exists. Document "hello world!".

Step 7 is the rule people forget in interviews: any new command clears the redo stack. Without it, redo would replay an old command against a different document, and positions would point at the wrong characters.
