When to use it, when not to

Use it when
  • You need undo/redo or a history of what the user did.
  • You need to queue, schedule, retry or defer work (job queues, thread pools, bottom halves).
  • You want macros: record a list of commands and replay it.
  • Several triggers (button, menu, shortcut, API) must start the same action without duplicating it.
  • You need an audit log or transaction log of operations.
Avoid it when
  • A plain function reference is enough. In Java pass a lambda (Runnable); in Python pass a function. One class per action for no reason is ceremony.
  • Actions cannot be reversed (an SMS sent, money paid out). Then "undo" is really a new compensating command, and you should say so.
  • There is no queueing, no history and only one caller: a direct method call is clearer.

Design tips and pitfalls

  • Capture undo state at execute time, not at construction time. A delete only knows what it removed once it runs.
  • Stale state. A command queued at 10:00 and run at 10:05 may see a different world. Validate in execute(), not only when the command is created.
  • Memory. An unbounded undo stack grows forever. Cap it (keep the last N) or merge small commands (typing ten letters becomes one "insert word" command).
  • Undo by inverse operation vs by snapshot. Command undo stores the inverse operation (small). Memento stores a copy of the state (simple, but large). Real editors mix both: commands for most edits, snapshots for operations that are hard to reverse.
  • Serializable commands (type + arguments, no live pointers) can be written to disk or sent over a network. That is how job queues and replication logs work.
  • Idempotency. Retried commands may run twice. Give each one an id so the receiver can ignore duplicates.
