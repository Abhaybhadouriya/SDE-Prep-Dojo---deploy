Interview Q&A

Design undo and redo for a text editor.

Model every edit as a command with execute() and undo(). The editor (invoker) keeps an undo stack and a redo stack. Run: execute, push to undo, clear redo. Undo: pop undo, call undo(), push to redo. Redo: pop redo, call execute(), push to undo. Commands store what they need to reverse themselves (a delete keeps the removed text). Cap the history and merge consecutive keystrokes into one command so memory stays bounded.

How to answer

Draw the two stacks and walk four operations, then state the "new command clears redo" rule before the interviewer asks.

Likely follow-ups
  • How do you undo a "replace all" of 500 matches? (One macro command.)
  • How do you limit memory?
  • Command vs Memento for undo?
Command vs Strategy: both are "an object with one method". What is the difference?

Strategy is about how: a context picks one of several interchangeable algorithms for a job it already knows it must do (fare calculation, sorting). Command is about what and when: a request is packaged so an invoker that knows nothing about it can run it later, queue it, log it or undo it. A Strategy is called by its context as part of the context's work; a Command is carried around and triggered by someone else.

How to answer

Give one example of each in the same app: payment method choice (Strategy) vs "refund order 77" job in a queue (Command).

Likely follow-ups
  • Is a Comparator a Command or a Strategy? (Strategy.)
  • Is a Runnable passed to an executor a Command? (Yes.)
Some commands cannot be undone (an email was sent, money was paid). How does your undo design handle them?

Be honest in the model: give the command a canUndo() flag, and either block undo past it (many editors clear history after a save-and-publish) or implement undo as a compensating command (a refund for a payment, a "sorry, ignore that" email). Compensation is a new forward action that is recorded in history too. This is the same idea as compensating steps in a saga.

How to answer

Separate "reversible" from "compensatable" from "final", and give one example of each.

Likely follow-ups
  • What if the compensation itself fails? (Retry with idempotency keys, then alert a human.)
How would you implement a macro recorder?

While recording, every command the invoker runs is also appended to a list. Stopping the recording wraps that list in a MacroCommand, which is itself a command: execute() runs the children in order and undo() undoes them in reverse order. Because commands store absolute positions, replaying at a different place needs commands that are relative to the cursor, or the macro should copy and re-target its children before replay.

How to answer

Say "a macro is a Composite of commands" and mention reverse-order undo.

Likely follow-ups
  • What happens if step 3 of 5 fails? (Undo steps 2 and 1, then report: all-or-nothing.)
Design a job queue where jobs are retried on failure. Where does Command fit?

Each job is a serializable command: a type name, its arguments, an id, an attempt count. Producers enqueue commands; workers dequeue and call execute(). On failure the worker re-enqueues with a delay (exponential backoff) until a max attempts limit, then moves it to a dead-letter queue. Because jobs can run twice (a worker crashes after doing the work but before acking), receivers use the job id as an idempotency key.

How to answer

Command object, queue as invoker, worker pool, retries with backoff, dead-letter queue, idempotency. That is the full list.

Likely follow-ups
  • How do you guarantee ordering per customer? (Partition by key.)
  • Why serialize type + args instead of the object?
Where is the Command pattern in the Linux kernel?

struct work_struct holds a function pointer; it is embedded in the driver's own struct, which holds the arguments, and container_of recovers them. An interrupt handler calls schedule_work() and returns; a kworker thread executes the function later. struct bio is an I/O request object passed down the block layer with a completion callback. io_uring SQEs are operations written into a shared ring and executed by the kernel.

How to answer

Name the struct, the invoker (workqueue) and why: separate the fast "ask" from the slow "do".

Likely follow-ups
  • What happens if you schedule the same work item twice before it runs? (It is queued only once; a pending item is not re-added.)
Isn't a separate class per command over-engineering?

Often, yes. If you only need to defer or pass an action, a lambda or method reference is a perfectly good command (Runnable, a Python function). Write classes when each command must carry extra behaviour: undo(), a display name for the history menu, serialization for a queue, or validation. In an interview, start with the interface and two concrete classes, and say you would use lambdas for the simple cases.

How to answer

Show judgement: classes where they earn their keep, lambdas elsewhere.

Likely follow-ups
  • Can a lambda support undo? (Pair two lambdas, do and undo, in a small record.)
