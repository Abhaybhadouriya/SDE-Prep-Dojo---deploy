7. Web Crawler Multithreaded: when are we done?

Problem (LeetCode 1242, premium; also reported in a Rubrik screen, post, 2024-05): starting from one URL, visit every page on the same host. getUrls(url) is slow (a network call), so fetch pages in parallel and visit each page exactly once.

Two hard parts hide inside this question:

  1. No duplicates. "If not seen, mark seen and fetch" is a check-then-act race: two workers can both see "not seen". Use one atomic step: seen.add(url) on a concurrent set returns true only for the first caller.
  2. Termination. The queue can be empty while a worker is still fetching a page that will add ten more URLs. "Queue empty" does not mean "done". Count tasks in flight instead, and finish when that count reaches zero.
static List<String> crawl(String start, HtmlParser parser, int threads) throws InterruptedException {
    String host = start.split("/")[2];
    Set<String> seen = ConcurrentHashMap.newKeySet();
    AtomicInteger pending = new AtomicInteger();          // tasks submitted but not finished
    CountDownLatch done = new CountDownLatch(1);
    ExecutorService pool = Executors.newFixedThreadPool(threads);
    class Submitter {
        void submit(String url) {
            if (!url.split("/")[2].equals(host) || !seen.add(url)) return;  // atomic check-then-act
            pending.incrementAndGet();                    // count BEFORE the task can finish
            pool.execute(() -> {
                try { for (String next : parser.getUrls(url)) submit(next); }
                finally { if (pending.decrementAndGet() == 0) done.countDown(); }
            });
        }
    }
    new Submitter().submit(start);
    done.await();
    pool.shutdown();
    return new ArrayList<>(seen);
}

Our test graph has a cycle (/ to /b back to /) and a link to another host that itself links back to a "secret" page on our host. The crawler returned the 4 same-host pages, called getUrls exactly 4 times, and never followed the foreign link.

From your world

"In-flight counter that wakes a waiter at zero" is a kref plus a completion: every outstanding I/O holds a reference, the release function for the last kref_put() calls complete(), and the teardown path sleeps in wait_for_completion(). Taking the child's reference before dropping the parent's is the same rule that keeps a refcount from touching zero too early.

Alternative: CompletableFuture recursion (supplyAsync(getUrls).thenCompose(children -> allOf(...))) also works and hides the counter, but it is harder to explain on a whiteboard. Mention it as a follow-up; see Thread Pools, Executors & Futures.
