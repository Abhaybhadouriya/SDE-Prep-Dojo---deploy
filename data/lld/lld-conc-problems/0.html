The story: the relay baton

Explain like I'm 5

Four children run a relay race. Only the child holding the baton may run. When she finishes her lap she hands the baton to the next child, who has been standing still, waiting. Nobody runs early, nobody runs twice, and nobody pushes. If two children each wait for the other to hand over a baton that neither has, the race stops forever.

Every problem on this page is a relay race. Several threads (independent workers inside one program) run at the same time, and the puzzle asks you to make them act in a fixed order or in fixed groups: "print foo, then bar, then foo again", "release two hydrogen atoms and one oxygen atom together", "let five philosophers eat without starving". The answer is always the same idea: decide what the baton is, who waits for it, and who hands it on.

These puzzles come from the LeetCode concurrency problem set and from interview reports. Rubrik is known for a whole "multithreading" round; recent reports there asked a multithreaded web crawler and a shared-bathroom scheduling problem (post, 2024-05), a reader-writer lock and a bounded queue (post, 2026-04), and a searcher-inserter-deleter list problem (post, 2026-02). "Print odd and even numbers with two threads" still shows up in screens (post, 2026-06).

From your world

You have written this code before, in C. A struct completion with wait_for_completion() / complete() is a latch. struct semaphore with down() / up() is a semaphore. wait_event(wq, cond) plus wake_up(&wq) is a monitor with a condition. The rule "always take inode->i_rwsem before the page lock" is lock ordering, and lockdep checks it at run time. Java and C++ give the same tools different names.

Where this breaks: in the kernel you can disable preemption or interrupts to make a short section atomic. In Java or user-space C++ you cannot; every handover must go through a real synchronisation object, or the memory model gives no visibility guarantee.
