6. Dining Philosophers: break the cycle

Problem (LeetCode 1226, first posed by Dijkstra): five philosophers sit at a round table with one fork between each pair. To eat, a philosopher needs both the fork on the left and the fork on the right. Design wantsToEat(p, ...) so nobody deadlocks and nobody starves.

Before. The natural code takes the left fork, then the right fork. If all five pick up their left fork at the same moment, every fork is held and every philosopher waits for a neighbour: a cycle of waits, which is a deadlock.

We did not just argue this, we measured it. The test below forces the bad interleaving with a CyclicBarrier (all five grab the left fork, then all try the right) and uses tryLock(300 ms) so we can count the stuck philosophers instead of hanging forever. A second barrier makes everyone keep the left fork until all five have timed out; without it, one timeout firing a few milliseconds early (Windows timers are that coarse) frees a fork for a neighbour and the count drops below 5. Result in every run we made: 5 of 5 stuck. With ordering, 5 threads x 1000 meals each finished every time.

static int naivePhilosophersStuck() throws InterruptedException {
    ReentrantLock[] forks = new ReentrantLock[5];
    for (int i = 0; i < 5; i++) forks[i] = new ReentrantLock();
    CyclicBarrier allHoldLeft = new CyclicBarrier(5);
    CyclicBarrier allTried = new CyclicBarrier(5);             // nobody lets go until everyone has tried
    AtomicInteger stuck = new AtomicInteger();
    Thread[] ts = new Thread[5];
    for (int p = 0; p < 5; p++) {
        final int me = p;
        ts[p] = new Thread(() -> {
            forks[me].lock();                                  // left fork
            try {
                allHoldLeft.await();                           // now every fork is held
                if (forks[(me + 1) % 5].tryLock(300, TimeUnit.MILLISECONDS)) forks[(me + 1) % 5].unlock();
                else stuck.incrementAndGet();                  // would have waited forever
                allTried.await();                              // keep the left fork until all 5 timed out,
            } catch (Exception e) { throw new RuntimeException(e); }   // or an early timeout frees a fork
            finally { forks[me].unlock(); }
        });
        ts[p].start();
    }
    for (Thread t : ts) t.join();
    return stuck.get();                                        // 5 on every run
}
class DiningPhilosophers {
    private final ReentrantLock[] forks = new ReentrantLock[5];
    DiningPhilosophers() { for (int i = 0; i < 5; i++) forks[i] = new ReentrantLock(); }

    void wantsToEat(int p, Runnable pickLeft, Runnable pickRight, Runnable eat,
                    Runnable putLeft, Runnable putRight) {
        int left = p, right = (p + 1) % 5;
        ReentrantLock first = forks[Math.min(left, right)];   // global order: lower id first
        ReentrantLock second = forks[Math.max(left, right)];
        first.lock();
        try {
            second.lock();
            try { pickLeft.run(); pickRight.run(); eat.run(); putLeft.run(); putRight.run(); }
            finally { second.unlock(); }
        } finally { first.unlock(); }
    }
}
class DiningPhilosophers {
public:
    void wantsToEat(int p, const std::function<void()>& eat) {
        std::mutex& left = forks_[p];
        std::mutex& right = forks_[(p + 1) % 5];
        std::lock(left, right);           // takes both or neither: never holds one while blocked
        std::lock_guard<std::mutex> a(left, std::adopt_lock), b(right, std::adopt_lock);
        eat();
    }
private:
    std::mutex forks_[5];
};
Lock ordering (pick this first)
  • Simple, no extra object, no retries.
  • Scales to any number of locks: sort by id, take in order.
  • The same rule fixes "transfer money between two accounts".
Watch out for
  • Prevents deadlock, not starvation: with an unfair lock a philosopher can lose every race. Use a fair lock (new ReentrantLock(true)) if the interviewer asks.
  • Needs a stable global order (an id); with dynamic lock sets, use tryLock with back-off.
  • Back-off without random jitter can turn deadlock into livelock (everyone retries in step).

From your world

Kernel code solves this with documented lock order: many source files carry a comment at the top listing which lock must be taken before which, and lockdep records every order it sees and warns the first time an inversion appears, before any real hang. double_rq_lock() in the scheduler takes two runqueue locks in a fixed order for the same reason.
