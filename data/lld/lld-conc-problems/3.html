2. FooBar: passing a baton with two semaphores

Problem (LeetCode 1115): thread A calls foo(), which prints "foo" n times; thread B calls bar(), which prints "bar" n times. The output must be foobarfoobar.... The same shape answers "print odd and even numbers with two threads".

Before: a spin flag. The first idea most people write is a shared boolean and a busy loop.

// BEFORE: works only because of volatile, and burns a whole CPU core while waiting
class FooBarSpin {
    private volatile boolean fooTurn = true;   // drop volatile and bar() may spin forever
    void foo(Runnable printFoo) {
        for (int i = 0; i < n; i++) {
            while (!fooTurn) { }                 // busy-wait: 100% CPU doing nothing
            printFoo.run();
            fooTurn = false;
        }
    }
    void bar(Runnable printBar) {
        for (int i = 0; i < n; i++) {
            while (fooTurn) { }
            printBar.run();
            fooTurn = true;
        }
    }
}

It is correct only because the flag is volatile (without it, the JIT may hoist the read out of the loop and spin forever; see visibility). It also wastes a core and can time out on a judge. The fix is to sleep while waiting, and the cleanest sleeping baton is a pair of semaphores.

  1. Start: the only permit (the baton, the moving dot) sits in fooTurn. B calls barTurn.acquire() and sleeps, because barTurn has 0 permits.
  2. A takes the permit from fooTurn and prints "foo".
  3. A calls barTurn.release(): the baton moves to barTurn. A loops and sleeps on fooTurn.acquire().
  4. B wakes, takes the permit, prints "bar", then calls fooTurn.release().
  5. The baton is back in fooTurn. Exactly one permit exists at any moment, so exactly one thread can print.
class FooBar {
    private final int n;
    private final Semaphore fooTurn = new Semaphore(1);   // foo may go first
    private final Semaphore barTurn = new Semaphore(0);   // bar must wait
    FooBar(int n) { this.n = n; }

    void foo(Runnable printFoo) throws InterruptedException {
        for (int i = 0; i < n; i++) { fooTurn.acquire(); printFoo.run(); barTurn.release(); }
    }
    void bar(Runnable printBar) throws InterruptedException {
        for (int i = 0; i < n; i++) { barTurn.acquire(); printBar.run(); fooTurn.release(); }
    }
}
// C++14 has no semaphore, so build one: a counter + mutex + condition variable
class Semaphore {
public:
    explicit Semaphore(int permits) : permits_(permits) {}
    void acquire() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this] { return permits_ > 0; });
        --permits_;
    }
    void release() {
        { std::lock_guard<std::mutex> lk(m_); ++permits_; }
        cv_.notify_one();
    }
private:
    std::mutex m_;
    std::condition_variable cv_;
    int permits_;
};

class FooBar {
public:
    explicit FooBar(int n) : n_(n), foo_(1), bar_(0) {}
    void foo(const std::function<void()>& printFoo) {
        for (int i = 0; i < n_; ++i) { foo_.acquire(); printFoo(); bar_.release(); }
    }
    void bar(const std::function<void()>& printBar) {
        for (int i = 0; i < n_; ++i) { bar_.acquire(); printBar(); foo_.release(); }
    }
private:
    int n_;
    Semaphore foo_, bar_;
};

From your world

This is the kernel's ping-pong between an interrupt handler and a thread: the IRQ calls up(&sem), the thread sleeps in down(&sem). A semaphore is the right tool exactly because the thread that releases is not the thread that acquired. A mutex forbids that (only the owner may unlock), which is why "use a mutex for FooBar" is a wrong answer.
