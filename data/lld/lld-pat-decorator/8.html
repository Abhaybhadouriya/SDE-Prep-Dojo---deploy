When to use it, when not to

Use it when
  • Features are optional and combinable: add-ons, toppings, pricing rules, I/O layers, middleware.
  • You want to add behaviour to an object at run time, or per instance, not to every instance of a class.
  • You cannot or should not subclass: the class is final, from a library, or subclassing would explode.
  • Cross-cutting concerns (logging, metrics, caching, retry, auth) should stay out of the core class (single responsibility).
Avoid it, or watch out, when
  • The order of wrappers changes the result in ways people will get wrong. Hide the stacking in a factory or builder that applies a fixed order.
  • Code depends on object identity or concrete type: a wrapped object is not == the original and instanceof Espresso fails on a Milk.
  • The Component interface is large. Every decorator must forward every method, and forgetting one silently skips the inner object's behaviour.
  • You need to remove a feature from the middle of a stack. Decorators are easy to add and awkward to peel off.
  • Deep stacks make debugging and stack traces long. Ten tiny wrappers for one call is a smell.

Pricing design tip: decorators are great when add-ons truly wrap (each one changes the result of the one below). If add-ons are just a list of priced items, a List<AddOn> on the order is simpler and easier to show on a receipt. Say both options and pick by the requirement.
