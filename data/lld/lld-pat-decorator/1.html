The problem: the subclass explosion

The first idea is one subclass per combination:

class Espresso              { int price() { return 120; } }
class EspressoWithMilk      extends Espresso { int price() { return 140; } }
class EspressoWithShot      extends Espresso { int price() { return 150; } }
class EspressoWithMilkShot  extends Espresso { int price() { return 170; } }
class EspressoWithMilkMilk  extends Espresso { int price() { return 160; } }   // double milk?
class ChaiWithMilk          extends Chai     { int price() { return  60; } }
// ... and Large versions of every one of these

The second idea is boolean flags in one class:

class Coffee {
    boolean milk, shot, caramel, large, oatMilk, decaf;     // grows forever
    int price() {
        int p = base;
        if (milk) p += 20;
        if (shot) p += 30;
        if (caramel) p += 25;
        if (large) p = p * 3 / 2;
        return p;                  // and "two shots" needs an int, not a boolean
    }
}

Count the pains:

  • Combinations explode. With 3 drinks and 4 optional add-ons that is 3 x 24 = 48 subclasses before sizes or doubles.
  • Every new add-on edits tested code. The flags class changes for each new topping, breaking the Open/Closed Principle, and every drink carries fields it never uses.
  • Inheritance is fixed at compile time. A customer cannot "add milk" to an object that already exists; you would have to construct a different class.
  • Repeats are awkward. "Double milk" or "three shots" do not fit a boolean.
