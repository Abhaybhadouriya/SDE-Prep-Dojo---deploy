Interview Q&A

Design pizza pricing: base pizzas plus any number of toppings.

A Pizza interface with cost() and description(). Concrete bases (Margherita, FarmHouse) implement it. An abstract ToppingDecorator implements Pizza and holds a Pizza. Each topping (ExtraCheese, Mushroom) returns inner.cost() + its price. An order is built as new Mushroom(new ExtraCheese(new Margherita())). Adding a topping means adding one class.

How to answer

Show the explosion first (one line), then the four participants, then one call trace. Keep money in integer paise.

Likely follow-ups
  • Toppings priced differently by pizza size? (Pass size down, or let the topping ask inner.size().)
  • How do you show an itemised bill? (Each decorator appends a line; or keep a list of toppings instead.)
Why use Decorator instead of inheritance?

Inheritance fixes behaviour at compile time and for every instance of the class, and combining features needs one subclass per combination. Decorators add behaviour at run time to one object, combine freely, can repeat (two shots), and keep each feature in its own small class. The cost is many small objects and the loss of object identity.

How to answer

Compile time vs run time, class vs instance, combinations vs composition.

Likely follow-ups
  • When is plain inheritance still better? (One stable variation that never combines.)
Decorator vs Proxy: the diagrams are the same. How do you tell them apart?

By intent and by who builds the wrapper. A decorator adds behaviour, is meant to be stacked, and is composed by the client (new Buffered(new Gzip(file))). A proxy controls access to a real object (lazy loading, remote calls, permission checks, caching, rate limiting), usually creates or manages that real object itself, and the client often does not know it has a proxy (Spring's @Transactional, java.lang.reflect.Proxy).

How to answer

"Same shape, different intent", then one example of each.

Likely follow-ups
  • Is a caching wrapper a proxy or a decorator? (Either; say which intent you mean.)
Explain new BufferedReader(new InputStreamReader(new FileInputStream(f))).

From the inside out: FileInputStream is the concrete component that reads bytes from a file. InputStreamReader is an adapter: it turns a byte stream into a character Reader using a charset. BufferedReader is a decorator: it is a Reader that wraps a Reader and adds buffering and readLine(). So it is one adapter and one decorator stacked.

How to answer

Read it from the innermost object outward and name the pattern of each layer.

Likely follow-ups
  • Why are FilterInputStream subclasses decorators? (They extend InputStream and hold an InputStream.)
Add logging, metrics and retry to a payment client without touching it.

Put the client behind an interface, then write LoggingGateway, MetricsGateway and RetryingGateway, each implementing the interface and holding an inner one. Compose them at startup in a deliberate order: usually metrics outside retry (to count each logical call) or inside (to count each attempt), and retry only for idempotent operations with an idempotency key. The payment client stays unchanged and each concern is testable alone.

How to answer

Name the decorators, then spend your time on the order and on idempotency. That shows judgement.

Likely follow-ups
  • Where would a circuit breaker go in the stack?
What can go wrong with decorators in a real codebase?

Order bugs (a discount applied before tax instead of after); forgotten forwarding when the interface grows (a new method on the interface that a decorator does not override in a base that does not forward); broken equality and instanceof checks; awkward removal of a layer in the middle; and long, noisy stack traces. Mitigations: a small interface, an abstract base decorator that forwards everything, a builder or factory that owns the stacking order, and tests per decorator.

How to answer

Two or three concrete failures, each with its mitigation.

Likely follow-ups
  • How would you let a user remove an add-on from an order?
Where do you see the Decorator pattern in Linux?

Device-mapper: dm-crypt, dm-verity and dm-cache each take a block device and present a new block device with the same interface plus encryption, integrity checking or caching, and they stack. Stackable file systems (eCryptfs, overlayfs) do the same for the VFS. Each layer forwards I/O to the lower one and transforms it on the way.

How to answer

Name one stack (for example, ext4 on dm-crypt on LVM on a partition), then map it to Component, ConcreteComponent and decorators.

Likely follow-ups
  • Is LVM linear a decorator or an adapter? (Same block interface, remaps sectors: closer to a decorator or proxy.)
