How the decorator stacks, in one line of setup and one line of use:

PricingStrategy p = new LongStayDiscount(new WeekendSurcharge(new BaseRatePricing(), 20), 7, 10);
long total = p.price(400000, stay, 2);   // base, then +20% on Fri/Sat nights, then -10% if 7+ nights

Order matters and is a good thing to say out loud: discount-after-surcharge takes 10% off the surcharge too. If the business wants the discount on the base only, swap the wrapping order. The point of the pattern is that this is a configuration decision, not a code change.

From your world

PricingStrategy is a one-function ops table: a struct holding a function pointer, like file_operations.read, and each hotel points at its own implementation. The decorators are a stacked driver: think of a block device under device-mapper, where dm-crypt wraps a disk, does its own work, then calls the lower device's request function. Our BookingListener list is a notifier chain (blocking_notifier_call_chain): the core fires an event and every registered callback runs.

Where this breaks: a kernel driver stack is fixed at setup time and rarely re-ordered; here hotels change rules often, so keep each decorator immutable and swap the whole chain atomically (one reference write) rather than editing a chain in place.

Why the pattern earns its place: the if-ladder it replaces

Without decorators, every price rule is another if in one pricing method, and each combination needs care:

long price(Hotel h, RoomType t, DateRange stay) {
    long total = 0;
    for (LocalDate night : stay.nights()) {
        long p = h.baseRate(t);
        if (h.hasWeekendSurcharge && isWeekend(night)) p = p * 120 / 100;
        if (h.hasFestivalRate && festival(night)) p = p * 150 / 100;   // follow-up 1
        total += p;
    }
    if (h.hasLongStayDiscount && stay.nights().size() >= 7) total = total * 90 / 100;
    if (h.hasMemberDiscount && member) total -= 500_00;                // follow-up 2
    return total;                                                      // order of ifs = order of rules
}
interface PricingStrategy { long price(RoomType t, DateRange stay); }
abstract class PricingDecorator implements PricingStrategy {
    protected final PricingStrategy inner;          // wraps another strategy
}
PricingStrategy p = new LongStayDiscount(new WeekendSurcharge(new BaseRatePricing(rates), 20), 7, 10);
// a festival rate = one new decorator class; the stack is built per hotel

With the ladder, the follow-up "festival rates" edits the one pricing method shared by every hotel. With decorators it is one new class in Policies.java, stacked only for the hotels that use it.

From your world: the same move in C

struct pricing { long (*price)(const struct pricing *p, int type, struct range stay); const struct pricing *inner; };
static long weekend_price(const struct pricing *p, int t, struct range s)
{ return p->inner->price(p->inner, t, s) + weekend_extra(s); }
/* like stacked netfilter targets or layered block devices: each layer calls the one below */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
