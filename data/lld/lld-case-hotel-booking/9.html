Concurrency and thread safety

The last double room for the night of 5 February. Two guests press "Book" at the same moment. If "is a room free?" and "take it" are two separate steps, both guests pass the check and both take the room. That is the check-then-act race, and in a hotel it has an extra twist: the check covers several nights, so a lock-free "pop one item" trick (as in a parking lot) is not enough. All nights must be checked and taken as one unit.

  1. Guest A asks for the nights of 5 and 6 February: one room is free on both.
  2. Before A writes anything, guest B asks the same question and gets the same answer.
  3. Both write "taken". The counters now say 2 reserved out of 1. Nothing crashes; a family arrives at the desk to find no room.
  4. The fix: check every night and take every night inside one critical section on the hotel's lock. B then waits, sees 0 free, and gets a clear error. The demo runs 8 threads at H2's only double: exactly 1 winner, 7 rejections.

Why one lock per hotel, and not one global lock or one per night?

  • Global lock: obviously correct, but a booking in Goa waits for a booking in Delhi. Fine for a 20-minute demo, weak for an SDE-2 answer.
  • Per hotel (ours): bookings in different hotels never wait for each other; a booking touches exactly one hotel, so there is never a second lock to order.
  • Per (type, night): more parallel, but a 3-night stay needs 3 locks, so you must take them in date order to avoid deadlock, and a failed check means unlocking everything. It is the right shape for a database (row locks), not for in-memory code in an interview.

Two smaller rules matter as much as the lock. Never call listeners while holding the lock: an email sender that blocks for two seconds would block every booking in that hotel. And expire lazily: search and hold call expireHolds() first, and confirm checks the time itself, so correctness never depends on a background timer firing on time. A scheduled sweep can still run in production for tidiness.

The database version

When inventory lives in the room_type_inventory table, there are two standard answers. Say both and pick by contention:

-- 1. Guarded update (no explicit lock; it implicitly row-locks the matched nights until COMMIT)
UPDATE room_type_inventory
   SET reserved = reserved + :rooms
 WHERE hotel_id = :h AND room_type = :t
   AND night >= :check_in AND night < :check_out
   AND reserved + :rooms <= total;
-- success only if the row count equals the number of nights; otherwise ROLLBACK

-- 2. Pessimistic: lock the night rows in a fixed order, then check and update
BEGIN;
SELECT night, total - reserved AS free
  FROM room_type_inventory
 WHERE hotel_id = :h AND room_type = :t AND night >= :check_in AND night < :check_out
 ORDER BY night
   FOR UPDATE;
-- if every night has free >= :rooms: UPDATE ... SET reserved = reserved + :rooms; COMMIT
-- else ROLLBACK

The guarded update is short and implicitly locks only the matched rows, in index order (and, in InnoDB, the gaps next to them), until commit, so it rarely deadlocks; it is not impossible if other transactions lock nights in a different order or the planner picks another index. Still retry on deadlock and serialization errors (PostgreSQL 40P01/40001, MySQL 1213). Check that the row count equals the number of nights and ROLLBACK when it does not. It also leans on the CHECK (reserved <= total) constraint as a final safety net. The ORDER BY night in the pessimistic version is not cosmetic: two transactions that lock the same nights in the same order cannot deadlock. A version column with retries is the third option and fits when contention is low (most nights of most hotels). See Booking concurrency and Deadlock for the general patterns, and the HLD hotel design for how this scales across services.

From your world

The per-hotel lock is a per-object lock, like inode->i_rwsem or a per-socket lock (a ReentrantLock is a sleeping mutex, not a spinlock: a waiting thread blocks instead of spinning): fine-grained enough that unrelated objects never contend, coarse enough that one operation needs only one lock. Locking night rows ORDER BY night is the kernel's lock-ordering rule (for example, double_rq_lock() always takes the lower run-queue first). The state machine guarding HELD to CONFIRMED is the same discipline as a TCP state table: an ACK that arrives after a timer moved the socket to CLOSED is simply dropped.
