Idempotency: safe to call twice

An operation is idempotent if doing it twice has the same effect as doing it once. balance() is idempotent for free. setPrice(100) is too. transfer(200) is not: run it twice and Asha loses 400. Yet callers will call twice: the network times out after the server did the work, the user double-taps "Pay", a queue redelivers a message.

The standard fix is an idempotency key: the client makes a unique id per logical operation and sends it with every retry. The server remembers key to result.

This is exactly how real payment APIs behave. Stripe's API reference says it stores the status code and body of the first request made with a key, compares the parameters of later requests with the same key and errors if they differ, and may prune keys once they are at least 24 hours old (Stripe: idempotent requests). Razorpay documents idempotency in its API basics as well.

// lld-code/lld-uml-api/WalletApi.java (compiled and run)
public synchronized TransferReceipt transfer(TransferRequest r) {
    requireText(r.idempotencyKey(), "idempotencyKey");
    requirePositive(r.amount());
    if (r.fromWallet().equals(r.toWallet())) throw new InvalidRequestException("cannot transfer to the same wallet");
    TransferRequest earlier = seenRequests.get(r.idempotencyKey());
    if (earlier != null) {
        if (!earlier.equals(r)) throw new IdempotencyConflictException("key reused with a different request");
        return receipts.get(r.idempotencyKey());          // replay, no side effects
    }
    Wallet from = find(r.fromWallet()), to = find(r.toWallet());
    if (from.balance.lessThan(r.amount()))
        throw new InsufficientFundsException(from.id + " has " + from.balance + ", needs " + r.amount());
    from.balance = from.balance.minus(r.amount());
    to.balance   = to.balance.plus(r.amount());
    TransferReceipt receipt = new TransferReceipt("T" + (nextId++), from.id, to.id, r.amount(), from.balance);
    seenRequests.put(r.idempotencyKey(), r);
    receipts.put(r.idempotencyKey(), receipt);
    return receipt;
}

A design choice to say out loud: this version stores only successes, so a transfer that failed with "insufficient funds" can be retried with the same key after a top-up. Stripe's v1 API instead replays the saved first response (including errors) once execution has begun. Either is defensible; what matters is that you picked one and can say why.

From your world

TCP solved this decades ago: sequence numbers are idempotency keys. A retransmitted segment with a sequence number the receiver already acknowledged is dropped and re-ACKed, not delivered twice to the application. The idempotency store is the receiver's "what have I already seen" window, and its 24-hour retention is the equivalent of the window size.
