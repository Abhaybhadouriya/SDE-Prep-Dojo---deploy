Driver-facing APIs in a machine-coding round

In Flipkart-style machine coding (90 minutes, your own IDE, then a review call) the rules stated by candidates are consistent: working, demoable code first, in-memory storage only, no UI or database, and a driver or demo class that shows the features (workat.tech guide). Razorpay and PhonePe rounds look similar, with a review on extensibility and concurrency. The driver is where your API gets exercised, so separate it cleanly.

static void run(WalletService svc, String line) {
    String[] t = line.trim().split("\\s+");
    try {
        String out = switch (t[0]) {
            case "create"   -> "created " + svc.createWallet(t[1]);
            case "deposit"  -> "balance " + svc.deposit(t[1], new Money(Long.parseLong(t[2])));
            case "transfer" -> "ok " + svc.transfer(new TransferRequest(t[1], t[2], t[3], new Money(Long.parseLong(t[4]))));
            case "balance"  -> t[1] + " = " + svc.balance(t[1]);
            default         -> throw new InvalidRequestException("unknown command " + t[0]);
        };
        System.out.println("> " + line + "\n  " + out);
    } catch (WalletException e) {                       // one place turns errors into output
        System.out.println("> " + line + "\n  ERROR " + e.code + ": " + e.getMessage());
    }
}

Checklist before you write the first method body

  1. One method per use case on the orchestrator, named by intent. Confirm the list with the interviewer.
  2. Signatures: ids and value objects in, a receipt or id out, read-only collections.
  3. Errors: pick exceptions or result types; list the 3-5 failure kinds per method.
  4. Validation order: shape, idempotency, state rules, then mutate atomically.
  5. Retries: which commands need an idempotency key? (Anything that moves money or books inventory.)
  6. Variation: which behaviour sits behind an interface so "now add X" is a new class?
