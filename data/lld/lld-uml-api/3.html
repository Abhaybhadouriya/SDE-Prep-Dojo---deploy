Error contracts: how failure is reported

Every public method has two halves to its contract: what it returns on success, and what the caller sees on failure. The interviewer will ask "what happens if the spot is taken / the wallet does not exist / the amount is negative?" You need one consistent answer, chosen on purpose.

A good default for Java or C++ interviews: exceptions for commands, Optional for "find" queries, built on a small hierarchy with a stable machine-readable code. Do not throw Exception or RuntimeException itself, and do not make twenty exception classes. Four or five that the caller could actually react to differently is right.

static class WalletException extends RuntimeException {
    final String code;
    WalletException(String code, String msg) { super(msg); this.code = code; }
}
static final class InsufficientFundsException extends WalletException {
    InsufficientFundsException(String m) { super("INSUFFICIENT_FUNDS", m); }
}

// caller
try { svc.transfer(req); }
catch (InsufficientFundsException e) { ui.suggestTopUp(); }
catch (WalletException e)            { log.warn(e.code + " " + e.getMessage()); }
sealed interface TransferResult permits Ok, Rejected {}
record Ok(TransferReceipt receipt) implements TransferResult {}
record Rejected(String code, String message) implements TransferResult {}

// caller: the compiler makes you handle both (Java 21 pattern matching)
switch (svc.tryTransfer(req)) {
    case Ok ok            -> print(ok.receipt());
    case Rejected(var c, var m) -> print("failed: " + c);
}

From your world

The kernel's ERR_PTR / IS_ERR / PTR_ERR trick is a result type squeezed into a pointer: one return value that is either a valid object or an error code, and the caller must check. Exceptions are closer to a goto out_err that unwinds many frames at once. Both are fine; the sin in both worlds is returning NULL with no reason, or ignoring the code. Map your exception names to errnos and you will remember them: InvalidRequest is -EINVAL, NotFound is -ENOENT, a conflict is -EBUSY or -EEXIST.

For depth on checked vs unchecked exceptions, the Java exceptions tutorial is the official reference. For a production-grade error model to borrow names from, see Google AIP-193 (errors) and Stripe's error handling guide.
