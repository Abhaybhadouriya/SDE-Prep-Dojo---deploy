Inputs and outputs: what crosses the boundary

  • Take ids or small value objects, not internal entities. transfer("W1", "W2", amount) or transfer(TransferRequest), not transfer(Wallet from, Wallet to): a caller that holds your Wallet objects can bypass you.
  • Wrap meaningful primitives. Money rather than double; UserId rather than a bare String when several string ids could be swapped by mistake. (See value objects in From Use Cases to Classes.)
  • Return what the caller needs next. A TransferReceipt (id, amount, balance after) is more useful than void, and it is what an idempotent retry must return again.
  • Return copies or read-only views of collections. In Java, List.copyOf or Collections.unmodifiableList.
  • Queries do not change state; commands do not return internals. This is command-query separation. balance(w) must never move money; transfer returns a receipt, not the Wallet.
record Money(long paise) {                                   // validated value object
    Money { if (paise < 0) throw new InvalidRequestException("amount must be >= 0"); }
}
record TransferRequest(String idempotencyKey, String fromWallet, String toWallet, Money amount) {}
record TransferReceipt(String transferId, String from, String to, Money amount, Money fromBalanceAfter) {}

Java records are ideal here: immutable, value-equal and one line each. In C++ use a small struct with const members; in Python a @dataclass(frozen=True).
