Designing for change without breaking callers

The interviewer's favourite follow-up is "now add X". A good API absorbs X with additions, not edits. Practical rules:

  • Request objects grow, signatures do not. Adding an optional note to TransferRequest breaks no caller. Adding a seventh positional parameter breaks all of them.
  • Depend on interfaces. The driver holds a BookingService, not InMemoryBookingService. Tests can pass a fake; a database version slots in later. This is the Dependency Inversion Principle applied to the API.
  • Put the variation behind a strategy, not behind a flag. assignDriver(ride, boolean nearestFirst) becomes a mess at the third rule. DriverMatchingStrategy injected into the service does not.
  • Keep the old method while adding the new. In a library, mark the old one @Deprecated and make it call the new one. In a service, version the endpoint. Same idea as a kernel keeping an old syscall number alive.
  • Do not expose what you may want to change. Returning HashMap instead of Map, or exposing the internal id format, freezes those choices.
