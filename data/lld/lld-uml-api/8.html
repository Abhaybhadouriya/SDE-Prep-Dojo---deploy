Interview questions

What should the public API of your ParkingLot class look like?

One method per use case, named by intent: Ticket park(Vehicle v), Receipt unpark(TicketId t), int freeSpots(SpotType type), maybe addFloor(...) for admin. park throws NoSpotAvailableException (or returns Optional<Ticket> if "full" is a normal answer); unpark throws TicketNotFoundException for unknown or already-used tickets. Spot allocation and fee rules are strategies injected into the constructor. Floors and spots are never returned for callers to edit.

How to answer

Write the interface first, 4-6 lines, and say the failure of each method next to it.

Likely follow-ups
  • Two cars arrive at the same time for the last spot.
  • Add a monthly pass.
Exceptions or return codes for business failures? Defend your choice.

In Java/C++ LLD I use a small hierarchy of unchecked domain exceptions for commands (each with a stable code) and Optional for lookups where "not found" is normal. Exceptions keep the happy path readable and cannot be silently ignored the way a boolean can. When failure is a frequent, expected outcome the caller must branch on (a payment decline), a result type makes handling explicit and is cheaper than an exception. Never null without a reason and never a bare Exception.

How to answer

Give the rule, one reason for, one case where you would switch.

Likely follow-ups
  • Checked or unchecked?
  • How does this map to HTTP status codes?
How do you make a "transfer money" or "place order" method safe to retry?

Require an idempotency key chosen by the client per logical operation. Inside the method, before any rule check, look up the key: if found with the same request body, return the stored result without side effects; if found with a different body, reject as a conflict. Otherwise run validation and the mutation, and save key and result in the same atomic step as the mutation (same lock in memory, same transaction in a database). Expire keys after a retention window; Stripe documents pruning after at least 24 hours.

How to answer

Name the failure (timeout after success), then the key, then the two edge cases (different body, concurrent duplicates).

Likely follow-ups
  • Two retries arrive at the same moment on different threads.
  • Do you store failed attempts?
Where does validation go: the service, the entity or the driver?

All three, for different checks. The driver checks parsing only (is this a number?). Value objects validate their own shape in the constructor (Money is never negative), so invalid values cannot exist. Entities enforce their invariants in their own methods (a Wallet cannot be debited below zero). The service checks use-case rules that need several objects or current state (both wallets exist, daily limit not exceeded) and orders the checks before the mutation.

How to answer

Layer it, give one check per layer from the current problem.

Likely follow-ups
  • New rule: KYC-less wallets max 10,000 per month. Where do you add it without editing transfer?
Your getter returns the internal list of bookings. Why does the interviewer object?

Any caller can add or remove bookings without going through the rules, and a caller iterating while another thread modifies it gets a ConcurrentModificationException. It also freezes the internal data structure as part of the API. Return List.copyOf(...), an unmodifiable view, or better, a query method that answers the real question (isBooked(seat), bookingsFor(user)).

How to answer

Encapsulation, thread safety, freedom to change: three reasons in one breath.

Likely follow-ups
  • Copy or unmodifiable view: which is safer under concurrency?
The interviewer asks for a new optional "discount code" on checkout. How do you add it?

If checkout takes a request object, add an optional discountCode field; existing callers are untouched. The calculation goes into a pricing pipeline: a Discount interface (or a chain of price rules) resolved from the code, so new discount kinds are new classes. Validation of the code (exists, not expired, applicable) is a state rule in the service before the order is created. If checkout had positional parameters, I would add an overload that builds the request and keep the old one delegating to it.

How to answer

Show additive change: request field, strategy, validation slot.

Likely follow-ups
  • Two discounts at once: order of application?

Scenario: the review call after machine coding

Your 90-minute solution works. In the review the interviewer says: "Your Main calls repo.getAll().get(i).setStatus(...) in three places. Add a 'cancel booking' feature now."

Adds a fourth place in Main that edits the status, copying the checks from the other three.

"First I will move these into the service: BookingService.cancel(bookingId) that validates the current state, changes it and frees the seats under one lock. Main calls the service only. Then cancel is one new method plus one transition rule, and the three old call sites become one-line calls." Then does exactly that and shows the demo still runs.

Likely follow-ups
  • Cancel and confirm race on the same booking. What happens?
