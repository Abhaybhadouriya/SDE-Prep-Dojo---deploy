One front door: the orchestrator class

Hello Interview's LLD delivery guide recommends designing the orchestrator first, the class that drives the main workflow, and keeping its API small, with each method tied to a requirement (delivery framework). In pattern terms it is a Facade: one simple surface over many collaborating objects.

Name methods after what the user wants

The commonest weak API is a set of setters that lets the caller drive the internal state by hand. It moves the business rules out of your class and into every caller.

// Caller must know the protocol, and can get it wrong.
Seat s = show.getSeat("C7");
if (s.getStatus() == SeatStatus.FREE) {          // check ...
    s.setStatus(SeatStatus.BOOKED);              // ... then act: a race, and no rules
    s.setUserId(userId);
    show.getBookings().add(new Booking(userId, List.of(s)));   // caller edits our list
}
public interface BookingService {
    /** Holds the seats for 10 minutes. Throws SeatUnavailableException if any is taken. */
    HoldId holdSeats(UserId user, ShowId show, List<SeatId> seats);
    /** Turns a hold into a booking after payment. Idempotent per holdId. */
    BookingId confirm(HoldId hold, PaymentRef payment);
    void cancel(BookingId booking);
    List<SeatId> availableSeats(ShowId show);   // a read-only copy
}

The second version is smaller, reads like the requirements, keeps the check-then-act inside one method where it can be made atomic, and gives every rule (10-minute hold, payment before confirm) one home.
