Validation: where each check belongs

"Validate input" is not one step. There are layers, cheapest first, and each check belongs in a specific place. Doing them in order means a bad request never touches state, and an invalid object can never exist.

  1. Shape checks need no state: required fields, ranges, formats. Many live in the value objects themselves (Money refuses negatives in its constructor), so they cannot be forgotten.
  2. Idempotency lookup comes before any rule that could change: a retry of a request that already succeeded must get the same answer, even if the balance has since dropped.
  3. State rules need current data: does the wallet exist, is there enough money, is the seat still free, is the order in a state that allows cancel?
  4. Mutate only after every check passes, and record the idempotency key together with the result.
  5. Steps 3 and 4 must be one atomic unit. If another thread can run between "balance is enough" and "debit", two transfers can both pass the check: a double spend. In machine coding a synchronized method or one lock per wallet (taken in a fixed order) is enough; see Locks.

Invariants live in the entity; use-case rules live in the service. "Balance can never go negative" is an invariant of Wallet and could be enforced by a Wallet.debit method. "A KYC-less wallet may not send more than a limit per day" is a policy that the service checks, ideally through a pluggable rule (Strategy or Specification) so that new rules do not edit old code.
