The story: the front panel of a vending machine

Explain like I'm 5

A vending machine has a front panel: a coin slot, a few buttons, a little screen and a tray. Inside there are motors, coils, a coin counter and a fridge. You never touch the motors. You press "B4" and a juice falls out. If you press "B4" when juice is sold out, the screen says SOLD OUT and gives your coin back. It does not explode, and it does not silently keep your money.

If you press the button twice because nothing happened, a good machine still gives you one juice, not two, and charges you once.

That front panel is an API (application programming interface): the small set of things the outside world may do, what each one returns, and what happens when something goes wrong. In LLD the front panel is usually one class, the orchestrator or service (ParkingLot, BookingService, WalletService). Everything else is the motors inside. Interviewers judge this surface closely because it is the part every caller, test and future feature depends on.

From your world

The system call table is the kernel's front panel. User space gets open, read, write, close; it never touches the page cache or the block layer directly. Errors come back as a small, documented set (-ENOENT, -EINVAL, -EAGAIN, -EBUSY). And the kernel's famous rule "we do not break user space" is API thinking: once a call is public, its contract is frozen. ioctl is the cautionary tale: a grab-bag entry point where every driver invents its own commands, which is exactly the "one execute(String cmd) method does everything" design you should avoid in an LLD round.
