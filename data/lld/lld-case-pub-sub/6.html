Core flows

The data layout first

Publish, fail, retry, dead-letter

  1. The producer calls publish("orders", "u4", "poison"). The topic asks its Partitioner; the stable hash of "u4" modulo 3 is 1.
  2. Partition 1 appends under its lock, assigns offset 2 and returns. The producer's work ends here: it never waits for any consumer.
  3. The append signalled the condition variable. The email worker for p1, asleep inside read(2, ...), wakes with the new message and calls the subscriber, which throws.
  4. The RetryPolicy says 3 attempts with exponential backoff: wait 5 ms, try again, wait 10 ms, try once more. All fail. Meanwhile other partitions' workers keep going.
  5. The worker publishes a copy (with the reason) to orders.dlq, then commits offset 3 and moves on to u1 o7. Without the DLQ, u1's later messages would be stuck behind the poison one forever.

The same flows in words

  1. Publish Broker.publish finds the topic, Topic.publish picks the partition with the Partitioner, Partition.append adds a Message with offset = log size and signals waiters.
  2. Start a group Assign partition p to member p mod n; start one worker thread per partition.
  3. Worker loop Read up to 16 messages from the group's next offset (wait up to 50 ms if caught up). For each: deliver, then advance the offset with a compare-and-set.
  4. Deliver Try the callback; on exception sleep backoffMs(attempt) and retry; after maxAttempts, dead-letter it.
  5. Seek Set the group's next offset for one partition. The worker notices that the offset it expected changed, drops the rest of its batch, and re-reads.
