Concurrency and thread safety

This is where Uber and Flipkart spend the second half of the round. Walk through each shared thing and say who touches it.

  1. The worker read offset 7 and delivered message 7. Before it commits 8, an operator seeks the group back to 0 to replay. A plain write of 8 would overwrite the seek.
  2. The guard: the worker commits with compareAndSet(7, 8) on an AtomicLong: "move to 8 only if it is still 7". The seek changed it to 0, so the commit fails.
  3. The worker notices the failed commit, reads the current offset (0) and continues from there. The seek wins, as it should.

Why not these simpler designs?

  • One global lock around the broker. Correct but every publish waits for every read. "Publishers never block subscribers" fails.
  • Calling subscribers inside publish. The producer now runs consumer code: a slow or throwing consumer blocks or breaks the producer. It is the same mistake as doing heavy work in an interrupt handler instead of deferring it to a softirq or workqueue.
  • A thread pool where any thread takes any message. Parallel, but two messages of one key can run at the same time on two threads and finish out of order. Fix: route by partition (or by key hash) to a single-threaded lane.
  • A BlockingQueue per subscriber, deleting on take. Fine for a work queue, but replay, late subscribers and "state of consumption per consumer" are gone. Also each publish copies to N queues.
  • Holding the partition lock while calling the subscriber. Producers to that partition would wait for consumer code. read copies the slice out and releases the lock before delivery.

Delivery semantics in one picture

Commit after processing (what we do)
  • At-least-once: a crash between processing and commit replays the message.
  • Nothing is lost while the process lives.
  • Consumers must be idempotent (dedupe by message id or offset).
Commit before processing
  • At-most-once: a crash after commit loses the message.
  • No duplicates.
  • Fine for metrics, wrong for payments.

From your world

The compareAndSet commit is the same idea as advancing a ring's consumer index with cmpxchg only if nobody reset it. The bounded awaitNanos wait is a wait_event_timeout(): the worker wakes regularly to check running, so stop() never hangs on a quiet partition. And "copy out under the lock, process outside it" is what you do in a driver when you pull descriptors off the ring under a spinlock and process the skbs after dropping it.

Shutdown and back-pressure

stop() flips a volatile flag, interrupts the workers (they may be sleeping in a backoff) and joins them with a timeout. Back-pressure is not needed for correctness in this design because producers only append, but memory grows forever. The honest answers are retention (drop segments older than T or beyond S bytes, and move slow groups' offsets forward with a warning) or a bounded log where publish blocks or fails when the slowest group is too far behind. Say which one the business wants: payments prefer blocking, metrics prefer dropping.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • Condition.await / awaitNanos, wait / notifyAll = pthread_cond_wait / pthread_cond_timedwait; always recheck the predicate in a while loop because of spurious wake-ups, as wait_event() does.
  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • BlockingQueue = a bounded producer-consumer ring with a mutex and two condition variables (a kfifo plus wait queues).
