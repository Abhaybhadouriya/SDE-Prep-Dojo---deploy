The story: the school notice board

Explain like I'm 5

The head teacher has news for the whole school. She could walk to every classroom and wait at each door until the class listens. That takes all day, and if one class is noisy she is stuck at that door.

So the school puts up notice boards. She pins a note and walks away. Each board has numbered notes: 1, 2, 3 and so on. Every class sends a monitor to read the board. The monitor remembers "we have read up to note 7". The next day the monitor starts at note 8. A different class may be at note 3; that is fine, because notes are never taken down.

If one note is in a language the monitor cannot read, he tries again a couple of times, then puts a copy in the "help" tray for a teacher, and moves on to note 9 so his class is not stuck forever.

That is the whole design. The head teacher is a producer. A notice board is a topic; when one board is too busy we put up several boards for the same topic, which are partitions. A note's number is its offset. Each class is a consumer group, and the monitor's "read up to 7" is the group's committed offset. The help tray is the dead-letter queue (DLQ). Producers never wait for readers, readers never delete notes, and every class reads at its own speed.

From your world

A partition is a ring buffer that never overwrites: one write index (the log end), and many independent read indexes, one per reader. The closest kernel shape is the printk ring buffer: every open /dev/kmsg reader keeps its own sequence number, and a slow reader never blocks the writer (it just sees a gap when old records are overwritten). The ftrace ring buffer's per-reader iterators work the same way. (A NIC RX descriptor ring is a different shape: it has exactly one consumer, the NAPI context, which frees descriptors as it goes.) Waking a sleeping reader when the producer appends is a wait_event() / wake_up() pair on a wait queue (here a condition variable). The Subscriber callback is a notifier block; per-partition worker threads are like per-CPU softirq queues: one queue is handled by one context at a time, so order inside that queue is kept for free. And the dead-letter topic is the "drop and count" path every packet pipeline has for a frame it cannot parse.

This is a low-level design: classes, threads, locks and running code inside one process. The distributed version (replication, brokers on many machines, disks) is the HLD page Design a Message Queue (Kafka itself), and the real thing is the Kafka core concepts track.
