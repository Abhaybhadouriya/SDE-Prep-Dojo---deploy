Follow-up questions

How do you guarantee ordering and still process in parallel?

Order only where it matters: per key. The key's hash picks a partition, and each partition in a group is served by exactly one worker thread, so messages of one key are processed one after another. Different partitions run in parallel. Total parallelism per group equals the number of partitions.

How to answer

Say "global order and parallelism are in conflict", then give key, partition and one-thread-per-partition. Mention that more members than partitions leaves members idle.

Likely follow-ups
  • What if one key is very hot?
  • What happens to order when partitions are added?
A consumer is down for an hour. What happens to its messages?

Nothing is lost: the log keeps every message and the group's committed offset stays where it was. When the consumer comes back, its worker continues from that offset and catches up; lag tells us how far behind it is. Other groups were never affected. If the consumer was "available but failing", retries and then the DLQ keep the partition moving.

How to answer

Separate "down" (offset waits) from "failing" (retry, DLQ). Mention retention as the limit on how long "down" can last.

Likely follow-ups
  • Memory is growing; what now?
  • How do you reprocess the DLQ?
Why not just call every subscriber from publish(), each in a new thread?

Thread per message is unbounded (a burst creates thousands of threads), loses ordering (two messages of one key race), and has no place to keep progress, so a crash or a failing subscriber loses messages. A fixed worker per partition bounds threads, keeps order, and stores progress as an offset.

How to answer

Three problems: resource bound, order, durability of progress. Then the fix.

Likely follow-ups
  • Would a thread pool fix it?
  • How many worker threads in total?
Is your delivery at-least-once, at-most-once or exactly-once?

At-least-once: the offset is committed after the callback returns, so a crash or a seek can cause a redelivery. Exactly-once processing needs the consumer's side effect and the offset commit to be atomic (store the offset in the same database transaction) or an idempotency key the consumer checks. Our demo's replay shows the duplicates directly.

How to answer

Name it, show where in the code the choice is made (commit after deliver), and give the idempotency fix.

Likely follow-ups
  • How do you dedupe in the consumer?
  • What does Kafka's idempotent producer solve?
A poison message blocks a partition. How do you handle it without losing order guarantees?

Bounded retries with backoff, then move it to a dead-letter topic with its origin (topic, partition, offset) and reason, commit, and continue. Order is preserved for everything else; the poison message itself leaves the ordered stream by design, which the business must accept. If later messages of the same key depend on it, an option is to park the whole key (pause that key) instead of skipping, at the cost of complexity.

How to answer

Head-of-line blocking, retries, DLQ, then the trade-off for dependent messages.

  • Retryable vs non-retryable errors?
How would you add message filtering per subscriber?

Give join an optional Predicate<Message>. The worker evaluates it before delivery; non-matching messages are skipped but their offset is still committed, otherwise the group would stall on them. Filtering on the consumer side keeps the log shared; filtering on the producer side would need per-subscriber copies.

How to answer

Where the filter lives, and the "still commit" detail.

A new consumer joins a running group. Walk me through rebalancing.

Bump the group generation, signal all workers to stop after their current message, wait for them, compute the new assignment (round robin or range), and start workers for the new owners from the committed offsets. Commits carry the generation; a commit from an old generation is rejected so a slow, stopped worker cannot move an offset it no longer owns. During the pause there is no processing for the group, which is why real systems use incremental (cooperative) rebalancing.

How to answer

Stop, reassign, resume from committed offsets, fence stale owners with a generation number.

How do you stop the broker cleanly when workers are blocked waiting for messages?

Workers never wait forever: read waits with a timeout (50 ms) and re-checks the running flag, and stop() also interrupts them out of backoff sleeps, then joins with a timeout. The C++ version joins threads in the group destructor, and the broker owns groups after topics in declaration order, so groups (which reference topics) are destroyed first. This answers Adobe's "destructor while threads wait" follow-up (post).

How to answer

Flag + wake-up + join; destruction order in C++.

Likely follow-ups
  • Should stop() drain remaining messages first?
How would you persist the log so a restart does not lose messages?

Put a LogStore interface behind Partition. The file version appends length-prefixed records to a segment file, keeps an in-memory index from offset to file position, and rolls to a new segment at a size limit. Group offsets go to a small file written atomically (write temp, fsync, rename). On start, rebuild the index by scanning segments. Batching fsync trades durability for throughput.

How to answer

Interface first (no rewrite), then segment files, offset file, fsync trade-off.

Observer pattern vs pub-sub: what is the difference here?

In Observer, the subject holds the list of observers and calls them directly, usually synchronously. In pub-sub, a broker sits in the middle: publishers know only a topic, subscribers know only a topic, delivery is asynchronous and can be stored and replayed. Our Subscriber callback is Observer at the edge, but the broker, log and offsets are what make it pub-sub.

How to answer

Who holds the list, sync vs async, storage. Link to Observer.
