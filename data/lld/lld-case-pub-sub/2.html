Clarify requirements

Spend the first 5-8 minutes here. Say the requirements out loud, write them as a list, and get a nod. In a machine-coding round this list is also your test plan.

Functional

  1. Topics Create a topic with N partitions. Publishing to an unknown topic is an error.
  2. Publish publish(topic, key, value) appends the message and returns where it went (partition, offset). Same key always lands in the same partition.
  3. Subscribe A subscriber joins a consumer group on a topic. Every group receives every message (fan-out). Inside one group, each message is processed by one member (load sharing).
  4. Ordering Messages with the same key are processed in publish order by every group.
  5. Offsets The broker tracks, per group and per partition, the next offset to deliver. A group can seek to replay or skip.
  6. Failures If a subscriber throws, retry with backoff up to a limit, then move the message to a dead-letter topic and continue.
  7. Lag Report how far behind a group is (messages published minus messages committed).

Non-functional

  • Producers never block on consumers. Publishing is an append under a short lock.
  • Subscribers run in parallel across partitions and across groups; a slow group does not slow another group.
  • Thread-safe under many producers and many consumers.
  • At-least-once delivery: a message may be seen twice (after a retry or a replay) but is never silently lost while the process is alive.
  • Extensible: new partitioning rule, new retry rule, filters, persistence, without rewriting the core.

Out of scope (say it, so you are not graded on it)

  • Network protocol, multiple broker machines, replication and leader election (that is HLD).
  • Disk persistence and retention. Mention it as a follow-up: the log is already append-only, so writing it to a file is natural.
  • Exactly-once processing and transactions.
  • Live rebalancing when members join a running group (we will design for it in extensibility).
