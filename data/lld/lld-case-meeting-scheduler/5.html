The one line that matters: overlap

Two half-open intervals [s1, e1) and [s2, e2) overlap exactly when s1 < e2 && s2 < e1. That single condition covers all five cases people try to enumerate with if/else: left overlap, right overlap, containment, being contained, and identical. Back-to-back meetings are not overlaps because e1 == s2 fails the strict "less than".

Checking a room in O(log n): only two neighbours matter

  1. Bookings in one room are sorted by start and never overlap. A request for 10:30-11:30 arrives.
  2. Find the booking that starts at or before 10:30: floorEntry in a TreeMap, bisect_right - 1 in Python, prev(upper_bound) in C++. Here it is B.
  3. B ends at 11:00, which is after 10:30, so the request clashes. We never looked at A or C.
  4. For 11:00-12:00, B ends exactly at 11:00 (fine) and the next booking C starts exactly at 12:00 (fine). Two lookups, O(log n), done.

From your world

RoomSelectionStrategy is an ops table: the scheduler calls strategy->rank() the way the VFS calls file->f_op->read(), without knowing the implementation. MeetingListener is a notifier chain: register_netdevice_notifier() lets any module hear NETDEV_UP; addListener() lets any service hear "meeting scheduled". And the recurrence "first slot in, all slots out" function is a plain function pointer, which is why Python and C++ express it as a lambda.

Where this breaks: notifier callbacks in the kernel often run under a lock or in atomic context. We deliberately call listeners after releasing every lock, so a slow email sender cannot block other bookings.

Why the pattern earns its place: the if-ladder it replaces

Without the Strategy, every room-selection rule is a branch inside schedule:

Room pickRoom(List<Room> free, MeetingRequest req) {
    Room best = null;
    for (Room r : free) {
        if (r.capacity() < req.attendees()) continue;
        if (policy == Policy.BEST_FIT) {
            if (best == null || r.capacity() < best.capacity()) best = r;
        } else if (policy == Policy.NEAREST_FLOOR) {
            if (best == null || Math.abs(r.floor() - req.floor()) < Math.abs(best.floor() - req.floor())) best = r;
        } else if (policy == Policy.HAS_VIDEO) {   // follow-up edits schedule's class
            ...
        }
    }
    return best;
}
interface RoomSelectionStrategy {
    List<Room> order(List<Room> candidates, MeetingRequest req);
}
final class BestFitCapacity implements RoomSelectionStrategy { ... }
final class NearestFloor implements RoomSelectionStrategy { ... }

for (Room r : strategy.order(candidates, req))       // inside schedule()
    if (roomCal(r).tryReserveAll(slots, id)) return book(r);

With the ladder, the follow-up "prefer rooms with video" edits MeetingScheduler. With the interface it is one class in Strategies.java and a setStrategy call.
