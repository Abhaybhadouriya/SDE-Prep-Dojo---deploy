Interview follow-ups

Write the overlap check for two meetings. Which cases does it cover?

a.start < b.end && b.start < a.end on half-open intervals. It covers partial overlap on either side, containment both ways and identical slots, and it treats back-to-back meetings as non-overlapping. The negation is easier to reason about: two intervals do not overlap when one ends at or before the other starts.

How to answer

State the interval convention first, write the one-liner, then test it aloud on 10-11 vs 11-12 and on 10-12 vs 10:30-11.

Likely follow-ups
  • How do you check one new meeting against 10,000 existing ones quickly? (Sorted map, two neighbours.)
n rooms and a stream of requests: allocate any free room. How do you choose, and how fast is it?

Filter rooms by capacity, rank them with a RoomSelectionStrategy (smallest that fits by default), and try each with an atomic tryReserveAll; the first success wins. Each try is O(log b) for b bookings in that room, so a request is O(r log b) for r candidate rooms. If requests arrive in time order and we only need a count of rooms (the DSA version), a min-heap of end times gives O(log r) per request.

How to answer

Separate "which order" (strategy) from "is it free" (calendar). Mention the heap solution to show you see the DSA cousin (Meeting Rooms II).

Likely follow-ups
  • Prefer the room that leaves the smallest gap? (A new strategy that looks at neighbours.)
Two users book the same room at the same time. What happens?

Both reach RoomCalendar.tryReserveAll. The room's lock serialises them: the first checks and inserts; the second then checks, sees the overlap and returns false, and the scheduler tries the next candidate or throws NoRoomAvailableException. There is no gap between check and insert. Our test fires 50 threads at one slot and asserts exactly one booking.

How to answer

Name check-then-act, show the lock scope, and offer the test. For a database, mention an exclusion constraint or SELECT ... FOR UPDATE on the room row.

Likely follow-ups
  • Optimistic version per room instead of a lock? (Read version, insert with "where version = v", retry on conflict; good when contention is low.)
You lock several participants' calendars. How do you avoid deadlock?

Acquire locks in one global order: sort participants by user id, lock them in that order, and always take the room lock last. Deadlock needs a cycle of waits, and a total order on lock acquisition makes a cycle impossible. Alternatives are tryLock with a timeout and back-off, or a single coarse lock if throughput does not matter.

How to answer

Draw the two-thread cycle, then the fix. Name the four Coffman conditions and say which one you break (circular wait).

Likely follow-ups
  • What if user ids can change? (Order by an immutable internal key.)
  • Can you avoid participant locks entirely? (Yes, with the ALLOW policy.)
How do you store recurring meetings? Expand them or store the rule?

For an interview and for bounded series, expand into occurrences: overlap checks are exact and the code is simple. For "every week forever", store the rule plus a series id and expand lazily up to a horizon (a year), with exceptions stored as dates to skip or override. That is the model used by the iCalendar standard (RRULE plus EXDATE). Booking a series in a room must be all-or-nothing, which we do by checking and inserting every occurrence under one room lock.

How to answer

Give both options with their trade-offs (write cost vs read cost, exactness of conflicts), then pick one for the scope you agreed.

Likely follow-ups
  • Cancel only next Tuesday's occurrence?
  • How does a database row for a series look?
Where do notifications go in your design, and why not inside schedule()?

Behind a MeetingListener interface (Observer). The scheduler publishes onScheduled, onCancelled and onRsvp; a NotificationService turns them into messages. This keeps email/push/SMS details out of the core, lets us add reminders or audit logs as new listeners, and lets us call listeners after releasing locks so a slow mail server cannot block bookings. In production the listener would put events on a queue.

How to answer

Name the pattern, the events, and the "after unlock" detail; that detail separates good from great answers.

Likely follow-ups
  • What if the notification fails? (Retry from the queue; booking stays valid.)
  • Different channels per user? (Strategy inside the notification service.)
Find a 30-minute slot when all five people are free today.

Collect every busy interval of the five people inside the window, sort by start, sweep with a cursor: when the next busy block starts after the cursor and the gap is at least 30 minutes, emit the gap; then move the cursor to max(cursor, block end). The tail after the last block is also a candidate. O(k log k) for k busy blocks. To also need a room, intersect each gap with that room's free time.

How to answer

Say "merge intervals", walk through two overlapping blocks, and point at the max() that handles overlap.

Likely follow-ups
  • Working hours differ per person? (Treat outside-hours as busy.)
  • Time zones? (Convert to UTC first.)
Which data structure holds a room's bookings, and why not a boolean array of 15-minute slots?

A sorted map from start to booking (TreeMap, or an interval tree). It supports any minute, uses memory proportional to bookings, and checks a slot in O(log n). A boolean array is great if the business really uses fixed 15-minute slots and a short horizon (it is O(slots in meeting) and trivially lockable), but it wastes memory for long horizons and breaks when someone wants 10:05.

How to answer

Ask about time granularity first, then choose; show you know both.

Likely follow-ups
  • What changes if bookings in one room could overlap? (A real interval tree with max-end per node.)
A booking must update the room service and the people service, which live in two databases. How do you keep them consistent?

Inside one process we used locks. Across services, a two-phase commit gives atomicity but blocks if the coordinator fails, so most systems prefer a saga: reserve the room (a hold with an expiry), add the meeting to people's calendars, then confirm the hold; if a step fails, run compensations (release the hold). Make each step idempotent with a request id so retries are safe. The Zepto candidate was asked about two-phase commit at this point.

How to answer

Contrast 2PC and saga in two sentences each, then pick saga with holds and idempotency keys. Link to multi-step processes if you want depth.

Likely follow-ups
  • What if the confirm never comes? (The hold expires.)
Why is room choice a Strategy and not a parameter like sortBy="capacity"?

Because the rules are not just sort keys. "Nearest floor", "has video", "keep the board room for VPs", "leave the smallest gap" all need different logic and sometimes different data. A Strategy lets each rule be a class with its own tests, chosen at runtime (we switch in the demo), and the scheduler stays closed for modification.

How to answer

Give two rules that are not simple sort keys, then point at setStrategy.

Likely follow-ups
  • Combine two rules? (A composite strategy that sorts by the first, then the second.)
