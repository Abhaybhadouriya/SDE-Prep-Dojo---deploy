Concurrency and thread safety

Two races and one deadlock hide in this problem. Name all three in the interview.

Race 1: two people, one room, one slot

The classic check-then-act: both requests check Focus 10:00-11:00, both see it free, both insert. The fix is to make the check and the insert one atomic step under the room's lock: tryReserveAll holds RoomCalendar.lock while it checks every occurrence and inserts them. The demo fires 50 threads at Huddle for the same hour: exactly 1 wins and 49 are told the room is taken. With "any room", 40 threads and 3 rooms produce exactly 3 bookings in 3 different rooms, because a loser of one room simply moves on to the next candidate.

Race 2: a person double-booked by two organizers

With the REJECT policy, "is chen free?" and "add the meeting to chen's calendar" must also be atomic, or two organizers can both see chen free at 10:00 and both book him, in two different rooms. Room locks do not help here (different rooms). So we lock every participant's calendar for the whole schedule call.

The deadlock this creates, and the fix

  1. Thread 1 schedules a meeting for alice and bob and locks alice first. Thread 2 schedules one for bob and alice and locks bob first.
  2. Each now waits for the lock the other holds. Neither ever proceeds: a deadlock. No exception, the threads just hang.
  3. The fix is a global lock order. We sort participants by user id before locking, then take the room lock last. Every thread acquires locks in the same order, so a cycle of waiting is impossible. The demo runs 200 such pairs on 8 threads and finishes.

From your world

This is double_rq_lock() in the Linux scheduler: to lock two runqueues it always takes the one with the lower address first. Lockdep exists to catch exactly the "A then B here, B then A there" pattern. Our ordering key is the user id instead of an address, and the hierarchy "participants, then room" is the same idea as the kernel's documented lock nesting levels.

Trade-offs you should say out loud

  • Lock granularity: one global lock would be correct and simplest, but every booking in the company would queue behind it. Per-room plus per-person locks let unrelated bookings run in parallel.
  • Lock hold time: the participant locks are held while we try rooms one by one. With 500 rooms that could be long; an optimisation is to pre-filter free rooms without locks, then lock and re-check (check, lock, re-check).
  • ALLOW policy: if people may double-book (most real calendars just warn), we can skip participant locks entirely and only the room lock remains. That is a big simplification; ask early.
  • In a database: a unique or exclusion constraint does the room check for you. PostgreSQL can reject overlapping ranges per room with an exclusion constraint, but mixing room_id equality with range overlap in one GiST index needs the btree_gist extension: CREATE EXTENSION IF NOT EXISTS btree_gist; ALTER TABLE booking ADD CONSTRAINT no_overlap EXCLUDE USING gist (room_id WITH =, slot WITH &&); where slot is a tstzrange built with '[)' bounds, the same half-open rule as TimeSlot; otherwise lock the room row with SELECT ... FOR UPDATE before inserting. More on this in booking concurrency.
