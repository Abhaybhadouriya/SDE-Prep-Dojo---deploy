When to use it, and when not

Use it when
  • The concrete type is chosen at run time from data: a config value, a CLI flag, a JSON field, a request parameter.
  • Several callers create the same family of types and you want one place for the choice and the validation.
  • The set of types is small and changes rarely (a switch is fine), or changes often but you can use a registry map.
  • Construction has a little logic you do not want repeated: defaults, normalising input, caching.
Skip it or move on when
  • There is only one concrete class and no sign of a second. A factory is ceremony (YAGNI).
  • The switch is edited every sprint. It breaks the Open/Closed Principle; switch to a registry, or to Factory Method if subclasses should decide.
  • Products must come in matching sets (a Windows button with a Windows checkbox). That is Abstract Factory.
  • The object needs many optional parameters. That is a Builder problem, not a "which class" problem.
  • The factory starts doing business logic (pricing, saving to the DB). It is becoming a god function; keep it to creation.

Testing trap: a static factory called directly from deep inside a service is hard to replace in a unit test. If tests need a fake product, inject the factory (or a Function<String, Vehicle>) through the constructor. See Dependency Injection.
