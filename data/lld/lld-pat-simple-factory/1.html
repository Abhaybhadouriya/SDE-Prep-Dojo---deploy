The problem: new scattered everywhere

A parking lot app receives a vehicle type as a string from the entry gate ("car", "bike", "truck"). The first version builds objects wherever it needs them:

// EntryGate.java
Vehicle v;
if (type.equals("car"))        v = new Car(plate);
else if (type.equals("bike"))  v = new Bike(plate);
else if (type.equals("truck")) v = new Truck(plate);
else throw new IllegalArgumentException(type);

// AdminImportJob.java - the same ladder, copied
// MonthlyPassService.java - the same ladder again, but someone forgot "truck"
// ReportService.java - uses "CAR" in capitals, so it never matches

What hurts:

  • Duplication. The same if/else lives in three or four classes. They drift apart (one forgot trucks, one is case-sensitive).
  • Every caller depends on every concrete class. EntryGate imports Car, Bike and Truck, even though after construction it only calls methods on Vehicle.
  • Adding a type is a scavenger hunt. Product asks for electric cars. You must find every ladder, edit each, and re-test each caller.
  • Validation is inconsistent. Some callers throw on unknown types, some return null, one silently makes a Car.

Smell name: refactoring catalogues call this "Switch Statements" (a type switch repeated in many places). One fix is exactly this page: move the switch into one creation method. See Code Smells & Refactoring.
