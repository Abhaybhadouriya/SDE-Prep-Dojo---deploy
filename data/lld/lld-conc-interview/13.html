Two threads run if (!spot.taken) spot.taken = true; on a volatile boolean. Is it safe?

  1. Yes, volatile makes it atomic
  2. Yes, booleans are always atomic
  3. No, the check and the write are two steps
  4. Only on x86
volatile gives visibility, not atomicity of a compound action. Use compareAndSet(false, true).

Why is a read-write lock a poor fit for an LRU cache?

  1. Read-write locks are deprecated
  2. get() changes the recency order, so it is a write
  3. LRU caches never have readers
  4. It cannot be used with HashMap
Moving an entry to the front on every hit mutates shared structure; two readers would corrupt the list.

A user may have at most 2 in-progress tickets. What should the lock protect?

  1. The user (the unit of the invariant)
  2. Each ticket separately
  3. The whole board
  4. Nothing: use volatile
The rule spans several tickets of one user, so per-ticket locks let two edits pass the check together.

Conflicts on a resource are rare. Which approach fits best?

  1. A global lock
  2. Pessimistic row locks
  3. A thread per resource
  4. Optimistic concurrency with a version check
Optimistic avoids waiting; the occasional conflict pays a retry.

Four workers each wait on get() for a sub-task submitted to the same 4-thread pool. What happens?

  1. It runs slowly but finishes
  2. The JVM adds threads automatically
  3. Thread-starvation deadlock: no worker is free to run the sub-tasks
  4. An exception is thrown
Do not block on tasks in the same bounded pool; use another pool or compose futures.

In C++, a queue is destroyed while consumers wait in pop(). What is the right fix?

  1. Call notify_all() in the destructor and return
  2. A close protocol: close, wake everyone, join the threads, then destroy
  3. Make the mutex static
  4. Use volatile
Waiters still reference the mutex and condition variable; the object must outlive every thread using it.

What does counting waitingWriters in a read-write lock achieve?

  1. Writer preference: new readers wait, so writers do not starve
  2. Reader preference
  3. It removes the need for a lock
  4. It allows two writers at once
New readers queue behind a waiting writer; the writer gets in when current readers leave.
