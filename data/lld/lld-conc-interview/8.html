"Now make it thread-safe": LLD follow-ups

Your parking lot works for one user. How do you handle concurrency?

Shared state: spot occupancy and the active-ticket map. Invariant: one vehicle per spot. In memory, make "find a free spot and take it" one atomic step: a CAS per spot (compareAndSet(FREE, TAKEN)) so losers simply try the next spot, or a lock per floor if a spot choice depends on several fields. Keep the ticket map a ConcurrentHashMap. If the lot is backed by a database, use a conditional update (UPDATE spot SET vehicle=? WHERE id=? AND vehicle IS NULL) and check the affected row count, which is optimistic and needs no lock held across a round trip.

Reported: Microsoft SDE2, the candidate chose pessimistic locking for the parking lot's concurrency follow-up (LeetCode Discuss, 2025-11-17). Case study: Parking Lot.

How to answer

Run the five-step method out loud. Show the measured race (our unsafe lot gave dozens of double allocations; the CAS lot gave zero).

Likely follow-ups
  • Pessimistic or optimistic, and why?
  • Two entry gates and one display board counting free spots: how do you keep the count right?
Cab allocation: many riders request at once. How do you never assign the same driver twice?

Make the driver's state transition the atomic point: driver.state.compareAndSet(AVAILABLE, ASSIGNED). Matching can run in parallel and read a slightly stale list of nearby drivers; only the CAS decides the winner, and losers move to the next candidate. Index available drivers in a concurrent structure per area (or per geohash cell) so matching does not scan everyone. Use the State pattern for the trip lifecycle so every transition goes through one method that does the CAS. For fairness to riders, a per-area queue of requests processed by one thread avoids contention entirely.

Reported: Uber SDE2 premium cab hailing, "concurrency was the real test" (LeetCode Discuss, 2026-08-29); Uber SDE2 premium cab allocation with multithreading (LeetCode Discuss, 2026-08-22). Case study: Ride Hailing.

How to answer

Separate "find candidates" (parallel, may be stale) from "claim one" (atomic). That one sentence is the answer; the rest is detail.

Likely follow-ups
  • The driver goes offline right after being assigned.
  • Would you use synchronized on the driver, a concurrent map, or optimistic locking? Trade-offs.
Ticket or hotel booking: two users click the same seat at the same moment.

Two phases. Hold: atomically move the seat from AVAILABLE to HELD(user, expiry), via CAS in memory or a conditional update in the DB; the loser is told immediately. Confirm: after payment, HELD to BOOKED, only if the hold still belongs to this user and has not expired. A scheduler (or lazy check on read) returns expired holds to AVAILABLE. For several seats at once, lock or claim them in sorted seat-id order, and release all if any claim fails.

Reported: Paytm, asked how to prevent double booking in concert ticketing (LeetCode Discuss, 2026-11-11); Zepto SDE3 hotel booking with locks (LeetCode Discuss, 2024-09-18). Deep dive: Preventing Double Booking.

How to answer

Draw the seat state machine (AVAILABLE, HELD, BOOKED) first. Every concurrency rule is then "this transition is atomic".

Likely follow-ups
  • Payment succeeds after the hold expired.
  • Ten thousand users want the same front-row seat: what changes?
Inventory: createOrder reserves stock and confirmOrder deducts it. Make it safe under concurrent orders.

Per product keep available and reserved. Reserve: atomically check available >= qty and move qty to reserved, under a per-product lock (or ConcurrentHashMap.compute on that product's entry, which runs atomically for one key). Confirm: move from reserved to sold. Cancel or timeout: move back to available. For an order with several products, lock products in id order to avoid deadlock, or reserve one by one and roll back on failure. Never read-then-write the count in two separate steps.

Reported: Meesho SDE3 inventory management with concurrency (LeetCode Discuss, 2024-10-03); Meesho stock exchange "take care of concurrency" (LeetCode Discuss, 2026-07-15).

How to answer

Name the invariant (available + reserved + sold is constant; nothing goes negative), then the atomic step, then multi-product ordering.

Likely follow-ups
  • A flash sale makes one product very hot.
  • What changes with two service instances and one database?
Sprint planner: a user may have at most 2 in-progress tickets. Two edits move two tickets to "in progress" at once. How do you keep the rule?

The rule spans several tickets, so a per-ticket lock is not enough: both edits would pass the check "user has 1 in progress". Lock (or serialise) on the user, the unit the invariant is about: locks.computeIfAbsent(userId, k -> new ReentrantLock()), then count and move under that lock. Alternatively keep an AtomicInteger inProgress per user and CAS it from n to n+1 only if n < 2, rolling back if the ticket move fails.

Reported: Meesho machine coding, sprint planner (LeetCode Discuss, 2024-04-20).

How to answer

"The lock belongs to the invariant, not to the object being edited." That is the insight being tested.

Likely follow-ups
  • The map of per-user locks grows forever: how do you clean it up?
  • Do it with a database constraint instead.
Write a thread-safe singleton. Why is plain double-checked locking broken?

Without volatile, instance = new X() can become visible to another thread before the constructor's writes are visible, so the second thread skips the lock and uses a half-built object. Fix: make the field volatile. Simpler options: the holder idiom (a nested static class whose static field is initialised lazily and safely by class loading), or an enum singleton, which also survives serialization and reflection. In C++11 and later, a function-local static is initialised thread-safely (or use std::call_once).

Reported: Goldman Sachs, thread-safe singleton plus a SOLID fix, offer (LeetCode Discuss, 2025-05-08); Walmart SSE, thread-safe singleton (LeetCode Discuss, 2025-07-26). Deep dive: Thread-Safe Singleton & Immutability.

How to answer

Write DCL with volatile, explain the reordering in one sentence, then say "in real code I would use the holder idiom or an enum".

Likely follow-ups
  • Break your singleton with reflection or serialization.
  • Why are singletons hard to test, and what would you use instead? (Dependency injection.)
Make an LRU cache thread-safe. Why is a read-write lock not a good fit?

In an LRU, get() writes: it moves the entry to the front of the recency list. So every operation mutates shared structure, and a read lock would let two "readers" corrupt the list. Options: one lock around the map and the list (simple, correct, serial; fine for small caches); striping (N independent LRU segments by key hash, each with its own lock, an approximate global LRU); or relaxing recency (record accesses in a buffer and replay them under the lock later, which is what high-performance caches do).

Reported: Sprinklr, implement LRU in a senior round (LeetCode Discuss, 2026-03-10); Uber, leaderboard follow-ups on caching and thread safety (LeetCode Discuss, 2024-10-19). Drill: Thread-Safe LRU Cache, Rate Limiter & Counters.

How to answer

Point out that get() mutates before anyone asks about read-write locks. That observation is what separates strong answers.

Likely follow-ups
  • What does striping cost in eviction accuracy?
  • Add TTL expiry without a thread per entry.
Pub-sub / Kafka-lite: publishers and subscribers must not block each other. How do you design the threading?

Store each topic (or partition) as an append-only list with a write lock (or one writer thread); publishers only append and never wait for subscribers. Each subscriber has its own offset and its own worker thread (or a task on a pool) that reads from its offset, so a slow subscriber only delays itself. Readers wait on a per-topic condition (or poll) for new messages. Per-partition order holds because each partition has one append point and each subscriber reads it sequentially. Offsets in an AtomicLong or under the subscriber's own lock allow reset and replay.

Reported: Uber SDE2 Kafka-like with concurrency (LeetCode Discuss, 2024-09-19); Uber multithreaded pub-sub (LeetCode Discuss, 2026-04-06); Flipkart SDE3, per-partition order and thread safety (LeetCode Discuss, 2025-10-01). Case study: Pub-Sub / Message Queue.

How to answer

"Log plus per-subscriber offset" is the key idea; it removes most locking. Bridge: a ring buffer with one producer index and per-consumer read indices.

Likely follow-ups
  • Retention: delete old messages while a slow subscriber still needs them.
  • Consumer groups: two workers share one subscription.
Make a per-user rate limiter thread-safe.

Keep a ConcurrentHashMap<userId, Bucket> created with computeIfAbsent. Each bucket's refill-and-take must be atomic: either a small synchronized method on the bucket (simple, contention only per user) or a CAS loop on a packed state (tokens plus last-refill time). A sliding-window log needs a per-user lock because it removes old timestamps and adds a new one together. Never put one global lock around the whole limiter: every user would wait for every other.

Related: two 2024 practice posts ask the community to review thread-safe fixed-window and sliding-window limiters (LeetCode Discuss, 2024-09-29, LeetCode Discuss, 2024-09-29). Case study: Rate Limiter.

How to answer

Per-key granularity first, then the atomic refill-and-take, then memory cleanup for idle users.

Likely follow-ups
  • Two servers share one limit.
  • Clock goes backwards.
Car and truck parking in a 1-D array: a car takes 1 slot, a truck takes 2 adjacent slots. Make it thread-safe.

A truck needs two slots at once, so a per-slot CAS is not enough: two trucks could each grab one slot of the same pair. Options: (1) one lock for the whole array (simple; fine for a small lot); (2) lock slots in increasing index order (slot i, then i+1), check both free, take both, which avoids deadlock between neighbours; (3) a segment lock per block of K slots with care for pairs that cross a segment boundary (take both segment locks in order). Fragmentation is the follow-up: many cars can leave no two adjacent free slots, so place cars from one end and trucks from the other.

Reported: Rubrik, "thread safe car and truck parking system in a 1-D array" (LeetCode Discuss, 2026-04-16).

How to answer

Spot that a truck is a two-resource operation, which is the dining-philosophers shape, and say "lock in index order".

Likely follow-ups
  • Trucks starve because cars keep taking single slots.
  • Find a free pair faster than a linear scan.
A job graph runs tasks in topological order. Make it run on many threads safely.

Keep an AtomicInteger of remaining dependencies per job. Start by submitting all jobs with zero dependencies to a pool. When a job finishes, decrement each dependant's counter; the thread whose decrement reaches zero submits that dependant (only one thread can see the transition to zero, so each job runs once). Track jobs in flight to know when everything is done, and on failure mark dependants as skipped. No global lock is needed.

Reported: Rubrik G5, topological-sort job graph made thread-safe (LeetCode Discuss, 2025-05-30).

How to answer

Kahn's algorithm, then "replace the queue with a pool and the in-degree array with atomics". The zero-transition argument is the correctness proof.

Likely follow-ups
  • Detect a cycle before running.
  • Limit concurrency per resource type.
Thread safety is not enough: the client retries a "place order" call after a timeout. How do you avoid two orders?

Locks protect against two threads at the same moment; retries are the same request arriving twice at different moments. Use an idempotency key: the client sends a unique request id; the service atomically records it (putIfAbsent in memory, a unique index in the DB) before doing the work, and returns the stored result for a repeated id. Combine with the per-order state machine so "pay" on an already-paid order is a no-op.

Reported: Zomato SDE1 food delivery LLD with thread safety and idempotency (LeetCode Discuss, 2026-10-24); PhonePe machine coding with a next-day concurrency review (LeetCode Discuss, 2025-09-23).

How to answer

Separate "concurrent" from "duplicate". Naming both is what earns the senior signal.

Likely follow-ups
  • How long do you keep idempotency keys?
  • The first request is still running when the retry arrives.
Your design is correct with one big lock but too slow. Walk through how you would make it faster.

Measure first: is the lock actually contended, and where is time spent while holding it? Then, in order: (1) move slow work (I/O, logging, callbacks) out of the critical section; (2) split the lock by data (per entity, or striped by key hash); (3) use read-mostly techniques where reads dominate (read-write lock, or immutable snapshots swapped with an atomic reference, i.e. copy-on-write); (4) replace small critical sections with atomics; (5) give each partition of the data to one owner thread and send it messages (no locks at all). Each step adds complexity, so stop when the numbers are good enough.

Reported: Oracle SMTS design round told to "concentrate on concurrency aspects" (LeetCode Discuss, 2025-11-14).

How to answer

A ladder, not a single trick. Bridge: the kernel's path from the big kernel lock to fine-grained locks, per-CPU data and RCU is the same ladder.

Likely follow-ups
  • How do you find which lock is hot? (profilers, lock contention events, thread dumps)
  • When is the single-owner-thread model a bad idea?
