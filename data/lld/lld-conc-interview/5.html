Coordination: waiting, signalling, queues

Print odd and even numbers alternately with two threads.

One monitor and one counter: each thread waits while next % 2 is not its parity, prints, increments, and calls notifyAll(). Both threads stop when next > max, and the one that sees it first wakes the other so it can exit too. Two semaphores also work (odd starts with 1 permit, even with 0). Our version prints 1 2 3 ... 10 on every run.

synchronized (this) {
    while (true) {
        while (next <= max && next % 2 != parity) wait();
        if (next > max) { notifyAll(); return; }
        out.append(next).append(' ');
        next++;
        notifyAll();
    }
}

Why must wait() sit inside a while loop? What is a lost wake-up?

A thread can return from wait() when its condition is false: spurious wake-ups are allowed, notifyAll wakes everyone, and another thread may consume the state between the notify and this thread getting the lock back. So re-check in a loop. A lost wake-up happens when the notify fires between a thread checking the condition and going to sleep; it then sleeps forever. Java prevents it by requiring you to hold the monitor for both the check and the wait(), which releases the lock atomically as the thread sleeps.

How to answer

Two reasons for the loop, then the lost wake-up, then "the kernel's wait_event() is exactly this loop".

Likely follow-ups
  • When is notify() enough instead of notifyAll()?
  • What do Condition objects add?
Implement a bounded blocking queue.

One lock, two conditions: notFull and notEmpty. put waits while the queue is full, adds, signals notEmpty; take waits while empty, removes, signals notFull. Both wait in while loops. Separate conditions mean a producer only wakes consumers, never other producers. In production use ArrayBlockingQueue or LinkedBlockingQueue; in the interview write it to show you understand it.

C++: what happens if your thread-safe queue is destroyed while threads are still waiting in pop()?

Undefined behaviour: the waiting threads still reference the mutex and condition variable that the destructor just destroyed. The destructor cannot fix that on its own. The design fix is a close protocol: close() sets a flag under the lock and calls notify_all() on both conditions; pop() returns false once closed and drained; push() returns false once closed. The owner calls close(), joins every thread, and only then lets the queue be destroyed. Our C++14 version sums 2 x 1000 pushes across 3 consumers to exactly 1,001,000 and runs clean under ThreadSanitizer.

bool pop(T& out) {                                  // false = closed AND drained
    std::unique_lock<std::mutex> lk(m_);
    notEmpty_.wait(lk, [this] { return closed_ || !q_.empty(); });
    if (q_.empty()) return false;
    out = std::move(q_.front());
    q_.pop_front();
    notFull_.notify_one();
    return true;
}
void close() {
    { std::lock_guard<std::mutex> lk(m_); closed_ = true; }
    notEmpty_.notify_all();                          // every waiter must see closed_
    notFull_.notify_all();
}

CountDownLatch vs CyclicBarrier vs Semaphore: when do you use each?

Latch: one or more threads wait until N events have happened; one-shot, cannot be reset ("wait until all 5 services are up"). Barrier: N threads wait for each other, then all continue; reusable for rounds ("each simulation step starts together"). Semaphore: at most K threads in a section at once, or a signal between threads ("max 10 concurrent downloads"). Phaser is a flexible barrier where parties can join and leave.

Related report: a blocking hasAllTasksCompleted() after non-blocking schedule() calls, which is a latch-like wait (LeetCode Discuss, 2024-03-24).

How to answer

One sentence and one example each. The H2O puzzle uses a semaphore and a barrier together, which is a great example to mention.

  • What happens to a barrier if one thread is interrupted? (It breaks: everyone gets BrokenBarrierException.)
Three kinds of threads share a linked list: searchers, inserters and deleters. Searchers run with each other; one inserter at a time but alongside searchers; a deleter excludes everyone. Design it.

Three rules, three tools. (1) Inserters exclude each other: an insertMutex. (2) Deleters exclude everyone: a "room empty" semaphore (a lightswitch pattern): the first searcher in takes the "no deleter" semaphore and the last one out releases it, and the same for inserters; a deleter must acquire that semaphore itself. (3) To stop deleters from starving behind a stream of searchers, add a turnstile semaphore that a deleter holds while waiting, so new searchers queue behind it.

Reported: Rubrik SDE2 system-coding round (LeetCode Discuss, 2026-02-21). It is a classic from the free Little Book of Semaphores.

How to answer

Write the compatibility matrix first (S-S yes, S-I yes, I-I no, D-anything no), then map each "no" to a lock. Mention starvation before the interviewer does.

Likely follow-ups
  • Can a ReentrantReadWriteLock express this? (Not directly: inserters are neither pure readers nor exclusive writers.)
  • How would RCU solve the searcher side?
