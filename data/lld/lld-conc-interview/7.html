Deadlock, read-write locks and atomics

What are the four conditions for deadlock, and how do you prevent it in an LLD?

Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. All four must hold, so break one. In LLD code the practical fixes are: lock ordering (take locks in a global order such as entity id: breaks circular wait), take everything at once or tryLock with timeout and back off (breaks hold and wait), and the best one: design so you never hold two locks (one lock per operation, or hand work to a single owner thread).

Related report: avoid deadlock at a four-way intersection where each vehicle occupies two road segments (LeetCode Discuss, 2024-02-16). Deep dive: Deadlock, Livelock & Starvation.

How to answer

Four conditions, then the fix you would ship (ordering), then how you would detect one (thread dump).

  • Detect a deadlock in a running JVM. (jstack, ThreadMXBean.findDeadlockedThreads())
  • Livelock vs starvation?
Transfer money between two accounts concurrently without deadlock.

Transfer A to B locks A then B; transfer B to A locks B then A: two threads can each hold one lock and wait for the other. Fix: always lock the account with the smaller id first, whatever the direction. Check the balance and move the money inside both locks. Our test ran 100,000 transfers each way at the same time: no deadlock, and the total stayed at exactly 2,000,000.

static void transfer(Account from, Account to, long amount) {
    Account first = from.id < to.id ? from : to;          // global order by id
    Account second = from.id < to.id ? to : from;
    first.lock.lock();
    try {
        second.lock.lock();
        try {
            if (from.balance < amount) throw new IllegalStateException("insufficient funds");
            from.balance -= amount;
            to.balance += amount;
        } finally { second.lock.unlock(); }
    } finally { first.lock.unlock(); }
}
How to answer

Show the deadlock interleaving in two lines first, then the ordering fix. Mention that in a database the same rule applies to row locks.

Likely follow-ups
  • What if accounts have no natural order? (System.identityHashCode plus a tie-breaker lock.)
  • What if a transfer touches N accounts? (Sort them.)
Implement a read-write lock. How do you stop writers from starving?

State: readers count, writing flag, waitingWriters count, all under one monitor. lockRead waits while a writer is active or waiting; lockWrite registers as waiting, then waits while anyone holds the lock. Counting waiting writers is what gives writer preference: new readers stop entering, so the writer gets in once current readers leave. Our test: 2 writers and 4 readers, and readers never saw a half-finished write. A second test cancels a waiting writer and checks that a reader queued behind it gets in.

synchronized void lockRead() throws InterruptedException {
    while (writing || waitingWriters > 0) wait();          // queue behind a waiting writer
    readers++;
}
synchronized void unlockRead() { if (--readers == 0) notifyAll(); }
synchronized void lockWrite() throws InterruptedException {
    waitingWriters++;
    try { while (writing || readers > 0) wait(); }
    catch (InterruptedException e) {                        // cancelled while waiting:
        waitingWriters--;
        notifyAll();                                        // readers queued behind us may enter now
        throw e;
    }
    waitingWriters--;
    writing = true;
}
synchronized void unlockWrite() { writing = false; notifyAll(); }

Reported: Rubrik, "implement reader writer lock, various cases" (LeetCode Discuss, 2026-04-16). Deep dive: Read-Write Locks, StampedLock & Read-Mostly Data.

How to answer

Start with the reader-preferring version, show how writers starve, then add waitingWriters. Mention that writer preference can starve readers instead, and that a fair queue alternates.

Likely follow-ups
  • What if a waiting writer is interrupted? (It must undo waitingWriters++ and call notifyAll(). A plain finally { waitingWriters--; } leaves the readers that queued behind it asleep until some unrelated unlock.)
  • Can a reader upgrade to a writer? (Not safely: two upgraders deadlock. Release the read lock and take the write lock, then re-check.)
Likely follow-ups
  • Support upgrading a read lock to a write lock. (Why it can deadlock with two upgraders.)
  • What does StampedLock's optimistic read add? Bridge: seqlock.
What is CAS, when is it better than a lock, and what is the ABA problem?

Compare-and-swap atomically sets a value only if it still equals the expected old value, and reports success. A CAS loop (read, compute, CAS, retry on failure) never blocks a thread, so it suits a single hot field such as a counter, a state flag (AVAILABLE to ASSIGNED) or a stack head. Under heavy contention many retries waste CPU; and it cannot protect an invariant across several fields. ABA: a value changes A to B and back to A between your read and your CAS, so the CAS succeeds although the world changed (a popped and re-pushed node). Fix: a version stamp (AtomicStampedReference) or never reusing nodes.

Related report: Uber cab allocation needed "proper locking on driver state transitions (available to assigned)" (LeetCode Discuss, 2026-08-29); a 2026 practice post compares a synchronized counter with an AtomicInteger one (LeetCode Discuss, 2026-08-11).

How to answer

Definition, the loop, when it wins, when it loses, ABA. Bridge: cmpxchg and atomic_cmpxchg().
