Foundations: races, visibility, locks

What is a race condition? Give an example from an LLD problem.

A race condition is a bug where the result depends on the timing of two threads that touch the same data without coordination. LLD example: two requests both run "find a free spot, then mark it taken"; both find spot 7 free before either marks it, so two cars get spot 7. The two shapes to name are check-then-act (that one) and read-modify-write (count++ is read, add, write: two threads can read the same old value and one increment is lost).

Reported: Cleartrip, "race conditions during order placement" (LeetCode Discuss, 2026-07-21). Our measurement: 8 threads x 100,000 plain increments ended near 130,000 instead of 800,000.

How to answer

Definition in one line, then the two shapes, then an example from the design on the whiteboard, then the fix (atomic step or lock).

Likely follow-ups
  • Is volatile int count; count++ safe? (No: visible, not atomic.)
  • How would you find a race in production?
What does volatile guarantee in Java, and what does it not?

It guarantees visibility and ordering: a write to a volatile field is visible to every later read of it, and writes made before the volatile write are visible to a thread after it reads that field (a happens-before edge). It does not make compound actions atomic: v++ on a volatile is still a race. Typical correct uses: a stop flag, and the instance field in double-checked locking.

Reported: Walmart, HashMap internals and volatile after a payment-gateway LLD (LeetCode Discuss, 2025-09-21).

How to answer

"Visibility yes, atomicity no", then one correct use and one incorrect use.

Likely follow-ups
  • Why does double-checked locking need volatile? (Without it, another thread can see the reference before the constructor's writes.)
  • How is volatile different from C's volatile? (C's only stops the compiler caching; it gives no inter-thread ordering. The kernel uses READ_ONCE/WRITE_ONCE plus barriers.)
Mutex vs semaphore: what is the difference?

A mutex is a lock with an owner: one thread holds it, and only that thread may release it. It protects a critical section. A counting semaphore is a counter of permits with no owner: acquire waits while the count is 0, release adds one, and any thread may release. It limits concurrency to K (a pool of K connections) or signals between threads (a producer releases, a consumer acquires). A binary semaphore looks like a mutex but has no ownership, so no priority inheritance and no "unlock by the wrong thread" check.

Reported: LinkedIn (LeetCode Discuss, 2025-02-05); AMD (LeetCode Discuss, 2026-10-07); Sprinklr, semaphores and thread synchronisation (a separate topic in the same round as a notification-system deep dive) (LeetCode Discuss, 2026-03-10).

How to answer

Ownership is the key word. Then one use case each. Kernel bridge: struct mutex has an owner field and lockdep checks; struct semaphore is used for IRQ-to-thread signalling.

synchronized vs ReentrantLock: when do you pick each?

Both are reentrant mutual-exclusion locks with the same memory effects. synchronized is simpler and releases automatically when the block exits, even on an exception. Pick ReentrantLock when you need what it adds: tryLock() and timeouts (back off instead of deadlocking), lockInterruptibly(), optional fairness, and several Condition queues on one lock (a bounded buffer with separate "not full" and "not empty" waits). The cost: you must unlock() in finally yourself.

How to answer

"Same guarantee, more control." List the four extras, and say you default to synchronized unless you need one.

Is HashMap thread-safe? What do you use instead, and why not Collections.synchronizedMap?

No. Concurrent writes can lose entries or corrupt the table during a resize. Use ConcurrentHashMap: reads take no lock, and writes lock only one bin (the head of one bucket). synchronizedMap wraps every call in one lock, so it is correct but serial, and compound actions ("if absent then put") are still races unless you lock the map yourself. With ConcurrentHashMap, use its atomic compound methods: putIfAbsent, computeIfAbsent, merge.

Reported: Cleartrip, "thread safety of HashMap" (LeetCode Discuss, 2026-07-21); Walmart, HashMap internals (LeetCode Discuss, 2025-09-21).

How to answer

No, why, what instead, and the compound-action trap. Show map.merge(key, 1, Integer::sum) as a thread-safe counter per key.

  • Why are null keys not allowed in ConcurrentHashMap?
What is "happens-before" and how do you get it in Java?

Happens-before is the Java memory model's rule for visibility: if action A happens-before action B, then B sees A's effects. You get it from: unlocking a monitor before a later lock of the same monitor; a volatile write before a later read of it; Thread.start() before anything in the new thread; everything in a thread before another thread's join() returns; and the hand-offs in java.util.concurrent (putting into a BlockingQueue before taking out, completing a Future before get() returns). Without one of these edges, a thread may see stale or partly built data.

Reported: Roku, Java internals focused on concurrency and thread safety (LeetCode Discuss, 2026-02-27).

How to answer

One-line definition, then three or four sources of the edge. Kernel bridge: smp_store_release()/smp_load_acquire() create the same edge.
