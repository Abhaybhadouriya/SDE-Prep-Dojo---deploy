The move that decides LLD rounds: "make it thread-safe"

When the interviewer says "now many users hit this at once", do not reach for synchronized on every method. A Google interviewer was reported to be unhappy with "just synchronized" as the answer for a thread-safe LFU cache (LeetCode Discuss, 2019-09-10, older than our window but still the classic warning). Walk the same five steps every time.

  1. Find the shared mutable state. List every field that more than one request can write. Immutable and per-request data are already safe.
  2. Write the invariants that must hold between those fields. They tell you which fields must change together.
  3. Choose the granularity: the smallest unit that protects one invariant (a spot, a seat, a driver, an account).
  4. Choose the mechanism: CAS for a single field, a per-entity lock for several fields, a queue to serialise work, a DB lock or version when the state lives in a database.
  5. Prove it and test it: no lock cycles, no lost wake-ups, every waiter can finish. Then hammer it with many threads started at the same instant.

Here is the parking-lot race, measured. Sixty-four threads are released at the same instant against 32 spots. The "before" version checks a boolean, yields (to widen the gap), then sets it. The "after" version uses AtomicIntegerArray.compareAndSet.

static class UnsafeLot {
    final boolean[] taken;
    UnsafeLot(int n) { taken = new boolean[n]; }
    int park() {
        for (int i = 0; i < taken.length; i++)
            if (!taken[i]) { Thread.yield(); taken[i] = true; return i; }   // gap between check and act
        return -1;
    }
}
static class SafeLot {
    final AtomicIntegerArray taken;                    // 0 = free, 1 = taken
    SafeLot(int n) { taken = new AtomicIntegerArray(n); }
    int park() {
        for (int i = 0; i < taken.length(); i++)
            if (taken.get(i) == 0 && taken.compareAndSet(i, 0, 1)) return i;   // check + act = one step
        return -1;
    }
    void leave(int i) { taken.set(i, 0); }
}

Say: "I will make it correct with one lock first, then shrink the lock to one spot, because the invariant is per spot." Starting coarse shows you value correctness; shrinking shows you know the cost.
