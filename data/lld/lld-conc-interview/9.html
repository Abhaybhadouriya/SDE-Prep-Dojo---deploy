Scenario drills

Scenario: "just add synchronized"

You finished an LRU cache. The interviewer: "Many threads will call it. Make it thread-safe."

"I will mark get and put synchronized." (Correct but says nothing about cost, and misses that get writes.)

"Shared state is the map and the recency list; get mutates the list, so a read-write lock does not help. I start with one lock around both, which is correct. If profiling shows contention, I stripe the cache into N segments by key hash, each its own LRU with its own lock, and accept approximate global recency."

Likely follow-ups
  • How big should N be?
  • What breaks for a global capacity limit?

Scenario: the double-booked driver

In load testing, the cab service occasionally assigns one driver to two riders. The code finds the nearest driver with state == AVAILABLE, then sets state = ASSIGNED.

"Add a global lock around matching." (Fixes it but serialises every rider in the city.)

"It is check-then-act on the driver's state. Keep matching lock-free and make the claim atomic: state.compareAndSet(AVAILABLE, ASSIGNED); if it fails, try the next candidate. Add a test that releases many riders at once and asserts no driver has two trips."

Likely follow-ups
  • The driver's location also changes concurrently: does that matter?

Scenario: the pool that hangs

A report generator submits 8 "section" tasks to a fixed pool of 4 threads. Each section task submits a "chart" sub-task to the same pool and calls get() on it. Under load, everything stops.

"Increase the pool to 16 threads." (Moves the cliff, does not remove it.)

"All 4 workers are blocked in get() waiting for sub-tasks that sit in the queue with no free worker: a thread-starvation deadlock. Fix: never block on a task in the same bounded pool; use a separate pool for sub-tasks, or compose with CompletableFuture.thenCompose so no thread waits."

Likely follow-ups
  • How would you detect this from a thread dump?

Scenario: shutdown never finishes

A service with a producer-consumer queue hangs on shutdown. Thread dumps show consumers parked in queue.take().

"Call System.exit()." (Loses in-flight work and hides the design bug.)

"Consumers have no way to learn that no more work is coming. Add a close protocol: either one poison-pill item per consumer, or a closed flag plus notifyAll so take returns empty once closed and drained. Shutdown order: stop producers, close the queue, join consumers with a timeout, then interrupt stragglers."

Likely follow-ups
  • Drain or drop remaining items?
  • Same question in C++: who may destroy the queue, and when?

Scenario: the counter that is "mostly right"

A metrics counter (requests++ on a shared int) under-reports by a few percent at peak, and exactly at low traffic.

"Make it volatile." (Visibility without atomicity: still loses increments.)

"Read-modify-write race. Use LongAdder for a hot write-mostly counter (striped cells, summed on read), or AtomicLong if reads must be exact and cheap. Our 8-thread test lost most increments with a plain int and was exact with LongAdder."

Likely follow-ups
  • Why is LongAdder faster under contention? (Bridge: per-CPU counters.)
