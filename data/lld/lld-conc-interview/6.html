Executors, thread pools and futures

Design your own ThreadPoolExecutor. What classes and what lifecycle?

Classes: ThreadPool (config: core size, max size, queue capacity, keep-alive; state: RUNNING, SHUTDOWN, TERMINATED), Worker (a thread that loops: take a task from the queue, run it, catch and record exceptions, repeat), a BlockingQueue<Runnable>, and a RejectionPolicy strategy (abort, caller-runs, discard, discard-oldest). submit() wraps a Callable in a FutureTask so the caller gets a Future. shutdown() stops accepting, lets workers drain the queue and exit; shutdownNow() interrupts workers and returns the unstarted tasks. A worker that dies from an exception is replaced.

How do you size a thread pool, and what goes wrong with an unbounded queue?

CPU-bound work: about one thread per core (more only adds context switches). I/O-bound work: more threads, roughly cores x (1 + wait time / compute time), then measure. An unbounded queue (the default of Executors.newFixedThreadPool) never rejects, so under overload tasks pile up until memory runs out and latency grows without limit. Use a bounded queue plus a rejection policy; CallerRunsPolicy gives natural backpressure by making the submitting thread do the work.

How to answer

Formula, then "measure", then the overload story. Bridge: a bounded queue with backpressure is a NIC ring that drops or pauses when full.

Runnable vs Callable vs Future vs CompletableFuture.

Runnable: no result, cannot throw checked exceptions. Callable<T>: returns a value and may throw. Future<T>: a handle to a pending result; get() blocks, cancel() tries to stop it. CompletableFuture<T>: a future you can complete yourself and chain without blocking (thenApply, thenCompose, thenCombine, allOf, exceptionally); it runs on the common pool unless you pass an executor, which you should for I/O.

Design a thread-safe task scheduler: schedule(task, delay) and scheduleAtFixedRate.

A min-heap of tasks ordered by next run time (a PriorityQueue guarded by one lock, or a DelayQueue). One dispatcher thread waits on a condition with a timeout until the head is due; when a new task arrives with an earlier time, signal the condition so the dispatcher re-checks. Due tasks go to a worker pool so a slow task does not delay others. Periodic tasks are re-inserted with nextRun += period after (or before) running, and that choice is "fixed rate" vs "fixed delay". Cancellation: mark the task cancelled and skip it when it reaches the head.

Reported: Salesforce SMTS, thread-safe task scheduler (LeetCode Discuss, 2026-03-02). Case study: Task / Job Scheduler.

How to answer

Data structure (heap), the one hard part (waking the dispatcher early), then workers. Bridge: hrtimer keeps timers in a time-ordered tree and reprograms the hardware when an earlier one arrives.
