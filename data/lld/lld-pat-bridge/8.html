When to use it, when not to

Use it when
  • Two dimensions vary independently and inheritance would multiply them (kind x channel, shape x renderer, file API x filesystem).
  • You must choose or change the implementation at runtime (fallback channel, a driver picked by configuration).
  • You want clients to compile against a stable API while implementations ship separately (drivers, plugins, bindings).
  • You want to share one implementation among several abstraction objects (many File objects over one backend).
Avoid it when
  • Only one dimension varies. Then it is just an interface, or a Strategy.
  • There is only one implementation and no real second one in sight. That is premature abstraction: extra classes, extra indirection, harder reading.
  • The Implementor interface cannot be stable: if every new abstraction needs new primitives, you are editing both sides anyway.
  • Hot paths where an indirect call per operation matters and the variation is fixed at build time (then templates or compile-time selection may be better).

Design tips

  • Keep the Implementor primitive. deliver and maxChars, not sendOtp and sendPromo. Once the implementor knows about notification kinds, the two sides are coupled again.
  • Put shared policy on the abstraction side. Trimming, templating, opt-out checks, retries across channels: written once for every implementation.
  • Inject the implementor. Pass it in the constructor (or let a factory choose it). That is also what makes the abstraction testable with a fake channel.
  • Optional operations: the kernel leaves unsupported ops NULL and the VFS returns -EINVAL; in Java prefer a capability check or a default method over a null.

Level 4: threads, testing and cost

  • Threads. If several abstraction objects share one implementor (many Notifications over one SMS gateway client), the implementor must be thread-safe or stateless. Swapping the implementor at runtime (fallback channel) must be a safe publication: a volatile or final field in Java, an rcu_assign_pointer() of the ops pointer in kernel C, never a half-written reference.
  • Testing. Test each side alone. Run the abstraction against a fake implementor that records deliver() calls (trimming, templating, opt-out rules are checked without a real gateway), and run one contract test suite against every concrete implementor (same limits, same error mapping).
  • Cost. One indirect call per primitive, like any ops table. The real cost is in design: the Implementor interface becomes a published API, and every primitive you add must be implemented by every backend. Add primitives rarely, and keep them small.
