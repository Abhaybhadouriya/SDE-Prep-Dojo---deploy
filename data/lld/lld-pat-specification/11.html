Interview Q&A

Design product search where users can combine filters: brand, price range, rating, in stock.

A Spec<Product> interface with leaves BrandIn, PriceBetween, RatingAtLeast, InStock, and composites And, Or, Not. The request (query parameters or JSON) is parsed into a spec tree by a small builder. The service calls productRepo.findAll(spec), then applies a sort strategy and pagination. New filters are new leaf classes plus one line in the builder.

How to answer

Draw the interface, two leaves and the AND composite. Then separate filter (spec), order (strategy) and page (offset or cursor).

Likely follow-ups
  • Ten million products: how does this run? (Push down to the database or search index; keep the tree, change the leaves' output.)
  • How do you show counts per facet?
Design coupon eligibility rules that an admin can configure, such as "age over 18 and cart value over 1000".

Represent each condition as a leaf spec over an evaluation context (user, cart, payment mode, time): AgeAbove(18), CartValueAbove(1000), PaymentModeIs(UPI). The admin screen builds a tree, stored as JSON ({"and": [...]}), and a factory turns it back into spec objects. Checkout evaluates coupon.rule().isSatisfiedBy(ctx); usage limits and expiry are separate checks on the coupon entity. To explain rejections, have each spec return which leaf failed.

How to answer

Rule as data, spec tree, factory from JSON, separate "is eligible" from "how much discount" (a strategy).

Likely follow-ups
  • Two users redeem the last use of a coupon at once: how do you stop over-use? (Atomic decrement or a conditional update, not a spec.)
Specification vs Strategy: what is the difference?

A specification answers a yes/no question about a candidate and is meant to be combined. A strategy performs a job (compute a price, choose a driver, rank results), and you normally choose one at a time. They often work together: specs filter the candidates, a strategy ranks or prices the survivors.

How to answer

"Judge vs do", "combine vs choose", then a one-line example using both.

Likely follow-ups
  • Is Comparator a strategy or a specification?
Your in-memory specification works for 1,000 items. How does it scale to a database of millions?

Give each spec a second method that translates it for the store: a leaf becomes a SQL predicate or a search-index clause, AND/OR/NOT become the same operators, so the database filters with its indexes and returns only matches. Spring Data JPA's Specification.toPredicate and Django's Q objects work this way. Keep in-memory evaluation for tests and for leaves the store cannot express, and apply those only to the already-reduced result.

How to answer

Same tree, two interpreters (memory and query). Name an index for the most selective leaf.

Likely follow-ups
  • What happens if a NOT wraps a leaf the database cannot express? (You cannot push down that branch; you must fetch a superset and filter in memory, which is expensive.)
Why not just use Java's Predicate everywhere?

For simple in-memory filtering, Predicate.and/or/negate is enough and very short. Named spec classes add things a lambda cannot: a describe() for logs and admin screens, inspectable parameters, serialisation to JSON, translation to SQL, and equality for caching. A good design has both: specs expose asPredicate() for streams.

How to answer

Agree that Predicate is the lightweight form; list what a named spec adds.

Likely follow-ups
  • How would you unit-test a spec tree?
How is a tcpdump filter like the Specification pattern, and what does the kernel do differently?

A filter such as tcp and port 443 and not host 10.0.0.5 is a boolean tree of primitive tests, exactly a spec tree. Instead of evaluating the tree object by object per packet, libpcap compiles it into a BPF program that runs in the kernel, which avoids copying unwanted packets to user space. That is the "push down to the store" idea taken to the extreme: translate the spec into the executor's native language and run it where the data is.

How to answer

Map primitives to leaves and and/or/not to composites, then explain why compiling beats interpreting at packet rates.

Likely follow-ups
  • Why is the filter evaluated in the kernel rather than in tcpdump itself?
How do you tell the user why a coupon or listing was rejected?

Add an evaluation method that returns a result object instead of a boolean: satisfied or not, plus the failing leaves. And collects failures from both children (or from the first, if you short-circuit); Or reports failures only if both sides fail; Not needs a message like "must not be X". Each leaf supplies a human message ("cart value must exceed 1000").

How to answer

Result object, composite rules for collecting reasons, user-facing messages on leaves.

Likely follow-ups
  • Do you short-circuit when explaining? (Usually not: users want every reason at once.)
