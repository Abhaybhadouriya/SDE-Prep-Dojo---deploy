In interviews

Specification rarely gets asked by name. It is the expected design whenever you hear "search with filters" or "rules". A public Amazon LLD report describes a coupon and voucher system where an admin creates coupons with rules such as age over 18 and cart value over 1000 (LeetCode post). In-memory search engines and rental or listing search show up in Razorpay and PhonePe machine-coding rounds in our recent questions notes.

  • Car rental and rental / listing search: filters as specs, then a ranking strategy, then paging.
  • Shopping cart: coupon eligibility as a spec; the discount amount as a strategy.
  • In-memory file system: a find command with name, size and type filters.
  • Hotel booking and food delivery: restaurant or room search with cuisine, rating, distance and price filters.
  • Library: search by author, genre, availability.

Strong 30-second answer: "Each filter is a small specification class with isSatisfiedBy. And, Or and Not specs combine them, so the UI's checkboxes build a tree and the search service just calls repo.findAll(spec). New filters are new classes. In memory I evaluate the tree with short-circuiting; against a database each leaf translates to a WHERE fragment, like Spring Data's Specification. Ranking is a separate strategy applied after filtering."
