Two definitions and one test

  • Coupling is about the links between modules (classes, packages, services): how much one needs to know about another to work. Less is better.
  • Cohesion is about what is inside one module: how strongly its parts belong together and serve one purpose. More is better.

The two usually move together. When you put things that belong together in one class (raising cohesion), the links that used to cross class borders become internal, so coupling between classes falls. The classic goal, stated by Larry Constantine and colleagues in the 1970s structured-design work, is low coupling, high cohesion.

The one test: "what breaks if this changes?"

Pick any class. Imagine a reasonable change to it: rename a field, change the storage, add a case. Now count how many other classes you must edit or re-test. That number is the practical size of its coupling. Then ask the reverse question for cohesion: "if I describe this class in one sentence, do I need the word and?" Two "and"s usually means two or three classes are hiding inside one.

A short version to say in interviews: coupling is how far a change travels; cohesion is how many reasons a class has to change. The second one is exactly the Single Responsibility Principle.

From your world

You already use this test on kernel patches. A patch that touches one driver file is cheap to review. A patch that changes struct sk_buff touches hundreds of files, because so much code reads its fields directly. The skb is a deliberately shared, highly coupled structure that is worth it for speed - and that is why changes to it are rare and heavily reviewed.
