Subsystem boundaries: the kernel as a coupling lesson

The Linux kernel is a large system that stays workable largely because of where it puts its boundaries. Read it as a coupling diagram:

  1. The syscall ABI is the most stable seam. User programs see read(), never VFS internals. The kernel guarantees not to break it, so millions of programs can stay coupled to it at data level.
  2. Subsystems (VFS, sockets, block) are each functionally cohesive: all file-ish logic is in VFS, all socket logic in the socket layer.
  3. Ops tables (file_operations, proto_ops, blk_mq_ops) are the narrow seams between a subsystem and its implementations. ext4 and xfs both depend on the VFS contract, never on each other.
  4. Exported symbols (EXPORT_SYMBOL_GPL) are the explicit list of what a module may touch. Anything not exported cannot be coupled to from a module - a compile-and-link-time coupling limit.
  5. Inside a subsystem, coupling is allowed to be tighter on purpose: internal APIs change freely, and the person changing them fixes all callers in the same patch. That is a deliberate trade: low coupling where code is owned by many teams, tighter coupling where one team owns both sides.

The same driver written both ways, in plain C (lld-code/lld-prin-coupling/coupling.c, builds with gcc -std=c99 -Wall):

struct e1000_priv { int tx_ring_used; int tx_ring_size; char name[16]; };

/* TIGHT (content coupling): core reads the driver's private layout */
static int core_can_send_tight(struct e1000_priv *p) {
    return p->tx_ring_used < p->tx_ring_size;   /* breaks when the driver changes */
}

/* LOOSE: core knows only a two-function contract */
struct netdev;
struct netdev_ops {
    int (*can_send)(struct netdev *dev);
    int (*xmit)(struct netdev *dev, const char *frame, int len);
};
struct netdev { const struct netdev_ops *ops; void *priv; };

static int core_send_loose(struct netdev *dev, const char *frame) {
    if (!dev->ops->can_send(dev)) return -1;       /* -EBUSY in the real kernel */
    return dev->ops->xmit(dev, frame, (int)strlen(frame));
}
$ gcc -std=c99 -Wall -o coupling coupling.c && ./coupling
tight check says can send: 1
  eth0: sent 3 bytes (ARP), ring 1/2
loose send 1 -> 0
  eth0: sent 4 bytes (PING), ring 2/2
loose send 2 -> 0
loose send 3 -> -1 (ring full)

From your world

The void *priv plus container_of() idiom is the C way of keeping a driver's private state private: the core holds an opaque pointer and never dereferences it. In Java or C++ the same effect comes from private fields and an interface type. Same idea, enforced by the compiler instead of by review.
