The coupling ladder

Coupling is not just "on" or "off". Structured design ranks kinds of coupling from worst to best. You do not need to memorise the order perfectly, but naming the kind you see makes your review comment precise.

KindWhat it meansSmall exampleFix
ContentOne module edits or depends on another's internalsCheckout code does cart.prices.add(x) and must also update cart.cachedTotalMake fields private; add a method that keeps the rule (cart.add(x))
CommonModules share mutable global dataGlobalConfig.TAX_RATE read by ten classes and written by onePass the value in (constructor injection) or make it immutable
ExternalModules share an outside format, protocol or deviceTwo services both parse the same CSV layout by column numberOne adapter owns the format; others use its typed output
ControlA caller passes a flag that tells the callee which path to takerender(rows, true) - what does true mean?Separate methods, or pass the behaviour (Strategy)
StampA whole structure is passed when only part is usedsendReceipt(Customer c) uses only c.emailPass the field, or a narrow interface (HasEmail)
DataOnly the needed plain values are passedsendReceipt(String email, long paise)This is the target for most calls
MessageModules communicate only by events/messages, no direct callsOrder service publishes OrderPlaced; mailer subscribesUse when you need it - it also hides the flow (see trade-offs)

Here are the four most common ones in machine-coding code, each as before and after. Both versions give the same result (the demo asserts it); only the dependencies change.

// BEFORE: the caller knows the cart's private rule "keep cachedTotal in sync"
final class CartBefore {
    public List<Long> pricesInPaise = new ArrayList<>();
    public long cachedTotal;
}
static long checkout(CartBefore c) {
    c.pricesInPaise.add(9900L);
    c.cachedTotal += 9900L;        // forget this line in one place = wrong bill
    return c.cachedTotal;
}

// AFTER: the rule lives with the data; callers only see add() and total()
final class Cart {
    private final List<Long> prices = new ArrayList<>();
    private long total;
    void add(long paise) {
        if (paise <= 0) throw new IllegalArgumentException("price");
        prices.add(paise); total += paise;
    }
    long total() { return total; }
}
// BEFORE: a mutable global. Any class can change it; every reader is coupled to every writer.
final class GlobalConfig { static double TAX_RATE = 0.18; }
static long tax(long paise) { return Math.round(paise * GlobalConfig.TAX_RATE); }

// AFTER: the value is an immutable object handed in by whoever builds the service.
record TaxPolicy(double rate) { long taxOn(long paise) { return Math.round(paise * rate); } }
static long tax(TaxPolicy p, long paise) { return p.taxOn(paise); }

// The demo edits the global halfway: the BEFORE version silently changes its answer
// (1800 -> 500), the AFTER version does not.
// BEFORE: the boolean steers the callee. Callers must know its internal branches.
static String render(Map<String, Long> rows, boolean asCsv) {
    StringBuilder sb = new StringBuilder();
    for (var e : rows.entrySet()) {
        if (asCsv) sb.append(e.getKey()).append(',').append(e.getValue()).append('\n');
        else       sb.append(String.format("%-6s %6d%n", e.getKey(), e.getValue()));
    }
    return sb.toString();
}

// AFTER: the caller passes the behaviour. A new format = a new lambda/class.
interface RowFormat { String row(String k, long v); }
static final RowFormat CSV   = (k, v) -> k + "," + v + "\n";
static final RowFormat TABLE = (k, v) -> String.format("%-6s %6d%n", k, v);
static String render(Map<String, Long> rows, RowFormat f) {
    StringBuilder sb = new StringBuilder();
    rows.forEach((k, v) -> sb.append(f.row(k, v)));
    return sb.toString();
}
record Customer(String id, String name, String email, String phone,
                String address, List<String> cards) {}

// BEFORE: needs a whole Customer (and its card list!) to send one email.
static String receipt(Customer c, long paise) { return "to " + c.email() + ": paid " + paise; }

// AFTER: data coupling - only what is used. Easier to test, cannot leak card data.
static String receipt(String email, long paise) { return "to " + email + ": paid " + paise; }
from typing import Callable

def render_before(rows: dict[str, int], as_csv: bool) -> str:      # control coupling
    return "\n".join(f"{k},{v}" if as_csv else f"{k:<6} {v:>6}" for k, v in rows.items())

RowFormat = Callable[[str, int], str]
CSV: RowFormat = lambda k, v: f"{k},{v}"
TABLE: RowFormat = lambda k, v: f"{k:<6} {v:>6}"

def render_after(rows: dict[str, int], fmt: RowFormat) -> str:      # behaviour passed in
    return "\n".join(fmt(k, v) for k, v in rows.items())

rows = {"tea": 2000, "cake": 12000}
assert render_before(rows, True) == render_after(rows, CSV)
assert render_before(rows, False) == render_after(rows, TABLE)

Stamp coupling is not always bad. Passing a small value object (Money, DateRange) is fine, and better than five loose parameters. The smell is passing a big object - especially one holding sensitive data - into code that uses one field.
