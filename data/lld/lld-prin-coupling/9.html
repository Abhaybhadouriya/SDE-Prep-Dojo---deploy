Interview questions

"Coupling and cohesion" is asked as a direct theory question in Java/backend rounds (for example in a reported Zeta interview), and indirectly in every LLD review: "how would you add X?" is a coupling question.

What are coupling and cohesion? Which do you want high?

Coupling is how much one module depends on others; cohesion is how closely the parts inside one module belong together. You want low coupling and high cohesion: changes stay local, classes are easy to name, test and reuse.

How to answer

Two definitions, the goal, then one concrete example from your own code (a flag parameter, a Utils class) and its fix.

Likely follow-ups
  • How do you measure them?
  • Can cohesion be too high?
How do you check coupling in your machine-coding solution before submitting?

Three checks: (1) count outgoing dependencies per class - five or more is a smell; (2) grep for public mutable fields, static mutable state and boolean/int mode parameters (content, common and control coupling); (3) for each likely extension in the problem (new vehicle type, new payment mode), list the files you would edit - ideally one new class plus one wiring line.

How to answer

Give the checklist, then show one thing you fixed. Reviewers value a candidate who self-reviews.

Likely follow-ups
  • Where does your wiring (object creation) live?
What is control coupling and why is a boolean parameter a smell?

The caller passes data that selects the callee's internal path. The caller must know the branches, the call site is unreadable (render(rows, true)), and each new mode edits the callee. Fix with two methods, an enum with behaviour, or a strategy object passed in.

How to answer

Show the unreadable call site first - that convinces quickly - then the fix.

Likely follow-ups
  • Is a builder flag like .withRetry(true) also control coupling? (It configures, not steers a branch per call; usually fine.)
Events reduce coupling, so should every service call be an event?

No. Events remove compile-time coupling but keep logical coupling (the consumer still depends on the event's shape and meaning) and hide the flow. Use events for fan-out reactions where the publisher does not need an answer; use direct calls when the caller needs the result now or the steps must be ordered and atomic.

How to answer

Separate compile-time from logical coupling; give one case for each choice.

Likely follow-ups
  • How do you version an event schema?
A class has 20 methods. Is it low in cohesion?

Not necessarily. Size is not cohesion. Check whether methods share fields (LCOM) and whether the class has one reason to change. A Matrix with 20 operations on the same data is cohesive; a 6-method OrderManager that prices, emails and saves is not.

How to answer

Reject the size heuristic, give the field-sharing test, then a counter-example each way.

Likely follow-ups
  • How would you split the OrderManager?
How do dependency injection and interfaces reduce coupling?

The class depends on an interface (what it needs), not on a concrete class (who provides it), and receives the object from outside instead of calling new. That turns a hard link into a narrow, replaceable one: tests pass fakes, and new implementations need no edits to the class.

How to answer

Before/after constructor: new MySqlRepo() inside vs Repo repo passed in. Link to DIP.

Likely follow-ups
  • Difference between DIP, DI and IoC?

Scenario: "Your OrderService has eleven constructor parameters"

In the review call the interviewer points at OrderService: it takes a cart repo, user repo, inventory, pricing, tax, coupon engine, payment gateway, mailer, SMS sender, audit log and a clock.
"That is dependency injection, so it is loosely coupled." (True for each link, but eleven links is high fan-out and low cohesion.)
"Fan-out of 11 says this class has several jobs. Pricing, tax and coupons always go together - I would hide them behind one PriceQuoteService. Mailer, SMS and audit react to an order being placed - they can be observers of an OrderPlaced event. That leaves OrderService with repos, inventory, quote and payment: one job, place an order."
Follow-ups: what if an observer fails? Should the SMS send happen inside the transaction?
