Trade-offs: when "less coupling" is not better

Coupling is a cost, but so is every tool that removes it. Senior answers name both sides.

Tool that lowers couplingHidden costUse it when
Interface in front of a classOne more file and one more jump when readingThere are two implementations now, or one is predicted, or tests need a fake
Events / message couplingThe flow is no longer visible in code; debugging needs tracing; ordering and retries appearMany independent reactions to one fact (notify, audit, analytics)
Copying code instead of sharing itDuplicate fixes later (DRY violated)The two copies serve different owners and will diverge - shared code between teams is coupling between teams
Splitting into microservicesNetwork calls, partial failure, distributed transactionsTeams and deploy cadence differ - not as a cure for messy classes

Zero coupling is impossible and not the goal. A system is useful only because parts work together. The goal is the right coupling: explicit (visible in signatures), narrow (few methods), stable (rarely changing) and pointing toward abstractions.

Connascence: a finer vocabulary

Meilir Page-Jones proposed connascence: two pieces of code are connascent if changing one requires changing the other. It ranks forms from weak to strong - of name (agree on a method name), of type, of meaning (agree that 2 means "admin" - a magic value), of position (argument order), of algorithm (both sides must hash the same way), up to dynamic forms like timing. The rule of thumb: convert strong forms to weaker ones (replace a magic number with an enum: meaning becomes name), and keep strong forms close together, inside one class.

Control coupling from the ladder above is often connascence of meaning in disguise: render(rows, true) only works because both sides agree what true means.
