Concurrency and thread safety

A real controller has at least four independent inputs: the 1-second clock, the vehicle detectors, the pedestrian buttons and the emergency receiver, plus a maintenance port. They arrive on different threads or interrupts.

  1. One lock, every input All public methods of the Controller are synchronized (Python: one lock; C++: a mutex in the -DTS_THREADS build, compiled and run with real threads on Linux, WSL Ubuntu g++ 13, with the same output: run-cpp-linux.txt). The rule that one tick thread owns the state at a time is covered in thread-safety basics. An emergency cannot arrive halfway through a tick that is switching lights, so the light changes of one transition are atomic. The Python test runs the clock, sensors and receiver on three threads for 2,000 seconds with zero conflicts.
  2. States run under the lock State methods are only called from inside the controller's public methods, so they need no locks of their own and stay simple.
  3. Listeners are called under the lock Keep them fast (set a lamp, append to a buffer). A slow listener (network upload to a dashboard) should copy the event to a queue and return. Listeners run under the lock here for simplicity: a listener must not block, and must not call back into the controller from another thread (it would wait for the lock the tick holds). The production version queues events under the lock and fires them after unlock, as in the auction and coffee machine cases.
  4. Event-queue alternative Put every input into one queue drained by a single thread that owns the controller. No locks at all, events are processed in arrival order, and the log is a perfect replay record. This is how most embedded controllers and PLC programs are structured.
  5. Timer accuracy If a tick is late (GC pause), the controller is still safe: time only runs slower. Safety never depends on timing; only throughput does.

From your world

The event-queue design is a softirq or a single-threaded event loop: interrupts (sensors, buttons) only enqueue; one context runs the state machine. The conflict monitor in a real signal cabinet is separate hardware that watches the lamp outputs and forces the junction into flashing mode if it ever sees conflicting greens: the same idea as a hardware watchdog that resets a hung kernel, independent of the software it checks.
