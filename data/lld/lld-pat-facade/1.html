The problem: every caller wires the whole subsystem

Without a facade, every place that places an order repeats the orchestration:

// in CheckoutController, again in MobileApiHandler, again in the bulk-order job...
if (!inventory.reserve(sku, qty)) return error("out of stock");
String paymentId;
try {
    paymentId = payments.charge(user, price * qty);
} catch (PaymentException e) {
    inventory.release(sku, qty);                 // one caller forgot this line
    return error("payment failed");
}
String awb = shipping.book(address, sku);
notifier.send(user, "confirmed " + awb);
audit.log(user, sku, paymentId);                 // another caller forgot this one

Count the pains:

  • High coupling. Every client depends on four or five subsystem classes and their call order. Change the order (say, fraud check before payment) and you edit every caller.
  • Duplicated, drifting logic. Three copies of the same sequence, each with a slightly different bug in its error handling.
  • A steep learning curve. A new engineer has to understand the whole subsystem just to do the common thing.
  • Hard to test. Testing a controller means mocking five services instead of one.
