Interview Q&A

What is a Facade, and give one example from code you have used.

A facade is one class with a small, simple API in front of a subsystem of many classes. It calls them in the right order, applies defaults, and handles cleanup, so clients do not need to know the subsystem. Examples: system calls over the kernel's subsystems, shutil over os, HttpClient over connection handling, a service-layer class over repositories and external clients.

How to answer

One-sentence definition, then one concrete example with what it hides.

Likely follow-ups
  • Can clients bypass the facade? (Yes; a facade simplifies but should not lock.)
Facade vs Mediator: what is the difference?

Direction of knowledge. A facade knows the subsystem, but the subsystem does not know the facade and works without it; the facade simply offers a simpler entry point to outside clients. A mediator sits between peers that know the mediator and send their messages through it; it holds the interaction logic between them (a chat room, an auction house, an air-traffic tower). Facade simplifies the outside view; Mediator decouples the inside.

How to answer

"Does anything call back into it?" Draw arrows: one direction for Facade, both directions for Mediator.

Likely follow-ups
  • Can one class be both? (It can drift into both roles; that is usually a sign to split it.)
Facade vs Adapter: both wrap. When is it which?

An adapter converts one existing interface into a different one the client already expects, usually wrapping one class, and the point is compatibility. A facade defines a new, simpler interface over many classes, and the point is ease of use. If you are matching an interface someone else defined, it is an adapter; if you are inventing a simpler front for your own subsystem, it is a facade.

How to answer

Number of wrapped classes, and whether the interface already exists.

Likely follow-ups
  • Is SLF4J a facade or an adapter? (The API is a facade; the bindings to each logging back end are adapters.)
Is a service layer (for example OrderService) a facade?

Often, yes. A service class that coordinates repositories, payment clients and notifiers behind use-case methods is a facade over those parts. It becomes a problem when it also holds domain rules that should live in entities or strategies, or when one service has every method for every team. Keep it as a thin orchestrator, one per bounded area.

How to answer

Say yes, then name the two ways it goes wrong and how you prevent them.

Likely follow-ups
  • Where does a discount rule go? (A Strategy or domain object the facade calls, not inside the facade.)
Your placeOrder() facade calls four services. Payment fails after stock is reserved. What happens?

The facade owns the compensation: it releases the reservation and returns a clear failure. In one process that is a try/catch with undo steps in reverse order. Across services it becomes a saga: each step has a compensating action, the orchestrator (a facade-shaped service) records progress so it can resume after a crash, and calls are idempotent so retries are safe.

How to answer

Local undo first, then scale it to a saga with idempotency keys.

Likely follow-ups
  • What if the release call itself fails? (Retry with backoff from a durable log; reservations also expire on a timer.)
Why are system calls a facade?

Because one call like open() or sendmsg() hides many kernel subsystems: path lookup and the dentry cache, permission and security checks, the specific file-system or protocol implementation, memory management and the fd table. User programs get a small, stable API; the kernel can change everything behind it.

How to answer

List three or four things one syscall touches, then say "stable simple API, changing internals".

Likely follow-ups
  • And libc's fopen()? (A facade over the facade: buffering on top of open/read.)
