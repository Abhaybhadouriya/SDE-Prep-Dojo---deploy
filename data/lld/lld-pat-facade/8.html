When to use it, when not to

Use it when
  • Clients keep repeating the same multi-step sequence over several classes.
  • You want to layer a system: each layer talks to the next one only through its facade.
  • You want to shield clients from a subsystem that changes often or is being replaced.
  • You want a simple API for 80% of uses while experts can still use the full subsystem.
Avoid it, or watch out, when
  • The facade becomes a god object: dozens of methods for every team's need, and every change touches it. Split by use case or audience.
  • The facade leaks subsystem types (returns a PaymentSdkResponse): clients are coupled again. Return your own result types.
  • It holds business rules that belong in domain classes. A facade orchestrates; it should not decide prices or discounts.
  • There is only one class behind it. That is a pointless pass-through, not a facade.
  • It is forced as the only door, blocking legitimate advanced uses. A facade simplifies; it should not lock.
