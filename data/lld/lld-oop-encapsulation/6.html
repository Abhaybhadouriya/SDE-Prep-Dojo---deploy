Interview questions

What is the difference between encapsulation and abstraction?

Encapsulation bundles state with the methods that change it and restricts direct access, so the object can keep its invariants. Abstraction exposes only the essential behaviour and hides the implementation, so callers can think at a higher level. An interface is the typical abstraction; private fields plus validating methods are the typical encapsulation. You can have one without the other: a struct with public fields behind an interface is abstract but not encapsulated.

How to answer

One sentence each ("hides state" vs "hides complexity"), then one example that shows both (PaymentGateway interface + private retry state in each implementation).

Likely follow-ups
  • How is abstraction achieved in Java? (Abstract classes and interfaces - see abstract classes vs interfaces.)
  • Is a class with all getters and setters encapsulated?
Explain Java's access modifiers. How does protected differ between Java and C++?

Java has public (everyone), protected (same package plus subclasses anywhere), package-private (same package; the default) and private (same top-level class). C++ has public, protected (class, friends, derived classes) and private (class and friends); a class defaults to private and a struct to public. Java's protected is wider because it includes the whole package.

How to answer

Draw the nested-boxes picture or the table, then call out the package detail and C++'s friend.

Likely follow-ups
  • Can a subclass reduce the visibility of an overridden method? (No - it may only widen it.)
  • Can a top-level class be private? (No - only public or package-private; nested classes can be private.)
Your class has a private List field and a getter. Is it encapsulated?

Not if the getter returns the list itself: the caller can mutate it and bypass every rule. Return Collections.unmodifiableList(list) (a live read-only view) or List.copyOf(list) (a snapshot), and copy defensively when accepting a list in the constructor. Better still, expose behaviour (addItem, removeItem) instead of the collection.

How to answer

Say "the reference leaks", show the one-line fix, mention view vs copy trade-off (live and cheap vs stable and costs a copy).

Likely follow-ups
  • What if the list holds mutable objects? (The view protects the list, not the elements - make elements immutable or copy them.)
What is "tell, don't ask"? Show a refactor.

Instead of pulling data out of an object and deciding for it, call a method that expresses the intent and let the object decide with its own data. Refactor if (acct.getBalance() >= x) acct.setBalance(acct.getBalance() - x) into acct.withdraw(x). Benefits: the rule lives in one place, callers cannot skip it, and the check-and-update can be made atomic with one lock.

How to answer

Show before/after and name the concurrency bonus; machine-coding reviewers specifically look for "anemic" classes full of setters.

Likely follow-ups
  • How does this relate to the Law of Demeter?
  • When is a plain data class acceptable? (DTOs, records with no rules.)
How would you get encapsulation in C?

With an opaque pointer: declare struct foo; in the header, define it only in foo.c, and expose create/destroy plus operation functions. Callers cannot dereference the incomplete type. Use static for private helper functions. The cost is one heap allocation and no inlining of accessors across files; the gain is a stable ABI and enforced invariants.

How to answer

Mention FILE* as the famous example and the C++ pImpl idiom as the same trick.

Likely follow-ups
  • How do you add polymorphism to that? (A function-pointer ops table in the struct - see From C structs to objects.)
