Invariants: the reason to hide anything

An invariant is a rule about an object's state that must be true whenever someone outside can look at it. Examples: "balance is never negative", "a ring buffer's count is between 0 and capacity", "a seat is either free or held by exactly one booking", "a TCP connection in ESTABLISHED has both sequence numbers set". Encapsulation exists so that only the class's own methods can change state, which means you only have to check those few methods to trust the rule everywhere.

Here is the same account written twice.

static class RawAccount {
    public long balancePaise;
    public List<String> history = new ArrayList<>();
}

RawAccount raw = new RawAccount();
raw.balancePaise = -500;     // nothing stops this
raw.history.clear();         // or this - the audit trail is gone
static final class Account {
    private final String id;
    private long balancePaise;                          // invariant: never < 0
    private final List<String> history = new ArrayList<>();

    Account(String id, long openingPaise) {
        if (openingPaise < 0) throw new IllegalArgumentException("opening balance < 0");
        this.id = id;
        this.balancePaise = openingPaise;
        record("open " + openingPaise);
    }
    void deposit(long paise) {
        requirePositive(paise);
        balancePaise += paise;
        record("deposit " + paise);
    }
    void withdraw(long paise) {                         // tell, don't ask
        requirePositive(paise);
        if (paise > balancePaise)
            throw new IllegalStateException("insufficient funds: have " + balancePaise + ", need " + paise);
        balancePaise -= paise;
        record("withdraw " + paise);
    }
    long balance() { return balancePaise; }                               // primitive: safe to return
    List<String> history() { return Collections.unmodifiableList(history); } // read-only view

    private void record(String e) { history.add(e); }
    private static void requirePositive(long p) {
        if (p <= 0) throw new IllegalArgumentException("amount must be > 0");
    }
}
class Account:
    def __init__(self, opening: int):
        if opening < 0:
            raise ValueError("opening balance < 0")
        self.__balance = opening          # name-mangled to _Account__balance

    @property
    def balance(self) -> int:             # read-only: no setter defined
        return self.__balance

    def withdraw(self, amount: int) -> None:
        if amount <= 0 or amount > self.__balance:
            raise ValueError(f"cannot withdraw {amount} from {self.__balance}")
        self.__balance -= amount
$ javac -d . Encapsulation.java && java -cp . Encapsulation
raw balance: -500  (invariant broken, nobody noticed)
rejected: insufficient funds: have 1500, need 5000
balance: 1200
history is read-only to callers
history: [open 1000, deposit 500, withdraw 300]

Look at what changed. The money is stored as long paise, not a double of rupees, so there is no rounding (a design choice worth saying out loud in an interview). All three checks live inside the class. And the history getter returns an unmodifiable view, so a caller can read the list but not clear it.

Leaking a reference breaks encapsulation even with private. If history() returned the real ArrayList, any caller could clear() it. Same for accepting a mutable object in the constructor and storing it directly: the caller still holds a pointer and can change your state later. Fix it with a defensive copy in (this.items = new ArrayList<>(items) or List.copyOf(items)) and an unmodifiable view or copy out. Copy depth is covered in shallow vs deep copy.
