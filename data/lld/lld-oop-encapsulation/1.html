Encapsulation vs abstraction: two different promises

People mix these up, and interviewers know it. Here is a clean way to separate them.

  • Encapsulation is about protection. Bundle data with the code that changes it, and restrict direct access, so the object can keep its rules true. Question it answers: "who is allowed to touch this state?"
  • Abstraction is about simplification. Expose what something does and hide how it does it, so callers think in terms of the idea. Question it answers: "what does the caller need to know?"

They work together. An interface like PaymentGateway.pay(amount) is an abstraction: callers do not care whether it talks to Razorpay, Stripe or a fake in tests. Each implementation class then encapsulates its own state (API client, retry counters, idempotency keys) so nobody outside can corrupt it.

One-line answer interviewers like: "Abstraction hides complexity (you see a simple interface); encapsulation hides state (you cannot touch the internals). Abstraction is a design-level idea, encapsulation is how a class enforces it."
