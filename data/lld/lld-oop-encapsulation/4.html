Getters and setters done right: tell, don't ask

A common misunderstanding: "encapsulation means make fields private and generate a getter and setter for each". If every field has a public setter, the field is effectively public; you just made it longer to type. The rules still live outside the class, copied into every caller.

The fix is a principle called tell, don't ask (described well by Martin Fowler): instead of asking an object for its data and making a decision for it, tell the object what you want and let it decide. The decision then lives next to the data it depends on.

// in PaymentService, OrderService, RefundService ... each one repeats this
if (account.getBalance() >= amount) {
    account.setBalance(account.getBalance() - amount);
    account.getHistory().add("withdraw " + amount);
} else {
    throw new IllegalStateException("insufficient funds");
}
// every caller
account.withdraw(amount);     // the rule, the update and the audit live in Account

The "ask" version has three problems an interviewer will spot. The rule is duplicated, so it drifts. Nothing stops a fourth caller from forgetting the check. And it is not thread-safe: between getBalance() and setBalance() another thread can withdraw too. Walk through it:

  1. T1 asks for the balance (1000) and decides 800 is affordable.
  2. Before T1 writes, T2 asks too and also sees 1000. Both decisions are based on stale data.
  3. T1 writes 200.
  4. T2 writes 1000 - 800 = 200 as well. Two payments of 800 went out; the balance shows 200 and one update is lost. A check-then-act race.
  5. With tell-style, the check and the update sit inside one method, so one lock (or one CAS loop) makes them atomic. You can only do that because the logic is in one place.

When are getters fine? Reading values for display, logging, or a query is fine: balance(), status(), id(). Return immutable things or copies. Setters are the suspicious part: replace setStatus(CANCELLED) with an intention-revealing method like cancel(reason) that checks "can this order still be cancelled?". The same thinking leads to the Law of Demeter ("talk to your friends, not to strangers"): order.getCustomer().getWallet().debit(x) reaches through two objects' internals; prefer order.chargeCustomer(x).

Not every class needs behaviour. A plain data carrier (a DTO, a Java record, a Python dataclass(frozen=True)) with no invariants is fine with public read access, especially when it is immutable. Encapsulation matters most for objects with rules: accounts, bookings, game boards, caches.
