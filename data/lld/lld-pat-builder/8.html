When to use it, and when not to

Use it when
  • More than about four parameters, especially optional ones or several of the same type.
  • You want an immutable result (thread safety, safe as a map key, safe to cache).
  • Rules span several fields and must be checked together.
  • Construction is multi-step or conditional (add a header only if...).
  • The same steps must produce different outputs (GoF director + several builders).
Avoid it when
  • Two or three fields: a constructor, a static factory, or a record is clearer.
  • Your language has named and default arguments (Python, Kotlin) and no cross-field rules.
  • The object really must change over its life; a builder only helps at creation.
  • You would duplicate every field in two classes for no gain (code generation like Lombok or protobuf removes this cost).

Two classic bugs. (1) Sharing one builder between threads: builders are mutable and not thread-safe; create one per build. (2) Forgetting the defensive copy: if build() stores the caller's list, the "immutable" product changes when the caller edits that list.
