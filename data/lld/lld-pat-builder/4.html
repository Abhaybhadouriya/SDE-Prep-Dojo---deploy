How it works: one fluent build, step by step

  1. Packet.to("10.0.0.2") creates a Builder. The required field goes in here; every other field starts with a sensible default. No Packet exists yet.
  2. .from("10.0.0.1").ttl(32) changes fields on the builder. Each method returns this, which is why calls can be chained.
  3. .vlan(100).payload(data) sets more fields. The builder copies the array so the caller cannot change it later.
  4. build() runs every rule in one place: ranges, required fields, rules across fields (payload must fit the MTU).
  5. If all rules pass, the private constructor Packet(Builder b) copies the fields into final fields. The product is immutable and safe to share between threads.
  6. If a rule fails (VLAN 5000 is outside 1..4094), build() throws. The caller never holds an invalid or half-built object.

From your world

You have built packets this way for years. Sending a UDP datagram in the kernel goes roughly: alloc_skb(len) gets a buffer, skb_reserve(skb, headroom) leaves room at the front, skb_put() appends the payload at the tail, then each layer calls skb_push() to prepend its header: UDP, then IP, then Ethernet. Netlink messages are built the same way with nlmsg_put() followed by nla_put_*() for each attribute, then nlmsg_end() to fix the length.

The difference: an sk_buff is mutable, and the builder and the product are the same buffer, because the kernel wants zero copies. In application code we pay one small copy in build() to get an immutable, validated object. nlmsg_end() is the closest thing to build(): it is the step that makes the message complete.
