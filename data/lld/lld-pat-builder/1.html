The problem: telescoping constructors and half-built objects

Say you model a network packet. Only the destination is required; source, protocol, TTL (time to live), DSCP (the QoS marking), VLAN and payload are optional with defaults. The first attempt is usually a "telescope" of constructors, each adding one more argument:

class Packet {
    Packet(String dst) { this(dst, "0.0.0.0"); }
    Packet(String dst, String src) { this(dst, src, 17); }
    Packet(String dst, String src, int proto) { this(dst, src, proto, 64); }
    Packet(String dst, String src, int proto, int ttl) { this(dst, src, proto, ttl, 0); }
    Packet(String dst, String src, int proto, int ttl, int dscp) { this(dst, src, proto, ttl, dscp, 0, new byte[0]); }
    Packet(String dst, String src, int proto, int ttl, int dscp, int vlan, byte[] payload) { /* ... */ }
}

// call site: which number is the TTL? which is the VLAN?
Packet p = new Packet("10.0.0.2", "10.0.0.1", 6, 32, 0, 100, data);
Packet q = new Packet("10.0.0.2", "10.0.0.1", 6, 100, 0, 32, data);   // swapped ttl and vlan: compiles fine

The usual "fix" is worse: a no-argument constructor plus setters (the JavaBeans style).

Packet p = new Packet();
p.setDst("10.0.0.2");
p.setVlan(5000);              // invalid, but nobody checks yet
sendQueue.add(p);             // another thread can see p NOW, half configured
p.setTtl(32);                 // ...and p changes while it sits in the queue
ApproachReadable?Validated once?Immutable?Scales to 10+ fields?
Telescoping constructorsNo (positional)YesYesNo (2n combinations)
Setters (JavaBeans)YesNo (any order, any time)NoYes
BuilderYes (named steps)Yes (in build())YesYes

Joshua Bloch's Effective Java (Item 2: "Consider a builder when faced with many constructor parameters") is where most Java developers first meet this version. Its advice in short: use a builder when you have more than a handful of parameters, especially optional ones of the same type.
