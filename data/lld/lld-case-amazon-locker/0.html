The story: the wall of doors at the petrol station

Explain like I'm 5

Imagine a big cupboard with many little doors: small ones for books, medium ones for shoes, a few big ones for a football. A delivery person brings a parcel. The cupboard looks for the smallest empty door the parcel fits in, opens it, and the parcel goes in. Then the cupboard sends your mum a secret number. When she types the number, only that door opens, and the number stops working.

If nobody comes for three days, the cupboard stops accepting the number, and the delivery person takes the parcel back so the door can be used again.

That is the whole problem. The doors are slots with a size, the cupboard is a locker station, "the smallest door that fits" is an allocation strategy, the secret number is a one-time pickup code, and "three days" is an expiry. The interview question is how to write the cupboard so that two couriers never get the same door, a code opens exactly one door exactly once, and a forgotten parcel never blocks a door forever.

From your world

You have written this allocator before. kmalloc() rounds a request up to the next size class (kmalloc-64, kmalloc-128, ...) and takes an object from that cache's free list; if the class is exhausted it does not hand out a smaller object. That is exactly our best-fit rule with one free list per size. The page allocator's watermarks (pages kept back for GFP_ATOMIC callers) are our ReservingBestFitStrategy, which keeps the last large slots for parcels only a large slot can hold. Marking a slot out of service is a bad-block table. And the pickup code is a capability: whoever holds the token may open the door, and it is revoked after one use, like a nonce.

Where this breaks: a kernel allocator can fail fast and the caller retries. A courier standing at the station cannot wait: when nothing fits, the design must say what happens next (try a nearby station, or take the parcel back). Say this in the room.
