Concurrency and thread safety

Start with a list of shared state and who touches it, then pick one protection per row. The answer here is one lock per station: every operation is a few map and deque steps, and stations share nothing, so a global lock would serialise the whole country for no reason.

Step through the race this section is about, then the fix the code uses:

  1. Courier A asks for a small slot: one free, S02.
  2. Courier B asks before A marks it: still one free, the same S02.
  3. Both put a parcel in S02 and both customers get a code for it.
  4. The fix: deposit is synchronized on the station, so count, poll, mark and code issue are one step. B then sees no small slot and the best-fit strategy upgrades it to a medium one. The demo's 8-thread stress test never double-allocates.

The three races to name

  1. Double allocation Two couriers both see one free small slot. Check (count) and act (poll) are in one synchronized method, so the second sees zero.
  2. Double pickup A customer taps "open" in the app while also typing the code on the keypad. Lookup, state check, state change and code removal happen under the lock; the second call finds no code. The demo's 2 racing pickers prove it: 600 opens, 600 refusals.
  3. Pickup versus expiry The sweep runs at the exact moment the customer types. Both paths compare now >= expiresAt under the same lock, so the delivery is either picked up or expired, never both. Pickup also checks expiry itself (lazy expiry), so a late sweep cannot let an expired code through.

Why not finer locks?

A lock per size class, or a lock-free ConcurrentLinkedDeque per size, sounds faster. But a best-fit deposit may read the small list and then take from the medium list, and the code index must change with the slot. Two locks means lock ordering and a window where invariants break; lock-free deques mean the "count then poll" race comes back. At a few hundred slots and a few operations per second per station, one lock costs microseconds. Say that, and offer finer locks only with a measurement.

From your world

This is the per-device lock versus big kernel lock decision. The station lock is like a per-device lock protecting a driver's descriptor rings (a sleeping mutex here, because nothing runs in interrupt context; a driver uses spinlock_t only for that reason): the slot free list and the "who owns slot N" map must change atomically together, the way a TX ring's head index and the skb array do. Listeners run after unlock, like deferring work to a workqueue instead of calling out while holding a spinlock.

Never call listeners under the lock. An SMS gateway that takes 2 seconds would block every courier at that station for 2 seconds, and a listener that calls back into the service (for example, to read availability) would deadlock on a non-reentrant lock in other languages.
