Interview follow-ups

How do you find the optimal locker quickly?

Keep one free list per size class. Best fit is "the first non-empty list at or above the parcel's size", which is at most three checks and an O(1) pop. Scanning every slot is O(n) per deposit and was the reason a 2019 candidate was asked to improve their code. With real dimensions instead of classes, keep free slots in a TreeMap keyed by volume (or by sorted dimensions) and use ceilingEntry, O(log n).

How to answer

State the data structure first, then the rule, then the cost. Mention the kmalloc size-class analogy if the interviewer is systems-minded.

Likely follow-ups
  • What if sizes are continuous? (TreeMap by volume plus a fit check for rotation.)
  • Which free slot of a size do you pick? (FIFO to spread wear, or nearest to the screen for accessibility.)
When should a small parcel get a medium slot, and when not?

Best fit upgrades only when the exact size is full. That maximises accepted parcels now, but can starve large parcels later: three small parcels can fill the only large slots. The fix is a reserve: allow an upgrade into size S only while more than k slots of S stay free (our ReservingBestFitStrategy). This is the same idea as memory watermarks. The right k comes from the station's parcel-size mix.

How to answer

Name the trade-off (utilisation now versus availability for big parcels), show it is a strategy swap, and suggest picking k from data.

Likely follow-ups
  • Could you move a small parcel out of a large slot later? (Not physically; plan at deposit.)
How would you design the OTP?

Six random digits from a cryptographically secure generator (SecureRandom, Python secrets), unique among live codes at that station, single use, valid until the delivery expires. Send it to the customer only, through a listener; never return it to the courier. Rate-limit guesses per keypad (we lock for 60 s after 5 misses): with, say, 300 live codes at a station, one random guess succeeds with probability 300 in a million, so unlimited guessing would empty a station. Store a hash of the code if the database might leak. For a station that must verify offline, derive the code with an HMAC over the delivery id and a per-station secret, in the style of RFC 6238.

How to answer

Cover generate, deliver, verify, expire, abuse. Give the guess-probability arithmetic; it shows why lockout matters.

Likely follow-ups
  • Why unique only per station? (The code is always entered at a known station, so the station id is part of the key.)
  • What if the SMS is delayed? (Resend from the delivery record; the code does not change.)
Two couriers deposit at the same station at the same moment. What can go wrong?

Both read "one small slot free" and both take it: one door, two parcels, and two codes that open it. Reading the count and popping the slot is a check-then-act, so it must be one critical section. Every station method is synchronized, which also covers the code index and the parcel index, so all three change together. Stations do not share slots, so the lock is per station and stations never block each other.

How to answer

Describe the interleaving step by step, name it check-then-act, give the lock and its scope, and justify the granularity.

Likely follow-ups
  • Could you avoid the lock with atomics? (Not without a CAS loop across several structures; not worth it here.)
  • How did you test it? (8 threads, 800 parcels, 600 slots, assert distinct slot ids.)
Who frees the slot when a parcel expires?

Not the expiry sweep: the parcel is still inside. Expiry only moves the delivery to EXPIRED and kills the code. The slot stays OCCUPIED until a courier runs collectExpired, which marks deliveries RETURNED, removes their codes and puts the slots back on the free lists. Freeing on expiry would let the system assign a door that still holds a parcel.

How to answer

Separate the logical state (delivery) from the physical state (slot). Draw the two state machines.

Likely follow-ups
  • What triggers the sweep? (A periodic job; pickup also checks expiry lazily.)
  • How do you avoid an O(n) sweep? (A min-heap by expiresAt per station.)
Why is there a Delivery class? Could Slot hold the code?

A slot is long-lived hardware; a delivery is a short-lived event with its own key (the code), its own timer (expiry) and its own history. With the code on the slot, you cannot keep an expired parcel's record while the slot is reused, you cannot audit "where was parcel p3", and reservations or returns need yet more fields on the slot. One class per lifecycle keeps each small.

How to answer

Point to the lifecycle mismatch and to one feature (history, returns) that breaks without the split.

How do you add reservations at checkout?

Add a RESERVED slot state and a Reservation (order id, size, slot, hold-until). At checkout, call the strategy and move the chosen slot from FREE to RESERVED. At deposit with a reservation id, skip the strategy and use the reserved slot. The expiry sweep releases reservations whose hold passed. The availability shown at checkout then becomes a promise instead of a hint, at the cost of idle slots while parcels travel.

How to answer

Show the new state on the state machine and which existing code stays unchanged (pickup, strategies).

Likely follow-ups
  • How long should a reservation hold? (Delivery ETA plus slack; release early on cancellation.)
Packages have real dimensions. How does allocation change?

Two options. Keep size classes and classify each box by its longest side (our Size.forBox); simple and fast but wastes space. Or keep free slots ordered by volume and check a true fit: sort the box's three dimensions and the slot's three dimensions and compare pairwise, which allows any axis-aligned rotation. Best fit is then the smallest-volume free slot that fits, found by walking up from ceilingEntry(boxVolume). The 2022 Amazon L5 post used the same "sort by max dimension, then check" idea.

How to answer

Offer the cheap option first, then the exact one with its cost.

The station loses power mid-deposit. What is the state?

In memory, nothing survives, so persist first. Write the delivery record (slot, parcel, code hash, expiry) durably before telling the hardware to open the door, and mark it confirmed when the door-closed sensor fires. On boot, rebuild slot states and free lists from the records; unconfirmed deposits are checked against door sensors. This is a write-ahead log: intent first, effect second.

How to answer

Say "write-ahead", give the order of steps, and say what recovery does with half-done operations.

Turn this into the HLD question: thousands of stations.

Each station runs this LLD locally (it must open doors without the network) and syncs with a regional service. The service owns station discovery by location (geo index), availability snapshots for checkout, code delivery and the return logistics. Stations are natural shards, so no cross-station transaction exists. The hard parts are offline verification (HMAC codes), eventual consistency of availability (reservations fix it) and idempotent deposit APIs.

How to answer

Draw the line between the station (LLD, local, authoritative for slots) and the cloud (HLD, authoritative for orders).
