Interview questions

Where this is asked

Every booking-style case study ends with the same follow-up: "two users, one seat, same instant". Open the case and look for the concurrency section:

Two users book the same seat at the same time. How does your design prevent double booking?

Name the race (check-then-act), then make check + act atomic at the right scope: a per-show or per-seat lock in memory (sorted order for multi-seat), or a CAS on a versioned seat state. For several servers, a conditional update or version column in the database, with a unique constraint as a safety net. Add TTL holds for the payment window.

How to answer

Race, scope (one process or many), granularity, then the hold lifecycle. Show you know both pessimistic and optimistic and pick one with a reason.

Likely follow-ups
  • What if payment succeeds after the hold expired?
  • How do you free expired holds?
Pessimistic or optimistic locking: which would you choose and why?

It depends on contention and on how long the decision takes. Pessimistic when conflicts are frequent and the critical section is short (hot stock, wallet balance): losers queue fairly. Optimistic when conflicts are rare or the user thinks between read and write (most bookings, profile edits): no locks held, no deadlocks, but heavy contention turns into retries. Many systems mix them: optimistic by default, pessimistic for known hot rows.

How to answer

Do not pick blindly. Ask about contention, then commit to one. "Most web apps use optimistic" is a fine thing to say if you also say when it fails.

Likely follow-ups
  • What is ABA and does your version column solve it? (Yes, versions only increase.)
Why is ConcurrentHashMap alone not enough here?

It makes single operations safe, not sequences. if (!map.containsKey(seat)) map.put(seat, user) is still two calls. Use one atomic method (putIfAbsent, compute, replace(k, old, new)) for single-key decisions, or a lock when the decision spans several keys.

How to answer

Show the two-call bug, then putIfAbsent returning null for the winner.

Likely follow-ups
  • Booking 3 seats atomically with only ConcurrentHashMap? (Not possible cleanly; use a lock per show or sorted per-seat locks.)
Design seat holds with a timeout. What can go wrong?

Hold = atomic state change to HELD with expiresAt. Problems: (1) relying on a timer to free seats exactly on time, so check expiry lazily on every read; (2) payment succeeding after expiry, so confirm must re-check and refund; (3) duplicate payment callbacks, so make confirm idempotent by hold or payment id; (4) server restart losing in-memory holds, so store them in the DB or Redis with a TTL; (5) clock skew across servers, so use the database's now() or one time source.

How to answer

Draw the state machine FREE, HELD, BOOKED, and walk each arrow's failure.

Likely follow-ups
  • How long should the TTL be? (Long enough for payment, short enough not to waste inventory: often a few minutes, shown as a countdown.)
A per-seat lock map grows forever. How do you bound it?

Options: lock striping (fixed array of N locks indexed by hash), locks per show (created when the show is created, dropped when it ends), or no lock objects at all (CAS on the seat state stored in the map). Removing per-key locks from the map while threads might hold them is subtle and best avoided.

How to answer

Striping first; mention Guava Striped or the old ConcurrentHashMap segments.

Likely follow-ups
  • What if two seats in one booking hash to the same stripe? (Sort and de-duplicate stripe indexes before locking.)
SELECT FOR UPDATE vs a version column in the database?

FOR UPDATE locks rows for the transaction: others wait (or fail with NOWAIT, or skip with SKIP LOCKED). Simple reasoning, but long transactions block others and multi-row locks need a consistent order to avoid deadlocks. A version column holds no locks; the update fails if someone wrote first. Better for short, rarely conflicting updates and when the user's think time sits between read and write.

How to answer

Map each to pessimistic and optimistic, then the rule: never hold a row lock across a network call to payment.

Likely follow-ups
  • Which isolation level do you need? (With a conditional update or row lock, the default READ COMMITTED is enough for a single row.)
Your lock is in one JVM, but the service runs on 10 pods. What now?

The in-memory lock no longer protects anything across pods. Move the atomic step to shared state: the database (conditional update, row lock, version, unique constraint), or a distributed lock with a TTL and fencing tokens. Alternatively route all requests for one show to one pod (partition by show id), so the in-memory lock is valid again for that partition.

How to answer

Shows you understand the scope of a lock. Partitioning by key is a senior answer.

Likely follow-ups
  • Redis lock expires while the holder is paused by GC. (Fencing token checked by the storage layer.)
