Holds with a TTL: when the user needs minutes

Real booking flows have a long gap between "I pick seats" and "payment succeeded": 30 seconds to 10 minutes. You cannot hold a Java lock or a database row lock for minutes. Instead you store a hold (a soft reservation) with an expiry time. The seat moves through states, and the lock is only held for the few microseconds each state change takes.

Rules that make holds correct:

  1. Hold is atomic. "All requested seats are FREE (or their hold expired) then mark them HELD by me until now + TTL" happens in one critical section or one conditional update.
  2. Expiry is checked, not trusted. Do not rely on a background job to free seats on time. Every read treats HELD with expiresAt <= now as FREE (lazy expiry). The cleaner job is only for tidiness and for releasing inventory in reports.
  3. Someone must delete expired holds. Lazy expiry frees the seat, but the hold record stays in memory (or in the table) until something removes it, so every abandoned checkout leaks one entry. Our HoldService drops expired holds for the seats it touches in hold() and confirm(), and exposes sweep() for a ScheduledExecutorService to call every minute; in a database the same job is DELETE FROM holds WHERE expires_at < now(). The last line of the Java run shows five abandoned holds swept.
  4. Confirm re-checks ownership and expiry. Payment can succeed after the hold expired and someone else grabbed the seat. Confirm must say "REJECTED, refund", never overwrite the new holder. The code run shows exactly this at t = 302 s.
  5. Inject the clock. A Clock or LongSupplier parameter lets tests jump time forward without sleeping. Interviewers notice this.
  6. Make confirm idempotent. The payment callback may arrive twice. Use the hold id (or a payment id) as an idempotency key, so the second call returns the same result.
