In the database: row locks, conditional updates, unique constraints

An in-memory lock only protects one process. The moment you run two app servers behind a load balancer, two JVMs have two separate lock maps, and the race is back. In a real system the database row is the shared thing, so the database must make check + act atomic. Four tools, from most to least common:

1. Conditional update (atomic check-and-act in one statement)

UPDATE show_seat
   SET status = 'HELD', user_id = :user, hold_until = now() + interval '5 minutes'
 WHERE show_id = :show AND seat_id = :seat
   AND (status = 'FREE' OR (status = 'HELD' AND hold_until < now()));
-- 1 row changed: you got it.  0 rows: someone else did. No read-then-write gap.

2. Optimistic version column

-- read
SELECT status, version FROM show_seat WHERE show_id = :show AND seat_id = :seat;   -- FREE, 41
-- write only if unchanged
UPDATE show_seat SET status = 'BOOKED', user_id = :user, version = version + 1
 WHERE show_id = :show AND seat_id = :seat AND version = 41;
-- 0 rows -> conflict -> re-read and decide

ORMs do this for you: a JPA entity with a @Version field adds the version check to every update and throws OptimisticLockException on conflict.

3. Pessimistic row lock: SELECT ... FOR UPDATE

BEGIN;
SELECT seat_id, status FROM show_seat
 WHERE show_id = :show AND seat_id IN ('A1','A2','A3')
 ORDER BY seat_id                -- consistent order: avoids deadlocks between transactions
 FOR UPDATE NOWAIT;              -- or SKIP LOCKED to grab any free ones, or plain FOR UPDATE to wait
-- application checks all three are FREE
UPDATE show_seat SET status = 'HELD', user_id = :user, hold_until = now() + interval '5 minutes'
 WHERE show_id = :show AND seat_id IN ('A1','A2','A3');
COMMIT;                          -- row locks are released here
  • FOR UPDATE locks the selected rows until the transaction ends; other FOR UPDATEs and writes on those rows wait. Plain reads still proceed (MVCC).
  • NOWAIT fails immediately instead of waiting; SKIP LOCKED silently skips rows someone else locked, which is perfect for "give me any 2 free seats in row F" or job queues. Both exist in PostgreSQL and MySQL 8.
  • Keep the transaction short: never call the payment gateway while holding the row lock. Hold the seat (commit), pay, then confirm in a second short transaction.

4. Unique constraint: the safety net

A UNIQUE (show_id, seat_id) on the bookings table means that even if all your application logic is wrong, the database refuses the second row. Use it in addition to one of the above, not instead of them, because the error arrives late (after payment, if you are careless).
