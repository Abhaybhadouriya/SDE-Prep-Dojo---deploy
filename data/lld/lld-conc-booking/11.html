Quiz

You replaced HashMap with ConcurrentHashMap but kept if (!m.containsKey(s)) m.put(s, u);. Is double booking fixed?

  1. Yes, ConcurrentHashMap is thread-safe
  2. No, the check and the put are still two separate steps
  3. Yes, but only on Java 21
  4. No, ConcurrentHashMap does not allow puts
Use putIfAbsent (returns null only for the winner) or a lock around both steps.

An UPDATE ... WHERE id = 7 AND version = 41 reports 0 rows changed. What does it mean?

  1. The database is down
  2. The seat does not exist
  3. Someone else updated the row first; re-read and decide
  4. The update will be applied later
That is the optimistic conflict signal. Re-read, re-check the business rule, then retry or report "taken".

A family books seats A3, A1, A2 with per-seat locks. How do you avoid deadlock with another multi-seat booking?

  1. Sort the seat ids and lock in that order
  2. Lock in the order the user clicked
  3. Use more threads
  4. Lock only the first seat
A global order removes circular wait. Alternatively, one lock per show.

Payment for a hold succeeds 20 seconds after the hold expired, and another user now holds the seat. What should confirm do?

  1. Overwrite the new holder, the first user paid
  2. Throw and crash
  3. Wait for the new hold to expire
  4. Reject the confirmation and refund the payment
Confirm must re-check ownership and expiry; the seat is no longer yours.

50,000 users race for 100 flash-sale items. Which is the worst fit?

  1. A queue in front of a single-writer allocator
  2. Optimistic CAS with unlimited retries
  3. A guarded atomic decrement WHERE stock > 0
  4. Pre-splitting stock into buckets
Under heavy contention almost every optimistic attempt conflicts, so retries dominate the work.

Why keep a version number if the CAS already compares the whole seat state?

  1. It makes the object smaller
  2. Java requires it
  3. To catch ABA: the state went FREE, BOOKED, FREE and looks unchanged
  4. To sort seats
A monotonically increasing version makes every change visible, even one that returns to an old value.

Your booking service runs on 10 pods with an in-memory lock per seat. What is true?

  1. Two pods can book the same seat; move the atomic step to the database or partition shows by pod
  2. It is safe because each pod has a lock
  3. Locks are shared automatically by the JVM
  4. Only reads are unsafe
A lock only protects the memory of its own process.
