Optimistic: versions and compare-and-set

Optimistic locking never holds a lock while deciding. Each seat carries a version number. You read the seat and its version, check it is free, and then write with a condition: "only if the version is still the one I read". If someone else wrote first, the version moved, your write fails, and you re-read. In memory the condition is an atomic compare-and-set (CAS); in a database it is UPDATE ... WHERE version = ?.

  1. Both users read the seat at the same time. Both see FREE at version 0. No lock is taken, so reads never wait.
  2. Riya commits first with a conditional write: "set owner = Riya and version = 1, only if the version is still 0". It is, so her write wins atomically.
  3. Kabir sends the same conditional write based on version 0. The current version is 1, so it changes nothing. In SQL the update reports 0 rows; in Java replace(key, old, new) returns false.
  4. Kabir re-reads, sees the seat is now Riya's, and the business check fails. He gets a fast, honest answer. No one waited on a lock, and no double booking happened.

In Java the cleanest in-memory version uses an immutable state object and ConcurrentHashMap.replace(key, expected, next), which succeeds only if the current value equals expected:

record SeatState(long version, String owner) {}

boolean book(String id, String user) {
    while (true) {
        SeatState cur = seats.get(id);                       // 1. read
        if (cur.owner() != null) return false;               // 2. business check
        SeatState next = new SeatState(cur.version() + 1, user);
        if (seats.replace(id, cur, next)) return true;       // 3. CAS: only if unchanged
        // 4. lost the race: loop, re-read, re-check
    }
}
  • Why the version, if we already compare the whole state? Because of ABA: a seat goes FREE to BOOKED (Riya) to FREE (Riya cancels). A client holding the very first FREE snapshot would see "FREE, same as before" and win, although the world changed twice. A version that only ever goes up makes every change visible. The C++ tab demonstrates exactly this.
  • Retry policy. On conflict, re-read and re-run the business check; do not blindly retry the write. Cap the retries. For a seat, one re-read usually ends in "taken"; for a counter (stock 10 to 9) a few retries are normal.
  • When optimistic is wrong. Under heavy contention (a flash sale where 50,000 users want 100 items) most CAS attempts fail and retry, burning CPU and database round trips. Then a queue, a pessimistic lock, or an atomic decrement in one statement is better.

From your world

This is the seqlock and cmpxchg mindset: readers never block, writers detect interference with a sequence number and retry. ABA is the same bug you avoid in lock-free lists by pairing the pointer with a generation counter (tagged pointers). Optimistic database locking is a seqcount stored in a row.
