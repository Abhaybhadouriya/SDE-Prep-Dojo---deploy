Pessimistic, in memory: lock the seat, not the theatre

The simplest correct answer is one lock around the whole booking method (synchronized on the service). It is correct, but every booking for every show in the city now waits in one line. Interviewers will immediately ask "how does this scale?". The better answer is one lock per resource: bookings for different seats never wait for each other.

private final ConcurrentHashMap<String, ReentrantLock> locks = new ConcurrentHashMap<>();

boolean book(String seatId, String user) {
    ReentrantLock lock = locks.computeIfAbsent(seatId, k -> new ReentrantLock()); // atomic: one lock per seat
    lock.lock();
    try {
        if (owner.containsKey(seatId)) return false;   // check ...
        owner.put(seatId, user);                       // ... and act, under the SAME lock
        return true;
    } finally {
        lock.unlock();
    }
}

computeIfAbsent matters: a plain get-then-put to create the lock is itself a check-then-act race, and two threads could end up with two different lock objects for the same seat.

Lock striping: a fixed number of locks

A lock per seat grows without bound (millions of seat-shows). Lock striping uses a fixed array of N locks and maps each seat to stripe = hash(seatId) mod N. Two seats may share a stripe and occasionally wait for each other, but memory is fixed and contention is still spread out. This is how the original ConcurrentHashMap (Java 5 to 7) used 16 segments, and how Striped in Guava works.

Booking several seats at once (and not deadlocking)

A family books A3, A1 and A2 together. You must take three locks, and if another request takes A2 then A1, you have the ABBA deadlock from the deadlock lesson. The rule: sort the seat ids, lock in that order, check all, write all, unlock in reverse. All or nothing: if any seat is taken, book none of them. With striping, sort the distinct stripe indexes instead.

List<String> sorted = new ArrayList<>(seatIds);
Collections.sort(sorted);                       // global lock order = seat id
List<ReentrantLock> held = new ArrayList<>();
try {
    for (String s : sorted) { ReentrantLock l = lockFor(s); l.lock(); held.add(l); }
    for (String s : sorted) if (owner.containsKey(s)) return false;   // any taken -> book none
    for (String s : sorted) owner.put(s, user);
    return true;
} finally {
    for (int i = held.size() - 1; i >= 0; i--) held.get(i).unlock();
}

Granularity is the interview conversation. Too coarse (one lock per theatre or per restaurant): simple, safe, slow. Too fine (one lock per seat, plus nesting): fast, but you now own lock ordering and memory growth. A common sweet spot is one lock per show: all seats of one screening share a lock, different shows run in parallel, and multi-seat bookings take only one lock, so deadlock is impossible. Say the options and pick one with a reason.
