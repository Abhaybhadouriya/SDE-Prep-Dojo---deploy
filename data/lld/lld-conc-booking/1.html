The bug: check-then-act

Almost every first draft of bookSeat looks like this:

boolean book(String seatId, String user) {
    if (seats.get(seatId).isFree()) {      // 1. CHECK
        seats.get(seatId).assign(user);    // 2. ACT
        return true;
    }
    return false;
}

Each line is fine on its own. The bug is the gap between them. Two threads can both pass the check before either one acts. This pattern has a name, check-then-act, and it is a race condition: the result depends on the timing of threads you do not control (the basics are in Thread Safety Basics).

Notice two traps people fall into when they "fix" it:

  • Making the map thread-safe is not enough. A ConcurrentHashMap makes each get and put safe, but the check and the act are still two separate calls. The fix must make check + act one atomic step.
  • Locking only the write is too late. Wrapping just assign() in synchronized means both threads still passed the check; they just write one after the other.

Every correct answer on this page is a way to make "is it free? then take it" indivisible. They differ in where that happens (one JVM or the database), how long the seat is reserved (milliseconds, or minutes while the user pays) and what losers experience (waiting, or a fast "sorry, taken").
