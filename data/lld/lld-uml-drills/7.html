Drill 4: Chat application (direct and group)

Prompt (10 min). Users can send messages to one other user or to a group. Groups have admins who add and remove members. Each message shows sent, delivered and read state per recipient. Users can see their conversations sorted by latest message, and fetch older messages page by page. Online users get messages pushed; offline users get them on reconnect.

Model answer: chat application

Clarify. Actors: User, Group admin (a role of User), Delivery channel. Use cases: send, receive, mark read, create group, add/remove member, list conversations, load history. Out of scope: media uploads, end-to-end encryption. Assume text only and in-memory storage.

Sort. Entities: User, Conversation, Message, Membership (user + role + lastReadMessageId). Values: MessageId, Timestamp. Enums: Role (MEMBER, ADMIN), ConversationType (DIRECT, GROUP), DeliveryState. Instance trap avoided: do not create separate DirectChat and GroupChat hierarchies with duplicated message logic: a direct chat is a conversation with exactly two members and no admins. Use the type enum for the few rules that differ. Hidden split: Message (the content, stored once) vs per-recipient receipt state (Membership's last-read pointer, or a Receipt per recipient).

API. Message send(UserId from, ConversationId c, String text) fails if the sender is not a member; void addMember(UserId admin, ConversationId c, UserId u) fails if the caller is not an admin or the chat is DIRECT; List<Message> history(c, beforeId, limit) pages backwards.

Patterns. Delivery is Observer-shaped: online sessions subscribe to conversations, the DeliveryChannel pushes; offline users pull from their last-read pointer on reconnect. Message ordering within a conversation comes from one sequence counter per conversation.

From your world

The per-member last-read pointer is a ring-buffer consumer index: one shared log of messages, and each reader keeps its own tail. That is also exactly how a Kafka consumer offset works.
