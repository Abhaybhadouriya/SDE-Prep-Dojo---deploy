Drill 1: Coffee shop ordering

Prompt (10 min). A coffee chain wants an ordering system for its counters. Customers order one or more drinks. Each drink has a base (espresso, latte, tea) in a size (small, medium, large) and can have any number of add-ons (extra shot, oat milk, syrup), each with a price. The menu and prices change often. An order is placed, paid, prepared by a barista and handed over. Customers get loyalty points: 1 point per 10 rupees. Show the class diagram and the main API.

Model answer: coffee shop

Clarify. Actors: Customer, Cashier, Barista. Use cases: browse menu, place order, pay, prepare, hand over, earn points. Out of scope: inventory of beans and milk. Assume prices are fixed at order time even if the menu changes later.

Sort. Entities: Order, Customer (loyalty account). Catalogue values: MenuItem (base drink + price per size), AddOn. Line data: OrderLine (one drink with chosen size and add-ons). Value objects: Money. Enums: Size, OrderStatus (PLACED, PAID, PREPARING, READY, HANDED_OVER). Hidden split: MenuItem (what the menu offers, price can change) vs OrderLine (what this customer bought, price frozen).

API. Order place(CustomerId c, List<LineRequest> lines) (fails: unknown item, add-on not allowed for that base), Receipt pay(OrderId o, PaymentRef p) (idempotent per order), void advance(OrderId o) (fails if the transition is illegal: you cannot hand over an unpaid order).

Traps. (1) A class per drink (Latte extends Coffee) when drinks differ only in name and price: they are catalogue data. (2) Decorator for add-ons: the classic textbook answer, and fine to mention (see Decorator), but a list of AddOn values with prices is simpler when add-ons only change the price; reach for Decorator when each wrapper adds behaviour. Say both and pick. (3) Status as free-form strings instead of an enum with allowed transitions.

Likely follow-ups
  • Add combos ("croissant + latte = 20 off").
  • Two baristas grab the same order.
