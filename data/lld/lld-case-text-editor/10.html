Concurrency and thread safety

A desktop editor has one keyboard, but its process still has several threads: the UI thread, autosave, a spell checker or language server reading the text, and maybe a plugin that edits. Rules:

  1. One lock around the editor Every public method is synchronized (Python: one lock; C++: a mutex in the -DED_THREADS build, compiled and run with real threads on Linux, WSL Ubuntu g++ 13, with the same output: run-cpp-linux.txt). See locks; one writer at a time is the rule, and read-write locks only pay off if rendering threads read far more often than the keyboard writes. An edit, its history push and the cursor update happen together, so a reader never sees new text with an old cursor. The Python test runs 4 threads typing 200 times each and checks that nothing is lost and everything undoes.
  2. Readers take a snapshot Autosave and the spell checker should not hold the lock while they work. They copy the text (or, with a rope or piece table, grab an immutable root, which is O(1)) and release the lock at once.
  3. Background edits go through the same door A formatter that rewrites the file must submit a Command, so its change lands in the history and can be undone like a keystroke. Do not let it write to the buffer directly.
  4. Single-thread model Most real editors run all edits on the UI thread and post work from other threads to it, like an event loop. Say that this removes locks from the core entirely.
  5. Many users Two people editing one document is not a lock problem: their positions shift under each other. That needs Operational Transformation (transform an incoming insert at 10 by a local insert at 5 to become an insert at 11) or a CRDT. Name both, say it is HLD, and stop.

From your world

Readers that grab an immutable root while a writer builds a new version is RCU: rcu_dereference() the current tree, read it without locks, and the writer publishes a new root with rcu_assign_pointer(). Persistent ropes give editors exactly this property.
