Interview follow-ups

How do you implement undo and redo?

Each edit is a Command object with execute and undo; insert stores (position, text), delete stores (position, removed text). The editor keeps two stacks. A new edit executes, is pushed on undo, and clears redo. Undo pops, calls undo(), restores the cursor saved with the entry, and pushes to redo. Redo pops from redo, calls execute() and pushes back to undo. Each step is O(size of that edit).

How to answer

Draw the two stacks and walk through "type a, type b, undo, redo, type c" saying what each stack holds.

Make every operation O(1): left, right, insert, backspace, undo.

Use two stacks of characters, left of cursor and right of cursor (equivalently, a gap buffer). Insert pushes on the left stack; backspace pops it; left moves one char from the left stack to the right one; right does the reverse. Undo pops a command, and each command is a single character insert or delete, so it is O(1) too. A move is not an edit, so undo restores the cursor by moving it back, which costs the distance moved since; if moves are frequent, store the cursor in the entry and move the gap lazily on the next edit.

Up and down keys: what goes wrong and how do you fix it?

Lines have different lengths. Naively keeping the column breaks on a short line (you clamp to its end and then lose the original column). Keep a goal column: set it on the first vertical move, aim for it on each later one, clamp to the target line's length, and reset it on any horizontal move or edit. Finding line starts is a scan to the previous newline in our buffer; with a line-start index (sorted offsets, or counts in rope nodes) it is O(log n).

Which data structure for the text? What about a 1 GB file?

For normal files a gap buffer: O(1) amortised typing at the cursor, O(distance) to jump. For huge files or many cursors a rope (balanced tree of chunks, O(log n) insert and index) or a piece table (read-only original plus append-only add buffer, with a tree of pieces). The piece table never copies the original file, so opening a 1 GB log is a memory map, and undo can be as cheap as restoring a piece list. VS Code moved from an array of lines to a piece tree for exactly this reason.

Command or Memento for undo?

Command stores the change and its inverse: memory grows with what you typed, not with the document size. Memento stores the state: always correct but costs a full copy per step. For text use commands, and use a memento for occasional checkpoints such as "revert to saved". For small states (a game board) memento is simpler and fine.

Undo removes one letter at a time. Users hate it. Fix it.

Coalesce: when a single typed character lands right after the previous insert, and no move, undo or other edit came in between, append it to that command instead of pushing a new one. Break the group at a word boundary (after a space or newline), on any cursor move, and optionally after a pause of about a second. Our InsertCommand.absorb implements the first three rules.

How does replace-all undo in one step, and why apply right to left?

Find all matches in the current text first, then build a MacroCommand of (delete, insert) pairs. Applying from the last match to the first keeps earlier offsets valid, because an edit only shifts text after it. Finding first also avoids an infinite loop when the replacement contains the search string. Undo of the macro undoes the parts in reverse order, giving back the original exactly.

Some commands run on a server. How does undo work then?

Keep the same Command interface, but execute and undo may be asynchronous calls. A history entry gets a status: pending, applied, failed. The UI applies local commands at once and remote ones optimistically, then rolls back on failure. Undo of a remote command sends its inverse request (or a compensating action when the server cannot invert, like a refund for a payment). Commands must be idempotent or carry an id so retries do not apply twice.

Where does Flyweight fit in a text editor?

Rendering. A document of a million characters would otherwise need a million glyph objects with font data. A factory hands out one shared Glyph per (character, font, style): that is the intrinsic state. The position (row, column, x, y) is extrinsic, computed from where the character is in the document while drawing. Our demo draws 1,200 characters with 8 glyph objects.

Two users edit the same document at once (Google Docs). What changes?

Positions stop being stable: my insert at 10 and your delete at 5 arrive in different orders on different machines. Operational Transformation rewrites each incoming operation against the operations it did not see (my insert at 10 becomes an insert at 9 after your delete at 5), coordinated by a server. CRDTs give each character a unique, ordered id so inserts commute without a central server. Undo becomes per-user: undo my last operation, transformed against everyone else's since. This is HLD; in an LLD round name it and keep the local design clean.
