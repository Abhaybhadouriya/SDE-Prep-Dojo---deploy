The story: the notebook with a pencil and an eraser log

Explain like I'm 5

You write in a notebook. Every time you write or erase something, your friend writes one line in a little log book: "wrote hello on line 1" or "erased the letter b from line 2". When you say "oops, undo", your friend reads the last line of the log and does the opposite: erases hello, or writes the b back. He moves that log line to a second pile. If you say "redo", he takes it from the second pile and does it again. If you write something new, he throws the second pile away, because that future no longer exists.

Your friend never photocopies the whole notebook. He only remembers the small change. That is the whole trick of undo: store the change, not the world.

The interview tests three things. First, the buffer: how text is stored so that typing in the middle of a big file is not O(n) per key. Second, undo/redo: edits as objects (the Command pattern) on two stacks, with the cursor restored too, and with sensible grouping so one undo removes a word, not a letter. Third, growth: replace, copy-paste, multi-cursor, styling and collaboration, added without rewriting the core.

From your world

An edit command is a struct work_struct with a second function pointer: struct edit_ops { size_t (*execute)(struct doc *, void *arg); void (*undo)(struct doc *, void *arg); }; plus the argument it captured. The undo stack is a journal, like jbd2 in ext4: record enough to reverse the change, and replay records in reverse to roll back. The gap buffer is skb_reserve() applied to text: keep free space exactly where the next write will land, so skb_push()-style inserts are O(1) and nothing else moves.

Interfaces in C terms: every interface on this page is, in C, a struct of function pointers; each implementation fills one in, like file_operations. Java and C++ build that table (the vtable) for you, and every object carries a pointer to it. More in OOP from C structs and polymorphism and vtables.
