Choosing the text buffer

Before classes, decide how characters are stored. A plain String or array makes every insert in the middle O(n), because everything after the cursor shifts. Four standard answers:

StructureIdeaInsert at cursorJump far awayUsed by
Array / StringOne contiguous blockO(n)O(1)Fine for a few KB; the naive answer
Gap bufferArray with a hole at the cursor; typing fills the holeO(1) amortisedO(distance) to move the gapGNU Emacs
RopeBalanced binary tree; leaves hold short strings; nodes store left lengthO(log n)O(log n)Many modern editors and string libraries for huge texts
Piece tableOriginal file (read-only) + append-only "add" buffer + a list of pieces pointing into themO(pieces), O(log n) as a treeO(log n) as a treeEarly word processors; VS Code's piece tree
List of linesOne string per lineO(line length)O(1) by line numberSimple editors; TextPad answers
  1. The text is "hi!\n" with the cursor after "hi". The free space sits exactly at the cursor.
  2. Typing writes into the gap and moves its start. That is why typing is O(1): a run of keystrokes at one place never shifts other characters.
  3. Moving the cursor far away moves the gap, copying the characters in between. Editing in one area and then jumping is O(distance), paid once.
  4. When the gap is used up, grow the array by doubling (our ensureGap), so the cost is amortised O(1) per character.

We pick the gap buffer: it is 60 lines of code, it is what the Google "all O(1)" follow-up is really asking for (two stacks around the cursor are the same idea), and it keeps undo simple because every edit is "insert at position" or "delete at position". Say that a rope or a piece tree is the answer for gigabyte files and many cursors, and that the editor talks to the buffer through insert(pos, s) and delete(pos, n) only, so the buffer can be swapped (the Strategy idea behind an interface).

From your world

A rope is a scatter-gather list kept balanced: like an skb with frags[] or an iovec array, the text is many small buffers, and a "length of the left subtree" in each node lets you find byte k in O(log n). A piece table is copy-on-write: the original file is mapped read-only (like a file-backed page), every new character goes to an append-only buffer, and the document is a list of (buffer, offset, length) descriptors, just like extents in a filesystem.
