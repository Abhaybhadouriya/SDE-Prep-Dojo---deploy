Extensibility: the follow-ups interviewers ask

Follow-upHow it plugs in
New policy (MRU, random, LIFO)A new EvictionPolicy class; zero changes to Cache. The demo's FifoPolicy is 7 lines.
Expire after last access (PhonePe)In get, on a hit, also set expiresAt = now + ttl. Make it a ExpiryPolicy strategy (after write / after access / fixed time) if both are needed.
Background expiryA ScheduledExecutorService calls purgeExpired() every few seconds. For huge caches, use a timer wheel or a min-heap of expiry times instead of a full scan.
Write-aroundWrites go to the store only and invalidate the cache entry; useful when written data is rarely read back. A third WritePolicy value.
Refresh-ahead / async loadWhen an entry is near expiry and is read, return the old value and reload it in the background. Load with a CompletableFuture so callers can choose to wait or not.
Capacity by bytesA Weigher function per entry; evict until totalWeight <= maxWeight.
Multi-level (Flipkart)Already there: new Cache(l1Cap, lru, new Cache(l2Cap, lfu, db, ...), ...). Discuss promotion (copy to L1 on an L2 hit) and invalidation (remove goes down the chain).
Eviction listener and metricsObserver: onEvict(key, value, cause); hit ratio = hits / (hits + misses).
Better hit ratio than LRULRU is fooled by one big scan; LFU keeps stale popular keys forever. Mention 2Q, ARC and W-TinyLFU (Caffeine's policy) as the next step, each still behind the same interface.
