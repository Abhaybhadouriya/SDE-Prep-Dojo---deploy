Interview follow-ups

Why a doubly linked list and not a singly linked one or an array?

To unlink a node from the middle in O(1) you need its predecessor. With a singly linked list you must walk to find it (O(n)). An array needs shifting. The hash map gives you the node; the prev pointer lets you cut it out with two writes and push it to the front with four.

How to answer

State the two operations that must be O(1) (move to front, remove tail), then show why prev is needed.

Likely follow-ups
  • Why the sentinel nodes?
  • What does the map store: node or value?
Make the eviction policy pluggable. What does the interface look like?

Four hooks: onPut, onAccess, onRemove, evict. The cache calls them at the right moments and keeps values in its own map; the policy keeps only key order. LRU, LFU and FIFO are then separate classes chosen at construction. A single evict() method is not enough because LRU needs to see accesses and LFU needs to see removals.

How to answer

Show the interface, then show FIFO in five lines to prove it is cheap to add one.

Likely follow-ups
  • Can the policy be changed at runtime? (Only by rebuilding its state from current keys.)
Implement LFU in O(1). How do you track the minimum frequency?

Map key to frequency; map frequency to an insertion-ordered set of keys; an integer minFreq. On access, move the key from bucket f to f+1; if bucket f became empty and f was minFreq, minFreq becomes f+1. On insert, minFreq is 1. Evict the first (oldest) key in bucket minFreq. Every step is a hash operation, so O(1).

How to answer

Draw the buckets, then walk one access and one eviction.

Likely follow-ups
  • What breaks minFreq? (An explicit remove; repair lazily at the next eviction.)
  • LFU's weakness? (Old popular keys never leave: add ageing or use W-TinyLFU.)
Make your LRU cache thread safe. Why not a ReadWriteLock?

Because a get moves the node to the front, it modifies the list; a read lock would let two "readers" corrupt the pointers. Use one exclusive lock around each operation. To scale, stripe the cache into segments with a lock each (approximate global LRU), or record accesses in a buffer and apply them in batches, as Caffeine does. A ConcurrentHashMap alone does not help: the list is the shared mutable state.

How to answer

Name the hidden write, give the simple lock, then the two scaling options with their trade-offs.

Likely follow-ups
  • What is the cost of synchronized on every get under 32 threads?
  • How do you test it?
On a miss you load from the database. A hot key expires and 500 requests miss at once. What happens?

Without protection all 500 hit the database (a cache stampede, or thundering herd). Fixes: coalesce loads with a per-key future so one thread loads and the rest wait; refresh-ahead so hot keys are reloaded before they expire; add small random jitter to TTLs so many keys do not expire together. Never hold the global cache lock during the load.

How to answer

Name it, then three fixes from simplest to best.

Likely follow-ups
  • What if the load fails? (Do not cache the failure for long; negative caching with a short TTL.)
Write-through vs write-back: when would you pick each?

Write-through updates the store on every put: simple, the store is never stale, but writes are as slow as the store. Write-back marks entries dirty and writes them on eviction or flush: fast writes and fewer store calls for keys updated often, but a crash loses unflushed data and other readers of the store see old values. Use write-through for money and anything others read directly; write-back for counters, sessions and high-write data you can rebuild.

How to answer

One line each, then the failure mode of write-back.

Likely follow-ups
  • Where else have you seen write-back? (The OS page cache and disk controllers.)
How do you implement TTL, and how do you test it without sleeping?

Store expiresAt on each entry. Expire lazily on get (cheap, but dead entries take space until read) and actively with a periodic sweep or a min-heap / timer wheel of expiry times. Inject a Clock; tests use a manual clock and call advance(999), then advance(1), so the boundary is tested exactly and the test takes no time.

How to answer

Lazy plus active expiry; the injected clock is the part that impresses.

Likely follow-ups
  • Should expired entries be evicted before the LRU victim?
Design a two-level cache for a movie catalogue.

L1: small, in-process, LRU, short TTL; L2: larger (in-process LFU, or a shared Redis), longer TTL; then the database. Because our Cache implements the store interface, L1's store is L2 and L2's store is the database. On an L2 hit, promote to L1. Writes go through both levels (or invalidate L1 and write L2). Discuss consistency: another server's L1 may keep a stale value until its TTL, so keep L1 TTL short or broadcast invalidations.

How to answer

Levels, read path, write path, staleness.

Likely follow-ups
  • How do you measure whether L1 is worth it?
Design a "recently watched" list for Prime Video.

It is an LRU per user with capacity N (say 20): watching a video is an access (move to front, insert if new, evict the oldest if full), and "get recent" walks the list from the front. Map plus doubly linked list per user; the list order is the answer. Persist per user in a key-value store if it must survive restarts.

How to answer

Recognise LRU, then add the "list from front" read.

Likely follow-ups
  • Remove a video from history?
  • Sync across devices?
LRU performs badly when a batch job scans every key once. Why, and what would you use?

A one-time scan touches each key once, so each becomes "most recent" and pushes out the genuinely hot keys: cache pollution. Fixes: 2Q or segmented LRU (new keys enter a probation queue and need a second hit to reach the main queue); ARC (balances recency and frequency adaptively); W-TinyLFU (a frequency sketch decides whether a newcomer deserves to evict a resident), which Caffeine uses. The kernel's active/inactive lists are the same idea as 2Q.

How to answer

Explain pollution, then name one scan-resistant policy and how it fits behind your interface.

Likely follow-ups
  • How would you compare policies? (Replay a real access trace and measure hit ratio.)
