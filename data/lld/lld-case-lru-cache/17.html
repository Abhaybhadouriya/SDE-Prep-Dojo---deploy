LRU capacity 3: put a, put b, put c, get a, put d. Which key is evicted?

  1. a
  2. b
  3. c
  4. d
After get a the order (most recent first) is a, c, b. b is least recently used.

LFU capacity 3: put a, b, c; get a, get a, get b; put d. Which key is evicted?

  1. a
  2. b
  3. c
  4. d
Frequencies are a=3, b=2, c=1. c has the lowest frequency.

Why is a ReadWriteLock with get() under the read lock wrong for LRU?

  1. get moves the node in the list, so it is a write
  2. Read locks are slower than exclusive locks
  3. ReadWriteLock is not reentrant
  4. It is fine
Two concurrent gets would both relink pointers. Access order is shared mutable state.

In write-back mode, a dirty entry is chosen as the eviction victim. What must happen?

  1. Drop it; the store will catch up
  2. Mark it clean and keep it
  3. Evict a different key
  4. Save it to the store before removing it
Otherwise the write is lost forever.

What is the best way to test a 1-second TTL?

  1. Thread.sleep(1001) in the test
  2. Inject a Clock and advance a manual clock
  3. Set TTL to 0
  4. Run the test many times
A manual clock tests the exact boundary instantly and never flakes.

A hot key expires and hundreds of threads miss at once. Which fix stops them all hitting the database?

  1. A bigger capacity
  2. Switching from LRU to LFU
  3. Coalescing loads with a per-key future so one thread loads
  4. Holding the cache lock during the load
Holding the global lock would also serialise everything else. A per-key in-flight future lets one thread load while the others wait for that key only.
