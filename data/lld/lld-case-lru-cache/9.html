Concurrency and thread safety

The surprise: get is a write. Every hit moves a node in the LRU list (or a key between LFU buckets). So a reader-writer lock buys nothing; two "readers" would both relink pointers and corrupt the list. Our cache uses one ReentrantLock around every operation, which is correct and simple.

  1. A hit is not a read: get(a) unlinks node a to move it to the front. At the same moment put(d) finds the cache full and evicts the tail, which is a. Two threads rewrite the same prev/next pointers: the list breaks and the size is wrong.
  2. The guard: one ReentrantLock around every operation, get included. A read-write lock would not help, because every "read" writes the list. A finishes moving a to the front.
  3. B takes the lock next. Now the tail is b, so b is evicted and d goes in. The list is d, a, c and the size is still 3.
  1. One lock (our code) Correct, easy to explain. Throughput is limited to one operation at a time, but each operation is a few hundred nanoseconds of pointer work, so this goes surprisingly far.
  2. Never do I/O under the lock Our get releases the lock before store.load and re-checks after. The cost: two threads that miss on the same key both load it (a cache stampede).
  3. Coalesce loads Keep ConcurrentHashMap<K, CompletableFuture<V>> inFlight; the first thread creates the future and loads, the others wait on it. This is what computeIfAbsent-style loaders in Caffeine and Guava give you.
  4. Lock striping Split the cache into N segments by hash(key) % N, each with its own lock, map and policy. Throughput scales with N; the price is that LRU becomes per-segment, an approximation of global LRU. Older Guava caches and ConcurrentHashMap in Java 7 used segments.
  5. Record accesses lazily Production caches avoid touching the list on every hit: Caffeine buffers access events and replays them under a lock in batches; Redis does not keep a full LRU list at all and samples a few keys to evict the oldest (approximated LRU and LFU, see the Redis eviction docs in resources).

From your world

The kernel faces the same problem on every page access, which is why it does not move a page on the LRU list on each touch. It sets an accessed bit (in hardware, in the page table entry) and lets reclaim look at the bits later. Caffeine's buffered access log and Redis sampling are the user-space versions of the same idea: make the hot path cheap, and do the ordering work in batches.

More on the locking options: read-write locks (and why they do not help here), concurrent collections, and the worked thread-safe LRU drill.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • ReentrantLock = pthread_mutex_t of the recursive kind (the owning thread may lock it again), with tryLock like mutex_trylock.
  • AtomicLong, AtomicReference, compareAndSet = atomic64_t and atomic64_cmpxchg(): one compare-and-swap instruction, no lock.
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • ExecutorService = a thread pool with a work queue, like a kernel workqueue.
  • Python threading.Lock = a plain mutex; with lock: is lock and unlock on every exit path.
