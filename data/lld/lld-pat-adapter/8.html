When to use it, when not to

Use it when
  • You must use a class whose interface does not match, and you cannot or should not change it: third-party SDKs, generated clients, legacy code, C libraries.
  • You want several providers interchangeable behind one interface (payments, SMS, email, maps, storage).
  • You want to keep vendor types out of your domain and out of your tests (fake the Target, not the SDK).
  • You are migrating: the old API is adapted to the new interface so callers can move one at a time.
Avoid it, or watch out, when
  • You own both sides. Just change one of them; an adapter would be pure indirection.
  • The adapter starts making decisions (retries, routing, discounts). That is business logic hiding in a translation layer.
  • The two interfaces do not really mean the same thing (a sync API adapted to an async one, or "refund" mapped onto a provider that only supports "void"). An adapter cannot invent missing capability; surface it as an error.
  • Adapters stacked on adapters. Usually a sign that the Target interface itself is the wrong shape.

Design rule for the Target: write it in your domain language (charge, paise as long, your result enum), never as a copy of the first vendor's API. Otherwise vendor number two needs an adapter that pretends to be vendor number one.
