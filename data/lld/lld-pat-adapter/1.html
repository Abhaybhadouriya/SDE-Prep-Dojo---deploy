The problem: vendor types leaking everywhere

Without an adapter, the quick fix is to call the vendor SDK directly where you need it:

class CheckoutService {
    private final OldBankSdk bank = new OldBankSdk();
    private final AcmePayClient acme = new AcmePayClient();

    Receipt pay(Order o, String provider) {
        if (provider.equals("oldbank")) {
            int code = bank.makePayment(o.id(), o.paise() / 100.0);   // rupees, as a double
            if (code == 0) return Receipt.ok(bank.lastTxn());
            if (code == 51) return Receipt.declined("insufficient funds");
            return Receipt.error("code " + code);
        } else if (provider.equals("acme")) {
            Map<String, Object> req = new HashMap<>();
            req.put("amount_minor", o.paise());
            req.put("currency_code", o.currency());
            Map<String, String> resp = acme.createCharge(req);
            return "captured".equals(resp.get("state")) ? Receipt.ok(resp.get("id"))
                                                        : Receipt.declined(resp.get("reason"));
        }
        throw new IllegalArgumentException(provider);
    }
}

It works today. Now count the pains:

  • Vendor details everywhere. Bank error codes, rupees-as-double, map keys like "amount_minor" sit inside your business logic. The refund service and the subscription service will copy the same translation, slightly differently.
  • Every new provider edits this method. That breaks the Open/Closed Principle: tested code is reopened for each integration.
  • Untestable. You cannot unit-test checkout without the real SDK classes.
  • Vendor upgrades ripple. When AcmePay renames "state" to "status", you hunt through the codebase.

You cannot change the SDKs (somebody else owns them), and you do not want to change your clean interface. You need something in between.
