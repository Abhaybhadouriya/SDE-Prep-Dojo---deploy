Records and immutable value objects

A value object is an object defined only by its values: Money(15000 paise, "INR"), a Point(1, 2), a DateRange. Two of them with the same values are the same thing. They should be immutable: once built, they never change. To "change" one, you make a new one.

Why interviewers like immutability:

  • Thread safety for free. No writes after construction means no races. Share it across threads without a lock.
  • Safe as a map key. Its hash code can never change while it sits in a HashMap.
  • Invariants hold forever. Validate once in the constructor ("money is never negative"), and it stays true.
  • Easy to reason about. Passing it to another method cannot surprise you later.

Java records (Java 16+)

A record declares an immutable data carrier in one line. The compiler writes the private final fields, the constructor, the accessors, equals, hashCode and toString. A compact constructor is where you validate.

record Money(long paise, String currency) implements Comparable<Money> {
    Money {                                                   // compact constructor
        Objects.requireNonNull(currency, "currency");
        if (paise < 0) throw new IllegalArgumentException("negative money: " + paise);
    }
    static Money inr(long rupees) { return new Money(rupees * 100, "INR"); }
    Money plus(Money o) { same(o); return new Money(paise + o.paise, currency); }   // a NEW Money
    private void same(Money o) { if (!currency.equals(o.currency)) throw new IllegalArgumentException("currency mismatch"); }
    public int compareTo(Money o) { same(o); return Long.compare(paise, o.paise); }
}

Store money as an integer count of the smallest unit (paise, cents), never as double. 0.1 + 0.2 is not 0.3 in binary floating point. In a wallet or Splitwise problem this one choice prevents a whole class of bugs. Use BigDecimal if you need fractions of a paisa (tax, FX).

Hand-written immutable class: the five rules

  1. Make the class final (or the constructor private) so a subclass cannot add mutable state.
  2. All fields private final.
  3. No setters. Offer "withers" that return a new object: order.moveTo(PAID).
  4. Defensive copy in mutable inputs: this.items = List.copyOf(items).
  5. Never leak mutable internals out. Return unmodifiable views or copies.
static final class Order {
    private final String id;
    private final List<String> items;
    private final OrderStatus status;
    Order(String id, List<String> items, OrderStatus status) {
        this.id = id; this.items = List.copyOf(items); this.status = status;   // copy in
    }
    List<String> items() { return items; }                                     // already unmodifiable
    Order moveTo(OrderStatus to) {
        if (!status.canMoveTo(to)) throw new InvalidStateException(status, to);
        return new Order(id, items, to);                                       // new object, old one untouched
    }
}

From your world

RCU (read-copy-update) is immutability with a pointer swap: readers see a published struct that nobody modifies; a writer builds a new copy and swaps the pointer. An immutable Java object plus an AtomicReference or a volatile field is the same trick. And const struct file_operations is the kernel saying "this table never changes after init", which is why it can be shared by every open file without a lock.

A record is shallowly immutable. record Cart(List<String> items) still lets someone mutate the list you passed in. Copy it in the compact constructor: items = List.copyOf(items);.
