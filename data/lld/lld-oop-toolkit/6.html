equals and hashCode: the contract behind every HashMap

== on objects compares identity (same address). equals() compares meaning (same values). Object.equals defaults to identity, so for value objects you override it. The moment you do, you must also override hashCode(), because hash-based collections use hashCode() to choose the bucket before they ever call equals().

  1. add() calls hashCode(), masks it to a bucket index, and stores the entry there. Exactly like a kernel hlist_head table indexed by hash & (size - 1).
  2. If the class overrides equals() but not hashCode(), a new but equal object gets a different identity hash, lands in a different bucket, and the lookup fails before equals() runs.
  3. With hashCode() built from the same fields as equals(), equal objects always land in the same bucket.
  4. Inside the bucket, equals() settles it. Rule: equal objects must have equal hash codes (the reverse is not required).

The contract (from the java.lang.Object docs, in our words)

  • Reflexive, symmetric, transitive, consistent: a.equals(a); if a.equals(b) then b.equals(a); chains hold; repeated calls agree while nothing changes.
  • a.equals(null) is false, never an exception.
  • Equal objects must have equal hash codes. Unequal objects may collide; that only costs speed.
final class GoodPoint {
    final int x, y;
    GoodPoint(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) { return o instanceof GoodPoint p && p.x == x && p.y == y; }
    @Override public int hashCode() { return Objects.hash(x, y); }     // same fields as equals
}

Mutable key trap. Put an object in a HashSet, then change a field used by hashCode(). The object now sits in the wrong bucket: contains() says false and remove() silently does nothing. Keys must be immutable, which is one more reason to use records for ids, coordinates and money.

Entities vs value objects. A User or Order is an entity: it has an identity that survives changes (a user who changes their name is still the same user). Base its equals on the id only, or keep identity equality. A Money is a value: base equals on all fields. Saying "entity vs value object" in an interview shows you have modelled domains before.
