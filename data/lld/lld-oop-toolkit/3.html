Exceptions: a small, typed hierarchy

An exception is an object that a method throws to say "I cannot do what you asked". The call stack unwinds until some catch block handles it. Java has two families:

Checked (extends Exception)Unchecked (extends RuntimeException)
Compiler forces callers to handle?Yes (throws or catch)No
Typical meaningOutside world failed: file, network (IOException)Caller broke a rule: bad argument, wrong state, unknown id
In a machine-coding answerRareDefault for domain errors: keeps method signatures clean

The pattern that reads well in every round: one base exception for your domain, a handful of specific children, each carrying an error code.

class DomainException extends RuntimeException {
    private final String code;
    DomainException(String code, String msg) { super(msg); this.code = code; }
    String code() { return code; }
}
class NotFoundException extends DomainException {
    NotFoundException(String what, Object id) { super("NOT_FOUND", what + " " + id + " not found"); }
}
class InvalidStateException extends DomainException {
    InvalidStateException(OrderStatus from, OrderStatus to) { super("BAD_STATE", "cannot move " + from + " -> " + to); }
}

// driver: catch the base once, print a clean line, keep the demo running
try { order.moveTo(OrderStatus.DELIVERED); }
catch (DomainException e) { System.out.println("[" + e.code() + "] " + e.getMessage()); }

From your world

Kernel code returns -ENOENT, -EINVAL, -EBUSY, or wraps them in a pointer with ERR_PTR() and checks with IS_ERR(). Every caller must remember to check, and the goto out_free ladder does the cleanup. A Java exception is an errno that cannot be ignored and carries a message and a stack trace. NotFoundException is your -ENOENT; InvalidStateException is -EINVAL/-EBUSY. try-with-resources and finally play the role of the cleanup labels.

Rules graders notice

Do
  • Validate at the edge (constructor or service entry) and throw early with a clear message.
  • Throw specific types; catch the base type in the driver.
  • Make the driver show one failure case per rule (unknown id, double cancel, not enough money).
  • Keep exceptions for exceptional paths. "Spot not available" in a search is a normal empty result, not an exception.
Avoid
  • catch (Exception e) {}: the error disappears and state may be half-updated.
  • return -1 or return null to mean "failed": the caller forgets to check.
  • throw new RuntimeException("error") everywhere: no type to catch, no code to map.
  • Using exceptions as a loop exit or for normal branching (slow and unclear).
