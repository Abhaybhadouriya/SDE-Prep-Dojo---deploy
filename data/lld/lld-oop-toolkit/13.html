  1. Nothing, ordinals are fixed forever

Which is the best signature for a repository lookup?

  1. User findById(String id) returning null if missing
  2. Optional<User> findById(String id)
  3. Optional<List<User>> findById(String id)
Optional states "zero or one" in the type. Null travels silently; Optional of a list is an anti-pattern.

A class overrides equals() but not hashCode(). set.add(new P(1,2)); set.contains(new P(1,2)) returns...

  1. almost always false
  2. always true
  3. a compile error
The identity hash codes differ, so the lookup checks the wrong bucket and never calls equals.

Which of these is NOT needed for a hand-written immutable class?

  1. private final fields
  2. defensive copy of a mutable list passed to the constructor
  3. synchronized getters
Immutable objects need no locks: nothing writes after construction.

In static <T> T best(Collection<? extends T> items, Comparator<? super T> c), why ? super T on the comparator?

  1. So it can return a supertype
  2. A comparator only consumes T, so one written for a supertype (e.g. Comparator<Object>) also works
  3. It is required by erasure
PECS: Consumer Super. The comparator takes T values in.

Your payment methods will grow every quarter, each with different validation logic. Best model?

  1. An interface with one class per method, plus a registry
  2. A giant enum with a switch in every service
  3. A String field "UPI", "CARD"
An open, growing set with different behaviour is the textbook case for polymorphism and the Open/Closed Principle.
