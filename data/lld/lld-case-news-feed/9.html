Concurrency and thread safety

Find the shared mutable state first, then protect each piece at the smallest scope that keeps it correct:

Step through the race this section is about, then the fix the code uses:

  1. Thread A handles "ana upvotes 001": it reads ana's previous vote (none) and plans to add 1.
  2. A duplicate request from ana's second tab reads the same empty previous vote.
  3. Both add 1: one user, two upvotes. Recounting later will not match the counters.
  4. The fix: votes.put(user, dir) on a ConcurrentHashMap returns the previous vote atomically for that key, and the two AtomicInteger counters move by the difference. The demo: 400 users vote down then up from 8 threads; the post ends at exactly 400 up, 0 down.

The demo proves two of these: 400 users each vote down then up on one post from 8 threads and the post ends at exactly 400 up, 0 down; 400 posts are fanned out concurrently and a follower's inbox holds all 401. There is no global lock, so a vote on one post never waits for a post by someone else. More on choosing these tools: locks and synchronisation.

What the code deliberately does not do

  • Fan-out happens on the posting thread. A user with 10 million followers would make post() take seconds. At scale, post() enqueues an event and a worker pool does the delivery (a producer-consumer queue, see thread pools). The feed then becomes eventually consistent: a follower may see the post a moment later.
  • A feed read is not a snapshot. Votes can change while we sort, so two posts may compare differently mid-sort. Java's TimSort is allowed to throw IllegalArgumentException ("Comparison method violates its general contract") when that happens. The clean fix is to copy each candidate's score and comment count into a small snapshot record first and sort the snapshots.
  • Offset cursors shift if new posts arrive between pages: a post can appear twice. See the pagination follow-up below.

From your world

Per-inbox locks are per-CPU or per-queue locks: they turn one hot lock into many cold ones, as multi-queue NICs give each RX queue its own lock and IRQ. The vote counters follow the kernel's refcount rule: change them only through atomic operations, and derive the score from the counters instead of recounting the map. Moving fan-out to a worker is the classic top half / bottom half split: post() does the minimum and defers the heavy part, like an interrupt handler scheduling a softirq or workqueue item.
