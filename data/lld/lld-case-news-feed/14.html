Interview follow-ups

Pull or push: which do you choose, and when?

Pull writes in O(1) and reads in O(k + page log k) for k followees; push writes in O(followers) and reads in O(page). Reads usually far outnumber writes, so push wins for normal users. Push breaks for celebrities (one post, millions of copies) and wastes work for inactive followers. The common answer is hybrid: push for normal authors, pull for high-follower authors, merged at read time.

How to answer

Give both costs as formulas, then the read/write ratio argument, then the celebrity problem, then hybrid. Point at FeedGenerator: the choice is a swap, not a rewrite.

Likely follow-ups
  • What threshold makes someone a celebrity? (Tune by measuring fan-out time; it is a config value.)
  • What about inactive users? (Skip their inboxes; rebuild by pull when they return.)
Every user can customise how their feed is ranked. How?

Ranking is a Strategy: an interface that returns a comparator for a viewer. The facade keeps Map<userId, FeedRanker> with a default. feed() looks up the user's ranker and sorts the candidates with it. A new ranking rule is a new class; nothing else changes. Because the ranker receives the viewer and the follow graph, rules like "followed first" or "my close friends first" fit the same interface.

How to answer

Show the interface, two implementations, the map, and the one line in feed().

Likely follow-ups
  • Combine rules ("top, but followed first")? (Comparator chaining with thenComparing, or a Composite ranker.)
  • User-defined weights? (A WeightedRanker(w1, w2, w3) instance per user.)
How do you get the 10 newest posts from everyone I follow efficiently? (LeetCode 355)

Each author's timeline is already sorted by time. Put the newest post of each followee (and mine) into a max-heap keyed by (time, sequence). Pop 10 times; after each pop, push the next older post from the same timeline. Cost O(k + 10 log k) for k followees, and no full scan.

How to answer

Say "k-way merge, like merging k sorted lists", draw three timelines and the heap.

Likely follow-ups
  • Why a sequence number? (Equal timestamps need a total order or pages become unstable.)
How do you paginate so that new posts do not cause duplicates or gaps?

An offset cursor shifts when new posts arrive at the top: page 2 then repeats the last item of page 1. For chronological feeds use a keyset cursor: "posts strictly older than (time T, seq S)", which is stable no matter what arrives. For ranked feeds the order itself changes as votes arrive, so cache the ranked list of ids per session on page 1 and page through that snapshot. Keep the cursor opaque so the format can change.

How to answer

Show the duplicate with a three-post example, then the keyset fix, then the ranked-feed snapshot.

Likely follow-ups
  • How do you show "5 new posts" at the top? (Query posts newer than the first item's key.)
Implement Flipkart's ranking: followed first, then score, then comments, then time.

A comparator chain: comparing(p -> !follows(viewer, p.author)) (false sorts first), then score descending, then comment count descending, then the newest-first comparator, which ends with the sequence number as the last tie-break. The candidates are everyone's recent posts (a global generator), because the sample shows non-followed posts too.

How to answer

Write the chain; mention that the final tie-break must be unique or two runs may print different orders.

Likely follow-ups
  • Count nested replies as comments? (Composite: threadSize().)
Where does the Observer pattern fit, and what are its risks here?

post() notifies every FeedListener; push fan-out is one listener, notifications or indexing could be others. Risks: a slow or failing listener slows or breaks posting (run listeners asynchronously through a queue, catch per-listener errors); ordering between listeners is not guaranteed; and listeners that are never unregistered leak.

How to answer

Name the subject (the network), the event (a new post), the observers, then the three risks with fixes.

Likely follow-ups
  • Exactly-once delivery to inboxes? (Make delivery idempotent by post id, so retries are harmless.)
How do you make voting correct under concurrency?

Keep a map user to direction per post. put on a concurrent map is atomic per key and returns the previous value, so I subtract the previous vote and add the new one on atomic counters. A user voting twice in parallel ends with one entry and consistent counters. The score is up - down, never recounted from the map on read.

How to answer

Name the race (read old vote, write new vote), then the atomic fix, then show the 400-user test.

Likely follow-ups
  • Very hot posts? (Sharded counters summed on read, like per-CPU counters.)
What happens on unfollow and on delete in a push design?

Copies already sit in inboxes. Eagerly removing them costs O(inbox) per follower. Instead, filter lazily at read time: skip posts whose author I no longer follow and posts marked deleted (a tombstone). Inboxes are trimmed by the cap anyway, so stale entries age out.

How to answer

Contrast eager vs lazy cleanup; mention that tombstones also make deletes idempotent.

Likely follow-ups
  • And on a new follow? (Backfill the followee's recent posts into the inbox, as our onFollow does.)
How would this design change at real scale?

The classes stay; their implementations move out of process. Timelines and inboxes become lists in a cache cluster keyed by user; the follow graph becomes a sharded store; fan-out becomes a queue consumed by workers; ranking may call a model service. The FeedGenerator, FeedRanker and listener interfaces are exactly the seams where those swaps happen. The full scale-out is in the News Feed HLD design.

How to answer

Map each class to its distributed replacement in one sentence each.

Likely follow-ups
  • Cap per inbox? (A fixed number of recent ids; older pages fall back to pull.)
How do you structure the console so a new command is easy to add?

A map from command word to a handler (a dispatch table, Command-lite; full Command would make each request an object you can queue or undo). run(line) splits on ~, looks up the handler, calls it, and converts domain exceptions and missing arguments into error: lines. The console holds only session state (the logged-in user); all logic is in the facade, so the same facade can be driven by tests or a REST layer.

How to answer

Show two entries of the map and the single try/catch.

Likely follow-ups
  • Undo a vote? (Command objects with an inverse, or just vote(user, post, 0).)
