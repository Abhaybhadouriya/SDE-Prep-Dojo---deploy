Using GRASP in the interview

Interviewers rarely say "GRASP". They ask "why is this method here?", "what changes if we add EV charging?", or "your service class is 400 lines, is that okay?". Use the principle names as a short justification, then move on:

  • "canFit is on the spot because the spot owns its size and occupancy - Information Expert. Nothing else needs to know those fields."
  • "The lot creates tickets because it just found the spot and has the vehicle and time - Creator."
  • "Pricing is behind an interface because the problem says rules will change - Protected Variations. A new rule is a new class."
  • "The repository is a pure fabrication so I can swap in-memory for a database without touching parking rules."
What is the Information Expert principle? Give an example.

Assign a responsibility to the class that has the information needed to fulfil it. Example: the ticket stores the entry time, so Ticket.minutesParked(exit) belongs on the ticket. The opposite is Feature Envy: a service that pulls fields out of other objects and decides on their behalf.

How to answer

Rule in one line, one example from the design on the whiteboard, then the limit: Expert is overruled when it hurts cohesion (a ticket should not save itself to a database).

Likely follow-ups
  • What if the data is spread over three classes? (Split the work; each expert does its part.)
  • How is this related to Tell, Don't Ask?
Your controller is doing all the work. What is wrong and how do you fix it?

It is a bloated controller: it computes, validates and stores, so it is low in cohesion and high in coupling (it knows every class). Push each computation to its expert (fee to the pricing policy and ticket, fit checks to the spot), storage to a repository, and leave the controller with ordering steps and handling failures. If it still has many operations, split it into use-case controllers.

How to answer

Name the smell, show one method you would move and to where, then say what the controller keeps (coordination and error handling).

Likely follow-ups
  • Facade controller vs use-case controller: when do you switch?
  • Where does input validation go?
What is a pure fabrication, and is a "Service" class always one?

A class that does not represent a domain concept, invented to keep cohesion high and coupling low: repositories, ID generators, clocks, gateways, factories. Most ...Service classes are fabrications, but a service that holds all business rules while entities are only getters is an anemic model, not good fabrication. Fabricate technical concerns and cross-object workflows; keep rules in entities.

How to answer

Definition, two examples from your design, then the anemic-model warning to show judgement.

Likely follow-ups
  • Which GoF patterns are pure fabrications?
  • How would you test the parking logic without a real database?
How do you design for "pricing rules will change often"?

Protected Variations: put a stable PricingPolicy interface at that point, with one class per rule (Strategy). The controller depends only on the interface and gets the policy injected. A new rule (surge, monthly pass) is a new class plus one wiring line; no tested code is edited. If rules combine (weekend + EV discount), use a decorator or a chain of policies.

How to answer

Say the principle, draw the interface with two implementations, show the one-line wiring change.

Likely follow-ups
  • How do you choose the policy at runtime (by time, by lot)?
  • How is this different from OCP?
Expert says Ticket should save itself. Cohesion says no. How do you decide?

Ask what changes together. Saving changes when the storage technology changes; the ticket's rules change when parking rules change. Different reasons to change mean different classes (SRP), so a repository wins. Expert is a default, the judges (coupling and cohesion) settle ties and conflicts.

How to answer

Use the "who asks for this change?" test and name the winner. Mention Active Record as the known alternative that some frameworks choose on purpose.

Likely follow-ups
  • When is Active Record acceptable?
How do GRASP, SOLID and design patterns relate?

GRASP is the reasoning for assigning responsibilities; SOLID gives rules for class shape and dependencies; GoF patterns are concrete reusable structures. Mapping: High Cohesion is close to SRP; Protected Variations covers OCP and DIP; Strategy and State are Polymorphism; Adapter and Facade are Indirection; Factory and Repository are Pure Fabrication; Facade can be a Controller.

How to answer

One line per layer, then two or three mappings. Do not recite all nine.

Likely follow-ups
  • Which one would you use first in a 45-minute round? (Expert and Controller when placing methods.)

Scenario: "Add EV charging spots"

Halfway through your parking-lot round the interviewer says: some spots now have chargers; EVs pay a charging fee per kWh on top of parking.
Add if (vehicle.isEV()) checks to the controller and the fee code, and a boolean hasCharger that the controller reads.
Spot owns hasCharger and answers canFit for EVs (Expert). Charging is a new predicted variation, so add a ChargingPolicy or decorate PricingPolicy with a charging layer (Protected Variations). The kWh reading comes from a Charger adapter (Indirection). The controller changes by at most one call.
Follow-ups: what if a charger fails mid-session? Where do you keep the kWh meter reading?
