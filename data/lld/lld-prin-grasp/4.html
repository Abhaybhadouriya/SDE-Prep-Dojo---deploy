2. Creator: who calls new?

Rule: class B should create objects of class A if one or more of these is true (the more, the better):

  1. B contains or aggregates A - a lot contains floors, so ParkingLot builds Floors.
  2. B records A - the lot keeps a counter of tickets it issued.
  3. B closely uses A - the lot is the one that parks a vehicle and needs the ticket right away.
  4. B has the data needed to initialise A - the lot is the one that just found the spot, knows the vehicle and the time.

In our model ParkingLot.admit(vehicle, now) finds the spot, parks the vehicle and returns new Ticket(...). It ticks all four boxes, so it is the creator. Making the controller call new Ticket(...) instead would force the controller to know about spots, floors and ID counters - more coupling for no gain.

// Creator: the lot contains the spots and has every value a ticket needs.
Optional<Ticket> admit(Vehicle v, long nowMinute) {
    for (Floor f : floors) {
        Optional<ParkingSpot> spot = f.findSpot(v);        // ask the expert
        if (spot.isPresent()) {
            spot.get().park(v);
            return Optional.of(new Ticket("T" + nextTicket++, v, spot.get(), nowMinute));
        }
    }
    return Optional.empty();                                 // lot full for this size
}

When creation gets complicated (many variants, choices made from config, recycling objects), Creator steps aside for a Factory or a Builder. Those are pure fabrications for creation: classes that exist only to build things.

From your world

The kernel follows Creator closely: the subsystem that owns a list allocates its members (alloc_netdev() for net devices, sock_alloc() inside the socket layer). When creation is hot or complex it moves to a fabrication - kmem_cache_create() gives you a slab cache whose only job is to make and recycle objects of one type.
