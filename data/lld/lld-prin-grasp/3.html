1. Information Expert: the data owner does the work

Rule: give a responsibility to the class that has the information needed to fulfil it. This is the GRASP principle you will use most - probably for eight out of ten methods.

Question: "how long was this car parked?" Who knows the entry time? The Ticket. So Ticket.minutesParked(exit). Question: "can this vehicle use this spot?" Who knows the spot's size and whether it is taken? The ParkingSpot. So ParkingSpot.canFit(vehicle). Question: "find a free spot on floor 2" - the Floor holds its list of spots, so Floor.findSpot().

Sometimes the information is spread out. Then the job is split, and each expert does its part. The total fee needs the duration (Ticket knows it) and the rate (the pricing policy knows it), so the policy asks the ticket for the duration and multiplies.

// The fee service "envies" the ticket's data: it pulls fields out and decides itself.
class FeeService {
    long fee(Ticket t, long exitMinute) {
        long minutes = exitMinute - t.getEntryMinute();          // ticket data
        if (minutes < 0) minutes = 0;
        long hours = Math.max(1, (minutes + 59) / 60);
        VehicleType type = t.getVehicle().getType();              // chain into Vehicle
        long rate = type == VehicleType.BIKE ? 2000
                  : type == VehicleType.CAR  ? 5000 : 10000;      // rate table hidden in an if
        return hours * rate;
    }
}
record Ticket(String id, Vehicle vehicle, ParkingSpot spot, long entryMinute) {
    // Expert: the ticket owns entryMinute, so it owns the duration rule.
    long minutesParked(long exitMinute) { return Math.max(0, exitMinute - entryMinute); }
}

final class HourlyPricing implements PricingPolicy {
    private final Map<VehicleType, Long> perHour;   // the policy owns its own rate table
    HourlyPricing(Map<VehicleType, Long> perHour) { this.perHour = perHour; }
    public long feeInPaise(Ticket t, long exit) {
        long hours = Math.max(1, (t.minutesParked(exit) + 59) / 60);
        return hours * perHour.get(t.vehicle().type());
    }
}

Where Expert goes wrong. Followed blindly, Expert says "a Ticket has all its own data, so Ticket.saveToDatabase()". That mixes storage with business rules and drags SQL into a domain class. When Expert hurts cohesion or coupling, the other principles (High Cohesion, Pure Fabrication) win. Expert is a first answer, not a final one.

Expert is also the formal name behind Tell, Don't Ask: instead of asking an object for its data and deciding outside, tell the object to do the job. If you see a.getB().getC().getD() in your code, the method probably belongs further down that chain.
