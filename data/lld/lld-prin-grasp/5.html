3. Controller: the first object behind the gate

Rule: a system event (a button press, a REST call, a CLI command, a message from a queue) should be handled first by a non-UI object that represents either the whole system (a "facade controller") or one use case (a "use-case controller", like ExitGateHandler).

The controller's job is to coordinate: look things up, call the experts in order, handle the outcome. It should not compute fees or check spot sizes itself. If it does, you get a bloated controller - a god class with every rule of the system inside it, and that is one of the most common reasons machine-coding solutions lose marks.

  1. The exit gate (UI layer) passes the ticket ID to the controller. The UI holds no rules.
  2. The controller asks the repository (a pure fabrication) for the open ticket.
  3. It asks the pricing policy for the fee. The policy asks the ticket, the expert on duration (130 minutes), and returns 15000 paise for a car (3 hours at Rs 50).
  4. It asks the payment gateway (indirection to a vendor) to charge the amount.
  5. Only after payment succeeds it tells the spot to free itself and closes the ticket.
  6. Count the work the controller did: none of the numbers. It only decided the order of steps and what to do on failure.
String onExit(String ticketId) {
    Ticket t = tickets.find(ticketId).orElseThrow(() -> new NoSuchElementException("no ticket " + ticketId));
    long fee = pricing.feeInPaise(t, clock.nowMinute());
    if (!payments.charge(t.id(), fee)) return "PAYMENT_FAILED";   // spot stays taken
    t.spot().free();
    tickets.close(t.id());
    return "PAID " + fee;
}

In a machine-coding round, your main() or driver class plays the UI. Keep it to parsing input and printing output; put a controller (or a service like ParkingService) right behind it. Reviewers at Flipkart-style rounds check exactly this "separation of concerns" line.

Facade controller or use-case controllers? With 2-4 system operations, one facade controller (ParkingController) is clear. When it grows past a handful of operations, split it per use case (EntryGateHandler, ExitGateHandler, AdminHandler) to keep each one cohesive.

From your world

The system call entry is a controller. sys_read() validates the fd, looks up the struct file and hands the work to file->f_op->read_iter. It does not know anything about ext4 blocks or socket buffers. A syscall that tried to do filesystem work itself would be a bloated controller.
