7. Pure Fabrication: invent a class when nothing fits

Rule: when giving a job to any domain class would hurt cohesion or coupling, invent a class that does not exist in the problem domain, just to hold that job.

Who stores open tickets so the exit gate can find them? Expert would say "the lot", since it issued them. But then ParkingLot handles spot allocation and storage and lookups, and when we later move storage to Redis we edit the class with all the parking rules in it. So we invent TicketRepository. The same goes for IdGenerator, Clock, FeeCalculator and most classes named ...Service.

Do not overdo it. If every domain class is a bag of getters and all logic lives in ...Service classes, you have built an anemic domain model - Expert has been ignored everywhere. Fabricate for technical concerns (storage, IDs, time, external calls) and for logic that truly spans many objects. Keep domain rules in domain objects. See Anti-patterns.

Many GoF patterns are pure fabrications: Repository, Factory, Adapter, Command objects.
