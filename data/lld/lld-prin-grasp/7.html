6. Polymorphism: let the type answer

Rule: when behaviour depends on a type ("if it is a bike then ..., if a car then ..."), give that behaviour to the types through a common interface, and call it without checking the type.

The tell-tale sign is the same switch on a type code in several places: one for spot size, one for the rate, one for the label on the receipt. Adding a new vehicle type (say, EV) then means editing every switch, and missing one is a bug.

static Size sizeFor(String type) {
    switch (type) {                       // repeated in sizeFor, rateFor, labelFor ...
        case "BIKE":  return Size.SMALL;
        case "CAR":   return Size.MEDIUM;
        case "TRUCK": return Size.LARGE;
        default: throw new IllegalArgumentException(type);   // typo = runtime crash
    }
}
enum VehicleType {                        // each constant carries its own behaviour/data
    BIKE(Size.SMALL), CAR(Size.MEDIUM), TRUCK(Size.LARGE);
    final Size size;
    VehicleType(Size s) { size = s; }
}

// ParkingSpot asks the type - no switch anywhere:
boolean canFit(Vehicle v) { return isFree() && v.type().size.compareTo(size) <= 0; }

A rich enum is enough when the variants are a closed, small set and differ only in data. When they differ in behaviour (each pricing rule computes differently), use an interface with one class per variant - that is the Strategy pattern, and PricingPolicy in our model is exactly that.

From your world

struct file_operations is GRASP Polymorphism in C. The VFS never writes if (is_ext4) ... else if (is_socket) ...; it calls f_op->read_iter() and each filesystem or driver answers for itself. A C++ or Java virtual method is the same function-pointer table, filled in by the compiler.
