When to use it, when not to

Use it when
  • The language is small and stable: a handful of operators, boolean rules, arithmetic formulas, a filter syntax.
  • Rules must be data, changed without a deploy (campaign targeting, discount rules, alert conditions).
  • You parse once and evaluate many times, so an immutable tree is cheap to share.
  • Adding an operator should be "one new class" or "one registry entry".
Avoid it when
  • The grammar is large (dozens of rules): one class per rule becomes unmanageable; use a parser generator such as ANTLR.
  • Speed matters per evaluation (millions per second): tree walking does a virtual call per node; compile to bytecode or native code instead.
  • You need many operations on the tree (evaluate, print, optimise, type-check): move them out into visitors rather than piling methods onto every node.
  • The rules never change at runtime: plain code, or Specification objects built in code, are simpler.
  • Untrusted users write the rules: you also need limits on depth and length, and no access to arbitrary fields or methods.

Never "interpret" a rule by passing user text to a general-purpose evaluator (eval in Python or JavaScript, a scripting engine). That runs arbitrary code. A small grammar of your own is the safe version of the same feature.
