In interviews

Why interviews skip the name. In the interview reports we collected, Interpreter is almost never asked for by name: the GoF grammar vocabulary is rarely needed for business apps, and refactoring.guru does not even list it. But the question it answers does appear, and it is a full machine-coding problem:

  • A Groww LLD round (2024) asked for an "expression gate": evaluate a boolean expression with &&, ||, ==, !=, <=, >= over a map of variables, so that new operators can be added without much code change (post). That is the Java tab of this page.
  • An Oracle onsite asked for a calculator over nested expressions such as 2 + (3 * 4) using the Composite pattern (post): the same tree, named after its shape.
  • Discount and coupon engines (shopping cart), alert conditions in a monitoring system, and "configurable rules" follow-ups in a notification service lead to the same design.

How to drive it: (1) write the grammar in three lines, with precedence; (2) draw Expr with terminal and nonterminal classes; (3) write the parser as one method per rule; (4) show extension (operator registry); (5) mention error handling (unknown variable, bad token, unexpected end) and that the parsed tree is immutable and thread-safe.

Strong 30-second answer: "I'd model the rule language with the Interpreter pattern: an Expr interface with interpret(context), terminal classes for comparisons and nonterminal classes for AND, OR and NOT. A small recursive-descent parser builds the tree once; we evaluate it per request. Operators live in a registry, so adding one is a single entry. If the grammar grew large I would switch to a parser generator, and if evaluation were on a hot path I would compile the rule, the way BPF does."
