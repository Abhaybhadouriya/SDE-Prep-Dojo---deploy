Interview Q&A

Design an evaluator for rules like age >= 18 && city != NY over a map of values, extensible to new operators.

Interpreter pattern: Expr.interpret(Map ctx); Compare(var, op, literal) as the terminal; And, Or, Not as nonterminals. A recursive-descent parser with one method per precedence level (or calls and calls unary). Operators in a Map<String, BiPredicate> so a new operator is one registration. Parse once, cache the tree per rule id, evaluate per request.

How to answer

Grammar first, then classes, then parser, then extension. Run two examples by hand.

Likely follow-ups
  • How do you handle a missing variable or a type mismatch?
  • How would you add parentheses or a between operator?
Interpreter vs Composite: what is the difference?

Structurally they are the same tree. Composite is the general shape (leaves and containers share an interface). Interpreter is a Composite where node classes correspond to grammar rules and the shared operation is "evaluate this sentence". An Oracle question asked for a calculator "using Composite"; describing it as an interpreter over an expression tree is the same design.

How to answer

"Interpreter is a Composite with a grammar." Then sketch Num, Add, Mul.

Likely follow-ups
  • Where does operator precedence live? (In the parser, not in the node classes.)
When does the Interpreter pattern stop being a good idea?

When the grammar is big (a class per rule is unmanageable; use ANTLR or similar), when evaluation is on a hot path (one virtual call per node; compile to bytecode or native, as BPF and regex engines do), and when you need many tree operations (move them into visitors). Also when untrusted users write rules: then you need depth limits, timeouts and a whitelist of fields.

How to answer

Three axes: grammar size, speed, number of operations.

Likely follow-ups
  • Why not just call eval?
Is BPF an example of the Interpreter pattern?

It is an interpreter in the broad sense, not the GoF tree-walking form. libpcap compiles a filter expression to classic BPF instructions; the kernel converts them to eBPF and runs them in an interpreter loop or as JIT-compiled native code. The GoF pattern keeps the AST and walks it; BPF flattens the tree into a program with jumps. The idea that links them: a small language, a context (the packet), and evaluation per input.

How to answer

Say "yes, broadly", then show the nuance: tree-walker vs bytecode VM vs JIT.

Likely follow-ups
  • Why does the kernel need a verifier before running eBPF?
Interpreter vs Specification for business rules: which would you choose?

If rules are written by developers and change with releases, Specification objects (isAdult().and(inCity("BLR"))) are simpler: no parser, type-safe. If rules must be stored as text and edited by operations or product teams without a deploy, add a grammar and parser: that is Interpreter, and the nodes can even be Specification objects.

How to answer

The deciding question is "who writes the rule, and when?"

Likely follow-ups
  • How would you validate a rule before saving it?
Is the parsed expression tree thread-safe? Should you cache it?

Yes, if nodes are immutable (final fields, no state written during interpret) and all per-request data travels in the context argument. Then one tree can be shared by every thread, and caching parsed trees by rule id (for example in a ConcurrentHashMap with computeIfAbsent) removes parsing from the request path. If an operator registry can change at runtime, make it a concurrent map or rebuild it copy-on-write.

How to answer

Immutability plus context passing, then the cache.

Likely follow-ups
  • How do you invalidate the cache when a rule is edited?
