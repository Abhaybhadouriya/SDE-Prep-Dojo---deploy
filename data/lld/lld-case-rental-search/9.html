Concurrency and thread safety

The workload is read-heavy: many searches, a few edits. The danger is not two writers; it is a reader seeing half an update, for example a listing whose price changed in the store but whose old location entry is still in the index.

  • One read-write lock around the store and both indexes. upsert removes the old listing's location and text entries, stores the new listing and adds its entries, all under the write lock. A search under the read lock sees the state before or after, never between. Many searches hold the read lock at once.
  • Do the slow part outside the lock. Candidate lookup and filtering happen under the read lock; sorting and paging happen after unlock on our own list of hits. Hits point at immutable listings, so nothing they read can change.
  • Prove it. The Java demo and the Python test run 3-4 writer threads changing prices at random while 3-4 reader threads search "gym, 20k-40k". Every hit must satisfy the filter it was found with. Thousands of searches, zero bad hits.
  • The facade's own state (users, active sessions, shortlists) lives in concurrent maps and synchronized sets; ids and the logical clock are AtomicLongs.
  • If writes get heavy: copy-on-write snapshots. Writers build a new index version (or batch a few edits) and publish it with one atomic reference swap; readers never block. That is how Lucene-style engines work: immutable segments plus a periodic refresh, at the cost of a short delay before an edit is searchable.
  • Writer starvation: with a constant stream of readers a writer can wait forever. Java's ReentrantReadWriteLock(true) (fair mode) or a writer-preferring lock fixes it. Our Python RWLock is writer-preferring: once a writer is waiting, new readers queue behind it (a test checks this). The price: a thread that already holds the read lock must not acquire it again while a writer waits, or it deadlocks (it waits behind the writer, and the writer waits for it to release its first read lock).

From your world

This is rwlock_t versus RCU. The read-write lock is the simple answer; under very heavy reads the kernel moves to RCU: readers take no lock at all, a writer builds a new copy, publishes it with rcu_assign_pointer() and frees the old one after a grace period. The copy-on-write snapshot above is the same idea, with the garbage collector as the grace period.
