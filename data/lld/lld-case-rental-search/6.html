Core flows: building the index, and one search end to end

First, the inverted index itself, on three tiny listings. Click through.

  1. Three listings. The tokenizer lower-cases and splits on anything that is not a letter or digit. Title words count 3, body words count 1.
  2. The postings: each term maps to the ids that contain it, with the weight. "pool" appears twice in #2's body, so its weight there is 2.
  3. Query "pool gym" means both words. Fetch both lists and start from the shorter one (pool has 2 ids, gym has 3).
  4. For each id in the short list, probe the long list. Both #1 and #2 are in it; add up the weights.
  5. Rank by score: #2 then #1. #4 (which says "no gym") was never touched, because it does not contain "pool".
  6. Remove: the forward map lists #2's terms, so we delete #2 from exactly those posting lists and drop any list that becomes empty. No scan of the whole index.

Now the full call sequence for search(text "pool gym").

  1. The client (console, test, REST controller) calls the platform with a built SearchQuery.
  2. The platform passes it straight to the engine; searching needs no login in our rules.
  3. The engine takes the read lock. Other searches can hold it at the same time; writers wait.
  4. Text is present, so candidates come from the text index: ids 2 and 1 with their scores.
  5. The query's Specification (available AND rent AND ...) tests each candidate. Both pass.
  6. The engine builds Hit objects and releases the lock. The hits point at immutable listings, so the rest needs no lock.
  7. Sort with the query's strategy: nearby-only last, then relevance, then newest, then id.
  8. Cut out the requested page and return it with the total, so the caller can show "page 1 of N".

The two classic bugs: deleting a document from the store but not from the posting lists (searches then return ids that no longer exist, or crash on a null), and sorting without a final tie-breaker (two listings at the same price swap places between requests, so page 2 repeats an item from page 1). The demo and tests check both.
