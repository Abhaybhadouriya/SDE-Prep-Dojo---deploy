Posting lists: "pool" has 40 ids, "gym" has 4,000, "parking" has 900. For the AND query "pool gym parking", where do you start?

  1. gym, the biggest list
  2. pool, the smallest list
  3. It does not matter
Walk the smallest list and probe the others: at most 40 candidates instead of 4,000.

What makes remove(id) fast and complete?

  1. Scanning every posting list for the id
  2. Rebuilding the index
  3. A forward map from id to the terms it added
The forward map tells you exactly which posting lists to touch.

The interviewer adds a "pets allowed" filter. With this design you:

  1. Add a field, a Spec and a builder method
  2. Add an if in search() and in every caller
  3. Build a new index for pets
Filters are Specifications; search() just calls spec.test().

Two listings have the same price. Sorting by price only, what can go wrong across pages?

  1. Nothing
  2. Their order can change between requests, so one repeats and one is skipped
  3. The sort throws an exception
Without a total order (e.g. price then id), page boundaries are not stable.

A listing is marked sold. What should happen?

  1. Delete it from every index and every shortlist
  2. Keep it in search results with a SOLD badge
  3. Hide it from search, keep it in shortlists and the owner's view with status SOLD
The Flipkart statement asks for exactly this: status, not deletion.

Why does upsert change the store, the text index and the location index under one write lock?

  1. So a search never sees a listing updated in one index but not the others
  2. Because HashMap needs it
  3. To make writes faster
The invariant is that all indexes agree with the store at every moment a reader can look.

"Promote Sony phones for the query android." Where does this rule belong?

  1. In the tokenizer
  2. In ranking, as a score booster applied to matching hits
  3. In the inverted index, as fake postings
Promotions change order, not matching; keeping them out of the index lets campaigns change without re-indexing.
