Interview follow-ups (Q&A)

Why an inverted index instead of scanning every document?

A scan costs time proportional to the total text on every search. The inverted index pays once at insert time and then answers "which documents contain this word?" with one hash lookup. A multi-word AND query costs about the size of the shortest posting list times the number of words, which is tiny for selective words. Memory is the price: roughly one entry per distinct word per document.

How to answer

State the cost of both, then the trade (memory for latency), as the Microsoft candidate did.

Likely follow-ups
  • What about very common words like "the"? (Stop words, or keep them but always intersect from the rarest list.)
How does remove work, and how do you know it is complete?

The index keeps a forward map: document id to the terms it added. remove(id) looks up those terms, deletes the id from each posting list and drops lists that become empty. No scan of the dictionary. Update is remove then add. To prove it, a test removes a document and checks that a word only it contained returns nothing and that the term count dropped; the engine also removes the location entries using the old listing's fields.

How to answer

Lead with the forward map; this is the exact bug that cost a candidate the 2026 round.

Likely follow-ups
  • Delete a million documents at once? (Mark deleted with a bitmap, filter at query time, compact later, as Lucene does.)
"Search by any combination of filters." How do you avoid a mess of ifs?

Each filter is a Specification with one test(listing), and specs combine with and, or, not. The query builder only adds the specs whose parameters were set, so search() calls spec.test() once per candidate and never checks for nulls. A new filter is one new spec and one builder method.

How to answer

Show the composed spec for one example query.

Likely follow-ups
  • OR across localities, AND across everything else? (locationIn(set) is the OR inside one spec.)
Order results by frequency, by created date or by updated date.

Ranking is a Strategy: a comparator chosen by the query. Frequency uses the score the index returns (sum of word counts); created and updated use the document's timestamps. Every comparator ends with the id so ties are broken the same way every time. Adding "by size" is one more comparator; the engine is unchanged.

How to answer

Mention the tie-breaker; it shows you have thought about paging.

Likely follow-ups
  • Combine two orders, e.g. relevance then newest? (thenComparing.)
Nearby localities must appear, but after exact matches. How?

Each listing stores its nearby localities, and the location index maps each of them to the listing too, so one lookup finds both kinds. The hit records nearbyOnly (its own locality is not in the query). The final comparator sorts on that flag first, then on the requested order. The location spec only accepts nearby matches when the query asked for them.

How to answer

Separate "is it a match?" (spec) from "where does it rank?" (comparator).

Likely follow-ups
  • Real distances instead of a nearby list? (Geohash or grid index for candidates, a distance spec, distance as a sort key.)
Make it feel instant while the user types.

Treat the last word as a prefix. Keep the term dictionary sorted (TreeMap, or a trie), so all terms starting with "balc" are one range scan; merge their posting lists and intersect with the full words before it. Cap the number of expanded terms, return the first page only, and debounce keystrokes on the client. For ranking tiers (name prefix above name substring above content), index name and content as separate fields with different weights.

How to answer

Data structure first (sorted terms), then the user-facing tricks (cap, debounce, first page).

Likely follow-ups
  • Trie or sorted map? (A trie shares prefixes and can store top-k per node; a sorted map is simpler and enough in a round.) See Autocomplete.
A brand pays to be shown first for "android". Where does that go?

In ranking, not in matching: promoted items must still match the query and the filters. Add a ScoreBooster that multiplies or adds to the relevance score based on rules (brand, keyword, campaign dates) and apply it to the hits before sorting. Several boosters chain as Decorators. Keep boosting out of the index so a campaign can start or stop without re-indexing.

How to answer

"Match, then filter, then rank; business rules live in ranking."

Likely follow-ups
  • Label promoted results? (A flag on the hit set by the booster.)
Searches and edits happen at the same time. What do you lock?

One ReentrantReadWriteLock around the store and both indexes. Edits take the write lock and change all three together, so nobody sees a listing in one index and not another. Searches share the read lock for candidate lookup and filtering, then sort and page outside the lock on their own list of immutable listings. If edits become frequent, switch to copy-on-write snapshots published through an atomic reference, so readers never block.

How to answer

Name the invariant ("indexes agree with the store") before the lock.

Likely follow-ups
  • Writers starve under heavy reads? (Fair mode or a writer-preferring lock.)
Page 2 showed an item that was already on page 1. Why, and how do you fix it?

Two causes. First, an incomplete sort key: two listings at the same price can come back in a different order on the next request. Fix: always end the comparator with the id. Second, data changing between requests: a new listing pushes everything down by one. Fix: keyset (cursor) pagination, where the client sends the last sort key and id it saw and the server returns items strictly after it.

How to answer

Give both causes; most candidates know only one.

Likely follow-ups
  • Why is OFFSET slow on a database? (It still reads and throws away the skipped rows.)
The data no longer fits on one machine. What changes?

The same pieces, distributed. Shard listings by id (or by city for rentals), each shard with its own inverted index; a query fans out to the shards, each returns its top N, and a coordinator merges them with the same comparator. Edits flow as change events (an outbox or CDC stream) into the indexers, so search is eventually consistent with the store. That is Elasticsearch's model; see HLD: Search Engine.

How to answer

Map each LLD class to its HLD counterpart; mention eventual consistency explicitly.

Likely follow-ups
  • Relevance across shards? (Global term statistics, or accept per-shard scores.)
