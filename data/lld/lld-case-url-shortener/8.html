// REST shape a controller would expose
POST   /api/links        {"url": "...", "alias": "team-docs", "ttlSeconds": 86400}  -> 201 {"code": "...", "shortUrl": "..."}
GET    /{code}                                                                 -> 302 Location: longUrl | 404 | 410
DELETE /api/links/{code}                                                       -> 204 | 403 | 404
GET    /api/links/{code}/stats                                                 -> 200 {"clicks": 5}

Why resolve returns a value instead of throwing: "not found" and "expired" are normal outcomes for a public link, and the controller needs to tell them apart (404 vs 410). Bad input to shorten is a caller error, so it throws a specific exception that maps to 400 or 409.

301 or 302? A 301 (permanent) redirect lets browsers cache it, so later clicks never reach your server: less load, but your click counts become wrong and you cannot change or expire the link for those users. Use 302 (or 307) when analytics or expiry matter, which is our case. Saying this unprompted is a strong signal.

Cost of each operation

OperationCostWhy
shortenO(L) + expected O(1) retriesNormalise and validate the URL (L characters), hash it, then one saveIfAbsent. With a hash or random generator a collision costs one more attempt; while the store is far from full the expected number of attempts stays close to 1. The counter never retries.
shorten with dedupeO(L)One computeIfAbsent on (owner, url) before the claim.
resolveO(1)One hash lookup, an expiry compare, a LongAdder increment.
deleteO(1)Remove the dedupe entry, then the row.
purgeExpiredO(N)Scans all N links; a real system keeps an expiry index (a heap or a TTL column with an index).
topK(k)O(N log N)Our version sorts all N links by clicks and takes k. One pass with a size-k min-heap makes it O(N log k).
