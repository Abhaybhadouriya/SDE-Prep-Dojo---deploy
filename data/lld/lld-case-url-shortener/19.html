Quiz

Which code generator never collides with its own earlier codes?

  1. SHA-256 cut to 7 characters
  2. Counter encoded in base62
  3. Random 7 characters
  4. MD5 cut to 7 characters
Each counter value is used once, so the codes are unique. It can still meet a custom alias, which the atomic claim handles.

Why is if (!repo.exists(code)) repo.save(u) wrong under concurrency?

  1. It is slow
  2. It throws on duplicates
  3. Two threads can both pass the check and the second save overwrites the first
  4. It breaks base62
Check-then-act has a gap. Use one atomic operation: putIfAbsent, or an INSERT with a unique key.

A link with TTL 60 s is resolved exactly 60 s after creation (now == expiresAt). Our design returns:

  1. EXPIRED (410)
  2. FOUND (302)
  3. NOT_FOUND (404)
  4. It depends on the generator
The rule is expired when now >= expiresAt. Pick a rule, write it down, and test the boundary.

Analytics and expiry are requirements. Which redirect status fits?

  1. 301, so browsers cache it
  2. 200 with the page content
  3. 404 then retry
  4. 302, so every click reaches the server
A cached 301 skips the server: clicks go uncounted and expiry cannot take effect.

With random codes from a space of N and n codes already used, the chance a new draw collides is about:

  1. 1 / N
  2. n / N
  3. n2 / N
  4. 0, if the generator is good
Each used code is one of N equally likely outcomes. Over many draws the total grows like n2 / 2N (the birthday estimate).

Why does CodeGenerator.generate take an attempt number?

  1. For logging
  2. To limit the code length
  3. So a deterministic generator (a hash) can return a different code on retry
  4. Because Java requires it
Without it, a hash generator would return the same taken code forever. Counter and random generators simply ignore it.

Where does switching from memory to MySQL change the code?

  1. Only a new UrlRepository implementation

The repository interface isolates storage; saveIfAbsent becomes an INSERT with a unique key.
