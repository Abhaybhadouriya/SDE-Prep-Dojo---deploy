Concurrency and thread safety

  1. Claim, do not check-then-insert The classic bug is if (!map.containsKey(code)) map.put(code, u): two threads both see "free" and the second overwrites the first user's link. ConcurrentHashMap.putIfAbsent is one atomic step; in SQL the same job is a unique key on code and treating a duplicate-key error as "collision, retry".
  2. Counter AtomicLong.getAndIncrement(): every thread gets a different number without a lock.
  3. Dedupe under races Eight threads shorten the same new URL at the same moment. With "look up, then claim, then record" each could create its own code. We use codeByUrl.computeIfAbsent((owner, url), ...), which runs the claim once per key; the other seven threads wait for that one result. Demo 9 checks it: 8 racing calls, 1 code. (Keep the function short: it runs while that map bin is locked. In Python a lock around the check and insert does the same.)
  4. Delete vs dedupe delete touches two structures: the dedupe map (owner, url) -> code and the repository row. If it removed the row first, a shorten landing in between would get the old code from the dedupe map, find no row, and fail (an HTTP 500). So delete removes the dedupe entry first, and shorten also checks: if the code it got has no row, it drops that entry with codeByUrl.remove(key, code) (only if it still maps to that code) and claims again. Check 6c in the demo forces the stale state and shows a fresh code instead of an exception.
  5. Click counts Many threads click a hot link. clicks++ on a long field loses updates. LongAdder spreads increments over cells (like per-CPU counters) and sums on read: 8 threads x 1,000 clicks = exactly 8,000 in our run.
  6. Random generator java.util.Random is thread safe but contended; at scale use ThreadLocalRandom or SecureRandom per thread.
  7. Expiry needs no lock expiresAt is final. resolve checks it on every read (lazy), and purgeExpired removes entries with delete(code), which is atomic. A race between a purge and a click only decides whether that click lands just before or just after the delete; both are correct.

From your world

The repository's contract is "insert succeeds for exactly one caller": the user-space version of cmpxchg(&slot, NULL, new) (see concurrent collections and atomics for putIfAbsent, computeIfAbsent and LongAdder). Everything else (generation, validation) can run in parallel with no lock because it only reads immutable inputs. That shape (do the work outside, publish with one atomic step) is the same one RCU writers use: prepare the new object, then publish the pointer.
