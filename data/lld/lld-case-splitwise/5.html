Key relationships and patterns (and why each)

Pattern / choiceWhereWhy it earns its place
StrategySplitStrategy with Equal / Exact / PercentThe only part that varies between split types is "how to turn a total into shares". New type (SHARE 2:1:1, ADJUSTMENT) = new class, zero edits to the service. Kills the switch(type) that interviewers look for.
Simple factory / registrySplitStrategyFactory (an EnumMap)One place maps the enum to its strategy. Strategies are stateless, so one shared instance each is enough.
FacadeExpenseServiceThe driver, a command parser or a future REST controller all call the same five methods. Locking lives here too.
Single responsibilityBalanceSheet separate from the serviceThe sheet only knows debts; it can be unit tested alone and swapped for a DB-backed version (Repository).
Immutable value objectsExpense, Transfer, UserSafe to share between threads and to keep as history. An expense is a fact; to change one you add a reversing expense.
Observer (follow-up)ExpenseListenerNotify participants or update a group feed when an expense lands, without the service knowing about email or push. See extensibility.

Do not make Split a class hierarchy with one object per participant (EqualSplit(user), PercentSplit(user, 40)), the shape many tutorials use. It works, but then every split type needs its own validator and the service ends up with instanceof checks. One strategy per split type, returning a plain map, is smaller and easier to extend.
