Why not store amounts as double?

Binary floating point cannot represent 0.1 exactly, so repeated additions drift (0.1 + 0.2 is 0.30000000000000004). After a few hundred expenses a balance can show 249.99 instead of 250.00, and a hidden test fails. Store integer paise in a long (or BigDecimal with a fixed scale in Java). Convert from the user's decimal input once, at the edge.

How to answer

Name the problem (binary fractions), give the fix (minor units), and say where conversion happens (input boundary only).

Likely follow-ups
  • When would you pick BigDecimal over long?
  • What about currencies with 3 decimals (KWD)?
100 rupees split 3 ways: who pays the extra paisa?

Divide in paise: 10000 / 3 = 3333 remainder 1. Give the remainder, one paisa each, to the first remainder participants (or to the payer, if that is the agreed rule). The invariant to state and test: the sum of shares equals the total, always. The exact owner of the leftover is a product decision; pick one and keep it consistent.

How to answer

Which design patterns did you use and why?

Strategy for split types, because the division algorithm is the one thing that varies; a simple factory (EnumMap) to choose it; a Facade service for the driver and for locking; immutable value objects for Expense and Transfer. If asked about notifications, Observer. Do not list patterns you did not need: no Singleton for the service (inject it), no Builder for a 4-field object.

Explain simplify debts. Is your answer optimal?

Compute each person's net balance; the debts graph can be replaced by any set of payments with the same nets. Greedy: match the largest debtor with the largest creditor using two heaps, O(n log n), at most n-1 payments. It is not always the minimum count: the exact minimum equals n minus the maximum number of disjoint zero-sum subgroups, which is NP-hard in general. For a small group, backtracking over subsets gives the optimum (LeetCode 465).

How to answer

Nets first, then greedy with complexity, then the honest limit.

Likely follow-ups
  • Should simplify run automatically or on request? (On request: users want to see who they actually spent with.)
  • Within a group or across groups?
How do you make addExpense thread safe? What if traffic grows?

Today: one lock around validate-and-apply, so an expense lands atomically. Growth: partition by group with a lock per group ledger (lock striping); expenses never cross groups. In a DB: one transaction for the expense, its shares and balance rows, with an idempotency key so retries do not double count. Avoid per-pair locks unless you also enforce a global lock order.

How to answer

Name the race (read-modify-write on several entries), give the coarse fix, then the partitioned fix.

Likely follow-ups
  • Optimistic versioning on the group row instead of a lock?
  • How do you test it?
Design the database schema. Do you store balances or compute them?

Tables: users, groups, group_members, expenses (payer, total, type, request_id unique), expense_shares (expense, user, share). Balances can be derived with a GROUP BY over shares (always correct, slower) or kept in a balances table keyed by the sorted user pair and updated in the same transaction (fast reads, needs care). Start derived; add the table when reads hurt, and add a reconciliation job that recomputes from shares.

How to answer

Facts tables first, then the derived-vs-stored trade-off.

How would you support editing or deleting an expense?

Treat expenses as an append-only log. Delete = add a reversing expense with negated shares; edit = reverse plus the new version, linked by an originalId. The sheet stays the sum of all facts, history is auditable and concurrent readers never see a half-edited row. This is event sourcing in miniature.

How to answer

Say "never mutate money history", then the reversing entry.

Why does the expense keep computed shares instead of the raw percentages?

After validation, everything downstream (sheet, history, DB, notifications) only needs "user X consumed Y paise". Storing the computed shares means no other class must know split types, rounding happens once, and replaying history always gives the same balances even if the rounding rule changes later. Keep the type and raw values too, for display only.

How to answer

Decoupling plus reproducibility.

Likely follow-ups
  • What if the PM changes the rounding rule?
A user is in 50 groups with 10,000 expenses. "Show my balance" is slow. Fix it.

Do not recompute from expenses on every read. Keep the per-group sheet incrementally updated (as our code does), and keep a per-user summary (net per counterparty) updated in the same lock or transaction. Reads become O(counterparties). For the DB version, a materialized balances table or a cache keyed by user, invalidated on new expenses in their groups.

How to answer

Incremental aggregates instead of recomputation; mention where the consistency boundary is.
