Clarify the requirements

Spend the first 5-8 minutes here. Write the list where the interviewer can see it. It becomes your contract, and it protects you when the interviewer "flips" expectations later.

Functional (P0: must work in the demo)

  1. Users Add a user with id, name (email and phone are optional fields).
  2. Add expense One payer, an amount, a list of participants (the payer may or may not be one of them) and a split type: EQUAL, EXACT (amount per person) or PERCENT (percent per person).
  3. Validate EXACT amounts must add up to the total; percentages must add up to 100; all users must exist; amount must be positive. A bad expense changes nothing.
  4. Show balances For everyone, or for one user: lines like "User2 owes User1: 250.00". Show only non-zero balances; print "No balances" when there are none.
  5. Rounding Two decimals. When the total does not divide, the shares still add up to the total (100 / 3 = 33.34 + 33.33 + 33.33).

P1 (bonus, only after P0 runs)

  • Simplify debts: suggest a short list of payments that settles everyone.
  • Groups (trip, flat) with balances per group; settle up (record a payment); expense history per user; SHARE split (by ratio, 2:1:1).

Non-functional

  • Correct money: integer paise, never double for stored amounts.
  • Extensible: a new split type must not edit the service (Open/Closed).
  • Thread safe: two people adding expenses at the same moment must not corrupt the sheet.
  • In-memory only, no UI, no HTTP, a driver/main that demos everything (the standard machine-coding rule).

Out of scope (say it out loud)

Login, real payments, notifications, currency conversion, receipts and images, persistence. Mention you would add them behind interfaces later.

Questions to ask

  • Is the payer always one of the participants? (No; our code handles both.)
  • Who absorbs the rounding paisa? (We give it to the first participant listed; say this and keep it consistent.)
  • Should balances be netted? If A owes B 100 and B owes A 30, show "A owes B 70" only? (Yes, almost always.)
  • Input as method calls or as text commands? (If commands, write a tiny parser on top of the service; never mix parsing into the domain.)
  • Do we need groups in P0? Simplify debts in P0?
  • Are amounts and percentages allowed to have decimals (12.5%)? (Yes: we store percent as basis points.)
