Quiz

An expense of 100.00 is split EQUAL among 3 users. Which shares are correct?

  1. 33.33, 33.33, 33.33
  2. 33.333 each, stored as double
  3. 33.34, 33.33, 33.33
  4. Reject the expense
Shares must add up to exactly 100.00. 10000 paise / 3 = 3333 remainder 1, so one person gets 3334.

Which design keeps ExpenseService unchanged when a SHARE split is added?

  1. A switch on SplitType inside addExpense
  2. A SplitStrategy interface with one class per type, picked by a factory
  3. A boolean flag per split type
  4. Subclassing ExpenseService per split type
Strategy plus a registry: the new type is a new class and one registry entry.

A PERCENT expense has percentages 50, 20, 20, 5. What should happen to the balance sheet?

  1. Nothing: the expense is rejected before any update
  2. The first three shares are recorded, the rest skipped
  3. The shares are scaled up to 100%
  4. It is stored and flagged for review
Validate first, mutate second. Partial updates are the classic bug.

A owes B 250. Then A pays 1200, split PERCENT between A (60%) and B (40%). What does SHOW print for this pair?

  1. "A owes B: 250.00" and "B owes A: 480.00"
  2. "B owes A: 230.00"
  3. "A owes B: 730.00"
  4. "A owes B: 230.00"
A paid, so B now owes A his 40% share, 480. Netted against the old 250 that A owed B, B owes A 230. Two lines for one pair means you forgot to net; the wrong direction means you did not check who paid.

The greedy simplify-debts algorithm for n users produces at most how many payments?

  1. n squared
  2. n - 1
  3. log n
  4. Exactly the minimum possible
Each match settles at least one person, and the last one settles two. It is not always the minimum; the exact minimum is NP-hard.

Two threads call addExpense at the same moment on the same group. What is the simplest correct fix?

  1. Make the maps volatile
  2. Use ConcurrentHashMap for the inner maps only
  3. One lock around validate-and-apply for the whole expense
  4. Retry until the totals look right
One expense touches several entries; it must be applied atomically. A concurrent map makes single puts safe, not the whole multi-entry update.
