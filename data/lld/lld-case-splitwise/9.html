Concurrency and thread safety

What can go wrong: two threads add expenses at once. Each does read-modify-write on the same map entries (owed[u1][u2]), so one update can be lost, exactly like two CPUs doing counter++ without a lock (see races and atomicity). Worse, one expense touches several pairs, so a reader in the middle could see half an expense applied.

  1. Two expenses touch the same pair at once. Each reads 100, adds its share and writes back. The second write overwrites the first: a lost update, exactly like two CPUs doing counter++ without a lock.
  2. The guard: every public method of the service is synchronized, so one expense is applied completely (all its pairs) before the next starts.
  3. B runs after A, reads 150 and writes 180. Both expenses count, and a reader can never see an expense half applied. One lock per group is the next step when this gets busy.
  1. Start simple: one lock on the service Every public method is synchronized (Python: one threading.Lock). An expense is applied atomically, readers never see half of it. Throughput is fine for an interview and for one group's traffic. The Python test above runs 4 threads x 200 expenses and checks the exact total.
  2. Scale out: one lock per group Expenses never cross groups, so a ConcurrentHashMap<groupId, GroupLedger> with a lock inside each ledger lets different trips proceed in parallel. This is lock striping, the same idea as per-bucket spinlocks in a kernel hash table.
  3. Per-pair locks? Be careful An expense touching pairs (u1,u2) and (u1,u3) must hold several locks. Take them in a fixed order (sorted user ids) or you can deadlock, just like nested spin_lock calls taken in two orders (see deadlock). Usually not worth it.
  4. Retries and duplicates A mobile client that times out and retries must not add the expense twice. Accept a client-generated requestId and keep a set of seen ids (an idempotency key, as in the payment system design).
  5. In a database Insert the expense and its share rows and update the balance rows in one transaction; or skip a balance table and compute balances from shares with SUM, which removes the update race altogether at the cost of slower reads.

From your world

The "validate everything, then apply" order is the same discipline as a netlink handler that parses and checks every attribute before taking rtnl_lock and changing state. Doing checks under the lock is fine; mutating before the last check is not.

Java volatile is not C volatile. In C, volatile only stops the compiler from caching the value; it says nothing about other CPUs. In Java, a volatile field gives visibility and ordering between threads: a write behaves like smp_store_release() (a WRITE_ONCE plus a release barrier) and a read like smp_load_acquire(), so everything written before the volatile write is visible to a thread that reads the new value. It does not make count++ atomic and takes no lock: use an AtomicLong or a lock for that. Details in Concurrency basics: volatile.

From your world: the Java primitives on this page

  • synchronized = a mutex built into every object: locked on entry, unlocked on every exit path, exceptions included (a scoped mutex_lock/mutex_unlock).
  • ConcurrentHashMap, computeIfAbsent, putIfAbsent = a hash table with per-bucket locking; computeIfAbsent is find-or-insert under the bucket lock, putIfAbsent inserts only if the key is absent, atomically.
  • Python threading.Lock = a plain mutex; with lock: is lock and unlock on every exit path.
