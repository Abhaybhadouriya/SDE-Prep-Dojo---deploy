Concurrency and thread safety

Unlike a cricket scorer, a task board has many writers: a whole team edits, moves and plans at the same time. Three problems to name and solve:

  • Races inside the board (two creates getting the same key, a sprint close running while someone moves an issue). Fix: one lock per board, held for the whole write template. Key generation (nextNumber++) is inside it. Different boards run fully in parallel. The Java test runs 8 threads creating and moving 2,000 issues on one board and checks 2,000 unique keys and exactly 4,000 events.
  • Torn reads (a search sees the new status but the old version). Fix: readers copy IssueViews under the lock, then filter and sort outside it, so the lock is held only for the copy.
  • Lost updates (two browser tabs load v1; the second save silently overwrites the first). A lock cannot fix this, because the two saves are seconds apart and each one is atomic. Fix: optimistic concurrency. The client sends the version it loaded; the server refuses if it changed.
  1. Alice and Bob both open PAY-3 and see version 1.
  2. Alice saves a new title with "expected v1". It matches, so the change is applied and the version becomes 2.
  3. Bob saves a new priority with "expected v1". The issue is now v2, so the server refuses with StaleUpdate (HTTP 409 or 412).
  4. Bob's screen reloads v2, he sees Alice's title, re-applies HIGH, and the issue becomes v3. Nothing was silently lost.
  • Listeners outside the lock. Events are collected during the write and delivered after unlock. A slow or failing webhook never holds the board, and a refused write delivers nothing (test 10).
  • Lock order. Every operation takes exactly one board lock, so there is no lock-ordering deadlock. The one cross-board read (activityOf) takes the locks one at a time, never two at once. If you add "move issue to another board", lock both boards in key order.
  • In a database the same ideas become a conditional update (WHERE version = ?), a unique index on the issue key, and the audit insert in the same transaction as the change.

From your world

The version check is compare-and-swap at the application level: "store the new value only if the old one is what I read", exactly cmpxchg, or a seqlock reader that retries when the sequence moved. Per-board locks instead of one global lock is the Big Kernel Lock story: the BKL was removed in favour of fine-grained locks so unrelated work stops serialising. And "collect events in the lock, deliver after unlock" is how you avoid calling a notifier chain while holding a spinlock.
