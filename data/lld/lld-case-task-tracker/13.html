Evaluator rubric checklist

  • Runs: one command plays the demo; refusals print clear reasons instead of stack traces.
  • Requirements: every action of the statement exists and every action is logged.
  • Model: status as configurable data, subtasks as a parent link, stats or views derived, not duplicated.
  • Separation: rules in guards, side effects in listeners, queries in predicates, the facade only orchestrates.
  • Validation: membership, existence, workflow and guards are checked before any mutation.
  • Concurrency: a lock per board, immutable views, a version check; you can explain lost updates.
  • Tests: the edge cases above, deterministic thanks to the injected clock.
  • Review readiness (PhonePe style): no brute-force loops you cannot defend (for example, look up by key in a map, not by scanning a list).
