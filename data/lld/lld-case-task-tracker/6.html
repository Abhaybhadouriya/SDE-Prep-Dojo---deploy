Core flow: moving an issue

Here is move("PAY-1", carol, DONE) from the demo. The first attempt is refused because subtask PAY-4 is still open; after PAY-4 is done, the same call succeeds. Step 4 shows the refusal, step 5 onward the success.

  1. The client (console, test or REST controller) calls move with the key, the actor and the target status.
  2. TaskTracker finds the board from the key prefix (PAY) and takes the board lock. Inside it, the first check is membership.
  3. The workflow table is asked: is IN_REVIEW to DONE a legal move? Yes. (TODO to DONE would be refused right here.)
  4. Each guard runs. "subtasksDone" finds PAY-4 still open and returns a reason; TaskTracker throws TransitionDenied. Nothing was changed and no event was written.
  5. Later, PAY-4 is done. This time every guard returns null (no objection).
  6. Only now does the state change: append a MOVED event to the board log, set the status, bump the version. Then unlock.
  7. Listeners receive the event after the lock is released, so a slow notifier cannot stall other users.

Every other write follows the same template: lock, check membership, validate everything, then mutate and log, unlock, notify. Validation before mutation makes each operation all-or-nothing without needing a rollback.

Sprint close

  1. Check the sprint is ACTIVE (a PLANNED or CLOSED sprint cannot be completed).
  2. Split its issues into done and not done, using the board's workflow (isDone), not a hard-coded "DONE" string.
  3. Carry over each unfinished issue to the backlog; its subtasks follow; log a SPRINT event per issue.
  4. Close the sprint; it is now frozen (adding to it is refused).

The two classic bugs: letting a parent reach DONE while a subtask is open (the guard fixes it), and writing the audit log from the caller or a listener, so one code path forgets it or a crash between "change" and "log" loses the record. Putting the log inside the locked write template makes both impossible.
