Interview follow-ups (Q&A)

Why is status a string in a table and not an enum or a State class?

Because statuses are configured per board. A to-do list has two, a Scrum board four, and a team that adds "QA" should not need a release. An enum hard-codes them; one State class per status hard-codes them too and adds classes that have no behaviour. A transition table keeps the state machine (illegal moves are still refused) and makes it data. If a state ever needs its own behaviour (say "Blocked" pauses an SLA timer), that behaviour goes into a listener or guard keyed by the state.

How to answer

Contrast "states that behave differently" (State pattern) with "states that only restrict moves" (table).

Likely follow-ups
  • How would an admin edit a workflow already in use? (Version the workflow; issues in a removed state need a mapping.)
Every action must be logged. Where does the logging happen?

Inside the facade's write template, in the same critical section as the change: validate, mutate, append the event. Not in the caller (someone forgets) and not in a listener (a failing listener loses the record, and listeners run after the lock). The log is append-only and survives deletion of the issue.

How to answer

Name the failure you prevent: "a change without a log line must be impossible".

Likely follow-ups
  • The log grows forever. Now what? (Archive by age to cold storage; keep an index by issue.)
How do you model subtasks, and what happens when the parent is removed?

A subtask is an Issue with type SUBTASK and a parentKey; the parent keeps a list of child keys. One level deep, so nesting is refused. Removing a parent removes its subtasks (and logs each); removing a subtask detaches it from the parent. A guard prevents the parent from reaching a done state while any child is open, and subtasks follow the parent's sprint.

How to answer

State the invariants (no grandchildren, parent done implies children done) and show where each is enforced.

Likely follow-ups
  • Allow any depth. (Composite; the guard and the cascade become recursive; watch for cycles if re-parenting is allowed.)
Design the filters so any combination works.

Each criterion is a small predicate over IssueView: status, assignee, priority at least, label, text, sprint. They combine with and, or and negate (the Specification pattern; in Java just Predicate). Search copies views under the lock, filters and sorts outside it. Six predicates cover every combination without a method per query.

How to answer

Show one composed query, then say how it maps to SQL: each predicate can also render a WHERE fragment.

Likely follow-ups
  • Filtering a million issues is slow. (Indexes by status and assignee in the store; push the predicate down to SQL or a search index.)
Two users edit the same issue at the same time. What happens?

Each save is atomic under the board lock, so the data is never corrupted. But the second save could silently overwrite the first one's change (a lost update). I prevent that with a version number: the client sends the version it loaded, and the server refuses with StaleUpdate (409 or 412) if it changed. The client reloads and re-applies. For fields that never conflict (adding a label), the check can be skipped.

How to answer

Separate "atomic" (locks) from "not lost" (versions). Interviewers listen for that distinction.

Likely follow-ups
  • Why not lock the issue while someone has it open? (Pessimistic locks held across user think-time block others and leak when tabs are closed.)
Why one lock per board and not per issue or a global lock?

A global lock serialises unrelated teams. Per-issue locks are too small: creating an issue bumps the board's counter, a sprint close touches many issues, and the log is per board, so you would need several locks and an ordering rule. The board is the natural consistency boundary (the aggregate), so one lock per board is simple and correct, and boards run in parallel.

How to answer

Pick the smallest unit that contains every invariant you must keep together.

Likely follow-ups
  • One huge board is hot. (Read-write lock, or move to the database's row-level locking with version checks.)
How would you add notifications without touching the tracker?

Implement TrackerListener: it receives every event after the write has committed and the lock is released. A notifier filters for ASSIGNED and MOVED and sends to the assignee and watchers. In production, the listener puts the event on a queue so delivery retries never slow the write path.

How to answer

Mention "after the lock" and "refused writes notify nobody".

Likely follow-ups
  • The process crashes after the write, before the notification. (Outbox: store the event with the change; a relay delivers it at least once.)
Complete a sprint. What exactly happens to the issues?

Only an ACTIVE sprint can be completed. Issues whose status is a done state of the board's workflow stay in the closed sprint (that is the record of what was delivered). The rest go back to the backlog (or to a target sprint, as a follow-up), their subtasks follow, and each move writes a SPRINT event. The closed sprint is frozen.

How to answer

Use the workflow's isDone, not the literal "DONE", so custom workflows work.

Likely follow-ups
  • Velocity per sprint? (Sum the story points of done issues; another read over the closed sprint.)
Can you rebuild an issue's state from its history? Should you?

Yes, because each event records the field, old value and new value, so replaying a board's events in sequence order rebuilds it (event sourcing). It also makes "show the board as of last Monday" and "undo" easy. But I keep current state as the source of truth for reads and use the log as an audit trail; full event sourcing adds snapshots, schema versioning of events and replay time. I would switch only if time-travel queries were a core requirement.

How to answer

Show you know the option and its cost; choose deliberately.

Likely follow-ups
  • A user asks to erase their data (GDPR) but the log is append-only. (Store user ids, not names; crypto-shred or redact the user record.)
Support custom workflows per issue type (bugs need a "Verified" step).

Change the board's single workflow into a map from issue type to workflow, with a default. move looks up the workflow by the issue's type; everything else (guards, the done check, the log) stays the same. Board columns are then the union of states, or one swimlane per type.

How to answer

Show the change is one lookup because the workflow was already data.

Likely follow-ups
  • Changing a type with a status that does not exist in the new workflow. (Require a status mapping, like Jira's migration screen.)
