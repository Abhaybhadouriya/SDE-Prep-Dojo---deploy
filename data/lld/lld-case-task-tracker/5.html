Patterns we deliberately skipped: the classic State pattern with one class per status (statuses are configurable and have no behaviour of their own; State pays off when each state behaves differently, like a vending machine), Composite for subtasks (one level deep, so a list of keys is enough), and a Singleton tracker (tests create a fresh one each time). Also not a listener: the audit log. If the log were an observer, a failing listener could lose an audit record; instead it is written inside the same lock as the change.

From your world

A table-driven state machine is how netfilter conntrack and many protocol stacks are written: a 2-D table indexed by (current state, input) gives the next state, and illegal combinations are rejected without any per-state code. Choosing "table plus guard hooks" over "one ops struct per state" is the same trade-off you make in C: an ops table per state (the State pattern) is worth it when states have different behaviour; when they only differ in which moves are legal, a table is shorter and can be loaded from configuration.

Why the pattern earns its place: the if-ladder it replaces

Without guard objects, every workflow rule is another if inside move:

void move(String key, String actor, String to) {
    Issue i = issue(key);
    if (!workflow.allowed(i.status, to)) throw new TransitionDenied(i.status + " -> " + to);
    if (to.equals("IN_PROGRESS") && i.assignee == null)
        throw new TransitionDenied("needs an assignee");
    if (to.equals("DONE") && i.subtasks.stream().anyMatch(s -> !s.done))
        throw new TransitionDenied("subtasks open");
    if (to.equals("DONE") && board.id.equals("PAY") && i.reviewer == null)   // follow-up:
        throw new TransitionDenied("needs review");                         // edits move()
    i.status = to;
}
interface TransitionGuard {
    Optional<String> refuse(Issue i, String to, Board b);   // empty = allowed
}
// per board: b.guards.add(Workflow.needsAssignee("IN_PROGRESS"));
for (TransitionGuard g : b.guards)                     // inside move(), under the board lock
    g.refuse(i, to, b).ifPresent(r -> { throw new TransitionDenied(r); });

With the ladder, the follow-up "PAY board needs a reviewer before DONE" edits TaskTracker.move for every board. With guards it is one new guard added to one board; move is unchanged.

From your world: the same move in C

struct guard { const char *(*refuse)(const struct guard *g, const struct issue *i, const char *to); };
/* like netfilter hooks: for (k = 0; k < b->nguards; k++)
       if ((why = b->guards[k]->refuse(b->guards[k], i, to))) return deny(why); */

The "after" version is an ops table: the caller holds a pointer to a struct of function pointers and never asks which implementation it has, exactly as the VFS calls file->f_op->read() without a switch on the file system type.
