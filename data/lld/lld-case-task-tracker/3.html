Identify entities: nouns, verbs and what changes

Underline the nouns (candidate classes) and the verbs (candidate methods), ask which parts the interviewer will vary, and cross out the nouns that are only values. Click through.

  1. Nouns: Board (members, issues), Issue (story, task, bug, subtask), Sprint, Workflow (statuses and moves) and Event (one line of the activity log).
  2. Verbs: create, assign and edit go through one facade; "move" asks the workflow table and the guards; sprints have their own tiny lifecycle; search runs filters; history reads the log.
  3. What changes: each team wants its own statuses (so the workflow is data), its own move rules (guards), its own notifications (listeners) and new filters (one predicate each).
  4. Not a class: a status is a string inside the workflow; a Trello list is a status; the backlog is "sprint = null"; a board column is a view computed from statuses.

The two modelling choices that decide the interview:

  • Status is data, not a type. If statuses were an enum (or one State class per status), every team that wants "QA" between "Review" and "Done" would need a code change. Jira lets admins draw their own workflow, so the honest model is a transition table per board. We still get a state machine; it is just table-driven.
  • The board is the unit of consistency. Issues, sprints and the log of one board change together (a sprint close touches many issues and writes many events), so one lock per board covers them. Different boards never share mutable state and run in parallel.

Should Subtask be a subclass of Issue? Say: "No. A subtask has the same fields and the same workflow. The difference is a parent key and two rules (no grandchildren, it follows its parent's sprint), so it is a type value plus checks, not a class." That is composition over inheritance in one sentence.
