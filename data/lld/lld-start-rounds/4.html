Archetype B: the machine-coding round

This is the round most common at Indian product companies. You receive a written problem statement (often two pages, with P0 requirements and "bonus" features) and must produce a working program in 90-120 minutes. No database, no UI, no HTTP: in-memory data structures and a main (driver) that demos the flows. Later, in a separate call, an engineer reads your code, runs it, and asks you to explain or extend it.

  1. Walkthrough. In Flipkart group drives, 20-60 candidates join a call; the problem is explained and questions are taken. Read everything; note which items are P0 and which are bonus.
  2. Plan. List entities, enums and the service class; decide the in-memory maps. Ten minutes of planning saves forty of rewriting.
  3. Code. Build P0 end to end first, then bonus. Compile and run often. Some rounds have a checkpoint where the interviewer looks at progress.
  4. Upload. Zip and send. Include the driver and a short README of how to run it.
  5. Evaluation. A separate call, sometimes the same day, sometimes 1-2 days later. They run your code, ask why you chose each class, and often ask for a small extension.

What reports and official briefs say:

  • Flipkart (25 reports, all machine coding): 90-120 minutes, any language, own IDE, AI tools forbidden in 2026 drives. A 2026 problem brief lists the evaluation criteria as demoable and correct code, readability, entity modelling, modularity and extensibility, separation of concerns, abstractions, exception handling and comments (report).
  • PhonePe (21 reports): 90 minutes live or a 1-day / 24-hour take-home, then a 30-45 minute review on patterns, extensibility, concurrency and thread safety. One candidate describes a 2-hour CodeSignal round with nobody watching and a 30-minute review 1-2 days later (report).
  • Razorpay (18 reports): 90-120 minutes on screen share with an interviewer present; some 2026 rounds allow AI tools and grade how you steer and check them.
  • Meesho, Groww, CRED: 60-120 minute variants; Meesho sometimes uses HackerRank with pre-written tests.

The workat.tech guide to the Flipkart format describes the same three phases: about 15 minutes before coding to understand the problem, about 90 minutes of coding, and about 15 minutes after to demo while the interviewer runs test cases (repo).

What "done" means here: a program someone else can run

Here is the shape the evaluator hopes to open: an enum, entities, a custom exception, an in-memory repository, a service with validation, and a driver that demos every P0 flow and checks itself.

New to the Java syntax below? Keep Reading Java as a C programmer open: it maps generics, lambdas, record, synchronized and List.of onto C ideas you already know.

public class Driver {
    public static void main(String[] args) {
        ClassRepository repo = new ClassRepository();
        repo.save(new FitClass("yoga-7am", "Yoga", 2));
        BookingService svc = new BookingService(repo);

        System.out.println("asha  -> " + svc.book("asha", "yoga-7am"));
        System.out.println("ravi  -> " + svc.book("ravi", "yoga-7am"));
        System.out.println("meena -> " + svc.book("meena", "yoga-7am"));
        try { svc.book("asha", "yoga-7am"); }
        catch (BookingException e) { System.out.println("error: " + e.getMessage()); }

        svc.cancel("ravi", "yoga-7am");
        System.out.println("after ravi cancels: " + svc.attendees("yoga-7am"));

        // self-checks the evaluator can run (java -ea Driver)
        List<String> now = svc.attendees("yoga-7am");
        if (!now.equals(List.of("asha", "meena"))) throw new AssertionError("waitlist promotion failed: " + now);
        System.out.println("all checks passed");
    }
}

enum BookingStatus { CONFIRMED, WAITLISTED, CANCELLED }

final class FitClass {
    final String id; final String name; final int capacity;
    final List<String> booked = new ArrayList<>();
    final Deque<String> waitlist = new ArrayDeque<>();
    FitClass(String id, String name, int capacity) { this.id = id; this.name = name; this.capacity = capacity; }
}

class BookingException extends RuntimeException {
    BookingException(String msg) { super(msg); }
}

final class ClassRepository {                       // in-memory store: no DB in machine coding
    private final Map<String, FitClass> byId = new HashMap<>();
    void save(FitClass c) { byId.put(c.id, c); }
    FitClass get(String id) {
        FitClass c = byId.get(id);
        if (c == null) throw new BookingException("no such class: " + id);
        return c;
    }
}

final class BookingService {
    private final ClassRepository repo;
    BookingService(ClassRepository repo) { this.repo = repo; }

    // synchronized = take this object's mutex for the whole method
    // (like mutex_lock(&svc->lock) ... mutex_unlock(&svc->lock)); one coarse lock: simplest safe choice
    synchronized BookingStatus book(String user, String classId) {
        FitClass c = repo.get(classId);
        if (c.booked.contains(user) || c.waitlist.contains(user)) throw new BookingException(user + " already in " + classId);
        if (c.booked.size() < c.capacity) { c.booked.add(user); return BookingStatus.CONFIRMED; }
        c.waitlist.addLast(user);
        return BookingStatus.WAITLISTED;
    }

    synchronized void cancel(String user, String classId) {
        FitClass c = repo.get(classId);
        if (c.waitlist.remove(user)) return;
        if (!c.booked.remove(user)) throw new BookingException(user + " has no booking in " + classId);
        String next = c.waitlist.pollFirst();       // promote the first waitlisted user
        if (next != null) c.booked.add(next);
    }

    synchronized List<String> attendees(String classId) { return List.copyOf(repo.get(classId).booked); }
}
class BookingService:
    def __init__(self, repo: ClassRepository) -> None:
        self._repo = repo
        self._lock = Lock()

    def book(self, user: str, class_id: str) -> BookingStatus:
        with self._lock:
            c = self._repo.get(class_id)
            if user in c.booked or user in c.waitlist:
                raise BookingError(f"{user} already in {class_id}")
            if len(c.booked) < c.capacity:
                c.booked.append(user)
                return BookingStatus.CONFIRMED
            c.waitlist.append(user)
            return BookingStatus.WAITLISTED

    def cancel(self, user: str, class_id: str) -> None:
        with self._lock:
            c = self._repo.get(class_id)
            if user in c.waitlist:
                c.waitlist.remove(user)
                return
            if user not in c.booked:
                raise BookingError(f"{user} has no booking in {class_id}")
            c.booked.remove(user)
            if c.waitlist:
                c.booked.append(c.waitlist.popleft())

def main() -> None:
    repo = ClassRepository()
    repo.save(FitClass("yoga-7am", "Yoga", 2))
    svc = BookingService(repo)
    for u in ("asha", "ravi", "meena"):
        print(f"{u:5} -> {svc.book(u, 'yoga-7am').value}")
    svc.cancel("ravi", "yoga-7am")
    assert svc.attendees("yoga-7am") == ["asha", "meena"], "waitlist promotion failed"
    print("all checks passed")

In a real round you would split this into packages (model/, repository/, service/, exception/) - see Machine-coding code layout. synchronized on a method means "take this object's mutex for the whole method": every book, cancel and attendees call on the service runs under one lock, like a struct mutex embedded in the service struct (more in Locks). That single lock is a deliberate first choice: simple and correct. In the review you can explain how you would narrow it to one lock per class (see Preventing double booking).

From your world

A machine-coding round is a small driver bring-up with a demo at the end. You would never hand a driver to QA without a test harness that loads it and exercises open/read/write/ioctl. The Driver.main() is that harness. And just as you get the basic data path working before tuning interrupt coalescing, you get P0 running end to end before touching bonus features.
