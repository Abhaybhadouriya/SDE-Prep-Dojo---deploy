Interview questions about the round itself

In a 90-minute machine-coding round, what do you do if you will not finish all requirements?

Finish P0 end to end so the driver runs, even with simple logic. Leave bonus features out rather than half-written. Where a better design is planned but not done, leave a short comment ("this would be a PricingStrategy interface"). A running core with clean seams scores better than an ambitious design that does not compile.

How to answer

Show prioritisation: P0 list, then checkpoints ("by minute 45 booking works, by 70 cancellation and waitlist, then bonus").

Likely follow-ups
  • How do you show the evaluator what is missing? (README with a "not done" list.)
  • How would you add the bonus now?
The interviewer says "Design a vending machine" and nothing else. What are your first three minutes?

Ask scoping questions and write the answers: which products and payments (coins, notes, card), refunds and change, what happens when out of stock, single machine or a fleet, any admin operations (restock, price change), concurrency (one user at a time?). Then read back a short P0 list and an out-of-scope list and get a nod.

How to answer

Requirements are often withheld on purpose in Amazon reports. Clarifying is part of the grade, not a delay.

Likely follow-ups
  • Which pattern models the machine's modes? (State.)
  • How would you add card payments later? (Strategy.)
Your part-1 solution works. The interviewer adds a rule that breaks your data structure. What do you do?

Say what has to change and why, then change the smallest unit: replace the structure behind its interface (for example a list behind a repository method becomes a sorted map), keep public method signatures, and rerun part-1 tests. If a rewrite is really needed, say so and estimate it before starting.

How to answer

Talk while refactoring. The interviewer grades how you reason about change as much as the result.

Likely follow-ups
  • What would you have done differently in part 1 if you had known?
  • Now make it thread-safe.
In the evaluation call, the reviewer asks "How would you make this production-ready?" What do you cover?

Swap the in-memory repository for a database-backed one behind the same interface; add proper concurrency control (row locks or optimistic versioning for bookings); move configuration (capacity, fees) out of code; add logging and metrics; split modules into services only if they scale differently; add unit tests per service.

How to answer

Point at your seams: "Because BookingService depends on ClassRepository, I can add a SQL implementation without touching the service."

Likely follow-ups
  • Which database and why?
  • Where would you put a cache?
The round allows AI assistants. How do you use them without hurting your evaluation?

Design first yourself: requirements, entities and interfaces. Then use the assistant for boilerplate (getters, test scaffolding, parsing), and review every generated line out loud. Point out and fix anything wrong. Interviewers in these rounds report grading how you steer and check the tool, not how much code it produced.

How to answer

Make the design decisions visibly yours; treat AI output like a junior's pull request.

Likely follow-ups
  • The AI wrote a non-thread-safe singleton. Spot the bug.

Scenario: you prepared diagrams, they wanted running code

A Microsoft-style LLD round opens with "Implement a parking lot; we will run a few test cases at the end." You have practised only class diagrams.

Spend 25 minutes drawing a full UML diagram with every vehicle subtype, then start coding with 20 minutes left and finish half the classes.

Spend 5 minutes on requirements and a quick sketch of 4-5 classes, then code the core (ParkingLot, Spot, Ticket, park/unpark) with a tiny driver. Run it by minute 35. Then add fee strategy and vehicle types. Mention the lock on spot allocation.

Likely follow-ups
  • Two cars request the last spot at once.
  • Add electric charging spots.
