Concurrency and thread safety

This is the review call's favourite topic. The races to name:

  • Double assignment of one issue: two threads call assignIssue("I7"); both see OPEN; both pick an agent. The issue ends up in two places.
  • Two issues for one agent: two threads assign different issues; both see a1 free; both call start(). a1 now "works on" two issues and one is lost.
  • Resolve versus assign: a1 resolves and pops its waitlist while another thread enqueues onto it. With an unsynchronised ArrayDeque the new id can vanish.

All three are check-then-act on shared state, the same bug as two CPUs doing if (!busy) busy = 1; without a lock (see races and atomicity).

  1. Start simple: one lock on the service Every public method is synchronized (Python: one RLock). Check-and-act happens atomically, and the strategy runs under the lock so it sees a consistent "who is free" view. The Java demo and the Python test run 8 threads x 50 assignments and prove exactly 5 issues are in progress. For a help desk (hundreds of assignments a second at most) this is enough, and it is what you should submit.
  2. Make the strategy's own state safe RoundRobin keeps a counter map. It is safe here only because it is called under the service lock; say so in a comment. If strategies may be called from elsewhere, use an AtomicInteger per type.
  3. Scale: stripe by issue type Agents can span types, so per-type locks are tricky: assigning a GOLD issue to a1 and a PAYMENT issue to a1 at the same moment touches the same agent. Either lock per agent (take the agent's lock after picking, re-check it is still free, retry if not: optimistic) or keep one lock but make it short.
  4. Optimistic claim With per-agent locks or a compare-and-set on agent.currentIssue (AtomicReference.compareAndSet(null, issueId)), the flow becomes: pick candidate, try to claim, on failure pick again. This is lock-free in the same spirit as cmpxchg on a slot, and it is the answer to "how would you avoid a global lock?".
  5. Reads during writes getIssues holds the lock while it copies the matching issues, so it never sees half an assignment. For heavy reads, a read-write lock (ReadWriteLock) lets many searches run in parallel, or return immutable snapshots.
  6. In a database UPDATE agents SET current_issue = ? WHERE id = ? AND current_issue IS NULL and check the row count: the database does the compare-and-set. Waitlist rows get a sequence number per agent; popping is SELECT ... WHERE agent_id = ? ORDER BY seq LIMIT 1 FOR UPDATE, a plain FOR UPDATE that waits for the head row. Do not add SKIP LOCKED here: if the head row is locked by another transaction, SKIP LOCKED silently returns the second row, which breaks FIFO order and can hand out item 2 while item 1 is rolled back. SKIP LOCKED is right for a shared pool of unassigned issues that many workers pull from, where order between workers does not matter.

From your world

"Pick under the lock, then claim" is the run-queue balancing problem: picking an idle CPU and enqueueing a task must be atomic with respect to that CPU's run-queue lock, or two wakeups pick the same idle CPU. The kernel takes the target rq lock and re-checks; you take the agent lock and re-check.
