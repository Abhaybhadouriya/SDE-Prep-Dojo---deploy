Interview follow-ups

Walk me through what happens when two threads call assignIssue at the same time.

Both methods are synchronized on the service, so they run one after the other. The first checks the issue is OPEN, collects experts, asks the strategy, and either starts the issue on a free agent or enqueues it, all before releasing the lock. The second then sees the updated state: if it was the same issue, it is no longer OPEN and is rejected; if it was a different issue, the agent the first one took is no longer free. Without the lock, both could see the same agent free and give it two issues.

How to answer

Name the check-then-act race, show where the lock is, then prove the invariant with the concurrent test.

Likely follow-ups
  • Can you avoid a global lock? (Per-agent CAS claim with retry.)
  • Is the strategy thread safe on its own?
Why is the assignment rule a Strategy and not a method with a switch?

The statement says "based on different strategies; for now any free agent", which is a direct hint that the rule will change. With an interface, a new rule (least loaded, highest rated, round robin) is a new class and a constructor argument; the service, its locking and its tests are untouched. A switch would grow with every rule and force a retest of the whole service each time.

How to answer

Quote the hint, name Open/Closed, then write LeastLoaded in two minutes.

Likely follow-ups
  • How would you pick the strategy at runtime per issue type? (A map from type to strategy.)
Why not a full State pattern class per issue status?

The four statuses differ only in which moves are legal; none has its own behaviour. An enum with a transition table gives the same safety (one place rejects illegal moves) in ten lines. I would switch to State classes when statuses start to behave differently, for example REOPENED starting an SLA timer or ESCALATED notifying a supervisor, because then the per-state code would otherwise become switches across the service.

How to answer

Show you know the pattern and the threshold for using it.

Likely follow-ups
  • Draw the state diagram with REOPENED added.
Per-agent waitlists or one global queue: which is better?

Per-agent waitlists are simple and match the 2022 statement, but a customer can be stuck behind a slow agent while another expert becomes free. A global queue per issue type is fairer: whichever expert frees up first takes the oldest waiting issue of a type they know. The cost is a scan over the agent's expertise types on each resolve (tiny). I would offer per-agent for the take-home and say the global queue is the production choice.

How to answer

Name the fairness problem (head-of-line blocking), then the trade-off.

Likely follow-ups
  • An agent knows PAYMENT and GOLD. Which queue does it take from first? (Oldest issue across both, or a priority.)
How does getIssues(filter) stay open for new filters?

The service takes a Predicate<Issue>. IssueFilters has small factory methods (byEmail, byType, byStatus, byAgent) and Java's and / or / negate compose them. A new filter, say "created in the last hour", is one more factory method; the service does not change. If the statement's map input is required, a tiny adapter turns each map key into a predicate.

How to answer

Specification pattern in one sentence, then the composition example.

Likely follow-ups
  • Search is slow with a million issues. (Index maps by email and by status, kept in sync on every change.)
Search by email is O(n). Make it fast.

Add secondary indexes: Map<email, List<issueId>> and Map<status, Set<issueId>>. Update them in the same locked section as the change (create adds to both; every moveTo moves the id between status sets). The filter API stays; the service picks the most selective index first and applies the remaining predicates to that subset. In a DB this is an index on (customer_email) and (status, type).

How to answer

Index plus "kept in sync inside the same critical section".

Likely follow-ups
  • What if the index update fails halfway?
Add customer reviews and incentives for agents. What changes?

Add an observer: interface IssueListener { void onResolved(Issue i, Agent a); }, registered on the service and called after the lock is released so slow work (email, rating prompts) does not block assignment. A review store records the customer's score per agent; an incentive calculator reads resolved counts and average scores per month. None of this touches assignment. A "highest rated agent first" strategy can then read the review store.

How to answer

Observer for side effects, a separate component for the numbers, Strategy if the numbers affect routing.

Likely follow-ups
  • How do you compute monthly averages? (See the rating system case.)
An agent leaves mid-shift with five issues in their waitlist. What happens?

Mark the agent unavailable (strategies skip them). Under the lock, move the current issue and every waitlisted issue back to OPEN (add those transitions to the table, or add a REQUEUED status), clear the agent's queue and call assignIssue for each in their original order so they keep their place relative to each other. History stays with the agent.

How to answer

State changes, the order you preserve, and that it is atomic.

Likely follow-ups
  • Should a half-worked issue keep its notes? (Yes; only the agent link is cleared.)
How would this scale to millions of issues and thousands of agents?

Move state to a database and the waiting work to a queue per issue type. Agents' clients long-poll or receive pushes. Assignment becomes an atomic claim: UPDATE agents SET current_issue = ? WHERE id = ? AND current_issue IS NULL, retried on a zero row count. Partition by issue type (separate queues and worker pools) since types rarely share agents at scale. This is the support chat and agent routing HLD.

How to answer

DB as the source of truth, atomic claim, queues per type, then link to HLD.

Likely follow-ups
  • How do you make createIssue idempotent? (Unique key on transaction id plus issue type.)
Why do agents keep issue ids rather than Issue objects?

The service owns the issues; the agent only refers to them. Ids avoid two owners, keep Agent small and serialisable, and match how the data would sit in a database (a foreign key). The cost is one map lookup when the service needs the issue, which is O(1).

How to answer

Ownership in one sentence, then the DB analogy.

Likely follow-ups
  • Would you ever store the object? (In a cache-friendly read model, yes.)
