How it is asked

Before you start: this case assumes OOP from C structs (objects as structs with an ops table) and interfaces vs abstract classes. The patterns it uses are explained on their own pages: Strategy, State, Specification, Facade. The per-agent queue is the producer-consumer shape.

This is a PhonePe problem first and last. It appears in our list four times since 2025 and in older posts going back to 2022, always as Round 1: a 90-minute machine-coding exercise (on CodeSignal, HackerEarth or your own IDE, then zipped and emailed), followed a day or two later by a 30-minute review call where the interviewer reads your code and asks about design patterns, extensibility and, almost every time, concurrency. Older shares of the same statement (LC 2569029, 2022, and LC 5189947, 2024) show one wording difference that matters: in the 2022 version, when every agent is busy the ticket goes onto the waiting list of an agent, to be picked after that agent's current ticket is resolved; the 2025 version just says the system marks it waiting. Our design supports the per-agent waitlist, which satisfies both readings. The function list in the statement, in decreasing order of importance, is:

createIssue(transactionId, issueType, subject, description, email)
addAgent(agentEmail, agentName, List<issueType>)
assignIssue(issueId)          // for now, assign to any one of the free agents
getIssues(filter)             // e.g. getIssues({"email": "testUser2@test.com"})
updateIssue(issueId, status, resolution)
resolveIssue(issueId, resolution)
viewAgentsWorkHistory()       // list of issues each agent worked on

The statement's evaluation criteria are spelled out: completeness of functional requirements, OO design principles, code efficiency, readability and maintainability, testability, corner cases and language proficiency. It also says in-memory data structures only, no REST, no third-party libraries, hard-coded input in a driver, and "a partial solution submitted on time is better than a complete solution submitted after time".

Two lessons from these posts. The functions are ordered by importance, so finish them top to bottom and do not polish viewAgentsWorkHistory while assignIssue is broken. And the review call always asks "what if two requests assign at the same time?", so write the thread-safety story into your code (a lock and a comment) before you submit.
