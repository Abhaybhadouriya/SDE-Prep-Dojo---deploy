Clarify the requirements

In a take-home you cannot ask questions, so write your assumptions as a comment block at the top of Main; the statement itself asks for that. In a live round, spend 5 minutes asking.

Functional (P0: must work in the demo)

  1. Create issue A customer raises an issue against a transaction id, with a type (PAYMENT, MUTUAL_FUND, GOLD, INSURANCE), subject, description and email. It starts OPEN and gets an id like I1.
  2. Onboard agent An admin adds an agent with an email (the agent's id), a name and one or more issue types they are expert in.
  3. Assign Pick an agent who has the expertise, using a pluggable strategy. A free agent starts on it at once (IN_PROGRESS). If all experts are busy, the issue joins one agent's waitlist (WAITING). If nobody has the expertise, the issue stays OPEN and can be assigned later.
  4. Search Get issues by any filter: customer email, issue id, type, status, agent, and combinations.
  5. Update and resolve The agent adds notes (updateIssue) and finally resolves the issue with a resolution text. The agent then automatically picks up the next issue from their waitlist.
  6. Work history For each agent, the issues they resolved, in order.

Non-functional

  • Correct invariants: an agent works on at most one issue; an issue has at most one agent; illegal status moves are rejected.
  • Extensible: a new assignment rule or a new filter must not edit the service (Open/Closed).
  • Thread safe: concurrent createIssue / assignIssue / resolveIssue calls never double-assign.
  • In-memory, driver-based, no REST, no DB, no third-party libraries.

Out of scope (say it out loud)

Login and roles enforcement, checking that the transaction really failed (we trust the caller), SLAs and escalation timers, notifications, persistence. Each can be added behind an interface later; we show how in extensibility.

Questions to ask (or assumptions to write down)

  • When all experts are busy, does the issue go to a global queue or to one agent's waitlist? (We use per-agent waitlists, as the 2022 statement says; the global-queue variant is a follow-up below.)
  • Which busy agent gets it? (Shortest waitlist; ties go to the agent onboarded first.)
  • Does assignIssue run automatically inside createIssue? (No: the statement lists it as a separate call. Calling it from create is a one-line change.)
  • Can an agent pick a waiting issue out of order? (No. FIFO per agent.)
  • What can updateIssue change? (Notes on the current status, or RESOLVED. Other moves belong to the system, so a caller cannot jump a waiting issue to in progress.)
  • What if an agent is onboarded after issues piled up OPEN? (Admin re-runs assignIssue for OPEN issues; automatic rebalancing is a follow-up.)
  • Is the email the agent's unique id? (Yes; adding the same email twice is an error.)
