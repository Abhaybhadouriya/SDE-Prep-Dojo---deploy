The story: the bank help desk

Explain like I'm 5

Think of a help desk at a bank. People walk in with a problem slip: "my payment failed", "my gold did not arrive". Behind the desk sit helpers. Some helpers know payments, some know gold, some know both. Each helper can look at only one slip at a time.

A manager stands at the door. When a slip comes in, the manager looks for a helper who knows that kind of problem and is free. If all of those helpers are busy, the manager puts the slip in the shortest pile in front of one of them. When a helper finishes a slip, they stamp it "done", put it in their "finished" folder, and take the next slip from their pile. That manager, the piles and the folders are the whole system.

In the interview you build exactly that, in memory, in about 90 minutes. Three ideas carry the design. First, the rule for choosing a helper changes often (any free agent today, least loaded tomorrow, round robin next week), so it lives behind an interface. Second, an issue has a life: open, waiting, in progress, resolved, and only some moves are legal. Third, "one issue per agent" is an invariant the code must never break, even when many requests arrive at once.

From your world

You already know all three ideas from the kernel. The assignment rule is a pluggable ops table: like struct Qdisc_ops, whose ->dequeue() decides which packet leaves next, an AssignmentStrategy decides which agent gets the next issue, and the service only calls strategy->pick(). The issue lifecycle is a protocol state machine, the same shape as TCP's TCP_SYN_SENT -> TCP_ESTABLISHED -> TCP_FIN_WAIT1 with a table of legal transitions. Each agent's waitlist is a per-CPU run queue: a FIFO of work bound to one worker, drained when the current item finishes.

Interfaces in C terms: every interface on this page is, in C, a struct of function pointers; each implementation fills one in, like file_operations. Java and C++ build that table (the vtable) for you, and every object carries a pointer to it. More in OOP from C structs and polymorphism and vtables.
