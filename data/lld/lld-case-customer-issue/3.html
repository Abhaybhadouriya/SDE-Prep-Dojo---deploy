Identify the entities (nouns and verbs)

Underline nouns (candidate classes) and verbs (candidate methods), then throw away nouns that are only attributes. This is the method from From use cases to classes, applied to this statement.

  1. Start from the problem statement. Read it twice.
  2. Underline nouns. Each is a candidate class: Customer, Issue, transaction, Agent, issue type, strategy, history.
  3. Underline verbs. They become the service's methods and tell you who owns which behaviour.
  4. Remove nouns that carry no behaviour: the customer is only an email on the issue, the transaction is only an id, the history is a list inside Agent. Making a Customer class here is a classic time-waster.
  5. "wait" is not a class either: it becomes the WAITING status plus a per-agent queue. "strategy" becomes an interface because the statement says "based on different strategies".

The most important modelling choice: the agent owns its queue (current issue, waitlist, history), and the issue owns its status. The service only coordinates the two. That split is what makes "one issue per agent" easy to prove: the only place that sets currentIssue is the agent itself, inside the service lock.
