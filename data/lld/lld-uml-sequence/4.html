Worked example: booking seats for a show

This is the flow behind BookMyShow-style questions. Requirements in one line: a user picks seats for a show; seats must be held atomically (no double booking); payment is charged; on success the booking is saved and a confirmation is sent; if any seat is taken or payment fails, nothing stays locked. Step through it.

  1. The request reaches the controller, which calls BookingService.book synchronously. Both activation bars stay open until the very end: the user's HTTP call is waiting.
  2. The service asks the lock manager to hold all seats. Inside, a loop fragment: one atomic putIfAbsent per seat, so only one user can win each seat.
  3. An alt fragment. If any seat is already held or booked, by anyone (even the same user), the manager releases only the seats this call just took and reports failure; the error travels back as 409. Otherwise all seats are locked.
  4. A synchronous charge. A break fragment covers the failure path: release the seats this call locked and return 402, skipping everything below.
  5. Save the booking with a synchronous call to the repository (another participant, so it gets its own lifeline; "self-call" is reserved for calls like validate() on the service's own lifeline). The seat holds are kept: they now are the booking, so the seats can never be acquired again. Then send the confirmation asynchronously: open arrowhead, no reply, the notifier runs on its own thread.
  6. Replies flow back: booking to controller, 201 Created to the user. The notifier may finish before or after this point; nobody waits for it.

Every arrow is a line of code. The runnable version is lld-code/lld-uml-sequence/BookSeat.java; here is the heart of it (the lock manager and the service method, copied from that file) with the fragments marked:

List<String> lockAll(String show, List<String> seats, String user) {
    List<String> taken = new ArrayList<>();                    // only the keys THIS call inserted
    for (String s : seats) {                                   // loop [for each seat]
        String key = show + ":" + s;
        String prev = holder.putIfAbsent(key, user);           // atomic: one winner per seat
        if (prev != null) {                                    // alt [seat held or booked, by anyone,
            unlock(taken);                                     //      even this same user]: undo only ours
            throw new SeatUnavailableException(s);
        }
        taken.add(key);
    }
    return taken;
}
void unlock(List<String> keys) { for (String k : keys) holder.remove(k); }

Booking book(String user, String show, List<String> seats, long pricePerSeat) {
    List<String> held = locks.lockAll(show, seats, user);      // 1. sync call; may throw (alt: taken)
    long amount = pricePerSeat * seats.size();
    String txn;
    try {
        txn = gateway.charge(user, amount);                    // 2. sync call to the gateway
    } catch (PaymentFailedException e) {                       // break [payment failed]
        locks.unlock(held);                                    //    release only what this call took
        throw e;
    }
    Booking b = new Booking("B-" + txn, user, show, seats, amount);   // 3. create message
    repo.save(b);                                              // 4. sync call to the repository
    // The hold is never released after a successful save: it is now the booking record,
    // so nobody (not even the same user) can acquire these seats again.
    notifier.sendAsync(user, "booked " + seats + " for " + show);     // 5. async, no wait
    return b;                                                  // 6. return (dashed arrow)
}

Look at the first two lines of output: asha's notification printed before the controller's reply. That is the async arrow in action. The order between the notifier and the reply is not fixed, exactly as the diagram promised. Note also that after bob's payment failed, ravi could book A3: the break path really released the seats. And asha's second request for A1 got 409: a seat that is already booked cannot be booked again, not even by the person who holds it, so nobody pays twice for one seat.

Real systems hold seats with a timeout. Here the lock lives only for one call. In a real booking app the hold lasts while the user is on the payment page (often a few minutes) and expires on its own. The BookMyShow case study and concurrent booking go deeper.
