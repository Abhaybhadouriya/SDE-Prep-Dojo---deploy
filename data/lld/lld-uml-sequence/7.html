In the interview

When would you draw a sequence diagram instead of (or as well as) a class diagram?

When the order of calls or the waiting behaviour is the hard part: concurrency on a shared resource (seat booking, driver assignment), multi-step flows with failure handling (payment then fulfilment), or calls to external systems. The class diagram says what exists; the sequence diagram proves the classes can actually carry out the use case.

How to answer

Name the specific flow you would draw and why ("the booking flow, because the double-booking and the payment rollback live there").

Likely follow-ups
  • What did the sequence diagram reveal that the class diagram missed?
What is the difference between a synchronous and an asynchronous message on a sequence diagram?

Synchronous: solid line, filled arrowhead; the sender blocks until a reply (usually drawn as a dashed return). Asynchronous: solid line, open arrowhead; the sender continues immediately and the receiver processes later, often on another thread or service. Async usually has no reply arrow, or a separate later message (callback/event).

How to answer

Give the code for each (method call vs executor.submit / queue publish) and a reason to choose async (latency, isolation of failure).

Likely follow-ups
  • How does the caller learn that an async task failed? (Callback, future, dead-letter queue, status polling.)
How do you show "if seat is free then lock, else return an error" and "retry three times"?

Wrap the branch in an alt fragment with guards [seat free] and [else], separated by a dashed line. Wrap the retry in a loop fragment with a guard like [attempt <= 3 and not ok] or bounds loop(1,3). For an early exit on error, a break fragment.

How to answer

Draw the frame with its corner tab while you talk. Mention that opt is an if with no else.

Likely follow-ups
  • How would you show two calls made in parallel? (par fragment.)
Your booking diagram shows two users locking the same seat. How does the diagram prove no double booking?

Draw both users' requests reaching the lock manager. The lock message is a single atomic operation on the seat (a putIfAbsent, a compare-and-set, or a row lock with a unique key), so the second one lands in the [seat held] branch of the alt. The diagram shows where atomicity must exist; the implementation guarantees it.

How to answer

Point at the exact arrow that must be atomic, then name the primitive. Mention all-or-nothing rollback when one of several seats fails.

Likely follow-ups
  • What if the process crashes after locking but before payment? (Hold with expiry / TTL.)
Draw the sequence for "rider requests a ride" at LLD level. Which messages are async?

Rider -> RideController.request; -> RideService creates a Trip (create message); -> MatchingStrategy.findDrivers (sync); loop over candidates: send offer to driver (async), wait for accept with timeout; on accept, Trip.assign(driver) atomically; notify rider (async). The offers and notifications are async; assigning the driver must be a synchronous, atomic step.

How to answer

Show that you separate "ask" (async, may time out) from "commit" (sync, atomic). Tie the Trip's life to a state diagram.

Likely follow-ups
  • Two drivers accept at the same moment: who wins?
What do activation bars tell you about threads and blocking?

An activation bar shows the object is executing (or waiting inside a call it made). Nested bars on one lifeline are a self-call or a re-entrant call. A long bar over a slow external call is a thread held for that whole time: on a fixed-size thread pool, that is a capacity problem. Async arrows end the caller's bar early, freeing the thread.

How to answer

Relate the bar to a thread in a pool, and suggest timeouts on long synchronous external calls.

Likely follow-ups
  • Where would you put a timeout and a circuit breaker on your diagram?
What are common mistakes when drawing sequence diagrams in interviews?

Using classes instead of objects without saying so; drawing every getter; nesting many alts until it becomes a flowchart; forgetting the failure path; showing a message to an object the sender has no reference to; not marking async calls; drawing the whole system instead of one use case.

How to answer

Pick two or three and say how you avoid them: one use case, happy path first, one failure branch, check every arrow against the class diagram.

Likely follow-ups
  • How do you keep the diagram in sync with the code? (Generate it from text: Mermaid/PlantUML in the repo.)

Scenario: "Your checkout is slow when the email server is slow"

The interviewer looks at your sequence diagram: Controller -> OrderService -> PaymentGateway, then OrderService -> EmailService.send (solid arrow, filled head), then reply. Users report checkout taking 8 seconds when SMTP is slow.
Weak answer: "Make the email server faster" or "add more threads".
Strong answer: the diagram shows the email call is synchronous and inside the order's activation, so its latency adds to checkout. Change it to an async message: publish an OrderPlaced event (or submit to an executor) and return. The email service consumes it with retries; a failed email no longer fails a paid order. Redraw that one arrow with an open head and no reply.
Follow-ups: what if the process dies after the payment but before publishing the event? (Outbox pattern: write the event in the same transaction as the order.) How does the user see that the email failed?
