What snapshots cost, and the alternatives

A memento is a copy, and copies cost memory and time. Before choosing it, estimate: state size x number of snapshots kept. A 2 MB document with 100 undo steps is 200 MB if every step is a full copy. Four ways to pay less:

ApproachWhat you store per stepGood forWatch out
Full mementoThe whole stateSmall state, complex edits whose inverse is hard to write, checkpoints before risky batchesMemory grows with state x history; cap the history
Delta mementoOnly the fields or ranges that changedLarge state with small changes (documents, game worlds)Restoring step k means replaying or reversing deltas in order
Command undo (inverse operation)The operation and enough data to reverse it ("deleted 'abc' at 5")Editors, drawing tools; tiny memory per stepEvery command needs a correct undo(); non-invertible actions (hashing, random) still need a memento
Persistent / copy-on-write stateA pointer to an immutable version that shares unchanged partsFunctional state stores, text ropes, file-system and VM snapshotsNeeds immutable data structures from the start

Mature systems mix them: a full checkpoint every N steps plus deltas or commands in between, so restore is "load the nearest checkpoint, then replay". Databases do this with periodic checkpoints plus a write-ahead log, and many games save a full slot at checkpoints while autosaving small changes. Collaborative editors go further and transform operations from many users (see the collaborative editor HLD).

Three bugs to name in interviews: (1) a shallow copy shares mutable objects, so the snapshot changes later; (2) snapshots that capture external resources (open files, sockets, locks) cannot really restore them; (3) unbounded history slowly eats memory. Fix with deep or immutable copies, by saving only plain data, and with a size or count limit.
