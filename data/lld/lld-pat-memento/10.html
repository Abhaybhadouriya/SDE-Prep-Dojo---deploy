In interviews

"Now add undo" is one of the most common follow-ups in machine-coding rounds. Public LeetCode Discuss reports include a Google onsite asking for a text editor with O(1) cursor moves and repeated undo, an Amazon onsite on insert, delete, undo and redo, and a Microsoft round on undo/redo when some commands run locally and some on a service. In all three the expected discussion is Command vs Memento and the cost of each.

  • Text editor: undo/redo stacks; commands with inverse operations, snapshots for complex edits.
  • Chess and tic-tac-toe: undo a move, or save and load a game.
  • Key-value store with transactions: BEGIN takes a checkpoint (or starts a change log), ROLLBACK restores it, nested transactions are a stack of checkpoints.
  • Shopping cart: restore the cart if checkout fails part-way.

The answer that impresses: "I would use Command for undo, because each step stores only the operation and its inverse data. For operations whose inverse is hard, the command stores a memento of just the affected part. History is two stacks with a size cap; a new edit clears redo. Snapshots are immutable so sharing them is safe."

Strong 30-second answer: "Memento lets an object save its state into an opaque snapshot and restore it later, without exposing its fields. The originator creates and reads it, the caretaker only stores it. The trade-off is memory: full snapshots scale with state times history, so for big state I use deltas or Command-based undo, cap the history, and make snapshots deep or immutable."
