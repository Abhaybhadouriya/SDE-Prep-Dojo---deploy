Quiz

What makes Memento different from simply copying fields?

  1. It is faster
  2. The originator creates and reads the snapshot, so encapsulation is kept
  3. It always writes to disk
  4. It works only with immutable objects
Anyone can copy fields if they are public. The pattern is about keeping them private while still allowing save and restore.

In an undo system, the caretaker:

  1. Reads the memento to show a preview
  2. Creates mementos itself from the originator's fields
  3. Stores mementos and gives them back, without inspecting them
  4. Modifies mementos to merge steps
Inspecting or building them would tie the caretaker to the originator's internals.

A 5 MB document, 200 undo steps, full snapshot per step. Best first fix?

  1. Store deltas or use Command-based undo, and cap the history
  2. Make snapshots shallow
  3. Make the editor a singleton
  4. Keep snapshots on another thread
About 1 GB of snapshots; store less per step and keep fewer steps. Shallow snapshots are a bug, not an optimisation.

After undoing twice, the user types a new character. What happens to the redo stack?

  1. It is replayed
  2. It is kept for later
  3. It is merged into the undo stack
  4. It is cleared
A new action starts a new branch of history; the undone steps no longer apply.

How does Java usually keep a memento opaque?

  1. Public fields with a comment
  2. A nested class with private fields, inside a top-level originator class
  3. Reflection
  4. Serialising it to a string
Private members are visible only inside the top-level class that encloses them. Make the originator that top-level class and keep the caretaker outside it.

Saving registers into pt_regs on interrupt entry and restoring them on exit is most like:

  1. Observer
  2. Iterator
  3. Memento
  4. Mediator
Save the context, do something else, restore exactly: a snapshot and restore.
