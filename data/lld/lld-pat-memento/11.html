Interview Q&A

Implement undo/redo for a text editor. Memento or Command?

Usually Command, with Memento where needed. Each user action becomes a command with execute() and undo(). Simple edits store just enough to reverse themselves (position and the inserted or deleted text). Complex edits (reformat a whole paragraph, find-and-replace all) store a memento of the affected region. History keeps an undo stack and a redo stack; executing a new command clears redo; a size cap bounds memory. Pure Memento (snapshot the whole document on every keystroke) is simplest but memory-hungry for large documents.

How to answer

Name both, pick a default with a reason (memory), show the two stacks and the "new edit clears redo" rule, then mention grouping keystrokes into one undo step.

Likely follow-ups
  • Some commands run on a server: how do you undo those? (Compensating commands that the server also executes; keep local and remote steps in one history.)
  • How do you merge 20 typed characters into one undo step?
How do you keep a memento opaque in Java, C++ and Python?

Java: a static nested class inside a top-level originator, with private fields and a private constructor. Private members are visible only inside the top-level class that encloses them, so keep the caretaker outside that class; it then sees only the type (or an empty marker interface such as interface Memento {}). C++: private members with friend class Originator. Python: no real privacy, so use a convention (_state, __slots__) or keep the snapshots inside the originator and give the caretaker only an opaque id.

How to answer

One mechanism per language and why it matters: the caretaker must not depend on the originator's fields.

Likely follow-ups
  • Why not just serialise the object? (Serialisation is a way to build mementos, but it exposes all fields to the serialised form and costs CPU.)
Your editor's undo history uses 2 GB. What do you change?

Measure what each step stores. Replace full-document snapshots with deltas or inverse-operation commands. Cap history by count or by bytes. Merge small steps (consecutive typing) into one. Use immutable structures (a rope or piece table) so snapshots share unchanged text. Optionally keep a full checkpoint every N steps and spill older history to disk.

How to answer

Diagnose first (size x count), then four levers: store less per step, keep fewer steps, share structure, move old history out of memory.

Likely follow-ups
  • How does a piece table make undo cheap?
Design transactions for an in-memory key-value store: BEGIN, SET, ROLLBACK, COMMIT, nested.

Keep a stack of change logs. BEGIN pushes an empty map. SET k v first records the old value of k (or "absent") in the top map if not already recorded, then writes. ROLLBACK pops the top map and restores each recorded old value. COMMIT clears the stack (or merges the top log into the one below for nested commits). Each log is a delta memento, so cost is proportional to keys touched, not to store size.

How to answer

Contrast "copy the whole store on BEGIN" (simple, O(n)) with the delta approach, then walk through a nested example.

Likely follow-ups
  • Add COUNT value that stays correct across rollbacks.
What is wrong with saving state by copying the object's fields into a dictionary?

It is a shallow copy: lists, maps and other mutable objects inside are shared, so later changes leak into the snapshot (our Python demo shows the inventory changing). Use a deep copy, store immutable values, or let the originator decide exactly what to copy. Also check that the snapshot does not capture things that cannot be restored, such as open files or locks.

How to answer

Name shallow vs deep, give the symptom, give two fixes.

Likely follow-ups
  • When is a shallow copy enough? (When every shared part is immutable.)
Where does the kernel save and restore state, and how is that like Memento?

On interrupt, exception or syscall entry, the entry code saves the interrupted context's registers into a struct pt_regs on the kernel stack; the handler runs; on exit the registers are restored. On a context switch the scheduler saves the outgoing task's CPU state in its task structures and loads the incoming one. In each case the state is captured by the code that owns it, stored without being interpreted by the rest of the kernel, and restored exactly, which is the Memento pattern. User-space setjmp/longjmp and CRIU checkpoint/restore are the same idea at other levels.

How to answer

Interrupt entry, context switch, then map originator / memento / caretaker.

Likely follow-ups
  • Why is FPU state often saved lazily or only when needed? (It is large; saving it on every switch costs time, the same snapshot-cost trade-off.)
