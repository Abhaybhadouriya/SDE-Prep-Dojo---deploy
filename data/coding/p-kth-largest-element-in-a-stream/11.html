Values can also be removed from the stream.

A plain heap cannot delete an arbitrary value cheaply. Keep two ordered multisets (a balanced BST / TreeMap with counts): "top" holds the k largest, "rest" the others. Remove from whichever set holds the value, then move the max of "rest" into "top" if "top" fell below k. O(log n) per operation. Lazy deletion with a heap plus a "to delete" hash map also works.

How to answer

Name the limitation of heaps (no arbitrary delete), then give the two-set or lazy-delete fix.

Values are small integers (say -104..104). Can you beat O(log k)?

Use a counting array over the value range plus a pointer to the current kth value. A new value above the pointer moves the pointer up to the next non-empty bucket, which is amortised fast in practice; a Fenwick tree over the range gives a guaranteed O(log V) "find kth" with no dependence on k.

How to answer

Point out the value range from the constraints, then trade memory (O(V)) for time.

Likely follow-ups
  • When is that worse? (Huge or real-valued ranges.)
The stream is distributed across many machines.

Each machine keeps its own size-k min-heap. The global kth largest is among the union of the local top-k sets, so the coordinator merges at most m·k values (another size-k heap) when asked. Updates stay local and O(log k).

How to answer

Argue that a value outside a machine's local top k cannot be in the global top k.

Likely follow-ups
  • Approximate answer with tiny memory? (Count-min sketch / t-digest for quantiles.)
Return the kth largest distinct value instead.

Keep a hash set of the values currently in the heap and skip a value that is already there. The heap then holds k distinct values and its top is the kth distinct largest. The set must be updated when the top is replaced.

How to answer

Clarify duplicates first; the original counts them.

Likely follow-ups
  • Memory if k is large? (O(k) for both structures.)
Many threads call add() at once.

Guard the heap with a mutex; the critical section is O(log k). To cut contention, do the cheap check "val <= top" with an atomic read of the current answer first and take the lock only when the value might enter, or shard per thread and merge on read.

How to answer

Fast path without a lock, slow path with one, like a read-mostly cache.
