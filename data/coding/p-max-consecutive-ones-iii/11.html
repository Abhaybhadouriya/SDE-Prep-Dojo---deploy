The input is an infinite stream and k is fixed. You cannot store the array.

The window needs nums[left] when it shrinks, so store only the positions of the last k + 1 zeros in a queue. When a (k+1)-th zero arrives, jump left to one past the oldest stored zero and pop it. Memory O(k), time O(1) per element.

How to answer

Point out that only zeros matter for the shrink step; the ones between them are implied.

Likely follow-ups
  • k = 1 (LC 487): two integers are enough (start of the current run, position of the last zero).

Why is this O(n) when there is a while loop inside the for loop?

Amortised argument: left only increases and never passes n, so the inner loop runs at most n times in total across the whole run, not per outer step. Total pointer moves <= 2n.

How to answer

Count pointer moves, not loop nesting.

Likely follow-ups
  • When does the "never shrink" if-version give the same answer, and why?
Each flip has a cost c[i] and you have a budget B instead of a count k.

Same window: keep cost = sum of c[i] over zeros inside, shrink while cost > B. Works because costs are non-negative, so validity stays monotone.

How to answer

State the requirement: non-negative weights. With negative weights, monotonicity breaks and you need prefix sums + a sorted structure.

Likely follow-ups
  • Longest subarray with sum <= B when values can be negative.
Many queries: different k values on the same array.

Store the zero positions z[0..m-1] once. For a given k < m, the best window spans from just after z[i-1] to just before z[i+k], so the answer is max over i of z[i+k] - z[i-1] - 1 (with sentinels -1 and n). That is O(m) per query, or precompute the answers for all k in O(m²) if queries are many and m is small.

How to answer

Switch from scanning the array to scanning gaps between zeros.

Likely follow-ups
  • k >= m: the answer is n.
