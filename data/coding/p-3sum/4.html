Approaches: brute → better → optimal

Hint 1

If you fix one number a, what is left is a classic problem: find pairs summing to -a.

Hint 2

The answer is a set of value-triplets, not index-triplets. What does sorting do to equal values?

Hint 3

On a sorted range, if lo + hi is too big, can the value at hi be part of any pair with the remaining values?

1. Brute force - three loops and a set

Idea: try every i < j < k; when the sum is 0, sort the three values and insert them into a set so duplicates collapse.

O(n³)time
O(answer)space

What is wasted: for a fixed pair (i, j) we scan all k just to find one value, -(a+b). A lookup can do that in O(1). -> rung 2.

2. Better - fix one, hash the second

Idea: for each i, walk j over the rest and keep a hash set of values seen so far in that walk; if -(nums[i] + nums[j]) is in the set, we have a triplet. Sorting first (or a set of sorted tuples) still removes duplicates.

nums.sort()
for i in range(n):
    if i and nums[i] == nums[i - 1]: continue
    seen = set()
    for j in range(i + 1, n):
        need = -nums[i] - nums[j]
        if need in seen: res.add((nums[i], need, nums[j]))
        seen.add(nums[j])
O(n²)time
O(n)space

What is wasted: a hash set per i and a result set for de-duplication. Once the array is sorted, we already have order, and order alone finds pairs. -> rung 3. (This version is still the right answer if you are not allowed to reorder, see the follow-ups.)

3. Optimal - sort + two pointers

for i in range(n - 2):
    if nums[i] > 0: break
    if i and nums[i] == nums[i - 1]: continue
    lo, hi = i + 1, n - 1
    while lo < hi: ...   # sum < 0: lo += 1, sum > 0: hi -= 1, else record and skip copies
  1. Sort once. Equal values become neighbours and every suffix is ordered.
  2. Fix the smallest number, nums[i]. Only look to its right, so each triplet is found from its smallest member exactly once.
  3. The sign of the sum picks the pointer. Sum < 0: nums[lo] is too small even with the largest partner, discard it. Sum > 0: nums[hi] is too big even with the smallest partner, discard it.
  4. De-duplicate by position. Skip an i equal to the previous one; after a hit, advance lo past copies of the value just used. Then every recorded triplet is new.
  5. Stop early. If nums[i] > 0, all three are positive: break.
O(n²)time
O(1)extra space (plus the sort and the output)

Why it works: each comparison removes one value from the pair search, and the removed value provably has no partner left: that is why one pass over the suffix finds all pairs. Skipping equal values is safe because a triplet is defined by its values; the first copy of a value already produced every triplet that copy could make, including those that use the later copies as partners.

Proof (optional)

Fix i. Let the window be [lo, hi]. Claim: every pair (p, q) with lo ≤ p < q ≤ hi and nums[p] + nums[q] = t (t = -nums[i]) is still inside the window. When sum < t we drop lo: any pair with lo has a partner q ≤ hi, so nums[lo] + nums[q] ≤ nums[lo] + nums[hi] < t; none exists. The case sum > t is symmetric. On a hit we record (nums[lo], nums[hi]) and move both; pairs that reuse lo would need the value nums[hi] again (already recorded), and the same for hi. The window shrinks by at least one per step, so the scan is O(n) per i, O(n²) in total.

The second de-duplication loop (for hi) is optional: after skipping copies at lo, the old hi value can no longer form 0 with the new, larger lo, so the sign rule moves past it anyway.
