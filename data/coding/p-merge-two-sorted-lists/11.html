Interview follow-ups

Recursive or iterative: which one, and why?

Both are O(m + n) time. Recursion uses one stack frame per node, so a list of 10^6 nodes can overflow the stack (and most languages do not optimise the tail call here). The iterative version is O(1) extra space, so I code that one and mention the recursive one as a shorter alternative.

How to answer

Give both costs, name the stack-depth risk, pick iterative.

Likely follow-ups
  • Is the recursive call a tail call? (No: a.next = merge(...) runs after it returns.)
Can you do it without the dummy node?

Yes: pick the head first (the smaller of the two fronts, after handling a null input), set tail to it, then run the same loop. It is a few more lines and the first-node case is a common source of bugs, which is why the dummy is preferred.

How to answer

Show you know what the dummy saves you from: a special case for the first link.

Likely follow-ups
  • In C, how would you avoid the special case without a dummy? (A pointer to pointer: ListNode **link = &head; and write through *link.)
Merge and remove duplicates at the same time.

Before linking a node, compare it with tail.val (when tail is not the dummy). If equal, skip the node and advance its list, but do not move tail. The output stays sorted with each value once.

How to answer

One extra comparison at the append point; remember to also check the leftover run, which can start with a duplicate.

Likely follow-ups
  • Keep only values that appear in both lists (intersection): advance the smaller front, link on equality.
Now merge k sorted lists.

Merging one by one into a growing result is O(N·k). Use a min-heap of the k fronts (O(N log k)), or merge pairs in rounds like merge sort (also O(N log k), O(1) extra). This function is the building block of the pairwise version.

How to answer

Name the trap (sequential merging) and both O(N log k) fixes.

Likely follow-ups
  • See LC 23 for the heap and divide-and-conquer code.
The lists are sorted in descending order, or you need the output descending.

For descending inputs flip the comparison (take the larger front). For ascending inputs and a descending output, merge normally but insert each taken node at the head of the result instead of after tail, which reverses the order as you go.

How to answer

Two small changes: the comparison, or head insertion.

Likely follow-ups
  • Why does head insertion reverse the list? (Each new node goes in front of all earlier ones.)
