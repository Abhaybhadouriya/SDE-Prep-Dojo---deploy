Interview questions

You have finished coding. The interviewer says nothing. What do you do next?

Start testing without being asked: "Before we call this done, let me trace it." Run the given example at a high level, then dry-run one small input that hits every branch with a variable table, then sweep the edge cases for the input type, pointing at the line that handles each. Finish with time and space complexity.

How to answer

Name the routine in one sentence so the interviewer can follow, then do it. Keep it to about five minutes.

Likely follow-ups
  • "Which case are you most worried about?" (name the boundary your loop is closest to: the last element, the size-two range).
  • "How would you test this in production code?" (unit table tests, a brute-force oracle, property-based tests).
Which edge cases would you test for a function that merges two sorted linked lists?

Both empty; one empty; one node each; all of one list smaller than all of the other (one list is used up first, the rest must be attached); equal values across the lists (stability, no lost nodes); different lengths. With a dummy head node, the empty cases need no special code, which is worth saying.

How to answer

Group by "size" cases, then "value order" cases. Point at tail.next = l1 or l2 as the line that handles the leftover.

Likely follow-ups
  • Merge k lists (a min-heap of the k heads, O(N log k)).
  • Do it recursively: what is the stack depth? (O(n + m), a risk for long lists).
Your binary search loops forever on some inputs. How do you find and fix it?

Find the smallest failing input, usually a range of size two. Trace it with a table that includes the range size; the row where the size does not drop is the bug. It is almost always lo = mid combined with a rounded-down mid (mid can equal lo). Fix by rounding mid up, lo + (hi - lo + 1) / 2, or switch to the half-open template where the branches are lo = mid + 1 and hi = mid.

How to answer

State the pairing rule (which update goes with which mid rounding), then show the size-two trace.

Likely follow-ups
  • Why lo + (hi - lo) / 2? (no overflow when lo + hi exceeds the int range).
  • How do you know the loop terminates? (the range strictly shrinks every iteration).
"Reverse the digits of a 32-bit signed integer; return 0 if the result overflows." Which tests matter most?

0; a single digit; a negative number; trailing zeros (120 becomes 21); INT_MAX (2147483647, its reverse overflows, so 0); INT_MIN (-2147483648, also overflows); and a value whose reverse is just inside the limit, such as 1463847412 (reverse 2147483641). The check must happen before the multiply: if rev > (INT_MAX - d) / 10 for positives, the mirror for negatives.

How to answer

List the cases by category (sign, zeros, limits), then show the pre-multiply check and why abs(INT_MIN) is unsafe in C-family languages.

Likely follow-ups
  • Assume you cannot use 64-bit integers (then the pre-check is mandatory).
  • Does the same check work in Python? (Python ints do not overflow, so you compare against the limits explicitly).
How do you dry-run a recursive tree solution without getting lost?

Use a tree of 3 to 5 nodes, and write each call's return value next to its node, bottom-up: leaves first, then parents. For a function that also updates a global (diameter, max path sum), keep a separate "best so far" cell and update it at each node. Then test the null root and a single node, which exercise the base case alone.

How to answer

Say "the return value means X, the global means Y" before tracing. Most recursive bugs are a mix-up between the two.

Likely follow-ups
  • A skewed tree with 105 nodes (recursion depth; convert to an explicit stack).
  • All node values negative (initialise the global to the minimum value, not 0).
The editor can run code. How would you test your solution in the time left?

First a few hand-written asserts: the given examples plus the boundary cases, each with a name. If the solution is subtle and time allows, a quick brute-force oracle and a random loop on tiny inputs with a fixed seed. Print the first mismatch, shrink it by hand, trace it. Never paste in large random tests you cannot check by eye.

How to answer

Show priorities: named edge cases first (cheap and readable), random testing second (powerful, but needs an oracle).

Likely follow-ups
  • What if there is no simple brute force? (check invariants instead: output sorted, sum preserved, every element used once).
  • How would you make a failure reproducible? (a fixed seed, and print the input).
During testing you find a bug and you have eight minutes left. What do you say and do?

Name the failing input and the wrong output, shrink it if possible, trace to the first wrong cell, say the cause in one sentence, and change the smallest piece of code. Re-run the failing input and the main example. If the fix is bigger than the time left, say exactly what you would change and why; a correct plan with a known bug beats a half-written rewrite.

How to answer

Calm narration is the signal: symptom, cause, patch, verification. Never go silent.

Likely follow-ups
  • "Are there other inputs with the same bug?" (think about the class of input, for example every all-negative array).
  • "How would you stop this bug in the future?" (a named test for that case).
How do you test a class-design problem like an LRU cache?

Write a short script of operations with the expected result after each, the way the problem examples do: capacity 2, put 1, put 2, get 1 (now 1 is most recent), put 3 (must evict 2, not 1), get 2 returns -1. Then the edges: capacity 1; put on an existing key (update the value and the recency, no eviction); get on a missing key; many operations on the same key. Check both structures stay in sync: the map size equals the list length after each step.

How to answer

Test the interaction ("get changes what gets evicted next"), not just each method alone.

Likely follow-ups
  • Thread safety (one lock around both structures; the list and the map must change together).
  • Add a TTL per key (lazy expiry on get, plus a periodic sweep).
