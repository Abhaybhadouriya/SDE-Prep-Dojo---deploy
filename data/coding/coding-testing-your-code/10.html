Common mistakes

  • Testing only the given example. It was chosen to explain the problem, not to break your code.
  • Tracing what you meant instead of what you wrote. Point at each line; read the operator out loud.
  • Testing a huge input by hand. Pick 4 to 6 elements. Large inputs are for the complexity argument, not the trace.
  • Listing edge cases without checking them. "Empty array, handled" must come with the line that handles it.
  • Rewriting instead of fixing. A new approach late in the round costs time and usually brings new bugs.
  • Fixing a symptom. Adding if n == 2: return ... to make one case pass hides the real off-by-one and the interviewer sees it.
  • Forgetting to re-run old cases after a fix. A fix for the empty case can break the one-element case.
  • Testing forever. Five minutes is plenty. Close with complexity and let the interviewer move on to the follow-up.
