The five-step test routine

Use the same routine every time, so you never have to decide what to do next under pressure. Say the step names out loud; the interviewer hears a plan, not panic.

  1. Re-read the given examples. Run the example from the problem statement through the code at a high level ("the loop sees 2, then 7, finds the complement..."). This catches misread requirements: 1-based output, "return the count" versus "return the list".
  2. Dry run one small example with a table. Pick an input of 4 to 6 elements that goes through every branch. Write one column per variable and one row per loop iteration. Do not trust your memory of what the code "should" do; read the line you wrote.
  3. Edge-case sweep. Walk the checklist for the input's data type (below). You rarely trace each case fully: for most, you point at the line that handles it.
  4. Fix the smallest thing. When a case fails, find the exact line, explain the cause in one sentence, change only that line.
  5. Re-run and close. Re-run the failing case and the main example, then state time and space complexity. Stop. Do not keep testing forever; the interviewer has more to ask.

Interviewers love this: testing before they ask. Saying "Let me trace this on [3, 1, 2] before we call it done" signals ownership. Waiting for "Are you sure it works?" signals the opposite, even when the code is right.
