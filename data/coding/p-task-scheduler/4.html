Approaches: brute -> better -> optimal

Hint 1

Which task type causes idle slots? What if every type had count 1?

Hint 2

Lay the most frequent type out first, n + 1 apart. How many holes does that leave, and can the others always fill them?

1. Brute force - try orders

Idea: search over which ready type to run at each time unit (or over permutations of the jobs), simulate the cooldown, keep the shortest. It is exponential, so it only serves to state the problem precisely and to test a faster idea on tiny inputs.

exponentialtime
O(n)depth

What is wasted: most choices are obviously bad. A simple exchange argument shows one choice is always safe: run the ready type with the most copies left. -> rung 2.

2. Better - greedy simulation with a max-heap and a cooldown queue

Idea: keep the remaining counts of ready types in a max-heap. Each time unit, pop the largest, run one copy, and park it in a FIFO with the time it becomes ready again (now + n). When the front of the FIFO is ready, push it back into the heap. If the heap is empty but the FIFO is not, that time unit is idle.

Why the most frequent first: the type with the most copies left is the one that can run out of time; delaying it can only create idles later, while delaying a rarer type never can.

O(T · log 26)time; T = answer ≤ tasks·(n+1)
O(26)space

This version is what you need when the interviewer asks for the actual order (and it is the base of Reorganize String and Rearrange String k Distance Apart). The tested files keep it as simulate and check it against the formula on 500 random inputs.

What is wasted: we only need the length, and the length depends only on the largest count and how many types share it. -> rung 3.

3. Optimal - count and use the frame

top = max(freq)
width = freq.count(top)
return max(len(tasks), (top - 1) * (n + 1) + width)
  1. The most frequent type sets the rows. Its top copies must be n + 1 apart, so they span at least (top - 1)(n + 1) + 1 time units. Draw them as the first column of top rows, each row n + 1 slots wide.
  2. Ties extend the last row. Every type with top copies also needs a cell in the last row, so the last row is width cells long, not 1.
  3. Everyone else fits in the gaps. A type with fewer than top copies goes column by column into earlier rows; its copies land in different rows, so they are at least n + 1 apart. Unused cells are idles.
  4. If the gaps run out, there are no idles. Widen the rows to hold the extra jobs. Wider rows only push same-type copies further apart, so the cooldown still holds and the answer is the job count.
O(n)time (one counting pass)
O(26)space

Why it works: both numbers are lower bounds, and the frame construction meets the larger one. You can never finish in fewer units than there are jobs, and the heaviest types force the frame length. The column-by-column fill shows a schedule of exactly that length always exists.

Proof (optional)

Lower bound. Let the width types with top copies have their first copies at times t1 < ... < twidth; then twidth ≥ width. That type's copies are n + 1 apart, so its last copy runs at time ≥ twidth + (top - 1)(n + 1) ≥ (top - 1)(n + 1) + width. Also the length is ≥ the number of jobs. Upper bound. Write the types in order of count, top types first, and fill the grid of top rows column by column (down a column, then the next column). A top type fills a whole column, so its copies are exactly one row width (≥ n + 1) apart. A type with c < top copies occupies c consecutive cells in column-major order: its copies sit in different rows, and if it wraps into the next column it skips at least one row, so consecutive copies are still at least one row width apart. If the jobs exceed the frame, the grid simply gets more columns and has no empty cell. Reading the grid row by row gives a valid schedule of length max(jobs, frame).
