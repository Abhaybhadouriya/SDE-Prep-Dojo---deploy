Running median: the two-heap invariant

Problem (restated from LeetCode 295, Find Median from Data Stream). Build a class with two methods. addNum(x) adds the integer x to the data seen so far. findMedian() returns the median of everything added so far as a floating-point number: the middle value when the count is odd, and the average of the two middle values when it is even. For example, after adding 2, 9 and 4 the median is 4.0; after also adding 6 it is (4 + 6) / 2 = 5.0. Limits: -105 <= x <= 105, at least one number is added before the first findMedian, at most 5 · 104 calls in total, and answers within 10-5 of the true value are accepted. Follow-ups: what if every number is in [0, 100]? What if 99% of them are?

Simple answers first, because the interviewer will ask why you did not use them. Keep a sorted array and insert with binary search: finding the spot is O(log n) but shifting is O(n) per add. Sort on every findMedian: O(n log n) per query. Both are too slow when adds and queries are mixed 5 · 104 times.

The two-heap design keeps exactly two facts true at all times:

  1. Order: every item in lo (the max-heap) is <= every item in hi (the min-heap). Checking the two tops is enough.
  2. Size: |lo| = |hi| or |lo| = |hi| + 1. We let lo take the extra item when the count is odd, so the odd-count median is simply lo's top.

Adding a number without breaking either rule takes three moves, always in this order: push x into lo; move lo's top to hi (this fixes the order rule, because the biggest of the small side crosses over); if hi is now bigger, move hi's top back. It looks wasteful, and it is a little: some numbers cross twice. But it has no special cases, so you cannot get it wrong under pressure. Step through it:

  1. 5 arrives. Push it into lo, move lo's top (5) to hi, and hi is now bigger, so move it back. lo = {5}. Odd count: the median is lo's top, 5.
  2. 15 arrives. Push into lo, then lo's top (15) moves to hi. Sizes 1 and 1 are fine. Even count: the median is the average of the two tops, (5 + 15) / 2 = 10.
  3. 1 arrives. lo gets 1, lo's top (5) moves to hi, hi now has 2 items and lo 1, so hi's top (5) comes back. lo = {5, 1}, hi = {15}. Median = lo's top = 5.
  4. 3 arrives. lo = {5, 3, 1}; its top 5 moves to hi, so hi = {5, 15} and lo = {3, 1}. Sizes are equal. Median = (3 + 5) / 2 = 4. Note how 5 crossed the line: that is the order fix.
  5. 8 arrives. It enters lo, but it is the biggest there, so it moves straight on to hi. hi now has 3 items and lo 2: hi's top (5) moves back. Median = lo's top = 5.
  6. 7 arrives. It goes into lo, is the biggest there, and moves to hi. Sizes 3 and 3. Median = (5 + 7) / 2 = 6. Every add did at most 3 heap operations: O(log n).

type MinInt []int

func (h MinInt) Len() int            { return len(h) }
func (h MinInt) Less(i, j int) bool  { return h[i] < h[j] }
func (h MinInt) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinInt) Push(x interface{}) { *h = append(*h, x.(int)) }
func (h *MinInt) Pop() interface{} {
	old := *h
	x := old[len(old)-1]
	*h = old[:len(old)-1]
	return x
}

// Invariant: every lo <= every hi, and lo.Len() == hi.Len() or hi.Len()+1.
type MedianFinder struct {
	lo *MaxInt
	hi *MinInt
}

func NewMedianFinder() *MedianFinder { return &MedianFinder{&MaxInt{}, &MinInt{}} }

func (m *MedianFinder) AddNum(x int) {
	heap.Push(m.lo, x)                 // 1. always enter through lo
	heap.Push(m.hi, heap.Pop(m.lo))    // 2. lo's biggest moves to hi (fixes order)
	if m.hi.Len() > m.lo.Len() {       // 3. fix the sizes
		heap.Push(m.lo, heap.Pop(m.hi))
	}
}

func (m *MedianFinder) FindMedian() float64 {
	if m.lo.Len() > m.hi.Len() {
		return float64(m.lo.MinInt[0])
	}
	return (float64(m.lo.MinInt[0]) + float64((*m.hi)[0])) / 2
}

        if (lo.size() > hi.size()) return lo.top();

    void addNum(int x) {
        lo.offer(x);                          // 1. always enter through lo
        hi.offer(lo.poll());                  // 2. lo's biggest moves to hi (fixes order)
        if (hi.size() > lo.size()) lo.offer(hi.poll());   // 3. fix the sizes

        if (lo.size() > hi.size()) return lo.peek();

The follow-ups

  • All numbers in [0, 100]. Drop the heaps. Keep count[101] and a total n. To find the median, walk the counts until you pass position n / 2 (and n / 2 - 1 for even n). That is O(1) add and O(101) per query: constant.
  • 99% in [0, 100]. Keep the 101 counters plus two small overflow structures: a count of values below 0 and a count above 100 (or a sorted list of each, if you might need the actual value). The median is almost certainly inside [0, 100], so the walk starts after the "below" count. Only when the outliers outnumber the middle do you look into an overflow side.
  • A huge stream that does not fit in memory. Exact medians need all the data. Offer an approximate answer: fixed buckets (a histogram), or a quantile sketch such as t-digest or the GK algorithm. Say "approximate" out loud.
