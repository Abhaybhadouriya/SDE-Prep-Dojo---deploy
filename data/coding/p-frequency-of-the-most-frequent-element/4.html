Approaches: brute → better → optimal

Hint 1

Can the best final value be a number that does not appear in the list?

Hint 2

If 9 is the target, which elements would you raise first? Where are they after sorting?

Hint 3

How do you get the cost of raising a whole block to its last value without looping over the block?

1. Brute force - every target, greedy neighbours

Idea: sort. For each index i as the target, walk left from i-1 and raise neighbours one by one while the budget lasts. Keep the largest count.

O(n²)time in the worst case (all values close together)
O(1)extra space after the sort

What is wasted: each target recomputes the cost of nearly the same block from scratch. For target i+1 the best block cannot start earlier than the best block for target i (the target only grew), and that fact is never used.

2. Better - prefix sums + binary search per target

Idea: with prefix sums, the cost of raising block [j..i] to nums[i] is nums[i] × (i-j+1) - (pre[i+1] - pre[j]) in O(1). For a fixed i, that cost only falls as j moves right, so binary search the smallest affordable j.

O(n log n)time: sort + one binary search per index
O(n)space for the prefix array

What is wasted: the binary searches ignore that the best j only moves right as i grows. Two pointers get the same answers in O(n) after the sort, without the extra array.

3. Optimal - sort + sliding window on the cost

nums.sort()
for right, target in enumerate(nums):
    window_sum += target
    while target * (right - left + 1) - window_sum > k:
        window_sum -= nums[left]; left += 1
    best = max(best, right - left + 1)
  1. Sort the list. Now the cheapest elements to raise to nums[right] are just to its left.
  2. The window [left..right] is a candidate group with target nums[right] (its largest value).
  3. Its cost is target × size - sum. Keep the window sum as a running total, so the check is O(1).
  4. Over budget? Drop from the left. The leftmost value is the smallest, the most expensive to raise.
  5. Record after the shrink. The window is affordable again; its size is a valid frequency.
O(n log n)time: the sort; the window itself is O(n)
O(1)extra space (O(log n) for the sort's stack)

Why it works: when right moves one step, the target grows (or stays) and the window gains one element, so the cost of every block [j..right] is at least the cost of [j..right-1]. A left edge that was too expensive for the old target is still too expensive for the new one, so left never needs to move back. Each index enters and leaves the window once: O(n) moves after sorting.

Proof (optional)

Target in the list: suppose an optimal answer raises a set S to a value v not in the list, and let u be the largest original value in S (u < v, since v is not in the list). Raising every element of S to u instead is allowed (each started ≤ u), gives the same frequency and costs |S|·(v-u) fewer operations. Contiguous block: for a target nums[i], the cost of a set S of size m below it is m·nums[i] - ΣS; that is minimised by the m largest values ≤ nums[i], which in sorted order are nums[i-m+1..i]. Monotone left edge: cost(j, i) = nums[i]·(i-j+1) - Σ nums[j..i]. Then cost(j, i+1) - cost(j, i) = (nums[i+1] - nums[i])·(i-j+1) ≥ 0, so feasibility of j can only be lost as i grows, and the smallest feasible j is non-decreasing in i.

A one-line trick from the top solutions: the window never needs to shrink by more than one. Replace the while with an if that drops one element per step: the window size never decreases, so it always equals the best size seen so far, and the answer is n - left at the end. It is shorter but harder to explain; give the while version first.
