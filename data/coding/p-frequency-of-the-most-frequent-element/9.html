  • Cue: at most k +1 operations, maximise how many values become equal.
  • Insight: sort; target = window max; raise the closest smaller values first.
  • State: left, running window sum; cost = nums[r] × size - sum.
  • Trap: 64-bit cost; shrink while cost > k (not ≥); sort first.
  • Cost: O(n log n) time (sort), O(1) extra; brute O(n²).
nums.sort(); l = s = best = 0
for r, x in enumerate(nums):
    s += x
    while x * (r - l + 1) - s > k:   # over budget
        s -= nums[l]; l += 1
    best = max(best, r - l + 1)

Why sort first?

  1. To use binary search on the answer
  2. So the cheapest elements to raise to a target sit right next to it
  3. To remove duplicates
After sorting, "closest smaller values" are a contiguous block ending at the target, which is what a window can hold.

What is the cost of levelling the window [l..r] up to nums[r]?

  1. nums[r] × (r - l + 1) - sum(nums[l..r])
  2. sum(nums[l..r]) - nums[l] × (r - l + 1)
  3. nums[r] - nums[l]
The full rectangle minus what is already there: exactly the increments.

Why can the left pointer never move back?

  1. Because k is positive
  2. Because the values are distinct
  3. Moving right only raises the target, so old blocks never get cheaper
cost(j, r+1) ≥ cost(j, r): an unaffordable left edge stays unaffordable.
