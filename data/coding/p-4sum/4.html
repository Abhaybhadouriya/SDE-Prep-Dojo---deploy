Approaches: brute -> better -> optimal

Hint 1

If you fix the first two values, what is left to solve?

Hint 2

After sorting, when do two choices for the same slot produce exactly the same quadruplets?

1. Brute force - four loops and a set

Idea: try every index quadruple, sort each matching quadruple, and insert it into a set to remove duplicates.

O(n⁴)time
O(answers)space for the set

Why it is not enough: 1.6 · 109 iterations at n = 200. Our tests still use it as the reference on small random arrays.

2. Better - three loops and a hash set for the fourth value

Idea: sort, fix i < j, then scan k from j+1 while a hash set holds values seen between j+1 and k-1; if target - a - b - c is in the set, record a quadruplet. Duplicates still need a set of results or careful skipping.

O(n³)time
O(n)space

The same order as the optimal, with more memory and messier duplicate handling. Since the array is sorted anyway, two pointers do the last pair with O(1) space and a clean skip rule.

3. Optimal - sort, two fixed loops, two pointers

sort(nums)
for i: skip if nums[i] == nums[i-1]
  for j > i: skip if j > i+1 and nums[j] == nums[j-1]
    need = target - nums[i] - nums[j]          # 64-bit
    lo, hi = j+1, n-1: move by the sign of nums[lo] + nums[hi] - need;
    on a match: record, move both, skip equal neighbours
  1. The pair search is exact. On a sorted range, if nums[lo] + nums[hi] is too small, nums[lo] cannot pair with anything (hi already holds the biggest partner), so drop it; mirror for too big. Every step discards one value that cannot be in an answer for this (i, j), so no answer is missed.
  2. Skipping by slot removes duplicates without a set. In sorted order, a quadruplet is identified by its values in slot order. Two choices of the same value for the same slot (i, or j for a fixed i, or the lo/hi pair) generate exactly the same quadruplets, so only the first one is tried. Equal values in different slots (like the two 0s in [-4,0,0,4]) are still allowed.
  3. Pruning is free with sorting. If the four smallest values from i already exceed the target, every later i is worse: break. If i plus the three largest values is still too small, this i cannot work: continue. Same at the j level.
  4. 64-bit sums. Compute need and every comparison sum in long/long long, casting before the first addition.
O(n³)time
O(1)extra space (plus the sort)

Generalising to k-Sum (the top-voted posts' main point): write kSum(start, k, target). If k == 2, run the two-pointer search; otherwise loop i from start, skip repeats, prune with nums[i] * k > target or nums[last] * k < target, and recurse with k - 1. Time O(nk-1). It is a good closing line in the interview.
