Interview follow-ups

The weights change between picks (update w[i]). How do you keep picks fast?

A prefix array costs O(n) per update. Keep a Fenwick (binary indexed) tree over the weights: an update is O(log n), and "first index whose prefix sum >= t" is a top-down descent of the tree in O(log n). A segment tree works the same way.

How to answer

Name the trade-off: static weights -> prefix array; dynamic weights -> Fenwick with a binary-lifting search.

Likely follow-ups
  • Weights can drop to 0 (index disabled): the search must skip empty blocks, which >= does naturally.
Make pickIndex O(1).

The alias method: scale weights so the average is 1, then repeatedly pair one "small" index (< 1) with one "large" index (> 1) to fill a box of size 1. Each box stores a threshold and an alias. A pick draws a box uniformly and a coin against its threshold. O(n) build, O(1) pick.

How to answer

Sketch why a box with at most two owners always exists (one below-average and one above-average weight always exist until all are filled).

Likely follow-ups
  • Floating point error in the thresholds: keep integers by scaling with n.
How would you test a randomised function?

Separate the deterministic part: test "ticket -> index" exhaustively on small inputs (as our test files do). For the random part, draw many samples and check each frequency against w[i] / total with a tolerance of several standard deviations, or a chi-square test, using a fixed seed in CI.

How to answer

Mention seeding for reproducibility and that tolerance must scale with 1/sqrt(samples).

Likely follow-ups
  • Injecting the random source (dependency injection) so tests can feed fixed tickets.
Pick k distinct indices, each round weighted by the remaining weights.

Repeat: pick, then set that weight to 0 and update (Fenwick: O(log n) each), so k picks cost O(k log n). An alternative one-pass method draws key u1/w[i] for each index and keeps the top k in a heap (Efraimidis-Spirakis), O(n log k).

How to answer

Clarify "without replacement" first; it changes the data structure.

Likely follow-ups
  • Streaming version: the same keys work with a size-k heap.
What if the weights are huge, with a total above 231?

Use 64-bit prefix sums and a 64-bit uniform draw (uniform_int_distribution<long long>, ThreadLocalRandom.nextLong(1, total + 1)). Python ints are unbounded. Under this problem's limits the total is at most 109, so int is enough.

How to answer

Compute the worst-case total from the constraints out loud before choosing the type.

Likely follow-ups
  • Real-valued weights: use doubles with upper_bound on a draw in [0, total).
