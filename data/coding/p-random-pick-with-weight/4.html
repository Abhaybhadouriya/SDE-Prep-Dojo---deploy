Approaches: brute -> better -> optimal

Hint 1

If every weight were 1, a uniform random index would do. How can you turn weight 3 into "three slots"?

Hint 2

You do not need the slots, only where each index's block of slots ends.

Hint 3

The block ends are increasing. What search finds the first end that is at least a given number?

1. Brute force - expand every ticket

Idea: build an array where index i appears w[i] times (for [3,1,4,2]: 0,0,0,1,2,2,2,2,3,3) and return a uniformly random element of it.

O(sum w)build time and space
O(1)per pick

What is wasted: the total can be 109, so the array does not fit in memory. But the array is just runs of equal values; each run is described by where it ends. -> rung 2.

2. Better - prefix sums + linear scan

Idea: store prefix[i] = w[0] + ... + w[i]. Draw t uniformly from [1, total]; walk i from 0 until prefix[i] >= t and return i.

t = random.randint(1, prefix[-1])
for i, p in enumerate(prefix):
    if p >= t:
        return i
O(n)build, O(n) per pick
O(n)space

What is wasted: the prefix array is sorted (weights are positive), and we are scanning it linearly for the first value >= t. That is exactly what binary search is for. -> rung 3.

3. Optimal - prefix sums + lower-bound binary search

  1. Build once: prefix[i] = prefix[i-1] + w[i]. Index i owns the tickets (prefix[i-1], prefix[i]], a block of exactly w[i] integers.
  2. Draw: t uniform in [1, total] (every ticket equally likely).
  3. Search: return the first i with prefix[i] >= t: bisect_left in Python, lower_bound in C++, sort.SearchInts in Go, a hand-written loop in Java.
O(n)build
O(log n)per pick
O(n)space

Why it works: the blocks (prefix[i-1], prefix[i]] partition the integers 1..total, and block i has w[i] members. A uniform t lands in block i with probability w[i] / total, which is what is asked. Because weights are positive, the prefix array is strictly increasing, so "the first prefix >= t" is unique and binary search finds it in O(log n).

Proof of the search loop (optional)

Invariant: the answer is in [lo, hi]. Start with [0, n-1]; the answer exists because prefix[n-1] = total >= t. If prefix[mid] >= t, mid is a candidate and nothing right of it can be the first, so hi = mid keeps the answer. Otherwise mid's block ends before t, as do all blocks left of it, so lo = mid + 1. The window shrinks every step because mid < hi when lo < hi; it stops at one index, the answer.

Draw from 1 or from 0? Both work if the comparison matches. Drawing t in [0, total) and searching for the first prefix > t (bisect_right, upper_bound) is the same partition shifted by one. Mixing the two (draw from 0, search with >=) gives index 0 one extra ticket and the last index one ticket too few.

Beyond O(log n): the alias method (Vose) preprocesses in O(n) into n equal-sized boxes, each holding at most two indices, so a pick is one uniform box plus one biased coin: O(1). Mention it as a follow-up; the interview answer is the binary search.
