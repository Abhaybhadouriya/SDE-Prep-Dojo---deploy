Approaches: brute -> better -> optimal

Hint 1

The last move into the goal was either "down" or "right". How many paths reach each of those two cells?

Hint 2

When you fill a row from left to right, which values from the previous row do you still need?

1. Brute force - try every path

Idea: paths(r, c) = 0 if out of the grid or on a rock, 1 at the goal, else paths(r+1, c) + paths(r, c+1).

Why it is slow: the same cell is reached through many different prefixes, and each time the whole subtree is re-explored. The call tree has up to C(m+n-2, m-1) leaves.

O(2m+n)time
O(m+n)stack

2. Better - memoise, or fill an m x n table

Cache paths(r, c): only m·n distinct states, each costs O(1). Bottom-up, the same thing is a table dp[r][c] = dp[r-1][c] + dp[r][c-1] for free cells, 0 for rocks, dp[0][0] = 1 if the start is free. A clean way to avoid special cases for row 0 and column 0 is to pad the table with an extra row and column of zeros and seed dp[0][1] = 1 (one highly voted solution does exactly this).

O(m·n)time
O(m·n)space

What is wasted: row r only reads row r-1. All older rows are dead memory. -> rung 3 keeps one row.

3. Optimal - one rolling row

ways = [0] * n; ways[0] = 1
for row in grid:
    for c in range(n):
        if row[c] == 1: ways[c] = 0          # rock
        elif c > 0:     ways[c] += ways[c-1]  # above (old) + left (new)
return ways[n-1]
O(m·n)time
O(n)space

Why it works: just before the update, ways[c] still holds the previous row's value (the cell above) and ways[c-1] already holds this row's value (the cell to the left). So the in-place += is exactly up + left. Column 0 has no left neighbour, so it just keeps the value from above, which also handles "a rock in column 0 blocks everything below it". The same holds for row 0: after a rock, every cell to its right adds 0 from the left and 0 from "above" (the initial zeros). And if the start is a rock, the first update sets ways[0] = 0 and nothing is ever non-zero. No special cases needed.

You can also roll over columns instead of rows and keep an array of length min(m, n); mention it, but it rarely matters.
