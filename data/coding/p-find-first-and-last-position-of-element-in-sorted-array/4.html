Approaches: brute -> better -> optimal

Hint 1

Finding a copy of the target is easy. What makes the first copy special?

Hint 2

When nums[mid] == target, could the first copy be at mid? Could it be to the left? So which half do you keep?

Hint 3

The last copy of 3 is just before the first value bigger than 3.

1. Brute force - linear scan

Idea: walk the array; remember the first index equal to the target and keep updating the last one.

O(n)time
O(1)space

What is wasted: it ignores the sorted order. Every comparison could discard half of the array instead of one element. -> rung 2.

2. Better - binary search for any copy, then expand

Idea: classic binary search finds some index with the target; then walk left while the previous value is the target, and right while the next one is.

i = classic_search(nums, target)     # any index, or -1
if i == -1: return [-1, -1]
lo = hi = i
while lo > 0 and nums[lo - 1] == target: lo -= 1
while hi + 1 < len(nums) and nums[hi + 1] == target: hi += 1
O(log n + k)time, k = number of copies
O(1)space

What is wasted: on [6,6,6,...,6] the walk is O(n), which breaks the stated requirement. The walk is itself a search for a boundary on sorted data, so it can be a binary search too. -> rung 3.

3. Optimal - two boundary searches

One helper, boundary(strict), returns the first index whose value passes a test: >= target when strict is false, > target when it is true, or n if no index passes.

  1. Half-open window. lo = 0, hi = n; the answer is always in [lo, hi], and hi = n means "none passes".
  2. Probe. mid = lo + (hi - lo) / 2. If nums[mid] passes, the answer is mid or to its left: hi = mid. Otherwise it is right of mid: lo = mid + 1.
  3. Stop at lo == hi. That index is the first one that passes.
  4. Combine. first = boundary(false). If first == n or nums[first] != target, the target is absent. Otherwise last = boundary(true) - 1.
O(log n)time (two searches)
O(1)space

Why it works: on a sorted array the test is monotone (F...F T...T), so "first T" is well defined and each probe tells you which side it is on. When nums[mid] passes we keep mid (hi = mid, not mid - 1) because mid itself may be the first T. Because mid < hi whenever lo < hi, both branches shrink the window, so the loop always ends. The targets are exactly the indices where the first test is T and the second is F: [first, boundary(true) - 1].

Why the two-element case never loops forever (optional)

With lo = 4, hi = 5, mid = 4. If it passes, hi = 4 = lo; if it fails, lo = 5 = hi. Either way the loop ends. The classic infinite loop comes from lo = mid (not mid + 1) with a floor midpoint, which this template never does.

Equivalent forms: C++ lower_bound(target) and upper_bound(target), or equal_range; Python bisect_left and bisect_right; Java has no bound in the standard library (Arrays.binarySearch returns some copy), so write the loop. Another common form calls one lower-bound helper twice, with target and target + 1; that is fine for integers in this range but needs care with overflow and does not work for doubles.
