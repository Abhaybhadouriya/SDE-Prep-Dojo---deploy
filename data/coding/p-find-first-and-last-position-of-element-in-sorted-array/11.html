Interview follow-ups

Return how many times the target occurs.

upper - lower where both are boundaries (0 when absent): boundary(true) - boundary(false). No equality check is needed.

How to answer

Point out that counting is cleaner than finding: the two boundaries are always valid indices in [0, n].

Likely follow-ups
  • Count values in a range [a, b]: upper(b) - lower(a).
Can you do it with a single binary search?

Two boundaries are needed, so the honest answer is "two searches, still O(log n)". You can share work (do one search until the window first contains a target, then split into two searches on the halves), but the asymptotic cost stays O(log n). A divide-and-conquer version that returns early when nums[lo] == nums[hi] == target is also O(log n).

How to answer

Say "two O(log n) searches is still O(log n)" and offer the shared-prefix optimisation.

Likely follow-ups
  • How many probes in the worst case? About 2·log2(n).
The array is too large to fit in memory and is read through get(i), with unknown length.

Find an upper end first by doubling: probe 1, 2, 4, 8, ... until get(i) is past the target or out of range (sentinel). Then run the same boundary searches inside [i/2, i]. Still O(log p), p = position of the answer (LC 702 style).

How to answer

Exponential search then binary search; mention it is also how you search a sorted stream or log file.

Likely follow-ups
  • Each get is a disk read: count I/Os, consider a B-tree index.
The sorted array was rotated (like LC 33), with duplicates. Find the first and last index of the target.

Find the rotation point (the minimum) first, then the array is two sorted parts and the target's block lies in one of them, or wraps across the cut. With duplicates, finding the minimum can be O(n) in the worst case ([2,2,2,...,1,2]), so say so.

How to answer

Reduce to the solved problem: locate the cut, then reuse boundary search on each part.

Likely follow-ups
  • Why do duplicates break the O(log n) guarantee? Equal ends give no information about the side.
Why lo + (hi - lo) / 2 rather than (lo + hi) / 2?

With 32-bit indices lo + hi can overflow when the array is near 231 elements (the famous JDK bug). Here n <= 105 so either works, but the safe form costs nothing. In Python integers do not overflow.

How to answer

Use the safe form by habit and explain in one line.

Likely follow-ups
  • (lo + hi) >>> 1 in Java is another safe form.
