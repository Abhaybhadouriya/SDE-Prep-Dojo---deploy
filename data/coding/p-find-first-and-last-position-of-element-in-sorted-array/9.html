60-second recall

  • Cue: sorted + first/last/count of a value in O(log n) -> lower and upper bound.
  • Insight: search for where a monotone test flips, not for the value itself.
  • State: lo = 0, hi = n (n means none); answer always in [lo, hi].
  • Trap: hi = mid (keep mid), lo = mid + 1; check first < n before nums[first].
  • Cost: two searches, O(log n) time, O(1) space; count = last - first + 1.
def first_true(test):            # test is F...F T...T over indices
    lo, hi = 0, len(nums)
    while lo < hi:
        mid = (lo + hi) // 2
        if test(nums[mid]): hi = mid
        else: lo = mid + 1
    return lo
first = first_true(lambda v: v >= t); last = first_true(lambda v: v > t) - 1

nums = [5, 7, 7, 8, 8, 10], t = 8. What do the two searches return: first index with v >= 8, first index with v > 8?

  1. 3 and 4
  2. 3 and 5
  3. 4 and 5
  4. 3 and 6
Lower bound = 3, upper bound = 5, so the answer is [3, 5 - 1] = [3, 4].

Same array, t = 6. The first search returns 1. What must the code check before answering?

  1. first < n and nums[first] == t
  2. first > 0
  3. lo == hi
  4. Nothing: 1 is the answer
The lower bound is an insertion point. nums[1] = 7 != 6, so the answer is [-1, -1]. If t were larger than every value, first = n and reading nums[n] would be out of bounds.

Inside while lo < hi, the test is true at mid. Why hi = mid and not hi = mid - 1?

  1. mid may itself be the first true index, so it must stay inside [lo, hi]
  2. It avoids integer overflow
  3. mid - 1 could become negative
  4. It is only style
hi = mid - 1 can skip the answer. The loop still ends because mid < hi whenever lo < hi.
