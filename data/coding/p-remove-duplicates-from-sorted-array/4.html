Approaches: brute -> better -> optimal

Hint 1

Where does the next distinct value have to go in the final array?

Hint 2

Keep a counter k of values kept so far. Which single earlier slot tells you whether nums[i] is a duplicate?

1. Brute force - collect the distinct values elsewhere

Idea: copy the distinct values into a new list (or an ordered set), then write them back over the start of nums and return the count.

O(n)time (O(n log n) with a tree set)
O(n)extra space

What is wasted: the extra buffer, which the task forbids. In Python, nums = sorted(set(nums)) even leaves the caller's list unchanged: it rebinds a local name. -> rung 2.

2. Better - delete in place by shifting

Idea: scan left to right; when nums[i] == nums[i-1], shift everything after i one place to the left and shrink the logical length.

O(n²)time (all equal)
O(1)extra space

What is wasted: each value is moved once per duplicate in front of it. Values do not have to be moved many times: each one has a single final slot, and we can drop it there directly. -> rung 3.

3. Optimal - read pointer and write pointer

k = 1
for i in range(1, len(nums)):
    if nums[i] != nums[k - 1]:
        nums[k] = nums[i]; k += 1
return k
  1. The prefix is the answer so far. nums[0..k-1] holds the distinct values seen so far, sorted. It starts as just nums[0], so k = 1.
  2. One comparison decides. Because the input is sorted, nums[i] is a duplicate exactly when it equals the largest kept value, which is nums[k-1].
  3. A new value goes to slot k. Write it and increase k. Since k ≤ i, the slot being written has already been read, so no unread input is destroyed.
  4. One pass, each element read once and written at most once.
O(n)time
O(1)extra space

Why it works: the loop keeps the invariant "nums[0..k-1] = the distinct values of the original nums[0..i-1], in order". A new distinct value is appended at the end of the prefix; a duplicate changes nothing. When i reaches n, the prefix holds all distinct values, and k is their count.

Proof (optional)

Comparing with nums[k-1] (the last kept value) rather than nums[i-1] (the previous input) is what makes this generalise. Both work for this problem: slot i-1 is only ever overwritten with its own value (a write to slot k = i-1 copies nums[i-1]), and in sorted input the previous value read equals the last value kept. The nums[k-1] form extends to "keep at most m copies": compare with nums[k-m] (LeetCode 80 uses m = 2). The value m slots back in the kept prefix equals x exactly when m copies of x are already kept, because the prefix is sorted.
