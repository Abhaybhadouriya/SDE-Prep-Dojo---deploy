Shape 5: comparator greedy (largest number)

Largest Number. Given a list of non-negative integers (1 to 100 of them, each 0 to 109), arrange them so their concatenation is the largest possible number, and return it as a string (it may not fit in any integer type). (Original: LeetCode 179.)

Sorting by numeric value fails (50 before 5 gives "505", but "550" is bigger), and so does plain descending string order: it puts "50" before "5" and turns 5, 56, 50, 9 into "956505", smaller than "956550". The right order compares the two ways of gluing a pair: put a before b when a + b > b + a as strings.

Why it is correct. The rule is transitive (if ab > ba and bc > cb then ac > ca; think of each string as a fraction of the form x / (10len - 1)), so it is a valid sort order. Then the exchange argument: in any arrangement, if two neighbours are in the "wrong" order, swapping them makes the number larger and leaves everything else in place. So the best arrangement has no wrong pairs, which is exactly the sorted one. Edge case: if the first element after sorting is "0", every element is 0; return "0", not "000".

Other comparator greedies: Queue Reconstruction by Height (tallest first, then insert at index k), job sequencing with deadlines, and "minimum time to finish tasks" problems that sort by a ratio. In each, write the pairwise swap check first; the sort key follows from it.
