Interview follow-ups

Allow duplicates (LC 381). What changes?

Map each value to a set of its indexes in the array. insert appends and adds the new index to the set. remove picks any index i from v's set, moves the last element (value w at index n-1) to i, removes n-1 from w's set and adds i, removes i from v's set (deleting the entry if empty), then pops. Order matters again when v == w. getRandom is unchanged and is automatically weighted by count.

How to answer

The top-voted community post says this was the follow-up in a real phone screen; practise it.

Likely follow-ups
  • Why a hash set of indexes rather than a list? (remove a specific index in O(1))
Is it really O(1)? What are the worst cases?

Average O(1): hash operations are O(1) expected, and array append is amortised O(1) (occasional doubling copies). Worst case per call is O(n) during a resize or with adversarial hash collisions. A pre-sized array and a randomised hash function reduce both.

How to answer

Use the words "expected" and "amortised" precisely; interviewers at this level check that.

Likely follow-ups
  • How do Java HashMaps defend against collision attacks? (treeified buckets)
Add getRandom weighted by a per-element weight.

With static weights: prefix sums + binary search, O(log n) per pick (LC 528), or the alias method for O(1) picks after O(n) setup. With updates: a Fenwick tree over weights gives O(log n) update and pick.

How to answer

Say O(1) is no longer realistic with dynamic weights and name the Fenwick tree.

Likely follow-ups
  • Explain the alias method briefly.
Make it thread-safe.

The two structures must change together, so one mutex around each operation is the simple, correct answer. A read-write lock helps only if getRandom dominates, and the random generator itself must be thread-local or locked. Lock-free versions are hard because remove touches two array slots and two map entries.

How to answer

Point out the multi-location invariant first; it is why fine-grained locking is tricky.

Likely follow-ups
  • How would you shard it across cores?
Add getRandom without replacement (each element returned once until all are drawn).

Keep a boundary k: draw an index in [0, k), swap that element with index k-1, decrement k, return it. This is an incremental Fisher-Yates shuffle; reset k to size when exhausted. Maintain pos for swapped elements too.

How to answer

Name Fisher-Yates; it is the same "swap to the end" idea.
