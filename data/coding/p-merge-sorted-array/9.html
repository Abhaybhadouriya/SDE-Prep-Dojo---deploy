Revision card

  • Cue: merge two sorted arrays into the one with free space at the end, in place.
  • Insight: fill from the back: the larger tail goes into the last free slot.
  • State: i = m - 1, j = n - 1, w = m + n - 1 (w = i + j + 1 always).
  • Trap: loop on j >= 0 and guard i >= 0; leftover nums1 is already in place.
  • Cost: O(m + n) time, O(1) space; copy + sort O((m+n) log(m+n)).
i, j, w = len_a - 1, len_b - 1, len_a + len_b - 1
while j >= 0:                        # until the second source is drained
    if i >= 0 and a[i] > b[j]: a[w] = a[i]; i -= 1
    else: a[w] = b[j]; j -= 1
    w -= 1

Quick quiz

Why does the loop stop when j < 0 even if i ≥ 0?

  1. It is a bug
  2. nums1[0..i] is already sorted and in its final place
  3. The rest are placeholders
  4. To save one comparison
When nums2 is empty, w == i, so the remaining nums1 values sit exactly where they belong.

nums1 = [0], m = 0, nums2 = [1], n = 1. What must the code avoid?

  1. Writing nums1[0]
  2. Reading nums2[0]
  3. Reading nums1[i] with i = -1
  4. Nothing special
The i >= 0 guard must come before nums1[i] in the condition.

Why merge from the back rather than from the front?

  1. The free space is at the back, so writes never hit unread values
  2. It is faster asymptotically
  3. It handles negatives
  4. It keeps the merge stable
Same O(m + n) either way; only the back avoids the O(m) copy.
