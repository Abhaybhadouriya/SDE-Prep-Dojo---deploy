Then merge forwards: put the read head of nums1 at index n (its first real value) and the write head at 0, and take the smaller head each time. The same invariant holds the other way round: the write head never passes the read head.

How to answer

Say the rule, not the code: "write into the side where the space is".

Return the merged array without duplicates.

Merge forwards into a new array and skip a value if it equals the last value written. Backwards in place also works: skip a value equal to nums1[w+1], then shift the result to the front at the end (or return the start index).

How to answer

Ask if the output may be shorter and where it should start.

  • Intersection of two sorted arrays (LC 349/350 sorted variant).
Merge k sorted arrays.

A min-heap of (value, array, index) heads: pop the smallest, push that array's next value. O(N log k) for N total values. Alternatively merge pairs in rounds (like merge sort), also O(N log k).

How to answer

Name both and say the heap is simpler to stream.

Likely follow-ups
  • The arrays are on disk and do not fit in memory: external merge sort with buffered readers.
No extra space at all: two separate sorted arrays, keep the smallest values in the first.

Compare the last of a with the first of b and swap while a[last] > b[first] (moving inwards), then sort both arrays: O((m + n) log(m + n)), O(1) extra. The gap method (shell-sort style, gap = ceil(len / 2) down to 1) does it without the sorts in O((m + n) log(m + n)).

How to answer

Point out why the back-fill trick does not apply: there is no free slot to write into.

Likely follow-ups
  • Prove the swap phase leaves every value of a ≤ every value of b.
One array is tiny (n = 3) and nums1 is huge (m = 10^6). Can you beat O(m + n)?

The values of nums1 that are larger than nums2's elements must still move right, so in the worst case you move O(m) values. But you can binary search where each nums2 value lands and move each block of nums1 with one memmove: O(n log m) comparisons plus the unavoidable data movement, which is fast in practice.

How to answer

Separate comparisons from data movement; this is how real libraries merge unbalanced runs (galloping in Timsort).
