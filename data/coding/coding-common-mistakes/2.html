2. Loops without a clear invariant

Symptom: binary search that loops forever on two elements, a sliding window that is off by one, < versus <= changed by trial and error until the examples pass. The interviewer asks "why hi = mid and not mid - 1?" and you do not know.

Fix: before the loop, write one comment that says what is true at the top of every iteration. Every update must keep it true, and the loop must end when it gives the answer. For binary search: "the answer is in [lo, hi]" with a half-open range.

  1. lo = 0, hi = 5 (one past the end, which means "not found"). mid = 2, a[2] = 3 < 4, so 0..2 are all too small: lo = mid + 1 = 3. The invariant holds.
  2. mid = 4, a[4] = 8 >= 4. Index 4 might be the answer, so it must stay inside: hi = mid, not mid - 1.
  3. mid = 3, a[3] = 5 >= 4: hi = 3. The range [3, 3) is now empty.
  4. lo == hi: the invariant says the answer is in [3, 3], so it is 3. No special cases, and the same code returns 5 for "not found" and 0 for an empty array.

The same idea fixes other loops: for a sliding window, "the window [l, r] is valid after the inner while"; for two pointers, "if an answer exists, it uses an index in [lo, hi]"; for Dutch flag partitioning, four named regions. If you cannot say the invariant, you are guessing.
