Scenario drills: catching the mistake live

The mistakes on this page are easy to list and hard to catch while the clock runs. Each drill shows the moment the mistake appears, a weak reaction and a strong one. Notice that the strong answer always names the cause before it changes any code.

Scenario: the greedy that looked right

For "jump game II" (fewest jumps to reach the last index) you chose "always jump to the farthest index you can land on". On the example it gives the right count. The interviewer asks: "Why is that greedy correct?"

Weak: "It works on the examples, so it should be fine." The interviewer asked for a reason, and examples are not a proof.

Strong: "Jumping to the farthest landing index is not the safe greedy: an index you land on short of that may reach further on the next jump. The safe version is BFS by levels: the indexes reachable with j jumps form a range, the next range ends at the farthest point any index in this range can reach, and each range costs one jump. Any optimal path has its j-th landing inside range j, so counting ranges cannot be beaten. O(n) time, O(1) space."

Likely follow-ups
  • Find an input where "land on the farthest index" goes wrong. (try [3, 4, 1, 1, 0, 1]: landing on index 3 leads to the 0 at index 4, a dead end, while 0 → 1 → 5 takes two jumps)
  • When does a greedy need a proof, and when is a quick counter-example search enough?

Scenario: the bug you find during the dry run

You finished binary search for "first index with a[i] >= x" and dry-run [1, 3, 5] with x = 6. The loop never ends.

Weak: "Let me rewrite it with a different template." You throw away code that is one line from correct and lose five minutes.

Strong: "With x bigger than every value, lo moves right until lo == hi == 2, but my loop is while lo <= hi with hi = mid, so it spins. I mixed two templates. With a half-open range [lo, hi) the loop is lo < hi and hi starts at n. Changing those two lines, lo ends at 3, which is n and means 'no such index'. Correct."

Likely follow-ups
  • What does your function return when every value is smaller than x?
  • Why write mid = lo + (hi - lo) / 2 instead of (lo + hi) / 2?

Scenario: overflow found late

You summed values up to 109 in an int for "maximum sum of a subarray of length k", and the interviewer asks: "What is the largest value this sum can take?"

Weak: "It should fit." Or change every variable to long long without saying which one actually overflows.

Strong: "k can be 105 and values reach 109, so the sum reaches 1014, far above 231 - 1, which is about 2.1 × 109. Only the running sum and the best sum need 64 bits; indexes stay int. In Python this cannot happen; in Java and Go I would use long and int64."

Likely follow-ups
  • Where else does overflow hide? (the mid computation, products, a - b comparators)
  • How do you check an overflow guess quickly? (largest value times count, said out loud)

Scenario: mutating the input you still need

For "merge intervals" you sort the input list in place. Later you realise the problem asks you to report which original intervals were merged, by their original index.

Weak: Notice nothing; the interviewer points it out after the final answer is wrong.

Strong: "I sorted intervals in place, but I return original indexes. Two fixes: sort a list of indexes by start, or copy before sorting. Sorting indexes is cheaper: O(n) extra integers. Complexity stays O(n log n) time and O(n) space."

Likely follow-ups
  • Is it okay to modify the input in an interview? (ask first; many interviewers say yes, but say it out loud)
  • What extra memory do the standard sorts use in Python, Java and C++?

Scenario: deep recursion on a big input

Your DFS for "number of islands" is recursive. The interviewer asks what happens on a 1000 × 1000 grid that is all land.

Weak: "Recursion is fine, it is the standard approach."

Strong: "The DFS can go about 106 calls deep on a snake-shaped path. Python stops near 1,000 frames by default, and C++ or Java can overflow the thread stack. I would switch to an explicit stack, or BFS with a queue: same O(rows × cols) time, and the extra memory is on the heap. I will mention it now and convert it if you want."

Likely follow-ups
  • What is the default recursion limit in Python, and why is raising it risky?
  • Does BFS use less memory than DFS here? (not in the worst case: both can hold O(rows × cols) cells)
