From your world: the TCP send window

From your world

You have seen this algorithm in every TCP stack. The sender tracks three sequence numbers (RFC 9293, section 3.3.1): SND.UNA, the oldest byte not yet acknowledged; SND.NXT, the next byte to send; and SND.WND, the window the receiver allows. The usable window is [SND.UNA, SND.UNA + SND.WND).

An ACK moves the left edge forward. A window update moves the right edge forward. Neither edge ever moves back. "Bytes in flight" = SND.NXT - SND.UNA is window state updated in O(1) per event, never recomputed by walking the retransmit queue. That is exactly the expand / shrink / record template with a running count.

Two more bridges: a ring buffer with head and tail indexes is a sliding window over an infinite stream, and a rate limiter that counts requests in "the last 60 seconds" is a time-based window where entries leave when they expire. And the "missing" counter of the minimum-window template is a reference count: the window is usable when it drops to zero.
