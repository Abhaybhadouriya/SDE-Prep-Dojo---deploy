Interview questions

Why is the expand/shrink loop O(n) when it has a while loop inside a for loop?

Both pointers only move forward. right moves n times. Every iteration of the inner while moves left forward by one, and left can never pass n, so the inner body runs at most n times over the whole run, not per outer iteration. Total: at most 2n pointer moves, each O(1) with an array or hash map of counts.

How to answer

Name the potential argument: "each element enters once and leaves once". Then state O(n) time and O(alphabet) or O(k) extra space.

Likely follow-ups
  • What if removal is not O(1)? (Then the bound is n times the removal cost, for example O(n log n) with a TreeMap.)
Longest run of 1s if you may flip at most k zeros. Walk me through it.

State = number of zeros inside the window. Expand with right; if a[right] == 0, zeros++. While zeros > k, move left and decrement zeros when a zero leaves. After the loop the window is valid; record right - left + 1. O(n) time, O(1) space.

A known shortcut: replace the while with an if. The window then never shrinks, it only slides when invalid, so its length stays at the best seen so far, and the answer is n - left at the end. It is correct but harder to explain; give the while version first.

How to answer

Restate as "longest window with at most k zeros", which shows you recognised the pattern.

Likely follow-ups
  • The input is a stream and k = 1. (Keep the index of the last zero; O(1) memory.)
  • Return the flipped positions too. (Record left and right with the best.)
Minimum window substring: how do you check "covers t" in O(1)?

Keep need[c] = copies of c still missing (starts as counts in t) and missing = total copies still missing. Adding c: if need[c] > 0, missing--; then need[c]--. Removing c: need[c]++; if it became > 0, missing++. The window covers t exactly when missing == 0. Negative need values mean "extra copies", which is fine.

How to answer

Say it is a "shortest" window, so you record inside the shrink loop. Complexity O(|s| + |t|).

Likely follow-ups
  • t has duplicates. (Counts handle it already.)
  • Order matters (a subsequence). (Minimum window subsequence: two-pointer scan forward then backward, or DP.)
Sliding window maximum: why a deque and not a heap?

A max-heap gives O(n log n) and needs lazy deletion of expired items (keep (value, index) and pop the top while its index is outside). The monotonic deque is O(n): it stores indexes with strictly decreasing values; a newcomer pops every smaller value at the back because those can never be the max while the newcomer is in the window; the front is the max and is popped when it expires.

How to answer

Give the heap first as the "obvious" fix, then the deque with the domination argument: "older and smaller is useless".

Likely follow-ups
  • Minimum instead? (Increasing deque.)
  • Median of each window? (Two heaps or an order-statistics tree; no deque trick.)
Count subarrays with exactly K distinct values. Why can't you use one window?

"Exactly K" is not monotone: shrinking a valid window can make it invalid, and so can growing it, so there is no single "best left" for each right. "At most K" is monotone, and the number of windows ending at right with at most K distinct is right - left + 1. So exactly(K) = atMost(K) - atMost(K - 1): two O(n) passes.

How to answer

Show the counting rule first, then the subtraction. Mention that the one-pass version with two left pointers exists.

Likely follow-ups
  • Binary array, count subarrays with sum S. (Same trick, or prefix sums.)
Longest repeating character replacement: why is it fine never to decrease max frequency?

Validity is length - maxf <= k. We only care about windows longer than the best so far, and a longer valid window needs a larger maxf. A stale (too high) maxf can only keep a window the same length as the best one already found; it can never report a length that was not achieved. So the answer stays correct with a non-decreasing maxf, and each step is O(1).

How to answer

Offer the safe version (recompute max over 26 counts, O(26n)) first, then the optimisation with the argument.

Likely follow-ups
  • Alphabet is all Unicode. (Hash map; recompute is no longer cheap, so the stale-max argument matters.)
The data is a stream of events with timestamps. Count events in the last 60 seconds per query.

This is a time-based window: keep a queue (or ring buffer) of timestamps. On each new event push it; on each query pop from the front while front <= now - 60. Size = answer. Amortised O(1) per event. If events are huge in number, bucket by second (60 counters in a ring) for O(1) memory.

How to answer

Tie it to rate limiting (sliding log vs sliding window counter) and say which you pick for exactness vs memory.

Likely follow-ups
  • Many threads write. (Per-shard counters or a lock per bucket.)
When is a problem about subarrays NOT a sliding window?

When the condition is not monotone in the window size: exact sums with negative numbers (use prefix sums plus a hash map), medians (two heaps), "maximum subarray sum" with no constraint (Kadane, which is a DP), or anything about subsequences.

How to answer

Give the test: "if I shrink a valid window, does it stay valid?" If no answer comes out cleanly, it is not a window.

Likely follow-ups
  • Subarray sum equals k with only positives. (Then a window works.)
