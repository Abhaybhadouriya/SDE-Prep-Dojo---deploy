60-second recall

  • Cue: singly linked list + compare front with back -> middle + reverse half.
  • Insight: reversing the back half lets you walk "backwards" forward; O(1) space.
  • State: slow, fast; back (reversed half head); a, b walkers; ok flag.
  • Trap: loop on back not front; restore before return; recursion is O(n) stack.
  • Cost: O(n) time, O(1) space; array copy or stack is O(n) space.
slow = fast = head
while fast.next and fast.next.next:
    slow, fast = slow.next, fast.next.next
back = reverse(slow.next)
a, b, ok = head, back, True
while b: ok &= a.val == b.val; a, b = a.next, b.next
slow.next = reverse(back)

The loop is while fast.next and fast.next.next. Where does slow stop for 1->2->2->1 and for 1->2->3->2->1?

  1. At the first 2, and at the 3
  2. At the second 2, and at the 3
  3. At the first 2, and at the second 2
  4. At the head both times
The back half starts at slow.next: [2, 1] in both cases. In the odd case the middle 3 stays in the front half and is never compared.

Why does the compare loop run while b (the reversed back half) and not while a?

  1. The back half is never longer than the front half, and the front walk carries on into the back half's old first node
  2. It is faster
  3. a can be null at the start
  4. There is no difference
slow.next still points at the node that is now the tail of the reversed half, so a would walk one node past the front half.

Why reverse the back half again before returning?

  1. The caller still owns the list; leaving it changed is a side effect
  2. Without it the answer is wrong
  3. It frees memory
  4. LeetCode rejects the answer otherwise
The answer was already decided. Restoring keeps the function free of side effects, and interviewers often ask for it.
