Interview follow-ups

Prove that the earliest-end greedy is optimal.

Exchange argument: take any optimal set and its first interval B. The globally earliest-ending interval G ends no later than B, so replacing B with G keeps the set valid and the same size. Repeat on the remaining intervals (those starting at or after G's end).

How to answer

Two sentences: "swap the first one for the earliest finisher; nothing later can conflict because G ends sooner".

Likely follow-ups
  • Why does "shortest first" fail? Show [[1,5],[4,7],[6,10]]: the short middle one blocks both others.
Return which intervals to remove, not just how many.

Sort indices by end instead of sorting the intervals, and push the index of every interval that fails the start >= lastEnd test into the result. Same O(n log n).

How to answer

Mention that the answer set is not unique; the greedy returns one valid minimum set.

Likely follow-ups
  • Keep the original order of the remaining intervals: mark removed indices, then filter.
Each interval has a profit; maximise the total profit kept (LC 1235).

Weighted interval scheduling. Sort by end. dp[i] = max(dp[i-1], profit_i + dp[p(i)]), where p(i) is the number of intervals ending at or before start_i, found by binary search over the sorted ends. O(n log n) time, O(n) space.

How to answer

Say why the greedy breaks: one heavy long interval can be worth more than many light short ones.

Likely follow-ups
  • Reconstruct the chosen set: walk back through dp choices.
You now have k rooms instead of one. Keep as many meetings as possible.

Sort by end. Keep a multiset of the k rooms' last end times. For each meeting, find the room whose end is the largest value ≤ start (best fit); if one exists, assign it and update its end, otherwise drop the meeting. O(n log k).

How to answer

Best fit, not any free room: giving the meeting the room that became free latest keeps earlier-free rooms for meetings that start sooner.

Likely follow-ups
  • Minimum rooms to keep all meetings: that is LC 253, a min-heap of end times.
Intervals arrive as a stream; answer "can I accept this booking?" online.

Keep the accepted bookings in a balanced BST keyed by start (TreeMap / std::map). For a new [s, e), check the floor entry (its end must be ≤ s) and the ceiling entry (its start must be ≥ e). O(log n) per booking. This is LC 729 My Calendar I.

How to answer

Note that online acceptance is first-come-first-served, so it no longer maximises the count; that needs the whole list (offline greedy).

Likely follow-ups
  • Allow double bookings but not triple (LC 731): a sweep-line count map.
