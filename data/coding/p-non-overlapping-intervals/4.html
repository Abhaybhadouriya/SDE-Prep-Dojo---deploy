Approaches: brute → better → optimal

Hint 1

Instead of choosing what to remove, choose what to keep. What is the largest set of intervals that do not overlap?

Hint 2

Among all intervals, which one is the safest to keep first? Think about which one leaves the most room on the right.

1. Brute force - try every subset

Idea: for every subset of intervals, check if it is pairwise non-overlapping and remember the largest. The answer is n minus that size.

O(2^n · n)time
O(n)space

What is wasted: we re-check the same compatible chains over and over. Sorting gives the chains an order, which gives a DP.

2. Better - DP like longest increasing subsequence

State: sort by start; keep[i] = the largest compatible set that ends with interval i. Transition: keep[i] = 1 + max(keep[j]) over j < i with end_j <= start_i. Base case: keep[i] = 1. Answer: n - max(keep).

O(n²)time (10^10 at n = 10^5: too slow)
O(n)space

What is wasted: we never need the whole table. An exchange argument shows that the interval with the earliest end can always be kept, which collapses the DP into one greedy scan.

3. Optimal - sort by end, keep greedily

intervals.sort(key=lambda iv: iv[1])        # core: 5 lines
kept, last_end = 0, float("-inf")
for s, e in intervals:
    if s >= last_end: kept, last_end = kept + 1, e
return len(intervals) - kept
  1. Flip the question. Fewest removed = n - most kept.
  2. The first finisher is always safe. Some best answer contains the interval with the smallest end (exchange argument below).
  3. Then repeat on what is left. Throw away everything that starts before that end, and pick the next earliest end. Sorting by end makes this one left-to-right scan with one variable, lastEnd.
  4. Touching is allowed. Use start >= lastEnd, not >.
O(n log n)time (the sort)
O(1)extra space (plus the sort's own)

Why it works: let G be the interval with the smallest end, and take any optimal set of kept intervals, sorted. Its first interval B ends at or after G ends. Swap B out and G in: every other kept interval started at or after B's end, so it also starts at or after G's end. The set is still valid and has the same size, so some optimal answer keeps G. Remove G and everything that overlaps it, and the same argument applies to what is left. That is exactly what the scan does.

Proof (optional) - "greedy stays ahead"

Let the greedy keep g1, g2, ... and an optimal answer keep o1, o2, ..., both sorted by end. By induction end(gk) ≤ end(ok): true for k = 1 by the choice of g1; and ok+1 starts at or after end(ok) ≥ end(gk), so ok+1 was still available to the greedy at step k + 1, which therefore picks something ending no later. If the optimum had more intervals than the greedy, its next one would still be available when the greedy stopped, a contradiction.

Variant - sort by start instead

Sorting by start also works if, on an overlap, you keep the one with the smaller end: if s < lastEnd: removed += 1; lastEnd = min(lastEnd, e) else: lastEnd = e. It is the same greedy written differently; sorting by end is easier to prove out loud.
