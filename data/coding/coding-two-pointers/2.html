Opposite ends 1: pair sum in a sorted array

The problem, in our words. A sorted (non-decreasing) list of integers vals is given, 1-indexed, plus an integer goal. Find the two positions p < q with vals[p] + vals[q] = goal and return [p, q] (1-based). There is exactly one solution, a position may not be used twice, and you may use only constant extra space.

  • 2 <= vals.length <= 3 x 104; -1000 <= vals[i] <= 1000; -1000 <= goal <= 1000; exactly one answer.
  • Example: vals = [1, 4, 6, 9, 12], goal = 15 -> [3, 4] (6 + 9). Example: vals = [-5, -1, 0], goal = -6 -> [1, 2].

Practice it: LeetCode 167 - Two Sum II (input array is sorted) · our write-up: Two Sum II. The unsorted version with a hash map is on the previous page.

  1. 1 + 12 = 13 < 15. Even the biggest partner (12) is not enough for 1, so 1 is in no answer: lo moves right.
  2. 4 + 12 = 16 > 15. Even the smallest partner left (4) is too much for 12, so 12 is in no answer: hi moves left.
  3. 4 + 9 = 13 < 15. Even the biggest partner (9) is not enough for 4, so 4 is in no answer: lo moves right.
  4. lo = 2, hi = 3: 6 + 9 = 15, the target. Return the 1-based positions [3, 4].

Why moving a pointer never skips the answer

Picture every possible pair as a cell in a table: row i, column j, with i < j. Because the array is sorted, sums grow to the right along a row and grow downwards along a column. The pointers always sit at the top-right corner of the part of the table that is still alive.

Invariant, in one line: "if an answer exists, it uses an index in [lo, hi]". When vals[lo] + vals[hi] < goal, vals[hi] is the largest partner vals[lo] can still get, so lo is in no answer and lo++ keeps the invariant. The other case is the mirror image.
