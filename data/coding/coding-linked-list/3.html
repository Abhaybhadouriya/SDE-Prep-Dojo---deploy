Move 2: fast and slow pointers

Two pointers start at the head. slow moves one node per step; fast moves two. Three classic questions fall out of this one loop:

  1. Middle. When fast reaches the end, slow has walked half as far, so it sits at the middle. With the loop condition while fast and fast.next, an even-length list gives the second middle (node 4 of 6). Start fast at head.next if you need the first middle, which you do when splitting a list for merge sort.
  2. Cycle? If the list ends, fast hits null. If it loops, fast gains one node on slow every step inside the loop, so it must land exactly on slow. It cannot jump over it, because the gap shrinks by exactly one each step.
  3. k-th from the end. A variation with equal speeds: move fast k nodes ahead first, then move both by one. When fast runs off the end, slow is k nodes behind it.

This is Floyd's cycle-finding algorithm (the "tortoise and hare"). Click through it on a list where the tail points back to node 3.

  1. Both pointers start at the head, node 1.
  2. One step: slow goes to 2, fast jumps two nodes to 3.
  3. slow at 3 (it has entered the loop); fast at 5.
  4. slow at 4; fast goes 6, then back round to 3. Inside the loop fast is now one node behind slow, and the gap closes by one node every step.
  5. slow at 5, fast at 5: they meet. A cycle exists. If fast had hit null, the answer would be "no cycle".
  6. Phase 2: put a pointer p back at the head and keep q at the meeting point.
  7. Move both one node at a time: p at 2, q at 6.
  8. p and q meet at node 3, which is exactly where the cycle starts. The next section shows why this always works.

The loop behind the steps. Invariant: fast moves two steps for each step of slow, so inside a cycle the gap closes by one per step and they must meet; after the meeting, a pointer from the head and one from the meeting point reach the cycle start together. Lifted unchanged from the tested templates below.

// Floyd: returns the node where the cycle starts, or nullptr.
ListNode* detectCycle(ListNode* head) {
    ListNode* slow = head;
    ListNode* fast = head;
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) {           // phase 1: they met inside the loop
            ListNode* p = head;       // phase 2: one from head, one from meeting point
            while (p != slow) { p = p->next; slow = slow->next; }
            return p;
        }
    }
    return nullptr;
}
def detect_cycle(head: Optional[ListNode]) -> Optional[ListNode]:
    """Floyd: node where the cycle starts, or None."""
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:                 # phase 1: met inside the loop
            p = head                     # phase 2: walk both at speed 1
            while p is not slow:
                p, slow = p.next, slow.next
            return p
    return None

Why phase 2 finds the start

Slow cannot finish a whole loop before fast catches it: once slow enters, fast is at most L-1 nodes behind and closes one node per step. That is why slow has walked only a + b with b < L. The whole algorithm is O(n) time and O(1) memory. A hash set of visited nodes also works in O(n) time but costs O(n) memory; mention it as the first idea, then improve.

The same loop finds a duplicate in an array of n+1 numbers in the range 1..n (LeetCode 287): treat i -> nums[i] as a next pointer. The duplicate value is the node two different indices point to, which is the start of a cycle. "Happy number" is the same trick on the digit-square-sum function. Spotting that a function x -> f(x) is a linked list is a favourite follow-up.
