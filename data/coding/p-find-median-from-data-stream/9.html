  • Cue: stream + "median / middle / percentile so far" -> two heaps split at the boundary.
  • Insight: only max(small half) and min(large half) decide the median.
  • State: low = max-heap (small half), high = min-heap (large half), len(low) - len(high) in {0, 1}.
  • Trap: push through low then move its top up (order), then rebalance (size); divide as double.
  • Cost: O(log n) add, O(1) median, O(n) space; sort-per-query O(n log n).
def add(x):
    push(high, pop_max(push(low, x)))   # order rule
    if len(high) > len(low):
        push(low, pop_min(high))        # size rule
def median():
    return top(low) if len(low) > len(high) else (top(low) + top(high)) / 2

Which heap holds the SMALLER half?

  1. min-heap
  2. max-heap, so its top is the largest of the small half
  3. either
  4. neither, it is a sorted list
The median needs max(small half) and min(large half): a max-heap and a min-heap.

Why push every new number through low first, then move low's top to high?

  1. speed
  2. it keeps every element of low <= every element of high
  3. Python needs it
  4. to keep sizes equal
This fixes the ORDER. A separate rebalance step then fixes the SIZE.

Sizes are equal and the tops are 2 and 3. In Java or C++, what can go wrong?

  1. nothing
  2. (2 + 3) / 2 in integers gives 2, not 2.5
  3. the heap is empty
  4. it overflows
Divide as a double: (a + b) / 2.0. For values near 10^5 the sum fits; in general use a + (b - a) / 2.0.
