Approaches: brute → better → optimal

Hint 1

You never need the whole sorted order. Which values decide the median?

Hint 2

Keep the lower half and the upper half apart. What do you need to read quickly from each half?

Hint 3

A new value can break two rules: "small half <= large half" and "sizes differ by at most one". Fix the first by passing through one heap, then fix the second by moving one top.

1. Brute force - store everything, sort on each query

Idea: append to a list in addNum; in findMedian, sort a copy and read the middle.

O(1)add
O(n log n)median
O(n)space

What is wasted: each query re-sorts values that were already in order last time. -> rung 2.

2. Better - keep the list sorted (insertion sort)

Idea: binary-search the insert position (bisect.insort, lower_bound + insert) so the list is always sorted; the median is an index lookup.

O(n)add (shifting)
O(1)median
O(n)space

What is wasted: the search is O(log n) but the shift is O(n). We keep the full order of both halves, and we only need their boundary. -> rung 3.

3. Optimal - two heaps

heapq.heappush(high, -heapq.heappushpop(low, -num))   # enter via low, its max moves up
if len(high) > len(low):
    heapq.heappush(low, -heapq.heappop(high))          # rebalance sizes
median = -low[0] if len(low) > len(high) else (-low[0] + high[0]) / 2
  1. Two halves, two heaps. low is a max-heap of the smaller half, high a min-heap of the larger half.
  2. Order rule: every value in low <= every value in high. Push the new value into low, then move low's top to high. Whatever moved up is the largest of the small side, so the rule holds even if num was huge.
  3. Size rule: len(low) is len(high) or one more. Step 2 always grows high; if it is now bigger, move its top back down.
  4. Read the answer from the tops. Odd count: low's top. Even count: the mean of both tops.
O(log n)add (3 heap ops)
O(1)median
O(n)space

Why it works: the order rule means the k smallest values are exactly the contents of low, and the size rule fixes k = ceil(n/2). So low's top is the ceil(n/2)-th smallest value and high's top is the next one: exactly the one or two middle values.

Proof (optional)

Assume both rules hold before addNum(x). After pushing x into low and moving m = max(low ∪ {x}) to high: every value left in low is <= m, and m <= old max(low) or m = x; in both cases m <= every old value of high or m is the largest of the small side, so max(low) <= m <= min(high ∪ {m}). The order rule holds. Sizes: before, (k, k) or (k+1, k); after the move, (k, k+1) or (k+1, k+1). Only the first breaks the size rule, and moving min(high) down keeps the order rule because that value is >= everything in low. Both rules hold again, by induction.
