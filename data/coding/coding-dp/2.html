The four-step recipe

Every DP solution, from climbing stairs to edit distance, is the same four decisions. Say them out loud in the interview, in this order, before writing code:

  1. State. What does dp[i] (or dp[i][j]) mean, in one exact English sentence? "dp[i] = number of ways to reach step i." "dp[i] = most money from houses 0..i." Most DP bugs are a vague state.
  2. Transition. How is a state built from smaller states? Think about the last decision: the last step was 1 or 2; the last house was robbed or skipped; the last character was decoded alone or with its neighbour.
  3. Base cases. The smallest states you can answer directly (dp[0], empty string, first row of a grid). Pick them so the transition never reads outside the table.
  4. Order and answer. Fill states so every state's inputs are ready first (usually increasing i). Say where the answer lives: dp[n], dp[n-1], the max over all dp[i], or dp[R-1][C-1].

Then state the cost: number of states x work per transition. Climbing stairs: n states x O(1) = O(n). Longest increasing subsequence: n states x O(n) = O(n2). This one formula gives the complexity of every DP you will write.

Interviewers love this: starting from a brute-force recursion, pointing at the repeated subproblem in the call tree, adding a memo, and then offering the bottom-up and O(1)-space versions. It shows you understand why DP works rather than recalling a formula.
