Approaches: brute → better → optimal

Hint 1

This is Subarray Sum Equals K with only 0s and 1s. Does the prefix-sum trick still work? Can you save the map?

Hint 2

Counting subarrays with sum at most S is easy with a window. How do you turn "at most" into "exactly"?

1. Brute force - every start, running sum

Idea: for each l, extend r and count every time the running sum equals goal. You may stop once the sum passes goal (it never comes back down: no negatives).

O(n2)time
O(1)space

What is wasted: each end is paired with every start one by one. The starts that work for an end form one contiguous range, so we only need its two edges.

2. Better - prefix sums + count map

Idea: sum(l..r) = pre[r+1] - pre[l]. Walk once with a running sum run; add seen[run - goal]; then record run. Seed seen[0] = 1. Since prefix sums of 0/1 values lie in 0..n, an int array of size n + 1 can replace the hash map.

seen = [0] * (n + 1); seen[0] = 1
run = ans = 0
for x in nums:
    run += x
    if run >= goal:
        ans += seen[run - goal]
    seen[run] += 1
O(n)time
O(n)space

Why it is worth saying: it is the general tool (it works with negatives too) and is often the first thing to code. The window version below is the "can you do O(1) space?" answer.

3. Optimal - two counting windows

  1. atMost(S): grow right, add nums[right]; while the sum exceeds S, drop nums[left]. Now every start in [left..right] gives a sum ≤ S, so add right - left + 1.
  2. Subtract: answer = atMost(goal) - atMost(goal - 1). Subarrays with sum ≤ goal minus those with sum ≤ goal - 1 are exactly those with sum = goal.
  3. Guard: atMost(-1) must return 0 (goal = 0). Without the guard the loop would try to shrink an empty window.
O(n)time (two passes)
O(1)space

Why it works: for a fixed end r, the sum of [l..r] shrinks (weakly) as l moves right, because values are non-negative. So the starts with sum ≤ S form a suffix [LS(r)..r], and LS(r) never moves left as r grows: a window can track it. The starts with sum exactly goal are those in the suffix for S = goal but not in the suffix for S = goal - 1, which is the band [Lgoal(r) .. Lgoal-1(r) - 1]. Summing the band sizes over r gives the answer, and summing suffix sizes separately and subtracting gives the same number.

Why one window with "shrink while sum > goal" is not enough: it finds one left edge per end, but with leading zeros several starts are valid at once ([0,0,1] with goal 1 has three subarrays ending at the 1). You need the second edge, and atMost(goal - 1) supplies it. A one-pass variant keeps both edges (or counts the zeros just after left) in the same loop; it is the same idea with more bookkeeping.
