Interview follow-ups

Do it without a dummy node.

Start lead and trail on head and move lead n steps. If lead is now null, n equals the length and the head is the target: return head.next. Otherwise slide both while lead.next exists and unlink trail.next. Same cost, one extra branch.

How to answer

Name the exact case the dummy was hiding (n == length) and show the one check that replaces it.

Likely follow-ups
  • In C: use struct node **pp = &head as the trailing pointer and write *pp = (*pp)->next; no dummy, no branch.
What if n can be larger than the length (invalid input)?

Guard the gap loop: before each of the n moves, check lead.next. If it is null, the list has fewer than n nodes, so return the list unchanged or raise an error, whichever the interviewer wants. The slide loop then never sees a null lead.

How to answer

Ask what the expected behaviour is, then guard the gap loop.

Likely follow-ups
  • Return the k-th node from the end, or -1 if it does not exist (the GfG version).
Is the gap version really faster than counting twice?

Not in big-O, and not much in pointer moves: both read about 2L - n nodes. The gap version wins when the list can only be read once (a stream or iterator) and has better locality, since trail revisits nodes lead touched only n steps earlier. For a 30-node list either is fine; I say this rather than claim a big speed-up.

How to answer

Be precise about what "one pass" buys you.

Likely follow-ups
  • Solve it with O(n) memory and a single read of a stream: keep the last n + 1 nodes in a ring buffer.
Solve it recursively.

Recurse to the end and count on the way back: the function returns the 1-based position from the end. When a node learns that its next has position n, it unlinks it (node.next = node.next.next). Call it on a dummy so the head is covered. O(L) time, O(L) stack.

How to answer

Give the return value (position from the end) and the stack cost.

Likely follow-ups
  • Why is this worse for long lists? (Stack depth L; the iterative version is O(1).)
Remove the n-th node from the end of a doubly linked list, or a circular one.

Doubly linked with a tail pointer: walk n - 1 steps back from the tail and unlink with both neighbours (fix prev.next and next.prev, plus head/tail if needed). Circular singly linked: count L once (stop when you are back at the start), take k = L - n steps from the head to land on the predecessor, and update the head if the head was removed.

How to answer

Show which pointers must be fixed for each list type.

Likely follow-ups
  • How does the kernel's list_del() unlink in O(1) with no search? (It is doubly linked and you already hold the entry.)
You are given only a pointer to the node to delete (not the head).

That is LC 237: copy the next node's value into this node and unlink the next node. It works for every node except the tail, and it changes node identity (anyone holding a pointer to the next node now holds a removed node), which is worth saying.

How to answer

Give the copy trick and its two limits.

Likely follow-ups
  • Why can't it delete the tail? (There is no next value to copy, and no way to reach the predecessor.)
