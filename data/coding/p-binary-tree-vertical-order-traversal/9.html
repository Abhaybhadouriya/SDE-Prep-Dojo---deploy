60-second recall

  • Cue: nodes by column, top to bottom, same cell left to right.
  • Insight: BFS order = the required order; columns are a contiguous range.
  • State: queue of (node, col); map col -> list; lo, hi.
  • Trap: not DFS; not sorted by value (that is 987); empty tree.
  • Cost: O(n) time, O(n) space.
if not root: return []
cols, lo, hi, q = defaultdict(list), 0, 0, deque([(root, 0)])
while q:
    n, c = q.popleft(); cols[c].append(n.val); lo, hi = min(lo, c), max(hi, c)
    if n.left: q.append((n.left, c - 1))
    if n.right: q.append((n.right, c + 1))
return [cols[c] for c in range(lo, hi + 1)]

Why BFS and not a pre-order DFS that records each node's column?

  1. DFS can reach a deeper node of column c before a shallower one, which breaks top-to-bottom order
  2. DFS is slower
  3. DFS cannot compute columns
  4. Both give the same answer
A DFS would need the row too, plus a stable sort. BFS emits each column in the required order for free.

Two nodes share the same row and column. Which comes first in LC 314?

  1. The one further left (BFS order)
  2. The smaller value
  3. The larger value
  4. Either one
Sorting ties by value is the rule in LC 987, a different problem.

Why track lo and hi instead of sorting the map's keys?

  1. A tree's columns form a contiguous range, so walking lo..hi lists them with no sort
  2. It is needed for correctness
  3. It uses less memory
  4. Hash maps cannot be iterated
Every column between the leftmost and the rightmost node holds at least one node, so the walk is O(width).
