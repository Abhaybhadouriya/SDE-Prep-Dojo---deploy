60-second recall

  • Cue: k closest / k smallest / k largest -> bounded heap of size k, or quickselect.
  • Insight: for the k smallest keep a MAX-heap; a new item only has to beat the root.
  • State: heap of (dist, point) with size <= k; dist = x*x + y*y (no sqrt).
  • Trap: heap direction, sqrt/doubles, fixed-pivot quickselect O(n²), comparator overflow.
  • Cost: heap O(n log k)/O(k); quickselect O(n) avg in place; sort O(n log n).
heap = []                                  # max-heap via negated keys
for item in items:
    key = score(item)
    if len(heap) < k: heappush(heap, (-key, item))
    elif key < -heap[0][0]: heapreplace(heap, (-key, item))
return [item for _, item in heap]

You keep the k closest points seen so far. Which heap do you use, and what is at its root?

  1. A max-heap by distance; the root is the farthest point kept
  2. A min-heap; the root is the closest point
  3. A max-heap; the root is the closest point
  4. A min-heap of size n
A new point only has to beat the farthest kept point. If it is closer, replace the root. Each step costs O(log k).

Why compare x*x + y*y instead of sqrt(x*x + y*y)?

  1. sqrt keeps the order, and integers avoid float cost and rounding (the max, 2·10^8, fits in int)
  2. sqrt changes the order
  3. LeetCode requires it
  4. It prevents overflow
Squared distance is monotone in distance, so the k smallest are the same points.

Quickselect always takes the last element as pivot. What is the worst case?

  1. O(n^2) on sorted or adversarial input; pick the pivot at random
  2. O(n log n)
  3. O(n) always
  4. O(k log n)
A random pivot makes the expected time O(n).
