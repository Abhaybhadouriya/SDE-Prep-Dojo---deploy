The story: reading a long scroll for a secret word

Explain like I'm 5

You are looking for the word ABAC in a long scroll of letters. You read A, B, A... then the next letter is B, not C. Bad luck.

A tired reader rolls the scroll back and starts again one letter later. A clever reader thinks: "the last letter I read was an A, and ABAC starts with an A. So I already have the first letter of a new try. I do not need to roll back at all." The clever reader never reads a letter of the scroll twice. That clever reader is KMP.

Most interview string problems pass with a naive O(n · m) search or the library call, and you should say so. String matching becomes its own topic when the interviewer asks the follow-up: "can you do it in linear time?", "what if the text is a stream?", "what if two hashes collide?". At Google, Meta, Bloomberg and Uber these follow-ups show up on problems like Shortest palindrome (LC 214), Repeated string match (LC 686) and Longest duplicate substring (LC 1044) (the Premium company lists tag all three).

From your world

You have used these algorithms without calling them by name. The kernel's lib/textsearch layer ships ts_kmp, ts_bm (Boyer-Moore) and ts_fsm, and iptables -m string --algo kmp|bm --string "..." runs them over packet payloads that arrive in pieces. glibc's strstr uses the Two-Way algorithm, another linear-time matcher. rsync's rolling checksum is Rabin-Karp: a cheap weak hash slides over the file and a strong hash confirms each hit. The interview version is the same idea on one string in memory.
