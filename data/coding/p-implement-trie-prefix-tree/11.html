Interview follow-ups

Add delete(word).

Walk to the word's node and clear isEnd. To also free memory, walk back up (recursion or a stack of the path) and remove a node when it has no children and is not an end. Add a per-node child count to make "has no children" O(1).

How to answer

Say "lazy delete = clear the flag" first, then offer pruning as the memory-saving version.

Likely follow-ups
  • What if the word was inserted twice? (Keep an end count instead of a flag.)
Return how many words start with a prefix.

Keep pass on every node: increment it on each node an insert walks through. The answer is pass of the prefix node, O(L). This is LeetCode 1804.

How to answer

Point out that you trade 4 bytes per node for O(L) instead of a DFS over the subtree.

Likely follow-ups
  • Support erase with counts? (Decrement pass along the path and the end count at the end.)
Memory is tight: 26 pointers per node is too much. Options?

Three options. (1) A hash map or a sorted small array of (letter, child) per node: only real edges cost memory. (2) A compressed (radix / Patricia) trie: chains of single-child nodes collapse into one edge labelled with a string. (3) Store nodes in one pool array and use 32-bit indexes instead of 64-bit pointers. A DAWG or a succinct trie goes further for static sets.

How to answer

Quantify: 26 × 8 bytes = 208 bytes per node versus a few bytes per real edge.

Likely follow-ups
  • Which one keeps O(L) lookups? (All of them; the radix trie compares edge labels instead of single letters.)
Turn it into autocomplete: top 3 suggestions for a prefix.

Walk to the prefix node, then DFS its subtree in letter order and stop after 3 words (lexicographic suggestions). For popularity ranking, store the top-k (word, count) list at every node and update the lists along the path on each insert; queries become O(L + k).

How to answer

Ask whether reads or writes dominate. Autocomplete is read-heavy, so precomputing top-k per node is the usual choice.

Likely follow-ups
  • Memory of top-k per node? (k entries × number of nodes; cap k and store word ids, not strings.)
Many threads search while a few insert. How do you make it safe?

Simplest: a reader-writer lock around the whole trie. Better for read-heavy use: inserts only ever add nodes and set flags, so publish a fully built child node with a single atomic pointer store (release) and let readers load child pointers with acquire; readers never block. Deletes need deferred freeing (RCU-style grace periods or epochs) so a reader is never left holding a freed node.

How to answer

Start with the lock, then explain why add-only structures allow lock-free reads, and name the problem with frees.

Likely follow-ups
  • Two inserts create the same child at once? (Compare-and-swap the slot; the loser frees its node and follows the winner's.)
The alphabet becomes all of Unicode. What changes?

A 26-slot array no longer fits; use a hash map per node keyed by code point (or by byte, walking the UTF-8 bytes with a 256-way or map node). Complexity stays O(L) expected.

How to answer

Say which unit you walk (code points or bytes) and why bytes keep the node small.

Likely follow-ups
  • Case-insensitive search? (Normalise when inserting and when querying.)
