Approaches: brute → better → optimal

Hint 1

If you keep only k numbers while scanning, which k should they be, and which one do you drop?

Hint 2

After one quicksort partition you know the pivot's final index. Compare it with n - k.

1. Brute force - sort

Idea: sort ascending, return scores[n - k].

O(n log n)time
O(1) to O(n)space (sort-dependent)

What is wasted: we order every element, but only one position matters.

2. Better - min-heap of size k

Idea: push each value; when the heap holds k + 1 values, pop the smallest. After the scan the heap holds the k largest, and its top is the k-th largest.

for x in scores:
    heapq.heappush(keep, x)
    if len(keep) > k: heapq.heappop(keep)
return keep[0]
O(n log k)time
O(k)space

Why interviewers like it: it works on a stream and never needs the whole array in memory. What is still wasted: the log k factor for a one-off query on an array we already hold.

3. Optimal - quickselect, random pivot, 3-way partition

pivot = a[random.randint(lo, hi)]
# partition a[lo..hi] into  < pivot | == pivot | > pivot
if target < lt:   hi = lt - 1
elif target > gt: lo = gt + 1
else:             return pivot
  1. Turn "k-th largest" into an index. In ascending order it sits at target = n - k.
  2. One partition fixes a block. After the 3-way split, every copy of the pivot is at its final sorted positions [lt, gt].
  3. Keep only one side. If target is left of the block, recurse left; if right, recurse right; if inside, the pivot is the answer.
  4. Random pivot and the equal block keep it linear. No fixed input is bad for a random pivot, and the "== pivot" block makes an array of equal values finish in one pass.
O(n)average time
O(n^2)worst case (very unlikely)
O(1)extra space (iterative)

Why it works: a random pivot lands in the middle half of the range with probability 1/2, which shrinks the range to at most 3/4 of its size. So the expected work is n + (3/4)n + (3/4)^2 n + ... = O(n). With a plain 2-way partition, an array of many equal values makes every pivot split badly (one side keeps almost everything), and quickselect degrades to O(n^2); the 3-way partition puts all equal values in the final block at once.

Proof (optional)

Call a round "good" if the pivot's rank is in the middle half of the current range; then the next range has at most 3/4 of the elements. Each round is good with probability at least 1/2, so the expected number of rounds between two good rounds is at most 2. Rounds between the j-th and (j+1)-th good round each cost at most (3/4)^j n, giving expected total at most 2n · (1 + 3/4 + (3/4)^2 + ...) = 8n. A deterministic O(n) worst case exists (median of medians), but nobody expects it coded in an interview.

Bonus - counting by value (uses the constraints)

Idea: values are in [-10^4, 10^4], so count them in an array of 20,001 buckets and walk from the top until k elements are passed. O(n + R) time, O(R) space with R = 20,001. Great to mention when the range is small; useless if values are up to 10^9.
