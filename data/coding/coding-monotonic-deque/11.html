Interview questions

Sliding window maximum in O(n). Why is it O(n) when there is a while loop inside the for loop?

Keep a deque of indexes with strictly decreasing values. For each i: pop the back while it is <= nums[i], push i, pop the front if it is <= i - k, and emit nums[front] once i >= k - 1. The inner while looks expensive, but it only pops, and every index is pushed once, so there are at most n pops in total over the whole run. That is amortised analysis: total work O(n), O(1) per element on average.

How to answer

Start with brute force O(nk), then the heap O(n log n), then the dominance argument ("an older smaller value can never be the max again") which gives the deque. Then the amortised count.

Likely follow-ups
  • Window minimum? (Mirror: increasing deque, pop back while >= nums[i].)
  • Data arrives as a stream? (Same code; memory O(k).)
  • Is there an O(n) solution without a deque? (Yes: split into blocks of k, prefix max and suffix max per block; max of window = max(suffix[i], prefix[i+k-1]).)
Longest subarray where the absolute difference between any two elements is at most limit.

"Any two differ by at most limit" is "max - min <= limit", and validity shrinks with the window, so use a variable sliding window. The state needs the window max and min under deletions from the left: keep a decreasing deque (max) and an increasing deque (min). Expand hi, push into both; while max - min > limit, lo++ and pop any front index < lo. O(n) time.

How to answer

Offer the TreeMap / multiset version first (O(n log n), very short), then upgrade to two deques. Explain why the window is monotone (sub-window of a valid window is valid).

Likely follow-ups
  • Count all such subarrays instead? (Add hi - lo + 1 per step: LeetCode 2762.)
  • Why can lo only move right? (A window that is invalid stays invalid if you add elements, so the best start for a larger hi is never to the left.)
Shortest subarray with sum at least K when the array can contain negatives.

Sliding window fails because removing a negative from the left increases the sum, so "shrink while valid" is no longer safe. Use prefix sums P with P[0] = 0 and a deque of start indexes with increasing P. For each j: while P[j] - P[front] >= K, record j - front and pop the front (later ends with this start are only longer). Then while P[back] >= P[j], pop the back (j is a later and lower start, strictly better). Push j. O(n).

How to answer

Prove the two pruning rules out loud; they are the whole solution. Mention 64-bit sums.

Likely follow-ups
  • Can you do it with a heap or a TreeMap? (Yes: for each j, find the largest P[i] <= P[j] - K among earlier starts, O(n log n).)
  • All values positive? (Plain sliding window, LeetCode 209.)
Jump Game VI: maximise the score of cells you land on with jumps of 1..k. Brute DP is O(nk). Make it faster.

dp[i] = nums[i] + max(dp[i-k .. i-1]). The max over the last k dp values is a sliding window max over dp, so keep a decreasing deque of indexes by dp value: drop the front if it is older than i - k, compute dp[i] from the front, pop back while dp[back] <= dp[i], push i. O(n) time, O(n) for dp (O(k) if you only keep the deque and the dp values it references).

How to answer

Write the O(nk) DP first, name the bottleneck ("max of a sliding window of dp values"), then drop in the deque. A max-heap with lazy deletion (O(n log n)) is an acceptable middle step.

Likely follow-ups
  • Constrained Subsequence Sum? (Same, with dp[i] = nums[i] + max(0, best).)
  • Why read the front before pushing i? (dp[i] depends only on earlier positions.)
Design a queue that supports push, pop and getMax in O(1) amortised.

Keep the real FIFO queue plus a monotonic deque of values (decreasing, duplicates kept by popping only strictly smaller values). push(x): append x to the queue; pop back of the deque while back < x; append x. pop(): remove the queue front; if it equals the deque front, pop the deque front too. getMax(): deque front. Another classic answer: a queue made of two stacks, each stack storing (value, max so far), and max = max of the two stack tops.

How to answer

Point out that a "max queue" is the sliding window maximum with the window boundaries controlled by the caller.

Likely follow-ups
  • Why keep duplicates in the deque here? (Without indexes, a popped value must match one copy; popping only strictly smaller values keeps equal copies.)
Max Value of Equation: points sorted by x, maximise yi + yj + |xi - xj| with |xi - xj| <= k and i < j.

Since x is sorted and i < j, |xi - xj| = xj - xi, so the value is (yj + xj) + (yi - xi). For each j we need the max of (yi - xi) over earlier points with xj - xi <= k: a sliding window max where the window is defined by x distance, not count. Deque of indexes with decreasing yi - xi; pop the front while xj - x[front] > k; evaluate; then push j popping dominated backs. O(n).

How to answer

The algebra step that splits the expression into a "j part" and an "i part" is the whole trick. Say it first.

Likely follow-ups
  • Heap version? (Max-heap of (yi - xi, xi), pop tops that are too far: O(n log n).)
When would you choose a heap over a monotonic deque for a window problem?

When the question is not "max or min of a contiguous window that slides". The deque needs two things: items leave in arrival order (FIFO expiry), and you only need the extreme value. For the median or k-th largest, or when items leave in arbitrary order (cancelled orders, timers removed by id), use a heap with lazy deletion or an ordered multiset.

How to answer

State the two preconditions (FIFO expiry, extreme value only). That shows you understand why the trick works.

Likely follow-ups
  • Sliding window median? (Two heaps plus a map of pending deletions, O(n log k).)
