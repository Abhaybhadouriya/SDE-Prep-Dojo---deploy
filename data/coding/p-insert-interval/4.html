Approaches: brute -> better -> optimal

Hint 1

The list is sorted and disjoint. Which intervals cannot possibly touch the new one?

Hint 2

The ones that end before it starts, and the ones that start after it ends. Everything in between merges into one block.

1. Brute force - append, sort, merge

Idea: add newInterval to the list, sort by start, and run the Merge Intervals sweep. Correct, and a fine first sentence, but it throws away the fact that the input is sorted.

O(n log n)time
O(n)space

What is wasted: the sort. Only one interval is out of place, so a single pass can put it where it belongs. -> rung 2. (The tested files keep this version as brute and compare against it on 500 random inputs.)

2. Optimal - one pass in three phases

while i < n and iv[i][1] < lo: out.append(iv[i]); i += 1
while i < n and iv[i][0] <= hi:
    lo, hi = min(lo, iv[i][0]), max(hi, iv[i][1]); i += 1
out.append([lo, hi]); out.extend(iv[i:])
  1. Left zone: end before the new start. end < lo means no shared point; copy as is. Strict <, because end == lo touches and must merge.
  2. Middle zone: start not after the block's end. While start <= hi, absorb: lo = min(lo, start) (only the first absorbed one can lower it), hi = max(hi, end).
  3. Emit the block once, then copy the right zone. The merged block always goes in, even when nothing overlapped (then it is just newInterval, placed in its sorted spot).
O(n)time, each interval read once
O(n)output (O(1) extra)

Why it works: sorted and disjoint means the ends increase too. So "ends before lo" is a prefix of the list and "starts after hi" is a suffix; what is between them overlaps the new block, directly or through a neighbour that it absorbed. The output is sorted because we write prefix, block, suffix in order.

Proof (optional)

Disjoint under the "sharing a point overlaps" rule means starti+1 > endi, so both starts and ends are strictly increasing. Phase 1 stops at the first interval with end ≥ lo; all later ones also have end ≥ lo. In phase 2, if hi grew to some endi greater than the original end, the next start is > endi = hi, so the loop stops there: growing hi never pulls in an interval that the original new interval did not touch. Every absorbed interval has start ≤ hi and end ≥ lo, so it shares a point with the block; every interval after it has start > hi and shares none. The result covers the same points, is sorted, and has no overlap.
