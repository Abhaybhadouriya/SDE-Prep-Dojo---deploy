  • Cue: "any local max", O(log n), neighbours differ -> binary search on the slope.
  • Insight: uphill at mid means a peak to the right; the edges are minus infinity.
  • State: lo, hi; invariant: a peak is in [lo, hi].
  • Trap: lo < hi with hi = mid (not mid - 1); compare mid with mid + 1.
  • Cost: O(log n) time, O(1) space; linear scan O(n).
lo, hi = 0, n - 1
while lo < hi:                 # "find a boundary" binary search
    mid = (lo + hi) // 2
    if good_side_is_right(mid): lo = mid + 1
    else: hi = mid             # mid may be the answer: keep it
return lo

nums[mid] < nums[mid + 1]. Where is a peak guaranteed?

  1. left of mid
  2. right of mid (mid + 1 .. hi)
  3. at mid
  4. nowhere
Walking uphill to the right must end at a peak, because nums[n] counts as minus infinity.

With lo < hi, why set hi = mid and not mid - 1 when nums[mid] > nums[mid + 1]?

  1. for speed
  2. mid itself may be the peak
  3. to avoid overflow
  4. it does not matter
Dropping mid could throw away the only peak in range.

Is the array sorted, and why does binary search still work?

  1. yes, sorted
  2. no; it works because the comparison with a neighbour says which side surely holds a peak
  3. no, and it does not work in general
  4. only when there is one peak
Binary search needs a rule that discards half, not sorted input.
