Approaches: brute → better → optimal

Hint 1

Stand at any index and look right. If the next reading is higher, is there certainly a peak somewhere to the right? Why?

Hint 2

Walking uphill must stop before the end of the array (or at it). Where it stops, the reading is higher than both neighbours. Now pick the standing point in the middle.

1. Brute force - check every index

Idea: for each i, test nums[i] > nums[i-1] (or i = 0) and nums[i] > nums[i+1] (or i = n-1). Return the first that passes.

O(n)time
O(1)space

What is wasted: we look at both neighbours of every index, and we ignore the fact that a single comparison already tells us a direction. -> rung 2.

2. Better - first drop wins (still linear)

Idea: scan left to right and return the first i with nums[i] > nums[i+1]; if the array never drops, return n - 1. It works because before the first drop the array is strictly rising, so that i beats its left neighbour too.

O(n)time
O(1)space

What is wasted: this is the "walk uphill" idea, one step at a time. The fix is to jump: start the walk from the middle and throw away the half behind you. -> rung 3.

3. Optimal - binary search on the slope

lo, hi = 0, len(nums) - 1
while lo < hi:
    mid = (lo + hi) // 2
    if nums[mid] < nums[mid + 1]: lo = mid + 1   # uphill: peak to the right
    else: hi = mid                              # downhill: mid or a peak to its left
return lo
  1. The range always holds a peak. At the start [0, n-1] does, because the global maximum is a peak.
  2. Uphill at mid means a peak in (mid, hi]. nums[mid] < nums[mid+1]: walk right from mid+1 while the next reading is higher. The walk stops inside the range, because the reading after hi is lower than nums[hi] (it is either minus infinity or was ruled out by an earlier "downhill" step). Where it stops is a peak.
  3. Downhill at mid means a peak in [lo, mid]. nums[mid] > nums[mid+1]: walk left from mid the same way. mid itself stays in the range because it may be the peak.
  4. Stop when one index is left. lo == hi, and the range still holds a peak, so that index is it.
O(log n)time
O(1)space

Why it works: binary search does not need a sorted array; it needs an invariant that each comparison preserves while halving the range. Here the invariant is "a peak lies in [lo, hi], and the reading just outside each end of the range is lower than the end itself". Both updates keep it: lo = mid + 1 is chosen exactly when nums[mid] (the new left outsider) is lower, and hi = mid exactly when nums[mid+1] (the new right outsider) is lower.

Proof (optional)

Claim: if nums[lo-1] < nums[lo] and nums[hi] > nums[hi+1] (with the minus-infinity convention), then [lo, hi] contains a peak. Take the maximum m of nums[lo..hi]. Inside the range its neighbours are not larger (and differ, so they are smaller). If m = lo, its left neighbour is nums[lo-1] < nums[lo]; if m = hi, its right neighbour is nums[hi+1] < nums[hi]. So m is a peak. The two updates preserve the two outsider conditions, the range shrinks every step because mid < hi, and when lo == hi the claim says that single index is a peak.

Stuck? Why compare with mid + 1 and not mid - 1

With mid = lo + (hi - lo) / 2 and lo < hi, mid is always strictly less than hi, so mid + 1 is in range and you never read outside the array. Comparing with mid - 1 needs the upper-middle mid = lo + (hi - lo + 1) / 2 and the mirror updates.
