Add an arbitrary integer k instead of 1.

Use k itself as the carry: for i from the end, s = digits[i] + k, write s % 10, set k = s / 10. When the digits run out and k is still positive, prepend its digits. That is LC 989.

How to answer

Show that "plus one" is the special case where the carry never exceeds 1.

Likely follow-ups
  • Can k overflow? (k up to 104 plus a digit fits easily; say so.)
The digits are in a singly linked list, most significant first. Add one.

One pass: remember the last node whose value is not 9. Add 1 to it and set every node after it to 0. If there is no such node, add a new head 1 (use a dummy head with value 0 to unify the cases). O(n) time, O(1) space, no reversal needed.

How to answer

Map "first non-9 from the right" to "last non-9 from the left".

Likely follow-ups
  • Recursive version? (Return the carry from the tail up; O(n) stack.)
Do it in place without ever allocating, if the caller gives you one spare slot at the front.

Run the same loop on positions 1..n. In the all-nines case write 1 into slot 0 and report the start index 0; otherwise report start index 1. This is how fixed-buffer big-number code avoids reallocations.

How to answer

Return (buffer, offset) instead of a new array.

Likely follow-ups
  • What if digits are little-endian? (Then the carry walks forward and the new digit goes at the end, which is an O(1) append.)
What is the average number of digits you touch?

For random digits, a trailing 9 happens with probability 1/10, two with 1/100, and so on, so the expected work is 1 + 1/10 + 1/100 + ... ≈ 1.11 digits: O(1) on average, O(n) only for long runs of 9s.

How to answer

Geometric series over the length of the trailing 9 run.

  • Same for a binary counter increment? (Amortised O(1): the classic amortisation example.)
