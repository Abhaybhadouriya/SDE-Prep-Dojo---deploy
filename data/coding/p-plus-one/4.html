Approaches: brute -> better -> optimal

Hint 1

When does adding 1 change more than the last digit?

Hint 2

If every digit became 0 in your loop, what was the input, and what is the answer?

1. Brute force - convert to an integer and back

Idea: build the integer value, add one, split it back into digits.

O(n)time (with big ints, more)
O(n)space

What is wasted: it is wrong, not slow. A 100-digit number overflows long after 19 digits. Python and Java's BigInteger make it work, but the interviewer is asking for the digit arithmetic. -> rung 2.

2. Better - general addition with a carry variable

Idea: treat it as adding the number 1: carry = 1, then for i from the end compute sum = digits[i] + carry, write sum % 10, set carry = sum / 10. If a carry is left after index 0, prepend 1.

O(n)time, always
O(1)extra (in place)

Good, and it generalises to "add k" (LC 989) and "add two numbers". It just keeps looping after the carry is 0. -> rung 3 stops at once.

3. Optimal - stop at the first digit below 9

for i in range(len(digits) - 1, -1, -1):
    if digits[i] < 9:
        digits[i] += 1; return digits   # carry absorbed: done
    digits[i] = 0                       # 9 + 1 = 10: write 0, carry on
return [1] + digits                     # all were 9s
  1. The carry is always exactly 1 while the loop runs. So you do not need a carry variable: being inside the loop means "carry = 1".
  2. A digit below 9 cannot overflow. It becomes digit+1 and the carry is 0, so return right away.
  3. A 9 becomes 0 and the carry moves one place left.
  4. Falling out of the loop means every digit was 9. All are now 0; the answer is 1 followed by those n zeros.
O(n)worst case, O(1) average
O(1)extra (O(n) only for all 9s)

Why it works: adding 1 changes exactly the trailing run of 9s (each to 0) and the digit just before it (+1). Digits further left see no carry, so they are already correct. Only for all-nines is there no "digit before", and then the result is 10n, which is 1 and n zeros.
