Representing a graph in code

Before any algorithm, you need the graph in memory. There are four common shapes, and picking the right one is part of the answer:

ShapeWhat it isMemoryUse when
Adjacency listadj[u] = list of neighbours of uO(V + E)Default for almost every interview problem (sparse graphs)
Adjacency matrixm[u][v] = 1 (or the weight) if there is an edgeO(V2)Small, dense graphs; you need "is there an edge u-v?" in O(1) (Number of Provinces gives you one)
Edge listlist of (u, v[, w]) pairsO(E)The usual input format; Kruskal and union-find consume it directly
Implicit graphneighbours are computed, never stored: grid cells, word mutations, lock statesO(1) extraGrids and "state space" puzzles; generate neighbours on the fly

Building the list from an edge list is two lines in any language, and you should be able to write it without thinking:

adj = [[] for _ in range(n)]
for u, v in edges:
    adj[u].append(v)
    adj[v].append(u)      # drop this line for a directed graph

From your world

An adjacency list is the kernel's struct list_head per vertex: a node owns the head of a list of its links. An adjacency matrix is a routing table indexed by (source, destination) with one slot per pair: fast lookup, wasteful when most pairs have no route.

Grids are graphs

A grid of R rows and C columns is a graph whose vertices are the cells (r, c) and whose edges join each cell to its 4 neighbours (up, down, left, right; sometimes 8 with diagonals). You never build the adjacency list: you loop over a small dirs array and check bounds. This "implicit graph" trick covers a third of all graph questions you will meet.
