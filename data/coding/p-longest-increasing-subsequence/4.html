Approaches: brute → better → optimal

Hint 1

Suppose you know the LIS that ends exactly at each index j < i. How do you get the one ending at i?

Hint 2

Two subsequences of the same length: which one is more useful for the future, the one with the smaller last value or the larger?

1. Brute force - every subsequence

Idea: recursively decide for each element "take it (if bigger than the last taken) or skip it", and keep the longest valid result.

O(2^n)time
O(n)stack

What is wasted: the answer for "best chain from index i given the last taken value" is recomputed many times; only (i, last index) matters, which leads to a DP.

2. Better - O(n²) DP "ends at i"

State: dp[i] = length of the longest strictly increasing subsequence that ends at index i.

Transition: dp[i] = 1 + max(dp[j]) over all j < i with nums[j] < nums[i] (or 1 if there is none).

Base case: dp[i] = 1 for every i (the element alone).

Answer: max(dp), not dp[n-1]: the LIS may end anywhere.

dp = [1] * n
for i in range(n):
    for j in range(i):
        if nums[j] < nums[i]: dp[i] = max(dp[i], dp[j] + 1)
return max(dp)
O(n²)time
O(n)space

What is wasted: for each i we scan all j. But among the subsequences of the same length, only the one with the smallest end value can matter: any number that extends a larger end also extends the smaller one.

3. Optimal - tails + binary search (patience sorting)

tails = []                                # core: 5 lines
for x in nums:
    k = bisect_left(tails, x)             # first tail >= x
    if k == len(tails): tails.append(x)
    else: tails[k] = x
return len(tails)
  1. tails[k] = the smallest end of any increasing subsequence of length k + 1 seen so far. One number per length.
  2. tails is strictly increasing. A length-(k+2) subsequence contains a length-(k+1) prefix with a smaller end, so tails[k] < tails[k+1].
  3. x extends the longest chain whose end is < x. Because tails is sorted, that is just before the first tail ≥ x, found by binary search.
  4. Append or overwrite. If no tail is ≥ x, x makes a new longest length. Otherwise x is a smaller end for length k + 1: overwrite tails[k].
  5. The length is the answer, not the contents. tails may mix values from different subsequences, but len(tails) is always the LIS length.
O(n log n)time
O(n)space

Why it works: the invariant "tails[k] is the minimum possible end of a length-(k+1) increasing subsequence of the prefix read so far" is kept by each step: the new x can only improve the length it extends to (k + 1, where tails[k-1] < x ≤ tails[k]), and it cannot improve any other length. So when the scan ends, a subsequence of length len(tails) exists and none longer does.

Proof (optional) - why only one slot changes

Let k = lower_bound(tails, x). For lengths ≤ k: their tails are already < x, so x is not a smaller end. For length k + 1: tails[k-1] < x, so x extends a length-k chain, and x ≤ tails[k], so x is at least as good an end. For lengths > k + 1: x would need to extend a length-(k+1) or longer chain, whose ends are all ≥ x, which strict increase forbids. Hence exactly tails[k] may change, and the invariant holds after the step.

Stuck? lower_bound vs upper_bound

Strictly increasing: replace the first tail ≥ x (lower_bound / bisect_left), so an equal x does not extend. Non-decreasing: replace the first tail > x (upper_bound / bisect_right), so an equal x extends. Swapping them is the most common bug: [4, 4, 4] would give 3.
