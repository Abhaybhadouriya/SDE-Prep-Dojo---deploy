Interview follow-ups

Can you tighten the search range?

Yes: lo = ceil(sum / h), because in h hours you print at most k · h pages, and hi = max(piles). Tighter bounds save only a few iterations: the cost is logarithmic anyway.

How to answer

Give the lower bound with its one-line reason, then say the gain is small because the search is O(log range).

Likely follow-ups
  • Compute sum in 64 bits: up to 10^13.
What if the printer can move on to the next job inside the same hour?

Then only the total matters: hours = ceil(sum / k), and the answer is directly ceil(sum / h). No search needed. The "idle for the rest of the hour" rule is what makes each job cost a separate ceil and forces the search.

How to answer

Show you know which rule creates the difficulty.

Likely follow-ups
  • What if the order of jobs is fixed and loads must be contiguous? That is LC 1011.
Speeds can be real numbers. How do you search?

Binary search on doubles with a fixed number of iterations (about 60-100) or until hi - lo < eps. With real k, hours(k) is still monotone. This is the shape of LC 774 (minimise the max distance to a gas station).

How to answer

Prefer a fixed iteration count over an epsilon loop: it always ends and its precision is easy to state.

Likely follow-ups
  • Can you avoid floats? Sometimes, by scaling to integers.
There are m printers working in parallel, all at the same speed.

The check changes: can the jobs be scheduled on m machines within h hours each? Each job still costs ceil(p / k) hour-slots, and you have m · h slots, but a job cannot be split across machines unless allowed. If a job may continue on another machine in a later hour, the check is Σ ceil(p / k) ≤ m · h plus ceil(p / k) ≤ h for every job (one job never runs on two machines in the same hour). If not, it becomes bin packing, which is NP-hard in general: say so and ask which rule applies.

How to answer

Clarify the rules first; the search on k stays, only the check changes.

Likely follow-ups
  • Workers with different speeds: LC 2594 style.
Many queries with different h on the same piles.

Each query is O(n log max). With q queries that is O(q · n log max). The answer is monotone in h too (more hours never needs a faster speed), so if the queries can be sorted by h, each answer bounds the next search: hi for a larger h is the previous answer. Caching hours(k) for the k values you have already checked also avoids repeat O(n) passes.

How to answer

Separate the search (log max) from the check (n), and speed up the part that repeats.

Likely follow-ups
  • Return the speed and the hours used.
