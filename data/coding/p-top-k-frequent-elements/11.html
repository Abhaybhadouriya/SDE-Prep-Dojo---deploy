The numbers arrive as a stream and you must answer "top k so far" at any time.

Keep the count map plus a structure ordered by count. A size-k heap alone is not enough because counts of items already inside it change. Options: a balanced tree / sorted set of (count, value) where you remove and re-insert on every update (O(log u) per event), or the LFU-style "count -> doubly linked list of values" buckets that give O(1) increments.

How to answer

Say why the static heap breaks (stale keys), then pick the sorted set for simplicity, or the O(1) bucket list if asked for speed.

Likely follow-ups
  • Memory is limited and approximate answers are fine: Count-Min Sketch + a size-k heap, or Misra-Gries / Space-Saving counters.
Ties are possible now. Return them ordered by count, breaking ties by the smaller value.

Use a total order on (count desc, value asc). In the min-heap the "worst" item is the one with the lower count, and among equal counts the larger value; pop that when the size exceeds k, then sort the k survivors. With buckets, sort each bucket by value before reading it.

How to answer

Write the comparator first and test it on two equal-count items.

Likely follow-ups
  • This is exactly LC 692 with strings.
Which is better in practice, the heap or the buckets?

Buckets are O(n) worst case but allocate n + 1 lists even when u is tiny; the heap is O(n + u log k) and uses O(k) extra beyond the counts. For small k the heap is as fast and lighter. For k close to u, buckets or quickselect win.

How to answer

Compare in terms of n, u and k, not "Big-O only".

Likely follow-ups
  • How do you make quickselect's worst case safe? (Random pivot, or median of medians.)
The log is 1 TB spread over 100 machines. Find the global top k.

Each machine counts its own shard, but local top-k lists are not enough (a value can be 11th everywhere and 1st globally). Shuffle by hash(value) mod R so all counts of a value meet on one reducer (MapReduce), each reducer computes its local top k, then merge R lists of k with a heap.

How to answer

Point out the trap with merging local top-k lists first, then give the partition-by-key fix.

Likely follow-ups
  • Skewed keys overload one reducer: combine counts on the mapper side first.
Can you do it with O(1) extra space besides the output?

Not with arbitrary values: you must remember counts. If you may modify the input, sort it (O(n log n), in place) and count runs, keeping a size-k heap of run lengths, which is O(k) extra. The value range [-104, 104] also allows a fixed 20001-entry count array, which is "O(1)" in n but not small.

How to answer

Separate "extra space in n" from "space in the value range"; mention the trade-off with time.

Likely follow-ups
  • What if the values are 64-bit ids? (Back to a hash map.)
