Approaches: brute → better → optimal

Hint 1

Before choosing anything, you need every value's count. What structure gives that in one pass?

Hint 2

Sorting all u (value, count) pairs works but costs u log u. Do you need the full order, or only the best k?

Hint 3

Counts are integers between 1 and n. What sort runs in linear time on small integer keys?

1. Brute force - count, then sort all distinct values by count

Idea: build count[value] with a hash map, put the u distinct values in a list, sort it by count descending, return the first k.

O(n + u log u)time
O(u)space

What is wasted: we fully order all u values but only need the top k. With u close to n this is O(n log n), which the follow-up rules out. -> rung 2.

2. Better - a min-heap that never holds more than k values

Idea: push each (count, value) into a min-heap; whenever the size goes above k, pop the smallest. The heap's root is always the weakest member of the current top k, so a new candidate only has to beat the root.

heap = []
for value, c in count.items():
    heapq.heappush(heap, (c, value))
    if len(heap) > k: heapq.heappop(heap)     # throw out the weakest
return [v for _, v in heap]
O(n + u log k)time
O(u + k)space

Why interviewers like it: it works on a stream of counts, it is short in every language, and when k is small it is effectively linear. What is still wasted: log k comparisons per value, although the keys are small integers. -> rung 3.

Stuck? Max-heap or min-heap?

A max-heap of all u items and k pops costs O(u + k log u) with heapify; it is fine too, but it stores all u items. The min-heap of size k is the standard answer because its memory is O(k) beyond the counts.

3. Optimal - bucket sort by count

bucket = [[] for _ in range(n + 1)]        # index = count
for value, c in count.items(): bucket[c].append(value)
for c in range(n, 0, -1):                  # highest count first
    for value in bucket[c]:
        top.append(value)
        if len(top) == k: return top
  1. A count is an integer in [1, n]. So an array of n + 1 lists can hold every value at the index of its count.
  2. Each distinct value is placed once. u appends, no comparisons.
  3. Reading from index n down visits counts in decreasing order. The first k values read are the k most frequent.
  4. Uniqueness makes the stop safe. If we stop in the middle of a bucket, every value left in it has the same count as the last one taken; the guarantee says that cannot happen at the k boundary, so any order inside a bucket is fine.
O(n)time
O(n)space

Why it works: sorting by count is a sort on integer keys in a range of size n + 1, and a counting/bucket sort does that in O(n + range) = O(n). We never compare two counts; the array index does the ordering.

Proof (optional)

Let the returned set be T. Suppose a value x outside T has a count cx greater than some y in T. The scan visits bucket cx before bucket cy (it goes from n down), and it only stops once |T| = k; y was taken at bucket cy < cx, so the scan passed bucket cx while |T| < k and took every value in it, including x. Contradiction. The time bound: counting is n steps, placing is u <= n, the scan touches n + 1 buckets and at most k values.

4. Alternative - quickselect on the distinct values

Idea: put the u distinct values in an array and run the Hoare/Lomuto partition step by count, as in Kth Largest Element; after it, the k values with the largest counts sit on one side of index u - k. Average O(n), worst case O(u2) unless the pivot is random. This is the approach the official editorial ends with.
