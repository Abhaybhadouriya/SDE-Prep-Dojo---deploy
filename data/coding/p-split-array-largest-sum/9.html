  • Cue: minimise the max piece/load/day + k contiguous groups -> binary search the cap.
  • Insight: feasible(cap) = greedy pieces ≤ k; it is monotone (F..F T..T), find the first T.
  • State: lo = max(nums), hi = sum(nums); greedy run sum and piece count.
  • Trap: lo must be ≥ max value; while lo < hi with hi = mid; parts starts at 1; 64-bit sums.
  • Cost: O(n log sum) time, O(1) space; DP O(k·n²); brute exponential.
lo, hi = smallest_possible, largest_possible
while lo < hi:
    mid = (lo + hi) // 2
    if feasible(mid): hi = mid     # minimise: keep mid
    else: lo = mid + 1
return lo

Why is the lower end of the search range max(nums) and not 0?

  1. Binary search needs a positive start
  2. Some piece must contain the largest value, so no cap below it is possible
  3. It makes the loop run exactly k times
Any piece containing the largest value has a sum at least that value, so the answer is at least max(nums).

The greedy check says cap 14 needs 2 pieces and k = 3. What does that mean?

  1. Cap 14 is not allowed, because we need exactly 3 pieces
  2. The answer is exactly 14
  3. Cap 14 is feasible; the answer is 14 or smaller
At most k pieces is enough: split any piece with 2+ values to reach exactly k without raising any sum.

Which loop is correct with hi = mid on success?

  1. while lo < hi, then return lo
  2. while lo <= hi, then return lo
  3. while lo < hi - 1, then return hi
With lo <= hi and hi = mid, the state lo == hi == mid repeats forever.
