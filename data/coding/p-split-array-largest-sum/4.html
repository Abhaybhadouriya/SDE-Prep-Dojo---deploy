Approaches: brute -> better -> optimal

Hint 1

If someone tells you a limit L, can you decide quickly whether the array can be cut into at most k pieces with every piece ≤ L?

Hint 2

Greedy: keep adding to the current piece until the next value would exceed L. Why can a smarter cut never use fewer pieces?

Hint 3

The answer is between max(nums) and sum(nums), and "feasible(L)" is monotone in L.

1. Brute force - try every set of cut positions

Idea: choose k - 1 cut points among the n - 1 gaps, compute the largest piece for each choice, keep the minimum. A recursion "where does the first piece end?" does the same thing.

O(C(n-1, k-1) · n)time (exponential)
O(k)space (recursion)

What is wasted: the same suffix "cut nums[j..] into p pieces" is solved again and again for every way of cutting the prefix. Memoising that state gives the DP.

2. Better - DP over (pieces, prefix length)

State: dp[p][i] = the best (smallest) largest-piece cost when the first i values are cut into p pieces.

Transition: the last piece is nums[j..i-1] for some j: dp[p][i] = min over j of max(dp[p-1][j], pre[i] - pre[j]), with prefix sums pre.

Base case: dp[0][0] = 0; everything else starts at infinity.

Answer: dp[k][n].

Space optimisation: row p only reads row p - 1, so two rows of length n + 1 are enough.

O(k · n²)time (5·10^7 at the limits)
O(n)space with two rows

What is wasted: the DP computes the exact best cost for every prefix and every piece count, but we only need one number. And the answer is a number in a known range with a cheap yes/no test: that is the setting for binary search.

3. Optimal - binary search on the cap + greedy check

lo, hi = max(nums), sum(nums)
while lo < hi:
    mid = (lo + hi) // 2
    if parts_needed(mid) <= k: hi = mid      # mid works: answer is mid or smaller
    else: lo = mid + 1                         # mid fails: answer is bigger
  1. The answer lies in [max(nums), sum(nums)]. Some piece holds the largest value, and one piece holding everything is always allowed (k = 1).
  2. For a fixed cap, greedy gives the fewest pieces. Fill the current piece until the next value would push it over the cap, then start a new piece.
  3. Feasibility is monotone. If cap L can be done with ≤ k pieces, so can any L' > L (the same cut still works). So feasible(L) reads F F ... F T T ... T.
  4. "At most k" is the same as "exactly k". With ≤ k pieces you can split a piece of 2+ values further until there are exactly k (k ≤ n); splitting never raises a piece sum.
  5. Find the first T with lower-bound binary search. hi = mid on success keeps mid as a candidate; lo = mid + 1 on failure.
  1. Range: lo = 9 (the largest value must fit in some part) and hi = 24 (everything in one part). The answer is in 9..24.
  2. mid = 16. Greedy fill: 4+9+3 = 16 fits, 6 would make 22, so a new part starts: [4,9,3] | [6,2]. 2 parts ≤ k: feasible, so hi = 16.
  3. mid = 12. 4+9 = 13 > 12, so 9 starts part 2; 9+3 = 12; 6 starts part 3. 3 parts > k: caps ≤ 12 all fail, lo = 13.
  4. mid = 14. [4,9] = 13, adding 3 gives 16 > 14, so [3,6,2] = 11 is part 2. 2 parts: feasible, hi = 14.
  5. mid = 13 (= lo). [4,9] = 13 fits exactly; [3,6,2] = 11. Still 2 parts: feasible, hi = 13.
  6. lo = hi = 13: the smallest feasible cap. Answer 13, split [4,9] | [3,6,2]. 4 checks of O(n) each instead of trying every split.
O(n · log(sum))time: about 30 checks of O(n)
O(1)extra space

Why it works: we never search over cuts at all. We search over the answer value, and for each candidate the greedy tells us the minimum number of pieces in one pass. Because that count only goes down as the cap goes up, the smallest cap with count ≤ k is the answer.

Proof (optional)

Greedy is optimal for a fixed cap L (each value ≤ L). Let the greedy pieces end at g1 < g2 < ... and any valid cut's pieces end at o1 < o2 < .... By induction gi ≥ oi: the greedy's i-th piece starts at or before the other cut's i-th piece (since g(i-1) ≥ o(i-1)) and extends as far as the cap allows, so it reaches at least as far. Hence the greedy uses no more pieces than any valid cut. Monotone: a cut valid for L is valid for every larger cap. Range: feasible(sum) is true and feasible(max - 1) is false, so the first true value exists in [max, sum] and is exactly the minimum possible largest piece.
