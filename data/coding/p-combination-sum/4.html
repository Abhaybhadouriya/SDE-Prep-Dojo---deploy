Approaches: brute -> better -> optimal

Hint 1

Think of it as a sequence of decisions: "which value do I add next?" What stops you from finding [2,3,3] and [3,2,3] separately?

Hint 2

Only allow the next value to come from the same index or later. Then every combination is produced in non-decreasing order, exactly once.

1. Brute force - all sequences, then deduplicate

Idea: recurse "add any candidate" until the sum reaches or passes the target; on an exact hit, sort the sequence and put it in a set.

O(nT/m)sequences (T = target, m = min value)
largeset of duplicates

What is wasted: each multiset of size k is generated up to k! times (every ordering), then thrown away by the set.

2. Better - take / skip binary choice

Idea: at index i, either take c[i] (stay at i, since it can be reused, and reduce the target) or skip it (move to i + 1, never use it again). Stop when the target is 0 (record) or i == n or the target goes negative. Each multiset corresponds to exactly one path, so no deduplication is needed. This is the form Striver's sheet teaches.

def go(i, left):
    if left == 0: out.append(pick[:]); return
    if i == len(c) or left < 0: return
    pick.append(c[i]); go(i, left - c[i]); pick.pop()   # take c[i] (again)
    go(i + 1, left)                                      # done with c[i]

What is wasted: without sorting it explores branches whose next value is already too big, and the skip chain creates a long path of "skip" nodes.

3. Optimal - for-loop over the next value, sorted, with a break

Idea: dfs(start, left) loops i from start to n - 1, appends c[i], recurses with dfs(i, left - c[i]), and pops. Sorting first lets the loop break at the first value larger than left: every later value is larger still. This is the same search as rung 2, written so that each tree node is a real partial combination.

  1. Start index = no reordering. A child may use indices ≥ its parent's choice, so the picked values are non-decreasing. Each multiset has exactly one non-decreasing ordering, so it is found exactly once.
  2. Recurse with i, not i + 1. That keeps c[i] available for reuse.
  3. Copy on record. pick is shared and mutated; store a copy, or every stored list ends up empty.
  4. Break, not continue. Because the array is sorted, once c[i] > left nothing later can fit.
  1. Start at the root: 8 is left to reach, start index 0 (value 2). Candidates are sorted: [2, 3, 5].
  2. Take 2 (index 0). 6 left. The child may again start at index 0, because 2 can be reused.
  3. Take 2 again: 4 left.
  4. Take 2 twice more: 2 left, then 0 left. Exact hit: record a copy of [2, 2, 2, 2]. Back at "2 left", the next value 3 is bigger than 2, so the loop breaks.
  5. Back at 4 left: undo the last 2, try 3 (index 1): 1 left. From index 1 the smallest value is 3 > 1: dead end. Value 5 > 4 breaks the loop at the parent too.
  6. Back at 6 left: try 3 -> 3 left, start index 1. Take 3 again -> 0: record [2, 3, 3]. The child never looks at 2 again: [2, 3, 2, ...] would be the same multiset in another order.
  7. Still at 6 left: try 5 -> 1 left, start index 2: 5 > 1, dead end. The whole "starts with 2" subtree is done.
  8. Root, next choice 3 -> 5 left, start index 1, so 2 is now off the table (every set with a 2 was already found). Taking 3 -> 2 left is a dead end; taking 5 -> 0: record [3, 5].
  9. Root, choice 5 -> 3 left, start index 2: 5 > 3, dead end. The loop ends. Answer: [[2,2,2,2], [2,3,3], [3,5]], 13 nodes visited.
O(nT/m + 1)loose upper bound on nodes; really output-sensitive
O(T/m)recursion depth and pick size

Why it works: there is a bijection between search-tree leaves with left == 0 and valid multisets. Any valid multiset, written in non-decreasing order, is a path the loop can take (each next value has index ≥ the previous one). Conversely, every path the loop takes is non-decreasing, so two different paths give two different multisets. Pruning only cuts subtrees whose remaining target is smaller than every allowed value, which contain no hits.

Complexity, honestly

The tree depth is at most T/m (here 40/2 = 20) and each node has at most n children, giving the usual quoted bound O(nT/m) nodes, each copying up to T/m values at a hit. In practice the break pruning makes the work proportional to the number of nodes that still have a reachable target, and the problem guarantees fewer than 150 answers. In the interview, say "exponential, bounded by n to the power T/min, and output-sensitive"; the editorial gives the same bound.
