Approaches: brute -> better -> optimal

Hint 1

Every character is allowed inside a string. So how can the decoder know where a string ends without looking at its characters?

Hint 2

Which part of what you write could be made of a small, known set of characters?

1. Naive - join with a delimiter

Idea: ",".join(strs) and s.split(",").

O(L)time (L = total length)
wrongfor data containing the delimiter

Why it is not enough: every one of the 256 characters may appear in the data, so every delimiter breaks some input (see the table above). -> rung 2.

2. Better - escaping (byte stuffing)

Idea: pick a separator such as " # " and double every # inside the data. A lone # (between spaces) can then only be a separator. One Most Votes solution uses this; add a trailing marker so empty strings and an empty list stay different.

O(L)time
up to 2Loutput size

What is not ideal: correct, but the decoder must look at every character, the output can double, and getting the escape rules exactly right on a whiteboard is error-prone. -> rung 3.

3. Optimal - length prefix

encode: "".join(f"{len(s)}#{s}" for s in strs)
decode: while i < len(s):
            j = s.index("#", i); k = int(s[i:j])
            out.append(s[j + 1 : j + 1 + k]); i = j + 1 + k
  1. The header has a known alphabet. It is only digits and then one #. So the first # after the start of a header always ends the header, whatever the strings contain.
  2. The payload is never inspected. The decoder copies exactly k characters, so a # or digits inside a string are just data.
  3. The reader always lands on a header. After a payload it jumps to j + 1 + k, which is exactly where the encoder wrote the next header. It is never "inside" a string when it searches for #.
  4. Empty strings are free. "" becomes 0#; an empty list becomes "". They are different.
O(L + n)time, encode and decode
L + O(n log L)output size (headers)

Why it works: by induction on the strings: if the decoder is at the start of header i, it reads the length the encoder wrote, takes the exact payload, and ends at the start of header i + 1. The search for # only ever scans digits. The format is prefix-free: no frame can be mistaken for the start of another. A fixed-width header (for example 4 bytes, big-endian, like gRPC) avoids the # entirely and is the usual production choice.
