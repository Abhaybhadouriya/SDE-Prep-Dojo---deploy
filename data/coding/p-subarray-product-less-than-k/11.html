Interview follow-ups

Why is this O(n) when there is a while loop inside the for loop?

left only increases and never passes right + 1, so the inner loop runs at most n times over the whole run. Total pointer moves are at most 2n; each move is O(1) work.

How to answer

Count pointer moves, not loop nesting.

Likely follow-ups
  • What if the division were expensive? Keep it: each element is divided out at most once.
Values can be 0. What changes?

Any subarray containing a 0 has product 0, which is < k whenever k > 0. Split the array at the zeros: count with the window inside each zero-free segment, then add the subarrays that contain at least one zero, which is all subarrays minus those of the zero-free segments: n(n+1)/2 - sum of len(len+1)/2.

How to answer

Point out that the division step breaks first (division by zero), then that validity is no longer "longer = worse".

Likely follow-ups
  • Handle k = 0 in this version (then nothing counts).
Values can be negative. Can you still count in O(n log n)?

The window no longer works: a negative factor can turn a huge product small. Track the sign and the log of the absolute value separately. A subarray with a negative product is always < k (for k >= 0); subarrays with an even number of negatives need sum of logs < log k, which is a "count pairs of prefix values below a bound" problem: sort the prefix log sums per parity class and use a Fenwick tree or merge sort. O(n log n).

How to answer

Name the broken property first (monotone product), then reduce products to sums with logs and use the prefix-sum counting toolbox.

Likely follow-ups
  • Precision: compare with an epsilon, or count with exact integers where you can.
Return the longest subarray with product < k instead of the count.

Same window; keep best = max(best, right - left + 1) instead of adding. With all values >= 1 you can also use the never-shrinking variant (move left at most once per step).

How to answer

Show that the loop body is shared and only the "use the window" line changes: count, max or min.

Likely follow-ups
  • The shortest window with product >= k (like LC 209 with products).
Products could overflow 64 bits (k and values much larger). What then?

Test before multiplying: if prod > (k - 1) / x then prod * x >= k, so shrink first without forming the overflowing product. Or compare in log space with an epsilon. In C, the same check avoids undefined behaviour on signed overflow.

How to answer

Mention that here prod < k <= 10^6 before every multiply, so it cannot happen with the given constraints; then give the division check.

Likely follow-ups
  • Use __builtin_mul_overflow in C/C++.
Count the subarrays with product exactly k.

Use "exactly = atMost - atMostSmaller": count with product < k + 1 (that is, <= k) minus count with product < k. Both are this same function. Ones make the count non-trivial, since [1, k, 1] has several subarrays with product k.

How to answer

Reuse the function you already wrote; do not write a new window.

Likely follow-ups
  • The same trick for sums: LC 930 Binary Subarrays With Sum.
