The method: operations first, structures second

  1. Write the API and the target cost of each call. get(key) O(1), put(key, value) O(1), evict the least recently used. Ask about capacity, duplicates, empty calls and whether timestamps arrive in order.
  2. Give each operation the structure that does it fast. Find by key: hash map. Keep an order and move items in O(1): doubly linked list. Pick uniformly at random: an array. Min or max at any time: a stack that stores the running min, or a heap. "Only the last 5 minutes": a ring buffer or a deque.
  3. Link them with handles. The map does not store the value; it stores the list node or the array index. The node stores its key, so an eviction from the list can also delete from the map.
  4. Walk every operation through every structure. For each method ask: which structures does it touch, and are all of them updated? Most bugs are one structure left stale.

Constraints tell you: "at most 2·105 calls" and "each call O(1)" or "O(log n)" is the whole spec. O(1) for find plus order means map + linked list. O(log n) allowed usually means a heap or a balanced tree (TreeMap, std::map) is fine.
