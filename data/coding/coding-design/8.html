Stream and time designs

These read events with timestamps and answer questions about a recent window. Always ask first: do timestamps arrive in order? On LeetCode they usually do (Hit Counter: "calls are made in chronological order"; Time Based Key-Value Store: set timestamps are strictly increasing), and that is what makes the simple designs correct.

// 7a. Time-based key-value store (LC 981).
type stamped struct {
	t int
	v string
}

type TimeMap struct{ m map[string][]stamped }

func NewTimeMap() *TimeMap { return &TimeMap{m: map[string][]stamped{}} }

func (tm *TimeMap) Set(k, v string, t int) { tm.m[k] = append(tm.m[k], stamped{t, v}) }

func (tm *TimeMap) Get(k string, t int) string {
	a := tm.m[k]
	i := sort.Search(len(a), func(i int) bool { return a[i].t > t }) // first entry after t
	if i == 0 {
		return ""
	}
	return a[i-1].v
}

// 7b. Hit counter (LC 362): ring of 300 buckets.
type HitCounter struct{ stamp, cnt [300]int }

func (h *HitCounter) Hit(t int) {
	i := t % 300
	if h.stamp[i] != t {
		h.stamp[i], h.cnt[i] = t, 0
	}
	h.cnt[i]++
}

func (h *HitCounter) GetHits(t int) int {
	s := 0
	for i := 0; i < 300; i++ {
		if t-h.stamp[i] < 300 {
			s += h.cnt[i]
		}
	}
	return s
}
// 7a. Time-based key-value store (LC 981): timestamps arrive increasing per key.
class TimeMap {
    unordered_map<string, vector<pair<int, string>>> m;
public:
    void set(const string& k, const string& v, int t) { m[k].push_back({t, v}); }
    string get(const string& k, int t) {
        auto it = m.find(k);
        if (it == m.end()) return "";
        auto& v = it->second;                                      // last entry with time <= t
        auto p = upper_bound(v.begin(), v.end(), t, [](int x, const pair<int, string>& e) { return x < e.first; });
        return p == v.begin() ? "" : prev(p)->second;
    }
};

// 7b. Hit counter (LC 362): ring of 300 one-second buckets.
class HitCounter {
    int stamp[300] = {0}, cnt[300] = {0};
public:
    void hit(int t) {
        int i = t % 300;
        if (stamp[i] != t) { stamp[i] = t; cnt[i] = 0; }           // bucket is stale: reuse it
        cnt[i]++;
    }
    int getHits(int t) {
        int s = 0;
        for (int i = 0; i < 300; i++) if (t - stamp[i] < 300) s += cnt[i];
        return s;
    }
};
// 7a. Time-based key-value store (LC 981): floorEntry does the binary search.
static class TimeMap {
    final Map<String, TreeMap<Integer, String>> m = new HashMap<>();
    void set(String k, String v, int t) { m.computeIfAbsent(k, x -> new TreeMap<>()).put(t, v); }
    String get(String k, int t) {
        TreeMap<Integer, String> tm = m.get(k);
        if (tm == null) return "";
        Map.Entry<Integer, String> e = tm.floorEntry(t);
        return e == null ? "" : e.getValue();
    }
}

# 7a. Time-based key-value store (LC 981).
class TimeMap:
    def __init__(self):
        self.times, self.vals = defaultdict(list), defaultdict(list)

    def set(self, key, value, t):
        self.times[key].append(t)                   # increasing per key: stays sorted
        self.vals[key].append(value)

    def get(self, key, t):
        i = bisect.bisect_right(self.times.get(key, []), t)
        return self.vals[key][i - 1] if i else ""

# 7b. Hit counter (LC 362): ring of 300 buckets.
class HitCounter:
    def __init__(self):
        self.stamp, self.cnt = [0] * 300, [0] * 300

    def hit(self, t):
        i = t % 300
        if self.stamp[i] != t:
            self.stamp[i], self.cnt[i] = t, 0
        self.cnt[i] += 1

    def getHits(self, t):
        return sum(c for s, c in zip(self.stamp, self.cnt) if t - s < 300)

Rate limiter as a coding question

When "design a rate limiter" is asked in a coding round (not system design), code one of: fixed window (counter per user per minute; simple, but allows a 2x burst at the window edge), sliding log (deque of timestamps per user; exact, memory O(limit)), or token bucket (tokens refill at rate r up to capacity b; store only tokens and lastRefill per user, refill lazily on each call). Token bucket is the usual best answer: O(1) memory per user and it allows controlled bursts. The distributed version (shared counters in Redis, per-node quotas) is in the HLD track.

From your world

Linux traffic control already ships it: the tbf qdisc is a token bucket filter with a rate, a burst size and lazy refill based on elapsed time. The hit counter ring is the same idea as per-second counters in a stats ring that a driver exports.
