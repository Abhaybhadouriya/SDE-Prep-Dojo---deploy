Interview questions

Design an LRU cache with O(1) get and put.

Hash map from key to a node of a doubly linked list. The list is ordered by recency, head = newest. get: look up, move the node to the head, return. put: update and move, or insert at the head; if over capacity, remove tail.prev from the list and its key from the map. Sentinel head and tail remove every null check.

How to answer

State why each structure is needed (map: find; list: O(1) reorder and evict). Draw the picture, then code the list helpers (unlink, pushFront) first; get and put become four lines each.

Likely follow-ups
  • Make it thread safe; then make it scale (sharding, CLOCK).
  • Add a time-to-live per key (store expiry; check on get; a min-heap or timing wheel for background cleanup).
  • Why not a singly linked list? Unlinking needs the previous node.
Design an LFU cache. Why is a heap not good enough?

A heap ordered by (count, last use) works but every get and put is O(log n), and updating an element inside a heap needs an index map. The O(1) design keeps an LRU list per count, a map from key to node, and minFreq. A touch moves the node from list f to the front of list f+1; eviction takes the tail of list minFreq; a new key sets minFreq = 1.

How to answer

Offer the heap first as the "obvious O(log n)" design, then explain the bucket idea and the two rules that keep minFreq correct without a search.

Likely follow-ups
  • Counts grow forever, so old popular keys never leave: add aging (halve counts periodically), which is the idea behind TinyLFU.
Insert, delete and getRandom in O(1). What breaks with duplicates?

Array of values plus map from value to index. Delete copies the last value into the hole, updates its index, pops the end. getRandom picks a random index. With duplicates, the map holds a set of indexes per value; delete takes any index of x, moves the last element there, and updates both sets. Edge case: the removed element is the last one.

How to answer

Explain why neither structure alone works, then the swap-with-last trick. Run the "remove the last element" case out loud.

Likely follow-ups
  • Weighted random? Prefix sums + binary search (O(log n)), or the alias method for static weights.
Design a stack that returns its minimum in O(1). Can you use less memory?

Store (value, min so far) per entry: simple and safe. A second stack that only pushes when a new value is <= the current min saves memory when values mostly rise. The "one variable" trick stores 2x - min when x is a new minimum and decodes on pop; it saves memory but overflows easily, so mention it and prefer the pair version in code.

How to answer

Give the invariant (the min below an item never changes while it is there), code the pair version, then mention the space-saving variants and their risks.

Likely follow-ups
  • Add popMax / popMin: now you need a sorted structure (Max Stack, O(log n)).
  • Min queue: two min-stacks, or a monotonic deque.
Design a hit counter for the last 5 minutes. What if there are millions of hits per second?

Simple version: a queue of timestamps, pop from the front while older than t - 300. That is O(hits) memory. For huge traffic, keep 300 buckets of (second, count): hit goes to bucket t % 300 and resets it if its second is old; getHits sums buckets whose second is within the window. Fixed memory, O(300) per query (or keep a running total and subtract as buckets expire).

How to answer

Start with the queue, ask about volume and precision, then switch to buckets and say what precision you trade (one second).

Likely follow-ups
  • Concurrent hits: an atomic counter per bucket, or per-thread counters merged on read.
  • Across many servers: each server keeps buckets, an aggregator sums them.
  • Timestamps out of order: buckets still work if a hit is within the window.
Time Based Key-Value Store: get(key, t) returns the latest value set at or before t.

Map from key to a list of (time, value). Set times arrive strictly increasing, so appending keeps each list sorted. get does a binary search for the last time <= t (upper bound minus one); empty string if there is none. Set O(1), get O(log n). In Java a TreeMap.floorEntry per key is the same thing with a larger constant.

How to answer

Point at the constraint that makes appends sorted. Then write the binary search carefully: the boundary case is t smaller than every stored time.

Likely follow-ups
  • Times not in order: use a sorted map per key (O(log n) set).
  • Delete old versions: trim from the front of each list.
Your LRU cache is used by 64 threads. Make it fast.

Step 1: one mutex around get and put; correct but serial. A read-write lock does not help because get also moves the node. Step 2: shard by key hash into N independent LRU caches with their own locks; contention drops by about N, and eviction becomes per shard (approximate global LRU). Step 3: approximate recency: CLOCK keeps a reference bit per entry that get sets without a lock, and a sweeping hand evicts entries whose bit is clear. That is how the kernel's page reclaim and many production caches avoid a lock on every hit.

How to answer

Correct first, then scalable, and say what each step gives up (exact LRU order).

Likely follow-ups
  • Lock-free hash map? Mention striped locks or a concurrent map (Java ConcurrentHashMap) and that the list is the hard part.
