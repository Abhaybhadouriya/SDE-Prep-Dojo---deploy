  • Cue: grid + connected regions/islands -> count components with BFS/DFS flood fill.
  • Insight: each new land cell met by the scan = a new island; flood it so it is never met again.
  • State: islands counter, queue, grid itself as the visited set ('1' -> '0').
  • Trap: mark on push, check bounds first, 4 directions, char '1' not int 1.
  • Cost: O(m·n) time, O(m·n) worst-case queue; recursive DFS risks stack depth.
for each cell s in grid:
    if is_new(s):
        count += 1; mark(s); q = deque([s])
        while q:
            u = q.popleft()
            for v in neighbours(u):
                if inside(v) and is_new(v): mark(v); q.append(v)

BFS flood fill: why mark a cell as water when you push it, not when you pop it?

  1. popping order would change the count
  2. otherwise one cell can sit in the queue several times (up to once per land neighbour)
  3. it is required for correctness of the island count
  4. it makes the grid read-only
Marking on pop still gives the right count if you skip visited cells on pop, but a cell can be queued up to 4 times. Marking on push queues each cell once.

On a 300 × 300 all-land grid, how deep can a recursive 4-direction DFS go?

  1. about 300
  2. about 600
  3. up to m·n = 90,000 frames
  4. about log(90,000)
The recursion can snake through every cell before it returns. 90,000 frames fit in an 8 MB Linux stack but are risky on Windows' 1 MB; use BFS or an explicit stack.
