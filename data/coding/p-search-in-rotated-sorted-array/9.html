  • Cue: sorted + rotated + O(log n) -> binary search on "which half is sorted".
  • Insight: at any mid, one half has no drop; range-check the target only there.
  • State: lo, hi, mid; test nums[lo] <= nums[mid].
  • Trap: use <= in the sorted test; strict at mid in the range test; distinct values only.
  • Cost: O(log n) time, O(1) space; linear scan O(n); duplicates O(n) worst.
while lo <= hi:
    mid = (lo + hi) // 2
    if a[mid] == t: return mid
    if a[lo] <= a[mid]:   # left sorted
        lo, hi = (lo, mid - 1) if a[lo] <= t < a[mid] else (mid + 1, hi)
    else:                 # right sorted
        lo, hi = (mid + 1, hi) if a[mid] < t <= a[hi] else (lo, mid - 1)

[4, 5, 6, 7, 0, 1, 2], lo = 0, mid = 3. Which half is sorted?

  1. left [4..7]
  2. right [7, 0, 1, 2]
  3. neither
  4. both
nums[lo] = 4 <= nums[mid] = 7, so lo..mid has no drop. Check the target against that range only.

Why is the sorted-half test nums[lo] <= nums[mid] and not <?

  1. for speed
  2. when lo == mid (two elements left) the left half is one element and is sorted
  3. to allow duplicates
  4. it is a typo; < is correct
With <, a 2-element range [3, 1] picks the wrong half and can miss the target.

What changes if values can repeat (LC 81)?

  1. nothing
  2. nums[lo] == nums[mid] == nums[hi] hides the sorted half; shrink lo and hi by one, worst case O(n)
  3. you must sort first
  4. the answer becomes the index of the first copy
[1, 0, 1, 1, 1] cannot be told from [1, 1, 1, 0, 1] at mid, so you give up one step.
