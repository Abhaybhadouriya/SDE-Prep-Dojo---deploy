The problem (in our words)

You get an integer array nums whose values are all distinct and were sorted in ascending order. Before you see it, the array may have been rotated at an unknown pivot k: it became [nums[k], nums[k+1], ..., nums[n-1], nums[0], ..., nums[k-1]]. For example, the shelf [2,9,17,24,33,40,45] rotated at k = 5 becomes [40,45,2,9,17,24,33]. Given the rotated array and an integer target, return the index of target in nums, or -1 if it is not there.

You must write an algorithm that runs in O(log n) time.

Signature: int search(int[] nums, int target) (LeetCode style).

  • 1 <= nums.length <= 5000
  • -104 <= nums[i] <= 104
  • All values of nums are unique.
  • nums is an ascending array that is possibly rotated.
  • -104 <= target <= 104

Practice it: LeetCode 33 · GfG Search in a Rotated Array · TUF article

Constraints tell you: n is only 5000, so a linear scan would pass the judge, but the statement demands O(log n): the interview is about the binary-search argument. "Distinct" is what makes nums[lo] <= nums[mid] a reliable "left half is sorted" test; with duplicates (LC 81) that test breaks.
