Approaches: brute → better → optimal

Hint 1

Pick any mid. Compare nums[lo] with nums[mid]. What does that tell you about [lo..mid]?

Hint 2

In a sorted range you can test "target in range?" with first <= target <= last. Which half can you test that way?

Hint 3

If the target is not in the sorted half, it can only be in the other half, sorted or not.

1. Brute force - scan every index

Idea: loop i from 0 to n - 1 and return i when nums[i] == target.

O(n)time
O(1)space

What is wasted: it ignores that the array is two sorted runs. -> rung 2.

2. Better - find the pivot, then a normal binary search

Idea: first binary-search the index of the minimum, rot (compare nums[mid] with nums[hi]: if bigger, the drop is to the right). Then search the "unrotated" array by mapping a virtual index m to the real index (m + rot) % n.

lo, hi = 0, n - 1
while lo < hi:                       # find the smallest value
    mid = (lo + hi) // 2
    if nums[mid] > nums[hi]: lo = mid + 1
    else: hi = mid
rot = lo                             # then binary search on (m + rot) % n
O(log n)time
O(1)space

Good: it reuses two textbook searches and is easy to prove. What is wasted: two passes and an index mapping that is easy to get off by one. -> rung 3 does it in one pass.

3. Optimal - one binary search, keep or drop the sorted half

if nums[lo] <= nums[mid]:                  # left half sorted
    if nums[lo] <= target < nums[mid]: hi = mid - 1
    else: lo = mid + 1
else:                                      # right half sorted
    if nums[mid] < target <= nums[hi]: lo = mid + 1
    else: hi = mid - 1
  1. The range [lo..hi] is always a rotated sorted array. Any contiguous piece of one is (it has at most one drop).
  2. One half has no drop. If nums[lo] <= nums[mid], the values rise from lo to mid, so [lo..mid] is sorted; otherwise the drop is inside [lo..mid], so [mid..hi] is sorted.
  3. A sorted half answers membership exactly. The target is in it only if it lies between that half's first and last values.
  4. Drop one half every step. If the target fits, search the sorted half; else search the other one. Each step at least halves the range: O(log n).
O(log n)time
O(1)space

Why it works: we never decide based on the half we cannot reason about. We only ask the sorted half "could the target be here?", whose answer is exact. A "no" means the target, if present, is in the other half; a "yes" means it can only be here, because values are distinct.

Proof (optional)

Invariant: if the target is in nums, its index is in [lo, hi]. It holds at the start. In a rotation of distinct sorted values, every value after the drop is smaller than every value before it. Case nums[lo] <= nums[mid]: if the drop were inside (lo, mid], nums[mid] would be after it and nums[lo] before it, so nums[mid] < nums[lo], a contradiction. So nums[lo..mid] increases, and the target is in [lo, mid - 1] exactly when nums[lo] <= target < nums[mid]; otherwise it can only be in [mid + 1, hi]. Case nums[lo] > nums[mid]: the drop is in (lo, mid], so nums[mid..hi] has none and increases; the mirror test applies. Each step removes mid and one side, so the loop runs at most ⌊log2 n⌋ + 1 times and returns -1 only when the range is empty.

Stuck? Why <= in nums[lo] <= nums[mid]?

When lo == mid (two elements left), the left "half" is the single cell [lo]. It is trivially sorted, and with < you would wrongly treat the right side as sorted. Example: [30,10], target 10.
