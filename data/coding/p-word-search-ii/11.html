Interview follow-ups

The board is all 'a' and the words are like "aaaaaaaaab". Why is it slow, and what helps?

Every path of 'a's matches the trie, so the DFS explores nearly all 4·39 paths from every cell before the final 'b' fails. Two cheap fixes: (1) drop a word up front if the board does not hold enough of each of its letters (a count check); (2) insert the word reversed when its last letter is rarer on the board than its first, so the path dies on the first letter instead of the tenth (remember to un-reverse when reporting).

How to answer

Name the adversarial input, then give the letter-count filter and the reverse trick.

Likely follow-ups
  • Does pruning help here? (Only once words are found; failing words are never pruned.)
Allow diagonal moves (Boggle).

Use 8 directions instead of 4. Nothing else changes; the worst case grows to m·n·8·7L-1, which is why pruning and the letter-count filter matter more.

How to answer

Point to the direction list as the only change.

Likely follow-ups
  • Return the words sorted, or with the start cell of each.
The trie uses too much memory. What can you do?

An array of 26 child pointers per node is fast but wasteful. Use a hash map per node, or a sorted small array of (letter, child) pairs, or a node pool with int indices (as in the C++ code) instead of pointers. Pruning also frees memory as the search goes. For a fixed dictionary, a compressed trie (radix tree) merges single-child chains.

How to answer

Give the space/time trade-off of each child representation.

Likely follow-ups
  • Unicode letters instead of a-z: the map version works unchanged.
Can you avoid modifying the input board?

Yes: use a separate visited[m][n] boolean grid (or a 144-bit mask, since m·n ≤ 144) and set/clear it instead of writing '#'. Same complexity, O(m·n) extra memory. Mention that the in-place version restores the board, so the caller sees it unchanged at the end.

How to answer

Offer the visited grid and say the in-place trick is only an optimisation.

Likely follow-ups
  • Make it safe to run in parallel threads: each thread needs its own visited grid (and its own copy of a pruned trie, or no pruning).
Parallelise the search over a large board.

Split the start cells between workers. Each worker needs its own visited marks. The shared trie is read-only if you drop pruning and one-shot clearing; collect results in per-worker sets and merge. If you keep pruning, guard node deletion (or give each worker a copy of the trie), which costs more memory but avoids locks.

How to answer

Identify the shared mutable state (board marks, trie pruning, results) and handle each.

Likely follow-ups
  • Distribute the dictionary instead: shard words by first letter across machines.
Return how many times each word can be traced, not just whether.

Do not clear node.word and do not prune; instead increment a counter on the end node each time the DFS lands on it. Every distinct path is counted once because a DFS visits each path once. The run time becomes the full worst case, since nothing can be cut.

How to answer

Say which optimisations you must give up and why.

Likely follow-ups
  • Count distinct start cells instead of distinct paths.
