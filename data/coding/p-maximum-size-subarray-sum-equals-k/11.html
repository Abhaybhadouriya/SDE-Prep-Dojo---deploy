All values are positive. Can you use O(1) space?

Yes. With positive values the window sum grows when r moves and shrinks when l moves, so a sliding window finds every window with sum exactly k: extend r, shrink l while the sum exceeds k, record r - l + 1 when it equals k. O(n) time, O(1) space.

How to answer

Name the property (monotonic window sum) and why negatives break it.

Likely follow-ups
  • Zeros allowed? The window still works for "longest" (keep extending through zeros), but be careful when counting.

When best improves at index i, save (first[run - k] + 1, i). With a strict improvement test the leftmost of the longest answers is kept.

Shortest subarray with sum exactly k (negatives allowed).

Same scan, but overwrite: keep the LAST index of each prefix value and take the minimum of i - last[run - k]. The closest start gives the shortest run.

How to answer

One flip in the map policy: first index for longest, last index for shortest.

Likely follow-ups
  • Shortest with sum AT LEAST k and negatives? That needs a monotonic deque of prefixes (LC 862).
Longest subarray with sum at most k (negatives allowed).

For end r you need the earliest l with pre(l) ≥ pre(r) - k. Build prefix maxima from the left (non-decreasing), then binary search the first position whose prefix max is ≥ pre(r) - k. O(n log n).

How to answer

Show that "equals" becomes "at least", so a hash map no longer helps but a monotone array does.

Likely follow-ups
  • O(n)? A two-pointer method over suffix minima exists; mention it only if asked.
Worst case of the hash map, and the memory used.

Up to n + 1 distinct prefixes, so O(n) entries (about 200 k here). Average O(1) per operation; adversarial keys can degrade unordered_map / HashMap buckets, so mention a randomised hash or sorting-based alternatives if the input is hostile.
