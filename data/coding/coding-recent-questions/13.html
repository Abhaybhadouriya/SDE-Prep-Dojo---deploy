Interview questions

LRU Cache: why a doubly linked list and not a singly linked one?

Both operations must be O(1). On get we move a node from the middle to the front, and on eviction we remove the last node. Unlinking a node needs its predecessor; a singly linked list would need an O(n) walk to find it (or the trick of storing the previous node in the map, which breaks after every move). With prev pointers and two sentinels, unlinking is two pointer writes and never needs a special case for the first or last node.

How to answer

Name the two operations that must be O(1), show which one needs the predecessor, then mention the sentinels.

Likely follow-ups
  • "Why store the key in the node?" (to delete the evicted node from the map).
  • "What is the memory overhead per entry?" (two pointers, the key, plus the map entry).
Now make your LRU cache safe to call from many threads.

The simple correct answer is one mutex around get and put: note that get writes too (it moves the node), so a reader-writer lock does not help. If that lock is a bottleneck, shard: N independent LRU caches, each with its own lock, chosen by hash(key) % N. The cost is that eviction is per shard, so the cache is only approximately LRU overall. A third option is to buffer the "move to front" events and apply them in batches, which is what some production caches do.

How to answer

Start with the single lock and say why a read lock is wrong, then offer sharding with its trade-off.

Likely follow-ups
  • "How do you add a TTL?" (store an expiry time per node; on get, treat expired as a miss and remove it).
Course Schedule II: how do you detect a cycle with Kahn's algorithm, and what do you return?

Count in-degrees, push every course with in-degree 0, and repeatedly pop one, append it to the order and decrement its neighbours, pushing any that reach 0. If the order ends with fewer than n courses, the rest are stuck behind a cycle (none of them ever reaches in-degree 0), so return an empty list. Time and space O(V + E).

How to answer

Give the loop, then the one-line cycle test "len(order) < n". Mention the DFS three-colour version as the alternative.

Likely follow-ups
  • "Fewest semesters if you can take any number of courses at once?" (process Kahn's queue level by level and count levels).
  • "Which courses are in the cycle?" (those left with in-degree > 0 include them; DFS with colours finds one cycle exactly).
Rotting Oranges: why put every rotten orange in the queue at the start, and why mark when you push?

All rotten oranges spread at the same time, so they are all at distance 0. Starting BFS from all of them gives each fresh orange its distance to the nearest rotten one in a single O(rows x cols) pass; running one BFS per rotten orange would be O(k x rows x cols). Marking on push guarantees each cell is enqueued once; marking on pop lets two neighbours push the same cell in the same level.

How to answer

Say "multi-source BFS, levels are minutes", then the two invariants: all sources at level 0, each cell pushed once.

Likely follow-ups
  • "Return -1 when?" (fresh oranges remain after the queue empties: they are cut off by empty cells).
Merge Intervals, follow-up: the intervals arrive one at a time and you must answer "merged list so far" after each. What changes?

Re-sorting after every arrival costs O(n log n) per insert. Keep the merged intervals in a balanced ordered map keyed by start (a TreeMap in Java, std::map in C++). For a new interval, find the last start <= its start, then absorb every overlapping neighbour to the right and delete them. Each interval is inserted once and deleted at most once, so the total over all arrivals is O(n log n).

How to answer

Point out the cost of the naive approach, name the ordered map, and give the amortised argument.

Likely follow-ups
  • "And if intervals can be removed?" (store the raw intervals too, or use a segment tree over coordinates).
Random Pick with Weight: how do you pick, and what if the weights change between picks?

Build prefix sums once: for weights [1, 3, 2] they are [1, 4, 6]. Draw a random integer r in [1, total] and binary search for the first prefix >= r; that index is the pick. Build is O(n), each pick O(log n). If weights change, a plain prefix array costs O(n) per update; a Fenwick tree gives O(log n) updates and O(log n) picks (search down the tree for the target sum). Use 64-bit totals if weights can be large.

How to answer

Draw the number line split into segments of length w[i]; the picture makes the binary search obvious.

Number of Islands on a 1000 x 1000 grid: DFS or BFS?

Both are O(rows x cols). The difference is memory and safety: recursive DFS can go a million frames deep on an all-land grid and overflow the stack, especially with an 8 MB default thread stack or in Java and Python. BFS with a queue, or DFS with an explicit stack, keeps the extra memory on the heap. Union-find is the third option and is the right one when cells are added over time (Number of Islands II).

How to answer

Give the complexity first, then the stack-depth risk, then when union-find wins.

You recognise the problem as one you have practised. What do you do?

Solve it the normal way: restate it, ask about the constraints, give the brute force in a sentence, then the better approach, and code it. Rushing to a memorised answer skips the reasoning the interviewer is grading, and a twist usually follows. If the interviewer asks whether you have seen it, say yes; many will just move to the follow-up.

How to answer

Honest, short, and then back to the process.
