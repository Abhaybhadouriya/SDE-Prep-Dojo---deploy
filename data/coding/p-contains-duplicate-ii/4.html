Approaches: brute → better → optimal

Hint 1

When you stand at index i, which indices could possibly be its partner if you only look backwards?

Hint 2

If a value appeared several times before i, which of those earlier copies is the only one worth checking?

1. Brute force - compare with the next k elements

Idea: for every i, compare nums[i] with nums[i+1] .. nums[min(n-1, i+k)]. Return true on the first match.

O(n · min(n, k))time (10^10 in the worst case)
O(1)space

What is wasted: each element is compared with the same neighbours again and again. A hash structure answers "is this value among the last k?" in O(1).

2. Better - last-seen index map

Idea: walk left to right with a map value → latest index. At index i, if nums[i] is in the map and i - last[nums[i]] <= k, return true; then overwrite last[nums[i]] = i.

Why the latest index is enough: for the current i and any later index, the nearest earlier copy of the value is the most recent one. If the most recent copy is more than k away, every older copy is even farther, so throwing older indices away loses nothing. This is the idea in most top-voted answers.

O(n)time (expected, hashing)
O(n)space (one entry per distinct value)

What is wasted: the map keeps values from far back that can never pair again. With k much smaller than n, memory can be bounded by k.

3. Optimal - sliding window set of size k

for i, x in enumerate(nums):        # core
    if x in window: return True
    window.add(x)
    if i >= k: window.remove(nums[i - k])
  1. Invariant: when the loop reaches index i, the set holds exactly the values of nums[i-k .. i-1] (fewer near the start). Those are the only indices within distance k behind i.
  2. Check, then insert. If nums[i] is already in the set, an equal value lies at most k back: true. Otherwise add it.
  3. Evict. Before moving to i + 1, remove nums[i-k]: it is k + 1 away from i + 1. Because we return on the first repeat, all values in the set are distinct, so removing one value removes exactly that index.
O(n)time (expected)
O(min(n, k))space (at most k + 1 values)

Why it works: every pair (j, i) with j < i and i - j <= k is examined exactly when the scan reaches i, because j is then inside the window. Pairs farther apart are never in the set together. So the scan returns true iff such a pair exists. The "set values are distinct" property is what makes value-based removal safe: without the early return, two copies of one value in the window would share one set entry and removing it would forget the newer copy.

Sort by value instead? (optional)

Sort the pairs (value, index); equal values become adjacent and sorted by index, so the closest pair of equal values is always adjacent. Scan adjacent pairs: O(n log n) time, O(n) space. It works but is worse than both hash versions, so mention it only if hashing is ruled out.
