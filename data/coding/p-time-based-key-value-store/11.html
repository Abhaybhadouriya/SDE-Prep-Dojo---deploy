Interview follow-ups

Timestamps of set may arrive out of order. What changes?

The array is no longer sorted by appending. Use a balanced sorted map per key (TreeMap.floorEntry, std::map, or Python sortedcontainers.SortedList): O(log n) set and get. If out-of-order writes are rare, appending and fixing up with one insertion step (like insertion sort) keeps the array and is fast in practice.

How to answer

Tie the choice of structure to the ordering guarantee; that is the point of the question.

Likely follow-ups
  • Two sets with the same timestamp? (Define it: last writer wins, or reject.)
Memory is limited: old versions must be dropped.

Keep a retention window W: on each set, pop entries older than now - W from the front of the key's list (a deque makes it O(1) amortised), and answer gets for older times with "". Or cap the versions per key at k. This is how MVCC stores compact history.

How to answer

Ask which reads must stay correct, then pick time-based or count-based retention.

Likely follow-ups
  • Compact keys nobody reads? (Track last access, evict in LRU order.)
Make it thread-safe for many readers and one writer.

A read-write lock per key (or striped locks over key hashes) lets gets run in parallel. Because lists are append-only, a lock-free variant works too: the writer appends, then publishes the new length with a release store; readers load the length with acquire and search only that prefix. Growth of the array still needs care (copy-on-grow, publish the new pointer).

How to answer

Point out that append-only data is the easy case for concurrency, the same reason log-structured storage is popular.

Likely follow-ups
  • What about the hash map itself? (A concurrent map, or a lock only for creating a new key.)
Add getRange(key, t1, t2) returning all values written in [t1, t2].

Two binary searches: lower bound of t1 and upper bound of t2, then return the slice between them. O(log n + k) for k results.

How to answer

Reuse the same search helper; this is why writing upper/lower bound as a function pays off.

Likely follow-ups
  • Across all keys? (A global time index, or a merge of per-key results.)
Scale it to many machines.

Shard by key hash (consistent hashing), so each key's history lives on one node and gets stay one binary search. Replicate each shard; with a single writer per key the append order is preserved. Persist as an append-only log per shard and rebuild the in-memory index on restart.

How to answer

Keep the per-key invariant (one ordered history) and push all distribution concerns to the key level.

Likely follow-ups
  • Clock skew between writers? (Use a logical clock or a sequencer instead of wall time.)
