Interview follow-ups

DFS or BFS - which and why?

Both are O(m·n) and both are correct; the order of repainting is the only difference. Recursive DFS is the shortest code; BFS (or DFS with an explicit stack) has no recursion-depth limit. Choose BFS when you also need distances (rotting oranges, shortest path in a grid).

How to answer

Name the trade-off in one sentence and pick the iterative one if the image can be large.

Likely follow-ups
  • Worst-case queue size for BFS? (O(m + n)-ish for a frontier in a square, but O(m·n) is the safe bound.)
The image is 20,000 x 20,000 pixels. What breaks and how do you fix it?

Recursive DFS overflows the call stack (4·108 frames). Use an explicit stack/queue on the heap. To cut memory further, use scanline fill: from a pixel, extend left and right along the row while the colour matches, paint the whole run, and push only one seed per run in the rows above and below. That pushes O(runs) seeds instead of O(pixels).

How to answer

First the stack problem, then the memory optimisation that real paint programs use.

Likely follow-ups
  • Can it be parallelised? (Tile the image, fill tiles independently, merge regions across tile borders with union-find.)
Do not modify the input; return a new image.

Copy the image first (O(m·n) extra) and fill the copy. If you must keep the input untouched and avoid a copy until the end, keep a separate visited matrix and paint the output as you go.

How to answer

Mention that in-place marking is a space trick, and that it changes the caller's data.

Likely follow-ups
  • Space with a visited bitset? (m·n bits, 8x less than a bool array.)
Neighbours include the four diagonals (8-connectivity).

Use eight direction pairs instead of four; nothing else changes. Mention that the example's (1,2) pixel would then be filled, because it touches (0,1) and (2,1) diagonally.

How to answer

Keep directions in a table so the change is one line.

Likely follow-ups
  • Hex grid? (Six neighbours with row-parity-dependent offsets.)
Many fill queries on the same image. Can you answer each fast?

Pre-label components once (one traversal or union-find over the grid, O(m·n)), storing for each component its pixel list. A fill query then repaints that list directly, and recolouring may merge it with neighbouring components of the new colour: union-find handles the merges, which is the standard "repeated paint bucket" approach.

How to answer

Move from per-query traversal to precomputed components; mention merges explicitly.

Likely follow-ups
  • Count the components after each query? (Union-find with a running counter.)
