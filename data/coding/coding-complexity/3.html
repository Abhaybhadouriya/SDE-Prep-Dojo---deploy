Counting loops: the shapes you will meet

Most interview code is loops. Recognise these shapes and you can state the complexity at a glance.

for (i = 0; i < n; i++)              /* O(n) */
for (i = 0; i < n; i++)
    for (j = 0; j < n; j++)          /* O(n^2) */
for (i = 0; i < n; i++)
    for (j = i + 1; j < n; j++)      /* n(n-1)/2 pairs: still O(n^2) */
for (i = 1; i < n; i *= 2)           /* doubles: O(log n) */
for (i = n; i > 0; i /= 2)           /* halves: O(log n) */
for (i = 1; i <= n; i++)
    for (j = i; j <= n; j += i)      /* n/1 + n/2 + n/3 + ... = O(n log n) (harmonic sum) */
for (i = 0, j = 0; i < n; i++)
    while (j < n && ok(i, j)) j++;    /* j never moves back: O(n) total, not O(n^2) */

The last shape is the one people get wrong. A while nested inside a for looks quadratic, but if the inner pointer only moves forward and never resets, it moves at most n times over the whole run. That is why two-pointer and sliding-window solutions are O(n). The same argument covers a monotonic stack: each element is pushed once and popped at most once, so the total work is O(n) even though one iteration might pop many elements. This is your first taste of amortised analysis.

Calls hide loops. s.substring(i, j), list.index(x), x in list, s1 + s2, sorted(a) and vector.insert(begin, x) are all loops inside a library. A single line inside a loop can turn O(n) into O(n²). See hidden costs.
