The story: finding a name in a phone book

Explain like I'm 5

You want to find "Meera" in a phone book with 1,000 pages. Plan one: start at page 1 and look at every page. If Meera is near the end, you turn almost 1,000 pages. Plan two: open the book in the middle. If the names there start with "S", Meera must be in the first half, so tear the book in half and throw the back half away. Do it again and again. After about 10 tears only one page is left. Plan one gets twice as slow when the book gets twice as thick. Plan two needs just one more tear.

Complexity is the habit of asking "how does the work grow when the input grows?" instead of "how many milliseconds did it take on my laptop?". Plan one is linear: work grows in step with the number of pages, written O(n). Plan two is logarithmic: work grows by one step each time the input doubles, written O(log n). In a coding interview you will be asked for the time and space complexity of every solution, and the constraints in the problem statement tell you which complexity is good enough.

From your world

You already reason this way. The Linux 2.6 "O(1) scheduler" was named for its pick-next-task cost; CFS replaced it with a red-black tree, O(log n) per enqueue, and nobody worried because n is the number of runnable tasks on one CPU. Connection tracking uses a hash table so a lookup does not scan every flow. A route lookup in a longest-prefix-match trie costs at most one step per address bit (32 for IPv4), whatever the table size. Interview complexity is the same thinking, applied to arrays, strings, trees and graphs.
