Read the constraints first: n tells you the target

Interview platforms and LeetCode-style statements give limits such as 1 ≤ n ≤ 10⁵. A widely used rule of thumb is that a judge runs on the order of 10⁸ simple operations per second. Plug n into each complexity class and see which ones fit in about a second. This is not exact (constant factors, language speed and cache behaviour matter), but it tells you where to aim before you start.

Largest nTargetTypical techniqueExample
≤ 10 to 12O(n!) or O(n! · n)generate all permutationsPermutations
≤ 20 to 25O(2ⁿ · n)subsets, backtracking, bitmask DPSubsets
≤ 500O(n³)interval DP, Floyd-Warshall, three nested loopsburst-balloons style DP
≤ 5,000O(n²)2D DP table, all pairsLIS (the n² version)
≤ 10⁵ to 10⁶O(n log n) or O(n)sort, heap, binary search, two pointers, sliding window, hashingMerge Intervals
≥ 10⁹ (a value, not an array)O(log n) or O(√n)binary search on the answer, fast power, mathSqrt(x), Pow(x, n)

Say it out loud: "n is up to 10⁵, so O(n²) is 10¹⁰ steps, too slow. I'm aiming for O(n log n) or better." This one sentence shows the interviewer you plan before you code, and it often points straight at the technique (sorting, a heap, binary search).

When the statement gives no limits (common in live interviews), ask: "How large can n get? Can values be negative? Is the input sorted?" The answer usually decides between a brute force and the intended solution.
