Space: memory you allocate plus the call stack

Space complexity counts the extra memory your algorithm needs as n grows. Interviewers usually mean auxiliary space: memory beyond the input. By common convention the output array is not counted (say so: "O(1) extra space, not counting the output"). Three sources add up:

  1. Data structures you create: a hash map of n entries is O(n), a DP table m × n is O(mn), a visited array is O(V).
  2. The call stack: each recursive call keeps a frame alive until it returns. Space = maximum depth × frame size, so recursion with depth n is O(n) space even if you allocate nothing.
  3. Hidden copies: slicing (a[1:] in Python copies), string concatenation, passing a vector by value in C++, and recursion that builds new lists at every level.

From your world

The x86-64 kernel stack is 16 KB per thread, which is why kernel code avoids recursion entirely. User space is more generous (a main thread commonly gets 8 MB on Linux, set by ulimit -s), but online judges and languages add their own limits: Python's default recursion limit is 1,000 frames, Java threads default to a stack of around 512 KB to 1 MB depending on the platform. A recursive DFS on a 10⁵-node path graph can crash in Python or Java. Say it in the interview and offer an iterative version with an explicit stack: same O(n) space, but on the heap.

A useful trick for DP: if row i depends only on row i - 1, keep two rows (or one), turning O(mn) space into O(n). Mention it even if you do not code it; it is a common follow-up.
