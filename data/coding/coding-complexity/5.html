Amortised analysis: the occasional expensive step

Some operations are usually cheap and occasionally expensive. Amortised cost is the total cost of a whole sequence of operations divided by the number of operations, in the worst case over sequences. It is a guarantee, not an average over random inputs. The classic example is appending to a dynamic array (C++ vector, Java ArrayList, Python list, Go slice).

  1. Capacity 1. Pushing the first element costs one write.
  2. The array is full, so push 2 allocates a new array of twice the size and copies the old element across. Copying is the expensive part.
  3. Full again at 2: allocate 4, copy 2. Notice each copy is as big as all the cheap pushes since the previous copy.
  4. Push 4 lands in a free slot: cost 1.
  5. Full at 4: allocate 8, copy 4.
  6. Pushes 6, 7 and 8 are cheap. Most pushes are like this.
  7. Push 9 copies 8 elements. Total work for 9 pushes is 24, under 3 per push. Copies add up to 1 + 2 + 4 + 8 < 2n, so each push is O(1) amortised even though one push is O(n).

Why does it work? When capacity grows by a constant factor (2× in libstdc++, 1.5× in Java's ArrayList), the copies form a geometric series that sums to a constant times n. Growing by a fixed amount (say +10 slots) would make the copies 10 + 20 + 30 + ... = O(n²). That is exactly why you should never write realloc(p, (len + 1) * sizeof *p) in a loop in C.

The other amortised argument you will use constantly is the aggregate (counting) method from the loop shapes above: count how many times each element can be touched in total. In a monotonic stack, every index is pushed once and popped at most once, so n iterations do at most 2n stack operations. In a sliding window, the left edge and right edge each move at most n times. Union-find with path compression and union by rank is the famous advanced case: nearly O(1) amortised per operation (inverse Ackermann), which you can state without proof.

From your world

Amortised O(1) is fine for throughput but bad for latency: one push in a million still pays the full copy. Kernel code often cannot accept that spike, which is why the kernel's resizable hash table (rhashtable) grows its table in a deferred worker instead of inside the insert that crossed the threshold, and why fixed-size ring buffers are preferred on fast paths. If an interviewer asks "what if one slow operation is unacceptable?", mention pre-sizing (reserve, initial capacity) or incremental rehashing.
