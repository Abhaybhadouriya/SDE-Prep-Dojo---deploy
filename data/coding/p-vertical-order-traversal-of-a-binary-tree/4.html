Approaches: brute -> better -> optimal

Hint 1

If you knew every node's (row, col), could you write the answer without looking at the tree again?

Hint 2

The required order is: by column, then by row, then by value. That is exactly lexicographic order on the tuple (col, row, val).

1. Brute force - one pass over the tree per column

Idea: find the minimum and maximum column with one traversal. Then for each column c, traverse the whole tree again, collect the (row, val) pairs whose column is c, sort them, and output the values.

O(n · w + n log n)time, w = width
O(n)space

What is wasted: every node is visited once per column; on a chain that is O(n2). One traversal already knows every node's column. -> rung 2.

2. Better - nested maps: col -> row -> sorted values

Idea: traverse once and insert each value into map[col][row] (a TreeMap of TreeMaps, or a hash map of lists that you sort later). Read columns in increasing order, rows in increasing order, and values sorted inside each cell. This is the approach most top Java solutions use (TreeMap<Integer, TreeMap<Integer, PriorityQueue<Integer>>>).

O(n log n)time
O(n)space

Correct, but three nested containers are a lot to type and to explain under pressure. -> rung 3 says the same thing with one array and one sort.

3. Optimal and simplest - record triples, sort once, group

cells = []                                  # (col, row, val) per node
dfs(root, row=0, col=0)                     # left: (row+1, col-1), right: (row+1, col+1)
cells.sort()                                # col, then row, then val
start a new output list each time col changes
  1. Coordinates are local. A child's (row, col) depends only on its parent's, so any traversal (pre-order DFS, BFS) computes them in O(n).
  2. The order is a tuple order. "Leftmost column first; inside a column top to bottom; inside one cell smaller value first" is exactly lexicographic order on (col, row, val). Sorting the triples applies all three rules at once.
  3. Grouping is one scan. After the sort, nodes of the same column are contiguous; cut where col changes.
O(n log n)time
O(n)space

Why it works: sorting by a tuple key is sorting by the first field, breaking ties by the second, then the third. The problem's rule has exactly that shape, so the sort is not a trick, it is a direct translation of the statement. Because the sort imposes the order, the traversal order does not matter at all: pre-order, in-order, BFS, iterative stack all give the same answer.

Can it be O(n)? (optional)

Columns are a contiguous range of width w <= n, so you can bucket by column in O(n) and, with BFS, rows arrive in increasing order for free. Only nodes sharing one exact cell still need sorting by value, so the cost is O(n + sum of k log k) over cells of size k. In the worst case that is still O(n log n), and the interviewer will accept the single sort. Mention the bucket idea only as a follow-up.
