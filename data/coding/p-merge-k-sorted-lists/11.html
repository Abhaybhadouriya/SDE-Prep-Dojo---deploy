Interview follow-ups

Heap or divide and conquer: which would you code, and why?

Both are O(N log k). I code the heap first because it has fewer moving parts and maps directly to the invariant. If the interviewer wants O(1) extra space, I switch to pairwise merging done iteratively.

How to answer

State both bounds, pick one with a reason (simplicity, space, parallelism), and offer the other.

Likely follow-ups
  • Which one has better cache behaviour? (Pairwise walks lists sequentially; the heap jumps between lists.)
  • What is the recursion depth of the recursive D&C? (log k.)
The lists are huge sorted files on disk. How do you merge them?

This is the merge phase of an external sort. Open k buffered readers, keep a min-heap of (current value, file id), and write the output through a buffered writer. Memory is O(k × buffer size). If k is too large for open file handles or memory, merge in several passes (for example groups of 100 files), which is the pairwise idea with a wider fan-in.

How to answer

Name external merge sort, then talk about buffers, file handles and number of passes.

Likely follow-ups
  • How do you choose the fan-in? (Memory / buffer size, and the cost of each extra pass over the data.)
Turn it into an iterator over k sorted streams (next / hasNext).

Keep the heap as a member. The constructor pushes the first element of each stream. next() pops the top, pulls the next element from the same stream if it has one, pushes it, and returns the popped value. hasNext() is "heap not empty". Each call is O(log k) and nothing is merged ahead of time.

How to answer

Show that the heap solution is already lazy; only the loop moves into next().

Likely follow-ups
  • A stream may block or be infinite: what then? (The heap still works; you only need each stream's next value.)
Return only the k-th smallest value over all lists.

Run the same loop but stop after the k-th pop: O(k log L) where L is the number of lists, independent of N. For sorted arrays you can also binary search on the value and count elements ≤ mid in each array.

How to answer

Reuse the merge and stop early; mention the value binary search as an alternative.

Likely follow-ups
  • Compare with LC 378 (sorted matrix).
Remove duplicates while merging.

Before linking a popped node, compare it with tail.val. If equal (and the output is not empty), skip it but still push its successor. The output remains sorted and holds each value once.

How to answer

One extra comparison at the append point; do not forget to advance the list you skipped from.

Likely follow-ups
  • Keep only values that appear in all k lists. (Count how many lists each value came from.)
Can you use several threads?

Yes with divide and conquer: in each round the pairwise merges are independent, so give them to a thread pool. There are log k rounds with a barrier between rounds. The last round is a single merge of two halves, so speed-up is limited at the end; a parallel merge (split by value ranges) fixes that if needed.

How to answer

Point at the independent pairs, the barrier per round, and the serial last round.

Likely follow-ups
  • Why is the heap version hard to parallelise? (Each pop depends on the previous one.)
