  • Cue: k sorted lists/arrays/streams -> one sorted output or k-th smallest overall.
  • Insight: the next output is always one of the k heads; min-heap of heads.
  • State: heap of (value, list id, node), dummy head, tail pointer.
  • Trap: skip null heads; tie-break so nodes are never compared; C++ needs greater-than.
  • Cost: O(N log k) time, O(k) space; D&C pairs O(N log k), O(1); one-by-one O(N·k).
heap = [(first(s), i) for i, s in enumerate(seqs) if s]
heapify(heap)
while heap:
    v, i = heappop(heap); emit(v)
    if has_next(i): heappush(heap, (next_of(i), i))

What is the largest the heap ever gets?

  1. N
  2. k (one head per non-empty list)
  3. N / k
Each pop is followed by at most one push from the same list, so the heap size never grows past the number of lists.

Merging list 0 with list 1, then the result with list 2, and so on, costs:

  1. O(N log k)
  2. O(N)
  3. O(N·k)
The growing result is walked again in every merge; early nodes are walked about k times.

Why does Python need a tie-breaker in (val, i, node)?

  1. On equal values Python would compare the ListNode objects and raise TypeError
  2. To keep the merge stable for the judge
  3. heapq only accepts 3-tuples
Tuples compare element by element; ListNode has no ordering, so equal values must be decided by the unique index.
