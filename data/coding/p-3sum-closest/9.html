60-second recall

  • Cue: three elements, sum closest to a target, return the sum -> sort + fix i + two pointers.
  • Insight: below the target, lo is useless with any partner left of hi: lo++. Above: hi--.
  • State: best (a real sum), i, lo = i+1, hi = n-1.
  • Trap: INT_MAX start overflows; return the sum, not the distance; exact hit returns early.
  • Cost: O(n²) time, O(1) extra.
a.sort(); best = a[0] + a[1] + a[2]
for i in range(len(a) - 2):
    lo, hi = i + 1, len(a) - 1
    while lo < hi:
        s = a[i] + a[lo] + a[hi]
        if abs(s - t) < abs(best - t): best = s
        if s == t: return s
        lo, hi = (lo + 1, hi) if s < t else (lo, hi - 1)
return best

Sorted [-4,-1,1,2], target 1, i = 0. The first sum is -4 + (-1) + 2 = -3. What moves?

  1. hi--
  2. lo++
  3. both
  4. i++
-3 < 1: the sum must grow, and only moving lo right can raise it while i is fixed.

Why is best = INT_MAX a bug in C++ for target = -5?

  1. It is never updated
  2. It returns the distance
  3. INT_MAX - (-5) overflows
  4. It breaks sorting
INT_MAX + 5 does not fit in int: signed overflow is undefined behaviour. A real starting sum avoids it.

The sum equals the target. What should the loop do?

  1. Return it: distance 0 is optimal
  2. Move both pointers like 3Sum
  3. Move lo only
  4. Keep scanning for a closer one
No sum can be closer than distance 0, so return immediately.
