Approaches: brute -> better -> optimal

Hint 1

If you fix one of the three numbers, what problem is left for the other two?

Hint 2

On a sorted array, if a pair sum is too small, which pointer can make it bigger, and what do you lose by moving it?

1. Brute force - every triplet

Idea: three nested loops over a < b < c; keep the sum with the smallest |sum - target|. Correct by definition, so we use it as the test oracle in the code files.

O(n³)time (~2*10⁷ at n = 500)
O(1)space

What is wasted: for a fixed pair (a, b), the best third element is simply the one closest to target - nums[a] - nums[b]. Scanning all c to find it is the waste.

2. Better - sort, fix two, binary search the third

Idea: sort; for each pair i < j, binary-search target - nums[i] - nums[j] in nums[j+1..] and check the element at the insertion point and the one before it (the two closest candidates). Clean proof, but one log factor too many.

O(n² log n)time
O(1)extra (sort in place)

What is wasted: as j moves right, the wanted third value moves left. The binary search starts from scratch each time instead of continuing from where it was. Two pointers exploit exactly that.

3. Optimal - sort, fix one, squeeze two pointers

nums.sort(); best = nums[0] + nums[1] + nums[2]
for i in range(n - 2):
    lo, hi = i + 1, n - 1
    while lo < hi:
        s = nums[i] + nums[lo] + nums[hi]
        if abs(s - target) < abs(best - target): best = s
        if s < target: lo += 1
        elif s > target: hi -= 1
        else: return s
  1. Sort once (O(n log n)); the problem asks for a sum, so losing the original indices does not matter.
  2. Fix i as the smallest index of the triplet; the other two come from nums[i+1..n-1].
  3. Squeeze: compute the sum, update best if it is strictly closer, then move lo right if the sum is below the target, hi left if above, and return immediately if it is equal (distance 0 cannot be beaten).
  4. Optional speed-up: skip i when nums[i] == nums[i-1]: the same fixed value would replay the same pairs. It does not change the O(n²) bound.
O(n²)time (sort is O(n log n))
O(1)extra (O(log n) for the sort's stack)

Why it works: for a fixed i, suppose the sum with (lo, hi) is below the target. Every other partner of lo that is still in range sits left of hi, so it is <= nums[hi] and gives a sum that is <= this one: even further below the target. So lo has already met its best partner and can be dropped. Symmetrically, a sum above the target lets us drop hi. Every step drops one index without losing the optimum, so a pass of at most n steps sees the closest pair sum for this i. The top-voted community solution draws exactly this "each index has a direction to move" picture.

Proof (optional)

Fix i and let (p, q) with p < q be the pair that is closest for this i. While both p and q are inside [lo, hi], the loop cannot skip them: if lo = p and hi > q, then sum(lo, hi) >= sum(p, q). If that sum is above the target we move hi, which is correct; if it is below or equal, then sum(p, q) <= sum(lo, hi) <= target, so (p, hi) is at least as close as (p, q) and the loop has already recorded a sum that good. The case hi = q, lo < p is the mirror. So the closest distance for i is always recorded before p or q leaves the window.
