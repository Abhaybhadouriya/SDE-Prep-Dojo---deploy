Approaches: brute -> better -> optimal

Hint 1

What does rotating a list of length 5 by 5 do? By 7?

Hint 2

After rotating right by k (k < len), which node becomes the new tail? Count from the head.

1. Brute force - one rotation at a time

Idea: repeat k times: walk to the second-last node, detach the last node and put it in front.

O(n × k)time
O(1)space

What is wasted: with k = 2 × 10^9 this never finishes, and every full circle of len rotations does nothing.

2. Better - k modulo length, then rotate one at a time

Count len first and set k %= len; now at most len - 1 single rotations: O(n²) worst case. Passes for n ≤ 500, but each rotation re-walks the list to find the second-last node.

Another "better" option: copy values into an array, rotate the array, write them back. O(n) time but O(n) space, and it moves values rather than nodes (interviewers often forbid that).

3. Optimal - close the ring, cut once

  1. Guard: empty list, one node, or k = 0 -> return head.
  2. Walk to the tail and count len.
  3. k %= len. If it becomes 0, the list is unchanged: return head (and do not create a ring).
  4. Find the new tail: node number len - k counting from 1, i.e. len - k - 1 steps from head.
  5. Re-link: newHead = newTail.next; newTail.next = null; tail.next = head.

Why it works: rotating right by k (0 < k < len) splits the list into a front part of len - k nodes and a back part of k nodes and swaps them. The front part ends at node len - k, so that node must become the tail, the node after it must become the head, and the old tail must point to the old head so the two parts are glued in the new order. Rotation by len is the identity, so rotation by k equals rotation by k mod len.

O(n)time (at most two walks)
O(1)space

The most-voted community solution points out that a slow/fast pointer trick does not save any moves here: you need the length anyway for the modulo, so one counting walk is the cleanest.
