  • Cue: ranges + overlap/union/merge -> sort by start, sweep with one open block.
  • Insight: after sorting, a merged group is contiguous; only the last block can grow.
  • State: out list; out[-1] is the open block.
  • Trap: end = max(end, e) (containment); <= so touching merges.
  • Cost: O(n log n) for the sort, O(n) sweep; brute overlap graph O(n²).
items.sort(key=lambda x: x.start)
out = []
for it in items:
    if out and it.start <= out[-1].end:
        out[-1].end = max(out[-1].end, it.end)
    else:
        out.append(it)

After sorting by start, the open block is [1, 10] and the next interval is [2, 5]. What is the open block after merging?

  1. [1, 5]
  2. [1, 10]
  3. [2, 10]
  4. [2, 5]
end = max(end, e). Writing end = e would shrink the block to [1, 5] when one interval contains the other.

Do [1, 4] and [4, 6] merge in this problem?

  1. yes, into [1, 6]
  2. no, they only touch
  3. only if sorted by end
  4. it depends on the input order
Touching intervals count as overlapping here, so the test is start <= end (not <).

Why sort by start and not by end?

  1. sorting by end is slower
  2. with starts in order, every interval that can join the open block arrives right after it
  3. the output must be sorted by end
  4. it removes duplicates
Sorted by start, a merged group is a contiguous run, so one sweep with one open block is enough.
