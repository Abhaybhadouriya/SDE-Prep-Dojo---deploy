Prove the predicate is monotone.

Let the single be at index s. Cells 0..s-1 hold complete pairs, so s is even and pairs there are (0,1), (2,3), ...: P(i) is true for every even i < s. From s on, the pairs are (s+1, s+2), (s+3, s+4), ...: an even i ≥ s is s itself or the right half of a pair, so nums[i] != nums[i+1]. So P is all-true then all-false, and the first false is s.

How to answer

Draw the indexes under a 7-cell example and point at the shift. It takes 30 seconds and settles every off-by-one question.

Likely follow-ups
  • Why is the final nums[lo] safe? Because the invariant keeps s in [lo, hi] and the loop ends with lo == hi.
The array is not sorted, but equal values are still adjacent.

The parity argument never used the order of values, only that each pair sits side by side. So the same O(log n) search works unchanged, for example on [7,7,2,2,9,4,4].

How to answer

Say which assumption the proof needs (adjacent pairs) and which it does not (sorted).

Likely follow-ups
  • If pairs are not adjacent at all, you are back to XOR in O(n).
Every value appears three times except one, still sorted and adjacent.

Groups now occupy (0,1,2), (3,4,5), ... before the single and are shifted after it. Force mid down to a multiple of 3. If nums[mid] == nums[mid+1], the group starting at mid is intact and the single is right of mid + 2 (lo = mid + 3); else the shift has already happened and hi = mid. Same shape, period 3 instead of 2.

How to answer

Generalise the invariant: lo and hi stay multiples of k.

Likely follow-ups
  • Unsorted and triple: Single Number II, bit counts mod 3.
Can you do it with the XOR-partner trick instead?

Yes: compare nums[mid] with nums[mid ^ 1]. Equal means mid is inside an intact pair before the single, so lo = mid + 1; otherwise hi = mid. It removes the "force mid even" line; the reasoning is identical.

How to answer

Explain why mid ^ 1 is the partner for both parities.

Likely follow-ups
  • Is (lo + hi) / 2 safe? Here n ≤ 105, yes; in general use lo + (hi - lo) / 2.
What if the input might be invalid (two singles, or none)?

The search then returns some index without a guarantee. If validity matters, verify the result in O(1): check nums[lo] differs from both neighbours. If it fails, report bad input; a full validation is O(n).

How to answer

Separate "what the algorithm assumes" from "how to detect a violation cheaply".

Likely follow-ups
  • Find both singles when two values appear once: unsorted version is LC 260 (XOR, then split by a set bit).
