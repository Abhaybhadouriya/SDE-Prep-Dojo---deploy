Approaches: brute → better → optimal

Hint 1

Try one window with "shrink while distinct > k, count when distinct == k". On [1,2,1], k = 2, which subarray does it miss?

Hint 2

Counting subarrays with at most k distinct values is a standard window. How do two such counts give "exactly k"?

1. Brute force - every start, grow a set

Idea: for each l, extend r and add nums[r] to a set; count when its size is k, stop when it passes k (it never shrinks again).

O(n2)time
O(n)space

What is wasted: for a fixed end, the good starts are one contiguous band (fewer distinct as the start moves right). We check every start in it one by one.

2. Better - see why one window is not enough

Idea: a single window "shrink while distinct > k, count 1 when distinct == k" counts one start per end. On [1,2,1], k = 2, at r = 2 the window is [1,2,1] and the starts 0 and 1 are both good ([1,2,1] and [2,1]), but it adds only 1, so it returns 2 instead of 3. Shrinking further to reach the shortest good window would lose the longer ones for later ends. The good starts for end r form a band [Lk(r) .. Lk-1(r) - 1]: it has two edges, and one window tracks only one.

3. Optimal - atMost(k) - atMost(k - 1)

  1. atMost(k): grow right; if freq[x] goes 0 → 1, distinct++. While distinct > k: decrement freq[nums[left]], if it hits 0 then distinct--, left++.
  2. Count: now [left..right] has at most k distinct, and so does every shorter suffix, so add right - left + 1.
  3. Subtract: answer = atMost(k) - atMost(k - 1). (atMost(0) is 0: every non-empty subarray has a value, the window empties itself each step.)
O(n)time (two passes, each pointer moves ≤ n)
O(n)space (count array of size n + 1)

Why it works: for a fixed end r, the number of distinct values in [l..r] can only drop as l moves right (we remove elements). So "at most k distinct" holds on a suffix of starts [Lk(r)..r], and Lk(r) never decreases as r grows, which is what a forward-only window needs. "Exactly k" = "at most k" and not "at most k - 1", so the good starts are the suffix for k minus the suffix for k - 1, and their count is (r - Lk + 1) - (r - Lk-1 + 1). Summing over r, the two sums separate into atMost(k) - atMost(k - 1).

One-pass variant (from a top community post): keep three indices, left, mid and right. mid is pushed right while nums[mid] still appears later in the window, so [mid..right] is the shortest good window ending at right and [left..right] the longest; add mid - left + 1. When a (k+1)-th value arrives, drop nums[mid] completely and set left = mid = mid + 1. Same O(n) in one pass, but harder to get right under pressure; code the subtraction.
