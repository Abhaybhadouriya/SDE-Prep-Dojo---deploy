Interview follow-ups

Why not run a DFS from every cell and memoise?

Equal heights create cycles (a plateau), so a cell's answer can depend on a neighbour that is still being computed, and a naive memo returns wrong "false" values. Reversing the search removes the dependency: each flood is a plain reachability BFS.

How to answer

Name the plateau cycle as the concrete failure, then give the reverse flood.

Likely follow-ups
  • How would you make the memo version correct? (Collapse each plateau into one node first.)
There are k oceans on different edge segments. Return the cells that reach all of them.

One flood per ocean, each with its own bitmap; AND them. O(k·m·n) time. To save memory, keep one counter grid and increment it per flood; the answer is cells with count k (each flood still needs its own visited set, a bitset of m·n bits).

How to answer

Generalise the AND to a count; mention bitsets.

Likely follow-ups
  • Cells that reach at least one ocean? (A single flood seeded with all edges.)
BFS or DFS here?

Both visit each cell once per flood. Recursive DFS is shorter but its depth can reach m·n (40,000) on a spiral; Python fails at about 1,000 by default. BFS or an explicit stack is safe in every language.

How to answer

Pick BFS, mention the stack depth in one sentence.

Likely follow-ups
  • Memory of the BFS queue in the worst case? (O(m·n), all cells equal.)
Return, for each cell, the minimum number of steps to reach the Pacific.

Keep the uphill rule and the multi-source BFS from the Pacific edge; BFS layers are distances in steps, so store the layer number instead of a boolean. Cells never reached get -1.

How to answer

Point out that multi-source BFS already computes distance to the nearest source.

Likely follow-ups
  • Steps have different costs (height differences)? (Dijkstra with a heap.)
The heights change: one cell is raised or lowered per query. Keep the answer up to date.

One change can both add and remove paths: raising a cell makes it easier to enter from below but harder to climb out of toward higher neighbours. So there is no simple monotone update. The honest baseline is to recompute both floods, O(m·n) per query, and say so. If updates are rare and queries ("does cell x reach both?") are many, precompute once and recompute lazily on the next query after a change.

How to answer

Show why it is not monotone with one cell, then give the recompute cost; fully dynamic reachability is research-level, not an interview answer.

Likely follow-ups
  • Only "lower to sea level" updates? (A lowered cell can only lose paths through it as a stepping stone and gain direct drainage from higher neighbours: re-flood locally.)
