60-second recall

  • Cue: grid + "which cells can reach the border/exit" -> flood from the border, not from cells.
  • Insight: reverse the move rule (climb to >= heights); one flood per ocean, answer = AND.
  • State: two visited grids, one queue seeded with a whole edge set each time.
  • Trap: use >= not >, separate visited per ocean, mark on push, corners are in both.
  • Cost: O(m·n) time and space; brute force from every cell is O((m·n)²).
def flood(seeds, can_enter):        # multi-source BFS
    seen = set(seeds); q = deque(seeds)
    while q:
        u = q.popleft()
        for v in neighbours(u):
            if v not in seen and can_enter(u, v): seen.add(v); q.append(v)
    return seen
answer = flood(edgeA, rule) & flood(edgeB, rule)

The reverse flood starts at an ocean edge. When may it step from cell u to a neighbour v?

  1. h[v] >= h[u]
  2. h[v] > h[u]
  3. h[v] <= h[u]
  4. |h[v] - h[u]| <= 1
Water flows from v down to u when h[v] >= h[u]. Equal heights flow too, so > would miss plateaus.

Why use two visited grids instead of one shared grid?

  1. A cell the Pacific flood has reached must still be enterable by the Atlantic flood
  2. To save memory
  3. BFS needs two queues
  4. To keep the output sorted
With one grid, the second flood stops at cells the first flood marked, and the AND of the two sets comes out wrong.

Why not run a DFS from every cell to see if it reaches both oceans?

  1. Each search can re-explore the grid: O((m·n)^2), about 1.6·10^9 steps at 200 x 200
  2. It is wrong on plateaus
  3. It needs a priority queue
  4. It cannot handle the corners
Two border floods visit each cell at most twice: O(m·n).
