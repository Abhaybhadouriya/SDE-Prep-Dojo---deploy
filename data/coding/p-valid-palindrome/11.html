Interview follow-ups

You may delete at most one character. Is it a palindrome now?

Run the same scan. At the first mismatch (l, r), the answer is "is s[l+1..r] a palindrome, or is s[l..r-1]?". Each check is linear, so the total is O(n). LC 680.

How to answer

Explain why only the first mismatch matters: everything outside it already matched, and one of the two characters must go.

Likely follow-ups
  • At most k deletions? (n - LPS(s) ≤ k, an O(n²) DP; LC 1216.)
The input is Unicode (accents, other scripts).

Iterate by code point, use Unicode-aware "is letter or digit" and case folding (Java Character.isLetterOrDigit(int) with codePointAt, Python str.casefold()). For accents, normalise first (NFC/NFD). Byte-level pointers would split multi-byte characters.

How to answer

Name the two issues: multi-byte encoding (pointers must move by whole characters) and case folding beyond ASCII ("ß" folds to "ss").

Likely follow-ups
  • Moving r backwards in UTF-8? Step back over continuation bytes (10xxxxxx).
Do it recursively. Any problem?

It works, but recursion depth is up to n/2 = 10^5, which can overflow the stack in Java/Python (Python's default limit is 1000). The loop is the right answer; mention tail recursion is not guaranteed to be optimised.

How to answer

Show you can write it, then argue for the iterative version with the depth number.

Likely follow-ups
  • Recursion on a linked list? Same depth issue; reverse the second half instead.
The text is a stream: you cannot go back. Can you still decide?

Not exactly in O(1) memory: the first half must be remembered. Options: a stack of the first half if the length is known, or a rolling hash of the filtered text forwards and backwards (h = h*B + c and g = g + c*B^k), which answers "palindrome so far?" in O(1) per character with a tiny false-positive chance.

How to answer

State the memory lower bound first, then offer the hash with its trade-off.

Likely follow-ups
  • Make it exact? Double hashing lowers the risk; exact needs O(n) memory.
