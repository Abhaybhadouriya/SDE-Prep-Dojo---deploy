Approaches: brute -> better -> optimal

Hint 1

For a fixed substring, how many changes does it need to become one letter? (Which letter would you keep?)

Hint 2

If a window needs more than k changes, does any bigger window that contains it need fewer?

1. Brute force - every start, extend to the right

Idea: for each start i, extend j and keep counts and the running max count; the substring i..j is valid when (j - i + 1) - maxCount <= k. Track the longest valid one.

O(n2)time
O(26)space

What is wasted: once i..j is invalid, every longer window from i is invalid too, and the next start re-counts almost the same letters. -> keep one window and move both ends forward.

2. Better - classic shrinking window, O(26·n)

Idea: move right one step at a time; while the window needs more than k changes, move left and decrement its count. Compute the max count by scanning the 26 counters each time.

for right, ch in enumerate(s):
    count[ch] += 1
    while (right - left + 1) - max(count.values()) > k:
        count[s[left]] -= 1; left += 1
    best = max(best, right - left + 1)
O(26 · n)time
O(26)space

Why it works: validity is monotone: shrinking a window never increases the changes it needs (size drops by 1, the max count drops by at most 1). So for each right end the loop finds the smallest valid left, and the longest valid window ending at right is checked. Every index enters and leaves once.

3. Optimal - never shrink, keep a stale max count, O(n)

  • Keep maxFreq = the largest count of one letter seen in any window so far; only raise it, never lower it.
  • For each right: add s[right], update maxFreq. If size - maxFreq > k, move left by exactly one (an if, not a while).
  • The window size never decreases, so at the end the answer is n - left.
O(n)time
O(26)space

Why a stale maxFreq is safe (the key insight from the top-voted answers): the answer is maxFreq + k for the best window, so a window can only be longer than the best so far if some letter's count beats the old maxFreq. While no count beats it, we do not care whether the current window is valid - we just carry the best size along by sliding (add one on the right, drop one on the left). When a count finally exceeds maxFreq, the window really contains that many copies and is valid, so it is allowed to grow. The window may be invalid in the middle of the sweep, but its size is always the length of some valid window seen earlier.
