The problem (in our words)

Build a class LRUCache that stores key-value pairs up to a fixed capacity:

  • LRUCache(int capacity) creates an empty cache that holds at most capacity keys.
  • int get(int key) returns the value of key if it is present, else -1. A successful get counts as a use of that key.
  • void put(int key, int value) sets the value of key, inserting it if it is new. It counts as a use. If the insert makes the number of keys exceed capacity, remove the key that was used least recently.
  • get and put must each run in O(1) average time.

Input format (LeetCode): a list of operation names and a list of argument lists; the output is the list of return values, with null for the constructor and for put.

Constraints:

  • 1 <= capacity <= 3000
  • 0 <= key <= 104
  • 0 <= value <= 105
  • At most 2 * 105 calls in total to get and put.

Practice it: LeetCode 146 · GfG LRU Cache

Constraints tell you: 2·105 calls with capacity 3000 means an O(capacity) scan per call is 6·108 steps: too slow. "O(1) each" is the spec, and O(1) find plus O(1) reorder means map + linked list. Keys are small (<= 104), so a plain array of 104+1 node pointers could replace the hash map; mention it as a constant-factor win.
