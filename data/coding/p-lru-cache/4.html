Approaches: brute → better → optimal

Hint 1

Write down the four things the class must do fast (table above). Which single structure does all four? None, so pick two.

Hint 2

A singly linked list cannot remove a node in O(1) unless you know its predecessor. What does a doubly linked node know?

1. Brute force - a list ordered by use

Idea: keep (key, value) pairs in an array, most recent first. get: scan for the key, move it to the front. put: scan, update or insert at the front, drop the last element when over capacity.

O(capacity)per call
O(capacity)space

What is wasted: the scan to find the key, and the shifting to move it. -> a map fixes the find.

2. Better - hash map + last-used timestamps

Idea: map key -> (value, lastUsed tick). get/put are O(1), but eviction must find the smallest tick: an O(capacity) scan, or a min-heap of (tick, key) with lazy deletion (skip stale entries), O(log n) amortised.

O(1) / O(n)get / evict (scan)
O(log n)with a heap

What is wasted: we keep the whole order only to read its oldest end. A list where the oldest is always at one end, and any node can be moved in O(1), removes the search. -> rung 3.

3. Optimal - hash map + doubly linked list with sentinels

def get(self, key):
    n = self.where.get(key)
    if n is None: return -1
    self._unlink(n); self._push_front(n)      # a read is a use
    return n.val
  1. The map stores the node, not the value. So a lookup lands directly on the list position.
  2. A doubly linked node can unlink itself in O(1). n.prev.next = n.next; n.next.prev = n.prev, no search for the predecessor.
  3. Sentinel HEAD and TAIL remove every edge case. The list is never empty, so insert and unlink never test for null.
  4. The node stores its key. When TAIL.prev is evicted, its key tells us which map entry to delete.
  5. put on an existing key is an update + move, never an eviction. Check the map first; evict only before inserting a new key into a full cache.
O(1)get and put (average, hashing)
O(capacity)space

Why it works: the list is always ordered by last use, because every use moves its node to the front and nothing else reorders it. So the node next to TAIL is, at every moment, the least recently used key, and the map and the list always hold the same set of keys because every insert and every eviction updates both.

4. Built-ins - say them, but be ready to build it

Java LinkedHashMap(cap, 0.75f, true) with removeEldestEntry returning size() > cap; Python OrderedDict with move_to_end and popitem(last=False); C++ std::list + unordered_map<int, list::iterator> with splice. All are O(1). Most interviewers accept them as a first answer and then ask you to implement the list by hand.
