Revision card

  • Cue: O(1) get/put + evict least recently used -> hash map of handles + doubly linked list.
  • Insight: every use moves its node to the front, so TAIL.prev is always the LRU key.
  • State: cap, map key -> node, HEAD/TAIL sentinels, node {key, val, prev, next}.
  • Trap: update existing key = move, not evict; get is a use; node keeps its key.
  • Cost: O(1) per call, O(capacity) space; array scan O(n) per call.
def use(node): unlink(node); push_front(node)
get:  n = map.get(k); if n: use(n); return n.val; return -1
put:  if k in map: map[k].val = v; use(map[k]); return
      if len(map) == cap: old = tail.prev; unlink(old); del map[old.key]
      n = Node(k, v); push_front(n); map[k] = n

Capacity 2, the cache holds keys 1 and 2 (2 used last). You call put(1, 9). What is evicted?

  1. key 2
  2. key 1
  3. nothing
  4. both
Key 1 already exists, so put only updates its value and moves it to the front. The size does not grow, so nothing is evicted. Evicting here is the classic bug.

Why does each list node store its key, not only its value?

  1. to sort the list
  2. so the evicted tail node can be deleted from the hash map
  3. Java needs it for hashCode
  4. it saves memory
On eviction you reach the node through TAIL.prev. To erase it from the map you need its key, and the node is the only place that has it.

Capacity 2: put(8,1), put(4,2), get(8), put(6,3). Which key was evicted?

  1. 8
  2. 4
  3. 6
  4. none
get(8) is a use, so 8 becomes most recent and 4 is the least recent when 6 arrives. get(4) now returns -1.
