Interview follow-ups

Make it thread-safe. What does it cost?

Simplest: one mutex around get and put. A read-write lock does not help, because get also changes the list. To scale: shard the cache by key hash into N independent LRUs, each with its own lock (lock striping); the global order becomes approximate, which is usually fine. Production caches (and the Linux page cache) go further with approximate LRU such as CLOCK or sampled eviction, so a hit only sets a flag instead of relinking under a lock.

How to answer

Name the hot spot (every get writes the list), then offer sharding, then approximation.

Likely follow-ups
  • How does Redis pick a key to evict? (It samples a few keys and evicts the oldest of the sample.)
Add a time-to-live: a key expires t seconds after its put.

Store the expiry time in the node. On get, an expired node is treated as a miss and removed (lazy expiry). To free memory without reads, also keep a min-heap or a timer wheel by expiry and pop expired keys on each call.

How to answer

Separate the two orders: recency (list) and expiry (heap or wheel).

Likely follow-ups
  • Does get refresh the TTL? Ask; both are common.
Capacity is in bytes and values have different sizes.

Track usedBytes. On put, evict from the tail while usedBytes + size > limit. One put can evict several keys; reject a value larger than the whole limit.

How to answer

Change the if to a while and handle the too-big value explicitly.

Likely follow-ups
  • Should a big rarely-used value be evicted before several small ones? (That is size-aware policies like GDSF.)
Why the sentinel nodes, and why does the node store the key?

Sentinels make the list never empty, so insert and unlink have no branches for "first node" or "last node". The key in the node is needed at eviction time: we reach the victim through the list, and must delete its map entry.

How to answer

Show the version without sentinels has four null checks; that is the argument.

Likely follow-ups
  • Memory per entry? (Map entry + node with two pointers, key and value.)
The cache must be shared by many servers.

Partition keys across cache nodes with consistent hashing; each node runs its own LRU. Replicate hot keys if needed. The global LRU order is not kept, only per node, which is what Memcached-style deployments do.

How to answer

Move from the data structure to the system: partitioning, replication, invalidation.

Likely follow-ups
  • What happens to hit rate when a node is added? (Only about 1/N of keys move with consistent hashing.)
