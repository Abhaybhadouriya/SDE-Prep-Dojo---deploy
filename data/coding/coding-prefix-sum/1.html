The prefix array and the one-subtraction query

Define P[0] = 0 and P[i + 1] = P[i] + a[i]. So P has n + 1 entries, and P[i] is the sum of the first i values. Think of the entries as sitting on the boundaries between cells, not on the cells.

The rule to remember:

sum(a[l..r]) = P[r + 1] - P[l]      # both ends included

Building P is one O(n) pass. After that every range sum is O(1). That is the whole of Range Sum Query - Immutable. The extra zero at the front is the trick that removes every special case: a range that starts at index 0 is just P[r + 1] - P[0].

Use the n + 1 version, always. The "P[i] includes a[i]" version forces you to write l == 0 ? P[r] : P[r] - P[l - 1], and that l - 1 is where off-by-one bugs live.

The same idea gives the easy warm-ups: Find Pivot Index (left sum = P[i], right sum = total - P[i + 1]) and Product of Array Except Self, where you keep a running product from the left and another from the right, because division is not allowed.

From your world

You already think in prefix sums. The counters in /proc/net/dev, /proc/stat or an ethtool -S dump are cumulative: rx_bytes since the interface came up. Nobody stores "bytes in each second". A tool like sar or a Prometheus rate() reads the counter twice and subtracts. That is P[r + 1] - P[l]. And just as a 32-bit counter can wrap, a prefix sum of 105 values up to 109 overflows a 32-bit int: use 64-bit.
