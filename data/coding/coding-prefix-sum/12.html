Interview questions

Count subarrays with sum k. The array can have negative numbers. Why does the hash-map solution work?

Let P be the prefix totals with P[0] = 0. A subarray i..j sums to k exactly when P[j + 1] - P[i] = k, so P[i] = P[j + 1] - k. Walking left to right, every earlier prefix equal to run - k is a different start for a good subarray ending at j, so adding count[run - k] counts each good subarray exactly once (at its end). Seed with {0: 1} for starts at index 0; look up before inserting so k = 0 does not match the empty subarray. O(n) time, O(n) space.

How to answer

Say the brute force (O(n²)) first, then explain why a sliding window fails (negatives break monotonicity), then derive P[i] = P[j + 1] - k. Run a 4-element example with a negative number out loud.

Likely follow-ups
  • Return the longest such subarray. (Store the first index per prefix, not a count.)
  • All values are positive and memory is tight. (Sliding window, O(1) space.)
  • Count subarrays with sum in a range [lo, hi]. (That is Count of Range Sum: sorted prefixes with merge sort or a Fenwick tree, O(n log n).)
Longest subarray with equal numbers of 0s and 1s.

Map 0 to -1 and keep the running balance. A block has equal counts exactly when the balance at its two ends is the same. Store the first index at which each balance appeared (seed balance 0 at index -1); at each i, if the balance was seen before at j, the block j + 1..i is balanced. Keep the max of i - j. O(n) time; the balance is between -n and n, so an array of size 2n + 1 can replace the map.

How to answer

Draw the up/down walk; "same height twice" makes the idea obvious to the interviewer.

Likely follow-ups
  • Three symbols a, b, c with equal counts. (Key = the pair (count_a - count_b, count_b - count_c).)
  • Count such subarrays instead of the longest. (Store counts.)
Continuous Subarray Sum: why store the first index per remainder, and what about k = 0 or negatives?

Equal remainders mean the block between them sums to a multiple of k. The block must have length at least 2, so we need two equal remainders at least 2 apart; keeping the earliest index maximises the distance, so if any valid pair exists we see it. In the current LeetCode version k >= 1 and values are non-negative, so plain % works; if negatives were allowed, normalise with ((x % k) + k) % k. If k = 0 were allowed, "multiple of 0" means "sum is 0", so you would key by the raw prefix sum instead.

How to answer

Mention the trap [5, 0, 0, 0], k = 3 (true, from [0, 0]) to show why you never overwrite.

Likely follow-ups
  • Count all such subarrays of any length. (Subarray Sums Divisible by K: counts per remainder.)
Path Sum III in O(n). What changes compared with the array version?

Every downward path lies on a root-to-node line, so do the array algorithm on the current DFS path: run = root-to-node total, look up run - target, then insert run, recurse into both children, and decrement run on the way back. The decrement is what keeps sibling subtrees separate: the map always holds exactly the prefixes of the ancestors of the current node. O(n) time, O(h) extra space.

How to answer

Start from the O(n²) "DFS from every node", then say "a path is a subarray of a root-to-leaf line" and reuse 560.

Likely follow-ups
  • The tree is very deep (a linked list of 105 nodes). (Iterative DFS with an explicit stack and an exit marker to undo, or raise the stack limit.)
  • Paths may go up and down (any two nodes). (A different problem: DFS returning best downward sums, as in Binary Tree Maximum Path Sum.)
Car Pooling: compare the difference array with sorting events and with a heap.

Difference array: +people at from, -people at to, one prefix sweep over the stops; O(n + S) with S = number of stops (1,001 here). Event sort: make 2n events (time, delta), sort with drops before pickups at equal time, sweep; O(n log n), works for huge coordinates. Heap: sort trips by start, keep a min-heap of (end, people) to drop finished trips; O(n log n). With small bounded coordinates the array is simplest and fastest; with coordinates up to 109, use events or an ordered map.

How to answer

Ask the coordinate range first. That one question picks the method and shows you think about constraints.

Likely follow-ups
  • Return the first stop where it overflows. (The sweep already knows it.)
  • Trips arrive online and you must answer after each one. (Fenwick tree with range add, or an ordered map: see range queries.)
Many range-sum queries on an array. What if the array also gets point updates?

Static array: prefix sums, O(n) build and O(1) per query. With updates, one change shifts every later prefix, so an update costs O(n). The balanced answer is a Fenwick tree (binary indexed tree) or a segment tree: O(log n) for both update and query. If updates are rare and queries frequent, rebuilding is fine; if both are frequent, use the tree. A square-root split (blocks of size about √n) is a middle option at O(√n) each.

How to answer

Give the trade-off table: build, update, query for each structure. Then pick by the ratio of updates to queries.

Likely follow-ups
  • Range updates and range queries. (Segment tree with lazy propagation, or two Fenwick trees.)
Count submatrices whose sum equals a target.

Fix a top row and a bottom row (O(R²) pairs). For each pair, the sums of each column between them form a 1D array of length C (update it incrementally as the bottom row moves down). Count subarrays of that array with sum = target using the prefix-map loop: O(C). Total O(R² × C) time, O(C) space. Put the smaller dimension in the squared term.

How to answer

Say "reduce 2D to 1D by fixing two rows", then reuse Subarray Sum Equals K by name.

Likely follow-ups
  • Max sum rectangle no larger than k. (Same reduction, then a sorted set of prefixes and a ceiling lookup per column: O(R² C log C).)
Count subarrays whose XOR equals k.

Same loop as sum = k, with XOR: run ^= x; the XOR of a block is X[j] ^ X[i], and X[j] ^ X[i] = k means X[i] = run ^ k. Add count[run ^ k], then count[run]++. Seed {0: 1}. O(n). This works because XOR is associative and every value is its own inverse, which is all the prefix trick needs.

How to answer

State the general rule: the prefix trick works for any operation you can undo (sum with minus, XOR with XOR, product with division when there are no zeros). Max and min cannot be undone, which is why range max needs a sparse table or segment tree.

Likely follow-ups
  • Maximum XOR of any subarray. (Insert prefix XORs into a binary trie and greedily search for the opposite bits.)
