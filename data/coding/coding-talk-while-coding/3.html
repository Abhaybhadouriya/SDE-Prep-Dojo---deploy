Clarifying questions that change the code

A good question has an answer that changes what you write. "What language should I use?" rarely does; "can the array be empty?" always does. Think in four buckets:

Input typeQuestions worth asking
Array of numbersSorted? Duplicates? Negatives or zero? Can I modify it? Is the sum within 32 bits?
StringCharacter set (lowercase only, ASCII, Unicode)? Case-sensitive? Spaces and punctuation?
Linked list / treeCan it be empty? Values unique? Is it a BST? Do nodes have parent pointers? Can I rewire it?
GraphDirected? Weighted (negative weights)? Connected? Cycles? Self-loops? How is it given (edges, matrix, adjacency)?
Intervals / timesClosed or half-open? Do touching ends overlap? Sorted by start?
Design (LRU, iterator)Call frequency of each operation? Capacity limits? Thread safety needed?

Then let n choose the algorithm and say it: "n is 104, so O(n2) is 108 simple steps, borderline; I will aim for O(n log n)." The constraints table on the start page gives the usual cut-offs.
