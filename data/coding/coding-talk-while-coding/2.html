A script for the first five minutes

The first five minutes after the introductions decide whether you build the right thing. Here is the script, played on a real question. The problem is LeetCode 56, restated in our words:

Problem (our words). A meeting room log is a list of bookings [start, end] with start <= end. Merge every group of overlapping bookings into one booking and return the resulting list of non-overlapping bookings, covering exactly the same times. Bookings that only touch ([1,4] and [4,5]) count as overlapping. Constraints: 1 <= n <= 104; 0 <= start <= end <= 104. Example: [[1,3],[2,6],[8,10],[15,18]] gives [[1,6],[8,10],[15,18]]. Original: LeetCode 56 - Merge Intervals; our write-up: Merge Intervals.

  1. Restate (about 30 seconds). Say the task back in your own words and end with a question. It catches misreadings early and shows you listened. Type it as the first comment in the editor.
  2. Clarify (about 1-2 minutes). Ask only questions whose answer changes your code: boundary rules (touching), input order, empty input, output order, mutation, and the size of n (which tells you the target complexity). Write each answer down as a comment.
  3. Examples (about 1 minute). Write two or three small inputs with expected outputs, including one nasty one. These become your test cases later, so you never have to invent tests under pressure.
  4. Brute force (about 30 seconds). Say the obvious correct method and its cost, even if you will not code it. It proves you understand the problem and gives the interviewer a baseline.
  5. Plan and agreement (about 1 minute). Name the waste in the brute force, the idea that removes it and the new cost, then ask "shall I code that?". Only start typing after a yes.

Ask, then propose. When the interviewer answers a question with "what do you think?", give a sensible default and move on: "Then I will assume touching bookings merge, since they leave no free gap; easy to change." Assumptions said out loud cost nothing; silent assumptions cost the round.
