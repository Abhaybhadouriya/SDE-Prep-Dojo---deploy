Brute force first, then optimise out loud

Say the brute force in one or two sentences with its cost, even if it is obviously slow. Then use a three-part sentence to move to the better idea: "The brute force is slow because ___ ; I can avoid that by ___ ; that makes it ___ ."

  • Two Sum: "For each number I scan the rest for its partner, O(n2). The repeated work is the scan; a hash map of seen values answers 'have I seen target - x?' in O(1), so O(n) time and O(n) space."
  • Merge intervals: "I compare every pair because I do not know which bookings are close. Sorting by start puts overlapping ones next to each other, so a single sweep works: O(n log n)."
  • Sliding-window problems: "I recompute each window from scratch; when the window moves by one, only two elements change, so I update a running count instead."

The useful questions to ask yourself out loud: What is computed more than once? (cache it: a map, prefix sums, DP). What order would make this easy? (sort, or a heap). What do I need to query fast? (pick the data structure that answers that query). Can I stop early? (two pointers, binary search on a monotone condition).

Interviewers love this. Naming the bottleneck ("the inner scan") before naming the fix shows the reasoning, not a memorised answer. If you jump straight to "use a heap", the interviewer cannot tell whether you understood the problem or recognised the title.
