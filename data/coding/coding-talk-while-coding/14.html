Common mistakes

  1. Coding in the first minute. The interviewer has not agreed on anything yet; you may build the wrong thing quickly.
  2. Long silences. Over a minute without a word reads as stuck. If you need quiet, ask for it and give a time.
  3. Narrating keystrokes. "Now an if, now an else." Say why; they can see what.
  4. Asking questions with no effect on the code while skipping the ones that matter (empty input, size of n).
  5. Hiding the brute force because it feels "too easy". It is the baseline that makes your optimisation meaningful.
  6. Arguing with a hint instead of testing it on an example.
  7. Saying "done" without testing. Always trace one example and one edge case before you say it works.
  8. Complexity without a source. "O(n log n)" alone; say "from the sort" and what the space is.
  9. Apologising repeatedly. One "good catch, fixing it" is enough. Calm fixes are a strong signal.
