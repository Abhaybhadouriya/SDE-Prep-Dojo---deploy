Interview questions about the round itself

How much should I talk? Is silence while I think always bad?

Talk at decision points: the plan, each block's purpose, invariants, bugs and tests. Short quiet stretches are fine if you announce them ("let me think for thirty seconds") and then summarise what you concluded. What hurts is unannounced silence of minutes, because the interviewer has nothing to write and cannot help.

How to answer

In practice: record a mock and count silences longer than 30 seconds. Replace each one with a sentence that starts with "I am checking whether...".

Likely follow-ups
  • What if I think better in silence? (Think in short, announced bursts; summarise after each.)
The problem looks familiar; I know the optimal solution. Should I still say the brute force?

Yes, briefly: one sentence and its cost. Then derive the optimal idea from the brute force's waste instead of announcing it. Interviewers are grading reasoning; a derived solution shows it, a recalled one does not. If you have seen the exact problem, being open about it is the safe choice; the interviewer may switch problems or go straight to a follow-up.

How to answer

"The obvious approach is O(n2) because ___. The repeated work is ___, so ___ brings it to O(n)." Twenty seconds, then code.

Likely follow-ups
  • Prove the optimal one is correct (state the invariant).
  • Can it be done in less space?
Which clarifying questions are worth the time in a 20-minute Meta-style slot?

With two problems in 45 minutes there is time for two or three questions per problem, so ask only the ones whose answers change the code: input size (picks the complexity), empty or invalid input (picks the guard), boundary rules (touching, duplicates, negatives) and output format or order. Propose defaults for the rest out loud.

How to answer

Show the habit: "n up to 105, so O(n log n) or better; I will assume no empty input since the constraints say n >= 1; duplicates may appear. OK?" One sentence, three answers.

Likely follow-ups
  • What if they say "you decide"? (State a default and why, and keep the code easy to change.)
I found a bug in my own code halfway through. What do I say?

Say it as soon as you see it, explain it in one sentence, and fix it without drama: "This breaks for touching intervals because I used < instead of <=; fixing it." Finding and fixing your own bug is positive evidence for the verification part of the rubric. Do not rewrite everything; change the smallest thing and re-trace the failing example.

How to answer

Name the input that fails, the line, and the fix. Then re-run that one example out loud.

Likely follow-ups
  • How would you have caught it earlier? (The nasty example written in minute three.)
The interviewer gave me a hint I do not understand. What now?

Repeat it back and connect it to what you have: "You are suggesting the sorted order matters; so if I sort by start, then... overlapping ones are adjacent?" If it still does not click, ask a narrow question about it ("do you mean sort the input, or keep a sorted structure?"). Taking a hint quickly and using it is itself a signal; pretending to understand wastes minutes.

How to answer

Repeat, connect, act. If you disagree, test the hint on an example rather than arguing.

Likely follow-ups
  • Does a hint mean I failed? (No; how you use it is what gets graded.)
Ten minutes left and my optimal solution is not working. What is the best use of the time?

Say what you are doing and switch to safety: either fix the specific failing case if you know it, or code the brute force cleanly (often 5 minutes), test it, and describe the optimal version and where it breaks in words. A correct solution plus a clear explanation of the better one usually scores better than broken clever code. Leave the last minute for complexity and "with more time I would...".

How to answer

"I have 10 minutes. I will make the O(n2) version correct first, then explain the fix to the fast one." The interviewer will often redirect you if they prefer something else.

Likely follow-ups
  • Describe exactly which case the fast version fails.
As a senior candidate, what should my narration add beyond a correct solution?

Trade-offs and context, in single sentences: why this approach over the alternative (time against memory, simplicity against speed), how the code would be tested for real (a brute-force oracle and random inputs), and what changes at scale or under concurrency. Also drive the session: propose the plan, set checkpoints, finish early and raise the follow-up yourself.

How to answer

Add one "in production I would..." sentence per phase, no more. The coding is still the main thing being graded.

Likely follow-ups
  • Make it work on a stream or on data that does not fit in memory.
  • Make it thread-safe.
How do I state complexity so it sounds complete?

Give the dominant term with its source, then space split into output and extra: "O(n log n) time from the sort, the sweep is linear; O(n) for the output and O(log n) extra for the sort's recursion in C++." Mention "expected" for hash maps and "amortised" where it applies, and the recursion stack for DFS.

How to answer

Say it unprompted at the end of coding, before testing, so the interviewer can mark it.

Likely follow-ups
  • Can you reduce the space? (Often: sort in place, or reuse the input.)
  • What is the worst case of the hash map? (O(n) per operation under collisions.)
