Interview follow-ups

Now give an O(n log n) solution.

Prefix sums are strictly increasing because every value is positive. For each start l, binary search the first j with pre[j] ≥ pre[l] + target; the length is j - l. Alternative: binary search the answer length L; "some window of length L reaches the target" is monotonic in L and checked with a fixed window in O(n).

How to answer

State why the prefix array is sorted before you use binary search on it; that is the point being tested.

Likely follow-ups
  • Which is better in practice? The O(n) window: fewer passes and O(1) space.
The array can contain negative numbers. What changes?

The window breaks: dropping a negative raises the sum. Use prefix sums and a deque of indices with increasing prefix values. For each r: while pre[r] - pre[deque.front] ≥ k, record r - front and pop the front (no later r can do better with that start); while pre[deque.back] ≥ pre[r], pop the back (r is a later and lower start, so it dominates). O(n). This is LC 862.

How to answer

Name the property that fails (monotonic window sum), then show the two pop rules and why each popped index is useless.

Likely follow-ups
  • Why can we pop the front for good? Any later r gives a longer window from that start.
Return the subarray itself (start and end), not just its length.

Store left and right whenever best improves inside the shrink loop. Ties: the first window found is the leftmost shortest one, because the scan moves left to right and we only update on a strict improvement.

How to answer

Mention how ties are resolved before the interviewer asks.

Likely follow-ups
  • Return all shortest windows: collect on equality too.
Values arrive as a stream; after each value report the shortest window so far.

The window is already online: each new value is one "grow" plus some "shrinks", and best only goes down. You need to keep only the values inside the current window (a queue) to know what to drop, so memory is the window length, not the whole stream.

How to answer

Point out nothing looks ahead; the state is left, sum and the queue of window values.

Likely follow-ups
  • Bound the memory: if best is already b, the window never needs more than b values.
Can the sum overflow? What type would you use?

The largest sum is 105 x 104 = 109 < 231 - 1, so int32 is enough here. In the binary search version, pre[l] + target can reach 2·109, just under the int32 limit of about 2.147·109: it fits, with almost no headroom, so a 64-bit prefix array is cheap insurance.

How to answer

Do the bound arithmetic out loud and point at the one expression that can overflow.

Likely follow-ups
  • What if values can be 0? The window still works (shrink while sum ≥ target); prefix sums become non-decreasing, lower_bound still works.
Find the longest subarray with sum at most target instead.

Flip the loop: grow right, shrink while the sum is greater than target (invalid), and record right - left + 1 after the shrink loop. Same O(n), same proof (validity is monotonic). This is Codeforces 279B "Books".

How to answer

Show the one-line rule: shortest valid = shrink while valid; longest valid = shrink while invalid.

Likely follow-ups
  • Count those subarrays: add right - left + 1 per step (LC 713 style).
