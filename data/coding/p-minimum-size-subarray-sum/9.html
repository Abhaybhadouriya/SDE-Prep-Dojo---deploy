  • Cue: shortest subarray with sum ≥ target, all values positive -> variable window.
  • Insight: positive values make the window sum monotonic, so both pointers only move forward.
  • State: left, running sum, best = n + 1.
  • Trap: while not if; record inside the loop; return 0 when best = n + 1.
  • Cost: O(n) time, O(1) space; follow-up O(n log n) = binary search on the sorted prefix sums.
left = s = 0; best = n + 1
for right, x in enumerate(nums):
    s += x
    while s >= target:              # valid: record, then shrink
        best = min(best, right - left + 1)
        s -= nums[left]; left += 1
return 0 if best == n + 1 else best

Quick quiz

Why is the nested while loop still O(n) overall?

  1. The inner loop runs at most once per step
  2. The array is short
  3. left only moves forward, so it moves at most n times in total
  4. Binary search inside
Amortised: the inner loop's total work across the whole run is bounded by n left-moves.

The values can now be negative. What breaks?

  1. Nothing
  2. Dropping an element can raise the sum, so a window that stops shrinking may hide a shorter valid one
  3. Only the sentinel
  4. The prefix sums overflow
The window relies on "shorter means smaller sum". With negatives use prefix sums + a monotonic deque (LC 862).

In the O(n log n) version, why may you binary search the prefix array?

  1. Positive values make it strictly increasing, so it is sorted
  2. Because we sort it first
  3. Binary search works on any array
  4. Because the target is positive
pre[i+1] = pre[i] + nums[i] > pre[i]; no sorting needed and the indices stay correct.
