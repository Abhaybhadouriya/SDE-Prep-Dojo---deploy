Approaches: brute → better → optimal

Hint 1

Draw the values as a graph: what shape does a rotated sorted array have?

Hint 2

If you know one value of the array that is surely in the low run, can you tell for any index which run it is in?

Hint 3

The last element is always in the low run (or the array is sorted and everything is "low").

1. Brute force - scan for the smallest

Idea: walk the array and keep the smallest value seen. It ignores the sorted structure completely.

return min(nums)   # O(n)
O(n)time
O(1)space

What is wasted: we look at values that the order already tells us cannot be the minimum.

2. Better - find the drop

Idea: in a rotated sorted array there is at most one index where nums[i] < nums[i - 1]. That index holds the minimum; if no drop exists, the array is sorted and the answer is nums[0].

O(n)time (worst case)
O(1)space

What is wasted: the scan still walks up to n cells, yet it already uses the key fact: the array is two sorted runs. A test that says which run an index belongs to lets us halve instead of walk.

3. Optimal - binary search against the last value

lo, hi = 0, len(nums) - 1          # core: 6 lines
while lo < hi:
    mid = (lo + hi) // 2
    if nums[mid] > nums[hi]: lo = mid + 1   # mid in the high run
    else: hi = mid                          # mid..hi sorted; keep mid
return nums[lo]
  1. The array is two sorted runs, high then low. Every value of the left run is bigger than every value of the right run (or the left run is empty when it is fully sorted).
  2. Keep the minimum inside [lo, hi]. Start with the whole array.
  3. nums[mid] > nums[hi] means mid is in the high run. The values drop somewhere between mid and hi, so the minimum is strictly right of mid: lo = mid + 1.
  4. nums[mid] < nums[hi] means mid..hi is one sorted piece. Its smallest value is nums[mid], so the minimum is mid or to its left: hi = mid (not mid - 1).
  5. Stop when lo == hi. One candidate is left, and it was never discarded: return it.
O(log n)time (about 13 steps for n = 5000)
O(1)space

Why compare with the last value and not the first? Comparing with nums[lo] is ambiguous: nums[mid] > nums[lo] holds both for a sorted array (minimum on the left, at lo) and for a rotated one like [4, 5, 6, 1, 2] (minimum on the right). Comparing with nums[hi] never is: if nums[mid] > nums[hi], the piece mid..hi is not sorted, so the drop is inside it; otherwise it is sorted and its minimum is nums[mid]. The fully sorted case needs no special code.

Proof (optional) - the loop is correct and always ends

Invariant: the index of the minimum, m, lies in [lo, hi]. Since lo < hi and mid rounds down, lo ≤ mid < hi, so nums[mid] and nums[hi] are different values (they are unique). Case nums[mid] > nums[hi]: if m were ≤ mid, then mid and hi would both be in the low run, which is increasing, so nums[mid] < nums[hi], a contradiction; so m > mid and lo = mid + 1 keeps m. Case nums[mid] < nums[hi]: if m were in (mid, hi], then the drop would be in (mid, hi], placing mid in the high run and hi in the low run, so nums[mid] > nums[hi], a contradiction; so m ≤ mid and hi = mid keeps m. Each step shrinks hi - lo (hi = mid < hi, or lo = mid + 1 > lo), so the loop ends with lo = hi = m.

Stuck? Why not while (lo <= hi)?

With hi = mid, the condition lo <= hi keeps looping when lo == hi: mid == hi, nothing changes, and the loop spins forever. The "keep mid" update goes with while lo < hi. If you prefer lo <= hi, track a running best = min(best, nums[mid]) and use hi = mid - 1.
