Revision card

  • Cue: sorted then rotated + O(log n) → binary search on "which run is mid in?".
  • Insight: compare nums[mid] with nums[hi]: bigger means the drop is right of mid.
  • State: lo, hi (the minimum is always in [lo, hi]), mid rounding down.
  • Trap: hi = mid, not mid - 1; loop while lo < hi; never compare with nums[lo].
  • Cost: O(log n) time, O(1) space; brute O(n); duplicates (LC 154) O(n) worst.
lo, hi = 0, n - 1          # first index where pred(i) is True
while lo < hi:
    mid = (lo + hi) // 2
    if pred(mid): hi = mid  # pred: nums[mid] <= nums[hi]
    else: lo = mid + 1
return lo

Quick quiz

lo = 3, hi = 8, nums[mid] < nums[hi]. What is the update?

  1. lo = mid + 1
  2. hi = mid
  3. hi = mid - 1
  4. return nums[mid]
mid..hi is sorted, so its minimum is nums[mid]; keep mid in the range.

Why is the comparison with nums[lo] unsafe?

  1. It overflows
  2. It is slower
  3. nums[mid] > nums[lo] holds both for sorted and rotated arrays
  4. nums[lo] can be negative
The same outcome points left in one case and right in the other; the last value has no such ambiguity.

What breaks if values may repeat?

  1. nums[mid] == nums[hi] gives no information
  2. Nothing
  3. The loop overflows
  4. The answer may not exist
Equal values cannot tell the runs apart; LC 154 shrinks hi by one in that case.
