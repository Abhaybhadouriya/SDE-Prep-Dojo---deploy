Interview follow-ups

Return how many times the array was rotated.

The rotation count is the index of the minimum (modulo n): an array rotated r times (r < n) has its minimum at index r, and r = n gives index 0. Return lo instead of nums[lo].

How to answer

Reuse the same loop; only the return value changes. This is the GfG "rotation count" problem.

Likely follow-ups
  • Find the maximum: it is at index (lo - 1 + n) % n.
What if values can repeat?

When nums[mid] == nums[hi] you cannot tell which run mid is in ([1, 3, 3, 3] vs [3, 3, 1, 3]). It is safe to drop hi (do hi -= 1), because nums[mid] has the same value and stays in the range. The worst case (all equal but one) becomes O(n), and no algorithm can do better in that case.

How to answer

Give the failing example first, then the one-line fix and its worst case. That is LC 154.

Likely follow-ups
  • Why is O(n) a lower bound? An adversary can hide the single smaller value anywhere among equal ones.
Now search for a target value in the same array.

Option 1: find the minimum index r with this code, then binary search the sorted piece that can contain the target ([0, r - 1] or [r, n - 1]). Option 2 (one pass): at each mid, one half is sorted; check if the target lies inside that half's range and go there, else go to the other half. Both are O(log n).

How to answer

Option 1 is easier to get right under pressure because it reuses two simple searches.

Likely follow-ups
  • Do it with duplicates (LC 81).
Can you solve it by comparing with nums[0] instead?

Yes, with a guard: if nums[0] < nums[n - 1] the array is sorted, return nums[0]. Otherwise the predicate "nums[i] < nums[0]" is false on the high run and true on the low run, and you search its first true. It works, but it needs the special case, which is why the nums[hi] form is the usual answer.

How to answer

Show you know the reference element must be one whose run is certain.

Likely follow-ups
  • Which version handles n = 1 without special code? Both, if written carefully.
The data is a ring buffer you can only read through a get(i) call that costs a disk seek.

The same algorithm makes about log2(n) + 1 reads, and you can cache nums[hi] between steps because hi only changes to mid (whose value you just read). For a huge buffer on disk, reading one block per probe and searching inside the block at the end cuts the seeks further.

How to answer

Count the reads, not the comparisons, and say which values you can reuse.

Likely follow-ups
  • What if the buffer is being written while you search? Take a snapshot of the head pointer first.
