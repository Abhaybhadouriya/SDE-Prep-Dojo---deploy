Interview questions

Implement a trie with insert, search and startsWith. What are the costs?

Node = 26 child pointers + an end flag. All three operations walk one node per character, creating missing children only in insert. Search requires the final node's end flag; startsWith only requires the node to exist. O(L) time per operation, O(total characters) nodes overall, each node 26 pointers in the array design.

How to answer

Ask about the alphabet first (lowercase only?), pick array vs map from the answer, write one private walk helper and build search and startsWith on it.

Likely follow-ups
  • Delete a word? (Walk down, clear end; on the way back up remove nodes that have no children and no end flag.)
  • Count words with a prefix? (Keep a pass counter per node, incremented on insert.)
Add and search words where '.' matches any letter. What is the worst case?

Normal letters follow one edge; a dot recurses into every existing child at that depth and returns true on the first branch that ends on an end node. The worst case is O(26d · L) for d dots, bounded by the trie size; with LC's limit of at most two dots it is fast. Bucketing words by length is a cheap extra filter.

How to answer

Code the recursive matcher with an index into the query; state the worst case honestly and mention the constraint that makes it acceptable.

Likely follow-ups
  • What if '*' matches any sequence? (Branch on "skip the star" or "consume one letter and stay on the star", like regex matching; memoise on (node, index).)
  • Could a hash set do it? (Only by generating all 26d substitutions per query, which is fine for d = 1 and bad beyond.)
Word Search II: why a trie, and how do you keep it from timing out?

Running a grid DFS per word repeats almost the same work k times. With all words in one trie, a single DFS from each cell carries a trie pointer and stops the moment the path is not a prefix of any word. Store each word at its end node, clear it when found (no duplicates), mark visited cells in place and restore them, and delete trie nodes that become empty so later searches stop earlier.

How to answer

Start from Word Search I, explain the repeated work, then introduce the trie. Name the three optimisations (end-node word, in-place marking, pruning empty nodes) before coding.

Likely follow-ups
  • Time complexity? (O(m·n·4·3L-1) worst case for max length L, plus O(total letters) to build; pruning cuts it a lot in practice.)
  • Words can reuse cells? (Then it is a graph walk with memoisation on (cell, trie node), no visited marking.)
Search Suggestions System: trie or binary search?

Both pass. Sorting the products and binary searching each prefix's lower bound, then scanning at most three entries, is O(n log n + L log n) with no extra structure, and is very hard to get wrong. A trie that keeps up to three sorted suggestions at each node answers each keystroke in O(1) after the step, which is better when the product list is fixed and queries are many.

How to answer

Give both, pick one based on what they stress (simplicity vs many queries), and note that the binary-search bound can only move right as the prefix grows.

Likely follow-ups
  • Rank by popularity instead of alphabet? (Store counts; keep a top-k per node and refresh it along the path on each update.)
  • Millions of products across machines? (Precompute top-k per prefix offline and shard by prefix: the HLD typeahead design.)
Maximum XOR of two numbers: why is the greedy walk on a bit trie correct?

XOR value is decided by the highest differing bit: 2k is larger than the sum of all lower bits (2k - 1). So for a fixed x, taking the opposite bit at the highest possible position can never be beaten by any choice that gives up that bit. The trie tells you in O(1) per bit whether some inserted number has the opposite bit, given the bits chosen so far. O(31·n) time and nodes.

How to answer

State the "high bit dominates" argument in one sentence, draw a 3-bit trie, then code insert and query as two 31-step loops.

Likely follow-ups
  • Each query may only use values <= m? (Sort queries by m and insert values offline, or store the subtree minimum at each node.)
  • Maximum XOR of a subarray? (Insert prefix XORs; the answer for each prefix is its best XOR with an earlier prefix.)
Design an autocomplete system that returns the top 3 hottest sentences for the typed prefix.

Trie over characters; each end node stores the sentence's count. For fast reads, each node also stores its current top 3 (by count desc, then alphabetical). On "#", increment the sentence's count and refresh the top-3 list of every node on its path, O(L · k log k). Keep the current node between keystrokes so each new character is a single step, and a "dead" flag once the prefix falls off the trie.

How to answer

Clarify the ranking and the reset rule, present the read-optimised trie, and contrast it with "DFS the subtree per keystroke". Mention memory: top-3 per node is three references, not copies.

Likely follow-ups
  • Too much memory for all prefixes? (Store top-k only up to a depth limit; below it, DFS on demand.)
  • Counts change constantly at scale? (Batch updates and rebuild the per-prefix top-k periodically, as typeahead services do.)
When would you use a hash set instead of a trie?

When you only need exact-membership checks. A hash set lookup is O(L) to hash the word plus O(1) average, uses less memory, and has no pointer chasing. A trie wins when you need prefix queries, sorted iteration, wildcard matching, or to test many words against one walk (grids, streams), or when shared prefixes make it smaller than the set.

How to answer

Name the operations each structure is good at, then map them to the problem's operations. Interviewers want to hear that you did not pick a trie just because the input is strings.

Likely follow-ups
  • Memory of a trie for 105 words of length 10? (Up to 106 nodes; at 26 pointers each that is about 200 MB worst case, so use a map, a node pool with int indices, or a compressed radix tree.)
  • What is a radix tree? (A trie where chains of single-child nodes are merged into one edge labelled with a string.)
