Autocomplete: suggestions per prefix

Search Suggestions System (LC 1268): given a product list and a search word, after each typed character return up to three products, in lexicographic order, that start with the prefix typed so far. Two clean solutions:

  1. Sort + binary search. Sort the products. For each prefix, binary search the first product >= prefix and check the next three for the prefix. O(n log n + L log n), tiny memory. Often the best answer for this exact problem.
  2. Trie with a top-3 list at each node. Insert products in sorted order; while walking down, append the product to each node's list if it has fewer than three. A query is then one walk, reading the list at each node. O(total letters) to build, O(L) to answer.

Design Search Autocomplete System (LC 642, Premium; MongoDB, Pinterest, Amazon and Google in the data) adds hotness: each sentence has a count, # ends a query and adds one to that sentence's count, and the system returns the top 3 by count, ties broken alphabetically. The design choice to discuss:

ApproachQuery costUpdate costWhen
Count only at end nodes; DFS the subtree on each keystroke, pick top 3 with a heapO(size of subtree)O(L)Few queries, many updates
Keep a top-k list at every node, refresh it along the path on updateO(1) per keystroke after the stepO(L · k log k)Read-heavy (real autocomplete), the usual interview answer

Keep a pointer to the current trie node between keystrokes, so each new character is a single step rather than a fresh walk from the root, and remember "dead" (the prefix fell off the trie) so later characters return empty at once until # resets everything. This links straight to the HLD typeahead design: at web scale the same top-k-per-prefix idea is precomputed offline and sharded.
