Node design: array of 26 or a hash map?

Array next[26]Hash map children
Step costOne index, O(1), cache friendlyHash + probe, O(1) average, slower constant
Memory per nodeFixed 26 pointers (208 bytes on 64-bit)Proportional to real children (plus map overhead)
AlphabetMust be small and known (a-z, 0/1 bits, digits)Any characters, Unicode, whole tokens (path segments)
Sorted iterationFree: loop i = 0..25Needs a sorted map (TreeMap) or a sort
Use in interviewsDefault for "lowercase English letters"Python (dict is idiomatic), file paths, mixed alphabets

Read the constraints: "words consist of lowercase English letters" means the array. "Paths like /a/b/c" or "any printable character" means a map keyed by segment or character. In C++ or Java a third option is a node pool: all nodes in one vector, children stored as integer indices, index 0 meaning "none". It avoids thousands of small allocations, and the bit-trie code below uses it.

From your world

This is the same density trade-off as a direct-mapped table versus a hash table in a driver. The kernel's radix tree / XArray chose fixed-size nodes (64 slots by default) and saves memory differently: it only creates nodes along paths that have entries, and collapses a tree that holds a single entry at index 0 into the root. The node pool is a slab: one allocation, objects addressed by index.
