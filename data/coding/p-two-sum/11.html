Interview follow-ups

What if the array is sorted?

Two pointers: lo = 0, hi = n - 1. If the sum is below target, lo++; above, hi--. O(n) time and O(1) space. Each move discards a value that cannot be in any pair with the remaining range.

How to answer

Give the discard argument in one sentence: "if a[lo] + a[hi] < t, a[lo] is too small even with the largest partner".

Likely follow-ups
  • 3Sum (LC 15): fix one element, then this.
Return all pairs (or count them), with duplicates.

Keep count[value]. For each x, add count[target - x] to the answer, then increment count[x]. For unique value-pairs, iterate the distinct keys and handle x == target - x with c*(c-1)/2.

How to answer

Ask: "pairs of indices or pairs of values?". The two answers differ.

Likely follow-ups
  • Use each element at most once (LC 1679).
Memory is tight: you cannot afford a hash map.

Sort (value, index) pairs and use two pointers: O(n log n) time. If even that copy is too much and indices are not needed, sort in place: O(1) extra space (heap sort) or O(log n) (introsort).

How to answer

State the trade-off plainly: time for space.

Likely follow-ups
  • Values are small (0..10^6)? A bitmap or counting array instead of a hash map.
Numbers arrive as a stream; answer "is there a pair summing to t?" at any time.

Keep the set of values seen. On each arrival x, check t - x in O(1), then insert x. For a query with a different t each time (LC 170), you either scan the set on find (O(n)) or precompute all pair sums on add (O(n) per add, O(n²) memory): pick based on the add/find ratio.

How to answer

Ask about the read/write ratio before choosing.

Likely follow-ups
  • Sliding time window of the last k values? Remove expired values from a count map.
The array is too big for one machine.

Partition by value: send x to shard h(x) and also send a "query" for t - x to shard h(t - x). Each shard joins values with queries locally. This is a hash join, the same idea at cluster scale.

How to answer

Name it a hash join; mention the skew problem when one value is very frequent.

Likely follow-ups
  • Hot keys? Salt them across several shards.
Is the hash map really O(1)? What is the worst case?

Expected O(1) per operation; adversarial inputs can force collisions and O(n) per lookup, so O(n²) total. Java 8+ turns long buckets into trees (O(log n)); in C++ you can use a randomised hash. The sort-based O(n log n) has no bad case.

How to answer

Say "expected O(n)" and mention the sort fallback.

Likely follow-ups
  • Why reserve in C++? To avoid rehashing during the pass.
