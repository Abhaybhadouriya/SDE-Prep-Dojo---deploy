Approaches: brute -> better -> optimal

Hint 1

Values of nums2 that are still waiting for their answer: what order are they always in?

Hint 2

When a new value is bigger than the most recent waiting value, who else might it answer?

1. Brute force - find, then scan right

Idea: for each query, find its index in nums2, then scan right for the first bigger value.

O(n · m)time
O(1)extra space

What is wasted: the "find the index" part repeats a linear search for every query. -> rung 2.

2. Better - index map, then scan right

Idea: store value -> index in nums2 once, so each query starts scanning immediately.

O(n · m)worst-case time
O(m)space

What is still wasted: on a decreasing array, every scan runs to the end. The same "bigger value" is rediscovered for many queries. -> rung 3.

3. Optimal - one pass with a decreasing stack

for x in nums2:
    while stack and stack[-1] < x:
        next_bigger[stack.pop()] = x
    stack.append(x)
return [next_bigger.get(q, -1) for q in nums1]
  1. The stack holds values still waiting. They have not seen a bigger value yet.
  2. Waiting values are decreasing. If a smaller value sat below a bigger one, the bigger one would have answered it when it arrived.
  3. A new value answers from the top down. It pops every waiting value smaller than itself; it is the first bigger value each of them has seen. It stops at the first value that is bigger, because everything below that is bigger still.
  4. Leftovers get -1. Whatever is still on the stack at the end never met a bigger value.
O(n + m)time: each value pushed and popped once
O(m)stack + map

Why it works: when x pops y, every value between them in nums2 was smaller than y (otherwise it would have popped y earlier), so x is the first bigger value after y. And if y is never popped, no later value was bigger. The inner while looks costly, but there are only m pushes, so there can be at most m pops in total: amortised O(1) per value.
