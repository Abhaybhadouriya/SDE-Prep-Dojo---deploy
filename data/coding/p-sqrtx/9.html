60-second recall

  • Cue: "largest r such that test(r)" with a monotone test -> binary search on the answer.
  • Insight: r·r <= x is yes...yes no...no; the answer is the last yes.
  • State: lo always valid, answer in [lo, hi]; fits -> lo = mid, too big -> hi = mid - 1.
  • Trap: round mid UP when lo = mid; square in 64 bits or test mid <= x / mid.
  • Cost: O(log x), ~31 probes; integer Newton r = (r + x/r)/2 converges faster.
def last_true(lo, hi, ok):       # ok(lo) is True, ok is monotone
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if ok(mid): lo = mid
        else: hi = mid - 1
    return lo

lo = 2, hi = 3, x = 8, mid = (lo + hi) // 2, and 'fits -> lo = mid'. What happens?

  1. An endless loop: mid = 2 = lo every time
  2. It returns 2
  3. It returns 3
  4. hi becomes 1
With lo = mid, round mid up: (lo + hi + 1) // 2.

x = 2^31 - 1 and mid is about 46341. Why test mid <= x / mid, or square in 64 bits?

  1. 46341^2 = 2147488281, which is above INT_MAX and overflows 32-bit int
  2. Division is faster
  3. mid can be 0
  4. It changes the answer
mid <= x / mid with integer division matches mid*mid <= x for mid >= 1.
