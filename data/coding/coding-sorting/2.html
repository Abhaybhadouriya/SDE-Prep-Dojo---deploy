Custom comparators that never break

Most interview sorts are one library call plus a comparator: a function that says whether a must come before b. Three shapes cover almost everything.

ShapeExampleHow to write it
Key tupleby frequency, then by value descending (Sort Array by Increasing Frequency)Compare the primary key; only if equal, compare the next. In Python: key=lambda x: (freq[x], -x).
Rank from a tableorder letters by a given alphabet (Custom Sort String, Relative Sort Array)Build rank[c] once, then sort by rank. Often counting is even faster.
Pairwise rulearrange numbers to form the largest numbera before b if the string a+b > b+a. There is no simple key, so you need a real comparator.

The contract every library relies on: the comparator must be a strict weak ordering. In plain words: less(a, a) is false, if a is before b then b is not before a, and "before" chains (a before b before c means a before c). Break it and C++ std::sort has undefined behaviour (it can read past the array), and Java's TimSort may throw IllegalArgumentException: Comparison method violates its general contract.

Every version on this page, Go included, was compiled and run (Go 1.27, C++14, Java 21, Python 3.11) and passes its checks.

// 1. Custom comparator: frequency ascending, ties by value descending (LC 1636 shape).
func frequencySort(nums []int) []int {
	freq := map[int]int{}
	for _, x := range nums {
		freq[x]++
	}
	out := append([]int(nil), nums...)
	sort.Slice(out, func(i, j int) bool {
		a, b := out[i], out[j]
		if freq[a] != freq[b] {
			return freq[a] < freq[b]
		}
		return a > b
	})
	return out
}

// 2. Concatenation comparator (LC 179).
func largestNumber(nums []int) string {
	s := make([]string, len(nums))
	for i, x := range nums {
		s[i] = strconv.Itoa(x)
	}
	sort.Slice(s, func(i, j int) bool { return s[i]+s[j] > s[j]+s[i] })
	if s[0] == "0" {
		return "0"
	}
	return strings.Join(s, "")
}
// 1. Custom comparator: order by frequency ascending, ties by value descending (LC 1636 shape).
vector<int> frequencySort(vector<int> nums) {
    unordered_map<int, int> freq;
    for (int x : nums) freq[x]++;
    sort(nums.begin(), nums.end(), [&](int a, int b) {
        if (freq[a] != freq[b]) return freq[a] < freq[b];  // primary key
        return a > b;                                       // tie-break
    });                                                     // must be a strict "less than"
    return nums;
}

// 2. Concatenation comparator (LC 179): a goes first if a+b > b+a.
string largestNumber(vector<int>& nums) {
    vector<string> s;
    for (int x : nums) s.push_back(to_string(x));
    sort(s.begin(), s.end(), [](const string& a, const string& b) { return a + b > b + a; });
    if (s[0] == "0") return "0";                            // all zeros
    string out;
    for (auto& t : s) out += t;
    return out;
}
// 1. Custom comparator: frequency ascending, ties by value descending (LC 1636 shape).
static int[] frequencySort(int[] nums) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int x : nums) freq.merge(x, 1, Integer::sum);
    Integer[] boxed = Arrays.stream(nums).boxed().toArray(Integer[]::new);
    Arrays.sort(boxed, (a, b) -> !freq.get(a).equals(freq.get(b))
            ? Integer.compare(freq.get(a), freq.get(b))
            : Integer.compare(b, a));      // never "a - b": it can overflow
    return Arrays.stream(boxed).mapToInt(Integer::intValue).toArray();
}

// 2. Concatenation comparator (LC 179).
static String largestNumber(int[] nums) {
    String[] s = new String[nums.length];
    for (int i = 0; i < nums.length; i++) s[i] = String.valueOf(nums[i]);
    Arrays.sort(s, (a, b) -> (b + a).compareTo(a + b));
    if (s[0].equals("0")) return "0";
    return String.join("", s);
}

    s = [str(x) for x in nums]

    def cmp(a, b):
        if a + b > b + a:
            return -1
        return 1 if a + b < b + a else 0

    s.sort(key=functools.cmp_to_key(cmp))
    return "0" if s[0] == "0" else "".join(s)

Three comparator bugs that cost offers: (1) return a - b in Java overflows for large values of opposite sign: use Integer.compare. (2) <= instead of < in C++ is not a strict ordering. (3) In Largest Number, forgetting that [0, 0] must print "0", not "00".

Why is "a+b > b+a" a valid ordering for Largest Number?

Treat each number as a string. Comparing a+b with b+a is the same as comparing a / (10len(a) - 1) with b / (10len(b) - 1), so each string maps to one real number and the rule just orders those numbers. That makes it transitive, so sorting by it is safe. Then an exchange argument finishes the proof: if two neighbours were in the other order, swapping them would make the result at least as large.

How to answer

Say "it is a total order because each string maps to a fraction value / (10^len - 1)", then give the swap argument in one line. Mention the all-zero edge case.

Likely follow-ups
  • Smallest number instead? Flip the comparison, and handle leading zeros.
  • Cost? O(n log n) comparisons, each O(L) for string length L.
