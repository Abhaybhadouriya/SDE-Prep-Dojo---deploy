Interview questions

Which sort does your language use, and is it stable?

C++ std::sort is introsort (quicksort that falls back to heapsort when recursion gets deep, insertion sort for tiny ranges): O(n log n) worst case, not stable; std::stable_sort is a merge sort. Java sorts primitives with dual-pivot quicksort and objects with TimSort, which is stable. Python's sort is TimSort-based and guaranteed stable. Go's sort.Slice and slices.SortFunc are pdqsort and not stable; use the Stable variants.

How to answer

Name the algorithm, its worst case and stability in one sentence, then say when stability matters (multi-key sorts, "keep original order on ties").

Likely follow-ups
  • Why does Java use a different algorithm for primitives? Stability is meaningless for equal primitives, and quicksort is faster and in place.
  • Why does introsort need heapsort? To cap the worst case at O(n log n).
Find the k-th largest element. Walk me through every option.

Sort: O(n log n). Min-heap of size k: push each value, pop when size exceeds k, the top is the answer: O(n log k), works on a stream. Quickselect: partition around a random pivot, continue only on the side that holds index n-k: expected O(n), O(1) extra space, worst case O(n2). With bounded values, a count array is O(n + range).

How to answer

Start with the heap (safe, short code), then offer quickselect and explain why the pivot is random and the partition 3-way. State the worst case honestly.

Likely follow-ups
  • The data arrives as a stream: heap (Kth Largest Element in a Stream).
  • You need the median of a stream: two heaps.
  • Guaranteed linear time: median of medians.
When is counting sort better than a comparison sort, and when is it a bad idea?

When the key range k is small compared with n (letters, ages, scores 0..100, frequencies 1..n), counting sort is O(n + k) and stable. It is a bad idea when the range is large or unknown (32-bit values), because memory is O(k). Then use radix sort (several stable counting passes over digits) or a normal sort.

How to answer

Give the O(n log n) lower bound for comparison sorts, then explain that counting sort escapes it by indexing, not comparing. Mention the prefix-sum step that makes it stable.

Likely follow-ups
  • How does radix sort use counting sort? LSD radix sorts by the lowest digit first; stability keeps earlier digit orders.
Count pairs i < j with nums[i] > 2 · nums[j] (Reverse Pairs).

Merge sort. After both halves are sorted, count the crossing pairs with two pointers: for each left item, move j forward while left[i] > 2 · right[j]; add j - mid. j never moves back because the left half is sorted. Then merge normally. O(n log n) time, O(n) extra space. Use 64-bit for 2 · nums[j].

How to answer

Brute force O(n2) first, then the claim "pairs crossing the middle can be counted on sorted halves". Explain why counting is a separate pass here (the counting rule differs from the merge rule).

Likely follow-ups
  • Solve it with a Fenwick tree: compress values, scan from the right, query how many seen values are below nums[i] / 2.
  • Return the count per index (Count of Smaller Numbers After Self): sort indexes.
Sort an array of 0s, 1s and 2s in one pass without a library.

Dutch national flag with three pointers: [0, lo) holds 0s, [lo, i) 1s, (hi, n) 2s, and [i, hi] is unknown. On 0 swap with lo and move both; on 1 move i; on 2 swap with hi and shrink hi without moving i. One pass, O(1) space.

How to answer

Draw the four regions first, then the three cases. The interviewer is checking that you do not advance i after the swap with hi.

Likely follow-ups
  • Two passes with counting is also fine: say so, then give the one-pass version.
  • k colours? Counting sort, or repeated partitioning.
Sort 100 GB of 64-bit numbers with 4 GB of RAM.

External merge sort. Read 4 GB chunks, sort each in memory, write 25 sorted runs to disk. Then do a k-way merge with a min-heap holding one buffered value per run, streaming the output sequentially. Disk access stays sequential, which is what matters. If there are more runs than you can buffer, merge in several passes.

How to answer

Name the two phases (run creation, k-way merge), the heap of size k, and the I/O cost (each byte read and written about twice). Mention buffering so each run reads large blocks.

Likely follow-ups
  • Many duplicates? Count them (a hash map of value to count may fit in RAM).
  • Distributed? Sample to pick range boundaries, shuffle by range, sort each range locally (that is how TeraSort works).
Merge sort or quicksort for a linked list? For an array?

Linked list: merge sort. Splitting needs slow/fast pointers, merging needs only pointer changes and no extra array, it is stable, and quicksort's random access does not exist on a list (Sort List expects O(n log n) and O(1) extra with bottom-up merge). Array: quicksort is in place and cache friendly, merge sort needs O(n) extra but is stable with a guaranteed O(n log n).

How to answer

Compare on four axes: worst case, extra memory, stability, access pattern. That is also the kernel's choice (list_sort is a merge sort).

Likely follow-ups
  • Bottom-up merge sort to avoid recursion depth.
