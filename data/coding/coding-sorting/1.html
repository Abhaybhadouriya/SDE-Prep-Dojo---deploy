When to sort first

Sorting costs O(n log n). That is cheap when the brute force is O(n2), and the constraints usually tell you that you can afford it: n up to 105 means about 1.7 million steps for n log n. After sorting, four things become true that were not true before:

  1. Equal values sit next to each other. Duplicates, groups and "same key" questions become one linear scan (Group Anagrams sorts each word to make its key).
  2. Pairs can be found with two pointers. If the sum is too small move the left pointer right; too big, move the right one left. Each pointer moves at most n times.
  3. Binary search works. "First value at least x" and "how many values are below x" cost O(log n).
  4. Greedy choices become safe. Intervals sorted by start (merge them) or by end (pick the most non-overlapping); people sorted by weight (pair the lightest with the heaviest in Boats to Save People).

When not to sort: when the answer needs the original positions (then sort a list of indexes, or pairs of value and index), when the input is a stream that never ends, or when a hash map already gives O(n). Two Sum with "return the indexes" is the classic trap: a hash map is O(n), while sorting would make you carry the indexes along.

Constraints tell you: n ≤ 105 or 2·105 allows O(n log n), so "sort first" is on the table. Values in a small range (0..100, lowercase letters, ages) invite counting sort. "k-th largest" with n up to 105 allows a heap (n log k) or quickselect (expected n).
