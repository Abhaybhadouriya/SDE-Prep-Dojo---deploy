Interview questions

Signals take time to travel along directed links. From one node, how long until every node has the signal?

This is Network Delay Time. Build an adjacency list, run Dijkstra from the source, and return the largest distance, or -1 if any node stayed at infinity. Every node hears the signal at its shortest-path time, so the last one to hear it sets the answer. O(E log V) time, O(V + E) space.

How to answer

Say "weighted, non-negative, single source: Dijkstra", then the reduction "all nodes informed = max over shortest distances". Mention 1-indexed input before you write code.

Likely follow-ups
  • Weights are all equal? (BFS, O(V + E).)
  • Graph has 100 nodes and 6,000 edges? (Dense: the O(V2) array Dijkstra or even Floyd is fine.)
Why does lazy Dijkstra need the stale-entry check, and what is its complexity with and without it?

A vertex can be pushed once per improvement, so the heap can hold up to E entries. Without the check, an old entry with a worse distance is popped later and its edges are relaxed again. None of those relaxations succeed, so the answer is still right, but each stale pop rescans the adjacency list: on adversarial inputs that multiplies work by the vertex degree. With the check, each vertex expands once, giving O(E log V). A decrease-key heap (Fibonacci in theory, an indexed binary heap in practice) keeps one entry per vertex and gets O(E + V log V) with Fibonacci heaps, but nobody writes that in an interview.

How to answer

Explain duplicates exist because standard library heaps lack decrease-key, then the cost of not skipping them.

Likely follow-ups
  • Can you use a TreeSet / std::set instead? (Yes: erase the old (dist, v) and insert the new one, a true decrease-key in O(log V).)
Cheapest flight with at most K stops: why not plain Dijkstra? Give two working approaches.

Dijkstra settles each city once at its cheapest price, but that cheapest route may use too many stops, and a pricier route with fewer stops may be the only one that still reaches the destination within the limit. Approach 1: K + 1 rounds of Bellman-Ford where each round relaxes every flight from a copy of the previous round, O(K x E). Approach 2: Dijkstra or BFS over states (city, stops used), keeping the best price per state, or pruning a state only when the same city was reached with both fewer stops and lower cost.

How to answer

Show the counterexample in one sentence, then give Bellman-Ford with the copy and explain why the copy matters.

Likely follow-ups
  • Return the route itself? (Keep a parent per (round, city).)
  • What if K is larger than V? (It no longer binds: V - 1 rounds suffice, or use plain Dijkstra.)
Path With Minimum Effort: give three different solutions and compare them.

(1) Dijkstra where a path's cost is its maximum step: nd = max(d, |h[v] - h[u]|), stop when the target is popped; O(RC log RC). (2) Binary search the effort X over [0, maxHeight]; for each X, BFS using only steps ≤ X and check if the target is reachable; O(RC log H). (3) Union-find: list all adjacent-cell edges with their step, sort them, union in order until start and target share a root; the current weight is the answer; O(RC log RC) for the sort. All three exploit that a "max" cost is monotone: extending a path never lowers it.

How to answer

Lead with Dijkstra (one-line change), then offer the others as alternatives that show range. Mention the union-find one is Kruskal stopped early.

Likely follow-ups
  • Many start/target queries on the same grid? (Build the minimum spanning tree once; the answer for a pair is the largest edge on their tree path.)
Why does Dijkstra fail with negative edges? What do you use, and how do you detect a negative cycle?

Dijkstra finalises a vertex when it is popped because every unexplored route can only add non-negative cost. A negative edge breaks that: a route through a vertex popped later can come back cheaper to an already final vertex. Use Bellman-Ford: V - 1 rounds of relaxing all edges, O(V x E). Run one more round; if any distance still improves, a negative cycle is reachable from the source. For all pairs, Floyd-Warshall handles negative edges, and a negative d[i][i] shows a cycle through i.

How to answer

State the invariant, point at the line of the proof that needs w ≥ 0, then the replacement.

Likely follow-ups
  • Small example where it fails? (s → a 1, s → b 3, b → a -3: Dijkstra finalises a at 1, the truth is 0.)
Count the number of different shortest paths from city 0 to city n - 1, modulo 109+7.

Run Dijkstra with an extra array ways, ways[0] = 1. On a strictly better distance, overwrite ways[v] = ways[u] and push; on an equal distance, add ways[v] = (ways[v] + ways[u]) % MOD. Because vertices settle in distance order and weights are positive, every predecessor on a shortest path is settled (and its count final) before v is. Use 64-bit distances: times up to 109 summed over many roads overflow 32 bits.

How to answer

Name it as "shortest-path DAG counting", explain the equal-distance branch, and call out the overflow trap.

Likely follow-ups
  • Zero-weight edges allowed? (Equal-distance vertices can then depend on each other; you must count in a topological order of the zero-weight sub-DAG.)
When do you choose Floyd-Warshall over running Dijkstra from every vertex?

Floyd is O(V3) time and O(V2) space with a tiny constant and three lines of code; V Dijkstras are O(V x E log V). Choose Floyd when V is small (a few hundred), the graph is dense, negative edges exist, or you need the whole matrix for many queries. Choose repeated Dijkstra for large sparse graphs, or when only a few sources matter.

How to answer

Compare the two formulas at E ~ V and E ~ V2, then mention negative edges and code simplicity.

Likely follow-ups
  • An edge's weight drops after the matrix is built? (Update in O(V2): for each pair, try i → a → b → j and i → b → a → j.)
Design question tail: shortest routes on a road map with tens of millions of nodes, answered in milliseconds. What changes?

Plain Dijkstra explores a ball around the source, which is far too much at continent scale. Steps up: bidirectional Dijkstra (search from both ends, stop when the frontiers meet properly), A* with an admissible heuristic such as straight-line distance divided by the top speed (or landmark-based ALT bounds), and preprocessing such as contraction hierarchies, which add shortcut edges so queries only climb "upwards" in importance and touch a few hundred nodes. Live traffic means edge weights change, so systems separate a slowly changing structure from fast weight updates (customisable route planning). Partition the graph by region for sharding.

How to answer

Start from Dijkstra's cost, then bidirectional, A*, then preprocessing; tie each to a measurable win and to the update problem.

Likely follow-ups
  • Why must the A* heuristic never overestimate? (Then the first time the target is popped is still optimal.)
