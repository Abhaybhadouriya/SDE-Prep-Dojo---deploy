Do it in O(1) extra space.

Bottom-up merge sort: count n, then for size = 1, 2, 4, ... cut pairs of runs of length size, merge them, and append behind a tail pointer. log n passes of O(n) each, constant extra pointers, no recursion.

How to answer

Explain that recursion only builds sorted runs of doubling length, so you can build them in loops.

Likely follow-ups
  • Write the cut(head, k) helper and say what it returns when fewer than k nodes remain.
Why not quicksort on the list?

Quicksort on a list is possible (partition into less / equal / greater sublists) and in place, but its worst case is O(n2) on sorted input with a head pivot, and picking a random pivot needs O(n) walking. Merge sort is O(n log n) on every input and stable. That is also why the kernel's list_sort is a merge sort.

How to answer

Compare worst case, stability and access pattern; do not say quicksort "cannot" work.

Likely follow-ups
  • Is your merge sort stable? (Yes, with <=.)
What if the list is doubly linked?

Sort using only next as above (treat it as singly linked), then make one final pass setting each node's prev to the node before it. Fixing prev during every merge is possible but adds bugs for no asymptotic gain.

How to answer

Reduce to the singly linked case and repair once.

Likely follow-ups
  • And a circular doubly linked list? (Break the ring at the head, sort, re-close.)
The list does not fit in memory (a huge file of records).

External merge sort: read chunks that fit in RAM, sort each and write it out as a sorted run, then k-way merge the runs with a min-heap of their current heads, streaming the output. It is the same "sorted runs, then merge" idea, with disk I/O as the cost to minimise.

How to answer

Name the two phases and the heap for the k-way merge.

Likely follow-ups
  • How do you pick the chunk size and k? (Memory / buffer per run.)
Values are only in a small range (say 0..100).

Counting sort on the values in O(n + range): count the values in one pass, then overwrite them in a second pass. Or, to move nodes instead of values, keep one bucket list per value and concatenate the buckets: O(n + range) and stable.

How to answer

Use the range to beat n log n; mention the payload issue with overwriting values.

Likely follow-ups
  • Three values only? (That is the Dutch flag idea: three bucket lists.)
