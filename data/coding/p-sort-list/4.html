Approaches: brute -> better -> optimal

Hint 1

Which O(n log n) sort never needs to jump to index i?

Hint 2

How do you find the middle of a list in one pass? And how do you stop a 2-node list from splitting into 2 + 0?

1. Brute force - copy to an array, sort, write back

Idea: walk the list into an array, sort the array with the library sort, then walk the list again and overwrite each val.

O(n log n)time
O(n)extra space

What is wasted: O(n) memory, and it changes values rather than nodes, which is wrong when nodes carry payloads (the kernel case). Say it in one sentence as a baseline; many interviewers then ask for the real thing. Insertion sort on the list is O(1) space but O(n2) time.

2. Better - top-down merge sort (the expected answer)

  1. Base case. 0 or 1 node: already sorted, return it.
  2. Find the middle. slow = head, fast = head.next; move slow one step and fast two steps while fast and fast.next exist. Slow ends on the last node of the left half.
  3. Cut. right = slow.next, slow.next = null. Now there are two separate lists.
  4. Recurse and merge. Return merge(sortList(head), sortList(right)), where merge appends the smaller front node behind a dummy and finally attaches the leftover list in one step.
  1. dummy → (empty). a = 1, b = 2. 1 <= 2, so link 1 after tail and advance a.
  2. a = 4, b = 2. 2 is smaller: link it, advance b.
  3. a = 4, b = 3. Take 3.
  4. a = 4, b = 8. Take 4.
  5. a = 5, b = 8. Take 5. a becomes null.
  6. a is null: tail.next = b appends 8 in O(1), no loop over the rest. Return dummy.next.
O(n log n)time: log n levels, O(n) merge work per level
O(log n)stack: one frame per level

Why it works: by induction on the length. A list of 0 or 1 node is sorted. For a longer list the split always makes two non-empty, strictly shorter halves (because slow stops on the last node of the left half, a 2-node list splits 1 + 1), so both recursive calls return sorted lists by the induction hypothesis. Merging two sorted lists by always taking the smaller front node produces a sorted list containing every node exactly once. The <= in the merge takes the left node on ties, which makes the sort stable.

3. Optimal for the follow-up - bottom-up merge sort, O(1) space

Idea: the recursion only exists to produce sorted runs of size 1, 2, 4, ... Do that directly: count the length n once; for size = 1, 2, 4, ... while size < n, walk the list, cut off two runs of size nodes, merge them, and append the result behind a tail pointer. After ⌈log2 n⌉ passes the list is one sorted run.

O(n log n)time: log n passes over n nodes
O(1)extra space: a few pointers
Bottom-up version (Python, tested in the same driver) 
def sort_list_bottom_up(head):
    n, p = 0, head
    while p:                                   # count the nodes once
        n, p = n + 1, p.next

    def cut(h, k):                             # keep k nodes of h, return the rest
        for _ in range(k - 1):
            if h is None:
                break
            h = h.next
        if h is None:
            return None
        rest, h.next = h.next, None
        return rest

    dummy = ListNode(0, head)
    size = 1
    while size < n:                            # runs of 1, 2, 4, ... are sorted
        tail, cur = dummy, dummy.next
        while cur:
            left = cur
            right = cut(left, size)
            cur = cut(right, size)
            tail.next = merge(left, right)
            while tail.next:                   # move tail to the merged run's end
                tail = tail.next
        size *= 2
    return dummy.next
