60-second recall

  • Cue: sort a linked list in O(n log n); no indexing.
  • Insight: merge sort; merging lists is free in space.
  • Split: slow = head, fast = head.next; cut at slow.next.
  • Merge: dummy + tail, take the smaller (<=), attach the rest.
  • Follow-up: bottom-up passes of size 1, 2, 4 → O(1) space.
def sortList(h):
    if not h or not h.next: return h
    slow, fast = h, h.next
    while fast and fast.next: slow, fast = slow.next, fast.next.next
    right, slow.next = slow.next, None
    return merge(sortList(h), sortList(right))

Why is merge sort preferred over quicksort for a linked list?

  1. Quicksort cannot sort negatives
  2. Merging needs only sequential access and no extra array; partitioning around good pivots wants random access
  3. Merge sort is O(n)
Lists are walked, not indexed. Merge sort only walks.

On the 2-node list 3 → 1 with fast = head, what goes wrong?

  1. It returns 3 → 1 unchanged
  2. It drops a node
  3. The left half is both nodes, so the call repeats forever
slow moves to 1, the cut after slow leaves an empty right half.

What is the extra space of the top-down version?

  1. O(log n) for the recursion stack
  2. O(1)
  3. O(n) for the merge
The merge relinks nodes; only the stack grows, one frame per level.
