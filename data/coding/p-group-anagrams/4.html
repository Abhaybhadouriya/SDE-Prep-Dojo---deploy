Approaches: brute → better → optimal

Hint 1

If you could turn every word into a "fingerprint" that is the same for all its anagrams, what data structure groups items by fingerprint?

1. Brute force - compare each word with each group

Idea: keep a list of groups. For each word, test it against the first word of every group with an "is anagram" check (count letters, O(K)); join the first group that matches or open a new one.

O(N² · K)time (worst case: all words in different groups)
O(N · K)space (the output)

What is wasted: we recompute a fingerprint for the group leaders again and again and scan all groups linearly. Compute one fingerprint per word once and look it up in a hash map.

2. Better - sorted word as the key

Idea: key = sorted(word); "stop", "pots", "tops" all become "opst". Append the word to map[key], return the map's values. Short, clear, and what most people write first.

O(N · K log K)time
O(N · K)space

What is wasted: sorting is more than we need. The alphabet has only 26 letters, so counting gives the same information in O(K).

3. Optimal - 26 letter counts as the key

for w in strs:                                  # core
    count = [0] * 26
    for ch in w: count[ord(ch) - 97] += 1
    groups[tuple(count)].append(w)
  1. The count vector is a perfect fingerprint. Two words are anagrams exactly when every letter occurs the same number of times in both, which is exactly "equal count vectors".
  2. Make it hashable. Python: tuple(count). Java/C++: a 26-character string where character c holds the count of letter c. Go: the array [26]byte itself is a valid map key.
  3. One lookup per word. Existing key: append. New key: open a bucket. A side list keeps the buckets in first-seen order, so the output is deterministic.
O(N · (K + 26))time = O(N · K)
O(N · K)space (keys + output)

Why it works: "is an anagram of" is an equivalence relation (reflexive, symmetric, transitive), so the words split into disjoint classes. A function that is equal exactly within a class names each class, and a hash map groups by name in expected O(1) per word. Any valid key works; the count key is cheapest to build.

Is the count key really faster? (optional)

Asymptotically yes (K vs K log K), but with K ≤ 100 both are fast, and hashing a 26-char key costs about the same as hashing a short word. In an interview, say both, code either, and state the complexity of the one you code. For long words over a small alphabet, counting clearly wins; for short words over a huge alphabet (Unicode), sorting is safer.
