Approaches: brute → better → optimal

Hint 1

Solve LRU Cache first. Now imagine many LRU caches, one per use count. What moves between them, and when?

Hint 2

When can the smallest count change? Only on two events: a new key arrives (it becomes 1), or the last key with the smallest count is used (it becomes that count + 1).

1. Brute force - scan for the victim

Idea: map key -> (value, count, lastUsedTick). get/put update the entry in O(1); eviction scans all keys for the smallest (count, lastUsed).

O(1) / O(capacity)get / evicting put
O(capacity)space

What is wasted: the full scan on every eviction. We only ever need the minimum of (count, tick). -> keep it ordered.

2. Better - a sorted set (or heap) of (count, tick, key)

Idea: keep (count, tick, key) in a balanced BST (std::set, TreeSet). A use removes the old triple and inserts a new one; eviction removes the smallest. A heap works too with lazy deletion (skip stale triples).

O(log n)get and put
O(capacity)space

What is wasted: a count only ever changes by +1, and new keys always start at 1. A general ordered structure pays log n for flexibility we do not use. -> buckets.

3. Optimal - count buckets of LRU lists + minFreq

def touch(key):                     # one more use
    f = freq[key]; del by_freq[f][key]
    if not by_freq[f]:
        del by_freq[f]
        if min_freq == f: min_freq = f + 1
    freq[key] = f + 1; by_freq[f + 1][key] = None
  1. State: nodes (key -> node with value and count), byFreq (count -> doubly linked list, most recent first), minFreq.
  2. get: miss -> -1. Hit -> touch (move to the front of list f+1) and return the value.
  3. put, existing key: update the value and touch. Never evict on an update.
  4. put, new key, cache full: evict the tail of byFreq[minFreq] and delete it from nodes (the node stores its key).
  5. put, new key: insert at the front of list 1 and set minFreq = 1.
O(1)get and put (average, hashing)
O(capacity)space

Why minFreq is always right without a search: it can only change on two events. (1) A new key arrives with count 1, and no key has a count below 1, so minFreq = 1. (2) A key with count f is used and moves to f+1. If list f still has keys, the minimum is unchanged. If list f is now empty and f was the minimum, the key we just moved has count f+1 and nothing is below it, so the new minimum is exactly f+1. Eviction does not need an update: it is always followed by inserting a new key, which sets minFreq = 1.

Why the tie-break works

Inside each list, a node enters at the front when it reaches that count, and nodes in one list never reorder otherwise. So the tail of a list is the key that reached that count earliest, which, among keys with that count, is the one whose last use is oldest.
