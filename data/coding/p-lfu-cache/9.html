Revision card

  • Cue: O(1) cache, evict lowest use count, tie -> least recent: LFU buckets.
  • Insight: one LRU list per count; a use moves a node f -> front of f+1.
  • State: nodes{key: node(val, freq)}, byFreq{f: list}, minFreq, cap.
  • Trap: new key -> minFreq = 1; f empties AND f == minFreq -> minFreq++; update = use.
  • Cost: O(1) per call, O(capacity) space; sorted set O(log n) as a fallback.
get(k):  if k not in nodes: return -1; touch(k); return val[k]
put(k,v): if k in nodes: val[k] = v; touch(k); return
          if full: victim = by_freq[min_freq].pop_oldest(); forget(victim)
          add k to by_freq[1] (newest end); min_freq = 1
touch(k): move k from by_freq[f] to by_freq[f+1]
          if by_freq[f] empty and min_freq == f: min_freq = f + 1

Quick quiz

minFreq = 1 and key 9 moves from count 3 to 4, emptying list 3. What is minFreq now?

  1. 4
  2. 2
  3. 1
  4. 3
Only the minimum list emptying moves minFreq; list 3 was not the minimum.

Why does eviction never need to recompute minFreq?

  1. It is always followed by inserting a new key, which sets minFreq = 1
  2. Eviction never empties a list
  3. minFreq is recomputed lazily on get
  4. The victim always has count 1
Eviction happens only inside put of a new key, and that key has count 1.

Inside one count's list, which key is evicted?

  1. The most recently used
  2. The one that reached this count earliest (least recent)
  3. The smallest key
  4. A random one
Nodes enter at the front on reaching a count, so the tail is the oldest use among them.
