Interview questions

Explain union-find and its two optimisations. What is the complexity?

Each set is a tree stored in a parent array; the root represents the set. find climbs to the root, union links one root under the other. Path compression re-points every vertex on a find path straight to the root. Union by rank (or size) hangs the shorter tree under the taller, which caps height at log n. With both, any sequence of m operations on n items costs O(m α(n)), where α is the inverse Ackermann function and is at most 4 in practice. With only one of them you get O(log n) per operation.

How to answer

Draw the parent array and one tree, then add each optimisation with the problem it fixes (chains).

Likely follow-ups
  • Rank or size, which is better? (Same bound; size also gives you set sizes, so it is often more useful.)
  • Is it worst-case O(1)? (No, amortised; a single find can still be O(log n).)
Find the edge that makes an undirected graph not a tree. Why does the first failed union give the right answer?

A tree plus one edge has exactly one cycle. Processing edges in input order, every edge merges two sets until the moment the cycle's last edge (in input order) arrives, when both ends are already connected through the rest of the cycle. That edge is both removable and the last removable edge in the input, which is what the problem asks for. O(n α(n)) time.

How to answer

State the "tree plus one edge = one cycle" fact first; the tie-break argument then takes one sentence.

Likely follow-ups
  • Directed version? (Redundant Connection II: handle a node with two parents separately from a cycle; try removing each candidate parent edge.)
  • Without DSU? (DFS before adding each edge to check whether its ends are already connected: O(n2).)
Accounts Merge: how would you design the solution, and what is the complexity?

Treat each account as a DSU element. Keep a map from email to the first account that owns it; when another account lists the same email, union the two. Then group every email by the root of its owner, sort each group and prepend the owner's name. Unions cost O(E α(n)) for E emails; sorting the groups costs O(E log E) and dominates. Never merge on the name, since names are not unique.

How to answer

Say "merge by a shared key" and explain why no explicit graph is needed.

Likely follow-ups
  • Do it with DFS. (Build an email graph linking each account's first email to the rest, then collect components.)
  • Millions of accounts arriving as a stream? (DSU handles it online; the email map becomes the memory bottleneck, so shard by email hash.)
Land cells are added one at a time. Report the number of islands after each addition.

Use a DSU over all m x n cells, initially water. Adding a cell increments the island count; then for each of its four neighbours that is already land, a successful union decrements the count. Skip positions that are already land. Each addition is O(α(mn)), total O(mn + k α(mn)), versus O(k x mn) for re-running a flood fill each time.

How to answer

Start by naming the naive approach and its cost, then show how DSU turns each step into a few unions.

Likely follow-ups
  • The grid is huge and sparse. (Replace arrays with a hash map keyed by cell, creating DSU entries lazily.)
  • Cells can also turn back into water. (DSU cannot split; process offline in reverse, or use a dynamic connectivity structure.)
Making a Large Island: what is the trap, and what is your complexity?

Precompute each island's size once (DSU by size or DFS labelling). For every 0, sum the sizes of the distinct islands among its four neighbours, plus one. The trap is double counting: the same island often touches a cell from two sides, so collect roots in a small set first. Also handle the all-land grid, where there is no 0 to flip. O(n2 α(n2)) time, O(n2) space.

How to answer

Reject the O(n4) flip-and-flood idea first, then present "precompute sizes, then one neighbour scan".

Likely follow-ups
  • Allow flipping k cells. (Much harder; no simple extension, so discuss search with pruning for small k.)
When would you choose BFS or DFS over union-find for a connectivity problem?

When the graph is static and I only need components once, both are linear and I pick whichever is simpler to write. I pick BFS when I need distances or a path, since DSU forgets how things got connected, and DFS or topological sort for directed problems. DSU wins when edges arrive online, when I need to know whether an edge closes a cycle, or when items link through a shared key without an explicit edge list.

How to answer

Frame it as "when do the edges arrive, and what do I need back?".

Likely follow-ups
  • Can DSU support deletions? (Not directly; offline reverse-time processing turns deletions into unions.)
How does Kruskal's algorithm use union-find, and why is it correct?

Sort edges by weight. Walk them in order and keep an edge exactly when its union succeeds, i.e. its ends are in different components; stop after n - 1 kept edges. Correctness is the cut property: the lightest edge crossing any cut between the current components belongs to some minimum spanning tree. Cost is O(E log E) for sorting plus O(E α(V)) for the unions.

How to answer

Give the algorithm, name the cut property, then the cost split between sorting and DSU.

Likely follow-ups
  • Dense graph with all pairs (Min Cost to Connect All Points)? (Prim's with an array is O(V2) and avoids sorting V2 edges.)
