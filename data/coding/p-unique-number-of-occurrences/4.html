Approaches: brute -> better -> optimal

Hint 1

First find how many times each value occurs. Which structure maps a value to a number?

Hint 2

Now you have a list of counts. How do you check that a list has no duplicates?

1. Brute force - count each value by scanning

Idea: for each distinct value, scan the array to count it; then compare every pair of counts.

O(n2)time
O(n)list of counts

What is wasted: each value's count is rebuilt from scratch, and the pairwise comparison of counts is O(k2).

2. Better - sort, measure runs, sort the run lengths

Idea: sort the array so equal values form runs, record each run length, sort the run lengths and check neighbours for equality. This is the most-voted community approach that uses no map or set.

O(n log n)time
O(n)run lengths (sorting in place changes the input)

What is wasted: sorting the whole array just to group equal values. A hash map groups them in one pass.

3. Optimal - hash map of counts, hash set of counts

freq = Counter(arr)
seen = set()
for c in freq.values():
    if c in seen: return False
    seen.add(c)
return True
  1. Count. One pass builds freq[value].
  2. Check the counts. Walk the map's values; a count already in seen means two distinct values share it.
  3. Early exit. Stop at the first repeat. The short form len(freq) == len(set(freq.values())) is equivalent but always builds the whole set.
O(n)time (expected, hashing)
O(k)k = distinct values <= n

Why it works: every distinct value contributes exactly one count to freq.values(). The counts are unique exactly when this list has no duplicates, which is what the set check (or the size comparison: k values, k distinct counts) tests. The order in which the map is walked does not matter.

Bounded-value variant (from the top-voted C++ answer): since values lie in [-1000, 1000] and counts in [1, 1000], use int freq[2001] indexed by v + 1000 and bool seen[1001] indexed by the count. Same logic, no hashing, guaranteed O(n + 2001).

A useful bound: if all k counts are distinct, they are at least 1 + 2 + ... + k = k(k+1)/2 <= n, so k <= about sqrt(2n). With more distinct values than that, the answer is false before you check anything. It does not change the big-O, but it is a nice remark in the interview.
