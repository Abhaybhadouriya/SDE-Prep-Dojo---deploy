Now at most k transactions.

Arrays buy[1..k], sell[0..k]: for each price, for j = 1..k, buy[j] = max(buy[j], sell[j-1] - p) and sell[j] = max(sell[j], buy[j] + p). O(n·k) time, O(k) space. When 2k >= n the limit cannot bind, so switch to the greedy sum of rises to avoid O(n2).

How to answer

Show that the two-trade code is the k = 2 unrolling.

Likely follow-ups
  • Why does k >= n / 2 mean "unlimited"? (Each trade needs at least two days.)
Return the actual buy and sell days, not just the profit.

With the split version it is easiest: record, for each left[i] and right[i], the buy and sell day that produced it, then report the pair for the best split. With the state machine, store alongside each state the day indices that last improved it (for buy2, the day plus the trade stored with sell1 at that moment).

How to answer

Carry "argmax" data next to each running max.

Likely follow-ups
  • What if there are ties? (Agree on earliest or shortest.)
Add a transaction fee per trade.

Subtract the fee once per trade, for example on the sell: sell1 = max(sell1, buy1 + p - fee) and likewise for sell2. With unlimited trades this is LC 714 with just two states. The structure does not change.

How to answer

Put the fee on one transition only, to avoid charging twice.

Likely follow-ups
  • And a cooldown day after each sell? (A third state for "just sold".)
Explain why updating the four variables in place in this order is safe.

Each state reads the state before it in the chain (buy1 → sell1 → buy2 → sell2). Updating in chain order means a state may read a value already improved today, which is equivalent to doing both steps today. For buy then sell on the same day the gain is -p + p = 0; for sell then buy it is +p - p = 0. So no impossible profit appears, and the true optimum is still reachable.

How to answer

Show the zero-profit same-day argument explicitly.

Likely follow-ups
  • Would updating in reverse order (sell2 first) also be correct? (Yes, then every state reads yesterday's values.)
