The problem (in our words)

You get a list equations where equations[i] = [A_i, B_i] and a matching list values, meaning A_i / B_i = values[i]. Each A_i or B_i is a string naming one variable.

You also get queries where queries[j] = [C_j, D_j]. For each query, return the value of C_j / D_j derived from the equations. If it cannot be determined, return -1.0 for that query. A variable that never appears in any equation is unknown, so a query that uses it answers -1.0 (even x / x).

The input is always valid: no division by zero and no contradicting equations. Answers within 1e-5 of the true value are accepted.

Signature: double[] calcEquation(List<List<String>> equations, double[] values, List<List<String>> queries).

  • 1 <= equations.length <= 20, equations[i].length == 2
  • 1 <= A_i.length, B_i.length <= 5
  • values.length == equations.length, 0.0 < values[i] <= 20.0
  • 1 <= queries.length <= 20, queries[j].length == 2
  • 1 <= C_j.length, D_j.length <= 5
  • All names are lowercase English letters and digits.

Practice it: LeetCode 399 · editorial

Constraints tell you: at most 20 equations, so at most 40 variables and 20 queries. Even a fresh DFS per query (O(V + E) each) is trivially fast. The tiny limits mean the interviewer cares about the model (directed weighted graph, reciprocal edges, the unknown-variable rule) and maybe the union-find upgrade, not raw speed.
