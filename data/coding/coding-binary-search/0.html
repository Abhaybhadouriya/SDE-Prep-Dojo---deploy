The story: guess my number

Explain like I'm 5

I think of a number from 1 to 100. You guess, and I say "higher" or "lower". If you guess 1, 2, 3... it can take 100 tries. If you always guess the middle (50, then 25 or 75, ...) each answer throws away half of what is left. 100, 50, 25, 13, 7, 4, 2, 1: at most 7 guesses.

A phone book works the same way. You open it in the middle, see "M", and you know "Patel" is in the second half. You never read the first half.

Binary search needs one thing: a question you can ask about the middle item whose answer tells you which half to throw away. Sorted data gives you that question for free ("is the middle smaller than what I want?"). Later on this page the question is cleverer: "which half of this rotated array is sorted?", "am I walking uphill?".

From your world

You have used binary search on code history: git bisect finds the commit that broke the build by testing the middle commit and marking it good or bad. 1,000 commits take about 10 builds. The kernel ships a generic bsearch() in lib/bsearch.c, used for sorted tables such as exception tables. And the predicate "commit is bad" is exactly the false...false, true...true shape this page is built on.
