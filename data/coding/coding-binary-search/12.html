Interview questions

Find the first and last position of a target in a sorted array with duplicates, in O(log n).

Two searches. First = lower_bound(target); if it is n or a[first] != target, return [-1, -1]. Last = upper_bound(target) - 1. Both use the half-open template, so the same loop with < versus <= in the comparison.

How to answer

Reject "find any copy, then scan both ways": that is O(n) when the whole array is the target.

Likely follow-ups
  • Count occurrences. (upper - lower.)
  • The array is huge and on disk. (Same; each probe is a page read, log n of them.)
Search in a rotated sorted array. Why does comparing a[lo] and a[mid] work?

The array is two sorted ramps with one drop. The interval [lo, mid] contains the drop only if a[lo] > a[mid]. So if a[lo] <= a[mid], [lo, mid] is sorted and we can test "target in [a[lo], a[mid])" exactly; otherwise [mid, hi] is sorted and we test "target in (a[mid], a[hi]]". One half is always testable, so we always discard one half: O(log n).

How to answer

Draw the two ramps first; the code follows from the picture.

Likely follow-ups
  • Duplicates allowed. (When a[lo] == a[mid] == a[hi], shrink lo and hi by one; worst case O(n).)
  • Find the rotation count. (Index of the minimum.)
Find a peak element in O(log n). Prove it always finds one.

Invariant: [lo, hi] contains a peak, where outside the array is minus infinity. Start [0, n - 1]: true, since the global max is a peak. If a[mid] < a[mid + 1], then going right from mid + 1 you either meet a drop (a peak) or reach the end (a peak, because the outside is minus infinity), so [mid + 1, hi] has one. Otherwise [lo, mid] has one by the mirror argument. The range shrinks every step and ends at a single index, which is a peak.

How to answer

Say "walk uphill", then give the invariant. Mention that equal neighbours would break it.

Likely follow-ups
  • 2D peak. (Binary search on columns: take the max of the middle column, compare with its left and right neighbours, O(rows log cols).)
Search a matrix whose rows and columns are sorted. What is the best you can do?

If each row starts after the previous row ends, it is one sorted array: O(log(mn)) with the flat index. If rows and columns are only sorted on their own, use the staircase from the top-right: O(m + n), and each step removes a full row or column. Binary searching every row is O(m log n), which is better only when one dimension is much smaller.

How to answer

Ask which kind of matrix it is before coding. That question alone earns points.

Likely follow-ups
  • Count elements <= x. (Staircase in O(m + n), the core of k-th smallest in a sorted matrix.)
Design a time-based key-value store: set(key, value, t), get(key, t).

A hash map from key to a list of (t, value). Sets append (timestamps per key are increasing, so the list stays sorted). Get does upper_bound on times for t and steps back one; if that index is -1, return "". Set O(1) amortised, get O(log m).

How to answer

Name it a floor lookup. Offer TreeMap.floorEntry (Java) or map::upper_bound (C++) as the library version, and say why the list is enough here (append-only, ordered).

Likely follow-ups
  • Timestamps may arrive out of order. (Use a balanced tree per key, O(log m) set.)
  • Memory is limited. (Drop versions older than the oldest reader, like MVCC garbage collection.)
Why lo + (hi - lo) / 2 and not (lo + hi) / 2?

lo + hi can overflow a 32-bit int when both are above 230, giving a negative mid and a crash or wrong answer. This bug sat in the JDK's own binary search for years until Joshua Bloch described it in 2006. lo + (hi - lo) / 2 never exceeds hi. In Java, (lo + hi) >>> 1 also works because the unsigned shift treats the overflowed sum correctly.

How to answer

One sentence on overflow, one on the safe form. Python ints do not overflow, but say you would still write it this way.

Likely follow-ups
  • Does C have the same problem? (Yes for int; signed overflow is undefined behaviour in C.)
Your loop sometimes never ends. How do you debug it?

Check that every branch strictly shrinks the range. The usual cause: lo = mid with mid rounded down, so when hi = lo + 1, mid == lo and nothing changes. Fix by rounding up (mid = lo + (hi - lo + 1) / 2) or by turning the question into "first true" so the branch becomes lo = mid + 1. The other cause is mixing while lo <= hi with hi = mid.

How to answer

Trace the two-element case by hand. Every binary search bug shows up on n = 1 or n = 2.

Likely follow-ups
  • Write "last index with a[i] <= x" both ways. (first_true(a[i] > x) - 1, or the round-up version.)
Median of two sorted arrays in O(log(min(m, n))): what are you binary searching?

Not a value, a cut. Choose i elements from the shorter array A and j = (m + n + 1) / 2 - i from B, so the left side has half the elements. The cut is right when A[i - 1] <= B[j] and B[j - 1] <= A[i]. If A[i - 1] > B[j], i is too big; else if B[j - 1] > A[i], i is too small. That is a monotone predicate over i in [0, m], so binary search it. The median comes from the max of the left side and the min of the right side.

How to answer

Give the O(m + n) merge first, then the cut idea, then the edge sentinels (minus and plus infinity at the ends).

Likely follow-ups
  • K-th smallest of two sorted arrays. (Same cut with k instead of half.)
