  • Cue: reverse sub-lists of a linked list in place -> dummy head + node-before + 3-pointer reverse.
  • Insight: probe k ahead first; reverse with prev = after, so the outgoing seam fixes itself.
  • State: prevTail, kth (new head), first (new tail), after (next group).
  • Trap: stitch prevTail.next = kth, then prevTail = first (not kth); return dummy.next.
  • Cost: O(n) time, O(1) space; recursion O(n/k) stack; array copy O(n).
prev_tail = dummy
while (kth := advance(prev_tail, k)):      # None if fewer than k left
    first, after = prev_tail.next, kth.next
    prev, cur = after, first
    while cur is not after:
        cur.next, prev, cur = prev, cur, cur.next
    prev_tail.next, prev_tail = kth, first

The last group has fewer than k nodes. What happens to it?

  1. it is reversed
  2. it stays as it is
  3. it is dropped
  4. it is padded
Probe k nodes ahead first; if the probe runs out, stop and leave the tail alone.

After reversing a group, which node becomes prevTail for the next group?

  1. kth, the new head
  2. first, the old head that is now the group's tail
  3. after
  4. dummy
Setting prevTail = kth is the classic bug: the next stitch then cuts the list.

Why start the reversal with prev = after (the node after the group)?

  1. it is required by LeetCode
  2. the old head then points at the next group automatically
  3. to save one pointer
  4. to handle k = 1
The outgoing seam fixes itself; only the incoming seam (prevTail.next = kth) needs a write.
