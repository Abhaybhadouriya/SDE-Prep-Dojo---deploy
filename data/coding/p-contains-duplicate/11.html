Interview follow-ups

Solve it with O(1) extra space.

Sort in place and compare neighbours: O(n log n) time. Heap sort is truly O(1) extra; std::sort (introsort) uses O(log n) stack. If the input must not change, there is no O(1)-space method faster than O(n2) for arbitrary values.

How to answer

State the time-for-space trade and ask whether the array may be modified.

Likely follow-ups
  • Values are in 1..n? Then use the array itself: negate nums[|x| - 1], a negative slot means x was seen (LC 442).
Hash set or sort: which is faster in practice?

For n = 105 both are fast. The hash set wins asymptotically and can exit early, but every insert may touch a random cache line and allocate a node (unordered_set, HashSet<Integer> boxes each int). Sorting a contiguous int array is cache-friendly and allocation-free, so it is often competitive. Adversarial inputs can also force hash collisions.

How to answer

Say "expected O(n) vs O(n log n)", then mention constants: memory layout, allocation and early exit.

Likely follow-ups
  • How would you make the C++ set faster? reserve(n) to avoid rehashing, or an open-addressing table.
Now the two copies must be at most k indices apart.

That is LC 219. Keep a set of the last k values: before reading index i, remove nums[i - k - 1]; then check and insert as before. O(n) time, O(min(n, k)) space. Alternatively store value → last index and test i - last <= k.

How to answer

Reuse the same loop; the only change is that old values expire.

Likely follow-ups
  • And values may differ by up to t (LC 220)? Buckets of width t + 1; check the own bucket and both neighbours.
The IDs arrive as a stream too large to keep in memory.

Exact: hash-partition the stream to disk (value mod P into P files), then run the set check per file, since equal values always land in the same file. Or an external sort and a neighbour scan. Approximate: a Bloom filter answers "definitely new" or "maybe seen" in fixed memory; confirm a "maybe" against the disk partition if false positives matter.

How to answer

Ask whether a false "duplicate" is acceptable; that decides Bloom filter vs exact partitioning.

Likely follow-ups
  • Size the Bloom filter: about 10 bits per element gives roughly a 1% false-positive rate with 7 hash functions.
Values are 32-bit unsigned and memory is fine. Can you avoid hashing altogether?

A bitmap with one bit per possible value: 232 bits = 512 MB, test-and-set per element, strictly O(n) with no collisions. Worth it only when n is huge compared with that fixed cost; for the stated range (2·109 values, 250 MB) and n = 105, the hash set is far smaller.

How to answer

Compare memory: bitmap = range / 8 bytes, hash set = n times (key + overhead).

Likely follow-ups
  • Radix sort is the other no-hash O(n) option for fixed-width integers.
Return the repeated values (each once) instead of a boolean.

Use two sets: seen and dup. If x is in seen, add it to dup; otherwise add it to seen. Return dup. Or count with a map and keep the keys with count ≥ 2. No early exit any more, so it always reads all n values.

How to answer

Point out what the new output costs: the early exit is gone.

Likely follow-ups
  • In order of first repetition? Append to a list the moment a value first hits seen.
