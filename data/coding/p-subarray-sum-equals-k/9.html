  • Cue: count subarrays with sum k, negatives allowed -> prefix sum + count map.
  • Insight: sum(l..r) = pre[r+1] - pre[l]; at each r add seen[run - k].
  • State: run (prefix so far), count, seen{prefix: how many times}.
  • Trap: seed {0: 1}; look up BEFORE insert; counts not a set; no sliding window.
  • Cost: O(n) time, O(n) space; brute O(n²) with a running sum.
seen = {0: 1}; run = ans = 0
for x in a:
    run += x
    ans += seen.get(run - k, 0)      # key/seed change per variant
    seen[run] = seen.get(run, 0) + 1
return ans

run = 4, needs a prefix of 0, which is only there because of the seed.

Why is a sliding window wrong here?

  1. It is O(n²)
  2. k can be negative
  3. The array is not sorted
  4. Values can be negative, so the window sum is not monotonic in its size
Shrinking or growing must move the sum in a known direction for the window to be safe; negatives break that.

To find the LONGEST subarray with sum k instead, what changes?

  1. Store the first index of each prefix, seed {0: -1}, take max(r - first)
  2. Store counts and take the max count
  3. Use a sliding window
  4. Sort the array first
For the longest, the earliest occurrence of pre[l] is the best start, so keep only the first index (LC 325).
