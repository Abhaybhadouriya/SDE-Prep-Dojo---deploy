Approaches: brute -> better -> optimal

Hint 1

Where in the input can the largest square be?

Hint 2

If you always know where the largest remaining square is, which slot of the output should it go into?

1. Brute force - square, then sort

Idea: replace each element by its square and sort. Correct, three lines, and a fine opening sentence.

O(n log n)time
O(1) - O(n)space (sort's own)

What is wasted: the input is already sorted; the sort throws that information away.

2. Better - find zero, merge outward

Idea: binary-search (or scan) for the first non-negative index p. Then nums[p-1], nums[p-2], ... have increasing squares, and so do nums[p], nums[p+1], .... Merge these two runs like merge sort, writing from the smallest square forward. O(n), but you must handle "no negatives" and "no non-negatives" boundaries for both cursors.

3. Optimal - two pointers from the ends, fill from the back

lo, hi = 0, n - 1
for w in range(n - 1, -1, -1):
    if nums[lo]**2 > nums[hi]**2: out[w] = nums[lo]**2; lo += 1
    else:                         out[w] = nums[hi]**2; hi -= 1
O(n)time: one pass
O(1)extra space besides the output

Why it works: invariant: before each step, nums[lo..hi] are exactly the elements not yet written, and out[w+1..n-1] holds the largest squares in sorted order. Because the array is sorted, the element with the largest absolute value in nums[lo..hi] is either the most negative one (nums[lo]) or the most positive one (nums[hi]). So the larger of the two end squares is the largest remaining square, and it belongs in slot w. Writing it and shrinking the range keeps the invariant. Filling from the back is the trick: you always know the largest remaining square, but not the smallest (that is somewhere in the middle, near zero).

The top community solutions on LeetCode all converge on this form; some build the answer with a deque or by reversing at the end, which works but is extra work (see the links below).
