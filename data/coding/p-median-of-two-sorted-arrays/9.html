  • Cue: two sorted arrays + median / k-th + O(log) → binary search the cut.
  • Insight: pick i from the shorter array, j = half - i; checks a[i-1] ≤ b[j], b[j-1] ≤ a[i].
  • State: lo = 0, hi = m (inclusive), half = (m + n + 1) / 2, ±inf sentinels.
  • Trap: search the SHORTER array; hi = m not m - 1; divide by 2.0.
  • Cost: O(log min(m, n)) time, O(1) space; merge is O(m + n).
lo, hi = 0, m                      # cut positions 0..m
while lo <= hi:
    i = (lo + hi) // 2; j = half - i
    if ok(i, j): return answer(i, j)
    if too_many(i, j): hi = i - 1
    else: lo = i + 1

Quick quiz

a = [1, 2], b = [3, 4]. Which i (count taken from a) is the valid cut?

  1. 0
  2. 1
  3. 2
  4. none
half = 2. Taking both from a gives left {1, 2}, right {3, 4}: a[1] = 2 ≤ b[0] = 3. So i = m = 2, which is why hi must start at m.

a[i-1] > b[j]. Where does the search go?

  1. hi = i - 1
  2. lo = i + 1
  3. j = j - 1 only
  4. stop, it is valid
A value from a sits left of a smaller value from b, so a gave too many: shrink i.

Why binary-search the shorter array?

  1. It is faster to sort
  2. So that j = half - i always stays within 0..n
  3. Because the median is always in it
  4. It does not matter
With m ≤ n, half - i is between 0 and n for every i in 0..m. It also makes the cost O(log min).
