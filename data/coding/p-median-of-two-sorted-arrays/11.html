Interview follow-ups

Find the k-th smallest element instead of the median.

Same search with half = k. The range for i becomes [max(0, k - n), min(k, m)] so that j stays valid. Return max(a[i-1], b[j-1]). Alternatively, the recursive "drop k/2 elements from the array with the smaller k/2-th value" method runs in O(log k).

How to answer

Say the median is just k = half, so the general k-th is a two-line change: the size of the left part and the bounds of i.

Likely follow-ups
  • k-th across three or more arrays? (Value-space binary search with a count, or a heap.)
What if there are k sorted arrays, not two?

The cut trick has k - 1 free variables, so it no longer reduces to one search. Binary-search on the value instead: for a candidate x, count elements ≤ x with upper_bound in each array (O(k log n)); find the smallest x with count ≥ target. Total O(k log n log V). A min-heap merge of the first half is O(N/2 log k).

How to answer

Name the switch from "search the index" to "search the value and count"; it works on any number of sorted sources.

Likely follow-ups
  • Distributed shards that cannot be copied? (Same value search, each shard returns a count: O(log V) rounds.)
The numbers arrive as a stream. Report the running median.

Keep a max-heap for the lower half and a min-heap for the upper half, sizes equal or the lower one bigger by one. Each insert is O(log n), the median is O(1). This is the same "cut" idea, maintained instead of searched (LC 295).

How to answer

Connect it: "the heaps hold the left and right part of the cut, and their tops are max(left) and min(right)".

Likely follow-ups
  • Sliding window median (LC 480): add lazy deletion or two multisets.
Why is it O(log min(m, n)) and not O(log(m + n))?

The search range is only the m + 1 cut positions of the shorter array. log min(m, n) ≤ log(m + n), so it meets the requirement with room to spare.

How to answer

Mention that this is also why we swap: searching the longer array costs more and breaks the j bounds.

Likely follow-ups
  • Can you do better than log? (No in the comparison model: you must locate a position among m + 1 choices.)
The arrays are huge files on disk. What changes?

Nothing in the algorithm: each probe reads four values (a[i-1], a[i], b[j-1], b[j]), so the cut search does O(log m) random reads. A merge would read half of both files sequentially. For very large data, O(log) seeks beat O(N) streaming.

How to answer

Count I/O, not CPU: four reads per probe, about 40 probes for a billion elements.

Likely follow-ups
  • The files are compressed in blocks? Keep a small index of each block's first value and search that first.
Return the median as an exact fraction / avoid floating point.

Return the pair (sum of the two middles, 2) or the single middle. With values up to 10^6 the sum fits easily in 32 bits; for full 32-bit inputs use a 64-bit sum before dividing.

How to answer

Point to the overflow: INT_MAX + INT_MAX overflows int, so add as long or as double.

Likely follow-ups
  • Round half up vs banker's rounding? Ask which the product needs.
