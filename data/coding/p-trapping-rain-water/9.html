  • Cue: per-index answer needs best-to-the-left AND best-to-the-right -> prefix/suffix max.
  • Insight: water[i] = min(maxL, maxR) - h[i]; the lower side is always the limit.
  • State: l, r, leftMax, rightMax, water.
  • Trap: settle the side with the LOWER bar; update its max before adding.
  • Cost: O(n) time, O(1) space; arrays O(n) space; brute O(n²).
l, r = 0, n - 1
while l < r:
    if a[l] < a[r]:
        best_l = max(best_l, a[l]); use(best_l, l); l += 1
    else:
        best_r = max(best_r, a[r]); use(best_r, r); r -= 1

Two pointers: h[l] == h[r]. Which side do you settle?

  1. only the left side is correct
  2. only the right side is correct
  3. either side; the equal bars bound each other
  4. neither; move both
With equal heights the max on the far side is at least as high as the current side's max, so settling either side is safe. Most code uses else for that case.

Why can the pointer at the lower bar be settled without knowing the full max on the other side?

  1. the other side's max is at least that high, so min(maxL, maxR) is already known
  2. water never collects at the lower side
  3. the lower bar always holds zero water
  4. the array is sorted
If leftMax <= h[r] <= rightMax, the limit at l is leftMax no matter what lies between.

Water at index i is min(maxL, maxR) - h[i]. Must maxL include h[i] itself?

  1. no, it would make the answer negative
  2. yes, so the result is never below 0
  3. only at the edges
  4. it makes no difference to the code
Updating leftMax with h[i] before adding keeps min(...) - h[i] >= 0, so no extra clamp is needed.
