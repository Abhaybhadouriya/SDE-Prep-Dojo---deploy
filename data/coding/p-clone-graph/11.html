Interview follow-ups

Do it without recursion.

BFS with a queue (rung 4), or DFS with an explicit stack. Create and register the copy when a node is first discovered, and wire copy[cur].neighbors.append(copy[nb]) for every neighbour as you scan cur. O(V + E) time, O(V) space (on the heap).

How to answer

Point out that the "register on discovery" rule is the same as the recursive "register before neighbours" rule.

Likely follow-ups
  • Does the neighbour order still match? (Yes: each list is appended in scan order.)
The graph may be disconnected and you get a list of all nodes.

Keep one map across all components and start a traversal from every node not yet in the map. Return the list of copies in the same order. Still O(V + E).

How to answer

Same outer loop as counting connected components.

Likely follow-ups
  • How many traversals start? (One per component.)
The graph is directed and may have self-loops. Does the code change?

No. A self-loop u -> u hits the map on the very first neighbour lookup and appends u' to itself. Direction does not matter because we copy each adjacency entry as it is. With a directed graph, "given one node" only reaches its reachable set, which is exactly what should be copied.

How to answer

Trace the self-loop in one line to show the early map entry handles it.

Likely follow-ups
  • Repeated edges? (Two entries in the list, two entries in the copy: still exact.)
Values are unique here. Can you key the map by value instead of node?

Yes, and with values in 1..100 you can even use an array of size 101 instead of a hash map. But it relies on the uniqueness guarantee; identity keys work for any graph, so say both and pick identity unless memory or speed matters.

How to answer

Name the assumption explicitly: "only because values are unique".

Likely follow-ups
  • Python: dict keys on objects use identity hashing by default, so node as a key is fine.
Serialise the graph to a string and rebuild it on another machine.

Assign each node an id during a traversal (the map now stores node -> id), emit id: val, [neighbour ids] lines, and on the other side create all nodes first, then wire lists by id: rung 2's two-pass method. This is the adjacency-list format the judge itself uses.

How to answer

Show that the map moves from "address -> address" to "address -> id", like pointer swizzling.

Likely follow-ups
  • Why can a copy not just reuse the raw addresses? (They are meaningless in another address space.)
Clone it with multiple threads.

The shared map becomes the contention point: use a concurrent map with an atomic "put if absent" so exactly one thread creates each copy, and let workers pull nodes from a shared queue. Each copy's neighbour list is written only by the thread that scanned that original node, so lists need no lock. Mention that for 100 nodes the overhead is not worth it.

How to answer

Find the invariant (one copy per node) and make that single step atomic.

Likely follow-ups
  • How do you know when all workers are done? (Count of pending nodes reaching 0.)
