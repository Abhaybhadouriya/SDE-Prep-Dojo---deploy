The story: the guessing game on a shelf

Explain like I'm 5

You are looking for the book with number 47 in a strange library. At the door stands a helper holding book 50. "47 is smaller than mine," she says, "go to the left door." Behind the left door stands a helper with book 30: "47 is bigger, go right." The next helper holds 47. Found it, after three questions, even though the library has a thousand books.

Every helper follows the same rule: every book behind my left door is smaller than mine, every book behind my right door is bigger. That rule is a binary search tree. Each question throws away a whole side of the library, just like guessing a number between 1 and 100 by asking "higher or lower?".

There is one catch. If the books were put on the shelves in sorted order, every helper sends you right, and you end up walking past all thousand helpers. The rule is the same, but the shape went bad.

From your world

You have used BSTs in the kernel for years: struct rb_node (lib/rbtree.c) is a self-balancing BST embedded in your own struct. The CFS scheduler kept runnable tasks in one ordered by virtual runtime and picked the leftmost node to run next (EEVDF, its successor since Linux 6.6, still uses an augmented rbtree); hrtimers and epoll use the same tree. When you write rb_insert code you walk down with if (key < this->key) link = &(*link)->rb_left; else link = &(*link)->rb_right;, which is exactly the insert on this page. Interviews use the plain, unbalanced version, so the rebalancing part of rb_insert_color is not on the menu, but knowing that it exists is a good answer to "what if the tree gets skewed?".
