Interview questions

Is checking "left child < node < right child" at every node enough to validate a BST?

No. The rule covers whole subtrees: in root 6, right child 9, and 9's left child 4, every parent-child pair is fine, yet 4 is in the right subtree of 6 and smaller than 6. Either pass an open interval (lo, hi) down from the ancestors, or walk inorder and require each value to be strictly bigger than the previous one. Both are O(n) time and O(h) space.

How to answer

Draw the 6-9-4 counterexample first; it shows you understand the rule. Then code one version, and mention the INT_MIN/INT_MAX trap and the strict comparison for duplicates.

Likely follow-ups
  • Without recursion? (Iterative inorder with a stack, comparing with prev.)
  • In O(1) extra space? (Morris inorder with the same prev comparison, letting it finish to remove threads.)
Design a BST iterator with next() in O(1) average time and O(h) memory.

Keep a stack with the unvisited left spine. The constructor pushes the root and all its left descendants. next() pops the top (the smallest unvisited key) and pushes the left spine of its right child; hasNext() checks the stack. Each node is pushed and popped exactly once over the full iteration, so n calls cost O(n) in total: O(1) amortized. The stack never holds more than one root-to-leaf path, so memory is O(h).

How to answer

Say "it is iterative inorder, paused after each visit". Explain amortized O(1) with the push-once, pop-once argument, not by hand-waving.

Likely follow-ups
  • Add prev() as well? (Keep a list of returned values plus an index; move back in the list, and only advance the stack when the index is at the end. That is LeetCode 1586.)
  • Reverse iterator? (Mirror it: push the right spine, after popping push the left child's right spine.)
Kth smallest element in a BST. What if the tree changes often and kth is asked often?

Base answer: iterative inorder that stops at the kth pop, O(h + k) time, O(h) space. For frequent queries on a changing tree, augment every node with the size of its subtree. Query: with L = size(left), if k == L + 1 return the node; if k <= L go left; otherwise go right with k -= L + 1. Insert and delete update sizes along their path, so every operation is O(h). Use a balanced tree (and update sizes during rotations) to make that O(log n).

How to answer

Give the simple version, then upgrade only when asked. Name it: an order-statistic tree. Mention that the same augmented field gives "rank of a key" in O(h).

Likely follow-ups
  • Kth largest? (Reverse inorder, or kth smallest with k' = n - k + 1.)
  • Can you avoid modifying nodes? (Keep a separate ordered structure, or a Fenwick tree over compressed keys if the key universe is known.)
Delete a node with two children. Why the inorder successor, and why does deleting it stay simple?

The node needs a replacement key that is bigger than everything in its left subtree and smaller than everything else in its right subtree. The inorder successor (leftmost node of the right subtree) is exactly that, and so is the predecessor. Copy its key into the node, then delete it from the right subtree. The successor is a leftmost node, so it has no left child: deleting it is the 0- or 1-child case and the recursion stops there. Total O(h).

How to answer

List the three cases before coding. Use the recursive "return the new subtree root" style; it handles deleting the root with no special case.

Likely follow-ups
  • Other code holds pointers to nodes; can you still copy keys? (No: relink the successor node into the deleted node's position, as rb_erase does.)
  • Iteratively? (Track the parent link pointer, like struct node **link in C, and splice through it.)
Two nodes of a BST were swapped. Find and fix them. Can you do it in O(1) space?

In the inorder sequence, the swap causes one dip (neighbours swapped) or two dips (far apart). Track prev during inorder; at a dip (prev > cur) set first = prev if first is unset, and always set second = cur. Swap first and second values at the end. With a stack this is O(n) time and O(h) space; with Morris inorder it is O(1) extra space, because the dip check needs only prev, first and second.

How to answer

Draw a sorted array, swap two values, and show the dips. Then show the neighbour case so the "always update second" rule makes sense. Mention Morris at the end, with the warning that it temporarily modifies the tree.

Likely follow-ups
  • What if more than two nodes are out of place? (Collect inorder, sort the values, write them back in inorder: O(n log n).)
  • Could you stop early? (Not safely with Morris; with the stack version you could stop after the second dip, but you cannot know there is no later dip without finishing.)
Find the inorder successor of a node when nodes have no parent pointer.

Walk from the root. If p's key is smaller than the current node, the current node is bigger than p, so it is a candidate; remember it and go left looking for a smaller candidate. Otherwise go right. When the walk ends, the remembered candidate is the successor (or null if p is the maximum). O(h) time, O(1) space. With parent pointers: if p has a right child, return the leftmost node there; otherwise climb until you come up from a left child, and that parent is the answer.

How to answer

Explain why every left turn is a candidate and why the last one is the best. Then give the parent-pointer variant; it is a common second question.

Likely follow-ups
  • Predecessor? (Mirror: a node is a candidate when p's key is bigger; then go right.)
  • Ceiling of an arbitrary key that may not be in the tree? (Same walk, with key <= node as the candidate test.)
Return the k values in a BST closest to a target. Do better than O(n).

Inorder makes it "k closest in a sorted array", so O(n) with a sliding window is the baseline. To get O(h + k), seed two stacks with one search for the target: a predecessor stack (nodes with key <= target, the path where you went right) and a successor stack (key > target, where you went left). Each stack behaves like a BST iterator, one moving down in value and one moving up. Then merge like two pointers: take whichever top is closer, advance that iterator, k times.

How to answer

State the O(n) window first and code it if time is short. Then describe the two iterators clearly; the code is two copies of the iterator, mirrored.

Likely follow-ups
  • Only one closest value? (A single downward walk, O(h): the answer is on the target's search path.)
  • k is close to n? (Then the O(n) window is just as good and simpler.)
When would you not write your own BST in an interview, and what do you use instead?

When the BST is only a means to an end (ordered keys with floor, ceiling, delete), use the language's balanced tree: C++ std::set/std::map (red-black trees) with lower_bound, Java TreeMap/TreeSet with floorKey/ceilingKey. Python and Go have no built-in: use a sorted list with bisect or sort.Search (O(n) inserts, fine for moderate n), or mention sortedcontainers. For rank queries ("how many smaller after me"), a Fenwick tree over compressed values is simpler than an augmented BST.

How to answer

Show that you know the guarantees (O(log n) because the library tree is balanced) and the API names. Write your own only when the question is about the tree itself.

Likely follow-ups
  • How does a red-black tree stay balanced? (Colour rules make the longest path at most twice the shortest; inserts and deletes fix violations with O(1) rotations and recolouring along the path.)
  • Why do databases use B-trees instead? (Wide nodes match disk pages: far fewer levels, so fewer page reads.)
