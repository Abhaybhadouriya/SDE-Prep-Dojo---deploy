Interview Q&A about the round itself

Questions candidates ask about coding rounds, and questions interviewers ask that are not about the algorithm.

I have seen this exact problem before. Should I say so?

Yes, briefly: "I have seen something close to this." Then solve it properly, with clarifying questions and a dry run. Interviewers expect common problems to be familiar; what they grade is your reasoning. Pretending to discover a famous trick on the spot often looks rehearsed.

How to answer

Be honest, then over-deliver on explanation and testing. If they switch problems, that is normal and not a penalty.

Likely follow-ups
  • "Then let's change it: the input is now a stream." Be ready for the variant.
I cannot find the optimal solution. What should I do with 20 minutes left?

Code the best solution you have, cleanly, and say its complexity. A working O(n log n) solution with tests beats an unfinished O(n) idea. While coding, mention where the waste is ("we sort only to find the minimum; a heap might avoid that"), which often prompts a hint.

How to answer

Ask: "Would you like me to code this version, or keep looking for better?" Many interviewers will say code it.

Likely follow-ups
  • "Where is the bottleneck in your solution?"
  • "What data structure would remove it?"
Which language should I use: C, C++, Java, Python or Go?

The one you write fastest with the fewest bugs, as long as it has a standard library with a hash map, a heap and a sorted map. That rules out plain C in practice. For a C engineer, C++ is the shortest jump (STL unordered_map, priority_queue, map). Python is the shortest to write. Java and Go are fine but wordier for heaps.

How to answer

Pick one language and use it for every practice problem for at least a month. Know its heap, sort with a custom comparator, and integer overflow rules by heart.

Likely follow-ups
  • "Why is Python's heap a min-heap only, and how do you get a max-heap?" (push negatives)
The interviewer asks "What is the complexity?" What exactly should I say?

Time and space, each with the variables named and the reason: "O(n log n) time because of the sort; the scan after it is O(n). O(n) extra space for the output, O(1) besides that." Mention the hash map average case if you used one.

How to answer

Point at the line of code that dominates. Say whether the input itself counts towards space.

Likely follow-ups
  • "What is the worst case for the hash map?"
  • "Can you get the space down to O(1)?"
How is an SDE-3 coding round different from an SDE-2 one?

The question is often the same difficulty (our reports show Medium at about 62% for both levels; SDE-3 has more Hard, 29% vs 20%). The difference is the follow-ups and the bar on judgement: handling a stream or huge input, making it thread-safe, choosing between two optimal approaches by their constants and memory, and writing code with clear interfaces.

How to answer

Practise every problem to its last follow-up. After solving, ask yourself: "What if n were 109? What if it were distributed over 100 machines?"

Likely follow-ups
  • "How would you test this in production?"
There is no compiler in the editor. How do I test my code?

Dry-run it by hand. Take your small example, keep a table of every variable, and step through line by line. Then test the edge cases you listed at the start: empty, one element, all equal, the largest value. Fix bugs out loud, without rewriting from scratch.

How to answer

Practise without a compiler for a week before a loop. The stress-test template above is for training; the hand trace is for the room.

Likely follow-ups
  • "What test would break your solution?"
What is an Amazon Bar Raiser looking for in a coding round?

The Bar Raiser is an experienced interviewer from outside the hiring team whose job is to keep the hiring bar high across Amazon. In the coding part they grade the same rubric, often with a harder problem or a deeper follow-up, and they also probe Leadership Principles such as Dive Deep and Insist on the Highest Standards through how you handle bugs and trade-offs.

How to answer

Treat it as a normal round, but test more carefully and explain trade-offs more explicitly. Read Amazon's own interview pages (linked below).

Likely follow-ups
  • "Tell me about a time you found a bug in production." (Leadership Principles in the same slot)
