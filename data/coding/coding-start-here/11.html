Common mistakes

  • Coding in the first two minutes. You solve a different problem from the one asked, or miss that the input can be empty. Clarify first, every time.
  • Hiding the brute force. Candidates skip it because it feels weak. Saying it costs 20 seconds, proves you understand the problem, and gives you a fallback.
  • Going silent. The interviewer cannot give credit for thinking they cannot hear. If you are stuck, say what you are trying.
  • Saying "done" without a dry run. Most bugs (off-by-one, wrong initial value, not updating a pointer) show up in a 2-minute trace of your own example.
  • Ignoring the constraints. An O(n²) answer for n = 105 is a fail even if it is correct.
  • Memorising solutions instead of patterns. The interviewer changes one detail and the memorised answer falls apart. Learn the template for the variant, not the code for the title.
  • Grinding 600 problems without revision. 150 problems you can redo cold beat 600 you saw once. Use the revision queue.
