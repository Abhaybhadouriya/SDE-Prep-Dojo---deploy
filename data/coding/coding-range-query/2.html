The Fenwick tree (binary indexed tree)

A Fenwick tree is an array t[1..n] (1-based on purpose) where t[i] holds the sum of a block that ends at i. The length of the block is the lowest set bit of i, written lowbit(i) = i & -i. So t[6] (binary 110, lowest bit 2) holds a[5] + a[6]; t[8] (1000) holds a[1..8]; every odd i holds just a[i].

Two loops, each over the bits of i:

  • Prefix sum of a[1..i]: add t[i], then jump to the block just before it with i -= i & -i (clear the lowest bit). Stop at 0.
  • Add delta to a[i]: add delta to t[i], then jump to the next block that also covers i with i += i & -i. Stop when i > n.

Click through both on the picture above:

  1. Query: sum of a[1..7]. Start with i = 7 and sum = 0. In binary 7 is 0111. Each step takes the node t[i] and then removes the lowest set bit of i.
  2. i = 7 (0111): add t[7] = 1, which already holds a[7..7]. sum = 1. Then i -= i & -i drops the lowest set bit: i = 6.
  3. i = 6 (0110): add t[6] = 25, which already holds a[5..6]. sum = 26. Then i -= i & -i drops the lowest set bit: i = 4.
  4. i = 4 (0100): add t[4] = 13, which already holds a[1..4]. sum = 39. Then i -= i & -i drops the lowest set bit: i = 0. i is 0, so we stop.
  5. Three nodes covered seven cells: one per set bit of 7. A prefix query reads at most log2(n) + 1 nodes.
  6. Update: add 10 to a[3]. Now go the other way: every node whose bar covers index 3 must change. Start at i = 3 and add the lowest set bit each time.
  7. i = 3 (0011): t[3] covers a[3..3], so it gets +10. Then i += i & -i: i = 4.
  8. i = 4 (0100): t[4] covers a[1..4], so it gets +10. Then i += i & -i: i = 8.
  9. i = 8 (1000): t[8] covers a[1..8], so it gets +10. Then i += i & -i: i = 16. That is past n = 8, so we stop.
  10. Only 3 nodes changed (t[3], t[4], t[8]). A plain prefix array would have to rewrite P[3..8], six entries; with n = 105 that is the difference between 17 steps and 100,000.
class Fenwick:                      # 0-based API, 1-based inside
    def __init__(self, n):
        self.n, self.t = n, [0] * (n + 1)
    def add(self, i, delta):         # a[i] += delta
        i += 1
        while i <= self.n:
            self.t[i] += delta
            i += i & -i              # next block that covers i
    def prefix(self, i):             # a[0] + ... + a[i-1]
        s = 0
        while i > 0:
            s += self.t[i]
            i -= i & -i              # block just before
        return s
    def range_sum(self, l, r):       # a[l..r]
        return self.prefix(r + 1) - self.prefix(l)

Why does it work? Write i in binary. Clearing the lowest bit again and again splits 1..i into at most log2(n) + 1 blocks whose lengths are exactly the set bits of i (for 7 = 4 + 2 + 1: blocks of 1, 2 and 4). That is a disjoint cover, so the sum is right. For the update, the blocks that contain a fixed index i are exactly the ones you reach by adding the lowest bit: each jump goes to the next larger block that still reaches back over i. You do not need to prove it in an interview, but you should be able to say "one node per bit, both ways".

Notice that a range sum is two prefix sums subtracted, just like the prefix array. That is why a Fenwick tree only does operations you can undo. Range max cannot be built from two prefix maxima, which is where the segment tree comes in.

From your world

i & -i is the two's-complement trick you already know from bitmap allocators: it isolates the lowest set bit, the same bit that ffs(), __builtin_ctz or the x86 TZCNT / BSF instruction finds. A Fenwick tree is a sum table indexed by that bit. Because t[] is one flat array with no pointers, it is also cache-friendly and trivially serialisable, the way you would like a kernel structure to be.
