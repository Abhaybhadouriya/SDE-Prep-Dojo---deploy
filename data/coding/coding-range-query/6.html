The ordered map: floor and ceiling

Many "range" interview problems are not about array indices at all. The positions are times or interval ends up to 109, and you insert them one at a time. A balanced binary search tree keyed by those positions (a red-black tree in TreeMap and std::map) answers the two questions that matter in O(log n):

  • floor(x): the largest key <= x (Java floorKey/floorEntry; C++ prev(upper_bound(x))).
  • ceiling(x): the smallest key >= x (Java ceilingKey; C++ lower_bound(x)).

My Calendar I

My Calendar I: bookings arrive as half-open intervals [start, end); accept one only if it overlaps nothing already accepted. Keep a map from start to end. Since the accepted bookings never overlap, they are sorted by start and by end, so the new booking only has to be compared with two neighbours: the one that starts at or before it (floor) and the one that starts at or after it (ceiling).

map<int, int> ev;                                    // start -> end, never overlapping
bool book(int start, int end) {
    auto next = ev.lower_bound(start);                // ceiling: first start >= start
    if (next != ev.end() && next->first < end) return false;
    if (next != ev.begin() && prev(next)->second > start) return false;   // floor
    ev[start] = end;
    return true;
}

Two comparisons, O(log n) per booking. The O(n) answer "scan every booking" is fine for the given limit of 1,000 calls; say it first, then say the map makes it O(log n), which is what an interviewer with a follow-up "now 106 bookings" wants.

My Calendar II and III: a sparse difference array

When overlaps are allowed but counted ("no triple booking", "what is the largest overlap so far"), keep a map from time to change: +1 at start, -1 at end. Walking the keys in order with a running total gives the number of active bookings at every moment: exactly the difference array, but stored only at the times that matter.

That sweep is O(n) per booking, so O(n²) overall: fine for 400 or 1,000 calls. If asked for better, the answer is a lazy segment tree over compressed (or dynamically created) times with "range add, global max": O(log n) per booking.

In Python and Go, say out loud that the sorted-list insert is O(n) (a memmove, which is fast in practice) and that a balanced tree would make it O(log n). Interviewers accept that; they do not expect you to write a red-black tree. The same floor lookup solves Time Based Key-Value Store and Snapshot Array, where the timestamps only grow so a plain list plus binary search is already sorted.

From your world

The kernel is full of this. CFS kept runnable tasks in a red-black tree keyed by vruntime and cached the leftmost node; memory areas of a process were looked up by address in an rbtree (the maple tree replaced it in Linux 6.1); and include/linux/interval_tree_generic.h is an augmented rbtree that answers "which intervals overlap [a, b]?" for the reverse-mapping code in mm. A "find the VMA that contains this address" lookup is exactly floor(addr) followed by "does it end after addr?", the same check as My Calendar.
