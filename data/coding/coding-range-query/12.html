Interview questions

Design a class with update(i, val) and sumRange(l, r). Both are called many times.

Prefix sums make updates O(n); a plain array makes queries O(n). A Fenwick tree makes both O(log n): keep a copy of the array, and on update add the difference val - a[i] to the tree; sumRange is prefix(r + 1) - prefix(l). A segment tree gives the same bounds and also supports min or max. Build is O(n log n) by n adds, or O(n) with the parent-push trick.

How to answer

Start with the table: build, update, query for array, prefix sums, Fenwick, segment tree. Ask about the ratio of updates to queries; if updates are rare, rebuilding prefix sums is a valid answer.

Likely follow-ups
  • The same on a 2D matrix. (2D Fenwick, nested lowbit loops, O(log R · log C).)
  • Range min instead of sum. (Segment tree; Fenwick cannot undo a min.)
  • Many updates at once, then a read. (Difference array.)
For each element, count the smaller elements to its right.

Compress the values to ranks, walk from right to left, and keep a Fenwick tree of counts per rank. At i, the answer is prefix(rank[i]) (ranks strictly below), then add 1 at rank[i]. O(n log n) time, O(n) space. The alternative is merge sort: while merging, every element taken from the left half gains the number of right-half elements already placed. Both are O(n log n); the Fenwick version is shorter to write.

How to answer

Say the O(n²) double loop, then "this is counting inversions per element", then pick BIT or merge sort and explain why compression is needed (negatives, large range).

Likely follow-ups
  • Count pairs with a[i] > 2 a[j] (Reverse Pairs). (Compress both x and 2x, or a merge-sort count before merging.)
  • Count teams of three with increasing ratings. (For each middle: smaller-left times larger-right, plus the decreasing case.)
My Calendar I: accept a booking only if it does not overlap. Make it O(log n) per booking.

Keep accepted bookings in an ordered map from start to end. Because they never overlap, the only candidates for a clash are the floor (latest start <= new start) and the ceiling (earliest start >= new start). Reject if the floor ends after the new start, or the ceiling starts before the new end. Insert otherwise. O(log n) per booking, O(n) space. In Python or Go use a sorted list with binary search and note the O(n) insert.

How to answer

Give the O(n) scan first, then the "only two neighbours matter" insight with a picture of the timeline. State that intervals are half-open, so touching is allowed.

Likely follow-ups
  • Allow double booking but not triple (My Calendar II). (Keep a second list of overlaps, or a +1/-1 map and a sweep.)
  • Return the maximum overlap after each booking (My Calendar III). (+1/-1 map and a sweep, or a lazy segment tree for O(log n).)
  • Many rooms: which room is free? (That is Meeting Rooms II / a heap of end times, see intervals.)
Fenwick tree vs segment tree: when do you pick which?

Fenwick: about ten lines, n + 1 slots, very fast, but only for operations with an inverse (sum, count, xor), because a range is two prefixes subtracted. Segment tree: 2n slots iterative (4n recursive), handles any associative operation (min, max, gcd, "max with index"), supports descending to find the first position meeting a condition, and extends to lazy range updates. Default to Fenwick for sums and counts, segment tree for everything else.

How to answer

Name the deciding property: "can I undo the operation?". Then give one problem for each side.

Likely follow-ups
  • Can a Fenwick tree do prefix max? (Yes, if values only increase at each index; range max, no.)
  • What is the memory for n = 106? (Fenwick 8 MB of int64; iterative segment tree 16 MB.)
Range Module: track half-open ranges with add, remove and query. What structure, and what are the edge cases?

An ordered map from start to end of disjoint, non-touching intervals. addRange(l, r): find the floor of l; if it reaches l, extend l to its start; then remove every interval whose start is <= r, extending r to the largest end seen; insert [l, r). removeRange splits the intervals that stick out on either side. queryRange(l, r): the floor of l must exist and its end must be >= r. Each call is O(log n) plus the intervals it removes, so amortised O(log n). A lazy segment tree over compressed coordinates also works but is heavier.

How to answer

Draw the number line with three existing intervals and walk through add and remove with a range that overlaps two of them. Be explicit about touching intervals ([1, 3) and [3, 5) merge on add).

Likely follow-ups
  • Count the covered integers (Count Integers in Intervals). (Keep a running total while merging.)
  • Stream of numbers into disjoint intervals. (Same merge with floor and ceiling.)
Range add and range sum, both up to 105 times. Explain lazy propagation.

A segment tree where each node stores the sum of its range and a pending "add v to all my cells" tag. A range add stops at the O(log n) nodes fully inside the range: it increases their sum by v times their length and adds v to their tag. Any later operation that must go below a tagged node first pushes the tag to both children. Queries and updates are both O(log n). For add-only updates, two Fenwick trees (one for v, one for v times i) give the same result in fewer lines.

How to answer

Explain why the naive range update is O(n), then "do the work at the highest node that fully covers the range, owe the rest". Mention that tags must compose: add then add is one add; assign must clear a pending add.

Likely follow-ups
  • Range assign plus range max (Falling Squares). (Tag = assigned value; with n = 1,000 an O(n²) scan is fine.)
  • The coordinates are up to 109. (Compress offline, or create nodes on demand: a dynamic segment tree.)
Time Based Key-Value Store: set(key, value, timestamp) and get(key, timestamp) returns the value with the largest timestamp <= the given one.

A hash map from key to a list of (timestamp, value). Timestamps for set are strictly increasing, so each list is already sorted: get is a floor lookup by binary search, O(log m). If timestamps could arrive out of order, use a TreeMap per key (floorEntry). O(1) set, O(log m) get.

How to answer

Point out the guarantee that timestamps increase; it is why a list beats a tree here. Then write the binary search for "last index with ts <= t" carefully (upper_bound minus one).

Likely follow-ups
  • Delete old versions to save memory. (Trim the front of each list, or a ring buffer per key.)
  • Snapshot Array. (The same per index, keyed by snapshot id.)
Count subarrays whose sum lies in [lower, upper].

With prefix sums, a subarray ending at j is good when an earlier prefix P[i] lies in [P[j+1] - upper, P[j+1] - lower]. Walk left to right and count earlier prefixes in that window: compress all prefix values (and the two bounds per step), and keep a Fenwick tree of counts, two prefix queries per step: O(n log n). Merge sort on the prefix array gives the same bound: while merging, for each left-half prefix move two pointers in the right half.

How to answer

Reduce it to "count earlier values in a range", which is the counting-Fenwick pattern. Note that a hash map (as in Subarray Sum Equals K) only works for an exact target, not a range.

Likely follow-ups
  • Values are all positive. (Two sliding windows: atMost(upper) - atMost(lower - 1), O(n).)
