Interview Q&A for the Uber loop

Users want an alert when a stock moves 5% from yesterday's close. Where does each price tick go?

Ticks arrive from the exchange feed into a stream (for example Kafka, partitioned by symbol). A detector service keeps, per symbol, the close price and a sorted list of subscriber thresholds in memory. For each tick it finds only the thresholds that were just crossed (a range lookup, not a scan), and emits "alert events" for those. A notification service looks up user details and sends push/SMS. The database is touched only for those few crossed alerts, never per tick.

How to answer

Say the hot-path rule first ("no DB call per tick"), then draw feed, stream, detector, notifier. Mention partitioning by symbol so one detector owns a symbol.

Likely follow-ups
  • A detector instance crashes: how do you rebuild its in-memory index?
  • How do you avoid sending the same alert twice?
  • One symbol is 100x hotter than the rest; what now?
Now the alert is "moved X% within the last hour / day / week". What changes?

"Move within a window" needs the window's min and max, not just the close. Keep per-symbol roll-ups at a few granularities (per minute, per hour, per day) and use a monotonic deque or pre-aggregated buckets to get the min and max of the window cheaply. For long windows (month, year), use the daily buckets from a time-series store. Each subscription stores its window and percentage; group subscriptions by (symbol, window) so one window computation serves many users.

How to answer

Name the data needed (min/max over window), then the structure, then the storage per granularity. Show you know the cost grows with the number of distinct windows, not users.

Likely follow-ups
  • Remove a subscription once it triggers or after a month: how?
  • Up versus down moves?
Explain geohash to someone who is not an engineer, then say why it helps the Uber Eats home page.

Cut a map into 32 squares and give each a letter. Cut each square again into 32 and add a second letter. Keep going. A longer code means a smaller square, and places that share the first few letters are close to each other. For the home page, you take the user's code, look up restaurants with the same prefix (plus the 8 neighbouring squares, for edges), and rank them. A prefix lookup on an index is fast, unlike computing the distance to every restaurant.

How to answer

Analogy first, then the edge problem (neighbours), then the alternative (quadtree adapts to density) and when you would pick it.

Likely follow-ups
  • Restaurants close at night: do you rebuild the quadtree?
  • Latency target drops to 50 ms; what do you cache?
Design a live driver heat map. How exactly does Redis get the data to the browser?

Driver apps send location every few seconds to an ingest service, which writes to a stream. A stream job maps each point to a geo cell (geohash or H3) and keeps counts per cell over a sliding window. It writes the latest counts to Redis (a hash per city) and publishes a small "city X changed" message on a Redis pub/sub channel. WebSocket servers subscribe to the channels for the cities their clients watch, read the hash, and push the diff to each socket. Daily views come from a batch job over the same stream stored in a data lake.

How to answer

Be concrete about each hop; the interviewer in 7682158 drilled exactly here. Say what is in Redis (key and value shape) and who subscribes to what.

Likely follow-ups
  • A WebSocket server dies; what happens to its clients?
  • Pub/sub is fire-and-forget: is that OK here?
"Design an in-memory cache, single node." What do you focus on?

Data structures and concurrency, not distribution: a hash map plus a doubly linked list for LRU, a TTL min-heap or lazy expiry on read, striped locks or a read-write lock to reduce contention, memory limits with eviction, and an optional write-ahead log or snapshot for restart. Distributed topics only if the interviewer opens that door.

How to answer

Repeat the constraint aloud ("single node, so no CAP talk"), then go component by component.

Likely follow-ups
  • How do you make GET lock-free?
  • What happens to TTLs after a restart from the log?
Real-time restaurant dashboard: orders, top-3 dishes and sales for the last hour, day and 7 days, at 100k orders/sec.

Order events go to a stream partitioned by restaurant. A stream processor keeps per-restaurant counters in tumbling one-minute buckets; the hour view sums 60 buckets, the day view sums hourly roll-ups, and the 7-day view sums daily roll-ups. Top-3 dishes per restaurant is a tiny heap since a restaurant has few dishes. Results go to a key-value store keyed by (restaurant, window). The dashboard polls or subscribes for updates.

How to answer

Start with the numbers: 100k/sec across 10k restaurants is only ~10/sec per restaurant on average, so per-restaurant state is small; the challenge is the total stream and hot restaurants.

Likely follow-ups
  • Late events?
  • Exactly-once counts or approximate?
Your round invite says LLD, but the interviewer starts asking about architecture. What do you do?

Ask directly in the first minute: "Would you like me to focus on classes and code, or on services and scale?" Then follow their answer and confirm the deliverable (diagram, APIs, schema, or code). One SDE-1 candidate lost time by preparing the wrong round.

How to answer

Show you clarify scope before solving; that itself is a signal interviewers grade.

Likely follow-ups
  • What would your LLD look like if they switch back halfway?
Uber SOS: a phone sends a heartbeat every 5 minutes; after two misses, call an external safety API. Design the backend.

Store, per active trip, the "next deadline" (last heartbeat + 10 minutes) in a store that supports time-ordered scans, such as a Redis sorted set scored by deadline, sharded by trip id. Each heartbeat moves the deadline forward. A pool of checker workers repeatedly pops entries whose deadline has passed and puts an "escalate" job on a queue. An escalation worker calls the external API with retries and an idempotency key (trip id + window), so retries never double-call. Trips end by removing the key.

How to answer

Spot that this is a timer/scheduler problem, not a messaging problem. Then cover duplicates and the external API failing.

Likely follow-ups
  • A checker dies holding entries?
  • The phone is just in a tunnel: false alarms?
"Tell me about a time you disagreed with a senior engineer." How do you answer as a networking engineer?

Use STAR with a technical disagreement where data decided: for example a buffer-size change you thought would cause tail drops. Situation and task in two sentences, then what you measured, how you raised it, what was decided, and what happened. End with what you learned about influencing without authority.

How to answer

Keep it to about 2 minutes; spend most time on Action. Avoid stories where you were simply right and they were wrong.

Likely follow-ups
  • What if the data had gone the other way?
  • How did the relationship look afterwards?
