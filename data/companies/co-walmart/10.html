Interview Q&A for the Walmart loop

Design an inventory service that handles heavy concurrent stock updates. You have 20 minutes.

Store stock per (item, store/warehouse). For a decrement use a conditional update: UPDATE stock SET qty = qty - :n, version = version + 1 WHERE sku = :s AND node = :w AND qty >= :n; zero rows updated means "not enough". This is optimistic and needs no long locks. For very hot items, move the counter to Redis with an atomic script, or split stock into several sub-counters. Emit a stock-changed event to Kafka for search, analytics and replenishment.

How to answer

In 20 minutes: one data model, one atomic write, one hot-item fix, one event. Keep a plan B ready in case the interviewer rejects plan A.

Likely follow-ups
  • Why not SELECT ... FOR UPDATE?
  • How does the online store's "in stock" view stay fresh?
Optimistic vs pessimistic locking for ticket booking: which and why?

Pessimistic (lock the row, then update) is simple and safe when conflicts are frequent, but holds locks and can deadlock under load. Optimistic (read a version, update only if unchanged) has no lock waits and suits low-to-medium contention, but needs retries when it loses. For seats, use optimistic conditional updates for the hold and a short TTL; for a hot event (concert opening), add a queue/waiting room so contention stays low.

How to answer

Define both in one line each, then pick based on contention, then fix the hot case.

Likely follow-ups
  • What isolation level would you use?
Twitter is read-heavy across several regions. How do you serve timelines fast everywhere?

Precompute home timelines (fan-out on write) for normal users into a cache in each region; for celebrities, merge their tweets at read time. Replicate tweet data asynchronously to all regions; users read from their nearest region, and writes go to the user's home region. Media goes through a CDN. Accept eventual consistency: a tweet may appear a second later in a far region.

How to answer

Read path first (cache, CDN, local replica), then the write path and replication, then the consistency trade-off.

Likely follow-ups
  • A region goes down?
  • How do you avoid write conflicts?
Design a ledger. What makes it different from a normal "balance" table?

A ledger is append-only and double-entry: every transfer writes two entries (debit one account, credit another) that sum to zero, in one transaction. Balances are derived (sum of entries) and cached in a balance table updated in the same transaction. Nothing is updated or deleted; corrections are new reversing entries. Every request has an idempotency key so retries do not double-post.

How to answer

Append-only, double-entry, idempotency, then audit and reconciliation.

Likely follow-ups
  • How do you shard accounts and still do cross-shard transfers?
Chess game with ELO and a near-real-time leaderboard. What do you keep in Redis?

A sorted set for the global leaderboard (member = player id, score = rating) and one per region or country for local ranks. After each game the game service updates both players' ratings in the DB and then in the sorted sets. ZREVRANK gives a player's rank and ZREVRANGE the top N. Live moves go over WebSockets to a game server that holds the board state.

How to answer

Keep it simple and finish well - the reported rejection was for over-engineering at the end.

Likely follow-ups
  • A game server crashes mid-game?
"Why do you need a message queue in your grocery delivery design?"

Give the concrete reason for this design: placing an order should return fast, while packing, payment capture, notifications and delivery assignment happen later and can be retried. The queue decouples these steps, absorbs the morning spike of subscription orders, and lets each consumer scale and fail on its own without losing orders.

How to answer

One sentence per benefit, tied to this system, not a generic list.

Likely follow-ups
  • What if a consumer processes an order twice?
Code an LFU cache. What data structures give O(1) get and put?

A hash map key to node (value, frequency); a hash map frequency to a doubly linked list of nodes (most recent at the head); and a minFreq variable. On get, move the node from its frequency list to frequency+1 and update minFreq if its old list became empty. On put when full, evict the tail of the minFreq list.

How to answer

Draw the two maps first, then walk through get, put and evict with a small example.

Likely follow-ups
  • Make it thread-safe.
  • When is LFU worse than LRU?
Your competency list includes HA/DR and Kubernetes. How do you bring them into a design answer?

After the core design, add a short "running it" part: services as Deployments with multiple replicas across zones, readiness probes and autoscaling; stateful stores replicated with a clear RPO/RTO; a second region for DR with a tested failover; CI/CD with canary releases; metrics, logs and traces with alerts on the SLOs. Keep it to 3-4 minutes unless they ask for more.

How to answer

This is your strength as an infra engineer - use it, but after the core design, not instead of it.
