Worked example: Adobe's LLD + HLD round

An Adobe MTS-2 candidate who received an offer (2026-06) had one design-heavy round with two problems. Source: post 8317368.

  1. The prompts. Design a rate limiter and a file upload system.
  2. How it ran. Start from LLD (classes, APIs), then move to HLD (scaling and infrastructure).
  3. What was probed. Concurrency, failure cases, DB design, bottlenecks, horizontal scaling and data consistency, with each answer drilled until the edge cases ran out.
  4. Lesson. Prepare both layers for the same problem: a clean class design and the distributed version. For the rate limiter that means a token bucket class and then a Redis-backed limiter; for uploads, an upload API and then presigned, resumable uploads with async processing.

Full design on this site: Distributed Rate Limiter and Document Upload & Async Processing (d74).

Scenario: The rate limiter on two servers

Your in-memory token bucket works on one server. After scaling to two servers behind a load balancer, users get twice their limit.
Weak answer: Use sticky sessions so each user always hits the same server.
Strong answer: Move the counter to a shared store (Redis with an atomic Lua script or INCR plus expiry), or give each server a share of the limit. Say what happens if Redis is down: fail open for reads, fail closed for expensive writes.
  • How do you rate-limit per tenant and per API at once?
  • How do you resume a 2 GB upload after a network drop?
