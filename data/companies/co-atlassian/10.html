Interview Q&A for the Atlassian loop

Design the API for a tagging service shared by Jira, Confluence and other products.

Treat every taggable thing as an entity reference: (product, entityType, entityId). Core calls: PUT /tags/{tagId}/entities/{product}:{type}:{id} to attach (idempotent), DELETE the same to detach, GET /entities/{ref}/tags, GET /tags/{tagId}/entities?product=&cursor= with cursor pagination, GET /tags?prefix= for autocomplete, and GET /tags/popular?window=7d. Tags are scoped to a tenant (site). Products never send content, only references, so the service stays product-agnostic.

How to answer

Start with the entity-reference idea; it is what makes the service "cross-product". Then idempotency and pagination, then tenancy.

Likely follow-ups
  • Why REST and not GraphQL or gRPC here?
  • How do permissions work if a user can't see the Jira issue?
What schema and database would you use for tags, and how do you shard it?

Three logical tables: tag(tenant, tag_id, name), and the mapping stored twice for the two lookup directions: entity_tags(tenant, entity_ref, tag_id) keyed by entity, and tag_entities(tenant, tag_id, entity_ref) keyed by tag. A relational DB works for one region at moderate scale; a wide-column store (Cassandra/DynamoDB) fits a write-heavy, two-key access pattern. Shard by tenant, and for very popular tags add a bucket to the partition key so one tag's rows spread over several partitions. Counts for "popular tags" live separately (counters or a stream job), not computed by COUNT(*).

How to answer

Derive tables from the API's queries, then choose the store, then the shard key and the hot-tag fix. Name the trade-off of writing twice (consistency between the two tables).

Likely follow-ups
  • How do you keep the two tables in sync if one write fails?
  • Rename a tag used on 10 million items?
Show the top 10 most viewed Confluence pages this week, but never pages the user already viewed.

View events go to a stream. A job keeps per-tenant counts in time buckets and maintains a candidate list of the top few hundred pages per tenant (a sorted set). At read time, fetch the top ~100 candidates and filter out those the user has viewed, using a per-user "viewed" set (or a Bloom filter for large histories), then return the first 10. Because the filter is per user, precompute the shared part (candidates) and do the personal part at read time.

How to answer

Separate the global ranking (precomputed) from the personal exclusion (at read time). Say why fetching more than 10 candidates matters.

Likely follow-ups
  • What if the user has viewed all 100 candidates?
  • How do you define "engagement" beyond views?
How would you find the top-10 trending tags in the last hour?

Every tag attach emits an event. Keep per-minute counters per tag; the hourly score is the sum of the last 60 buckets. Maintain a Redis sorted set per tenant updated as counts change, and read ZREVRANGE 0 9. For huge tag counts, use a count-min sketch plus a small heap to keep memory bounded.

How to answer

Exact first, then approximate when the numbers demand it. One reported candidate got positive feedback with sorted sets.

Likely follow-ups
  • Trending versus simply popular: how do you weight recency?
In the tech screen you have 20 minutes to code a rate limiter, then design it. Where does it run and where does config live?

Code a token bucket per client (capacity, refill rate, last refill time). For design: run it at the API gateway so every service benefits; keep counters in a shared store like Redis with an atomic script so all gateway instances agree; keep limits in a config service with a local cache and a short refresh, so changes don't need a deploy. Fail open or closed is a product choice; say which and why.

How to answer

Keep the code tiny and correct, so you have time for the design half; time pressure is the reported difficulty.

Likely follow-ups
  • Sliding window versus token bucket?
  • Redis is down: what happens?
Rapid-fire: "a Facebook clone shows each user's friend count; how does it scale?" (answer in 2-3 minutes)

Don't count friends on every page view. Keep a stored counter per user, updated when a friendship is added or removed (in the same transaction or via an event). Cache it. For celebrities with huge counts, shard the counter into several rows and sum them, or accept slightly stale counts. Rebuild from the friendship table if they drift.

How to answer

One idea, one trade-off, one failure case. Rapid-fire rounds reward crisp answers, not full designs.

Likely follow-ups
  • How stale may the count be?
The interviewer asks "why did you pick Cassandra?" How do you defend a technology choice?

Tie it to the access pattern and the requirement, then name what you give up. For example: "Writes are 10x reads and every read is by partition key, so a wide-column store fits; I give up ad-hoc queries and joins, which we don't need, and I accept eventual consistency for counts." If a read needs a sort over the whole dataset, Cassandra is the wrong tool - which is why one candidate drew criticism for using it for an org-wide "most engaged" view.

How to answer

Pattern: requirement, access pattern, choice, cost. Offer the alternative you rejected.

Likely follow-ups
  • What would make you switch to Postgres?
Values interview: "Tell me about a time you shared bad news." Which value is this, and how do you answer?

It probes "Open company, no bullshit". Pick a real case: you found that a release would miss a customer date because of a driver bug. STAR: Situation (release, customer), Task (you owned the driver), Action (told the lead early, with data and two options), Result (customer told in advance, date moved by a week, trust kept). Close with what you would do the same next time.

How to answer

Show the "brains, thoughtfulness, caring" side: what you said, when, and how.

Likely follow-ups
  • What if your manager asked you to keep quiet?
