Interview Q&A

Design a notification system for food delivery that never sends duplicates.

Order services publish events to Kafka keyed by order id. A notification service consumes them, looks up user preferences and picks channels (push, SMS, email). Before sending, it writes a dedupe record keyed by (event id, channel) with a unique constraint; if the insert fails, the message was already sent. Channel workers retry with backoff and park failures in a dead-letter queue.

How to answer

Say why Kafka (decouple, replay, absorb spikes) instead of direct API calls, then show the dedupe key and the crash case: sent but not recorded.

Likely follow-ups
  • Provider accepted but you crashed before recording? (Provider idempotency key, or accept rare duplicates for low-risk messages.)
  • Some messages go to many channels? (Fan out per channel, dedupe per channel.)
  • Rate limits from SMS providers? (Token bucket per provider.)
Design order tracking for a food delivery app.

An order is a state machine: placed, accepted, preparing, picked up, delivered, cancelled. Every transition is an event on Kafka with the order id as key so events stay in order. A tracking service keeps the latest state and rider location in a cache, and pushes updates to the customer app over WebSocket or SSE. Rider location updates come every few seconds into a separate, lossy pipeline.

How to answer

For SDE-1, spend time on entities and the state machine; for SDE-2, add the location pipeline and scaling.

Likely follow-ups
  • Out-of-order events? (Key by order id; reject transitions that skip states.)
  • App offline? (Fetch latest state on reconnect.)
Design dark-store inventory for 10-minute delivery.

Stock is kept per store per item in a strongly consistent store. The app reads availability from a search index or cache with a short TTL, updated by events from the store. At checkout, reserve stock with a conditional decrement (stock >= qty) and a reservation expiry; confirm after payment, release on failure. Route each order to the nearest store that has everything.

How to answer

Separate the 'show' path (fast, may be slightly stale) from the 'take' path (exact). Compare pessimistic and optimistic locking.

Likely follow-ups
  • Picker finds the shelf empty? (Mark out-of-stock, refund or substitute, fix the count.)
  • Sale spike on one item? (Pre-allocated stock buckets or a queue in front of the hot row.)
Kafka or a direct API call between order service and notification service?

Direct calls are simpler and give an immediate answer, but couple the services: if notifications are slow, orders slow down. Kafka decouples them, absorbs spikes, lets many consumers read the same event and allows replay, at the cost of eventual delivery and more moving parts.

How to answer

Give the rule: use a call when you need the answer now (payment authorisation); use an event when you only need it to happen soon (notification).

Likely follow-ups
  • How do you keep order per order? (Partition key = order id.)
  • What if the producer crashes after the DB write? (Transactional outbox.)
Design a ticket booking system (Blinkit SDE-1 version).

Shows have seats; a seat is held with a conditional update or a short lock with TTL, then confirmed after payment. Seat maps are cached; holds are not. A cleanup job releases expired holds.

How to answer

The interviewer may have little time after a DSA warm-up, so lead with the key decision (how you prevent double booking) before the full diagram.

Likely follow-ups
  • Two users click the same seat? (First update wins.)
  • Payment succeeds after the hold expired? (Refund or re-check.)
Design an ad pacing service for restaurant ads.

Each campaign has a daily budget. Split it across the day by expected traffic (hourly weights), and give each ad server node a small token allowance per interval. Nodes serve ads while they have tokens and report spend; a central pacer adjusts the allowances. This prevents spending the whole budget in the first hours.

How to answer

This is a rate limiter in disguise: a token bucket per campaign, refilled by a traffic-weighted schedule.

Likely follow-ups
  • Overspend because of delayed reports? (Small allowances, a safety margin.)
  • Peak dinner traffic? (Weights from historical traffic.)
Design WhatsApp-style QR-code login where the QR rotates every minute.

The web client opens a session and shows a QR that encodes a short-lived token tied to that session; the token rotates (time-based, like TOTP). The logged-in phone scans it and calls the server with its own auth; the server links the web session to the user and pushes a 'logged in' event to the waiting browser over a WebSocket. The browser then gets its own tokens (JWT plus refresh).

How to answer

Walk the three parties: browser, phone, server. Then the security points: expiry, single use, binding to the session.

Likely follow-ups
  • Someone photographs the QR? (Short expiry, single use, confirm on phone.)
  • Log out the web session from the phone? (Revoke its refresh token.)
Design inventory for a restaurant chain (Zepto version).

Each outlet tracks ingredients; recipes map menu items to ingredient quantities. An order decrements ingredients in a transaction; low stock triggers reorder events to a central supply service. Report and forecast from the event log.

How to answer

Cover transactions and locks for concurrent orders at one outlet, then the central view across outlets (eventual).

Likely follow-ups
  • Two orders race for the last portion? (Row lock or conditional update.)
  • Scale Kafka 100x? (More partitions, more brokers, check consumer parallelism.)
How much depth does a Zomato SDE-1 design round need?

Entities and relationships, a clean schema, the main APIs, the order or notification flow, Kafka basics, dedupe, and sync vs async choices. Deep scale math is not the focus. A SQL query on your schema (for example top 5 delivery partners by area) may be asked.

How to answer

Show solid basics and clear reasons. Do not drop names you cannot explain.

Likely follow-ups
  • Write the SQL for top partners by area? (GROUP BY area, partner with a window function or ORDER BY + LIMIT per area.)
