Interview Q&A

Why does a payment API need idempotency, and how do you implement it?

Networks time out, so the client cannot tell whether the request or the reply was lost. It must retry, and a retry must not charge twice. The client sends a unique key per logical payment; the server stores key, request hash and result under a unique constraint. A retry with the same key returns the stored result.

How to answer

Use the 'lost ACK' framing, then the table, then the race: two retries at once (unique constraint plus row lock).

Likely follow-ups
  • Same key, different amount? (Reject by comparing the request hash.)
  • How long do you keep keys? (Longer than the retry window.)
  • Why do indexes make writes slower? (Each index is updated on every insert.)
Design a merchant settlement system that pays merchants T+1 after commission.

Every transaction is written to an append-only ledger with merchant id and date. A daily job (or streaming aggregation) sums per merchant per day, subtracts commission, and creates a settlement record and a bank payout instruction. Payout results are reconciled against bank files. A merchant can see a daily ledger view built from the aggregates.

How to answer

Double-entry ledger first, then the batch, then failure: payout failed, payout unknown, partial day.

Likely follow-ups
  • Merchant asks for a one-time early settlement? (A separate settlement request that locks those entries.)
  • How do you shard? (By merchant, with date partitions.)
Design live stock-price fan-out for 5M users (Paytm / Groww style).

Exchange ticks come into an ingest tier and Kafka, partitioned by instrument. A fan-out tier keeps, for each instrument, the latest price and the set of connected users watching it. Users hold WebSocket connections to gateway nodes; each node subscribes only to instruments its users watch. Send the latest price at a fixed rate (conflate), and drop stale ticks instead of queuing them, to meet the freshness bound.

How to answer

Do the numbers from the prompt: users times instruments watched, divided across gateway nodes. Then explain conflation.

Likely follow-ups
  • A slow client? (Drop to latest value; never buffer unbounded.)
  • Order placement in the same app? (Separate path, strong consistency, idempotent order ids.)
Design a GTT (Good Till Triggered) order service on top of an existing order service.

Store GTT orders with trigger price and expiry. A trigger engine subscribes to ticks for instruments that have GTTs and keeps the triggers in sorted structures per instrument (price levels). When a tick crosses a level, it places a normal order through the existing service with an idempotent id. Because exchange orders expire at day end, a daily job re-places or re-arms what is still active.

How to answer

Show the intermediate states (armed, triggered, placed, filled, failed) and what happens if the order service is down at trigger time.

Likely follow-ups
  • Thousands of GTTs on one hot stock? (Shard by instrument; process levels in batches.)
  • Duplicate triggers? (Idempotent order id per GTT.)
Design a recurring subscription product on top of a payments platform.

Plans define price and cycle. A subscription holds the customer's mandate or card token and next charge date. A scheduler finds due subscriptions and creates charge attempts with idempotent ids; failures go through a retry policy with notifications; repeated failure pauses the subscription. Every attempt is logged for reconciliation.

How to answer

Connect three known designs: scheduler, payment, notification. Then cover the failure cases one by one.

Likely follow-ups
  • Customer changes plan mid-cycle? (Proration rules.)
  • The scheduler runs twice? (Idempotent charge id per cycle.)
Design a job scheduler that takes a job file and a cron expression.

Store jobs with next run time. Scheduler nodes poll due jobs with row locks (or a time-bucketed queue), push them to a work queue, and compute the next run time. Workers lease jobs, heartbeat, and report results; expired leases return to the queue. Keep job files in object storage.

How to answer

Name the two hard parts: never run a job twice by accident, never miss one. Then lease plus idempotent job runs.

Likely follow-ups
  • Clock skew between nodes? (Use DB time or a single leader.)
  • A job runs longer than its interval? (Policy: skip, queue, or allow overlap.)
Design Instagram's feed for billions of users (PhonePe version).

Hybrid fan-out: push new posts into followers' feed caches for normal users, but pull at read time for accounts with huge follower counts. Store posts in a partitioned store, timelines in a cache, media in object storage behind a CDN. For read-your-own-writes, merge the author's own recent posts into their feed on read.

How to answer

One PhonePe interviewer rejected a pure queue fan-out at that scale, so present hybrid fan-out early.

Likely follow-ups
  • Likes and comments counts? (Sharded counters, batched writes.)
  • Ranking? (A light ranker over a candidate set.)
Design an online auction system with consistent bidding.

Each auction has a current highest bid with a version. A bid is accepted only if it is higher than the current one, using a conditional update or a single-writer actor per auction. Bidders search listings via a search index. Push the new highest bid to watchers in real time. At close time, a job finalises the winner.

How to answer

The core is concurrency on one hot row: show conditional update and the per-auction serialisation option.

Likely follow-ups
  • A last-second bid storm? (Queue bids per auction; process in order.)
  • Seller and bidder the same user? (Rejected by rule.)
How do you prepare for a PhonePe or Razorpay machine-coding round?

Practise 90-minute builds of common problems (Splitwise, pub-sub queue, parking lot, rate limiter, order book). Keep a clean structure: models, services, repositories, an in-memory store, and a small driver or tests. Handle concurrency where it is natural.

How to answer

Say you stick to the stated requirements first, then extend only if time remains: over-extending was a rejection reason.

Likely follow-ups
  • How do you make it extensible? (Interfaces and strategies at the points likely to change.)
  • Thread safety? (Concurrent maps, locks per entity.)
