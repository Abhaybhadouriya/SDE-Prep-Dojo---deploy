Interview Q&A

What does a Salesforce MTS/SMTS loop look like, and where does HLD fit?

OA on HackerRank, then DSA, LLD, HLD and a hiring-manager round, each one eliminatory. HLD is usually its own 60-minute round, but some MTS loops skip it, and the hiring manager may ask for an HLD of your own project instead.

How to answer

Show you have read the pattern and that you prepared both LLD and HLD, because labels can be wrong.

Likely follow-ups
  • What if the round is labelled LLD? (Ask in the first minute which depth they want.)
  • How do you prepare for the HM round? (Own project HLD + values stories.)
Design a distributed rate limiter for a multi-tenant API platform.

Start with the rule: N requests per tenant (and per user) per window. Compare fixed window (cheap, but a burst at the boundary can double the rate), sliding log (exact, memory-heavy), sliding window counter (good approximation, small memory) and token bucket (allows bursts up to bucket size). Keep counters in Redis, update them atomically with a Lua script or INCR plus expiry, shard by tenant id, and put the check in the API gateway. Decide fail-open vs fail-closed when Redis is down.

How to answer

Lead with algorithms and their trade-offs (accuracy vs memory vs throughput), then storage, then the multi-tenant angle: per-org quotas so one tenant cannot starve others.

Likely follow-ups
  • How do you handle a hot tenant? (Local token buckets synced in batches, or a dedicated shard.)
  • Multi-region? (Per-region budgets, eventual sync.)
  • What header do you return? (429 with Retry-After and remaining quota.)
Design a login / authentication system.

Passwords stored with a slow salted hash (bcrypt, scrypt or Argon2). After login, issue a short-lived access token (JWT) and a long-lived refresh token stored server-side so it can be revoked. Add MFA or OTP, rate limiting and lockout on failed attempts, and audit logs. Sessions or tokens are checked at the gateway.

How to answer

Walk the flow: sign-up, login, token refresh, logout and revoke. Then the protection list: brute force, credential stuffing, token theft, replay.

Likely follow-ups
  • Why not keep everything in a JWT? (Hard to revoke.)
  • How do you log out of all devices? (Delete refresh tokens; bump a token version.)
  • Where do you store the session? (Redis with TTL.)
Design a large-scale payment processing platform.

Client sends an idempotency key with every payment request. The payment service writes a payment row with a state machine (created, processing, succeeded, failed, unknown) and an outbox event in one transaction. Workers call the PSP; a timeout becomes 'unknown' and is settled by a status query or by reconciliation. Kafka carries events to ledger and notification services.

How to answer

Say idempotency in the first two minutes, then the state machine, then failure cases. The Salesforce report said NFRs drove the follow-ups, so state them up front.

Likely follow-ups
  • Two retries arrive at once with the same key? (Unique constraint plus row lock.)
  • SQL or NoSQL for payments? (SQL for the money tables: transactions, constraints.)
  • How do you monitor it? (Success rate, unknown-state count, reconciliation diffs.)
Design an Airbnb-like booking system that never double books.

Availability is stored per property per date. Booking takes a short hold (for example 5 minutes) on the dates, then payment, then confirm. Enforce it with a unique constraint or conditional update on (property, date), or a lock with TTL. Search is separate: listings flow by CDC into a search index so reads stay fast. Payment is its own service.

How to answer

Split the read path (search) from the write path (book). For the write path, show two ways to stop double booking and pick one.

Likely follow-ups
  • Hold expires mid-payment? (Payment checks the hold; release on timeout.)
  • Host updates thousands of listings at once? (Bulk async job, batched index updates.)
Design a job scheduler that assigns jobs to workers with a max capacity each.

Jobs are stored durably with state and next run time. A scheduler picks due jobs and puts them on a queue. Workers pull work and hold a lease with a heartbeat; each worker advertises free capacity, and the assigner only gives work to workers with room. Expired leases go back to the queue. Retries use backoff and a dead-letter queue.

How to answer

Make capacity a first-class field, and explain lease plus heartbeat so a crashed worker does not lose jobs.

Likely follow-ups
  • How do you avoid two schedulers picking the same job? (Row lock / SELECT ... FOR UPDATE SKIP LOCKED, or leader election.)
  • Priority jobs? (Separate queues or a priority field.)
Design a flash sale for a single product that starts at a fixed time.

Pre-load stock into Redis and decrement atomically. Put a queue or token gate in front so only as many buyers as there is stock reach checkout. Rate-limit per user, serve the page from CDN, and reserve stock for a short time while payment completes. The report asked for consistency over availability: never oversell.

How to answer

Name the hot spot (one row, one key) and show how you protect it.

Likely follow-ups
  • Redis dies? (Replica plus reconciliation against the DB.)
  • Bots? (Captcha at entry, per-account limits.)
Design a metrics collection system.

Agents scrape or push metrics; a collector tier writes to a time-series store partitioned by metric and time. Keep recent data at full resolution and roll up older data. Alerts run rules on the stream. Watch label cardinality, which is what usually breaks such systems.

How to answer

Use real examples from your network monitoring work (SNMP polling vs streaming telemetry). Hands-on detail is exactly what one rejected candidate lacked.

Likely follow-ups
  • Pull or push? (Pull for discovery and health; push for short jobs.)
  • How do you handle a cardinality explosion? (Limits per tenant, drop or aggregate labels.)
How would you keep tenants isolated in any of these designs?

Put the tenant id in every key, row and partition. Enforce per-tenant quotas at the gateway. Shard so one large tenant can move to its own shard. Encrypt per tenant where needed, and check tenant id on every read, not only at login.

How to answer

This is a natural Salesforce follow-up even when the question does not say 'multi-tenant'. Bring it up yourself.

Likely follow-ups
  • Noisy neighbour? (Quotas, separate pools, bulkheads.)
  • One tenant needs a schema change? (Metadata-driven custom fields instead of per-tenant tables.)
Walk me through the HLD of your current project.

Draw your current system as boxes: clients, control plane, data plane, storage, management interfaces. Explain one hard decision and what you would change today. A networking candidate can describe a router or controller software stack the same way.

How to answer

Prepare one diagram and three 'why' answers. The posts say the HM round can become a full CV deep dive.

Likely follow-ups
  • What failed in production and how did you find it?
  • How would you scale it 10x?
