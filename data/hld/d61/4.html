Data model

Flipkart spent half the round here: "a song can be a single or part of an album; queries filter on singer". The trick is to make every track belong to a release, where a release is an album, an EP or a single. Spotify's public API does the same: an album object has an album_type of album, single or compilation. Then "singles by this artist" is just a filter, not a special case. Store-choice reasoning is in Choosing Storage.

CREATE TABLE release (
  release_id   BIGINT PRIMARY KEY,
  title        TEXT NOT NULL,
  release_type TEXT NOT NULL CHECK (release_type IN ('album','single','ep','compilation')),
  release_date DATE,
  primary_artist_id BIGINT NOT NULL
);
CREATE TABLE track (
  track_id     BIGINT PRIMARY KEY,
  release_id   BIGINT NOT NULL REFERENCES release,
  disc_no      SMALLINT NOT NULL DEFAULT 1,
  track_no     SMALLINT NOT NULL,
  title        TEXT NOT NULL,
  duration_ms  INT NOT NULL,
  isrc         CHAR(12) UNIQUE,          -- industry id of the recording
  UNIQUE (release_id, disc_no, track_no)
);
CREATE TABLE track_artist (
  track_id  BIGINT REFERENCES track,
  artist_id BIGINT NOT NULL,
  role      TEXT NOT NULL DEFAULT 'main',  -- main | featured
  PRIMARY KEY (track_id, artist_id)
);
CREATE INDEX track_by_artist ON track_artist (artist_id, track_id);   -- "songs by this singer"

Apple's follow-up was "why a relational DB, why S3?" Answer with properties, not brand names: the catalogue is small, heavily related (artist-release-track), needs uniqueness (ISRC) and multi-row updates when a label re-releases an album, and is read far more than written - a relational database with replicas and a cache is the simplest thing that fits. Audio is large, immutable and read by byte range - object storage gives cheap, durable, effectively unlimited space and is a natural CDN origin. A database row holding 5 MB blobs would bloat backups, replicas and the buffer cache for no benefit.
