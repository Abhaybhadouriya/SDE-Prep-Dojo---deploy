Deep dives

1. Fast play start: encoding, chunks, CDN and the client cache

Encode once, many ways. When a label delivers a master file, an ingestion pipeline transcodes it to every format and bitrate we support (for example Ogg Vorbis 96/160/320, AAC 128/256 for some devices, a 24 kbps low-data version), normalises loudness, encrypts each file and writes them to S3. This is a batch job on a worker fleet, triggered by a queue; see Long-running Tasks. Audio is immutable after that, which is why caching it is easy: a cached chunk is never stale.

Chunks, not whole files. The player asks for byte ranges (HTTP Range requests) or for numbered segments listed in a manifest, as HLS and DASH do. The first request is small so the first sound comes quickly; the player then fills a buffer of several seconds ahead. Music is much lighter than video (160 kbps vs several Mbps), so a 5 MB song can be fully downloaded in a few seconds on a good network; chunks matter most for fast start, seeking, and weak mobile networks.

Adaptive bitrate. The player measures download speed and buffer level. If the buffer drains, it fetches the next chunks at a lower bitrate; when the network recovers, it steps up. Users can also pin "very high" quality on Wi-Fi.

The CDN and the origin. Spotify's engineering blog says audio streaming runs on Akamai and AWS as "business-critical" content, with Fastly used for other content such as images. A multi-CDN setup gives you failover if one provider has a bad day. Popular songs follow a power law: a small share of the catalogue gets most plays, so edge hit rates for audio are high; the long tail is fetched from S3 on a miss and cached. For a megastar's new album at midnight, pre-warm the CDN by pushing the files to edges before release.

The client cache. The app keeps recently played and downloaded songs on disk (encrypted). Spotify's 2010 measurements found about 55% of played data came from the local cache. Repeat listening is very common in music, unlike video, so a disk cache of a few GB removes a large share of network traffic. The same paper measured a median play start of 265 ms (75th percentile 515 ms, 90th 1,047 ms), cached tracks included.

From your world

Prefetching the next track is the same trick as CPU prefetching or TCP slow-start avoidance: start the next transfer before you need it so its latency is hidden behind the current song. Adaptive bitrate is congestion control at the application layer: measure throughput, back off when the buffer (your queue) drains.

2. Search under 200 ms: how Elasticsearch actually does it

Two Flipkart candidates said they were grilled on Elasticsearch; one could not explain how search would work and did not move on. So go one level deeper than "use Elasticsearch".

  1. Indexing Each track, artist and release becomes a document. The text is analysed: split into tokens, lower-cased, accents folded (so "beyonce" finds "Beyoncé"). For prefix matching while typing, an edge n-gram analyser also stores "sh", "sha", "shap", "shape". Each token points to the list of documents containing it: the inverted index.
  2. Fuzzy matching A fuzzy query allows a small Levenshtein edit distance (insert, delete, substitute, or swap two adjacent letters). With fuzziness: AUTO Elasticsearch allows 0 edits for terms of 1-2 characters, 1 edit for 3-5 characters, and 2 edits for longer terms. It expands the term into at most max_expansions (default 50) similar terms, so setting prefix_length: 1 (first letter must match) keeps it fast.
  3. Ranking Text relevance (BM25) alone ranks an obscure cover above the hit. Combine it with a popularity signal (recent play counts) using a function_score, and boost exact title matches. Personal signals (artists you play) can re-rank the top 50 in the search service.
  4. Sharding 100M documents of about 1 KB is about 100 GB: a handful of primary shards with replicas. Replicas carry read QPS: at 35K QPS peak, add replicas until each node is comfortably under its measured capacity.
  5. Keeping it fresh The catalogue database is the source of truth. Changes flow out by change data capture to Kafka, and an indexer updates Elasticsearch within seconds. Popularity is re-indexed in a periodic batch. Search is a derived view: if it is a little stale, nothing is lost.
  6. Latency tricks Cache results for the top few thousand queries (they are a large share of traffic), debounce keystrokes, return only ids and titles (hydrate cover art from the CDN), and set a timeout so one slow shard returns partial results instead of a late page.

3. Playlists: order, reshuffle, share

Apple asked for exactly this service. The traps are ordering and concurrent edits.

  • Order without renumbering. If each item stores an integer position, moving song 900 to the top rewrites 900 rows. Instead store a sortable rank between neighbours: a fractional number or a string key (often called a LexoRank-style key; Jira uses this idea for ranking issues). Moving an item writes one row: its new rank sits between the two items it lands between. When ranks get too long, rebalance the playlist in the background.
  • Shuffle is a play order, not an edit. "Shuffle play" generates a random permutation on the client (or the server, seeded) and does not change the saved order. "Reshuffle the playlist" (persist a new order) is a bulk rewrite of ranks in one transaction; fine, because playlists are small (thousands of items at most, and apps cap the size), so a full rewrite is bounded.
  • Concurrent edits. Every playlist has a version. Clients send operations ("insert t_9 after item_41", "delete item_77"), not the whole list. The server applies operations in order inside a transaction, increments the version, and publishes a change event. Because operations reference item ids rather than positions, two friends adding songs at the same moment both succeed. Only a true conflict (moving an item someone just deleted) is rejected, and the client refreshes.
  • Sharing. A playlist_member(playlist_id, user_id, role) table gives viewer or editor rights. A public link is a signed token. Followers get updates through the change event: push if they have the playlist open, otherwise they fetch on next open using the version number (send only changes since version N).
  • Big public playlists. A chart playlist followed by 30M users is read-heavy and edited by one curator: cache the whole list at the CDN or in Redis keyed by version.

4. Listening history, play counts and consistency

Plays are a firehose (about 140K per second at peak in our estimate). The client batches events and sends them every few seconds; if offline, it stores them and sends later, which is also how offline plays are counted. The events API writes to Kafka keyed by user_id (keeps each user's history in order) and returns at once.

  • Recent history: a consumer writes to Cassandra, partition (user_id, month), newest first. "Recently played" is one partition read.
  • Play counts and likes: a stream job counts per track per minute and adds to counters; the number shown on an artist page may lag by minutes, which is fine. Use distributed counter techniques for hot tracks (shard the counter).
  • Royalties: money depends on plays, so the authoritative count is a daily batch job over the complete event log in the data lake, with de-duplication by playId. "Eventual" here means late but complete, never lossy.
  • Recommendations: the same log feeds feature pipelines and models (Discover Weekly style). Spotify's event delivery reached about 8M events per second at peak in 2019, moving from Kafka to Google Cloud Pub/Sub to make it happen.

The Amazon report asked where you would pick eventual vs strong consistency. Give a rule, then examples: "Strong where a wrong answer costs money or access: payments, subscription status, login, licensing. Eventual where a slightly stale answer is harmless: play counts, likes, follower counts, search index, playlist followers' copies. Read-your-writes for the user's own edits: after I add a song to my playlist, I must see it."

5. "Alexa, play Believer": the voice flow

An Amazon SDE-2 phone screen for an Alexa team asked how audio plays when you ask Alexa for music. Walk it as a pipeline:

  1. Wake word on device The Echo detects "Alexa" locally and starts streaming the voice clip to the cloud.
  2. Speech to intent Speech recognition turns audio into text; language understanding turns text into an intent like PlayMusic(song="Believer", artist="Imagine Dragons").
  3. Resolve the entity The music skill calls the same search service (with spoken-form tweaks: numbers, homophones) to get a track_id, using the user's history to break ties ("play my workout playlist").
  4. Entitlement and URL The playback service checks the subscription and returns a signed stream URL, exactly as for the phone app.
  5. Directive to the device The cloud sends the device a play directive with the stream URL (the Alexa Skills Kit has an AudioPlayer.Play directive for this), and the device streams from the CDN. Play events flow back just like the app's.

The lesson: voice is only a different front door. Search, entitlement and the CDN path are shared.
