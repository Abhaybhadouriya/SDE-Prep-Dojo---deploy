Architecture: from "play" to sound

Click Next or Play. The control path (small JSON calls) goes through our services; the data path (audio bytes) goes straight from a CDN to the phone.

  1. Client to gateway. The app (phone, web, car, Echo) talks HTTPS to an API gateway that checks the login token, applies rate limits and routes to services. Every service behind it is stateless and runs many copies behind a load balancer.
  2. Search. The search service cleans the query (lower case, strip accents), then asks Elasticsearch for tracks, artists and albums with fuzzy matching and a popularity boost. Target p95 under 200 ms.
  3. Catalogue. Opening an album or artist page reads the catalogue service: Redis first, then a read replica of the relational database. Cache hit rates are very high because new releases are rare compared with reads.
  4. Play: permission, not bytes. The playback service checks the subscription and licence rules (is this track available in this country? free or premium quality?), picks the file list, and returns a short-lived signed URL to the CDN plus a key id for decryption.
  5. Bytes from the edge. The player fetches the first chunk at a low-to-medium bitrate to start fast, then keeps a buffer ahead. CDN edges serve popular songs from cache; a miss goes to the S3 origin once and is cached for everyone nearby. Near the end of a song the player prefetches the next track, so there is no gap.
  6. Playlists and library. Separate service and store. Edits carry the playlist version; the server applies "insert after item Y" changes and bumps the version, which also tells shared listeners to refresh.
  7. Every play is an event. The client batches events (started, 30 seconds reached, skipped, finished) to the events API, which writes them to Kafka. Consumers update recent history, stream play counts (eventual), and land everything in a data lake for recommendations and royalty reports.
