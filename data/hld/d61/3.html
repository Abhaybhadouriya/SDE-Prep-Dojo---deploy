Key APIs

REST over HTTPS through an API gateway; background in API Design & Client-Server Communication.

# search across songs, artists, albums (typo tolerant)
GET  /v1/search?q=shap%20of%20yu&types=track,artist,album&limit=20&cursor=...
  -> 200 { "tracks": [ { "id": "t_9", "title": "Shape of You", "artists": ["a_7"], "albumId": "al_3" } ], ... }

# catalogue
GET  /v1/tracks/t_9
GET  /v1/albums/al_3                     # tracks in order
GET  /v1/artists/a_7/albums?type=single,album

# play: ask permission and get byte locations (the server never streams bytes)
POST /v1/playback/t_9/start  { "deviceId": "d_1", "quality": "auto" }
  -> 200 { "playId": "p_55", "manifestUrl": "https://cdn.example/t_9/manifest?sig=...&exp=...",
           "keyId": "k_12", "expiresIn": 900 }

# playlists
POST   /v1/playlists                       { "name": "Gym", "public": false }
POST   /v1/playlists/pl_1/items            { "trackId": "t_9", "after": "item_41" }
DELETE /v1/playlists/pl_1/items/item_77
PATCH  /v1/playlists/pl_1/items/item_77    { "after": "item_12" }     # move = one row change
POST   /v1/playlists/pl_1/share            { "friendIds": ["u_8"], "role": "editor" }
GET    /v1/playlists/pl_1?version=42       # client sends the version it has

# library and history
PUT    /v1/me/library/tracks/t_9           # like (idempotent)
GET    /v1/me/history?limit=50
POST   /v1/events  [ { "type": "play_progress", "playId": "p_55", "ms": 30000 } ]   # batched

Three details interviewers notice. (1) start returns a signed, expiring CDN link, not audio. (2) Playlist moves send "put item X after item Y", not the whole list, so two friends editing do not overwrite each other. (3) PUT for like is idempotent: liking twice is still one like.
