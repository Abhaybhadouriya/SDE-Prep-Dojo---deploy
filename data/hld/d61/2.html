Back-of-envelope estimation

Method from Back-of-Envelope Estimation. A Flipkart candidate who skipped this step reported that it cost them; do it right after the requirements, out loud, in about three minutes.

~2 PBlossy audio, all bitrates (+~1.8 PB lossless)
~16 Tbpspeak audio egress
~35K/speak search QPS
~140K/speak play events
  1. Check the 5 MB number A 3.5-minute song is 210 seconds. At 160 kbps (Spotify's common Ogg Vorbis quality): 160,000 / 8 = 20 KB per second, x 210 = 4.2 MB. So "about 5 MB a song" matches one mid-quality file. Good: the interviewer's number is consistent.
  2. Raw audio storage 70M x 5 MB = 350 TB for one quality.
  3. All qualities Spotify's support pages list Ogg Vorbis at 96, 160 and 320 kbps, AAC at 128 and 256 kbps, and HE-AACv2 at 24 kbps. Six files whose bitrates add up to about 984 kbps, roughly 6x the 160 kbps file: 350 TB x 6 = about 2 PB. Say "about 2 PB of lossy audio". S3 handles redundancy for us, so we do not multiply again.
  4. Lossless Spotify now also offers Lossless, listed on its audio quality page as up to 24-bit/44.1 kHz FLAC. FLAC bitrates vary by track; assume about 1,000 kbps or more, so one lossless copy of a 5 MB (160 kbps) song is about 30 MB, roughly 6x. 70M x ~26 MB extra = about 1.8 PB more, so about 4 PB in total. Lossless is the biggest single storage cost; store it only for tracks whose label supplied lossless masters.
  5. Peak egress 100M concurrent listeners x 160 kbps = 16,000,000,000 kbps = 16 Tbps. No origin fleet serves that; this number alone proves we need a CDN and client caching. Sanity-check the input out loud: the prompt's 100M concurrent is 50% of the 200M DAU, which is very high for a music app. Confirm it with the interviewer; at a more typical 10-20% of DAU (20-40M concurrent), egress is about 3-6 Tbps. Keep 16 Tbps as the prompt's worst case. Spotify's own 2010 measurement found only 8.8% of played music came from its servers; the rest came from the client cache (about 55%) and peer-to-peer (about 36%). P2P was later dropped, but the client cache still matters.
  6. Metadata size 70M tracks x about 2 KB (title, artists, album, duration, ISRC code, file pointers, genres) = 140 GB, plus about 10M artists and 20M albums. Small: one relational cluster with read replicas, and the hot part fits in a cache.
  7. Search QPS 200M DAU x 5 searches = 1B a day / 86,400 = about 11.6K per second; peak 3x = about 35K per second. Search-as-you-type sends a request per keystroke, so debounce on the client (wait about 150 ms after the last key) or the number multiplies by 5 to 10.
  8. Play events 200M DAU x 20 plays = 4B plays a day = about 46K per second, peak 3x = about 140K per second. Each event (user, track, timestamp, ms played, device, source) is about 200 bytes: 4B x 200 B = 800 GB a day of history. Spotify's event pipeline peaked near 8M events per second globally in 2019 because it logs far more than plays, so ours is modest.
  9. Play-start API calls Each play asks "may I play this, and where are the bytes?" Same 46K per second average. Each answer is small (a signed URL and a key). Cheap if entitlement and file locations are cached.

What the numbers tell you: metadata is tiny and read-heavy (cache it, replicate it). Audio is huge but immutable (put it in object storage behind a CDN and never touch it again). History is a firehose (log it through Kafka, aggregate later). Three different shapes, three different stores.
