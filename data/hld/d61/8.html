Trade-offs, bottlenecks and failure modes

DecisionOption AOption BPick
Audio deliveryStream bytes through app serversSigned URLs to a CDN, S3 originB. App servers would need 16 Tbps; a CDN already has it.
ChunkingWhole-file downloadRange requests or HLS/DASH segments with adaptive bitrateB for fast start, seeking and weak networks.
Catalogue storeDocument DB (one blob per album)Relational with track_artist join tableRelational: small, related, needs constraints; cache hides join cost.
SearchSQL LIKE '%x%'Elasticsearch inverted index with fuzzy + popularityElasticsearch. LIKE cannot use an index for infix and has no typo tolerance.
Playlist orderInteger positionsFractional / string ranksRanks: a move writes one row.
Play countsUPDATE counter per play in SQLKafka + stream aggregation, batch for royaltiesB. 140K updates per second on hot rows would lock.
ServicesOne monolithMicroservices by domainStart with a few domain services: search, catalogue, playback, playlist, user, events. Split by scaling shape, not by noun.

Failure modes

  • A CDN provider degrades: multi-CDN; the playback service returns URLs on the healthy provider, steered by real-user error rates.
  • Elasticsearch cluster slow: timeouts return partial results; cached top queries still work; playback is unaffected.
  • Catalogue DB primary fails: reads continue from replicas and cache; only catalogue ingestion pauses.
  • Kafka backlog on play events: history and counts lag; nothing user-critical waits on them.
  • Entitlement service down: allow cached entitlement for a short grace period (premium users keep playing) rather than stopping all music.
  • Midnight mega-release: pre-warm CDN, pre-compute the artist page into cache, and add search replicas before the release.
