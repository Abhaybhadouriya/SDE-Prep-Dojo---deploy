60-second answer, said out loud: "Three shapes of data. Metadata is small and read-heavy: a relational catalogue where every track belongs to a release typed album or single, a track_artist join for singers, Redis in front, and Elasticsearch as a derived search index with fuzzy matching and popularity boosts, fed by CDC. Audio is huge and immutable: each song is transcoded to several bitrates, encrypted, stored in S3 and served through multiple CDNs; the playback service only checks entitlement and returns a signed URL, and the player streams chunks with adaptive bitrate and prefetches the next song, so 16 Tbps of peak egress never touches our servers. Plays are a firehose: batched client events go to Kafka, feed recent history in Cassandra, eventual play counts, and a data lake for recommendations and exact royalty counts. Strong consistency only for payments, auth and licensing."

SDE-1 stops here / SDE-2 adds. SDE-1: the three-store split, S3 + CDN with signed URLs, a clean schema with release types and the singer join table, Elasticsearch for search, Kafka for play events. SDE-2 adds: the egress arithmetic that forces the CDN, chunking and adaptive bitrate, how fuzzy search and ranking work inside Elasticsearch, rank keys and versioned operations for playlists, explicit consistency choices, CDN pre-warming for releases, and the voice front door.

You might confuse this with Netflix. Both use a CDN and adaptive bitrate, but music files are about 100x smaller, repeat listening is common (so the client cache matters more), catalogue search is a bigger feature, and playlists are user-generated content with concurrent edits. Netflix's hard part is bandwidth per stream and its own CDN boxes inside ISPs; Spotify's is search, personalisation and very fast start.

Follow-up questions

Why a relational database for the catalogue, and why S3 for audio?

The catalogue is about 150 GB of strongly related data (artist, release, track, featured artists), needs uniqueness (ISRC, track number within a disc) and multi-row transactional updates during label ingestion, and is read far more than written. A relational database with read replicas and a cache is simple and fits. Audio is petabytes of immutable blobs read by byte range: object storage is cheap per GB, extremely durable, scales without capacity planning, and is a standard CDN origin. Blobs in the database would bloat it for nothing.

How to answer

Name the access pattern and size of each data type, then the property of the store that matches it. Mention what you would use if the interviewer pushes (DynamoDB for user library and history, where the access is always by user and the volume is huge).

Likely follow-ups
  • Would NoSQL ever be better for the catalogue? (Only if you denormalise into per-page documents for reads; keep SQL as the source.)
  • How do you control access to S3 objects? (Private bucket, CDN with signed URLs or cookies, short expiry.)
How does search actually work? Walk me through Elasticsearch for "shap of yu".

At index time the title is tokenised, lower-cased, accent-folded and stored in an inverted index (token to list of document ids), plus edge n-grams for type-ahead. At query time the search service sends a multi_match with fuzziness: AUTO: "shap" (4 letters) may differ by one edit, so it matches "shape"; "yu" (2 letters) gets no edits, but "you" may still match through n-grams or a phonetic or synonym field. Candidates are scored with BM25 and multiplied by a log of 30-day popularity, so the hit beats a karaoke cover. The index is split into shards with replicas; a query goes to one copy of each shard, and results are merged.

How to answer

Cover four words: analyse, inverted index, fuzzy (edit distance), rank (BM25 + popularity). Then sharding and freshness (CDC to indexer). This is where Flipkart candidates lost points.

Likely follow-ups
  • How do you keep p95 under 200 ms? (Query cache, debounce, prefix_length, small result payloads, replicas, timeouts.)
  • How do you handle a new song that must be searchable immediately? (CDC lag is seconds; for a planned release index it before release with a visible_from filter.)
How do you scale the streaming servers horizontally?

Separate control from data. The playback service is stateless and scales by adding instances behind a load balancer; it returns signed CDN URLs. The bytes are served by CDN edges, which scale across thousands of machines and many cities. If we run our own edge or origin tier, shard it with consistent hashing on track id so each node caches a stable slice, add nodes to grow, and use the CDN's request collapsing so a burst of misses for one new song becomes one origin fetch.

How to answer

Start with the egress estimate (16 Tbps) to show why servers alone cannot do it, then the split.

Likely follow-ups
  • What metrics drive autoscaling? (Requests per second and p95 latency for the playback service; for edges, bandwidth and hit ratio.)
A song can be a single or part of an album, and we need "all songs by this singer". Design the schema.

Every track belongs to exactly one release; a release has a type (album, single, EP, compilation). A single is a release with one track, so there is no nullable album_id and no special case. Singers attach to tracks through track_artist(track_id, artist_id, role) because a song can have several singers, with an index on (artist_id, track_id). "Albums by X" uses release.primary_artist_id; "all songs sung by X, including features" uses track_artist.

How to answer

Draw the four boxes, state the cardinalities, then show the two queries running on the indexes. Mention that the same song released on an album and later on a compilation shares an ISRC, so play counts can be merged.

Likely follow-ups
  • Where do genres go? (A tag table on release or track.)
  • How do you serve an artist page fast? (Precompute it into a cached document on catalogue change.)
Design the playlist service: add, delete, reshuffle and share with friends.

Tables: playlist(id, owner, name, version), playlist_item(playlist_id, item_id, track_id, rank, added_by), playlist_member(playlist_id, user_id, role). Order by a sortable rank key so inserts and moves write one row. Clients send operations with item ids; the server applies them in a transaction, bumps the version and emits a change event. Shuffle play is a client-side permutation; persisting a new order rewrites ranks in one transaction (bounded by the playlist size cap). Sharing is a member row or a signed link; followers sync by asking for changes since their version.

How to answer

Lead with the two traps (renumbering and lost updates) and fix each. Draw the rank picture.

Likely follow-ups
  • Two editors move the same song at once? (Last operation wins on that item; both see the final version.)
  • A playlist followed by 30M people? (Cache by version at the CDN; push only a "version changed" hint.)
Where do you use eventual consistency and where strong?

Strong: payments, subscription state, authentication, licensing and region rights, because a wrong answer costs money or breaks contracts. Eventual: play counts, like counts, follower counts, the search index, recommendation features. Read-your-writes for a user's own edits (playlist, likes): route that user's reads to the primary or use the returned version for a short time.

How to answer

State the rule ("money and access strong, everything else eventual"), give three examples on each side, and name the mechanism.

Likely follow-ups
  • Royalties depend on play counts. Is eventual OK? (Yes if it is complete: the authoritative count is a batch job over the durable log with de-duplication.)
Explain how audio streams when a user says "Alexa, play music".

Wake word on device, voice clip to the cloud, speech recognition to text, language understanding to a PlayMusic intent with slots, entity resolution through the music search service (with personal context), entitlement check, signed stream URL, a play directive sent to the device, device streams chunks from the CDN, and play events flow back to Kafka. Latency budget: most of it is speech processing; the music part should add only a few hundred ms.

How to answer

Draw it as a pipeline and point out which boxes are shared with the phone app.

Likely follow-ups
  • The user says "play the next one" while music plays? (The device holds a queue; next-track requests reuse the same playback API.)
  • Multi-room music? (One leader device keeps the clock; others sync to it.)
How does listening history feed recommendations without slowing playback?

The client batches events and posts them asynchronously; the events API only appends to Kafka. Consumers fan out: recent history to Cassandra, counts to a stream aggregator, raw events to the data lake. Recommendation pipelines read the lake (batch, daily or weekly) and a feature store (streaming, minutes), and write results back as precomputed lists the app fetches. Playback never waits for any of it.

How to answer

Say "write once to a log, read many ways". Mention offline buffering on the client and de-duplication by play id.

Likely follow-ups
  • What counts as a play? (A common rule is 30 seconds; send progress events and decide downstream.)
Monolith or microservices? Where would you draw the boundaries?

Draw boundaries where the scaling shape, data store or team differs: search (Elasticsearch, read QPS), catalogue (relational, cache), playback and entitlement (latency-critical, stateless), playlist and library (user-generated writes), events (firehose), user and payments (strong consistency). Do not split into a service per noun; a playlist service and a "playlist item service" would only add network hops.

How to answer

Give the rule, then the list, then one example of a split you would not do.

Likely follow-ups
  • How do services talk? (Synchronous REST/gRPC for queries, Kafka events for changes.)
A huge artist drops an album at midnight. What breaks and how do you prepare?

Three hot spots: the CDN (millions request the same new files, all misses), the artist page and search (one key, huge QPS), and counters (one track's play count). Prepare by pushing the files to CDN edges before release (pre-warm) with request collapsing at the origin, precomputing the artist and album pages into cache, adding search replicas and caching the obvious queries, and sharding the hot counters. Release visibility is a time flag already in the index.

How to answer

Name the three hot spots, then one fix each.

Likely follow-ups
  • How do you avoid leaking the album before midnight? (Signed URLs are only issued after the release time; files are encrypted.)

Scenario drills

Scenario: songs take 2 seconds to start in one country

Play-start p95 in one country jumped from 400 ms to 2 s. Search and the rest of the app are normal.
Weak answer: "Add more playback servers."
Strong answer: split the play-start time into its parts (API call, DNS, TLS to edge, first-byte, buffer fill) using client timing events. If the API call is fine and first-byte is slow, it is the CDN in that country: check the edge hit ratio and the provider's status, steer that country to the second CDN, and confirm the fix with real-user metrics. Also check whether a recent change raised the starting bitrate.
Follow-ups
  • Which metrics would you have on the dashboard already? (Play-start p50/p95 by country and CDN, rebuffer ratio, edge hit ratio.)

Scenario: "the search is wrong" for a famous artist

Searching for a famous singer shows a tribute band first.
Weak answer: "Increase fuzziness."
Strong answer: this is ranking, not matching. Check the popularity field is fresh for both documents, boost exact matches on artist name, and add an artist-type result block above tracks. Validate with an offline test set of top queries and their expected first result before deploying.
Follow-ups
  • How do you test ranking changes safely? (Offline judged set, then an A/B test on click-through.)

Common mistakes

  • Streaming audio through the application servers.
  • Storing audio blobs in the database.
  • A nullable album_id on track instead of releases with a type.
  • Saying "Elasticsearch" and then being unable to explain an inverted index or fuzzy matching.
  • Integer positions for playlist order, and whole-list overwrites on edit.
  • Updating play counts synchronously in SQL on every play.
  • Skipping estimation (one Flipkart candidate reported this hurt).
