Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key user_id keeps one listener's plays in order. Consumer-group sizing: a group uses at most one consumer per partition, so with 48 partitions the history consumer can scale to 48 pods; KEDA adds pods when lag grows. The HPA on the playback Deployment scales on CPU and p99 latency, because each request is small and stateless.

"How do you scale the streaming servers horizontally?" (Amazon, 2026-07). The honest answer: our "streaming servers" are only the playback service, which is stateless (token in, signed URL out), so you add pods behind the load balancer. The heavy bytes are scaled by the CDN, which is already horizontal across thousands of edges. If you run your own origin or edge tier, put it behind consistent hashing on track_id so each node caches a stable slice of the catalogue instead of every node caching everything.
