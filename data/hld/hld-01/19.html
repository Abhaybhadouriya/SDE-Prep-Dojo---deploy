Quick quiz

Your app servers keep the user's cart in local memory. What breaks when you add more servers behind a load balancer?

  1. Nothing
  2. The database runs out of connections
  3. A user's next request may land on another server that does not have their cart
Horizontal scaling needs stateless servers. Move the cart into a shared store (Redis) or the database.

Which load balancer can send /api/search and /api/cart to different services?

  1. An L7 load balancer
  2. An L4 load balancer
  3. Either - they are the same
Only an L7 proxy reads the HTTP request (path, headers). L4 sees only IPs and ports.

In cache-aside, what should the app do to the cache after updating a row in the database?

  1. Nothing, the TTL handles it
  2. Update the cached value with the new row
  3. Flush the whole cache
  4. Delete that key so the next read refills it
Deleting is simpler and safer than updating, because two writers updating the cache in the wrong order can leave an old value behind.

With N=3 replicas, which setting guarantees a read overlaps the latest successful write?

  1. W=1, R=1
  2. W=1, R=2
  3. W=2, R=2
Overlap needs W + R > N. 2 + 2 = 4 > 3. With W=1, R=2, the sum is 3, which is not greater than N.

You go from 4 to 5 cache servers. Roughly what share of keys move with consistent hashing?

  1. About 1/5 - only the keys the new server takes over
  2. About 4/5
  3. All of them
Only keys in the new server's arcs move (about 1/N). With hash % N, about 80% would move, as the script on this page shows.

Which statement about CAP is correct?

  1. You can build a CA distributed system by picking good hardware
  2. When the network partitions, you choose between consistency and availability
  3. CAP means a system is always either fast or correct
Partitions happen whether you like it or not. CAP describes the choice you must make while one is happening.

Your queue gives at-least-once delivery, so a consumer may see the same "charge order 42" message twice. What makes processing safe?

  1. Make the consumer faster so it never crashes
  2. Switch to at-most-once delivery
  3. Make the consumer idempotent: record each message ID and skip IDs already processed
At-least-once means duplicates will happen. An idempotent consumer (dedupe by message ID, or an upsert keyed by it) turns a duplicate into a no-op. At-most-once would lose charges instead.

Chat messages arrive at 200,000 writes per second and are always read by chat ID, newest first. Which store family fits best?

  1. Wide-column (Cassandra-style): partition by chat ID, cluster by time
  2. A single relational primary with joins
  3. A graph database
The access pattern is "one key, a range sorted by time", at very high write rates. A wide-column store partitioned by chat ID (with time buckets) handles that well; a single SQL primary would be the write bottleneck.
