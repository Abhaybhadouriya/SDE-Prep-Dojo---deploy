60-second answers to say out loud

Practise these until they sound like you, not like a textbook.

"What is a cache and how does it go stale?" - "A cache keeps copies of hot data in memory so most reads skip the database. I use cache-aside with a TTL and delete the key on every write. It goes stale when the database changes but the copy does not - the TTL caps how stale, and delete-on-write fixes most cases. The hard parts are stampedes when a hot key expires, which I fix by letting one request refill while others wait, and hot keys, which I fix with a small local cache."

"What is sharding and how do you pick a key?" - "Sharding splits data across machines so each holds a part, which scales size and writes. I pick the key from the main query - usually the user or tenant ID - so most requests touch one shard. It needs many distinct values and even traffic. I hash it so load spreads evenly, and use consistent hashing so adding a shard moves only a small share of data. The risks are hot keys and cross-shard queries, so I plan for both."

"Replication vs sharding?" - "Replication copies the same data to several machines for survival and read scale; sharding splits different data across machines for size and write scale. Real systems shard first and then replicate each shard, usually three copies with one leader per shard."

"Why a queue here?" - "The user only needs to know the order was placed. Email, analytics and search indexing can happen a second later. Publishing one event to Kafka lets those consumers work at their own pace, absorbs spikes, and means a slow email provider cannot fail an order. Delivery is at-least-once, so consumers are idempotent by message ID."
