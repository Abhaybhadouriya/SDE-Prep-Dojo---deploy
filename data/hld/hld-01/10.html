Consistent hashing: the ring Must know: ring + vnodes Deep dive: the details

The problem: with hash(key) % N, changing N from 4 to 5 servers changes the answer for most keys. For a cache, that means almost every key misses at once; for a database, it means moving most of the data. Consistent hashing fixes this. Picture a clock face (the ring) numbered 0 to 232 - 1 (after the top it wraps back to 0). Hash each server onto the ring. Hash each key onto the ring too. A key belongs to the first server clockwise from it.

Explain like I'm 5

Kids sit around a round table. Toys are scattered around the edge. Each toy belongs to the next kid sitting clockwise from it. When a new kid sits down between two others, only the toys between the new kid and the kid before them change owner. Everyone else keeps their toys.

  1. The ring. Four servers A-D are hashed to positions on a circle. The white dot shows a key travelling clockwise to its owner.
  2. Keys. Each key is hashed onto the ring and owned by the first server clockwise. B owns the most keys here, because its arc is big - a sign we need virtual nodes.
  3. Add a server. E lands between A and B. Only the keys in that arc (k1, k6) move, from B to E. With modulo hashing most keys would have moved.
  4. Virtual nodes. Each server appears at many points on the ring. Arcs become small and even, load spreads fairly, and a bigger machine can simply get more points.
  5. Replication. To keep 3 copies, store each key on its owner plus the next 2 distinct servers clockwise.

Do not take my word for it. This short Python script compares the two methods on 100,000 keys:

import bisect, hashlib
from collections import Counter

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % (2**32)

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.vnodes, self.points = vnodes, []        # sorted (hash, node)
        for n in nodes:
            self.add(n)
    def add(self, node):
        for i in range(self.vnodes):
            bisect.insort(self.points, (h(f"{node}#{i}"), node))
    def owner(self, key):
        i = bisect.bisect(self.points, (h(key), ""))
        return self.points[i % len(self.points)][1]    # wrap around the ring

keys = [f"user:{i}" for i in range(100_000)]

before = {k: h(k) % 4 for k in keys}
after  = {k: h(k) % 5 for k in keys}
print(f"modulo   4 -> 5 servers: {sum(before[k] != after[k] for k in keys)/len(keys):.1%} of keys moved")

ring = Ring(["A", "B", "C", "D"])
before = {k: ring.owner(k) for k in keys}
ring.add("E")
after = {k: ring.owner(k) for k in keys}
print(f"ring     4 -> 5 servers: {sum(before[k] != after[k] for k in keys)/len(keys):.1%} of keys moved")
print("keys per server:", dict(sorted(Counter(after.values()).items())))
$ python ring.py
modulo   4 -> 5 servers: 80.2% of keys moved
ring     4 -> 5 servers: 14.8% of keys moved
keys per server: {'A': 20285, 'B': 21013, 'C': 20450, 'D': 23467, 'E': 14785}

Modulo moved 80% of the keys. The ring moved about 15%, and every moved key went to the new server E - nothing shuffled between old servers. The ideal is 20% (1/5); E got a bit less because its 100 random points happened to cover slightly less of the ring. More virtual nodes bring it closer to even.

Where it is used: Amazon's Dynamo paper, Cassandra, Discord (routing requests by channel), Slack (placing channel servers on a ring), many cache clients, and L4 load balancers like Maglev. Full design: Distributed Key-Value Store (Dynamo).

From your world

This is resilient hashing in ECMP. Plain ECMP with hash % paths reshuffles almost every flow when a link goes down; resilient hashing keeps a bucket table so only flows on the dead link move. Consistent hashing is the same goal: when a member leaves or joins, re-home only its share. A consumer-group rebalance in Kafka is the same problem again. Where this breaks: ECMP buckets are a fixed table in hardware; a hash ring is a sorted list in software with no fixed size, and you can weight members by giving them more points.

Stop here for SDE-1. Ring, clockwise owner, "adding a node moves about 1/N of the keys", virtual nodes for balance. That is enough. Bounded-load variants, jump hash and rendezvous hashing are SDE-2+ bonus material covered in Distributed Building Blocks, "Beyond the ring".
