CAP and PACELC: what happens when the network breaks Must know

Three words first (one-line version in the glossary). Consistency (C) in CAP means every read sees the most recent write, as if there were only one copy. Availability (A) means every request to a working node gets a non-error answer. Partition tolerance (P) means the system keeps running when the network between nodes drops messages.

You asked: is it really "pick two"? No. In a distributed system the network will partition sometimes, so P is not optional. CAP really says: when a partition happens, you must choose between C and A for the requests that cannot reach the other side.

Level 4 - Advanced

PACELC: the part CAP forgets

Partitions are rare. Most of the time the network is fine, and you still face a trade-off. Daniel Abadi's PACELC says: if there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. Waiting for replicas to agree makes every request slower, even on a perfect network.

System (default settings)During partitionNormal operationPACELC
DynamoDB, CassandraStay availablePrefer low latencyPA/EL
Google Spanner; a single-leader RDBMS with synchronous replicas and reads from the primaryStay consistentPay latency for consistencyPC/EC
etcd, ZooKeeper (coordination)Minority side refuses writesEvery write waits for a majorityPC/EC

Careful with the RDBMS row: it is PC/EC only when replicas are synchronous or reads go to the primary. The common setup, asynchronous replicas with reads spread to the followers, behaves EL in normal operation: reads are fast but can be stale.

Footnote: DynamoDB the AWS service is not the 2007 Dynamo paper. Each DynamoDB partition has a leader (writes are replicated with Paxos), and you choose an eventually consistent read (the default) or a strongly consistent read (served by the leader) per request. It lands in PA/EL only because of that default. Cassandra and Riak are the leaderless, Dynamo-paper-style stores. The common PostgreSQL/MySQL setup (asynchronous replicas, some reads sent to followers) behaves EL in normal operation: follower reads are fast but can be stale.

Many stores let you tune this per request. Cassandra and DynamoDB let you ask for stronger reads (a quorum, or a "strongly consistent read") when a particular read needs it, at extra latency.

From your world

A partition is a split-brain scenario in an HA cluster. Choosing C is what a well-built cluster does: the side without quorum stops serving (fences itself). Choosing A is two routers both forwarding with their own view, possibly inconsistent, until the link heals and they reconcile. Eventual consistency is OSPF flooding until every LSDB matches. Where this breaks: routing converges on its own in seconds; application data conflicts (two people edited the same cart) need a business rule to merge, not just "newest wins".

60-second answer: "CAP says that during a network partition a replicated system must choose between consistency and availability; partitions are not optional, so it is really C versus A when the network breaks. etcd and Spanner choose consistency; Cassandra defaults to availability, and DynamoDB defaults to eventually consistent reads (a leader per partition, but you can ask for a strongly consistent read). PACELC adds that even without a partition you trade latency for consistency. In a design I choose per data type: payments and inventory decrements get strong consistency; likes, feeds and view counts can be eventually consistent."
