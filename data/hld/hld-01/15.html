Common mistakes and gotchas

  1. Sharding on day one. Start with one database, caching and read replicas. Shard when you can say which limit you hit (write QPS, data size).
  2. "I'll add a cache" without saying how it stays fresh. Always say: what is cached, the TTL, and what happens on a write (delete the key).
  3. Forgetting the load balancer is a box that can fail. Say "LBs run as a redundant pair or managed fleet".
  4. Saying "CAP: I pick CA". A distributed system cannot opt out of partitions. Say what happens during a partition.
  5. Using a sequential or time-based shard key for heavy writes. All new rows land on the last shard (a hot shard). Hash it, or add a bucket.
  6. Reading your own write from a lagging replica. Route a user's reads to the leader for a short time after they write.
  7. Treating at-least-once as exactly-once. Duplicates will happen. Make consumers idempotent with message IDs.
  8. Caching personal pages on a CDN. Use Cache-Control: private or put the user in the cache key.
  9. Running a Redis cache on the defaults. maxmemory 0 means it grows until the OS kills it; a limit with noeviction means writes fail when full. Set both maxmemory and maxmemory-policy allkeys-lru.
  10. Over-explaining internals. Name the box, say why, say the trade-off, move on. Go deeper when asked.
