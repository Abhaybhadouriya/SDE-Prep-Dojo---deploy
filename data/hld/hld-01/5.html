Caching: keep the popular answers close Must know

A cache is a small, fast store that keeps copies of answers you will probably need again, so you skip the slow work. A hit means the answer was in the cache. A miss means you had to go to the slow source. The hit ratio (hits / all lookups) decides how much a cache helps: at a 95% hit ratio, only 1 request in 20 reaches the database.

You asked where caches go. The answer: at every layer, from the user's phone to the database itself.

Cache-aside: the pattern to draw by default

In cache-aside (also called lazy loading), the application talks to both the cache and the database itself. Click through a read miss, a read hit, and a write.

  1. Read, miss. The app asks the cache for user:42. Not there.
  2. Read the database. The app runs the slow query and gets the row.
  3. Fill the cache. The app stores the row in Redis with a TTL (time to live), so it expires on its own.
  4. Read, hit. The next read is served from RAM in about a millisecond. The database is not touched.
  5. Write. Update the database first, then delete the cache key (not update it). The next read refills it with fresh data.
import json, random

def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached is not None:                       # hit
        return json.loads(cached)
    row = db.fetch_one("SELECT * FROM users WHERE id = %s", (user_id,))   # miss
    ttl = 300 + random.randint(0, 60)            # jitter so keys do not all expire together
    redis.set(key, json.dumps(row), ex=ttl)
    return row

def update_user(user_id, fields):
    db.execute("UPDATE users SET name = %s WHERE id = %s", (fields["name"], user_id))
    redis.delete(f"user:{user_id}")              # delete, do not update: avoids racing writers

Try the cache yourself with Redis in Docker (docker run -d --name redis -p 6379:6379 redis:8; any recent tag behaves the same here):

$ docker exec -it redis redis-cli
127.0.0.1:6379> SET user:42 "{\"name\":\"Asha\"}" EX 300
OK
127.0.0.1:6379> GET user:42
"{\"name\":\"Asha\"}"
127.0.0.1:6379> TTL user:42
(integer) 297
127.0.0.1:6379> DEL user:42
(integer) 1
127.0.0.1:6379> GET user:42
(nil)
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"

That last line matters, together with one you did not see: by default maxmemory is 0 (no limit on 64-bit builds) and the policy is noeviction. With those defaults Redis never evicts anything; it just keeps growing until the operating system's OOM killer steps in. For a cache, set both: CONFIG SET maxmemory 2gb and CONFIG SET maxmemory-policy allkeys-lru (or allkeys-lfu). If you set a limit but keep noeviction, writes fail with an OOM error once memory is full instead of old keys being thrown out.

The other write strategies

StrategyHow a write worksGoodBadUse for
Cache-asideApp writes DB, deletes cache keySimple; cache holds only what is readFirst read after a write is a miss; small race windowThe default for most read-heavy services
Read-throughCache library loads from DB on a miss for youApp code is simplerNeeds a cache that knows your DBSame cases as cache-aside
Write-throughWrite cache and DB together, synchronouslyCache is always freshEvery write is slower; caches data nobody readsRead-after-write heavy data, like profiles
Write-back (write-behind)Write cache now, flush to DB laterVery fast writes, batchingData loss if the cache dies before flushingCounters, metrics, view counts
Write-aroundWrite DB only; cache fills on readDoes not pollute the cacheRecent writes always missWrite-once, rarely-read data such as logs

Eviction is how a full cache picks what to throw out: LRU (least recently used), LFU (least frequently used) or by TTL. LRU is the usual default answer.

How caches go wrong (the interview gold)

ProblemWhat happensFixes
Stale dataThe DB changed but the cache still has the old valueTTL as a safety net; delete on write; invalidate from the DB's change log (CDC, change data capture: reading the database's own write-ahead log, like tailing a commit log, and deleting the keys that changed); versioned keys
Cache stampede (thundering herd)A hot key expires and 10,000 requests miss at once and all hit the DBRequest coalescing (one request refills, others wait), a lock or lease per key, jittered TTLs, serve-stale-while-refreshing
Hot keyOne key (a celebrity, a flash-sale item) gets more traffic than one cache node can serveSmall local cache in each app server; copies of the key with suffixes (item:7#1..#8) spread across nodes
Cache penetrationRequests for keys that do not exist always miss and hit the DB (often an attack)Cache the "not found" result briefly; a Bloom filter of keys that exist (a tiny bit array that can answer "definitely not here"; details in Building Blocks)
Cold startA new or restarted cache is empty, and the DB gets the full loadWarm the cache before taking traffic; bring nodes back slowly

Facebook's NSDI 2013 paper "Scaling Memcache at Facebook" describes leases: on a miss, the cache gives one client a token to refill the key, and others wait briefly or get a slightly stale value. That one idea fixes both the stampede and stale sets from racing writers. Discord describes request coalescing in its message-store post: many readers of one hot row share a single database query. See Scaling Reads (and caching pitfalls) and the design Distributed Cache.

From your world

This is the CPU cache hierarchy one zoom level up: browser = L1, CDN = L2, Redis = L3, database = DRAM, object store = disk. Write-through and write-back mean exactly what they mean in a CPU, including the risk that write-back loses dirty lines on power loss. The FIB is a cache of the RIB. Where this breaks: CPUs have hardware coherence protocols (MESI) that invalidate every copy for you. Distributed caches have no coherence protocol; you must invalidate yourself, and messages can be lost or delayed. That is why "cache invalidation is hard".

60-second answer: "I default to cache-aside with Redis: read the cache, on a miss read the DB and set the key with a TTL; on a write, update the DB then delete the key. The TTL bounds staleness. For hot keys I add a small in-process cache and coalesce misses so one request refills the key. If the data must be fresh right after a write, like a user's own profile, I read from the DB for that user for a short time or use write-through."
