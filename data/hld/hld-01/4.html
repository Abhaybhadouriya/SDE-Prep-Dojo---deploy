Load balancers: L4 vs L7 Must know

A load balancer (LB) sits in front of a group of servers and spreads requests across them. It also does health checks: if a server stops answering, the LB stops sending it traffic. You asked which one is "the" load balancer in diagrams - there are two kinds, and real systems often use both.

How the LB picks a server

AlgorithmHow it worksUse when
Round robin1, 2, 3, 1, 2, 3...Servers are equal and requests are similar
Weighted round robinBigger servers get more turnsMixed server sizes, a canary (new version) at 5% of traffic
Least connectionsSend to the server with the fewest open requestsRequests vary a lot in length
Power of two choicesPick 2 servers at random, send to the less busy oneLarge fleets; nearly as good as least-connections with little shared state
IP hash / consistent hashSame client (or key) always goes to the same serverSticky sessions, cache affinity

Health checks come in two kinds: active (the LB calls /health every few seconds) and passive (it notices real requests failing and ejects the server, called outlier detection). The LB itself must not be a single point of failure: real setups run LBs in pairs or fleets, often with a floating IP or anycast in front.

From your world

An L4 LB is ECMP plus a NAT table. Google's Maglev and Facebook's Katran hash the 5-tuple with consistent hashing so a flow stays on one backend even when the backend set changes - the same reason a router keeps one flow on one ECMP path (to avoid reordering). A health check that ejects a server is a readiness signal that pulls a member out of an ECMP group. Where this breaks: an L7 proxy is not a forwarding device at all; it is a full TCP endpoint that reads, parses and opens a new connection to the backend.

Try it: a real L7 load balancer in 2 minutes

This lab runs two tiny web servers and NGINX in front of them with Docker. Save this as nginx.conf:

upstream app_servers {
    # default is round robin; try "least_conn;" here
    server web1:80 max_fails=3 fail_timeout=10s;
    server web2:80 max_fails=3 fail_timeout=10s;
}
server {
    listen 80;
    location / {
        proxy_pass http://app_servers;
    }
}
docker network create lb-lab
docker run -d --name web1 --network lb-lab traefik/whoami
docker run -d --name web2 --network lb-lab traefik/whoami
docker run -d --name lb --network lb-lab -p 8080:80 \
  -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" nginx:1.28
for i in 1 2 3 4; do curl -s localhost:8080 | grep Hostname; done

The hostnames alternate (round robin). When web1 dies, NGINX still tries it in its turn; the connect fails and NGINX retries that same request on web2 (proxy_next_upstream error timeout is the default). After 3 failures within 10 s (max_fails=3 fail_timeout=10s) it stops sending to web1 for 10 s, then tries it again. Users see no errors, but the first few requests can be a few seconds slow while the connect to the dead IP times out (NGINX resolved web1 at startup, so it keeps dialling the old address). Lowering proxy_connect_timeout (for example 2s; the default is 60 s) shortens that. Your container IDs will differ. Clean up with docker rm -f web1 web2 lb && docker network rm lb-lab. The Docker networking page explains how web1 resolves by name, and Kubernetes Services show the same idea built into a cluster.
