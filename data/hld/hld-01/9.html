Sharding: split the data across machines Must know

Replication copies all the data to every replica. That does not help when the data is too big for one machine, or when there are too many writes for one leader. Sharding (also called partitioning) splits the data so each machine (a shard) holds only a part. Each shard is then usually replicated too.

The most important choice is the shard key: the field that decides which shard a row lives on.

How to pick a shard key

  1. Follow the main query. If almost every query says "for this user", shard by user_id. Then one query touches one shard.
  2. High cardinality. The key needs many distinct values (millions of users, not 3 countries). AWS's DynamoDB docs make exactly this point for partition keys.
  3. Even load, not just even data. Watch for a hot key: a celebrity's account, one flash-sale SKU, one huge chat channel. One key cannot be split by hashing; you need special handling (split the key into sub-keys, cache it, queue its writes).
  4. Avoid cross-shard work. Joins and transactions across shards are slow and complex. Group data that is used together under the same key (all of one user's orders on that user's shard).

Real example: Discord's message store uses the partition key (channel_id, bucket), where a bucket is a fixed window of time. That keeps one channel's recent messages together for fast reads, while stopping a very old, very busy channel from becoming one giant partition. (Source: Discord's "How Discord stores trillions of messages" post.)

Careful: sharding is a one-way door. It makes joins, unique constraints, transactions and schema changes harder, forever. In an interview, say why you need it ("writes exceed one primary" or "data is 50 TB") before you shard. YouTube built Vitess to shard MySQL when it had no choice.

Dynamic range partitioning: let the database split hot ranges Deep dive

Explain like I'm 5

A library puts books on shelves by the first letter of the title. One day the "M" shelf is overflowing while "X" is nearly empty. Nobody planned this. So the librarian does two simple things: she cuts the "M" shelf in two ("Ma-Mm" and "Mn-Mz") and carries one half to an empty bookcase. Later, when "X" and "Y" are both tiny, she puts them back on one shelf. She never re-sorts the whole library; she only splits, merges and moves single shelves.

Range sharding with fixed ranges (A-H, I-P, Q-Z, chosen by a human) breaks as soon as the data does not look like your guess. Dynamic range partitioning fixes that. The database starts with one range covering every key, and from then on it manages ranges by itself:

  1. Split a range in two when it grows past a size limit, or when it gets too much traffic (a load-based split).
  2. Move one half to a less-busy node. A balancer process keeps the nodes roughly even.
  3. Merge small, cold neighbouring ranges so you do not end up with millions of tiny ones.
  4. Route every request with a small metadata map ("keys from m up to t live on node 2") that clients cache and refresh when they are told it changed.

You keep the big win of range sharding (neighbouring keys stay together, so range scans hit one or two shards) and lose most of its pain (hand-picked ranges that turn uneven). Bigtable, HBase, MongoDB, DynamoDB, Spanner, CockroachDB and TiKV all work this way under different names.

  1. One range holds every key from a to z. It has grown past the size limit and is taking most of the writes.
  2. The database picks a middle key (m) and splits the range in two. On the same node this is only a metadata change.
  3. The balancer moves [m, z) to the emptier node 2. In MongoDB this copies documents; in Bigtable it is nearly free because the data lives on a shared file system.
  4. The router map gets a new version. A client with an old map sends the write to node 1, is told "moved", re-reads the map and retries on node 2.
  5. Later, small cold neighbours are merged, so the number of ranges (and the size of the map) stays sane.

From your world

A range map is a routing table, and a range split is prefix de-aggregation. One router announces 10.0.0.0/16; when that prefix carries too much traffic, you announce the two more-specific /17s and point one at a different next hop. A merge is route summarization back into the /16. Clients caching the map are like a FIB with a version number: a stale entry gets a "moved" redirect instead of a silent black hole.

Where this breaks: changing a next hop is instant because packets carry no state. Moving a MongoDB range means copying gigabytes first and then flipping ownership (make-before-break), which is why balancers limit themselves to one migration per shard at a time. Bigtable and HBase cheat by keeping the bytes on a shared file system, so for them a move really is just a next-hop change.

Gotchas: (1) a single hot key can never be split; splitting works on ranges of keys, so a celebrity row still needs caching or key splitting. (2) A brand-new table has one range: pre-split it before a bulk load. (3) Moves cost I/O and network; MongoDB lets you set a balancing window so migrations run off-peak. (4) DynamoDB adaptive capacity cannot exceed the table's total provisioned throughput or the per-partition maximum.
