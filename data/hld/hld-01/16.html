Interview questions

Company tags show where these questions are frequently reported, not a promise that they are always asked.

What happens when you type a URL and press Enter? Where would you add caching?

DNS resolves the name (cached in the browser, OS and resolver by TTL). The browser opens TCP and TLS to the nearest edge: static assets come from the CDN. Dynamic requests go to a load balancer, which picks a stateless app server. The app checks Redis, and on a miss reads the database and fills the cache. The response returns with Cache-Control headers that decide whether the browser and CDN may keep it. So there are caches at the browser, DNS, CDN, app memory, Redis and the database buffer pool.

How to answer

Walk the hops left to right in one breath, naming the cache at each one and its TTL. Then offer to go deep on one hop ("I can talk about TLS or the cache invalidation, which would you like?"). Do not spend five minutes on DNS packet formats.

Likely follow-ups
  • How does the CDN know when content changed? (TTL, versioned file names, purge API)
  • What if the LB dies? (redundant pair, floating IP or anycast)
  • Where does TLS terminate and why? (at the LB/edge, to offload CPU and allow L7 routing)
Vertical vs horizontal scaling: when would you pick each?

Vertical first, because it is simple and needs no code changes - and today's machines are big. Horizontal when you hit the hardware ceiling, need to survive a machine failure, or want to scale with traffic. Horizontal scaling requires stateless app servers (sessions in Redis or a signed token) behind a load balancer. The database is the hard part: scale it vertically, add a cache and read replicas, and shard only when writes or data size force it.

How to answer

Give the default ("start vertical"), the trigger for switching, and the requirement (statelessness). Close with the DB caveat - that is what separates a good answer.

Likely follow-ups
  • Where do sessions go? Pros and cons of sticky sessions?
  • How do you scale the database?
Explain CAP. Give an example of a CP and an AP system.

During a network partition, a replicated system must either refuse some requests to stay consistent (CP) or answer them with possibly stale data to stay available (AP). Partitions are not optional, so "pick two" is misleading. CP examples: etcd, ZooKeeper, Spanner - the minority side stops accepting writes. AP examples: Cassandra or Riak at consistency level ONE - every reachable replica answers and they reconcile later. DynamoDB is in between: its default eventually consistent reads can be served by any replica, but writes and strongly consistent reads need the partition leader. PACELC adds that without a partition you still trade latency for consistency.

How to answer

Correct the "pick two" myth in the first sentence, give one example on each side, then tie it to the design in front of you: "for the inventory decrement I want CP; for the product page view count, AP is fine."

Likely follow-ups
  • What is PACELC?
  • Can one system be CP for some data and AP for other data? (Yes - tunable consistency per request)
  • What does the user see in each case?
SQL or NoSQL for this service? How do you decide?

From the access patterns and the guarantees needed, not fashion. If the data needs transactions, constraints and joins - orders, payments, bookings, inventory - I use a relational database and scale reads with replicas, shard later by customer or tenant. If it is huge write volume always read by one key - chat messages, feeds, location pings, events - I use a wide-column or key-value store like Cassandra or DynamoDB with a carefully chosen partition key. Search goes to Elasticsearch beside the main store, and files go to blob storage.

How to answer

Use the sentence: "I'll use X because the main access pattern is A and we need B; the cost is C, which is fine because D." Name the partition key if you pick NoSQL.

Likely follow-ups
  • What partition key would you use and what if it gets hot?
  • How would you shard the SQL database later?
How does consistent hashing work, and why do we need virtual nodes?

Servers and keys are hashed onto the same ring; a key belongs to the first server clockwise. Adding or removing a server only moves the keys in its arc - about 1/N of them - instead of nearly all keys as with hash % N. With few servers, the arcs are uneven, so each server is placed at many points (virtual nodes). That evens out load, lets a bigger machine take more points, and means a new server takes a little from everyone. Replicas are stored on the next N distinct servers clockwise. Dynamo, Cassandra and many cache clients work this way.

How to answer

Start with the problem (modulo reshuffles everything), then the ring, then vnodes, then one real system. Drawing a quick circle helps.

Likely follow-ups
  • How do you find the owner quickly? (binary search over sorted ring points)
  • What about a single hot key? (the ring does not help; split or cache it)
  • Alternatives? (rendezvous hashing, jump hash)
Cache-aside vs write-through: which would you use, and how do you handle stale data?

Cache-aside by default: read the cache, on a miss read the DB and set the key with a TTL; on a write, update the DB and delete the key. It only caches what is read and survives a cache outage. Write-through keeps the cache fresh but slows every write and caches unread data. Staleness is bounded by the TTL; deleting on write fixes most of it. There is still a small race (a slow reader sets an old value after a delete), which leases or versioned values fix - Facebook's memcache paper describes leases.

How to answer

Pick one, justify, then show you know the failure: stale reads and the race. Mention TTL jitter and stampedes for bonus points.

Likely follow-ups
  • Why delete instead of update the key?
  • What is a cache stampede and how do you stop it?
  • What if Redis goes down?
When would you add a message queue, and what delivery guarantee do you get?

I add a queue when work does not have to finish while the user waits (emails, thumbnails, search indexing, analytics), when one event has several independent consumers, or when traffic is spiky and the downstream cannot absorb the peak. The producer writes the event and replies; consumers drain at their own pace, and a dead consumer means messages wait instead of orders failing. The guarantee I design for is at-least-once: a consumer can crash after doing the work but before acknowledging, so the message is delivered again. Therefore every consumer is idempotent: each message carries a unique ID, and the consumer records processed IDs (a unique constraint, or an upsert keyed by that ID) so a repeat changes nothing. Messages that keep failing go to a dead-letter queue with an alert. For the tool: a task queue such as SQS or RabbitMQ when each job is done once and deleted; a log such as Kafka when several services must read the same events, ordering per key matters, or I need replay.

How to answer

Three reasons (async work, fan-out, load levelling), then the guarantee and its consequence (idempotency), then the failure path (retries, DLQ), then the tool choice. Do not promise "exactly-once" end to end; say "at-least-once plus idempotent writes".

Likely follow-ups
  • Kafka vs SQS for this? (replay and many consumer groups vs a simple managed task queue)
  • How do you keep order for one user's events? (same partition key)
  • The queue keeps growing - what do you do? (check consumer lag, scale consumers up to the partition count, find the slow dependency)
Your primary database dies. Walk me through failover and what data you can lose.

First, detection: health checks or a coordinator (for example Patroni with etcd, or the managed service) notice the primary missed several heartbeats. Second, promotion: the most up-to-date replica becomes the new primary. Third, re-routing: clients reach it through a DNS name, a proxy or a virtual IP that moves. Fourth, what you lose depends on the replication mode. With asynchronous replication, writes the old primary acknowledged but had not yet shipped are lost; that window is the replication lag, usually small but larger under load. With synchronous (or semi-synchronous) replication to at least one replica, an acknowledged write already exists on two machines, so you lose nothing, at the cost of slower writes. Finally, split-brain: if the old primary was only cut off and comes back still believing it is primary, two primaries would accept writes. You prevent that with fencing: the old node must lose its lease or be powered off (STONITH, "shoot the other node in the head") before the new one takes writes, and a majority-based coordinator decides who is primary.

How to answer

Use four words: detect, promote, re-route, fence. Then give the data-loss answer as a trade-off: async = small loss window, sync = no loss but slower writes. Use the terms RPO (how much data you may lose) and RTO (how long you are down) if the interviewer does.

Likely follow-ups
  • How long are writes unavailable? (detection time plus promotion; check your managed service's documented failover time instead of guessing)
  • How do clients find the new primary?
  • What if the network, not the primary, failed? (exactly the split-brain case; the majority side decides)
How would you shard a users table? What happens when one shard gets hot?

Shard by a hash of user_id, since nearly every query is "for this user", using consistent hashing or a lookup directory so I can move ranges later. Keep a user's related rows (orders, addresses) on the same shard to avoid cross-shard joins. A hot shard usually means a hot key (a celebrity) or a bad key (time-based). Fixes: cache the hot user's data, split a hot range to a new shard via the directory, and for one extreme key, split its writes into sub-keys and merge on read. Global queries ("all users in Pune") go to a separate index or analytics store.

How to answer

Key choice with reason, then the hot-shard plan, then cross-shard queries. Name the trade-off: hashing loses range scans.

Likely follow-ups
  • How do you re-shard without downtime? (double-write or copy plus catch-up, then switch the directory)
  • How do you keep a username unique across shards?
L4 vs L7 load balancer - which would you use?

Usually both. An L4 balancer works on IP and port, is very fast and protocol-agnostic, and is the front door (AWS NLB, Maglev). Behind it, a fleet of L7 proxies (NGINX, Envoy, ALB) terminate TLS, read HTTP and route by path or header, retry, rate-limit and do canary splits. If the service is plain TCP (a database, MQTT, a game server), L4 alone is enough.

How to answer

Define both in one line each, then say "both, layered" and why. Your networking background is a strength here - use it briefly (ECMP, consistent hashing for flow affinity).

Likely follow-ups
  • How does the LB know a server is unhealthy?
  • How do you drain a server before a deploy?
How do databases like Bigtable, HBase or MongoDB keep range shards balanced without a human picking the ranges?

They use dynamic range partitioning. The table starts as one range. When a range passes a size limit (MongoDB's default range size is 128 MB, HBase's region limit 10 GB) or gets a traffic spike, the database splits it at a middle key. A balancer then moves one half to a less-loaded node and updates a versioned metadata map that routers or clients cache. Small, quiet neighbours are merged back. Bigtable and HBase keep data on a shared file system (Colossus, HDFS), so a move only changes ownership; MongoDB copies the documents, which is why it limits migrations and offers a balancing window.

How to answer

Say the loop in one breath: split, move, merge, update the map. Then name the one thing splitting cannot fix: a monotonically increasing key (all writes go to the newest range) or a single hot key. Offer the fix: a hashed or salted key prefix.

Likely follow-ups
  • What happens to a request that arrives at the old owner mid-move? (It is rejected with a "moved"/stale-config error, the client refreshes the map and retries.)
  • Why pre-split a new table before a bulk load?
  • How does DynamoDB handle one very hot item? (Adaptive capacity isolates it on its own partition, up to 3,000 RCU / 1,000 WCU.)

Scenario: the database is at 95% CPU every evening

A product-listing service slows down every evening at peak. The single PostgreSQL primary is at 95% CPU, and 90% of the queries are reads of product pages. The interviewer asks what you would do.

Weak answer: "Shard the database into 10 shards."

Strong answer: "First, confirm it is reads with the slow-query log. With 90% reads, I add a Redis cache-aside layer for product pages with a TTL of a few minutes and delete-on-update - that should remove most of the load. I add read replicas for whatever still misses, and check for missing indexes. I would shard only if writes became the bottleneck, which they are not here. I would also add a small in-process cache for the top products, because peak traffic is often concentrated on a few items."

Likely follow-ups
  • How do you stop a stampede when a hot product's key expires?
  • The price changed but users still see the old one - why, and how do you fix it?

Scenario: users see their own update "disappear"

After users change their display name, some of them see the old name when the page reloads. A refresh a few seconds later shows the new one.

Weak answer: "It is a caching bug, clear the cache."

Strong answer: "That is replication lag: the write went to the leader and the reload read a follower that had not caught up yet. I would give read-your-writes consistency: for a short window after a user writes, route that user's reads to the leader, or remember the log position of their write and only read from a replica that has reached it. I would also check whether a cache was refilled from a lagging replica, and refill caches from the leader."

Likely follow-ups
  • How would you measure replication lag?
  • What if the leader is in another region?
