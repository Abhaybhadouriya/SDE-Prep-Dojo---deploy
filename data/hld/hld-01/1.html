Client, server, and what happens when you type a URL Must know

A client is the thing that asks (a phone app, a browser). A server is a program on a computer that answers. They talk over HTTP (a text protocol on top of TCP, usually encrypted with TLS, which makes it HTTPS). A request is one question ("give me the home page"), and a response is one answer.

An interviewer favourite, frequently reported at Amazon and Microsoft: "What happens when you type a URL and press Enter, and where would you add caching?" Click Next to walk through it. Each box is a real component you will draw in designs.

  1. DNS lookup. The browser asks DNS "what is the IP for shop.com?". The answer is cached by the browser, the OS and the resolver for the record's TTL. Cache #1.
  2. CDN edge. Static files (images, JavaScript, CSS) come from a CDN server near the user. Cache #2. Only dynamic requests go further.
  3. TCP + TLS to the load balancer. The connection lands on a load balancer, which hides many servers behind one address.
  4. App server. The LB picks one of several identical, stateless app servers to run the business logic.
  5. Cache. The app first asks an in-memory cache like Redis. If the answer is there (a hit), we are done in about a millisecond. Cache #3.
  6. Database. On a miss, the app reads the database, the durable source of truth, then fills the cache for next time.
  7. Back to the user. The response returns. HTTP headers like Cache-Control decide whether the browser or CDN may keep it. Cache #4.

You can see the first few steps yourself. curl can print how long each phase took:

curl -o /dev/null -s -w "dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n" https://example.com
$ curl -o /dev/null -s -w "dns=... total=%{time_total}\n" https://example.com
dns=0.012418 connect=0.045102 tls=0.098770 first_byte=0.151335 total=0.151671
# example output - your numbers depend on where you are.
# Each value is cumulative seconds since start. Run it twice: DNS drops to ~0 (cached).

"A million users" in real numbers

You asked what "scale to a million users" actually means. It sounds huge, but turn it into requests per second (RPS or QPS) and it becomes concrete. The trick: a day has 86,400 seconds, so round it to 100,000 (105).

Assumption (rule of thumb)Per dayAverage RPSPeak RPS (x3)
1M daily users x 20 requests each20M~230~700
10M daily users x 20 requests200M~2,300~7,000
100M daily users x 20 requests2B~23,000~70,000

So a million daily users is a few hundred requests per second. One decent server can often handle that. The design gets interesting at 10k+ RPS, at large data sizes, or at sudden peaks like a flash sale (where traffic can be 10-100x normal for a few minutes). A full method lives in Back-of-Envelope Estimation.

From your world

You think in packets per second on one ASIC, often in the millions. A web request is far heavier than a packet: it may parse JSON, check auth, call three other services and read a database, costing milliseconds of CPU and I/O, not nanoseconds. So "only 20,000 RPS" can need dozens of servers. Where this breaks: forwarding is stateless per packet; requests usually touch shared state (the database), and that shared state is what limits scale.
