Vertical vs horizontal scaling Must know

Vertical scaling ("scale up") means a bigger machine: more CPU, RAM, faster disks. Horizontal scaling ("scale out") means more machines of the same size, with something in front to spread the work.

Vertical - pros
  • No code changes; nothing distributed to reason about
  • Great first step, especially for databases
  • Modern machines are very large
Vertical - cons
  • A hard ceiling and rising cost per unit
  • One machine = one point of failure
  • Upgrades often mean downtime

The rule that makes horizontal scaling work: stateless servers

A stateless server keeps nothing about the user between requests. Any server can answer any request, so the load balancer can send you anywhere, and a dead server loses nothing. Where does the state go? Session data (who is logged in, the cart) moves to a shared store like Redis, or into a signed token (for example a JWT, JSON Web Token: a small signed blob the server can verify with a key, without a database lookup, like checking a signed certificate) that the client sends with every request. Files go to blob storage (S3). The durable data goes to the database.

Careful: "just add servers" works for the app tier. The database is the hard part, because it holds shared state. The usual order is: vertical scale the DB, add a cache, add read replicas, and only then shard. Each step is covered below.

60-second answer: "I start vertical because it is simple. Once one box is not enough, or I need to survive a machine failure, I scale out the app tier behind a load balancer, which requires stateless servers with sessions in Redis or a token. The database is the real bottleneck, so I would add caching and read replicas first and shard only when writes or data size force it."
