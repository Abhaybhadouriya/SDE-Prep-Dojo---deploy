OAuth 2.0: delegated access without sharing passwords

OAuth 2.0 is an authorization framework. It lets a client app get an access token to call an API on behalf of a user, with limited scopes, without the app ever seeing the user's password. The four roles:

  • Resource owner: the user who owns the data.
  • Client: the app that wants access (a photo printing site, a mobile app, a backend job).
  • Authorization server: logs the user in, asks for consent, issues tokens (Google, Microsoft Entra ID, Okta, Auth0, or your own).
  • Resource server: the API that holds the data and checks the token.

Authorization code flow with PKCE, step by step

This is the flow to use for web, mobile and single-page apps. PKCE (Proof Key for Code Exchange, RFC 7636) binds the one-time code to a secret only the real client knows, so a malicious app that intercepts the redirect cannot redeem it. Click through:

  1. Make a secret. The client generates a random code_verifier (43 to 128 characters) and its hash, the code_challenge (BASE64URL of SHA-256, method S256).
  2. Redirect to the authorization server with client_id, the exact redirect_uri, the requested scope, a random state (blocks CSRF) and the challenge. Only the hash travels here.
  3. User authenticates and consents on the authorization server's page. The client never sees the password.
  4. Code comes back through the browser redirect. It is short-lived and single-use, and an attacker could see it, which is why the next step needs the verifier.
  5. Back-channel exchange. The client posts the code plus the original verifier to the token endpoint over TLS. The server hashes the verifier, compares it with the stored challenge, and issues an access token (and usually a refresh token).
  6. Call the API. The client sends Authorization: Bearer <token>. The resource server checks the signature, audience, expiry and scopes, then does its own object-level checks.

Which grant to use

Grant / flowUse it forStatus in RFC 9700 (OAuth Security BCP, Jan 2025)
Authorization code + PKCEWeb apps, SPAs, mobile and desktop appsRecommended; PKCE MUST for public clients, SHOULD for confidential ones
Client credentialsMachine to machine: a backend job calling an API, no userFine; protect the client secret or use mTLS / private key auth
Device authorizationTVs, consoles, CLIs: show a code, user approves on a phoneFine
Refresh tokenGetting a new access token without a new loginFor public clients, refresh tokens MUST be sender-constrained or rotated
Implicit (token in the URL)Old SPAsSHOULD NOT be used
Resource owner passwordApp collects the user's password directlyMUST NOT be used

Other rules from RFC 9700 worth quoting: authorization servers must match redirect URIs exactly (no wildcards), access tokens should be restricted to a specific audience, and sender-constrained tokens (bound to a client certificate via mTLS, or to a key via DPoP) are recommended so a stolen token is useless on another machine.

Common confusion: OAuth 2.0 alone does not tell the client who the user is. An access token is for the API, not for the client to read. "Login with Google" needs OpenID Connect on top.
