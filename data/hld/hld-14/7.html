API security: the OWASP API Top 10 (2023)

The OWASP API Security Top 10 is the list interviewers half-remember. Know the top five well and map each to a design decision.

#RiskWhat it looks likeDesign fix
API1Broken Object Level Authorization (BOLA)GET /orders/1002 returns someone else's order if you change the idCheck ownership on every object access in the service; use unguessable ids as defence in depth, not as the fix
API2Broken AuthenticationWeak login, no rate limit, tokens never expire, unsigned JWTs acceptedUse a proven IdP, MFA, short-lived tokens, strict JWT validation, login throttling
API3Broken Object Property Level AuthorizationResponse leaks password_hash; client can set "role":"admin" in a PATCH (mass assignment)Explicit response DTOs and allow-lists of writable fields
API4Unrestricted Resource ConsumptionNo limits on page size, upload size, requests, or costly calls (SMS, LLM tokens)Rate limits and quotas per user/key, max page size, timeouts, cost budgets (d02 Rate Limiter)
API5Broken Function Level AuthorizationA normal user can call /admin/refundDeny by default; role checks at gateway and service; separate admin APIs
API6Unrestricted Access to Sensitive Business FlowsBots buy all flash-sale stock or book every ticketBot detection, per-account purchase limits, queues and device fingerprinting (d09, d14)
API7Server Side Request Forgery (SSRF)"Fetch this image URL" is used to hit 169.254.169.254 or internal admin portsAllow-list destinations, block private ranges, fetch through an isolated egress proxy
API8Security MisconfigurationVerbose errors, open CORS, missing TLS, default credentialsHardened templates, config scanning, least privilege
API9Improper Inventory ManagementForgotten /v1 or debug endpoints still liveAPI catalog, gateway as the only entry, retire old versions
API10Unsafe Consumption of APIsTrusting a partner API's data and redirects blindlyValidate third-party responses, timeouts, TLS, treat them as untrusted input

Beyond the list, the classic web basics still apply (the System Design Primer's short security section): encrypt in transit and at rest, sanitize inputs to stop XSS and injection, use parameterized SQL queries, and grant least privilege. In a design, the API gateway is where you centralize TLS termination, token validation, coarse authorization, rate limiting, request size limits and a WAF (web application firewall, which filters known-bad patterns such as SQL injection strings). Object-level checks still belong in each service, because only the service knows who owns order 1002.

Pre-signed URLs: for large uploads and downloads, the API authorizes the user, then hands back a short-lived signed URL to the object store, so bytes never flow through your servers and access expires on its own. See Pattern: Handling Large Blobs and d36 S3.
