Encryption at rest, keys and secrets

Encryption at rest protects data on disks, backups and object stores, so a stolen disk, snapshot or misplaced backup is useless without keys. The hard part is not the cipher (AES-256 is standard) but key management: where keys live, who can use them, and how they rotate.

Envelope encryption

Big systems never encrypt terabytes directly with one master key. They use envelope encryption: each chunk of data gets its own data encryption key (DEK); the DEK is encrypted ("wrapped") by a key encryption key (KEK) held in a key management service (KMS) or hardware security module (HSM); the wrapped DEK is stored next to the data. Google's documentation of its default encryption describes this layering: data is split into chunks (up to several GB), each chunk gets its own AES-256 DEK, a new DEK on every update; DEKs are wrapped by per-service KEKs in a highly replicated internal keystore; the keystore's own keys are wrapped by a root key held in memory on dedicated machines with physical backups.

LayerProtects againstDoes not protect against
Disk / volume encryptionStolen or recycled physical disksAnyone who can query the running database
Database / object-level encryption with KMSLeaked snapshots and backups; gives per-tenant keys and audit logsA compromised app that is allowed to decrypt
Application-level (field) encryption or tokenizationEven DBAs and log readers seeing card numbers, national idsBugs in the app itself; costs search and indexing on those fields
End-to-end encryptionEven the service operator reading content (chat, backups)Compromised endpoints; makes server-side search and moderation hard

Secrets management

A secret is any credential a program needs: database passwords, API keys, signing keys, TLS private keys. Rules that show up in every good answer:

  • Never in code or images. Not in git, not baked into a Docker image layer (layers are easy to inspect; see Docker: Running & Managing), not in plain environment files committed by mistake.
  • A central secret store (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) with access by workload identity, audit logs and rotation. Kubernetes Secrets are only base64-encoded by default; enable encryption at rest for etcd or sync from an external store (ConfigMaps & Secrets).
  • Prefer short-lived, dynamic credentials. Vault's database secrets engine creates a unique database user per request with a lease you configure per role and revokes it when the lease ends. (The docs' example role uses a 1-hour TTL and a 24-hour max; a role with no TTL set inherits Vault's system default of 768 hours, about 32 days, so always set it.) Each instance then has its own SQL user, which also makes audits clearer. A leaked credential expires on its own.
  • Rotate and revoke without redeploys: services re-read secrets, and signing keys are published with a kid so old and new keys overlap during rotation.
  • Keep secrets out of logs and traces. ByteByteGo's secure-API cheatsheet calls out keeping passwords and card numbers out of monitoring data.
