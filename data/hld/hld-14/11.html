Interview questions

What is the difference between authentication and authorization? Where does each happen in your design?

Authentication proves identity ("you are user 42"); authorization decides permission ("user 42 may read order 1002"). Authentication happens once at login through an identity provider and is then carried by a session or token; failures return 401. Authorization happens on every request; failures return 403. In a microservice design the API gateway validates the token and enforces coarse rules (is the user logged in, do they have the seller role), while each service enforces object-level rules (does this order belong to this user), because only it knows ownership.

How to answer

One-line definitions, the status codes, then the placement split between gateway and service. Mention BOLA as the bug you are preventing.

  • How do services get the user's identity behind the gateway?
Sessions or JWTs for a large e-commerce app with web and mobile clients?

A hybrid. Issue a short-lived JWT access token (about 15 minutes) signed with the IdP's private key, so the gateway and every microservice can verify it locally with the cached public key, with no shared session store on the hot path. Issue a long-lived refresh token that is stored server-side and rotated on each use; reuse of an old refresh token signals theft, so revoke the whole family. Logout or a password change kills the refresh tokens, so access ends within one access-token lifetime; for instant cut-off on high-risk events keep a small deny-list of token ids checked at the gateway. On the web keep tokens in HttpOnly, Secure, SameSite cookies, not localStorage; on mobile use the platform keystore.

How to answer

State the trade-off (lookup vs revocation), pick hybrid, give the lifetimes, then cover storage on the client. Mention key rotation with kid.

Likely follow-ups
  • How do you revoke a JWT immediately?
  • What checks must a service do on a JWT?
  • What is refresh token rotation and reuse detection?
Walk me through OAuth 2.0 authorization code flow with PKCE. Why PKCE?

The client creates a random code verifier and sends its SHA-256 hash (the code challenge) in a redirect to the authorization server, along with client id, exact redirect URI, scopes and a random state value. The user logs in and consents there. The server redirects back with a short-lived, single-use authorization code. The client then exchanges the code plus the original verifier at the token endpoint over TLS; the server hashes the verifier, compares it to the stored challenge and issues an access token and usually a refresh token. PKCE exists because on mobile and in browsers the redirect can be intercepted (for example by a malicious app registering the same URL scheme); without the verifier, a stolen code is useless. RFC 9700 makes PKCE mandatory for public clients and recommended for all.

How to answer

Draw the four roles, then the six steps. Name what each parameter defends against: state against CSRF, exact redirect matching against code theft, PKCE against interception.

OAuth vs OIDC vs SAML: which would you use for SSO into an internal HR portal and a mobile app?

OAuth 2.0 is for delegated authorization: an access token for an API. OIDC adds authentication on top: an ID token (a JWT for the client) that says who the user is, plus discovery and JWKS. SAML is an older XML-based standard for web SSO assertions. For a modern internal portal and a mobile app I would use OIDC with authorization code and PKCE against the company IdP, because it works natively on mobile and also gives access tokens for the portal's APIs. If some legacy enterprise apps only speak SAML, the IdP can serve both, or an identity broker can translate. Either way the IdP enforces MFA and becomes a critical dependency that needs high availability.

How to answer

Define each in one line by what it outputs (access token, ID token, assertion), then choose by client type.

Likely follow-ups
  • What happens to all apps if the IdP is down?
  • How does single logout work?
How do microservices authenticate each other inside your cluster?

With mTLS using workload identities, not network location. Each workload gets a short-lived certificate from an identity system such as SPIFFE/SPIRE or a service mesh CA, rotated automatically, and the sidecar or library does mutual TLS so both ends prove identity and traffic is encrypted. On top, authorization policies say "only checkout may call payments POST /charges". When the call is on behalf of a user, the end-user's identity travels too, either as the original access token or as a downscoped internal token minted by the gateway, so services can do user-level checks. This is the zero-trust idea from Google's BeyondCorp: being inside the network grants nothing.

How to answer

Separate the two identities: the calling service (mTLS) and the end user (token). Mention rotation and who issues certs.

Likely follow-ups
  • What does a service mesh add beyond mTLS?
  • How would you handle a leaked service certificate?
How would you store user passwords and protect the login endpoint?

Store only a slow, salted hash: Argon2id with at least 19 MiB memory and 2 iterations per OWASP, a unique random salt per user, optionally a pepper kept in a vault. Never store plaintext or a fast hash. On the endpoint: TLS only; rate limits per account and per IP with exponential delays; detect credential stuffing (many accounts, few attempts each, from many IPs) and challenge it; MFA or passkeys; generic error messages so attackers cannot enumerate users; check new passwords against breached-password lists. Re-hash with stronger parameters on the next successful login when you raise the cost.

How to answer

Storage first (algorithm, salt, pepper), then online attack defences, then MFA.

Likely follow-ups
  • Why not SHA-256 with a salt?
  • How do you migrate from bcrypt to Argon2id without forcing resets?
Explain encryption at rest with a KMS. What is envelope encryption and why use it?

Each object or chunk is encrypted with its own random data key (DEK, AES-256). The DEK is encrypted by a key encryption key that never leaves the KMS or HSM, and the wrapped DEK is stored with the data. To read, the service asks the KMS to unwrap the DEK (an audited, permission-checked call), decrypts locally, and drops the plaintext key from memory. Benefits: the KMS only handles tiny keys, so it scales; rotating the master key means re-wrapping DEKs instead of re-encrypting everything; per-tenant KEKs give tenant isolation and crypto-shredding (delete the key to make data unreadable). Google documents exactly this hierarchy for its default encryption, with per-chunk DEKs wrapped by KEKs and a root key above them.

How to answer

Draw the two-level picture, then list the three benefits: scale, rotation, isolation. Be clear about what at-rest encryption does not protect (a compromised app).

  • When do you need field-level encryption on top?
Where do your services get database passwords and API keys from?

From a central secret manager (Vault, AWS Secrets Manager, Azure Key Vault), authenticated by workload identity, never from code, images or committed config. Better still, dynamic secrets: Vault's database engine creates a unique database user per request with a lease you set per role (for example the docs' 1-hour TTL with a 24-hour max; an unset role inherits Vault's 32-day system default) and revokes it when it expires, so a leak is short-lived and each instance is separately auditable. Secrets are rotated without redeploys, access is logged, and secrets are scrubbed from logs. In Kubernetes, encrypt Secrets at rest in etcd or sync them from the external store.

How to answer

Name the store, how a pod authenticates to it, and why short-lived beats static.

  • How does CI/CD deploy without long-lived cloud keys?
Name the top risks in the OWASP API Top 10 and how your design prevents them.

API1 Broken Object Level Authorization: changing an id in the URL returns someone else's data; prevent it with ownership checks in every service on every object access. API2 Broken Authentication: weak login and token handling; use a proven IdP, MFA, short-lived validated tokens. API3 Broken Object Property Level Authorization: leaking or mass-assigning fields; use explicit response and request schemas. API4 Unrestricted Resource Consumption: no limits; add rate limits, quotas, pagination caps, timeouts. API5 Broken Function Level Authorization: users reaching admin functions; deny by default and separate admin APIs. I would also mention API6 for flash sales and ticketing (bots abusing business flows) and API7 SSRF for any feature that fetches user-supplied URLs.

How to answer

Do not recite all ten. Give five with a concrete example and fix each, then pick the one most relevant to the design in front of you.

  • What belongs in the gateway vs the service?
Your service is hit by a DDoS during a sale. How is your architecture protected?

In layers. At L3/L4, traffic enters through an anycast CDN or DDoS service with many edge locations, so a flood is split across sites near its sources and dropped in the fast path (kernel XDP/eBPF filters, SYN cookies); the origin accepts only traffic from edge IP ranges, so it cannot be bypassed. At L7, the CDN serves cacheable pages, a WAF blocks known-bad patterns, and rate limits apply per IP, per token and per account, with bot challenges on login and checkout. Inside, load shedding protects checkout over browsing, and queues absorb bursts for heavy work. Scale numbers matter here: Cloudflare reported a 7.3 Tbps attack in 2025, far beyond any single site's capacity, so absorbing at the edge is the only option. Autoscaling alone just converts the attack into a bill.

How to answer

Split by layer, then by where each defence sits. Separate a real DDoS from a legitimate traffic spike (which you handle with capacity planning and queues).

Likely follow-ups
  • How do you tell a flash-sale spike from an attack?
  • What is a reflection or amplification attack?

Scenario: a user can see other people's orders

A security researcher reports that changing /api/orders/88123 to /api/orders/88124 in the mobile app shows another customer's address and items. The gateway does validate the JWT.

Weak answer: "Switch order ids to UUIDs so they cannot be guessed."

Strong answer: this is BOLA (OWASP API1). The gateway proves who the caller is, but nobody checks that order 88124 belongs to them. Fix in the order service: load the order and compare order.user_id with the token's sub (or check a delegated permission), return 404 rather than 403 so ids cannot be probed, and do it in a shared authorization middleware so every endpoint gets it. Add automated tests that call each endpoint with another user's ids. Unguessable ids are fine as extra defence, but not the fix. Then check access logs to find whether it was exploited and notify affected users.

Likely follow-ups
  • How would you find every endpoint with the same bug?
  • Should support staff be able to view any order? How?

Scenario: a signing key leaked

The private key your auth service uses to sign JWTs was committed to a public repo an hour ago. Access tokens last 15 minutes; refresh tokens last 30 days.

Weak answer: "Delete the commit and move on."

Strong answer: assume compromise. Generate a new key pair in the KMS with a new kid, start signing with it, and remove the leaked key from the published JWKS so every service rejects tokens signed with it (services refresh JWKS on unknown kid or on a short timer). That forces everyone to refresh; refresh tokens are server-side, so they stay valid unless you suspect they leaked too. Rotate the secret wherever else it was used, purge it from git history, and add secret scanning in CI. Longer term, keep signing keys in a KMS/HSM so they can never be exported to a repo in the first place.

Likely follow-ups
  • How do you rotate keys normally without downtime?
  • What if refresh tokens were also JWTs signed with that key?
