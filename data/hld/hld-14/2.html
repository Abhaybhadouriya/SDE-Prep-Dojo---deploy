Sessions vs JWT: how a login is remembered

HTTP is stateless, so after login the server must give the client something to send on every request. There are two families.

  • Server-side session: the server creates a random session id, stores session_id -> {user, roles, expiry} in a store such as Redis, and sends the id in a cookie. Every request looks it up. Logging out is deleting a row.
  • Self-contained token (JWT): the server puts the facts (claims) into a JSON Web Token and signs it. Any service holding the public key can verify it locally, with no lookup. The catch: you cannot easily "un-sign" it, so revocation is hard until it expires.

Inside a JWT

A JWT (RFC 7519) is three base64url parts joined by dots: header.payload.signature. The header names the algorithm, the payload holds claims, and the signature covers both. It is signed, not encrypted: anyone can decode and read the payload, so never put secrets in it.

// header
{ "alg": "RS256", "typ": "JWT", "kid": "2026-11-key-1" }
// payload (claims)
{
  "iss": "https://auth.example.com",   // who issued it
  "sub": "user_42",                    // who it is about
  "aud": "orders-api",                 // who it is for
  "iat": 1795400000,                   // issued at (unix seconds)
  "exp": 1795400900,                   // expires 15 minutes later
  "jti": "a7c1-...",                   // unique id, helps block replay
  "scope": "orders:read orders:write"
}

A service that receives it must check: the signature against the issuer's key (looked up by kid), that alg is one it expects (never accept none), that iss and aud match, and that exp/nbf are valid with a small clock-skew allowance.

The answer interviewers want: "Use both. A short-lived JWT access token, about 5 to 15 minutes, so services verify locally; plus a long-lived refresh token stored server-side and rotated on each use, so I can revoke a user by killing their refresh token. Worst case a stolen access token works until it expires." Then mention where tokens live on the client: an HttpOnly; Secure; SameSite cookie, not localStorage, which any XSS script can read.

Put numbers on it: 50,000 requests per second

Interviewers like it when you size the choice instead of reciting pros and cons. A worked estimate (rule of thumb, measure on your own hardware with openssl speed rsa2048 ecdsap256 and redis-benchmark):

  1. Sessions. 50k RPS means 50k Redis GETs per second, on every request, forever. One Redis node handles that, but the store is now on the critical path of every call: you run it replicated (often clustered) for availability, every service needs network access to it, and each request pays a network round trip, roughly 0.5-1 ms inside a zone.
  2. JWT. 50k signature verifies per second. An RSA-2048 or ECDSA P-256 verify costs tens of microseconds of one CPU core, so 50k/s is on the order of one to a few cores, spread across all gateway pods. No network call, no shared store, nothing new that can go down.
  3. Revocation list. To revoke JWTs early you keep a deny-list of token ids (jti) until they would have expired anyway. Its size is revocations per day x token lifetime: 100,000 logouts or bans a day with a 15-minute token is 100,000 x (15 / 1,440) = about 1,000 live entries, a few tens of KB. That is small enough to push to every gateway in memory (or a bloom filter), which is why short access tokens make revocation cheap.
  4. Conclusion to say out loud. "At 50k RPS across many services I verify JWTs locally at the gateway, keep them 5-15 minutes, rotate refresh tokens server-side, and push a tiny jti deny-list for emergencies. For a single web app at a few hundred RPS, plain server sessions are simpler and give instant logout."

Cookie and session hygiene (OWASP Session Management Cheat Sheet)

  • Session ids need at least 64 bits of entropy from a cryptographically secure random generator.
  • Set Secure (HTTPS only), HttpOnly (no JavaScript access) and SameSite=Strict or Lax (blocks most cross-site request forgery). The __Host- prefix pins the cookie to your exact host.
  • Idle timeout: about 2-5 minutes for high-value apps, 15-30 minutes for low-risk ones; an absolute timeout (for example 4-8 hours for an all-day office app).
  • Regenerate the session id at login and on any privilege change, which defeats session fixation.

From your world

A session store is a stateful connection table, like conntrack: fast to tear down, but every packet needs a lookup and the table must be shared or replicated. A JWT is closer to a signed routing advertisement: any router with the right key can validate it on its own, but once flooded you cannot recall it until it ages out. The refresh token is the hold-down timer you control.
