Idempotency keys: making retries safe

Networks fail in three ways for a request like "charge Rs 500". Stripe's idempotency post lists them: the request never arrives, the server fails halfway, or the server succeeds but the response is lost. From the client's side, the last one looks exactly like the first. If the client retries blindly, the customer may be charged twice. If it never retries, the customer may never be charged.

The fix: the client generates a unique idempotency key (a UUID) per logical operation and sends it with every attempt, for example in an Idempotency-Key header. The server remembers the key and the result. A repeat with the same key returns the stored result instead of running again.

  1. Send with a key. The client creates one UUID for this payment and sends it.
  2. Record atomically. The server stores the key and does the work in the same transaction, so there is never a key without a charge or a charge without a key. (If the work is a call to another system, such as a payment provider, see the note below the code: you record IN_PROGRESS first.)
  3. Response lost. The charge succeeded, but the client times out.
  4. Retry. The client retries with exponential backoff and jitter, reusing the same key.
  5. Replay. The server sees the key and returns the original result. The customer is charged exactly once.
CREATE TABLE idempotency_keys (
  account_id    BIGINT       NOT NULL,
  idem_key      VARCHAR(64)  NOT NULL,
  request_hash  CHAR(64)     NOT NULL,     -- detect same key, different body
  status        VARCHAR(16)  NOT NULL,     -- IN_PROGRESS | DONE
  response_code INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, idem_key)       -- the uniqueness is the lock
);
-- expire rows after a retention window (for example 24 h to a few days)

AWS's Builders' Library article on idempotent APIs adds the details that separate a good answer from a great one:

  • Use a caller-provided token, not a hash of the parameters. Two identical requests can be intentional (launch two identical EC2 instances), so the client must say "this is the same operation". EC2 calls it ClientToken, and the AWS SDKs generate one automatically and reuse it across their own retries.
  • Same token, different parameters is an error. Store the original request (or its hash) and reject a mismatch with a validation error, because the caller's intent changed.
  • Return a semantically equivalent response, not "AlreadyExists". The caller should not have to guess whether its request created the resource.
  • Record the token and the side effect atomically, and keep tokens only for a bounded time.

When the side effect is outside your database. A call to a payment service provider (PSP) cannot sit inside your DB transaction. So: (1) insert the key as IN_PROGRESS and commit; (2) call the PSP, passing the same idempotency key so the PSP also de-duplicates; (3) record DONE plus the response. If the server crashes between (1) and (3), a recovery job finds rows stuck in IN_PROGRESS, asks the PSP what happened to that key, and finishes or fails the row. Airbnb's Orpheus library uses exactly this pre-RPC / RPC / post-RPC split; see hld-10.

Concurrent duplicates: if two attempts with the same key arrive at the same moment, the primary key insert makes one win. The loser should either wait and return the stored result or return 409 Conflict ("request in progress, retry later"). Never let both run.

Idempotency keys only protect the edge. Inside the system, events from Kafka are delivered at least once, so consumers must also de-duplicate (by event ID, or by making the write itself idempotent: "set status=PAID where status=PENDING"). That is covered in Distributed transactions & events and Kafka delivery semantics. Retry timing (exponential backoff, jitter, retry budgets) is in the AWS article on timeouts, retries and backoff with jitter.
