Pagination: offset vs cursor

Any list that can grow must be paginated, and the page size must be capped (for example limit at most 100). There are two main families. ByteByteGo's pagination guide lists six variants (offset, cursor, page, keyset, time-based, hybrid), but they reduce to these two ideas: "skip N rows" or "continue after this row".

  1. Page 1. Both methods return the three newest posts. The cursor method also returns where it stopped.
  2. Data changes. A new post #91 is inserted at the top before the client asks for page 2.
  3. Page 2. Offset counts positions, so everything shifted down and #88 shows up twice (deletes cause skipped rows instead). The cursor says "older than #88", so it is stable.
  4. Cost. Deep offsets scan and discard rows; cursors use the index directly.
-- Offset: simple, supports "jump to page 7", unstable and slow when deep
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 140;

-- Keyset / cursor: stable and fast; needs a unique, indexed sort key
-- cursor = base64("2026-11-20T10:15:00Z|98123") decoded by the server
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ('2026-11-20T10:15:00Z', 98123)
ORDER BY created_at DESC, id DESC
LIMIT 21;   -- fetch one extra row to know if there is a next page

Slack's engineering blog tells exactly this story. Slack started with offset pages (count and page) and moved to cursors because large offsets were slow and frequent writes made pages skip or repeat items. Slack's cursors are opaque Base64 strings returned as next_cursor, and the server fetches one extra row to know whether another page exists. Because the cursor is opaque, one endpoint can encode an offset inside it and another can encode a last ID per shard, without clients noticing. The price is that there is no total count and no "jump to page 9".

From your world

Offset pagination is like asking a ring buffer for "the 500th entry from the head" while the producer keeps writing: the answer moves under you. Cursor pagination is like remembering a sequence number and asking for "everything after seq 98123", which is how a Kafka consumer offset or a TCP ACK works. Sequence-based resumption is always stable.

Where this breaks: a ring-buffer sequence number is one dense counter, but an API cursor must encode the sort key (for example created_at plus id), so a cursor only works for orders you have an index on, and you cannot jump to "page 37".
