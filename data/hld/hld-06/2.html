Resource modelling in REST

Start from the core entities you listed in the requirements step. Each becomes a plural noun. Relationships become nesting (when the child cannot exist without the parent) or query filters (when it is just a filter). Hello Interview's guide puts the rule simply: resources are things, not actions.

# Ticket booking (see d14) - resources, not verbs
GET    /v1/events?city=pune&date=2026-12-01&cursor=...   # search, paginated
GET    /v1/events/{eventId}                              # one event
GET    /v1/events/{eventId}/seats?status=available       # seats belong to an event
POST   /v1/bookings          Idempotency-Key: 7c9e...     # create a booking (hold seats)
GET    /v1/bookings/{bookingId}                          # check status
POST   /v1/bookings/{bookingId}/payment                  # sub-resource for an action-like step
DELETE /v1/bookings/{bookingId}                          # cancel

# Weak (verbs in URLs, inconsistent):
POST /getEvents   POST /bookSeat   GET /cancelBooking?id=9
MethodMeaningSafe (no side effects)?Idempotent (repeat = same effect)?
GETReadYesYes
PUTReplace the whole resource at this URLNoYes
DELETERemoveNoYes (second delete is a no-op, may return 404)
PATCHPartial updateNoDepends: "set status=paid" yes, "add 1 to count" no
POSTCreate, or run an actionNoNo - needs an idempotency key

Status codes and errors

Interviewers care most that you separate 4xx (the client did something wrong; do not blindly retry) from 5xx (the server failed; retry with backoff may help). The ones to know: 200 OK, 201 Created, 202 Accepted (work queued, check later), 204 No Content, 400 Bad Request, 401 Unauthenticated, 403 Forbidden, 404 Not Found, 409 Conflict (seat already taken, version mismatch), 422 Unprocessable (valid JSON, invalid meaning), 429 Too Many Requests, 500, 502 Bad Gateway, 503 Unavailable, 504 Gateway Timeout. Never return an error inside a 200.

{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "Seat B12 was booked by someone else.",
    "retryable": false,
    "request_id": "req_01HZX3"
  }
}

Tip: take the user ID from the auth token, never from the request body. Hello Interview's networking guide makes the point that clients can change anything they send. GET /v1/me/bookings is safer than GET /v1/bookings?userId=7.

Long jobs (video transcoding, report generation, LLM batch) should not hold an HTTP request open for minutes. Return 202 Accepted with a job resource (/v1/jobs/{id}) and let the client poll it, subscribe via SSE, or receive a webhook. See Managing long-running tasks.
