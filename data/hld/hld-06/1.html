Three API styles: REST, gRPC, GraphQL

REST (representational state transfer) models the world as resources with URLs, and uses HTTP methods as verbs: GET /orders/42. gRPC is a remote procedure call framework: you call a typed function like GetOrder(id=42), encoded as Protocol Buffers over HTTP/2. GraphQL exposes one endpoint and a typed schema; the client sends a query that names exactly the fields it wants.

Hello Interview's guide gives two numbers worth remembering. In its gRPC example the binary protobuf encoding is about 15 bytes against about 40 bytes of JSON for the same message, and some benchmarks show up to about 10x throughput. For GraphQL it shows the N+1 problem: listing 100 events and then loading each event's venue naively runs 101 database queries instead of 2, which is why GraphQL servers use batching ("dataloader") to merge those lookups.

"I will use REST for the client-facing API because it is simple, cacheable and every client speaks it. Between internal services I would use gRPC for typed contracts and lower overhead. I would only bring in GraphQL if we have many client types that need very different data shapes." Say this once, then move on. Interviewers dislike GraphQL or gRPC chosen without a reason.

gRPC has four call types, all from the official core-concepts doc: unary (one request, one response), server streaming, client streaming, and bidirectional streaming. It also has deadlines: the client says how long it will wait and gets DEADLINE_EXCEEDED after that, and the deadline travels with the call so downstream services can stop wasting work. That is a great detail to mention when you talk about timeouts in microservices.
