Versioning and evolving an API

Once mobile apps ship, you cannot force every user to upgrade. So the real rule is: additive changes are safe, everything else is a new version. Adding an endpoint or a new optional field is safe. Removing a field, renaming it, changing its type, or changing what it means is breaking.

ApproachExampleProsCons
URL path/v1/orders, /v2/ordersExplicit, easy to route at the gateway, easy to testBig-bang versions; two code paths to run
HeaderAccept: application/vnd.shop.v2+json or Api-Version: 2Clean URLsLess visible, harder to test in a browser, CDN must vary on it
Date-based, pinned per account (Stripe)Stripe-Version: 2024-06-20Small, frequent breaking changes; old clients keep workingNeeds a transformation layer for every change
Schema evolution (gRPC / GraphQL)New proto field numbers; deprecate GraphQL fieldsNo version numbers; old clients ignore new fieldsDiscipline: never reuse a field number

Stripe's API versioning post is the best real example. Stripe names versions by date, pins each account to the version current at its first request, and lets a Stripe-Version header override per request. Internally, responses are built in the newest shape and then walked backwards through small "version change modules" until they match the caller's version. Stripe reports almost a hundred breaking upgrades over six years while staying compatible with every version back to 2011. For interviews, say "URL versioning, /v1, additive changes only within a version" and mention Stripe's approach if asked about evolving a public API.
