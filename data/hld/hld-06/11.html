Quick quiz

Which endpoint is best REST style for cancelling a booking?

  1. DELETE /v1/bookings/9 (or PATCH status to CANCELLED)
  2. POST /cancelBooking?id=9
  3. GET /bookings/9/cancel
Resources plus HTTP verbs. A GET must never change state, and verbs in URLs are a common interview mistake.

A feed uses LIMIT 20 OFFSET 20 for page 2. New posts arrive while users scroll. What goes wrong?

  1. Users see duplicate posts, and deep pages get slow
  2. Nothing
  3. The database rejects the query
New rows shift positions, so page 2 repeats items from page 1. Deep offsets also scan every skipped row. Use a cursor.

A payment POST timed out. The client retries with the same idempotency key, and the first attempt had succeeded. What should the server do?

  1. Charge again; it is a new request
  2. Return the stored original result without charging again
  3. Return 409 "already exists" and nothing else
Return a semantically equivalent response so the client can continue. AWS's idempotency article explicitly avoids "AlreadyExists"-style errors.

The same idempotency key arrives with a different amount. Best response?

  1. Process it as a new payment
  2. Reject it with a validation error (for example 422)
  3. Return the old result
  4. Overwrite the old payment
The caller's intent changed, so it is a bug or an attack. Store a request hash with the key to detect it.

A live cricket score page only needs updates from the server. Simplest good choice?

  1. WebRTC
  2. WebSockets
  3. Webhooks
  4. Server-Sent Events
One-way, server to client: SSE is plain HTTP and reconnects automatically. WebSockets would work but add two-way complexity you do not need. Webhooks cannot reach browsers.

GitHub marks a webhook delivery as failed if your endpoint does not answer 2xx within:

  1. 1 second
  2. 60 seconds
  3. 10 seconds
GitHub's best-practices page gives 10 seconds, which is why you acknowledge quickly and process from a queue.

Which change to a v1 API is safe without a new version?

  1. Renaming total to amount
  2. Adding a new optional response field
  3. Changing paid from boolean to a status string
Adding is safe if clients ignore unknown fields. Renames and type changes break existing clients (Stripe lists exactly these as breaking).

Why does a group video call use an SFU instead of a full peer-to-peer mesh?

  1. Mesh makes every client upload to every other client, which does not scale and exposes IPs
  2. Browsers cannot send UDP
  3. SFUs mix audio into one stream
With N people, mesh means N-1 uploads per client. An SFU receives one upload and forwards it. Mixing is what an MCU does, not an SFU.
