Real-time to the client: polling, long polling, SSE, WebSockets, WebRTC

HTTP was built for "client asks, server answers". When the server has news (a chat message, a driver moved, a token was generated) you need one of five techniques. Watch the timelines: each dot is a message from the server.

The details that matter

  • SSE resumes for free. Each event can carry an id:; MDN's SSE guide shows the id sets the client's last event ID and the stream reconnects on its own (the retry: field sets the delay in milliseconds). Your server must still be able to replay what was missed. MDN also warns that without HTTP/2, browsers allow only 6 connections per domain, so several tabs of an SSE app can starve each other; HTTP/2 raises this to a negotiated number of streams (default 100).
  • SSE through proxies. Some proxies buffer responses, which breaks streaming. Turn buffering off at the gateway and send comment lines (: ping) as keep-alives so idle timeouts do not cut the stream.
  • WebSockets need justification. Hello Interview's networking guide notes interviewers dislike WebSockets chosen without a real need for frequent two-way messages. If the client only receives, SSE is simpler: it is plain HTTP, works with existing auth and load balancers, and reconnects automatically.
  • WebRTC is niche. Use it for audio and video. It needs a signalling channel (often a WebSocket), STUN to discover public addresses, and TURN relays when NAT traversal fails. For groups, peers send to a media server instead of to each other.
  1. Connect. Each client holds one WebSocket to some gateway (spread by least connections). The gateway records "user to gateway" in a registry, or subscribes to the user's channels.
  2. Send. A message goes to a stateless service, often over normal HTTP, which validates and stores it.
  3. Publish. The service publishes to a pub/sub topic for that conversation or channel (Redis pub/sub, Kafka).
  4. Deliver. Every gateway subscribed to that channel pushes the message down its sockets. Business logic stays out of the gateways.

This is how Slack describes its real-time stack. Clients keep a WebSocket to gateway servers deployed in several regions close to users (behind Envoy at the edge). Channel servers own a consistent-hash slice of channels. A sent message reaches the owning channel server, which fans it out to every gateway subscribed to that channel, and each gateway pushes to its clients. Slack reports worldwide delivery in about 500 ms and replacing a failed channel server in under 20 seconds. Discord's voice post shows the WebRTC side: around 2.6 million concurrent voice users on more than 850 voice servers in 13 regions, using a selective forwarding unit (SFU) instead of peer-to-peer mesh because mesh "becomes prohibitively expensive" as participants grow, and because it hides users' IP addresses.

From your world

Short polling is a driver polling a status register. Long polling is a blocking read() with a timeout. SSE and WebSockets are an interrupt line: the device tells you. And the WebSocket gateway fleet is just a huge epoll loop holding sockets; its limits are the ones you know: file descriptors, kernel memory per socket buffer, and ephemeral ports between the LB and the gateways. WebRTC's STUN/TURN is NAT traversal you have debugged before: STUN discovers the mapped address, TURN relays when hole punching fails (symmetric NAT).

Where this breaks: an interrupt line is reliable and local; a WebSocket can drop silently through a NAT or proxy timeout, so you need app-level heartbeats, reconnect logic and a "resume from event id" step that hardware never needed.
