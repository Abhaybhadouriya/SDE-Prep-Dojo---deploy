The story: the restaurant

Explain like I'm 5

At a restaurant you do not walk into the kitchen. You read the menu and tell the waiter "one pizza, please". The menu is a promise: if you ask for something on it, in the way it says, the kitchen will make it. That menu is an API.

Sometimes you shout "is my pizza ready?" every minute. That is polling. It is annoying. Better: the waiter says "I will tell you when it is ready". That is a push.

And if you ask twice because the waiter did not hear you, you do not want two pizzas and two bills. So you say "this is order number 7". If the kitchen already has order 7, it does not cook it again. That number is an idempotency key.

An API (application programming interface) is the contract between a client and a server: which operations exist, what goes in, what comes out, and what errors look like. In a system design interview the API step usually takes about five minutes. Hello Interview's API design guide calls spending much longer than that a common mistake. But a sloppy API leaks into everything later: no pagination means a timeout at scale, no idempotency means double charges, the wrong push mechanism means a fleet you cannot scale.

From your world

You already design APIs: a syscall table, an ioctl, a netlink message, a gRPC/NETCONF interface on a router. The same rules apply on the web. Keep the contract stable (never change the meaning of an existing field, just like you never renumber a syscall). Make operations safe to retry (like a TCP retransmit that the receiver de-duplicates by sequence number). And choose push vs poll the same way you choose interrupts vs polling in a driver: poll when events are frequent and cheap to check, push when they are rare and latency matters.

Where this breaks: a syscall caller and kernel share one machine and fail together; a web API client and server fail independently, so the client often cannot tell whether a request ran, which is why retries and idempotency matter far more here.
