Interview questions

REST vs gRPC vs GraphQL: which would you choose and why?

REST for public and client-facing APIs: universal, simple, HTTP-cacheable, easy to debug. gRPC between internal services: typed contracts from .proto files, compact binary encoding over HTTP/2, streaming and deadlines; but poor browser support and needs L7 balancing. GraphQL when many client types need different shapes of data and over- or under-fetching is a real cost; but caching, N+1 queries, query cost limits and field-level authorization get harder.

How to answer

Give the default (REST outside, gRPC inside), then one trigger for each alternative. Show you know a cost of each, not only benefits.

Likely follow-ups
  • How do you stop an expensive GraphQL query from taking down the database?
  • How do you call a gRPC service from a browser?
  • How do you version a protobuf schema?
Design the APIs for a food delivery app (Swiggy/Zomato).

Core entities: restaurant, menu item, cart, order, delivery. GET /v1/restaurants?lat=&lng=&cursor= (nearby, paginated); GET /v1/restaurants/{id}/menu; PUT /v1/me/cart (replace cart, idempotent); POST /v1/orders with an Idempotency-Key, body = cart ID + address + payment method, returns 201 with order ID and status PENDING_PAYMENT; GET /v1/orders/{id}; live order and rider location via SSE GET /v1/orders/{id}/events (one-way) and rider app sends location with POST /v1/riders/me/location every few seconds (or a WebSocket if very frequent). User ID always from the token.

How to answer

List entities, then 5-7 endpoints, then mark: auth, pagination, idempotency, real-time channel. Five minutes, then move to architecture.

Likely follow-ups
  • Why SSE and not WebSockets for the customer?
  • What happens if payment succeeds but the order call times out?
Offset vs cursor pagination: when do you use each?

Offset (LIMIT/OFFSET or page numbers) is simple and supports jumping to page N and totals, so it fits admin tables and small or slow-changing data. It breaks on live data: inserts cause duplicates, deletes cause skips, and deep offsets scan every skipped row. Cursor/keyset pagination returns an opaque token for "after this sort key", uses an index seek, is stable under writes and works across shards, so it fits feeds, chat history and infinite scroll. It cannot jump to arbitrary pages or give cheap totals. Slack moved from offset to opaque cursors for exactly these reasons.

How to answer

Show the duplicate example in one sentence, then the SQL (WHERE (created_at,id) < (...)), then the trade-off.

Likely follow-ups
  • Why include id as well as created_at in the cursor? (Ties.)
  • Why make the cursor opaque?
  • How do you paginate a result merged from 16 shards?
How do you make a payment API safe to retry?

The client generates an idempotency key (UUID) per logical payment and sends it on every attempt. The server, in one transaction, inserts (account_id, key, request_hash, status) with a unique constraint. Because the charge is a call to an external PSP, it cannot live inside that transaction: the row is first committed as IN_PROGRESS, the PSP is called with the same idempotency key, and the row is then marked DONE with the stored response; a recovery job resolves rows stuck in IN_PROGRESS by querying the PSP. A repeat with the same key returns the stored response; the same key with a different body is rejected; a concurrent duplicate loses the unique insert and gets 409 or waits for the result. Keys expire after a retention window. Clients retry only on timeouts and 5xx, with exponential backoff and jitter. Downstream (PSP calls, Kafka consumers) also need idempotency, using the same key or the payment ID.

How to answer

Name the three failure cases (lost request, partial failure, lost response), then the key, the atomic record, the replay, and the edge cases from AWS's article.

Likely follow-ups
  • Who generates the key, and when is a new key created? (New key per new user intent, same key for retries.)
  • Where do you store keys at 50k payments per second?
  • What if the call to the bank times out?
Polling vs long polling vs SSE vs WebSockets: how do you choose?

Ask two questions: does the client need to send frequently too, and how fresh must data be? Updates every few seconds are fine with short polling (simple, stateless, cacheable). Server-to-client only and real time: SSE (plain HTTP, auto-reconnect with last event ID). Frequent two-way messages (chat typing, games, collaborative editing): WebSocket. Audio/video: WebRTC. Long polling is a fallback when streaming is blocked. Every persistent option means stateful servers, so you also need L4 or WS-aware load balancing, a connection registry and a reconnect strategy.

How to answer

Start from the requirement, not the technology. Pick the simplest one that meets it and say what it costs operationally.

Likely follow-ups
  • How do you scale to 10 million open connections?
  • How does a message reach a user connected to another server?
  • What happens on deploy?
A message must reach a user whose WebSocket is on a different server. How?

Two standard options. (1) Registry: on connect, the gateway writes user to gateway-id into Redis with a TTL refreshed by heartbeats; the sender looks it up and sends to that gateway directly (Netflix Zuul Push uses a push registry like this). (2) Pub/sub: gateways subscribe to topics for the users or channels they hold; the service publishes once and the right gateways receive it (Slack's channel-server fan-out). Registry suits 1:1 delivery; pub/sub suits group channels. Offline users get the message from storage on reconnect and a push notification.

How to answer

Draw gateway, registry or pub/sub, and storage. Mention TTLs for stale entries and what happens when a gateway dies.

Likely follow-ups
  • How do you handle a user on three devices?
  • Redis pub/sub loses messages if a subscriber is down; is that okay?
How do you version a public API without breaking mobile clients?

Make additive changes only within a version: new endpoints and new optional fields are fine; removing, renaming, retyping or changing meaning is breaking and needs a new version. Use URL versioning (/v1, /v2) routed at the gateway, run both until traffic on the old one drops, announce deprecation with headers and dates, and track usage per client version. Clients must ignore unknown fields. For a large public API, Stripe's date-based versions pinned per account with transformation modules let you ship small breaking changes without forcing upgrades.

How to answer

State the compatibility rule first, then the mechanism, then the migration process.

Likely follow-ups
  • How long do you keep v1 alive?
  • How do protobuf field numbers help?
You are integrating with a payment gateway. Webhooks or polling for the payment result?

Both. The webhook gives fast notification: verify the signature and timestamp, return 2xx immediately, enqueue, and process idempotently by event ID because delivery is at-least-once and may be out of order. Polling (or a reconciliation job that lists recent payments from the gateway) catches anything the webhook missed, for example during your outage. The order state machine only moves forward (PENDING to PAID), so a late or duplicate event is harmless.

How to answer

Say "webhooks for speed, reconciliation for correctness", then the four receiver rules.

Likely follow-ups
  • What if the webhook says FAILED after a SUCCESS?
  • How do you secure the webhook endpoint?
How would you stream tokens from an LLM to a web client?

SSE: the client POSTs the prompt (or opens a GET for a created request ID) and the server streams data: events per token chunk with ids, ending with a done event. It is one-way, works through standard HTTP infrastructure, and auth uses normal headers or cookies. Disable proxy buffering at the gateway, send keep-alive comments, and make the generation resumable or cheap to cancel when the client disconnects. A WebSocket is only needed if the client must send while receiving (voice, interrupting mid-stream).

How to answer

Match direction (server to client) to SSE, then cover the proxy and disconnect details.

Likely follow-ups
  • How do you load balance long streams fairly across GPU servers?
  • What happens if the user refreshes mid-answer?
Design a one-to-many video call (Teams/Zoom): how do clients talk to the server?

Signalling (join, leave, mute, SDP offers) over a WebSocket to a signalling service. Media over UDP with WebRTC to a selective forwarding unit (SFU) in the nearest region; the SFU forwards each sender's stream to the others without decoding, and with simulcast it chooses a lower-quality layer per receiver's bandwidth. STUN discovers public addresses; TURN relays when UDP or NAT traversal fails, with TCP/TLS 443 as the last resort. Mesh peer-to-peer only works for 2-3 people. Discord runs about 2.6 million concurrent voice users this way on 850+ voice servers in 13 regions.

How to answer

Separate control plane (signalling) from data plane (media); your networking background shines here.

Likely follow-ups
  • Why not an MCU that mixes all streams?
  • How do you record the meeting?
Which HTTP methods are idempotent, and why does it matter?

GET, PUT and DELETE are idempotent by definition (repeating them leaves the same state); GET is also safe (no side effects). POST is not, and PATCH depends on the operation ("set" vs "increment"). It matters because clients, proxies and SDKs retry on timeouts: idempotent calls can be retried freely, while POSTs that create money movements or bookings need an idempotency key.

How to answer

Define idempotent vs safe, list the methods, then connect to retries.

Likely follow-ups
  • Is DELETE really idempotent if the second call returns 404?
  • How would you make "add to cart" idempotent?

Scenario: customers charged twice

After a network incident at a Flipkart-like checkout, 0.3% of orders show two charges. Logs show the mobile app retried POST /orders after 10-second timeouts; the first attempts had actually succeeded.

Weak answer: "Increase the timeout so the app does not retry" or "turn off retries".

Strong answer: make the endpoint idempotent. The app creates an idempotency key when the user taps "Pay" and reuses it on every retry; the server stores the key with the order in one transaction under a unique constraint and returns the stored result on repeats; same key plus a different body is rejected. Pass the key (or order ID) to the payment provider so it also de-duplicates. Then refund existing duplicates with a reconciliation job, and add an alert on "two charges for one cart".

Likely follow-ups
  • What if the duplicate arrives while the first is still running?
  • How long do you keep the keys?

Scenario: the notification bell melts the database

A web app polls GET /notifications every 2 seconds from 3 million open tabs. That is about 1.5 million requests per second, almost all returning "nothing new", and the notifications DB is at 95% CPU.

Weak answer: "Add read replicas" or "switch everything to WebSockets".

Strong answer: the data flows one way, so use SSE: one connection per tab, the server pushes only when something happens, and the stream resumes from the last event ID. Behind it, gateways subscribe to a per-user pub/sub channel, so the DB is read only on (re)connect. If SSE cannot be deployed quickly, cut cost first: poll every 30 s, add ETag/If-None-Match so empty polls return 304 from a cache of "latest notification ID per user", and add jitter to spread the load.

Likely follow-ups
  • What about the 6-connections-per-domain limit with many tabs? (HTTP/2, or one shared connection across tabs.)
  • How do you deploy the SSE servers without a reconnect storm?

The 60-second answer. "Public APIs I expose as REST with resource nouns, cursor pagination and additive versioning; service-to-service I use gRPC over HTTP/2 for typed contracts and streaming; GraphQL only when many clients need different shapes of the same data. Every write that can be retried takes a client idempotency key, unique per logical operation, stored with the result so a retry replays it. For server-to-server events I use signed webhooks with retries, and to the browser I pick SSE for one-way updates and WebSockets only when both sides talk."
