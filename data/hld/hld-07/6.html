MVCC: readers never block writers

MVCC (Multi-Version Concurrency Control) keeps several versions of a row so readers can see a consistent snapshot while writers create new versions. Readers do not take locks, so a long report does not freeze checkout. It is how both Postgres and InnoDB implement Read Committed and Repeatable Read.

  1. Transaction B starts and takes a snapshot: it may see versions committed by transaction 200 or earlier.
  2. Transaction A (id 201) updates the balance. A new version is created; the old one is kept and linked.
  3. B reads the balance. Version 201 is not committed and is not in B's snapshot, so B follows the chain to the version 100. No lock was needed.
  4. A commits. Under Read Committed, B's next statement would see 200. Under Repeatable Read, B keeps seeing 100 until it ends.
  5. When no running transaction can see the old version, it is garbage. Postgres VACUUM removes dead tuples; InnoDB purge trims the undo log.

Production trap: one idle transaction left open (a forgotten BEGIN in a console, or a stuck worker) pins the oldest snapshot. Nothing newer can be cleaned up, so tables bloat and queries slow down for everyone. Postgres has idle_in_transaction_session_timeout for this. Uber hit a cousin of this problem: long reads on Postgres replicas blocked WAL replay until the replica killed them.

From your world

MVCC is RCU (read-copy-update) for rows. Readers in the kernel walk an RCU-protected list with no lock; an updater publishes a new copy and the old one is freed only after a grace period when no reader can still hold it. VACUUM is the grace-period reclaim. Same idea: readers never wait, writers pay with copies and deferred freeing.

Where this breaks: an RCU grace period ends in milliseconds; one long-running database transaction can pin old row versions for hours, so tables bloat and VACUUM cannot reclaim them until that transaction ends.
