Transactions and isolation levels

A transaction is a group of reads and writes that succeed or fail as one unit. ACID names its four promises: Atomic (all or nothing), Consistent (rules hold before and after), Isolated (concurrent transactions do not step on each other), Durable (once committed, it survives a crash, thanks to the WAL). Isolation is the one with a dial, because full isolation is expensive.

The anomalies, in plain words

  • Dirty read - you read a value another transaction wrote but has not committed. It rolls back; you acted on something that never existed.
  • Non-repeatable read - you read a row twice in one transaction and get different values, because someone committed in between.
  • Phantom read - you run the same range query twice and new rows appear ("seats WHERE show_id = 9 AND free").
  • Lost update - two transactions read balance 100, both add 10, both write 110. One deposit vanished.
  • Write skew - two transactions each read the same set, each decide "safe", each write a different row, and together break a rule. Classic: two on-call doctors both go off-call because each saw the other still on call.

-- Postgres: ask for a level per transaction
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE shift_id = 7 AND on_call;
UPDATE doctors SET on_call = false WHERE id = 1 AND shift_id = 7;
COMMIT;   -- may fail with SQLSTATE 40001: the app must retry the whole transaction

Careful: "We use Repeatable Read, so we are safe" is a trap. Snapshot isolation stops non-repeatable reads but not write skew, and the exact behaviour differs between Postgres and MySQL. In an interview, name the anomaly you are worried about, then name the fix.
