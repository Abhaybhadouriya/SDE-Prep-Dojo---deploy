Quick quiz

You have an index on (user_id, created_at). Which query can NOT use it efficiently?

  1. WHERE created_at > '2026-01-01'
  2. WHERE user_id = 7
  3. WHERE user_id = 7 ORDER BY created_at DESC
The leading column user_id is missing, so the database cannot jump to a contiguous slice of the index.

Why does an LSM-tree engine handle writes faster than a B-tree engine?

  1. It turns random in-place updates into sequential appends and batched flushes
  2. It has no write-ahead log
  3. It skips indexing
Writes go to the WAL and memtable, then flush as sorted immutable files. Compaction pays the cost later in the background.

Two transactions each read that two doctors are on call, and each sets a different doctor off call. Which anomaly is this?

  1. Dirty read
  2. Write skew
  3. Lost update
Each writes a different row based on a shared read, so no row conflict is detected under snapshot isolation.

What is PostgreSQL's default isolation level?

  1. Serializable
  2. Repeatable Read
  3. Read Committed
Postgres defaults to Read Committed; MySQL InnoDB defaults to Repeatable Read.

What does a covering index let the database skip?

  1. Reading the table rows
  2. The WAL
  3. Query planning
All needed columns are in the index, so it is an index-only scan.

A cart where one user occasionally edits from two tabs. Best concurrency choice?

  1. Optimistic locking with a version column
  2. Table-level lock
  3. Serializable isolation for every read
Conflicts are rare, so a cheap version check plus a retry beats holding locks.

What do bloom filters do in an LSM engine?

  1. Compress SSTables
  2. Let reads skip files that definitely do not contain the key
  3. Order keys in the memtable
A bloom filter never gives a false "no"; at 10 bits per key it gives a false "maybe" about 1% of the time.
