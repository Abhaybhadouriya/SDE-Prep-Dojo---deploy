Schema from access patterns

An access pattern is one concrete question your application asks the database, with its rate. "Get the 20 newest orders for user 42, about 2,000 times a second" is an access pattern. "Store orders" is not. Hello Interview's data-modeling guide lists three forces that shape a schema: how much data there is, the access patterns (the most important), and how consistent the data must be. The schema is the answer to those three.

The five-step recipe

  1. List the core entities. Nouns from the requirements: User, Restaurant, MenuItem, Order, OrderItem, Rider. Spend about two minutes here.
  2. Write each API's query. For every endpoint, write the read or write it needs in one line. GET /users/{id}/orders becomes "orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 20".
  3. Pick keys. A primary key (PK) uniquely names a row. Use a system-generated ID (a surrogate key), not business data like an email that can change. A foreign key (FK) points at another table's PK.
  4. Index what you filter and sort by. Each query from step 2 should hit an index. If a query has no index, either add one or explain why a scan is fine.
  5. Decide denormalization and sharding. Copy data only where a hot read needs it, and pick a shard key that matches the main access pattern (more in Fundamentals and Scaling Writes).

Now turn the APIs into queries and check each one has an index:

Relationship shapes

  • One-to-many (a user has many orders): put the FK on the "many" side, orders.user_id.
  • Many-to-many (users follow users, students take courses): add a join table such as follows(follower_id, followee_id) with a composite PK.
  • One-to-one is rare. It is often a hint that two tables should be one, or that you want to split rarely-read wide columns away from a hot row.

Tip: Foreign keys protect integrity but cost a check on every write. At very large scale, and once data is sharded across machines, many teams enforce relationships in application code instead. Say this out loud if the interviewer pushes on scale.
