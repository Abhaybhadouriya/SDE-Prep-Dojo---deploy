Normalization vs denormalization

Normalization means each fact lives in exactly one place. If a restaurant's name is stored once in restaurants, renaming it is a single update. Store the name inside every order row instead and you get three classic bugs, called anomalies:

  • Update anomaly - you rename the restaurant in 9,999 order rows and miss one.
  • Insert anomaly - you cannot add a new restaurant until it has an order, because restaurant data only lives in orders.
  • Delete anomaly - deleting the last order of a restaurant also deletes the only record that the restaurant existed.

The normal forms are the formal rules. 1NF: one value per cell, no repeating groups. 2NF: no column depends on only part of a composite key. 3NF: no column depends on another non-key column (city depends on pincode, not on user_id, so pincode-to-city goes in its own table). A table in 3NF is usually free of the three anomalies. That is what people mean by "normalized".

Denormalization is the deliberate opposite: copy data so a hot read avoids a join. The System Design Primer notes that reads often outnumber writes 100:1 or even 1000:1, so paying a little extra on writes to make reads cheap is often a good deal. It also warns that once data is sharded, a join may cross machines, which makes denormalization even more attractive. But under heavy writes, a denormalized table can perform worse than the normalized one.

Three safe ways to denormalize

  1. Materialized view. The database stores the result of a query and you refresh it (Postgres and Oracle support this natively). Good for dashboards that can be minutes stale.
  2. Cache or read model. Keep the normalized tables as the source of truth, and build a denormalized copy in Redis, Elasticsearch or a separate table. Update it from change events (CDC, see CDC pipeline) or the outbox pattern (Distributed Transactions).
  3. Counter columns. Store like_count on the post instead of counting the likes table each time. Accept that it can lag by a second. For huge counts see Distributed Counter.

The N+1 problem. Code fetches 20 posts (1 query) and then fetches each author in a loop (20 more queries). Each query is fast alone, but 21 network round trips add up. Fix it with a single JOIN, a batched WHERE id IN (...), or by denormalizing the author name onto the post. ORMs cause this silently; watch for it in any feed or list API.

From your world

Normalization is like keeping one routing table (the RIB) as the truth. Denormalization is the FIB pushed into each line card: a copy shaped for the fast path. You accept the cost of keeping copies in sync because lookups vastly outnumber route changes. Same trade, same failure mode when the copy goes stale.

Where this breaks: a FIB is pushed by one control plane that owns the truth; denormalized rows are often updated by many services through async events, so copies can diverge for seconds or be lost entirely unless you add an outbox or a repair job.
