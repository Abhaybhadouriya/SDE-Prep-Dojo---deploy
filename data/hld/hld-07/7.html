Locking: pessimistic vs optimistic

MVCC handles readers. When two writers want the same thing (the last seat, the last unit of stock, the same wallet), you need a concurrency strategy. There are two.

Pessimistic locking assumes conflict. Lock the row first, then work, then commit and release. Others wait.

BEGIN;
SELECT qty FROM inventory WHERE sku = 'TV-55' FOR UPDATE;  -- row lock held
-- app checks qty > 0
UPDATE inventory SET qty = qty - 1 WHERE sku = 'TV-55';
COMMIT;                                                    -- lock released

Optimistic locking assumes conflict is rare. Read without locks, remember a version number, and make the write conditional. If someone else changed the row, zero rows update and you retry.

SELECT qty, version FROM inventory WHERE sku = 'TV-55';    -- qty=3, version=17
UPDATE inventory
   SET qty = qty - 1, version = version + 1
 WHERE sku = 'TV-55' AND version = 17;                     -- 0 rows? someone won: retry
-- even simpler for counters: a guarded atomic update
UPDATE inventory SET qty = qty - 1 WHERE sku = 'TV-55' AND qty > 0;

Lock types and deadlocks

A shared (S) lock lets many readers in; an exclusive (X) lock lets one writer in. Locks come at row, page or table granularity: finer means more concurrency and more bookkeeping. InnoDB also takes gap and next-key locks on index ranges during locking reads, so nobody can insert a phantom row into a range you are checking. A deadlock happens when A holds row 1 and wants row 2 while B holds row 2 and wants row 1. Databases detect the cycle and kill one transaction. You prevent it by always locking rows in the same order (for example, sorted by id) and keeping transactions short.

From your world

Pessimistic locking is a mutex or spinlock. Optimistic locking is a seqlock or a cmpxchg loop: read the sequence number, do the work, and retry if it changed. The kernel uses seqlocks for things read often and written rarely (like jiffies/time), which is exactly when optimistic locking wins in a database too. Lock ordering to avoid deadlock is the same rule lockdep enforces.

Where this breaks: a kernel deadlock hangs the machine, but databases detect deadlocks and kill one transaction, so your app must expect "deadlock detected" errors and retry; and a cmpxchg retry costs nanoseconds while a database retry costs a full round trip.

Across services or machines a row lock is not enough. Then you reach for a lease-based distributed lock with a fencing token (a version number the storage checks, which is optimistic locking again). Kleppmann's essay on distributed locking explains why; see Distributed Lock Service and the Dealing with Contention pattern.
