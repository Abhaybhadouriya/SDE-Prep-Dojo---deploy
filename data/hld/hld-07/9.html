Interview questions

When would you denormalize, and how do you keep copies in sync?

Denormalize when a hot read path needs data from several tables and reads far outnumber writes (feeds, product pages, search documents). Keep the normalized tables as the source of truth and derive the copy: in the same transaction for small copies (a counter column), or asynchronously from change events (CDC or an outbox) for read models in Redis or Elasticsearch. Accept and state the staleness window, and add a periodic reconciliation job.

How to answer

Give the read/write ratio argument, name the source of truth, name the sync mechanism, name the staleness you accept.

Likely follow-ups
  • What if the event to update the copy is lost?
  • Why not just add a cache?
  • What is a materialized view and when does it go stale?
A query WHERE created_at > ? AND user_id = ? is slow even though there is an index on (created_at, user_id). Why, and what do you do?

The range column leads the index, so the database must scan every entry after the date for all users and then filter by user. Reorder it as (user_id, created_at): the equality column first narrows to one user, then the range is a contiguous slice. If the query also selects a couple of columns, add them with INCLUDE to make it covering and skip the table read.

How to answer

State the leftmost-prefix rule, "equality first, range last", then mention EXPLAIN to confirm the plan.

Likely follow-ups
  • Do we keep the old index? (Only if another query needs created_at alone.)
  • What does each extra index cost on writes?
What is a covering index and when is it worth it?

An index that contains every column a query needs, so the database answers from the index without visiting the table (an index-only scan). It is worth it for a very hot, narrow query, such as a user's last 20 orders showing status and total. It costs index size and write time, and in Postgres it only helps when most pages are marked all-visible in the visibility map.

How to answer

Define, give one concrete query, give the cost, mention INCLUDE.

Likely follow-ups
  • Why not include every column?
  • How does InnoDB's clustered PK make some queries covering for free?
B-tree vs LSM-tree: which would you pick for storing chat messages, and why?

Chat is write-heavy, append-mostly, and read by recent range ("last 50 messages in channel X"). An LSM store like Cassandra or ScyllaDB fits: sequential writes, partition by (channel_id, time bucket), cluster by message id descending. Reads are a single-partition range scan. The cost is compaction: if it falls behind, read latency climbs, as Discord saw on 177 Cassandra nodes before moving to 72 ScyllaDB nodes with p99 reads at 15 ms. For a small team chat a Postgres table with (channel_id, msg_id) is fine; B-tree wins when you need transactions and ad-hoc queries.

How to answer

Start from the workload (write rate, read shape), map to engine family, give the partition key, then name the failure mode you would monitor (compaction backlog, hot partitions).

Likely follow-ups
  • What is write amplification and how does compaction strategy change it?
  • How do bloom filters help reads?
  • How do deletes work in an LSM tree? (Tombstones.)
Two users try to book the last seat at the same time. How do you make sure only one succeeds?

Make the database the referee with one atomic, guarded write: UPDATE seats SET status='HELD', holder=?, hold_until=now()+'10 min' WHERE show_id=? AND seat_no=? AND status='FREE'. Exactly one transaction gets "1 row updated"; the other gets 0 and is told the seat is gone. There is no explicit SELECT ... FOR UPDATE, but the UPDATE still briefly row-locks the seat, so the loser waits for the winner to commit. At Read Committed (the Postgres and Oracle default) the second transaction then re-checks the WHERE clause against the new row and updates 0 rows. At Repeatable Read or Serializable, Postgres instead raises a serialization error (SQLSTATE 40001), which the app must catch and report as "seat taken". Interviewers like that follow-up. For a multi-seat booking, take SELECT ... FOR UPDATE on the seats in sorted order (pessimistic, deadlock-safe), or use a unique constraint on (show_id, seat_no) in a bookings table. Expired holds are released by a sweeper.

How to answer

Show the exact SQL. Mention both strategies, choose by contention, and mention ordering locks to avoid deadlocks. Link it to the reservation hold timer.

Likely follow-ups
  • What changes for a flash sale with 1 million users on 1,000 items? (Queue or Redis atomic decrement in front, see d09.)
  • What if the seats are in different shards?
Explain isolation levels. What does Repeatable Read not protect you from?

Read Committed stops dirty reads; Repeatable Read also stops non-repeatable reads (and in Postgres, phantoms) by giving the transaction one snapshot; Serializable makes the result equal to some serial order. Repeatable Read, implemented as snapshot isolation, still allows write skew: two transactions read the same rows and write different rows, breaking an invariant (two doctors both going off call, two meetings booked into one room). Fix with Serializable (and retry on SQLSTATE 40001), or lock the rows you read with FOR UPDATE, or turn the invariant into a unique constraint.

How to answer

Walk the ladder of anomalies, then give the write-skew example. Mention defaults: Postgres Read Committed, MySQL InnoDB Repeatable Read.

Likely follow-ups
  • Why not always use Serializable?
  • How is a lost update different from write skew?
What is MVCC, and what goes wrong with it in production?

The database keeps multiple versions of each row; every transaction reads the versions visible to its snapshot, so readers never block writers. Postgres stores new tuples in the table and cleans dead ones with VACUUM; InnoDB updates in place and keeps old versions in the undo log. Problems: long-running or idle transactions pin old versions, causing bloat and slow queries; heavy updates on many-index tables cause write amplification (Uber's Postgres case); on replicas, long reads can conflict with replay.

How to answer

One-line definition, Postgres vs InnoDB storage difference, then two production failure modes and their fixes (timeouts, fewer indexes, short transactions).

Likely follow-ups
  • Why did Uber move from Postgres to MySQL?
  • What is a visibility map?
Optimistic or pessimistic locking for a shopping cart? For inventory in a flash sale?

Cart: optimistic. One user edits their own cart, conflicts are rare (two tabs), a version column and a retry are enough. Flash-sale inventory: contention is extreme on a single row, so optimistic retries would storm. Use a guarded atomic decrement (qty = qty - 1 WHERE qty > 0), or move the hot counter into Redis (single-threaded atomic DECR) or shard the stock into buckets, and put a queue in front to smooth the spike.

How to answer

Decide by contention rate, then show you know that the hottest rows need a different design, not just a lock choice.

Likely follow-ups
  • How do you avoid overselling if Redis and the DB disagree?
  • How do you release stock from abandoned carts?
Your write latency doubled after a teammate added five indexes. Explain.

Every insert and every update to an indexed column must also update each index: more random page writes, more WAL, more lock time, and more memory pressure in the buffer pool. In Postgres a non-HOT update may touch every index on the table. Audit with the database's index usage statistics, drop unused indexes, merge overlapping ones (an index on (a, b) also serves queries on a alone), and keep write-heavy tables lean.

How to answer

Explain the mechanism, then give a measured cleanup plan.

Likely follow-ups
  • When is a full scan better than an index?
  • Should you drop indexes before a bulk load?
Why use a surrogate ID instead of email as the primary key?

Emails change, are long (bigger indexes everywhere they are a FK), and may be personal data you want to avoid spreading. A surrogate key (bigint or a time-ordered ID like Snowflake) is short, immutable and sorts by creation time, which keeps B-tree inserts at the right edge. Keep email unique with a separate UNIQUE index.

How to answer

Three reasons (mutability, size, privacy), then the index-locality bonus of time-ordered IDs.

Likely follow-ups
  • Why are random UUIDv4 keys bad for B-tree inserts?
  • How do you generate IDs across shards? (d31.)

Scenario: double-booked meeting rooms

Your calendar service (Microsoft and Uber both ask a Google Calendar question) occasionally books two meetings into the same room for overlapping times. The code checks "no overlapping booking exists" and then inserts. The database runs at Repeatable Read.

Weak answer: "Raise the isolation level to Repeatable Read" (already on) or "add a cache".

Strong answer: this is write skew / a phantom: both transactions check the same empty range and both insert different rows. Fixes, from strongest: (1) an exclusion constraint on (room_id, time range) so the database rejects overlaps; (2) lock the room row first with SELECT ... FROM rooms WHERE id = ? FOR UPDATE, which serializes bookings per room; (3) run the transaction at Serializable and retry on 40001. Then add a test that fires parallel bookings.

Likely follow-ups
  • What if rooms and bookings live in different services?
  • How do you handle recurring meetings?

Scenario: metrics ingest is falling over

A Postgres table receives 200,000 metric points per second with five indexes. Disk I/O is pegged and inserts time out. Dashboards query the last hour by (metric, host).

Weak answer: "Buy a bigger disk" or "add another index for the dashboard".

Strong answer: the workload is append-only and write-heavy, which is the LSM sweet spot. Move points to a time-series or wide-column store partitioned by (metric, host, time bucket), batch writes, and keep only one index matching the dashboard query. Keep Postgres for metadata (metric definitions, alerts). Watch compaction lag and set retention with TTLs so old data is dropped by whole files. See d20 Metrics and Choosing Storage.

Likely follow-ups
  • How do you downsample old data?
  • Why not partition by time alone?

The 60-second answer. "I start the data model from the access patterns: list the top queries, then pick keys and indexes that answer each with one lookup or one range scan. I normalize the source of truth and denormalize only hot read paths, kept in sync by events from an outbox. A composite index serves queries on its leading columns, and a covering index avoids the table hop. For write-heavy append data I pick an LSM store like Cassandra; for transactional mixed load, a B-tree database like Postgres. For contention I use a guarded atomic UPDATE or optimistic version checks, and row locks in a fixed order only when I must."
