Indexes: primary, secondary, composite, covering

An index is a separate, sorted data structure that maps a column value to where the row lives. Without one, the database does a full table scan: read every row and test it. With one, it walks a short path to the answer. The price is real: every insert, update and delete must also update every index on the table, and an index can take almost as much disk as the data itself (Hello Interview). For a table of a few hundred rows, a scan is often faster than using an index.

How a B-tree index finds a row

Almost every relational index is a B-tree (strictly a B+ tree: values live in the leaves, leaves are linked left to right). Each node is one disk page, typically 8 KB in Postgres, so one node holds hundreds of keys. The tree is short and fat. With a fan-out of a few hundred, three levels reach millions of rows and four levels reach billions. Finding id = 350 might read only 2 to 3 pages: root, maybe one internal node, then a leaf.

Worked estimate (rule of thumb).

  1. Fan-out. An 8 KB page divided by about 20 bytes per entry (an 8-byte key, a 6-byte child pointer and some overhead) gives about 400 children per node.
  2. Rows per depth. 4002 = 160 thousand, 4003 = 64 million, 4004 = 25.6 billion leaf entries.
  3. So a billion-row table is 4 levels deep, and a point lookup costs 3 to 4 page reads. The root and upper levels are almost always in RAM, so in practice it is 1 to 2 real disk reads. That is why point reads on an indexed column stay fast as the table grows 1,000x: you add one level, not 1,000x the work.

Primary vs secondary index

The primary index is built on the primary key. A secondary index is any other index, such as on email. What a secondary index entry points to differs by engine, and Uber's famous migration write-up shows why it matters:

MySQL InnoDBPostgreSQL
Table layoutClustered: rows live inside the PK B-tree, sorted by PKHeap: rows in an unordered file; every index points at a physical location (ctid)
Secondary index storesThe PK value; lookup = two B-tree searchesThe row's ctid; lookup = one index search + one heap read
Update of one columnOnly indexes on changed columns are touchedA new row version gets a new ctid, so every index may need a new entry (Uber: one update, 12 index writes, all in the WAL)

Postgres later added optimizations for this (heap-only tuple updates), but the lesson stays: more indexes means more write amplification. Index the queries you have, not the ones you might have.

Composite indexes and the leftmost-prefix rule

A composite (multi-column) index on (user_id, created_at) sorts first by user, then by time within each user. Think of a phone book sorted by last name then first name. It is great for "Sharma, Riya" and for "all Sharmas", and useless for "everyone named Riya".

Query on index (user_id, created_at)Uses index well?
WHERE user_id = 42Yes (leftmost column)
WHERE user_id = 42 AND created_at > '2026-11-01'Yes (equality, then range)
WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20Yes, and no sort step: rows come out in order
WHERE created_at > '2026-11-01'Poorly: leading column skipped (PostgreSQL 18+ can "skip scan" when user_id has few distinct values; older versions cannot)

The rule of thumb from the Postgres docs: put columns used with equality first, the range or sort column last, and be suspicious of indexes with more than three columns. Postgres allows up to 32 columns, but that is a limit, not a goal.

Covering indexes

A covering index contains every column the query needs, so the database answers from the index alone and never reads the table. Postgres calls this an index-only scan and lets you add non-key payload columns with INCLUDE:

-- feed query: newest 20 orders for a user, showing status and total
CREATE INDEX orders_user_time
  ON orders (user_id, created_at DESC)
  INCLUDE (status, total_amount);

SELECT created_at, status, total_amount
FROM orders
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;           -- served entirely from the index

One Postgres detail: index entries carry no visibility information, so an index-only scan checks a visibility map (one bit per table page). It only saves work on pages marked "all visible", which is the norm for mostly static rows.

Indexes can also be dense (one entry per row; find by binary search, more upkeep) or sparse (one entry per block; smaller, then scan inside the block). Kafka's offset index and SSTable block indexes are sparse; most B-tree secondary indexes are dense.

Say it like this: "For every API I listed, here is the index that serves it. (user_id, created_at DESC) covers the history page with no sort. I am not indexing status alone because it has four values; a scan of the index would not narrow much." Tying each index to a query is what separates strong answers.
