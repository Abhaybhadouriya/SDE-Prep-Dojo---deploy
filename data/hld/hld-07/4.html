Storage engines: B-tree vs LSM-tree

A storage engine is the part of a database that lays bytes on disk. There are two big families, and knowing them lets you predict how a database behaves before you read its docs.

B-tree engines update in place. To change a row, find its page, modify it, write the page back. Before that, the change is appended to a write-ahead log (WAL) so a crash cannot lose it. Reads are fast and predictable. Writes are random I/O: one small change rewrites a whole 8 to 16 KB page.

LSM-tree engines never update in place. LSM stands for Log-Structured Merge tree. Writes go to the WAL and an in-memory sorted table, then are flushed to disk as immutable sorted files called SSTables (Sorted String Tables). Background compaction merges files. Writes become sequential and fast. Reads may have to look in several places. Click through the write and read path:

  1. Log first. The write is appended to the WAL. Sequential append, so it is fast, and after a crash the WAL is replayed.
  2. Memtable. The same write goes into a sorted in-memory structure, often a skip list. The client gets "OK" now.
  3. Flush. When the memtable fills (tens of MB), it is written out in one sequential pass as an immutable SSTable. The WAL for it can be dropped.
  4. Compact. Background jobs merge SSTables, keep only the newest version of each key, and drop deleted keys (tombstones). In leveled compaction each level is 10x the one above.
  5. Read. Check the memtable, then L0 files, then at most one file per lower level. Several places to look: this is read amplification.
  6. Bloom filter. (The read box is replaced by the filter check; the red file is one the filter rules out.) Each SSTable keeps a small bloom filter. At RocksDB's default 10 bits per key it wrongly says "maybe" about 1% of the time, so most files that do not hold the key are skipped without a disk read.

The three amplifications

The RocksDB tuning guide gives the vocabulary every storage discussion uses:

  • Write amplification = bytes written to disk / bytes the app wrote. If you write 10 MB/s and the disk sees 30 MB/s, it is 3. In RocksDB's own leveled example (500 GB database) it is about 33, because compaction rewrites data at each level.
  • Read amplification = disk reads per query. Five page reads per lookup means 5.
  • Space amplification = disk used / real data size. Leveled compaction keeps it near 1.1; universal (tiered) compaction trades lower write amplification for more space.

You can push one down only by pushing another up. B-trees have low read and space amplification but rewrite whole pages for tiny changes. LSM trees make writes cheap and pay later in compaction and read work.

Real failure story: compaction debt. Discord stored trillions of messages in Cassandra, partitioned by (channel_id, bucket) where a bucket is a fixed time window. When compaction fell behind, reads had to touch more SSTables, latency climbed, and through quorum reads the slowness spread across the cluster. Busy channels created hot partitions; JVM garbage-collection pauses made it worse. They moved to ScyllaDB (same LSM model, C++, no GC): 177 Cassandra nodes became 72, p99 read latency (p99 = the latency that 99% of requests beat; 1 in 100 is slower) went from 40-125 ms to 15 ms, and p99 inserts from 5-70 ms to a steady 5 ms. Their final migration even stalled at 99.9999% on token ranges full of uncompacted tombstones.

From your world

The WAL is exactly ext4's journal (jbd2): write intent sequentially, apply later, replay after a crash. A memtable flush is the page cache writing back dirty pages in one batch. An LSM engine is a log-structured filesystem (think F2FS on flash) with compaction playing the role of the segment cleaner. And the reason LSM loves SSDs is the same reason flash translation layers exist: flash hates small random in-place writes.

Where this breaks: a filesystem journal is usually replayed and then truncated, but an LSM engine keeps many overlapping sorted files for good, so reads must check several of them, which a journaling filesystem never needs to do.

Kafka sits at the far end of this spectrum: a pure append-only log with a sparse offset index and no in-place updates at all. See Kafka storage internals for how far sequential I/O can go.
