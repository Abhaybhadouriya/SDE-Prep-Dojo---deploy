Architecture: follow one post

Click Next or Play. A user in Bengaluru posts "Power cut in Koramangala again #BescomFail".

  1. Publish. The posting service writes the post to its database and publishes it to the Kafka topic posts.created. Trends is one more consumer group; posting is not slowed.
  2. Filter. Drop replies and low-quality posts, apply spam signals (account age, bot score), language detection and safety rules. Twitter's 2015 trends post describes exactly this kind of filtering step.
  3. Extract terms. Pull hashtags, named entities and short phrases; normalise ("#BescomFail" → "bescom fail"); map the user to locations (city IN-BLR, country IN, global). Emit one small event per (location, term), keyed by location|term.
  4. Count. A Flink job owns each key's partition. It keeps 1-minute buckets with exact counts for candidates, a count-min sketch for the long tail, and a HyperLogLog of distinct authors per term.
  5. Score. Every 30-60 s it compares the last 10 minutes with the term's baseline for this hour of the week (from the baseline store, refreshed by a batch job) and computes a z-score-like velocity score.
  6. Merge. Each partition sends its local top 100 per location to a merger, which builds the global top 30 per location, applies the blocklist and clusters variants ("#INDvAUS", "India vs Australia").
  7. Serve. The merger writes trends:{location} to Redis with an as_of time. The Trends API reads it; a CDN caches responses for ~30-60 s. Home screens never trigger computation.

From your world

Keying term events by location|term is ECMP flow hashing: every packet of one flow goes to one path so one place sees the whole flow. Here every mention of one (location, term) goes to one worker so one worker holds the complete count, with no locks and no cross-worker adds. The local-top-K → merger step is like line cards exporting their top talkers to the route processor, which merges them into a chassis-wide view. Where it breaks: ECMP only needs to keep packets in order, and re-hashing a flow costs nothing. Here the key also decides which worker holds the counters, so changing the key or the partition count moves state, and a skewed key cannot be spread by hashing alone - you must salt it.

The whiteboard version

posts topic → filter + extract → term-events (key = location|term) → windowed counters + scorer (Flink) → merger → Redis/CDN → Trends API, with a batch job feeding baselines. Six boxes plus one side box.
