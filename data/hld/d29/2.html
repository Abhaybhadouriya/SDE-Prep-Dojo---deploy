Back-of-envelope estimation

All numbers are interview assumptions. The method is what matters. (Refresher: Back-of-Envelope Estimation.)

  1. Posts per second. Assume 500M posts/day. 500M / 86,400 ≈ 500M / 100k = ~6k posts/s average. Assume 5x at a normal daily peak (~30k/s) and design for ~60k/s during a huge event.
  2. Term events. Each post yields ~3 candidate terms (hashtags, entities, phrases). Each term is counted for the post's city, its country and global: ~3 location keys. So 6k x 3 x 3 ≈ ~54k counter updates/s average, ~0.5M/s in a huge spike.
  3. Bandwidth. A term event (term, location, user id, timestamp, post id) ≈ 100 bytes. 54k x 100 B ≈ 5.4 MB/s. Tiny for Kafka. Raw posts at ~1 KB each are ~6 MB/s.
  4. Why not exact counts? The vocabulary is unbounded: misspellings, new names, every random hashtag. If an hour sees ~50M distinct (location, term) keys and each exact counter with its key costs ~60 bytes in a hash map, that is ~3 GB per hour bucket, and we want many buckets. A sketch keeps memory fixed.
  5. Count-min sketch size. Error ≤ ε x N with probability 1 - δ. Width w = ⌈e/ε⌉, depth d = ⌈ln(1/δ)⌉. With ε = 0.001 and δ = 0.01: w = 2,719, d = 5 → ~13.6k counters ≈ 54 KB at 4 bytes each. Global per minute N ≈ 6k x 3 x 60 ≈ 1.1M, so error ≤ ~1,100 counts - too coarse for small cities but fine as a candidate filter when combined with exact counts for the few top candidates.
  6. Buckets. 1-minute buckets, kept for 24 hours (for the baseline) = 1,440 buckets per location. Exact counts only for candidates (say top 1,000 per location) → 400 locations x 1,000 terms x 1,440 x ~16 B ≈ ~9 GB total - spread over the stream workers, fine.
  7. Reads. Assume 200M daily users x 10 home loads = 2B reads/day ≈ ~23k reads/s. But the answer is tiny: 400 locations x 30 trends x ~100 B ≈ 1.2 MB. Precompute and cache it everywhere. Reads are trivial; the work is all on the write path.
