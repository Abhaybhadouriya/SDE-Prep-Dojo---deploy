1. Velocity, not volume: the trend score

If we rank by raw count, "good morning", "happy birthday" and the name of the most famous footballer trend every day. We want surprise. A simple, explainable score: treat the expected count in this window as b (from the baseline for this term, location and hour of the week) and the observed count as c. Counts of independent events behave roughly like a Poisson process (random, independent arrivals at a steady average rate - think packet arrivals on a quiet link), whose standard deviation is about the square root of the mean. A z-score = how many standard deviations the observed value sits above normal. So:

import math

def trend_score(c, b, distinct_users, k=10):
    """c = mentions in the last 10 min, b = expected mentions for this
    term/location/hour-of-week, k = smoothing so brand-new terms with b=0
    need a real crowd before they score highly."""
    if distinct_users < 50:          # minimum crowd: one loud account is not a trend
        return 0.0
    return (c - b) / math.sqrt(b + k)

print(round(trend_score(c=12000, b=11500, distinct_users=9000), 1))   # "good morning"
print(round(trend_score(c=2400,  b=40,    distinct_users=1900), 1))   # "power cut"
$ python trend_score.py
4.7
333.8

"Good morning" is huge but expected, so it scores about 4.7; "power cut" is small but 60x its baseline, so it scores about 334. Production systems add more: seasonality (baseline by hour-of-week, because Sunday-night cricket chatter is normal), exponential decay so a trend fades smoothly after the spike, and a minimum distinct users threshold.

"Trending is anomaly detection: observed rate vs expected rate for that term, place and hour. I would start with a Poisson-style z-score because it is explainable and cheap, and tune it offline against labelled past events."

2. Sliding windows without recounting everything

"Last 10 minutes, updated every minute" is a hopping (sliding) window. Naively recounting 10 minutes of events every minute wastes work. Instead keep 1-minute buckets in a ring: the 10-minute count is the sum of the last 10 buckets; every minute add the new bucket and subtract the oldest. Count-min sketches can be added and subtracted cell by cell too, as long as they share the same width, depth and hash functions.

Use event time (when the post was made), not processing time, with a watermark that waits a few seconds for late events; otherwise a consumer that falls behind would create fake spikes when it catches up. In Flink SQL:

SELECT window_start, window_end, location, term,
       COUNT(*)                AS mentions,
       COUNT(DISTINCT user_id) AS authors
FROM TABLE(
  HOP(TABLE term_events, DESCRIPTOR(event_time), INTERVAL '1' MINUTES, INTERVAL '10' MINUTES))
GROUP BY window_start, window_end, location, term;

3. Counting the long tail: sketch + candidates

Use two tiers. The count-min sketch sees every term and answers "roughly how often?" with fixed memory. When a term's sketch estimate crosses a small threshold, promote it into a candidate set (a min-heap or Space-Saving structure of a few thousand entries - Space-Saving keeps k counters, and when a new term arrives and all k are full it evicts the smallest counter and gives the newcomer that count + 1, so heavy terms can never be pushed out) that keeps exact counts from then on. Scoring and display use exact candidate counts. Redis ships both structures, which is handy for a prototype (its Top-K uses HeavyKeeper, a newer sketch that decays the counters of small items so heavy ones stay):

In the real pipeline these structures live inside the stream job's state (checkpointed), not as network calls per event - 54k Redis round trips per second is possible, but in-process state is cheaper and survives failures through checkpoints. The detailed maths of merging local top-Ks is on Top-K / Heavy Hitters.

4. Hot keys: when the whole country says one word

During a cricket final, "#INDvAUS" in location "IN" may be 30% of all events, and all of them hash to one partition and one worker. Fixes: (a) pre-aggregate before the shuffle - the extractor keeps a tiny in-memory map per second and sends "#INDvAUS +412" instead of 412 events (a combiner, as in MapReduce: pre-sum on the sender so fewer, bigger messages cross the network); (b) salt known-hot keys into N sub-keys (IN|#INDvAUS|3) and sum them in the merger. Pre-aggregation alone usually cuts traffic by orders of magnitude for the hottest terms.

5. Spam, manipulation and safety

Trends are valuable, so people attack them. Defences, cheapest first:

  • Count people, not posts. Score on distinct authors (HyperLogLog, ~12 KB per counter, about 0.81% standard error; held in the stream job's state in production) so one account posting 10,000 times counts once.
  • Weight by trust. New accounts, accounts flagged by the spam system, or accounts that all post the same text get low weight.
  • Diversity checks. A real trend has many unrelated users in many places; a campaign has a tight cluster created last week. Twitter's research on event detection uses clustering of related terms for this kind of grouping.
  • Policy layer. Blocklists, a human review queue for high-visibility locations, and a "pause trends" switch.

Careful: do not let the blocklist live only in code. It must be updatable in seconds (a broadcast stream or a config watched by the job), because the moment you need it is during an incident.
