Where Kafka, Kubernetes and Docker fit

📨

Kafka

Trends is an independent consumer group on posts.created. A second topic, trends.term-events, is keyed by location|term so each key has one owner. Lag in seconds = how stale trends are.

 🌊

Flink / Kafka Streams

Windowed, keyed, stateful counting with event time and watermarks. Checkpoints save counters and Kafka offsets together, so a crash neither loses nor doubles counts.

 ☸️

Kubernetes

Flink runs under its Kubernetes operator; parallelism matches partitions. The Trends API is a stateless Deployment with an HPA; Redis runs as a StatefulSet or managed service.

 🐳

Docker locally

One Kafka broker, Redis 8 (image: redis:8.2 - count-min sketch and Top-K are built into Redis 8; on Redis 7.x use redis/redis-stack) and a Python producer replaying a sample of posts in Compose is enough to watch a fake trend appear.

 
$ kafka-topics.sh --bootstrap-server localhost:9092 --create \
    --topic trends.term-events --partitions 48 --replication-factor 3 \
    --config retention.ms=604800000 --config compression.type=lz4
Created topic trends.term-events.

(Other designs on this site pin redis:7.4; that image has no CMS.* / TOPK.* commands and answers "ERR unknown command".)

Partition 17 is far behind while the others are fine - a classic hot key signature (deep dive 4). Lag on every partition would instead point to the whole job being too slow or a downstream sink blocking.

From your world

Consumer lag is queue depth. One queue deep while its siblings are empty is an elephant flow stuck on one ECMP member. The fix is also the same: split the elephant (salting) or summarise before the bottleneck (pre-aggregation). Where it breaks: a router queue drains at line rate, so depth maps straight to delay; Kafka lag is in messages, and the delay depends on how fast that one worker processes them - divide lag by the consumer's rate to get seconds, which is the number to alert on.
