The solution ladder: naive to best

Rung 1: call the services one after another in a request handler

The checkout handler calls inventory, then payment, then shipping, then returns. It is easy to write and fine for a demo. It breaks when: a call times out (did it succeed?), the handler crashes between calls (nobody remembers what was done), a step must wait hours (an HTTP request cannot), or a retry repeats a non-idempotent call. Every fix you bolt on (retry loops, "pending" flags, a cron that cleans up stuck orders) mixes infrastructure failure handling into business logic.

Rung 2: two-phase commit (2PC)

A coordinator asks every participant to prepare (lock what you need and promise you can commit). If all say yes, it tells them to commit; if any says no, everyone aborts. You get true atomicity across databases. karanpratapsingh's book lists the problems: what if a node crashes, what if the coordinator crashes, and above all, it is a blocking protocol. Prepared participants hold locks until they hear the decision. Three-phase commit adds a pre-commit phase so steps can time out, but it is rarely used: it assumes a synchronous network (messages arrive within a known time). Under a network partition, one side can time out and commit while the other times out and aborts, so the outcome is inconsistent anyway. Real systems instead make the coordinator itself fault-tolerant by replicating its decision with consensus (Spanner-style 2PC whose coordinator and participants are Paxos groups). Most importantly, Stripe, a courier API and Kafka cannot take part in 2PC at all. Use 2PC only inside one database product that offers it (for example, a distributed SQL database across its own shards).

Level 3 - Intermediate

Rung 3: the saga (choreographed with events)

A saga, in karanpratapsingh's words, is a sequence of local transactions where each one updates its database and publishes an event that triggers the next. In choreography, there is no central boss. The order service writes the order and emits OrderCreated; inventory listens, reserves stock and emits StockReserved; payment listens and charges; and so on. A failure event (PaymentFailed) makes earlier services run their compensations.

Azure's saga guidance lists the trade-off: choreography is simple for a few steps and has no single point of failure, but it gets confusing as steps are added, risks cyclic dependencies between services, and is hard to test because all services must run. Netflix built Conductor for exactly this reason: their content-platform processes were glued together with pub/sub, direct REST calls and a database for state, and as the services grew, they lost visibility into the flows.

Rung 4: the orchestrated saga

In orchestration, one component (the orchestrator) owns the process. It stores the saga's state, tells each participant what to do, and runs compensations in reverse on failure. Azure notes the benefits (clear flow, no cyclic dependencies, easier to change) and the main drawback (the orchestrator is extra infrastructure and a potential point of failure, so it must itself be durable).

  1. The orchestrator records "step 1 started", asks inventory to reserve stock, and records the result.
  2. It asks payment to charge the card with an idempotency key (the order id), then records the payment id.
  3. Shipping fails with a business error. Retrying will not help, so the saga must go backwards.
  4. Compensations run in reverse order. Payment refunds the charge (a new transaction, not an erase).
  5. Inventory releases the reservation. Each compensation is idempotent and retried until it succeeds.
  6. The saga ends in a known, consistent final state: cancelled and refunded. Nothing is left half-done.
Level 4 - Advanced

Compensable, pivot and retryable steps

Azure's saga guidance gives three useful labels. Compensable steps can be undone by another transaction (release stock, refund). The pivot step is the point of no return; once it succeeds, the saga must go forward. Retryable steps come after the pivot; they must be idempotent and are retried until they succeed (send the email, update search). Design trick: order the steps so the risky, hard-to-undo step is the pivot and comes as late as possible. For example, reserve stock and authorise the card first (cheap to undo), and capture the payment or dispatch the courier last.

Sagas are not isolated

A database transaction hides its half-finished state; a saga does not. microservices.io names this as the main drawback: lack of isolation, so concurrent sagas can see each other's partial results. Azure lists the anomalies: a lost update (one saga overwrites another's change without reading it), a dirty read (one saga reads data another saga has written but not yet finished or may undo), and a fuzzy read (one saga reads the same data twice and gets different values because another saga changed it in between). Here is a concrete dirty read:

  1. t = 0. Saga A reserves the last unit of a phone. Stock goes from 1 to 0.
  2. t = 1 s. Customer B asks for the same phone. Saga B reads stock 0 and refuses: "sold out".
  3. t = 3 s. Saga A's payment is declined, so A compensates and releases the unit. Stock is back to 1.
  4. Result. B was turned away because of a change that never really happened. Inside one database, B would not have seen A's uncommitted change.

Countermeasures include a semantic lock (a status flag such as PENDING or RESERVED that a saga sets on the record, and that other sagas and the UI respect; here, B could see "reserved, may free up" and offer a wait-list instead of "sold out"), commutative updates (apply deltas, not absolute values), a pessimistic view (reorder steps to reduce exposure), rereading values before writing, and version files (record the order of operations). In interviews, the semantic lock is the one to name: the order is visibly "PENDING_PAYMENT", and the UI and other services treat it that way.

Rung 5: the transactional outbox (so events are never lost)

Every saga step does two things: change its own data and tell the next step. If you write to the DB and then publish to Kafka, a crash between them loses the event (or, in the other order, publishes an event for a change that never committed). The outbox fixes it: write the business row and an outbox row in one local transaction. A separate relay reads the outbox and publishes. Debezium's post describes doing this with change data capture: the outbox columns are an id, an aggregate type, an aggregate id (used as the Kafka key, so events for one order stay in order), an event type and a payload, and its EventRouter transform routes each row to a topic.

BEGIN;
UPDATE orders SET status = 'PENDING_PAYMENT' WHERE id = :order_id;
INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)
VALUES (gen_random_uuid(), 'Order', :order_id, 'OrderPlaced', :json);
COMMIT;
-- Debezium (or a poller) turns each outbox row into a Kafka message keyed by aggregateid

The outbox gives at-least-once publishing, so every consumer must be idempotent: keep a "processed message ids" (inbox) table, or make the operation naturally idempotent. More detail is in Distributed Transactions & Event-Driven Data and CDC Pipeline.

Rung 6: durable execution (workflow engines)

Writing a correct orchestrator by hand (state tables, timers, retries, versioning) is a big job. Workflow engines do it for you. There are two styles:

  • Code-first durable execution: Temporal and Uber's Cadence (Temporal's ancestor). You write the workflow as ordinary code. Uber's Cadence 1.0 announcement says it is used by over a thousand services at Uber, and by DoorDash, HashiCorp and Coinbase.
  • Definition-first state machines: AWS Step Functions (JSON state language) and Netflix Conductor (a JSON blueprint of tasks), plus Airflow for data pipelines.

How durable execution works, following the Hello Interview Temporal deep dive: the engine records an event history for each workflow run (step started, step completed with result, timer fired). Workflow code is split into the workflow (deterministic orchestration logic) and activities (the side effects: call Stripe, write the DB). If a worker dies, another worker replays the workflow code from the start; completed activities are not called again, their recorded results are returned. That is why workflow code must be deterministic: no reading the real clock or random numbers directly, only the SDK's replay-safe versions. A sleep(5 days) becomes a durable timer stored by the engine, so no process stays alive while waiting. External events (a courier webhook) arrive as signals recorded in the history.

Important caveat from the same source: if an activity succeeds but the worker dies before the engine records completion, the engine will run it again. So activities that touch the outside world still need idempotency keys. Airbnb's Orpheus shows a clean way to structure such a call: a pre-RPC phase that records the request in the database, the RPC itself with no database work, and a post-RPC phase that records the result and whether a failure is retryable, keyed by an idempotency key with an expiring lease. Airbnb also learned to read idempotency records only from the primary, because replica lag once caused a duplicate payment.

Step Functions guarantees, in AWS's words: Standard workflows can run up to one year and follow an exactly-once model for task execution (unless you configure retries), which suits non-idempotent steps like payments. Express workflows run up to five minutes and are at-least-once, so their steps must be idempotent (more precisely, asynchronous Express executions are at-least-once and synchronous Express executions are at-most-once; see AWS's Standard vs Express comparison). Choose by duration and by whether your steps can safely run twice.

Hard parts engines do not remove

  • Versioning. Changing workflow code while millions of runs are mid-flight can break replay. Engines offer version markers or "run new code only for new workflows".
  • History size. A workflow that loops forever (a subscription that renews every month) grows its history without bound; you periodically restart it with fresh history (Temporal calls this continue-as-new).
  • Exactly-once is your job at the edges. The engine gives durable orchestration; the external API still needs an idempotency key.
  • The engine is critical infrastructure. Temporal's own services (frontend, history, matching) scale as separate fleets over PostgreSQL, MySQL or Cassandra; history is split into a fixed number of shards. Someone has to run it, or you pay for a managed service.

Worked estimate: how many sagas are in flight?

Interviewers ask "how big does the orchestrator store get?". Use Little's Law: items in the system = arrival rate x time each item stays. Example numbers for practice (not from a source):

  1. In flight. 500 orders/s x a saga that lasts about 10 minutes (600 s) = 300,000 sagas running at any moment.
  2. History rows. About 10 history events per saga (started, reserved, authorised, shipped, timers...) = 3 million rows of live history.
  3. Write rate. 500 orders/s x 10 events = 5,000 history writes/s, plus outbox rows for each event.
  4. What it justifies. 5,000 writes/s and millions of hot rows is past a comfortable single primary for this workload, so shard the orchestrator store by workflow id (Temporal splits history into a fixed number of shards for this reason), keep each history short (continue-as-new for long loops), and delete outbox rows soon after they are published.

The same formula sizes a waiting queue: if a saga instead waits 3 days for a courier, 500/s x 259,200 s = about 130 million open sagas. That is why long waits belong in durable timers on cheap storage, not in threads or open connections.
