Kafka, Kubernetes and Docker in this pattern

Kafka: the event spine of a saga

  • Key by saga id (order id) so all events for one order are in one partition and arrive in order (partitions).
  • Outbox + Debezium through Kafka Connect publishes events reliably (Connect).
  • Idempotent consumers: Kafka delivers at least once by default; exactly-once transactions only cover Kafka-to-Kafka flows, not your database or Stripe (delivery semantics).
  • Retry topics and DLQs for steps that keep failing, with an alert and a manual replay tool (pipeline retries & DLQ).

Kubernetes

Workflow workers are ordinary stateless Deployments: they poll a task queue, so you can scale them on queue depth with an autoscaler (autoscaling). Temporal's server components run well as separate Deployments (frontend, history, matching) with the database outside or as a StatefulSet (StatefulSets). Kubernetes itself is a big orchestrator: controllers loop "observe, compare desired to actual, act", which is the same retry-until-consistent idea as a saga's retryable steps. Kubernetes Jobs with backoffLimit cover one-step batch work; Argo Workflows adds DAGs on top for CI/CD and data pipelines.

Docker

The quickest way to learn this is to run it. Temporal ships a Docker Compose setup for a local server, and Debezium's examples repository has a Compose-based outbox demo with Postgres, Kafka and Connect (Compose, build the pipeline locally).
