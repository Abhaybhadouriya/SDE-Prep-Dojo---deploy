In the interview

Phrases that land well

  • "There is no transaction across these services, so I'll use a saga: each step is a local transaction with a compensating action."
  • "Payment capture is the pivot, so I put it last; steps after it are idempotent and retried until they succeed."
  • "Each step writes its state and an outbox row in one transaction, so no event is lost."
  • "Every external call carries an idempotency key derived from the order id and step name."
  • "The order shows PENDING while the saga runs; that is a semantic lock, since sagas have no isolation."

Traps

  • Proposing 2PC across Stripe, Kafka and your DB. They cannot participate.
  • Treating compensation as "delete the row". A refund is a new transaction; the history stays.
  • Forgetting that compensations can fail too: they must be idempotent and retried.
  • Publishing to Kafka after the DB commit without an outbox (the dual-write bug).
  • Using a workflow engine for a two-step flow that a single transaction plus an outbox could handle.
Explain the saga pattern vs two-phase commit. When would you use each?

2PC makes a change atomic across participants by preparing (locking) everywhere and then committing. It gives isolation but blocks while the coordinator is slow or down, and every participant must support the protocol. A saga is a sequence of local transactions, each with a compensating action; it gives eventual consistency without cross-service locks, but no isolation, so you add semantic locks like a PENDING status. Use 2PC only within one database system that implements it across its shards. Use sagas across services and external APIs.

How to answer

One line each, then the deciding question: "Can every participant join a transaction, and can I afford to hold locks?"

Likely follow-ups
  • Choreography or orchestration for checkout?
  • What happens if a compensation fails?
Your server charges the card and crashes before saving the result. What happens and how do you make it safe?

On restart we do not know if the charge happened. Make the charge idempotent: before calling, record the attempt with an idempotency key (order id + step) in our DB; send the same key to the payment provider so a retry returns the original result instead of charging again; after the call, record the result. On recovery, any attempt without a recorded result is retried with the same key or reconciled by querying the provider. Airbnb's Orpheus formalises this as pre-RPC, RPC and post-RPC phases. A durable engine (Temporal) records completions too, but it may still re-run an activity if the crash came before the completion was recorded, so the key is still needed.

How to answer

Name the gap (side effect done, record not saved), then close it with an idempotency key on both sides plus reconciliation.

Likely follow-ups
  • How long do you keep idempotency keys?
  • Why read idempotency records from the primary only? (Airbnb saw a duplicate payment from replica lag.)
What is the transactional outbox and why do you need it?

It solves the dual write: updating a DB and publishing to a broker cannot be one atomic action. Write the business change and an outbox row in the same local transaction. A relay (Debezium reading the WAL, or a poller) publishes outbox rows to Kafka, keyed by aggregate id to keep per-entity order. Publishing is at least once, so consumers dedupe with an inbox table or idempotent operations.

How to answer

Draw the two failure orders of dual writes, then the single-transaction fix, then the duplicate caveat.

Likely follow-ups
  • Polling relay vs CDC: trade-offs?
  • How do you clean up the outbox table?
Design the order placement flow for an e-commerce site with inventory, payment and shipping services.

Client calls POST /orders with an idempotency key. The order service creates the order as PENDING and starts an orchestrated saga (outbox event or a workflow start). Steps: reserve stock with a TTL (compensate: release), authorise payment (compensate: void), create shipment (compensate: cancel), then capture payment as the pivot, then retryable steps: confirm order, email, update search. Each step is idempotent, keyed by order id. The client polls or receives a push for the final status. A reconciliation job compares orders, payments and shipments daily. One more failure mode to raise: card authorisations expire (often about 7 days, but it is provider-specific), so if the flow can wait longer than that (backorder, a human approval), re-authorise or capture at a bounded deadline; a durable timer in the workflow handles this.

How to answer

Draw the forward line and the compensation line, mark the pivot, then talk failures step by step.

Likely follow-ups
  • Payment provider is down for 10 minutes. What does the user see?
  • Two sagas compete for the last unit. (Reservation in Dealing with Contention.)
Transfer money between two wallets on different database shards.

Option 1: a saga. Debit A with a ledger entry and a "transfer pending" record (outbox event); credit B on its shard (idempotent by transfer id); mark the transfer complete. If crediting B fails permanently, compensate by crediting A back. Users may briefly see money "in transit", which is acceptable and honest. Option 2: if both shards are in a database with native distributed transactions, use it. Either way, use a double-entry ledger and reconciliation so total money is conserved.

How to answer

State the invariant (money is conserved), then the saga, then how you detect violations (reconciliation).

Likely follow-ups
  • How do you stop A from spending the pending amount twice?
  • See Digital Wallet & Ledger.
When would you use a workflow engine like Temporal or Step Functions instead of a queue-based saga?

When the process has many steps, branches, long waits (hours or days), human tasks or complex retries, and you need to see the state of each run. The engine gives durable timers, signals for external events, retries with backoff, history and replay, so business code stays readable. For a two or three step flow with no waits, an outbox and a few consumers is simpler. Uber built Cadence for this, and its 1.0 announcement says over a thousand Uber services use it.

How to answer

List the signals that justify an engine (long waits, branching, visibility), then the cost (new infrastructure, determinism rules, versioning).

Likely follow-ups
  • Why must Temporal workflow code be deterministic?
  • How do you deploy a change while workflows are running?
How does durable execution survive a worker crash, and what rules does it put on your code?

The engine stores an append-only event history per run: activities scheduled and completed with results, timers, signals. A new worker replays the workflow function from the start; when the code reaches an activity that already completed, the engine returns the recorded result instead of calling it. So workflow code must be deterministic: no direct clock, random numbers or network calls, only the SDK's replay-safe versions, and all side effects go in activities. Waits become durable timers, so nothing stays in memory. Long-running workflows restart with fresh history periodically to keep it small.

How to answer

Explain it as event sourcing for code: history plus deterministic replay. Then give one example of non-determinism breaking replay (reading the time to choose a branch).

Likely follow-ups
  • Where is the history stored and how is it sharded?
  • Is an activity exactly-once?
Two sagas run at once on the same order or the same stock. What anomalies can happen and how do you prevent them?

Because sagas commit each step, others can see partial state: a cancel saga may run while a payment saga is mid-way (lost update), or a report may read stock that a failing saga will release (dirty read). Countermeasures from Azure's guidance: a semantic lock (status PENDING; other sagas wait or reject), commutative updates (apply deltas), reordering steps so risky ones come later, rereading values before writing, and version numbers to detect conflicts. Simplest in interviews: one saga per order at a time, enforced by the order's state machine.

How to answer

Say "sagas are ACD, not ACID", give one concrete anomaly, then the semantic lock.

Likely follow-ups
  • User clicks cancel while payment is being captured. Who wins?
Choreography or orchestration: which would you choose and why?

Choreography for short flows owned by independent teams, where loose coupling matters and it is fine that nobody has the whole picture. Orchestration once there are more than a few steps, compensations, timeouts or a need to answer "where is this order?". Netflix moved to an orchestrator (Conductor) because ad-hoc pub/sub plus REST plus database state lost visibility as the number of services grew. A mix is common: orchestrate the core flow, publish events for side listeners like analytics.

How to answer

Give the rule of thumb (number of steps and need for visibility) and a real example.

Likely follow-ups
  • Is the orchestrator a single point of failure?
A food order must be accepted by the restaurant within 5 minutes or it is cancelled and refunded. How do you build the timeout?

Model the order as a workflow: after payment, wait for an "accepted" signal or a 5-minute durable timer, whichever comes first. On timeout, run compensations (refund, notify user) and mark CANCELLED. Without an engine: store accept_deadline on the order, put a delayed message on a queue (or poll an index on deadlines), and make the timeout handler conditional (UPDATE ... WHERE status='PLACED') so a late acceptance and the timeout cannot both win.

How to answer

Show the race between "accept" and "timeout", then resolve it with one conditional state transition.

Likely follow-ups
  • How do you handle a million orders with timers at once?

Scenario: customers charged, no order

Support reports 40 customers per day who were charged but have no order. The checkout handler calls payment, then inserts the order, then publishes to Kafka.

"Add more retries around the insert."

This is a missing-state bug: the side effect happens before we durably know about it. Create the order as PENDING first (with outbox), then charge with the order id as idempotency key, then record the result. Add a recovery job that finds PENDING orders older than N minutes and asks the provider for the charge status by idempotency key. Add daily reconciliation between provider reports and our ledger, and refund the existing 40.

Likely follow-ups
  • Which metric would have caught this earlier?

Scenario: a workflow deploy breaks running orders

You added a fraud check as step 2 of the Temporal order workflow. After deploy, thousands of in-flight workflows fail with non-determinism errors.

"Roll back and never change workflows."

Old runs replay their history against new code, which now schedules a different activity at step 2, so replay no longer matches. Use the engine's versioning: branch on a version marker so old runs keep the old path and new runs take the new one, or start new runs on a new workflow type and let old ones drain. Add a replay test in CI that replays recorded histories against the new code.

Likely follow-ups
  • When can you delete the old code path?
