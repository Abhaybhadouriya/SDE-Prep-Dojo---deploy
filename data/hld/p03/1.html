When you hit this problem

On one database, a transaction makes several writes all-or-nothing. Across services, there is no shared transaction: the order DB, the payment provider, Kafka and the courier API cannot all join one commit. Debezium's outbox post states it plainly: Kafka cannot be enlisted in a distributed XA transaction with your database (XA is the standard protocol that lets several databases and message brokers join one two-phase commit; see rung 2), so "save the order" and "publish the event" can fail separately. This is the dual-write problem, and every multi-step process is built on top of it.

Signals in the interview question

  • Several services own the data: order, payment, inventory, shipping, wallet A and wallet B on different shards.
  • An external system you do not control: Stripe, Razorpay, a bank, a courier, an email provider.
  • Waiting: "wait for the restaurant to accept", "the video is transcoding", "the driver has 15 s to accept", "send a reminder if unpaid after 24 h".
  • "What if it fails halfway?": the interviewer asks what happens if the server crashes right after charging the card.

The failure that defines the pattern

The Hello Interview Temporal deep dive puts the core question in one line: Stripe charges the customer, your server crashes immediately afterward, and the server that takes over has no idea whether the charge happened. Run the step again and you may charge twice; skip it and you may ship for free. Airbnb wrote a whole idempotency framework, Orpheus, for exactly this, because its payments services must move money "at most once" even when clients retry.

Explain like I'm 5

Pressing the lift button five times does not call five lifts. The first press does the work; the others change nothing. A step like that is idempotent: safe to run twice, because the second run changes nothing. "Set the light to ON" is idempotent; "flip the light switch" is not.

An idempotency key is how you make a step like "charge the card" idempotent. The client picks a unique id for the attempt (for example the order id plus the step name) and sends it with the request. The server stores that key with the first result. If the same key arrives again, the server does not charge again; it returns the stored first result. Almost every fix on this page needs one.

From your world

Idempotent is writing a register with a value rather than incrementing it: replaying the write leaves the same state. An idempotency key is the TCP sequence number of a business request: the receiver sees "already have this one" and acknowledges without applying it twice.
