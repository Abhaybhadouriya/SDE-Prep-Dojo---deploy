The story

Explain like I'm 5

You are planning a birthday party. You book the hall, then order the cake, then buy balloons. If the cake shop says "sorry, we are closed that day", you do not pretend the party is fine. You go back and undo what you did: cancel the balloons and cancel the hall. You also keep a notebook of what you have done so far, so if you fall asleep in the middle, you can wake up, read the notebook and carry on from the right step, without booking the hall twice.

Each booking is a local transaction in one service. The list of bookings with an "undo" for each is a saga. Each undo is a compensating action (a new action that reverses the effect, like a refund; you cannot erase the past). The notebook is durable workflow state. Hello Interview's pattern page uses a very similar example, an e-commerce fulfilment flow: charge payment, reserve inventory, create a shipping label, wait for a warehouse worker, send a confirmation email. Every step talks to a different system, any of which can fail or time out, and your own server can crash or be redeployed in the middle.

From your world

Think of pushing one configuration change to fifty routers. You cannot hold a lock on all fifty boxes while you wait (that is 2PC, and one slow box blocks everyone). Instead you apply box by box, keep a record of where you are, and if box 31 rejects the change, you roll back boxes 1 to 30 with an explicit reverse config. The "commit confirmed" timer on Junos or IOS-XR is the same idea in miniature: an automatic compensation if confirmation never arrives.
