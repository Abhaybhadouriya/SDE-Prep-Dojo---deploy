Data model

DataShape and keyStoreWhy
Title metadatatitle_id -> names, cast, episodes, artwork, per-country rightsWide-column/KV + in-memory cache (EVCache)Read-heavy, global, fine to be seconds stale.
Asset catalogue(title_id, rendition_id) -> codec, bitrate, resolution, file path, checksumSQL or KVWritten by the encoding pipeline, read by playback and fill.
Viewing history and bookmarks(profile_id, title_id) -> position, last watchedWide-column (Cassandra)Huge write volume from heartbeats, simple key access; Netflix has written about Cassandra for viewing history.
OCA registryoca_id -> site, ISP, IP prefixes it serves, health, capacity, stored filesReplicated in-memory serviceSteering decisions in milliseconds.
Video filesMasters and every renditionObject storage (S3) as origin; copies on OCAsDurable, cheap, the fill source.
TelemetryEventsKafka -> stream processing -> data warehouseQuality dashboards, recommendations, A/B tests.

Why mostly NoSQL here: nothing in streaming needs multi-row ACID transactions. The access patterns are key lookups at high volume across regions, where availability and latency matter more than strict consistency. Billing (not in this design) is where SQL would come back. See Choosing Storage.
