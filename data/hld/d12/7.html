Where Kafka, Kubernetes and Docker fit

  • Kafka carries the telemetry firehose: playback heartbeats, quality-of-experience events, UI events, logs. Netflix's Keystone pipeline is Kafka-fronted with Flink stream processing; reported numbers grew from about 1 trillion events/day in 2016 to about 1.3 trillion/day with a 12 million events/s peak in 2017 (InfoQ coverage). Consumers update bookmarks, compute live quality dashboards per ISP and OCA, and land data in the warehouse for recommendations and A/B tests. Key heartbeats by playback_id so one session's events stay in order. Delivery is at-least-once; bookmark updates are idempotent ("set position to X at time T, if T is newer"). See Consumers & Consumer Groups and the ShopStream pipeline for the same pattern hands-on.
  • Containers run the control-plane microservices and the encoding workers. Netflix built its own container platform, Titus, on top of EC2; InfoQ (2026) reports it still launches millions of containers a week across tens of thousands of EC2 instances. In an interview you can say "Kubernetes" for the same role: Deployments plus HPA for API services, and batch Jobs for encoding.
  • OCAs are not containers: they are tuned bare-metal appliances. Containers are for flexibility; the data plane needs every last bit of the hardware.
apiVersion: batch/v1
kind: Job
metadata:
  name: encode-t81234-av1-1080p
spec:
  completionMode: Indexed     # each pod gets JOB_COMPLETION_INDEX = chunk number
  completions: 240            # 240 chunks of 30 s = a 2-hour film
  parallelism: 60             # 60 chunks encoding at once
  backoffLimitPerIndex: 3     # retry EACH chunk up to 3 times (Indexed Jobs only, GA in K8s 1.33)
  maxFailedIndexes: 5         # more than 5 dead chunks = something is wrong: fail the whole Job
  podFailurePolicy:
    rules:
    - action: FailIndex       # encoder exits 42 = poison input: do not retry that chunk
      onExitCodes: { containerName: encoder, operator: In, values: [42] }
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: encoder
        image: registry.example/encoder:2.4.1
        args: ["--title=t81234", "--codec=av1", "--height=1080", "--bitrate=3000k"]
        resources:
          requests: { cpu: "4", memory: "8Gi" }
          limits:   { memory: "8Gi" }
# Make a 2-rung HLS ladder from any local MP4 (ffmpeg 6+)
ffmpeg -i input.mp4 \
  -map 0:v -map 0:a -map 0:v -map 0:a \
  -c:v libx264 -c:a aac \
  -b:v:0 800k  -s:v:0 640x360 \
  -b:v:1 3000k -s:v:1 1280x720 \
  -f hls -hls_time 4 -hls_playlist_type vod \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0 v:1,a:1" \
  -hls_segment_filename "out_%v/seg_%03d.ts" out_%v/index.m3u8
$ ls out_0 | head -4
index.m3u8
seg_000.ts
seg_001.ts
seg_002.ts
$ cat master.m3u8
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=1020800,RESOLUTION=640x360,CODECS="avc1.64001e,mp4a.40.2"
out_0/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=3520800,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
out_1/index.m3u8

Exact BANDWIDTH and CODECS values depend on your input and ffmpeg build. Serve the folder with any static web server and open master.m3u8 in an HLS player to watch ABR switch rungs.
