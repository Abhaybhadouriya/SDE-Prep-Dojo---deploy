Trade-offs, bottlenecks and failure modes

DecisionNetflix-style choiceAlternativeWhen the alternative wins
DeliveryOwn CDN, boxes inside ISPsCommercial CDN (CloudFront, Akamai)Almost always for smaller services: no hardware, no ISP deals. Own CDN only pays at enormous, predictable volume.
Cache fillPush, off-peak, predictedPull on missUnpredictable or user-generated content (YouTube's long tail, live streams).
Streaming protocolHTTP segments + ABR (DASH/HLS-style)RTP/WebRTCReal-time, sub-second latency: video calls, cloud gaming (see Zoom).
EncodingPer-title ladders, many codecsOne fixed ladder, one codecSmall catalogues where encode compute matters more than bandwidth.
Metadata storesNoSQL + caches, multi-regionSingle SQL databaseSmall scale, one region, strong consistency needs.

Say the choice out loud (pattern: "I would pick X because A; the cost is B; if C becomes a problem I would switch to Y"):

  • "I would build our own edge cache inside ISPs because at tens of terabits per second transit cost dominates and demand is predictable; the cost is hardware, ISP deals and a steering service; if we were small or launching in a new country, I would start on CloudFront or Akamai and move only the hottest regions to our own boxes."
  • "I would push-fill caches off-peak because most views go to a predictable head of the catalogue; the cost is wasted copies of titles nobody watches in that region; if the catalogue became long-tail or live, I would switch to pull-on-miss with a mid-tier cache."
  • "I would use HTTP segments with ABR because any CDN and any device can serve them; the cost is 10-30 seconds of latency; if we added live sports with chat, I would move to low-latency HLS/DASH with short parts."
