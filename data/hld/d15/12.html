Quick quiz

What does storing the top-k at every trie node buy you?

  1. Less memory than a plain trie needs
  2. Typo tolerance for free at lookup time
  3. A lookup that only walks the prefix
Ranking is done at build time, so serving is a walk plus a read. Storing lists at every node costs more memory, not less. Typo tolerance needs extra work such as edit-distance search; a trie only matches exact prefixes.

Which event should increase a query's popularity?

  1. A submitted search or clicked suggestion
  2. Every keystroke the user types
  3. Every suggestion shown on screen
  4. Every time a page of results loads
Only what users actually chose counts. Keystrokes would turn fragments like "harr" into suggestions. Counting impressions rewards whatever is already shown, a feedback loop. Result page loads include pagination and refreshes, which inflate counts.

Why is sharding the trie by first letter a bad idea?

  1. A trie cannot be split across machines
  2. Letters differ hugely in traffic
  3. It needs exactly 26 servers, too many
  4. Prefix lookups then cross shards
Traffic is skewed: "s" gets far more than "x", so one shard melts. Tries split fine by prefix ranges. The count is not the issue; 26 is small. A prefix always starts with its first letter, so lookups stay on one shard; skew is the real problem.

How do trending queries get into suggestions within minutes?

  1. Rebuild the whole trie every minute
  2. Users vote suggestions up and down
  3. Drop browser and CDN caching entirely
  4. A stream job feeds a trending boost
A small fast layer beside the big slow one, merged at query time. Rebuilding tens of GB every minute is too expensive. Voting invites abuse and is not how search works. Dropping caches would multiply load and is not needed with short TTLs.

What is the safest way for a serving node to switch to a new trie snapshot?

  1. Load it beside the old one, then swap
  2. Overwrite the trie in place while serving
  3. Delete the old trie first, then load
Double-buffering (like RCU) means no empty results and an instant rollback. Overwriting in place lets readers see a half-written trie. Deleting first leaves a window where the node returns nothing.

Global suggestions use Cache-Control: public, max-age=300, s-maxage=600. What is s-maxage for?

  1. How long the server keeps its own copy
  2. How long a shared cache like a CDN keeps it
  3. How long the browser keeps the response
  4. How long a personal response is private
s-maxage applies only to shared caches such as CDNs; max-age is what the browser uses. Server-side caching is not controlled by response headers. Personal responses should be marked private, which is a different directive.

Why keep personalised suggestions in a separate response?

  1. Personal data cannot be sent as JSON
  2. The trie would grow too large to load
  3. So global replies stay publicly cacheable
A CDN may only hold responses that are the same for everyone; mixing personal history in would leak it or make nothing cacheable. JSON can carry anything. Personal history lives in a separate small store, not in the global trie, so trie size is not the reason.

The suggest service times out. What should the user see?

  1. An error message under the search box
  2. A spinner until the service recovers
  3. A full-page error with a retry button
  4. No suggestions; search still works
Autocomplete is a nice-to-have on top of search, so it fails silently. An error message or spinner draws attention to a minor feature and blocks typing. A full-page error would break search itself for a cosmetic failure.
