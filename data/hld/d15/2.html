Back-of-envelope estimation

These are the classic round-number assumptions used for this question (they match the well-known ByteByteGo chapter). Write them down; the method is what counts.

  1. Users and searches. 10 million daily active users, 10 searches each per day = 100 million searches per day.
  2. Keystrokes. A query averages about 20 characters. If every keystroke sent a request: 100M x 20 = 2 billion requests per day.
  3. QPS. 2,000,000,000 / 100,000 seconds (rounding 86,400 up) = about 20,000-24,000 requests per second on average. Peak at 2x: about 50,000/s.
  4. Debounce effect. If the client waits for a short pause (say 150 ms) before asking, assume only 1 in 3 keystrokes becomes a request. Now the average is about 8,000/s. Browser caching removes more (backspace and retyping hit the cache). Say "the client is the cheapest place to cut load".
  5. New data. Assume 20% of daily queries are new strings never seen before: 100M x 20% x 20 bytes = 0.4 GB of new query text per day. Logs of all searches: 100M x about 100 bytes (query, time, locale, user) = 10 GB per day. Small for a batch system.
  6. Trie size. Keep only queries searched at least a few times. Assume 100 million distinct queries survive, average 20 characters. Shared prefixes make the node count much lower than 2 billion; assume about 500 million nodes. If each node stores its children plus top-10 query IDs (10 x 8 bytes), say about 150 bytes per node: about 75 GB. That is too big to copy to every server comfortably, so either shard it or prune harder (keep the top 10-20 million queries: about 10 GB, which fits in RAM on one server and can be replicated).

What the numbers change: 24k/s of tiny reads is easy for a few in-memory servers, so the hard parts are latency (keep it in RAM, close to users) and freshness (how often to rebuild). The trie size decides between "replicate the whole trie everywhere" (simple, if it fits) and "shard by prefix" (needed when it does not).
