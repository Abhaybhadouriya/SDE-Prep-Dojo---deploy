Deep dives

1. Cutting keystroke load before it reaches you

  • Debounce (wait for a pause of about 100-300 ms) is the biggest single saving. Too long feels laggy; too short saves nothing.
  • Minimum prefix length: some products skip 1-character prefixes or serve them from a static list, because "a" has the same answer for everyone.
  • Browser cache: with Cache-Control: max-age=300, backspacing from "harr" to "har" is free. Some clients even prefetch the next likely prefix.
  • CDN cache: short global prefixes are a tiny set with huge traffic, which is perfect for edge caching. Keep personal results out of these responses.
  • Client-side filtering: when the "har" response returns 10 items and the user types "harr", the client can filter that list locally while it waits for the real answer.

From your world

Debounce is literally the term from hardware: a mechanical switch bounces for a few milliseconds, so firmware waits until the signal is stable before reporting one press. It is also interrupt coalescing: the NIC waits a little to raise one interrupt for many packets. Where it breaks: here the "bounce" is a human typing, so the timer is tuned for perceived latency (about 100-300 ms), not for electrical noise.

2. Sharding the trie, and the skew problem

If the trie fits in RAM (after pruning), the simplest design is to replicate the whole trie on every serving node and load-balance freely. When it does not fit, shard by prefix. Naive sharding by first letter fails because letters are not equally popular: far more English queries start with "s" or "c" than with "x" or "z".

  • Range sharding by measured load keeps prefixes together (a lookup touches one shard) and balances traffic. The builder recomputes boundaries with every snapshot.
  • Hashing the full query balances storage but breaks prefix lookups (the completions of "har" would be on every shard), so avoid it for the serving trie.
  • Hot prefixes ("i", "ip", "iph" on a phone launch day) are answered by the CDN and by more replicas of that shard.
  • Language and region are natural first-level shards: Hindi and English tries can live on different servers and be built separately.

3. Freshness: batch rebuild plus a trending layer

A full rebuild from 30 days of logs might take an hour and run once a day (or once a week in the textbook version). That is too slow for "earthquake in Delhi" or a cricket score. So we keep two layers.

  • Time decay in the batch layer: a search from yesterday counts more than one from last month (for example weight = count x 0.9^days_ago), so old fads fade.
  • Trending detection compares the current window with a baseline (for example the same hour last week). A query whose count jumps far above its baseline gets a boost for a few hours. This is the same windowed counting as Top-K / Heavy Hitters.
  • Swapping a snapshot safely: load the new trie into memory beside the old one, warm it, then switch one pointer. In-flight lookups finish on the old trie; the old memory is freed after a grace period. Keep the previous snapshot for instant rollback if a bad build ships.
  • Blocklist changes skip the rebuild: they are pushed to serving nodes within minutes and applied as a filter on every response.

From your world

The snapshot swap is RCU (read-copy-update): readers keep using the old structure without locks while a writer prepares a new copy, publishes it with one pointer update, and frees the old copy after a grace period, once no reader can still hold it. It is also make-before-break when a router downloads a new FIB to the line card. Where it breaks: RCU readers are CPUs in one kernel; here the "readers" are many servers, so the swap is per node and the fleet is briefly mixed-version. Responses carry a version so you can see that.

4. Ranking, filtering and personalisation

  • Base score from decayed popularity, maybe adjusted by click-through rate on suggestions (if people often pick suggestion 3 over suggestion 1, suggestion 3 should move up).
  • Context: language, country and device. "football" means different things in different countries.
  • Personal blend: fetch the user's own recent queries that match the prefix from a small per-user store (for example the last 100 searches), and merge them on top. Keep this a separate call or step so the global part stays cacheable.
  • Safety filters: a blocklist of offensive or legally removed phrases, plus rules for sensitive patterns (people's names next to crimes). Apply them in the builder and at serving time, because the builder runs rarely.
  • Spelling tolerance: a plain trie only does exact prefixes. Fuzzy matching (edit distance 1-2) is done with automata over the FST (Lucene does this), or with a separate "did you mean" step. Say it is an extension, not the core.

5. Alternatives you should be able to compare

One sorted set per prefix, score = popularity. Simple and good for small to medium catalogs (say, a product catalog), with live updates. Memory grows with (queries x average length), because each query is stored under every prefix.

redis-cli ZINCRBY ac:har 900 "harry potter"
redis-cli ZINCRBY ac:har 700 "harry styles"
redis-cli ZINCRBY ac:har 450 "harvard"
redis-cli ZRANGE ac:har 0 4 REV WITHSCORES
$ redis-cli ZRANGE ac:har 0 4 REV WITHSCORES
1) "harry potter"
2) "900"
3) "harry styles"
4) "700"
5) "harvard"
6) "450"

A completion field builds an in-memory FST per index segment with weights. Fast prefix lookups, optional fuzzy matching and contexts (category, location). Updates arrive through normal indexing. Good when you already run Elasticsearch for search (see Product Catalog Search).

PUT /suggest
{ "mappings": { "properties": {
    "suggest": { "type": "completion" } } } }

POST /suggest/_doc
{ "suggest": { "input": ["harry potter"], "weight": 900 } }

POST /suggest/_search
{ "suggest": { "s": { "prefix": "har",
    "completion": { "field": "suggest", "size": 5,
                    "fuzzy": { "fuzziness": 1 } } } } }

A purpose-built in-memory trie (or FST) per shard, built offline. Best latency and memory control at very large scale, full control of ranking and the swap. Most work to build and operate. This is the classic interview answer for "design Google's autocomplete".
