Key APIs

# Serving: one GET per (debounced) keystroke. Small, cacheable.
GET /v1/suggest?q=har&limit=8&lang=en&region=IN
-> 200
Cache-Control: public, max-age=300, s-maxage=600   # browser 5 min, CDN 10 min
{ "prefix": "har",
  "suggestions": [
    { "text": "harry potter",  "score": 0.98 },
    { "text": "harry styles",  "score": 0.91 },
    { "text": "harvard",       "score": 0.70 } ],
  "version": "trie-2026-11-23T02:00Z" }

# Personal suggestions are separate so the global response stays cacheable
GET /v1/suggest/personal?q=har            # Cache-Control: private, max-age=60

# Collection: log the search the user actually submitted (not every keystroke)
POST /v1/search { "q": "harry potter", "from_suggestion": true, "position": 1 }

Why such short cache times? We promise trends within 15 minutes, so an hour-long browser cache would break that promise. max-age is for the browser, s-maxage for shared caches like the CDN. When a phrase is added to the blocklist, waiting even 10 minutes is too long, so the builder also purges the CDN for the affected prefixes (most CDNs let you tag responses with a surrogate key such as prefix:har and purge by tag in seconds). Browsers cannot be purged, which is the reason their TTL is the shortest.

  • Normalise the prefix on the server: lowercase, trim, collapse spaces, Unicode normalisation (so "Café" and "café" match). The normalised prefix is the cache key.
  • Do not log keystrokes as searches. Only submitted queries (and clicked suggestions) count toward popularity, or half-typed junk like "harr" would become a suggestion.
  • Return a version so you can debug "why did I see this?" and do A/B tests on ranking.
  • Cancel stale requests on the client (for example with AbortController in the browser) and ignore late responses for an old prefix, or results flicker out of order.
