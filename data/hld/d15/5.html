Architecture, step by step

Whiteboard version (6 boxes). Draw this first; the stepper adds the detail.

Click Next or Play. The top half is the fast serving path; the bottom half is the slow data path that builds the trie.

  1. Type. The browser waits for a short pause (debounce), checks its own cache for this prefix, and only then sends GET /v1/suggest?q=har.
  2. Edge cache. Popular prefixes ("a", "ha", "iph") are the same for everyone in a region, so the CDN answers them without touching our servers.
  3. Route. A stateless router normalises the prefix and picks the trie shard that owns it (by prefix range or a lookup table), then a healthy replica.
  4. Lookup. The trie server walks the prefix in memory and reads the precomputed top-k. This takes microseconds.
  5. Blend and filter. Merge with a small trending list and (if logged in) personal history, drop anything on the blocklist, and return the top 8.
  6. Log. When the user submits a search, the search service publishes the query (normalised) to the Kafka topic search.queries.
  7. Count. A Flink job counts queries per 5-minute window for trending. The raw stream also lands in the data lake, where a daily Spark job computes counts with time decay.
  8. Build and swap. The trie builder filters, ranks and shards, writes a versioned snapshot to object storage, and serving nodes load it beside the old one and swap atomically. Roll back by loading the previous version.
