Say the choice out loud (pattern: "I would pick X because A; the cost is B; if C becomes a problem I would switch to Y"):

  • "I would precompute the top-k at every trie node because a keystroke must answer in a few milliseconds and the ranking barely changes within a day; the cost is a bigger trie and an offline build; if suggestions had to change per user or per second, I would rank a small candidate set on the fly and keep the precomputed list as the candidate source."
  • "I would cache global suggestions in the browser and CDN because short prefixes are the same for everyone; the cost is up to a few minutes of staleness; if blocklist removals had to be instant, I would purge the CDN by surrogate key and keep the browser TTL very short."
  • "I would replicate the whole trie on every node because it fits in RAM after pruning and needs no router; the cost is RAM on every node; if it stopped fitting, I would shard by load-balanced prefix ranges."

What breaks, and what we do

  • A trie server dies: the router sends to another replica of that shard. Nothing is lost; the trie is a read-only copy.
  • A bad snapshot ships (empty, or full of junk): validate before publishing (size within limits, known queries present, blocklist applied), roll out to a canary first, and keep the previous version loaded for instant rollback.
  • The build pipeline is down for a day: keep serving yesterday's trie. Suggestions get a little stale; nobody notices.
  • Suggest service is slow: the client times out after, say, 300 ms and shows nothing. Search still works, which is why autocomplete is always "fail silent".
  • Poisoning: bots search an offensive phrase millions of times to push it into suggestions. Count unique users (not raw searches), cap one user's influence, require a minimum number of distinct users, and keep human-reviewed blocklists.
  • Thundering herd on a new snapshot: every pod downloads tens of GB from object storage at once. Stagger the rollout and use a node-local cache or peer-to-peer distribution.

What went wrong in the real world (illustrative scenario). Search engines have publicly removed offensive or defamatory autocomplete suggestions many times, but we did not find a sourced post-mortem with internals, so this is built from the failure modes above. A nightly build runs while the blocklist service is timing out; the builder treats "no blocklist" as "empty blocklist" and ships. By morning an offensive phrase that bots pushed up is the top suggestion for a common prefix, and the CDN has cached it. How teams notice: user reports and press, not dashboards. The fixes on this page: fail the build if the blocklist cannot be loaded, validate known-bad phrases are absent before publishing, keep the previous snapshot for one-command rollback, apply the blocklist again at serving time, and purge the CDN by prefix.
