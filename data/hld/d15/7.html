Where Kafka, Kubernetes and Docker fit

Kafka

  • One topic, many readers: search.queries is read by the trending Flink job, an S3 sink (Kafka Connect) for the data lake, and maybe spell-correction and analytics, each in its own consumer group. Producers never wait for any of them.
  • Key by normalised query so all counts for one query arrive in one partition and can be summed locally (keys and partitions). A single viral query becomes a hot partition, so pre-aggregate: count in each producer or in a first Flink stage for a few seconds, then send (query, partial count).
  • Losing a few events is acceptable here (popularity is statistical), so this topic can trade durability for cost (for example acks=1), unlike a payments topic. Say this trade-off explicitly: it shows you choose settings per use case. Throughput tuning: compression (lz4), batching (linger.ms), see Operations & Tuning.
  • The same "events to Kafka, aggregate in Flink, serve from a fast store" shape is the end-to-end pipeline on this site.

Kubernetes

Trie servers are read-only and hold a big in-memory snapshot, so the important settings are memory and readiness. A pod must not receive traffic until its snapshot is loaded, or users get empty suggestions (Deployments & Rollouts).

apiVersion: apps/v1
kind: Deployment
metadata:
  name: trie-server-shard-07
spec:
  replicas: 6
  selector:
    matchLabels: { app: trie-server, shard: "07" }
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 2 }   # never drop below capacity
  template:
    metadata:
      labels: { app: trie-server, shard: "07" }
    spec:
      initContainers:
        - name: fetch-snapshot
          image: registry.example.com/snapshot-fetcher:1.2.0
          args: ["--src=s3://tries/latest/shard-07.bin", "--dst=/data/trie.bin"]
          volumeMounts: [{ name: data, mountPath: /data }]
      containers:
        - name: server
          image: registry.example.com/trie-server:3.4.1
          resources:
            requests: { cpu: "2", memory: 24Gi }
            limits:   { memory: 24Gi }      # equal: predictable, no surprise OOM kills
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }   # true only after the trie is in RAM
            periodSeconds: 5
          volumeMounts: [{ name: data, mountPath: /data }]
      volumes:
        - name: data
          emptyDir: {}

The builder is a batch job, so a CronJob (or Spark on Kubernetes) fits. New snapshots can either roll out as a new Deployment revision (simple, slow) or be hot-swapped inside running pods when a "new version" message arrives (fast, needs the double-buffer memory headroom).

Docker

Package the trie server as a small image; the snapshot is data, not code, so do not bake it into the image (it changes daily and is tens of GB). Pull it at start-up or mount it (Writing a Dockerfile).

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY server/ ./server/
USER 10001
EXPOSE 8080
CMD ["python", "-m", "server", "--trie=/data/trie.bin", "--port=8080"]
