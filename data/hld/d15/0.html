The story

Explain like I'm 5

There is a very fast librarian. You start to say a book's name: "Har..." and before you finish, she holds up three cards: "Harry Potter", "Harry Styles", "Harvard". How is she so quick? Every night after the library closes, she counts which books children asked for that day. Then she makes a little stack of the top three cards for every beginning: one stack for "H", one for "Ha", one for "Har", and so on. In the morning she does not search at all. She just grabs the right stack.

And if a new book suddenly becomes famous at lunchtime, she keeps a small "today's hot books" note on her desk and mixes it in.

The drawers of stacks are a trie (say "try"): a tree where each step down adds one letter, so every node stands for a prefix (the beginning of a word). The pre-made stacks are the top-k list stored at every node, where k is a small number like 5 or 10. The night-time counting is an offline batch pipeline that turns search logs into a new trie. The lunchtime note is a real-time trending layer.

The big idea: do the hard work when nobody is waiting, so that answering a keystroke is just a lookup. Ranking millions of queries at keystroke time would be far too slow.

From your world

You already know this structure. The Linux IPv4 routing table is an LC-trie (fib_trie), and every router does longest-prefix match on a trie of address bits. Autocomplete is the same walk on characters instead of bits. Where it breaks: a FIB lookup needs one best match; autocomplete needs the k most popular completions under a prefix, so we store a ranked list at each node, which a FIB never does.

New words, once each (you will meet them below):

  • Trie = a tree where each edge is one character, so every node stands for a prefix.
  • Shard = one slice of the trie, by prefix range (say "ha" to "hz"), served by its own group of nodes.
  • Flink = a stream processor: a long-running job that keeps running counts over time windows ("searches per query in the last 5 minutes").
  • Spark = a batch engine that reads a whole day of files at once, crunches them on many machines and writes the result.
  • Data lake = cheap object storage that holds raw files for later analysis. Parquet = a column-oriented file format used there, so a job can read just the "query" column without the rest.
  • Time decay = older counts weigh less (for example a search from 7 days ago counts half), so last month's fad fades out.
  • CDN = cache servers near users. TTL = how long a cached answer may be reused. p99 = 99 of 100 requests are faster than this.

You might confuse: a trie (prefix to completions: what can follow "har"?) with an inverted index (word to documents: which pages contain "harry"?). Autocomplete uses the first; the search results page behind it uses the second. Also suggestions (what people searched) vs results (pages that match).
