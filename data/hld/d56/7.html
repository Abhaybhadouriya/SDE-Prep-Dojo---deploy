Where Kafka, Kubernetes and Docker fit

  • Kubernetes Services are an L4 load balancer. A ClusterIP is a virtual IP; kube-proxy programs iptables (still the default mode in v1.37), nftables (GA since 1.33, recommended on newer kernels) or IPVS (deprecated since 1.35, removal planned around v1.40) so each node DNATs connections to pod IPs. Cilium can replace kube-proxy with eBPF. See Services and networking.
  • Ingress / Gateway API is the L7 tier: an Envoy- or NGINX-based controller doing host/path routing and TLS. The community ingress-nginx controller was retired in March 2026; Gateway API is the recommended path. See Ingress and Gateway API.
  • Draining in Kubernetes: a terminating pod is removed from EndpointSlices while it keeps serving; use a preStop hook and terminationGracePeriodSeconds long enough for the LB to notice.
  • Kafka does not sit behind a normal LB. Clients must reach the specific broker that leads a partition, so a bootstrap address returns broker addresses and clients connect directly. Putting an L7 LB in front of brokers breaks this. See Kafka core concepts. LB access logs are, however, a classic Kafka source for analytics.
  • Docker: run Envoy or HAProxy plus three copies of a backend with Compose to practise health checks and draining (Compose).
# Gateway API: L7 routing in Kubernetes (Gateway API v1, standard channel)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
spec:
  parentRefs:
    - name: public-gateway
  hostnames: ["shop.example.com"]
  rules:
    - matches:
        - path: { type: PathPrefix, value: /cart }
      backendRefs:
        - name: cart-svc
          port: 8080
          weight: 90
        - name: cart-svc-canary
          port: 8080
          weight: 10
