Interview: how to drive 45 minutes

  1. 0-5: clarify. L4, L7 or both? One region or global? TLS? Sticky sessions? Request rate and response size?
  2. 5-10: estimate. Bandwidth in vs out, packets/s, number of nodes per tier.
  3. 10-20: architecture. DNS/anycast, ECMP, L4 tier, L7 tier, control plane.
  4. 20-35: deep dives. Consistent hashing + conntrack, health checks and draining, algorithm choice (P2C), LB HA.
  5. 35-45: failure modes and ops. Upgrades, retry storms, DDoS, observability (per-backend latency and errors, conntrack size, drops).

60-second answer, said out loud: "Two tiers. DNS returns an anycast VIP; the router spreads packets over a few L4 nodes with ECMP. Each L4 node looks up the flow in its connection table, and on a miss uses a Maglev consistent-hash table so every L4 node picks the same L7 proxy for the same 5-tuple; it encapsulates the packet to that proxy, and the reply goes straight back (direct server return), because responses are 10x bigger than requests. L7 proxies such as Envoy terminate TLS, parse HTTP, route by path and pick a backend with power-of-two-choices least-request. A control plane pushes backend lists and runs deduplicated health checks with hysteresis, draining and slow start. L4 is packet-bound and cheap; L7 is CPU-bound and wider. Adding or losing a node moves only a slice of flows, and conntrack keeps the rest where they are."

SDE-1 stops here / SDE-2 adds. SDE-1: L4 vs L7, round robin vs least connections, health checks, no single LB box (active-passive or ECMP), TLS termination at L7, sticky sessions and why to avoid them. SDE-2 adds: the bandwidth maths that justifies DSR, Maglev tables vs ring hashing, conntrack plus consistent hashing and second-chance forwarding, P2C, draining and slow start, retry storms, and how kube-proxy and cloud LBs map onto the same ideas.

You might confuse this with an API gateway. An L7 load balancer chooses which copy of a service gets the request; an API gateway also does auth, rate limits, request shaping and API versioning. Many products do both, but say which job you mean. Also do not confuse L4 vs L7 with OSI purity: "L4" here means "never reads the payload", "L7" means "terminates the connection and reads HTTP".

Common mistakes

Common mistakes: one LB box (single point of failure); hash % N; forgetting connections must survive LB changes; health checks without hysteresis; no draining story; putting TLS on L4 nodes; ignoring that responses are much bigger than requests.

Design a load balancer for 1M requests per second.

Two tiers. Routers spread packets over an active-active L4 tier with ECMP; each L4 node uses a Maglev-style consistent-hash table plus a local connection table to pick an L7 proxy, encapsulates the packet, and the proxy replies with DSR. The L7 tier (Envoy-like) terminates TLS, routes by host/path, and picks backends with P2C least-request over pooled connections. A control plane stores config in etcd/Consul, runs deduplicated health checks and pushes versioned config. Sizing: 16 Gbps in, 160 Gbps out, ~5 L4 nodes and ~34 L7 nodes per region with headroom.

How to answer

Do the in/out bandwidth math first; it justifies DSR and the two tiers. Then walk one packet through the stepper.

Likely follow-ups
  • What happens to live connections when you add an L4 node?
  • How do you deploy new proxy code safely?
L4 vs L7 load balancing: when do you use which?

L4 looks at IPs and ports only, forwards packets (NAT or encapsulation), is very fast and works for any TCP/UDP protocol; examples are AWS NLB, IPVS, Maglev. L7 terminates the connection, reads HTTP (path, headers, cookies), can route, retry, rewrite and terminate TLS, at much higher CPU cost; examples are AWS ALB, Envoy, NGINX, HAProxy. At scale you stack them: L4 for raw distribution, L7 for application logic.

How to answer

One line each, one example each, then "in practice both".

Likely follow-ups
  • Can an L4 LB do TLS passthrough with SNI routing?
How does Maglev hashing work, and why not a hash ring?

Each backend derives a permutation of the M slots (M prime, default 65,537) from an offset and skip hash (worked by hand in deep dive 1: with M = 7, B0 with offset 3 and skip 4 prefers slots 3, 0, 4, 1, 5, 2, 6); backends take turns filling their next preferred free slot until the table is full. Lookup is one array index. Shares differ by at most one slot, and M > 100 x N keeps imbalance under ~1%. A ring with virtual nodes is less even and needs a binary search; Maglev moves slightly more keys on changes, which conntrack covers.

How to answer

Draw a tiny table before and after removing one backend.

Likely follow-ups
  • How would you support weights? (Katran's extended Maglev gives a backend more turns.)
An L4 node dies. Do its TCP connections break?

Mostly no. Routers withdraw it from ECMP and rehash its flows onto other nodes. Those nodes have no conntrack entry, but they build the same Maglev table from the same backend list, so they choose the same proxy, and the proxy still has the TCP socket. Connections break only if the backend set changed at the same moment. Stateless designs (GLB, Unimog) add a second-chance hop to the previous server to cover that too.

How to answer

Say "consistent hashing covers LB changes, conntrack covers backend changes".

Likely follow-ups
  • And if the L7 proxy dies? (Its connections are lost; clients reconnect and retry idempotent requests.)
How do you deploy a new version of a backend without dropping requests?

Mark the instance draining: the LB stops sending new requests, in-flight ones finish (ALB waits up to 300 s by default, finishing early if idle), then remove it. In Kubernetes, the pod leaves EndpointSlices on termination while a preStop sleep and grace period let in-flight work finish. New instances join through slow start so cold caches are not flooded. Use weighted routing for canaries (90/10).

How to answer

Draining + slow start + canary weights, in that order.

Likely follow-ups
  • What about WebSocket connections that last hours?
Why is "send to the least loaded server" dangerous with many LB nodes? What do you use instead?

Each LB node only sees its own counts, or a slightly stale global view, so all nodes pick the same "least loaded" server and overload it (herding). Power of two choices: sample two random healthy backends and pick the less loaded. It is nearly as good as full least-loaded and avoids synchronised decisions. Envoy uses it by default for equal weights.

How to answer

Name the herding problem, then P2C, then mention latency-aware variants (EWMA).

Likely follow-ups
  • How do you handle backends with different capacity?
A bug makes health checks fail on every backend. What should the LB do?

Fail open: if the share of healthy backends drops below a threshold, ignore health and send to all, because "everything is down" is more likely a checker or shared-dependency problem than a real total outage. ALB does this. Also cap how many hosts outlier detection can eject at once, alert loudly, and keep health checks shallow enough not to depend on shared downstreams.

How to answer

Show you distrust your own monitoring; give the threshold idea.

Likely follow-ups
  • Deep vs shallow health checks: which and why?
How do you make the load balancer itself highly available?

Small scale: an active-passive pair sharing a VIP with VRRP (keepalived), failover in seconds. Large scale: active-active, every node announces the VIP over BGP, routers ECMP across them; a dead node is withdrawn; capacity grows by adding nodes. Across regions: DNS or anycast. Maglev moved from pairs to ECMP because pairs wasted half the machines and capped a VIP at one box.

How to answer

Present both, recommend active-active with the reason.

Likely follow-ups
  • What does BGP convergence time mean for failover?
Where do you terminate TLS, and how do resumed sessions work across many proxies?

At the L7 tier (or edge PoP), not on L4 nodes, so L4 stays packet-fast and certificates live in one managed place. Share and rotate session-ticket keys across all proxies so a client can resume on any proxy. If compliance requires encryption inside, re-encrypt to backends with mTLS (a service mesh does this). L4 can do TLS passthrough when the backend must hold the key.

How to answer

Mention CPU cost of handshakes as the reason the L7 tier is the bigger tier.

Likely follow-ups
  • How does the backend learn the client's IP? (X-Forwarded-For, or PROXY protocol at L4.)
Why do Maglev and Katran use DSR and encapsulation instead of NAT?

Responses are often 10x larger than requests. With DSR the backend (which owns the VIP on loopback) answers the client directly, so the LB only carries inbound traffic and scales much further. Encapsulation (GRE, IP-in-IP, GUE) keeps the original packet intact, so the backend sees the real client address and the VIP, and routing works across L3 networks. NAT would force replies back through the same LB and rewrite addresses.

How to answer

Use your estimate numbers (16 vs 160 Gbps).

Likely follow-ups
  • What about MTU? (Encapsulation adds bytes; Unimog turns 1,500 into 1,536 and uses jumbo frames internally.)
After moving behind an AWS ALB, a Node.js service sees a small, steady rate of 502s with no errors in its own logs. What is happening?

Almost always the keep-alive race. The ALB reuses idle backend connections for up to its idle timeout (60 s by default), but Node closes idle keep-alive connections after 5 s by default. Sometimes the ALB sends a request on a connection at the same moment Node closes it; the request meets a closed socket and the ALB returns 502. The app never saw the request, so its logs are clean. Fix: make the app's keep-alive longer than the ALB's idle timeout (keepAliveTimeout = 65000 and headersTimeout a bit higher), which is AWS's own guidance. Confirm with HTTPCode_ELB_502_Count rising while target 5xx stays flat.

How to answer

Name both timers, say which side closes and which side reuses, then give the rule (backend timeout > LB timeout) and the metric that proves it. Contrast with 504 (target too slow).

Likely follow-ups
  • How do you prepare an ALB for a launch-day spike? (LCU reservation sized from PeakLCUs or a load test; historically a pre-warm request.)
  • Why do idle connections through an NLB get reset after about 6 minutes? (350 s flow timeout; use TCP keepalives below it.)

Scenario: one backend is at 95% CPU, the rest at 40%

The LB uses source-IP hashing. A big customer sends all traffic through one corporate NAT address.

Weak answer: "Add more servers."

Strong answer: source-IP hashing puts everything behind one NAT address on one backend. Adding servers does not move it. If affinity is not needed, switch to P2C least-request. If it is (cache locality), hash on a finer key (user ID, session cookie) and use bounded-load consistent hashing so no backend takes more than, say, 1.25x average. Verify with per-backend RPS and CPU.

Likely follow-ups
  • How would you detect this automatically?

Scenario: every LB fleet upgrade drops a few thousand connections

Rolling restarts of L4 nodes coincide with autoscaling of backends.

Weak answer: "Upgrade at night."

Strong answer: this is the double-change case: a flow moves to a new L4 node (no conntrack) while the backend table also changed. Freeze backend-set changes during LB rollouts, drain each L4 node (withdraw BGP, wait) before restart, or move to a stateless design with a second-chance hop to the previous owner like GLB/Unimog.

  • How long must you wait before restarting a drained node?
