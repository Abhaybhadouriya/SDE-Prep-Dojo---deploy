Data model and state

Two kinds of state with very different needs:

StateWhereSize / change rateConsistency
Config: VIPs, pools, backends, weights, routes, certsStrongly consistent store (etcd / Consul / a SQL DB) behind the control plane; pushed to every nodeKBs-MBs; changes per deployVersioned; every node must converge to the same version
Health stateHealth checker -> pushed with config, or local per nodeChanges every few secondsEventually consistent is fine for a few seconds
Maglev lookup table per VIPComputed locally on each L4 node from the backend list65,537 entries (Maglev's default prime size)Deterministic: same input gives same table on every node, no sync needed
Connection table (5-tuple -> backend)RAM on each L4 node, LRUMillions of entries, churns constantlyLocal only; never replicated
TLS session tickets / keysShared key, rotated, on all L7 nodesSmallNeeded so a resumed session works on any proxy

Choice of store: config needs strong consistency and watches (etcd or Consul; Cloudflare's Unimog uses Consul for forwarding tables, health and leader election of its control loop). There is no hot database on the packet path at all: the data plane decides in memory.
