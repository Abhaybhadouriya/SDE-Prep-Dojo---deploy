Deep dives

1. Maglev hashing: even spread, small disruption

Plain hash % N reshuffles almost every flow when N changes. A hash ring with virtual nodes fixes that but can be uneven and slow to look up. Maglev builds a lookup table of prime size M (65,537 by default). Each backend gets its own permutation of table slots, derived from two hashes of its name (an offset and a skip). The backends take turns claiming their next preferred empty slot until the table is full. Result: every backend owns either floor(M/N) or ceil(M/N) slots, so shares differ by at most one entry, and Google picks M larger than 100 x N to keep hash-space differences under about 1%.

Here is the paper's own tiny example, worked by hand, with M = 7 and three backends. Click Next to build the table, then remove B1.

  1. Preferences. Two hashes of each backend's name give an offset and a skip. Because M = 7 is prime, stepping by any skip from 1 to 6 visits every slot once, so each backend gets a full preference list (a permutation).
  2. Take turns. B0, B1, B2, B0, B1, ... each claims its next preferred slot that is still empty. Every backend ends with floor(7/3) or ceil(7/3) slots: B0 has 3, B1 and B2 have 2.
  3. The table. Lookup is table[hash(5-tuple) mod 7]: one array read, the same on every L4 node, because every node runs the same algorithm on the same backend list.
  4. Remove B1 and rebuild. B0 now takes 3, 0, 1, 2 and B2 takes 4, 5, 6. B1's two slots moved, and one other slot moved too. With M = 65,537 the extra movement is a tiny fraction, and connection tracking keeps existing flows where they were.

Maglev deliberately accepts slightly more disruption than ring hashing in exchange for evenness and speed. Envoy's docs quantify the trade: its Maglev builds tables about 10x faster and picks hosts about 5x faster than its ring hash (at a 256K ring), but roughly twice as many keys move when hosts are removed. Meta's Katran uses an extended Maglev hash that also supports unequal weights, handy when old and new server generations share a pool.

2. Connection tracking + consistent hashing: belt and braces

Two independent events can move a flow: the LB set changes (ECMP sends the flow to a different L4 node) or the backend set changes (the table changes). Each mechanism covers one:

  • Connection table (per node, LRU): if this node saw the flow before and the backend is still healthy, reuse its choice even if the table changed. Protects against backend-set changes.
  • Consistent hashing (same table everywhere): if a new node receives a mid-stream flow, it computes the same answer as the old node did. Protects against LB-set changes.
  • Both at once (a node dies and a backend changes) can break a few connections. Maglev's paper calls this rare; rolling upgrades of the LB tier, which can last over an hour, are when it matters most.
  • The table is finite and a SYN flood can fill it. Katran keeps a size-limited LRU and even has a "compute only" switch to skip it under memory pressure.

GitHub and Cloudflare went further and removed per-connection state from the L4 tier entirely. Each table row holds two servers. The receiving server checks whether it has a socket for the packet; if not, it forwards it to the second server named in the encapsulation header. Draining becomes "swap primary and secondary for that server and wait for the longest connection you care about". Cloudflare runs this on every server (no separate LB tier) using XDP, for under 1% CPU overhead.

3. Health checks, draining and slow start

  • Active checks: TCP connect (cheap, shallow) or HTTP GET /healthz (checks the app). Mark down after 2-3 failures, up after 2-3 successes, to avoid flapping.
  • Passive checks / outlier detection: watch real traffic; eject a backend with a high 5xx or connect-error rate. AWS ALB's Automatic Target Weights compares each target's error rate with its peers and shifts traffic every five seconds.
  • Fail open: if too many backends look unhealthy at once, the checker is probably wrong (or a shared dependency is down). AWS ALB sends to all targets when not enough are healthy. Never let a bad health check take down 100% of a service.
  • Draining: stop new connections, let in-flight requests finish, then remove. ALB waits 300 s by default (configurable). In GLB, a false-positive health check only swaps primary and secondary, so it never drops connections.
  • Slow start: a freshly started backend with cold caches gets a linearly increasing share of traffic for a configured period instead of its full share at once.

Why P2C? If 30 proxies each send to "the least loaded backend", they all pick the same one at the same moment and overload it. Random choice between two spreads that out while still avoiding bad servers. It is a lovely, short point to make in an interview.

5. High availability of the LB itself

  • Active-passive pair (VRRP / keepalived): one VIP owner, heartbeats about every second, failover in 1-3 s. Simple, but half the hardware idles and a VIP cannot exceed one box. Maglev started this way and moved away.
  • Active-active with ECMP: all nodes announce the VIP; routers spread flows; capacity scales by adding nodes; a dead node is withdrawn by BGP. Google says the move to ECMP gave "a great deal of capacity, efficiency, and operational simplicity".
  • Across regions: DNS-based global load balancing (latency or geo policies) or anycast so BGP chooses the nearest PoP. See Networking for HLD for DNS and anycast.
  • TLS keys: share session-ticket keys across proxies so resumption works whichever proxy a client lands on; terminate TLS at the edge, re-encrypt (mTLS) to backends if required.

From your world

Kernel-bypass forwarding (DPDK in Maglev and GLB) and XDP (Katran, Unimog) are the data-plane tricks you know from fast-path line cards: poll-mode drivers, per-core RX queues, no locks on the hot path, packets never copied to user space. Maglev measured kernel-stack mode at under 30% of kernel-bypass throughput. RSS needs entropy in the outer header, which is why Katran varies the outer source IP per flow and GLB sets the GUE UDP source port from a flow hash.

6. Managed LBs in practice: what bites you on AWS ALB and NLB

Most teams never build Maglev; they rent one. AWS's Application Load Balancer (ALB, L7) and Network Load Balancer (NLB, L4) hide the data plane, but three things still leak through and cause real outages: how they scale, how they time out idle connections, and how many connections they can open.

How they scale, and why launch day can hurt

You do not pick an ALB size. AWS adds and resizes load balancer nodes as traffic grows, and bills in LCUs (load balancer capacity units). One ALB LCU per hour covers whichever of these four is highest:

25new connections / s
3,000active connections / min
1 GBprocessed per hour (EC2 / IP targets)
1,000rule evaluations / s

For an NLB the unit is the NLCU, and its TCP numbers are much bigger: 800 new flows per second, 100,000 active flows and 1 GB per hour. That difference is the L4 vs L7 cost difference in numbers.

  • Plan the spike. For a known event, set an LCU reservation: a minimum capacity (at least 100 LCU) the ALB or NLB will not scale below, while it still scales above it. Size it from the CloudWatch metric PeakLCUs of a past event or a load test. Before this feature existed, the answer was a support ticket asking AWS to "pre-warm" the load balancer; you will still hear that word in interviews.
  • Load test with a ramp, not a cliff. A test that jumps from 0 to 50,000 requests per second in one second mostly measures the LB's scale-up, not your service.
  • Leave room in the subnets. AWS asks for at least a /27 and 8 free IP addresses per ALB subnet so new nodes can be added; an ALB that cannot get IPs keeps serving on old nodes and can return 5xx while stuck.
  • Do not pin IPs. ALB node IPs change as it scales, so clients must re-resolve DNS. If a partner needs a fixed IP for a firewall rule, put an NLB (one static or Elastic IP per AZ) in front.

Idle timeout vs keep-alive: the classic 502

An ALB keeps a pool of connections to your targets and reuses them. It closes a connection that has been idle longer than its idle timeout (60 s by default, 1-4000 s). Your server has its own keep-alive timeout, and many defaults are short: Node.js's server.keepAliveTimeout is 5 seconds, Gunicorn's keepalive is 2 seconds. If the server gives up first, there is a race: the server sends FIN just as the ALB sends the next request down that same connection. The request hits a closed socket, gets an RST, and the client sees a 502 Bad Gateway. AWS's own guidance is to set the application's idle timeout larger than the load balancer's.

  1. The ALB sends a request on a pooled connection and gets the response.
  2. The connection goes back to the pool and sits idle, ready for reuse.
  3. After 5 seconds, Node's default keep-alive timeout closes it. If the ALB picks that connection at the same instant, the request meets a closed socket and the client sees a 502. Rare per request, steady at scale.
  4. Make the side that reuses connections (the ALB) also be the side that closes them: app keep-alive greater than the LB idle timeout.
// Node.js (Express or plain http): keep backend connections open longer than the ALB's 60 s
const server = app.listen(8080);
server.keepAliveTimeout = 65_000;   // must be > ALB idle timeout
server.headersTimeout   = 66_000;   // must be > keepAliveTimeout
# nginx as the target: keepalive_timeout 75s;   (the default, already above 60 s)
# Check and change the ALB side
aws elbv2 describe-load-balancer-attributes --load-balancer-arn "$ALB_ARN" \
  --query "Attributes[?Key=='idle_timeout.timeout_seconds']"
aws elbv2 modify-load-balancer-attributes --load-balancer-arn "$ALB_ARN" \
  --attributes Key=idle_timeout.timeout_seconds,Value=60
[
    {
        "Key": "idle_timeout.timeout_seconds",
        "Value": "60"
    }
]

How to tell which problem you have: in ALB metrics, HTTPCode_ELB_502_Count rising while HTTPCode_Target_5XX_Count stays flat means the LB could not get a good response (often this race, or a crashed target); HTTPCode_ELB_504_Count means the target did not answer before the idle timeout (a slow request, not a closed connection).

Long-lived connections and connection limits

  • WebSockets and long polls are idle most of the time. Send an application ping (a WebSocket ping frame every 20-30 s) so the ALB idle timer never fires. Note that ALBs do not count HTTP/2 PING frames as activity.
  • NLB tracks TCP flows and forgets one after 350 s of silence by default (configurable 60-6000 s); a packet after that gets a TCP RST. TCP keepalives reset the timer. UDP flows are forgotten after 120 s.
  • Source ports run out. With client IP preservation off, an NLB can make about 55,000 connections per minute to each unique target (IP and port) from each of its IPs. Beyond that, AWS reports port allocation errors; the fix is more targets (or more NLB secondary IPs).
  • Drain before you deploy. The deregistration delay (300 s by default) lets in-flight requests finish; set it to just above your longest normal request, or every deploy waits five minutes.

From your world

This is conntrack and NAT timeouts, rented. The NLB's 350 s flow timeout is exactly a stateful firewall's nf_conntrack_tcp_timeout_established: when the entry ages out, the next packet is unknown and gets an RST. Linux's default net.ipv4.tcp_keepalive_time is 7,200 s, far longer than 350 s, so default kernel keepalives will not save an idle database connection through an NLB (or a NAT gateway); lower it (or set TCP_KEEPIDLE per socket) below the middlebox timeout. The 502 race is the same lesson in reverse: two ends with independent idle timers, and the one that closes is not the one that reuses.

Where this breaks: an ALB is not a middlebox that forwards your packets; it terminates TCP and opens its own connections to the targets. Tuning keepalive on the client side does nothing for the ALB-to-target pool; that timer lives in your server's HTTP settings.
