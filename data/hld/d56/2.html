Back-of-envelope estimation

Work out how many boxes each tier needs. Assumptions first, then math. The method is from Back-of-Envelope Estimation.

  1. Traffic. Peak 1M requests/s in one region. Average request 2 KB in, response 20 KB out.
  2. Bandwidth. In: 1M x 2 KB = 2 GB/s = 16 Gbps. Out: 1M x 20 KB = 20 GB/s = 160 Gbps. Responses are 10x bigger than requests, which is why direct server return (DSR) matters: with DSR the L4 tier only carries the 16 Gbps inbound.
  3. L4 packet rate. Inbound packets average maybe 500 bytes (handshakes, ACKs, small requests): 2 GB/s / 500 B = ~4M packets/s. Maglev's paper: a 10 Gbps link is 813K pps at 1,500-byte packets, and Maglev keeps line rate even with small packets. So budget ~10 Gbps and a few Mpps per L4 box: 16 Gbps / 10 = 2 boxes. Add N+2 for failures and maintenance, per zone: ~4-5 L4 nodes.
  4. L7 proxies. Assume one proxy node does 50k requests/s with TLS (measure this in real life; TLS handshakes dominate CPU). 1M / 50k = 20 nodes. Run at 60% utilisation for headroom: 20 / 0.6 = ~34 L7 nodes, spread over 3 zones.
  5. L7 egress. 160 Gbps / 34 nodes = ~4.7 Gbps per node. Fits a 10 or 25 Gbps NIC.
  6. Connection table. With keep-alive, say 5M concurrent client connections. One entry (5-tuple + chosen backend + timestamp) ~ 64-100 bytes: 5M x 100 B = 500 MB spread across L4 nodes. Easily fits RAM; it is a cache, so loss is survivable (deep dive 2).
  7. Health checks. 34 proxies each check 2,000 backends every 5 s = 13,600 checks/s against the fleet, or ~7 checks/s per backend: wasteful. Deduplicate: have a central health service or let each proxy check a subset. Maglev deduplicates health checks by backend IP.

The punchline to say out loud: "L4 is packet-bound and cheap; L7 is CPU-bound by TLS and HTTP parsing and needs 5-10x more machines." Here that is about 5 L4 nodes against about 34 L7 proxies. That ratio is the reason for a two-tier design: a few fast packet movers in front, a wider pool of HTTP-aware proxies behind.
