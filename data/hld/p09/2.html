The solution ladder: naive to best

Rung 1: count at query time

Store every like or click as a row, and compute SELECT COUNT(*) FROM clicks WHERE ad_id=? AND ts BETWEEN ... whenever someone asks. It is exact and always fresh, and fine for a small app.

When it breaks: the work happens on every read and grows with the data. Hello Interview's ad-click breakdown dismisses this approach at 10,000 clicks a second with a sub-second query target: scanning millions of rows per dashboard refresh cannot meet it.

Rung 2: one counter row, incremented on each event

Keep likes(post_id, count) and run UPDATE likes SET count = count + 1 WHERE post_id = ?. Reads are now O(1).

When it breaks: a viral post sends thousands of increments a second to one row. Each update takes the row lock, so they queue up one after another; it is a hot key. The systemdesign.one counter article makes the same point: a single locked row gives strong consistency but falls over under very high concurrent writes.

Rung 3: shard the counter, batch the writes

Three tools, usually combined:

  1. Sharded counters. Split one logical counter into N rows or keys (post:42:s0 ... s99). Each increment hits a random shard, so N writes can proceed in parallel. A read sums all N (a small scatter-gather) or reads a total that a background job refreshes. Use many shards only for hot keys; a post with 3 likes does not need 100.
  2. Batching (write-behind). Each app server keeps a local in-memory map post_id -> delta and flushes it every second or two as one count = count + delta per key. One million likes on a viral post become a few hundred database writes. The cost: the number lags by the flush interval, and a crash loses the unflushed deltas, unless the deltas come from a durable log you can replay.
  3. An in-memory counter store. Redis INCRBY is atomic and very fast. The systemdesign.one article warns that a plain INCR is not idempotent (idempotent = safe to run twice: the second run changes nothing, like setting a register to a value rather than incrementing it). If the reply is lost and you retry, you may count twice. When accuracy matters, record the event ID too (a set of who liked, or a Lua script that checks and increments together).

From your world

The Linux kernel solved this exact problem with per-CPU counters (percpu_counter, and per-CPU network statistics). Each CPU increments its own copy with no shared cache line and no lock; a reader sums all CPUs' copies. A sharded counter is a per-CPU counter spread across machines, and write-behind batching is the per-CPU "batch" threshold before folding into the global count. It is also why ip -s link reads cheap per-queue counters and adds them up, instead of every packet taking a global lock.

Rung 4: stream aggregation with windows

For "clicks per ad per minute" at 10,000 events a second, the standard answer is a stream pipeline: events go into Kafka (keyed by ad_id so one ad's events land in one partition), a stream processor such as Flink keeps a running count per (ad, minute) in memory, and when the minute is over it writes one row per ad to an OLAP store (OLAP = online analytical processing: a database built for fast group-by and sum queries over huge tables, such as Druid, Pinot or ClickHouse; the opposite of an OLTP database that serves many small row reads and writes). Click through it.

  1. Capture. The click service records the event with a unique ID (e.g. a signed impression ID) and an event time (when the click happened, not when we saw it).
  2. Partition. Kafka, keyed by ad_id: all events for one ad go to one partition, so one Flink task owns that ad's counter. Kafka keeps the events for days, so we can replay.
  3. Window. Flink adds each event to the counter for its (ad, minute) window. A watermark ("I have probably seen everything before 12:02") tells it when the 12:01 window can close.
  4. Emit. One row per ad per minute is written to the OLAP store, instead of 10,000 rows a second.
  5. Query. Dashboards read pre-aggregated minute rows; daily or weekly rollups are built from them for long ranges.
  6. Reconcile. All raw events also land in object storage. A nightly batch job recounts from raw and corrects the OLAP rows. This is the Lambda idea: a fast path plus a correct path.

Windows: tumbling, sliding, session

  • Tumbling - fixed size, no overlap; each event in exactly one window. Billing per minute, metrics per 10 s.
  • Sliding (hopping) - fixed size, starts every slide interval; overlaps when slide < size. "Requests in the last 5 minutes, updated every 30 s". Cheap trick: keep 1-minute tumbling counts and add the last 5.
  • Session - per key, closes after a gap of inactivity. "Pages viewed per visit".

Event time vs processing time. A phone that was offline sends a 12:00 click at 12:07. If you bucket by when you received it (processing time), the 12:00 count is wrong and replays give different answers. Bucket by event time, and use a watermark to decide when a window is "done enough". Flink's docs say the default allowed lateness is 0: elements behind the watermark are dropped, unless you allow lateness (the window state is kept a while longer and re-fires) or send late elements to a side output to handle separately. Always say what happens to late data.

Keep state small. Flink's docs separate incremental aggregation (ReduceFunction / AggregateFunction, which keep only a running result) from ProcessWindowFunction, which buffers every element until the window fires. For counts and sums, always aggregate incrementally.

From your world

Windowed counts are what you already do with interface counters: SNMP or sar samples a monotonic counter every 60 s and reports the delta as a rate - a tumbling window. A watermark is like a reassembly timeout: you wait a bounded time for out-of-order fragments, then you give up and move on. Late data is the fragment that arrives after the reassembly buffer was freed.

Rung 5: approximate when "almost exact" is enough

Two questions are expensive to answer exactly: "how many distinct?" (you must remember everything you have seen) and "how often did each of a billion keys appear?" (one counter per key). Sketches answer them in fixed, tiny memory with a known error.

HyperLogLog: distinct counts in 12 KB

HyperLogLog (HLL) hashes each item and remembers, in a small set of registers, the longest run of leading zeros seen; long runs are rare, so they reveal roughly how many distinct items passed by. You never store the items. Redis's docs give the numbers: up to 12 KB per key (much less when small), a standard error of 0.81%, cardinalities up to 2^64, and PFADD / PFCOUNT in constant time. The killer feature is merging: PFMERGE gives the HLL of the union. Keep one HLL per page per day, then merge 30 of them for monthly uniques without touching raw data.

> PFADD visitors:2026-11-23 user:17 user:42 user:17
(integer) 1
> PFCOUNT visitors:2026-11-23
(integer) 2
> PFMERGE visitors:2026-11 visitors:2026-11-22 visitors:2026-11-23
OK

Facebook's engineering blog on HLL in Presto shows the payoff at scale: a distinct count that would take days and terabytes of memory with plain SQL ran in about 12 hours with under 1 MB, with speedups of 7x to 1,000x depending on the query. Presto's APPROX_DISTINCT has about 2.3% standard error, and sketches (APPROX_SET) are stored per day and merged for any date range. Note what HLL cannot do: you cannot remove an item, and you cannot list who the uniques were.

Count-min sketch: frequencies for a billion keys

A count-min sketch (CMS) is a small 2-D array of counters, d rows by w columns, with one hash function per row. Every key shares the same array, so collisions inflate counts; taking the minimum across rows picks the least-polluted counter. Our research notes record the standard sizing: w = ceil(e / epsilon), d = ceil(ln(1 / delta)), with error at most epsilon x total count, with probability 1 - delta; for epsilon 0.001 and delta 0.01 that is about 2,719 x 5 = 13.6k counters, around 54 KB. Redis's CMS docs stress the practical catch: counts below error x total count are noise and should be ignored, so a CMS is great for heavy hitters and poor for the long tail. That is exactly what top-K needs: keep a CMS for counts plus a small min-heap of the current top K candidates.

From your world

Switch ASICs and NetFlow/sFlow probes have the same constraint: line-rate updates, tiny SRAM, millions of flows. Hashed flow counters that accept collisions and only trust the "elephant flows" are a count-min sketch in silicon. HLL is how some telemetry systems estimate distinct source IPs during a DDoS without storing every address.

Rung 6: ranking - sorted sets and top-K merging

For an exact ranking of up to tens of millions of members, a Redis sorted set is the standard tool (our research notes for the leaderboard design): ZINCRBY lb:game 50 user42 to add points and ZREVRANK lb:game user42 for "my rank" are O(log N); fetching the top 10 with ZRANGE lb:game 0 9 REV WITHSCORES (ZREVRANGE before Redis 6.2, now deprecated) is O(log N + M) for M returned members. That M matters: paging through ranks 0-9999 returns 10,000 members. It is a skip list plus a hash table. Treat it as a cache of truth: write scores to a durable log or database first so you can rebuild it.

For top-K over a stream too big for one machine: each partition keeps a local top-K (exact counts for its keys, or a CMS + heap), and a merger combines the partition lists into a global top-K every few seconds. Because Kafka keys by item, each item lives in one partition, so local counts are complete and the merge is a simple pick of the largest K. For trending, rank by velocity versus a baseline, not by raw count, or "good morning" trends every day.

Rung 7: count each event exactly once

Pipelines retry. Producers resend on timeouts, consumers reprocess after a crash, users double-click. If counting is not idempotent, every retry inflates the number - which in ad billing means charging advertisers for clicks that never happened. Layers of defence:

  1. Give every event an ID at the source. Hello Interview's ad-click design has the ad server issue a unique impression ID, signed with an HMAC so clients cannot forge or replay it. The click service checks a Redis cache of seen IDs before writing to the stream; about 100M IDs x 16 bytes is only about 1.6 GB a day.
  2. Dedupe in the stream processor. Uber's ad-event pipeline drops duplicate events using Flink keyed state before aggregating.
  3. Make the sink idempotent. Upsert by (ad_id, minute) or by a result UUID instead of "add". Uber gives each aggregate record a UUID used to dedupe in Hive and to upsert in Pinot.
  4. Transactions end to end where it pays. Uber's Flink jobs write to Kafka transactionally; outputs become visible only when a checkpoint completes (two-phase commit), and consumers use read_committed. In plain words: Flink's transactional sink runs a two-phase commit between its checkpoint and Kafka. Phase 1 (prepare): while a checkpoint is taken, the sink flushes its writes into an open Kafka transaction. Phase 2 (commit): once every operator has finished the checkpoint, the sink commits that transaction. A read_committed consumer only sees records of committed transactions, so a crash before the commit leaves nothing visible to count twice. The same prepare-then-commit idea is the 2PC rung of Multi-Step Processes. They checkpoint every 2 minutes, which sets the latency floor. See Delivery Semantics & Exactly-Once.
  5. Reconcile. Recount from raw events in batch and correct the serving store.
