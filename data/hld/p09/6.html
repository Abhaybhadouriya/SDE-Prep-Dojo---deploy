How Kafka, Kubernetes and Docker help

Kafka

  • The log you can recount from. Key events by the thing you count (ad_id, post_id) so each key's events are ordered in one partition and owned by one consumer. Retention of days (Uber's ad pipeline keeps 3 days in our research notes; Kreps' Kappa example uses 30) makes replay possible.
  • Kafka Streams / Flink state. Windowed counts are kept in local state stores backed by changelog topics, so a restarted task rebuilds its counters. See Kafka Connect, Streams & Flink.
  • Exactly-once. Idempotent producers plus transactions and read_committed consumers let a stream job read, count and write atomically; the sink must still be idempotent for anything outside Kafka.
  • Consumer lag = staleness. Lag tells you how far behind real time the counts are. Alert on it.

Kubernetes

  • Run Flink with the Flink Kubernetes Operator: JobManager and TaskManagers as pods, checkpoints in object storage, savepoints for upgrades (the Kappa "v2 job" is a new deployment from a savepoint or from offset 0).
  • Redis (sorted sets, HLL, counters) as a managed service or a StatefulSet with persistent volumes; remember it is rebuildable from the log.
  • OLAP stores like ClickHouse or Pinot have operators too; scale ingestion separately from query.

Docker

For practice, one docker compose file with Kafka, a Flink job (or a small Python consumer), Redis and ClickHouse reproduces the whole ad-click pipeline on a laptop. The end-to-end ShopStream pipeline on this site counts orders per minute the same way.
