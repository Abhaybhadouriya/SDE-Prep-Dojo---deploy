Quick quiz

A viral post's like counter row is causing lock contention. Best first fix?

  1. Add a read replica
  2. Split it into N sharded counters (or batch increments) and sum on read
  3. Use a bigger database server
  4. Count with SELECT COUNT(*) instead
Sharding or batching spreads or merges the writes; replicas only help reads.

What does Redis HyperLogLog give you?

  1. Exact distinct counts in unlimited memory
  2. Frequencies of each key
  3. Approximate distinct counts in at most 12 KB with about 0.81% standard error
  4. A sorted ranking
HLL estimates cardinality in fixed memory and can be merged with PFMERGE.

A count-min sketch's error is always...

  1. An overestimate (never under the true count)
  2. An underestimate
  3. Either, randomly
  4. Zero
Collisions only add to counters, and taking the minimum picks the least-inflated one.

Billing counts clicks per minute. Which time should define the window?

  1. Processing time at the consumer
  2. Time the dashboard was opened
  3. Kafka broker time
  4. Event time of the click, with watermarks for lateness
Event time gives the same answer on replay and handles out-of-order events correctly.

Which window type fits "requests in the last 5 minutes, refreshed every 30 seconds"?

  1. Tumbling
  2. Sliding
  3. Session
  4. Global
Sliding windows overlap: size 5 min, slide 30 s.

A consumer restarts and replays 10,000 events into an INCRBY sink. What prevents inflated counts?

  1. Nothing; this is unavoidable
  2. A bigger Redis
  3. Event IDs with dedupe, and idempotent upserts keyed by (entity, window)
  4. Processing-time windows
At-least-once delivery needs idempotent effects to give exactly-once results.

Main criticism of the Lambda architecture?

  1. The same logic must be built and kept in sync in two systems
  2. It cannot be exact
  3. It cannot use Kafka
  4. It has no batch layer
Kreps' point: two codebases, double the operational pain. Kappa replays one stream job instead.

One ad gets 40% of all clicks and its partition is overloaded. Why doesn't adding partitions help?

  1. Kafka has a partition limit of 10
  2. Flink cannot read new partitions
  3. Partitions slow down reads
  4. One key always hashes to one partition; you must salt or pre-aggregate the hot key
Key salting spreads one key across many partitions; sums are combined afterwards.
