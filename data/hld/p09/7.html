Interview: phrases, traps and questions

Phrases that score

  • "How exact and how fresh? That picks between counters, sketches, and stream + batch."
  • "Hot counters get sharded or batched; reads sum the shards or read a cached total."
  • "Window by event time with watermarks; late events go to a side output or a correction path."
  • "Every event has an ID; dedupe in the stream and upsert in the sink, so retries do not inflate counts."
  • "HyperLogLog for uniques - 12 KB, under 1% error, mergeable across days."
  • "Fast path for the dashboard, batch reconciliation for billing."

Traps

  • COUNT(*) over raw rows on every page view.
  • Processing-time windows for billing (replays and late phones change history).
  • Saying "exactly-once" without dedupe IDs and idempotent sinks.
  • Using a CMS for the long tail, or HLL when you must remove items.
  • Ignoring the hot key (one viral post or ad).
  • Adding a user_id label to a metric: cardinality explosion.
Design the like counter for a post that may get 100,000 likes a minute.

Store the like itself (user_id, post_id) as the source of truth with a unique constraint, so a double-like is rejected - this is the dedupe. For the displayed number, do not update one row per like. Either shard the counter (N keys per hot post, random shard per increment, sum on read and cache the sum for a second) or batch: app servers or a stream consumer aggregate deltas per post for 1-2 s and apply one INCRBY. Reads hit a cache; the count may be a second or two stale, which is fine for likes. Rebuild from the likes table if counters drift.

How to answer

Separate the truth (who liked) from the displayed count. Then fix the hot key. Then state staleness.

Likely follow-ups
  • Unlikes? (Decrement; or a PN-counter if multi-region.)
  • How many shards? (Only for hot posts; scale with write rate.)
How would you count daily active users across 1 billion users cheaply?

A HyperLogLog per day (and per country, platform... as needed). Each login does PFADD dau:2026-11-23 user_id. Redis HLL uses at most 12 KB per key with 0.81% standard error. Weekly and monthly actives are PFMERGE of the daily sketches - no raw scan. If finance needs the exact figure, compute COUNT(DISTINCT) in the warehouse nightly. Facebook stores HLL sketches per day in Presto/Hive and merges them for any date range.

How to answer

Name HLL, give memory and error, then the merge trick for longer ranges, then the exact batch fallback.

Likely follow-ups
  • How does HLL work intuitively? (Leading zeros of hashes.)
  • Can you remove a user? (No.)
Clicks per ad per minute for billing: walk me through the pipeline and how you avoid double counting.

Click service validates a signed impression ID, checks a seen-ID cache, writes the event (with event time) to Kafka keyed by ad_id, and redirects the user. Flink dedupes by impression ID in keyed state, counts in 1-minute tumbling event-time windows with a watermark, and upserts (ad_id, minute) rows into an OLAP store. Raw events go to S3; a nightly batch recomputes and corrects. Hot ads: salt the key and re-sum. Exactly-once inside Kafka via transactions (Uber checkpoints every 2 minutes with two-phase commit); idempotent upserts outside.

How to answer

Follow the event left to right; at each hop say how a duplicate is stopped.

Likely follow-ups
  • A click arrives 10 minutes late - what happens?
  • How do you query a 90-day range quickly? (Daily rollups.)
Tumbling vs sliding vs session windows - when do you use each?

Tumbling: fixed, non-overlapping buckets, each event counted once - billing per minute, metrics per 10 s. Sliding: fixed size that advances by a smaller step, so windows overlap - "last 5 minutes, updated every 30 s", rate limiting, trending; implement cheaply as a sum of small tumbling buckets. Session: per key, ends after a gap of inactivity - visits, user sessions.

How to answer

One line and one use case each; mention the bucket trick for sliding.

Likely follow-ups
  • How does a sliding-window rate limiter differ? (See Rate Limiter.)
What is a watermark and what do you do with late events?

A watermark is the stream processor's estimate that no more events older than time T will arrive; when it passes a window's end, the window fires. Events behind the watermark are late. In Flink the default allowed lateness is 0, so they are dropped. Options: allow lateness (keep window state longer and emit an updated result), send late events to a side output and apply them as corrections, or rely on batch reconciliation. Choose the watermark delay as a trade-off: longer delay = more complete but slower results.

How to answer

Define, then the three options, then the latency/completeness trade-off.

Likely follow-ups
  • Event time vs processing time?
  • What if one partition is idle and holds the watermark back?
Find the top 100 products by views in the last hour across 1 billion views a day.

About 12k views/s average. Key view events by product_id in Kafka. Each partition keeps per-minute counts for its products (exact, or a count-min sketch + min-heap if the key space is huge), and maintains a rolling 60-minute sum (sliding window from 60 tumbling buckets). Every few seconds each partition emits its local top 100; a merger takes the global top 100 and caches it. Because each product lives in one partition, local counts are complete. For exact daily "best sellers", run a batch job and overwrite.

How to answer

Estimate, partition by key, local top-K, global merge, then exact batch. Mention CMS overestimation and why it is fine for heavy hitters.

Likely follow-ups
  • Top 100 per category? (Key by category+product or keep a heap per category.)
  • See Top-K / Heavy Hitters.
Design a leaderboard with my rank among 50 million players.

A Redis sorted set per board: ZINCRBY on each score and ZREVRANK for my rank, both O(log N); ZRANGE lb:game 0 9 REV WITHSCORES (ZREVRANGE before Redis 6.2) for the top 10, O(log N + M) for M returned members. One set holds tens of millions of members on a node. Shard by game, region or season rather than splitting one board; for a single huge global board, keep the exact top-K and give everyone else an approximate percentile. Persist scores to a database or Kafka first and rebuild the set on loss. Break ties by encoding time into the score.

How to answer

Sorted set commands with complexity, then the scaling limit, then durability.

Likely follow-ups
  • Friends leaderboard? (Fetch friend IDs, ZMSCORE, sort in app.)
  • See Leaderboard.
Lambda or Kappa for an analytics pipeline? Defend your choice.

Default to Kappa if the stream processor can produce correct results and history fits in the log: one codebase, and when logic changes, replay the retained log into a new output table and switch (Kreps' approach). Choose Lambda when you need audit-grade exact numbers over long history (billing), already have a warehouse with raw data, or the batch logic is much richer than the streaming one. Hello Interview's ad-click design uses a daily Spark reconciliation for exactly that reason. The cost of Lambda is maintaining the same logic twice.

How to answer

Pick one, give the condition that would flip your choice.

Likely follow-ups
  • How long can Kafka retain data? (Tiered storage makes long retention cheaper.)
Count views of a video across three regions, writable in each region.

Each region counts locally (fast writes), and regions exchange counters asynchronously. A CRDT counter makes merging safe: a G-counter keeps one slot per region and the total is the sum; a PN-counter adds a second slot set for decrements. Merges are commutative, associative and idempotent, so replaying a sync message does no harm. The total is eventually consistent, typically seconds behind, which is fine for views. The systemdesign.one counter article describes these CRDT variants.

How to answer

Local counting + async merge + why CRDT merge is safe.

Likely follow-ups
  • Why not a global lock or a single-region counter?
Your metrics system's memory exploded after a deploy. Counting-related cause?

Most likely a cardinality explosion: someone added a high-cardinality label (user_id, request_id, full URL) to a counter, and every distinct value creates a new time series. Series count is the product of label value counts, so a user_id label on 10M users means 10M series per metric. Fix: remove the label, aggregate before emitting, or move per-user analysis to logs/OLAP; add cardinality limits in the pipeline.

How to answer

Name it, show the multiplication, give the fix and the guardrail.

Likely follow-ups
  • See Metrics & Monitoring.

Scenario: the advertiser says you over-billed by 3%

An advertiser's own logs show 3% fewer clicks than your invoice for last week. Your pipeline: click service to Kafka to a consumer that does INCRBY in Redis per (ad, minute), and a job copies Redis into the billing DB hourly.

Weak answer: "Their logs must be wrong; our system counts every click."

Strong answer: the pipeline is at-least-once with a non-idempotent sink, so every consumer restart or rebalance replayed some events and INCRBY counted them twice; bot double-clicks may also be counted. Fix the design: a unique, signed impression ID per click; dedupe at the click service and in the stream processor; write windowed results as idempotent upserts keyed by (ad, minute) instead of increments; bucket by event time; archive raw events and run a batch reconciliation that produces the billable number. Then re-run last week from the raw log and issue a credit with the evidence.

Likely follow-ups
  • How do you detect click fraud? (See Fraud Detection.)
  • How do you prove the new number is right?

Scenario: IPL final, one ad gets 40% of all clicks

During a cricket final, one sponsor's ad gets 40% of all clicks. The Flink task owning its partition is at 100% CPU and the dashboard is 6 minutes behind for every ad on that partition.

Weak answer: "Add more Kafka partitions."

Strong answer: more partitions do not help, because one key always maps to one partition. Salt the hot key (ad_id:0..15) so its events spread over 16 partitions and tasks, then sum the partial counts in a small second stage (or with upsert-SUM in the store). Pre-aggregate at the click servers for one second so each server sends one combined increment. Detect hot keys automatically (top-K on the ingest path) so salting is applied only where needed.

Likely follow-ups
  • Does salting break per-key ordering? Does that matter for counting? (No, sums commute.)
