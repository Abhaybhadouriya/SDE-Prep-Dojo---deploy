Back-of-envelope estimation

Inputs below are assumptions for the interview; the sanity check is Dropbox's own description of its scale ("hundreds of billions of files, trillions of file revisions, and exabytes of customer data", accessed from "hundreds of millions of devices", in its Nucleus post). Use 105 seconds per day. (Method: Back-of-Envelope Estimation.)

  1. Users (assumption). 500 million registered users, 100 million daily active.
  2. Commits per second. Each DAU creates or changes 2 files a day: 200,000,000 / 100,000 = 2,000 file commits/s average, about 6,000/s at a 3x peak. That is the metadata write rate - modest for a sharded database.
  3. Upload bandwidth. Say an average change sends 1 MB of new blocks (most files are small; delta upload shrinks big ones). 200M x 1 MB = 200 TB/day; 200 TB / 100,000 s = 2 GB/s (about 16 Gbit/s) of ingress on average, roughly 3x at peak. This must go straight to block servers, never through metadata servers.
  4. Download bandwidth. If each change is fetched by about 2 other devices, downloads are about 2x uploads: 4 GB/s average.
  5. Stored bytes. 500M users x 2 GB average = 1 EB (an exabyte = 1,000 PB) of logical data, before dedup and before replication / erasure-coding overhead. That matches the "exabytes" order of magnitude.
  6. Metadata rows. 500M users x 1,000 files = 500 billion file entries (matches "hundreds of billions of files"). At about 500 bytes each that is about 250 TB of metadata - far too big for one database, so we shard by namespace.
  7. Notification connections. Hundreds of millions of devices waiting for "anything changed?". Polling once a second would be about 100 million requests per second of mostly "no". Long-poll or WebSocket connections that only wake up on a change cut that to roughly the real change rate.
  8. Blocks per big file. A 50 GB file / 4 MB = 12,800 blocks. At 100 Mbit/s that upload takes over an hour - so it must be resumable and parallel.

From your world

Content-addressed blocks are the same trick as dedup in a storage array (and as content-addressed registries for Docker image layers): name a chunk by its hash, store each unique chunk once, and a "file" becomes a list of pointers. The metadata/data split is the control-plane/data-plane split: the metaserver decides what should exist (like a routing daemon programming the FIB), the block servers move the heavy bytes (like line cards forwarding packets). Where the analogy breaks: a FIB entry is overwritten in place; a file version here is immutable - a new version is a new row pointing to (mostly) old blocks.
