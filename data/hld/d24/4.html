Data model

Dropbox's server-side file system is built on namespaces: every user has a root namespace, and every shared folder is its own namespace that can be mounted inside many users' roots. A file is identified by (namespace id, relative path). The big metadata table is the Server File Journal (SFJ): append-only, one row per file version, with a journal ID (JID) that increases within each namespace.

DataShapeStore and why
Namespaces(ns_id PK, owner, type: root | shared)Relational DB. A shared folder = one namespace mounted in many roots, so sharing needs no copying.
Mounts(user_id, ns_id, mount_path, role)Relational DB; answers "what can this user see?"
File journal (SFJ)(ns_id, jid) PK -> path, blocklist, size, rev, deleted, author, tsSharded relational DB (shard by ns_id). Append-only = version history; "rows after jid N" = change feed.
Latest view(ns_id, path) -> latest jidIndex / derived table for fast "list folder".
Block indexsha256 -> (cell, bucket, checksum, refcount)Large sharded KV / MySQL (Dropbox's Magic Pocket uses a sharded MySQL "Block Index").
Block bytessha256 -> encrypted, compressed 4 MBBlob store: S3 or an in-house store like Magic Pocket. Immutable.
Device cursors(device_id, ns_id) -> last jid seenKept by the client; the server only needs it in requests.

Why SQL for metadata and not a document store? Commits need a small transaction: "check parentRev, append a journal row, bump the latest pointer" atomically within one namespace. Sharding by ns_id keeps every such transaction on one shard. The bytes go to a blob store because a database is the wrong place for exabytes of immutable 4 MB values - one of the classic interview mistakes is "putting file bytes in the SQL DB".
