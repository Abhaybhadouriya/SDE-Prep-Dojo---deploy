The story

Explain like I'm 5

You and your cousin in another city share a giant poster. Mailing the whole poster every time you colour one corner would be slow and expensive. So you cut it into numbered puzzle pieces. When you colour the top-left corner, you mail only that piece plus a little note: "the poster is now pieces 1-new, 2, 3, 4". Your cousin already has pieces 2, 3 and 4, so she just swaps in the new piece 1. And if a friend already mailed the post office an identical piece, the post office says "we already have that one, don't send it".

That is exactly how Dropbox works. Files are cut into blocks of 4 MB. Each block is named by its hash - a fingerprint computed from its bytes (SHA-256), so identical bytes always get the same name. A file is just an ordered list of block hashes, which Dropbox calls a blocklist. Change one paragraph of a 100 MB file and only the block(s) containing it change, so only those are uploaded. Other devices learn "something changed", ask "what changed since my last cursor?", and download only the blocks they do not already have.

So the design splits cleanly into two worlds: metadata (which files exist, their paths, versions and blocklists - small, needs to be consistent) and block data (the bytes - huge, immutable, content-addressed). Keeping them apart is the single most important idea on this page.

Reported in the wild: "Design Dropbox / Google Drive" is listed as common at Meta, Microsoft and Amazon, and is a full chapter ("Design Google Drive") in Alex Xu's System Design Interview Vol. 1. Hello Interview rates it easy to start but uses it to test the "handling large blobs" pattern: never push file bytes through your API servers or your SQL database.
