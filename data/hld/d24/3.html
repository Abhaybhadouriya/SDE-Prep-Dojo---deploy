Key APIs

The desktop protocol below follows Dropbox's own description (commit, store_batch, list, retrieve_batch, long-poll); the names are theirs, the JSON shapes are ours.

# 1) Metadata server: try to commit a new version of a file
POST /v1/commit
  { "ns": 9001, "path": "/docs/report.pdf", "parentRev": 41,
    "blocklist": ["h1x", "h2", "h3", "h4"], "size": 14680064 }
  -> 200 { "rev": 42, "jid": 1007 }                    # success: a new journal row
  -> 409 { "needBlocks": ["h1x"] }                     # upload these first, then retry
  -> 412 { "conflict": true, "serverRev": 42 }         # someone else committed first

# 2) Block server: upload / download raw blocks (content-addressed)
PUT  /v1/blocks/{sha256}      body: up to 4 MB (compressed)     -> 201
GET  /v1/blocks/{sha256}                                       -> bytes

# 3) Change feed for a device
GET  /v1/list?ns=9001&cursor=1003   -> { "entries": [ ...rows with jid 1004..1007... ], "cursor": 1007 }
GET  /v1/longpoll?cursors=9001:1007,5120:88   # waits up to ~60 s
  -> { "changes": true }   or   { "changes": false }  (then poll again)

Reading the status codes: 409 Conflict here means "cannot commit yet - some blocks are missing; upload them and retry" (the server's state conflicts with the request). 412 Precondition Failed means "your parentRev is stale - someone else committed first". 429 Too Many Requests / 503 Service Unavailable, used later, mean "slow down" / "try again later".

  • Commit is retried until it works: the first attempt is a cheap question "do you already have all these blocks?". For a brand new file the answer is usually "need all of them"; for a re-upload of a common file it may be "need none" - instant upload via dedup.
  • parentRev is optimistic concurrency control: "I edited version 41". If the server is already at 42, the commit is rejected and the client creates a conflicted copy (deep dive 4).
  • Block uploads are idempotent: uploading the same hash twice stores it once. Retries are free, which is exactly what flaky mobile networks need.
  • An alternative many interview answers use (Hello Interview's breakdown) is pre-signed URLs: the API returns short-lived signed URLs and the client uploads parts directly to S3 with multipart upload. Same principle: bytes bypass your app servers. (Pattern: Handling Large Blobs.)
