1. Chunking, hashing and dedup - try it yourself

Content addressing means identical bytes produce identical names. Make a 10 MB file of zeros, split it into 4 MB blocks, and hash them: two blocks are byte-for-byte identical, so they get the same hash and would be stored once.

head -c 10485760 /dev/zero > big.bin          # 10 MiB file
split -b 4M -d big.bin blk_                   # blk_00 blk_01 (4 MiB) blk_02 (2 MiB)
sha256sum blk_*
$ sha256sum blk_*
bb9f8df61474d25e71fa00722318cd387396ca1736605e1248821cc0de3d3af8  blk_00
bb9f8df61474d25e71fa00722318cd387396ca1736605e1248821cc0de3d3af8  blk_01
5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee  blk_02

Now change one byte in the middle (byte 5,000,000 falls in the second block) and hash again. Only that block's hash changes - so only 4 MB of a 10 MB file would be uploaded:

printf 'X' | dd of=big.bin bs=1 seek=5000000 conv=notrunc
split -b 4M -d big.bin blk_ && sha256sum blk_*
$ sha256sum blk_*
bb9f8df61474d25e71fa00722318cd387396ca1736605e1248821cc0de3d3af8  blk_00
ddd263d1b440219165699747d3c9d3334597cdd657695a0855777c148b8335b2  blk_01
5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee  blk_02

The weakness of fixed-size blocks: insert one byte at the very start and every block boundary shifts, so every hash changes. Two fixes: (1) content-defined chunking - cut where a rolling hash of the last ~48 bytes matches a pattern (Rabin fingerprinting), so boundaries follow the content and an insert only changes nearby chunks (used by backup tools); (2) keep fixed blocks but send an rsync-style delta of a changed block against the old one. Dropbox's post says it uses compression and rsync on block transfers.

From your world

The rolling hash in content-defined chunking is the same family of trick as a rolling CRC or the rsync weak checksum: slide a window one byte at a time and update the hash in O(1) instead of recomputing. You have probably used the idea for pattern matching in packet payloads. Where it breaks: here the goal is choosing stable cut points, not detecting errors.

You might confuse this with... Some articles shorten content-defined chunking to "CDC". On this site CDC always means Change Data Capture (streaming database changes, as in the CDC Pipeline design). Here we always write "content-defined" or "rolling-hash" chunking.

Dedup across users has a privacy edge. If uploading a file is "instant" whenever someone else already has the same bytes, an attacker can test whether a specific file exists anywhere in the system. Common mitigations: dedup only within a user or team, or always make the client prove it has the bytes. Mentioning this trade-off unprompted is an SDE-2 signal.

2. Large files and flaky networks: resumable, parallel upload

  • A 50 GB file is 12,800 independent 4 MB blocks. Upload several in parallel (e.g. 4-8 at a time) to fill the pipe.
  • Each block upload is idempotent and verified by hash, so a dropped connection only costs the in-flight block. After a crash or reboot the client simply re-runs commit: "need blocks" tells it exactly what is still missing - the server is the checkpoint.
  • Hash on the client while reading the file, and re-check on the server; reject a block whose bytes do not match its claimed hash (protects against corruption and tampering).
  • Throttle bandwidth on the client and back off on 429 / 503 with jitter, so a million clients reconnecting after an outage do not flatten the block servers.
  • With pre-signed S3 URLs the same logic uses S3 multipart upload: parts are uploaded independently and the object is assembled at the end.

3. Telling devices about changes without polling them to death

Each device keeps a cursor (the last JID it has seen) per namespace. It holds one idle long-poll HTTP request to a notification server: the server holds the request open until something changes in one of those namespaces (or a timeout of about a minute), then answers changes: true. The device then calls list(cursor) to get the actual rows. The notification is a doorbell; the journal is the parcel.

The notification tier holds hundreds of millions of mostly idle connections, so it is built like a chat gateway: many connections per server, subscriptions by namespace (a pub/sub fan-out from the commit path), and cheap reconnects. Because the signal carries no data, a lost notification is harmless: the next long-poll or a periodic safety list catches up from the cursor. Mobile apps often rely on push notifications (APNs / FCM) instead of holding a connection.

4. Conflicts: when two devices edit the same file

The laptop and the phone both start from version 41 and both save. The laptop commits first and becomes 42. The phone's commit says parentRev: 41; the server is at 42, so it rejects it. For arbitrary binary files there is no safe automatic merge (unlike text, see Collaborative Editor), so the client downloads 42 as the main file and saves its own edit next to it as "report (conflicted copy).pdf". The user decides. This is optimistic concurrency: no locks, cheap in the common case, explicit when a conflict happens. Alternatives: lock files while open (Office-style co-authoring does its own merge), or last-writer-wins (simple but silently loses data - say why you reject it).

Moves and renames are harder than edits. Dropbox's "Rewriting the heart of our sync engine" post explains that the old engine represented a move as a delete plus an add and lacked a stable file identifier that survived moves, which caused problems at scale. The rewrite (Nucleus) gave files stable IDs, put almost all logic on one deterministic control thread, and fuzzes it with seeded random simulation tests. Lesson for interviews: the client sync engine is half the system.

5. Storing exabytes: the block store

You can say "S3" and move on - Dropbox started on S3. At their scale they built Magic Pocket. From the "Inside the Magic Pocket" post: blocks are named by SHA-256 and grouped into buckets (blocks uploaded around the same time), buckets live in volumes across several machines, either replicated or erasure-coded (EC: split data into pieces plus parity pieces spread across machines, like RAID-5/6 but across servers - a few pieces can be lost and rebuilt, for roughly 1.5x storage instead of 3x for three full copies); a cell holds around 50 PB of raw data; storage machines (OSDs, "object storage devices" - servers full of disks) can hold over a petabyte each; every block is stored in at least two separate geographic zones; and a large sharded MySQL Block Index maps hash to cell and bucket. New uploads are replicated first and later erasure-coded to save space.

Garbage collection. Blocks are shared by many file versions and users, so you cannot delete a block when one file is deleted. Keep a reference count (or periodically mark-and-sweep: walk every live blocklist and mark the blocks it uses, then sweep away blocks nobody marked), honour version-history retention, and only then delete. Get this wrong and you delete someone else's data - so be conservative and delayed.
