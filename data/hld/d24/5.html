Architecture: follow one saved file

Click Next or Play. Top row: the laptop uploads. Bottom row: the phone downloads.

  1. Detect and chunk. The client's file watcher (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows) sees report.pdf change. It splits the file into 4 MB blocks and hashes each with SHA-256. A local database remembers the old blocklist, so it knows only block 1 changed (h1 became h1x).
  2. Commit first, as a question. The client sends the new blocklist with parentRev to the metadata server. The server checks access and whether all hashes are known. Answer: "need blocks: [h1x]".
  3. Upload only missing blocks, directly. The client sends h1x to a block server (compressed; Dropbox also uses rsync-style deltas on these transfers). The block server checks the hash matches the bytes and stores it in the blob store. Metadata servers never touch file bytes.
  4. Commit again. Now every hash is known, so the server appends a journal row (ns 9001, jid 1007, blocklist [h1x, h2, h3, h4]) in one transaction. The file version officially exists. The notification service is told "ns 9001 changed".
  5. Wake the other devices. The phone has an idle long-poll connection to the notification service with its cursor (jid 1003). It gets changes: true - just a signal, no data.
  6. List what changed. The phone calls list(ns 9001, cursor 1003) and receives journal rows 1004-1007, then advances its cursor to 1007.
  7. Fetch only missing blocks. It checks which hashes it already has locally (in other files or a deleted-file cache) and downloads only h1x from the block server, then reconstructs the file and writes it to disk atomically (temp file + rename).
  8. Watch out: concurrent edits. If the phone had also edited version 41 offline, its commit with parentRev 41 is rejected because the server is at 42. The client keeps the server version and saves its own as "report (conflicted copy).pdf" - no silent overwrite.

Streaming sync. In the basic flow the phone cannot start downloading until the laptop's commit finishes. Dropbox's "Streaming File Synchronization" post describes letting other clients prefetch blocks of a file that is still being uploaded, so the downloader stays about one block behind the uploader. They report sync latency improved by up to 2x, and a 100 MB file between two clients went from about 89 s to 64 s in their test.
