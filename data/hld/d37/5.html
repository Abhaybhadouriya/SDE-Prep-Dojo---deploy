Architecture: how one navigation works

Click Next or Play. The left half is the read path (tiles and routes). The right half is the write path (GPS pings becoming traffic).

  1. Draw the map. The phone computes which z/x/y tiles cover the screen and fetches them from the nearest CDN edge. Misses go to the tile store (object storage). Most requests never reach our servers.
  2. Find the destination. "Gandhi Nagar bus stand" goes through the API gateway to geocoding, which returns a lat/lng (a point).
  3. Ask for directions. The navigation service receives origin, destination, mode and departure time.
  4. Search the graph. The routing service owning that region runs a contraction-hierarchy or CRP query on an in-memory graph whose edge weights already include current traffic. It returns the best path plus 1-2 alternatives in milliseconds.
  5. Fix the ETA. The routing ETA (sum of segment times) is adjusted by an ML model that predicts the error ("residual") - the approach Uber describes for DeepETA.
  6. Answer. The client gets an encoded polyline, step list and ETA, and the trip starts. The navigation session is stored with a TTL.
  7. Report while driving. Every ~15 s the phone sends a batch of GPS points. The location service only validates and appends to Kafka (keyed by region), then returns 202 - it never blocks on processing.
  8. Turn pings into traffic. Stream processors snap points to road segments (map matching), compute speeds per segment per minute, and update the live-speed store. The routing tier periodically re-customises edge weights from it.
  9. Push a reroute. When a segment on an active route slows a lot, the session service recomputes the ETA/route and pushes it over the open connection.
