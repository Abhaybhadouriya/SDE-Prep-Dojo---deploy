Back-of-envelope estimation

The only published numbers here are Google's (2B monthly users) and the road-graph sizes from research papers. Everything else is a stated assumption - in the interview, say your assumptions and round hard.

1. Location pings (the write path)

  1. Users who navigate. Assume 1 billion daily active users, and 10% of them navigate on a given day: 100 million navigators/day, each driving 30 minutes.
  2. How many are driving at once? 100M x 30 min / 1,440 min per day = about 2 million concurrent navigators on average. Peak (rush hour across big time zones) about 3x = 6 million.
  3. Batching. The phone samples GPS once per second but sends a batch every 15 seconds (saves battery and radio wake-ups). Requests per second = 2M / 15 = ~140K QPS average, ~400K QPS peak.
  4. Bytes. One sample = lat (8 B) + lng (8 B) + timestamp (8 B) + speed, heading, accuracy (~8 B) + ids, about 50 bytes. Ingress = 2M samples/s x 50 B = ~100 MB/s average.
  5. Storage per day. 100M navigators x 1,800 samples x 50 B = 9 TB/day raw. Keep raw points only briefly (privacy), keep the aggregated segment speeds long term (much smaller).

2. Map tiles (the read path)

  1. How many tiles? Zoom level z has 4z tiles of 256 x 256 px (OpenStreetMap scheme). Zoom 18 alone is 68.7 billion tiles; zoom 21 is 421 = about 4.4 trillion.
  2. Raw size at the deepest zoom. Assume ~100 KB per raster tile: 4.4 trillion x 100 KB = ~440 PB. But about 70% of Earth is ocean and most land is empty fields - those tiles compress to almost nothing. Assume only ~10% are "busy": ~44 PB.
  3. All zoom levels. Each level up has 1/4 the tiles: 1 + 1/4 + 1/16 + ... = 4/3. Total ~44 x 4/3 = ~60 PB of raster tiles. Vector tiles (send road geometry, let the phone draw it) are several times smaller and one tile can be drawn at many zooms.
  4. Tile QPS. Assume each daily user loads 50 tiles: 1B x 50 / 86,400 = ~600K tile requests/s, peak ~2M/s. This must be a CDN job; origin servers only see cache misses.

3. Routing

  1. Route requests. Assume 1B route requests/day (including reroutes): 1B / 86,400 = ~12K QPS, peak ~40K QPS. Small QPS, but each one is heavy CPU work.
  2. Graph size. The standard Western Europe benchmark used in routing research has 18 million junctions and 42 million road arcs (from the paper on Customizable Route Planning, CRP, by Microsoft Research). If each arc costs ~40 bytes (target, length, speed class, flags, shortcut data), Europe is ~2 GB. A world graph is maybe 10x: tens of GB - it fits in RAM on a large server, so routing servers hold whole regions in memory.
  3. CPU. Plain Dijkstra is far too slow at this size, so real systems use routing algorithms that precompute shortcuts (Contraction Hierarchies, CH; Customizable Route Planning, CRP - both explained in deep dive 1). If a query takes ~2 ms of CPU (the CH/CRP range), one core does ~500 queries/s. Peak 40K QPS / 500 = ~80 cores plus headroom and alternatives (3x cost) - a few dozen machines per region. The expensive part is not the query; it is re-applying live traffic to the graph (see deep dives).

From your world

Batching GPS samples every 15 s is the same trick as interrupt coalescing / NAPI: the radio is like an expensive interrupt, so you wake it rarely and move many samples per wake-up. And the tile pyramid (4z tiles, each split into 4 children) is a radix tree over 2-D space, just like a multi-level page table splits the address space.
