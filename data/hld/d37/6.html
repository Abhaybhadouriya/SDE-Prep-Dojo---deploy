Deep dives

1. Routing on a continent in milliseconds

Plain Dijkstra grows a circle of explored junctions around the start until it reaches the goal. On a continental graph it takes a few seconds per long query (the CRP paper's own words). With 40K QPS that is hopeless. The ladder of speed-ups:

TechniqueIdeaQueryWeakness
DijkstraExplore by increasing distanceSeconds on a continentVisits millions of nodes
A* (with landmarks: ALT)Bias the search toward the goal using a lower-bound estimateSeveral times fasterStill large search spaces on long trips
BidirectionalSearch from both ends, stop when they meet~2x fewer nodesSame growth problem
Contraction Hierarchies (CH)Offline, rank junctions by importance, remove ("contract") unimportant ones and add shortcut edges that preserve distances. Query only goes "upward" from both ends.Sub-millisecond; a few hundred nodes visitedPreprocessing is tied to one set of weights; traffic changes need re-contraction
CRP / Multi-Level Dijkstra (MLD)Partition the graph into nested cells. Precompute topology once; when weights change, only recompute small cell-boundary cliques ("customization").< 2 ms (CRP paper)Slightly slower queries than CH, but traffic updates take seconds, not hours
  1. The road graph has many low-importance junctions (side streets). Searching through all of them is the slow part.
  2. Offline, we "contract" v: remove it from the search graph.
  3. A witness search checks whether u-v-w is the only shortest way from u to w. It is, so we add a shortcut u-w with weight 7 and remember "via v" to unpack the real path later.
  4. At query time both searches only move to more important nodes, so they touch a few hundred nodes instead of millions, then unpack shortcuts to draw the route.

From your world

This is OSPF areas and route summarisation for roads. Inside an area you know every link; between areas you only keep summary routes at the border routers. CH shortcuts are like summary routes; CRP cells are like areas whose boundary costs you recompute when a link cost changes, instead of re-running SPF over the whole autonomous system. Live traffic is a link-cost change, and CRP's customization step is a cheap partial SPF.

Real numbers from the Customizable Route Planning paper by Delling, Goldberg, Pajor and Werneck at Microsoft Research - described as the core of the Bing Maps routing engine: on the 18M-node Europe graph, applying a brand-new set of weights takes about 11 seconds on one core, about 1 second on 12 cores, and queries stay under 2 ms. Open-source OSRM ships both pipelines: osrm-contract (CH) and osrm-partition + osrm-customize (MLD, its default).

The killer line: "I want CH-speed queries, but traffic changes every minute. So I separate topology (changes rarely, preprocess for hours) from metric (changes every minute, customise in seconds). That is what CRP / MLD does."

2. From GPS pings to live traffic

A GPS point is noisy, so first decide which road the car was on: map matching.

  • The classic method models it as a Hidden Markov Model (Newson and Krumm, Microsoft Research, 2009): hidden states are candidate road segments near each point; "emission" probability falls with distance from the point to the road; "transition" probability prefers moves whose road distance is close to the straight-line distance. The Viterbi algorithm finds the most likely sequence. Sparser sampling means lower accuracy.
  • Lyft published a variant for "when the map is wrong" that tracks vehicles both on and off the known roads, so new roads can be learned (arXiv 1809.09755).

Then a stream job computes, per segment and per 1-minute window, the average speed from all matched cars. Partition the Kafka topic by region / map cell, so all points of one area land on the same consumer and the per-segment state stays local (see Kafka partitions and Kafka Streams & Flink).

Stop here for SDE-1. "Plain Dijkstra takes seconds; precompute shortcuts (CH) or cells (CRP) so a query takes milliseconds" and "GPS pings go through Kafka, get map-matched and become per-segment speeds" are the interview-sufficient core. Deep dives 3-5 (the ML ETA correction, vector tiles, mass rerouting) are what an SDE-2 answer adds.

3. ETA: graph time + history + ML

The routing ETA is a sum of segment travel times. But "now" is not the future: in 20 minutes the jam ahead may grow. Google explains that it combines historical patterns (how this road behaves at 6 pm on a Tuesday) with live speeds, and after COVID-19 cut traffic by up to 50% it started weighting the last 2-4 weeks more heavily. DeepMind's graph neural network groups road pieces into Supersegments and reduced inaccurate ETAs by up to 50% in cities like Berlin, Jakarta, Sao Paulo, Sydney, Tokyo and Washington D.C.

Uber uses a clean two-stage pattern you can say in the interview: the routing engine predicts an ETA, and an ML model predicts the residual (the error) using features like origin, destination, time and real-time traffic. Uber says DeepETA must answer in a few milliseconds and is its highest-QPS model. Benefit: you can retrain the ML part often without touching the routing engine.

Routing ETA alone
  • Explainable (sum of segments)
  • No training pipeline
Why add ML
  • Misses future build-up of traffic
  • Misses turns, signals, pickup delays, local quirks

4. Tiles: raster vs vector, and keeping them fresh

  • Raster tiles are pre-drawn images: simple for any client, but every zoom and every style (dark mode) needs its own set, and rotation blurs labels.
  • Vector tiles carry geometry as compact binary and the phone draws them on the GPU: smaller, smooth zoom/rotation, client-side styles. Cost: a heavier client renderer.
  • Freshness: Google reports about 100 million map updates per day. Rebuild only the tiles whose cells changed, bump their version (ETag) and let the CDN refetch. Long TTLs for low zooms, shorter for busy city zooms.
  • Offline maps (follow-up): ship a region's vector tiles plus a routing-graph slice to the phone.

5. Rerouting millions of drivers

When segment 7 suddenly slows down, who should hear about it? Scanning all 2 million active sessions is wasteful. Keep an inverted index from segment id to active sessions whose remaining route uses that segment (only the next ~30 minutes of road). When the traffic aggregator emits "segment 7 now 8 km/h", look up the affected sessions, recompute their ETA (cheap) and only rerun routing if the ETA got worse by more than a threshold (for example 2 minutes or 10%). Push it via the connection server holding the WebSocket - the same fan-out shape as notifications - see Notification System and Pattern: Fan-out.

Herding risk: if you send every driver to the same alternative road, you create a new jam there. Real systems spread load across alternatives and feed the expected extra traffic back into predictions.
