Data model and storage choices

DataShapeStoreWhy
Map tileskey z/x/y -> blob (raster PNG or vector protobuf)Object storage + CDNImmutable per map version, huge, read-only, cache-friendly. See S3-like Object Storage.
Road graph (routing tiles)nodes, arcs, turn costs, partitioned by region/cellBuilt offline into binary files; loaded into RAM by routing serversNeeds pointer-chasing at memory speed. A database round trip per edge would be millions of times too slow.
Live segment speeds(segment_id, time_bucket) -> avg_speed, samplesIn-memory KV (Redis-like) for "now", wide-column/time-series store for historyVery high write rate, simple key access, history used to train ETA models.
Places / addressesplace_id, name, category, lat/lng, geohash/S2 cellSearch index (inverted index + geo index) over a document storeFull-text + "near me" queries. See Post Search and Geo & prefix indexes.
Raw GPS pointsappend-only stream by sessionKafka (hours-days retention), then cold storage for training, anonymisedWrite-once, read in order by stream processors.
Active navigation sessionssession_id -> route_id, segment list, last position, connection serverIn-memory KV with TTLNeeded for reroute/ETA push. Short-lived.

There is almost no relational transaction here: the truth is an offline-built map plus streams of observations.
