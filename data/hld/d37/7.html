Where Kafka, Kubernetes and Docker fit

ToolRole hereDetail
KafkaShock absorber for GPS pingsWhy here: pings arrive far faster and burstier than map matching can process them, and losing them is fine but blocking phones is not. Kafka lets the location service write and return 202 at once while consumers catch up at their own pace. Topic gps-points, key = region cell, so one consumer owns one area (and its map-matching state). Retention of hours to a few days lets you replay after a bug in map matching. A second topic segment-speeds feeds the live-speed store, the routing customiser, the reroute service and the ETA training lake. Consumer lag = "how stale is traffic" - alert on it.
KubernetesRun stateless and semi-stateful tiersWhy here: the API tiers swing with commute hours, and routing servers need careful rollouts because each one holds GBs of graph. Location service, geocoding and navigation API are stateless Deployments with an HPA (Horizontal Pod Autoscaler: adds pods when CPU or QPS rises). Routing servers load GBs of graph into RAM at start: use a readiness probe that passes only after the graph is loaded, large memory requests, and slow rolling updates (maxUnavailable small) so capacity never dips. See Scheduling & Autoscaling.
DockerPackage the map-build pipelineWhy here: the map build must be repeatable - if a new graph version breaks routing, you rebuild or roll back the exact same thing. The offline pipeline (ingest road data, build graph, partition, contract, render tiles) runs as container jobs; each map version is a reproducible image + data artifact. See Writing a Dockerfile.
