60-second answer, said out loud: "A central tag service that products call through REST: PUT and DELETE on /entities/{ref}/tags/{name} so retries are safe, GET both directions with cursors. Data is three things: a tag dictionary unique by tenant and normalised name, entities referenced as product:type:id, and an entity_tag mapping whose primary key serves tags-of-entity and whose second index on tenant, tag and time serves entities-of-tag newest first. PostgreSQL sharded by tenant through a directory keeps both directions in one transaction and isolates customers; giant tenants get their own shard. Every change writes an outbox row, relayed to Kafka, which feeds counts, product search and trending: per-tenant hourly Redis sorted sets unioned over 24 hours. Permissions are checked by the product on the candidates we return."

SDE-1 stops here / SDE-2 adds. SDE-1: the three-table schema with both indexes, idempotent REST APIs with pagination, a cache for tags-of-entity, Redis sorted sets for top-10. SDE-2 adds: the shard-key analysis and tenant directory, row-level security and quotas, bulk async writes, maintained counts for hot tags, outbox for derived views, decay-weighted trending buckets, and the permission filter on reads.

You might confuse this with Trending Topics (hashtags at Twitter scale). There the hard part is global counting over a firehose; here the hard part is the data model and API, and trending is a per-tenant widget at modest volume. Do not spend 20 minutes on Count-Min Sketch in an Atlassian round.

Follow-up questions

Walk me through your DB schema and the indexes. Why these?

tag(tenant_id, tag_id, name, normalized_name, usage_count) with unique (tenant_id, normalized_name); entity_tag(tenant_id, entity_ref, tag_id, tagged_at, tagged_by) with primary key (tenant_id, entity_ref, tag_id) for tags-of-entity and duplicate prevention, and index (tenant_id, tag_id, tagged_at DESC, entity_ref) for entities-of-tag newest first, covering the query so no table lookup is needed. Tenant first in every key for isolation and sharding.

How to answer

For each index, name the query it serves. An index with no query is a cost; a query with no index is a scan.

Likely follow-ups
  • Why not a tags array on the entity? (No cross-product by-tag lookup; renames touch every row.)
  • Why tagged_at in the second index? (Newest-first pagination with a cursor.)
Why REST? Why this database? Justify concretely.

REST because the domain is resources and links; add and remove map to idempotent PUT and DELETE (safe retries from any product), reads are GET and cacheable, and every product team already consumes REST through the gateway. Internally, gRPC is fine. PostgreSQL because we need a uniqueness constraint, an idempotent upsert, a transaction covering tag-create, link and outbox, and two B-tree indexes; 1.2 TB is comfortable when sharded by tenant. I would choose DynamoDB if the platform standard is DynamoDB: the adjacency-list pattern with a flipped GSI gives the same two lookups, at the cost of an eventually consistent GSI.

How to answer

Tie every technology to a requirement in your list. One report says the interviewer rejected a generic "we can scale later" story.

Likely follow-ups
  • Would GraphQL help? (For a UI that wants entity + tags + users in one call; not for the core write API.)
Tag writes become very heavy. What changes?

Separate many small writers from bulk writers. Many tenants: add shards; each write is one short transaction. Bulk: async job API, batched multi-row inserts of about 1,000, per-tenant rate limits so a bulk job does not starve others. Hot tag: never count on read; maintain counts from events. Keep derived work (search, trending) off the write path via the outbox. If one giant tenant still saturates a shard, give it a dedicated shard and split its two directions by entity and by tag hashes.

How to answer

Ask "heavy how?" - many tenants, one tenant, or one tag - then answer each.

Likely follow-ups
  • What does the user see during a 50,000-issue bulk tag? (Job progress; issues appear tagged gradually.)
How do you shard, and how do you keep tenants isolated?

Shard by tenant through a directory table so both directions are local and tenants can be moved. Isolation: tenant id from the auth token, first in every key; row-level security as a second fence; tenant-prefixed cache keys; per-tenant quotas; dedicated shards for the largest customers. Never accept tenant id from a request parameter.

How to answer

Show the three shard-key options in a small table and why tenant wins, then name its weakness (giant tenant) and fix.

Likely follow-ups
  • How do you move a tenant to a new shard online? (Copy, then replay changes from CDC, then flip the directory entry during a short write pause.)
Show the top-10 trending tags. How?

Tag events flow to an aggregator that ZINCRBYs per-tenant hourly sorted sets with a TTL. The read unions the last 24 buckets with decaying weights and returns ZREVRANGE 0 9, cached for a minute. O(log N) updates, cheap reads, no subtraction of old events. Optionally score growth against a baseline so evergreen tags do not dominate.

How to answer

Define trending first (recent volume vs growth), then the buckets. Mention Count-Min Sketch only if they push to global scale.

Likely follow-ups
  • Trending across all tenants? (Only for public content; aggregate in a stream job with a sketch plus heap.)
  • Exactly-once counting? (Not needed for a widget; at-least-once with small overcount is fine.)
How does tag search (autocomplete) work, and "entities with tag A and B"?

Autocomplete: B-tree prefix range scan on (tenant_id, normalized_name), ordered by usage count, cached per tenant; Elasticsearch with edge n-grams if tenants have huge dictionaries or need fuzzy matching. A AND B: start from the rarer tag's list in the by-tag index and probe the other tag via the primary key, or GROUP BY entity HAVING COUNT(DISTINCT tag) = 2. Complex combined queries go to each product's search index, which receives tags via events.

How to answer

Show you know which index each query uses; mention "start from the smaller list".

Likely follow-ups
  • Case and spaces? (Normalise on write; keep the display name.)
Two users create the same tag at the same moment. What happens? (concurrency)

The unique constraint on (tenant_id, normalized_name) decides: one insert wins; the other uses INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING tag_id and gets the same id. Linking is idempotent by primary key. No application lock is needed. Add and remove of the same link race at the row: the later committed operation wins, and both are safe to retry.

How to answer

Push concurrency into database constraints rather than distributed locks. Bar raisers like hearing why you do not need a lock.

Likely follow-ups
  • And with DynamoDB? (Conditional put on the tag-name item; transactions for tag plus link.)
A user clicks a tag. How do you avoid showing issues they are not allowed to see?

Permissions belong to the products. The tag service returns a page of candidate entity references; the product (or a gateway composition layer) runs a batch permission check and hydrates only visible entities, fetching another page if too many were filtered. Never cache the filtered list across users. For very sensitive spaces, products can also tag with a visibility hint so the service can pre-filter.

How to answer

State ownership first ("the tag service does not own permissions"), then the filter-and-refill loop.

Likely follow-ups
  • What if 99% are hidden? (Pre-filter by project or space ids the user can see, passed in the query.)
How do search, counts and trending stay in sync with tag writes?

Transactional outbox: the link change and an event row commit together; a relay (or Debezium CDC) publishes to Kafka; consumers update derived views idempotently. If a consumer is down, it catches up from its offset. This avoids the dual-write bug of writing the DB and then publishing separately.

How to answer

Name the failure you avoid (link saved, event lost), then the fix.

Likely follow-ups
  • Event ordering? (Key by tenant; per-entity order is preserved within a partition.)

Scenario drills

Scenario: one customer's automation rule tags 2M issues in an hour

Write latency on one shard climbs and other tenants on it complain.
Weak answer: "Scale up the database."
Strong answer: this is a noisy neighbour. Per-tenant write quotas push the automation into the async bulk path (batched writes, lower priority). Move the tenant to a dedicated shard via the directory if it keeps happening. Check for an automation loop. Monitor per-tenant write rate so you see it before others do.
Follow-ups
  • How do you tell the customer? (Job progress plus a quota-exceeded response with a retry-after.)

Scenario: "the tag count says 1.2M but the list shows 900K"

A large tag's displayed count disagrees with the entities you can page through.
Weak answer: "Run COUNT(*) on every request."
Strong answer: two causes. Counts are eventually consistent (consumer lag or a lost increment), and the list is permission-filtered. Reconcile counts with a nightly batch from the table; label the number "about" in the UI; and explain that the list shows only what you can see.
Follow-ups
  • Should the count be per viewer? (Too expensive; show per-viewer counts only for small tags.)

Common mistakes

  • Only one index, so one of the two directions scans.
  • Tenant id from the request body, or missing from keys and cache names.
  • OFFSET pagination and COUNT(*) on hot tags.
  • Rushing to sharding and Kafka before the API and schema are solid (the reports say Atlassian cares most about these).
  • Using distributed locks for tag creation instead of a unique constraint.
  • Forgetting permissions on "entities of tag".
