Key APIs

One interviewer wanted concrete reasons for REST. Here they are: tags and entity-tag links are resources; adding is PUT on the link (idempotent, so retries are safe); removing is DELETE (idempotent too); reads are GET and can be cached by gateways and clients. Internal product services can call the same contract over gRPC for lower overhead. See API Design.

# entity reference = {product}:{type}:{id}, URL-encoded; tenant comes from the auth token, never the body
PUT    /v1/entities/jira:issue:10042/tags/performance      # add (creates tag if new) -> 200 or 201
DELETE /v1/entities/jira:issue:10042/tags/performance      # remove -> 204 (also if it was not there)
GET    /v1/entities/jira:issue:10042/tags                  # tags on one entity
  -> 200 { "tags": [ { "id": "tg_51", "name": "performance" }, { "id": "tg_9", "name": "q3" } ] }

POST   /v1/entities/tags:batchGet  { "entities": ["jira:issue:10042", "confluence:page:777", ...] }
                                                            # one call for a board or search page of 50 items
GET    /v1/tags/performance/entities?product=jira&limit=50&cursor=eyJ0cyI6...
  -> 200 { "items": [ { "entity": "jira:issue:10042", "taggedAt": "..." } ], "nextCursor": "..." }

GET    /v1/tags?prefix=perf&limit=10                       # autocomplete
GET    /v1/tags/trending?window=24h&limit=10               # top-10 trending
GET    /v1/tags/popular?limit=10                            # all-time top-10

POST   /v1/tags:bulkApply  { "tag": "release-42", "entities": [ ... up to 1,000 ... ] }
  -> 202 { "jobId": "j_7" }                                  # async for large batches

Details interviewers probe: cursor pagination (an opaque token holding the last (tagged_at, entity) seen), never OFFSET, because offset gets slower the deeper you page and skips rows when new tags arrive. Tenant from the token, never from a parameter, so one customer cannot ask for another's tags. Batch get, because a Jira board renders 50 issues and should not make 50 calls.
