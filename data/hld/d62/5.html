Architecture: from "add tag" to the trending widget

Click Next or Play. The write path is synchronous for the link and asynchronous for everything derived from it.

  1. Product calls the tag API. A user adds a tag in Jira; the Jira frontend or backend calls the tag API through the gateway, which authenticates the user, takes the tenant id from the token, and applies per-tenant quotas.
  2. Write the link. The stateless tag service, in one transaction on the tenant's shard: upsert the tag by (tenant, normalized_name), insert the mapping with ON CONFLICT DO NOTHING, and write an outbox row. Both indexes update inside the same transaction, so both directions are consistent immediately.
  3. Cache. "Tags of entity" is cached in Redis per entity (or batched for boards); the write deletes that key, so the next read is fresh and the writer sees their own change.
  4. Publish the event. A relay reads the outbox (or CDC reads the log) and publishes TagAdded / TagRemoved to Kafka, keyed by tenant_id. The outbox guarantees the event exists if and only if the transaction committed.
  5. Count trends. A stream aggregator counts tag adds per tenant per minute in memory, then ZINCRBYs hour buckets in Redis: one sorted set per tenant per hour, with a TTL of a few days.
  6. Other consumers. Product search indexes pick up the tag so "label = performance" works in JQL-like search; a periodic job updates tag.usage_count for the all-time popular list.
  7. Read trending. "Top-10 in 24 h" unions the last 24 hour buckets (optionally weighted so recent hours count more), caches the result for a minute, and returns the top 10 with ZREVRANGE 0 9.

The two paths, running: the solid dot is the synchronous link write; the second dot is the asynchronous event that feeds trends.
