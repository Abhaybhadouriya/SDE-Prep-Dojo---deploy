Data model

Three tables. Most of the Atlassian reports say this is where the round was won or lost. More on modelling in Data Modeling & Indexing.

CREATE TABLE tag (
  tenant_id       BIGINT NOT NULL,
  tag_id          BIGINT NOT NULL,
  name            TEXT   NOT NULL,          -- as first typed: "Performance"
  normalized_name TEXT   NOT NULL,          -- lower-cased, trimmed: "performance"
  usage_count     BIGINT NOT NULL DEFAULT 0, -- updated asynchronously
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, tag_id),
  UNIQUE (tenant_id, normalized_name)       -- one tag per name per tenant
);
CREATE INDEX tag_prefix ON tag (tenant_id, normalized_name text_pattern_ops);  -- autocomplete

CREATE TABLE entity_tag (
  tenant_id  BIGINT NOT NULL,
  entity_ref TEXT   NOT NULL,               -- 'jira:issue:10042'
  tag_id     BIGINT NOT NULL,
  tagged_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  tagged_by  BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, entity_ref, tag_id)            -- tags of an entity; also blocks duplicates
);
CREATE INDEX entity_tag_by_tag
  ON entity_tag (tenant_id, tag_id, tagged_at DESC, entity_ref);   -- entities of a tag, newest first
  • Why a tag table and ids, not just strings on the mapping? Renaming a tag becomes one row change instead of millions; ids are short and fixed-length, so indexes are smaller; and the dictionary gives autocomplete and counts a home.
  • Why the entity reference is a typed string (product:type:id): the tag service must not know each product's schema. A typed reference lets new products join without a migration, and lets "entities of a tag" filter by product with a prefix.
  • Why the primary key includes tag_id: adding the same tag twice is a no-op (INSERT ... ON CONFLICT DO NOTHING), which makes PUT idempotent at the database level.

"Why this database?" Say it concretely: "PostgreSQL, because the core is a many-to-many relation that needs a uniqueness constraint (one tag name per tenant), an idempotent insert, transactions for create-tag-then-link, and two B-tree indexes. 1.2 TB is fine sharded by tenant. If the team runs on DynamoDB, the same model is an adjacency list: partition key entity, sort key tag, and a global secondary index flipped to tag then entity - AWS documents this exact pattern for many-to-many."
