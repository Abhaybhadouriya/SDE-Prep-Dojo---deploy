Back-of-envelope estimation

The reports do not give numbers, so state assumptions and round hard. Method from Back-of-Envelope Estimation.

6Btag mappings
~1 TBmappings + indexes
~60K/speak reads
~5K/speak writes (bursts 10x)
  1. Entities Assume 300K tenants and 2B taggable entities across products, with 30% tagged and an average of 3 tags on tagged ones: 2B x 0.3 x 3 = about 2B mappings. Round up for growth to 6B over a few years.
  2. Mapping row size tenant id (8 B), tag id (8 B), entity reference (about 40 B, e.g. "jira:issue:10042"), created time and user (16 B), plus overhead: about 100 B. 6B x 100 B = 600 GB. Two indexes (one per direction) roughly double it: about 1.2 TB. Too big for comfort on one node, easy across a handful of shards.
  3. Distinct tags Assume 500 distinct tags per tenant on average: 150M tag rows x 100 B = 15 GB. Small; the tag dictionary per tenant fits in cache.
  4. Reads 20M daily active users x 100 issue or page views = 2B views a day = about 23K per second; peak 2.5x = about 60K per second for "tags of entity". "Entities of a tag" (a user clicks a tag) is much rarer: say 1% of that.
  5. Writes 20M users x 2 tag changes a day = 40M a day = about 460 per second; peak 10x during working hours plus automation = about 5K per second. A bulk edit ("add tag release-42 to these 5,000 issues") or an automation rule can burst far higher for a single tenant and a single tag: that is the hot-key problem in deep dive 2.
  6. Trending Every write is also a counting event: 5K per second into the stream aggregator. A top-10 query per tenant is cheap from a sorted set.

What the numbers tell you: reads are about 10x writes and dominated by "tags of this entity", which should be served from a cache or even stored with the entity. Storage is modest. The real dangers are (1) one tag that is on millions of entities (a hot partition on the by-tag index) and (2) write bursts from bulk operations.
