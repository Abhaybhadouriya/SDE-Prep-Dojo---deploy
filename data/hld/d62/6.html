Deep dives

1. Sharding: by tenant, by entity, or by tag?

The two lookups want different partition keys. "Tags of entity" wants the entity; "entities of tag" wants the tag. Three options:

Shard keyTags of entityEntities of tagVerdict
tenant_id (both indexes on the same shard)One shardOne shardDefault. Both directions local, one transaction, and natural tenant isolation. Breaks only for a giant tenant.
entity_refOne shardScatter to all shardsBad for the by-tag query.
Two tables: by entity and by tag, each sharded on its own keyOne shardOne shardFor huge scale (NoSQL). Costs a cross-shard dual write: write one, propagate the other by CDC, and accept a short lag on the by-tag view.

Start with tenant sharding: most tenants are small, and both directions plus the tag dictionary live together. Map tenants to shards through a directory (a lookup table), not a hash formula, so a big tenant can be moved to its own shard and noisy neighbours can be separated. For the very largest tenants, split further by hashing entity_ref for the by-entity table and tag_id for the by-tag table (option 3) - only for them.

Multi-tenant isolation (asked as a follow-up): tenant id is the first column of every key and index, taken from the auth token, never the request body; row-level security policies in PostgreSQL (tenant_id = current_setting('app.tenant')) are a second fence if application code has a bug; caches and Redis keys are prefixed by tenant; per-tenant quotas protect everyone from one tenant's automation storm; big customers can get a dedicated shard (and, if contracts need it, data residency in their region).

2. Heavy writes and the hot tag

Interviewers asked "what if tag writes are very heavy?". Split the question:

  • Many tenants writing a little: spread across shards by tenant; each write is one small transaction (about 3 index updates). PostgreSQL handles thousands of these per second per shard; add shards as tenants grow.
  • One tenant bulk-tagging ("add release-42 to 50,000 issues"): accept the request as an async job (202 plus job id), write in batches of about 1,000 rows per transaction with multi-row inserts, and rate-limit per tenant so the shard stays healthy for others. The UI shows progress.
  • One tag on millions of entities (for example "bug"): the by-tag index has one long run of rows. Reads stay fast because pagination walks the index newest-first from a cursor. Counting it with COUNT(*) is the slow part, so never compute counts on read: keep usage_count updated from the event stream.
  • Write amplification: each link updates the primary key index and the by-tag index. Do not add more indexes casually; derived views (search, trending) are built from events instead.

Concurrency (Amazon Pay's variant): two users create "urgent" in the same second. The unique constraint on (tenant_id, normalized_name) makes one insert win; the other's INSERT ... ON CONFLICT (tenant_id, normalized_name) DO UPDATE SET name = tag.name RETURNING tag_id gets the same id back. No lock, no duplicate tag. Removing a tag while another user adds it is ordered by the database: last write wins on that one link, and both operations are idempotent.

3. Tag search and multi-tag queries

Autocomplete is a prefix search inside one tenant's dictionary (hundreds to a few thousand names). A B-tree index on (tenant_id, normalized_name) answers WHERE tenant_id = ? AND normalized_name LIKE 'perf%' as a range scan. Order suggestions by usage_count. For a tenant with 100K tags, cache the dictionary in memory per tenant or move it into Elasticsearch with an edge n-gram analyser; fuzzy matching ("perfromance") comes free there.

Entities with tag A AND tag B: fetch the two entity lists from the by-tag index and intersect. Start from the rarer tag (smaller list, known from usage_count) and probe the other via the by-entity primary key: for each entity in the small list, "does it have tag B?" is one index lookup. In SQL: GROUP BY entity_ref HAVING COUNT(DISTINCT tag_id) = 2 over both tags. For rich queries combined with text and fields, push tags into each product's search index (deep dive 5's events) and let it do the boolean query.

Permissions: "entities of tag" must only show what this user can see. The tag service does not own permissions, so it returns a page of candidates and the calling product filters with a batch permission check, fetching more pages if many were hidden. Say this out loud: it is a classic Atlassian follow-up.

4. Popular and trending tags

Popular (all time) is usage_count on the tag row, updated by a consumer of tag events; top-10 is an index on (tenant_id, usage_count DESC) or a per-tenant sorted set popular:{tenant}.

Trending means "used a lot recently". A candidate in a 2025-03 Atlassian report used Redis sorted sets and got positive feedback. The clean version uses time buckets:

# on each TagAdded event (batched per minute by the aggregator)
ZINCRBY trend:t42:2026112310  17 "tg_51"     # tenant 42, hour bucket 10:00, +17 uses
EXPIRE  trend:t42:2026112310  259200         # keep 3 days

# read: top-10 over the last 24 hours (cached ~60 s)
ZUNIONSTORE tmp:t42:24h 24 trend:t42:2026112310 trend:t42:2026112309 ... WEIGHTS 1 0.97 0.94 ...
ZREVRANGE   tmp:t42:24h 0 9 WITHSCORES

Sorted set inserts and score updates are O(log N) (Redis uses a skip list plus a hash table), and reading the top 10 is O(log N + 10). Weights that shrink with age give a smooth decay, so a tag used heavily 23 hours ago does not beat one exploding right now. "Trending" can also mean "growth vs normal": score = recent count / (baseline count + k), which stops always-popular tags like "bug" from owning the list. Bucketing removes the need to ever "subtract" old events.

At much bigger scale (global trending across all tenants, millions of distinct tags), use a Count-Min Sketch plus a small heap per window, as in Top-K Heavy Hitters.

5. Keeping derived views in sync, and deletes

  • Outbox: write the event row in the same transaction as the link, and relay it to Kafka. Avoids the dual write bug where the link commits but the event is lost (or the reverse).
  • Entity deleted in Jira: Jira publishes EntityDeleted; the tag service consumes it and deletes that entity's links in batches. Until then, product-side permission filtering hides the dead entity anyway.
  • Tag renamed or merged: rename is one row. Merge "perf" into "performance" is a background job that re-points links in batches and leaves a redirect from the old name.
  • Rebuild: Redis trending and caches can be rebuilt by replaying Kafka (7 days retention) or from the database.
