RAG: retrieval-augmented generation

A model only knows what was in its training data, which is old and does not include your company's documents. Fine-tuning on private data is slow, costly, and cannot cite sources. Retrieval-augmented generation (RAG) instead looks up relevant passages at question time and pastes them into the prompt. The original RAG paper (Lewis et al., 2020) described it as combining parametric memory (the model's weights) with non-parametric memory (a dense vector index of Wikipedia) and showed more specific, factual answers on open-domain question answering.

RAG has two pipelines. The ingestion pipeline runs offline or as a stream: split documents into chunks (a few hundred tokens each), turn each chunk into an embedding (the list of numbers from the section above), and store it in a vector index with metadata. The query pipeline runs per request. Click through it:

  1. Embed the question with the same embedding model (and version) used at ingestion, or the vectors will not be comparable.
  2. Retrieve. Approximate nearest-neighbour search finds chunks whose vectors are close to the question, filtered by metadata such as tenant or permissions. A keyword (BM25) search often runs in parallel because embeddings miss exact terms like error codes and product IDs.
  3. Rerank. A heavier model scores the merged candidates. Anthropic's recipe retrieves about 150 chunks, reranks, and keeps the top 20.
  4. Build the prompt. Fixed system rules first, then retrieved chunks with their source IDs, then history, then the question. Fixed parts first also makes prefix caching work.
  5. Generate. The LLM answers using only the supplied context and cites chunk IDs, so the UI can link sources.
  6. The trap. If retrieval brings the wrong chunks, the model writes a fluent wrong answer. Evaluate retrieval (did the right chunk appear in top-k?) on its own.

Making retrieval better (with real numbers)

A chunk cut out of a long document often loses its context ("revenue grew 3%" - whose revenue? which quarter?). Anthropic's Contextual Retrieval write-up prepends a short, document-aware summary to each chunk before embedding and before BM25 indexing. On their tests the top-20 retrieval failure rate went from 5.7% to 3.7% with contextual embeddings (35% fewer failures), to 2.9% when also using contextual BM25 (49% fewer), and to 1.9% with reranking added (67% fewer).

The same article gives a useful "do you even need RAG?" rule: if the whole knowledge base is under about 200,000 tokens (roughly 500 pages), just put all of it in the prompt and use prompt caching. RAG earns its complexity when the corpus is large, changes often, or needs per-user permissions.

Ingestion is a data pipeline. New or edited documents arrive as events (for example from CDC into Kafka), workers chunk and embed them in batches, and upserts land in the index. Deletes matter too: a deleted HR document must stop being retrievable, so propagate deletes and permission changes, not just inserts.
