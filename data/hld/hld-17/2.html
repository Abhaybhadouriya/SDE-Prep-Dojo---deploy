Inference serving: prefill, decode and the KV cache

Every LLM request has two phases with very different hardware needs. Getting this one idea right explains batching, the KV cache, latency metrics and even why some companies split their GPU fleets in two.

Prefill and decode

  • Prefill: the model processes every prompt token in parallel. This is big matrix-times-matrix maths, so it keeps the GPU's compute units busy (compute-bound).
  • Decode: the model makes one token per step. Each step must stream the whole model's weights from GPU memory to do a small matrix-times-vector job. The GPU spends its time moving bytes, not computing. Databricks and NVIDIA both describe decode as memory-bandwidth bound.

The two latency numbers

TTFTtime to first token
TPOTtime per output token
100 msTPOT = ~10 tokens/s per user
46 msTTFT, MPT-7B on 1x A100 (Databricks)

Databricks gives the formula you should write on the whiteboard: latency = TTFT + TPOT x output_tokens. A 500-token answer at 50 ms per token takes about 25 seconds to finish, which is why every chat product streams. Hello Interview's ChatGPT breakdown makes the same point: users judge the product by the blank screen before the first token, not by total completion time.

The KV cache: the model's notebook

To make token number 500, the attention layers need information about tokens 1 to 499. Recomputing that every step would be wasteful, so the server stores two vectors per token per layer, the key and the value. That store is the KV cache. It lives in GPU memory next to the weights and grows by one entry per token, for every request in flight.

# KV cache bytes per token (NVIDIA's formula)
kv_per_token = 2 * num_layers * (num_heads * head_dim) * bytes_per_value
#              ^ K and V

# Llama 2 7B: 32 layers, hidden size 4096, FP16 (2 bytes)
kv_per_token = 2 * 32 * 4096 * 2      # = 524,288 bytes, about 0.5 MB
kv_4k_tokens = kv_per_token * 4096    # about 2 GB for ONE 4k-token sequence
weights      = 7e9 * 2                # about 14 GB just for the weights

Those numbers match NVIDIA's worked example (14 GB of weights, about 2 GB of KV cache for one 4,096-token sequence). Anyscale gives the same picture for a 13B model on a 40 GB A100: about 26 GB of weights leaves about 14 GB, which at nearly 1 MB per token holds only about 14,000 tokens in total - roughly 28 sequences of 512 tokens, or 7 sequences of 2,048. GPU memory, not compute, caps how many users one GPU can serve.

From your world

The KV cache is per-connection state, like a TCP control block plus its receive buffer: small per packet, but it grows with the stream and multiplied by thousands of concurrent flows it decides how many connections a box can hold. Decode being memory-bound is the same story as a router that is limited by memory bandwidth for packet buffers, not by the CPU's instruction rate.
