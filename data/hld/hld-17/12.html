Interview questions

Why do LLM services stream responses, and how would you implement it?

Total latency is TTFT + TPOT x output tokens, so a long answer can take tens of seconds, but the first token can arrive in well under a second. Streaming shows progress at TTFT instead of making the user wait for the whole answer. Implement it with Server-Sent Events (one-way server-to-client over HTTP, simple through proxies and load balancers) or WebSockets if the client must also send mid-stream (cancel, tool results). The inference server emits tokens; the API tier relays them; each event carries a sequence number. The service appends generated tokens to the message record in batches so a dropped client can reconnect with Last-Event-ID and resume, and a cancel request frees the GPU slot immediately.

How to answer

Start with the latency formula, choose SSE and justify it, then cover reconnects, cancels and proxy timeouts (disable buffering, heartbeats).

Likely follow-ups
  • What happens to the stream during a deploy of the API tier?
  • How do you bill tokens if the user cancels halfway?
  • SSE vs WebSocket vs long polling here?
What is the KV cache, and why does it limit how many users a GPU can serve?

During decode, each new token needs the attention keys and values of all previous tokens. The server stores them per token per layer instead of recomputing them: that is the KV cache. Its size is about 2 x layers x hidden size x bytes per value per token; for Llama 2 7B in FP16 that is about 0.5 MB per token, so a 4k-token sequence is about 2 GB, versus 14 GB for the weights. Every concurrent sequence needs its own cache, so once weights are loaded the remaining GPU memory divided by (tokens per sequence x bytes per token) gives the maximum batch. Anyscale's 13B example on a 40 GB A100 leaves room for about 14k tokens total. Memory, not FLOPs, caps concurrency.

How to answer

Define it, give the formula and one concrete number, then connect it to batch size, throughput and cost. Mention levers: PagedAttention, grouped-query attention, quantised KV, shorter contexts.

Likely follow-ups
  • What happens when the KV cache fills up mid-generation?
  • How does a longer context window change your fleet size?
What problem does PagedAttention solve? Relate it to operating systems.

Older servers reserved a contiguous KV region per request sized for the maximum output length, wasting 60-80% of KV memory through fragmentation and over-reservation (vLLM blog). PagedAttention stores the KV cache in small fixed-size blocks allocated on demand, with a per-request block table mapping logical positions to physical blocks. Waste drops below 4%, so more sequences fit in a batch. Like virtual memory: block table = page table, block = page frame; identical prefixes can share physical blocks with reference counts, and copy-on-write lets parallel samples share the prompt (up to 55% less memory). The paper reports 2-4x throughput over FasterTransformer and Orca at equal latency.

How to answer

Problem (fragmentation), mechanism (blocks + table), consequence (bigger batches), and the OS analogy - which is a strength for a systems engineer.

Likely follow-ups
  • How does this enable prefix caching?
  • What is the trade-off of a larger block size?
Design a "chat with our internal documents" feature (RAG). Walk through it.

Two pipelines. Ingestion: document change events (CDC or upload events into Kafka) feed workers that extract text, chunk it (a few hundred tokens with overlap, ideally with a short document-context prefix), embed in batches, and upsert into a vector index with metadata: doc ID, tenant, ACL groups, embedding model version. Deletes and permission changes propagate the same way. Raw docs stay in object storage and a metadata DB; the vector index is rebuildable. Query: authenticate, embed the question, run ANN search with an ACL filter plus BM25 keyword search, merge, rerank (e.g. 150 candidates down to 20), build the prompt with stable rules first, generate with citations, stream back, log everything for evaluation. Add a semantic cache only for non-personal FAQ traffic.

How to answer

Clarify corpus size first (under ~200k tokens may not need RAG), then draw ingestion and query as two flows, then deep-dive on permissions, freshness and evaluation.

Likely follow-ups
  • How do you stop a user retrieving a document they cannot open?
  • How fresh is the index after an edit?
  • How do you know retrieval is good?
Where would you put caches in an LLM application, and what are the risks of each?

Three layers. (1) Exact response cache keyed by a hash of normalised prompt + model + parameters: zero GPU work, low hit rate for chat, risk of stale answers and leaking personal data, so scope keys by user or tenant. (2) Semantic cache keyed by an embedding with a similarity threshold: more hits, but false hits return an answer to a different question; use only for public FAQ-style traffic. (3) Prefix/KV cache on the inference server: reuses prefill for shared prefixes (system prompt, long document). It needs an exact token prefix, so put stable content first; hosted APIs price cache reads at a fraction of normal input (0.1x in Anthropic's docs) with a short TTL. Route same-conversation requests to the same replica for warm caches.

How to answer

List three caches with key, what is saved, and the risk. Then connect prefix caching to routing (affinity vs load balance).

Likely follow-ups
  • How do you invalidate when the underlying document changes?
  • Can prefix caching leak data between tenants?
Design rate limiting for an LLM API. Why are request counts not enough?

Cost scales with tokens, not requests: one 100k-token prompt costs far more than many tiny ones. Limit RPM and TPM (and daily totals) per API key and model, plus a concurrency cap because GPU memory is consumed by concurrent streams. Output length is unknown at admission, so reserve prompt tokens + max_tokens from a token bucket (Redis, atomic Lua), then refund the unused part when the stream ends. Return 429 with Retry-After and remaining-token headers; clients back off with jitter. Tiers map to priority queues or reserved pools; batch/offline work runs in a low-priority lane. Shed load early when queue wait would break the TTFT target.

How to answer

Start from cost, name the dimensions, solve the unknown-output problem with reserve/refund, then fairness and overload behaviour. Reuse token bucket from the classic rate limiter.

Likely follow-ups
  • The limiter runs in 5 regions - global or per-region budgets?
  • What if Redis is down: fail open or closed?
Estimate the GPUs needed for a chat service with 120k concurrent streams.

State assumptions: 13B-class model, about 1 MB KV per token, average live context 2,000 tokens, so about 2 GB per stream. A 40 GB GPU with about 26 GB of weights has about 14 GB left, so about 7 streams per GPU, and 120k / 7 is about 17k GPUs before headroom. Then check the decode side: throughput is roughly memory bandwidth / bytes read per step, and TPOT must stay under the target (say 50-100 ms). Then show the levers: 80 GB GPUs, grouped-query attention, quantised weights and KV, context summarisation, prefix sharing, smaller models for easy prompts, response caching. The point is to size by KV memory per concurrent stream, not by QPS.

How to answer

Write the chain on the board: concurrency x context x bytes/token vs free memory per GPU. Say "assume" for every number. End with which lever you would pull first and why.

Likely follow-ups
  • How does doubling the context window change the answer?
  • How many GPUs for prefill vs decode if you disaggregate?
How do you evaluate an LLM feature before and after launch?

Offline: a versioned golden set of real questions with expected facts, run in CI for every prompt, model or retrieval change. Measure retrieval separately (recall@k of the right chunk) from answers (correctness, groundedness in context, format validity). Use an LLM judge with a rubric, calibrated against human labels; keep a human review sample (LinkedIn reports linguists reviewing up to 500 conversations a day). Online: thumbs, regenerate and abandonment rates, latency (TTFT, TPOT) and cost per request, with canaries and A/B tests for changes. Feed production failures back into the golden set.

How to answer

Offline vs online, retrieval vs generation, automatic vs human. Tie it to release process: no prompt change ships without the eval run.

Likely follow-ups
  • How do you detect hallucinations automatically?
  • The model provider silently updated the model - how would you notice?
What is prompt injection, and how would you defend a RAG or agent system against it?

Prompt injection (OWASP LLM01) is input that changes the model's behaviour against the developer's intent, either typed by the user or hidden in retrieved content (indirect injection). Because instructions and data share one channel, no prompt wording is a full fix. Defend at the system level: treat retrieved text as data and label it as such; run input and output classifiers; give tools least privilege and scoped credentials; require human confirmation for side effects (send, pay, delete); validate outputs against schemas before using them; filter retrieval by the user's own permissions so injection cannot reach other tenants' data; log and rate limit tool calls.

How to answer

Define it with an indirect example, admit it cannot be fully solved in the prompt, then list layered controls that limit the blast radius.

Likely follow-ups
  • How is this similar to SQL injection, and how is it different?
  • Which OWASP LLM risks apply to the vector store itself?
Your LLM service has rising TTFT at peak while GPUs show high utilisation. What do you do?

First split the latency: queue wait vs prefill time. If queue wait dominates, you are out of capacity: autoscale on queue depth and KV utilisation (with warm headroom, since GPU nodes are slow to start), shed or downgrade low-priority traffic, enforce per-tenant concurrency. If prefill dominates, long prompts are the problem: enable prefix caching and route by prefix for affinity, cap or summarise context, use chunked prefill so big prompts do not block decode, or disaggregate prefill and decode pools (Splitwise reported 1.4x throughput at 20% lower cost). Check that batch size is not so large that TPOT also suffers.

How to answer

Measure before fixing: decompose TTFT, then pick levers per cause. Mention the metric you would alert on (p95 TTFT per tier).

Likely follow-ups
  • What does your autoscaling signal look like on Kubernetes?
  • How would you protect paid users during the spike?

Scenario: the support bot quotes a refund policy that was changed last week

An e-commerce company's RAG support bot keeps telling customers the old 30-day refund window. The policy page was updated to 15 days a week ago.

Weak answer: "Fine-tune the model on the new policy" or "add 'always use the latest policy' to the prompt."

Strong answer: this is a data freshness bug, not a model bug. Check the ingestion path: did the edit event reach the pipeline, was the old chunk deleted or only a new one added (now both are retrieved), is the semantic or response cache still serving old answers, and does the index carry an updated_at so retrieval can prefer newer chunks? Fix: upsert by stable chunk IDs, propagate deletes, invalidate caches keyed by source doc ID on change, add a freshness SLO (edit to searchable within N minutes) with a canary query that checks it, and add this case to the golden eval set.

Likely follow-ups
  • How do you find every cached answer that used the old document?
  • What if two versions must coexist (policy by region)?

Scenario: one enterprise customer's batch job makes everyone's chat slow

A tenant starts summarising 2 million documents through the same API that powers your chat product. Chat TTFT p95 goes from 0.8 s to 9 s.

Weak answer: "Add more GPUs."

Strong answer: separate the workloads. Enforce per-tenant TPM and concurrency caps; move bulk work to a batch API with its own queue that only fills spare capacity (or a separate pool), with priority scheduling so interactive requests always admit first; shed batch traffic when interactive queue wait crosses the TTFT target. Then right-size: batch jobs can use bigger batches and higher TPOT, interactive pools keep smaller batches. Bill and report batch usage separately.

Likely follow-ups
  • How do you guarantee the batch job still finishes by a deadline?
  • Would you ever pre-empt a running batch sequence?
