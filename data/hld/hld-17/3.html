Batching and PagedAttention

Because decode is memory-bound, the trick is to read the weights once and use them for many requests. That is batching. Databricks measured a single A100 serving MPT-7B: batch size 64 gave about 14x the throughput of batch size 1, while per-user latency went up about 4x. Batching is a throughput-versus-latency dial.

Static vs continuous batching

With static batching the server waits for a group of requests, runs them together, and keeps the batch fixed until every request finishes. A 20-token answer waits for a 1,000-token answer in the same batch, and its GPU slot sits idle. Continuous batching (the Orca paper calls it iteration-level scheduling) re-forms the batch after every decode step: finished sequences leave, waiting ones join.

The Anyscale numbers come from OPT-13B on one A100 40 GB, compared with naive static batching. The exact multiplier depends on how much output lengths vary: the more they vary, the more static batching wastes.

PagedAttention: virtual memory for the KV cache

Continuous batching moves the bottleneck to memory. Older servers reserved one contiguous KV region per request, sized for the maximum possible output length. Most requests never use that space. The vLLM team reported that existing systems wasted 60% to 80% of KV memory to fragmentation and over-reservation.

PagedAttention (the vLLM paper) splits the KV cache into small fixed-size blocks, allocates them on demand, and keeps a per-request block table that maps logical token positions to physical blocks anywhere in GPU memory. Waste falls to under 4% (only the last, partly filled block). More free memory means bigger batches, which means more throughput: the paper reports 2-4x over FasterTransformer and Orca at the same latency, and the vLLM blog reports up to 24x over plain Hugging Face Transformers.

From your world

This is exactly the kernel's virtual memory: block table = page table, KV block = page frame, sharing a prefix block = two processes mapping the same read-only page, and copy-on-write when one of them diverges (vLLM uses this for parallel sampling, cutting memory up to 55%). The vLLM authors say outright that the design comes from OS paging. If you can explain mmap and page tables, you can explain PagedAttention.
