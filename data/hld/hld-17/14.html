Quick quiz

Why is the decode phase of LLM inference usually slow per token?

  1. It is compute-bound on huge matrix-matrix products
  2. It waits for the network between tokens
  3. Each step reads all weights and the KV cache from memory to make one token per sequence
Decode is memory-bandwidth bound: lots of bytes moved for little maths per step. That is why batching (one weight read, many sequences) helps so much.

A 13B model on a 40 GB GPU leaves about 14 GB for KV cache at about 1 MB per token. Roughly how many 2,048-token sequences fit?

  1. About 70
  2. About 28
  3. About 7
14 GB / (2,048 x 1 MB) is about 7. Anyscale gives the same figure.

What does continuous batching change compared with static batching?

  1. Sequences can leave and join the batch after every decode step
  2. All requests are padded to the same length
  3. Each request gets its own GPU
Iteration-level scheduling refills slots as soon as a sequence ends, so short requests do not wait for long ones.

Your system prompt begins with the current timestamp. What breaks?

  1. Nothing, timestamps are ignored
  2. The vector index
  3. Prefix caching: the prefix differs on every request, so it never hits
Prefix caches need an exact token prefix match. Put stable content first and changing content last.

Why do LLM APIs limit tokens per minute and not only requests per minute?

  1. Tokens are easier to count than requests
  2. Cost and GPU work scale with tokens; one big prompt can cost as much as thousands of small ones
  3. Requests are encrypted
Request counts hide the real cost. Limit tokens and concurrency, reserving max_tokens at admission.

You switch to a new embedding model. What must happen to the vector index?

  1. Re-embed the corpus (often into a second index) and cut over after evaluation
  2. Nothing, vectors are compatible
  3. Only new documents need the new model
Vectors from different models live in different spaces. Store the model version and migrate with a dual index.

Which is the main risk of a semantic cache?

  1. It uses too little memory
  2. A false hit returns the answer to a different but similar-looking question
  3. It cannot be shared across servers
Similarity is not identity ("cancel my order" vs "cancel my subscription"). Use strict thresholds, tenant scoping and only safe traffic.
