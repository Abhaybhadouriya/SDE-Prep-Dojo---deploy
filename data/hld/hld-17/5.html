Embeddings and vector databases

An embedding is a fixed-length array of numbers that a model produces for a piece of text (or an image, a user, a product). The model is trained so that similar things land close together. "How do I get my money back?" and "refund policy" end up near each other even though they share no words. Closeness is measured with cosine similarity (angle between vectors), dot product, or Euclidean distance.

Finding the exact nearest neighbours means comparing the query with every vector: for 1M vectors of 1,536 dimensions that is 1M x 1,536 = about 1.5 billion multiply-adds (about 3 billion floating-point operations) per query. So vector databases use approximate nearest neighbour (ANN) indexes, trading a little recall (the fraction of the true top-k you actually return; 95% is a common target) for a lot of speed. You tune three things against each other: recall, latency and memory.

From your world

HNSW's layers are a skip list in many dimensions, and the descent is like hierarchical routing: a backbone hop gets you to the right region, then local hops get you to the host. IVF (below) is like first matching the longest prefix to pick a few buckets, then scanning only those buckets.

System design concerns

  • It is an index, not the source of truth. Keep documents in a normal database or object store; the vector store holds IDs, vectors and filter metadata. It is rebuildable.
  • Filtering. "Top-5 similar chunks that this user may see." Post-filtering can return fewer than k results; pre-filtering can bypass the index. Engines differ (pgvector lets the planner choose; Elasticsearch and Pinecone filter during graph traversal). For multi-tenant RAG, a namespace or shard per large tenant avoids leaking data through a weak filter.
  • Writes. HNSW inserts are expensive, so many systems keep a small "hot" index for fresh data plus a large "cold" one, query both, and merge; then rebuild periodically. Updates are delete + insert with tombstones; HNSW over 10M vectors can take an hour or more to build.
  • Sharding. Shard by document ID (scatter the query to all shards, merge top-k) or by tenant (query one shard). Replicate for read throughput. Same trade-offs as any search index.
  • Model version. Vectors from two embedding models are not comparable. Store the model version with each vector; migrating means re-embedding everything, usually with a dual index during the switch.
  • Choice. Start with an extension you already run (pgvector, Elasticsearch kNN, Redis). Hello Interview suggests considering a purpose-built engine (Milvus, Qdrant, Weaviate, Pinecone) above roughly 100M vectors. More on storage choices in Choosing Storage and Specialized Indexes.
