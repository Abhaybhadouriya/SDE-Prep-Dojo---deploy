L4 vs L7 load balancing

The layer numbers are the OSI layers you know. An L4 load balancer looks only at the IP and TCP/UDP headers (the 5-tuple). It picks a backend once per connection and then forwards every packet of that connection to the same backend. An L7 load balancer terminates the TCP (and usually TLS) connection, reads the HTTP request, picks a backend per request, and opens or reuses a separate connection to that backend.

The gRPC trap: gRPC runs over HTTP/2, which keeps one long TCP connection and multiplexes many calls on it. Put an L4 balancer in front and every call from a client sticks to whichever backend got the connection, so new pods get no traffic. Fix it with an L7 (HTTP/2-aware) balancer, a service mesh sidecar like Envoy, or client-side load balancing. This is a favourite follow-up for anyone who says "gRPC between services".

Hello Interview's rule of thumb matches what you would guess from the table: round robin or random for stateless services, least connections for persistent connections like WebSockets and SSE.

Health checks, stickiness and draining

  • Health checks: an L4 check only proves the port accepts a TCP connection. An L7 check calls something like GET /healthz and expects a 200. A good health endpoint checks the process can do real work, but not every dependency, or one slow database marks the whole fleet unhealthy at once.
  • Sticky sessions: a cookie or IP hash keeps a user on one server. It makes servers stateful and hurts balancing; prefer stateless servers with the session in Redis.
  • Connection draining: when you remove a server (deploy, scale-in), stop sending new connections and let existing ones finish for a grace period. Kubernetes does the same with a pod's terminating state and preStop; see Deployments & rollouts.
  • The LB is not a single point of failure if you run it as a fleet: an active-passive pair sharing a virtual IP (VRRP or keepalived), or an active-active fleet behind ECMP and anycast.

From your world

An L4 LB is essentially DNAT with a conntrack table. The Kubernetes Service does exactly this with iptables or IPVS rules on every node (see Services & cluster networking). Direct server return (DSR) is the trick where the LB rewrites only the destination MAC, the backend owns the VIP on a loopback interface, and replies go straight back to the client, so the LB only sees the small inbound half of the traffic. Google's Maglev paper describes a software L4 balancer on commodity Linux servers, fed by ECMP from routers, using consistent hashing plus connection tracking so that a machine failure moves as few connections as possible. Google says it has run in production since 2008 and one machine can saturate a 10 Gbps link with small packets.
