HTTP/1.1 vs HTTP/2 vs HTTP/3 (QUIC)

Your TCP knowledge makes this section short. The whole story of HTTP versions is: stop paying for handshakes, and stop one lost packet from blocking everything.

Where HTTP/1.0 fits: in HTTP/1.0 (RFC 1945, 1996) the server closes the TCP connection after every response unless both sides opt in to a non-standard Connection: keep-alive extension. So a page with 30 images paid for 30 TCP handshakes (and 30 TLS handshakes over HTTPS), and every new connection started again in TCP slow start. HTTP/1.1 made persistent connections the default and made the Host header mandatory, which is what lets one IP address serve many websites. You will still meet HTTP/1.0 in old health-check scripts and some load-balancer probes.

# Same two requests, forced to HTTP/1.0 and then HTTP/1.1 (watch the connection lines)
curl -sv --http1.0 -o /dev/null https://example.com/ -o /dev/null https://example.com/ 2>&1 | grep -E "Connected|shutting down connection|Re-using|left intact|^> GET"
curl -sv --http1.1 -o /dev/null https://example.com/ -o /dev/null https://example.com/ 2>&1 | grep -E "Connected|shutting down connection|Re-using|left intact|^> GET"
# HTTP/1.0: two connections, two TCP + TLS handshakes
* Connected to example.com (104.20.23.154) port 443
> GET / HTTP/1.0
* shutting down connection #0
* Connected to example.com (104.20.23.154) port 443
> GET / HTTP/1.0
* shutting down connection #1
# HTTP/1.1: the second request re-uses connection #0
* Connected to example.com (104.20.23.154) port 443
> GET / HTTP/1.1
* Connection #0 to host example.com left intact
* Re-using existing connection with host example.com
> GET / HTTP/1.1
* Connection #0 to host example.com left intact

Exact wording differs a little between curl versions, and the IP address will differ for you, but the pattern (a new "Connected" line per request versus "Re-using existing connection") is the whole lesson.

Cloudflare's HTTP/3 history post explains the key point clearly: to TCP, an HTTP/2 connection is just one byte stream, so a single lost packet holds back every stream behind it. QUIC makes streams a transport concept, so only the affected stream waits. Cloudflare's 0-RTT post gives the round trip counts: a page load over a new connection costs 4 RTT plus DNS with TLS 1.2 and 3 RTT with TLS 1.3, and a resumed TLS 1.3 connection with 0-RTT gets that down to 2 RTT (all counted over TCP, including the HTTP request itself).

0-RTT can be replayed. Early data is sent before the handshake proves freshness, so an attacker can copy and resend it. Cloudflare only answers GET requests without query parameters over 0-RTT, and adds a header so the origin can spot replays. In design terms: 0-RTT is fine for idempotent reads, never for "place order". This links straight to idempotency keys.

From your world

HTTP/2 over TCP is like putting many flows into one strict-FIFO ring buffer: one stuck descriptor blocks everyone behind it. QUIC gives each stream its own reassembly queue, like per-flow queues on a NIC. QUIC also lives in user space (not the kernel TCP stack), which is why it could evolve fast, and why it costs more CPU per byte than kernel TCP with offloads. Middleboxes that drop or rate-limit UDP are the main reason clients always keep an HTTP/2 fallback.

Interview rule: say "HTTP/2 between services (often gRPC), HTTP/1.1 or HTTP/2 from browsers, HTTP/3 at the CDN edge for mobile users". You rarely need more. Hello Interview's networking guide notes that most interviewers will not require HTTP/3, so mention it when the question is about mobile latency or video start-up, not by default.
