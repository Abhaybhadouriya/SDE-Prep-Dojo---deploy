Interview questions

What happens when you type a URL into a browser and press Enter?

The browser checks its caches, then the OS asks a recursive resolver, which walks root, TLD and authoritative servers (or answers from cache) to get an IP. The client opens a TCP connection (or QUIC over UDP), does a TLS handshake (1 RTT with TLS 1.3), and sends an HTTP request. At a big site the IP is an anycast or GeoDNS address of a CDN edge, which serves cached content or forwards to the origin region. There an L4/L7 load balancer picks a healthy server, often through an API gateway that checks auth and routes by path. The server builds a response, maybe from a cache or DB, and it comes back; the browser parses HTML and fetches more resources over the same multiplexed connection.

How to answer

Walk the layers in order and stop for 10 seconds at each: DNS, transport and TLS, edge/CDN, LB, gateway, app, render. Then offer to go deep on any one: "I can go deeper on DNS caching, TLS 1.3, or how the LB picks a server". Your networking background is the differentiator here; show it in the TCP and TLS parts.

Likely follow-ups
  • How many round trips before the first byte? (Count them.)
  • What changes with HTTP/3?
  • Where would you cache, and for how long?
What is the difference between a reverse proxy, a load balancer and an API gateway?

All three are reverse proxies in front of servers. A plain reverse proxy fronts and shields servers (TLS termination, caching, compression), and is useful even with one server. A load balancer spreads traffic across many identical replicas and removes unhealthy ones. An API gateway is API-aware: it routes different paths to different services and centralises cross-cutting concerns like authentication, rate limiting, API keys and request validation. One product (NGINX, Envoy) can do all three; I separate them by job.

How to answer

Give the "whose side, how deep it reads" framing, then one example each, then say how you draw them in a design (usually one box "LB + gateway" unless asked).

Likely follow-ups
  • What is a forward proxy then?
  • Would you put a gateway in front of a monolith?
  • Where does the rate limiter live?
When would you choose an L4 load balancer over an L7 one?

L4 when I need raw throughput and protocol independence: long-lived WebSocket or TCP connections, non-HTTP protocols (databases, MQTT, game UDP), TLS passthrough, or as the first tier in front of L7 proxies. L7 when routing depends on content (path, host, header, cookie), when I want per-request balancing of HTTP/2 or gRPC, retries, header rewrites, WAF, or auth at the edge. Large sites use both: an L4 tier (ECMP, anycast, Maglev-style) spreading connections over a fleet of L7 proxies.

How to answer

State the unit of balancing (connection vs request) first; every other difference falls out of that. Close with the two-tier architecture.

Likely follow-ups
  • Why does gRPC break with L4 balancing?
  • How does an L4 balancer keep a connection on the same backend when the LB fleet changes?
  • What is direct server return?
Design the load balancing tier for a service taking 1M requests per second across three regions.

Region selection by latency-based DNS (or anycast) with health-checked failover. In each region, routers ECMP flows to a fleet of stateless L4 balancers that share a VIP; they use consistent hashing on the 5-tuple plus a local connection table, so adding or losing an L4 node moves few connections (the Maglev approach). The L4 tier spreads connections over an autoscaled L7 proxy fleet (Envoy/NGINX) that terminates TLS, does path routing, retries with budgets, and least-request balancing to services. Health checks at both tiers; connection draining on deploys; per-tier capacity headroom of about 30-50% so a region can absorb a failed neighbour.

How to answer

Layer it: global (DNS/anycast), regional L4, L7, service. For each layer say how it scales and how it fails. Mention that no single LB box exists; it is a fleet.

Likely follow-ups
  • What happens to open connections when an L4 node dies?
  • How do you avoid a retry storm when one backend is slow?
  • How long does a region failover take, and what decides that?
Why is DNS-based failover slow, and what do you do about it?

Answers are cached at every layer for the TTL, some resolvers and clients cache longer than the TTL, and DNS has no idea about load. So after a region dies, some users keep going there for minutes. Mitigations: low TTLs (30-60 s) on the region record, health-checked DNS, anycast IPs whose routes withdraw in seconds, global L4/L7 load balancers with a single anycast VIP, and clients that retry against a second endpoint.

How to answer

Name the cause (caching and TTL), then the trade-off (lower TTL means more DNS queries), then the stronger tool (anycast or a global LB).

Likely follow-ups
  • What does GeoDNS actually see about the user?
  • Active-active or active-passive across regions?
Where would you terminate TLS in an e-commerce system, and why?

At the CDN edge and the regional L7 balancer for performance and features (WAF, routing, caching), then re-encrypt inside with mTLS for anything carrying payment or personal data, typically via a service mesh. For card data under PCI rules I would keep the payment service on its own encrypted path, possibly passthrough, so fewer components hold keys or see plaintext.

How to answer

Give the three options (terminate, re-encrypt, passthrough), choose per data class, and mention the cost: double crypto and certificate rotation.

Likely follow-ups
  • How do certificates get rotated across 500 services?
  • What is SNI and why does an L4 LB care?
Explain HTTP/2 vs HTTP/3. When does HTTP/3 actually help?

HTTP/2 multiplexes many streams over one TCP connection with binary framing and header compression, but a lost TCP segment stalls all streams (TCP head-of-line blocking). HTTP/3 runs over QUIC on UDP: streams are independent at the transport layer, the transport and TLS 1.3 handshakes are combined (1 RTT, 0-RTT on resume), and connections survive IP changes using connection IDs. It helps most on lossy, high-latency, mobile networks and for user-facing startup latency; inside a data centre with near-zero loss, HTTP/2 is fine.

How to answer

Tell it as a story of removing round trips and removing head-of-line blocking. Mention the cost: user-space crypto, UDP blocked on some networks, so keep a fallback.

Likely follow-ups
  • Why is 0-RTT dangerous for POST?
  • Why did QUIC go into user space instead of the kernel?
How does a CDN decide what to cache, and how do you update content safely?

The origin tells it with Cache-Control headers; the cache key is usually the URL plus a few chosen headers. Pull CDNs fetch on the first miss; push CDNs are pre-loaded. To update safely, use content-hashed or versioned URLs so a change is a new object, and use purges only as an emergency tool. An origin shield tier collapses misses from many POPs into one origin request; request coalescing at each POP stops a stampede on a hot object.

How to answer

Cover: what is cacheable, cache key, TTL, invalidation, origin protection. Mention user-specific data must be private.

Likely follow-ups
  • How would you serve paid videos only to subscribers? (Signed URLs.)
  • Would you cache API responses at the CDN?
You have 2 million WebSocket connections. How do you load balance them and deploy new code?

An L4 (or WebSocket-aware L7) balancer with least-connections spreads new connections over connection servers sized for a known number of sockets each. A registry (Redis) records user to server, so other services can push to the right box, as Netflix's Zuul Push does. Deploys: mark a server draining, stop new connections, send clients a "reconnect" message in batches with jitter, so 2 million clients do not reconnect in the same second. Clients reconnect with exponential backoff and resume from their last message ID.

How to answer

Separate the three problems: placing new connections, finding an existing connection, and moving connections during deploys and failures.

Likely follow-ups
  • Why does round robin go wrong after a deploy? (New servers stay empty.)
  • How many connections can one server hold, and what limits it (file descriptors, memory per socket, ephemeral ports at the LB)?
What is a backend-for-frontend, and when would you not use one?

A BFF is a thin API layer per client type (mobile, web, partner) that aggregates and shapes calls to generic services, so a phone gets one small response instead of making many calls. Skip it when there is a single client type, a monolith, or a small team, because each BFF is another service to deploy and keep in sync. GraphQL can replace several BFFs with one flexible schema.

How to answer

Define it, give the mobile example, give the cost, give the alternative.

Likely follow-ups
  • Who owns the BFF, the app team or the platform team?
  • How do you stop business logic leaking into it?
How do you stop the load balancer or gateway from being a single point of failure?

Never run one box. Options: an active-passive pair sharing a virtual IP with VRRP/keepalived (seconds of failover), an active-active fleet behind router ECMP with consistent hashing so a lost node moves only its share of flows, multiple regions behind DNS or anycast, and keep gateways stateless so any instance can serve any request (rate-limit counters live in Redis, not in the gateway's memory). Also protect against config mistakes: staged config rollout, because a bad route table pushed to every gateway at once is a global outage.

How to answer

Go from box, to pair, to fleet, to multi-region. End with "config is the most likely cause of a gateway outage".

Likely follow-ups
  • What breaks in active-passive during a split brain?
  • How do you test failover regularly?

Scenario: new pods get no traffic

Your team moved internal calls from REST to gRPC. After a scale-up from 4 to 12 pods of the pricing service, CPU on the 4 old pods stays at 90% and the 8 new pods are nearly idle. The Kubernetes Service is a normal ClusterIP.

Weak answer: "Increase the replicas more" or "restart the service".

Strong answer: ClusterIP is L4 (iptables/IPVS) and balances connections. gRPC clients keep one long HTTP/2 connection and multiplex every call on it, so calls stay glued to the old pods. Fix: L7 balancing of HTTP/2 requests (Envoy sidecar or mesh), or client-side load balancing with a headless Service so the client sees every pod IP, plus a max connection age on the server so clients reconnect and rebalance periodically.

Likely follow-ups
  • What is a headless Service?
  • Would the same thing happen with WebSockets? (Yes; least-connections for new ones, and planned reconnects.)

Scenario: the region is down but users still go there

Your API runs in two regions with DNS round robin. Region A fails. Monitoring shows 40% of users still hitting region A ten minutes later.

Weak answer: "DNS will fix itself eventually."

Strong answer: resolvers and clients cache the old answer for the TTL, and some longer. Short term: remove A from DNS, reduce the TTL, and make clients retry the other region on connection failure. Long term: health-checked DNS failover with a 30-60 s TTL, or a single anycast VIP / global load balancer so failover is a routing change measured in seconds, and plan capacity so region B can take 100% of the load.

Likely follow-ups
  • What is the cost of a 10-second TTL?
  • How do you avoid the recovered region getting a thundering herd?

The 60-second answer. "When I draw the front door of a design, I say: DNS (latency-based, short TTL) picks the region, an anycast CDN edge terminates TLS close to the user and serves cacheable content, and a regional L7 load balancer plus API gateway checks the token, applies rate limits and routes by path to the service pools. I use L4 for long-lived WebSocket or raw TCP traffic, least-connections for those fleets, and re-encrypt with mTLS inside for payment data. Failover is fast at the LB layer and slow at the DNS layer, so I keep DNS TTLs short and plan headroom in the other region."
