The API gateway and backend-for-frontend

Hello Interview's API gateway deep dive gives the request lifecycle in six steps: validate the request, run middleware (auth, rate limits), route it, let the backend process it, transform the response, and optionally cache it. Click through the same flow below.

  1. Validate. Reject malformed URLs, missing headers or oversized bodies before they cost anything.
  2. Authenticate. Check the token (often a JWT signature check, no network call) and attach the user ID for downstream services.
  3. Rate limit. Count requests per user or API key, usually in Redis. See Distributed rate limiter.
  4. Route. Map path and method to a service, discovered through a registry or Kubernetes DNS. This is the core job, and the one candidates forget to say.
  5. Transform. Translate formats if needed (REST outside, gRPC inside), strip internal headers, compress.
  6. Fail fast. Bad token gives 401, too many requests gives 429, all without touching a backend.

Gateways are usually stateless, so they scale horizontally behind an L4 or L7 load balancer, with one gateway fleet per region and GeoDNS sending users to the nearest region.

Backend-for-frontend (BFF)

A phone app wants small responses and few round trips; a web dashboard wants rich data; a partner API wants stability. A BFF is a thin gateway per client type that calls several services and assembles exactly what that client needs. It keeps the services generic and stops the phone making seven calls over a slow mobile link. The price is more code to own; GraphQL is often used as a BFF (see API styles).

Real-world: Netflix Zuul

Netflix's edge gateway is Zuul. Its wiki describes using filters for "surgical routing" (sending one customer's or one device's traffic to a debug cluster), for gradually ramping load onto a small cluster to find its breaking point, and for shedding and prioritising traffic during incidents. Netflix also built Zuul Push on the same stack for WebSocket and SSE notifications; an InfoQ report of Netflix's QCon 2018 talk gives more than 5.5 million connected clients at peak, with a Redis/Cassandra-backed push registry recording which server holds which client connection, and Kafka decoupling senders from that registry. That "registry of who is connected where" is the same idea you will use in chat and real-time updates.

Why have a gateway
  • Clients see one host; internal layout can change freely
  • Auth, rate limits, logging done once, not in 40 services
  • Canary and surgical routing at the edge
  • Protocol translation (REST to gRPC)
What it costs
  • Extra hop (usually a few ms)
  • A shared component every team depends on: config errors take everything down
  • Can grow into a "smart pipe" full of business logic; keep logic in services
  • Not needed for a monolith with one client
