DNS: the internet's phone book

DNS (Domain Name System) maps names to records. The common records are A (IPv4 address), AAAA (IPv6 address), CNAME (an alias to another name), NS (which servers are authoritative for a zone), MX (mail servers), TXT (free text, used for domain verification and email security) and SRV (host and port of a service).

A lookup that misses every cache walks a tree. Click through it.

  1. Ask. The OS stub resolver checks its own cache, then asks a recursive resolver (your ISP's, or a public one).
  2. Root. On a cold cache the resolver asks a root server. The root does not know the answer; it refers the resolver to the .com servers.
  3. TLD. The .com top-level-domain servers refer it to the authoritative name servers for example.com.
  4. Authoritative. The authoritative server owns the zone and gives the real record.
  5. Answer. The resolver returns the A record plus a TTL to the client.
  6. Cache. Every layer caches the answer until the TTL runs out. This is why DNS is fast on average and slow to change.

Karan Pratap Singh's system design book lists the same eight-step resolution and notes that there are 13 root server identities, each copied many times around the world using anycast. So even the root of DNS is a load-balanced, anycast service.

DNS as the first load balancer

Managed DNS (Route 53, Azure Traffic Manager, Cloudflare, NS1) can return different answers to different users. The system design primer lists three routing styles you should name:

DNS routing policyWhat it doesUse it for
Weighted round robinReturns IPs in a rotating order, or by weights (90/10)Spreading load, canary or A/B tests, draining a cluster for maintenance
Latency-basedReturns the region with the lowest measured latency to the resolverMulti-region APIs
Geolocation (GeoDNS)Returns an answer based on where the resolver isData residency (EU users to EU), language, licensing
Failover (health-checked)Stops returning a region whose health check failsActive-passive disaster recovery

Careful: DNS failover is only as fast as the TTL, and some resolvers and clients ignore short TTLs. Hello Interview's networking guide puts it simply: record changes cannot propagate faster than the TTL. DNS also does not know if a server is busy, only whether a health check passed. Use DNS to pick a region, and a real load balancer to pick a server.

Two more DNS facts that show up in designs:

  • The resolver's location is not the user's location. GeoDNS sees the recursive resolver's IP. A user in Mumbai using a public resolver may be "seen" somewhere else. The EDNS Client Subnet extension passes part of the client IP to fix this.
  • DNS is an attack target. The primer notes that DDoS attacks on DNS providers have taken sites offline even though their servers were fine. Large services use two DNS providers.
  • The web crawler needs its own caching DNS resolver, because crawling billions of pages means billions of lookups.

Anycast: one IP, many places

With unicast, one IP lives in one place. With anycast, the same IP prefix is announced over BGP from many data centres, and the internet's routing sends each packet to the "nearest" one in BGP terms. Cloudflare's anycast primer shows a traceroute dropping from about 50 ms (a unicast origin) to about 9.5 ms (the nearest anycast site in San Jose) for the same site. It also lists the two big wins: if one site dies, routes withdraw and traffic flows to the next-nearest one, and a DDoS attack gets split across every site instead of landing on one.

From your world

You have configured this. Anycast is plain BGP: the same prefix originated from several POPs (points of presence: edge data centres in many cities, each with its own routers and servers). Inside a POP, routers then use ECMP (equal-cost multipath, hashing the 5-tuple) to spread flows across many load balancer machines that all own the same VIP. The classic worry is a route change in the middle of a TCP connection sending packets to a different POP that has no state for it. That is why anycast is perfect for short UDP DNS queries and works well for TCP in practice when routes are stable, and why big operators add connection tracking or consistent hashing behind the ECMP layer.
