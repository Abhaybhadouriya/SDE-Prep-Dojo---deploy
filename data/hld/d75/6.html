2. The latency budget

  • Segment duration is the biggest knob. A player must buffer at least one segment; with 6 s segments and a 3-segment buffer you are 18 s+ behind.
  • LL-HLS (Apple) adds partial segments, blocking playlist reload (the server holds the request until the next part exists, so no polling delay) and preload hints for the next part. LL-DASH uses CMAF chunks with chunked transfer. Both keep HTTP and CDN caching.
  • WebRTC gets sub-second latency but is peer-connection based and much harder to fan out through ordinary CDNs - use it for co-streaming or calls (see Zoom), not for 50M viewers.
  • Twitch's reported path: about 15 s, then 10 s, then about 3 s with low-latency HLS, and 1.5 s in some regions.
  • Trade-off: lower latency = smaller buffer = more rebuffering on bad networks. A cricket app may choose ~5-10 s for smoothness; Twitch chooses ~3 s for chat interaction.

3. Real-time transcoding and the ABR ladder

  • Decode once, encode many: one process takes the source and produces each rendition, keeping keyframes aligned across renditions so the player can switch at segment boundaries.
  • Example ladder (illustrative): 1080p 6 Mbps, 720p 3 Mbps, 480p 1.5 Mbps, 360p 0.8 Mbps, 160p 0.3 Mbps, plus audio-only.
  • Capacity is the cost centre. Twitch said transcoding was once offered to only 2-3% of channels, and that a hardware transcoder gave 10x capacity at 2x the cost. Design answer: transcode popular or partner channels fully; give others source quality only, or a short ladder; use GPUs/ASICs for density.
  • Redundancy for big events: two encoders in different locations producing identical, time-aligned outputs; the packager or player fails over between them. A cricket final has no "retry later".
  • Scheduling transcoders is a bin-packing problem: a stream must stay on one transcoder for its life, so route new streams to origins with headroom rather than moving running ones.

4. CDN fan-out and the origin

  • Request coalescing at edge and shield is what stops a thundering herd when a new segment appears and 300K players ask for it in the same 100 ms.
  • Cache key must not include the token; otherwise every viewer is a cache miss. Validate the signed cookie at the edge, then look up by path only.
  • Short TTL for playlists (they change every part), long TTL for segments (immutable once written).
  • Multi-CDN steering by real-time QoE (rebuffer rate, throughput) per region and ISP; ISP-embedded caches for the biggest events.
  • Twitch's ingest blog describes nearly 100 PoPs on a private backbone feeding origin data centres - the same shape: many edges, few origins.

5. Subscriptions and secure, expiring playback links (the Oracle question)

  1. Subscribe writes an entitlement row (SQL, after payment). Push the entitlement into a per-user cache so playback never hits the payment DB.
  2. "Dynamically generated link" = at play time, the playback API checks the entitlement, device count and region, and signs a policy: path prefix /live/match123/*, expiry now + 10 min, optionally the client IP range. CloudFront calls these custom policies; other CDNs use token auth with an HMAC.
  3. Expiry is short so a leaked link dies quickly. The player refreshes before expiry; a revoked or expired subscription simply fails the refresh.
  4. Anti-sharing: limit concurrent playback sessions per account (session table with TTL, refreshed by heartbeats); bind tokens to a device id; for premium sports add DRM licence checks and forensic watermarking.
  5. At match start do not make 30M users all hit the API in the same second: issue tokens when users open the match page before the start, add jitter to refresh times, and keep the playback API stateless behind a cache.

6. The match-start spike (Hotstar lessons)

  • Reactive autoscaling is too slow for a wall of users in minutes. Scale ahead of the schedule (match start, toss, innings break) from traffic forecasts, and keep a buffer.
  • Scale infrastructure in steps. ByteByteGo's write-up of Disney+ Hotstar's 2023 preparation reports Kubernetes API-server throttling past about 400 nodes added at once, fixed by scaling in steps of 100-300 nodes, and a move to six EKS clusters.
  • Push cacheable APIs to the CDN. The same write-up says they split cacheable APIs (scorecards, highlights) onto a CDN domain and slightly reduced refresh rates of features like scorecards. Every request the CDN answers is one your services never see.
  • Degrade gracefully. Under extreme load turn off non-essential features (recommendations, personalised rails, high-frequency reactions) before anything touches playback. Cap the default bitrate if the CDN is near capacity.
  • Login storms: long-lived sessions so returning users do not log in again; a waiting room / admission token if the auth service is the limit.
  • The 2019 record was 25.3M concurrent; the 2023 final hit 59M (ICC figure) - plan for the next record, not the last.

7. Concurrent-viewer counter: read fan-out vs write fan-out (JioHotstar)

The interviewer focused on read fan-out vs write fan-out. Frame it like a feed (see Fan-out: push vs pull):

  • Write side: 50M viewers x 1 heartbeat / 30 s = ~1.7M/s. Never send these to one key. Aggregate per edge or region (count sessions seen in the last 60 s per stream), then sum globally every few seconds. This is the sharded-counter idea from d39; for unique viewers use HyperLogLog sketches that merge across regions.
  • Write fan-out (push): the counter pushes the new number to every viewer over WebSockets. 50M pushes every 5 s = 10M messages/s just to update a number. Expensive.
  • Read fan-out (pull): publish the number as a tiny cacheable object (/streams/123/count.json, TTL 5 s) on the CDN; players poll it. 50M / 5 s = 10M requests/s, but almost all are CDN hits - the origin sees a handful.
  • Hybrid: piggyback the count on something players already fetch (the playlist or a periodic metadata response) - zero extra requests. Approximate and a few seconds stale is acceptable; say so.
  • Leaving: a viewer who closes the app sends nothing, so count "heartbeat in the last N seconds", not joins minus leaves.
