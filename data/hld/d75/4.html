Data model and storage

DataShapeStoreWhy
Channels, matches, tournamentschannel(id, owner, title, category), match(id, tournament_id, starts_at, status, stream_id)SQLRelational, low write rate, heavily cached.
Stream sessionsstream(id, channel_id, ingest_pop, origin, state, started_at, ladder)SQL + cacheControl plane looks up where a stream lives.
Stream keyshash(stream_key) -> channel_idKVIngest auth must be a fast point lookup.
Subscriptions / entitlements(user_id, product_id) -> valid_from, valid_until, planSQL (truth) + KV cache per userMoney: ACID writes; reads at 50K/s served from cache.
Playback sessions(user_id, device_id) -> stream_id, last_seen with TTLRedis / DynamoDB TTLConcurrent-device limits, viewer counting.
Segments and manifests/live/{stream}/{rendition}/{seq}.m4sOrigin storage (memory/SSD) then S3 for VODLive segments are short-lived; VOD keeps them.
Viewer countsstream_id -> count, as_ofRedis, pushed to edge cacheApproximate is fine; must be cheap to read.

The Zepto prompt asked for the "DB architecture". The key point: video never touches the database. Databases hold catalog, entitlement and session state; segments live on origin servers and object storage. Entitlement is the only money-path table and stays relational.
