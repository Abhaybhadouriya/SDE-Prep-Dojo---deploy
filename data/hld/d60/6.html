Deep dives

1. Storing passwords and surviving credential stuffing

  • Never encrypt passwords; hash them with a slow, salted, memory-hard function. OWASP's current guidance: Argon2id with at least m = 19 MiB, t = 2, p = 1; if unavailable, scrypt (N = 217, r = 8, p = 1); bcrypt only for legacy, with work factor 10 or more and a 72-byte input limit; PBKDF2-HMAC-SHA256 with 600,000 iterations when FIPS-140 is required.
  • Salt per password (libraries do it for you, and store it inside the hash string). Optionally a pepper: one secret kept outside the database (in a vault or HSM), so a database-only leak is not enough to start cracking.
  • Store the parameters with the hash (Argon2 strings do), so you can raise the cost later and re-hash each user at their next successful login.
  • Password rules from NIST SP 800-63B-4: minimum 15 characters for password-only accounts (8 if used only with MFA), allow at least 64, no composition rules ("one uppercase, one symbol"), no forced periodic changes, and check every new password against a list of breached and common passwords. Allow paste and password managers.

Credential stuffing is the main attack: bots try email/password pairs leaked from other sites, millions per hour, spread over many IPs. Defences, in layers:

  1. Rate limit by several keys. Per account (slow down after a few failures), per IP and per IP range, per device fingerprint. Use the token-bucket designs from Rate Limiter. NIST caps consecutive failures per authenticator at 100 before it is disabled - an upper bound; most products throttle much earlier.
  2. Prefer throttling over hard lockout. A hard lockout lets an attacker lock out any user on purpose (a denial of service). Add increasing delays and a risk-based step-up (ask for MFA or a challenge) instead.
  3. Breached-password checks at login too. If a user's password appears in a known breach corpus, force a reset.
  4. MFA. Even a correct password is not enough.
  5. Constant-time comparisons and equal-time failures. Hash a dummy password when the email is unknown, so response time does not reveal which emails exist.

From your world

A slow password hash is deliberate CPU and memory cost, like a SYN cookie in reverse: you make the attacker pay. Argon2id's memory hardness matters because attackers crack with GPUs and ASICs that have huge compute but limited fast memory per core; forcing 19 MiB per guess kills their parallelism. Per-IP and per-account rate limits are your ingress policers.

2. Sessions vs JWT - and how to revoke

Opaque session cookies are simple and the right answer for a single web app: a random id with at least 64 bits of entropy (OWASP), the user data kept server-side, a cookie with Secure, HttpOnly, SameSite=Strict or Lax, ideally the __Host- prefix; a new id after login (to stop session fixation); idle timeouts of 2-5 minutes for high-value apps or 15-30 minutes for low-risk ones, plus an absolute timeout. NIST's AAL2 guidance is at most 24 hours overall and 1 hour of inactivity before re-authentication.

JWTs (RFC 7519) are signed JSON: iss, sub, aud, exp, iat, scopes. Any service with the public key can verify one. Rules that prevent the classic bugs:

  • Pin the algorithm (for example RS256 or ES256) on the verifier side; never trust the token's own alg, and reject none.
  • Check iss, aud (a token for the payments API must not work on the chat API), exp with a small clock-skew allowance.
  • Keep tokens small and free of secrets - anyone can base64-decode the payload.
  • Rotate signing keys: publish the next key in JWKS before using it, sign with it, keep the old one until all its tokens have expired.

Refresh-token rotation with reuse detection. RFC 9700 (the OAuth 2.0 Security Best Current Practice) requires refresh tokens for public clients to be either sender-constrained or rotated. Rotation: every refresh returns a new refresh token and invalidates the old one, all within one "family". If an old token is ever presented again, someone copied it - revoke the whole family and force a login. Both the thief and the real user are logged out, but the thief loses access within one access-token lifetime.

The grace window (do not skip this). A legitimate client can also present R1 twice: the refresh response carrying R2 was lost on a flaky mobile network, or two browser tabs refreshed at the same moment. Strict reuse detection would then revoke the family and log out real users at scale. So allow a short reuse window, for example 30-60 seconds: if R1 is presented again inside the window, from the same client and device binding, return the same R2 (and an access token) idempotently, without rotating again. Outside the window, or from a different device fingerprint, treat it as theft and revoke the family. Okta's docs describe exactly this "grace period" after rotation, for the case where new tokens never reach the client. Store previous_refresh_hash and rotated_at next to current_refresh_hash to implement it. The same window also solves the contention of two tabs refreshing at once (see Dealing with Contention): the second request gets the result of the first instead of racing it.

  1. The user refreshes with R1. The service stores "current token of family F is R2" and returns R2 (and a new access token).
  2. An attacker who stole R1 earlier tries to use it.
  3. R1 is not the current token and the short grace window (30-60 s for a lost response or two tabs) has passed, so it was copied. The service revokes the whole family, killing R2 too. The real user logs in again; the thief is out.

Revoking access tokens before they expire. Put the session (family) id in every access token. On "log out everywhere" or an admin kill, add the family id to a denylist with a TTL equal to the access-token lifetime, and publish it (Redis pub/sub or Kafka) so every service's in-memory set updates within a second. The set stays tiny because entries expire after 15 minutes. For the very highest-risk actions (changing a password, moving money), do a live check against the session store anyway - step-up, not every request. Token validation is a classic read-scaling problem: 300k checks a second answered from local caches (public keys and the pushed denylist) rather than one central store. See Scaling Reads.

From your world

An opaque session id is like a file descriptor: a meaningless number that indexes kernel state, so closing it takes effect immediately. A JWT is like a self-contained, signed capability: whoever holds it can use it, and you cannot "close" it remotely - you can only let it time out, the way a cached ARP or DNS entry lives until its TTL. A short TTL plus a small invalidation broadcast is the same trick as a gratuitous ARP.

3. Being an OpenID Connect provider (SSO)

OAuth 2.0 is about authorisation: letting an app act on your data without your password. OpenID Connect (OIDC) adds authentication on top: an ID token (a JWT) that says who logged in. SAML is the older XML-based way, still common in enterprises. For a new web or mobile SSO, use OIDC with the authorization code flow plus PKCE.

  1. The app makes a random code_verifier, sends only its SHA-256 hash (code_challenge, method S256), plus a random state (CSRF protection) and nonce (replay protection).
  2. The browser goes to the identity provider. If the user already has an IdP session cookie, there is no password prompt - that is SSO. Otherwise they log in (and do MFA).
  3. The IdP redirects back only to a pre-registered, exactly matching redirect URI, with a short-lived, single-use code.
  4. The app checks state matches what it sent.
  5. The app exchanges the code at the token endpoint, proving it is the same party with the original code_verifier. A thief who intercepted the code does not have the verifier.
  6. The IdP returns tokens. The app validates the ID token: issuer, audience = its client_id, expiry, nonce and signature (OIDC Core spells out these checks), then creates its own session.

Rules from RFC 9700 worth quoting in an interview: do not use the implicit grant; public clients must use PKCE and servers must support S256; redirect URIs are compared by exact string match; the password grant must not be used (it hands the user's password to the client and blocks MFA); tokens should be audience-restricted and ideally sender-constrained (mTLS or DPoP) so a stolen token is useless on another machine.

Single logout is the hard part of SSO. Logging out of one app does not log you out of the IdP or other apps. Options: OIDC back-channel logout (the IdP calls each app's logout endpoint), front-channel logout (iframes), or simply short app sessions that re-check the IdP silently. Be honest that it is best effort.

4. MFA, passkeys and recovery

FactorPhishing-resistant?Notes
SMS / voice codeNoNIST 800-63B-4 classes it as "restricted": allowed, but offer alternatives and check for SIM swap signals.
TOTP app (6-digit code)NoShared secret, 30-second windows; can be phished in real time by a proxy site.
Push approvalNoWatch for "MFA fatigue" spam; use number matching.
WebAuthn / passkeys (FIDO2)YesPublic-key signature bound to the site's origin, so a look-alike domain gets nothing useful. NIST requires at least one phishing-resistant option at AAL2.

Store only the passkey's public key and its counter. Recovery is usually the weakest link: "forgot password" by email or SMS can undo all your MFA. Use single-use, short-lived, hashed reset tokens; notify the user on every security change; and require a second factor or a waiting period for high-value accounts. Step-up authentication: request a fresh MFA (OIDC acr / max_age) before sensitive actions even inside a valid session.

5. Never the bottleneck: auth at scale

  • Validate at the edge, propagate identity inside. Netflix describes moving authentication and token handling to its edge gateway (Zuul). The edge validates whatever the device sent (cookies, various tokens) and turns it into an internal, integrity-protected identity object called a Passport; client tokens never go past the edge. Inner services only understand one simple, signed format, and changing token formats touches only the edge.
  • Service-to-service: mTLS between services (a service mesh does it automatically) answers "which service is calling"; the propagated user identity answers "on whose behalf".
  • Multi-region. Token verification needs only public keys, so it works in every region even if the central DB is down. Logins and refreshes need the user and session data: replicate them, and accept that a region failover may briefly force some re-logins.
  • Graceful degradation. If the token service is down, existing access tokens keep working until expiry; extend nothing silently. If the hashing pool is overloaded, queue and shed at the edge rather than letting the whole auth service fall over.
  • Keys in an HSM/KMS. The signing key is the crown jewel: whoever has it can mint a token for anyone. Sign inside the KMS, or keep a short-lived signing key in memory that the KMS rotates.

From your world

Edge authentication is a provider-edge router: classify and police at ingress, push an MPLS label or VLAN tag, and let the core switch on the label without re-inspecting the customer's packet. Netflix's Passport is that label for identity - but signed, because unlike your core network, a compromised microservice could otherwise forge it. mTLS between services is the MACsec of the service mesh.
