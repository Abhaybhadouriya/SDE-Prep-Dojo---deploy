Back-of-envelope estimation

Assumptions (state them): 100 million registered users, 20 million daily active, 3 devices each, 500 API calls per active user per day. Password-hash parameters come from the OWASP Password Storage Cheat Sheet. We use 100,000 seconds per day. (Method: Back-of-Envelope Estimation.)

  1. Logins. Most sessions persist, so assume 1 full login per active user per day: 20M/day = 200 logins/s. A morning peak or a mass "log in again" event after an incident: 10x = 2,000/s.
  2. Password hashing cost. OWASP's minimum for Argon2id is 19 MiB of memory, 2 iterations, parallelism 1. Assume one hash takes about 50 ms of one CPU core (benchmark it on your hardware). At 2,000 logins/s: 2,000 x 0.05 = 100 cores just for hashing. Memory in flight: 100 concurrent hashes x 19 MiB = about 1.9 GB. That is the price of making stolen hashes expensive to crack - so size a separate hashing pool for it.
  3. Token validations. 20M x 500 = 10 billion/day = 100,000/s average, about 300,000/s at peak. If each one called a central auth database, that database would need 300k QPS and would be the single point of failure for the company. So validation must be local: verify a signature, or hit a nearby cache.
  4. Refreshes. With 15-minute access tokens and, say, 5 million sessions active at once: 5M x 4 per hour / 3,600 = about 5,500 refreshes/s. That is the real load on the central token service - and it is the moment we can re-check revocation.
  5. Storage. Users: 100M x 1 KB = 100 GB. Sessions / refresh-token families: 100M x 3 devices x 200 bytes = 60 GB. A denylist only needs entries until the access token would expire anyway (15 minutes): a few thousand entries - megabytes.

From your world

This is a control plane / data plane split again. The login and refresh paths are the control plane: slow, central, stateful, a few thousand per second. Token validation is the data plane: 300k/s, must be answered locally like a forwarding lookup in a line card. A line card does not ask the route processor about every packet; a microservice should not ask the auth server about every request.
