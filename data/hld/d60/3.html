Key APIs

Words you need before the endpoints (Level 2).

  • OAuth 2.0: a standard for delegated access. An app gets an access token that lets it call an API on the user's behalf, without ever seeing the user's password. It says nothing, by itself, about who the user is.
  • OIDC (OpenID Connect): an identity layer on top of OAuth 2.0. It adds an id_token, a JWT that says "this is user 42, they logged in at 10:02 with MFA", plus standard endpoints such as /.well-known/openid-configuration and /userinfo. "Sign in with Google" is OIDC.
  • SAML: an older, XML-based SSO standard, still common in enterprises. Same idea as OIDC (the IdP vouches for the user to an app) but with signed XML documents posted through the browser.
  • Authorization code flow: the app sends the browser to the IdP; after login the IdP redirects back with a one-time code; the app swaps that code for tokens on a back channel. Tokens never travel in the browser's address bar.
  • PKCE (Proof Key for Code Exchange, said "pixie"): the app makes a random secret, sends only its hash (code_challenge) at the start, and must show the secret (code_verifier) when it swaps the code. A stolen code is useless without it.
  • state and nonce: random values the app checks on the way back, so an attacker cannot inject their own login response (CSRF) or replay an old id_token.
  • TOTP: the 6-digit code an authenticator app computes from a shared secret and the current time. WebAuthn / passkeys: the device signs a challenge with a private key bound to the site, so there is nothing to phish.
  • JWT (JSON Web Token): three base64url parts, header.payload.signature. Anyone can read the payload; only the holder of the private key can sign it, and anyone with the public key can verify it. Decoded, an access token looks like this:
// header
{ "alg": "RS256", "kid": "2026-11-key-b", "typ": "JWT" }
// payload (claims)
{ "iss": "https://id.example.com", "sub": "user_42", "aud": "orders-api",
  "exp": 1763890900, "iat": 1763890000, "sid": "fam_9c1", "scope": "orders:read" }
// signature = RS256( base64url(header) + "." + base64url(payload), private key )

kid says which public key in JWKS to use, exp is the expiry (15 minutes after iat here), and sid is the session (refresh family) id used for revocation. If you want to see the whole login flow before reading the endpoints, jump to the architecture stepper and the OIDC flow in deep dive 3.

From your world

OAuth vs OIDC is like 802.1X vs the RADIUS attributes it carries: one protocol moves the "you may connect" decision around, and the identity claims ride on top of it. A JWT is a signed routing update: any router can verify it came from the trusted speaker without asking that speaker again.

If OAuth is new to you, watch this five-minute explainer before reading the endpoints:

# first-party login
POST /v1/signup            {email, password}                     -> 201 (send verification email)
POST /v1/login             {email, password}                     -> {mfaRequired, mfaToken} | session
POST /v1/login/mfa         {mfaToken, totpCode | webauthnAssertion}  -> session
POST /v1/token/refresh     {refreshToken}                        -> {accessToken (JWT, 15 min), refreshToken (new)}
POST /v1/logout            {refreshToken | allDevices:true}      -> 204
POST /v1/password/reset    {email}                               -> 202 (always, even if email unknown)

# OpenID Connect provider (standard endpoints)
GET  /.well-known/openid-configuration       -> issuer, endpoints, supported algs
GET  /.well-known/jwks.json                  -> public signing keys, each with a "kid"
GET  /oauth2/authorize?response_type=code&client_id=..&redirect_uri=..&scope=openid%20email
                      &state=..&nonce=..&code_challenge=..&code_challenge_method=S256
POST /oauth2/token     grant_type=authorization_code&code=..&code_verifier=..   -> {access_token, id_token, refresh_token}
GET  /oauth2/userinfo  (Bearer access token)  -> {sub, email, name}
POST /oauth2/revoke    token=..               -> 200
  • /password/reset answers the same way whether or not the email exists, so attackers cannot use it to discover accounts (user enumeration). Login error messages should be equally vague: "email or password is wrong".
  • The jwks.json endpoint publishes public keys. Every service caches it and verifies tokens locally. The kid (key id) in each token header says which key signed it, which makes key rotation painless.
  • Standard endpoints matter: any OIDC library in any language can talk to us without custom code.
