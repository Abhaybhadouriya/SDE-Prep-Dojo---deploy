Interview: driving the 45 minutes

  1. 0-5 min: scope: first-party login, tokens for microservices, SSO via OIDC, MFA, revocation. Name the validation-vs-revocation tension.
  2. 5-10 min: estimate: 2,000 logins/s (100 hashing cores), 300k validations/s (must be local), 5,500 refreshes/s.
  3. 10-15 min: APIs (login, refresh, OIDC endpoints, JWKS) and tables.
  4. 15-25 min: architecture: edge, auth service + hash pool, token service + KMS, session store, local verification.
  5. 25-40 min: deep dives: password storage and stuffing, sessions vs JWT and revocation, OIDC code + PKCE.
  6. 40-45 min: failure modes: key leak, region failover, MFA recovery.

60-second answer, said out loud: "Passwords are hashed with Argon2id or bcrypt on a separate, rate-limited hashing pool, because a slow hash is the point and credential stuffing will hit it. On login, with MFA if needed, the token service creates a session, a refresh family, and signs a 15-minute JWT access token with a key held in a KMS. Every service verifies JWTs locally with cached JWKS public keys, so the 300k validations a second never touch the auth service. Refresh tokens are opaque, rotated on every use with reuse detection and a short grace window. To revoke early, I push the session id to a small in-memory denylist that only needs 15 minutes of entries. For SSO I am a standard OpenID Connect provider: authorization code flow with PKCE, exact redirect URIs, an id_token for identity. Auth events go to Kafka for audit and anomaly detection."

SDE-1 stops here / SDE-2 adds. SDE-1: password hashing (never encryption), sessions vs JWTs and the revocation trade-off, short access tokens plus refresh tokens, OAuth vs OIDC in one sentence each, the code flow with PKCE, MFA basics. SDE-2 adds: refresh rotation with reuse detection and the grace window, the pushed denylist, key rotation through JWKS and kid, edge validation with an internal identity (Netflix Passport), credential-stuffing defence that protects the hashing pool, multi-region failover of the control plane, and account recovery that does not bypass MFA.

You might confuse this with OAuth vs OIDC. OAuth 2.0 answers "may this app call this API for the user?" with an access token; OIDC answers "who is the user?" with an id_token. Using an OAuth access token as proof of identity is a classic bug. Also do not confuse authentication (who you are, this page) with authorisation (what you may do: roles, scopes and policies, usually decided by each service).

Common mistakes

Common mistakes: strict refresh-token reuse detection with no grace window (mass logouts on flaky networks); encrypting or fast-hashing passwords (MD5/SHA-256); calling the auth service on every request; long-lived JWTs with no revocation story; tokens in localStorage; shared HS256 secrets across all services; implicit grant or password grant; wildcard redirect URIs; hard lockouts that attackers can trigger; forgetting account recovery bypasses MFA.

How should we store user passwords?

Never encrypted, never with a fast hash. Use a slow, salted, memory-hard password hash: Argon2id with at least 19 MiB memory, 2 iterations, parallelism 1 (OWASP's minimum); scrypt or bcrypt (work factor 10+) if needed, PBKDF2-HMAC-SHA256 with 600,000 iterations under FIPS. A unique salt per password, stored in the hash string with the parameters so we can raise cost later. Optionally a pepper kept in a KMS/HSM outside the database. Follow NIST rules: length over complexity, no forced rotation, breached-password blocklist.

How to answer

Name the algorithm and parameters, then explain why slow and memory-hard (GPU cracking). Mention re-hashing on login.

Likely follow-ups
  • How do you migrate 100M users from MD5 to Argon2id? (Wrap the old hash now, re-hash on next login.)
  • What does the pepper protect against, and what not?
Sessions or JWTs for a microservice platform? How do you revoke a JWT?

Short-lived JWT access tokens (5-15 minutes) verified locally with JWKS public keys, because a central lookup at 300k requests/s would be a bottleneck and a single point of failure. Long-lived opaque refresh tokens stored (hashed) in a session store, rotated on every use. Revocation: put the session id in each JWT; on logout-all or admin kill, revoke the family in the store (no more refreshes) and push the id to an in-memory denylist on every service with a TTL equal to the token lifetime. For password change or payments, step up to a live session check.

How to answer

State the trade-off (local vs instant), then the hybrid with numbers for the window.

Likely follow-ups
  • Why not just make JWTs 1 minute long?
  • How big does the denylist get?
Walk me through "Sign in with ..." (OIDC). Why PKCE?

Authorization code flow with PKCE. The app sends the browser to /authorize with client_id, exact redirect_uri, scope openid, state, nonce and a code_challenge (SHA-256 of a random verifier). The user logs in at the IdP - or is already logged in there, which is SSO. The IdP redirects back with a one-time code. The app checks state, then exchanges code + code_verifier at /token and receives an ID token, access token and refresh token. It validates the ID token's issuer, audience, expiry, nonce and signature. PKCE stops an attacker who intercepts the code (for example via a malicious app registered for the same custom URL scheme) from redeeming it, because they do not have the verifier. RFC 9700 makes PKCE mandatory for public clients.

How to answer

Draw the three lanes (browser, app, IdP). Mark where state, nonce and PKCE each defend.

Likely follow-ups
  • Why is the implicit flow deprecated?
  • ID token vs access token - which one goes to the API?
What exactly makes SSO "single"? How does a second app avoid asking for a password?

The identity provider keeps its own session, a cookie on the IdP's domain. When the second app redirects to /authorize, the browser sends that cookie; the IdP sees a valid session (and checks it meets the app's required authentication level and age) and immediately issues a code without a prompt. Each app then has its own local session. The flip side: logging out of one app does not end the IdP session or other apps; use back-channel logout or short app sessions.

How to answer

Two layers of sessions: IdP session and app sessions. Then logout.

Likely follow-ups
  • SAML vs OIDC - when would you still pick SAML?
Attackers are trying millions of leaked passwords against our login. What do you do?

Layered defence before the expensive hash: per-IP, per-IP-range, per-account and per-device rate limits at the edge (token buckets in Redis); throttle and step up (MFA or a challenge) rather than hard-locking accounts, which attackers could abuse; check passwords against breach corpora and force resets for exposed ones; uniform error messages and timing so emails cannot be enumerated; alert from the auth-events stream on failure spikes by ASN or country. Protect the hashing pool with admission control so a flood cannot starve real logins. Long term, push users to passkeys.

How to answer

Order matters: cheap checks first, expensive hash last. Name the lockout DoS trap.

Likely follow-ups
  • The attack uses 1 million residential IPs, 1 attempt each. Now what?
How do downstream microservices know who the user is?

Authenticate once at the edge gateway and propagate a trusted identity. Either forward a validated, audience-restricted JWT, or - as Netflix describes - translate whatever the client sent into an internal, integrity-protected identity object (their Passport) so client tokens never pass the edge and inner services handle one format. Combine with mTLS between services for caller identity. Services never accept identity from plain headers set by clients; the edge strips any such header.

How to answer

User identity vs service identity; both are needed.

Likely follow-ups
  • A service needs to call another one asynchronously an hour later, on behalf of the user. Which identity does it carry?
How do you rotate the JWT signing key without logging everyone out?

Every token carries a kid. Publish the new public key in JWKS first and wait longer than the services' JWKS cache time. Then start signing new tokens with the new key. Keep the old public key published until the last token it signed has expired (15 minutes for access tokens), then retire it. For an emergency (key leak), remove the old key immediately and accept that everyone refreshes or logs in again; refresh tokens are opaque and stored, so refresh still works and users barely notice.

How to answer

Overlap windows: publish, then use, then retire.

Likely follow-ups
  • Where does the private key live, and who can use it?
Which MFA methods would you support, and why are passkeys better?

Support TOTP apps and passkeys (WebAuthn); allow SMS only as a fallback, since NIST 800-63B-4 classes it as restricted. Passkeys are phishing-resistant: the private key never leaves the device and the signature is bound to the real site's origin, so a look-alike site gets nothing reusable - unlike a code you can be tricked into typing. Store only the public key and counter. Mind recovery: email reset must not silently bypass MFA.

How to answer

Rank by phishing resistance; mention recovery as the weak link.

Likely follow-ups
  • A user loses their only passkey device - what now?
The primary region with the user database goes down. What still works?

Every service keeps verifying access tokens, because verification needs only cached public keys. Users stay logged in for up to the access-token lifetime. Refreshes and new logins need user and session data: if they are replicated to a standby region (asynchronously), we fail over and accept a tiny window where a very recent revocation or password change may be lost - so on failover, we also push a "credentials changed after T" rule to be safe. Signing keys must be available in the second region (multi-region KMS keys). Rate limits and denylists rebuild quickly from Kafka.

How to answer

Separate the data plane (survives) from the control plane (needs failover), then name the consistency risk.

Likely follow-ups
  • Would you make the session store multi-leader? What can go wrong?
After you ship refresh-token reuse detection, support reports thousands of mobile users being logged out every day. Why, and what do you change?

Reuse detection is firing on honest clients. A phone sends refresh with R1, the server rotates to R2, and the response is lost when the network drops; the app retries with R1, which is now "reused", so the whole family is revoked. Two tabs or two app processes refreshing at once do the same. Fix: keep the previous token hash and the rotation time, and allow a short grace window (30-60 s) in which R1 from the same client and device binding returns the same R2 idempotently. Outside the window, or from a different device, it is still treated as theft. Okta documents this as a grace period after rotation. Also make clients serialise refreshes (one in-flight refresh per app, shared across tabs) and measure "family revoked by reuse" as a metric.

How to answer

Name the two honest causes (lost response, concurrent refresh), then the window, then the safety boundary (same client, short time) so you do not reopen the theft hole.

Likely follow-ups
  • Could an attacker exploit the window? (Only within seconds of the real refresh and with the same binding; sender-constrained tokens such as DPoP close it fully.)
  • How do you test this before shipping?

Scenario: a stolen laptop

An employee reports their laptop stolen. Security wants the sessions on it dead now. Your access tokens are 15-minute JWTs.
Weak answer: "Delete the user's refresh tokens; the access token will expire in 15 minutes anyway."
Strong answer: Revoke that device's refresh family in the session store (no new tokens), add the family id to the denylist with a 15-minute TTL and publish it so every service rejects the current access token within a second, end the IdP session so SSO cannot mint new codes, and send back-channel logout to OIDC clients. Audit the auth-events stream for activity since the theft and force a password reset if the password may be cached.
  • How do you prove all services enforced it?

Scenario: login latency jumps to 4 seconds

At 9 a.m. login p99 goes from 300 ms to 4 s. CPU on the auth pods is at 100%. Failed logins are up 50x.
Weak answer: "Lower the Argon2 cost so hashing is faster."
Strong answer: This is a credential-stuffing wave consuming the hashing pool. Rate limit at the edge by IP range and ASN before any hashing happens, add a challenge for suspicious traffic, and keep a reserved share of hashing capacity for requests with a known device cookie. Scale the hash pool separately. Keep the cost parameters: lowering them helps the attacker more than the users.
