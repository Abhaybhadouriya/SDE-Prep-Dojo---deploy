Interview questions

User-based or item-based collaborative filtering for an e-commerce "customers also bought" widget? Why?

Item-based. Item-item similarity is stable (an item's buyer base changes slowly), so it can be computed offline, truncated to top-K per item and served from a key-value store; the online cost is a few lookups proportional to the items the user touched, independent of the number of users. User-based needs a neighbour search over all users at request time, user rows are sparse and drift quickly, and new users have almost no row. Item-based is also explainable ("because you bought X"). This is the choice in Amazon's 2003 item-to-item paper.

How to answer

Name both, pick item-based, give the three reasons: stability (offline), online cost, sparsity/cold users. Then sketch the offline job and the KV layout with a storage estimate.

Likely follow-ups
  • How do you stop the phone charger being similar to everything?
  • How fresh does the table need to be, and how do you refresh it?
Why cosine similarity and not Euclidean distance for rating vectors? When is cosine wrong?

Cosine compares direction and ignores magnitude, so heavy and light users (or popular and niche items) with the same pattern still match; Euclidean distance would call two items far apart just because one has many more interactions. Cosine is wrong when magnitude is the signal: for MF embeddings trained for dot product, the vector length encodes popularity or confidence, and the objective is maximum inner product, so normalising throws information away. Also, raw cosine is unstable for tiny overlaps (two co-buyers can give 1.0), so add shrinkage or a minimum co-count.

How to answer

Define it in one line, give the "generous vs harsh rater" example, then the counter-case (MIPS) and the small-sample fix.

Likely follow-ups
  • What does adjusted cosine change?
  • What would you use for 0/1 data?
Explain matrix factorization for recommendations. Why is it not really SVD?

Approximate the user-item matrix as U x VT, with a k-dimensional vector per user and per item; predicted affinity is their dot product, usually plus global, user and item biases. You fit the vectors on observed entries with L2 regularisation. Textbook SVD needs a complete matrix; filling the roughly 99% missing cells with zero teaches the model that everything is zero. So "SVD" in recommender talk (Funk SVD from the Netflix Prize) means fitting only known cells by gradient descent. Benefits over item-item: generalises to pairs never co-consumed, compact (k x (users + items) numbers), and the vectors double as embeddings for ANN retrieval.

How to answer

Draw R ~ U x VT, write the loss with biases, explain the missing-value problem, then state what MF gives you that item-item cannot.

Likely follow-ups
  • How do you pick k?
  • What happens for a user who signed up after training?
ALS or SGD to train matrix factorization on 1 billion implicit interactions? Walk through why.

ALS (weighted ALS). The joint problem is non-convex, but fixing items makes each user's vector an exact k x k least-squares solve, and all users are independent, so it parallelises perfectly across a Spark cluster; then swap roles. It needs no learning rate and converges in 10-20 iterations. Crucially for implicit data, the Hu-Koren-Volinsky formulation treats every unobserved cell as a weak negative, and the VTV precomputation keeps the cost proportional to observed interactions. SGD would need negative sampling and suffers write conflicts when parallelised. SGD wins when you need a non-squared loss (BPR, logistic) or a neural model.

How to answer

State the alternating insight, the parallelism, the implicit-data trick, and the one case where SGD is better.

Likely follow-ups
  • What is the network cost per iteration and how does Spark reduce it?
  • How do you set alpha?
How do you handle implicit feedback like plays and clicks, where there are no negative ratings?

Split each cell into preference (1 if any interaction, else 0) and confidence (1 + alpha x count). Train on all cells weighted by confidence, so a show watched 20 times pulls hard and an empty cell pulls weakly towards 0. Evaluate with ranking metrics on a time-based split, not RMSE. Log impressions so you know what the user saw and skipped. In sampled (neural) models, draw negatives, with care about popularity bias.

How to answer

Name the "missing is not negative" problem first, then preference + confidence, then evaluation and impressions.

Likely follow-ups
  • Is a skip after 5 seconds a negative?
  • How do you avoid the model just learning popularity?
You have 50M item embeddings and 200M user embeddings. Design the serving layer for p99 under 50 ms.

Users: key-value lookup only (no index), 200M x 128 x 2 bytes (float16) is about 51 GB, sharded Redis or DynamoDB with DAX, or fold-in from recent activity. Items: an ANN index, 50M x 128 x 4 bytes is about 26 GB raw plus graph links for HNSW; shard by item id across nodes, query all shards for top-k/shards with some slack, and merge (scatter-gather), replicate for QPS. Request path: get user vector (about 1 ms), KNN for 500 candidates with a stock filter (a few ms), rank, filter seen items. Publish new model versions as a complete new index plus user table and flip an alias atomically; reject requests whose user and item versions differ. Fall back to popular items on timeout or cold start.

How to answer

Separate the two tables by access pattern, size each, then draw the request path with a latency budget, then cover versioning and fallback.

Likely follow-ups
  • How do you add 100k new items per hour without rebuilding?
  • What if one shard is slow?
Compare HNSW with ScaNN. What does anisotropic quantization do?

HNSW is a graph index over raw vectors: excellent recall and latency, supports online inserts, but needs all vectors plus links in RAM. ScaNN partitions vectors (k-means leaves), scores candidates in the chosen leaves with compressed codes (asymmetric hashing), then rescores a short list exactly. Its quantizer uses an anisotropic loss: it penalises the part of the compression error parallel to the data point more than the perpendicular part, because parallel error distorts the high inner products that decide the top-k. Result: better recall per unit of compute for MIPS; Google reports about 2x the QPS of the next library at equal accuracy on glove-100-angular. Trade-off: batch rebuilds, more tuning knobs.

How to answer

Graph vs partition + quantize + rescore; explain anisotropic in one sentence with the "parallel error hurts ranking" idea; end with when you would pick each.

Likely follow-ups
  • Which knob raises recall in each?
  • Why rescore with full vectors?
How do you solve cold start for a new user and a new item in a CF system?

New user: start with popular or trending items for their region and context, ask a short onboarding question if the product allows, then switch to item-based recommendations from the very first click, and fold-in an MF user vector (one least-squares solve with frozen item factors) after a few interactions. New item: CF cannot score it, so use a content embedding (title, description, image) mapped into the same space, or a hybrid two-tower model with item features; reserve exploration slots so it collects interactions. Spark ALS returns NaN for unseen ids by default, which is your signal to use the fallback.

How to answer

Treat user and item separately, give a ladder (popular, then item-item, then fold-in), mention content features and exploration.

Likely follow-ups
  • How many slots do you give exploration?
  • How do you measure if cold-start handling works?
Estimate the item-item similarity job and table for 20M items and 300M users.

Table: 20M items x top 100 neighbours x 12 bytes is about 24 GB, a modest replicated KV cluster. Job: cost is the number of emitted pairs, about the sum over users of nu2/2. If users average 20 items, that is 300M x 200 = 60 billion pairs before combining; a map-side combine and capping heavy users (say 500 items) keep it tractable on a daily Spark job. Then shuffle by pair key, sum, divide by norms, keep top-K per item with a heap. Refresh daily; add a streaming delta for trending items if needed.

How to answer

Size the output first, then the job by pair count, name the heavy-user cap, then refresh cadence.

Likely follow-ups
  • What dominates the job's cost?
  • Where would you store the table and why?
