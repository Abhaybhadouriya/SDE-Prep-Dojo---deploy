Serving embeddings from memory (Redis)

Good to know (SDE-2)

After training you have two tables: user vectors and item vectors. At request time you need (1) the user's vector by id, in under a millisecond, and (2) the items whose vectors have the highest dot product with it. Recomputing either from the data lake per request is far too slow, so both live in RAM.

Sizing it

512 Bone 128-dim float32 vector
~5 GB10M item vectors, raw
~1.3 GBHNSW links at M = 16 (32 x 4 B per vector on layer 0)
~51 GB100M user vectors at 128 dims

Item vectors need an ANN index (you search them). User vectors do not: you only look them up by key, so they can sit in a plain hash, a key-value store like DynamoDB, or even be computed on the fly from recent activity (fold-in: one ALS user solve with the frozen V, a few microseconds). Storing float16 halves memory with little ranking loss; int8 quantises further.

Redis commands, end to end

# 1) index over hashes with prefix item:  (HNSW defaults: M 16, EF_CONSTRUCTION 200, EF_RUNTIME 10)
FT.CREATE idx:items:v42 ON HASH PREFIX 1 item:v42: \
  SCHEMA category TAG in_stock TAG \
         emb VECTOR HNSW 10 TYPE FLOAT32 DIM 128 DISTANCE_METRIC IP M 16 EF_CONSTRUCTION 200

# 2) load vectors (raw little-endian float32 bytes; 128 x 4 = 512 bytes each)
HSET item:v42:991 emb "<512 bytes>" category scifi in_stock yes

# 3) KNN with a filter; LIMIT is needed or you get only 10 rows back
FT.SEARCH idx:items:v42 "(@in_stock:{yes})=>[KNN 500 @emb $vec EF_RUNTIME 200 AS score]" \
  PARAMS 2 vec "<user vector bytes>" SORTBY score LIMIT 0 500 RETURN 1 score DIALECT 2

Redis reports distance, not similarity: for IP it is 1 - dot product, so smaller is better and SORTBY score ascending is right. Redis docs recommend FLAT (exact) below about 1M vectors and HNSW above. Redis 8.2 added SVS-VAMANA, a compressed graph index, for memory-bound cases.

From your world

This is RIB vs FIB. Training in the lake is the routing protocol building the RIB: slow, complete, on cheap storage. The Redis index is the FIB: a compact, read-optimised copy in fast memory, built from the RIB and pushed down. Versioned keys plus an alias flip is make-before-break: build the new table fully, switch the pointer atomically, then garbage-collect the old one. And just like a FIB, it is never the source of truth; you can always rebuild it.

Two Redis paths. Redis 8 also has a native Vector Set type (VADD to add, VSIM to query; HNSW with built-in quantisation), the simpler choice for a pure "nearest items to this vector" lookup. Use the Query Engine (FT.CREATE / FT.SEARCH, above) when you need filters such as in_stock, hybrid text-plus-vector queries or aggregations.

Rules that keep serving correct

  • Same model version on both sides. A user vector from model v41 dotted with item vectors from v42 is meaningless (the factor axes are re-learned every run). Store the version with the vector and fail closed on mismatch.
  • Inner product vs cosine. MF is trained for dot product, where vector length carries popularity. Searching by cosine silently removes that signal; searching by raw inner product boosts popular items. Pick deliberately; this is maximum inner product search (MIPS).
  • Cold start fallbacks. New user: popular-in-region or content-based items until a few clicks arrive, then fold-in. New item: content embedding (text, image) or a boosted exploration slot until it collects interactions.
  • Hot key. One user vector is read once per request, which is fine; but a global "trending" key read by every request is a hot key. Replicate it or cache it in the pod. See Scaling Reads.
