Training at scale: SGD vs ALS

Good to know (SDE-2)

There are two standard ways to minimise the MF loss. The loss is not convex in U and V together (both are unknown and they multiply), but it is a plain least-squares problem if you freeze one of them. That observation gives ALS.

  • SGD (stochastic gradient descent): loop over observed ratings; for each one compute the error and nudge that user's and item's vectors a little. Simple, flexible (any loss), used by Funk. Hard to parallelise cleanly because two workers may update the same item vector.
  • ALS (alternating least squares): freeze V and solve every user's vector exactly with a small k x k linear system; then freeze U and solve every item's vector. Repeat 10-20 times. Each half-step can only lower the loss, so it converges (to a local optimum).

If you only remember one thing: fix one side, and each row becomes a tiny linear regression you can solve exactly, in parallel. Everything below (the closed-form solve, implicit feedback, WALS) is that idea plus bookkeeping.

  1. Start: item vectors V are random; user vectors U are unknown. With V fixed, the loss for each user is an ordinary least-squares problem.
  2. Solve users. Asha's vector depends only on V and Asha's own ratings, so all four users are solved exactly and independently, in parallel.
  3. Solve items. Now freeze U and do the same per item. One full iteration is done: the training RMSE on observed cells is 0.908 (from the run below).
  4. Repeat. Each half-step can only lower the loss: 0.396 after two iterations, 0.129 after five, 0.096 after ten.

For one user u with observed items I(u), the exact solve is U[u] = (V_IT V_I + lambda I)-1 V_IT r_u: a k x k system (k = 64 means a 64 x 64 solve, microseconds). Here is ALS on our toy matrix, run for real:

import numpy as np
rng = np.random.default_rng(7)
R = np.array([[5, 4, 0, 0], [4, 5, 1, 0], [0, 1, 5, 4], [0, 0, 4, 5]], dtype=float)
M = R > 0                                  # observed cells only
k, lam = 2, 0.1                            # 2 latent factors, L2 penalty
U = rng.normal(scale=0.5, size=(4, k))     # user factors
V = rng.normal(scale=0.5, size=(4, k))     # item factors
I = np.eye(k)
for it in range(10):
    for u in range(4):                     # fix V, solve each user exactly
        Vo = V[M[u]]
        U[u] = np.linalg.solve(Vo.T @ Vo + lam * I, Vo.T @ R[u, M[u]])
    for i in range(4):                     # fix U, solve each item exactly
        Uo = U[M[:, i]]
        V[i] = np.linalg.solve(Uo.T @ Uo + lam * I, Uo.T @ R[M[:, i], i])
    err = np.sqrt(np.mean((R[M] - (U @ V.T)[M]) ** 2))
    if it in (0, 1, 4, 9): print(f"iter {it+1:2d}  train RMSE {err:.3f}")
print(np.round(U @ V.T, 1))

Spark MLlib ALS (what production code looks like)

from pyspark.ml.recommendation import ALS
from pyspark.ml.evaluation import RegressionEvaluator

ratings = spark.read.parquet("s3://lake/ratings/")      # userId, movieId, rating
train, test = ratings.randomSplit([0.8, 0.2], seed=42)

als = ALS(rank=64, maxIter=15, regParam=0.05,
          userCol="userId", itemCol="movieId", ratingCol="rating",
          coldStartStrategy="drop")         # drop NaN rows for unseen users/items
model = als.fit(train)

rmse = RegressionEvaluator(metricName="rmse", labelCol="rating",
                           predictionCol="prediction").evaluate(model.transform(test))
print(f"test RMSE = {rmse:.3f}")
model.itemFactors.show(2, truncate=60)         # id, features[64]
model.recommendForAllUsers(100).write.parquet("s3://lake/recs/v42/")

Spark's defaults are rank=10, maxIter=10, regParam=1.0, numBlocks=10. By default a user or item not seen in training gets a NaN prediction (coldStartStrategy="nan"), which is useful in production as a "use the fallback" signal but breaks evaluation, hence "drop" during tuning. The output of itemFactors is exactly the item embedding table you will serve.

From your world

ALS is the control-plane / data-plane split you already know. The frozen item matrix is like a FIB computed centrally and pushed to every line card; each card (worker) then processes its own users independently with no locking, just like per-flow processing on separate RSS queues. Then the roles swap. The cost you watch is the "FIB push": broadcasting a 10M x 64 float matrix (about 2.5 GB) to every worker each half-step, which is why Spark ALS partitions users and items into blocks.
