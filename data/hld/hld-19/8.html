ANN search: HNSW recap and ScaNN

Good to know (SDE-2)

Exact top-k over 10M item vectors of 128 dims is 1.28 billion multiply-adds per request. At thousands of requests per second that is too much, so we accept approximate nearest neighbours, measured by recall@k (how many of the true top-k we return).

HNSW in one paragraph

HNSW (Malkov and Yashunin, arXiv 1603.09320) builds a layered proximity graph: the bottom layer holds every vector, each higher layer a random sample. Search enters at the top, greedily walks to the closest node, drops a layer, and repeats, keeping a candidate list of size ef. Knobs: M (links per node: memory and recall), efConstruction (build quality), efSearch / EF_RUNTIME (recall vs latency per query). It needs all vectors in RAM and inserts are costly. The picture and table are on Specialized Indexes and AI building blocks; we do not repeat them here.

Quantization: compressing vectors to search faster

The other family shrinks vectors so many more fit in cache and distances are cheap. Product quantization (PQ) splits a 128-dim vector into, say, 64 sub-vectors of 2 dims; for each sub-space it learns 16 centroids with k-means; each sub-vector is then stored as a 4-bit centroid id. 512 bytes becomes 32 bytes. At query time you build a small lookup table of (query sub-vector . each centroid) once, and every database distance becomes 64 table lookups and adds. This is "asymmetric" scoring: the query stays exact, the database is compressed.

ScaNN: Google's three-stage search

ScaNN (Scalable Nearest Neighbors, Google Research, ICML 2020 paper "Accelerating Large-Scale Inference with Anisotropic Vector Quantization") targets MIPS. Its key idea is in stage 2.

The anisotropic trick

Normal quantization picks codes that minimise the average distance between a vector and its compressed version (reconstruction error), treating every direction equally. But for top-k by inner product, the error that hurts is the part parallel to the data point, because it directly changes the scores of the high-inner-product pairs you care about. Error perpendicular to the point mostly does not change the ranking. ScaNN's loss weights parallel error more than perpendicular error ("anisotropic" = direction-dependent). Google's blog shows that choosing a compressed point that is farther away but in a better direction can keep the correct ranking.

The official ScaNN example (GloVe-100, 1,183,514 vectors, 10,000 queries):

import numpy as np, scann          # pip install scann  (x86 needs AVX + FMA)
normalized = dataset / np.linalg.norm(dataset, axis=1)[:, np.newaxis]
searcher = (scann.scann_ops_pybind.builder(normalized, 10, "dot_product")
            .tree(num_leaves=2000, num_leaves_to_search=100, training_sample_size=250000)
            .score_ah(2, anisotropic_quantization_threshold=0.2)
            .reorder(100)
            .build())
neighbors, distances = searcher.search_batched(queries)
print("Recall:", compute_recall(neighbors, true_neighbors[:, :10]))
neighbors, distances = searcher.search_batched(queries, leaves_to_search=150)
print("Recall:", compute_recall(neighbors, true_neighbors[:, :10]))
Recall: 0.8999      # 10,000 queries in about 1.4 s
Recall: 0.92327     # search 150 leaves: higher recall, about 1.8 s

Those are the outputs recorded in Google's notebook; your timings depend on the CPU. The levers map one-to-one to the stages: num_leaves_to_search (stage 1), score_ah with 2 dims per block (stage 2), reorder size (stage 3). The ScaNN docs give rules of thumb: brute force below about 20k points, AH + rescoring below about 100k, all three stages above that, with num_leaves around the square root of the dataset size. Google's blog reports ScaNN handled about twice the queries per second of the next-best library at equal accuracy on the glove-100-angular benchmark.

From your world

Stage 1 is a hash or prefix table that picks a few buckets; stage 2 is a cheap first-pass match on a compressed key (like matching on a hash of the 5-tuple); stage 3 is the full-key compare on the short list to resolve collisions. You build lookup tables this way for the same reason: touch the expensive memory as little as possible.

Where engineers meet ScaNN in practice: as a library (pip scann), as a managed ScaNN index in AlloyDB (PostgreSQL, pgvector-compatible), and inside Vertex AI Vector Search, which is built on the same algorithm.
