Back-of-envelope estimation

The numbers are our assumptions, chosen to match the public versions of this problem. Write each step on the board; the reasoning matters more than the exact digits. (Refresher: Back-of-Envelope Estimation.)

Part A: search traffic

  1. Searches per day. 100M daily users x 5 searches each = 500M searches/day.
  2. Average QPS. 500M / 86,400 s = about 5,800 searches/s.
  3. Peak QPS. Lunch and dinner peaks: assume 3x, so about 17,400 searches/s. Round to ~20k QPS.
  4. Business writes. Say 1% of 200M businesses change per day = 2M/day = about 23 writes/s. Reviews: assume 10M/day = about 116 writes/s. Writes are tiny next to reads.

Part A: storage

  1. Business rows. 200M x about 1 KB (name, address, hours, category, lat/lng) = 200 GB. Photos live in object storage (S3-like store), not here.
  2. Geo index. Each entry is (geohash, business_id): about 8 + 8 = 16 bytes. 200M x 16 B = 3.2 GB. Even with 3x overhead this fits in the RAM of one machine.
  3. Quadtree alternative. Split cells until each leaf has at most 100 businesses: at least 2M leaves (more like 3-4M, because leaves are not full). Leaf payload = 200M ids x 8 B = 1.6 GB. Nodes: about 4M x 64 B (bounding box + 4 child pointers) = 0.26 GB. Total about 2 GB.
  4. Reviews. If we keep 5B reviews x 500 B = 2.5 TB. That is a sharded DB, but it is not on the search hot path.

Part A: bandwidth

A search returns 20 results x about 200 B of summary each = about 4 KB. 20k QPS x 4 KB = 80 MB/s out. Business detail pages and photos go through a CDN.

Part B: location updates

  1. Concurrent users. 1B users x 10% opted in = 100M; x 10% online at once = 10M connected phones.
  2. Update QPS. Each phone sends a location every 30 s: 10M / 30 = ~334k writes/s. This is why it cannot go into a normal SQL table.
  3. Fan-out. Assume 400 friends per user and 10% of them online: each update must be checked for ~40 friends. 334k x 40 = ~13M distance checks/s, and only the ones inside 5 miles become pushes.
  4. Connections. 10M WebSockets. If one server holds 50k-100k idle-ish connections (an assumption you must state), you need 100-200 WebSocket servers.
  5. Location cache. 10M x about 100 B (user id, lat, lng, timestamp, overhead) = 1 GB. Tiny in size, but 334k writes/s means we shard it over a few Redis nodes.
  6. History (optional). 334k/s x 32 B = about 10.7 MB/s = about 0.9 TB/day if we keep every point. Write-heavy, append-only: Cassandra or a time-series store.
  7. Pub/sub. One channel per opted-in user: 100M channels. If each channel record plus its subscriber list costs about 2 KB, that is 200 GB, so 2-3 large servers by memory. But if one server can push about 100k messages/s (assumption), 13M/s needs ~130 servers. The pub/sub tier is CPU-bound, not memory-bound. Say this conclusion; it is the interesting bit.

From your world

The nearby-friends math is a classic line-rate problem: 334k "packets" per second in, each replicated to ~40 output ports (like multicast replication on a switch), so the replication engine, not the buffer memory, is the bottleneck. Same lesson you know from ASIC multicast tables.
