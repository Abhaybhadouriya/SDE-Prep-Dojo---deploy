Requirements

First ask: "Is this Yelp (find places), or nearby friends (find moving people), or both?" Many interviewers start with Yelp and then say "now add nearby friends". We design both, as Part A and Part B.

Part A - Proximity service (Yelp)

  • Search nearby: given a location (latitude, longitude) and a radius, return businesses inside it, optionally filtered by category ("pizza") or name. Common radius choices are 0.5, 1, 2, 5, 10 and 20 km.
  • View a business: details, photos, rating, reviews.
  • Business owners add, update or remove a business. A change does not need to appear in search instantly; next day is acceptable in the classic version of the problem.
  • Reviews: a user leaves a 1-5 star rating with optional text; Hello Interview's breakdown adds "one review per user per business" as a rule.

Part B - Nearby friends

  • An opted-in user sees a list of friends within, say, 5 miles, with distance and "last updated" time.
  • The list refreshes every few seconds as people move; a friend whose location is older than about 10 minutes drops off.
  • Privacy: opt-in only, and the user can stop sharing at any time.

Say this out loud: "These two halves have opposite shapes. Yelp is read-heavy over static data, so I will precompute an index and cache it. Nearby friends is write-heavy over moving data, so I will keep it in memory with a TTL and push updates." That one sentence shows the interviewer you see the real problem.
