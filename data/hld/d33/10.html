How real companies do it

  • Yelp. Moved core business search from a custom Lucene master/replica system to Elasticsearch, mainly because real-time updates took minutes and code pushes took hours. Indexes are geosharded (San Francisco and Chicago are separate) and then micro-sharded by business_id % n; a coordinator picks the geo shard and merges the micro-shard results. Ranking runs as a hot-reloadable plugin.
  • Uber geofences. The service that answers "which polygons contain this point?" became Uber's highest-QPS service: 170k QPS at peak on New Year's Eve 2015, on 40 machines at 35% CPU, p99 under 50 ms and p95 under 5 ms. It used a simple two-level index (find the city, then scan that city's few hundred geofences) instead of an R-tree, and refreshed by building a new index on the side and swapping it in.
  • Uber H3. Open-source hexagonal grid: 16 resolutions, each about 1/7 the area of the previous, 64-bit cell IDs. Uber measures supply and demand per hexagon for surge pricing; hexagons were chosen because all six neighbours are the same distance away.
  • Tinder. Moved from one global Elasticsearch index to "geoshards" built from Google S2 cells (levels 7-8, roughly 45 and 22 miles), grouped by load. A query only touches the shards its distance filter covers; Kafka keyed by user ID keeps each user's updates ordered as they move between shards.
  • Redis. GEOADD/GEOSEARCH store a 52-bit interleaved geohash as a sorted-set score; this is the off-the-shelf version of the design in this page.
