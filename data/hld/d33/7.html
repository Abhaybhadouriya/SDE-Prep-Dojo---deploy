Where Kafka, Kubernetes and Docker fit

  • Kafka for business changes. The Business Service writes to SQL; change-data-capture (Debezium) publishes each change to a business-changes topic keyed by business_id. An indexer consumes it and updates the Redis geo sets or Elasticsearch. Keying by ID keeps updates for one business in order (partitions and ordering). Tinder did the same: Kafka partitions keyed by user ID so all updates for one user stay ordered as they move between geo-shards.
  • Kafka for location history, not live fan-out. 334k location updates/s into a Kafka topic, then a consumer batch-writes to Cassandra, is a good fit. But for the live friend push we want at-most-once and low latency: a stale location has no value, so replaying it is useless. That is why Redis pub/sub (fire-and-forget) beats Kafka on the hot path here. Saying this unprompted is a strong signal.
  • Kubernetes. LBS is a stateless Deployment with a Horizontal Pod Autoscaler on CPU (autoscaling). WebSocket servers are also a Deployment, but they need a long terminationGracePeriodSeconds and a preStop hook so scale-down drains connections instead of dropping 50k users at once. Redis pub/sub nodes fit a StatefulSet (stable names for the hash ring) or a managed service.
  • Docker. The nightly quadtree/index builder is a container image run as a Kubernetes CronJob; it writes a snapshot to object storage that LBS pods load at start-up.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ws-gateway
spec:
  replicas: 200
  selector:
    matchLabels: { app: ws-gateway }
  template:
    metadata:
      labels: { app: ws-gateway }
    spec:
      terminationGracePeriodSeconds: 300      # time to drain long-lived sockets
      containers:
        - name: ws
          image: registry.example.com/ws-gateway:1.4.2
          ports: [{ containerPort: 8080 }]
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "curl -s -X POST localhost:8080/drain; sleep 240"]
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }   # returns 503 once draining starts

From your world

Draining a WebSocket server is the same idea as graceful shutdown of a BGP speaker or a load-balanced server pool member: withdraw the route (readiness probe fails, so the Service stops sending new connections), let existing flows finish or move, then shut down. Killing the process is like pulling the cable.
