Architecture: the request flow

Part A splits into two services with very different load: a stateless Location-Based Service (LBS) that only answers "what is near here?", and a Business Service for details and owner writes. Click Next or Play.

  1. Request. The phone sends lat, lng, radius and an optional category to the API gateway, which handles auth, rate limiting and load balancing.
  2. Split by job. Search goes to the LBS; detail pages and owner edits go to the Business Service. LBS is stateless and read-only, so we scale it by adding pods.
  3. Find candidates. LBS picks a geohash precision from the radius (2 km -> length 5, 1 km -> length 6), computes the user's cell plus its 8 neighbours, and fetches the business IDs in those 9 cells from the geo index.
  4. Filter and rank. LBS batch-fetches business summaries from cache, computes the exact distance (haversine), drops anything outside the radius or category, sorts by distance and rating, returns the top 20.
  5. Write path. Owner edits go to the primary DB. The geo index is rebuilt or updated asynchronously (nightly job, or change-data-capture events), which is fine because "visible tomorrow" is acceptable.
  6. Steady state. A search is two in-memory lookups plus CPU math. The database primary is never on the read path, so 20k QPS is easy with a few replicas and a cache.

Part B: nearby friends flow

Here the server is stateful: each WebSocket server holds live connections. The core loop: a phone sends its location, the server stores it and publishes it on that user's channel, and every server holding a connection of one of that user's friends receives it, checks the distance and pushes it if close.

On connect, Bob's WebSocket server (1) loads Bob's friend list, (2) reads all their cached locations in one batch (MGET) to build the first snapshot, and (3) subscribes to each friend's channel. On disconnect it unsubscribes. When Bob adds a friend, his server subscribes to the new friend's channel; when he removes one, it unsubscribes.
