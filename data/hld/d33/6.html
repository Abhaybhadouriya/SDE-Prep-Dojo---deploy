Deep dives

1. Why a normal index fails, and the ladder of geo indexes

The naive query is WHERE lat BETWEEN a AND b AND lng BETWEEN c AND d. With separate B-tree indexes on lat and lng, the database can use only one well: it finds a thin strip of the world (every place at that latitude, all around the globe) and then filters the other dimension. A B-tree sorts on one dimension; space has two. Hello Interview's proximity deep dive makes the same point: every spatial index is a way to turn 2-D closeness into something a 1-D index or a tree can find quickly, producing a candidate set that exact distance math then filters.

  1. Evenly spaced grid. Cut the world into fixed squares. Simple, but Manhattan squares hold thousands of places and ocean squares hold none.
  2. Geohash. A recursive grid encoded as a string, so a normal B-tree, a Redis sorted set or a DynamoDB sort key can do prefix lookups. Fixed cell sizes per length; easy to update (recompute one string).
  3. Quadtree. Split a cell into 4 only when it has too many points (ByteByteGo uses 100). Adapts to density: deep in cities, shallow in deserts. Usually an in-memory tree.
  4. Google S2 / Uber H3. Hierarchical cells on the sphere (S2: cube faces + Hilbert curve; H3: hexagons, 16 resolutions, each about 1/7 the area of its parent). Better shapes and no edge-of-world surprises, at the cost of a library.
  5. R-tree family (PostGIS GiST, Elasticsearch BKD). Index bounding boxes, so they handle polygons and "point inside delivery zone" too. Best for complex geometry; heavier writes.

2. Geohash done right: precision, the 9-cell query and the boundary problem

Pick the longest (most precise) geohash whose cell is still at least as big as the search radius. With the size table above, length 6 (1.2 km) is too small for 2 km, so a 2 km radius uses length 5 (4.9 km cells); a 500 m radius uses length 6 (1.2 x 0.6 km). Then query the user's cell and its 8 neighbours.

Two more geohash facts worth saying: cells are not equal in area (degrees of longitude shrink toward the poles, so a cell in Norway is narrower than one in Singapore), and if the 9 cells return fewer results than asked, expand by using one character less (each step is about 32x more area) rather than failing.

Redis implements exactly this idea: GEOADD stores a 52-bit interleaved geohash as the score of a sorted set, and GEOSEARCH scans the bounding boxes around your circle, then filters by real distance. Its documented cost is O(N + log M), where N is the number of items in the grid-aligned box.

$ redis-cli GEOADD biz:pizza -122.4016 37.7564 b_123 -122.4090 37.7599 b_456
(integer) 2
$ redis-cli GEOSEARCH biz:pizza FROMLONLAT -122.4016 37.7564 BYRADIUS 2 km ASC COUNT 20 WITHDIST
1) 1) "b_123"
   2) "0.0000"
2) 1) "b_456"
   2) "0.7583"

Illustrative output: the distance is the haversine distance between the two points using Redis's Earth radius (6,372,797.56 m). The last digits can differ slightly on a real server because Redis stores each point as a 52-bit geohash, not exact coordinates.

One sorted set per category (biz:pizza, biz:atm) makes category filtering free. One giant set works too, but then you filter categories after the geo lookup.

3. Quadtree: adaptive, but you must plan its lifecycle

  • Search: walk from the root to the leaf that holds the user, collect its businesses, and if there are not enough, add neighbouring leaves until you have K. Cost is about O(log n + k).
  • Memory: about 2 GB for 200M businesses (our estimate above), so every LBS server can keep a full copy. No network hop to search.
  • Build: O(n log n). ByteByteGo says building it for 200 million businesses can take "a few minutes" at start-up, and the server cannot serve while building. So roll out new LBS versions to a small slice of servers at a time, or load a pre-built snapshot from object storage instead of rebuilding.
  • Updates: adding or removing a business means walking to its leaf and maybe splitting or merging, under a lock, on every replica. Since "visible tomorrow" is allowed, the simplest correct answer is a nightly rebuild plus a blue/green swap of the new tree (the same trick Uber's geofence service uses: build a new index on the side, then swap it in under a read-write lock).
  • Disk: a quadtree is pointer-chasing; on disk, every hop is a random read. That is why on-disk engines use R-trees or BKD trees instead.

From your world

A quadtree is a 2-bit-per-level radix trie, the 2-D cousin of the Linux fib_trie (an LC-trie for route lookup). Its path compression trick (skip levels with one child) is exactly what a compressed quadtree does. A nightly rebuild plus atomic swap is RCU: readers keep using the old tree until the pointer flips.

4. Ratings and "one review per user"

Search results show an average rating, and Hello Interview lists "keep the average cheap to read" as a core deep dive. Computing AVG(stars) over millions of reviews per search is far too slow. Store rating_sum and rating_count on the business row and update them in the same transaction as the review insert (or with an atomic UPDATE ... SET rating_sum = rating_sum + :s, rating_count = rating_count + 1). The average is sum / count, and the index cache can refresh it lazily. For "one review per user", the primary key (business_id, user_id) makes the database reject a second insert, which is safer than an application-level "check then insert" race. Return HTTP 409 and let the client switch to "edit your review".

5. Nearby friends at scale: the stateful tier and the pub/sub tier

  • Distance filter on the receiver side. Bob's server knows Bob's last location, so it can drop Alice's update if she is more than 5 miles away. This turns ~40 friends into the handful who are actually close.
  • Pub/sub is CPU-bound. From the estimate: ~13M deliveries/s. Shard channels across a cluster of Redis pub/sub nodes by hashing the user ID on a consistent-hash ring; keep the ring in a coordination store (etcd or ZooKeeper, see Lock Service) so every WebSocket server agrees which node owns which channel. Resize rarely and during low traffic, because moving a channel means re-subscribing everyone on it.
  • Scaling the WebSocket tier. Adding servers is easy. Removing one is the hard part: mark it "draining" at the load balancer so it gets no new connections, wait for clients to reconnect elsewhere (or tell them to), then stop it. On reconnect, the new server rebuilds the snapshot from the location cache.
  • Hot users. Someone with 5,000 friends causes huge fan-out. Cap how many friends the feature tracks per user, and rate-limit pushes from users with very large friend lists (for example, at most one fan-out per interval).
  • "Random people nearby" (not just friends). Make channels per geohash cell instead of per user: a phone publishes to its cell's channel and subscribes to its cell plus 8 neighbours, re-subscribing when it crosses a cell edge. This is how you extend the design to Tinder-style or "find a nearby driver" features.

6. Sharding and multi-region

The Part A index is small enough to replicate everywhere, so sharding is mostly for throughput and locality, not size. Yelp's search on Elasticsearch shards first by geography (San Francisco and Chicago live in separate indexes), then splits each geo index into micro-shards by business_id % n. Tinder did similar "geosharding" with S2 cells, grouping neighbouring cells into shards with roughly equal load. The risk of geo-sharding is hot spots: New York and London are not the same size as Iceland. Balancing by load (users and queries per cell), not by area, fixes that. Deploy one LBS cluster per region close to its users; a search in Mumbai never needs data from Ohio.

Hot partition trap: "shard by the first geohash character" sounds tidy, but almost all of India falls under one or two first characters. Shard by load-balanced ranges of cells, or by business ID with a scatter-gather, and say why.
