Interview: how to drive 45 minutes

  1. 0-5 min: requirements. Places or people or both? Radius range? Filters? Freshness needed for new businesses? Scale (DAU, number of businesses).
  2. 5-10 min: estimation. ~20k QPS read-heavy; index fits in RAM. For friends: 334k writes/s and 13M deliveries/s.
  3. 10-15 min: API + data model. Search endpoint; business, geo_index, review tables; Redis TTL key for live location.
  4. 15-25 min: high-level design. LBS vs Business Service; read replicas and cache; WebSocket + pub/sub for friends.
  5. 25-40 min: deep dives. Geohash vs quadtree (with the boundary problem), index refresh, ratings, pub/sub sizing, draining.
  6. 40-45 min: wrap up. Failure modes, multi-region, what you would monitor (p99 search latency - p99 = 99% of searches are faster than this; the slowest 1% are what users complain about - index age, push lag).

Common mistakes: doing lat BETWEEN ... AND lng BETWEEN ... and calling it done; using a geohash prefix without the 8 neighbours; putting 334k location writes/s into MySQL; polling for friends' locations; using Kafka with replay for the live push; ignoring that WebSocket servers are stateful when scaling down; forgetting privacy (opt-in, TTL).

Design a service that returns businesses near a user (Yelp / Google Places).

Clarify radius, filters, scale (100M DAU, 200M businesses) and freshness (next day is fine). Estimate ~20k peak QPS and a 3-4 GB geohash index. Split into a stateless LBS (search) and a Business Service (CRUD, details) over SQL with read replicas. LBS maps radius to geohash length, reads the 9 cells from an in-memory or Redis index, batch-loads summaries from cache, filters by exact distance and category, ranks and returns 20 with a cursor. Index updates are async (nightly or CDC). Shard and replicate by region.

How to answer

Name the shape first (read-heavy, static data), then the index choice with the boundary problem, then caching. Volunteer "I would use Redis GEO or PostGIS in real life; here is what they do inside".

Geohash or quadtree? Defend your choice.

Geohash if I want simplicity and cheap updates: it is a string column on a normal index or a Redis sorted set, updating a business is recomputing one string, and the boundary problem is fixed with the 9-cell query. Quadtree if density is very uneven and I want "give me the nearest 20" with similar cost in Manhattan and in Nevada: it adapts cell size to data. But it lives in memory, takes minutes to build for 200M points, and needs a careful refresh (snapshot + swap). For Yelp-like static data both work; I default to geohash and mention quadtree for density. For moving points I prefer geohash/H3 cells because updates are just "remove from old cell, add to new cell".

How to answer

Give one win and one cost for each, then decide based on the requirements you wrote down. Interviewers want reasoning, not a favourite.

Design "nearby friends". Why not just store locations in the database and poll?

10M concurrent users updating every 30 s is ~334k writes/s, and polling every few seconds would add millions of mostly empty reads per second. Instead: WebSocket connections; each update goes to a Redis location cache with a TTL (stale data expires itself), optionally to history via Kafka into Cassandra, and to the user's own Redis pub/sub channel. Each WebSocket server subscribes to the channels of the online friends of its connected users, filters by distance and pushes. Redis pub/sub is fire-and-forget, which matches the data: the next update arrives in 30 s.

How to answer

Do the write QPS first; it justifies everything else. Then draw the one-update path (phone, WS server, cache, channel, friend's WS server, phone).

How do you size the pub/sub tier?

Memory: 100M channels x ~2 KB (record + subscriber list) is about 200 GB, so a few big boxes. CPU: 334k updates/s x ~40 online friends is ~13M deliveries/s; at an assumed ~100k pushes/s per node that is ~130 nodes. So it is CPU-bound and needs a cluster. Shard channels by user ID with consistent hashing, store the ring in etcd/ZooKeeper, and avoid resizing at peak because moving a channel forces re-subscription.

How to answer

Compute both memory and CPU; the "aha" is that the smaller-looking number (memory) is not the bottleneck. State your per-node assumption out loud.

How do you keep the average rating fast and enforce one review per user?

Never compute AVG at read time. Keep rating_sum and rating_count on the business and update them atomically in the same transaction as the review insert. Enforce uniqueness with a primary key on (business_id, user_id), so the DB rejects duplicates even under concurrent requests; return 409 and offer edit. If reviews are sharded separately, publish a "review added" event and update the aggregate idempotently using the review ID.

How to answer

The 9 cells around the user return only 3 restaurants. What now?

Expand the search: drop one geohash character (cells about 32x bigger) and query the 9 bigger cells, repeat until you have enough or hit the maximum radius. With a quadtree, keep adding neighbouring leaves. Always filter by the real distance at the end and tell the client the effective radius. Cache "sparse area" results, since they rarely change.

How to answer

Mention expansion before the interviewer asks; it shows you thought past the happy path.

How would you change the design if the points move (drivers, delivery riders) instead of businesses?

Moving points flip the read/write ratio. Drop the nightly rebuild and the quadtree; use cells (geohash or H3) where an update is "remove from old cell, add to new cell", in memory (Redis GEO or a sharded in-memory index keyed by cell), with a TTL so silent drivers disappear. Shard by region or cell. Keep SQL only for trips and payments. This is the core of ride hailing and food delivery.

How to answer

Say "static vs dynamic data" explicitly and show which parts change.

How do you shard the geo index across regions without hot spots?

The index is small, so first replicate it per region for locality. If one region still needs sharding, shard by contiguous ranges of cells balanced by load (queries and businesses per cell), not by equal area or the first geohash character. S2's Hilbert-curve ordering is useful here: cells that are close on the map are close in ID order, so a shard is a contiguous ID range (Tinder grouped S2 cells this way). Queries near a shard boundary scatter to two shards and merge.

How to answer

Call out the "shard by first character" trap, then propose load-based ranges.

How do you scale down WebSocket servers without dropping users?

Mark the server draining: its readiness check fails so the load balancer sends no new connections, then ask connected clients to reconnect (or wait for natural churn), with jitter so they do not all land at once. Give the pod a long termination grace period. On reconnect, the new server reloads friends, fetches their cached locations and re-subscribes. Because state lives in the location cache and pub/sub, the server itself holds nothing that cannot be rebuilt.

How to answer

Mention "stateful tier" and "drain" explicitly; that is the word interviewers listen for.

Extend nearby friends to "show random people near me who opted in".

There is no friend list to define channels, so make channels per geohash cell. A phone publishes its location to its current cell's channel and subscribes to its cell plus the 8 neighbours. When it crosses into a new cell it unsubscribes from the old set and subscribes to the new one. Choose a cell size near the radius so 9 cells cover it. Dense cells (a stadium) get many publishers, so sample or rate-limit, and filter by exact distance on the receiving server.

Scenario: a new restaurant complains it never shows up

An owner added a business two days ago. It is in the database but missing from search. Other new businesses appear fine.

Weak answer: "Clear the cache and rebuild the index."

Strong answer: check the pipeline step by step. Is the change event in the business-changes topic? Did the indexer consume it (consumer lag, dead-letter queue)? Is the geohash computed from swapped lat/lng (a classic bug: a place in Mumbai indexed in the Arabian Sea)? Is it in the geo set for the right category? Then fix the root cause, add a reconciliation job that compares DB rows with index entries nightly, and alert on index age and count drift.

Likely follow-ups
  • How would you make new businesses visible within a minute?

Scenario: New Year's Eve, push lag climbs to 40 seconds

Nearby-friends updates arrive 40 s late in a few big cities. WebSocket servers look healthy; two Redis pub/sub nodes are at 100% CPU.

Weak answer: "Add more WebSocket servers."

Strong answer: the pub/sub tier is CPU-bound and two nodes own hot channels (popular users in dense cities). Short term: shed load by lowering update frequency server-side (ask clients for 60 s instead of 30 s), drop updates older than one interval instead of queueing them, and rate-limit fan-out for users with very many friends. Longer term: more pub/sub nodes with more virtual nodes on the ring, resized before the event, and a load test of peak fan-out. Freshness is the requirement, so dropping stale updates is correct, not a bug.
