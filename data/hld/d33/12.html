Quick quiz

Why do we query the user's geohash cell plus its 8 neighbours?

  1. Nine small lookups are faster than one big lookup
  2. Close points can have different prefixes
  3. Geohash cells are only defined in 3 x 3 blocks
  4. The neighbours hold copies of the user's own cell
The boundary problem: 9q8yy and 9q8zn touch but share only "9q8". Searching the 3x3 block and then filtering by exact distance avoids misses.

A user searches with a 2 km radius. Which geohash length is the best starting point?

  1. 4 (about 39 km)
  2. 6 (about 1.2 x 0.6 km)
  3. 7 (about 153 m)
  4. 5 (about 4.9 km)
Pick the longest (most precise) length whose cell is still at least the radius: length 6 (1.2 km) is too small, so use length 5 (4.9 km), whose 3x3 block covers the 2 km circle. Length 4 works but scans far more businesses.

What is the main advantage of a quadtree over a fixed grid or geohash?

  1. It adapts cell size to how dense the data is
  2. Updates are instant and need no locking at all
  3. Its cell IDs can be range-scanned on any B-tree
  4. It needs no memory, since it lives in the database
Dense cities get deep, small cells; deserts stay as one big cell. The cost is in-memory build time and careful updates.

10M users each send a location every 30 s. Roughly what write rate is that?

  1. 33k/s
  2. 3.3M/s
  3. 334k/s
  4. 10M/s
10,000,000 / 30 = about 333,333 writes per second.

Why is Redis pub/sub (fire-and-forget) acceptable for the live friend push?

  1. It guarantees exactly-once delivery to subscribers
  2. A lost location is replaced about 30 s later
  3. It keeps the last hour of messages for reconnects
  4. It writes every message to disk before it is sent
Freshness beats completeness here. Kafka's durable replay is wasted on stale locations; use Kafka for history instead.

Which property makes Uber's H3 good for surge pricing?

  1. Its IDs can be range-scanned on a B-tree
  2. Each cell splits into exactly 4 children
  3. Every cell has exactly the same area
  4. Hexagons: all neighbours are equally far
Equal neighbour distance simplifies smoothing and analysis. H3 IDs are not range-scannable, children are approximately 7 per parent, not 4, and cell areas vary a little.

How do you enforce "one review per user per business" safely?

  1. A unique constraint on (business_id, user_id)
  2. Check in the app whether a review exists, then insert
  3. A nightly job that deletes the newer duplicate
  4. A Redis lock on the user while the review is saved
Check-then-insert races under concurrency. The database constraint is atomic. A lock works only while every writer remembers to take it.
