Trade-offs, bottlenecks and failure modes

Which geo index?

IndexGood atWeak atPick it when
GeohashWorks on any B-tree / sorted set; cheap updates; easy to explainBoundary problem; fixed sizes ignore density; unequal areas near polesDefault interview answer; Redis GEO; frequently moving points
QuadtreeAdapts to density; nearest-K is naturalIn-memory build time; updates need locks; poor on diskStatic places with very uneven density, fits in RAM
Google S2Hierarchical cells on a sphere; Hilbert curve keeps neighbours close in ID order; good region coveringLibrary complexity; harder to explainSharding by area (Tinder used S2 levels 7-8)
Uber H3Hexagons: every neighbour centre is the same distance away; great for aggregation (surge per cell)IDs are not range-scannable; children only approximately fit their parentAnalytics, pricing, "count supply in this area" (surge pricing)
PostGIS / Elasticsearch (R-tree / BKD)Polygons, containment, combined text + geo + filtersHeavier writes; another system to runSearch with many filters (Yelp uses Elasticsearch), delivery zones

Failure modes

FailureEffectMitigation
Geo index node downSearches fail in that shardReplicas (index is small, keep 3+ copies); LBS falls back to another replica
Index builder fails overnightNew businesses missingKeep serving yesterday's snapshot; alert; never swap in a partial index (check counts before swap)
Hot city at dinner timeOne shard meltsCache results per (cell, category) for a few minutes; shard by load
WebSocket server crash50k users disconnectedClients reconnect with jittered backoff; new server rebuilds snapshot from location cache
Pub/sub node downUpdates for its channels lostConsistent hashing moves channels to the next node; servers re-subscribe; updates resume within 30 s
Location cache lost"Nobody nearby" for a momentAcceptable: the cache refills from the next round of updates in 30 s. No need to persist it
Precompute + cache (Part A)
  • Reads are memory-speed
  • Easy to replicate per region
  • DB primary off the read path
Cost
  • Index lags writes (minutes to a day)
  • Rebuild and swap must be operated carefully
  • Cache invalidation when a business moves
