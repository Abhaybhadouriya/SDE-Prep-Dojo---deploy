The dual-write problem

Each microservice usually owns its own database. When an order is created, the Order service saves it and must also tell Inventory, Payments and Search. The tempting code is:

orderRepository.save(order);                 // 1. write to my database
kafka.send("orders", new OrderCreated(order)); // 2. publish an event
return ok();

This is a dual write: two separate systems written one after the other with nothing tying them together. The process can crash, the network can drop, or the broker can be down between step 1 and step 2.

Order of writesFailure in betweenResult
DB, then brokerCrash after DB commitState changed, nobody told (lost event)
Broker, then DBDB write fails / rolls backEverybody told about an order that does not exist (phantom event)
Publish inside the DB transactionDB commit fails after publishSame phantom event; also holds DB locks during a network call
Either order, with retriesTimeout but the write actually landedDuplicates unless the receiver is idempotent

You cannot fix this with a try/catch, because the crash can happen in the one instruction between the two calls. And Kafka cannot join an XA (distributed) transaction with your database. The fixes below all follow one rule: write to exactly one system atomically, and derive everything else from it.

From your world

It is the same reason a filesystem uses a journal. Updating an inode and a data block as two separate disk writes can tear on power loss. ext4 writes both into the journal as one transaction, then replays the journal into place. The outbox is that journal for your services, and the relay is the replay thread.
