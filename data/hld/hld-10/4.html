Transactional outbox and CDC

The transactional outbox removes the dual write. In the same local database transaction that changes business data, the service inserts the event into an outbox table. Either both rows commit or neither does. A separate relay later reads the outbox and publishes to the broker, retrying until the broker acknowledges.

BEGIN;
  INSERT INTO orders (id, user_id, total, status)
       VALUES ('o-17', 'u-9', 499.00, 'PENDING');
  INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)
       VALUES ('7f3c...e1', 'Order', 'o-17', 'OrderCreated',
               '{"orderId":"o-17","total":499.00}');
COMMIT;

The column names above are the ones Debezium's outbox router expects: aggregatetype picks the topic (Order events go to an OrderEvents-style topic), aggregateid becomes the Kafka message key so all events for one order land in one partition in order, and id is a unique event id consumers use to drop duplicates.

Worked estimate (rule of thumb, round numbers).

  1. Rate. 5,000 orders per second, one event each, so 5,000 outbox rows per second.
  2. Per day. 5,000 x 86,400 s = about 432 million rows a day. At about 1 KB per row (payload plus columns) that is about 430 GB a day of outbox data.
  3. Table growth. If you never clean up, the table grows 430 GB a day, so delete sent rows within minutes (or use Debezium's insert-then-delete trick so the table stays empty and only the WAL carries the rows). Even with cleanup, the WAL or binlog must keep those 430 GB a day until the relay has read them.
  4. Polling relay. To keep up, poll interval x batch size must exceed the rate: every 100 ms you must fetch and publish about 500 rows, then mark them sent and later delete them. Each event is now written three times (insert, update, delete) and the poll query runs 10 times a second against a hot table.
  5. When to switch. Somewhere in the low thousands of events per second (a judgement call, not a hard limit), that extra write and query load starts to hurt the primary, and log-based CDC such as Debezium wins: it reads the WAL that is written anyway and adds no queries. Below a few hundred per second, a simple poller is fine and easier to run.

Both relays are at-least-once: if the relay crashes after publishing but before recording its progress, it publishes again on restart. Microsoft's Cosmos DB outbox example shows exactly this (restart from the last checkpoint) and removes the duplicates with the broker's duplicate detection on a message id. In general, consumers must be idempotent (below).

CDC beyond the outbox

Change data capture means streaming every insert, update and delete from a database's log to other systems. Even without an outbox table, CDC replaces many dual writes: keep Elasticsearch, a cache or a data warehouse in sync from the primary database instead of having the app write to both. The flow in ByteByteGo's guide is: transaction log, source connector (Debezium), Kafka, sink connector, target store.

(p99 in the stats means the 99th-percentile latency: the time that 99 of 100 records beat; 1 in 100 is slower.) Shopify moved to log-based CDC because their older query-based polling could run only hourly, missed hard deletes, missed intermediate states of rows that changed twice between polls, and depended on an unreliable updated_at column. Their hard parts were snapshots (initial SELECT * with read locks), records bigger than Kafka's 1 MB default, and breaking schema changes leaking to consumers who are now coupled to internal tables.

Raw CDC vs outbox: raw table CDC tells consumers what changed, not why, and couples them to your schema. Hello Interview makes the same point: CDC fits "consumers need a copy of the data" (search index, warehouse, migration), not "consumers need to react to a business intent" (send the shipped email). For intent, publish explicit domain events through an outbox - which can still be relayed by CDC. The full pipeline is design d28 CDC Data Pipeline.

From your world

Debezium reading the binlog is a replication client, exactly like a MySQL replica or a tcpdump on the database's own change stream. A Postgres replication slot is a ring buffer with a reader that must keep up: if the connector stops consuming, the slot pins WAL segments and the primary's disk fills - the same failure as a stuck consumer never advancing a DMA ring's tail pointer.
