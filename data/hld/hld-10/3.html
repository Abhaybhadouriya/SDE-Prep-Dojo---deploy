Sagas: a chain of local transactions

A saga splits one business transaction into a sequence of local transactions, each inside one service's own database. Each step, once committed, triggers the next. If a step fails, the saga runs compensating transactions that semantically undo the earlier steps (refund the card, release the stock). There is no global lock and no global rollback, so the system is eventually consistent.

Microsoft's saga guide names three kinds of steps, and naming them in an interview shows depth:

  • Compensable steps can be undone by another transaction (reserve stock / release stock).
  • The pivot step is the point of no return (charge the card, ship the parcel). After it succeeds, the saga only moves forward.
  • Retryable steps come after the pivot and must be idempotent so they can be retried until they succeed (send the confirmation email, update loyalty points).

  1. Step 1 commits. The orchestrator (top box) sends the first command and will record every reply in its own durable saga state. The order is stored as PENDING (not CONFIRMED - the state itself tells readers the saga is in flight; this is a "semantic lock").
  2. Step 2 commits. Inventory reserves the item in its own database, ideally with a TTL so a stuck saga cannot hold stock forever.
  3. Step 3 fails. The payment provider declines the card. The orchestrator records the failure in its saga state.
  4. Compensate step 2. The orchestrator sends "release reservation". Compensations run in reverse order and must themselves be idempotent and retryable.
  5. Compensate step 1. The order becomes CANCELLED. Had step 3 succeeded (the pivot), step 4 would simply be retried until it worked - never compensated.

Sagas have no isolation - plan for it

Because each step commits on its own, other requests can see half-finished sagas. The Azure guide lists the anomalies and fixes:

AnomalyExampleCountermeasure
Lost updateTwo sagas overwrite each other's stock countCommutative updates (stock = stock - 1, not "set to 41"); version checks
Dirty readA report counts stock that a failing saga is about to releaseSemantic lock (PENDING state); "pessimistic view" - move risky updates after the pivot
Fuzzy readPrice changes between step 1 and step 3Reread and verify before acting; carry the value in the saga

Say this: "Payments and inventory are separate services, so I won't use 2PC. I'll run an orchestrated saga: create order as PENDING, reserve stock with a TTL, charge the card as the pivot, then confirm. Each step is idempotent, every event is published through an outbox, and compensations release stock or refund." This is the heart of Pattern: Multi-step Processes.
