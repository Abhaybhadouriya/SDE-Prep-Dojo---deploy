CQRS: separate the write model from the read models

Command Query Responsibility Segregation splits the system into a command side that validates and changes state, and one or more query sides shaped for reading. The write side is normalised and strict; the read sides are denormalised copies - a search index, a Redis cache, a reporting table - updated from events.

CQRS does not require event sourcing, and event sourcing almost always uses CQRS. Use it when reads and writes have very different shapes or scale (a product catalogue with 1,000 reads per write, a feed). Avoid it for simple CRUD: it adds a second store, a pipeline, duplicate and out-of-order messages, and read-your-own-writes problems (fix by reading the write DB right after a user's own update, or by returning the new version and having the UI wait for the projection to reach it). See Pattern: Scaling Reads.
