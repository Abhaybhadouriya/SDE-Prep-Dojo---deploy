Event sourcing

Normal (CRUD) tables store only the current state: balance = 70. Event sourcing stores the full list of facts that happened - AccountOpened, Deposited 100, Withdrew 30 - in an append-only event store, and computes current state by replaying (folding) them. This is called rehydration. The events are the source of truth; tables become caches you can rebuild.

Why teams choose it
  • Complete audit trail - essential for ledgers, payments, compliance
  • Rebuild any read model or answer "what was the state on 1 March?"
  • Append-only writes avoid update-in-place lock contention
  • Events are a natural feed for other services
What it costs
  • You cannot edit history; bugs need compensating events or upcasters
  • Event schema versioning forever
  • Queries need projections (so you need CQRS) and are eventually consistent
  • Right-to-be-forgotten needs personal data outside events or crypto-shredding
  • Design events around intent. "2 seats reserved" is far more useful than "remaining seats changed to 42" (Azure's example).
  • Concurrency. Two handlers both see "5 seats left". The event store rejects the second append because the stream version moved; the handler reloads and retries.
  • Kafka is not an event store. It is great for distributing events, but it lacks per-entity stream reads and optimistic-concurrency appends. Use a database table (stream_id, version primary key) or a purpose-built store (EventStoreDB) as the system of record, and Kafka to fan out.
  • Use it selectively. Microsoft's own guidance: apply it to the ledger or order pipeline, keep CRUD for profiles and config.

Walmart's inventory-availability write-up and the d41 Digital Wallet & Ledger design are the classic interview homes for event sourcing.
