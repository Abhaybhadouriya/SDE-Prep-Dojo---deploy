Quick quiz

The Order service commits to its DB, then the pod is killed before kafka.send(). What fixes this class of bug?

  1. Writing the event to an outbox table in the same DB transaction and relaying it
  2. Retrying the send three times
  3. Sending to Kafka first, then writing the DB
Retries cannot run if the process is dead, and reversing the order creates phantom events. Only one atomic write plus a relay closes the window.

What is the main weakness of 2PC?

  1. It cannot commit more than two databases
  2. It is eventually consistent
  3. Participants can block holding locks if the coordinator fails after the votes
A YES voter cannot decide on its own, so it waits with locks held until it learns the decision.

In a checkout saga, the card charge succeeds but sending the confirmation fails. What should happen?

  1. Refund the card and release stock
  2. Do nothing
  3. Retry the confirmation (idempotently) until it succeeds
The charge is the pivot. Steps after it are retryable and the saga only moves forward.

Why do outbox events use the aggregate id (for example the order id) as the Kafka key?

  1. To compress messages
  2. So all events for one order go to the same partition and stay in order
  3. So consumers can skip the event id
Kafka orders records only within a partition; the key decides the partition.

Your Kafka Streams app uses exactly-once and calls an SMS API for each record. Can a user get two SMS?

  1. No, exactly-once covers it
  2. Yes - side effects outside Kafka are not covered; the SMS call needs its own idempotency
  3. Only if acks=1
An aborted and retried transaction re-runs the processing, including the external call.

In event sourcing, what prevents two handlers from both booking the last seat?

  1. A nightly batch job
  2. Deleting old events
  3. Appending with an expected stream version, so the second append is rejected
Optimistic concurrency on the stream version; the loser reloads, sees 0 seats and rejects the booking.

Which statement about CQRS is true?

  1. It separates the write model from read models that are usually updated asynchronously
  2. It requires event sourcing
  3. It guarantees strongly consistent reads
CQRS can use a plain DB plus CDC into read stores; reads are usually eventually consistent.

  1. Charge the new amount

  3. Return the original success silently
