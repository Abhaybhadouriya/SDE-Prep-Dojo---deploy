Interview questions

What is the dual-write problem, and how does the outbox pattern solve it?

Writing to the database and then publishing to a broker are two independent operations; a crash between them leaves state changed but no event (or an event for a change that rolled back). The outbox pattern inserts the event into an outbox table in the same local transaction as the business change, so both commit or neither. A relay (polling or CDC such as Debezium) publishes outbox rows to Kafka and retries until acknowledged. Delivery is at-least-once, so consumers deduplicate on the event id.

How to answer

Show the two-line bad code, name the failure window, then the outbox SQL, the relay, and finish with "therefore consumers must be idempotent".

Likely follow-ups
  • Polling vs CDC relay: which and why?
  • How do you keep events for one order in order? (key = aggregate id)
  • How do you stop the outbox table growing forever?
2PC vs saga: when would you use each?

2PC gives atomic, isolated commits but needs every participant to support prepare, holds locks across network round trips, and blocks if the coordinator dies after votes. It fits inside one distributed database that runs 2PC over consensus-replicated shards. Sagas fit across microservices and external APIs: local transactions plus compensations, no global locks, eventual consistency, and you must handle the lack of isolation (semantic locks, commutative updates). For an order-payment-inventory flow across services I pick an orchestrated saga.

How to answer

A two-column comparison: atomicity/isolation, availability, latency, participants supported, failure handling. Then a concrete pick for the interviewer's system.

Likely follow-ups
  • What is the blocking problem in 2PC exactly?
  • What if a compensation fails?
  • Why does 3PC not fix things in practice?
Design an order management flow (place, pay, deliver). How do you keep the services consistent?

An orchestrated saga driven by a state machine: Order (PENDING) - reserve inventory with a TTL - charge payment with an idempotency key (pivot) - confirm and schedule delivery (retryable). Each service writes its state and its outgoing event through an outbox; Kafka carries events keyed by order id; each consumer stores processed event ids. Failures before the pivot trigger compensations in reverse (release stock, cancel order); failures after it are retried. Reservations expire on their own if the saga dies, and a reconciliation job compares payments with orders daily.

How to answer

Draw the four steps, mark compensable / pivot / retryable, then show the outbox and idempotency under each arrow.

Likely follow-ups
  • Where is the saga state stored, and what if the orchestrator crashes?
  • How does the customer see "processing" vs "confirmed"?
  • How do you handle a payment provider timeout? (query by idempotency key before retrying)
Choreography or orchestration for a saga? Defend your choice.

Choreography (services react to each other's events) is simple and has no central component, good for 2-3 steps owned by one or two teams. As steps, branches and timeouts grow, the flow becomes invisible and services couple to each other's events, with risk of cycles. Orchestration puts the flow in one durable state machine (Temporal, Cadence, Step Functions), making status, retries, timeouts and compensation explicit, at the cost of running a highly available orchestrator. For payments or bookings I choose orchestration.

How to answer

Give the decision rule (number of steps, need for visibility), then name a tool.

Likely follow-ups
  • How does a workflow engine survive its own crashes? (event-sourced workflow history)
  • How would you trace a choreographed saga?
How do you make a Kafka consumer handle duplicates safely?

Assume at-least-once: commit offsets only after processing, and make processing idempotent. Either make the write naturally idempotent (upsert by key, set-state rather than increment), or keep a processed-events table and insert the event id in the same DB transaction as the effect, relying on a unique constraint. For Kafka-to-Kafka pipelines use transactions with offsets in the transaction and read_committed consumers. External side effects (payments, emails) need idempotency keys at the provider.

How to answer

"Exactly-once = at-least-once + dedup." Then the three techniques and where each applies.

Likely follow-ups
  • What if processing succeeds but the offset commit fails?
  • How long do you keep processed ids?
  • How do you handle poison messages? (retry topic + DLQ)
Explain how Kafka achieves exactly-once semantics, and where it stops.

The idempotent producer has a producer id and per-partition sequence numbers, so the broker drops duplicate retries. Transactions let a producer (stable transactional.id) write to many partitions and commit its consumed offsets atomically; the coordinator writes commit or abort markers and read_committed consumers skip aborted data. That gives exactly-once for consume-transform-produce inside Kafka. It does not cover side effects in other systems: a database write or an API call needs its own idempotency. Confluent measured about 3% throughput cost for transactional producers with 100 ms transactions.

How to answer

Three layers (idempotence, transactions, read_committed), one boundary sentence, one number.

Likely follow-ups
  • What is a zombie producer and how does fencing via transactional.id epoch stop it?
  • What does a longer commit interval trade off?
When would you use event sourcing, and when would you avoid it?

Use it where history is the product: ledgers, payments, inventory movements, order lifecycles, anything needing an audit trail or rebuilding state at a past point. Events are appended with optimistic concurrency (expected version), snapshots bound replay time, and CQRS projections serve queries. Avoid it for simple CRUD, short-lived systems, or where users need strongly consistent query views, because you pay for schema versioning forever, projections are eventually consistent, and deletion for privacy is hard.

How to answer

Give one fitting domain (ledger) and one non-fitting (user profile), then the four mechanics: append, version check, snapshot, projection.

Likely follow-ups
  • Can Kafka be your event store? (distribution yes, system of record usually no)
  • How do you fix a bug that wrote wrong events?
  • How do you handle GDPR deletion?
What is CQRS? Does it require event sourcing?

CQRS separates the model that handles commands (validate and change state) from models that answer queries (denormalised views such as a search index or cache), updated asynchronously. It does not require event sourcing; a normal database plus CDC into read stores is CQRS. It helps when read and write shapes or volumes differ a lot, and costs a second store, eventual consistency and read-your-own-writes handling.

How to answer

Definition, one picture, "no, it doesn't require ES", then the consistency trade-off and a fix for read-your-writes.

Likely follow-ups
  • How does a user see their own update immediately?
  • How do you rebuild a corrupted projection?
A payment request timed out. Do you retry? How do you avoid charging twice?

A timeout means "unknown", not "failed". Every charge carries an idempotency key generated once per logical payment and stored with the order before calling the provider (pre-RPC). On timeout, retry with the same key, or first query the provider by that key; the provider returns the original result instead of charging again. Record the outcome and whether the error is retryable (post-RPC). Never hold a DB transaction open across the provider call. A daily reconciliation against the provider's settlement report catches anything left.

How to answer

Name the three states (success, failure, unknown), then idempotency key, retry policy with backoff and jitter, reconciliation.

Likely follow-ups
  • What if the provider doesn't support idempotency keys?
  • What if the same key arrives with a different amount?
How would you keep Elasticsearch in sync with your product database?

Not with dual writes from the app. Use log-based CDC: Debezium reads the MySQL binlog or Postgres WAL, publishes row changes to Kafka keyed by primary key (so updates to one product stay ordered), and an indexer consumer upserts documents by id - which is naturally idempotent - and handles deletes via tombstones. Do an initial snapshot or backfill, monitor lag end to end, and design for schema evolution through a schema registry.

How to answer

Reject dual write, draw DB - CDC - Kafka - indexer, then cover ordering, idempotent upsert, deletes, backfill, lag.

Likely follow-ups
  • What happens if the indexer is down for an hour?
  • How do you reindex everything after a mapping change?

Scenario: orders with no stock reservation

Support reports a few hundred orders per week marked PAID with no inventory reserved and no confirmation email. The Order service saves the order and then calls kafka.send(). Error logs show occasional broker timeouts during deploys.

Weak answer: "Add retries around kafka.send() and increase the timeout."

Strong answer: this is the dual-write problem; retries still lose events when the pod is killed during a deploy between commit and send. Introduce an outbox table written in the same transaction, relay it with Debezium (or a poller for a quick win), key events by order id, and make Inventory and Email idempotent on event id. Backfill: find PAID orders with no reservation by joining the two databases (or replaying the outbox once it exists) and re-emit events. Add a reconciliation metric: orders older than 5 minutes without a matching reservation.

Likely follow-ups
  • How do graceful shutdown and preStop hooks reduce this, and why are they not enough?
  • How would you roll this out without downtime?

Scenario: the saga that half-finished

A hotel booking saga reserved the room and charged the card, then the orchestrator pod was evicted before it called the confirmation service. The guest has a charge but no booking email; the room shows as held.

Weak answer: "Refund the card when this happens."

Strong answer: the charge was the pivot, so the saga must move forward, not back. The orchestrator must persist saga state (current step, idempotency keys) durably before and after each step - workflow engines like Temporal do this by recording an event history - so a new orchestrator instance resumes at "confirm" and retries it with the same key until it succeeds. Confirmation must be idempotent. Add a timeout watchdog that alerts if a saga stays in one step too long.

Likely follow-ups
  • What if confirmation is impossible (hotel closed)? (business compensation: refund + apology, a new saga)
  • Where would you store saga state?
