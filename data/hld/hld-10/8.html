Idempotent consumers and idempotency keys

An operation is idempotent if doing it twice has the same effect as doing it once. Every at-least-once system (outbox relays, CDC, Kafka consumers, HTTP retries, saga steps) depends on it. There are three common techniques:

  1. Naturally idempotent writes. SET status = 'PAID' or an upsert keyed by id is safe to repeat; balance = balance - 10 is not.
  2. Processed-message table. Store each handled event id in the same transaction as the business change. A unique constraint turns a duplicate into a no-op.
  3. Idempotency keys on APIs. The client generates a key per logical request and sends it on every retry; the server stores the key with the result and returns the same response for repeats. AWS calls it a ClientToken (EC2 RunInstances returns the same instance on a retry); Stripe uses an Idempotency-Key header.
-- consumer: dedup and effect in ONE local transaction
BEGIN;
  INSERT INTO processed_events (event_id, consumer)
       VALUES ('7f3c...e1', 'inventory')
  ON CONFLICT DO NOTHING;              -- 0 rows inserted => duplicate, skip
  -- only if 1 row was inserted:
  UPDATE stock SET reserved = reserved + 1
   WHERE sku = 'robot-1' AND reserved < on_hand;
  -- if 0 rows updated (out of stock): INSERT a ReservationFailed event
  -- into the outbox in this same transaction, so the saga orchestrator
  -- learns about it and can compensate (never drop it silently)
COMMIT;                                -- then commit the Kafka offset

Details that separate good answers from great ones (from the AWS Builders' Library and Airbnb's payments team):

  • Record the key and the effect atomically. Never save the token without the change, or the change without the token.
  • Return a semantically equivalent response to a retry, not an "already exists" error the caller cannot interpret.
  • Same key, different parameters is an error - store the original request fingerprint to detect it.
  • Do not mix network calls into DB transactions. Airbnb's Orpheus library splits each request into pre-RPC (record intent in the DB), RPC (call the provider), post-RPC (record the result and whether it is retryable) and wraps only the DB phases in transactions.
  • Keep keys long enough to cover every plausible retry, then expire them.

The idempotent consumer in three steps

  1. Process once. Message id 77 arrives. In one database transaction the consumer inserts 77 into processed_ids and reserves the stock. Both rows commit together.
  2. Crash before the offset. The consumer dies after the DB commit but before it commits its Kafka offset. Kafka still thinks 76 is the last one handled, so it will deliver 77 again.
  3. Redelivery is skipped. After restart, 77 arrives again. The insert hits the primary key, ON CONFLICT DO NOTHING reports 0 rows, so the consumer skips the stock update and just commits offset 77. Stock was reserved exactly once.

From your world

This is TCP's receive side. A retransmitted segment whose sequence number is already below rcv_nxt is dropped and simply ACKed again; the application never sees it twice. processed_ids is your sequence-number check, and committing the Kafka offset is the ACK. Where this breaks: TCP's sequence numbers are one ordered counter per connection, but message ids are random and arrive out of order across partitions, so you need a real table (with expiry), not a single "highest seen" number.
