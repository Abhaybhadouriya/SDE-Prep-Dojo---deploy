Exactly-once with Kafka

Networks force a choice: if you never retry you may lose messages (at-most-once); if you retry you may duplicate them (at-least-once). "Exactly-once" in practice means at-least-once delivery plus deduplication, so the effect happens once. Kafka provides this inside Kafka with three features:

  1. Idempotent producer. The broker gives each producer an id, and the producer numbers every batch per partition. A retried batch with a sequence number the broker already has is dropped, so retries cannot create duplicates or reorder. On by default since Kafka 3.0 along with acks=all.
  2. Transactions. A producer with a transactional.id can write to many partitions atomically: all the records become visible, or none do. A transaction coordinator in the broker keeps the state in an internal replicated topic.
  3. Offsets in the transaction. In a consume-transform-produce loop, the consumer's offset commit is part of the same transaction as the output. Readers with isolation.level=read_committed never see aborted output. Kafka Streams turns all of this on with one setting.
// producer side (Kafka 3.x / 4.x client)
props.put("enable.idempotence", "true");           // default since 3.0
props.put("acks", "all");                           // default since 3.0
props.put("transactional.id", "payments-proc-1");   // stable per processor instance
producer.initTransactions();

producer.beginTransaction();
producer.send(new ProducerRecord<>("ledger", key, value));
producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
producer.commitTransaction();                       // or abortTransaction() on error

// consumer side
props.put("isolation.level", "read_committed");

Idempotent producerNegligible throughput impact

Kafka Streams exactly-once, 30 s commit intervalNo measurable overhead for messages of 1 KB or more

The boundary: Kafka's exactly-once covers Kafka-to-Kafka. The moment your consumer calls a payment API, sends an email or writes to Postgres, Kafka cannot undo that side effect on abort. Exactly-once end to end needs an idempotent sink: an upsert keyed by event id, or a processed-events table updated in the same DB transaction as the effect.

From your world

The idempotent producer is TCP's sequence numbers at the application layer: the receiver tracks the next expected sequence per (producer, partition) and silently drops retransmitted segments. Transactions with commit markers are like a two-phase barrier in a DMA ring: descriptors are written but only become visible to the consumer when the "valid" bit is flipped for the whole batch.
