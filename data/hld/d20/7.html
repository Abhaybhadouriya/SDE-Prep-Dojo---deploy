Where Kafka, Kubernetes and Docker fit

Docker: run the whole thing on your laptop in 2 minutes

# prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ["localhost:9090"]
  - job_name: node
    static_configs:
      - targets: ["node-exporter:9100"]
$ docker network create mon
$ docker run -d --name node-exporter --network mon prom/node-exporter
$ docker run -d --name prometheus --network mon -p 9090:9090 \
    -v "$PWD/prometheus.yml:/etc/prometheus/prometheus.yml" prom/prometheus
$ curl -s 'localhost:9090/api/v1/query?query=up' | jq -c '.data.result[] | [.metric.job, .value[1]]'
["node","1"]
["prometheus","1"]

up = 1 means the last scrape worked. Stop the node-exporter container and within one scrape interval you will see ["node","0"] - your first "target down" signal. (Docker basics: Docker Compose to keep this in one file.)

Kubernetes: discovery, operator and autoscaling

On Kubernetes, the Prometheus Operator adds CRDs so teams declare what to scrape, and the operator writes the Prometheus config. A ServiceMonitor says "scrape every Service with this label on this port":

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: checkout
  namespace: checkout
  labels: { release: prometheus }
spec:
  selector:
    matchLabels: { app: checkout }
  endpoints:
    - port: http-metrics
      interval: 15s
      path: /metrics

Kubernetes itself is a heavy metrics user: kubelet exposes container CPU/memory (cAdvisor), kube-state-metrics turns object state (desired vs ready replicas) into series, and the HPA reads metrics to scale pods (Scheduling & Autoscaling, Observability & Troubleshooting). The long-term store (ingesters, store gateways) runs as StatefulSets with persistent volumes (StatefulSets & Operators).

Kafka: monitored, and sometimes the pipe

Monitoring Kafka is a classic follow-up. The broker metrics the research notes mark as must-alert: UnderReplicatedPartitions > 0, OfflinePartitionsCount > 0 (outage), ActiveControllerCount must be exactly 1 across the cluster, request handler and network processor idle percent (low = saturated), request latency p99, bytes in/out, ISR shrink rate, and consumer lag. Lag is best alerted in seconds behind, not raw message counts. See Kafka operations.

Kafka as the pipe: Prometheus does not need Kafka. But at very large scale, or when many consumers want the same metric stream (anomaly detection, billing, a second vendor), some teams put a Kafka topic between collectors and the storage tier as a buffer, keyed by series ID so each series stays in order on one partition. Say it as an option with a cost (extra latency and another system), not as a default.
