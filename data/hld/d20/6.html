1. Pull vs push

Pull (scrape)Push
Who controls loadThe monitor (it cannot be flooded)Clients (a buggy client can flood you; needs rate limits)
Dead target detectionFree: scrape fails → up == 0Need "no data for N minutes" logic
Short-lived jobsAwkward (Pushgateway)Natural
Firewalls / NAT / serverlessHard: monitor must reach targetsEasy: outbound only
DebuggingOpen /metrics in a browserNeed to inspect the collector
Who uses itPrometheusGoogle Monarch, OpenTelemetry OTLP, Datadog agents, network streaming telemetry

Good interview answer: "Inside our Kubernetes clusters I use pull, because service discovery is easy and failed scrapes double as health checks. For short-lived jobs, edge devices and serverless functions I accept push through an OpenTelemetry Collector, which converts to the same storage. The store does not care how samples arrived."

2. Cardinality: the number that decides everything

The number of series for one metric is the product of the number of values of each label. This is the most important formula on this page:

  • Rule: label values must come from a small, bounded set. Never use user IDs, order IDs, emails, full URLs with IDs, or timestamps as labels. Prometheus's own naming guide warns about this.
  • Guard rails: per-tenant limits on active series and on series per metric at the distributor; sample_limit per scrape job so one bad target is rejected instead of poisoning the server; relabel rules that drop dangerous labels.
  • Find the culprit: the TSDB status page lists the metrics and labels with the most series.
$ curl -s localhost:9090/api/v1/status/tsdb | jq '.data.seriesCountByMetricName[0:3]'
[
  { "name": "http_request_duration_seconds_bucket", "value": 412360 },
  { "name": "container_memory_working_set_bytes",   "value": 98211 },
  { "name": "kafka_consumergroup_lag",               "value": 40112 }
]

Interviewers love: "Metrics answer 'how many, how fast', for groups. If you need per-user detail, that is a log or an event, not a metric."

3. Inside the TSDB: WAL, head block, compression

Prometheus's storage is a small, beautiful piece of systems engineering - you will enjoy it.

  • WAL: every incoming sample is appended to a write-ahead log on disk, like a filesystem journal. On crash, Prometheus replays the WAL to rebuild memory.
  • Head block: the last ~2 hours live in memory, organised per series.
  • Blocks: every 2 hours, the head is written as an immutable block directory: chunks/, an index (posting lists), meta.json and tombstones. Background compaction merges small blocks into larger ones. Deleting old data = deleting whole block directories (cheap, like dropping a whole Kafka segment).
  • Compression (Gorilla-style): timestamps arrive at a regular interval, so store the difference of differences - usually 0, which costs 1 bit. Values change slowly, so XOR each value with the previous one and store only the changed bits. Facebook's Gorilla paper reported about 1.37 bytes per sample this way; Uber's M3TSZ is based on the same idea.

From your world

The WAL is your ext4 journal (jbd2): append first, apply later, replay on crash. Delta-of-delta is the same idea as run-length or delta encoding you have seen in packet-capture compression or hardware counter snapshots: send what changed, not the whole value. And dropping whole 2-hour blocks for retention is like freeing whole pages instead of individual objects. Where this breaks: a filesystem journal protects metadata you cannot afford to lose; Prometheus accepts losing a few seconds of samples, so it does not fsync every write, and a crash can lose the last moments of data. Monitoring trades a little durability for speed on purpose.

4. Scaling past one Prometheus server

  1. Vertical first. One Prometheus can go a long way. Scale up until memory (active series) hurts.
  2. Functional sharding. One Prometheus per cluster or per team. Simple, but no global view.
  3. Hash sharding. Within a big job, N servers each scrape the targets where hashmod(address, N) == i.
  4. HA pairs. Run two identical replicas per shard. Both scrape and both fire alerts; Alertmanager dedups; the long-term store dedups samples by replica label.
  5. Global view + long retention. Remote-write everything into a horizontally scalable store (Mimir/Cortex, Thanos, M3) that replicates each series to 3 ingesters and keeps blocks in object storage. Downsample old data (5 min, 1 h).

From your world

Remote write behaves like TCP retransmission with backoff. Each Prometheus server keeps a queue of samples (read from its WAL) per remote endpoint; if the store answers 5xx or times out, it retries with exponential backoff, and it only moves its read position forward when a batch is acknowledged. A store outage shows up as growing "pending samples", like a growing send buffer. Where this breaks: TCP's buffer is bounded and the sender blocks; Prometheus's buffer is the WAL, which is cut at the 2-hour block boundary. An outage longer than about 2 hours means the oldest unsent samples are gone from the WAL and never reach the long-term store, even though local queries still show them.

5. Alerting that people do not hate

  • Alert on symptoms, not causes. Page on "checkout error rate above 2% for 5 minutes" or "p99 latency above 1 s", which users feel. CPU at 90% is a cause; put it on a dashboard or a ticket, not a 3 AM page.
  • SLO burn-rate alerts. If the SLO allows 0.1% errors per month, page when the error budget is being burned 14.4x faster than allowed over 1 hour, paired with a 5-minute short window so the page stops quickly once the fire is out (the Google SRE workbook figure: 14.4x for an hour spends 2% of a 30-day budget). This catches big fires fast and slow leaks eventually, with few false alarms. See SLOs & reliability.
  • Grouping, inhibition, silences. If a whole region is down, inhibit the 400 per-service alerts under the one "region down" alert.
  • Every page needs a runbook link and an owner label.
# alert-rules.yaml
groups:
  - name: checkout-slo
    rules:
      - record: service:http_errors:ratio_rate5m
        expr: |
          sum by (service) (rate(http_requests_total{status=~"5.."}[5m]))
            /
          sum by (service) (rate(http_requests_total[5m]))
      - alert: CheckoutHighErrorRate
        expr: service:http_errors:ratio_rate5m{service="checkout"} > 0.02
        for: 5m
        labels:
          severity: page
          team: checkout
        annotations:
          summary: "Checkout 5xx above 2% for 5 minutes"
          runbook_url: "https://runbooks.example.internal/checkout-5xx"   # the name Grafana and kube-prometheus render as a link
# alertmanager.yaml (routing tree)
route:
  receiver: default-slack
  group_by: [alertname, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: [ 'severity="page"', 'team="checkout"' ]
      receiver: checkout-pagerduty
inhibit_rules:
  - source_matchers: [ 'alertname="RegionDown"' ]
    target_matchers: [ 'severity="page"' ]
    equal: [ region ]
