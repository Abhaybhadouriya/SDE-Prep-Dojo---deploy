Data model

A time series is identified by its metric name plus its full set of labels. Change any label value and you have a different series:

http_requests_total{service="checkout", method="POST", status="200", region="ap-south-1"}
http_requests_total{service="checkout", method="POST", status="500", region="ap-south-1"}   # a different series
Metric typeWhat it isExampleHow you query it
CounterOnly goes up (resets on restart)http_requests_totalrate(x[5m]) = per-second increase
GaugeGoes up and downmemory_used_bytes, queue depthUse directly, avg_over_time
HistogramCounts per latency bucket (le = "less or equal")http_request_duration_seconds_buckethistogram_quantile(0.99, ...)
SummaryQuantiles computed in the apprpc_duration_seconds{quantile="0.99"}Cannot be aggregated across pods - prefer histograms

Storage choice: not SQL, not a general NoSQL store. Metrics are append-only, time-ordered, mostly-recent reads, and regular in time - perfect for a purpose-built TSDB (Prometheus TSDB, Mimir/Cortex, Thanos, M3DB, VictoriaMetrics). A generic store would waste 10-20x more space because it cannot use the delta tricks below.
