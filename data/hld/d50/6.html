Deep dives

1. Turning counts into a stable multiplier

Raw demand / supply per cell per minute is noisy: one cell might have 3 requests and 0 drivers this minute, giving an infinite ratio. A production design layers several controls. Uber has not published its formula, so present these as a reasonable design, not as Uber's exact method:

  1. Spatial smoothing Blend each cell with its ring of 6 neighbours (H3 gridDisk(cell, 1)). Drivers 300 m away are real supply. Hexagons make this one uniform weight.
  2. Sparse roll-up If a cell has fewer than N events, use its parent cell's ratio (res 8 to res 7).
  3. Temporal smoothing Exponentially weighted moving average: s_t = a * r_t + (1 - a) * s_(t-1), so a single spike does not flip the price.
  4. Curve and caps Map the smoothed ratio to a multiplier with a monotonic curve, floor at 1.0, cap per city or by regulation, and round to steps (1.1, 1.2...).
  5. Hysteresis Raise quickly, lower slowly (or need the ratio to drop below a lower threshold), so prices do not flap every minute.
  6. Forecast A model can add predicted demand (concert ends at 22:00) so supply is nudged before the spike.

From your world

This is congestion control. The EWMA is the same trick as TCP's smoothed RTT estimator. Hysteresis is like a link-flap dampening timer, and "raise fast, lower slowly" is the mirror of TCP's additive-increase / multiplicative-decrease. A controller with too much gain and too much delay oscillates, whether it controls a window size or a price.

2. Freshness over consistency in the stream

  • Event time, not arrival time. Windows use the timestamp from the phone. A watermark (event time minus allowed lateness, say 10 s) closes each window. Events behind the watermark are dropped. Uber: "late-arriving messages do not contribute to the surge computation".
  • Lossy-but-fast Kafka. Using acks=1 and a throughput-tuned cluster is acceptable because the next ping replaces the lost one in 5 s. Compare payments, where you would use acks=all and idempotent producers (Delivery semantics).
  • Deduplicate supply. Count distinct drivers per cell per window, not pings (a driver sends 12 pings a minute). Use a set of driver ids per cell, or HyperLogLog if cardinality is large (Big Data & Streaming).
  • Hot cells. A stadium cell gets a burst of events. Pre-aggregate in a combiner before the keyed shuffle (local counts per task, then merge), the same trick as in Ad Click Aggregator.

3. Multi-region: active-active without replicating state

Uber's paper describes the disaster-recovery design. Trip events go to regional Kafka clusters, then are replicated into aggregate clusters that hold the global view. Every region runs the same large-memory Flink job on the same aggregate input, so every region computes the same state. An all-active coordinator marks one region's "update service" as primary; only the primary writes results to an active/active database. If that region fails, the coordinator promotes another region, whose Flink job is already warm.

The trade-off is cost: you run redundant pipelines everywhere. The paper contrasts this with an active/passive consumer mode for jobs that can tolerate a slower failover. See Reliability, Multi-Region & DR.

4. ETA: routing engine plus an ML residual

Uber's routing post tells the history, and it is a great interview story:

  • Road graph: intersections are nodes, road segments are edges, weights are travel time. Plain Dijkstra is too slow in production.
  • Contraction hierarchies (used by OSRM) answer in a few ms by preprocessing, but rebuilding the world graph took about 12 hours, so live traffic could not be used. Even dynamic re-weighting took about 10 minutes when 10% of segments changed. Too slow.
  • A* handles live weights with no preprocessing and is fine for short pickup trips, but a cross-city route took ~120 ms.
  • Uber's answer (Gurafu, 2015): split the graph into layers of small, relatively independent cells, and rerun preprocessing only for the cells whose traffic changed, in parallel. Result: hundreds of thousands of ETA requests per second at single-digit ms. (This is the idea behind customizable route planning.)
  • Live speeds come from map-matching drivers' GPS traces to road segments and aggregating speeds per segment (Uber's historical traffic system was called Flux).

Then the ML layer. The DeepETA post says the routing engine is the "physical model", and an ML model predicts the residual (real arrival time minus routing ETA) from origin, destination, time, live traffic and request type. Uber first used one of the largest XGBoost ensembles, then moved to a deep model with a linear transformer encoder. To stay within "a few milliseconds", it discretises every input and looks up embeddings (lat/lng are hashed into multi-resolution grids), so one prediction touches only about 0.25% of hundreds of millions of parameters. It trains with an asymmetric Huber loss so a business can say "being late is worse than being early". Requests go through uRoute (routing front end) to the routing engine and then to Michelangelo online prediction.

5. Price lock, fairness and auditing

  • Quote = contract. Store quote id, price, surge version, route ETA with a TTL. Booking reads the quote strongly (single-key read); if expired, re-quote.
  • Idempotent booking. Idempotency key so a double tap does not create two rides (Payment System).
  • Audit trail. Persist every published surge snapshot (cell, multiplier, inputs) to the lake so you can explain any price later and train better models.
  • Guardrails. Caps during emergencies, kill switch per city, alerts when a city's average multiplier jumps unusually.
