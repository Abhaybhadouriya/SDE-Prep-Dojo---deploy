Architecture, step by step

Click Next or Play. Steps 1-5 are the surge pipeline (asynchronous, every minute). Steps 6-8 are the synchronous quote path a rider hits.

  1. Ingest. Driver location pings and rider demand events (fare views, requests, trip state) land in Kafka, keyed so a cell's events go to one partition. Uber's paper notes surge uses a Kafka cluster tuned for throughput, not lossless delivery.
  2. Aggregate. A Flink job (a stream processor that keeps per-key state in memory) maps each event to its H3 cell and counts per cell, per product, per 1-minute tumbling window (fixed back-to-back 60 s buckets). Watermarks ("all events up to time T have arrived") close the window on time; late events are dropped, by design. See the picture below the stepper.
  3. Price. For each cell, a pricing model turns demand vs supply into a multiplier and smooths it across neighbouring cells and over time. Uber says this is "a complex machine-learning based algorithm in Flink"; the exact formula is not public.
  4. Publish. Changed multipliers are written to a key-value store, each value tagged with a version (the window timestamp), so readers can tell how fresh it is and a quote can record exactly which value it used. Only cells that changed need writing.
  5. Tell drivers. The heatmap service pushes surge areas to driver apps, which is how surge pulls supply toward demand.
  6. Quote request. A rider asks for a price. The quote service converts the pickup point to an H3 cell id and reads the multiplier from an in-memory cache of the KV store.
  7. ETA. It calls the ETA service, which asks the routing engine for a route time on the live road graph, then asks an ML model to predict the error, called the residual (actual arrival time minus routing time, for example +40 s for a hard pickup spot), and adds it.
  8. Lock the price. The quote (price, surge version, ETA) is stored with a short TTL and returned. Booking with the quote id honours that price even if surge changes a second later.

From your world

A tumbling window is a fixed 60-second bucket per key, exactly like a NetFlow/IPFIX exporter with an active timeout: count packets per flow, and every 60 s export the record and start a fresh one. A watermark is the exporter saying "I believe every packet stamped before time T has now arrived", so the bucket for [T-60 s, T) can be closed and exported. A packet that turns up after that is late: either you drop it (surge does) or you send a correction. Waiting longer means more complete counts but staler prices.
