Data model: two very different kinds of data

Split the data by how it behaves. Hot, disposable, high-rate: the latest driver positions and statuses, which change every few seconds and can be rebuilt from the next pings. That lives in memory. Cold, precious, low-rate: trips, fares, payments, which must never be lost or duplicated. That lives in a transactional, strongly consistent store. See Choosing Storage and Geospatial Indexes.

CREATE TABLE trips (
  trip_id        BIGINT PRIMARY KEY,          -- Snowflake-style id
  city_id        INT NOT NULL,                -- shard key
  rider_id       BIGINT NOT NULL,
  driver_id      BIGINT,                      -- NULL until matched
  state          VARCHAR(16) NOT NULL,        -- REQUESTED, MATCHED, ARRIVING, IN_TRIP, COMPLETED, CANCELLED
  fare_paise     BIGINT,
  pickup_lat     DOUBLE PRECISION, pickup_lng DOUBLE PRECISION,
  drop_lat       DOUBLE PRECISION, drop_lng   DOUBLE PRECISION,
  idempotency_key UUID UNIQUE,                -- the rider's request key
  version        INT NOT NULL DEFAULT 0,      -- optimistic locking
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Only one active trip per driver, enforced by the database itself
CREATE UNIQUE INDEX one_active_trip_per_driver
  ON trips (driver_id)
  WHERE state IN ('MATCHED','ARRIVING','IN_TRIP');

-- Move a trip forward only from the state we expect (no lost updates)
UPDATE trips SET state = 'IN_TRIP', version = version + 1, updated_at = now()
 WHERE trip_id = 5521 AND state = 'ARRIVING' AND version = 3;   -- 1 row = success, 0 rows = someone else won
# location service: store the latest point (geohash inside a sorted set)
GEOADD drivers:blr:mini 77.59410 12.97231 d42
GEOADD drivers:blr:mini 77.60102 12.96810 d77
# matching: free drivers within 2 km, nearest first
GEOSEARCH drivers:blr:mini FROMLONLAT 77.5946 12.9716 BYRADIUS 2 km ASC COUNT 10 WITHDIST
# driver state with a TTL: no ping for 30 s means the key expires (driver gone)
SET driver_state:d42 AVAILABLE EX 30

Output shape from redis-cli (Redis 6.2+ or Valkey); distances are in km and approximate. Try it with docker run --rm -p 6379:6379 redis:7. Note: GEOADD takes longitude first, then latitude, a classic bug.

  • Why SQL for trips? We need transactions, unique constraints ("one active trip per driver") and conditional updates. 700 writes/s per region is tiny for sharded Postgres/MySQL. Uber itself built a MySQL-based store called Schemaless for trip data.
  • Why shard by city? Almost every query is local: a rider in Bengaluru never needs a driver in Delhi. City sharding keeps matching in one shard and limits the blast radius of a failure. Big cities can be split further by region.
  • Why a TTL on driver state? Phones die, tunnels happen. Instead of a cleanup job, the key simply expires if pings stop, and the driver drops out of matching.
