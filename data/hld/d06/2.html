Back-of-envelope estimation

Round assumptions, not Uber's real numbers (except where noted). Method from Back-of-Envelope Estimation: 1 day = 86,400 s, round to 105.

~250K/slocation writes, peak
~700/sride requests, peak
~100 MBRAM for all live positions
~400K/s"cars near me" map reads
  1. Location writes 1M online drivers, one ping every 4 s: 1,000,000 / 4 = 250,000 writes/s at peak. This is the biggest number in the design, and it is why locations do not go into the SQL trip database.
  2. Ping size and bandwidth driver id, lat, lng, heading, speed, timestamp, status: about 100 bytes with framing. 250K x 100 B = 25 MB/s in. Small for the network; the cost is the write rate, not the bytes.
  3. Memory for live positions Only the latest point per driver matters for matching: 1M x ~100 B = ~100 MB. That fits in one machine's RAM! So we shard the geo index for write throughput and availability, not for size. Say this out loud; it surprises interviewers.
  4. Ride requests 20M trips/day / 86,400 is about 230 trips/s on average. Peaks (Friday night, rain, festivals) maybe 3x: ~700 requests/s. Each one triggers a geo search, a few ETA calls and an offer. Low QPS, but every one matters (money, a person waiting).
  5. Map reads Before requesting, riders see nearby cars. If 2M riders have the app open at peak and refresh every 5 s: ~400K reads/s. Trick: they do not need exact positions. Compute "cars in cell X" once per second per cell and cache it; thousands of riders in the same cell share one answer.
  6. Trip storage One trip row with pickup, drop, fare, status history: ~2 KB. 20M x 2 KB = 40 GB/day, about 15 TB/year before replicas. A sharded SQL or strongly consistent store handles this.
  7. GPS traces (for fares, safety, disputes) A 20-minute trip with a ping every 4 s is 300 points of ~50 B = 15 KB. 20M x 15 KB = 300 GB/day. Written once, read rarely: append to Kafka, then to cheap storage (Cassandra or object storage).
  8. Offers If the first driver declines 30% of the time (assumption), each request needs about 1.4 offers on average, so ~1,000 offers/s at peak, each with a 15 s timer. Timers live in memory in the matching service, not in a database.

What the numbers decided: 250K writes/s of throwaway data -> in-memory geo index + Kafka, not SQL. 100 MB total -> shard by city/region for throughput and blast radius. 700 requests/s that must be correct -> strongly consistent trip store with atomic driver locks. 400K map reads/s of fuzzy data -> per-cell cache.
