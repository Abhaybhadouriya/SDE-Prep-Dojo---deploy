Key APIs

The driver app keeps a long-lived connection (WebSocket or a gRPC stream) so it can stream locations up and receive offers down without polling. The rider app uses normal HTTPS for actions and a stream for live updates. Uber built its own push platform for this server-to-app direction. See API Design & Communication.

// driver -> server, every ~4 s (can batch 2-3 points on weak networks)
{ "type":"loc", "points":[{"lat":12.97231,"lng":77.59410,"heading":87,"speed_mps":8.2,"ts":1763920801000}],
  "status":"AVAILABLE" }

// server -> driver: an offer with a deadline
{ "type":"offer", "offer_id":"of_771", "ride_id":"r_5521", "pickup":{"lat":12.9716,"lng":77.5946},
  "pickup_eta_s":180, "expires_in_s":15 }

// driver -> server
{ "type":"accept", "offer_id":"of_771" }      // or { "type":"decline", ... }

// trip actions (also allowed over HTTPS)
{ "type":"arrived", "ride_id":"r_5521" }
{ "type":"start_trip", "ride_id":"r_5521", "otp":"4821" }
{ "type":"end_trip", "ride_id":"r_5521" }
  • Money as integers in the smallest unit (paise, cents), never floats.
  • 202 Accepted for a ride request: matching is asynchronous; the app then listens for updates.
  • Offers carry an offer_id, so a late or duplicated "accept" for an old offer can be rejected safely.
  • Driver and rider ids come from auth tokens, never from the request body.
