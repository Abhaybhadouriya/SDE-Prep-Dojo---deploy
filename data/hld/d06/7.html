Where Kafka, Kubernetes and Docker fit

Kafka

Kafka carries two very different streams. Uber is one of the largest Kafka users in the world (its engineering blog reports trillions of messages and multiple petabytes a day), and ride hailing shows why. New to these words? Read Core Concepts.

$ kafka-topics.sh --bootstrap-server localhost:9092 --create --topic driver-latest \
    --partitions 24 --replication-factor 3 --config cleanup.policy=compact
Created topic driver-latest.
$ kafka-console-producer.sh --bootstrap-server localhost:9092 --topic driver-latest \
    --property parse.key=true --property key.separator=:
>d42:{"lat":12.97231,"lng":77.59410,"ts":1763920801000}
>d42:{"lat":12.97302,"lng":77.59488,"ts":1763920805000}

After compaction runs, only the second (newest) value for key d42 remains. Compaction is lazy, so consumers may still see older values for a while. Read Storage Internals for how it works.

  • Why key by driver, not by cell? A driver moves between cells; keying by cell would split one driver's pings across partitions and reorder them. Consumers that need cells (surge) compute the cell themselves.
  • Retries without blocking: a payment consumer that fails on one trip should not block the partition. Uber's "reliable reprocessing" design moves failures to retry topics with growing delays and finally a dead-letter topic. See Stream Processing, Retries & DLQ.
  • Outbox: the ride service writes the trip row and an outbox row in one transaction, and a relay (or Debezium CDC) publishes to trip-events. No dual write.

Kubernetes

Most services (ride, ETA, payments, notification) are stateless Deployments with autoscaling. The interesting ones are the location and matching servers, because each owns a slice of the map in memory:

apiVersion: apps/v1
kind: StatefulSet                 # stable names: matching-blr-0, -1, -2 own fixed cell ranges
metadata:
  name: matching-blr
spec:
  serviceName: matching-blr
  replicas: 3
  podManagementPolicy: Parallel
  selector: { matchLabels: { app: matching, city: blr } }
  template:
    metadata: { labels: { app: matching, city: blr } }
    spec:
      topologySpreadConstraints:              # one replica per zone
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector: { matchLabels: { app: matching, city: blr } }
      containers:
      - name: matching
        image: registry.example.com/matching:5.2.0
        env:
        - { name: CITY, value: "blr" }
        - { name: POD_NAME, valueFrom: { fieldRef: { fieldPath: metadata.name } } }  # decides which cells this pod owns
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }    # ready only after the geo index is warmed from driver-latest
        resources:
          requests: { cpu: "4", memory: "8Gi" }
          limits:   { memory: "8Gi" }
  • Readiness after warm-up: a new matching pod reads the compacted driver-latest topic (or simply waits one or two ping intervals) before it reports ready. Otherwise it would answer "no drivers nearby".
  • Headless Service gives each pod a stable DNS name (matching-blr-0.matching-blr), so the ride service can route a request to the owner of a cell. See StatefulSets & Operators.
  • The control plane is not on the hot path: if the Kubernetes API server is down, running pods keep matching. Only new scheduling stops. See K8s Architecture.
  • Scale ahead of known peaks (New Year's Eve, festivals, big matches): autoscalers react in minutes, crowds arrive in seconds.

Docker

Every service is an image. For learning, a Compose file with Redis, a single KRaft Kafka broker and a tiny fake-driver simulator lets you watch GEOSEARCH answers change as cars move:

# compose.yaml - local ride-hailing lab
services:
  redis:
    image: redis:7
    ports: ["6379:6379"]
  kafka:
    image: apache/kafka:4.3.2            # Kafka 4.x: KRaft only (same image as Build It Locally)
    ports: ["29092:29092"]               # host tools: localhost:29092; containers: kafka:9092
    environment:                         # set any KAFKA_* and the image needs the full set
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093,HOST://:29092
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,HOST://localhost:29092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,HOST:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
  driver-sim:
    build: ./driver-sim                  # sends GEOADD + Kafka pings for 200 fake drivers every 4 s
    environment: { REDIS_URL: "redis://redis:6379", KAFKA_BOOTSTRAP: "kafka:9092", DRIVERS: "200" }
    depends_on: [redis, kafka]
  matching:
    build: ./matching
    ports: ["8080:8080"]
    environment: { REDIS_URL: "redis://redis:6379" }
    depends_on: [redis]

Why the long Kafka block: with default settings the image advertises localhost:9092, so driver-sim (which bootstraps to kafka:9092) would be told to reconnect to its own localhost and fail. KAFKA_ADVERTISED_LISTENERS gives containers kafka:9092 and your laptop localhost:29092. See Docker Compose and the Build It Locally lab, which uses the same image, for a full working setup.
