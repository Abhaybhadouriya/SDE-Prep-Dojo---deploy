1. The geo index: geohash vs quadtree vs S2 vs H3

"Find points near me" on a 2-D map is hard for normal database indexes, which sort along one dimension. Every option turns 2-D space into cells with ids, so "near" becomes "same or neighbouring cell".

# H3 (pip install h3, v4 API): pickup cell plus its ring of neighbours
import h3
cell = h3.latlng_to_cell(12.9716, 77.5946, 9)   # resolution 9: a cell is roughly city-block sized
search = h3.grid_disk(cell, 1)                   # the cell + 6 neighbours = 7 cells
print(len(search))                               # 7 (for a normal hexagon)
# widen the search if too few drivers: grid_disk(cell, 2) gives 19 cells

Cell sizes per resolution are listed in the H3 docs; pick the resolution so a cell holds a useful number of drivers in a busy area.

Interview line: "I would start with geohash or Redis GEO because it is simple, always query the neighbours to avoid the boundary bug, and move to H3 or S2 if we need uniform neighbours for things like surge pricing." Uber open-sourced H3 in 2018 and computes surge per hexagon.

2. Matching without double booking

Two riders near each other request at the same moment. Both matching calls find driver D42 as the best. Without care, D42 gets two offers, or worse, two trips. The fix is a state machine with atomic transitions for the driver and the trip:

  • Driver reservation: in Redis, a small Lua script that checks state == AVAILABLE and sets OFFERED:ride_id with a short TTL, all in one atomic step. Or route all offers for a city through one matching shard owner (single writer) so there is no race at all.
  • Trip commit: the final MATCHED write happens in the SQL trips DB with a conditional update and the unique "one active trip per driver" index. Even if the cache lock had a bug, the database refuses the second trip. Belt and braces.
  • Offer expiry: the TTL on OFFERED means a crashed matching server cannot keep a driver locked forever.
  • Late accepts: an accept for an expired offer_id is rejected politely; the driver sees "this ride was taken".
  • Batch matching (good to know): instead of greedily matching each request, collect requests and drivers for 1-2 seconds in an area and solve an assignment problem that minimises total pickup time. Food-delivery companies use the same idea for riders. It trades a little latency for better global matches.

From your world

The driver lock is a compare-and-swap with a lease, like the ownership word on a shared DMA descriptor ring: the producer only writes a descriptor whose owner bit says "free", atomically. The TTL is the lease that protects you from a dead owner, like a watchdog that reclaims a descriptor stuck with a crashed core. Martin Kleppmann's point about locks applies too: a lease alone can be violated by a long pause, which is why the final truth is the database's conditional update (a fencing check: a fencing token is a number that increases with each lock grant, so the database rejects writes from an older lock holder). Where it breaks: a DMA owner bit is flipped by one atomic instruction on shared memory with no delays; a Redis lease travels over a network, the holder can pause (GC, VM stall) past its TTL and still believe it owns the driver, so the cache lock alone is never enough.

3. The location firehose and hot cells

  • Shard by geography: each city (or region of a big city) is owned by a set of location and matching servers. Uber's early dispatch system sharded by S2 cell using Ringpop, its gossip plus consistent-hash-ring library (gossip = each node periodically tells a few random peers what it knows, so membership news spreads like a flooding protocol), so a server "owns" some cells and requests for those cells are forwarded to it.
  • Drop, do not queue: if a location server is overloaded, dropping an old ping is fine, because a fresher one arrives in 4 s. Never let a backlog of stale positions build up (keep only the newest per driver).
  • Hot cells: when a concert ends, thousands of riders and hundreds of drivers sit in a few cells near the stadium or airport. Fixes: use finer cells there (or a quadtree that splits automatically), cap the candidate list, cache "nearby cars" per cell for a second, and use queue-based pickup zones (airports often run a virtual driver queue).
  • Adaptive ping rate: drivers on a trip or moving fast need frequent pings; parked, idle drivers can ping less often. Fewer writes for the same accuracy.
  • Smoothing: GPS jumps; snap points to roads ("map matching") before showing them to riders or computing fares.

The classic bug: searching only the rider's own geohash cell. A driver 50 metres away across the cell border is invisible, so the app says "no cars" while one is parked across the street. Always search the cell plus all neighbours, and widen the ring if there are too few results.

4. ETA: why straight-line distance is wrong

A driver 400 m away on the other side of a river or a highway divider may be 15 minutes away by road. So matching ranks the few nearest candidates by a routing ETA: the road network as a weighted graph (edge weight = travel time with live traffic), searched with fast shortest-path algorithms using precomputed shortcuts (contraction hierarchies: offline, add shortcut edges that skip over unimportant roads, so a query explores thousands of nodes instead of millions). ETAs are then corrected by an ML model trained on actual trip times. This is its own big system; see Google Maps (Routing & ETA) and Surge Pricing & ETA. In the interview, say it exists, give it a latency budget (tens of milliseconds per batch), and call it in batches for the top 10 candidates.

5. The trip lifecycle and money

  • Start-trip OTP (common in India): the rider tells the driver a 4-digit code, proving the right person got in.
  • Fare is computed from the GPS trace (distance + time) and the upfront price rules, after the trip ends.
  • Payment is a separate service fed by TripCompleted events, using an idempotency key per trip so a retried event never charges twice. Cash trips just record a ledger entry. See Payment System.
  • Driver phone dies mid-trip? The trip stays IN_TRIP in the DB; the rider app keeps showing the last known position; the driver app resumes from server state on reconnect. Durable state lives on the server, not the phone.
