Architecture: follow a page view and a vote

Click Next or Play. Meera opens r/india, then upvotes a post, then replies to a comment.

  1. Edge. Meera is logged out. The CDN serves the whole r/india page from cache, no origin work at all. Reddit fronts the site with a CDN (Fastly per ByteByteGo) that also routes requests to different backend stacks by path and cookie.
  2. Read a listing. She logs in. The API asks the listing service for (r/india, hot). It reads one precomputed list of 25 post IDs from memcached, then does one multi-get for the 25 post objects. Only on a cache miss does it go to Postgres replicas. No ORDER BY runs.
  3. Vote. She taps upvote. The vote service upserts (user=meera, thing=t3_9xk2) -> +1 in Cassandra and replies 202. The app already shows an orange arrow. If she taps again with the same direction, nothing changes: the stored state is already +1.
  4. Defer the expensive part. The vote service puts a small job on a queue chosen by hash(community) mod N. Reddit split its single vote queue this way in 2012 so fewer workers fight over the same listing lock.
  5. Rescore. A vote worker runs anti-cheat checks, applies the delta (new direction minus old direction) to the post's up/down counters, recomputes the hot score, and edits the affected listings in place: the community listing, plus separate messages for the domain listing and the author's profile listing, each on its own partitioned queue.
  6. Reply. She replies to a comment. The comment is written durably to Postgres first. Updating the precomputed comment tree is expensive, so it goes to a comment-tree queue and is applied in batches. A manually flagged huge thread gets its own "fastlane" queue so it cannot slow the rest of the site.
  7. Failure. If workers fall behind, users still read pages from cache and still see their own vote; only global scores lag. Each queue has a maximum length (a quota) so one runaway thread cannot fill the broker's memory, which is exactly what happened to Reddit in early 2016.

From your world

The vote path is a NIC with receive side scaling. RSS hashes each flow to one RX queue and one CPU, so packets of a flow are handled in order by one core with no shared lock. Hashing votes by community to one queue and one worker does the same thing: a listing is only ever edited by one worker at a time, so the lock is almost never contended.
