Interview: how to drive 45 minutes

LevelWhat the answer looks like
SDE-1 answer looks like..."Store each vote as (user, item, direction), update the count asynchronously through a queue, and rank listings with a time-decayed hot score cached in Redis or memcached."
SDE-2 adds..."I partition the vote queue by community so workers do not fight over the same listing lock, make the read-old-write-new step atomic, and store megathread comment trees so one page load is a bounded number of reads."
  1. 0-5 min: requirements. Post, vote (one per user), listings by hot/new/top, threaded comments, home feed. Read heavy, eventual scores, no double counts.
  2. 5-10 min: numbers. ~870 votes/s average, ~12k views/s; show that writes are small but each vote fans out.
  3. 10-15 min: API and data model. Vote as state (dir -1/0/1), cursor listings; Postgres for posts and comments, Cassandra for votes and listings.
  4. 15-25 min: high-level design. CDN, API, listing service on memcached, vote service + partitioned queue + workers, comment service + tree workers.
  5. 25-40 min: deep dives. Hot formula, Wilson "best", lock contention and partitioning, comment trees for megathreads.
  6. 40-45 min: failure modes and metrics. Queue depth, p99 vote latency, cache hit rate, listing staleness.

Related designs: News Feed, Distributed Counter, Top-K, Post Search, Live Comments, News Aggregator, Rate Limiter, plus the patterns Dealing with Contention and Scaling Writes. Framework: 45-minute interview framework.

How do you make sure a user can vote only once, can change their vote, and retries do not double count?

Store the vote as state keyed by (user_id, thing_id) with direction -1, 0 or +1, and make the API "set my vote to X". On each request, read the old direction, upsert the new one, and emit the delta (new minus old) to the counter pipeline. A retry with the same direction produces delta 0. Counters are derived data and can be rebuilt from the vote table.

How to answer

Start with the API shape (set state, not increment), then the key, then the delta, then mention rebuildability. Reddit kept a relational copy of votes so Cassandra data could be regenerated.

Likely follow-ups
  • What if two vote requests from the same user race? (Conditional write or version check on the vote row.)
  • What if the queue delivers the delta twice? (Carry the vote version, skip if already applied.)
Explain Reddit's hot ranking. Why the log, and why does it not need constant rescoring?

hot = sign(score) x log10(max(|score|, 1)) + (created_seconds - epoch) / 45000. The log makes the first 10 votes worth as much as the next 90, so early engagement matters. The time term gives newer posts a growing head start: 12.5 hours of newness is worth 10x the votes. Because the formula uses creation time, not the current time, a post's value only changes when it is voted on. Old posts sink relative to new ones without any batch job.

How to answer

Write the formula, give the 12.5 h = 10x intuition with one example, then make the systems point: no time-based rescoring, so listings can be mutated in place on votes.

Likely follow-ups
  • The numbers grow forever; is that a float precision problem? (Rounded to 7 decimals; rebase the epoch if needed.)
  • How would you add "rising"? (Rate of votes in a recent window.)
How should comments be sorted? Why not by score or by percentage of upvotes?

Net score favours old comments and ignores the ratio (600 up / 400 down beats 6 up / 0 down). Percentage overrates tiny samples (1 up, 0 down = 100%). Use the lower bound of the Wilson score interval: the lowest upvote ratio we are fairly confident about given the votes so far. Reddit's "best" sort uses it at 80% confidence (z ~ 1.28) and caches a lookup table for small counts. Example: 1/0 scores 0.38, 100/1 scores 0.97.

How to answer

Show both failure examples, then name Wilson, explain it in one plain sentence, then note it has no time term because a thread is short-lived.

Likely follow-ups
  • How do new comments get a chance? (Blend in "new", or sample new comments into views.)
  • Is it expensive? (Constant time per comment; Reddit precomputes a table.)
How do you serve r/india sorted by hot in under 50 ms at 35,000 page views per second?

Do not sort on read. Keep a precomputed listing per (community, sort, window): the top ~1,000 (post_id, score) pairs, persisted in Cassandra and served from memcached. A page read is one listing fetch plus one multi-get for 25 post objects. Vote workers mutate listings in place when scores change. Logged-out traffic is served by the CDN.

How to answer

Walk Reddit's evolution: SQL sort, cached query, mutate in place, denormalized index. Size the cache (~10 GB for 600k listings) to show it fits.

Likely follow-ups
  • A user pages past item 1,000? (Fall back to a slower query, or cap like Reddit does.)
  • How do you keep it consistent with the DB? (Rebuild jobs, repair tooling.)
Votes are waiting hours in the queue at peak. You add more workers and it gets worse. What is happening and how do you fix it?

Workers are contending on a shared resource, most likely the lock that protects a hot listing. More workers means more lock waiters, more retries and more context switches. Prove it with timers around each phase of vote processing. Fix: partition the queue by the listing key (community ID mod N) so each listing has a single writer. If p99 is still bad, look for cross-partition work, such as a domain or profile listing touched by votes from many communities, and split each vote into separate messages per listing type, each partitioned by its own key.

How to answer

Diagnose before fixing: averages vs p99, timers per phase. This is exactly Reddit's 2012 story; naming it shows you read real postmortems.

Likely follow-ups
  • Can you remove the lock entirely? (Single-writer per partition, or lockless structures; Reddit was testing lockless cached queries.)
  • How many partitions? (Enough for peak, more than workers, keys hashed evenly.)
How do you store and load a thread with 50,000 comments?

Store comments with parent_id, sharded by post_id so the thread is on one shard. Keep a precomputed tree structure (parent -> children with sort keys) per post. To render, read the structure, walk it by "best" until a budget (for example 200 comments, depth 8), multi-get only those bodies, and emit "load more" stubs for the rest. Updates to the structure go through a batched queue; megathreads get an isolated queue; every queue has a length quota.

How to answer

Compare adjacency list, materialized path and closure table quickly, pick one, then talk about the page budget and the async tree update.

Likely follow-ups
  • A reply arrives before its parent is processed? (Order-sensitive; buffer or recompute.)
  • Deep links to a comment 20 levels down? (Render its ancestors as context plus its subtree.)
A thread page has 500 comments. How do you show which ones this user has voted on, cheaply?

Partition votes by user_id with thing_id as the clustering key, then do one read for (user, IN [500 ids]) or a range read for that post if the key includes post_id. Most results are "no vote", so Bloom filters (which Cassandra keeps per SSTable) answer most lookups without touching disk. Cache the user's recent votes for the session.

How to answer

Point out that the common answer is "no", which is exactly what Bloom filters make cheap. Reddit cited this as a reason Cassandra worked well for votes.

Likely follow-ups
  • False positives? (Only cost an extra read; never a wrong answer.)
How do you build "Top of this week" and "Top of all time"?

Top is net score inside a time window. For hour and day, maintain windowed counters from the vote stream (tumbling windows in a stream processor, or bucketed counters) and keep a top-K per community per window. For week and all time, a periodic batch job over the vote or post table is fine because these listings change slowly. Store results as precomputed listings like hot.

How to answer

Separate fast-changing windows (stream) from slow ones (batch). Link to top-K and windowed aggregation.

Likely follow-ups
  • Exact vs approximate? (Exact per community is cheap; approximate sketches help for global top-K.)
Postgres for posts and comments is running out of write capacity. How do you shard it?

First split by table (vertical partitioning): Reddit early on used separate master databases for links, accounts, subreddits, comments and votes. Then shard big tables horizontally: comments by post_id so threads stay local, posts by post_id. Range sharding helps if range queries dominate (Quora chose range-based sharding for that reason and keeps the shard map in ZooKeeper); hash sharding spreads load more evenly. Migrate with copy + binlog replay, dark reads and dark writes, then cut over, as Quora described.

How to answer

Name the shard key from the access pattern, then the migration plan. Interviewers want the plan, not just "shard it".

Likely follow-ups
  • Queries by author across shards? (Secondary index table or scatter-gather; keep shard count small.)
Half your memcached fleet disappears at once. What happens and how do you protect the database?

Every miss goes to Postgres; replicas saturate and pages time out. This happened to Reddit in 2016 when an autoscaler, pointed at the old ZooKeeper cluster during a migration, saw migrated servers as unhealthy and terminated hundreds, caches included. Protect with: request coalescing (one DB fetch per key), serving stale data, rate-limiting misses, gradual re-warm, and tooling that refuses to act on too many servers at once (Reddit's autoscaler v2 does exactly that).

How to answer

Describe the blast, then mitigations in order of time: immediate (shed, stale), short term (warm), long term (safety checks on destructive automation, separate tooling for stateful services).

Likely follow-ups
  • How do Kubernetes PodDisruptionBudgets help? (They cap voluntary evictions.)
How is Quora different from Reddit in design?

Same skeleton (content, votes, threads, cache), different ranking and grouping. Quora organises by question and topic, ranks answers with a machine-learned quality model where votes are one feature, and builds a personalized feed from followed topics and people. It stores core data (questions, answers, upvotes, comments) in sharded MySQL, with heavy caching. Reddit organises by community and uses formula-based sorts that are easy to precompute.

How to answer

Map the nouns first, then say what changes in the architecture: the ranking service and feed become an ML pipeline (candidate generation plus ranker).

Likely follow-ups
  • How do you dedupe near-identical questions? (Text embeddings plus nearest-neighbour search, merge suggestions.)

Scenario drills

Scenario: a breaking-news thread is slowing the whole site

A major event; one thread gets tens of thousands of comments in an hour. Comment and vote latency rises everywhere, not just in that thread.

Weak answer: "Add more servers to the database."

Strong answer: the shared tree-update queue is being hogged by one thread. Isolate it on a dedicated queue with its own workers (Reddit's fastlane), batch its tree updates more aggressively, cap the comments rendered per page, and put a length quota on every queue so isolation cannot itself fill the broker. Watch for recompute loops: if inconsistency triggers a recompute on every view, rate-limit recomputes per post.

Likely follow-ups
  • Which metrics would have shown this early? (Per-queue depth, top posts by queue messages.)

Scenario: "Why not just compute hot with SQL and add an index?"

The interviewer pushes back on your precomputed listings as over-engineering.

Weak answer: insist on caches without numbers.

Strong answer: "For a small site, yes: an expression index on hot(ups, downs, created) per community works, and since hot only changes on a vote, the index update cost is per vote. At ~35k page views/s and 2,600 votes/s, the index updates and sorted reads land on one primary, and every community page is the same query run thousands of times a second. A precomputed list turns that into one key read. Reddit walked exactly this path."

Likely follow-ups
  • At what scale would you switch? (When the DB's read CPU or replica lag becomes the bottleneck.)

Common mistakes

  • Treating a vote as "increment a counter" from the client: double counts on retry.
  • Running ORDER BY on every page view.
  • Scaling workers on a shared queue without thinking about lock contention.
  • Storing the whole comment tree as one JSON blob that every reply rewrites.
  • Pushing every post into every subscriber's feed in a community of millions.
  • Only watching averages; Reddit's second 2012 slowdown showed only in p99.
