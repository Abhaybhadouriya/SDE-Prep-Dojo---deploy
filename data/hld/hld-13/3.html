Redundancy and failover: active-passive vs active-active

Failover is moving work from a failed part to a healthy copy. There are two basic shapes.

  • Active-passive (primary-standby): only the primary serves traffic. A standby waits, receiving replicated data and heartbeats. When heartbeats stop, the standby takes over the primary's address or DNS name. A hot standby is running and caught up; a cold one must boot first, so downtime is longer.
  • Active-active: all copies serve traffic and share load. If one dies, the rest absorb its share. DNS or the load balancer must know about every copy. You must keep enough spare capacity: two regions each running at 70% cannot absorb each other.

A regional failover, step by step

Click Next or Play to walk through what really happens when the primary region of an active-passive system fails.

  1. Normal. All users go to Region A. The database replicates asynchronously to a replica in Region B, which runs a small copy of the app.
  2. Failure. Region A degrades: maybe a network fault, maybe a bad config push. Often it is a gray failure, half-working, which is harder to detect than a clean crash.
  3. Detect. Health checks from several vantage points fail several times in a row. Requiring agreement avoids failing over on one noisy probe, because a false failover itself costs data and availability.
  4. Promote. The replica in B is promoted to primary. AWS notes that a non-Aurora RDS replica promotion takes a few minutes, while an Aurora global database can promote a secondary region in under a minute.
  5. Shift traffic and scale. DNS or the global load balancer points users to B, and B scales up to full size. AWS recommends using data-plane actions (health-check switches) for this rather than control-plane APIs, because control planes are less available during big events.
  6. Fence the old primary. When A comes back it must rejoin as a replica, not as a second primary. Otherwise you get split brain: two writers, divergent data. Use fencing tokens or a lease from a consensus store (see hld-09).

Automatic or manual? The AWS DR whitepaper warns that automatic failover on health checks "should be used with caution" because a false alarm costs you RPO and RTO for nothing. A common answer: automate every step, but let a human press one button for a whole-region failover; automate fully only for in-region, well-understood failures (a dead database node, a dead AZ).
