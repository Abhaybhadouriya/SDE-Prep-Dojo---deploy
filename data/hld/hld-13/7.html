Observability: metrics, logs and traces

You cannot keep an SLO you cannot see. Observability is being able to answer "what is wrong and where?" from the outside, using three kinds of signals (OpenTelemetry calls them signals):

SignalWhat it isGood forCost trapTypical tools
MetricsNumbers over time with a few labels (requests/s, error ratio, p99 latency)Dashboards, SLOs, alerts; cheap to keep for monthsHigh-cardinality labels (user_id) explode series countPrometheus, Monarch (Google), CloudWatch
LogsTimestamped event records, ideally structured JSONThe "why" for one request or errorVolume; you pay to ship, index and store every lineELK/OpenSearch, Loki
TracesOne request's path across services as a tree of timed spansFinding which hop is slow in a fan-outUsually sampled, so rare paths may be missingJaeger, Zipkin, OpenTelemetry

What to measure: the four golden signals

The SRE book's chapter on monitoring distributed systems says that if you can only measure four things on a user-facing system, measure:

  1. Latency Time to serve a request; track successes and errors separately, because a fast error can make averages look good.
  2. Traffic Demand, in a system-specific unit (requests/s, concurrent sessions, messages/s).
  3. Errors Explicit (HTTP 500), implicit (HTTP 200 with wrong content) or by policy (slower than your limit).
  4. Saturation How full the most constrained resource is (CPU, memory, disk, queue depth, connection pool). Systems degrade before 100%.

The same chapter's alerting rules: page on symptoms (users see errors) rather than causes (one DB node is slow); every page should need human judgment; anything mechanical should be automated. Combine mostly white-box monitoring (internal metrics) with a few black-box probes that act like a user from outside.

Distributed tracing at Google started with Dapper (2010). Its key ideas still shape OpenTelemetry today: low enough overhead to run always in production, instrumentation hidden in a few shared libraries so app developers do not have to change code, and sampling only a fraction of requests. The trace id is passed along in request headers (W3C traceparent), and also written into every log line so you can jump from a metric spike to a trace to a log.

From your world

Metrics are your SNMP interface counters and /proc/net/dev: cheap, aggregated, always on. Logs are syslog: detailed, expensive at volume. A trace is traceroute for a request through microservices: each hop reports its own timing, and a shared id ties the hops together. Saturation is the familiar ring-buffer occupancy or queue depth that rises before packets drop.
