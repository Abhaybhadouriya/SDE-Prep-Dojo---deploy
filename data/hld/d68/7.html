Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key store_id keeps each dark store's stock history in order; riders' locations use rider_id. Consumer-group sizing: 48 partitions over 1,000 stores is about 20 stores per partition, and at most 48 pods per group. Consumer lag on stock.changed is the "how stale is search" number, so alert on it. The API HPA scales on request rate with a scheduled pre-scale before the evening peak.

Kafka

  • Topics: order.events, stock.movements, stock.changed, rider.location. Key = store_id (riders: rider_id), so each store's history is ordered within one partition.
  • Outbox from the inventory and order databases (or CDC with Debezium) so no change is published without being committed, or committed without being published.
  • Consumers: Redis stock-set updater, category-page builder, search freshness, notifications, analytics lake, demand forecasting, fraud checks on COD.
  • Consumer lag on stock.changed is the "how stale is search" metric. Alert on it.

Kubernetes and Docker

  • Stateless services (serviceability, search API, order API, dispatch) as Deployments scaled by the HPA on request rate; a scheduled pre-scale before the evening peak and big matches.
  • The per-store scheduler is a StatefulSet or a Deployment with store ownership by consistent hashing plus leases, so each store has exactly one active scheduler.
  • Async jobs (prescription OCR/LLM, reindex) as queue-driven workers scaled by KEDA on queue length.
  • Store devices (picker scanners, printers) talk to cloud APIs; a small local edge box per store can buffer scans if the store's internet drops.
