Data model

-- Inventory: the truth, one row per store x SKU, sharded by store_id
CREATE TABLE store_inventory (
  store_id     TEXT,
  sku_id       BIGINT,
  on_hand      INT NOT NULL,        -- physically on the shelves (WMS view)
  reserved     INT NOT NULL DEFAULT 0,
  safety_buf   INT NOT NULL DEFAULT 0,   -- hidden units to absorb count errors
  version      BIGINT NOT NULL DEFAULT 0,
  updated_at   TIMESTAMPTZ,
  PRIMARY KEY (store_id, sku_id),
  CHECK (reserved >= 0 AND reserved <= on_hand)
);

-- Every change is also a ledger row (audit + rebuild + reconciliation)
CREATE TABLE inventory_movement (
  movement_id  UUID PRIMARY KEY,   -- idempotency: the same event is applied once
  store_id TEXT, sku_id BIGINT,
  kind TEXT,          -- GRN | RESERVE | RELEASE | PICK | DAMAGE | COUNT_ADJUST | RETURN
  qty INT, ref_id TEXT, created_at TIMESTAMPTZ
);

CREATE TABLE orders (
  order_id UUID PRIMARY KEY, user_id BIGINT, store_id TEXT,
  status TEXT,        -- CREATED|RESERVED|PAID|PICKING|PACKED|ASSIGNED|OUT|DELIVERED|CANCELLED
  promised_by TIMESTAMPTZ, amount_paise INT, payment_method TEXT,
  created_at TIMESTAMPTZ
);
CREATE TABLE order_line (order_id UUID, sku_id BIGINT, qty INT, picked_qty INT,
  price_paise INT, PRIMARY KEY (order_id, sku_id));

SQL vs NoSQL per component (the Zepto question)

ComponentStoreWhy
Store inventory, reservationsPostgres/MySQL, sharded by store_idConditional updates, CHECK constraints, multi-line transactions for a cart. Per-store sharding keeps every cart inside one shard.
Orders, paymentsSQL (or DynamoDB with conditional writes)State machine with strict transitions, money, audit. Zepto has published that it moved high-volume order data to DynamoDB on AWS (see Real world); either works if transitions are conditional writes.
Catalog (product master)Document store (MongoDB) + object storage for imagesFlexible attributes per category (weight, flavour, expiry); read-heavy; changes slowly.
Search indexElasticsearch/OpenSearchText, synonyms ("curd" = "dahi"), typo tolerance, ranking.
Hot stock and availability cacheRedisSub-millisecond "in stock at BLR-114?" for search filtering; short TTL plus event invalidation.
Rider locationsRedis GEO + Kafka stream4,000 writes/s of overwrite-only data; only the latest point matters for assignment.
Events (orders, stock changes)Kafka, keyed by store_idPer-store ordering, replay to rebuild caches and analytics.
Analytics, demand forecastingLakehouse (S3 + Spark/Trino)Which SKUs to stock where, per hour; trained offline.
