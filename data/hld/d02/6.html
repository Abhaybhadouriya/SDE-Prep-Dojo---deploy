Deep dives: the hard parts

Stop here for SDE-1? For SDE-1, knowing the algorithms, the Redis + atomic script design and "fail open" is a strong answer. SDE-2 candidates should also handle deep dives 2-5 below.

Deep dive 1: race conditions (must know)

The naive code is count = GET key; if count < limit: SET key count+1. With 50 gateway pods, two pods can GET the same value at the same time and both allow. Fixes, from simplest to most flexible:

  • INCR first, check after: INCR is atomic and returns the new value; if it is above the limit, reject. Perfect for fixed windows.
  • Lua script: for token buckets and sliding windows, which need read + compute + write together.
  • Avoid distributed locks per request: far too slow for 500k checks/s.

Deep dive 2: Redis is down. Fail open or fail closed? (must know)

The limiter is a protection layer. If it becomes the reason the API is down, it has failed at its own job. So most API limiters fail open: if Redis times out (use a tight timeout, a few milliseconds), allow the request and raise an alarm. Stripe's post says exactly this: their limiters fail open when Redis is unavailable, and they added kill switches and dark-launched new limiters (log the decision without enforcing) before turning them on.

  • Fail closed where letting traffic through is worse than refusing it: login attempts, OTP sends, money transfers.
  • Middle ground: fall back to a local in-memory bucket in each gateway pod with limit ÷ number of pods. Rough, but it still stops a runaway client.
  • Wrap Redis calls in a circuit breaker, so that when Redis is sick the gateways stop waiting on it for every request.

Deep dive 3: hot keys and very high rates (good to know)

One huge customer at 50,000 requests/s means all checks for that key go to one Redis shard. Options:

  • Local token buckets with periodic sync: each gateway pod gets a share of the budget (or leases a batch of tokens, for example 100 at a time, from Redis) and spends it locally with no network call. Accuracy drops a little; latency and Redis load drop a lot. This is the same "lease a block" idea as the URL shortener's ID ranges.
  • Split the key into N sub-buckets (k_8f2:0..7) each with limit ÷ N, and pick one at random per request.

Deep dive 4: multi-region (SDE-2)

A client might hit Mumbai and Singapore at once. Options:

  • Per-region limits (each region enforces limit ÷ regions, or its own full limit): simple and fast, but not exact.
  • Local enforcement + async sync: each region counts locally and gossips counts to others every second; the client may get a bit more than the limit during that second.
  • One global store: exact, but adds a cross-region round trip (tens to hundreds of milliseconds) to every request. Almost never worth it.

Say the trade-off clearly: "I accept a small overshoot in exchange for keeping every check inside one region."

Deep dive 5: beyond request counts (good to know)

  • Concurrency limiter: limit requests in flight, not per second. Stripe runs one; it protects slow, expensive endpoints. Implement with a counter incremented on start and decremented on finish (with a TTL in case the decrement is lost).
  • Load shedding: when the whole fleet is overloaded, reject low-priority traffic first and keep capacity for critical calls. Stripe's fleet usage shedder reserves a share of capacity (their example is 20%) for critical requests and answers the rest with 503. See the AWS Builders' Library on load shedding.
  • Cost-based limits: a search query might cost 10 tokens, a GET by ID 1 token (the cost argument in our script).
  • Client behaviour: clients should retry 429s with exponential backoff and jitter, honouring Retry-After. Otherwise all rejected clients retry at the same instant and create the next spike. See timeouts, retries and backoff with jitter.

From your world

Backoff with jitter is Ethernet's binary exponential backoff after a collision: wait a random slot from a window that doubles each try, so stations stop colliding in lockstep. And the "local bucket, sync later" idea is like distributed policers on a multi-line-card chassis, where each card gets a share of the aggregate rate. Where it breaks: Ethernet stations share one wire and see every collision; API clients are independent programs you do not control, so you can only ask them to back off (with Retry-After) and must still survive the ones that ignore it.
