Architecture: where it runs and how a check flows

Rate limiting can happen at several layers. The common interview answer is in the API gateway, with a shared counter store:

Now one request through the gateway limiter. Click Next or Play.

  1. Request arrives. A gateway pod (one of many behind the load balancer) receives POST /v1/orders and extracts the limit keys: API key k_8f2 and route.
  2. Look up rules locally. Rules live in an in-memory cache inside the pod, refreshed by a push or poll from a config service (or a Kubernetes ConfigMap). No network call for rules on the hot path.
  3. Atomic check in Redis. The pod sends one EVALSHA call to the Redis shard that owns this key. The Lua script refills, checks and spends in one step, so two gateway pods cannot both spend the last token.
  4. Allowed. The request goes on to the backend. The added cost was one round trip, about a millisecond.
  5. Rejected. The gateway answers 429 with Retry-After and remaining-quota headers. The backend never sees the request.
  6. Observe. Decisions are sampled or counted and sent (asynchronously) to Kafka for dashboards, billing, and abuse detection. This never blocks the request.

The atomic check: a token bucket in Lua

Redis runs one script at a time on a shard, so everything inside the script is atomic. That kills the race where two pods both read "1 token left" and both spend it. We read time inside Redis (TIME) so 50 gateway clocks do not need to agree.

-- bucket.lua   KEYS[1] = bucket key   ARGV = capacity, refill_per_sec, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local t   = redis.call('TIME')                         -- server time: {seconds, microseconds}
local now = t[1] * 1000 + math.floor(t[2] / 1000)       -- milliseconds

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity           -- new key starts full
local ts     = tonumber(data[2]) or now

tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)   -- refill
local allowed = 0
if tokens >= cost then
  tokens  = tokens - cost                                         -- spend
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)  -- idle keys disappear
return { allowed, math.floor(tokens) }
$ redis-cli --eval bucket.lua rl:k_8f2 , 10 5 1
1) (integer) 1
2) (integer) 9

The first call on a new key: allowed (1), 9 tokens left. The PEXPIRE means idle clients cost no memory after their bucket would be full anyway.

From your world

The Lua script is the distributed version of doing a read-modify-write under a spinlock (or with an atomic compare-and-swap) on a shared counter in the kernel. Without it you get the classic lost-update race: two CPUs read tokens = 1, both decrement, both proceed. Redis gives you the "lock" for free because each shard is single-threaded for commands. Where it breaks: a spinlock costs a cache-line bounce of tens of nanoseconds; a Redis call is about 1 ms away over the network, so you could never spin on it. That is why the whole read-modify-write is shipped to Redis as one script instead of locking from the gateway.
