Back-of-envelope estimation

The limiter itself is light. What we must size is the shared counter store (Redis or Valkey) and the latency we add.

Step 1: checks per second

  1. Peak traffic. 500,000 requests/s at the gateway (given).
  2. Rules per request. Say 2 rules (per key + per endpoint). If each rule is one Redis call, that is up to 1M Redis operations/s. Batch both rules in one script call: 500k calls/s.
  3. Redis capacity. Rule of thumb: one Redis node does roughly 100k+ simple operations per second, fewer for scripts. So plan for roughly 8-10 primary shards (with a replica each) to have headroom. Shard by the limit key.

Step 2: memory

  1. Token bucket state per key. Two numbers (tokens, last refill time) plus the key name and Redis overhead: call it about 100 bytes (assumption).
  2. All keys. 10M keys × 100 B = 1 GB. Memory is not the problem; throughput is.
  3. Compare: sliding window log. If the rule is 1,000 requests/hour, the log keeps up to 1,000 timestamps per key: 1,000 × 8 B = 8 KB per key, × 10M keys = 80 GB. That is why the exact log is rarely used at scale.

Step 3: latency budget

  1. Network round trip to Redis in the same zone: roughly half a millisecond to a millisecond (rule of thumb).
  2. Script execution on Redis: microseconds.
  3. Total added: about 1 ms per request. Acceptable for most APIs. If not, use a local in-memory bucket and sync to Redis in the background (deep dive 4).
