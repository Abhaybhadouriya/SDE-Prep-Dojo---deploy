Quick quiz

Limit: 100 per minute, fixed window. What is the worst case in a 2-second span?

  1. 100 requests
  2. 101 requests
  3. 200 requests
100 at the end of one window and 100 at the start of the next. That is the fixed window's boundary problem.

In a token bucket, what controls the largest burst a client can send at once?

  1. The bucket capacity
  2. The refill rate
  3. The window length
A full bucket can be spent at once, so capacity = maximum burst. The refill rate controls the long-run average.

Why do we run the token bucket logic as a Lua script in Redis?

  1. Lua is faster than Python
  2. The read-refill-spend steps run atomically, so two gateways cannot both spend the last token
  3. Redis cannot store numbers without Lua
Redis runs each script to completion on a shard before the next command, which removes the GET-then-SET race.

Redis for an API quota limiter goes down. What is the usual choice?

  1. Fail closed: reject all requests
  2. Fail open: allow requests and alert
  3. Return 500 to everyone
The limiter protects the API; it must not become the outage. Security limits (login, OTP) are the exception and fail closed.

Which status code means "you, the client, sent too many requests"?

  1. 503
  2. 403
  3. 429
429 Too Many Requests (RFC 6585). 503 is server overload; 403 is "forbidden".

A sliding window log for 1,000 requests/hour and 10M keys needs roughly how much memory at 8 bytes per timestamp?

  1. About 80 GB
  2. About 1 GB
  3. About 8 MB
1,000 × 8 B = 8 KB per key; × 10M keys = 80 GB. A token bucket needs about 1 GB for the same keys.

Where does Kafka fit in a rate limiting design?

  1. It makes every allow/deny decision
  2. Queueing work to process at a fixed rate, and carrying usage events for billing and analytics
  3. It replaces Redis as the counter store
Per-request decisions need ~1 ms; Kafka is for asynchronous flows: shaping (queue then drain) and metering.
