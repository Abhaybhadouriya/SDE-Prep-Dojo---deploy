Requirements

First line to say: "Rate limiters come in many shapes, so let me ask what we are limiting, by what key, and where it runs."

  1. What is the client key? User ID, API key, IP address, or a mix? (Assume API key for logged-in calls, IP for anonymous.)
  2. What rules? Example: 100 requests/minute per API key; 5 login attempts/minute per username; 1,000 requests/second per endpoint total.
  3. Where does it run? In the API gateway in front of many services (assume yes), or as a library inside one service?
  4. Hard or soft limit? Is letting through 102 instead of 100 acceptable? (Usually yes for API quotas; no for paid quotas or security.)
  5. Scale? Assume 10 million active clients and a peak of 500,000 requests per second through the gateway fleet.
  6. What does the client see? A 429 with headers saying when to retry.

Functional

  • For each request: decide allow or reject using the rules for its key.
  • Support many rules per request (per user, per endpoint, global).
  • Rules are configurable without a deploy.
  • Rejected requests get 429 plus Retry-After and remaining-quota headers.
  • Log/meter decisions for dashboards and abuse detection.

Non-functional

  • Very low added latency: the check is on every request. Target about 1 ms (a design goal).
  • Highly available: if the limiter breaks, it must not take the API down with it.
  • Accurate enough: small overshoot is fine for quotas; security limits must be stricter.
  • Scales to 500k checks/s and 10M keys.
  • Works across many gateway nodes, and ideally across regions.

Never trust the client. A client-side limiter (in a mobile app or SDK) is polite, but anyone can bypass it. The real limit must be enforced on the server side.
