Remember this

You might confuse this with:

  • 429 vs 503: 429 = "you sent too much" (one client over its quota); 503 = "we are overloaded" (load shedding, hits everyone).
  • Rate limiting vs load shedding: a rate limit is a fixed per-client budget checked on every request; load shedding is an emergency brake based on the server's own health.
  • Token bucket vs leaky bucket: token bucket allows a burst up to the bucket size, then a steady rate; leaky bucket queues requests and lets them out at a perfectly even rate (no bursts reach the backend).

Remember this

  • Token bucket = capacity (burst) + refill rate (long-run limit). Same as a QoS policer's CBS + CIR.
  • Fixed window allows up to 2x at the boundary; sliding counter fixes it with two numbers.
  • Many gateways → shared state in sharded Redis → atomic update via INCR or a Lua script.
  • State is small (~1 GB for 10M keys); the challenge is throughput and ~1 ms latency.
  • 429 + Retry-After for client limits; 503 for load shedding.
  • Fail open for API quotas; fail closed for login/OTP/money.
  • Hot keys and multi-region: enforce locally, lease tokens, sync asynchronously, accept small overshoot.
  • Kafka is for queueing and metering, never for the per-request decision.
