Data model: the four algorithms are four data models

Each algorithm stores something different per key. Pick the algorithm and you have picked the data model.

1. Token bucket (our default)

Store {tokens, last_refill_ts} per key. On each request: add (now - last) × rate tokens (up to the capacity), then spend one if available. Allows short bursts up to the capacity; long-run rate equals the refill rate. Used by Stripe (in Redis) and by AWS API Gateway throttling.

2. Leaky bucket

A FIFO queue per key that drains at a fixed rate. Requests that find the queue full are rejected. Output is perfectly smooth, which protects a fragile backend, but a burst waits in line and adds latency. NGINX's limit_req is a leaky bucket (its burst sets the queue size, and nodelay serves queued requests at once while still counting them).

3. Fixed window counter

Store one integer per key per window: INCR rl:{key}:{minute} and set a 60-second TTL only on the first request of the window. Simplest and cheapest. Flaw: a client can send 100 at 12:00:59 and 100 more at 12:01:00: 200 requests in 2 seconds with a 100/minute limit.

$ redis-cli
127.0.0.1:6379> MULTI

127.0.0.1:6379(TX)> EXPIRE rl:k_8f2:202611231405 60 NX

127.0.0.1:6379(TX)> EXEC
1) (integer) 1
2) (integer) 1

The first reply is the new count for this minute; the second means the 60-second TTL was set. NX (Redis 7+) means "set the TTL only if the key has none yet", so later requests in the same minute do not keep pushing the expiry forward. On older Redis, use the pattern from the Redis INCR docs: run EXPIRE only when INCR returned 1. If the count is above the limit, reject.

4. Sliding window log and sliding window counter

Log: keep every request timestamp in a Redis sorted set; drop entries older than the window (ZREMRANGEBYSCORE), count the rest (ZCARD). Exact, but memory grows with the limit (80 GB in our estimate). Counter (approximation): keep only this window's count and the previous window's count, and weight the previous one by how much of it still overlaps the sliding window. Cloudflare described this approach in its post "Counting things, a lot of different things": two numbers per key, and very close to exact.

Run all four on the same traffic

Ten requests at second 59 and ten more at second 61, with a limit of 10 per 60 seconds:

# limiters.py - compare four rate limiting algorithms on the same traffic
import math
from collections import deque

LIMIT, WINDOW = 10, 60.0

class FixedWindow:
    def __init__(self): self.win, self.count = None, 0
    def allow(self, t):
        w = math.floor(t / WINDOW)
        if w != self.win: self.win, self.count = w, 0
        if self.count < LIMIT: self.count += 1; return True
        return False

class SlidingLog:
    def __init__(self): self.log = deque()
    def allow(self, t):
        while self.log and self.log[0] <= t - WINDOW: self.log.popleft()
        if len(self.log) < LIMIT: self.log.append(t); return True
        return False

class SlidingCounter:              # Cloudflare-style approximation
    def __init__(self): self.win, self.cur, self.prev = None, 0, 0
    def allow(self, t):
        w = math.floor(t / WINDOW)
        if w != self.win:
            self.prev = self.cur if self.win == w - 1 else 0
            self.win, self.cur = w, 0
        overlap = 1 - (t % WINDOW) / WINDOW
        if self.prev * overlap + self.cur < LIMIT: self.cur += 1; return True
        return False

class TokenBucket:
    def __init__(self, capacity=LIMIT, rate=LIMIT / WINDOW):
        self.cap, self.rate, self.tokens, self.last = capacity, rate, capacity, 0.0
    def allow(self, t):
        self.tokens = min(self.cap, self.tokens + (t - self.last) * self.rate)
        self.last = t
        if self.tokens >= 1: self.tokens -= 1; return True
        return False

burst = [59.0] * 10 + [61.0] * 10          # straddles the minute boundary
for cls in (FixedWindow, SlidingLog, SlidingCounter, TokenBucket):
    lim = cls()
    ok = sum(lim.allow(t) for t in burst)
    print(f"{cls.__name__:15s} allowed {ok:2d} of {len(burst)} requests within 2 seconds")
$ python limiters.py
FixedWindow     allowed 20 of 20 requests within 2 seconds
SlidingLog      allowed 10 of 20 requests within 2 seconds
SlidingCounter  allowed 11 of 20 requests within 2 seconds
TokenBucket     allowed 10 of 20 requests within 2 seconds

The fixed window lets through double the limit. The sliding log is exact. The sliding counter allows one extra (its estimate of the old window is 10 × 59/60 ≈ 9.83, just under 10): that is the "approximate" in "approximation". The token bucket is exact here too, and it is the only one with an explicit, tunable burst.
