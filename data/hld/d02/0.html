The story

Explain like I'm 5

Grandma has a cookie jar. The rule is: the jar holds at most 10 cookies, and grandma adds one new cookie every 6 minutes. Whenever you want a treat, you take one cookie. If the jar is empty, you have to wait. If you were away all morning, the jar is full and you can eat a few in a row (a "burst"), but you can never eat more than 10 at once, and over a long day you can only eat as fast as grandma bakes. Now imagine grandma has 50 kitchens in 50 houses, and you visit a different kitchen each time. The kitchens must somehow share one jar count for you, or you could eat 10 cookies in every house. That second part is the hard bit of this design.

A rate limiter decides, for every incoming request, "allow or reject?" based on how many requests the same client (a user ID, an API key, an IP address) has made recently. When it rejects, it answers with HTTP 429 Too Many Requests (defined in RFC 6585) instead of doing the work.

Why do companies need one?

  • Protect the service from overload: one buggy script in a retry loop can take down an API for everybody.
  • Fairness: one big customer should not use all capacity.
  • Cost and abuse: stop password guessing on login, SMS-pumping on OTP endpoints, scraping, and runaway bills on paid third-party calls.
  • Business tiers: free plan 100 requests/minute, paid plan 10,000.

From your world

This is the token bucket policer you configure on Cisco or Ciena gear. CIR (committed information rate) = the refill rate; CBS (committed burst size) = the bucket capacity. "Reject with 429" is policing (drop or mark the excess); "queue it and send later" is shaping, which is the leaky bucket. Same maths. Where the analogy breaks: a policer lives in one ASIC with nanosecond access to its own counters. Here, 50 separate gateway machines must share one bucket per user over the network, with millisecond round trips, partial failures and races. That shared state is the whole interview.

Interviewers love this: it is a small problem with a deep follow-up chain: algorithm → where it runs → shared state → race conditions → Redis failure → multi-region. Commonly reported at Amazon, Google, Atlassian, Stripe and Uber at SDE-2 level.

New words, once each. 429 = the HTTP status code "Too Many Requests": the server is fine, you are just over your limit, try again later (it usually comes with a Retry-After header). Lua = a small scripting language that Redis can run inside the Redis server, so several commands execute as one uninterrupted unit. p99 = the latency that 99 out of 100 requests beat; the slowest 1% are slower. Gateway = the front door service every API request passes through (auth, routing, limits). Valkey = the open-source fork of Redis (Linux Foundation), with the same commands; wherever we say Redis, Valkey works too. EVALSHA = run a Lua script that is already loaded in Redis, naming it by its SHA1 hash instead of sending the whole script each time. Circuit breaker = after repeated failures, stop calling a sick dependency for a while and take a fallback path, like err-disabling a flapping port. Load shedding = when the whole service is overloaded, reject some work (low priority first) so the rest still succeeds (deep dive 5). All of these are also in the site glossary.
