Where Kafka, Kubernetes and Docker fit

  • Kubernetes: the gateway runs as a scalable Deployment. Today the forward path on Kubernetes is the Gateway API (the community Ingress NGINX controller was retired: Kubernetes announced it on 11 November 2025, and best-effort maintenance ended in March 2026; your Ingress knowledge is still useful because many clusters run it, but new designs should use the Gateway API, see Ingress & Gateway API). With Envoy Gateway, global rate limiting is a policy object; Envoy calls a separate rate limit service backed by Redis, exactly the design on this page. Rules can live in a ConfigMap and be hot-reloaded. Redis runs as a managed service or as a StatefulSet via an operator.
  • Kafka: not on the decision path (too slow for a per-request check). It carries decision and usage events for analytics, billing ("how many calls did customer X make this month?") and abuse detection, and lets you queue work instead of rejecting it: an API can accept a request with 202, put it on a topic, and let workers process at a fixed rate. That is a leaky bucket built from Kafka plus a consumer group whose speed you control. See Why messaging and consumer groups.
  • Docker: the Envoy proxy, the rate limit service (envoyproxy/ratelimit) and Redis all ship as container images; a local Compose file is a quick way to test rules.
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: orders-api-ratelimit
spec:
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: orders-api
  rateLimit:
    # older Envoy Gateway releases also required "type: Global" here; current ones infer it from "global:"
    global:                      # shared across all Envoy pods (Redis-backed rate limit service)
      rules:
      - clientSelectors:
        - headers:
          - name: x-api-key
            type: Distinct       # one bucket per distinct API key
        limit:
          requests: 100
          unit: Minute

Field names follow the Envoy Gateway global rate limit task; check that page for the version you install.

# config for the standalone envoyproxy/ratelimit service
domain: public-api
descriptors:
  - key: api_key
    rate_limit:
      unit: minute
      requests_per_unit: 100
  - key: route
    value: "POST /login"
    rate_limit:
      unit: minute
      requests_per_unit: 5
# nginx.conf - leaky bucket per client IP, 10 req/s, queue of 20, answer 429 not 503
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

server {
    listen 80;
    location /api/ {
        limit_req zone=api burst=20 nodelay;
        limit_req_status 429;        # default is 503
        proxy_pass http://backend;
    }
}

The NGINX docs say a 1 MB zone holds about 16 thousand 64-byte states, so 10m is room for roughly 160 thousand client IPs. Each NGINX box counts on its own, so with 10 boxes a client can get up to 10x the limit: fine for crude flood protection, not for per-customer quotas.
