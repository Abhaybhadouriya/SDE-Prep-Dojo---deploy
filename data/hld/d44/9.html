Interview: how to drive 45 minutes

  1. 0-5 min: requirements. Post, live view, history, reactions. AP, under 200 ms, eventual.
  2. 5-10 min: numbers. Show 1011 naive deliveries, then the human cap.
  3. 10-15 min: API and storage. POST, cursor history, SSE stream; Cassandra/DynamoDB by video and time bucket.
  4. 15-25 min: high-level design. Gateways, co-location by video, pub/sub or dispatcher.
  5. 25-40 min: deep dives. Protocol, fan-out, mega-stream, reconnects, reactions.
  6. 40-45 min: failure modes and monitoring (end-to-end latency p99, dropped-frame rate, connections per gateway).
LevelWhat the answer looks like
SDE-1 answer looks like..."Comments are POSTed and stored in Cassandra by video and time; viewers hold an SSE stream to a gateway, the load balancer groups a video's viewers on a few gateways, and each new comment is published once per gateway through Redis pub/sub."
SDE-2 adds..."For a 25M-viewer stream I cap delivery at ~10 comments/s per viewer by sampling, batch one frame per second, size each video's gateway set by viewer count, aggregate reactions in 2-second windows, and spread reconnects with jitter plus a CDN snapshot mode under extreme load."

Why SSE instead of WebSockets for live comments?

The traffic is one-directional: millions of viewers receive, a small fraction post. SSE is a normal HTTP response that streams events, so it passes through proxies and firewalls, works with HTTP/2 multiplexing, and the browser's EventSource reconnects automatically and resumes with Last-Event-ID. Posting is a regular POST. WebSockets add a full-duplex channel we do not need.

How to answer

Lead with the read/write asymmetry, then the operational benefits, then admit when you would pick WebSockets (chat, games, typing indicators at high rate).

Likely follow-ups
  • What breaks SSE? (Buffering proxies, HTTP/1.1 per-domain connection limits.)
  • How do mobile apps do it?
Viewers of one video are on 500 different servers. How does a comment reach all of them?

Publish once to a per-video channel (Redis pub/sub sharded by video_id) or to a dispatcher that reads an endpoint store mapping video to gateways. Each gateway that has viewers subscribes; the publisher sends one copy per gateway and the gateway copies to its local connections. To keep the number of gateways per video small, the L7 load balancer hashes video_id so viewers co-locate.

How to answer

Draw the three options (broadcast, channel per video, dispatcher). Reject broadcast with the wasted-work argument; choose one of the others and explain co-location.

Likely follow-ups
  • Why not Kafka? (Every gateway would consume every topic.)
  • How do you keep subscriptions fresh when gateways die?
An IPL final has 25 million viewers and 5,000 comments per second. What changes?

Every viewer cannot get every comment: that is 1011 messages/s. Cap each viewer at ~10 comments per second, sampled with priority (own, friends, verified), batched into one frame per second. Add a relay tier so no dispatcher fans out to hundreds of gateways. Above a threshold, switch the stream to CDN snapshot mode: publish the last 100-200 comments every second to the CDN and let clients poll. Pre-scale gateways before the match and lower per-user comment rate limits.

How to answer

Do the multiplication first. The number makes the case for sampling for you.

Likely follow-ups
  • How do you avoid flapping between modes? (Hysteresis.)
  • Does the commenter see their own comment? (Yes, optimistically on the client.)
A user's phone drops for 20 seconds. How do they get missed comments?

On reconnect the client sends Last-Event-ID (or its last seen comment id). Any gateway can replay newer comments from a shared Redis recent buffer, bounded to a few minutes. For longer gaps, the client fetches history over HTTP with a cursor. Clients de-duplicate by comment id since replay and live may overlap.

How to answer

Two tiers: short gap from cache, long gap from storage. Mention de-duplication.

Likely follow-ups
  • Should a phone in the background keep the connection? (No; disconnect and catch up on return.)
How many connections can one gateway hold, and what limits it?

LinkedIn reported about 100,000 persistent connections per frontend in practice. Limits are memory for socket buffers and per-connection state, file descriptors, CPU for TLS and serialisation, and fan-out work per message. It is not the 65k port range, because connections are identified by the 4-tuple. Use event-driven I/O (epoll, actors, Netty) rather than a thread per connection.

How to answer

Give a number with its source, then the real bottlenecks. A kernel engineer can shine here.

Likely follow-ups
  • How do you rebalance after scaling out?
Design the flying hearts / emoji swarm.

Clients batch taps locally and send counts every second or two. An ingest API writes asynchronously to Kafka. A stream job (Flink or Spark) sums per (video, emoji) in 2-second windows and publishes totals on the video channel. Clients animate a swarm scaled to the totals. Nothing per-tap is stored. Hotstar ran this shape with Spark 2-second micro-batches and a 500 ms batched Kafka writer.

How to answer

Say "aggregate, don't forward" in the first sentence.

Likely follow-ups
  • Exactly-once counting? (Not needed; approximate is fine.)
A gateway with 100k viewers crashes. What happens next?

No data is lost; the gateway held only connections. Clients reconnect with exponential back-off plus jitter, the load balancer spreads them across healthy gateways, and those gateways subscribe to the video if needed. Clients resume with Last-Event-ID. The endpoint store entry for the dead gateway expires by TTL or is removed after a failed push.

How to answer

Name the storm and the jitter fix; that is what is being tested.

Likely follow-ups
  • How do you deploy a new gateway version without the same storm?
Which database stores comments and how do you paginate history?

A wide-column store (Cassandra or DynamoDB), partitioned by (video_id, time bucket) and clustered by comment_id descending. History uses cursor pagination: "comments before id X, limit 20", one seek and stable under inserts. Offset pagination is slow and shifts while new comments arrive.

How to answer

Justify by access pattern: append-heavy, newest-first, no joins.

Likely follow-ups
  • How do you delete abusive comments? (Status flag plus a "hide" event; avoid tombstone storms.)
How do you run this across three regions?

Each region has its own gateways and keeps only local subscriptions. A comment is written in the commenter's region and published to the dispatchers of every region, which each deliver to their local gateways. LinkedIn chose this cross-region publish over replicating subscription state; Facebook's 2011 design similarly wrote locally and read globally because comments are rarer than views. Storage replicates asynchronously.

How to answer

Compare "replicate subscriptions" vs "replicate publishes" and pick the one that moves less data.

Likely follow-ups
  • What happens to ordering across regions? (Approximate, by time-sortable id.)

Scenario: comments freeze when India hits the winning six

At the big moment, comment latency jumps from 200 ms to 15 s and some viewers see nothing. Video is fine.

Weak answer: "Scale up the database."

Strong answer: the write path is probably fine (writes are only thousands/s). Check fan-out: dispatcher CPU, gateway send queues, and per-connection buffer drops. Immediate mitigation: raise the sampling strength (fewer comments per frame), flip the stream into CDN snapshot mode, and reduce per-user post rate. Longer term: relay tier, pre-scaling before scheduled events, load tests that replay a real spike.

Likely follow-ups
  • Which three metrics would have warned you earlier?

Scenario: "Just use Kafka with a topic per video"

The interviewer suggests Kafka for everything since it is "the standard for streaming".

Weak answer: agree and draw gateways consuming topics.

Strong answer: "Kafka is my durable log behind the write path. But millions of short-lived topics, and gateways that need to join and leave video subscriptions every second, are a poor fit. Each gateway would end up consuming many partitions it does not need. A lightweight pub/sub or a dispatcher with an endpoint store gives cheap dynamic subscriptions. LinkedIn made the same call."

Likely follow-ups
  • When would Kafka be right for the last hop? (Few, long-lived, high-value streams.)

Common mistakes

  • Polling the database for new comments.
  • Promising every viewer every comment on a mega-stream.
  • Routing every comment to every gateway (broadcast).
  • Treating each reaction tap as a stored event.
  • Ignoring reconnect storms and deployments of connection servers.
