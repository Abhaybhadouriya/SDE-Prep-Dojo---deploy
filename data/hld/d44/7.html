Where Kafka, Kubernetes and Docker fit

ToolJobDetails
KafkaDurable log behind the write path; reactions pipelineTopic comments keyed by video_id feeds moderation, search, analytics and replay. Topic reactions feeds the windowed aggregator (Flink or Spark). Not used for the per-viewer last hop. See Kafka core concepts and Streams & Flink.
KubernetesRuns gateways, dispatchers, comment serviceGateways are stateful-ish (long connections): scale on connection count, not CPU, using a custom metric in HPA; pre-scale before a known match start. Use a long grace period and PodDisruptionBudgets so node upgrades do not cause reconnect storms. See Scheduling & Autoscaling and Services & Networking.
DockerPackaging and tuningGateway image sets file-descriptor limits and sysctls for many sockets; keep it small so new pods start fast during a spike. See Docker in production.

Why each tool sits where it does. Kafka keyed by video_id keeps one stream's comments in order on one partition, so moderation and replay see them in the order they were posted, and a crashed consumer resumes from its offset without losing anything. Kubernetes fits the gateways only if you scale on the thing that actually runs out (open connections and file descriptors), because a gateway holding 100,000 idle sockets uses little CPU. Docker matters because the limits that cap a gateway (ulimit, socket buffers) are set in the image and pod spec, and a small image means a new gateway is ready in seconds when a match starts.

Careful: a Kubernetes Service in iptables mode balances new connections, not load. After a scale-up, old gateways keep their long-lived connections, so new pods sit idle. Gateways must actively shed (ask a share of clients to reconnect) to rebalance.
