Deep dives

1. How do comments reach the browser? Polling vs long-poll vs SSE vs WebSocket

OptionHowVerdict here
Short pollingGET every N secondsFacebook tried polling when it launched live commenting in 2011 and found even 5-second intervals not good enough for real-time feel (Meta engineering). It also hammers the database.
Long pollingServer holds the GET until there is dataWorks through any proxy, but one request per batch adds overhead and reconnect gaps.
SSEOne long HTTP response streaming text/event-streamBest fit. Traffic is almost all server-to-client; it is plain HTTP; browsers have EventSource with built-in reconnect and Last-Event-ID. LinkedIn chose SSE, noting WebSockets sometimes get blocked by firewalls.
WebSocketFull-duplex TCP channel after an HTTP upgradeGreat for chat or games where both sides talk a lot. Here posts are rare and can use a normal POST.

SSE gotchas to mention: some proxies buffer streamed responses (disable buffering, send a heartbeat comment line every ~15 s), and HTTP/1.1 browsers limit connections per domain (use HTTP/2, where streams share one TCP connection). More in Pattern: Real-time Updates and API Design & Communication.

From your world

A gateway holding 100,000 idle connections is an epoll problem. Each connection is a socket file descriptor plus kernel send/receive buffers. The limits are memory (buffers), ulimit -n and fs.file-max, and CPU for TLS, not the 65,535 port numbers, because a server socket is identified by the full 4-tuple. Tune net.ipv4.tcp_rmem/wmem down for mostly-idle streams.

2. Fan-out across gateways: three designs

  • Why co-locate viewers? If a stream's 25M viewers are spread over all 2,000 gateways, every gateway subscribes to it, and B collapses into A. Hashing video_id at the load balancer (consistent hashing) packs a video's viewers onto as few gateways as needed. Hello Interview recommends exactly this layer-7 trick. But be careful: plain consistent hashing of one video_id maps every viewer to one gateway, and the 25M-viewer stream needs ~250-500 gateways by our own estimate. Use consistent hashing with bounded loads (a node that is full passes the key to the next node on the ring), or map each video to a gateway set sized by viewer count: hash(video_id, i) for i in 0..k-1, growing k as viewers grow. Then a mega-stream gets just enough gateways and a small stream gets one.
  • Why not Kafka for the last hop? A gateway cannot know in advance which of millions of videos its viewers will want, so with Kafka every gateway ends up consuming every topic. LinkedIn's talk makes this point: adding frontends then stops helping. Kafka is great behind the comment service (durable log for analytics, moderation and the reactions aggregator), not for per-viewer routing. systemdesign.one reaches the same conclusion.
  • Redis pub/sub is fire-and-forget: if a gateway is briefly disconnected it misses messages. That is acceptable because comments are already stored and clients can catch up.
  • Multiple regions. Keep subscriptions local to each data center and publish every comment to the dispatchers of each region. LinkedIn chose cross-region publish over replicating subscription tables; Facebook's 2011 design similarly wrote locally and read globally because comments are rarer than views.

Stop here for SDE-1. "SSE for one-way push, POST for writes" and "co-locate a video's viewers on a few gateways and publish once per gateway through pub/sub" are the interview-sufficient core. Deep dives 3-6 (mega-stream sampling and relay trees, reconnect storms, reaction aggregation, ordering and moderation) are what an SDE-2 answer adds.

3. The mega-stream: sampling, batching, relay trees and CDN snapshots

When 5,000 comments a second meet 25 million viewers, you combine four tools:

  1. Sample per viewer. Each gateway keeps a small per-video ring buffer and picks at most ~10 comments per second, ranked: the viewer's own comment, friends, verified accounts, then random. Report "312 more" so the UI shows activity.
  2. Batch into frames. One SSE event per second with many comments is far cheaper than many tiny writes. Each write() syscall and TLS record has fixed cost.
  3. Relay tree. A dispatcher sending to 500 gateways becomes the bottleneck. Add a middle tier: dispatcher to 20 regional relays, each relay to 25 gateways. Discord hit the same wall fanning messages out to big servers and built Manifold, which groups recipients by remote node so the sender does one send per node (Discord blog).
  4. CDN snapshot mode. Above a threshold (Hello Interview suggests numbers like 100,000 viewers or 500 comments/s, with hysteresis so you do not flap), stop pushing per connection. Publish a snapshot of the latest 100-200 comments to the CDN every ~1 s; clients poll it and animate. You trade 1-2 s of extra delay for near-free fan-out.

From your world

The relay tree is a multicast distribution tree (think PIM): replicate as late as possible, close to the receivers, so the root link carries one copy. Sampling under overload is tail drop / RED on a congested queue: you deliberately drop low-priority packets so the important ones still meet their latency budget.

4. Slow consumers, disconnects and reconnect storms

  • Slow phone on 3G. If a client's TCP send buffer fills, the gateway must not queue forever. Keep a tiny per-connection queue and drop the oldest frame (comments are stale after seconds anyway). This is backpressure with a drop policy.
  • Short disconnects. The browser's EventSource reconnects automatically and sends Last-Event-ID (defined in the HTML SSE spec). The gateway replays from the Redis recent buffer, bounded to a few minutes. The client de-duplicates by comment id, because the replay and the live stream can overlap.
  • Reconnect storm. If a gateway with 100k connections crashes, 100k clients reconnect at the same instant. Use randomised, exponential back-off with jitter on the client (and the SSE retry: field to suggest a delay), and admission control at the load balancer.
  • Deployments. Never kill all gateways at once. systemdesign.one recommends keeping old servers running for hours so long-lived connections drain naturally. In Kubernetes, that means a long terminationGracePeriodSeconds and a slow rolling update.

5. Reactions: count, do not forward

Hotstar's emoji system is a good real example. Clients send emoji submissions to a Go HTTP API, which writes them to an in-memory channel and returns success without waiting. Goroutines flush to Kafka every 500 ms. A Spark Streaming job aggregates in 2-second micro-batches and writes results to a second Kafka topic. A consumer normalises the totals and pushes the most popular emojis to clients over Hotstar's in-house PubSub system, and clients play the animation (High Scalability repost). The trade-off they accepted: async writes risk losing a few emojis, which nobody can notice.

Viewer counts work the same way: gateways report local connection counts per video every few seconds and an aggregator sums them. Exact counts are not needed; approximate unique viewers use HyperLogLog. See Distributed Counter and Counting & Aggregation.

6. Ordering and moderation

Order is "roughly by time" using time-sortable IDs; perfect global order across regions is not worth the latency. Moderation runs in two speeds: a fast synchronous filter (blocklist, rate limit, spam score) before publish, and slower ML or human review consuming the Kafka log. If a comment is later hidden, publish a small "hide id X" event so clients remove it.
