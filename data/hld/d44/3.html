Key APIs

First, the transport. The stream below uses SSE (Server-Sent Events): the browser makes one ordinary HTTP GET, and the server never finishes the response. It keeps writing small text lines (id:, event:, data:) down that one long-lived response. It is one-way (server to client only), and the browser's built-in EventSource reconnects by itself and sends Last-Event-ID so the server can resume where it stopped. A WebSocket is different: after an HTTP upgrade it becomes a full-duplex framed channel over TCP, where both sides can send at any time. Long polling is the old trick: the server holds each GET open until it has data, answers, and the client asks again.

From your world

SSE is like streaming syslog or telemetry push over one TCP session: the device opens the session once and keeps writing records down it, and the collector just reads. WebSocket is more like a full bidirectional control session where both ends issue commands. Deep dive 1 compares all four options in more detail.

# Post a comment (user id comes from the auth token, never from the body)
POST /v1/videos/{videoId}/comments
Authorization: Bearer ...
{ "text": "What a six!", "clientMsgId": "c-91f2" }        -> 202 { "commentId": "1739..." }

# History page when joining late: cursor pagination, newest first
GET  /v1/videos/{videoId}/comments?before={commentId}&limit=20

# Real-time stream: Server-Sent Events (one long-lived HTTP response)
GET  /v1/videos/{videoId}/stream
Accept: text/event-stream
Last-Event-ID: 1739...          (sent automatically by the browser on reconnect)

# Reactions are batched by the client: counts, not individual taps
POST /v1/videos/{videoId}/reactions   { "counts": {"heart": 7, "fire": 2}, "windowEnd": 1732350000 }

What the stream sends (each SSE event has an id so the client can resume):

id: 1739003
event: comments
data: {"items":[{"id":"1739001","user":"asha","text":"What a six!"}, ...], "dropped": 312}

event: reactions
data: {"heart": 48211, "fire": 9120, "window": "2s"}

event: viewers
data: {"count": 24873110}
  • Cursor, not offset, for history: "comments with id below X, newest first" is one index seek and stays stable while new comments arrive. Offsets shift under you on a busy stream.
  • clientMsgId lets the server drop a retried duplicate post and lets the commenter's own client show the comment instantly (optimistic UI).
  • Comment IDs are time-sortable (Snowflake-style, see Unique ID Generator), so ordering and cursors come for free.
