Quick quiz

Why is SSE a good default for live comments?

  1. It carries binary frames, which compact comment batches need
  2. It guarantees exactly-once delivery to each viewer
  3. Traffic is one-way, and SSE is plain HTTP with resume
SSE streams events over a normal HTTP response; EventSource reconnects and sends Last-Event-ID. SSE is text-only (binary is a WebSocket feature), and nothing in it promises exactly-once.

25M viewers and 4,000 comments/s with full fan-out is roughly how many deliveries per second?

  1. 1011 (4 x 103 x 2.5 x 107)
  2. 108, one push per comment per gateway
  3. 105, since pub/sub publishes each comment once
Every viewer would get every comment: 4 x 103 x 2.5 x 107 = 1011. Publishing once per gateway saves broker work, but the gateways still write to every socket. Hence sampling and batching.

Why hash video_id at the layer-7 load balancer?

  1. To spread one video's viewers evenly over every gateway
  2. So a video's viewers share few gateways, shrinking fan-out
  3. So each gateway can keep its videos' comment history locally
Co-location keeps the number of gateways subscribed to each video small. Spreading viewers over every gateway is exactly what makes per-video pub/sub collapse into "everyone gets everything".

Why is plain consistent hashing of video_id not enough for a 25M-viewer stream?

  1. It maps every viewer to one gateway, but ~250+ are needed
  2. It spreads viewers over all 2,000 gateways, so B becomes A
  3. It breaks Last-Event-ID resume, since ids differ per gateway
One key hashes to one node. Use bounded-load consistent hashing or a per-video gateway set hash(video_id, i) for i in 0..k-1, with k sized by viewer count.

Why is Kafka a poor fit for delivering comments to gateways?

  1. Kafka cannot keep up with 4,000 writes per second on a topic
  2. Kafka messages are too large for short comment text
  3. Gateways can't know which videos they need, so they read all
LinkedIn's talk makes this exact argument; subscriptions change every second as viewers come and go. Kafka handles far more than 4,000 writes/s and stays behind the write path.

How should flying-heart reactions be processed?

  1. Store every tap so a replay can show the exact animation
  2. Batch on the client, count in short windows, push totals
  3. Forward each tap through pub/sub, the same way as comments
Hotstar aggregated emojis in 2-second Spark micro-batches and pushed only totals. Individual taps have no value later, and forwarding them multiplies the fan-out problem.

A gateway crashes. What prevents a thundering herd on reconnect?

  1. A bigger database to absorb the reconnect reads
  2. Sticky sessions so clients return to the same gateway
  3. Client back-off with random jitter
Jitter spreads 100k reconnects over seconds instead of one instant. The database is not the bottleneck, and the old gateway is gone, so stickiness cannot help.

What is the trade-off of CDN snapshot mode?

  1. Comments shown in snapshot mode are never stored in history
  2. It needs WebSockets, because CDNs cannot cache SSE
  3. ~1-2 s extra delay in return for near-free fan-out
Clients poll a CDN-cached snapshot; latency grows slightly but servers stop doing per-viewer pushes. Storage is unchanged, and snapshots are plain cached HTTP GETs.
