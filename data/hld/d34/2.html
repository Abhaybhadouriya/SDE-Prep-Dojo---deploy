Back-of-envelope estimation

Two very different traffic shapes live in this system: a calm practice load every day, and a sharp contest spike. Estimate both. (See Back-of-Envelope Estimation for the method.) The practice numbers below are our own round assumptions; the contest numbers follow Hello Interview's worked example.

Practice traffic (normal day)

  1. Users. Assume 300,000 daily active users (Hello Interview describes LeetCode as "a few hundred thousand users" - small by interview standards).
  2. Submissions per user. Assume 10 Run/Submit clicks per user per day. 300,000 x 10 = 3 million submissions per day.
  3. Average QPS. A day has about 86,400 seconds, call it 100,000 for easy maths. 3,000,000 / 100,000 = about 30 submissions per second.
  4. Peak QPS. Evenings are busier. Multiply by 5: about 150 submissions per second.
  5. Compute. Say a submission runs 50 test cases at about 20 ms each (most finish in 10-50 ms) = 1 CPU-second. 150 per second x 1 CPU-second = about 150 busy cores at peak. That is a handful of servers.

Contest traffic (the hard case)

  1. Burst. 100,000 participants. Assume 10% submit in the same moment (right after the start, or in the final minutes): 10,000 submissions at once.
  2. Tests. Each submission runs about 100 hidden test cases. 10,000 x 100 = 1,000,000 test runs.
  3. Time per test. Use a cautious 100 ms per test. 1,000,000 x 0.1 s = 100,000 CPU-seconds of work.
  4. Deadline. We want the whole burst drained in about 60 seconds. 100,000 / 60 = about 1,667 cores.
  5. Conclusion. One machine tops out at a few hundred vCPUs, so vertical scaling cannot work. We need horizontal, elastic workers, ideally scaled up before the contest starts, because we know the start time.

Storage and read traffic

  1. Submission code. Average source file about 2 KB. 3 million/day x 2 KB = 6 GB/day, about 2.2 TB/year. Fine for a sharded SQL or a key-value store; old code can move to object storage.
  2. Problems and tests. 4,000 problems x 100 tests x about 10 KB = about 4 GB (a few problems have multi-MB inputs). Small enough that every worker can cache the hot ones locally.
  3. Status polling. While 10,000 submissions are pending, each browser polls once a second: 10,000 reads/s. These must hit a cache, not the main DB.
  4. Leaderboard polling. 100,000 contestants refreshing every 5 s = 20,000 reads/s, served from Redis or a CDN-cached snapshot.
