Deep dives

1. The sandbox: running hostile code safely

Start with the ladder of options. Hello Interview grades them: running code inside the API server is bad (one infinite loop or rm -rf takes the service down), a VM per submission is good but slow and costly to start, and containers or serverless functions are great. Then go one level deeper than most candidates: a plain container is not a security boundary by itself, because it shares the host kernel. You layer defences.

From your world

You already know every layer. A sandbox is a process started with clone(CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUSER ...), put in a cgroup v2 with memory.max, pids.max and cpu.max, given setrlimit on file size and stack, then locked with a seccomp-BPF filter before execve. A "Time Limit Exceeded" is your supervisor sending SIGKILL when CPU time crosses the limit, and "Memory Limit Exceeded" is the cgroup OOM killer. The fork bomb is stopped by pids.max, exactly like on any shared Linux box.

Real failure: Judge0, a popular open-source judge, had a sandbox escape in 2024 (CVE-2024-28185, CVSS 10.0, fixed in 1.13.1). The judge wrote a run_script into the sandbox directory, and a symlink planted by user code pointed that write at a file outside the box. The lesson: the code that prepares the sandbox (running with privileges, outside it) is part of the attack surface too. Never follow links inside a box from a privileged process, and keep a second wall (gVisor or a VM) under the first.

2. Fair timing and correct verdicts

A judge must be fair: the same code should get the same verdict. Three rules make that true.

  1. Measure CPU time, not elapsed time. The time the job sat in the queue, or the time the OS ran someone else, must not count. isolate's --time limits CPU time and reports both time and time-wall in its meta file. A wall-time limit is still needed, but set it much higher, only to catch programs that sleep.
  2. Avoid noisy neighbours. Pin each sandbox to dedicated cores (cgroup cpuset), run at most one sandbox per physical core during contests, and do not oversubscribe. Hyper-threading siblings and memory bandwidth still cause jitter, so time limits get a safety margin.
  3. Map exit states to verdicts clearly. isolate's meta file gives status TO (timed out), SG (killed by signal), RE (non-zero exit), XX (internal error), plus max-rss and cg-oom-killed. Your worker turns these into TLE, RE, MLE, and turns XX into "retry on another worker", never into a user-facing failure.

Test harness. Write the tests once per problem, not once per language. Use a standard text format for inputs (for example a binary tree as a level-order array [3,9,20,null,null,15,7]), and give each language a small harness that parses it, calls the user's function and prints the result. For problems with many correct answers (any valid path, floating point within 1e-6) use a checker program instead of an exact string compare. Stop at the first failed test to save CPU, and return which test failed (but never reveal hidden input).

Stop here for SDE-1. The sandbox layers (namespaces, cgroups, seccomp, no network, gVisor or Firecracker for stronger isolation) and fair CPU-time verdicts are the interview-sufficient core. Deep dives 3-5 (contest autoscaling, the leaderboard encoding, retry safety) are what an SDE-2 answer adds.

3. Contest spikes and elastic workers

The estimate said about 1,667 cores to drain a 10,000-submission burst in a minute, while a normal evening needs about 150. Paying for 1,667 cores all week is waste, so:

  • Pre-scale before the start time. Contests are scheduled; registration counts tell you roughly how many workers you need.
  • Autoscale on queue depth, not CPU. CPU only rises after work arrives; queue depth tells you how far behind you are right now. Workers needed = pending jobs x average job seconds / target drain seconds.
  • Warm pools. Keep sandboxes pre-created per language (containers are reused across submissions after a reset, or a pool of snapshotted microVMs) so a job never waits for an image pull or a JVM start.
  • Priority lanes. Contest jobs first, practice jobs second; "Run" (sample tests) can use a smaller, faster lane than "Submit".
  • Back-pressure. If the queue is still too deep, show "judging, position 3,200" rather than timing out. The verdict is still correct; only the wait grows.

4. The live leaderboard

Ranking rule (Hello Interview's version): score = problems solved; ties broken by the time taken from contest start. Encode both in one number so a single Redis sorted set does all the work:

# score = solved * 10^7 - penaltySeconds   (higher is better; penalty under 10^7 s)
ZADD   contest:42:lb  29995120  user:981      # 3*10^7 - 4,880 s penalty
ZRANGE contest:42:lb  0 99  REV  WITHSCORES   # top 100 (ZREVRANGE is deprecated since Redis 6.2)
ZREVRANK contest:42:lb user:981               # my rank

Updates happen only when a verdict is Accepted for a problem the user had not solved yet, so the write rate is small (at most 100,000 users x 10 problems over 90 minutes, about 185 writes/s on average). Reads are the big part: about 20,000/s. Two tricks keep them cheap: every few seconds publish a snapshot of the top 1,000 to a cache or CDN that everyone reads, and answer only "my rank" from Redis. The full design of rankings is on Real-time Leaderboard. Many real contests also freeze the public board in the final hour - a product rule that also caps read load.

5. Retries without double counting

A worker can die mid-run (node lost, spot instance reclaimed). The queue then redelivers the job, so delivery is at least once. Make the result write idempotent: UPDATE submission SET verdict=?, status='DONE' WHERE submission_id=? AND status<>'DONE', and only bump the leaderboard if that update changed a row and it is the user's first AC for the problem. Use a visibility timeout a bit longer than the worst-case job (100 tests x up to about 100 ms plus compile, so around 30 s), and send jobs that fail three times with XX to a dead-letter queue for a human. The general pattern is on Managing Long-running Tasks.
