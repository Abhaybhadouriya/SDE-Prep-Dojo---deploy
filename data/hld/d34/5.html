Architecture: follow one submission

Click Next or Play. Each step adds one box, so you can rebuild the drawing on a whiteboard in the same order.

  1. Submit. The browser POSTs the code with an idempotency key to the API server.
  2. Record first. The API writes a Submission row with status QUEUED (server-side timestamp) and returns 202 {submissionId}.
  3. Enqueue. A small message {submissionId, problemId, language} goes to a queue. The queue absorbs spikes and lets a failed job be retried.
  4. Pull and sandbox. A worker for that language pulls the job and starts code in a fresh, locked-down sandbox (no network, CPU/memory/time limits, read-only filesystem).
  5. Tests from cache. The worker reads the hidden tests from local disk; on a miss it downloads that test-set version from object storage once.
  6. Verdict. The harness compares output with expected output (or runs a custom checker), stops at the first failure, and writes the verdict back.
  7. Fan out. The worker updates the status in Redis (where polls are served) and, for a contest, bumps the user's score in a Redis sorted set.
  8. Spike. During a contest the queue depth jumps. Autoscaling on queue depth (and pre-scaling before start) adds workers until the burst drains.
