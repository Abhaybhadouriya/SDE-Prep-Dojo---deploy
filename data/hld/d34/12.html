Quick quiz

Which resource dominates capacity planning for an online judge?

  1. Disk for submissions, since every run keeps its code and output
  2. Network bandwidth for uploading test cases to each worker
  3. Database connections, since every poll is a database read
  4. CPU-seconds inside sandboxes during contest bursts
Code is about 2 KB per submission; the burst needs about 1,667 cores to drain 100k CPU-seconds in a minute. Polls are cheap cache reads.

Why should Time Limit Exceeded be based on CPU time?

  1. So queue waits and noisy neighbours do not penalise the user
  2. Because wall time cannot be measured inside a container
  3. Because CPU time also counts the time spent reading stdin
  4. So multi-threaded code gets a proportionally larger limit
Wall time includes waiting. CPU time measures only the program's own work, which makes verdicts repeatable. (Keep a looser wall-time cap too, so a sleeping program cannot hold a worker forever.)

What stops a fork bomb inside the sandbox?

  1. Docker's default seccomp profile, which blocks fork()
  2. A read-only root filesystem, so no new binaries can start
  3. A cgroup pids limit (or isolate's process limit)
  4. A separate network namespace with no interfaces
Limiting the number of processes (pids.max) caps fork bombs. The default seccomp profile still allows fork and clone; isolate allows only one process by default.

What does gVisor add on top of a normal container?

  1. A small hardware VM per container, booted in about 125 ms
  2. A user-space kernel that handles the app's syscalls
  3. A seccomp filter generated from the language runtime
  4. Faster syscalls, because it skips the host scheduler
gVisor's Sentry intercepts syscalls and services them itself, so a host-kernel bug is much harder to reach. The cost is slower syscall-heavy code. The 125 ms microVM is Firecracker.

Why autoscale judge workers on queue depth instead of CPU?

  1. Kubernetes cannot read CPU metrics from sandboxed pods
  2. CPU-based scaling never scales a deployment back down
  3. Queue depth is cheaper to store in the metrics system
  4. Queue depth shows the backlog now; CPU rises only later
Backlog is the leading signal of how far behind you are; CPU is a lagging one, and it stays flat while jobs wait for a free worker.

A job is redelivered after a worker crash. What prevents a double leaderboard bump?

  1. Kafka exactly-once, which stops the job being delivered twice
  2. Running each job twice and keeping only matching verdicts
  3. A conditional verdict write, bumping only on the first AC
  4. A longer visibility timeout so the job is never redelivered
Delivery is at least once at the consumer side whatever the queue promises, and a longer timeout only makes redelivery rarer. Make the side effects idempotent (safe to repeat).

Why is a classic Kafka consumer group a weak fit as the judge's work queue?

  1. Ordered per-partition commits: head-of-line blocking, capped parallelism
  2. Kafka cannot store messages bigger than 1 KB, so code will not fit
  3. Kafka deletes a message as soon as any one consumer in the group reads it
  4. Kafka has no way to replay jobs after a worker crashes
A slow job blocks the partition behind it, and you cannot run more consumers than partitions. Per-message-ack queues (SQS, RabbitMQ) fit better. Kafka 4.x share groups (KIP-932, Queues for Kafka) add per-message acks and consumers beyond the partition count; check their maturity in your version. Classic consumer groups keep the head-of-line problem.
