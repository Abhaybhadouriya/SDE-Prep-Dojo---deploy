Where Kafka, Kubernetes and Docker fit

🐳

Docker

One image per language runtime (python:3.12, eclipse-temurin:21, gcc). Run with --network none, --read-only, --memory, --pids-limit, --cap-drop ALL, a custom seccomp profile, and a non-root user.

 ☸️

Kubernetes

Worker Deployments per language on a dedicated node pool (taints), a RuntimeClass using gVisor's runsc, a deny-all NetworkPolicy, and KEDA scaling on queue length.

 📨

Kafka

Good for the event stream (submission-judged events feeding leaderboard, analytics, plagiarism checks). For the work queue itself, a per-message-ack queue (SQS, RabbitMQ) is a simpler fit than classic consumer groups. Kafka 4.x share groups (KIP-932, "Queues for Kafka") add per-message acks and more consumers than partitions; check their maturity in your version.

 
# Kubernetes: run judge pods under gVisor, no network, hard limits
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: { name: gvisor }
handler: runsc
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: judge-python }
spec:
  replicas: 20
  selector: { matchLabels: { app: judge-python } }
  template:
    metadata: { labels: { app: judge-python } }
    spec:
      runtimeClassName: gvisor
      automountServiceAccountToken: false
      tolerations: [{ key: "judge", operator: "Exists", effect: "NoSchedule" }]
      containers:
      - name: worker
        image: registry.example.com/judge-python:3.12
        securityContext:
          runAsNonRoot: true
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities: { drop: ["ALL"] }
          seccompProfile: { type: RuntimeDefault }
        resources:
          requests: { cpu: "1", memory: "512Mi" }
          limits:   { cpu: "1", memory: "512Mi" }

Why not Kafka as the job queue? A Kafka consumer commits offsets per partition in order. If one job in a partition takes 10 s (or hangs), the jobs behind it wait - head-of-line blocking - and you can only have as many parallel consumers as partitions. A judge wants "any free worker takes any job, ack each job separately, redeliver on timeout". That is SQS/RabbitMQ semantics. Kafka shines one step later, as the durable log of judged submissions that many consumers read. Compare on Kafka vs RabbitMQ vs SQS.
