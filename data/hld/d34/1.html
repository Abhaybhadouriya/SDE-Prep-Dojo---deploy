Requirements

Always split requirements into what the system does (functional) and how well it must do it (non-functional). Hello Interview's breakdown of this problem uses four of each; we keep the same spine and add the pieces a kernel engineer would ask about.

Functional (in scope)
  • Browse a list of problems (about 4,000 on a site like LeetCode), filter by level and tag.
  • Open a problem, write code in a browser editor, pick a language (Python, Java, C++, Go, ...).
  • Run against sample tests, and Submit against the full hidden test set; get a verdict.
  • Join a timed contest (for example 90 minutes, 10 problems) and watch a live leaderboard.
Out of scope (say it out loud)
  • Login and accounts (assume a session or JWT gives us userId).
  • Payments, discussion forums, profiles, social features.
  • Plagiarism detection (mention as a later async consumer).
  • Problem authoring tools (an admin uploads statements and tests).
Non-functional requirementTargetWhy it matters
Isolation and securityUser code must never read other users' code, the hidden tests, the network, or the hostThis is the number one requirement. A sandbox escape is a full breach.
Verdict latencyResult within about 5 seconds for a normal submissionUsers wait on the page. Hello Interview uses 5 s as the target.
Contest scale100,000 participants in one contest; bursts of about 10,000 submissions at onceTraffic is calm all week and spikes hard at contest time.
FairnessThe same code gets the same verdict every time; time limits measure CPU time, not queue waitA "Time Limit Exceeded" caused by a noisy neighbour is a correctness bug.
Availability over consistencyBrowsing and submitting stay up; the leaderboard may lag a few secondsSlightly stale ranks are fine; a down site during a contest is not.
Durability of submissionsNo accepted submission is ever lostContest ranking and user history depend on it.
