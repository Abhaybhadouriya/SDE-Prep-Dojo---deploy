Data model

Split each email into three parts with very different shapes. This is the single most important storage decision.

PartSizeAccessWhere it lives
Metadata (from, subject, date, snippet, flags, labels, thread id)~1 KBRead on every inbox list, updated often (read, label, move)Wide-column store partitioned by user_id (Bigtable / HBase / Cassandra style)
Body (raw MIME text, HTML)tens of KBWritten once, read when opened, never editedObject store or a body column, compressed, keyed by message id
Attachmentsup to 25 MBWritten once, read rarelyObject store, content-addressed by hash, cold tier after months
Search indexa fraction of textWritten on delivery, read on searchPer-user inverted index (separate cluster)
 
-- CQL-style tables. Partition key in the first ( ), clustering after.
CREATE TABLE folders_by_user (
  user_id     bigint,
  folder_id   text,            -- 'inbox','sent','trash' or a label id
  name        text,
  unread      counter,
  PRIMARY KEY ((user_id), folder_id));

CREATE TABLE messages_by_folder (       -- the inbox list query
  user_id     bigint,
  folder_id   text,
  message_id  timeuuid,        -- time-ordered id: newest first for free
  thread_id   bigint,
  from_addr   text,
  subject     text,
  snippet     text,            -- first ~100 chars, avoids reading the body
  is_read     boolean,
  has_attach  boolean,
  PRIMARY KEY ((user_id, folder_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

CREATE TABLE messages_by_id (           -- open one message
  user_id     bigint,
  message_id  timeuuid,
  rfc_msg_id  text,            -- the Message-ID header, used for threading + dedupe
  labels      set<text>,
  body_ref    text,            -- object-store key of the MIME body
  attachments list<frozen<attachment>>,  -- name, size, sha256, blob key
  PRIMARY KEY ((user_id), message_id));

CREATE TABLE threads_by_user (
  user_id bigint, thread_id bigint, message_id timeuuid,
  PRIMARY KEY ((user_id, thread_id), message_id));

Why not plain SQL? Why not plain Cassandra?

  • Relational (MySQL / Postgres): great for small rows and secondary indexes. Poor at 50 KB+ values and at 400k writes/s spread over a billion tiny "tables" (one per user). Facebook tried MySQL for Messages and found it performed badly on long-tail data as indexes grew.
  • Cassandra: scales writes beautifully, but it is eventually consistent by default. Facebook rejected it for Messages in 2010 because its consistency model was hard to fit (a read/unread flag that flips back is a visible bug). You can use quorum reads and writes, but you pay latency.
  • What big providers do: Gmail sits on Google's own Bigtable-family storage; Facebook Messages chose HBase (strong per-row consistency on HDFS); Microsoft Exchange runs its own ESE database replicated in software; Fastmail runs Cyrus IMAP stores. The common theme: a single writer (primary) per mailbox, so each mailbox is strongly consistent, and many mailboxes per machine.
  • Read and unread at NoSQL scale: wide-column stores cannot do WHERE is_read = false cheaply. The ByteByteGo chapter denormalises into separate read_emails and unread_emails tables (mark read = delete from one, insert into the other) and keeps an unread counter per folder.

From your world

Think of each mailbox as a small file system owned by one process. "One primary per mailbox" is like one kernel thread owning a socket's receive queue: no locks between writers, because there is only one writer. Replicas get the change log, much like a standby route processor that replays the active one's state updates.
