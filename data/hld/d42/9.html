Interview: drive the 45 minutes

Email (Gmail or Outlook) is a ByteByteGo Volume 2 chapter and a Grokking Advanced case study. In our gap analysis it maps to Microsoft (Outlook is their product, so expect deep questions on storage and sync) and to Google onsite reports ("design an email system like Gmail"). A good plan, using the 45-minute framework:

  1. 0-5 min: scope. Send, receive, list, search, attachments, threads, spam. Cut calendar and chat. State "never lose mail" as the top NFR.
  2. 5-10 min: numbers. 100k sends/s, 400k deliveries/s, ~730 PB metadata + ~1.5 EB attachments a year. Conclude: queue, user partition, blob split.
  3. 10-15 min: APIs. SMTP between servers, HTTP API + push for our apps, pre-signed upload.
  4. 15-30 min: architecture. Walk the stepper above: edge, durable queue, spam, mailbox writer, blob, index, notify, outbound.
  5. 30-40 min: deep dives. Pick two the interviewer cares about: durability + idempotency, storage + consistency, search, deliverability.
  6. 40-45 min: failures and wrap-up. Shard failover, remote down, bad model; what you would build next.
LevelWhat the answer looks like
SDE-1 answer looks like..."An SMTP edge writes each accepted message to a replicated queue before it says 250 OK; workers store metadata partitioned by user_id and bodies and attachments in object storage, and clients read the inbox through an HTTP API."
SDE-2 adds..."Delivery is idempotent on a Message-ID dedupe key, each mailbox has one primary with a lagged copy against logical corruption, search is a per-user index fed by events, and outbound mail uses per-domain lanes, DKIM signing and IP pools to protect reputation."
Walk me through what happens when an outside server sends mail to one of our users.

The sender looks up our MX records and connects to our SMTP edge on port 25. The edge negotiates TLS, checks IP reputation and rate limits, validates the recipient and size, and checks SPF/DKIM/DMARC. It writes the raw message to a replicated inbound queue and only then answers 250 OK. Spam consumers score it; the mailbox writer applies filters, computes the thread, stores body and attachments in the object store, writes metadata into the user's partition, and emits a "stored" event that feeds search indexing and a push notification to the user's devices.

How to answer

Tell it as a pipeline with one sentence per box, and stress the "ack after durable" moment. Draw it while you talk.

Likely follow-ups
  • What if the queue write succeeds but the 250 reply is lost?
  • Where do you reject cheaply?
How do you guarantee an email is never lost and never shows up twice?

Never lost: acknowledge SMTP only after the message is on at least two machines (replicated queue with acks=all, or a shadow copy as in Exchange's Shadow Redundancy), keep a post-delivery copy for a while to resubmit after a mailbox failover (Exchange's Safety Net), and replicate mailbox storage. Never twice: every hop retries, so make the final write idempotent with a dedupe key such as (user_id, Message-ID, content hash). A duplicate finds the key and becomes a no-op.

How to answer

Separate the two halves: durability is about when you ack, duplicates are about idempotent sinks. Name at-least-once + idempotent = effectively once.

Likely follow-ups
  • Some senders reuse Message-IDs or omit them. Now what?
  • Does Kafka exactly-once solve this?
Which database would you use for mailbox metadata and why?

A wide-column store partitioned by user (Bigtable/HBase-style, or Cassandra with care), with clustering by a time-ordered message id so the inbox list is one sequential partition read, newest first. Each mailbox has one primary for strong per-mailbox consistency. Bodies and attachments go to an object store. A relational DB struggles with the write rate and large values; plain eventual consistency causes read/unread flicker, which is why Facebook picked HBase over Cassandra for Messages.

How to answer

Lead with the access pattern (all queries per user, newest first, write-heavy), then the choice, then one real-world reference.

Likely follow-ups
  • How do you query unread mail in a NoSQL store?
  • How do you move a user to another shard?
How does search work across a user's 15 years of email?

A per-user inverted index, partitioned by user_id so a query touches one shard. Indexing is asynchronous from a "message stored" event, so new mail becomes searchable in seconds. Options are Elasticsearch with user-routing for a mid-size system, or a custom LSM-style index stored beside the mailbox at Gmail/Outlook scale. Old mail's index can sit on a colder tier. The mailbox is the source of truth, so an index can be rebuilt by replay.

How to answer

Emphasise "search is per user", which avoids scatter-gather over a billion users. Then the freshness trade-off.

Likely follow-ups
  • How do you handle deletes and label changes in the index?
  • How do you search inside attachments?
How would you build conversation threading?

Use headers: Message-ID on every mail, In-Reply-To and References on replies. At delivery, look up the referenced ids in a per-user (rfc_msg_id -> thread_id) table; join the existing thread or start a new one. If nothing matches, fall back to the normalised subject within a time window. Out-of-order arrivals get a placeholder parent. This is the REFERENCES algorithm in RFC 5256, derived from JWZ's threading algorithm.

How to answer

Name the three headers and the fallback. Say it is computed server-side at write time and stored, not recomputed on every read.

Likely follow-ups
  • Two unrelated mails both titled "Hi". What stops them merging?
  • What if a user forwards a thread to someone new?
Design the spam filtering pipeline.

Layered, cheapest first. At connect time: IP reputation, rate limits, greylisting of unknown IPs. At envelope time: SPF, DKIM, DMARC alignment. Then content ML (text, URLs, attachments, sender history), combined with per-user signals. Output inbox, spam or quarantine. User "spam / not spam" clicks feed training. Models are versioned images, canaried, and can re-score from the Kafka log after a bad release. Google reports blocking over 99.9% of spam this way, and TensorFlow models added about 100 million blocks a day.

How to answer

Show the funnel: cheap checks remove most traffic before expensive ML. Mention the feedback loop and personalisation.

Likely follow-ups
  • How do you avoid false positives on password-reset mails?
  • How fast must the model run at 400k/s?
Our outgoing mail keeps landing in Gmail's spam folder. What do you change?

Check authentication first: SPF and DKIM on every mail, DMARC published and aligned with the From: domain, valid reverse DNS, TLS. Keep the complaint rate under Gmail's 0.3% limit (aim under 0.1%), add one-click unsubscribe for bulk mail, split transactional and bulk mail onto separate IP pools and domains, warm up new IPs slowly, process bounces and complaint feedback, and suspend accounts that spam.

How to answer

Authentication, then reputation, then hygiene. Quote the real 2024 Gmail sender rules; it shows current knowledge.

Likely follow-ups
  • What exactly does DKIM sign?
  • Why separate IPs for OTP mail?
How do a user's phone, laptop and web tab stay in sync?

Each mailbox has a monotonically increasing change counter. Every change (new mail, read, move) bumps it and is logged. Clients store the last state they saw and call /changes?since=state for a delta. To avoid polling, the server pushes a small "something changed" hint over WebSocket for web and APNs/FCM for mobile; the client then pulls the delta. IMAP has the same idea with IDLE and MODSEQ; JMAP standardises it over HTTP.

How to answer

Push a hint, pull the data. Mention why: pushes can be lost, the delta is authoritative.

Likely follow-ups
  • A phone was offline for a month. Delta or full resync?
  • How do you handle offline edits that conflict?
An all-company email with a 10 MB attachment goes to 100,000 people. What happens to storage and load?

Store the attachment once, content-addressed by SHA-256, and the body once if shared; each recipient gets a small metadata row with a pointer and the blob keeps a reference count. Fan-out is 100,000 small metadata writes, pushed through the queue and spread over many partitions, so it is rate-smoothed. Virus-scan the blob once. Without dedupe this would be 1 TB; with it, about 10 MB plus 100,000 rows of ~1 KB (~100 MB).

How to answer

Do the arithmetic out loud. Then mention deletion via reference counts and per-user encryption trade-offs.

Likely follow-ups
  • How does dedupe interact with per-user encryption keys?
  • When is the blob actually deleted?
A mailbox storage server dies. Walk me through the failover and what the user sees.

Health checks detect it; the control plane promotes a replica of each affected mailbox shard and updates the directory, and proxies start routing there. Deliveries during the gap wait in the inbound queue. Messages that were acknowledged but not yet replicated are resubmitted from the post-delivery copy (Safety Net style) and deduplicated by key. Fastmail targets under 10 seconds for a failover (sometimes up to ~30 s); users see a dropped IMAP connection and a reconnect. We chose consistency, so writes to those mailboxes pause briefly rather than split-brain.

How to answer

Detection, promotion, routing, catch-up, dedupe, user impact, in that order. Mention split-brain and fencing.

Likely follow-ups
  • How do you prevent two primaries (split brain)?
  • What does a lagged copy protect against that replicas do not?

Scenario: a remote provider is down for six hours

A large provider's MX hosts return 421 "service unavailable" for six hours. Our users keep sending mail to them, about 5,000 messages a second.

Weak answer: "Retry every second until it works." That hammers the remote, fills worker slots, and blocks mail to everyone else.

Strong answer: mail to that domain sits in its own lane of the outbound queue, so other domains are unaffected. Retries use exponential backoff with jitter (RFC 5321 suggests at least 30 minutes between tries, and not giving up before 4-5 days), with a per-domain concurrency cap. Six hours x 5,000/s = ~108 million queued messages x 50 KB = ~5.4 TB, which a replicated queue holds easily. When the remote recovers, drain gradually so we do not look like a flood. Users get a "delayed" notice after a few hours and a bounce only after the give-up time.

Likely follow-ups
  • How do you know the remote is back without hammering it?
  • Which mails should jump the queue (OTPs)?

Scenario: the new spam model sends real mail to spam

After a model release, "not spam" clicks jump 5x and a bank complains its OTP emails go to spam.

Weak answer: "Whitelist the bank." It fixes one sender and hides the bug.

Strong answer: roll back the model image tag (it was canaried, so only a slice of traffic got it); replay the affected window from the Kafka log through the old model and move mail back to inbox for affected users; add the "not spam" rate as an automatic canary gate; add a regression set of known-good transactional senders to model evaluation.

Likely follow-ups
  • How do you move already-delivered mail without confusing users?

Common mistakes: storing attachments in the database; designing search as one global index; acking SMTP before the message is replicated; forgetting outbound retries and per-domain queues; ignoring SPF/DKIM/DMARC; using eventual consistency for read/unread state; treating email like chat (email is store-and-forward and must interoperate with the whole internet). Compare with chat and notification system.
