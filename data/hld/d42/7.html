Where Kafka, Kubernetes and Docker fit

ToolWhereWhy
KafkaInbound queue (raw mail), "message stored" events (to search, notifications, analytics), outbound queue, bounce and complaint topicsAbsorbs 400k/s bursts; replicated log so we can ack SMTP safely; replay lets us rebuild a search index or re-run a fixed spam model. Partition by recipient user_id so one user's mail stays in order.
KubernetesSMTP edge, spam scorers, mailbox writers, indexers, API, IMAP gateway, SMTP out workersAll are stateless and scale on queue lag (KEDA / HPA on consumer lag). Spam ML models roll out with canaries. See autoscaling.
Not on plain KubernetesMailbox storageExabyte stateful storage usually lives on dedicated storage fleets (Fastmail's 2U slot servers, Exchange's JBOD servers). If you do run it on Kubernetes, use StatefulSets with local volumes and an operator (operators).
DockerEvery service image; the spam-model server image pins the model versionSame image in test and production; a bad model rolls back by image tag.

An outbound SMTP worker pool on Kubernetes needs fixed, warmed-up egress IPs (reputation is per IP). Say "egress gateway with a stable IP pool per mail class". This is a nice detail that shows you have thought about deliverability, not only scaling.
