Architecture: the life of an email

Click Next or Play. We follow one email from an outside sender to Bob, and then Bob's reply going out.

  1. SMTP edge. DNS MX records point the world at our edge (behind an L4 load balancer). It does the TLS handshake, checks the sender IP's reputation, rate-limits abusive IPs, checks SPF and DKIM, and rejects unknown recipients or over-size mail early (cheap rejects save everything downstream).
  2. Durable queue first. The raw message is written to a replicated inbound queue (Kafka or a replicated spool). Only then do we answer 250 OK. Exchange Online does the same: each transport server keeps a redundant copy before it acknowledges (Shadow Redundancy).
  3. Spam, phishing, virus. Consumers score each message with ML plus rules (sender reputation, DMARC result, URLs, attachments). Google says this mix blocks over 99.9% of spam, phishing and malware. Result: inbox, spam folder, or quarantine.
  4. Mailbox writer. Applies the user's filters and labels, finds the thread, writes body and attachments to the blob store (dedup by hash), then writes metadata rows into the user's partition and bumps the unread counter. Keyed by (user, Message-ID), so a redelivery is a no-op.
  5. Search indexing. A "message stored" event goes to the indexer, which updates Bob's per-user inverted index. It is asynchronous, so it is seconds behind, which users accept.
  6. Notify. A notification service pushes "new mail" over an open WebSocket (web) or APNs/FCM (mobile). Bob's app then fetches the delta. See real-time updates.
  7. Bob replies. The client calls send with an idempotency key. The send service stores a copy in Bob's Sent folder and writes the message to the outbound queue. If the recipient is also our user, it skips SMTP and goes straight into step 4.
  8. SMTP out. Workers pull from per-destination-domain lanes, look up the MX, sign with DKIM, open TLS and deliver. Different IP pools are used for personal mail and for bulk mail, so one bad sender does not hurt everyone's reputation.
  9. Failure path. If the remote server is down or answers 4xx, the message stays in the queue and is retried with growing gaps. RFC 5321 suggests waiting at least 30 minutes between tries and not giving up for at least 4-5 days, then sending a bounce (DSN) back to Bob.

From your world

Per-destination-domain lanes are virtual output queues: a switch keeps a separate queue per egress port so one congested port does not block traffic to the others (head-of-line blocking). If yahoo.com is slow, mail to outlook.com must not wait behind it. The retry schedule is TCP's retransmission timer with exponential backoff, just stretched from milliseconds to hours.
