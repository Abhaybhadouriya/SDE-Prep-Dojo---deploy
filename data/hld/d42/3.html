Key APIs

There are two worlds. Between servers we must speak standard SMTP on port 25. Between our own apps and our backend we are free to use a modern HTTP API (Gmail and Outlook do; the open standard version of this idea is JMAP, RFC 8620). Old desktop clients still use IMAP, so we keep an IMAP gateway too.

# Client API (HTTPS + OAuth token). All calls are scoped to the signed-in user.
POST   /v1/messages/send            # body: to[], cc[], bcc[], subject, body, attachmentIds[]
       Idempotency-Key: 5c1e...     # retry-safe: same key = same email, never two
POST   /v1/attachments              # returns uploadUrl (pre-signed) + attachmentId
GET    /v1/folders                  # inbox, sent, drafts, labels, unread counts
GET    /v1/folders/{folderId}/messages?limit=50&cursor=...   # newest first
GET    /v1/messages/{messageId}     # headers + body; attachments as links
GET    /v1/threads/{threadId}       # all messages in a conversation
PATCH  /v1/messages/{messageId}     # {isRead:true} | {labels:+["work"]} | {folderId:"trash"}
GET    /v1/search?q=from:alice invoice&cursor=...
GET    /v1/changes?since=state_8812 # delta sync for mobile: what changed since my last state
WS     /v1/events                   # push: new mail, read-state change on another device

# Server-to-server (the internet): plain SMTP
S: 220 mx.example.com ESMTP
C: EHLO mail.sender.org
C: STARTTLS ...
C: MAIL FROM:<alice@sender.org>
C: RCPT TO:<bob@example.com>
C: DATA   ... headers + MIME body ...  .
S: 250 OK queued as 7Hk2   # only after the mail is durably stored!

Attachments do not travel through the API servers. The client uploads them straight to the object store with a pre-signed URL, then sends only the attachmentId. This is the handling large blobs pattern, the same one used in S3-like storage and Dropbox.

The /changes?since= call is how phones stay in sync cheaply: the server keeps a per-mailbox change counter (a "state" or modification sequence), and the client asks only for the delta. IMAP has the same idea (CONDSTORE / MODSEQ). See API design.
