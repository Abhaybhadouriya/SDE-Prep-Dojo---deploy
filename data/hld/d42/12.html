Quick quiz

When should the SMTP edge reply "250 OK" to a sending server?

  1. After the message is safely on more than one machine
  2. As soon as DATA ends, so the sender is never kept waiting
  3. After spam scoring, so we never accept junk we must store
After 250 the sender deletes its copy, so the message must already be safe on replicated storage. Spam scoring runs later on the durable copy; holding the SMTP session for ML would slow every sender.

With 1 billion users each receiving 40 emails a day, roughly how many deliveries per second is that?

  1. 4,000, dividing 4 x 10^10 by ~10^7 seconds
  2. 40,000, since mail arrives over only 10% of the day
  3. 400,000 (4 x 10^10 / ~10^5 s)
A day has ~86,400 s, round to 10^5. 4 x 10^10 / 10^5 = 4 x 10^5 = 400,000 per second on average, and peaks are higher, not lower.

What is the best partition key for mailbox metadata?

  1. sender domain, so all mail from one company sits together
  2. (user_id, folder), clustered by a time-ordered id
  3. a hash of message_id, so writes spread evenly over nodes
Every query is about one user's mailbox, newest first, so (user_id, folder) + time-ordered id makes the inbox list one partition read. Hashing message_id spreads writes but turns every inbox open into a scatter-gather.

Which headers let a server build conversation threads?

  1. Message-ID, In-Reply-To and References
  2. Subject and Date, grouping replies that start with "Re:"
  3. Received and Return-Path, which trace the reply's route
Replies point to their parents with In-Reply-To and References. Subject is only a fallback, and Received headers describe the hops, not the conversation.

A 10 MB attachment is sent to 50,000 colleagues. What should the storage layer do?

  1. Store 50,000 copies so each mailbox shard stays independent
  2. Inline it in every metadata row so an open needs one read
  3. One blob by content hash, plus a pointer per recipient
Content-addressed dedupe turns 500 GB into about 10 MB plus small pointer rows. Inlining bloats the hot metadata tier that the inbox list reads.

Why does an outbound queue keep a separate lane per destination domain?

  1. SMTP requires one connection queue per receiving domain
  2. Smaller per-lane queues make DKIM signing much faster
  3. One slow provider must not block mail to all the rest
It avoids head-of-line blocking, like virtual output queues in a switch. SMTP itself does not mandate lanes, and DKIM cost does not depend on queue size.

Since 2024, what does Gmail require from bulk senders (over 5,000 mails a day)?

  1. SPF or DKIM, the same baseline rule as for every sender
  2. SPF + DKIM + DMARC, one-click unsubscribe, spam < 0.3%
  3. A paid sender certificate and a registered IP range
Those are Google's published bulk-sender requirements. "SPF or DKIM" is the baseline for all senders; bulk senders need all three plus unsubscribe and a low complaint rate.

Kafka is configured for exactly-once. Why does the mailbox writer still need a dedupe key?

  1. Kafka EOS covers Kafka-to-Kafka; the mailbox write is outside it
  2. EOS is off by default and too slow to switch on at mail volume
  3. Only mail from outside senders can arrive twice, so it is for them
Writing into the mailbox database is an external side effect. A consumer can crash after the write but before committing its offset, so the replay must find the (user_id, Message-ID, hash) key and do nothing. Duplicates come from internal retries too.
