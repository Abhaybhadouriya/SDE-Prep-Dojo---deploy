Back-of-envelope estimation

We use the same starting numbers as the ByteByteGo distributed email chapter: 1 billion users, each sends ~10 and receives ~40 emails a day, and the average email's metadata (headers, body text, everything except the attachment files) is about 50 KB. A day is 86,400 seconds; round it to 105.

  1. Send QPS. 109 users x 10 = 1010 sends a day. 1010 / 105 = 100,000 sends per second on average. Peak (Monday 9 a.m. in a big time zone) maybe 2-3x, so plan for ~300,000.
  2. Receive (delivery) QPS. 109 x 40 = 4 x 1010 deliveries a day = 400,000 deliveries per second. Receives are higher than sends because of mailing lists, newsletters and spam: one send can fan out to many mailboxes.
  3. Read QPS. Assume each user opens the inbox or a folder ~20 times a day: 2 x 1010 / 105 = ~200,000 list reads per second, plus email opens of a similar size. Most are served from a cache of the first page.
  4. Search QPS. Assume 2 searches per user per day: ~20,000 searches per second. Small next to delivery, but each search touches an index.
  5. Metadata storage per year. 4 x 1010 received/day x 365 x 50 KB = 4 x 1010 x 365 x 5 x 104 B ≈ 7.3 x 1017 B = ~730 PB a year, before replication.
  6. Attachment storage per year. ByteByteGo's assumption: 20% of emails carry an attachment, average 500 KB. 4 x 1010 x 0.2 x 365 x 500 KB ≈ ~1,460 PB (1.46 EB) a year. Attachments are 2x the metadata, so they get their own cheap storage tier.
  7. Ingest bandwidth. 400,000 deliveries/s x 50 KB = ~20 GB/s of metadata written, plus attachments. With 3 copies, the storage layer absorbs ~60 GB/s of writes.

The lesson from the numbers: writes are huge and never stop, every query belongs to one user, and storage is exabyte-scale. So: (1) a durable queue absorbs the 400k/s deliveries, (2) a wide-column store partitioned by user holds metadata, (3) an object store holds bodies and attachments, and (4) hot and cold tiers keep the bill sane.
