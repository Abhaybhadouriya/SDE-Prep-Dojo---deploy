A full worked mini-example: "Design a notification service"

Read this as a script. I = interviewer, C = candidate (you, at SDE-2 level). Notice the order, the numbers, the trade-off sentences, and how the candidate checks in. The full design lives on Notification System.

Minutes 0-8: hello and requirements

I: Design a notification system for an e-commerce app.

C: Before I design, a few questions. Which channels - push, SMS, email? Who sends - other internal services, or marketing too?

I: All three channels. Internal services send order updates and OTPs; marketing sends campaigns.

C: So functionally: one, services call an API to send a notification to a user on one or more channels. Two, users can opt out per channel and per category. Three, we track whether each notification was delivered. I'll leave the template editor UI and A/B testing out of scope. Non-functionally: OTPs must arrive within seconds, marketing can be slow. We must not send duplicates, especially OTPs and payment messages. Availability matters more than strict consistency. How many users?

I: Around 50 million daily active users.

Minutes 8-11: estimates

C: Let me size it. Say 50M users get about 10 notifications a day on average: 500 million a day. A day is about 10^5 seconds, so about 5,000 per second on average. Marketing campaigns are bursty - if a campaign goes to all 50M users in 10 minutes, that's about 80,000 per second for a while. So the key point: the peak is driven by campaigns, and it is much bigger than the average. That tells me we need a queue to absorb bursts, and OTPs must not wait behind a campaign.

Minutes 11-15: API and data model

POST /v1/notifications
Idempotency-Key: 4f1c...            // caller-generated, one per logical message
{
  "userId": 42,
  "category": "ORDER_UPDATE",       // or OTP, MARKETING
  "channels": ["PUSH", "SMS"],
  "templateId": "order_shipped_v3",
  "params": { "orderId": "ord_81f2" }
}
-> 202 Accepted { "notificationId": "ntf_9a1..." }

GET /v1/notifications/ntf_9a1...    -> status per channel: QUEUED | SENT | DELIVERED | FAILED

C: The API returns 202 because sending is asynchronous. The idempotency key lets callers retry safely. For data: user preferences and device tokens are small and read on every send, so a key-value store with a cache in front. The notification log is write-heavy and queried by user and time, so a wide-column store like Cassandra partitioned by user ID.

Minutes 15-25: high-level design

C: Walking an OTP through: the Auth service calls the API with an idempotency key. The API checks the dedupe store, loads preferences from the cache, renders the template and writes one message per channel to Kafka. OTPs go to a separate high-priority topic with its own workers, so a 50-million-user campaign can't delay them. SMS workers call the vendor and record the result in the log. Does this cover what you had in mind before I go deeper?

I: Yes. What happens when the SMS vendor is slow or down?

Minutes 25-37: deep dives

C: Two parts: vendor failure, and duplicates. For vendor failure, I'd put a circuit breaker (a switch that stops calling a failing dependency for a while) per vendor: after a run of timeouts, stop calling it for a short time and fail over to a second SMS vendor. Retries use exponential backoff with jitter. After N attempts the message goes to a dead-letter topic (a DLQ) and we alert. For OTPs I'd rather fail over quickly than retry slowly, because an OTP is useless after a minute - so OTP messages carry a TTL and workers drop expired ones. The trade-off: two vendors cost more and need two integrations, but SMS for login is critical enough.

C: For duplicates: Kafka consumers are at-least-once, so after a worker crash a message can be redelivered. Each message carries the notification ID, and the worker uses a two-state claim in Redis. Before calling the vendor it runs SET ntf:{id} SENDING NX EX 60 - set only if absent, expire in 60 seconds. If the key already says SENT, skip: it was delivered. If it says SENDING, another worker owns it right now, so skip too; if that worker died, the short TTL expires and a redelivery can take over. After the vendor returns OK, the worker sets the key to SENT with a long TTL, say 24 hours. That gives effectively-once sending. The remaining window is a crash after the vendor call but before writing SENT: once the 60-second claim expires, a redelivery sends again. For an OTP a rare duplicate is acceptable, and much better than a lost one. For a "payment received" message I'd also pass the notification ID to the vendor as its own dedupe or reference key, so the vendor drops the repeat.

I: How do you scale the campaign path?

C: Marketing goes through a separate topic with many partitions, keyed by user ID so one user's messages stay ordered. Email workers scale horizontally up to the partition count; on Kubernetes I'd autoscale them on consumer lag. We also rate-limit per vendor, because vendors throttle us - so for campaigns the vendor quota, not our servers, is the real ceiling. I'd spread a big campaign over time instead of blasting it.

Minutes 37-41: wrap-up

C: To wrap up: the first bottleneck at 10x is vendor quota, then the preferences cache. I'd monitor per-topic consumer lag, end-to-end OTP latency at p99, vendor error rate per vendor, and the DLQ size, with an alert on OTP p99 above a few seconds. Next I'd add per-user frequency caps so marketing doesn't spam, and a delivery-receipt webhook from vendors to fill in DELIVERED.

Notice what the candidate never did: name a technology without a reason, go silent, or spend ten minutes on one box before the whole flow worked. Also notice the check-ins at the end of each phase - they let the interviewer steer you to what they want to grade.
