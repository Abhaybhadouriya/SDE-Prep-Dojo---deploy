Phrases to use (and the trade-off sentence)

You do not need fancy words. You need a few sentences that show structured thinking. Use these on purpose.

MomentSay
Right after the prompt"Before I start, I'd like to pin down scope. Who are the users, and what are the 2-3 things it must do?"
The interviewer says "you decide""Then I'll assume 100 million daily users and a 10:1 read-to-write ratio. Tell me if you'd like different numbers."
Cutting scope"I'll leave analytics and admin tools out of scope, and come back to them if we have time."
Before estimating"Let me do quick maths to see if this fits on one machine or needs sharding."
After the first diagram"This covers the core flows end to end. Before going deeper - is there a part you'd like me to focus on?"
Choosing"There are two options here... I'd pick the second, because..."
Failure"If this box dies, here's what the user sees, and here's how we recover."
You don't know"I haven't used that directly. Reasoning from first principles, I'd expect... Does that match your experience?"
Time check"I'm conscious of time - let me finish the happy path, then I'll do the hot-key deep dive."
Wrap-up"The first bottleneck at 10x would be..., I'd watch p99 latency, error rate and consumer lag, and I'd roll out behind a feature flag (a switch that turns new code on for a few users first)."

The trade-off sentence: "I'd pick X because of A. The cost is B. If C becomes a problem, I'd switch to Y." Say it every time you choose something.

Ten worked trade-off sentences

  1. SQL vs NoSQL "I'd pick Postgres for orders because we need transactions across order and payment rows. The cost is harder horizontal scaling. If one primary can't keep up with writes, I'd shard by customer ID or move to a distributed SQL store."
  2. Kafka vs SQS "I'd pick Kafka because several teams need to read the same order events and we may need to replay them. The cost is running a cluster. If we only had one consumer and no replay, SQS would be simpler."
  3. Push vs pull feed "I'd fan out on write so feeds load instantly. The cost is a huge write burst when a celebrity posts. For accounts above a follower threshold I'd switch to pulling their posts at read time."
  4. Cache-aside vs write-through "Cache-aside, because reads dominate and a miss is cheap. The cost is a short window of stale data, which I bound with delete-on-write and a TTL. If staleness hurt, I'd write through."
  5. Sync vs async "The user waits only for the order to be saved; email and analytics go async through a queue. The cost is eventual consistency for those side effects. If a step must succeed before we confirm, it stays synchronous."
  6. Strong vs eventual "Strong consistency for the seat inventory, because double booking is unacceptable. The cost is latency and lower availability during partitions. Seat-map display can be eventual, since we re-check on purchase."
  7. Monolith vs microservices "Start as a modular monolith (one deployable app, split into clean internal modules) because the team is small and the boundaries aren't clear yet. The cost is that everything deploys together. When teams step on each other, split along the busiest boundary."
  8. Polling vs WebSockets "WebSockets for chat, because messages must arrive in under a second. The cost is stateful connection servers. For a status page that changes every minute, polling is simpler."
  9. Single region vs multi-region "One region with multiple availability zones, because that gives high availability at sane cost. The cost is a region-wide outage risk. If the SLA (the availability promised to customers) or user geography demands it, go active-passive (a standby region takes over on failure), then active-active (every region serves live traffic)."
  10. Partition count "Start the topic with enough partitions for our peak consumer parallelism plus headroom - say 3x. The cost is more open files and slower failover per broker. Adding partitions later changes key-to-partition mapping, so I'd rather over-provision early."
