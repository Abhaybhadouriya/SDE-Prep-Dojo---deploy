Wrap-up: monitoring and rollout in 60 seconds

"I'd monitor it" is hand-waving. A concrete wrap-up names what you measure for each box, when a human gets paged, and how new code reaches users without breaking them. Three parts, about 20 seconds each:

  1. Four golden signals per box. From Google's SRE book: latency (how long requests take, at p99, not the average), traffic (requests per second, messages per second), errors (the share of requests that fail) and saturation (how full the box is: CPU, connection pool, disk, consumer lag for a queue). Say them for the 2-3 boxes that matter: "for the redirect service, p99 latency and 5xx rate; for the cache, hit rate and memory; for Kafka, consumer lag".
  2. Alert on the user's pain, tied to an SLO. An SLO is the target you promise yourself, such as "99.9% of redirects under 200 ms". Page a human on symptoms, not on causes: "page if p99 redirect latency is above 200 ms for 5 minutes" or "page if the error budget is burning 10x faster than allowed". CPU at 90% is a dashboard graph, not a 3 a.m. page.
  3. Roll out in steps, roll back automatically. Deploy to a canary (1% of servers or users), compare its error rate and latency with the old version, then go 10%, 50%, 100%. If the canary's errors or latency get worse, or the error budget burns too fast, the pipeline rolls back on its own. Risky behaviour changes sit behind a feature flag so you can turn them off without a deploy. Schema changes go in backward-compatible steps (add the column, deploy code, backfill, then remove the old one).

Say it like this: "For each box I'd track the golden signals: latency at p99, traffic, errors and saturation, with consumer lag for the queues. I'd page on the SLO, for example p99 redirect above 200 ms for 5 minutes, not on CPU. New versions go out as a 1% canary, then 10, 50 and 100%, with an automatic rollback if the error budget starts burning, and risky changes behind a feature flag."

From your world

You already run all three pillars. Metrics are your SNMP counters and streaming telemetry (interface errors, drops, queue depth: that is errors and saturation). Logs are syslog. Traces are a packet capture that follows one packet across every hop, except a distributed trace follows one request across every service, carried by a trace ID in the headers. A canary is the same as upgrading one line card or one router in a pair, watching it, then rolling the rest. Where this breaks: a router's counters come from hardware and are cheap and exact; in software, every metric label you add (such as user ID) multiplies the number of time series, so high-cardinality data belongs in logs and traces, not metrics.

How to draw so it does not look messy

  • Flow goes left to right: client on the left, storage on the right. Async work goes below.
  • At most 6-8 boxes in the main diagram. Zoom into one box on the side for deep dives.
  • Label every arrow with the action ("POST /orders", "OrderPlaced event").
  • Draw stores as cylinders and queues as a long thin box - interviewers read shapes fast.
  • Number the steps of the main flow (1, 2, 3...) and narrate them in order.
