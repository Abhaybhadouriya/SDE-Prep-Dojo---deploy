Storage overhead of Reed-Solomon with 8 data + 4 parity shards?

  1. 3x, the same as three replicas
  2. 1.33x, since only 4 of 12 are parity
  3. 12x, one full copy per shard
  4. 1.5x
(8 + 4) / 8 = 1.5, and any 8 of the 12 shards rebuild the object. 1.33x mixes up parity/total with total/data.

Why does a PUT write the metadata row last?

  1. Metadata writes are slower, so they go off the critical path
  2. A crash then leaves orphan bytes, never a key with no data
  3. It lets the client receive its 200 before the bytes land
  4. Writing metadata first would double the network traffic
The metadata row is the moment the object exists; it must only appear once the bytes are durable. Orphan bytes are cleaned up later by GC.

12 shards are placed 4 per zone across 3 zones. One zone fails. What happens?

  1. Data is lost, since 4 shards of every object are gone
  2. Reads stop until the zone returns; writes still work
  3. Still readable: 8 shards remain, which is enough
  4. Only objects with a full replica elsewhere stay readable
Any 8 of 12 shards reconstruct the object; repair re-creates the missing 4 elsewhere.

The main reason Haystack packs photos into large volume files is...

  1. To skip file-system metadata seeks per photo read
  2. To compress similar photos together in one file
  3. To make nightly backups faster with fewer files
  4. To encrypt many photos under a single volume key
NFS needed about 3 disk ops per photo (directory, inode, data); an in-memory index leaves only the data read.

Which metadata partitioning makes LIST by prefix cheapest?

  1. Hash of (bucket, key), so load spreads evenly
  2. Random placement plus a global secondary index
  3. Hash of the bucket name only, one shard per bucket
  4. Range partitioning ordered by (bucket, key)
A prefix maps to contiguous ranges, so LIST is a range scan; hash partitioning forces scatter-gather. One shard per bucket breaks on huge buckets.

What caused S3's old eventual consistency, according to Werner Vogels?

  1. Reads and writes hitting different metadata caches
  2. Erasure-coded shards arriving at zones at different times
  3. Cross-region replication racing with local reads
  4. Slow disks that acknowledged writes before syncing
The fix was a cache-coherence protocol with an in-memory witness acting as a read barrier.
