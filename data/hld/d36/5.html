Architecture: follow a PUT, then a GET

  1. Authenticate. The client's PUT (or presigned URL) hits a stateless API service, which checks identity and bucket policy.
  2. Place. A placement service picks 12 disks on 12 different nodes, spread across 3 zones (4 each), avoiding hot or nearly full disks.
  3. Encode. The API streams the bytes, cuts them into 8 data shards, computes 4 parity shards (Reed-Solomon), and checksums every shard.
  4. Write shards. Shards are appended to volume files on the 12 disks in parallel. The write needs a quorum of acknowledgements (at least 8, usually more) before moving on.
  5. Commit metadata last. Only after the data is durable does the API write the object row (key, version, size, checksum, placement). That row is the moment the object "exists".
  6. Acknowledge. 200 OK with the ETag. A GET now reverses the path: metadata lookup, then read shards, verify checksums, stream bytes.
  7. Failure. Lose all of zone A (4 shards). 8 shards remain in zones B and C, and any 8 of 12 rebuild the object. A repair process re-creates the 4 lost shards elsewhere.

Why metadata last? If the API crashes after writing shards but before the metadata row, the result is orphan shards (garbage to clean up later) - never a key that points to missing data. Ordering writes this way turns a hard consistency problem into an easy cleanup problem.
