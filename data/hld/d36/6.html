1. Durability: replication vs erasure coding, with numbers

Erasure coding splits data into k data shards plus m parity shards; any k of the k + m rebuild the object (Vogels describes S3 using Reed-Solomon this way, spreading each object over tens of drives). Storage overhead is (k + m) / k.

Durability math (illustrative, assumes independent failures). Say a drive has a 2% annual failure rate and we repair a lost shard within 1 day. The chance a given drive dies in a given day is about 0.02 / 365 = 5.5 x 10-5.

  1. 3 replicas. After one copy dies, we lose data only if both other copies die before repair: about (5.5 x 10-5)2 = 3 x 10-9 per incident.
  2. RS(8,4). After one shard dies, we lose data only if 4 of the other 11 die before repair: about C(11,4) x (5.5 x 10-5)4 = 330 x 9 x 10-18, roughly 3 x 10-15 per incident - about a million times safer, at half the storage.
  3. The real enemy is correlation. A whole rack, a power feed, a bad firmware batch or a buggy deployment kills many drives at once. That is why shards go to different nodes, racks and zones, why S3 spans at least 3 AZs, and why Amazon runs formal "durability reviews" on every change.
  4. Faster repair is the cheapest durability. Halving repair time cuts loss risk by about 4x for 3 replicas ((1/2)^2) and about 16x for RS(8,4) ((1/2)^4), because data is lost only if further failures land inside the repair window. Spreading each disk's shards across many peers means a failed disk is rebuilt by hundreds of disks in parallel.

From your world

This is RAID-6 grown up: RAID-6 is a k + 2 code across disks in one box; an object store does k + m across machines, racks and buildings. Reed-Solomon is the same family of codes used in the FEC of optical transport and in QR codes. And the per-shard checksums are your CRC on every frame - plus a background scrubber that re-reads data and checks CRCs to catch silent bit rot before a second failure makes it fatal (Vogels notes bit errors around 1 in 1015 still happen at this scale).

2. Small objects and the 120-IOPS disk

A hard drive gets bigger every year but still does about 120 random I/Os per second. Vogels points out that at 200 TB per drive that is about one I/O per second per 2 TB stored. So seeks, not bytes, are the scarce resource. Two consequences:

  • Never store one object per file. Facebook found that a NAS/NFS photo store needed about 3 disk operations per photo (directory, inode, data) and sometimes more than 10. Haystack packs millions of photos as "needles" into 100 GB append-only volume files and keeps a tiny in-memory index (key -> volume, offset, size), so a read costs at most one disk operation. Result reported: 28% cheaper per usable TB and 4x more reads per TB than the NAS.
  • Read a small object from one shard. Use a systematic code (data shards hold plain bytes) and pack a small object inside a single data shard of a large stripe. A GET is then one seek; the parity is only read on failure. Large objects are split across all 8 data shards and read in parallel for bandwidth.
  • Heat management. Vogels describes spreading each customer's objects across many drives so that one bursty workload is served by a huge number of spindles (one genomics customer burst across over a million disks), and no single disk becomes a hot spot. Aggregating millions of workloads also smooths the total demand.

3. Multipart upload, versioning and garbage collection

  1. Multipart. Start an upload (get an uploadId), PUT parts 1..10,000 (5 MiB-5 GiB each, last part any size) in parallel and in any order, then Complete with the list of part ETags. Each part is stored like a small object; Complete only writes a metadata row that stitches the parts together. A failed part is simply re-sent. AWS suggests multipart once objects reach about 100 MB.
  2. Abandoned uploads. Parts of uploads never completed still use storage. A lifecycle rule ("abort incomplete multipart uploads after 7 days") lets the GC free them.
  3. Versioning. With versioning on, a PUT adds a new version row; a DELETE adds a delete marker (the newest version says "gone"). Old versions stay readable by version id until a lifecycle rule expires them.
  4. Deletes are lazy. Volumes are append-only, so deleting marks the entry dead (Haystack sets a flag in the needle). A compaction job later copies live entries into a new volume and drops the old one; erasure-coded stripes are rewritten when enough of a stripe is dead.
  5. GC must be paranoid. Only delete a shard when no metadata row (including any version or in-progress multipart) references it, and add a grace period. Deleting live data is the worst bug an object store can have.

4. Strong consistency (and how S3 got it)

Before December 2020, S3 was eventually consistent for some operations: a read right after an overwrite could return the old object. The cause, in Vogels' words, was the metadata cache: a write could go through one cache node and a later read through another. Bypassing the cache would hurt performance, so the team built a cache-coherence protocol:

  • A replication component orders all operations on each object.
  • A lightweight witness service is told about every change and acts as a read barrier: on each read it tells the cache whether its copy is stale. Stale means invalidate and read from the persistence tier.
  • The witness holds minimal in-memory state, no disk, so it is fast and failed witnesses are replaced without state transfer.
  • They verified it with model checking and proofs - reportedly more effort than writing it. The launch was at no extra cost and without trading away performance or availability.

In your own design, the simple version is: the metadata store is the source of truth with per-key linearizable writes (a consensus-replicated shard, see Replication & Consensus), and any cache in front of it must be invalidated or version-checked on every read.

5. LIST, hot prefixes and the 503 Slow Down

LIST returns keys in order, 1,000 at a time, with a continuation token (the last key returned). With range-partitioned metadata, a prefix is usually one or a few contiguous ranges, so LIST is a cheap range scan. The catch is hot prefixes: millions of writes per minute to logs/2026-11-23/ all hit one range. The store splits that range as traffic grows; AWS's guide says the scaling is gradual and clients may see 503 Slow Down until it finishes, and recommends spreading keys across prefixes (for example a short hash at the start of the key). Clients should retry 503s with exponential backoff and jitter.
