The story

Explain like I'm 5

You run a giant coat-check room. People hand you a bag and you give them a ticket with a name on it. You write in a notebook: "ticket photo.jpg is on shelf 7, spot 42". The bags go on shelves; the notebook is a separate, very carefully kept book. Shelves sometimes collapse, so you do something clever: you cut a copy of each bag's contents into 8 pieces, make 4 extra "magic" pieces, and put all 12 on different shelves in different rooms. Any 8 pieces can rebuild the bag. Four shelves can fall down at the same time and nobody loses anything - and you used only one and a half times the shelf space, not three times.

The ticket is the object key (like photos/2026/cat.jpg) inside a bucket (a named top-level container). The bag is the object: bytes plus a little metadata. The notebook is the metadata store. The shelves are data nodes full of hard disks. The 8 + 4 pieces are erasure coding, a way to survive failures with much less extra storage than copying.

Object storage is not a file system. There are no directories to rename, no partial overwrites, no file locks. You can only PUT a whole object, GET it (or a byte range), DELETE it, and LIST keys by prefix. Giving up those file-system features is exactly what lets it scale to exabytes.

Asked as "Design S3" or "Design a blob store" (ByteByteGo Vol 2, AlgoMaster, Educative's blob-store block, Grokking's GFS/HDFS deep dives). At Amazon it is a "design a real Amazon service" favourite. The interviewer is looking for three things: split metadata from data, explain durability with numbers, and handle large uploads.
