CREATE TABLE runs (
  run_id       BIGINT PRIMARY KEY,
  tenant       TEXT NOT NULL,           -- team / namespace
  repo         TEXT NOT NULL,
  commit_sha   CHAR(40) NOT NULL,
  trigger      TEXT NOT NULL,           -- push | pull_request | tag | schedule | manual
  status       TEXT NOT NULL,           -- QUEUED | RUNNING | SUCCEEDED | FAILED | CANCELLED
  queued_at    TIMESTAMPTZ NOT NULL,
  started_at   TIMESTAMPTZ,
  finished_at  TIMESTAMPTZ,
  delivery_id  TEXT NOT NULL,           -- X-GitHub-Delivery / X-Gitlab-Event-UUID, or a generated id for schedule/manual
  attempt      INT  NOT NULL DEFAULT 1, -- re-runs of the same commit get attempt 2, 3, ...
  UNIQUE (delivery_id)                  -- a redelivered webhook cannot create a 2nd run
);
CREATE INDEX runs_repo_sha  ON runs (repo, commit_sha);
CREATE INDEX runs_repo_time ON runs (repo, queued_at DESC);

The UNIQUE (delivery_id) constraint is the idempotency key: Git hosts retry webhooks with the same delivery id, and our Kafka consumer is at-least-once, so the same push can arrive twice. The second insert fails and is ignored. We deliberately do not make (repo, commit_sha, trigger) unique: a manual "re-run failed step" and a nightly schedule on an unchanged main commit are legitimate new runs of the same commit, so they get a new delivery id and the next attempt number.

SQL vs NoSQL: run metadata is modest (50k rows/day ≈ 18M/year), relational and queried in many ways - PostgreSQL is the simple, correct choice. The heavy bytes (logs, images) never touch the database.
