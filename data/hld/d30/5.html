Architecture: follow one commit to production

Click Next or Play. An engineer merges a fix to payments-api.

  1. Webhook. The Git host calls POST /webhooks/git. The webhook service checks the HMAC signature (so nobody can fake a push), writes the event to Kafka ci.events, and returns 200 within milliseconds. If anything downstream is slow, the event waits safely in Kafka.
  2. Schedule. The pipeline controller consumes the event, reads .ci.yaml at that commit, inserts the run (idempotent on repo+sha), and creates Kubernetes objects (a Tekton PipelineRun or Jobs) in the team's namespace, subject to that team's quota and priority.
  3. Build and test. The Kubernetes scheduler places a fresh pod. Rootless BuildKit builds the image using a remote layer cache; tests are split into parallel shards. No Docker socket, no privileged mode. The pod is deleted afterwards.
  4. Publish. The image is pushed by digest, with an SBOM and build provenance attached, and signed (for example keyless signing with Sigstore cosign, using the pod's short-lived OIDC identity).
  5. Promote. The pipeline does not touch production. It commits the new digest to the GitOps repo for staging (and after staging checks pass, for prod) - a reviewed, auditable change.
  6. Sync. Argo CD, running inside each target cluster (or a central instance with per-cluster credentials it holds), notices the repo changed and applies the new desired state. An admission policy in the cluster refuses images without a valid signature.
  7. Canary. Argo Rollouts shifts 5% of traffic to the new version, then queries Prometheus for error rate and latency. Healthy → 25% → 100%.
  8. Auto-rollback. If the analysis fails, the rollout aborts and traffic goes back to the old ReplicaSet within seconds. The platform marks the release failed and notifies the team; the GitOps repo is reverted so Git and the cluster agree.

From your world

Argo CD is a reconciliation loop, just like a routing daemon programming the FIB: it watches the desired state (Git) and the actual state (the cluster API), computes the diff and fixes it - forever, not once. If someone hand-edits a Deployment with kubectl, Argo CD reports drift and, with self-heal on, puts it back - like a config management daemon reverting an unsaved CLI change on a box. Where it breaks: a FIB is rebuilt from a RIB that lives on the same box, and a manual change there can stick until the next update. Here Git is the only truth: a fix made in the cluster without a Git commit (even a good emergency fix) is undone on the next sync, so the revert must go through Git too.

The whiteboard version

Git → webhook → Kafka → pipeline controller → ephemeral build pods (cache) → registry (signed) → GitOps repo → Argo CD → canary + metrics → done or rollback.
