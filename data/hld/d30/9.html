Why is mounting the Docker socket into a CI job dangerous, and what do you use instead?

The Docker socket is the API of a daemon running as root. Anyone who can talk to it can start a privileged container that mounts the host's root filesystem - that is full root on the node, including other jobs' secrets. In CI, which runs untrusted PR code, that is a direct path to compromise. Instead build with a daemonless, rootless builder (BuildKit in rootless mode) inside an unprivileged pod, and push to the registry with a short-lived token.

How to answer

Explain the "socket = root" chain in one sentence, then the replacement, then mention Pod Security Admission to enforce it.

Likely follow-ups
  • What about Docker-in-Docker? (needs privileged mode - same problem)
  • How do you cache layers if the pod is fresh each time? (registry cache export/import)
How does a CI job deploy to the cloud without storing a long-lived access key?

Workload identity federation with OIDC. The CI platform issues the job a signed, short-lived OIDC token whose claims say who it is (repo, branch, workflow, environment). The cloud provider is configured to trust that issuer and to map specific claims (only repo:payments/api on main) to a role. The job exchanges the token for credentials that expire in minutes. Nothing to leak, rotate or forget; and a fork PR does not get a matching claim, so it gets nothing.

How to answer

Contrast with a stored key, walk the token exchange, and stress the claim-based scoping.

Likely follow-ups
  • With GitOps, does CI even need prod credentials? (no - only Git write and registry push)
Push-based deploys from CI vs pull-based GitOps - which and why?

Pull-based GitOps for production. With push, the CI system - which runs untrusted code - holds admin credentials to every cluster, and there is no continuous check that the cluster still matches what was deployed. With pull, an agent inside each cluster applies what is in Git: no inbound credentials, every change is a reviewed commit, drift is detected and repaired, and rollback is a revert. I would keep push only for dev clusters where speed matters more.

How to answer

Use the trade-off sentence: "I pick GitOps because of security and audit; the cost is an extra repo and a little latency; if we need instant deploys for dev I allow push there."

Likely follow-ups
  • How do you promote from staging to prod in GitOps? (PR that copies the digest to the prod overlay, gated by checks)
  • What if someone edits the cluster by hand? (self-heal reverts it)
How does automatic rollback actually decide to roll back?

It needs a metric, a threshold and a comparison window. During the canary step, an analysis job queries the metrics system every minute - for example success rate and p99 latency of the canary pods only. If success rate drops below 99% (or below the stable version by some margin) on more than the allowed number of checks, the rollout aborts: traffic weight goes back to 0%, the canary pods scale down, and the release is marked failed. The thresholds must be per service and the canary needs enough traffic to be statistically meaningful - 5% of a tiny service may be a handful of requests.

How to answer

Make it concrete: metric, query, threshold, interval, action. Then name the pitfall (low traffic, noisy metrics).

Likely follow-ups
  • What about bugs that only show up after an hour? (longer bake times, synthetic tests, business metrics)
  • Canary vs blue-green? (Canary shifts a small share of real traffic to the new version and grows it while metrics stay healthy - cheap, gradual, but both versions run side by side for a while. Blue-green runs a full second copy, tests it, then flips all traffic at once - instant switch and instant rollback, but double capacity during the switch and no gradual real-traffic test. See the table in deep dive 5.)
Main breaks several times a day even though every PR passes CI. Why, and how do you fix it?

Each PR is tested against the main it branched from, not the main it lands on. Two PRs that are fine alone can conflict semantically. Fix: a merge queue that tests each PR on top of current main plus every PR ahead of it, merging only if that exact combination passes; run several speculative combinations in parallel to keep throughput, and evict failing PRs. Add flaky-test quarantine, or the queue will reject good PRs.

How to answer

State the root cause in one line ("tested against a stale base"), then the queue, then how to keep it fast.

Likely follow-ups
  • How do you size the speculation depth? (based on the PR failure rate and build time)
One team's huge test suite fills the cluster every afternoon and everyone else waits. Design the fix.

Multi-tenant scheduling: namespace per team with a ResourceQuota so no team can request more than its share; priority classes so hotfix and release pipelines preempt PR builds; per-tenant queues in the controller so admission is fair (round-robin across teams rather than FIFO globally); and cluster autoscaling with a warm pool for burst. Then help the team: test sharding, affected-only tests and caching usually cut such suites dramatically.

How to answer

Fairness (quota + fair queue), priority, capacity (autoscale), then reduce demand.

Likely follow-ups
  • What is shuffle sharding and why use it for runner pools? (Give each team a random small subset of runner nodes or pools, say 2 of 16. Two teams rarely share the same whole subset, so one team's poisoned or overloaded jobs can hurt only the few teams that overlap with it, not everyone - a smaller blast radius than one shared pool.)
How do you make sure only images built by your pipeline run in production?

Sign at build time and verify at admission time. The pipeline signs the image digest (for example with Sigstore cosign, keyless via the job's OIDC identity) and attaches provenance (which repo, commit and builder produced it, in the spirit of SLSA). In every prod cluster an admission controller policy rejects any pod whose image is not referenced by digest and does not carry a valid signature from the expected identity. Plus: images only from your own registry, and SBOMs so you can find every image containing a vulnerable library within minutes.

How to answer

"Sign, attest, verify at the door." Mention digest pinning - signing a tag is meaningless if the tag moves.

Likely follow-ups
  • What is an SBOM used for during a zero-day? (The SBOM - software bill of materials - lists every package and version inside each image. When a new vulnerability lands, you query all SBOMs for the affected package and get the exact list of images and running services to patch in minutes, instead of scanning everything.)
Why put Kafka between webhooks and the pipeline controller? Isn't it overkill for 1 event per second?

It is not about throughput. It decouples the fast, must-not-fail edge (Git hosts give up after a few retries and have short timeouts) from the slower controller, which may be restarting or deploying. Events are durable and replayable, ordered per repo when keyed by repo, and several consumers - controller, notifier, audit, DORA analytics - read the same events independently. A managed queue (SQS, Pub/Sub) would also work; I would pick whatever the company already runs well.

How to answer

Acknowledge the low volume, then give the real reasons: buffering, durability, fan-out, ordering. Offer a simpler alternative.

Likely follow-ups
  • How do you avoid building the same commit twice? (dedupe on the webhook delivery id; a deliberate re-run creates a new attempt of the same commit)
How do you roll out a change to 50 clusters in 6 regions safely?

In waves with bake time and automatic halts: wave 0 an internal/canary cluster, wave 1 one cluster in one low-traffic region, wave 2 one full region, then the rest in growing batches - never all regions at once. Each wave must pass health checks (rollout analysis, SLO burn rate) for a bake period before the next starts; any failure halts the whole train and reverts the waves already done. In GitOps this is a sequence of commits to per-cluster overlays driven by a release orchestrator (or Argo CD ApplicationSets with progressive sync).

How to answer

Blast radius first: "what is the most damage one bad change can do?" Then waves, bake, halt, revert.

Likely follow-ups
  • An urgent security fix must go everywhere in an hour - how do you shorten the waves safely? (Keep the order of waves but shrink the bake times, run more clusters per wave in parallel, and keep automatic halts on. Prepare a pre-approved "expedite" path in advance, watch the first wave extra closely, and still never push to every region in one step - a broken fix everywhere is worse than the bug.)

Common mistakes

  • Long-lived, shared build VMs ("snowflakes") that nobody can rebuild.
  • Mounting the host Docker socket or running build pods privileged.
  • CI deploying with a cluster-admin kubeconfig instead of GitOps pull.
  • Deploying tags (:latest) instead of digests.
  • "Rolling update" presented as safe rollout with no metrics-based analysis.
  • Forgetting database migrations during canaries (both versions run at once).
  • No fairness - one team's suite starves everyone.

Scenario: Docker Hub rate limits block every deploy

At 11 AM builds and pod starts begin failing with toomanyrequests from Docker Hub. A production incident needs a hotfix deployed now.

Weak answer: "Buy a paid Docker Hub plan and retry."

Strong answer: "Stabilise: the hotfix image is in our own registry, so the deploy itself should not need Docker Hub - if pods still pull public base images at start, that is the bug. Short term, point builds at a pull-through cache mirror and rerun the hotfix pipeline with high priority. Long term: mirror every base image into our registry, reference by digest, and block direct pulls from public registries in prod clusters. Add an alert on registry pull errors."

Likely follow-ups
  • How do you keep mirrored base images patched? (scheduled rebuilds + scanning)

Scenario: the canary looked fine, then checkout broke

A release passed a 10-minute canary at 5% and went to 100%. Thirty minutes later checkout errors spike. The bug only happens for orders with gift cards (1% of orders).

Weak answer: "Make the canary longer."

Strong answer: "First roll back by reverting the GitOps commit - minutes, no debugging needed. Then: 5% traffic x 1% gift-card orders x 10 minutes was too few events to see the failure, so the analysis had no statistical power. Fix with per-endpoint and business metrics (checkout success by payment type), a minimum number of requests before a canary can pass, and synthetic transactions that exercise rare paths during the canary."

Likely follow-ups
  • Feature flags vs canaries - when would a flag have helped here? (A canary tests a new build on a share of traffic; a feature flag turns one feature on for chosen users without redeploying. Had the gift-card change been behind a flag, ops could have switched off just that path in seconds while the rest of the release stayed live, and turned it on gradually per payment type.)
