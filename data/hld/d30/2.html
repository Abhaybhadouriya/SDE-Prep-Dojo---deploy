Back-of-envelope estimation

Interview assumptions, worked on the board. (Refresher: Back-of-Envelope Estimation.)

  1. Builds per day. 5,000 engineers x ~10 pipeline runs/day (pushes to PRs, re-runs, merges) = 50,000 runs/day.
  2. Build-minutes. Average run ~15 minutes of pod time → 50,000 x 15 = 750,000 pod-minutes/day.
  3. Average concurrency. A day has 1,440 minutes → 750,000 / 1,440 ≈ ~520 pods running on average.
  4. Peak concurrency. Work is bunched into office hours across a few time zones; assume peak ≈ 3x average → ~1,500 concurrent build pods.
  5. Compute. If a build pod requests 4 vCPU and 8 GiB, peak = 6,000 vCPU and 12 TiB RAM. On 32-vCPU nodes that is ~190 nodes at peak and ~65 at average - so autoscale node pools; at night you can shrink by two thirds.
  6. Events. 50k runs/day is ~0.6/s on average; with per-step status events (~20 per run) ≈ 12 events/s, maybe 100/s at peak. Tiny for Kafka - the event bus is about decoupling and durability, not throughput.
  7. Logs. ~5 MB of logs per run x 50k = ~250 GB/day; keep 30 days hot = ~7.5 TB in object storage.
  8. Registry. Layers are content-addressed and shared, so a typical build adds only its changed layers, say ~50 MB → 50k x 50 MB = ~2.5 TB/day of new blobs. Without garbage collection that is ~900 TB/year - so PR images expire after ~14 days and only released images are kept long term.
  9. Deploys. 2,000 services x ~3 deploys/day ≈ 6,000 deploys/day, each touching 1-50 clusters.
