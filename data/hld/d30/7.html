Where Kafka, Kubernetes and Docker fit

☸️

Kubernetes is the build farm

Every job is a pod; Tekton turns tasks and pipelines into CRDs (Task, Pipeline, PipelineRun). Quotas, priorities, autoscaling and node pools give multi-tenancy for free.

 🚀

Kubernetes is the target

Deployments/Rollouts, readiness probes and ReplicaSets do the actual rollout; Argo CD reconciles them from Git.

 🐳

Docker images are the artifact

Multi-stage, small, non-root images, referenced by digest, scanned, signed and shipped with an SBOM.

 📨

Kafka is the event spine

Webhooks land in ci.events (keyed by repo so pushes to one repo stay ordered); run status events feed notifications, PR checks and DORA dashboards as separate consumer groups.

 
apiVersion: tekton.dev/v1
kind: Task
metadata:
  name: unit-test
spec:
  params:
    - name: shard
      type: string
  workspaces:
    - name: source
  steps:
    - name: test
      image: python:3.12-slim
      workingDir: $(workspaces.source.path)
      env:
        - name: SHARD                 # pass params via env, never inline in script (injection)
          value: $(params.shard)
      script: |
        pip install --no-cache-dir -r requirements.txt pytest-shard==0.1.2
        pytest -q --shard-id="$SHARD" --num-shards=8

# keyless signing with the job's OIDC identity (Sigstore)
cosign sign --yes registry.example.com/payments/api@sha256:4c1f...e9

# what an admission policy effectively checks before allowing the pod.
# Tekton Chains signs with the builder pod's Kubernetes service-account token, so the
# issuer is the cluster's OIDC issuer URL and the identity is that service account.
cosign verify \
  --certificate-identity 'https://kubernetes.io/namespaces/ci-team-payments/serviceaccounts/builder' \
  --certificate-oidc-issuer https://oidc.ci.example.com \
  registry.example.com/payments/api@sha256:4c1f...e9

# (on GitHub Actions instead, the pair would be:
#   --certificate-identity-regexp '^https://github.com/payments/api/.github/workflows/release.yml@refs/heads/main$'
#   --certificate-oidc-issuer https://token.actions.githubusercontent.com )

The identity and issuer you verify must match exactly what the builder's OIDC token asserted when it was signed - mixing one CI system's issuer with another's identity can never succeed.

From your world

Keying ci.events by repo is the same as keeping one flow on one ECMP path: two pushes to the same repo are handled in order, so an older commit's pipeline never "wins" over a newer one. Different repos spread across partitions and are processed in parallel. Where it breaks: ECMP order is only a nicety for TCP, but here ordering is per repo only within one partition. If you add partitions, a repo's events can move to a new partition while older ones are still queued on the old one, so the controller should also compare commit order (or run numbers) instead of trusting arrival order alone.
