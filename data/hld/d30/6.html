1. Isolation: a pull request is untrusted code

A CI system runs arbitrary code written by anyone who can open a PR. Treat every job as hostile.

  • Ephemeral pods. One fresh pod per job, deleted afterwards (ttlSecondsAfterFinished on Jobs). Nothing survives to the next job - no leftover files, credentials or poisoned caches on disk.
  • Never mount /var/run/docker.sock. Whoever controls the Docker socket controls the host (they can start a privileged container that mounts /). Build images with rootless BuildKit instead. (Kaniko was a popular daemonless option, but Google archived its repository in 2025.)
  • Pod Security Admission restricted on test and job namespaces: no privileged pods, no host paths, non-root. For very untrusted code (public forks), use a sandboxed runtime (gVisor, Kata Containers) or dedicated node pools.
  • Builders are the honest exception. Rootless BuildKit still needs seccompProfile: Unconfined and appArmorProfile: Unconfined (its own Kubernetes example says so), and its setuid newuidmap needs privilege escalation - both restricted and baseline reject that, so admission would block every build pod. So run builders separately: a buildkitd service per team in a ci-builders namespace labelled enforce: privileged, on a dedicated node pool (ideally with a gVisor/Kata RuntimeClass), guarded by a ValidatingAdmissionPolicy or Kyverno rule that allows only the pinned moby/buildkit:vX-rootless image running as UID 1000. The job pod stays restricted and just talks to that service with buildctl --addr over mTLS.
  • NetworkPolicy: build pods can reach the registry, package mirrors and the cache - not the production network or the cloud metadata endpoint.
  • No long-lived secrets. The job gets a short-lived OIDC token for its identity ("repo X, branch main, workflow release") and exchanges it with the cloud for a credential scoped to that one job. PRs from forks get no secrets at all.
  • Namespace per team with ResourceQuota and LimitRange, so one team cannot eat the cluster.
# the Namespace must come first: kubectl apply processes documents in order

metadata:
  name: ci-team-payments

    pod-security.kubernetes.io/enforce: restricted   # test/job pods; builders live elsewhere

2. Speed: caching, sharding and doing less

The fastest build is the one you skip. Three levers:

  • Layer cache. Order the Dockerfile so dependencies install before source is copied (see Images & Layers). Ephemeral pods have empty disks, so export/import the cache to the registry.
  • Remote build/test cache. Tools like Bazel hash every action's inputs; if any machine already ran the same action, reuse its output. Monorepos depend on this.
  • Affected-only + sharding. Build and test only targets whose inputs changed; split a long test suite into N parallel shards by historical duration.
$ buildctl --addr tcp://buildkitd.ci-builders.svc:1234 build \
    --frontend dockerfile.v0 --local context=. --local dockerfile=. \
    --output type=image,name=registry.example.com/payments/api:8f3a2c1,push=true \
    --export-cache type=registry,ref=registry.example.com/payments/api:buildcache,mode=max \
    --import-cache type=registry,ref=registry.example.com/payments/api:buildcache
#5 [deps 2/3] RUN pip install --no-cache-dir -r requirements.txt
#5 CACHED
#7 [app 3/3] COPY . .
#7 DONE 0.3s
#9 exporting to image
#9 pushing layers 1.8s done
#9 DONE 4.2s

The dependency layer is CACHED, so only the source layer is rebuilt and pushed.

Flaky tests are a speed problem too: a test that fails 2% of the time, in a suite of 500 such tests, fails almost every run. Track flakiness per test, auto-retry once, and quarantine repeat offenders (still run, but non-blocking) with an owner ticket.

3. Keeping main green: the merge queue

With hundreds of merges a day, two PRs can each pass alone and break together (one renames a function the other calls). Testing each PR against an old copy of main is not enough. A merge queue tests each PR on top of main plus all PRs ahead of it in the queue and merges only if that combination passes. To keep throughput, it tests several queue positions speculatively in parallel; if PR 2 fails, the builds that included it are discarded and rebuilt without it. Uber described its SubmitQueue for this; GitHub and GitLab offer merge queues built in.

4. GitOps: pull, don't push

The naive CD step is kubectl apply from the CI job using a cluster-admin kubeconfig. That puts the keys to every production cluster inside the most exposed system you have (it runs untrusted code). With GitOps, CI only writes to a Git repo; an agent inside each cluster (Argo CD or Flux) pulls and applies. Benefits: no inbound credentials to prod, a full audit log (every change is a commit), drift detection, and rollback by git revert. Cost: one more repo and the "two sources of truth" moment if someone reverts in the cluster but not in Git - always roll back through Git.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: payments-api-prod-ap-south-1
  namespace: argocd
spec:
  project: payments
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: services/payments-api/overlays/prod-ap-south-1
  destination:
    server: https://kubernetes.default.svc
    namespace: payments
  syncPolicy:
    automated:
      prune: true       # delete resources removed from Git
      selfHeal: true    # undo manual kubectl edits (drift)

5. Progressive delivery and automatic rollback

A plain Kubernetes rolling update replaces pods gradually but does not look at error rates - it only checks readiness probes. Argo Rollouts (or Flagger) adds steps and analysis: shift a percentage of traffic, query metrics, continue or abort.

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payments-api
spec:
  replicas: 20
  selector: { matchLabels: { app: payments-api } }
  template:
    metadata: { labels: { app: payments-api } }
    spec:
      containers:
        - name: api
          image: registry.example.com/payments/api@sha256:4c1f...e9
  strategy:
    canary:
      steps:
        - setWeight: 5
        - analysis: { templates: [ { templateName: success-rate } ] }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
    - name: success-rate
      interval: 1m
      count: 5
      failureLimit: 1
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="payments-api",code!~"5.."}[2m]))
            /
            sum(rate(http_requests_total{app="payments-api"}[2m]))

Database migrations are where canaries break: v41 and v42 run at the same time, so the schema must work for both. Use expand → migrate → contract: add new columns first (both versions are fine), deploy code that uses them, and drop old columns only in a later release.

6. Fair scheduling and autoscaling

  • Queues per tenant + priorities. Release and hotfix pipelines get a higher PriorityClass than PR builds; within a priority, teams share fairly (each team's quota caps its share).
  • Shuffle sharding of runner pools. Assign each team to a random small combination of node pools. A team whose jobs crash nodes only hurts the few pools it shares, and almost no other team shares exactly the same combination (AWS Builders' Library explains the maths).
  • Autoscaling. Runner controllers (for example Actions Runner Controller for GitHub Actions) create runner pods based on queued jobs; the cluster autoscaler adds nodes when pods are Pending. Keep a small warm pool of idle nodes so the first jobs of the morning do not wait for VMs to boot.
