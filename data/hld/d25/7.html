Where Kafka, Kubernetes and Docker fit

ToolWhereDetail
KafkaBetween scheduler and workersDurable buffer for spikes; topics per priority; key = tenant_id so one tenant's runs keep order if needed. Retry topics with increasing delays and a DLQ. Kafka has no built-in "deliver later", so the scheduler holds the delay and Kafka only carries due work. Kafka 4.2+ share groups (Queues for Kafka) let many workers read the same partition with per-record acknowledgement, a natural fit for a work queue. Note: share groups give up per-partition ordering (records are acquired and redelivered individually), so use them for independent jobs and classic consumer groups where one tenant's runs must stay ordered. Share groups are new, so run the latest 4.2.x patch release and read its notes. See consumer groups.
KafkaSlack's real lessonSlack's job queue ran on Redis; when Redis ran out of memory it lost jobs. They put Kafka in front of Redis as a durable write buffer and only committed the Kafka offset after the job was safely in Redis.
KubernetesWorker poolsDeployments per priority, autoscaled by KEDA on consumer lag. terminationGracePeriodSeconds long enough for a job to finish, plus a preStop hook that stops pulling new work.
KubernetesScheduler podsA Deployment of N pods competing for shard leases (the same Lease objects that kube-scheduler and controllers use for leader election in coordination.k8s.io).
KubernetesThe built-in mini schedulerCronJob creates Jobs that run pods. Fine for tens of cluster-internal crons, not for 100 M runs/day: each run is a whole pod, and the CronJob controller is one control loop per cluster.
DockerJob packaging and local testContainer targets: the job is an image, so "run job" means "start a pod from this image". Locally, docker compose with Postgres + one Kafka broker + a worker reproduces the whole flow. See build it locally.

Here is a real Kubernetes CronJob with the settings that matter. It is also a great mini-lesson in scheduler semantics:

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"            # 02:00 every day
  timeZone: "Asia/Kolkata"         # GA since Kubernetes 1.27
  concurrencyPolicy: Forbid        # Allow (default) | Forbid | Replace
  startingDeadlineSeconds: 300     # if we missed the start by > 5 min, skip it
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 4              # default is 6 retries
      activeDeadlineSeconds: 3600  # kill it after 1 hour
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: report
            image: ghcr.io/example/report:1.4.2
            args: ["--date", "yesterday"]
$ kubectl apply -f nightly-report.yaml
cronjob.batch/nightly-report created
$ kubectl get cronjob nightly-report
NAME             SCHEDULE    TIMEZONE       SUSPEND   ACTIVE   LAST SCHEDULE   AGE
nightly-report   0 2 * * *   Asia/Kolkata   False     0        <none>          8s
$ kubectl create job --from=cronjob/nightly-report manual-run-1
job.batch/manual-run-1 created
$ kubectl get jobs
NAME           STATUS     COMPLETIONS   DURATION   AGE
manual-run-1   Complete   1/1           14s        20s

Gotcha from the CronJob docs: if the controller was down and more than 100 schedules were missed (and startingDeadlineSeconds is not set), it does not start the job and logs an error instead. Also, the docs warn that a CronJob may occasionally create two Jobs or none for one schedule, so jobs must be idempotent even here. That is the same lesson as our big design.
