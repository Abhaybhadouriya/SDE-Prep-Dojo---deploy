Deep dives: the hard parts

Stop here for SDE-1. If you can explain the architecture above, the data model and at-least-once + idempotency, you have a solid SDE-1 answer. Deep dives 1-3 are expected at SDE-2. Deep dives 4-5 are "good to know".

1. Finding due jobs fast (must know)

Three ways, from simple to fancy:

ApproachHowGoodBreaks when
DB pollingIndex on (shard, next_run_at), poll every 1-2 sSimple, durable, easy to debug. Dropbox's ATF polls its store about every 2 sPrecision is limited to the poll interval; very high rates hammer the index
Sorted set / delay queueRedis ZADD due_jobs <epoch> job_id; ZRANGEBYSCORE due_jobs 0 nowFast, sub-second precisionRedis replication is async, so a failover can lose entries; keep the DB as the truth
Hierarchical timer wheelIn-memory wheel of buckets (seconds, minutes, hours); load the next minute from DBO(1) insert and fire; millisecond precisionMemory only, so it must be rebuilt from the DB after a restart

Best answer: combine them. The database is the source of truth. Each scheduler leader loads "jobs due in the next 60 s" from its shard into an in-memory timer wheel and fires them on time. If the leader dies, the new leader just reloads the window. Nothing is lost, because the DB still has the rows.

From your world

This is the Linux timer wheel (kernel/time/timer.c) moved into user space. Insert is O(1): hash the deadline to a bucket. Each tick only looks at one bucket. Where this breaks: the kernel never loses its wheel unless the box reboots; ours lives on one pod that Kubernetes may kill at any time, so it is only a cache of the next minute. The database is the RIB, the wheel is the FIB.

2. Never run the same run twice at the same time: leases and fencing tokens (must know)

A worker claims a run and gets a lease that expires in 30 s. (A GC pause = the runtime stops all threads to reclaim memory, sometimes for seconds - like a process frozen by SIGSTOP. The process does not know it was frozen.) It must renew it. If the worker dies, the lease expires and the reaper gives the run to someone else. Simple. But here is the trap interviewers love:

The worker is not dead, only paused. A long garbage-collection pause, a CPU-throttled container, or a network partition can freeze worker A for 40 s. Its lease expires, worker B claims the run, and then A wakes up and keeps writing. Now two workers do the same job. A lease alone does not prevent this, because A does not know its lease expired.

  • Fencing token: a counter that increases with every claim of the run. Every status write says "I am token 33". The store does UPDATE job_runs SET status=... WHERE run_id=? AND fencing_token=33. If B already holds 34, A's update matches zero rows.
  • Pass the token to the target too (for example an X-Fencing-Token header), so the billing service can refuse stale calls. This idea is explained well in Martin Kleppmann's post "How to do distributed locking".
  • Self-fencing: Dropbox's executors kill themselves after three missed heartbeats, and the lease timeout is longer than that window, so a worker that cannot reach the store stops before anyone else is allowed to start.

From your world

Fencing tokens are the STONITH ("shoot the other node in the head") and generation numbers of HA clusters, or a TCP sequence number check: the receiver drops a segment from an old incarnation. In Kafka itself, the same idea is the producer epoch: a new transactional producer bumps the epoch and the broker fences the old "zombie" one. See Kafka replication for leader epochs. Where it breaks: STONITH physically powers the old node off, so it cannot do anything; a fencing token only makes its late writes rejected, and only if the target checks the token. A target that ignores tokens (a plain HTTP endpoint, an email API) still receives the zombie's call, so those jobs need their own idempotency key.

3. At-least-once + idempotent jobs = "effectively once" (must know)

There are three places where a run can be duplicated: the scheduler crashes after publishing but before marking QUEUED; the worker finishes but crashes before committing the Kafka offset; a paused worker's lease expires. And there is one place where a run can be lost: the scheduler commits the job_runs row (PENDING) and crashes before publishing. Committing to the DB and publishing to Kafka are two separate writes (a dual write), so one can succeed without the other.

Close the loss gap. Treat the job_runs row as an outbox: the reaper (or a small relay) re-publishes every run that is still PENDING/QUEUED past scheduled_at + N seconds, and only marks it QUEUED after Kafka acks. A run published twice is harmless because of the natural run id and the claim below; a run never published is a silent miss, which is far worse. A heavier option is a real outbox table relayed by CDC (see CDC Pipeline).

You cannot remove all of the duplicate sources. So:

  1. Natural run id. run_id = job_id + scheduled_at. Two schedulers creating the same occurrence collide on the primary key; only one row exists.
  2. Idempotency key to the target. The worker sends Idempotency-Key: run_id to the billing service. Billing stores processed keys and returns the old result for a repeat. Charging twice becomes impossible.
  3. Commit the offset after the side effect. Process, write status, then commit. The reverse order (commit first) gives at-most-once: a crash loses the run.

If the interviewer says "but I want exactly-once", answer: "Kafka's exactly-once covers read-from-Kafka, process, write-to-Kafka. Our job calls an external HTTP service, which Kafka cannot roll back. So the honest design is at-least-once delivery plus an idempotency key at the target; the effect happens once even if the delivery happens twice." See Kafka delivery semantics.

4. Leader election and sharding the scheduler (should know)

  • One scheduler for everything is a single point of failure and a throughput cap. Split jobs into 64 logical shards by hash(job_id). Many scheduler pods compete for shard leases in etcd; each shard has exactly one owner at a time, and a pod may own several shards.
  • When a pod dies, its etcd leases expire (for example after 10 s) and other pods pick up those shards. Use the lease revision as the fencing token for the scheduler's own DB writes.
  • Even without perfect leader election, the design stays correct: two schedulers on the same shard would both try to insert the same run_id and the primary key stops the duplicate. Leader election is for efficiency; the database constraint is for correctness. Say this sentence in the interview.
  • Rebalancing: more shards than pods (64 vs, say, 8) means you can move shards around without rehashing jobs, the same trick as Kafka partitions and Redis Cluster's 16,384 slots.

5. The thundering herd at :00, priorities and fairness (good to know)

  • Spread the load: for jobs that say "hourly" but do not care about the exact second, add deterministic jitter: run at :00 + hash(job_id) % 300 seconds. Kubernetes does not do this for you; many cloud schedulers offer a "flexible time window" for exactly this reason (AWS EventBridge Scheduler has one).
  • Kafka absorbs the rest: the spike becomes consumer lag, not errors. Workers autoscale on lag with KEDA's Kafka scaler (KEDA = a Kubernetes autoscaler that scales pods on external metrics such as Kafka consumer lag, not just CPU). Start delay grows a little for low-priority jobs, which is acceptable.
  • Priorities: separate topics (jobs.high, jobs.low) with separate worker pools. Never put both in one FIFO, or a batch of 1 M low-priority emails sits in front of a payment retry.
  • Tenant fairness: per-tenant quotas at submit time (token bucket on job creation) and at run time (max concurrent runs per tenant). Dropbox's ATF gives each "lambda" its own queue and worker cluster for the same reason.
  • Retries with back-off and jitter: exponential back-off (10 s, 20 s, 40 s...) with random jitter, so 10,000 jobs that failed because the target was down do not all retry in the same second and knock it down again. Read the AWS Builders' Library article on backoff with jitter.

6. Long jobs, cancellation and dependencies (deep dive)

  • Long jobs (a 2-hour report): keep heartbeating; checkpoint progress in the job's own storage, so a retry resumes instead of restarting.
  • Cancel: set the run's desired state to CANCELLED; the worker sees it in its next heartbeat response and stops. Same pattern as a Kubernetes controller: write the desired state, let the owner react.
  • Concurrency policy per job, copied from Kubernetes CronJob: Allow (overlap ok), Forbid (skip if the last run is still running), Replace (kill the old one).
  • Dependencies / DAGs ("run B after A succeeds"): this becomes a workflow engine. Name the real tools: Apache Airflow (a scheduler + executor + metadata DB, born at Airbnb), Temporal (durable workflows), Netflix's Maestro. Interviewers are happy if you say "out of scope, but I would add a DAG layer on top of this scheduler".
