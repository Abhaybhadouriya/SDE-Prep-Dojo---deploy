Data model

Two tables: the definition (what and when) and the run (one attempt to execute at one scheduled time).

CREATE TABLE jobs (
  job_id        TEXT PRIMARY KEY,
  tenant_id     TEXT NOT NULL,
  schedule      JSONB NOT NULL,          -- cron / once / delay + tz
  target        JSONB NOT NULL,
  retry_policy  JSONB NOT NULL,
  priority      SMALLINT NOT NULL,
  state         TEXT NOT NULL,           -- ACTIVE | PAUSED | DELETED
  next_run_at   TIMESTAMPTZ,             -- the one column the scheduler cares about
  shard_id      SMALLINT NOT NULL,       -- hash(job_id) % 64
  version       BIGINT NOT NULL          -- optimistic locking
);
CREATE INDEX jobs_due ON jobs (shard_id, next_run_at) WHERE state = 'ACTIVE';

CREATE TABLE job_runs (
  run_id           TEXT PRIMARY KEY,     -- = job_id || ':' || scheduled_at  (natural idempotency key)
  job_id           TEXT NOT NULL,
  scheduled_at     TIMESTAMPTZ NOT NULL,
  attempt          INT NOT NULL,
  status           TEXT NOT NULL,        -- PENDING|QUEUED|RUNNING|SUCCEEDED|FAILED|DEAD
  worker_id        TEXT,
  fencing_token    BIGINT,
  lease_expires_at TIMESTAMPTZ,
  started_at TIMESTAMPTZ, finished_at TIMESTAMPTZ, error TEXT
);

SQL or NoSQL?

"I would pick sharded PostgreSQL (or MySQL) because the scheduler needs a range query on next_run_at and atomic state changes on a run; the cost is manual sharding; if writes outgrow it, I would move run history to Cassandra or DynamoDB with a time-bucket partition key."

  • SQL gives us SELECT ... FOR UPDATE SKIP LOCKED, which lets many scheduler threads grab different due rows without blocking each other.
  • In NoSQL (Cassandra / DynamoDB) you cannot range-scan the whole table by time. The trick is a partition key of (time_bucket_minute, shard): "all jobs due in minute 09:00, shard 7" is one partition. The scheduler reads the current minute's partitions. Run history (append-heavy, read by key) is a perfect NoSQL fit.
-- one scheduler thread, shard 7: grab up to 500 due jobs that nobody else holds
BEGIN;
SELECT job_id, schedule, next_run_at
FROM   jobs
WHERE  shard_id = 7 AND state = 'ACTIVE' AND next_run_at <= now()
ORDER  BY next_run_at
LIMIT  500
FOR UPDATE SKIP LOCKED;
-- for each row: INSERT job_runs (... ON CONFLICT (run_id) DO NOTHING),
--               UPDATE jobs SET next_run_at = <next cron time>, version = version + 1
COMMIT;

Careful: the run insert and the next_run_at update must be in one transaction. If you advance next_run_at but crash before creating the run, that occurrence is lost forever. If you create the run but do not advance, the next poll creates it again (the ON CONFLICT DO NOTHING on run_id saves you).
