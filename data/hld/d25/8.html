What if this box fails?

  • Job API down: no new jobs, but existing jobs still run. Stateless pods, so Kubernetes restarts them; run 3+ replicas across zones.
  • A DB shard primary down: that shard's jobs pause until a replica is promoted (seconds). Other 63 shards are fine. When it comes back, the scheduler catches up because due rows are still due (next_run_at <= now()). Decide per job: run late ("catch up") or skip missed runs (startingDeadlineSeconds-style).
  • Scheduler leader dies: its etcd lease expires, another pod takes the shard and reloads the next-minute window. A few seconds of delay, no loss.
  • Kafka broker dies: with RF=3, min.insync.replicas=2, acks=all, a new leader takes over and nothing acknowledged is lost. Publishing retries briefly. See replication.
  • Workers die: leases expire, the reaper re-queues; uncommitted Kafka messages are redelivered.
  • Target service down: retries with back-off and jitter, then DLQ. Add a per-target circuit breaker (stop calling a failing dependency for a while, then test it with a few calls - like route dampening for a flapping route) so 50,000 runs do not hammer a dead service.
  • Clock skew: never compare times from two machines. The DB's now() decides "due" and lease expiry; workers only use durations.
Strengths of this design
  • Correctness comes from DB constraints and fencing, not from perfect leader election
  • Spikes become lag, not outages
  • Every piece scales out independently
Costs
  • Many moving parts (DB, etcd, Kafka, workers)
  • Job owners must write idempotent jobs
  • Sub-second precision needs the in-memory wheel
