Back-of-envelope estimation

Use round numbers. The goal is to discover which part is hard, not to be exact. (Cheat: 1 day = 86,400 s, round it to 100,000; so 1 million per day is about 12 per second.)

  1. Average start rate. 100 M runs/day / 86,400 s = about 1,160 runs/s. Call it 1.2k runs/s.
  2. Peak. Humans love round times. Many cron jobs say 0 * * * * (top of every hour) or 0 0 * * * (midnight). Rule of thumb: assume 10x at the minute and hour boundaries, so about 12k runs/s for a few seconds. This "thundering herd at :00" is the first real problem we found.
  3. Concurrent running jobs (Little's law). Running jobs = arrival rate x time per job. If an average job runs 2 s: 1.2k x 2 = 2,400 jobs running at once on average, and 12k x 2 = 24,000 at the peak (if the peak lasts longer than 2 s).
  4. Workers. If one worker pod runs 20 jobs at once (mostly waiting on I/O): 24,000 / 20 = 1,200 pods at peak, about 120 on average. So we need autoscaling; keeping 1,200 pods all day wastes money.
  5. Job definitions. Say 50 M active job definitions (many are recurring) x 1 KB (schedule, payload pointer, retry policy, owner) = 50 GB. Fits a sharded SQL database or a few Cassandra nodes easily.
  6. Run history. 100 M runs/day x 500 bytes (status, timings, worker, error) = 50 GB/day. Keep 30 days hot = 1.5 TB, times 3 replicas = 4.5 TB. Older history goes to cheap object storage.
  7. Scheduler reads. If the scheduler polls "what is due?" every second per shard, with 64 shards that is only 64 small index queries per second. Polling is cheap if the query hits an index on next_run_at.

What the numbers tell us: storage and average QPS are easy. The hard parts are (1) the spike at round times, (2) finding due jobs fast without scanning everything, and (3) correctness when workers die. Say this conclusion out loud; it tells the interviewer where your deep dives will go.
