Architecture, step by step

Click Next or Play. The whiteboard version is only 6 boxes: API, Jobs DB, Scheduler, Queue, Workers, Run store.

  1. Create. The client calls POST /v1/jobs. The Job API validates the cron expression, checks the idempotency key, computes the first next_run_at, and writes one row to the shard chosen by hash(job_id) % 64.
  2. Find due jobs. Each shard has exactly one active scheduler instance, chosen by holding a lease in etcd (or ZooKeeper / a DB lock row). Every second it runs the SKIP LOCKED query, inserts a job_runs row per due job, and advances next_run_at in the same transaction. It also keeps an in-memory timer wheel for jobs due in the next 60 s, so it fires them on time instead of waiting for the next poll.
  3. Enqueue. At the due time the scheduler publishes {run_id, job_id, attempt} to a Kafka topic per priority (or SQS queue), keyed by tenant_id. Kafka is the shock absorber: if 12k runs become due at 09:00:00, they wait safely in the log instead of crushing the workers.
  4. Execute. Worker pods (a Kubernetes Deployment, autoscaled on consumer lag) read the message, call :claim on the run store, and get a lease (say 30 s) plus a fencing token. Then they run the job: call the HTTP target or start a container.
  5. Heartbeat and finish. While the job runs, the worker renews the lease every 10 s. At the end it writes SUCCEEDED or FAILED, and only then commits the Kafka offset. If the worker crashes before committing, Kafka redelivers the message: at-least-once.
  6. Retry. A failed run goes to a retry topic with a delay (10 s, then 1 min, then 10 min...). After max_attempts it goes to the DLQ and the owner is alerted. Retries do not block the main topic, the pattern Uber described for Kafka reprocessing.
  7. Rescue lost runs. A reaper scans for two kinds of lost run. (1) RUNNING but the lease expired (the worker died without a word): re-queue with attempt + 1. (2) PENDING or QUEUED long past scheduled_at + 60 s: the scheduler committed the row but crashed before (or while) publishing to Kafka, so nothing will ever pick it up - re-publish it. This is the teacher taking back the chore card, and finding the cards that were never handed out.
  8. Watch it. The key metric is start delay = actual start - scheduled time (p50/p95/p99), plus Kafka consumer lag and DLQ size. Start delay is the user-visible promise.

Which process does what (no magic): the Job API writes definitions; the scheduler (one leader per shard) is the only process that turns a definition into a run; workers are the only processes that execute; the reaper is the only process that re-queues a stuck run. Each one has a single job, so each one is easy to reason about when it fails.
