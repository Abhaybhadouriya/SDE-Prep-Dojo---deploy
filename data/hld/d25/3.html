Key APIs

Keep the API small. Every create call takes an idempotency key so a client that retries after a timeout does not create two jobs.

POST   /v1/jobs                       # create a job
  Idempotency-Key: 6f1c...            # client-generated UUID
  { "name": "charge-subscription",
    "schedule": { "type": "cron", "expr": "0 9 1 * *", "tz": "Asia/Kolkata" },
                 # or { "type": "once", "at": "2026-12-01T09:00:00+05:30" }
                 # or { "type": "delay", "seconds": 600 }
    "target":   { "type": "http", "url": "https://billing.internal/charge", "timeout_s": 30 },
    "payload":  { "subscription_id": "sub_123" },
    "retry":    { "max_attempts": 5, "backoff": "exponential", "base_s": 10 },
    "priority": "high", "concurrency": "forbid" }
  -> 201 { "job_id": "job_9f2", "next_run_at": "2026-12-01T03:30:00Z" }

GET    /v1/jobs/{job_id}              # definition + next_run_at
GET    /v1/jobs/{job_id}/runs?limit=20 # run history
POST   /v1/jobs/{job_id}:pause | :resume | :trigger
DELETE /v1/jobs/{job_id}

# internal, used by workers
POST   /v1/runs/{run_id}:claim        -> { lease_expires_at, fencing_token }
POST   /v1/runs/{run_id}:heartbeat    -> extends the lease
POST   /v1/runs/{run_id}:complete     { status: "SUCCEEDED" | "FAILED", error }
  • Store times in UTC, but keep the user's time zone with cron jobs, otherwise "9 a.m. every day" drifts when daylight saving changes.
  • Payloads bigger than a few KB go to object storage; the job keeps a pointer. Keeps the hot table small.
  • The worker gets a fencing token (an increasing number) with each claim. We will see why in the deep dives.
