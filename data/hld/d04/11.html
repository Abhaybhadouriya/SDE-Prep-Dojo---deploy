Remember this

You might confuse this with:

  • client_msg_id vs msg_id: the phone makes client_msg_id before sending, to dedupe retries; the server assigns msg_id after storing, as the message's permanent id.
  • Delivered vs read: two ticks = the receiver's device has it; blue ticks = the person opened the chat. Different receipts, sent at different times.
  • Session registry vs message store: the registry is soft, short-lived state (which gateway, TTL 60 s) and may be lost; the message store is durable truth and must never lose an acked message.

Remember this

  • The biggest number in chat is open connections (and heartbeats), not messages per second.
  • Dumb, stable gateways hold sockets; a stateless chat service holds the logic.
  • Session registry: user:device -> gateway with a TTL; missing means offline -> inbox + push.
  • Ack (1 tick) only after a durable quorum write. Delivered and read are receipts from the other device.
  • At-least-once + client_msg_id dedupe = exactly-once on screen.
  • Order per chat with a server sequence number; never trust phone clocks.
  • Messages in a wide-column store keyed by (chat_id, bucket); media in blob storage + CDN.
  • Groups: store once, fan out pointers asynchronously; huge channels switch to pull.
