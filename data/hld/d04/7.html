Where Kafka, Kubernetes and Docker fit

Kafka

  • Not on the 1:1 hot path in our default design: the sender wants one tick in milliseconds, so the chat service writes to the store and pushes to the gateway directly. Some designs do put Kafka in the middle (write to Kafka, then consumers persist and deliver), which gives a durable buffer and replay at the cost of a few extra milliseconds.
  • Topics: chat-events keyed by chat_id (so one chat's events stay in one partition, in order - see Topics, Partitions, Offsets), offline-push keyed by user_id, receipts, presence (short retention, lossy is fine).
  • Consumers are idempotent: a push worker that crashes and re-reads the same offset must not send two notifications - keep a short-lived "sent" key per (user, msg_id). See Delivery Semantics and Notification System.

Kubernetes

Gateways are the unusual workload: each pod holds hundreds of thousands of long-lived connections, so killing a pod is expensive. Settings that matter:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: chat-gateway
spec:
  replicas: 300
  strategy:
    rollingUpdate: { maxUnavailable: 1, maxSurge: 5 }   # replace very slowly
  selector:
    matchLabels: { app: chat-gateway }
  template:
    metadata:
      labels: { app: chat-gateway }       # the PodDisruptionBudget below selects this label
    spec:
      terminationGracePeriodSeconds: 600   # time to drain sockets politely
      containers:
      - name: gateway
        image: registry.example.com/chat-gateway:2.14.0
        ports: [{ containerPort: 8443 }]
        lifecycle:
          preStop:
            exec: { command: ["/bin/gateway", "drain", "--over=540s"] }  # ask clients to reconnect elsewhere, gradually
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }
        resources:
          requests: { cpu: "4", memory: "16Gi" }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: chat-gateway-pdb }
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: chat-gateway } }
  • Expose gateways with a layer-4 load balancer (Service type: LoadBalancer backed by an NLB), because WebSocket is a long TCP stream; see Services & Networking.
  • Autoscale gateways on open connections per pod (a custom metric), not CPU - an idle socket costs memory, not CPU.
  • Chat service and workers are ordinary stateless Deployments with an HPA. Cassandra and Kafka run as StatefulSets or operators (for example Strimzi for Kafka - see Kafka on K8s), or as managed services.

Docker

Every service ships as a small image (multi-stage build, non-root user, see Writing a Dockerfile). For local development, one docker compose file can run gateway + chat service + Redis + a single-node Cassandra + Kafka so you can test reconnect storms on your laptop (Docker Compose).

From your world

Draining a gateway is like taking a router out of service gracefully: you raise the OSPF cost or set BGP graceful-shutdown so traffic moves away before you reboot, instead of yanking the cable. preStop + a long terminationGracePeriodSeconds is the Kubernetes way to do it. Where it breaks: an OSPF cost-out moves stateless packets instantly; a gateway's WebSockets are stateful, so every client must reconnect and resync, which is why the drain is spread over minutes to avoid a reconnect storm.
