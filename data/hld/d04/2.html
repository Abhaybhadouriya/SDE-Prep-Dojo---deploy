Back-of-envelope estimation

Numbers marked "assumption" are ours, picked to be round and easy. Use the method from Back-of-Envelope Estimation: one day is about 86,400 seconds, round it to 100,000 (105) when you need speed.

  1. Messages per day 500M users x 40 messages = 20 billion messages/day (assumption).
  2. Average write QPS 20B / 86,400 s is about 231,000 messages/s. Quick way: 20B / 105 = 200K/s. Close enough.
  3. Peak QPS Chat is spiky (New Year's Eve, festivals, cricket finals). Use 3x as a planning factor (assumption): ~700K messages/s. Say "for festival spikes I would plan for more and load-test".
  4. Size of one message Text body ~100 bytes, plus ids, timestamps, sender, chat id and encryption overhead: call it 200 bytes stored.
  5. Storage per day 20B x 200 B = 4 TB/day. With 3 replicas: 12 TB/day. If we kept everything for 1 year: 12 TB x 365 = about 4.4 PB. That number tells us: use a horizontally scalable store (Cassandra/ScyllaDB/HBase style), not one SQL box.
  6. The WhatsApp twist WhatsApp historically used store-and-forward: the server keeps a message only until it is delivered, then deletes it, and history lives on the phones (plus user backups). Then server storage is just the undelivered backlog, a tiny fraction of 4 TB. Telegram, Messenger, Slack and Discord keep history on the server. Ask the interviewer which one they want - it changes the storage answer by 1,000x.
  7. Concurrent connections Assume 30% of daily users are online at the busiest moment: 0.3 x 500M = 150M open connections.
  8. Gateway servers WhatsApp reported over 2 million TCP connections on one server in 2012 after heavy FreeBSD and Erlang tuning. A safer planning number (assumption) is 500K per server, leaving headroom for a server to fail: 150M / 500K = 300 gateway servers, plus spares across zones.
  9. Heartbeats (the hidden load) Mobile networks silently drop idle connections, so clients send a tiny ping, say every 30 s (assumption). 150M / 30 = 5M pings/s - more than 7x the peak message rate. They are handled by the gateway in memory and never touch a database.
  10. Bandwidth 700K msg/s x 200 B = 140 MB/s in. Group fan-out multiplies the outgoing side: if the average message reaches 3 devices, ~420 MB/s out. Media is the real bandwidth eater, which is why media goes to blob storage and a CDN, never through the chat servers.

From your world

Holding 500K-2M idle TCP sessions on one box is the C10M problem you may know from network appliances: one thread can not block per socket, so you use epoll (Linux) or kqueue (FreeBSD) and an event loop, keep per-connection state tiny, and raise file-descriptor and socket-buffer limits. The 5M heartbeats/s are your keepalives (think BFD hellos or LACP PDUs) - cheap, handled at the edge, never sent to the control plane. Where it breaks: a network appliance terminates or forwards packets in a fast path, but a chat gateway must also run TLS and an application protocol per socket, so memory per connection (TLS buffers, socket buffers) is usually the limit, not the event loop.
