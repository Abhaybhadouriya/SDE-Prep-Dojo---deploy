Quick quiz

When should the server send the "1 tick" ack to the sender?

  1. As soon as the gateway receives the frame
  2. After the receiver's phone gets it
  3. After the message is durably written to the store
  4. After the receiver reads it
The single tick is a promise that the message will not be lost, so it must come after a durable (quorum) write. Delivered and read come later from the receiver.

Why does the client send a client_msg_id with every message?

  1. To encrypt the message
  2. So retries do not create duplicate messages
  3. To pick the gateway
It is the idempotency key. A retry with the same id is recognised and returns the original ack.

With 150M connections and a 30 s heartbeat, about how many heartbeats per second arrive?

  1. 5 million
  2. 500 thousand
  3. 50 million
150M / 30 = 5M per second. That is more than the message rate, which is why heartbeats are handled in the gateway's memory only.

What is the best way to order messages inside one chat?

  1. The sender phone's timestamp
  2. Alphabetical by sender
  3. A per-chat sequence number assigned by the server
Phone clocks are wrong and differ. A server-assigned sequence per chat gives every member the same order and lets clients spot gaps.

The session registry has no entry for Ben. What does the chat service do?

  1. Rejects the message
  2. Keeps it in Ben's inbox and triggers a push notification
  3. Retries forever until Ben connects
No entry means offline. The message is already durable; Ben drains his inbox on reconnect and gets a push now.

Why is (chat_id, bucket) a better partition key than just chat_id?

  1. It stops very old, busy chats from becoming one giant hot partition
  2. It makes joins faster
  3. It is required for encryption
A time bucket caps the partition size. Discord describes exactly this layout for its message store.

What is the right load balancer type in front of WebSocket gateways, and how should they autoscale?

  1. L7 with 30 s timeouts; scale on CPU
  2. DNS round robin; never scale
  3. L4 (or L7 with long idle timeouts); scale on connections per pod
WebSockets are long TCP streams. Idle connections cost memory, not CPU, so connections per pod is the honest scaling signal.
