Key APIs

A chat app has two kinds of APIs. The real-time channel is one WebSocket per device that carries small JSON (or binary protobuf) "frames" both ways. Normal HTTPS calls handle things that are request/response by nature: logging in, loading old history, getting an upload URL for a photo. See API Design & Communication for polling vs long-polling vs SSE vs WebSocket.

// client -> server: send a message
{ "type": "send", "client_msg_id": "c7f1e2a0-4b1d-4e7c-9a55-1f0d2b6e9c11",
  "chat_id": "dm:alice:ben", "body": "<ciphertext base64>", "sent_at": 1763900000123 }

// server -> sender: stored durably (1 tick)
{ "type": "ack", "client_msg_id": "c7f1e2a0-...", "msg_id": "1859230094471831552", "seq": 4182 }

// server -> receiver: new message
{ "type": "msg", "chat_id": "dm:alice:ben", "msg_id": "1859230094471831552", "seq": 4182,
  "from": "alice", "body": "<ciphertext base64>" }

// receiver -> server: delivered (2 ticks) or read (blue)
{ "type": "receipt", "chat_id": "dm:alice:ben", "up_to_seq": 4182, "status": "delivered" }

// either way, every ~30 s
{ "type": "ping" }
# Load older messages (cursor = the seq you already have; never use page numbers)
GET  /v1/chats/{chat_id}/messages?before_seq=4100&limit=50

# Sync after being offline: everything newer than what this device has
GET  /v1/sync?since_cursor=eyJ1IjoiYmVuIiwicyI6OTkxMn0

# Get a short-lived upload URL for a photo (bytes go straight to blob storage)
POST /v1/media/upload-url     {"mime":"image/jpeg","size":482113}
  -> {"media_id":"m_9f2c", "put_url":"https://blob.example/...signed...", "expires_in":300}

# Create a group
POST /v1/groups               {"name":"Family","members":["ben","chitra"]}
  • msg_id is sent as a string. It is a 64-bit Snowflake id (a unique number built from a timestamp, a machine number and a counter; details in deep dive 3). Snowflake ids exceed JavaScript's 253 safe-integer limit, so a web or React Native client would silently round a bare JSON number and break dedupe. Twitter added id_str to its API for exactly this reason.
  • client_msg_id is a UUID the phone creates before the first try. If the network drops and the phone resends, the server sees the same id and does not store a second copy. That is the idempotency key of chat.
  • seq is a per-chat sequence number from the server. It defines the order everyone sees.
  • Receipts carry up_to_seq, not one receipt per message: "I have everything up to 4182" acknowledges a whole batch, like a cumulative TCP ACK.
  • The user id comes from the auth token on the connection, never from the message body (so nobody can send as someone else).
