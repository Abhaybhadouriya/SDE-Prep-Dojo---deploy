The 60-second answer (say it out loud)

"Each device keeps one WebSocket to a dumb gateway behind an L4 load balancer. A stateless chat service stores the message with a quorum write in a wide-column store keyed by chat and time bucket, then acks the sender (one tick). It looks up the receiver's gateway in a Redis session registry and pushes; offline users get an inbox entry plus an APNs/FCM push. A client_msg_id dedupes retries and a per-chat seq gives order. Groups fan out through Kafka. The hard numbers are 150M open connections and 5M heartbeats a second, so gateways stay simple and drain slowly on deploy."

Common mistakes: using HTTP polling every second (battery and server cost); sorting by the phone's clock; acking before the write is durable; one database row per message per member for big groups; forgetting the offline path; sending media through the chat servers; ignoring reconnect storms; spending 15 minutes on encryption maths instead of the system.

Why WebSocket instead of normal HTTP requests for chat?

Chat needs the server to send data whenever a message arrives. With plain HTTP the client must ask repeatedly (polling), which wastes battery, bandwidth and server capacity, and adds up to one polling interval of delay. Long polling helps but still re-opens a request after every message. A WebSocket upgrades one HTTP connection into a two-way TCP stream that stays open, with a few bytes of framing per message. SSE (server-sent events) is one-way, which is fine for feeds but chat also sends upstream.

How to answer

Name the need (server push), compare 3 options in one line each, pick WebSocket, and mention long polling as a fallback for networks that block it.

Likely follow-ups
  • What load balancer do you put in front of WebSockets? (L4, or L7 with upgrade support and long idle timeouts.)
  • How do you detect a dead connection? (Heartbeats.)
How does the server know which machine Ben is connected to?

On connect, Ben's gateway writes ben:device1 -> gw17 into a session registry (Redis) with a TTL around 60 s, refreshed by heartbeats. The chat service looks it up and sends the message to gw17 over an internal RPC. If there is no entry, Ben is offline: the message stays in his inbox and we send a push. Alternatives are consistent hashing of users to gateways (no lookup, but painful rebalancing) or per-user pub/sub topics that gateways subscribe to.

How to answer

Give the registry answer first, then say what happens when the entry is stale (send fails, treat as offline, TTL clears it).

Likely follow-ups
  • What if Redis is down?
  • How does Slack do it? (Channel servers on a consistent hash ring.)
Explain the one tick, two ticks and blue ticks. Who sends what?

One tick: the server acks the sender after the message is durably stored. Two ticks: the receiver's device acks receipt to the server, which forwards a "delivered" receipt to the sender. Blue: the receiver's app sends a "read" receipt when the chat is opened. Receipts are cumulative (up_to_seq), so one receipt covers many messages, and they travel through the same path as messages (and the inbox if the sender is offline).

How to answer

Draw three arrows on a sequence diagram. Stress "ack only after durable".

Likely follow-ups
  • How do ticks work in a group? (Per member; show blue when all members read.)
  • Privacy setting to hide read receipts?
The network drops after the server stored the message but before the ack arrived. What happens?

The app times out and resends with the same client_msg_id. The server checks (chat_id, client_msg_id), sees it already exists, does not create a new row, and returns the original seq as the ack. Delivery to Ben may also happen twice (live push and later sync), so Ben's app ignores a msg_id it already has. Net effect: at-least-once delivery, exactly-once display.

How to answer

Say "at-least-once plus idempotency" in the first sentence, then show both dedupe points.

Likely follow-ups
  • How long do you keep dedupe keys?
  • Is exactly-once delivery possible? (Not over an unreliable network; you fake it with dedupe.)
How do you keep messages in order?

Order only matters within one chat. The server assigns a per-chat sequence number (atomic increment) when it stores a message; clients sort by it and can detect gaps (they have 4180 and 4182, so they fetch 4181). Never trust phone clocks. Keep one chat's events on one ordered path, such as a Kafka partition keyed by chat_id. Snowflake ids are an alternative when a counter per chat is too costly; they are only roughly ordered across servers.

How to answer

"Global order is not needed; per-chat order is." Then sequence numbers, then gap detection.

Likely follow-ups
  • Two people send at the same instant - who is first? (Whoever got the lower seq; both see the same order.)
  • Where does the counter live?
How would you design group chat for 1,000 members, and what changes at 1 million?

For about 1,000 members: store the message once under the group, then fan out asynchronously (Kafka keyed by group) to each member's gateway if online or inbox pointer if offline. At 1 million followers (a broadcast channel), writing a million inbox entries per post is too much; switch to fan-out on read: members fetch the channel's latest messages when they open it, and you push only a lightweight "channel updated" hint to online members who have it open. It is the push-vs-pull trade-off from news feeds.

How to answer

Give the numbers (1 x 1,000 vs 1 x 1,000,000), then the switch point.

Likely follow-ups
  • How do read receipts work for big groups? (Aggregate counts, not per-person ticks.)
  • How does encryption work in groups? (Sender keys.)
How do you build "online" and "last seen" without melting the servers?

Heartbeats refresh a presence key with a TTL in Redis; when the key expires, write "last seen". Do not broadcast changes to every contact. Push presence only to users who are currently viewing that person (subscribe on chat open, unsubscribe on close), debounce offline by a few seconds, and batch updates. Accept that presence is eventually consistent and lossy.

How to answer

Start with "presence is the hidden fan-out problem", give the math (500 contacts x millions of flaps), then the subscribe-on-view fix.

Likely follow-ups
  • How often do heartbeats go? Trade-off of battery vs accuracy.
A user has a phone, a laptop and a tablet. How does sync work?

Treat each device as its own endpoint: the registry key is user:device, each device keeps its own sync cursor, and messages are delivered to every connected device. Messages you send from one device are also delivered to your other devices. Offline devices catch up via /sync?since_cursor=. With end-to-end encryption each device has its own key pair, so senders encrypt for each device, which is one reason the number of linked devices is limited.

How to answer

"Device, not user, is the unit of delivery." Then cursors.

Likely follow-ups
  • How is a read on the laptop reflected on the phone? (Read receipts also sync to your own devices.)
You need to deploy a new gateway version. How do you avoid a reconnect storm?

Roll very slowly (one pod at a time, PodDisruptionBudget), and in preStop ask connected clients to reconnect elsewhere gradually over several minutes instead of closing all sockets at once. Clients use exponential backoff with random jitter. Keep business logic out of gateways so they rarely need deploying. Protect the sync API with rate limits and watch reconnect rate and sync latency during the rollout.

How to answer

Name the failure (thundering herd), then server side (drain), client side (jitter), and protection (rate limit).

Likely follow-ups
  • What metric would page you?

Would you put Kafka between the chat service and delivery? Argue both sides.

For: a durable, replayable buffer; consumers (persist, deliver, push, analytics) scale independently; ordering per chat via the partition key; survives a delivery-tier outage. Against: extra hops add milliseconds to the most latency-sensitive path; partition count limits parallelism; a slow consumer causes head-of-line blocking for every chat on that partition. My pick: write to the store and push directly for 1:1 (fast path), and use Kafka for async work (group fan-out, push, analytics), where delay is acceptable.

How to answer

Use the trade-off sentence pattern, and finish with a hybrid decision.

Asha is in India and Ben is in the US. Where is the message stored and how fast is delivery?

Each user is homed in the region nearest to them; their gateway is local. The chat (or the sender's region) owns the write; the message is stored there and replicated asynchronously to the other region. Delivery crosses regions once via an internal backbone, so expect the cross-region round trip (tens of ms within a continent, about 150-250 ms India to US East) on top of local hops. If a region fails, users reconnect to another region and sync; a few seconds of not-yet-replicated messages may be delayed, which is why the client keeps unsent/unacked messages and retries.

How to answer

Home region + async replication + client retry. Be honest that physics sets the floor.

Likely follow-ups
  • Active-active or active-passive? See Multi-Region & DR.

Scenario: messages show two ticks late for users in one city

Support reports that in one city, messages take 20-30 seconds to show "delivered". Sending still works.

Weak answer: "Add more chat servers."

Strong answer: delivered receipts depend on the receiver's connection. Check gateway metrics for that region: connection count, reconnect rate, heartbeat timeouts. A likely cause is a mobile carrier killing idle connections faster than our heartbeat interval, so devices are "online" in the registry but the socket is dead until the next ping fails. Confirm with per-carrier reconnect graphs; fix by shortening heartbeat interval for that network or using push-to-wake, and make sends to a dead socket fail fast to the offline path.

  • How would you detect this automatically next time?

Scenario: New Year's Eve, midnight

Traffic jumps 5x in one minute in one time zone. Sync latency rises and some sends time out.

Weak answer: "Autoscaling will handle it."

Strong answer: autoscaling reacts in minutes, the spike is in seconds and is predictable. Pre-scale chat service, store and Kafka ahead of time per time zone; degrade non-essential features (typing indicators, presence updates, link previews) behind feature flags; keep group fan-out async so 1:1 sends stay fast; rate-limit sync per device; watch inbox backlog and drain it after the peak.
