Data model: what we store and where

Look at how the data is read. Almost every read is "give me the latest N messages of this chat" or "give me everything for this user since cursor X". There are no joins. Writes are huge (hundreds of thousands per second) and append-only. That pattern points to a wide-column NoSQL store (Cassandra, ScyllaDB, HBase, or DynamoDB) partitioned by chat. Users, groups and settings are small and relational, so they can live in SQL. The "who is connected where" table changes every second and can be rebuilt, so it lives in memory (Redis or the gateways themselves). See Choosing Storage.

-- Cassandra CQL. One partition = one chat + one time bucket (e.g. 10 days),
-- so a very old, busy chat never grows into one giant partition.
CREATE TABLE messages (
  chat_id    text,
  bucket     int,          -- days_since_epoch / 10
  seq        bigint,       -- per-chat order
  msg_id     bigint,       -- Snowflake-style, globally unique, roughly time-sorted
  client_msg_id uuid,      -- for de-duplicating retries
  sender_id  text,
  body       blob,         -- ciphertext
  created_at timestamp,
  PRIMARY KEY ((chat_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);

-- Latest 50 messages of a chat: hits exactly one partition, already sorted.
SELECT seq, sender_id, body FROM messages
 WHERE chat_id = 'dm:alice:ben' AND bucket = 2040 LIMIT 50;

Why the bucket? Discord's engineering blog explains it partitions messages by (channel_id, bucket) where a bucket is a fixed time window, and uses Snowflake ids for messages. Without buckets, one chat that has existed for ten years would be one enormous partition on one set of nodes - a hot spot and a slow compaction.

Why wide-column for messages
  • Writes are sequential appends (LSM tree = log-structured merge tree: writes go to memory and are flushed to sorted files in big sequential chunks, like log-structured flash writes), so hundreds of thousands per second is normal.
  • Adding nodes adds capacity linearly; data spreads by hashing the partition key.
  • "Latest N of chat X" is a single-partition, pre-sorted read.
What you give up
  • No joins and no ad-hoc queries; you design tables per query.
  • Tunable but eventual consistency by default (use QUORUM writes and reads for messages: with 3 replicas, wait for 2 of 3 to answer).
  • Deletes create tombstones (a delete marker written instead of removing data; it is cleaned up later by compaction, the background job that merges sorted files). Many tombstones slow reads if you are careless.

For more depth on LSM trees and compaction see Data Modeling, Indexing & Storage Engines; for picking a wide-column store see Choosing Storage.

From your world

The partition key is a hash key, just like the 5-tuple hash that picks an ECMP next hop: the same chat always lands on the same replica set, so its messages stay together and in order. The clustering key (seq) is the sort order inside that bucket, like entries in a ring buffer ordered by index. Where it breaks: ECMP rehashes flows the moment a next hop dies, but a Cassandra partition key never moves data implicitly; adding or removing nodes streams data between them, which takes time and bandwidth.
