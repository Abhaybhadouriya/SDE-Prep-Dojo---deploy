Requirements

Always start an interview by agreeing what you are building. Say the top three features out loud, then the "-ilities" with numbers. Write "out of scope" items too, so the interviewer can pull one back in if they want.

Functional (what it does)

  • 1:1 chat: send a text message to one person; they get it in real time if online.
  • Offline delivery: if the receiver is offline, store it and deliver when they come back; send a push notification.
  • Receipts: sent (1 tick), delivered (2 ticks), read (blue ticks).
  • Group chat: up to about 1,000 members (WhatsApp's documented cap is 1,024; re-check the help centre).
  • History: scroll up and load older messages; works across your devices.
  • Presence: "online" / "last seen", and "typing...".
  • Media: photos and video as attachments.

Non-functional (how well)

  • Scale (assumption): 500M daily active users, 40 messages sent per user per day.
  • Latency: message on the other phone in under ~500 ms p99 when both are online (Slack reports about 500 ms worldwide delivery for its system).
  • Durability: once the sender sees one tick, the message must never be lost.
  • Ordering: messages in one chat appear in the same order for everyone. Global order across chats does not matter.
  • No duplicates on screen even when the network retries.
  • Availability: 99.99% for sending (about 52 minutes of downtime a year).
  • Privacy: end-to-end encryption; the server sees only ciphertext.

Out of scope unless asked: voice and video calls (a different real-time media problem - see Video Conferencing), stories/status, payments, large broadcast channels, message search on the server (impossible anyway with end-to-end encryption).

Say this early: "Chat is a write-heavy, latency-sensitive, connection-heavy system. The biggest numbers are not messages per second, they are concurrent open connections." It shows you know where the real cost is.
