Deep dives: the hard parts

Stop here for SDE-1? If you can explain the stepper above, the data model and the receipts below, you have a solid SDE-1 answer. SDE-2 candidates are expected to lead at least two of these deep dives without being asked.

1. Routing: how does a message find the right gateway?

There are three common answers, from simple to clever.

OptionHow it worksGoodBad
Session registry (our default)Gateways write user:device -> gateway in Redis with a TTL; senders look it up.Simple; any user can be on any gateway; easy to reason about.One extra lookup per message; the registry must be highly available; stale entries after a crash (TTL fixes it in ~60 s).
Consistent hashing of user to gatewayThe client is told "connect to the gateway that owns hash(user)"; senders compute the same hash.No lookup at all.When a gateway dies, its users must move; clients need a smart connect step; uneven load if hashing is naive.
Pub/sub per user or channelEach gateway subscribes to topics for the users it holds (Redis Pub/Sub, or an internal broker); the chat service publishes to "user:ben".Decouples senders from gateway ids; great for multi-device and channels.Millions of tiny subscriptions; the broker becomes the critical path.

Slack's engineering blog describes a mix: stateful channel servers placed on a consistent hash ring (each owns a set of channels), and gateway servers in many regions that hold the WebSocket subscriptions. A message goes to the channel server that owns the channel, which pushes it to every gateway that has a subscriber. That works well when one message goes to many people (channels). For mostly 1:1 chat, the session registry is simpler. See Team Chat (Slack / Teams) for the channel version.

2. Delivery guarantees, ticks and duplicates

Networks fail in the worst places: the server stored the message but the ack never reached the phone. The phone will retry. If the server blindly stores it again, Ben sees "Hi! Hi!". The fix is at-least-once delivery plus de-duplication on both sides.

  • Server-side dedupe: keep (chat_id, client_msg_id) for a few days (a unique key in the store, or a Redis set with TTL). A repeat returns the original seq.
  • Client-side dedupe: the receiving app ignores a msg_id it already has. The server may push the same message twice (for example, once live and once from /sync after a reconnect).
  • Never ack before durable: the 1-tick ack is a promise. Write with QUORUM (2 of 3 replicas) first.

From your world

This is TCP reliability, one layer up. client_msg_id is a sequence number that lets the receiver drop a retransmitted segment; the cumulative up_to_seq receipt is a cumulative ACK; the offline inbox is the retransmission queue. TCP only protects one connection - when the phone switches from Wi-Fi to 4G, the TCP session dies, so the app must repeat the trick end to end. Where it breaks: TCP state lives in two kernels for one connection; here the "receiver window" is spread across the store, the inbox and several devices, so dedupe keys must be stored durably and shared, not kept in one process.

3. Ordering inside a chat

Phones have wrong clocks, so you can not sort by the sender's timestamp. Two options:

  1. Per-chat sequence number The chat service does an atomic increment on chat_state.next_seq (or Redis INCR seq:{chat_id}) before writing. Everyone sorts by seq. Simple and exact. The cost is one tiny hot counter per chat - fine, because even a busy group sends a few messages per second.
  2. Time-sortable unique ids (Snowflake: 41 bits of milliseconds, 10 bits of machine, 12 bits of sequence; see Unique ID Generator). No coordination, roughly ordered by server time. Two messages sent within the same millisecond on different servers may swap, which is usually acceptable for chat.

Also route all messages of one chat through the same path where possible (for example, Kafka keyed by chat_id), so a later message can not overtake an earlier one in a queue.

4. Group chats: fan-out

  • Store once, deliver many. The message body is written once under the group's chat_id. Each member's inbox gets only a small pointer (chat_id, seq).
  • With a cap around 1,000 members, write-time fan-out is fine: 1 message becomes at most ~1,000 deliveries. Do it asynchronously through Kafka (key = group_id) so the sender's ack is not delayed by 1,000 pushes.
  • For huge channels (100K+ followers), switch to fan-out on read: members pull the channel's latest seq when they open it, like a news feed. That is the same push-vs-pull choice as News Feed and Fan-out (Push vs Pull).
  • With end-to-end encryption, groups use "sender keys": the sender encrypts once with a group key that members already hold, instead of once per member.

5. Presence and "typing..."

Presence is the sneaky expensive feature. If one user with 500 contacts goes online, a naive server tells 500 people. Multiply by millions of users flapping between Wi-Fi and 4G and presence traffic dwarfs messages.

  • Store presence as a key with a TTL, refreshed by heartbeats; "last seen" is the time the key expired.
  • Push presence only to people who are looking: when Ben opens the chat with Asha, his app subscribes to Asha's presence; when he leaves, it unsubscribes.
  • Debounce: wait a few seconds before announcing "offline" so a tunnel does not cause flicker.
  • "Typing..." is fire-and-forget: never stored, dropped if the receiver is offline, rate-limited to one event every few seconds.

6. Multi-device, media and encryption

  • Multi-device: the registry key is user:device, and each device has its own inbox cursor. With end-to-end encryption, each device has its own keys, so the sender's app encrypts once per recipient device (that is why device count is capped).
  • Media: the app asks for a signed upload URL, uploads bytes straight to blob storage (S3-like, see Object Storage), and sends only a small message with media_id and the decryption key. The chat servers never carry megabytes. Receivers download through a CDN.
  • End-to-end encryption (Signal protocol): the server routes and stores ciphertext only. Consequences you should say out loud: no server-side search, no server-side spam scanning of content, and backups must be encrypted by the user.

Gateway restarts are the classic outage. When a gateway with 500K connections restarts, 500K phones reconnect at once - a reconnect storm - and they all call /sync. Defend with: draining gateways slowly during deploys, clients reconnecting with exponential backoff plus random jitter, and the sync API protected by a rate limiter (see Rate Limiter).
