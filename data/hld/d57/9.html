Interview: how to drive 45 minutes

  1. 0-5: scope. Web scale or a site? How many pages, QPS, freshness? Is crawling in scope or given?
  2. 5-10: estimate. Raw size, index size, shard count, fan-out, crawl bandwidth.
  3. 10-20: two halves. Indexing pipeline and serving tree, joined by immutable shards.
  4. 20-35: deep dives. Inverted index layout, doc vs term sharding, ranking phases, tail latency.
  5. 35-45: freshness and ops. Real-time tier, index push safety, caching, failures.

60-second answer, said out loud: "Two halves joined by an immutable index. Offline, crawlers fill a document store; a batch pipeline parses, dedupes to canonical URLs, computes PageRank over the link graph, and builds an inverted index split by document into about 600 shards, each replicated tens of times; a change stream feeds a small real-time tier for fresh news. Online, DNS picks a cluster, the frontend checks a result cache, then a root fans the query through a tree of mixers to one replica of every shard. Each leaf intersects posting lists, scores cheaply with text match plus static rank, and returns its top 20; mixers merge, and the root re-ranks a few hundred candidates with an ML model and fetches snippets from docservers. Tail latency at 600-way fan-out is the hard part: deadlines, hedged requests, good-enough results and a top tier of best pages."

SDE-1 stops here / SDE-2 adds. SDE-1: inverted index and posting lists, document sharding with replicas, scatter-gather with a merge, result cache, PageRank as an offline static score, batch index rebuild and swap. SDE-2 adds: the mixer tree and per-leaf k arithmetic, doc vs term partitioning trade-offs, tail latency maths (63% at 100-way fan-out) with hedged and tied requests, early termination with tiers, index compression, and the incremental / real-time freshness path.

You might confuse this with the web crawler. The crawler only fetches pages and finds links (stage 1); search is indexing and serving on top of it. Also do not confuse document partitioning (every shard has all words for a slice of pages, so every query hits every shard) with term partitioning (each shard has all pages for some words), and do not confuse static rank (per page, offline) with relevance (per query, online).

Common mistakes

Common mistakes: "put pages in Elasticsearch" with no sharding or fan-out reasoning; scanning documents at query time; updating the index in place; ignoring tail latency at fan-out; computing PageRank per query; forgetting dedupe and canonical URLs; no story for freshness.

Design Google Search (given a crawler).

Pipeline: fetched pages land in a wide-column repository; parsers render, extract text and links, dedupe (hash + SimHash) and choose canonical URLs; a batch graph job computes PageRank; an index builder inverts documents into compressed posting lists, partitioned randomly by document into ~600 shards, each replicated. Serving: DNS to the nearest cluster, frontend with result cache, query understanding, a root/mixer tree fanning out to one replica per shard with deadlines; leaves intersect and cheaply score, return top-k; root re-ranks with ML; docservers produce snippets. Freshness via a stream-fed real-time tier. Tail latency via hedging, good-enough results and canaries.

How to answer

Split write side and read side early. Use your shard estimate to motivate the fan-out and tail-latency discussion; that is where Level 5 marks are.

Likely follow-ups
  • How do you push a new index version safely?
  • How would you add personalization?
Shard the inverted index by document or by term? Why?

By document for most systems: each shard has a full index of a random subset of documents, so intersections stay local, reply sizes are small and even, and adding documents means adding shards. The cost is that every query hits every shard, which you pay for with replicas, tiering and caching. By term means fewer shards per query but you ship long posting lists across the network to intersect multi-term queries and get hot shards for common terms.

How to answer

Draw both, then pick with one sentence of reason. Mention Google 2003 and Elasticsearch both use document partitioning.

Likely follow-ups
  • When could term partitioning win? (Very selective single-term lookups, small clusters.)
Each query touches 600 shards. How do you keep p99 latency low?

Fan out through a tree of mixers with per-hop deadlines; hedge a request to a second replica if a shard has not replied by the ~95th-percentile time (Google showed about 5% extra load, and in one benchmark 99.9th-percentile went from 1,800 ms to 74 ms with 2% more requests); put slow replicas on probation; return good-enough results when most shards replied, since a single leaf rarely holds the best answer; reduce fan-out with a top tier and a result cache; use micro-partitions to rebalance quickly.

How to answer

Start with the 63% math so the interviewer sees why it matters, then list techniques by cost.

Likely follow-ups
  • Hedging doubles load in a brownout. How do you cap it? (Budget, lower priority, only after p95.)
Explain PageRank and where it runs.

A random surfer model: a page's rank is (1 - d) plus d times the sum of rank shared by every page that links to it, each sharing its rank equally over its out-links; d is usually 0.85. Iterate until values stop changing. It is query-independent, so it runs offline as a batch graph job over the link graph and is stored as a static score per document used by leaves at query time.

How to answer

Give the formula, the intuition, and the key systems point: offline, not per query.

Likely follow-ups
  • How do link farms game it and how do you defend? (Spam detection, trust propagation, demotion.)
How do you make breaking news searchable within minutes?

Crawl news sources frequently (learned change rate, sitemaps, feeds), push fetched pages into a stream, and build small real-time index segments in minutes. Serve them from a real-time tier that the root queries alongside the main tier and merges, with freshness as a ranking signal. Periodically fold the real-time tier into the main index. Percolator-style incremental processing is Google's published approach; it halved average document age.

How to answer

Name the two-speed architecture (batch + stream), like a Lambda architecture.

Likely follow-ups
  • How do you avoid a stale cached result for a news query? (Short TTL for fresh-intent queries.)
How does a leaf intersect posting lists fast?

Lists are sorted by docID and delta-compressed. Start from the shortest list and, for each candidate, advance the other lists with skip pointers (galloping search) rather than scanning. Score only documents present in all lists (for AND queries), keep a min-heap of the top k. With lists ordered by static rank within tiers, stop early once enough good matches are found.

How to answer

Relate it to merging sorted arrays; mention compression saves RAM and memory bandwidth.

Likely follow-ups
  • How do you support phrase queries? (Positions in postings.)
How do you roll out a new index version without breaking search?

Build shards offline, validate (checksums, document counts, quality metrics on a query sample), then load onto a few replicas per shard, compare results and latency against the old version, and roll out replica by replica while keeping the old files for instant rollback. Serving data is read-only, so a replica is drained, swapped and rejoined, as Google's cluster paper describes.

How to answer

Treat it like a deploy: canary, metrics, rollback.

Likely follow-ups
  • What metrics prove quality did not drop? (Click-through, offline relevance judgments.)
How do you handle duplicate and near-duplicate pages?

Normalise URLs, hash content for exact duplicates, and use SimHash-style fingerprints for near duplicates (pages differing by ads or timestamps). Cluster duplicates and choose one canonical URL using signals like rel=canonical, redirects, HTTPS and link popularity; index only the canonical and keep others as alternates. This saves index space and avoids ten identical results.

How to answer

Exact vs near duplicates, then canonical selection.

Likely follow-ups
  • Where in the pipeline do you dedupe: before fetch (URL) or after (content)? (Both.)
What changes if this is product search for an e-commerce site instead of the web?

Much smaller corpus (millions to a billion items) that fits in an Elasticsearch/OpenSearch cluster; structured filters and facets (price, brand, size) matter as much as text; freshness of price and stock is critical, so indexing is event-driven from the catalog (CDC to Kafka to the indexer); ranking uses sales, conversions and personalization rather than links; no crawler. The serving shape (document shards, replicas, two-phase ranking, caches) is the same.

How to answer

Show which parts transfer and which do not; link to the product search design.

Likely follow-ups
  • How do you keep stock status fresh without re-indexing whole documents?

Scenario: p99 doubled after the index grew 30%

The team added documents to existing shards instead of adding shards. Median latency is fine; p99 doubled.

Weak answer: "Add replicas."

Strong answer: replicas add throughput, not per-query speed. Bigger shards mean longer posting lists and more RAM pressure (more SSD reads), so the slowest shard got slower, and fan-out amplifies the slowest shard. Split shards (more, smaller shards) or move to micro-partitions, check page-cache hit rate, enable hedging after p95, and push the long-tail documents to a lower tier.

Likely follow-ups
  • How do you resplit shards without downtime?

Scenario: one query pattern crashes thousands of leaves

A malformed query with a huge number of terms triggers a bug; every leaf it reaches crashes.

Weak answer: "Restart them automatically."

Strong answer: canary requests: send each new query to one or two leaves first and fan out only if they reply successfully, so a query of death kills at most a couple of servers. Add input validation (term limits) at the frontend, blocklist the query signature quickly, and alert on correlated crashes.

Likely follow-ups
  • What does the canary phase cost in latency? (One extra leaf round trip, small and predictable.)
