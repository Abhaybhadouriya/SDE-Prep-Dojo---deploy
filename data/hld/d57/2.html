Back-of-envelope estimation

Search words you need first.

  • Posting list: the sorted list of docIDs (plus positions) for one word. "red" -> 7, 92, 1004, ...
  • Leaf server: a machine that holds one index shard and answers "best matches in my slice".
  • Root / mixer: the servers that fan a query out to many leaves and merge their answers. The root is the top of the tree; mixers are the middle layers.
  • Docserver: a separate sharded store that returns title, URL and snippet for a docID. Leaves return only ids and scores.
  • Static rank: a quality score per page computed offline, independent of the query (PageRank, spam score).
  • Top tier: a small, extra index of the best-ranked pages; most queries are answered from it without touching the full index.

Assumptions first, then the arithmetic. The method is from Back-of-Envelope Estimation. Every number below is our assumption unless a source is named.

  1. Query rate. Assume 1B users x 5 searches a day = 5B queries/day. 5B / 86,400 s = ~58K queries/s on average. Peak is about 2x the average, so plan for ~100K+ QPS, which is the target in the requirements table.
  2. Raw pages. 10B pages x 100 KB average HTML = 1 PB raw. Compressed and stripped to text: ~10 KB/page = 100 TB of text.
  3. Inverted index. Compressed posting lists with positions are a fraction of the text; assume 30%: ~30 TB. Plus per-document data (URL, title, static rank, snippet source) for docservers: the 100 TB text store.
  4. Shards. Keep each shard's hot index in RAM/SSD at ~50 GB: 30 TB / 50 GB = 600 index shards, each holding a random slice of ~17M documents (document partitioning, deep dive 2).
  5. Query fan-out. Every query goes to all 600 shards (one replica each). 100k QPS x 600 = 60M shard lookups/s.
  6. Mixer tier. No single root can take 600 replies per query. Put one mixer over every ~25 leaves: 600 / 25 = ~24 mixers per query, then one root over the mixers. Each leaf returns its top ~10-20 with scores, so a mixer merges 25 x 20 = 500 candidates down to its best ~20-50, and the root sees about 24 x 20 = a few hundred candidates, not 30,000.
  7. Replicas. Assume one leaf server handles 2,000 lookups/s on its shard: 100k / 2,000 = 50 replicas per shard; with 30% headroom and spread over several datacenters, ~65. Total: 600 x 65 = ~39,000 leaf servers. This is why real engines add a small "top tier" of best pages that answers most queries without touching the full index.
  8. Result cache. Query popularity is heavily skewed. If 30-50% of queries hit a result cache, leaf load drops by that much. Cache entry: query -> top 10 docIDs (~200 B); 100M cached queries = 20 GB per cluster.
  9. Crawl bandwidth. Re-crawl all 10B pages every ~10 days = 1B pages/day = 1B / 86,400 = ~11,600 pages/s x 100 KB = 1.16 GB/s = ~9 Gbps inbound. (Brin and Page's 1998 crawler averaged 48.5 pages/s; scale shows how far this has come.)
  10. Link graph for PageRank. Assume 40 out-links per page: 400B edges x 8 bytes = 3.2 TB per pass, iterated tens of times as an offline batch job.

Say the punchline: "Each query touches hundreds of shards, so the real problem is not storage but fan-out latency and cost: caching, tiering and tail-latency control decide the design." Google's 2003 paper says one query already read hundreds of MB and used tens of billions of CPU cycles.
