Key APIs

# public
GET /search?q=red+panda&start=0&num=10&hl=en&gl=in
  -> {results:[{url, title, snippet, rank_score}], spell_suggestion, next_start}

# internal: root/mixer -> leaf index servers (gRPC)
Search(shard_id, parsed_query{terms, phrases, filters}, k=20, deadline_ms=80)
  -> [{doc_id, score}]                      # top-k per shard
GetDocs(doc_ids[], query_terms) -> [{url, title, snippet}]   # docservers

# indexing side
SubmitUrl(url, priority)                   # crawler frontier
OnPageFetched(url, content_hash, html_ref) # event to the indexing pipeline

Internal calls use gRPC (binary protobuf messages over HTTP/2, with built-in deadlines). The root calls mixers, the mixers call leaves, and once the top 10 are known the frontend calls the docservers for display data.

// GET /search?q=red+panda&start=0&num=10
{
  "query": "red panda",
  "spellSuggestion": null,
  "results": [
    { "docId": 5310, "url": "https://example.org/red-panda",
      "title": "Red panda - facts", "snippet": "The red panda is a small mammal ..." }
  ],
  "nextStart": 10,
  "partial": false,          // true if some shards missed the deadline
  "servedFrom": "top-tier"   // or "full-index", "cache"
}
  • Every internal call carries a deadline; leaves return what they have by then. If a few shards miss it, the root returns "good-enough" results and sets partial, instead of failing the whole query.
  • start paging is offset-based; deep pages beyond ~1,000 results are not served (nobody reads them, and it keeps per-shard k bounded).
  • The leaf API returns only {doc_id, score}. Fetching titles and snippets only for the final 10 keeps 600 leaves from shipping text they would throw away.
  • The indexing side is event-driven: the crawler emits OnPageFetched, and the pipeline decides whether the page changed (by content_hash) before doing any work.
