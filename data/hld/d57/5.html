Architecture

Two halves joined by the index: an offline / near-line indexing pipeline that writes it, and an online serving tree that reads it.

Serving one query, step by step

  1. Pick a cluster. DNS-based load balancing sends the user to a nearby cluster with spare capacity; after that the query is handled entirely inside that cluster (as in Google's 2003 cluster paper).
  2. Frontend and cache. A load balancer picks a web server (GWS). It normalises the query and checks the result cache; popular queries end here in a few ms.
  3. Understand the query. Spell correction, tokenising, synonyms, phrase detection, language and location. Output: a parsed query of terms and filters.
  4. Fan out. The root sends the query down a tree of mixers to one replica of every index shard (600 here). With one mixer per ~25 leaves that is ~24 mixers. A tree, not a flat fan-out, so no single node handles 600 replies.
  5. Leaf work. Each leaf looks up posting lists for the terms, intersects them (shortest list first), computes a cheap score (text match + static rank like PageRank), and returns its top ~10-20 docIDs with scores before the deadline.
  6. Merge. Each mixer merges its ~25 leaves' lists and keeps the best; the root takes the merged top few hundred, runs the expensive ML re-ranker on them, and keeps the top 10.
  7. Docservers. For those 10 docIDs, docservers (also sharded and replicated) return title, URL and a query-specific snippet.
  8. Respond. The frontend adds spelling suggestions (and ads in the real product), renders, caches the result, and replies.

From your world

The mixer tree is a multicast distribution tree in reverse: one packet fans out to hundreds of receivers, and their replies are aggregated hop by hop on the way back, so no single node gets 600 replies at once (the incast problem you know from data-center TCP).
