Data model and storage

StoreKey -> valueTech choice and why
Document repositoryURL (reversed host) -> raw HTML versions, crawl time, headersWide-column store (Bigtable/HBase): huge, sparse, versioned, scanned in batch
Doc tabledocID -> canonical URL, title, language, static rank, content hashSame wide-column store; also exported to docservers
Link graphdocID -> out-links (+ anchor text)Files on a distributed FS for batch graph jobs
Lexiconterm -> termID, document frequency, pointer to posting listIn memory on each leaf
Posting liststermID -> sorted [docID, term freq, positions/hits]Custom immutable compressed files per shard, memory-mapped
Result cachenormalized query -> top resultsIn-memory cache (Redis/memcached-like) with short TTL

Why not SQL? The serving index is read-only, enormous, and needs custom compression and intersection code; a general database adds overhead with no benefit. Google's 2003 paper makes this point: most serving data is read-only, updates are infrequent and done by diverting queries away from a replica, which sidesteps general-purpose database consistency issues. Brin and Page designed their 1998 structures around one rule: avoid disk seeks (about 10 ms each).
