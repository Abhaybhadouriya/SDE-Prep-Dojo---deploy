Kafka, Kubernetes and Docker in this pattern

Kafka: serialise by key instead of locking

A Kafka partition is consumed by exactly one consumer in a group at a time, so keying by the contended id (item+store, account id, show id) turns concurrent updates into an ordered stream handled by one thread. That is Walmart's inventory approach. Two cautions: a rebalance can briefly give the same partition to a new consumer while the old one is still finishing, so writes must still be idempotent or version-checked; and a hot key makes one partition hot (consumer groups, delivery semantics). For a flash sale, Kafka also acts as a buffer: accept "intent to buy" quickly, then process orders at the rate the database can take.

Kubernetes: leases and leader election

Kubernetes itself uses this pattern. Controllers run several replicas, but only the one holding a coordination.k8s.io/v1 Lease object acts; the others wait. The Lease is updated with optimistic concurrency on the object's resourceVersion, which etcd checks atomically (rung 3 again). You can use the same Lease API for your own "only one pod runs this" jobs (architecture, operators).

apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: inventory-reconciler
  namespace: shop
spec:
  holderIdentity: reconciler-7c9f-abcde
  leaseDurationSeconds: 15
  renewTime: "2026-11-23T10:15:30.000000Z"

Docker

Use Docker Compose to reproduce races locally: start Postgres and Redis, then fire 200 concurrent "buy" requests at one SKU with a load tool and check that the final stock is never negative (Compose). Many teams keep such a test in CI.
