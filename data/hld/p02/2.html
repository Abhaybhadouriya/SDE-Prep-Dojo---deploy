The solution ladder: naive to best

Climb only as high as you need. Each rung is more powerful, but also more moving parts.

Rung 1: one atomic conditional write

Put the check inside the write. The database applies it to one row atomically, so only one of the two requests can succeed.

-- returns 1 row updated for the winner, 0 for the loser
UPDATE concerts
SET    available_seats = available_seats - 1
WHERE  concert_id = 'weeknd_tour'
  AND  available_seats > 0;

-- per-seat version: claim a specific seat only if it is still free
UPDATE seats
SET    status = 'BOOKED', booked_by = :user
WHERE  show_id = :show AND seat_id = :seat AND status = 'AVAILABLE';

The application checks the "rows affected" count. Unique constraints are the same idea: a UNIQUE (show_id, seat_id) on a bookings table makes the database reject the second insert. DynamoDB offers the same thing as a ConditionExpression, and Redis as SET key value NX, or DECR whose returned value you check (INCR back and reject if it went below 0), or a Lua check-and-decrement. Note that a bare DECR is atomic but not conditional: it happily goes below zero, which is exactly the oversell in the flash-sale scenario below. This rung solves a surprising number of interview questions on its own. Say it first.

Rung 2: pessimistic locking

"Pessimistic" means you assume a conflict will happen, so you lock first. In PostgreSQL, SELECT ... FOR UPDATE locks the rows it returns. Other transactions that try to update or lock them wait until the first transaction ends. Use it when the logic between read and write is more than one statement (check balance, check limits, write two rows).

BEGIN;
SELECT balance FROM accounts WHERE id IN (:from, :to)
ORDER BY id                      -- always lock in the same order: avoids deadlocks
FOR UPDATE;
-- application checks balance >= amount
UPDATE accounts SET balance = balance - :amt WHERE id = :from;
UPDATE accounts SET balance = balance + :amt WHERE id = :to;
COMMIT;

Where it breaks: (1) deadlocks when two transactions lock rows in opposite orders; PostgreSQL detects them and aborts one, and the docs warn you cannot predict which; (2) long holds: never keep a row lock open while a human types a card number; (3) hot rows: every buyer queues behind one lock. Useful options: NOWAIT (fail at once instead of waiting) and SKIP LOCKED (skip rows someone else holds, which is how job queues let many workers claim different jobs).

Level 3 - Intermediate

Rung 3: optimistic concurrency control (OCC)

"Optimistic" means you assume conflicts are rare, so you do not lock. You read the row and its version, do your work, and write only if the version is unchanged. If someone else got there first, your write affects zero rows and you retry (or tell the user). AWS documents this for DynamoDB: each item carries a version attribute, and an update succeeds only if the server-side version still matches.

-- read
SELECT booked, total, version FROM rooms_inventory WHERE hotel=:h AND day=:d;   -- version = 7
-- write only if nobody changed it
UPDATE rooms_inventory
SET    booked = booked + 1, version = version + 1
WHERE  hotel=:h AND day=:d AND version = 7 AND booked < total;

Great when conflicts are rare (editing a profile, booking a hotel room-night most days). Bad when conflicts are common: under a flash sale, 1,000 requests read version 7, one wins, and 999 retry, then 998 retry again. That is a retry storm, and it costs more than it looks. With N requests racing on one version, round 1 makes N attempts and 1 wins, round 2 makes N - 1 attempts, and so on: N + (N - 1) + ... + 1 = N(N + 1)/2, roughly N2/2 attempts. For N = 1,000 that is about 500,000 database writes to sell 1,000 units, against 1,000 writes for a rung-1 conditional decrement. A version number that only goes up also avoids the ABA problem (a value that changes A to B and back to A looks unchanged if you compare values, but not if you compare versions).

Rung 4: reservations with a TTL (holds)

Checkout takes minutes. Users hate typing a card number only to hear the seat is gone, but you cannot hold a database lock for 5 minutes. So split the flow into reserve and confirm. A seat moves AVAILABLE → HELD (with held_by and hold_expires_at) → BOOKED. The hold itself is taken with a rung-1 conditional write. The Hello Interview Ticketmaster breakdown calls long-running database locks a bad solution, and recommends either this status-plus-expiry design or a Redis lock with a TTL (time to live: an expiry time after which the store deletes the entry by itself).

From your world

A hold with a TTL is an ARP or MAC table entry that ages out. Nobody has to send a "delete": if the owner stops refreshing it, the entry expires on its own and the slot is free again. That is why abandoned checkouts do not lock seats forever.

-- take a 10-minute hold; also steals holds that have already expired
UPDATE seats
SET    status='HELD', held_by=:user, hold_expires_at = now() + interval '10 minutes'
WHERE  show_id=:show AND seat_id=:seat
  AND  (status='AVAILABLE' OR (status='HELD' AND hold_expires_at < now()));

The neat trick is in the last line: "free" means "available, or held but expired". So correctness never depends on a sweeper job running on time. A sweeper can still tidy rows later. The Redis variant is SET hold:{show}:{seat} {user} NX EX 600; for several seats, use a Lua script so the hold is all-or-nothing.

Level 4 - Advanced

Rung 5: distributed locks (and why they need fencing tokens)

Sometimes the thing you protect is not one database row: a file in S3, a call to a payment provider, a job that must run on one machine. Then you need a lock that lives outside the database. Redis documents the single-instance version as SET resource my_random_value NX PX 30000: set only if absent, expire after 30 s, and release only if the stored value is still yours. The multi-node Redlock algorithm takes the lock on a majority of N independent masters (the docs use N=5, so at least 3).

Martin Kleppmann's well-known critique asks the key question: is the lock for efficiency (avoid doing work twice; an occasional failure is fine) or for correctness (two holders would corrupt data)? For correctness, any lease-based lock can fail, because the holder can pause (a GC stop-the-world, a page fault, even a SIGSTOP), the lease expires, someone else takes it, and the first holder wakes up and writes anyway. The fix is a fencing token: the lock service hands out an increasing number with each lease, and the storage rejects writes with a token older than one it has already seen. In his example, client 1 gets token 33, pauses, client 2 gets 34 and writes; client 1's late write with 33 is rejected.

Practical rule for interviews: use Redis locks for efficiency (dedupe a cron run, avoid two workers rebuilding the same cache). For correctness, prefer the database's own atomic operations, or a consensus-backed lock service (ZooKeeper, etcd) plus fencing at the storage layer. The deep version is in Replication, Consensus & Coordination and Distributed Lock Service.

Rung 6: remove the contention: single writer, queues and sharding

The best lock is the one you never take. If all updates for one key go to one thread, there is nothing to race against.

  • Partition by key so one consumer owns it. Walmart's real-time inventory (written up on Confluent's blog) needed to make sure no two consumer threads updated the same item-store at once, so each item-store key always goes to one Kafka partition and therefore one consumer.
  • Single-threaded core. The LMAX exchange, described by Martin Fowler, runs its business logic on a single thread that handles about 6 million orders per second, with no locks at all. Stock matching engines (d26) work this way per symbol.
  • Split the hot row. 10,000 units of stock can be 10 rows of 1,000; a like counter can be 100 sub-counters summed on read (see Distributed Counter and Scaling Writes).

Rung 7: admission control and virtual waiting rooms

When demand is 100x supply, protect the contended path by letting in only what it can handle. Shopify's Part I post describes a leaky-bucket throttle at the Nginx/OpenResty edge that admitted a fixed number of checkouts per 5-second window. Throttled users saw a cached "you are in line" page that polled, and admitted users got a signed cookie to skip the throttle. Polling at random made the queue unfair, so Part II added a first-attempt timestamp in a signed cookie and a stateless "now serving" threshold on each load balancer, tuned with a PID controller. Ticketmaster's Verified Fan adds pre-registration and bot filtering before the queue.

From your world

The "now serving" threshold tuned by a PID controller is the same feedback loop as a fan-speed controller or a rate shaper. The controller measures checkout latency, compares it with a target (say 300 ms), and raises or lowers the admit rate by an amount based on how far off it is now (P), how long it has been off (I) and how fast the error is changing (D). Too slow: admit fewer. Plenty of headroom: admit more.

Worked estimate: how fast should the waiting room admit?

Example numbers (made up for practice, not from a source): 1M users click Buy for 10,000 units. The checkout database handles about 2,000 writes per second, and each checkout costs about 3 writes (take the hold, create the order, record the payment result).

  1. Capacity. 2,000 writes/s / 3 writes per checkout = about 666 checkouts/s.
  2. Headroom. Keep about 10% spare for retries and other traffic, so admit about 600 users/s (3,000 per 5-second window, in Shopify's style).
  3. Drain time. If every admitted user buys one unit, 10,000 units / 600 per second = about 17 seconds to sell out.
  4. The other 990,000. Once stock reaches 0, flip a "sold out" flag that the CDN serves, so the queue stops and those users never touch the database.

Say the chain out loud in the interview: "DB write budget / writes per checkout = admit rate; units / admit rate = sell-out time." Without the waiting room, 1M concurrent requests hit a store that can take 2,000 writes a second.
