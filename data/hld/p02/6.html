In the interview

Phrases that land well

  • "The race is read-check-write. I'll make the check part of the write: UPDATE ... WHERE available > 0 and check rows affected."
  • "Payment takes minutes, so I'll split reserve and confirm, with a hold that expires. Expiry is checked in the write itself."
  • "Is this lock for efficiency or correctness? If correctness, I need fencing tokens or the DB's own atomicity."
  • "For a hot SKU, the bottleneck is one row. I'll put a waiting room in front and split the stock into shards."

Traps

  • Reaching for Redlock first. Interviewers will ask about GC pauses and clock drift.
  • Holding a database transaction open across a payment call or user think-time.
  • Using OCC for a flash sale (999 of 1,000 requests retry).
  • Forgetting idempotency: a retried "confirm" must not book twice. Use an idempotency key: a unique id the client chooses per attempt, which the server stores with the first result so a retry gets that same result back (see idempotency keys).
  • Relying on a cron job to release holds on time; correctness should not depend on it.
Two users click "book" on the last seat at the same time. How do you guarantee only one wins?

Make the check and the write one atomic statement: UPDATE seats SET status='BOOKED', user=? WHERE seat_id=? AND status='AVAILABLE', then check rows affected (1 = won, 0 = lost). Or insert into a bookings table with UNIQUE(show_id, seat_id). Both rely on the database's row-level atomicity, so no extra lock service is needed. If the flow includes payment, use a hold with expiry first (AVAILABLE to HELD to BOOKED).

How to answer

Show the race in one sentence, give the one-line SQL fix, then extend to holds and to scale only if asked.

Likely follow-ups
  • What if the user picks 4 seats? (All-or-nothing: one transaction, or a Lua script in Redis.)
  • What isolation level do you need for this statement?
Optimistic vs pessimistic locking: when would you pick each?

Pessimistic (SELECT ... FOR UPDATE) locks rows up front; others wait. Good when conflicts are frequent and the transaction is short, since waiting is cheaper than redoing work. Optimistic reads a version, writes with WHERE version = ?, and retries on conflict. Good when conflicts are rare and you want no lock waits or deadlocks, including across HTTP requests (store the version in the form). Under heavy conflict OCC causes retry storms, and pessimistic locking causes queues; then change the design (holds, queues, sharding).

How to answer

Define both in one line each, give the "conflict rate" rule, then a concrete example of each.

Likely follow-ups
  • What is the ABA problem and how do versions fix it?
  • How do you avoid deadlocks with pessimistic locks? (Lock in a fixed order; keep transactions short; use timeouts.)
How do you hold a seat for 10 minutes while the user pays, without double booking or leaking seats?

Add status, held_by and hold_expires_at. Take the hold with a conditional update that treats "HELD but expired" as free. On payment success, a conditional update moves HELD to BOOKED only if held_by matches and the hold has not expired (otherwise refund). Abandoned holds expire on their own; a sweeper only tidies. Alternative: Redis SET NX EX 600 per seat, with the database still making the final BOOKED write conditionally. Use the payment's idempotency key so a retried confirm is safe.

How to answer

Draw the three-state machine, then walk the success, timeout and late-payment paths.

Likely follow-ups
  • Payment succeeds one second after the hold expired and someone else holds the seat. What now?
  • How long should the TTL be, and who decides?
Is a Redis lock safe? What can go wrong?

For efficiency, yes. For correctness, not by itself. A holder can pause (GC, page fault, SIGSTOP) past the lease, another client takes the lock, and both act. Failover to a replica that did not get the key also loses the lock, and Redlock depends on bounded clock drift and timing. Kleppmann's fix is a fencing token: an increasing number from the lock service that the storage checks, rejecting older tokens. Redlock does not give one, so for correctness use ZooKeeper or etcd (where a zxid or revision can serve as a token) or rely on the database's own atomic writes.

How to answer

Ask "efficiency or correctness?", then tell the 33/34 story.

Likely follow-ups
  • Why must the lock value be random, and why release with compare-and-delete?
  • What if the storage cannot check tokens (a third-party API)?
Big Billion Days: 1 million users want 10,000 phones in the first minute. Design the stock decrement.

First shrink the crowd: CDN-served page, bot filtering, a virtual waiting room that admits users at the rate checkout can handle (Shopify's edge leaky bucket, admitting a fixed number per 5 s with a signed token). Then make the decrement cheap and atomic: stock in Redis, DECR (or a Lua check-and-decrement), split across 10 shard keys of 1,000 units to avoid one hot key. A winner gets a hold with a TTL and an order event goes to Kafka; order and payment services process at their own pace. Unpaid holds expire and return stock. Reconcile Redis with the database after the sale.

How to answer

Funnel first (protect), then the atomic decrement (correctness), then async processing and stock return (resilience).

Likely follow-ups
  • Redis fails mid-sale. Do you oversell or undersell?
  • How do you make the queue fair? (Shopify Part II: first-attempt timestamp in a signed cookie.)
Inventory updates for the same item come from 10 sources at once. How do you avoid lost updates without locks?

Serialise per key: publish every event to Kafka keyed by item+store so all events for that key land in one partition and one consumer applies them in order. Walmart's inventory system does exactly this to stop two threads updating the same item-store. Make each event idempotent (event id dedupe) and apply deltas (debit/credit) rather than absolute values. Align the database partition key with the Kafka key.

How to answer

Say "single writer per key" and explain why it removes the race instead of guarding it.

Likely follow-ups
  • What happens during a consumer-group rebalance?
  • One item is 100x hotter than others. Now what?
Many workers poll a jobs table. How do you make sure each job is claimed once?

Claim with SELECT ... FROM jobs WHERE status='READY' ORDER BY run_at LIMIT 10 FOR UPDATE SKIP LOCKED, then set status to RUNNING with a lease expiry and worker id in the same transaction. SKIP LOCKED lets each worker grab different rows instead of queueing on the same ones. If a worker dies, the lease expires and another worker reclaims the job, so the job itself must be idempotent.

How to answer

Name SKIP LOCKED, the lease, and idempotency; that covers claim, crash and retry.

Likely follow-ups
  • When would you move from a table to a queue like SQS or Kafka?
  • How do you stop a slow worker and the reclaimer both running the job?
Two users book Airbnb dates that overlap but are not identical. How do you prevent the overlap?

Model inventory per listing per night (one row per date), and book a stay by conditionally updating every night in one transaction, locking rows in date order; if any night is taken, roll back. PostgreSQL can also enforce it declaratively with an exclusion constraint on a date range per listing. Hotels with many identical rooms keep total and booked per room type per night and use WHERE booked < total or OCC.

How to answer

Turn ranges into discrete rows (or a range constraint), then apply rung 1 or 2.

Likely follow-ups
  • How do you show availability quickly in search without hitting these rows?
A celebrity post gets 500,000 likes per minute and the counter row is the bottleneck. Fix it.

Correctness here is easy (increments commute); the problem is throughput on one row. Split into N sub-counters (post:42:shard:0..99), increment a random shard, and sum on read (cache the sum for a second). Or buffer increments in memory or Kafka and apply one batched update per second. Keep per-user "did I like it" rows separately for idempotency.

How to answer

Spot that it is throughput contention, not correctness, and say "shard the hot key, batch the writes".

Likely follow-ups
  • How many shards? Can you add shards dynamically?
Which isolation level stops the double-booking race?

A single UPDATE ... WHERE status='AVAILABLE' is safe even at READ COMMITTED, because the row lock plus re-check on update decides the winner. The race reappears when you read in one statement and write in another: at READ COMMITTED both reads see "available". Fix it with FOR UPDATE, with SERIALIZABLE, or by moving the check into the write. Know how SERIALIZABLE behaves on your database: in PostgreSQL, SERIALIZABLE (SSI, serializable snapshot isolation) aborts one transaction with a serialization failure rather than blocking; MySQL InnoDB's SERIALIZABLE turns plain reads into shared locking reads, so transactions block and can deadlock instead. Either way, the app must retry. Saying that difference is a strong signal.

How to answer

Separate "one statement" from "read then write", then name the fix for each.

Likely follow-ups
  • What is write skew?

Scenario: oversold by 3%

After a flash sale, 10,300 orders exist for 10,000 phones. The code reads stock from Redis, checks it is above zero, then calls DECR.

"Add a Redis lock around the read and the DECR."

The bug is read-check-write across two commands. Use the atomic result instead: call DECR and if the returned value is below zero, INCR back and reject; or one Lua script that checks and decrements. Then make order creation idempotent, reconcile Redis stock with the order DB after the sale, and add a test that fires thousands of concurrent buys at one SKU.

Likely follow-ups
  • What if Redis failed over during the sale and lost recent writes?

Scenario: deadlocks in the wallet service

Transfers A to B and B to A run at the same time and Postgres reports deadlocks several times a minute at peak.

"Retry on deadlock."

Retrying is a band-aid. Lock both accounts in a fixed global order (lower account id first) in every code path, keep the transaction short (no remote calls inside), and set a lock_timeout. For very hot accounts (a merchant receiving millions of payments), stop updating one balance row: append ledger entries and compute or roll up balances asynchronously.

Likely follow-ups
  • How does this change when the two accounts are on different shards? (See sagas.)
