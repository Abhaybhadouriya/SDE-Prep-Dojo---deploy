The story

Explain like I'm 5

There is one cookie left in the jar. Two kids look at the jar at the same moment. Both see one cookie. Both say "it's mine!" and both run to grab it. One gets the cookie, the other gets a broken promise and cries. Grown-ups fix this in a few ways. Only one kid may hold the jar at a time (a lock). Or each kid must say "I saw exactly one cookie" and the grab only works if that is still true (a check-and-set). Or the kid gets a ticket that says "this cookie is saved for you for 5 minutes" (a reservation). And if a hundred kids show up, they stand in a line and go in one by one (a queue).

Contention means many requests competing for the same piece of data at the same time. A race condition is the bug you get when the result depends on who happens to run first. Hello Interview's pattern page opens with exactly this example: the last concert ticket, Alice and Bob both click Buy, both read "1 seat left", both are charged, and the seat count goes to minus one.

  1. Alice's request reads the row: 1 seat available.
  2. Before Alice writes anything, Bob's request reads the same row: still 1.
  3. Alice's check passed, so she writes 0 and her card is charged.
  4. Bob's check also passed (on stale data), so he writes again. Two buyers, one seat.
  5. The root bug: the check and the write were separate steps. Every fix below joins them or orders them.

From your world

This is the classic non-atomic read-modify-write on shared memory. Rung 1 below is atomic_dec_if_positive() or a compare-and-swap. Pessimistic locking is a spinlock or mutex around the critical section. Optimistic versions are a seqlock: readers note a sequence number and retry if it changed. A fencing token is the generation number you put on a lease so a stale owner's writes are dropped, like a stale route with an old sequence number being ignored by a link-state protocol.
