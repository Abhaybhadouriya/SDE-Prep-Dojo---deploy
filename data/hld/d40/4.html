Data model

The key insight: guests do not book a room, they book a room type for a set of nights. The exact room number is given at check-in. So inventory is a counter per (hotel, room type, date). That counter is the "boxes on each page" from the story.

Airbnb variant: single-unit calendars

An Airbnb listing usually has exactly one unit, so the "counter" is just 0 or 1. You can keep a listing_night(listing_id, date, status) table, where status is available, blocked, held or booked. Or you can store reservations as ranges and let the database refuse overlaps. PostgreSQL can do this natively with an exclusion constraint:

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE booking (
  booking_id  uuid PRIMARY KEY,
  listing_id  bigint NOT NULL,
  stay        daterange NOT NULL,        -- [checkin, checkout)
  status      text NOT NULL,
  hold_expires_at timestamptz,
  EXCLUDE USING gist (listing_id WITH =, stay WITH &&)
    WHERE (status IN ('HELD','CONFIRMED'))
);

Two overlapping active bookings for the same listing now fail at commit time, whatever bug the application has. One catch: the constraint's WHERE cannot say "and the hold has not expired", because index predicates must be immutable and now() is not. So an expired HELD row still blocks the dates until something flips it to EXPIRED. Deep dive 2 shows how the booking transaction does that itself, so it never waits for a background job. The half-open range [checkin, checkout) means that a guest leaving on the 27th does not clash with a guest arriving on the 27th.

SQL or NoSQL?

DataStoreWhy
Inventory, holds, reservationsRelational (MySQL / Postgres), sharded by hotel_idMulti-row ACID transactions, constraints, and a low write rate. The rows for a booking all live on one shard.
Hotel and listing content, photos metadataRelational or document store + CDN for imagesRead-heavy and rarely changes, so cache it hard.
Search index (geo, dates, amenities, price)Elasticsearch / OpenSearchGeo and full-text queries. Fed by CDC, and may be seconds stale.
Availability cacheRedis, key hotel:roomType:dateServes the 300 QPS read path. The database stays the source of truth.
Idempotency recordsSame SQL primary, sharded by keyMust be read from the primary, never a lagging replica (Airbnb learned this).

What "fed by CDC" means. CDC (change data capture) tails the database's write-ahead log and publishes each committed row change to Kafka. The outbox pattern is the alternative: the service writes the event into an outbox table in the same DB transaction as the booking, and a small relay publishes it. Either way the database commit and the event can never disagree. It is like a journal replay in a filesystem: the log is the truth, and every copy downstream (search index, Redis) is rebuilt from it in order.
