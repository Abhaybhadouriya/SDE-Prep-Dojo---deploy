Deep dives

1. The last-room race (double booking)

One Deluxe room is left. Alice and Bob both read total_reserved = 99 out of 100. Both add 1. Both write 100. Two people now hold one room. This is the classic lost update, and default isolation levels (READ COMMITTED, and even MySQL REPEATABLE READ) do not stop it if you read first and write later in application code.

There are four standard fixes. ByteByteGo compares the first three. The fourth is the one most production systems end up with.

OptionHowGood whenPain
Pessimistic lockSELECT ... FOR UPDATE on the N night rows, then updateVery hot rows, short transactionsBlocks other bookers. Deadlocks if two stays lock nights in different order (always lock in date order). Do not hold the lock across a payment call.
Optimistic (version)Read the version, then UPDATE ... SET version=v+1 WHERE version=v. Retry if 0 rows change.Low contention. Hotel booking is ~3 TPS.Many retries and a poor experience when everyone wants the same room. Prefer versions to timestamps, because clocks drift.
DB constraintCHECK (total_reserved <= total_inventory) or a Postgres EXCLUDE range constraintAny load. This is a last line of defence.Not every database supports it, and constraints live outside code review.
Conditional atomic updateOne statement: UPDATE ... SET reserved = reserved + :n WHERE ... AND reserved + :n <= cap, then check that the row count = nightsThe default choiceFor multi-night stays you must check that every night succeeded, and roll back otherwise.
 
BEGIN;
-- (expire stale holds for these nights first - see deep dive 2)
UPDATE room_type_inventory
   SET total_reserved = total_reserved + :rooms,
       version        = version + 1
 WHERE hotel_id = :h AND room_type_id = :rt
   AND date >= :checkin AND date < :checkout
   AND total_reserved + :rooms <= FLOOR(total_inventory * 1.10);   -- 10% overbooking
-- application: if affected_rows <> nights(:checkin, :checkout) then ROLLBACK (some night is full)
INSERT INTO reservation (reservation_id, hotel_id, room_type_id, start_date, end_date, room_count, status, hold_expires_at)
VALUES (:rid, :h, :rt, :checkin, :checkout, :rooms, 'HELD', now() + interval '10 minutes');
COMMIT;

From your world

The conditional update is compare-and-swap, the same idea as cmpxchg or atomic_add_unless() in the kernel. You never read the value into a register, decide, and write it back without a lock. The optimistic version column is a seqlock: readers check that the sequence number did not change, and retry if it did.

2. Holds, expiry and the state machine

Between "Reserve" and "paid" the guest needs a few minutes. If we take the room only after payment, two people pay and one gets a refund, which is bad. If we take it at "Reserve" with no timeout, abandoned carts lock rooms forever, which is also bad. The answer is a hold with an expiry. Hello Interview's Ticketmaster breakdown uses 10 minutes.

  • Lazy expiry is the correctness rule. The sweeper is only housekeeping. Hello Interview stresses that correctness must not depend on the sweeper running on time. Lazy expiry has two halves. On the read path, the availability query counts status='HELD' AND hold_expires_at < now() as free, so guests see the room. On the write path, the booking transaction expires those holds inline before it touches the counters (SQL below), so the conditional UPDATE sees the real free count. A cron or delayed-queue job only tidies up nights that nobody is trying to book.
  • Redis lock variant. SET hold:{room}:{date} {user} NX EX 600 gives an atomic, self-expiring hold. But Redis is now a second source of truth. The database must still have a constraint, because Redis can fail over and lose a key.
  • The TTL lapses mid-payment. Extend the hold when payment starts, and make the CONFIRM transition conditional (WHERE status='HELD'). If it loses, refund automatically. This rare case is cheaper than locking rooms for long.

Here is the inline expiry that runs at the top of the booking transaction from deep dive 1. It flips overlapping stale holds to EXPIRED and gives their rooms back to the counters, all inside the same transaction:

BEGIN;
-- 1. expire stale holds that overlap the requested nights
WITH expired AS (
  UPDATE reservation SET status = 'EXPIRED'
   WHERE hotel_id = :h AND room_type_id = :rt
     AND status = 'HELD' AND hold_expires_at < now()
     AND start_date < :checkout AND end_date > :checkin      -- overlaps our dates
  RETURNING start_date, end_date, room_count
)
-- 2. give their rooms back, night by night (sum, because holds can share a night)
UPDATE room_type_inventory i
   SET total_reserved = i.total_reserved - x.rooms
  FROM (SELECT d::date AS night, SUM(e.room_count) AS rooms
          FROM expired e,
               generate_series(e.start_date, e.end_date - 1, interval '1 day') AS d
         GROUP BY d::date) x
 WHERE i.hotel_id = :h AND i.room_type_id = :rt AND i.date = x.night;
-- 3. now the conditional UPDATE + INSERT from deep dive 1
COMMIT;

Because the status flip is conditional (WHERE status='HELD'), only one actor wins it: the booking transaction, the sweeper, or the payment webhook. The counters are decremented exactly once. For the Airbnb EXCLUDE model, the same first step is UPDATE booking SET status='EXPIRED' WHERE listing_id=:l AND status='HELD' AND hold_expires_at < now() AND stay && :stay, run just before the INSERT, so the constraint no longer sees the stale hold.

3. Idempotency: the double-click and the retry storm

Mobile networks drop responses. Users double-tap. Clients retry. The rule: every write carries an idempotency key, and the server stores the outcome under that key. Airbnb's payments team built a library called Orpheus for exactly this. Their write-up gives practical rules:

  1. Split each request into pre-RPC, RPC and post-RPC. The database is written only before and after the external call, and never during it. No network calls run inside a database transaction.
  2. Take a lease on the key. Each request takes a row-level lock on its idempotency key, and the lease expires. Make the lease longer than the RPC timeout, so that a retry cannot run while the first try is still in flight.
  3. Classify errors. Treat 5xx and network errors as retryable, and 4xx validation errors as non-retryable. A wrong label either fails a request forever or causes a double payment.
  4. Read idempotency data from the primary, never a replica. With replica lag, a retry might not see the first success and could charge again. Airbnb shards this table by idempotency key, because the keys are high-cardinality and evenly spread.

Common mistake: "We disable the button in JavaScript." That helps the experience, but a script, a retry or a second tab bypasses it. The server-side key is the real fix.

4. Search vs booking consistency (and the cache)

Search must answer "which of 50,000 Goa listings are free for these 3 nights, under Rs 8,000, with a pool" in about 200 ms. You cannot run that against the sharded inventory database. Instead:

  • Index approximate availability in Elasticsearch, for example a per-listing bitmap of free nights for the next 365 days. Feed it from CDC. Airbnb built SpinalTap for this: it tails MySQL binlogs, keeps per-row ordering, delivers at least once, and feeds search indexing among other uses.
  • Re-check on the detail page against Redis, which is also fed by CDC or written after commit.
  • Make the final decision only in the database transaction. Stale caches cause a "sorry, just booked" message, never a double booking. ByteByteGo calls this acceptable because the database validates.

OTA twist (Agoda, Expedia): an aggregator does not own the inventory. Prices and availability come from supplier APIs, and suppliers enforce per-second request quotas. Agoda's PriceAggregator caches supplier answers per itinerary (hotel, check-in, check-out, adults, children, rooms). It spends its leftover quota pre-fetching the itineraries most likely to be booked before they expire. The cache TTL and the quota become the design.

5. Hot inventory and sharding

  • Shard by hotel_id (or listing_id). All nights of one stay live on one shard, so the booking transaction stays local. There is no 2PC.
  • A hot hotel (New Year's Eve in Goa) is a hot shard. At 3 TPS per chain that is fine. For flash sales, put a virtual waiting room in front, or serialise per room type through a queue partition. See flash sale.
  • Calendar sync (iCal/channel manager). Hosts list the same property on several sites. External calendars are pulled periodically, so there is a window in which a double booking across platforms can happen. Real systems accept it and handle it with policy and support.
  • Reservations and inventory in one service. ByteByteGo deliberately keeps reservations and inventory in the same service and database, so that one ACID transaction covers both. Splitting them into microservices would force a saga with compensations, for little benefit.
