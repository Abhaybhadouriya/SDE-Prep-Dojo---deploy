Where Kafka, Kubernetes and Docker fit

ToolRole in this designDetail
KafkaChange events off the booking pathTopic inventory-changes keyed by hotel_id, so per-hotel order is kept. Consumers: the search indexer, the Redis updater, notifications, pricing. Use the outbox or CDC (Debezium) rather than dual writes (a dual write = the service writes the DB and then Kafka separately, and a crash between them loses one). See Kafka and CDC pipeline.
KafkaHold expiryA delayed "check hold H at T+10 min" message is one option. Airbnb also built Dynein for delayed jobs. Lazy expiry in SQL keeps correctness independent of it.
KubernetesStateless servicesSearch, hotel, rate, reservation and payment run as Deployments with a HorizontalPodAutoscaler on CPU or QPS. Search scales independently of booking. Use a PodDisruptionBudget on the reservation service.
KubernetesSweeperA CronJob every minute releases expired holds. It is idempotent, so overlapping runs are harmless (concurrencyPolicy: Forbid anyway).
DockerPackaging and testsEach service is one image. Integration tests start Postgres and Redis containers and fire 100 parallel "book last room" calls to prove that exactly one wins.
 
apiVersion: batch/v1
kind: CronJob
metadata:
  name: release-expired-holds
spec:
  schedule: "* * * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: sweeper
            image: registry.example.com/reservation-sweeper:1.4.2
            args: ["--batch=500", "--older-than=0s"]
