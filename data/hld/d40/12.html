Quick quiz

A 5,000-hotel chain with 1M rooms, 70% occupancy and 3-night stays makes roughly how many bookings per second?

  1. About 3,000, since every hotel books about once a second
  2. About 300, since bookings track page views one to one
  3. About 3 (240,000 a day over ~10^5 s)
700,000 occupied rooms / 3 nights is about 240,000 bookings a day. Divided by ~10^5 seconds, that is ~3 per second. Page views are about 100x more, which is why the funnel, not the booking rate, sizes the read path.

Why is inventory modelled per room type and date, not per room?

  1. Guests buy a type for nights; the room number comes at check-in
  2. Per-room rows would need one lock per room, which SQL cannot take
  3. Room ids change after renovations, so they make unstable keys
Counting per type per night matches how hotels sell, and a booking becomes N counter updates. SQL locks rows fine, and room ids are stable; neither is the reason.

A 3-night conditional UPDATE changed 2 rows. What should the service do?

  1. Commit the two nights and waitlist the guest for the third
  2. Roll back: one of the nights is full
  3. Re-run the same UPDATE until all three rows change
Every night must succeed. A row count lower than the number of nights means one night failed the capacity condition, so the whole stay is refused. Re-running would only spin, because the full night stays full.

Why must the idempotency check read from the primary database?

  1. Replicas are read-only, so they cannot hold the stored response
  2. Replica lag can hide the first success, so a retry charges again
  3. Reads on the primary are cheaper because it has the warmest cache
Airbnb shows this: a few seconds of lag can turn a safe retry into a duplicate payment. The response is written on the primary anyway; the danger is reading a copy that has not caught up.

The sweeper job has been down for an hour. What stops expired holds from making rooms look sold out?

  1. Nothing: the counters stay high until the sweeper restarts
  2. Redis evicts the hold keys and the DB counters follow them
  3. The booking transaction expires overlapping holds inline
Lazy expiry has two halves. Reads count HELD rows past hold_expires_at as free, and the booking transaction flips them to EXPIRED and decrements the counters before its conditional UPDATE. The sweeper is only cleanup. Redis is a cache and never drives the database.

Search shows a listing as available, but booking fails with "just booked". Is this a bug?

  1. No: search is eventually consistent; the DB transaction decides
  2. Yes: the search index must be updated inside the booking transaction
  3. Yes: the availability cache breaks consistency and must be removed
Search trades freshness for speed and is fed by CDC seconds later. Putting the index inside the booking transaction is a dual write across systems. Correctness lives in the booking path.

Which Postgres feature rejects overlapping stays for the same listing?

  1. A UNIQUE index on (listing_id, checkin) catches every overlap
  2. A foreign key from each booking to a calendar row for its first night
  3. EXCLUDE USING gist (listing_id =, stay &&)
Exclusion constraints reject rows whose ranges overlap. UNIQUE only catches equal check-in dates, so 24-27 and 25-28 would both pass. A foreign key checks existence, not overlap.

At OTA scale, where does "30,000 QPS over 16 shards" come from?

  1. 30,000 bookings per second, which is 1,000x the chain's 30/s peak
  2. 3,000 bookings/s x the 10x funnel, at the booking API
  3. All page views across the site, including search and photos
3 bookings/s x 1,000 = 3,000 bookings/s. One step up the funnel is 10x more traffic, so the booking page and reservation API see ~30,000 QPS. Split over 16 hotel_id shards that is ~1,875 QPS each. Page views are far higher and are served from caches, not the shards.
