Back-of-envelope estimation

We use the numbers from the ByteByteGo chapter: a hotel chain with 5,000 hotels and 1 million rooms, 70% occupancy and an average stay of 3 nights. Then we scale it up to an online travel agency (OTA) such as Booking.com or Expedia.

  1. Reservations per day. 1,000,000 rooms x 0.7 occupied = 700,000 occupied rooms each night. Each stay lasts 3 nights, so about 700,000 / 3 = ~233,000 new reservations a day. Round it to 240,000.
  2. Reservation TPS. A day has 86,400 seconds. Round it to 105 for easy maths. 240,000 / 100,000 = ~3 bookings per second. That is tiny. Even a 10x peak is only ~30 per second.
  3. The funnel (where the load really is). Assume 10% of users move on to each next step. If 3 users per second reserve, then 30 per second open the booking page and 300 per second view hotel or room pages. Search sits above that again.
  4. Inventory rows. 5,000 hotels x 20 room types x 365 days x 2 years = 73 million rows. Assume each row is about 50 bytes (ids, date, two counters, a version). That is about 3.7 GB. One database server holds that easily.
  5. Reservation rows. 240,000 a day x 365 = ~88 million a year. At ~500 bytes each, that is ~44 GB a year. Archive old years to cold storage.
  6. OTA scale. ByteByteGo notes that a site like Booking.com could see about 1,000x more QPS. Work it step by step: 3 bookings/s x 1,000 = 3,000 bookings/s. With the 10x funnel from step 3, the booking page and reservation API together see about 3,000 x 10 = 30,000 QPS, and page views are hundreds of thousands per second above that. Now one database is not enough: shard by hotel_id (sharding = splitting rows across many database servers by a key). 30,000 QPS / 16 shards = ~1,875 QPS per shard, which one MySQL or Postgres primary can handle.

The lesson from the numbers: the write rate is small, so you can use one relational database with ACID transactions for booking. The interview is about correctness under contention, not raw throughput. Say this out loud. It shows that you let numbers drive the design. See estimation basics.
