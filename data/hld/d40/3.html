Key APIs

These are REST-style endpoints. The important detail is the idempotency key on every write that moves inventory or money.

# browse (read path, cache-friendly)
GET  /v1/search?city=goa&checkin=2026-12-24&checkout=2026-12-27&guests=2&cursor=...
GET  /v1/hotels/{hotelId}
GET  /v1/hotels/{hotelId}/availability?roomTypeId=..&checkin=..&checkout=..

# book (write path, strongly consistent)
POST /v1/holds                  # body: hotelId, roomTypeId, checkin, checkout, roomCount
     Idempotency-Key: 7f3c...   # returns holdId + expiresAt (now + 10 min)
POST /v1/reservations           # body: holdId, paymentMethodToken
     Idempotency-Key: 7f3c...   # returns reservationId, status=PENDING_PAYMENT
GET  /v1/reservations/{id}
DELETE /v1/reservations/{id}    # cancel -> releases inventory, triggers refund

# admin (staff / host, internal network)
PUT  /v1/hotels/{hotelId}/rooms/{roomTypeId}/rates/{date}
PUT  /v1/listings/{listingId}/calendar   # block or unblock nights

In the ByteByteGo version, the client gets a reservationID from a unique-ID generator when the order-review page loads. The client then sends it with the POST. It is the reservation table's primary key, so a second submit of the same form hits a unique-constraint error instead of a second booking. This is idempotency for free. See unique ID generator.
