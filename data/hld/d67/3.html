Key APIs

One Amazon interviewer skipped APIs and went straight to architecture (post). Keep this part to two minutes: name the five calls and the idempotency key, then move on.

# 1. Search centres near a point (cached, stale by seconds is fine)
GET  /v1/centres?lat=19.11&lon=72.85&radius_km=10&date=2021-05-08&vaccine=COVISHIELD&age=18
  -> [{centre_id, name, distance_km, fee, slots_summary:{"09:00":3,"09:30":0,...}}]

# 2. Availability for one centre and day (cached in Redis, 1-5 s fresh)
GET  /v1/centres/{centre_id}/slots?date=2021-05-08
  -> [{slot_id, start, end, capacity, available}]

# 3. Hold N places in a slot (strongly consistent; the only hot write)
POST /v1/holds          Idempotency-Key: 7f3c...
  {slot_id, beneficiary_ids:[b1,b2]}
  -> 201 {hold_id, expires_at}     | 409 SLOT_FULL | 429 TOO_MANY_HOLDS

# 4. Confirm (free centre) or start payment (paid centre)
POST /v1/bookings       Idempotency-Key: 7f3c...
  {hold_id}
  -> 201 {booking_id, status:"CONFIRMED"}            (free)
  -> 202 {booking_id, status:"PAYMENT_PENDING", payment_url}   (paid)

# 5. Payment provider calls us (signed, retried, may arrive twice)
POST /v1/payments/webhook   {psp_order_id, status, signature}

# 6. Cancel / reschedule
DELETE /v1/bookings/{booking_id}
POST   /v1/bookings/{booking_id}/reschedule  {new_slot_id}

Why a separate hold call? It splits "I want this" (cheap, fast, may be abandoned) from "I am committed" (payment, notifications, certificate). Holds let a user pay without someone stealing the place mid-payment. For free centres you can merge hold and book into one call: the hold exists for a few milliseconds inside one transaction.
