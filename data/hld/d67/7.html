Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key centre_id keeps every event for a centre's slots in order, so the cache never applies "cancel" before "confirm". Consumer-group sizing: 24 partitions cap each group at 24 pods; the availability updater rarely needs more than a few. The HPA scales the read tier on CPU and request rate, and a KEDA cron trigger pre-scales 15 minutes before a known slot release, because the crowd arrives faster than the HPA reacts.

Kafka

  • Outbox to Kafka: booking.confirmed / cancelled / expired events, published by a relay (or Debezium CDC) from the outbox table, so the DB write and the event never diverge.
  • Partition key = centre_id (or slot_id): all events for a slot stay in order, so the cache updater never applies "cancel" before "confirm".
  • Consumers: SMS/push, reminders, Redis availability updater, CDN JSON builder, analytics, "slots opened near you" alerts.
  • Surge write queue (optional): hold requests for hot ride slots on a partition per slot, processed by one consumer in order.

Kubernetes and Docker

  • Each service (search, availability, booking, payment, sweeper) is a Docker image run as a Deployment; the HPA scales the stateless read tier on CPU and request rate.
  • Pre-scale before a known release (a scheduled scale-up 15 minutes before 4 pm). Autoscaling reacts in minutes; the crowd arrives in seconds.
  • The sweeper and archiver run as a CronJob or a small Deployment with SKIP LOCKED batches, so two pods never double-release.
  • A PodDisruptionBudget keeps enough booking pods alive during node upgrades.
  • Postgres usually runs as a managed service (RDS / Aurora / Cloud SQL) rather than in the cluster.
# Pre-scale the booking tier before a scheduled slot release (KEDA cron scaler)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: booking-svc }
spec:
  scaleTargetRef: { name: booking-svc }
  minReplicaCount: 6
  maxReplicaCount: 80
  triggers:
    - type: cron
      metadata:
        timezone: Asia/Kolkata
        start: "45 15 * * *"      # 15:45, before the 16:00 release
        end:   "30 16 * * *"
        desiredReplicas: "60"
    - type: cpu
      metricType: Utilization
      metadata: { value: "60" }
