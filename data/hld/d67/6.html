Deep dives

1. Never overbook: four ways to protect a counter

The naive code reads the slot, checks booked < capacity in Java, then writes booked + 1. Two requests read 9 of 10 at the same time, both pass the check, both write: 11 of 10. This is the classic read-check-write race. Four fixes, from simplest to most specialised:

ApproachHowGood whenBreaks when
Conditional (atomic) updateUPDATE slot SET held = held + :n WHERE slot_id = :id AND booked + held + :n <= capacity; check row count = 1Default answer. One statement, row lock held for microseconds, no retries in code.Thousands of writers on the same row: they queue on its lock (still correct, but slow).
Optimistic (version)Read version; UPDATE ... SET version = version + 1 WHERE slot_id = ? AND version = :v; retry on 0 rowsLow contention, logic too complex for one WHERE clause.High contention: most attempts fail and retry, wasting work (retry storms).
PessimisticSELECT ... FOR UPDATE, check in code, update, commitMulti-row decisions (a service needs 2 consecutive slots) with a fixed lock order.Long transactions hold locks; risk of deadlock without a lock order; never hold it across a network call (payment!).
Pre-created tokensInsert one row per place (10 rows for 10 places); a hold claims one with FOR UPDATE SKIP LOCKEDTiny capacity, very hot (8 seats per ride): writers grab different rows instead of queueing on one.Large capacities (200 doses = 200 rows per slot); more rows to manage.

Whichever you pick, add the CHECK constraint booked + held <= capacity. It is a seat belt: even a buggy admin tool or a new code path cannot overbook, because the database refuses the write.

Optimistic vs pessimistic, in one breath: "Optimistic wins when conflicts are rare, because nobody waits. Pessimistic wins when conflicts are common and the work is short, because retries cost more than waiting. A slot counter is the special case where a single conditional UPDATE gives you the pessimistic row lock for one statement only, with no retry loop: that is my default."

2. Holds: "many users selected the slot but have not booked yet"

This was the exact follow-up in a June 2025 Amazon SDE2 round that ended in a down-level to SDE1 (post). The problem: if selecting a slot reserves nothing, two people both reach the payment page for the last place and one is charged for nothing. If selecting reserves forever, abandoned carts make a slot look full while it is empty.

  1. Count holds against capacity. The condition is booked + held + n <= capacity, so held places are not offered to anyone else.
  2. Give every hold a deadline. expires_at = now() + 5 minutes (long enough for UPI on a slow phone, short enough that abandoned holds return quickly). Show a countdown timer to the user.
  3. Expire actively. A sweeper runs every few seconds: UPDATE hold SET status='EXPIRED' WHERE status='ACTIVE' AND expires_at < now() RETURNING slot_id, qty, then held -= qty on each slot, in the same transaction. Use FOR UPDATE SKIP LOCKED with a batch limit so several sweeper pods never fight over the same holds.
  4. Limit holds per user. At most one active hold per beneficiary (a partial unique index), and a rate limit per account. Otherwise one script can "pencil in" a whole district.
  5. Optional Redis gate. For very hot slots, keep a Redis counter per slot and run a small Lua script that checks and increments it with a TTL key per hold. Requests that fail in Redis never touch Postgres. Requests that pass still do the database hold, which is the record. If Redis loses data on failover, the worst case is more requests reach the database, which still refuses overbooking.

Redis TTL alone is not enough. Redis key expiry is lazy plus periodic sampling, and keyspace "expired" notifications are fire-and-forget (lost if no subscriber is connected). So you cannot rely on an expiry event to give a place back. Keep the hold row in the database with expires_at, and let the sweeper or the hold query itself treat old holds as free.

3. Surges: the minute slots open

The October 2026 Amazon report lists "queue buffer for surges" and "CDN vs Redis" among the discussion points (post). Three layers keep the database calm:

  • Reads at the edge. Publish district-level availability as a small JSON file on the CDN with a 2-5 second TTL. A million refreshes a second become a few hundred origin requests. Redis serves the per-centre detail behind it. CDN vs Redis: the CDN is for identical responses to many users (district lists); Redis is for keyed lookups the CDN cannot cache well (per user, per centre, with auth).
  • Admission control. A waiting room hands out signed tokens at a fixed rate (say 2,000 per second per shard). Users get a queue position instead of an error. The booking tier only sees traffic it was sized for. This is the "fast, fair no" from the estimation.
  • Queue the writes (option). For the adventure-park case (10K people for 80 seats), put hold requests for each ride slot onto a Kafka partition keyed by slot_id. One consumer per partition processes them in order, in memory, with the counter loaded from the database, and writes results in batches. No lock contention at all, and order of arrival is fair. The cost: the user waits a second or two for "you got it" via push or polling.
  • Stagger releases. A product fix, not a tech fix: release slots district by district at different times, or by lottery for very popular centres. Say it; interviewers like seeing you question the requirement.
  • Captcha and bot defence at the hold step. CoWIN was reported to add a captcha to scheduling in May 2021 after scripts and Telegram alert bots grabbed slots in seconds.

4. Payment, webhooks and the Saga

Payment is a step you do not control: the user may close the app, UPI may take two minutes, the PSP may send the webhook twice or never. Never hold a database lock across it. The booking is a Saga: a chain of local steps, each with a compensation.

StepLocal transactionCompensation if a later step fails
1. Holdheld += n, insert hold (5 min)Release hold: held -= n (or let it expire)
2. Create paymentBooking PAYMENT_PENDING + PSP order with idempotency key = booking_idCancel PSP order
3. Payment succeeded (webhook)Verify signature; hold to CONVERTED, held -= n, booked += n, booking CONFIRMED, outbox rowRefund (if confirm is impossible)
4. Notify / certificate slotKafka consumersRetry; these never undo a booking
  • Duplicate webhooks: the confirm UPDATE names the state it leaves (WHERE status='PAYMENT_PENDING'), and psp_order_id is UNIQUE. A second delivery changes 0 rows and returns 200.
  • Missing webhook: a reconciler polls the PSP for orders PAYMENT_PENDING for more than a few minutes. Webhooks are an optimisation; polling is the safety net.
  • Payment after the hold expired: try to re-take the place with the same conditional update. If the slot is now full, mark REFUNDED and refund automatically with an idempotency key. Never confirm a place you no longer own. A small grace window (hold counts as live until expires_at + 1 minute for a payment already in flight) cuts how often this happens.
  • Why not two-phase commit with the PSP? You cannot make an external bank join your transaction, and 2PC blocks on failure. Saga + idempotency + reconciliation is the industry pattern.

5. The meeting-room and venue variant: ranges and time zones

Rooms differ in two ways: capacity is 1, and users pick arbitrary ranges (14:15 to 15:45), not fixed windows. Asked at Amazon SDE2 (2025-12), Yellow.ai (2026-10, with time zones) and as venue rental packages at Salesforce (2026-06).

  • Option A, fixed grid: cut the day into 15-minute cells and book cells with the slot logic above (capacity 1 each, all cells in one transaction, locked in time order). Simple, works with any database.
  • Option B, range constraint: Postgres can enforce "no overlap" itself with an exclusion constraint: 
    CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE room_booking (
  room_id  BIGINT,
  during   TSTZRANGE,       -- [start, end) in UTC
  status   TEXT,
  EXCLUDE USING gist (room_id WITH =, during WITH &&) WHERE (status <> 'CANCELLED')
);
    Two overlapping inserts for the same room: the second fails with an exclusion violation. No application-level check can race it.
  • Time zones: store instants in UTC (timestamptz), store each room's or venue's IANA zone (Asia/Kolkata, America/New_York), and convert only at the edges. Recurring meetings ("every Monday 10:00 New York time") must be stored as a rule plus the zone, and expanded per occurrence, or daylight-saving changes move the meeting by an hour.
  • Venue packages (Salesforce): a package is a bundle (ground + lights + 4 hours). Model package and package_item, and a booking that holds every resource in the bundle in one transaction.
  • Amazon's grilling was on Redis, Kafka, Elasticsearch and database choices: be ready to say why each exists (Redis for free/busy cache and holds, Kafka for invites and calendar sync events, Elasticsearch for "find a free room with a projector for 8 people", Postgres for the booking itself).
