Quick quiz

Two requests both read "9 of 10 booked" and both write 10. What fixes this most simply?

  1. A larger connection pool for the database
  2. Caching the slot count in Redis first
  3. One UPDATE with the capacity check in WHERE
  4. Retrying the request after a random delay
The conditional UPDATE checks and writes atomically under the row lock. More connections only make the race more frequent. Redis adds a second copy that can be stale and still has the same race. Random retries do not stop two writers from both passing the check.

Why must held places count against capacity?

  1. So nobody else pays for the same last place
  2. So the sweeper can run less often
  3. So the CDN cache never goes stale
If holds do not reduce availability, two users can both reach payment for one place. The sweeper still needs to run; holds counting against capacity makes timely release more important, not less. CDN staleness is unrelated to how holds are counted.

Why is a Redis key with a TTL not enough as the only record of a hold?

  1. Redis cannot store keys for five minutes
  2. Redis TTLs are rounded to whole hours
  3. Redis is slower than Postgres for counters
  4. Writes can be lost on failover; expiry events are not guaranteed
Replication is asynchronous, so a failover can lose holds, and keyspace expiry notifications are fire-and-forget. Redis happily stores keys with second or millisecond TTLs, and it is faster than Postgres for counters, which is why it is a good gate in front of the record.

A payment webhook arrives after the hold expired and the slot is now full. What should happen?

  1. Confirm it; whoever paid has priority
  2. Mark it refunded and refund automatically
  3. Cancel the newest booking for that slot
Never confirm a place you do not hold; compensate with an idempotent refund and tell the user. Confirming overbooks the slot. Cancelling someone else's valid booking punishes a user who did nothing wrong.

10,000 people want 8 seats on one ride slot. What is the core problem?

  1. Storage: 10,000 hold rows will not fit
  2. Bandwidth: the seat map is too large
  3. Contention: many writers on one counter
  4. Search: geo queries become too slow
17K requests per second is easy for caches; thousands of writers queueing on one row is the issue, solved by a gate, a per-slot queue or SKIP LOCKED tokens. 10,000 small rows are trivial to store, a ride's seat map is tiny, and the user already chose the ride, so geo search is not involved.

What does a Postgres exclusion constraint on (room_id WITH =, during WITH &&) give you?

  1. The database rejects overlapping bookings
  2. Bookings are stored in the room's time zone
  3. Old bookings are deleted after they end
The constraint makes a second booking with an overlapping range for the same room fail atomically. It does nothing about time zones (store UTC plus the room's zone) or retention (a separate archive job).

Why put the slot counters and the bookings in the same database?

  1. It lets you skip the payment Saga
  2. The invariant becomes one local transaction
  3. It removes the need for any caching
  4. Search queries can read bookings directly
"Bookings <= capacity" spans both tables, so co-locating them makes confirmation one ACID transaction. You still need a Saga for the external payment. Caching is still needed for a million reads per second, and search should never read the booking tables.
