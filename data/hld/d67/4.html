Data model

The heart is one small table: one row per slot with a capacity and two counters. Everything else is ordinary.

-- Reference data (rarely changes; cache it everywhere)
CREATE TABLE centre (
  centre_id    BIGINT PRIMARY KEY,
  name         TEXT, district_id INT, pincode TEXT,
  lat DOUBLE PRECISION, lon DOUBLE PRECISION,
  fee_paise    INT DEFAULT 0,          -- 0 = free centre
  tz           TEXT DEFAULT 'Asia/Kolkata'
);

-- The inventory: one row per bookable window
CREATE TABLE slot (
  slot_id      BIGINT PRIMARY KEY,
  centre_id    BIGINT NOT NULL REFERENCES centre,
  starts_at    TIMESTAMPTZ NOT NULL,   -- always store UTC instants
  ends_at      TIMESTAMPTZ NOT NULL,
  vaccine      TEXT, min_age INT,
  capacity     INT NOT NULL,
  booked       INT NOT NULL DEFAULT 0,
  held         INT NOT NULL DEFAULT 0,
  version      BIGINT NOT NULL DEFAULT 0,
  CHECK (booked + held <= capacity),   -- the database itself refuses overbooking
  UNIQUE (centre_id, starts_at, vaccine)
);

-- Pencil marks: one row per hold
CREATE TABLE hold (
  hold_id      UUID PRIMARY KEY,
  slot_id      BIGINT NOT NULL REFERENCES slot,
  user_id      BIGINT NOT NULL,
  qty          INT NOT NULL,
  status       TEXT NOT NULL,          -- ACTIVE | CONVERTED | EXPIRED | RELEASED
  expires_at   TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON hold (expires_at) WHERE status = 'ACTIVE';

-- Pen marks: the booking (same database as slot, on purpose)
CREATE TABLE booking (
  booking_id   UUID PRIMARY KEY,
  hold_id      UUID UNIQUE REFERENCES hold,   -- one booking per hold: idempotent
  slot_id      BIGINT NOT NULL, user_id BIGINT NOT NULL,
  status       TEXT NOT NULL,          -- PAYMENT_PENDING | CONFIRMED | CANCELLED | REFUNDED | ATTENDED
  amount_paise INT, psp_order_id TEXT UNIQUE,
  created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE booking_beneficiary (
  booking_id UUID, beneficiary_id BIGINT, dose_no INT,
  live BOOLEAN NOT NULL DEFAULT true,     -- false once cancelled or refunded
  PRIMARY KEY (booking_id, beneficiary_id));
-- A beneficiary may have only one live appointment per dose
CREATE UNIQUE INDEX one_live_appt ON booking_beneficiary (beneficiary_id, dose_no) WHERE live;

SQL or NoSQL?

DataStoreWhy
slot, hold, bookingPostgres / MySQL, sharded by state or districtNeeds a transaction that changes a counter and inserts a booking together, plus CHECK and UNIQUE constraints. Data is small. This is exactly what a relational database is for.
Centre searchElasticsearch (geo_point)Geo distance, filters (vaccine, age, fee) and text search; rebuilt from the centre table by CDC.
Availability counts for readsRedis + CDNA million reads per second, a few seconds stale is fine. Updated by events, never trusted for the decision.
Holds (fast gate)Redis with TTL (optional)Cheap pre-filter in front of the database for hot slots; the database hold row is still the record.
Notifications, audit streamKafkaFan-out to SMS, reminders, analytics; replayable.
Old bookingsS3 / object storage (Parquet)Archive after 30-60 days; cheap; queryable by Athena/Spark.

"Keep the order and the slot in the same transactional database." This is the exact phrase from the October 2026 Amazon report (post). If slot counts live in one service's database and bookings in another, you need a distributed transaction or a Saga just to avoid overbooking. Put them together and it is one local transaction. Split services by reason to change, not by noun.
