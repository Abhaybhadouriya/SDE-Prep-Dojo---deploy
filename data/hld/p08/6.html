How Kafka, Kubernetes and Docker help

Kafka

  • The fan-out queue. The post service writes a post-created event (keyed by author ID) to Kafka and returns. The fan-out service is a consumer group; add partitions and consumers to fan out faster. Kafka keeps the events, so if fan-out workers fall behind or crash, nothing is lost and lag shows how far behind you are.
  • Pub/sub fan-out for services. One topic, many consumer groups: the feed fan-out, the notification service, the search indexer and the analytics pipeline each read the same event independently. That is fan-out between systems, and it is Kafka's core strength. See Consumers & Consumer Groups.
  • Split celebrity work. A celebrity post can be expanded into many "fan-out chunk" messages (followers 0-5k, 5k-10k...) on a separate topic so it spreads across all partitions instead of one hot partition.
  • Not a per-user topic. Do not create a topic or partition per user or per channel; millions of tiny partitions do not work. Use a few topics with keys, and keep per-user state in Redis or a database.

Kubernetes

  • Fan-out workers are a Deployment autoscaled on Kafka consumer lag (for example with KEDA's Kafka scaler) rather than CPU.
  • Connection gateways are long-lived and stateful: use generous terminationGracePeriodSeconds, drain connections slowly on deploys (clients reconnect with backoff and jitter, or you get a reconnect storm), and spread pods across zones with topology spread constraints. See Services & Networking.
  • Redis timeline cluster runs as a StatefulSet or, more often, a managed service; it is a cache of truth that can be rebuilt by pull.

Docker

Package the fan-out worker, the feed reader and the gateway as separate images so each scales and deploys independently. Locally, a docker compose stack of Kafka + Redis + the three services is enough to demo the hybrid end to end; see Docker Compose.
