The solution ladder: naive to best

Rung 1: pull from the database at read time (naive fan-out on read)

Store each post once in a posts table. When Alice opens her feed: look up everyone she follows, fetch each one's recent posts, merge them by time, return the top 50. In SQL it is one query with a join and an ORDER BY created_at DESC LIMIT 50.

When it breaks: at 300,000 feed reads a second, each touching hundreds of followees spread across many shards, the database melts. Latency is set by the slowest shard you touch (tail latency). Here is why touching many shards makes the tail worse. Say each shard is slow only 1% of the time. A request that touches 100 shards is fast only if all 100 are fast: 0.99100 is about 0.37, so about 63% of requests (1 - 0.99100) hit at least one slow shard. One shard's rare bad case becomes the common case for the whole request. This is what p99 measures: the 99th-percentile latency, the time under which 99 of every 100 requests finish. It tracks the slow tail, not the average. Users who follow 5,000 accounts get the slowest feeds of all. Hello Interview's Facebook news feed breakdown starts here and moves on for the same reason.

Rung 2: fan-out on write into precomputed feeds (push)

Move the work to write time. Keep a small list per user, the home timeline or inbox, in a fast store such as Redis. When Bob posts, a fan-out service looks up Bob's followers and pushes the new post's ID onto each follower's list. Reading a feed becomes a single key lookup plus "hydration" (fetching the post bodies for those IDs from a post cache with a multi-get).

What goes in the list matters. Store IDs, not posts: the system-design-primer sketches a Redis list where each entry is about 17 bytes (8-byte tweet ID, 8-byte user ID, 1 byte of flags). Twitter kept at most 800 entries per home timeline, replicated 3 times in Redis, and only for users active in the last 30 days. Hello Interview's breakdown caps the precomputed feed at about 200 post IDs: around 2 KB per user, so roughly 4 TB for 2 billion users. Older pages fall back to the slow pull query, which few people ever scroll to.

When it breaks: the celebrity problem. A user with 31 million followers (Lady Gaga in Twitter's 2012 talk) turns one tweet into 31 million inserts. High Scalability's summary of the talk gives the delivery times: a median of about 3.5 seconds to reach 1 million followers, but a p99 of up to 5 minutes. Meanwhile the celebrity's replies arrive before the original tweet for some followers, and the fan-out workers are too busy to deliver ordinary users' posts quickly. You also waste work: you push into the lists of millions of followers who will never open the app today.

Rung 3: the hybrid - push for most, pull for celebrities

Pick a threshold (for example, 10,000 or 100,000 followers; it is tunable). Accounts below it are pushed. Accounts above it are flagged "do not fan out"; their posts are stored once, and pulled at read time for each reader who follows them. Since a typical user follows only a handful of celebrities, the read-time merge is small. Twitter's 2012 talk named this as the planned fix (stop fanning out the largest accounts and merge their tweets at read time); Hello Interview's breakdown uses the same flag-and-merge idea. Click through a hybrid feed read.

  1. Request. Alice opens the app: GET /feed?cursor=....
  2. Pushed part. Read her precomputed timeline: one key, a few hundred post IDs written by fan-out workers.
  3. Pulled part. Look up the few high-follower accounts she follows and fetch their recent post IDs (these lists are hot and cached, because millions read them).
  4. Merge. Combine both lists, drop duplicates and blocked/deleted posts, then sort by time or score with the ranking model.
  5. Hydrate. Multi-get the bodies, author names, like counts and media URLs for the top 50 IDs from the post cache.
  6. Respond. Return the page with a cursor (the ID or timestamp of the last item), never an offset, so new posts do not shift pages.

From your world

Push vs pull is interrupts vs polling, and the hybrid is NAPI. A NIC that raises an interrupt per packet is "push"; great at low rates, but an interrupt storm at high rates livelocks the CPU. Polling is "pull"; wasteful when idle. NAPI switches: interrupt to start, then poll while the load is heavy. Feeds do the same split, but by sender size instead of by load. It is also proactive vs reactive routing: a precomputed FIB (push the answer before anyone asks) versus resolving on demand (ARP on first packet). Precompute for the common case, resolve on demand for the rare and expensive one.

Rung 4: fan out to connections, not just to lists

Chat and live comments add a twist: the receivers are online right now, holding WebSocket connections, and a message should appear within half a second. Now fan-out is about delivering to connection servers. The trick big systems share: fan out once per server, not once per user.

  • Slack: each channel lives on one in-memory channel server, chosen by consistent hashing; a channel server holds about 16 million channels at peak. When you connect, your gateway server subscribes to the channel servers for your channels. A message goes to the channel's server, which sends it to every subscribed gateway, which pushes to its clients. Slack reports about 500 ms delivery worldwide.
  • Discord: each guild (server) is an Erlang process that sends events to every connected member's session process. Plain per-member sends worked for small groups but, for guilds with tens of thousands of online members, publishing one event took roughly 0.9 to 2.1 seconds at peak. Their library Manifold groups recipients by remote node, sends once per node, and lets workers on that node do the local fan-out, splitting recipients across CPU cores by hash.

From your world

This is IP multicast. The source sends one packet; routers replicate it only where the tree branches, and IGMP snooping on the last switch delivers it only to ports with listeners. Slack's gateway subscriptions are IGMP joins; Discord's Manifold is replication at the branch point. Unicasting a copy to every receiver from the source is exactly the naive fan-out that falls over.

Rung 5: make fan-out cheap, fair and resilient

  • Async with a queue: the post API returns as soon as the post is stored; fan-out happens in workers. Split a big follower list into chunks (say 5,000 followers per task) so many workers share one celebrity's fan-out and one slow chunk can be retried alone.
  • Priorities: keep celebrity or "broadcast" fan-out on a separate queue so it cannot delay normal users' posts. In notifications, OTPs and transactional messages get their own queue ahead of marketing.
  • Only push to active users: Twitter kept timelines in RAM only for users active in the last 30 days. Inactive users' feeds are rebuilt by pull when they return.
  • Cap the list: trim to the newest few hundred IDs so memory stays bounded.
  • Deletes and privacy: do not try to un-fan-out a deleted post from 31 million lists. Filter at read time against a "deleted/blocked" check during hydration.
  • Idempotent inserts: idempotent means safe to run twice: the second run changes nothing, like setting a register to a value rather than incrementing it. Fan-out workers retry, so insert by post ID (a sorted set keyed by post ID, or a dedupe check) so a retry does not show the post twice.
