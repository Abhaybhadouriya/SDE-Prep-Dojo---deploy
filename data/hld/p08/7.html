Interview: phrases, traps and questions

Phrases that score

  • "Reads dominate, so I precompute: fan-out on write into a capped list of post IDs per user."
  • "Celebrity accounts above a tunable threshold are not fanned out; their posts are merged at read time."
  • "Fan-out is asynchronous through a queue, chunked, with a separate priority lane, and inserts are idempotent."
  • "Store IDs, hydrate from a post cache; filter deletes and blocks at read time."
  • "For online delivery, fan out once per gateway server, not once per user."

Traps

  • Picking push or pull without numbers. Always compare reads vs writes and the follower distribution.
  • Storing full post objects in every follower's feed (edits and deletes become impossible).
  • Offset pagination on a feed that changes every second; use a cursor.
  • Synchronous fan-out inside the post request.
  • Forgetting inactive users, deletes, blocks and the reply-before-original ordering glitch.
Explain fan-out on write vs fan-out on read.

Fan-out on write (push): when a user posts, copy the post ID into every follower's precomputed feed. Reads are one lookup; writes cost one insert per follower. Fan-out on read (pull): store the post once; at read time gather recent posts from everyone the reader follows and merge. Writes are cheap; reads are expensive and slow. Feeds are read far more than written (Twitter, 2012: about 300K reads/s vs 6K writes/s), so push is the default, with pull for very large accounts.

How to answer

Define both in one line each, give the cost in O(), then the read/write ratio that decides it, then mention the hybrid.

Likely follow-ups
  • What is the celebrity problem?
  • Where do you store the precomputed feed?
What is the celebrity (hot user) problem and how do you solve it?

With push, a user with tens of millions of followers turns one post into tens of millions of inserts. It takes minutes (Twitter saw p99 of up to 5 minutes for very large fan-outs), clogs the fan-out workers for everyone, and wastes work on inactive followers. Fix: mark accounts above a threshold as "pull"; store their posts once in a hot, cached per-author list; at read time merge the few celebrity lists a user follows with the user's pushed timeline. Keep celebrity fan-out (if any) on a separate queue.

How to answer

Quantify the cost, then the hybrid, then the read-time merge cost (small, because a user follows few celebrities).

Likely follow-ups
  • How do you pick the threshold? (Measure; tune by cost; per-account flag.)
  • What happens when a normal user suddenly goes viral?
What exactly do you store in the precomputed feed, and how big is it?

Only post IDs (plus maybe author ID and a flag byte), in a capped list per user, newest first. The primer's layout is about 17 bytes per entry. At 200 entries that is a few KB per user; Hello Interview estimates about 4 TB for 2 billion users at ~2 KB each, which fits in a Redis cluster. Twitter kept 800 entries, replicated 3x, only for users active in the last 30 days. Post bodies, counts and media live in a separate post cache and are hydrated with a multi-get.

How to answer

Show the arithmetic: entries x bytes x active users x replicas.

Likely follow-ups
  • What happens when a user scrolls past the cached 200?
  • What if Redis loses a node?
A user deletes a post that was already fanned out to 2 million feeds. What do you do?

Do not chase 2 million lists synchronously. Mark the post deleted in the post store (the source of truth). During hydration the feed service drops any ID whose post is deleted, so it disappears from every feed instantly. Optionally a background job lazily removes the dangling IDs, or they simply age out of the capped lists. Same for blocks and privacy changes: filter at read time.

How to answer

Source of truth + read-time filter; cleanup is lazy and optional.

Likely follow-ups
  • And edits? (IDs, not copies, so edits are free.)
A user who follows 5,000 accounts complains the feed is slow. Why, and how do you fix it?

If the feed is pull-based, or that user follows many accounts above the celebrity threshold, each read scatters to thousands of lists and waits for the slowest. Fixes: make sure that user's feed is pushed (precomputed) for all normal followees; cap the read-time merge (take only the top few posts from each celebrity list, or only recently active celebrities); cache the merged first page for a short TTL; and hedge slow shard requests. LinkedIn's broker sends duplicate requests to replicas and takes the first.

How to answer

Find which path is slow (push or pull part), then bound the fan-in.

Likely follow-ups
  • What is request hedging and what does it cost?
Design message delivery for a Teams/Slack channel with 100,000 members.

Store the message once in the channel's log (partitioned by channel ID, ordered by a per-channel sequence). For online members, route the message to the channel's owner server (consistent hashing), which sends one copy to each gateway server that has subscribers in that channel; gateways push to their sockets. For offline members, do not write 100,000 inbox entries: keep a per-user "last read sequence" per channel and compute unread counts lazily; send push notifications only to members whose settings ask for them (mentions), through the notification queue. This matches Slack's channel-server and gateway-server split.

How to answer

Separate online delivery (connection fan-out per server) from offline catch-up (pull from the channel log).

Likely follow-ups
  • How do you compute unread badges for 100k members?
  • What if the channel server dies? (Rehash; Slack reports a replacement in under 20 s in our research notes.)
Should the fan-out happen inside the "create post" request?

No. The request stores the post, emits a post-created event to a queue (Kafka/SQS), and returns. Fan-out workers consume the event, look up followers in pages, and insert into feeds. This keeps post latency flat no matter how many followers, absorbs spikes, and lets failed chunks retry. The author sees their own post immediately because their own timeline is written synchronously (read-your-writes for the author).

How to answer

Async + queue + chunking + "author sees own post now".

Likely follow-ups
  • How do you avoid duplicate entries when a worker retries?
  • See Managing Long-running Tasks.
Why might a company choose pure pull for its feed, like LinkedIn did?

Because push stores an ordering. When ranking is ML-based and changes with every experiment, stored feeds must be re-sorted or rebuilt; with pull, scores are computed fresh at read time. Push also stores many copies (LinkedIn measured about 62x more data for push in its experiments) and does work for passive readers. LinkedIn made pull fast by partitioning per-author timelines (720 partitions), scoring in parallel on index nodes, and hedging requests, reaching about 140 ms p99 on mobile.

How to answer

Name the two costs of push that pull avoids (storage, re-ranking), then how pull is made fast.

Likely follow-ups
  • What makes the pull path's tail latency acceptable?
How do you deliver live comments to 5 million viewers of one stream?

Pure push per viewer is 5 million sends per comment. Use two-level fan-out: viewers connect to many connection servers; each server subscribes once to the stream's pub/sub channel; a comment is published once and each server delivers to its local sockets. Then reduce volume: batch comments into one frame every few hundred ms, sample (nobody can read 10,000 comments a second), and prefer comments from friends. Discord's Manifold shows the same "send once per node, fan out locally" trick.

How to answer

Two-level fan-out, then batching and sampling as product-level load shedding.

  • See Live Comments and Real-time Updates.
A marketing push to 100 million users is delaying OTP messages. What went wrong?

Both shared one fan-out queue and worker pool, so the giant campaign sat in front of the OTPs (head-of-line blocking). Separate queues and worker pools by priority: transactional (OTP, payment) first, marketing on its own throttled lane; rate-limit campaign fan-out; chunk it by segment. Monitor age of oldest message per lane.

How to answer

Name head-of-line blocking, then isolation by priority.

  • See Notification System.

Scenario: a cricket star joins your app

Your Instagram-like app uses pure fan-out on write. A famous cricketer joins and gains 40 million followers in a week. Each of their posts now takes 20 minutes to appear in all feeds, and ordinary users' posts are delayed too.

Weak answer: "Add more fan-out workers and a bigger Redis."

Strong answer: this is the celebrity problem. Short term: move celebrity fan-out to its own queue so normal posts recover immediately. Real fix: hybrid. Flag accounts above a threshold (say 100k followers) as pull; their posts go into a hot per-author list that is cached heavily; the feed service merges the few celebrity lists a reader follows with the pushed timeline at read time. Back-fill: when an account crosses the threshold, stop fanning out new posts; existing entries age out. Watch read-path latency after the change, and cache the merged first page briefly.

Likely follow-ups
  • What if a normal user's post goes viral? (Virality is about readers, not followers; it is a hot-key read problem: cache the post, see Scaling Reads.)
  • How do you keep ordering correct when merging two sources?
