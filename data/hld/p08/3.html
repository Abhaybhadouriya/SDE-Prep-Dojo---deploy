The maths: when push wins and when pull wins

Let W = posts written per second, F = average followers per poster, R = feed reads per second, K = average accounts a reader follows.

  • Push cost = W x F list inserts per second (writes) + R single-key reads.
  • Pull cost = W inserts + R x K lookups per second (reads), each read waiting for its slowest shard.

Plug in the primer's assumptions: W = 6,000, F = 10, so push costs 60,000 inserts a second - very affordable - and turns 100,000 reads a second into single lookups. If the average reader follows K = 200 accounts, pull would cost 20 million lookups a second. Push wins easily on average. The trouble is the tail of F: one poster with F = 30,000,000 costs as much as 3 million ordinary posts (at F = 10) in a single moment. The hybrid removes exactly that tail.

Also count what is wasted. Push does work for followers who never read; pull does work only when someone reads. So in a product where most followers are passive (huge broadcast accounts, news publishers), pull is cheaper even before the celebrity problem. LinkedIn measured this: in their experiments a push design used about 62 times more data than their pull design, and stored feeds would need re-sorting every time the ranking model changed.

Case study: LinkedIn chose pull on purpose

LinkedIn's FollowFeed (2016) is the best counter-example to "always push". They keep one timeline per author (keyed by entity and content type) in RocksDB, spread over 720 partitions (a number with many divisors so the cluster can grow in many sizes). A feed request goes to a broker, which maps the viewer's followed entities to partitions and asks each index node in parallel; each node scores its candidates with the ranking model, returns its top N, and the broker merges. They hedge tail latency by sending duplicate requests to replicas and keeping the first answer. Results they report: mobile feed p99 about 140 ms, about five times faster than the previous system, with half the servers. The reason: ranking is fresh at every read, and A/B testing a new model needs no rewrite of stored feeds.

Lesson: push precomputes an ordering. If the ordering changes often (ML ranking, experiments) or reads are rare compared with writes, pull becomes attractive. If the feed is mostly chronological and read constantly, push wins.
