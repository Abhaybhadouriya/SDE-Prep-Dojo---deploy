Where Kafka, Kubernetes and Docker fit

  • Kafka: the invalidation bus above (see the pipeline architecture for CDC end to end, and Kafka core concepts for keys and partitions). A consumer group of invalidators gives failover; replay lets you re-run invalidations after a bug. Kafka is also the classic place to put a write-behind buffer: counters are incremented in Redis and flushed to the DB through a topic.
  • Kubernetes: run Redis as a StatefulSet or with an operator so each pod keeps its name and volume; use pod anti-affinity and topology spread so a primary and its replica never share a node or zone. Set the container memory limit above Redis maxmemory (buffers, fork for snapshots); if maxmemory equals the cgroup limit the kernel OOM killer will kill Redis before Redis evicts anything (requests and limits). Many teams use a managed cache (ElastiCache, Azure Cache for Redis, Memorystore) instead.
  • Docker: the one-line local cache above, or a Compose file with app + Redis + database for testing cache-aside locally (Docker Compose).
# redis.conf for a cache node (excerpt)
# redis.conf has no inline comments: every comment must be on its own line.
# leave headroom below the container/VM limit
maxmemory 48gb
# evict any key, least frequently used first
maxmemory-policy allkeys-lfu
# better eviction accuracy, a bit more CPU
maxmemory-samples 10
cluster-enabled yes
# ms before a node is suspected failed
cluster-node-timeout 5000
# pure cache: no AOF
appendonly no
# no RDB snapshots (or keep one for warm restarts)
save ""
