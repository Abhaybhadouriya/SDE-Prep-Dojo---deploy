Data model: what lives inside one node

Inside one cache node there is no SQL vs NoSQL choice: it is a hash table in RAM. Each entry holds the key, the value, an expiry time, and a little metadata for eviction (a last-access clock for LRU or a frequency counter for LFU). The interesting parts are how expiry and eviction work at O(1) cost.

The O(1) LRU: hash map + doubly linked list

This is the exact low-level design question Microsoft-style rounds ask. A hash map finds the node in O(1). A doubly linked list keeps nodes in order of use: move a node to the front on every access, evict from the back. Both operations are O(1) because unlinking a node from a doubly linked list needs only its neighbours.

class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=None, val=None):
        self.key, self.val, self.prev, self.next = key, val, None, None

class LRUCache:
    """O(1) get/put: hash map for lookup + doubly linked list for recency."""
    def __init__(self, capacity: int):
        self.cap, self.map = capacity, {}
        self.head, self.tail = Node(), Node()      # sentinels: head = newest side
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n

    def get(self, key):
        n = self.map.get(key)
        if n is None:
            return None
        self._unlink(n); self._push_front(n)       # mark as most recently used
        return n.val

    def put(self, key, val):
        if key in self.map:
            n = self.map[key]; n.val = val
            self._unlink(n); self._push_front(n)
            return
        if len(self.map) == self.cap:              # evict least recently used
            lru = self.tail.prev
            self._unlink(lru); del self.map[lru.key]
            print("evict", lru.key)
        n = Node(key, val); self.map[key] = n; self._push_front(n)

c = LRUCache(2)
c.put("a", 1); c.put("b", 2)
c.get("a")          # a is now most recent
c.put("c", 3)       # evicts b
print(c.get("b"), c.get("a"), c.get("c"))
$ python lru.py
evict b
None 1 3

How real caches cheat (cleverly)

  • Redis approximates LRU. A linked list costs two pointers per key and a write on every read. Redis instead stores a small access clock per key and, when it must evict, samples a few keys (maxmemory-samples, default 5) and evicts the best candidate among them. Bigger samples get closer to true LRU at more CPU cost. LFU mode keeps a small logarithmic frequency counter that decays over time, which protects popular keys from being pushed out by a one-off scan.
  • Expiry is lazy plus active. An expired key is deleted when someone touches it (lazy), and a background cycle also samples keys that have a TTL and deletes the expired ones, so memory does not fill with dead keys nobody reads.
  • Memcached uses a slab allocator. Memory is pre-cut into size classes (slabs) to avoid fragmentation, with an LRU per slab class. The catch: if your value sizes shift over time, one slab class can starve while another has free memory.

From your world

Memcached's slab classes are the kernel's slab allocator (kmalloc size caches); Redis's sampled LRU is the same trick as the kernel's clock-style page reclaim, which approximates LRU with reference bits instead of a perfect list. Where this breaks: the kernel reclaims pages it can re-read from disk for free; a cache eviction costs a database query later, so the policy choice shows up directly in database load.

Key design

Name keys like paths: user:42:profile, product:9001:price:v3. Put a version in the key when the value's format changes, so new code never reads old-format entries. Keep values small (KBs, not MBs): big values block a single-threaded server and saturate the network.
