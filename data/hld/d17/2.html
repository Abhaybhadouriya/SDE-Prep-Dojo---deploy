Back-of-envelope estimation

  1. Memory. 1 TB of values plus keys and per-entry overhead (pointers, expiry, allocator fragmentation). Assume about 1.5x overhead (assumption; measure with INFO memory), so about 1.5 TB of RAM needed.
  2. Nodes by memory. Use about 64 GB usable per node (leave headroom for fork-based snapshots, buffers and the OS). 1.5 TB / 64 GB is about 24 primary nodes.
  3. Nodes by throughput. Plan with a conservative per-node figure such as 100,000 simple ops/s (assumption; a single Redis process executes commands on one main thread, so measure your real number with redis-benchmark). 1,000,000 / 100,000 = 10 nodes. Memory (24) is the larger number, so memory decides.
  4. Replicas. One replica per primary across zones: 24 primaries + 24 replicas = 48 nodes. Round to 50-60 for headroom and hot spots.
  5. Bandwidth. 1 M ops/s x 1 KB = 1 GB/s, about 8 Gbit/s for the whole cluster, about 0.33 Gbit/s per primary. Network is fine; big values (100 KB+) would change that quickly.
  6. Hot key check. If 10% of reads hit one key (a celebrity profile, a flash-sale product), that is 90,000 ops/s on one node, close to its whole budget. Even load on average does not mean even load per key. This number is what motivates the hot-key deep dive.
  7. What the cache saves. With a 95% hit ratio, the DB sees 5% of 900,000 reads = 45,000 reads/s. If the cache disappears, it sees all 900,000. That 20x jump is why a cache outage is a database outage.

From your world

"Average is fine but one flow is hot" is the elephant-flow problem in ECMP: a single big flow hashes to one link and saturates it while others sit idle. A hot cache key is an elephant flow. The fixes rhyme too: split it (key salting, like flowlet switching), or serve it closer to the source (a local cache, like a punt-path cache on the line card). Where this breaks: an elephant flow is usually one long transfer you can predict; a hot key appears in seconds (a viral post) and is mostly reads, so you must detect it live (per-key counters or sampling) and reads are the easy part to copy, writes are not.
