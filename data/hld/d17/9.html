Interview: how to drive 45 minutes

  1. 0-5: requirements. Read/write ratio, data size, value size, latency target, can we lose data, how stale is OK.
  2. 5-10: estimate. RAM with overhead, nodes by memory vs by ops (take the bigger), replicas, bandwidth, the hot-key number.
  3. 10-15: single node. Hash map + LRU (O(1)), TTL with lazy + active expiry. If it is an LLD-flavoured round, write the LRU code.
  4. 15-25: distribute. Hash slots or consistent hashing (say why not modulo), smart client vs proxy, replicas across zones, failover.
  5. 25-38: hard parts. Cache-aside vs write-through, invalidation race and fixes, hot keys, stampede.
  6. 38-45: operate. Failure table, metrics (hit ratio, evictions, p99, memory, replication lag), and protecting the DB.

Common mistakes: modulo-N hashing; no TTL; updating the cache on write instead of deleting; assuming Redis replication is synchronous; no plan for a stampede or a hot key; forgetting the default noeviction; treating the cache as the source of truth; ignoring what happens to the database when the cache is down.

60-second answer, said out loud: "I'd build a cluster of in-memory nodes, each a hash map with approximate LRU or LFU eviction and TTLs expired lazily plus by a background sampler. Keys map to 16,384 hash slots by CRC16, and a slot table maps slots to nodes, so adding a node moves only a few slots; smart clients route directly and follow MOVED redirects. Each primary has an async replica in another zone, promoted by majority vote on failure, so we may lose a few writes, which is fine for a cache. Apps use cache-aside: read the cache, on miss read the DB and set with a jittered TTL; on write, commit then delete. For hot keys I add a short-lived local cache and key replication; for stampedes, request coalescing or leases; for correctness, leases or versioned sets plus CDC-driven invalidation through Kafka. I'd alert on hit ratio, evictions, p99 and per-node skew."

Design an LRU cache with O(1) get and put. Then make it distributed.

Single node: a hash map from key to a node in a doubly linked list. Get: find via map, move node to head. Put: insert at head; if over capacity, remove the tail and its map entry. Both O(1). Add a lock (or shard the map into segments with a lock each) for concurrency. Distributed: partition keys over nodes with consistent hashing or hash slots, run one LRU per node, replicate each node asynchronously, and route with a smart client or proxy. Note that LRU is now per node, not global, which is fine.

How to answer

Write the single-node code cleanly first (sentinel head/tail), state complexity, then scale out in three moves: partition, replicate, route.

Likely follow-ups
  • How do you make it thread-safe without one global lock?
  • Why does Redis approximate LRU instead?
  • LRU vs LFU: when does LRU fail? (one big scan flushes the cache)
Why not use hash(key) mod N to pick a node?

Because changing N remaps most keys: from 4 to 5 nodes about 80% of keys change node, so the hit ratio collapses and the DB is flooded. Consistent hashing with virtual nodes or fixed hash slots move only about 1/N of keys when a node is added.

How to answer

Give the percentage, then the fix, then mention virtual nodes for even load.

Likely follow-ups
  • Why does Redis use 16,384 slots instead of a ring?
  • What are hash tags for?
Cache-aside vs write-through vs write-behind: which and why?

Cache-aside for most read-heavy data: simple, the cache can fail without blocking writes, only requested data is cached. Write-through when data is read immediately after it is written and you want the cache always warm, at the cost of slower writes. Write-behind for very write-heavy data that tolerates loss (counters, view counts), because writes are batched into the DB later.

How to answer

Use the trade-off sentence: pick X because A, cost B, switch to Y if C.

Likely follow-ups
  • What happens to write-behind data when a node dies?
A hot key is about to expire and 5,000 requests are waiting. What happens and how do you prevent it?

Without protection all 5,000 miss and query the DB at once (a stampede). Prevent with: request coalescing per process; leases so only one client per key is allowed to refill (others wait or get the stale value); jittered TTLs; early background refresh before expiry; serving stale during refresh.

How to answer

Name it (stampede / thundering herd), give two fixes at two layers (in-process coalescing, server-side leases), then one preventive (jitter).

Likely follow-ups
  • What if the refill query itself takes 10 s?
Users see stale data after updating their profile. Walk through why and fix it.

Check the order of operations. If the code sets the cache before committing, or updates rather than deletes, two writers can reorder. Even with "commit then delete", a slow reader can refill an old value after the delete. Fixes: delete (not set) after commit; leases or versioned compare-and-set to reject old fills; a TTL backstop; CDC-driven invalidation; and for the user's own view, read-your-writes by reading from the DB (or bypassing the cache) for a few seconds after their own write.

How to answer

Draw the three-step race on the board. Interviewers love seeing the actual interleaving.

Likely follow-ups
  • How do you invalidate caches in another region?
One product key gets 100,000 reads per second during a flash sale. What do you do?

A single node cannot carry it. Add a local in-process cache with a 1-2 s TTL in every app server (staleness accepted for product details, not for stock count); replicate the key under salted names across nodes; serve reads from replicas. For the stock count, do not read it from cache for correctness: decrement atomically in one place (a Redis Lua script or the DB) and show an approximate number on the page.

How to answer

Separate "display data" (staleness OK) from "decision data" (must be exact). Link to building blocks and the flash-sale design.

Likely follow-ups
  • How do you detect hot keys before they hurt?
Is Redis replication synchronous? What can you lose?

No, asynchronous. The primary replies to the client and then streams to replicas. If it crashes before the stream reaches a replica, and that replica is promoted, the acknowledged write is lost. WAIT lets a client block until N replicas ack, reducing the window, but failover can still lose data, so Redis is not a strongly consistent store.

How to answer

One sentence of mechanism, one of consequence, one of mitigation, and "fine for a cache".

Likely follow-ups
  • Then how would you build a reliable lock on Redis? (careful: fencing tokens)
The whole cache cluster goes down. What happens to the database?

DB read load jumps by 1 / (1 - hit ratio): 20x at 95%. It will likely fall over. Prepare: circuit breakers so app servers fail fast and shed non-critical traffic; a local L1 cache that serves stale data; a gutter pool; rate-limited warm-up when the cache returns; and capacity planning that knows how much miss traffic the DB can survive.

How to answer

Do the multiplication out loud. Then talk about graceful degradation, not just "add replicas".

Likely follow-ups
  • How do you warm a new cluster without hurting the DB?
Redis or Memcached? Pick one for a session store and for a product-page cache.

Sessions: Redis (TTL per key, replication and failover built in, optional persistence so a restart does not log everyone out). Product pages (big, simple blobs, huge volume): either works; Memcached is simpler and multi-threaded, Redis gives one tool for everything and built-in clustering. Many teams choose Redis for both to run one system.

How to answer

Tie each choice to one concrete feature, not brand preference.

Likely follow-ups
  • Where would you store sessions if the cache is not allowed to lose them?
How do you invalidate caches across three regions?

Make invalidation an event stream. CDC reads the primary DB's commit log and publishes changes to Kafka; each region runs an invalidator consumer group that deletes keys in its local cache. Order per key is kept by keying events by primary key. Keep TTLs as a backstop for lost or delayed events, and monitor consumer lag per region as your staleness metric.

How to answer

Commit log -> Kafka -> per-region invalidators; then say lag = staleness.

Likely follow-ups
  • What if an invalidation arrives before the region's DB replica has the new row? (refill reads stale replica: delay or use versions)

Scenario: DB CPU hits 100% right after a deploy

Every deploy at 10:00 causes a 3-minute database overload. Cache hit ratio drops from 96% to 40% for those minutes.

Weak answer: "Scale up the database."

Strong answer: the deploy is changing keys or emptying caches. Likely the key format includes a version that changed, or in-process caches are cold in all new pods at once, or the cache was flushed. Fix: roll pods gradually so caches warm in steps; keep key formats backward compatible or pre-warm the new keys; coalesce misses; add jitter to TTLs set at startup. Verify with the hit-ratio and miss-by-key-prefix dashboards.

Likely follow-ups
  • How would you pre-warm safely?

Scenario: Redis pod keeps restarting with OOMKilled

On Kubernetes, the Redis pod restarts every few hours; kubectl describe pod shows OOMKilled, exit code 137. Redis logs show no eviction.

Weak answer: "Double the memory limit."

Strong answer: the container limit equals or is below what Redis really uses. maxmemory counts the dataset, not replication buffers, client output buffers or the copy-on-write pages of a background save fork. Set maxmemory to about 60-75% of the container limit (a rule of thumb), pick an eviction policy, disable snapshots if not needed, and watch used_memory_rss vs the cgroup limit.

Likely follow-ups
  • Why exit code 137? (128 + SIGKILL 9)
