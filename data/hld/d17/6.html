Deep dives

1. Partitioning: modulo, consistent hashing, or hash slots

The naive rule node = hash(key) mod N breaks the moment N changes: going from 4 to 5 nodes changes the answer for about 80% of keys (only keys where h mod 4 == h mod 5 stay), so the hit ratio collapses and the database is flooded. Two fixes are used in practice:

  • Consistent hashing with virtual nodes (Memcached clients, Dynamo, Cassandra): put many points per server on a hash ring; a key belongs to the next point clockwise. Adding a server only takes the slices next to its points, about 1/N of keys. See Distributed Building Blocks.
  • Fixed hash slots (Redis Cluster): the key space is cut into exactly 16,384 slots; slot = CRC16(key) mod 16384; a small table maps slots to nodes. Scaling moves whole slots between nodes. A hash tag {...} makes several keys hash only on the part inside braces, so {user:42}:cart and {user:42}:profile land in one slot and can be used together in a multi-key command.
def crc16(data: bytes) -> int:            # CRC16-XMODEM, as in the Redis Cluster spec
    crc = 0
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) if crc & 0x8000 else (crc << 1)
            crc &= 0xFFFF
    return crc

def key_slot(key: str) -> int:
    s = key.find("{")
    if s != -1:
        e = key.find("}", s + 1)
        if e > s + 1:                     # non-empty {hash tag}
            key = key[s + 1:e]
    return crc16(key.encode()) % 16384

print(hex(crc16(b"123456789")))          # spec test vector: 0x31c3
for k in ["user:42", "user:43", "{user:42}:cart", "{user:42}:profile"]:
    print(f"{k:20} slot {key_slot(k)}")

Smart client vs proxy. A smart client (Redis Cluster clients, Memcached clients with consistent hashing) saves one network hop but puts routing logic in every language's library. A proxy (Twitter's twemproxy, Meta's mcrouter, Envoy's Redis filter) centralises routing, connection pooling and failover policy, at the cost of an extra hop and another tier to run. Big fleets often choose the proxy for operational control.

2. Replication and failover: async, so it can lose writes

Each primary streams its writes to one or more replicas. Redis replication is asynchronous: the primary acknowledges the client first and sends to replicas afterwards. If the primary crashes between those two moments, the promoted replica never saw the write. The WAIT numreplicas timeout command makes the client wait until N replicas acknowledged, which shrinks that window but does not make the system strongly consistent (a failover can still pick a replica that missed it).

Failure detection: in Redis Cluster, nodes ping each other over a cluster bus; when a majority of primaries agree a primary is unreachable for longer than cluster-node-timeout, one of its replicas is elected and promoted. In standalone mode, Redis Sentinel processes do the same job. Put each replica in a different availability zone from its primary.

From your world

Primary-replica with heartbeat failover is your active-standby control card with hello timers. Async replication is a standby that is "warm but behind": on switchover you lose whatever was not yet mirrored. The cluster's majority vote before promotion is split-brain protection, the same reason HA pairs use a quorum or witness. Where this breaks: a router's standby rebuilds state from neighbours (graceful restart); a cache replica cannot rebuild lost writes, it just turns them into misses, which is fine because the database still has them.

Persistence is optional for a cache. Redis offers RDB snapshots (a forked child writes the dataset to disk) and an AOF append-only log. Snapshots are useful for a warm restart: a cold 64 GB node means 64 GB of misses hitting the database. But note the fork: copy-on-write during a snapshot can temporarily need much more memory under heavy writes, which is one reason to leave RAM headroom.

3. Hot keys and the thundering herd

Hot keys. From the estimate: one key at 90,000 reads/s maxes out its node no matter how many nodes you add. Fixes, cheapest first:

  • Local in-process cache (L1) with a very short TTL (1-5 s) in every app pod. 200 pods each refreshing once per 2 s turns 90,000 reads/s into about 100 reads/s on Redis. Cost: up to 2 s of staleness.
  • Replicate the hot key: write it under N salted names (product:9001#0 .. #7) that land on different nodes; readers pick one at random. Writers must update all copies.
  • Read from replicas for that key (acceptable staleness).
  • Detect it: client-side sampling, redis-cli --hotkeys (needs an LFU policy), or proxy metrics. You cannot fix what you cannot see.

Cache stampede (thundering herd, dogpile): a hot key expires, and 5,000 requests miss at the same instant and all run the same expensive query. Fixes:

  • Request coalescing ("single flight"): inside one process, concurrent misses for the same key share one in-flight load. Discord describes doing this in its Rust data services in front of its message database.
  • Leases (Meta's memcache paper): on a miss the server hands out a lease token to only one client; others are told to wait briefly and retry. Meta's paper says servers issue a token for a given key at most once every 10 seconds. The same token also stops stale sets (deep dive 4).
  • Jittered TTLs: ttl = 300 + random(0, 60) so keys filled together do not expire together.
  • Early refresh: when a hot key is close to expiry, one request refreshes it in the background while others keep reading the current value (probabilistic early expiration).
  • Serve stale: keep the old value a little past its soft TTL and return it while the refresh runs.

4. Keeping the cache and the database consistent

Learner question answered: "How does a cache go stale?" Here is the classic race in cache-aside even when you delete on write:

  1. Reader A misses and reads the old value v1 from the database. Then A is slow (GC pause, network).
  2. Writer B updates the database to v2 and deletes the cache key.
  3. Reader A wakes up and writes v1 into the cache. Now the cache holds stale data until the TTL expires.

Fixes, from simple to strong:

  • TTL as a backstop: always set one, so any bug heals within seconds or minutes.
  • Leases: a delete invalidates any outstanding lease token, so A's late set with the old token is rejected. This is exactly how Meta's memcache prevents stale sets.
  • Versioned sets: store a version (row version or commit timestamp) with the value and only overwrite with a higher version (compare-and-set).
  • Delete after commit, and delete again ("double delete"): delete once after commit and once more a short delay later to catch in-flight fills. Cheap, not perfect.
  • CDC-driven invalidation: instead of the app deleting keys, a change-data-capture tool (Debezium) reads the database's commit log and publishes each change to Kafka; an invalidator service consumes it and deletes the matching cache keys. You cannot forget an invalidation in some code path, and it works for writes from any service. Meta's memcache paper describes the same idea (daemons tailing the MySQL commit log to broadcast deletes to other regions).

Why delete instead of update on write? If two writers each do "update DB, then set cache", their cache writes can arrive in the opposite order of their DB commits, leaving the older value cached forever (until TTL). Deletes are idempotent and order does not matter: the next reader loads whatever the DB says now.

5. Protecting the database when the cache fails

A failed node turns its whole key range into misses. With a 95% hit ratio, that slice's database load jumps 20x. Defences: replicas with fast failover; a small gutter pool (Meta's paper: a few idle servers that take over a failed server's keys with short TTLs, so misses do not go straight to the DB); circuit breakers and load shedding in the app; and a cache warm-up plan before you put a new cluster in front of real traffic.
