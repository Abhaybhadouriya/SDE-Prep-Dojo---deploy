The story

Explain like I'm 5

You are doing homework and keep needing the same facts from a big book in the library cupboard at the end of the hall. Walking there every time is slow. So you write the facts you use most on sticky notes and stick them on your desk. Now most answers take one second instead of one minute.

Your desk is small, so when it is full you throw away the note you have not looked at for the longest time. Some notes go out of date (the book got a new edition), so each note has a little "use until Friday" date on it. And when the whole class shares one big desk, the teacher splits the notes into piles by the first letter, so everyone knows exactly which pile to check.

A cache is a small, fast store that keeps copies of data that lives somewhere slower (the source of truth, usually a database). A distributed cache spreads that store over many machines so it can hold more data and serve more requests than one machine could. Redis and Memcached are the two famous ones; Valkey is the open-source fork of Redis run by the Linux Foundation.

New words, defined once:

  • Hit / miss - a hit means the data was in the cache; a miss means we had to go to the database. Hit ratio = hits / all lookups.
  • TTL (time to live) - how long an entry may stay before it expires on its own.
  • Eviction - throwing entries out when memory is full (for example the least recently used one, LRU).
  • Invalidation - deleting or updating a cache entry because the real data changed. Famously the hardest part.
  • p99 latency - the time within which 99% of requests finish. "p99 under 1 ms" means only 1 in 100 requests is slower than 1 ms.

From your world

You already know caches: CPU L1/L2, the TLB, and the FIB cache on a line card. Same ideas, same words: hit ratio, eviction policy, working set, and the cost of a miss. The difference is the miss path: a TLB miss walks page tables in nanoseconds; a web-cache miss is a database query of milliseconds, and ten thousand misses at once can take the database down. Where this breaks: CPU caches are kept coherent by hardware (MESI). A distributed cache has no coherence protocol with the database; your code is the coherence protocol, which is why invalidation is hard.

Reported in the wild: a Microsoft SDE-2 candidate reported a 75-minute HLD + LLD round on a "distributed LRU cache" with O(1) operations. Meta, Amazon and Flipkart interviews use caching as a follow-up in almost every design. The interviewer wants to hear partitioning, eviction, replication, and then hot keys, stampedes and stale data.

This page is about a cache where losing data is acceptable. If losing data is not acceptable, you are designing a database: see Distributed Key-Value Store (Dynamo).
