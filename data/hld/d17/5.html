Architecture

The cluster has many nodes, each owning part of the key space, each with a replica in another zone. Clients find the right node either by themselves (smart client) or through a proxy. The application uses the cache-aside pattern (also called lookaside): the app, not the cache, talks to the database.

  1. Route. The smart client hashes the key to one of 16,384 hash slots and looks up which node owns that slot in its cached slot map. No proxy hop, no central lookup.
  2. Read: miss. The client asks node C for user:42. Not there (first time, expired, or evicted).
  3. Read from the database. The application, not the cache, queries the source of truth. This is what "cache-aside" means.
  4. Fill. The app writes the value into the cache with a TTL (here 300 s). The TTL is the safety net: even if an invalidation is lost, staleness is bounded.
  5. Read: hit. The next reads are served from RAM in well under a millisecond, and the database never sees them.
  6. Write. On update, the app first commits to the database, then deletes the cache key (not updates it). The next read misses and refills with fresh data. Deleting is idempotent and avoids racing two writers' values.
  7. Resharding. If slot 15880 has moved to a new node D, node C answers MOVED 15880 <D's address>. The client retries at D and refreshes its slot map. During a live migration, ASK redirects are used for keys already copied.
  8. Failure. If C dies, the remaining primaries notice through the cluster gossip bus (gossip = nodes periodically exchange "who is alive" messages with a few random peers, like OSPF hellos but peer-to-peer, so news spreads to everyone in a few rounds), agree that C is failed, and its replica C' is promoted to own the slots. Writes acked by C but not yet copied to C' are lost: replication is asynchronous.

Write strategies compared

StrategyHow it worksGood forRisk
Cache-aside (lookaside)App reads cache, on miss reads DB and fills; on write updates DB and deletes keyThe default for most read-heavy appsStale window; race on fill (deep dive 4)
Read-throughCache itself loads from DB on missUniform loading logic, libraries like CaffeineCache must know the DB
Write-throughWrite goes to cache and DB synchronouslyData read right after writeSlower writes; caches data nobody reads
Write-behind (write-back)Write to cache, flush to DB later in batchesVery write-heavy counters, metricsData loss if the cache node dies before flushing
Write-aroundWrite to DB only; cache fills on readData written once, rarely readFirst read is always a miss

Trade-off sentence: "I would pick cache-aside with delete-on-write because it is simple and the cache can fail without breaking writes; the cost is a short stale window and a refill miss after each write; if stale reads become a problem I would add CDC-driven invalidation or leases."
