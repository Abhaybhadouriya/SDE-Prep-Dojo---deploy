Key APIs

Applications talk to the cache through a client library, not raw HTTP: a binary or text protocol over long-lived TCP connections, because a 1 ms budget has no room for HTTP overhead. The logical API:

get(key)                        -> value | MISS
set(key, value, ttl_seconds)    -> OK
delete(key)                     -> 1 | 0
mget([k1, k2, ...])             -> [v1 | MISS, ...]       # one round trip per node
incr(key, by)                   -> new integer value      # atomic counter
cas(key, value, version)        -> OK | CONFLICT          # optimistic update
lease_get(key)                  -> value | (MISS, lease_token)   # anti-stampede (Memcache-style)

Here is the same thing with Redis. Start a local Redis with Docker (see Running & Managing Containers) and try it:

docker run -d --name cache -p 6379:6379 redis:8
docker exec -it cache redis-cli
127.0.0.1:6379> SET user:42:name Asha EX 60
OK
127.0.0.1:6379> GET user:42:name
"Asha"
127.0.0.1:6379> TTL user:42:name
(integer) 57
127.0.0.1:6379> INCR page:home:views
(integer) 1
127.0.0.1:6379> SET lock:order:9 worker-3 NX PX 30000
OK
127.0.0.1:6379> SET lock:order:9 worker-5 NX PX 30000
(nil)
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"

Two lessons hide in that output. SET ... NX (only if not exists) is how people build a simple lock or a "first writer wins" guard; the second writer gets (nil). And the default eviction policy is noeviction: when memory is full, Redis rejects writes with an error instead of evicting. For a cache you must change it (for example to allkeys-lru or allkeys-lfu) and set maxmemory.
