The ladder: naive to best

Rung 0 - Bytes in the database

A BYTEA or BLOB column is fine for a 20 KB avatar in a small app. It breaks as files grow: rows get huge, backups and replicas carry every byte, and the database's expensive storage and memory is spent on data nobody queries. Breaks at: roughly megabytes per object or gigabytes in total.

Rung 1 - Split metadata from bytes

Store the bytes in an object store under a key, and store a metadata row in your database: file_id, owner_id, blob_key, size, content_type, sha256, status, created_at. Every query (list my files, search by name, permissions) hits the small row; only an actual download touches the blob. Dropbox describes exactly this split: its Magic Pocket system stores only file contents (as blocks), while file and user metadata live elsewhere and file changes are recorded in a separate journal. The S3 design applies the same split inside the storage system itself.

Breaks when: bytes still flow through the API to reach the store.

Rung 2 - Presigned URLs (the valet key)

Microsoft's Azure guide names this the Valet Key pattern: give the client a token that grants time-limited access to one specific resource for only the needed operation, so the client moves data directly and the application stays out of the data path. Creating the key is just signing a string, so it is cheap and needs no call to the store.

  • Scope tightly. One bucket, one object key you chose (never the client's file name as the key), one verb (PUT to upload, GET to download). Azure's sample grants only create permission (no overwrite, so the token is effectively single-use) for about three minutes.
  • Expire quickly. AWS allows S3 presigned URLs up to 7 days with Signature V4 (SigV4, AWS's request-signing scheme: an HMAC over the method, path, chosen headers and expiry, so changing any of them breaks the signature) from the SDK or CLI (1 minute to 12 hours from the console), and a URL signed with temporary credentials dies when those credentials do. S3 checks expiry when the request starts: a download that began just before expiry finishes, but a retry after expiry fails.
  • Treat it as a bearer token. Anyone holding the URL can use it until it expires. Use HTTPS, keep the URLs out of logs, and record which user each was issued to, because S3's logs identify the signer, not the person who used it.
  • Constrain size and type. S3 presigned POST policies support a content-length-range; for a presigned PUT you can sign the exact Content-Length and Content-Type as signed headers, so S3 rejects an upload of any other size or type. Use POST when you need a size range rather than an exact size. Always validate after upload.
  • Browser uploads need CORS on the bucket, since the page and the bucket are different origins. (CORS, cross-origin resource sharing, is the browser rule that a page from site A may only call site B if B's response headers say A is allowed. An origin is scheme + host + port, so https://app.example.com and the bucket's host are different origins.) Allow PUT from your site's origin, and for multipart uploads add ETag to ExposeHeaders: each UploadPart response returns its ETag in a response header, and browsers hide headers from JavaScript unless the CORS rule exposes them. Without it the page cannot read the part ETags it must send to CompleteMultipartUpload. The "Bucket CORS" tab in the Kafka/Kubernetes/Docker section below shows the rule.

Breaks when: the file is large. A single 2 GB PUT that fails at 95% starts again from zero. AWS recommends considering multipart uploads once an object reaches about 100 MB.

Rung 3 - Multipart and resumable uploads

Split the file into parts, upload them independently (and in parallel), and assemble at the end. S3's limits: up to 10,000 parts per upload, each 5 MiB to 5 GiB (the last part can be smaller). Step through a full presigned multipart upload:

  1. Ask. The client sends only metadata (size, type, a content hash). The API checks auth and quota, and writes a metadata row with status PENDING.
  2. Initiate. The API starts a multipart upload on the blob store (gets an upload_id) and returns presigned URLs, one per part. The API never sees a byte of video.
  3. Upload parts in parallel. The client sends parts straight to the store. Each part's response carries an ETag (a checksum) that the client keeps. ByteByteGo's example splits a 1.6 GB file into eight 200 MB parts.
  4. Failure. The connection drops. Nothing is lost except the part in flight. The client (or the API, from its record of confirmed parts) works out which parts are done.
  5. Resume. Only missing parts are re-sent. This is the whole point: a failure at 99% costs 1%.
  6. Complete. The client sends the list of part numbers and ETags; the store assembles the object in part order and verifies each part.
  7. Sync state. The store emits an object-created event; a consumer flips the metadata row to UPLOADED and queues follow-up work (virus scan, thumbnail, transcode). Hello Interview's YouTube breakdown uses exactly this: one object-level event starts processing.

Two ways to know which parts are done after a crash:

  • Ask the store. S3's ListParts returns uploaded parts for an upload_id (paginated: at most 1,000 parts per call, so a larger upload needs follow-up calls with PartNumberMarker set from NextPartNumberMarker). Simple, but the client needs the upload_id saved locally.
  • Track in your DB. Hello Interview's YouTube design keeps a chunk list per video in metadata, each with a fingerprint and status; the client reports part number + ETag after each part. This works across devices and lets the server show progress.

Outside S3, the open tus protocol standardises resumable uploads over plain HTTP: POST creates an upload and returns its URL, HEAD returns the current Upload-Offset, and PATCH appends bytes from that offset (a wrong offset gets 409 Conflict). Extensions add per-chunk checksums, server-side expiry of abandoned uploads, and parallel partial uploads that are concatenated. Google Cloud Storage offers its own resumable upload sessions.

Clean up abandoned uploads. Parts of an upload that is never completed still sit in the bucket and are billed. AWS recommends a lifecycle rule with AbortIncompleteMultipartUpload (their example uses 7 days). Likewise, a periodic job should expire PENDING metadata rows whose upload never finished.

From your world

Why parallel parts are faster on one connection's worth of bandwidth: a single TCP flow is limited by its window divided by RTT (bandwidth-delay product), and one loss halves its congestion window. Several flows in parallel fill the pipe and a loss hurts only one. It is the same reason link aggregation and ECMP spread flows. And a per-part ETag is a per-frame CRC: detect a bad unit and resend just that unit, like selective ACK instead of go-back-N.

Rung 4 - Content-addressed chunks and dedup

For sync products (Dropbox, OneDrive, Google Drive) go one step further: split files into fixed-size blocks and name each block by the hash of its content. Dropbox's Magic Pocket stores blocks of up to 4 MB, compressed and encrypted, keyed typically by their SHA-256 hash; blocks are immutable once written, and the put path checks a block index before storing.

  • Dedup across versions and users for free: same bytes, same hash, one copy. (Cross-user dedup has privacy implications - it can leak "someone already has this file" - so many products dedup only within one account.)
  • Integrity for free: the name is the checksum.
  • Immutable blocks are easy to cache, replicate and erasure-code. Deletion becomes garbage collection of blocks no file version references.
  • Fixed vs content-defined chunking: fixed 4 MB blocks are simple, but inserting one byte at the front shifts every boundary. Content-defined chunking (rolling hash, as in rsync-style tools) keeps boundaries stable. Mention it as a refinement.

Docker does this too. A container image is a list of layers, and each layer is a blob named by its sha256 digest. docker push asks the registry which digests it already has and uploads only the missing layers, in chunks, then commits by digest. That is why rebuilding an image with one changed layer pushes in seconds. See Images & Layers.

Rung 5 - Downloads: CDN, signed URLs, range requests

  • Public content (product images, avatars): put a CDN in front with long cache lifetimes and versioned keys (img/sku123_v4.jpg), so a change is a new key and you never purge. See Scaling Reads.
  • Private content: keep the bucket private; serve through the CDN with signed URLs or signed cookies (CloudFront supports both, and lets only the CDN read the origin), or a presigned GET straight from the store for low-volume cases.
  • Range requests: Range: bytes=start-end returns 206 Partial Content. Players seek, download managers resume, and clients fetch several ranges in parallel. Video goes further: transcode into short segments (HLS/DASH: HTTP streaming formats where a video is cut into segment files of 2-10 seconds each, plus a playlist file that lists them; the player fetches the playlist, then segments one by one, switching quality between segments) so each segment is a small, cacheable object (Video Streaming).
  • Pre-position the hot set: Netflix's Open Connect fills its appliances inside ISP networks ahead of demand, instead of pulling on a miss.
