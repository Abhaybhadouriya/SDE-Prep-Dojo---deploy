Interview: phrases, traps and questions

Phrases that land: "Metadata in the database, bytes in object storage." - "The API hands out a presigned URL scoped to one key, one verb, a few minutes." - "Multipart so a failure at 99% costs one part." - "Status flips on the storage event, and a reconciler catches anything missed." - "Downloads through a CDN with signed URLs and range requests."

Traps: streaming uploads through the API; storing files in the DB; trusting the client's "upload done" call; using the user's filename as the object key (collisions, path tricks); long-lived or over-broad presigned URLs; serving user uploads without scanning; forgetting orphan cleanup; sending blobs through Kafka.

How would you let users upload 10 GB videos reliably from mobile phones?

The client asks the API to start an upload with size, type and hash. The API checks quota, writes a PENDING row, starts a multipart upload and returns presigned part URLs (for example 10 MB parts: 1,000 parts, well under S3's 10,000 limit). The client uploads parts in parallel, keeps ETags, and on reconnect asks which parts are done and sends only the rest. Complete assembles the object; the storage event marks the row UPLOADED and queues transcoding. A lifecycle rule aborts abandoned uploads.

How to answer

Control plane vs data plane first, then resumability, then state sync. Do the parts arithmetic aloud.

Likely follow-ups
  • The app is killed - where does it remember the upload ID?
  • How do you show progress across devices?
  • What part size would you choose on 3G vs Wi-Fi?
What is a presigned URL and how do you keep it safe?

A URL carrying a signature made with the server's credentials that authorises one operation (PUT or GET) on one object until an expiry time. Anyone holding it can use it, so: scope it to a server-chosen key and a single verb, expire it in minutes, issue it only after authenticating the user, deliver over HTTPS, keep it out of logs, record who it was issued to, and validate the object after upload. Microsoft calls this the Valet Key pattern.

How to answer

Define it, say "bearer token", then list scope, time, audit, validate.

Likely follow-ups
  • How do you stop someone uploading 50 GB with a URL meant for 5 MB? (presigned POST with content-length range, or check size after and delete)
  • Can you revoke one? (rotate the signing credentials; short expiry is the real defence)
The upload fails at 99%. What does the user experience, and how does your design recover?

With multipart, only the in-flight part is lost. On reconnect the client calls GET /uploads/{id}; the server (from its part table or S3 ListParts) returns completed part numbers, and the client re-sends the missing ones and completes. The user sees the progress bar resume from 99%. If presigned URLs expired meanwhile, the client requests fresh URLs for the remaining parts only.

How to answer

Name the two sources of truth for "which parts are done" and pick one. Cover expired URLs.

Likely follow-ups
  • The client lost the upload ID - now what?
  • Two devices resume the same upload at once?
Design how Dropbox / OneDrive avoids re-uploading a 1 GB file when the user edits one paragraph.

Split the file into blocks (Dropbox uses up to 4 MB) and name each by its SHA-256. The client hashes the new version, asks the server which hashes it lacks, uploads only those blocks, then commits a new file version as an ordered list of block hashes in the metadata journal. Unchanged blocks are shared between versions. Content-defined chunking keeps block boundaries stable when bytes are inserted.

How to answer

Content addressing, the "which do you have" round trip, version = list of hashes. Mention dedup and integrity as side benefits.

Likely follow-ups
  • Should dedup work across users? (privacy leak; often per-account only)
  • How do you garbage-collect blocks?
  • See File Sync
Your metadata DB says a file is uploaded but the blob is missing (or the reverse). How do you design so this cannot persist?

There is no shared transaction, so design for convergence. Create the row first as PENDING; flip it only from the store's object-created event (not the client); on delete, mark the row deleted first and remove the blob later. A reconciler periodically lists recent objects and pending rows: promotes rows whose blob exists, expires rows with no blob, and deletes orphan blobs past a grace period. Make event handling idempotent since events can repeat.

How to answer

Enumerate the four inconsistent states and the fix for each. That table impresses.

Likely follow-ups
  • What if the storage event is lost?
  • How long a grace period, and why?
How do you serve private photos fast to users around the world?

Keep the bucket private. The API checks that the viewer may see the photo and returns a short-lived signed CDN URL (or sets signed cookies for a whole album). The CDN edge serves cached copies and is the only identity allowed to read the origin. Store several pre-resized variants with versioned keys so thumbnails are tiny and edits never need a purge.

How to answer

Separate "may you see it" (API) from "deliver it" (CDN). Mention variants and versioned keys.

Likely follow-ups
  • A user revokes sharing - how quickly does access stop? (URL expiry bounds it)
  • Signed URL vs signed cookie?
Users can upload anything. How do you protect other users and your systems?

Uploads land in a quarantine prefix or bucket that nothing serves. The object-created event triggers validation: real content type (magic bytes, not the extension), size limits, malware scan, image/video re-encoding to strip active content, and moderation where needed. Only after it passes is the object moved or marked servable. Serve user content from a separate domain so it cannot read your main site's cookies, with Content-Disposition for downloads. Rate-limit upload URL issuance per user.

How to answer

Quarantine, scan, then publish. Note that direct upload means you cannot scan inline, so the pipeline is mandatory.

Likely follow-ups
  • Scanning takes 2 minutes - what does the uploader see meanwhile?
  • Where does this run? (Long-running Tasks)
Why not just put the image bytes into the Kafka event so consumers have everything?

Kafka's default max message size is about 1 MB; large messages slow brokers, replication and every consumer, and they stay in the log for the whole retention period, multiplied by the replication factor. Use the claim-check pattern: store the bytes in object storage and publish a small event with the key, hash and size. Consumers fetch the blob only if they need it.

How to answer

Give the limit, the cost multiplier (retention x replication), then the claim-check fix.

Likely follow-ups
  • The blob is deleted before a slow consumer reads the event?
In a "design S3" round: how does the store itself keep 11 nines of durability without 3x the disks?

Erasure coding: split each object into k data shards and add m parity shards (Reed-Solomon); any k of the k+m shards rebuild it, so the overhead is (k+m)/k instead of 3x for triple replication. Place shards across disks, racks and availability zones so one failure domain never holds more than m. Detect bit rot with checksums and background scrubbing; repair quickly from surviving shards. S3 spreads objects across tens of drives and each customer thinly across many disks, so hot workloads do not create hot disks (each disk does only ~120 random IOPS).

How to answer

Replication vs erasure coding with the overhead maths, placement across failure domains, repair speed. Then the metadata plane.

Likely follow-ups
  • Erasure-coded reads are slower for small objects - what do you do? (replicate small or fresh objects, code later, like Dropbox)
  • See S3 design

Scenario: the API fleet keeps running out of memory on upload days

A HR portal lets employees upload documents and short videos. On appraisal week, API pods OOM and restart; uploads fail at random, and the team keeps raising the memory limit.

Weak answer: "Increase pod memory and add an HPA."

Strong answer: "The API is buffering file bodies, so memory scales with bytes in flight. Move bytes off the API: presigned PUT for small files and presigned multipart for videos, metadata row first, status from storage events, scanning in a worker queue. The API then handles small JSON calls and its memory stays flat. Add a lifecycle rule and a reconciler for abandoned uploads."

Likely follow-ups
  • Corporate proxy blocks the storage domain - fallback?
  • How do you migrate existing clients?

Scenario: the storage bill doubled but file count did not

A video app's object storage cost doubled in three months while the number of finished videos grew only 10%.

Weak answer: "Move to a cheaper storage class."

Strong answer: "Look for bytes nobody references: incomplete multipart uploads (billed until aborted - add the lifecycle rule), orphan blobs from failed metadata writes (reconciler), old renditions and intermediate transcode files (lifecycle expiry on the temp prefix), and duplicate uploads of the same file (hash on start and dedup). Then tier cold originals to an infrequent-access class."

Likely follow-ups
  • How would you find orphans in a bucket with a billion objects? (inventory report joined with the DB, not LIST calls)
