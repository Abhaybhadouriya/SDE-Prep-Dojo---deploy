Kafka, Kubernetes and Docker

  • Kafka carries references, not blobs. Kafka's default maximum message size is about 1 MB, and big messages hurt every consumer. Use the claim-check idea: put the bytes in object storage and send {file_id, blob_key, sha256, size} on the topic. Object-store events ("object created") can be bridged into Kafka so scanners, thumbnailers and transcoders each consume in their own group (Consumer groups, Why messaging).
  • Kubernetes runs the processing, not the storage of record. Transcode or scan jobs run as Jobs or autoscaled worker Deployments that pull a blob, process it, and write results back (Autoscaling). Pod volumes (PV/PVC) are block or file storage for scratch space, not the place for user files (K8s Storage). MinIO can run on Kubernetes as an S3-compatible store for on-prem or local practice.
  • Docker images are the content-addressed blob pattern in daily use: layers named by digest, chunked uploads to the registry, dedup across images (Images & Layers). Run MinIO with Compose to try presigned URLs locally (Compose).

import boto3, math, uuid
s3 = boto3.client("s3")
PART = 10 * 1024 * 1024                      # 10 MiB parts (min 5 MiB)

def start_upload(user_id, size, content_type):
    key = f"uploads/{user_id}/{uuid.uuid4()}"  # server-chosen key, never the file name
    db.insert_file(key=key, owner=user_id, size=size, status="PENDING")
    up = s3.create_multipart_upload(Bucket="media", Key=key, ContentType=content_type)
    n = math.ceil(size / PART)               # must be <= 10,000 parts
    urls = [s3.generate_presigned_url("upload_part",
              Params={"Bucket": "media", "Key": key,
                      "UploadId": up["UploadId"], "PartNumber": i},
              ExpiresIn=900)                 # 15 minutes per URL
            for i in range(1, n + 1)]
    return {"key": key, "upload_id": up["UploadId"], "part_size": PART, "urls": urls}
