Keeping metadata and blobs in agreement

Two systems, no shared transaction. Every failure leaves one of these states, and you must handle each:

StateHow it happensFix
Row PENDING, no blobClient gave upExpire after N hours; lifecycle rule aborts parts
Blob exists, row still PENDINGClient crashed before "complete", or event lostDrive status from the store's event, not the client; reconcile by listing recent objects
Blob exists, no row (orphan)Row creation failed or row deleted firstAlways create the row first; GC job deletes objects with no row after a grace period
Row says READY, blob missingBlob deleted before rowDelete order: mark row deleted, then delete blob; never the reverse

The rule: the metadata row is created first and is the source of truth for "does this file exist for users"; the blob store's event is the source of truth for "are the bytes there". A periodic reconciliation job compares the two. This is the dual-write problem from Distributed Transactions & Events in a new costume.

Durability and placement (what the store does for you)

Andy Warfield's write-up on running S3 gives the scale: millions of hard disks, each still only good for about 120 random I/Os per second. S3 spreads each object across tens of drives using erasure coding (k data shards plus m parity shards; any k of them rebuild the object), and spreads each customer's data thinly across many disks so one hot workload cannot overload a disk. Dropbox replicates fresh blocks to at least two zones within about a second of upload, then erasure-codes 1 GB buckets of blocks later for efficiency. You get this by choosing a real object store; in a "design S3" question you must explain it (S3 design, Choosing Storage).

What direct-to-store buys you
  • API fleet sized for requests, not bytes
  • Client-to-store full bandwidth, parallel parts
  • No long-held workers or temp disks
  • Durability and scale of the object store
What it costs
  • You cannot inspect bytes before they land: scan after
  • Size limits are hard to enforce on plain PUT URLs
  • Two systems to keep consistent
  • Leaked URLs are usable until expiry

Say this: "The API never touches the bytes. It authorises, writes a PENDING metadata row and hands out presigned multipart URLs. The client uploads parts in parallel and resumes failed parts. The store's object-created event flips the row and triggers processing. Downloads go through a CDN with signed URLs."
