Why should a 2 GB upload not pass through your API servers?

  1. HTTP cannot carry 2 GB
  2. It doubles bandwidth and ties up API workers and memory for the whole transfer
  3. Object stores reject uploads from servers
Direct upload with a presigned URL lets the API handle only a small control request; the store moves the bytes.

What is the S3 limit on parts in one multipart upload?

  1. 100
  2. 1,000
  3. 10,000
  4. Unlimited
Up to 10,000 parts, each 5 MiB to 5 GiB except the last.

Who should flip a file's status from PENDING to UPLOADED?

  1. A consumer of the blob store's object-created event, backed by a reconciler
  2. The client, when it says it is done
  3. Nobody; status is not needed
The client may crash or lie. The store's event reflects the bytes actually being there; a reconciler catches lost events.

A presigned URL is best described as...

  1. A permanent public link
  2. A user's password in a URL
  3. An encrypted copy of the object
  4. A time-limited bearer token for one operation on one object
Whoever holds it can use it until it expires, so scope it narrowly and keep the expiry short.

How does a sync client avoid re-uploading a 1 GB file after a small edit?

  1. It compresses the file harder
  2. It uploads only blocks whose content hash the server does not already have
  3. It uploads the diff as a Kafka message
Content-addressed blocks: unchanged blocks keep the same hash and are already stored.

Your bucket is growing with parts from uploads users abandoned. What is the standard fix?

  1. A bigger bucket
  2. Delete the metadata rows
  3. A lifecycle rule with AbortIncompleteMultipartUpload
Incomplete multipart parts are stored and billed until aborted; the lifecycle rule aborts them after N days.
