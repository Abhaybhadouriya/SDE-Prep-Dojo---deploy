Back-of-envelope estimation

Use round numbers and say each assumption. The method is from Back-of-Envelope Estimation.

500Kconcurrent games (peak)
1Mopen WebSockets
~133Kmoves/sec (peak)
~1.7Knew games/sec
  1. Connections 500K games x 2 players = 1M concurrent WebSockets. If one gateway node comfortably holds about 50K connections (a planning assumption, tune it with a load test), that is about 20 gateway nodes, so plan 30 for headroom and rolling deploys.
  2. Game length A 3+0 game lasts at most 6 minutes of clock (3 per side). Many games end early (resignation, checkmate, a flag falling), so assume an average of about 5 minutes of wall time and about 80 half-moves (plies) per game. This is an assumption; a shorter average raises every rate below.
  3. Move rate 500K games x 80 moves / 300 s = about 133K moves per second at peak. Sanity check against reality: Chess.com reported about 16,000 moves per second on average during its record month in January 2023, with 31.7M games on one day. Our peak target is roughly 8x that average, which is a sensible design ceiling.
  4. Bandwidth A move message (game id, ply number, move like e2e4, clock values) is about 100 bytes of JSON. In: 133K x 100 B = 13 MB/s. Out: each move goes to both players (the mover gets an ack with the new clocks), so about 27 MB/s plus framing. Tiny for a datacentre, which tells you the hard part is connection count and routing, not bandwidth.
  5. Game starts If games last about 5 minutes and 500K are always live, then 500K / 300 s = about 1,700 games start per second, so matchmaking must pair about 3,400 queue entries per second.
  6. Live state in memory A board as a FEN string (Forsyth-Edwards Notation: a one-line text snapshot of where every piece is, under 100 bytes), move list (80 x 5 bytes) and two clocks are under 2 KB per game. 500K x 2 KB = 1 GB. All live games fit in the RAM of a handful of servers.
  7. Storage Take 30M finished games per day (close to Chess.com's record day). Each archived game is about 1 KB (moves in compact PGN, Portable Game Notation, which is the plain-text list of moves; plus players, ratings, result, timestamps). 30M x 1 KB = 30 GB/day, about 11 TB/year before replication. Lichess stores over 12 billion games in MongoDB, so the archive is a write-once, read-rarely, append-heavy store.
  8. Leaderboard 10M players x about 32 bytes (id + score) in a Redis sorted set = about 320 MB, plus Redis overhead. systemdesign.one estimates 2.2 GB for 70M players with the same per-record size, so 10M fits on one node with replicas.

What the numbers tell you: storage is small, bandwidth is small, memory is small. The interesting problems are 1M long-lived connections, keeping each game on one owner, 1M ticking clocks, and a 1,700-per-second matchmaking race.
