Deep dives

1. Never match a player into two games

Matchmaking runs on several instances for availability. At 3,400 queue entries per second, two matchmakers will sometimes pick the same waiting player at the same moment. This is a classic contention problem (see Dealing with Contention).

  1. Naive Read the queue, pick two players, remove them, create the game. Two instances can both read Bob before either removes him. Bob gets two games.
  2. Better: atomic claim Do the whole "find neighbour + remove both" step in one Redis Lua script. Redis runs a script atomically on a single shard, so only one script can remove Bob. ZREM returns 1 to exactly one caller.
  3. Belt and braces: player status lock Before creating the game, set player:{id}:status from searching to in_game:{gameId} with a compare-and-set. If either set fails, roll back and requeue the other player.
  4. Scale out Shard the queue by time control + region (blitz-EU, blitz-NA, bullet-EU). Each shard is a separate sorted set with one owner, so no cross-shard pairing is needed. Hello Interview asks what to do when matchmaking outgrows Postgres; the answer is this: an in-memory sorted structure per bucket, partitioned so each bucket has a single writer.

The caller must already be in the queue (the join API does ZADD mm:blitz:eu <rating> <userId>). The script then removes the caller and the candidate together, and it first checks that the caller is still waiting. Without that first check, a subtle bug remains: Bob's script removes Alice and Bob, then Alice's own matchmaker loop runs the script for Alice, finds Carol and matches Alice a second time. Guarding only the candidate is not enough; you must guard both sides.

-- KEYS[1] = mm:blitz:eu   ARGV[1] = my userId  ARGV[2] = my rating  ARGV[3] = window
if not redis.call('ZSCORE', KEYS[1], ARGV[1]) then
  return 'ALREADY_MATCHED'                     -- someone else already paired me
end
local lo = tonumber(ARGV[2]) - tonumber(ARGV[3])
local hi = tonumber(ARGV[2]) + tonumber(ARGV[3])
local cands = redis.call('ZRANGEBYSCORE', KEYS[1], lo, hi, 'LIMIT', 0, 5)
for _, c in ipairs(cands) do
  if c ~= ARGV[1] then
    if redis.call('ZREM', KEYS[1], c, ARGV[1]) == 2 then  -- both removed, atomically
      return c                                   -- opponent found
    end
  end
end
return nil                                     -- keep waiting, widen window later

Because Redis runs the whole script without interleaving other commands, the == 2 check is a safety net: inside one script it always holds once the caller passed the first guard. The caller then sets both players' status keys (step 3 above) before creating the game.

The rating window should widen with wait time: start at +/- 50, add 25 every 3 seconds, cap at +/- 400. That trades match quality for wait time, and it is a knob product owners love to tune.

2. Scaling to 500K concurrent games on many servers

Each game must have exactly one owner, and every message about it must reach that owner. Options:

ApproachHowGoodBad
Stateless servers + DB lock per moveAny server loads the game from Redis, validates, writes back with a version checkSimple failoverAn extra round trip and a contention point on every move; clocks need a separate timer service
Sticky owner (actor per game)Consistent hash on gameId picks the game server; it keeps the game in memory as an actor with its own timerOne writer, zero locks, microsecond moves, timers are localNeed routing, ownership leases (a lease is a lock with an expiry: you hold it only while you keep renewing it) and journal-based failover
Connect players straight to the game serverMatchmaker returns the owner's address; clients open a socket to itOne fewer hopConnection storms when a server restarts; hard to put behind a normal LB; mixes connection and game concerns

Pick the sticky owner. To avoid two owners after a network split, the owner holds a lease for its hash range (for example in etcd or ZooKeeper) and writes a fencing token (the lease epoch) with every journal append. A stale owner that lost its lease gets rejected by the journal. Redis does not check epochs by itself, so the append is a Lua script: read the game's stored epoch, refuse if the writer's epoch is lower, otherwise XADD. Because the script is atomic, the check and the append cannot be split. One more honest caveat: Redis replication is asynchronous, so if the Redis primary fails over, the last few acknowledged moves can be lost. If that is unacceptable, call WAIT 1 <ms> (wait until one replica has the write) before acking, or use a quorum log such as a Raft-backed store. This is the same idea as in Distributed Lock Service and Replication, Consensus & Coordination.

Real-world check: Chess.com ran its live server on literally one machine in Virginia for years and its own help centre says that. Its January 2023 post describes rewriting the live server "from a single server to a distributed service". Its newer Realtime Chess Network now carries more than 99.7% of live games, and its Google Cloud post says gameplay nodes are deployed around the world so each player connects to a nearby node. One machine goes very far; you shard when you must.

3. Fair clocks over an unfair network

The server owns both clocks. When a move arrives, the server computes elapsed = now - turnStartedAt and subtracts it from the mover's clock. But part of that elapsed time was the move travelling over the network, not the player thinking. Someone on a 300 ms mobile link would be punished on every move.

So platforms add lag compensation. Chess.com documents its "lag forgiveness" in detail: travel time to and from the server is credited back, up to a cap per move with a small bank that refills every two moves.

Time controlAuto forgiveness per moveBank (refills every 2 moves)
Rapid500 ms1000 ms
Blitz300 ms400 ms
Bullet200 ms100 ms

How to measure lag? The gateway pings the client every few seconds and keeps a moving average of round-trip time; or the client reports its own measured think time and the server trusts it only up to the cap. The cap is the whole point: you can forgive lag, but you cannot let a client invent time. Lichess similarly says its compensation limits depend on the time control and on lag already compensated.

Detecting flag fall: with 500K games there are up to 500K running clocks. Do not poll. Each game actor schedules one timer at turnStartedAt + remaining; a move cancels it and schedules the opponent's. Implement with a hashed timing wheel: O(1) insert and cancel.

From your world

This is the Linux kernel timer wheel again: millions of TCP retransmit timers that almost always get cancelled before they fire. Chess clocks have the same shape: a timer per game, armed on each move, cancelled on the next move, firing only on a timeout. Same data structure, same O(1) arm/cancel.

4. Reconnection and server crashes

  1. Normal play: server 7 owns game g_9c2 under lease epoch 4 and appends every move to the journal before acking.
  2. Server 7 dies (OOM, node drain, kernel panic). Its lease in etcd expires after a few seconds. Clocks are frozen for the outage; the server records the pause.
  3. The hash ring moves that range to server 9. It takes the lease with epoch 5, reads the journal (22 plies and clock values), rebuilds the board and restarts the timer of the side to move. Any late write from server 7 carries epoch 4 and is rejected.
  4. Clients reconnect (with jittered backoff) and send sync lastPly. Server 9 sends the missing plies and current clocks. The game continues.

For a simple network drop on one side, nothing moves: the game stays on its owner, the player's clock keeps running (that is fair, it is their turn), and the opponent sees "Bob disconnected, can claim win in 30 s". The reconnect uses sync to catch up.

5. The leaderboard at 10M players

Use a Redis sorted set: ZADD lb:blitz 1734 u_42 on each rating change, ZREVRANGE lb:blitz 0 99 WITHSCORES for the top 100, ZREVRANK lb:blitz u_42 for "my rank". ZREVRANK is O(log n); ZREVRANGE 0 99 is O(log n + 100), because it also walks the 100 members it returns. systemdesign.one notes that computing rank in a relational table needs a COUNT(*) WHERE rating > x style query that can take about 10 seconds on 10M rows even with indexes, which is why the sorted set wins.

Two traps. First, update the leaderboard from the rating service, after the rating transaction commits, so the two never disagree for long. Second, many players share the same rating, so break ties (for example score = rating x 1010 + (1010 - epochSeconds), so whoever reached the rating first ranks higher and nothing wraps; ratings in the low thousands keep this well inside a double's 53-bit exact range) or accept "tied rank". Rebuild the set nightly from Postgres to repair drift. More detail in Real-time Leaderboard.
