Key APIs

Two styles. Plain REST over HTTPS for things that happen once (join queue, read leaderboard). A WebSocket (a long-lived, two-way connection that starts as an HTTP request and then upgrades) for the game itself, because the server must push the opponent's move the instant it arrives. See API Design & Client-Server Communication and the Real-time Updates pattern.

# join the matchmaking queue (idempotent per user + time control)
POST /v1/matchmaking/queue        { "timeControl": "3+0" }
  -> 202 { "ticketId": "t_81f", "status": "SEARCHING" }

DELETE /v1/matchmaking/queue      # cancel search

# leaderboard
GET /v1/leaderboard?timeControl=blitz&limit=100
GET /v1/leaderboard/me?timeControl=blitz      -> { "rank": 48211, "rating": 1734 }

# finished games
GET /v1/games/{gameId}            -> players, result, PGN
// client -> server (an intent, not a fact)
{ "type": "move", "gameId": "g_9c2", "ply": 23, "uci": "g1f3" }
{ "type": "resign", "gameId": "g_9c2" }
{ "type": "sync", "gameId": "g_9c2", "lastPly": 21 }

// server -> client (facts, with server clocks)
{ "type": "matched", "gameId": "g_9c2", "color": "white", "opponent": {"id": "u_7", "rating": 1712} }
{ "type": "moved", "gameId": "g_9c2", "ply": 23, "uci": "g1f3",
  "clocks": { "white": 141250, "black": 152900 }, "serverTs": 1763890000123 }
{ "type": "rejected", "gameId": "g_9c2", "ply": 23, "reason": "ILLEGAL" }
{ "type": "gameOver", "gameId": "g_9c2", "result": "0-1", "reason": "TIMEOUT" }

Two details interviewers look for. First, every move carries a ply number (the half-move count). The server accepts ply 23 only if the game is at ply 22 and it is that player's turn, so a retried or duplicated message is harmless. That property is called idempotent: safe to retry, because doing it twice has the same effect as doing it once. The queue join is idempotent too (joining again while already searching returns the same ticket). Second, the server replies with clock values in milliseconds; clients just render them and count down locally between messages.

From your world

The ply number is the TCP sequence number of the game. The server keeps "next expected ply"; anything older is a duplicate and gets a re-ack, anything from the future is out of order and is rejected. The sync message with lastPly is like a selective ACK on reconnect: "I have up to 21, send me the rest".
