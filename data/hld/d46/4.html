Data model

Split data by how hot it is. Live game state is tiny and hot, so it sits in memory on the owner game server and is journaled to a fast log. Finished games are cold, written once, and go to a scalable document or wide-column store. Users and ratings need transactions, so they go in a relational database. Rankings need sorted order, so they go in a Redis sorted set. Chess.com's 2023 outage post is a lesson here: its overloaded database held both user and gameplay data, and one of the fixes was to separate them.

CREATE TABLE ratings (
  user_id     BIGINT      NOT NULL,
  perf        TEXT        NOT NULL,          -- 'blitz', 'bullet', ...
  rating      REAL        NOT NULL DEFAULT 1500,
  rd          REAL        NOT NULL DEFAULT 350, -- rating deviation (uncertainty)
  volatility  REAL        NOT NULL DEFAULT 0.06,
  games       INT         NOT NULL DEFAULT 0,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, perf)
);

CREATE TABLE processed_games (            -- idempotency for rating updates
  game_id     TEXT PRIMARY KEY,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Glicko-2 is the rating system Lichess and Chess.com use. Besides a rating it keeps a rating deviation (RD), the uncertainty of the rating, which starts at 350 for a new player, and a volatility that starts at 0.06. A 95% confidence range is roughly rating +/- 1.96 x RD. Matchmaking can use RD: a new player with a wide range can be matched more loosely.
