Where Kafka, Kubernetes and Docker fit

📨

Kafka

Topic game-finished, keyed by gameId. Consumers: rating service, archiver, anti-cheat, analytics. Not on the move path: a move must take milliseconds and only two people care about it.

 ☸️

Kubernetes

Gateways are a Deployment behind a Service with long connection drain. Game servers are a StatefulSet (stable names for the hash ring). Use a PodDisruptionBudget and a preStop hook that hands games off before a node drains.

 🐳

Docker

Each service ships as a small image. The chess rules library is a pure dependency baked into the game server image, versioned so a rules fix rolls out like any other release.
  • Why Kafka for game-end only: the finished-game event is the system of record for "what happened". Replaying it rebuilds ratings and the leaderboard after a bug. That is the event-driven idea from Distributed Transactions & Event-Driven Data. Use acks=all and an idempotent producer; consumers dedupe on gameId (see Delivery Semantics).
  • Rolling deploys with live sockets: set terminationGracePeriodSeconds long enough (for example 10 minutes, more than one blitz game) for gateways so most games finish naturally; the client reconnects to another gateway for the rest. For game servers, move ownership first, then stop.
  • Autoscaling: scale gateways on connection count, not CPU; scale game servers on live games per pod (a custom metric). See Scheduling & Autoscaling.
