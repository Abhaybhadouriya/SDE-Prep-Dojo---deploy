Architecture: one game, start to finish

Click Next or Play. The flow below is close to how Lichess is built: its README says WebSocket traffic is handled by a separate server (lila-ws) that talks to the main application through Redis, and chess rules live in a separate pure library (scalachess).

  1. Connect. Alice and Bob open the app. A layer-4/7 load balancer spreads WebSocket connections over stateless-ish gateway nodes. Gateways only hold sockets; they own no game logic.
  2. Queue. Both press "Play 3+0". The matchmaker adds them to the sorted set mm:blitz:eu with score = rating, then looks for a neighbour within a rating window (for example +/- 50, widening every few seconds of waiting).
  3. Pair and place. The matchmaker atomically claims both players (deep dive 1), picks a game id, and asks the cluster which game server owns that id (consistent hash of gameId: every node hashes the id onto the same ring, so all agree on the owner, and adding a server moves only a slice of games). That server creates the game in memory and starts White's clock.
  4. Play. Each move goes client -> gateway -> owner game server. The server checks it is the mover's turn and the ply number, validates legality with the rules library, applies it, stops one clock, starts the other, then pushes moved to both gateways (through pub/sub on the game's channel: publish to a named channel and every subscriber gets a copy, like sending to a multicast group), which push to both sockets.
  5. Journal. Before acknowledging, the server appends the move to the game's Redis stream (an append-only log). The append is a small Lua script that first checks the writer's lease epoch, so a stale owner is rejected (deep dive 2). If the server dies, a new owner replays the journal and the game continues.
  6. Finish. Checkmate, resign or flag fall (a timer fires on the server). The server writes one game-finished event to Kafka, keyed by gameId.
  7. Fan out. Independent consumers read the event: the rating service updates both Glicko-2 ratings in one Postgres transaction (idempotent by gameId); the archiver writes the PGN to the game store.
  8. Rank. The rating service updates the leaderboard sorted set with ZADD lb:blitz rating userId. A few seconds after the game, both players see their new rank.

From your world

Think of a chassis router. The gateways are line cards: they terminate sessions and move frames, but they hold no control state. The game server is the route processor for one game: single owner, single writer, all decisions made in one place. The pub/sub layer is the backplane. Choosing the owner by hashing gameId is like ECMP hashing a 5-tuple so every packet of a flow lands on the same path.
