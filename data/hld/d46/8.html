Trade-offs, bottlenecks and failure modes

DecisionChoiceAlternativeWhy
TransportWebSocketLong polling, SSE + POST, WebRTC peer-to-peerTwo-way, low overhead per message; peer-to-peer would let a client cheat and breaks the authoritative server
Game ownershipSticky actor per gameStateless + optimistic lockingSingle writer per game removes all contention on moves
Durability of live gamesAppend to Redis stream before ackWrite to Postgres per move; or no journal~133K writes/s is easy for a sharded Redis; no journal means a crash loses games
Rating updateAsync via KafkaInside the game server at game endGame server stays simple; ratings can be replayed; a few seconds of lag is fine
Matchmaking storeRedis ZSET per bucketPostgres table with index on ratingRange-by-score in memory, atomic Lua claims, 3,400 ops/s is trivial
Move validation on client tooYes, for instant feedbackServer onlyClient validation is UX; server validation is truth. Never trust the client
Strengths of this design
  • Moves never wait on a database
  • One owner per game, so no races
  • Crash recovery from the journal in seconds
  • Everything after game end is replayable from Kafka
Weak spots to mention
  • Hot gateway during a reconnect storm (add jittered backoff, admission control)
  • Redis journal is a dependency on the move path (replicate it; shard by gameId)
  • Async Redis replication: a primary failover can drop the last few acked moves unless you use WAIT or a quorum log
  • Lease expiry time = outage time for affected games (freeze clocks during it)
  • Cross-region players: put the game in the region between them, or in the higher-rated player's region

Failure mode from the real world: Chess.com's 2023 symptoms were 502 errors when the database was overloaded and live-server disconnections when the game server was overloaded. That is exactly the coupling this design avoids: the move path does not touch the main database at all.
