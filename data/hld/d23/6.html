1. Why naive approaches lose edits (must know)

  • Lock the document while someone types: correct but nobody else can type. Fine for a wiki, not for live collaboration.
  • Last write wins on the whole document: Alice's and Bob's full texts overwrite each other; one person's work vanishes.
  • Send raw positions and apply in arrival order: "delete at 2" means a different letter on a copy where someone already inserted before position 2. The copies diverge silently. This is exactly the bug OT and CRDTs fix.

2. Operational Transformation, worked by hand (SDE-2)

OT's core is one function: transform(a, b) = "rewrite operation a so it still means the same thing after operation b has already been applied". For single characters the rules fit on a napkin: if b inserted before a's position, shift a right by one; if b deleted before it, shift a left by one; if both deleted the same character, drop a; if both inserted at the same spot, break the tie consistently (e.g. lower user id goes first).

  1. Alice inserts "X" at position 1 on her copy: "aXbc". She shows it at once and sends it with baseRev 42.
  2. Bob, at the same moment, deletes position 2 (the "c") on his copy: "ab". He also sends it with baseRev 42.
  3. The server picks an order. Alice's op arrives first and becomes revision 43. Bob's op says baseRev 42, so the server knows it missed revision 43.
  4. Transform. Alice inserted at 1, which is before Bob's position 2, so everything after it moved one place right. Bob's op becomes "delete at 3" and is stored as revision 44.
  5. Converge. Alice receives rev 44 = "delete at 3" and gets "aXb". Bob receives rev 43 = "insert X at 1" (his own pending delete was already applied; his client transforms the incoming insert against it - 1 < 2, unchanged) and also gets "aXb".
# ot.py - minimal OT for single-character insert/delete. Run: python ot.py
from dataclasses import dataclass, replace

@dataclass
class Op:
    kind: str      # "ins" or "del"
    pos: int
    ch: str = ""
    site: int = 0  # tie-breaker for two inserts at the same position

def apply(doc, op):
    if op.kind == "ins":
        return doc[:op.pos] + op.ch + doc[op.pos:]
    return doc[:op.pos] + doc[op.pos + 1:]

def transform(a, b):
    """Rewrite a so it can be applied AFTER b (both made on the same doc)."""
    if b.kind == "ins":
        # same position: a delete always shifts past the new char;
        # the site tie-break is only for two inserts
        if b.pos < a.pos or (b.pos == a.pos and (a.kind == "del" or b.site < a.site)):
            return replace(a, pos=a.pos + 1)
        return a
    if b.pos < a.pos:                     # b is a delete before a
        return replace(a, pos=a.pos - 1)
    if b.pos == a.pos and a.kind == "del":
        return None                       # both deleted the same char
    return a

doc = "abc"
alice = Op("ins", 1, "X", site=1)
bob = Op("del", 2, site=2)
at_alice = apply(apply(doc, alice), transform(bob, alice))
at_bob = apply(apply(doc, bob), transform(alice, bob))
print(at_alice, at_bob)

# tie case: delete and insert at the SAME position
alice = Op("del", 1, site=1)          # delete "b"
bob = Op("ins", 1, "X", site=2)       # insert "X" before "b"
at_alice = apply(apply(doc, alice), transform(bob, alice))
at_bob = apply(apply(doc, bob), transform(alice, bob))
print(at_alice, at_bob)
$ python ot.py
aXb aXb
aXc aXc

The second line is the tricky tie: a delete and an insert at the same position. The delete must always shift past the newly inserted character (otherwise Alice would delete Bob's "X" and the two copies would diverge as "aXc" vs "abc"). The site tie-break only decides the order of two inserts. Bugs like this are exactly why you use a proven library.

Why a central server makes OT practical. With a server that totally orders operations, each client only has to transform incoming ops against its own few pending (unacknowledged) ops. The Google Wave OT whitepaper describes exactly this client-server model (derived from Jupiter, a 1990s Xerox PARC collaboration system that first used one central server to order OT operations): a client keeps at most one operation in flight and buffers the rest until the server acknowledges it, which keeps the state space small. Peer-to-peer OT without a server needs extra properties of transform that are notoriously hard to get right - several published algorithms were later shown to be wrong. (The famous one is TP2, "transformation property 2": transforming an op against two concurrent ops must give the same result whichever order you take them in. A central server sidesteps it because there is only one order.) ShareDB, which appears in the comparison table below, is an open-source Node.js OT server that follows this central-server model.

Real OT is bigger than this toy. Production ops are ranges ("retain 5, insert 'hello', retain 20, delete 3"), carry formatting attributes, and the transform must handle every pair of op types. Undo is the inverse of your own op, transformed over everything that happened since. Say "I would use a proven library (e.g. ShareDB's OT types) rather than write transform functions myself."

3. CRDTs: give every character a name (SDE-2)

A sequence CRDT stops using positions at all. Every inserted character gets a unique, permanent ID, typically (clientId, counter), and records which character it was inserted after. Delete does not remove the character; it marks it as a tombstone (hidden but still there, so others' references to it still work). Because "insert after alice:3" and "delete bob:7" mean the same thing on every replica, operations commute: apply them in any order, any number of times, and every replica reaches the same result. No transform, no central ordering.

You can watch a real CRDT do this. Yjs is a production CRDT used in many collaborative editors:

npm init -y && npm i yjs@13.6.27
// merge.mjs - two replicas edit "offline", then exchange updates in any order
import * as Y from 'yjs'
const alice = new Y.Doc(), bob = new Y.Doc()
alice.getText('t').insert(0, 'abc')
Y.applyUpdate(bob, Y.encodeStateAsUpdate(alice))   // both start with "abc"
alice.getText('t').insert(1, 'X')                  // Alice, offline
bob.getText('t').delete(2, 1)                      // Bob, offline: delete "c"
Y.applyUpdate(alice, Y.encodeStateAsUpdate(bob))   // exchange in any order
Y.applyUpdate(bob, Y.encodeStateAsUpdate(alice))
console.log('alice:', alice.getText('t').toString())
console.log('bob:  ', bob.getText('t').toString())
$ node merge.mjs
alice: aXb
bob:   aXb

The answer interviewers want: "We already have a central server per document for permissions and persistence, so OT is a good fit and keeps the data small - that is the Google Docs model. If offline-first or peer-to-peer editing is a core requirement, I would use a CRDT like Yjs and keep the server as a relay and store." Picking with a reason beats reciting both.

You might confuse this with...

  • OT vs CRDT: OT keeps positions and rewrites concurrent ops so they still mean the same thing; a CRDT names every character so ops never need rewriting.
  • OT/CRDT vs locking: locking prevents concurrency (only one editor at a time); OT and CRDTs allow it and merge afterwards.
  • Single owner vs a lock: the owner session server is not a lock on typing - everyone types at once; the owner only decides the order of ops.

Figma's take. Figma's engineering blog explains they decided against OT as more complex than their problem needed. Their documents are trees of objects with properties, so they use a CRDT-inspired design where the server is still the authority: one server process per multiplayer document over WebSockets, last-writer-wins per object property, and fractional indexing to order children (a new item between positions 0.3 and 0.4 gets 0.35, so nothing else is renumbered). Clients apply their own edits immediately and ignore conflicting server updates for a property until their own change is acknowledged.

4. Storage: op log, snapshots and compaction (good to know)

Every accepted op is appended at (doc_id, rev) before it is acknowledged. A snapshot is written every ~1,000 ops or after the document goes idle, so loading never replays more than ~1,000 ops. Old ops can be compacted: keep fine-grained ops for recent history (e.g. 30 days), merge older ones into coarser versions ("version from 3 March, 14:00"), and move them to cold object storage. Version history then becomes "list of snapshots + ability to replay between them". For a CRDT, compaction also means garbage-collecting tombstones once every replica has seen the delete - which is hard when an offline replica might still reference them; Yjs and Automerge offer encodings and GC options for this.

5. Scaling WebSockets and routing (SDE-2)

  • Separate gateways from session servers. Gateways only hold sockets and forward frames; session servers hold document state. You can deploy session servers without dropping 3 million sockets.
  • Route by doc_id. Either consistent hashing of doc_id over session servers, or an explicit registry with leases (more control: you can move a hot doc, drain a server). Hello Interview's breakdown treats "how do we scale to millions of WebSocket connections?" as the first deep dive for this question.
  • Hot documents. A company-wide document with thousands of viewers: let viewers subscribe through a pub/sub fan-out tier (read-only), and keep the editor count per document bounded, which real products do.
  • Reconnect storms. When a gateway dies, its 100k clients reconnect at once. Clients use exponential backoff with jitter; the LB spreads them; session servers serve them from memory.
  • Failover correctness. Two servers must never both think they own a document (split brain would create two revision 1043s). Use a lease with a fencing token: the op log write is conditional on "rev = expected and owner epoch = mine", so a zombie old owner's writes are rejected. (Leases are explained from scratch in the story of Distributed Job Scheduler.) Why would an owner not know its lease expired? A GC pause: the runtime (JVM, Go, .NET) stops all threads to reclaim memory, sometimes for seconds - like a process frozen by SIGSTOP. When it resumes it has no idea time passed. The job scheduler page shows the same trap.

From your world

A fencing token is just an epoch number that only goes up: every time ownership moves, the registry hands the new owner epoch + 1. Storage remembers the highest epoch it has seen and rejects any write carrying an older one - like a router ignoring hellos from a stale designated router that still advertises a lower sequence number, or OSPF dropping an LSA whose sequence number is older than the one in its database. Where it breaks: the check must live in the storage layer. If the op log does not compare the token on every write, the token is useless - a paused old owner that wakes up will still write, because nothing stops it.

6. Presence, cursors, offline and undo (good to know)

  • Presence and cursors are ephemeral: kept in the session server's memory, broadcast at most every ~50-100 ms per user, never written to the op log. A cursor is a position too, so it must be transformed by incoming ops (OT) or anchored to a character ID (CRDT), or it jumps around.
  • Offline. The client keeps a queue of unacknowledged ops with their baseRev in local storage. On reconnect it sends them; the server transforms them over everything that happened meanwhile. After a long offline period this can be thousands of transforms - one reason offline-first products choose CRDTs.
  • Undo is "undo my last change", not the global last change: take the inverse of my op and transform it over everything applied after it.
  • Comments are a separate service; their anchor is a range that is transformed like a cursor (or anchored to CRDT IDs), so the highlight follows the text.
  • Permissions are checked when the socket opens and on every op (a viewer's op is rejected). Revoking access closes the session server's subscription for that user.
