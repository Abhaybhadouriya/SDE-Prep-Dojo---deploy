Where Kafka, Kubernetes and Docker fit

📨

Kafka: downstream, not the hot path

Publish accepted ops / "doc changed" events to a topic keyed by doc_id (ordered per doc) for search indexing, notifications, audit and analytics. Keep the authoritative op log in a store that can answer "ops for doc X after rev N" directly - a Kafka partition mixes many documents.

 ☸️

Kubernetes

Gateways and session servers as Deployments. Long-lived sockets need graceful drain: a preStop hook tells clients to reconnect elsewhere and a long terminationGracePeriodSeconds. Autoscale gateways on connection count (custom metric), not CPU.

 🔀

Networking

An L7 load balancer / Ingress or Gateway that supports WebSocket upgrade and long idle timeouts; routing to the right session server happens inside the app (registry lookup), not by sticky sessions alone.

 🐳

Docker

Compose a local lab: Postgres (metadata), Redis (presence pub/sub) and two session-server containers, then kill one to test failover.

 
# Part of a gateway Deployment: drain WebSockets gently during a rollout
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 120
      containers:
        - name: ws-gateway
          image: registry.example.com/ws-gateway:1.8.0
          ports: [{ containerPort: 8080 }]
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "curl -s -X POST localhost:8080/admin/drain; sleep 90"]
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }

The drain endpoint (your own code) stops accepting new sockets, makes readiness fail so the Service stops sending traffic, and tells connected clients to reconnect with jitter - so a rolling update does not cause a reconnect storm. See Deployments for maxSurge / maxUnavailable.
