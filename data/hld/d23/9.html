Interview: driving the 45 minutes

  1. 0-5 min: clarify. Plain text or rich? How many simultaneous editors per doc? Offline needed? History? Write it down.
  2. 5-10 min: estimate. Connections, not QPS per doc, are the scale problem. State assumptions.
  3. 10-15 min: API + data. REST for docs, WebSocket for ops with baseRev and (clientId, seq); op log + snapshots.
  4. 15-25 min: high-level design. LB -> gateways -> owner session server per doc -> op log; broadcast. Show why naive last-write-wins loses edits.
  5. 25-40 min: deep dives. OT worked example (draw "abc"), CRDT contrast, then scaling sockets and failover with fencing.
  6. 40-45 min: wrap-up. Presence, offline, monitoring (ack latency, reconnect rate, divergence checksums), and what you would build next (history UI, comments).

Common mistakes: locking the whole document; last-write-wins on the full text; storing cursors in the database; "use a CRDT" without saying what it costs; putting every keystroke through a heavy queue on the hot path; no plan for owner failover (or two owners); forgetting that the client applies its own edits before the server confirms them.

60-second answer

"Each open document has one owner session server, found through a lease registry. Clients connect over WebSockets through gateways, apply their own edits locally, and send operations tagged with the revision they were based on. The owner orders operations, transforms any op that missed newer revisions - that is OT, like Google Docs - appends it to an op log keyed by document and revision, acknowledges, and broadcasts. Snapshots every thousand ops keep loading fast and give version history. Cursors and presence are in memory only. If the owner dies, another server takes the lease with a higher epoch, loads snapshot plus log, and clients resend unacknowledged ops, deduplicated by client sequence numbers. If offline-first were a must, I would switch the document model to a CRDT such as Yjs."

Why can't we just send the full document on every change and keep the latest?

That is last-write-wins on the whole document. If Alice and Bob both change it within the same second, whichever save arrives second overwrites the other's work. It also sends kilobytes per keystroke and loses history. Sending small operations and merging them (OT or CRDT) keeps both people's edits and costs about 100 bytes per op.

How to answer

Give the two-user example; it shows you understand the core problem before any boxes.

Likely follow-ups
  • What about locking paragraphs instead? (Works for coarse editing like Confluence sections, but two people in one paragraph still block each other, and stale locks need timeouts.)
Explain OT versus CRDT and pick one for this design.

OT keeps positional operations and transforms concurrent ones against each other; with a central server that orders everything, each client only transforms against its few pending ops. CRDTs give every element a unique ID so operations commute and replicas merge in any order without a server, at the cost of per-character metadata and tombstones. Since we already have a per-document server for auth and persistence, I would pick server-based OT (the Google Docs model). For offline-first or peer-to-peer I would choose a CRDT like Yjs or Automerge.

How to answer

One sentence each, one row on cost, then a decision tied to your requirements. Draw the "abc" example if there is a whiteboard.

Likely follow-ups
  • Why is peer-to-peer OT hard? (Without one order, transform must satisfy extra properties (TP2) across all paths; several published algorithms were later proven wrong.)
  • How big does CRDT metadata get, and how do libraries shrink it? (Naively an ID per character; Yjs/Automerge store runs of consecutive inserts as one item and compress encodings, plus tombstone GC.)
  • What does Figma do? (Server-authoritative, one process per document, last-writer-wins per object property, fractional indexing for ordered children.)
How do all editors of a document end up on the same server?

Gateways look up the owner of doc_id in a registry backed by a consensus store (etcd/ZooKeeper) where servers hold leases; or use consistent hashing of doc_id over the session-server ring. On first open, a server acquires the lease and loads the document. A registry is more flexible than pure hashing: you can rebalance hot documents and drain servers for deploys.

How to answer

State the requirement first: "one writer per doc gives us a total order", then the mechanism, then the failure story.

Likely follow-ups
  • The owner is paused by GC and its lease expires - what stops it writing? (Fencing token / epoch.)
The session server crashes mid-edit. Walk me through recovery.

Acknowledged ops are already in the op log, so nothing acknowledged is lost. The lease expires; another server acquires it with a higher epoch, loads the latest snapshot and replays ops after it to reach the latest revision. Clients see the socket close, reconnect with backoff, and resend unacknowledged ops with their baseRev and (clientId, seq). The new owner dedups ops it already stored, transforms the rest, and continues. Old owner writes are rejected by the epoch check.

How to answer

Split into: what is durable, who takes over, what clients do, how duplicates and zombies are prevented.

Likely follow-ups
  • How long is the user-visible outage? (Lease TTL + snapshot load + replay: typically a few seconds; shorter TTLs cut it but risk false failovers.)
  • What if the op log write succeeded but the ack was lost? (The client resends with the same (clientId, seq); the server sees it is already at a revision and re-acks it instead of applying twice.)
How do you show other users' cursors?

Presence messages over the same WebSocket, throttled to every 50-100 ms, held only in the session server's memory (and Redis pub/sub if users of one doc are on different gateways). Never written to the op log. Cursor positions are transformed by incoming ops - or anchored to character IDs in a CRDT - so they stay on the right letter. On disconnect, a timeout removes the user.

How to answer

Separate durable data (ops) from ephemeral data (presence) explicitly; interviewers check for this.

Likely follow-ups
  • A document has 2,000 viewers - do you broadcast every cursor to everyone? (No: show only editors' cursors, throttle harder, or show "2,000 viewing" as a count; viewers get a read-only fan-out tier.)
How do you keep storage under control when every keystroke is logged?

Clients batch keystrokes (100-200 ms) so one op carries several characters. Snapshots every ~1,000 ops bound load time. Recent ops are kept fine-grained for history; older ones are compacted into coarser versions and moved to cold object storage. For CRDTs, tombstones are garbage-collected once all replicas have seen the delete, and libraries encode runs of characters compactly.

How to answer

Do the arithmetic (about 100 MB/s, about 8.6 TB/day raw at the assumed load), then show three levers: batch, snapshot, compact.

Likely follow-ups
  • How do you show "version from last Tuesday"? (Load the nearest snapshot before that time and replay ops up to the timestamp; precompute named versions.)
A user edits offline on a flight for 3 hours. What happens when they land?

With OT, the client's queued ops (based on an old revision) are sent; the server must transform them over every op since - potentially thousands, and the result can surprise users. Products often cap this and present conflicts as suggestions. With a CRDT, the client sends its state update and merges the server's; convergence is guaranteed, though concurrent edits in the same sentence can interleave oddly. This scenario is the strongest argument for CRDTs.

How to answer

Compare both models on this exact scenario; that is where the difference is clearest.

Likely follow-ups
  • How do you show the user what changed while they were away? (Diff the revision they last saw against the current one and highlight it, grouped by author.)
Would you use Kafka as the operation log?

Not as the primary one. Recovery needs "all ops for document X after revision N" and conditional appends (epoch + expected revision) - a KV / wide-column store keyed by (doc_id, rev) does that directly, while a Kafka partition interleaves many documents. Kafka is great right after: publish accepted ops keyed by doc_id for search indexing, notifications, analytics and audit, so those consumers never slow typing.

How to answer

Show you know what Kafka is good at (ordered, replayable fan-out) and what it is not (random per-key reads).

Likely follow-ups
  • What partition key, and why? (doc_id: keeps each document's events in order for downstream consumers, and spreads load across millions of docs.)
Scale to millions of concurrent WebSocket connections.

Dedicated gateway tier (holding sockets only), autoscaled on connection count; L7 LB with long idle timeouts and WebSocket support; heartbeats to detect dead clients; per-gateway memory budget measured, not guessed. Session servers own many documents each. Deploys drain gateways gradually; clients reconnect with exponential backoff + jitter. Hot docs: viewers go through a read-only fan-out tier, editors are bounded.

How to answer

Name the separation of concerns, the scaling metric (connections), and the reconnect-storm plan.

Likely follow-ups
  • How do you route a reconnecting client back to the right owner? (Any gateway accepts it, then looks up doc_id in the registry or hash ring - stickiness to a gateway is not needed.)
How do comments stay attached to the right text?

Comments live in their own service with an anchor (start, end). The anchor is transformed by every op just like a cursor - or, with a CRDT, it references character IDs so it never drifts. If the anchored text is deleted, the comment becomes "orphaned" and is shown in a side list.

How to answer

Reuse the cursor idea; show you see the pattern.

Likely follow-ups
  • How do you notify mentioned users? (The comment service publishes a "mention" event to Kafka; the notification system consumes it and sends email/push.)

Scenario: two users see different text

Support reports that after a busy meeting, two people looking at the same document see different sentences in one paragraph. Refreshing fixes it for one of them.

Weak answer: "Tell users to refresh."

Strong answer: refresh fixing it means the server copy is consistent and a client diverged - so a client-side transform bug or a dropped/duplicated broadcast. Check whether the session changed owner in that window (split brain would make the server wrong). Add a periodic checksum: clients send a hash of their text at revision N, the server compares, and on mismatch forces a resync and logs the op sequence for replay in a test. Fix the transform case (usually same-position inserts or overlapping range deletes) and add a fuzz test that generates random concurrent ops and checks convergence.

Likely follow-ups
  • How would you reproduce it deterministically? (Record the op stream; replay with the same ordering.)

Scenario: every deploy causes a "reconnecting..." storm

Each rolling deploy of the gateway causes 30 seconds of high latency and some failed edits across all documents.

Weak answer: "Deploy at night."

Strong answer: pods are being killed with open sockets, so all their clients reconnect at once and session servers get floods of resends. Add a drain: preStop marks the pod not-ready, tells clients to reconnect elsewhere spread over a minute, and waits; raise terminationGracePeriodSeconds; lower maxUnavailable; make clients use jittered backoff. Measure reconnects per second and ack latency during the next deploy.

Likely follow-ups
  • Why does deploying session servers hurt less if gateways are separate? (Sockets stay open on the gateways; only the doc ownership moves, so clients just see a short pause, not a reconnect.)
