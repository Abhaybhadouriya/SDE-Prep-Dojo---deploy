Key APIs

# REST: everything that is not live editing
POST   /v1/docs                         { "title": "Q4 plan" }            -> { "docId": "d_9f2" }
GET    /v1/docs/{docId}                                                   -> { "rev": 1042, "content": "...", "role": "editor" }
GET    /v1/docs/{docId}/history?before=1042                               -> list of versions
POST   /v1/docs/{docId}/share           { "email": "...", "role": "commenter" }

# WebSocket: live editing session (one socket per open document tab)
WS     /v1/docs/{docId}/live?token=...

  client -> server   { "type": "op", "clientId": "c7", "seq": 18, "baseRev": 1042,
                       "ops": [ { "ins": "X", "pos": 1 } ] }
  server -> client   { "type": "ack", "seq": 18, "rev": 1043 }
  server -> others   { "type": "op",  "rev": 1043, "author": "c7", "ops": [ { "ins": "X", "pos": 1 } ] }
  client <-> server  { "type": "presence", "cursor": { "pos": 2 }, "name": "Alice" }   # not stored
  • baseRev says "this op was made on top of revision 1042". If the server is already at 1045, it knows the op missed 3 others and must be transformed against them.
  • (clientId, seq) is the idempotency key: if the socket drops and the client resends op 18, the server recognises it and just re-sends the ack.
  • Why WebSocket? It is one long-lived, two-way TCP connection, so the server can push others' edits the moment they happen. Polling every second would add latency and waste. (Background: API Design & Client-Server Communication.)
