Back-of-envelope estimation

No company publishes these numbers, so state your assumptions out loud and let them drive the design. The point is the shape of the load, not the exact values. (Method: Back-of-Envelope Estimation.)

  1. Users (assumption). 50 million daily active editors, each with a document open for about 30 minutes a day.
  2. Concurrent connections. 50,000,000 x 30 min / 1,440 min per day = about 1 million open documents-with-a-person on average. Peak (working hours across regions) about 3x = 3 million WebSocket connections.
  3. Operations per second. Clients do not send every keystroke separately; they batch for roughly 100-200 ms. Assume an open editor sends about 1 batch/s on average (most of the time people read, not type). 1M x 1 = 1 million ops/s average, about 3 million/s at peak - but spread over a million different documents.
  4. Per document. Most documents have 1-5 editors. So the per-document rate is tiny (a few ops/s); the challenge is the number of documents, not one document's speed. One server process can easily own thousands of documents.
  5. Op log volume. About 100 bytes per op with metadata (doc id, revision, user, position, text). 1M ops/s x 100 B = 100 MB/s, about 8.6 TB/day. Keeping every op forever is expensive, so we snapshot and compact (deep dive 4).
  6. Document storage (assumption). 1 billion documents x 50 KB average = 50 TB of current snapshots. Large, but ordinary for a blob store.
  7. WebSocket servers (assumption). If one gateway holds about 100,000 idle-ish connections (it depends heavily on memory per connection - measure it), 3M / 100k = 30 servers; run about 60 for headroom and zone failures.

From your world

This is like a router with millions of BGP sessions where each session is quiet most of the time. The hard part is connection state (memory per socket, keepalives, reconnect storms after a restart), not raw packet rate. And just as one routing process owns each peer, we will make one server process own each document so its operations have a single, total order - like a single-writer ring buffer with one producer index. Where it breaks: a BGP session carries routes that are idempotent to re-apply; an edit op is not - replaying "insert X at 1" twice inserts two X's, so every op needs an ID and dedup.
