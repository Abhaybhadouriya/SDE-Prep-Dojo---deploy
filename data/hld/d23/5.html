Architecture: follow one keystroke

Click Next or Play. The key idea: every editor of a document talks to the same document session server, which gives the document's operations a single order.

  1. Type locally, then send. Alice's keystroke shows on her screen at once. Her editor batches it into an op {baseRev:1042, ins "X" @1} and sends it over her WebSocket. When she opened the doc, the L7 load balancer (layer 7: it reads HTTP, so it can route the WebSocket upgrade request) turned the HTTP connection into a long-lived WebSocket.
  2. Gateways hold the sockets. A fleet of stateless-ish WebSocket gateways terminates millions of connections. Keeping sockets separate from document logic means a document server can restart without dropping every connection.
  3. Route to the owner. The gateway asks a registry "who owns d_9f2?" (a lease in etcd/ZooKeeper, or consistent hashing on doc_id) and forwards the op. That session server holds the document in memory and is the only writer, so it assigns revision 1043 - a single total order. If 1042 is not the latest, it first transforms the op against the ops it missed.
  4. Persist before ack. The op is appended to the op log at (d_9f2, 1043). Only after the write succeeds is it "real".
  5. Ack and broadcast. Alice gets ack rev 1043; Bob (and every other session member, via their gateways) gets the op. Bob's editor transforms it against any of his own unacknowledged ops, then applies it.
  6. Background work. A snapshotter writes the full document every ~1,000 ops. Change events go to Kafka for search indexing, notifications ("Alice edited your doc") and audit - none of which may slow down typing.
  7. Failure. If the owner crashes, its lease expires; another server takes ownership, loads the latest snapshot, replays the op log after it, and clients reconnect and resend their unacknowledged ops (deduplicated by clientId + seq).

From your world

Single owner per document = the classic "single writer" rule you use for lock-free rings: one producer assigns sequence numbers, so there is no contention on order. The doc-to-owner lease is the same pattern as an active/standby control card holding mastership with a heartbeat; when hellos stop for the dead interval, the standby takes over. Where the analogy breaks: here the "standby" is any server in the pool, and it rebuilds state from the log instead of from a mirrored checkpoint.
