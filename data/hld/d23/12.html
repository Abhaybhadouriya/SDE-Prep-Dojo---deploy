Quick quiz

Doc "abc". Alice inserts "X" at 1. Concurrently Bob deletes at 2. The server orders Alice first. What does Bob's delete become?

  1. delete at 1
  2. delete at 2
  3. delete at 3
  4. it is dropped
Alice's insert is before position 2, so everything after it moves right by one: delete at 3, and both copies become "aXb".

What makes CRDT operations safe to apply in any order?

  1. They reference unique element IDs instead of positions, so they commute
  2. A server sorts them by timestamp
  3. They lock the document
"Delete element bob:7" means the same on every replica regardless of what else happened; that is why no transform is needed.

Why route all editors of a document to one session server?

  1. To save memory
  2. A single writer gives the document's ops one total order (revision numbers) cheaply
  3. WebSockets require it
Per-document load is tiny, so one owner is enough, and it removes the need for distributed agreement on every keystroke.

An old owner wakes from a long GC pause after its lease expired. What stops it corrupting the log?

  1. Kafka acks=all
  2. The client's undo stack
  3. A bigger snapshot interval
  4. A fencing epoch checked by the op log's conditional write
The storage rejects writes with an older epoch, so correctness does not depend on the old server noticing it lost the lease.

Where should live cursor positions be stored?

  1. In the op log with every keystroke
  2. In memory on the session server (plus pub/sub), never persisted
  3. In the snapshot
Presence is ephemeral and high-frequency; persisting it wastes storage and adds latency.

Which requirement most strongly favours a CRDT over server-based OT?

  1. Long offline editing or peer-to-peer sync
  2. Plain text documents
  3. Fewer than 10 editors per document
CRDT replicas merge whenever they meet, without transforming against a long history on a server.

Why are snapshots written every ~1,000 ops?

  1. To make OT correct
  2. Because Kafka requires it
  3. To bound load and recovery time: snapshot + at most ~1,000 ops to replay
Without snapshots, opening an old document would replay its entire history.

What does (clientId, seq) on each op protect against?

  1. Unauthorised edits
  2. Applying the same op twice when a client resends after a reconnect
  3. Cursor jumps
It is an idempotency key: the server recognises a resent op and only re-sends the ack.
