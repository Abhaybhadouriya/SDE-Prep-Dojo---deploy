Data model

DataShapeStore and why
Document metadata(doc_id PK, title, owner_id, created_at, latest_snapshot_rev)Relational DB (Postgres/MySQL, sharded by doc_id). Small, transactional.
Permissions(doc_id, principal_id, role)Relational DB; cached at the session server for the life of a session.
Operation log(doc_id, rev) -> {author, clientId, seq, ops, ts}Wide-column / KV store (Cassandra, Bigtable, DynamoDB): partition key doc_id, clustering key rev. Append-only, read as a range "all ops after rev N".
Snapshots(doc_id, rev) -> full document contentObject storage (S3-like) or a blob column. Written every N ops.
Presence / cursorsdoc_id -> {user: cursor, colour, lastSeen}Memory of the session server (+ Redis pub/sub across gateways). Never persisted.
Comments(comment_id, doc_id, anchor, thread, resolved)Relational DB; the anchor is a range that moves with edits.

Why not store the document as one big row and overwrite it on every keystroke? Two writers would overwrite each other (last write wins = lost edits), a 50 KB rewrite per keystroke is wasteful, and you lose history. An append-only op log + periodic snapshots gives you ordering, durability of every edit, cheap writes (about 100 bytes) and version history for free. This is event sourcing: the log is the truth, the document is a materialised view of the log.
