Data model

Most of the data here is either small and relational, or hot and short-lived. The media itself is never stored in a database. Storage choices are explained in Choosing Storage.

DataStoreKeyWhy this store
Users, orgs, licences, meeting settings, schedulesSQL (PostgreSQL / Azure SQL), sharded by orgmeeting_id, org_idRelational, low volume, needs transactions (billing, licence limits)
Live meeting state: roster, mute state, who publishes what, hostRedis cluster (in memory) with a TTLmtg:{meetingId} hashChanges many times per second, lives for an hour, OK to rebuild from clients
Meeting to SFU assignment, SFU health and loadetcd / ZooKeeper / Consul (service discovery)sfu/{region}/{node}, assign/{meetingId}Needs consistent, watchable membership; Discord used etcd for this
In-meeting chatWide-column store (Cassandra / ScyllaDB)partition meeting_id, clustering tsAppend-only, time-ordered, same as Team Chat
RecordingsObject storage (S3 / Blob), metadata in SQLrec/{org}/{meetingId}/{part}Petabytes of write-once blobs, see Handling Large Blobs
Quality telemetry (loss, jitter, RTT per participant)Kafka then a columnar store (ClickHouse / Druid)topic media-qosHigh-volume time series for dashboards and alerting
 
CREATE TABLE meetings (
  meeting_id    BIGINT PRIMARY KEY,
  org_id        BIGINT NOT NULL,
  host_user_id  BIGINT NOT NULL,
  title         TEXT,
  scheduled_at  TIMESTAMPTZ,
  settings      JSONB,          -- waiting room, passcode, recording policy
  status        TEXT CHECK (status IN ('scheduled','live','ended'))
);
CREATE TABLE meeting_sessions (  -- one row per actual run of the meeting
  session_id    BIGINT PRIMARY KEY,
  meeting_id    BIGINT REFERENCES meetings,
  region        TEXT,            -- home region chosen at start
  started_at    TIMESTAMPTZ,
  ended_at      TIMESTAMPTZ,
  peak_participants INT
);
