Architecture: one meeting, start to finish

Click Next or Play. The shape follows what Zoom and Discord publish. Zoom calls its media server a Multimedia Router (MMR); MMRs are grouped into Meeting Zones run by Zone Controllers, which report to a Global Cloud Controller. Discord's equivalent is a signalling service plus a homegrown C++ SFU per voice server, with servers found through etcd.

  1. Join. Asha opens the link. The API checks the meeting, passcode and waiting room in SQL and creates a participant record. Geo DNS or anycast already sent her to the nearest region.
  2. Place. The placement service looks up whether this meeting already has an SFU. If not, it picks the least-loaded healthy SFU in Asha's region from etcd (Zoom: "least-loaded server" in the nearest data centre). The answer goes back in the join response with a short-lived token.
  3. Signal and find a path. Asha opens a WebSocket to the signalling server and sends an SDP offer. In parallel, ICE uses STUN to learn her public address and, if UDP is blocked, a TURN relay on TLS 443. Many SFU systems skip full ICE: the SFU has a public address, so the client simply connects to it (Discord does this).
  4. Publish. Asha's client sends audio and three simulcast video layers (for example 180p, 360p, 720p) as SRTP over UDP to the Mumbai SFU. One upload, no matter how many people watch.
  5. Forward. For each subscriber the SFU picks the best layer that fits that subscriber's bandwidth (learned from RTCP feedback) and forwards those packets, rewriting sequence numbers. It never decodes video.
  6. Cascade. Ben is in London. Instead of making him cross the world to Mumbai, placement gives him the London SFU, and the two SFUs exchange streams over the backbone (Jitsi calls this Octo). Each person talks to a nearby server.
  7. Record. When the host presses Record, a recorder bot joins as a hidden subscriber, decodes and composites the streams, and uploads MP4 parts to object storage. Mixing happens here, off the live path.
  8. Events. Join/leave, recording-ready and per-participant quality reports go to Kafka for billing, analytics, notifications ("your recording is ready") and alerting. Media never goes through Kafka.
