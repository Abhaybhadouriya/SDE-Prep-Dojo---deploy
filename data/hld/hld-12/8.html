Event time, watermarks and late data

Processing time is the clock of the machine running the operator. It is simple and fast, but results change if the job lags or restarts. Event time is the timestamp inside the event, set where it happened (the phone, the ad server). Results are deterministic and replayable, but events arrive out of order: a phone in a tunnel uploads 3-minute-old clicks. So when is the 00:00-00:05 window complete?

A watermark is Flink's answer. Watermark(t) is a marker that flows with the data and says "event time has reached t; expect no more events with timestamp <= t". The usual generator is bounded out-of-orderness: watermark = largest timestamp seen minus a fixed delay (say 30 s). When the watermark passes a window's end, the window fires. An operator with several inputs uses the minimum watermark of its inputs, so one idle Kafka partition can stall everything. That is why Flink lets you mark idle sources.

  1. Events arrive carrying their own timestamps: first 1:10, then 4:20. The delay is 30 s, so the watermark is "largest timestamp seen minus 30 s".
  2. An out-of-order event. Next, an event stamped 3:00 arrives. The watermark is 4:20 - 30 s = 3:50. That is still before 5:00, the end of window 0-5, so the window is open and the 3:00 event is counted.
  3. Window fires. Now 5:50 arrives. The watermark jumps to 5:50 - 30 s = 5:20, which is past 5:00, so window 0-5 fires and emits count = 3 (1:10, 3:00 and 4:20). The 5:50 event goes into window 5-10. Rule: an event stamped before 5:00 is counted only if it arrives before any event stamped 5:30 or later has been seen. Pick the delay from how late your events usually are.
  4. Late event. An event stamped 2:00 arrives after the window fired. By default (allowed lateness 0) Flink drops it. You can set allowedLateness to keep the window state longer and re-fire with a corrected result, or send late events to a side output for a later batch correction.

You might confuse this with... event time (when it happened, stamped at the source), ingestion time (when Kafka or Flink first saw it) and processing time (the operator's clock right now). Only event time gives the same answer when you replay the data. Also, allowed lateness is not the watermark delay: the delay decides when a window first fires; allowed lateness decides how long after that the window can still be corrected.

The delay is a trade-off you must say out loud in an interview: a longer delay means more complete results but later answers. Uber's surge pricing simply ignores late messages, while a billing pipeline must not drop them, so it uses side outputs plus a nightly batch reconciliation.

// Flink (Java): clicks per ad per minute, on event time, tolerating 30 s of disorder
WatermarkStrategy<Click> wm = WatermarkStrategy
    .<Click>forBoundedOutOfOrderness(Duration.ofSeconds(30))
    .withTimestampAssigner((c, ts) -> c.eventTimeMillis)
    .withIdleness(Duration.ofMinutes(1));          // do not let an idle partition stall time

OutputTag<Click> late = new OutputTag<Click>("late-clicks") {};

SingleOutputStreamOperator<AdCount> counts = env
    .fromSource(kafkaSource, wm, "clicks")
    .keyBy(c -> c.adId)
    .window(TumblingEventTimeWindows.of(Duration.ofMinutes(1)))
    .allowedLateness(Duration.ofMinutes(2))
    .sideOutputLateData(late)
    .aggregate(new CountAgg());

counts.getSideOutput(late).sinkTo(lateClicksSink);   // reconcile later in batch
