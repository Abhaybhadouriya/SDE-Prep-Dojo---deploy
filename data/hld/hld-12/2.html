Data warehouse, data lake, lakehouse

  • Data warehouse: a managed SQL database for analytics. Data is cleaned and given a schema before it is loaded (schema-on-write). Fast and reliable, but storage is proprietary and costly, and ML code cannot read it directly. Examples: Snowflake, BigQuery, Redshift, Teradata.
  • Data lake: cheap object storage (S3, ADLS, GCS, HDFS earlier) holding raw files in open formats like Parquet and ORC. Anything can be dumped in, and the schema is applied when reading (schema-on-read). Cheap and flexible, but without transactions or quality control it easily becomes a "data swamp".
  • Lakehouse: a lake plus a table format (Delta Lake, Apache Iceberg, Apache Hudi) that adds ACID transactions, schema enforcement, time travel and upserts on top of Parquet files. Warehouse-style SQL engines (Spark SQL, Trino/Presto) and ML jobs read the same files.

The Databricks paper that named the Lakehouse (CIDR 2021) describes the problem it fixes. Most big companies run a two-tier setup: data is ETLed into a lake, then ETLed again into a warehouse. That means two copies, stale data, extra failure points, and ML jobs that cannot read the warehouse's private format. The authors report that a SQL engine over plain Parquet can be competitive with cloud warehouses on the TPC-DS benchmark.

From your world

Row vs column layout is the same question as array-of-structs vs struct-of-arrays in C. If your loop touches one field of every element, struct-of-arrays keeps that field contiguous, so cache lines and SIMD are fully used. Columnar files are struct-of-arrays on disk. Where this breaks: a struct-of-arrays in RAM is cheap to update in place, but a columnar file is written once and rewritten in bulk, so single-row updates are slow (that is why lakehouses batch their upserts).
