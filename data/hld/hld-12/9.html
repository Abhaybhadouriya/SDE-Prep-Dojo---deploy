Lambda vs Kappa architecture

Stream results can be wrong (late data, bugs). Batch results are right but slow. How do you get both?

Lambda (Nathan Marz)Kappa (Jay Kreps, 2014)
Code pathsTwo (batch + speed), kept in sync by handOne streaming job
ReprocessingRerun the batch layerStart a second job from the start of the log, swap tables when caught up
NeedsTwo systems to operateLong log retention (Kreps' example: 30 days), ~2x output storage while swapping
WeaknessLogic drift, double operations costReplaying months through a stream engine is slow and needs huge retention

Real life sits in between. Uber's paper explains that it keeps Kafka retention to only a few days at its scale, so pure Kappa was not possible. Uber built Kappa+: the same Flink streaming code reads archived Hive tables for backfills, with throttling and bigger windows to cope with out-of-order history. Uber's real-time OLAP store Pinot itself uses a lambda-style split: real-time segments from Kafka plus offline segments from batch. Lakehouse table formats (Iceberg/Delta) are making this easier, because the same table can receive streaming appends and batch rewrites.
