Probabilistic structures: huge questions, tiny memory

Exact answers at web scale can need gigabytes per key. These three structures accept a small, known error in exchange for kilobytes. Hello Interview's advice applies: use them when exact structures truly do not fit, and talk about trade-offs, not internals. Using a Bloom filter where a hash set would do is a red flag.

Bloom filter: "have I seen this before?"

A Bloom filter is a bit array of m bits plus k hash functions. To add an item, set the k bits it hashes to. To check, look at those k bits: if any is 0, the item is definitely not in the set. If all are 1, it is probably in the set (other items may have set those bits). No false negatives, a tunable false-positive rate, and no deletes (a counting Bloom filter fixes that with small counters).

Sizing (worth memorising). For n items and target false-positive rate p: m = -n ln p / (ln 2)2 bits and k = (m/n) ln 2 hashes. That is about 9.6 bits per item for 1% and 14.4 for 0.1%. Example: a crawler with 1 billion seen URLs at 1% needs about 9.6 billion bits (around 1.2 GB) and 7 hashes. An exact hash set of 1 billion 100-byte URLs would be over 100 GB.

Where it is used. Bigtable lets clients create Bloom filters per SSTable so most lookups for missing rows never touch disk. Cassandra does the same, with bloom_filter_fp_chance defaulting to 0.01 (0.1 for leveled compaction); its docs note that going from 0.1 to 0.01 takes about 3x the memory. Other uses: crawler URL dedup (d16), "skip profiles you have already swiped" (d59), "is this username taken?" pre-checks, and CDN "cache only on second request" (avoiding one-hit wonders).

HyperLogLog: "how many different ones?"

Counting distinct users exactly needs memory proportional to the number of users. HyperLogLog (Flajolet et al., 2007) estimates it in fixed memory. The intuition: hash each item to random-looking bits. Seeing a hash that starts with many zeros is rare. If the longest run of leading zeros you have seen is r, you have probably seen about 2r distinct items. One such guess is noisy, so HLL splits items into m buckets by the first hash bits, keeps the max run per bucket, and combines them with a harmonic mean. Standard error is about 1.04/sqrt(m).

  • Redis: up to 12 KB per key, standard error 0.81% (that is 16,384 registers: 1.04/sqrt(16384) = 0.81%), counts up to 264. Commands: PFADD, PFCOUNT, PFMERGE.
  • The paper: beyond 109 distinct items with about 2% error using only 1.5 KB.
  • Mergeable: the HLL of a union is the per-register max of the HLLs. Daily unique visitors per page can be merged into weekly ones without rescanning. Intersections are not exact, though.
$ redis-cli PFADD uv:page42:2026-11-23 user:17 user:99 user:17
(integer) 1
$ redis-cli PFCOUNT uv:page42:2026-11-23
(integer) 2
$ redis-cli PFMERGE uv:page42:week48 uv:page42:2026-11-23 uv:page42:2026-11-24
OK

Count-min sketch: "how often?"

A count-min sketch is d rows of w counters, with one hash function per row. To add an item, increment one counter in each row. To query, read its d counters and take the minimum. Collisions only ever add, so the estimate can be too high but never too low; the minimum picks the row with the fewest collisions. With w = ceil(e/epsilon) and d = ceil(ln(1/delta)), the overestimate is at most epsilon x (total count) with probability 1 - delta. Example: epsilon 0.001, delta 0.01 gives w = 2,719 and d = 5, about 13,600 counters, or roughly 54 KB at 4 bytes each, whatever the number of distinct keys.

Count-min only answers "how many times did X appear?". To get the top K, pair it with a small min-heap of size K: after each update, if the item's estimate beats the heap minimum, swap it in. That is the core of Top-K / Heavy Hitters (d35) and Trending Topics (d29), usually with per-window sketches (they merge by adding counters) and a batch job for exact numbers later. Redis ships it as CMS.INITBYDIM, CMS.INCRBY, CMS.QUERY.

From your world

You have used these ideas in hardware. A count-min sketch is a set of hashed flow counters in a switch ASIC that accept collisions (sFlow/NetFlow-style heavy-hitter detection). A Bloom filter is a cheap pre-check before an expensive TCAM or DRAM lookup. "Mergeable sketches" are why line cards can count locally and the supervisor just sums or maxes them. Where this breaks: an ASIC usually resets its counters every polling interval, while a sketch used for "the last hour" needs one sketch per time bucket that you keep and merge.
