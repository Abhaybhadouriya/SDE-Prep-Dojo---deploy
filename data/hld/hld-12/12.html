Interview questions

What is the difference between OLTP and OLAP, and why are analytics databases columnar?

OLTP serves the application: many small, latency-critical reads and writes by key, normalised schema, row storage. OLAP serves analysis: few queries that scan billions of rows but touch few columns. Columnar storage reads only the needed columns, compresses each column well (similar values sit together, so run-length and dictionary encoding work), and enables vectorised execution. Keep them separate and feed OLAP by CDC or events, so a heavy report never hurts checkout latency.

How to answer

One line each, then the layout picture (rows vs columns), then "never run analytics on the primary".

Likely follow-ups
  • What is a star schema?
  • How fresh can OLAP be? (real-time OLAP: Pinot/Druid/ClickHouse ingesting from Kafka in seconds)
Data lake vs data warehouse vs lakehouse?

A warehouse is managed, schema-on-write SQL storage: fast and governed, but proprietary and costly, and awkward for ML. A lake is cheap object storage with open files (Parquet/ORC), schema-on-read: flexible and cheap, but with no transactions or quality control. A lakehouse adds a table format (Iceberg, Delta, Hudi) to the lake for ACID commits, schema enforcement, time travel and upserts, so warehouse-style SQL and ML read one copy. That removes the double ETL of the common two-tier lake + warehouse setup.

How to answer

Use a table with cost, schema, transactions and ML access, then name one product per column.

Likely follow-ups
  • How does a table format give ACID on S3? (an atomic swap of a metadata/manifest pointer; optimistic concurrency)
  • What is the small-files problem? (compaction)
Walk me through MapReduce. What are its bottlenecks?

Input splits (16-64 MB) go to mappers scheduled near the data. Mappers emit key-value pairs, a combiner pre-aggregates locally, the shuffle partitions by hash(key) mod R, reducers sort and merge per key, and output is written to the distributed file system. Failures are handled by re-execution: tasks are deterministic, so the master just reruns them. Bottlenecks: the all-to-all shuffle over the network, writing every intermediate step to disk (bad for iterative jobs), data skew (one hot key overloads one reducer), and stragglers (handled with backup tasks; without them the paper's sort took 44% longer).

How to answer

Draw split, map, shuffle, reduce. Then fault tolerance. Then the 3 bottlenecks with a fix for each.

Likely follow-ups
  • How do you handle a skewed key? (salting: key#rand, then a second aggregation)
  • Why must map and reduce be deterministic?
Why is Spark faster than Hadoop MapReduce?

Spark keeps intermediate data in memory across stages instead of writing it to the distributed file system after every job. It recovers lost partitions from lineage (the recorded transformations) rather than by replicating data, and it plans the whole DAG lazily, so it can pipeline narrow transformations and only shuffle at wide ones. The RDD paper reports up to 20x speed-ups on iterative jobs and interactive queries over 1 TB in seconds. For one-pass jobs dominated by disk I/O, the gap is smaller.

How to answer

Memory + lineage + DAG planning, then say where the gain is biggest (iterative ML, interactive).

Likely follow-ups
  • Narrow vs wide dependencies?
  • What happens if data does not fit in memory? (spills to disk)
Event time vs processing time. What is a watermark and how do you handle late data?

Processing time is the operator machine's clock: fast but non-deterministic. Event time is the timestamp when the event happened: correct and replayable, but events arrive out of order. A watermark is a marker in the stream asserting "no more events at or before time t". It is usually max seen timestamp minus an allowed disorder (for example 30 s). A window fires when the watermark passes its end. For late data: (1) choose the delay from the measured lateness distribution, (2) use allowedLateness to update results for a while, (3) send the rest to a side output, and (4) reconcile in batch if money is involved. Say the trade-off: a longer delay is more complete but slower.

How to answer

Define both times, the watermark, then the four-step late-data policy tied to the business (surge drops late data; billing reconciles).

Likely follow-ups
  • Why can one idle partition stall the job? (minimum watermark across inputs; use idleness)
  • What if device clocks are wrong? (bound timestamps by server ingest time)
"Show trending items in the last 5 minutes, refreshed every 30 seconds." Which window?

A sliding window of 5 minutes with a 30 s slide. To avoid keeping 10 overlapping windows per key, keep tumbling 30 s buckets per key (or a count-min sketch per bucket) and sum the last 10 buckets on each refresh. Only keep a top-K candidate heap per bucket, not every key. Use event time with a small watermark delay. Trending tolerates slightly late or approximate data, so favour freshness.

How to answer

Name the window, then the bucket optimisation, then approximation (sketch + heap) and freshness vs accuracy.

Likely follow-ups
  • How do you exclude items the user already saw? (per-user Bloom filter)
  • How do you scale a hot key? (pre-aggregate per partition, then merge)
Lambda or Kappa? How would you reprocess a year of data after a bug fix?

Lambda keeps a batch layer for correctness and a speed layer for freshness, merged at query time. The cost is two code bases that drift. Kappa keeps one streaming job and reprocesses by replaying the log into a new job and output table, then switching readers. That needs retention covering the reprocessing window. For a year of data, Kafka retention is rarely kept that long (Uber keeps only a few days). So do what Uber calls Kappa+: run the same streaming code over the archived lake tables (Hive/Iceberg) as a bounded source, throttle it, then catch up from Kafka and swap the output table. Alternatively, use tiered storage in Kafka for longer retention.

How to answer

Define both, name the costs, then give a concrete reprocessing plan with a table swap and rollback.

Likely follow-ups
  • How do you make the output switch atomic? (versioned tables, alias swap)
  • How do you keep the replay from starving live jobs?
How do you get exactly-once counts in an ad click aggregator?

End-to-end exactly-once needs three parts. Source: a replayable log (Kafka) whose offsets are stored in the checkpoint. Processing: Flink checkpoints with aligned barriers, so state and offsets are snapshotted together and restored together. Sink: transactional (Kafka transactions committed when the checkpoint completes, readers use read_committed) or idempotent (upsert by (ad_id, window_start)). Also dedupe the input: clicks carry a unique click_id, deduped in keyed state with a TTL, because the ad server itself may resend. Reconcile with a batch job over the raw log for billing.

How to answer

Source, processing, sink, plus input dedup. Mention the checkpoint interval as a latency vs recovery-cost trade-off.

Likely follow-ups
  • What happens to output between checkpoints after a crash?
  • Why is "exactly-once" really "effectively once"?
How does a Bloom filter work, and how big must it be for a web crawler?

It is an m-bit array with k hashes. Add sets k bits. Check reports "definitely not present" if any bit is 0, else "probably present". There are no false negatives, there are false positives, and you cannot delete (unless counting). Size: m = -n ln p / (ln 2)^2, k = (m/n) ln 2. For 1 billion URLs at 1%: about 9.6 bits per URL, so about 1.2 GB and 7 hashes, versus over 100 GB for an exact set. For a crawler, a false positive means skipping a page that was never crawled, which is acceptable. Shard the filter by URL hash across crawler nodes.

How to answer

Mechanism, the one-sided error, the sizing formula with numbers, and why the error direction is acceptable for this use.

Likely follow-ups
  • What happens when it fills past n? (FP rate climbs; use scalable Bloom filters)
  • Where do databases use them? (LSM SSTables: Bigtable, Cassandra)
Count daily unique visitors for 10 million pages. Exact or approximate?

Exact sets would hold every visitor ID per page per day, which is gigabytes to terabytes. HyperLogLog uses at most 12 KB per page per day in Redis (0.81% error); sparse encoding makes small pages far smaller. HLLs merge by register max, so weekly or monthly uniques come from merging daily ones without rescanning. Use exact counting only where money depends on it (billing), and do that in batch from the raw log.

How to answer

Show the exact-memory estimate, then HLL numbers, then mergeability, then where you would still be exact.

Likely follow-ups
  • Can you get "users who visited both A and B"? (only by inclusion-exclusion, with large error)
  • How does HLL work intuitively? (leading zeros of hashes)
Find the top 100 products by views in the last hour across billions of events.

Ingest views into Kafka keyed by product. Flink workers each keep a count-min sketch plus a min-heap of size K (with some buffer, say 2K) per 1-minute bucket. Every minute, partial top-K lists go to an aggregator that merges the last 60 buckets and publishes the global top 100 to a cache. Sketch sizing: epsilon 0.001 gives ~54 KB per bucket. For exact numbers, run a batch job on the lake hourly (lambda style) and let it overwrite the approximate result. The hot-key danger is solved because the sketch is per partition and merged.

How to answer

Start with exact (hash map + heap) and show why it does not fit, then sketch + heap, then windows, then the exact batch correction.

Likely follow-ups
  • Why is merging partial top-K lists only approximate?
  • Per-category top-K?

Scenario: dashboard counts drop every night at midnight

Your Flink job counts orders per city in 1-minute tumbling event-time windows. Every night the 23:58-00:02 windows show 30% fewer orders than the next morning's batch report.

Weak answer: "Flink lost data; restart it."

Strong answer: compare the arrival lateness distribution with the watermark delay. At midnight, mobile clients batch-upload and a nightly job pauses one Kafka partition. Late events go past the watermark and are dropped (allowed lateness 0). Alternatively, an idle partition holds the minimum watermark back and then jumps it forward. Fixes: measure lateness and set the bounded-out-of-orderness delay from its p99 (the lateness that 99% of events beat; 1 in 100 is later); add withIdleness; set allowedLateness and a side output; reconcile with the batch numbers. Show both the "live" and the "final" figures on the dashboard.

Likely follow-ups
  • How would you alert on this? (late-event counter on the side output)
  • Would processing time fix it? (no: then counts depend on lag and replays)

Scenario: the analytics query is slowing down checkout

Analysts run a daily revenue report directly on the orders Postgres primary. During the report, checkout p99 jumps from 80 ms to 2 s.

Weak answer: "Add an index on created_at."

Strong answer: the report is an OLAP scan on an OLTP database. It evicts the buffer cache and competes for I/O. Short term: run it on a read replica. Proper fix: CDC (Debezium) from Postgres into Kafka, land the data in a lakehouse table partitioned by date in Parquet, and point the BI tool at Trino/Spark SQL or a warehouse. Analysts get history and joins; checkout gets its database back.

Likely follow-ups
  • How fresh will the report be? (minutes with CDC)
  • How do you handle schema changes? (schema registry, compatible evolution)
