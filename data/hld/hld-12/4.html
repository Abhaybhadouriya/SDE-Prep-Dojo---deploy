Spark: keep it in memory

MapReduce writes every intermediate result to disk and to the distributed file system. That is fine for one pass, but slow for jobs that loop over the same data (machine learning, graph algorithms) or for people running query after query. Apache Spark (from the 2012 RDD paper by Zaharia et al.) keeps datasets in memory across steps.

  • RDD (Resilient Distributed Dataset): an immutable, partitioned collection built by coarse transformations (map, filter, join). DataFrames and Spark SQL sit on top of it today.
  • Lineage instead of replication: Spark remembers how each partition was computed. If a machine dies, it recomputes only the lost partitions from their parents. It does not copy all data three times.
  • Lazy DAG: transformations only build a plan. An action (count, write) makes the scheduler cut the DAG into stages at shuffle boundaries and run them.

Click through one small job: read click logs, parse them, keep only clicks, then count per ad. The first three steps are narrow (partition 2 only needs partition 2 of its parent). The count is wide: every output partition needs data from every input partition, so it needs a shuffle.

  1. Lazy plan. textFile, map, filter and reduceByKey run nothing yet. Spark only records the DAG: which RDD came from which parent, and by what function.
  2. Action cuts stages. When you call count() or write, the scheduler cuts the DAG at the wide dependency. Stage 1 runs map and filter back to back inside one task per partition, in memory. Stage 2 starts after the shuffle files from stage 1 are written.
  3. A machine dies. The executor holding partition 2 of clicks crashes. Nothing was replicated.
  4. Lineage recompute. Spark knows clicks p2 = filter(map(lines p2)), so it re-reads only block 2 of the file and re-runs map and filter for that one partition. Partitions 1 and 3 are untouched. (If a shuffle output is lost, the parent stage's tasks for it are re-run.)

The paper reports Spark up to 20x faster than Hadoop MapReduce for iterative jobs, a 40x speed-up for a real analytics report, and interactive scans of a 1 TB dataset in 5-7 seconds. Spark also does streaming (Structured Streaming in micro-batches), but for low-latency, per-event, stateful work the common choice is Flink.
