False positives and count mode: shipping rules safely

Good to know (SDE-2)

A WAF rule that blocks real customers is an outage you caused yourself. A false positive is a legitimate request matched as an attack: a support form whose text contains SQL keywords, a JSON body that looks like XSS, a corporate NAT that looks like one very busy IP. The standard way to avoid this is to never ship a new rule straight to Block.

  1. Deploy in Count. For a managed rule group, set the group's override action to count; for your own rule, use the Count action. Traffic is unaffected.
  2. Watch the logs for a week (or through a full business cycle, including your peak). Which rules matched, on which URIs, for which clients?
  3. Tune. Add scope-down statements, exclude specific rules for specific paths (for example the rich-text editor endpoint), or raise a threshold.
  4. Flip to Block for one rule at a time, ideally first on a canary host or a share of traffic, with an alarm on the blocked-request rate.
  5. Keep a fast rollback: rules are code (Terraform), so reverting is one commit; an emergency allow-list rule at the top priority is your break-glass.
resource "aws_wafv2_web_acl" "shop" {
  name  = "shop-edge"
  scope = "CLOUDFRONT"
  default_action { allow {} }

  rule {
    name     = "aws-common"
    priority = 10
    override_action { count {} }          # observe first; change to none {} to enforce
    statement {
      managed_rule_group_statement {
        vendor_name = "AWS"
        name        = "AWSManagedRulesCommonRuleSet"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "aws-common"
      sampled_requests_enabled   = true
    }
  }

  rule {
    name     = "login-rate"
    priority = 20
    action { block {} }
    statement {
      rate_based_statement {
        limit                 = 100       # per IP per window
        evaluation_window_sec = 300
        aggregate_key_type    = "IP"
        scope_down_statement {
          byte_match_statement {
            search_string         = "/login"
            field_to_match { uri_path {} }
            positional_constraint = "STARTS_WITH"
            text_transformation {
              priority = 0
              type     = "NONE"
            }
          }
        }
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "login-rate"
      sampled_requests_enabled   = true
    }
  }

  visibility_config {
    cloudwatch_metrics_enabled = true
    metric_name                = "shop-edge"
    sampled_requests_enabled   = true
  }
}

With WAF logs in CloudWatch Logs, a Logs Insights query shows what a counted rule would have blocked (output illustrative):

fields @timestamp, httpRequest.clientIp, httpRequest.uri
| filter nonTerminatingMatchingRules.0.ruleId = "aws-common"
| stats count(*) as hits by httpRequest.uri
| sort hits desc
| limit 5

httpRequest.uri            hits
/api/support/ticket        4812
/search                     219
/wp-login.php               188
/api/cart                    14
/.env                         9

Reading it: /wp-login.php and /.env are real attack probes (you do not run WordPress). But 4,812 hits on the support-ticket endpoint are almost certainly customers typing text that trips a rule. Exclude that rule for that path before enforcing, or you will block your own support queue.

Rate limits and NAT. A mobile carrier's CGNAT or an office proxy can put thousands of real users behind one IPv4 address. A per-IP rate limit sized for a single person blocks all of them at once. Prefer keys that identify a client better (session token, API key, account, or IP plus fingerprint) for authenticated flows, and keep per-IP limits generous for the anonymous ones.
