Risk scoring: reCAPTCHA Enterprise-style

Must know (SDE-1)

Naming: Google has since folded reCAPTCHA Enterprise into one product, now simply "reCAPTCHA" in Google Cloud, and classic keys were migrated to it. This page keeps "Enterprise-style" as the name of the concept: invisible, score-based assessment.

The old CAPTCHA asked everyone to click traffic lights. Modern bot defense flips this around: run invisibly, return a score, and let the site decide what to do with it. In reCAPTCHA Enterprise the score runs from 0.0 to 1.0, and a higher score means lower risk: 1.0 is very likely a real human, 0.0 very likely abuse. Cloudflare uses the opposite scale idea with numbers 1 to 99, where 1 means "automated" and 30-99 counts as "likely human". The principle is identical: a probability, not a yes/no.

  1. The page loads the risk script, which quietly gathers device and behaviour signals while the user browses.
  2. On a sensitive action (login, sign-up, checkout) the page asks for a token bound to that action name and sends it with the form.
  3. Your backend sends the token, the site key and the expected action to the risk service (an assessment). Never trust a score the browser reports itself.
  4. The service returns token properties (valid, action) and a risk analysis: a score and reason codes such as AUTOMATION or TOO_MUCH_TRAFFIC.
  5. Your code decides: allow, add friction (OTP, email check), queue for review, or block. The score is an input to your policy, not the policy.

The backend call looks like this (project and key are placeholders):

curl -s -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  "https://recaptchaenterprise.googleapis.com/v1/projects/PROJECT_ID/assessments" \
  -d '{"event": {"token": "TOKEN_FROM_CLIENT", "siteKey": "SITE_KEY", "expectedAction": "login"}}'
{
  "riskAnalysis": { "score": 0.2, "reasons": ["AUTOMATION"] },
  "tokenProperties": {
    "valid": true,
    "hostname": "shop.example.com",
    "action": "login",
    "createTime": "2026-11-23T10:02:11.418Z"
  },
  "event": { "expectedAction": "login", "siteKey": "SITE_KEY" },
  "name": "projects/PROJECT_ID/assessments/b6ac310000000000"
}

Three checks before you even read the score: valid must be true; action must equal what you expected (a token minted on the newsletter page should not unlock login); and the hostname should be yours. Then apply thresholds per action. Google's guidance is to start by observing scores on your real traffic before acting, because the right cut-off differs by site and by action.

Challenge vs silent scoring: the friction ladder

ResponseUser seesUse when
Allow silentlyNothingHigh score (likely human) or verified good bot
Silent challengeNothing, or a split-second interstitial; the browser runs a JS proof (AWS WAF Challenge action)No token yet, medium risk; scripts without a real browser fail
Attestation tokenNothingPrivate Access Tokens / Privacy Pass (the OS or a trusted issuer vouches for a real device) or Cloudflare Turnstile (invisible browser checks): proves "real device or browser" without a puzzle; the trade-off is privacy and reliance on the issuer, and it says nothing about intent
Interactive CAPTCHAA puzzleMedium-high risk on a valuable action; accept some user drop-off
Step-up in the appOTP, email link, card 3-D SecureLogin or payment risk; bots cannot receive the OTP
Tarpit / shadow responseSlow or fake-success responsesScrapers and stuffers you want to waste time and money

Silent scoring wins because friction has a real cost: every puzzle loses some genuine customers, and CAPTCHA-solving farms make puzzles cheap for attackers anyway. Use challenges as a tool for uncertainty (to collect a stronger signal) rather than as a gate for everyone.

Do not block on one signal. AWS's own Bot Control docs note that an automation-extension signal fires whenever a user has such an extension installed, even if not using it, and suggest CAPTCHA instead of Block or combining labels. Data centre IPs include corporate VPNs; residential IPs include botnets. Combine signals; reserve Block for high confidence.
