The story

Explain like I'm 5

You go to a photo shop to print your holiday photos. The shop does not make you stand at the counter for an hour. The person takes your memory card, gives you a little ticket with a number, and says "come back later, or we will call you".

In the back room, workers take cards from a basket one by one. One worker prints. Another, a very careful old man, checks every photo, and he is slow - a few minutes each. If he is sick, the card just waits in the basket for tomorrow. Nothing is lost.

If a card is broken and fails three times, it goes on a special "problem shelf", and a manager looks at it. You can look at the shop's board any time: "Ticket 42: printing... checking... ready!"

Map the story to the system:

  1. Memory card handed over = upload. The file goes straight to object storage (S3) using a pre-signed URL, not through your servers.
  2. Ticket = document id + tracking link. Returned in milliseconds. The user does not wait for processing.
  3. Basket = queue. A message queue holds "process document 42" jobs.
  4. Workers = async consumers. Scan for viruses, extract text and fields (OCR or an LLM), call the slow third-party validator.
  5. Problem shelf = dead-letter queue after N failed tries, for a human or a replay.
  6. The board = status API + notifications. A state machine in the database; an event when it changes.

From your world

This is the top half / bottom half split from interrupt handling. The interrupt handler (the API) must return fast, so it only acknowledges the event and queues the heavy work to a softirq / workqueue (the worker). The queue is a ring buffer between them; the DLQ is your error counter plus a capture buffer. Visibility timeout is a watchdog: if the worker does not finish in time, the job is handed out again.
