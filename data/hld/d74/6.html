Deep dives

1. Sync vs async - and the hybrid

The Acko SDE-1 round was mostly about this. Lay out the options:

StyleHowGood whenBreaks when
Fully synchronousUpload request calls scan, OCR and vendor inline, returns the resultTiny volume, fast steps, user must know nowAny step is slow or flaky: threads pile up, timeouts, vendor outage = upload outage
Fully asynchronousReturn 202 + id; queue + workers; notify laterSlow or unreliable steps, spikes, many stepsUser genuinely needs an instant answer (then the UX feels slow)
HybridStart async; the API waits up to ~3 s for completion and returns the result if done, else 202Most jobs finish fast, a few do notAdds complexity; still needs the async path

Decision rule to say out loud: if a step is slow, external or can fail, take it off the request path. The 2-3 s vendor call is all three.

2. Queues: visibility timeout, retries and the DLQ

  • Visibility timeout (SQS default 30 s, max 12 hours) must be longer than the slowest normal job. For a 3,000-page PDF OCR, either set it high or have the worker extend it periodically (a heartbeat) while it works.
  • At-least-once means duplicates will happen (crash after the work but before delete). So every worker must be idempotent (next deep dive).
  • Retries with exponential backoff and jitter: wait random(0, min(cap, base x 2^attempt)) ("full jitter", recommended in the AWS Builders' Library) so 10,000 failed jobs do not retry in lockstep and hammer the recovering vendor.
  • Classify errors. Retry transient ones (timeout, 429, 503). Do not retry permanent ones (corrupt PDF, password-protected file, vendor says "invalid ID") - mark REJECTED at once.
  • DLQ after maxReceiveCount (say 5). Alarm on DLQ depth > 0. Provide a "redrive" tool to replay after a fix. SQS keeps messages 4 days by default, up to 14 days - set the DLQ to 14 so you have time to react.
  • Pointers, not payloads. The message is {document_id, step}. SQS's max message is 1 MiB; files are megabytes.

3. Idempotency: duplicate jobs, duplicate uploads, duplicate vendor calls

  1. Duplicate API calls. The client sends an Idempotency-Key; the server stores key -> response and replays it. Stripe's version is a good model: keys up to 255 characters, kept at least 24 hours, and a reused key with different parameters is an error.
  2. Duplicate queue messages. Each step is a conditional transition: UPDATE documents SET status='EXTRACTING', version=version+1 WHERE id=? AND status='UPLOADED'. If 0 rows change, another worker already did it - acknowledge and stop.
  3. Duplicate side effects. Write results keyed by (document_id, step) so a rerun overwrites the same row. Notifications carry an event_id; the notifier and webhook receivers dedupe on it.
  4. Duplicate vendor calls (they cost money). Cache results by (purpose, sha256); pass document_id as the vendor's idempotency/reference id if it supports one; record "call started" before calling so a restarted worker checks the vendor's status first.
  5. Duplicate uploads by the user. Same sha256 + same owner + same purpose within a window -> return the existing document.

"Exactly-once processing" is not something a queue gives you. Say: at-least-once delivery + idempotent consumers = exactly-once effects. Interviewers listen for this sentence.

4. Taming the slow third-party validator

  • Concurrency from Little's law: allowed rate 60/s x 2.5 s = 150 calls in flight. Size the worker pool to that, not to the queue depth.
  • Async I/O (Netty, asyncio, Go routines): one pod holds hundreds of waiting HTTP calls; threads are not burned on sleeping.
  • Bulkhead: the validator has its own queue and pool, so a vendor outage does not stall virus scanning and OCR for other documents.
  • Breaker open: stop calling; put jobs back with a delay (SQS message timers go up to 15 minutes); show users "verification delayed" instead of "failed".
  • Fallback vendor for critical flows (KYC), with the same idempotency rules.

The event must come from the same transaction as the status change. Writing the DB and then publishing to Kafka separately is a dual write: a crash in between leaves "VERIFIED" in the DB but no email. The outbox pattern (or CDC) fixes it.

6. Scaling the workers

  • Scale on queue depth / age, not CPU: the right signal is "messages waiting" or "age of oldest message". In Kubernetes, KEDA has an SQS and a Kafka scaler for exactly this.
  • One queue per stage (scan, extract, validate). Each stage scales independently: OCR is CPU-heavy and scales wide; validation is I/O-bound and capped by the vendor quota.
  • Priority: a separate high-priority queue for paying or time-critical customers, or weighted polling.
  • Spot / preemptible nodes for OCR are fine because jobs are idempotent and requeued on loss.

7. Optional: OCR and LLM extraction

Managed OCR has real limits you should quote. Amazon Textract's synchronous API takes one page, up to 10 MB; the asynchronous API takes PDFs and TIFFs up to 500 MB and 3,000 pages and notifies completion through SNS - itself an async job pattern. For LLM extraction: send the OCR text (or the image) with a strict JSON schema, get fields plus a confidence, validate with rules (PAN format, totals add up), and send low-confidence fields to human review (NEEDS_REVIEW). Treat document text as untrusted input: it must never be able to change the instructions given to the model.
