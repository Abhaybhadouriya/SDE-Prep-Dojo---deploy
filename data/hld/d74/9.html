LevelWhat the answer looks like
SDE-1 answer looks like..."Upload to S3 with a pre-signed URL, store metadata and status in SQL, push a job on a queue, workers process it with retries and a DLQ, and the user polls a status API from the tracking link."
SDE-2 adds..."Separate queues per stage as bulkheads; the vendor pool is sized by Little's law and capped by a token bucket with a breaker; every transition is a conditional update so duplicates are harmless; results and events commit together through an outbox; workers autoscale on queue age."
Why not just process the document synchronously in the upload request?

Because the validator alone takes 2-3 s and can fail. Inline, every slow or failed vendor call becomes a slow or failed upload, request threads pile up (100/s x 2.5 s = 250 blocked), client and load-balancer timeouts fire, and users retry - adding more load. Async returns a ticket in milliseconds, absorbs spikes in a queue and retries safely in the background.

How to answer

Give the rule: slow, external or failure-prone steps leave the request path. Then mention the hybrid (wait up to ~3 s, else 202) to show nuance.

Likely follow-ups
  • When is sync the right call? (tiny volume, fast and reliable steps, user must know now)
How does the user get a tracking link and see progress?

POST /documents returns a document id and an opaque tracking token at once. The tracking page calls GET /documents/{id} every few seconds (or opens an SSE stream). Status comes from the state machine row: UPLOADED, SCANNING, EXTRACTING, VALIDATING, then a final state with a reason. When it reaches a final state, an event triggers push/email so users who left are told too.

How to answer

Name the states explicitly; that is "good UX" in the JPMorgan prompt. Show what the user sees at each one.

Likely follow-ups
  • Polling vs WebSocket vs SSE for this? (polling or SSE; one-way updates)
  • Can the tracking link leak PII? (opaque token, no data in the URL)
Why store bytes in S3 and metadata in a database?

Different access patterns. Files are large, immutable and read rarely: object storage is cheap, durable and scales without limit. Metadata is small, changes through a state machine, and is queried by owner and status: a SQL DB gives transactions and indexes. Putting blobs in the DB bloats backups, replication and caches. Upload directly to S3 with a pre-signed URL so 200 MB/s never passes through app servers.

How to answer

One sentence per store, then the pre-signed URL as the key trick, then its security (short expiry, one key, bearer token).

Likely follow-ups
  • How do you know the upload finished? (S3 event or /complete, verify size and hash)
  • Very large files? (multipart upload)
A worker crashes halfway through. What happens to the job?

The message was hidden, not deleted. When its visibility timeout ends it becomes visible and another worker picks it up. The new worker reads the document's state, sees which step is done (conditional transitions + step history), and continues. After maxReceiveCount failures the redrive policy moves it to the DLQ and the document is marked FAILED with an alarm.

How to answer

Explain visibility timeout in one line, then idempotency, then DLQ. Draw the loop.

Likely follow-ups
  • What if a job takes longer than the timeout? (extend visibility as a heartbeat)
How do you avoid processing (and paying for) the same document twice?

Layered idempotency. API: Idempotency-Key and same-hash dedupe. Queue: each step is a conditional UPDATE (WHERE status = expected) so a duplicate message changes nothing. Results keyed by (document_id, step). Vendor: cache by (purpose, sha256), send document_id as a reference id, and record "call started" so a restarted worker checks the vendor before calling again. Notifications carry event_id for dedupe.

How to answer

Say "at-least-once delivery + idempotent consumers = exactly-once effects", then walk each layer.

Likely follow-ups
  • Is SQS FIFO with dedup enough? (only a 5-minute dedup window on send; it does not cover worker side effects)
The third-party validator is slow, rate-limited and sometimes down. How do you design around it?

Its own queue and worker pool (bulkhead). Pool size by Little's law (quota x latency, e.g. 60/s x 2.5 s = 150 in flight) using async I/O. A token bucket enforces the quota; per-call timeout; retries with exponential backoff and full jitter for 429/5xx only; a circuit breaker that opens on high error rate and delays jobs instead of failing them. Cache results by file hash. Show "verification delayed" in the UI. Optional fallback vendor for KYC.

How to answer

Start with the number (250 in flight at peak) - it shows why this needs design at all.

Likely follow-ups
  • Vendor down for 2 hours - what does the backlog look like and how do you drain it without exceeding quota?
How do retries and the DLQ work, and which errors should not be retried?

Transient errors (timeouts, 429, 503, connection reset) are retried with exponential backoff plus jitter up to a cap and a max attempt count. Permanent errors (corrupt or encrypted PDF, unsupported type, vendor says "document invalid") go straight to REJECTED with a reason - retrying them only wastes money. After max attempts the message moves to a DLQ; alarm on depth; a redrive tool replays after a fix.

How to answer

The error classification is what separates a good answer from "retry 3 times".

Likely follow-ups
  • How long are DLQ messages kept? (SQS: up to 14 days - set it to the max)
Explain event-driven architecture here. How do other services learn the document is verified?

The document service publishes domain events (document.uploaded, document.verified, document.rejected) to a topic. Notifier, loan underwriting, analytics and audit subscribe independently; the document service does not call them or know about them. Events are written through an outbox in the same transaction as the status change, keyed by document_id for per-document ordering.

How to answer

Contrast with request/response: loose coupling, easy to add consumers, but eventual consistency and harder tracing. Mention the outbox to avoid dual writes.

Likely follow-ups
  • Choreography or orchestration? (choreography for a short linear flow; an orchestrator such as Step Functions or Temporal when it branches or waits on humans)
How do you scale the workers, and on what metric?

Each stage is its own Deployment scaled on queue depth or age of oldest message (KEDA's SQS/Kafka scalers), not CPU. OCR scales wide on CPU-heavy nodes (spot is fine because jobs are idempotent); validation is capped by the vendor quota, so adding workers beyond the token bucket does nothing. Graceful shutdown releases or finishes messages on scale-in.

How to answer

Point out that "more workers" is wrong for the validator stage - its limit is external.

Likely follow-ups
  • With Kafka as the queue, what caps consumer parallelism? (partition count)
SQS or Kafka for the job queue? Defend it.

SQS (or RabbitMQ) for jobs: per-message ack, visibility timeout, built-in redrive to a DLQ, delays up to 15 minutes, no partitions to manage, and one slow job does not block others. Kafka for the event stream: many independent consumers, replay, ordering per key. Using Kafka for jobs works but you build retry topics and a DLQ yourself, and a slow message holds up its partition.

How to answer

The Amazon round "discussed every decision with trade-offs". Give the choice, two reasons, and what would make you switch.

Likely follow-ups
  • What if you need strict order of steps per document? (the state machine enforces it; FIFO groups by document_id if needed)
KYC documents are sensitive. What security controls do you add?

Short-lived pre-signed URLs for one key, PUT only; bucket blocks public access; SSE-KMS encryption; virus scan before any human or model opens the file; access to originals only through short signed GET links issued after an authorisation check; audit log of every access; retention and deletion rules per regulation; no PII in logs, URLs or queue messages; least-privilege IAM per worker stage.

How to answer

Group by lifecycle: upload, storage, processing, access, deletion.

Likely follow-ups
  • How do you stop a user uploading a 5 GB file to a 20 MB slot? (signed content-length condition / POST policy, check after upload)

Scenario: the vendor is down for two hours on month-end

Uploads are 100/s. The validator returns 503 for everything. The validate queue has 500K messages and is growing.

Weak answer: "Retry harder" or "scale up the validator workers".

Strong answer: The breaker is open, so workers stop calling and delay messages; uploads keep succeeding because the vendor is off the request path. Users see "verification delayed" and are told they will be notified. Scan and OCR keep running in their own pools. When the vendor recovers, the breaker half-opens with a few probes, then the token bucket drains the backlog at the contract rate (500K at 60/s is about 2.3 hours). If the business needs it faster, negotiate a temporary quota or route a share to a fallback vendor. Check that DLQ retention (14 days) and visibility settings cannot drop anything during the outage.

Likely follow-ups
  • Should new urgent documents jump the backlog? (priority queue for time-critical purposes)

Scenario: users receive two "verified" emails

About 0.5% of users get duplicate emails, more after deploys.

Weak answer: "Use exactly-once delivery."

Strong answer: Deploys kill workers after the status update but before the message delete, so the job runs again and publishes another event. Fix the root: transition with WHERE status = 'VALIDATING' so the second run changes nothing and emits nothing; emit the event through the outbox only on a real transition; give each event an id the notifier dedupes on; add graceful shutdown so workers finish or release in-flight messages.

Common mistakes: uploading bytes through the API; putting the file in the queue message; calling the vendor inside the request; retrying everything (including corrupt files) immediately and forever; no DLQ; no idempotency ("the queue guarantees once"); separate DB write and event publish; scaling workers on CPU; one shared pool so a vendor outage blocks OCR.
