Back-of-envelope estimation

Our own assumptions for a fintech/insurance platform. Day = 100,000 s (see Estimation).

  1. Volume. Assume 2M documents/day. 2M / 100K s = 20 uploads/s average; month-end peak 5x = 100/s.
  2. Bytes. Average 2 MB: 2M x 2 MB = 4 TB/day into object storage, ~1.5 PB/year before lifecycle rules. Inbound bandwidth at peak: 100/s x 2 MB = 200 MB/s - which is exactly why bytes go straight to S3, not through API servers.
  3. Metadata. ~1 KB per document row + ~10 state events of 200 B = ~3 KB: 2M x 3 KB = 6 GB/day. Easy for one SQL primary.
  4. The slow validator (Little's law). In-flight calls = rate x latency = 100/s x 2.5 s = 250 concurrent calls at peak. With one blocking thread per call that is 250 threads; with async I/O a few pods do it.
  5. Vendor rate limit. Assume the contract allows 60 calls/s. Peak demand is 100/s, so the queue grows by 40/s for the peak hour = 144K jobs behind. It drains when load drops. The queue is the shock absorber; the rate limiter protects the contract.
  6. Extraction compute. Assume 3 pages per document and ~1 CPU-second per page for OCR: 100/s x 3 s = 300 cores at peak, ~60 average. This is the stage that needs autoscaling.
  7. Queue size. Messages carry only ids (~200 bytes), not files. SQS's limit is 1 MiB per message, so never put the document in the message.

The punchline: "2-3 s per call" sounds small, but at 100 uploads/s it means 250 calls permanently in flight and a vendor limit you will exceed. That single number is why the design must be asynchronous with a rate-limited worker pool.
