Architecture: the request flow

Click Next or Play. Steps 1-3 are the fast path (milliseconds); steps 4-8 run in the background.

  1. Client calls POST /documents. The API checks auth and quotas, inserts a row (PENDING_UPLOAD), and returns a pre-signed PUT URL for one key plus a tracking link. No bytes touch the API.
  2. Client uploads directly to S3 with the pre-signed URL (multipart for big files). S3 stores it encrypted.
  3. S3 emits ObjectCreated (or the client calls /complete). A small handler checks size and hash, sets status UPLOADED and enqueues {document_id} on the process queue.
  4. Scan + extract workers pull jobs: virus scan, file-type check by magic bytes, then OCR or LLM extraction. Each step updates status with a conditional write and records history.
  5. Validation jobs go to a separate queue with a worker pool limited to the vendor's quota (token bucket). Each call has a timeout, retries with backoff, and a circuit breaker.
  6. The result lands in the DB in one transaction: status VERIFIED / REJECTED / NEEDS_REVIEW plus an outbox row, so status and event can never disagree.
  7. A relay publishes outbox rows to doc-events. The notifier sends push/email/webhook; the tracking page polls or listens via SSE.
  8. A job that fails N times moves to the DLQ; the document is marked FAILED, an alarm fires, and an operator can fix and replay it.
