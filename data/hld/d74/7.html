Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key document_id keeps each document's status events in order (uploaded, scanned, OCR done). Consumer-group sizing: 24 partitions allow 24 consumers; the heavy OCR work itself sits on a job queue (SQS-style), so a slow file does not block a partition. The API HPA scales on RPS; each worker stage is a Deployment that KEDA scales on queue depth.

With Kafka as the job queue you build retry topics and a DLQ topic yourself, and one slow message blocks its partition. See Kafka vs others, Delivery semantics.
