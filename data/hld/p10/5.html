How Kafka, Kubernetes and Docker help

Kafka: the location firehose

  • Partition key = cell id (or city). All pings from one area land in one partition, in order, so one consumer owns that area's index. See topics, partitions, offsets.
  • Compacted topic for "latest location". With cleanup.policy=compact and key = driver id, Kafka keeps only the newest value per driver, which is exactly the state a restarted geo shard needs to rebuild. See storage internals.
  • Stream processing per cell. Surge, heat maps and ETA features are per-H3-cell windowed aggregates in Flink or Kafka Streams. See Connect, Streams & Flink.
  • Hot partition warning. If the key is the city, one big city becomes one hot partition. Key by a finer cell, or by driver id and let the consumer re-bucket.

Kubernetes: stateful, memory-heavy shards

  • In-memory geo shards are best run as a StatefulSet: stable names (geo-0, geo-1) map cleanly to shard ownership.
  • Set memory requests equal to limits so the scheduler does not overpack nodes and an index does not get OOM-killed mid-rebuild. Use a readiness probe that only passes after the index has loaded (quadtree build, Kafka catch-up), so traffic never hits a cold shard. See scheduling & autoscaling.
  • Scale stateless pieces (gateway, matcher) with HPA on CPU or connections; scale shards deliberately, because adding one moves cells.
  • Use topology spread or anti-affinity so the replicas of one shard sit in different zones.
