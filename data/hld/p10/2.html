The solution ladder: naive to best

Climb one rung at a time. In an interview, say each rung out loud and say exactly when it breaks. That shows judgement, which matters more than naming a library.

Rung 0: scan everything and compute distance

SELECT * FROM places ORDER BY haversine(lat, lng, :me) LIMIT 10. This is correct and fine for a few thousand rows. It breaks quickly: Hello Interview's Yelp problem has 10 million businesses and 100 million daily users. Even 1,000 searches a second times 10 million distance checks is 10 billion maths operations a second.

Rung 1: a bounding box on two B-tree indexes

Turn the radius into a box (lat BETWEEN a AND b AND lng BETWEEN c AND d), then check exact distance on what comes back. Better, but the database still walks one long strip (picture above). It works for small, read-only tables. It breaks with many rows per strip or with frequent writes.

Rung 2: a fixed grid

Cut the map into equal squares, say 1 km. Store cell_id with each place and index it. A query reads your cell and its 8 neighbours. Simple and fast, but cells are the same size everywhere. A cell in central Mumbai may hold 50,000 shops while a cell in the sea holds none. That is a hot cell problem for both query cost and sharding, as the System Design Newsletter's summary of Tinder notes for evenly spaced grids.

Rung 3: geohash, a grid with a hierarchy

Geohash (Gustavo Niemeyer, 2008, public domain) halves the world again and again. The bits alternate: one bit for longitude (east half = 1, west = 0), then one for latitude (north = 1, south = 0), and so on. Every 5 bits become one base-32 character. Points that share a longer prefix are usually closer, so a plain string index with a prefix scan finds a cell. Click through to see the first character being built for Bengaluru (12.97 N, 77.59 E).

  1. Longitude first. Is 77.6 east of 0? Yes, so the first bit is 1 and we keep the east half.
  2. Then latitude. Is 12.97 north of 0? Yes, bit 1. We keep the top-right quarter.
  3. Longitude again. The range is now 0..180; 77.6 is below 90, so bit 0.
  4. Latitude again. The range is 0..90; 12.97 is below 45, so bit 0.
  5. Longitude once more. The range is now 0..90; 77.6 is above 45, so bit 1. Bits so far: 1 1 0 0 1.
  6. Five bits make one character. 11001 is 25, and position 25 of the alphabet 0123456789bcdefghjkmnpqrstuvwxyz is t.
  7. More characters, smaller cells. Each extra character adds 5 bits and cuts the cell into 32. Seven characters (tdr1v9q) is roughly a city block.
  8. The trap. Nearness does not guarantee a shared prefix. Points either side of a cell edge, the equator, the Greenwich meridian or the 180 meridian can share no prefix at all. So you always search the 8 neighbour cells too.

How long a prefix should you use? Pick the length whose cell is a bit bigger than your search radius, then search that cell plus its 8 neighbours. The cell sizes below are from the karanpratapsingh system-design book and the Wikipedia geohash table.

When geohash breaks: cells are still fixed size at a given length, so dense downtown cells hold too many points and rural ones hold none. Cells near the poles are distorted. And the 9-cell query reads up to 9 times the radius area.

Rung 4: quadtree, a grid that adapts to density

A quadtree is a tree where each node is a square and has exactly four children. Start with the whole world. When a square holds more than a threshold of points (about 100 is the common interview choice), split it into four. Dense cities get deep trees and the desert stays one big leaf. Hello Interview's write-up describes dense Manhattan reaching ten or more levels while rural Vermont needed about two.

A quick check for the interview (our own arithmetic): 10 million businesses, each stored as an 8-byte id plus two 8-byte coordinates, is about 240 MB of leaf data. Internal nodes add a little more. That fits in RAM on one ordinary server, so you can replicate the whole tree to every search server instead of sharding it. When a quadtree breaks: it is a pointer structure, so it is poor on disk; frequent moves (drivers) mean constant splits and merges with locking; and rebuilding a big tree on startup takes time, so new servers need a warm-up before they take traffic.

Level 4 - Advanced

Rung 5: S2 and H3, cells built for a round Earth

S2 (Google) projects the globe onto the 6 faces of a cube, then splits each face like a quadtree. Each cell id is a 64-bit integer laid out along a Hilbert curve, a space-filling curve that keeps nearby cells close in id order far better than geohash's Z-order. The picture below shows why.

From your world

Interleaving the bits of x and y (x1 y1 x0 y0...) is how geohash and Z-order build one id from two coordinates. The leading bits then name the big square and the later bits the small square inside it, so "cells inside this square" is a longest-prefix match, exactly like a routing table where 10.1.0.0/16 covers every 10.1.x.x address. Hilbert ids keep that prefix property and add one more: consecutive ids are always physical neighbours, like numbering switch ports in the order the cable actually snakes through the rack.

The S2 docs explain that a cell's descendants form one contiguous id range, so "everything inside this cell" is a simple id BETWEEN min AND max on a normal B-tree. A region coverer turns a circle into a small set of cells of mixed sizes. MongoDB's 2dsphere index is built on S2.

H3 (Uber, open-sourced 2018) uses hexagons. Each finer resolution has about one seventh the area of the one above. Uber's H3 blog gives the main reason for hexagons: every neighbour's centre is the same distance away. A square has two neighbour distances (edge and corner) and a triangle has three. That makes "rings" around a cell a good stand-in for a circle, and it makes smoothing values across neighbours simple.

Optional depth: levels, base cells and real cell sizes (safe to skip)

S2 levels. S2 runs from level 0 (one cube face) to level 30 (leaf cells about 1 cm across); each level splits a cell into 4.

H3 resolutions. There are 16 resolutions (0 to 15). Resolution 0 has 122 base cells, 12 of which are unavoidable pentagons (you cannot tile a sphere with hexagons alone) that Uber placed in the oceans.

Real sizes help you pick a level. From the H3 resolution table: resolution 7 averages 5.16 km² per hexagon, resolution 8 about 0.74 km² (edge about 530 m), resolution 9 about 0.105 km² (edge about 200 m). From the S2 cell statistics: level 12 averages 5.07 km², level 13 about 1.27 km², level 16 about 0.02 km². Hello Interview's example uses roughly 200 m H3 cells for dispatch.

When S2/H3 break: the libraries are more complex than geohash; H3 ids are not ordered by space, so you must compute the ring cell list and query cell IN (...) rather than a range scan; and H3 children only roughly fit inside their parent.

Rung 6: R-tree, when the data is shapes, not points

An R-tree groups objects into nested minimum bounding rectangles and stays balanced like a B-tree with page-sized nodes. PostGIS builds one through Postgres's GiST index framework. The PostGIS workshop explains the two-step trick: the index finds features whose boxes overlap the query box (fast), then an exact geometry test runs only on those candidates. On their test machine one query fell from about 300 ms to about 50 ms with the index. Use an R-tree when the question is about polygons: delivery zones, "is this point inside this geofence", roads. Its weakness is write cost: rebalancing and overlapping rectangles make it a poor fit for two million moving drivers a second. Elasticsearch uses a related disk-friendly structure, the BKD tree, for geo fields.

Moving things: the location-ingestion path

Static places (shops, lockers, hotels) change a few times a day. Moving things (drivers, delivery partners, friends) change every few seconds, and that flips the problem from read-heavy to write-heavy. Numbers from our sources:

4 sUber driver GPS interval (HighScalability, 2015 talk)
1M/swrites the Uber DISCO geo index was designed for
2M/s10M drivers / 5 s (Hello Interview Uber breakdown)
30 sno update for this long = remove stale driver (Hello Interview)

At that rate you never write each ping to a disk-based SQL table. The location is short-lived: only the latest value matters, and if you lose it, the driver sends a new one in 5 seconds. So you keep it in memory and accept small losses.

Two ways to build the in-memory index:

  • Redis GEO. GEOADD interleaves lat/long into a 52-bit geohash stored as the score of a sorted set. GEOSEARCH (Redis 6.2+) does radius or box search. The Redis docs give its cost as O(N + log M), where N is the number of items in the grid-aligned box around your shape. Hello Interview's Uber answer pairs it with a second sorted set of timestamps so stale drivers can be expired. Watch the key layout: one key per city (drivers:blr below) lives on one Redis shard, and one Redis primary handles on the order of 100K+ simple operations a second, so a big city's update stream makes it a hot key. For big cities, key by a coarser geohash or H3 cell instead (drivers:tdr1v) so writes spread across shards, and query the few cells that cover the search circle.
  • Your own sharded in-memory cell map. Uber's DISCO used S2 level-12 cells (about 3.3 to 6.4 km²) as the shard key. Each driver update maps to a cell, is written to that cell's shard, and is copied to a few replicas. Membership and routing used Uber's ringpop: a consistent-hash ring with SWIM gossip, where any node can take a request and forward it to the owner.
# driver 42 reports its position (longitude first!)
GEOADD drivers:blr 77.5946 12.9716 driver:42
# 10 nearest drivers within 3 km, with distance
GEOSEARCH drivers:blr FROMLONLAT 77.5946 12.9716 BYRADIUS 3 km ASC COUNT 10 WITHDIST
# faster but unsorted: stop once 10 are found
GEOSEARCH drivers:blr FROMLONLAT 77.5946 12.9716 BYRADIUS 3 km COUNT 10 ANY
# side index to expire stale drivers (score = last seen, epoch seconds)
ZADD drivers:blr:seen 1763880000 driver:42

import h3  # pip install h3   (h3-py v4 API)

BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"

def geohash(lat, lng, length=7):
    lat_r, lng_r = [-90.0, 90.0], [-180.0, 180.0]
    bits, use_lng = [], True
    while len(bits) < length * 5:
        rng, val = (lng_r, lng) if use_lng else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        if val >= mid:
            bits.append(1); rng[0] = mid
        else:
            bits.append(0); rng[1] = mid
        use_lng = not use_lng
    return "".join(BASE32[int("".join(map(str, bits[i:i + 5])), 2)]
                   for i in range(0, len(bits), 5))

Nearest-K: grow the search until you have enough

"Find the 10 closest" has no fixed radius. The standard approach: start small, and widen until you have at least K candidates, then rank them exactly. Stop growing at a maximum radius so a query in the desert does not scan a continent.

  1. Start at your own cell. One cell, one driver. We need five.
  2. Add ring 1. Six more hexagons (seven in total). Three drivers so far.
  3. Add ring 2. Twelve more hexagons (19 in total). Eight candidates, so stop widening.
  4. Rank exactly. A driver in ring 2 can be closer than one in ring 1's far corner, so always rank the whole candidate set, not ring by ring.
  5. Cap the growth. In a sparse area, stop at a maximum radius (say 10 km) and return fewer results, rather than fanning out to the whole country.

With Redis you get much of this for free: one GEOSEARCH ... BYRADIUS r ASC COUNT K, retried with a bigger r if it returns fewer than K. The Redis docs warn that a very large area with a small COUNT can still be slow, because the server has to sort everything it matched; ANY trades exact order for speed.

Sharding by geography

When one machine cannot hold the index or take the writes, split it by place. Options from simplest to best:

  1. By city or region. Bengaluru on one shard, Mumbai on another. Simple, and most queries never cross a city. Breaks when one city is far bigger than the rest, and at borders.
  2. By cell id with consistent hashing. Uber's DISCO shards by S2 cell; a query computes the cells that cover its circle and asks the shards that own them (scatter-gather). Hash spreading avoids hot cities but a query can touch several shards.
  3. By ranges of a space-filling curve, balanced by load. Tinder groups users into "geoshards" made of S2 cells. Tinder found most users' distance preference was within about 50 miles, so S2 levels 7 (about 45 miles) and 8 (about 22.5 miles) fit. Shards are sized by load rather than area, and the System Design Newsletter's Tinder write-up says a typical 160 km search queries about 3 shards on average. Tinder's own engineering post (summarised by ByteByteGo) reports that the geosharded design handled 20 times more computation than the old single index.

From your world

Scatter-gather across geo shards is like an ECMP fan-out with a merge at the end, and a hot downtown shard is an elephant flow pinned to one link. The fixes are the same family: split the hot prefix finer (more specific routes), spread shards across more machines, and keep a hash ring so a dead node's range moves to the next node instead of blackholing. Dropping a stale driver after 30 seconds without an update is a hold timer, exactly like a BGP or BFD session declaring the peer down.
