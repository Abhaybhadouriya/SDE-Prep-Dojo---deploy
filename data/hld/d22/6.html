Deep dives

1. "Players around me" and percentiles

Two calls: first r = ZREVRANK lb mallow007 (say 360), then ZREVRANGE lb (r-4) (r+4) WITHSCORES (356 to 364). Clamp at 0 for the top players. For a player ranked 3,000,000th out of 25,000,000, show a percentile instead of a scary number: top% = 100 x (r + 1) / ZCARD (the +1 because ZREVRANK is 0-based) = 3,000,001 / 25,000,000 = "top 12%". The percentile is the other side of the same number: 100 - 12 = the 88th percentile (you beat 88% of players). Do not mix the two words. Many real games show "Top 12%" below the top 1,000 because a seven-digit rank is depressing, not useful.

2. Ties and time windows

Ties. Redis orders equal scores by member name: ZRANGE ascending, ZREVRANGE / ZREVRANK descending - so on a high-score board read with ZREV* commands, "zara" always beats "aaron". Either way it is arbitrary and unfair. If the rule is "same score = same rank", compute rank as ZCOUNT lb (score +inf (number of strictly higher scores) instead of ZREVRANK. If the rule is "earlier achiever wins", pack a time component into the score so the number itself is unique:

# Redis scores are IEEE-754 doubles: integers are exact only up to 2**53 (about 9e15).
# Pack: high part = points, low part = "how early" in this tournament.
MONTH_SECONDS = 31 * 24 * 3600          # 2,678,400 < 2**22 (4,194,304)
SHIFT = 2**22

def packed(points: int, achieved_at: int, month_end: int) -> int:
    earliness = month_end - achieved_at   # bigger = earlier = better
    assert 0 <= earliness < SHIFT
    assert points < 2**31                 # 2**31 * 2**22 = 2**53 -> still exact
    return points * SHIFT + earliness

def points_of(score: float) -> int:
    return int(score) // SHIFT

The catch: with a packed score you can no longer use ZINCRBY blindly (it would add to the time part too). Read the current points, compute the new packed value, and write it with ZADD inside one Lua script. If the board is "best single score" instead of "total", use ZADD lb GT score member (Redis 6.2+): it only updates when the new score is greater - which is also naturally safe to retry.

Time windows. One key per window: lb:2026-11, lb:2026-11-23, lb:2026-W47. Each score event updates all the windows it belongs to (3 ZINCRBYs in the same Lua script). Set EXPIRE on daily keys so they clean themselves up. When the month ends, a job writes the final top N and every player's final rank to the database, then the old key expires. A "last 7 days" rolling board can be built with ZUNIONSTORE lb:last7 7 lb:day1 ... lb:day7, but that is O(total members) - run it every few minutes in the background, not per request.

3. Scaling past one Redis: 500M DAU

At 65 GB and 250,000 updates/s, one node is not enough. A sorted set is one key, and in Redis Cluster one key lives in one hash slot on one node (slot = CRC16(key) mod 16384), so you cannot just "turn on cluster mode" - you must split the board yourself. Two options:

A. Range (by score)B. Hash (by user)
Top 101 shard (the highest range)Ask all S shards for their top 10, merge S x 10 rows
My rankLocal ZREVRANK + ZCARD of every higher shard (cacheable)Sum of ZCOUNT lb (myScore +inf over all shards - S calls of O(log N), run in parallel
UpdateMay move a user between shards (remove + add); need a user-to-score lookup to find the shardAlways the same shard; simple
BalanceSkewed: most players have low scores; ranges need tuning as the month goes onEven by construction
Tail latencyGoodRead waits for the slowest shard

The pragmatic answer most strong candidates give: keep an exact board for the top players (say the top 10,000 - a small sorted set that only accepts scores above the current cut-off), and give everyone else an approximate rank from a score histogram ("you are in the top 12%"). Nobody needs to know they are exactly 81,234,567th. The histogram is an array of counts per score bucket; rank estimate = sum of counts in higher buckets. That turns a 65 GB problem into a few MB.

From your world

Hash partitioning a board by user_id is ECMP: a hash keeps each flow (user) on one path (shard), and load spreads evenly. The pain is the same too: to answer a global question ("total bytes across all paths", "who is the top talker") you must poll every member and merge. Range partitioning is like assigning prefixes to line cards by range - lookups go straight to one card, but a hot range overloads one card. Where it breaks: a flow never "moves" between ECMP members by itself; a player crossing a score boundary does.

4. Never count a match twice

Kafka gives at-least-once delivery to a normal consumer: if the leaderboard service crashes after ZINCRBY but before committing its offset, the event is delivered again after restart. ZINCRBY is not idempotent (running it twice is not the same as once), so mary would get +6. Fix it by recording the match_id in the same atomic step:

-- score.lua  -  KEYS[1]=board key, KEYS[2]=seen-set key, ARGV[1]=match_id, ARGV[2]=points, ARGV[3]=user
-- Redis runs a script atomically: no other command runs in the middle.
if redis.call('SADD', KEYS[2], ARGV[1]) == 1 then
  redis.call('EXPIRE', KEYS[2], 3024000)         -- keep ids ~35 days (the tournament + margin)
  return redis.call('ZINCRBY', KEYS[1], ARGV[2], ARGV[3])
else
  return false                                    -- duplicate: do nothing
end
$ redis-cli --eval score.lua lb:{2026-11} seen:{2026-11} , m-88f2 3 mary
"122"
$ redis-cli --eval score.lua lb:{2026-11} seen:{2026-11} , m-88f2 3 mary
(nil)

In Redis Cluster both keys of one script must be in the same slot - give them a hash tag: lb:{2026-11} and seen:{2026-11}. Here the braces are literal Redis syntax, not a placeholder: Cluster hashes only the part inside {...}, so both keys land in the same slot. (That is why the data model above writes placeholders as <boardId>, and why the demo above already uses the tagged names.) A seen-set of 1.5 billion match IDs per month is big; alternatives are a per-match key SET seen:m-88f2 1 NX EX 86400 (only needs to cover the retry window), or making the write absolute (ZADD with the total computed from the score DB), which is naturally idempotent.

5. Durability: Redis is a view, not the truth

Redis keeps data in RAM. It can snapshot (RDB = a point-in-time dump file) or log every write (AOF = append-only file of commands, replayed on restart) to disk, and it replicates to a replica - but replication is asynchronous, so a write acknowledged by the primary can be lost if the primary dies before the replica copies it. Restarting a large instance from disk also takes a while. So: keep the per-match log in a durable database (or in Kafka with retention longer than a month), treat Redis as a rebuildable index, and write a "rebuild board from the log" job before you need it. With the idempotency check above, replaying the log over a half-built board is safe.

Friends leaderboard. Fetch the player's friend IDs (usually hundreds), call ZMSCORE lb:2026-11 f1 f2 ... fN once, sort in the application. No new data structure needed - small N makes the "dumb" approach the right one. If friend lists are huge (followers on a social game), precompute per-user boards only for the most active users.
