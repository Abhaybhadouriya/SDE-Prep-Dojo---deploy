Back-of-envelope estimation

Numbers follow the ByteByteGo / System Design Interview Vol. 2 chapter. Use 100,000 (105) seconds per day - it is close to the real 86,400 and makes the maths easy. (Method: Back-of-Envelope Estimation.)

  1. Players per second. 5,000,000 DAU / 100,000 s = 50 players/s on average. Games peak in the evening, so assume peak = 5x average = 250 players/s.
  2. Score-update QPS. Each player plays 10 matches a day: 50 x 10 = 500 updates/s average, 500 x 5 = 2,500 updates/s at peak.
  3. Top-10 read QPS. If the board loads once when a player opens the game, that is about 50 reads/s. Even if it is 100x more because players keep refreshing, a precomputed top 10 is trivial to cache.
  4. Memory per entry. user_id as a 24-character string (24 bytes) + a small integer score (2 bytes) = 26 bytes of raw data.
  5. Memory for one board. Worst case every MAU has an entry: 26 bytes x 25,000,000 = 650 MB. The book doubles it for skip-list and hash overhead: about 1.3 GB. One Redis server holds that easily.
  6. Can one Redis node take the load? 2,500 writes/s plus a few hundred reads/s is far below what a single Redis instance handles (single-threaded, but each sorted-set op is microseconds). So for 5M DAU: one primary + one replica.
  7. Now 100x: 500M DAU. Memory 650 MB x 100 = 65 GB; peak updates 2,500 x 100 = 250,000/s. Now we must shard (deep dive 3).
  8. History. One snapshot of the top players per month is tiny. The full per-match log (user, match, points, time) is the source of truth: 5M x 10 = 50M rows/day; at about 50 bytes each that is about 2.5 GB/day in a normal database or object storage.

Be honest about overhead. 26 bytes is the raw payload. Real per-member memory in a Redis sorted set is several times larger (skip-list node with pointers and levels, hash-table entry, string headers). In an interview say "the book doubles it; in production I would load 1 million fake members and run MEMORY USAGE to get the real number". Interviewers love a candidate who measures instead of guessing.

From your world

You already think in "packets per second on one ASIC". Same skill: 2,500 updates/s is a tiny rate for a RAM data structure - like a control-plane process handling 2,500 route updates/s. The scary number in this design is not QPS, it is one global sorted order that cannot be split as easily as a hash table. That is where the design gets interesting. Where it breaks: an ASIC's per-packet work is independent, so you add ports to add capacity; a global rank is not independent - every update can change many players' ranks, so "add another box" does not simply add capacity.
