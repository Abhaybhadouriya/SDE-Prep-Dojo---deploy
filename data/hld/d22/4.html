Why not just SQL? The rank query in SQL is "count everyone with a higher score": SELECT COUNT(*) FROM scores WHERE board_id = ? AND score > ?. With an index on (board_id, score) it is a range scan - fine for thousands of rows, but at millions of rows and thousands of updates per second every update also rewrites the index, and every rank read walks a large part of it. The book reports a full rank over millions of rows taking tens of seconds. A sorted set keeps the order incrementally, so a rank is a walk down a few levels instead of a count.

Inside a Redis sorted set

A sorted set is two structures glued together: a hash table (member to score, so "what is Mary's score?" is O(1)) and a skip list (score order, so "rank" and "range" are O(log N)). A skip list is a sorted linked list with extra "express lanes" on top: each higher lane skips more nodes, like taking the highway and getting off near your exit. Redis also stores, on each express-lane link, how many nodes it skips (the "span"), so while it walks to a member it can add up the spans and get the rank for free. Small sets (up to zset-max-listpack-entries, 128 by default) use a compact listpack instead.

From your world

A skip list is the same idea as a multi-level lookup you have seen in routing tables and page tables: a coarse index on top, finer below, so a lookup touches O(log N) entries instead of scanning. It is randomised (each node picks its height by coin flips) instead of balanced by rotations, which keeps inserts simple and lock-free friendly. Where the analogy breaks: a trie / page table indexes by key bits; a skip list indexes by sort order, which is exactly what "rank" needs.
