Architecture: follow one score

Click Next or Play. The upper path is the write (a match ends); the lower path is the read (a player opens the board).

  1. Match ends. The client reports "game over", but it does not send a score. Clients are untrusted.
  2. Game server verifies and publishes. It decides the points and publishes {user_id, match_id, points} to the Kafka topic score-events, keyed by user_id so one user's events stay in order. Kafka is its only write: a second consumer group copies every event into the score DB (the durable match log, dashed arrow). Writing the DB and Kafka separately from the game server would be a dual write. (Small games can call the leaderboard service directly; Kafka earns its place when analytics, achievements and anti-cheat also want the same events.)
  3. Leaderboard service consumes. A consumer group reads the topic. More partitions = more consumers in parallel.
  4. Update Redis atomically. A short Lua script runs inside Redis: "if this match_id is new, remember it and ZINCRBY lb:2026-11 3 mary1934". One round trip, no double counting on retry. Commit the Kafka offset after it succeeds.
  5. Read path. The player opens the board. The request goes through the load balancer / API gateway to a stateless leaderboard API (any pod can serve any request).
  6. Read from Redis. Top 10 = ZREVRANGE lb:2026-11 0 9 WITHSCORES; my rank = ZREVRANK; names come from a small profile cache. All tens of milliseconds.
  7. Failure plan. Redis is a fast view, not the truth. If it is lost, promote the replica; if both are lost, rebuild the set from the score DB (or by replaying Kafka from the start of the month).

Avoid the dual write. If the game server wrote a row to the score DB and then, separately, published to Kafka, a crash between the two leaves them disagreeing: the DB has a match the board never sees, or the board counts a match the DB does not have. That is the dual-write problem the CDC Pipeline design warns about. Two safe shapes: (1) Kafka is the only write (as drawn here) and a consumer fills the DB, so both are fed from one log; or (2) write the match row and an outbox row in the same DB transaction and let CDC (Debezium) relay the outbox to Kafka. Either way there is exactly one place where the write can succeed or fail.

Try it on your laptop

Everything above is a few Redis commands. Start Redis in Docker and play (see Run and manage containers if docker run is new):

docker run -d --name lb -p 6379:6379 redis:7.4
docker exec -it lb redis-cli
127.0.0.1:6379> ZADD lb:2026-11 120 ravi 118 anu 117 joe 116 mary
(integer) 4
127.0.0.1:6379> ZINCRBY lb:2026-11 3 mary
"119"
127.0.0.1:6379> ZREVRANGE lb:2026-11 0 2 WITHSCORES
1) "ravi"
2) "120"
3) "mary"
4) "119"
5) "anu"
6) "118"
127.0.0.1:6379> ZREVRANK lb:2026-11 mary
(integer) 1
127.0.0.1:6379> ZCARD lb:2026-11
(integer) 4
127.0.0.1:6379> ZCOUNT lb:2026-11 (119 +inf
(integer) 1
127.0.0.1:6379> ZMSCORE lb:2026-11 anu joe nobody
1) "118"
2) "117"
3) (nil)
  • ZREVRANK is 0-based: mary is rank 1 means second place. Add 1 before showing it.
  • ZCOUNT key (119 +inf = "how many have a score strictly greater than 119". That is the tie-aware rank: players with equal scores get the same rank. We will reuse this for sharding.
  • ZMSCORE (Redis 6.2+) fetches many scores in one call - perfect for a friends board.
  • Newer Redis also has ZRANGE key 0 9 REV WITHSCORES, which replaces ZREVRANGE; both work.
