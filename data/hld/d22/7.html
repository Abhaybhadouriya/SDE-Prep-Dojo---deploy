Where Kafka, Kubernetes and Docker fit

📨

Kafka

Topic score-events, keyed by user_id so one player's events are ordered. Decouples the game server from the leaderboard; analytics, achievements and anti-cheat read the same events. Retention longer than a month = you can rebuild a board by replay.

 👥

Consumer group

The leaderboard service is one consumer group. Consumer lag (how far behind the newest event it is) = how stale the board is. Alert on it.

 ☸️

Kubernetes

Leaderboard API and consumer as Deployments; the API scales with an HPA on CPU/RPS; consumers scale up to the partition count. Redis as a managed service or a StatefulSet with an operator.

 🐳

Docker

One docker compose up gives you Kafka + Redis + the service locally for testing the Lua script and the rebuild job.

 
# compose.yaml - local lab: Kafka (KRaft, single node) + Redis
services:
  kafka:
    image: apache/kafka:3.9.0
    ports: ["9092:9092"]
  redis:
    image: redis:7.4
    ports: ["6379:6379"]
docker compose up -d
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic score-events --partitions 6 --replication-factor 1
docker compose exec kafka /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic score-events --property parse.key=true --property key.separator=:   # Kafka 4.2+: --reader-property
> mary:{"match_id":"m-88f2","points":3}

The apache/kafka image starts a single KRaft broker with defaults, which is enough for a lab. A full end-to-end version of this pattern (producer, consumer, sink, on Kubernetes) is built step by step in the ShopStream pipeline track.
