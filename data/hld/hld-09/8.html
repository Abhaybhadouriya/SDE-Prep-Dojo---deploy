Time and ordering: Lamport and vector clocks

Machine clocks drift and NTP can step them backwards, so "the write with the larger timestamp wins" (last-write-wins, LWW) can silently throw away a newer write from a node whose clock runs slow. Distributed systems therefore track causality with counters instead of wall time.

  • Lamport clock - one counter per node. Increment on every event; on receiving a message, set your counter to max(yours, theirs) + 1. If A caused B, then L(A) < L(B). But the reverse is not true, so Lamport clocks cannot tell you that two events were concurrent.
  • Vector clock (version vector) - one counter per node carried with each version, like [A:2, B:1]. Version X happened-before Y if every counter in X is <= the one in Y. If neither dominates, the writes were concurrent and you have a conflict to resolve. Dynamo keeps both siblings and lets the application merge them (the cart takes the union of items).
  • Hybrid logical clock - wall-clock time plus a logical counter, so versions sort roughly by real time but still respect causality. CockroachDB-style databases use this. Google Spanner goes further with TrueTime: GPS and atomic clocks give a bounded uncertainty window, and a commit waits out that window.

For collaborative editing, the conflict-free relatives of vector clocks are CRDTs - see d23 Collaborative Editor.
