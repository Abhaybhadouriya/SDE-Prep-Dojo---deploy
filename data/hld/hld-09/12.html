Interview questions

Explain quorum reads and writes. Why does R + W > N give you the latest value?

Each key is stored on N replicas. A write is successful after W acks, a read queries R replicas. If R + W > N, any read set and any write set share at least one replica, so the read always reaches one node that has the latest acknowledged write; you return the version with the highest version (vector clock or timestamp) and read-repair the others. With N=3, W=2, R=2 you tolerate one replica down for both reads and writes, which is the Dynamo paper's common setting.

How to answer

Draw three boxes and two overlapping circles. State the pigeonhole argument. Then add the caveat: sloppy quorums and concurrent writes still allow anomalies, so it is not linearizability.

Likely follow-ups
  • What happens to a write if only 1 of 3 replicas is reachable? (fails, or sloppy quorum + hinted handoff)
  • How would you tune it for a read-heavy workload?
  • What is LOCAL_QUORUM and why use it multi-region?
Walk me through how Raft elects a leader and how it prevents two leaders.

Followers expect heartbeats. When one's randomized election timeout (typically 150-300 ms) fires, it increments the term, votes for itself and sends RequestVote. Each server grants one vote per term, and only to a candidate whose log is at least as up to date as its own. A candidate with a majority becomes leader and heartbeats immediately. Two leaders in one term are impossible because each needs a majority and two majorities would need some server to vote twice in one term. A stale leader from an old term steps down as soon as it sees a higher term.

How to answer

Terms, timeouts, votes, majority, up-to-date check, step-down. Mention randomization avoids repeated split votes, and give the timing rule broadcast << election timeout << MTBF.

Likely follow-ups
  • What if the vote splits 2-2 in a 5-node cluster with one down?
  • Why must the voter check the candidate's log?
  • Can an old leader still serve reads? (Only with a lease or a read-index round trip.)
Why do etcd and ZooKeeper clusters use 3 or 5 nodes, never 4 or 6?

A majority of n is floor(n/2)+1. A 3-node cluster needs 2 and tolerates 1 failure; a 4-node cluster needs 3 and still tolerates only 1. The fourth node adds cost and one more participant per write but no extra fault tolerance. 5 tolerates 2. Beyond about 7, writes get slower because every commit fans out to more replicas, which is why etcd's FAQ caps practical size around 7.

How to answer

Write the table for 3, 4, 5. Mention the Kubernetes control plane runs 3 or 5 etcd members.

Likely follow-ups
  • How do you spread 5 members over 3 availability zones?
  • What happens to Kubernetes if etcd loses quorum?
Design a distributed lock for booking a locker / seat. How do you make it safe?

First ask whether a lock is needed: if the slot lives in one database, a conditional update (UPDATE slot SET holder=? WHERE id=? AND holder IS NULL) or a version check is simpler and safe. If a cross-system lock is needed, use a consensus-backed store (etcd lease or ZooKeeper ephemeral sequential znode) with a TTL so crashed holders release automatically. Every grant returns a fencing token (etcd revision, ZooKeeper zxid). The resource being protected rejects any write with a token lower than the highest it has seen, which neutralises a holder that paused past its lease.

How to answer

Efficiency vs correctness lock; lease + TTL; the GC-pause story; fencing token; "prefer DB constraints when possible".

Likely follow-ups
  • Why not Redis SETNX? Why not Redlock?
  • What TTL would you choose and how do you renew?
  • How do waiters avoid a thundering herd? (watch only your predecessor znode)
Is Redis SETNX with a TTL a correct distributed lock?

It is fine as an efficiency lock (avoid duplicate work) if you release with an atomic compare-and-delete so you never delete someone else's lock. It is not a correctness lock: the holder can pause beyond the TTL, a failover to an async replica can lose the key, and there is no monotonically increasing token for fencing. Kleppmann's critique of Redlock adds that its safety relies on bounded clock drift and pauses. For correctness, use etcd/ZooKeeper plus fencing, or the database.

How to answer

Split "efficiency vs correctness" up front, then list the three failure modes: pause, replica failover, no fencing.

Likely follow-ups
  • Could you build fencing on top of Redis with INCR?
  • What does Uber or your company use for leader election?
What is split brain, and how do you prevent it in an active-passive database pair?

Split brain is when a partition makes both nodes think they are primary and both take writes, creating divergent histories. With only two nodes you cannot get a majority, so add a third voter (a witness/arbiter, or put leadership in an external etcd/ZooKeeper). Only the side that holds the majority-backed lease may write. Combine with fencing: bump an epoch at each failover and have clients/storage reject the old epoch; optionally STONITH (power off the old primary).

How to answer

Define it, explain why 2 nodes cannot decide, give quorum + epoch fencing, then talk about failover time versus false failovers.

Likely follow-ups
  • Active-active vs active-passive: when is each worth it?
  • How fast can failover be? (Meta: about 2 s with Raft vs 20-40 s before)
Vector clocks vs last-write-wins: when do you need vector clocks?

LWW keeps the version with the larger timestamp. It is simple but silently drops concurrent writes and suffers from clock skew. Vector clocks carry a counter per writer and can tell "happened before" from "concurrent". When concurrent versions appear, the store keeps both siblings and the application merges them (Dynamo's cart merges items). Use LWW when losing a concurrent update is acceptable (a profile photo), vector clocks or CRDTs when it is not (a cart, a document).

How to answer

Draw the A, B, C example. Mention size growth and truncation (Dynamo trims at about 10 entries) and that CRDTs are the modern alternative.

Likely follow-ups
  • Why did deleted items reappear in Dynamo's cart?
  • What is a hybrid logical clock?
Design a distributed unique ID generator. What are the options?

Clarify: 64-bit or 128-bit allowed, must IDs be time-sortable, what throughput. UUIDv4 needs no coordination but is 128 bit and unsortable. A ticket server is simple but central. Snowflake packs 41 bits of milliseconds, 10 bits of machine id and 12 bits of sequence: 4,096 IDs per ms per machine, 1,024 machines, about 69 years, sortable, and generated locally with no network hop. Assign machine ids through ZooKeeper/etcd leases or StatefulSet ordinals, and refuse to issue IDs if the clock goes backwards.

How to answer

Requirements first, then the options table, then pick Snowflake and go deep on the clock and machine-id problems.

Likely follow-ups
  • What if you need more than 4,096 IDs in a millisecond?
  • How do you avoid exposing order volume through sequential IDs?
  • How would you handle a leap second or NTP step?
How does a cluster of 1,000 nodes know who is alive without a central monitor?

Gossip. Every second each node picks a random peer and exchanges its membership table with heartbeat counters. A rumour reaches all nodes in about log2(1000), roughly 10 rounds. Each node runs a local failure detector; Cassandra uses phi accrual, which turns observed heartbeat inter-arrival times into a suspicion score so jittery links get more slack. Dead nodes are marked down after the score crosses a threshold, and that status gossips out too.

How to answer

Contrast with central heartbeats (O(N) load, single point), give the log N spread, mention false positives and tuning.

Likely follow-ups
  • Is gossip strongly consistent? (No - use consensus for decisions.)
  • How do seed nodes help a new node join?
How is Paxos different from Raft, and why do most new systems choose Raft?

Both are crash-fault-tolerant majority consensus with the same fault tolerance. Basic Paxos agrees on a single value in two phases (prepare/promise, accept/accepted) with any proposer; Multi-Paxos adds a stable leader to skip phase 1 and allows holes in the log. Raft makes the leader mandatory, keeps the log contiguous, and specifies elections, log repair and membership changes as one package. That makes it easier to implement and verify, which is why etcd, KRaft, CockroachDB and TiDB use Raft, while Chubby and Spanner use Paxos.

How to answer

Give the two Paxos phases and the "must re-propose an accepted value" rule, then the three practical differences.

Likely follow-ups
  • What does Byzantine fault tolerance add, and who needs it?
  • How does Raft change membership safely? (joint consensus / one member at a time)
Two replicas of a key-value store may have drifted. How do you find and fix the differences efficiently?

Read repair fixes keys that are read. For the rest, run anti-entropy with Merkle trees: each replica hashes its key ranges into a tree; compare roots, then descend only into children whose hashes differ, and stream just those ranges. Cost is proportional to the difference. Hinted handoff covers short outages so the trees have little to fix.

How to answer

Three layers: hinted handoff (short failures), read repair (hot keys), Merkle anti-entropy (everything else).

Likely follow-ups
  • What happens to the tree when nodes join and key ranges move?
  • How often would you run repair?

Scenario: the cron job ran twice

Your billing job runs on 3 pods for availability. One night customers are charged twice. Logs show two pods both believed they were leader for about 40 seconds after a network blip. Leadership is a Redis key with a 30 s TTL.

Weak answer: "Increase the TTL to 5 minutes so leadership doesn't flap."

Strong answer: the old leader paused or was partitioned past the TTL, the new leader took over, and the old one never checked again before charging. Fix in layers: (1) move leader election to an etcd/ZooKeeper lease (Kubernetes Lease objects do this) so it is consensus-backed; (2) include the leader epoch/fencing token with every charge and make the billing table reject older epochs; (3) make the charge itself idempotent with an idempotency key per customer per billing period, so even a duplicate run is harmless. Measure: alert when two pods claim leadership.

Likely follow-ups
  • Which of the three fixes would you ship first and why?
  • How does idempotency relate to exactly-once? (see hld-10)

Scenario: writes stall in one region

You run a 5-node etcd/Raft cluster spread as 2 nodes in us-east, 2 in eu-west, 1 in ap-south. The transatlantic link fails.

Weak answer: "Both sides keep working, Raft handles it."

Strong answer: the side that can reach 3 of 5 keeps quorum. us-east (2) + ap-south (1) = 3 if that link still works, so it keeps or elects the leader; eu-west (2) cannot commit writes and should serve only stale/follower reads or fail. Every commit now pays the us-east to ap-south RTT. If write latency matters more, keep the voting quorum inside one region and replicate asynchronously elsewhere (or use a FlexiRaft-style small data quorum), accepting a slower, manual cross-region failover.

Likely follow-ups
  • How would you place 5 members across 3 zones in one region instead?
  • What happens to clients connected to eu-west?
