Quorums: why R + W > N works

In a leaderless store each key lives on N replicas. A write waits for W of them to say "stored". A read asks R of them and takes the newest version. If R + W > N, the set of nodes you read from and the set you wrote to must overlap in at least one node, so every read sees at least one copy of the latest write. That is the pigeonhole principle, nothing more.

When the quorum is not enough: sloppy quorum, hinted handoff, read repair

  • Sloppy quorum + hinted handoff. Dynamo writes to the first N healthy nodes on its preference list, not strictly the N "home" nodes. If home node A is down, node D takes the write with a hint ("this belongs to A") and hands it back when A recovers. This keeps the store "always writeable", which is why the Amazon shopping cart never rejects an add-to-cart. The price: during that window R + W > N no longer guarantees overlap with the home nodes.
  • Read repair. When a read sees replicas disagree, the coordinator writes the newest version back to the stale ones.
  • Anti-entropy. A background job compares replicas with Merkle trees and fixes keys nobody has read lately.

Careful: R + W > N is not "strong consistency". Concurrent writes, sloppy quorums and clock-based "newest" choices can still give surprising results. If you need a single agreed order of operations (locks, leader identity, bank balances), you need consensus, not just a quorum read.
