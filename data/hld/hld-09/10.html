Generating unique IDs across machines

Once you shard a database, the auto-increment column no longer works: each shard would hand out id 1. Interviewers love this because every design needs IDs (tweets, orders, short URLs). Options from simplest to best-known:

ApproachSizeSortable by time?CoordinationWeak spot
UUID v4 (random)128 bitNoNoneBig; random inserts fragment B-tree indexes
UUID v7 / ULID128 bitYes (ms prefix)NoneStill 128 bit; ordering only as good as clocks
Ticket server (central DB counter)64 bitYesEvery ID hits one DBBottleneck/SPOF; mitigated with 2 servers (odd/even) or block allocation
Range/block allocation64 bitRoughlyOne DB call per block of e.g. 1,000Gaps on crash; not strictly ordered across nodes
Snowflake (time + machine + sequence)64 bitYes (k-sorted: roughly ordered, each id at most k positions from its true time order)Only to assign machine idsClock going backwards; machine id assignment

The dangerous part is the clock. The original Twitter Snowflake rejects requests (it throws an invalid-clock error) while the clock is behind its last-issued timestamp; other implementations wait it out or borrow from the sequence bits; long backward steps need alerting. Machine IDs must be unique, so they are usually handed out by ZooKeeper/etcd (a lease per worker) or by the pod ordinal of a Kubernetes StatefulSet. Full design: d31 Unique ID Generator.
