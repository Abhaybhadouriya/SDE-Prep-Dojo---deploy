The story: the class notebook

Explain like I'm 5

Five friends keep the same class notebook, each with their own copy. When the teacher says "homework is page 12", they all must write the same thing in the same order. But sometimes a friend is sick, or a note passed across the room gets lost. So they make a rule: one friend is the captain. Only the captain decides what gets written next. The captain reads it out, and once at least three of the five have written it down, it counts. If the captain goes quiet for too long, the others hold a vote for a new captain - and you need three votes to win, so there can never be two captains at once.

From your world

You have run this already: VRRP or HSRP elects one active router, OSPF hello and dead timers decide when a neighbour is gone, and a RAID-1 mirror keeps two copies of every block. This page is those same ideas made safe for a network that can split in half: majority votes instead of "highest priority wins", and an epoch number so an old master that wakes up cannot do damage.

That is the whole page in one story. The notebook is a replicated log (the same list of changes copied onto several machines). The captain is a leader. "Three of five" is a majority quorum (the smallest group whose agreement counts). The vote is leader election. Going quiet is detected by heartbeats (small "I am alive" messages). And the rule that makes all of it safe is that any two groups of three out of five must share at least one friend, so a decision can never be silently forgotten.

Every big system you will design in an interview - a key-value store, a lock service, a job scheduler, Kafka itself, Kubernetes' etcd - is built on these few ideas. You rarely implement them yourself. But interviewers want to hear that you know which tool gives you which guarantee, and what breaks when you pick the wrong one.
