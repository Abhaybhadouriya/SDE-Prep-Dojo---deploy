Back-of-envelope estimation

Method from Back-of-Envelope Estimation. The goal is to show the interviewer that the load is small, so your effort goes into correctness and the edge.

~1Mcompartments
~500Kparcels per day
~60/speak drop-offs
~1K/speak locker searches
  1. Compartments 25,000 locations x 40 compartments = 1M compartments.
  2. Parcels per day A parcel sits about a day before pickup (Educative notes most customers collect within 48 hours), plus time between parcels. Assume each compartment turns over 0.5 times a day: 1M x 0.5 = 500K parcels a day.
  3. Drop-off rate 500K / 86,400 = about 6 per second on average. Drivers arrive in waves (morning routes, holiday season), so take 10x = about 60 per second at peak. Each drop-off is a handful of writes.
  4. Pickups About the same count as drop-offs: 500K a day, spread over the day and evening.
  5. Locker searches at checkout Assume 10M checkout sessions a day show a locker map with one geo query each: 10M / 86,400 = about 115 per second, peak 10x = about 1K per second. Read-only and cacheable.
  6. Kiosk heartbeats 25,000 kiosks x one heartbeat per minute = about 420 per second of tiny messages, plus door and sensor events (open, close, occupied) of about 4 per parcel = 2M a day.
  7. Storage Compartments: 1M x 200 bytes = 200 MB. Reservations and assignments: 500K a day x 1 KB = 0.5 GB a day, about 180 GB a year. Audit events: 2M x 300 bytes = 0.6 GB a day. All small; keep audit in cheap storage.
  8. Pickup code space A 6-digit code has 1,000,000 values. With 40 active codes at one kiosk, a random guess hits some code with probability 40 / 1,000,000 = 1 in 25,000. Keep this number; it drives the security deep dive.

What the numbers tell you: one well-indexed relational database could hold all of it. The design is about atomic allocation, capacity prediction, security of a 6-digit code, and offline kiosks, not about sharding petabytes.
