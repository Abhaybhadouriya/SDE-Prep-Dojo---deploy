Deep dives

1. When to reserve, and what exactly to reserve

There are three options and interviewers like to hear all three.

OptionWhat happensProblem
Pick a specific compartment at checkoutBox C_17 is held from checkout until deliveryWastes capacity: a box sits empty for a day or more waiting for a truck
Reserve nothingHope a box is free when the driver arrivesFailed drops on busy days; the parcel goes back on the truck
Reserve capacity per (locker, size, day), assign at drop-offA counter says "40 M-boxes, 31 held for Wednesday"; the exact box is chosen when the driver is standing thereNeeds a forecast of how many boxes will be free that day (parcels already inside may not be picked up yet)

The third is the usual answer. Educative's write-up describes it as reserving capacity by probability rather than a fixed box, and choosing the compartment at drop-off. The forecast matters: total for Wednesday is not "40", it is "40 minus the parcels we expect still to be inside on Wednesday". A simple model: count parcels due to expire or likely to be picked up by then (most are collected within 48 hours) and keep a safety buffer. Their example splits a 100-compartment locker into 30% for same-day, 50% for next-day and 20% buffer. When in doubt, show fewer lockers: a missing option costs a little; a broken promise costs a re-delivery.

2. Concurrency: never one box for two parcels

Two drivers stand at the same kiosk and both ask for an M-box at the same moment. Or one driver's kiosk retries after a timeout. Without care, both requests read "C_17 is AVAILABLE" and both get it.

  • Compare-and-set in the database (the main answer). Claim with UPDATE ... WHERE state = 'AVAILABLE' AND version = v. Exactly one request wins; the loser picks the next candidate. No lock service needed. This is optimistic concurrency, explained in Dealing with Contention.
  • Serialise at the kiosk. The kiosk agent processes one door operation at a time per compartment (a single-threaded command queue), which also prevents a pickup and a drop-off on the same box at once.
  • Idempotency. A unique request_id on the assignment row means a retry finds the existing assignment and opens the same door.
  • Distributed locks? The interviewer may ask "would you use a distributed lock per locker?". You can (a lease in ZooKeeper or etcd), but be careful: Martin Kleppmann's well-known essay explains that a process can pause after its lease expires and still act as if it holds the lock, so a lock that protects correctness needs fencing tokens that the storage checks. A version column already is that fencing check, which is why compare-and-set is simpler and safer here. See Distributed Lock Service.

From your world

The version-checked update is cmpxchg: read the value and its version, then write only if nobody changed it in between. The losing CPU retries with fresh data. A distributed lock with a lease is like a spinlock held by a thread that might get descheduled for a long time: other CPUs may decide it is dead. Fencing tokens are the generation number that makes a stale holder's write fail.

3. Offline kiosks: edge-first design

Kiosks live in metro stations, shops and campuses. Their network will fail. The rule: pickups must keep working offline, drop-offs should mostly work, and new reservations can pause.

  • Push valid codes down early. As soon as a code is issued, the cloud pushes its hash, compartment and deadline to the kiosk. The kiosk can validate a typed code locally (hash it and compare) without a round trip.
  • Desired vs reported state. AWS IoT's Device Shadow is a good model to name: the cloud writes the desired state (valid codes, out-of-service compartments), the device writes its reported state (doors, sensors), and the difference is a delta. Every update carries a version, so a device that receives deltas out of order can discard older ones. When the kiosk reconnects, it fetches the current shadow and catches up.
  • Outbox with sequence numbers. Every door event is written to local flash with a per-kiosk sequence number before it is sent. The cloud acknowledges by sequence. After an outage the kiosk replays from the last ack; the cloud ignores duplicates by (locker_id, seq).
  • Pre-assigned drop-offs. For a driver's route, the cloud can pre-assign compartments for each reservation the night before (or give the kiosk a small pool of boxes it may assign itself), so drop-offs work offline too. Reconcile when back online.
  • Degraded mode. If a kiosk is offline longer than a threshold, the capacity service stops selling new reservations there; checkout simply stops showing it.
  • MQTT is the usual protocol: a small publish/subscribe protocol for constrained devices, with keep-alive and persistent sessions so queued messages are delivered after reconnect.

4. The pickup code: how safe is six digits?

From the estimation: with 40 active codes at a kiosk, one random guess opens some box with probability 1 in 25,000. That sounds safe, but an attacker can keep trying. Defences, in layers:

  1. Lockout After about 5 wrong codes, lock the keypad for a growing period (Educative mentions lockout after about 5 failed attempts). 5 tries per lockout window gives 5 / 25,000 = 1 in 5,000 per window. With a 15-minute lockout that is still about 480 tries a day, roughly a 2% daily chance of opening some box, so lockouts must grow (15 min, 1 h, 1 day) and trigger an alert.
  2. Unguessable and single-use Generate codes from a cryptographically secure random generator (Hello Interview stresses this), never sequential or derived from the order id. Mark used on first open.
  3. Bound and short-lived A code works only at one kiosk, for one compartment, until its deadline.
  4. Stored as a keyed hash (HMAC), with the key kept elsewhere A plain or salted hash does not protect a 6-digit code: there are only 106 possible codes, so anyone holding the hash and its salt can try all of them offline in seconds to minutes, even with a slow hash such as Argon2. What protects the code is a secret key. Store HMAC(key, code) (a keyed hash: without the key you cannot compute it), where the key lives in the kiosk's secure element or TPM and in a cloud KMS, never next to the data. A stolen disk or a database dump then holds values nobody can check guesses against. The real hardening on top is longer codes, or app/barcode unlock for valuable parcels.
  5. Stronger factors when needed Barcode or app unlock (the phone proves the account), and camera monitoring. Amazon's own guidance says some lockers need a barcode scan or the app, not just the six-digit code.

Do the 1-in-25,000 arithmetic out loud. It turns "I would add a lockout" into an engineering argument, and shows why lockout alone is not enough.

5. The state machine, expiry and returns

Write the compartment state machine on the board. Every transition is one conditional update, and every transition is driven by a real event (a sensor reading or a command), not by a timer alone.

  • Expiry: a scheduler (a delayed queue or a time-indexed scan) finds assignments past code_expires_at, revokes the code (desired state to the kiosk), moves the box to EXPIRED, creates a retrieval task for the next driver visit, and emits ParcelExpired so the order service refunds or returns the item. Use the server's clock for the deadline, not the kiosk's. Patterns for timers are in Distributed Job Scheduler and Long-running Tasks.
  • Reminders: one notification about 24 hours before the deadline cuts expiries.
  • Returns run the same machine in reverse: the customer reserves a box for a return, gets a drop code, the door closes on the return parcel, and a carrier's pickup frees it.
  • Faults: a jammed door or a sensor that disagrees with software goes to OUT_OF_SERVICE, the capacity counter for future days drops by one, and any parcel inside is re-routed by operations. A nightly reconciliation compares sensor state with database state.

6. Store pickup (the Walmart variant)

"Buy online, pick up in store" swaps boxes for items on shelves and pickup time slots.

  • Inventory reservation: when the order is placed, decrement the store's available-to-promise count for each item with the same conditional-update trick, and hold it with a time limit until it is picked. See Inventory Management.
  • Slot capacity: a slot is limited by people, not boxes. Walmart describes a capacity and slot management system that decides which slots are open from the size of orders and the labour available (orders and associates per store, day and time). Model it as a counter per (store, slot) in "picking minutes", not "orders".
  • Check-in and dispense: the customer taps "I am here", staff bring the order out or a pickup tower dispenses it. Walmart's Store Assist product has separate picking and check-in-and-dispense components, which is a good boundary for services.
