Data model

Relational, strongly consistent, and small. The heart of the design is that allocation must be atomic, which SQL transactions or DynamoDB conditional writes give you. Storage choices in Choosing Storage.

-- Reserve capacity atomically: succeeds only if space remains for that locker, size and day.
UPDATE capacity_day
   SET held = held + 1
 WHERE locker_id = 'L_BLR_0412' AND size = 'M' AND date = DATE '2026-11-25'
   AND held < total;                        -- 0 rows updated means NO_CAPACITY

-- Assign a compartment at drop-off: compare-and-set on state + version.
UPDATE compartment
   SET state = 'ASSIGNED', current_assignment_id = 'A_313', version = version + 1
 WHERE locker_id = 'L_BLR_0412' AND compartment_id = 'C_17'
   AND state = 'AVAILABLE' AND version = 41;  -- 0 rows means someone else won; pick another

The same thing in DynamoDB is a conditional write: UpdateItem with a ConditionExpression such as held < total. If the condition fails, DynamoDB returns ConditionalCheckFailedException. AWS notes that a conditional write that checks the attribute it updates is safe to retry, while a plain atomic counter is not idempotent. That is why the reservation table also has a unique order_id: a retry of the same order cannot hold two slots.
