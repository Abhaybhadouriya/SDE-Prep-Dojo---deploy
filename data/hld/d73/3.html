Key APIs

# customer side
POST /v1/contacts                     {channel: "chat", order_id?: "o-881", locale}
     Idempotency-Key: <uuid>          -> 201 {contact_id, predicted_intent: "LATE_DELIVERY",
                                               queue: "delivery", position: 14, eta_sec: 180,
                                               ws_url, ws_token}
GET  /v1/contacts/{id}                -> {state, position, eta_sec, agent?}
GET  /v1/contacts/{id}/messages?after_seq=120&limit=50   (history, resume)

# agent side
PUT  /v1/agents/me/status             {status: "AVAILABLE" | "AWAY" | "OFFLINE"}
POST /v1/offers/{offer_id}/accept     -> 200 {contact_id, context: {orders, past_contacts}}
POST /v1/offers/{offer_id}/reject
POST /v1/contacts/{id}/transfer       {to_queue | to_agent, note}
POST /v1/contacts/{id}/escalate       {reason}
POST /v1/contacts/{id}/close          {disposition: "REFUND_ISSUED", summary}

# WebSocket frames (both sides)
-> {type: "msg",  contact_id, client_msg_id, text}
<- {type: "msg",  contact_id, seq: 121, sender: "agent", text, ts}
<- {type: "ack",  client_msg_id, seq: 121}
-> {type: "typing" | "read", contact_id, up_to_seq}
<- {type: "offer", offer_id, contact_id, intent, expires_in: 15}     (agent only)
<- {type: "queue", position: 9, eta_sec: 120}                        (customer only)
  • Idempotent contact creation. A double tap on "Chat with us" or a mobile retry must not open two contacts. The idempotency key plus "one open contact per customer per topic" rule handles it.
  • Offer / accept is a two-step handshake. The router reserves an agent slot and sends an offer that expires (15 s here). Accept confirms; reject or timeout puts the contact back at the front of its queue.
  • Per-contact sequence numbers (seq) give ordering and let a reconnecting client ask "everything after 120".
  • client_msg_id lets the server dedupe a resent message after a flaky network.
