Back-of-envelope estimation

These are our own round-number assumptions for a large e-commerce marketplace. Say them out loud. We round a day to 100,000 seconds, as in Estimation.

  1. Contacts per day. Assume 5M support contacts/day, 70% chat = 3.5M chats/day, 1.5M calls.
  2. Arrival rate. 3.5M / 100K s = 35 new chats/s average. A delivery-delay incident or sale day: assume 5x = 175/s for an hour.
  3. Concurrent chats (Little's law). L = arrival rate x time in system. Assume an average chat lasts 12 min = 720 s (wait + talk). 35 x 720 = ~25K concurrent chats; at spike 175 x 720 = ~126K.
  4. Agents needed. Assume each agent handles 3 chats at once (Amazon Connect caps active chats per agent at 10). Average: 25K / 3 = ~8.4K agents online. At spike you will not have 42K agents - so the queue grows, and you must absorb the wait rather than drop it. This is the key insight.
  5. Messages. 20 messages per chat x 3.5M = 70M messages/day = ~700 msg/s average, ~3.5K/s at spike. Tiny for a messaging system.
  6. Storage. ~500 bytes per message with metadata: 70M x 500 B = 35 GB/day, ~13 TB/year. Attachments go to object storage, assume 10% of chats x 1 MB = 350 GB/day.
  7. Connections. 126K customers + ~10K agents = ~136K WebSockets at peak. LinkedIn described holding hundreds of thousands of persistent connections on one machine, so a handful of gateway hosts suffice; run 6-10 for redundancy and deploys.
  8. Prediction calls. One per new contact: 175/s peak, each reading the last ~10 orders. A cache plus the order service handles this easily.

Punchline: the traffic is small. The hard parts are correctness (never lose or double-assign a contact) and the human bottleneck (agents cannot autoscale). That is why "scale for spikes" is really about queueing, deflection and fairness, not just adding EC2 instances.
