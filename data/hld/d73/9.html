  2. 5-10 min: numbers - Little's law for concurrent chats; agents are the bottleneck, not servers.
  3. 10-15 min: APIs incl. offer/accept and seq-numbered messages; contact state machine.
  4. 15-25 min: diagram: gateway, contact service, predictor, skill queues, router, presence, chat service, stores.
  5. 25-40 min: deep dives - atomic assignment (SQL/ACID), no-drop guarantees, prediction with fallback, spike handling.

LevelWhat the answer looks like
SDE-1 answer looks like..."A contact row in SQL with a state, a queue per skill, a router that gives the oldest contact to a free agent with that skill, and WebSockets for messages stored by contact id."
SDE-2 adds..."Assignment is one ACID transaction with a conditional update on agent capacity, offers expire and re-queue at the front, Redis is only an index rebuilt from SQL, prediction has a timeout and fallback, and spikes are absorbed by durable queues plus deflection because agents cannot autoscale."
How would you scale the chat service for a sudden spike in contacts?

Split the problem. Servers: stateless services autoscale on RPS; gateways scale on open connections and drain gracefully; the message store is partitioned by contact_id so it scales out. Humans: agents are fixed in the short term, so the queue grows. Make the queue durable, show honest wait times, offer callbacks, and cut demand by deflection (live tracking for "where is my order", proactive "your order is delayed" notifications, bots for top intents). Shed optional features (typing, read receipts) before anything else.

How to answer

Say the sentence "servers can autoscale, agents cannot" early. Then show you handle both halves. Use Little's law to show how concurrent chats jump from 25K to 126K.

Likely follow-ups
  • What metric triggers gateway scaling? (open connections per pod, not CPU)
  • How do you avoid a reconnect storm on scale-in? (drain, jittered backoff)
Why SQL over NoSQL here?

For contacts and agent capacity, because assignment must be atomic across two records: check the agent has a free slot, take it, and move the contact to OFFERED - all or nothing. A relational DB gives transactions, row-level locks and conditional updates, and the write rate (tens per second per queue) is well within one primary. For messages I would use NoSQL partitioned by contact_id because they are append-only, high-volume and read in order by one key.

How to answer

Never answer "SQL is better". Map each data type to its access pattern and consistency need, then pick per data type. That is what the interviewer is probing.

Likely follow-ups
  • Could DynamoDB do the assignment? (yes - TransactWriteItems with condition expressions; say the trade-off)
  • How do you shard contacts if one primary is not enough? (by contact_id; agents by agent_id; route assignment within a region)
How do you guarantee DB consistency and ACID when two routers try to assign the same agent?

Each assignment is one transaction: UPDATE agent SET used = used + 1 WHERE id = ? AND used < max AND status = 'AVAILABLE' and UPDATE contact SET state = 'OFFERED', agent_id = ? WHERE id = ? AND state = 'QUEUED'. If either touches zero rows, roll back and retry with the next candidate. Atomicity means no half-assignment; isolation plus the WHERE guards means two routers cannot both take the last slot; durability means a crash after commit keeps the assignment, and a reaper handles expired offers. Additionally, one router owns each queue via a lease, so conflicts are rare - but correctness never depends on the lease.

How to answer

Name each ACID letter with what it protects in this system. Show the actual guarded UPDATE.

Likely follow-ups
  • Which isolation level? (read committed is enough with guarded updates; explain why)
  • What if the offer message is lost after commit? (offer expiry + reaper)
Why EC2 for the chat service? Why not Lambda?

Gateways hold long-lived WebSocket connections and per-connection memory, and need controlled draining during deploys - long-running hosts (EC2 or containers on EC2) fit that. Lambda's 15-minute maximum and per-invocation model suit short stateless work; API Gateway WebSocket APIs can hold the socket and invoke Lambda per message, which is a valid managed alternative at moderate scale with less ops, at higher per-message cost and less control. I would use containers on EC2 (EKS/ECS) for gateways and chat service, and serverless for the predictor or survey sender.

How to answer

It is a trade-off question, not a trivia question. Give one reason for, one alternative, and when you would switch.

Likely follow-ups
  • How do you autoscale EC2 for this? (ASG / HPA + cluster autoscaler on connections, warm pool before known events)
What does auto-scaling look like, and what can it NOT fix?

Services: HPA on RPS/CPU; gateways: HPA on open connections with a max per pod; nodes: cluster autoscaler or Karpenter; scheduled pre-scaling before known events (sale day). Autoscaling takes minutes, so keep headroom (for example 30%). It cannot add trained agents, and it cannot fix a hot single-leader component (one router per queue) - for that, split the queue or shard routers by queue.

How to answer

State the trigger metric for each tier and the warm-up delay. Mention scheduled scaling for predictable peaks.

Likely follow-ups
  • Scale-in safety for WebSockets? (preStop drain, PDB)
How do you make sure no call (contact) is ever dropped?

Make the contact a durable SQL row with a state machine whose only exits are explicit (closed, abandoned by customer, converted to callback). Then cover every gap: idempotent creation; Redis queue as a rebuildable index; offers that expire and are reaped back to the front of the queue; agent heartbeats that re-queue ACTIVE contacts if the agent disappears; admission control and callbacks instead of rejection when the queue is too long. Monitor "contacts in OFFERED past expiry" and "QUEUED older than max wait" - both should be near zero.

How to answer

List the failure points one by one (client, queue node, router, agent, overload) and give a fix for each. The Flipkart discussion refined the design step by step, so expect "what if X dies?" after each answer.

Likely follow-ups
  • The media server for a voice call crashes - what now? (contact row survives; offer callback; telephony has its own redundancy)
  • How do you show the customer their queue position?
How do you predict the customer's issue from their past orders?

Layered: use the order page context if present; else rules over recent order states (late, returned without refund, delivered recently with damage photo, payment failed); then a classifier trained on past contacts with disposition codes as labels. Return intent + confidence. Above a threshold route straight to the skill queue and pre-load the order for the agent; below it, ask the customer to pick from the top guesses. Strict timeout and fallback to a general queue.

How to answer

Start with rules - they explain most cases and are debuggable - then add ML, and talk about where labels come from. Interviewers like the feedback loop.

Likely follow-ups
  • How do you measure the predictor? (transfer rate after first agent, first-contact resolution)
  • Privacy of order data on agent screens?
You said "Uber-style matching". How exactly is the agent chosen?

Event-driven router per queue. On "contact enqueued" or "agent slot freed", take the oldest or highest-priority contact, filter agents with the skill, AVAILABLE status and a free slot, and pick by proficiency band then longest idle, with an occupancy cap so the best agents are not overloaded. Reserve atomically, offer with a 15 s expiry. After the contact waits past T seconds, widen eligibility to lower proficiency or an overflow queue.

How to answer

Contrast with Uber: no geography, scoring is skill and idle time, supply is capacity slots. Then show the reservation transaction.

Likely follow-ups
  • How do you prevent starvation of low-priority contacts? (age-weighted priority)
How do messages stay ordered and not get lost if the customer's network flickers?

Per-contact sequence numbers assigned by the chat service when it persists the message. The client resends with the same client_msg_id until it gets an ack with the seq; the server dedupes on client_msg_id. On reconnect, the client asks for history after its last seq. Ordering is only needed within one contact, so a single owner per contact (or a per-partition counter) is enough.

How to answer

Say "at-least-once delivery plus idempotent receive = effectively once". Mention it is two-party, so no group fan-out problem.

Likely follow-ups
  • Read receipts and typing indicators - persisted? (read receipts yes as up_to_seq; typing no, ephemeral)
How do transfer and escalation work without losing context?

Transfer is a state change on the same contact: ACTIVE -> QUEUED (target queue or named agent), keeping contact_id and the transcript. The current agent's slot frees only once the new agent accepts (warm transfer) or immediately (cold transfer) - pick per business rule. Escalation adds a supervisor as a participant or transfers to a supervisor queue with higher priority. The new agent's screen shows the transcript and a handover note.

How to answer

Show transfer as an arrow in your state machine back to QUEUED. That proves the design generalises.

Likely follow-ups
  • Limit on transfers? (yes, to stop ping-pong; Amazon Connect caps a task at 11 transfers)
LP: "Tell me about a time you disagreed with a design decision but committed" - how does it tie in?

Amazon paired this HLD with Earn Trust and Disagree-and-Commit. A natural story from this design space: you argued for a durable SQL-backed queue while a teammate wanted Redis-only for speed; you showed the failure case with data (a measured Redis failover losing in-flight entries in a test), the team chose a compromise or the other option, and you committed fully and helped make it work, then measured the result. For Earn Trust: you told the customer-facing team honestly about wait times during an incident instead of hiding queue depth.

How to answer

STAR format, real numbers, and show you committed after the decision - no sulking. Prepare one story per LP from your own work.

Likely follow-ups
  • What would you do differently? What did the data show afterwards?

Scenario: delivery outage, chats triple in 10 minutes

A carrier outage delays 2M orders. Chat arrivals jump from 35/s to 120/s. Queue LATE_DELIVERY has a 40-minute wait. Agents are fixed.

Weak answer: "Autoscale the chat servers."

Strong answer: Servers will autoscale, but the real limit is agents. First, deflect: push a proactive notification to affected customers with the new date; when a customer opens chat about an affected order, the predictor recognises it and shows the new date and tracking before queuing. Second, offer callbacks and keep queue position so nobody is dropped. Third, enable overflow so agents with a secondary delivery skill take LATE_DELIVERY after 5 minutes. Fourth, temporarily shed typing indicators and lower history page size. Watch queue depth, abandonment and offer timeouts.

Likely follow-ups
  • How does the predictor know about the outage? (a feature flag / incident tag on affected orders)

Scenario: two agents got the same chat

Support leads report that sometimes two agents both reply to the same customer.

Weak answer: "Add a distributed lock around the router."

Strong answer: Root cause is likely an unguarded assignment: two router instances (overlapping leases after a deploy) each read the contact as QUEUED and wrote OFFERED. Fix in the database: UPDATE contact SET state='OFFERED', agent_id=? WHERE id=? AND state='QUEUED' in the same transaction as the agent slot update, and abort if 0 rows. Keep the lease for efficiency, but correctness comes from the guarded update. Add an alert on "contact with two accept events".

Common mistakes: making Redis the only copy of the queue; assigning without a capacity check in the same transaction; no offer timeout (contacts stuck forever on a ghost agent); routing the live chat through Kafka; blocking contact creation on the ML model; claiming autoscaling fixes a human bottleneck; forgetting transfer and history; one giant global router.
