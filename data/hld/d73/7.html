Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key contact_id keeps one conversation's events (queued, offered, accepted, closed) in order; the live chat messages themselves do not go through Kafka. Consumer-group sizing: 24 partitions cap each analytics group at 24 pods. Gateways scale on a custom "open connections" metric with a long termination grace period; routers stay small and elect one leader per queue.

"Why EC2?" (an Amazon follow-up). Long-lived WebSocket connections and in-memory connection state suit long-running hosts (EC2, or containers on ECS/EKS running on EC2) better than short-lived functions. AWS Lambda functions have a maximum run time of 15 minutes and do not hold sockets themselves; API Gateway WebSocket APIs can hold the socket for you, which is a valid alternative for small teams. Say: "EC2/containers for the gateways because connections live for many minutes and I want control over draining and memory per connection; Lambda or Fargate is fine for bursty stateless pieces like the predictor."
