Trade-offs: which queue or engine?

OptionStrengthsWeaknessesPick it when
DB table + SKIP LOCKEDNo new system; enqueue in the same transaction as your dataPolling load on the primary; limited throughputSmall/medium scale, strong need for transactional enqueue
Redis list / streamVery fast, simple (Celery, Sidekiq, RQ)Memory-bound; durability depends on config. The primer warns messages can be lostShort jobs, losses tolerable, or Redis fronted by something durable
SQS / RabbitMQPer-message ack, visibility timeout / redelivery, DLQ built in; SQS is fully managedAt-least-once; standard SQS is not ordered; SQS visibility capped at 12 hThe default for job queues: independent tasks, per-task retries
KafkaHuge throughput, durable, replayable, many consumer groupsOffset per partition, not per message: one slow job blocks its partition; retries need retry topics; parallelism capped by partition countVery high volume of short jobs, or as a durable buffer in front of a work queue
Temporal / Step FunctionsDurable multi-step state, timers, retries, replay; resume after crashAnother system to run or pay for; deterministic-code rulesMulti-step, hours/days long, human-in-the-loop, compensation
Kubernetes JobEach task gets its own pod, image and resource limits; built-in retriesPod start cost (seconds); not for thousands of tiny tasks a secondBig batch jobs: builds, ML training, data backfills
What the pattern gives you
  • Fast, predictable API latency
  • Workers scale and fail independently of the web tier
  • Bursts absorbed by the queue
  • Retries and crash recovery instead of lost work
  • Right hardware per job type (GPU, big RAM)
What it costs
  • Eventual completion: the user waits for a notification
  • Duplicates: handlers must be idempotent
  • More moving parts: queue, DLQ, job table, monitoring
  • Backlogs can hide outages until they are huge
  • Harder debugging across async hops (trace IDs needed)
