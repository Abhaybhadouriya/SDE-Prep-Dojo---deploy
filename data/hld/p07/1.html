When you hit it: the signals

A normal web request (load a profile, add to cart) takes well under 100 ms. Hello Interview's write-up of this pattern contrasts that with a PDF annual report that needs at least 45 seconds, and notes that web servers and load balancers commonly time out after about 30-60 seconds. When the work is longer than the timeout, the request can never finish, no matter how fast your code is.

Listen for these words in an interview question. Each one is a hint that you need this pattern:

  • "Upload a video and we make it playable in 4 resolutions" - transcoding takes minutes (YouTube upload).
  • "Generate a report / export my data / import this CSV" - scans millions of rows.
  • "Send this campaign to 10 million users" - one click, millions of sends (Notification system).
  • "Run the user's code against 100 test cases" - CPU-heavy, untrusted (Online judge).
  • "Crawl", "index", "train", "build", "deploy" - batch work with many steps (Web crawler, CI/CD).
  • "Run this at 9 AM every day" - scheduled work (Job scheduler).
  • Any time the non-functional requirements say "the user should not wait" or "must not lose a job if a server dies".

Say it early: "This operation is slow and can fail, so I will make it asynchronous: the API accepts the request, stores a job, puts it on a queue and returns a job ID. Workers process it and update the job status. The client polls or gets notified." Then spend your time on failure handling, which is where the points are.

From your world

You already know this pattern from the Linux kernel. An interrupt handler (the top half) must be tiny: it acknowledges the device and returns. The slow part is deferred to a bottom half - a softirq, tasklet or a workqueue run by kworker threads. The API server is the top half, the job queue is the workqueue, and the workers are the kworkers. Same reason too: never hold the "interrupt" (the HTTP connection) while doing slow work.
