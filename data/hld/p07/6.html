How Kafka, Kubernetes and Docker help

Kafka: a durable buffer in front of the work

Kafka is a log, not a classic work queue: a consumer commits an offset per partition, not an ack per message. So a single 10-minute job blocks everything behind it in that partition, and parallelism is capped by the number of partitions. That is why many teams put Kafka in front of a work queue rather than using it as one.

Slack's engineering blog tells exactly this story. Their job queue was Redis. When a database problem slowed job execution, Redis filled its memory, and because dequeuing also needed free memory, the queue locked up even after the database recovered. The fix was not a rewrite: they put Kafka in front of Redis. A small Go service (Kafkagate) accepts jobs over HTTP and writes them to Kafka; another (JQRelay) moves jobs from Kafka into Redis at a controlled rate and only advances the offset after the Redis write succeeds. They report over 1.4 billion jobs on busy days and peaks of 33,000 jobs a second, on 16 brokers with 32 partitions per topic, replication factor 3 and 2-day retention.

If you do process jobs straight from Kafka, use retry topics (jobs.retry.1m, jobs.retry.10m) and a DLQ topic, so a failing message is moved aside and the partition keeps flowing. Details on Stream Processing, Retries & DLQ and Consumers & Consumer Groups.

Kubernetes: workers that scale with the queue

  • Workers as a Deployment pulling from the queue, autoscaled by KEDA (it has scalers for SQS, Kafka lag, RabbitMQ, Redis and more) instead of CPU. Set terminationGracePeriodSeconds longer than a typical job, and on SIGTERM stop taking new jobs and finish (or release) the current one.
  • One pod per task with a Job for big batch work. backoffLimit (default 6) caps retries, the retry delay starts at 10 s and doubles up to 6 minutes, activeDeadlineSeconds kills a job that runs too long, ttlSecondsAfterFinished cleans up, and completionMode: Indexed hands each pod a shard number. CronJob adds a schedule with concurrencyPolicy: Forbid to avoid overlap. See Scheduling & Autoscaling.
apiVersion: batch/v1
kind: Job
metadata:
  name: monthly-report-backfill
spec:
  completions: 20            # 20 shards of the work
  parallelism: 5             # at most 5 pods at once
  completionMode: Indexed    # pod gets JOB_COMPLETION_INDEX 0..19
  backoffLimit: 6
  activeDeadlineSeconds: 7200
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: registry.example.com/report-worker:1.4.2
        args: ["--shard=$(JOB_COMPLETION_INDEX)", "--of=20"]
        resources:
          requests: { cpu: "1", memory: 2Gi }
          limits:   { memory: 2Gi }

Docker: one image per worker type

Package each worker type as its own image (the transcoder needs ffmpeg, the report worker needs a PDF library), so you can deploy, scale and roll back them separately from the API. For untrusted code (online judge, CI), the container is also the sandbox boundary: no network, read-only root filesystem, CPU and memory limits, a hard wall-clock timeout. See Docker production & security.
