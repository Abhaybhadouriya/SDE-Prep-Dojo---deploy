The solution ladder: naive to best

We climb five rungs. Each rung fixes the thing that broke on the rung below.

Rung 1: do it inside the request (synchronous)

The API server receives "make my report", does all the work, and replies with the file. Simple, and fine for work under about a second.

When it breaks: (1) the load balancer or the browser times out first; (2) each waiting request pins a thread and a connection, so 200 people exporting reports can starve the server that also serves logins; (3) the user hits refresh, which starts the job again; (4) if the server restarts mid-job, the work is gone and nobody knows.

Rung 2: fire a background thread on the same server

Reply "202 Accepted" right away and start a thread in the same process to do the work. The user is no longer blocked.

When it breaks: the job lives only in that server's memory. A deploy, a crash or an autoscaler scale-in kills it silently. There is no shared place to ask "what is the status of job 42?", because another API server cannot see the thread. Slow jobs and fast requests still fight for the same CPU and memory, so a burst of exports slows checkout. You cannot scale "report capacity" without scaling the whole web tier.

Rung 3: job table + queue + worker pool (the core pattern)

Split the system in two. The API tier only validates, records and enqueues. A separate worker tier does the slow work. They talk through two things: a durable queue (who should work on what next) and a job table (the truth about each job: status, progress, result location). Click through the flow.

  1. Request. The client asks for the slow thing, ideally with an idempotency key so a double-click does not create two jobs.
  2. Record, then enqueue. The API writes a job row (QUEUED) and puts the job ID on a durable queue. Store the job first so it can never be "on the queue but unknown".
  3. Answer fast. The API returns 202 Accepted with the job ID and a status URL, in milliseconds. The connection is free.
  4. Work. A free worker pulls the job, marks it RUNNING, and updates progress as it goes.
  5. Finish. Big outputs go to a blob store; the job row gets DONE and a pointer (URL) to the result, never the bytes themselves.
  6. Tell the user. The client polls GET /jobs/42, or the system pushes: SSE/WebSocket, a mobile push, an email, or a webhook to a partner server.

Now each tier scales on its own. Web servers scale with request rate. Workers scale with queue depth or age of the oldest message. Heavy work can run on different hardware (GPUs for transcoding, big-memory boxes for reports) without touching the web tier. And the queue absorbs bursts: 10,000 jobs can arrive in a minute while 50 workers chew through them.

// POST /v1/reports   Idempotency-Key: 7f1c...   ->  202 Accepted
{ "job_id": "job_42", "status": "QUEUED", "status_url": "/v1/jobs/job_42" }

// GET /v1/jobs/job_42   (poll every 2-5 s, or long-poll)
{ "job_id": "job_42", "status": "RUNNING", "progress": 0.4, "attempt": 1 }

// later
{ "job_id": "job_42", "status": "SUCCEEDED",
  "result_url": "https://files.example.com/r/job_42.pdf?sig=...", "expires_in": 3600 }
CREATE TABLE jobs (
  job_id          TEXT PRIMARY KEY,
  owner_id        TEXT NOT NULL,
  type            TEXT NOT NULL,          -- 'report', 'transcode', ...
  idempotency_key TEXT UNIQUE,            -- dedupe client retries
  status          TEXT NOT NULL,          -- QUEUED | RUNNING | SUCCEEDED | FAILED | CANCELLED
  attempt         INT  NOT NULL DEFAULT 0,
  progress        REAL,
  lease_owner     TEXT,                   -- which worker holds it
  lease_until     TIMESTAMPTZ,            -- heartbeat pushes this forward
  result_url      TEXT,
  error           TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

Rung 4: make it survive crashes - leases, heartbeats, retries, DLQ

Rung 3 still has a hole. A worker pulls job 42 and then the machine loses power. Who notices? The answer is a lease: when a worker takes a job, the job becomes invisible to everyone else for a limited time only. If the worker finishes, it deletes (acks) the job. If it dies, the lease runs out and the job reappears for another worker.

Amazon SQS calls this the visibility timeout. Its documentation gives the numbers: the default is 30 seconds, you can extend it per message with ChangeMessageVisibility, and the total cannot go past 12 hours from the first receive. For long or unpredictable work AWS recommends a heartbeat: while the job is still running, the worker keeps extending the timeout a little at a time, instead of setting one huge timeout up front. A huge timeout means a dead worker's job sits invisible for hours.

Leases bring the next problem: the same job can run twice. Worker A may only be slow (a long GC pause, a network blip), not dead. Its lease expires, Worker B starts, then A wakes up and also finishes. SQS says it plainly: delivery is at-least-once, and even the visibility timeout does not guarantee a message is never delivered twice. So the rule is: every job handler must be idempotent (safe to run twice). Dropbox's task framework (ATF) says the same about its task functions. Three ways to get there:

  1. Deterministic output names. Write the result to s3://reports/job_42.pdf, not a random name. A second run just overwrites the same object.
  2. Conditional state changes. UPDATE jobs SET status='SUCCEEDED' WHERE job_id=? AND status='RUNNING' AND lease_owner=?. Only the worker that still owns the lease can finish the job. This is a fencing check.
  3. Dedupe side effects. For "send email" or "charge card", record the job ID (or an idempotency key) with the side effect, and skip it if it is already there.

Dropbox adds a nice trick for the "slow, not dead" case: an ATF executor sends heartbeats while running, and if three heartbeats in a row fail it kills itself. The heartbeat timeout on the server side is set longer than that window, so the task is only handed to a new executor after the old one has surely stopped.

Retries with backoff. Most failures are temporary (a dependency is down for 20 seconds). Retry, but wait longer each time and add random jitter so a thousand failed jobs do not all retry in the same second. Temporal's default activity retry policy is a good reference: first retry after 1 s, multiply by 2.0 each time, cap the wait at 100 s, and no attempt limit by default.

Dead-letter queue. Some jobs will never succeed - a corrupt file, a bug for one input. These are poison messages. Without a limit they loop forever and burn worker time. SQS uses a redrive policy with maxReceiveCount: after a message has been received that many times without being deleted, it moves to the DLQ. The AWS Builders' Library advice is to alarm on any message in a DLQ, because it means a bug, and to redrive the messages back after the fix. One gotcha from the SQS docs: for standard queues the expiry clock keeps the original enqueue time, so set the DLQ retention longer than the source queue's, or messages vanish before you look.

From your world

A visibility timeout is a retransmission timer. TCP does not know if a segment was lost or just slow, so when the timer fires it resends, and the receiver must cope with duplicates using sequence numbers. Here, the queue does not know if the worker died or is just slow, so it redelivers, and your handler copes with duplicates using the job ID. The worker heartbeat is a watchdog on an HA control card: miss three kicks and you are considered dead, and the standby takes over. The "kill yourself after three missed heartbeats" rule is exactly STONITH from clustering: make sure the old owner is really gone before the new one acts.

Rung 5: many steps, hours long - use a workflow engine

Some "jobs" are really a chain: upload, then scan for viruses, then transcode into 4 resolutions in parallel, then make thumbnails, then publish, then notify followers. If step 4 fails after 30 minutes, you do not want to redo steps 1-3. You could build this from queues, a state column per step and lots of glue code. Or you use a durable execution engine like Temporal or AWS Step Functions.

Temporal's docs describe the idea: the workflow is ordinary code, and every completed step (an activity) is recorded in an event history. If the worker running the workflow crashes, a new worker re-runs the code from the start and replays the history: finished activities return their recorded results instead of running again, so the workflow continues exactly where it stopped. Executions can run for days or years. The price: workflow code must be deterministic (no reading the clock or random numbers directly), and you run or rent another piece of infrastructure. SQS also hints at this rung: if a task needs more than the 12-hour visibility limit, AWS suggests Step Functions or splitting the task into smaller steps. The full story of sagas and compensation is on Multi-step Processes.

Rule of thumb: one step, minutes long, retry-safe: queue + workers (rung 4). Several dependent steps, hours long, needs "resume where it stopped" or human approval in the middle: workflow engine (rung 5). Say both, and pick based on the question.
