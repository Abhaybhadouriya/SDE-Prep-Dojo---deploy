Rate limiting, load shedding and backpressure

These three are often mixed up. They answer different questions.

ToolQuestion it answersWho decidesTypical response
Rate limitingIs this client over its quota?Per key (user, API key, IP), fixed policy429 Too Many Requests + Retry-After
Load sheddingAm I (the server) over capacity right now?The server, from its own health (queue time, in-flight, CPU)503, dropped early and cheaply, lowest priority first
BackpressureCan the consumer keep up?The consumer signals the producer to slow downBounded queue blocks, credits, pull-based consumption (Kafka)
Graceful degradationWhat cheaper answer can I still give?Product + engineering, decided in advanceCached, partial or simpler result

Rate-limit algorithms (token bucket, leaky bucket, fixed window, sliding log, sliding window counter) and how to run them across many nodes with Redis are covered in depth in Design a Distributed Rate Limiter (d02). In short: a token bucket allows bursts up to the bucket size and a steady refill rate; a sliding window counter is the usual memory-cheap choice for "N per minute".

Why load shedding: goodput

The AWS Builders' Library separates throughput (requests per second you receive) from goodput (requests answered correctly and in time to be useful). Past capacity, an unprotected server keeps accepting work. It spends its time context-switching and on garbage collection, latency climbs to the client timeout, and goodput falls off a cliff. Once median latency reaches the client timeout, about half of all requests fail. Shedding early keeps goodput flat at capacity.

How real shedders decide. Uber's Go library Cinnamon tags each request with a priority tier (0-5, set at the edge and passed down the call chain) and a user cohort, so shedding "5% of tier 5" drops the same users in every service. A service counts as overloaded when its request queue has not emptied for about 10 s; a PID controller then sets how much to reject, and a TCP-Vegas-style tuner adjusts the in-flight limit from latency. In Uber's test (about 1,300 rps of capacity, 2,000 rps offered) goodput stayed about 1,300, while the older CoDel-based shedder fell to 552 rps at 3,000 rps offered. Netflix likewise moved from fixed Hystrix limits to adaptive concurrency limits learned from latency.

  • Shed at the front: rejecting before parsing, auth and DB work is cheapest.
  • Bounded queues: Google SRE suggests queues of about 50% or less of the thread pool size for steady traffic. A queue 10x the thread count, with 100 ms of work each, adds about 1 s of waiting.
  • Drop dead requests: if a request's deadline has passed while it sat in the queue, skip it. LIFO or CoDel queues favour fresh requests.
  • Prioritise: load-balancer health checks first (failing them shrinks the fleet and makes overload worse), paying users over crawlers, "finish checkout" over "browse".
  • Exclude shed requests from latency metrics: a server shedding 60% looks fast if you average in the instant rejections (AWS).

From your world

Load shedding is tail drop vs RED/CoDel in a router queue: drop early and selectively so the queue stays short and latency stays low. Backpressure is TCP flow control (the receive window) or PFC pause frames. Adaptive concurrency limits are literally TCP congestion control (Vegas, AIMD) applied to RPCs.
