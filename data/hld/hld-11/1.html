Monolith vs microservices

A monolith is built and deployed as one unit. All modules (orders, payments, catalog) live in one process and call each other with plain function calls. A microservice owns one business capability (one "bounded context"), has its own code base and its own database, and is deployed on its own. Services talk only through APIs (HTTP/gRPC) or events (Kafka).

QuestionMonolithMicroservices
Call between partsFunction call (nanoseconds, never "lost")Network call (milliseconds, can time out or fail)
TransactionsOne ACID transaction across modulesNo shared transaction; need sagas/outbox (hld-10)
DeployWhole app redeployed for any changeEach team ships its service alone
ScalingScale everything togetherScale only the hot service
Blast radius of a bugOne memory leak can crash all featuresContained to one service, if you add resilience patterns
DebuggingOne stack trace, one logNeeds distributed tracing and correlation IDs
Best forSmall teams, new products, tight latency pathsMany teams that block each other on one code base

There are useful middle points. A modular monolith is one deployable, but the code is split into strict modules with clear interfaces, so you can pull a module out later. N-tier (presentation, logic, data tiers) is about layers, not about business boundaries. Serverless (AWS Lambda and friends) pushes the idea to the extreme: tiny functions that the cloud starts on demand and bills per call.

The distributed monolith trap. If your "microservices" share one database schema, must be deployed together, or call each other in long synchronous chains, you have the costs of both worlds and the benefits of neither. Karan Pratap Singh's free system design book lists exactly these signs: shared resources, tight coupling, services that do not scale on their own.

Real case: Amazon Prime Video. In 2023 the Prime Video team that checks live streams for audio/video defects reported moving one service from a distributed serverless design (AWS Step Functions orchestrating Lambdas, passing video frames through S3) to a single process where the converter and detectors share memory. Two things were expensive at scale: Step Functions bills per state transition (many per second per stream), and every frame went through S3 between steps. Keeping data in memory cut that service's infrastructure cost by over 90%. The lesson for interviews is not "microservices are bad". It is "split along boundaries where data does not need to flow at high volume between the pieces".
