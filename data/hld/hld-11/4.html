Timeouts: the first and most important rule

A remote call can succeed, fail, or hang. A hang is the worst outcome because it holds a thread, a socket and memory while doing nothing. Every remote call needs a connect timeout and a request timeout. That includes calls to a "local" sidecar or another process on the same box.

How to pick the number (AWS Builders' Library method). Choose how many good calls you can afford to cut off by mistake, the false timeout rate, for example 0.1%. Then set the timeout to the dependency's latency at that percentile: p99.9. (A percentile is a point in the latency distribution: p50 is the median, half the calls are faster; p99 is the latency that 99% of requests beat, so 1 in 100 is slower; p99.9 means 1 in 1,000 is slower.) If p99.9 is very close to p50, add padding. For clients on the public internet, add the worst network latency you expect. The article also tells a real story: a 20 ms timeout kept failing right after deploys because the very first call also had to do the TLS handshake. Warming connections at startup fixed it.

Deadline propagation. Google's SRE book recommends sending one absolute deadline down the call tree rather than a fresh timeout at every hop. If the user request had 30 s and 7 s are already spent, the next call gets 23 s. A server that dequeues a request whose deadline has already passed should drop it, since nobody is waiting for the answer. gRPC carries this for you as grpc-timeout.

From your world

Think of TCP's retransmission timer: RTO is derived from measured RTT plus variance, not picked at random, and it doubles on each loss (exponential backoff). Application timeouts should be set the same way, from measured latency percentiles.
