Putting it together: the resilient call

In production these patterns stack in a fixed order around every outbound call. Learn this order; interviewers like to hear it.

  1. Rate limit / shed at the edge so excess never enters (API gateway, hld-05).
  2. Bulkhead: acquire a slot in this dependency's pool, or reject at once.
  3. Circuit breaker: if open, skip to fallback.
  4. Timeout on the call (from the remaining deadline).
  5. Retry with capped, jittered backoff, only for retryable errors, within a retry budget, and only if idempotent.
  6. Fallback: cached or degraded response.
  7. Observe: emit metrics for breaker state, rejections, retries; trace IDs across hops (hld-13).

Where Kubernetes, Kafka and Docker fit:

  • Kubernetes: Services + DNS = discovery; readiness probes take sick pods out of rotation; liveness probes restart hung ones; resource limits and namespaces = bulkheads; HPA adds capacity (but too slowly to replace shedding). See Deployments and Scheduling & Autoscaling.
  • Kafka: turning a synchronous call into an event removes the "hang" problem entirely. The consumer pulls at its own speed (natural backpressure), and failed messages go to retry topics with backoff and then a DLQ. See Delivery Semantics and Retries & DLQ.
  • Docker: one service per image, and memory/CPU limits per container (cgroups) so a leak in one cannot starve its neighbours. See Running & Managing Containers.
# Istio DestinationRule: bulkhead (connection pool) + outlier detection
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: recommendations
spec:
  host: recommendations
  trafficPolicy:
    connectionPool:
      tcp:  { maxConnections: 50 }
      http: { http1MaxPendingRequests: 20, maxRequestsPerConnection: 100 }
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 10
