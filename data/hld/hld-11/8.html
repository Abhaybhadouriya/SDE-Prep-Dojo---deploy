How one slow service takes down everything

Google's SRE book defines a cascading failure as failure that grows by positive feedback, and names overload as the most common cause. Walk through how it happens, and which pattern breaks each link of the chain.

  1. Healthy. Each request holds a thread for ~30 ms. 1,000 rps needs only about 30 busy threads (Little's law: in-flight = rate x latency).
  2. One dependency slows down. The orders DB goes from 50 ms to 5 s. In-flight work jumps: 1,000 rps x 5 s would need 5,000 threads.
  3. Resource exhaustion spreads. All 200 threads are stuck waiting for the DB. Requests for search, which is perfectly healthy, find no free thread and fail too. Users and upstreams retry and add load.
  4. Contained. A short timeout frees threads fast, a bulkhead limits orders calls to 40 threads, and the breaker opens so calls fail instantly with a fallback. Search and the rest of the site stay up.

The SRE book gives a sharp number: if 5% of requests hang until a 100 s deadline on a frontend with 1,000 threads, the frontend ends up serving only about 19.6% of requests. Roughly 80% fail, though 95% of the work was healthy.
