Service discovery: who is at which address?

In a monolith, payments.charge() is a function pointer. In microservices, the payments service is 12 pods whose IP addresses change every deploy, autoscale and crash. Service discovery answers "give me a healthy address for payments right now".

  • Service registry: a highly available database of name to list of instance addresses (Consul, etcd, ZooKeeper, Eureka, or the Kubernetes API server).
  • Registration: either the instance registers itself and sends heartbeats (self-registration), or the platform watches instances and registers them (third-party registration; Kubernetes does this from Pod readiness).
  • Client-side discovery: the caller asks the registry, gets the list, and picks an instance itself (Netflix Eureka + Ribbon style). Fewer hops, but every client language needs the library.
  • Server-side discovery: the caller sends to one stable name or virtual IP, and a load balancer picks the instance (Kubernetes Service, AWS ALB). Clients stay simple; the LB is one more hop.

From your world

A Kubernetes Service is server-side discovery done with kernel tricks you already know: a stable ClusterIP (a virtual IP nobody owns), DNS name payments.default.svc.cluster.local pointing to it, and kube-proxy programming iptables/IPVS DNAT rules so a packet to the VIP is rewritten to one ready pod IP. Readiness probes decide which pods are in the endpoint list, like a routing protocol withdrawing a dead next hop. See Services & Cluster Networking.
