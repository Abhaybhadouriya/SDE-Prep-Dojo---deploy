Retries, exponential backoff and jitter

Many failures are transient: a pod restarting, a dropped packet, a short leader election. Trying again often works. But retries are dangerous. The AWS Builders' Library calls them "selfish": a retry spends more of the server's capacity to raise your chance of success. When the server is failing because it is overloaded, retries add load right when it can least take it.

Retry amplification

Retries multiply across layers. If each of 4 layers makes 1 try plus 2 retries (3 attempts), one user click can become 3 x 3 x 3 x 3 = 81 calls to the bottom database. Google's SRE book shows a small stack where retries add up to 64 attempts on the database; AWS's example of 5 layers each making 3 attempts gives 35 = 243x load on the bottom layer.

Rules for safe retries

  1. Only retry what is safe. Reads are safe. Writes are safe only if they are idempotent (repeating has the same effect as once), usually via an idempotency key. See hld-06.
  2. Only retry retryable errors. Timeouts, 503, 429 (honour Retry-After) and connection resets: yes. 400, 401, 404, validation errors: never.
  3. Retry at one layer. Usually the edge or the layer closest to the failure, not every layer.
  4. Cap attempts (2-3 total is typical) and cap the backoff.
  5. Use a retry budget. Google SRE suggests a per-process budget (their example: 60 retries per minute); also a ratio like "retries may be at most 10% of requests". AWS SDKs since 2016 use a local token bucket: retries spend tokens, and when tokens run out, retries stop.
  6. Back off exponentially and add jitter.

Why jitter matters

Exponential backoff waits base x 2attempt between tries, up to a cap. That spaces out each client's tries, but if 1,000 clients failed at the same instant, they all wait 100 ms, then all retry together, then all wait 200 ms, then all retry together. The load arrives in synchronized spikes. Jitter adds randomness so the spikes smear into a flat rate.

Marc Brooker's AWS Architecture Blog post simulated 100 clients fighting over one row with optimistic concurrency. Plain exponential backoff helped only a little because calls still came in clusters. Adding jitter cut the total number of calls by more than half and finished sooner. Of the variants he compared, "Equal Jitter" was the loser; "Full Jitter" did the least work, and "Decorrelated Jitter" was close and slightly faster. His conclusion: jittered backoff should be a standard approach for remote clients.

import random, time

RETRYABLE = {408, 429, 500, 502, 503, 504}

def call_with_retries(do_call, max_attempts=3, base=0.1, cap=2.0):
    """do_call() returns (status, body). Full-jitter capped exponential backoff."""
    for attempt in range(max_attempts):
        status, body = do_call()
        if status < 400:
            return body
        if status not in RETRYABLE or attempt == max_attempts - 1:
            raise RuntimeError(f"giving up after {attempt + 1} tries: {status}")
        sleep = random.uniform(0, min(cap, base * 2 ** attempt))   # full jitter
        time.sleep(sleep)
