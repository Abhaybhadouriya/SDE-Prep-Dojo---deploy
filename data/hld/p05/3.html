Quick wins
  • Batch inserts and use multi-row writes
  • Hash the key so writes do not pile on the newest range
  • Aggregate counters in memory for a few seconds
  • Put a queue in front of slow sinks
Hidden costs
  • Cross-shard queries become scatter-gather
  • Global uniqueness needs an ID service
  • Resharding is a months-long project
  • Async writes need a status story for users

Estimate before you shard

Example: 1 M active drivers send a location every 4 s = 250K writes/s. At 100 bytes each that is 25 MB/s, about 2 TB per day. If each node takes 10K writes/s comfortably, that is 25 nodes just for raw writes, before replication. But only the latest location matters for matching, so keep it in an in-memory geo index (overwrite in place) and send the stream to Kafka for history: the database write rate collapses. Always ask whether every write must hit durable storage individually. See Estimation and Geo & Proximity.

Say this: "Reads I can copy; writes I have to split or shrink. I'll shard by X because most queries include it, hash it to avoid a hot tail, split known hot keys into N sub-keys, and put Kafka in front so a burst becomes lag instead of an outage."
