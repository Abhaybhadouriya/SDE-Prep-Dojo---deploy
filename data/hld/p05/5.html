Kafka, Kubernetes and Docker

  • Kafka is sharding plus buffering plus batching in one box. A topic's partitions are shards; the producer's partitioner is the shard-key function (hash(key) % partitions), so all events for one key stay in order on one partition. Partitions are append-only logs on disk - the same sequential-write trick as an LSM commit log. A hot key in Kafka is a hot partition: same fixes (salt the key, or aggregate before producing). See Core Concepts, Producers and Consumer groups.
  • Consumer lag is your backlog meter. Alert on it; scale consumers up to the partition count. More consumers than partitions sit idle, which is why you choose the partition count for peak parallelism up front.
  • Kubernetes scales the stateless writers and consumers (KEDA or HPA on consumer lag, see Autoscaling) and runs sharded stateful stores as StatefulSets, one PersistentVolume per shard (StatefulSets & Operators, Storage). Kafka itself runs on K8s with Strimzi (Kafka ops).
  • Docker: run Kafka in KRaft mode and Postgres locally with Compose to feel batching: insert 100K rows one by one, then in batches of 500, and compare (Build it locally).
// Producer tuned for write throughput (Kafka 3.7+/4.x)
Properties p = new Properties();
p.put("bootstrap.servers", "kafka:9092");
p.put("acks", "all");                 // durable: wait for in-sync replicas
p.put("enable.idempotence", "true");  // retries do not duplicate
p.put("linger.ms", "10");             // wait up to 10 ms to fill a batch
p.put("batch.size", "131072");        // 128 KB batches per partition
p.put("compression.type", "lz4");     // fewer bytes on disk and wire
KafkaProducer<String, String> producer = new KafkaProducer<>(p, new StringSerializer(), new StringSerializer());
// key = shard key: all clicks for one ad stay ordered on one partition
producer.send(new ProducerRecord<>("ad-clicks", adId, clickJson));
