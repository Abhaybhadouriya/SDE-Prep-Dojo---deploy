When you hit it

As a rough rule of thumb (an order-of-magnitude planning number from our estimation notes, not a benchmark), a single relational database on good hardware handles a few thousand to low tens of thousands of simple writes per second, depending on row size, indexes and durability settings. Long before that ceiling, other things break. Notion's engineering team sharded Postgres because VACUUM (Postgres's background cleanup that removes dead row versions left behind by updates and deletes) kept stalling, and transaction-ID wraparound became a real risk. Postgres numbers transactions with a 32-bit counter; after about 2 billion transactions old IDs would start to look like future ones, so VACUUM must "freeze" old rows in time, and if it falls too far behind, Postgres stops accepting writes to protect itself. CPU spikes also paged on-call engineers. Figma's databases grew about 100x from 2020, starting from one Postgres on AWS's largest instance; some tables reached several terabytes and billions of rows and approached the RDS IOPS limit.

Signals in the interview question

  • Event ingestion. Clicks, logs, metrics, GPS pings: "1 M drivers send location every 4 seconds" is 250K writes/s. That is Ad Click Aggregator, Metrics, Log Aggregation, Ride Hailing.
  • One thing everyone writes to. The like count on a viral post, the stock of a flash-sale SKU, the balance of a merchant account that receives every payment. That is a hot key.
  • Bursts. A sale opens at 12:00, a match ends, a push notification goes out. Average load is fine; the peak is 50x.
  • Data that grows forever. Chat messages, time series, audit logs. Even at modest write rates, one machine runs out of disk.
  • The interviewer says "now 10x the traffic". Hello Interview notes interviewers probe write bottlenecks exactly this way: to see how you react to fast growth.

From your world

A NIC with Receive Side Scaling hashes each flow's 5-tuple to one of N RX queues, each served by one CPU, so packets of one flow stay in order on one core while different flows run in parallel. That is hash sharding with a shard key. An elephant flow that pins one queue at 100% is a hot partition. Interrupt coalescing and NAPI polling (handle 64 packets per interrupt, not one) are batching. And the page cache absorbing write() calls before writeback flushes them is a write buffer - with the same risk of losing data if the box dies before the flush.
