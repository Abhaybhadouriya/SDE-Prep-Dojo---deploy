The ladder: naive to best

Hello Interview's guide orders the moves like this: stay on one box as long as you can (bigger hardware, the right database), then shard, then handle bursts with queues and load shedding, then batch and aggregate hierarchically. It stresses that scaling writes is not only about adding hardware. We follow the same order.

Rung 0 - Bigger box, cheaper writes

Vertical scaling (more CPU, faster NVMe, more RAM) is boring and often correct for an SDE-2 answer at moderate scale. Then make each write cheaper:

  • Drop indexes you do not need. Every secondary index is another write on every insert.
  • Write-optimised storage. A B-tree database updates pages in place (random I/O). An LSM-tree (log-structured merge tree) database such as Cassandra, RocksDB or ScyllaDB turns every write into a sequential append. ByteByteGo's comparison sums it up: B-trees are usually faster for reads, LSM-trees for writes.
  • Vertical partitioning. Move unrelated tables to their own databases. Figma did this first: files, organisations and so on got their own databases. Its limit is that the smallest unit is one table, so it does nothing for the one giant table.

The LSM write path is worth knowing in detail, because it explains why Cassandra and Bigtable take writes so cheaply. Step through it:

  1. Log first. The write is appended to a commit log (a write-ahead log) - one sequential write. If the server crashes, replaying the log rebuilds memory. Bigtable uses group commit here: many writes share one log flush.
  2. Then memory. The write goes into the memtable, a sorted in-memory structure. The client gets its acknowledgement now. No page was read or rewritten on disk.
  3. Flush. When the memtable reaches a threshold it is frozen and written out as an immutable, sorted file (an SSTable). Bigtable calls this a minor compaction.
  4. Compact. In the background, several SSTables are merged into one, dropping overwritten and deleted values (merging and major compaction). This keeps the number of files a read must check small.
  5. The price. Data gets rewritten several times during compaction, and a read may have to check the memtable plus several SSTables (Bloom filters help skip files). LSM trades read cost and background I/O for very cheap writes.

Breaks when: one machine's disk, CPU or NIC is full, or the data no longer fits. Then you must split ownership.

Rung 1 - Shard by a good key

Horizontal sharding gives each machine a subset of the rows. Every write is routed by its shard key. ByteByteGo lists four ways to map keys to shards:

SchemeHowStrengthWeakness
RangeKey ranges: A-F, G-M; or by dateRange scans stay on one shardHot spots: all of today's writes go to the newest range
Hashhash(key) mod NEven spreadRange scans hit every shard; changing N moves almost every key
Consistent hashingHash ring with virtual nodes (Dynamo, Cassandra)Adding a node moves only about 1/N of keysStill one owner per key; hot keys stay hot
Virtual buckets / directoryKey → logical bucket → physical shard via a lookup tableMove a bucket without rehashing; flexibleThe directory is a critical service to keep available

How to choose the shard key

  1. High cardinality. Many distinct values, so load can spread. country is a bad key; user_id is good.
  2. Even load, not just even data. One merchant with 30% of payments makes merchant_id skewed even though most merchants are tiny.
  3. Matches the main access pattern. Notion picked workspace ID because every block belongs to exactly one workspace and users query one workspace at a time, so most queries never cross shards. Figma groups tables that share a key into "colos" so joins and transactions within one user, file or org stay on one shard.
  4. Avoid monotonic keys with range sharding. A timestamp or auto-increment ID sends every new write to the last shard. Hash it, or prefix it.

What sharding takes away. Figma's write-up is honest: queries without the shard key become scatter-gather across every shard; joins only work within a colo on the shard key; atomic cross-shard transactions are not supported, so partial failures must be handled in product logic; global unique IDs and unique indexes need new machinery. Their first table took about nine months to shard. Say this in an interview - it shows you know sharding is a cost, not a free lunch. For cross-shard work, see Multi-step Processes (Sagas) and Unique ID Generator.

Resharding without downtime follows the same recipe at Notion and elsewhere: double-write to old and new (Notion used an audit log plus a catch-up script), backfill history (about three days for them), verify with sampled comparisons and "dark reads" that compare both systems, then switch over with a rollback path ready. YouTube built Vitess in 2010 to do this routing and resharding for MySQL behind a proxy.

Breaks when: one key - not one shard - is too hot. Sharding spreads different keys; it does nothing for a single key that gets millions of writes.

Rung 2 - Split hot keys

DynamoDB documents its limits plainly: each partition delivers at most 3,000 read units and 1,000 write units per second (one write unit = one 1 KB write). Discord saw the same thing in Cassandra: one very busy channel bucket overloaded a node, and because reads and writes used quorum (a majority of the replicas, for example 2 of 3, must answer before the request completes), that node's slowness spread to unrelated users. A hot key needs to become several keys.

  • Random suffix. AWS's example: append a random 1-200 to a date key (2014-07-09.1 ... .200). Writes spread 200 ways; reading the day means 200 queries merged.
  • Calculated suffix. Use hash(order_id) % 200 instead of random, so a single item can still be found directly while writes stay spread.
  • Sharded counters. Firebase's distributed-counter guide does exactly this for counts: a counter is a set of shard documents, each increment goes to a random shard, the total is the sum. Their sample treats one shard as good for about one update per second, so 10 shards gives roughly 10x. Read cost grows with shard count, so add a periodically updated rollup.
  • Split all keys or only hot ones? Hello Interview names both. Splitting every key is simple but taxes every read. Splitting only detected hot keys (a "hot list" consulted by writers and readers) is cheaper on average but adds a moving part. Start with all keys for a known-hot key type (like counts on posts), dynamic for unpredictable ones.
  • Isolate the noisy tenant. Shopify learned this in February 2016: a Kylie Cosmetics sale overloaded one database shard and took down every other store on that shard too. Big tenants get their own shard; AWS's shuffle sharding limits how many customers share any one failure.

Rung 3 - Queues as shock absorbers

When the problem is a burst, not a steady rate, put a durable queue between the producer and the database. Producers append to the queue at whatever rate they like; consumers drain it at the rate the database can take. Microsoft calls this queue-based load leveling.

Why Kafka handles this so well: it is designed for sequential disk I/O and batching at every stage. In LinkedIn's 2014 benchmark on three ordinary machines (six SATA disks each, 1 Gb Ethernet), three producers wrote about 2 million 100-byte records per second with 3x asynchronous replication; median latency was 2 ms. Synchronous replication roughly halved single-producer throughput (from about 787K to 422K records/s), which is the durability cost made visible. See Kafka storage internals.

  • The client must accept "accepted, not done". Return 202 Accepted and an ID; the write becomes visible a little later. Fine for clicks and logs, wrong for "did my payment go through?" unless you add a status API (see Long-running Tasks).
  • A queue does not raise the sustained limit. If producers average more than consumers can write, lag grows forever. A queue buys time for bursts; for steady overload you still need more shards.
  • Load shedding is the honest alternative when even the queue would overflow: reject or degrade low-priority writes early. Shopify's first checkout throttle was a leaky bucket at the Nginx/OpenResty edge that sent excess users to a cached queue page instead of a 429 error (HTTP "429 Too Many Requests", the standard "slow down" reply). Its weakness, found at the next sale, was fairness: waits reached 40 minutes because random retries gave early arrivals no priority.

Rung 4 - Batch and aggregate before you write

Every write has a fixed cost: a network round trip, a lock, a log flush, an index update. Batching pays it once for many records. LinkedIn notes their producer uses group-commit-style batching, and Bigtable uses group commit for its commit log. In Kafka, linger.ms (default changed from 0 to 5 ms in Kafka 4.0) and batch.size control how long a producer waits to fill a batch.

  • Client-side batching: buffer 100 ms or 500 rows, whichever first, then one multi-row insert.
  • Aggregate in memory: for counters, do not write 10,000 "+1"s; keep a per-key sum for 5 seconds and write "+10,000" once. This is how ad click aggregation and like counters survive.
  • Hierarchical aggregation: edge servers pre-sum, regional aggregators sum the edges, one writer updates the store. Live reactions on a stream with millions of viewers work this way (Live Comments).
  • Coalesce overwrites: if a driver's location is written every 4 s but only the latest matters, keep the last value per key in memory and drop the rest.

Batching and buffering lose data on a crash unless the buffer is durable. A count that is a little low after a crash may be fine (views). A lost payment is not. For money, write each event durably (to Kafka with acks=all, where the producer waits until all in-sync replicas have the write, or to a WAL) before aggregating, and make flushes idempotent with an offset or batch ID - see Delivery Semantics.
