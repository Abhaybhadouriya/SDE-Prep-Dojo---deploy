Your write load is too high for one database. Which change does NOT help writes?

  1. Hash sharding
  2. Adding read replicas
  3. Batching inserts
  4. Dropping unused indexes
Every replica must still apply every write. Replicas scale reads only.

Orders are range-sharded by creation timestamp. What goes wrong?

  1. Range scans become slow
  2. Shards get uneven total data
  3. All new writes land on the newest shard
Monotonic keys put every new write at the end of the range: one hot shard.

What is the per-partition write limit DynamoDB documents?

  1. 1,000 write units per second
  2. 10,000 write units per second
  3. 100 write units per second
Each partition delivers up to 3,000 read units and 1,000 write units per second; hence write sharding.

A like counter is split into 20 sub-counters. What gets more expensive?

  1. Writes
  2. Storage of each like event
  3. Nothing
  4. Reading the total
The total is the sum of all sub-counters, so reads fan out - or you read a periodic rollup.

Producers average 12K writes/s; consumers can write 10K/s. You add a Kafka queue. What happens?

  1. The problem is solved
  2. Lag grows without bound
  3. Kafka drops 2K/s
A queue absorbs bursts. Under sustained overload the backlog grows forever; you need more consumer or database capacity.

Why did Notion choose 480 logical shards?

  1. It equals the number of CPU cores
  2. Postgres allows at most 480 schemas
  3. It has many divisors, so it spreads evenly across many host counts
480 divides evenly into 32, 40, 48 and more hosts, so future scale-outs stay balanced.

In an LSM-tree, when is the client's write acknowledged?

  1. After the commit log append and memtable insert
  2. After compaction
  3. After the SSTable flush
The log makes it durable and the memtable makes it readable; flushing and compaction happen later in the background.
