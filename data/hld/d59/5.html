Architecture: from location to match

  1. The phone talks to an API gateway, which checks the token and rate limits. Profile and location updates go to the profile service, whose source of truth is a KV store.
  2. Every profile or location change becomes an event on Kafka, keyed by userId, so one user's updates stay in order. An indexer writes them into a geo-sharded search cluster (one index per region of S2 cells).
  3. For a stack, the recommendation service finds the geoshards that overlap the user's distance circle, queries them in parallel with the filters, ranks the results, drops anyone in the user's seen Bloom filter, and caches about 100 cards in Redis.
  4. Each swipe goes to the swipe service. For a right swipe it runs one atomic Redis Lua script on the pair key: record my "yes", read the other direction. Left swipes skip Redis and only go to the durable store and the seen filter.
  5. The swipe is also written durably (Cassandra or DynamoDB) - asynchronously via a log, or synchronously if we want zero loss.
  6. If the other direction was already "yes", it is a match: return matched: true to this swiper and emit a match event; the notifier pushes it to the other person.
