Deep dives

1. Never miss a match (the race)

The naive flow is "write my swipe, then read the other person's swipe". Watch what happens when both run at the same time:

  1. Both write their own "yes" at almost the same moment, to different rows (or different replicas).
  2. Both read the other row before the other write is visible (different partitions, replica lag, or simply interleaving).
  3. Each concludes "no match yet". Nobody creates the match. Two people who like each other never find out.
  4. Fix: put both directions under one key and do write-and-check in one atomic operation. Operations on one key are serialised, so whoever runs second is guaranteed to see the first.

Options, weakest to strongest:

ApproachHowProblem
Polling jobA batch job scans for mutual likes every few minutesLate notifications, heavy DB load. OK only as a safety net.
Distributed transactionLock both users' rows across partitionsTwo-phase commit at 60k/s is slow and fragile. Cassandra lightweight transactions (Paxos) work only inside one partition.
Pair key in CassandraPartition key min:max; write my column and read the row in one partitionWorks; watch out for very active users and growing partitions; LWT adds Paxos round trips.
Pair key in Redis + LuaA Lua script runs atomically: set my direction, return the other; shard by key with consistent hashing; stream to Cassandra for durabilityIf Redis loses recent data, a match from the last moments can be missed - so a reconciliation job checks durable swipes
 
-- Only RIGHT swipes call this script; a left swipe can never complete a match,
-- so it goes only to the durable store (and the Bloom filter), never to Redis.
-- KEYS[1] = "swipe:{min}:{max}"   ARGV[1] = my direction field ("a2b" or "b2a")
-- ARGV[2] = other direction field
redis.call('HSET', KEYS[1], ARGV[1], 'yes')
redis.call('EXPIRE', KEYS[1], 1209600)        -- 14 days hot; older swipes live in Cassandra
return redis.call('HGET', KEYS[1], ARGV[2])   -- "yes" = match; nil = not in the hot window

If the script returns nil, the other person either has not swiped or swiped yes more than 14 days ago. The swipe service then does one single-partition read of the pair row in Cassandra. That read is safe from the race, because a swipe older than the hot window was written long ago and is visible; the race only exists between two swipes seconds apart, and those both go through Redis. Storing only right swipes for 14 days is what keeps Redis at about 1.5 TB instead of tens of TB (see the estimation).

Redis runs a script as one unit: no other command on that server runs in the middle of it. Because both users' swipes hash to the same key, they hit the same shard and are serialised. Creating the match itself uses the deterministic id min:max with "insert if not exists", so even if both requests somehow detect the match, only one match row and one notification pair is produced.

From your world

This is a critical section on one shared word. Two CPUs doing "store my flag, then load your flag" without a barrier can both miss each other - the classic store-buffer litmus test, and the reason Dekker/Peterson locks need memory fences. The fix is the same idea as an atomic read-modify-write on one cache line: put both flags in one location and update it atomically. The pair key is "same cache line"; the Lua script is the atomic instruction.

2. The geo-filtered stack: geosharding

The naive query is SQL: WHERE age BETWEEN ... AND gender = ... AND lat BETWEEN ... AND lng BETWEEN .... A B-tree can use one range well, not two, so this scans. Better: a search engine (Elasticsearch / OpenSearch) with geo-point fields, or a geo index (geohash, quadtree, S2). The real question at Tinder's scale is how to shard that index.

Tinder's engineering series "Geosharded Recommendations" (2019), as summarised by ByteByteGo, explains their answer:

  • Use Google's S2 library: it divides the Earth into a hierarchy of cells along a Hilbert curve, so nearby places get nearby cell ids. S2 cells at one level have roughly equal area (S2's statistics: level 7 averages about 5,189 km2, level 8 about 1,297 km2). Tinder found levels 7 and 8 the best fit.
  • Do not use equal-size shards: an ocean cell is empty, a Manhattan cell is on fire. Give each cell a load score (active users and queries from it), then group neighbouring cells into a "container" until it reaches a load threshold. That container becomes one geoshard. Dense cities get small shards, rural areas big ones.
  • All geoshards are separate indexes in one Elasticsearch cluster (cross-cluster queries were weaker and harder to run). Busy city shards get more replicas, quiet ones fewer, and shards are spread randomly across nodes so different time zones' peaks average out.
  • A query fans out to the geoshards that overlap the user's distance circle - the systemdesign.one write-up says about 3 shards on average for a 160 km radius - in parallel, then merges.

Users move. When a user travels (or uses a "Passport" feature), their document must leave the old shard and enter the new one. If "delete from old" and "insert into new" are processed out of order, you get a ghost in two places or in none. Tinder's fix: put every user's updates through Kafka partitioned by user id, so one user's updates are applied in order, and use the Elasticsearch Get API (which reads the latest version) where a strongly consistent read is needed. A background job periodically re-syncs the search index with the source of truth, catching failed writes.

Did it pay off? Tinder's 2025 post on migrating to Elasticsearch 8 says over 90% of their recommendations come from a single Elasticsearch cluster, that geosharding used about 12% CPU versus about 50% for a single-index approach, and that the migration cut p99 search latency by 12% to 56%. ByteByteGo's summary of the original work says the system handled about 20 times more computation while keeping latency low.

From your world

Partitioning one user's updates to one Kafka partition is per-flow hashing. NICs use RSS and routers use ECMP flow hashes so that all packets of one TCP flow take the same queue or path - otherwise they arrive reordered. Here a "flow" is one user's location updates, and reordering would put them in the wrong shard.

3. A stack that feels endless and fast

  • Precompute. A background job builds about 100 ranked candidates per active user into stack:{userId} with a TTL under an hour. The app loads from cache: well under 300 ms.
  • Refill early. When the client has only about 10-20 cards left, it asks for more. The server serves the cached remainder and computes a fresh batch from the index in the background - the user never hits an empty pile.
  • Invalidate on big changes. A new city or changed filters drops the cached stack.
  • Warm only active users. Precomputing stacks for 75M users who will not open the app today wastes compute; do it for users active recently and compute on demand for the rest.
  • Ranking. Within the candidates, order by predicted chance of a mutual like. The High Scalability "Designing Tinder" article describes a logistic regression on profile, history and photo features; Tinder's 2025 post reports two-tower model experiments that raised match rate by 6.5%. In an interview, one sentence on "candidate generation, then ranking" is enough (see Recommendation System).

4. Never the same card twice: Bloom filters

Filtering out already-swiped profiles with a database "NOT IN (my 50,000 swipes)" is slow and can miss very recent swipes that have not replicated yet. Layer it:

  1. Client cache. The phone remembers its last few hundred swipes and filters them out locally. That covers the replication gap.
  2. Per-user Bloom filter. On the server, seen:{userId} holds a Bloom filter of every profile the user swiped. Each candidate is checked with BF.MEXISTS before it goes into the stack.
  3. Source of truth. Swipe history in the durable store; the filter can always be rebuilt from it.

Why this error direction is perfect here: a false positive means we hide a profile the user never saw - a tiny loss nobody notices. A false negative (showing a repeat) is impossible. Sizing from the Redis docs: 1% error = 7 hash functions and 9.585 bits per item; 0.1% = 10 hashes and 14.378 bits. Bloom filters cannot delete items, which is fine (a swipe is forever; for "undo last swipe" keep the last swipe in a small exact list). Redis can stack sub-filters when a filter outgrows its capacity, at some cost in lookup latency.

Operational catch: if the Redis node holding the filters is lost, rebuilding millions of filters from swipe history is a big batch job. Persist the filters (RDB/AOF snapshots or BF.SCANDUMP), replicate them, and rebuild lazily: on a missing filter, rebuild that one user's filter on first use while the client cache covers the gap.

5. Hot users and spikes

  • Very popular profiles receive many right swipes. With the pair key, each (fan, star) pair is a different key, so the load spreads across shards. The star's "who liked me" list is the hotspot: write it asynchronously and cap it.
  • Evening peaks are predictable by time zone: scale the swipe service on schedule and on request rate.
  • Hot geoshards (a festival, New Year's Eve in one city) get extra replicas; the abstraction layer can re-balance shards because they are logical indexes, not machines.

6. Location privacy: do not let "3 km away" become a GPS fix

Explain like I'm 5

You hide a toy and your friend walks around asking "how far is it?". If you answer exactly ("4 steps", "7 steps", "2 steps"), three questions are enough to find it. If you only say "it is in this room", walking around the room tells your friend nothing new.

Showing "3 km away" on a card feels harmless. It is not. An attacker can fake their own GPS position (the app trusts whatever latitude and longitude the phone sends), ask for the distance to one victim from three different places, and draw three circles. The circles cross at the victim's home. This is trilateration (distances, not angles, so not triangulation), and it has hit real dating apps more than once:

  • Tinder (reported by Include Security, 2014): the API returned distances to other users with about 15 decimal places, enough to place someone within about 100 feet.
  • Bumble (reported by Robert Heaton, 2021): distances were rounded to whole miles, but rounded down. By moving the fake position step by step and watching when "3 miles" flipped to "4 miles", the attacker learned the exact 4.0-mile points, and three of those were enough again. Bumble fixed it within days of the report.
  1. The attacker fakes position P1 and asks for the victim's distance. One circle: the victim is somewhere on it.
  2. A second fake position, a second circle. Now there are only two candidate points.
  3. A third circle picks one point. With exact (or cleverly probed rounded) distances, that point is the victim's home.
  4. The fix: on the server, snap every user's location to the centre of a coarse grid cell before computing any distance.
  5. Now every fake position inside one cell gets the same answer, and the best any attacker can recover is the cell centre, not the person.

The layered fix

  1. Never send other users' coordinates to the phone. Compute distance on the server. (Tinder's first fix; necessary but not enough.)
  2. Snap before you compute. Round each stored location to a grid cell (Heaton suggests about 0.1 degree of latitude and longitude; a coarse S2 or geohash cell works the same way) and compute the distance between cell centres. 0.1 degree of latitude is about 11 km; 0.1 degree of longitude is about 11 km at the equator, 10.8 km in Bengaluru and 6.9 km in London (it shrinks with the cosine of latitude).
  3. Show bands, not numbers. "Less than 2 km", "2-5 km", "5-10 km" after snapping. Rounding alone leaks the flip points; snapping first means the flip points are cell edges, not the victim.
  4. No fresh random noise per request. If each query adds new random jitter, the attacker asks 100 times and averages it away. Noise must be fixed per pair (or per cell and time window), or skipped in favour of snapping.
  5. Make spoofing expensive. Rate-limit location updates and distance lookups per account; flag "impossible travel" (three positions 5 km apart in one minute); limit how many distances to one profile a viewer can request.
  6. Collect less. If the product only needs the cell, store only the cell. Data you never keep cannot leak in a breach either.
import math

CELL = 0.1  # degrees, about 11 km north-south

def snap(lat, lng, cell=CELL):
    """Move a point to the centre of its grid cell."""
    return ((math.floor(lat / cell) + 0.5) * cell,
            (math.floor(lng / cell) + 0.5) * cell)

def haversine_km(a, b):
    lat1, lng1, lat2, lng2 = map(math.radians, (*a, *b))
    h = (math.sin((lat2 - lat1) / 2) ** 2
         + math.cos(lat1) * math.cos(lat2) * math.sin((lng2 - lng1) / 2) ** 2)
    return 2 * 6371 * math.asin(math.sqrt(h))

def band(km):
    for limit in (2, 5, 10, 25, 50):
        if km < limit:
            return f"less than {limit} km"
    return "more than 50 km"

victim = (12.9352, 77.6245)            # true location, never leaves the server
for attacker in [(12.9300, 77.6200), (12.9500, 77.6300), (12.9100, 77.6400), (13.0500, 77.7000)]:
    exact = haversine_km(attacker, victim)
    shown = haversine_km(snap(*attacker), snap(*victim))
    print(f"attacker {attacker}: exact {exact:.3f} km -> shown '{band(shown)}' (snapped {shown:.1f} km)")

Three spoofed positions that are 0.8, 1.8 and 3.3 km from the victim all get the same answer, so they carry no information. Only a position in another cell gets a different band, and that tells you about cells, not people.

From your world

Snapping to a cell is route summarization for privacy: you advertise the /16, never the /32, so an outsider learns which network a host is in but not which host. The averaging attack on random noise is the same trick you use to measure latency through jitter: one ping is noisy, the mean of 1,000 pings is precise. Rounding down and probing for the flip point is a classic side channel too, like timing a non-constant-time compare one byte at a time.

Gotchas: two people 200 m apart on opposite sides of a cell edge will show as about one cell apart; that is the price, and bands hide most of it. Snap the stored value too, not only the displayed one, or a later feature (or a log line) leaks the precise point. "Recently active" and "last seen" timestamps combined with location can identify routines, so coarsen time as well. Geosharding (deep dive 2) can keep using precise cells internally; only what crosses the API boundary needs to be coarse.
