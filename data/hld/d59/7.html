Where Kafka, Kubernetes and Docker fit

PieceRole here
Kafkaprofile-updates keyed by userId (ordering for geoshard moves, as Tinder did); swipes keyed by pair key (durable write-behind from Redis to Cassandra, analytics, model training); matches for the notifier. Tinder's ES8 migration used a Kafka stream as the source of truth to backfill a brand-new cluster with a new consumer group. On a consumer-lag spike (say the indexer falls 10 minutes behind on profile-updates during an evening peak): swiping and matching are unaffected, because they do not wait on Kafka; what degrades is freshness, so moved users appear in the wrong area and new profiles show up late. Watch lag per consumer group, scale the indexer on lag (KEDA or an HPA on a lag metric), and, if lag on swipes grows, remember that the durable copy is behind, so the reconciliation job must not run on a window that Kafka has not yet delivered. See Kafka core concepts.
KubernetesSwipe, recommendation and notifier services as Deployments with HPA (swipe service scales on request rate, the indexer on consumer lag). Tinder runs Elasticsearch with Elastic Cloud on Kubernetes (ECK) per its 2025 post - a StatefulSet-based operator. See StatefulSets & Operators and autoscaling.
DockerEach microservice is an image; the ranking model is packaged with the recommendation service or served from a model server image. See Dockerfile.
