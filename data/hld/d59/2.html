Back-of-envelope estimation

Inputs from Hello Interview (20M DAU, 100 swipes/day, about 100 bytes per swipe). Public figures for scale checks: ByteByteGo's write-up of Tinder's geosharding (splitting the search index into shards by geographic area, with busy cities getting smaller shards) says Tinder matches "over 75 million users"; the systemdesign.one newsletter reports around 26 million matches a day and about 500 microservices. Other numbers are our assumptions. We use 100,000 seconds per day. (Method: Back-of-Envelope Estimation.)

  1. Swipes per day. 20M users x 100 = 2 billion swipes/day.
  2. Swipe write QPS. 2,000,000,000 / 100,000 = 20,000 writes/s average. Evenings peak at maybe 3x: 60,000/s. This is the hottest path.
  3. Swipe storage. 2B x 100 bytes = 200 GB/day, about 73 TB/year. Keep hot data (recent months) online in Cassandra or DynamoDB; archive left swipes to cheap object storage.
  4. What fits in Redis? Not every swipe. If Redis kept every pair for 90 days: 2B x 90 = 180B pair entries; at 100-200 bytes per small hash including Redis overhead, that is 18-36 TB of RAM. Too much. A match only needs to know that the other side said yes, so keep only right swipes in Redis, for a short window. Assume 30-40% of swipes are right swipes (our assumption) and a 14-day TTL: 0.35 x 2B/day x 14 days = ~10B entries x ~150 B = ~1.5 TB across the Redis cluster, which is a normal sharded cluster. Older right swipes are checked in Cassandra.
  5. Matches. About 26M/day (reported) = 260 matches/s, each triggering 2 notifications. Small.
  6. Stack loads. If a stack holds about 100 cards, a 100-swipe user loads 1-2 stacks a day: 20M x 2 = 40M/day = 400 stack requests/s. Each one is a geo + filter query, so 400 heavy searches/s, not 20,000.
  7. Location updates. Assume 5 per user per day (app opens): 100M/day = 1,000 index updates/s into the geo index.
  8. Profile index size. 75M searchable profiles x about 1 KB (age, gender, preferences, location cell, scores) = 75 GB. Fits in a modest search cluster; photos live in object storage + CDN.
  9. Seen-filter size. A Bloom filter at 1% false positives needs 9.585 bits per item (Redis docs). A heavy user with 100,000 swipes needs 100,000 x 9.6 / 8 = about 120 KB. An exact set of 8-byte ids would be 800 KB+ with overhead.

The numbers tell us the shape: the swipe service is a write-heavy, simple key-value workload and must scale on its own; the recommendation service is a low-QPS but expensive geo search. Split them into separate services and stores.
