Back-of-envelope estimation

Method from Back-of-Envelope Estimation. All counts below are our assumptions; say them out loud and let the interviewer change them.

~11K/smeter readings (avg)
~100K/stemperature readings
~250K/sdriver pings (peak)
~10 GB/daymeters after compression

Smart meters

  1. Devices Assume 10M households, one reading every 15 minutes (a common metering interval; ask). That is 96 readings per meter per day.
  2. Average rate 10M x 96 = 960M readings a day. 960M / 86,400 s = about 11K per second.
  3. The real peak If every meter sends exactly at :00, :15, :30, :45, then 10M readings arrive in a few seconds: millions per second for a moment, then silence. That synchronised burst, not the average, sizes the front door. Fix it with jitter: each meter adds a random 0-300 s offset (set by device config), which spreads 10M readings over 5 minutes = about 33K per second.
  4. Storage One reading is about 100 bytes with metadata (device id, timestamp, kWh, voltage, quality flags). 960M x 100 B = about 96 GB a day raw. Time-series compression (delta-of-delta timestamps, XOR floats, columnar) commonly gives around 10x on regular sensor data: about 10 GB a day, roughly 3.5 TB a year.
  5. Rollups Hourly per meter: 10M x 24 = 240M rows a day, but a "my usage this year" chart reads only 8,760 rows (or 365 daily rows). That is why history reads come from rollups.

Continent temperature heatmap

  1. Devices Assume 1M sensors, one reading every 10 s: 100K readings per second, about 8.6B a day.
  2. Grid Europe is about 10M km2. An H3 resolution-5 cell averages about 253 km2 (H3 resolution table), so the whole map is about 40K cells. A browser can draw 40K cells; it cannot draw 1M sensor points nicely.
  3. Live state 40K cells x about 50 bytes (avg, min, max, count, updated_at) = 2 MB. The whole live map fits in one Redis hash.
  4. Zoom Zoomed in, use resolution 7 (about 5.2 km2) for the visible area only. Each finer resolution has cells about 1/7 the area of the parent.

Uber driver heatmap

  1. Devices Assume 1M drivers online at peak worldwide, each phone sending a location every 4 s: 250K pings per second.
  2. Per city A big city might have 50K online drivers = 12.5K pings per second. At H3 resolution 8 (about 0.74 km2 per cell), a 1,500 km2 metro is about 2,000 cells.
  3. Output size Live heatmap for one city = 2,000 cells x (cell id 8 bytes + count 4 bytes) = 24 KB. Send it once as a snapshot, then only changed cells once per second: a few KB per second per viewer.
  4. Viewers Operations dashboards, not riders: say 5,000 viewers worldwide. 5,000 x 5 KB/s = 25 MB/s outbound. Small. The heat is in ingest and aggregation, not fan-out.

Machine sensors

  1. Devices 100K machines x 10 sensors x 1 reading per second = 1M readings per second. Alerting must keep per-sensor state for 1M sensors: about 1M x 200 bytes = 200 MB. Fits in Flink keyed state spread over a few workers.

What the numbers tell you: ingest rate is high but each event is tiny and independent, so it partitions perfectly by device. The live view is small (thousands of cells). The two real problems are bursts and lateness at the front door and doing the aggregation once, correctly (no double counting) before fanning out to dashboards.
