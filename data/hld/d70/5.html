Architecture: from a device shout to a red hexagon

Click Next or Play. One ingest path, then three consumers of the same Kafka topic: live view, history, alerts.

  1. Devices connect. Each device opens one MQTT connection over TLS with its own certificate and publishes at QoS 1 (at-least-once). A managed broker such as AWS IoT Core handles millions of connections; its documented limits include a 128 KB payload and 100 publishes per second per connection, so devices batch small readings. Simple devices may POST over HTTPS instead.
  2. Land in Kafka. A rule or bridge forwards every message to telemetry.raw, keyed by device_id, so each device's readings stay in order on one partition. Kafka is the shock absorber for the quarter-hour burst and lets us replay if a consumer has a bug.
  3. Process once. Flink drops duplicates by (device_id, seq) using keyed state with a TTL, converts location to an H3 cell (fixed devices look it up from the registry; drivers compute it per ping), assigns event time, and aggregates per (cell, window). Late data is handled with watermarks and allowed lateness.
  4. Update the live state. Once per second per city (or region), Flink writes changed cells into a Redis hash heat:{city} and bumps a version number.
  5. Push to dashboards. Flink also publishes a small delta {version, changedCells} on a Redis channel heat:{city}. Each WebSocket gateway pod subscribes only to channels its connected viewers watch, and forwards the delta to those sockets. A new viewer first GETs the snapshot (the hash), then applies deltas with a higher version.
  6. Store history. A sink writes raw readings to the TSDB (continuous aggregates build hourly and daily rollups) and to S3 as Parquet. Batch jobs on S3 build the "after 24 hours" daily bucketed view and repair anything the stream got wrong (late data).
  7. Evaluate alerts. A separate Flink job keyed by sensor_id keeps a tiny state per sensor (in or out of range, since when). Rules arrive as broadcast state. On a sustained breach it opens an alert (the unique index refuses duplicates) and calls the notification system.
  8. Serve queries. The query API reads history from rollups (choosing resolution from the range), lists alerts, and performs ack / resolve / ignore as guarded state transitions.
