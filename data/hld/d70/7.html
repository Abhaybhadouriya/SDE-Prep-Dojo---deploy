Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key device_id keeps each meter's readings in order and spreads load evenly. Consumer-group sizing: 250K events/s needs only about 5 partitions for throughput, but plan 64-128 (here 96) so the Flink job can run up to 96 parallel tasks. Gateways scale on open connections; Flink scales by changing job parallelism, which re-distributes keyed state from checkpoints.

  • Kafka: telemetry.raw keyed by device_id (ordering per device, even spread). Partitions: at 250K events per second and, say, 10 MB/s per partition with 200-byte events (50K events per second), 5 partitions would do, but plan 64-128 for consumer parallelism and growth. Retention 3-7 days so any consumer can replay. A second topic telemetry.cells (keyed by cell) carries pre-aggregated minute buckets; alerts.events carries breach events. Use the Kafka producer with acks=all and idempotence on the bridge.
  • Kubernetes: WebSocket gateways as a Deployment scaled by connection count (custom metric via HPA or KEDA), with a long terminationGracePeriodSeconds so clients reconnect gently during rollouts. Flink via the Flink Kubernetes Operator, with checkpoints to S3. Query API as a normal stateless Deployment. The MQTT broker is usually managed (AWS IoT Core, Azure IoT Hub); self-hosted brokers (EMQX, HiveMQ, Mosquitto) run as a StatefulSet.
  • Docker: every service ships as an image; a docker compose file with Mosquitto, Kafka (KRaft), Flink, Redis and TimescaleDB gives a laptop-sized copy of the whole pipeline for testing.

Rebalance gotcha: when the alert evaluator scales, Kafka partitions move between workers. Flink handles this with checkpointed keyed state (state moves with the key group). A plain Kafka consumer keeping per-sensor state in memory would lose it on rebalance, so it would need a state store (Kafka Streams RocksDB with changelog topics) instead.
