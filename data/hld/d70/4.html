Data model

Store choice reasoning is in Choosing Storage. Five kinds of data, five access patterns.

DataStoreKeyWhy
Device registry: id, type, owner, fixed location + H3 cell, cert fingerprint, firmware, config versionPostgreSQL (or DynamoDB)device_id; index by owner, by cellSmall, relational, needs uniqueness and joins to owners
Raw readingsTime-series DB (TimescaleDB hypertable, InfluxDB, Amazon Timestream) or Cassandra wide rows(device_id, ts), partitioned by time chunkAppend-only, range reads per device, compresses well, drop old chunks cheaply
Rollups: per device per hour/day; per cell per minute/hourContinuous aggregates in the TSDB, or an OLAP store (Apache Pinot, ClickHouse, Druid)(device_id | cell, bucket)Years of history at chart speed; area queries scan cells, not devices
Live state per cellRedis hash per region/cityheat:{city} field = cell idO(1) upsert and full-map read in milliseconds

-- TimescaleDB: raw readings, chunked by day, compressed after 2 days, dropped after 90
CREATE TABLE reading (
  device_id  BIGINT       NOT NULL,
  ts         TIMESTAMPTZ  NOT NULL,
  seq        BIGINT       NOT NULL,
  metric     SMALLINT     NOT NULL,
  value      DOUBLE PRECISION,
  PRIMARY KEY (device_id, ts, metric)
);
SELECT create_hypertable('reading', 'ts', chunk_time_interval => INTERVAL '1 day');

-- hourly rollup maintained in the background
CREATE MATERIALIZED VIEW reading_1h WITH (timescaledb.continuous) AS
SELECT device_id, metric, time_bucket('1 hour', ts) AS bucket,
       sum(value) AS total, avg(value) AS avg, min(value) AS min, max(value) AS max, count(*) AS n
FROM reading GROUP BY device_id, metric, bucket;

SELECT add_compression_policy('reading', INTERVAL '2 days');
SELECT add_retention_policy('reading', INTERVAL '90 days');   -- rollups are kept longer

-- alerts: one OPEN alert per (sensor, rule) at a time
CREATE TABLE alert (
  alert_id     BIGINT PRIMARY KEY,
  machine_id   BIGINT NOT NULL,
  sensor_id    BIGINT NOT NULL,
  rule_id      BIGINT NOT NULL,
  state        TEXT   NOT NULL,      -- OPEN, ACKNOWLEDGED, RESOLVED, IGNORED
  opened_at    TIMESTAMPTZ NOT NULL,
  first_value  DOUBLE PRECISION,
  peak_value   DOUBLE PRECISION,
  acked_by     BIGINT, acked_at TIMESTAMPTZ,
  resolved_at  TIMESTAMPTZ, resolution TEXT,     -- AUTO (back in range) or MANUAL
  ignore_until TIMESTAMPTZ
);
CREATE UNIQUE INDEX one_active_alert ON alert (sensor_id, rule_id)
  WHERE state IN ('OPEN', 'ACKNOWLEDGED');

The partial unique index is the interview gem: the database itself refuses a second active alert for the same sensor and rule, so a retried or duplicated breach event cannot open two alerts. Same idea as the armed flag in Price Tracker & Alerts.
