Deep dives

1. The front door: bursts, duplicates, late and out-of-order data

Devices are not polite clients. They retry, they lose connectivity for hours, their clocks drift, and a firmware default can make 10M of them speak in the same second. Handle each problem with a specific tool:

  • Synchronised bursts: jitter in device config (random offset per device), plus Kafka as a buffer. The broker and Kafka are sized for the jittered peak; consumers can lag a little.
  • Duplicates: QoS 1 means at-least-once, so the same reading can arrive twice. Each reading carries (device_id, seq). Flink keeps the highest seen sequence (or a small recent set) per device in keyed state; repeats are dropped. The TSDB primary key also rejects them, so dedupe exists at two layers.
  • Offline backlog: the device stores readings locally and uploads a batch on reconnect. They have old event timestamps. Use event time (when measured), not processing time, for buckets.
  • Late data: a Flink watermark of, say, "max event time seen minus 30 s" closes windows. Allowed lateness (Flink's default is 0) keeps window state open a bit longer and re-fires with the corrected value. Anything later still goes to a side output and to S3, where the nightly batch includes it. The live map is "fast and almost right"; the daily view is "slow and right".
  • Clock skew: reject or clamp timestamps far in the future, and record both device time and broker arrival time.

A smart-meter design that uses processing time puts a meter's 2 a.m. usage into the 9 a.m. bucket when it reconnects in the morning. For billing that is a real bug, not a rounding error.

2. Spatial bucketing: geohash vs H3

A heatmap needs "which area is this point in?". Options:

GeohashH3
ShapeRectangles, size depends on latitudeHexagons (plus 12 pentagons), near-uniform area
IndexBase-32 string; prefix = parent64-bit integer; 16 resolutions (0-15), each about 1/7 the parent's area
Neighbours8, at two different distances6, all at the same distance
Good forPrefix range scans in any KV storeHeatmaps, surge pricing, smoothing (k-ring), moving objects

Uber built H3 because people in a city are always moving, and hexagons limit the error when you count things crossing cell edges; it buckets ride requests, trip starts and food orders into hexagons and computes supply and demand per hexagon for surge pricing (Uber Engineering: H3). For a fixed sensor the cell is computed once at registration; for a driver it is computed on every ping, which is cheap (a few microseconds). Pick the resolution per zoom level: about 0.74 km2 (res 8) for a city view, about 253 km2 (res 5) for a continent. Rolling up is just "parent of this cell", so compute the fine resolution in the stream and derive coarse ones by summing children. More in Geo & Specialized Indexes and Geo Proximity.

3. Stream vs batch: the Uber "20 minutes live, daily after 24 hours" split

The 2025-08 Uber bar-raiser version asked for two views of the same data: a near-real-time heatmap of the last 20 minutes, and a bucketed view that is available after 24 hours. That is a hint to name both paths and say why each exists.

  • Counting moving drivers correctly. A driver pinging every 4 s appears 300 times in 20 minutes. "Driver density" means distinct drivers, not pings. Two good definitions: (a) latest position: keep each driver's current cell (keyed state); on a move, decrement the old cell and increment the new; drop drivers silent for 60 s. That gives "drivers here now". (b) distinct drivers per cell in the window: a HyperLogLog sketch per cell per minute, merged over 20 minutes. Ask which the dashboard wants.
  • Windows. Flink tumbling windows of 1 minute per cell, then a 20-minute sliding sum (keep 20 buckets per cell in a ring, like a kernel's per-CPU counters). A Flink sliding window of size 20 min and slide 1 min works too, but each event lands in 20 windows, so pre-aggregating into minute buckets is cheaper.
  • Daily view. Nightly (or hourly) batch over S3: group by cell and hour, write a table. It includes late events and corrections. This is the classic Lambda split; a Kappa alternative replays Kafka with a longer allowed lateness. Saying "the batch job is the correctness backstop" is the point.
  • Real-world shape. Uber's city-operations dashboards run on Apache Pinot, which ingests from Kafka (sometimes after FlinkSQL pre-aggregation) and combines real-time and historical data, tracking demand-supply balance and things like delayed orders in the last five minutes (Operating Apache Pinot at Uber). So "Kafka to Flink to an OLAP store, dashboards query it" is a realistic answer for the history and analytics side.

4. Pushing updates: exactly how Redis pub/sub feeds WebSockets

This is where a 2026-03 Uber candidate lost the senior level: they said "Redis as cache and pub/sub to push via WebSockets", and the interviewer asked how, exactly. Here is a complete answer you can draw.

  1. Two Redis structures, two jobs The hash heat:{city} is the state (the current count per cell). The channel heat:{city} is the signal. Never use the channel as the only copy of the data.
  2. Writer Every second, the Flink sink for a city runs a small Lua script (or a MULTI): HSET the changed cells, INCR heat:{city}:ver, and SPUBLISH heat:{city} {ver, cells}. Running them together guarantees the published version matches the stored state.
  3. Gateway subscribes on demand When the first browser on pod A asks for Bangalore, pod A runs SSUBSCRIBE heat:blr and keeps a local map channel -> set of sockets. When the last viewer leaves, it unsubscribes. One Redis subscription per pod per city, no matter how many browsers.
  4. New viewer The browser opens the WebSocket, the pod sends the snapshot from HGETALL heat:blr together with its version, then forwards only deltas whose version is higher.
  5. Missed messages Redis pub/sub is at-most-once: if a subscriber is disconnected, the message is simply lost (Redis docs). So the client checks versions; if it gets 915 after 912, it re-fetches the snapshot. If you need replay, use Redis Streams or Kafka instead of pub/sub.
  6. Scale In Redis Cluster, classic PUBLISH is broadcast to every node over the cluster bus. Sharded pub/sub (SPUBLISH/SSUBSCRIBE, Redis 7.0+) hashes the channel to one slot like a key, so adding shards adds pub/sub capacity. Channel per city keeps the per-channel rate tiny (one message per second).
  7. Backpressure If a browser cannot keep up, the pod drops intermediate deltas and sends the latest snapshot. Throttle to one push per second per channel; a human cannot see faster.
  8. Sticky routing not required Any pod can serve any city because state is in Redis. The load balancer only needs WebSocket support and long idle timeouts; pods are scaled by connection count.

If asked "why not have Flink push straight to the WebSocket servers?": Flink would need to know which pod holds which viewer, and pods come and go. Pub/sub decouples them: Flink publishes per city, pods subscribe per city. Alternatives worth naming: Kafka consumer per pod (replayable, heavier), or managed services (AWS AppSync, API Gateway WebSockets). Polling every 2 s is a fine SDE-1 answer for 5,000 internal viewers; say so, then show the push design.

5. The alert state machine (machine sensors)

The Microsoft round wanted thresholds per sensor type and alerts that users can acknowledge, resolve or ignore. The trap is flapping: a temperature hovering at 80.1 / 79.9 opens and closes 100 alerts an hour.

  • Rule lookup: effective rule = per-machine override if present, else per sensor type. Rules are small, so broadcast them to every evaluator (Flink broadcast state) and update them without a restart.
  • Debounce: open only after the value is out of range for forSeconds (or N consecutive readings). Prometheus alerting rules use the same for: idea.
  • Hysteresis: close only when back inside the range by a margin (for example below 78 when max is 80), so one noisy reading does not resolve it.
  • Idempotent open: the evaluator emits an event with key (sensor_id, rule_id, breach_start); the alerts service inserts with the partial unique index, so replays and retries are harmless.
  • User actions: ack and resolve are compare-and-set transitions: UPDATE alert SET state='ACKNOWLEDGED', acked_by=?, acked_at=now() WHERE alert_id=? AND state='OPEN'. Zero rows updated means someone else got there first; show the current state.
  • Ignore: sets ignore_until; the evaluator checks a suppression list before opening. Always time-bound it (maintenance windows), never "forever".
  • Escalation: an OPEN alert not acknowledged in 15 minutes pages the next person. That is a delayed job, like in Job Scheduler.

6. Time-series storage: downsampling and retention

Raw readings are the biggest data set and the least read. Keep raw data hot for days, compressed for weeks, and delete it after the retention period; keep rollups far longer. In TimescaleDB, continuous aggregates refresh in the background and can be stacked (hourly from raw, daily from hourly); real-time aggregates combine the materialized part with the most recent raw rows, so "today" is always current (TimescaleDB docs). Set the raw retention policy longer than the aggregate refresh window, otherwise you delete data before it is rolled up.

TierResolutionKeptServes
Raw, uncompressedEvery reading2 daysDebugging, late-data merges, alert replays
Raw, compressedEvery reading90 days"Show me last week at full detail"
Hourly rollupsum / avg / min / max / count2-5 yearsMonthly and yearly charts, billing checks
Daily rollupSameForever (tiny)Multi-year trends
S3 ParquetEvery readingPer policy (years, cold)Re-processing, analytics, audits

Store sum and count, not just the average: you can re-aggregate sums and counts into coarser buckets, but you cannot average averages. Choose the rollup in the query API from the range: under 2 days use raw, under 3 months use hourly, beyond that daily. Every chart then reads a few hundred to a few thousand points.
