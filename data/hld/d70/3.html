Key APIs

Devices talk MQTT (or HTTPS for simple ones); dashboards talk REST plus a WebSocket. Background in API Design & Client-Server Communication and Real-time Updates.

# --- device side (MQTT, TLS with a per-device X.509 certificate) ---
PUBLISH  telemetry/{deviceId}         QoS 1
  { "seq": 88123, "ts": "2026-11-23T08:15:02Z", "kwh": 0.42, "v": 231.4 }
PUBLISH  telemetry/{deviceId}/batch   QoS 1     # backlog after being offline
  { "readings": [ {"seq": 88124, ...}, {"seq": 88125, ...} ] }
SUBSCRIBE config/{deviceId}                     # sampling rate, jitter, thresholds

# --- device side, HTTP fallback ---
POST /v1/ingest   (mTLS)  [ {deviceId, seq, ts, metric, value} ... ]  -> 202 Accepted

# --- dashboards ---
GET  /v1/heatmap?region=eu&res=5&metric=temp           -> snapshot { version, cells:[[h3, avg, n], ...] }
GET  /v1/heatmap/drivers?city=blr&res=8&window=20m     -> snapshot { version, cells }
GET  /v1/heatmap/drivers/daily?city=blr&date=2026-11-22&bucket=1h
GET  /v1/devices/{id}/series?metric=kwh&from=..&to=..&step=1h
GET  /v1/areas/{h3}/series?metric=temp&from=2025-03-01&to=2025-03-31&step=1d
WS   /v1/live?channel=heat:blr                       # server pushes {version, changedCells}

# --- alerts ---
GET   /v1/alerts?machineId=m_77&state=OPEN
POST  /v1/alerts/{id}/ack        { "note": "tech on the way" }
POST  /v1/alerts/{id}/resolve    { "note": "fan replaced" }
POST  /v1/alerts/{id}/ignore     { "until": "2026-11-24T00:00:00Z", "reason": "maintenance" }
PUT   /v1/rules/{sensorType}     { "min": 10, "max": 80, "forSeconds": 30 }
PUT   /v1/machines/{id}/rules/{sensorType}   # per-machine override

Three details interviewers notice. (1) Every reading carries a per-device sequence number: it makes retries and replays idempotent (dedupe on (device_id, seq)). (2) The live API is snapshot + versioned deltas, so a client that misses a delta can detect the gap and refetch. (3) Alert actions are state transitions with a reason and an actor, not "update the row however you like".
