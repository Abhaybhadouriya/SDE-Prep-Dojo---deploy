Quick quiz

Which storage approach scales best for "every Tuesday, forever"?

  1. One row per occurrence, so every read is a plain range scan
  2. The rule as truth plus a materialised window of dates
  3. Only the rule, expanded on every read, so edits stay cheap
The hybrid keeps edits cheap (one rule) and reads fast (an index of the next months), with on-demand expansion beyond the window. "Forever" rules out one row per occurrence, and expanding on every read is slow for the 200,000 reads/s peak.

A weekly meeting at 09:00 America/New_York. What should be stored?

  1. 09:00 plus the zone America/New_York
  2. 13:00 UTC, converted once when the event is saved
  3. 18:30 IST, the server's own local time zone
Wall time plus zone keeps the meeting at 09:00 for the organizer across DST; UTC is computed per occurrence. A single UTC value is right for half the year and an hour off for the other half.

How do you model "change the time from 6 January, this and following"?

  1. Add an EXDATE for each future date of the old series
  2. Edit the master rule, so all past dates move too
  3. End the old rule with UNTIL; start a new series on 6 Jan
Splitting keeps past occurrences unchanged and gives future ones the new values. EXDATEs for every future date never end on a "forever" series, and editing the master rewrites history.

Why does the reminder engine need sharded minute buckets?

  1. Reminders are spread evenly, so any shard can take any job
  2. Phones accept one push a minute, so buckets throttle them
  3. They spike before :00 and :30; one scanner is too slow
Meetings start on round times, so reminders bunch up into one hot minute. Shards let many workers read that minute in parallel.

A ticker loaded a reminder, then the organizer moved the meeting. What prevents a wrong reminder?

  1. The row carries SEQUENCE; the worker drops stale versions
  2. Kafka exactly-once delivery cancels the queued reminder
  3. Nothing; it fires, and the user sees the new time anyway
A version check at fire time makes the race safe even if the cancel message has not been processed yet. Kafka EOS cannot un-send a message that a worker already holds in memory.

A device's sync token is too old and the server returns 410 Gone. What should the client do?

  1. Retry with the same token, using exponential backoff
  2. Clear local data and do a full sync
  3. Ignore it; the next incremental sync will catch up
Google's sync guide says a 410 means the token is invalid; the client wipes its store and resyncs from scratch. Retrying the dead token returns 410 forever.

What should a free/busy query return?

  1. Busy start/end intervals only, with no titles
  2. Full event details, so assistants can plan around them
  3. Only events the caller organised, with their attendees
Free/busy shares availability without leaking what people are doing. Events the caller did not organise still block time, so they must be counted.

Which number should size the reminder system?

  1. The average of ~4,000 notifications per second
  2. The total of ~10 billion deliveries a month
  3. The ~140,000/s spike in the minute before :00
Reminders cluster before round times. A system sized for the average would be 35x too small in the minute that matters.
