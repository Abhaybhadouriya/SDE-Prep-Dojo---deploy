Data model

The industry standard for calendar data is iCalendar (RFC 5545). Its words are worth using in the interview because every real system, Google and Outlook included, speaks it:

  • RRULE - the repeat rule. FREQ is required; COUNT or UNTIL ends it (never both); INTERVAL, BYDAY, BYMONTH refine it.
  • RDATE adds extra dates; EXDATE removes dates. Google defines the set of occurrences as all RRULE and RDATE results minus the EXDATE ones.
  • RECURRENCE-ID - names one occurrence by its original start, so an override can point at it. With RANGE=THISANDFUTURE it means "this and all later ones".
  • SEQUENCE - a revision number that goes up on every significant change, so a client can tell which copy is newer.
  • VALARM with TRIGGER - the reminder, usually a negative duration such as 10 minutes before start.

SQL or NoSQL?

Pick a relational store sharded by calendar_id (Postgres or MySQL with Vitess, or a globally distributed SQL database such as Spanner or CockroachDB). Reasons:

  • An edit touches several rows together: the master event, its exceptions, attendee rows and the change log. Transactions keep them consistent.
  • The main query is a range scan: "all instances for calendar X between Monday and Sunday". A B-tree on (calendar_id, start_utc) does that in one seek plus a short scan.
  • Write volume (~7,000/s peak) is modest. We do not need a write-optimised wide-column store for events.

The reminders_due table is different: it is a pure time-ordered queue with heavy insert and delete. A key-value store with a sort key (DynamoDB, Cassandra) or a dedicated delayed-queue service suits it. Airbnb's open-source Dynein scheduler stores its schedules in a DynamoDB table keyed by shard_id (hash key) and date_token (range key) (Dynein README), which is exactly this shape.
