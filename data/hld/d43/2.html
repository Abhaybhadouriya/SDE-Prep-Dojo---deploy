Back-of-envelope estimation

We will use the scale figures Educative uses for its Google Calendar case study: about 500 million monthly active users, about 2 billion events created per month, about 10 billion notification deliveries per month, and 3-4 devices per active user. The rest are our own stated assumptions. In an interview, always say "assume" before a number you made up. See Back-of-Envelope Estimation for the method.

  1. Seconds in a month. 30 days x 86,400 s = 2.6 million seconds. Round to 2.5 x 106 to make division easy.
  2. Event writes. 2 x 109 / 2.5 x 106 = ~800 creates/s on average. Add edits and RSVPs (assume 2x creates) and you get ~2,400 writes/s. Office hours on Monday morning can be 3x the average, so plan for ~7,000 writes/s peak. That is small; a sharded SQL fleet handles it easily.
  3. Reads. Assume 200 million daily active users, each opening a view 5 times a day, and each of 3 devices syncing 10 times a day: 200M x (5 + 30) = 7 x 109 reads/day. Divide by 86,400 (round to 105): ~70,000 reads/s average, ~200,000 reads/s peak. Read to write ratio is roughly 30:1, so this is a read-heavy system. Caching the week view matters.
  4. Reminder rate, average. 10 x 109 notifications / 2.5 x 106 s = ~4,000 per second on average.
  5. Reminder rate, the real peak. Meetings start on the hour and half hour, and the default reminder is a fixed number of minutes before. So reminders pile into a few seconds at :50, :55, :20 and :25. Assume 20% of a busy hour's reminders land in one minute: with an hourly rate of 4,000 x 3,600 x 3 (busy-hour factor) = 43 million, the spike minute holds 8.6 million reminders, which is ~140,000 per second for that minute. This spike, not the average, sizes the reminder system.
  6. Event storage. Assume ~1 KB per event row (title, description, times, rule, metadata) and 100 bytes per attendee row with 4 attendees on average. Per year: 24 x 109 events x 1.4 KB = ~34 TB/year. With 3 replicas, ~100 TB/year. Ten years of history is a petabyte-class store, so we shard.
  7. Instance index (materialised occurrences). Count active series from users, not from creates. Assume each of the 500 million MAU owns about 0.6 active recurring series (a weekly 1:1, a team stand-up). That is ~300 million active series. Most recurring series end or get replaced (a "this and following" edit ends one series and starts another), so the active count does not grow with the 2 billion monthly creates. Assume weekly on average and expand 12 months ahead: 52 rows each. 300 million x 52 = 15.6 billion index rows x 50 bytes = ~0.8 TB, cheap enough to keep hot. (If instead you assumed 30% of creates are new long-lived series, you would get billions of active series and ~10 TB. Still fine, but say which assumption you use.)
  8. Bandwidth. A week view is ~20 events x 1 KB = 20 KB. 200,000 reads/s x 20 KB = 4 GB/s = ~32 Gbit/s peak egress, mostly served from cache and compressed.
