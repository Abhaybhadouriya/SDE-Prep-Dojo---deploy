What this design gets right
  • One source of truth; every other store is rebuildable.
  • Reminder spike is spread across shards and buffered.
  • DST changes are handled by recomputation, not data migration.
Where it hurts
  • Materialised windows must be extended and re-expanded on tz rule changes.
  • Huge invites need a separate read path.
  • Eventual consistency means a just-created event may take a second to appear on another device.

Failure modes to mention

  • Ticker worker dies mid-minute. Its shard leases expire; another worker takes them and scans "overdue and still pending" rows. Dynein's config exposes the same idea as a heartbeat stall tolerance and a look-ahead for recovering stuck jobs.
  • Notification provider (APNs/FCM/SMTP) is slow. Reminders queue in reminders-due; the clock is unaffected. Drop reminders that are hopelessly late (a reminder for a meeting that ended is noise).
  • Shard hot spot. A celebrity-style public calendar ("national holidays") followed by millions is a hot key; serve it from cache as a shared read-only calendar, never fan it out.
  • Region loss. Events DB replicates synchronously within a region and asynchronously across regions; reminders for the failed region must fail over with their shards, so run tickers per region with region-pinned shards.
