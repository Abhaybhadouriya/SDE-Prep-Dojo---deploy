Architecture: follow one event

Click Next or Play. We follow Asha creating a weekly "Team sync" with two attendees, then watch the reminder fire next Tuesday.

  1. Request in. The client sends POST /events with an idempotency key. The gateway checks the auth token and the per-user rate limit.
  2. Write the source of truth. The event service checks Asha's ACL on the calendar, validates the RRULE and time zone, and in one transaction writes the event row, attendee rows, and a row in the change log / outbox table.
  3. Publish the change. A CDC connector (or outbox relay) reads the committed change and publishes it to the Kafka topic event-changes, keyed by event_id so all changes to one event stay in order.
  4. Fan out invites. A consumer adds the event to each attendee's calendar view (and sends invite emails for external guests). The organizer's copy stays the source of truth.
  5. Expand recurrences. Another consumer runs the recurrence engine and writes the next ~12 months of occurrences into the instance index, then invalidates the cached week views of every affected calendar.
  6. Schedule the next reminder. The reminder scheduler computes only the next occurrence's fire time (start minus 10 minutes, in UTC) and inserts one row per attendee into the right minute bucket of reminders_due.
  7. Fire. At 09:50 next Tuesday, ticker workers read that minute's bucket, hand each reminder to the notification service (see Notification System), and schedule the following week's reminder.
  8. Edits race with timers. Each reminder row carries the event's SEQUENCE. At fire time the worker compares it with the current value, so a reminder for an old version of the event is silently dropped.

Steps 2-3 in plain words. CDC (change data capture) tails the database's write-ahead log and publishes each committed row change to Kafka. The outbox pattern writes the event into an outbox table in the same DB transaction as the event row, and a small relay publishes it. Either way, the database and Kafka can never disagree about whether a change happened.

From your world

The outbox plus CDC step is the same trick as writing to a journal before applying a change in a file system. The database commit is the single point of truth, and every downstream view (instances, reminders, devices) is rebuilt from that log, like a routing table being recomputed from the link-state database.
