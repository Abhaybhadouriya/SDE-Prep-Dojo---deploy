1. Snapshot first, then stream - and the handoff in between

The log only holds recent changes (binlogs are purged after days). A new consumer needs all existing rows first. The classic Debezium initial snapshot does SELECT * on each table (emitting op: "r" events), records the log position from when it started, then streams from that position. The trouble: a full snapshot of a 2 TB table takes hours, and the older approach needed locks or a long-running consistent read.

The better way is the incremental, watermark-based snapshot, published by Netflix as DBLog and adopted by Debezium. The connector keeps streaming the log, and in between it reads the table in small primary-key chunks. Around each chunk it writes a low watermark and a high watermark into a signal table, so those markers appear in the log too. Any row that also shows up as a live log event between the two watermarks is dropped from the chunk, because the log event is newer. No locks, and you can snapshot one table any time.

-- Ask Debezium for an incremental snapshot of one table (signal table configured
-- with signal.data.collection=public.debezium_signal; the table is created, granted and
-- added to the publication in the Postgres setup tab further down)
INSERT INTO debezium_signal (id, type, data)
VALUES ('resnap-orders-2026-11-23', 'execute-snapshot',
        '{"data-collections": ["public.orders"], "type": "incremental"}');

2. Ordering, keys and deletes

Kafka orders records only inside a partition. Debezium uses the primary key as the record key, so every change to row 1042 goes to the same partition and arrives in commit order. That is enough for most sinks, because they apply changes per row. What you do not get for free:

  • Cross-row / cross-table order. An order row and its order_items rows are in different topics. A consumer may see items before the order. Fix: make the sink tolerant (upsert, allow "orphan" items briefly), or use the outbox pattern to publish one business event per transaction.
  • Primary-key changes. If someone updates the PK, Debezium emits a delete for the old key (plus tombstone) and a create for the new key - two partitions, so there is a moment where both or neither exist downstream.
  • Partition count changes. Adding partitions changes hash(key) mod N, so new changes for row 1042 may land on a different partition than old ones. Pick partition counts up front for CDC topics.

Dual write vs outbox, in one picture

The cross-table fix above deserves a picture, because it is the question interviewers ask most. A dual write means the application writes to two systems (the database and Kafka) in two separate steps. There is no transaction across them, so a crash or a failed call between the steps leaves them disagreeing - in either order.

You might confuse this with...

  • Polling vs CDC vs outbox: polling = a job runs SELECT ... WHERE updated_at > ? on a timer (misses deletes, adds DB load, minutes of delay); CDC = read the database's own change log (every insert, update and delete, in commit order); outbox = what you write (a deliberate event row in the same transaction), usually relayed by CDC. Outbox and CDC work together; they are not rivals.
  • Raw-table CDC vs outbox events: raw-table CDC publishes your internal columns as they are (great for analytics, fragile as a contract); outbox events are designed, versioned business events (best for service-to-service).
  • At-least-once vs effectively-once: CDC delivers each change at least once (after a crash some are re-sent). "Effectively once" is what you get when the consumer is idempotent - upsert by key, or dedup by event id - so duplicates change nothing.

Deletes become a delete event plus a tombstone (key, null value). On a compacted topic the tombstone tells the log cleaner "forget this key" after delete.retention.ms (default 1 day), so a consumer rebuilding from scratch never sees the deleted row.

3. The replication slot that ate the disk

Postgres keeps WAL until every replication slot has confirmed it. If the Debezium connector stops (crashed, paused, misconfigured) the slot stays, and the primary keeps every WAL segment from that moment on. Hours later the database disk fills and production writes stop. This is one of the most common CDC outages reported by teams running Debezium on Postgres.

$ psql -c "SELECT slot_name, active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
    FROM pg_replication_slots;"
    slot_name     | active | retained_wal
------------------+--------+--------------
 debezium_shop    | f      | 187 GB
(1 row)

Defences: (a) alert on retained WAL per slot and on connector state, (b) set max_slot_wal_keep_size (Postgres 13+) so Postgres invalidates the slot instead of dying - you then re-snapshot, which is far better than an outage, (c) set Debezium heartbeat.interval.ms so a slot on a quiet database still advances, (d) drop slots of retired connectors. MySQL has the mirror-image risk: the binlog is purged on a timer (binlog_expire_logs_seconds) whether or not you have read it, so a connector down longer than that loses its position and must re-snapshot.

From your world

The slot is a receive window that never closes: the sender (Postgres) must buffer everything the slowest receiver has not acknowledged. A dead receiver with no timeout means unbounded buffer growth - the same reason TCP has keepalives and BFD has dead intervals. max_slot_wal_keep_size is your "drop the session after N bytes of unacked data" knob. Where it breaks: when TCP drops a session, the peer just reconnects and resends. When Postgres invalidates a slot, the WAL it needed is gone for good, so the connector cannot resume - it must take a fresh snapshot of every table.

4. Schema changes without breaking consumers

Someone runs ALTER TABLE orders ADD COLUMN gift_wrap BOOLEAN. Debezium sees the new column and registers a new schema version. With Avro or Protobuf plus Schema Registry in BACKWARD compatibility mode, adding an optional column with a default is allowed; old consumers just ignore it. Be precise about what each mode rejects: under BACKWARD (new schema must read old data) you may delete fields and add fields that have defaults, and only adding a field without a default is rejected; under FORWARD or FULL, deleting a field without a default is rejected. Changing a type incompatibly is rejected in every mode. A rejection makes the connector fail loudly instead of silently breaking ten downstream teams - but note what BACKWARD lets through: a rename registers as "delete old + add new", and because Debezium maps nullable columns to optional fields with default null, the registry usually accepts it. Old consumers then silently see the old field disappear (null). Use FULL / FULL_TRANSITIVE, or a contract layer such as the outbox, when consumers must not break. Iceberg supports adding and renaming columns as metadata-only changes, so the lake can evolve too.

The cultural fix matters as much: raw table CDC exposes your internal schema as a public contract. If the orders team renames a column, every consumer breaks. That is the main argument for the outbox pattern for service-to-service events: publish a deliberate, versioned business event, and keep raw table CDC for analytics.

5. Upserts in the lake: copy-on-write vs merge-on-read

Object storage files are immutable. Updating one row in a 512 MB Parquet file means either rewriting that file (copy-on-write: slow writes, fast reads) or writing a small delete file that says "row 1042 in file X is gone" plus the new row in a new file (merge-on-read: fast writes, reads merge on the fly). CDC streams are update-heavy, so merge-on-read is the usual choice for freshness, with a scheduled compaction job that rewrites small files and folds delete files back in.

-- Flink SQL: upsert CDC rows into an Iceberg v2 table
CREATE TABLE lake.orders (
  id BIGINT, status STRING, total_paise BIGINT, updated_at TIMESTAMP(3),
  PRIMARY KEY (id) NOT ENFORCED
) WITH ('format-version' = '2', 'write.upsert.enabled' = 'true');

-- Spark: nightly maintenance so small files do not pile up
CALL lake.system.rewrite_data_files(table => 'db.orders');
CALL lake.system.expire_snapshots(table => 'db.orders', older_than => TIMESTAMP '2026-11-16 00:00:00');

6. Delivery guarantees, said precisely

Treat the change stream as at-least-once: after a crash the connector replays from its last saved position, so some events appear twice. Kafka Connect added exactly-once support for source connectors (KIP-618, Kafka 3.3), but whether a connector supports it depends on the connector and version, so check before you promise it. Kafka transactions also stop at Kafka's edge - they do not cover writes into Elasticsearch or S3 (see Delivery Semantics). So the honest design is: at-least-once transport + idempotent sinks. Upsert by primary key, and ignore an event whose source position (LSN or binlog position) is older than what the sink already applied. That gives effectively-once results.

"CDC is at-least-once. I make every sink idempotent: upsert by primary key and drop events whose source LSN is not newer than the stored one. That turns duplicates and replays into no-ops." This one sentence answers half the follow-ups.
