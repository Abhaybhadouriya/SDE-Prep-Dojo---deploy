Quick quiz

What does a log-based CDC tool like Debezium read?

  1. The tables, with SELECT every minute
  2. The application's HTTP requests
  3. The database's transaction log (binlog / WAL)
It tails the log the database already writes for crash recovery and replication, so it sees every committed change, including deletes.

Why is the primary key used as the Kafka record key?

  1. All changes to one row go to one partition and stay in order
  2. It makes messages smaller
  3. Kafka requires numeric keys
Same key → same partition → ordered. An update then delete is never applied backwards.

A Debezium Postgres connector has been stopped for a day. What is the main risk?

  1. WAL retained by the replication slot fills the primary's disk
  2. Kafka deletes the topic
  3. The tables get locked
Postgres keeps WAL until the slot confirms it. Alert on retained WAL and set max_slot_wal_keep_size.

What is a tombstone in a CDC topic?

  1. An event marking a dropped table
  2. A record with the deleted row's key and a null value
  3. A corrupted message
After a delete event, the tombstone lets log compaction remove the key entirely.

The connector crashes and restarts. What does a sink see?

  1. A gap: some changes are lost
  2. Exactly the same events, never repeated
  3. Some events repeated, because it resumes from the last saved position
Offsets are saved periodically, so the window since the last save is replayed: at-least-once. Sinks must be idempotent.

How does an incremental (watermark) snapshot avoid overwriting newer data with an old snapshot row?

  1. It locks the table while reading
  2. It reads only from a backup
  3. It drops chunk rows that also changed in the log between the low and high watermarks
That is the DBLog technique: log events in the window win over the chunk's copy.

Which lake write mode suits an update-heavy CDC stream best?

  1. Merge-on-read with scheduled compaction
  2. Copy-on-write with no compaction
  3. Append-only with no updates
Merge-on-read makes writes cheap (small delete files); compaction keeps reads fast later.

The orders service must publish "OrderPlaced" to other services reliably. Best approach?

  1. Write DB, then publish to Kafka in the same method
  2. Outbox table in the same transaction, relayed by Debezium
  3. Poll the orders table every minute
One atomic DB transaction, then the log-based relay publishes it. No dual-write gap, and a clean event contract.
