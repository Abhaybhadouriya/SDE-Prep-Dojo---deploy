Data model

There are four "places" data lives in this design. Name each, say its key, and say why that store.

WhereShapeKeyWhy this choice
Source DB (MySQL/Postgres)Normal OLTP tablesPrimary keySource of truth. We only read its log.
Kafka change topicOne topic per table, e.g. shop.public.ordersPrimary key → partitionSame row → same partition → ordered. Retention 7 days, or cleanup.policy=compact for a "latest row per key" topic.
Connect internal topicsconnect-configs, connect-offsets, connect-statusConnector nameWhere the connector remembers its binlog position / LSN. This is the "bookmark".
Lakehouse table (Iceberg)Columnar Parquet files + snapshot metadataPrimary key (for upserts), partitioned by dayCheap object storage, SQL with Trino/Spark, time travel, upserts with format v2.
Search index / cacheDocuments / key-valuePrimary key = document id / cache keyUpsert by id makes duplicates harmless (idempotent).

SQL vs NoSQL here? The question flips: the sources are SQL (we do not choose them), the stream is Kafka, and the analytic store is a lakehouse table format (Apache Iceberg, Apache Hudi or Delta Lake) on object storage. Say: "I pick Iceberg because it gives ACID snapshots and row-level upserts on cheap S3-style storage and is readable by Trino, Spark and Flink; the cost is file maintenance (compaction, snapshot expiry)."
