Architecture: follow one change

Click Next or Play to follow one UPDATE orders SET status='SHIPPED' from the database to every consumer.

  1. Commit. The order service runs a normal transaction. MySQL appends the row change to the binlog (Postgres to the WAL) before it acknowledges the commit. The app knows nothing about CDC.
  2. Read the log. The Debezium connector, running as a task inside a Kafka Connect worker pod, is connected like a replica (MySQL replication protocol; Postgres logical replication slot with pgoutput). It receives the committed change and builds the before/after envelope.
  3. Publish. The Connect worker's Kafka producer writes the event to topic shop.public.orders, key = primary key, schema registered in Schema Registry. Periodically it saves the log position (binlog file+pos / GTID, or Postgres LSN) to connect-offsets.
  4. Lake path. A Flink job (consumer group lake-orders) reads the topic, drops duplicates, masks PII, and upserts rows into an Iceberg table. It commits a new Iceberg snapshot on each checkpoint (say every 5 minutes).
  5. Online paths. Other consumer groups read the same events independently: an Elasticsearch sink upserts the document by id; a small cache invalidator deletes order:1042 from Redis so the next read reloads it.
  6. Query. Analysts query the Iceberg table with Trino or Spark - data minutes old instead of a day old. Each consumer group has its own offset, so a slow lake never slows the cache.
  7. Failure. If the connector pod dies, Connect restarts the task on another worker; it resumes from the last saved position. Changes since that save are sent again - which is why every sink must be idempotent.

From your world

Debezium connecting "like a replica" is the same trick as a route reflector client or a monitoring station on a BGP session: it speaks the protocol the system already uses for replication, so the source needs no new code. The saved LSN in connect-offsets is a sequence number checkpoint - on reconnect you say "send me everything after sequence N", like resuming a sliding window after a link flap. Where it breaks: the checkpoint is saved periodically, not per event, so a restart replays a small window - duplicates, not gaps.
