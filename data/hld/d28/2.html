Back-of-envelope estimation

These are interview assumptions, not facts about any company. Write each step on the board. (Method refresher: Back-of-Envelope Estimation.)

  1. Change rate. 64 MySQL shards x ~700 row changes/s each ≈ 45k/s, plus Postgres ≈ 5k/s. Total ~50k changes/s average. Rule of thumb for sale days: 3x, so ~150k/s peak.
  2. Event size. A CDC event carries the before and after row plus source metadata (file/position, transaction id, timestamp). Assume a 300-byte row: with Avro (schema stored once in the registry, not in every message) the event is ~1 KB; as plain JSON with an embedded schema it can be several KB. We plan with 1 KB.
  3. Bandwidth. 50k x 1 KB = 50 MB/s average, 150 MB/s peak, into Kafka.
  4. Per day. 50 MB/s x 86,400 s ≈ 50 MB x 100,000 = ~4.3 TB/day raw. With lz4/zstd batch compression assume 3x (rule of thumb) → ~1.4 TB/day on disk.
  5. Kafka storage. Change topics keep 7 days (the Kafka default) so a sink can be rebuilt after a week-long bug: 1.4 TB x 7 x RF 3 ≈ ~30 TB across brokers. Compacted "latest row" topics are smaller - they hold one record per primary key.
  6. Partitions. Big tables (orders, order_items) get 12-24 partitions so sinks can parallelise; small tables get 1-3. Key = primary key keeps per-row order.
  7. Connectors. A Debezium MySQL or Postgres connector reads one database log with one task (a log is a single sequential stream). So we need ~74 connectors: one per shard/database. If one Connect worker pod comfortably runs ~8-12 connectors (assumption - measure it), that is ~8 worker pods plus headroom. Shopify reported ~150 connectors on 12 Connect pods.
  8. Lake files. If the Flink job commits to Iceberg every 5 minutes, each table partition gets 288 commits/day. Without compaction, 100 tables x 288 commits x a few files = tens of thousands of small files per day. That is why compaction is in the design from day one.

Say the conclusion out loud: "This is not a throughput problem - one Kafka cluster handles 150 MB/s easily. It is a correctness and operations problem: never lose a change, keep per-row order, survive schema changes, and never let the pipeline hurt the source database." That sentence steers the interview to the interesting deep dives.
