60-second answer, said out loud: "A feed handler normalises the exchange feed into Kafka keyed by symbol. Subscriptions are stored in a database and also published, via an outbox, to an alert-changes topic with the same key and partition count. Evaluators in one consumer group each own a set of symbols and keep everything in memory: per symbol, an UP book and a DOWN book of absolute triggers sorted by price - 5% from close and deltas are converted to prices - and for rolling windows, a shared min/max per symbol and window size using monotonic deques over multi-resolution bars, with subscribers sorted by percent. A tick pops only the rules it fires; no database on the hot path. Fired rules are removed, marked FIRED with a conditional update for idempotency, and sent to a fired topic keyed by user for the notification service, which is scaled for crash-day bursts. Expiry is a heap plus a nightly sweep. On a crash, a new owner reloads rules from a snapshot plus changes, rebuilds windows from Kafka and bars, and duplicates are absorbed by the fire guard."

SDE-1 stops here / SDE-2 adds. SDE-1: Kafka keyed by symbol, subscriptions in a DB, a separate evaluator that keeps rules in memory, notifications through a queue, remove on fire. SDE-2 adds: converting rules to sorted price triggers, co-partitioning ticks and rule changes, monotonic deques and bars for windows, the conditional-update fire guard, snapshot-plus-replay recovery with checkpointed offsets, hot-symbol handling and the crash-day burst maths.

You might confuse this with Price Tracker & Alerts (shop prices). There prices change rarely and you must go and fetch them, so a database range query per change is fine. Here prices arrive every second by push, so the rules must be in memory. Same idea, opposite rate.

Follow-up questions

Your design queries the subscriptions DB on every tick. What is wrong, and how do you fix it?

10K ticks per second become 10K queries per second that almost always return nothing, all day, and latency depends on the database. Fix: a separate threshold-evaluation service consumes ticks and holds rules in memory per symbol (sorted triggers), so a tick costs a couple of comparisons. Only crossings leave the service. The DB is the durable copy, read on startup and rebuild.

How to answer

Do the arithmetic first, then the fix, then how memory is kept in sync (co-partitioned change topic).

Likely follow-ups
  • How does a new subscription reach the right evaluator? (Outbox event keyed by symbol to a co-partitioned topic.)
  • Could Redis hold the rules instead? (Yes, sorted sets per symbol, but it adds a network hop per tick; local memory is faster.)
Support "moved X% within a rolling window" from one minute to one year.

Fix the window menu. Per symbol per window size keep rolling min and max with monotonic deques over the right resolution: seconds for short windows, minute, hour and day bars for longer ones. Move up = (P - min) / min, move down = (max - P) / max. Per (symbol, window, direction), subscribers are sorted by percent; pop all with percent <= move. State is shared by all users, so it is small.

How to answer

Define the move precisely first (vs min for up, vs max for down), then the data structure, then memory per year-window.

Likely follow-ups
  • Why not recompute min over a year on every tick? (6M points per symbol per tick.)
  • Arbitrary window lengths? (Round to the nearest supported size, or use a segment tree over bars.)
How do you guarantee an alert fires only once, even after a crash?

In memory, a fired rule is removed. Across crashes, replayed ticks may re-fire it, so the evaluator does a conditional update (status ACTIVE to FIRED) and only publishes if it changed a row; the notifier also de-dupes by alert id. At-least-once processing plus idempotent effects.

How to answer

Name the duplicate source (replay after crash), then the guard. Avoid promising "exactly-once" without saying how.

Likely follow-ups
  • The update succeeds but the publish fails? (Write an outbox row in the same transaction; a relay publishes it.)
An evaluator dies at market open. Walk me through recovery.

The consumer group reassigns its partitions. The new owner loads active rules for those symbols from the DB snapshot, then replays alert-changes after the snapshot's position. Window state comes from the last checkpoint, or is rebuilt from bars in the time-series DB plus replayed recent ticks. It resumes from the last committed tick offset (committed only after checkpoint). Duplicates are absorbed by the fire guard. For the hottest symbols a warm standby cuts recovery to seconds.

How to answer

Separate durable rules from derived window state, and say where each comes back from.

Likely follow-ups
  • How long does it take? (Load about 500 MB of rules plus bars: seconds to tens of seconds.)
One symbol is very hot. What breaks?

Three kinds of hot: many rules (tick cost stays O(log n); the fan-out on a big move is the issue, so emit in chunks and scale notifiers on lag), many ticks (coalesce to the latest price every 100 ms), and a hot partition (custom partitioner to isolate the few biggest symbols). If one symbol's rules exceed one machine's memory, split its books by price range across evaluators and broadcast its ticks to them.

How to answer

Ask "hot in what?" then answer each kind.

Likely follow-ups
  • What is your partition count? (Enough for future evaluators, say 64 to 128; symbols are few, so assignment is cheap.)
What do you store in the time-series database, and why?

Raw ticks (about 5 GB a day for 10K symbols) and 1-minute, 1-hour and daily bars with open, high, low, close. Used for user charts, for rebuilding long rolling windows after a crash, and for audits ("why did my alert fire?"). It is off the hot path: a separate consumer writes it.

How to answer

Give the size and the three readers.

Likely follow-ups
  • Which TSDB? (TimescaleDB if the team knows Postgres; ClickHouse for heavy analytics; kdb+ is common in finance.)
Show the DB schema and the message queues.

One alert table with type, direction, percent, window, base price, status and expiry, indexed by symbol for active rows (rebuild only) and by user (listing). Topics: ticks and alert-changes co-partitioned by symbol; alerts-fired keyed by user. The outbox ties the DB and alert-changes together.

How to answer

For each index and topic key, say which reader needs it.

Likely follow-ups
  • Why key fired alerts by user? (Per-user ordering, collapsing several alerts into one push, per-user rate limits.)
How do you remove subscriptions idle for a month?

Each rule has expires_at. Evaluators keep a min-heap by expiry and remove expired rules every minute, marking them EXPIRED in a batch; a nightly DB sweep catches stragglers (or a TTL attribute in DynamoDB). The user is optionally told "your alert expired".

How to answer

Cover memory and DB both; do not rely on one cron alone.

Likely follow-ups
  • Does a renewal extend it? (Yes: update expires_at and emit a change event.)
The interviewer jumps to deep dives before you finish the basic design. What do you do?

Spend the first ten minutes getting the six boxes on the board (feed, Kafka, subscription service + DB, evaluator, fired topic, notifier), then follow the interviewer. One Uber report says a strict "simple first, deep later" plan backfired; another says the HLD was the most important round. Have the deep dives ready as small, self-contained explanations you can start at any point.

How to answer

This is about process: show you can adapt while keeping a coherent picture.

Likely follow-ups
  • Which deep dive would you pick yourself? (DB-per-tick vs in-memory, then rolling windows.)

Scenario drills

Scenario: Nifty falls 6% at 09:20

Within five minutes, 12M alerts fire. Push notifications are arriving 15 minutes late.
Weak answer: "Add evaluators."
Strong answer: evaluators are fine; alerts-fired lag shows the bottleneck is notification. Scale notifiers on lag up to the push provider's limits, collapse multiple alerts per user into one message, send push before SMS and email, and pre-scale before market open on volatile days. Include the trigger price and time in each message so late alerts are still honest.
Follow-ups
  • What SLO do you alert on? (p99 tick-to-push, measured with timestamps carried in the events.)

Scenario: a fat-finger tick

The feed reports one tick of 12.40 for a stock trading near 1,240. Thousands of "down 5%" alerts fire.
Weak answer: "That is what the exchange sent."
Strong answer: add a validation stage in the feed handler: reject ticks outside the exchange's price band or more than N% from the last price unless confirmed by the next tick. Window rules use validated prices only. Offer a correction notice for alerts already sent.
Follow-ups
  • How do you avoid blocking a real crash? (Confirm with the next tick or a second vendor; delay of one second is acceptable.)

Common mistakes

  • Hitting the database on every tick.
  • Keeping a separate window per user instead of per symbol and window size.
  • Recomputing min/max over the full window each tick.
  • Partitioning rule changes differently from ticks, so the evaluator never sees new rules in order.
  • Claiming exactly-once without a fire guard.
  • Sizing for average alerts instead of the crash-day burst.
  • Spending 20 minutes on requirements while the interviewer wants deep dives.
