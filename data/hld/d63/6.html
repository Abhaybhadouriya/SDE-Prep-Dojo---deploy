Deep dives

1. Turn every rule into a price, then sort

The key trick: most rules are an absolute price trigger in disguise.

  • 5% down from close: trigger = close x 0.95. Close is fixed for the whole day, so the trigger is a constant. Recompute all FROM_CLOSE triggers once at the start of each trading day, and re-base them after a split, bonus or other corporate action adjusts the reference price (a 2:1 split halves the close, which would otherwise fire every "down 5%" rule at the open).
  • Delta 2% from my price: trigger up = base x 1.02, trigger down = base x 0.98. Constant from creation.

Per symbol, keep two sorted books: UP rules sorted by trigger ascending, DOWN rules sorted by trigger descending. On a tick with price P, pop from the front of UP while trigger <= P, and from the front of DOWN while trigger >= P. Each pop is a fired rule. A tick that fires nothing costs two comparisons with the book heads. Inserts and cancels are O(log n) in a balanced tree, skip list or a heap with lazy deletion.

Alternative: price buckets. A second pattern, closer to the fix described in one 2026-05 report: a lightweight movement detector per symbol emits an event only when the move from close crosses a 1% step (-1%, -2%, ...). A subscriber-lookup service then reads subscriptions for (symbol, direction, bucket) from a cache or DB. The DB is hit only on crossings, a few times per symbol per day, not on every tick. It is simpler to operate but coarser (rules must use whole-percent steps or be re-checked) and adds a lookup on the alert path. Present the sorted books as the main design and buckets as the simpler option.

2. Rolling windows: "up 3% within the last hour"

"Moved X% within window W" means: compared with the lowest price in the last W, the current price is up X% (or, for down, compared with the highest, it is down X%). So per symbol per window size we need the rolling min and max, updated every second.

  • Monotonic deque (the sliding-window-maximum trick from DSA): keep a deque of (time, price) where prices are increasing for the min deque. On each tick, pop from the back while the back's price >= new price, push the new one, pop from the front while it is older than W. The front is the window minimum. Amortised O(1) per tick. A mirror deque gives the maximum.
  • Long windows use bars. A 1-year window at 1-second resolution is 6M points per symbol: too much. Use the right resolution per window: seconds for 1 minute and 5 minutes, 1-minute bars (min and max of each minute) for 1 hour and 1 day, 1-hour bars for a week and month, daily bars for a year. A year is then about 250 trading days of daily bars, plus today's live partial bar.
  • Share state across users. The window state is per (symbol, window size), not per user. 10K symbols x 7 window sizes = 70K window objects, each small.
  • Thresholds per window: for each (symbol, window, direction) keep subscribers sorted by percent. On each tick compute the current move m = (P - min) / min. Every UP rule with percent <= m fires: again pop from the front of a sorted list.

From your world

Multi-resolution bars are what RRDtool and SNMP counters on routers do: keep fine samples for the recent past and coarse averages (here min and max) for long history, so memory stays fixed however long the window.

3. Fire once, and the one-month expiry

  • In memory: popping a rule removes it, so the same evaluator cannot fire it twice.
  • After a crash an evaluator may replay ticks it already processed and fire again. The guard is the database: UPDATE alert SET status='FIRED' WHERE alert_id=? AND status='ACTIVE'. If zero rows change, the alert was already fired; drop the event. On a crash day that is 25K single-row writes per second at the worst moment, so batch the claims: every 50-100 ms run UPDATE alert SET status='FIRED' WHERE alert_id = ANY(:ids) AND status='ACTIVE' RETURNING alert_id and notify only the ids it returns (or claim in Redis with SET NX and persist asynchronously). The notification service also de-duplicates by alert_id. Together: at-least-once processing, effectively-once delivery.
  • Expiry: keep a min-heap of expires_at per evaluator; every minute pop expired rules from memory and mark them EXPIRED in a batch. A nightly sweep in the database catches anything missed. With DynamoDB, a TTL attribute can delete expired rows.
  • Should it re-arm? The spec says remove after firing. If the interviewer changes it to "notify every time", add a cooldown and hysteresis (re-arm only after the price moves back by a margin) so a price wobbling around 242.25 does not send 30 pushes.

4. Worker failure and state recovery

An evaluator holds two kinds of state: rules (durable in the DB and in alert-changes) and window state (derived from ticks). Recovery for a partition it takes over:

  1. Rules Load a snapshot of active alerts for its symbols (the alert_active_by_symbol index), recording the snapshot's position in alert-changes; then replay changes after that position. A compacted Kafka topic keyed by alert_id is an alternative snapshot source.
  2. Windows Short windows (minutes) rebuild by replaying recent ticks from Kafka. Long windows rebuild from 1-minute and daily bars in the time-series DB. Or checkpoint the whole in-memory state periodically (Flink and Kafka Streams do this with RocksDB state plus checkpoints) and restore the latest checkpoint.
  3. Offsets Commit tick offsets only after the state for them is checkpointed, so a restart re-processes a small, bounded slice. Duplicates are absorbed by the fire-once guard.
  4. Speed Keep a warm standby (a second consumer that follows the same partitions but does not emit) for the busiest symbols if a minute of downtime at market open is unacceptable.

Ordering trap: a subscription created at 10:00:00.500 must not be evaluated against a tick from 09:59:59. Because ticks and changes for a symbol go to the same evaluator, it can apply the change before processing ticks with a later timestamp. A DELTA rule also takes its base_price from the server's latest price at creation, not from the client.

5. Hot symbols and the crash-day burst

  • Hot by rules: TSLA may have 2M subscriptions. Tick cost is still O(log n). The pain is a big move firing 500K at once: emit fired events in chunks, and let the notification side scale on lag.
  • Hot by ticks: if the feed sends every trade (not one per second), a busy symbol may get thousands of ticks per second. Coalesce: evaluate on the latest price every 100 ms per symbol; nobody needs an alert faster than that.
  • Hot by partition: Kafka assigns symbols to partitions by hash; check that the busiest few symbols are not on the same partition, and give very hot symbols their own partition through a custom partitioner.
  • Crash day: 15M alerts in minutes. Kafka absorbs the burst. Push first (high provider limits), SMS and email after; collapse many alerts for one user into one message ("6 of your alerts fired"). Shed or delay nothing paid; delay low-priority channels.
