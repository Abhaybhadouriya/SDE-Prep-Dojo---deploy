Our pick: B, counter + base62, with range leasing. It never collides and needs no read before write.

If guessability matters (people scanning sho.rt/1000001, 1000002... to find private documents): scramble the number with a reversible one-to-one function before encoding. Unique number in, unique code out, and the codes no longer look sequential.

M, K = 62**7, 1_000_003            # K shares no factor with M (see below)
scr  = (n * K) % M                  # scramble before base62 encoding
orig = (scr * pow(K, -1, M)) % M    # unscramble: pow(K, -1, M) is K's modular inverse
$ python -c "M,K=62**7,1_000_003; n=56800235585; s=(n*K)%M; print(s, (s*pow(K,-1,M))%M, ((n+1)*K)%M)"
284002177923 56800235585 284003177926
# n and n+1 now land far apart; unscrambling gives back the original n.
Maths for the curious (SDE-2, optional)
  • The scramble is a bijection (every input has exactly one output and vice versa) only when K is coprime to 627, meaning gcd(K, 627) = 1. Since 627 = 27 × 317, K must be odd and not divisible by 31.
  • A K that shares a factor (for example 31 × 1,000,003) is not reversible: two inputs can map to the same code. Always check the gcd.
  • Multiplying is easy to undo if someone guesses K. A stronger option is a small keyed Feistel cipher: split the number into two halves and mix them over a few rounds with a secret key. It is reversible by design. If an output falls outside 0..627-1, run it through again (cycle-walking) until it lands inside.

The base62 encoder is just "repeated divide by 62", the same as printing a number in hex, but with 62 digits:

# b62.py
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def encode(n: int) -> str:
    if n == 0:
        return ALPHABET[0]
    out = []
    while n:
        n, r = divmod(n, 62)
        out.append(ALPHABET[r])
    return "".join(reversed(out))

def decode(s: str) -> int:
    n = 0
    for ch in s:
        n = n * 62 + ALPHABET.index(ch)
    return n

if __name__ == "__main__":
    start = 62**6            # first 7-character number
    print("62^6 =", start, "->", encode(start))
    print("62^7 =", 62**7)
    for n in (125, start + 1, 3_000_000_000_000):
        code = encode(n)
        print(n, "->", code, "->", decode(code))

From your world

Base62 is just a number base, like hex. 125 in base 62 is "21" because 2 × 62 + 1 = 125, exactly like 0x21 = 2 × 16 + 1 = 33. Starting the counter at 626 is the same trick as starting a counter at 0x100000 so every value prints with the same width. Where it breaks: hex digits are case-insensitive (0xAB = 0xab), but base62 needs case, so aZ3 and AZ3 are different codes. Anything that lowercases the URL path (some email clients, some proxies) silently breaks a base62 link; base36 (0-9, a-z) avoids that at the cost of slightly longer codes.

Deep dive 2: many servers, one counter (must know)

A single global counter (one Redis INCR or one database sequence) works, but it is a single point of failure and a network call per link. The fix is range leasing: each write pod asks for a block of 1,000 IDs at a time and hands them out from memory.

  • At 3,500 writes/s peak and 1,000 IDs per block, the range service sees only ~3.5 requests per second. Tiny.
  • The range service stores one row, for example next_free = 56,800,240,584 (it was seeded at 626 = 56,800,235,584 and has handed out five blocks so far). The range service starts at 626 for the same reason tiny.py does: every number from there on encodes to exactly 7 base62 characters. It does an atomic "read and add 1,000" (a database row update in a transaction, Redis INCRBY ids 1000, or a ZooKeeper/etcd compare-and-set).
  • If a pod crashes, its unused IDs are simply lost. With 3.5 trillion codes, wasting a few thousand is fine.
  • If the range service is down, pods keep working until their current block runs out. Make blocks bigger (10,000) to buy more time.
  • Alternative: a Snowflake-style ID (time + machine ID + sequence) needs no central service at all. The catch: a 64-bit Snowflake value is larger, so the base62 code becomes about 11 characters. That is fine if the interviewer accepts longer codes.
$ redis-cli SET ids:next 56800235584      # seed once at 62^6, so every code is 7 chars

From your world

This is exactly how a label manager hands label blocks to line cards, or a DHCP server gives a relay a pool: allocate in big chunks centrally, then hand out single values locally with no coordination. Where it breaks: unlike labels, short codes are never returned to the pool, so a lost block is gone for good (and we do not care).

Deep dive 3: caching and the viral link (good to know)

  • Cache-aside: read pod checks Redis; on a miss reads the store and fills Redis. Since a mapping never changes, staleness is not an issue, except after a delete or disable: then delete the Redis key too (and purge the CDN).
  • TTL: put a TTL (say 24 h) on every cache entry so cold links drop out. Use LRU eviction (maxmemory-policy allkeys-lru; the Redis default is noeviction, which would start rejecting writes when memory is full).
  • Hot key: a link shared by a celebrity can get a huge spike that all lands on one Redis shard. Fixes: a tiny in-process cache in each read pod (a few seconds TTL), and the CDN caching the 302 for a few seconds.
  • Cache stampede: when a hot key expires, thousands of requests miss at once and hit the store. Fix with request coalescing (one pod-level lock per key: only one request goes to the store, the rest wait for its answer) and jittered TTLs.
  • Cache penetration: bots request random codes that do not exist, so every request misses. Cache the "not found" answer for a short time, or keep a Bloom filter of all valid codes.

What is a Bloom filter? A bit array plus k hash functions. To add a code, set the k bits it hashes to. To check a code, test those k bits: if any bit is 0 the answer is "definitely not present"; if all are 1 it is "maybe present" (other codes may have set those bits). It never gives a false "no", gives a false "maybe" about 1% of the time, and needs only about 10 bits per item, so 1 billion codes fit in about 1.2 GB of RAM. A "maybe" simply falls through to the normal cache/store lookup, so false positives cost a little load, never a wrong answer. (You cannot delete from a plain Bloom filter; rebuild it nightly or use a counting variant.)

Deep dive 4: counting clicks without slowing redirects (SDE-2)

A naive design does UPDATE urls SET clicks = clicks + 1 on every redirect. At 116k reads/s that turns a read-heavy system into a write-heavy one, and one viral link becomes a hot row lock. Instead, the read pod publishes a click event to Kafka and forgets it. A consumer group aggregates counts in memory per minute and writes one row per (code, minute) to an analytics store. This is the counting and aggregation pattern, and the same pipeline shape you build in the ShopStream pipeline.

Deep dive 5: custom aliases, expiry and abuse (good to know)

  • Custom alias: a conditional insert (INSERT ... ON CONFLICT DO NOTHING, or DynamoDB attribute_not_exists(code)). If zero rows inserted, return 409. Keep aliases in the same table so a custom alias can never clash with a generated code. To be extra safe, require aliases to contain a character the generator never produces in that position, or a minimum length of 8.
  • Expiry: check expires_at on every read (cheap, and correct even if cleanup is late). A daily cleanup job deletes or archives expired rows in small batches. DynamoDB and Cassandra both support a per-row TTL that does this for you.
  • Abuse: shorteners are used to hide phishing links. Check new URLs against a malware/phishing blocklist asynchronously, let users report links, and support "disable" (status = 1, return 410). Rate-limit creation per API key and per IP.
  • Same long URL twice? Decide: either always mint a new code (simple, lets per-campaign analytics differ) or look up (owner_id, md5(long_url)) first and return the existing code.
