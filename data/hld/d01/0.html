The story

Explain like I'm 5

Your friend lives at "House number 42, Blue Gate, Behind the Big Mango Tree, Near the Old Post Office, Green Valley Road". That is far too long to write on a birthday card. So the town post office gives you a tiny sticker: "G7". You write "G7" on the card. The postman looks up G7 in his big book, sees the long address, and walks there. The post office has only two jobs: when someone brings a long address, give out a new tiny sticker; when someone shows a sticker, look up the long address. Almost everybody is doing the second job. Lots of people read stickers; only a few make new ones.

A URL shortener (TinyURL, bit.ly, t.co on Twitter/X, amzn.to on Amazon) does exactly this for web links. You give it https://www.example.com/products/2026/winter-sale?campaign=diwali&ref=email and it gives you back https://sho.rt/aZ3kP9q. Anyone who clicks the short link is sent to the long one. The short part, aZ3kP9q, is called the code (or "key" or "alias").

Why is this such a popular interview question? Because it is small enough to finish in 45 minutes but touches almost every building block: an API, a database choice, a unique ID scheme, a cache, a read-heavy traffic pattern, a CDN, and (at SDE-2 level) an analytics pipeline with Kafka. If you can design this one well, you have a template for many others.

From your world

A short code is like a DNS name for a single URL, or a tiny NAT table entry: an external key (the code) maps to an internal address (the long URL), and the lookup must be fast because it sits on the data path of every click. The "allocate unique codes from many servers" problem is the same as handing out MPLS labels or DHCP leases from a pool without two routers giving out the same one. Where the analogy breaks: a NAT entry is short-lived; a short link may live for years, so this table is durable storage, not soft state.

Interviewers love this: they often use this question to check whether you start from the user and the numbers instead of jumping into internals. Open with two clarifying questions, write the requirements, then estimate. See the 45-minute framework.

New words, once each. p99 = the time that 99 out of 100 requests beat (the slowest 1% are slower). CDN (content delivery network) = many cache servers in cities near users that answer for us when they can. TTL (time to live) = how long a cached copy may be kept before it must be thrown away, like an ARP or route cache timer. Shard = one slice of the data; the full table is split across many machines and each row lives on exactly one of them. All of these are also in the site glossary.
