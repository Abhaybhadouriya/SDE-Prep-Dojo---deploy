Data model: one big lookup table

The heart of the system is a single mapping: code → long URL. Every redirect is "look up one row by its primary key". No joins, no range scans.

CREATE TABLE urls (
  code        VARCHAR(16)  PRIMARY KEY,      -- 7 chars normally; custom aliases can be longer
  long_url    TEXT         NOT NULL,
  owner_id    BIGINT,                        -- who created it (nullable for anonymous)
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
  expires_at  TIMESTAMPTZ,                   -- NULL = never
  status      SMALLINT     NOT NULL DEFAULT 0 -- 0 active, 1 disabled (abuse)
);
-- Optional: "same long URL from same owner returns the same code"
CREATE INDEX urls_owner_long ON urls (owner_id, md5(long_url));

SQL or NoSQL? Say it in one sentence

"The access pattern is a pure key lookup at very high read volume, with about 91 TB over 5 years and no joins, so a key-value store such as DynamoDB or Cassandra fits naturally. A sharded Postgres/MySQL with the code as the primary key also works and gives us a unique constraint for free." Both are acceptable answers. What matters is the reason. More on choosing: Data modeling and indexing.

Key-value / wide-column (DynamoDB, Cassandra)
  • Scales horizontally by design; partitioned by key.
  • Single-digit-ms key lookups.
  • Multi-region replication built in.
Watch out
  • "Insert only if the code is new" needs a conditional write (DynamoDB attribute_not_exists, Cassandra lightweight transaction, which is slower).
  • Fewer ad-hoc queries ("all links of user X" needs a second table or index).

From your world

Hashing the code to pick a shard is ECMP flow hashing: hash the 5-tuple, pick a path, and the same flow always lands on the same path. Consistent hashing is resilient ECMP hashing: when one next-hop dies, only its own flows move, not all of them. Where it breaks: a link can carry any flow at any moment, but a shard also stores data, so moving keys to a new shard means copying bytes (and serving reads during the copy), not just rehashing.
