Interview: how to drive the 45 minutes

  1. 0-5 min: requirements. Shorten, redirect, alias, expiry, analytics? Numbers: 100M/day, 100:1. Write them down.
  2. 5-10 min: estimation. ~1.2k writes/s, ~116k reads/s, 7 chars, ~91 TB. Say the conclusion: "read-heavy, sharded, cached".
  3. 10-15 min: API + data model. POST and GET, 302 with the reason, one table keyed by code.
  4. 15-25 min: high-level diagram. LB, write API, read API, cache, store, ID ranges. Walk one write and one click.
  5. 25-40 min: deep dives. Code generation (compare the three), range leasing, cache hot keys, analytics via Kafka.
  6. 40-45 min: wrap-up. Failure of each box, multi-region, what you would monitor (redirect p99, cache hit ratio, 5xx rate, consumer lag).

What a good SDE-1 answer shows

  • Clear requirements and correct maths.
  • A working design: API, table, base62 counter, cache.
  • Knows 301 vs 302 and why reads dominate.

What a good SDE-2 answer adds

  • Drives the session without prompts.
  • Compares hash vs counter vs KGS and defends a pick.
  • Range leasing, hot keys, async analytics, failure of each box, multi-region ID ranges.

Common mistakes: skipping estimation or doing it without a conclusion; "use MD5" with no collision plan; picking 6 characters without checking 626 against 5 years of links; writing click counts into the URL table on every redirect; one global INCR with no fallback; forgetting expiry and abuse; spending 15 minutes on database internals before the diagram exists.

The 60-second answer (say it out loud)

"It is a read-heavy key-value lookup: about 1,000 new links and 100,000 clicks per second. I give every new link a unique number from a counter, with each server leasing blocks of 1,000 numbers so there is no hot spot, and write the number in base62. Seven characters give 3.5 trillion codes, enough for years. I store code to URL in a sharded key-value store with replicas. Redirects go through a separate read service that checks Redis first and returns a 302, so we keep click analytics. Each click is published to Kafka and counted asynchronously, so analytics can never slow a redirect. Viral links are absorbed by a CDN and an in-process cache."

Design TinyURL. Where do you start?

With requirements and numbers, not boxes. "Shorten, redirect, optional alias and expiry; 100M new links a day; read:write about 100:1." That gives ~1.2k writes/s and ~116k reads/s, 7 base62 characters for 5 years, and ~91 TB of data. Then I state the design consequence: separate the read path, cache aggressively, shard the store.

How to answer

Ask 3-5 clarifying questions, write the numbers on the board, and end the estimation with one sentence that links the numbers to a design choice.

Likely follow-ups
  • Why 7 characters and not 6?
  • What if it were 1 billion new links a day?
How do you make sure two servers never generate the same code?

Make uniqueness come from the ID, not from luck. A central range service hands out disjoint blocks of 1,000 (the first block above 626 to pod A, the next to pod B) with an atomic operation such as Redis INCRBY or a transactional row update. Each pod encodes numbers from its own block, so two pods can never produce the same number. As a safety net the store insert is conditional ("only if the code does not exist"). Alternatively, Snowflake IDs put a machine ID inside every ID.

How to answer

Name the race first (two servers, same counter value), then the mechanism (disjoint ranges + atomic allocation), then the safety net (conditional insert).

Likely follow-ups
  • What happens to a block when a pod crashes?
  • What if the range service is down?
  • How does this work across two regions?
Why not just hash the long URL with MD5 and take 7 characters?

You can, but a 7-character slice of a hash can collide: two different URLs can produce the same prefix, and the chance grows as the table fills (the birthday effect). So every write needs a lookup ("is this code taken?") and a retry with a salt on collision. That is an extra read per write, and a race if two writers check at the same time, so you still need a conditional insert. The upside is that the same URL naturally gets the same code. A Bloom filter can make the "is it taken?" check cheap, but it is still more moving parts than a counter.

How to answer

Do not dismiss hashing. Give its one real advantage, its two costs, and say when you would still use it.

Likely follow-ups
  • How would a Bloom filter help here? What about false positives?
  • How would you make the same URL return the same code with a counter design?
301 or 302? Which would you return?

302 (or 307) if we need click analytics, expiry or the ability to change a target, because browsers do not cache it, so every click reaches us. 301 is cached by browsers, which cuts our load but means repeat clicks are invisible to us and a target can never really change. For a product with analytics, 302. For a pure internal shortener with no stats, 301 is reasonable.

How to answer

Give the trade-off (load vs visibility) and tie the choice to a requirement you wrote earlier.

Likely follow-ups
  • Can a CDN cache a 302? For how long, and what do you lose?
How would you count clicks at 100,000 per second?

Never on the redirect's critical path. The read service publishes a small event (code, timestamp, country) to a Kafka topic keyed by code and returns the 302 immediately. A consumer group aggregates counts in memory per code per minute and writes one row per (code, minute) to an analytics store such as Cassandra or ClickHouse. Kafka retention lets us replay if the counter had a bug; consumers are idempotent by writing aggregates keyed by (code, minute) as upserts. Counts are eventually consistent by seconds, which is fine for a dashboard.

How to answer

Say "off the hot path" first, then the pipeline shape, then exactly-once worries (duplicates on retry) and how you live with them.

Likely follow-ups
  • What if one link gets half of all clicks? (hot partition: pre-aggregate in the read pod, or add a random suffix to the key)
  • How do you show "unique visitors"? (HyperLogLog: a tiny sketch, about 12 KB in Redis, that estimates the number of unique items with ~1% error)
SQL or NoSQL for the URL table?

The access pattern is "get one row by primary key" at very high volume, with no joins, ~91 TB over five years, and immutable rows. That fits a key-value store such as DynamoDB or Cassandra, which shards and replicates automatically. A sharded MySQL/Postgres with code as primary key is also fine and gives a strong unique constraint. I would choose based on what the team runs well; the important thing is that the shard key is the code.

How to answer

Decide from the access pattern and size, in one sentence, and show you know the other option is not wrong.

Likely follow-ups
  • How do you list all links for one user in a key-value store? (a second table keyed by owner_id)
One link goes viral: 50,000 clicks per second on a single code. What breaks and how do you fix it?

All requests for that code hash to one Redis shard and, on a miss, one store shard: a hot key. Layers of fixes: (1) a CDN or edge caches that 302 for a few seconds, so most clicks never reach us; (2) each read pod keeps a tiny in-process LRU cache with a few seconds TTL, so Redis sees one request per pod per few seconds; (3) request coalescing so only one miss per pod goes to the store; (4) click events for that code are pre-aggregated in the pod before going to Kafka, to avoid a hot partition.

How to answer

Name where the load concentrates (cache shard, store shard, Kafka partition), then fix each from the outside in.

Likely follow-ups
  • What happens when the hot key's cache entry expires? (stampede, coalescing, jittered TTL)
Your codes are sequential. Why is that a problem and how do you fix it?

Anyone can walk 1000001, 1000002... and find links others thought were private (shared documents, password reset pages), and competitors can count how many links you create per day. Fix it by passing the counter value through a reversible scramble (a bijection on 0..627-1, such as a keyed Feistel network) before base62. Each input still maps to exactly one output, so uniqueness is kept, but neighbours look unrelated. Or use pre-generated random keys (KGS). And never treat a short link as a secret: private links still need authentication.

How to answer

Give the attack, then a fix that keeps uniqueness, then the honest caveat that obscurity is not access control.

Likely follow-ups
  • Why not just add random characters to the end?
How do you run this in two regions?

Reads: replicate the URL table to both regions (DynamoDB global tables, Cassandra multi-DC). Rows are written once and never changed, so there are no conflicts. A click is served by the nearest region. Writes: give each region its own disjoint ID space (for example region bit in the high part of the number, or separate range blocks), so both regions can create codes at the same time without talking. The small catch is replication lag: a link created in Mumbai might 404 in Virginia for a second. Fix by falling back to the other region on a miss for young codes, or by routing a creator's first clicks to the home region.

How to answer

Split reads and writes. Immutability makes reads easy; disjoint ID spaces make writes easy; name the lag edge case.

Likely follow-ups
  • How do you fail over DNS between regions? How fast?
How do expiry and deletion work?

Store expires_at per row and check it on every read, which is correct even if cleanup is late. Use the database's TTL feature (DynamoDB TTL, Cassandra TTL) or a nightly batch job that deletes expired rows in small batches. On delete or disable, also delete the Redis key and purge the CDN entry, or a cached redirect could live on. Return 410 Gone for expired or disabled links so crawlers and clients know they are not coming back.

How to answer

Correctness on the read path first, cleanup second, and remember every cache layer.

Likely follow-ups
  • Can an expired code be reused? (Usually no: old printed links would point to someone else's page.)
Design Pastebin. What do you reuse from the URL shortener, and what changes?

Reuse the key side: pre-generated base62 keys from a KGS (or counter ranges), a read path of GET /{key}, caching of hot metadata, rate limits on creation. What changes is the value: pastes are KBs to MBs, so I split storage. A metadata row (key, owner, title, language, size, visibility, expires_at, s3_key) lives in a database with indexes by key, owner and expiry; the body lives in S3 under the key, served through a CDN or a pre-signed URL. I write the body first and the row second, so a crash leaves only an orphan object for cleanup. Limits: a maximum size (413 above it) and quotas. Expiry is checked on every read (410), and S3 lifecycle rules on expiry-class prefixes delete the bodies in bulk. Raw content is served from a separate domain as text/plain with nosniff to prevent stored XSS.

How to answer

Open with "same key service, new value problem", give the envelope (1M pastes/day at 10 KB is about 10 GB/day of bodies but only 300 MB of metadata), then the write order and expiry. Add versioning only if they mention Gists.

Likely follow-ups
  • Tiny pastes: why store them inline in the row? (Saves an S3 round trip for most reads.)
  • How would you add revisions like Gists? (Content-addressed bodies plus a revisions table.)
  • Burn after reading? (A conditional delete so only one reader gets it.)

Scenario: redirects slow down every day at 9 PM

Monitoring shows redirect p99 jumping from 20 ms to 900 ms each evening. Cache hit ratio drops from 98% to 60% at the same time. Nothing was deployed.
Weak answer: "Add more read pods and a bigger database."
Strong answer: "The hit ratio drop is the clue: something is causing misses. Check whether Redis is evicting (memory full, evictions metric), whether many keys share the same TTL and expire together (a daily batch created at 9 PM yesterday), or whether a bot is hitting random non-existent codes (penetration). Fixes: jitter TTLs, add memory or shards, cache negative lookups or use a Bloom filter, and rate-limit the bot. Then protect the store with coalescing so a future miss storm cannot flatten it."
Follow-ups: How would you prove it is a bot? Which dashboard would you build so this is caught in 5 minutes next time?
