Where Kafka, Kubernetes and Docker fit

  • Docker: the write service and read service are each built as a container image (see Dockerfile). Same image in dev, test and production, so "works on my machine" disappears.
  • Kubernetes: both services are stateless, so they run as Deployments behind a Service and an Ingress / Gateway that routes /api/* and /*. The read Deployment uses a HorizontalPodAutoscaler on CPU; the write Deployment can stay small. Redis (if self-hosted) runs as a StatefulSet or via an operator; most teams use a managed cache instead.
  • Kafka: the clicks topic, keyed by code so all clicks of one link land on the same partition (see partitions and keys). The click-counter service is a consumer group; add consumers to scale up to the partition count. Kafka also absorbs spikes: if the analytics DB is slow, events wait in the log (consumer lag grows) instead of slowing redirects.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redirect
spec:
  replicas: 6
  selector:
    matchLabels: { app: redirect }
  template:
    metadata:
      labels: { app: redirect }
    spec:
      containers:
      - name: redirect
        image: registry.local/shortener-redirect:1.4.2
        ports: [{ containerPort: 8080 }]
        env:
        - { name: REDIS_ADDR, value: "redis-master:6379" }
        - { name: KAFKA_BOOTSTRAP, value: "kafka:9092" }
        resources:
          requests: { cpu: "250m", memory: "256Mi" }
          limits:   { memory: "512Mi" }
        readinessProbe:
          httpGet: { path: /healthz, port: 8080 }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: redirect
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: redirect }
  minReplicas: 6
  maxReplicas: 60
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
# Kafka 4.x (KRaft), e.g. inside the apache/kafka:4.4.0 container
/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic clicks --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2 --config retention.ms=604800000
Created topic clicks.

12 partitions lets up to 12 consumers share the counting. Retention is 7 days (604,800,000 ms, also the Kafka default), so we can replay a day of clicks if the counter had a bug. On a single-broker laptop use --replication-factor 1 and drop min.insync.replicas.
