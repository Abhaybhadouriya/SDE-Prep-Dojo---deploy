Variant: Pastebin / Gists

"Design Pastebin" is the URL shortener's sibling and is often asked as a follow-up. The key half is identical: a short, unguessable base62 key from the same KGS or counter, and a read path of GET /{key}. The value half is what changes. A long URL is about 100 bytes; a paste can be 10 KB of code or 5 MB of log output. That one difference decides the storage design.

Explain like I'm 5

A library card catalogue has a small card for every book: title, author, shelf number. The books themselves sit on big shelves in the back. You search the little cards fast, then walk to the shelf. Pastebin keeps the little card (metadata) in a database and the big book (the paste text) in object storage.

Hybrid storage: metadata row in the DB, body in S3

Why split it
  • Metadata rows stay tiny, so the indexes (by key, by owner, by expires_at) fit in memory.
  • S3 costs a fraction of database storage per GB and is designed for 11 nines of durability.
  • Bodies are immutable: perfect for a CDN and long cache lifetimes.
  • Big uploads can go straight from the client to S3 with a pre-signed URL, skipping your API servers.
What it costs
  • Two systems to keep consistent (write order matters, below).
  • An extra hop on reads, so tiny pastes are often stored inline in the row instead.
  • Garbage: orphaned objects need a cleanup job or a lifecycle rule.

Back of the envelope: 1 million new pastes a day at an average 10 KB is about 10 GB of bodies per day, roughly 3.65 TB per year, while 1 million metadata rows at about 300 bytes is only 300 MB per day. Bodies are 97% of the bytes and almost none of the queries. That ratio is the whole argument for the split.

The write path, in the right order

  1. Reject oversized bodies early (HTTP 413). The limit is a product choice; a plan tier can raise it.
  2. Take a key from the KGS pool, exactly as in the shortener. No collision check needed.
  3. Upload the body to S3 first (for large pastes, give the client a pre-signed PUT URL instead).
  4. Only then insert the metadata row. A crash between steps 3 and 4 leaves an orphan object, which cleanup removes; the reverse order could leave a row pointing at nothing.
  5. Return the short URL. The paste is readable as soon as the row exists.
CREATE TABLE pastes (
  paste_key   CHAR(8)      PRIMARY KEY,          -- from the KGS
  owner_id    BIGINT,                            -- NULL for anonymous
  title       VARCHAR(200),
  language    VARCHAR(32),                       -- syntax highlighting hint
  size_bytes  INT          NOT NULL,
  visibility  SMALLINT     NOT NULL DEFAULT 0,   -- 0 public, 1 unlisted, 2 private
  body_inline TEXT,                              -- set only when size_bytes <= 4096
  s3_key      VARCHAR(64),                       -- set otherwise
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
  expires_at  TIMESTAMPTZ                        -- NULL = never
);
CREATE INDEX pastes_owner   ON pastes (owner_id, created_at DESC);
CREATE INDEX pastes_expires ON pastes (expires_at) WHERE expires_at IS NOT NULL;

Size limits and expiry

  • Size limits protect cost and abuse: a hard maximum per paste (say 10 MB), a smaller limit for anonymous users, and a per-account quota. GitHub's Gist API is a good real-world reference: it returns at most 1 MB of each file inline, marks bigger files truncated with a raw_url to fetch the rest, and asks you to clone the gist with git for files over 10 MB.
  • Expiry options (10 minutes, 1 day, 1 month, never) are stored as expires_at and checked on every read (return 410 Gone), because background deletion is always late.
  • Delete the bodies cheaply with an S3 lifecycle rule. Lifecycle rules expire objects by age under a prefix (or tag), so write each body under a prefix that matches its expiry class: ttl-1d/, ttl-30d/, keep/. A nightly job deletes expired metadata rows in batches.
  • Burn after reading: a conditional delete (DELETE ... WHERE paste_key = $1 RETURNING s3_key) so exactly one reader wins.

What makes Gists different

  • Versions and forks: each gist is a small git repository, so every edit is a revision and forks are cheap. If the interviewer wants history, store bodies content-addressed (sha256 of the text as the S3 key) so unchanged files are never stored twice, and keep a revisions table pointing at them.
  • Many files per paste: metadata becomes one paste row plus one row per file.
  • Serve raw text from a separate domain (GitHub uses a different host for raw gist content) with Content-Type: text/plain and X-Content-Type-Options: nosniff, so a paste full of HTML and JavaScript can never run as a page on your main site (stored XSS).
  • "Unlisted" is not "secret": it only means "not in search". Keys must be long and random enough that guessing is useless, and private pastes need real access checks.

From your world

This is a NIC descriptor ring. The ring holds small, fixed-size descriptors (length, flags, a pointer), and the payload sits in separate DMA buffers. You scan and index the descriptors fast and touch the big buffers only when you must. Pastebin's metadata rows are the descriptors and S3 objects are the buffers. The write-order rule is the same too: fill the buffer before you hand the descriptor to the consumer, never the other way round.

Interviewers love this line: "Same key service as the shortener; the new problem is the value. I keep metadata in the database and bodies in object storage, write the body first, check expiry on every read, and let lifecycle rules do the bulk deletes."
