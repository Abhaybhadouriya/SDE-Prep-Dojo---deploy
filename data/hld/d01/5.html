Architecture: the write path and the read path

Because reads are 100x writes, we draw the two paths separately. Click Next or Play.

  1. Client. A browser either creates a link (POST) or follows one (GET). Both arrive at our public address.
  2. Load balancer. An L7 load balancer terminates TLS and routes by path: /api/v1/urls goes to the write service, anything else goes to the read service. The two services scale separately.
  3. Write service gets IDs in bulk. Each write pod holds a block of IDs in memory (for example 1,000). When the block runs out it asks the ID range service for the next one. No network call per link.
  4. Store. The pod base62-encodes the next ID, writes code → long URL to the sharded store (with "insert if not exists"), and returns 201 with the short URL.
  5. Read path. A GET goes to a read pod, which checks Redis first. On a hit it answers 302 in about a millisecond of server time; on a miss it reads the store, fills Redis with a TTL, then answers.
  6. CDN for viral links. If a link is clicked millions of times in an hour, a CDN edge can cache the 302 for a few seconds, so most clicks never reach us.
  7. Analytics off the hot path. The read pod publishes a small "click" event to Kafka and returns immediately. A separate consumer counts clicks and writes totals to a stats store. If analytics is slow or down, redirects still work.

From your world: L4 vs L7 load balancer (step 2)

An L4 load balancer picks a backend from the TCP/UDP 5-tuple and forwards the packets, like ECMP plus NAT; it never looks inside the bytes. An L7 load balancer is a full proxy: it terminates TLS (it holds the certificate, finishes the TLS handshake with the browser and decrypts the traffic), reads the HTTP request line, and can then route /api/... to one pool and /aZ3kP9q to another, add headers, or retry on a different backend. Here we need path routing (write service vs read service), so L7. The chat design uses an L4 balancer because a WebSocket is one long-lived TCP stream that only needs to be pinned to one gateway. Where it breaks: ECMP hashing is stateless; an L7 proxy keeps a TCP and TLS session per client, so it costs CPU and memory per connection and is a tier you must scale. From your world: what a CDN is (step 6)

CDN = content delivery network: hundreds of cache servers grouped in PoPs (points of presence) in cities near users. DNS or anycast steers your request to the nearest PoP, and the PoP answers from its cache if it has a fresh copy; otherwise it asks our servers (the "origin") and keeps the answer for its TTL. In your terms: anycast plus a cache at every edge PoP. So yes, it is "like anycast routing", with storage added. Where it breaks: a CDN only helps for responses that are safe to cache. A 302 kept for a few seconds is fine (we lose a few click counts); a POST that creates a link, or a per-user page, must always reach the origin.

What actually happens on one click (named processes)

  1. DNS resolves sho.rt to the load balancer's (or CDN's) address. Browsers and resolvers cache this.
  2. TCP + TLS handshake with the load balancer (for example NGINX, Envoy or a cloud L7 balancer).
  3. The LB picks a healthy read pod (round robin or least-connections) and forwards GET /aZ3kP9q.
  4. The read pod runs GET url:aZ3kP9q on Redis. Hit: go to step 6.
  5. Miss: it reads the row from the store shard that owns the code, checks status and expires_at, then SET url:aZ3kP9q ... EX 86400 in Redis.
  6. The pod sends 302 Location: ..., and fire-and-forget publishes {code, ts, country, referrer} to the Kafka clicks topic.
  7. The browser follows the Location header to the real site. Our job is done.
