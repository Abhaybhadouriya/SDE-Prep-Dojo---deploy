Remember this

You might confuse this with:

  • At-least-once vs exactly-once: at-least-once = every message arrives, maybe twice (Kafka's normal mode); exactly-once = the effect happens once. For an SMS you get "effectively once" by pairing at-least-once delivery with a dedupe sent log; the provider call itself can never be exactly-once.
  • Retry topic vs DLQ: a retry topic holds messages that will be tried again after a delay; the DLQ (dead-letter queue) holds messages we gave up on, waiting for a human.
  • Idempotency-Key vs event ID: the Idempotency-Key dedupes the caller's retries of the API call; the event ID dedupes our own Kafka redeliveries inside the workers.

Remember this

  • Flow: services → API (202, idempotency) → Kafka → router (prefs, caps, template) → per-channel, per-priority topics → workers → APNs/FCM/SMS/email.
  • Priority isolation = separate topics + separate worker pools + separate provider quotas. A campaign must never delay an OTP.
  • Kafka is at-least-once → dedupe on (event ID, channel); claim → send → mark.
  • Temporary errors → retry topics with backoff → DLQ. Permanent errors → fix data (delete dead tokens).
  • Two vendors behind circuit breakers for SMS and email.
  • TTL on messages: a late OTP is worse than none.
  • Scale workers on consumer lag (KEDA); partitions cap parallelism in a classic group.
  • 1B/day ≈ 10k/s average; plan ~60k/s peak with campaigns.
