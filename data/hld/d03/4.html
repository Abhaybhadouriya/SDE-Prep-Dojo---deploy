Data model

Several small stores, each chosen for its access pattern.

-- Preferences and device tokens: read on every send, small, key lookups -> KV store + cache
user_prefs(user_id PK, prefs_json, quiet_start, quiet_end, tz, updated_at)
device_tokens(user_id, device_id, platform /* ios|android|web */, token, app_version,
              last_seen_at, PRIMARY KEY (user_id, device_id))

-- Templates: few, read-mostly -> SQL + in-memory cache in the workers
templates(template_id, version, channel, locale, body, dlt_template_id /* India SMS */,
          PRIMARY KEY (template_id, version, channel, locale))

-- Notification log: 1B rows/day, write-heavy, read by user and time -> wide-column (Cassandra)
-- partition = (user_id, day bucket) keeps partitions bounded; cluster by time, newest first
notifications(user_id, day, created_at, notification_id, channel, category, template_id,
              params, status /* queued|sent|delivered|failed|dropped */, provider_msg_id,
              PRIMARY KEY ((user_id, day), created_at, notification_id))
  WITH CLUSTERING ORDER BY (created_at DESC)

-- Dedupe / sent log: "was (event, channel) already sent?" -> unique key, TTL a few days
sent_log(event_id, channel, status, PRIMARY KEY (event_id, channel))   -- or Redis SET NX EX

Why NoSQL for the log? "It is an append-mostly log of 1 billion rows a day, always read as 'this user's recent notifications', so a wide-column store partitioned by user and day gives cheap writes and a single-partition read for the inbox." Preferences could be SQL or KV; they are tiny and heavily cached. See data modeling and indexing.
