Deep dives: the hard parts

Stop here for SDE-1? For SDE-1, the architecture above plus priority topics, retries with a DLQ and a dedupe key is a solid answer. SDE-2: be ready for all five deep dives.

Deep dive 1: OTPs must never wait behind campaigns (must know)

If everything shares one queue, a 100M-message campaign puts 100M messages in front of the next OTP. At 30,000/s that is almost an hour of waiting. Fixes, in layers:

  • Separate topics per priority (push.high, push.low), with separate consumer pools. High-priority workers are always running and are never shared with campaigns.
  • Throttle campaigns on purpose: the campaign sender releases messages at a controlled rate (for example spread over 2 hours), leaving provider quota for transactional traffic.
  • Separate provider accounts or quotas where possible (a dedicated sender for OTP SMS, a different email IP pool for marketing so marketing spam reports do not hurt transactional email).
  • Time to live: an OTP is useless after a few minutes. Carry ttl_seconds and drop expired messages instead of sending them late. The AWS Builders' Library post on queue backlogs explains why working through a stale backlog in FIFO order after an outage delays fresh requests, and why dropping expired work (or serving newest first) recovers faster.

Deep dive 2: exactly once is a lie; dedupe is the truth (must know)

Kafka consumers are at-least-once by default: if a worker sends the push, then crashes before committing its offset, the next worker gets the same message again. Without protection, user 42 gets two pushes. The fix is an idempotent consumer: a sent log keyed by (event_id, channel).

# dedupe.py - claim, send, mark: a "sent log" with a unique key stops duplicates
import sqlite3, time

db = sqlite3.connect(":memory:")
db.execute("""CREATE TABLE sent_log (
    event_id   TEXT NOT NULL,
    channel    TEXT NOT NULL,
    user_id    INTEGER NOT NULL,
    status     TEXT NOT NULL,          -- SENDING or SENT
    claimed_at REAL NOT NULL,
    PRIMARY KEY (event_id, channel))""")
STUCK_AFTER = 30   # seconds: a SENDING row older than this means the worker died mid-send

def provider_send(tag, user_id, text, crash=False):
    if crash:
        raise RuntimeError("worker crashed before the provider answered")
    print(f"SEND  {tag} -> user {user_id}: {text}")      # ... call APNs / FCM / SMS gateway here ...

def send_once(event_id, channel, user_id, text, now, crash=False):
    # 1. CLAIM: insert SENDING, or take over a SENDING row that is stuck (older than the timeout)
    cur = db.execute("INSERT OR IGNORE INTO sent_log VALUES (?, ?, ?, 'SENDING', ?)",
                     (event_id, channel, user_id, now))
    if cur.rowcount == 0:
        cur = db.execute("""UPDATE sent_log SET claimed_at = ? WHERE event_id = ? AND channel = ?
                            AND status = 'SENDING' AND claimed_at < ?""",
                         (now, event_id, channel, now - STUCK_AFTER))
        if cur.rowcount == 0:
            print(f"skip  {event_id}/{channel}: already sent (or being sent)")
            return
        print(f"retry {event_id}/{channel}: stuck in SENDING, taking it over")
    # 2. SEND
    try:
        provider_send(f"{event_id}/{channel}", user_id, text, crash)
    except RuntimeError as e:
        print(f"CRASH {event_id}/{channel}: {e}; row stays SENDING")
        return
    # 3. MARK
    db.execute("UPDATE sent_log SET status = 'SENT' WHERE event_id = ? AND channel = ?",
               (event_id, channel))

# Kafka is at-least-once: after a consumer crash, the same records are delivered again.
t = time.time()
send_once("ord-981:shipped", "push", 42, "Your order has shipped", t)
send_once("ord-981:shipped", "sms",  42, "Your order has shipped", t)
send_once("ord-981:shipped", "push", 42, "Your order has shipped", t + 1)     # redelivered
send_once("otp-5521", "sms", 77, "Your OTP is 482913", t, crash=True)         # dies mid-send
send_once("otp-5521", "sms", 77, "Your OTP is 482913", t + 5)                 # too soon: skip
send_once("otp-5521", "sms", 77, "Your OTP is 482913", t + 60)                # stuck: retry
send_once("otp-5521", "sms", 77, "Your OTP is 482913", t + 61)                # now SENT: skip
$ python dedupe.py
SEND  ord-981:shipped/push -> user 42: Your order has shipped
SEND  ord-981:shipped/sms -> user 42: Your order has shipped
skip  ord-981:shipped/push: already sent (or being sent)
CRASH otp-5521/sms: worker crashed before the provider answered; row stays SENDING
skip  otp-5521/sms: already sent (or being sent)
retry otp-5521/sms: stuck in SENDING, taking it over
SEND  otp-5521/sms -> user 77: Your OTP is 482913
skip  otp-5521/sms: already sent (or being sent)

In production the sent log is Redis (SET sent:{event}:{channel} 1 NX EX 259200, kept 3 days) or a table with a unique key. The code above already uses the production order, which interviewers probe: claim, send, mark. If you mark "sent" before calling the provider and then crash, the message is lost; if you mark after, a crash in between causes a duplicate. The usual answer (what dedupe.py does) is: store status SENDING first, call the provider, then set SENT. A redelivered message that finds SENDING older than a timeout is retried; you can see the OTP survive a crash in the output above. You accept a rare duplicate rather than a rare loss (for OTPs, a duplicate is safer than a missing code). Push providers also offer collapse keys (FCM collapse_key, APNs apns-collapse-id) so a phone shows only the latest of several similar notifications.

From your world

The sent log is the application's version of TCP sequence numbers: a retransmitted segment with a sequence number the receiver has already seen is not delivered to the app twice. Here event_id is the sequence number and the sent log is the receive window's memory. Where it breaks: a TCP receiver forgets old sequence numbers when the connection closes, and only one receiver ever sees them. The sent log must outlive crashes and be shared by every worker, so it lives in Redis or a database with a TTL instead of in one process's memory. See consumer groups and offset commits for why redelivery happens.

Deep dive 3: retries, backoff, DLQ and provider failover (must know)

  • Classify errors. Temporary (timeout, HTTP 5xx, 429 throttling): retry. Permanent (bad token, invalid phone number, user unsubscribed): do not retry; fix data instead.
  • Do not block the partition. If a worker sleeps 10 minutes waiting to retry, every message behind it in that partition waits too. Instead, publish the failed message to a retry topic (push.retry.1m, push.retry.10m) whose consumer waits until the message's due time, then re-sends. After N attempts, publish to push.dlq and alert.
  • Exponential backoff with jitter on retries, so a provider recovering from an outage is not hit by everyone at once.
  • Provider failover: wrap each SMS vendor in a circuit breaker. If vendor A's error rate crosses a threshold, route OTPs to vendor B for a while, then probe A again. Keep two vendors for SMS and email; push has only APNs/FCM, so there you can only retry and queue.
  • Kafka 4.x option: share groups ("queues for Kafka", KIP-932) became production-ready in Kafka 4.2 and gained a built-in DLQ for share groups in 4.4. They let many workers consume one partition with per-message acknowledgements, which suits "send and ack each notification" work. Classic consumer groups plus retry topics remain the common, well-understood answer in interviews.

Deep dive 4: campaigns to 100 million users (SDE-2)

  • Do not make one API call per user from the marketing tool. Send one POST /v1/campaigns with a segment ID.
  • A campaign planner reads the segment in pages (user ID ranges) and publishes batches to notif.requests at a controlled rate. It records progress (last user ID done) so a crash resumes instead of restarting, which would double-send.
  • Time zones and quiet hours: bucket users by time zone and release each bucket at its local send time; messages that fall into quiet hours are delayed to the end of the quiet period (via the scheduled/retry path) or dropped if they expire.
  • Frequency caps: "no more than 3 promos per user per day" is a per-user counter (the rate limiter again, with a daily window) checked by the router.
  • Provider limits: email providers and SMS gateways enforce sending rates per account; the channel workers pace themselves with a token bucket per provider.

Deep dive 5: device tokens and in-app inbox (good to know)

  • Token lifecycle: the app registers its APNs/FCM token at startup (PUT /v1/devices). Tokens change after reinstalls and restores. When APNs answers 410 (reason Unregistered) or FCM returns an UNREGISTERED error, delete that token, or you keep paying to send to dead devices.
  • Multi-device: a user with a phone and a tablet gets the push on both; the router sends one message per active token.
  • In-app inbox: just a read of the notification log partition (user_id, day), newest first, with an unread counter in Redis. For a live bell badge, push the update over the app's WebSocket/SSE connection if it is open (see the chat design for connection gateways).
