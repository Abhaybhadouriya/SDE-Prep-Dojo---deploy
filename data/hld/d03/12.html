Quick quiz

Why does the send API return 202 instead of 200?

  1. 202 is faster to send
  2. The work is queued, not finished; the caller should not wait for providers
  3. 200 is only for GET requests
202 Accepted means "I have taken the job". Delivery happens later, asynchronously.

What is the best way to stop a 100M-user campaign from delaying OTPs?

  1. Add a priority field to each message in one shared topic
  2. Send OTPs by email instead
  3. Separate high-priority topics and worker pools (and provider quotas)
A priority field in a shared queue still leaves the OTP behind millions of messages. Physical isolation does not.

A worker sends a push, then crashes before committing its offset. What happens next?

  1. Another worker gets the same message again; dedupe must skip it
  2. The message is lost
  3. Kafka deletes the message
Kafka redelivers from the last committed offset (at-least-once). The sent log keyed by (event ID, channel) prevents a second push.

Why use a retry topic instead of sleeping in the consumer?

  1. Sleeping uses too much CPU
  2. Sleeping blocks every later message in that partition (head-of-line blocking)
  3. Kafka forbids sleeping
Messages in a partition are processed in order, so one sleeping message holds up all others behind it.

APNs answers 410 "Unregistered" for a device token. What should you do?

  1. Retry with backoff
  2. Send it to the DLQ for a human
  3. Delete the token; it is a permanent error
The app was uninstalled or the token changed. Retrying wastes money and time; clean the data.

Which metric should drive autoscaling of channel workers?

  1. Consumer lag on their topic
  2. CPU usage
  3. Number of users
Workers mostly wait on network calls, so CPU stays low even when a huge backlog exists. Lag shows real work waiting.

1 billion notifications a day is roughly how many per second on average?

  1. About 1,000
  2. About 10,000
  3. About 100,000
1B ÷ 105 s ≈ 10,000/s (exact about 11,600/s). Peaks with campaigns are several times higher.
