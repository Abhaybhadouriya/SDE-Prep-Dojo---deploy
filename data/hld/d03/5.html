Architecture: one notification, start to finish

Follow "order 981 shipped" for user 42. Click Next or Play.

  1. Intake. The order service calls POST /v1/notifications with Idempotency-Key: ord-981:shipped. The API validates the request, checks the key (Redis SET NX), and answers 202 Accepted in milliseconds.
  2. Durable queue. The API writes the request to the Kafka topic notif.requests (keyed by user_id, so one user's notifications stay in order) with acks=all. Once Kafka has it, it will not be lost.
  3. Route and enrich. A router consumer reads it, loads user 42's preferences and device tokens (from a cache), checks opt-outs, quiet hours and frequency caps, renders the template in the user's language, and decides the channels: push and SMS.
  4. Fan out per channel. The router writes one message per channel to push.high and sms.high. Campaign traffic goes to the .low topics instead.
  5. Deliver. Channel workers (consumer groups) check the sent log (dedupe), call APNs/FCM or the SMS vendor, then commit their Kafka offset. Each pool scales on its own.
  6. Retry. A temporary failure (timeout, 5xx, provider throttling) sends the message to a delayed retry topic. After a few tries it lands in a dead-letter queue (DLQ) for a human or a repair job. Permanent errors (invalid token) are not retried.
  7. Track. Workers write "sent" to the notification log. Providers later call back (or report on the next request) "delivered" or "failed"; the app reports "opened". The in-app inbox reads the same log.
