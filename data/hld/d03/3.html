Key APIs

# 1) Send to one user (called by order, payment, auth services)
POST /v1/notifications
Idempotency-Key: ord-981:shipped            # same key twice = same notification, sent once
{
  "user_id": 42,
  "category": "order_update",              # drives priority + preference checks
  "template_id": "order_shipped_v3",
  "params": { "order_id": "981", "eta": "Tue" },
  "channels": ["push", "sms"],             # optional; default from category + prefs
  "priority": "high",                      # high | normal | low
  "send_at": null,                         # or a future time; quiet hours still apply
  "ttl_seconds": 3600                      # drop if not delivered within this time
}
-> 202 Accepted  { "notification_id": "n_7Gk2...", "status": "queued" }

# 2) Campaign (segment fan-out, low priority)
POST /v1/campaigns
{ "segment_id": "bbd-2026-electronics", "template_id": "bbd_launch", "priority": "low",
  "window": { "start": "2026-11-25T09:00:00+05:30", "end": "2026-11-25T11:00:00+05:30" } }
-> 202 Accepted  { "campaign_id": "c_19", "estimated_recipients": 31200000 }

# 3) Status
GET /v1/notifications/n_7Gk2...
-> 200 { "push": "delivered", "sms": "sent", "opened_at": null }

# 4) User preferences (called by the app's settings screen)
PUT /v1/users/42/preferences
{ "promotional": { "push": true, "sms": false, "email": true },
  "quiet_hours": { "start": "22:00", "end": "08:00", "tz": "Asia/Kolkata" } }

# 5) Provider callbacks (webhooks from the SMS / email providers)
POST /v1/callbacks/sms/{provider}   { "message_id": "...", "status": "DELIVERED" }

Note 202 Accepted, not 200: we have queued the work, not finished it. The caller should not wait for APNs. The Idempotency-Key lets a caller retry safely after a timeout (see the IETF draft). The send API sits behind the rate limiter so one buggy caller cannot flood users.
