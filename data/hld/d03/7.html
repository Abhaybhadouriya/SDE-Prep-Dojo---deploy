Where Kafka, Kubernetes and Docker fit

This design is a textbook Kafka use case, so this section is bigger than usual.

  • Kafka is the backbone. It decouples fast intake (202 in milliseconds) from slow delivery (seconds, retries), absorbs bursts (a campaign can enqueue faster than providers accept), keeps order per user (key = user_id, so "order placed" is not shown after "order delivered"), and allows replay after a bug thanks to retention. Each channel is a separate consumer group, so push and email progress independently. Producers use acks=all with enable.idempotence=true (both defaults in Kafka 4.x clients) and topics use replication factor 3 with min.insync.replicas=2 (see replication).
  • Kubernetes runs every box as a Deployment: API, router and one worker Deployment per channel and priority. Scale workers on consumer lag (messages waiting), not CPU, because workers mostly wait on the network. KEDA's Kafka scaler does exactly that. Keep a high minReplicaCount for the .high pools so OTP workers are never cold. Provider credentials (APNs keys, SMS API keys) are Secrets.
  • Docker: each service is an image; a Compose file with Kafka (KRaft, single node), Redis and fake providers is how you test the whole flow on a laptop, the same way the ShopStream pipeline is built locally.
# Kafka 4.x (KRaft). Inside the apache/kafka:4.4.0 container: export PATH=$PATH:/opt/kafka/bin
B=localhost:9092
kafka-topics.sh --bootstrap-server $B --create --topic notif.requests --partitions 48 --replication-factor 3 --config min.insync.replicas=2
kafka-topics.sh --bootstrap-server $B --create --topic push.high      --partitions 24 --replication-factor 3 --config min.insync.replicas=2
kafka-topics.sh --bootstrap-server $B --create --topic push.low       --partitions 96 --replication-factor 3 --config min.insync.replicas=2
kafka-topics.sh --bootstrap-server $B --create --topic push.retry.1m  --partitions 12 --replication-factor 3
kafka-topics.sh --bootstrap-server $B --create --topic push.dlq       --partitions 6  --replication-factor 3 --config retention.ms=1209600000

(On a one-broker laptop, use --replication-factor 1 and drop min.insync.replicas.) The DLQ keeps 14 days (1,209,600,000 ms) so humans have time to look. Kafka prints the metric-name warning for every topic containing a period or underscore; it is harmless as long as you never mix the two styles (we use only periods).

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: push-low-workers
spec:
  scaleTargetRef:
    name: push-low-workers          # the worker Deployment
  minReplicaCount: 2
  maxReplicaCount: 96               # no point going above the partition count
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka:9092
      consumerGroup: push-low-workers
      topic: push.low
      lagThreshold: "5000"          # target lag per replica
