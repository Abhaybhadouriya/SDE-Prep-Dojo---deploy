Architecture: follow one post, then one feed read

Click Next or Play. Steps 1-5 are the write path (Mia posts). Steps 6-9 are the read path (Sara opens the app). The two paths meet only in the caches, which is what keeps reads fast.

  1. Post request. Mia's app uploads the photo straight to blob storage (presigned URL), then sends POST /v1/posts. The API gateway checks her token and rate limit and forwards it to the stateless post service.
  2. Store it durably. The post service writes the row to the posts DB (and posts_by_author), then returns 201. Mia's own app inserts the post locally, so she sees it at once (read-your-own-writes).
  3. Publish an event. A PostCreated event goes to the Kafka topic post-events. Use the outbox pattern or CDC so "row saved" and "event sent" can never disagree (no dual write). New words: dual write = saving to the DB and then separately sending to Kafka; a crash in between loses the event. Outbox = write the event into a table in the same DB transaction as the post; a relay process publishes it to Kafka. CDC (change data capture, for example Debezium) = a tool that reads the database's own log and publishes each change. Deep dive 4 and Distributed Transactions & Event-Driven Data go deeper.
  4. Fan-out workers wake up. A consumer group reads the event and asks the graph service "who follows Mia?" in pages of, say, 1,000 ids. If Mia is flagged as a celebrity, the worker stops here: no push.
  5. Push ids into feeds. For each follower (skipping inactive accounts), the worker does a pipelined ZADD feed:{follower} plus a trim. 200 tiny writes, done in milliseconds. Mia's post is now in Sara's mailbox.
  6. Sara opens the app. GET /v1/feed reaches the feed service, which reads the top ids from feed:sara in one call.
  7. Pull the celebrities. The feed service looks up which celebrities Sara follows (a short, cached list) and reads their newest post ids from posts_by_author (heavily cached). It merges both lists by score.
  8. Hydrate. One multi-get to the post cache turns 20 ids into full posts, plus counters and "liked by me". Misses fall through to the posts DB. Deleted or private posts are filtered here.
  9. Rank and return. Optionally re-order with a ranking model, attach a cursor, and send 20 ready-to-draw posts. Images load from the CDN in parallel.

Whiteboard version (6 boxes, 30 seconds): Client -> API gateway -> Post service -> Posts DB + Kafka -> Fan-out workers -> Feed cache <- Feed service <- Client. Draw this first; add the graph service, post cache and celebrity pull when you explain the steps.
