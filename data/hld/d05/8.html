Trade-offs, bottlenecks and failure modes

Say each row as: "I pick X because A; the cost is B; if C becomes a problem I switch to Y." Example for the first row: "I pick push fan-out because reads outnumber writes about 100 to 1; the cost is write amplification, one insert per follower; if a celebrity with 50M followers posts, I switch to pull for that author and merge their posts at read time."

Trade-off sentence pattern: "I would pick hybrid fan-out because reads are 100x writes; the cost is two code paths and a celebrity flag to maintain; if ranking needs very fresh features I would move more users to pull, like LinkedIn did."

What if this box fails?

BoxWhat the user seesMitigation
Feed cache shardSlower feed for users on that shardReplica promotion; fall back to pull-building the feed; refill in the background

Graph serviceFan-out stalls; follow button failsCache follower lists; queue follow writes; fan-out retries later
Whole regionFeeds unavailable in that regionMulti-region with async replication; feeds can be rebuilt in the surviving region (see Reliability & DR)
Strengths of this design
  • Feed reads are a few cache calls
  • Posting is fast and never waits for fan-out
  • Caches are rebuildable, so losing one is not data loss
  • Each consumer (search, counters, notify) scales on its own
Costs and risks
  • Terabytes of RAM for feed caches
  • Celebrity flag and two code paths
  • Eventual consistency confuses some product flows
  • Hot keys for viral posts need special handling
