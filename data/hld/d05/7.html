Where Kafka, Kubernetes and Docker fit

Kafka

Kafka is the spine between "a post was saved" and "everything that reacts to it": fan-out, search indexing, notifications ("Mia posted for the first time in a while"), counters, ranking features and analytics. Each of those is a separate consumer group reading the same topic at its own pace. If you are new to these words, read Core Concepts and Consumers & Groups.

  • Key choice: key post-events by author_id so one author's create/edit/delete events stay in order. For the internal fanout-chunks topic, key by post_id + chunk_no (or leave keyless) so chunks spread evenly, because order between chunks does not matter.
  • Separate lanes: a fanout-chunks-big topic for accounts near the celebrity line keeps them from blocking everyone else (the "classic outage" above).
  • Delivery: at-least-once plus idempotent ZADD is enough; no Kafka transactions needed. See Delivery Semantics.
  • Do not dual-write: "save to DB, then send to Kafka" can lose the event if the process dies in between. Use the transactional outbox or CDC (Debezium). See Pipeline Architecture and CDC Data Pipeline.

Kubernetes

Every service here except the stores is stateless, which is the easy case for Kubernetes: Deployments behind Services, scaled by an autoscaler. The fan-out workers should scale on consumer lag, not CPU, because lag is what users feel. A common way is KEDA (an add-on that feeds Kafka lag into the Horizontal Pod Autoscaler). Note that more consumers than partitions do nothing, so the partition count caps how far workers can scale. See Scheduling & Autoscaling.

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: fanout-workers
spec:
  scaleTargetRef:
    name: fanout-workers          # a normal Deployment
  minReplicaCount: 4
  maxReplicaCount: 48             # never more than the topic's partition count
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka-bootstrap.kafka.svc:9092
      consumerGroup: fanout-workers
      topic: fanout-chunks
      lagThreshold: "5000"        # target lag per replica
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: feed-service
spec:
  replicas: 60
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 10% }
  selector:
    matchLabels: { app: feed-service }
  template:
    metadata:
      labels: { app: feed-service }     # Services and the PodDisruptionBudget select pods by this label
    spec:
      containers:
      - name: feed
        image: registry.example.com/feed-service:3.8.1
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }   # ready only after cache clients connect
        resources:
          requests: { cpu: "2", memory: "4Gi" }
          limits:   { memory: "4Gi" }
  • Redis/Valkey feed caches and Cassandra run as StatefulSets with operators, or (more often) as managed services; Kafka can run on Kubernetes with Strimzi (Kafka on K8s).
  • Use a PodDisruptionBudget on the feed service so node maintenance never removes too many replicas at once, and spread pods across zones with topology spread constraints.

Docker

Each service ships as a small image built with a multi-stage Dockerfile (Writing a Dockerfile). For local learning, one Compose file gives you the whole write path on a laptop:

# compose.yaml - a tiny local news feed lab
services:
  kafka:
    image: apache/kafka:4.3.2          # Kafka 4.x: KRaft only, no ZooKeeper (same image as Build It Locally)
    ports: ["29092:29092"]             # host tools use localhost:29092; containers use kafka:9092
    environment:                       # once you set any KAFKA_* variable, the image needs the full set
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093,HOST://:29092
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092,HOST://localhost:29092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,HOST:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
  redis:
    image: redis:7
    ports: ["6379:6379"]
  post-service:
    build: ./post-service
    environment: { KAFKA_BOOTSTRAP: "kafka:9092" }
    depends_on: [kafka]
  fanout-worker:
    build: ./fanout-worker
    environment: { KAFKA_BOOTSTRAP: "kafka:9092", REDIS_URL: "redis://redis:6379" }
    deploy: { replicas: 2 }            # two consumers in one group
    depends_on: [kafka, redis]

Post a few times, watch ZRANGE feed:sara 0 -1 fill up, then stop one worker and watch the lag on the other. The Build It Locally page walks through a full Compose lab like this, and Docker Compose explains the file.

Why the long Kafka block? With no settings, the image advertises localhost:9092. A client in another container bootstraps to kafka:9092, receives "talk to localhost:9092" in the metadata, and then fails to connect, because localhost inside that container is itself. KAFKA_ADVERTISED_LISTENERS fixes it: containers are told kafka:9092, your laptop is told localhost:29092.
