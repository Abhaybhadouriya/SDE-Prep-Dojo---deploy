Key APIs

Plain HTTPS REST is enough for a feed: the client asks, the server answers. (For a live "new posts" pill you can add server push later; see API Design & Communication.) The user id always comes from the auth token, never from the request body.

# 1. Get an upload URL for a photo (bytes go straight to blob storage)
POST /v1/media/upload-url        {"mime":"image/jpeg","size":812345}
  -> 200 {"media_id":"m_7Qx2","put_url":"https://blob.example/...signed...","expires_in":300}

# 2. Create the post (Idempotency-Key makes a retried tap safe)
POST /v1/posts
Idempotency-Key: 6f1c2b9e-3d4a-4a8e-9c1f-2a7b5e0d9f31
{"text":"Sunset at Marine Drive","media_ids":["m_7Qx2"]}
  -> 201 {"post_id":"1859300011122233344","created_at":"2026-11-23T18:04:11Z"}

# 3. Read the home feed, first page
GET /v1/feed?limit=20
  -> 200 {"items":[{"post_id":"18593...","author":{...},"text":"...","media":[...],
                    "like_count":1284,"liked_by_me":false}, ...],
          "next_cursor":"eyJzIjoxNzYzOTIwMDAwLCJpZCI6IjE4NTkyOTk5In0"}

# 4. Next page: pass the cursor back, never a page number
GET /v1/feed?limit=20&cursor=eyJzIjoxNzYzOTIwMDAwLCJpZCI6IjE4NTkyOTk5In0

# 5. Social graph and reactions
POST   /v1/users/{user_id}/follow
DELETE /v1/users/{user_id}/follow
POST   /v1/posts/{post_id}/like
GET    /v1/users/{user_id}/posts?cursor=...      # profile page
// The cursor is opaque to the client: base64 of the last item's sort key.
{ "s": 1763920000, "id": "18592999" }
// Server meaning: "give me items with (score, post_id) strictly below (1763920000, 18592999)".
// Redis filters by score only, so the service asks for score <= 1763920000 (inclusive)
// and then drops members with score == 1763920000 and post_id >= 18592999 itself.
// New posts arriving at the top do not shift this position, so no duplicates and no gaps.
  • Why cursors, not ?page=3? While you scroll, new posts land at the top. With offsets, page 3 now starts 5 items earlier, so you see duplicates. A cursor points at a fixed item, so it is stable. Offsets also get slower the deeper you go (the database must skip N rows).
  • Why an idempotency key on create? On a flaky mobile network the app may resend the same post. The server stores the key for a day and returns the first result instead of creating a duplicate post. See Payment System for the full idea.
  • Hydrated response: the feed API returns ready-to-draw objects (author name, avatar URL, counts), so the phone does not make 20 extra calls.
