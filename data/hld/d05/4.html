Data model: what we store and where

Start from the reads. The hot reads are (1) "the newest N post ids in my feed", (2) "the full post for these 20 ids", (3) "who follows user X" (for fan-out) and (4) "who does user Y follow" (for pulling celebrities). None needs a join across shards. That tells us: key-value and wide-column style stores, each keyed by the thing we look up. See Choosing Storage and Data Modeling.

-- Posts: one row per post, looked up by id (hydration)
CREATE TABLE posts (
  post_id     bigint PRIMARY KEY,        -- Snowflake id: time-sortable
  author_id   bigint,
  body        text,
  media_keys  list<text>,
  created_at  timestamp,
  deleted     boolean
);

-- One author's own posts, newest first (profile page and celebrity pull)
CREATE TABLE posts_by_author (
  author_id bigint,
  post_id   bigint,
  PRIMARY KEY ((author_id), post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);

-- The social graph, stored twice so both directions are one-partition reads
CREATE TABLE followers_of (followee bigint, follower bigint, since timestamp,
  PRIMARY KEY ((followee), follower));
CREATE TABLE following_of (follower bigint, followee bigint, since timestamp,
  PRIMARY KEY ((follower), followee));
# Fan-out worker: add post 1859300 to Sara's feed with score = created time
ZADD feed:sara 1763920251 1859300
# keep only the newest 500 entries (drop the oldest)
ZREMRANGEBYRANK feed:sara 0 -501
# Feed service: first page, newest first, with scores (for the cursor). Redis 6.2+ form:
ZRANGE feed:sara +inf -inf BYSCORE REV LIMIT 0 20 WITHSCORES
# Next page: INCLUSIVE of the cursor score (no "(" prefix), one extra item of slack.
# The service then skips members with score == 1763920000 and id >= 18592999,
# so posts made in the same second as the cursor item are not lost.
ZRANGE feed:sara 1763920000 -inf BYSCORE REV LIMIT 0 21 WITHSCORES

Two ways to handle ties. (1) As above: query inclusively and filter on (score, post_id) in the service. (2) Simpler: make the score unique by using the Snowflake post_id itself as the score, since it is already time-ordered; then an exclusive range such as ZRANGE feed:sara (18592999 -inf BYSCORE REV LIMIT 0 20 works directly. ZREVRANGEBYSCORE still works but has been deprecated since Redis 6.2 in favour of ZRANGE ... BYSCORE REV. (Snowflake ids above 253 lose precision as a Redis double score, so option 2 needs ids shortened to 53 bits, or option 1.)

$ redis-cli ZADD feed:sara 1763920251 1859300 1763920102 1859277 1763919950 1859201
(integer) 3
$ redis-cli ZRANGE feed:sara +inf -inf BYSCORE REV LIMIT 0 2 WITHSCORES
1) "1859300"
2) "1763920251"
3) "1859277"
4) "1763920102"
$ redis-cli ZCARD feed:sara
(integer) 3

Real output shape from redis-cli; try it with docker run --rm -p 6379:6379 redis:7 (or Valkey). Note: when two posts share a score, Redis orders equal scores by member, so use the post id in the cursor as a tie-breaker.

  • Why NoSQL for posts and the graph? Billions of rows, lookup by key, no joins, and easy horizontal scaling. Facebook actually keeps its graph in sharded MySQL behind a graph cache called TAO, so "sharded SQL + a big cache" is also a correct answer. Say why, not which brand.
  • Why store the graph twice? Fan-out asks "followers of X" and pull asks "who does Y follow". One table can only be partitioned one way. Writing two rows per follow is cheap; scanning the wrong partition is not.
  • Why ids in the feed, not full posts? A post edited or deleted would otherwise need fixing in 200 (or 50M) places. Store the id; hydrate from one place.
  • Why Snowflake ids? They are 64-bit and roughly time-ordered (41 bits of milliseconds first), so sorting by id is sorting by time. See Unique ID Generator.
