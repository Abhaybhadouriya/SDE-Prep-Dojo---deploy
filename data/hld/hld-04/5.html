Eight worked exercises (try first, then reveal)

Cover the answer, set a 3-minute timer, and say your working out loud. Then click the question to compare. The user counts below are assumptions for practice, not real company figures.

1. URL shortener: 100M new URLs a month, 100 reads per write, 500 bytes per record, kept 10 years. QPS and storage? Must know
  1. Writes 100M / (30 x 86,400 = about 2.6M s) = about 40 writes/s.
  2. Reads 100 x 40 = about 4,000 reads/s average, maybe 8,000-12,000 at peak.
  3. Storage 100M x 12 months x 10 years = 12 billion records x 500 B = 6 TB (before replication; about 18 TB with 3 copies).

What it changes: 6 TB fits on a few machines; the system is extremely read-heavy, so a cache in front of the store does most of the work. 12 billion codes also tells you the code length: base62 with 7 characters gives 62^7, about 3.5 trillion codes - plenty.

How to answer

Month seconds (2.5M), then ratio, then storage, then one design conclusion.

Likely follow-ups
  • How many characters do you need for the short code?
  • How big should the cache be? (See exercise 6.)
2. A Twitter-like app: 200M DAU, each posts 2 times a day and loads the home feed 20 times a day. Tweet text 300 B; 10% of tweets have a 500 KB image. QPS and daily storage? Must know
  1. Post QPS 200M x 2 = 400M posts/day / 86,400 = about 4,600/s, peak about 10,000-15,000/s.
  2. Feed QPS 200M x 20 = 4 billion feed loads/day = about 46,000/s, peak 100,000+/s.
  3. Text storage 400M x 300 B = 120 GB/day.
  4. Media storage 400M x 10% x 500 KB = 20 TB/day, about 7 PB a year before replication.

What it changes: feeds are read 10x more than posts are written, so precompute feeds (fan-out on write) or cache them; media dominates storage by over 100x and belongs in object storage plus a CDN. See News Feed.

How to answer

Split reads and writes, split text and media. Point out which number dominates.

Likely follow-ups
  • A celebrity with 50M followers posts. How many feed writes is that with fan-out on write?
3. Photo storage: 10M photos uploaded a day, 2 MB each (all sizes together), kept 5 years, 3 replicas. How much storage? Must know
  1. Per day 10M x 2 MB = 20 TB/day.
  2. Per year 20 TB x 365 = about 7.3 PB.
  3. 5 years about 36.5 PB; x3 replicas = about 110 PB.

What it changes: no database stores this - object storage only. Erasure coding (storing data plus parity chunks instead of three full copies) can cut the raw overhead from 3x to around 1.5x, which matters at 100 PB. Old photos can move to cheaper, colder storage tiers.

How to answer

Day, year, total, replicas. Then say the storage tier.

Likely follow-ups
  • How would you cut that cost? (Compression, erasure coding, cold tiers, dedupe.)
4. Chat app: 500M DAU, 40 messages per user per day, 100 B per message. Message QPS, storage per day, and how many connection servers if 10% of users are online at once? SDE-2
  1. Messages 500M x 40 = 20 billion/day / 86,400 = about 230,000 msgs/s, peak about 500,000/s.
  2. Storage 20B x 100 B = 2 TB/day, about 730 TB a year (before replication).
  3. Connections 10% of 500M = 50M open WebSocket connections at the same time.
  4. Servers assume one gateway holds about 100,000 connections (an assumption; well-tuned servers hold far more) = about 500 gateways, plus spares.

What it changes: the write rate needs a write-optimised store partitioned by conversation (Cassandra-style); connection count, not CPU, sizes the gateway fleet; you need a registry of which gateway holds which user. See Chat App (WhatsApp).

How to answer

Separate the three resources: write rate, disk, and long-lived connections. Name the assumption for connections per server.

Likely follow-ups
  • What limits connections per server? (File descriptors, memory per socket, ephemeral ports, epoll efficiency - your kernel knowledge.)
5. Video streaming: 1 million people watch at the same time at 5 Mbps each. What egress bandwidth is needed?
  1. Bits 1,000,000 x 5 Mbps = 5,000,000 Mbps = 5 Tbps.
  2. Bytes 5 Tbps / 8 = about 625 GB per second.
  3. Per hour 625 GB/s x 3,600 = about 2.25 PB per hour of watching.

What it changes: no single data centre should serve this from the origin; it must come from CDN caches close to users (Netflix pre-positions content inside ISP networks with its Open Connect appliances). Adaptive bitrate lets clients drop to a lower rate when the network is busy. See Video Streaming (Netflix).

How to answer

Multiply, convert bits to bytes (divide by 8), and conclude "CDN".

Likely follow-ups
  • A live cricket final has 10x that audience. What changes? (Pre-scale; cap bitrate; more CDN capacity booked ahead.)
6. Cache sizing: the URL shortener gets 4,000 reads/s. If the hottest 20% of each day's requested links serve most traffic, how much cache memory, at 500 B per entry? Must know
  1. Daily reads 4,000 x 86,400 = about 350 million reads a day.
  2. Hot set 20% of that = 70 million entries (an upper bound - many reads repeat the same link).
  3. Memory 70M x 500 B = about 35 GB.

What it changes: 35 GB fits in RAM on one large machine or a small Redis cluster (add replicas for availability). Because many reads repeat, the real unique hot set is smaller, so this is a safe ceiling. LRU eviction keeps the hot links in.

How to answer

Reads per day, hot fraction, entry size. Then say "fits in memory on a few nodes".

Likely follow-ups
  • One link goes viral at 50,000 reads/s. What now? (Hot key: local in-process cache and CDN.)
7. Servers: a checkout API expects 50,000 requests/s at peak during a sale. Assume one app server handles about 1,000 requests/s. How many servers, and what about the database? SDE-2
  1. App servers 50,000 / 1,000 = 50 servers. Never run at 100%: target about 60-70% utilisation, so about 75-80 servers, spread across availability zones so losing one zone still leaves enough.
  2. Database if each checkout does 3 writes, that is 150,000 writes/s - far above what one relational primary handles (thousands to tens of thousands per second, roughly).
  3. So shard the order data, move non-critical writes to a queue, and protect the database with a rate limiter or a waiting room.

What it changes: the app tier scales easily (stateless, add pods); the database is the real bottleneck. This is the core of Flash Sale design.

How to answer

Divide, add headroom, then multiply out to the database to find the real bottleneck.

Likely follow-ups
  • How do you know a server handles 1,000/s? (Load test it; it is never a guess in production.)
  • How fast can Kubernetes add 30 more pods? (Pre-scale for known events; autoscaling lags.)
8. Kafka sizing: 100,000 click events/s at 1 KB each, kept 7 days, replication factor 3. Disk needed, and how many partitions if one consumer handles about 5 MB/s? SDE-2
  1. Ingress 100,000 x 1 KB = 100 MB/s into the cluster.
  2. Retention 100 MB/s x 86,400 x 7 = about 60 TB; x3 replicas = about 180 TB of broker disk (plus headroom, say 30-50%).
  3. Partitions 100 MB/s / 5 MB/s per consumer = 20 consumers in parallel, so at least 20 partitions; plan about 3x for growth, so around 60. Choose the number up front, because adding partitions later changes which partition a key maps to.
  4. Network replication adds 2x the ingress between brokers (200 MB/s), and each consumer group reads another 100 MB/s.

What it changes: disk, not CPU, usually sizes a Kafka cluster with long retention; tiered storage (offloading old segments to object storage) can cut it. See Operations, Tuning & Kafka on K8s and Ad Click Aggregator.

How to answer

Ingress, retention x replicas, partitions from consumer throughput, then network.

Likely follow-ups
  • Why not 1,000 partitions "to be safe"? (More files, more memory, slower leader elections and rebalances.)
