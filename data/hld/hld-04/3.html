The five formulas Must know

Almost every estimate uses just these. Write the assumption on the board before each one.

  1. Average QPS = daily active users (DAU) x actions per user per day / 10^5 seconds. (QPS = queries, or requests, per second.)
  2. Peak QPS = average x peak factor. Rule of thumb: 2-3x for normal consumer apps; flash sales, ticket launches and campaigns can be 10-100x. Always say which you assume.
  3. Storage = new items per day x size per item x days kept x replication factor (often 3).
  4. Bandwidth = QPS x payload size. Compute ingress (writes coming in) and egress (reads going out) separately - egress is usually much bigger.
  5. Cache memory = daily reads x fraction that is hot (often 20%, the "80/20 rule") x size per item.

And one more for capacity: servers needed = peak QPS / QPS one server can handle, plus spare servers so you survive losing some (N+1 or N+2). What one server can handle depends hugely on the work per request, so always say it as an assumption.

Ballpark single-node capacityOrder of magnitude (planning only)
Well-tuned Postgres or MySQL primary, simple writesThousands to tens of thousands per second
Redis node, simple operationsRoughly 100k+ per second
Kafka broker, sequential writesHundreds of MB per second

Careful: these are not benchmarks. Say "roughly" and "order of magnitude", and let the interviewer correct you. Never present a planning number as a measured fact.

Little's Law: how many requests are in flight?

QPS tells you how many requests arrive each second. It does not tell you how many are being worked on at the same moment, and that second number is what sizes thread pools, database connection pools and memory. Little's Law connects them:

L = λ x W   (requests in flight = arrival rate x time each request spends in the system)

  1. Example. A checkout API takes 50,000 requests/s at peak, and each request takes 20 ms end to end. In flight: 50,000 x 0.020 s = 1,000 requests at once.
  2. So the pools must hold that. If every request holds one DB connection for its whole 20 ms, the fleet needs about 1,000 connections (plus headroom). Spread over 50 app servers that is 20 per server, a sensible pool size.
  3. Now the DB slows down. If latency goes from 20 ms to 200 ms (a slow query, a failover), in-flight jumps to 50,000 x 0.2 = 10,000. The pools run dry, new requests wait, latency rises further - a feedback loop. This is why timeouts and load shedding exist.

From your world

You already use this law: average buffer occupancy = packet rate x time each packet spends queued. The TCP bandwidth-delay product is the same idea in bytes: a 10 Gbps link with a 50 ms RTT needs about 10e9 / 8 x 0.05 = 62.5 MB in flight to stay full, so the window must be at least that big. A connection pool is a TCP window for database calls. Where this breaks: Little's Law is about long-run averages in a steady state. Real traffic is bursty and latency has a tail, so size for peak arrival rate and roughly p99 latency, not the averages, or the pool runs out exactly when it matters.

The recipe, step by step

Click Next to watch one estimate grow on the board. The example is a photo-sharing app with 10 million daily users.

  1. Start from users. Write down the assumption: 10 million daily active users, each uploads one photo a day.
  2. Average write QPS. 10 million per day divided by about 86,400 seconds is about 116 per second. Tiny for writes.
  3. Peak and reads. Peak at 3x is about 350 writes per second. If each photo is viewed 100 times, reads are about 11,600 per second on average and about 35,000 at peak. This is read-heavy: caching and a CDN will matter.
  4. Storage. 10 million photos x 2 MB = 20 TB a day. Over 5 years with 3 copies: about 110 PB. That will never fit in a database - it is object storage (like S3).
  5. Bandwidth. Ingress is about 116 x 2 MB, roughly 230 MB per second. Egress for 35,000 reads per second of thumbnails and photos is much larger, which is why a CDN serves them.
  6. Say the decision. The numbers told us: photos go to object storage behind a CDN; metadata (a few hundred bytes per photo) fits in a normal database; the metadata read path needs a cache.

Here is the same estimate as a tiny script, so you can play with the assumptions:

# estimate.py - back-of-envelope helper (assumptions are inputs, not facts)
DAY = 86_400

def human(n, unit=""):
    for suffix, size in (("P", 1e15), ("T", 1e12), ("G", 1e9), ("M", 1e6), ("K", 1e3)):
        if n >= size:
            return f"{n / size:,.1f} {suffix}{unit}"
    return f"{n:,.1f} {unit}"

def estimate(dau, actions_per_user, bytes_per_action, read_ratio, peak_factor, years, replicas):
    writes_day = dau * actions_per_user
    write_qps = writes_day / DAY
    read_qps = write_qps * read_ratio
    storage = writes_day * bytes_per_action * 365 * years * replicas
    print(f"writes/day      {human(writes_day)}")
    print(f"write QPS       {write_qps:,.0f} avg, {write_qps * peak_factor:,.0f} peak")
    print(f"read QPS        {read_qps:,.0f} avg, {read_qps * peak_factor:,.0f} peak")
    print(f"ingress         {human(write_qps * bytes_per_action, 'B/s')}")
    print(f"storage         {human(storage, 'B')} over {years} years x{replicas} copies")

# a photo-sharing app: 10M DAU, 1 upload each/day, 2 MB per photo, 100 reads per write
estimate(dau=10e6, actions_per_user=1, bytes_per_action=2e6,
         read_ratio=100, peak_factor=3, years=5, replicas=3)
