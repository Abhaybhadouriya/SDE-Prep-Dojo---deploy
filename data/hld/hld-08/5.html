Block, file and object storage

ByteByteGo's storage overview gives the three layers. Block storage is raw disk blocks given to one server (a local SSD, an EBS volume, an iSCSI LUN); databases sit on it. File storage adds directories and is shared over NFS or SMB. Object storage (S3, Azure Blob, GCS) throws away directories and in-place edits: you PUT and GET whole immutable objects by key over HTTP. It trades latency for huge scale, durability and low cost.

The golden rule for every design with photos or video (d13, d24, d12): bytes go in object storage, metadata goes in a database, and clients upload straight to the object store with a pre-signed URL so your API servers never carry the bytes. The full pattern is p06 Handling Large Blobs.

How S3 stays durable: erasure coding

Copying every object three times costs 3x the disk. Object stores instead use erasure coding: split the object into k data shards, compute m parity shards (Reed-Solomon), and spread the k + m shards across different drives. Any k shards rebuild the object. Amazon's S3 blog says objects are encoded across tens of drives, and that a single bursty customer can be served by over a million disks because data is spread so widely.

Two more numbers from that S3 post that make good interview colour: a hard drive still does only about 120 random I/Os per second, roughly the same as in 2006, while drives have grown to 26 TB. So S3 is designed around heat (requests per disk), spreading every customer's data thinly across the fleet so no single disk gets hot. Its durability target is the famous "11 nines". HDFS, the Hadoop file system, uses the same ideas for analytics data: big blocks, three replicas or erasure coding, a central NameNode for metadata (hld-12).

From your world

Erasure coding is RAID 6 spread across a data centre instead of one disk shelf, and it is the same maths as forward error correction on a lossy link: send k packets plus m repair packets, and the receiver rebuilds from any k. The "heat" problem is ECMP hashing: you spread flows so no single link (disk) is saturated.

Where this breaks: FEC repairs a packet in microseconds on the same link, but rebuilding a lost 20 TB disk from k other disks across a data centre takes hours of network bandwidth, which is why S3-like systems also care about repair traffic, not just durability maths.

Row stores vs column stores

OLTP (online transaction processing) databases like Postgres store each row together: perfect for "load order 7". OLAP (online analytical processing) databases like ClickHouse store each column together: perfect for "sum revenue by country for last month over 2 billion rows", which touches 3 columns out of 40.

ClickHouse adds a sparse primary index: data is sorted by the primary key and the index keeps one entry ("mark") per granule of 8,192 rows. In the ClickHouse docs example, 8.87 million rows need just 1,083 marks (about 97 KiB, easily in RAM); a lookup binary-searches the marks and reads one granule of about 8,000 rows instead of the whole table. Inserts create new immutable parts that merge in the background (an LSM idea again), so batch your inserts.
