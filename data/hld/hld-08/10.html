Interview questions

SQL or NoSQL for a new service? How do you decide in an interview?

Start from requirements, not fashion. If the data is relational and correctness matters (orders, payments, bookings), or the queries are not fully known, choose a relational database: it gives transactions, constraints and ad-hoc SQL, and one well-tuned Postgres node handles far more than most interview prompts at the start. Move to NoSQL when a specific number forces it: write throughput beyond a single primary, a key-only access pattern at massive scale, a need for multi-region always-writable data, or a data shape (documents, time-series, text search) that a specialised store handles much better.

How to answer

Name the default, then name the trigger that would make you switch, then name the cost of switching (no joins, query-driven tables, eventual consistency).

Likely follow-ups
  • At what QPS would Postgres stop being enough, and what would you do first? (Read replicas, cache, then sharding: p05.)
  • What does "NoSQL" actually give up?
  • Can you use both? (Yes: polyglot with CDC.)
Which database would you use to store chat messages for WhatsApp or Slack, and what is the key?

Messages are append-heavy, almost never updated, and read as "latest N in conversation X". That is a wide-column/LSM workload: Cassandra, ScyllaDB or DynamoDB. Primary key ((conversation_id, time_bucket), message_id), clustering descending on a time-ordered Snowflake ID. The bucket bounds partition size. Discord did exactly this and moved from 177 Cassandra nodes to 72 ScyllaDB nodes with p99 reads at 15 ms. Keep users, groups and membership in a relational DB; attachments in S3.

How to answer

Workload first (append, range read), then the store family, then the exact key, then the failure mode (hot partitions for huge groups, compaction).

Likely follow-ups
  • How do you handle a 100k-member channel that is a hot partition?
  • How do you search old messages? (Separate Elasticsearch index via CDC.)
  • How do you delete messages and what are tombstones?
When is Redis the wrong choice as a primary database?

When losing recent writes is unacceptable or the data does not fit in RAM. By default Redis persists with periodic RDB snapshots, so a crash can lose minutes of writes; with AOF enabled, the default appendfsync everysec can still lose about 1 s, and replication is asynchronous either way, so a failover can lose acknowledged writes. appendfsync always exists but costs throughput. There are no joins or cross-key queries, and multi-key operations need keys in the same hash slot. So: Redis for caches, counters, rate limits, leaderboards, sessions and locks you can rebuild; a durable database for money, orders and anything audited.

How to answer

Give the durability fact, the memory fact, and the query fact, then list what it is great for.

Likely follow-ups
  • Your leaderboard lives in Redis. What happens if the node dies? (Rebuild from the score events in Kafka or the DB.)
  • Is a Redis lock safe for payments? (Only with fencing tokens; see d55.)
  • How do you handle a hot key?
Design storage for a product catalog with search (Flipkart / Amazon).

Three stores. (1) Source of truth: products, sellers, prices and stock in a relational DB (or a document store for variable attributes), because price and stock changes need correctness. (2) Search: an Elasticsearch index of denormalized product documents (title, brand, category, attributes, price, rating) for full-text, facets and ranking, fed by CDC through Kafka, roughly one second behind. (3) Images in S3 behind a CDN. Add Redis for hot product pages. The product page reads truth for price and stock at checkout; search results may be a second stale.

How to answer

Split by job: truth, search, bytes, cache. State the sync path and the staleness you accept, and where you re-check (checkout).

Likely follow-ups
  • A flash sale changes stock 10,000 times a second. Do you reindex every change? (No: keep stock out of the index or only index in-stock flags.)
  • How do you reindex the whole catalog without downtime? (Build a new index, switch an alias.)
  • See d49.
How would you store metrics for a monitoring system like Prometheus or Datadog?

A time-series database. Example load from Hello Interview: 100,000 servers x 5 metrics every 10 s = 50,000 points/s, about 4.3 billion points a day. Store series as metric name + tags, append into time-partitioned blocks, compress with delta-of-delta timestamps and XOR floats (about 1.37 bytes per (timestamp, value) point instead of 16, roughly 12x), keep rollups (10 s for a day, 1 min for a week, 1 h for a year), and expire whole blocks for retention. Guard cardinality: never use user ids as tags.

How to answer

Estimate the write rate, name the TSDB tricks (append, compress, partition, roll up), then name the cardinality limit.

Likely follow-ups
  • How do you answer "top 10 hosts by CPU across 1 million series"? (A columnar store or pre-aggregation.)
  • How do you make ingest survive a TSDB outage? (Buffer through Kafka.)
  • See d20.
You chose DynamoDB. One partition key is being throttled even though the table has spare capacity. Why, and what do you do?

Capacity is per partition: about 3,000 read units and 1,000 write units per second per partition. A single hot key (a celebrity, a flash-sale item, a date used as partition key) cannot use the table's total capacity. Fixes: add a random or computed suffix to spread writes across N keys (write sharding) and read all N on query; cache reads with DAX; aggregate writes in memory or a stream before writing; or redesign the key so traffic is naturally spread (user_id instead of date).

How to answer

State the per-partition limit, name the hot key, give write sharding and caching, and the cost (scatter reads).

Likely follow-ups
  • GSI vs LSI: which would you add for "orders by status"?
  • Can you do a transaction across 3 items? (Yes, up to 100 items.)
  • How is this the same problem as a hot partition in Cassandra?
Why is Elasticsearch not used as the primary database? How do you keep it in sync?

It is a search engine: writes become visible only after a refresh (1 s by default), updates are delete-plus-insert in immutable segments, there are no multi-document transactions, and historically it had durability issues. So the truth lives in Postgres or DynamoDB and Elasticsearch holds a denormalized, rebuildable copy. Sync with CDC (Debezium on the WAL, or DynamoDB Streams) into Kafka, with an idempotent indexer keyed by document id and version. Never dual-write from the app. Keep the ability to rebuild the whole index from the source and swap an alias.

How to answer

Three reasons it is not the truth, then the CDC pipeline, then idempotency and rebuild.

Likely follow-ups
  • What if CDC events arrive out of order? (Use the source version or LSN; ignore older versions.)
  • How stale can results be and is that OK for the product?
  • See d28 and d38.
Design storage for user-uploaded videos and photos. Why not store them in the database?

Databases are built for small records with indexes, transactions and replication of every byte to every replica; multi-MB blobs bloat backups, replication and buffer caches. Object storage is cheaper per GB, erasure-coded for durability (any k of k+m shards rebuild the object, so about 1.5x overhead instead of 3x for copies), and scales to millions of disks. So: the client asks the API for a pre-signed URL, uploads straight to S3 (multipart for big files), S3 emits an event, a worker transcodes; the database stores only metadata and the object key; reads go through a CDN.

How to answer

Split bytes from metadata, explain direct upload, mention durability and CDN.

Likely follow-ups
  • How do you resume a failed 2 GB upload? (Multipart upload.)
  • How do you delete a user's files for privacy requests?
  • See p06 and d13.
Your analytics queries on the OLTP Postgres are slowing down checkout. What do you do?

Separate OLTP from OLAP. Short term: route reports to a read replica so they cannot block the primary. Proper fix: stream changes (CDC to Kafka) into a columnar store such as ClickHouse, Druid or BigQuery, where an aggregate over billions of rows reads only the needed columns, compressed, using vectorized execution. ClickHouse's sparse index needs one entry per 8,192 rows, so the index stays in memory even for huge tables. Dashboards read the columnar store; checkout keeps the primary to itself.

How to answer

Name the conflict (long scans vs short transactions), give the quick fix, then the architectural fix and why columnar is faster.

Likely follow-ups
  • How fresh do dashboards need to be?
  • Why are many small inserts bad for ClickHouse?
  • See d21.
Do you need a graph database to store a social network's follow graph?

Usually not. Feeds and profiles need one-hop queries: who do I follow, who follows me, do I follow X. A sharded table of edges (src_id, type, dst_id, created_at) with an inverse edge table (or index) serves these, plus a cache. That is what Facebook's TAO does on MySQL, at over a billion reads per second. A graph database earns its place when queries walk several hops at request time (mutual friends of friends, fraud rings), and even then many teams run those offline in batch.

How to answer

Separate one-hop from multi-hop, cite TAO, say when you would add a graph DB.

Likely follow-ups
  • How do you shard the edge table: by src or dst? (Both: keep two copies.)
  • How do you handle a celebrity with 100 million followers? (p08.)
Add semantic search ("find similar documents") to an existing product. Which store?

Generate embeddings for each document with a model, store them next to the data, and build an ANN index. Size it first: 1,536 dimensions x 4 bytes is about 6 KB per vector, so 10 million documents is about 60 GB raw, and the HNSW graph adds only a few percent on top (the vectors themselves are the RAM problem, so consider int8 quantisation to cut them 4x). At that size pgvector (if the data already lives in Postgres) or Elasticsearch kNN (if you also need keyword search and filters together) is fine; past roughly 100 million vectors consider a dedicated vector DB. Tune recall vs latency (HNSW typically gives 95%+ recall), decide pre- vs post-filtering for tenant or permission filters, and plan re-embedding when the model changes.

How to answer

Embeddings, sizing maths, ANN algorithm, product choice by size, filtering and re-indexing.

Likely follow-ups
  • How do you combine keyword and vector scores? (Hybrid search.)
  • How do you handle fresh inserts in HNSW? (Small hot index plus a big cold index.)
  • See hld-17.
How does a MongoDB replica set fail over, and how can you still lose an acknowledged write?

Secondaries tail the primary's oplog and replay it in order. If they miss heartbeats from the primary for electionTimeoutMillis (10 s by default), one calls an election and the candidate with a majority of votes becomes primary; MongoDB says median failover should normally stay under about 12 s. Writes fail during that window, and drivers retry a write once. The loss case: with a weak write concern (w: 1) the old primary acknowledged a write that no secondary had copied yet. When it rejoins, that write is rolled back. w: "majority" prevents this because the write exists on a majority, and any new primary must come from that majority.

How to answer

Describe heartbeat, timeout, majority vote in three sentences, then name the rollback case and the fix (majority write concern). Mention that the oplog window decides how long a secondary can be offline before it needs a full resync.

Likely follow-ups
  • Why at most 7 voting members? (Elections need fast majority agreement; extra members can be non-voting.)
  • How do you index an array of tags? (A multikey index: one entry per element.)
  • Can a compound index cover two array fields? (No, at most one array per document.)
Elasticsearch or OpenSearch: does the choice change your design?

Not the architecture. Both are Lucene-based search clusters with shards, replicas, near-real-time refresh and the same "not the source of truth" rule; OpenSearch is a fork of Elasticsearch 7.10.2 made in 2021 after Elastic moved to the SSPL / Elastic License. The choice is about licence, hosting and features: OpenSearch is Apache 2.0, run by the OpenSearch Software Foundation and offered as Amazon OpenSearch Service, with security and alerting bundled; Elastic offers Elastic Cloud and newer features of its own, and since 2024 an AGPLv3 option. Their APIs have drifted since 7.10, so clients and some features are not interchangeable.

How to answer

Say "same design, different licence and vendor", give the one-line history, then pick based on where the team runs (AWS-managed: OpenSearch; Elastic Cloud or Elastic-only features: Elasticsearch).

Likely follow-ups
  • What is ISM vs ILM? (Index lifecycle tools of OpenSearch and Elastic.)
  • How would you migrate from one to the other? (Snapshot/restore within the compatible versions, or reindex from a new pipeline.)

Scenario: "Just use MongoDB for the payments service"

In a mock interview for a wallet (d41), the candidate picks MongoDB "because it scales" and stores each user's balance in their profile document. The interviewer asks how a transfer between two users stays correct.

Weak answer: "MongoDB has transactions too, so it is fine," with no mention of the ledger, idempotency or isolation.

Strong answer: money needs an append-only double-entry ledger where each transfer writes a debit and a credit atomically, plus constraints and an idempotency key. A relational database gives that directly with a transaction and a unique index on the idempotency key. Balances are derived (or updated in the same transaction with a guarded update). Scale by sharding on account id; cross-shard transfers use a saga with compensation (p03). Document stores are fine for user profiles, not for the ledger.

Likely follow-ups
  • What isolation level for the transfer? (hld-07.)
  • How do you reconcile with the bank every night?

Scenario: the search index is showing deleted products

Your catalog writes to Postgres and then calls Elasticsearch from the same request handler. Customers see products that were taken down hours ago, and a few new products never appear in search.

Weak answer: "Add a retry around the Elasticsearch call" or "lower the refresh interval".

Strong answer: this is the dual-write problem; the second write fails or lands out of order and nothing repairs it. Replace it with CDC: Debezium reads the Postgres WAL and publishes to Kafka; an idempotent indexer applies changes by product id, ignoring versions older than what it has. Deletes become delete events. Add a nightly reconciliation that compares counts or checksums, and keep a full rebuild path (new index plus alias swap). The refresh interval was never the issue.

Likely follow-ups
  • How do you backfill the index the first time?
  • What lag do you alert on?

The 60-second answer. "I choose storage from three things: the shape of the data, the access pattern, and the guarantee needed. Money, bookings and inventory go in a relational database like Postgres for transactions and constraints. Huge append-heavy data read by key and time, like chat messages, goes in a wide-column LSM store like Cassandra or DynamoDB. Hot derived data goes in Redis, which I can lose and rebuild. Full-text search goes in Elasticsearch fed by CDC, never as the source of truth. Blobs go in S3 behind a CDN, analytics in a columnar store, and embeddings in pgvector until about 100 million vectors. One source of truth, everything else derived through an outbox or CDC."
