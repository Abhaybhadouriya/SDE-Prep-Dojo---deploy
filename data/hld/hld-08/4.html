Graph, time-series, search and vector stores

Graph databases

A graph database stores nodes (a user, a page) and edges (follows, likes) as first-class things, so walking "friends of friends who live in Pune" is a pointer chase instead of a chain of self-joins. Neo4j and Amazon Neptune are the usual names.

The interesting fact for interviews: the largest social graph in the world does not run on a graph database. Facebook's TAO stores objects and associations (typed, directed edges, each with a time) in sharded MySQL, with a write-through cache tier in front. It serves over a billion reads and millions of writes per second. Most "social graph" designs need one-hop queries (my followers, my likes), which a sharded table with (src_id, edge_type, created_at) serves perfectly. Reach for a true graph DB when the product needs multi-hop traversal at query time: fraud rings, recommendations by path, knowledge graphs.

Time-series databases

A time-series database (TSDB) stores streams of (series, timestamp, value). A series is a metric name plus tags, like cpu{host="web-1"}. Hello Interview's TSDB deep dive gives a concrete load: 100,000 servers emitting 5 metrics every 10 seconds is 50,000 writes per second and about 4.3 billion points a day. In a naive Postgres row each point costs 50-100 bytes; the real data is about 16 bytes (a timestamp and a float).

TSDBs win with four tricks:

  1. Append-only LSM writes. Points arrive in time order, so writes are sequential.
  2. Compression. Timestamps use delta-of-delta encoding (regular intervals cost almost nothing) and floats use XOR against the previous value, from Facebook's Gorilla paper: about 1.37 bytes per (timestamp, value) point instead of 16, roughly 12x smaller.
  3. Time partitions. One block or chunk per day. Retention means dropping whole files, not running giant DELETEs.
  4. Rollups. Keep 10-second data for a day, 1-minute averages for a week, 1-hour averages for a year. A 5-minute rollup has 30x fewer points than 10-second raw data (288 points per series per day instead of 8,640).

The cardinality trap. Every unique tag combination is a series with an in-memory index entry. 1,000 hosts x 50 metrics = 50,000 series: fine. Add a user_id tag with 10 million users and you could create 500 billion series and run out of memory. High-cardinality values (user ids, request ids) belong in logs or a columnar store, not in TSDB tags. This is the core trap in d20 Metrics & Monitoring.

From your world

You already know time-series: SNMP interface counters polled every 30 seconds, or /proc/net/dev sampled by a collector. Delta-of-delta encoding is the same idea as storing counter increments instead of absolute values. Rollups are what RRDtool did for MRTG graphs on every router you ever monitored.

Where this breaks: SNMP counters have a fixed, small set of interfaces; a metrics database must handle unbounded label combinations (cardinality), and one careless tag such as user id can create millions of series and take it down.

Search engines and the inverted index

A search engine like Elasticsearch builds an inverted index: for each word (token), the list of documents that contain it, called a postings list. A query for "red shoes" fetches two postings lists and intersects them, instead of scanning every product.

Facts worth saying out loud: each Elasticsearch shard is one Lucene index made of immutable segments; an update is a soft delete plus a new insert, so updates cost more than inserts; new documents become searchable after a refresh, every second by default (near real time, not instant); sorting and aggregations use doc values, a per-field columnar store; and deep from/size paging gets expensive past about 10,000 results. Most important: Hello Interview's deep dive is blunt that Elasticsearch should not be your primary database. Keep the truth in Postgres or DynamoDB and feed the index through change data capture (CDC). Prefix and geo indexes get their own page: hld-15.

Vector databases

An embedding is a list of numbers that captures meaning, produced by a model. Similar items have nearby vectors. A vector database answers "give me the 10 nearest vectors to this one". Exact search compares against everything: for 1 million vectors of 1,536 dimensions that is about 1.5 billion multiply-adds (about 3 billion floating-point operations) per query. So vector stores use approximate nearest neighbour (ANN) indexes:

  • HNSW (Hierarchical Navigable Small World): a layered graph you walk greedily from the top. Typically 95%+ recall, roughly O(log n) search. The graph links add roughly M x 2 x 4 bytes per vector (about 0.1-0.3 KB at the common M=16), small next to a 6 KB 1,536-dim vector; the real memory cost is that the full vectors must stay in RAM for fast search, which is why int8 or binary quantisation is common. The most common production choice.
  • IVF (inverted file): cluster vectors with k-means, search only the nearest few clusters (nprobe). Builds faster, uses less memory, usually lower recall at the same latency.

Sizing in one line: a 1,536-dim float32 vector is about 6 KB, so 1 million vectors is about 6 GB raw and about 6.2-6.5 GB with the HNSW graph on top (the links add a few percent). Hello Interview's rule of thumb is that pgvector or Elasticsearch kNN is fine until roughly 100 million vectors; past that, look at purpose-built systems (Milvus, Pinecone, Qdrant). Retrieval-augmented generation (RAG) is covered in hld-17 and d47.
