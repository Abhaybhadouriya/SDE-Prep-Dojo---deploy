PostgreSQL: the default answer

Model: relational tables, B-tree indexes by default (plus GIN, GiST, BRIN), MVCC, a write-ahead log. Default isolation is Read Committed; Serializable uses SSI. Extensions make it multi-model: JSONB columns, PostGIS for geo, pgvector for embeddings, Timescale for time-series, built-in full-text search.

Use when: you need transactions, constraints (unique, foreign keys, exclusion), joins, and ad-hoc queries. Bookings, payments, users, orders, inventory. Instagram, Reddit and Figma all scaled on it (Figma by sharding it horizontally).

Watch out: one process per connection, so you put a pooler (PgBouncer) in front; an update writes a whole new row version, and with many secondary indexes every update touches every index (the write amplification Uber described when it moved to MySQL); long transactions cause bloat until VACUUM runs. Scaling writes beyond one primary means sharding (Citus, app-level) or a distributed SQL system.

MySQL (InnoDB)

Model: relational, InnoDB engine with a clustered primary key: rows live inside the PK B-tree, and secondary indexes store the primary key, so a secondary lookup is two B-tree walks. Default isolation is Repeatable Read with gap and next-key locks; old versions live in the undo log.

Use when: same OLTP sweet spot as Postgres. Netflix uses MySQL for billing, subscriptions and revenue; Facebook's TAO graph sits on sharded MySQL; Uber moved its Schemaless store from Postgres to MySQL citing cheaper secondary-index updates and replication.

Watch out: random UUID primary keys fragment the clustered index (use time-ordered IDs, see d31); large schema changes need online-DDL tools; sharding is manual (Vitess is the common answer).

Redis: in-memory data structures

Model: keys mapping to strings, hashes, lists, sets, sorted sets, streams, geo indexes, bitmaps, HyperLogLog. Commands run one at a time on a single thread (no locks needed inside a command); ByteByteGo's three reasons it is fast are RAM, I/O multiplexing on one event loop, and efficient data structures.

Numbers: roughly 100k writes/s per node and sub-millisecond reads (Hello Interview). Redis Cluster splits keys into 16,384 hash slots; clients cache the slot map and follow MOVED redirects. Hash tags like {user:123} force related keys into one slot so multi-key commands work.

Use for: cache, sessions, rate limiters (INCR + EXPIRE in Lua), leaderboards (sorted sets, d22), nearby search (GEOSEARCH), short-lived locks (SET key token NX EX 30), lightweight queues.

Watch out: data must fit in RAM; by default Redis persists only with periodic RDB snapshots, so a crash can lose minutes of writes; with AOF turned on (appendonly yes), the default appendfsync everysec can lose about 1 s; replication is asynchronous either way; Pub/Sub is at-most-once with no persistence; hot keys overload one node. It is not a system of record unless you accept those losses.

From your world

Redis's core loop is an epoll event loop on one thread, exactly like a high-performance packet daemon: no locks, no context switches, everything in cache-friendly memory. Hash slots are like ECMP buckets: hash the key, map the bucket to a next hop (node), move buckets to rebalance.

Where this breaks: ECMP rehashing just moves flows; moving a Redis hash slot means copying its keys to the new node while clients follow redirects, so resharding is slow and visible, not instant.

Apache Cassandra (and ScyllaDB)

Model: wide-column, PRIMARY KEY ((partition key), clustering keys); LSM storage (commit log, memtable, SSTables, compaction, tombstones for deletes); consistent-hash ring with virtual nodes; leaderless replication with tunable consistency (ONE, QUORUM, ALL); gossip for membership and a phi-accrual failure detector; NetworkTopologyStrategy for rack and data-centre aware replicas.

Use when: very high write throughput, availability over strict consistency, access patterns known up front. Netflix calls it its default for viewing history, user and device data; Discord stored trillions of messages in it.

Watch out: no joins and no multi-partition transactions (atomicity only within a partition); one table per query; unbounded partitions (bucket by time); tombstone build-up from deletes; compaction debt. ScyllaDB is a C++ rewrite with the same model and no JVM pauses.

Amazon DynamoDB

Model: managed key-value and document store, partition key (hashed) plus optional sort key (range within a partition). Items up to 400 KB. Data is replicated across three Availability Zones automatically; Global Tables add multi-region replication.

Numbers: each partition serves up to 3,000 read units and 1,000 write units per second (about 12 MB/s reads, 1 MB/s writes), so a hot partition key throttles no matter how big the table is. Up to 20 Global Secondary Indexes (own partitions, eventually consistent) and 5 Local Secondary Indexes (same partition key, strongly consistent, defined at creation, 10 GB per partition key value). Transactions cover up to 100 items across tables. Strongly consistent reads cost twice as much as eventually consistent ones.

Use when: you want single-digit-ms latency at any scale with no servers to run, and you know your access patterns. DAX adds a microsecond read cache; DynamoDB Streams provide CDC to Lambda or Elasticsearch.

Watch out: ad-hoc queries and aggregations (Scan is a full read); cost at very high volume; vendor lock-in; leaning on many GSIs often means you wanted Postgres. Ask the interviewer whether managed AWS services are allowed.

MongoDB

Model: document store of BSON documents in collections, B-tree indexes (WiredTiger engine), replica sets with a primary and secondaries, sharding by a shard key (ranged or hashed). Limits: 16 MiB per document, 100 nesting levels, 64 indexes per collection.

Use when: entities are read and written as a whole and their fields vary: product catalogs (d49), CMS content, user profiles, game state. "Store together what is read together."

Watch out: unbounded arrays inside documents (embed the 5 newest reviews, reference the rest); choosing a monotonically increasing shard key makes one hot shard; heavy many-to-many relationships push joins into code. Single-document writes are atomic; multi-document transactions exist but cost more.

Replica sets, the oplog and elections

A replica set is one primary plus secondaries holding the same data (up to 50 members, at most 7 of them voting). All writes go to the primary. The primary records every change in the oplog (local.oplog.rs), an ordered, fixed-size (capped) collection. Each secondary tails that oplog and replays the entries in order. Oplog entries are written so that replaying one twice gives the same result (an $inc becomes "set the field to 6"), which makes catch-up after a hiccup safe. If a secondary falls further behind than the oplog holds (the oplog window), it cannot catch up and needs a full initial sync.

Members send each other heartbeats. If secondaries cannot reach the primary for electionTimeoutMillis (10 seconds by default), one of them calls an election; the candidate that wins votes from a majority becomes primary. MongoDB's docs say the median failover should not normally exceed about 12 seconds. During that gap writes fail; reads can continue only if you allow reads from secondaries. Drivers retry a failed write once by default (retryable writes), which hides most short failovers.

  1. Normal life: the app writes to primary A; B and C pull oplog entries and replay them in order.
  2. A dies. Writes now fail because there is no primary.
  3. After electionTimeoutMillis (10 s by default) without a heartbeat, B asks the others for votes.
  4. B wins a majority (2 of 3) and becomes primary. Drivers find it and retry the failed write once.
  5. When A returns it becomes a secondary. Any write it had accepted but never replicated to a majority is rolled back. Use w: "majority" for writes you cannot lose.

Indexing nested fields and arrays (multikey indexes)

Documents nest, so indexes must too. You index a field inside an embedded document with dot notation, and if the indexed field holds an array, MongoDB creates a multikey index: one index entry per array element. A query for one tag then finds the document straight from the index.

db.products.insertOne({ sku: "P1", tags: ["shoe", "running", "sale"], seller: { city: "Pune", rating: 4.6 } })
db.products.createIndex({ tags: 1 })                          // multikey: 3 index keys for P1
db.products.createIndex({ "seller.city": 1, "seller.rating": -1 })  // nested fields
db.products.find({ tags: "running" }).explain("queryPlanner")
// excerpt of the winning plan
stage: 'IXSCAN',
keyPattern: { tags: 1 },
indexName: 'tags_1',
isMultiKey: true,
multiKeyPaths: { tags: [ 'tags' ] },

Watch out: a compound index may contain at most one array field per document (two arrays would mean a cross product of keys, so MongoDB refuses the insert or the index build); a document with a 1,000-element array adds 1,000 index keys, so large arrays make writes slow; and schema-less does not mean schema-free: use JSON Schema validation ($jsonSchema) on the collection so one buggy service cannot write a different shape.

From your world

The oplog is the same idea as a write-ahead log or the MySQL binlog, and a secondary tailing it is a follower replaying a journal. Elections are VRRP with a quorum: VRRP lets the highest-priority backup take the virtual IP after missed adverts, but MongoDB also demands a majority vote, so a node cut off on the minority side of a partition can never become a second primary (no split brain).

Elasticsearch / OpenSearch

Model: JSON documents indexed into an inverted index (Lucene). An index is split into shards, each a Lucene index of immutable segments, with replicas for availability and read throughput. Queries fan out to shards and a coordinating node merges results.

Numbers: refresh every 1 second by default, so writes become searchable in about a second; deep paging beyond about 10,000 hits needs search_after; Hello Interview suggests you may not need it at all under about 100k documents.

Use for: full-text search, autocomplete, faceted filters, log search (d19), geo queries, hybrid keyword + vector search.

Watch out: not a source of truth (eventual, can be noticeably stale); frequent updates are expensive (delete + reinsert); denormalize documents so one query answers the screen; sync drift from the primary DB through CDC is the classic bug.

Why OpenSearch exists: the 2021 licence fork

Elasticsearch and Kibana were Apache 2.0 licensed until early 2021. In January 2021 Elastic moved new versions (from 7.11) to a choice of the Server Side Public License (SSPL) or the Elastic License, mainly to stop cloud providers selling Elasticsearch as a managed service without a deal with Elastic. Neither licence is approved by the Open Source Initiative. AWS answered by forking the last Apache 2.0 releases, Elasticsearch 7.10.2 and Kibana 7.10.2, into OpenSearch and OpenSearch Dashboards; OpenSearch 1.0 became generally available in July 2021, still under Apache 2.0. In August 2024 Elastic added the AGPLv3 as a third licence option, and in September 2024 AWS moved OpenSearch to the new OpenSearch Software Foundation under the Linux Foundation.

Mention the fork only when cost, licence or "we are on AWS" comes up, or when the interviewer asks why a team runs OpenSearch. Amazon S3 (object storage)

Model: buckets of immutable objects addressed by key, accessed over HTTP. Launched in 2006, built from millions of hard disks and hundreds of microservices; erasure-coded across tens of drives; designed for 11 nines of durability. The bottom layer that manages each disk, ShardStore, was rewritten in Rust and checked against a small executable specification on every commit.

Use for: images, video segments, user uploads, backups, logs, and the data lake under analytics (Netflix keeps almost all images, video, metrics and logs in S3, with Apache Iceberg tables on top).

Watch out: no partial updates or appends (replace the object or use multipart upload); per-request latency in tens of milliseconds, so put a CDN in front for reads; listing millions of keys is slow, so keep an index of objects in your own database. Design one yourself in d36.

ClickHouse (columnar OLAP)

Model: column-oriented MergeTree tables sorted by a primary key; sparse index with one mark per 8,192-row granule; every INSERT writes a new part, merged in the background; per-column compression codecs (Delta, Gorilla, ZSTD); vectorized execution that processes batches of rows with SIMD and splits a query into one lane per CPU core.

Use for: analytics over billions of events: ad-click aggregation (d21), product analytics dashboards, observability backends, top-K reports (d35). Aggregating merges can pre-compute rollups at merge time.

Watch out: many tiny inserts create many parts (batch them, or buffer through Kafka); single-row updates and deletes are heavy; it is not an OLTP database. Druid, Pinot, Redshift and BigQuery sit in the same family.
