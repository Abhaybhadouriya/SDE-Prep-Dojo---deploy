Polyglot persistence: keeping many stores in sync

Polyglot persistence means using several data stores in one system, each for what it does best. Netflix is the cleanest public example: MySQL for billing, Cassandra as the default for user data and viewing history, EVCache (on Memcached) for caching the homepage, Atlas for metrics, Druid and Redshift for analytics, and S3 for almost all files.

The hard part is not picking stores; it is keeping them consistent. Never "dual write" from the app (write Postgres, then write Elasticsearch): if the second write fails, the copies silently diverge. Instead write once to the source of truth and stream its changes out.

This is the transactional outbox and CDC story from hld-10, and the full pipeline is designed in d28 CDC Pipeline. Flipkart's AESOP change-propagation system and DynamoDB Streams are real examples of the same idea. The Kafka side (Connect, Debezium) is in Kafka Connect & Streams.

Running stateful stores on Kubernetes

Databases need stable names and their own disks, which is what a StatefulSet gives: pods cassandra-0, cassandra-1 keep their identity and their PersistentVolumeClaim across restarts (StatefulSets & Operators, K8s Storage). In practice teams run Postgres, Cassandra and Kafka through operators (CloudNativePG, K8ssandra, Strimzi) or pick a managed service. In an interview, "managed RDS / DynamoDB unless we have a reason" is a fine answer; for local development, one Docker Compose file with Postgres, Redis and Kafka mirrors the stack.
