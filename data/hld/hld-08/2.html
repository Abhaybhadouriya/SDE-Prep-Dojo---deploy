Key-value and document stores

A key-value store is the simplest database: you give a key, you get a value. The store does not look inside the value. Reads and writes are O(1). The System Design Primer calls its abstraction "hash table" and notes that all extra query power has to move into your application code.

A document store is a key-value store that does understand the value. The value is a JSON-like document, and you can index and query fields inside it. MongoDB's data modeling guide sums up the rule in one line: data that is accessed together should be stored together. So an order document holds its line items, and the product page reads one document instead of joining five tables.

When documents win and when they hurt

Pros
  • One read returns the whole entity: no joins on the hot path.
  • Flexible fields: product catalogs where a TV and a T-shirt have different attributes.
  • Shards naturally by document id.
Cons
  • Duplicated data drifts (the seller name copied into 10 million product documents).
  • Many-to-many relationships turn into application-side joins.
  • Hard limits: MongoDB caps a document at 16 MiB and nesting at 100 levels, so "embed all comments in the post" breaks for viral posts.

MongoDB's own example is useful in interviews: on a product page that shows only the five newest reviews, keep reviews in a separate collection (reference them) because the long tail of old reviews is read rarely. Embed what is small, bounded and read together; reference what is large, unbounded or shared.

From your world

A key-value store is the kernel's hash table of sockets or the ARP cache: lookup by exact key, nothing else. Memcached and Redis are that table exposed over TCP. A document is like a netlink message with nested attributes (TLVs): one blob carries the whole object, and the reader picks the fields it understands.

Where this breaks: the ARP cache lives in one kernel and is lost on reboot; a key-value store is shared by many machines, must be replicated, and must survive a node crash, so you now have to choose between consistency and availability, which a local hash table never faces.
