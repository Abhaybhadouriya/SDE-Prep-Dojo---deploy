Key APIs

Use Server-Sent Events (SSE) for the answer: an ordinary HTTP response that stays open and carries data: lines as tokens are produced. It is one-way (server to client), which is all we need, and it works through normal HTTP proxies and load balancers. Hugging Face's TGI and OpenAI's API both stream this way. WebSockets would also work but add complexity for no gain. See Real-time Updates.

# start a turn in a conversation; response is an SSE stream
POST /v1/conversations/{convId}/messages
  Idempotency-Key: 7f3a...           # retry-safe
  { "content": "Explain PagedAttention", "model": "chat-large", "max_tokens": 800 }

  -> 200 Content-Type: text/event-stream
  id: m_91:1
  data: {"delta":"Paged"}

  id: m_91:2
  data: {"delta":"Attention stores"}
  ...
  event: done
  data: {"messageId":"m_91","usage":{"input":1840,"output":612},"finish":"stop"}

# resume a dropped stream from the last event id
GET /v1/messages/m_91/stream        Last-Event-ID: m_91:2

# stop generating (frees the GPU slot)
POST /v1/messages/m_91/cancel

# history
GET /v1/conversations?cursor=...&limit=20
GET /v1/conversations/{convId}/messages?before=m_80&limit=50
{
  "requestId": "m_91",
  "tenantTier": "paid",
  "priority": 1,
  "model": "chat-large",
  "promptTokens": [128000, 9906, 11, ...],   // already tokenized
  "prefixHint": "conv_55:turn_6",            // for prefix-cache-aware routing
  "maxNewTokens": 800,
  "deadlineMs": 60000,
  "stream": { "topic": "tokens", "key": "m_91" }
}

Rate-limit headers follow the OpenAI convention: x-ratelimit-remaining-tokens, x-ratelimit-reset-tokens, and Retry-After on a 429. OpenAI's docs note that usage is counted from the larger of max_tokens and an estimate from the request size, so a client that asks for a huge max_tokens pays for it in quota up front.
