The story

Explain like I'm 5

There is a magic storyteller who can answer any question, but she can only say one word at a time, and each word takes a little thinking. Thousands of children line up to ask questions. If she answered one child completely before starting the next, the line would never move. So she does something clever: she says one word to child A, then one word to child B, then one word to child C, round and round. When one child's story ends, a new child steps into the circle right away. Each child hears their story trickle in word by word, so nobody waits in silence. She also keeps a little notebook page for each child so she does not forget what she already said. The notebook is small, so she tears pages out neatly and reuses them.

The storyteller is a GPU running a large language model (LLM). "One word at a time" is autoregressive decoding: the model produces one token (a word piece, roughly three quarters of an English word) per step and feeds it back in. Talking to many children in a circle is continuous batching. The notebook pages are the KV cache, and tearing out and reusing pages neatly is PagedAttention. Hearing the story trickle in is token streaming.

In this interview the model itself is a black box. You are designing the serving system around it: the API, streaming, routing to GPUs, batching, memory, fairness, cost and storage. Hello Interview's ChatGPT breakdown sets exactly this scope.

LLM words you need first (Level 2).

  • Token: a word piece, about three quarters of an English word. Models read and write tokens, and providers bill by tokens.
  • Prefill: the first pass, where the model reads the whole prompt at once (fast, compute-heavy). Decode: the loop that then produces one new token per step (slow, memory-heavy).
  • KV cache (a cache): the per-request scratch memory on the GPU that remembers the Key and Value vectors of every token so far, so each decode step does not re-read the whole prompt.
  • Context window: the most tokens (prompt + answer) the model can look at in one request, for example 8K or 128K.
  • SSE (Server-Sent Events): a one-way server push over a plain HTTP response that stays open, one data: line per chunk.
  • fp16 / bf16: 16-bit floating-point numbers, 2 bytes each. Model weights are usually stored this way.
  • Quantization: storing weights (or the KV cache) in fewer bits, such as 8 or 4, so more fits in GPU memory, at some risk to quality.
  • Prefix cache: keeping the KV cache of a prompt start that many requests share (a system prompt, earlier chat turns), so prefill can skip it.
  • Grouped-query attention (GQA): a model design where several attention heads share one Key/Value head, which shrinks the KV cache.
  • Wide-column store: a NoSQL database such as Cassandra where rows are found by a partition key and sorted by a clustering key inside it.

From your world

"Decode is memory-bandwidth bound" is the same as a packet path limited by DRAM bandwidth, not by the ALU. To produce one token for one sequence, the GPU must stream every weight (tens of GB) from its memory, but does very little maths on each byte. Processing 64 sequences in that same pass reuses the bytes already fetched, the way batching packets amortises one descriptor fetch or one cache-line load. That is why bigger batches are nearly free throughput, until the KV cache runs out of memory.
