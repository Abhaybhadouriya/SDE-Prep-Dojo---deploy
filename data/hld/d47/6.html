Deep dives

1. Continuous batching: keeping the GPU full

Decoding one token means reading all model weights from GPU memory once. Doing that for one sequence wastes the GPU's compute; doing it for 64 sequences at once costs almost the same memory traffic. That is why Anyscale calls LLM inference "memory-IO bound, not compute bound", and why batching is the main lever.

Static batching waits until every sequence in the batch is done. A 20-token answer sits finished while a 900-token answer keeps the batch alive, and newcomers wait. Continuous batching (Orca's "iteration-level scheduling", OSDI 2022) re-forms the batch every iteration: finished sequences leave, waiting ones join immediately.

  1. Static batching. A and B start together. A finishes early but its slot stays empty until B finishes. C waits outside the whole time.
  2. Continuous batching. Same A and B, but the scheduler re-forms the batch every iteration.
  3. Refill. The moment A finishes, C takes its slot; when C finishes, D takes it. The GPU never runs a half-empty batch while work is waiting.
  4. Result. Orca reported 36.9x the throughput of FasterTransformer on GPT-3 175B at the same latency; Anyscale measured up to 23x over naive static batching with vLLM.

From your world

Static batching is like a DMA engine that only refills the TX ring when the whole ring has drained. Continuous batching refills each descriptor as soon as it completes. Same hardware, far better link utilisation.

2. The KV cache and PagedAttention

During decoding the model needs the Keys and Values of every earlier token. Recomputing them each step would be quadratic, so they are cached in GPU memory: the KV cache. It grows by one entry per token, and you do not know in advance how long an answer will be. Older servers reserved one contiguous chunk per request sized for the maximum length. The vLLM team measured that existing systems waste 60-80% of KV-cache memory to fragmentation and over-reservation.

PagedAttention (vLLM, SOSP 2023) borrows the operating system's virtual memory idea. The KV cache is split into fixed-size blocks (for example 16 tokens each). Each sequence has a block table mapping its logical blocks to physical blocks anywhere in GPU memory. Blocks are allocated only when needed, so waste drops to the last partly filled block: under 4% in vLLM's measurements. More sequences fit, so batches get bigger: the paper reports 2-4x throughput over FasterTransformer and Orca at the same latency, and the vLLM blog reports up to 24x over Hugging Face Transformers and up to 3.5x over TGI.

From your world

This is literally paging. Block table = page table, physical block = page frame, "allocate on first write" = demand paging. When two parallel samples share a prompt, vLLM shares the prompt's blocks with reference counts and copies a block only when one sample writes to it: copy-on-write after fork(). The vLLM blog says this sharing cuts memory by up to 55% for parallel sampling and beam search. When memory runs out, vLLM can preempt a sequence and swap its blocks to CPU memory or recompute them later, which is swapping.

3. Scheduling and routing across GPU workers

  • Admission by memory, not by count. A worker accepts a new sequence only if it has enough free KV blocks for the prompt plus some growth. Otherwise the request waits in the scheduler queue. TGI exposes this as a max-concurrent-requests limit and returns an overloaded error so clients can back off.
  • Prefix-cache-aware routing. In a multi-turn chat, turn 7's prompt starts with turns 1-6. vLLM's automatic prefix caching hashes each full block together with everything before it, so a block is reused only if the whole prefix matches, and evicts unused blocks LRU. To benefit, route a conversation's next turn to the worker that served the last one (consistent hash on conversation id, with fallback when that worker is full). The shared system prompt is a prefix every request has.
  • Prefill vs decode. Prefill is a big compute-heavy pass over the whole prompt; decode is many small memory-bound steps. Mixing them on one GPU makes ongoing streams stutter whenever a long prompt is prefilled. Two fixes: chunked prefill (split a long prefill into slices mixed with decode steps), or disaggregation, running prefill and decode on separate GPU pools and shipping the KV cache between them. DistServe (OSDI 2024) reports up to 7.4x more requests served within latency SLOs this way.
  • Priority and preemption. Separate queues per tier; weighted fair queuing between users; under pressure, preempt free-tier sequences (swap or recompute) before paid ones.
  • Cancellation. When the user clicks Stop or the SSE connection closes, the gateway sends a cancel to the worker, which drops the sequence from the next iteration and frees its blocks. Without this, abandoned answers keep burning GPU time.

4. Rate limits counted in tokens

A request for a 5-word answer and a request with a 100K-token document are not the same cost. So limits are in tokens per minute (TPM) as well as requests per minute (RPM), and whichever is hit first applies, as in OpenAI's API.

  1. Reserve At admission, debit input tokens + max_tokens from the user's token bucket in Redis (atomic Lua).
  2. Reconcile At finish, refund the unused part (max_tokens - actual output).
  3. Tier Bucket size and refill rate depend on the plan; paid tiers also get a higher scheduler priority.
  4. Signal Return 429 with Retry-After and remaining-token headers; clients must back off with jitter. OpenAI's docs point out that failed requests still count, so instant retries make things worse.

More on the algorithms in Distributed Rate Limiter.

From your world

This is a token-bucket policer, the same one in a router's QoS config, except the "bytes" are model tokens and the burst size is the plan's TPM. Reserve-then-refund is like charging a frame's full size at enqueue and crediting back on early drop.

5. Long conversations: cost without amnesia

Every turn re-sends the whole history as the prompt, so turn 30 costs far more prefill than turn 1, and context windows have a hard limit. Options, cheapest first:

6. Streams that survive reconnects and deploys

Phones switch networks and edge nodes get redeployed mid-answer. Do not couple the stream to one TCP connection. The worker publishes tokens to a per-message buffer (a Redis stream with TTL, or a pub/sub topic); the edge node subscribes and writes SSE events with an id:. On reconnect, the browser's EventSource sends Last-Event-ID automatically (MDN documents this), any edge node reads the buffer from that id and continues. Generation on the GPU never stopped.
