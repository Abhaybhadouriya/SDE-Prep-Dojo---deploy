Back-of-envelope estimation

Method from Back-of-Envelope Estimation. Assumptions are marked.

20Kprompts/s peak
120Kconcurrent streams
~10Moutput tokens/s
~0.8 MBKV cache per token (13B model)
  1. Requests 200M DAU x 5 prompts/day (assumption, "a few") = 1B prompts/day, about 11.6K/s on average; Hello Interview's peak is ~20K/s.
  2. Concurrency (Little's law) In-flight = arrival rate x time in system = 20K/s x ~6 s per answer = 120K concurrent streams. This matches Hello Interview's figure.
  3. Token rate Assume 500 output tokens per answer. 20K x 500 = 10M output tokens per second at peak. Per stream that is 500 / 6 s = ~83 tokens/s, faster than anyone reads.
  4. KV cache size per token For every token in context, each layer stores a Key and a Value vector. Size = 2 x layers x hidden size x bytes. For a 13B model (40 layers, hidden 5,120, fp16 = 2 bytes): 2 x 40 x 5,120 x 2 = ~0.8 MB per token. Anyscale's continuous-batching post uses "about 1 MB per token" for 13B, and the vLLM blog says one LLaMA-13B sequence can need up to 1.7 GB (2,048 tokens x 0.8 MB). Bigger models use grouped-query attention (GQA: several query heads share one K/V head) to shrink this.
  5. Why memory sets throughput Anyscale's worked example: a 13B model on a 40 GB A100 uses 26 GB for weights, leaving ~14 GB, which holds ~14K tokens of KV cache, so only ~28 sequences of 512 tokens or 7 of 2,048 tokens fit in one batch. Every sequence you cannot fit is throughput you cannot have.
  6. GPU fleet (order of magnitude) Assume a replica can keep ~100 sequences in flight with good batching (assumption; depends on model, context length and hardware). 120K / 100 = ~1,200 replicas. How many GPUs that is depends on the model, so say which one: for the 13B model used above (fits on 1 GPU per replica) it is ~1,200 GPUs; for a 70B-class model split over 8 GPUs with tensor parallelism it is ~10K GPUs, before headroom and regions. (For a 70B model with grouped-query attention, the KV line becomes 2 x 80 layers x 8 KV heads x 128 dims x 2 bytes = ~0.33 MB per token, smaller per token than the 13B model because only 8 KV heads are stored.) The point is not the exact count: it is that a 2x gain in sequences per GPU halves the bill, which is why batching and KV-cache tricks matter.
  7. Conversation storage 1B prompts/day x 2 messages x ~2 KB (prompt + answer text, metadata) = ~4 TB/day, ~1.5 PB/year before replication. Big but ordinary for a wide-column store.
  8. Streaming bandwidth If each SSE event carries a few tokens in ~100 bytes, 10M tokens/s / 3 tokens per event x 100 B = ~330 MB/s outbound. Fine for a CDN-fronted edge tier; the hard part is holding 120K long-lived connections.

From your world

Little's law is the same one you use to size a NIC ring buffer: occupancy = arrival rate x residence time. Here the "ring" is GPU memory holding KV caches, and the "packets" are sequences that stay resident for seconds.
