Architecture: one prompt, end to end

  1. Edge. The client sends the prompt over HTTPS. The API gateway authenticates, checks the user's tier and token budget (deep dive 4), and keeps the SSE connection open.
  2. Build the prompt. The chat service loads recent messages for this conversation, adds the system prompt, trims or summarises old turns to fit the context window, tokenizes, and runs input moderation. It writes the user message and an empty assistant message (status streaming).
  3. Schedule. The request goes to a per-model scheduler with separate queues per tier. Paid traffic is drained first; free traffic gets the rest, with fair-share per user.
  4. Place on a GPU worker. The router picks a worker with free KV-cache blocks, preferring one that already holds this conversation's prefix in cache (Worker 2), so prefill can skip the earlier turns.
  5. Generate and stream. The worker runs continuous batching: each iteration produces one token for every sequence in its batch. New tokens go out through the stream path (via a buffer) and the gateway writes them as SSE events. Dots are tokens.
  6. Persist and meter. Tokens are also appended to a short-lived Redis stream so a reconnect can resume. On finish the full answer is saved, and a usage event (input/output tokens) goes to Kafka for billing and analytics.
