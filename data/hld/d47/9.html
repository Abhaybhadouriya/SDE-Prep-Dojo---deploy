60-second answer, said out loud: "The model is a black box; I am designing the serving system. Clients stream answers over SSE through a gateway that enforces token-based limits per tier. A chat service builds the prompt from history and routes it, with prefix affinity, to a scheduler that queues by tier. GPU workers run continuous batching with a paged KV cache, because decode is memory-bandwidth bound and the batch size is limited by KV memory. Tokens go through a resumable buffer so a dropped phone connection can continue. Usage and finished messages go to Kafka for billing and storage in a wide-column store. I watch TTFT and TPOT p99, queue depth and KV utilisation."

SDE-1 stops here / SDE-2 adds. SDE-1: SSE streaming, token-based rate limits, a queue in front of GPUs, conversation storage by user and conversation, the idea that batching raises throughput. SDE-2 adds: the KV-cache memory maths, continuous batching vs static batching, PagedAttention, prefix-aware routing, prefill/decode split (DistServe), preemption under memory pressure, and cancellation freeing GPU slots.

You might confuse this with a normal request/response web service with a model behind it. In CRUD services, requests per second is the capacity unit. Here the unit is tokens (and KV memory): one request with a 100K-token context can cost more than a thousand short ones. Also do not confuse TTFT (time to first token, set by prefill and queueing) with TPOT (time per output token, set by decode and batch size); they are tuned differently.

Why stream tokens instead of returning the full answer?

Total generation time is the same, but perceived latency drops from "whole answer" to "first token". Hugging Face's example: at 100 tokens/s a 1,000-token answer takes 10 s; with streaming the user sees text immediately and half of it by 5 s. It also lets users stop a bad answer early, which saves GPU time. Use SSE: one HTTP response with incremental events, works through proxies, auto-reconnects.

How to answer

Separate TTFT from total time, give the numeric example, pick SSE and say why not WebSocket.

What is continuous batching and why does it matter so much?

Decode is memory-bandwidth bound: each step reads all weights once regardless of batch size, so bigger batches are nearly free throughput. Static batching keeps a batch until its longest member finishes, leaving finished slots idle. Continuous (iteration-level) batching, from the Orca paper, re-forms the batch every decode step so finished sequences leave and waiting ones join. Orca reported 36.9x over FasterTransformer on GPT-3 175B; Anyscale measured up to 23x over naive batching with vLLM.

How to answer

Start with "memory-bound", then the idle-slot picture, then the numbers.

Explain the KV cache and PagedAttention to someone who knows operating systems.

The KV cache holds each layer's Key and Value vectors for every token so far, about 0.8 MB per token for a 13B fp16 model, so it is the dominant memory cost and grows unpredictably. Contiguous per-request allocation wastes 60-80% to fragmentation and over-reservation (vLLM's measurement). PagedAttention stores it in fixed-size blocks with a per-sequence block table, like pages and a page table: allocate on demand, no external fragmentation, share prefix blocks copy-on-write, swap to CPU under pressure. Waste drops under 4%, batches grow, and throughput rises 2-4x versus prior systems at the same latency.

How to answer

Do the per-token size math out loud, then map every vLLM idea to an OS idea.

Likely follow-ups
  • What is the block size trade-off?
  • What happens when GPU memory is full?
How do you route requests across 1,000 GPU replicas?

A scheduler per model holds tiered queues. Workers report free KV blocks, batch size and which prefixes they cache. The router prefers the worker that served this conversation last (prefix-cache hit saves prefill), falls back to the one with the most free KV memory, and never admits more than memory allows. Use weighted fair queuing between users and preempt free-tier sequences under pressure. Long prompts may go to a prefill pool if you disaggregate.

How to answer

Make "admission by KV memory" and "prefix affinity" your two key ideas.

Design rate limiting for an LLM API. Why tokens and not requests?

Cost scales with tokens: a 100K-token prompt costs vastly more than a tiny one. Keep both RPM and TPM buckets per user/org in Redis; the first one exhausted wins. On admission reserve input tokens + max_tokens, refund the unused output at the end. Return 429 with Retry-After and remaining-token headers. Tie bucket sizes to tiers, and add a global concurrency cap per tier so a spike cannot starve paid users.

How to answer

The user's Wi-Fi drops halfway through an answer. What happens?

Generation continues on the GPU; tokens are written to a per-message buffer (Redis stream, TTL ~10 min) with sequence ids. The browser's EventSource reconnects and sends Last-Event-ID; any edge node reads from that id and continues. If the user never returns, the final message is still saved. If they cancel, the cancel propagates to the worker to free the slot.

How to answer

Decouple "generation" from "connection" and say where the buffer lives.

Long prompts are making everyone's streaming stutter. Why, and what do you do?

A prefill of a long prompt is one big compute-heavy step. When it runs in the same iteration as decode steps, every streaming user in the batch waits for it, so TPOT spikes. Fixes: chunked prefill (slice the prefill and interleave with decode), cap prompt size per tier, or disaggregate prefill and decode onto separate GPU pools and transfer the KV cache; DistServe reports up to 7.4x more requests within SLO. Prefix caching also shrinks how much prefill is needed for multi-turn chats.

How to answer

Name the two phases and their different bottlenecks (compute vs memory) first.

How do you store and load conversation history?

Wide-column store: conversations partitioned by user_id sorted by updated_at; messages partitioned by conv_id sorted by sequence. ~4 TB/day of appends. Write the assistant message as streaming at start and finalize at the end. When building a prompt, load the last N turns plus a stored rolling summary of older ones to fit the context window.

How do you autoscale GPU workers?

On queue depth / waiting time and KV-cache utilisation, not CPU. GPU nodes are slow to start (driver, multi-GB image, tens of GB of weights), so keep warm headroom, pre-pull images, cache weights on local disk, and scale ahead using daily traffic patterns. Readiness probes keep traffic off loading workers. Graceful termination lets in-flight answers finish.

How to answer

Pick the right signal and talk about cold start honestly.

Estimate how many concurrent sequences one GPU can hold.

Free memory after weights / (KV bytes per token x average context length). Anyscale's 13B example: 40 GB A100, 26 GB weights, ~14 GB free, ~1 MB/token, so ~14K tokens: ~28 sequences of 512 tokens or 7 of 2,048. That is why long contexts are expensive and why paging, quantized KV and grouped-query attention (fewer K/V heads) matter.

How to answer

Write the formula, plug in numbers, and draw the consequence.

Scenario: launch day, TTFT goes from 0.8 s to 20 s

A new model launches. Traffic triples. Queues are long, streams time out, paid users complain.

Weak answer: "Add more GPUs."

Strong answer: GPUs cannot appear in minutes, so protect the SLO with policy. Enforce tier priority (paid queue first), lower free-tier max_tokens and context, shed free load with a clear "at capacity" message, turn on prefix caching for the common system prompt, check KV-cache utilisation and preemption rates, then add capacity that was pre-reserved. Afterwards, plan headroom from the launch forecast.

Common mistakes

Common mistakes: treating it as a normal CRUD service with "a model server"; rate-limiting by requests only; static batching; ignoring KV-cache memory; no cancel path; coupling the stream to one connection; scaling GPUs on CPU metrics.
