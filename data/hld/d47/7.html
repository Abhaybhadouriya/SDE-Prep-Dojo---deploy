Where Kafka, Kubernetes and Docker fit

📨

Kafka

Usage events for billing, message-saved events for search indexing and analytics, moderation audit logs. Not the token path: tokens need millisecond delivery to one reader, which a Redis stream or direct gRPC stream does better.

 ☸️

Kubernetes

GPU nodes with the device plugin, pods requesting nvidia.com/gpu: 8, node pools per GPU type, taints so only inference pods land there. Autoscale on queue depth and KV-cache utilisation, not CPU.

 🐳

Docker

Inference images are huge (CUDA + engine). Keep model weights out of the image; mount them from a local cache or pull from object storage so a new node starts in minutes, not tens of minutes.

 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-worker-chat-large
spec:
  replicas: 4
  selector: { matchLabels: { app: llm-worker } }
  template:
    metadata: { labels: { app: llm-worker } }
    spec:
      nodeSelector: { gpu-type: h100 }
      tolerations: [{ key: "gpu", operator: "Exists", effect: "NoSchedule" }]
      terminationGracePeriodSeconds: 300      # let in-flight answers finish
      containers:
      - name: engine
        image: registry.example.com/llm-engine:1.4.2
        args: ["--model=/models/chat-large", "--max-num-seqs=128", "--enable-prefix-caching"]
        resources:
          limits: { nvidia.com/gpu: 8 }
        readinessProbe: { httpGet: { path: /health, port: 8000 }, periodSeconds: 5 }
        volumeMounts: [{ name: weights, mountPath: /models, readOnly: true }]
      volumes:
      - name: weights
        persistentVolumeClaim: { claimName: model-weights-ro }

The engine flags are illustrative of vLLM-style options; check your engine's docs. Slow start (loading tens of GB of weights) means you scale ahead of demand, keep warm spare capacity, and use readiness probes so the router never sends traffic to a worker that is still loading.
