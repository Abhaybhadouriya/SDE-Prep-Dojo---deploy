Trade-offs, bottlenecks and failure modes

DecisionChoiceAlternativeTrade-off
Streaming transportSSEWebSocket, long pollingSSE is one-way, HTTP-native, auto-reconnects with Last-Event-ID; WebSocket only needed for two-way (voice, interrupts)
BatchingContinuous, memory-awareStatic / dynamic batchingFar better throughput; scheduler is more complex
Batch sizeTuned per SLO"As big as fits"Bigger batch = more tokens/s per GPU but slower TPOT for each user
Prefill/decodeChunked prefill on shared GPUsDisaggregated poolsDisaggregation protects TPOT and scales phases separately, but must move KV cache across the network
RoutingSticky by conversation (prefix hits)Least loadedCache hits vs load balance; fall back when the sticky worker is hot
Precisionfp16/bf16, maybe 8-bit4-bit quantizationSmaller weights and KV = more sequences, at some quality risk
Message storageWide-column by conv_idPostgresHuge append-only writes and simple keys favour NoSQL
What holds up well
  • Stateless edges; streams resumable from a buffer
  • GPU memory used near-fully via paging
  • Fair, tiered access via token buckets + priority queues
  • Billing from an event log, replayable
Failure modes to name
  • GPU worker crash: in-flight answers lost; retry from the prompt (mark message interrupted)
  • Traffic spike: queues grow, TTFT explodes; shed free tier first, show "at capacity"
  • Cold start: new GPU nodes take minutes; keep warm headroom
  • Thundering herd of retries after an outage: Retry-After + jitter
