Key APIs

REST, with an Idempotency-Key header on every POST that creates something. Background in API Design & Client-Server Communication.

# --- merchant: plans ---
POST /v1/plans   Idempotency-Key: 7c1...
  { "productId": "sku_milk_500ml", "quantity": 2, "interval": "week", "intervalCount": 1,
    "anchor": { "weekday": "MON" }, "price": { "amount": 6000, "currency": "INR" },
    "trialCycles": 0, "maxCycles": null }
  -> 201 { "planId": "plan_w_milk2" }

# --- customer: subscribe (returns what the client must do next) ---
POST /v1/subscriptions   Idempotency-Key: 9f2...
  { "planId": "plan_w_milk2", "startDate": "2026-11-30", "addressId": "addr_1",
    "slot": "06:00-08:00", "paymentMethod": { "type": "card" } }
  -> 201 { "subscriptionId": "sub_881", "status": "PENDING_AUTH",
           "nextAction": { "type": "redirect", "url": "https://gateway.example/mandate/abc" } }

# --- gateway calls us back after bank 2FA (signed, may arrive more than once) ---
POST /v1/webhooks/payments   X-Signature: ...
  { "event": "mandate.activated", "mandateId": "md_55", "reference": "sub_881" }

# --- manage ---
POST  /v1/subscriptions/sub_881/pause    { "from": "2026-12-14", "to": "2026-12-28" }
POST  /v1/subscriptions/sub_881/resume
POST  /v1/subscriptions/sub_881/skip     { "cycleDate": "2026-12-07" }
PATCH /v1/subscriptions/sub_881          { "quantity": 3 }            # applies from next cycle after cut-off
POST  /v1/subscriptions/sub_881/cancel   { "atPeriodEnd": true, "reason": "moving" }
GET   /v1/subscriptions/sub_881/cycles?from=2026-11-01&limit=10     # history + upcoming

# --- internal: called by the scheduler, idempotent by (subscriptionId, cycleNo) ---
POST /internal/cycles/run   { "subscriptionId": "sub_881", "cycleNo": 5 }

Two details worth saying. (1) Subscribe returns PENDING_AUTH plus a nextAction, because the bank's 2FA step happens outside our system and finishes with a webhook, not with this response. (2) Every "manage" call changes state with a version check (If-Match or WHERE version = ?), so a pause and a scheduler run cannot both win.
