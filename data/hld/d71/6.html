Deep dives

1. Exactly one order and one charge per cycle

The scheduler will run twice (a deploy, a crash after work but before commit), workers will retry, the gateway will time out after actually charging. The design must make every repetition harmless:

  • Cycle row as the anchor. PRIMARY KEY (subscription_id, cycle_no). Creating cycle 5 twice fails on the second insert; the scheduler treats that as "already done".
  • Derived idempotency keys downstream. Order service: sub_881:5. Payment: sub_881:5:attempt. If the worker crashes and retries, Order returns the same order and the gateway returns the same charge. Stripe, Razorpay and most gateways accept an idempotency key on create calls for exactly this reason.
  • State machine with guarded transitions. UPDATE cycle SET state='CHARGING' WHERE ... AND state='ORDERED'. Zero rows updated means another worker owns it; stop.
  • Unknown outcome is a state. If the charge call times out, the cycle stays CHARGING and a reconciler asks the gateway "what happened to key sub_881:5:1?" before any retry. Never retry a timed-out charge with a new key.
  • Outbox for events (cycle.ordered, cycle.paid), so the database change and the message cannot disagree. See Distributed Transactions & Events.

The classic double charge: worker calls the gateway, the gateway charges, the response is lost, the worker retries with a fresh request. Without a stable idempotency key the customer pays twice. Say this failure out loud; interviewers wait for it.

2. The scheduler: finding due subscriptions

Three designs, from simple to scalable. Pick based on volume and say why. The Amazon candidate noted that job-scheduler designs are the closest reference; see Job Scheduler.

  • A. Indexed poll. A partial index on next_cycle_at for active subscriptions; pollers run SELECT ... WHERE next_cycle_at <= now() ORDER BY next_cycle_at LIMIT 500 FOR UPDATE SKIP LOCKED, process, commit. Several pollers never pick the same row. Good up to millions of subscriptions; most teams should start here.
  • B. Time-bucketed table. due(bucket_start, shard, subscription_id) with 5-minute buckets and, say, 64 shards. A worker owns (bucket, shard) via a lease and reads exactly its slice, like a timer wheel. Spreads the Monday spike and avoids one hot index. Rewrite the entry when the subscription is rescheduled.
  • C. Delayed queue. Put a message that becomes visible at the due time (SQS delay up to 15 minutes, so chain or combine with polling; RabbitMQ delayed exchange; Redis sorted set by score). Fast, but queues lose or duplicate messages, so the worker must check the database row before acting, and a nightly sweeper catches anything missed.
  • Look-ahead. The scheduler does not act at the delivery time, it acts at the action time: the order cut-off for goods (for example 20:00 the day before) and the pre-debit time for Indian charges (26 h before, following Stripe's documented wait). Store next_cycle_at as that action time.
  • Catch-up. If the scheduler was down for an hour, it processes everything with next_cycle_at in the past, oldest first, and for goods it skips cycles whose delivery date has passed (with a notice) instead of delivering Monday's milk on Wednesday.

3. Mandates, card-on-file and the callback flow

Recurring payments need standing permission, and that permission is created with the customer present and then used without them. In India the rules are specific: register the e-mandate once with AFA (3-D Secure for cards, UPI PIN for UPI), alert the customer at least 24 hours before each debit with an option to opt out, and require AFA again for any recurring debit above Rs 15,000 (summarised in Stripe's India recurring payments guide).

  1. Create intent Subscription service asks the payment service for a mandate setup with max amount (for example Rs 5,000), frequency (weekly or as presented) and end date (one year).
  2. Redirect The app opens the gateway page; the customer enters card or UPI details there, never on our servers. We store only the gateway's token and mandate reference (this keeps us out of most of PCI DSS scope).
  3. Bank 2FA OTP or 3-D Secure or UPI PIN at the bank or UPI app.
  4. Callback The browser returns to our return_url (show "processing") and, separately, the gateway sends a signed webhook. Trust the webhook (verify the signature; dedupe by event id), not the browser redirect, which the user can close or fake.
  5. First charge Often taken during setup (on-session), so the customer pays cycle 1 with 2FA and later cycles happen off-session.
  6. Each cycle Send the pre-debit notice with the exact amount, wait the window, then charge. If the amount exceeds the mandate's max or Rs 15,000, the customer must authenticate that debit: model it as a cycle state AWAITING_CUSTOMER_AUTH.
  7. Mandate lifecycle Customers can revoke a mandate from their bank or UPI app; the gateway tells us by webhook, and we move the subscription to PAST_DUE and ask for a new payment method before the next cycle.

Outside India, the flow is lighter (card networks allow merchant-initiated transactions on a saved card after one authenticated payment), but the shape is the same: authorise once with the customer present, charge later with a stable idempotency key, react to webhooks.

4. Failed payments: retries and dunning

  • Soft vs hard declines. Insufficient funds or a network timeout: retry later. Lost or stolen card, revoked authorisation: do not retry with the same method; ask for a new one. Stripe documents a list of hard decline codes it never retries automatically.
  • Schedule. Spread retries over days (for example day 1, 3, 5, 7), at times more likely to succeed (after typical salary dates, early morning local time). Stripe's default Smart Retries policy is up to 8 retries within 2 weeks; a custom schedule is up to three retries at chosen day offsets. Note Stripe does not auto-retry India-issued card payments, because every debit needs its own pre-debit notice: the retry is a new notified attempt.
  • Communication. Email and push on each failure with a link to update the payment method ("card expiring" reminders a week before expiry prevent many failures).
  • Goods are different. For milk, decide the policy: deliver on credit and retry (good customers), or hold the order until paid (charge before the cut-off). Many grocery subscriptions charge at order creation; if the charge fails, the order is not released to the warehouse.
  • Every retry is a new payment_attempt with its own idempotency key sub:cycle:attempt; the cycle remembers the attempt count.

5. Pause, skip, cancel, change: races with the scheduler

A customer taps "skip next Monday" at 19:59:58; the scheduler claims the subscription at 20:00:00. Who wins?

  • Cut-off rule (from requirements): changes at or after the cut-off apply from the next cycle. The UI shows it ("changes now apply from 14 December").
  • Serialise per subscription: both the API and the scheduler update the subscription row with WHERE version = ? (or take a row lock). One commits first; the other re-reads and acts on the new state.
  • Skip writes a schedule_change for that cycle date; the cycle worker marks the cycle SKIPPED instead of ordering. Pause sets status PAUSED with a resume date; the scheduler skips paused subscriptions and resumes automatically. Pausing does not count towards max_cycles (decide and say it).
  • Cancel: immediately (refund or no refund of the current period per policy) or at period end (cancel_at_period_end). Never delete: keep history for invoices, support and analytics. Also cancel the mandate at the gateway if no other subscription uses it.
  • Plan change: upgrade now with proration (charge the difference for the rest of the period) or from the next cycle; downgrades usually from the next cycle. Proration is a nice SDE-2 detail; mention it, do not implement it.
  • Out of stock at order time: substitute (if the customer allowed it), partially fulfil, or skip the cycle and do not charge. The cycle stores the outcome.
