Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key subscription_id means the cycles of one subscription are never processed in parallel, so one subscription cannot be charged twice by two workers. Consumer-group sizing: 24 partitions allow up to 24 workers, and KEDA scales on lag with a hard maximum so the order and inventory services are not overrun at 20:00 on Sunday. The scheduler is a Deployment with leader election, not a single CronJob pod.

  • Kafka (or SQS): cycle.due keyed by subscription_id so cycles of one subscription are processed in order and never in parallel; cycle.events (ordered, paid, failed, skipped) for notifications, analytics and the merchant dashboard; payment webhooks are put on a topic as soon as they are verified, so the HTTP handler returns 200 fast and processing retries safely. This is the "why do we need a message queue" answer from the Walmart round: decouple the nightly burst from the order and inventory services, absorb retries, and let several consumers react to one event. Use the Kafka outbox pattern to publish from the database transaction.
  • Kubernetes: Subscription API as a Deployment; cycle workers as a Deployment scaled on consumer lag (KEDA) with a hard cap so the order service is not overrun; the scheduler as a Deployment with leader election or SKIP LOCKED sharing (not a single CronJob pod, which is a single point of failure, though a CronJob is fine for the nightly reconciler and the sweeper).
  • Docker: images per service; a compose file with PostgreSQL, Kafka and a fake gateway (which can be told to time out or decline) lets you test the double-charge and webhook-replay cases locally.
