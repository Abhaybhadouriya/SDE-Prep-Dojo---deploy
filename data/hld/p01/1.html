When you hit this problem

Plain HTTP is request-response: the client asks, the server answers, done. The server cannot start a conversation. ByteByteGo's guide puts it simply: an HTTP server cannot open a connection to a browser, so the browser must always start. Any feature where the server learns something first and the user must see it quickly needs this pattern.

Signals in the interview question

  • "see it instantly", "live", "real time": chat messages, typing dots, read receipts (WhatsApp, Slack / Teams).
  • "track it on a map": the driver or rider moving every few seconds (Uber, Swiggy / Zomato).
  • "many people look at the same thing": live comments, scoreboards, seat maps, stock tickers (Live comments, BookMyShow, Stock exchange).
  • "two people edit or play together": Google Docs, chess, a whiteboard (Collaborative editor, Chess).
  • "stream the answer as it is generated": ChatGPT tokens appearing one by one (LLM serving).
  • "online / last seen": presence dots.

The numbers that make it hard

2.27MTCP sockets on one WhatsApp FreeBSD box (2012)
100KSSE connections per LinkedIn node
~5Mconcurrent Discord users on Elixir
500 msSlack worldwide message delivery

Holding a socket is cheap but not free: each one is a file descriptor, kernel buffers, TLS state and some application memory. LinkedIn measured about 20 KB of JVM memory per TLS connection. At 100,000 connections that is about 2 GB just for TLS, which is why their nodes ran out of heap first, not CPU. The hard parts are therefore (1) holding millions of mostly idle connections, (2) finding the right connection for each update, and (3) surviving the moment when a million clients reconnect at once.

Worked estimate: how many gateways?

Example numbers for practice (the per-connection memory is in line with LinkedIn's 20 KB TLS figure above; the rest are assumptions to state out loud):

  1. Boxes. 50M concurrent users / a target of 200,000 connections per box = 250 gateways. Double it so a zone or half the fleet can fail, or a rollout can drain boxes: about 500 gateways.
  2. Memory per box. About 20 KB of TLS state + 10 KB of app state = 30 KB per connection. 200,000 x 30 KB = about 6 GB of RAM just for connections, before any message buffers.
  3. Heartbeats. One ping every 30 s per connection: 50M / 30 = about 1.7M pings per second across the fleet (about 3,300 per second per box at 500 boxes). Cheap one by one, but it is why heartbeat intervals and presence updates are tuned carefully.
  4. File descriptors. 200,000 sockets per box means raising nofile far above the usual default of 1,024.

Saying this chain (users / per-box target, x2 for failover, x memory per connection, / heartbeat interval) is what turns "use WebSockets" into a design.
