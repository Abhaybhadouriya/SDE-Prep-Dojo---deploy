In the interview

Phrases that land well

  • "There are two hops. For the client hop I'll use SSE because traffic is mostly server to client; for the server hop I'll use a registry plus pub/sub."
  • "The socket is a notification pipe, not the source of truth. Every message is stored first, and clients resume from their last sequence number."
  • "Gateways are dumb and horizontally scaled; business logic lives in stateless services behind them."
  • "I'll protect against reconnect storms with jittered backoff, connection lifetime dithering and slow draining."

Traps

  • Saying "WebSockets" and stopping. The interviewer then asks "how does a message reach the server holding the other user?" and the answer is missing.
  • Keeping business logic or the only copy of a message on a gateway. Gateways die; state must be elsewhere.
  • Using WebSockets for a one-way feed with rare updates. Polling or SSE is simpler and fine.
  • Ignoring mobile: phones in the background lose sockets, so you need APNs/FCM as a fallback.
Explain short polling, long polling, SSE and WebSockets. When do you pick each?

Short polling asks on a timer; simple, stateless, but wasteful with up to one interval of delay. Long polling parks the request until there is news; near-instant, still HTTP, but one request per message. SSE keeps one HTTP response open and streams events one way, with built-in reconnect and Last-Event-ID. WebSockets upgrade one TCP connection to a two-way framed channel. Pick polling for slow dashboards, SSE for feeds, tracking and token streaming, WebSockets when the client also sends frequently (chat, games, editors), and WebRTC for media.

How to answer

Draw a timeline for each, then give one rule: "who talks, how often". Mention a cost for each (wasted QPS, per-message requests, 6-connection limit on HTTP/1.1, stateful servers).

Likely follow-ups
  • Why might you start with SSE even for chat? (LinkedIn did, for compatibility.)
  • What happens to SSE across seven browser tabs?
User A is on gateway 1 and user B is on gateway 5. How does A's chat message reach B?

A's gateway forwards the message to a stateless chat service. It stores the message with a per-chat sequence number, then routes it. Option 1: look up B -> gateway 5 in a registry (Redis with a TTL, refreshed by heartbeats) and RPC to gateway 5. Option 2: gateway 5 subscribed to B's topic when B connected, so the service publishes to that topic. If B is offline, the message waits in B's inbox and a mobile push is sent. B acknowledges with its last seen sequence number.

How to answer

Name both hops, store first, then route. Say what happens when B is offline and when gateway 5 crashes between lookup and send (B reconnects and resumes from the store).

Likely follow-ups
  • How do you avoid stale registry entries?
  • Group chat with 500 members: registry or pub/sub?
  • How does Slack solve this? (Channel servers on a consistent hash ring, gateways subscribe to them.)
How many WebSocket connections can one server hold, and what limits it?

It depends on memory and kernel tuning more than CPU. WhatsApp showed over 2.2 million TCP connections on one 24-core FreeBSD box in 2012. LinkedIn held 100,000 SSE connections per JVM node after raising the listen backlog, the per-process fd limit and the heap (TLS cost about 20 KB per connection). Limits: file descriptors, socket buffer memory, TLS and application memory per connection, listen backlog, load balancer connection limits and ephemeral ports, and the cost of heartbeats. For design I'd plan conservatively, for example 100k-500k per gateway, and add gateways horizontally.

How to answer

Give a range with a source, then list limits as a kernel engineer would. Turn it into estimation: 50M concurrent users / 200k per box = 250 gateways, plus headroom for failover.

Likely follow-ups
  • Why can new gateways stay idle after a scale-out?
  • Would you terminate TLS at the load balancer or the gateway?
A deploy restarts all gateways and the auth service falls over. What happened and how do you prevent it?

A reconnect storm: every client reconnected at once, each doing TLS, token validation, registry writes and subscriptions. Prevent it with client jittered exponential backoff, a rolling deploy that drains a small percent of connections per interval, randomised maximum connection lifetimes (Zuul Push's reconnect dither), cached or locally verifiable tokens (JWT) so auth is not a remote call per reconnect, and admission control that returns "retry after N seconds". Discord also learned to make callers fail fast with a semaphore instead of queueing behind a slow registry.

How to answer

Name the failure (thundering herd), then defend at each layer: client, load balancer, gateway, dependency.

Likely follow-ups
  • How long should the drain take for 10M connections?
  • Why not a circuit breaker? (Discord avoided one so a burst of timeouts would not stop all attempts.)
The connection drops for 30 seconds. How does the client avoid missing or duplicating messages?

Every message has a per-conversation sequence number assigned by one owner. The client stores its last applied sequence. On reconnect it sends it (SSE sends Last-Event-ID automatically). The server replays everything after it from the store, or tells the client to fetch a fresh snapshot if the gap is too big. The client ignores duplicates by sequence. Facebook Messenger's snapshot + delta model and Figma's "download a fresh copy, reapply local edits" are real examples.

How to answer

Say "the socket is lossy, the store is the truth", then show the resume handshake.

Likely follow-ups
  • What if the sequence must be global across devices?
  • How long do you keep the replay buffer?
How do you keep messages in order when they pass through many servers?

Only promise order within a conversation. Route every event for a conversation through a single owner: one Kafka partition keyed by chat id, one channel server picked by consistent hashing (Slack), one process per document (Figma) or one guild process (Discord). The owner stamps an increasing sequence number. Clients buffer and reorder by sequence and request gaps.

How to answer

Scope the guarantee first, then give the single-owner trick, then the client-side check.

Likely follow-ups
  • What happens to ordering when the owner moves during a rebalance?
  • What if one chat is extremely hot?
Design the live order tracking page ("your rider is 3 minutes away").

Rider apps send GPS every few seconds to a location service, which writes to Kafka keyed by order id and updates the latest position in Redis. A router consumes and publishes to the topic for that order. The customer's browser holds an SSE stream to a gateway subscribed to that order. Throttle to one update every 2-5 seconds, send only the changed fields, and on reconnect send the latest snapshot from Redis. One-way traffic makes SSE a better fit than WebSockets.

How to answer

Estimate first (active orders x 1 update / 4 s), choose SSE with a reason, then explain hop 2 and the snapshot on reconnect.

Likely follow-ups
  • How does the ETA update without the rider moving?
  • What if the app is in the background?
One update must reach 10 million viewers (a live match score). What changes?

Per-user routing no longer makes sense. Publish once to a topic; each gateway that holds viewers of the match subscribes once and copies the update to its local sockets, so the fan-out is "number of gateways", not "number of users", at the pub/sub layer. Co-locate viewers of the same match on fewer gateways with L7 hashing on the match id. Batch updates (one frame per second), coalesce (only the latest score matters), and consider serving the state from a CDN with short polling for the long tail.

How to answer

Do the multiplication out loud, then show the two-level fan-out and the "latest value wins" shortcut.

Likely follow-ups
  • Why did Discord build Manifold? (Per-process send cost made big-guild publishes take up to 2.1 s.)
  • When would you switch from push to pull?
How would you build presence (online/offline, last seen)?

Each gateway sends a heartbeat for its connected users to a presence store (Redis key with a TTL of, say, 30-60 s). A key that exists means online; expiry means offline, so crashes clean themselves up. Publish presence changes only to users who are currently looking at that person: Slack's clients receive presence only for users visible on screen. Debounce flapping (wait a few seconds before declaring someone offline).

How to answer

Heartbeat + TTL, then limit the fan-out, then debounce.

Likely follow-ups
  • How do you handle a user with five devices?
  • Why not write presence to the main database?
How should load balancers treat WebSocket or SSE connections?

Use an L4 or L7 balancer that supports the HTTP Upgrade and long-lived streams, raise idle timeouts above your heartbeat interval, and use least-connections rather than round robin. Hash on a room or document id at L7 if you want co-location. Accept that existing connections do not move when you add servers; cap connection lifetime so the fleet rebalances. Watch ephemeral port and per-backend connection limits on the balancer.

How to answer

List three settings (upgrade support, idle timeout, balancing algorithm), then the rebalancing caveat.

Likely follow-ups
  • Where do you terminate TLS?
  • How does this look with Kubernetes Ingress?

Scenario: messages vanish after a deploy

After each gateway deploy, a few users report that messages sent during the deploy never arrived, even after reopening the app. Gateways use Redis Pub/Sub topics per user.

"Redis lost them; switch to Kafka for everything."

Pub/sub has no memory: messages published while the user was between gateways were dropped by design. Make the store the truth: persist each message with a sequence number before publishing, have the client send its last seen sequence on reconnect, and replay the gap. Then also slow the deploy drain and add jitter so fewer users are in the gap at once.

Likely follow-ups
  • How do you test this? (Kill gateways in a chaos test and compare sent vs received counts.)

Scenario: one region goes dark

Your Mumbai gateway region fails at 9 pm during an IPL match. 4 million connected clients must move to Chennai.

"DNS fails over and they all reconnect."

They will reconnect at once, so plan for it: clients use jittered backoff; Chennai has pre-scaled headroom or sheds load with retry-after; auth uses locally verifiable tokens; subscriptions are recreated lazily. Slack describes a draining mechanism that moves users from a bad region to the nearest good one. Afterwards, drain users back slowly, not all at once.

Likely follow-ups
  • How much spare capacity do you keep per region?
