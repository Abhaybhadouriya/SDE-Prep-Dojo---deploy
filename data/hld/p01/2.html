The solution ladder: naive to best

We climb hop 1 first (how the client receives), then hop 2 (how the server side routes). Each rung says when it breaks.

Rung 1: short polling

The client sends GET /orders/42/status every N seconds. Simple, works through every proxy and firewall, and every server stays stateless. It breaks in two ways. Latency is up to N seconds. Cost is wasted: if 10 million users poll every 2 seconds, that is 5 million requests per second, and almost every answer is "nothing new".

Rung 2: long polling

The client sends a request, and the server holds it open until there is news or a timeout (often 20-30 s). Then it answers, and the client immediately asks again. Latency becomes near-instant, and it is still plain HTTP. karanpratapsingh's book lists the costs: a new request per message, a gap between "answer" and "next request" where messages can pile up, and ordering trouble when several requests overlap. Long polling is a great fallback, and Facebook's original Messenger used a similar pull-after-a-nudge model.

Level 3 - Intermediate

Rung 3: Server-Sent Events (SSE)

The client opens one normal HTTP request with Accept: text/event-stream, and the server never finishes the response. It writes events as lines of text whenever it likes. The browser's EventSource API reconnects on its own and sends a Last-Event-ID header, so the server can replay what was missed. Traffic is one-way (server to client). The client sends its own actions as ordinary POSTs.

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 1041
event: order_status
data: {"order":42,"status":"OUT_FOR_DELIVERY"}

retry: 5000
id: 1042
event: rider_location
data: {"lat":12.9716,"lng":77.5946}

LinkedIn chose SSE over WebSockets for instant messaging because it is plain HTTP and so works on the widest range of networks. One gotcha from MDN: on HTTP/1.1 a browser allows only 6 connections per domain across all tabs, so seven open tabs can starve each other. Over HTTP/2 many streams share one connection (MDN cites a default of 100). SSE is also the standard way LLM APIs stream tokens.

Rung 4: WebSockets

The client sends an HTTP request with Upgrade: websocket. The server answers 101 Switching Protocols (defined in RFC 6455). From then on, the same TCP connection carries small binary or text frames in both directions. This is the default for chat, games and collaborative editing. Slack, Discord and Figma all run their real-time layer on WebSockets. The cost: you lose HTTP's conveniences (caching, simple retries, many L7 proxy features), you must write your own reconnect and resume logic, and some corporate proxies break it.

Rung 5: WebRTC (peer to peer)

For audio, video or very low-latency game state between a few people, browsers can talk directly to each other over UDP with WebRTC. A server is still needed for signalling (exchanging connection offers, usually over a WebSocket) and for STUN/TURN to get through NAT. Mention it for video calls; it is overkill for chat.

From your world

A WebSocket gateway is an epoll loop holding a huge number of mostly idle TCP sockets. The limits are the ones you already know: ulimit -n file descriptors, the listen backlog (net.core.somaxconn, which LinkedIn found at its default of 128), socket buffer memory and ephemeral ports on the load balancer side. WhatsApp's 2012 post shows kern.ipc.maxsockets=2400000 and kern.maxfiles=3000000 on a 24-core box. Heartbeats (WebSocket ping/pong) are your BFD or keepalive timers: they detect dead peers that never sent a FIN.

Hop 2: getting the update to the right gateway

Now say the user's phone holds a WebSocket to gateway-7, and the order service in another rack learns that the rider picked up the food. How does the event reach gateway-7? Hello Interview lists three answers, and they form their own ladder.

  1. Gateways poll a store. Each gateway checks a database or cache for changes for its users every second. Simple and stateless, but wasteful, and latency is the poll interval. Fine for low-volume feeds.
  2. Registry + direct send (or consistent hashing). When a user connects, the gateway writes user42 -> gateway-7 to a registry with a TTL (time to live: an expiry time after which the store deletes the entry by itself, like a MAC table entry ageing out), and refreshes it while the user stays connected. A sender looks up the gateway and calls it directly. Netflix's Zuul Push documents exactly this two-level registry: a local in-memory map on each push server, plus an off-box global store such as Redis, Cassandra or DynamoDB, with a record TTL. A variation skips the registry: hash the user (or channel) to a gateway, so everyone knows where a user lives. Slack does this for channels.
  3. Pub/sub topics. Gateways subscribe to topics for the users or rooms they currently hold (chat:room9). Senders publish once, without knowing any gateway. Redis Pub/Sub is the common interview answer. This is the best fit when one update goes to many users (a group chat, a live match).
  1. Asha's phone sends the message over its WebSocket to Gateway 1, which hands it to the stateless chat service.
  2. The chat service stores it durably first. The database is the truth; the real-time path is only a fast notifier.
  3. It publishes once to the topic for room 9. It does not know or care which gateways hold the members.
  4. Gateways 2 and 3 subscribed to room:9 when Ravi and Meera connected, so each gets one copy.
  5. Each gateway writes the frame to its local sockets. One publish, two deliveries.
  6. If a gateway dies, its clients reconnect elsewhere and fetch what they missed from the store using their last seen message id.

Redis Pub/Sub is fire-and-forget. If a gateway is not subscribed at the moment of publish, the message is gone. That is why the durable write in step 2 matters: pub/sub only says "something changed", and the store lets a reconnecting client catch up.

Level 4 - Advanced

The hard parts that break real systems

Reconnect storms (the thundering herd)

Deploy a new gateway version, or lose one region, and a million clients reconnect in the same second. Every reconnect does TLS, auth, a registry write and many subscriptions. Discord learned this the hard way: nearly 5 million session processes stampeded a guild registry, timeouts piled up, queues ballooned and Erlang VMs ran out of memory, causing cascading outages. Their fix was a semaphore that makes sessions give up early instead of queueing. The standard defences:

  • Jittered exponential backoff on the client (wait random 0-1 s, then 0-2 s, 0-4 s...).
  • Spread planned disconnects. Zuul Push has a "reconnect dither" setting that randomises each client's maximum connection lifetime, so reconnects are spread over time instead of synchronised.
  • Drain gateways slowly during deploys (close 1% of connections per minute) and use admission control to shed load with a "retry after" hint.

Missed messages and resume

Connections drop all the time on mobile. Treat the socket as a fast but lossy pipe. Give every update a per-stream sequence number or id. On reconnect, the client says "my last id was 1041" (SSE does this for you with Last-Event-ID). The server replays from a durable store or a short in-memory buffer. Facebook Messenger formalised this as snapshot + delta: fetch one snapshot over HTTPS, then apply pushed deltas over MQTT. Their post reports about 40% less non-media data, and switching from JSON to Thrift cut payloads by roughly half. Figma does the same on reconnect: download a fresh copy, reapply offline edits, then resume syncing.

Ordering

Order matters per conversation, not globally. Route all events of one chat or document through one owner (one partition, one channel server or one document process) and stamp a sequence number there. Figma runs a separate server process per multiplayer document. Slack maps each channel to one Channel Server by consistent hashing. Discord relies on one guild process per server and built Manifold to fan out in parallel without breaking that order.

Hot topics (one update, millions of receivers)

A cricket score or a celebrity's live stream turns one publish into millions of socket writes. Fan-out must be spread across many gateways, and each gateway should receive one copy and multiply it locally. Discord measured that a single Erlang send took 30-70 microseconds, so publishing one event in a big guild took 900 ms to 2.1 s, until Manifold grouped receivers by node and sent one message per node. For very large audiences, sample or batch (see Live comments) and consider pull instead of push.

Load balancers and idle timeouts

Long-lived connections confuse load balancers built for short requests. Zuul's docs warn that ELB and older HAProxy or Nginx versions cut idle connections after a short timeout, so you must raise the idle timeout and send heartbeats more often than it. Connections are also "sticky by nature": adding a new gateway does not rebalance existing users until they reconnect. Use least-connections balancing, and cap each connection's lifetime so the fleet slowly rebalances.
