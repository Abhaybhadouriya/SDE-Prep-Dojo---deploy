Kafka, Kubernetes and Docker in this pattern

Kafka

Kafka sits behind the real-time layer, not in front of every socket. Producers (order service, location service) write durable events to Kafka topics keyed by order id or chat id, which keeps per-key order (partitions). A small "router" consumer group reads those topics and forwards each event to the right gateway through the registry or pub/sub. Kafka is a poor fit for one topic per user: millions of topics is not what it is built for, and gateways would have to consume partitions full of other people's events. Use it as the durable spine and replay source, and keep the last hop on Redis, NATS or direct RPC.

Kubernetes

  • Gateways are stateful in practice. Run them as a Deployment, but give them a long terminationGracePeriodSeconds and a preStop hook that drains connections slowly, so a rollout does not trigger a reconnect storm (rollouts).
  • Autoscale on connections, not CPU. Idle sockets use memory and fds, not CPU. Export "open connections" as a custom metric for the HPA (autoscaling).
  • Ingress timeouts. NGINX Ingress and cloud load balancers default to short idle timeouts; raise read/send timeouts for WebSocket and SSE routes, and disable response buffering for SSE (Ingress).
  • PodDisruptionBudgets stop node drains from killing too many gateways at once.

Docker

File-descriptor limits are per container. Set --ulimit nofile=1048576:1048576 (or the Kubernetes equivalent through the node's runtime config) and tune net.core.somaxconn with namespaced sysctls. Remember that these are kernel limits inside a network namespace (Docker internals).

# Kubernetes: a gateway that drains gently on shutdown
spec:
  terminationGracePeriodSeconds: 300
  containers:
  - name: ws-gateway
    image: ws-gateway:1.4.2
    lifecycle:
      preStop:
        exec:
          # The app drains on SIGUSR1 (closes ~2% of sockets every 10 s), so the
          # hook needs no curl in the image. PID 1 is the gateway process.
          command: ["/bin/sh", "-c", "kill -USR1 1; sleep 280"]
    # preStop time counts against terminationGracePeriodSeconds (300):
    # 280 s of draining leaves about 20 s after SIGTERM to finish.
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
