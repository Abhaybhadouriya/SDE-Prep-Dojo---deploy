Where Kafka, Kubernetes and Docker fit

Kafka

  • The message event log: topic channel-events keyed by channel_id, so all events of a channel land in one partition and keep their order (topics & partitions).
  • Consumers: search indexer, notification service, mention counters, compliance export, analytics, link unfurling. Each is its own consumer group with its own lag.
  • Not on the hot path to connections: Kafka is not built for one topic per user or per channel at millions of topics. The channel-server -> gateway path stays an in-memory RPC fan-out.
  • Slack also used Kafka as a durable buffer in front of Redis for its job queue (1.4 billion jobs on busy days, 33K jobs/s peak) - the same "buffer the bursts" idea for top-of-hour spikes.
  • Notification delivery needs idempotency (delivery semantics): key by (message_id, user_id) so a replay does not double-buzz a phone.

Kubernetes and Docker

  • Stateless tiers (web API, admin servers, notification workers, indexers) are ordinary Deployments with an HPA on CPU or on Kafka lag (autoscaling).
  • Gateways hold long-lived connections. Rolling them kills sockets. Use a long terminationGracePeriodSeconds, a preStop hook that stops accepting new sockets and sends clients a "reconnect elsewhere" event in batches, and a PodDisruptionBudget so only a few drain at once. Clients reconnect with jittered backoff.
  • Channel servers are stateful and owned by a ring: a StatefulSet gives stable names; the ring manager, not Kubernetes, decides ownership. Readiness only after the ring has assigned channels and warm history is loaded.
  • Behind a cloud L4 load balancer or an Envoy-based Gateway API for WebSocket upgrade and TLS.
  • Microsoft said in 2020 it planned to move Teams from VM-based deployments to containers on Azure Kubernetes Service. Every service ships as a Docker image built once, promoted through rings.
# Gateway pods: drain WebSockets gently on rollout
apiVersion: apps/v1
kind: Deployment
metadata: { name: gateway }
spec:
  replicas: 60
  strategy: { rollingUpdate: { maxUnavailable: 2, maxSurge: 4 } }
  template:
    spec:
      terminationGracePeriodSeconds: 600     # time to migrate ~375K sockets slowly
      containers:
      - name: gateway
        image: registry.example.com/chat/gateway:1.42.0
        ports: [{ containerPort: 8443 }]
        lifecycle:
          preStop:
            exec: { command: ["/bin/gateway-ctl", "drain", "--batch=5000", "--interval=1s"] }
        readinessProbe: { httpGet: { path: /ready, port: 8080 }, periodSeconds: 5 }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: gateway-pdb }
spec:
  maxUnavailable: 2
  selector: { matchLabels: { app: gateway } }
