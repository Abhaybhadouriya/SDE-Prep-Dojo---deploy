Quick quiz

In Slack's real-time design, what is hashed onto the consistent-hash ring to pick a channel server?

  1. The user id of the sender
  2. The channel id
  3. The workspace id
  4. The WebSocket connection id
Channel ids are hashed to channel servers. A team's channels spread over all hosts, so one failure touches a small slice of each team.

Why fan out one copy per gateway instead of one per user?

  1. Gateways can decrypt messages
  2. It makes ordering global
  3. Network sends from the channel server drop from "members online" to "gateways with listeners"
  4. Users do not need real-time delivery
Each gateway copies locally to its own sockets, like a last-hop multicast router. This is what Discord's Manifold and Slack's Flannel plan do.

What is the cheapest correct way to show whether a channel is unread?

  1. Compare the channel's latest message id with the user's last-read id
  2. Increment a counter for each member on each message
  3. Scan all messages on every page load
  4. Ask the client to count
Time-sortable ids make this a single comparison. Per-member counters cost a write per member per message.

With 60M connections and a heartbeat every 30 s, roughly how many heartbeats per second hit presence?

  1. 20K
  2. 200K
  3. 600K
  4. 2M
60M / 30 = 2M per second - far above the message rate, which is why presence lives in memory.

What did Microsoft switch off for two weeks in 2020 to cut peak load on parts of Teams by 30%?

  1. File uploads
  2. The typing indicator
  3. Push notifications
  4. Message search
Typing is low value, high volume. Design it behind a flag so it can be browned out.

Why did Slack move away from one MySQL shard per workspace?

  1. MySQL could not store text
  2. Workspaces were too small
  3. Big customers outgrew the largest hardware and one shard outage took a whole customer down
  4. Vitess required it
Tenant sharding gives hot spots and a big blast radius; sharding messages by channel spreads load.

How does LinkedIn's presence design avoid showing a user offline during a brief network blip?

  1. It only publishes offline when a timer (d + 2e) fires and the entry, which lives d + e after the last heartbeat, has expired
  2. It never publishes offline
  3. It writes every heartbeat to a database
  4. It asks the user to confirm
Each heartbeat resets the delayed trigger; short gaps never fire it, so status does not flap.

Where does Kafka fit best in this design?

  1. One topic per user for delivery
  2. One topic per channel
  3. Replacing WebSockets
  4. An event log keyed by channel_id feeding search, notifications and compliance
Kafka is great for ordered, replayable side paths; it is not built for millions of tiny per-user topics.
