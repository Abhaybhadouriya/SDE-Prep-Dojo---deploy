Architecture, step by step

This follows the structure Slack published for its real-time stack. Click Next or Play. Steps 1-3 are what happens when you open the app; steps 4-8 are one message being sent.

  1. Boot. The client calls the web app API (stateless; Slack's is a Hack/PHP monolith). It gets an auth token, a slim initial state and the WebSocket URL. Metadata comes from the sharded SQL store.
  2. Connect. The client opens one WebSocket to the nearest region. An Envoy edge proxy terminates TLS and hands the connection to a gateway server, which keeps the user's subscriptions in memory. Gateways are the only tier deployed in many regions.
  3. Subscribe. The gateway reads the user's channel list and subscribes, asynchronously, to every channel server that owns one of those channels. It finds them with the same consistent-hash ring everyone uses. Now the user can receive events.
  4. Send. Asha posts a message through the normal HTTPS API with a client-generated client_msg_id for idempotency. The API checks permission (is Asha a member of C42?) and rate limits.
  5. Route. An admin server (stateless) hashes the channel id on the ring and forwards to the one channel server that owns C42.
  6. Order and persist. The channel server is the single writer for C42, so it assigns the next ordered id. The message is written durably to the message store (and an event log such as Kafka) before it is acknowledged. The channel server also keeps recent history in memory.
  7. Fan out to gateways. The channel server sends one copy per subscribed gateway, in every region - not one per user.
  8. Deliver. Each gateway pushes the event down the WebSocket of every local, subscribed device. Slack reports about 500 ms end to end worldwide. Offline members get nothing here; the notification service handles them (next section).

Side paths that hang off the event log (not drawn, to keep it readable): a notification service that decides who gets a mobile push or email (offline, not muted, mentioned or DM), a search indexer, unread/mention counters, compliance export and analytics. All of them are Kafka consumer groups reading the same stream at their own speed.

From your world

A gateway subscribing to channel servers is IGMP/PIM join for a multicast group: the gateway says "I have listeners for group C42", and the channel server (the root of the tree) sends one copy per joined branch. When the last local listener leaves, the gateway prunes its subscription. The hash ring that maps channel to channel server is the same idea as ECMP or Maglev hashing a flow to one backend, with the key being the channel id instead of a 5-tuple.
