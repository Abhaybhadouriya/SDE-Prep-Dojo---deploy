Interview: driving the 45 minutes

Asked at Microsoft (Teams is its product), Atlassian, and as a variant of the chat question at Meta, Amazon and Flipkart. The interviewer usually wants you to show you know how it differs from 1:1 chat. Follow the interview framework:

  1. 0-5 min: scope Workspaces, channels, DMs, threads, history, unread, presence, search. Ask: max channel size? Retention? Enterprise compliance in scope?
  2. 5-10 min: numbers DAU, messages/s, fan-out, concurrent connections, heartbeats. Conclude: "delivery fan-out and presence dominate, not writes".
  3. 10-15 min: API + data model HTTPS send, WebSocket receive; metadata in SQL, messages by (channel, bucket); bookmark-based unread.
  4. 15-25 min: high-level design Gateways per region, channel servers on a hash ring, message store, Kafka side paths.
  5. 25-40 min: deep dives Large-channel fan-out; presence; unread + multi-device; sharding by channel; search permissions. Let the interviewer pick two.
  6. 40-45 min: failures and ops Reconnect storms, channel server failover, region drain, brownouts.

60-second answer, said out loud: "Clients send messages over HTTPS and receive over a WebSocket held by regional gateways. Each channel is owned by one channel server chosen by a consistent-hash ring; it orders messages, stores them in a message store partitioned by channel and time bucket, and fans out one copy per gateway that has a subscriber, not one per user, so a 50K-member channel costs a few hundred sends. Gateways copy locally to sockets. Presence is heartbeats with in-memory timeouts, sharded by user, and clients subscribe only to users on screen. Unread state is a per-user read bookmark, not a counter per message. Kafka carries side paths: search indexing, notifications, compliance. Metadata (workspaces, channels, members) lives in sharded SQL."

SDE-1 stops here / SDE-2 adds. SDE-1: WebSocket gateways, HTTPS send, messages partitioned by channel, a channel server per channel, fan-out to online members, presence with heartbeats and a TTL, read bookmarks for unread. SDE-2 adds: per-gateway fan-out for huge channels, the hash ring and failover, presence subscription only for visible users, reconnect storms and resume-from-event-id, hot channels, shared channels across tenants, and permission-filtered search.

You might confuse this with 1:1 chat (WhatsApp). WhatsApp-style designs fan out per recipient and store per-user inboxes, which is fine for groups of a few hundred. Team chat has channels of 50K people and a shared history everyone scrolls, so you store once per channel and fan out per gateway. Also do not confuse presence (soft, lossy, can be dropped under load) with messages (durable, ordered, never dropped).

Common mistakes

Common mistakes: copying the WhatsApp design and fanning out per user for a 50K channel; one Kafka topic per channel or per user; a database write per heartbeat; an unread counter incremented for every member on every message; sharding everything by workspace; sending the whole workspace roster at login; forgetting permission filtering in search; treating typing indicators as durable messages.

How is designing Slack/Teams different from designing WhatsApp?

Four big differences. (1) Group size: channels can have tens of thousands of members, so fan-out per user is too expensive; route by channel and fan out per gateway. (2) History: messages are business records kept for years and searchable, so the server is the system of record, not a temporary relay. (3) Tenancy and compliance: the company owns the data; retention, legal hold, export, residency, customer keys. (4) Desktop-heavy usage: users are online all day, so presence and typing generate far more events than messages.

How to answer

Lead with "the key changes from 1:1 chat are..." and list them, then show how each changes one box in the diagram. It signals you are not reciting a memorised WhatsApp answer.

Likely follow-ups
  • Then why not use the same per-user inbox model?
  • Would you still use end-to-end encryption? (Usually no: search and compliance need server access; offer customer-managed keys instead.)
A user's WebSocket is on gateway 17. A message is posted to their channel on a different machine. How does it reach them?

The channel is owned by one channel server, found by consistent hashing of channel_id. When the user connected, gateway 17 subscribed to the channel servers for all of the user's channels. On post, the API routes to the owning channel server, which persists, assigns order and sends one copy to every subscribed gateway, including 17, which pushes it down the socket. Slack runs this design and reports about 500 ms worldwide delivery.

How to answer

Contrast two options: a user-to-gateway registry in Redis (good for DMs) and channel-keyed routing (good for channels). Pick the second for team chat and say why: one lookup per message instead of one per member.

Likely follow-ups
  • What happens when the channel server dies? (Ring manager reassigns; under 20 s at Slack; messages already durable.)
  • How do you avoid two owners after a ring change? (Epoch / fencing token.)
  • Could you use Redis pub/sub instead? (Yes for smaller scale; you lose in-memory history and ordering control.)
Someone posts @channel in a 100,000-member channel. Walk me through what happens and what breaks.

The write is one message - easy. The problems are the fan-out: tens of thousands of online pushes, tens of thousands of notification decisions, and a herd of clients fetching, reacting and marking read. Use per-gateway fan-out (a few hundred sends, not 100K), lazy client updates, and queue notifications through rate-limited workers (offline users only, respect mute and do-not-disturb). Coalesce identical history reads and serve the newest page from the channel server's memory. Product guardrails: restrict @channel in huge channels, or warn the sender.

How to answer

Separate the three costs (realtime push, notifications, read herd) and give one mitigation for each. Quote Discord: publishing in a huge guild took up to 2.1 s before they grouped sends by node.

Likely follow-ups
  • How do you count how many people read it? (Compare bookmarks lazily; do not write per read.)
  • What if 20,000 people react with the same emoji? (Aggregate reaction counts; batch reaction events per second.)
Design presence for 50 million concurrent users.

Heartbeats every d seconds go to presence servers sharded by user id, held in memory with a TTL. Online is published on the first beat; offline only after a timer of about d + 2e expires without a beat (LinkedIn's design), which suppresses flapping. Clients subscribe only to users visible on screen, through their gateway. Last-seen is written on disconnect, not per heartbeat. At 30 s heartbeats, 50M users is about 1.7M heartbeats/s, so this must be memory-only. Presence is first in line to be degraded under load.

How to answer

Do the heartbeat maths out loud - it shows why a database write per heartbeat is impossible. Then cover: detection, distribution (who gets told), and degradation.

Likely follow-ups
  • How do you handle a user on three devices? (Online if any device is active; "away" when all idle.)
  • What happens when a presence server crashes? (Users look offline for a moment; rebuild from the next round of heartbeats; Discord used semaphores so sessions failed fast instead of piling up.)
How do you compute unread counts and mention badges efficiently?

Store a read bookmark per (user, channel): the last read message id. Because ids are time-sortable, "unread?" is latest_id > last_read_id, which needs only the channel's latest id (cached) and the user's bookmark. Exact counts for the open channel are a range count capped at 99+. Keep a real counter only for @mentions, incremented for the few mentioned users. Marking read on one device updates the bookmark and emits an event to the user's other devices.

How to answer

Start by rejecting "increment a counter for every member" with the maths (20,000 writes per post in a big channel). Then show the bookmark.

Likely follow-ups
  • Unread counts across 500 channels at login? (Batch: latest ids from cache, bookmarks from one user-keyed read.)
  • Threads? (Separate bookmark per followed thread.)
How would you shard the message data? Why not one shard per company?

Shard messages by channel id (with time buckets inside). One-shard-per-tenant is attractive for isolation but fails at both ends: a huge enterprise outgrows the biggest machine, and a shard outage takes a whole company offline. Slack lived through this and moved to Vitess with channel-id sharding; it reports 2.3M QPS peak at 11 ms p99. Keep tenant-level boundaries where they help: the search index, encryption keys, and residency placement.

How to answer

Say "the tenant is the natural unit for isolation, the channel is the natural unit for load", then explain which data uses which key.

Likely follow-ups
  • How do shared channels between two companies work? (One copy of the channel on the originating shard, bridge rows per workspace.)
  • How do you list all channels of a user fast? (Secondary index on membership by user id.)
How do you guarantee message order in a channel, and no duplicates?

One owner (the channel server) sequences each channel, assigning increasing ids; the store's clustering order is by id, so history reads are ordered. Clients send a client_msg_id; the server dedupes on (channel, client_msg_id) so retries do not create twins. Clients render by server id, and show their own unsent message as "pending" until the ack arrives. Global order across channels is not needed.

How to answer

Scope ordering to "per channel", name the single sequencer, then idempotency key. Mention fencing for owner changes.

Likely follow-ups
  • Two people send at the same millisecond? (Sequencer decides; both see the same order.)
  • Edits and deletes? (Events referencing the original id; tombstone for delete.)
Design search across messages with correct permissions.

Index from the event log (Kafka) into Solr/Elasticsearch, partitioned by workspace. At query time, the search service fetches the user's channel memberships and applies them as a filter, plus public channels of the workspace. Rank in two phases: cheap text score to get candidates, then a re-ranker with recency, author affinity, channel importance and reactions (Slack's approach). Edits and deletes are indexed as updates/tombstones; retention deletes whole time ranges.

How to answer

Two keywords: async indexing and query-time permission filter. Explain why not to bake ACLs into each document (membership changes would need reindexing every message).

Likely follow-ups
  • A user is removed from a private channel - when do results disappear? (Immediately, because the filter uses live membership.)
  • How fresh is the index? (Seconds; show a "recent" fallback from the DB for the last minute if needed.)
It is March 2020 and traffic doubles in a week. What do you do?

Buy time first, then add capacity. Brownout low-value features (Teams turned off the typing indicator for two weeks: 30% less peak traffic on some parts), rate limit non-critical APIs via central config, reduce prefetch (Teams' mobile calendar prefetch change cut requests 80%), lengthen cache TTLs, compress cache payloads (Teams: protobuf plus LZ4 gave 65% smaller payloads). Then scale out: more regions so each holds less spare capacity, smaller clusters, flexible VM types, move background work to regions where it is night. Freeze non-critical changes.

How to answer

Structure: protect the core (send/receive), shed the optional, then scale. Cite the real Teams numbers - interviewers at Microsoft know this post.

Likely follow-ups
  • How do you decide which features to brown out? (Rank by user value vs cost; pre-build flags.)
  • How do you forecast? (Teams used ARIMA and other models, plus external data like COVID impact dates.)
How do you deploy a new version of the gateway without disconnecting 60 million users at once?

Roll a few gateway pods at a time (PodDisruptionBudget), drain each slowly: stop accepting new sockets, then tell connected clients in batches to reconnect, with random jitter. Clients reconnect to other gateways, resume from their last event id, and re-subscribe. Keep boot cheap with an edge cache so reconnects do not hammer the backend. Watch reconnect rate and boot latency as rollout gates.

How to answer

Show you know WebSockets are stateful: "rolling restart" means "controlled reconnect storm". Name drain, jitter, resume, and gates.

Likely follow-ups
  • What if a client misses events during the switch? (Resume by event id; full sync only for channels that changed.)
  • Why not keep the same pod forever? (Kernel and security patches; you will drain eventually, so make it routine.)

Scenario: Monday 9 am, everyone in one region connects and boot takes 40 seconds

A large customer's users report long loading screens every morning. Backend metadata DB CPU is pegged between 8:55 and 9:10; the rest of the day is fine.

Weak answer: "Add read replicas to the metadata DB."

Strong answer: the boot call sends the full team snapshot, and every user in a 30K-person company asks for nearly the same data at the same time. Make boot lazy (send only channels with unread and what is on screen, fetch the rest on demand) and put an edge cache with team affinity in front, so many users of the same team are served from one cached copy - Slack's Flannel approach cut boot payloads up to 44x and served 4M connections. Add jitter to client auto-reconnect and use "resume since event id" for clients that were only briefly gone.

Likely follow-ups
  • How do you keep the edge cache correct? (It subscribes to the same real-time events and updates itself.)
  • What metric proves the fix? (p95 time-to-first-render at boot, DB QPS per connecting user.)

Scenario: one channel server is at 100% CPU and its channels lag by seconds

A company-wide "#incident" channel with 80,000 members is extremely active during an outage. Its channel server is hot; other channels on the same host are slow too.

Weak answer: "Add more channel servers to the ring."

Strong answer: adding servers moves other channels, but this one channel still lives on one host. Short term: move the co-located channels off the hot host (ring weight or virtual-node change), batch typing and reaction events for that channel, and make sure fan-out is per gateway. Serve history reads from memory with coalescing. Longer term: allow a "split" mode for extreme channels where the sequencer stays single but fan-out is handed to a tier of relay nodes (a tree), the same way a multicast tree adds replication points.

Likely follow-ups
  • Can you shard one channel's ordering? (Only by giving up total order, e.g. per-thread order - usually not worth it.)
