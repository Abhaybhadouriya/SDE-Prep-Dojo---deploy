Deep dives

1. Finding the right machine: channel servers on a consistent-hash ring must-know

The classic chat question is "the receiver's socket is on another server - how does the message get there?" For 1:1 chat a user -> gateway registry is enough (see WhatsApp). Team chat flips the key: most traffic is "post to channel", so route by channel.

  • Each channel id (and in Slack's design, also user, team, file and huddle ids) is hashed onto a ring. The next channel server clockwise owns it. Slack reports a host can hold about 16 million channels at peak.
  • Owning a channel means: be the single sequencer for its order, keep its recent history in memory, and keep the set of gateways subscribed to it.
  • A team's channels are spread over all channel servers, so a dead server hurts only a small slice of each team.
  • A ring manager (Slack calls them CHARMs) watches health, replaces a dead host, and publishes the new ring through service discovery (Consul). Slack's replacement host is ready in under 20 seconds; during that window, users of the affected channels see higher latency, not lost messages, because messages were persisted first.
  • Use virtual nodes (many points per server on the ring) so load evens out and adding a server moves only about 1/N of channels. See Distributed Building Blocks.

Split brain risk. For a few seconds two channel servers might both think they own C42 (old ring vs new ring). Protect order with a fencing token / ring epoch: the message store rejects writes stamped with an old epoch, or ids come from a per-channel sequence in the store. See Coordination & Consensus.

2. Large channels: the fan-out problem must-know

A 50,000-member "#announcements" channel with 20,000 people online turns one @channel post into 20,000 pushes, plus 20,000 notification decisions, plus a thundering herd of clients fetching the new message, reacting, and marking read. Tools, from simplest to strongest:

  1. Fan out per gateway, not per user. Slack's Flannel post listed exactly this as the next step: send one copy of each event to each edge server, which then fans out to its users. Discord hit the same wall with Erlang: publishing in a huge guild took 900 ms to 2.1 s until they built Manifold, which groups recipients by remote node and makes at most one send per node.
  2. Only push to what is on screen. A client in a 50K-member workspace does not need every membership change or presence flip. Subscribe to the active channel's full events and to a lighter "unread badge" signal for the rest.
  3. Lazy loading at boot. Slack's old rtm.start sent the whole team (all users, channels, members) at startup. For a 32K-user team, lazy loading through its edge cache Flannel made the boot payload about 44x smaller (about 7x for a 1.5K-user team).
  4. Coalesce the read herd. After a big post, thousands of clients fetch the same "latest messages". Discord's Rust data services do request coalescing: the first request runs the query, the rest wait for its result. Route by channel id so the same instance sees all those requests.
  5. Defer the non-urgent. Notifications for 50K people go through a queue with rate limits; nobody needs an email within 100 ms. Admins can also restrict who may post @channel in huge channels (a product fix for a systems problem - interviewers like it).

Name the threshold explicitly: "Small channels and DMs: push to everyone. Above a few thousand members: per-gateway fan-out, lazy member lists, no presence for the full list, rate-limited notifications." Hello Interview's WhatsApp breakdown makes the same move at about 25 members for switching from per-user to per-chat pub/sub channels. Pattern page: Fan-out: Push vs Pull.

Stop here for SDE-1. If you can explain the hash ring that picks a channel server and why large channels fan out per gateway instead of per user, you have the core of this round. Deep dives 3 and 4 (presence, unread) are "good to know" and often come up as follow-ups; 5 and 6 are SDE-2 depth. Reading time to here is about 20 minutes.

3. Presence at scale (the green dot) good to know

Our estimate gave ~2.2M heartbeats/s - presence is the biggest event source in the system. Designs that work:

  • Heartbeat + timeout, in memory. LinkedIn's published presence design: while connected, a heartbeat for member M arrives every d seconds. Here e is a small grace margin, for example 5 s with d = 30 s. If no live entry exists, publish "online" and store an entry that expires after d + e. A per-member timer fires after d + 2e; if the entry has expired, publish "offline". So any gap between heartbeats shorter than d + e keeps the entry alive and never shows as offline - no flapping. Only silence longer than d + e (detected when the timer fires at d + 2e) publishes "offline". They report p99 under 200 ms for status changes.
  • Shard presence servers by user id. Slack hashes users to presence servers; the gateway is where clients ask for presence.
  • Subscribe only to visible users. Slack clients get presence updates only for users currently on screen. Slack reported that moving presence to this pub/sub model cut the presence events clients received by 5x.
  • Last seen is not a heartbeat log. Write "last active" only on disconnect or every few minutes, not on every heartbeat.
  • First to degrade. In March 2020 Microsoft turned off the Teams typing indicator for two weeks, which cut peak traffic by 30% on parts of the infrastructure. Design presence and typing behind feature flags so you can brown them out.

From your world

This is OSPF hello / dead interval (hello 10 s, dead 40 s) or BFD's detect multiplier. Same trade-off too: a smaller d detects failure faster but costs more packets; a bigger one is cheaper but slower. And just like you dampen route flaps, you dampen presence flaps so a laptop going through a Wi-Fi handover does not spam 5,000 colleagues.

4. Unread counts, mentions and multi-device sync good to know

Never store "unread = 17" as a counter you increment for every member on every message - that is a write per member per message (20,000 writes for one big post). Instead:

  • Store a bookmark, compute the count. Each (user, channel) row holds last_read_message_id. Since message ids are time-ordered (Snowflake-style; see Unique ID Generator), "is this channel unread?" is just latest_message_id > last_read_message_id - one comparison, no counter.
  • Exact numbers only where needed. The sidebar mostly needs bold/not bold. The exact "17 new" is computed for the open channel by counting ids after the bookmark (capped: show "99+").
  • Mentions are the exception. @you is rare and important, so keep a real mention_count per member and increment it only for mentioned users (or for @channel, lazily, by comparing with the bookmark).
  • Multi-device. When the laptop calls conversations.mark, the server updates the bookmark and emits a channel_marked event to the user's other devices, which clear their badge. Push notifications already sent to the phone are withdrawn by a silent push.
  • Catch-up after reconnect. The client remembers the last event id it saw; on reconnect it asks "what changed since X?" For a short gap the channel server's in-memory history answers; for a long gap, fall back to history API calls only for channels that are now unread. This avoids the reconnect storm Slack described, where a whole office reconnecting after a network blip overloaded the backend.

From your world

The read bookmark is a TCP cumulative ACK: "I have everything up to sequence N". The unread count is the sender's view of bytes in flight (latest seq minus acked seq). Nobody keeps a per-byte flag - and you should not keep a per-message-per-user flag either.

5. Storage, sharding and hot partitions deep dive (SDE-2)

  • Shard by channel, not by tenant. Slack's first design (one shard per workspace) broke in three ways: the largest customers outgrew the largest machines, a shard outage took a whole customer down, and cross-company features (Enterprise Grid, Slack Connect) broke the "one team, one shard" assumption. With Vitess, message data is sharded by channel id. Slack reported 2.3M QPS at peak (2M reads, 300K writes) at 2 ms median and 11 ms p99.
  • Shared channels: one copy. When two companies share a channel, Slack keeps a single copy of the channel and its messages on the originating side's shard, plus a shared_channels bridge row per workspace for local names and settings. Copying messages to both sides was rejected: double writes, divergent histories.
  • Time buckets bound partition size. The (channel_id, bucket) key keeps any one partition from growing forever. A busy channel gets small buckets; a quiet channel's bucket is large.
  • Hot channel. A huge, busy channel is a hot partition. Discord saw a single hot partition slow quorum reads for unrelated queries on the same nodes. Fixes: in-memory recent history on the channel server (most reads never reach the DB), request coalescing, and caching the newest page.

6. Search and compliance (the enterprise half) deep dive (SDE-2)

  • Index asynchronously from the event log; a few seconds of delay is fine. Partition the index by workspace, so a query only touches one tenant's data and a tenant can be deleted or moved as a unit.
  • Filter by permission at query time. A user may only see channels they belong to (and public channels of their workspace). Pass the user's channel list as a filter; never trust the client. Private channel membership changes must be honoured immediately, so filter on live membership rather than baking it into documents.
  • Rank in two stages. Slack's search uses Solr to fetch candidates with cheap features, then re-ranks in the app with a learned model (signals: message age, text score, the searcher's affinity to the author, channel priority, reactions). Adding the work graph raised searches with clicks by 9%.
  • Retention, legal hold, export, eDiscovery. Retention is a background job that deletes buckets older than the policy (time buckets make this cheap), unless a legal hold pins them. Deletion must also reach the search index, caches and backups (tombstones, then compaction).
  • Customer-managed keys. Large customers want to hold the encryption key (Slack EKM). Encrypt message content with a per-workspace key that the customer can revoke; this also makes deletion by key-destruction possible.
  • Data residency. Metadata and messages for an EU tenant stay in EU regions. Microsoft notes that even when it moved Teams background work to idle regions at night, it did so "while always respecting compliance and data residency requirements". See Security & Identity.
