Key APIs

Two kinds of interface. Commands that change data go over normal HTTPS (easy to authenticate, retry and rate-limit). Real-time events come down a single WebSocket per device. This split is how Slack works: clients post messages via the web API, and receive events over WebSocket from a gateway server.

# 1. Boot: get a token, a small initial state, and where to open the WebSocket
POST /api/client.boot            -> { user, workspaces, channel_ids_with_unread, ws_url }

# 2. Send (idempotent: client_msg_id is a UUID made on the device)
POST /api/chat.postMessage
     { channel_id, text, thread_ts?, client_msg_id }
     -> { message_id, ts }        # ts = server-assigned, ordered within the channel

# 3. History (cursor pagination, newest first)
GET  /api/conversations.history?channel_id=C42&before=<message_id>&limit=50
     -> { messages[], next_cursor }

# 4. Read marker (moves the bookmark; clears unread on all devices)
POST /api/conversations.mark { channel_id, last_read_message_id }

# 5. Membership
POST /api/conversations.join | leave | invite { channel_id, user_ids[] }

# 6. Presence: ask only for the users visible on screen
WS  -> { "type": "presence_sub", "user_ids": ["U1","U7","U9"] }

# 7. Search (permission-filtered on the server)
GET  /api/search.messages?q=deploy+failed&in=C42&from=U7&cursor=...
// Server -> client events on the WebSocket (one socket, many event types)
{ "type": "message",        "channel": "C42", "id": "1730000000.000200", "user": "U7", "text": "hi" }
{ "type": "reaction_added", "channel": "C42", "item": "1730000000.000200", "reaction": "tada" }
{ "type": "user_typing",    "channel": "C42", "user": "U7" }          // transient, never stored
{ "type": "presence_change","user": "U9", "presence": "away" }
{ "type": "channel_marked", "channel": "C42", "last_read": "1730000000.000200" }  // from another device

Cursor, not offset. Slack's API team wrote that they moved from offset pagination to opaque cursors because offsets get slow and skip or repeat rows while new messages arrive. For chat history the natural cursor is the message id itself ("give me 50 older than X"). More in API Design & Communication.
