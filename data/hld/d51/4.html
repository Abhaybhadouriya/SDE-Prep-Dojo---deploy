Data model

There are two very different kinds of data, and they want different stores.

-- Metadata (relational, sharded)
CREATE TABLE channels (
  channel_id     BIGINT PRIMARY KEY,      -- Snowflake-style id
  workspace_id   BIGINT NOT NULL,         -- the ORIGINATING workspace
  name           VARCHAR(80),
  is_private     BOOLEAN NOT NULL,
  kind           ENUM('channel','dm','group_dm'),
  created_at     TIMESTAMP
);

CREATE TABLE channel_members (
  channel_id           BIGINT,
  user_id              BIGINT,
  last_read_message_id BIGINT,             -- the "bookmark"
  mention_count        INT DEFAULT 0,      -- unread @mentions, kept as a counter
  notify_pref          TINYINT,
  PRIMARY KEY (channel_id, user_id)
);
CREATE INDEX by_user ON channel_members (user_id, channel_id);  -- "my channels"

-- Shared channels across companies: ONE copy of the channel, plus a bridge row per workspace
CREATE TABLE shared_channels (
  channel_id              BIGINT,
  target_workspace_id     BIGINT,
  originating_workspace_id BIGINT,
  name_override           VARCHAR(80),
  PRIMARY KEY (channel_id, target_workspace_id)
);
-- Messages (Cassandra/ScyllaDB style, the shape Discord describes)
CREATE TABLE messages (
  channel_id  bigint,
  bucket      int,          -- fixed time window, e.g. 10 days, so one partition never grows forever
  message_id  bigint,       -- Snowflake: sortable by time
  author_id   bigint,
  thread_root bigint,       -- null for top-level messages
  content     text,
  edited_at   timestamp,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

SQL or NoSQL? Say both, and why

  • Metadata wants SQL. Permissions and membership need transactions and constraints; it is far smaller than messages. Slack runs this, and messages too, on MySQL sharded with Vitess.
  • Messages can be either. The access pattern is "append, then range read by (channel, time)". A wide-column store does that natively and spreads writes well. Sharded MySQL also works if the shard key is the channel. Discord moved from 177 Cassandra nodes to 72 ScyllaDB nodes and saw history-fetch p99 fall from 40-125 ms to about 15 ms.
  • The shard key matters more than the engine. Slack's original design put each whole workspace on one MySQL shard. The biggest customers outgrew the biggest hardware and one shard outage took a whole company offline. Moving to shard messages by channel id spread the load.
