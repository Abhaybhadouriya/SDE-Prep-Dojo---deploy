Back-of-envelope estimation

Anchor on a public number, then state every other assumption clearly. Microsoft published that Teams had more than 75 million daily active users in April 2020. We will size for that. Everything below marked "assume" is our own round number, not a published fact.

75MDAU (Teams, Apr 2020)
~100K/speak messages sent
~3M/speak WebSocket deliveries
~180gateway servers
~3 PBmessages per year, replicated
  1. Messages written. Assume each active user sends 40 messages a day (people chat a lot at work). 75M x 40 = 3 billion messages/day. Divide by ~86,400 s/day (use 105 for quick maths): 3 x 109 / 105 = ~30-35K messages/s average.
  2. Peak. Work traffic is squeezed into about 8 hours, with peaks around 11 am and 2 pm and spikes on the hour (Slack's blog describes this shape). Assume peak = 3x average: ~100K messages/s.
  3. Fan-out (deliveries). A message goes to every online member of the channel. Most channels are small, a few are huge. Assume the average message reaches 30 online devices. 100K x 30 = ~3M WebSocket pushes/s at peak. This is the real load - 30x the write rate. Reactions, edits, read-markers and typing events ride the same pipes and can easily double it.
  4. Connections. Assume 60% of DAU are connected at peak, with 1.5 devices each: 75M x 0.6 x 1.5 = ~67M concurrent WebSockets. Discord reported one Erlang VM holding up to 500K live session processes (sessions, not raw WebSocket gateway sockets); WebSocket gateways commonly hold hundreds of thousands of mostly idle connections per box. We plan ~375K per gateway as an assumption to load-test: 67M / 375K = ~180 gateway servers, spread over regions.
  5. Presence heartbeats. If each connection sends a heartbeat every 30 s: 67M / 30 = ~2.2M heartbeats/s. That is 20x the message rate. Lesson: presence must be handled in memory, near the edge, never as a database write per heartbeat.
  6. Storage. Assume ~1 KB per message row including metadata, ids and index overhead. 3 x 109 x 1 KB = 3 TB/day. With 3 replicas: 9 TB/day, about 3.3 PB/year. Kept "forever", so storage keeps growing; old buckets go to cheaper disks.
  7. Search index. Text is maybe 200-300 bytes of the row; an inverted index is often similar in size to the text. Budget roughly 1 TB/day of new index, before replicas.
  8. Memberships and unread state. Assume 50 channels per user: 75M x 50 = 3.75 billion (user, channel) rows, each about 40 bytes (user id, channel id, last-read message id, flags) = ~150 GB. Small enough to shard and cache hot parts.
  9. Bandwidth. 3M pushes/s x ~1 KB = ~3 GB/s, about 24 Gbps egress at peak, spread over all gateway servers (~130 Mbps each). Fine for NICs; the limit per gateway is CPU and memory per connection, not bandwidth.

From your world

Notice the shape: a modest ingress rate (100K/s) multiplied into a large egress rate (3M/s). That is exactly multicast replication in a router: you do not want the source to send N unicast copies; you want each downstream hop to replicate once per interface. Gateways play the role of the last-hop router replicating to its local ports.
