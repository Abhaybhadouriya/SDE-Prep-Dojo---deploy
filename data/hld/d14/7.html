Where Kafka, Kubernetes and Docker fit

Kafka

  • Not on the hold path. The user is waiting for "you got F7"; that answer comes from the database in milliseconds. (The per-show serialiser in deep dive 5 is the exception, for extreme cases.)
  • After the decision: booking.events (held, released, confirmed, cancelled) keyed by show_id, so events for a show stay in order in one partition (keys and partitions). Consumers in separate consumer groups generate tickets, notify, update the seat map and feed analytics.
  • Outbox, not dual writes. Writing to Postgres and then to Kafka from the app can lose one of the two on a crash. Insert an outbox row in the same transaction as the booking, and let a relay or Debezium CDC publish it. Consumers dedupe on booking_id because delivery is at-least-once.
  • Waiting room telemetry (queue joins, admissions, drop-offs) is another stream used to tune the admission rate live.

Kubernetes

On-sale traffic arrives at a known minute, so pre-scale instead of waiting for the HPA: HPA reacts to metrics after they rise, and new pods and nodes take time to start. Raise minReplicas an hour before, with a scheduled job or a KEDA cron trigger, then let the HPA handle the rest (Scheduling & Autoscaling). Protect the booking pods with a PodDisruptionBudget so a node upgrade does not drain them mid-sale.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: booking-svc
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: booking-svc }
  minReplicas: 60            # raised from 6 before a big on-sale, lowered after
  maxReplicas: 200
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:
    scaleDown: { stabilizationWindowSeconds: 900 }   # don't shrink during the sale
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: booking-svc
spec:
  minAvailable: 90%
  selector: { matchLabels: { app: booking-svc } }
---
apiVersion: batch/v1
kind: CronJob                 # backup sweeper; the main sweeper is a loop in a Deployment
metadata:
  name: hold-sweeper
spec:
  schedule: "* * * * *"       # every minute (the smallest CronJob interval)
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: sweep
              image: registry.example.com/booking-tools:2.3.0
              args: ["sweep-expired-holds", "--batch=5000"]

Docker

For local practice, a Compose file with Postgres and Redis is enough to reproduce the race above and test the sweeper (Docker Compose):

services:
  db:
    image: postgres:17
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: demo }
    ports: ["5432:5432"]
  redis:
    image: redis:8
    ports: ["6379:6379"]
$ docker compose up -d
[+] Running 3/3
 ✔ Network tickets_default    Created
 ✔ Container tickets-db-1     Started
 ✔ Container tickets-redis-1  Started
$ docker compose exec redis redis-cli SET seat:1:F7 h_81 NX EX 600
OK
$ docker compose exec redis redis-cli SET seat:1:F7 h_99 NX EX 600
(nil)
$ docker compose exec redis redis-cli TTL seat:1:F7
(integer) 594

The second SET ... NX returns (nil): the key exists, so Ben's hold fails, and the key vanishes by itself after 600 seconds. For several seats at once, use a Lua script that checks every key first and sets them all only if all are free, because Redis runs a script atomically.

From your world

The conditional UPDATE is a compare-and-swap, the same idea as a cmpxchg on a lock word: "set to HELD only if it is still AVAILABLE", and the hardware (here the row lock) makes it atomic. The hold TTL is a lease, like a DHCP lease: if the client does not renew or confirm in time, the address goes back to the pool. Where it breaks: a CAS on one machine is instant; here the "memory" is a database across a network, so every retry costs a round-trip and contention costs real latency.
