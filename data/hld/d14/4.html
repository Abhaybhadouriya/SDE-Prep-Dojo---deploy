Data model

Use a relational database (PostgreSQL or MySQL) for everything about seats, holds, bookings and payments: we need transactions, conditional updates and unique constraints. Use Elasticsearch (or similar) for search, and Redis for caches. Static layouts (venue, screen, seat grid) change rarely; the per-show seat status changes constantly.

CREATE TABLE shows (
  show_id     BIGINT PRIMARY KEY,
  event_id    BIGINT NOT NULL,
  screen_id   BIGINT NOT NULL,
  starts_at   TIMESTAMPTZ NOT NULL,
  on_sale_at  TIMESTAMPTZ NOT NULL
);

-- One row per seat per show: the inventory. This is the table that matters.
CREATE TABLE show_seats (
  show_id     BIGINT      NOT NULL,
  seat_id     VARCHAR(8)  NOT NULL,          -- 'F7'
  price_tier  SMALLINT    NOT NULL,
  status      VARCHAR(10) NOT NULL DEFAULT 'AVAILABLE',   -- AVAILABLE | HELD | BOOKED
  hold_id     UUID,
  held_until  TIMESTAMPTZ,
  booking_id  BIGINT,
  version     INT         NOT NULL DEFAULT 0,
  PRIMARY KEY (show_id, seat_id)               -- seat ownership is per (show, seat)
);
CREATE INDEX ON show_seats (hold_id);
CREATE INDEX ON show_seats (held_until) WHERE status = 'HELD';   -- for the sweeper

CREATE TABLE bookings (
  booking_id      BIGINT PRIMARY KEY,
  user_id         BIGINT NOT NULL,
  show_id         BIGINT NOT NULL,
  hold_id         UUID   NOT NULL UNIQUE,     -- one booking per hold, even on retries
  status          VARCHAR(16) NOT NULL,       -- PAYMENT_PENDING | CONFIRMED | FAILED | REFUNDED
  amount_paise    BIGINT NOT NULL,            -- integer money
  idempotency_key VARCHAR(64) NOT NULL UNIQUE,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
  • Why one row per seat per show? It turns "is F7 free?" into a single-row question with a primary key, which databases answer and lock very cheaply. It also makes the hold one conditional UPDATE.
  • Sharding: shard (or partition) everything by show_id. A booking only ever touches one show, so it never needs a cross-shard transaction. At movie scale one primary is enough; at Ticketmaster scale you shard by event or show.
  • Seat map cache: a Redis bitmap or small hash per show (seatmap:{show_id}), updated by events when status changes, read by thousands of browsers. A 50,000-seat stadium needs about 6 KB per status bitmap (50,000 bits, one per seat).
