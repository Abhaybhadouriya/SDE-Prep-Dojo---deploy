Trade-offs, bottlenecks and failures

DecisionOption AOption BPick when
Seat guardConditional UPDATE in SQLRedis locks with TTLA as the truth, always. B as an optional fast pre-filter for hot shows.
Hold expirySweeper onlyLazy check in the hold query + sweeperB: correct even if the sweeper is late.
Seat map freshnessPoll every few secondsPush via SSE/WebSocketA for normal shows (simple). B for hot events where seats vanish in seconds.
Seat selectionUser picks exact seatsServer picks best availableA for cinemas. B for stadium on-sales: far fewer conflicts.
Flash crowdAutoscale everythingWaiting room + pre-scaleB. You cannot autoscale a database 100x in a minute.
Payment orderCharge, then take seatsHold, charge, confirm (refund on failure)B. Charging for a seat you cannot give is the worst outcome.
Event busApp writes DB then KafkaOutbox + CDC relayB. No lost or phantom events on crashes.

Say the choice out loud (pattern: "I would pick X because A; the cost is B; if C becomes a problem I would switch to Y"):

  • "I would hold seats with a conditional UPDATE in Postgres because it is atomic, durable and the database is already the record of who owns a seat; the cost is row-lock contention on hot seats; if one show's hold rate became too high, I would put a Redis SET NX pre-filter in front, and keep the UPDATE as the final check."
  • "I would use a waiting room because no database can absorb a million requests a second for 50,000 seats; the cost is a worse first impression and one more system; if the event were small, I would skip it and rely on rate limits."
  • "I would poll the seat map every few seconds because it is simple and cacheable; the cost is a few seconds of staleness; if seats vanish faster than that in hot on-sales, I would push changes over SSE."

What breaks, and what we do

  • Postgres primary fails: a synchronous standby is promoted (Patroni or a managed failover). Holds in flight fail with an error and the app retries with the same idempotency key. Never fail over to an asynchronous replica for seat data without accepting possible lost holds.
  • Redis seat-map cache dies: seat maps fall back to a slower DB read with a short cache, or show "loading". Bookings are unaffected, because Redis never decides ownership.
  • Kafka is down: bookings still confirm; outbox rows pile up and are published later. Tickets arrive late. Show the ticket in the app straight from the DB.
  • PSP is slow or down: holds expire while users wait. Detect PSP latency and extend holds automatically for users already in payment, or offer another payment method.
  • Bots: per-account ticket limits enforced in the DB (count confirmed + held tickets per user per event), CAPTCHA at the queue entry, device fingerprinting, and admission tokens that cannot be shared.
  • Many tiny holds that never pay (seat hoarding): limit active holds per user, shorten TTL for repeat offenders.
