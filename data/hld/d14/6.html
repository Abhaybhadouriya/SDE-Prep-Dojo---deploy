Deep dives

1. Making double booking impossible

Here is the race. Asha and Ben both read "F7 = AVAILABLE". Both send "hold F7". If the code does read, check in the app, then write, both writes succeed and the second overwrites the first. Two tickets, one seat. The fix is to make the check and the write one atomic step inside the database.

-- Hold seats F7 and F8 for 10 minutes, all-or-nothing.
BEGIN;
UPDATE show_seats
   SET status = 'HELD', hold_id = :hold_id,
       held_until = now() + interval '10 minutes', version = version + 1
 WHERE show_id = :show_id
   AND seat_id = ANY(:seat_ids)                     -- {'F7','F8'}
   AND (status = 'AVAILABLE'
        OR (status = 'HELD' AND held_until + interval '2 minutes' < now()));  -- expired (plus grace) = free
-- app: if rows_updated <> 2 then ROLLBACK and return 409, else COMMIT
COMMIT;

-- Confirm after payment: only if WE still hold them and the hold has not expired.
UPDATE show_seats
   SET status = 'BOOKED', booking_id = :booking_id, held_until = NULL
 WHERE hold_id = :hold_id AND status = 'HELD' AND held_until > now() - interval '2 minutes';
-- A real grace window: the hold query above treats a seat as free only 2 minutes AFTER
-- held_until, so nobody can take it while a payment that finished at the deadline confirms.
-- If even the grace window is missed, the confirm changes 0 rows and we auto-refund.

The phrase to use: "Correctness comes from the database, not from a lock service. A conditional update on the seat row is the guard; Redis can speed things up but never decides who owns a seat." If they push on Redis locks, mention Martin Kleppmann's point that a lock without a fencing token cannot protect a resource when a client pauses (for example a long GC) past its lease.

2. Holds, expiry and the payment race

  • Lazy plus active expiry. The hold query treats held_until + interval '2 minutes' < now() as free (lazy, after a 2-minute grace window). A sweeper also runs every few seconds: UPDATE show_seats SET status='AVAILABLE', hold_id=NULL WHERE status='HELD' AND held_until + interval '2 minutes' < now() RETURNING show_id, seat_id, and publishes the freed seats so the seat map turns green again. Lazy expiry gives correctness; the sweeper gives a fresh seat map.
  • Hold length is a business dial. Too short and people fail at the UPI app; too long and sell-outs look fake. 5-10 minutes is common. Show a countdown in the UI.
  • The nasty race: the user pays at 9:59 into a 10-minute hold, but the webhook arrives at 10:03. The confirm UPDATE finds the hold expired (0 rows). Options: a short grace window (above), or try to re-take the same seats if still free, and if they are gone, automatically refund and tell the user. Never confirm a seat you no longer own.
  • Webhooks are at-least-once. The PSP may send "paid" twice or out of order. Make the confirm step idempotent: bookings.hold_id is UNIQUE, and a second CONFIRMED event for the same booking is a no-op.
  • Lost webhooks. A reconciliation job polls the PSP for PAYMENT_PENDING bookings older than a few minutes, using the same order reference. This is the safety net (see ledger and reconciliation).
  • Charge without ticket is the worst outcome. Decide the order: hold first, then charge, then confirm; if confirm fails, refund. Use the transactional outbox so "booking confirmed" and "send ticket" can never disagree (outbox and sagas).

3. The virtual waiting room for hot on-sales

When 2 million people want 50,000 seats, most will go home without tickets no matter what we build. Our job is to make that fair, fast and calm instead of a crash. The waiting room is a queue at the edge that hands out admission at a controlled rate.

  1. Before the sale users land on a static, CDN-served waiting page. Pre-registration (Ticketmaster's "Verified Fan" is one example) and presale codes reduce bot traffic and give a known audience size.
  2. At the start everyone already waiting gets a random position (fairer than "who clicked first by a millisecond"); later arrivals join at the back.
  3. Admission rate is chosen from capacity: if the hold path handles a known rate comfortably and a user needs about 5 minutes to finish, admit that many users per minute. Increase the rate as seats run out or users leave quickly.
  4. Admitted users get a signed, short-lived token tied to their account; the booking APIs reject requests without it. The queue state lives at the edge (for example Cloudflare's Waiting Room is built on Workers and Durable Objects), so the origin barely notices the crowd.
  5. When it is sold out tell everyone still waiting right away, instead of letting them wait an hour for nothing.

What went wrong in 2022: Ticketmaster's own statement says the Eras Tour presale traffic was far above what it planned for, with bots and people without codes adding load. The lesson interviewers want: admission control, bot defence and a known audience before the sale, not autoscaling during it.

4. A live seat map that does not melt the database

  • The seat map is read thousands of times per write. Serve it from Redis: a bitmap (1 bit per seat for "taken") or a small hash per show. 50,000 seats = 50,000 bits = about 6 KB.
  • Update it from events (seat.held, seat.released, seat.booked) rather than by reading the DB on every request.
  • Push changes to open pages with SSE or WebSocket for hot shows (see Live Comments for the fan-out pattern), or poll every 2-5 seconds for normal shows. Either way it is a hint; the hold is the check.
  • Best available instead of picking: for stadiums, let the user choose a section and count, and the server picks seats. This spreads the load across rows instead of 100,000 people all fighting over the front row, so far fewer holds fail.

Order matters: if "released" and then "held" for the same seat arrive swapped, the map shows a free seat that is taken. Keying events by show_id keeps one show's events in order in one partition. Each event carries the seat's version, and the updater skips an event older than what it already applied. A page that reconnects re-reads the bitmap first, then follows the stream, like a router doing a full table sync before applying incremental updates.

5. Hot shows and scaling the write path

  • Partition by show: different shows never contend. A movie platform's write load spreads across thousands of shows naturally.
  • One super-hot show: row locks are per seat, so contention only occurs on the same seats. With the waiting room plus best-available, one Postgres primary handles a single show's hold traffic.
  • If it still is not enough: serialise holds per show through a Kafka partition keyed by show_id with a single in-memory allocator per show (like an exchange's matching engine), writing results to the DB in batches. Faster, but you trade simplicity and need careful recovery from the log. The picture and the details are below.
  • Read replicas for "my bookings" and show pages; never for the hold check.
  • Why it is fast: a decision is an array lookup in RAM, so one allocator can decide hundreds of thousands of holds per second for one show. The database sees one batched write every few milliseconds instead of a storm of competing UPDATEs.
  • Recovery: the allocator is a pure function of the log. If its pod dies, a new one loads the last state written to the database, then replays the partition from the last committed offset and reaches exactly the same decisions. Decisions must be deterministic (no random or clock-based choices), and each request carries an id so a replayed decision is not sent to the user twice.
  • The cost: a user's request is now async (they wait for a reply event over SSE or poll), you operate Kafka in the hot path, and one show's throughput is capped by one thread. That is why you reach for it only after the waiting room and best-available are not enough.

From your world

The waiting room is admission control with a token-bucket policer, like a CAR/policer on an ingress interface: tokens refill at the admission rate, each admitted user spends one, and the bucket size sets how big a burst you tolerate when the doors open. The allocator is a single-producer, single-consumer ring: one reader drains it in order, so no locks are needed. Where this breaks: a policer drops excess packets and TCP retries silently; here excess users must be queued in order and shown their position, and a dropped "packet" is an angry fan who may retry from three devices.
