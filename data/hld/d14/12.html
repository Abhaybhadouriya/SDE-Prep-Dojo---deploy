Quick quiz

Why is "read the seat, check in code, then update" unsafe?

  1. The extra SELECT makes the hold too slow
  2. Two requests both read AVAILABLE and both write
  3. Postgres forbids a SELECT before an UPDATE
The gap between the read and the write is the race; a conditional UPDATE closes it by checking inside one atomic statement. Speed is not the problem; correctness is. Postgres allows reads before writes; it just does not protect you across them unless you lock.

Ben's conditional UPDATE returns "UPDATE 0". What does that mean?

  1. The database crashed mid-statement
  2. Ben should retry until it returns 1
  3. Ben's transaction hit a deadlock
  4. The seat was no longer AVAILABLE
Zero matching rows means the WHERE condition was false at write time: Ben lost the race, so show "just taken". A crash returns an error, not a row count. Retrying the same seat just returns 0 again. A deadlock is reported as an error and rolled back.

Why does the hold query treat a HELD seat as free once held_until + 2 minutes has passed?

  1. So holds expire even if the sweeper is late
  2. So two users can share a hold briefly
  3. So the sweeper can be switched off
Lazy expiry inside the WHERE clause makes correctness independent of the background job, and the extra 2 minutes is a real grace window for late payments. Two owners is exactly what we prevent. The sweeper still runs so the seat map shows freed seats promptly.

Payment succeeds after the hold expired and the seat was resold. The right move?

  1. Confirm anyway; the payer has priority
  2. Cancel the other person's booking
  3. Refund automatically and tell the user
  4. Keep the money and offer a credit later
Never confirm a seat you no longer own; compensate with an idempotent refund. Confirming double-books the seat. Cancelling the other booking punishes someone who did nothing wrong. Keeping money without giving a ticket is the worst outcome and usually illegal.

What is the main tool for a 2-million-fan on-sale?

  1. A bigger primary database server
  2. A waiting room that admits at a fixed rate
  3. Autoscaling every tier when traffic hits
Demand shaping at the edge keeps the booking tier at the load it was sized for. A bigger server buys perhaps 2-4x, not 40x. Autoscaling takes minutes and cannot scale the database 100x, while the crowd arrives in one second.

A user's first hold on an event runs UPDATE ... SET count = count + 2 WHERE ... AND count + 2 <= 6. What happens?

  1. It matches 0 rows: wrongly looks over limit
  2. It inserts a new row with count = 2
  3. It fails with a unique-key violation
  4. It works, because count starts at NULL
There is no row yet, so UPDATE matches nothing and the app reads 0 rows as "limit exceeded". UPDATE never inserts; that is what the upsert (INSERT ... ON CONFLICT) is for. No insert happens, so no unique-key error. And NULL + 2 is NULL, which fails the check anyway.

What is Redis SET key value NX EX 600 good for here?

  1. The permanent record of who owns a seat
  2. A fast pre-filter hold that expires itself
  3. A replacement for the PSP webhook
  4. Locking the whole show for 10 minutes
It is an efficiency lock in front of the database, which stays the source of truth. Redis alone can lose writes on failover, so it must not be the record. It has nothing to do with payments. The key is per seat, not per show, so other seats stay open.

In the per-show allocator design, how does a new allocator recover after its pod dies?

  1. It asks every client to resend its holds
  2. It starts empty and treats all seats as free
  3. It loads DB state, replays from last offset
  4. It copies the in-memory state of a replica
The allocator is a deterministic function of the log, so loading the last persisted state and replaying the partition from the last committed offset reaches the same decisions. Clients cannot be relied on to resend. Starting empty would resell booked seats. There is no live replica in this design; the log is the backup.
