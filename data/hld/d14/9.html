Interview: driving the 45 minutes

  1. 0-5 min: scope Movies or concerts? Pick seats or best-available? Max seats per booking? Hold length? Say: no double booking (CP for seats), browsing AP.
  2. 5-10 min: numbers Normal load is small (about 12 bookings/s, GB-size inventory). Hot on-sale: 1M requests/s for 50k seats. Conclude: shape demand with a waiting room; one SQL primary per shard is enough.
  3. 10-15 min: API + data Hold, book, webhook, seatmap. show_seats with PK (show_id, seat_id) and the status column.
  4. 15-25 min: diagram The stepper: edge, catalog, seat map from cache, hold in DB, pay, confirm via webhook, Kafka fan-out, sweeper.
  5. 25-40 min: deep dives Lead with the race and the conditional UPDATE. Then the payment-after-expiry race, then the waiting room.
  6. 40-45 min: wrap up Failures per box; metrics: hold success rate, hold-to-booking conversion, payment latency, queue length and admission rate, expired-hold count, double-booking alarms (should be zero, checked by a reconciliation query).

An SDE-1 answer sounds like

"Seats per show live in a SQL table. To hold, I update the status from AVAILABLE to HELD with a 10-minute expiry, only if it is still available, and check the row count. After payment succeeds, I mark it BOOKED. A job frees expired holds. Search and seat maps are cached." Correct and safe.

An SDE-2 answer adds

"All-or-nothing multi-seat holds in one transaction; lazy expiry inside the WHERE clause so a late sweeper cannot block sales; idempotent webhooks with a unique hold_id; auto-refund if payment lands after expiry; outbox to Kafka for tickets and seat-map updates; and for on-sales a waiting room with signed admission tokens, best-available allocation and pre-scaling, because the database cannot absorb a million requests a second." Numbers, races, failure handling.

60-second answer (say it out loud): "Browsing and seat maps are read-heavy and may be a few seconds stale, so they come from caches. Taking a seat is a tiny strongly consistent write: one row per seat per show in Postgres, and a hold is a single conditional UPDATE from AVAILABLE to HELD with a 10-minute expiry, checked by row count, all seats in one transaction. Expired holds count as free inside the same WHERE clause, so a slow sweeper never blocks sales. After the PSP's signed webhook, we flip HELD to BOOKED only if we still hold it, otherwise auto-refund. An outbox sends events to Kafka for tickets, emails and seat-map updates. For a hot on-sale, a waiting room admits users at the rate the database can handle."

Common mistakes: read-then-write in application code; locking the whole show row (serialises every seat); holds with no expiry; trusting the seat map cache for the decision; using Redis as the only record of who owns a seat; charging before holding; ignoring webhook retries; "just autoscale" for the concert; forgetting per-user limits and bots; not saying what the user sees when they lose a race.

How do you guarantee two users never book the same seat?

Make the check and the write one atomic database operation on the seat row: UPDATE show_seats SET status='HELD', ... WHERE show_id=? AND seat_id=? AND status='AVAILABLE', then check that the number of updated rows equals the number of seats requested. The row lock serialises concurrent updates on the same seat; the loser re-checks the WHERE clause, matches 0 rows, and gets a 409. For multiple seats, do it in one transaction and roll back if the count is short. Confirmation is another conditional update from HELD (by this hold) to BOOKED.

How to answer

Describe the race first (read, check, write), then the fix (conditional update), then the multi-seat detail. Mention alternatives in one line each.

Likely follow-ups
  • Why not SELECT FOR UPDATE? (It works; it holds locks longer and needs a fixed lock order to avoid deadlocks.)
  • What isolation level do you need? (READ COMMITTED is enough for this single-statement pattern in Postgres.)
How do holds expire, and what if the expiry job is down?

Each held seat has held_until. The hold query treats an expired hold as free (OR (status='HELD' AND held_until + interval '2 minutes' < now())), so correctness does not depend on any background job. A sweeper still runs every few seconds to reset expired rows and publish "seat released" events, which keeps the seat map green and the counts right. If the sweeper is down, sales continue; only the seat map looks fuller than reality for a while.

How to answer

"Lazy for correctness, active for freshness." Then say what the user sees in each failure.

Likely follow-ups
  • Could you use Redis key expiry instead? (Yes, as a pre-filter; keyspace notifications are not guaranteed delivery, so don't rely on them alone.)
The payment succeeds one minute after the hold expired, and someone else took the seat. What now?

The confirm UPDATE (WHERE hold_id=? AND status='HELD') changes 0 rows, so we never confirm. The booking moves to FAILED_SEAT_LOST and we trigger an automatic refund through the PSP with an idempotent refund key, then notify the user, ideally offering nearby seats. To make this rare: a short grace window on confirm, extending holds while a payment is known to be in progress, and showing a countdown. The rule is "never confirm a seat you do not own; refund instead".

How to answer

State the invariant, then the compensation (refund), then the tricks that reduce how often it happens.

Likely follow-ups
  • How do you make the refund safe to retry?
  • What if the webhook never arrives? (Reconciliation job polls the PSP.)
A Taylor Swift on-sale: 2 million users, 50,000 seats. Walk me through it.

Do not try to serve 2 million users at the booking tier. Put a virtual waiting room at the CDN edge: users arriving before the start get random positions, later arrivals queue behind, and an admission controller lets in a rate the hold path can handle, issuing signed short-lived tokens. Reduce demand before it reaches us: pre-registration, presale codes, CAPTCHA, per-account limits. Inside, use best-available allocation by section to cut conflicts, a pushed seat map, and pre-scaled pods. Stop the queue and tell people as soon as inventory is gone.

How to answer

Start from the ratio (1M req/s vs 50k seats), say "shape demand, don't scale the DB", then walk the funnel from outside in.

Likely follow-ups
  • How do you choose the admission rate?
  • How do you stop one person sharing an admission token with friends?
Would you use a Redis distributed lock for seats?

Only as an optimisation, never as the guarantee. SET seat:{show}:{seat} hold NX EX 600 is fast and expires on its own, so it can reject obvious losers before they reach the database. But a lock in Redis can be lost on failover, and a client that pauses past its lease can still write later. Kleppmann's critique of Redlock points out that safe locks need fencing tokens checked by the resource. Our resource is the database, so the conditional update in the database is the real guard.

How to answer

"Efficiency lock vs correctness lock" is the distinction to name.

Likely follow-ups
  • What is a fencing token?
  • How would you hold 4 seats atomically in Redis? (Lua script.)
How do you keep the seat map fresh for 100,000 people looking at it?

Serve it from Redis (a bitmap or hash per show, a few KB), never from the database per request. Update it from seat events published after each hold, release and booking. For normal shows, clients poll every few seconds with caching headers; for hot shows, push deltas over SSE/WebSocket through a fan-out tier. Accept a few seconds of staleness, because the hold call is the real check and returns "just taken" if the map was wrong.

How to answer

Say "hint vs truth" early, then the cache, then push vs poll.

Likely follow-ups
  • How many WebSocket connections per server? What happens on reconnect storms?
Where does Kafka belong in this design, and where does it not?

Not in the synchronous hold decision, because the user waits for the answer and the database already serialises it. Kafka belongs after the decision: an outbox publishes booking.events keyed by show_id, and independent consumer groups generate tickets, send notifications, update the seat-map cache, and feed analytics and fraud detection. That keeps slow side effects off the booking path and lets each consumer retry independently. The one exception is an extreme hot show, where you could serialise all holds for that show through one partition and an in-memory allocator.

How to answer

Draw the line between "decide" (sync, DB) and "react" (async, Kafka), and mention the outbox.

Likely follow-ups
  • How do consumers avoid sending two tickets? (Idempotency on booking_id.)
  • Why key by show_id and not booking_id?
How do you enforce "max 6 tickets per person per event" under concurrency?

Two concurrent holds from the same user could each see "4 so far" and both succeed. Make the limit part of the same transaction: keep a row per (user, event) with a counter, and change it with an upsert in the same transaction as the seat hold (a plain UPDATE would match 0 rows on the user's first hold and look like "limit exceeded"):

INSERT INTO user_event_limits (user_id, event_id, count)
VALUES (:user, :event, :n)
ON CONFLICT (user_id, event_id) DO UPDATE
   SET count = user_event_limits.count + :n
 WHERE user_event_limits.count + :n <= 6;
-- 1 row affected: allowed.  0 rows: over the limit, ROLLBACK the hold.

(For a first hold, check :n <= 6 in the app before the insert.) Release the count when holds expire. Back it with identity checks (verified phone, payment instrument) since one person can own many accounts.

How to answer

Show the race, then reuse the same conditional-update trick. Mention that accounts are not people.

Likely follow-ups
  • What about resale and scalping?
How would you shard this system for many countries and huge events?

Shard by show_id (or event for stadiums): every hold, booking and seat event touches exactly one show, so there are no cross-shard transactions. Place each shard in the region nearest the venue, because the people buying tickets for a Mumbai show are mostly in India. Search and catalog are global, read-mostly and replicated. User data (bookings history) can be sharded by user and populated asynchronously from booking events. A directory service maps show to shard so a hot event can get a dedicated shard.

How to answer

Pick the key from the transaction boundary ("what does one booking touch?"), then talk about placement and hot events.

Likely follow-ups
  • How does "my bookings" across all shards work? (A per-user read model built from events.)

Scenario: the show sold out, but the hall was 20% empty

After a big Friday release, the cinema reports many empty seats in "sold out" shows. Customers complained they could not book.

Weak answer: "Probably a bug in the front end; I would add more logging."

Strong answer: compare BOOKED vs HELD counts at show time. If many seats were HELD and never paid, holds were too long, the sweeper or the lazy check was broken, or bots hoarded holds. Check payment latency during the peak (holds expiring while users waited on the PSP). Fixes: confirm the lazy expiry clause exists, cap active holds per user, shorten TTL, alert on "held seats older than TTL + 1 min".

Likely follow-ups
  • What dashboard would have caught this live?

Scenario: two customers have tickets for the same seat

A support ticket: two people arrived with valid QR codes for seat F7 in the same show.

Weak answer: "Our UPDATE prevents that, so it must be fraud."

Strong answer: assume our invariant was broken until proven otherwise. Look for a code path that bypasses the conditional update (admin tool, offline box-office sync, a retry that confirms without checking hold_id), a failover to an async replica that lost a write, or cache-based confirmation. Add a DB constraint so it cannot happen again (for example a unique ticket per (show_id, seat_id)), and a nightly reconciliation query that alarms on duplicates.

Likely follow-ups
  • How do you sync the cinema's offline box office with the online inventory?
