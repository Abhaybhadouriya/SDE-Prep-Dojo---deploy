Key APIs

# Browse (cacheable, CDN-friendly)
GET  /v1/cities/{city}/events?date=2026-11-28
GET  /v1/events/{event_id}/shows
GET  /v1/shows/{show_id}/seatmap          -> layout + status bitmap, may be ~seconds stale

# Hold seats (strongly consistent, small)
POST /v1/shows/{show_id}/holds
Idempotency-Key: 3b9e...                  # a retried tap must not create a 2nd hold
{ "seat_ids": ["F7","F8"] }
-> 201 { "hold_id": "h_81", "expires_at": "2026-11-28T18:10:00Z", "amount": 640 }
-> 409 { "error": "SEATS_TAKEN", "taken": ["F8"] }       # all-or-nothing

DELETE /v1/holds/{hold_id}                # user changed their mind

# Pay and confirm
POST /v1/bookings
Idempotency-Key: 9c1d...
{ "hold_id": "h_81", "payment_method": "upi" }
-> 202 { "booking_id": "b_552", "status": "PAYMENT_PENDING", "pay_url": "..." }

POST /v1/payments/webhook                  # from the payment gateway, signed
GET  /v1/bookings/{booking_id}            -> CONFIRMED | FAILED | EXPIRED, ticket QR

# Hot events: the waiting room
GET  /v1/queue/{event_id}                  -> { "position": 48211, "eta_s": 540 }
                                              later: { "admitted": true, "token": "eyJ..." }
  • Holds are all-or-nothing. If one of four seats is gone, hold none and tell the user which one. A family does not want three seats together and one in another row.
  • Every write takes an idempotency key (a unique client-generated id; see Digital Wallet & Ledger for the full idea), because mobile networks retry.
  • The admission token from the waiting room is a short-lived signed token (for example a JWT bound to the user and event). The hold API rejects requests without a valid token during an on-sale.
  • The server is the only judge of seat status. The seat map is a hint; the hold call is the truth. Never trust the client's "this seat was free when I saw it".
