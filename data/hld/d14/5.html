Architecture, step by step

Whiteboard version (6 boxes). Draw this first; the stepper adds the detail.

Click Next or Play. Notice where the cache is allowed to be stale, and the one place it is not.

  1. Edge. Every request passes the CDN and API gateway: TLS, auth, rate limits per user and IP, bot checks. Posters and static pages come from the CDN.
  2. Browse. The catalog service answers "what is playing in Pune tonight?" from Elasticsearch and caches. Stale by a few seconds? Fine.
  3. Seat map. The seat-map service returns the layout plus a status bitmap from Redis. Open seat-map pages can get live updates through SSE or WebSocket, or poll every few seconds. Still only a hint.
  4. Hold. The user taps seats. The booking service runs one conditional UPDATE in Postgres. It either holds every seat or none. This is the only strongly consistent step, and the seat-map cache is never consulted here.
  5. Pay. The booking row is created as PAYMENT_PENDING with an idempotency key, and the payment service creates an order at the payment service provider (PSP). The user pays in the PSP's page or app (UPI, card).
  6. Confirm. The PSP calls our signed webhook. In one transaction we flip the seats HELD to BOOKED (only if still held by this hold), mark the booking CONFIRMED and write an outbox row; a relay publishes booking.confirmed to Kafka.
  7. Fan out. Consumers generate the ticket and QR code, send email/SMS/push, update the seat-map cache and analytics. Each is idempotent on booking_id.
  8. Expire. A sweeper releases holds whose held_until has passed; the hold query also treats expired holds as free, so a slow sweeper never blocks sales.
  9. Hot on-sale. For a big event a waiting room sits in front of steps 3-5 and admits users at a fixed rate with a signed token. Everything behind it sees calm, predictable load.
