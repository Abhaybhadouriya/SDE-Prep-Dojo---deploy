Deep dives: the hard parts

7.1 Search performance: connections, caching and precomputed routes

  • Model flights as a graph per day: airports are nodes, flights are edges with times. With max one stop, a connection is A->X then X->B where the second departs at least the minimum connection time (MCT) after the first arrives, and within a maximum layover (say 8 hours).
  • Precompute valid one-stop pairs for each (origin, destination) when schedules change (daily), store them as a table and in memory. A search then becomes "look up candidates, fetch prices", not a graph search per request.
  • Round trip = two one-way searches, combined. Some fares are only valid as a round trip, so suppliers that price round trips natively are asked for the combination too.
  • Cache by key (supplier, origin, dest, date, cabin, pax) with TTL that depends on days to departure: a flight next month can be cached for an hour; a flight tomorrow for a few minutes. Skyscanner's partner docs describe a similar rule: serve a cached quote until its age passes a configured limit, then call the partner.
  • Serve stale, refresh async for popular routes, and pre-warm the top routes before peak hours.
  • Rank by price and duration; cap results per airline so one carrier does not fill the page.

7.2 Aggregating 20-200 suppliers

The Agoda IC5 review round focused on exactly this: API contracts and external supplier integrations.

  • Adapter per supplier behind one internal contract: search, price, hold, ticket, cancel, retrieve. Version the contract; map supplier error codes into our small set (SOLD_OUT, PRICE_CHANGED, TIMEOUT, INVALID).
  • Scatter-gather with a deadline: call all suppliers in parallel, stream answers, stop waiting at about 1.5-2 s. One slow supplier must not slow the page. See scatter-gather.
  • Bulkheads and circuit breakers per supplier: separate connection pools; a supplier with 50% timeouts is skipped (served from cache only) until it recovers. See circuit breaker.
  • Rate limits and cost: a per-supplier token bucket; prefer cache when near the limit. Some suppliers charge per search, so the look-to-book ratio is a cost metric, not just a technical one.
  • Dedup: the same flight can come from a GDS, the airline and a consolidator at different prices. Group by (carrier, flight_no, date, fare family) and show the best offer, keeping alternates for fallback.
  • Contract tests: each adapter has recorded responses from the supplier sandbox; the build fails when parsing breaks.

7.3 Seat locking, per-seat prices, and "other platforms sell the same seats"

The CRED SDE-2 follow-up: other platforms sell the same seats, so how do you prevent double booking? The answer the interviewer accepted: the airline (or the GDS acting for it) locks the seats; the platform cannot.

  1. Race. Two different platforms try to get the same seat. Neither can see the other's database, so a lock in our Redis means nothing to them.
  2. Single owner decides. The airline's inventory system serialises the requests (its own row-level lock or conditional update). The first gets a hold inside a PNR; the second gets "unavailable" and we offer other seats.
  3. Time-limited hold. We store the supplier's hold expiry and set our own payment timer shorter than it (for example, 10 minutes for the user when the supplier gives 15), leaving time to ticket.
  4. Finish or release. Ticket before expiry, or let it expire (or cancel it explicitly to be polite). A GDS guide from Finnair notes that if a ticket is not issued before the time limit, the segments are cancelled.
  • If we are the airline (the Flipkart framing): a seat row per (flight, seat) with status, hold_owner, hold_expires_at. Hold = UPDATE seat SET status='HELD', hold_owner=?, hold_expires_at=now()+15m WHERE flight_id=? AND seat_no=? AND (status='FREE' OR hold_expires_at < now()); one row changes or none. Same pattern as ticket booking.
  • Seat count vs seat number: airlines sell fare-class inventory (how many seats left in a price bucket) separately from seat assignment. Booking decrements the bucket; the seat map assigns a specific seat. Say this distinction; it explains why "seats left: 3" and the seat map can disagree.
  • Per-seat prices: total = fare (from the fare bucket) + seat fee (by seat type, sometimes by row). The seat price is part of the priced offer and the hold, so it cannot change between selection and payment.
  • Never hold seats during search. Holds are scarce and annoy airlines; only create them when the user commits to booking.

7.4 Multi-segment bookings and the payment saga

A round trip or a connection is several segments. The goal: all ticketed and paid, or nothing charged.

  • Best case: one supplier, one PNR. Ask the supplier to hold all segments in one reservation; it is atomic on their side.
  • Hard case: different suppliers (outbound on one airline, return on another, or a self-transfer connection). There is no distributed transaction across airlines, so use a saga:
StepActionIf it fails
1Hold segment 1 (supplier A)Fail booking; nothing to undo.
2Hold segment 2 (supplier B)Cancel hold 1; offer alternatives.
3Authorise payment (not capture)Cancel both holds.
4Ticket segment 1Cancel both holds; void authorisation.
5Ticket segment 2Void ticket 1 (voids are usually possible within a short window), or rebook segment 2 on another flight if the user agreed; then void or partially capture.
6Capture payment; CONFIRMEDRetry capture (idempotent); tickets exist, so never cancel here.
  • Order of steps: hold everything first (cheap and reversible), then authorise, then ticket (expensive to reverse), then capture. Each step is persisted in the booking state machine before the next, so a crash resumes instead of restarting.
  • Unknown results: a ticketing call that times out is "maybe ticketed". Retrieve the PNR from the supplier before retrying. Same rule as any external side effect.
  • Idempotency on both sides: our idempotency key per booking step; supplier calls carry our booking reference so a retrieve can find them.
  • Reconciliation: a daily job compares our bookings with supplier PNRs and payment settlement files; mismatches go to an ops queue. With money and third parties, reconciliation is not optional.

7.5 Premium-member pricing (the ClearTrip variant)

  • Cache neutral prices, personalise after. The cache holds supplier net or base prices. The pricing service applies markup, member discounts and coupons per request. Otherwise every member tier multiplies the cache.
  • Rules engine: rules by tier, route, airline, date range, with priority and a cap. Loaded in memory, versioned; every price records the rule version used (for audit and disputes).
  • Honour the shown price: the price token signs the member price and expiry; booking checks it. If the supplier's live price moved, show the new total and ask the user to confirm.
  • The Paytm SDE-2 round around this question also covered load-balancing algorithms, auto-scaling, DB sharding and health-check thresholds: have one line on each ready (least-connections LB for long supplier calls; scale search on CPU and in-flight requests; shard bookings by booking_id; health checks that test dependencies lightly).

7.6 Observability, CAP, testing and NFR validation (the Agoda rounds)

  • CAP in one sentence: search chooses availability (serve cached, possibly stale prices during a partition); booking chooses consistency (if we cannot reach the supplier or our DB primary, fail the booking rather than guess). See CAP.
  • Network failures: timeouts on every call, retries only on idempotent operations, retrieve-before-retry for holds and tickets, circuit breakers, and graceful degradation (hide a supplier rather than fail the page).
  • Metrics: time to first result and to complete; per-supplier latency, error and timeout rates; cache hit rate and quote accuracy (how often re-price differs from search price); look-to-book per supplier; booking funnel conversion; hold expiries; sagas stuck in a state for more than N minutes; reconciliation mismatches.
  • Testing: contract tests against recorded supplier responses; integration tests in supplier sandboxes (Amadeus offers a test environment); a fake supplier with injectable latency and errors for chaos tests; load tests replaying real search traffic; synthetic test bookings in production on a sandbox supplier.
  • Validating NFRs: write SLOs (p95 first-results under 2 s, booking success rate, zero double charges), load-test at 2x expected peak, canary each release with automatic rollback on SLO burn.

7.7 The newer format: review and improve an existing design

Agoda's IC5 round (October 2026, selected) gave an existing flight search and booking HLD plus its FR/NFR, and asked the candidate to find weaknesses in scalability, reliability and correctness, review API contracts and supplier integrations, and explain how to test and validate the NFRs.
