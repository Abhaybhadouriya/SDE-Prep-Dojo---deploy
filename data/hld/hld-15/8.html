Inverted index, TF-IDF and BM25

A trie answers "what starts with". Full-text search answers "which documents contain these words, best first". The structure is an inverted index: for every term, a sorted list of the document IDs that contain it. This list is the postings list. It is "inverted" because a normal document store maps document to words, and this maps word to documents.

Ranking. Finding matches is half the job. You must also rank them. The classic score is TF-IDF:

  • TF (term frequency): a word that appears often in a document says that document is about it.
  • IDF (inverse document frequency): a word that appears in almost every document ("the", "kafka" on a Kafka forum) tells you little, so it gets a small weight. Rare words get big weights.

BM25 is the modern default in Lucene, Elasticsearch and OpenSearch. It fixes two weaknesses of TF-IDF. First, term-frequency saturation: the 20th "kafka" in a page should add much less than the 2nd. The parameter k1 (default 1.2) controls how fast the curve flattens. Second, length normalisation: a long page contains every word by accident, so matches in short fields count for more. The parameter b (default 0.75) controls how strongly length matters. Elastic's BM25 article explains both defaults.

# BM25 score of one document D for query terms q (Lucene-style IDF)
# N = total docs, n(q) = docs containing q, f = count of q in D, |D| = length of D
idf(q)  = ln(1 + (N - n(q) + 0.5) / (n(q) + 0.5))
score   = sum over q of  idf(q) * f * (k1 + 1) / (f + k1 * (1 - b + b * |D| / avgdl))
# k1 = 1.2, b = 0.75 by default. b = 0 ignores length; k1 = 0 ignores repeats.

How Lucene stores it. New documents are buffered in memory and written as a new immutable segment. Searches read all segments. Background merges combine small segments and finally drop deleted documents. An update is a delete plus an insert. That is why Elasticsearch is near real time (new docs show up after a refresh, about a second by default) and why it is a poor fit for write-heavy counters such as likes. Hello Interview's Elasticsearch deep dive gives the standard advice: do not make it your primary database. Keep the truth in Postgres or DynamoDB and feed the search index through CDC or Kafka.

From your world

Immutable segments plus background merging is the same shape as an LSM tree, or a log-structured file system. Writes are sequential appends, readers see a consistent set of files, and compaction cleans up later. Postings-list intersection is a merge of two sorted arrays, the same loop you would write in C. Where this breaks: an LSM tree answers "the latest value for this key", while a search index must score and rank many matching documents, so merging also has to keep term statistics for BM25.

Sharding a search index. There are two choices. Document-partitioned (each shard holds all terms for a subset of documents) is what Elasticsearch does: a query fans out to every shard and a coordinator merges the top results. Term-partitioned (each shard holds all documents for a subset of terms) makes single-term queries hit one shard, but multi-term queries must join across shards. Interviews almost always expect document partitioning plus scatter-gather.
