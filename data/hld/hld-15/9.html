Vector search: nearest neighbours by meaning

Keyword search fails when the words differ but the meaning is the same: "my pod keeps restarting" and "CrashLoopBackOff". An embedding model turns text, images or products into a vector, a list of numbers (often 128 to 1536 of them), where similar meaning means vectors that point in similar directions. Searching by meaning becomes "find the K vectors closest to the query vector" by cosine similarity, dot product or L2 distance.

Exact search compares the query with every vector, so it is O(n). For one query over 1M vectors of 1,536 dimensions, that is 1M x 1,536 = about 1.5 billion multiply-adds, or about 3 billion floating-point operations, per query. So real systems use approximate nearest neighbour (ANN) indexes, which trade a little recall (the share of the true top-K you actually find) for a huge speed-up.

HNSW in one picture

HNSW (Hierarchical Navigable Small World, Malkov and Yashunin, 2016) is the most common ANN index. It is a graph: each vector is a node linked to some of its near neighbours. On top of that bottom layer sit sparser layers with fewer nodes and longer links, like express lanes. Each node's top layer is chosen at random with exponentially falling odds, so it behaves like a skip list in many dimensions. A search enters at the top, greedily jumps to the neighbour closest to the query, drops a layer when it cannot get closer, and finishes with a local search on layer 0. The paper reports logarithmic scaling.

  • Knobs. M is the number of links per node and ef_construction is how many candidates are kept while building. Elasticsearch's dense_vector defaults are m = 16 and ef_construction = 100, with a maximum of 4096 dimensions. At query time a candidate-list size (ef_search, called num_candidates in Elasticsearch) trades latency for recall.
  • Memory. A float32 is 4 bytes, so a 1536-dim vector is about 6 KB, and 1M vectors is about 6 GB raw. HNSW adds graph links of roughly M x 2 x 4 bytes per vector on the bottom layer (about 0.1-0.3 KB at M = 16), which is small next to the 6 KB vector itself: about 6.2-6.5 GB in total, a few percent more. The real memory problem is that the full vectors must stay in RAM for fast search. That is why systems quantise vectors to int8 or even single bits. Elasticsearch now quantises by default.
  • IVF (inverted file) is the main alternative. It runs k-means to make clusters and searches only the nprobe nearest clusters. It builds faster and uses less memory, but usually gives lower recall at the same latency.
  • Filters are the hard part. "Similar shoes, size 9, in stock" mixes ANN with metadata filters. Post-filtering can return too few results, and pre-filtering may not use the graph. Engines that filter during graph traversal handle this best.
  • Hybrid search. Production search often runs BM25 and vector search together and merges the lists (for example reciprocal rank fusion), then re-ranks the top results with a heavier model.

Say this: "The vector index is not the source of truth. It returns IDs and scores. I fetch the real records from the primary DB, and I re-embed everything when the embedding model changes." It shows you know where vector stores fit. More on this in AI/LLM System Building Blocks.
