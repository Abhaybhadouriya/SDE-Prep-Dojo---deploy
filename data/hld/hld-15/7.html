Trie: the prefix index behind autocomplete

A trie (from retrieval, also called a prefix tree) stores strings one character per edge. All words with the same prefix share the same path from the root. To find completions of "ca", walk c then a, and everything below that node starts with "ca". The walk costs O(length of prefix), no matter how many words you store.

A plain trie still has to search the whole subtree to find the most popular completions. The interview trick is to cache the top K completions at every node. Now a lookup is just "walk the prefix, read the list". It uses more memory, but the read path becomes O(prefix length) and nothing else.

  1. The user types c. We step from the root to node c and return the 3 cached suggestions stored there.
  2. The user types a. One more hop to ca, another cached list. In practice the client also debounces keystrokes so it does not send a request on every letter.
  3. The total work is one hop per typed character plus one list read. That is why a trie with cached top-K can answer in a few milliseconds.

Making it real at scale

  1. Build offline, serve read-only. Query logs flow into Kafka. A batch or streaming job counts query frequency (often with time decay) and rebuilds the trie with top-K lists. Servers swap in the new trie. Many designs rebuild hourly or daily and add a small "trending" layer that updates within minutes.
  2. Cap the prefix. Nobody needs suggestions after 50 characters, and capping keeps the trie bounded.
  3. Shard by prefix. Split by first one or two characters, but balance by traffic, not alphabet. "s" gets far more queries than "x", so ranges are uneven on purpose.
  4. Cache the hottest prefixes. One- and two-letter prefixes are a tiny set and get most of the traffic. Put them in a CDN or browser cache with a short TTL.
  5. Filter. Drop offensive or one-off queries before they reach the trie, for example a minimum count threshold.

Worked example (our own numbers, not from a source): 10M distinct queries, average length 20 chars. With prefix sharing, assume about 50M trie nodes. Each node caches 10 suggestions as 8-byte pointers (80 B) plus about 40 B of node overhead, so about 120 B x 50M = 6 GB. That fits in RAM on one large machine, and you replicate it for read QPS. Say this kind of estimate out loud in the interview.

From your world

The Linux routing table (FIB) uses an LC-trie for longest-prefix match, and many routers use compressed tries in hardware. A radix tree (compressed trie) merges single-child chains into one edge, exactly what you would do to shrink an autocomplete trie. Where this breaks: a FIB lookup returns one best match, while autocomplete must return the top K completions under a prefix, so each trie node also caches a ranked list.
