Architecture: write path and read path

Click Next or Play. Steps 1-4 are the write path (indexing); 5-8 are the read path (a query).

  1. Events. The post and like services publish to Kafka. Search never sits on the posting request path.
  2. Ingest. Workers consume posts.created, tokenise (lowercase, split, strip punctuation, maybe stem), add language and hashtags. A separate job aggregates likes.
  3. Index. Each post goes to one shard chosen by hash(post_id) (document partitioning). The shard appends the id to each term's posting list in its active in-memory segment. Older tiers live on SSD.
  4. Likes, cheaply. The like job only rewrites a post's popularity score at milestones (1, 2, 4, 8 ... or 10, 100, 1000), so a post with 1,000 likes costs ~10 index writes, not 1,000.
  5. Query. The user searches "world cup". The CDN or Redis cache answers hot queries directly (TTL under a minute).
  6. Scatter. On a miss the broker normalises the query and sends it to one replica of every shard in the needed time tiers.
  7. Gather. Each shard intersects "world" and "cup" postings locally and returns its top-K; the broker merges these small lists.
  8. Re-rank and hydrate. For "most liked", fetch fresh counts for the top ~2K candidates, re-sort, then load post bodies from the post store and return page 1 with a cursor.
