Quick quiz

Why does WHERE text LIKE '%cup%' not scale?

  1. SQL databases cannot store long text columns
  2. A leading wildcard cannot use a B-tree index
  3. It only works when all posts sit on one shard
  4. Text comparison in SQL is case-sensitive
B-trees need a known prefix, so every row is scanned. Sharding only divides the full scan.

Main advantage of document partitioning over term partitioning?

  1. Adding a post updates only one term's shard
  2. Each query touches only one or two shards
  3. Shards need no replicas because data is split
  4. Multi-word ANDs stay local; hot terms spread
Each shard is a mini search engine over its own posts. Term partitioning touches fewer shards per query, but its AND queries move whole posting lists across the network.

With milestone updates at powers of 10, about how many index writes does a post with 1,000 likes cause?

  1. 4 (at 1, 10, 100, 1,000)
  2. About 100, one per ten likes
  3. About 10, one per doubling
  4. 1,000, one per like
Only crossings of 1, 10, 100 and 1,000 rewrite the score; exact counts come at re-rank time. One per doubling would be the powers-of-2 version.

Why did Twitter assign document ids based on creation time?

  1. To compress posting lists by storing small gaps
  2. So ids reveal which server wrote the tweet
  3. So postings stay in time order, newest first
  4. To make ids unique without a central counter
27 bits of ms timestamp + 4-bit counter; newest-first traversal stops after enough hits. Gap compression and uniqueness are side effects, not the reason.

In a document-partitioned index with 500 shards, what most hurts p99 latency?

  1. The slowest shard replica on each query
  2. The number of terms in the user's query
  3. The front-end's CPU while merging 500 lists
  4. Network bandwidth between shards
Fan-out means every query waits for all 500 shards, so the slowest responder decides; hedged requests and replicas help.

What should a query-result cache TTL be tied to?

  1. How often the hot query is searched per second
  2. How long the index takes to rebuild a shard
  3. The number of shards the query fanned out to
  4. The freshness target (e.g. under 1 minute)
TTL (time to live) is how long a cached result may be served. A TTL longer than the freshness target would break the requirement for hot queries.

A user sorts by "most liked". The index stores approxLikes from milestones. How do you return the right top 20?

  1. Trust approxLikes, since milestones keep it within 1%
  2. Take ~40 by approxLikes, re-sort by exact counts
  3. Sort every match by exact count from the counter service
  4. Update approxLikes on every like for top posts only
Retrieve-then-rerank: over-fetch 2N candidates by the approximate score, then fix the order with exact counts. Fetching exact counts for every match would be millions of lookups.

Why are the Kubernetes index pods a StatefulSet and not a Deployment?

  1. StatefulSets autoscale faster on CPU
  2. Deployments cannot mount any volumes
  3. Each pod keeps a stable name and disk
  4. StatefulSets skip readiness probes
index-7 must always be shard 7 with its own local SSD data, so a replacement pod keeps the same identity and volume. Deployments treat pods as interchangeable.
