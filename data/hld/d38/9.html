Interview: drive the 45 minutes

This is a Meta favourite (Hello Interview's breakdown is written for Meta loops, often with "no Elasticsearch allowed"). Indian product companies ask cousins of it: Swiggy SDE-2 "book search", PhonePe "Stack Overflow with search", and Flipkart has written about near-real-time product search indexing (see Product Catalog & Search).

  1. 0-5 min: scope - keyword search, two sort orders, freshness target, no personalisation.
  2. 5-10 min: numbers - 10K posts/s, 100K likes/s, 10K searches/s, index too big for RAM.
  3. 10-15 min: API + entities; why LIKE '%x%' fails.
  4. 15-25 min: diagram - Kafka -> ingestion -> doc-sharded index; broker scatter-gather; cache.
  5. 25-40 min: deep dives - like counts (milestones + re-rank), partitioning, real-time segments.
  6. 40-45 min: failures, tail latency, monitoring (indexing lag, p99, cache hit rate).
LevelWhat the answer looks like
SDE-1 answer looks like..."New posts flow through Kafka to indexers that build an inverted index (word to list of post ids), sharded by post_id; a query front-end asks every shard, merges their top results and caches hot queries for under a minute."
SDE-2 adds..."I compare document vs term partitioning, keep like counts out of the hot index (milestone updates plus re-rank of the top 2N), use time-ordered ids for newest-first early termination, and cut tail latency with replicas and hedged requests."
What is an inverted index and why not just use SQL LIKE?

An inverted index maps each term to the list of documents containing it. It is built once at write time, so a query reads a few lists instead of scanning all text. LIKE '%word%' has a leading wildcard, so a B-tree index cannot help and the database scans every row; sharding only splits that scan.

How to answer

Draw three posts and their index (like the diagram above). It takes 30 seconds and proves you understand it.

Likely follow-ups
  • What goes inside a posting besides the id? (positions, term frequency, payloads)
Would you shard the index by term or by document? Defend it.

By document. A post is written to one shard; multi-word ANDs run locally; hot terms are spread across all shards. The cost is that every query fans out to all shards, so tail latency matters: replicate each shard, use hedged requests, and set a per-shard timeout with partial results. Term sharding needs ~20 shard writes per post, ships long lists across the network for ANDs, and one shard owns the hottest word.

How to answer

Give the table: write cost, AND cost, hot keys, fan-out. Cite that Google's 2003 cluster and Twitter's Earlybird use document partitioning.

Likely follow-ups
  • With 1,000 shards, how do you keep p99 low?
  • How do you add shards as data grows? (new time tiers instead of rehashing)
Likes arrive at 100K/s. How do you support "sort by most liked"?

Keep exact counts in a sharded counter service, not in the index. Update the index's approximate score only at milestones (powers of 2 or 10), so a post with 1,000 likes causes about 10 index writes. At query time, pull the top 2N by approximate score from each shard, fetch exact counts for those candidates, re-sort and return N. Optionally batch likes in 30-second windows first to absorb viral bursts.

How to answer

Start by computing the naive write amplification (likes x terms), then fix it. Name the pattern: retrieve then re-rank.

Likely follow-ups
  • Can a post be missing from results because its approx score is stale? (bounded error: at most one milestone behind; widen candidate set)
How do you make a new post searchable within seconds?

Stream posts through Kafka into index servers that append to an in-memory active segment immediately (no batch rebuild). Use one writer per segment with lock-free readers (atomic pointer publish), time-based document ids so out-of-order arrivals still sort correctly, and freeze/compact full segments in the background. Twitter reports going from ~15 s to ~1 s with this approach. If you use Elasticsearch, the knob is the refresh interval - shorter means fresher but more segment merging.

How to answer

Separate "durable in Kafka" from "visible in the index"; explain what blocks visibility.

Likely follow-ups
  • What happens to the in-memory segment if the server crashes? (rebuild from Kafka offset + last snapshot)
How would you cache search results, and what are the risks?

Because results are not personalised, cache by normalised query + sort + page in Redis and at the CDN with a TTL under the freshness SLA (for example 30 s). Risks: thundering herd when a hot key expires (use request coalescing or early refresh), stale results after deletes (purge on delete events for hot queries, or filter deleted ids at hydration), and low hit rate on the long tail (fine - those go to the index).

How to answer

Tie the TTL to the stated freshness requirement.

Likely follow-ups
  • What changes if results become personalised?
How do you answer a phrase query like "world cup final"?

Intersect the three posting lists starting from the shortest, then check stored positions to confirm the words are adjacent and in order. For very common phrases, index bigrams such as "world_cup" so the lookup is direct; limit this to frequent pairs to avoid exploding the vocabulary.

How to answer

Mention skip pointers to speed up intersection - shows depth.

Likely follow-ups
  • How would you find frequent bigrams? (count-min sketch over the query log)
The index is 500+ TB. How do you store it affordably?

Tier by time. Most queries want recent posts, so keep the last days in RAM with fast writes; older data goes to SSD-backed read-only segments built by batch jobs; rarely used terms can live in blob storage. Shard in two dimensions - time tier x hash partition - so growth means adding a new tier, not reshuffling old shards. Compress postings (delta encoding + variable-length integers).

How to answer

Show the estimate first (160 GB/day of postings), then the tiering. Cite Twitter's RAM real-time index vs 100x larger SSD full index.

Likely follow-ups
  • How do you query across tiers and merge? (broker sends to tiers newest-first and stops when it has enough)
How do deletes and edits work in an append-only index?

Do not rewrite posting lists. A delete adds the id to a per-segment deleted bitmap; queries skip those ids, and the hydration step also drops posts the post store says are gone. An edit is delete + re-index under the same post id. Space is reclaimed when segments merge or are rebuilt.

How to answer

Mention legal/privacy urgency: deletes must disappear from results quickly even if bytes are reclaimed later.

Likely follow-ups
  • How do you guarantee a deleted post never shows from the cache?
Would you use Elasticsearch here? What are its limits?

Yes as a first version: it is a document-partitioned Lucene index with replicas, scatter-gather and near-real-time refresh built in. Keep the source of truth in the database and feed ES from Kafka/CDC (see CDC pipeline). CDC (change data capture) tails the database's write-ahead log and publishes each committed row change to Kafka; the outbox pattern instead writes the event into an outbox table in the same DB transaction, and a relay publishes it. Either way the index is rebuilt from the database's own log, like a journal replay in a filesystem. Limits at extreme scale: cost of keeping everything hot, shard sizing (aim for 10-50 GB), refresh vs merge overhead, and very high update rates on fields like like counts - which is why counts are kept outside or updated at milestones.

How to answer

Say yes, then show you know what it does inside, so the interviewer does not think it is a magic box.

Likely follow-ups
  • What if the interviewer says "no Elasticsearch"? (build the inverted index yourself - this page)

Scenario: the World Cup final

During the final, posts jump 4x and 30% of searches are "world cup". p99 search latency goes from 200 ms to 3 s and new posts take 5 minutes to appear.

Weak answer: "Add more index shards."

Strong answer: Two separate problems. (1) Reads: the hot query is missing the cache or stampeding on expiry - add request coalescing and serve a slightly stale cached page; every shard is doing the same huge "world" AND "cup" work, so cache that result on the broker. (2) Writes: indexing lag means consumers are behind; scale ingestion workers up to the partition count and temporarily skip expensive enrichment (URL expansion) and add it later as a field update, as Twitter does for delayed fields. Then watch Kafka lag and p99 per shard.

Likely follow-ups
  • Why would adding shards not help quickly? (rebalancing moves data during the spike)

Scenario: one replica is slow

One index server has a failing SSD. Every query fans out to all shards, so 100% of queries are slow.

Weak answer: "Increase the timeout."

Strong answer: Use hedged requests (after p95 time, ask another replica of that shard and take the first answer), have the broker eject replicas whose latency is an outlier, and keep 3 replicas per shard so ejecting one is safe. Alert on per-replica p99, not just the global p99.

Likely follow-ups
  • What does hedging cost? (a few percent extra load if done after p95)

Common mistakes: LIKE '%x%' on a sharded DB; updating the index on every like; term-sharding without noticing hot terms; offset pagination; forgetting deletes; calling search synchronously from the post service.
