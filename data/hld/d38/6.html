Deep dives

1. Partition by document or by term?

This is the classic question. Real large-scale systems (Google's 2003 cluster paper, Twitter's Earlybird, Elasticsearch) use document partitioning.

Document-partitionedTerm-partitioned
Write of one post1 shard~20 shards (one per term)
Query fan-outAll shards (scatter-gather)Only shards owning the query terms
Multi-word ANDLocal per shard - cheapShip long posting lists across the network to intersect
Hot termsSpread evenly over shardsOne shard melts ("the", "worldcup")
Tail latencySlowest shard decides; fix with replicas + hedged requestsFewer shards per query
Used byGoogle (2003 paper), Twitter Earlybird, ElasticsearchSimple Redis-keyword designs; some research systems

From your world

Document partitioning is like RSS (receive-side scaling) hashing flows to CPU cores: each core owns whole flows and needs no cross-core locking. Scatter-gather then is a multicast and collect, and your p99 is set by the slowest responder - the same reason one slow line card hurts a whole ECMP group. Replicas per shard play the role of redundant paths.

Google's 2003 paper describes exactly this: index shards each hold a randomly chosen subset of documents, every shard has a pool of replica machines behind a load balancer, and because shards do not talk to each other the speedup is nearly linear. Elasticsearch suggests keeping shards between 10 and 50 GB and under 200 million documents.

2. Real-time indexing: one writer, many readers, no locks

Twitter's Earlybird paper (2012) and the 2020 follow-up give a very concrete design:

  • Each server holds several segments (12 in 2012, each up to 223 = ~8.4M tweets). Only one segment is active (being written); the others are frozen and converted into a compact read-only form (about 55% smaller).
  • Document ids encode time. In 2020, Twitter packed a 31-bit id as 27 bits of millisecond timestamp + a 4-bit counter, so ids sort by creation time even when tweets arrive out of order. Searching from the newest id lets a query stop early after the first N hits.
  • Posting lists moved from a prepend-only unrolled linked list (needs strictly ordered input) to a skip list with a 1:5 level ratio, so late-arriving tweets can be inserted in place.
  • A single writer per segment publishes new entries by an atomic pointer update; reader threads (one per core) never take a lock.
  • Result: indexing latency dropped from about 15 seconds to about 1 second, while serving hundreds of thousands of QPS.

From your world

That single-writer, lock-free-reader trick with an atomic pointer publish is RCU (read-copy-update) from the Linux kernel. Readers see either the old or the new head, never a torn one. Frozen read-only segments are like making a page read-only after it is built.

Stop here for SDE-1. An inverted index sharded by document (post_id), scatter-gather across shards, and Kafka feeding an append-only real-time index are the interview-sufficient core. Deep dives 3-5 (likes via milestones and re-rank, phrase queries, hot queries and tiers) are what an SDE-2 answer adds.

3. Sorting by likes without 100K index writes per second

If every like rewrote the popularity score in every term's sorted set (a post has ~20 terms), 100K likes/s would become 2M index writes/s. Options:

ApproachIndex writesDownside
Update on every likelikes x termsMelts on viral posts
Batch per 30 s windowOne per post per windowHelps viral posts; a post with 1 like/minute still writes 1,440 times a day
Milestones + re-rank~log10(likes): 1,000 likes = 4 writes (at 1, 10, 100, 1,000); powers of 2 would be ~10Index order is approximate; fix it at query time

With milestones, the index stores an approxLikes field. At query time take the top 2N candidates by approximate score, fetch exact counts from the counter service, re-sort, return the top N. This retrieve-then-rerank pattern is the same as in recommendation systems (see Recommendation System). The exact counts themselves come from a sharded counter.

4. Multi-word and phrase queries

  • AND = intersect posting lists. Sorted lists intersect like a merge; skip pointers let you jump ahead in the longer list (Twitter keeps a "search finger" so the next jump is O(log d), not O(log n)). Always start from the shortest list.
  • Phrases ("world cup" as adjacent words) need positions stored in postings, or index bigrams (word pairs) for popular pairs only - indexing all bigrams can grow keys from ~10M to over 100M.

5. Hot queries, caching and cold data

  • Cache normalised query results in Redis and at the CDN with a TTL under the freshness target (for example 30 s). During a final, "world cup" might be a large share of all traffic - cache it, and use request coalescing so a cache miss triggers one backend query, not thousands (see Pattern: Scaling Reads).
  • Time tiers: recent tier in RAM, older tiers on SSD, built in batch. Twitter's 2014 full index held about half a trillion tweets with < 100 ms average latency, sharded in two dimensions: time tiers x hash partitions, so the cluster grows by adding new tiers instead of reshuffling old ones.
  • Rarely searched terms can be moved to blob storage and loaded on demand.
  • Deletes: do not rewrite posting lists. Keep a per-segment "deleted ids" bitmap, filter at query time, and purge when segments are rebuilt or merged.
