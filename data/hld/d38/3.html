Key APIs

GET  /search?q=world+cup&sort=recent|likes&limit=25&cursor=<opaque>
     -> {results:[{post_id, author, snippet, created_at, like_count}], next_cursor}

# internal events (Kafka topics), not public APIs
posts.created  {post_id, author_id, text, created_at, lang}
posts.deleted  {post_id}
likes          {post_id, user_id, delta:+1|-1, ts}
  • Use a cursor (opaque token holding the last seen post id / score per shard), not offset=10000. Deep offsets force every shard to produce and throw away 10,000 results. See API design: pagination.
  • Search is read-only and not personalised in our scope, so identical queries return identical results - great for caching.
  • The index is fed by events, not by the post service calling the search service. If search is down, posting still works; the index catches up from Kafka.
