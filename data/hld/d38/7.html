Where Kafka, Kubernetes and Docker fit

ToolRoleDetail
KafkaThe indexing backboneposts.created partitioned by post_id, mapped so one index shard consumes a fixed set of partitions. Its committed offset is the shard's "indexed up to here" mark; a new replica rebuilds by replaying from a snapshot offset. Freshness SLO (service level objective: the target we alert on) = consumer lag. Why Kafka here: indexing must never slow down posting, and a crashed or new index replica must be able to catch up by replaying - Kafka gives both. Edits and deletes ride the same topic so ordering per post is kept. See Consumer groups.
KubernetesRun query front-ends and index nodesThe query front-ends (Earlybird calls them roots/brokers - not Kafka brokers) are stateless Deployments with an HPA (Horizontal Pod Autoscaler: adds pods when CPU or QPS rises). Why Kubernetes here: index nodes are stateful and slow to warm, so you need stable identities and careful rollouts, while front-ends need fast autoscaling - Kubernetes does both. Index shards are a StatefulSet (stable names like index-7 map to shard 7, local SSD volumes); readiness only after the segment snapshot is loaded and Kafka lag is below a threshold. A PodDisruptionBudget (PDB: a rule that limits how many replicas can be down during maintenance) keeps 2 of 3 replicas up during node drains. See StatefulSets & Operators.
DockerPackage batch buildersWhy Docker here: the online indexer and the offline builders must tokenise text identically, or a word indexed one way is searched another way. The offline "rebuild old tiers" jobs (Twitter ran over a thousand stateless builders in parallel) are container jobs; the same tokeniser image is used online and offline so results match.
