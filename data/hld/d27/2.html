Back-of-envelope estimation

  1. Average scoring rate: 100 M payments/day / ~100,000 s = about 1,200 scores/s (exact: 1,157).
  2. Peak: sales and festival evenings. Rule of thumb 5-10x: design for 10,000 scores/s.
  3. Feature reads: each score needs features for several entities (card, user, device, IP, merchant, email) over several windows: say 30 values, fetched in about 5 batched multi-get calls. At peak: 10,000 x 30 = 300,000 feature values/s, or 50,000 network calls/s. A Redis or Aerospike-style cluster handles this; the point is that calls must be batched and parallel, never 30 sequential round-trips.
  4. Latency budget (100 ms, worked below): network + API ~10 ms, features ~15 ms, model ~20 ms, rules ~5 ms, logging and decision ~5 ms, ~45 ms headroom for p99 tails.
  5. Event volume: an enriched payment event (payment + features + decision) ~2 KB x 100 M = 200 GB/day into Kafka and the data lake. Keep 2 years for training: 200 GB x 730 = ~146 TB in object storage (cheap).
  6. Labels: at ~1 in 1,000, about 100,000 fraud cases/day out of 100 M. The training set is 999 good : 1 bad, so accuracy is a useless metric (a model that says "never fraud" is 99.9% accurate).
  7. Online feature store size: say 300 M active entities x 50 features x 8 bytes = 120 GB (+ overhead and replicas, a few hundred GB). Fits in an in-memory cluster.
