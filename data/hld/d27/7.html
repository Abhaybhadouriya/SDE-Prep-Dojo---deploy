Where Kafka, Kubernetes and Docker fit

ToolWhereDetail
KafkaBackbone of the async pathsTopics: payments (key = card fingerprint, so a card's events stay ordered for Flink), fraud.decisions, fraud.labels, fraud.rules (compacted). Producers use acks=all + idempotence (the defaults since Kafka 3.0). Flink reads with exactly-once checkpoints. See consumer groups and Connect, Streams and Flink.
KafkaCDC for labels and profilesChargebacks and account changes live in OLTP databases; Debezium streams them into Kafka instead of nightly dumps. Razorpay has described a Debezium -> Kafka (MSK) -> stream processing pipeline for real-time anomaly detection. See CDC pipeline.
KubernetesScoring and model servingDeployments with a high minReplicas (cold start is too slow for a sale spike), HPA on CPU or request rate, a PodDisruptionBudget, readiness probes that check the model is loaded. Model servers often get a separate node pool (GPU or large-memory nodes).
KubernetesFlink jobsThe Flink Kubernetes Operator manages a FlinkDeployment custom resource: JobManager, TaskManagers, savepoint-based upgrades. See operators.
DockerReproducible models and local testsEach model version ships as an image (model + exact feature code + library versions), which also removes one source of training-serving skew. Locally, docker compose with Kafka, Redis and Flink runs the whole pipeline. See build it locally.

The official flink image contains Flink but not your job, so bake the job JAR into your own image first:

# Dockerfile - job JAR baked into a Flink image
FROM flink:1.20
COPY target/fraud-features.jar /opt/flink/usrlib/fraud-features.jar
apiVersion: flink.apache.org/v1beta1
kind: FlinkDeployment
metadata:
  name: fraud-features
spec:
  image: registry.example.internal/risk/fraud-features:0.3.0   # job JAR baked into a Flink image
  flinkVersion: v1_20
  serviceAccount: flink
  flinkConfiguration:
    taskmanager.numberOfTaskSlots: "4"
    execution.checkpointing.interval: "30s"
    state.backend.type: rocksdb
  jobManager:
    resource: { memory: "2048m", cpu: 1 }
  taskManager:
    resource: { memory: "8192m", cpu: 4 }
  job:
    jarURI: local:///opt/flink/usrlib/fraud-features.jar
    parallelism: 32          # = partitions of the payments topic
    upgradeMode: savepoint   # keep window state across upgrades
$ kubectl apply -f fraud-features.yaml
flinkdeployment.flink.apache.org/fraud-features created
$ kubectl get flinkdeployment
NAME             JOB STATUS   LIFECYCLE STATE
fraud-features   RUNNING      STABLE
$ kafka-consumer-groups.sh --bootstrap-server kafka:9092 --describe --group fraud-features
GROUP           TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
fraud-features  payments  0          5512990         5513004         14
fraud-features  payments  1          5498112         5498112         0

The metric that matters for features: consumer lag of the Flink job, converted to seconds (lag / rate). If it grows to minutes, your "real-time" velocity features are stale, and the model is quietly making worse decisions without any error showing. Alert on it like an outage. (Flink with Kafka reports offsets on checkpoint, so the group lag view moves in steps.)
