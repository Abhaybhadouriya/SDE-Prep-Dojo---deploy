Key APIs

POST /v1/risk/score                    # called by the payment service, timeout 100 ms
  { "payment_id": "pay_8812",            # idempotency: same id -> same decision
    "amount_minor": 499900, "currency": "INR",
    "card_fingerprint": "fp_4111x", "user_id": "u_77", "merchant_id": "m_12",
    "device_id": "d_9a", "ip": "203.0.113.7", "channel": "web",
    "event_time": "2026-11-23T14:05:11.204Z" }
  -> 200 { "decision": "CHALLENGE",      # ALLOW | CHALLENGE | BLOCK
           "score": 0.83, "model": "gbdt-v41", "rules_hit": ["velocity_card_1m"],
           "reasons": ["5 payments on this card in 60 s", "new device"] }

POST /v1/rules                          # analysts, versioned, starts in shadow mode
  { "name": "velocity_card_1m", "when": "card.txn_count_1m > 4 and amount_minor > 200000",
    "action": "CHALLENGE", "mode": "shadow" }

POST /v1/labels                         # chargebacks, reviews, customer reports
  { "payment_id": "pay_8812", "label": "FRAUD", "source": "chargeback",
    "reported_at": "2026-12-19T09:00:00Z" }

GET  /v1/cases?status=open              # review queue for analysts
  • The caller sets a hard timeout and has a fallback decision if the call fails (deep dive 4). The fraud service never sits on the path without a timeout.
  • event_time is when the payment happened; features use it, not the time the service received it.
  • Never send raw card numbers to the fraud system: use a fingerprint (a token or keyed hash) so the fraud stack stays out of the strictest card-data compliance scope.
