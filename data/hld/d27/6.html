Deep dives: the hard parts

Stop here for SDE-1: the three paths (sync scoring, streaming features, offline training), the latency budget and "rules + model" are a strong SDE-1 answer. Deep dives 1-4 are expected at SDE-2. 5-6 are what make an answer memorable.

1. Streaming velocity features and the freshness gap (must know)

A velocity feature counts or sums events for one key over a time window: "payments on card X in the last hour". Flink computes it by keying the stream by card (all events of a card go to the same Flink task, just like a Kafka key goes to one partition) and keeping a window per key in its state.

  • Event time vs processing time: windows use the time the payment happened. A watermark says "I believe all events up to time T have arrived", so Flink can close a window; late events within an allowed lateness update it.
  • The freshness gap: the scorer publishes to Kafka, Flink consumes, aggregates and writes back; that is seconds end to end. A fraudster's tenth payment in 5 seconds may be scored before Flink has seen the first. Fix: the scorer updates a short synchronous counter itself (Redis sorted set or INCR per time bucket) on the request path, and Flink owns the longer windows.
  • Hot keys: one big merchant produces a huge share of events, so the Flink task that owns its key becomes a bottleneck. Pre-aggregate per partition first (local combine), then merge; or split the key into sub-keys (merchant#0..15) and sum.

Flink SQL for a 1-hour sliding (hop) window, updated every 10 seconds:

CREATE TABLE payments (
  payment_id   STRING,
  card_fp      STRING,
  amount_minor BIGINT,
  event_time   TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND   -- tolerate 5 s of disorder
) WITH (
  'connector' = 'kafka',
  'topic' = 'payments',
  'properties.bootstrap.servers' = 'kafka:9092',
  'properties.group.id' = 'fraud-features',
  'scan.startup.mode' = 'latest-offset',
  'format' = 'json'
);

SELECT card_fp, window_end,
       COUNT(*)          AS txn_count_1h,
       SUM(amount_minor) AS amount_sum_1h
FROM TABLE(
  HOP(TABLE payments, DESCRIPTOR(event_time), INTERVAL '10' SECOND, INTERVAL '1' HOUR))
GROUP BY card_fp, window_start, window_end;

What this query costs. Each event belongs to 3,600 s / 10 s = 360 overlapping windows. Flink stores 10-second slices and combines them, so state is not copied 360 times - but the output is one new row per active card every 10 s, for an hour after its last payment. Every row is a write to the online feature store, and at the 10k/s peak that write fan-out is the real bottleneck. Batch and upsert those writes, or switch to a CUMULATE window or an incremental per-card counter with 1-minute buckets if the store cannot absorb it. Naming this unprompted is a strong SDE-2 signal.

And the synchronous 60-second counter on the request path, using a Redis sorted set (score = timestamp in ms):

$ redis-cli ZADD win:card:fp_4111x 1795442711204 pay_8812     # = 2026-11-23T14:05:11.204Z (event_time of pay_8812)
(integer) 1
$ redis-cli ZREMRANGEBYSCORE win:card:fp_4111x 0 1795442651204   # = that time minus 60,000 ms
(integer) 2
$ redis-cli ZCARD win:card:fp_4111x
(integer) 5
$ redis-cli EXPIRE win:card:fp_4111x 120
(integer) 1

Add the payment, drop entries older than 60 s, count what remains (5 payments in the last minute), and set a TTL so idle cards cost nothing. In production you run these in one pipeline or Lua script so it is one round-trip.

From your world

Keying the stream by card is ECMP flow hashing: every packet of a flow goes to the same core, so per-flow state lives in one place without locks. A sliding-window counter is a token-bucket policer per flow in reverse: instead of allowing N per interval, you measure N per interval and raise an alarm. The watermark is like a reassembly timeout: how long you wait for out-of-order fragments before you decide. Where it breaks: ECMP picks a path only to keep packets in order, and re-hashing a flow costs nothing. Here the Kafka key also decides which worker holds the state (the card's counters), so changing the key or the partition count moves state, and the job must be restored from a savepoint to re-key it.

Just enough ML (no magic)

A model is just a function: feature vector in, fraud probability out. It is learned from labelled history (past payments marked "fraud" or "fine"), instead of being written by hand. Gradient-boosted trees (GBDT) = many small if-then trees ("amount > 5,000 and card age < 1 day?"), each one fixing the errors of the ones before, whose scores are added up - like a committee voting. A DNN (deep neural network) is a bigger, less explainable function of the same kind. A z-score = how many standard deviations a value sits above the user's normal (z = 3 means "very unusual for this user"). Calibration = adjusting outputs so a score of 0.8 really means "80% of payments with this score were fraud". Drift = fraudsters change behaviour, so the learned function slowly gets worse on new traffic. Champion / challenger = the live model (champion) runs while a new one (challenger) scores the same traffic in shadow, and replaces it only if it does better. Down-sampling = keeping only a fraction of the many "fine" examples in training, because fraud is so rare. The area under the precision-recall curve is one number that sums up precision vs recall across every possible threshold (higher is better).

From your world

Think of the model as a learned ACL: instead of an engineer writing "drop if rate > X from new source", the thresholds and combinations are fitted automatically from past attack traffic. Where it breaks: an ACL does exactly what it says forever; a model is only as good as its training data, so when attackers change tactics (drift) it degrades silently and must be retrained and monitored.

2. Training-serving skew and point-in-time correctness (must know)

Training-serving skew means the model sees different feature values in training than in production, so it performs worse live than in tests. Two classic causes:

  • Two implementations: data scientists compute "txn_count_1h" in a Spark notebook, engineers compute it in Flink, and the definitions differ slightly (inclusive vs exclusive window end, time zone, counting declined payments or not). Fix: define features once (a feature store such as Feast, or shared feature definitions) and log the exact feature values the scorer used, then train on those logs.
  • Leakage from the future: when you build training data, a naive join takes today's value of "card's chargeback count", which includes the chargeback of the very payment you are labelling. The model learns to cheat. Fix: a point-in-time join: for each payment at time t, use only feature values that existed at time t.

3. Labels: late, rare and biased (must know at SDE-2)

  • Late: chargebacks can take weeks. So the newest weeks of data have incomplete labels. Train on data old enough to be mostly labelled, and use faster proxy signals (manual review results, customer "I didn't do this" reports) for recent data.
  • Rare: with 1 fraud per 1,000, use metrics that ignore the easy majority: precision (of payments we blocked, how many were fraud?) and recall (of all fraud, how much did we catch?), and the area under the precision-recall curve. Down-sample good payments or weight fraud cases higher in training.
  • Pick thresholds by money, not by accuracy: a false positive costs a lost sale and an angry customer; a false negative costs the fraud amount plus a chargeback fee. Different merchants and amounts deserve different thresholds, and CHALLENGE is the cheap middle option.
  • Selection bias (the subtle one): payments you block never get a label, because they never happened. Over time the model only learns from what it let through. Fix: let a tiny random fraction of would-be-blocked low-amount payments go to CHALLENGE instead, to keep learning, and evaluate new models in shadow on all traffic.

Worked example to say out loud (illustrative numbers): "Out of 1,000,000 payments, about 1,000 are fraud. If my model flags 2,000 and 800 of them are fraud, precision is 40% and recall is 80%. I have blocked 1,200 good customers to stop 800 frauds. Whether that is good depends on average fraud loss vs the value of a good sale, so I would set the threshold, and use CHALLENGE instead of BLOCK in the grey zone."

4. Fail-open vs fail-closed, and degraded modes (must know)

  • Fail-closed (block when the scorer is down): safe from fraud, but every payment fails, which during a sale is a business outage.
  • Fail-open (allow when down): payments keep flowing, but fraudsters who notice can exploit the gap.
  • Best answer: fail-open with guard rails. The payment service keeps a small, local fallback policy that is refreshed every few minutes: block-lists, a cap on amount for new cards or new devices, and CHALLENGE above a threshold. Alert immediately, and track how much volume went through the fallback.
  • Partial failures: if only the feature store is slow, score with the features you have (models should be trained with missing-value handling) and mark the decision "degraded". If only the model server is down, rules alone decide. Each dependency gets its own timeout inside the 100 ms budget, and a circuit breaker.

From your world

This is the same question as "what does the firewall do when its inspection engine crashes?": fail-open (bypass mode, like a hardware bypass NIC) or fail-closed. Networks usually pick per segment. Payments usually pick fail-open with a reduced, local rule set, like a line card that keeps forwarding on its last FIB when the control plane is gone. Where it breaks: a bypassed firewall costs only the inspection; a fail-open payment path costs real money that fraudsters can take on purpose. Attackers can try to cause the outage, so the fallback must keep amount caps and velocity limits, and fail-open must be time-boxed and loudly alerted.

5. Rules that change in minutes: dynamic rules and shadow mode (should know)

  • Rules are data, not code: stored versioned in a DB, pushed to scorers (poll every few seconds, or via a compacted Kafka topic fraud.rules where the latest value per rule_id is the current version).
  • In Flink, rules that need streaming state use broadcast state: the rules stream is broadcast to every task, and each task applies the current rules to its keyed events. The Apache Flink blog series on a fraud detection case study shows exactly this, including choosing the grouping key per rule at runtime.
  • Shadow mode for every new rule and model: evaluate it on live traffic, log what it would have done, compare against the current one, then promote. A bad rule ("block amount > 100" with a missing zero) can block a whole country in seconds.
  • Champion / challenger: send a small percentage of traffic to the new model's decision, with automatic rollback if block rate or complaint rate jumps.

6. Fraud rings: graph features (good to know)

  • Build the graph from shared identifiers: device, card fingerprint, phone, email, address, IP block.
  • Graph features are usually computed in batch or near-real-time jobs (connected components, counts of neighbours with fraud labels) and written to the online feature store like any other feature. Real-time graph queries on the scoring path are expensive; precompute.
  • Beware super-nodes: a public Wi-Fi IP or a shared office device links thousands of innocent users. Cap degrees or ignore known shared identifiers.
