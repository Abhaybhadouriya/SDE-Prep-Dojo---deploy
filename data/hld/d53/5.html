Architecture: from a price tag to a phone buzz

Click Next or Play. Three flows share one pipeline: the fetch loop (we go and look), the extension loop (a user's browser tells us what it saw), and the alert loop (a change becomes a notification).

  1. Schedule. For each shop, a Redis sorted set holds every product with score = next due time. The scheduler pops the most overdue items (ZRANGEBYSCORE due:shop -inf now LIMIT 0 500) and hands them to workers. Hot products get a short interval, cold ones a long one.
  2. Fetch politely. Workers call the shop's official product API or partner feed when one exists, and otherwise fetch the public product page. A per-shop token bucket caps the rate, and the worker obeys the shop's robots.txt (cached for at most 24 hours, as RFC 9309 recommends). Workers are stateless containers that scale on queue depth.
  3. Extension reports. When a user opens a product page, the extension shows the chart (a lookup) and can also report the price the page showed. That report is untrusted: the ingest API answers 202 and treats it as a hint, never as the truth.
  4. One log for all observations. Fetched and reported prices land on one Kafka topic keyed by product_id. Keying by product keeps every observation of a product in order on one partition, so the next stage sees them in sequence.
  5. Validate and detect a change. The validator rejects nonsense (a price of 0, a price 10x the usual range, a currency mismatch) and, for extension reports, waits for confirmation. If the price really changed, it appends a row to the time-series DB, updates the current price in Redis and PostgreSQL, and drops the chart cache.
  6. Match. A price-changed event (product, condition, old price, new price) goes to Kafka. The alert matcher runs one range query: armed watches on this product with target_price >= new_price, and it disarms them in the same transaction. Armed means "not alerted since the last re-arm", so only users who have not yet been told come back. Percentage watches are checked the same way against the price when they were created.
  7. Notify once. For each hit, the matcher writes (watch_id, crossing_id) to the sent-alerts table (unique key = idempotency), disarms the watch, and hands the message to the shared notification system, which owns email, push, user preferences and rate limits.
  8. Close the loop. Watch counts flow back to the scheduler: a product that just got its 100th watcher moves to the hot tier; one with no watchers for 30 days drifts to cold. The fetch budget follows user interest.
