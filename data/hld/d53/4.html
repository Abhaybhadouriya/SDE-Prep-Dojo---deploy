Data model

Four kinds of data, four access patterns. Store choice reasoning is in Choosing Storage.

DataStoreKey / indexWhy
Products: id, shop, URL, title, current price per condition, tier, next fetch time, watcher countPostgreSQL, sharded by product_idPK product_id; unique (shop, shop_item_id)Small rows, updated per fetch, needs uniqueness (one row per shop item)
Watches: id, user, product, condition, target price or drop %, armed flag, last notified price and timePostgreSQL, sharded by product_idIndex (product_id, condition, target_price) where armed; secondary by user_idThe matcher asks "armed watches on this product with target at or above the new price"; a B-tree range scan on a partial index (armed rows only) answers it
Price history: product, condition, time, price, sourceTime-series DB (TimescaleDB hypertable) or a wide-column store(product_id, condition, ts)Append-only, read as one product's time range, compresses very well, needs rollups
Rollups: hourly and daily min / max / avg / lastContinuous aggregates in the same TSDBSame key plus bucketA 1-year chart reads 365 rows, not 8,760 hourly points
Current price and chart cacheRedisprice:{product}, chart:{product}:{range}Extension lookups need single-digit ms
Fetch scheduleRedis sorted set (score = next due time)due:{shop}"Give me the 500 most overdue products for this shop" is a range-by-score
Sent alerts (audit + dedup)PostgreSQL or DynamoDB with TTL(watch_id, crossing_id) uniqueIdempotency: a retry cannot send the same alert twice
 
CREATE TABLE watch (
  watch_id      BIGINT PRIMARY KEY,
  user_id       BIGINT NOT NULL,
  product_id    BIGINT NOT NULL,
  condition     TEXT   NOT NULL DEFAULT 'new',     -- new / used / third-party
  target_price  NUMERIC(12,2),                     -- either this ...
  drop_percent  SMALLINT,                          -- ... or this
  armed         BOOLEAN NOT NULL DEFAULT TRUE,     -- false after it fires, until re-armed
  last_notified_price NUMERIC(12,2),
  last_notified_at    TIMESTAMPTZ
);
-- the matcher's query path: only armed watches, ordered by target
CREATE INDEX watch_match ON watch (product_id, condition, target_price) WHERE armed;

Why shard watches by product and not by user? The hot path is "price of product P changed; who cares?". Sharding by product keeps that query on one shard. The "list my watches" page is rarer; serve it from a small secondary index by user_id (or a separate copy of the table keyed by user, kept in sync by an event).
