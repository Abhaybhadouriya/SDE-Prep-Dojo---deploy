Deep dives

1. The fetch budget: what to look at, and how often

You cannot look at 500M products every hour, and you should not try. The fix is a priority schedule driven by user interest. Each product has a next due time. When it is fetched, the next due time is set from its tier: hourly for hot, daily for warm, weekly for cold. Tier comes from simple signals: number of watchers, recent page views from the extension, and how often the price has changed recently (a product that changes daily deserves more looks than one stable for a year).

Politeness is part of the design, not an afterthought. Every request to a shop goes through a per-shop token bucket (for example 1 request per second per worker IP with a small burst). Workers obey robots.txt: RFC 9309 says a crawler should not use a cached copy for more than 24 hours, should treat a 5xx on robots.txt as "disallow everything", and should apply the longest matching rule. Use the shop's official product API or an affiliate or partner feed wherever it exists: fewer bytes, a clear contract, and no cat-and-mouse. (Amazon, for example, has moved its affiliate catalogue access from PA-API 5 to a newer Creators API; the point for the interview is "use the official API, and plan for it to change".) If a shop says no, the honest design answer is "we do not track that shop", not "we evade its bot defences".

Do not propose rotating residential proxies or CAPTCHA solving in an interview as your main plan. It is legally risky, against most sites' terms, and interviewers read it as a red flag. Talk about official feeds, rate limits, caching, and the extension instead.

From your world

The per-shop token bucket is the same token bucket you know from traffic policing on a router interface: tokens refill at a fixed rate, a burst can use saved tokens, and an empty bucket means wait. The sorted "next due" set is a timer wheel: pop everything whose deadline has passed. The tiers are like multi-level feedback queues in a CPU scheduler, where interactive (watched) tasks get more turns.

The extension as a free sensor. One million extension users open product pages all day. If each browser reports the price it just showed, the server gets millions of free observations of exactly the products people care about. One case study estimates that extension-reported prices could cut server-side fetching by 50-80%. The catch is trust, which is deep dive 3.

2. Matching: find the users whose line was just crossed

A price changed from 3,200 to 2,800. Who gets an alert? The naive way is to loop over all watches on the product and compare each target. That is fine for 10 watchers and terrible for 200,000. Worse, if you ask "who has target >= 2,800?", you re-alert everybody who was already notified at 2,900 yesterday.

The right question is a crossing: which armed watches have target_price >= new_price? Armed means "this user has not been alerted since the watch was created or last re-armed". With an index on (product_id, condition, armed, target_price) (or the partial index below, which holds only armed rows), this is one B-tree range scan: O(log n) to find the start, then one step per alert you actually send. The matcher disarms each hit in the same transaction that records the alert.

Why not use the old price as the lower edge, new_price <= target < old_price? It looks tighter, but the armed flag is what stops repeats, not the old price. The old price is unreliable: a price-changed event can be dropped or arrive out of order, the matcher can be down for an hour, a watch can be created when the price is already below its target, or a re-arm can run late. In each case an armed watch with a target at or above the old price would never fire. Using only "armed and target >= new price" makes the query robust to lost and reordered events: the next price event (or the nightly sweep) catches anything that was missed. Also run the same check once when a watch is created, so a user who sets a target above today's price is told at once.

-- inside one transaction, for a price-changed event
UPDATE watch
   SET armed = false, last_notified_price = :new_price, last_notified_at = now()
 WHERE product_id = :product_id AND condition = :condition
   AND armed = true AND target_price >= :new_price
RETURNING watch_id, user_id, target_price;
-- served by the partial index watch_match (product_id, condition, target_price) WHERE armed

Re-arming. After a watch fires it is disarmed, so price wobbling around the target (2,799, 2,801, 2,799...) does not send ten emails. It re-arms only when the price climbs back above the target by a margin, say 5% (this margin is called hysteresis, exactly like a thermostat or a Schmitt trigger). On the way up, the matcher runs the mirror query: disarmed watches with target_price * 1.05 < new_price get re-armed.

Percentage watches ("tell me if it falls 20%") become absolute thresholds when created: target = price at creation x 0.8. Store the computed target and the same index works. A "20% below the 90-day average" rule is rarer; evaluate it in a periodic batch job using the daily rollups.

Stock variant (Uber's bar-raiser shape). Here prices are pushed by the exchange feed many times per second, so you keep the thresholds in memory. Shard by symbol: each matcher process owns a set of symbols and holds, per symbol, two sorted structures: "below" alerts sorted by price descending and "above" alerts sorted ascending. On each tick, pop from the front while the tick has crossed the alert's price. Each tick costs O(log n) plus the alerts it fires. It looks a lot like one side of an order book in a stock exchange matching engine. Persist alerts in a database and rebuild the in-memory structures from it (plus a Kafka replay from a stored offset) when a matcher restarts.

3. Trust: fake prices and broken parsers

Hello Interview lists "malicious price updates from Chrome extension users" as a core deep dive. Two very different things can produce a wrong price, and both end in the same disaster: a million users told "your item is now Rs 0!".

  • Bad actors. Someone scripts the extension API to report a fake low price (to spam, or to damage trust). Defences: authenticate extension installs and rate-limit per install; never alert on a single report; require k agreeing reports from distinct installs, or better, treat a report as a trigger to schedule an immediate fetch of our own and alert only on our own confirmed reading.
  • Our own bugs. The shop changes its page layout, the parser reads an empty field, and "no price" becomes "price 0". One case study calls this extraction drift. Defences: prefer structured data (an API response, or the page's embedded product markup) over screen-scraping; run two extractors and require agreement; reject prices outside a sanity band (for example 50% to 200% of the recent range) into a quarantine queue instead of alerting; keep a small canary set of products per shop that is fetched after every parser deploy and alarms on any change.

A useful trick from trivago's price pipeline (about 70 billion prices over a week): prices are roughly exponential, so a "3 standard deviations" outlier rule works badly on raw prices. They take log10 of the price first and then reject outliers. trivago also found that about 88% of incoming price records were duplicates, which is a reminder to dedupe observations before you store them.

Interviewers love the "price 0" story. Say: "An alert is a user-visible side effect, so I put a validation gate in front of it: sanity band, two sources or a confirmation fetch, and quarantine instead of alert when in doubt. A late alert is fine within our 1-hour budget; a wrong alert to a million people is not."

4. The flash-sale burst and alert fatigue

On a big sale day, one popular phone drops 30% and 200,000 people are watching it. Hundreds of products do the same within minutes. The case study we read models this as tens of millions of alert events in a few minutes. Three things keep the system calm:

  1. Decouple with Kafka The matcher writes alert events to an alerts topic; the notification system drains it at the rate email and push providers allow. Lag grows, nobody crashes. See consumer groups for how to add consumers.
  2. Re-key for fan-out price-changed is keyed by product (to keep order per product). One hot product would pin all its 200,000 matches to one partition, so the matcher pages through the watch range in chunks of, say, 1,000 and emits chunk tasks keyed by watch_id, spreading the work across all partitions. This is the fan-out pattern in Fan-out (Push vs Pull).
  3. Protect the user At most one alert per watch per hour, a daily cap per user, and a digest ("5 of your items dropped today") when a user has many hits at once. If lag passes the freshness budget, shed or delay the lowest-priority alerts (for example free tier) first and keep paid or stock alerts on time.

Idempotency. Kafka consumers can see an event twice after a crash (at-least-once delivery). The matcher inserts (watch_id, crossing_id) into the sent-alerts table with a unique constraint before handing off; a duplicate insert fails, and the duplicate alert is dropped. crossing_id can be the id of the price-changed event. Details in Delivery Semantics.

5. Fast history charts (under 500 ms)

A 2-year chart from raw points could mean thousands of rows. Keep three resolutions: raw points for 30 days, hourly rollups for a year, daily rollups beyond that. TimescaleDB's continuous aggregates keep those rollups up to date in the background as new rows arrive, and only recompute the time buckets that changed. The API picks the resolution from the range (1 month = raw or hourly, 1 year = daily). Then cache the finished chart JSON per (product, range) in Redis and invalidate it when that product's price changes. Since most products change rarely, hit rates are very high, and the extension's lookups mostly never reach the database.
