Common mistakes: designing a matching engine (that is the exchange); pushing every tick to every user; JSON ticks; Redis as the only copy of GTTs; a cron that re-places 1M orders at 09:15; resending an order after a timeout without checking the exchange; writing history and order tables separately from the API; dividing daily volume by 86,400; floats for prices; ignoring multiple exchanges when asked to "scale".

Walk me through every state of a GTT order. What happens if your service crashes in the middle of triggering?

ACTIVE -> TRIGGERING -> TRIGGERED or FAILED, plus CANCELLED and EXPIRED. The trigger engine claims a GTT with a conditional update (WHERE status='ACTIVE' AND version=?), which is the only way to leave ACTIVE, so two engines or an engine racing a user cancel cannot both win. It then places the order with idempotency key gtt_id:version and records the order id. If it crashes after the claim, the row stays in TRIGGERING; a sweeper picks up rows stuck for more than 30 s, asks the order service whether an order with that key exists, and finishes the row (TRIGGERED with that id, or places it now). No state is a dead end and no retry can create a second order.

How to answer

Draw the state machine first, then for each arrow say who moves it, what makes it atomic, and how a crash right after it is repaired. That is literally what this interviewer kept asking.

Likely follow-ups
  • The order is rejected by the exchange (circuit limit, no margin). State? (FAILED with reason, notify the user; do not re-arm automatically.)
  • OCO: both legs cross on one gap? (Claim the GTT once; place only the leg that matches the direction of the move.)
Why not store GTTs in Redis and have an end-of-day cron re-place them on the exchange every morning?

Three problems. Durability: Redis with async replication or persistence off can lose acknowledged writes on failover, and a GTT must live for up to a year. Semantics: re-placing as day orders puts real resting orders on the exchange that block margin and may fill without the trigger ever being hit. Failure handling: a cron that dies half-way has no record of which of the 1M orders it placed; rerunning duplicates, skipping loses. Instead: Postgres as the source of truth, an in-memory sorted index per instrument rebuilt from it, and a per-GTT state machine with idempotent order placement.

How to answer

Do not just say "Redis is bad". Name the failure each part causes and offer the replacement.

Likely follow-ups
  • Can Redis still be used? (Yes, as a cache or as the trigger index, as long as it can be rebuilt from the DB.)
An order event goes Kafka to the order DB to order history. Where can it be lost or duplicated, and how do you prevent it?

Lost if a producer writes the DB and then crashes before publishing (dual write), or if a consumer commits its offset before applying the event. Duplicated whenever a consumer applies and crashes before committing (Kafka is at-least-once). Fixes: the order service writes the state change and an outbox row in one transaction, and a relay publishes; consumers apply the event first and commit the offset after; every event has (order_id, seq) and consumers ignore a seq they already applied (an upsert with a version check); history is derived from the event stream, never written separately. Topic keyed by order_id keeps events of one order in order. End-of-day reconciliation with the exchange trade file catches anything left.

How to answer

Name the three failure points (produce, consume, commit), then the three tools (outbox, idempotent consumer, reconciliation).

Likely follow-ups
  • Would Kafka exactly-once fix it? (Only inside Kafka; the DB write and the push notification are outside effects.)
How do you ingest the exchange feed? Where do the ticks come from?

From the exchange's market-data feed, delivered as sequenced UDP multicast in colocation or over leased lines, usually as two redundant feeds (A and B). Feed handlers on dedicated hosts receive both, keep whichever copy of each sequence number arrives first, detect gaps and recover from the retransmit or snapshot service, and normalise exchange-specific messages into one internal tick with integer prices and the exchange timestamp. They then publish to an internal bus keyed by instrument. Feed handler health metrics: last sequence per channel, gap count, and lag between exchange timestamp and our timestamp.

How to answer

This is exactly where the Paytm candidate was unsure. Say "multicast, A/B feeds, sequence numbers, gap recovery, normalise", and you have closed the gap.

Likely follow-ups
  • Why not run feed handlers as normal autoscaled pods? (They need the leased-line network, a registered IP and kernel tuning; autoscaling them adds nothing.)
1M ticks/s, 5,000 instruments, 5M users with 20 each, 500 ms freshness. Size the fan-out.

Naive push is 5M x 20 x 200 ticks/s = 20 billion messages/s, so we conflate: latest value per instrument every 500 ms means the whole market is 10,000 updates/s, about 1 MB/s. Send that to every WebSocket gateway; each gateway builds one binary frame per user per 500 ms with that user's 20 instruments: 10M frames/s overall. At about 200 bytes per LTP frame that is about 2 GB/s of egress; with full quotes about 9 GB/s, so depth goes only to the open stock page. At 50,000 connections per node we need about 100 nodes, 150 with headroom. Slow clients get overwrite-not-queue semantics.

How to answer

Show the naive number, then cut it with one idea (conflation), then size the edge. Numbers beat boxes here.

Likely follow-ups
  • Redis pub/sub in the middle? (Fine for 10k msg/s, but every gateway subscribing to everything makes Redis a single fan-out point; a simple TCP broadcast tier or Kafka works too.)
  • Freshness proof? (Measure exchange timestamp to client render at p99 with client-side sampling.)
Each order must be placed within 10 ms. Where does the time go, and what do you remove from the hot path?

Budget: about 1 ms for auth and validation (stateless, local JWT check), 1 ms for risk (in-memory margins partitioned by user, no DB read), 2-4 ms to durably record the order (replicated log append or a fast DB insert), 1-3 ms to send over an already-open exchange session, and slack for pauses. Everything else is moved off the hot path: notifications, history, analytics and position rebuilds consume order-events asynchronously. Pre-warm instrument master and user limits in memory before 09:15. Measure p99, not average.

How to answer

Give a budget table. "Too basic" feedback usually means no numbers and no failure path, so include the UNKNOWN state on timeout too.

Likely follow-ups
  • Can you skip the durable write? (Only if you can rebuild from exchange order status after a crash, which is slower and riskier; most brokers journal first.)
Extend the design to multiple exchanges and segments.

Instrument identity becomes (exchange, segment, token). One adapter per exchange+segment behind a common interface, each with its own session, rate limiter and bulkhead. Kafka topics and engine shards are partitioned by exchange+segment so one venue's trouble stays local. The RMS loads segment-specific margin rules (cash vs F&O margin files). Schedules (market hours, square-off time, GTT expiry handling, settlement) are per segment; commodity trades late. Feed handlers per exchange normalise into the same tick format so everything downstream is unchanged. Optionally, smart routing chooses NSE or BSE for a stock listed on both by best price.

How to answer

Show that the design was built with an "adapter" seam and that isolation (bulkheads) is the main benefit. This was the missing piece in the 2025 feedback.

Likely follow-ups
  • How do you add a new exchange without downtime? (New adapter and feed handler, instrument master rows behind a feature flag, then enable per user cohort.)
Design auto square-off: close a user's intraday position the moment price crosses their risk threshold.

Turn each rule into an absolute exit price at the start of the day (previous close 100, rule +18% -> exit at 118). Keep, per instrument, a sorted structure of (exit_price, position_id), sharded by instrument like the tick stream. On each tick, pop all crossed entries in O(log n + k), and for each send a market or protected-limit Sell or Cover through the order service with key (position_id, rule_id, date), then notify. Recompute the exit price when a position changes (partial exit, add-on). Block new exposure-increasing orders for that user while the exit is in flight. A separate scheduled job squares off all remaining MIS positions at the broker's cut-off time, per position and idempotent.

How to answer

Point out that it is the same engine as GTT with a different source of thresholds. Reuse wins points.

Likely follow-ups
  • Millions of updates per second? (Shard by instrument; the per-tick work is a sorted-set peek, so one core handles hundreds of thousands of ticks/s.)
  • Price hits the upper circuit and no sellers exist? (Order rests; retry or escalate to the risk desk; that is why the exit is set below the circuit.)
Candle data sits in a cache. Design moving it to SQL and aggregating it to larger timeframes.

Live: a stream processor keyed by instrument builds 1-minute candles by exchange timestamp; the forming candle stays in Redis; when the minute closes (plus a small grace period) it is upserted to SQL with key (instrument, tf, start_ts) in one batch per minute. Rollups to 5m, 15m, 1h and 1D are computed from 1m rows by a scheduled job or continuous aggregates. One-time migration: copy per instrument per day with idempotent upserts, verify counts and checksums, dual-read for a while, then switch reads and expire cache keys. Storage is small (about 94 MB/day), so the hard parts are correctness and cut-over, not size.

How to answer

Separate "live pipeline" from "one-time migration"; interviewers often mean both. State the idempotent key early.

Likely follow-ups
  • A late tick changes a closed candle? (Upsert the same key; rollups that include it are recomputed.)
  • Which database? (Postgres partitioned by month, or TimescaleDB; both handle this volume.)
Scale to 20M orders a day. What is the peak rate and how do you store orders?

20M over 22,500 trading seconds is about 900/s average and about 9,000/s at the open or on expiry day, with 3-5 events per order. Store orders in Postgres sharded by user_id (all of a user's orders on one shard for the order book screen), partitioned by trade_date so old days can move to cheaper storage. Order events go to Kafka and an append-only history table. Hot views (today's orders, positions) are served from Redis. About 20 GB/day, 5 TB/year.

How to answer

Use trading hours, not 24 hours, and say why the shard key is user_id (the main reads are per user).

Likely follow-ups
  • Why SQL and not NoSQL? (State transitions need conditional updates and transactions with the outbox; the volume is modest.)
Stop-loss orders: does the broker watch the price or the exchange?

For a regular SL order the exchange does: the broker sends an order with a trigger price and a limit price, and the exchange activates it when the trigger is reached. The broker only holds triggers that the exchange will not keep, such as GTT orders that must last beyond today, or broker-side features like trailing stops. Delegating to the exchange is simpler and more reliable because the exchange sees every trade.

How to answer

Short answer, then use it to explain why GTT is the special case that needs our own engine.

Likely follow-ups
  • Why can a stop-loss limit order still not fill? (The price can gap through the limit.)

Scenario: 09:15, the market opens 3% down

200,000 GTT buy triggers and 150,000 square-off rules cross on the first tick. Exchange order-rate limits apply per session.

Weak answer: "Fire them all in parallel; autoscale the order service."

Strong answer: claims are cheap and happen at once; order placement goes through per-adapter queues that respect exchange rate limits, with square-off (risk) at higher priority than GTT buys. Every item is idempotent, so a slow queue only delays, never duplicates. Users see "triggered, placing" quickly. Add more exchange sessions in advance on known heavy days.

Likely follow-ups
  • Which GTTs first? (Fair order by trigger time, or by how far price moved; state the rule and keep it deterministic.)
