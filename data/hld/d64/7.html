Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key order_id keeps each order's life cycle (placed, partially filled, filled) in order; gtt-changes is keyed by instrument instead, so a trigger-engine shard sees its instruments in order. Consumer-group sizing: 32 partitions cap each group at 32 pods, far more than the order rate needs. The gateway HPA scales on open connections, not CPU, because idle sockets cost memory, not cycles.

PieceToolSetting that matters
order-eventsKafka, key = order_idacks=all, min.insync.replicas=2, idempotent producer. Consumers: positions, history, notifications, reconciliation.
gtt-changesKafka from outbox / DebeziumKey = instrument so a trigger-engine shard sees its instruments' changes in order.
ticksKafka or in-memory pub/subShort retention (hours), key = instrument. Kafka if you want replay for candles; in-memory for the lowest display latency.

Zerodha's blog notes they adopted Kubernetes mainly to make deployments uniform, not for performance. That is a good line for an interview: the cluster is for the stateless fleet; the latency-critical edges sit on carefully tuned machines.
