Trade-offs, bottlenecks and failure modes

DecisionChoiceAlternativeWhy
Price transportWebSocket, binary, conflatedSSE; pollingTwo-way subscribe, small frames. Polling 5M users every 500 ms = 10M HTTP req/s.
Fan-out topologyFull conflated feed to every gatewayPer-instrument topics, gateways subscribe10k updates/s is tiny; avoids subscription churn in the middle. Switch to per-topic only if instruments grow 100x.

GTT storePostgres + in-memory indexRedis onlyMust survive a year and failovers; memory is only an index you can rebuild.
GTT firing guardConditional update + idempotency keyDistributed lockA lock can expire mid-call; a version check and dedup key cannot double fire.
Risk pricesFull or 100 ms stream500 ms display streamRisk errors cost money; display staleness only costs a blink.

Failure modes to volunteer

  • Feed gap: sequence jump on feed A; take B or retransmit; if both lost, snapshot and mark prices stale in the UI rather than showing wrong ones.
  • Exchange session drop: orders in SENT become UNKNOWN; reconnect, request order status for all of them, then resume.
  • Risk engine node dies: standby rebuilds margins from the journal (snapshot + replay) before accepting orders for that user partition; meanwhile those users get "try again" rather than an unchecked order.
  • Gateway rollout: drain slowly; clients reconnect with jitter.
  • Hot instrument: at expiry, NIFTY options get huge tick rates; the conflator caps output at 2/s regardless, and trigger engines can split one instrument's triggers by price range across shards.
