Key APIs

# Market data: one WebSocket per app session
WS  /ws/ticker?token=...           # client sends {"a":"subscribe","v":[408065, 884737], "mode":"ltp"}
                                   # server sends binary frames: [count][len][packet]...

# Orders (REST over HTTPS, idempotent by client_order_id)
POST   /orders                      {client_order_id, exchange, symbol, side, qty, type: MARKET|LIMIT|SL,
                                     price?, trigger_price?, product: CNC|MIS|NRML}
       -> 202 {order_id, status: "PENDING"}   # final status arrives as a push event
PUT    /orders/{order_id}           {qty?, price?, trigger_price?}
DELETE /orders/{order_id}
GET    /orders?date=2026-11-23       # order book for today
GET    /positions                    # today's net positions with live P&L
GET    /holdings                     # demat holdings

# GTT
POST   /gtt   {client_gtt_id, type: SINGLE|OCO, exchange, symbol,
               trigger_values: [1400], last_price: 1520,
               orders: [{side: BUY, qty: 10, type: LIMIT, price: 1400}], expires_at}
       -> 201 {gtt_id, status: "ACTIVE", version: 1}
PUT    /gtt/{gtt_id}  {..., version}  # optimistic concurrency
DELETE /gtt/{gtt_id}

# Charts
GET    /candles/{instrument}?tf=1m&from=...&to=...
  • client_order_id is the idempotency key. A retried POST with the same key returns the same order, never a second one. See idempotency key.
  • 202 Accepted, not 200 Filled. The exchange decides the fill; the client learns it from a push event on the same WebSocket (Kite uses text messages for order updates and binary for ticks).
  • Ticks use a binary format: Kite's docs describe 8, 44 and 184 byte packets for LTP, quote and full modes. JSON would be 5-10x larger.
  • Kite Connect's GTT API stores last_price at creation. It tells the engine which direction the trigger is ("price must fall to 1,400" vs "rise to 1,400").
