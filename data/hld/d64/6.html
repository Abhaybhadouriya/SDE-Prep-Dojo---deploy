Deep dives: the hard parts

7.1 Live price fan-out: 1M ticks/s to 5M users in under 500 ms

This was the Paytm SSE prompt, nearly word for word. The candidate there used Redis pub/sub and SSE but was unsure how to ingest the exchange feed. Here is a complete answer, in layers.

  1. Ingest (the part people skip). Exchanges publish market data over UDP multicast from their colocation or via leased lines, with sequence numbers. Run feed handlers on dedicated hosts (not autoscaled pods) with both the A and B feeds; take whichever packet arrives first, detect gaps by sequence number, and recover from the exchange's retransmit or snapshot channel. Normalise into one internal format: {instr_id, exch_seq, exch_ts, ltp_paise, vol, oi, bid1, ask1}.
  2. Distribution. Publish to a bus keyed by instrument. Kafka works (ordered per partition, replayable) and adds a few milliseconds; for the price path many brokers use an in-memory pub/sub (NATS, Redis pub/sub, or their own TCP fan-out) because losing a tick is acceptable here. Say this trade-off out loud.
  3. Conflation. A conflator holds latest[instr] and a dirty bit. Every 250-500 ms it publishes only dirty instruments. Freshness is then at most one interval plus network time.
  4. Gateways. WebSocket servers written in an event-loop style (Go, Netty, Node) hold 50k+ connections each. Zerodha's engineering blog describes its Go ticker serving hundreds of thousands of concurrent WebSocket connections and millions of quotes per second from a single binary. Each gateway gets the full conflated feed and filters per connection.
  5. Slow clients. A phone on a bad network cannot read fast enough. Never queue for it: keep one "pending frame" per connection and overwrite it. If the socket buffer stays full for seconds, drop the connection and let the app reconnect and resnapshot.
  6. Reconnect storms. At 09:14 millions of apps open. Add jitter to client reconnects, put connection limits per gateway, and use the snapshot-then-stream pattern so a reconnect costs one Redis read per instrument (served from the gateway's own copy, really).
WebSocket
  • Two-way: subscribe and unsubscribe on the same socket.
  • Binary frames: 5-10x smaller than JSON.
  • What Kite, Groww and most brokers use.
SSE
  • One-way and text only (binary must be base64).
  • Changing the watchlist needs a separate HTTP call.
  • Fine for a simple "price card" web widget; weaker for a trading app.

7.2 Order placement within 10 ms

The Groww SDE-II prompt (April 2025): order events arrive on a queue and each must be placed within 10 ms. The candidate discussed sharding, indexing, caching and retries; the feedback was "too basic" and it "should have extended to multiple exchanges and segments". The 10 ms budget forces a specific design.

StepBudgetHow
Auth, validation, dedup~1 msStateless pods; token verified locally (JWT); dedup check on a local + Redis set of recent client_order_ids.
Risk check and margin hold~1 msIn-memory RMS partitioned by user_id; no DB read on the hot path.
Durable record2-4 msAppend the order to a replicated log (Kafka acks=all inside one region, or a Postgres insert on a fast disk). Without this, a crash loses an order the user saw as placed.
Send to exchange1-3 msLong-lived exchange session in the adapter, leased line, no connection setup.
Slack~2 msGC pauses, queueing at peak.

The order state machine (every transition is an event in order-events):

  • Timeouts: if the exchange does not ack within, say, 500 ms, mark UNKNOWN and query the exchange's order status by our id. Only if the exchange confirms it does not have the order may we resend. Resending blindly can double-buy.
  • Stop-loss: exchanges support SL orders natively (a trigger price plus a limit price), so the broker sends them to the exchange and the exchange watches the trigger. The broker only holds triggers that the exchange will not keep, which is exactly GTT.
  • Positions and holdings: positions are a fold over today's fills; holdings come from the depository and are updated at end of day (T+1 settlement) with today's delivery buys shown on top. Serve both from Redis, rebuilt from the database.

7.3 GTT orders: consistency and failure states (the Groww 2026 question)

This is the question that sank a candidate: they proposed "keep GTTs in Redis and re-place them with an end-of-day cron", and the interviewer kept asking "what if it fails here?" about every arrow. The fix is a durable per-GTT state machine with conditional updates, not a batch job.

Same core as Stock Price Alerts (d63): rules indexed by trigger price per symbol in two sorted books, so each tick touches only the rules it crosses. That page explains the evaluator in depth; this section adds what changes when the action is a real order instead of a notification.

  1. Create. In one database transaction, insert the GTT (status ACTIVE) and an outbox row. The user gets 201 only after commit. The database is the source of truth, not Redis.
  2. Load. A relay (or Debezium CDC) publishes the outbox row to gtt-changes, keyed by instrument. Trigger-engine shards own a range of instruments; each holds two sorted structures per instrument: "fire when price ≤ x" and "fire when price ≥ x". On restart, a shard rebuilds from SELECT ... WHERE status='ACTIVE' AND instrument_id IN (my range), then resumes the topic.
  3. Detect and claim. A tick crosses 1,400. The engine pops matching triggers and claims each with a conditional update: UPDATE gtt SET status='TRIGGERING', version=version+1 WHERE gtt_id=? AND status='ACTIVE' AND version=?. If 0 rows change, someone else (another replica, a user cancel) won: do nothing. This is the guard against double firing.
  4. Place. Call the order service with idempotency key gtt_id:version. If the engine retries after a timeout, the order service returns the same order instead of placing a second one.
  5. Finish. Store placed_order_id and set TRIGGERED (or FAILED with the reason, for example "rejected: circuit limit" or "insufficient margin"). Notify the user. Kite's GTT API shows the same idea: a triggered GTT records the result of the order it placed, and a triggered GTT does not guarantee a fill.
  6. Crash in the middle. If the engine dies after the claim but before the order call (or before saving the result), the row sits in TRIGGERING. A sweeper finds rows in TRIGGERING for more than 30 s, asks the order service "do you have an order with key gtt_id:version?", and completes the row either way. Every intermediate state has an owner and a way forward.

Why "Redis + end-of-day cron" was rejected

  • Redis is not a source of truth for money. Brokers often run Redis with persistence off (Zerodha's blog says its caches do), and async replication can lose recent writes on failover. A GTT that silently vanishes is a lost customer order.
  • A cron is all-or-nothing with no memory. If it dies after placing 400,000 of 1M orders, which ones were placed? Without a per-item state and an idempotency key, rerunning it duplicates orders and skipping it loses them.
  • It does the wrong thing. Re-placing GTTs as day orders every morning puts real orders on the exchange that block margin all day and fill at a price the user did not trigger. GTT means "do nothing until the price is hit".
  • Thundering herd. One million orders at 09:15 hit exchange rate limits exactly when markets are busiest.

Kafka to order DB to order history: no dual writes

The interviewer drilled the hop where an event in Kafka becomes a row in the order DB and then a row in history. Rules that answer every "what if it fails here?":

  1. One writer per fact. The order service owns the order row. History is derived from order-events, never written separately by the API (a dual write loses one side on a crash).
  2. Outbox. State change and event go into the same DB transaction; a relay publishes. See outbox.
  3. Idempotent consumers. Every event carries (order_id, seq); consumers upsert and ignore a seq they have already applied. Kafka is at-least-once, so duplicates are normal.
  4. Ordering. Key the topic by order_id so all events of one order are in one partition, in order. A fill is never processed before the ack.
  5. Reconciliation. At end of day, compare our trades with the exchange's trade file. Any difference opens an incident. This is the safety net for bugs no design can rule out.

Market open gap

If INFY closes at 1,420 and opens at 1,380, every "buy at 1,400" trigger fires on the first tick. Expect a burst; push triggered orders through a queue per exchange that respects the exchange's order-rate limits, and process OCO legs so only one leg can win (claim both legs in one conditional update).

7.4 Intraday auto square-off

Groww SDE-2 (April 2026): live ticks for thousands of stocks at millions of updates/s; users or admins set rules as a percent move from the previous close (example from the post: previous close 100, upper circuit 120, exit at 118); evaluate in real time, send the Sell or Cover order at once, and notify.

  • Precompute the exit price. "Exit if price moves +18% from previous close" becomes "exit when LTP ≥ 118" at the start of the day. Now it is the same problem as GTT: per instrument, a sorted list of (exit_price, position_id). For loss-based rules (mark-to-market loss > 80% of margin), recompute the exit price whenever the position changes.
  • Shard by instrument, the same keying as the tick stream, so one shard sees all ticks of its instruments in order.
  • Idempotent exits. Key = (position_id, rule_id, trade_date). A replayed tick or a second replica cannot square off twice.
  • Priority. Square-off orders jump the queue ahead of new user orders for that user, and new MIS orders that would increase exposure are blocked while a square-off is in flight.
  • Time-based square-off. Brokers also close all open intraday positions at a fixed time before the close. Zerodha's published equity cut-off moved from 15:20 to 15:25 in a December 2025 update. A scheduler fans this out in batches across shards, but each position is still closed by an idempotent per-position job, not one giant loop.
  • Do not use conflated 500 ms prices for risk if you can avoid it: consume the full stream or a 50-100 ms conflation. Display can be lazy; risk should not be.

7.5 OHLC candles: from cache to SQL

Groww SDE-II (August 2025, selected) was asked to design the migration and aggregation of candle data from the cache to SQL; it was planned for one hour and ran two.

  • Windows by exchange time, not by arrival time, so a late packet goes into the right minute. Allow a short grace period (watermark) before closing a minute; a later correction is an upsert of the same key.
  • Idempotent writes: primary key (instrument_id, tf, start_ts) and INSERT ... ON CONFLICT DO UPDATE. Replaying a day rebuilds the same candles.
  • Batching: 5,000 instruments close a minute together, so write 5,000 rows in one multi-row insert per minute rather than 5,000 round trips.
  • Rollups: 5m = aggregate of five 1m rows (open of the first, close of the last, max high, min low, sum volume). TimescaleDB continuous aggregates or a scheduled job do this.
  • Migration of existing cache data: copy day by day per instrument with upserts, verify row counts and checksums per (instrument, day), dual-read (SQL first, cache as fallback) for a while, then switch reads and set TTLs on the cache keys. Never delete the source before verification.

7.6 Many exchanges and segments

  • Instrument master: every tradable thing is (exchange, segment, token) with lot size, tick size, price band and expiry. Download the exchange files every morning before 09:00.
  • Adapter per exchange+segment behind one internal interface (place, modify, cancel, event stream). Each has its own session, rate limits and bulkhead (separate thread pools and pods), so an MCX outage does not block NSE orders.
  • Risk per segment: cash equity needs full price or intraday margin; F&O uses exchange-published margin files (SPAN plus exposure). The RMS loads segment-specific rules.
  • Partition order flow by (exchange, segment) for Kafka topics and engine shards. Market hours differ (commodity trades into the night), so square-off and GTT expiry schedules are per segment.
