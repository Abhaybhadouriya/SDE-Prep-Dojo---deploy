Back-of-envelope estimation

Market data in

  1. Ingress ticks: 1M ticks/s. A normalised tick (instrument id, LTP, volume, OI = open interest, the number of futures or options contracts still open, timestamps, best bid/ask) is about 64-100 bytes, so about 64-100 MB/s, or under 1 Gbps. One good server can parse this; we run two (A and B feeds) for redundancy.
  2. Per instrument: 1M / 5,000 = 200 ticks/s on average. Hot ones (index futures, large caps) get far more; illiquid ones almost none.

Market data out (the scary part)

  1. Subscriptions: 5M users x 20 instruments = 100M (user, instrument) pairs. Average watchers per instrument = 100M / 5,000 = 20,000, but popular ones (NIFTY, RELIANCE) may have over 1M watchers.
  2. Naive fan-out (every tick to every watcher): each user would get 20 x 200 = 4,000 messages/s. Times 5M users = 20 billion messages/s. Impossible, and no phone can render that.
  3. Conflate to the freshness limit: send the latest value per instrument every 500 ms = 2 updates/s/instrument. Per user: 20 x 2 = 40 updates/s. Batch all updates for one user into one frame per 500 ms: 2 frames/s/user, so 5M x 2 = 10M frames/s overall.
  4. Bandwidth: Kite Connect's binary packets are 8 bytes (LTP only), 44 bytes (quote) or 184 bytes (with depth). With 20 quote packets (about 900 bytes) per frame: 10M x 900 B = about 9 GB/s, or 72 Gbps. With LTP-only for the watchlist (about 200 bytes per frame): about 2 GB/s, 16 Gbps. So the watchlist uses compact LTP-style packets and only the open stock page gets depth.
  5. Gateway count: if one WebSocket node holds 50,000 connections and pushes 100,000 frames/s, we need 5M / 50,000 = 100 nodes, about 150 with headroom for a node failure and the 09:15 login burst.
  6. Key insight: after conflation the whole market is only 5,000 x 2 = 10,000 updates/s, about 1 MB/s. That is small enough to send the entire conflated feed to every gateway and let each gateway filter per connection. No per-user routing table is needed in the middle tier.

Orders

  1. Daily orders: 20M/day. Trading hours are 6 h 15 min = 22,500 s (not 86,400). Average = 20M / 22,500 = about 900 orders/s.
  2. Peak: the first minutes after 09:15 and expiry days run about 10x average: about 9,000 orders/s. Each order has 3-5 state events (placed, open, partial fill, filled), so about 40,000 events/s at peak.
  3. Storage: about 1 KB per order including its events = 20 GB/day. Over 250 trading days = 5 TB/year of order history, kept for years for audit: partition by trade date.

GTT and risk

  1. GTT: 1M new per day (prompt: about 10 orders per user, 10% of them GTT). They live up to a year, so the active set can reach tens of millions. Say 20M active x 300 bytes = 6 GB. That fits in memory across a few shards.
  2. Trigger checks: on each price update for an instrument, find triggers crossed. With per-instrument sorted thresholds, that is O(log n + k), where k is the number fired.
  3. Auto square-off: say 2M open intraday positions at peak. Same structure: per instrument, positions sorted by their exit price.

Candles

  1. NSE equity trades 375 minutes a day. 5,000 instruments x 375 = 1.9M one-minute candles/day x about 50 bytes = about 94 MB/day. Ten years is about 230 GB, a normal SQL or time-series database.

Saying "after conflation the whole market is 10,000 updates/s" is the moment the interviewer relaxes. It turns a 20-billion-messages problem into a filtering problem at the edge.
