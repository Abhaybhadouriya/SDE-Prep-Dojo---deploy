Requirements

Functional

  1. Home page recommendations A personalised list (or rows) for each user when they open the app.
  2. Item page "similar items" / "people also bought" Recommendations for an item, optionally personalised.
  3. Freshness Watching, buying or clicking something changes recommendations within minutes (Netflix's example: update after a member starts watching).
  4. Filters and rules Never show out-of-stock items, items already bought, or content not licensed in that country; support promotions.
  5. Experimentation Run A/B tests between models.

Level 2: embeddings, ANN and the feature store in one picture

Before the numbers, four words you will see in every line of the estimation.

  • Embedding: a list of, say, 128 numbers per item (and per user). A model learns them so that items people like together end up close to each other, the way two cities are close on a map. "Find similar items" becomes "find nearby points".
  • ANN search (approximate nearest neighbour): find the 500 points nearest to a query point without measuring the distance to all 100M. You accept that a few true neighbours are missed (recall of 95%+) in exchange for answering in milliseconds. Exact k-nearest-neighbour (kNN) would scan everything.
  • HNSW (Hierarchical Navigable Small World): the usual ANN index. It is a layered graph: the top layer has few points with long links, lower layers have more points with short links. A search starts at the top, hops greedily towards the query, and drops a layer each time it cannot get closer.
  • Feature store: a key-value store of precomputed inputs for the ranking model, such as "user u_42 watched 3 thrillers this week" or "item t_91 click rate today". The ranker reads them with one batched multi-get instead of computing them per request.

From your world

HNSW is a skip list for points in space. A skip list has sparse upper levels for long jumps and a dense bottom level for the final steps; HNSW does the same with a graph, so a search takes about log(n) hops. The feature store is a precomputed lookup table on the fast path, like a FIB compiled from the routing table (more on that below).
