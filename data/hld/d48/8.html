Trade-offs, bottlenecks and failure modes

DecisionOption AOption BHow to choose
Serving modePrecompute per-user lists offlineCompute online per requestPrecompute is cheap and robust but stale; online is fresh but costly. Most systems precompute candidates and rank online.
RetrievalTwo-tower + ANNItem-to-item CF listsANN generalises and handles new items via content; i2i is simple, explainable, very strong for "also bought". Use both.
ANN indexHNSWIVF-PQHNSW for recall when RAM allows; IVF-PQ for billions of vectors.
Ranker sizeBig model, fewer candidatesSmall model, more candidatesSet by latency budget; distil the big model into the light ranker.
Feature freshnessDaily batchStreamingStream only the features whose value decays fast (session intent); batch the rest.
RetrainingDaily full retrainContinuous / hourly fine-tuneFresher models vs operational risk; needs automated validation.
Resilience moves
  • Fallback chain: heavy model -> light model -> precomputed list -> popular in region
  • Per-stage timeouts; return partial candidates rather than nothing
  • Cache item features in the ranker process
  • Blue/green ANN index swaps
Failure modes
  • Feature pipeline silently stalls: model sees stale or null features (monitor freshness)
  • Training-serving skew after a feature code change
  • Feedback loop: popular gets more popular; new items starve
  • Hot item (viral launch) floods caches and one ANN shard

Netflix's warning, in short: a purely online computation may miss its SLA, so always have a fast fallback such as reverting to a precomputed result. Say this out loud in the interview.

Related patterns: Scaling Reads (caching precomputed lists), Fan-out (precompute vs compute on read is the same trade-off as push vs pull feeds), Resilience Patterns.
