Architecture: serving one request

  1. Request. The client calls the recommendation API. The orchestrator checks the experiment assignment and, if the ML path is slow or down, can return a precomputed list instantly.
  2. Retrieve (in parallel). Several candidate sources each return a few hundred items: nearest neighbours of the user's embedding, item-to-item lists for recently viewed items, trending in the region, continue-watching. X's open-source timeline does the same: about half its candidates come from accounts you follow, the rest from out-of-network sources.
  3. Fetch features. One batched multi-get to the online feature store for user features and per-candidate features (popularity, price, freshness, past interactions).
  4. Light ranking. A cheap model (often a distilled version of the heavy one) cuts ~1,000 candidates to ~150. Instagram Explore's first pass took 500 down to 150.
  5. Heavy ranking. A big multi-task model predicts several outcomes (click, play, buy, like, hide) and a value model combines them into one score. Instagram's final pass picked the top 25 for the first page.
  6. Re-rank and filter. Remove already-bought or unavailable items, apply business rules and diversity (no five items from the same author/brand in a row), then return.
  7. Log and learn. Impressions with features, plus clicks and plays, go to Kafka. Stream jobs update fresh features (for example "last 5 items viewed") within seconds to minutes; the lake feeds daily training.

From your world

The funnel is a router's fast path and slow path. A TCAM lookup or hash table handles every packet cheaply; only the few that need it get punted to the CPU for expensive processing. Retrieval is the TCAM; the heavy ranker is the route processor. You never send line-rate traffic to the slow path.
