Interview: drive the 45 minutes

  1. 0-5 min Which surface (home, item page, email)? Catalogue size? Freshness need? Business objective (watch time, purchases)?
  2. 5-10 min Numbers: 17K QPS, 1,000 candidates, 17M scores/s, 100 GB index, 116K events/s. Conclude "funnel".
  3. 10-25 min Serving path (API, sources, feature store, rankers, re-rank) and data path (Kafka, stream jobs, lake, training, registry).
  4. 25-40 min Deep dives: ANN retrieval, feature store/skew, cold start, offline/nearline/online, A/B testing.
  5. 40-45 min Fallbacks, monitoring (latency per stage, feature freshness, CTR by model, coverage of catalogue).

60-second answer, said out loud: "The catalogue is too big to score per request, so it is a funnel. Several candidate sources run in parallel: ANN search over item embeddings with the user's embedding as the query, item-to-item lists, trending. That gives about a thousand items. A light model cuts to about 150, a heavy multi-task model scores those, and a re-ranker applies diversity and business rules. Heavy work is offline (training, embeddings, lists), fresh signals come nearline from Kafka through stream jobs into an online feature store, and only the last mile runs online in about 200 ms. Every response is logged with a request id so clicks become training labels, and there is always a precomputed fallback."

SDE-1 stops here / SDE-2 adds. SDE-1: the funnel, precomputed lists in a key-value store, events to Kafka, a fallback when the ML path is slow, the request id for logging. SDE-2 adds: two-tower retrieval and the ANN index choice (HNSW vs IVF-PQ) with memory maths, training-serving skew and point-in-time-correct features, cold start, offline/nearline/online placement of each computation, and A/B testing with exposure logging.

You might confuse this with exact kNN. Exact k-nearest-neighbour measures the distance to every vector, so it is always right and always slow (100M comparisons). ANN gives up a little recall to answer in milliseconds. Also do not confuse retrieval (find a thousand plausible items fast) with ranking (score a few hundred carefully): an interviewer will push back if you run the heavy model on retrieval.

Why can't you just score every item for every request?

Arithmetic: 17K requests/s x 100M items = 1.7 trillion model evaluations per second, impossible within 200 ms. So use a funnel: cheap retrieval (ANN, precomputed lists) to ~1,000, a light ranker to ~150, a heavy ranker to ~50, then re-rank. Each stage spends more per item on fewer items. Instagram Explore published 500 -> 150 -> 50 -> 25.

How to answer

Do the multiplication first; the funnel then sounds forced by the numbers rather than memorised.

Explain offline, nearline and online computation with examples.

Offline: batch jobs over the lake with no latency limit, e.g., training, item embeddings, "also bought" lists refreshed daily. Nearline: event-driven stream jobs that store results, e.g., update "recently watched" seconds after a play starts. Online: inside the request with a strict SLA, e.g., ranking candidates for this context. Combine them: precompute the heavy parts, add freshness online, and keep offline results as the fallback (Netflix's framing).

How to answer

One example per mode, then the "combine + fallback" sentence.

How does "customers who bought this also bought" work at Amazon scale?

Item-to-item collaborative filtering. Offline, for each item, look at its buyers' purchases and score related items by how much more likely A's buyers are to buy B than an average customer (not raw co-counts, which would just surface bestsellers; Amazon also corrected for heavy buyers). Store the top-N related items per item in a key-value store. Online, take the user's recent items, union their related lists, weight and rank. It scales because each item has a small set of buyers, and Amazon found daily refresh of every list feasible.

How to answer

Contrast with user-based CF (compare against all customers: too slow) and stress the offline precomputation.

Design the embedding retrieval for 100M items with 10 ms latency.

Two-tower model; item tower runs offline daily to embed all items (128-dim float32 = ~51 GB raw). Build an HNSW (or IVF-PQ if memory-bound) index, sharded by item hash across N nodes with replicas for QPS. Query: compute the user vector (online tower or cached), fan out to all shards in parallel, each returns top-K, merge. Rebuild offline and swap blue/green; for new items, add to a small real-time index merged at query time. Filter by availability after retrieval, over-fetching to compensate.

How to answer

Memory math, index choice with its trade-off, sharding, rebuild strategy, freshness for new items.

Likely follow-ups

  • What if you need to filter by country before retrieval?
What is a feature store and why do you need one?

A system that defines features once and serves them two ways: an offline store (lake tables) for point-in-time correct training data, and an online store (Cassandra/Redis) for millisecond lookups at serving. Batch jobs and stream jobs write both. It removes training-serving skew, lets teams reuse features, and tracks owners and freshness SLAs. Uber's Michelangelo: ~10K features, online P95 under 10 ms with Cassandra.

How to answer

Two stores, one definition; name skew as the problem it solves.

How do you handle cold start for new users and new items?

New users: contextual popularity (region, device, time), onboarding choices, and fast nearline updates so a few clicks change the next page. New items: a content-based tower (category, text, image embeddings) gives a vector immediately; reserve exploration slots (bandit) so items gather interactions; boost very new items in re-ranking with a decay.

How to answer

Split users vs items; name exploration and the feedback loop it breaks.

The ranking service is slow during a sale. What happens to the home page?

Each stage has a timeout and a fallback: if the heavy ranker misses its budget, return the light ranker's order; if retrieval is degraded, return the precomputed per-user list from the key-value store; if that is missing, popular in region. The page always renders. Autoscale rankers ahead of the sale, cache item features in-process, and shed optional rows first.

How to answer

Show a fallback ladder; "recs must degrade, not fail".

Where do Kafka and stream processing fit in a recommender?

Clients and services publish impressions, clicks, plays and orders to Kafka (keyed by user_id). Stream jobs compute fresh features (session activity, recent items, trending counts) into the online feature store; a sink writes raw events to the lake for training; the impression log joins with outcomes to create labels. The serving path never waits on Kafka.

How to answer

Name the three consumers: nearline features, lake, label join.

Likely follow-ups

  • What partition key and why?
How do you safely roll out a new ranking model?

Offline gates (AUC/NDCG vs current, feature-coverage checks), then shadow mode (score live traffic, compare distributions, no user impact), then an A/B test on a small hashed bucket with guardrail metrics (latency, errors, revenue), then ramp. Log model version and experiment id on every impression. Keep the previous version loaded for instant rollback.

How to answer

Offline -> shadow -> canary/A-B -> ramp, with guardrails.

Likely follow-ups
  • Offline metric improved but online got worse. Why?
How do you avoid recommending things the user already bought or that are out of stock?

Filters in the re-rank stage using fresh data: a per-user "purchased / hidden" set (nearline-updated, in the feature store or a Bloom filter for large histories) and real-time availability from the inventory service (cached with a short TTL). Over-fetch candidates so that filtering still leaves enough items. Hard filters run after ranking, before response, so they always use the freshest data.

How to answer

Separate business filters from the model; say where the fresh data comes from.

Scenario: click-through dropped 8% overnight, no deploy

No code or model change, but CTR on home recommendations dropped sharply.

Weak answer: "Retrain the model."

Strong answer: suspect data, not code. Check feature freshness and null rates (a stalled stream job or failed batch load), fallback-served rate (is the ML path timing out?), candidate source mix (did the ANN index swap fail?), and upstream schema changes. Compare served features in the impression log with yesterday's distribution. Fix the pipeline, then add alerts on feature freshness.

Scenario: Big Billion Days, 10x traffic

A sale event drives 10x home-page traffic for 6 hours.

Weak answer: "Autoscale everything."

Strong answer: pre-scale rankers and ANN replicas, warm caches with precomputed lists for active users, cut candidates per request (1,000 to 500) and skip the heavy ranker for logged-out users, push sale items through a dedicated candidate source, and keep the fallback ladder ready. Common mistakes

Common mistakes: diving into ML algorithms and forgetting the system; no funnel; no fallback; ignoring how training data is logged; no cold-start plan; treating "real time" as needing everything online.
