Deep dives

1. Offline, nearline, online: where each computation lives

Netflix's 2013 architecture post (Amatriain and Basilico) is still the clearest framing. Online computation reacts to the current context but must meet a response-time SLA, which limits model complexity. Offline batch jobs can use any amount of data and complex models but go stale between runs. Nearline computes like online, in response to events, but stores the result instead of serving it immediately. Their advice: combine all three, and always keep a fast fallback such as a precomputed result.

2. Candidate generation: two-tower embeddings and ANN

A two-tower model has one neural network for users and one for items. Each turns its entity's features into an embedding, a vector of maybe 64-256 numbers. Training pushes users close to the items they engage with. Because the towers are independent, item embeddings can be precomputed (daily at Instagram) and loaded into an approximate nearest neighbour (ANN) index. At request time you compute or look up the user's vector and ask the index for its top few hundred neighbours in a few milliseconds. The cost of independence: the model cannot use user-item interaction features; that is the ranker's job.

Scaling the index: shard items across ANN nodes (by item id hash), query all shards in parallel, merge top-K (scatter-gather), and replicate each shard for QPS. Rebuild offline and swap atomically (blue/green index). Hello Interview's rule of thumb: start with an extension in an existing database (pgvector, Elasticsearch, Redis) and reach for a dedicated vector DB beyond roughly 100M vectors.

Other candidate sources matter as much: item-to-item collaborative filtering ("customers who bought A also bought B", where B is related to A if A's buyers buy B more often than the average customer does, which avoids recommending bestsellers to everyone), graph walks (X's GraphJet-based UTEG), popularity and trending, and the user's own history. Mix sources with tunable weights, as Instagram describes.

3. Feature store and training-serving skew

Uber's Michelangelo is the reference design: an offline store in Hive/HDFS for training, an online store in Cassandra for serving, batch jobs that bulk-load features every few hours or daily, and near-real-time features computed from Kafka by streaming jobs and written to both stores. Uber reported about 10,000 shared features, online P95 under 10 ms with Cassandra lookups, and its busiest models serving over 250,000 predictions per second. A shared feature definition language guarantees the same transformation at training and prediction time.

  • Point-in-time correctness: when building training rows, join each label with feature values as of the moment of the impression, never later. Otherwise you leak the future into training.
  • Log what you served: store features with each impression so training uses exactly the serving values.
  • Freshness SLA per feature: owner, description and SLA live in feature metadata (as at Uber), and monitoring alerts on stale or null-heavy features.

4. Cold start and exploration

New user: no history, so no embedding. Use context (country, device, time), onboarding choices, and popularity within a segment; switch to personalised retrieval after a few interactions, which the nearline pipeline captures within minutes. New item: no interactions, so collaborative filtering cannot see it. Use a content tower (title, category, text and image embeddings) so it gets a vector on day one, and reserve a small share of slots for exploration (a bandit approach) so new items earn data. Without exploration, the system only learns about what it already shows: a feedback loop.

5. Evaluation, A/B tests and feedback loops

  • Offline metrics (recall@K for retrieval, AUC / NDCG for ranking) on held-out data are a gate, not the verdict.
  • Online A/B tests decide: assign users to buckets by hash, log the experiment id on every impression, compare business metrics (plays, purchases, retention). Netflix's part-1 post describes combining offline experimentation with online A/B testing.
  • Position bias: items shown at the top get clicked more because they are at the top. Log position and correct for it in training.
  • Rollout: shadow-score a new model on live traffic, then canary 1% of users, then ramp. Keep the previous model warm for rollback.
