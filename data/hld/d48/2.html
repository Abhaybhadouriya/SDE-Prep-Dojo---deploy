Back-of-envelope estimation

All inputs below are stated assumptions; the method is from Back-of-Envelope Estimation.

~17Krec requests/s peak
~17Mitem scores/s
~116Kevents/s (avg)
~100 GBitem-embedding index
  1. Requests 100M DAU x 5 home-page loads per day = 500M requests/day = ~5.8K/s average. Peak at 3x = ~17K requests/s.
  2. Ranking work If each request ranks ~1,000 candidates, that is 17K x 1,000 = 17M item scorings per second at peak. This is why the heavy model only sees a few hundred items, and why there is a light ranker first.
  3. Feature lookups 1,000 candidates x ~100 features each per request: the online feature store must answer batched multi-gets for ~1.7 billion feature values per second at peak. In practice you cache item features in the ranking service and fetch only user features and a few item-user cross features per request.
  4. Embeddings 100M items x 128 dimensions x 4 bytes (float32) = ~51 GB of raw vectors. An HNSW index needs roughly 2x the raw vectors (Hello Interview's rule of thumb) = ~100 GB, so shard it across several nodes or compress the vectors. User embeddings: 300M x 128 x 4 B = ~154 GB in a key-value store.
  5. Events 100M DAU x 100 events/day (impressions, clicks, plays, add-to-cart) = 10B events/day = ~116K events/s average, maybe 350K/s at peak. At ~200 bytes each that is ~2 TB/day into the data lake.
  6. Precomputed lists 300M users x 500 items x 8 bytes (id) = ~1.2 TB in a key-value store such as Cassandra or a memcached tier (Netflix uses Cassandra, EVCache and MySQL for results).
  7. Latency budget (200 ms total): retrieval ~30 ms (sources in parallel), feature fetch ~30 ms, light rank ~20 ms, heavy rank ~50 ms, re-rank and filters ~10 ms, the rest for network and serialisation. Uber's Michelangelo reported online model P95 under 10 ms with feature-store lookups, so these budgets are realistic.

What the numbers say: you cannot score the whole catalogue per request (17K x 100M = 1.7 trillion scores/s). The funnel is not an ML nicety; it is forced by arithmetic.
