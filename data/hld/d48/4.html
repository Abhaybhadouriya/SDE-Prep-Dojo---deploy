-- served-impressions log: the most important table you will build
CREATE TABLE impressions (
  request_id     STRING,
  user_id        BIGINT,
  item_id        BIGINT,
  position       INT,
  candidate_src  STRING,          -- 'ann', 'i2i', 'trending', 'in_network'
  model_version  STRING,
  experiment     STRING,
  features_json  STRING,          -- features exactly as seen at serving time
  served_at      TIMESTAMP
) PARTITIONED BY (dt STRING, hr STRING);

Logging the features as served (not recomputed later) is how big teams avoid training-serving skew, the bug where the model is trained on slightly different numbers than it sees in production. SQL vs NoSQL here is not a single choice: the catalogue is relational, serving stores are key-value, training data lives in a lake. See Choosing Storage.

From your world

The offline and online feature stores are the RIB and FIB. The offline store is the full, rich history, like the routing information base. The online store is a compiled, lookup-optimised subset, like the forwarding table in the line card. A batch job "compiles" one into the other, and nearline streams push incremental updates the way BGP updates trickle into the FIB without a full rebuild.
