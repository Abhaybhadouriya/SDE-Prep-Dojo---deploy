Key APIs

# home page: rows of recommendations
GET /v1/recommendations/home?userId=u_42&surface=web&limit=40&cursor=...
  -> { "requestId": "r_7f1", "rows": [
        { "title": "Because you watched Dark", "items": [{"id":"t_91","score":0.82}, ...] },
        { "title": "Trending in India", "items": [...] } ],
       "modelVersion": "rank-2026-11-22", "experiment": "exp_118:B" }

# item page: "similar items" / "people also bought"
GET /v1/items/{itemId}/similar?userId=u_42&limit=20&cursor=c_ab12
  -> { "requestId": "r_8a2", "experimentId": "exp_204:A",
       "items": [
         { "id": "p_311", "score": 0.91, "source": "i2i_also_bought",
           "reason": "Bought together with this item" },
         { "id": "p_078", "score": 0.77, "source": "ann_item_vec",
           "reason": "Similar to this item" } ],
       "nextCursor": "c_ab32",          # opaque; encodes offset + list version
       "fallback": false }               # true when served from the precomputed list

# feedback events (batched from clients, fire-and-forget)
POST /v1/events
  [ { "type": "impression", "requestId": "r_7f1", "itemId": "t_91", "position": 3, "ts": ... },
    { "type": "play", "itemId": "t_91", "ts": ... } ]

The requestId on every impression and click is essential. It joins "what we showed, at which position, from which model" with "what the user did", which is the training label for the next model. Events go to Kafka through a thin ingestion service; the API never waits on them.

Three more fields earn their place. source says which candidate source produced the item (ANN, item-to-item list, trending), which makes debugging and per-source metrics possible. reason is the short "because you watched..." text shown to the user. experimentId records which A/B arm served the response, so clicks can be credited to the right model. The cursor is opaque and pins the list version, so page 2 is cut from the same ranked list as page 1 even if a new model ships meanwhile (ranked results for a cursor are cached for a few minutes).

Timeouts: the API gives the ML path a hard budget (for example 150 ms). If it does not answer in time, the API returns the user's precomputed list from the key-value store (written by last night's batch job) with fallback: true, and if that is missing too, a "popular in your region" list. The user always gets something.
