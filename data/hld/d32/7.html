Where Kafka, Kubernetes and Docker fit

  • Kubernetes. Storage nodes run as a StatefulSet: stable network identity (kv-0.kv.svc) matters because the ring maps tokens to node identities, and each pod gets its own PersistentVolumeClaim (Storage). Use pod anti-affinity and topology spread constraints across zones so the N replicas really land in different failure domains. Production Cassandra on Kubernetes is usually run by an operator (for example K8ssandra) that knows how to bootstrap, decommission and repair safely; a plain rolling update is not enough.
  • PodDisruptionBudget. With N = 3 and quorum 2, never allow more than one replica of a range down during maintenance: maxUnavailable: 1.
  • Kafka. Often sits next to a KV store as its change log: DynamoDB Streams or Cassandra CDC (change data capture: it tails the store's commit log and publishes each committed change to Kafka, like a journal replay in a filesystem) feed Kafka so search indexes, caches and analytics stay in sync (see CDC Pipeline). Kafka's own design shares ideas with this page: partitions, replication, a commit log. The difference: Kafka uses a leader per partition with an in-sync replica set (Replication & ISR), much like DynamoDB, not like Dynamo.
  • Docker. Each node is one container with data on a mounted volume, never in the container's writable layer. Use Docker Compose to run a 3-node local cluster for testing failure cases (stop one container, watch hinted handoff).
