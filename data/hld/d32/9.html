Common mistakes: saying "use consistent hashing" without virtual nodes or replica placement; claiming R+W>N gives linearizability (it does not with sloppy quorums or concurrent writes); forgetting deletes need tombstones; not mentioning how a new node bootstraps; ignoring hot keys.

Design a distributed key-value store like Dynamo.

Clarify AP vs CP and sizes. Partition with consistent hashing and virtual nodes; replicate each key on the next N = 3 distinct physical nodes (across AZs). Any node coordinates; writes go to all N and return after W acks, reads after R (3, 2, 2). Accept writes during failures with sloppy quorum + hinted handoff; detect divergence with vector clocks and return siblings, or use LWW if the data allows. Repair with read repair and Merkle-tree anti-entropy. Membership via gossip with seed nodes. Each node stores data in an LSM tree (commit log, memtable, SSTables, Bloom filters).

How to answer

Walk Dynamo's Table 1 as problem then technique. For each technique say what it costs. End with "if we needed strong consistency, I would switch to a leader per partition with Raft, like DynamoDB did".

N=3, R=2, W=2. Can a read still return stale data?

Yes, in several cases: (1) a sloppy quorum sent the write to stand-in nodes outside the home set, so read and write sets did not overlap; (2) a write is still in progress (one replica has it, the read hits the two that don't yet); (3) a write failed after reaching one replica, which is not rolled back; (4) concurrent writes produce siblings. R + W > N gives overlap on strict quorums, not linearizability.

How to answer

Agree with the textbook rule first, then list the exceptions. This is a seniority signal.

Likely follow-ups
  • How would you make it linearizable? (Leader + consensus, or read-repair synchronously plus strict quorum, with care.)
Explain vector clocks with an example. When would you choose last-write-wins instead?

A vector clock is a list of (node, counter). D2 = [Sx,2]. If Sy writes from D2 we get [Sx,2][Sy,1]; if Sz also writes from D2 we get [Sx,2][Sz,1]. Neither dominates, so both are kept and returned; the client merges and writes [Sx,3][Sy,1][Sz,1]. Choose LWW when losing a concurrent update is acceptable (session data, caches, sensor readings) and you want no client merge logic; Dynamo itself used timestamp reconciliation for session state. Choose vector clocks or CRDTs when every update matters (carts, counters).

How to answer

Draw the diamond (D2 forks to D3, D4, merges into D5). Then the decision rule.

Likely follow-ups
  • How big do clocks get? (Dynamo truncated at 10 entries.)
  • What is a CRDT?
Why virtual nodes? What goes wrong with one token per server?

With one token per server, ranges are uneven (random positions), a bigger server cannot take more load, and when a server dies its whole range falls on one neighbour, which must also rebuild it alone. With many virtual nodes per server, ranges average out, capacity can be weighted by token count, and a failure spreads load and re-replication across many peers in parallel. Too many tokens also hurts: more neighbours, more repair work (Cassandra moved from 256 random tokens to far fewer with a smart allocator).

How to answer

Three benefits (balance, heterogeneity, parallel recovery), one cost.

Likely follow-ups
  • Which keys move when a node joins?
A node was down for 3 days. How does it catch up?

Hints are only kept for a limited window (stand-in nodes would otherwise fill up), so after days most changes are not in hints. When it returns, gossip marks it up; it must not serve reads with R = 1 until repaired. Run anti-entropy: compare Merkle trees per range with peers and stream only differing ranges. Meanwhile read repair fixes hot keys. If it was down longer than the tombstone grace period, wipe and re-bootstrap it instead, or deleted data can come back to life.

How to answer

Layers: hints (short), Merkle repair (long), re-bootstrap (too long). Mention the zombie-delete trap.

Likely follow-ups
  • How do you throttle repair so it does not hurt live traffic?
One key gets 100x more traffic than the rest. What do you do?

For reads: cache in front (with request coalescing so a miss triggers one fetch), allow reads from all N replicas (R = 1 with load spreading), or replicate the hot key more widely. For writes: split the key into K sub-keys (key#0..key#K-1), write to a random one, and sum or merge on read (good for counters). Detect hot keys with per-key sampling at coordinators. Discord's real fix for hot channels was coalescing plus routing all requests for one channel to one service instance.

How to answer

Split reads vs writes; give one concrete technique each, then a real example.

Likely follow-ups
  • See Distributed Counter for the write-split pattern.
DynamoDB is named after Dynamo. Is it the same design?

No. Dynamo is leaderless with sloppy quorums and vector clocks. DynamoDB uses a leader per partition chosen by Multi-Paxos, replicas across three AZs, a central control plane, and offers strongly consistent reads served by the leader. It trades a bit of write availability during leader changes for simpler semantics and predictable performance, which managed-service customers wanted. The 2022 paper reports a peak of 89.2 million requests per second during Prime Day 2021.

How to answer

Make a two-column comparison (writes, conflicts, consistency, membership). Shows you read beyond the 2007 paper.

Start simpler: design an in-memory KV store on one machine (Redis-like). Then scale it.

One machine: a hash map with a lock per bucket (or a single-threaded event loop like Redis), TTL via a min-heap or lazy expiry, eviction with LRU (hash map + doubly linked list, O(1)). Durability with an append-only log replayed at start, plus periodic snapshots. To scale: shard by consistent hashing in the client or a proxy, add a replica per shard (leader-follower with async replication), and fail over with a coordinator. This is the bridge from LLD to this page.

How to answer

How does a new node join the ring without downtime?

An operator (or control plane) assigns it tokens. It announces itself via a seed node; gossip spreads the new ring. For each range it will own, it streams data from current owners while they keep serving. Writes for those ranges are sent to both old and new owners during the move (pending ranges). When streaming completes, ownership flips and old owners drop the data after a cleanup. With fixed partitions (Dynamo's strategy 3) a move is just copying whole partition files.

How to answer

Key word: dual-write during handoff so no write is lost.

Likely follow-ups
  • What if two nodes join at once?
Make it multi-region. What changes?

Replicate per region (e.g. 3 replicas in each of 2 regions). Use local quorums (LOCAL_QUORUM) so a request never waits for a cross-region round trip, and replicate asynchronously between regions. Conflicts across regions are now normal, so you need a rule: LWW with good clocks, vector clocks, or CRDTs, or home each key in one region (writes go there). DynamoDB Global Tables replicate across regions this way.

How to answer

Latency budget first (cross-region RTT 50-150 ms), then the conflict policy. Link to Reliability & Multi-Region.

Likely follow-ups
  • What is the RPO if a region dies?

Scenario: "items keep coming back in my cart"

Users report that items they deleted reappear a few minutes later.

Weak answer: "Add a cache invalidation."

Strong answer: this is sibling merge by union. A delete on one replica and an older "add" on another become concurrent versions; the union merge brings the item back. Fix: represent the cart as an observed-remove set (OR-Set CRDT) that keeps remove markers, or record deletions explicitly with tombstones per item. Also check whether clients send the context from their last read; a blind write without context always creates siblings.

Likely follow-ups
  • How would LWW behave here instead?

Scenario: p99 latency doubles every night at 2 am

No traffic change, but tail latency spikes nightly.

Weak answer: "Add more nodes."

Strong answer: look for scheduled background work: anti-entropy repair, compaction, backups. Throttle them with an admission controller tied to foreground latency (Dynamo did exactly this), spread repairs over the day by sub-range, and check compaction strategy. Confirm with per-node metrics: disk I/O, compaction pending, repair progress.
