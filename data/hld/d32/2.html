Back-of-envelope estimation

Assume a general-purpose store for a big company. These are our interview assumptions, not published numbers. (Method: Estimation.)

  1. Data size. 10 billion keys x (100 B key + 1 KB value + ~100 B of version metadata: a vector clock - a list of (node, counter) pairs, explained in deep dive 1 - plus timestamps) = about 12 TB of logical data.
  2. Replication. N = 3 copies: 36 TB stored. LSM storage engines need free space for compaction; plan for about 50% headroom: about 72 TB of raw disk.
  3. Nodes. With 4 TB of SSD per node: 72 / 4 = 18 nodes. Round up to 24 so a rack can fail and so each node is not too large to re-replicate quickly. (Discord ran 72 ScyllaDB nodes with 9 TB each for trillions of messages, so this order of magnitude is realistic.)
  4. Traffic. Peak 1,000,000 reads/s and 200,000 writes/s. With N = 3, every write becomes 3 replica writes: 600,000 replica writes/s across 24 nodes = 25,000 writes/s per node. Reads with R = 2 touch 2 replicas: 2,000,000 replica reads/s / 24 = about 83,000 per node. That is high, so either add nodes, or read with R = 1 for data that tolerates staleness, or put a cache in front.
  5. Bandwidth. Reads: 1M x 1.2 KB = about 1.2 GB/s out to clients. Writes: 200k x 1.2 KB x 3 = about 720 MB/s of replication traffic inside the cluster. 10/25 GbE NICs handle this when spread over 24+ nodes.
  6. Recovery time. A dead 4 TB node must be rebuilt from its peers. With virtual nodes, all other nodes share the copy work: at 100 MB/s each from 20 peers, that is 2 GB/s, so 4 TB takes about 35 minutes instead of 11 hours from a single peer. This is one big reason virtual nodes exist.
