Key APIs

PUT    /v1/kv/{key}      body: value bytes
       headers: X-Context: <opaque version (vector clock) from last read>
                X-W: 2                    # optional per-request write quorum
       -> 200 {"context": "..."}           # new version token

GET    /v1/kv/{key}      headers: X-R: 2
       -> 200 {"values": ["..."], "context": "..."}       # usually 1 value
       -> 300 {"values": ["v1", "v2"], "context": "..."}  # siblings: client must merge

DELETE /v1/kv/{key}      headers: X-Context: ...         # writes a tombstone

Dynamo's real interface was exactly this shape: get(key) returns one object, or a list of conflicting versions, plus a context; put(key, context, object) sends the context back so the store knows which versions this write replaces.

Why the context? The context is the version metadata from your last read (a vector clock: a list of (node, counter) pairs; deep dive 1 shows how they are compared). Without it the store cannot tell "this write saw version A and replaces it" from "this write never saw A". The context carries the vector clock, so the server can decide which old versions to drop.
