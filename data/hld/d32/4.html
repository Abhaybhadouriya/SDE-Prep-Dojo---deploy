Data model and storage engine

On each node the data is just key -> (value, version, tombstone?, timestamp). The interesting choice is the local storage engine.

EngineGood atUsed by
LSM tree (memtable + SSTables)High write rates: writes are sequential appendsCassandra, ScyllaDB, RocksDB, LevelDB
B-treeReads, in-place updatesDynamo used Berkeley DB (BDB) in most instances, MySQL for larger objects; DynamoDB keeps a B-tree per replica
In-memory hash + logLowest latency, data must fit RAMRedis-like stores

Dynamo made the engine pluggable: the distributed logic does not care what stores the bytes. Most interview answers pick an LSM tree because a KV store is usually write-heavy.

From your world

The commit log is a journal, like ext4's journal or a write-ahead log in a router's config database: append first, then apply. The memtable flush is like the page cache writing back dirty pages in big sequential batches. Compaction is garbage collection of old segments, the same job as a log-structured filesystem's cleaner.

SQL or NoSQL? It is a NoSQL store by definition. Choosing it in a bigger design means you accept "access by key only" and design your keys for your queries (see Choosing Storage).
