Deep dives

1. Conflicts: vector clocks vs last-write-wins

Because any replica can take a write during a partition, two clients can update the same key on different nodes. Now there are two versions and neither "wins" by itself. Dynamo tracks causality with vector clocks: a list of (node, counter) pairs. If every counter in version X is <= the matching counter in Y, X is an ancestor of Y and can be dropped. Otherwise they are concurrent siblings, and both are kept and returned to the client to merge.

  • Clock growth. Clocks grow with the number of coordinators. Dynamo truncated them: once a clock had 10 pairs, it dropped the oldest. Rarely a problem in practice.
  • How often do siblings happen? In a 24-hour sample of the shopping cart, 99.94% of requests saw exactly one version; 0.00057% saw two. Most divergence came from concurrent writers (often automated clients), not failures.
  • The merge cost. A union-merge of carts can resurrect deleted items ("I removed it and it came back"). Dynamo accepted this: losing an "add to cart" costs more than showing a removed item.
  • Last-write-wins (LWW). Cassandra keeps the version with the highest timestamp and treats each CQL row as an LWW-element-set CRDT, so changes to different columns do not conflict. Simple, no siblings, but concurrent writes to the same column silently lose one, and it depends on synced clocks.
  • CRDTs. Data types that merge automatically (counters, sets, maps). Riak offers them as eventually consistent data types.

2. Failure detection and membership: gossip

No central registry. Each node, every second, picks a random peer and exchanges its view of the ring (who owns which tokens, who is up). Information spreads like a rumour in O(log n) rounds. Seed nodes (well-known addresses) stop the cluster from splitting into islands. Failure is a local opinion: a node that stops answering is treated as down by the nodes that notice, and they route around it. Cassandra uses a phi accrual failure detector that outputs a suspicion level from heartbeat arrival times instead of a fixed timeout, and never removes a node from membership without an explicit decommission.

From your world

Gossip is like a link-state routing protocol flooding LSAs (OSPF), but lazier and randomized. Phi accrual is BFD with a dial instead of a fixed miss-count. Hinted handoff is store-and-forward: a neighbour buffers frames for a link that is down and forwards them when it comes back up.

Stop here for SDE-1. Ring + virtual nodes, N/R/W quorums, vector clocks vs last-write-wins and gossip membership are the interview-sufficient core. Deep dives 3-6 (Merkle repair, hot keys, Dynamo vs DynamoDB, tombstones) are SDE-2 depth: an SDE-1 candidate only needs to name them.

3. Permanent failures: Merkle-tree anti-entropy

Hints cover short outages. For long ones (or a lost hint), replicas must compare their data. Sending every key would be huge, so each node keeps a Merkle tree per key range: leaves are hashes of key buckets, parents are hashes of children. Two replicas compare roots; if equal, the range is identical. If not, they walk down only the branches that differ and sync just those keys.

There is also read repair: when a read sees a stale replica among its R replies, the coordinator writes the newest version back to it. Cheap, but it only fixes keys that are read.

4. Hot keys and hot partitions

Consistent hashing spreads keys, not traffic. One celebrity key can melt its N replicas. Discord saw this with Cassandra: messages partitioned by (channel, time bucket) meant a very busy channel hammered one partition, and quorum reads spread the latency pain cluster-wide. Their fixes: a data-service layer that coalesces identical concurrent reads into one query, and consistent-hash routing so requests for the same channel hit the same service instance. Other tools: a cache in front for hot reads (see Scaling Reads), splitting a hot key into sub-keys with a suffix for writes (see Scaling Writes), and DynamoDB-style adaptive capacity that moves throughput to hot partitions.

5. Leaderless (Dynamo) vs leader-per-partition (DynamoDB)

Here is the plot twist interviewers enjoy: Amazon's managed DynamoDB (2012) shares the name but not the core design. Per its 2022 USENIX ATC paper, each partition has a replication group spread across availability zones that uses Multi-Paxos (a consensus protocol: the replicas vote so that exactly one leader is agreed on, even if some replicas fail) to elect a leader. Only the leader serves writes and strongly consistent reads; any replica can serve eventually consistent reads. Why move away from leaderless? Customers wanted strong consistency and predictable latency more than they wanted "always writeable with siblings", and a managed service cannot ask every customer to write merge functions. The paper also shows that operations matter as much as algorithms: request routers cache partition metadata with about a 99.75% hit rate, and a cold cache could have sent 400x more load to the metadata service, so they built a separate cache service (MemDS) to avoid that failure mode.

6. Deletes and tombstones

You cannot just remove a key from one replica: anti-entropy would copy it back from another replica that still has it. So a delete writes a tombstone (a marker with a version). Tombstones are kept until every replica surely has them (Cassandra's gc_grace_seconds), then compaction drops them. Too many tombstones make reads slow; Discord's migration stalled on token ranges full of uncompacted tombstones until they compacted them.
