Architecture

Every node is the same (symmetric): there is no master. Any node can take a client request; it becomes the coordinator for that request. Inside, each node has six parts. Here is one node, one line per part, before we zoom into each:

Partitioning: the ring with virtual nodes

Read more about the ring itself in Distributed Building Blocks. Dynamo tried three token strategies and ended with strategy 3: split the ring into Q equal fixed partitions and give each node Q/S of them (S = the number of nodes). It balanced best and shrank membership metadata by three orders of magnitude, and moving a partition became "copy one file". Cassandra learned a similar lesson: version 2.x needed 256 random tokens per node to balance, and from 3.x a deterministic allocator balances with far fewer, because every extra token adds neighbours and makes repairs slower.

A write, step by step (N=3, W=2)

  1. Client sends put. To any node (or, better, straight to a replica using a partition-aware client: Dynamo measured client-driven coordination at 30.4 ms vs 68.9 ms server-driven at p99.9).
  2. Coordinator finds the preference list. Hash the key, walk the ring, take the first N healthy distinct nodes. It creates the new version (vector clock entry for itself incremented).
  3. Send to all N replicas in parallel. Each appends to its commit log and memtable.
  4. Reply after W acks. With W = 2 the client gets OK as soon as two replicas confirm. The third catches up a little later. Latency is set by the 2nd-fastest replica, not the slowest.
  5. A replica is down. A strict quorum would fail the write if fewer than W of the "home" replicas are up. Dynamo does not want that.
  6. Sloppy quorum + hinted handoff. The coordinator writes A's copy to the next healthy node D, tagged with a hint "this belongs to A". The write still reaches W nodes.
  7. Hand back. When gossip shows A is back, D pushes the hinted data to A and deletes its copy. If A never returns, Merkle-tree repair takes over.

Quorum math: R + W > N

Pick N copies. A write waits for W acks, a read waits for R replies. If R + W > N, every read set overlaps every write set in at least one node, so a read sees the latest acknowledged write (when the quorum is strict and there are no concurrent writes). Dynamo's common setting was (N, R, W) = (3, 2, 2).

SettingBehaviourDynamo use
N=3, R=2, W=2Balanced; overlap guaranteed; tolerates 1 slow/dead replica on each pathMost services
N=3, R=1, W=3Very fast reads, writes need every replica"High-performance read engine" (product catalog, promotions)
N=3, R=1, W=1Fastest, weakest; reads may be staleOnly for data where staleness is harmless
N=3, R=3, W=1Writes always succeed fast; reads slowRare

Trap: with a sloppy quorum, R + W > N no longer guarantees overlap, because the W writes may have gone to stand-in nodes outside the home set. Riak's docs show this: right after a failure, a fallback node can answer "not found" for R = 1. Riak offers PR/PW (primary-only quorums) to force real overlap. Say this in the interview; it is a favourite follow-up.
