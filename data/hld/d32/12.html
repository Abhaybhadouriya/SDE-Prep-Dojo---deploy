Quick quiz

With N = 3 and a strict quorum, which (R, W) pair guarantees that read and write sets overlap?

  1. R=1, W=2, since together they touch all three replicas
  2. R=1, W=1, since writes reach all 3 replicas eventually anyway
  3. R=2, W=2
  4. R=2, W=1, since a 2-replica read always sees the latest
Overlap needs R + W > N. 2 + 2 = 4 > 3, so at least one node is in both sets. R=1, W=2 gives 3, which is not greater than 3.

What is a hinted handoff?

  1. A stand-in keeps a write for a down replica and hands it back later
  2. Moving a partition leader to a healthier node after a failure
  3. Splitting a hot key into sub-keys and hinting clients to spread reads
  4. A gossip message hinting that a node is suspected down
The hint records the real owner so the data can be handed back.

Two versions have clocks [Sx,2][Sy,1] and [Sx,2][Sz,1]. What are they?

  1. The first is newer, because Sy sorts before Sz
  2. The second is newer, because Sz has the higher node ID
  3. They are equal, since both start with [Sx,2]
  4. Concurrent siblings; keep both
Neither clock is >= the other in every entry, so neither descends from the other.

Why do replicas compare Merkle trees instead of all keys?

  1. Merkle trees compress the keys so the full list fits in one packet
  2. Equal subtree hashes let them skip identical ranges
  3. It lets replicas skip gossip and talk to each other directly
  4. Merkle trees sign data so a corrupt replica is spotted and dropped
Only branches whose hashes differ are explored.

Why does a delete write a tombstone instead of removing the key?

  1. To save disk, since a tombstone is smaller than the value
  2. To speed up reads by caching the "not found" answer
  3. So TTL compaction can find and expire the key later
  4. Else repair copies the old value back from a replica that missed it
The tombstone is a newer version that wins over the old value during repair.

How does DynamoDB (the service) differ from the 2007 Dynamo design?

  1. A Multi-Paxos-elected leader per partition takes writes
  2. It keeps vector clocks per item and returns siblings to clients
  3. It drops replication and relies on disk snapshots for durability
  4. It uses a sloppy quorum with W=1 so writes are always available
Per the 2022 USENIX ATC paper, DynamoDB is leader-based, not leaderless.

What main benefit do virtual nodes give when a server dies?

  1. No data needs copying, because vnodes on one host share a disk
  2. Clients stop retrying, because the ring is rebuilt instantly
  3. Its load and rebuild work spread across many peers
  4. Its keys all move to one neighbour, which keeps repair simple
Many small ranges have many different neighbours.

Which storage engine suits a write-heavy KV node best?

  1. A plain sorted array, rewritten on each put for binary search
  2. LSM tree: commit log + memtable + SSTables
  3. A B-tree with in-place updates, so each key lives in one page
  4. An on-disk hash table with in-place overwrites, so no compaction
Writes become sequential appends; compaction cleans up later.

During a partition, a sloppy quorum accepts a W = 2 write on stand-in nodes. Does R + W > N still guarantee that a later read sees it?

  1. Yes, R + W > N always guarantees overlap, whichever nodes took it
  2. Yes, because hinted handoff copies the write home before any read
  3. No, because a sloppy quorum silently lowers W to 1
  4. No: the W acks may come from stand-ins outside the key's home N
Overlap needs both sets drawn from the same N home replicas. A sloppy quorum counts stand-ins, so a read of the home replicas can miss the write until the hint is handed back. That is why Dynamo is eventually consistent even with R + W > N.
