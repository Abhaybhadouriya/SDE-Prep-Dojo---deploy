Interview questions

These questions are frequently reported in SDE-1/SDE-2 loops. Company tags show where they are commonly reported, not a guarantee.

Explain the saga pattern. Why not two-phase commit?

A saga breaks a cross-service operation into local transactions. Each step commits in its own service and triggers the next; each has a compensating action. If a step fails, the earlier steps are undone by their compensations - for checkout: create the order as PENDING, reserve stock with a short hold, charge the card, then confirm. If the charge fails, release the stock and cancel the order. I put the charge last on purpose because it is the hardest step to undo; a refund is only needed if a step after it, like shipping, fails. I usually orchestrate it with a workflow engine so the state is visible, and publish events through an outbox. I avoid 2PC across services because it is blocking - if the coordinator dies after the prepare votes, every participant holds locks until it returns - and it ties the availability of all services together. The cost of a saga is that it is not isolated: other readers can see the "paid but not reserved" state, so I use explicit states like PENDING and make every compensation idempotent.

How to answer

Define it in one sentence, give the checkout example with one failure (and say why the charge is the pivot step that goes last), name orchestration vs choreography, say why not 2PC (blocking + coupling), and finish with the honest cost (no isolation).

Likely follow-ups
  • What if the compensation itself fails? (Retry with backoff, it must be idempotent; alert to a human after N tries.)
  • Orchestration or choreography for 6 steps? (Orchestration - easier to reason about.)
  • Where is 2PC still used? (Inside one database or one system, like Kafka transactions.)
What is the transactional outbox and why do we need it?

It fixes the dual-write problem. If a service writes to its database and then publishes to Kafka, a crash between the two leaves them disagreeing - a saved order nobody hears about. With an outbox, the service writes the business row and an event row into an outbox table in one local transaction, so both commit or neither does. A relay - typically Debezium reading the database's write-ahead log, or a poller - publishes outbox rows to Kafka. The relay is at-least-once, so consumers dedupe on the event ID.

How to answer

Start with the failure (draw the crash between two writes), then the one-transaction fix, then the relay, then the duplicate caveat.

Likely follow-ups
  • Poller vs CDC? (Poller is simple but adds DB load and latency; CDC reads the log with low latency.)
  • How do you keep ordering per order? (Use the order ID as the Kafka key.)
  • How do you clean the outbox table? (Delete or partition by time after publish.)
How would you make a payment API safe to retry?

With an idempotency key. The client generates one UUID per logical payment and sends it in an Idempotency-Key header on every retry. On the server, I insert the key into a table with a unique constraint before doing any work. If the insert succeeds, this request owns the payment: it charges the card and saves the response against the key. If the insert conflicts, it is a retry: I return the stored response, or 409 if the first attempt is still in progress. I also store a hash of the request body, so the same key with a different amount is rejected. Keys are read on the primary, kept for at least the retry window - Stripe documents 24 hours - and clients retry with exponential backoff and jitter.

How to answer

Explain why retries happen (lost reply), who makes the key, the unique-constraint trick, and the three outcomes (new, done, in progress).

Likely follow-ups
  • What if the server crashes after charging but before saving the response? (Record phases; on recovery, query the payment provider using the same reference before charging again.)
  • Why not SELECT then INSERT? (Race between concurrent retries.)
  • How does this relate to Kafka consumers? (Same idea, keyed on event ID.)
How does leader election work, and what happens if two nodes think they are leader?

In Raft, followers expect heartbeats from the leader. If one times out (randomised, so not everyone at once), it becomes a candidate for a new, higher term and asks for votes. Each node votes once per term and only for a candidate whose log is at least as complete as its own, so at most one candidate can get a majority in a term. That majority rule is what prevents split brain: in a partition, only the side with a majority can elect a leader or commit writes. A deposed leader that wakes up sees a higher term and steps down. When leadership is done with leases instead, a paused old leader can still try to write after its lease expired, so the storage must check a fencing token - an increasing number handed out with each lease - and reject older tokens.

How to answer

Timeout, term, votes, majority. Then the split-brain answer (majority + term), then leases and fencing. Mention etcd under Kubernetes and KRaft in Kafka as real uses.

Likely follow-ups
  • Why 5 nodes and not 4? (2f + 1; 4 tolerates only 1.)
  • What happens to Kubernetes if etcd loses quorum? (No writes: no new pods or changes; running pods keep running.)
  • Is a Redis lock safe for correctness? (Only with fencing; otherwise treat it as an efficiency lock.)
What is a Bloom filter, and where would you use one in a design?

A Bloom filter is a bit array plus k hash functions that answers "definitely not present" or "maybe present". Adding sets k bits; checking reads them, and any zero means a guaranteed no. False positives happen, false negatives do not. About 10 bits per item gives about 1% false positives, so 100 million items fit in roughly 120 MB. I would use one in a web crawler to skip URLs I have already fetched, in front of a database to avoid disk lookups for keys that do not exist (Cassandra keeps one per SSTable, an immutable sorted file on disk used by LSM-tree stores), or to check if a username or short-URL alias is taken before querying the main store.

How to answer

Mechanism, the one-sided error, the sizing rule, then two concrete uses tied to the design you are discussing.

Likely follow-ups
  • How do you delete? (Counting Bloom filter, or rebuild periodically.)
  • What happens when it fills past its planned size? (False-positive rate climbs; resize or use a scalable Bloom filter.)
How would you find the top 10 trending hashtags over the last 5 minutes at Twitter scale?

Exact counting of every hashtag in memory is too expensive across millions of distinct tags, so I would use a count-min sketch per one-minute window on each ingest server, plus a small min-heap of the current top K. Sketches merge by adding cells, so an aggregator combines the per-server sketches and the last five one-minute windows. The sketch only over-counts, and the error is relative to total traffic, so it is excellent for heavy hitters and bad for rare tags - which is fine here. Events flow through Kafka keyed by hashtag, a stream processor maintains the windows, and the top-K list is served from a cache. If exact numbers are needed later, a batch job recounts from the raw log.

How to answer

Say why exact is too costly, then sketch + heap + windows + merge, then the error trade-off, then where Kafka and the batch path fit.

Likely follow-ups
  • How do you handle one very hot tag overloading one partition? (Pre-aggregate locally before sending.)
  • Sliding vs tumbling windows? (Tumbling per minute, then sum the last five.)
Design a distributed rate limiter for an API that runs on 50 servers.

First I pin the rule: "each API key gets 100 requests per second with bursts up to 200". A counter inside each server only sees about 1/50 of a key's traffic, so the state goes in a shared fast store: Redis. I use a token bucket per key, stored as a small hash (tokens, last refill time). The refill-and-take must be atomic, so it runs as one Lua script, which Redis executes without interleaving; the key gets a TTL so idle keys disappear. Over the limit, the API returns 429 Too Many Requests with a Retry-After header, plus X-RateLimit-Remaining so good clients can slow down. Cost: one Redis round trip per request, about half a millisecond in the same data centre. For scale I shard Redis by key (Redis Cluster). If Redis is unreachable I fail open: allow the request, alert, and apply a rough local limit of 100/50 per server, because a limiter outage must not become an API outage.

How to answer

Rule first, then why local counters fail, then token bucket + atomic Lua in Redis, the 429 response, and finish with the failure mode (fail open) and the latency cost.

Likely follow-ups
  • Token bucket or sliding window? (Token bucket allows bursts; sliding-window counter is closer to "exactly 100 per minute".)
  • Can you avoid a Redis call on every request? (Each server takes a batch of tokens and spends them locally; cheaper, a little less exact.)
  • Multi-region? (Separate limits per region, or accept that a global limit is approximate.)
  • How does this map to QoS? (Capacity = burst size, refill = committed rate, 429 = the drop action.)
Geohash or quadtree for finding nearby Uber drivers?

Drivers send their position every few seconds, so the index must be cheap to update, not just to query. With a geohash, an update is "compute a short string, write it": I keep driver positions in Redis (its GEO commands store a geohash-based score in a sorted set) and query the rider's cell plus its 8 neighbours, then filter by real distance. A 6-character cell is about 1.2 km across, so for a 2 km search I use 5 or 6 characters and the neighbours. The weakness is that cells are a fixed size: a downtown cell can hold thousands of drivers while a rural one holds none. A quadtree adapts to density by splitting crowded squares, which is great for static places like restaurants on Yelp, but moving points force constant splits and merges, so it is usually an in-memory structure rebuilt periodically. My pick for drivers: geohash (or Uber's own H3 hexagons) in Redis; for static businesses, a quadtree or a geo index in the database.

How to answer

Start from the access pattern (frequent updates, radius queries), compare update cost and density handling, name the border trap, and pick per data type.

Likely follow-ups
  • How many updates per second? (1M active drivers / 4 s = 250k writes/s: shard the Redis by city or cell.)
  • Why does Uber use hexagons? (Every neighbour is the same distance away, which suits surge pricing per cell.)
How would you tune N, W and R for a shopping cart, and for a bank balance?

Shopping cart: availability beats consistency - a customer who cannot add to the cart is a lost sale. I use N = 3 with W = 1 or 2 and R = 1, plus sloppy quorum and hinted handoff so writes are accepted even while a replica is down. Conflicting versions are merged by taking the union of the items, the way the Dynamo paper describes; the known side effect is that a deleted item can occasionally reappear, which the business accepted. Bank balance: I would not use a leaderless quorum for the decrement at all. Even W + R > N is not linearizable when two writers race, so two withdrawals could both succeed. A balance needs a single leader or consensus with real transactions: a relational primary with a synchronous replica, or Spanner. If I were stuck on Cassandra, I would use its lightweight transactions (compare-and-set built on Paxos) for that one table and accept the extra round trips.

How to answer

Ask what failure costs the business in each case, map that to W and R, and show you know where quorums stop helping (concurrent writes).

Likely follow-ups
  • What does W = 3, R = 1 give you? (Fast reads; a write fails if any replica is down.)
  • What is read repair? (The coordinator writes the newest version back to a stale replica it read from.)
Your Kafka consumer cannot keep up with the producer. What are your options?

First I measure: is lag rising steadily (drain slower than fill) or just a spike that is draining? Then I turn lag into time - lag of 1.2M messages at 2,000/s consumed is 10 minutes behind - and compare it with the topic's retention, because lag older than retention means lost data. Options, in the order I'd try them: speed up each consumer (batch database writes, async I/O, remove a slow call); scale out by adding consumers up to the partition count, automatically with KEDA on lag; add partitions if consumers are already at the partition count, knowing that changes which partition a key maps to; shed or defer low-priority events to a separate topic; and push back on the producer - block, or return 429 at the API - if the backlog would otherwise exceed retention. Kafka already gives me the "buffer durably" option, so a short spike just becomes lag on disk.

How to answer

Diagnose (trend, lag in time vs retention), then name the five moves: speed up, scale out, add partitions, shed, push back.

Likely follow-ups
  • Why not just 200 consumers? (Extra consumers beyond the partition count sit idle.)
  • Processing is slow because of an external API. Now what? (Concurrency inside the consumer with per-key ordering, or a bounded worker pool.)
Strong or eventual consistency for a like count, and for a cinema seat?

Like count: eventual. If one phone shows 1,203 and another 1,205 for a few seconds, nobody is harmed, and eventual consistency lets me count with cheap, fast writes (even a count-min sketch or batched counters). I'd add read-your-writes for the person who liked, so their own heart turns red at once. Seat: strong. Two people must never both get seat F12, so the final "book this seat" must be linearizable: a conditional update on the primary (UPDATE seats SET held_by = ? WHERE id = ? AND held_by IS NULL) or a short hold with a TTL. The seat map people browse can still be eventual and slightly stale, because I re-check at purchase time. The cost of strong consistency is latency and lower availability during a partition, and I only pay it on the one write that needs it.

How to answer

Ask what a wrong answer costs. Pick per operation, not per system, and say where the cheap guarantee (read-your-writes) is enough.

Likely follow-ups
  • What happens in CAP terms if the seat database is partitioned? (Refuse the booking: choose C.)
  • How do you show an exact like count on a celebrity post? (You usually don't; show "1.2M" from an approximate counter.)
How does a distributed system decide that a node is dead?

It cannot know for sure; it can only stop hearing from it. Each node sends heartbeats, and a monitor declares it dead after a timeout. The timeout is a trade-off: short means fast failover but false alarms during a GC pause or a network blip, which cause needless failovers or rebalances; long means fewer false alarms but a longer outage when a node really dies. Real examples: a Kubernetes node is marked NotReady after a 50-second grace period and its pods are evicted after a further 300 seconds by default; a Kafka consumer is removed from its group after session.timeout.ms, 45 seconds by default. Cassandra uses a phi-accrual detector, which turns the history of heartbeat gaps into a suspicion level instead of a yes/no timeout, and spreads membership by gossip. Because a slow node and a dead node look the same, the failover must be safe even if the "dead" node comes back: fencing tokens or a majority vote.

How to answer

Heartbeat + timeout, the false-positive vs detection-speed trade-off with one real number, then phi-accrual and gossip, and close with "make the failover safe because you can be wrong".

Likely follow-ups
  • Why not a 1-second timeout everywhere? (GC pauses and noisy networks would cause constant failovers.)
  • How does gossip scale to 1,000 nodes? (Each node talks to a few random peers per second; news spreads in about log N rounds.)

Scenario: customers are charged twice

Support reports a few hundred double charges after a deploy. The payment API already "has idempotency".

Weak answer: "Add a check in code: if a payment exists for this order, skip it."

Strong answer: check how keys are generated - a new client release may create a key per retry instead of per payment. Check the server: is the dedupe a SELECT-then-INSERT race, is it reading from a lagging replica, did the key TTL get shorter than the client's retry window? Check webhook and Kafka consumers for duplicates without an inbox. Fix with a unique constraint on the key, reads on the primary, one key per logical payment, and reconcile the affected charges with the provider and refund them.

Likely follow-ups
  • How do you prove the fix works? (Load test with injected reply loss and concurrent retries.)

60-second answers

"Strong vs eventual consistency?" "Strong means every read sees the latest committed write, as if there were one copy - I need it for money, stock counts and bookings, and I pay in latency and in availability during partitions. Eventual means copies converge later - fine for likes, views and feeds. In between, read-your-writes is the cheap guarantee that fixes most user complaints: after you write, your own reads go to the leader for a few seconds."

"What is a quorum?" "With N replicas, a write waits for W acknowledgements and a read asks R replicas. If W + R > N, every read overlaps at least one replica with the latest write. N=3, W=2, R=2 survives one dead replica on both paths. Lower W or R buys speed and availability at the cost of stale reads."

"How do you protect a service from overload?" "At the edge, a token-bucket rate limiter per API key in Redis, returning 429 with Retry-After, failing open. Inside, bounded queues and backpressure: block, reject fast, or shed low-priority work, and put Kafka between stages so spikes become lag on disk instead of out-of-memory. Then autoscale the slow stage on lag."
