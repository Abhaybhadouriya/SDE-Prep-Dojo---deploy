Beyond the ring: other ways to map keys to servers SDE-2 bonus

Consistent hashing with a ring and virtual nodes is the default answer, and it is enough for SDE-1. It has two weak spots: it needs many virtual nodes (memory, lookup time) to spread keys evenly, and a single very popular key or an unlucky range can still overload one server. Four alternatives fix one weak spot each. You only need to know what each one is, why it exists and where it is used.

TechniqueHow it worksWhy it existsCostWhere it is used
Rendezvous hashing (highest random weight)For a key, compute a score hash(key, server) for every server and pick the highest. For 3 replicas, take the top 3.No ring and no virtual nodes, yet keys spread evenly; removing a server moves only that server's keysEach lookup touches all N servers (fine for tens, slow for thousands)Proxy-cache arrays (Microsoft's CARP), picking replicas in some storage and cache clients
Jump consistent hash (Lamping and Veach, Google, 2014)A few lines of arithmetic map a key to a bucket number 0..n-1 with no stored statePerfectly even, almost no memory, very fastBuckets must be numbered; you can only add or remove at the end, not remove an arbitrary serverSharding data into numbered shards, where each shard is itself replicated
Consistent hashing with bounded loads (Google, 2016)The ring as usual, but each server has a cap of about (1 + epsilon) times the average load; if the owner is full, the key moves clockwise to the next server with roomStops one hot range from overloading a server while keeping most keys in placeA little more movement and a shared view of current loadVimeo's video-cache load balancing, added to HAProxy as hash-balance-factor
Maglev hashing (Google, 2016)Each backend fills slots of a fixed-size lookup table (for example 65,537 entries) in its own pseudo-random order; a packet's flow hash indexes the tableO(1) lookup per packet, very even spread, small disruption when a backend changesRebuild the table on every change; slightly more disruption than a ringGoogle's Maglev L4 load balancer; also Facebook's Katran and Cilium

From your world

Maglev's lookup table is resilient ECMP hashing done in software: a fixed bucket table where each next hop owns a share of the buckets, so a link failure only re-homes the flows in its buckets. Bounded loads is like ECMP with a utilisation check that steers new flows off a hot link. Where this breaks: a switch rebuilds its bucket table in hardware in microseconds; a software load balancer fleet must agree on the same table on every machine, or a flow's packets land on different backends.

For how a real key-value store combines these choices, see Distributed Key-Value Store (Dynamo).
