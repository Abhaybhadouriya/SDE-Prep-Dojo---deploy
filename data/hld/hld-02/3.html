Idempotency keys: make retries safe

Explain like I'm 5

At the fair you drop a numbered raffle ticket in the box. If you drop the same ticket number twice by accident, you are still in the draw once. The number makes the second drop harmless.

An operation is idempotent if doing it twice has the same effect as doing it once. "Set balance to 500" is idempotent; "add 100 to balance" is not. Networks force retries: the client sends "pay Rs 999", the server charges the card, and the reply is lost. The client cannot tell "never arrived" from "done, reply lost", so it retries. Without protection, the user pays twice.

The fix: the client generates a unique idempotency key (a UUID) once per logical operation and sends it with every retry of that operation. The server stores the key with the result. A repeat with the same key gets the saved result back, and the card is not charged again. Stripe's API works exactly like this, using an Idempotency-Key header.

How the server implements it

The key insight is to let the database do the duplicate check with a unique constraint, not a "SELECT then INSERT" (two concurrent retries could both pass the SELECT).

CREATE TABLE idempotency_keys (
  key           text PRIMARY KEY,
  user_id       bigint NOT NULL,
  request_hash  text   NOT NULL,          -- same key + different body = client bug
  status        text   NOT NULL,          -- STARTED | DONE
  response_code int,
  response_body jsonb,
  created_at    timestamptz NOT NULL DEFAULT now()
);

-- Step 1: claim the key. Exactly one concurrent request wins.
INSERT INTO idempotency_keys (key, user_id, request_hash, status)
VALUES ('7f3a9c2e-5b1d-4d0e-9a77-1e2f3a4b5c6d', 42, 'sha256:ab12...', 'STARTED')
ON CONFLICT (key) DO NOTHING
RETURNING key;
-- 1 row back  -> we own it: charge the card, then UPDATE status='DONE', save response
-- 0 rows back -> already seen: read the row and return the saved response
--                (or 409 Conflict if it is still STARTED, or 422 if request_hash differs)

The status codes follow the IETF httpapi Idempotency-Key draft. Stripe itself returns 400 (idempotency_error) when a key is reused with different parameters.

curl -X POST https://api.example.com/v1/payments \
  -H "Idempotency-Key: 7f3a9c2e-5b1d-4d0e-9a77-1e2f3a4b5c6d" \
  -H "Content-Type: application/json" \
  -d '{"amount_paise": 99900, "currency": "INR", "order_id": "ord_81f2"}'
  • Who makes the key? The client, once per user action ("pay for order 81f2"), and it reuses it for every retry. If the client makes a new key on each retry, the protection is gone - a very common production bug.
  • How long to keep it? Long enough to cover all retries. Stripe's docs say keys can be removed after 24 hours.
  • Read from the primary. Airbnb's payments team reads and writes idempotency records on the primary database, never a lagging replica, or a retry might not see the first attempt.
  • Retries need backoff with jitter (wait 1 s, 2 s, 4 s ... plus a random extra), or every client retries at the same instant and creates a thundering herd. See the AWS Builders' Library article in Resources.
  • Consumers too. Kafka consumers are at-least-once by default, so they see duplicates after a rebalance or crash. Use the event ID as the key in an inbox table, or write with an upsert. Details in Delivery Semantics & Exactly-Once.

From your world

An idempotency key is a TCP sequence number at the application level. When a segment is retransmitted with the same sequence number, the receiver's TCP stack drops the duplicate and the application reads the bytes once. Where this breaks: TCP state lives for one connection; an idempotency key must survive across connections, server restarts and even different servers, so it lives in a shared database.
