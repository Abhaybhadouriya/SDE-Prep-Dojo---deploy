Count-min sketch: "roughly how many?" in fixed memory

A Bloom filter answers "seen it?". A count-min sketch answers "how many times?" - for millions of different items, in a small, fixed amount of memory. It is a grid of counters with d rows and w columns, and one hash function per row.

  • Add an item: in every row, hash the item to a column and add 1 to that counter.
  • Estimate an item: look at its counter in every row and take the minimum.

Why the minimum? Other items can collide into the same counter and push it up, but nothing ever pushes it down. So every counter is an over-estimate, and the smallest one is the closest to the truth. The estimate is never too low, only sometimes too high.

Sizing: with error factor epsilon and failure probability delta, use w = ceil(e / epsilon) columns and d = ceil(ln(1/delta)) rows. Here e is Euler's number (about 2.718), epsilon is the error you accept as a fraction of the total count, and delta is the chance of missing that bound. The estimate is within epsilon x (total of all counts) of the truth with probability 1 - delta. With epsilon = 0.001 and delta = 0.01 you get w = 2,719 and d = 5: about 13,600 counters, roughly 54 KB with 4-byte counters, however many distinct items you see.

import hashlib, math

class CountMinSketch:
    def __init__(self, epsilon, delta):
        self.w = math.ceil(math.e / epsilon)      # columns
        self.d = math.ceil(math.log(1 / delta))   # rows (hash functions)
        self.table = [[0] * self.w for _ in range(self.d)]

    def _col(self, row, item):
        h = hashlib.blake2b(f"{row}:{item}".encode(), digest_size=8).digest()
        return int.from_bytes(h, "big") % self.w

    def add(self, item, count=1):
        for r in range(self.d):
            self.table[r][self._col(r, item)] += count

    def estimate(self, item):
        return min(self.table[r][self._col(r, item)] for r in range(self.d))

cms = CountMinSketch(epsilon=0.001, delta=0.01)
print("width:", cms.w, "depth:", cms.d, "counters:", cms.w * cms.d)
cms.add("#ipl", 50_000)
cms.add("#diwali", 20_000)
for i in range(200_000):
    cms.add(f"#tag{i % 40_000}")        # long tail: 40k tags x 5 each
print("#ipl    ~", cms.estimate("#ipl"))
print("#diwali ~", cms.estimate("#diwali"))
print("#tag7   ~", cms.estimate("#tag7"), "(true 5)")
$ python cms.py
width: 2719 depth: 5 counters: 13595
#ipl    ~ 50035
#diwali ~ 20045
#tag7   ~ 55 (true 5)

Look closely at that real output. The big items (#ipl, #diwali) are within 0.1% - great for "what is trending". The tiny item (#tag7) is 11 times too high, because the error is relative to the total count (270,000 here, so the bound is about 270), not to the item. Count-min is for finding heavy hitters, not for exact small counts. In a trending-topics or top-K design you pair it with a small min-heap of the current top K, and you keep one sketch per time window (say, per minute) so old counts age out. Tip: sketches can be merged by adding the grids cell by cell. So every server keeps its own sketch for one minute, and an aggregator adds them up. That is what makes them fit streaming systems so well.
