Quorums: how many copies must say yes?

Explain like I'm 5

Three teachers each keep a copy of the class marks. When a mark changes, at least two teachers must write it down. When you ask for a mark, you ask at least two teachers. Because two writers and two askers out of three must share at least one teacher, you always reach someone who has the newest mark.

In a leaderless database such as Cassandra or the original Amazon Dynamo design, each piece of data is stored on N replicas. A write is "successful" when W replicas confirm it (this count is a quorum). A read asks R replicas and takes the newest version. The rule to remember:

W + R > Nread set and write set overlap
N=3, W=2, R=2the Dynamo paper's example

Do not mix this up with the majority rule of consensus systems such as Raft and etcd (2f + 1 nodes survive f failures), covered in Leader election later on this page. Raft elects one leader that orders every write, and a write commits when a majority stores it. A Dynamo-style W/R quorum has no leader: any node can coordinate a request, W and R can be tuned per request, and two concurrent writes can both "succeed" and must be merged later.

What actually happens (who does what)

  1. Client to any node. The client (or its driver) sends the write to any node in the cluster. That node becomes the coordinator for this one request. In Cassandra every node can coordinate.
  2. Coordinator finds the replicas. It hashes the partition key onto the consistent-hash ring and picks the N nodes that own that range.
  3. Send to all N, wait for W. It sends the write to all N replicas at once and replies "OK" to the client as soon as W of them acknowledge. The others still get the write; nobody waits for them.
  4. Hints for replicas that are down. If a replica does not answer, the coordinator stores a hint ("this write belongs to node C") and replays it when C comes back (hinted handoff).
  5. Reads. For a read, the coordinator asks R replicas, compares the versions (timestamps) and returns the newest. If one replica returned an old version, the coordinator writes the newest value back to it. That fix-up is called read repair.
  6. In the background. A scheduled repair job compares replicas range by range with Merkle trees (below) and copies over anything that both reads and hints missed.

Turning the knobs changes the trade-off:

Setting (N=3)Good atCost
W=2, R=2Balanced; survives one slow or dead replica on both reads and writesEach request waits for the 2nd fastest replica
W=3, R=1Very fast readsA write fails if any single replica is down
W=1, R=3Very fast writesReads are slow and fail if any replica is down
W=1, R=1Fastest, most availableW + R = 2, not > 3, so reads can be stale (eventual)

Cassandra exposes this as a consistency level per query: ONE, QUORUM, ALL, plus LOCAL_QUORUM to count only replicas in the local data centre (so a write does not wait for another continent).

-- cqlsh: choose the consistency level per session, then run queries
CONSISTENCY QUORUM;
INSERT INTO shop.carts (user_id, item_id, qty) VALUES (42, 'sku-9', 2);
SELECT qty FROM shop.carts WHERE user_id = 42 AND item_id = 'sku-9';
cqlsh> CONSISTENCY QUORUM;
Consistency level set to QUORUM.

Two honest footnotes

  • Sloppy quorum and hinted handoff. Dynamo keeps accepting writes during a failure by writing to a healthy "stand-in" node with a note (a hint) saying "this belongs to node C". When C comes back, the hint is handed over. This favours availability, but it means W + R > N no longer guarantees overlap during the failure.
  • Quorum is not linearizable on its own. Two concurrent writers can both "win" on different replicas, so you need a rule to pick a winner: last-write-wins (LWW: the newest timestamp wins; simple, can lose data) or version vectors (a small counter per replica that shows whether two versions are "one after the other" or "at the same time"; the store keeps both and the app merges them). Background repair slowly fixes replicas that missed writes: read repair (described above) and Merkle-tree anti-entropy. A Merkle tree is a tree of hashes over key ranges; two replicas compare the root hash, then only the branches that differ, so they find the few differing ranges without sending all the data.
