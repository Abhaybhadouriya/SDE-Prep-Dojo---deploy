Rate limiting algorithms

Explain like I'm 5

A cookie jar holds at most 5 cookies, and one new cookie drops in every minute. You may eat a cookie only if one is in the jar. You can eat 5 quickly at a party (a burst), but after that you get only one a minute.

A rate limiter caps how many requests a caller (a user, an API key, an IP) may make in a time period. It protects the service from one noisy caller, from bots and from accidental retry storms. When a caller is over the limit, the server replies HTTP 429 Too Many Requests (defined in RFC 6585), ideally with a Retry-After header.

Run the token bucket in your head with this tiny simulation (capacity 5, 1 token per second, 8 requests arrive at once, then one per second):

class TokenBucket:
    def __init__(self, capacity, refill_per_sec):
        self.capacity = capacity
        self.rate = refill_per_sec
        self.tokens = capacity
        self.last = 0.0
    def allow(self, now):
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

b = TokenBucket(capacity=5, refill_per_sec=1)
for t in [0]*8 + [1, 2, 3]:
    print(f"t={t}s allowed={b.allow(t)} tokens_left={b.tokens:.0f}")

Distributed: many servers, one limit

With 50 API servers behind a load balancer, each server's local bucket only sees 1/50 of a user's traffic. So the counters go in a shared, fast store - usually Redis. The read-refill-decrement must be atomic, or two servers read "1 token left" at the same moment and both allow. Redis runs a Lua script atomically, so the whole check is one step:

-- KEYS[1] = bucket key, ARGV = capacity, refill_per_sec, now_ms
local cap  = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now  = tonumber(ARGV[3])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return allowed

Two production lessons from Stripe's post on their rate limiters: fail open (if Redis is down, let requests through and alert, rather than taking the whole API down), and dark-launch new limits (log "would have blocked" first). The full design is in Distributed Rate Limiter.

From your world

This is the token-bucket policer from QoS. Capacity is the committed burst size (CBS), refill rate is the committed information rate (CIR), and a 429 is a "drop" action for exceeding traffic. The leaky bucket is a shaper draining a queue at line rate. You already know how to pick these numbers. Where this breaks: a policer runs on one ASIC with one counter in hardware; a web rate limiter shares its counter across many servers over the network, so it adds a Redis round trip and must decide what to do when that store is unreachable.
