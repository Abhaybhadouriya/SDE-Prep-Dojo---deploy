Failure detection: when is a node "dead"?

Explain like I'm 5

Your friend promised to wave from her window every minute. If she stops waving, is she ill, or just busy tying her shoe? You cannot tell from across the street. If you wait two minutes before calling her mum, you sometimes panic for nothing. If you wait an hour, you are slow to help when something is really wrong.

Every block on this page (leader election, quorums, consumer groups) needs to know which nodes are alive. Over a network you can never know a remote node has crashed; you only know you have not heard from it. A failure detector (built on heartbeats) turns "silence for a while" into "suspected dead".

Heartbeats and timeouts

Each node sends a small heartbeat message at a fixed interval. A monitor (a leader, a controller, or every peer) declares the node dead when no heartbeat arrives within the timeout. The timeout is the whole design decision:

Short timeout
  • Fast failover when a node really dies
  • Less time with a leaderless partition or stuck requests
  • But: false positives during GC pauses, CPU starvation or a brief network blip, each causing a needless failover or rebalance
Long timeout
  • Rides through pauses and blips
  • Fewer flapping failovers
  • But: a real crash is noticed late, so requests to that node fail or wait for the whole timeout

Smarter detectors: phi-accrual and gossip

  • Phi-accrual detector. Instead of a fixed "dead after X seconds", the detector remembers how far apart recent heartbeats arrived and computes a suspicion level (phi) that grows the longer a heartbeat is overdue compared with that history. On a jittery network the normal gaps are wider, so it waits longer before suspecting anyone; on a quiet network it suspects sooner. Cassandra uses one and convicts a node when phi passes a threshold (phi_convict_threshold, default 8).
  • Gossip membership. With 1,000 nodes, everyone heartbeating everyone is a million messages per interval. With gossip, each node, about once a second, picks a random peer and swaps what it knows: its own heartbeat counter and the latest counters it has heard for every other node. News spreads like a rumour, reaching everyone in about log N rounds. Cassandra and the Dynamo design gossip once per second; HashiCorp's Serf/Consul and Uber's Ringpop use the SWIM gossip protocol.

Notice the pattern: the closer to the data path (Raft), the faster the detector; the more expensive a false alarm (moving every pod off a node), the longer the wait. Kubernetes deliberately waits minutes, because evicting a healthy node's pods is a big, disruptive action.

From your world

This is BFD and the OSPF hello/dead timers. A BFD session with a 50 ms interval and a multiplier of 3 declares the neighbour down after 150 ms; OSPF on a broadcast link uses a 10 s hello and a 40 s dead interval. A Kafka session.timeout.ms is a dead interval; the Kubernetes 300 s eviction delay is a hold-down timer to stop flapping. Where this breaks: BFD usually runs in hardware or a high-priority process, so the sender keeps its rhythm. In a JVM or Go service the heartbeat thread stops during a stop-the-world garbage-collection pause, so a perfectly healthy node looks dead - and a network partition looks exactly like a crash. That is why detection is always paired with fencing or a majority vote.

Say it like this: "We can't tell slow from dead, so the timeout is a trade-off between detection speed and false failovers. I'd set it above the worst normal GC pause, use something adaptive like phi-accrual where the platform has it, and make the failover itself safe with fencing, because the detector will sometimes be wrong."
