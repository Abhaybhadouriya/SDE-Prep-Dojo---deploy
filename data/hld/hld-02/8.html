Geohash and quadtrees: "what is near me?"

Explain like I'm 5

Draw a map and cut it into 32 squares, and give each square a letter. Cut each square into 32 smaller squares and add a second letter. Keep going. Now every tiny spot has a "name" like tdr1v. Two spots whose names start the same way are usually close together - like houses on the same street sharing the start of their address.

"Find drivers within 2 km" is hard for a normal database index, because an index sorts by one number but a location is two (latitude and longitude). Geo indexes turn 2-D space into something a normal index can search.

Geohash

A geohash repeatedly halves the world, alternating longitude and latitude, writing 1 for "upper half" and 0 for "lower half". The bits are interleaved and written in base-32 text. Longer string = smaller cell. Roughly (from the Wikipedia precision table): 5 characters is about +-2.4 km, 6 is about +-0.61 km, 7 is about +-76 m.

$ python geo.py
MG Road      tdr1vfp
Indiranagar  tdr1yf8
Mumbai       te7ud2e

(Computed with a 15-line encoder while writing this page.) Two Bengaluru spots about 4 km apart share the prefix tdr1; Mumbai starts differently. So "nearby" becomes "same prefix" - a plain string index can do WHERE geohash LIKE 'tdr1v%'.

You do not need to write this yourself. Redis stores locations in a sorted set using a geohash-based score:

127.0.0.1:6379> GEOADD drivers 77.6066 12.9756 driver:17 77.6408 12.9784 driver:42
(integer) 2
127.0.0.1:6379> GEOSEARCH drivers FROMLONLAT 77.6100 12.9760 BYRADIUS 2 km ASC WITHDIST
1) 1) "driver:17"
   2) "0.3712"

Only driver 17 is within 2 km (about 0.37 km away); driver 42 is about 3.3 km away, so it is left out. Note the order: Redis takes longitude first, then latitude.

Quadtree

A quadtree starts with one square for the whole map. When a square holds too many points (say more than 100), it splits into 4 children. Dense cities end up with many tiny squares; deserts stay as one big square. Searching walks down the tree to the small squares near you. It adapts to density, which a fixed geohash length does not, but it usually lives in memory and must be rebuilt or updated as points move.

IndexIdeaBest forWatch out
GeohashFixed grid, string prefixSimple, works in any DB or RedisBorder cells; fixed size does not adapt to density
QuadtreeSplit a square into 4 when fullUneven density (city vs desert)Usually in memory; updates for moving points
Google S2Cube projected on sphere, cells ordered along a Hilbert curve (a line that visits every cell so that cells close on the line are close in space)Accurate cells on a globeMore complex library

From your world

A geohash prefix is an IP prefix for space. Longer prefix = smaller area, just as a /28 is smaller than a /24, and "find nearby" is longest-prefix match. The border gotcha is the same as two adjacent addresses that sit on opposite sides of a /24 boundary: numerically close, different prefix. Where this breaks: a router only needs the single longest match; a proximity search needs every cell around you, so you query several prefixes.

For moving objects (drivers sending GPS every few seconds), keep locations in memory (Redis), not in the main database. Full designs: Uber, Yelp, and the deeper Geospatial, Text & Prefix Indexes page and Pattern: Geo & Proximity.
