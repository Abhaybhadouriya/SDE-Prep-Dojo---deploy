Architecture: the first second of the sale

  1. CDN. The product page, images and countdown are static files on the CDN, pre-warmed before the sale. The page reads the time from the server (not the phone clock) so nobody's button opens early. Most of the 1.5M requests per second end here.
  2. Waiting room. At T0, clicks go to a waiting room at the edge. Each user gets a signed token with their arrival time. The room admits users at the rate the backend can handle, oldest first, and everyone else sees a cheap, cached "you are in the queue" page that polls with jitter.
  3. Gateway. Admitted users present a short-lived admission token. The gateway checks it, applies per-user and per-device rate limits, and sends suspicious traffic to a challenge. No token, no entry: bots that skip the room are dropped here.
  4. Reserve. The reservation service picks the user's stock bucket and runs a Lua script on that Redis shard: "if this user has not won and stock > 0, decrement and remember the user". It is one atomic step inside Redis. No database is touched yet.
  5. Record and reply. On success, the service writes a reservation.created event to Kafka (with acks=all) and only then replies "201: you got it, pay by 12:10". The user's experience is now fast and final.
  6. Drain to the database. An order-writer consumer group reads the topic and inserts reservations and pending orders into SQL at a controlled rate, idempotently by reservationId. Kafka is the shock absorber between a burst of seconds and a database that likes a steady pace.
  7. Expire. If a user does not pay by pay_by, the expiry worker marks the reservation EXPIRED (a conditional update from HELD) and INCRs the stock back into its bucket, so a later user can win it.
  8. Sold out. When all buckets reach 0, the service sets the sold-out flag. The CDN and waiting room pick it up and answer "sold out" themselves, so millions of people stop polling. If expiries return stock, the flag is cleared and a second wave is admitted from the queue.

The whiteboard version: CDN -> Waiting room -> Gateway -> Reservation svc (+ Redis stock) -> Kafka -> Order writer -> SQL. Draw the funnel shape around it, and write the per-layer request rate next to each box.

From your world

Flipkart's own BBD 2015 memoir splits the system into a user path (very high QPS: browsing, the product page) and an order path (promise, order management, fulfilment), where every single order is treated as top priority. That is exactly the data plane vs control plane split you know from routers: protect the precious, low-volume path from the flood on the high-volume one. Where it breaks: on a router the control plane is protected by hardware (CoPP, separate CPU queues); here both paths share CDNs, gateways and sometimes databases, so the separation exists only if you build it: separate clusters, separate rate limits and separate capacity.
