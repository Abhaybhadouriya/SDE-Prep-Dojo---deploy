Common mistakes: decrementing stock in the database for every click; "add more servers" with no admission control; returning errors that trigger refreshes; a non-atomic GET-then-DECR in Redis; trusting Redis as the only record; forgetting stock must come back on unpaid reservations; relying on autoscaling; running the sale on the same database shard as the rest of the shop.

Why can't we just decrement the stock row in the database?

The conditional UPDATE is correct, but every buyer targets the same row. The database serialises them on one row lock, so throughput is capped by how fast one row can be locked, updated, committed and unlocked. Waiting transactions hold connections, pools fill up, and because the database is shared, the whole shop slows down. Shopify's Kylie Cosmetics sale took down every store on the shared shard. So I keep the database out of the hot path: an atomic counter in Redis behind a waiting room, with the database written asynchronously.

How to answer

Agree the SQL is correct first (do not claim it oversells), then explain the contention and blast radius. That shows you know the difference between correctness and capacity.

Likely follow-ups
  • At what rate would the DB row be good enough?
  • What about SELECT ... FOR UPDATE SKIP LOCKED with one row per unit?
Show me the exact Redis logic. Why Lua and not GET then DECR?

GET then DECR from the application is two round trips, and another client can run between them, so two users can both see 1. DECR alone is atomic, but then you need "if the result is below 0, INCR back", which works but briefly shows negative stock, and it cannot also enforce one-per-user. A Lua script runs atomically on the Redis thread: check the buyers set, check stock, DECRBY, SADD, return what is left. Both keys share a hash tag so they sit in one cluster slot.

How to answer

Write the five lines of the script. Point out the hash tag; it is a detail that proves you have used Redis Cluster.

Likely follow-ups
  • Isn't a long Lua script dangerous? (Yes. It blocks the shard, so keep it O(1).)
  • What happens to the script if the primary fails over?
One Redis key is now the hot spot. How do you scale past it?

First check that you need to: one shard does on the order of 100k simple ops per second, and the waiting room may admit far less. If you do need more, split the stock into N buckets with different hash tags so they live on different shards. Route a user by hash(userId) to a bucket. When a bucket is empty, try the next ones before saying sold out. The per-user limit now spans buckets, so add a global SET NX claim per user and the SQL unique constraint as a backstop. Near the end, merge leftovers to avoid "sold out" while stock still exists.

How to answer

Push back with a number first, then shard, then name the two new problems yourself. Mention the kernel's per-CPU counters as the same idea.

Likely follow-ups
  • How many buckets? (Enough to spread over your shards, few enough that leftovers are small.)
Redis says the user got the phone, but the database write fails. What happens?

The reservation is first recorded in Kafka with acks=all before we reply, so the promise is durable even if the database is down. The order-writer consumer retries the insert with backoff and does not commit its offset until it succeeds. Inserts are idempotent by reservationId, so retries cannot duplicate. If the Kafka write itself fails, we put the unit back in Redis and tell the user to retry, so we never say yes without a durable record. After the sale, reconciliation compares Redis, Kafka and SQL.

How to answer

Make the ordering explicit: decrement, durable log, reply, then async DB. Then cover both failure points.

Likely follow-ups
  • The event is poison (bad data). Where does it go? (A DLQ with an alert; it is a real customer, so a human fixes it.)
Can Redis failover cause an oversell? How would you handle it?

Yes. Redis replication is asynchronous, so a promoted replica can miss the latest decrements and let a few extra units sell. Kafka still has every reservation, so no order is lost, but the counter is now too high. Handling: after any failover, pause that shard's buckets and rebuild the counters as total minus reservations recorded in Kafka/SQL; use WAIT to narrow the window; optionally hold back a small buffer released after reconciliation; or, if the business forbids any risk, use a strongly consistent store for the counter and accept lower throughput behind the waiting room.

How to answer

Admitting the weakness unprompted is a senior signal. Give the mechanism, the detection, the repair and the business trade-off.

Likely follow-ups
  • Does WAIT make Redis strongly consistent? (No. It reduces the window but is not consensus.)
Design the waiting room. How do you make it fair and keep it from falling over?

Make it stateless at the edge: on arrival, issue a signed token with the arrival time. Each edge node admits tokens below a "now serving" threshold that rises at the backend's capacity, adjusted by a feedback loop on backend health (Shopify used a PID controller). Users already waiting at T0 get a random order, so network speed does not decide. Throttled users see a cached queue page that polls at server-chosen intervals with jitter. Admitted users get a short-lived admission token bound to their account. If the room fails, fail closed with "sale paused".

How to answer

Cover state (signed tokens), rate (threshold + feedback), fairness (lottery then FIFO) and the failure mode. Cite Shopify Part I and Part II.

Likely follow-ups
  • How do you show an honest queue position without a central store?
  • Build or buy (for example a managed waiting room)?
A winner does not pay within 10 minutes. Walk me through returning the stock.

A worker pops due items from a sorted set of (reservationId, payBy). For each, it runs UPDATE ... SET status='EXPIRED' WHERE id=? AND status='HELD'. Only when that affects one row does it INCRBY the bucket and clear the sold-out flag, which admits the next wave from the waiting room. If the payment callback arrives later, it sees EXPIRED and either re-reserves (if stock is left) or refunds automatically. The conditional update is what makes "paid" and "expired" mutually exclusive.

How to answer

Name the race (late payment vs expiry) and resolve it with a single conditional transition.

Likely follow-ups
  • Why not use Redis key expiry events? (They can be missed.)
  • Should the TTL change if a payment provider is degraded?
How do you stop bots from buying all the stock?

Layers: no admission token, no reserve call (so scripts cannot skip the room); tokens are short-lived and bound to the account; limits per account, device, address and payment instrument; risk scoring with challenges only for suspicious sessions, so real users are not punished; pre-registration or verified buyers for the hottest drops; and after the sale, cancel orders that break the rules and return the stock. Ticketmaster's Eras Tour statement is the cautionary tale: 3.5 billion requests, largely bots and people without codes.

How to answer

Show defence in depth at different layers and say what each layer costs real users.

Likely follow-ups
  • A bot farm has 10,000 real accounts. What now?
Why not rely on the Kubernetes HPA to handle the spike?

The HPA reacts to metrics with a delay, new pods need image pulls and warm-up, and if nodes are full the cluster autoscaler needs minutes to add machines. The spike arrives in one second. So I pre-scale: raise minReplicas ahead of T0 (a scheduled job or the KEDA cron trigger), keep placeholder pods with a negative PriorityClass so spare nodes already exist, pre-pull images and warm caches. The HPA remains as a safety net for the hours after.

How to answer

Give the three delays (metrics, pods, nodes), then the pre-scale toolkit. Link it to autoscaling concepts.

Likely follow-ups
  • How do you size the pre-scale? (From the load test at the expected admitted rate plus headroom.)
Why put Kafka between the reservation and the order database?

The reservation burst happens in seconds, but the database wants a steady rate. Kafka records each reservation durably (replicated, acks=all), so we can answer the user immediately and let an order-writer consumer group insert at a controlled pace. If the database slows or fails, events wait in the log instead of failing users. Every reservation is replayable for reconciliation and for rebuilding Redis after a failover. Consumers must be idempotent because delivery is at-least-once.

How to answer

Name it a shock absorber or buffer, then give durability, decoupled pace and replay. Admit the cost: order rows appear slightly later.

Likely follow-ups
  • What partition key, and why does ordering not matter here?
  • How many partitions do you need?
Your service gets 10x traffic tomorrow for a sale. What do you do today?

Run a load test at the expected peak, including failure drills. Pre-scale compute and pre-provision nodes; check every dependency's limits (database connections, Redis memory, Kafka partitions, payment provider quotas). Put the waiting room and rate limits in front, with tested settings. Add feature flags to turn off non-critical features, and a kill switch to pause the sale. Freeze deploys. Prepare the war-room dashboard and alerts (admitted rate, error rate, p99, stock left, consumer lag, payment success), write runbooks for each failure, and agree who decides what.

60-second answer (say it out loud)

"Demand is thousands of times bigger than supply, so I design a funnel and reject traffic as early and cheaply as possible. The product page is static on a CDN with a server-time countdown. At T0 users enter a stateless waiting room at the edge with signed arrival-time tokens, and it admits them at the rate the backend can take, fairly. Admitted users call the reservation service, which runs one atomic Lua script in Redis: check the user has not won, check stock, decrement and record the buyer. If one key gets too hot, I split stock into buckets on different shards. A winner's reservation is written to Kafka with acks=all before we reply 'pay within 10 minutes', and an idempotent consumer writes orders to SQL at a steady rate. Unpaid reservations expire with a conditional update and return their stock. When stock hits zero, a sold-out flag goes to the edge so 99% of users get the cheapest possible answer. I isolate the sale in its own cell, pre-scale instead of autoscaling, and reconcile Redis, Kafka and SQL afterwards."

Scenario: the database melts at T0 + 3 seconds

At sale open, the shared orders database hits 100% CPU. Search and "My orders" for all customers start timing out. Redis looks healthy.
Weak answer: "Add read replicas and scale the database vertically."
Strong answer: "Something in the hot path writes to the shared database synchronously. First, protect the shop: lower the waiting room admission rate and pause the order-writer consumers (Kafka holds the reservations safely). Then find the culprit: probably a synchronous insert or a stock read in the reserve path, or the payment page querying the order row. Fix: move it behind Kafka or read from the reservation. Afterwards, move the sale onto its own database cell and add a load test that fails if any reserve call touches the shared database."
Follow-ups: How do you know Kafka will not lose the reservations while the consumers are paused? (Retention, replication factor 3, min.insync.replicas=2.)

Scenario: you sold 10,040 units of 10,000

Post-sale reconciliation finds 10,040 PAID or HELD reservations. The logs show a Redis primary failover at T0 + 8 s.
Weak answer: "Redis is unreliable; switch to the database next time."
Strong answer: "The promoted replica missed about 40 decrements because replication is asynchronous. Short term: honour or cancel the 40 last reservations (ordered by reservation timestamp or the time-ordered Snowflake reservation_id, not by Kafka offset, which is only ordered within one partition) following the business policy, with compensation for affected users, and check whether the warehouse has spare units. Long term: on any failover, auto-pause the affected buckets and rebuild counters from the Kafka log before reopening; add WAIT on the reserve path; hold back a small buffer released only after reconciliation; and alert on 'reservations in Kafka > total - Redis stock' in real time."
Follow-ups: How would you detect this during the sale rather than after? (Stream a running count of reservation events and compare it to Redis every second.)

Scenario: "sold out" shows, but stock is left

Users see SOLD OUT at T0 + 20 s, yet SQL shows only 9,200 reservations, and support is flooded.
Weak answer: "Clear the cache."
Strong answer: "With sharded buckets, the sold-out flag was probably set when a bucket emptied, or a user's fallback did not try the other buckets. Check the flag-setting code and the bucket counters. Fix: set sold-out only when all buckets are 0 (track an empty-bucket bitmap), make fallback scan every bucket, merge leftovers into one bucket near the end, and add a 'stock left vs flag' consistency alert. Re-open the sale from the waiting room queue so the people who waited get the units first."
Follow-ups: How do you tell users fairly that stock is back?
