Remember this

You might confuse this with:

  • Reservation vs order: a reservation is the Redis "yes, one unit is held for you" with a payment deadline; an order is the durable row written later by the order writer after the Kafka event. A reservation can expire; a paid order cannot.
  • Waiting room vs rate limiter: a rate limiter rejects excess requests per client; a waiting room queues people fairly and admits them at the rate the backend can take.
  • Stock bucket vs Redis shard: a bucket is a slice of the stock (one key); a shard is a Redis server. Several buckets can live on one shard.

Remember this

  • Demand is far bigger than supply, so design a funnel: CDN -> waiting room -> gateway -> Redis counter -> Kafka -> DB.
  • Make "sold out" and "please wait" the cheapest answers, served from the edge. Never answer with errors that cause refreshes.
  • The waiting room is stateless (signed tokens), rate-controlled by a feedback loop, and fair (a lottery at T0, then FIFO).
  • Stock: one atomic Lua script (check user, check stock, DECRBY, SADD). Shard into buckets only when needed, and handle the per-user limit and uneven emptying.
  • Reply only after the reservation is durable in Kafka. Write the DB asynchronously and idempotently.
  • Redis failover can oversell. Rebuild counters from the log, use WAIT, keep a buffer, or pick a strongly consistent store.
  • Payment TTL: a conditional HELD -> EXPIRED update, then return the stock. Late payments are re-reserved or refunded.
  • Isolate the sale's blast radius, pre-scale (do not autoscale), load test, and reconcile after.
