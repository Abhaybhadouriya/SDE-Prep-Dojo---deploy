Data model

Two places hold the truth for different moments. During the sale, Redis holds the live counter (fast, atomic). Kafka holds the record of every reservation (durable, replayable). The SQL database holds reservations and orders as the long-term source of truth, written at a pace it can handle.

Key / tableStoreHoldsNotes
sale:{bbd26:b3}:stockRedisunits left in bucket 3Stock split into N buckets. The hash tag {bbd26:b3} puts each bucket's keys in one slot, and different buckets on different shards. (A Redis Cluster splits keys into 16,384 slots spread over shards; a hash tag is the part in braces, and only that part is hashed to pick the slot. More with the script in deep dive 2.)

sale_reservationsSQLreservation, user, status, pay_byUNIQUE (sale_id, user_id) is the last-line defence for "one per user".
 
CREATE TABLE sale_reservations (
  reservation_id BIGINT PRIMARY KEY,
  sale_id        TEXT   NOT NULL,
  user_id        BIGINT NOT NULL,
  bucket         INT    NOT NULL,
  status         TEXT   NOT NULL,         -- HELD, PAID, EXPIRED, CANCELLED
  pay_by         TIMESTAMPTZ NOT NULL,
  order_id       BIGINT,
  UNIQUE (sale_id, user_id)               -- one per user, enforced by the database too
);

-- the sale's ground truth after the dust settles
SELECT status, count(*) FROM sale_reservations WHERE sale_id = 'bbd26' GROUP BY status;
 status  | count
---------+-------
 PAID    |  9412
 HELD    |   211
 EXPIRED |   377
(3 rows)

(An example result.) Reconciliation checks the invariant: PAID + HELD must never be more than total stock, and Redis's remaining stock should equal total minus PAID minus HELD. Here 9,412 + 211 = 9,623, so 377 units came back from expired reservations and can go to a second wave or the waitlist.
