Deep dives

Stop here for SDE-1: the waiting-room idea (deep dive 1), the Version A Lua counter (deep dive 2, first half) and async orders through Kafka (deep dive 3) are enough. Buckets, Redis failover and bot defence are SDE-2 material.

1. The waiting room: admission control done kindly (must know)

The best real story here is Shopify's. In February 2016 a Kylie Cosmetics flash sale overloaded a database shard, and every other store on that shard went down with it. Shopify's fix, described in a two-part engineering post, was a throttle in its Nginx + OpenResty (Lua) load balancers:

  • Part I: a leaky bucket at the edge lets a fixed number of checkouts through per time window. Throttled users get a cached queue page (not an error). Users who are let through receive a signed cookie, so they are not throttled again mid-checkout. The flaw: users polled with random timeouts, so a newcomer could get lucky before someone who had waited for minutes. It was unfair.
  • Part II: each user's first arrival time goes into a signed cookie (so it cannot be faked). Each load balancer computes a threshold, like a deli's "Now Serving: 42" sign, and lets through only users who arrived before it. The threshold moves automatically based on capacity using a PID controller from control theory. Because each load balancer calculates it independently, there is no shared datastore to fail under load.

From your world

Part I is a leaky-bucket shaper (the QoS shaper you configure on a WAN link). Part II adds a closed control loop: measure the error (current vs desired admitted rate), feed it through proportional, integral and derivative terms, and adjust the threshold. It is the same PID loop as a fan controller or a clock-recovery circuit. Where it breaks: the "packets" are humans who refresh the page, so the queue page must be cheap, honest about position, and stable.

Design choices for your waiting room:

  • Pre-T0 arrivals: people who arrive at 11:55 should not win just by having a faster network at 12:00:00.000. A common fair option: everyone already in the room at T0 gets a random position (a lottery), and later arrivals queue FIFO behind them.
  • Stateless edge: keep state in signed tokens, as Shopify did, so the room scales with the CDN or load balancer fleet and has no database to fall over. Managed options exist (for example Cloudflare Waiting Room).
  • Admission rate: set it from the backend's tested capacity, and adjust it live from its health (error rate, p99 latency) with a feedback loop.
  • Short-lived admission tokens (a minute or two), bound to the user, so a token cannot be shared or reused by a bot farm.

Ticketmaster's November 2022 Eras Tour presale shows what happens without enough of this: Ticketmaster said it saw 3.5 billion total system requests, 4x its previous peak, much of it from bots and from fans without presale codes. The lesson in its statement is to combine pre-registration (Verified Fan), a queue and bot defence. See also ticket booking.

2. The stock counter: atomic, then sharded (must know; buckets are SDE-2)

Why not the database row? UPDATE inventory SET stock = stock - 1 WHERE sku = 'X' AND stock > 0 is correct, and it is what normal checkout does. But in a flash sale every request wants the same row. The database serialises them on that one row lock, every transaction waits for the one ahead, connection pools fill up, and the database (shared with the rest of the shop) slows for everyone. That is the Shopify shard story again.

Version A: one Redis key with a Lua script. Redis runs a Lua script atomically: no other command runs in the middle. One script can check "has this user already won?", check stock, decrement and record the winner, all as one step.

-- reserve.lua   KEYS[1] = stock key   KEYS[2] = buyers set   ARGV[1] = userId   ARGV[2] = qty
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -2                                    -- this user already won
end
local left = tonumber(redis.call('GET', KEYS[1]) or '0')
local qty  = tonumber(ARGV[2])
if left < qty then
  return -1                                    -- not enough stock here
end
redis.call('DECRBY', KEYS[1], qty)
redis.call('SADD', KEYS[2], ARGV[1])
return left - qty                              -- units left after this reservation

Try it with docker run -d -p 6379:6379 redis:7. We start the bucket with 2 units:

$ redis-cli SET 'sale:{bbd26:b3}:stock' 2
OK
$ redis-cli --eval reserve.lua 'sale:{bbd26:b3}:stock' 'sale:{bbd26:b3}:buyers' , u101 1
(integer) 1
$ redis-cli --eval reserve.lua 'sale:{bbd26:b3}:stock' 'sale:{bbd26:b3}:buyers' , u101 1
(integer) -2
$ redis-cli --eval reserve.lua 'sale:{bbd26:b3}:stock' 'sale:{bbd26:b3}:buyers' , u202 1
(integer) 0
$ redis-cli --eval reserve.lua 'sale:{bbd26:b3}:stock' 'sale:{bbd26:b3}:buyers' , u303 1
(integer) -1

u101 wins (1 left), u101 tries again and is refused (-2), u202 takes the last unit (0 left), and u303 finds it empty (-1). In redis-cli --eval, keys come before the comma and arguments after it. The {bbd26:b3} part is a Redis Cluster hash tag: only the text inside the braces is hashed, so both keys land in the same slot and one script may touch both.

Version B: split the hot key into buckets. One Redis key lives on one shard and is executed by one thread. A single shard handles on the order of 100,000 simple operations per second (order of magnitude; a Lua script costs more, so measure). If the waiting room admits less than that, Version A is enough, and saying so is a good senior answer. If you must go faster, split 10,000 units into, for example, 10 buckets of 1,000, each with its own hash tag ({bbd26:b0} ... {bbd26:b9}), so they spread across shards.

Buckets bring two new problems, and naming them is what makes this a Level 5 answer:

  • The per-user limit now spans buckets. Route each user to a bucket by hash(userId) % N, so the same user always hits the same bucket and that bucket's buyers set catches repeats. Add a global guard as a separate step, SET sale:bbd26:user:<userId> 1 NX EX 900, before decrementing, and the UNIQUE (sale_id, user_id) constraint in SQL as the final word. Because the claim is a separate step, delete it (DEL) on every failure path: the bucket was sold out, the Kafka write failed, or the payment hold expired; otherwise the user stays locked out of a retry or a second wave. (The user id is written without braces on purpose: in Redis Cluster, braces in a key name would make a hash tag.)
  • Uneven emptying. Bucket 3 can be empty while bucket 8 still has units. When a user's bucket returns -1, try the next buckets in a fixed order before saying "sold out", and keep a small "all buckets empty" bitmap so you stop trying fast. Near the end you can also merge leftovers into one bucket.

From your world

This is the Linux kernel's per-CPU counter idea (percpu_counter, this_cpu_* operations): instead of every CPU fighting over one cache line with atomic operations, each CPU updates its own local counter and the global value is the sum. Contention disappears, and the cost is that "the exact global value" needs a fold. Here the "CPUs" are Redis shards, and the fold is "check the other buckets before sold out". Where it breaks: summing per-CPU counters takes nanoseconds in shared memory; summing Redis buckets costs a network round trip per bucket, which is why you keep the "all buckets empty" bitmap instead of re-reading every bucket.

3. Asynchronous orders through Kafka, and "Redis said yes but the DB failed" (must know)

Once Redis says "yes", the user has won. Writing the order synchronously to SQL would bring the database back into the hot path. Instead the reservation service writes a reservation.created event to Kafka and replies. An order-writer consumer group drains the topic into SQL at a rate the database is comfortable with.

  • Order of operations: Redis decrement, then a Kafka write with acks=all, then the reply. If the Kafka write fails, give the unit back (INCR and remove the user from the buyers set) and return an error. The user never hears "yes" for something that is not recorded.
  • Idempotent consumer: the order writer inserts with ON CONFLICT (reservation_id) DO NOTHING, so a redelivered event cannot create a second order. A UNIQUE (sale_id, user_id) violation means a bug upstream: send it to a DLQ and alert.
  • DB write fails: the consumer does not commit its offset and retries with backoff. The event stays in Kafka, so it is not lost while the database recovers. This is the answer to the classic follow-up.
  • Backpressure is free: if the database slows down, consumer lag grows, but users already have their answer. Lag is exactly the "queue depth" you would watch on a NIC ring.

The honest weak spot: Redis durability. Redis replicates asynchronously. If the primary of a shard dies right after a decrement, the replica that takes over may not have it, and the counter "un-sells" a unit that was already promised. Kafka still has the reservation event, so you will not lose the order. But Redis may now allow one extra sale, which is an oversell. Mitigations, from cheap to strong:

  1. Treat Kafka as the record. After any Redis failover, pause the sale for a moment and rebuild the counter as total - (reservations in Kafka/SQL) before reopening.
  2. Use WAIT 1 50 after the script, so the reply waits until at least one replica has the write (or 50 ms pass). This narrows the window but does not make Redis strongly consistent.
  3. Hold back a small buffer of units and release it only after reconciliation. The business decides whether a tiny buffer or a rare apology is cheaper.
  4. Use a strongly consistent store for the counter if the business demands it, and pay for it with lower throughput behind the waiting room.

4. Payment TTL: giving stock back safely (good to know)

Many winners will not pay: the UPI app fails, they change their mind, or a bot grabbed it and cannot pay. A reservation therefore lives for, say, 10 minutes. When it expires:

-- only a HELD reservation can expire; a PAID one is untouched
UPDATE sale_reservations SET status = 'EXPIRED'
 WHERE reservation_id = 88121 AND status = 'HELD' AND pay_by < now();

If that returns UPDATE 1, and only then, the worker does INCRBY on the bucket and removes the user from the buyers set (if your rules allow a second try). UPDATE 0 means it was paid or already expired, so nothing is returned. That conditional update is what stops a slow payment callback and an expiry from both "winning".

  • Do not rely on Redis key-expiry notifications to trigger this. They are fire-and-forget and can be missed. Use a sorted set of (reservationId, payBy) plus a worker that pops due items, with the SQL row as the truth.
  • Payment arrives after expiry: the payment callback sees status EXPIRED. Either re-reserve if stock is available, or refund automatically. Never ship a unit that has been given to someone else.
  • Returned stock clears the sold-out flag and admits the next users from the waiting room. That is how a "sold out" item comes back ten minutes later.

5. Protect everything else: blast radius, pre-scaling and bots (SDE-2)

  • Isolate the sale. Run the reservation service and its Redis on their own cluster (a "cell"). If they melt, search, other products and old orders keep working. The Kylie Cosmetics incident took down every store that shared the shard.
  • Pre-scale, do not autoscale. Autoscalers react in minutes, and the spike arrives in one second. Scale up hours before, warm caches, open connection pools, and pre-provision nodes. Flipkart's BBD 2015 memoir describes about four months of preparation, with infrastructure programs taking the two months before code freeze.
  • Load test and rehearse. Run game days at production scale. Test the failure paths too: Redis failover, Kafka broker loss, a payment provider slowdown.
  • Shed load on purpose. Turn off non-critical features (recommendations, reviews, personalisation) with feature flags during the first minutes. Keep a critical-traffic reserve, as in Amazon's load-shedding guidance.
  • Stop retry storms. Clients use exponential backoff with jitter. Servers return final answers (410 sold out). Polling intervals are set by the server (pollAfterMs) and spread out.
  • Bots: admission tokens bound to the user, limits per account, device, address and payment instrument, challenges only for suspicious sessions, pre-registration for the hottest deals, and post-sale cancellation of orders that break the rules.

Interviewers love this line: "I will design so that the sold-out answer is the cheapest response in the whole system." 99.8% of users get that answer, so it must come from the edge, not from your database.
