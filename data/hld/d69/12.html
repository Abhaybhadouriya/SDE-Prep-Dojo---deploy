Quick quiz

Why must services read config from local memory instead of calling the service per request?

  1. Network calls cannot return JSON documents
  2. The service only supports one client at a time
  3. So a config outage cannot take down traffic
Keeping the service off the request path means its failure only delays changes. JSON over the network is routine, and the distributor tier serves a million clients, so neither of the other reasons is true.

Why does each long-poll include the version the client already has?

  1. A missed notification is fixed on the next request
  2. It lets the server skip authentication
  3. It makes the response smaller by compression
  4. It forces the store to create a new version
Stating the current version makes delivery level-triggered: any gap is detected and filled on the next request. Authentication is separate. Deltas can shrink payloads, but that is a side benefit, not compression. Reads never create versions.

How is rollback done in a design with immutable versions?

  1. Edit the current version back to the old values
  2. Delete the bad version from the store
  3. Redeploy every service with the old file
  4. Move each target's pointer to the previous version
Pointer moves are fast, audited and use the normal delivery path. Editing or deleting versions destroys history and audit. Redeploying takes far longer and is exactly what the config service is meant to avoid.

What is the bake time in a staged rollout?

  1. How long the client takes to parse a config
  2. Time alarms are watched before going wider
  3. The long-poll timeout on the distributor
Bake time is the observation window after a step (AppConfig also watches after reaching 100%), and an alarm in it triggers rollback. Parse time and the long-poll timeout are unrelated timings.

Why not let a million clients watch etcd directly?

  1. etcd has no watch API
  2. etcd cannot store JSON values
  3. Every watcher loads the consensus cluster
  4. etcd watches only work inside Kubernetes
Watchers are load and state on a small consensus cluster, and a leader change would make them all reconnect; a distributor tier absorbs that. etcd does have watches, stores any bytes including JSON, and runs outside Kubernetes too.

A new config version fails validation inside the client SDK. What should the SDK do?

  1. Keep the current version and report the rejection
  2. Apply it anyway, since the server validated it
  3. Crash so that the orchestrator restarts the pod
Keep running on the known-good config and report "rejected v42" so the rollout controller can stop and roll back. Trusting the server alone skips the last line of defence. Crashing turns one bad config into an outage.

In the concurrent LRU cache, why does get() need the same lock as put()?

  1. Python dictionaries cannot be read concurrently
  2. get() may evict the least recently used entry
  3. The hit counter must be stored on disk
  4. get() moves the key in the recency list
A get changes recency order, which is a write to the shared list, so it must be serialised with puts. Evictions happen in put, not get. Concurrent dict reads are fine in themselves, and counters live in memory.
