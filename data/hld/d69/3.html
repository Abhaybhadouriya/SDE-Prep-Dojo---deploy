Key APIs

# Admin (control plane) - authenticated, authorised per namespace, audited
PUT  /v1/configs/{ns}/{env}/{name}        If-Match: "v41"          # CAS on version
     {content:{...}, schema_ref, change_reason}
     -> 201 {version: 42}   | 412 PRECONDITION_FAILED (someone else wrote v42)
GET  /v1/configs/{ns}/{env}/{name}/versions?limit=20
GET  /v1/configs/{ns}/{env}/{name}/diff?from=41&to=42
POST /v1/deployments  {config, version:42, strategy:"canary10-bake20", targets:"prod/*"}
POST /v1/deployments/{id}/rollback

# Data plane - what client SDKs call (via the distributor tier)
GET  /v1/watch?keys=payments/prod/limits@41,flags/prod/checkout@7&timeout=60
     -> 200 {changes:[{key, version:42, content|delta, checksum}]}   # something changed
     -> 304 (timeout, nothing new: ask again)
GET  /v1/snapshot?keys=...                    # full fetch at startup

Why If-Match on writes? Two engineers editing the same config at the same time must not silently overwrite each other. Compare-and-set on the version gives the "strong at write" guarantee: the second writer gets 412 and must rebase on v42. This is optimistic locking on the config document.
