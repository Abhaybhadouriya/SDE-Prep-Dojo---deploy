Deep dives

1. Push, watch or long-poll?

ModelHowProsCons
Periodic pollEvery 30 s: "give me config X"Simplest; stateless servers; works through any proxyDelay up to the interval; wasted requests; full payload each time unless you send ETags
Long-poll"Anything newer than v41?"; server holds up to 60 sNear-instant; plain HTTP; client decides the version it has, so no lost updatesOpen connections per client; reconnect storms need jitter
Server push (gRPC stream / SSE / WebSocket)Persistent stream; server sends changesFastest; efficientServer must track per-stream state; resume after disconnect needs a revision anyway
Watch on etcd/ZooKeeper directlyClient SDK watches the consensus storeNo extra tier; ordered, consistent notificationsDoes not scale to a million clients; every client is load on the consensus leader

My pick: long-poll (or a gRPC stream) to a distributor tier, with the client always stating the version or revision it has. That makes delivery level-triggered: if a notification is lost, the next request still says "I have v41" and gets v42. Edge-triggered "here is a change" messages alone can be missed forever. The distributors are the only watchers of the store.

Watch gotchas you should name. Classic ZooKeeper watches are one-time triggers: after firing, the client must re-read and re-register, and changes in between are seen only as the latest value (persistent watches arrived in 3.6). etcd watches resume from a revision, but if that revision was compacted away the watch fails and the client must re-fetch a full snapshot. Both are fine for a few thousand watchers, not a million.

2. The client SDK: cache, last-known-good, never block

The SDK matters more than the server. Its rules:

  1. Reads are local. config.get("timeout_ms") reads an in-memory, immutable snapshot. Zero network calls on the request path.
  2. Startup order: try the service (snapshot); if it fails, load last-known-good from local disk; if there is none, use defaults compiled into the binary and raise an alert. Never refuse to start because the config service is down (unless a config is marked "required fresh", like a kill switch for a security issue).
  3. Validate before swap. Checksum, schema, and the service's own validator. If v42 fails validation, keep v41, report "rejected v42", and let the rollout controller see it.
  4. Atomic swap of the whole snapshot (a pointer replace), so a request never sees half of v41 and half of v42.
  5. Jittered reconnect with exponential backoff, so a distributor restart does not become a thundering herd.
  6. Report the applied version (metrics or a heartbeat), so the control plane knows rollout progress and stragglers.

This is a good candidate for "implement a small component", which one Microsoft L61/L62 round asked for after the HLD (post). A compact version:

import json, os, random, threading, time, hashlib

class ConfigClient:
    """Watches one config via long-poll; reads are local and lock-free."""

    def __init__(self, fetch, key, lkg_path, validate, defaults):
        self._fetch = fetch            # fetch(key, have_version, timeout) -> (ver, text, sha) or None
        self._key, self._lkg, self._validate = key, lkg_path, validate
        self._snap = (0, defaults)     # (version, dict) - replaced atomically, never mutated
        self._stop = threading.Event()
        self._load_lkg()

    def get(self, name, default=None):  # request path: no network, no lock
        return self._snap[1].get(name, default)

    def version(self):
        return self._snap[0]

    def _load_lkg(self):
        try:
            with open(self._lkg, encoding="utf-8") as f:
                saved = json.load(f)
            self._snap = (saved["version"], saved["content"])
        except (OSError, ValueError, KeyError):
            pass                         # keep compiled-in defaults

    def _apply(self, ver, text, sha):
        if hashlib.sha256(text.encode()).hexdigest() != sha:
            return False                 # corrupted download
        try:
            content = json.loads(text)
        except ValueError:
            return False                 # unparseable: keep current
        if ver <= self._snap[0] or not self._validate(content):
            return False                 # stale or invalid: keep current
        self._snap = (ver, content)      # atomic reference swap
        tmp = self._lkg + ".tmp"
        with open(tmp, "w", encoding="utf-8") as f:
            json.dump({"version": ver, "content": content}, f)
        os.replace(tmp, self._lkg)       # atomic on the same filesystem
        return True

    def stop(self):
        self._stop.set()                 # run() exits after the current poll

    def run(self):
        backoff = 1.0
        while not self._stop.is_set():
            try:
                res = self._fetch(self._key, self._snap[0], timeout=60)
                if res and not self._apply(*res):
                    # Stale (lagging distributor), corrupt or invalid: do not
                    # re-poll at once, or we hot-loop against the distributor.
                    self._stop.wait(backoff * random.uniform(0.5, 1.5))
                    backoff = min(backoff * 2, 60)
                    continue
                backoff = 1.0            # None means "304: nothing newer"
            except Exception:
                self._stop.wait(backoff * random.uniform(0.5, 1.5))   # jitter
                backoff = min(backoff * 2, 60)

3. Staged rollout and automatic rollback

Configuration changes deserve the same rollout discipline as code. AWS AppConfig is a good public model: a deployment strategy has a growth rate, a step interval and a bake time, during which AppConfig keeps watching CloudWatch alarms after reaching 100%, and rolls back automatically if an alarm fires. Its predefined strategies include AppConfig.Canary10Percent20Minutes and AppConfig.Linear20PercentEvery6Minutes, and AWS labels the fastest one as suitable only for testing.

  • Who is in the canary? Pick instances by a stable hash (instance id mod 100 < 10), so the same 10% stays on v42 during the step, and include each region and each service that reads the config. For feature flags, hash the user id instead, so a user sees a consistent experience.
  • What does "healthy" mean? The service's own SLO alarms (error rate, latency) plus config-specific signals: SDK "rejected" reports, crash loops right after applying. Compare canary with control, not with yesterday.
  • Rollback is a forward move of the pointer to an old immutable version, recorded as a new revision. Nothing is deleted or edited.
  • Emergency path: a kill-switch flag may skip the waves (with extra approval), because sometimes "turn it off everywhere now" is the safe action.
  • Mixed versions are normal. During a rollout, some instances run v41 and some v42. Every config change must be safe to run mixed; if not (two services must agree), roll the consumer first, or put both values in one config with a switch-over time.

4. Consistency: strong at write, eventual at read

  • Writes go through one linearizable path (Raft leader or a single primary) with compare-and-set on the version. No lost updates; one total order of revisions. Two edits never interleave.
  • Reads are served from distributor caches and client memory, so different instances can be a few seconds apart. That is acceptable because the service is designed for mixed versions.
  • Monotonic reads per client: the client sends its version; a distributor that is behind (it has only v41) must not "downgrade" a client to v41. It either holds the request until it catches up or redirects the client.
  • Read-your-writes for the author: the admin UI reads from the store's leader (or waits for its revision), so the engineer sees v42 immediately after saving.
  • Multi-region: one writer region (or one consensus group per region for region-scoped configs), asynchronous replication of versions to other regions, each with its own distributors. Global configs roll out region by region anyway, so cross-region lag is absorbed by the rollout plan.

5. Security, access control and audit

  • RBAC per namespace and environment: the payments team can edit payments/*; prod requires a second approver; read access for service identities is limited to the configs they subscribe to (clients authenticate with mTLS or workload identity).
  • Secrets are not configs. Store a reference (secret://payments/db-password) and let the SDK resolve it from a secrets manager (Azure Key Vault, AWS Secrets Manager, Vault) with its own audit and rotation.
  • Audit every read of sensitive configs and every write: who, what diff, why, which ticket, which deployment. Append-only, shipped to write-once storage.
  • Validation as code: schemas and validators live next to the config and run in CI and again at publish time. Facebook's Configerator compiles configs from code and runs validators before they can be committed.
