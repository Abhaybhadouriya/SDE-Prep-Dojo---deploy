Architecture, step by step

  1. Submit. The engineer (UI, CLI or a merged Git pull request) submits v42 with a reason. The API authenticates, checks the namespace permission, requires an approval for prod, and validates the content against its schema and custom validators.
  2. Commit. The API writes v42 with compare-and-set on v41 into the consensus store (etcd/Raft or a single-primary database). The commit assigns global revision 9001 and an audit entry. Strong consistency lives here, and only here.
  3. Plan the rollout. The rollout controller moves only the canary pointer (prod/us-east/canary) to v42. The others still point to v41.
  4. Distribute. Each distributor holds one watch on the store from its last revision, sees revision 9001, fetches v42 once and caches it. It does not need to ask the store per client.
  5. Wake the clients. Clients in the canary group have a long-poll open ("anything newer than v41?"). Their distributor answers them at once with v42 (or a delta). Other clients keep waiting.
  6. Apply safely. The SDK verifies the checksum, validates the content locally, then swaps the in-memory config atomically (readers see v41 or v42, never half). It writes v42 to local disk as the new last-known-good and reports "applied v42".
  7. Bake. The controller watches alarms (error rate, latency, crash loops) for the canary group during the bake time, and compares them with the control group still on v41.
  8. Widen. Green: move pointers wave by wave (25%, then each region) with a bake between waves, until every target points to v42.
  9. Roll back. Red at any point: the controller moves the pointers back to v41. It is the same delivery path, so rollback takes seconds and needs no deploy. The deployment is marked ROLLED_BACK and the author is notified.

Stop here for SDE-1: requirements, versions, the long-poll or watch, client cache with last-known-good. The Microsoft rounds were senior (L61-L64), so expect the rollout controller, consistency, the distributor tier and a coding follow-up.
