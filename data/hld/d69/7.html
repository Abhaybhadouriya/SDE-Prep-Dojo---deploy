Where Kafka, Kubernetes and Docker fit

Concrete settings. Kafka here is only the change feed, not the delivery path. Partition key config_key on a compacted topic keeps the latest revision per key, so a new consumer can rebuild state. Consumer-group sizing: change volume is tiny, so 6 partitions are plenty. The distributor HPA scales on open long-poll connections (a custom metric), since each held connection costs memory, not CPU.

Kubernetes

  • Kubernetes already has a tiny config service: ConfigMaps stored in etcd, with a 1 MiB size limit. Mounted as a volume, a changed ConfigMap appears in the pod after the kubelet's sync delay (eventually consistent); as environment variables it never updates until the pod restarts.
  • That is fine for per-cluster settings, but there is no staged rollout, no cross-cluster view and no per-user flags, which is why companies add a dedicated service (or roll ConfigMap changes through a Deployment rollout so pods restart in waves).
  • The distributor tier is a stateless Deployment behind a Service; a PodDisruptionBudget and topology spread keep connections spread across zones; preStop hooks drain long-polls gracefully.
  • The consensus store is a 3- or 5-member StatefulSet (or managed), separate from the cluster's own etcd.

Kafka and Docker

  • Kafka is not the delivery path to a million clients (consumers per partition and group management do not fit that shape), but it is a good change feed: every committed revision published to config.changes (compacted, keyed by config_key) for audit pipelines, cache warmers, search over configs and analytics on rollouts.
  • A compacted topic keeps the latest version per key forever, so a new consumer can rebuild the full current state from offset 0.
  • Docker images embed compiled-in defaults and nothing environment-specific: the same image runs in dev and prod, and differs only by config. That separation is the reason a config service exists.
# A ConfigMap consumed as a volume: updates arrive eventually, without a restart
apiVersion: v1
kind: ConfigMap
metadata: { name: payments-limits }
data:
  limits.json: |
    {"timeout_ms": 800, "max_retries": 2}
---
# in the Pod spec
volumes:
  - name: cfg
    configMap: { name: payments-limits }
containers:
  - name: app
    volumeMounts: [{ name: cfg, mountPath: /etc/config, readOnly: true }]
