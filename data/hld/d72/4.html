Data model

Auctions and bids in a relational database (PostgreSQL / Aurora / MySQL) or DynamoDB, sharded by auction_id so one auction's row and its bids live together. Search in Elasticsearch, fed by CDC. Store choice reasoning in Choosing Storage.

CREATE TABLE auction (
  auction_id     BIGINT PRIMARY KEY,
  seller_id      BIGINT NOT NULL,
  item_id        BIGINT NOT NULL,
  start_price    BIGINT NOT NULL,
  reserve_price  BIGINT,
  starts_at      TIMESTAMPTZ NOT NULL,
  ends_at        TIMESTAMPTZ NOT NULL,          -- moves forward on soft close
  soft_close_s   INT NOT NULL DEFAULT 0,
  status         TEXT NOT NULL,                 -- SCHEDULED, LIVE, CLOSING, CLOSED, SETTLED, CANCELLED
  current_price  BIGINT NOT NULL,
  leader_id      BIGINT,
  leader_max     BIGINT,                        -- the leader's secret maximum (proxy bidding)
  bid_count      INT NOT NULL DEFAULT 0,
  version        BIGINT NOT NULL DEFAULT 0
);
CREATE INDEX auction_ending ON auction (ends_at) WHERE status = 'LIVE';

CREATE TABLE bid (
  auction_id   BIGINT NOT NULL,
  seq          BIGINT NOT NULL,                 -- = auction.version after this bid
  bid_id       BIGINT NOT NULL UNIQUE,
  bidder_id    BIGINT NOT NULL,
  amount       BIGINT NOT NULL,
  max_amount   BIGINT,
  kind         TEXT NOT NULL,                   -- DIRECT, PROXY_AUTO
  idem_key     TEXT NOT NULL,
  server_ts    TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (auction_id, seq),
  UNIQUE (bidder_id, idem_key)
);

Two design points. Denormalise the current price and leader onto the auction row: the bid check reads one row, never "SELECT max(amount) FROM bid". And keep bids append-only, including rejected ones if you want a full audit; the auction row is the summary, the bid table is the history.
