Key APIs

REST for actions, SSE or WebSocket for live updates. Background in API Design & Client-Server Communication.

# --- sellers ---
POST /v1/auctions        (role = SELLER)
  { "title": "Signed cricket bat", "categoryId": 12, "startPrice": 50000, "reservePrice": 200000,
    "buyNowPrice": null, "startsAt": "2026-11-24T10:00:00Z", "endsAt": "2026-12-01T10:00:00Z",
    "photos": ["s3://..."], "softCloseSeconds": 120 }
  -> 201 { "auctionId": "a_42", "status": "SCHEDULED" }
GET  /v1/sellers/me/auctions?status=LIVE

# --- bidders ---
GET  /v1/search?q=cricket+bat&category=12&maxPrice=300000&sort=ending_soon
GET  /v1/auctions/a_42          -> { price, bidCount, leaderMasked, endsAt, status, minNextBid, version }
POST /v1/auctions/a_42/bids     (role = BIDDER)   Idempotency-Key: 3b7...
  { "amount": 125000 }                            # or { "maxAmount": 300000 } for a proxy bid
  -> 201 { "bidId": "b_9001", "accepted": true, "leading": true, "price": 125000, "endsAt": "..." }
  -> 409 { "accepted": false, "reason": "TOO_LOW", "minNextBid": 130000 }
  -> 409 { "accepted": false, "reason": "AUCTION_CLOSED" }
GET  /v1/auctions/a_42/bids?cursor=...            # history

# --- live updates ---
GET  /v1/auctions/a_42/stream    (SSE)  -> event: price {"version":57,"price":125000,"bidCount":31,"endsAt":"..."}

# --- winner ---
POST /v1/auctions/a_42/checkout  -> payment intent for the winning amount

Bid responses carry minNextBid and the server's endsAt, so the client never computes rules or trusts its own clock. Prices are integers in minor units. The idempotency key makes a double-tap one bid.
