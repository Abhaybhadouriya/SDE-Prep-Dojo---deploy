Deep dives

1. Accepting bids consistently under heavy concurrency

The bug to avoid: two servers read "current price 110", both accept 120 and 125 as "higher than 110", and the lower bid overwrites the higher one, or both bidders are told they lead. Options, from weakest to strongest:

  1. Pessimistic lock SELECT ... FOR UPDATE on the auction row, check, write the bid, update the row, commit. Correct; holds a lock for the whole transaction, so a hot auction queues on it. Fine up to hundreds of bids per second per auction if the transaction is short.
  2. Conditional update (optimistic, single statement) The usual best answer: 
    UPDATE auction
   SET current_price = :amount, leader_id = :bidder, bid_count = bid_count + 1, version = version + 1
 WHERE auction_id = :id AND status = 'LIVE' AND now() < ends_at
   AND :amount >= CASE WHEN bid_count = 0 THEN start_price
                    ELSE current_price + increment_for(current_price) END
RETURNING version;            -- 0 rows: reject with the fresh price
    Then insert the bid with seq = version in the same transaction. DynamoDB does the same with a ConditionExpression; a failed condition raises ConditionalCheckFailedException, and the write is idempotent if the condition is on the attribute being changed (AWS docs).
  3. Per-auction serialisation through a partitioned queue The bid API publishes each bid to Kafka keyed by auction_id; one consumer per partition processes bids for that auction strictly in order, keeping the current price in memory (backed by the database) and writing results. No row contention at all and natural ordering, at the cost of an asynchronous answer (the client waits for a result event, typically tens of milliseconds) and more moving parts.
  4. Redis Lua script Keep the hot auction's state in Redis and run check-and-set atomically in a Lua script (Redis runs one script at a time per shard). Very fast; you must still persist durably (write-behind to the database or Kafka) and handle failover carefully.

A good interview path: start with the conditional update (simple, correct, synchronous), then say "if one auction gets thousands of bids a second, I move that auction's bids onto a Kafka partition with a single consumer", which is the queue option. This is exactly the "conflict resolution between simultaneous bids" follow-up from the Razorpay round. See also Dealing with Contention.

Do not use a distributed lock (Redis SETNX) around a read-then-write as your main answer. Locks expire during GC pauses and network stalls, and then two writers proceed. A conditional write inside the store that owns the data is simpler and safer; if you must lock, add a fencing token.

2. Proxy bidding and ties

eBay's automatic bidding lets you enter the most you are willing to pay; eBay then bids for you in increments, only enough to keep you ahead, never above your maximum. Increments depend on the price (eBay's table runs from $0.05 for prices under $1 to $100 for prices of $5,000 and up).

  • Store the leader's secret maximum on the auction row (leader_max), never shown to others.
  • New bid with max M from a different bidder: if M > leader_max, the new bidder leads at min(M, leader_max + increment); else the old leader stays and the price rises to min(leader_max, M + increment), recorded as an automatic bid. Both outcomes are one conditional update on the row.
  • Ties: the earlier bid wins. With a total order (seq) this is unambiguous: whoever reached the row first holds the lead. Never use client timestamps.
  • Proxy bidding also reduces sniping pressure, because a sniper must beat your maximum, not your last visible bid.

3. Closing exactly at the end time, and anti-sniping

  • The bid check enforces the end, not the closer. now() < ends_at in the conditional update, using the database's clock (one clock, no skew between app servers). A bid at 10:00:00.001 is rejected even if the closer has not run yet.
  • Closer: poll auction_ending index every second (ends_at <= now() AND status='LIVE', with SKIP LOCKED across instances), or schedule a delayed message per auction at ends_at (a Redis sorted set by end time, or a delay queue). On firing, re-read: if ends_at moved (soft close), reschedule; else UPDATE ... SET status='CLOSED' WHERE status='LIVE' AND ends_at <= now(). Conditional, so duplicates are harmless.
  • 10M auctions spread their end times, but sellers like round times (Sunday 20:00). Shard the closer by auction id and size it for the busiest minute: say 50K auctions ending at 20:00 closed within a few seconds = tens of thousands of conditional updates, spread over shards.
  • Anti-sniping options: soft close (extend by N seconds when a bid lands in the last N seconds; many auction sites do this), proxy bidding (eBay keeps a fixed end time and relies on automatic bids), or a sealed final phase. The extension is part of the bid's conditional update: ends_at = GREATEST(ends_at, now() + soft_close). Cap total extensions if the business wants a hard stop.
  • Announce the new endsAt in every price event, so all clients count down to the server's time, not their own guess.

4. Real-time updates to watchers

An accepted bid produces one event; a hot auction may have 100K watchers. Pattern: clients open SSE (one-way is enough) or a WebSocket to a gateway; the gateway subscribes to Redis channel auction:{id} while it has watchers for that auction; the publisher sends {version, price, bidCount, endsAt}. Because Redis pub/sub is at-most-once, every message carries the version and clients refetch GET /auctions/{id} on a gap or reconnect. For a hot auction, coalesce: send at most a few updates per second per auction (the latest state wins); watchers do not need every intermediate bid, only the current price. Polling every 2 to 5 seconds is a valid fallback and an honest SDE-1 answer. Full treatment in Real-time Updates and Live Comments.

5. Settlement: winner, reserve, payment, second chance

  1. Reserve check If the final price is below the hidden reserve, the auction closes with no sale; seller and top bidder are told.
  2. Create the order Settlement creates an order and a payment request for the winner with an idempotency key auction_id, and a deadline (for example 48 hours). If the bidder has a saved payment method and agreed to auto-pay, charge immediately.
  3. Notify Winner, seller, and all other bidders ("auction ended").
  4. Non-payment After the deadline, mark EXPIRED, optionally offer the item to the second-highest bidder at their bid (second chance), and record the non-paying bidder (strike).
  5. Saga Payment success then order confirmed then seller payout after delivery. Each step has a compensating action (refund, relist). See Payment System and Multi-step Processes.

Consistency vs availability (a follow-up the Razorpay interviewer pushed): bids are CP. If the auction's shard leader is unreachable, reject bids for that auction ("try again") rather than accept them on a replica that might disagree. Browsing, search and the live price feed are AP: show slightly stale data rather than an error. Saying exactly where you draw that line is the answer.
