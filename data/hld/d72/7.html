Where Kafka, Kubernetes and Docker fit

Concrete settings. Partition key auction_id is the serialisation point: one partition has one consumer in the group, so each auction's bids are applied in order with no locks. Consumer-group sizing: 32 partitions allow 32 bid processors; more partitions spread more auctions but never split one hot auction. API pods scale on CPU and latency; SSE gateways on connection count with a graceful drain.

  • Kafka: auction.events keyed by auction_id (bid accepted, auction closed) from the outbox; consumers: pub/sub publisher, notifications, search indexer, analytics. In the queue-based bid design, bids.in keyed by auction_id is the serialisation point: one partition has one consumer in a group, so each auction's bids are processed in order with no locks. A hot auction stays on one partition (a single consumer handles thousands of simple bids a second); add partitions for more auctions, not for one auction. See Kafka.
  • Kubernetes: Bid service and Auction service as Deployments scaled on CPU and latency; SSE/WebSocket gateways scaled on connection count with graceful drain; the closer as a Deployment with sharded ownership (lease per shard) rather than a single CronJob; Elasticsearch via its operator or a managed service.
  • Docker: images per service; a compose file with PostgreSQL, Kafka, Redis and Elasticsearch plus a load script that fires 1,000 concurrent bids at one auction is the best way to prove your conditional update works.
