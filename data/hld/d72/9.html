60-second answer, said out loud: "Sellers create auctions through an Auction service; changes flow by CDC into Elasticsearch for search. The bid path is the core: the auction row holds current price, leader, the leader's secret maximum, ends_at and a version, sharded by auction id. A bid is one conditional update: status live, now before ends_at by the database clock, amount at least price plus increment; it bumps the version, extends ends_at in the soft-close window, and appends the bid with seq equal to the version, all in one transaction. Losers get TOO_LOW with the next minimum. For a single auction with thousands of bids a second, I move its bids onto a Kafka partition with one consumer. Accepted bids go through an outbox to Kafka, then Redis pub/sub to SSE gateways, versioned so clients refetch on gaps. A closer closes auctions with a conditional update when ends_at passes; settlement charges the winner idempotently and falls back to a second-chance offer."

SDE-1 stops here / SDE-2 adds. SDE-1: entities and tables, the bid API, a transaction or lock so two bids cannot both win, a scheduled job that closes auctions, polling for the live price, search with Elasticsearch. SDE-2 adds: the single-statement conditional update and why read-then-write fails, queue-per-auction serialisation for hot items, proxy bidding and tie rules, enforcing the end in the bid check with one clock, soft close inside the same update, versioned push with coalescing, idempotent settlement and the CP-vs-AP split.

Follow-up questions

Two bidders bid at the same millisecond. How do you resolve the conflict?

Make the check and the write one atomic operation on the auction row: UPDATE ... WHERE current_price + inc <= :amount AND status='LIVE' AND now() < ends_at. The database serialises the two updates on the row; the first commits and bumps the version; the second re-evaluates the condition against the new price and either succeeds (if still high enough) or returns 0 rows and is rejected with the new minimum. The version becomes the bid's sequence number, so there is one total order; equal maximums are won by the earlier sequence.

How to answer

Show the lost-update race first, then the conditional update, then "and if this one auction is very hot, a Kafka partition per auction".

Likely follow-ups
  • Why not a distributed lock? (Expiry under pauses lets two writers in; a conditional write inside the data store has no such gap.)
  • How does DynamoDB do it? (ConditionExpression; ConditionalCheckFailedException on failure.)
Consistency or availability for bids? What about the rest?

Bids: consistency. One leader per auction shard; if it is unavailable, reject bids for that auction briefly instead of accepting them somewhere that could diverge. Reads (item pages, search, live price): availability with bounded staleness, served from replicas, caches and the search index. The bid response itself always reflects the authoritative row.

How to answer

Name the split explicitly and give the user-facing behaviour for each during a failure.

Likely follow-ups
  • Multi-region? (Home each auction in one region; bids from elsewhere route there; reads are local.)
A celebrity auction gets thousands of bids per second in its final minute. What changes?

The conditional update still gives correct answers but many bids lose and retry against one row. Move that auction's bids to a Kafka partition keyed by auction id with a single consumer that holds the current state in memory and writes results in order; the API returns 202 and the client gets the result over the stream or by polling the bid id. Alternatively a Redis Lua check-and-set with durable write-behind. Also coalesce price pushes to a few per second.

How to answer

Show you know the cost: asynchronous result and more components, worth it only for hot auctions. You can route only flagged hot auctions this way.

Likely follow-ups
  • What if the consumer crashes? (Another takes the partition, rebuilds state from the DB, resumes from the committed offset; processing is idempotent by bid id.)
How do you close auctions exactly at the end time?

Two parts. Correctness: the bid's conditional update includes now() < ends_at using the database clock, so no bid is accepted late regardless of the closer. Announcement: a closer polls the partial index on ends_at for live auctions every second (SKIP LOCKED across instances) or fires delayed messages per auction, re-reads ends_at (it may have moved), and runs LIVE -> CLOSED conditionally, then emits auction.closed for settlement and notifications.

How to answer

Separate "who wins" (decided by the bid check) from "when we announce" (closer). That shows real understanding.

Likely follow-ups
  • 50K auctions end at 20:00 Sunday. (Shard the closer; each shard closes its slice in parallel.)
How do you stop sniping?

Offer proxy bidding so honest bidders can set a maximum in advance, and optionally a soft close: a bid in the last N seconds sets ends_at = max(ends_at, now() + N) inside the same conditional update, and every price event carries the new end time. Cap the number of extensions if needed. eBay itself keeps a fixed end and relies on automatic bidding; many other auction sites use soft close.

How to answer

Give both mechanisms and the one-line SQL change.

Likely follow-ups
  • Does the closer need to know? (It re-reads ends_at before closing and reschedules.)
Walk me through the entities, data model and why you chose SQL or NoSQL.

User (with role), Item, Auction (prices, times, status, denormalised current price, leader, leader max, bid count, version), Bid (append-only, seq per auction, idempotency key), Watch, Settlement. SQL fits: relational data, transactions spanning the auction row and the bid insert, unique constraints. Shard by auction id so the hot transaction stays on one shard. DynamoDB also works: auction item plus bid items in one partition key with conditional writes and a transaction; then search and "my bids" need secondary indexes or Elasticsearch.

How to answer

Derive the store from the bid transaction, not from habit.

Likely follow-ups
  • How do you show "my active bids"? (Secondary index by bidder, or an event-built read model.)
How does search with Elasticsearch stay in sync with live prices?

The database is the source of truth; CDC or an outbox publishes auction changes to Kafka; an indexer updates the Elasticsearch document (price, bid count, ends_at, status). It is near real time and eventually consistent; the item page reads the database or cache. For price changes on hot auctions, batch index updates (at most one per auction per few seconds) to avoid hammering the index.

How to answer

Say "never dual-write from the bid path" and why (partial failures).

Likely follow-ups
  • Sort by "ending soon"? (Index ends_at; filter status LIVE.)
How do watchers see the new price in real time?

SSE or WebSocket from browser to a gateway; gateway pods subscribe to auction:{id} in Redis while they have watchers; the publisher sends versioned events from the outbox stream. Clients drop events with an older version and refetch on gaps or reconnects (Redis pub/sub is at-most-once). Coalesce to a few updates per second per hot auction. Fall back to polling every few seconds.

How to answer

Draw publisher, Redis, two gateway pods, clients. Mention versions.

Likely follow-ups
  • Why SSE over WebSocket? (Updates are one-way; bids go over normal POST.)
The winner does not pay. What happens?

Settlement creates the order and payment request with a deadline and an idempotency key. On expiry, mark the settlement EXPIRED, record a strike against the bidder, and offer the item to the next-highest distinct bidder at their bid (second chance) or relist. Every step is a state transition with a compensating action, run as a saga.

How to answer

Show the settlement state machine and reuse the payment service.

Likely follow-ups
  • Auto-charge at close? (Possible with a saved method and consent; still idempotent by auction id.)

Scenario drills

Scenario: two people were told they won

A customer complaint: both bidders received "You are the highest bidder" in the last second, and the final price is the lower bid.
Weak answer: "Add a cache so reads are faster."
Strong answer: classic lost update. The bid service read the price, checked in application code, then wrote unconditionally. Fix with the conditional update (check inside the write) and return "leading" only from the row the update returned. Repair data from the bid log (append-only, sequenced), contact both bidders, and add a test that fires concurrent bids at one auction.
Follow-ups
  • How would you detect it in production? (Invariant check: final price equals the maximum accepted bid; alert if not.)

Scenario: bids accepted after the end

An auction ended at 20:00:00 but a bid timestamped 20:00:02 won.
Weak answer: "Run the closer more often."
Strong answer: the bid path trusted the closer (checked status only) or used app-server clocks. Put now() < ends_at in the conditional update with the database clock; then the closer's speed no longer matters for correctness.
Follow-ups
  • What about network latency for a bid sent at 19:59:59.9? (Server receipt time is the rule; say so in the terms.)

Common mistakes

  • Read-then-write bid logic, or computing the high bid with SELECT max(amount) on every bid.
  • Relying on the closer job to stop late bids.
  • Using client timestamps for ordering or ties.
  • Writing to Elasticsearch directly from the bid transaction (dual write).
  • Treating total bid throughput as the scale problem and ignoring the single hot auction.
  • Forgetting reserve price, settlement and non-payment.
  • Saying "eventual consistency everywhere".
