Data model

One database cannot be good at everything, so we pick a store per access pattern. This is the one-sentence rule to say: "Transactions go to SQL, search goes to a search index, hot moving data goes to memory, and history goes to a log."

-- Orders: the money and the promise. Shard by order_id (hash) when one primary is not enough.
CREATE TABLE orders (
  order_id        BIGINT PRIMARY KEY,          -- Snowflake-style id, time sortable
  idempotency_key UUID   NOT NULL UNIQUE,      -- one row per checkout attempt, ever
  customer_id     BIGINT NOT NULL,
  restaurant_id   BIGINT NOT NULL,
  rider_id        BIGINT,                      -- NULL until assigned
  city_id         INT    NOT NULL,
  status          TEXT   NOT NULL,             -- PLACED, CONFIRMED, ACCEPTED, ...
  total_paise     BIGINT NOT NULL,             -- integer money, never float
  prep_minutes    INT,
  promised_eta    TIMESTAMPTZ,
  version         INT    NOT NULL DEFAULT 0,   -- optimistic concurrency
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON orders (customer_id, created_at DESC);   -- "my orders"
CREATE INDEX ON orders (restaurant_id, status);          -- restaurant tablet queue

-- Every state change is also appended here (audit + debugging "where did my order go?")
CREATE TABLE order_events (
  order_id BIGINT, seq INT, from_status TEXT, to_status TEXT, actor TEXT, at TIMESTAMPTZ,
  PRIMARY KEY (order_id, seq)
);

-- Outbox: written in the SAME transaction as the order change, relayed to Kafka
CREATE TABLE outbox (
  id BIGSERIAL PRIMARY KEY, aggregate_id BIGINT, event_type TEXT, payload JSONB, created_at TIMESTAMPTZ DEFAULT now()
);

New word - outbox: events are written into this table inside the same transaction as the order, so the event and the order can never disagree (both saved or neither). A small relay process (or a CDC tool reading the database log) then copies new rows to Kafka. The full story is in deep dive 4 below; for now, read "outbox row" as "an event waiting to be published".
