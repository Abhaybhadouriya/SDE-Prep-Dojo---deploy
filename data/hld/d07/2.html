Back-of-envelope estimation

We will use the cheat-sheet rule from estimation: one day is 86,400 seconds, which we round to 100,000 (105) seconds. Numbers marked assumption are ours, chosen to be round and believable. Say "let me assume" in the interview, and the interviewer will correct you if they want a different scale.

A. Orders

  1. Daily orders (assumption). 3 million orders a day for one large country.
  2. Average rate. 3,000,000 / 100,000 s = 30 orders per second.
  3. Dinner peak (assumption). Food orders bunch up at lunch and dinner. Assume the peak hour is 5x the average: about 150 orders/s.
  4. Sanity check with a real number. Zomato's CEO reported a peak of 4,254 orders per minute on New Year's Eve 2020 (reported by The Week). 4,254 / 60 = about 71 orders per second. So our 150/s is about 2x that reported peak, a realistic big-night number with room for growth. Design for 2x headroom: 300 orders/s.
  5. Lesson. 300 writes per second is small for one well-tuned SQL primary. The order table is not our scaling problem. Keep this in mind, because it changes where we spend our interview time.

B. Browsing (reads)

  1. Reads per order (assumption). People scroll a lot before they order. Assume 50 search, list or menu requests per placed order.
  2. Read rate. 3M x 50 = 150M requests a day, so 150M / 105 = 1,500 reads/s on average, and about 7,500 reads/s at the 5x peak.
  3. What it means. Reads are about 50x the writes. Cache menus and restaurant cards hard, and put search on a search index (Elasticsearch / OpenSearch), not on the order database.

C. Rider locations (the real write load)

  1. Riders online at peak (assumption). 250,000.
  2. Ping interval. Uber drivers were reported to send GPS about every 4 seconds. Assume the same for riders.
  3. Write rate. 250,000 / 4 = 62,500 location writes per second. That is 200x the order rate.
  4. Where they go. Only the latest location matters for matching, so keep it in memory (Redis GEO or an in-memory geo index). Send the full stream to Kafka for tracking and analytics. Never write every ping as a row in the order database.

D. Tracking fan-out and storage

  1. Orders in flight. At 150 orders/s, and assuming 40 minutes from order to door (assumption), there are 150 x 2,400 s = 360,000 live orders at once.
  2. Tracking pushes. If each customer watching gets an update every 4 s, that is 360,000 / 4 = 90,000 pushes/s. At ~200 bytes each, that is about 18 MB/s of outgoing bandwidth. That is fine for a fleet of WebSocket gateways.
  3. Order storage. Assume 2 KB per order with its items and status history: 3M x 2 KB = 6 GB a day, about 2.2 TB a year, about 6.6 TB with 3 replicas. Easy.
  4. Location history. Average maybe 100,000 riders online: 25,000 pings/s x 86,400 s = about 2.2 billion pings a day. At ~100 bytes each, that is about 216 GB a day. Keep a few days in Kafka, and move the rest to cheap object storage for ML training.

From your world

This is a control plane vs data plane split you already know. Orders are the control plane: few messages, each one must be correct. Rider pings are the data plane: a huge, steady stream where losing one packet is fine because the next one arrives in 4 seconds, just like you would not retransmit a stale telemetry sample. Where the analogy breaks: a router drops data-plane packets silently, but here we still keep the stream in Kafka for replay and ML.
