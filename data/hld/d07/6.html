Deep dives

Stop here for SDE-1. If you can explain the stepper above with the idempotent order and the outbox, you have a solid SDE-1 answer. SDE-2 interviewers will push on the next five topics, usually two or three of them.

1. Rider assignment: why "nearest rider" is the wrong answer

The naive answer is "when an order comes in, find the closest free rider and assign them". It sounds fine and it fails in three ways:

  • Too early. The nearest rider arrives in 3 minutes, but the food needs 15. The rider stands idle for 12 minutes, and that rider could have delivered another order.
  • Greedy is unfair to later orders. Order A grabs rider R1, who is the only rider near restaurant B. Order B, a second later, now gets a rider 4 km away. Looking at both orders together would have given both a good rider.
  • No batching. Two orders from the same restaurant going the same way can share one rider. Greedy one-at-a-time matching never sees that.

The better answer is batched matching. Dispatch is split by zone (a group of H3 cells in one city area). Every short window (for example every 30-60 seconds, a tunable) it takes all unassigned orders and all free or soon-free riders in the zone and builds a cost for each (order, rider) pair:

# cost of giving `order` to `rider` (lower is better); weights are tuned with experiments
def cost(order, rider):
    t_to_restaurant = eta_service.travel(rider.location, order.restaurant)   # road ETA, not straight line
    t_food_ready    = order.ready_at - now()
    rider_wait      = max(0, t_food_ready - t_to_restaurant)     # rider idles at the kitchen
    food_wait       = max(0, t_to_restaurant - t_food_ready)     # food goes cold on the counter
    t_to_customer   = eta_service.travel(order.restaurant, order.customer)
    return (W_FOOD * food_wait          # the customer cares most about this
          + W_RIDER * rider_wait        # wasted fleet capacity
          + W_LATE * max(0, now() + t_to_restaurant + rider_wait + t_to_customer - order.promised_eta))

Then it solves an assignment problem (a minimum-cost bipartite matching, for example with the Hungarian algorithm or a min-cost-flow solver, or a fast heuristic at large sizes). Swiggy's Akka case study describes exactly this shape: scoring every order-and-rider pairing for a city and returning the batch inside a one-minute SLA.

Locking the rider. Two zones or two dispatch workers must never offer the same rider two jobs. Store rider status in Redis and flip it atomically, with a TTL so a crashed dispatcher does not freeze a rider forever:

127.0.0.1:6379> SET rider:17:offer o_81234 NX EX 30
OK
127.0.0.1:6379> SET rider:17:offer o_99999 NX EX 30
(nil)
127.0.0.1:6379> TTL rider:17:offer
(integer) 27

NX means "only set if the key does not exist", so the second offer fails. EX 30 is the 30-second offer timeout. When the rider accepts, the order service writes the assignment to SQL with a conditional update (... WHERE status = 'ACCEPTED' AND rider_id IS NULL), so even a bug in Redis cannot assign two riders to one order.

From your world

Batch matching is a scheduler, the same shape as the Kubernetes scheduler (filter feasible nodes, then score them) or admission control that places a flow on a line card with spare capacity. The time window is like interrupt coalescing: wait a little to batch work, and get much better decisions for a small latency cost. Where it breaks: riders can say no, so every placement is only an offer until they accept.

2. The ETA is a sum of predictions

"Your food will arrive in 32 minutes" is a promise. If you promise too low, customers are angry. If you promise too high, they order elsewhere. The ETA is built from parts, and each part has its own model:

  • Prep time is the hardest. The restaurant's own estimate is often wrong, so a model uses the dish mix, the restaurant's history at this hour, and how many orders it has open right now.
  • Travel time comes from a routing service on the road graph with live traffic (see Google Maps design), never straight-line distance.
  • Last mile (parking, finding the gate, the lift in an apartment block) is learned per building or area from past deliveries.
  • Re-estimate continuously. After pickup, the ETA is recomputed from live pings every few seconds. Smooth the number shown to the user, so it does not jump around.

Model serving is its own system. Swiggy's vendor case study reports P99 prediction latency dropping from 144 ms to 71 ms at more than 5,000 predictions per second on one model. That is a useful reminder that ML calls sit on the hot path and need latency budgets like any other dependency. Read more in surge pricing and ETA.

3. Geo: "who can deliver to me?" and "which riders are near?"

These are two different geo questions:

  • Serviceability (static-ish): each restaurant has a delivery polygon, which can shrink at peak. Precompute the set of H3 cells each polygon covers and index restaurants by cell. A customer query becomes "restaurants indexed under my cell", which is one fast lookup or an Elasticsearch terms filter. Uber's H3 uses hexagons at 16 resolutions, and each finer level has about 1/7 of the area.
  • Nearby riders (moving): riders move every few seconds, so use an in-memory geo index. Redis GEOADD / GEOSEARCH (a geohash in a sorted set) is the simplest real option. Shard it by city, because riders never cross cities mid-shift.

Try it locally with docker run -d -p 6379:6379 redis:7 and redis-cli:

127.0.0.1:6379> GEOADD riders:blr 77.6420 12.9716 rider:17 77.6310 12.9650 rider:42 77.6650 12.9900 rider:88
(integer) 3
127.0.0.1:6379> GEOSEARCH riders:blr FROMLONLAT 77.6400 12.9700 BYRADIUS 3 km ASC WITHDIST
1) 1) "rider:17"
   2) "0.2805"
2) 1) "rider:42"
   2) "1.1229"

rider:88 is about 3.5 km away, so it is not returned. (The last digit of a distance can differ slightly, because Redis stores positions as 52-bit geohashes.) Two gotchas: a rider who stops pinging still sits in the set, so also keep rider:{id}:alive with a short TTL and filter on it. And a geohash cell boundary can split two points that are very close, so a radius search must also look at the neighbouring cells (Redis does this for you; your own grid index must do it too).

From your world

A geohash prefix is like an IP prefix: a longer prefix means a smaller area, and "same prefix" usually means "near". Two adjacent addresses can sit on different sides of a /24 boundary, and two neighbouring points can sit in different geo cells, which is why you check the neighbours. Deeper detail is on the geo indexes page.

4. The order state machine and exactly-once transitions

An order is a small state machine. Many actors push it forward (the payment callback, the restaurant tablet, dispatch, the rider app), and many of them retry. The rule is: every transition is a conditional update from an expected state, so retries and races are harmless.

-- One statement (PostgreSQL): the outbox INSERT only sees rows the UPDATE actually changed.
WITH moved AS (
  UPDATE orders
     SET status = 'RIDER_ASSIGNED', rider_id = 17, version = version + 1
   WHERE order_id = 81234 AND status = 'ACCEPTED' AND rider_id IS NULL
  RETURNING order_id
)
INSERT INTO outbox (aggregate_id, event_type, payload)
SELECT order_id, 'rider.assigned', '{"riderId":17}' FROM moved;
INSERT 0 1      -- first attempt: the order moved, so exactly one outbox row is written
INSERT 0 0      -- the retry: the WHERE matched 0 rows, "moved" is empty, so no outbox row either

Why not a plain UPDATE followed by an INSERT? Because the INSERT would run on the retry too and write a duplicate rider.assigned event. If you prefer two statements, the app must check rows affected: if cur.rowcount == 1: insert the outbox row and COMMIT, else: ROLLBACK. The single statement above makes that rule impossible to forget.

The outbox row commits together with the status change, so the Kafka event can never be "lost after commit" or "sent for a rollback". This is the transactional outbox, explained on distributed transactions and events. Consumers still dedupe by (orderId, eventType), because the relay is at-least-once.

5. Peaks: the bottleneck is riders, not servers

On New Year's Eve 2020, Zomato's CEO said publicly that they "ran out of delivery partner capacity" before the peak. No amount of autoscaling creates more riders. A strong answer treats peak as a supply problem and shows how the system degrades on purpose:

  • Honest ETAs. When riders are scarce, the ETA model sees it and the promise goes up. That alone moves some demand.
  • Shrink serviceable areas. Turn off far-away restaurants for a cell (fewer long trips means more deliveries per rider-hour).
  • Kitchen throttles. Cap open orders per restaurant. A kitchen with 40 pending orders should stop appearing at the top of the list.
  • Surge or "high demand" fee and rider incentives for that zone and hour.
  • Admission control. In the worst case, show "we are very busy, try in 10 minutes" before the cart, never after payment.
  • Pre-scale the tech anyway. Discovery, gateways and tracking get pre-scaled before known peaks, because autoscalers react in minutes and the dinner spike arrives in minutes too.

Interviewers love the line "Autoscaling fixes CPU, not riders." Then list the levers above. It shows product thinking, not just boxes.
