Back-of-envelope estimation

These are our own round-number assumptions for a large social app (state them out loud; round a day to 100,000 seconds as in Estimation).

  1. Users. Assume 500M daily active users (DAU).
  2. Like writes. 20 likes per user per day = 10B likes/day. 10B / 100K s = 100K likes/s average. Assume peak = 3x = 300K/s.
  3. View writes. 50 views per user per day = 25B/day = 250K views/s average.
  4. Count reads. Each user scrolls past 200 posts a day and each shows a count: 500M x 200 = 100B reads/day = 1M count reads/s. Reads are ~10x writes - the same ratio systemdesign.one assumes.
  5. The hot key. Average load is not the problem; skew is. Assume one celebrity post peaks at 50K likes/s. DynamoDB documents a ceiling of 1,000 write units per second per partition. 50K / 1K = at least 50 shards for that single counter; pick 64-100 for headroom. A normal post needs 1.
  6. Counter storage. 10B posts with counters x ~64 bytes (key + 8-byte count + overhead) = ~640 GB. Small; fits in a modest sharded cluster or largely in cache.
  7. Like edges (who liked what). Needed for dedup and hasLiked. 10B/day x 365 = 3.65T edges/year x ~24 bytes (user_id, post_id, timestamp) = ~88 TB/year raw. This, not the count, is the big table.
  8. Unique viewers. A Redis HyperLogLog is at most 12 KB. 100M "active" videos x 12 KB = 1.2 TB worst case - but small HLLs use a compact sparse form, so real usage is far lower. An exact set of 64-bit ids for a video with 10M viewers alone would be 80 MB.
  9. Event bandwidth. (300K + 250K) events/s x ~100 bytes = ~55 MB/s into Kafka - easy for a few brokers.

The punchline of the estimate: total storage is tiny and total throughput is ordinary. The only hard number is "writes per second on one key". Say that sentence; it tells the interviewer you found the real problem.
