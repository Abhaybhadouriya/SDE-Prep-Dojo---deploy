Deep dives

1. The hot key: why one row cannot keep up

An increment is a read-modify-write. To be correct, the database must serialise every update to the same row: a row lock in MySQL/Postgres, a compare-and-swap loop, or one leader replica for that partition key. Adding machines does not help - the key lives on one partition. Netflix's write-up names the same three problems with "a single row per counter": heavy contention, no idempotency, and the need for secondary keys (buckets) to spread load.

The ladder of fixes, from cheapest to most complex:

2. Sharded counters done right

  • Random vs calculated shard. AWS's DynamoDB guide shows both: a random suffix (say 1-200) spreads writes best, but reads must query every suffix; a calculated suffix (hash of something you know) lets you find one item again. For counters you never read one shard alone, so random (or round-robin per writer) is right.
  • How many shards? Write rate on the key / safe rate per shard. Google's Firestore sample notes each shard document handles roughly one increment per second, so 10 shards give about 10x; DynamoDB's partition limit is 1,000 writes/s. Our 50K/s post needs at least 50 on DynamoDB; on Redis (much higher per-key rate) far fewer.
  • Do not shard everything. TAO's numbers say most counts are tiny. Start every counter with 1 shard and split hot keys dynamically: when a key's write rate crosses a threshold, raise its shard count in a small metadata map that writers cache. Shrinking is a merge: stop writing old shards, fold them into one.
  • Reads. Firestore's own doc warns that read cost grows linearly with shards and suggests a separate roll-up document. That is the rollup box above.

systemdesign.one's version of the same trick appends a random two-digit suffix to the page id, splitting one key into 100 keys, and accepts that a read must touch all 100. The rollup removes that read cost.

Level 4 - Advanced (deep dives 3-6)

3. Batching and the "immutable window" (Netflix's approach)

Netflix (Nov 2024) tried four simpler designs before settling on one. Per-instance in-memory aggregation lost data on crashes and deployments. A durable queue (Kafka partitions keyed by counter) fixed loss but made auditing and recounting impossible once counts were pre-aggregated. A raw log of every increment was auditable but made reads slow and partitions wide. Their final design combines them:

  1. Log every delta as an event with event_time + event_id in their TimeSeries store (Cassandra underneath), split by time_bucket and event_bucket so one hot counter does not create one giant partition. The time + id pair is the idempotency key: a retried write lands on the same row.
  2. Send a tiny "rollup event" (just namespace + counter name, no delta) to an in-memory queue on a rollup server. A fast hash (XXHash) sends the same counter to the same queue, and events are drained into a set, so a counter touched 10,000 times in a window is rolled up once.
  3. Aggregate only inside an immutable window: from lastRollupTs up to "now minus a safety lag". The store rejects events with timestamps beyond an accept_limit (5 s in their sample config), so nothing new can land inside a window being summed. Races between two rollup servers are then harmless - both compute the same answer.
  4. Store the result (count + rollup timestamp together) in a rollup table and cache it in EVCache. Reads are one point read. The "experimental accurate" counter adds the delta since the last rollup at read time.

Netflix reports this service handling close to 75K count requests per second globally with single-digit millisecond latency. The cost is lag: counts trail reality by seconds. Their sample config keeps raw events for 7 days, then relies on the rollups.

4. Idempotency: count every like exactly once

Networks retry. A mobile client times out and resends; a Kafka consumer crashes after writing but before committing its offset and reprocesses. Each turns into a double count unless the design is idempotent at every hop:

  • Client to like service: the edge table's unique key (post, user) makes "like" naturally idempotent. For views, a client-generated event_id does the same job.
  • Service to Kafka: only emit when the edge insert actually created a row. Use the outbox table or CDC so "row written" and "event sent" cannot diverge (see Distributed transactions & events and CDC pipeline).
  • Consumer to counter store: either use Kafka transactions / exactly-once (read-process-write with offsets committed in the same transaction - see Delivery semantics), or store the last applied offset per partition next to the counter and skip anything older.
  • Repair: because edges are the truth, a nightly batch can recount COUNT(*) per post and correct drift. SoundCloud's "Stitch" did exactly this: a speed layer with Cassandra counters for live numbers plus Hadoop batch jobs that regenerate correct buckets after bugs or outages.

Redis INCR and Cassandra counters are atomic but not idempotent. "Atomic" means two increments never collide; it does not mean a retried increment is ignored. Interviewers like to probe this difference.

5. Views and unique viewers: HyperLogLog

"How many different people watched this?" needs deduplication. An exact set costs memory proportional to viewers (8 bytes per 64-bit id, so 80 MB for 10M viewers - per video, per day). HyperLogLog (HLL) hashes each id and remembers, per bucket, the longest run of leading zeros it has seen; rare long runs mean many distinct items. Redis documents its HLL as using at most 12 KB with a 0.81% standard error, able to count up to 2^64 items, with PFADD (add), PFCOUNT (estimate) and PFMERGE (union).

PFADD  hll:video:9f2:2026-11-23  user:101 user:202 user:101   # duplicate ignored
PFCOUNT hll:video:9f2:2026-11-23                              # -> 2 (approx)
PFMERGE hll:video:9f2:week  hll:video:9f2:2026-11-17 hll:video:9f2:2026-11-23

Limits to say out loud: HLL cannot remove an item (no "unview"), so it suits views, not likes. Count-min sketch can add and subtract amounts but over-estimates. Netflix explicitly chose not to use probabilistic structures for its general counters because they do not natively support resets or TTLs per key. For billing, never approximate.

6. Read-your-writes and multi-region

  • Your own like must stick. The total may lag seconds, but if you like a post and refresh, the heart must still be red. Two cheap tricks: (a) liked_by_me comes from the edge table (read from the leader or the same region for a short time after a write), and (b) the client adds its own pending +1 to the displayed number until the server count catches up.
  • Monotonic reads. Do not show 1,204 then 1,198 because two replicas lag differently. Pin a session to one replica/region, or never display a value older than one already shown (keep last_rollup_ts with the count).
  • Multi-region. Each region counts locally and replicates its own tally: a G-counter (grow-only) or PN-counter (separate positive and negative tallies) CRDT. Merge = per-region max, then sum, which is commutative and idempotent, so duplicate replication messages do no harm. Cloudflare's rate limiter makes the same choice for request counts: it counts locally in each data centre, because anycast keeps a client on one PoP and a global counter would add latency and an availability risk.
