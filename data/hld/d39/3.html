Key APIs

POST   /v1/posts/{post_id}/likes          (user from auth token)
       Idempotency-Key: <uuid>             -> 200 {liked: true, count: 1204331}
DELETE /v1/posts/{post_id}/likes          -> 200 {liked: false, count: 1204330}
GET    /v1/counts?ids=p1,p2,...,p50       -> {p1: {likes: 1204331, views: 9.8e6, liked_by_me: true}, ...}

# view events are fire-and-forget, batched by the client
POST   /v1/events/views   [{video_id, ts, session_id}, ...]  -> 202 Accepted

# internal counter service (like Netflix's Counter Abstraction)
AddCount(namespace, counter, delta, idempotency_token{event_id, event_time})
GetCount(namespace, counter)
ClearCount(namespace, counter, idempotency_token)
  • Like is a set operation, not "+1". The client says "user U likes post P". The server turns that into +1 only if the (U, P) edge did not already exist. Retrying the same request is harmless by design.
  • Batch reads. A feed screen needs 20-50 counts, so GET /counts?ids=... fetches them in one call (multi-get from cache).
  • Views return 202: accepted for counting later. Nobody waits for a view to be counted.
  • The internal API mirrors Netflix's (published Nov 2024): AddCount takes a delta (can be negative) and an idempotency token so clients can safely retry or hedge.
