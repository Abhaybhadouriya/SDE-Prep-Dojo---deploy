Quick quiz

A system handles 100K likes/s in total without trouble, but one viral post at 50K likes/s breaks it. Why?

  1. Kafka tops out near 50K messages/s, so the topic itself is full
  2. Writes to one key serialise on one row, whatever the cluster size
  3. The database runs out of disk, because each like is a new row
  4. The load balancer pins that post's users to one overloaded API pod
A key lives on one partition. Adding nodes spreads different keys, not one key.

What is the main cost of a sharded counter with 64 shards?

  1. Writes get slower, since each one must lock all 64 shards
  2. It can count only up to 64, one unit per shard
  3. A read must sum 64 values unless you keep a rollup
  4. Shards drift apart, so the total is never exact
Writes parallelise; reads fan out. A rollup brings reads back to one point lookup.

Which makes "like" safe to retry?

  1. Using Redis INCR, because an atomic increment cannot double count
  2. A longer client timeout, so the client never needs to retry
  3. Wrapping the counter update in a database transaction
  4. Insert the (post_id, user_id) edge with a unique key; count new rows only
Atomic operations do not ignore duplicates. A unique key does.

Why is HyperLogLog a poor fit for like counts?

  1. It cannot remove an item, so "unlike" is impossible
  2. It uses too much memory: about 12 KB per counter is too big
  3. It only counts up to about a million distinct items
  4. Its error is too high: roughly 10% on every count
HLL estimates distinct items added; it has no delete. Fine for views, wrong for likes.

In Netflix's rollup design, why aggregate only up to "now minus a lag"?

  1. To save CPU, since recent events are rolled up by a cheaper job
  2. Because Cassandra cannot read data written in the last few seconds
  3. So the window is immutable and racing rollups agree
  4. To give EVCache time to expire stale values before the rollup
The accept limit rejects events beyond the boundary, making the summed range fixed.

Adding Kafka partitions did not fix lag for one viral post. What does?

  1. Increase retention so the consumer can catch up later
  2. Pre-aggregate in the producer or salt that post's key
  3. Switch the producer to acks=0 to cut send latency
  4. Add consumers beyond the partition count to share the load
One key always hashes to one partition. Spread the key or shrink its event count.

A PN-counter merges two replicas by...

  1. Adding both replicas' totals together
  2. Keeping the value with the newest timestamp
  3. Summing every increment message both replicas have received
  4. Max of each replica's P and N slot, then summing
Max per slot is idempotent and commutative, so duplicate messages are harmless.

The like service writes the edge row to the database and then publishes the +1 event to Kafka. The process crashes between the two. What prevents a lost or phantom count?

  1. Kafka's idempotent producer, which retries the send after restart
  2. A two-phase commit across the database and Kafka on every like
  3. The outbox pattern or CDC: the event comes from the database's own committed change
  4. Writing the event to Kafka first, then the database row
With an outbox, the event row is written in the same DB transaction as the edge, and a relay publishes it; with CDC, a connector tails the write-ahead log. Either way the event exists exactly when the edge commits. The idempotent producer only dedups retries of a send that already started.
