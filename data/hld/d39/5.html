Architecture: like path and read path

Click Next or Play. Steps 1-5 are the write path for a like, step 6 is views, steps 7-8 are the read path.

  1. Tap. The app sends POST /posts/42/likes. The like service authenticates and rate-limits (stops a bot from liking 10K posts a minute).
  2. Dedup by edge. Insert (post 42, user U) into the edge table. If the row already exists, stop: the like is already counted. This unique key is what makes retries safe.
  3. Publish an event. Only a new edge produces {post 42, +1, event_id} to Kafka, keyed by post_id so all events for one post land in one partition, in order. (Use the outbox pattern or CDC so the DB write and the event cannot disagree. CDC, change data capture, tails the database's write-ahead log and publishes each committed row change to Kafka; the outbox pattern writes the event into an outbox table in the same DB transaction, and a small relay publishes it. Like a journal replay in a filesystem: the log is the truth and everything downstream is rebuilt from it.)
  4. Batch. A stream job (Kafka Streams / Flink) sums deltas per post over 1-5 second windows. 50K likes/s on post 42 become one +50,000 write per second.
  5. Write the counter. Most posts have one counter row. Known-hot posts get N shards (here 64); the aggregator adds to a random or round-robin shard and periodically writes a rolled-up total with its timestamp.
  6. Views are a separate, cheaper path. Player events go through a rules filter (drop bots, replays, refresh spam), then into a Redis HyperLogLog per video per day for unique viewers, with a raw view count alongside. Snapshots are written to durable storage every few seconds.
  7. Read. The feed asks for 50 counts at once. A cache multi-get answers almost all of them in about a millisecond.
  8. Miss and read-your-writes. On a miss, read the rolled-up count (one point read) rather than summing 64 shards. The client adds the user's own just-sent like locally, so the number they see is never "behind" their own action.

From your world

You already know this design from the Linux kernel: percpu_counter. Each CPU keeps its own local delta and only folds it into the shared global count when the delta passes a batch size, because hammering one shared cache line from 64 cores causes cache-line bouncing (the hardware version of a hot row). percpu_counter_read() is fast but approximate; percpu_counter_sum() walks every CPU for the exact value. Sharded counter = per-CPU slots; aggregator = batch fold; "read rollup vs sum shards" = read vs sum.
