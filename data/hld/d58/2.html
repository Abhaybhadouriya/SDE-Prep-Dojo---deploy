Back-of-envelope estimation

Hello Interview gives only "thousands of publishers". Google's 2007 personalisation paper says Google News then aggregated more than 4,500 sources and had several million unique visitors in a few days. Today's numbers are not public, so the figures below are our stated assumptions - in an interview you say them out loud and move on. (Method: Back-of-Envelope Estimation.) We use 100,000 seconds per day for easy maths (the real value is 86,400).

Ingestion (write side)

  1. Feeds. Assume 50,000 feeds (about 10,000 publishers x 5 section feeds each).
  2. Polling rate. Freshness target 30 minutes; we aim for a 5-minute average poll. 50,000 feeds / 300 s = about 170 fetches/s. Tiny. Polling cost is not the problem; politeness and wasted bytes are.
  3. Wasted bytes. An RSS file is maybe 50 KB. 170/s x 50 KB = 8.5 MB/s if we download every feed every time. With conditional GET (HTTP 304 Not Modified when nothing changed) most polls cost a few hundred bytes. That is a 10-100x saving.
  4. New articles. Assume 1 million new articles per day: 1,000,000 / 100,000 = 10 articles/s average, maybe 50/s at peak.
  5. Article metadata. URL, title, snippet, publisher, times, fingerprint, story id: about 2 KB. 1M x 2 KB = 2 GB/day, about 730 GB/year. Fits in one sharded table easily.
  6. Thumbnails. We store a resized copy, about 50 KB: 1M x 50 KB = 50 GB/day, about 18 TB/year. That goes to object storage plus a CDN, never to the database.

Reading (read side)

  1. Readers. Assume 100 million daily active users, each loading 10 feed pages a day: 1 billion feed requests/day.
  2. Average read QPS. 1,000,000,000 / 100,000 = 10,000 QPS. Peak (morning) about 3x = 30,000 QPS. Breaking news another 3-5x on top: plan for 100,000+ QPS bursts.
  3. Read:write ratio. 10,000 reads/s vs 10 article writes/s = 1,000 : 1. Precompute feeds; never run a ranking query per request.
  4. Response size. 20 cards x about 1 KB of JSON = 20 KB. 10,000 x 20 KB = 200 MB/s of JSON (images come from the CDN separately).
  5. Feed cache size. 200 regions x 20 categories = 4,000 feeds. Keep the top 1,000 story ids per feed: 4,000 x 1,000 x 16 bytes = 64 MB. The whole "board" fits in RAM on one Redis node; we replicate it only for throughput.
  6. Dedup index. Keep 30 days of 64-bit SimHash fingerprints: 30M x 8 bytes = 240 MB. Also fits in RAM. (Google's crawler kept 8 billion fingerprints in 64 GB - our problem is 300x smaller.)

From your world

This is the RIB vs FIB split from routing. The control plane (ingestion, dedup, ranking) is slow, complex and runs at 10 events per second. It computes a small, flat "forwarding table" - the precomputed feed lists - and pushes it to the data plane. The data plane (feed API + cache + CDN) only does lookups at 100,000 per second. Never let a lookup trigger route computation.
