Key APIs

# read path (served from cache)
GET /top-k?window=1h|1d|30d|all&k=100&category=books  -> [{itemId, count}]   # K <= 1000, no pagination

# write path (internal; clients just emit events)
POST /events   body: {itemId, eventType:"view"|"sale", ts, eventId}         -> 202

The write API is fire-and-forget: it validates, stamps the event and appends it to Kafka. The client never waits for a counter update. The eventId lets the pipeline drop duplicates if the client retries.

There are two read shapes. The global read (GET /top-k?window=1h&k=100) and the per-category read (&category=books) hit different precomputed keys in the cache (top-k:1h vs top-k:1h:books), so a category page never has to filter the global list. The response says which window it covers, when it was computed and whether the counts are approximate, so the client can show "as of 10:04" when the pipeline is behind:

{
  "window": "1h",
  "category": "books",
  "windowStart": "2026-11-23T09:00:00Z",
  "windowEnd":   "2026-11-23T10:00:00Z",
  "computedAt":  "2026-11-23T10:04:12Z",
  "approximate": false,
  "items": [
    {"rank": 1, "itemId": "b-9781", "count": 48211},
    {"rank": 2, "itemId": "b-1203", "count": 47002}
  ]
}

approximate is true when the list came from the count-min sketch path (deep dive 3) and false when it came from exact per-item counts. There is no pagination: K is at most 1,000, so the whole list is about 16 KB (1,000 x ~16 bytes of id + count) and fits in one cached response.
