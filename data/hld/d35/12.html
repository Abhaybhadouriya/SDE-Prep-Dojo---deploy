Quick quiz

When is merging each shard's local top-K guaranteed to give the exact global top-K?

  1. Always, as long as every shard reports at least K items
  2. When K is larger than about 100, so ties no longer matter
  3. When each item's full count lives on exactly one shard
  4. When events are spread round-robin so shards stay balanced
If an item's count is split across shards, it can sit just below the cut on every shard yet be first overall. Round-robin is exactly the split case.

A count-min sketch estimate for one item is...

  1. Never lower than the true count
  2. Sometimes lower, when two items share a counter
  3. Exact once the sketch has 5 or more rows
  4. Unbiased: too high and too low equally often
Collisions only add to counters; taking the minimum across rows keeps the closest overestimate, so it can be too high but never too low.

Roughly how many counters does a count-min sketch need for epsilon = 0.001 and delta = 0.01?

  1. About 1,000 (one counter per 0.1% of error)
  2. About 100,000 (1/epsilon x 1/delta)
  3. About 4 billion (one counter per distinct item)
  4. About 13,600 (2,719 wide x 5 deep)
w = ceil(e/0.001) = 2,719; d = ceil(ln(1/0.01)) = 5; about 54 KB at 4 bytes per counter. Width grows with 1/epsilon, depth only with ln(1/delta).

Why not let the stream engine keep a month-long window that slides every minute?

  1. Flink only supports tumbling windows, not sliding ones
  2. Each event would belong to 43,200 overlapping windows
  3. Kafka's retention cannot be set longer than 7 days
  4. Sliding windows are less accurate than tumbling ones
60 x 24 x 30 = 43,200 overlapping windows per event. Use minute buckets and add the newest / subtract the oldest instead.

The Amazon sales-rank example has about 400 writes/s and hourly updates. A good first design is...

  1. A Flink cluster with count-min sketches per category
  2. An hourly Spark or MapReduce job into a cached table
  3. A per-request SQL GROUP BY over the orders table
  4. A Redis sorted set per category, bumped on every sale
The low write rate and hourly freshness make batch simple and exact. A sorted set would work too, but a per-request GROUP BY at 40k reads/s would not.

What is the cheapest first fix for a viral item overloading one partition?

  1. Add more Kafka brokers so the partition has more disks
  2. Switch the whole pipeline to a count-min sketch
  3. Pre-aggregate increments per item at the ingest servers
  4. Re-key the topic by user so the load spreads out
Summing per item per second before Kafka shrinks the hottest keys the most. More brokers do not split one partition, and keying by user breaks exact merging.

"Trending" differs from "top-K" because it ranks by...

  1. Change versus a baseline for the same item
  2. The highest raw count in the last minute
  3. The all-time count, decayed by item age
  4. The number of distinct users, not events
Otherwise always-popular terms like "good morning" would trend every day. Trending compares now with what is normal for that item.
