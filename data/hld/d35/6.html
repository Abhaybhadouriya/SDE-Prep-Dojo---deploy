Deep dives

1. Is "merge the local top-Ks" actually correct?

It depends on how you partitioned. This is the question that separates good answers from great ones.

  • Partitioned by item (our design): every item's full count is on one shard. The global top-K must be in some shard's local top-K, so merging K items from each of N shards is exact.
  • Partitioned any other way (round-robin, by time, by user): an item's count is split across shards. An item can be number 1,001 everywhere and number 1 overall. Merging local top-Ks is then approximate.

Real systems live with the second case. Apache Druid's TopN query returns the top 1,000 local results from each segment and merges them at the broker, and its documentation states the result is approximate only when a dimension has more than 1,000 values. Their fix for exactness is a second pass: find candidates with TopN, then re-count just those candidates exactly. Use the same two-pass trick in an interview when you cannot partition by item.

2. Windows: tumbling, sliding, and all-time

  • Tumbling windows do not overlap; each event belongs to exactly one window (09:00-10:00, 10:00-11:00). Cheap: one counter set per window.
  • Sliding windows have a size and a slide; with a 10-minute size and 5-minute slide each event lands in two windows (Flink docs). A month sliding by the minute would put each event in 43,200 windows - too much state.
  • The practical answer: keep minute buckets, then maintain each window total by adding the newest bucket and subtracting the expired one (the ring buffer above). Hello Interview offers a neat variant: a second Kafka consumer group that reads the same topic one hour behind and decrements - no minute storage, but Kafka retention must exceed the longest window.
  • Product shortcut: sliding for "last hour", tumbling (aligned) for day and month. Users rarely notice the difference for long windows.
  • Late events. Allow about 1 minute: use event time with a watermark (Hello Interview uses 30 seconds of out-of-orderness in Flink) and a small allowed lateness; anything later goes only to the batch path.

Stop here for SDE-1. "Partition by item so merging local top-Ks is exact" and "minute buckets that you add and subtract for sliding windows" are the interview-sufficient core. Deep dives 3-5 (count-min sketch, hot-key salting, the Lambda split) are what an SDE-2 answer adds.

3. Approximate counting: count-min sketch + heap

When keys are too many for exact counters, or memory per node is tight, use a count-min sketch: a d x w grid of counters and d hash functions. To add an item, increment one counter in each row. To query, take the minimum across rows. Collisions can only add, never subtract, so the estimate is never too low, and with probability 1 - delta it is at most epsilon x total count too high.

  1. Add. "cat" is seen 5 times; each of the 3 hash functions picks one counter per row and adds 5.
  2. Collision. "dog" (seen 3 times) hashed into the same row-2 counter, so it reads 8. Collisions only ever inflate.
  3. Query. Take the minimum across rows: 5. The smallest counter is the one with the fewest collisions.
  4. Keep the winners. A min-heap of K items sits beside the sketch: after each update, if the item's estimate beats the heap's smallest, swap it in.

Redis's own docs warn that counts below the threshold error x total_count are noise. A count-min sketch is great at finding heavy items, useless for the long tail. That is exactly what top-K needs - but never use it to show a small creator their exact view count.

4. Hot keys: when one item is the whole stream

Partitioning by item makes merging exact, but a viral video can send a huge share of 700k events/s to one partition. Fixes, cheapest first:

  1. Pre-aggregate before Kafka. Each ingest server sums events per item for 1 second and sends (item, +350) instead of 350 messages. This is a "combiner" in MapReduce terms and cuts volume most for exactly the hottest items.
  2. Salt the hot key. Write video:42#0..7 to 8 partitions; the merger sums the 8 partial counts before ranking. Only salt keys you detect as hot: salting every key multiplies merge and read work by the salt factor. Also make sure the partials are summed before any local top-K cut - if a shard ranks video:42#3 on its own, it can drop it, and the merge becomes approximate.
  3. Batch writes downstream. Flush aggregated counts to the store every few seconds, not per event - the 2-100x reduction from the estimation.

The general toolbox is on Scaling Writes; the sibling problem is Distributed Counter.

5. Fast-and-approximate plus slow-and-exact (Lambda)

Many teams run two paths: the stream gives a fresh, possibly approximate answer within a minute; a batch job over raw events in object storage gives an exact answer hours later and overwrites the stream's numbers for closed windows. system-design-primer's Amazon example is pure batch - a two-step MapReduce (sum per (category, product), then distributed sort) run hourly into a sales_rank table. The alternative, Kappa, keeps one streaming path and fixes bugs by replaying Kafka. See Big Data: Batch, Streaming & Probabilistic Structures and Counting, Ranking & Windowed Aggregation.

Atlassian twist: "top-K pages, excluding ones this user already viewed." Compute a global candidate list of K + buffer (say 3K), then filter per user against their viewed set (a Bloom filter is fine - a false positive only hides one page). Never compute a per-user top-K from raw events.
