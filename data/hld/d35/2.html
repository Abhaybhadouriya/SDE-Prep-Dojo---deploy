Back-of-envelope estimation

Numbers from Hello Interview's YouTube breakdown, then system-design-primer's Amazon sales-rank example. (Method: Back-of-Envelope Estimation.)

YouTube top-K videos

  1. Write QPS. About 70 billion views/day (YouTube Shorts scale). Use 100,000 seconds/day for easy maths: 70,000,000,000 / 100,000 = 700,000 events/s.
  2. Number of keys. About 1 million new videos/day, so about 3.6 billion in 10 years; round to 4 billion videos.
  3. Counter storage. 4 billion x (8-byte id + 8-byte count) = 64 GB for all-time counts. Fits in RAM across a few machines, or in a sharded DB.
  4. Write sharding. If one DB node handles about 10,000 writes/s, raw events need 700,000 / 10,000 = 70 shards. Pre-aggregating in a stream processor (sum views per video per short interval, then write once) cuts writes by 2-100x, so 5-10 shards are enough.
  5. Sliding-window cost. A one-month window that slides every minute means 60 x 24 x 30 = 43,200 overlapping windows if you let a stream engine keep each one - which is why we use minute buckets and add/subtract instead.
  6. Reads. The answer is at most 1,000 items x about 16 bytes = 16 KB per window. Precompute it every few seconds and cache it; any read QPS becomes cheap.

Amazon sales rank by category

  1. Inputs. 10 million products, 1,000 categories, 1 billion transactions per month, 100 billion reads per month.
  2. Write QPS. A month is about 2.5 million seconds. 1,000,000,000 / 2,500,000 = 400 transactions/s.
  3. Read QPS. 100,000,000,000 / 2,500,000 = 40,000 reads/s (100:1 read-heavy).
  4. Storage. About 40 bytes per transaction x 1 billion = 40 GB/month, 1.44 TB over 3 years. The primer recomputes the weekly rank hourly with MapReduce.
