Where Kafka, Kubernetes and Docker fit

📨

Kafka

The spine. Kafka keyed by itemId keeps one video's events on one partition, so one aggregator owns its count and the merge stays exact. Replaying from a saved offset rebuilds an aggregator's state after a crash. Retention longer than the longest window lets you replay or run a "decrement" consumer group. Consumer lag = how stale the top-K is.

 🌊

Flink / Kafka Streams

Windowed aggregation with checkpointed state (RocksDB). On failure it restores state and rewinds Kafka offsets, so counts are not lost or doubled. Why here: writing your own windowing, late-event handling and checkpoints is weeks of work, and getting it wrong double counts.

 ☸️

Kubernetes

Run Flink with its operator (it handles job upgrades and restores from checkpoints). Aggregator parallelism is tied to the partition count, so you scale by adding partitions, not just pods. The stateless API and merger run as Deployments with an HPA (Horizontal Pod Autoscaler: adds pods when CPU or QPS rises); Redis as a StatefulSet (stable name and disk per pod) or a managed service. Docker images pin the Flink and connector versions so every pod runs the same job code.

 
// Flink sketch: per-video counts per 1-minute tumbling window, then per-window top-K
views
  .assignTimestampsAndWatermarks(
      WatermarkStrategy.<View>forBoundedOutOfOrderness(Duration.ofSeconds(30))
                       .withTimestampAssigner((v, ts) -> v.ts))
  .keyBy(v -> v.videoId)
  .window(TumblingEventTimeWindows.of(Duration.ofMinutes(1)))
  .aggregate(new CountAgg())                 // incremental: keeps one long per key
  .keyBy(c -> c.windowEnd)
  .process(new TopKPerWindow(100))           // min-heap of 100
  .addSink(new RedisSortedSetSink("top-k:1m"));

Use an incremental AggregateFunction rather than a ProcessWindowFunction that buffers every event - Flink's docs note the latter must keep all elements of the window in state. Hands-on Kafka-to-processor practice is in the ShopStream pipeline.
