Architecture: follow the events

Click through. The top half is the fast streaming path; the bottom is the slower exact batch path.

  1. Ingest. Clients emit view or sale events; a thin API validates and returns 202 at once.
  2. Kafka, keyed by itemId. All events for one item land on one partition, so one consumer owns that item's count. Kafka also lets us replay after a bug.
  3. Aggregate locally. Each consumer (Flink task) sums counts per item per minute in memory, rolls them into window totals, and keeps a local top-K heap for each window.
  4. Merge. Every few seconds, local top-K lists go to a merger. Because each item lives on exactly one partition, the global top-K is exactly the top K of the union of the local lists.
  5. Publish. The merged list per window (and category) is written to Redis with a timestamp; the API only reads it. Tens of milliseconds, any QPS.
  6. Exact batch path. Raw events also land in object storage. A daily/monthly batch job recomputes exact numbers and overwrites the streaming result - the "Lambda" pattern.
  7. Watch out. One viral video sends a huge share of events to a single partition. Deep dive 4 shows how to spread it.
