Architecture, step by step

  1. Connect. Every device keeps one long-lived, mutually authenticated (mTLS, device certificate) connection to a gateway. The gateway records device_id -> gateway node in a presence store so the backend can push to it.
  2. Setup by relay. The new device opens a setup session; the user picks the old device; the setup service pushes "send your settings" to the old device over its connection. The old device encrypts settings for the new device's public key and streams them through the relay. The server passes bytes through and stores nothing: the storage-reduction answer.
  3. Fallback. If the old device is offline (broken, unplugged), use the last committed backup snapshot or the cloud copy of non-default settings, or offer to wait and notify when the old device comes online.
  4. State write. A change ("light off") arrives at the state service with the device's base version. A conditional write succeeds only if the version matches, then assigns version N+1 and appends to the change log.
  5. Fan-out. The change goes to state-changes (key = user_id, so one user's changes stay in order). A push service looks up which gateways hold that user's other devices and pushes to them. Offline devices will catch up with since=N.
  6. Backup. On schedule, a device chunks its data, asks which chunk hashes are missing, uploads only those straight to object storage, then commits a manifest. Commit is atomic.
  7. Replicate. Chunks and manifests are replicated to a second region (asynchronously, with a lag alarm). Restore can read from either.
