Deep dives: the hard parts

7.1 Old-to-new sync without storing copies in the cloud

In the Amazon SDE-2 round (selected, July 2025), the interviewer pushed on reducing storage, and the accepted answer was to stop keeping config files in the cloud and pull them straight from the old device during setup. Here is how to make that safe and fast.

  1. Find the old device. After login, the new device lists the user's registered devices (device table by user_id) with online status from presence. The user picks one, or the system picks the most recent device of the same family.
  2. Pair. Both devices belong to the same account, which proves ownership. Add a short confirmation (a code shown on the new device and confirmed in the app, or a button press on the old one) so a stolen account token alone cannot pull settings.
  3. Key exchange. The new device sends its public key; the old device encrypts the settings bundle with it (an ECDH-derived key). The relay sees only ciphertext: end-to-end encryption, so Wi-Fi passwords never sit readable in our cloud.
  4. Transfer path. Prefer local (same Wi-Fi or Bluetooth) when both are in the same room; otherwise the cloud relay. Both carry the same encrypted bundle.
  5. Translate. A settings schema with a version and per-model capability map: the new device keeps what it supports, ignores the rest, and migrates old schema versions ("v3 do-not-disturb" to "v4 quiet hours").
  6. Parallelise the slow parts. While settings transfer, start firmware check, account linking and skill or app downloads. Settings themselves take milliseconds.
Pull from old device
  • Almost zero cloud storage for settings.
  • Always the freshest settings, no sync lag.
  • Smaller attack surface: no long-lived copy of secrets.
Costs
  • Fails when the old device is dead (the common "replacement" case), so a fallback is mandatory.
  • Needs both devices online at the same time.
  • Old firmware must speak the transfer protocol (version it).

Middle ground to offer: store only non-default settings in the cloud (a few KB per user, not 50 KB per device), deduplicated per user rather than per device, because most of a user's devices share the same preferences. That is a 10-100x storage cut while still covering the dead-device case.

7.2 Keeping 10 devices in the same state

Amazon SDE-2 (May 2025): "user turns off a light from one device; all other devices must reflect it." The core model is the one AWS IoT's Device Shadow uses: a JSON document per thing with desired and reported state, a version that increments on every update, and a computed delta.

  • Who owns the truth? For a physical light, the light (its hub) is the authority for reported state; other devices write desired state ("I want it off"). The UI on every device shows reported, with a spinner while desired and reported differ. For a pure preference (wake word, theme), the cloud document is the truth.
  • Versioned writes. Each write carries base_version. The state service does a conditional write; on mismatch it returns 409 with the current value, and the device rebases. AWS IoT documents exactly this: an update with an old version gets an error and the client must resync.
  • Push. After commit, publish to users/{user_id}/state. Gateways push to the user's connected devices. A device that receives version N+1 but has N-1 knows it missed N and calls GET state?since=N-1.
  • Offline catch-up. On reconnect, the device sends its last version. If the change log still has it (30 days), send the changes; if not (410 Gone), send a full snapshot. The same pattern as Kafka consumers that fall behind retention.
  • Idempotency. client_op_id on every write so a retried "light off" after a dropped connection does not create a second version.

7.3 Scheduled backup: chunking, dedup and the thundering herd

Amazon SDE-2 (July 2026, selected): back up device settings, files and media on a schedule and restore them on a new device. Apple (April 2026) asked a backup system with data integrity, scalability, multi-region replication, observability and resiliency.

  1. Chunk. Split files into variable-size chunks using content-defined chunking (boundaries set by a rolling hash, around 1-4 MB on average). Inserting bytes near the start of a file changes only nearby chunks, unlike fixed-size blocks which shift every boundary after the edit.
  2. Hash and ask. SHA-256 each chunk. Send the list of hashes for changed files to the backup service.
  3. Dedup. The service checks its chunk index (scoped to this user) and answers with only the missing ones. Unchanged chunks cost nothing.
  4. Upload direct. The device uploads missing chunks straight to object storage with presigned URLs, resumable per chunk. The server verifies size and hash before accepting.
  5. Commit. Upload the encrypted manifest (file tree plus chunk lists) and commit. Only now is the snapshot restorable, and only now do chunk reference counts go up.
  • Scheduling without a server cron per device. 10M devices cannot be scheduled by a central cron that calls each device. The device schedules itself (Android's Auto Backup, for example, runs when backup is enabled, at least 24 hours have passed, the device is idle and on Wi-Fi) with random jitter. The server protects itself with admission control: POST /backups can answer "retry after 40 min" when the ingest fleet is busy.
  • Dedup scope. Per user is the safe default. Cross-user dedup saves more but lets an attacker learn "someone already has this file" and conflicts with end-to-end encryption (each user's key makes the same file look different). Mention convergent encryption as the trade-off, then choose per user.
  • What goes in a backup. Only what does not already sync elsewhere: Apple's support pages say an iCloud backup holds information and settings that do not already sync to iCloud (photos syncing through iCloud Photos are left out). Same principle: settings that live in the state service (7.2) need no backup copy.
  • Retention and garbage collection. Keep, say, the last 3 snapshots per device. Expiring a snapshot decrements chunk ref counts; a background mark-and-sweep deletes chunks at zero after a grace period. Never delete in the same transaction as the decrement: a concurrent backup may be about to reference that chunk.

7.4 Integrity, multi-region replication and observability (the Apple variant)

  • End-to-end checksums: hash on the device, verify on upload, store the hash with the object, verify again on restore. Periodic scrubbing jobs re-read a sample of chunks and compare hashes, catching silent corruption (bit rot).
  • Atomic snapshots: the manifest is the commit point; a snapshot with a missing chunk is a bug that scrubbing must find before the user does.
  • Replication: object storage cross-region replication for chunks, plus metadata replication (global tables). Track replication lag and treat "snapshot committed in region A but chunks not yet in B" as a state: restore from B waits or reads from A.
  • Restore drills: automatically restore a random sample of real backups into a sandbox and compare hashes. A backup you never restored is a hope, not a backup.
  • Metrics: percent of devices with a successful backup in the last 24 h / 7 days, age of the oldest successful backup per device, bytes uploaded vs deduped, upload error rate by firmware version, restore time to "usable" and to "complete", replication lag, scrub failures.

7.5 Restore to a new device fast

Order matters for the 1-5 minute target: (1) settings and account (KB, seconds), so the device is usable; (2) app list and small app data; (3) media in the background, most recent first, while on Wi-Fi. Apple's guidance after an iCloud restore is to stay on Wi-Fi so photos and videos can continue downloading: the device is usable before the restore is complete. Show two progress numbers: "ready" and "fully restored".

7.6 The Nutanix variant: a database backup service

Same skeleton, different source. Nutanix MTS-2/3 (March 2025) asked for a database backup service; the recruiter did not say whether it was HLD or LLD, and it was HLD.

  • Full + incremental: a periodic full backup (storage snapshot or pg_basebackup-style copy) plus continuous shipping of the write-ahead log (WAL / binlog) to object storage.
  • Consistency: a backup must be crash-consistent at least: use the database's own snapshot mechanism or a storage-level snapshot taken at one instant, not a file copy while writes continue.
  • Point-in-time recovery: restore the latest full before time T, replay logs up to T. RPO = how much log could be lost (seconds if shipped continuously); RTO = full restore time plus replay time.
  • Control plane: policies (every 6 h full, log continuously, keep 30 days), a scheduler that spreads jobs across hosts, a job state machine (SCHEDULED, RUNNING, UPLOADING, VERIFIED, FAILED) with retries, and a catalog of restore points.
  • Verify: restore into a scratch instance and run checks. Throttle backup I/O so it does not hurt production latency.
