  1. 0-7 min: Which device types? What is "a setting"? Which of setup, live sync and backup? Numbers: users, devices per user, setup time target, security needs. Write entities: Device, User, Settings (and Snapshot, Chunk for backup).
  2. 7-12 min: Estimate; show settings are tiny and the time goes elsewhere; size connections and backup bandwidth with jitter.
  3. 12-20 min: APIs and data model, with versions and idempotency keys visible.
  4. 20-30 min: Draw gateways, setup relay, state service, push, backup service, object storage, second region.
  5. 30-40 min: Deep dives the interviewer picks: storage reduction and offline fallback; conflicts and catch-up; chunking, dedup, integrity.
  6. 40-45 min: Failures, observability, security. Then expect the 2 LP questions.

Common mistakes: storing a full settings copy per device forever; trusting device clocks for conflicts; one central cron calling 10M devices; uploading whole files on every backup; making a snapshot visible before all chunks exist; global dedup without mentioning privacy; no answer for "old device is offline"; forgetting that the Wi-Fi password is a secret; never testing restores.

How would you reduce the storage this setup service needs?

Do not keep config copies in the cloud at all on the happy path: when the new device is set up, pull settings straight from the old device through an end-to-end-encrypted relay (or locally over Wi-Fi or Bluetooth), and the server stores nothing but a short-lived session. For the case where the old device is gone, keep only non-default settings, once per user rather than per device (most of a user's devices share preferences), compressed and versioned. That turns about 50 KB per device into a few KB per user.

How to answer

This is the follow-up the Amazon candidate got and the accepted answer. Say it, then immediately offer the fallback so the interviewer does not have to ask.

Likely follow-ups
  • Does the relay store anything? (Only ciphertext in flight, in memory; nothing on disk.)
  • How do you know what is "default"? (Defaults per model and firmware version, shipped with the firmware.)
The old device is offline or broken during setup. What now?

Three-level fallback: (1) restore from the latest committed backup snapshot of that device, if backups exist; (2) otherwise use the per-user cloud copy of non-default settings; (3) otherwise start with defaults plus account-level data (linked services, routines stored in the account) and register a "pending import" so when the old device next connects it is asked to send its settings, which are merged with version checks. Tell the user what was restored and what is pending.

How to answer

Walk the branches in order of preference. Device-team interviewers dig into offline cases, so having all three ready shows depth.

Likely follow-ups
  • The user already changed a setting on the new device before the import? (The newer edit wins per field; import only fills fields still at default.)
Settings include the Wi-Fi password and account tokens. How do you secure the transfer?

Device identity with per-device certificates and mTLS to the gateways. Both devices must be on the same account, plus an explicit pairing confirmation (code or button) so a stolen session cannot pull settings remotely. The new device generates a key pair; the old device encrypts the bundle for that public key, so the relay sees only ciphertext. Account tokens are not copied at all: the new device gets its own token through login (copying tokens would make two devices share an identity). Short session TTL, audit log of every transfer, and a notification to the user's phone ("a new device received your settings").

How to answer

Separate "who is allowed" (account + pairing), "who can read" (E2E), and "what should never move" (tokens).

Likely follow-ups
  • Lost old device? (User revokes it in the app; its certificate is revoked and it can no longer be a source.)
The new device must be ready in 1-5 minutes. What is on the critical path?

Not the settings: 50 KB moves in milliseconds. The critical path is Wi-Fi join, login, firmware check or update, and downloading apps or skills. So: apply Wi-Fi first (the old device can provide it), run firmware check, settings transfer and content downloads in parallel, mark the device "ready" once settings and account are done, and finish large downloads in the background. Measure time to ready per step at p50 and p95 by model.

How to answer

Use your estimate to say what is not the bottleneck; that is the Dive Deep moment.

Likely follow-ups
  • A mandatory firmware update takes 4 minutes? (Download it during setup, install it later at night unless it is a security fix.)
Keep up to 10 devices of one user in the same state: the user turns off a light on one device, and all others must reflect it.

Model state as a versioned document per user (like an IoT device shadow: desired vs reported, plus a version). The device writes desired "off" with its base version; the state service conditionally writes and assigns version N+1, appends to a per-user change log, and publishes to a per-user channel. Gateways holding the user's other devices push the change over persistent connections. The light's hub reports the actual state, and all devices show reported state. Offline devices reconnect with their last version and get changes since then, or a snapshot if they are too far behind.

How to answer

Name the three parts: versioned truth, push, catch-up. Draw the per-user channel.

Likely follow-ups
  • How do you find which gateway holds each device? (Presence store: device_id -> gateway, with TTL refreshed by heartbeats.)
  • Why per-user ordering? (So version N+1 never arrives before N; key Kafka by user_id.)
Two devices change the same setting at the same time. Who wins?

Online, the server decides: both send base version 7, the first conditional write creates 8, the second fails with 409 and the current value, and that device shows the new value (or retries if the user's intent still applies). Offline edits are merged per field with server-assigned order on arrival, so edits to different fields both survive. Lists use merge rules with tombstones; counters or sets edited offline on many devices can use CRDTs. Never compare device clocks.

How to answer

Give the default (optimistic locking), then escalate only where the data type needs it.

Likely follow-ups
  • Why per field and not per document? (Per document LWW would drop a whole edit because of an unrelated field.)
Design the backup scheduler for millions of devices without melting the backend at 2 AM.

Devices schedule themselves: back up when at least 24 hours have passed, the device is idle, charging or plugged in, and on Wi-Fi, with a random offset across the night (as Android Auto Backup does with its conditions). The server keeps control with admission: a backup start request may get "retry after N minutes" when ingest is busy, and tokens per region cap concurrent uploads. Backups are incremental (only missing chunks) so most nights upload a few MB. A fleet-level job tracks devices whose last success is older than 7 days and nudges them.

How to answer

Show the jitter math: 100 TB in one hour is 28 GB/s; spread over 24 h it is 1.2 GB/s.

Likely follow-ups
  • User taps "Back up now"? (Same path with higher priority, still subject to admission.)
How do incremental, chunked uploads and dedup work? Why not upload the whole file?

Split files with content-defined chunking (rolling hash picks boundaries, about 1-4 MB on average), hash each chunk with SHA-256, ask the server which hashes are missing for this user, and upload only those, straight to object storage with presigned URLs and per-chunk retries. A manifest lists each file's chunk hashes; committing it makes the snapshot visible. Unchanged files cost zero bytes, and an edit to a large file costs only the changed chunks. Content-defined boundaries matter because with fixed blocks an insert near the start shifts every later block.

How to answer

Draw a file as boxes, change one, and show which boxes upload.

Likely follow-ups
  • Cross-user dedup? (Saves more, but leaks file existence and breaks E2E encryption; choose per user.)
  • When can a chunk be deleted? (When no committed manifest references it, after a grace period; mark-and-sweep.)
How do you guarantee data integrity and survive a region loss? What do you monitor?

Integrity: hash on the device, verify on upload, store the hash, verify on restore; scrub stored chunks periodically; commit snapshots atomically via the manifest; run automatic restore drills on samples. Region loss: replicate chunks and metadata asynchronously to a second region, track replication lag, and let restore read from the replica. Monitor: percent of devices backed up in 24 h and 7 days, oldest successful backup, dedup ratio, error rate by firmware, restore time to ready and to complete, replication lag, scrub failures. Alert on the trend of "devices without a good backup", not on single failures.

How to answer

Apple's prompt listed integrity, scalability, multi-region, observability and resiliency: answer each by name, in that order.

Likely follow-ups
  • RPO and RTO? (RPO = time since last committed backup, at most about 24 h; RTO = time to ready, minutes.)
Design a database backup service.

Policies define full backups (storage or database snapshot, consistent at one instant) every few hours plus continuous log shipping (WAL or binlog) to object storage. A scheduler spreads jobs across hosts and throttles I/O; each job runs a state machine with retries and records a restore point in a catalog. Point-in-time restore = latest full before T plus log replay to T. Verify by restoring to a scratch instance on a schedule. Retention deletes old fulls and logs together so every kept restore point stays complete. Replicate to another site for disaster recovery.

How to answer

Reuse the backup skeleton (schedule, incremental, commit, verify, replicate) and add the database-specific parts: consistency and log replay.

Likely follow-ups
  • How do you back up without hurting production? (Back up from a replica, rate-limit I/O, use storage snapshots.)

The two Leadership Principles that came with these rounds

Amazon rounds were reported as about 45 minutes of design plus about 15 minutes of LPs (the July 2026 report split it 30 + 30). The 2025-07 round asked Customer Obsession and Dive Deep. Tie your stories to the design: for Customer Obsession, a time you cut a user-facing wait (like "ready in 1-5 minutes") even when it cost engineering effort; for Dive Deep, a time metrics looked fine but you dug into the tail (p99, a single firmware version) and found the real cause. Use STAR, give numbers, and say what you personally did.

Scenario: "Lights show ON on two devices after the user turned them OFF"

Support tickets: after a gateway deploy, some devices show stale state for hours.

Weak answer: "Increase push retries."

Strong answer: the devices reconnected to new gateways but presence still pointed to old nodes, so pushes went nowhere, and the devices had no gap detection because no newer version arrived. Fix: presence TTL tied to heartbeats, re-register on reconnect, and on every reconnect the device sends its last version and pulls changes. Add a metric: devices whose version lags the user's latest by more than 60 s.

Likely follow-ups
  • Which LP story fits? (Dive Deep: found it from a lag metric, not from the deploy dashboard.)
