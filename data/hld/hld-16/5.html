The design patterns that cover most problems

The Gang of Four book lists 23 patterns. AlgoMaster's LLD repo groups them as creational, structural and behavioural. In practice four patterns cover most LLD rounds, and the problem statement tells you which one to use.

When the problem says...UseWhere it shows up
"support different ways to X" (split, price, assign a spot, pick an elevator)Strategy: an interface with one implementation per algorithm, chosen at runtimeSplitwise split types, parking fee and spot allocation, elevator dispatch, payment methods
"notify users when Y happens"Observer: subscribers register with a subject and are called on eventsSeat available, price drop alert, display boards in a parking lot, train arrival boards
"the object behaves differently depending on its status"State: one class per state, the context delegates to its current stateElevator (idle, moving, doors open), vending machine, booking (held, confirmed, cancelled), chess game
"create the right kind of thing from input"Factory: one place that maps input to a concrete classVehicle from type string, split from command, notification channel
"exactly one shared instance"Singleton (use carefully)The ParkingLot or a service registry. Prefer injecting one instance, because Singletons hurt testing.
"add-ons that stack" / "undo"Decorator / CommandPizza toppings, coffee add-ons / editor undo, a queue of elevator requests
"pass it along until someone handles it"Chain of responsibilityATM cash dispenser (2000, 500, 100 notes), logging levels, approval workflows

Strategy vs State, a common trick question. Refactoring.guru explains it well: both delegate work to a helper object. With Strategy, the client picks the algorithm and the strategies do not know about each other. With State, the state objects know about each other and trigger their own transitions. For example, the elevator's MovingUp state switches to DoorsOpen when it reaches a requested floor.

From your world

You have used these patterns under other names. Netfilter hooks are a chain of responsibility. Netlink and notifier chains (register_netdevice_notifier) are the Observer pattern. A TCP connection's state machine (SYN_SENT, ESTABLISHED, FIN_WAIT_1) is the State pattern written as a switch. Picking a congestion-control algorithm (cubic, bbr) through tcp_congestion_ops is textbook Strategy.

Where this breaks: kernel code names none of these patterns, but interviewers want the names; say "this is the Strategy pattern" out loud so they can tick the box.
