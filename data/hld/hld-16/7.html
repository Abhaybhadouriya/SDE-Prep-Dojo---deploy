Concurrency inside LLD

Almost every LLD classic has one shared, scarce thing: a parking spot, a seat, a locker, an elevator. Two threads must never both get it. The requirement often says it directly, for example "handle multiple entry and exit points and support concurrent access" (AlgoMaster's parking lot). You have four tools, in order of preference:

  1. Atomic check-and-set on a concurrent map. ConcurrentHashMap.putIfAbsent(seatId, userId) either wins or loses in one step. It is lock-free and simple.
  2. Fine-grained locks. Lock one spot or one show, never the whole parking lot. Always lock several seats in a fixed order (sorted by ID) to avoid deadlock.
  3. Optimistic versioning. Keep a version number on the object and update only if it is unchanged. This is the in-memory version of UPDATE ... WHERE version = ?.
  4. Coarse synchronized methods. Correct but slow. Fine for a demo, so say you would refine it.

Which language should a C engineer use? Pick Java, Python or C++ for LLD and machine-coding rounds. C is usually not accepted for object-oriented design rounds, because there are no classes or interfaces to show; check with the recruiter before the loop. Java is the most common choice in Indian SDE-2 loops and maps most directly to the patterns on this page; Python is fastest to type; C++ is fine if you are fluent in its classes and smart pointers. // In-memory seat hold with expiry: the heart of a BookMyShow LLD
public class InMemorySeatLockProvider implements SeatLockProvider {
    private final Map<String, SeatLock> locks = new ConcurrentHashMap<>();
    private final Duration ttl;

    public InMemorySeatLockProvider(Duration ttl) { this.ttl = ttl; }

    @Override
    public boolean tryLock(String showId, List<String> seatIds, String userId) {
        Map<String, SeatLock> acquired = new LinkedHashMap<>();
        for (String seat : seatIds.stream().sorted().toList()) {     // fixed order
            String key = showId + ":" + seat;
            SeatLock mine = new SeatLock(userId, Instant.now().plus(ttl));
            SeatLock now = locks.compute(key, (k, cur) ->
                (cur == null || cur.isExpired() || cur.userId().equals(userId))
                    ? mine : cur);                                      // free, expired, or already mine: (re)take
            if (now != mine) {                                          // someone else holds it
                // roll back ONLY the holds we placed: remove(key, value) is a no-op
                // if another user took the seat after our hold expired
                acquired.forEach((k, v) -> locks.remove(k, v));
                return false;
            }
            acquired.put(key, mine);
        }
        return true;
    }
}

record SeatLock(String userId, Instant expiresAt) {
    boolean isExpired() { return Instant.now().isAfter(expiresAt); }
}

From your world

This is the same discipline as kernel locking. Hold the smallest lock for the shortest time, take multiple locks in a global order to avoid ABBA deadlocks, and prefer atomic compare-and-swap (cmpxchg) over a big spinlock. ConcurrentHashMap.compute is effectively a per-bucket lock plus CAS.

Where this breaks: a kernel spinlock holder never sleeps, but a Java thread inside synchronized can be paused by the garbage collector or the scheduler for a long time, so in LLD you prefer short critical sections and expiry (TTL) on holds rather than trusting the holder to release quickly.

In the HLD half the same idea becomes distributed: a Redis SET key value NX PX 600000 hold with a TTL, or a database row lock or version check. See Pattern: Dealing with contention and Replication, consensus and coordination.
