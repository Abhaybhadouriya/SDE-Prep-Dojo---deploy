Interview questions

What is the difference between HLD and LLD?

HLD is the architecture of the whole system: services, data stores, caches, queues, how they communicate, and how the system scales and survives failures. It is drawn as boxes and arrows with numbers. LLD is the inside of one component: classes, interfaces, methods, relationships, state transitions and in-process concurrency, written as class diagrams and code. HLD decides "a booking service backed by Postgres with Redis seat holds". LLD decides "a SeatLockProvider interface with an in-memory implementation, injected into BookingService".

How to answer

Give one sentence for each, then one example that zooms from an HLD box to its LLD classes.

Likely follow-ups
  • Which matters more at SDE-2?
  • What is a machine-coding round?
How do you approach a 90-minute machine-coding round?

About 10 minutes reading and scoping (mark musts versus bonuses, confirm in-memory storage and a demo driver). About 10 minutes on entities, interfaces and package layout. About 40 minutes building the core flows end to end so something runs early. About 20 minutes on validation, custom exceptions and thread safety. About 10 minutes on a demo main that runs the sample inputs, plus tidying. Put storage behind repository interfaces, put the varying behaviour behind a strategy, keep classes small, and never end with code that does not compile.

How to answer

Give the time plan, then the three qualities graded: it runs, it is modular, and it is easy to extend.

Likely follow-ups
  • How would you move storage to a DB?
  • Add a new feature live: what changes?
Explain SOLID with one example each.

S: FeeCalculator is separate from ParkingLot, so a pricing change never touches allocation. O: a new split type is a new SplitStrategy class, with no edits to ExpenseService. L: every Vehicle subclass honours getSize(), with no "unsupported" exceptions. I: Payable and Refundable are separate, so a gift-card gateway need not fake refunds. D: BookingService receives a PaymentStrategy and a SeatLockProvider in its constructor instead of creating concrete classes.

How to answer

Keep all five examples in one domain (parking or booking), so it sounds like design experience and not a memorised list. Add that you apply them only where change is likely (KISS, YAGNI).

Likely follow-ups
  • Show an LSP violation and fix it.
  • Can SOLID be overdone?
Design a parking lot (LLD). Walk through the classes.

Scope: multiple floors, bike/car/truck with matching spot sizes, multiple gates, ticket on entry, fee on exit. Classes: ParkingLot owns ParkingFloors, which own ParkingSpots (composition). Vehicle is abstract with subclasses. Ticket records the spot and entry time. EntryGate and ExitGate call a ParkingService. Variation points are a SpotAllocationStrategy (nearest to gate, lowest floor) and a FeeStrategy (hourly, flat, weekend). Concurrency: each (floor, size) has a concurrent queue of free spots, so assignment is an atomic poll() and two gates never get the same spot. Observers update display boards when counts change.

How to answer

Scope first, then draw the composition chain, then name exactly two strategies and the concurrency fix. Stop there and ask which part to code.

Likely follow-ups
  • Add EV charging spots.
  • Large vehicles taking two adjacent spots?
  • Now 1,000 lots in a city: what changes? (HLD)
Design an elevator system. How do you schedule requests?

Each Elevator has a current floor, a direction, a state (Idle, MovingUp, MovingDown, DoorsOpen as State classes), and two sorted stop sets for up and down. It serves every stop in its current direction, then reverses only if stops remain the other way (LOOK). The ElevatorController takes hall calls and picks a car through a DispatchStrategy: prefer a car moving toward the caller in the same direction, else the nearest idle car, else the least loaded. Each elevator runs its own loop over a thread-safe queue, so button presses never mutate state directly. Capacity is checked at each stop.

How to answer

Draw the state diagram first, then the stop-set algorithm, then the dispatcher as a pluggable strategy.

Likely follow-ups
  • How do you prevent starvation of a far floor?
  • Express elevators or zoning?
  • Emergency or fire mode? (another State)
BookMyShow LLD: how do you make sure two users cannot book the same seat?

Seat state lives per show. Booking is two-phase: first a temporary hold, then confirm. SeatLockProvider.tryLock(show, seats, user) acquires each seat atomically (ConcurrentHashMap.compute or putIfAbsent) in sorted order, and rolls back if any seat is taken. Holds carry an expiry, so abandoned checkouts free themselves. On payment success the booking moves to CONFIRMED and seats to BOOKED, and the confirm step checks that the hold still belongs to this user. In the distributed version the hold is a Redis key with NX and a TTL, or a DB row with a version check, and payment callbacks are idempotent. Walmart reportedly asks for the optimistic vs pessimistic locking trade-off here.

How to answer

Separate "hold" from "book", show the atomic operation, then cover the timeout and the distributed version.

Likely follow-ups
  • Optimistic vs pessimistic: when is each better?
  • Payment succeeds after the hold expired. Now what?
Splitwise machine coding: model the classes and implement "simplify debts".

Classes: User, Group, Expense (payer, amount, splits), a Split hierarchy or SplitStrategy (equal, exact, percent) with validation, and a BalanceSheet map. Keep amounts in integer paise. To simplify, compute each user's net balance (total paid minus total share). The sum is zero. Put creditors in a max-heap and debtors in a max-heap by absolute value. Repeatedly settle min(top debtor, top creditor) and push back any remainder. That gives at most n - 1 transfers. Thread safety: ConcurrentHashMap.merge for balance updates.

How to answer

Validate splits first (sums, percentages), then balances, then the greedy algorithm with a worked 4-person example.

Likely follow-ups
  • How do you round 100 split 3 ways?
  • Is greedy always minimal? (No. The true minimum is NP-hard in general, but greedy is accepted.)
Strategy vs State pattern: what is the difference?

Both delegate behaviour to a helper object behind an interface. In Strategy, the client chooses the algorithm, strategies are independent, and they do not change the context, for example a fee strategy or a payment method. In State, the object's behaviour depends on its current state, and the state objects themselves trigger transitions to other states, for example an elevator going from MovingUp to DoorsOpen. Rule of thumb: "different ways to do X" means Strategy, and "different behaviour depending on status" means State.

How to answer

One sentence on the similarity, one on the difference (who switches), one example of each.

Likely follow-ups
  • Model a vending machine.
  • When would a simple enum and switch be better? (few states that rarely change)
Design an LRU cache class, then make it thread-safe and pluggable to LFU.

A HashMap<K, Node> plus a doubly linked list gives O(1) get and put. On a hit, move the node to the head. On insert past capacity, drop the tail. Put eviction behind an EvictionPolicy interface (keyAccessed, keyAdded, evict), so LFU (frequency buckets, each an LRU list) is a new class. For thread safety, one lock around get and put is correct but serialises everything. Striping into N independent segments, each with its own lock and LRU list, scales better at the cost of approximate global LRU order. Add a TTL with lazy expiry on read plus a background sweeper.

How to answer

Data structure first, then the interface seam, then the lock trade-off. If it is a combined round, then go to sharding across nodes.

Likely follow-ups
  • Why not LinkedHashMap? (fine in practice; say it, then build it yourself if asked)
  • Distribute it across nodes.
What are the most common mistakes in LLD rounds?

Over-engineering: Hello Interview says KISS is the principle candidates violate most, by adding factories and decorators nobody needs. Other common mistakes are god classes that do everything; public mutable fields; inheritance where composition fits (LSP breaks); ignoring concurrency on the scarce resource; using double for money; not asking scoping questions; and, in machine coding, code that does not run or has no demo. The fix is to scope tightly, put an interface only at the real variation points, build a thin runnable slice, then extend.

How to answer

List three or four, and pair each with the habit that prevents it.

Likely follow-ups
  • When is a Singleton acceptable?

Scenario: 50 minutes in, nothing runs

Flipkart machine coding: a food-ordering system. You have built beautiful interfaces, factories and five model classes, but no flow works end to end. 40 minutes remain.

Weak answer: keep polishing the abstractions and hope to finish all features in the last 10 minutes.

Strong answer: freeze new abstractions. Pick the single most important flow (place an order and assign a restaurant), wire it through with the simplest in-memory repository, and run it from main within 15 minutes. Then add the next mandatory feature, then validation. Leave a short comment listing what you would add next. In the review, explain where the extension points are. A working, modular slice beats a complete but non-running design.

Likely follow-ups
  • Reviewer: "Add restaurant rating-based assignment." Show it is one new strategy class.

Scenario: the combined round that never reached the classes

Microsoft SDE-2, 75 minutes, "design a distributed LRU cache". You spent 55 minutes on consistent hashing and replication. The interviewer then asks for the eviction code and you have 20 minutes.

Weak answer: rush the code with a single global lock and no interface, and skip edge cases.

Strong answer (next time): at minute 2, ask "broad or deep?" and agree a split, roughly 20 minutes HLD and 35 minutes LLD. In the time left now, write the HashMap plus doubly linked list core with an EvictionPolicy seam, say aloud that you would stripe locks per segment, and list TTL and hot-key handling as next steps. Show you can manage time, not just design.
