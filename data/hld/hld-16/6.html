Class diagrams in 5 minutes

Most interviewers accept a quick, informal UML (Unified Modeling Language) class diagram. A box has three parts: the name, the fields (- means private), and the methods (+ means public). The lines are what matter:

One worked example: ParkingLot, Floor, Spot

Here is how you would talk through the parking lot's core classes in the first 5 minutes, writing exactly this on the whiteboard or in a text file:

ParkingLot                       (one per site; a singleton is fine in a demo)
  - floors : List<Floor>           ParkingLot ◆── Floor        1 to 1..*  (composition)
  - strategy : SpotStrategy        ParkingLot ──> SpotStrategy             (association)
  + park(v : Vehicle) : Ticket
  + unpark(t : Ticket) : Receipt

Floor
  - number : int
  - spots : Map<SpotType, List<Spot>>  Floor ◆── Spot       1 to 1..*  (composition)
  + freeSpot(type : SpotType) : Optional<Spot>

Spot
  - id : String
  - type : SpotType               (enum: BIKE, COMPACT, LARGE, EV)
  - occupiedBy : Vehicle or null  Spot ──> Vehicle          0..1        (association)
  + tryOccupy(v : Vehicle) : boolean   (atomic: see concurrency below)

Vehicle (abstract)  <|── Bike, Car, Truck           (inheritance)
SpotStrategy (interface) <|.. NearestFirst, EvFirst  (implements)
Ticket  ──> Spot, Vehicle, entryTime                (association)

Read it out like this: "A ParkingLot owns its floors, and a floor owns its spots: delete the lot and they go too, so that is composition. A spot only refers to the vehicle parked in it, because the car exists before and after, so that is a plain association with multiplicity 0..1. Vehicle is abstract with three subclasses because each needs a different spot size. Choosing a spot varies between sites, so it is a SpotStrategy interface (Strategy pattern), and that is where I would add EV-first later without touching ParkingLot (open/closed)." That one paragraph shows all five line types and two principles.

Two other diagrams help in specific problems. A state diagram (elevator, vending machine, order status) shows states as circles and events as arrows. A sequence diagram (BookMyShow booking, ATM withdrawal) shows who calls whom, in time order. Draw one only if it makes a tricky flow clearer.
