Four classic LLD walkthroughs (outline level)

Each outline follows the same five steps from AlgoMaster's "how to answer an LLD problem": clarify requirements, pick entities, design classes and relationships, implement the core, then handle edge cases. The requirement lists are condensed from AlgoMaster's open-source problem set.

1. Parking lot

Requirements to confirm: multiple floors; vehicle types (bike, car, truck) and matching spot sizes; assign a spot on entry, free it on exit; show live availability; several gates at once; fee by duration.

  • Patterns: Strategy for spot allocation and fees. Factory for vehicles. Observer for display boards. AlgoMaster's version makes ParkingLot a Singleton. Mention it, and add that you would rather inject one instance so tests stay easy.
  • Concurrency: two gates can grab the same spot. Use an atomic "mark occupied if free" per spot, or keep one free-spot queue per (floor, size) and poll() from a concurrent queue.
  • Extension questions: EV charging spots (new spot type plus allocation rule), reservations, multiple lots (now it is an HLD question: see d54 Amazon Locker for the same shape).

2. Elevator system

Requirements to confirm: N elevators, M floors; hall calls (up/down buttons on a floor) and car calls (floor buttons inside); capacity limit; minimise waiting; prefer elevators already moving toward you in the right direction.

  • Classes: Elevator (current floor, direction, state, stop sets), Request (source, destination, direction), ElevatorController (receives hall calls, picks an elevator), Door, Display.
  • Scheduling: each elevator keeps two sorted sets of stops, for up and down. It serves all stops in its current direction, then reverses. This is the LOOK variant of the SCAN "elevator algorithm", the same one used for disk-arm scheduling. Use a TreeSet so "next stop above me" is O(log n).
  • Patterns: State for the elevator. Strategy for the dispatcher (nearest car, least loaded, zone-based). Observer for floor displays. Command if you queue requests.
  • Concurrency: buttons are pressed from many threads. Each elevator runs its own loop thread and reads from a thread-safe request queue. Do not let the controller mutate elevator state directly.

3. BookMyShow (movie ticket booking)

Requirements to confirm: browse movies by city, theatre and show; view the seat map; choose seats; pay; confirm. No double booking. Seat types and prices. Admin adds shows.

  1. Hold. tryLock(show, [A5, A6], user) places a temporary hold with a TTL. If any seat is held by someone else, the whole request fails and partial holds roll back.
  2. Create the booking. A Booking in state PENDING, priced from each seat's type (normal, premium).
  3. Pay. A PaymentStrategy chosen at runtime. The booking service does not know whether it is UPI or card.
  4. Success. Payment OK: the booking moves to CONFIRMED, seats move to BOOKED, and the hold is removed.
  5. Failure or timeout. No payment before the TTL: the hold expires on its own and the seats are free again. No cleanup job is needed for correctness.
  • Classes: Movie, Theatre, Screen, Show (movie + screen + time), Seat (row, number, SeatType), Booking (BookingStatus), User, SeatLockProvider, PaymentStrategy.
  • Key decision: seat status is per show, not per physical seat. Keep a Map<showId, Map<seatId, status>> or a ShowSeat object.
  • HLD twin: the hold becomes Redis SET NX PX or a DB row with an expiry, plus idempotent payment callbacks. See d14 Ticket booking and d10 Payment system.

4. Splitwise

Requirements to confirm: users and groups; add an expense (payer, amount, participants); split equally, by exact amounts or by percentage; show who owes whom; settle up; history.

  • Classes: User, Group, Expense (payer, amount, list of Split), abstract Split with EqualSplit, ExactSplit and PercentSplit, a BalanceSheet (Map<userId, Map<userId, amount>>), and Transaction for settlements.
  • Patterns: Strategy (or a Split hierarchy) for split types, Factory to build splits from input, Observer to notify participants.
  • Edge cases: percentages must sum to 100; exact splits must sum to the amount; rounding (100 / 3) needs a rule, such as giving the leftover paisa to the payer; use BigDecimal or integer paise, never double.
  • Concurrency: two expenses updating the same pair's balance. Use ConcurrentHashMap.merge for atomic adds, or lock the pair in a fixed order.
  • HLD twin: a real money ledger is append-only double-entry. See d41 Digital wallet and ledger.

Also seen often: LRU and LFU caches (Microsoft, Walmart), an in-memory key-value store (Microsoft), chess (Amazon bar raiser), vending machine (State), rate limiter (Strategy per algorithm), and pub-sub. AlgoMaster's repo has requirement lists and code for most of them.
