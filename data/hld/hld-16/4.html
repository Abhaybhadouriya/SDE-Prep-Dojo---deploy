SOLID and the principles that actually get graded

SOLID is five rules for classes that are easy to change. Learn each with one picture-sized example. The examples below are our own, in the style of AlgoMaster's "SOLID explained with code".

PrinciplePlain wordsInterview-sized exampleSmell that breaks it
Single responsibilityOne class, one reason to change.ParkingLot does not compute fees. FeeCalculator does.A BookingManager that books, pays, emails and logs.
Open/closedAdd behaviour by adding classes, not editing old ones.New split type = new SplitStrategy class.if (type == "EQUAL") ... else if (type == "PERCENT") in five places.
Liskov substitutionA subclass must work wherever its parent works.Any Vehicle can call getSize().Bicycle.startEngine() throws "not supported".
Interface segregationSmall, focused interfaces.Payable and Refundable as separate interfaces.One fat PaymentGateway with 15 methods, half unused.
Dependency inversionDepend on interfaces and inject the real thing.BookingService(SeatLockProvider locks, PaymentStrategy pay)new RazorpayClient() inside the service.

From your world

The Linux VFS is SOLID in C. struct file_operations is an interface: a table of function pointers (read, write, open). ext4, procfs and a socket each fill it in differently. The kernel's read() path depends only on the table (dependency inversion), and adding a new filesystem never touches the VFS core (open/closed). A net_device_ops table plays the same role for drivers.

Where this breaks: the kernel has no inheritance and no garbage collector, so "Liskov" and "interface segregation" show up only as conventions; in Java or Python the compiler and the type system enforce them, and the interviewer expects you to use those features.

Careful: Hello Interview says the principle candidates violate most is KISS (keep it simple). The usual cause is over-engineering: adding factories, builders and decorators to show off patterns where a plain class is enough. Also follow YAGNI (you aren't gonna need it): do not add valet parking unless the requirements mention it. Use a pattern only where the problem says something will vary.

Three more rules you will be judged on: composition over inheritance (a Car has a ParkingStrategy, rather than SmartCar extends Car), encapsulation (no public mutable fields, so state changes only go through methods that check rules), and the Law of Demeter (avoid chains like order.getCustomer().getAddress().getCity()).
