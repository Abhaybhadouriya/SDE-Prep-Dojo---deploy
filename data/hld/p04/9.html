Quick quiz

A user updates their profile and immediately sees the old one. Writes go to the primary, reads to async replicas. What is the most likely cause?

  1. The cache TTL is too long
  2. The index is missing
  3. Replication lag
  4. A hot key
With asynchronous replication, the replica may not yet have applied the write. Route that user's reads to the primary briefly, or use the log position.

In cache-aside, what should the application do with the cache key when the row is updated?

  1. Overwrite it with the new value
  2. Delete it, after writing the database
  3. Nothing; wait for the TTL
Deleting is safe against reordering: two concurrent overwrites can land in the wrong order, two deletes cannot. The next read refills it.

Adding more cache nodes does not fix a hot key because...

  1. The key still hashes to a single node
  2. Redis is single-threaded per cluster
  3. The TTL is shared
Consistent hashing places each key on one node. Spread it with suffixed copies or local caches.

Bots request millions of IDs that do not exist. Which pair of fixes targets this?

  1. Write-through and longer TTLs
  2. Read replicas and sharding
  3. Negative caching and a Bloom filter
  4. A CDN and versioned URLs
This is cache penetration. Cache "not found" briefly and reject definite non-members with a Bloom filter.

What did Facebook's memcache leases achieve on herd-prone keys?

  1. Hit rate went from 50% to 99%
  2. Peak DB queries dropped from about 17K/s to 1.3K/s
  3. Cache memory dropped by half
The paper reports a peak of 17K/s without leases and 1.3K/s with them, because only one client per key per 10 s may refill.

Thousands of keys were all loaded at 08:55 with the same 300 s TTL. What is the simplest fix for the 09:00 spike?

  1. Remove the cache
  2. Use write-behind
  3. Add a read replica
  4. Add random jitter to the TTL
Synchronised expiry causes the spike. Jitter spreads the expiries across a window.

A home feed needs a join and sort that takes 800 ms. Which rung fits best?

  1. A precomputed read model (CQRS / fan-out)
  2. A pull CDN
  3. A longer TTL on the per-user result
The problem is the query's shape, not its count. Precompute the answer on write so the read is one key lookup.
