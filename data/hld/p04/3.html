Caching is right when
  • Reads repeat (a skewed, Zipf-like popularity curve)
  • Staleness of seconds is fine
  • The source query is expensive
  • The data set's hot part fits in RAM
Caching is wrong when
  • Requests rarely repeat (unique search queries)
  • Data changes on most reads
  • The cache is no faster than the store
  • Correctness needs the latest value (balances)

The "wrong when" list is Karan Pratap Singh's, almost word for word: caches help only when access repeats and the data is slower to fetch from the source.

Sizing a cache, quickly

Hello Interview's "numbers to know" and the AWS article both push you to estimate rather than guess. A worked example: 100 M product pages, 2 KB each, is 200 GB. If 20% of products take 80% of views, caching the hot 20% means 40 GB - two or three Redis nodes with headroom, plus a replica each. With a 90% hit rate on 50,000 reads per second, the database sees 5,000 per second. If the hit rate drops to 50% after a cold restart, it sees 25,000 - five times its normal load. Size the database for the bad day, or protect it (coalescing, warmup, rate limits). See Estimation.

Say this: "I'll put the cache in to protect latency, but I'll size the database so it survives a cache restart, or I'll add request coalescing and warm-up, because a cache that the database cannot live without is a single point of failure."
