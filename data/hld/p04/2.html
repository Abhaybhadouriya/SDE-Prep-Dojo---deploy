The ladder: naive to best

Climb in this order. Each rung costs more complexity than the one before it, so in an interview say why the lower rung is no longer enough before you step up. Hello Interview's guide uses the same order: optimise inside the database, then scale it horizontally, then add caches outside it.

Rung 0 - Make the database do less work

Before adding machines, make each read cheaper. A missing index turns a 1 ms lookup into a full table scan. Fix that first (see Data Modeling & Indexing). Then look at denormalisation: store the author's name on the post row so the feed does not join two tables on every read. The system-design-primer notes the cost clearly: reads get faster, but writes must now update several copies, and heavy write loads can do worse than a normalised schema. A materialised view (a stored query result the database refreshes for you, in Postgres or Oracle) is the in-database version of the same idea.

Breaks when: one machine's CPU, memory or disk I/O is saturated even with good indexes. That is a physical limit; you need more machines.

Rung 1 - Read replicas

A read replica is a copy of the database that receives the primary's change log and replays it. Writes go to the primary; reads can go to any replica. Five replicas give roughly five times the read capacity.

Who decides where a query goes? Either the application (a "read" connection pool and a "write" pool) or a database proxy in the middle. ByteByteGo's read-replica guide describes the proxy option: the middleware speaks the MySQL wire protocol, so clients do not change, but now every query crosses one more highly-available box and one more network hop.

The catch is replication lag. Replication is usually asynchronous: the primary acknowledges the write before replicas have it. A user who edits their profile and immediately reloads may read from a replica that has not caught up, and see the old profile. Fixes, from simplest to strongest:

  1. Read-your-writes by time. After a user writes, route that user's reads to the primary for a short window (say 10 seconds).
  2. Read-your-writes by position. The write returns a log position (an LSN in Postgres, a GTID in MySQL). The client sends it back; the router picks a replica that has replayed at least that far, or falls back to the primary.
  3. Critical reads go to the primary. Checkout totals, balances and "is this seat free?" never read from a replica.
  4. Synchronous replicas. The primary waits for at least one replica before acknowledging. Fresher, but every write is slower and a slow replica slows everyone.

The primer lists the other costs: promotion logic when the primary dies, possible loss of writes that never reached a replica, and more lag as you add more replicas. See Replication & Consensus for the full story.

Breaks when: the data set no longer fits on one machine (replicas copy everything), or you need sub-millisecond reads, or the same few rows get so much traffic that even many replicas melt. That is when you add a cache, or shard (see Scaling Writes).

Rung 2 - A cache in front (cache-aside)

A cache is a key-value store in RAM (Redis or Memcached) that keeps answers to popular reads. The most common way to use it is cache-aside (also called lazy loading): the application checks the cache, and on a miss reads the database and fills the cache. On a write, the application updates the database and then deletes the cache key. Walk through it:

  1. Miss. The app asks the cache for user:42. It is not there.
  2. Read the truth. The app reads the row from the database (or a replica).
  3. Fill. The app stores the result in the cache with a TTL (time to live), so it expires even if we forget to delete it.
  4. Hit. The next thousand reads for user:42 are served from RAM in under a millisecond. The database never sees them.
  5. Write, then delete. On an update the app writes the database first, then deletes the key. The next read refills it with the new value. Delete is safer than overwrite because two concurrent overwrites can land in the wrong order.
  6. The race. Reader A misses and reads the OLD row. Writer B updates the row and deletes the key. Then A, a bit late, SETs the old row into the cache. Now the cache is stale until the TTL expires. Facebook calls this a "stale set"; their fix is leases (below).

Local plus remote. The AWS Builders' Library article on caching contrasts an in-process (local) cache - fastest, but every server holds a different copy and the load on the database grows with fleet size - with an external cache like Redis, which gives one shared view and survives deployments but is another system to run. Big systems use both: a tiny local cache for the hottest keys (seconds of TTL) plus a shared Redis tier.

Breaks when: the cache itself becomes the failure point. The AWS article calls this modal behaviour: the system behaves differently when an item is cached and when it is not, and a sudden shift (cache restart, a deploy that changes keys) can send the full read load to a database that was sized for 5% of it. The next rungs - and the pitfalls section - are about that.

Rung 3 - CDN and edge caching

A CDN is a fleet of cache servers in hundreds of cities. Static files (images, JS, video segments) and even whole API responses can be cached at the edge, close to the user. The primer and Karan Pratap Singh's book describe two styles:

  • Pull CDN: the edge fetches from your origin on the first request and keeps it for the TTL. Low effort, best for heavy traffic; the first request in each city is slow.
  • Push CDN: you upload content ahead of time. More control and no first-request penalty, but more storage. Netflix's Open Connect pre-positions popular titles inside ISP networks overnight, which is the extreme form (see Video Streaming).

Use versioned URLs (app.4f3a9c.js, avatar_v7.jpg) so you never need to purge: a new version is a new key. Use Cache-Control: max-age and stale-while-revalidate headers so the edge can serve a slightly old copy while it refetches.

Breaks when: content is personalised per user (a feed, a cart). You cannot cache "my feed" at a shared edge. Move up to read models.

Rung 4 - Precomputed read models (CQRS)

Sometimes the problem is not the number of reads but the shape of the query. "Show my feed" might mean "join follows with posts, sort by time, take 20". Doing that on every read is expensive whatever cache you add. Instead, build a separate store shaped exactly like the answer and keep it updated from the write side. This is CQRS (Command Query Responsibility Segregation): writes go to one model, reads come from another. Microsoft's Azure pattern guide describes the read store as possibly a different database, kept in sync by events, with the price being eventual consistency between the two.

Examples on this site: the precomputed feed list in News Feed (fan-out on write is a read model), the top-k suggestions stored at each trie node in Search Autocomplete, and the search index in Product Catalog Search (Elasticsearch is a read model fed by CDC). Distributed Transactions & Events covers CDC and the outbox that keep these in sync.

Breaks when: the read model is expensive to keep current (a celebrity with 50 million followers turns one post into 50 million writes - see Fan-out: Push vs Pull), or users need to see their own change instantly.

Level 4 - Advanced

Rung 5 - Protect the cache: the pitfalls

A cache that sits in front of a small database is not an optimisation any more; it is load-bearing. These are the four classic ways it collapses, and the fixes interviewers expect.

Pitfall 1: Cache stampede (thundering herd)

A popular key expires. In the next 50 ms, 5,000 requests miss at once, and all 5,000 run the same expensive database query and try to SET the same value. The database falls over, which makes the queries slower, which keeps more requests in the miss window. Fixes:

  • Request coalescing (single-flight). Only one request per key goes to the database; the others wait for its result. Discord's Rust "data services" do this in front of their message database: the first request for a row starts a worker task, and later identical requests subscribe to it. They also route by channel ID with consistent hashing, so all requests for one channel land on the same instance - which makes the coalescing work. Instagram described a similar trick: cache a promise of the value, not the value, so everyone waits on one fetch.
  • Leases. Facebook's memcache paper gives a client a 64-bit lease token on a miss. Only the lease holder may fill the key, and the server hands out at most one token per key every 10 seconds; others are told to wait briefly and retry. On a set of herd-prone keys measured for a week, peak database queries fell from 17K/s without leases to 1.3K/s with them.
  • Probabilistic early refresh (XFetch). The intuition in one line: the closer a key is to expiry, the more likely each reader is to refresh it early. With many readers, one of them almost always refreshes a little before the expiry, so the key never actually goes missing and no herd forms. No locks, and expiries spread out naturally.
    Optional depth: the XFetch formula (safe to skip)

    Vattani, Chierichetti and Lowenstein (VLDB 2015) give each reader this test: refresh early if now - delta * beta * log(rand()) >= expiry. Here delta is how long the recompute takes and beta (default 1) tunes eagerness. rand() is between 0 and 1, so -log(rand()) is a positive random number that is usually small and only sometimes large: most readers do nothing, and a few "look ahead" far enough to cross the expiry and refresh. A slow recompute (big delta) makes readers look further ahead, so expensive keys are refreshed earlier.

  • Jittered TTLs. If you load 10,000 keys at startup with TTL 300 s, they all expire together at 300 s. Use 300 s ± random 30 s. (When a whole cache tier expires at once, people call it a cache avalanche.)
  • Serve stale. Keep a soft TTL (refresh after it) and a hard TTL (stop serving after it). The AWS caching article recommends this so a failing database does not turn straight into user errors.

From your world

The thundering herd name comes from the kernel: many processes sleeping on one event (an accept() on a listening socket) all wake, and all but one go back to sleep having wasted a context switch. Linux fixed it with exclusive wake-ups (EPOLLEXCLUSIVE, SO_REUSEPORT). Request coalescing is the same fix one layer up: wake one worker, let the rest wait for its answer. And Facebook's lease is just load-link/store-conditional for a cache key - the paper says so itself.

Pitfall 2: Hot keys

Consistent hashing puts each key on exactly one cache node. If one key - the IPL final score, a viral tweet, the flash-sale product - gets 30% of all traffic, that one node's CPU or NIC saturates while the rest sit idle. More nodes do not help, because the key still lives on one node.

  • Local (L1) cache for detected hot keys, with a very short TTL. One hundred app servers absorb the load before it reaches Redis.
  • Key replication with suffixes: store score#0 .. score#N-1, read a random one, write all. Facebook did a version of this with a dedicated "replicated pool" for very frequently read data; it had about 2.7 times the get rate of their next busiest pool.
  • Read replicas of the cache (Redis replicas) for that shard.
  • Detect hot keys: sample requests, count top-k with a Count-Min sketch (see Top-K / Heavy Hitters), and promote the winners to the L1 cache automatically.

Pitfall 3: Cache penetration

Requests for keys that do not exist - a bot probing random short URLs, a deleted product ID - always miss the cache and always hit the database, because there is nothing to cache. Fixes: negative caching (cache "not found" with a short TTL; the AWS article reports real incidents caused by not doing this), and a Bloom filter of all valid IDs in front of the database, which answers "definitely not present" in memory (see Big Data & Probabilistic Structures).

Pitfall 4: Stale data and invalidation

Phil Karlton's old joke says cache invalidation is one of the two hard things in computer science. Practical rules:

  • Always set a TTL as a safety net, even when you also delete on write.
  • Delete, do not update, on write. Two updates can arrive out of order; two deletes cannot do harm.
  • Invalidate from the commit log, not the web server. Facebook runs a daemon (mcsqueal) on every database that reads committed SQL and broadcasts deletes. Because the log is durable, lost deletes can be replayed. Batching deletes this way gave an 18x improvement in deletes per packet. The modern version is CDC with Debezium into Kafka (see CDC Pipeline).
  • Version the value. Store the row version with the cached value and refuse a SET with an older version - this kills the stale-set race.
  • Plan cold starts. Facebook's "cold cluster warmup" lets an empty cache cluster read from a warm one instead of the database, bringing it to full capacity in hours instead of days. Their memcached servers took a few hours to reach 90% of peak hit rate, so restarts were done carefully and the cache was moved into shared memory so it survived a software upgrade.

And when a cache node dies?

Rehashing a dead node's keys onto the survivors moves load onto nodes that do not have the data, so they all miss together. Facebook's answer was a small spare pool called Gutter - about 1% of the memcached servers. When a get gets no reply, the client retries in Gutter, whose entries expire quickly. The paper reports this cut client-visible failures by 99% and that Gutter hit rates exceeded 35% within four minutes of a server failure.
