Interview: phrases, traps and questions

Phrases that land: "This is read-heavy, roughly 100:1, so I'll optimise the read path." - "Cache-aside with delete-on-write and a TTL as a safety net." - "Replicas give read-your-writes only if I route the writer back to the primary or track the log position." - "For the hot key I'll add a local cache and replicate the key across nodes." - "The database must survive a cold cache."

Traps: adding a cache before checking the index; caching data that must be exact (balances, seat holds); forgetting what happens when the cache is empty; updating instead of deleting on write; one TTL for every key (synchronised expiry); assuming more cache nodes fix a hot key.

Cache-aside vs write-through: which would you use, and how do you handle stale data?

Default to cache-aside: read the cache, on a miss read the DB and fill with a TTL; on write, update the DB then delete the key. Write-through keeps the cache warm for data read right after writing, at the cost of slower writes and caching things nobody reads. For staleness: TTL as a safety net, delete rather than overwrite, and close the stale-set race with leases or a version check (only SET if the version is newer).

How to answer

Name the flow in one line, give one scenario where each wins, then volunteer the race condition before you are asked. That last part is what separates SDE-2 answers.

Likely follow-ups
  • Why delete instead of update?
  • What if the delete fails after the DB commit? (TTL, or invalidate from CDC so it is retried)
  • Write-behind for a like counter - what can you lose?
What is a cache stampede and how do you prevent it?

A hot key expires and thousands of concurrent requests miss together and all hit the database. Prevent it with request coalescing (single-flight or a short lock: one fetch per key), leases (Facebook's memcache gives one fill token per key per 10 s; peak DB load on herd-prone keys fell from 17K/s to 1.3K/s), probabilistic early refresh (XFetch), jittered TTLs, and serving stale while one request revalidates.

How to answer

Define it in one sentence, list three fixes from cheapest to strongest, quote one real number. Mention that the lock or lease must expire so a crashed holder does not block everyone.

Likely follow-ups
  • Coalescing is per process - what about 200 app servers? (route by key with consistent hashing, as Discord does, or use a distributed lease)
  • What if the recompute takes 5 seconds?
  • How is an avalanche different?
One product page gets 40% of traffic during a sale and its cache node is at 100% CPU. What do you do?

It is a hot key; adding nodes does not help because the key lives on one node. Short term: put the product in an in-process L1 cache on every app server with a 1-2 s TTL, and serve the static page from the CDN. Structural: replicate the key as sku#0..sku#7 on different nodes and read a random suffix; add Redis replicas for that shard. Detect hot keys automatically with sampling and a top-k sketch so this happens before the sale, not during.

How to answer

Diagnose first (why scaling out fails), then fix at the layer closest to the user, then the structural fix, then detection.

Likely follow-ups
  • The price changes mid-sale - how stale can the L1 copy be?
  • How do you write all 8 replicas consistently?
  • Where does the stock count live? (not in this cache - see Contention)
Explain replication lag and how you would give users read-your-writes.

With asynchronous replication the primary acknowledges before replicas apply the change, so a replica read right after a write may return old data. Options: route the writing user to the primary for a few seconds; return the commit log position (LSN/GTID) with the write and only read from replicas that have caught up; send critical reads to the primary always; or use a synchronous replica and pay write latency.

How to answer

Explain why lag exists in one line, then give two fixes with their costs. Note that read-your-writes is per user; other users may still see old data briefly, which is usually fine.

Likely follow-ups
  • What about monotonic reads (not going back in time between two replicas)? (stick a user to one replica)
  • The user has two devices - does your fix still work?
Your Redis cluster restarts and every key is gone. Walk me through the next five minutes.

Hit rate drops toward zero and the database sees the full read load - if it normally sees 10% of reads, that is a 10x surge. Protections, in order: request coalescing so each key is fetched once; a rate limit or concurrency cap in front of the DB with fallback to stale or degraded responses; warm the cache from a warm replica cluster (Facebook's cold-cluster warmup brought caches to full capacity in hours instead of days); restart cache nodes one at a time rather than all at once; use Redis replicas and persistence so a single node failure is a failover, not a cold start.

How to answer

Quantify the surge first, then protect the DB, then recover the cache, then prevent recurrence.

Likely follow-ups
  • Would you size the DB for zero hit rate?
  • How do you test this? (AWS: load test with caches disabled)
TinyURL: how do you serve 100x more redirects than creations with p99 under 50 ms?

The mapping is immutable after creation, which is the best case for caching. Store code-to-URL in a KV store, put Redis (LRU) in front, and push the very hottest codes to the CDN edge. Use 301 if you want browsers to cache (less load, lose analytics) or 302 to count every click. Cache "not found" briefly and keep a Bloom filter of valid codes so random-code scanners do not reach the DB.

How to answer

Point out that immutability removes the invalidation problem, then spend your time on hot links and penetration.

Likely follow-ups
  • A link is deleted for abuse - how fast does it stop working at the CDN?
  • How big is the cache for 1 B links?
The home feed query joins follows and posts and takes 800 ms. Caching the result per user does not help. Why, and what do you do?

Per-user results have a low hit rate (each user reads their own feed a few times) and go stale whenever anyone they follow posts. The fix is to change the shape of the data: a CQRS read model where each user's feed is a precomputed list of post IDs, updated by fan-out on write from a Kafka stream, with hydration from a shared post cache (high hit rate, because posts are shared). Celebrities are pulled at read time and merged.

How to answer

Say why the cache fails (hit rate and invalidation), then move the work from read time to write time, then handle the fan-out explosion.

Likely follow-ups
  • What threshold makes someone a celebrity?
  • How long can the read model lag?
  • See Fan-out
Autocomplete must answer in under 100 ms for every keystroke. Where do you cache?

At every layer: debounce and cache in the browser (prefixes repeat as the user types and deletes); the CDN or edge for the most common short prefixes; an in-memory trie service with the top-k already stored at each node, so a lookup is O(prefix length) with no sorting. The trie is a read model rebuilt offline from query logs and swapped in, so the serving path never writes.

How to answer

Walk outward-in along the request path and say what each layer saves.

Likely follow-ups
  • Prefix "s" is much bigger than "x" - how do you shard?
  • How do trending queries appear within minutes?
Attackers send millions of requests for product IDs that do not exist. Your cache hit rate is fine but the DB is overloaded. Why?

This is cache penetration: misses for non-existent keys are never filled, so each one reaches the DB. Cache negative results with a short TTL (30-60 s), put a Bloom filter of valid IDs in front (no false negatives, so a "no" is safe to return immediately), validate ID format at the edge, and rate-limit per client.

How to answer

Name it, explain why ordinary caching cannot help, give the two data-structure fixes and one edge fix.

Likely follow-ups
  • A new product is added - how does the Bloom filter learn about it?
  • How do you delete from a Bloom filter? (you cannot; rebuild or use a counting filter)
You run caches in three regions; writes go to one primary region. How do you keep remote caches from caching stale data?

If the web server in the primary region deletes keys in a remote region immediately, the remote region may refill from its replica database before replication arrives - caching old data. Facebook's answer was to invalidate from each region's own database replication stream (mcsqueal), so a delete in a region happens only after that region's database has the change. For users who just wrote, they set a "remote marker" so reads go to the primary region until replication catches up.

How to answer

Describe the race precisely (invalidate arrives before data), then the fix (invalidate after local replication), then read-your-writes for the writer.

Likely follow-ups
  • How would you do this with CDC and Kafka MirrorMaker?
  • What does the user see during a region failover?
25 million people watch a live match and refresh the score card. Design the read path.

The score is one tiny object read by millions: the ultimate hot key. Serve it from the CDN with a 1-2 second TTL and stale-while-revalidate, so the origin sees roughly one request per edge per second, not millions. Behind the CDN, an origin cache with coalescing so all edges collapse into one DB read. Better still, push updates over a long-lived connection (see Real-time Updates). Pre-scale before the match - autoscaling reacts too slowly to a toss.

How to answer

Compute the fan-in at each layer (edges x 1/s), show the origin load is tiny, then cover the push alternative.

Likely follow-ups
  • What if the CDN itself throttles you?
  • How fresh is "fresh enough" for a score?

Scenario: the database melts every day at 9:00 sharp

A shopping app's product database spikes to 100% CPU at 09:00:00 every morning for about 30 seconds, then recovers. Traffic is smooth. A nightly job refreshes all product data at 08:55 and repopulates the cache.

Weak answer: "Add more read replicas and a bigger Redis."

Strong answer: "Every key is written at 08:55 with the same 300 s TTL, so they all expire at 09:00:00 - a synchronised expiry (avalanche). I'd add TTL jitter (±10-20%), have the job refresh keys in place rather than relying on expiry, add single-flight so each key is fetched once, and use soft/hard TTLs so readers get the old value while one refresh runs. I'd confirm by graphing cache miss rate against DB CPU."

Likely follow-ups
  • Why not just set a 24-hour TTL?
  • How do you alert on this before customers notice?

Scenario: "I changed my name but the app still shows the old one"

Users report that after editing their profile, a refresh sometimes shows the old name for a few seconds, and occasionally for 5 minutes.

Weak answer: "Lower the TTL to 10 seconds."

Strong answer: "Two bugs. The few seconds is replica lag - the reload read a replica; route the writer's reads to the primary for a short window, or pass the LSN. The 5 minutes is the stale-set race: a slow reader filled the cache with the old row after our delete, and it lived for the full TTL. Fix with a version check on SET, or a lease, or delete again a second later (delayed double delete) as a cheap patch."

Likely follow-ups
  • Which fix would you ship today, and which next quarter?
