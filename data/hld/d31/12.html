Quick quiz

In a Snowflake ID, what guarantees that two different workers never create the same ID?

  1. The timestamp bits, since no two workers ever read the same millisecond
  2. The worker (machine) ID bits
  3. The sequence bits, since the counter is synced across all workers
  4. The sign bit, which each worker flips to mark its own IDs
Two workers can have the same timestamp and sequence, but never the same worker ID, so their IDs always differ.

About how long do 41 bits of milliseconds last?

  1. About 7 years, which is why a custom epoch is required
  2. About 700 years, since 2^41 ms is roughly 2 x 10^13 ms
  3. About 35 years, because the sign bit halves the range
  4. About 70 years
2^41 ms is about 2.2 x 10^12 ms, about 69.7 years.

A worker sees the clock is 3 ms behind the last timestamp it used. The safest move is:

  1. Keep issuing with the current time; the sequence bits keep IDs unique
  2. Reset the sequence to 0 and continue; the worker ID keeps IDs unique
  3. Wait until the clock passes the last timestamp, or refuse
  4. Bump the worker ID by one so new IDs land in a fresh range
Issuing with an older timestamp can recreate an ID already issued. Waiting (small jumps) or refusing is correct.

Why do Flickr's two ticket servers use auto-increment-increment = 2?

  1. To make IDs time-sorted when both servers are read together
  2. So one hands out odd numbers and the other even
  3. To halve the write load on each server's one-row table
  4. So a client can tell which datacenter issued an ID
With offsets 1 and 2 and a step of 2, the two servers have disjoint number sets.

Why are random UUIDv4 primary keys slow in a B-tree index compared with Snowflake IDs?

  1. Random keys hit random pages (splits, cache misses) and are 2x the size
  2. They cannot be compared with <, so the index falls back to hashing
  3. Each one needs a round trip to a coordinator before the insert
  4. Their version bits are re-checked on every lookup, doubling read CPU
Time-ordered keys append at the right edge; random keys scatter writes. RFC 9562 cites this as a reason for UUIDv7.

What extra benefit does Instagram's layout give?

  1. IDs fit in 32 bits, which halves the primary-key index size
  2. No clock is needed, because PostgreSQL sequences already order rows
  3. Each shard can issue unlimited IDs per ms without sequence wrap
  4. The shard ID is inside the ID, so routing needs no lookup
13 bits of shard ID let any service find the row's shard from the ID alone.

Your API returns IDs as JSON numbers and the web app shows wrong IDs. Why?

  1. JS numbers lose precision above 2^53; send 64-bit IDs as strings
  2. A base62 encoding bug in the API layer drops the last character
  3. Clock skew between API servers produces slightly different IDs
  4. The browser sorts the IDs as strings and reorders the digits
JS uses 64-bit floats with 53 bits of integer precision. Discord sends snowflakes as strings for this reason.
