Where Kafka, Kubernetes and Docker fit

  • Kubernetes. Run a standalone ID service as a StatefulSet, not a Deployment: pods get stable names (idgen-0, idgen-1...), and the ordinal makes a natural worker ID. Kubernetes also exposes the ordinal as the pod label apps.kubernetes.io/pod-index (added in 1.28), which you can pass in with the Downward API. Combine it with a cluster ID so two clusters never overlap. Use a PodDisruptionBudget so a rollout never takes all generators down at once.
  • Pod time. Containers share the node's kernel clock, so clock discipline (chrony/NTP slewing) is a node setting, not a pod setting. Put it in your node image. See Docker internals for why containers have no separate clock.
  • Kafka. Kafka gives each record an offset that is unique only within one partition. It does not give you a global ID. Many pipelines stamp a Snowflake ID on each event at the producer so consumers can dedupe (an idempotency key) and sort events across partitions. See Delivery Semantics.
  • Docker. The ID library ships inside each service's image; nothing special. If the worker ID comes from an environment variable, never bake it into the image, or every container started from it gets the same ID.
