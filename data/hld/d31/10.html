How real companies do it

  • Twitter (2010). Built Snowflake when moving off MySQL; it needed "minimum 10k ids per second per process" and k-sorted 64-bit IDs. The open-sourced Thrift version is archived; the code shows the 41/5/5/12 layout and the refuse-on-rollback rule.
  • Flickr (2006). Two MySQL ticket servers, odd/even, using REPLACE INTO on a one-row table plus LAST_INSERT_ID(). The author called it the "dumbest possible thing that will work". It had run since January 2006.
  • Instagram (2012). IDs made inside PostgreSQL per logical shard: 41 bits time, 13 bits shard, 10 bits sequence, custom epoch 1314220021721.
  • Discord. Snowflakes with a 2015 epoch (1420070400000), 42-bit timestamp, 5-bit worker, 5-bit process, 12-bit increment, sent as strings in JSON.
  • Sony. Sonyflake: 39 bits of 10 ms units, 8-bit sequence, 16-bit machine ID, trading per-machine rate for a 174-year life and 65,536 machines.
  • Baidu. UidGenerator: seconds-based, 22-bit worker IDs assigned per boot from MySQL, and a padded ring buffer of pre-made IDs.
  • Meituan. Leaf offers both segment mode (double-buffered DB ranges) and snowflake mode (ZooKeeper worker IDs, clock checks every 3 s); about 50,000 QPS per 4C8G VM, TP999 1 ms.
