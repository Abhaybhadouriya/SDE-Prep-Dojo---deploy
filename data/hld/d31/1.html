Requirements

Always ask before you draw. The answers change the design a lot: "unique" alone is easy (UUID), "unique + 64-bit + time-sorted" is the real problem.

Functional

  • nextId() returns an ID that has never been returned before, by any generator, ever.
  • IDs are numeric and fit in a 64-bit signed integer (so they fit a BIGINT column and a Java long).
  • IDs are roughly time ordered ("k-sorted"): an ID made later is usually bigger. Snowflake's README set the bound at about 1 second and aimed for tens of milliseconds.
  • Optional: batch call nextIds(n); decode an ID back to its creation time (handy for debugging and for "posts before time T" queries).

From your world

p99 is tail latency, like the worst-case queueing delay through a switch buffer, not the average. An ID call that is fast on average but stalls 1 request in 100 for 50 ms stalls 1 write in 100 across the whole company. An SLO (service level objective) is the target we alert on, for example "p99 under 2 ms over 5 minutes".

Say this early: "Unique is easy; unique and sortable and 64-bit without coordination is the actual problem." It shows you know why UUIDv4 is not the end of the conversation.
