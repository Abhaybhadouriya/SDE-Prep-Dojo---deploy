Deep dives: the hard parts

1. The clock goes backwards

Snowflake trusts the wall clock. NTP can step the clock back, a VM can be paused and resumed, and leap seconds happen. If a worker reuses a millisecond it already used, with a sequence it already used, you get a duplicate ID, which is the one thing this system must never do.

  • Refuse. Twitter's code compares now to lastTimestamp and throws "Clock moved backwards. Refusing to generate id" until time catches up. Its README recommends running NTP in a mode that does not step the clock back (slewing only).
  • Wait out small jumps. Meituan Leaf waits if the rollback is 5 ms or less (it sleeps twice the offset, then checks again) and raises an error and alerts for anything bigger.
  • Guard across restarts. In-memory last is lost on restart. Leaf writes each node's time to ZooKeeper every 3 seconds and refuses to start if the local clock is behind its last report, or far from the average of the other nodes. Meituan says this logic protected them during the 2017 leap second.
  • Borrow from the future. Baidu's UidGenerator uses seconds, not milliseconds, and lets the timestamp run ahead of real time when it is busy, so it never needs the wall clock to move forward first.

From your world

This is CLOCK_REALTIME vs CLOCK_MONOTONIC. Wall time can jump (settimeofday, NTP step); monotonic cannot, but it resets at boot. A robust generator uses the wall clock only as the ID value and a persisted high-water mark to make sure it never goes below the last value issued, which is the same idea as a TCP sequence number never moving backwards within a connection.

2. Assigning worker IDs safely

Two live workers with the same worker ID will create duplicates within the first millisecond they overlap. Options, from simplest to most robust:

MethodHowRisk
Static configOps writes worker_id=17 in each host's configHuman error; breaks with autoscaling
Derived from IP / hostnameSonyflake's default uses the lower 16 bits of the private IPFine inside one /16; collides across VPCs or after IP reuse
Kubernetes StatefulSet ordinalPod idgen-17 uses 17Unique within one StatefulSet only; add a cluster/DC prefix
ZooKeeper / etcd leaseCreate a sequential or ephemeral node; its number is your ID; renew with a heartbeatNeeds the coordinator at startup; a paused worker must stop when its lease expires
DB row per boot (Baidu)Insert a row at startup; the auto-increment row ID becomes the worker IDBurns IDs on every restart, so Baidu gives worker ID 22 bits (about 4.2 million)

Zombie worker trap. A worker freezes (long GC pause), its lease expires, a new worker takes the same ID, then the old one wakes up and keeps issuing. Fix: the worker checks lease validity before issuing and stops if it has not renewed within the lease time minus a safety margin. This is the same fencing problem as in the Distributed Lock Service.

Stop here for SDE-1. If you can draw the 41/10/12 layout, explain clock rollback (wait or refuse) and explain how worker IDs are leased, you have the interview-sufficient core. Deep dives 3-6 (bit budgets across companies, Instagram's in-database IDs, segments, UUIDv7) are SDE-2 depth: read them when the basics feel easy.

3. Choosing the bit split

The 64 bits are a budget. Every real system spends it differently:

SystemTimeMachine / shardSequenceResult
Twitter Snowflake41 bits, ms5 DC + 5 worker12 bits~69 years, 1,024 workers, 4,096/ms each
Instagram41 bits, ms13-bit logical shard10 bits8,192 shards, 1,024/ms per shard, made inside PostgreSQL
Discord42 bits, ms since 2015-01-015 worker + 5 process12 bitsSame as Snowflake with a later epoch
Sonyflake39 bits, units of 10 ms16 bits8 bits~174 years, 65,536 machines, only 256 per 10 ms each
Baidu UidGenerator28 bits, seconds22 bits13 bits~8.5 years by default (2^28 s / 31.56M s per year; Baidu's README rounds to 8.7), millions of worker IDs, 8,192/s per worker plus future-borrowing

Rule of thumb: more time bits = longer life; more machine bits = more generators (good for autoscaling and per-boot IDs); more sequence bits = more IDs per tick per generator. You cannot have all three.

4. Instagram's trick: generate the ID inside the database

Instagram (2012) sharded PostgreSQL into several thousand logical shards mapped onto fewer physical servers. Each logical shard is a schema with a PL/pgSQL function next_id() used as the column default. It takes the current milliseconds minus a custom epoch, shifts left 23, ORs in the 13-bit shard ID shifted left 10, then ORs in a per-shard sequence modulo 1024. Two wins: no extra service to run, and the shard is inside the ID, so given any ID you know which shard holds the row without a lookup table.

Interviewers love this: "Embed the shard ID in the primary key so routing needs no directory lookup." It links ID design to sharding (see Choosing Storage and Data Modeling & Indexing).

5. Segment (range) allocation: the boring option that works

If you do not need time order across servers, hand out blocks. Meituan Leaf-segment keeps one row per business tag with max_id and step:

BEGIN;
UPDATE id_segment SET max_id = max_id + step WHERE biz_tag = 'order';
SELECT max_id, step FROM id_segment WHERE biz_tag = 'order';
COMMIT;
-- this server now owns (max_id - step, max_id] and serves it from memory

Leaf keeps a double buffer: when about 10% of the current block is used it fetches the next block in the background, so callers never wait on the database. Meituan sizes a block at about 600 x peak QPS (roughly 10 minutes of IDs), so the generator keeps working for 10 to 20 minutes if the database is down. The cost: IDs from different servers interleave (server A is handing out 1,000-1,999 while server B hands out 2,000-2,999), and a crash wastes the rest of a block. Gaps are fine; IDs are names, not counts.

From your world

Double-buffered segments are DMA ping-pong buffers: the device fills one while the CPU drains the other. Baidu's CachedUidGenerator goes further and pre-fills a power-of-two ring buffer of IDs with tail and cursor pointers, and pads slots to avoid false sharing on cache lines. Baidu claims over 6 million QPS per instance that way.

6. UUIDs: when they are the right answer

A UUIDv4 is 122 random bits: no coordination at all, but 128 bits (too big for our 64-bit requirement) and random, so new keys land all over a B-tree index. RFC 9562 (May 2024) added UUIDv7: a 48-bit Unix millisecond timestamp at the front, then random bits. It keeps the "no coordination" property of v4 and gets time order back, and the RFC notes that time-ordered keys give much better index locality. ULID is the same shape (48-bit time + 80 random bits) written as 26 Crockford base32 characters. If the interviewer drops the 64-bit requirement, UUIDv7 is often the best real-world answer.
