Back-of-envelope estimation

ID generators are small systems, so the estimation is mostly about bits, not servers. Work it in this order. (See Back-of-Envelope Estimation for the general method.)

  1. Peak rate. Assume 1,000,000 IDs/s at peak across all services. Average is lower, say 200,000/s, so 200,000 x 86,400 s = about 17 billion IDs per day.
  2. Sequence bits. How many IDs must one generator make in one millisecond? If each worker handles up to 4,000 IDs/ms (4 million/s), we need 12 bits, because 212 = 4,096. Snowflake picked exactly 12.
  3. Machine bits. How many generators may run at once? 10 bits gives 210 = 1,024 workers. Snowflake split those as 5 bits datacenter + 5 bits worker (32 x 32).
  4. Time bits. What is left: 64 - 1 sign bit - 10 - 12 = 41 bits of milliseconds. 241 ms = 2,199,023,255,552 ms = about 69.7 years. Twitter's epoch is 1288834974657 (4 Nov 2010), so its IDs last until about July 2080.
  5. Theoretical capacity. 1,024 workers x 4,096 IDs/ms = 4.19 million IDs per ms. We need 1,000 per ms. Bits are never the bottleneck; the network call is. Meituan measured its Leaf service at about 50,000 QPS per 4-core/8 GB VM over RPC, so 1M/s as a remote service needs about 20 such boxes (40 with headroom), but as an in-process library it needs zero extra boxes.
  6. Storage effect. Each ID is 8 bytes; a UUID is 16 bytes. At 17 billion new rows/day that is 136 GB/day vs 272 GB/day of primary-key bytes alone, before every secondary index that repeats the key. Smaller keys mean more of the index fits in RAM, the exact reason Flickr gave for avoiding GUIDs.
  7. Bandwidth. A request plus a 19-digit decimal reply is well under 200 bytes; 1M/s x 200 B = 200 MB/s if every ID is a network call. Batching 100 IDs per call cuts calls by 100x.
