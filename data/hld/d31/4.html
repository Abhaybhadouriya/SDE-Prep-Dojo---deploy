Data model: the bit layout is the schema

A Snowflake generator stores almost nothing. Its "data model" is the layout of the 64 bits, plus a tiny bit of state per worker: the last timestamp it used and the current sequence. The only shared data is who owns which worker ID.

Worked example with Twitter's epoch. Say at 2026-11-23 10:00:00 UTC, datacenter 3, worker 17 makes its 43rd ID in that millisecond (sequence 42):

EPOCH = 1288834974657                     # Twitter's custom epoch (ms)
ts    = 1795428000000 - EPOCH             # = 506593025343 ms since epoch
id    = (ts << 22) | (3 << 17) | (17 << 12) | 42
print(id)                                 # 2124805152568709162  (19 digits)

# decode
ts_back = (id >> 22) + EPOCH              # creation time
dc      = (id >> 17) & 0x1F               # 3
worker  = (id >> 12) & 0x1F               # 17
seq     =  id        & 0xFFF              # 42

The only table you might need

-- Worker-ID leases (if you do not use ZooKeeper/etcd)
CREATE TABLE worker_lease (
  worker_id     SMALLINT PRIMARY KEY,      -- 0..1023
  owner_host    VARCHAR(128) NOT NULL,
  last_ts_ms    BIGINT NOT NULL,           -- last timestamp this worker used (clock guard)
  lease_expires TIMESTAMP NOT NULL
);

SQL or NoSQL? Neither matters much: the state is tiny (1,024 rows at most). What matters is that the lease store is strongly consistent, so two machines can never hold the same worker ID. That is why real systems use ZooKeeper or etcd (consensus stores) or a single SQL row with a transaction, not an eventually consistent store. See Replication, Consensus & Coordination.

From your world

This is the same trick as a MAC address: the OUI prefix is handed out centrally once, then every vendor numbers its NICs locally with no coordination. Worker ID = OUI, sequence = the vendor's serial counter. And packing fields with shifts and masks is exactly how you build an IPv4 header word or a page-table entry in C.
