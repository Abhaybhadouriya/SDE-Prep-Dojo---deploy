Interview: driving 45 minutes

  1. 0-5 min: Clarify. Physical goods? Multiple sellers and warehouses? Which payment methods? Is the cart in scope? State the split: the cart is AP, the order is CP.
  2. 5-10: Estimate. Orders per second at peak (anchor: Flipkart's 2,000+/s), cart writes per second, storage per year. Conclude: shard orders by customer, put the cart in a KV store.
  3. 10-15: API. Cart APIs, the checkout session with a quote, and POST /orders with an idempotency key. Spell out the 201 / 202 / 409 responses.
  4. 15-25: Architecture. Walk the saga: claim the key, quote, reserve, authorise, confirm + outbox, fan out.
  5. 25-40: Deep dives. Idempotency mechanics, compensations and the pivot, oversell, the unknown payment state. Offer the hot SKU problem as a bridge to flash sales.
  6. 40-45: Wrap up. Failure per box, metrics (checkout conversion, Place Order p99, payment success rate, reservation expiry rate, outbox age), reconciliation.

SDE-1 vs SDE-2. SDE-1: cart in a KV store, an idempotent Place Order, an atomic stock update, a clear order state machine. SDE-2: explains why not 2PC, designs the saga with compensations and a pivot, handles the UNKNOWN payment, uses an outbox, and talks about reconciliation without being prompted.

Common mistakes: one giant transaction across services; "check stock then decrement" (a race); reserving at add-to-cart; the server generating the idempotency key; retrying a timed-out payment with a new key; publishing to Kafka outside the DB transaction; floats for money; forgetting that compensations can fail too.

How do you make sure a double click on "Place order" does not create two orders?

The client creates an idempotency key when the review page loads and sends it on every attempt. The orders table has UNIQUE (customer_id, idempotency_key). The first request's insert wins and runs the checkout. Any repeat hits the constraint, reads the existing row and returns its saved response (or "in progress"). I also store a hash of the request body and reject the same key with a different body. Downstream, the order id is the idempotency key for the payment provider, so even an internal retry cannot charge twice.

How to answer

Cover four things: who makes the key, how it is enforced (a constraint, not a read), what a repeat returns, and how the key is propagated downstream. Mention Amazon's client request token as prior art.

Likely follow-ups
  • How long do you keep keys? (At least as long as clients retry, for example 24 hours, then archive.)
  • Why must the idempotency read hit the primary?
Why not use a distributed transaction (2PC) for inventory + payment + order?

2PC holds locks in every participant until the coordinator decides. A slow or dead coordinator blocks all of them, and latency is set by the slowest participant. It couples the services' availability together. And the payment provider is an external HTTP API that will never take part in our 2PC. A saga keeps each step a short local transaction with a compensating action. The cost is that intermediate states are visible (stock looks reserved), so I make them explicit with a PENDING status and reservations with a TTL.

How to answer

Give the three costs of 2PC (blocking, coupling, external participants), then the saga's cost (no isolation) and how you handle it. That is a balanced trade-off answer.

Likely follow-ups
  • Orchestration or choreography here, and why?
  • What is a pivot transaction?
Walk me through a failure: inventory is reserved and then the payment is declined.

The orchestrator has saved "steps 1 and 2 done". The payment step returns DECLINED, so it runs compensations in reverse: release the reservation (an idempotent call keyed by orderId+sku that sets the reservation to RELEASED and decreases reserved), then mark the order PAYMENT_FAILED and save that response for the idempotency key. The customer sees "payment declined, try another method". If they try again, the client creates a new key, because this is a new attempt. If the release call fails, it is retried with backoff. The reservation TTL is the last safety net.

How to answer

Narrate the saga state at each moment. Show that compensations are idempotent, retried and backed by TTLs.

Likely follow-ups
  • What if the orchestrator crashes between the decline and the release?
  • Should a retry after a decline reuse the old key?
The payment call times out. What do you do?

Never assume. Store the payment as UNKNOWN and keep the reservation. Retry the authorisation with the same idempotency key (the provider will return the first result if it already processed it), query the provider's status API, and also accept the webhook. Show the customer "confirming your payment". If it is still unknown after a limit, a reconciliation job against the provider's report decides. Then confirm the order, or release the stock and void the authorisation.

How to answer

Name the two wrong answers (retry with a new key = double charge; assume success = free goods), then give the UNKNOWN state plus reconciliation.

Likely follow-ups
  • How do you dedupe webhooks?
  • How long should the reservation outlive an unknown payment?
How do you prevent overselling the last unit?

Make the check and the change one atomic statement: UPDATE inventory SET reserved = reserved + q WHERE sku = ? AND on_hand - reserved >= q, then look at rows affected. A CHECK constraint (reserved <= on_hand) protects against bugs. Reserve at checkout with a TTL, confirm on shipment, release on failure or expiry. The cached "only 3 left" is display-only. For extremely hot SKUs, move the counter to Redis behind a waiting room, as in the flash sale design.

How to answer

Show the race first (check-then-write), then the atomic fix. Mention the lock-contention limit and when you would switch to flash-sale techniques.

Likely follow-ups
  • Multiple warehouses: which one do you reserve in?
  • What if the physical count is wrong (damaged item)?
Why is the cart in a key-value store and the order in SQL?

The cart is a single-key document with a very high write rate, and the business wants it to accept writes even during failures, so an AP key-value store (DynamoDB-style) fits. A rare stale read or a merged conflict is cheap. Orders need multi-row transactions (order + lines + outbox), unique constraints for idempotency, and strong consistency for money. A relational database does that natively. Amazon's Dynamo paper uses the shopping cart as its motivating example of an always-writable service.

How to answer

One sentence each, tied to access patterns and the consistency each needs. That is the "SQL vs NoSQL" justification interviewers want.

Likely follow-ups
  • How do you merge two conflicting cart versions?
  • How do you shard orders?
How do downstream services learn about a confirmed order reliably?

With a transactional outbox: the CONFIRMED status and an outbox row commit in one transaction. A relay (Debezium CDC on the WAL, or a poller) publishes the row to the order-events topic, keyed by orderId. Delivery is at-least-once, so every consumer dedupes by event id or makes its effect idempotent (an upsert, a unique constraint, a state machine that ignores repeats). Kafka's exactly-once transactions only cover Kafka-to-Kafka processing. They do not make the email send or the warehouse API exactly-once.

How to answer

Name the dual-write problem, give the outbox, then pre-empt the "exactly-once" trap.

Likely follow-ups
  • Poller or CDC: which and why?
  • How do you keep the outbox table from growing forever?
A coupon can be used once per user and only 10,000 times in total. How do you enforce it at checkout?

Two checks inside the saga, both atomic. Per user: a coupon_redemptions table with UNIQUE (coupon_id, user_id), inserted as a saga step (its compensation deletes or voids the row if the order fails). Global cap: an atomic counter, either a conditional update ... SET used = used + 1 WHERE used < cap or a Redis DECR for very hot coupons. The quote shows the discount, but redemption happens at Place Order, so an abandoned checkout does not burn a use.

How to answer

Treat a coupon exactly like inventory: a reservation with a compensation.

Likely follow-ups
  • What if the order is refunded later: does the use come back?
How would you shard the orders table, and what queries get harder?

Shard by customer_id (hash), so "my orders" and the idempotency check stay on one shard. Embed the shard id in the order id (Snowflake-style bits), so a lookup by order id goes straight to the right shard. Queries across customers, such as "all orders for seller X" or "all orders in warehouse 7 today", become scatter-gather. Serve those from a different read model, built from order-events into a seller-sharded store or a search index.

How to answer

Choose the key from the most common query, name the query that suffers, and solve it with a second read model fed by events (CQRS).

Likely follow-ups
  • A huge business customer places millions of orders. Is that a hot shard?
Why authorise at order time but capture at shipment?

An authorisation holds funds without moving them. If the order is cancelled or cannot be fulfilled before shipping, you void the hold, and the customer is never charged. A capture followed by a refund takes days to show up and costs fees. Capturing at shipment also matches "charge when we deliver value". The cost: authorisations expire after a provider-defined window, so long-delayed shipments may need re-authorisation, and some methods (UPI, many wallets) do not support separate auth and capture, so they need a refund path instead.

How to answer

Explain the money difference in one sentence, then name the expiry and payment-method caveats. Those caveats are what separate a good answer from a memorised one.

Likely follow-ups
  • The order has items shipping from two warehouses on different days. How do you capture?

60-second answer (say it out loud)

"I split checkout into two worlds. The cart is an availability problem: a key-value store keyed by user, always writable, with conflicts merged as a union. Placing the order is a correctness problem: the client sends an idempotency key, the orders table has a unique constraint on it, and repeats get the saved response. The orchestrator then runs a saga: check the price quote, reserve stock with an atomic conditional update and a TTL, authorise the payment with the order id as the provider's key, and finally confirm the order and write an outbox row in the same transaction. If a step fails, compensations run in reverse: void, release, fail. A timeout means an UNKNOWN payment that I resolve by querying and reconciling, never by retrying with a new key. Events go from the outbox through CDC to Kafka, keyed by order id, to fulfilment, email and analytics, and every consumer is idempotent."

Scenario: customers report double charges after a deploy

Since this morning's release, about 0.1% of orders show two payment authorisations. There is only one order row per checkout.
Weak answer: "Add a check that looks for an existing payment before calling the provider."
Strong answer: "One order but two auths means the provider-side key changed. I would diff the release for how the payment idempotency key is built: did it switch from the order id to a fresh UUID per call, or add a timestamp? A retry inside the payment client with a new key would cause exactly this. Mitigation now: roll back, and void the duplicate auths found by joining our payments table with the provider report. Prevent it: a unique constraint on (order_id) in payments, a contract test that retries must reuse the key, and an alert on 'auths per order > 1'. A 'check then call' is racy and would not fix it."
Follow-ups: How do you find every affected customer? (Reconciliation report.) What do you tell them? (Proactive void plus an apology. Auths drop off without a refund.)
