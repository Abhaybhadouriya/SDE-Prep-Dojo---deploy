Deep dives

Stop here for SDE-1. The stepper with an idempotency key, a reservation and an outbox is a strong SDE-1 answer. SDE-2 rounds dig into the topics below: the exact idempotency mechanics, the saga and its failure cases, oversell, and unknown payment outcomes.

1. Making Place Order idempotent (for real)

"Use an idempotency key" is the slogan. The interviewer wants the mechanics. There are four rules:

  1. The client creates the key once per checkout attempt (when the review page loads) and resends the same key on every retry. A key created on the server after the request arrives is useless: the retry would get a new one.
  2. A UNIQUE constraint enforces it, not a "SELECT then INSERT". Two parallel requests can both pass a SELECT, but only one can win an INSERT.
  3. Store the request hash. The same key with a different body is a client bug. Return an error instead of guessing (Stripe documents this behaviour).
  4. Store the final response and replay it on a retry. If the first request is still running, return 202 "in progress" or make the retry wait briefly.
INSERT INTO orders (order_id, customer_id, idempotency_key, request_hash, status, total_minor, currency, quote_id)
VALUES (5001, 42, '0d5c3f0a-6b0e-4a39-9a51-2f1f8d0b6c11', 'sha256:ab12...', 'PENDING', 1899900, 'INR', 'q_9')
ON CONFLICT (customer_id, idempotency_key) DO NOTHING;
INSERT 0 1     -- first click: we own this checkout attempt, run the saga
INSERT 0 0     -- double click / retry: read the existing row and return its saved response

Amazon's Builders' Library describes the same idea for EC2: the caller passes a client request token, and the service returns the original result for repeats. Airbnb's payments team adds a lesson learned the hard way: read and write idempotency records on the primary, never on a lagging replica, or a retry may not "see" the first attempt.

2. The saga: orchestrated, with compensations

Inventory, payment and orders are different services with different databases. One ACID transaction across all of them would need two-phase commit (2PC): every participant locks its rows and waits for a coordinator. If the coordinator dies at the wrong moment, the locks stay held. Across microservices and an external payment provider (which will never join your 2PC), it is not workable.

A saga replaces one big transaction with a list of local ones, and each step has a compensating step that semantically undoes it:

#Step (local transaction)CompensationKind
1Create order PENDINGMark order PAYMENT_FAILEDcompensatable
2Reserve inventory (TTL)Release reservationcompensatable
3Authorise paymentVoid authorisationcompensatable
4Confirm order + outbox(none: this is the pivot)pivot
5Fulfil, capture at ship, emailRetried until done; cancel = a new refund flowretriable

Orchestration vs choreography. In choreography each service listens to events and reacts ("OrderCreated" -> inventory reserves -> "StockReserved" -> payment authorises ...). Nobody owns the whole flow, and with five or more steps it becomes hard to see where an order is stuck. In orchestration one component (the checkout orchestrator, or a workflow engine like Temporal or AWS Step Functions) stores the saga state and calls each step. For checkout, pick orchestration: the flow is business-critical and you want one place that answers "where is order o_5001 right now?".

Saga rules that interviewers check:

  • Persist saga state after every step so a crashed orchestrator resumes instead of starting again.
  • Every step and every compensation is idempotent, keyed by (orderId, step), because resuming means re-sending.
  • Compensations must eventually succeed. Retry them with backoff and alert a human if they keep failing. "Void failed" can never be silently dropped.
  • Sagas are not isolated. Between steps other users can see the intermediate state (stock looks lower because it is reserved). Design for it with "semantic locks" such as the PENDING status and the reservation itself.

From your world

A saga is like a network-wide config push with commit confirmed (Junos or IOS-XR style): apply on each box locally, and if a later box fails, roll back the earlier boxes, instead of holding a lock across the whole network while you wait. The pivot step is the moment you "confirm" the commit. Where it breaks: a router rollback restores the exact old state, but a saga compensation is a new business action (a void, a refund), and others may have seen the intermediate state.

3. Inventory: never oversell, and do not lock the world

Three approaches, from weakest to strongest:

  • Check, then write ("SELECT stock; if > 0 then UPDATE"): two buyers both see 1 and both buy. This is a classic race. Never do it.
  • Pessimistic lock (SELECT ... FOR UPDATE, then update): correct, but every buyer of that SKU waits in line on one row lock. That is fine for normal items and terrible for a hot one.
  • Atomic conditional update: one statement that checks and changes together. Correct, short, and the database does the locking for microseconds only.
UPDATE inventory
   SET reserved = reserved + 1
 WHERE sku = 'B0-PHONE-128' AND warehouse_id = 7
   AND on_hand - reserved >= 1;
UPDATE 1     -- reserved: insert the reservation row with expires_at = now() + interval '15 minutes'
UPDATE 0     -- not enough stock in warehouse 7: try the next warehouse, or tell the customer

Reservations expire. A sweeper job finds expired HELD rows and releases them (each release is the same idempotent compensation the saga uses). It must skip any reservation whose payment is still in flight, or a slow payment that later succeeds will find its stock sold to someone else:

SELECT r.reservation_id
  FROM reservations r
 WHERE r.status = 'HELD' AND r.expires_at < now()
   AND NOT EXISTS (SELECT 1 FROM payments p
                    WHERE p.order_id = r.order_id
                      AND p.status IN ('UNKNOWN', 'AUTH_PENDING'));   -- payment still being decided

Choose the TTL with the payment flow in mind: long enough for a UPI app switch or a 3-D Secure page, short enough that abandoned checkouts do not hide stock for long.

Where to reserve: add-to-cart or checkout? Amazon-style shops reserve at checkout, not at add-to-cart. Carts are wish lists and most are abandoned, so reserving at add-to-cart would hide stock from real buyers. The product page's "only 3 left" comes from a cache and is advisory. The decision is made by the conditional update.

Hot SKUs. When one SKU gets thousands of buyers per second (a lightning deal), one row is the bottleneck. That is the flash sale problem: gate the traffic, split stock into sub-counters, and move the counter into Redis. Normal checkout does not need those tricks, and adding them everywhere is over-engineering.

4. Payment timeouts: the "unknown" state

The payment provider call times out. Did the bank hold the money or not? You do not know, and guessing either way is a bug:

  • Assume failure and let the user retry with a new key: you may charge twice.
  • Assume success and ship: you may ship for free.

The correct answer is to store the payment as UNKNOWN, keep the reservation, and ask: query the provider's status API with the same reference, retry the authorisation with the same idempotency key (the provider dedupes it), and wait for the provider's webhook. A reconciliation job compares your payments table with the provider's settlement report daily, and fixes any mismatch with explicit, audited actions. The customer sees "We are confirming your payment" rather than an error.

Tie this to the reservation sweeper (deep dive 3). "Keep the reservation" only works if the sweeper agrees: it skips reservations whose payment is UNKNOWN or AUTH_PENDING, and when reconciliation finally decides, the saga either confirms the reservation or releases it. (An equivalent design extends expires_at whenever a payment enters UNKNOWN.) Without this link, a 15-minute TTL plus a 20-minute UPI delay is an oversell or a forced refund.

Webhooks arrive more than once and out of order. Verify the signature, dedupe by the provider's eventId, and apply state changes only forward (AUTHORIZED cannot go back to AUTH_PENDING). Shopify's "Building resilient payment systems" post covers timeouts, circuit breakers, idempotency keys and reconciliation together.

5. The outbox: reliable events without dual writes

After the order is CONFIRMED, fulfilment must hear about it. The tempting code is "commit, then kafka.send()". If the process dies between the two lines, the order exists but no warehouse ever ships it. Reversing the order (send, then commit) is worse: the warehouse may ship an order that rolled back.

The transactional outbox writes the event into an outbox table in the same transaction as the order change. A relay then publishes outbox rows to Kafka: either a poller, or Debezium reading the database's write-ahead log with its Outbox Event Router. The relay is at-least-once, so consumers dedupe by event id. Full walk-through: distributed transactions and events and the ShopStream pipeline, which builds exactly this.

From your world

The outbox is a write-ahead log idea: record the intent durably in the same atomic write as the state change, and let a separate process replay it to the outside world, like a journaling file system replays its journal after a crash. Debezium literally reads the database's own WAL (Postgres) or binlog (MySQL). Where it breaks: a journal is replayed once, by one owner, onto the same disk; outbox rows are delivered at-least-once to many independent consumers over a network, so each consumer must dedupe by event id, and nothing rolls them back if a consumer misbehaves.
