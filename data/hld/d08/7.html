Where Kafka, Kubernetes and Docker fit

ToolWhereDetail
Kafkaorder-eventsKeyed by orderId, so placed -> confirmed -> shipped stay in order per order. Producers use acks=all and the idempotent producer (the default since Kafka 3.0). Consumer groups: fulfilment, notifications, analytics, recommendations, fraud.
Kafkainventory-eventsKeyed by sku. Feeds the "only 3 left" cache and the search index, and the catalogue search availability filter.
KafkaRetry and DLQ topicsA consumer that fails (for example the email provider is down) moves the message to order-events.retry-1m, then a DLQ, without blocking the partition. See consumers and groups.
KubernetesCheckout tierDeployments with readiness probes and maxUnavailable: 0 rolling updates, so a deploy never drops capacity during checkout. HPA on CPU and request rate. Pre-scale before sale events.
KubernetesSaga workersTemporal (or similar) workers run as a Deployment. Saga state lives in the workflow engine's database, so pods are disposable.
KubernetesSweeper and reconciliationA CronJob for expired reservations and the daily payment reconciliation. Make each run idempotent, and set concurrencyPolicy: Forbid.
DockerTestsTestcontainers (Postgres, Kafka) in CI: fire 100 parallel Place Order calls with the same key and assert exactly one order; kill the orchestrator mid-saga and assert it resumes.
 
# Reservation sweeper: release holds whose TTL passed
apiVersion: batch/v1
kind: CronJob
metadata:
  name: reservation-sweeper
spec:
  schedule: "*/1 * * * *"          # every minute
  concurrencyPolicy: Forbid         # never two sweepers at once
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: sweeper
              image: shop/inventory-tools:1.8.2
              args: ["release-expired", "--batch=500"]
$ kubectl apply -f sweeper.yaml
cronjob.batch/reservation-sweeper created
