Remember this

You might confuse this with:

  • Reservation vs order: a reservation is a temporary hold on stock with an expiry; the order is the customer's purchase record. One order can hold several reservations (one per SKU and warehouse).
  • Authorise vs capture: authorise = the bank holds the money; capture = the money actually moves, here at shipment. A void cancels an authorisation; a refund reverses a capture.
  • Idempotency key vs order id: the client makes the key so retries can be recognised; the server makes the order id once the key is claimed.

Remember this

  • The cart is AP (KV store, always writable, merge as a union). The order is CP (SQL, transactions, constraints).
  • Place Order: a client-generated idempotency key + a UNIQUE constraint + a request hash + a saved response.
  • Saga steps: claim key -> quote -> reserve (TTL) -> authorise -> confirm + outbox (pivot) -> fulfil and capture.
  • Compensations run in reverse, are idempotent, are retried, and are backed by TTLs.
  • No oversell: one atomic conditional UPDATE, never check-then-write. Reserve at checkout, not at add-to-cart.
  • A payment timeout means UNKNOWN: same key, query, reconcile. Never a new key.
  • Events through the outbox to Kafka (keyed by orderId). Consumers dedupe. Kafka EOS does not cover emails or bank calls.
