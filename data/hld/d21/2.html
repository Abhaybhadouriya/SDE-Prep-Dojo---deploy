Back-of-envelope estimation

Interview assumptions, worked step by step. (Method: Back-of-Envelope Estimation.)

  1. Average click rate. 1B clicks / 86,400 s ≈ 1B / 100k = ~12k clicks/s (rounded down from 11.6k).
  2. Peak. 5x average ≈ 60k clicks/s. Design every component for this, not the average.
  3. Event size. click_id, impression_id, ad_id, campaign_id, advertiser_id, hashed user ID, timestamp, country, device, IP hash, user agent ≈ 500 bytes.
  4. Ingest bandwidth. 60k x 500 B = 30 MB/s at peak (6 MB/s average). Modest for Kafka.
  5. Raw storage. 1B x 500 B = 500 GB/day; x 365 ≈ ~180 TB/year before compression - goes to object storage (columnar files compress well).
  6. Kafka. Keep 7 days for replay: 500 GB x 7 x RF 3 ≈ ~10 TB of broker disk. Partitions: peak 30 MB/s is small, but we want parallelism for Flink and room for hot ads: 64 partitions. (Apache Flink = a separate cluster of stream-processing workers that read Kafka, keep per-key state in memory/RocksDB, and checkpoint it - it is not part of Kafka itself; see Stream processing. One Flink worker task can read one or more partitions, so the partition count caps useful parallelism.)
  7. Aggregated rows. Suppose 2M distinct ads get clicks each day and ~200k are clicked in any given minute. Minute rows/day ≈ 200k x 1,440 ≈ 288M rows/day; at ~50 B per row ≈ ~15 GB/day. Hourly and daily rollups are much smaller. Aggregation shrinks data ~30x and query cost far more.
  8. Dedup state. Remember click IDs for 1 hour to catch duplicates. Size it for the peak, like everything else: 60k/s x 3,600 ≈ 216M IDs x ~40 B ≈ ~8.6 GB of keyed state (about 1.7 GB at the 12k/s average). Spread over 32 task slots that is ≈ 270 MB each in RocksDB - still easy. This 1-hour state lives in a separate DataStream dedup operator in front of the window; the Flink SQL version shown later only dedups within one window.
  9. Query load. 100k advertisers, a few thousand online at once, each dashboard refreshing every minute: hundreds to low thousands of queries/s - read from pre-aggregated tables plus a cache.
