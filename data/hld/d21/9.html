60-second answer: "The click link hits a stateless click service that checks a signed token, sends an event to Kafka asynchronously and returns a 302 - counting never slows the redirect. Events go to a Kafka topic keyed by ad ID with acks=all and idempotence, 7 days of retention. A Flink job dedups by click ID - the impression ID - with keyed state and a TTL, filters obvious fraud, and counts clicks in 1-minute tumbling windows on event time, with a watermark about 30 seconds behind so late clicks still land in the right minute. Checkpoints save state and offsets together, and the sink upserts the full window value by ad and minute, so a replay after a crash rewrites the same number instead of adding to it. Results land in an OLAP store like Pinot or ClickHouse with hour and day rollups, behind a cached query service. Raw events also go to object storage, and a nightly batch recount reconciles and finalizes billing numbers. Hot ads get salted keys and two-stage aggregation."

Why not just insert each click into a SQL table and run COUNT(*)?

At 60k inserts per second the database becomes the bottleneck, and every dashboard query scans millions of rows - so both writes and reads get slower as data grows. The click redirect would also depend on the database. Pre-aggregating in a stream processor turns a billion rows a day into a few hundred million small window rows, and queries read those. The raw clicks still exist in Kafka and object storage for audits.

How to answer

Show the numbers, name both bottlenecks (write rate, scan cost), then propose pre-aggregation - and keep raw data for truth.

Likely follow-ups
  • What about Redis INCR per ad-minute? (fast, but not idempotent and loses data on failover)
How do you make sure a click is counted exactly once?

Handle each duplicate source separately. User double-clicks and reloads: dedup on click_id (the signed impression ID), kept in Flink keyed state with a TTL. Producer retries: Kafka's idempotent producer drops repeated sequence numbers. Processor crashes: Flink checkpoints save state and Kafka offsets together, so after a restart it replays from a consistent point; the sink either upserts the whole window value by key (idempotent) or uses a transactional 2-phase-commit Kafka sink with read_committed downstream. Finally, a nightly batch recount verifies it - because "exactly-once" claims should be checked, not trusted.

How to answer

Three duplicate sources, three fixes, plus verification. Avoid saying "Kafka exactly-once" as the whole answer.

Likely follow-ups
  • What if the same click arrives 2 hours later, after the TTL? (batch reconciliation catches it; or a longer-lived dedup store keyed by impression)
  • What does read_committed do? (The consumer skips messages from aborted transactions and waits for commit markers, so it only sees exactly-once output.)
Event time vs processing time - which do you use and how do you handle late clicks?

Event time, because billing must attribute a click to the minute it happened, and because replays must produce the same answer as live processing. A watermark set to "newest event time minus 30 seconds" decides when a window is complete. Clicks that arrive within an allowed-lateness period update the window (the upsert handles the update). Later clicks go to a side output and are included by the nightly batch. I would pick the watermark delay from the measured lateness distribution.

How to answer

Define both in one line each, choose event time with two reasons, then explain watermark + allowed lateness + side output as three tiers.

Likely follow-ups
  • What happens if one partition has no traffic? (watermark stalls; configure idleness)
  • Tumbling vs sliding vs session windows? (Tumbling = fixed, non-overlapping minutes; sliding = overlapping, e.g. last 5 min every 1 min; session = closes after a gap of inactivity per key.)
One ad gets 30% of all clicks during a big cricket match. What breaks and how do you fix it?

With key = ad_id, that ad's clicks all go to one Kafka partition and one Flink task, which saturates while the rest idle; its lag and the freshness of that ad's numbers suffer. Fix: salt hot keys (ad_id#(hash(click_id) mod N)) so they spread over N partitions/tasks, count partially per salt and window, then sum the N partial counts per ad in a second, cheap stage. Using click_id for the salt keeps duplicates together, so dedup still works. Also enable local pre-aggregation in the job.

How to answer

Name the symptom (one partition's lag), explain the cause (key skew), then the two-stage fix and why dedup still holds.

Likely follow-ups
  • How do you know which ads are hot in advance? (top-K from the last minute, or campaign metadata)
How do you keep the redirect fast even if Kafka is slow?

The click service never waits for Kafka. It hands the event to the producer's in-memory buffer (asynchronous send with a callback) and returns the 302 immediately. If the buffer fills because Kafka is unreachable, events spill to local disk and a background sender retries. The service exposes metrics for buffer and spill size, and readiness fails only if the spill is nearly full. The redirect target comes from the signed token itself, so no database lookup is needed either.

How to answer

"Decouple the user path from the counting path" - then the buffering layers, then how you would notice trouble.

Likely follow-ups
  • What if the click service pod dies with events in memory? (small window of loss; reconcile with impression logs, or a synchronous write for very high value clicks)
Lambda vs Kappa - which would you choose here?

For billing data, I keep a Lambda-style batch check: the nightly job recounts from raw files and finalizes numbers, which protects against subtle streaming bugs and very late events. For reprocessing after a code bug, I use the Kappa approach: deploy the fixed streaming job, replay from Kafka (or tiered storage/object storage) into a new table, and switch reads. So: one processing codebase (stream), plus an independent verification (batch).

How to answer

Define both briefly, then give a mixed, reasoned answer tied to "this is money".

Likely follow-ups
  • How long must Kafka retain data for Kappa replays? (as long as your replay window; tiered storage makes it cheap)
Which database stores the aggregates, and what is the primary key?

A columnar OLAP store - Pinot, Druid or ClickHouse - because queries are time-range scans with sums and group-bys, and these stores ingest from Kafka and serve sub-second aggregations. The minute table's key is (ad_id, window_start, country, device); the job upserts the full count for that key, so retries are harmless. Hour and day rollup tables serve long ranges, and the query service picks the coarsest table that answers the question.

How to answer

Query shape → store type → key design → rollups.

Likely follow-ups
  • How would you support "unique users per ad"? (HyperLogLog sketches per window, mergeable across windows)
How do you detect and handle click fraud without hurting latency?

Two speeds. Inline in the stream job, apply cheap deterministic rules: bad signature, click without a matching impression, known bot user agents and data-centre IP ranges, and rate limits per user/IP per second. These mark clicks invalid before counting. Asynchronously, an ML model scores clicks over minutes to hours using richer features; invalid clicks are subtracted through corrections, and the nightly batch finalizes. The redirect itself never waits for fraud scoring - the user still goes to the site; we just do not bill the click.

How to answer

Separate "do not redirect" (almost never) from "do not bill" (fraud), then fast rules vs slow ML.

Likely follow-ups
  • How do advertisers see corrected numbers? (final flag, adjustments table)
A Flink TaskManager crashes in the middle of a window. Walk me through recovery.

The JobManager notices the lost TaskManager (heartbeat timeout), cancels the running tasks and restarts the job from the latest completed checkpoint, using a replacement pod. Each operator restores its state - dedup sets, partial window counts - from the checkpoint in object storage, and the Kafka sources rewind to the offsets stored in the same checkpoint. The job re-reads the events after that point, rebuilds identical partial counts, and when the window closes it upserts the same value as before (or, with a transactional sink, the uncommitted transaction is aborted and redone). The only visible effect is a short delay.

How to answer

Detection → restore state + offsets together → replay → idempotent/transactional output. The word "together" is the key.

Likely follow-ups
  • Why are offsets stored in the checkpoint and not committed to Kafka first? (So offsets and state describe the same instant; committing offsets first would skip events whose state was never saved.)
  • What is a savepoint? (a manual checkpoint used for upgrades)
How would you run this across regions?

Put click services and a Kafka cluster in every region so clicks are captured locally with low latency and survive a region failure of the aggregation site. Either aggregate per region and merge the small aggregate streams centrally, or mirror raw clicks to one or two aggregation regions with MirrorMaker 2. Uber's ad pipeline is described as running its Flink jobs in two regions. Deduplication must use the global click ID so a click replicated to two regions is still counted once, and the merged per-ad totals are upserted by key.

How to answer

Capture locally, aggregate where convenient, dedup globally, merge idempotently.

Likely follow-ups
  • Active-active aggregation in two regions - how do you avoid double counting? (one region is the writer for billing; or dedup on merge)

Common mistakes

  • Writing every click to SQL and running COUNT(*) for dashboards.
  • Counting with processing-time windows (wrong minute, non-repeatable replays).
  • Incrementing counters in the sink (retries double count).
  • Saying "Kafka exactly-once" and stopping there.
  • Making the redirect wait for Kafka, the database or fraud checks.
  • Ignoring hot ads and late events.
  • No reconciliation for billing data.

Scenario: an advertiser says you over-billed them by 4%

An advertiser compares your dashboard with their own site analytics for last Tuesday and claims you counted 4% more clicks than they received. Your streaming numbers and nightly batch numbers agree.

Weak answer: "Our system is exactly-once, so they are wrong."

Strong answer: "First I reproduce from raw data: pull that advertiser's raw clicks for Tuesday from object storage and check duplicates by impression ID, clicks without impressions, and the distribution of IP hashes and user agents. If batch and stream agree, the counting is consistent, so the question is definitions: their analytics counts page loads, and users who bounce before the page loads are clicks for us but not visits for them - some gap is normal and is in the contract. If I find duplicates with different impression IDs from the same user within seconds, that is a dedup rule gap, and I would add a per-user/ad time-window rule, recompute, issue a credit, and add a monitor on duplicate patterns."

Likely follow-ups
  • How do you issue corrections without rewriting history? (adjustment records, versioned final tables)

Scenario: the dashboard shows zero for the last 10 minutes

At 8:10 PM the advertiser dashboard shows no clicks after 8:00, but the click service is serving redirects normally.

Weak answer: "Restart Flink."

Strong answer: "Clicks are reaching Kafka (I check bytes-in on ad-clicks), so data is safe. Next: is Flink consuming? If consumer lag is growing, the job is stuck or slow - check for a failing checkpoint, backpressure from the sink, or a restart loop. If lag is near zero but no windows close, the watermark is stuck: one idle partition or one producer with a wrong clock holds it back. Fix with source idleness configuration and by clamping absurd future timestamps. After recovery the windows emit, and the upsert sink fills in the missing 10 minutes without duplicates."

Likely follow-ups
  • What would you alert on to catch this in 2 minutes? (watermark lag vs wall clock, last window emitted time)
