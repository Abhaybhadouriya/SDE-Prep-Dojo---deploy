Why an OLAP store (Apache Pinot, Apache Druid, or ClickHouse) and not Postgres or Cassandra? Queries are "sum clicks for these ads over this time range, grouped by country" - scans and aggregations over many rows, with time filters. Columnar OLAP stores are built exactly for that and ingest from Kafka directly. Postgres would struggle with the write rate and the scan sizes; Cassandra is great for key lookups but weak at ad-hoc group-bys. The raw events go to object storage as Parquet/Iceberg for audit and the nightly batch job.

Jargon check. OLAP (online analytical processing) = a database built for big sums and group-bys over many rows, not for single-row updates. Columnar = it stores each column together on disk, so "sum clicks" reads only the clicks column and skips the rest. Parquet = a columnar file format (a file you can drop in S3). Iceberg = a table layer over many Parquet files in S3 that adds upserts, snapshots and schema changes, so the files behave like one table. unique_users_sketch = a HyperLogLog: a ~12 KB structure that estimates "how many distinct users" within about 1%, and two sketches can be merged (minute sketches add up to an hour sketch) - exact distinct counts would need to store every user ID.

More words you will meet below. HMAC = a keyed hash: only someone holding our secret key can produce a valid signature, so only we can mint click tokens. 302 = the HTTP "Found" redirect status; the browser follows the Location header to the advertiser. TTL (time to live) = how long a stored item is kept before it is deleted automatically. Keyed state = memory a Flink operator keeps per key (per ad, per click ID), saved in checkpoints. RocksDB = an embedded on-disk key-value store that Flink uses to hold large state on local SSD instead of the JVM heap. Task slot = one unit of parallel work inside a Flink worker (like one core's worth of a pipeline). Savepoint = a checkpoint you trigger by hand before an upgrade, so the new version resumes from it. Spark = a batch engine that crunches big files in parallel. MirrorMaker 2 = a tool that copies topics from one Kafka cluster to another (cross-region). Chandy-Lamport = the classic algorithm for taking a consistent snapshot of a distributed system by sending marker messages along every channel.

The aggregate row's primary key matters: if the stream job writes (ad-42, 10:02, IN, android) = 1251 twice, an upsert (overwrite by key) leaves 1251, while an increment would give 2502. Choosing "write the full value by key" instead of "add to a counter" is one of the most important decisions on this page.

You might confuse this with...

  • Upsert vs increment: upsert = "set row K to 1251" (repeat it and nothing changes); increment = "add 1251 to row K" (repeat it and you double). Same SQL keyword family, opposite behaviour on retry.
  • Event time vs processing time: event time = when the user tapped (stamped on the phone); processing time = when Flink saw it. Billing and replays need event time.
  • Dedup vs idempotent sink: dedup removes duplicate input clicks; an idempotent sink makes duplicate output writes harmless. You need both.
