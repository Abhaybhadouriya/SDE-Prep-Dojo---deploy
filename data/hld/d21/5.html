Architecture: follow one click

Click Next or Play. We follow one click on ad-42 at 10:02:13 from the user's tap to the advertiser's chart and the nightly check.

  1. Redirect first. Click service checks the signed token, hands the event to the Kafka producer, returns 302 at once.
  2. Durable log. Event goes to topic ad-clicks, key = ad_id, so all ad-42 clicks land on p17 in order.
  3. Filter and dedup. The Flink job (a separate stream-processing cluster) drops fraud and any click_id already seen.
  4. Window by event time. Clicks fill 1-minute windows by tap time; the watermark closes the 10:02 window.
  5. Idempotent sink. The window value is upserted into OLAP by key, so writing it twice changes nothing.
  6. Serve. Query service picks the right rollup table, caches ~30 s, returns buckets to the dashboard.
  7. Reconcile. Raw clicks also go to object storage; a nightly batch recounts and marks the day final.
  8. Failure. A Flink worker dies; it restores state + offsets from the checkpoint, replays and upserts the same values.

The same 8 steps, in detail

  1. Redirect first. The click service checks the token's HMAC signature, builds the click event, hands it to the Kafka producer (which batches in memory and sends asynchronously), and immediately returns a 302. The user lands on the advertiser site in milliseconds. If Kafka is briefly slow, the producer buffers; it has a local disk spill as a last resort so the redirect never waits.
  2. Durable log. The event is produced to topic ad-clicks with acks=all, idempotence on, key = ad_id. All clicks for ad-42 land on one partition (here p17), in order. RF 3 with min.insync.replicas=2: a broker loss loses nothing. 7 days of retention lets us replay.
  3. Filter and dedup. A Flink job (Apache Flink: a separate cluster of stream-processing workers, not part of Kafka - see Stream processing) reads all partitions in parallel (one task slot per partition group). It drops invalid or obviously fraudulent clicks (bad signature, bot user agent, too many clicks from one IP hash in a second) and drops any click_id it has already seen, using keyed state with a 1-hour TTL.
  4. Window by event time. Clicks are grouped into 1-minute tumbling windows (fixed, non-overlapping: 10:02:00-10:03:00) using the click's event_time, not the time Flink sees it. A watermark - "I believe I have now seen everything up to time T" - trails the newest event by 30 s. When the watermark passes 10:03:00, the 10:02 window closes and emits (ad-42, 10:02) = 1251.
  5. Idempotent sink. The result is written to the OLAP store as an upsert keyed by (ad_id, window_start, country, device). Writing it twice leaves the same value. (Alternative: a transactional Kafka sink that the OLAP store ingests with read_committed.)
  6. Serve. The query service reads the right rollup table (minute for the last day, hour for weeks, day for months), caches hot answers for ~30 s, and returns buckets to the dashboard. Hourly and daily rollups are produced by the stream job or by the OLAP store itself.
  7. Reconcile. In parallel, a Kafka Connect sink (or a Flink job) writes all raw clicks to object storage. Each night a batch job (Spark) recounts yesterday from raw data with the same dedup and fraud rules, compares with the streaming numbers, corrects any differences, and marks the day as final for billing.
  8. Failure. A Flink worker dies mid-window. Flink restores operator state and the matching Kafka offsets from the last checkpoint, re-reads the clicks after that point, rebuilds the same window counts, and upserts the same values. No double count, no gap.

Whiteboard version: Click service → Kafka (key ad_id) → Flink (dedup → 1-min event-time windows) → OLAP (upsert) → Query service → Dashboard, and underneath Kafka → S3 → nightly batch → reconcile.

From your world

A Flink checkpoint is a consistent snapshot taken by injecting barrier markers into every input stream (Chandy-Lamport style). Each operator saves its state when the barrier passes. It is like freezing a forwarding pipeline by sending a marker packet through every stage so you can capture counters that all describe the same instant. Restoring = loading those counters and replaying input from the matching sequence numbers. Where it breaks: unlike a pipeline freeze, processing does not stop - barriers flow along with the data, and with aligned barriers an operator with two inputs must hold back the fast input while it waits for the slow one's barrier, which can stall throughput (unaligned checkpoints trade that stall for bigger snapshots).
