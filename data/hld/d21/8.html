Trade-offs, bottlenecks and failure modes

Failure / bottleneckWhat happensMitigation
Kafka slow or unreachableClick events pile up in the click serviceAsync send + bounded memory buffer + local disk spill; redirect never waits. Alert on spill size.
Flink task crashReplays from the last checkpointState + offsets restored together; idempotent sink.
Hot adOne task lags; that ad's numbers are lateKey salting + two-stage aggregation; local pre-aggregation.
Late eventsCounted in the wrong minute or droppedEvent-time windows, watermark delay, allowed lateness, side output, nightly batch.
Dedup state too bigMemory pressure, slow checkpointsRocksDB state backend, TTL of 1 h, incremental checkpoints.
Bug in aggregation logicWrong numbers for daysReconciliation alert; replay from Kafka/object storage into a new table.
OLAP store downDashboards stale; stream backs upKafka buffers; Flink backpressure; serve cached results with a "data delayed" banner.
Region outageClicks in that region not countedClick service in every region writing to a local Kafka; cross-region replication (MirrorMaker 2) for the aggregation region, or aggregate per region and merge.
DecisionOption AOption BPick when
Stream engineFlink (separate cluster)Kafka Streams (a Java library inside your own app, no separate cluster)Flink for large shared stateful jobs with event-time windows; Kafka Streams for a service-embedded processor. (A common rule of thumb; both are covered in the Kafka section of this site.)
Sink semanticsIdempotent upsertTransactional 2PC sinkUpsert for low latency when the store supports it; 2PC when the next hop is Kafka.
Window size1 minute10 secondsProduct need. Smaller windows = more rows and more state for little user value.
ArchitectureLambda (stream + batch check)Kappa (stream + replay)Billing data: keep a batch check. Non-billing analytics: Kappa is simpler.
StorePinot / DruidClickHouseAll fit; Pinot/Druid ingest from Kafka with low-latency upserts; ClickHouse is simpler to run for batchy inserts.
