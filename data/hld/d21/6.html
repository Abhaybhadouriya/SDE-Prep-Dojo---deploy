1. The solution ladder: from naive to real (must know)

2. Exactly-once: what it really means here (SDE-2)

"Exactly-once" in streaming means the final state looks as if each event was processed once, even though events may be read more than once after a crash. There are three places duplicates come from, and each needs its own fix:

Where duplicates come fromExampleFix
The user / browserDouble tap, page reload, prefetchDedup by click_id (= impression ID) in keyed state with TTL.
Producer retries into KafkaNetwork blip after the broker wrote the batchIdempotent producer (on by default since Kafka 3.0): broker drops repeated sequence numbers.
Processor crash + replayFlink restarts from checkpoint and re-reads 2 minutes of inputState and offsets restored together from the checkpoint; sink is idempotent (upsert) or transactional (2-phase commit).

Two sink strategies, both valid - say which you choose and why:

  • Idempotent upsert (my default): write the complete window value keyed by (ad_id, window, dims). Retries overwrite. Simple, low latency, needs a store that supports upsert (Pinot upsert tables, Cassandra/DynamoDB or any key-value store by key, which truly overwrite). Careful with ClickHouse ReplacingMergeTree: it removes duplicate keys only during background merges, so until a merge runs a plain SUM(clicks) counts both copies of a retried row. Query it with FINAL, or with argMax(clicks, version) ... GROUP BY key, to get exact results.
  • Transactional sink: Flink's Kafka sink uses Kafka transactions with two-phase commit tied to checkpoints; downstream readers use isolation.level=read_committed and only see committed results. Cost: results appear only after each checkpoint completes, so latency is at least the checkpoint interval. Uber's ad pipeline used this with a 2-minute checkpoint interval.

Never say "Kafka gives exactly-once, so we are done." Kafka transactions cover Kafka-to-Kafka processing. The moment you write to an external database, you need an idempotent or transactional sink - and a reconciliation job to prove it. (More: Distributed transactions & events.)

3. Event time, watermarks and late clicks (SDE-2)

Processing time = when our server sees the click. Event time = when the user actually clicked. A phone in a tunnel may send a 10:02 click at 10:05. If we count by processing time, that click lands in the wrong minute, and a replay of yesterday would count everything into "now". So we count by event time.

  • Watermark delay is a dial: 30 s waits for most stragglers but delays results by 30 s. Measure the real lateness distribution (event_time vs received_time) and pick a delay that covers ~99.9% of clicks.
  • Allowed lateness: Flink can keep a closed window's state a bit longer and re-emit an updated value if a late click arrives (the upsert sink handles the update naturally).
  • Very late clicks (hours) go to a side output topic; the nightly batch job includes them, so final billing numbers are complete anyway.
  • Idle partitions can stall the watermark (no events, so time does not advance). Flink's idleness setting tells it to ignore idle sources.
-- Flink SQL: 1-minute tumbling windows on event time, with dedup INSIDE each window
CREATE TABLE clicks (
  click_id   STRING,
  ad_id      STRING,
  country    STRING,
  device     STRING,
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '30' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'ad-clicks',
  'properties.bootstrap.servers' = 'kafka:9092',
  'properties.group.id' = 'click-agg',
  'properties.isolation.level' = 'read_committed',
  'scan.startup.mode' = 'group-offsets',
  'properties.auto.offset.reset' = 'earliest',  -- used only when the group has no committed offset yet
  'format' = 'json'
);

-- COUNT(DISTINCT click_id) inside the window TVF keeps the input append-only,
-- so the planner accepts it and the event_time attribute stays intact.
SELECT ad_id, country, device, window_start, window_end,
       COUNT(DISTINCT click_id) AS clicks
FROM TABLE(TUMBLE(TABLE clicks, DESCRIPTOR(event_time), INTERVAL '1' MINUTE))
GROUP BY ad_id, country, device, window_start, window_end;

-- Alternative: Flink "window deduplication", then aggregate
-- SELECT ... FROM (
--   SELECT *, ROW_NUMBER() OVER (PARTITION BY window_start, window_end, click_id
--                                ORDER BY event_time ASC) AS rn
--   FROM TABLE(TUMBLE(TABLE clicks, DESCRIPTOR(event_time), INTERVAL '1' MINUTE))
-- ) WHERE rn = 1;

Why not a plain ROW_NUMBER() OVER (PARTITION BY click_id ...) dedup first? A regular (non-windowed) dedup can emit updates - an earlier duplicate arriving late retracts the first row - and window aggregation expects append-only input, so the planner rejects it or the time attribute is lost. Both forms above dedup within one window. A duplicate that straddles two windows (first tap 10:02:59.9, second 10:03:00.1) is caught by a DataStream job with keyed state + 1-hour TTL in front of the windows, or by the nightly batch. In production also enable checkpointing (for example every 60 s) in exactly-once mode.

4. Hot ads (hot keys) (SDE-2)

A Super Bowl or IPL ad can get a big share of all clicks. With key = ad_id, all of them hit one partition and one Flink task: that task's CPU saturates and its lag grows while others idle.

  • Salting: key = ad_id + "#" + (hash(click_id) mod N) for ads on a hot list (or for all ads with a small N). Note dedup still works because the salt comes from click_id, so duplicates land in the same sub-key.
  • Local pre-aggregation: Flink (and Flink SQL's mini-batch / two-phase aggregation option) can combine counts inside each task before shuffling, shrinking traffic for hot keys.
  • Click service side: keep the producer simple; do not try to aggregate in the stateless click service, because a crash there would lose counts.

5. Reconciliation: the safety net (good to know)

Streaming is fast but complex; batch is slow but simple and easy to verify. Running both is called a Lambda-style check. Every night, the batch job recounts from raw files in object storage with the same rules. If stream and batch differ by more than a tiny tolerance, the batch number wins, the table is corrected, and an alert fires so engineers can find the bug.

The modern alternative is Kappa: only a streaming job, and to fix a bug you deploy a fixed job and replay from Kafka (or from tiered storage / object storage) into a new table, then switch reads over. Many teams do Kappa for processing but still keep a batch check for billing data.

6. Click fraud (just enough) (good to know)

  • Inline, cheap rules in the Flink job: invalid signature, known bot user agents, data-centre IP ranges, too many clicks per user/IP per second, click before impression.
  • Async ML scoring later (minutes to hours) marks clicks as invalid; corrections flow into the final numbers. Never block the redirect on fraud checks.
  • See consumer groups: the fraud team simply adds its own consumer group on the same ad-clicks topic.
