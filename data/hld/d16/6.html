Deep dives

1. The URL frontier: priority and politeness at the same time

A single FIFO queue fails in two ways. Links on a page usually point to the same site, so the head of the queue fills with one host and politeness forces you to wait, which stalls everything (head-of-line blocking). And FIFO ignores importance: a news home page and a 10-year-old forum post get equal treatment. The classic fix comes from the Mercator crawler (Heydon and Najork, 1999) and is taught in the Stanford IR book: split the frontier into two layers.

  • Front queues (say 10 to 100): the prioritizer scores each URL (page importance such as PageRank or in-link count, how often it changes, whether it is a seed or sitemap URL) and puts it in the matching queue. A biased random pick reads high queues more often, so low-priority pages still move forward (no starvation).
  • Back queues: each back queue holds URLs from one host only. The Mercator rule of thumb is about three times as many back queues as fetcher threads, so a fetcher always finds a host that is ready.
  • The heap: one entry per back queue, keyed by the earliest time that host may be contacted. Delay can be fixed (1 s), taken from robots.txt Crawl-delay, or adaptive: Mercator waited about 10 times the duration of the last fetch, so slow (struggling) servers automatically get fewer requests.
  • Spill to disk: the frontier can hold billions of URLs, far more than RAM. Keep the head of each queue in memory and the tail on local disk (RocksDB or plain append-only files), just like a router buffering in DRAM behind SRAM.

From your world

Front queues are strict-ish priority classes; back queues are per-flow queues; the heap is a calendar queue / timer wheel that tells the scheduler which flow's shaper has tokens again. Adaptive delay is AIMD congestion control in spirit: when the far end slows down, you back off. Where this breaks: a shaper smooths bits; a crawler's unit is whole requests, and the far end's "capacity" is unknown, so the delay is a guess you keep adjusting from response times and HTTP 429/503 codes.

2. Distributing the crawl: shard by host

With 10-20 fetcher machines, who owns which URLs? The key insight: partition by host name, not by URL. If every URL of shop.example goes to one shard, then politeness, robots.txt caching and the host's DNS entry are all local to one machine, and no cross-machine lock is needed to enforce "one connection per host".

From your world

This is ECMP flow hashing. A 5-tuple hash pins a flow to one path so packets stay in order and per-flow state lives in one place; here a host-name hash pins a website to one shard so its politeness state lives in one place. And like resilient ECMP hashing, you want consistent hashing so a shard joining or leaving does not reshuffle every host. Where this breaks: a few giant hosts (one huge site with hundreds of millions of pages) make that shard hot, so very large sites get their own dedicated shard or a per-host budget.

Sharding by host has one subtlety: hosts that share one IP address (shared hosting, CDNs). Politeness really protects the server, so serious crawlers also rate-limit per IP or per IP range, not only per host name.

3. Dedup: URLs with a Bloom filter, content with fingerprints

URL dedup. Before enqueueing, ask "have I ever seen this normalised URL?" A hash set of 10 billion 16-byte hashes is about 160 GB; a Bloom filter answers the same question in about 12 GB at 1% error (from the estimate). A Bloom filter is a big bit array plus k hash functions: to add a URL, set k bits; to check, see whether all k bits are set. It can say "maybe seen" for a URL it never saw (a false positive), but it never says "not seen" for a URL it did see. For a crawler, a false positive means we skip a page we should have fetched, 1 time in 100. That is an acceptable loss; fetching every page twice is not.

The Bloom filter is a fast first gate, not the truth. The URL table stays the source of truth: on "maybe seen", some designs do a second lookup in the URL table for high-priority URLs to recover from false positives. Shard the filter by host hash, the same as the frontier, so each frontier shard owns its own filter in RAM and snapshots it to disk regularly (losing it means a burst of duplicate fetches, not a correctness bug).

Content dedup. Different URLs often serve the same page: http vs https, www vs no www, session IDs, mirrors, print versions. Two levels:

  • Exact duplicates: a SHA-256 of the body. If it is already in the content table, store a pointer and do not re-parse.
  • Near duplicates: pages that differ only in an ad or a timestamp. SimHash builds a 64-bit fingerprint where similar documents get fingerprints that differ in only a few bits. Google's 2007 paper on near-duplicate detection for crawling (Manku, Jain and Das Sarma) used 64-bit SimHash fingerprints and treated pages within a Hamming distance of 3 bits as near-duplicates. MinHash with locality-sensitive hashing is the other well-known option.

URL normalisation is the cheapest dedup of all. Here is a tiny, runnable version:

import hashlib
from urllib.parse import urlsplit, urlunsplit

def normalise(url: str) -> str | None:
    s = urlsplit(url.strip())
    if not s.hostname:                       # mailto:, relative links: not crawlable as-is
        return None
    host = s.hostname.lower()
    default = {"http": 80, "https": 443}.get(s.scheme.lower())
    netloc = host if s.port in (None, default) else f"{host}:{s.port}"   # http://h:443 keeps :443
    path = s.path or "/"
    return urlunsplit((s.scheme.lower(), netloc, path, s.query, ""))  # drop #fragment

for u in ["HTTP://Example.COM:80/a/b#top", "http://example.com/a/b"]:
    n = normalise(u)
    print(n, hashlib.sha256(n.encode()).hexdigest()[:16])
$ python normalise.py
http://example.com/a/b 649028aa54628de9
http://example.com/a/b 649028aa54628de9

4. robots.txt, DNS and the hidden bottlenecks

robots.txt rules from RFC 9309 (worth quoting precisely in an interview): a crawler must be able to parse at least 500 KiB of robots.txt; it should not use a cached copy for more than 24 hours; if robots.txt returns a 4xx "unavailable" status the crawler may crawl freely; and if it is "unreachable" (5xx or network error) the crawler must assume the whole site is disallowed. When several rules match, the most specific (longest) match wins, and Allow wins a tie. So cache robots.txt per host for up to a day, refresh it in the background, and fail closed on server errors.

from urllib import robotparser

rules = """
User-agent: *
Disallow: /cart/
Disallow: /search
Allow: /search/help
Crawl-delay: 2
""".splitlines()

rp = robotparser.RobotFileParser()
rp.parse(rules)
for path in ["/products/42", "/cart/checkout", "/search?q=tv", "/search/help"]:
    print(path, rp.can_fetch("DojoBot", "https://shop.example" + path))
print("crawl-delay:", rp.crawl_delay("DojoBot"))
$ python robots_demo.py
/products/42 True
/cart/checkout False
/search?q=tv False
/search/help False
crawl-delay: 2

Gotcha we hit while writing this page. Look at the last line: Python's built-in urllib.robotparser says /search/help is blocked. Under RFC 9309 the longer Allow: /search/help rule should win, so it should be allowed. The standard-library parser applies the first matching rule in file order instead. Also, if you call rp.read() on a site that answers your default User-Agent with 403, the parser marks the whole site disallowed. Production crawlers use an RFC-compliant parser (Google open-sourced its C++ robots.txt parser) and test it against tricky files.

DNS is the classic hidden bottleneck. Every new host needs a lookup; standard resolver calls are often blocking, and public resolvers rate-limit you. At about 1,000 fetches per second across many distinct hosts, uncached DNS can easily cost more time than the fetch. Fixes: a local caching resolver on every fetcher node (respecting TTLs), asynchronous DNS in the fetcher, and pre-resolving the next hosts in the back queues while their politeness timers run down. The Mercator team reported building their own multi-threaded DNS resolver for this reason.

From your world

The DNS cache is the ARP cache of the crawler: without it, every "packet" waits for a resolution round trip. Pre-resolving hosts while they wait in the heap is like ARP-ing for a next hop before the first packet arrives. Where this breaks: DNS TTLs and CDNs mean the IP behind a host can change often, so you cache by TTL, not forever.

5. Crawler traps, freshness and JavaScript

  • Traps: infinite calendars, session IDs in every URL, endless filter combinations on shop pages (?color=red&size=m&sort=price...), and symbolic-link loops like /a/b/a/b/a/b. Defences: maximum URL length; maximum depth from a seed; a per-host page budget per crawl cycle; strip known session and tracking parameters; detect repeating path segments; and watch for hosts whose "new URL" rate is far above their "new content" rate (lots of new URLs, same SimHash) and demote them.
  • Freshness / recrawl: every fetched URL gets a next_fetch time. A simple adaptive rule: if the content hash changed since last time, halve the interval (down to a floor); if not, double it (up to a cap). Use conditional GET (If-Modified-Since, If-None-Match with the ETag) so unchanged pages come back as a cheap 304 Not Modified. Sitemaps with lastmod tell you what changed without guessing.
  • Crawl budget: Google's documentation describes crawl budget as a mix of the crawl rate a site can handle and how much Google wants to crawl it (popularity, staleness). Same idea: capacity limit times demand.
  • JavaScript-heavy pages: many modern pages render their content with JavaScript. Running a headless browser (Chromium) costs far more CPU and memory than a plain HTTP fetch, so do it as a second pass: fetch HTML first, and send only pages that look empty or important to a separate rendering pool.

A strong closing line for the deep dives: "The frontier is the product. Everything else - fetchers, parsers, storage - is stateless and scales horizontally. The frontier holds the state: priority, politeness timers and seen-sets, so I shard it by host and make it durable."
