Quick quiz

Why do crawlers keep one back queue per host?

  1. So a host's delay never blocks other hosts
  2. So pages come out sorted by URL
  3. Because HTTP/1.1 limits one queue per host
  4. So each host gets its own fetcher pod
Per-host queues plus a heap of ready times remove head-of-line blocking while still spacing out requests to each host. Sorting is irrelevant. HTTP has no such rule. Many hosts share one fetcher; the queue, not the pod, is per host.

A Bloom filter says a URL was "probably seen" but it was not. What is the cost?

  1. The page is fetched twice
  2. That page is skipped this time
  3. The crawler crashes on the lookup
  4. The filter must be rebuilt now
A false positive means we wrongly think we saw it, so we skip it. Fetching twice would come from a false negative, which Bloom filters never give. A false positive is normal behaviour, not an error, and you size the filter so the rate is acceptable instead of rebuilding.

Under RFC 9309, robots.txt returns HTTP 503. What should the crawler do?

  1. Crawl everything, as for a 404
  2. Use the cached copy for a week
  3. Treat the site as disallowed for now
  4. Ignore robots.txt for that host
Unreachable (5xx) means assume complete disallow and retry later. Crawling freely is the rule for 4xx (unavailable), not 5xx. RFC 9309 says not to use a cached copy for more than 24 hours. Ignoring robots.txt is never an option for a polite crawler.

Fetch rate drops but fetcher CPU is idle. Most likely first suspect?

  1. Not enough CPU cores per fetcher
  2. DNS, or too few hosts ready
  3. The HTML parser is too slow
Idle CPU means workers are waiting, and DNS and politeness are the usual waits. More cores would help only if CPU were busy. A slow parser would show high CPU, the opposite of what we see.

Why shard the frontier by hash of host instead of hash of full URL?

  1. Host strings are shorter, so hashing is faster
  2. It spreads load far more evenly
  3. A host's queue, robots and timers stay on one shard
  4. It removes the need for a URL-seen test
Locality of per-host state is the point: no cross-shard locks for politeness. Hash speed is not the bottleneck. Load actually gets slightly less even (giant hosts), which you handle separately. Deduplication is still needed, since many pages link the same URL.

normalise() drops the port when it is 80 or 443 for any scheme. Why is that a bug?

  1. http://h:443/ becomes a different URL
  2. Ports are not allowed in URLs at all
  3. It makes the hash function collide
  4. It breaks the #fragment removal
Only the scheme's own default port may be dropped: http://h:443/ is HTTP on port 443, not http://h/. Ports are legal in URLs. The hash is fine; the input is wrong, so two different URLs merge. Fragment removal is unrelated.

Which is a crawler trap?

  1. A page returning 404
  2. A calendar with endless "next month"
  3. A sitemap.xml listing every page
  4. A page that redirects once to HTTPS
It produces infinitely many unique URLs with almost no new content. A 404 ends the path. A sitemap is a helpful list, not a trap. One redirect is normal; only redirect loops are a problem.

Why is Kafka alone a poor URL frontier?

  1. Kafka deletes each message once read
  2. A Kafka topic cannot hold billions of URLs
  3. Consumers cannot read from many partitions
  4. A partition is FIFO: no per-host delays
A partition is read in order, so you cannot pick "the next host whose delay has passed" or reorder by priority. Kafka does not delete on read; it uses retention. Billions of small messages are fine for Kafka. A consumer can read many partitions.

Using Little's law, 1,000 fetches/s at 1 s each needs about how many requests in flight?

  1. 10
  2. 100
  3. 1,000
  4. 10,000
In flight = arrival rate x time in system = 1,000/s x 1 s = 1,000. 10 and 100 divide instead of multiply. 10,000 would be the answer for 10 s per fetch.
