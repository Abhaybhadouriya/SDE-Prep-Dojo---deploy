Architecture

Here is the whiteboard version you should be able to redraw in 30 seconds. Then we walk one URL through it step by step.

One URL, step by step

Click Next or Play. Each step names the real component doing the work, because "the crawler fetches it" is not an answer.

  1. Pick. The frontier shard's scheduler pops the host whose next_allowed_at time has passed (a min-heap keyed by time), then takes the highest-priority URL from that host's queue.
  2. Check. The fetcher asks the robots cache "is this path allowed for my User-Agent, and what is the crawl delay?" and the DNS cache "what IP is this host?". Both are local caches; misses go to the network.
  3. Fetch. HTTP GET with a connect timeout, a total timeout and a size cap (for example 10 MB), and a limit on redirects. The fetcher records status, headers and timing.
  4. Store. The compressed body goes to the blob store (appended into a WARC file); the URL row is updated with status, time and content_hash. If the content hash was already seen, we stop here: duplicate content.
  5. Parse. The parser extracts <a href> links, resolves relative links against the page URL, reads rel="nofollow" and <meta name="robots">, and computes a SimHash for near-duplicate detection. Content goes on to the indexer.
  6. Filter. Each link is normalised (lower-case host, drop default port, drop #fragment, sort or strip tracking query parameters), checked against length/depth limits and blocklists, then checked in the Bloom filter: "seen before?".
  7. Enqueue. Truly new URLs are routed to the frontier shard that owns their host (hash of host), with a priority. The URL is then marked as seen.
  8. Failure. A fetcher holds each task on a lease. If it crashes, the lease times out and the task returns to the frontier. That is why stages must be idempotent: a URL may be fetched twice, never lost.
