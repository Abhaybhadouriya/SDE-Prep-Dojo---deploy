Key APIs

A crawler has no public users, so its APIs are internal: an admin API for operators and the contracts between stages. Interviewers still want to see them, because they define the boundaries of each service.

# Admin / control plane
POST /v1/seeds            {"urls": ["https://news.example/"], "priority": 9}
GET  /v1/crawl/stats      -> {"fetched_per_sec": 412, "frontier_size": 8.1e9, "errors_5xx": 0.7}
PUT  /v1/hosts/{host}     {"max_qps": 0.5, "blocked": false}     # manual politeness override
GET  /v1/urls/{url_hash}  -> {"url": "...", "last_fetch": "...", "status": 200, "next_fetch": "..."}

# Internal stage contracts (messages, not HTTP)
FetchTask    {url, url_hash, host, priority, depth, attempt}
FetchResult  {url_hash, status, fetched_at, content_hash, blob_key, headers, redirect_to}
LinksFound   {from_url_hash, links: [normalised_url, ...]}

Two details show maturity. First, every task carries url_hash, so a retried or duplicated message is harmless (the stages are idempotent, meaning doing them twice has the same effect as doing them once). Second, the fetcher sends an honest User-Agent header such as DojoBot/1.0 (+https://dojo.example/bot) so site owners can identify you and write robots.txt rules for you.
