Data model and storage choices

There are four kinds of data, and each wants a different store. Learner question answered: "When do I pick SQL vs NoSQL, and how do I justify it in one sentence?" The sentence here: URL metadata is billions of rows looked up by a single key with no joins, so I pick a horizontally sharded wide-column store; the raw pages are large immutable blobs, so they go to object storage.

DataShapeStoreKey
URL metadataurl, host, status, last_fetch, next_fetch, content_hash, priority, depthCassandra / Bigtable / DynamoDBurl_hash (SHA-256 of the normalised URL, first 8-16 bytes)
Host tablehost, robots rules, robots_fetched_at, crawl_delay, next_allowed_at, ip, error_rateSame wide-column store + in-memory cache on each frontier shardhost
Raw pagesCompressed HTML, 10-100s of KB each, never updatedObject storage (S3, GCS, MinIO); often packed into large WARC filescontent_hash or date/shard/file + offset
Seen sets"Have I seen this URL / this content fingerprint?"Bloom filter in RAM per shard, backed by the URL table; SimHash index for near-duplicateshash bits
 
-- Cassandra-style table for URL metadata (CQL)
CREATE TABLE crawl.urls (
  url_hash     blob PRIMARY KEY,   -- 16 bytes of SHA-256(normalised URL)
  url          text,
  host         text,
  status       smallint,           -- last HTTP status
  last_fetch   timestamp,
  next_fetch   timestamp,
  content_hash blob,               -- SHA-256 of body, for exact dedup
  simhash      bigint,             -- 64-bit fingerprint, near-dup
  priority     tinyint,
  depth        smallint
);

-- Pages due for recrawl, partitioned by shard and hour bucket
CREATE TABLE crawl.due_by_shard (
  shard int, due_hour timestamp, url_hash blob,
  PRIMARY KEY ((shard, due_hour), url_hash)
);

Why not one big relational database? The access pattern is "get or upsert by one key" at thousands of operations per second, the data is 5 TB and growing, and we never join. A relational DB would work for a small crawl (and is a fine answer for SDE-1 if you say where it stops scaling), but a sharded key-value or wide-column store scales out simply by adding nodes. Raw pages are written once and read in bulk by the indexer, which is exactly what object storage is good at. The WARC format (Web ARChive) is the standard container used by the Internet Archive and Common Crawl: many pages appended into one big file, which avoids billions of tiny objects.

You might confuse this with "the URL table is the frontier". It is not. The URL table is the long-term memory (everything we know). The frontier is the short-term working set (what to fetch next, in which order, and when each host is allowed again).
