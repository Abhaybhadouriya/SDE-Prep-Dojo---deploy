Interview: how to drive 45 minutes

  1. 0-5: requirements. Purpose (search, archive, price tracking?), scale (pages/month), content types, freshness, politeness, JavaScript? Write the numbers on the board.
  2. 5-10: estimate. 400/s average, ~1,000/s peak, 100 TB/month raw, ~1,000 in flight, Bloom filter ~12 GB.
  3. 10-20: draw the loop. Seeds -> frontier -> fetcher (DNS, robots) -> store -> parser -> filter/dedup -> frontier. Walk one URL through it.
  4. 20-35: deep dives. Frontier (front/back queues + heap), shard by host, dedup (Bloom + SimHash), traps, failure of a fetcher.
  5. 35-42: scale and fail. Box-by-box failure table, Kafka between stages, autoscaling limits, DNS.
  6. 42-45: wrap up. Monitoring (fetch rate, error rate per host, frontier age, duplicate ratio, DNS p99) and what you would build next (JS rendering pool, freshness model).

Common mistakes: one global FIFO queue (kills politeness and causes head-of-line blocking); no URL normalisation; ignoring robots.txt or caching it forever; storing the frontier only in memory; saying "use Kafka as the frontier" without explaining delays and priority; forgetting DNS; no answer for traps; diving into HTML parsing details for ten minutes (the learner's own warning: do not over-explain internals and forget the user and the API).

60-second answer, said out loud: "A crawler is a loop: take a URL from the frontier, fetch it, store it, extract links, filter them and add new ones back. At a billion pages a month that is about 400 fetches a second, a thousand in flight, and 100 TB a month of raw HTML, so pages go to object storage and URL metadata to a sharded wide-column store. The hard part is the frontier: front queues for priority, one back queue per host plus a heap of next-allowed times for politeness, and I shard it by host hash so each host's state lives on one machine. I dedup URLs with a Bloom filter and content with SHA and SimHash, respect robots.txt with a 24-hour cache, cache DNS locally, and cap depth and URL length against traps. Fetchers and parsers are stateless pods connected by Kafka topics, so a crashed worker's tasks are simply redelivered."

Why not just use one big FIFO queue for the frontier?

Because links cluster by host. A page from shop.example mostly links to shop.example, so a FIFO fills with one host at the head. Politeness forces a delay between requests to that host, so the whole crawler waits (head-of-line blocking). FIFO also has no notion of importance. Split it: priority front queues plus one back queue per host, with a heap of next-allowed times.

How to answer

Name the failure (head-of-line blocking), then the two-layer fix, then one number (about 3x as many back queues as fetcher threads, per Mercator).

Likely follow-ups
  • How do you stop low-priority URLs from starving?
  • What if one host has 100 million URLs?
How do you avoid crawling the same URL twice across 20 machines?

Normalise the URL, hash it, and route it by host hash to the one shard that owns that host. That shard checks its own Bloom filter (fast, in RAM) and, when needed, the URL table (truth). Because one host always maps to one shard, two machines never race on the same URL. The URL table upsert keyed by url_hash makes a rare double insert harmless.

How to answer

Ownership first (shard by host), then the data structure (Bloom), then why false positives are acceptable.

Likely follow-ups
  • How big is the Bloom filter? (do the math)
  • How do you delete from a Bloom filter?
Size a Bloom filter for 10 billion URLs at a 1% false-positive rate.

m = -n ln p / (ln 2)^2 = 10^10 x 4.6 / 0.48, about 9.6 x 10^10 bits, about 12 GB. k = (m/n) ln 2, about 6.6, so 7 hash functions. Split across shards (12 shards = about 1 GB each). In practice compute the k positions from two base hashes (h1 + i x h2) instead of 7 independent hash functions.

How to answer

Write the formula, round loudly, give bytes per item (about 9.6 bits per URL at 1%), and say what a false positive costs here (a skipped page).

Likely follow-ups
  • What happens to the error rate if you insert 20 billion instead?
  • Bloom vs cuckoo filter?
How do you detect and escape crawler traps?

Prevention: max URL length, max depth from seed, max pages per host per cycle, strip session/tracking parameters, detect repeating path segments. Detection: a host producing many new URLs but few new content fingerprints (same SimHash) is likely a trap or a faceted-search explosion; demote or cap it. Allow manual host overrides via the admin API.

How to answer

Give two concrete traps (infinite calendar, session IDs), then limits, then a signal-based detector.

Likely follow-ups
  • Won't a per-host cap hurt big legitimate sites like Wikipedia?
How do you detect near-duplicate pages?

Exact duplicates: hash the body (SHA-256). Near duplicates: SimHash. Split the text into features (word shingles), hash each feature, add or subtract weights per bit, and keep the sign of each bit: similar pages produce fingerprints with few differing bits. Google's 2007 crawling paper used 64-bit fingerprints and a Hamming distance threshold of 3. To find neighbours fast, split the 64 bits into blocks and index by block, since two fingerprints within 3 bits must share at least one block exactly.

How to answer

Two levels (exact, near); one algorithm explained in one sentence; how you search the index.

Likely follow-ups
  • SimHash vs MinHash?
  • What do you do when you find a duplicate - drop it or keep a canonical URL?
A fetcher crashes in the middle of 200 fetches. What happens to those URLs?

They were leased, not deleted. With Kafka, the fetcher had not committed their offsets, so after the group rebalances another fetcher re-reads them. With a custom frontier, each handed-out task has a lease timeout; when it expires the task is re-queued. Some URLs get fetched twice, which is fine because writes are keyed by url_hash (idempotent). That is at-least-once delivery.

How to answer

Say "at-least-once plus idempotent stages" in the first sentence; that is the phrase they are listening for.

Likely follow-ups
  • How long should the lease be?
  • How do you avoid a poison URL crashing fetchers forever? (attempt counter -> dead-letter)
How do you decide when to recrawl a page?

Each URL has a next_fetch time. Start from priority (important pages sooner). Adapt using history: if the content hash changed, shorten the interval; if not, lengthen it, within floor and cap. Use sitemaps' lastmod and conditional GET (ETag, If-Modified-Since) so unchanged pages cost a 304. A due-by-time table per shard feeds the frontier.

How to answer

Change rate x importance = urgency. Mention the 304 trick; it saves bandwidth and the site's CPU.

Likely follow-ups
  • How do you crawl breaking news within minutes?
What does robots.txt require, and what if it is unreachable?

Per RFC 9309: match your User-Agent group, longest matching rule wins (Allow wins ties), parse at least 500 KiB, do not use a cache older than 24 hours. If robots.txt returns 4xx, crawling is allowed. If it is unreachable (5xx or network error), assume complete disallow. So: fail closed on server errors, retry later.

How to answer

Quote the RFC number; it signals you know this is a real standard, not folklore.

Likely follow-ups
  • Is Crawl-delay part of RFC 9309? (No, it is a common extension; Google ignores it.)
Could Kafka be the entire frontier?

Not on its own. A partition is a FIFO log: no priority reordering, no per-host delay without blocking the partition, no dedup. If you key by host, one slow host blocks every other host in its partition. Kafka is excellent between stages (durable, replayable, consumer groups for failover) and as the input to frontier shards, but the politeness scheduler has to live in the shard service. Queue-style share groups (KIP-932, production-ready in Kafka 4.2) add per-message acknowledgement but still not per-host timers.

How to answer

Say what Kafka is good at first, then the exact missing feature (time-delayed per-key scheduling).

Likely follow-ups
  • Would SQS with delay queues work? (per-message delay up to 15 minutes, but no per-host grouping)
You go from 1 billion to 30 billion pages a month. What changes?

30x everything: about 12,000 fetches/s average, about 3 PB/month raw. Fetchers and parsers just scale out. The frontier and seen-sets need more shards (use consistent hashing so resharding moves few hosts). DNS becomes a serious tier (dedicated resolver fleet). Per-IP politeness matters more because many hosts share CDNs. Storage moves to WARC packing plus tiered cold storage. Probably multi-region crawling to be close to sites, with each region owning a host range so politeness stays global.

How to answer

Recompute the numbers first, then name which components are stateless (easy) and which are stateful (hard).

Likely follow-ups
  • How do two regions avoid crawling the same host at once?
Design it for an SDE-1 interview in 15 minutes. What do you keep?

The loop, a frontier with per-host queues and a fixed delay, robots.txt check, a seen-set (a Bloom filter or a DB unique key), pages in object storage, metadata in a DB, workers that retry on failure. Skip SimHash and recrawl models unless asked. SDE-1 interviewers judge clarity and a working design; SDE-2 interviewers expect you to bring up politeness, sharding and failure without being asked.

How to answer

Show you know what to leave out and why.

Likely follow-ups
  • What is the first thing that breaks as you scale this?

Scenario: a site owner emails "your bot took us down"

A small shop says your crawler sent hundreds of requests per second last night. Your politeness config says 1 request per second per host.

Weak answer: "Our config says 1 per second, so it was not us."

Strong answer: check the logs by IP and User-Agent. Likely causes: the shop has many host names (subdomains or wildcard DNS) that all resolve to one small server, so per-host limits added up; or a resharding moved the host to two shards at once. Fix: enforce politeness per resolved IP as well as per host, add a global per-IP limiter, back off on slow responses and 503/429, and give site owners a clear bot info page and contact.

Likely follow-ups
  • How would you enforce a per-IP limit if hosts of one IP are on different shards?

Scenario: fetch rate halves, CPU is idle

After a deploy, pages per second drops by 50%. Fetcher CPU and network are both low.

Weak answer: "Add more fetcher pods."

Strong answer: idle CPU plus low throughput means the fetchers are waiting. Check, in order: DNS latency and cache hit ratio (a resolver config change is a classic), the number of hosts ready in the heap (if few are ready, the frontier is the limit), timeout settings, and lease/ack errors. Adding pods does nothing if the limit is politeness or DNS.
