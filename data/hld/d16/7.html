Where Kafka, Kubernetes and Docker fit

Interviewers often ask "would you use Kafka here?" The honest answer: Kafka is a great pipe between stages, but it is a poor frontier by itself, because a Kafka partition is a strict FIFO log. It cannot reorder by priority, cannot delay one host for 2 seconds while serving others, and cannot dedup. So we use Kafka for the durable hand-offs and keep the smart frontier in the shard services.

  • Kafka (core concepts): fetch-tasks (key = host, so a fetcher partition sees a host in order), pages (metadata + blob pointer, not the 100 KB body; Kafka's default max message size is about 1 MB, and pointers keep the log small), and links-found (key = host so links land on the partition read by the owning frontier shard). Each stage is a consumer group (consumer groups): if a parser dies, its partitions move to another parser and it resumes from the last committed offset. This gives replay for free: found a parser bug? Reset the parser group's offsets and re-parse a day of pages.
  • Kubernetes: fetchers and parsers are stateless Deployments that autoscale on consumer lag (KEDA's Kafka scaler or an HPA on an external metric; see autoscaling). Frontier shards hold state (queues on disk, Bloom filter snapshots), so they are a StatefulSet with a persistent volume per shard and a stable name (frontier-0, frontier-1) that maps to a host-hash range. A node-local DNS cache runs as a DaemonSet.
  • Docker: one small image per stage (multi-stage builds, see Dockerfiles). The JavaScript-rendering pool is a separate, much bigger image with headless Chromium, and gets its own resource limits so it cannot starve the cheap fetchers.
# KEDA ScaledObject: scale fetchers on Kafka consumer lag
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: fetcher
spec:
  scaleTargetRef:
    name: fetcher            # the Deployment
  minReplicaCount: 4
  maxReplicaCount: 40        # never more than the topic's partition count
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: fetchers
        topic: fetch-tasks
        lagThreshold: "5000"

Trap: autoscaling fetchers does not make you crawl a given site faster. Politeness caps per-host throughput. More fetchers only help when you have many hosts ready at once. Say this before the interviewer does.
