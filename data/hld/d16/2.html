Back-of-envelope estimation

Learner question answered: "How do I estimate QPS and storage without a calculator?" Round hard, write each step, and label assumptions. One month is about 30 x 86,400 s, which is about 2.6 million seconds. (See Back-of-Envelope Estimation for the cheat sheet.)

  1. Fetch rate. 1,000,000,000 pages / 2,600,000 s is about 400 pages per second on average. Crawls are not tied to human day/night traffic, but assume bursts and catch-up after failures, so plan for about 1,000 pages/s peak (2.5x, a rule of thumb).
  2. Page size. Assume an average HTML page of 100 KB (assumption; real averages vary by crawl).
  3. Bandwidth. 400 pages/s x 100 KB = 40 MB/s, which is about 320 Mbit/s average and about 800 Mbit/s at peak. That fits in a few 10 Gbit NICs with lots of headroom; bandwidth is not the bottleneck.
  4. Raw storage per month. 1 B x 100 KB = 100 TB per month before compression. HTML compresses well; assume about 4x with gzip or zstd (assumption), so about 25 TB/month stored, about 300 TB/year, and with 3 copies in object storage about 900 TB/year. If we keep 5 years: a few petabytes. That is why raw pages go to object storage (S3-like), not a database.
  5. Concurrency (the number people forget). Little's law: concurrent requests = rate x time per request. If an average fetch takes about 1 s (DNS + TCP + TLS + slow servers; assumption) then at peak we need about 1,000 fetches in flight. With async I/O one machine can hold hundreds of open sockets, so roughly 10-20 fetcher pods is enough. The limit is politeness and DNS, not CPU.
  6. URLs seen. If each page has many links (assume ~50 raw links, most duplicates), the set of distinct URLs we have ever seen grows into the tens of billions. Take 10 billion URLs for sizing the "seen" filter.
  7. Bloom filter size. For n = 10 billion and a 1% false-positive rate: bits m = -n ln(p) / (ln 2)^2 = 10^10 x 4.6 / 0.48, about 9.6 x 10^10 bits, which is about 12 GB. Best number of hash functions k = (m/n) ln 2, about 9.6 x 0.69, so 7 hashes. 12 GB fits in RAM split over a few shards.
  8. URL metadata. About 500 bytes per URL row (URL, host, hashes, timestamps, status) x 10 B = 5 TB, which is a job for a wide-column store, sharded.

From your world

Little's law is the bandwidth-delay product you already know. A long fat pipe needs a big TCP window to stay full; a crawler with slow remote servers needs many requests in flight to hit its rate. Doubling server latency doubles the number of open sockets you need, not the bandwidth. Where this breaks: a TCP window is one connection to one peer; a crawler's "window" is spread over thousands of hosts, and politeness caps how much of it any single host may use, so slow hosts cannot simply be given a bigger window.

$ python -c "import math; n=10_000_000_000; p=0.01; m=-n*math.log(p)/math.log(2)**2; print(f'bits={m:.3e} GB={m/8/1e9:.1f} k={m/n*math.log(2):.2f}')"
