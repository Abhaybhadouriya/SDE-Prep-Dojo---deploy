Requirements

Always start by asking what the crawler is for. A search-engine crawler, a price-monitoring crawler and an archive crawler make different choices. We will design a general-purpose crawler for a search index, which is the usual interview prompt.

Functional (what it does)

  1. Start from seeds Accept a list of seed URLs and crawl outward by following links.
  2. Fetch and store Download HTML pages and store the raw content plus metadata (URL, fetch time, HTTP status, content hash).
  3. Extract links Parse each page, find outgoing links, normalise them and add new ones to the frontier.
  4. Be polite Obey robots.txt, use at most one open connection per host, and wait between requests to the same host.
  5. Recrawl Visit pages again over time; pages that change often (news home pages) more often than pages that rarely change.
  6. Hand off Publish fetched content to downstream systems (indexer, link graph, analytics).

Out of scope (say it out loud)

Ranking, the search index itself, and the search UI. Images and video (HTML only for now). Logging in to sites. Running JavaScript for every page (we will discuss it as an extension).

From your world

Think of the crawler as a router fabric where every website is an egress port with its own shaper. The frontier is a set of per-destination queues, and politeness is a per-port rate limiter (a token bucket per host). The big lesson from QoS carries over directly: one shared FIFO causes head-of-line blocking. If the head of the queue is 10,000 URLs for one slow site, every other site starves. Where this breaks: a router drops packets when a queue fills; a crawler must never drop URLs silently, so its queues spill to disk instead.
