Deep dives: the hard parts

1. Ordering and "one writer per key"

Walmart's Confluent post describes the exact bug this prevents: one consumer thread reads an item-store and writes 20, another writes 22, and the final value depends on timing. Their fix was a partitioning strategy where each item-store always goes to one partition, so only one consumer handles that combination. Kafka guarantees order inside a partition, and a consumer group gives each partition to exactly one member. Together those give us serial, lock-free updates per key, while 128 partitions still run in parallel.

From your world

This is ECMP flow hashing. A router hashes the 5-tuple so all packets of one flow take one path and stay in order, while different flows spread across links. Here the "flow" is item+location and the "links" are partitions. Adding partitions is like changing the ECMP group size: flows get re-hashed and you can briefly lose ordering. Where it breaks: ECMP with resilient hashing limits the churn; Kafka's default partitioner does not, so many keys move at once.

  • Never change the partition count casually. hash(key) % N changes for most keys when N changes. If you must grow, either create a new topic with more partitions and migrate with a pause per key, or accept a short window where you drain the old topic before switching.
  • Align the database partitioning with the Kafka key (Walmart's post recommends this for Cassandra) so one consumer's writes land on a small set of database partitions.
  • Rebalances pause work. When a pod dies, its partitions move to others after the session timeout. Use static membership and cooperative rebalancing to reduce pauses (see Consumers & Consumer Groups).

2. Never sell the last unit twice

Two shoppers press "Reserve for pickup" on the last unit within the same second. The availability cache says 1 for both. The cache is allowed to be stale; the reserve step must not be. The reservation service does one atomic conditional update:

UPDATE inventory_position
   SET reserved = reserved + 1, reserved_version = reserved_version + 1, updated_at = now()
 WHERE item_id = 'SKU123' AND location_id = 'store-42'
   AND on_hand - reserved - safety_stock >= 1;
-- 1 row  -> reserved; insert the reservation row in the same transaction
-- 0 rows -> 409 INSUFFICIENT_STOCK; show "not available, try another store"
  • Why two owners on one row is safe: each column has exactly one owner, with no exceptions. The processor changes on_hand for every event type (sales, receipts, returns, counts and picks) and bumps only onhand_version. The reservation service changes reserved for holds, releases, commits and picks and bumps only reserved_version. The processor's write is an upsert guarded by its own version (... SET on_hand = :v, onhand_version = :ver WHERE onhand_version < :ver), so a replayed old write is ignored. The reservation service always uses one atomic statement of the form SET reserved = reserved + :delta, never "read, compute in the app, write back", and the reserve check reads both columns at the moment of the update. Neither writer ever puts back a value the other one changed, so no lost update is possible.
  • TTL on holds. A held reservation expires (say 15 minutes) if the order is not paid. A sweeper releases expired holds by decrementing reserved, idempotently (only rows still HELD).
  • When the item is picked, the PICK event (with one event_id) flows to both owners. The processor applies it like a sale: on_hand -= q in its state store, then writes the new value with the next onhand_version. The reservation service consumes the same event idempotently (it skips an event_id it has already applied) and releases the hold in one transaction: 
    BEGIN;
UPDATE reservations
   SET status = 'FULFILLED'
 WHERE reservation_id = :r AND status = 'COMMITTED';      -- 0 rows = already applied: stop here
UPDATE inventory_position
   SET reserved = reserved - :q,
       reserved_version = reserved_version + 1
 WHERE item_id = :item AND location_id = :loc;
COMMIT;
    The two writes land a moment apart. If on_hand drops first, available briefly falls by 2 for one unit, which can cause a false "not available" on a low-stock item for a second or so. We accept that dip: safety stock usually covers it, and a false "no" is far cheaper than an oversell. The processor's state store always includes the pick, so its next write (for a till sale, say) can never put the old on_hand back.
  • Safety stock absorbs the gap between "system says 1" and "shelf has 0". For hot or theft-prone items, raise it; for slow movers, lower it.
  • Alternative: route reservation requests through the same Kafka partition so the processor (the single writer) decides. That is consistent and lock-free but adds Kafka latency to checkout; the DB conditional update is simpler to explain.

3. Duplicates, late events and absolute counts

  • Duplicates: producers retry, so events can arrive twice. Dedupe by event_id: keep recent ids in a windowed state store, or in a KeyValueStore that a punctuator (a timer callback in Kafka Streams) cleans every few minutes, with a retention you choose (for example 7 days; a plain KeyValueStore has no TTL of its own). Kafka Streams' exactly_once_v2 makes state updates and output records commit together, but it covers only Kafka-to-Kafka. The write to the position DB is outside it, so that write must be idempotent too: a sink connector (Walmart's post describes a Cassandra connector) or an upsert keyed by item|location that only applies a newer onhand_version.
  • Delta vs absolute events. SALE, RETURN and RECEIPT are deltas (+/- qty). COUNT is absolute ("there are 7 as of 14:00"). A delta is safe to apply once; an absolute event resets the number.
  • Late events after a count. A till that was offline uploads a sale from 13:50 at 14:05, after the 14:00 count. The count already includes that sale (the item was gone from the shelf). Rule: when a COUNT arrives, store last_count_at; ignore deltas whose event_time is before it. This is event time vs processing time in a real business setting.
  • Per-source sequence numbers (source_seq) let the transformer detect gaps ("store 42 sent 917 then 919") and ask the source to resend.

4. The read path at 250,000 lookups/s

  • Serve status buckets, not exact numbers. Most pages only need IN_STOCK / LOW / OUT. A bucket changes far less often than the exact count, so caches stay valid longer and the update stream is smaller.
  • Precompute regional rollups. For "ship to ZIP 560103 by Friday", keep a view keyed by item+region listing the best few locations with stock, updated from the positions stream.
  • Layered caches: a short TTL in the app/CDN for product pages (seconds), Redis/Valkey for the availability view, the position DB only for misses.
  • Always re-check at reserve time (deep dive 2). Browsing is eventually consistent; checkout is strongly consistent.

5. Hot SKUs on launch day

A console launch puts thousands of reservations per second on a few keys. One key lives in one partition and one database row, so it cannot scale out. Options: pre-split online stock into buckets (10 rows of 100 units) and pick a random bucket; or put a Redis counter with atomic DECR in front as a gate and settle the DB asynchronously; plus a virtual waiting room. This is the same problem as Flash Sale and the Dealing with Contention pattern.

6. Replenishment and multi-region

A replenishment consumer reads positions, compares them with a reorder point (forecast demand over lead time plus safety stock) and creates purchase or transfer orders. Walmart's replenishment post describes a Kafka-based micro-batch framework for this. For disaster recovery, run Kafka per region and mirror topics with MirrorMaker 2; keep each item-location's writer in one region at a time (a home region per store) so two regions never both write the same key.
