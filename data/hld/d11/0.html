The story

Explain like I'm 5

Imagine a toy shop with one big chalkboard by the door. It says "Teddy bears: 10". Every time a cashier sells a bear, she shouts "one bear sold!" and a helper rubs out 10 and writes 9. When the truck brings 5 more bears, the driver shouts "five bears in!" and the helper writes 14.

Now imagine 5,000 shops, 100,000 kinds of toys, and children ordering on the internet too. If two helpers try to change the same number at the same moment, one of them gets it wrong. So we give every toy-and-shop pair exactly one helper. All the shouts about "teddy bears in shop 42" go to that one helper, in the order they happened. She is never confused, because nobody else touches her number.

Once a week, someone walks the shelves and counts the bears by hand. If the board says 9 and the shelf has 7, the board was wrong, so we fix the board.

That is the whole design in a story. The shouts are inventory events (a sale, a return, a delivery). The helper for each toy-and-shop pair is a single writer for that key. The ordered line of shouts is a Kafka partition. The chalkboard number is the inventory position. The weekly hand count is a cycle count, and fixing the board is reconciliation.

This question is very commonly reported at Walmart, Flipkart and Amazon-style retail loops, because it combines everything they live with: huge numbers of stores and SKUs (a SKU, stock keeping unit, is one sellable product variant, like "blue T-shirt, size M"), online and offline sales of the same stock, and big sale days.

New words, once each (you will meet them in the next sections):

  • p99 = the 99th percentile latency: 99 of every 100 requests are faster than this number. "p99 under 5 s" means only 1 in 100 updates may take longer than 5 seconds to show up.
  • Shard = one slice of a database that has been split by key, each slice on its own servers. A "sharded database" is many smaller databases that together hold all the rows.
  • Eventual consistency = a reader may see a value a few seconds old, but if writes stop, every copy ends up the same. Strong consistency = every reader sees the latest committed value.
  • Idempotent = doing it twice has the same effect as doing it once.
  • Event sourcing = store every change as an event and compute the current number from them, instead of storing only the number.
  • Denormalised = data copied into the shape a reader needs (fields from several tables in one row), so reads need no joins.
  • Micro-batch = process events in small groups every few seconds instead of one at a time or once a night.
