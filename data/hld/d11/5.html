Architecture: follow one sale

Whiteboard version (5 boxes): sources, Kafka, inventory processor, position DB, availability view, plus a reservation service on the side. Click Play.

  1. Events in. A till sells one teddy. The store system produces a sale event to a Kafka source topic. If the network to the data centre is down, the store buffers locally and sends later, so the till never waits on us.
  2. Make it canonical. A transformer service reads each source topic, validates the event, converts it to the canonical shape, and drops exact duplicates by event_id.
  3. Key it. It produces to inventory-events with key item_id|location_id. Kafka hashes the key, so every event for "SKU123 at store-42" lands in the same partition, in order.
  4. One writer per key. The inventory processor (a consumer group, e.g. Kafka Streams or Flink) owns each partition with exactly one instance. It applies the event to the position: on_hand 10 becomes 9. No locks needed: nobody else writes that key's on_hand.
  5. Persist. It writes the new on_hand to the position DB (and keeps it in its local state store, backed by a Kafka changelog topic for recovery). The processor is the only writer of on_hand, for every event type, including picks.
  6. Publish the result. It emits the new position to inventory-positions. The availability service consumes it, computes available = on_hand - reserved - safety, maps it to a status (IN_STOCK / LOW / OUT) and updates the cache. The website reads the cache.
  7. Reservations. When a shopper checks out a pickup order, the reservation service does an atomic conditional update on the position row: reserve only if enough is available. It owns the reserved column (and its own reserved_version); the processor owns on_hand (and onhand_version). The line from the reservation service goes straight to the position DB, not through the processor.
  8. Other consumers. Replenishment reads positions to create purchase orders when stock passes a reorder point; analytics and the data lake keep the full history.
  9. Reconcile. A store associate counts the shelf: 7 teddies, while the system says 9. The count becomes a COUNT event in the same partition and resets on_hand to 7. The 2-unit gap is logged as "shrink" (loss) for finance.
