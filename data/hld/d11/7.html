Where Kafka, Kubernetes and Docker fit

  • Kafka: source topics, the canonical inventory-events topic (key item|location), a compacted inventory-positions topic (keeps only the latest position per key, like a MAC table keeps the latest entry per address), changelog topics for processor state, and a DLQ for events that fail validation. See Topics, Partitions, Offsets and Connect, Streams & Flink.
  • Kubernetes: the processor runs as a StatefulSet with a PersistentVolume for its RocksDB state, so a pod that was shut down cleanly reuses local state instead of replaying the whole changelog. (Under exactly_once_v2, a crash leaves no valid checkpoint, so the store is wiped and fully restored; standby replicas are what keep that failover fast.) Stateless services (transformer, availability API, reservation API) are Deployments with HPAs (Horizontal Pod Autoscaler: adds or removes pods when CPU or another metric crosses a target). Kafka itself can run on K8s with the Strimzi operator (an operator is a controller that runs Kafka for you: it creates the broker pods, disks and certificates and handles upgrades) (see StatefulSets & Operators and Deploy on Kubernetes).
  • Docker: each service ships as an image; locally, a Docker Compose file with one Kafka broker, Postgres and Redis is enough to test the whole flow (see Build It Locally).
StreamsBuilder builder = new StreamsBuilder();

KStream<String, InventoryEvent> events = builder.stream(
    "inventory-events", Consumed.with(Serdes.String(), eventSerde));   // key = item|location

KTable<String, Position> positions = events
    .groupByKey(Grouped.with(Serdes.String(), eventSerde))   // already keyed: no repartition; serdes given
                                                              // because the config sets no default serdes
    .aggregate(
        Position::empty,
        (key, event, pos) -> pos.apply(event),      // dedupe by event_id, apply delta or count
        Materialized.<String, Position, KeyValueStore<Bytes, byte[]>>as("positions-store")
            .withKeySerde(Serdes.String())
            .withValueSerde(positionSerde));

positions.toStream().to("inventory-positions", Produced.with(Serdes.String(), positionSerde));
application.id=inventory-processor
bootstrap.servers=kafka:9092
processing.guarantee=exactly_once_v2
num.standby.replicas=1
state.dir=/var/lib/kafka-streams
replication.factor=3
# internal changelog/repartition topics also need 2 in-sync copies
topic.min.insync.replicas=2
# transformer producing to inventory-events
# (both are the defaults since Kafka 3.0; write them anyway so the choice is visible)
acks=all
enable.idempotence=true

Walmart's post reports choosing acks=1 for throughput. We show acks=all because with min.insync.replicas=2 an acknowledged sale survives a leader crash. See the trade-off table below.

kafka-topics.sh --bootstrap-server localhost:9092 --create --topic inventory-events \
  --partitions 128 --replication-factor 3 --config min.insync.replicas=2

kafka-topics.sh --bootstrap-server localhost:9092 --create --topic inventory-positions \
  --partitions 128 --replication-factor 3 --config cleanup.policy=compact

Partition 17 is far behind while the others are fine: that is a hot key or a slow pod, not a cluster-wide problem. Lag that grows on all partitions means the whole group is under-provisioned or the database is slow.
