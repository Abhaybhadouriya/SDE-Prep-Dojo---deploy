How Walmart (and others) do it

  • Walmart real-time inventory on Kafka (Confluent blog, May 2020, written by a former Walmart director of engineering): more than 10 event sources with different shapes, a central "smart transformation engine" that converts them to a canonical inventory event, Kafka Streams to build a debit/credit inventory state per item-store, and a Kafka connector into Cassandra. They partition so that each item-store always goes to one partition and one consumer, align Kafka and Cassandra partitioning, tune linger.ms and batch.size, and size consumers to about the partition count. (Walmart's real-time inventory system powered by Apache Kafka)
  • Walmart replenishment on Kafka: a micro-batch framework on 18 brokers with 20+ topics of 500+ partitions each, with CDC (change data capture: stream every committed row change out of the database's commit log) feeding a denormalised view. (How Walmart uses Kafka for real-time omnichannel replenishment)
  • Walmart at Kafka scale: Walmart Global Tech describes trillions of messages a day and 25K+ consumers, and a Messaging Proxy Service that keeps per-key ordering while avoiding rebalance pain (Reliably processing trillions of Kafka messages per day; opens in a browser; summary on ByteByteGo).
  • Event sourcing and CQRS background: Martin Fowler's Event Sourcing and CQRS.

What went wrong in the real world (illustrative scenario)

We could not find a public, sourced post-mortem of an inventory drift incident, so this is an illustrative scenario built from the failure modes on this page, not a real company's story. A retailer adds partitions to its inventory topic the night before a sale (from 64 to 96) to get more consumers. hash(key) % N changes for most keys, so for a few minutes a SKU's old events are still being processed on one partition while its new events start on another. Two processor instances now write on_hand for the same key, and some stores show 4 units when the shelf has 0. Pickup cancellations jump. How a team notices: the "can't find item" rate in the picker app and the reservation 409 rate both spike for the same stores, while consumer lag looks normal. Fix: stop producers, drain the old assignment, replay positions from the event log, and from then on grow capacity by moving to a new topic instead of resizing in place.
