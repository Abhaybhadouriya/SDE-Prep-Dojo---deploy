Back-of-envelope estimation

All inputs are assumptions for practice, not Walmart's real numbers. Say them out loud. Then let the numbers pick the design.

  1. Keys. Assume 5,000 locations, each stocking about 50,000 SKUs on average: 5,000 x 50,000 = 250 million item-location pairs.
  2. State size. About 200 bytes per position row (ids, 4-5 counters, version, timestamps): 250M x 200 B = 50 GB. That fits comfortably in a sharded database or in the state stores of a stream-processing cluster.
  3. Write events per day. Assume 100M till line items + 20M online order lines + 30M receipts, returns, transfers and adjustments = 150M events/day.
  4. Average and peak write rate. 150M / 100,000 s = 1,500 events/s. Big sale mornings (Black Friday, Big Billion Days) can be 10x: plan for 15,000 events/s.
  5. Reads. Assume 50M site/app visits a day, 20 product views each, each view checks about 5 nearby stores: 50M x 20 x 5 = 5 billion lookups/day, about 50,000/s average, and maybe 250,000/s at peak.
  6. Read/write ratio. 50,000 / 1,500 is about 30:1, higher at peak. So reads must be served from a precomputed, cached view, not by recomputing stock.
  7. Kafka volume. 150M events x about 500 B = 75 GB/day; keep 7 days = about 525 GB, x3 replicas = about 1.6 TB on the brokers. Small for Kafka.
  8. Partitions. If one processor instance handles about 500-1,000 events/s including its database writes (an assumption you would load-test), 15,000/s peak needs at least 15-30 parallel consumers. Because changing the partition count later reshuffles keys, start high: 64-128 partitions.

What the numbers decided: the current state is small, the event rate is moderate, the reads are huge. So: an event log for writes, one writer per key for correctness, and a separate read-optimised view with caching for the website. That is CQRS (command query responsibility segregation: separate models for writing and for reading).
