Data model

We keep three things: the event log (truth about what happened), the position per key (current numbers, derived from events), and reservations. Then a read view for the website.

-- Current position, one row per item-location (the "chalkboard")
CREATE TABLE inventory_position (
  item_id        VARCHAR(32),
  location_id    VARCHAR(32),
  on_hand        INT    NOT NULL,          -- owned by the stream processor
  reserved       INT    NOT NULL DEFAULT 0, -- owned by the reservation service
  safety_stock   INT    NOT NULL DEFAULT 0,
  in_transit     INT    NOT NULL DEFAULT 0,
  last_count_at  TIMESTAMPTZ,              -- time of the last physical count
  onhand_version   BIGINT NOT NULL DEFAULT 0, -- bumped only by the stream processor
  reserved_version BIGINT NOT NULL DEFAULT 0, -- bumped only by the reservation service
  updated_at     TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (item_id, location_id)
);

CREATE TABLE reservations (
  reservation_id VARCHAR(32) PRIMARY KEY,
  order_id       VARCHAR(64) NOT NULL,
  item_id        VARCHAR(32), location_id VARCHAR(32), qty INT NOT NULL,
  status         VARCHAR(12) NOT NULL,     -- HELD | COMMITTED | RELEASED | FULFILLED
  expires_at     TIMESTAMPTZ NOT NULL
);

-- Dedupe of incoming events (or keep it inside the processor's state store)
CREATE TABLE processed_events (event_id VARCHAR(64) PRIMARY KEY, processed_at TIMESTAMPTZ);

From your world

This is the split between a link-state database and the routing table. OSPF routers flood LSAs (events). Each router keeps the LSDB and computes its RIB/FIB (a derived view) from it. Nobody edits the FIB by hand; you change it by new LSAs. Our event log is the LSDB; the position table and availability view are derived "FIBs". Where it breaks: OSPF state converges by flooding to everyone; here each key has exactly one writer and other readers get a copy of its result.
