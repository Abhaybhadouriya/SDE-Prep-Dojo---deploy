API design

Two kinds of interface. Stock changes arrive as events on Kafka topics (tills and warehouse systems produce them; they never call a synchronous API, so a slow central system cannot stop a till). Questions and reservations are HTTP/gRPC calls from the website, the order system and store apps.

# Availability (read path, cached, eventually consistent)
GET /v1/availability?items=SKU123,SKU456&locations=store-42,store-57
200 { "results": [
  { "item": "SKU123", "location": "store-42", "status": "IN_STOCK", "available": 12, "as_of": "2026-11-23T10:15:03Z" },
  { "item": "SKU456", "location": "store-42", "status": "LOW",      "available": 2,  "as_of": "2026-11-23T10:15:01Z" } ] }

# Ship-to-address promise: best locations that can fulfil
GET /v1/promise?item=SKU123&qty=1&zip=560103

# Reserve stock for an online order (write path, strongly consistent, idempotent)
POST /v1/reservations
Idempotency-Key: ord-88231-attempt-1
{ "order_id": "ORD-88231", "ttl_seconds": 900,
  "lines": [ { "item": "SKU123", "location": "store-42", "qty": 1 } ] }
201 { "reservation_id": "res_7Q2", "expires_at": "2026-11-23T10:30:03Z" }
409 { "error": "INSUFFICIENT_STOCK", "item": "SKU123", "available": 0 }

POST   /v1/reservations/res_7Q2/commit    # order paid: keep it until the item is picked
DELETE /v1/reservations/res_7Q2           # order cancelled or TTL expired: give stock back

Word check. Idempotent = doing it twice has the same effect as doing it once. Phones and networks retry, so the order system may send the same reserve call two or three times. It sends the same Idempotency-Key each time; the server remembers the key with the first result and simply returns that result again instead of reserving a second unit. Strongly consistent = every reader sees the latest committed number (no stale copy). Eventually consistent = a reader may see a number a few seconds old, which is fine for "In stock" badges.

From your world

An idempotency key is like a TCP retransmit carrying the same sequence number: the receiver sees it has that segment already and ACKs again without delivering the bytes twice. Where this breaks: TCP forgets sequence numbers when the connection closes; our server must remember idempotency keys for a fixed time (say 24 hours), so a retry after that window would reserve again.

A canonical event is the one common shape every source is converted into (Walmart's Confluent post explains that forcing every source team onto one schema was not practical, so a central transformer converts them):

{
  "event_id": "pos-42-20261123-000918-3",
  "type": "SALE",
  "item_id": "SKU123",
  "location_id": "store-42",
  "qty_delta": -1,
  "event_time": "2026-11-23T10:14:59.120Z",
  "source": "pos",
  "source_seq": 918
}

type is one of SALE, RETURN, RECEIPT, TRANSFER_OUT, TRANSFER_IN, ADJUST or COUNT. COUNT events carry qty_absolute ("there are 7 now") instead of qty_delta.
