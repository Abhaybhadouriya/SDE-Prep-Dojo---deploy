Quick quiz

On hand 20, reserved 5, safety stock 3. What does the website show as available?

  1. 15 (on hand minus reserved)
  2. 17 (on hand minus safety)
  3. 12 (minus reserved and safety)
  4. 20 (everything on the shelf)
Available to promise = 20 - 5 - 3 = 12. 15 forgets the safety buffer for theft and miscounts. 17 forgets that 5 units are already promised to online orders. 20 is on hand, which still includes those promised units.

Why does keying by item+location remove the need for locks?

  1. A key's events share one partition, and one member owns it
  2. Kafka takes a row lock in the position DB for each key
  3. The broker blocks a second write to a key until the first acks
  4. All group members share a partition and take turns by key
Order inside a partition plus a single owner per partition gives one writer per key. Kafka never touches your database rows, brokers do not block writes per key, and a partition is never shared by two members of the same group.

The availability cache says 1 unit, but the reserve call returns 409. What is going on?

  1. A bug: the cache TTL is too long and should be zero
  2. A bug: reserve should trust the number in the cache
  3. The network dropped the call, so the client should retry
  4. Normal: browsing may be stale; the conditional update decides
Browsing is eventually consistent by design and the write path is strict, so this is expected. A zero TTL would melt the database at 250k reads/s. Trusting the cache is exactly how you oversell. A 409 is a real answer from the server, not a lost packet, so retrying returns 409 again.

A sale from 13:50 arrives at 14:05. A cycle count at 14:00 set on hand to 7. What should the processor do?

  1. Subtract 1, because every delta must be applied once
  2. Ignore it, because the 14:00 count already includes it
  3. Park it in the DLQ until a person reviews it
The bear left the shelf at 13:50, so the 14:00 count already saw it missing. Subtracting would count the sale twice (6 instead of 7). Nothing is wrong with the event, so a DLQ (dead-letter queue, for events that cannot be processed) is the wrong place; the rule "ignore deltas older than last_count_at" handles it automatically.

Lag grows on one partition only. Will adding more consumer pods fix it?

  1. Yes: new pods split that partition's records between them
  2. No: one member owns a partition; find the hot key or slow pod
  3. Yes: if every pod also raises max.poll.records
  4. No: you must recreate the topic with more partitions first
A partition has exactly one owner in a group, so new pods take other partitions or sit idle. Bigger polls do not help if one key or one slow pod is the cause. Recreating the topic is drastic and reshuffles every key; diagnose first.

Why run the Kafka Streams processor as a StatefulSet with a volume?

  1. After a clean restart it reuses its RocksDB files
  2. Deployments cannot mount any kind of volume
  3. StatefulSet pods get a faster path to brokers
Stable identity plus persistent storage means a cleanly restarted pod restores only the changelog tail. Under exactly_once_v2 a crash still wipes the store and restores it fully, so standby replicas keep failover fast. Deployments can mount volumes, but pods have no stable identity to reclaim their own disk. A StatefulSet does nothing for network speed.

What is a "canonical event"?

  1. An event signed by the source so it cannot be forged
  2. An event kept forever in the data lake for audits
  3. One common shape every source format is turned into
  4. The first event for a key, which later deltas build on
Walmart's post describes a transformation engine that converts many source formats into one common inventory event. Signing, long retention and "first event" are all real ideas, but none of them is what canonical means.
