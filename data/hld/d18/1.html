Requirements

Functional

  1. Topics Producers publish messages (key, value, headers) to a named topic; consumers subscribe to topics.
  2. Ordering Messages with the same key are delivered in the order they were written. (Not global order across the whole topic: that cannot scale, and we will say why.)
  3. Consumer groups Several instances of one service share the work; different services each get every message.
  4. Replay A consumer can rewind to an earlier offset or timestamp and read again.
  5. Retention Keep messages for a configured time or size (for example 7 days), or keep only the latest value per key (compaction).
  6. Delivery guarantee At-least-once by default; exactly-once within the system as an option.

Non-functional

QualityTarget (assumed)
Throughput1 million messages/s in at peak, average message 1 KB (so 1 GB/s in)
Fan-out3 consumer groups read everything (3 GB/s out), plus replication traffic
DurabilityNo acknowledged message lost if any one broker (server) dies
AvailabilityKeep accepting writes with one broker or one availability zone down
LatencyProduce-to-consume in tens of milliseconds at p99 (assumed target)
Retention7 days (Kafka's default log.retention.hours is 168)
Scale outAdd brokers and partitions without downtime

Trap requirement: if the interviewer says "strict global ordering of all messages", push back politely. Global order means one sequence, which means one writer path and one reader at a time: the throughput of one machine. Offer per-key ordering instead and explain the trade-off. This is one of the most common follow-ups.
