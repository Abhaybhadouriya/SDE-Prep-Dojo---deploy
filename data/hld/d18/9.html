Interview: how to drive 45 minutes

  1. 0-5: requirements. Throughput and message size, ordering scope, delivery guarantee, retention and replay, number of consumer groups, durability under failure.
  2. 5-10: estimate. Ingress, replication, egress, storage x RF, the point that disk decides; partitions from consumer throughput.
  3. 10-18: single node. One append-only log per partition, segments + sparse index, offsets, pull API. Why it is fast.
  4. 18-30: distribute. Partitions over brokers, key hashing, leader/followers, ISR, HW, acks + min ISR, controller.
  5. 30-40: consumers and semantics. Groups, offset commits, rebalancing, at-least-once vs exactly-once, retries and DLQ.
  6. 40-45: operate. Failure table, metrics (under-replicated partitions, lag, request latency), retention vs tiered storage, scaling.

Common mistakes: promising global ordering; forgetting where consumer offsets are stored; deleting messages on read and then also promising replay; push delivery with no flow-control story; acks=all without min.insync.replicas; claiming exactly-once covers database writes; saying "add partitions" without mentioning that it remaps keys; no controller (who elects leaders?); never doing the storage math.

Turn your background into an answer. When an interviewer says "you have no web experience", answer with a translation, not an apology (the full script is on the interview framework page). Examples for this design: "I tuned interrupt coalescing on a NIC driver: that is the same latency-for-throughput trade as linger.ms and batch.size." "I debugged ring-buffer overruns between a producer and consumer thread: consumer lag is the same queue depth, and retention is what happens when the ring wraps." "Key hashing to partitions is ECMP flow hashing: per-flow order, spread across links, and resizing the group re-hashes flows." Then go straight back to the design.

60-second answer, said out loud: "I'd model each topic as N partitions, each an append-only log split into segment files with a sparse offset index, so writes are sequential and reads by offset are a binary search plus a short scan. Producers hash the key to a partition, which gives per-key ordering, and send compressed batches to the partition leader. Followers on other brokers in other zones fetch from the leader; the in-sync set defines a high watermark, and with RF 3, acks=all and min ISR 2 no acked write is lost if one broker dies. Consumers pull from the leader up to the high watermark, served from the page cache with zero-copy, and commit one offset per partition per group to an internal compacted topic, so each group replays independently. A Raft controller quorum stores metadata and elects leaders. Retention deletes whole segments by time or size, compaction keeps the latest per key, and tiered storage moves old segments to object storage, because at 7 days and RF 3, disk, not throughput, sizes the cluster."

How does partitioning work, and how would you scale a Kafka-based system?

The producer hashes the key (murmur2 in Kafka) modulo the partition count; same key, same partition, same order. Partitions are the unit of parallelism: a consumer group can use at most one consumer per partition. To scale consumption, add consumers up to the partition count; beyond that, add partitions. But adding partitions changes the key mapping, so ordering for a key is broken at the switch moment. Plan partitions up front from throughput (target / per-consumer rate), and watch per-partition skew from hot keys.

How to answer

Mechanism (hash mod N), consequence (order per key, parallelism = partitions), the trap (adding partitions remaps keys), then how you size it.

Likely follow-ups
  • How do you add partitions safely for an ordered topic? (create a new topic and migrate, or drain then switch)
  • What if one key is 30% of traffic?
How do you make sure related events go to the same partition?

Give them the same message key (for example order ID or user ID), so the default partitioner sends them to the same partition. If "related" spans several IDs, choose the entity whose order matters (the order, not the user) or write a custom partitioner. Keep the partition count stable. With a null key, Kafka spreads records with a sticky partitioner and gives no ordering.

How to answer

One sentence on keys, one on choosing the right key, one on the partition-count caveat.

Likely follow-ups
  • Does retry ever reorder messages within a partition? (not with idempotence and max.in.flight <= 5)
How do you persist messages safely and handle failed ones?

Persistence: RF 3 across zones, min.insync.replicas 2, acks=all, idempotent producer, unclean leader election off. Failed processing: the consumer retries a few times in-process for transient errors, then publishes the message to a delayed retry topic and commits the original offset; after N attempts it goes to a dead-letter topic with error headers, which is alerted on and can be replayed after a fix. Consumers must be idempotent, because at-least-once means duplicates.

How to answer

Split it into two halves: "safe in the broker" and "safe through processing". Interviewers often mean the second.

Likely follow-ups
  • How do you keep order for a key if one of its messages goes to retry?
  • How do you replay the DLQ?
Explain ISR, high watermark and min.insync.replicas.

ISR is the set of replicas caught up with the leader within replica.lag.time.max.ms. The high watermark is the smallest log-end offset in the ISR; records below it are on all in-sync replicas and visible to consumers. With acks=all the leader acks once all ISR members have the record; min.insync.replicas sets the smallest ISR size allowed to accept such writes. RF 3 and min ISR 2 tolerate one broker loss with no data loss and still accept writes.

How to answer

Define each term in one line, then show how they combine in the RF 3 / min ISR 2 example.

Likely follow-ups
  • Why can acks=all with min ISR 1 still lose data?
  • What is unclean leader election?
Why pull instead of push for consumers?

Pull lets each consumer go at its own speed and gives natural backpressure: a slow consumer just fetches less, the broker never buffers per-consumer state. It also enables large batched fetches and replay from any offset. The downside, busy-polling an empty topic, is solved with long polling (fetch.min.bytes, fetch.max.wait.ms).

How to answer

Name backpressure in the first sentence; connect it to TCP flow control if you like.

Likely follow-ups
  • When is push better? (low-latency fan-out to many clients, like notifications)
Is exactly-once really possible?

Within Kafka, yes: the idempotent producer removes retry duplicates, transactions make writes to many partitions plus the consumer's offset commit atomic, and read_committed consumers skip aborted data. That gives exactly-once for read-process-write pipelines inside Kafka. For external side effects (DB, email, payment), Kafka cannot undo them, so you need idempotent sinks: upserts keyed by message ID, idempotency keys, or the outbox pattern.

How to answer

"Yes inside the boundary, no outside it, and here is what you do outside." That structure is the whole answer.

Likely follow-ups
  • What is a zombie producer and how is it fenced?
A consumer group has 10 partitions and 15 consumers. What happens? And with 10 partitions and 3 consumers?

15 consumers: 10 get one partition each, 5 are idle standbys that take over during a rebalance if someone leaves. 3 consumers: each gets 3 or 4 partitions. Throughput scales with consumers only up to the partition count. Share groups (Kafka 4.2+) remove this limit for queue-style work, at the cost of per-partition ordering.

How to answer

Give both cases with numbers, then mention share groups as the modern escape hatch.

Likely follow-ups
  • How does a rebalance affect processing, and how do you reduce its impact?
How does a consumer find message offset 368,800 quickly?

Segment files are named by their base offset, so a binary search over segment names finds the file. Its sparse .index maps some offsets to byte positions; a binary search there finds the nearest entry at or below 368,800, and the broker scans forward a few KB. Replay by time uses the .timeindex to turn a timestamp into an offset first.

How to answer

Draw the three-level lookup; mention why the index is sparse (small enough to stay in memory, mmapped).

Likely follow-ups
  • Why not a dense index? (size: one entry per record would be huge and rarely needed)
Retention is 7 days and the cluster is out of disk. What are your options?

Short term: lower retention on the biggest topics (with owners' agreement), check for a topic someone forgot to set retention or compaction on, enable or raise compression. Medium term: tiered storage, keeping only a day locally and the rest in object storage. Long term: add brokers and reassign partitions (Cruise Control). Also confirm the math: retention x ingress x RF; disk is usually what decides size.

How to answer

Triage now, fix structurally later, show the formula.

Likely follow-ups
  • What are the limits of tiered storage? (compacted topics cannot be tiered)
What happens if the controller quorum goes down?

Brokers keep serving reads and writes for partitions whose leaders are alive; the data plane does not depend on the controller per request. What stops: leader elections (so a broker failure now makes its partitions unavailable), topic creation, config changes and ISR updates. With 3 controllers the quorum survives one loss; with 5, two. Run controllers on separate machines and zones.

How to answer

Control plane vs data plane, then what you lose, then quorum math (n-1)/2.

Likely follow-ups
  • Why did Kafka move from ZooKeeper to KRaft?
Design a "notify me when my request is provisioned" feature on top of your queue.

The provisioning service writes a request.provisioned event (key = request ID) to a topic, using the outbox pattern so the DB state change and the event cannot disagree. A notification consumer group reads it, looks up the user's channels, and sends email or push with an idempotency key (the event ID) so retries do not double-notify. Failures go to retry topics and a DLQ. Lag on the notification group is the "time to notify" SLO metric.

How to answer

Reported as a Walmart follow-up; show you can use the queue you just designed, end to end.

Likely follow-ups
  • How do you avoid notifying twice after a consumer crash?

Scenario: consumer lag keeps growing during a sale

The order-processing group's lag grows from 0 to 2 million in an hour. Brokers look healthy.

Weak answer: "Add more partitions."

Strong answer: lag growing with healthy brokers means consumers are slower than producers. Check per-partition lag: if it is one partition, it is a hot key or a poison message (a stuck offset). If it is all partitions, check processing time per record (a slow database call), rebalance churn, and whether consumers < partitions (then add consumers, which is instant). Adding partitions is last, because it remaps keys. Short-term relief: batch DB writes, move slow side effects out of the critical path.

Likely follow-ups
  • Lag in messages or in seconds: which do you alert on?

Scenario: messages lost after a broker failure

A broker's disk failed; afterwards a team reports missing orders that their producer had received acks for.

Weak answer: "Kafka is not reliable."

Strong answer: check the configs. Likely acks=1 (the leader acked before followers copied), or min.insync.replicas=1 with a shrunken ISR, or unclean.leader.election.enable=true, or RF 1. Fix: RF 3 across zones, min ISR 2, acks=all, idempotence, unclean election off, and alert on under-min-ISR partitions. Recover the missing data from the source system or outbox.

Likely follow-ups
  • What does that configuration cost you in availability?

Scenario: every deploy causes a 30-second processing pause

On Kubernetes, each rolling update of a 20-pod consumer group stalls all processing several times.

Weak answer: "Deploy at night."

Strong answer: each pod restart triggers a rebalance, and with eager rebalancing every consumer gives up every partition. Use static membership (group.instance.id set to the pod name, with a session timeout longer than a restart), cooperative or KIP-848 incremental rebalancing (group.protocol=consumer), and close consumers cleanly on SIGTERM so partitions are handed over quickly.

Likely follow-ups
  • Why does a StatefulSet help with static membership? (stable pod names)
