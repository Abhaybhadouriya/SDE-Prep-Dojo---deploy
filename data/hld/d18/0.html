The story

Explain like I'm 5

Picture a special class notebook. Anyone may write in it, but only on the next empty line. Nobody may rub anything out or write between lines. Each line has a number: line 0, line 1, line 2.

Kids who want to read it each keep their own bookmark. Asha has read up to line 40, Ravi only to line 12. Ravi being slow does not bother Asha at all. If Ravi spills juice on his bookmark, he can start again from any line he likes, because nothing was ever rubbed out. When the notebook gets very thick, the teacher tears out the oldest pages (only whole pages, and only after a week). To be safe, two helper kids copy every new line into their own notebooks, so if the main notebook falls in a puddle, a helper's copy takes over.

That notebook is a log: an ordered, append-only sequence of records. A message queue lets one program (a producer) hand messages to other programs (consumers) without both being online at the same moment. Classic queues (RabbitMQ, SQS) delete a message once a consumer acknowledges it. A log-based system like Kafka keeps messages for a retention period and lets each reader track its own position (the offset, our bookmark).

Learner questions answered right away:

  • "Is Kafka a queue? If a consumer reads a message, is it deleted?" No, reading does not delete. Kafka is a log; messages are removed only by retention (time or size) or compaction. Many independent groups can read the same data at their own pace. Since Kafka 4.2 (release notes), share groups add real queue-style behaviour on top (per-message acknowledgement), covered in deep dive 6.
  • "If Kafka keeps messages on disk, how is it different from a database?" A database is built for updating and querying records by value. Kafka only appends and reads in order by position. It has no indexes on content and no updates in place, which is exactly why it can be so fast and so simple to replicate.
