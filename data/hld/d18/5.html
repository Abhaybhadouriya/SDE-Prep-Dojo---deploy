Architecture

Whiteboard version (six boxes): producers, a cluster of brokers holding partition replicas, a small controller quorum holding metadata, and consumer groups. Here is one message's life with RF 3, acks=all and min.insync.replicas=2.

  1. Metadata. The producer asks any broker for metadata and caches it: which broker leads each partition of orders. The source of that answer is the controller quorum's metadata log, which every broker replicates.
  2. Partition and batch. The producer hashes the key (murmur2) modulo the partition count, so every message for user42 lands in partition 2 in order. It collects records into a per-partition batch until batch.size is full or linger.ms (default 5 ms since Kafka 4.0, changed from 0 by KIP-1030; see the producer config docs) passes, compresses it, and sends it to the leader of partition 2.
  3. Leader appends, followers fetch. Broker 1 appends the batch to the active segment (into the OS page cache; no fsync per message). Followers on brokers 2 and 3 are already long-polling the leader with Fetch requests, exactly like consumers, and append the same bytes.
  4. Commit point. When every in-sync replica (ISR) has the batch, the leader advances the high watermark (HW), the highest offset known to be on all in-sync replicas, and acknowledges the producer (acks=all). If fewer than min.insync.replicas are in sync, the write is refused with NOT_ENOUGH_REPLICAS instead.
  5. Consume. A consumer in group billing owns partition 2 and pulls from offset 100. It only sees data below the HW, so it never reads a message that could still vanish. Bytes go from page cache to socket with sendfile() (zero-copy) when TLS is off.
  6. Commit offset. After processing, the consumer commits offset 101 ("next to read") to __consumer_offsets. Process first, commit second = at-least-once.
  7. Failover. Broker 1 stops heartbeating. The active controller picks a new leader from the ISR (broker 2), writes it to the metadata log, and brokers and clients learn the change. Producers and consumers get NOT_LEADER errors, refresh metadata and continue. No acknowledged message is lost, because broker 2 had everything below the HW.
