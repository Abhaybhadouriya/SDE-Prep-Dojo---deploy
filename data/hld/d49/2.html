Back-of-envelope estimation

We anchor on numbers Flipkart published, and label our own assumptions. Method from Back-of-Envelope Estimation: 1 day is about 86,400 s, round freely, and show your work.

~90MSKUs (Flipkart 2016)
~160Mlistings
~40K/speak searches
~50K/sreal-time updates
  1. Search QPS from users (assumption check) Say 50M daily active users run 8 searches each: 400M searches/day. 400M / 86,400 s is about 4,600/s average. Sale days spike about 10x, so ~46K/s peak. That matches Flipkart's reported ~40K/s, so our assumptions are sane.
  2. QPS reaching the search engine Flipkart saw ~40K/s at the service but ~10K/s at Solr. So about 75% is absorbed by result caches (popular queries like "iphone" repeat a lot). Design the engine for ~10-15K/s.
  3. Index size Assume ~2 KB of indexable text per SKU and ~0.5 KB per listing (our assumption). 90M x 2 KB = 180 GB, plus 160M x 0.5 KB = 80 GB, so ~260 GB raw. An inverted index plus doc values (a column-wise copy of each field, stored for sorting, filtering and facet counting, because a word-to-documents index cannot answer "what is the price of doc 42" quickly) is in the same order, so plan for ~300 GB primary index.
  4. Shard count Elastic recommends shards of roughly 10-50 GB. 300 GB / 30 GB is about 10 primary shards.
  5. Replicas Replicas add read throughput. If one full copy of the index (all 10 shards) serves ~1,000 QPS on your hardware (assumption, you must load-test), then 12K QPS needs 12 copies, plus ~30% headroom: ~16 replica sets. Each copy is 300 GB, so ~5 TB of SSD in the search tier.
  6. Update stream Flipkart Sherlock: ~10K updates/s average, peak ~30K/s in Big Billion Days 2017 (4.5 billion updates in the sale). At ~200 bytes per change event, 30K/s x 200 B = 6 MB/s. Tiny for Kafka. The hard part is not bandwidth; it is the cost of applying updates to an inverted index.
  7. Catalog store Full product detail ~5 KB x 90M = ~450 GB of structured data. Fits a sharded SQL or document store easily.
  8. Images 8 images x 200 KB x 90M = ~144 TB. Goes to object storage behind a CDN, never in the database (see Handling Large Blobs).
  9. Reviews "Hundreds of millions" of reviews (Flipkart). At 300M x 1 KB = 300 GB of text. Reads in the hundreds of thousands per second, writes in the hundreds.
  10. Egress for search 20 results x ~1 KB of JSON = 20 KB per response. 40K/s x 20 KB = 800 MB/s, about 6.4 Gbps, excluding images served by the CDN.

From your world

The read path is like a router's fast path vs slow path. The forwarding table (search index) is a precomputed, optimised structure for lookups. The routing protocol (catalog + pipeline) updates it asynchronously. You never run the routing protocol per packet, and you never hit the catalog database per search.
