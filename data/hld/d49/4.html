Data model and storage choice

The catch: a phone has ram_gb, a shirt has sleeve_length, a fridge has capacity_litres. There are thousands of categories (Flipkart reported ~50 main and ~5,000 sub-categories). You cannot add a column per attribute.

Option for attributesHowGoodBad
Column per attributewide tablesimple SQLthousands of mostly-null columns; schema change per new category
EAV (entity-attribute-value)rows of (product_id, attr, value)fully flexibleevery read is a pivot/join; types are weak; slow at scale
JSON column + category schemaPostgres JSONB / MySQL JSON, schema registry validatesflexible, typed by registry, one-row reads, still transactionalad-hoc filtering on JSON is weak in OLTP (fine, search does that)
Document DBMongoDB, DynamoDBnatural fit, easy sharding by product_idmulti-item transactions are limited; joins to listings move to app

Choice: a relational store (sharded MySQL/Postgres, or a document store) for the catalog, keyed by product_id, with a JSON attribute bag validated by a category schema registry. Filtering and full text are not the catalog's job; they belong to the search index. The schema registry also tells the indexer which attributes are facets, which are searchable text and which are only for display. Read more in Data Modeling & Indexing and Choosing Storage.

Tip: keep fast-changing data (price, stock) out of the product row. Flipkart describes product and listing attributes as either "mostly static" or "dynamic"; the dynamic ones are owned by separate services (pricing, availability, offers) and flow separately.
