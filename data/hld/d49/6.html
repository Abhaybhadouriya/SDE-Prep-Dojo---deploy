Deep dives

1. Keeping search fresh without melting the index

An inverted index is built from immutable segments. Lucene (under Elasticsearch and Solr) cannot change one field in place: an update is a delete + re-insert of the whole document, and the old copy is removed only when segments merge. Elasticsearch makes new writes searchable at each refresh, by default every 1 second (for indices searched in the last 30 s). So a price that changes 50 times a day on 160M listings means a storm of whole-document rewrites, merges and cache invalidations.

Flipkart hit this exactly. Their 2016 talk lists the costs: a block-join update rewrites the product plus all its listings; every delete+add is streamed to all replicas; soft commits create many tiny segments and blow away filter caches. Their fix was to split the data by how fast it changes:

  • Fast lane details (Flipkart): every serving node runs a Kafka consumer that updates its in-memory NRT store. Because the store is not persisted, a starting node bootstraps from Redis and then resumes Kafka from a checkpointed offset. They reported ~50K real-time updates/s across ~150 signals and about 2x fewer out-of-stock products shown.
  • Lookup speed matters: their naive per-document lookup took ~10 s for ~1M lookups; mapping Lucene doc ids to compact NRT ids cut it to ~100 ms. Matches can be ~1M documents at p99, so per-match cost is everything.
  • Filtering choice: a post-filter checks live values per result (exact but slower) vs cached bitsets per filter value like Availability:T (fast but briefly inconsistent). Offer both and pick per use.
  • Ordering and idempotency: Sherlock processes updates idempotently and, where order matters, calls back the source for the latest value. Our version: every event carries a version; apply only if newer.

Careful: never trust the search index for the final stock decision. The index may lag by seconds. The product page fetches offers live, and checkout reserves inventory against the inventory service (d11, d09).

2. Scatter-gather, ranking and facets

A query goes to every shard (documents are sharded by product id, not by word, so each shard has its own small inverted index). Each shard returns its top K; the coordinator merges. Costs grow with shard count, so keep shards in the 10-50 GB band rather than making hundreds of tiny ones.

  • Two-phase ranking: phase 1 is cheap text relevance (BM25) plus static boosts, run on every match. Phase 2 is an ML model on the top few hundred, using features like click-through rate, conversion, price competitiveness and rating. This is how you afford ML on 40K queries/s.
  • Facets are counts per attribute value across all matches. Engines compute them from doc values, a column-oriented per-field store (Hello Interview's ES deep dive explains why columnar beats rows for this). The category schema registry decides which attributes are facetable, so you do not facet on free text.
  • Facets with fresh data: Flipkart wrote a custom facet component so counts like "in stock only" used the NRT store.
  • Pagination: deep page 500 forces every shard to return 10,000 hits. Cap depth (nobody reads page 500) and use cursors ("search after" the last sort key).

3. Ratings and reviews: CQRS for a 1000:1 read ratio

Flipkart's RnR team describes the write flow at a few hundred RPS and reads at a few hundred thousand, with read latency needing ~10 ms vs ~300 ms for writes. That ratio screams CQRS (command query responsibility segregation): one model for writes, other models built for reads.

  • Rating summary is a tiny per-product row: count, sum, and a 5-bucket histogram. Each approved review is an event that increments it. Average = sum / count, computed on read. Use the event's review id to make the increment idempotent (store "applied up to" per product, or a set of applied ids for recent events). For a viral product, batch increments in the stream job (see Distributed Counter).
  • Do not rank by raw average: a 5.0 from 2 reviews should not beat 4.6 from 20,000. Use a Bayesian average: (C*m + sum) / (C + count) where m is the category mean and C a prior weight.
  • Sort and filter reviews (most helpful, newest, by aspect like "battery"): Flipkart first used Redis sorted sets per (product, sort order); this grew to about half a terabyte. They then replaced 36-byte string UUID review ids with a per-product integer review number (~2 bytes with variable-length encoding, a 94% reduction), de-duplicated translated text, and ended with a working set under 100 GB that fit an in-process LFU cache (Caffeine) with over 95% hit rate at peak.
  • Only verified buyers can review: the write API checks the orderId against orders; one review per (user, product) via a unique key, which also makes retries idempotent.

4. Flexible schema evolution

When the "mobiles" category adds refresh_rate_hz, you bump the category schema version. Old products are valid (field optional). The indexer reads the schema registry to map the new attribute into a typed search field and, if it is a facet, a doc-values field. Adding a new field in Elasticsearch is cheap; changing a field's type is not, so you reindex into a new index and swap an alias (blue/green indexing). Plan a full reindex path from the start: Flipkart lists "a robust mechanism to completely refresh/reconcile data" as a key focus area, because streaming pipelines drift.

5. Sale-day traffic

  • Result cache on normalised query + filters, TTL of seconds to a minute; stale stock is fixed by the NRT layer and live offer checks.
  • Product page cache for hot products, with request coalescing so 100K people opening one phone page cause one backend fetch (Scaling Reads).
  • Graceful degradation: under overload, drop the ML re-rank or expensive facets before dropping searches.
  • Pre-scale search replicas before Big Billion Days; replicas are the throughput lever.
