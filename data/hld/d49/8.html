What this design does well
  • Reads never touch the write DB
  • Price/stock freshness in seconds
  • Search tier scales by adding replicas
  • Pipeline can be replayed from Kafka
Where it hurts
  • Many moving parts (CDC, Kafka, indexer, snapshot store, NRT bootstrap)
  • Eventual consistency must be explained to product teams
  • Drift between truth and index needs periodic reconciliation

Failure modes

  • Indexer lag grows (consumer lag on Kafka): results show stale prices. Alert on lag in seconds, not messages; auto-scale indexers up to the partition count; prioritise stock changes over text changes (Flipkart lists "priority updates" as a focus area).
  • Search node restart: in-memory NRT store is empty. Bootstrap from a snapshot (Redis/KV or compacted topic), then replay from a checkpointed offset. Flipkart ran Redis with multiple replicas because bootstraps during rolling restarts spike reads.
  • Out-of-order events: version checks; drop older versions.
  • Bad deploy of ranking model: keep last good model, A/B ramp, fall back to phase-1 ranking.
  • Mapping explosion: a seller sends 10,000 random attribute names. The schema registry rejects unknown attributes, so the index mapping cannot explode.
