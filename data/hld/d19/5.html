Architecture: follow one log line

Click Next or Play to follow a single line, charge timeout order_id=42, from the app to the engineer's screen.

  1. App prints. The payments container writes one JSON line to stdout. The container runtime (containerd via the CRI) saves it to a file under /var/log/pods/ on the node, with a timestamp and stream name. The app never talks to the log system.
  2. Agent tails. Fluent Bit runs as a DaemonSet (one pod per node). It tails the files, remembers its read position in a small database file (like a consumer offset), asks the Kubernetes API for pod labels and adds namespace, app, pod. It batches lines and compresses them.
  3. Buffer. The agent produces batches to the Kafka topic logs.raw with acks=all. Kafka keeps 3 days on disk, replicated 3 times. Now the line is durable even if every downstream system is down. The agent sets the record key to tenant + app + a small hash of the pod name (see the Fluent Bit config below), so one pod's lines stay in order inside one partition, and a big app still spreads over a few partitions.
  4. Process. A consumer group of processors (Vector, Logstash, Flink or a small Go service) reads in parallel - one consumer per partition at most. They parse JSON or regex formats, drop or mask secrets/PII, drop noisy debug lines by rule, and route audit logs to a separate topic. Lines that cannot be parsed go to a dead-letter topic (DLQ, the punt path) instead of blocking the partition.
  5. Index. A writer tier inserts big batches into the hot store, partitioned by time (and tenant). Offsets are committed to Kafka only after the store accepts the batch: at-least-once, so a crash means a re-insert, never a loss.
  6. Tier down. After 7 days, data moves to object storage: Elasticsearch ILM (index lifecycle management: rules that move old indexes to cheaper nodes and finally delete them) moves indexes to warm/cold nodes or searchable snapshots; Loki already stores chunks in S3; ClickHouse can move old parts to an S3 disk with a TTL rule. After a year, lifecycle rules delete it.
  7. Query and alert. The engineer types {app="payments"} |= "timeout" for the last hour. The query layer picks only matching streams and time partitions, fans out to many workers in parallel, merges and returns. Alert rules run the same kind of query every minute.
  8. Failure: the store is slow. Processors slow down, Kafka consumer lag grows, but nothing is lost and apps are untouched. When the store recovers, processors catch up. This is why the buffer exists.

The whiteboard version (draw this in 30 seconds): Apps → Agent (DaemonSet) → Kafka → Processors → Store (hot) → Object storage (cold), plus Query service → UI / Alerts on top of the store.

From your world

The agent's "position file" is exactly a ring-buffer read pointer that survives a restart. Kafka consumer lag is queue depth: if the drain (processors + store) is slower than the fill (agents), depth grows. Watching lag is like watching an interface's output-queue occupancy before tail drops begin - except Kafka's "queue" is days of disk, so we have a long time before anything drops. Where this breaks: a ring buffer's read index points into memory that the writer will overwrite; the agent's position points into a file that log rotation may delete. If the agent is down longer than the node keeps rotated files (by default the kubelet keeps 5 files of 10 MiB per container), the lines are gone before Kafka ever sees them. That is why agent lag is alerted on separately from Kafka lag.
