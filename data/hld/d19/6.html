Deep dives

Stop here for SDE-1: the architecture above plus deep dive 1 (backpressure) and deep dive 2 (choosing the store) is a passing SDE-1 answer. Deep dive 3 (cardinality) is expected at SDE-2. Deep dives 4-5 (redaction, multi-tenancy, tiers) are good to know and score extra points.

1. Backpressure: who slows down whom?

Backpressure means "a slow stage pushes back on the stage before it so it does not get flooded". Our chain has four places where this happens:

  • App to agent: the app writes to a file, so it never blocks on the network. Danger: if the agent falls far behind, the runtime rotates the file (kubelet's container log rotation) and unread lines are gone. Watch the agent's lag.
  • Agent to Kafka: Fluent Bit has a memory buffer limit (Mem_Buf_Limit) and can spill to a filesystem buffer. When Kafka is unreachable it pauses tailing instead of crashing the node.
  • Kafka to processors: consumers pull. If they slow down, lag grows. With 3 days of retention you have 3 days to fix it - but alert on lag long before that.
  • Processors to store: the writer must respect the store's 429/rejection responses with retry + exponential backoff and jitter, never a tight retry loop.

Without Kafka (agent writes straight to Elasticsearch), a slow cluster makes thousands of agents retry at once. Their buffers fill, they drop lines, and the retry storm makes the cluster even slower. This is the classic reason teams add a buffer.

2. Choosing the store (and saying why)

Use the trade-off sentence pattern: "I pick X because A; the cost is B; if C happens I switch to Y."

  • "I pick Loki-style label indexing with chunks in S3 because most debugging queries are 'this service, this time window, contains X', and storage cost is our biggest risk at ~43 TB/day. The cost is slower needle-in-haystack searches across all services. If security needs fast any-field search, I add a smaller Elasticsearch cluster just for audit logs."
  • "I pick Elasticsearch/OpenSearch when the main use is free-text search over a moderate volume and the budget allows it. I would keep shards in the 10-50 GB range, which is Elastic's own guidance, and use index lifecycle management to move old indexes to cheaper nodes."
  • "I pick ClickHouse when logs are structured (HTTP access logs, events) and people ask counting questions. Cloudflare's write-up is the reference for this."

3. Cardinality: the bug that kills log and metric systems

In Loki, every unique combination of label values is a separate stream, with its own chunks. If you add user_id as a label with 10 million users, you just asked for up to 10 million tiny streams: the index explodes, chunks are almost empty, and ingestion slows down. Grafana's own label guide says to keep labels few and low-cardinality, and to search high-cardinality values with filter expressions instead.

Elasticsearch has the cousin of this problem: mapping explosion. If apps log arbitrary JSON keys ({"user_123_cart": ...}), every new key becomes a new field in the index mapping, and the cluster state grows until the master node struggles. Fixes: a fixed schema (ECS - Elastic Common Schema), dynamic: false for unknown fields, or a field limit.

# Good: few labels, search the ID as text (LogQL)
{namespace="checkout", app="payments", level="error"} |= "order_id=42"

# Parse JSON on the fly, then filter by a field (no index needed)
{app="payments"} | json | latency_ms > 500

# Errors per app per minute, for a dashboard or alert
sum by (app) (count_over_time({namespace="checkout", level="error"}[1m]))

Interviewers love this line: "Labels are for where the log came from; content is for what happened. A trace ID or order ID belongs in the line, never in the index labels."

4. Parsing, multiline and PII redaction

  • Structured logs first. Ask teams to log JSON with standard field names. Parsing JSON is cheap; parsing free text with regex (Logstash "grok") is CPU-heavy and fragile.
  • Multiline. A Java stack trace is 40 lines that belong to one event. The agent must join them (Fluent Bit multiline parsers for docker/cri/java), or each line becomes a meaningless separate record.
  • PII and secrets. Redact at the earliest point you control (agent or first processor): mask card numbers, emails, tokens. Once a secret is in an index with replicas, snapshots and backups, deleting it everywhere is very hard.
  • Sampling and drop rules. Keep 100% of errors and audit logs; sample or drop chatty debug/health-check lines. Cloudflare's write-up describes keeping extra sampled tables (10%, 1%, 0.1%) so dashboards stay fast.

5. Multi-tenancy, hot partitions and retention tiers

  • Per-tenant limits at the gateway/distributor: ingest MB/s, lines/s, max label count. A team that suddenly logs 10x gets 429s, not the whole company.
  • Hot partitions in Kafka: if the key is just app, one very noisy app lands on one partition. Use tenant + app + (hash of pod mod N) as the key so one app spreads across N partitions while lines from one pod stay ordered.
  • Tiering: hot (SSD, replicas, 7 days) → warm (fewer replicas, HDD or searchable snapshots, 30 days) → cold (object storage, 1 year) → delete. Kafka itself can also offload old segments to object storage with tiered storage (KIP-405), which makes long replay windows cheap.

6. Kibana / OpenSearch Dashboards: the screen on-call engineers actually open

The pipeline is useless if nobody can read it at 3 a.m. On top of an Elasticsearch cluster the UI is Kibana; on top of OpenSearch it is OpenSearch Dashboards, a fork of Kibana 7.10.2 made when Elastic changed its licence in 2021 (the full story is in Choosing Storage). The two still share the same four building blocks:

  1. Index pattern / data view. A saved glob such as logs-* that says which indices to query, plus which field is the time (@timestamp). Daily indices (logs-2026.11.22, logs-2026.11.23) all match one pattern, so the time picker can search across them. Kibana renamed index patterns to data views in 8.0; OpenSearch Dashboards still calls them index patterns.
  2. Discover. The free-form search screen: pick a time range, type a query, see matching log lines with a field list and a hit histogram. This is where you hunt for the needle (one order ID, one trace ID).
  3. Saved search. A Discover query with its filters and chosen columns, saved by name ("checkout 5xx, last 15 min"). It can be dropped into a dashboard as a live log table.
  4. Visualizations and dashboards. Charts built from aggregations (error rate per service, top failing endpoints, p99 latency from access logs), arranged on a dashboard that shares one time picker and one filter bar.

Many companies run both: Grafana is the first screen an on-call engineer opens (metrics and alerts), and a link on the panel jumps into Kibana Discover with the same service and time range to read the actual lines.

  1. An alert fires from metrics: checkout 5xx rate is above 2%.
  2. The dashboard shows when it started and which endpoint; the time picker is set to that window.
  3. A drill-down link opens Discover with service.name : "checkout" and http.response.status_code >= 500 over the same 15 minutes.
  4. One log line has the trace ID; filtering on it shows the whole request across services (or jumps to the tracing UI).
  5. Root cause found; the saved search "checkout 5xx" is added to the dashboard so next time it is one click.
# Kibana 8.x: create a data view for all daily log indices
curl -s -X POST "$KIBANA_URL/api/data_views/data_view" \
  -H "kbn-xsrf: true" -H "Content-Type: application/json" -u "$KIBANA_USER" \
  -d '{"data_view": {"title": "logs-*", "name": "All logs", "timeFieldName": "@timestamp"}}'

# OpenSearch Dashboards: the same thing is a saved object of type index-pattern
curl -s -X POST "$OSD_URL/api/saved_objects/index-pattern" \
  -H "osd-xsrf: true" -H "Content-Type: application/json" -u "$OSD_USER" \
  -d '{"attributes": {"title": "logs-*", "timeFieldName": "@timestamp"}}'

From your world

Discover is Wireshark's display filter run over stored captures: you narrow by time window, then by fields (ip.src == ... there, service.name : ... here), then open one frame. An index pattern like logs-* is the glob you would use over rotated capture files (capture-*.pcap), and a dashboard is your interface-counter graphs (the MRTG/SNMP view) that tell you when to open the capture at all.

Gotchas: a dashboard with 20 panels over "last 30 days" fires 20 heavy aggregations at the cluster every refresh, so set sensible default time ranges and auto-refresh intervals; an index pattern without a time field cannot use the time picker; field type conflicts across daily indices (status is a number in one index and text in another) show up as "conflict" fields you cannot aggregate, which is another reason for a fixed schema such as ECS; and Dashboards saved objects should be exported and kept in Git like code.
