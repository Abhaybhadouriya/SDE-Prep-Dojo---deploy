Back-of-envelope estimation

These are assumptions for the interview, not facts about any company. The point is the method: write each step on the board so the interviewer can follow and correct you. (Method refresher: Back-of-Envelope Estimation.)

  1. Lines per second. 20,000 pods x 50 lines/s average = 1,000,000 lines/s. Peak (deploys, incidents) = 3x = 3M lines/s.
  2. Bytes per second. A log line with its metadata (timestamp, pod, namespace, level) is about 500 bytes. 1M x 500 B = 500 MB/s raw, 1.5 GB/s at peak.
  3. Bytes per day. 500 MB/s x 86,400 s ≈ 43 TB/day raw (rounding the seconds up to 100,000 gives ~50 TB, so plan with 40-50 TB).
  4. Compression. Logs are very repetitive. A rule of thumb is 5-10x with zstd/lz4 on batches; we plan with 5x to be safe. So ~9 TB/day compressed.
  5. Kafka buffer. Keep 3 days for replay: 9 TB x 3 days = 27 TB, times replication factor 3 = ~81 TB of broker disk. Partitions: if one partition comfortably handles ~10 MB/s (rule of thumb, measure yours) and compressed peak is 1.5 GB/s / 5 = 300 MB/s, we need ~30; round up to 64 partitions for headroom and consumer parallelism.
  6. Hot store (7 days). A full-text index adds a lot on top of the compressed data. If the store needs ~1x of raw size including index and one replica (planning number), 7 days x 43 TB ≈ 300 TB. With a labels-only index (Loki style) and compressed chunks on object storage: 7 x 9 TB ≈ 63 TB in S3, plus a small index.
  7. Cold (1 year). 9 TB x 365 ≈ 3.3 PB compressed in object storage. This is why cold data must go to the cheapest tier.
  8. Queries. 1,000 engineers, but only ~50 queries/s at peak (incident + dashboards). Reads are rare and heavy; writes are constant and huge. Write-heavy system.
