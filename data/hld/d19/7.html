Where Kafka, Kubernetes and Docker fit

Docker: where the log line physically lives

With plain Docker, the default json-file logging driver writes each line as JSON to /var/lib/docker/containers/<id>/<id>-json.log. On Kubernetes with containerd, the CRI writes a simple text format under /var/log/pods/, with symlinks in /var/log/containers/. Either way: a file on the node. That is why the agent runs on the node. (Basics: Running & managing containers.)

$ docker logs --tail 2 web

Kubernetes: the agent as a DaemonSet

A DaemonSet runs exactly one copy of a pod on every node - like a process that must run on every line card. New node joins, it gets an agent automatically. The agent mounts the node's log directory read-only.

From your world

The dead-letter topic is the punt path. A line card forwards normal packets in hardware; anything it cannot handle (options, TTL expiry, unknown protocol) is punted to the route processor instead of stalling the forwarding pipeline. Our processors parse normal lines at full speed and punt the strange ones to logs.dlq, where a slower job or a human looks at them, and a replay sends them back once the parser is fixed. Where this breaks: a router rate-limits the punt path (CoPP) and drops excess; we must not drop, so the DLQ needs its own retention, size alerts and an owner, or it silently fills for weeks.

[SERVICE]
    Flush             1
    storage.path      /var/fluent-bit/state/buffer

[INPUT]
    Name              tail
    Path              /var/log/containers/*.log
    multiline.parser  docker, cri
    Tag               kube.*
    DB                /var/fluent-bit/state/tail.db
    Mem_Buf_Limit     50MB
    storage.type      filesystem
    Skip_Long_Lines   On

[FILTER]
    Name              kubernetes
    Match             kube.*
    Merge_Log         On
    Keep_Log          Off

# build the Kafka key: tenant|app|bucket(pod), so one pod's lines keep their order
[FILTER]
    Name              lua
    Match             kube.*
    script            /fluent-bit/etc/key.lua
    call              add_key

[OUTPUT]
    Name              kafka
    Match             kube.*
    Brokers           kafka-0.kafka:9092,kafka-1.kafka:9092,kafka-2.kafka:9092
    Topics            logs.raw
    Format            json
    Message_Key_Field kafka_key
    rdkafka.compression.codec  lz4
    rdkafka.request.required.acks  -1
-- key.lua: called for every record by the lua filter above
function add_key(tag, ts, record)
  local k = record["kubernetes"] or {}
  local labels = k["labels"] or {}
  local tenant = k["namespace_name"] or "none"
  local app = labels["app"] or k["container_name"] or "none"
  local pod = k["pod_name"] or ""
  local h = 0
  for i = 1, #pod do h = (h * 31 + pod:byte(i)) % 8 end   -- 8 buckets per app
  record["kafka_key"] = tenant .. "|" .. app .. "|" .. h
  return 2, ts, record                                    -- 2 = record changed, keep timestamp
end

Without Message_Key_Field the agent would send records with no key, and the Kafka client would spread them over partitions (sticky batches, then the next partition), so per-pod order would be lost and you could only sort by timestamp at query time.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels: { app: fluent-bit }
  template:
    metadata:
      labels: { app: fluent-bit }
    spec:
      serviceAccountName: fluent-bit        # needs RBAC to read pod metadata
      tolerations:
        - operator: Exists                  # run on every node, even tainted ones
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:5.1.5        # pin a current release; check config keys when changing majors
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { memory: 256Mi }
          volumeMounts:
            - { name: varlog, mountPath: /var/log, readOnly: true }
            - { name: state,  mountPath: /var/fluent-bit/state }
      volumes:
        - name: varlog
          hostPath: { path: /var/log }
        - name: state
          hostPath: { path: /var/lib/fluent-bit, type: DirectoryOrCreate }

The rest of the platform (processors, Loki/Elasticsearch, Grafana) runs as Deployments and StatefulSets. Processors scale with the HPA on Kafka consumer lag (via KEDA or a custom metric), but never beyond the partition count. For K8s-side debugging tips see Observability & Troubleshooting.

Kafka: the shock absorber

$ kafka-topics.sh --bootstrap-server localhost:9092 --create --topic logs.raw \
    --partitions 64 --replication-factor 3 \
    --config retention.ms=259200000 \
    --config compression.type=lz4 \
    --config min.insync.replicas=2
Created topic logs.raw.

$ kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group log-indexer
GROUP        TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG      CONSUMER-ID
log-indexer  logs.raw  0          88412001        88412310        309      indexer-5f..
log-indexer  logs.raw  1          87990120        88601554        611434   indexer-7a..

Partition 1 has a lag of 611k lines while partition 0 is nearly caught up: classic sign of a hot partition or one slow consumer. Kafka gives us: durability (RF 3, min.insync.replicas=2), replay (reprocess 3 days after fixing a parser bug), fan-out (the security team's SIEM reads the same topic with its own consumer group), and decoupling (swap Elasticsearch for Loki without touching agents).
