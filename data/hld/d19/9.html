Turn your background into an answer. Logging is your world, so say so (full script on the interview framework page): "I ran syslog relays for a fleet of routers: this is the same pipeline with a durable buffer instead of UDP." "I tuned interrupt coalescing on a NIC driver: batching in the agent and linger.ms in Kafka is the same latency-for-throughput trade." "Our line cards punted unparseable packets to the CPU: the DLQ is that punt path." One sentence each, then back to the design.

60-second answer: "Apps just log to stdout. A Fluent Bit DaemonSet on every node tails the container log files, adds Kubernetes labels, batches and sends to Kafka with acks=all. Kafka is our durable shock absorber: 3 days, RF 3, so a slow or broken store never loses data or slows the apps. A processor group parses, redacts PII, drops noise and writes big batches to the store, committing offsets only after the write - at-least-once. For a cost-focused design I index only a few low-cardinality labels and keep compressed chunks in S3, like Loki; if we need rich text search I use Elasticsearch with time-based indexes and 10-50 GB shards. Data tiers from hot to warm to cold by age. Queries always carry a time range and labels so we only open the right chunks. I monitor agent lag, consumer lag, ingest rejects and query latency."

Why not have every service send logs directly to Elasticsearch over HTTP?

Because the store becomes part of every request's critical path and failure domain. When Elasticsearch slows down, thousands of clients retry at once, their memory buffers fill, they drop logs or block app threads, and the retry storm makes the cluster slower still. A node agent plus Kafka decouples the two: apps write to a local file (never blocks), the agent ships asynchronously, Kafka absorbs bursts for days, and processors pull at the rate the store can take.

How to answer

Name the failure mode (retry storm, coupling), then the fix (async local write + durable buffer + pull), then the cost (one more system to run, seconds of latency).

Likely follow-ups
  • When is direct shipping fine? (small scale, one consumer)
  • What if Kafka itself is down? (agent filesystem buffer)
What key would you use when producing logs to Kafka, and why?

Something like tenant + app + hash(pod) mod N. Logs from one pod stay in one partition, so they stay in order. One very noisy app spreads across N partitions instead of overloading a single one. Using only app risks a hot partition; using a random key loses per-pod ordering (which matters less for logs than for payments, so random is acceptable if ordering is solved by timestamps at query time).

How to answer

State the two forces - ordering and balance - and show a key that satisfies both. Connect it to ECMP flow hashing: keep a flow on one path, spread flows across paths.

Likely follow-ups
  • What happens to ordering if you add partitions later?
  • How do you detect a hot partition? (per-partition lag and bytes-in)
Elasticsearch vs Loki vs ClickHouse for 40 TB/day of logs - which and why?

At that volume cost dominates. I would default to a labels-only design (Loki) with compressed chunks in object storage, because most queries are "this service, this window, contains X". For structured access logs where people ask counting questions, ClickHouse is excellent - Cloudflare reported around 600 bytes per document in Elasticsearch vs about 60 bytes per row in ClickHouse. I would keep Elasticsearch/OpenSearch for a smaller, high-value slice (security/audit) that needs fast arbitrary-field search.

How to answer

Do not crown one winner. Map each store to a query shape and a cost profile, pick one default, and say when you would add the others.

Likely follow-ups
  • How does Loki answer a search for a trace ID without indexing it? (filter by labels + time, then parallel scan of chunks)
  • How big should an Elasticsearch shard be? (10-50 GB per Elastic's guide)
A team added request_id as a Loki label and ingestion slowed down. Explain and fix.

Each unique label combination is a separate stream. request_id is unique per request, so every request created a new stream with a tiny chunk: millions of streams, a huge index, high memory on the ingesters, and poor compression. Fix: remove it from labels (keep it in the log line), enforce a label allow-list or a max-streams-per-tenant limit at the distributor, and teach teams to query it with |= "req-123" or | json | request_id="req-123".

How to answer

Define cardinality in one line, show the multiplication, then give a technical fix and a governance fix.

Likely follow-ups
  • What is the Elasticsearch version of this problem? (mapping explosion)
  • How would you find the offending labels? (per-tenant stream counts)
How do you guarantee audit logs are never lost?

Audit logs get a stricter path: the agent uses a filesystem buffer, produces with acks=all and idempotence to a dedicated topic with RF 3 and min.insync.replicas=2, the processor commits offsets only after the store confirms, and the audit store keeps replicas plus write-once object storage for long retention. Then I add a reconciliation check: count events per source per hour at the agent and at the store and alert on a gap. Debug logs can be sampled; audit logs are never sampled.

How to answer

Walk hop by hop and say how each hop is made durable. End with "and I verify it" - interviewers like a counting check.

Likely follow-ups
  • What if the node disk dies before the agent ships? (that window is the remaining risk; keep it small with frequent flushes)
How does a query like "errors containing timeout for payments in the last hour" execute?

The query frontend splits the hour into smaller time slices (say 5 minutes) and checks a results cache. For each slice, the label index finds the streams matching {app="payments", level="error"} and the chunk references in that time range. Recent data still in ingester memory is queried directly; older chunks are fetched from object storage. Many querier workers scan their chunks in parallel for "timeout", then the frontend merges results sorted by time and applies the limit. The time range and labels decide how much data is touched, which is why both are mandatory.

How to answer

Describe it as prune (time, labels) then scan in parallel, then merge. Mention caching and limits.

Likely follow-ups
  • How do you stop one user from running a 30-day full scan? (cost limits, concurrency caps)
Someone logged credit card numbers for a week. What do you do and how do you prevent it?

Immediate: stop the source (hotfix the app), add a redaction rule in the first processor, then purge: delete or rewrite affected indexes/chunks for that week, including replicas, snapshots and the Kafka topic (lower retention temporarily or delete records). Record the incident for compliance. Prevention: redaction at the agent/processor for patterns like card numbers and tokens, structured logging libraries that mark sensitive fields, CI checks, and tests that scan sample logs.

How to answer

Contain, clean up everywhere the data was copied, then prevent. Mention that copies exist in more places than people think.

Likely follow-ups
  • Why is deleting from Kafka hard? (immutable log; rely on retention or compaction with tombstones for keyed data)
Consumer lag on logs.raw keeps growing. How do you debug it?

First, is it all partitions or a few? All partitions: the drain is too slow overall - check the store (rejections, write latency), processor CPU, and whether we are at the max consumers (= partitions). A few partitions: a hot key or one stuck consumer - check bytes-in per partition and that consumer's logs/GC. Then: scale processors up to the partition count, increase batch sizes to the store, add partitions or fix the key, and drop/sample noisy sources. While fixing, retention is my deadline: lag must not reach 3 days.

How to answer

Split "everywhere" vs "some partitions" first. It is the same as asking "is the whole link congested or just one queue?"

Likely follow-ups
  • Why can't you just add 100 more consumers?
  • What metric would you alert on? (lag in time, not only in messages)
How would you make this work across 5 regions?

Keep logs in the region where they are produced: each region runs its own agents, Kafka, processors and store. Cross-region transfer is expensive and logs are mostly read locally during incidents. A global query layer fans out a query to the regional query services and merges results. Only small, important slices (audit, security) are replicated to a central store. If one region is down, its logs are unavailable for search but other regions are unaffected.

How to answer

Say "data stays local, queries go global". Mention cost and blast radius.

Likely follow-ups
  • Data residency laws? (another reason to keep logs local)
DaemonSet agent vs sidecar container - which and why?

DaemonSet by default: one agent per node handles all pods, uses fewer resources, and apps need no change because they log to stdout. A sidecar (an extra container in the same pod) is useful when an app writes to log files inside its own filesystem, or when a tenant needs a special pipeline. The cost of sidecars is one extra container per pod - thousands of extra processes.

How to answer

Default, exception, cost. Link DaemonSet to "a process on every line card".

Likely follow-ups
  • What happens to logs when a pod is deleted? (agent must read the file before the kubelet cleans it up)
Kibana or Grafana for the log platform's UI? What does an on-call engineer actually use?

Both, for different jobs. Kibana (or OpenSearch Dashboards on OpenSearch) sits on one search cluster and is best at exploring log text: an index pattern or data view such as logs-* with @timestamp as the time field, Discover for free-form search, saved searches, and dashboards of aggregations like error rate per service. Grafana is source-agnostic and best at time-series: metrics from Prometheus, logs from Loki, and alerting across both. A common flow is a Grafana alert, a dashboard to find when and where, then a link into Discover with the same service and time window to read the lines and pick up a trace ID.

How to answer

Tie the UI to the store you chose: Elasticsearch/OpenSearch means Kibana/OpenSearch Dashboards; Loki means Grafana. Then describe the alert-to-log drill-down. Mention the cost of heavy dashboards on the cluster.

Likely follow-ups
  • Why can't you aggregate on a field marked "conflict"? (Different types across indices; fix with a fixed schema like ECS.)
  • How do you keep dashboards from overloading the cluster? (Shorter default ranges, fewer panels, rollup indices.)

Common mistakes

  • Starting with "I'll use ELK" without requirements or numbers.
  • Apps calling the log store synchronously.
  • No buffer, so a slow store means lost logs.
  • Indexing user_id / trace_id as labels.
  • Forgetting retention tiers and the cost of 1 year of data.
  • Forgetting PII redaction and per-tenant limits.
  • Claiming exactly-once for logs (unnecessary; say at-least-once and why it is fine).

Scenario: Black Friday log storm

At 9 PM traffic triples, a dependency starts timing out, and every service logs a stack trace per request. Ingest goes from 1M to 8M lines/s. Search is now 10 minutes behind and on-call engineers are blind.

Weak answer: "Add more Elasticsearch nodes."

Strong answer: "First, protect the store and the freshest errors: Kafka is absorbing the burst, so nothing is lost. I apply per-tenant limits and drop rules for DEBUG and duplicate stack traces (keep one per error signature per second), and give priority to the error stream so it is processed first - a separate topic for level=error helps here. I scale processors to the partition count. After the incident, I add stack-trace de-duplication at the agent, set default per-service volume budgets, and add an alert on ingest rate per tenant."

Likely follow-ups
  • How do you avoid losing the one important line among the 8M? (separate priority path for errors)
