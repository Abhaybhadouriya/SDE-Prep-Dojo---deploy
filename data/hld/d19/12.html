Quick quiz

Why do apps print logs to stdout instead of calling the log store directly?

  1. stdout is always faster than a network call
  2. So a slow log system never slows the app
  3. Kafka only accepts records from files
The runtime writes stdout to a local file and the agent ships it later, so the app never waits on the log system. Speed is a side effect; the point is isolation. Kafka accepts records from any producer; files are just how the agent picks them up.

Which field should NOT be a Loki label?

  1. namespace
  2. level
  3. cluster
  4. trace_id
trace_id is unique per request (high cardinality) and would create millions of streams. Keep it in the line and filter with |=. namespace, level and cluster have a handful of values each, which is exactly what labels are for.

The store is down for 30 minutes. With Kafka (3-day retention) in the middle, what happens?

  1. Lag grows, nothing is lost, consumers catch up
  2. Kafka deletes lines that were not consumed
  3. Agents block and the apps' stdout fills up
  4. Agents switch to sending straight to the store
Consumers pull, so they simply stop and Kafka keeps the data on disk until retention. Kafka never deletes because something was not consumed; only retention does. Agents keep writing to Kafka, which is healthy, so apps are untouched. Agents do not know about the store at all.

You run Fluent Bit's Kafka output with no Message_Key_Field. What happens to ordering?

  1. Records go to partitions with no key: order lost
  2. Kafka keys each record by its topic name
  3. Fluent Bit refuses to start without a key
With a null key the client spreads records over partitions (sticky batches, then the next partition), so one pod's lines can land in different partitions and arrive out of order. Kafka does not invent keys. Fluent Bit starts fine, which is why the bug is quiet.

Roughly how much raw data is 500 MB/s for a day?

  1. ~430 GB
  2. ~4.3 TB
  3. ~43 TB
  4. ~430 TB
500 MB x 86,400 s ≈ 43 million MB ≈ 43 TB. The others are the same digits off by a factor of 10 or 100; count the zeros: 86,400 is almost 100,000, so 500 MB x 10^5 is about 5 x 10^7 MB.

Only partition 7 of 64 shows growing lag. Most likely cause?

  1. The whole store is down
  2. Retention on the topic is too short
  3. A hot key or one slow consumer
  4. The agents stopped sending to Kafka
If the store were down, every partition would lag. Short retention loses old data but does not create lag on one partition. If agents stopped, lag would shrink, not grow. One lagging partition points to skewed keys or a stuck consumer.

A parser bug sends 20% of lines to logs.dlq. What should the team do after fixing it?

  1. Delete the DLQ: those lines are lost anyway
  2. Replay the DLQ (or raw topic) through the fix
  3. Restart the agents so they resend the lines
The DLQ keeps the original lines, and logs.raw keeps 3 days, so you replay them through the fixed parser. They are not lost; that is the point of a DLQ. Agents have already moved their positions forward and the source files may be rotated away.

Where should PII redaction happen?

  1. In the Grafana UI before showing results
  2. In the agent or the first processor
  3. Only when data moves to the cold tier
  4. In a nightly job that rewrites old indexes
Redact as early as you control the data: once a secret is in Kafka, indexes, replicas and snapshots, removing it everywhere is very hard. Masking in the UI leaves it stored. Cold tier and nightly jobs are too late; the secret is already in hot copies and backups.
