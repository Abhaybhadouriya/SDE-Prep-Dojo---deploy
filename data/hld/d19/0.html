The story

Explain like I'm 5

Every classroom in a big school keeps a diary: "9:02 - Riya spilled paint", "9:05 - window stuck". When something goes wrong, the principal wants to read all the diaries for that morning at once. Walking to 500 classrooms is too slow. So every evening (actually every few seconds!) a helper in each class drops the new diary pages into one big mailbox. A librarian takes the pages out, writes a little sticker on each one ("class 3B, Tuesday, paint"), and files them on shelves sorted by date. Now the principal can say "show me every page with the word paint from Tuesday" and get the answer in a moment. Old pages go to the basement, where shelves are cheap but walking there takes longer.

That is the whole design. The diaries are logs: lines of text a program writes about what it is doing. The helper in each class is a log agent (Fluent Bit, Vector or the OpenTelemetry Collector) that runs on every machine. The big mailbox is a buffer, usually Kafka, so pages are never lost if the librarian is busy. The stickers are labels and parsed fields. The shelves are the log store (Elasticsearch/OpenSearch, Grafana Loki, or ClickHouse). The basement is cheap object storage like S3 (see S3-like object storage).

"ELK" is the old name for this stack: Elasticsearch (store + search), Logstash (parse) and Kibana (UI). Today people swap pieces freely, so in an interview say "an ELK-style pipeline" and then pick each part on purpose.

From your world

You already built this on routers: every line card sends syslog to a relay, the relay buffers and forwards to a central collector, and you grep the collector during an outage. Log aggregation is the same idea, scaled to tens of thousands of machines and terabytes per day. The agent is your syslog relay; Kafka is a huge, replicated, disk-backed relay buffer. Where the analogy breaks: classic syslog over UDP drops lines when the collector is slow. Here we promise not to drop, so we need durable buffering and backpressure, like TCP flow control instead of UDP fire-and-forget.

Asked as "design a logging system", "design Splunk / ELK", or as a deep dive inside a monitoring question. The research notes list it among the classic infra designs (H19). It is a natural fit for a systems engineer: it is all about throughput, buffering, indexing and cost.

New words, once each (you will meet them below):

  • DaemonSet = a Kubernetes object that runs exactly one copy of a pod on every node, like a process that must run on every line card.
  • DLQ (dead-letter queue) = a side topic where lines that cannot be parsed are parked, so one bad line does not block the rest. It is the punt path: packets the fast path cannot handle go to the CPU instead of being dropped or stalling the ASIC.
  • Cardinality = how many different values a field can take (level: 5; user_id: millions). It decides the storage design, see deep dive 3.
  • ILM (index lifecycle management) = Elasticsearch rules that move old indexes to cheaper nodes, shrink them, and finally delete them, by age or size.
  • Searchable snapshot = an Elasticsearch index kept in object storage (S3) that can still be searched, slowly, without holding a full copy on local disks.
  • Mapping explosion = Elasticsearch creating a new field for every new JSON key apps log, until the index schema (the "mapping") is huge and slow.
  • Consumer lag = how far a consumer is behind the newest record in its partition: queue depth. Backpressure = a slow stage making the stage before it slow down, like TCP flow control.

You might confuse:

  • Logs vs metrics vs traces. Logs are individual events with text ("charge timeout for order 42"). Metrics are numbers over time ("5xx per second = 12"), cheap to store and alert on. Traces follow one request across services with timings per hop. You alert on metrics, look at traces to find the slow hop, and read logs for the exact error.
  • Label vs field. A label (Loki) is indexed and decides which chunks a query opens; a field inside the line is only scanned or filtered. Make something a label only if it has few values.
