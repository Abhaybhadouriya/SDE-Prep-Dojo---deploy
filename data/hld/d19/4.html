Data model

Cardinality means "how many different values a field can take". level has 5 values; user_id has millions. This single word decides your storage choice, so learn it now; the table below uses it.

One log record looks like this after parsing:

FieldExampleKindIndexed?
timestamp2026-11-23T10:15:02.123ZtimeAlways (partition + sort key)
namespace, app, cluster, levelcheckout, payments, prod-ap-south, errorlow-cardinality labels (few distinct values)Yes, always
pod, nodepayments-7c9f-x2kmedium cardinality (changes every deploy)Depends on store
trace_id, order_id, user_ida1b2c3, 42high-cardinality (millions of values)Never as a label; searchable as text or a column
messagecharge timeout after 3000 msfree textFull-text index (ES) or brute-force scan (Loki)

Read the "Kind" column as a rule: low-cardinality fields may be labels or index keys; high-cardinality fields stay inside the record.

Three ways to store the same lines

Elasticsearch / OpenSearchGrafana LokiClickHouse
What is indexedEvery token (inverted index)Only the label set of each streamPrimary/sort key + optional skip indexes
Best query"find this rare word anywhere""this service, this hour, contains X""count errors by service per minute"

Real evidenceCloudflare reported ~600 bytes per document in Elasticsearch vs ~60 bytes per row in ClickHouse for their HTTP logs, and moved from sampled to 100% of events (Cloudflare blog).

SQL or NoSQL? Neither in the usual sense. Logs are immutable, time-ordered, append-only data. You never update a log line. So pick a store built for that: a search engine, a log store, or a columnar analytics database, all partitioned by time. A normal OLTP database (Postgres/MySQL) would choke on 1M inserts per second and on full-text search.

Whatever the store, the physical layout is the same idea: partition by time first (one index per day in Elasticsearch, one table partition per hour in ClickHouse, chunks with start/end time in Loki), then by tenant/label. A query for "last hour" opens only the last hour's partitions. This is exactly like a router keeping per-interface counters in time buckets: you never scan the whole history.
