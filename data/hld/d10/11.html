Remember this

You might confuse this with:

  • Authorize vs capture vs settle: authorize = the bank holds the money on the card; capture = we ask for the held money (often at shipment); settle = the PSP actually pays the merchant's bank, usually in a daily batch.
  • Idempotency key vs payment_id: the client makes the idempotency key once per checkout attempt to dedupe retries; the server makes payment_id and reuses it as the PSP's idempotency key.
  • Failed vs unknown: failed = the PSP said no, safe to offer another method; unknown = we did not hear back, never retry with a new request, ask the PSP or wait for the webhook.

Remember this

  • Idempotent = doing it twice has the same effect as once. Every money-moving POST takes a client-made Idempotency-Key.
  • A timeout means "unknown", not "failed". Query, wait for the webhook, reconcile. Never re-charge with a new key.
  • A payment is a forward-only state machine; guard updates with WHERE status IN (...) and a version.
  • SQL with ACID for payments + ledger + outbox; shard by payment_id.
  • Outbox + Kafka + idempotent consumers = effectively-once events.
  • Daily reconciliation against PSP settlement files is the safety net.
  • Money in integer minor units; card data tokenised; secrets in a secret manager.

60-second answer: "The client creates a payment with an idempotency key. The payment service saves the key, records the payment as created in one transaction with an outbox row, runs a risk check, and calls the PSP using the payment id as the PSP's idempotency key. Results come back sync or by signed webhook; I dedupe by event id and move a forward-only state machine, writing ledger postings and outbox rows atomically. The outbox goes to Kafka, keyed by payment id, for the order service, merchant webhooks and analytics, all idempotent. Timeouts become 'unknown' and are resolved by status queries and daily reconciliation, so nobody is charged twice and nothing is lost."
