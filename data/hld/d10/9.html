Interview: how to drive 45 minutes

  1. 0-5 min: scope. Payins for an e-commerce merchant through PSPs; cards and UPI; refunds; out of scope: payouts, disputes, FX. Say "correctness first".
  2. 5-8 min: numbers. 50M/day, about 6k/s peak, about 60k row writes/s. Conclusion: shard, async PSP calls.
  3. 8-13 min: API. POST with Idempotency-Key, GET status, refunds, webhooks. Integer minor units.
  4. 13-18 min: data model. payments, payment_events, idempotency_keys, outbox, ledger postings. SQL, shard by payment_id.
  5. 18-28 min: high-level flow. Draw the stepper above. Name the state machine.
  6. 28-40 min: deep dives. Pick two: the unknown outcome and reconciliation; or idempotency phases and outbox. Let the interviewer steer.
  7. 40-45 min: wrap up. Failure table, monitoring (success rate per PSP, unknown count, webhook lag, recon mismatches), next 10x.
What is an idempotency key and why does a payment API need one?

It is a unique id the client generates once per logical action, such as one checkout attempt, and sends with every retry of that action. The server stores the key with the result of the first attempt. A retry with the same key gets the saved result instead of doing the work again. Payments need it because networks time out: the client cannot tell "the request was lost" from "the response was lost", so it must be able to retry safely without charging twice.

How to answer

Give the messenger story in one line, then the mechanism (unique constraint on merchant + key, stored response, request hash check), then one subtle point: the key comes from the client, and is checked on the primary DB.

Likely follow-ups
  • What if two requests with the same key arrive at the same time? (Row lock or locked_at; the second gets 409 and retries.)
  • How long do you keep keys? (Longer than the client's retry window, often 24 h.)
  • Same key, different amount? (Reject: compare the request hash.)
Your call to the bank timed out. Do you retry?

Not with a new request. A timeout means the outcome is unknown, so I mark the payment unknown and tell the user we are confirming. I query the PSP's status API using the same reference, or resend the identical request with the same idempotency key if the PSP supports it. I wait for the webhook. Anything still unknown after a threshold goes to a sweeper, and the daily settlement reconciliation is the final judge. If the money did move but we cancelled the order, we refund automatically.

How to answer

Say the three possibilities (never arrived, failed, succeeded). Then "query, don't act". Then reconciliation as the safety net. This is the single best signal of payment experience.

Likely follow-ups
  • What does the user see meanwhile?
  • How do you set the timeout value? (Above the PSP's p99, with a budget for the whole request.)
How do you make sure the "payment succeeded" event reaches the order service exactly once?

True exactly-once delivery across a network is not possible, so I make it effectively once: at-least-once delivery plus idempotent processing. The status change and an outbox row are written in one transaction, so the event is never lost. A relay or Debezium publishes the outbox to Kafka with an idempotent producer; it may publish twice after a crash. The order service stores processed event ids (or uses a conditional update like "set paid where status = pending"), so a duplicate does nothing.

How to answer

Name the dual-write problem first, then the outbox, then consumer dedupe. Mention that Kafka transactions only help for Kafka-to-Kafka flows.

Likely follow-ups
  • Why not publish to Kafka inside the DB transaction?
  • How do you keep events for one payment in order? (Key by payment_id.)
SQL or NoSQL for the payments database? Justify it in one sentence.

"SQL, because I need ACID transactions across the payment row, its event history, ledger postings and the outbox, plus unique constraints for idempotency; I will shard it by payment_id to scale writes." Then note that read-heavy merchant dashboards and analytics can use a search index or a warehouse fed from Kafka.

How to answer

Use the pattern: "I pick X because A; the cost is B; if C happens I switch to Y." Cost: sharding effort. Switch: a distributed SQL database (Spanner, CockroachDB) if cross-shard transactions become common.

Likely follow-ups
  • Why not shard by merchant_id?
  • How would you run "all payments for merchant M today"?
Webhooks from the PSP arrive twice and out of order. How do you handle that?

Three layers. Verify the signature and reject old timestamps. Dedupe by the PSP's event id with a unique insert. Apply changes through a forward-only state machine with a conditional update, so "failed" arriving after "succeeded" changes nothing. Return 2xx fast and do slow work async, otherwise the PSP will time out and retry even more.

How to answer

Draw the state machine; show the SQL WHERE status IN (...) guard.

Likely follow-ups
  • What if a webhook never arrives? (Sweeper polls stuck payments; reconciliation.)
What is reconciliation and why can't you skip it?

Reconciliation compares our records (payments table and ledger) with the external truth (PSP and bank settlement reports), usually daily. It catches what real-time logic missed: lost webhooks, timeouts that actually succeeded, fee and amount differences, bugs. Without it you can be wrong silently for weeks. Matched rows close; known mismatch patterns are fixed automatically; the rest go to an operations queue.

How to answer

Frame it as the system's safety net and as how finance and auditors trust the system. Mention metrics: mismatch count and value per PSP per day.

Likely follow-ups
  • How do you reconcile 50M rows quickly? (Partition by date and PSP, sort-merge join in a batch engine such as Spark.)
How do you store money amounts?

As integers in the currency's minor unit (paise, cents) with an explicit currency code, for example amount_minor BIGINT plus currency CHAR(3). Floats cannot represent most decimal fractions exactly, so sums drift. For currencies with three decimals or none, store the exponent per currency. Do conversions with a recorded FX rate.

How to answer

Short and confident; this is a quick filter question.

Likely follow-ups
  • How do you split Rs 100 three ways? (Allocate remainders deterministically.)
The payment succeeded but the order service crashed before marking the order paid. What happens?

Nothing is lost, because the order service learns about payments from the payment-events topic, not from a fire-and-forget call. It had not committed its offset, so after restart (or after another pod takes the partition in a rebalance) it reads the event again and processes it idempotently. If the order had been cancelled meanwhile (say a payment window expired), the saga's compensating step issues a refund. Monitoring on consumer lag tells us if this ever gets slow.

How to answer

Show you understand offsets: commit after processing, not before. Link to the saga for the compensation path.

Likely follow-ups
  • What if the order service has a bug and keeps failing on that event? (Retry topic, then DLQ with an alert.)
How do you keep card data secure and limit PCI-DSS scope?

Do not let raw card numbers touch our servers: the PSP's hosted fields or SDK collect the card and return a token, and we only store tokens. Never store CVV. If we must store cards, put them in an isolated vault service in its own network segment with strict access, encryption with keys in a KMS or HSM, and audit logs. Secrets are in a secret manager and rotated.

How to answer

Lead with "reduce scope" rather than "add encryption everywhere". Mention India's card-on-file tokenisation if the interviewer is Indian-market.

Likely follow-ups
  • How do support staff issue refunds safely? (RBAC, approval for large amounts, audit trail.)
During a big sale one PSP's success rate drops from 95% to 60%. What does your system do?

The router tracks success rate and latency per PSP and method over a sliding window. When it drops below a threshold, a circuit breaker reduces or stops new traffic to that PSP and routes new payments to healthy ones. In-flight payments on the bad PSP are not re-sent elsewhere; they go to unknown/pending handling. Alerts page the on-call, and dashboards show success rate per PSP, bank and method so we can tell "one bank is down" from "the PSP is down".

How to answer

Separate new traffic (safe to move) from in-flight payments (not safe). That distinction is the senior signal.

Likely follow-ups
  • How do you test failover before the sale? (Game days, fault injection, load tests.)
How would you design refunds?

A refund is its own object with its own idempotency key, its own state machine (pending, succeeded, failed) and its own ledger postings (the reverse direction). Validate that total refunds never exceed the captured amount, using a conditional update or a row lock on the payment. Call the PSP's refund API with the refund id as its key. Refunds often complete days later, so they reuse the same webhook and reconciliation machinery.

How to answer

Show reuse: "refunds are payments in reverse, with the same safety tools".

Likely follow-ups
  • Two support agents refund the same order at once?

Scenario: customers report being charged twice during a sale

Support tickets spike: "charged twice for one order". Logs show the PSP adapter hit timeouts, and the mobile app retried checkout.

Weak answer: "Increase the timeout and add more servers."

Strong answer: first, stop the bleeding: find duplicate charges by order_id in the payments table and the PSP report, and refund them automatically. Then find the root cause: the app generated a new idempotency key on each retry, or the adapter retried the PSP with a new reference after a timeout. Fix: one key per checkout attempt stored on the device, the PSP key = our payment_id, timeouts go to the unknown state. Add a partial unique index on (merchant_id, order_id) WHERE status NOT IN ('failed','canceled'), so only one live payment per order can exist but a customer can still retry with UPI after a card decline, and an alert on "more than one succeeded payment per order".

Likely follow-ups
  • How would you have caught this before customers did?

Common mistakes: generating the idempotency key on the server; using floats for money; retrying a timed-out charge with a new request; publishing to Kafka and writing the DB as two separate steps; trusting webhooks without signature checks; forgetting reconciliation; reading idempotency keys from a replica; letting a late "failed" webhook overwrite "succeeded".
