API design

Keep the public API small. Every POST that moves money takes an Idempotency-Key header (there is an IETF draft that standardises this header, and Stripe and Razorpay use the same idea). The merchant's identity comes from the API key or auth token, never from the request body.

# 1. Create a payment (idempotent)
POST /v1/payments
Authorization: Bearer <merchant-api-key>
Idempotency-Key: 6f1c2b9e-0d7a-4c55-9a51-1f0e3a6b8d21
Content-Type: application/json

{ "order_id": "ORD-88231", "amount": 49900, "currency": "INR",
  "method": { "type": "card", "token": "tok_visa_4242" },
  "capture": "automatic" }

# 201 Created
{ "payment_id": "pay_01HZX3", "status": "processing",
  "next_action": { "type": "redirect_3ds", "url": "https://psp.example/3ds/..." } }

# 2. Read status (safe to call any number of times)
GET /v1/payments/pay_01HZX3
# 200 { "payment_id": "pay_01HZX3", "status": "succeeded", "amount": 49900, ... }

# 3. Refund (idempotent too)
POST /v1/payments/pay_01HZX3/refunds
Idempotency-Key: 2c7d...   { "amount": 10000, "reason": "item_damaged" }

# 4. Inbound PSP callback (internal, signature-checked)
POST /internal/psp/razorpay/webhooks
X-Signature: <HMAC-SHA256 of body>   { "event_id": "evt_77", "type": "payment.captured", ... }

# 5. Outbound webhook to the merchant/order service
POST https://merchant.example/hooks/payments
X-Signature: t=1732350000,v1=<HMAC>   { "event_id": "pevt_12", "type": "payment.succeeded", ... }
  • Amounts are integers in minor units (paise, cents): 49900 means Rs 499.00. Never use floats for money; 0.1 + 0.2 is not 0.3 in binary floating point.
  • Statuses are a fixed set (see the state machine below), so clients can switch on them.
  • Same key + different body = error (HTTP 409 or 422). We store a hash of the first request to detect this, as Stripe does.
  • Webhooks are signed (HMAC with a shared secret plus a timestamp) so a receiver can reject fakes and replays.

Deeper API style choices (REST vs gRPC, pagination, versioning) are in API Design & Communication.
