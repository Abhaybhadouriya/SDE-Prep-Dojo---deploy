Quick quiz

Who should generate the idempotency key for "pay for order 88231"?

  1. The payment service, when the request arrives
  2. The client, once per checkout attempt, reused on every retry
  3. The PSP, after charging the card
If the server made the key on arrival, every retry would arrive as a new request with a new key, and the protection would be gone.

The PSP call timed out. What is the correct next state?

  1. failed, and tell the user to try again
  2. succeeded, because most payments succeed
  3. unknown, then query the PSP and reconcile
A timeout tells you nothing about the result. Treating it as failed invites a second charge; treating it as succeeded can ship goods for free.

Why do we write the outbox row in the same transaction as the status change?

  1. So the event can never be lost or published for a change that rolled back
  2. Because Kafka requires it
  3. To make the transaction faster
This solves the dual-write problem: one commit covers both, and a relay publishes later (maybe twice, which consumers dedupe).

A "failed" webhook arrives after the payment is already "succeeded". What should happen?

  1. Overwrite to failed, the newest message wins
  2. Ignore it, because succeeded -> failed is not a legal edge, and log it for review
  3. Refund immediately
Forward-only state machines make out-of-order webhooks harmless. A conflicting late event is a reconciliation signal, not an instruction.

How should Rs 499.00 be stored?

  1. FLOAT 499.0
  2. VARCHAR "499.00"
  3. BIGINT 49900 plus currency INR
Integer minor units are exact and fast to sum. Floats drift; strings cannot be summed safely.

Why key the payment-events topic by payment_id?

  1. All events of one payment land in one partition, so consumers see them in order
  2. It spreads load across brokers better than a random key
  3. Kafka requires a numeric key
Kafka orders messages only within a partition. Same key, same partition, same order.

What does daily reconciliation compare?

  1. Kafka offsets against consumer offsets
  2. Our payments table and ledger against the PSP or bank settlement report
  3. CPU usage across pods
Reconciliation checks our view of money against the external source of truth and fixes or flags differences.
