Architecture: follow one payment

First, the whiteboard version you should be able to redraw in 30 seconds: client, gateway, payment service, PSP adapter, database with outbox, Kafka. Then click Next or Play to walk the full path.

  1. Request in. The checkout page sends POST /v1/payments with an Idempotency-Key. The API gateway checks the merchant's API key, applies rate limits and forwards it to the payment service.
  2. Check the notebook. The payment service inserts the key with INSERT ... ON CONFLICT DO NOTHING. If the key exists and is finished, it returns the saved response. If it exists and is locked (a request still in flight), it returns 409 "try again shortly". If the body hash differs, it rejects the request.
  3. Record intent first. In one database transaction it inserts the payment row (status created), a payment_events row and an outbox row. Now, even if the server dies, we know a payment was started.
  4. Risk, then PSP. A risk/fraud check scores the attempt. The PSP adapter calls the chosen PSP and passes our payment_id as the PSP's idempotency key, so our own retries to the PSP are safe too. Status becomes processing.
  5. The outside world. The PSP talks to the card network and bank (or NPCI for UPI). It may answer at once (success, decline, "needs 3-D Secure") or say "pending".
  6. Async result. Minutes later the PSP calls our webhook endpoint. We verify the signature, dedupe by the PSP's event_id, move the state machine forward only (never backwards), and write ledger postings + an outbox row in one transaction.
  7. Publish reliably. An outbox relay (a poller, or Debezium reading the database log) publishes outbox rows to the Kafka topic payment-events, keyed by payment_id so one payment's events stay in order.
  8. Fan out. Independent consumer groups react: merchant webhook sender, order service (mark order paid, start fulfilment), notifications (SMS/email), analytics and fraud models. Each consumer is idempotent by event_id.
  9. The scary path. If the PSP call timed out we do not know if money moved. Mark the payment unknown, query the PSP's status API with the same reference, and let the daily reconciliation catch anything still unclear. Never retry with a fresh key.

The payment state machine

A payment is a small state machine. Writing it down stops a lot of bugs: an out-of-order webhook that says "failed" after we already recorded "succeeded" is simply ignored because that edge does not exist.

-- Move forward only if the row is still in the state we expect (optimistic locking)
UPDATE payments
   SET status = 'succeeded', version = version + 1, updated_at = now()
 WHERE payment_id = 'pay_01HZX3'
   AND status IN ('processing', 'authorized', 'unknown')
   AND version = 3;
-- 1 row updated  -> we won, now insert postings + outbox in the same transaction
-- 0 rows updated -> someone else already moved it (duplicate webhook): do nothing
