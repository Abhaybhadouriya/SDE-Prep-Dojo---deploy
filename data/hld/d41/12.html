Quick quiz

With 1,000 TPS per database node, how many nodes does ByteByteGo estimate for 1M transfers/s?

  1. 1,000, one node for every 1,000 transfers per second
  2. 2,000 (2 operations per transfer)
  3. 500, since a debit and credit share one node
Each transfer is a debit + a credit = 2 operations, so 2M ops / 1,000 = 2,000 nodes. The two accounts are usually on different nodes, so you cannot halve it.

In a cross-shard saga, which step goes first?

  1. Credit the receiver, so the user sees the money arrive fast
  2. Either, in parallel, because compensation can undo any failure
  3. Debit the sender
If you credit first and the debit then fails, the receiver may already have spent money that never existed, and no compensation can pull it back.

Why should idempotency checks read from the primary?

  1. Replica lag can hide a finished request, so a retry runs twice
  2. Replicas do not enforce UNIQUE constraints, so duplicates slip in
  3. Replicas are slower, and this check sits on the latency path
Airbnb documented duplicate payments caused by exactly this. Replicas do enforce constraints (they copy the primary), and speed is not the point.

In event sourcing, which data must be replicated with the strongest guarantee?

  1. Commands, because they are the original user intent
  2. Snapshots, because replay from them is the fastest
  3. Events, since state and snapshots derive from them
State and snapshots can be rebuilt from events. Commands may not deterministically produce the same events (for example a balance check can go either way), so replicate the validated facts.

A wrong posting was made yesterday. What is the correct fix?

  1. UPDATE the posting row and copy the old value to an audit table
  2. Post a reversing or adjusting journal entry
  3. DELETE the posting and insert the right one in one transaction
Ledgers are append-only, so the history must show both the mistake and the correction. An audit side-table still breaks the "postings never change" rule that replay depends on.

A merchant account receives thousands of credits per second. Best first fix?

  1. Split it into sub-accounts and credit a random one
  2. Move to a bigger database server with faster disks
  3. Add read replicas so the credits spread across copies
The bottleneck is one row's lock. Spreading the writes removes it, and the balance is the sum. Replicas cannot take writes, and a bigger box still serialises on the same row.

In a UPI payment, who actually debits the payer's money?

  1. The payer's bank, instructed via the NPCI switch
  2. The payment app's own wallet database, which settles later
  3. The payee's bank, which pulls the funds from the payer
UPI is bank-to-bank. The app orchestrates and records the intent and outcome; NPCI routes the debit to the payer's bank and the credit to the payee's bank.

A record is stamped 23:59:55 by us and 00:00:30 by the bank. Recon shows a mismatch. What is it?

  1. Fraud: the timestamps were edited, so freeze the account
  2. A lost payment that needs an automatic refund today
  3. A temporary break; re-check with the next day's file
Cut-off differences are normal. Classify them and clear them when the next file matches. Refunding would pay the user twice once the bank's record shows up.
