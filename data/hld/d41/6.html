Deep dives

1. Cross-shard transfers: 2PC vs TC/C vs saga

Accounts A and C live on different databases. ByteByteGo walks through three ways to make "A -1, C +1" atomic:

2PC (XA)TC/C (Try-Confirm/Cancel)Saga (orchestrated)
Who does itThe database (prepare, then commit)The application, in 2 phasesThe application: a sequence of local transactions
After phase 1Local transactions not committed, locks heldEach local transaction already committed (Try)Each step committed as it runs
On failureAbort allCancel = a new transaction that reverses TryCompensating transactions in reverse order
Parallel stepsYesYesNo (linear)
Main painLong-held locks, coordinator is a SPOF, needs XA supportOut-of-order Cancel before Try, and you must store the phase statusIntermediate states are visible, and you write N compensations
Use whenRarely at wallet scaleLatency-sensitive, many participantsThe default in microservices, and the current trend
  • Order matters. ByteByteGo shows that only "debit first, credit later" is valid. If you credit first and the debit then fails, C may already have spent the money, and you cannot take it back.
  • Store the phase status. For TC/C, keep a phase table (transaction id, the Try status per participant, the second-phase decision, an out-of-order flag) in the database of the debited account. Then a restarted coordinator knows where it stopped.
  • Out-of-order Cancel. A Cancel can arrive at C before C's Try (network delay). C records "cancelled before try", and a later Try must fail.
  • The in-flight state is visible. Between step 1 and step 2, the money is in neither account. Model it explicitly as a clearing or "in-transit" account, so that the books still balance at every instant.

Patterns in depth: distributed transactions, multi-step processes.

2. Idempotency end to end

  1. Client key. The app generates a UUID per user intent and reuses it on every retry. Stripe popularised the Idempotency-Key header, paired with exponential backoff with jitter on retries.
  2. Server lease. Insert the key with status IN_PROGRESS and a lease expiry. A concurrent duplicate sees IN_PROGRESS and gets 409 / "retry later". Airbnb's Orpheus uses a row lock and a lease longer than the RPC timeout.
  3. Unique constraint in the ledger. journal_entry.idempotency_key UNIQUE. Even if every layer above fails, the database refuses a second journal entry for the same intent.
  4. Downstream keys. Pass a derived key to the bank or the PSP, so it deduplicates too.
  5. Store the response. Retries get the same answer, including a "failed: insufficient funds" answer.

Replica lag causes double spends. If you check "has this key been processed?" on a read replica, a retry that arrives a few seconds after the first success can miss it and execute again. Airbnb documents this exact failure. Keep idempotency reads on the primary.

Stop here for SDE-1. The double-entry invariant, the same-shard ACID transaction with balance >= amt, a debit-first saga across shards, and idempotency at every layer are the interview-sufficient core. Deep dives 3-6 (event sourcing and Raft, hot accounts, reconciliation, UPI internals) are what an SDE-2 or fintech-team answer adds.

3. Event sourcing, CQRS and reproducibility

Auditors ask: "What was this balance at 23:59 on 31 March? Prove it. Prove the new code computes the same thing." ByteByteGo's answer is event sourcing:

  • Command: an intent ("transfer 1 from A to C"). It can be invalid.
  • Event: a validated fact ("transferred 1 from A to C"). It is immutable, in past tense, and must be applied.
  • State: the balances map, derived by applying events.
  • State machine: validates commands into events and applies events to state. It must be deterministic, so no random numbers and no I/O.

Replay the events from the start, or from a snapshot, and you get exactly the same balances. With CQRS (Command Query Responsibility Segregation: writes go to the event log, reads come from separate views built from it), read-only state machines build other views (statements, a balance at time T, fraud features) from the same event stream. For speed, ByteByteGo moves the command and event logs to local append-only files (mmap) and the state into RocksDB, which is an LSM tree and therefore write-optimised. It then replicates the event log with Raft: with 5 nodes, the system keeps working while 3 are up. Accounts are partitioned across Raft groups, and cross-group transfers use a saga on top.

From your world

A deterministic state machine replicated by a consensus log is exactly how a redundant control plane stays in sync. The active and standby route processors apply the same ordered update stream, so they reach the same RIB. Raft's "majority of 5" rule is the same quorum logic as split-brain protection in a cluster of line cards.

4. Hot accounts

A big merchant receives thousands of payments a second into one account row. Every credit takes that row's lock, so the account becomes the bottleneck.

  • Split into sub-accounts: merchant_42#0..#63. Credits go to a random sub-account, and the balance is the sum. Debits (payouts) are rare and can sweep the sub-accounts.
  • Credit-only fast path. Credits cannot overdraw, so you can append postings without the balance >= amt check, batch them, and update the cached balance asynchronously.
  • Pre-aggregate. Write one journal entry per N payments per second (a "batch posting"), with the details kept in the line items. This is the same idea as sharded counters.

5. Reconciliation: the safety net

Even with exactly-once code, the outside world disagrees sometimes: a bank's file is late, a timestamp falls on the other side of midnight, or a partner sends a malformed report. Reconciliation compares our ledger with bank settlement files and PSP reports every day, or as a stream.

  • Normalise the formats first (dates, amounts, ids).
  • Cut-off breaks: a record at 23:59:55 here and 00:00:30 at the bank shows as a mismatch. Mark it a temporary break and re-check against tomorrow's file (ByteByteGo).
  • Clearing accounts should be zero. Stripe's Ledger models each flow as money moving through accounts. In steady state, "clearing" accounts must be empty, so a single missing or wrong event shows up as a non-zero clearing balance. Stripe reports 5 billion events a day, with 99.99% of dollar volume fully ingested and verified within four days.
  • Scale: batch jobs (Spark/Hadoop) for end-of-day, and Flink for near-real-time.

6. How UPI actually moves money

For your design, this means that a UPI-based app is a payment orchestrator + ledger of intents, not a balance holder. Its hard problems are: timeouts with an unknown outcome (the "deemed" or pending state), status-check APIs, polling, and reversals, plus daily reconciliation with the banks. Treat every outbound call as "may have happened": store the intent first, call, and then record the response (the pre-RPC / RPC / post-RPC split).
