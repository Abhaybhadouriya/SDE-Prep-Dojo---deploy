Data model

Square's Books service shows the minimal shape. A book (account) holds a cached balance and a version. A journal entry is one atomic money movement. Book entries (postings) link the two and carry +/- amounts. Only the balance row is ever updated. Everything else is insert-only.

-- one transfer inside ONE shard: a single ACID transaction
BEGIN;
INSERT INTO journal_entry (entry_id, idempotency_key, type)
     VALUES (:eid, :idem, 'P2P');                         -- duplicate key -> already done, return stored result
UPDATE account SET balance = balance - :amt, version = version + 1
 WHERE account_id = :from AND balance >= :amt;           -- 0 rows -> insufficient funds -> ROLLBACK
UPDATE account SET balance = balance + :amt, version = version + 1
 WHERE account_id = :to;
INSERT INTO posting (entry_id, account_id, amount) VALUES (:eid, :from, -:amt), (:eid, :to, :amt);
COMMIT;

Why SQL (or NewSQL)

OptionFitNotes
Sharded MySQL / PostgresGoodACID per shard. A transfer across shards needs a distributed transaction (2PC, TC/C or a saga, compared in deep dive 1). This is the most common interview answer.
Spanner / CockroachDB / YugabyteDBVery goodDistributed ACID transactions hide the sharding. Square's Books is a purpose-built ledger service, reported to run on Cloud Spanner (per StackShare; Square's own post does not say). They are costlier and add commit latency.
Redis as the balance storeBad as the source of truthFast, but two updates on two nodes are not atomic. ByteByteGo's first design fails here: a crash between the debit and the credit loses money.
Event log + state machine (event sourcing)Best for audit and peak throughputAn append-only command/event log, deterministic replay, and snapshots. ByteByteGo's final design.
Purpose-built ledger DBAt huge scaleUber's LedgerStore: immutable, verifiable, tiered storage, trillions of index entries.
