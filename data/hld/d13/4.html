Data model

There are two kinds of data, and they want very different stores.

DataSize and shapeStoreWhy
Video bytes (original, renditions, segments, thumbnails)PBs per day, immutable, big objectsBlob / object storage (S3, GCS, Azure Blob, or in-house)Cheap per GB, very durable, scales horizontally, serves byte ranges. See S3-like Object Storage.
Video metadata (title, owner, status, durations)Billions of small rows, read on every watchSharded SQL (MySQL with Vitess at YouTube) plus a cacheNeeds transactions for status changes and simple secondary indexes. Size is small; QPS is high.
Upload sessions and processing jobsShort-lived, write-heavy stateSQL table or a workflow engine's storeMust be exact: which parts arrived, which tasks finished.
View counts, watch eventsHuge event streamKafka, then a stream aggregator, then a counter storeCounts can be approximate and late. Never increment a SQL row per view.
 
-- Sharded by video_id (Vitess keyspace "videos"); channel lookups use a secondary index table
CREATE TABLE videos (
  video_id      VARCHAR(16) PRIMARY KEY,      -- random, so writes spread over shards
  channel_id    BIGINT       NOT NULL,
  title         VARCHAR(200) NOT NULL,
  visibility    ENUM('PUBLIC','UNLISTED','PRIVATE') NOT NULL,
  status        ENUM('UPLOADING','UPLOADED','PROCESSING','READY','FAILED','BLOCKED') NOT NULL,
  duration_ms   INT,
  source_key    VARCHAR(512),                 -- raw/v_9Kx2/source.mp4
  manifest_key  VARCHAR(512),                 -- hls/v_9Kx2/master.m3u8
  created_at    TIMESTAMP NOT NULL,
  version       INT NOT NULL DEFAULT 0        -- optimistic locking for status changes
);

CREATE TABLE renditions (
  video_id   VARCHAR(16),
  profile    VARCHAR(16),        -- 'h264_720p', 'vp9_1080p'
  status     ENUM('PENDING','RUNNING','DONE','FAILED'),
  bytes      BIGINT,
  PRIMARY KEY (video_id, profile)   -- same shard as the video: no cross-shard join
);

CREATE TABLE segment_tasks (
  video_id   VARCHAR(16),
  profile    VARCHAR(16),
  seg_no     INT,
  attempt    INT DEFAULT 0,
  status     ENUM('PENDING','RUNNING','DONE','FAILED'),
  output_key VARCHAR(512),
  PRIMARY KEY (video_id, profile, seg_no)   -- the natural idempotency key of a task
);

Blob key layout matters too. Use raw/{video_id}/source, out/{video_id}/{profile}/seg_00042.m4s and out/{video_id}/master.m3u8. Putting the random video_id first spreads load across the storage system's internal partitions. A key that starts with a date would put all of today's writes in one hot range.
