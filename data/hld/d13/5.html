Architecture, step by step

Whiteboard version (6 boxes). This is what you draw from memory in the first minute. The stepper below adds the detail.

Click Next or Play. Watch how the heavy bytes avoid our servers, and how every slow step is behind a queue.

  1. Start. The app calls POST /v1/videos. The Upload API checks auth and quotas, writes a row with status=UPLOADING, starts a multipart upload in blob storage and returns presigned part URLs.
  2. Bytes go direct. The app PUTs 16 MB parts straight to the raw bucket, several in parallel, retrying only failed parts. Our servers only handle small JSON.
  3. Complete. The app calls complete (or the bucket emits an "object created" notification). The API flips the row to UPLOADED and, in the same transaction, writes an outbox row; a relay publishes video.uploaded to Kafka.
  4. Plan the work. The orchestrator consumes the event, probes the file (duration, codec, resolution), decides the ladder, splits the video into segments at keyframes, and enqueues one task per (segment, profile).
  5. Encode in parallel. Stateless worker pods pull tasks, download one segment, run ffmpeg, upload the output and report done. Hundreds of segments of one video encode at the same time.
  6. Package. When all segments of a profile are done, a packaging step writes HLS/DASH playlists and the master manifest. Thumbnails and copyright/policy checks run in parallel branches of the same DAG (directed acyclic graph: tasks with arrows for "depends on", no loops).
  7. Ready. The orchestrator sets status=READY with a conditional update and publishes video.ready. Notification, search indexing and recommendation services consume it.
  8. Watch. The player loads master.m3u8 through the CDN, picks a rendition from its measured bandwidth, and keeps switching per segment. CDN misses go back to the processed bucket (the origin).

From your world

This is a control plane / data plane split, the same one you know from routers. The Upload API is the route processor: it signs, decides and records. The blob store and CDN are the forwarding ASICs: they move the heavy bytes and never ask the control plane per packet. Where it breaks: here the "data plane" is a third-party storage service, so you control it only through policies (signed URLs, bucket rules), not through code.
