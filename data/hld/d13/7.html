Where Kafka, Kubernetes and Docker fit

Kafka

  • Lifecycle events (video.uploaded, video.ready, video.blocked) are a perfect fit: small, durable, replayable, and many independent consumers (search, notifications, recommendations, analytics) each read them in their own consumer group. Key by video_id so events for one video stay ordered in one partition (why keys matter).
  • Never put video bytes in Kafka. The default max message is about 1 MB. Put a pointer (the blob key) in the event. This is the "claim check" pattern.
  • Task queue caveat. Encoding tasks are long (seconds to minutes) and uneven. In a classic consumer group one slow task blocks its whole partition, and parallelism is capped at the partition count. Options: many partitions plus a worker that hands tasks to a local pool and commits carefully; Kafka share groups (KIP-932, production-ready since Kafka 4.2), which let many consumers share a partition with per-record acknowledgement; or a classic work queue such as SQS or RabbitMQ for the task hop while Kafka keeps the lifecycle events. Saying this trade-off out loud is an SDE-2 signal.
  • View events are a high-volume stream: Kafka plus a stream processor (Flink / Kafka Streams) for counts and trending. See the end-to-end pipeline for the same shape.

Kubernetes

Transcoder pods are stateless, CPU-hungry and safe to kill, which is the ideal Kubernetes batch workload. Scale them on queue depth (consumer lag), not CPU, using KEDA's Kafka scaler. Run them on a spot node pool with a low PriorityClass so the upload API always wins. (Background: Scheduling & Autoscaling.)

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: transcoder
spec:
  scaleTargetRef:
    name: transcoder            # a Deployment of ffmpeg workers
  minReplicaCount: 5
  maxReplicaCount: 256          # = partitions on transcode.tasks; 2000 needs >= 2000 partitions or share groups (Kafka 4.2+)
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka-bootstrap:9092
        consumerGroup: transcoder
        topic: transcode.tasks
        lagThreshold: "4"       # about 4 waiting tasks per pod
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: transcoder
spec:
  replicas: 5                  # starting size; KEDA owns it after that
  selector:
    matchLabels: { app: transcoder }
  template:
    metadata:
      labels: { app: transcoder }
    spec:
      priorityClassName: batch-low
      nodeSelector: { pool: spot-cpu }
      terminationGracePeriodSeconds: 120   # finish or abandon the current segment
      containers:
        - name: worker
          image: registry.example.com/transcoder:1.8.2
          resources:
            requests: { cpu: "4", memory: 4Gi }
            limits:   { memory: 6Gi }       # no CPU limit: avoid CFS throttling

Gotcha: by default KEDA's Kafka scaler will not scale a classic consumer group above the topic's partition count, because the extra consumers would sit idle. If you want 2,000 workers, the topic needs at least 2,000 partitions, or use share groups / a different queue.

Docker

Each stage is its own image. The transcoder image pins the exact ffmpeg build, because a different ffmpeg version can produce different output. Learn the basics in Writing a Dockerfile.

FROM debian:trixie-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends ffmpeg python3 python3-pip ca-certificates \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY worker.py .
# do not run ffmpeg as root on untrusted input
USER 10001
ENTRYPOINT ["python3", "worker.py"]

From your world

Splitting a video into segments and spreading them across workers is RSS (receive side scaling) for video: hash flows across CPU cores so no single core is the bottleneck. Consumer lag is the queue depth on that ring. Where it breaks: RSS keeps a flow on one core for ordering; here we deliberately spread one video's segments everywhere and restore order at the end (fan-in), because segments are independent.
