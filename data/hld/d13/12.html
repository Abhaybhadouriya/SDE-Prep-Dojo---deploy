Quick quiz

Why do uploads use presigned URLs to blob storage?

  1. Blob storage can run ffmpeg near the bytes
  2. So the heavy bytes skip our app servers
  3. Presigned URLs never need to expire
  4. Signed URLs make the upload encrypted
At hundreds of Gbit/s, proxying bytes through app servers is pure cost, so storage takes them directly. Blob storage does not run your encoder. Presigned URLs are bearer tokens, so they must expire quickly. Encryption comes from HTTPS, not from the signature.

A network drop happens at 80% of a multipart upload. What must be resent?

  1. The whole file, from byte zero
  2. The last 20% plus the first part
  3. Only the parts the store lacks
Each part is stored on its own with an ETag; the client lists the parts the store has and sends the rest. Starting over is exactly what multipart avoids. The first part is safe once its ETag came back.

A video was uploaded at 60 fps. The pipeline uses -g 48. What goes wrong?

  1. Nothing: -g counts seconds, not frames
  2. ffmpeg refuses 60 fps input with -g
  3. Keyframes land every 0.8 s, off the plan
  4. The audio track drifts out of sync
-g counts frames, so at 60 fps 48 frames is 0.8 s, not the planned 2 s, and segment cuts no longer match the plan. -g is not in seconds. ffmpeg accepts it happily, which is why the bug is quiet. Audio sync is unaffected. Set keyframes by time with -force_key_frames instead.

A spot VM dies mid-task and the task runs twice. Why is that safe?

  1. Kafka delivers to ffmpeg exactly once
  2. The orchestrator skips every second run
  3. The output key is fixed per segment task
  4. Spot VMs finish the task before they die
At-least-once delivery plus a deterministic output key (video, profile, segment) means a rerun overwrites the same object with the same bytes. Kafka exactly-once does not reach an external ffmpeg process. Nothing skips reruns. Spot VMs get about two minutes of notice at best, often not enough.

What is the problem with a classic Kafka consumer group as a queue for long encode tasks?

  1. One slow task blocks its whole partition
  2. Kafka deletes each task once it is read
  3. Kafka cannot hold messages under 1 KB
A partition is processed in order by one consumer, so a 10-minute task stalls everything behind it, and workers are capped at the partition count. Kafka does not delete on read; retention is time or size based. Small messages are Kafka's normal case.

What is the best way to keep view counts for a viral video?

  1. UPDATE views = views + 1 on each view
  2. Stream events, sum per minute, add deltas
  3. Count CDN log lines in a nightly batch
  4. Keep one counter in a single Redis key
Streaming aggregation turns millions of views into a few delta writes per minute. A per-view UPDATE creates one hot locked row. A nightly batch is too stale for creators. One Redis key is a single hot shard; you would still need to split or batch it.

Encoding costs are too high. Which lever fits "cost follows views"?

  1. Encode every upload in AV1 right away
  2. Only encode on the first view, then cache
  3. Basic ladder first, extra codecs if popular
Efficient codecs cost more compute but save bandwidth, which only pays off on videos that are watched. AV1 for every upload wastes compute on the long tail nobody watches. Encode-on-first-view makes the first viewer wait minutes.

In the Dockerfile, why must the comment sit on its own line above USER 10001?

  1. Dockerfiles only allow # at line start
  2. USER needs a comment to be valid
  3. BuildKit strips comments after USER
  4. A trailing comment makes it run as root
Docker treats # as a comment only at the start of a line, so a trailing comment becomes extra arguments and the build fails with "USER requires exactly one argument". USER needs no comment. BuildKit does not strip it, which is the problem. It does not silently fall back to root; the build simply fails.
