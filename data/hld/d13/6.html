Deep dives

1. Resumable, parallel, direct-to-storage upload

Phones lose signal, laptops sleep, and a 4 GB single PUT that fails at 99% is a disaster. So we use multipart upload: the file is cut into parts (S3 allows 5 MB to 5 GB per part and up to 10,000 parts per upload; check the S3 multipart docs). Each part has a number and gets an ETag back. Only when the client calls complete with the list of parts does the object appear, atomically.

  • Part size is a trade-off. Small parts (5-8 MB) lose less work on failure, which suits mobile. Big parts mean fewer requests, which suits fast desktop links. Let the server suggest a size from the file size and device type.
  • Parallelism: 3-6 parts in flight fill a fast link without starving the user's other apps. It is the same idea as a TCP window.
  • Integrity: send a checksum per part (for example Content-MD5 or a SHA-256 checksum header) so the store rejects corrupt parts, plus a whole-file hash to detect duplicate uploads.
  • Garbage: abandoned uploads leave orphan parts that cost money. Add a lifecycle rule such as "abort incomplete multipart uploads after 7 days".
  • Open protocol option: tus is an open resumable-upload protocol with a Go server (tusd) if you do not want vendor-specific multipart.
# Server side: create the multipart upload and sign one URL per part (boto3)
import boto3
s3 = boto3.client("s3")
mpu = s3.create_multipart_upload(Bucket="raw-videos", Key="raw/v_9Kx2/source.mp4",
                                 ContentType="video/mp4")
urls = [
    s3.generate_presigned_url(
        "upload_part",
        Params={"Bucket": "raw-videos", "Key": "raw/v_9Kx2/source.mp4",
                "UploadId": mpu["UploadId"], "PartNumber": n},
        ExpiresIn=3600)                      # 1 hour, one key, one part
    for n in range(1, 257)
]
# ...later, after the client reports its ETags:
# s3.complete_multipart_upload(Bucket=..., Key=..., UploadId=...,
#     MultipartUpload={"Parts": [{"PartNumber": n, "ETag": etag}, ...]})

2. The transcoding DAG and segment-level parallelism

Encoding a 2-hour 4K movie on one machine can take hours. So we split it. The orchestrator cuts the source at keyframes (frames that can be decoded alone, also called I-frames) into chunks of a few seconds, and fans out one task per chunk per profile. A DAG (directed acyclic graph) describes which steps wait for which.

  • Idempotent tasks. A task's identity is (video_id, profile, seg_no) and its output key is derived from it. If a spot machine dies mid-task and the task runs twice, the second run overwrites the same key with the same bytes. No duplicates, no locks.
  • Fan-in without races. When a worker finishes, it marks its row DONE and checks "are all segments of this profile DONE?" with one conditional query. Only the worker whose update made the count complete triggers packaging. Or let a workflow engine (Temporal, AWS Step Functions, Netflix-style workflow systems) own the DAG state.
  • Stragglers. One slow machine delays the whole video. Track task duration; if a task runs much longer than its peers, start a speculative copy elsewhere and take whichever finishes first. That is safe only because tasks are idempotent.
  • Poison segments. A corrupt chunk crashes ffmpeg every time. Count attempts; after 3, mark the task FAILED, send the details to a dead-letter queue, and fail or degrade the video (for example, publish without that rendition) instead of retrying forever.
  • Keyframe alignment. Every rendition must put keyframes at the same timestamps (for example every 2 s, with scene-cut keyframes off), or the player cannot switch quality cleanly at a segment edge. This is the detail that shows you have actually done it.
  • Fast first rendition. Encode a low and a medium rendition first so the video becomes watchable quickly, then add 4K and extra codecs later as background work.

3. Cost: do not encode everything for everyone

Most uploads get few views, while a small fraction gets most of them. Encoding every video into every codec at every resolution wastes compute and storage on videos nobody watches. The usual policy:

  • At upload: a basic H.264 ladder that every device can play.
  • When a video becomes popular: re-encode into more efficient codecs (VP9, AV1). They cost more CPU to encode but save CDN bandwidth on every later view, and bandwidth is the bigger bill for popular videos.
  • Per-title tuning: a cartoon with flat colours needs far fewer bits than a confetti-filled concert. Netflix publicly described choosing the ladder per title by complexity; the same idea applies here.
  • Storage tiers: move cold renditions and originals to colder, cheaper storage classes with erasure coding; keep hot segments on fast storage and the CDN.
  • Hardware: spot or preemptible VMs for batch encoding (tasks are short and idempotent, so losing a machine is cheap), GPUs or dedicated video encoding chips for scale. Google has publicly described building custom video transcoding hardware for YouTube.

4. Adaptive streaming: HLS and DASH

The player does not download "the video". It downloads a small text manifest that lists the renditions, then fetches segments one by one over plain HTTP. HLS (RFC 8216) uses .m3u8 playlists; DASH uses an XML .mpd. Because every segment is a normal cacheable HTTP object, any CDN can serve video.

Here is a real ffmpeg command that makes a 3-rung HLS ladder with aligned keyframes. Try it on any MP4 on your laptop:

mkdir -p out
ffmpeg -i input.mp4 \
  -filter_complex "[0:v]split=3[a][b][c];[a]scale=-2:1080[v0];[b]scale=-2:720[v1];[c]scale=-2:480[v2]" \
  -map "[v0]" -map "[v1]" -map "[v2]" -map 0:a -map 0:a -map 0:a \
  -c:v libx264 -preset veryfast -g 48 -keyint_min 48 -sc_threshold 0 \
  -b:v:0 5M -b:v:1 2800k -b:v:2 1400k \
  -c:a aac -b:a 128k \
  -f hls -hls_time 6 -hls_playlist_type vod \
  -hls_segment_filename "out/v%v/seg_%03d.ts" \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0 v:1,a:1 v:2,a:2" \
  "out/v%v/index.m3u8"
$ ls out out/v1 | head
out:
master.m3u8  v0  v1  v2

out/v1:
index.m3u8  seg_000.ts  seg_001.ts  seg_002.ts  ...

$ cat out/master.m3u8        # bandwidth numbers will differ for your file
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=5640800,RESOLUTION=1920x1080,CODECS="avc1.640028,mp4a.40.2"
v0/index.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=3220800,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
v1/index.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=1680800,RESOLUTION=854x480,CODECS="avc1.64001f,mp4a.40.2"
v2/index.m3u8

-g 48 -keyint_min 48 -sc_threshold 0 forces a keyframe every 48 frames (2 s at 24 fps) in every rendition, so all three ladders line up. That only works if the source is 24 fps: at 30 or 60 fps, 48 frames is 1.6 s or 0.8 s. Real pipelines set keyframes by time instead: replace -g 48 -keyint_min 48 with -force_key_frames "expr:gte(t,n_forced*2)" (keep -sc_threshold 0), or compute -g = 2 x the source fps after probing. Probe a file first with ffprobe -v error -show_entries format=duration:stream=codec_name,width,height -of json input.mp4; the orchestrator does the same to plan the ladder (no point making 1080p from a 720p source).

5. Metadata, view counts and hot videos

  • Metadata at scale. YouTube built Vitess in 2010 to shard MySQL behind a proxy layer, so applications see one database. Shard by video_id; keep renditions and tasks in the same shard; put a cache (Memcached/Redis) in front of the watch-page read.
  • View counts. Never UPDATE videos SET views = views + 1 per view: a viral video would make one row the hottest lock in the company. Send view events to Kafka, aggregate per video per minute in a stream job, and add the totals to a counter store. Counts lag by seconds to minutes, which is fine. See Top-K / Heavy Hitters for the same streaming pattern.
  • Hot videos. A viral video is a CDN problem, not a database problem: segments are immutable, so cache them with long TTLs. Use request coalescing at the CDN (many misses for the same segment become one origin fetch) and an origin shield (a mid-tier cache) so a new viral video does not stampede the bucket.
