Key APIs

Model it like Chubby/ZooKeeper: a tiny file-system-like namespace where any node can be a lock. gRPC or a custom RPC; clients use a thick library that handles sessions, caching and retries.

CreateSession(client_id, requested_ttl)        -> session_id, lease_expiry
KeepAlive(session_id)                          -> lease_expiry, events[]   # held open by server
CloseSession(session_id)

Acquire(path, mode=EXCLUSIVE|SHARED, session_id, wait_ms)
                                               -> granted, fencing_token
TryAcquire(path, mode, session_id)             -> granted | BUSY
Release(path, session_id, fencing_token)

Get(path) / Set(path, data, expected_version)  # compare-and-set on small data
Watch(path, events=[RELEASED, MODIFIED, DELETED, CHILDREN])
CheckToken(path, fencing_token)                -> valid | STALE  # like Chubby CheckSequencer()
  • Acquire is idempotent per session: retrying after a timeout returns the same grant, not a second one. (ZooKeeper's recipe handles this by putting a client GUID in the znode name, see deep dive 3.)
  • Set with expected_version is compare-and-swap. Many "locks" are better done this way (optimistic, no holder to die).
  • Events come back on the KeepAlive reply. Chubby piggybacks events and cache invalidations on KeepAlive replies, so one long-poll connection does everything.
