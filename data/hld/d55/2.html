Back-of-envelope estimation

The surprise in this design: lock operations are not the load. Heartbeats are. Let us show it with numbers. Assumptions are marked; real reference points come from the Chubby paper.

  1. Clients per cell. Assume one cell serves one datacenter with 50,000 client sessions (Chubby's snapshot cell had 22k direct clients plus 32k more through proxies, so this is realistic).
  2. KeepAlive rate. A session lease of 12 s (Chubby's default extension). The master holds each KeepAlive open and answers near the end of the lease, so roughly one KeepAlive per session per lease period: 50,000 / 12 s = ~4,200 KeepAlives/s.
  3. Lock acquires. Coarse locks change hands rarely. Assume 5% of clients re-acquire something every minute: 2,500 / 60 = ~42 writes/s. Even 10x that (420/s) is small. Chubby's real cell showed KeepAlives at 93% of RPCs and Acquire at only about 31 parts per million.
  4. Reads. Clients cache data and get invalidations, so reads that reach the master are mostly cache misses. Assume 1,000/s.
  5. Total master load: ~4,200 + 1,000 + 42 = ~5,300 RPC/s, 80% of it heartbeats. One server can do that, which is why Chubby has one master serving everything and four replicas only copying.
  6. Storage. Assume 200,000 nodes (locks + small files) x 1 KB average = 200 MB. Fits in RAM on every replica. Plus a write-ahead log and periodic snapshots on local disk.
  7. Write latency. One acquire = leader appends to log, sends to followers, waits for 2 of 4 followers (majority of 5 including itself) to fsync and ack. In one datacenter: network ~0.5 ms RTT + fsync 1-10 ms. Budget ~5-15 ms per acquire, which matches Chubby's "5-10 ms extra for the log".
  8. Bandwidth. 5,300 RPC/s x ~200 bytes = ~1 MB/s. Trivial. Replication traffic is writes x replicas x size = 42 x 4 x 1 KB = 170 KB/s.

Conclusion to say aloud: "Scaling this service means reducing heartbeat traffic (longer leases, proxies that merge many clients' KeepAlives), not making the consensus write path faster." Chubby's paper says exactly this: the key to scaling was cutting communication to the server, not server speed.
