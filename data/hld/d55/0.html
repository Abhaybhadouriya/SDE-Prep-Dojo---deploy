The story

Explain like I'm 5

A class has one toy microphone. Only the child holding the microphone may sing. The teacher keeps a notebook: "Riya has the mic". If Riya falls asleep holding it, the teacher waits a little, then writes "Arjun has the mic now" and gives Arjun a sticker with a bigger number, say 34. Riya's old sticker said 33.

Now the sound man only plays music for the highest sticker number he has seen. If sleepy Riya wakes up and starts singing with sticker 33, the sound man says "sorry, I already saw 34" and keeps her microphone off. The notebook is the lock service, the sticker is the fencing token, and the sound man is the storage that checks it.

One more thing: the notebook is too important to lose. So five teachers each keep a copy, and they only write a new line when at least three of them agree.

A distributed lock makes sure only one process in a cluster does something at a time: only one job runner sends the nightly invoice email, only one machine is the database primary, only one worker writes to a file. Google built Chubby for this in the mid-2000s; its OSDI 2006 paper describes how GFS and Bigtable use it to pick a master and to store small, critical metadata. Yahoo built ZooKeeper as an open-source cousin, and etcd (Raft-based) now backs every Kubernetes cluster.

Our gap analysis lists "design a distributed lock service" as a hard problem in AlgoMaster's list and in Grokking Advanced (Chubby deep dive), with self-reported asks at Google, Microsoft and Uber. Amazon's SDE-2 "Amazon Locker" HLD reports also ask about distributed locking for slot allocation. Even when it is not the whole question, it shows up as a 10-minute deep dive inside job schedulers, flash sales and booking systems.

From your world

You already know this problem from HA control cards in a router chassis: two route processors, one active, one standby, and a watchdog/heartbeat that decides when the standby takes over. The classic failure is "split brain": both cards think they are active and both program the line cards. A lock service is the software version of that arbiter, and a fencing token is like the line card refusing updates from a card whose "epoch" or generation number is older than the one it last accepted.

New words, once each: a lease is a lock with an expiry: you hold it only while you keep renewing it. A session is the client's registered, heartbeated relationship with the lock service; locks belong to sessions. A fencing token is a number that grows with every grant, so the resource can reject an old holder. Consensus (Paxos, Raft, ZAB) is how 3 or 5 replicas agree on one ordered log even if some fail. A quorum is a majority of replicas (3 of 5). Linearizable means every read sees the latest committed write, as if there were only one copy. An ephemeral node is an entry that the service deletes automatically when the session that created it dies. A watch is a one-shot "tell me when this changes" callback. Split brain is two nodes both believing they are the leader. The rest are in the glossary.

From your world

An ephemeral node is like a listening socket owned by a process: when the process exits, the kernel closes the socket and the port is free again, with no cleanup code. Linearizable reads are like reading a register on one CPU with proper barriers: no core can see a value older than the last completed store.
