Where Kafka, Kubernetes and Docker fit

  • Kubernetes runs on this design. Its state lives in etcd (Raft). kube-scheduler and kube-controller-manager in HA mode use Lease objects (coordination.k8s.io) for leader election, and every kubelet heartbeats by updating its Lease in the kube-node-lease namespace. Your own Deployments can use Leases too (client-go has a leader-election helper). See Kubernetes architecture.
  • Kafka used to depend on ZooKeeper for controller election and metadata; Kafka 4.0 removed ZooKeeper and uses KRaft, a Raft quorum inside Kafka. See KRaft cluster.
  • Kafka as an alternative to locks: if each key must be processed by one worker at a time, partition by key; a consumer group gives each partition exactly one consumer. Single-writer-per-partition removes the lock (with idempotent writes for the rebalance window). See consumer groups.
  • Docker / local practice: run a 3-node etcd or ZooKeeper with Compose (Compose) and kill containers to watch elections and lock hand-off.
$ etcdctl lease grant 30
lease 694d9a3c1b2e0a11 granted with TTL(30s)
$ etcdctl put --lease=694d9a3c1b2e0a11 /leader/invoice "worker-2:8080"
OK
$ etcdctl lock /locks/invoice -- ./run-invoice-batch.sh   # holds the lock while the command runs
$ etcdctl elect invoice-election worker-2                 # campaign for leadership

The lease ID above is an example; yours will differ. When the lease expires (no keep-alive), every key attached to it is deleted, which is the etcd version of an ephemeral znode.
