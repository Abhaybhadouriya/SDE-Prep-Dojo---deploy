Deep dives

1. Leases are timers, and timers lie: fencing tokens

A lock that never expires is useless: if the holder crashes, nobody can ever get it. So every distributed lock is really a lease: "yours until time T unless you renew". The trouble is that the holder can be paused for longer than the lease without knowing. Kleppmann lists GC pauses (reportedly several minutes in bad cases), page faults, CPU starvation, a stray SIGSTOP, and network delay: in one GitHub incident packets were delayed about 90 seconds. Checking "do I still hold the lease?" right before writing does not help, because the pause can hit between the check and the write.

The fix: fencing tokens. Every grant carries a number that strictly increases. The resource (database, file server, storage API) stores the highest token it has seen and rejects lower ones. In ZooKeeper use the czxid (creation zxid: the transaction id that created the lock-holder's sequential znode) or that znode's sequence number, both of which only grow. Do not use the znode's data version: each acquirer creates a brand-new znode whose version starts again at 0, so it does not increase across holders and cannot fence. In etcd, the key's revision (etcd's docs explicitly equate revision with a fencing token and Chubby's sequencer); in Chubby, the sequencer holds lock name, mode and lock generation number, and servers call CheckSequencer().

For resources that cannot check tokens, Chubby has a weaker defence: lock-delay. If a holder vanishes without releasing, the server refuses to give the lock to anyone else for a period the client chooses, bounded at one minute. It does not fix long pauses, but it absorbs everyday message delays and restarts.

Honest limit: etcd's own docs say its lock API cannot give mutual exclusion over an external resource by itself; the resource must validate versions. AWS's leader-election article says the same in other words: an election can briefly yield zero or two leaders, so the downstream system must stop the old one from interfering. A lock service plus a fencing check is the safe unit.

2. Sessions, KeepAlives, jeopardy and the grace period

Two Chubby words first. Jeopardy is the state a client enters when its own copy of the session lease runs out and it cannot reach a master: it is not dead yet, but it must stop trusting its cache. The grace period is how long it keeps trying (45 s by default) before it gives up and declares the session expired. Locks are tied to sessions, not to TCP connections. Chubby's flow is worth memorising because it shows how to survive leader failover without dropping everyone's locks:

  • The client's view of the lease is conservative: it assumes the lease ends earlier than the server thinks (it accounts for reply flight time and clock rate drift). Leases use elapsed time on each machine, not synchronized wall clocks.
  • The new master, on takeover, picks a new epoch number (so old-epoch messages are rejected), rebuilds sessions and locks from the replicated database, extends every session lease to the maximum the old master might have granted, and only then accepts lock operations.
  • ZooKeeper's equivalent: session timeout between 2x and 20x the server's tickTime; ephemeral znodes vanish when the session expires.
  • AWS's advice: check remaining lease time often (especially before side effects) and do not renew leases from a careless background thread that keeps renewing while the real work is stuck.

3. Queues instead of stampedes: the ZooKeeper lock recipe

A naive lock lets every waiter watch the one lock node. When it is released, all N waiters wake and race: the herd effect. ZooKeeper's recipe forms a fair queue instead:

  1. Create /locks/invoice/<guid>-lock- as ephemeral + sequential. ZooKeeper appends the counter.
  2. List children (no watch). If mine is the lowest, I hold the lock.
  3. Else watch my predecessor only with exists(). When it is deleted, go to step 2 (the predecessor may have died, not released, so re-check).
  4. Release = delete my node.

Why the GUID in the name? A create can succeed on the server, then the server crashes before the reply. The session is still valid, so the node exists, but the client does not know its name. On retry it lists children and looks for its GUID rather than creating a second entry. That is the idempotent-acquire requirement from the API section. Shared (read/write) locks use read- and write- prefixes: a reader waits only for lower write nodes.

4. Leader failover and split brain inside the service

  • Majority quorum: 5 replicas, majority 3. Two sides of a partition can never both have 3, so at most one side elects a leader. That is why sizes are odd: 4 replicas still need 3 votes but only tolerate 1 failure, same as 3 replicas.
  • Master lease: followers promise not to vote for another leader for a few seconds. The old leader stops serving reads when its own (conservative) lease timer ends, before anyone else can be elected.
  • Epoch / term numbers: every leader has a higher term; messages from an older term are ignored. Same idea as the fencing token, one level down.
  • Real numbers: Chubby's snapshot cell showed a 14 s failover; two elections took 6 s and 4 s, outliers 30 s. Across 700 cell-days they counted 61 outages, 52 under 30 s. etcd's FAQ recommends election timeout at least 5x the heartbeat interval and warns that slow disk fsync can cost the leader its leadership.

5. Scaling: coarse locks, proxies, partitioning

Chubby chose coarse-grained locks on purpose: held for hours or days (e.g. "I am the Bigtable master"), so the acquire rate is tiny and a short service outage barely matters. For fine-grained locks (per order, per seat, per locker slot) at thousands per second, Chubby's advice is: use the coarse lock to elect owners of lock groups, and let those application servers manage fine locks in memory with a simple monotonically increasing counter. That is exactly sharded ownership.

  • Proxies: a proxy holds one session to the cell on behalf of thousands of clients and answers their KeepAlives itself. Chubby notes a proxy serving N clients cuts KeepAlive traffic by N.
  • Longer leases under load: fewer KeepAlives per second at the cost of slower detection of dead clients.
  • Client caching with invalidation: reads hit the local cache; the leader sends invalidations (on KeepAlive replies) before a write completes. Chubby found negative caching (caching "file does not exist") significant too.
  • Partition the namespace: hash directories to different cells. Reads and writes per cell drop by N, but KeepAlives do not, because a client usually touches many partitions.
  • One cell per datacenter plus a global cell for rare global decisions; cross-region consensus adds 10-100 ms per write, so keep hot locks local.

From your world

Proxies merging KeepAlives is like BFD or LACP aggregation: instead of every flow running its own liveness probe, one session per link carries liveness for everything behind it. And "coarse lock elects owners of lock groups" is how a control plane hands out ownership of hardware tables to line cards, which then manage individual entries locally.
