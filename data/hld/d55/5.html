Architecture

One cell = 5 replicas spread across racks or availability zones, running a consensus protocol (Paxos in Chubby, ZAB in ZooKeeper, Raft in etcd). One replica is elected leader (master) for a master lease of a few seconds; it serves all reads and writes. Followers copy the log and vote. Clients find the leader through DNS (any replica answers "the master is X") and talk to it through a client library.

Acquire a lock, step by step

  1. Session first. W2's library opened session S7 and keeps it alive with KeepAlives. The session lease (say 12 s) is what keeps W2's locks alive.
  2. Acquire. W2 asks the leader for the exclusive lock /jobs/invoice. The previous holder W1's session expired, so the lock is free.
  3. Replicate. The leader appends "grant to S7, generation 34" to its log and sends it to all followers in parallel.
  4. Commit on majority. Leader + 2 followers have it on disk = 3 of 5. The entry is committed and applied. Slow followers catch up later.
  5. Reply with token. W2 gets token 34, which is the generation number. It is bigger than any token ever issued for this lock.
  6. Use the token. W2 sends its writes to storage with token 34. Storage remembers the highest token it accepted.
  7. Fencing. W1 was only paused (a long GC). It wakes up and writes with token 33. Storage rejects it. Without this check, two "holders" would both write.

Reads (for example "who is the GFS master?") are served by the leader alone without a consensus round. That is safe only while its master lease is valid, because the followers promised not to elect anyone else during that lease. This is the same trick Raft-based systems call lease reads.
