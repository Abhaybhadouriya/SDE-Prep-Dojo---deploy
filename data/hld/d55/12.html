  1. The lock service
  2. Client 2
  3. The storage, which has seen 34 and rejects 33
The lock service has no idea the write is happening; only the resource can fence it.

A 5-replica cell can keep granting locks with how many replicas down?

  1. 1
  2. 2
  3. 3
Majority of 5 is 3, so 2 can fail.

In a Chubby-like cell, what is most of the RPC traffic?

  1. Session KeepAlives
  2. Lock acquires
  3. File writes
Chubby's cell showed 93% KeepAlives; acquires were a few parts per million.

Why does each ZooKeeper lock waiter watch only its predecessor?

  1. To save disk
  2. Watches are limited to one per session
  3. So a release wakes one waiter instead of all (no herd effect)
Chained watches form a FIFO queue.

What does the grace period (45 s in Chubby) protect against?

  1. Clock drift between replicas
  2. Sessions and locks being lost during a short leader failover
  3. Slow disks
The client waits for a new master instead of declaring its session dead.

Why is Redis SET NX PX with a single master unsafe for correctness locks?

  1. Async replication can lose the key on failover, and its value is not a monotonic fencing token
  2. SET NX is not atomic
  3. Redis cannot expire keys
Both reasons are from Redis's own docs and Kleppmann's analysis.

You need 50,000 per-seat locks per second for a ticket sale. Best approach?

  1. One Chubby cell for all seats
  2. Redlock
  3. Conditional writes / sharded owners; keep the lock service for coarse ownership
Consensus leaders serialize writes; fine-grained locks belong with the data.
