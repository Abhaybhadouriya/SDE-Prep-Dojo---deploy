Data model

Hot path: the in-memory order book (one per symbol)

  • Price levels per side, sorted: bids high to low, asks low to high. A balanced tree / sorted map keyed by price, or, because prices move in ticks inside a price band, a plain array indexed by tick (O(1), very cache-friendly).
  • Each level is a FIFO queue (doubly linked list) of orders: that is time priority.
  • A hash map order_id -> node so cancel is O(1): find the node, unlink it.
  • Track best bid and best ask pointers so "top of book" is O(1).

Durable side: journal first, tables later

  • Sequenced journal (the source of truth): (seq, timestamp, symbol, event_type, payload), append-only, replicated before any acknowledgement leaves the exchange.
  • Derived tables (off the hot path, built by consumers of the journal): orders(order_id, client_order_id, member_id, symbol, side, price, qty, filled_qty, status, seq), trades(trade_id, symbol, buy_order_id, sell_order_id, price, qty, seq, ts).
  • Member limits and balances for pre-trade risk: loaded into the risk engine's memory at start of day, updated by the same event stream.

SQL vs NoSQL? Neither on the hot path: "I would keep the order book in memory and the truth in a replicated, sequenced journal, because a database round-trip and its locks would cost more than the whole matching budget; the derived trades and orders go to a relational database for reporting, because clearing and regulators query them with joins and need strong consistency."

The classic wrong answer: "Store the order book in a database table and run SELECT ... ORDER BY price, time FOR UPDATE for each new order." Every order would take a lock on the hottest rows in the system and wait for disk. It cannot be fair (lock order is not arrival order) or fast.
