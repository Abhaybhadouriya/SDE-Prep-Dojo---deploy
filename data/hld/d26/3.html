Key APIs

Brokers talk to exchanges over long-lived TCP sessions using the FIX protocol (Financial Information eXchange) or a faster binary protocol. Each session numbers its messages, so gaps are detected and resent. For the interview, a REST-like sketch is fine as long as you say "in reality this is FIX or binary over TCP".

# order entry (member/broker -> exchange), conceptually
NewOrder     { client_order_id: "brk42-000981",  # member's own id, used for dedup
               symbol: "INFY", side: "BUY", type: "LIMIT",
               price: 150025,                    # integer ticks: Rs 1500.25 = 150025 paise
               qty: 100, tif: "DAY" }
  -> ExecutionReport { order_id: "X7781", status: "NEW", seq: 88123401 }
  -> ExecutionReport { order_id: "X7781", status: "PARTIALLY_FILLED",
                       last_qty: 40, last_px: 150020, cum_qty: 40, seq: 88123477 }
CancelOrder  { order_id: "X7781" }   -> ExecutionReport { status: "CANCELED", ... }
ReplaceOrder { order_id: "X7781", qty: 60 } # reducing qty keeps time priority; raising price loses it

# market data (exchange -> everyone, UDP multicast, sequence-numbered)
AddOrder(seq, symbol, order_id, side, price, qty)
Executed(seq, order_id, qty, trade_id)
Cancel(seq, order_id)
Snapshot(symbol, last_seq, levels[...])     # for late joiners and gap recovery
  • Prices are integers (ticks or paise), never floating point. 0.1 + 0.2 is not 0.3 in binary floating point.
  • client_order_id gives idempotency: a broker that resends after a disconnect does not create a second order.
  • Real feeds are public: Nasdaq's TotalView-ITCH spec describes exactly these add / execute / cancel messages with sequence numbers.
