Back-of-envelope estimation

Assumptions (say them out loud): 5,000 listed symbols, 1 billion order messages per day (new + cancel + modify; most orders are cancelled, not traded, which is normal for markets with algorithmic traders), market open about 6 hours 15 minutes.

  1. Do not divide by 86,400. Traffic only comes during trading hours: 6.25 h x 3,600 = 22,500 s. This is the trap in this question.
  2. Average rate: 1,000,000,000 / 22,500 = about 44,000 messages/s.
  3. Peak: the opening minutes and big news. Rule of thumb 10x: about 450,000 messages/s across the exchange.
  4. Hottest symbol: traffic is skewed. If the busiest stock gets 3%: 450k x 0.03 = about 13,500 messages/s on one symbol at peak. One thread can handle this easily: the LMAX team reported about 6 million orders/s on a single thread. So one thread per symbol shard is not the bottleneck; disk, network and coordination are.
  5. Journal: about 100 bytes per sequenced event x 1 B = 100 GB/day, x 3 copies = 300 GB/day. Trivial for disks; the challenge is writing it with low latency, in order.
  6. Market data bandwidth: each message changes the book: 450k updates/s x ~50 bytes = 22.5 MB/s, about 180 Mbit/s per feed. Sent by multicast, it costs the same for 10 or 10,000 receivers. Sent by unicast TCP to 10,000 subscribers it would be 1.8 Tbit/s. That one calculation justifies multicast.
  7. Order book memory: say 1 M resting orders x 100 bytes = 100 MB. All books fit in RAM on one machine. "In memory" is not a stretch; it is the obvious choice.

From your world

Think of this like sizing a line card, not a web farm: a fixed working set that fits in memory, a strict per-flow order, and a budget in microseconds. The question is "how do I keep one core fed and never stall it", which is the same as a run-to-completion DPDK packet loop: one core per queue, no locks, no syscalls on the hot path. Where this breaks: a line card forwards a packet and forgets it, but an exchange must also journal every input durably (and replicate it) before it acknowledges, so disk and network writes sit right next to the hot loop.
