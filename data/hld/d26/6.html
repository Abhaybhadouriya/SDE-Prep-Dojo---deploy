Deep dives: the hard parts

Stop here for SDE-1: the order book structure, price-time priority with one worked match, and "single thread per shard + sequencer + journal" is a strong SDE-1 answer. Deep dives 2-4 are SDE-2. 5-6 are "good to know".

1. Matching, one order at a time (must know)

The book has asks A 200 @ 101, B 100 @ 101 (B arrived after A), C 300 @ 102, and a bid D 500 @ 100. Now order E: BUY 400 @ 102 (limit) arrives. Click through:

  1. Cross? E is a buy at 102. The best ask is 101, which is at or below 102, so E can trade. It takes liquidity: E is the taker; resting orders are makers.
  2. Time priority. At 101, A arrived first, so A fills first: 200 @ 101. The trade price is the resting order's price (101), not E's limit (102). E has 200 left.
  3. Next in line. B fills 100 @ 101. Level 101 is now empty and is removed. E has 100 left.
  4. Next level. 102 is still within E's limit, so C fills 100 @ 102 and keeps 200 resting. E is done: three trades, each emitted as a sequenced event. If E had quantity left, it would rest on the bid side at 102.

Here is the same thing as runnable Python (about 50 lines). Production engines use linked lists and tick-indexed arrays instead of bisect.insort, but the logic is identical:

from collections import deque
import bisect

class Book:
    """One symbol's order book. Prices are integers (ticks), never floats."""
    def __init__(self):
        self.bids, self.asks = {}, {}          # price -> deque of [order_id, qty]
        self.bid_px, self.ask_px = [], []      # sorted ascending price lists
        self.index = {}                        # order_id -> [order_id, qty] entry

    def submit(self, oid, side, price, qty):
        trades = []
        if side == "BUY":                      # cross while best ask <= my price
            while qty and self.ask_px and self.ask_px[0] <= price:
                qty = self._fill(self.asks, self.ask_px, 0, oid, qty, trades)
        else:                                  # cross while best bid >= my price
            while qty and self.bid_px and self.bid_px[-1] >= price:
                qty = self._fill(self.bids, self.bid_px, -1, oid, qty, trades)
        if qty:                                # rest the remainder on the book
            book, prices = (self.bids, self.bid_px) if side == "BUY" else (self.asks, self.ask_px)
            if price not in book:
                book[price] = deque()
                bisect.insort(prices, price)
            entry = [oid, qty]
            book[price].append(entry)          # FIFO = time priority
            self.index[oid] = entry
        return trades

    def cancel(self, oid):
        entry = self.index.pop(oid, None)
        if entry:
            entry[1] = 0                       # lazy delete, skipped when matched

    def _fill(self, book, prices, pos, oid, qty, trades):
        price = prices[pos]
        level = book[price]
        while qty and level:
            maker = level[0]
            if maker[1] == 0:                  # cancelled earlier
                level.popleft(); continue
            n = min(qty, maker[1])
            trades.append((maker[0], oid, price, n))   # trade at the RESTING price
            maker[1] -= n; qty -= n
            if maker[1] == 0:
                level.popleft(); self.index.pop(maker[0], None)
        if not level:
            del book[price]; prices.pop(pos)
        return qty

b = Book()
b.submit("A", "SELL", 101, 200)
b.submit("B", "SELL", 101, 100)
b.submit("C", "SELL", 102, 300)
b.submit("D", "BUY", 100, 500)
for t in b.submit("E", "BUY", 102, 400):
    print("trade maker=%s taker=%s price=%d qty=%d" % t)
print("best bid", b.bid_px[-1], "best ask", b.ask_px[0], "left at 102:", b.asks[102][0])

2. Determinism: sequencer, event sourcing and the hot standby (must know)

The engine is a state machine: state(n) = apply(state(n-1), input(n)). If apply is deterministic (no wall-clock reads, no random numbers, no iteration over unordered hash maps, no thread timing), then the input log fully defines the state. That gives three superpowers at once:

  • Recovery: load last night's snapshot, replay the journal from the snapshot's sequence number. LMAX described snapshots plus replay giving a full restart in under a minute.
  • Hot standby: a replica that consumes the same sequenced input has the same state at every sequence number. Failover = "standby, start publishing from seq N+1".
  • Audit: regulators ask "why did order X fill before Y?" You replay and show it.
  • Time inside the engine comes from the sequencer's timestamp on each input, never from the engine's own clock. Otherwise primary and standby would disagree (for example on order expiry).
  • When is an order "accepted"? Only after its input is durably replicated in the journal. The ack to the broker is gated on that. This is what makes "no acknowledged order is lost" true.
  • The sequencer itself must be highly available: a primary/backup pair or a small consensus group (Raft) that agrees on the log. It is one logical writer per shard; that is the price of a total order.

From your world

This is active-active redundancy with lock-step inputs, like two route processors that receive the same protocol messages in the same order so the standby is "hot" (NSR, non-stop routing). It is also exactly how Kafka followers work: they replay the leader's log in offset order. Where this breaks: one hidden source of non-determinism (a timestamp read, an unordered map) and the two copies silently diverge, so real systems checksum state at checkpoints.

3. Why single-threaded? The LMAX Disruptor (must know at SDE-2)

Your instinct says "use many threads to go faster". For a single order book, threads would have to lock the book, and lock contention, cache-line bouncing between cores and context switches cost far more than the matching itself. LMAX's business logic ran on one thread, kept all state in memory, and fed it through a ring buffer called the Disruptor. Parallelism comes from sharding symbols across cores and machines, not from threads sharing one book.

  • LMAX reported ring buffers of 20 million slots (input) and 4 million (output), sized as powers of two so the slot index is a cheap bit mask.
  • Pre-allocated slots = no garbage collection on the hot path. Sequence counters padded to their own cache line = no false sharing.
  • Read the original: Martin Fowler's "The LMAX Architecture" and the Disruptor technical paper.

From your world

You have written this already: a NIC descriptor ring. The driver advances a producer index, the NIC (or the consumer) advances a consumer index, the size is a power of two so wrap-around is idx & mask, and memory barriers replace locks. The Disruptor is that idea in Java, with several consumers chained in a dependency graph. Where this breaks: a NIC ring has one producer and one consumer, but Disruptor consumers form a dependency graph (journaller and replicator must both pass a slot before business logic reads it), so the "free slot" index is the minimum over several consumer sequences, not one tail pointer. Pinning the engine thread with isolcpus / taskset and busy-polling instead of sleeping is NAPI-style polling taken to the extreme.

4. Risk checks and money: why eventual consistency is wrong here (must know)

  • Before an order reaches the book, the exchange (and before that, the broker) must know the member can pay. A broker typically blocks the funds or margin when the order is placed and releases the unused part on cancel or fill. That is a hold, like a hotel card pre-authorisation.
  • The risk engine keeps each member's limits and current exposure in memory, updated from the same sequenced stream of fills. A database round-trip here would add milliseconds to every order.
  • Never "accept the order and check the balance asynchronously later": by then it may have traded, and trades cannot be undone. Balances on the trading path must be strongly consistent within the shard that owns them.
  • Price bands and circuit breakers: reject orders far from the last price; halt a symbol (or the market) when it moves too far too fast, and restart it with an auction.

5. Market data fan-out and fairness (should know)

  • Two tiers: colocated professional members get raw multicast feeds in the exchange's data centre. Retail apps (a broker's mobile app) get a conflated feed (latest price every N ms) via WebSockets from the broker's servers. This is where Kubernetes and normal web scaling come back in.
  • Fairness: exchanges try to give every colocated member equal network paths, because a shorter cable is a faster trade. "Fair" is a physical property here.
  • Snapshot + incremental: a late joiner takes a snapshot tagged with last_seq, then applies incremental messages after that sequence. The same trick as a database replica: base backup + WAL.

From your world

This is IP multicast with IGMP joins and application-level sequence numbers: think of how routing protocols use sequence numbers to detect a missed LSA and request it again. The "snapshot + replay from sequence" join is like a new OSPF neighbour doing a database exchange and then receiving incremental updates. Where this breaks: IGMP only gets packets to you; it never repairs a gap. Market-data recovery is application-level: the subscriber notices a missing sequence number and must fetch it from a retransmit server, or, if it is too far behind, rebuild from a separate snapshot channel.

6. Sharding, hot symbols and the opening auction (good to know)

  • Shard by symbol. Symbols are independent books, so they are the natural unit. Each shard has its own sequencer stream and engine thread. Put a few hot symbols on dedicated shards; group the long tail of quiet ones.
  • Cross-symbol orders (spreads, baskets) break the "one shard" rule. Real exchanges handle them with special combination books or by routing to one shard that owns the combo. Mention it; do not try to solve it with distributed transactions.
  • Opening auction: at the open there is a burst of orders that already cross. Instead of matching them one by one, the exchange collects orders for a few minutes and picks one price that maximises traded volume (a call auction), then switches to continuous matching. It turns the worst spike into a single batch.
